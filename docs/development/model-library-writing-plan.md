## 谱系改成综合解析（2026-09-27）

对照稿的规则不变。谱系不再只顺着论文自己的叙述写。一个模型是数据、架构、算法、预训练、后训练、评测一起做出来的，解析要把这些面融进同一篇里。

写之前先搜这篇真正用到的技术：知乎、小红书、Reddit 和技术社区里的评价与解析。搜索是为了学习行文和组织，也为了把机制讲清楚。社区原帖不贴进正文，也不写成「知乎认为」「Reddit 认为」的清单。

禁止用「数据角度」「架构角度」「评测角度」当小节标题，把看法分成一串。读者读到的是一篇综合解析。论文没写的那一面（没给数据配比、没给后训练配方）就在叙述里说明本页没有，不要编数字，也不要为了凑视角注水。短公告、模型卡、发布页仍然在文首标 `[OM-FREEPLAY] 材料不够 5000`。

原有门槛里，汉字 5000 只是完整论文的下限，用来拦住写太短的稿，不是写到这里就该停。2026-09-27 复算：没有短材料标记的谱系里，94 篇落在 5000 到 5599 字，8000 字以上是 0 篇。技术多的论文和技术少的卡片被写成了差不多长。

长度跟着这篇真正写清的机制走。架构、数据配比、训练日程、后训练、评测协议，论文里规定了几件，解析里就要把这几件讲完：它是什么，这篇怎么用，代价在哪。讲完之前不要因为计数过了 5000 就收笔。机制多的长文必须明显长于只报分数的卡片。短公告、模型卡、发布页仍然标 `[OM-FREEPLAY] 材料不够 5000`，不要为了拉开差距去编。

## 能写深的再拉长（2026-09-27）

现有谱系里，不少机制只被点了名字：公式没有按项写开，消融只写谁赢、不写关掉的是哪一个量，数据配比和损失只留一句。这些地方要补上，字数会变长。补的是论文里已经规定、解析还没写开的那一层，不是把同一句判断换三种说法。

要写开的，限于下面几种：

- 公式只被点名。把式子写出来，逐项说每一项在约束什么。
- 消融只报了胜负。写清关掉的是哪一个量，剩下的比较还成立不成立。
- 数据配比、日程、损失、采样、掩码，论文给了做法，解析只用一句话带过。把做法写到能复述的程度。
- 两种设计的差别可以落到同一步计算上，解析没有落下去。

不要写的：

- 把表里的分数再列一遍，或把上一节的判断再说一遍。
- 「这说明了重要性」「值得注意的是」这类空句。
- 论文没有的实验、配比、配方。没有的数如果还是写，标明「报告里没写，是纯猜的」。
- 短公告、模型卡、文首已经标了 `[OM-FREEPLAY] 材料不够 5000` 的页。材料不够就停，不要注水。

没有新的字数上限。一篇写到它真正规定的机制讲完为止。讲完了还是短，就保持短。

强调不要打在每一个数字上。一个段落里值得停一下的那一个数可以加粗，年份、页码、表号、随手出现的百分数不要加粗。该加粗的是机制名和判断，例如负特征值、safe-completion、路由器，而不是 **1** 和 **0**。

中文引语用直角引号「」。英文原文里的引号留在英文段。不要把整篇中文都写成直引号。

## 说法（2026-09-27）

不要写「先看配置」「源文 §4.2」「把 37B 复核一遍」这种交代自己怎么读稿的话。从模型本身说：从模型架构上看，从路由上看。

报告里没有的数，如果还是写出来，就写「报告里没写，是纯猜的」。不要写成「估算，报告没有给」。

## 标题要有层次（2026-09-27，叠在全部旧规则上）

一篇正常的谱系或对照稿，正文标题至少两级，正常是三级。序号和层级都要有。

- 篇名用 `#`，不编号。
- 大段用 `## 1.`、`## 2.`。
- 大段里的机制用 `### 1.1.`、`### 1.2.`。
- 机制里还要分开时才用 `#### 1.1.1.`。用不到就不要硬加。

不要写成没有数字的大段标题（例如「另外两条线与成本边界」），也不要在新的大段下面留下原来的 `### 10.`。正文里「第 N 节」要跟着改成新序号，只改一次，避免 7 先改成 4、再被 4 的替换扫掉。

禁止通篇只有 `## 1.` `## 2.` `## 3.` 这种同一级标题一路排下去。那样没有层次。

也禁止为了凑层级去拆。一个小标题下面如果只有两三行，就不要单列标题，把这几行并回上一段。标题少、底下有内容，好过标题多、底下空。审稿时看到「小标题一串、每节两三行」，整篇退回，不因为编号齐全就过。

短公告、模型卡可以只有两级。仍然不允许十几个 `##` 各管两三行。

其余不变：不是第二遍翻译；每节至少两段中文，这里的「节」指真正写下内容的那一级，不是空标题；链接先确认文件存在；术语、缩放和 TestingTime、评测时的规则不变。逗号、句号、冒号仍用英文标点。

## 疑惑重校 (2026-09-27, 用户驳回后立的新规, 叠在第四条上)

旧批和本批 xAI 稿的疑惑被用户整批驳回：绝大多数是图片内容、OCR 残字、文件名、页脚版权、价格名目、导航菜单这类**非技术细节**，不是第四条要的题。新规如下，新写和返工都按这个来。

1. **只写技术题。** 疑惑抓的是报告写得不清、混乱、有歧义、看不懂的**机制**处，以读者视角给出自己的推断和验证路径，指明模糊点落在哪。主型是机理推断型，另两型是横向对比型（与同族/竞品的技术决策对比，指出取舍）和 claim 质疑型（对「这个设计导致这个结果」的因果链提出机理层面的怀疑）。
2. **禁止拿非技术细节凑数。** 「这张图是什么」「这个残字哪来的」「文件名为什么对不上」「版权行哪年」不是疑惑，见即删。唯一例外：该细节直接影响对技术 claim 的核验（如数据图数值在抽取时丢失，导致核心 claim 核不了）——这种情况可以写，但落点必须回到 claim 本身，不是图。
3. **短材料不凑条数。** 公告、模型卡、规格页能挖出几条技术题写几条，不足 10 允许，禁止为凑 ≥10 硬编。完整论文仍 ≥10，目标 20。bi 的疑惑和 analysis 的材料标记用同一个逻辑：材料不够就停。
4. **读者锚点：四层都涉猎、都不深入。** 训练侧、推理与系统、架构与数学、评测与 Agent 都读过不少报告，但都不是专家。题的难度对齐「读完很多报告的人仍要翻到式子或表才敢答」；机制要指到式号、表号、图号，但不重讲教科书概念，推断要落到机制层面。
5. **父代理审法更新。** 逐条疑惑判 keep / rewrite / delete。看到拿图片、价格、OCR、文件名充数的，整篇打回，不因条数够、格式对就过。

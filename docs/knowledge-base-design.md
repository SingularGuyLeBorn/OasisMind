# 知识库设计手册

> 这份手册解决的是「面对一个还不了解的领域, 怎样把资料组织成可以长期生长的知识库」. 文章具体怎么写, 仍以 [`writing-spec.md`](writing-spec.md) 为准.

## 1. 先决定这座知识库要回答什么

新建知识库时, 最容易做的事情是搜到几十篇论文, 然后按年份、作者或缩写建文件. 这样很快就能得到一棵目录, 但读者仍然不知道这些工作为什么出现、彼此改了哪里. **目录应该表达知识关系, 论文只是支撑这种关系的材料.**

动手建目录前, 先写一段不超过 300 字的定位草稿, 回答四件事:

1. 研究对象是什么. 例如稀疏注意力研究的是「在不计算完整注意力矩阵时, 怎样选择仍值得建立联系的 token」, 而不只是收集带 sparse 名字的论文.
2. 这个领域反复受到哪些约束. 可能是计算量、显存、通信、训练稳定性、监督信号、在线分布或评测口径.
3. 读者读完后应该能做什么. 是能推导算法、辨认技术路线、复现系统、理解一个团队的版本演进, 还是建立全领域坐标.
4. 它和已有知识库怎样分工. 基础概念应链接到综合库, 团队版本信息可以链接到模型库, 新库只展开自己的核心问题.

这段定位供建树时使用, 不会原样放进最终首页. 收进来的材料需要帮助回答定位中的问题; 热门程度不能单独决定它是否进入主干.

## 2. 陌生领域先调研, 再建树

不了解一个领域时, 第一版目录一定带有猜测. 创建正文前先完成一轮轻量建模, 可以减少后续反复移动文件的次数.

### 2.1. 建立资料池

至少从四类来源观察同一个领域:

- 综述、课程和高质量长文用于发现术语、主要分叉与公认起点;
- 奠基论文和代表论文用于确认机制、公式与实验口径;
- 官方代码、技术报告和作者说明用于确认实现与版本变化;
- 社区讨论用于发现读者真正卡住的地方、复现差异和容易混淆的概念, 其中的判断仍要回到论文、代码或实验核实.

不要只搜领域名称. 还要分别搜索 `survey`、`tutorial`、`taxonomy`、`benchmark`、`limitations`、`comparison`、代表方法名和作者团队. 新领域通常没有一篇材料能给出完整结构, 需要比较几套分类法.

### 2.2. 给材料做关系卡片

每项代表工作先只记七个字段, 不急着写文章:

| 字段 | 要记录的内容 |
|---|---|
| 对象 | 它修改模型、数据、目标函数、推理过程还是系统调度 |
| 起点 | 它默认哪个 baseline, 沿用了哪些记号与假设 |
| 缺口 | baseline 在什么条件下失效或成本过高 |
| 改动 | 它真正改变的变量、模块或反馈信号 |
| 代价 | 新增了什么训练、推理、存储或验证成本 |
| 证据 | 哪组实验能检验核心主张, 口径能否与别的方法对齐 |
| 关系 | 它继承、并列、组合、替代或反驳哪些工作 |

卡片用于寻找稳定的分类轴. 两篇论文如果只因同年发布而被放在一起, 卡片通常会暴露它们实际解决了不同问题.

### 2.3. 找到领域自己的分叉轴

先列出可能的轴, 再选一条作为主目录. 常见的轴包括:

- **处理阶段**: 数据 → 预训练 → mid-training → 后训练 → 推理 → 服务;
- **作用对象**: 参数 → 激活 → KV cache → 上下文 → 工具 → 工作流;
- **信息或反馈来源**: 人类偏好 → reward model → verifier → 教师分布 → 自生成经验;
- **算法选择**: 静态结构 → 内容路由 → 学习型 indexer → 混合或残差路线;
- **系统层级**: 单算子 → 单机 → 并行训练 → 集群调度 → serving;
- **生命周期**: 训练时 → 部署时 → 跨任务持续积累;
- **历史版本**: 基础模型 → 专项模型 → 后训练模型 → 系统与开源产物.

**主轴必须能解释相邻章节为什么分开.** 其他轴放进章内比较表或交叉链接, 不要同时拿两条轴给同一级编号. 例如一级目录已经按训练阶段划分, 就不能在同一级突然插入一家公司的模型章.

### 2.4. 先画知识图, 后决定目录

把代表工作之间的关系写成一张临时图: `前置 → 分叉 → 组合 → 评测`. 随后把关系紧密、共享 baseline 和记号的节点收成一个家族. 目录是这张图为阅读而做的投影, 所以允许交叉链接, 不必强迫每项工作只有一种学术归属.

建树前做三次检验:

1. **新增检验**: 明天出现一篇新论文, 能否判断它进入哪条路线? 如果只能新建一个「其他」章, 分类轴还不稳定.
2. **删除检验**: 拿掉所有论文名, 目录是否仍然描述一个领域? 如果只剩空壳, 这是论文清单.
3. **讲解检验**: 能否用相邻两章的差别解释研究者为什么从上一条路线走到下一条? 如果不能, 顺序只是文件排序.

## 3. 不同知识库使用不同骨架

下面给出的都是骨架, 不是必须照抄的目录名. 一个知识库可能兼有两种属性, 但应选一种作为主结构, 另一种通过局部章节和交叉链接表达.

### 3.1. 综合教程型

适合 `llm-guide` 这类从基础走向完整系统的知识库. 主轴通常是**依赖关系与学习顺序**.

```text
_garden.md
01-表示与基础组件/
02-模型架构/
03-数据与预训练/
04-后训练/
05-推理与部署/
06-Agent与评测/
```

这一类库先建立读者后面反复需要的符号和概念, 再进入训练目标与系统. 同一个概念只在首次成为必要前置时完整解释, 后文链接回去. 章节不能按「有什么资料」决定, 而要按「缺少哪一步就无法理解下一步」决定.

### 3.2. 技术专题型

适合稀疏注意力、OPD、扩散语言模型、持续学习等围绕一个技术问题展开的知识库. 主轴是**共同 baseline 上的机制分叉**.

```text
_garden.md
01-问题与基线/
02-路线A/
  02-路线A.md
  01-代表方法.md
  02-代表方法.md
03-路线B/
04-训练与稳定性/
05-评测与边界/
```

先把 baseline 推到足以比较的位置, 再按「改了哪一个量」拆路线. 每条路线首页负责统一记号、共同目标和家族差异, 具体方法页完成推导、手算、实现、实验与边界. 时间线可以帮助叙事, 但只有当后一个方法明确修补前一个方法的缺口时, 才适合作为目录主轴.

### 3.3. 团队与项目谱系型

适合 DeepSeek、OLMo 这类围绕团队长期工作展开的知识库. 主轴是**技术主线与版本继承**, 不能只按发布时间排列产品.

```text
_garden.md
01-团队路线与共同底座/
02-模型架构与算法/
03-训练与后训练/
04-数据评测与基础设施/
05-开源仓库/
```

每个版本都要回看采用的基础模型、数据、训练目标和系统条件. 同一技术跨多个版本演进时, 技术首页讲连续变化, 版本页保留该版本的完整配置与实验. 开源仓库不是附录清单: 它应说明仓库在训练流水线中的位置、输入输出以及和论文的对应关系.

### 3.4. 课程与学习笔记型

适合 CS336. 主轴是**课程建立能力的顺序**, 但内容可以吸收课后形成的理解, 不需要按资料来源分区.

```text
_garden.md
01-tokenizer与数据/
02-Transformer与算子/
03-训练目标与优化/
04-并行训练系统/
05-后训练与评测/
06-综合实验/
```

这一类库的价值在于从局部组件走到可运行训练过程. 理论、代码和实验应在同一知识节点内互相对应, 不要另建「课程原文」「个人补充」两套目录.

### 3.5. 经典论文与阅读地图型

适合 classic-papers. 主轴是**研究问题与奠基关系**, 不是论文发表年份.

```text
_garden.md
01-表示与序列建模/
02-Scaling与数据/
03-对齐与推理/
04-检索工具与Agent/
05-系统与评测/
```

章首页回答这一方向解决了什么长期问题、几篇论文各自建立了哪块基础、后来的工作为什么仍引用它们. 单篇论文保留历史语境、核心机制和影响. 「经典」必须能说明经典在哪里, 不能把高引用量直接当成目录结构.

### 3.6. 工程系统型

适合 LLM Infra. 主轴通常是**数据流、资源流与系统生命周期**.

```text
_garden.md
01-硬件与性能模型/
02-数据和训练输入管线/
03-单算子与内核/
04-并行训练/
05-容错检查点与调度/
06-推理Serving/
07-观测评测与容量规划/
```

系统文章应沿真实执行路径解释数据、张量、通信和状态怎样移动. 算法名称只有落到资源约束后才有意义. 训练和推理共享的组件可以共用基础章, 但性能模型、并行目标和故障形态要分别说明.

### 3.7. 问题集与面试型

适合 LLM Interview. 主轴是**能力域与问题依赖**, 不是问答来源或公司名称.

```text
_garden.md
01-架构与数学/
02-预训练与数据/
03-后训练与强化学习/
04-推理系统与性能/
05-Agent与业务场景/
```

每个节点先给问题成立所需的共同背景, 再进入推导、反例和工程判断. 问题不能只是把综合教程改成问句; 它应逼迫读者完成比较、估算、定位故障或设计实验.

### 3.8. 模型与产品目录型

适合 model-library. 主轴是**组织 / 家族 / 版本**, 目标是快速查清模型用了什么, 与专题库分工.

```text
_garden.md
组织或模型家族/
  家族首页.md
  版本A.md
  版本B.md
```

家族首页说明版本关系和共同技术底座, 版本页记录可核查的架构、训练、上下文、发布物与评测. 某个机制需要完整推导时链接到专题库, 不在每个版本页重复讲一遍.

## 4. 四类页面各自承担什么

| 页面 | 主要职责 | 不该承担的内容 |
|---|---|---|
| 花园首页 | 领域来由、全局坐标、主线关系、不同读法 | 逐篇摘要、裸链接清单、单个算法完整推导 |
| 章首页 | 一组路线共享的问题、对象、约束与比较口径 | 把所有叶子各缩写一遍 |
| 路线首页 | 共同 baseline、统一记号、分叉轴、典型方法关系 | 重复每篇叶子的公式和实验 |
| 叶子文章 | 一个能够闭合的论证单元 | 只有几段介绍、依赖上层才能成立的残片 |

文件结构固定使用三层知识树: 第一层章和第二层路线都必须是同名目录节点并包含同名首页, 第三层主题才允许直接成为叶子 Markdown. 这条规则与“是否已经有很多子页”无关;上层节点的职责是建立坐标和共同参照, 不是等叶子数量足够以后才补出来. 若第二层暂时只有一个三级主题, 仍要保留路线首页, 同时检查分类是否过窄、是否遗漏真正的同级方法.

**一页是否应该继续拆, 看论证对象是否已经变了.** 同一方法的动机、公式、训练和实验通常属于一个闭环, 篇幅再长也不必机械拆开. 当多个子方法共享足够多的前置内容, 或某个子问题已经拥有自己的论文谱系、公式体系和比较口径时, 它才应升级为非叶子节点.

反过来, 两三页都只有一千字左右、彼此必须来回跳才能看懂, 通常应该合并. 目录深度来自知识关系, 不来自文章数量.

## 5. 从资料到目录的实际流程

### 第一轮: 划边界

写定位草稿, 列出明确包含和交给其他知识库处理的内容. 初步收集综述、代表论文、官方实现和社区问题.

### 第二轮: 建坐标

制作关系卡片, 找到两到三套候选分类轴. 对每套轴做新增、删除和讲解检验, 选出主轴. 此时只写无编号的临时树, 避免过早被文件路径绑住.

### 第三轮: 选代表节点

每条路线先选 baseline、转折工作、当前代表和一个能暴露边界的反例. 一开始不追求收全. 如果一条路线只有一个孤立方法, 暂时作为章内小节; 材料增长后再升级节点.

### 第四轮: 写上层页面

先写花园首页和章首页的事实骨架, 检查它们能否解释所有叶子的位置. 上层写不出来, 往往说明分类只是名字相似, 此时应该重画树, 而不是用链接清单填满首页.

### 第五轮: 写叶子并反向修树

叶子写到公式、实验和失败条件后, 原先分类可能被材料推翻. 允许调整主树. 新库早期改结构的成本远低于维护两代平行稿的成本.

### 第六轮: 做交付检查

- 每个一级章都能用一句话说明与相邻章的差别;
- 每个一级章下面已经建立可打开的二级路线层, 每个二级路线下面至少有一个三级主题;
- 没有十几个方法直接堆在同一个目录;
- 没有按论文标题机械生成的平行目录;
- 共同定义和记号只在上层完整出现一次;
- 叶子可以独立完成一条论证, 链接不是正文的替代品;
- 一级、二级节点均使用同名目录和同名首页, 只有三级节点允许直接成为叶子;
- 编号、链接、图片和 frontmatter 符合 `writing-spec.md`;
- 首页与正文经过事实核查、去 AI 味和人工回读.

## 6. 可复制的建库规划底稿

这份底稿用于调研阶段, 不直接作为读者看到的首页模板.

```markdown
# <知识库名称>建库规划

## 定位
- 研究对象:
- 反复出现的约束:
- 读者读完能够:
- 与现有知识库的分工:

## 资料覆盖
- 综述 / 课程:
- 奠基工作:
- 当前代表工作:
- 官方实现与技术报告:
- 社区中反复出现的问题:

## 候选分类轴
1. <轴 A>: 为什么适合 / 哪里会冲突
2. <轴 B>: 为什么适合 / 哪里会冲突
3. 最终主轴:

## 临时知识图
- <baseline> → <路线 A> → <方法 A1 / A2>
- <baseline> → <路线 B> → <方法 B1 / B2>
- <路线 A> + <路线 B> → <组合方法>
- 统一评测口径:

## 临时目录
- 01-...
  - 01-...
  - 02-...
- 02-...

## 边界检查
- 新方法将按什么条件归类:
- 哪些内容只链接到别的库:
- 哪些节点材料不足, 暂不建文章:
- 哪些比较目前缺少统一口径:
```

## 7. 常见的坏结构

### 论文仓库冒充知识库

症状是目录里全是论文名, 首页按年份回顾. 修复时先找共享 baseline 和机制分叉, 论文退回到路线下的证据位置.

### 一层目录塞十几个编号

这通常说明缺少家族层. 先比较这些文章的作用对象、目标函数和信息来源; 能共享一套参照系的收进路线节点, 不能共享的分开.

### 为了三级而三级

只有一个叶子的目录、只放链接的首页、把同一篇文章按动机 / 方法 / 实验切成三篇, 都没有产生新的知识关系. 这种层级应合并.

### 同时使用两条主轴

例如前半按训练阶段, 中间改按公司, 末尾又加入论文年份章. 这种树无法稳定容纳新内容. 应选定一条主轴, 公司和时间用正文表格、标签或交叉链接表达.

### 首页补救错误目录

首页写得再长, 也无法修复叶子放错层的问题. 文件树和正文论证要一起调整. 同理, 目录正确也不意味着首页可以只剩链接.

### 两代稿件并行

两代目录同时存在会让链接、搜索和后续写作继续分叉. 重组时逐段迁移有效内容, 修正引用, 随后移除重复稿和跳转壳页.

## 8. 成型后的判断标准

一座合格的知识库, 读者只看首页和侧栏就能知道这个领域由哪些问题构成; 进入章首页后, 能看见方法为什么分叉; 到叶子文章里, 又能把公式、实现和实验连成一条线. 新论文出现时, 维护者知道它该放在哪里, 也允许它用新的证据迫使旧分类发生变化.

模板给出判断顺序, 各知识库仍会形成自己的外观. **可以长期复用的是「对象—约束—baseline—分叉—证据—边界」这套思考方式; 现成的章节名称只适合它原本所属的领域.**

# Dream,Mercury,Gemini Diffusion,Seed

LLaDA 用学术评测回答了 8B 掩码扩散能做到什么程度.产品与实验室另外几条线要回答的是:开源 7B 怎么从 AR 初始化;代码补全能不能到四位数 tokens/s;前沿实验室愿不愿意公开一张扩散对照表.四条工作的目标不同,共同出现并不能推出「2025 年扩散已经全面超过 AR」.

移位,退火和 WSD 等改编方法见[从自回归改编](../../5-训练-后训练与迁移/5.1-权重迁移与范式转换/5.1.1-从自回归权重改编.md).各家的吞吐数字只在自身协议内成立.开源代码模型 [DiffuCoder](../../5-训练-后训练与迁移/5.3-后训练与任务评测/5.3.2-代码模型的训练与评测.md) 使用单独的检查点,不属于这四种交付形态.

## 1. Dream 7B:开源权重里的改编样板

港大 NLP 与华为诺亚,arXiv:2508.15487.离散吸收态.权重从 Qwen2.5 7B 初始化,保持移位,按上下文重标定每个掩码位的噪声.继续预训练作者写成 580B token,Table 1 写作 0.6T.发布 Base 与 Instruct,推理接口是 `diffusion_generate()`.1B 尺度上扫过初始化,移位,噪声重标定,再接到 7B.学习率太大冲掉从左到右的知识,太小扩散训不动.

Table 1 带 $*$ 表示 Dream,LLaDA 8B,Qwen2.5 7B,LLaMA3 8B 同一评测协议.摘关键列(括号内 shot):

|---|---|---|---|---|
| 类型 | 扩散 | 扩散 | AR | AR |
| 训练 token | 0.6T | 2.3T | 18T | 15T |
| MMLU (5) | 69.5 | 65.9 | 71.9 | 63.5 |
| BBH (3) | 57.9 | 47.4 | 63.9 | 62.7 |
| GSM8K (8) | 77.2 | 70.9 | 78.9 | 55.3 |
| MATH (4) | 39.6 | 30.7 | 41.1 | 18.0 |
| HumanEval (0) | 57.9 | 32.9 | 56.7 | 35.4 |
| MBPP (4) | 56.2 | 39.0 | 63.6 | 49.2 |
| Countdown (8) | 16.0 | 13.2 | 6.2 | 3.7 |

通用任务上 Dream 贴近 Qwen2.5,MMLU 差 2.4 点,GSM8K 差 1.7 点,HumanEval 略高.规划任务上扩散两列都明显高于两列 AR:数独 81.0 对 21.0 不是边角.作者把原因放到「多约束要同时满足」:从左到右写到一半无法回头改已经提交的数字,掩码扩散可以整盘一起擦.这是机制假说,表只证明这三道题上差距存在.

LLaDA 原论文 Table 1 的 GSM8K 是 4-shot 的 70.3,HumanEval 是 35.4.Dream 这张 $*$ 表把 LLaDA 写成 8-shot 70.9 和 HumanEval 32.9.两套 harness 不要减出「LLaDA 退步了」.讨论 Dream 对 LLaDA 用本表;讨论 LLaDA 对 LLaMA3 用 Nie et al. 的 $*$ 表.

Table 2,SFT 之后.Dream 用 180 万对,3 epoch;LLaDA 450 万对;Qwen2.5 / LLaMA3 有 RL.

| 任务 | Dream 7B | LLaDA 8B | Qwen2.5 7B | LLaMA3 8B |
|---|---|---|---|---|
| 后训练 | SFT | SFT | SFT+RL | SFT+RL |
| 对齐数据 | 1.8M | 4.5M | 1M / 0.15M | — |
| MMLU | 67.0 | 65.5 | 76.6 | 68.4 |
| GSM8K | 81.0 | 78.6 | 91.6 | 78.3 |
| Math | 39.2 | 26.6 | 75.5 | 29.6 |

| IFEval | 62.5 | 59.9 | 74.7 | 49.7 |

Dream Instruct 的 GSM8K 81.0 高于 LLaMA3 Instruct 的 78.3,仍低于有 RL 的 Qwen2.5.HumanEval 55.5 对 84.8,代码缺口大.LLaDA 1.5 的 VRPO 把 Instruct 的 HumanEval 从 49.4 拉到 52.4,仍到不了 84.8.后训练深度不同.

Countdown 上调扩散步数,作者给出质量和速度的折中:步数设在 5–20 时,可以同时比 Qwen2.5 7B 更快更好.这是规划题上的曲线,不是 HumanEval 的默认.步数旋钮见[采样](../../2-数学与生成机制/2.3-生成因式分解与采样/2.3.2-采样后验调度与重掩.md).

Dream 仍是全双向掩码扩散,不是 Mercury 那种系统级吞吐怪兽.评它用质量表,不要用 H100 tokens/s 去羞辱它.

Dream 的 CART 根据可见 token 与掩码位置的距离,调整每个掩码位置的交叉熵权重.同一个全局掩码率下,不同位置能够读取的局部上下文并不相同.近处的可见 token 按几何分布贡献更多权重,远处贡献较少.这一实现改变训练损失的逐位置加权,没有仅凭重标定名称就为网络增加独立的逐位置时间输入.

移位则是改编能否保住基座的开关.Qwen2.5 的每一层 $h_i$ 已经对准 $x_{i+1}$.若扩散损失改去让 $h_i$ 预测 $x_i$,等于把预测头的靶子挪一格,继续预训练要重新学位置几何.DiffuLLaMA 和 Dream 都选择保住移位.dKV-Cache 后来从解码侧证明:推理时若把移位搞反,Dream 的 GSM8K 可以掉到 32.68.那不是 Dream 原文的主表,但是同一几何的反面教材.

规划题上的优势不要外推成「扩散更会思考」.数独和 Countdown 的共同点是:若干约束必须同时成立,从左到右写到一半很难改已经提交的数字.全双向去噪可以整盘一起擦.写小说,写文档,写解释题,约束稀疏得多,这张表上的 81.0 对 21.0 不会自动出现.作者在 1B 尺度上先确认初始化与噪声重标定有用,再接到 7B;没有公开「去掉移位,其它全同」的 7B 完整对照表.机制判断可以写,因果结论要等那张表.

Instruct 只有 SFT,代码缺口对着有 RL 的 Qwen2.5.这和 LLaDA Instruct 落后 LLaMA3 Instruct 是同一类口径问题.Dream 的 180 万对比 LLaDA 的 450 万对更少,GSM8K 81.0 仍高于 LLaMA3 的 78.3,说明改编基座(Qwen2.5)本身数学就不弱.HumanEval 55.5 对 84.8 则说明:基座会写代码,不等于扩散 SFT 能把代码能力完整接过来.后训练深度不同.

## 2. Mercury Coder:把并行写进产品

Inception Labs,技术报告 arXiv:2506.17298.Transformer 骨干,扩散训练与生成,代码向.Mini 与 Small 两档.Artificial Analysis 在 NVIDIA H100 上测到 Mini 1109 tokens/s,Small 737 tokens/s,相对当时速度优化的前沿 AR 最高约 10 倍吞吐,质量落在同类快速代码模型区间.Copilot Arena 上作者称质量第二,速度第一.上下文官方写 32k,可扩到 128k.

报告几乎不公开参数量,训练 token,是否块扩散.能引用的是第三方吞吐和「粗到细并行改多 token」.开源全双向模型和商业代码专用栈不在同一条速度曲线上.

## 3. Gemini Diffusion:实验室演示,有一张官方表

Google DeepMind 将其标为探索未来能力的实验 demo.模型从噪声状态开始迭代修改整段文本,生成中途可以修正已出现的内容,官方演示主要覆盖编辑,数学和代码改写.

官方对照 Gemini 2.0 Flash-Lite(AI Studio 默认采样,pass@1):

| 基准 | Gemini Diffusion | Flash-Lite |
|---|---|---|
| LiveCodeBench v6 | 30.9% | 28.5% |
| BigCodeBench | 45.4% | 45.8% |
| HumanEval | 89.6% | 90.2% |
| MBPP | 76.0% | 75.8% |
| GPQA Diamond | 40.4% | 56.5% |
| AIME 2025 | 23.3% | 20.0% |
| Global MMLU Lite | 69.1% | 79.0% |

代码接近,知识与科学落后.速度:评测平均采样 1479 tokens/s(不含 overhead),overhead 0.84s.硬件未写.SWE-Bench Verified 是非 agent,单轮编辑,最长 32k.这些限定要跟着数字走.HumanEval 89.6 和 LLaDA 8B Instruct 的 49.4 不能放进同一句「扩散代码」:规模,数据,是否闭源,评测库都不同.

## 4. Seed Diffusion Preview:H20 上的 2146 token/s

ByteDance Seed,arXiv:2508.02193,代码模型.作者报 H20 上 2146 token/s,并自己写了不能和 Mercury / Gemini 横比:Mercury 用 H100 和私有集,Gemini 速度是混合任务平均,硬件未公布,系统提示约束格式也会抬速度.LiveCodeBench 用 v1–v6 共 1055 题以迁就未知基线协议.

扩散训练前 80% 采用掩码腐蚀,后 20% 加入插入、删除和替换增强,使模型学习处理错误的可见 token.模型不强制直接复制全部未掩码输入.后续还进行约束顺序轨迹训练和 on-policy 优化,推理则采用块级并行采样,读取已完成块的 KV.块划分在推理时选择,论文没有采用固定块长的专项训练.

Seed 同时使用掩码恢复、编辑增强、轨迹训练、块解码与专用推理实现.掩码项保留吸收态结构,编辑项允许长度与可见内容变化,两者不能全部压成同一个固定位置的 $Q_t$.编辑增强提供错误上下文的训练覆盖,轨迹训练调整生成顺序,缓存与系统实现降低推理成本,分别作用于不同环节.

## 5. 速度表怎么读

| 名称 | 数字 | 硬件 | 作者提醒 |
|---|---|---|---|
| Mercury Mini | 1109 tok/s | H100 | Artificial Analysis |
| Mercury Small | 737 tok/s | H100 | 同上 |
| Gemini Diffusion | 1479 tok/s | 未公布 | 不含 0.84s overhead |

分母,是否含 prefill,batch,是否约束输出格式,全部可能差一倍.这些数字只并列报告,不形成排名.开源 Dream 没有把 H100 tokens/s 写成主卖点,缺这一格不是「Dream 慢」,是论文没测这条产品曲线.

### 5.1. 失效

把 Gemini 的 HumanEval 89.6 和 LLaDA 8B Instruct 的 49.4 放在同一句「扩散代码」里:规模,数据,是否闭源,评测库都不同.

把 Seed 的编辑腐蚀理解成「回到均匀 $Q_t$」:编辑是后 20% 的增强,主过程仍是掩码.

把四条都当成可以自托管的开源 7B:Dream 是;Mercury / Gemini / Seed Preview 不是同一类交付物.

读完四条线,手里应有一张交付物卡.Dream:开源 7B 权重,质量表可核对,吞吐不是卖点.Mercury:商业代码模型,H100 上四位数 tokens/s,参数量和训练 token 未公开.Gemini Diffusion:实验室 demo,有官方对照 Flash-Lite 的表,硬件未写,知识向基准落后.Seed Preview:代码向,H20 上 2146 token/s,作者禁止和前两者横比,训练后 20% 允许改已写字.四张卡不能合成「扩散 LLM 已经」后面跟任何一个全能谓语.

数独那一格特别容易被截图传播.81.0 对 21.0 是真的,协议写在 Table 1 的 8-shot 上,没有任务微调.它证明的是:这道题上双向去噪比从左到右更顺.它不证明写博客,写邮件,写 API 文档也会出现同样的倍数.约束同时成立的任务,扩散有结构借口;约束稀疏的任务,借口消失.把借口当定理,下一张表就会打脸.Dream Instruct 的 HumanEval 55.5 对 Qwen2.5 的 84.8,同一对模型,另一道题.

商业吞吐数字还有一层「系统提示约束格式」的水份.Seed 自己写了:约束输出格式会抬速度.评测若强制 JSON 或强制短代码块,tokens/s 变好看,因为有效生成更规律,提前结束更容易.读 1479 和 2146 时,问是不是混合任务平均,含不含 overhead,批大小是多少.答不出这三问,数字只能当数量级.数量级已经有用:扩散解码可以到四位数 tokens/s.精确排名没有用.

把 Dream Table 1 的 LLaDA HumanEval 32.9 抄进 LLaDA 家族当主数字:那是 Dream 的协议.Nie et al. Table 1 是 35.4.

把 Countdown 步数 5–20 的速度优势抄到写小说上:那条曲线是规划题,短画布.长文档,全双向注意力每步 $O(n^2)$,步数少省的是前向次数,省不掉每步的整段注意力.

初始化来自 Qwen2.5 这件事,读表时要始终放在分子里.Dream Base 的 MMLU 69.5 对 Qwen2.5 的 71.9,差距不大,不能证明「扩散目标比 AR 更会学知识」;更像是改编保住了大部分知识,扩散阶段没有把基座冲光.Sudoku 81.0 对 21.0 则不太能用「基座本来就会」解释:同一张表上 Qwen2.5 只有 21.0.结构差在规划题上被放大,在知识题上被缩小.这是读改编论文时应有的默认姿势:先问这格分数有多少来自基座,有多少来自改生成过程.问不清.

Instruct 的 180 万对,3 epoch 是轻量后训练.Qwen2.5 Instruct 有 RL,代码 84.8.Dream 55.5 的缺口,优先解释成后训练深度,第二步才解释成「扩散不会写代码」.LLaDA 1.5 用 VRPO 把 HumanEval 从 49.4 拉到 52.4,步子不大,说明偏好优化不会自动变成代码特训.截至目前,还没有可验证奖励配合 Dream diffu-GRPO 的公开主表.

上一句限定来自:Dream 原文 Table 2 对照的是有 RL 的 AR Instruct,没有同数据,同后训练深度的配对实验.

Trip planning 17.8 对 3.6 是同一张规划表上的第三格.题目来自 Zheng et al. 2024,few-shot,无任务微调.扩散两列(Dream 17.8,LLaDA 16.4)都明显高于 Qwen2.5 的 3.6 和 LLaMA3 的 8.7.作者把 DeepSeek V3-671B 也拉来当参考,正文写在某些 Countdown 设定上 7B 扩散甚至能超过这个大很多的 AR.那是规划题上的观察.参数量差两个数量级的对照,只能用来刺激「结构可能值钱」这种假说,不能用来做产品选型.

0.6T 对 Qwen2.5 的 18T 同样不能直接说成样例效率.Dream 的知识主体来自 Qwen 的 18T,0.6T 是继续预训练.公平的分母是改编阶段花了多少,不是「Dream 总共只看了 0.6T」.LLaDA 8B 才是真正只看 2.3T 从头训的那一列.三列分母不一样,并排在 Table 1 里是为了让使用者看见改编之后还剩多少能力,并非为了做 token 效率竞赛.

推理接口叫 `diffusion_generate()`,不是 `generate()`.调用方要传步数,温度,是否 remask,不能假设 Hugging Face 默认因果解码能跑.开源权重的意义是可复现表上的数,并非把 Dream 丢进 vLLM 就出 1109 tok/s.那条吞吐曲线属于 Mercury 的栈.把开源 7B 和商业 Mini 合成「扩散 7B 已经四位数吞吐」,是把交付物错误合并了.

Base 表上 HumanEval 57.9 对 Qwen2.5 的 56.7,代码几乎打平;Instruct 表 55.5 对 84.8,缺口全在后训练.读 Dream 的人常只截 Base 的代码列当宣传,或只截 Instruct 的代码列当「扩散不会写代码」.两张表要一起截.规划列同理:Base 的 Sudoku 81.0 很强,Instruct 表根本没再报 Sudoku.任务换了,列就没了,不能把 81.0 抄进指令模型规格.

Mercury 几乎把模型规格当成商业机密.技术报告确认了 Transformer 骨干,扩散训练与生成,代码向,两档尺寸,32k 上下文可扩 128k.参数量,是否块扩散,训练 token,词表是否与某开源基座相同均未公开,因此缺少与 Dream 7B 做同协议质量比较的条件.现有材料证明并行修改多个 token 已能产品化,第三方在 H100 上测到四位数 tokens/s.「质量落在同类快速代码模型区间」来自 Artificial Analysis 的相对位置,HumanEval 与 Qwen 的同协议表并不存在.Copilot Arena 的「质量第二,速度第一」来自 arena 投票.三项结果对应不同评测协议.

Gemini Diffusion 的官方表要连着限定读.Flash-Lite 是 AI Studio 默认采样,pass@1.LiveCodeBench v6 30.9 对 28.5,代码略高;Global MMLU Lite 69.1 对 79.0,知识明显落后;GPQA Diamond 40.4 对 56.5,科学问答落后.作者把模型定位成 demo,用来摸未来模型,不是 Gemini 旗舰的替代规格.1479 tokens/s 不含 0.84s overhead:短样本上 overhead 会把有效吞吐打下来.硬件未写,所以这条速度不能进和 Mercury Mini 1109 的减法.SWE-Bench Verified 还加了非 agent,单轮,最长 32k.缺任何一条限定,数字都会被读成「DeepMind 的扩散已经全面打平 Flash」.表自己不支持这句.

Seed 的 KV 复用是一项推理选择.[论文 v1 §3.4](https://arxiv.org/html/2508.02193v1#S3.SS4) 明确指出,未采用块专项训练的模型复用已生成块的 KV 可能引入偏差;作者在其评测中没有观察到明显的质量下降,并推测约束顺序轨迹训练有助于这一表现.因此这里的实测可用性不能直接转成严格的缓存等价证明.吞吐还依赖 H20、代码任务、块长与内部推理实现,与 Mercury、Gemini 的数字需要保留各自条件.

Dream 的 `diffusion_generate()` 还决定了生态位置.调用方必须传步数,温度,remask,Hugging Face 默认 `generate()` 走因果解码,直接套会分布外.开源权重的意义是可复现 Table 1–2,不是把 7B 丢进 vLLM 就出现 1109 tok/s.那条曲线属于 Mercury 的栈.把开源 7B 和商业 Mini 合成「扩散 7B 已经四位数吞吐」,交付物错误合并了.反过来,用 Dream 没有四位数吞吐去否定 Mercury 的产品曲线,也是错误合并.四条线写成四张卡,错误合并发生时才能指出混在哪一格.

1B 尺度上的配方扫描值得当成改编论文的读法,而不是轶事.作者先在 1B 上确认初始化,移位,噪声重标定各自有用,再把配方接到 7B.7B 上没有公开「去掉移位,其它全同」的完整对照表,所以 7B 的 Sudoku 81.0 不能单独归因于移位或单独归因于噪声重标定.能写的是:改编有配方,配方在小尺度上消融过,大尺度上作为整包交付.把 7B 表上的规划优势写成「因为他们用了 CART」,因果链中间缺一张 7B 消融.机制判断见[五条性质](../../4-联合依赖与结构设计/4.2-联合依赖建模/4.2-联合依赖建模.md).

四条线的使用者提问可以收成一张清单.只有开源权重,要复现规划题:Dream,走 `diffusion_generate()`,抄 Table 1 的 shot.只要代码补全吞吐,可以接受闭源:Mercury,报数字时写 H100 和 Artificial Analysis.要看前沿实验室愿不愿意公开对照表:Gemini Diffusion 官方页,连着 overhead 和「demo」一起读.要看训练时故意允许改已写字:Seed,前 80% 掩码,后 20% 编辑腐蚀,吞吐写 H20.清单里每一问只指向一张卡.一张卡回答不了的问题,换卡.

上下文长度同样不能横比.Mercury 官方写 32k,可扩 128k.2.0 文内称 32k 内 flash 稳定.Gemini 的 SWE-Bench 限定最长 32k.Dream 主表不是长上下文表.把这些 32k 写成「扩散已经解决长文本」,忽略了全双向每步 $O(n^2)$ 的计算代价.块扩散把长文本从「一次擦整篇」改成「一块一块续」,这才是 32k 能站住的机制.没有块,没有文档边界切断,32k 双向去噪会在打包处作弊,也会在注意力上把延迟打爆.

Dream Instruct 的 180 万对,3 个 epoch,是轻量后训练.基座会写代码,不等于这点 SFT 能把代码能力完整接过来.

### 5.2. 把四个名字放进同一套概率语言

四个名字经常被并排写进「扩散语言模型」,但它们公开出来的对象并不相同.Dream 给出了权重、训练配方和评测表;Seed 给出了较完整的方法预览,同时展示了一套面向代码生成的系统;Mercury 主要公开产品能力与速度测量;Gemini Diffusion 则是一扇实验窗口.如果只按产品名比较,很容易把未知项自动补成自己熟悉的 LLaDA 配方.更稳妥的办法是先写出一个最小生成问题,再逐项问公开资料究竟填了哪些格子.

设目标序列为 $x_0=(x_0^1,\ldots,x_0^L)$,噪声状态为 $x_t$,其中 $t\in[0,1]$.最常见的吸收态掩码过程对每个位置独立地做

$$
q_t(x_t^i\mid x_0^i)
=\alpha_t\,\delta(x_t^i=x_0^i)
+(1-\alpha_t)\,\delta(x_t^i=m),
$$

这里 $m$ 是掩码符号,$\alpha_t$ 随噪声增强而下降.训练时抽一个 $t$,生成 $x_t$,模型根据整段带噪上下文预测被遮住的真值.一种简化写法是

$$
\mathcal L(\theta)
=\mathbb E_{x_0,t,x_t}
\left[
\sum_{i:x_t^i=m}w(t,i,x_t)
\bigl(-\log p_\theta(x_0^i\mid x_t,t)\bigr)
\right].
$$

这条式子同时暴露出四个不能省的问题.第一,噪声究竟只有掩码,还是也允许插入、删除、替换;第二,模型预测干净 token、反向转移概率,还是另一个等价参数;第三,一次反向步更新多少位置,更新后是否还能把低置信位置重新弄脏;第四,长度 $L$ 在生成前是否已经给定.只写「从噪声迭代去噪」,这四项仍然全空.

Dream 的公开描述可以放进上面的吸收态框架,并且明确强调上下文相关的噪声重标定.Seed 的前 80% 训练也以掩码腐蚀为主,后 20% 又加入 Levenshtein 编辑噪声,因此它的状态空间不再只包含「原 token 或掩码」.Mercury 与 Gemini Diffusion 的公开页面足以确认迭代式、并行式生成,却不足以确认它们采用了同一条 $q_t$、同一个预测目标或同一套重掩规则.这不是无关紧要的实现空白:噪声决定模型看过什么错误,预测目标决定每一步学什么,重掩决定推理时能否真正撤回已经提交的选择.

把模型输出统一记作 $s_\theta(x_t,t)$.若它预测干净分布 $p_\theta(x_0^i\mid x_t,t)$,采样器还要结合已知的前向过程计算从 $t$ 到 $s<t$ 的后验.以单个位置为例,

$$
p_\theta(x_s^i\mid x_t)
=\sum_{x_0^i}
q(x_s^i\mid x_t^i,x_0^i)
p_\theta(x_0^i\mid x_t,t).
$$

产品展示的「整段文字不断变清晰」只描述外部行为.

吸收态掩码、离散替换噪声、插删改演化,以及分块生成配合局部修订,都能产生相似视觉效果.Mercury 和 Gemini 的公开材料并未列出前向核与反向参数化.

### 5.3. Dream 的难点不是加一个掩码符号

从头训练掩码扩散模型时,网络从一开始就习惯双向带噪输入.Dream 的问题更别扭:Qwen2.5 已经通过海量自回归数据学会用左侧前缀预测下一个 token,现在要让同一组权重处理任意位置被挖空的序列.直接换损失会同时改变输入分布、可见范围和隐藏状态对应的预测位置.模型刚学会的语言知识没有消失,但读取这些知识的坐标系变了.

所谓保留移位,可以从标签对齐看清.自回归训练通常用位置 $i$ 的隐藏状态预测 $x_{i+1}$.若改编时突然要求同一隐藏状态恢复 $x_i$,输出头收到的语义角色便整体左移.网络当然可以重新学,代价是把有限的继续预训练预算花在重新对齐上.保留移位相当于承认基座内部已经形成稳定约定,扩散阶段围绕这个约定安排输入与标签.它不能保证知识毫发无损,却减少了一种纯坐标变化.

![Dream 的移位预测与双向可见范围](../images/fig-dream-shift-v2.png)

> 图 2:自回归模型与 Dream 都用 $h_i$ 预测位置 $i+1$,区别在于因果与双向注意力的可见范围;依据 [Dream v1 Figure 2、§4.1](https://arxiv.org/html/2508.15487v1#S4.SS1),输入和目标使用五位置教学示例.

图 2 解析:

- 输入位置 0–4 与目标位置 1–5 对齐,例如 $h_1$ 对应目标位置 2.灰色 M 表示输入中的掩码,其真值 B、D 仅放在目标侧.
- 因果矩阵只开放包含对角线的下三角,双向矩阵开放全部位置.Dream 的 $h_1$ 能读取输入位置 3 的 C,同时保持对目标位置 2 的预测映射.
- Dream 的重构损失只计目标位置 2、4,但所有输入位置参与上下文计算.S 是可见前置 token,图示没有展开批次填充或末端边界处理.

上下文相关噪声重标定处理的是逐位置训练权重.记输入长度为 $N$,掩码符号为 $m$,当前位置为 $n$.[Dream v1 §4.2 式 (4)–(5)](https://arxiv.org/html/2508.15487v1#S4.SS2) 将普通的时间权重替换为

$$
w_n=\frac12\sum_{i=1}^{N}\mathbf1[x_t^i\ne m]\operatorname{Geo}(p,|n-i|-1),\qquad x_t^n=m.
$$

求和只包含可见位置,距离最近为 1,因此几何分布的自变量从 0 开始.其参数 $p$ 控制距离衰减:较大 $p$ 让权重更集中于附近的可见 token.训练时先按全局时间采样带噪序列,再由这条序列的可见位置计算 $w_n$,乘到位置 $n$ 的重构交叉熵上.**改变的是损失加权,不是为每个位置重新生成一条输入腐蚀轨迹.**

用五位置输入 `(A,M,M,M,E)` 手算,取教学参数 $p=0.5$,并采用 $\operatorname{Geo}(p,k)=p(1-p)^k$.位置 2 到可见位置 1、5 的距离分别为 1、3,于是 $w_2=(0.5+0.125)/2=0.3125$.位置 3 到两端的距离均为 2,得到 $w_3=(0.25+0.25)/2=0.25$.位置 4 与位置 2 对称,权重同为 0.3125.若三个位置的交叉熵均为 2,加权总和为 $0.3125\times2+0.25\times2+0.3125\times2=1.75$.这些数是说明距离加权的教学例子,不代表论文采用的超参数或实测损失.

![Dream CART 的距离贡献与逐位置加权损失](../images/fig-dream-cart-v1.png)

> 图 3:Dream CART 从可见位置计算距离权重,再与掩码位置的交叉熵逐项相乘;依据 [Dream v1 Figure 3 与式 (4)–(5)](https://arxiv.org/html/2508.15487v1#S4.SS2),五位置输入和数值为教学示例.

图 3 解析:

- 上方 A、E 是当前可见 token,M 是掩码.两端分别向位置 2、3、4 提供距离贡献,表中贡献尚未乘以公式的 $1/2$.
- 下方两条分支使用同一带噪输入:网络计算重构交叉熵,距离分支计算权重.二者在逐项乘法处汇合,得到三个位置的损失,求和为 1.75.
- 权重进入损失而非 Transformer 的时间输入.图中省略词表预测与真值标签,交叉熵数值 2 仅用于手算,不代表模型测量结果.

位置权重不要求相加为 1.它控制各项损失的贡献,并非 token 类别概率或选择位置的概率.可见 token 的距离也只是上下文信息的代理:近处 token 未必提供答案,远处约束也可能重要.CART 的收益需要通过消融检验,不能把这个距离公式直接视为真实条件熵的计算.

Dream 的规划表现也应沿着这个训练结构解释.以数独为例,一个格子的候选同时受行、列、宫约束.双向恢复可以在每一轮读取整盘当前状态,发现冲突后调整低置信格子.自回归模型并非不能规划,它可以在隐状态里计算、写草稿或调用搜索;差别在于普通输出接口把早期 token 当成已提交前缀.扩散状态把多个尚未确定的位置留在同一张画布上.这给全局约束提供了更合适的外部表示,但并未自动提供搜索深度.

设一轮中候选分布为 $p_i(v)$,最简单的并行提交会为许多位置同时选取 $\arg\max_v p_i(v)$.如果这些位置强相关,各自边际最优的组合未必联合可行.数独同一行两个格子可能都把数字 7 当成最高概率,逐格看都合理,放在一起便冲突.因此 Dream 的优势来源不能缩成「并行更多 token」.真正相关的是模型能在后续轮次重新观察组合,再修改尚未稳定的位置.并行带来画布,迭代才带来纠错机会.

公开表仍没有把这条因果链完全拆开.我们知道 1B 阶段做过配方扫描,也知道 7B 整体配方的结果;不知道每个部件在 7B Sudoku 上分别贡献多少.还不知道把 Qwen2.5 换成同算力、同数据的从头扩散基座会怎样.因此可支持的判断是「Dream 展示了 AR 基座向扩散目标迁移的有效路径」,而不是「上下文重标定单独创造了 60 个点的数独提升」.

### 5.4. Dream 的长度、步数与重掩要分开看

扩散生成常把长度藏在接口后面.自回归模型通过 EOS 决定何时停止,长度是生成轨迹的一部分.全序列掩码扩散通常先建立一个长度为 $L$ 的画布,再逐步填满.若 $L$ 由用户指定,任务就多了一个外部条件;若模型预测长度,长度误差会传播到整个画布;若画布留有 EOS 与填充位,采样器还要处理 EOS 后面的状态.

这会直接影响规划评测.数独答案格式固定,Countdown 和短行程规划也能给出相对稳定的输出预算,长度问题较轻.开放式写作没有这个便利.画布太短会截断论证,太长则出现重复、空尾或 EOS 位置摇摆.因此固定格式规划题上的能力与长文生成之间,隔着一个没有被主表充分测量的长度变量.

步数 $K$ 决定模型执行多少轮前向与采样.在长度为 $L$、每个位置只提交一次且各轮平均分配的简化情形中,每轮提交约 $L/K$ 个位置.实际提交数量由掩码日程和选择策略决定,可以均匀、前多后少或前少后多.减少 $K$ 通常降低前向次数,同时改变每轮需要确定的位置数;若多个相关位置在同一轮按独立分布采样,其联合约束可能更难满足.这种质量变化需要在固定模型、长度与采样器的条件下测量.

$$
\text{总成本}\approx K\cdot C_{\text{forward}}(L)+C_{\text{采样与调度}}.
$$

固定网络宽度和层数时,稠密注意力的 QK 与概率加权运算含有随 $L^2$ 增长的项,投影和逐位置前馈则含有随 $L$ 增长的项.**注意力的二次项不等于整个前向在所有长度下都由二次项主导.** 实际耗时还取决于算子实现、访存和硬件利用率.因此 Dream 的短规划速度曲线不能直接外推到 32k 文档.块采样缩小当前可变区域;具备适用缓存条件时还可减少历史重复计算,但已完成块固定后也限制了跨块回改.

重掩还要与「未提交」区分.有些采样器只是让掩码位置保持掩码,直到置信度够高;已经揭开的 token 从此固定.另一些采样器会把已揭开但低置信的 token 再次变回掩码.二者看起来都在反复刷新画布,纠错能力却不同.前者延迟承诺,后者撤销承诺.若训练从未见过错误的可见 token,推理时把错误 token 留在上下文再要求模型纠正,会造成训练与推理错配.Seed 的编辑腐蚀正面处理了这件事;Dream 的公开主线更适合描述为吸收态改编,不能把 Seed 的训练能力倒灌给 Dream.

### 5.5. Mercury:吞吐由哪些因素共同决定

理解 Mercury 的吞吐,可以分别检查模型一次提供多少位置的预测、采样器实际接受多少位置,以及推理系统如何执行这些计算.这三个层面共同影响速度,具体实现需要结合模型与服务的公开材料.

模型级并行指一次网络计算为多个位置提供分布.自回归解码在最朴素形式下每次新增一个 token,扩散状态可以让许多位置同时变化.采样级并行指调度器每轮究竟接受多少位置,低置信位置是否延迟或回退.系统级并行则包括批处理、算子融合、缓存、编译、服务调度与硬件利用率.最终速度近似满足

$$
\text{吞吐}
\approx
\frac{\text{每轮有效确定的 token 数}\times \text{批量}}
{\text{单轮前向时间}+\text{调度开销}}.
$$

这个式子解释了为什么「并行解码」不等于固定倍数加速.每轮并行提交很多 token,若随后因冲突反复修改,有效确定量并不高;网络对整段做稠密双向注意力,单轮时间也可能远高于一次 AR 增量解码;系统针对固定代码补全形态优化后,同一模型在通用聊天服务里未必保持数字.

代码是适合展示并行生成的场景.语法括号、缩进、类型名和重复标识符提供强约束,模型在局部上下文齐全时能一次确认多个位置.补全任务往往还给出前缀、后缀或文件上下文,未知区域比从零生成整份程序更集中.这可以提高一轮中高置信 token 的比例.不过代码也有长距离依赖:早期函数签名改变,后面调用都要同步;变量名看似高置信,选错后会污染多个位置.因此高吞吐并没有免除迭代校正,只是代码结构可能让每次校正更值钱.

Mercury 报告没有公开足够细节来回答它是否采用固定长度全画布、动态块、特定吸收态或显式编辑噪声.「粗到细」说明生成会迭代改善,不能据此断言使用了某篇论文的置信度重掩公式.参数规模也未公开,所以速度差不能归因于模型更小或更大.这些空格会让机制比较显得不够整齐,却是当前证据能到达的位置.

质量证据同样需要逐层对齐.Copilot Arena 的偏好票反映用户在特定交互中的选择,Artificial Analysis 的速度测量反映特定服务与硬件下的输出速率,论文基准反映固定数据集和判分器.三者可以共同说明 Mercury 已经是一项可用的代码产品,但不能拼成一个不存在的同协议实验.尤其不能用 arena 名次替代 pass@1,再拿 pass@1 推导训练目标.

上下文从 32k 扩到 128k 也没有公开回答每次反向步覆盖多大范围.模型能读取 128k 上下文,不代表同时对 128k 个输出位置做全双向迭代;输入上下文长度与生成画布长度是两回事.对代码补全而言,长上下文可能主要提供仓库线索,实际生成窗口仍短得多.没有输出长度分桶、首 token 延迟和端到端延迟,单个 tokens/s 只能告诉我们稳态生成很快.

### 5.6. Gemini Diffusion:能改字是一项可见行为,不是完整机制说明

Gemini Diffusion 的演示让人第一次直观看到闭源前沿模型在整段文本上反复修改.页面中的文字从不稳定状态逐渐成形,已经出现的片段也会变化.这足以支持「界面暴露了迭代修订」,却仍不能确定训练时是否使用掩码、随机替换、连续潜变量或编辑操作.产品层的可见状态还可能经过可视化处理,不能把屏幕动画逐帧当成模型内部 Markov 链.

从概率角度,能修改已显示 token 至少有两种来源.一种是该 token 尚未真正吸收到最终状态,界面提前显示当前候选;另一种是采样器确实执行回退,把已接受位置重新加入待生成集合.第一种更像「晚提交」,第二种才是「撤回提交」.如果不知道显示层与内部状态的对应关系,就不能用演示判断是哪一种.这也解释了为什么 Seed 要在训练过程里明确加入编辑腐蚀:它试图让模型在输入含有错误可见 token 时仍学会恢复真值,而不仅让 UI 看起来会改字.

官方表揭示了更有价值的能力形状.LiveCodeBench、HumanEval、MBPP 与 Flash-Lite 接近,说明这套生成方式在代码约束下没有明显失去可用性.AIME 2025 略高,但 GPQA Diamond 和 Global MMLU Lite 落后明显.一组结果可能同时受模型规模、训练数据、采样预算和后训练影响,无法只归因于扩散目标.它至少打破了「并行生成只能写局部模板」的简单印象,还没有证明同等训练条件下扩散优于自回归.

速度声明中的 1479 tokens/s 排除了 0.84 秒 overhead.设生成长度为 $N$,纯采样吞吐为 $r$,端到端时间可粗写成

$$
T(N)=0.84+\frac{N}{1479}.
$$

当 $N=100$ 时,纯采样只需约 0.068 秒,端到端却约 0.908 秒;有效吞吐约 110 tokens/s.当 $N=1000$ 时,采样约 0.676 秒,总时间约 1.516 秒,有效吞吐约 660 tokens/s.这不是对线上实测的替代,只说明固定开销在短回答中会支配体验.一个四位数稳态速度数字,无法单独回答用户点下发送后多久看到完整答案.

扩散界面还有一个自回归产品很少面对的问题:中间状态是否应该展示.若中间候选包含错误代码、敏感片段或互相矛盾的结论,边生成边展示会造成闪烁与误读;若等全部去噪结束再展示,极高吞吐仍可能缺少流式反馈.这属于交互层后果,并不改变模型原理,却会影响速度数字怎样转化为主观延迟.官方 demo 的价值正在于让这个问题可见.

SWE-Bench Verified 的非 agent、单轮限定尤其关键.真实修复流程常要检索文件、运行测试、阅读错误再修改,生成器只占其中一段.单轮编辑测的是给定上下文后产出补丁的能力,不能替代完整 agent 成功率.扩散对整块补丁并行修改可能很合适,但工具循环依然串行地受环境反馈约束.模型内并行没有消除任务外部的因果链.

### 5.7. Seed:把错误的可见 token 写进训练分布

标准吸收态前向过程将干净 token 变成掩码,已经进入掩码态的位置保持掩码.训练输入中未被遮住的 token 来自真值 $x_0$,不会被这个腐蚀核替换成错误的可见 token.对应的无撤回生成规则则让已提交 token 保持不变.推理若较早填错一个标识符,后续位置会读取这个错误上下文,而纯掩码训练没有主动覆盖这种可见错误.前向吸收与生成提交分别属于两个方向,需要分开定义.

Seed 后 20% 的编辑腐蚀改变了训练问题.设编辑操作序列 $e$ 包含插入、删除和替换,带噪序列写作

$$
x_t=\operatorname{Edit}(x_0;e).
$$

此时 $x_t$ 的长度可以与 $x_0$ 不同,可见 token 也可能来自错误替换.[Seed v1 §3.1 式 (3)–(4)](https://arxiv.org/html/2508.02193v1#S3.SS1) 通过连续执行编辑操作构造带噪序列,操作次数为 $k_t=\lfloor|x_0|\alpha_t\rfloor$,其中辅助编辑强度 $\alpha_t\in[0,0.1]$.**操作次数是腐蚀预算,不是最终最短编辑距离.** 插入后再删除同一 token 可以相互抵消;删除使带噪输入缺少原文位置,插入则增加多余 token.恢复原文需要处理长度变化和对应关系,不能直接沿用固定槽位的单步转移矩阵.

前 80% 的扩散训练采用掩码腐蚀,后 20% 加入编辑增强.式 (6) 保留掩码加权目标,同时加入编辑输入上的去噪损失,两项共同参与后期训练.这套课程先建立掩码恢复能力,再增加错误可见 token 的覆盖;80% 与 20% 是该工作的训练安排,收益仍需结合完整目标和采样配置理解.

作者提到不采用 carry-over,也应从训练目标理解.某些离散扩散参数化会把未被噪声破坏的位置直接从输入复制到输出,只要求网络预测真正变化的位置.在纯吸收态下,这种结构很自然:可见 token 就是真值,复制既正确又节省学习负担.一旦编辑腐蚀允许可见 token 是错的,无条件复制会让错误一直保留.放弃严格 carry-over,模型才有权改动可见位置.


### 5.8. 顺序轨迹与少步优化

编辑增强以后,Seed 还需要缩小有效生成轨迹的搜索范围.论文 §3.2 先用已有扩散模型为同一训练样本生成多条候选轨迹,按 ELBO 选择,再用保留轨迹上的中间状态训练恢复原文.训练目标的输入还经过类似编辑腐蚀的增强,不同噪声状态使用权重平衡.这一步将学习重点从任意排列转向筛选后的顺序,不是简单地指定左到右生成.

**on-policy 阶段同时优化采样步数与结果质量.** 当前模型根据训练 prompt 采样反向轨迹 $\tau$,目标为 $\mathbb E[|\tau|-V(\tau[0])]$,其中 $|\tau|$ 表示采样步数,$\tau[0]$ 表示最终结果,$V$ 是模型 verifier 的评价.最小化目标会偏向步数较少、评价较高的轨迹.论文 §3.3 用 log-derivative 方法优化评价项,并报告直接减少轨迹长度会使训练不稳定,因此采用渐进替代损失.质量反馈约束的是训练中的优化方向,每次输出仍需实际检验.

约束顺序与 on-policy 优化分别减少低效轨迹和调整实际采样行为.若只将 Seed 的速度归因于后期编辑增强,就会漏掉这两项训练变化以及推理实现.它们与缓存复用的关系也应分别检查:选择较顺序化的轨迹可能减轻训推差异,严格复用仍需要历史状态不依赖后续可变输入.

记当前块为 $b$,去噪轮次为 $r$,网络层为 $\ell$. 在第 $\ell$ 层,当前隐藏状态投影产生本轮的 $Q_b^{(\ell,r)},K_b^{(\ell,r)},V_b^{(\ell,r)}$,历史缓存提供前序块的 $K_{<b}^{\ell},V_{<b}^{\ell}$. 注意力沿 token 位置拼接历史与当前 KV,当前 Q 查询这组上下文. 当前块状态更新后,下一轮重新计算其隐藏状态和 Q/K/V,历史缓存仍作为只读输入.

![块扩散的逐轮重算与逐层缓存](../images/fig-seed-cache-v6.png)
> 图 4:块扩散中当前块逐轮前向、同层历史 KV 读取及完成块后的缓存扩展;依据 [Seed v1 §3.4](https://arxiv.org/html/2508.02193v1#S3.SS4) 展开计算关系,四 token 与两轮状态为教学示例.

图 4 解析:

- 上方状态条展示一次可能的提交顺序,实际采样步数和每轮提交数量由采样策略决定.
- 中间展开第 $\ell$ 层:当前 Q/K/V 从当前隐藏状态产生,历史 KV 从该层缓存读取. 后面的网络与采样得到下一轮输入,每轮都沿这条计算路径重新前向.
- 下方从当前块最终 token 建立各层 KV,追加后供下一块读取. 采样前的中间 KV 对应旧输入,不能直接冒充最终 token 的缓存;缓存构建可以独立前向或与相应计算合并.

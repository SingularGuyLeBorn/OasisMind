# 训练成本与调度

训练集群最容易制造一种错觉：只要 GPU 指标足够高，钱就没有白花。实际情况复杂得多。设备可以忙着计算 padding，可以反复执行故障后丢失的 step，可以在过大的数据并行规模下用更多卡换来很少的吞吐增量，也可以持续训练一个已经偏离目标的实验。监控面板里的忙碌与模型取得的有效进展之间隔着训练语义、扩展效率和可靠性三层关系。

成本口径要落到一次可验证的训练目标上。固定模型、数据版本、优化器、精度和目标验证指标后，设备时间、CPU、存储、网络与失败重跑才能归集到同一项工作。若比较的是预训练阶段，可以用达到指定 loss 所需的有效 token；若比较的是微调实验，可以用达到目标验证指标的一次完整运行。训练速度变化会影响每 token 的系统成本，batch 与学习率变化还会影响每 token 带来的统计进展，两部分必须同时进入计算。

## 有效进度比忙碌时间更接近目标

### 三个互不等价的利用率

设备分配率回答“多少 GPU 已经交给作业”，设备活跃率回答“多少采样窗口内有 kernel 运行”，计算效率回答“有效算术离硬件上限还有多远”。三者都高，训练仍可能浪费：重复样本、无效 padding、过量通信与即将回滚的计算都能让设备保持忙碌。作业侧还要记录有效 token、成功提交的 optimizer step、验证指标变化和最近的可恢复 checkpoint。

从成本角度看，最有用的分解是资源时间到有效进度的转换链：GPU·h 先经过排队、启动、数据等待、计算、通信、保存和故障重算，再产生有效 token；有效 token 又通过优化过程转化为 loss 或任务指标改善。链上任何一段变化，都可能改变最终成本。只用一个平均利用率会把原因混在一起。

### Goodput 把系统效率与统计效率接起来

Pollux 将训练 goodput 写成系统吞吐与统计效率的乘积。系统吞吐表示单位时间处理多少样本，统计效率表示这些样本相对基准 batch 能带来多少训练进展。增加 GPU 往往需要扩大 batch 才能喂满设备；吞吐会上升，单位样本带来的优化进展却可能下降。此时 samples/s 更高，不代表达到目标 loss 的时间更短。

设配置 $c$ 的吞吐为 $T(c)$，相对统计效率为 $E(c)$，可用

$$
G(c)=T(c)E(c)
$$

表示有效进度率。若 8 卡每秒处理 4000 个样本，$E=1$；32 卡每秒处理 11000 个样本，但大 batch 令 $E=0.62$，两者 goodput 分别为 4000 与 6820。卡数增加四倍，有效进度仅增至 1.705 倍。若设备单价相同，后者每单位进度的 GPU 时间反而更高。

### 完成成本必须包含失败路径

作业成本要覆盖整个实验历史。超参数搜索中提前终止的分支、基础设施故障导致的回滚、数据错误后的重跑、编译与 warmup 都消耗资源。对训练任务 $j$，可把直接资源成本写成

$$
C_j=\sum_r p_r t_{j,r}+C_{storage}+C_{network}+C_{ops},
$$

$r$ 表示 GPU、CPU 或内存等资源，$p_r$ 是单位时间价格，$t_{j,r}$ 是实际占用时间。再除以有效 token 或成功实验数，才得到可比较的单位成本。失败分类应保留责任域：用户代码、数据、设备、网络、调度器和外部依赖的治理方式完全不同。

## 调度处理的是带约束的作业组合

### Gang scheduling 与资源碎片

分布式训练通常需要一组 GPU 同时启动。集群即使空闲 64 张卡，也未必能满足一个要求同机 8 卡、同交换域 32 卡的作业。空闲设备散落在不同节点、型号或故障域时，会形成无法被当前队列使用的碎片。因而看板要同时展示空闲数量、可组成的拓扑形状和等待队列需求。

一个 32 卡作业等待时，让四个 8 卡短任务回填空隙可能提高利用率，也可能让大作业更晚凑齐资源。Backfilling 依赖运行时间估计与预约边界。估计偏短的作业越过预约时刻，就会破坏队列承诺；估计偏长则留下本可利用的空档。训练作业可利用历史 step time、剩余 step、保存时间和评估周期持续更新完成时间区间。

### 配额、借用与公平

静态配额能阻止单个团队耗尽资源，却容易在需求低谷留下闲置。更实用的策略包含最低保障、可借用余量与突发上限。团队 A 的保障份额暂时不用时，团队 B 可以借用；A 恢复需求后，调度器通过等待借用作业结束、缩容或抢占逐步归还。归还速度影响保障的实际含义。

公平也有多种分母。按 GPU 数公平会忽略不同硬件性能；按 GPU·h 公平会忽略作业扩展效率；按 dominant resource fairness 分配可同时考虑 GPU、CPU 与内存，却仍不表达训练进度。训练平台需要明确采用哪种口径，并把优先级、保障份额与借用规则暴露给用户。否则相同队列中的两个作业很难预测等待时间。

Kubernetes 的 `ResourceQuota` 可以限制 namespace 的资源总量，`PriorityClass` 与抢占决定高优先级 Pod 如何进入资源紧张的集群。这些机制提供控制积木，训练平台还需补上整组资源、拓扑、作业进度和 checkpoint 成本。仅给每个 worker 设置高优先级，无法表达一个训练任务必须完整获得 64 个成员才有用。

### 抢占要计算已经完成与尚未提交的工作

抢占成本由 checkpoint 年龄、保存与恢复时间、重新排队以及缓存冷却共同组成。设最近可恢复点距当前有 $A$ 分钟，保存耗时 $S$，恢复和 warmup 耗时 $R$，抢占后等待 $Q$，粗略损失为

$$
L_{preempt}=A+S+R+Q.
$$

异步保存时，$S$ 不一定全在关键路径上，但未提交 snapshot 不能计作恢复点。抢占策略读取最近的 committed checkpoint 时间戳，触发保存的时刻不能替代它。

短任务、高优先级生产修复与长期预训练之间常有冲突。可以先选择 checkpoint 新鲜、恢复快、缩容收益高的受害者；无法安全恢复的作业提高抢占代价。频繁抢占还会产生抖动，同一作业刚恢复又被移走。最小运行窗口、抢占冷却和每日损失上限能约束这种行为。

## 异构资源要用完成时间比较

### 峰值规格无法直接换算训练产能

两种 GPU 的峰值 FLOPS 比为 2:1，端到端训练吞吐可能受 HBM、互连、低精度格式、kernel shape 与软件栈影响。模型 A 在新卡上加速 1.8 倍，模型 B 的小矩阵和 all-to-all 只能加速 1.2 倍。调度器应保存 `(模型族, shape, 精度, 并行配置, GPU类型)` 的实测曲线，而非用统一换算系数。

价格比较也用有效进度。GPU X 每小时 4 元、goodput 为 100；GPU Y 每小时 7 元、goodput 为 220，则单位进度成本分别为 0.04 与约 0.0318。若 Y 只能以 8 卡整机申请而作业最佳规模是 2 卡，装箱与等待可能吃掉优势。供给粒度与拓扑进入最终选择。

### 扩展曲线决定分多少卡

对作业 $j$，在 $n$ 张 GPU 上的强缩放效率可写为

$$
\eta_j(n)=\frac{T_j(n)}{nT_j(1)}.
$$

若单卡不可运行，可选最小可运行规模 $n_0$ 作为基线。资源增加时，通信、较小 GEMM、数据等待与同步长尾会让 $\eta$ 下降。调度器分配额外 GPU 前，应比较边际 goodput：从 8 卡增至 16 卡若只增加 25% 有效进度，这 8 张卡交给另一个可线性扩展的作业通常更划算。

弹性训练允许改变数据并行规模，但 world size 变化会影响 global batch、学习率、数据顺序与 optimizer 状态。保持训练语义可能需要调整梯度累积；保持每卡 batch 又会改变 global batch。每个弹性点都要有数值验证，不能把进程数变化当作纯调度动作。

### 放置同时影响通信与碎片

将张量并行组放在 NVLink 域内、数据并行跨节点，通常比随机放置稳定。可是最紧凑的放置会留下难以使用的小块资源。调度器需要在作业局部性能与集群整体装箱之间取舍。可以为候选放置同时估算 step time、跨域字节、剩余拓扑形状和对已预约作业的影响。

异构池中的 checkpoint 迁移还涉及 dtype、kernel cache 和并行布局。目标卡支持相同模型不等于能够直接接管运行状态。迁移前要验证 checkpoint 可重分片、软件镜像可用、数值配方一致，并把编译与 warmup 时间计入迁移收益。持续时间很短的作业通常不值得跨池迁移。

## 成本归因需要稳定的数据模型

### 资源事件比月末账单更有解释力

月末总额只能说明花了多少钱。可操作的归因需要资源事件：作业提交、获得资源、开始运行、规模变化、保存、抢占、失败、恢复和完成。每个事件携带稳定的 job id、项目、团队、模型版本、环境、资源类型与故障域。设备占用按事件区间积分，避免从当前 Pod 状态倒推整月历史。

共享成本包括控制面、镜像仓库、对象存储、网络、监控和保留容量。分摊规则可以使用设备时间、读写字节、对象容量或请求次数，但规则要稳定且保留未分配项。把所有公共支出强行分完会制造虚假的精确度；未分配比例本身是标签质量和平台固定成本的指标。

### 指标标签要兼顾归因与基数

Prometheus 标签会形成时间序列组合。将原始用户 id、完整 checkpoint 路径或每个 sample id 放入标签，基数会快速膨胀。指标适合保存有界维度，如资源池、GPU 型号、队列、优先级和状态；高基数 job id 可放在事件日志与 trace 中，通过查询系统关联。

持续时间用 histogram 聚合不同实例的分布，counter 记录累计 GPU 秒、有效 token、失败 step 和读写字节，gauge 记录当前排队数、已分配设备与最近一次成功 checkpoint 的时间戳。查询端用当前时间减去时间戳得到年龄，也能发现更新逻辑停止；直接导出“距上次成功多少秒”依赖采集端持续刷新，故障时反而可能冻结。

### 一张作业损益表怎样读

某个 64 卡任务运行 20 小时，表面消耗 1280 GPU·h。时间线显示 1.5 小时等待数据、0.8 小时同步保存、一次故障回滚 40 分钟并恢复 20 分钟，真正产生已提交训练进度的时间为 17 小时。若并行 profile 又表明平均每卡只有 72% 时间用于有效 kernel，那么问题至少有三层：数据与保存造成 11.5% 墙钟损失，故障造成 5%，稳态执行还有通信与空泡。

处理顺序取决于可回收量和改造成本。数据等待若能通过预取降到 10 分钟，可回收 1.33 小时；checkpoint 改异步后若只节省 0.4 小时，就不应仅因实现新颖而优先。每项改动附带预期 GPU·h、风险、工程投入与验证期限，复盘时比较预测和实测。

## 用队列实验验证策略

### 回放保留到达、规模和运行时间相关性

训练作业并非独立同分布。大型预训练通常持续更久、需要更紧的拓扑，也更可能定期保存；短实验数量多，失败率和运行时间估计误差更大。回放数据要保留提交时间、资源形状、实际运行时间、优先级、用户或项目分组、抢占可恢复性和硬件兼容集合。随机打散会抹掉白天集中提交与发布前峰值。

历史运行时间存在删失：被取消或失败的作业没有自然完成时间。直接把已运行时长当总时长会低估长作业。可分别建模成功、失败和取消，或为未完成作业保留右删失标记。回放还要模拟 checkpoint 年龄，否则抢占看起来近乎免费。

### 同时报告效率、公平与可预测性

调度实验至少报告平均与 P95 排队时间、job completion time、slowdown、GPU·h、有效进度、抢占损失和拓扑碎片。平均完成时间改善可能来自长期压低大作业；因此还要按规模、团队和优先级分桶，观察保障份额是否兑现。

可预测性影响人的工作节奏。两个策略平均等待都为 30 分钟，一个多数作业在 20–40 分钟启动，另一个在 1 分钟与 4 小时之间摇摆，后者更难安排数据准备和协作。预约违约率、等待时间误差与规模变更次数能刻画这种差异。

### 故障注入检查成本闭环

在回放或预生产池中注入节点退出、网络降速、对象存储限流和调度器重启，观察资源是否释放、作业是否从已提交点恢复、配额是否重复扣减。计费区间若在 worker 消失后继续累积，会错误惩罚用户；若恢复出的替代 worker 没有关联原 job id，又会把一次任务拆成两份成本。

最终验收使用一段真实队列影子运行。新策略只给出调度建议，不实际改变资源，比较它与当前决策在相同供给下的预计结果；随后从低优先级资源池开始小流量执行。完成时间、单位有效进度成本、抢占损失和保障违约同时改善，才说明调度变化确实产生了收益。

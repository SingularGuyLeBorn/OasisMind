# 编译与内核：把计算图落到硬件

模型公式描述数值关系，硬件执行的却是带布局、tile、同步与数据搬运的 kernel。编译器需要在 shape、精度和设备约束下完成图优化、融合、内存规划与代码生成；内核则决定数据是否复用、访问是否合并、执行单元是否持续有工作。峰值 FLOPs 只有在这些条件同时满足时才可能兑现。

本章从计算图落到单个 kernel，再回到整条时间线。后续覆盖 tracing 与图捕获、算子融合、自动调优、Triton/CUDA 编程、attention 与 GEMM、量化 kernel、通信计算融合和动态 shape。优化必须同时检查数值误差、编译时间、缓存命中与回退路径。

## 导航

先理解 roofline 与 GPU 层次，再阅读具体 kernel；随后分析编译器怎样组合它们。microbenchmark 用于定位上限，端到端 profile 用于确认收益是否仍在关键路径。减少 kernel 数量不必然更快，融合造成的寄存器压力与并行度下降也要进入性能分析。

## 1. 从 eager 执行到可优化的图

eager 模式逐算子执行，框架在运行时创建张量、调度 kernel。编译器要优化跨算子数据流，先得到计算图或中间表示 IR。tracing 用示例输入记录实际执行路径，遇到数据相关控制流可能只捕获一条分支；字节码/源码分析能够保留更多语义，却需要处理 Python 动态行为。图捕获失败时通常产生 graph break，前后片段分别编译，中间退回 eager。

图不是越大越好。大图给融合、常量折叠和内存复用更多空间，但编译时间、峰值编译内存与缓存键复杂度上升；动态 shape 还可能触发反复重编译。服务启动和短训练若只执行几次，编译成本可能无法摊销。本章把编译时间、命中次数与运行收益并列，而不是只报告稳定后的最快一轮。

### 1.1. Guard 决定编译结果何时还能用

编译器对 dtype、device、rank、stride、部分维度和 Python 值建立 guard。新输入满足 guard 时复用已编译程序，不满足则重新编译或 fallback。把所有维度固定能生成更激进的专用 kernel，却会为不同 batch/序列长度建立大量变体；全部动态则可能失去 tile、展开和内存规划机会。

推理请求长度天然变化，常用 bucketing 将 shape 映射到有限区间，配合 padding 复用编译结果。padding 增加无效计算，桶太细又增加编译和缓存压力。选择桶边界时应依据线上长度直方图，计算每个桶的 padding token、命中率和编译版本数。

## 2. 图优化改变了哪些数据移动

常量折叠在编译期计算不随输入变化的表达式；公共子表达式消除复用相同结果；dead-code elimination 删除没有消费者的值。对 GPU 更关键的是融合和内存规划。两个逐元素算子分开执行，会让中间张量写入并读回 HBM；融合后可以保存在 register 中。若中间有 $N$ 个 BF16 元素，省下一次写加一次读约为 $4N$ byte。

融合边界受语义和资源限制。带归约的 softmax、LayerNorm 需要线程间同步；随机数、别名写入和数据相关分支也会限制重排。融合更多算子会延长临时值生命周期，增加 register，甚至导致 spill 或 occupancy 下降。因此编译器的成本模型需要同时估计省下的 launch/HBM 与新增的片上压力。

内存规划依据张量生命周期复用 storage。若 A 在时刻 $t$ 后无消费者，后续同 dtype/对齐要求的 B 可以占同一块空间。训练反向、view/alias 与异步 stream 会让生命周期判断复杂：一个 Python 对象不再使用，不等于设备 kernel 已完成访问。错误复用会破坏数值，过度保守又提高峰值显存。

## 3. Lowering 把算子落到 tile

高层 IR 表示矩阵乘、归约或 attention；lowering 将其映射为设备循环、tile 与内存层次。对 $C=A B$, kernel 选择 $T_M,T_N,T_K$, 让 A/B tile 从 HBM 经 L2 搬到 shared memory，再由 warp 送入矩阵指令，accumulator 留在 register。不同 shape、dtype 和布局需要不同参数。

自动调优生成候选配置并在目标硬件实测。候选过少会错过好配置，过多则编译和 benchmark 昂贵。缓存键至少包含硬件架构、shape/stride、dtype、编译器版本与相关选项；否则换驱动或布局后复用旧结果可能退化甚至错误。离线调优产生的数据库需要版本化，并保留 fallback。

### 3.1. Triton 与 CUDA 各自暴露什么

Triton 让作者按 program instance 表达 block 级张量操作，编译器负责向量化、共享内存和指令生成，适合快速写融合算子与可调 tile。CUDA 暴露 thread/block、shared memory、warp primitive 和更细的架构能力，能进行高度定制。二者都不能绕过硬件约束；抽象层不同，只是由谁负责排布细节不同。

一个 Triton kernel 的 `BLOCK_M`、`BLOCK_N`、`num_warps` 仍然决定并行度与资源。写出功能正确的代码只是第一步，还要检查 mask 边界、访存合并、register、occupancy 与数值精度。CUDA 手写 kernel 同样需要与库实现比较，避免为规则 GEMM 重复实现已高度优化的路径。

## 4. 专用 Kernel 为什么有效

FlashAttention 的主要改动是分块与在线 softmax，让 score/probability 不完整落到 HBM；它保持精确 attention 语义，却改变数据流。Paged attention 进一步根据页表读取离散 KV block，适应在线请求的非连续缓存。量化 kernel 将低比特权重读取、反量化和矩阵计算融合，省下权重带宽，但 scale/zero-point 布局与 group size 会影响额外工作。

专用化建立在假设上。某 kernel 可能只支持 head dimension 集合、连续 stride、特定 causal mask 或 GPU 架构。输入不满足时要 fallback。系统必须监控 fallback 比例和 shape；只对主流 shape benchmark 会漏掉线上最慢路径。新增 kernel 的验收矩阵应覆盖正常、边界、空张量、非整除和极端数值。

数值验证不能只比较一次随机输入。低精度累加、指数近似、归约顺序都会产生误差。按输出选择绝对/相对误差、余弦相似度或任务级指标，并与高精度参考对比。对 softmax 测大正负 logits，对归约测长向量和消去，对量化测异常通道。性能优化若改变随机数消费顺序，也要说明可复现性边界。

## 5. 编译、通信与动态执行

分布式图包含 collective。编译器可以重排通信与计算、把张量切分传播到后续算子，或将 reduce-scatter 与消费者配合；但必须遵守依赖与通信组语义。看似可重叠的 NCCL kernel 会占用 SM 和 HBM，成本模型若假设通信免费，可能得到更差计划。

动态控制流在 agent、稀疏路由与提前退出中越来越常见。将所有分支 padding 成静态大图简化编译，却执行大量无效工作；保留动态调度更灵活，但有 launch、同步和 graph break。常见折中是编译稳定的算子岛，由运行时调度岛之间的动态路径。优化单位不一定是整个模型。

CUDA Graph 记录一段稳定 launch 序列并重放，可减少 CPU 提交开销。它要求地址和部分执行结构稳定，在线 batching 的 batch/页表变化要放进预分配缓冲或准备多个图。Graph 加速的是提交路径，不会自动让 kernel 更快；若 GPU 已被长 kernel 占满，收益有限。

## 6. 怎样证明优化进入了关键路径

单 kernel 先用 microbenchmark 验证，预热并同步，扫描实际 shape，比较吞吐、字节与误差。替换进模型后检查 kernel 是否仍被调用、相邻位置是否出现转换或 graph break；端到端负载再比较 step、TTFT、TPOT 与 p99。三个层级缺一不可。

若新 kernel 快 30%，端到端只快 2%，可能因为该算子占比小，也可能融合前后增加了 layout conversion。Amdahl 定律给出上限：原占比为 $f$、局部加速为 $s$，总加速为 $1/[(1-f)+f/s]$。当 $f=0.1,s=2$，总加速只有约 1.053 倍。先 profile 占比再投入优化，通常比追逐孤立峰值有效。

编译缓存也要纳入端到端。若一次编译 60 s，每次调用省 2 ms，需要 30000 次调用才抵消；服务滚动发布、弹性副本与频繁 shape 变化可能永远达不到。可以预编译常见桶、持久化 cache 或缩小编译范围，但缓存必须与硬件和软件版本严格匹配。

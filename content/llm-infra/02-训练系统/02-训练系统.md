# 训练系统：并行、显存与吞吐

大模型训练系统的任务，是在容量、通信与故障约束下持续完成正确的优化 step。参数、梯度、优化器状态和 activation 具有不同生命周期；数据并行、张量并行、流水线并行和参数分片切开的也不是同一维度。能把模型放进设备，只解决容量问题；要提高有效 token 吞吐，还要把集合通信、重算、流水线空泡和数据等待放回依赖图。

本章以一次完整 step 为分析单位。后续依次讨论显存占用明细、并行策略、通信重叠、activation checkpointing、混合精度、数据管线与大规模调度。每种方案都要写出每卡状态量、每步通信量、同步次数和可遮蔽区间，并区分理论下界与实测差额。

## 一次训练 step 里有哪些状态

模型有 $N_p$ 个参数时，训练还可能保存梯度、优化器的一阶和二阶矩、低精度计算副本以及 master weight。参数状态要按每份副本的 dtype 逐项相加，结果随精度与优化器变化。activation 由 batch、序列长度、隐藏维度、层数和具体算子共同决定；它随输入 shape 变化，参数状态在模型配置与优化器确定后相对固定。两类状态需要分别核算。

前向计算按层产生 activation，反向从输出侧向输入侧消费它们并生成梯度。activation checkpointing 不保存部分中间结果，在反向到达对应层时重算前向。它减少峰值显存，代价是额外 FLOPs 和更复杂的执行时间线。省出的容量可能允许更大 microbatch，提高矩阵乘效率；额外计算也可能超过通信遮蔽区间，使 step time 增长。结论需在同一 global batch 与相同有效 token 数下测量。

梯度累积把一个 global batch 拆成多个 microbatch。多个 microbatch 的前向和反向依次完成，参数更新只发生一次。这样能降低单次 activation 峰值，却增加每次更新前的执行轮数。若报告 token/s 而不报告 global batch、microbatch 与累积步数，训练配置无法复算。混合精度还要说明前向矩阵乘、归约、梯度和优化器状态各自使用的类型，因为数值稳定与显存收益来自不同对象。

## 并行策略切开的不是同一个维度

数据并行为每个 rank 提供不同样本，模型副本完成本地前反向后归约梯度。它易于扩大吞吐，但完整复制参数和优化器状态。ZeRO 与 FSDP 逐步分片优化器、梯度和参数，需要在使用参数前聚合，并在反向后重新分散。容量下降对应更多通信和更短的参数驻留窗口，具体收益取决于 bucket 大小、预取和通信能否与相邻层计算重叠。

Tensor parallel 把层内矩阵沿行或列切到多卡。每张卡只计算部分输出，却在 attention 或 MLP 的特定位置执行 all-reduce、all-gather 或 reduce-scatter。通信位于层的关键路径，频率高，通常要求高带宽机内互连。Pipeline parallel 把连续层分成 stage，设备之间传输 activation 和梯度；microbatch 数不足时会出现 pipeline bubble，stage 计算不均衡还会让快 stage 等待慢 stage。

Sequence parallel 与 context parallel 按 token 维度分担状态和计算，常用于长上下文；expert parallel 则把 MoE expert 分布在设备上，通过 all-to-all 发送 token。后两者的通信量与输入分布和路由负载密切相关。实际大模型训练通常组合多种并行：高带宽域内使用 tensor parallel，节点间使用数据或流水线并行，再按容量需求加入分片。组合方案应从物理拓扑开始映射，不能只按设备总数分解整数因子。

## 重叠、气泡与关键路径

一次 step 的总通信字节不等于通信增加的时间。反向计算某层梯度后，对应 bucket 可以立即归约，同时继续计算更靠近输入侧的层；末尾尚未完成的通信才直接延长 step。bucket 太大时启动晚、重叠窗口短，太小时启动次数与框架调度开销增加。依赖图需要标出每个 bucket 的就绪时间、传输区间和优化器等待点。

流水线并行的 bubble 同样来自依赖。不同调度会安排前向与反向 microbatch 的交错顺序，改变 activation 驻留量和空闲比例。增加 microbatch 可以摊薄填充与排空，但也可能减小单个 microbatch，使 kernel 效率下降。stage 切分不能只按参数量平均；embedding、大词表输出层、attention 与 MLP 的计算和 activation 通信不同，需要根据实测时间平衡。

数据管线是训练依赖图的起点。样本读取、解压、tokenize、shuffle 和 batch 组装若没有在设备计算前完成，GPU 会出现输入空档。预取能够遮蔽平均延迟，无法无限吸收对象存储抖动或小文件请求放大。训练吞吐测试要同时记录 data wait、host 到 device 传输和设备 kernel 时间，避免把数据不足误判为模型并行效率低。

## 扩展到集群以后怎样判断瓶颈

弱扩展保持每卡工作量不变并增加设备，观察总吞吐是否近似线性；强扩展保持总问题规模不变，设备越多，每卡计算越少，通信和启动开销占比会上升。两种曲线回答不同问题。训练报告需要给出扩展方式、global batch 是否变化、学习率与优化是否随 batch 调整。若扩大设备同时扩大 batch，吞吐提高不能单独证明完成相同优化目标所需的时间缩短。

慢节点会放大同步训练的尾部。硬件降频、网络争用、数据读取和 kernel 抖动都可能让单个 rank 延迟，集合通信使其他 rank 一起等待。监控既要有 step time 分布，也要有各 rank 的计算、通信和输入时间线。平均 GPU 利用率无法定位短暂但周期性的同步停顿，单卡 profile 也看不到跨节点 straggler。

[系统模型](../01-系统模型/01-系统模型.md)提供 FLOPs、字节、容量与时延的共同坐标；本章把这些量放入训练 step 的依赖图。下一章[推理系统](../03-推理系统/03-推理系统.md)仍使用同一坐标，但状态从参数、梯度和 activation 转为请求、KV cache 与队列。后面的[数据存储](../04-数据存储/04-数据存储.md)继续展开样本和 checkpoint 路径，[可靠性](../06-可靠性/06-可靠性.md)则处理节点退出后哪些训练状态能够恢复。

训练系统同时包含状态生命周期、并行通信、调度执行和故障恢复。每卡容量决定配置能否启动；数据、张量、流水线、序列和 expert parallel 改变通信字节与时间线；checkpoint 又加入持久化和故障成本。四部分共同决定长期吞吐与可恢复性。

模型配置与 batch 决定每类训练状态的规模，并行策略决定哪些状态被切分、哪些仍在每个 rank 上复制，时间线则区分计算不足、通信尾部、pipeline bubble 和数据等待。吞吐改进必须放回相同有效工作量和收敛目标下比较，局部 profiler 指标不能替代完整训练结果。

复现训练配置时，还应保存并行拓扑、rank 到物理设备的映射、通信库版本、重算边界、bucket 配置和数据随机种子。同一组并行度若映射到不同的机内与机间链路，通信时间会明显变化；同一吞吐若来自更多丢弃样本或更高 padding，也不代表有效训练更快。训练系统的结论只有绑定这些条件，才可以在另一套集群上解释差异并重新选择方案。

训练结束后的 checkpoint 还要能恢复模型、优化器、学习率日程、随机数状态和数据消费位置；缺少其中任一项，都可能让恢复后的 step 与原训练轨迹分叉。

# 大模型训练的并行策略：从一张计算图到多维设备网格

单卡放不下模型时，「加卡」并不会自动解决问题。首先要决定哪些张量复制、哪些张量切分、切在哪个维度、什么时候聚合。切分减少单卡容量或计算，代价是新增通信与同步。训练系统的并行策略，本质上是在设备网格上放置计算图：让高频小通信留在快链路，让能重叠的大通信靠近计算，同时守住显存上限和全局 batch。

本文先用统一符号推导数据并行、张量并行、流水并行、上下文并行与专家并行，再把它们组合成多维网格。所有容量都是理想主项，真实实现还需加入 allocator、通信 bucket、临时 workspace 与 checkpoint 峰值。

## 1. 先写下不能改变的训练语义

设模型参数量为 $N$, 层数为 $L$, 隐藏维度为 $H$, 序列长度为 $S$, 全局 batch 为 $B_g$. 使用 $p$ 张设备时，若每卡 micro-batch 为 $B_m$, 数据并行度为 $p_d$, 梯度累积步数为 $g$, 则

$$
B_g=B_m p_d g.
$$

这条关系先于性能讨论。提高数据并行度却不调整 $B_m$ 或 $g$, 会改变全局 batch；学习率、优化器噪声与收敛可能随之改变。两个系统配置若每 step 时间不同、每 step token 也不同，应比较 token/s 和达到同等质量所需 token，而不是只比 step/s。

并行策略还要守住数值语义。一次完整梯度的 reduce 与多个局部梯度的求和在有限精度下可能有归约顺序误差，但不能漏项、重复或在错误的通信组中聚合。任何重构先用小模型对照 loss、梯度范数和更新后的参数，再进入大规模性能测量。

### 1.1. 数据并行：复制模型，切分样本

数据并行（DP）让每个 rank 持有完整模型，分别处理不同样本。反向后，各 rank 对梯度做 all-reduce，使更新保持一致。它几乎不改变单卡算子 shape，扩展简单，但参数、梯度和优化器状态仍完整复制，无法让超出单卡显存的模型直接运行。

设梯度总量为 $M_g$ byte，$p_d$ 个 rank 用 ring all-reduce，每 rank 算法通信量近似为

$$
V_{AR}=2\frac{p_d-1}{p_d}M_g.
$$

all-reduce 由 reduce-scatter 与 all-gather 两段组成，所以有系数 2。通信可按参数反向就绪顺序分成 bucket，与更早层的反向计算重叠。最后就绪的 bucket 后面没有计算可遮蔽，形成 exposed tail。bucket 太大启动晚；太小会放大每次 collective 的固定延迟。

### 1.2. ZeRO/FSDP 分片训练状态

AdamW 混合精度训练常按每参数 16 byte 粗算：低精度参数 2、梯度 2、FP32 主参数 4、两个 FP32 动量共 8。ZeRO-1 只分片优化器状态，ZeRO-2 再分梯度，ZeRO-3/FSDP 把参数也分片。理想静态容量随分片阶段逐步接近 $16N/p_d$，但计算某层前需要 all-gather 参数，反向后 reduce-scatter 梯度。

分片将容量问题转换成通信与生命周期问题。若每层参数在前向取回后一直保留到反向，峰值很高、通信少；前向后立即释放可省显存，反向前却需再次 all-gather。预取下一层参数可以隐藏通信，也会让两层参数同时驻留。FSDP wrap 粒度过粗时峰值高，过细时 collective 数量多。合理粒度应让单元计算足以覆盖其取回时间。

对 7B 参数、8 路完全分片，16 byte/参数的理想静态状态约 14 GB/卡，而不是 112 GB/卡。真实峰值还包括当前层与预取层的完整参数、通信 buffer、activation 和 allocator 保留。仅用 $16N/p$ 宣称「能放下」是不完整的。

### 1.3. 张量并行：切分层内矩阵

张量并行（TP）把单个线性层的权重沿输出或输入维切开。设 $Y=XW$, $X\in\mathbb{R}^{T\times H}$, $W\in\mathbb{R}^{H\times H_o}$。列并行把 $W$ 沿 $H_o$ 切成 $[W_1,\ldots,W_p]$，每 rank 得 $Y_i=XW_i$；若下一个算子可以消费分片输出，暂时不必聚合。行并行把 $W$ 沿输入维切分，同时把 $X$ 切为 $X_i$，局部计算 $X_iW_i$ 后需要求和：

$$
Y=\sum_{i=1}^{p_t}X_iW_i.
$$

MLP 常把第一个投影做列并行，激活后保持分片，第二个投影做行并行并 all-reduce。attention 的 QKV 投影可按 head 切分，输出投影再归约。这样每层通常有固定次数的 activation collective，消息量与 $TSw$ 或 $BSHw$ 相关，并且位于逐层关键路径。

TP 降低单卡参数和算子计算，但让 GEMM 变窄。并行度过高时，每 rank 的矩阵小到无法填满 Tensor Core，通信又增加。TP 通常优先放在节点内 NVLink/NVSwitch 域；跨节点小消息延迟会在每层重复。选择 TP degree 要同时比较单卡 GEMM 效率、每层通信和显存，而不是尽量切到最多卡。

### 1.4. Sequence parallel 与 TP 配合

LayerNorm、dropout 和部分逐元素算子若继续复制完整 $[B,S,H]$ activation，会削弱 TP 的显存收益。sequence parallel 将这部分 activation 沿 token 维切分，并把某些 all-reduce 改为 reduce-scatter/all-gather。它不必减少总通信字节，但减少每 rank activation，且让通信结果直接成为下一算子的分片输入。

通信算子名称变化不代表一定更快。reduce-scatter 后若很快又 all-gather，二者之间必须有足够计算或容量收益。时间线上要检查通信是否进入关键路径，显存时间线上确认完整 activation 是否真的不再驻留。

## 4. 流水并行：切分层，按 micro-batch 排程

流水并行（PP）把连续层分给不同 stage。stage 之间发送 activation，反向时发送 activation gradient。若有 $p_p$ 个 stage，每个 micro-batch 在每 stage 的时间近似为 $t$, 最简单 GPipe 调度用 $m$ 个 micro-batch 时，利用率约为

$$
U\approx\frac{m}{m+p_p-1}.
$$

$p_p-1$ 对应填充与排空空泡。$m$ 越大，空泡比例越小，却可能需要保留更多 activation。1F1B（一次前向、一次反向）在流水稳定后交替执行，可限制在途 activation 数量；interleaved schedule 让每个设备持有多个虚拟 stage，缩短空泡，但增加调度和通信复杂度。

stage 时间不平衡会让最快 stage 等最慢 stage。按层数均分不一定平衡：embedding、词表投影、不同 attention 结构、MoE 层和跨 stage 通信都不同。切分前先 profile 每层在目标 micro-batch 下的时间和峰值，再用最长 stage 作为节拍估算。一个 stage 比其他慢 20%，稳态吞吐就被它限制。

PP 的通信消息通常是 activation，大小约 $BSH w$，频率随 micro-batch 增加。跨节点放置时要考虑链路；相邻 stage 若隔着慢网络，发送会进入依赖路径。另一方面，PP 不要求每层都通信，适合节点之间的较慢连接。常见映射是节点内 TP、节点间 PP/DP。

### 4.1. 上下文并行：切分长序列

超长上下文使 activation 与 attention 工作增长，单纯 TP 仍可能在每 rank 保留完整序列。上下文并行（CP）沿 $S$ 切分 token。线性层可独立处理本地 token，attention 却需要远端 K/V。实现可以 all-gather K/V，也可以用 ring attention 让 K/V block 在 rank 间轮转，每轮计算本地 Q 与当前 K/V 的部分在线 softmax。

在线 softmax 合并局部块时要维护行最大值、指数和与加权输出。不同块的局部最大值不同时，旧累计量需重标定，才能得到与全局精确 attention 等价的结果。通信量、计算重叠和 causal mask 的负载平衡共同决定效果。

因果 attention 中，序列前部 Q 看到的 K/V 少，后部看到的多。按连续区间简单切分会导致 rank 工作不均。可采用 zigzag 等映射，让每个 rank 同时持有前后片段，平衡有效注意力元素。代价是位置映射和数据布局更复杂。

### 4.2. 专家并行：让 token 去找权重

MoE 层有 $E$ 个 expert，每 token 选择 $k$ 个。专家并行（EP）将不同 expert 放在不同 rank，路由后执行 all-to-all dispatch，专家计算完成再 all-to-all combine。参数容量按所有 expert 计，单 token 计算按激活的 $k$ 个计；通信载荷近似与 $kBSH w$ 成正比。

负载均衡比平均通信量更重要。若一个 expert 收到过多 token，其所在 rank 决定整个 all-to-all/专家阶段时间。容量因子为每 expert 预留固定槽位，能形成规则 GEMM，但 padding 浪费；超容量 token 的丢弃、重路由或备用 expert 会影响语义。监控需给出 expert token 分布、最大/平均比、padding、丢弃与每 peer 字节。

EP 通常与 TP/DP 组合。expert 权重可在 expert group 内分散，共享 attention 等 dense 参数在另一维复制或分片。通信组若配置错，可能让 all-to-all 跨越比预期更慢的链路。设备 mesh 应显式命名每个维度，并核对 rank 到物理 GPU/NIC 的映射。

## 7. 多维并行怎样组合

设总设备数

$$
p=p_d p_t p_p p_c p_e.
$$

不是每个模型都需要五维全部非 1。先由单卡容量判断需要多少参数/状态分片，再由单层 GEMM 效率限定 TP 上限，由序列长度判断 CP，由 MoE 架构决定 EP，剩余设备放到 DP 扩展吞吐。PP 用于跨节点容纳层与减少高频层内跨网通信。

一个 128 GPU、每节点 8 卡的 dense 模型，可以从 TP=8、PP=4、DP=4 起步：TP 留在节点内，PP stage 跨 4 个节点组，DP 在副本间同步。若长上下文 activation 放不下，可把 TP 降到 4、增加 CP=2，仍保持节点内 8 卡域。具体优劣需代入模型 shape 和拓扑测试。

### 7.1. 容量表

对每种状态列出是否被各维切分：参数可能被 TP、PP、FSDP 切；优化器随 FSDP 切；activation 随 TP/sequence、PP 和 CP 切；KV/attention 中间量受 CP；MoE expert 参数受 EP。切分因子不能盲目相乘，因为某张量并不参与所有维度。

例如 attention QKV 权重可能按 TP 切、按 PP 只存在于所属 stage、按 DP/FSDP group 分片；但 LayerNorm 参数很小，框架可能选择复制。容量估算应按参数组求和，而不是用总参数乘一个统一除数。

### 7.2. 通信表

DP/FSDP 通信多发生在层边界或梯度就绪时，可与反向重叠；TP 每层多次，延迟敏感；PP 每 micro-batch 在 stage 边界传 activation；CP 在 attention 内轮转或聚合 K/V；EP 在每个 MoE 层 all-to-all。把这些边放到同一 DAG 后，才能发现它们是否并发争用同一 NIC。

只分别 benchmark 各通信组会高估实际能力。DP all-reduce 与 EP all-to-all 若同时跨节点，叠加流量可能让二者都变慢。可以改变调度避免重叠、把组映射到不同 rail，或降低某个 collective 的 channel 占用。时间线负责判断哪种更好。

## 8. 从组合到选型

组合并行不是把允许的维度相乘到设备数就结束。候选必须同时满足训练语义、单卡容量、算子 shape、物理拓扑与恢复约束；其中任何一项不成立，后面的性能比较都没有意义。

选型先用模型排除明显不可行配置，再在真实硬件上测少量候选。模型负责解释方向和上限，实测负责吸收 kernel、协议和运行时细节。两者互相校准，避免穷举所有组合，也避免只凭经验固定参数。

### 8.1. 容量与拓扑筛选

第一步固定训练语义：模型、序列、全局 batch、精度和 optimizer。第二步列单卡静态状态、activation 与 workspace，算最少分片因子。第三步测关键 GEMM 随 TP degree 的效率，排除过窄 shape。第四步根据物理拓扑放置高频通信。第五步用真实训练片段测峰值显存、step 时间和各 collective 裸露尾部。

筛选过程要保留被排除原因。某候选是容量不足、矩阵效率下降，还是 TP group 跨慢链路，决定未来硬件/模型变化后是否值得重新启用。只保存胜出配置会让下一次搜索从头重复。

### 8.2. 性能与恢复验收

强缩放保持全局工作量，设备越多每卡工作越少，效率终会下降；弱缩放保持每卡工作量，观察总吞吐能否线性增长。大模型单卡跑不了时，可用最小可运行配置作基线，但要明确基线设备数。扩展效率不能把改变 batch 后的 step 时间直接相除。

故障恢复也属于并行策略。checkpoint 分片是否能在不同 world size 重新加载，通信组重建是否依赖固定 rank，数据游标是否随 DP 变化，这些决定配置能否弹性伸缩。只在稳定运行时最快、恢复必须原规模的方案，可能不适合长时间大集群训练。

可以进一步把一次 step 写成依赖图上的近似模型。设流水 stage $j$ 的单个 micro-batch 前向、反向计算分别为 $f_j,b_j$，相邻 stage 的 activation 往返通信为 $a_j$，该 stage 内无法隐藏的 TP/CP 通信为 $c_j$。稳态节拍不会小于

$$
t_{cycle}\ge \max_j(f_j+b_j+a_j+c_j).
$$

若采用 1F1B，$m$ 个 micro-batch 和 $p_p$ 个 stage 的 step 时间还要加入填充、排空以及最后 DP/FSDP 尾部。一个可读的粗估是

$$
T_{step}\approx (m+p_p-1)t_{cycle}+T_{dp,tail}+T_{host}.
$$

这不是精确调度模拟，但能快速发现数量级错误。假设四个 stage 的周期分别为 42、45、61、44 ms，$m=16$，即便前三个 stage 平均很快，流水节拍仍由 61 ms 限制；理想主体约 $(16+4-1)\times61=1159$ ms。若重新切层后四个 stage 变为 48、50、51、49 ms，主体降到约 969 ms。此时即使通信总字节不变，均衡 stage 也带来约 16% 的预测收益。

### 8.3. 一个 64 GPU 配置的手算

考虑 32 层、约 30B 参数的 dense 模型，集群为 8 个节点、每节点 8 GPU。假设单卡无法容纳完整训练状态，单节点高速互联明显快于节点间网络。候选 A 取 TP=8、PP=2、DP=4；候选 B 取 TP=4、PP=4、DP=4。两者都用 64 GPU，差别在于矩阵宽度、stage 边界和跨节点路径。

候选 A 每个 PP stage 有 16 层，节点内 8 路 TP。若每层隐藏 activation 为 $B_mS H w=256$ MiB，TP collective 每层发生在节点内；PP 边界每 micro-batch 发送一份分片或完整 activation，具体取决于布局。候选 B 的 TP GEMM 宽度更大，单卡计算效率可能更好，PP stage 只有 8 层，流水空泡却因 stage 数从 2 增到 4 而上升。若 $m=16$，均衡假设下 bubble 比例从 $(2-1)/(16+2-1)=5.9\%$ 增到 $(4-1)/(16+4-1)=15.8\%$。

再看容量。若单个 stage 的参数按 PP 均分，A 每 stage 约 15B 参数，再由 TP 切到每卡约 1.875B；B 每 stage 约 7.5B，再由 TP=4 切到每卡同样约 1.875B。二者参数主项接近，但 activation、通信 buffer 与 FSDP 组不同。A 的 TP collective 参与 8 卡，B 只有 4 卡；B 却多两次流水边界。可见「每卡参数一样」远不足以决定选择。

实际选型时，先在目标 GPU 测两种 TP 下的主要 GEMM，再测 256 MiB activation 跨 PP 边界和每层 TP collective。把结果代入 stage 模型。若 B 的 GEMM 快 12%，但新增 bubble 与跨节点 activation 使 step 多 18%，仍选 A；若 micro-batch 数能增至 64，B 的 bubble 降低，结论可能反转。配置与训练 batch、序列不可分离。

### 8.4. 通信重叠的上限怎么算

假设某个反向区间计算 80 ms，同时产生一个 all-reduce，独立测得通信 50 ms。无争用且依赖允许时，区间下界是 80 ms，最多隐藏 50 ms。并发后若计算因 HBM 争用变为 95 ms、通信变为 65 ms，而两者仍完全重叠，区间是 95 ms，只隐藏了串行和 $80+50=130$ ms 中的 35 ms。时间线有重叠色块，不等于隐藏了独立通信时长。

Bucket 就绪也限制重叠。设四层反向各 20 ms，梯度 bucket 覆盖四层并需 50 ms 通信，它只能在 80 ms 后启动，全部成为尾部；拆成两桶后，第一桶在 40 ms 启动，可与后 40 ms 计算重叠，第二桶仍留 50 ms 尾部。继续拆成四桶若每次固定启动延迟很高，通信总时间又会增加。合理 bucket 让每桶通信时间接近后续可覆盖计算，同时避免进入小消息低带宽区。

对 TP collective，通常没有数层之后才消费的余地：当前层输出归约完成，下一层才能继续。可尝试把 reduce-scatter 与后续分片算子衔接，或把通信分块成流水，但依赖更紧。优化重点常是拓扑与协议，而不是照搬 DP bucket 思路。

### 8.5. 负载不均与慢 rank

集合通信结束时间由最慢参与者决定。一个 rank 的前序 kernel 因长序列、热降频或数据等待晚到 30 ms，其他 rank 会在 collective 中等待；报表可能把这 30 ms 全记到通信。排查时同时记录各 rank 的 collective enter/exit：进入时间离散说明上游不均，进入一致而退出离散才更像链路或传输问题。

MoE 的慢 rank 常来自 token 路由。假设 8 个 expert rank 共处理 8192 个 token，平均 1024；某 rank 得到 1800，专家 GEMM 与 all-to-all 接收都更重。平均负载完全正常，最大/平均却为 1.76。容量因子若设 1.25，只容纳 1280 槽，剩余 token 要丢弃或二次路由；增大到 2.0 可容纳热点，却让其他 expert padding。监控和成本模型都要使用最大负载与分布，而非平均。

Pipeline 的不均来自层成本和通信。对异构层或 MoE 层，按层数平分会失败。可以把一个慢 stage 的部分层移给相邻 stage，或使用 interleaved virtual stages；后者减少局部不均，却让 activation 在设备间往返更多。每次改动都重新计算内存与边界通信。

### 8.6. 训练语义与性能验收清单

功能侧先在固定 batch 上保存单卡或较小并行配置的 loss、每层输出摘要、梯度范数和更新后参数摘要。多维并行结果按可解释的浮点容差比较。若使用 sequence/context parallel，特别检查 mask、位置与 padding；若使用 expert parallel，检查 token 去向、combine 权重与丢弃统计。

性能侧至少保留每 stage 计算时间、每类 collective 的消息大小与 p50/p99、通信裸露时间、GPU 空档、每卡峰值和有效 token/s。扩展实验固定训练语义；改变 batch 的实验另列为吞吐调优。恢复侧从实际分片 checkpoint 重新建立通信组，执行一个 step，并验证数据进度没有重放或跳跃。

最终配置还要留容量与性能余量。把显存压到 99% 可能被最长序列、保存或通信重试击穿；把网络长期跑满会在一个慢节点出现时放大长尾。并行策略是长期运行方案，不是一次微基准的最高数字。

### 8.7. Context Parallel 的通信复算

设序列长 $S$ 均分到 $p_c$ 个 rank，每 rank 有 $S/p_c$ 个 query 与本地 K/V。Ring attention 经过 $p_c$ 轮，让每块 K/V 依次访问所有 query rank。每 rank 发送的 K/V 有效量约为

$$
V_{ring}\approx 2\frac{p_c-1}{p_c}BSA_{kv}Dw,
$$

其中 2 是 K/V。它与一次 all-gather 的数量级相近，但分轮传输可与当前块 attention 计算流水。能否隐藏取决于单块计算 $O(B(S/p_c)^2H)$ 与单轮网络时间；继续增大 $p_c$ 会让每块计算按平方下降，通信轮数却增加，最终无法遮蔽。

因果 mask 造成负载不均。若连续切分，第一段 query 只看早期 K/V，最后一段看几乎全部；简单跳过被 mask 的块会让后 rank 更忙。Zigzag 分配把序列前后片段配对到同一 rank，使有效注意力元素更接近。验证不仅看总 token 数，还要给每 rank 实际 QK 元素与轮次时间。

假设 $S=64K,p_c=8$，每 rank 8K query。若某轮 K/V 传输 4 ms、本地块 attention 6 ms，流水后轮次约由 6 ms 限制；将 CP 增到 16 后，本地计算可能降到约 1.5 ms，而通信块虽减半仍需 2.2 ms，通信接管。CP=16 能省 activation，却不一定更快。

### 8.8. 并行度搜索不是笛卡尔穷举

候选空间可按约束逐层剪枝。先用容量模型排除放不下的 $(p_t,p_p,p_c,p_e)$；再用矩阵 shape 排除每 rank GEMM 过窄的 TP；用节点拓扑限制高频通信组；用全局 batch 限制 DP 和 micro-batch；最后对少量候选做实测。

性能模型不必一次预测绝对时间。它能可靠比较某维度变化的方向就有价值。例如两个候选参数容量相同，模型显示 B 多出每层跨节点 collective，即可先排除；候选只差 stage 切分时，用逐层 profile 做动态规划寻找最大 stage 最小的分割。

搜索结果与软件版本绑定。Kernel、通信库或硬件固件升级会改变 $P_{shape}$、$\alpha$、$B$，原最优点可能移动。保存候选输入、模型参数和原始 profile，升级后重跑代表性点；并行元组只对记录中的环境和负载成立。

成本也可进入目标函数。相同 token/s 下，更多 GPU 的配置恢复更快或尾延迟更稳，是否值得由每有效 token 成本与作业截止时间决定。将吞吐、显存安全区、故障恢复和租用成本并列，才能得到可运营的选择。

最后对候选做至少一次长跑，而不是只测十个 step。通信抖动、热降频、数据长尾与 checkpoint 会在小时尺度出现。记录每个 rank 的 step 分位数和慢因归类；平均吞吐相同的两个配置，p99 更稳者往往能减少集群同步等待和故障误判。

并行配置还应能被机器读取：设备 mesh、各维 group、stage 层范围、wrap 边界和 bucket 写入版本化配置，启动时校验乘积等于 world size、rank 不重复且物理拓扑符合约束。避免文档写一套、运行时因默认值落成另一套。

运行时还要将最终解析后的配置写入 checkpoint 与性能报告。恢复或复现实验时，如果只保存用户填写的局部参数，框架版本升级可能改变默认 bucket、prefetch 和通信算法，得到不同执行。显式记录默认展开值、环境变量和拓扑探测摘要，才能解释同一并行元组为何表现变化。

当某个 rank 退出或网络降级时，不要在线猜测新的通信组继续当前 step，除非训练框架明确支持弹性一致性。最安全的边界通常是终止本次 step，从最近一致 checkpoint 以新 mesh 恢复。丢掉一次局部计算比让不同 rank 更新到不同参数版本更可控。

**并行策略在容量约束下优化关键路径。** 每新增一个并行维度，都要明确被切分的张量、新增的 collective、使用的链路层级和可遮蔽它的计算。模型或集群变化后，这些量可以重新计算，原配置不应直接沿用。

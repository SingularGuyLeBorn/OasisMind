# 分布式检查点：一致快照、异步保存与弹性恢复

Checkpoint 必须在故障后重建同一训练状态。大模型训练把参数、梯度与优化器分散在许多 rank，数据迭代器和随机数也各有进度；任何一部分来自不同 step，恢复后的运行就不再等价。保存因此是一致性协议，性能优化必须服从版本边界。

## 1. 到底要保存什么

完整恢复通常需要模型参数、optimizer state、学习率调度、global step、混合精度 scaler、随机数状态和数据进度。只做推理发布可以丢弃 optimizer 与数据状态，但这种制品不能当训练 checkpoint。EMA、LoRA、MoE router 统计等附加状态是否需要，取决于训练算法。

数据进度不能只写「第 1000 step」。一个 step 含哪些 shard、样本顺序和混合源取决于 manifest、shuffle seed、worker/world size 与缓冲状态。严格恢复可保存全局样本编号和各数据源采样器状态；允许少量重复时也要明确边界，不能默默从 epoch 开头重来。

### 1.1. 分片格式与 Manifest

在 FSDP/ZeRO 下，每 rank 只持有局部 shard。最直接的保存让各 rank 写自身张量，元数据记录全局 tensor 的 shape、dtype、分片 offset 与文件位置。Manifest 还记录模型/优化器格式版本、step、world size、并行网格、校验和与必要配置。

恢复端先读 manifest，再并行读取目标 shard。若新 world size 与旧值相同，可以直接映射；若不同，需要根据全局 offset 把旧 shard 重分配给新 rank。转换最好流式进行：每次读取与当前目标范围相交的切片，避免单 rank 聚合完整状态。

一个版本先写临时命名空间。每个 shard 完成写入与 checksum 后上报，协调者确认必需文件齐全，再原子发布 manifest 或完成标记。恢复只列举已提交 manifest，忽略孤立临时文件。对象存储缺少传统 rename 时，可用不可变对象加一个很小的 commit record。

状态分片的一致性包含两个层次。第一个层次是每个逻辑张量内部：manifest 记录全局 shape、dtype、扁平区间和每片 checksum，所有区间的并集必须恰好覆盖 $[0,N)$，既没有缺口，也没有重叠。第二个层次是训练状态集合：参数、梯度缩放器、优化器 slot、scheduler、RNG 与数据进度必须共享同一个 checkpoint id 和逻辑 step。单个张量拼接正确，仍不能补救参数来自 step 8000、Adam 动量来自 step 7999 的混合版本。

假设参数 $W$ 有 1000 个元素，四个旧 rank 保存区间 $[0,250)$、$[250,500)$、$[500,750)$、$[750,1000)$。若 rank 2 的 manifest 误写为 $[499,750)$，文件总元素数变成 1001；只检查每片文件存在和 checksum 会通过，检查区间覆盖则能发现元素 499 重叠。恢复到五个 rank 时，目标区间每份 200 个元素，读取计划由旧区间与目标区间求交产生。每个目标 rank 只读相交 byte，并在装配完成后核对全局元素数和参数级 hash，避免先在单 rank 聚合完整张量。

Optimizer state 与参数通过稳定逻辑 id 关联。若 FSDP flatten 顺序改变，文件中的连续区间不再等于新运行时的 flat buffer 顺序；恢复器先把旧片映射到逻辑参数，再按新布局写入。共享 embedding/output weight 还要保存别名关系，否则恢复后会形成两份数值相同但 storage 独立的参数，后续更新逐渐分叉。Manifest 因而需要描述张量身份和布局，不能把 rank 文件名当作全部语义。

原子发布可用两类不可变对象。数据对象名称包含 checkpoint id、rank、chunk 与内容 hash；commit record 包含完整 manifest 的 hash、对象列表、逻辑 step 和格式版本。协调者采用条件创建发布 commit record，同一 id 已存在时只能接受内容完全相同的幂等重试。恢复端先读取 commit record，再按其中的 manifest hash 获取内容，不通过 LIST 猜测最新版本。这样即使部分对象晚到、重复上传或临时目录残留，也不会进入可见恢复集合。

### 1.2. 同步与异步保存

同步保存让训练在 step 边界停止，所有 rank 将状态写到持久介质，完成后继续。语义简单，停顿直接进入训练时间。假设 checkpoint 为 $Q$ byte，有效聚合写带宽为 $B$, 最低写入时间约 $Q/B$，小文件和元数据还增加固定延迟。

异步保存先获得稳定 snapshot，训练随后继续，后台完成序列化与上传。参数会在下一 step 被修改，因此后台线程必须读取不会继续变化的版本。可以复制到 CPU pinned buffer，使用 copy-on-write，或依赖版本化分片。只有 snapshot 完成后，训练才可以覆盖源页。

复制到 CPU 缩短 GPU 停顿，却增加 HBM→主机流量和主机峰值；后台写若慢于保存间隔，会积压多个版本。系统必须限制在途 checkpoint 数，通常宁可跳过中间版本，也不能无限占内存。跳过策略要保证仍有最近成功版本。

异步流水可以拆成冻结、D2H、序列化、暂存、远端上传、校验和提交七个阶段。设每 rank 状态为 $Q_r$ byte，D2H、序列化、网络速率分别为 $B_{pcie}$、$B_{ser}$、$B_{net}$，采用双缓冲并能充分流水时，长数据段的下界接近

$$
T_{pipe}\ge \frac{Q_r}{\min(B_{pcie},B_{ser},B_{net})}+T_{flush}+T_{commit}.
$$

GPU 停顿只覆盖建立稳定版本和首批 D2H，不等于 $T_{pipe}$。后台阶段会争用 PCIe、CPU 内存带宽、NIC 和对象存储，训练 step 即使没有显式暂停也可能变慢。验收同时记录 snapshot pause、远端 commit latency 和后台窗口内的 step slowdown。

取每 rank 12 GiB，PCIe 可持续 24 GiB/s、序列化 8 GiB/s、网络 4 GiB/s，单 rank 流水下界约 3 s；128 rank 总量 1.5 TiB，若存储后端聚合上限为 120 GiB/s，全局后端下界为 12.8 s，因此版本提交不可能在 3 s 完成。实测 18 s 时，先比较最慢 rank、后端限流和 commit 固定开销；盲目增加单 rank 上传线程无法越过 120 GiB/s 的共享上限。

双缓冲大小为 $C$ byte 时，至少要为当前 D2H 块和正在序列化/上传的前一块保留约 $2C$ 主机内存。$C=512$ MiB、每节点 8 rank，各 rank 独立双缓冲就需要约 8 GiB pinned memory；若节点还有数据 loader pinned buffer，可能触发主机内存压力。共享节点级 buffer 池并限制并发块数更可控。块过小会放大 PUT、checksum 和调度开销，块过大则延迟流水启动并提高失败重传成本。

在途版本上限必须与保存间隔联动。若每 10 分钟触发一次、p99 commit 为 14 分钟，允许两个版本并行会周期性占用两份 snapshot；只允许一个版本时，第二次触发需要跳过或等待。合理策略是保留当前上传任务，记录 missed checkpoint，并在完成后根据最近成功版本年龄决定是否立即补一次。覆盖当前稳定 snapshot 会让已经上传的分片与剩余分片来自不同 step，属于一致性错误，不能作为内存优化。

## 2. 保存间隔怎样选

设保存停顿为 $C_s$，保存间隔为 $I_c$，恢复耗时为 $R$，平均故障间隔为 $I_f$。正常保存开销比例约 $C_s/I_c$；故障发生在间隔内时，平均丢失约 $I_c/2$ 的计算，再加恢复 $R$。缩短间隔降低重算，却增加正常 I/O。

真实故障并非独立均匀，集群维护、网络波动与特定节点可能成簇发生。间隔应根据历史故障与任务价值调整。接近训练末尾或昂贵阶段可以更频繁，早期快速迭代可更稀疏。异步保存将停顿变小，但存储总字节没有消失。

增量 checkpoint 只写相对基线变化，适合某些状态，却让恢复依赖一条版本链。链过长会增加恢复和任一增量损坏风险；需要周期性完整基线与链校验。浮点参数每步几乎都变化，块级去重收益取决于格式与压缩，不能默认很高。

### 2.1. 恢复流程

恢复先选择最新完整版本，校验 manifest 与 shard；然后建立目标并行网格，加载/重分片参数和 optimizer，恢复 scheduler、RNG 与数据状态。所有 rank 到达一致边界后才开始下一 step，避免部分 rank 已更新、部分仍在加载。

格式升级要显式迁移。参数改名、拆层、合并 LoRA 或 optimizer state schema 变化，都通过版本化转换器处理。`strict=False` 静默忽略字段对推理加载可能方便，对训练恢复很危险。缺失状态应报出名称、预期 shape 与可否初始化。

恢复验收不止是 load 成功。至少执行一个 step，比较 checkpoint 前后 loss、学习率、梯度范数与数据样本；允许浮点差异时给容差。不同 world size 恢复还要检查全局 batch 和数据映射是否保持预期。

恢复时间可拆为发现版本、读取 manifest、下载、校验、反序列化、重分片、运行时初始化和首个成功 step：

$$
R=T_{discover}+T_{read}+T_{verify}+T_{reshard}+T_{init}+T_{first\_step}.
$$

若总 checkpoint 为 $Q$ byte，新集群有 $n$ 个读取 worker，每 worker 网络上限 $b_r$，存储聚合读取上限 $B_s$，下载下界为 $Q/\min(nb_r,B_s)$。重分片还可能经过节点内或节点间通信，不能假定下载完成就可训练。RTO 关注从故障发现到首个成功 step，而不是文件读取命令结束。

例如 1.5 TiB checkpoint 恢复到 64 个节点，每节点可读 3 GiB/s，后端聚合上限 100 GiB/s，纯下载下界约 15.4 s。实际观测为：调度新资源 90 s、manifest 与对象 HEAD 8 s、下载 24 s、校验和反序列化 20 s、重分片 35 s、编译与通信组初始化 70 s、首 step 18 s，总 RTO 约 265 s。继续提升存储带宽最多减少 8.6 s，优先缓存编译产物、减少资源启动与重分片成本更有效。

可验证恢复需要与保存前参考轨迹对照。固定输入 batch 和 RNG，在 step $s$ 完成后保存；原进程继续执行 step $s+1$，记录 loss、学习率、梯度范数、参数增量 hash、optimizer step 和下一批样本 id。新进程恢复后执行同一批次并比较这些字段。只比较加载后的 forward 会漏掉 Adam bias correction、scheduler、梯度 scaler和数据进度错误；只比较最终文本或指标又可能被数值容差掩盖。

世界规模变化时，目标全局 batch 也要明确。旧配置 64 rank、每 rank micro-batch 2、累积 4 次，全局 batch 为 512；恢复到 32 rank 后若其余配置不变，全局 batch 变成 256，优化轨迹已经改变。可以把累积次数改为 8 保持 512，也可以接受新 batch 并调整学习率，但必须作为新的训练配置记录，不能称为完全等价恢复。

### 2.2. 存储路径与请求放大

大量小 shard 会放大对象存储 PUT/LIST/HEAD 延迟；单个巨大文件又限制并发和失败重试。Shard 大小应让每个对象足以发挥吞吐，同时有足够对象分配给上传 worker。Manifest 避免依赖目录 LIST 的最终一致性，直接列出期望对象与 checksum。

多作业同时保存会形成 I/O 洪峰。调度器可以错峰、限速或使用节点本地 staging，再后台上传。Staging 盘容量必须为最坏积压预留，并在节点故障时承认尚未持久化版本会丢失。监控区分 snapshot 完成、staging 完成与远端 commit 完成。

压缩节省网络/存储，消耗 CPU 并延迟提交。浮点权重的通用压缩率可能有限，optimizer 某些状态更可压缩。先测目标张量，再决定是否在关键路径压缩；不要用小文件的压缩经验推断数百 GB tensor。

## 3. 常见故障边界

某 rank 写失败时，整个版本不能提交；其他已写 shard 保留为临时对象，后续 GC 根据未引用时间清理。协调者崩溃后，新的协调者可从上一个 committed manifest 恢复，不把「大部分 shard 存在」猜成完整版本。

保存期间训练作业失败，如果 snapshot 已一致但未上传完成，可由独立上传进程继续；若 snapshot 只在故障节点内存，本次版本丢失。协议要明确责任归属。删除旧版本也先确认新版本可加载，至少保留一个独立完整恢复点。

Silent corruption 依靠 checksum、张量元数据和恢复演练发现。Checksum 证明存储字节未变，不证明保存时张量就正确；因此还要做 shape/元素数统计和小规模 forward/step。长期冷存储可周期抽检。

故障注入要覆盖协议的每个边界。写 shard 前终止 rank，版本应保持不可见；上传一半时断开网络，重试必须从明确块继续或覆盖同名不可变对象；所有 shard 完成后、commit 前杀死协调者，新协调者能够核对对象并幂等提交；commit 成功后删除一个 shard，恢复应因 checksum/缺失失败并回退；下载期间损坏一个块，只重试该块且不把部分张量交给训练。

原子发布测试可以人为延迟 rank 7，同时让其余 rank 全部完成。恢复进程在延迟期间反复列出可用版本，任何一次都不能看到当前 checkpoint。rank 7 完成、commit record 写入后，新版本才一次性可见。随后删除临时对象或运行 GC，已提交 manifest 引用的对象不得被回收。若对象存储 LIST 有延迟，这个测试仍应通过，因为恢复入口依赖 commit record 和明确对象键，而非目录完整性。

异步保存的一致性注入更容易暴露混合版本。让训练在后台复制参数时持续执行，并在不同 tensor 的 D2H 之间插入延迟；同时保存每一步的参数 hash。恢复结果必须完整匹配某个确定 step 的参考 hash，不能一部分匹配 $s$、另一部分匹配 $s+1$。再对 optimizer slot、scaler、scheduler 和 RNG 做同样检查。Checksum 对混合版本无能为力，这类测试验证的是 snapshot 隔离机制。

恢复路径还要注入资源变化：以 world size 8 保存，使用 4 和 16 恢复；改变 rank 到节点的映射；让一个目标 rank 读取变慢；在重分片 collective 中终止参与者。成功场景核对全局张量与下一 step，失败场景确认所有 rank 共同退出或回退，不能出现部分 rank 已进入训练、其余仍在恢复。记录故障发生点、检测延迟、清理时间和最终选中的 checkpoint id，才能验证协议闭环。

长期演练可从每周抽取一个 committed 版本，在隔离集群恢复并执行若干 step。抽样不仅选最新版本，也覆盖冷存储里程碑和旧格式。结果写入 checkpoint 元数据：最近验证时间、目标 world size、恢复耗时、首 step 是否通过、参数/优化器/数据校验摘要。保留策略优先确保至少一个近期验证通过的完整版本，避免所有副本都来自从未执行过恢复的同一格式。

### 3.1. 性能与正确性验收

记录每次保存的 GPU snapshot 停顿、D2H、序列化、上传、commit 和总时长；同时记录训练 step 是否在后台保存期间变慢。异步 I/O 会争 CPU、PCIe 和网络，端到端损失不等于停顿时间。

容量测试覆盖训练稳态与保存峰值。若 state_dict 聚合导致额外完整副本，改用分片/流式保存；若 pinned buffer 过大，按块流水并控制在途数。恢复测试覆盖同规模、变规模、缺 shard、坏 checksum 和旧格式迁移。

### 3.2. 可恢复才算存在

**一个 checkpoint 只有在被成功恢复并继续训练后，才证明它存在。** 保存吞吐、格式与保留策略都围绕这个终点设计，而不是围绕文件数量设计。

因此提交成功只是一半验收。另一半是在隔离环境读取、重建训练状态并完成下一次更新；这一步应成为定期自动任务，而不是故障发生后第一次运行的脚本。

**一致快照的时间边界。**

设第 $s$ 步更新完成后的参数为 $\theta_s$，optimizer 状态为 $o_s$，scheduler 和数据位置为 $q_s,d_s$。可恢复点必须表示同一逻辑边界

$$
C_s=(\theta_s,o_s,q_s,d_s,r_s),
$$

其中 $r_s$ 是随机数状态。若参数来自 $s$、optimizer 来自 $s-1$，加载能够成功，下一步更新仍然错误。异步保存最先要保证的就是所有组件都被冻结在同一个 $s$。

分布式 rank 不会完全同时到达保存调用。可以在 optimizer step 后建立逻辑 barrier，确定 checkpoint id，再让各 rank 捕获本地 shard。Barrier 不要求所有 I/O 同步完成，只要求快照对应的训练状态不再变化。若使用流水并行，必须等所有 micro-batch 完成且无在途更新；若有异步 optimizer/offload，也要等相应 event。

Copy-on-write 能避免完整 CPU 副本，但需要页级或 tensor 级版本。训练写入仍被后台读取的页时，先复制旧内容；后台引用计数归零后释放。实现错误会产生混合版本，checksum 仍可能正确，因为损坏发生在 checksum 之前。功能测试要在保存期间持续更新参数，并将恢复结果与同步快照比较。

**分片重组算例。**

设一个长度 24 的一维参数，旧 world size 为 4，每 rank 连续持有 6 个元素：$[0,6),[6,12),[12,18),[18,24)$。恢复到 3 rank 后，目标范围变为每 rank 8 个元素。新 rank 0 读取旧 shard 0 的全部和旧 shard 1 的 $[6,8)$；新 rank 1 读取旧 shard 1 的 $[8,12)$ 与旧 shard 2 的 $[12,16)$；新 rank 2 读取剩余部分。

二维张量也可先定义全局扁平 offset，或按某个维度记录切片。关键是 manifest 描述全局布局，而不是只写「rank 2 的文件」。如果旧 TP 沿列切、新 TP 沿行切，恢复需要真正转置式重分发；可让存储读取器直接产生目标切片，避免每个 rank 读全量后 all-to-all。

Optimizer state 必须跟参数使用相同逻辑 id 和切片。参数改名或 flatten 顺序变化后，仅按文件位置匹配会错配动量。Manifest 为每个参数保存稳定名称/uuid、全局 shape 与 optimizer slots。共享/tied 参数还要记录别名，避免恢复成两个独立 storage。

**Checkpoint 吞吐模型。**

设每 rank 要写 $Q_r$ byte，序列化速率 $B_{ser,r}$，节点到存储有效带宽 $B_{net,r}$，后端聚合上限 $B_{store}$。若序列化和上传流水，单 rank 下界接近 $\max(Q_r/B_{ser,r},Q_r/B_{net,r})$；全局还受 $\sum Q_r/B_{store}$ 限制。完成时间由最慢 rank 和 manifest commit 决定。

例如 64 rank 各写 8 GiB，总量 512 GiB。单 rank 本地序列化 4 GiB/s，网络 2 GiB/s，后端聚合 80 GiB/s：单 rank 网络项 4 s，全局后端项 6.4 s，因此理想下界至少 6.4 s。若实测 25 s，继续增加每 rank 上传线程未必有用；先看后端 throttling、小对象与某些 rank 慢尾。

分块流水可在序列化第一个块后立即上传。块太小放大请求与 checksum 开销，太大让流水启动晚、失败重传大。对 8 GiB shard 取 256 MiB 块有 32 个请求，足以并发又不过度碎片化；具体阈值由对象存储测量决定。

**保存频率的数值例子。**

假设一次同步保存停顿 20 s，平均故障间隔 24 h，恢复 5 min。每 30 min 保存，正常开销约 $20/1800=1.11\%$；一次故障平均丢 15 min，再加 5 min。每 10 min 保存，正常开销升到 3.33%，故障平均丢 5 min。两者谁好取决于任务规模、故障概率与时间价值。

若异步快照只停 2 s，但后台上传 8 min，10 min 间隔理论可行；网络波动使上传偶尔超过 10 min 时，第二个版本会叠加。限制最多一个在途版本后，可跳过本次触发或等前一版本完成。不能覆盖唯一未提交 snapshot，否则一次上传失败会退回更老版本。

经典近似可以寻找 checkpoint interval，但现实中保存/恢复、故障分布和异步重叠并不满足简化假设。公式用来给初始范围，线上以长期浪费时间（保存、恢复、重算、等待）校准。

可以把单位运行时间的期望浪费写得更完整。设同步停顿为 $C_s$，异步窗口中训练相对减速为 $\delta$、持续 $C_a$，保存间隔为 $I_c$，故障率为 $\lambda_f$，恢复时间为 $R$，则近似浪费比例为

$$
W(I_c)\approx\frac{C_s+\delta C_a}{I_c}+\lambda_f\left(\frac{I_c}{2}+R\right).
$$

第一项是正常保存成本，第二项是故障导致的平均重算与恢复。忽略 $R$ 对最优间隔求导，可得 $I_c^*\approx\sqrt{2(C_s+\delta C_a)/\lambda_f}$。这个结果只用于给扫描范围：故障若成簇、保存与训练竞争非线性、上传会积压，实际最优点需要从长期 trace 重新评估。

例如 snapshot 停顿 3 s，后台上传 8 min，期间 step 慢 4%，等效保存成本为 $3+0.04\times480=22.2$ s；平均每 48 h 一次可恢复故障，$\lambda_f=1/172800$ s$^{-1}$，公式给出的间隔约为 $\sqrt{2\times22.2\times172800}=2770$ s，即约 46 min。若只把 3 s 停顿代入，会得到约 17 min，明显低估后台争用。再考虑 RPO 要求最多丢 30 min 进度，最终间隔仍需收紧到不超过 30 min，性能最优不能覆盖业务恢复目标。

保存间隔还受 commit 尾延迟约束。若 30 min 触发一次，commit p50 为 12 min、p99 为 38 min，平均上看没有积压，尾部却会跨过下一触发点。系统限制一个在途版本时，p99 场景会漏掉一次保护点；允许两个版本时，需要两份 snapshot 容量和更高共享 I/O。压测应注入后端限流，使 commit 超过间隔，验证跳过、排队和补存策略，并监控最近 committed age，而不是触发时间。

增量 checkpoint 会把恢复模型改成基线加一串 delta。设完整基线为 $Q_0$，第 $j$ 个增量为 $q_j$，读取带宽为 $B$，每段固定打开与校验开销为 $\alpha$，恢复下界约为

$$
T_{inc}\ge\frac{Q_0+\sum_{j=1}^{k}q_j}{B}+(k+1)\alpha+T_{apply}.
$$

即使每个 delta 很小，链长 $k$ 也会增加元数据、校验和任一段损坏的风险。可以在恢复 RTO 即将超过目标、链长达到阈值或累计增量接近完整基线时生成新基线。故障注入随机破坏链中一个 delta，恢复器必须回退到该段之前最近的完整可验证点，不能跳过差异继续加载。

**数据进度与弹性 world size。**

若数据集被 64 个 worker 按 shard id 取模分配，恢复到 48 worker 时直接恢复每 worker 本地 offset 没有定义。更稳妥的方法是使用不可变样本/块的全局序列与一个已消费前缀，或记录每个数据源确定性采样器的计数，再根据新 world size 重新分发后续单位。

Shuffle buffer 让边界复杂。保存整个 buffer 可精确恢复，却可能很大；只保存 seed 与读入计数，可通过重放重建，但恢复慢。允许 at-least-once 时可以回退到最近 shard 边界，明确最多重复多少样本。训练语义选择应写进格式，而不是由数据 loader 偶然决定。

多语料混合还要保存各源计数与调度 RNG。仅保存总 token 会改变混合比例的局部轨迹。若课程学习按 step 改权重，scheduler 状态也属于数据进度。恢复测试比较后续一小段样本 id 序列，最容易发现这些遗漏。

**异构和格式迁移边界。**

从 BF16 checkpoint 恢复到不同 GPU 通常可以，但 optimizer kernel、FP8 scale 或预打包权重可能绑定架构。可移植 checkpoint 保存规范逻辑张量，将硬件专用布局作为可重建 cache；否则升级硬件时要维护复杂转换。

量化推理制品不能自动还原训练 master weights。若部署格式只保存 INT4 权重与 scale，它适合推理回滚，不适合无损继续 BF16 训练。命名中明确 `train-checkpoint`、`model-export` 和 `engine-cache`，并分别设置保留策略。

架构改动如扩词表时，可迁移旧 embedding 行并初始化新增行；减少/重排层则是新训练实验，optimizer state 是否映射需要显式规则。转换器输出迁移报告：复用了哪些张量、初始化哪些、丢弃哪些，以及元素数校验。

**恢复演练与灾难场景。**

常规演练从最新版本恢复到相同规模。进一步随机删除一个临时 shard，确认未提交版本不会被选择；破坏 committed shard，确认 checksum 失败并回退上一个版本；让一个 rank 上传超时，确认本版不发布且训练不会无限等待。

灾难恢复还要考虑存储故障域。所有 checkpoint 在同一集群同一桶，区域故障时可能同时不可用；关键里程碑可异地复制。复制完成也通过 manifest/校验确认，不把异步复制开始当完成。

恢复时间目标决定是否保留本地热副本。远端可靠副本保证耐久，本地 SSD 可加速常见进程故障恢复；节点丢失时回退远端。监控分别记录 RPO（最多丢多少训练进度）和 RTO（多久恢复服务），让保存间隔与存储层级对应明确目标。

**优化器状态的恢复细节。**

Adam 的 $m_t,v_t$ 与 step 共同决定下一次更新：

$$
m_t=\beta_1m_{t-1}+(1-\beta_1)g_t,\quad
v_t=\beta_2v_{t-1}+(1-\beta_2)g_t^2.
$$

若只恢复 $m,v$ 而 step 归零，bias correction $1-\beta_1^t,1-\beta_2^t$ 改变；若 scheduler step 不一致，学习率也错。恢复测试只比较模型 forward 看不见这些问题，必须执行 optimizer step并对参数增量。

参数冻结/解冻或 optimizer parameter group 改变时，旧状态集合与新组不一一对应。继续训练需定义：保留匹配参数状态，新参数零初始化，已删除参数丢弃；group 超参数来自 checkpoint 还是新配置也要明确。迁移报告列出数量与例外。

分片 optimizer 可能把多个参数 flatten 到一个 buffer。保存规范逻辑参数 id 与 slice，恢复时按新 flatten 顺序重组。依赖 Python 遍历顺序容易在代码改动后错配，尤其参数 shape 相同而名称不同，错误可能不报 shape mismatch。

**安全、权限与删除。**

Checkpoint 包含完整模型能力，可能还含训练数据相关状态和密钥化配置引用。对象使用最小权限，训练作业只写自身前缀，恢复作业只读指定版本；日志不打印带签名 URL 或凭证。加密传输与静态加密不能替代访问审计。

保留策略通常保存最近 $k$ 个、周期里程碑和最佳指标版本。删除先读取 committed manifest 得到引用集合，再清理未被任何保留版本引用的对象。内容寻址/增量格式可能共享块，直接按目录递归删除会破坏其他版本。

删除本身应可审计并有延迟回收。误删发现后可在保留期恢复；法规要求的彻底删除则覆盖所有副本、缓存和异地复制。训练恢复可靠性与数据治理在这里相遇，不能只由临时清理脚本决定。

**端到端成本核算。**

假设 512 GiB checkpoint 每 30 min 一次，任务运行 30 天，约产生 1440 个版本、720 TiB 原始写入。若只保留最近 5 个加每日一个里程碑，稳态存储远小于全部保留，但写请求和网络成本仍已发生。压缩、增量和降低频率的收益要分别算存储、网络与故障风险。

异步保存若让训练 step 在 8 min 上传窗口内慢 3%，每 30 min 一次，其长期影响约 $8/30\times3\%=0.8\%$，再加 snapshot 停顿。只报告 2 s 停顿会低估。将 GPU 空转、后台争用、存储费用和故障重算统一为每有效训练 token 成本。

验收表至少包含 checkpoint byte、snapshot p50/p99、远端 commit 时间、后台期间 step slowdown、恢复下载/重分片/首 step 时间、失败率与最近成功版本年龄。这样保存系统是否健康不再由「目录里有新文件」判断。

**从一次失败恢复检查协议闭环。**

假设 step 12000 触发异步保存，64 个 rank 中 63 个已上传，rank 17 因节点故障缺 shard。协调者不能发布 step 12000 manifest；训练作业若也失败，恢复选择上一个 committed 的 step 11400。已经上传的 63 个对象属于未提交版本，带创建时间和 checkpoint id，等待 GC。

若 rank 17 只是网络超时而本地 staging 仍在，可由独立 uploader 重试。只有它成功且协调者/接管者重新校验全部对象，才发布 12000。Commit record 使用条件写，避免两个协调者重复发布冲突内容；相同内容的重试幂等。

恢复 step 11400 后，数据 loader 回到对应全局位置，scheduler/optimizer/RNG 同步恢复。系统记录损失的 600 step 和恢复 5 min，进入长期 RPO/RTO 统计。若监控只看「最近一次保存触发于 12000」，会误以为保护点更新，必须展示 committed checkpoint age。

**与训练调度器协同。**

Checkpoint 可能需要额外 CPU、网络和存储带宽。多作业在整点同时保存会形成洪峰，训练调度器可在允许窗口内错峰；但不能无限推迟，使 RPO 超限。作业上报最早/最晚保存时间与预计 byte，集群控制器分配 I/O 配额。

Spot/抢占实例收到终止预告时，可触发紧急 checkpoint。预告窗口若短于完整保存，可先完成一致 snapshot 到可靠的邻近层再后台转存，或提高常规保存频率；临近终止才开始完整保存通常来不及。紧急路径同样需演练。

扩缩容通常以 checkpoint 为重配置边界：完成 step、保存或形成内存 snapshot、销毁旧通信组、以新 world size 重分片恢复。在线弹性若试图边训练边迁移，需要更复杂的一致性协议。先把显式边界做可靠，再评估无停顿迁移是否值得。

**一手证据与实现核对。**

PyTorch Distributed Checkpoint 的 planner/storage abstraction、FSDP 的 state-dict 类型与官方文档用于确认可用语义；ZeRO 论文提供分片状态的原始设计。具体文件布局和异步实现仍以项目锁定版本为准，因为接口和默认值会变化。

实现时不从二手经验推断「某模式一定支持变 world size」。用最小两组进程实际保存/恢复，检查 optimizer 和数据进度；再扩大到目标 tensor。官方接口说明支持某能力，也不代表自定义模型、共享参数或旧格式自动兼容。

同样，不把存储返回成功等同 durable。对象存储的一致性、校验、条件写和生命周期按其官方保证设计；在本地/测试后端成立的 rename 语义不能直接搬到对象存储。协议明确依赖哪些原子原语，并为不具备的操作设计 commit record。

**最小可复现恢复实验。**

准备两层小模型与 AdamW，固定输入和 seed。运行三步后保存，继续两步得到参考参数；另起进程从第三步恢复，再运行相同两步。比较第五步 loss、学习率、每个参数与两个动量。这个实验能同时发现 optimizer step、RNG 和 scheduler 遗漏。

再用 world size 2 保存、world size 4 恢复，确认参数/optimizer 全局元素一致，数据样本序列按约定继续。注入一个坏 checksum 和一个缺 shard，恢复必须拒绝当前版本并选择上一个 committed，而不是用零填充继续。

异步保存测试让模型继续更新，并故意延迟一个 rank 上传。恢复出的第三步状态应与同步参考一致；若混入第四步 tensor，说明 snapshot 边界错误。小实验运行快，适合作为格式和框架升级的自动回归。

还可以把原子发布与恢复放进同一组确定性实验。Step 3 保存时让四个 rank 分别写两个 chunk，并记录预期对象键；rank 2 写完第一个 chunk 后暂停。此时启动恢复进程，只能看到 step 2 的 commit record。解除暂停后，协调者校验八个 chunk、写 manifest，再条件创建 step 3 的 commit record；恢复进程重新查询后才可选择 step 3。随后重复提交同一 commit，结果应幂等；用不同 manifest hash 提交相同 checkpoint id，则必须拒绝冲突。

进程分别在四个时间点终止：snapshot 前、部分 D2H 后、所有对象上传后但 commit 前、commit 后。前三种情况都不能产生可见的新版本；commit 后即使训练进程立即退出，该版本也应能够独立恢复。对每次残留对象运行 GC dry-run，确认只选择超过保留时间且未被任何 committed manifest 引用的内容。真正删除后再恢复所有保留版本，用来验证共享块或内容寻址没有被误清理。

恢复成功后执行两步更新并比较参考轨迹。第一步检查参数增量、Adam 动量、学习率、scaler、RNG 和样本 id；第二步用于发现只在状态再次更新时暴露的别名或 step 计数错误。若使用容差，分别给 loss、参数和 optimizer slot 设置阈值，并保存最大误差所在张量。简单地让加载函数返回成功，无法覆盖这些语义。

性能结果与正确性结果分开判定。某种格式恢复更快，但遗漏数据 sampler 或共享参数别名，不能进入性能比较；协议验证通过后，再报告 snapshot p50/p99、commit p50/p99、恢复分阶段时间和训练减速。这样可以防止为了得到更漂亮的保存带宽而省略必要状态或校验。

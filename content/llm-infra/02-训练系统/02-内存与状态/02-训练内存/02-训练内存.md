# 训练显存：从张量生命周期到分片与重算

训练 OOM 很少能用「模型参数乘 16」完整解释。静态状态、activation、梯度 bucket、算子 workspace、CUDA context 和 allocator 碎片在不同时间出现；峰值取决于哪些对象同时存活。一个优化减少静态容量，也可能因 all-gather 临时取回完整参数而产生更高瞬时峰值。

张量生命周期决定显存账本中的混合精度状态、反向保存、activation checkpoint、ZeRO/FSDP、offload 与碎片如何叠加。具体配置需要计算容量下界、定位峰值时刻，并用测量核对估算。

## 1. 显存由哪些部分组成

在时刻 $t$，设备占用可写成

$$
M(t)=M_{state}(t)+M_{act}(t)+M_{grad}(t)+M_{comm}(t)+M_{temp}(t)+M_{runtime}(t).
$$

峰值是 $\max_t M(t)$，不是各类别各自最大值之和。某个 attention workspace 只在前向中段出现，而梯度与优化器更新在反向末尾出现，二者峰值可能不重合。最可靠的账本给每个大对象记录 shape、dtype、分配、最后消费者和释放时刻。

框架常同时报告 allocated 与 reserved。allocated 是活跃张量占用，reserved 包含 allocator 从驱动申请但暂未分配给张量的块。reserved 高于 allocated 不一定是泄漏；内存池保留块可避免反复系统分配。真正 OOM 时要看是否有足够连续块满足新请求，以及历史 shape 是否造成不可复用碎片。

### 1.1. 静态训练状态逐项计算

设参数量 $N$。常见 BF16/FP16 AdamW 配置可能包含：低精度训练参数 $2N$ byte、梯度 $2N$、FP32 master parameter $4N$、一阶动量 $4N$、二阶动量 $4N$，合计 $16N$ byte。7B 参数为 112 GB（十进制），约 104.3 GiB。

实现并非总有 FP32 master parameter。BF16 参数可由优化器直接更新，某些框架保留 FP32 参数而低精度权重只是计算副本；8-bit optimizer 又会改变动量宽度与分组 scale。账本应从 optimizer state_dict 或实际 allocation 核对，不能把 16 byte 当物理定律。

### 1.2. 冻结与 PEFT

冻结参数仍需作为前向权重驻留，但不保存其梯度与优化器状态。LoRA 在若干线性层加入低秩矩阵 $A\in\mathbb{R}^{r\times d_{in}}$, $B\in\mathbb{R}^{d_{out}\times r}$，可训练参数为 $r(d_{in}+d_{out})$，远小于原权重 $d_{in}d_{out}$。然而全模型权重和 activation 仍存在，PEFT 主要减少梯度/优化器与更新通信，不会让基础模型权重消失。

量化基础权重的 QLoRA 进一步减少权重容量，但计算时要读取量化块、scale 并反量化。容量账本加入量化元数据和临时反量化片段；性能账本检查低比特读取是否真的进入融合 kernel。若框架把完整反量化权重长期缓存，理论节省会被抵消。

### 1.3. Activation 的生命周期

设层输入为 $X\in\mathbb{R}^{B\times S\times H}$。单个 BF16 张量占 $2BSH$ byte。Transformer 一层可能为反向保存输入、归一化统计、Q/K/V、attention 中间状态、MLP 激活和 dropout mask。FlashAttention 不保存完整 $S\times S$ probability，但会保存输出与每行 log-sum-exp；不同反向实现保存集合不同。

反向需要的张量由导数决定。例如线性层 $Y=XW$，有 $\partial L/\partial X=(\partial L/\partial Y)W^T$ 和 $\partial L/\partial W=X^T(\partial L/\partial Y)$，所以计算权重梯度需要前向输入 $X$。若释放 $X$，反向前必须重算或从其他介质取回。

训练开始时 activation 随前向层数累积，接近最后层达到高位；反向从顶层开始消费保存值并产生梯度，峰值可能在前向末尾，也可能在反向早期叠加梯度 bucket 与 workspace 时。只在 forward 完成后读取一次显存可能错过真正峰值。

### 1.4. 手算一个 activation 主项

取 $B=2,S=4096,H=4096,L=32$。一个 $[B,S,H]$ BF16 张量为 64 MiB。若每层等价保存 12 个此大小张量，32 层约 24 GiB。这个「12」不是通用常数，只是把实际保存 shape 归一到层输入大小后的系数；更换 fused attention、MLP 激活或 dropout 会改变它。

词表 logits 可能突然成为峰值。若词表 $V=128000$，$[B,S,V]$ BF16 logits 为 $2\times4096\times128000\times2$ byte，约 1.95 GiB。若 cross entropy 另存概率或 FP32 中间量，容量更大。融合 cross entropy 分块计算 loss，可以避免长期物化全部概率。

## 4. Activation Checkpoint 用计算换容量

checkpoint 只保存分段边界，反向到达该段时重新执行前向以恢复内部 activation。设 $L$ 层均匀分成段长 $c$，简化保存规模约为 $O(L/c+c)$：保存各段输入约 $L/c$ 份，重算某段时内部同时存在约 $c$ 层。最小值在 $c\approx\sqrt{L}$ 附近，但真实层不等大，框架调度也会改变峰值。

全层 checkpoint 通常每层只保留输入，节省大、重算多；只 checkpoint attention 或 MLP 可以针对主要 activation。非重入/选择性 checkpoint 能保存某些昂贵结果、重算便宜操作。评估要报告峰值显存、step 时间与实际重算 FLOPs，不能只说开启开关。

随机算子需要处理 RNG 状态。dropout 重算若使用不同 mask，梯度语义改变。框架会保存/恢复 RNG，带来少量状态与调度开销。包含状态更新、I/O 或不可重复副作用的函数不适合直接 checkpoint。

### 4.1. Checkpoint 与编译/融合的关系

重算边界可能阻断图融合，也可能让编译器生成两份不同前向路径。某些 fused kernel 的反向本就采用重算，例如不保存 softmax probability；再在外层 checkpoint 会重复更多计算。应从实际执行图数 kernel 和 FLOPs，而不是把两种技术节省简单相加。

checkpoint 释放容量后可以增大 micro-batch，提高 GEMM 效率并减少梯度累积次数。即使单 step 因重算变慢，token/s 可能因 batch 变大而改善。比较时固定全局 batch 或清楚说明变化。

### 4.2. ZeRO/FSDP 的取回窗口

完全分片把参数、梯度和 optimizer state 分散到数据并行 rank。某模块计算前 all-gather 其完整参数，计算后 reshard；反向再次取回并 reduce-scatter 梯度。稳态分片容量约按 $p$ 降低，峰值还包含当前模块完整参数与预取模块。

设最大 wrap 单元参数为 $M_u$，分片常驻为 $M_s$，同时预取一个下一单元，最粗略峰值参数项可能达到 $M_s+2M_u$，而不是只有 $M_s$。若 wrap 整个模型，$M_u$ 接近全参数，完全失去峰值优势；若每个很小子层单独 wrap，collective 太多。通常以 Transformer block 或参数量阈值为起点，再结合时间线调整。

`reshard_after_forward=false` 保留完整参数到反向，省第二次 all-gather，却使多个模块完整参数沿前向累积。适合显存宽松、通信昂贵的情形；显存紧张时前向后 reshard。CPU offload 将分片状态放主机，进一步省 HBM，但 optimizer update 与参数取回经过 PCIe，主机内存和 NUMA 也成为瓶颈。

### 4.3. 通信 buffer 与梯度累积

all-gather/reduce-scatter 使用 bucket buffer。bucket 越大带宽效率通常越高，峰值临时容量也越高。多个 stream 预取会让多个 bucket 同时在途。账本要读取真实 bucket 大小和并发数，而不是只按一个 buffer 估算。


o_sync` 梯度累积让多个 micro-batch 本地累加后再同步。在完全分片模式下，是否允许不归约的完整梯度长期驻留取决于实现；某些配置会显著增大峰值。梯度累积节省通信频率，但不保证节省显存。

## 6. Offload 把峰值搬到别的总线

把 optimizer/参数/activation offload 到 CPU 或 NVMe，HBM 容量下降，必须在消费者截止前取回。若每 step 需搬 $Q$ byte，PCIe 可持续带宽 $B_p$，不可隐藏时间至少为 $Q/B_p$。PCIe 4 x16 理论上限与实际有效带宽不同，还会与数据加载、GPU Direct Storage 或多卡共享 root complex 争用。

activation offload 最适合计算间隔足够长、张量大且可顺序预取的层。大量小张量会放大 DMA 启动；pageable host memory 还需 staging，pinned memory 又占用不可分页主机资源。实现通常把小张量打包成连续 buffer，异步 D2H 后在反向前 H2D 预取。

NVMe offload 容量大、延迟更高，需要深队列和顺序 I/O。若任务每层都等待 SSD，训练吞吐会崩溃；它依赖跨多层的预取窗口和 CPU/内存缓存。故障时 NVMe 上的临时状态通常不可替代持久 checkpoint。

### 6.1. 碎片、workspace 与意外峰值

allocator 按大小类管理块。动态序列、不同 micro-batch 与临时大张量反复交错，会留下总空闲足够但没有合适连续块的情形。减少 shape 种类、使用稳定 bucket、提前分配工作区可改善。频繁清空缓存会把问题转成昂贵的驱动分配，不应作为每 step 修复。

cuBLAS、attention 与编译 kernel 可能为特定算法申请 workspace。算法选择会在速度与 workspace 间权衡；warmup 阶段的 autotune 也可能短暂测试大工作区。OOM 若只在首轮发生，检查算法搜索和编译峰值；若训练若干步后发生，检查动态 shape、泄漏或通信重叠。

保存 checkpoint 时，state_dict 聚合、权重转换或序列化可能创建副本。ZeRO-3 若在 rank 0 汇聚完整模型，瞬时容量可能超过训练稳态。应使用分片保存、流式写出或 CPU 聚合，并把保存路径加入峰值测试。

### 6.2. 一次 OOM 的排查顺序

先记录 OOM 前 allocated、reserved、最大单次申请与各大张量 shape。然后在相同输入下获取内存快照，找出峰值时间和调用栈。若 allocated 接近容量，是实际 live tensor 过多；若 reserved 远高且空闲块零散，才重点看碎片。不要先盲目减 batch，因为那会掩盖保存副本或泄漏。

接着按数量级处理：参数/optimizer 太大，考虑分片、低精度或冻结；activation 太大，考虑 checkpoint、FlashAttention、序列并行或减小 micro-batch；瞬时 all-gather/workspace 太大，调整 wrap、预取与算法；碎片严重，稳定 shape 和生命周期。每次只改变一类，记录峰值和 step 时间。

最后做长时间验证。内存应在 warmup 后进入周期稳定状态；若每 step 缓慢上涨，检查保留 loss、输出、hook、日志 tensor 或未完成异步操作。周期性峰值则对齐 eval、保存和数据长度变化。

**显存预算必须包含动态工作和故障路径的余量。** 常规 batch 已占满 99% HBM 时，稍长序列、通信重试或保存 workspace 都可能触发 OOM。安全区应使用真实长度分布和保存、恢复流程验证。

### 6.3. 反向生命周期的逐层手算

用一个四层简化网络看峰值如何形成。假设每层输入 activation 为 1 GiB，层内为反向保存的其他张量为 2 GiB，每层参数相关静态状态已经分片后占 3 GiB，四层合计 12 GiB；运行时与通信常驻 4 GiB。不开 checkpoint 时，前向结束保存四层各 3 GiB，共 12 GiB，总占用约 28 GiB。

反向第 4 层开始时，若额外产生 1 GiB 输出梯度、2 GiB workspace，并让该层 2 GiB 梯度 bucket 就绪，瞬时变成 33 GiB。第 4 层完成后其 activation 释放 3 GiB，若 bucket 异步通信仍未结束，梯度 buffer 还不能释放。峰值因此可能发生在反向开头，而不是前向末尾。

若每两层做 checkpoint，只保存第 1、3 层段输入各 1 GiB，前向保存从 12 GiB 降为 2 GiB。反向处理第 3–4 层段时，要重算两层并临时生成该段内部 activation 约 6 GiB；此刻总量约为静态 16 GiB、边界 2 GiB、重算 6 GiB、梯度/workspace 5 GiB，共 29 GiB。节省不是 10 GiB 的简单差，而是从 33 降到约 29 GiB，因为重算窗口与梯度叠加。

这个例子也说明段长为何影响峰值。段更长，常驻边界更少，重算时的局部峰值更高；段更短则相反。层内 activation 大小不均时，把两个最重层放进同一段可能造成局部尖峰。实际切分应使用逐层保存字节与重算时间，而不是只按层数均分。

### 6.4. Attention 与 MLP 的保存集合

Attention 前向可能产生 Q、K、V、score、softmax probability、dropout mask 与输出。朴素实现若保存 $[B,A,S,S]$ probability，长上下文容量呈二次增长。IO-aware 实现通过分块与在线 softmax，只保留输出、行统计以及反向重算所需输入，避免完整 probability 驻留。它并没有让 Q/K/V 与层输入全部消失。

MLP 以 SwiGLU 为例，上投影常得到两个 $[B,S,H_f]$ 张量，门控激活后再下投影。若 $H_f\approx 8H/3$，中间 activation 比层输入更宽。融合门控与下投影前的某些操作可减少写回，但反向仍需输入或激活信息。选择性 checkpoint 常优先覆盖 MLP 大中间量，保留计算昂贵或容量小的统计量。

以 $B=2,S=4096,H=4096,H_f=11008$、BF16 为例，一个 $[B,S,H_f]$ 张量约 $2\times4096\times11008\times2=180{,}355{,}072$ byte，即约 172 MiB。两个上投影输出就约 344 MiB/层；32 层若同时保存，超过 10 GiB。若 fused backward 只需保存层输入、门控的压缩状态或选择重算，容量会显著变化。账本必须对应具体实现。

### 6.5. 混合精度与量化状态的真实字节

「FP16 训练」不表示每个状态都是 2 byte。矩阵输入和权重可能 BF16，归约与 optimizer 用 FP32，loss scaler 和某些统计量也为 FP32。编译器还会为对齐将张量 padding 到向量边界。逐项从 `numel × element_size` 统计，并将 storage alias 去重，比按 tensor 对象求和可靠。

8-bit optimizer 把动量按块量化，除了每元素 1 byte，还保存每块 scale、可能的最大值与异常通道。设两个状态均 INT8，块大小 2048，每块各有一个 FP32 scale，则主项约 $2N$ byte，scale 约 $2\times4N/2048$，远小于主项；但更新时可能需要 FP32 临时块。节省稳态不等于更新峰值按同样比例下降。

FP8 前向/反向可能维护 amax history 与 scale，数量不大，却影响图和同步。权重转置副本也常被忽略：某些 kernel/框架为了布局保留预打包权重，模型参数账本会多出一份或部分副本。内存快照中按 storage 地址确认是否共享。

### 6.6. FSDP 预取窗口的量化

假设一个 FSDP group 有 8 rank，连续三个 wrap 单元完整参数分别为 1.2、2.0、0.8 GiB；其分片常驻合计每 rank 0.5 GiB。计算第二单元时保留当前完整 2.0 GiB，并预取第三单元 0.8 GiB，参数相关峰值至少 3.3 GiB；如果第一单元的通信/引用尚未释放，再叠加 1.2 GiB，可到 4.5 GiB。

限制 all-gather 并发能降低峰值，却可能让第三单元等待。Backward prefetch 同理：提前取回下一反向单元以覆盖当前计算。最佳窗口由单元计算时间与 all-gather 时间决定。若 0.8 GiB 取回需 8 ms，当前单元反向 20 ms，单预取足够；同时预取两单元只增加容量，未必更多隐藏。

参数 persistence 阈值会让小参数长期完整保留，减少频繁 collective。LayerNorm 等小张量适合，阈值过大则大量参数绕过分片。报告应列分片常驻、完整持久参数与动态取回三类，而不是只有总 allocated。

### 6.7. 碎片的可证伪诊断

假设 reserved 70 GiB、allocated 55 GiB，新的 8 GiB 申请 OOM。不能仅凭 15 GiB 差额断言碎片，因为驱动、外部库和其他进程也占设备容量；allocator 内空闲块也可能被 stream/event 延迟复用。快照要显示空闲块大小分布与不可释放 segment。

可证伪实验是固定总 token，减少 shape 种类并关闭会变化的 autotune。如果 OOM 消失且 allocated 峰值近似不变，碎片/工作区复用是合理解释；若 allocated 同步下降，则真正 live tensor 也改变了。调整 allocator split size 只在证据指向块切分时使用。

内存泄漏与碎片表现不同。泄漏的 allocated 基线逐 step 上升，常见原因是把带计算图的 loss/tensor 放进列表、hook 持有输出、异步 future 未释放；碎片可能 reserved 上升后稳定，allocated 呈周期。画出多 step 的两条曲线比 OOM 时单点数字更有信息。

### 6.8. 显存预算怎样留安全区

设设备可用 80 GiB，稳态最长常规 batch 峰值 70 GiB，checkpoint snapshot 偶发再需 4 GiB，编译新 shape 最大 workspace 3 GiB。若三者可能重叠，至少需要 77 GiB；再给驱动波动和测量误差留 2–3 GiB，配置已经接近边界。若保存可以调度到训练空档，或预编译全部 shape，可证明部分峰值不重合，安全区才可减少。

长度动态的训练按 token/序列预算入队。用离线 profile 建立 $M(B,S)$ 表，运行时在组 batch 前预测；若 packing 改变 attention mask 或 MLP token 数，也纳入。拒绝一个超预算 batch 比运行到第 20 层 OOM 更节省，并能给数据调度器回退到更小组合。

最终报告同时给稳定峰值、最坏合法输入、保存/评估峰值与长期曲线。这样换 GPU、改序列或启用新 fused kernel 时，只替换对应条目，不会重新依赖「这次刚好没 OOM」的经验。

### 6.9. Pipeline 与梯度累积的 Activation 峰值

流水并行中，同时在途的 micro-batch 决定 activation 数量。GPipe 先完成所有前向再反向，单 stage 可能保存 $m$ 个 micro-batch activation；1F1B 在 warmup 后交替前后向，保存数量与 stage 位置和流水深度相关，通常显著更少。不能把单 micro-batch activation 乘全局累积次数，必须按调度表数 live micro-batch。

设一个 stage 每 micro-batch 保存 3 GiB，GPipe 有 $m=16$，最坏 48 GiB；1F1B 若该 stage 峰值仅保留 5 个，则 15 GiB。后者同时可能有反向梯度和通信 buffer，假设共 6 GiB，总计 21 GiB，仍远低于 GPipe。Interleaved schedule 每设备持有多个 virtual stage，activation 生命周期又会交错，需要从事件序列求和。

梯度累积不一定增加每个 micro-batch activation，因为反向结束会释放；它会让梯度 buffer 持续到最后一次累积。使用 `no_sync` 时某些分片框架暂不 reduce-scatter，可能保留完整梯度。测试 $g=1,2,4,8$ 的峰值是否近似稳定，若随 $g$ 增长，检查实现的同步语义。

### 6.10. 通信与内存优化的交叉代价

增大通信 bucket 通常提高带宽，但占更多显存并延迟启动。假设梯度 20 GiB，bucket 从 25 MiB 增到 200 MiB，单 buffer 多 175 MiB；若双缓冲和两类 collective 并发，新增可达数百 MiB。显存紧张时这会减少 micro-batch，反过来降低计算效率。

参数 all-gather 的 dtype 也影响字节与临时存储。计算权重 BF16，若通信错误使用 FP32，容量和网络均翻倍；某些压缩通信需要额外压缩/误差反馈 buffer。优化报告列出通信 payload dtype、bucket storage 和压缩残差，不把它们藏进 runtime。

Overlap 让对象生命周期延长。串行时通信完成即释放 bucket；并发时 bucket 跨越后续计算，可能与下一个 workspace 重叠。一次性能优化导致 OOM，并不矛盾：时间重叠改变了内存峰值。时间线与内存 snapshot 使用同一 event 标记，才能解释。

### 6.11. 编译与 CUDA Graph 的固定地址成本

CUDA Graph 重放常要求稳定地址，因此框架会建立固定内存池并保留最大 shape buffer。它减少 launch，却可能让小 batch 也占用大桶容量。为多个 shape bucket 捕获多个 graph 时，若每个有独立 pool，显存进一步增加；共享 pool 需要证明生命周期互斥。

编译器内存规划会复用不重叠的中间张量，但 graph break 把整体拆成片段，各片段可能分别保留 workspace。编译前后应比较 peak allocated 和 tensor 生命周期，不能假定融合必然省显存。某些融合减少 HBM 中间量，却增加 register spill/local memory 或持久 workspace。

首次编译/自动调优可能测试多个算法并申请大 workspace。生产预热在流量前完成，或限制算法 workspace；训练边界 shape 若运行中首次出现，也要留峰值余量。OOM 只发生在首个长序列时，优先检查这一层。

### 6.12. 从预算到配置的完整例子

一张 80 GiB 卡，框架与安全区预留 6 GiB，静态分片状态 18 GiB，通信/最大 workspace 8 GiB，剩 48 GiB 给 activation。Profile 表明单 micro-batch、2048 token activation 峰值 10 GiB；不开 checkpoint 最多 $B_m=4$ 但边界仅 8 GiB，保存时可能 OOM。

开启选择性 checkpoint 后每 micro-batch activation 降至 6 GiB，step 计算慢 12%。现在 $B_m=6$ 占 36 GiB，仍有 12 GiB 余量；GEMM 因 batch 增大使主体快 18%，综合 token/s 可能提高。需要实测而非只比较单 step：原配置每 step 1.0 s 处理 4 单位，4 unit/s；新配置若 1.08 s 处理 6，约 5.56 unit/s，吞吐提高 39%。

若全局 batch 固定 192，DP=8，原 $B_m=4$ 需累积 6 次，新 $B_m=6$ 累积 4 次；通信频率每 optimizer step不变，micro-batch launch 更少。模型质量语义保持。最终再运行最长序列、checkpoint 与 eval，确认 12 GiB 余量足够。

若新配置的长序列峰值升到 46 GiB activation，剩余只有 2 GiB，就应降低该长度桶的 micro-batch或加强 checkpoint，而不是让所有短序列一起降 batch。按长度自适应 batch 能保持大部分吞吐，但全局 batch 需由梯度累积补齐，数据调度也要记录每 step 有效 token。

显存账本最终与训练日志绑定：每次配置变更保存各类别估算、实测 peak、误差和时间位置。估算若长期比实测低，补入遗漏的 workspace/buffer；若过高，确认是否错误叠加互斥生命周期。模型越贴近实测，下一次换硬件或架构越能提前排除不可行方案。

对共享参数和 view 还要避免重复计数。Embedding 与输出头可能 tied，两个参数名指向同一 storage；切片/view 也与基张量共享。按 Python tensor 的 `numel` 求和会高估，按 storage 地址与覆盖区间去重更接近真实容量。反过来，编译/预打包若产生物理副本，即使逻辑参数名只有一个，也要从 snapshot 计入。

释放是否生效取决于最后引用和设备事件。删除 Python 变量只减少主机引用，异步 kernel 尚未完成时 allocator 不能安全复用；跨 stream tensor 还需正确记录 stream。用同步掩盖竞态会让峰值看似降低或时序改变，正式实现应以事件/所有权保证生命周期。

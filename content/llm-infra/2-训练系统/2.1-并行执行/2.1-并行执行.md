# 并行执行：把训练计算图放到设备网格

模型装进多张卡，只说明容量问题暂时解决了；训练能否扩展，还取决于每条张量边跨了什么链路、每个 collective 是否落在关键路径、切分后的矩阵是否仍能喂饱硬件。并行执行把具有数据依赖的计算图映射到具有层级带宽的设备网格。

训练系统通常同时使用数据并行、张量并行、流水并行、上下文并行和专家并行。它们切分的对象不同：DP 切样本，TP 切层内矩阵，PP 切连续层，CP 切序列，EP 切 expert。不同维度的通信频率和消息大小不同，适合的物理链路也不同。节点内高速互联应优先承载逐层发生的 TP/CP，跨节点网络更适合较大、可重叠的 DP 梯度通信或 stage 边界流量。

## 从三个约束开始

### 语义、容量与关键路径

第一是训练语义。全局 batch 满足 $B_g=B_m p_d g$，其中 $B_m$ 为每卡 micro-batch、$p_d$ 为数据并行度、$g$ 为梯度累积次数。调整并行度时若这个关系变化，学习率和收敛语义也可能变化。性能比较必须给每 step token 数，不能只看 step 时间。

第二是容量。参数、梯度、优化器、activation 和临时 workspace 并不被同一并行维度等比例切分。TP/PP 切部分参数，FSDP/ZeRO 在数据并行组内切状态，CP 切长序列 activation，EP 只切专家参数。容量表应按张量组计算，不能拿总参数除以所有并行度的乘积。

第三是关键路径。并行策略省下本地工作，同时新增通信和同步。总时间不是各项通信时间简单求和，也不能无条件取最大值。只有与计算真正并发且未因争用拖慢的部分才被隐藏。末尾梯度 bucket、逐层 TP collective 与流水 stage 等待通常会暴露出来。

### 技术路线怎样分工

[《并行策略》](2.1.1-并行策略.md)从 $Y=XW$ 推导列并行和行并行，从 micro-batch 推导流水空泡，从 KV 轮转推导上下文并行，再用设备网格组合 DP、TP、PP、CP 与 EP。每种状态的分片因子和每层 collective 因此可以从模型 shape 直接推出。

通信重叠由梯度就绪顺序、bucket 大小、通信 stream、NCCL 资源占用和 exposed tail 共同决定。异步 API 只负责排队；bucket 内末尾梯度晚到，或通信与 GEMM 同时争用 HBM，时间线中的色块重叠都不会等量转化为加速。

这两篇之间还有一条明确边界：并行策略决定通信必须存在以及参与 rank；通信重叠只改变它在时间线中的位置和资源分配，不改变数学结果。若一种「优化」通过跳过必要归约降低时间，那是语义错误，不是重叠。

## 拓扑与扩展

### 并行组落到物理链路

设一台节点有 8 张 GPU，通过 NVSwitch 互联；节点间经过 NIC。若 TP=8，逐层 activation collective 留在节点内。DP 跨节点的梯度 all-reduce 消息大、频率低于 TP，并可从反向后层开始逐桶启动。若 TP=16，逐层同步跨节点，小消息延迟与网络抖动会在几十层反复累积。

这不是「TP 永远不能跨节点」。当单层参数或 activation 不允许 TP=8 时，跨节点可能是必要代价；某些网络也足够快。正确做法是用实际消息大小测 collective 曲线，将每层通信代入，再比较减少的计算/容量。拓扑规则是成本模型，不是口号。

Rank 排列同样重要。逻辑上相邻的 TP rank 若被调度到不同机架，通信库再聪明也无法恢复预期路径。作业启动时应输出 DP/TP/PP/CP/EP group 到主机、GPU、NIC 的映射，并与拓扑探测结果核对。多 rail 系统还要确认流量确实分散，而不是所有 group 争用一张 NIC。

### 扩展效率怎样读

强缩放保持全局工作不变，增加设备后每卡矩阵变小、通信占比上升；弱缩放保持每卡工作量，观察总吞吐随设备增长。大模型单卡跑不了，可以最小可运行配置为基线，但要明确基线设备数。改变全局 batch 后直接计算线性效率，会把算法变化与系统扩展混在一起。

一个配置吞吐高，还需检查峰值显存与恢复。并行度改变 checkpoint 分片和数据游标；弹性恢复到不同 world size 时，参数/优化器能否重新切分？PP stage 或 expert 数是否绑定固定 rank？长时间训练中，无法快速恢复的峰值配置可能比略慢但可弹性的方案成本更高。

## 验收与失效边界

小模型负责验证 loss、梯度范数和一次更新结果，同时检查每种参数或 activation 的 shape 与所属通信组。功能正确后记录单 rank 计算基线，逐个启用并行维度，观察 GEMM shape、collective 字节和峰值显存。完整配置的时间线则用来区分计算、通信、空泡和主机空档。

扩展实验至少报告模型配置、序列、全局/micro batch、累积、精度、并行度元组、硬件拓扑、每卡峰值、token/s 和通信分位数。对 MoE 还要给 expert 负载与丢弃；对 PP 给 stage 时间和 bubble；对 CP 给 causal 负载平衡。

本路线最终要回答一个可以复算的问题：给定模型与集群，为何选择这一组并行度？答案应由容量下界、算子效率、通信路径和恢复约束共同组成，而不是「某个大模型也用了同样配置」。

### 常见失效模式

只看平均通信占比容易误判。某次 step 中通信总和只有 15%，末尾无法隐藏的 bucket 仍可能决定 step 尾部；大量通信若与反向完全重叠，优先级反而较低。判断依据应是依赖边上的裸露时间。

第二种是把逻辑并行度当作物理拓扑。配置写 TP=8 不代表八张卡真的处于同一高速域，容器调度、rank 顺序和网卡亲和都可能让它跨节点。启动时把通信组映射作为产物保存，避免靠命名猜路径。

第三种是过度切分。增加 TP/PP 能降低单卡容量，却让矩阵变窄、micro-batch 变小、collective 变多。若容量已有余量，减少并行维度、增加副本或 DP 往往有更高吞吐。选型应寻找满足容量后的最小必要模型并行，而不是最大并行。

第四种是基准没有覆盖保存、评估和长序列。稳态训练快，不代表 checkpoint 聚合不会 OOM；平均序列正常，不代表最长 batch 的 activation 能放下。验收负载必须包含这些周期事件和边界 shape。

路线选择还受故障域约束。跨八机做 TP 可能让一次节点故障拖垮整个模型副本，而机内 TP、跨机 DP 通常只损失一个副本并可从 checkpoint 重建。两套配置吞吐接近时，应比较故障后的有效训练时间：每周故障次数、重启耗时、checkpoint 间隔和重算 token 都要进入成本明细。峰值 token/s 略高却频繁整组重启，长期产出反而更低。

### 调度与性能模型

gang scheduling 要求所有 rank 同时获得设备，拓扑感知调度减少跨慢链路的通信，straggler 则把等待传播给 collective。性能模型将每层计算、通信、bubble 与重算汇总成 step 预测。

调度回答「资源何时可用」，性能模型预测「配置大概多快」。预测与 profile 之间的差额通常来自 kernel 效率、带宽争用、主机空档或长尾，实测结果用于重新校准模型参数。

并行度增加后，必须同时给出缩小的张量和新增的通信。只有「提高并行度会更快」无法支持配置决策；容量表、通信式和时间线才能说明方案是否可执行。

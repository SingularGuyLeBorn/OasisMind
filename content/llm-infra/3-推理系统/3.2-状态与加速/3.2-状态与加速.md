# 状态与加速：围绕 KV 减少逐 token 重复工作

自回归生成之所以能够逐 token 高效运行，是因为历史 K/V 被保存；它之所以仍然慢，是因为每一步仍要读权重、扫描 KV 并等待串行依赖。状态与加速路线围绕这两个事实展开：先管理不断增长的 KV，再用复用、量化、迁移或投机减少每个确认 token 的时间。

这条路线不把「缓存」和「加速算法」分开。投机解码的大模型验证仍然需要 KV；prefix cache 节省 prefill 后改变调度；KV 量化影响 attention kernel；跨节点迁移决定 PD 分离能否交接。每项技术都要同时看数值语义、状态生命周期和系统收益。

## 1. KV 是在线推理的主要可变状态

单请求 KV 容量为 $2LSA_{kv}Dw$。权重对副本固定，KV 随请求长度和并发增长。分页将逻辑 token 映射到固定物理 block，避免按最大长度预留连续区域；prefix cache 和 beam search 又让多个逻辑请求共享 block，需引用计数与 copy-on-write。

[《KV 缓存》](02-KV缓存.md)从 attention 公式推导 K/V 为何可缓存、Q 为何无需保存，然后进入分页地址、碎片、前缀键、量化、offload 与迁移。读完应能算出每 token 字节、给定 HBM 的理论 token 槽位，并说明请求取消后何时可以安全回收。

KV 的优化同时影响容量和带宽。GQA/MQA 或低比特缓存减少每 token 字节，让更多请求驻留，也降低 decode 每轮读取；反量化、scale 元数据与非连续地址又会增加计算。收益需要在目标上下文和 batch 上测量。

### 1.1. 投机解码改变串行确认方式

[《投机解码》](03-投机解码.md)由 draft-verify 的接受规则开始，解释小 draft 模型、多预测头和 n-gram proposer 怎样提交候选，以及 target 为何能够一次并行验证多个位置。若一次提出 $k$ 个 token，全部接受就让一次 target 前向确认多个 token；拒绝较早时，后续候选作废，draft 计算和验证宽度成为浪费。

性能由接受长度、draft 成本、target 验证效率和调度共同决定。高接受率不是充分条件：draft 太大或 target 对 $k$ token 的验证没有形成高效矩阵，仍可能不加速。反之，中等接受率若 draft 很便宜、验证高度并行，也可能获益。

投机过程需要维护状态。Draft 与 target 各有 KV；候选被拒绝后要回滚到接受前缀，不能保留错误分支。分页与 COW 可让候选分支共享旧 KV，只为新 token 分配临时 block；提交时转正，拒绝时释放。状态管理错误会直接改变输出。

### 1.2. Prefix 复用与投机的区别

Prefix cache 复用「过去已经计算且 token 完全相同」的状态，节省 prefill；投机解码预测「未来可能被接受」的 token，节省 target 串行轮次。前者命中必须精确满足模型/tokenizer/位置条件，后者通过接受算法保证分布。

二者可以叠加：请求先命中公共系统提示的 KV，从未命中处 prefill，再进入投机 decode。容量竞争也会叠加：保留大量冷 prefix 可能挤压活跃 draft/target KV。缓存淘汰应按未来节省时间与字节，而不仅是最近访问。

## 2. 状态流动与收益模型

### 2.1. 状态迁移与故障

PD 分离或负载迁移要发送 KV，以及 token 范围、层/head、dtype/layout、位置和模型版本。源目标 TP 布局不同还需重分片。迁移期间请求可能继续增长，协议必须选择冻结边界或快照加增量，并在目标确认后原子切换所有权。

KV 通常可由 token 序列重算，不必像 checkpoint 一样持久保存。设备故障后，新副本 prefill 已生成 token 即可恢复；但采样 RNG、约束解码状态和外部工具进度另需保存。重算造成的延迟应计入可用性，而不是因为「能恢复」就忽略。

跨租户复用是安全边界。KV 包含输入的内部表示，缓存命名空间必须绑定授权域；释放后 mask/页表必须保证新请求不会读到旧区域。Debug 测试应覆盖取消与立即复用、迁移失败、共享块 COW 和 generation id，排除陈旧引用。

### 2.2. 加速收益如何复算

基线每输出 token 时间为 $T_b$。投机一次 draft $k$ 个候选花 $T_d(k)$，target 验证花 $T_v(k)$，平均接受并确认 $a(k)$ 个 token，则每确认 token 时间近似

$$
T_{spec}(k)=\frac{T_d(k)+T_v(k)+T_{sched}(k)}{a(k)}.
$$

只有 $T_{spec}<T_b$ 才加速。$a(k)$ 随任务、温度和 draft 质量变化；$T_v$ 随 batch、验证长度和 kernel 变化。线上需要按请求类型观测，而不是用一个离线接受率覆盖全部流量。

KV 量化可写成相似的成本模型：节省的读取时间约由减少字节/有效带宽决定，新增反量化与误差评测是成本。Prefix cache 收益是避免的 prefill 时间减查询、保留和可能的负载倾斜。迁移收益是目标队列缩短减传输与接管。

## 3. 实验、版本与回退

先建立不带投机/复用的正确基线，固定模型、采样、输入输出与硬件。然后单独验证 KV 分页结果与连续参考一致，再启用 prefix、量化、offload 或迁移。每项都做 logits/任务质量与生命周期压力测试。

投机解码先在单请求测 draft、verify、接受长度，再放入连续 batching。不同请求的候选长度不同，验证 batch 会 ragged；调度器若等候凑批，可能把局部加速变成排队。报告 target 调用次数、确认 token、被拒候选、draft/verify 时间与端到端 TPOT。

容量和故障压力覆盖缓存接近满载、热门前缀、取消风暴、迁移中断和 draft/target 版本不一致。异常路径应安全回退到普通解码或重算，禁止返回未经目标模型确认的错误 token。

这条路线的核心判断很简单：状态是否仍对应当前已确认 token，额外工作是否换来了更少的 target 串行轮次或更少的字节。把这两点量化后，各种缓存和投机技术才具有共同的比较坐标。

### 3.1. 状态版本决定能否复用

缓存键需要覆盖所有会影响 K/V 的因素：模型权重、adapter、tokenizer、模板、位置参数、量化布局和执行语义。服务滚动升级时，新旧副本可能同时存在，缓存不能跨版本误命中。使用内容寻址加版本命名空间，比依赖进程内指针可靠。

Draft 与 target 也有兼容关系。投机算法允许两个模型分布不同，但 tokenizer/词表映射必须能对候选 token 达成一致；某些方法需要额外 head 或 target 中间状态。部署系统要把这类制品作为一个版本集合发布，不能只更新其中一半。

Prefix、KV 量化和投机参数会改变内核缓存。新 layout 上线前先预热常见 shape，避免首批请求同时触发编译；回滚时确认旧 kernel 与旧 KV 命名空间仍可用。运行状态的版本管理，是模型发布的一部分。

### 3.2. 观测与回退

状态优化的指标除了延迟，还有命中 token、活跃/冷 KV 字节、内部碎片、量化 kernel 占比、draft 接受长度、拒绝位置和回滚 block。聚合平均会掩盖某类任务的低接受率或某个租户的缓存污染，应按模型版本、请求类型和长度分组。

每种加速都要有安全回退。Prefix 校验失败就普通 prefill，量化 kernel 不支持 shape 就用标准 KV，投机异常就单步 target decode，迁移失败就留在源端或重算。回退路径必须定期压测；长期无人执行的 fallback 往往在真正故障时已经失效。

当回退比例上升，系统应先保护正确性和 SLO，再诊断版本、shape 或容量。不能为了维持面板上的命中率复用不确定状态，也不能在接受率低时继续强制投机。加速策略本身也是调度对象。

最终评审要同时查看质量、状态安全、容量与端到端收益；四项缺一项，都不能把实验性优化当成稳定能力。

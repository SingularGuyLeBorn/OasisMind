# 预处理与背压

训练数据抵达 DataLoader 之前，通常已经走过一条很长的生产线：抓取或接收原始对象，解析容器，抽取正文，规范化编码，识别语言与质量，去重、过滤、脱敏，再用确定版本的 tokenizer 编码，写成带索引和统计信息的 shard。任何一步都可能把数据量放大，也可能突然变慢。上游继续全速生产时，中间结果会占满内存、对象存储或本地磁盘；直接丢弃又会改变数据集。核心问题是让一条异构 DAG 在资源边界内稳定前进，并且故障后只重做必要部分。

这个主题与[训练数据流水线](../4.1-训练数据流水线/4.1-训练数据流水线.md)分工明确。训练数据流水线研究已经发布的数据版本如何被分片、洗牌、packing 并送到 GPU；预处理研究一个数据版本怎样被生产出来。前者的提交边界通常是 optimizer step 与 batch 序列，后者的提交边界是 work unit、阶段产物和 manifest。两者都需要背压与恢复，但状态坐标、资源瓶颈和正确性条件并不相同。

## 1. 预处理是一张有状态 DAG

预处理不能只写成一串脚本。解析、去重、分类、tokenize 和写 shard 对 CPU、内存、网络、GPU、临时磁盘的需求不同；全局去重和排序还会形成需要物化数据的边界。DAG 中每条边携带带版本的数据块，每个节点声明输入 schema、输出 schema、代码与模型版本、资源需求和失败策略。这样才能知道某一步升级后哪些产物失效，而不是从原始语料盲目全量重跑。

一条记录需要稳定身份。原始对象可以由内容哈希、来源版本与对象内位置共同定位，阶段输出再绑定算子版本与参数。只要输入身份与算子指纹相同，重试就应得到同一逻辑产物。随机抽样、近似去重和模型推断若含随机性，还要把 seed、模型权重和推理配置写入指纹。最终 manifest 汇总 shard checksum、样本数、token 数、过滤原因统计和血缘，训练只读取已经原子发布的版本。

## 2. 背压控制的是在途工作

背压表示下游暂时接不动，上游应减少发起新工作。它不是报错，也不等于把所有阶段串行化。流式执行允许多个算子同时处理不同 block，但每个算子的输入队列、输出队列、运行中任务和待提交结果都有显式上限。Ray Data 的流式执行同样以 block 连接算子，并在缓存达到预算后停止继续启动任务；官方监控把 task submission backpressure 与 task output backpressure 分开统计，这正好对应“任务不再发起”和“任务已经运行但结果暂时交不出去”两种情况。

队列上限要按字节和活跃工作集计算。十个压缩对象可能解压出完全不同的数据量，一个 OCR 或 tokenizer 任务还会同时持有输入、模型 workspace 和输出。只按任务数限制，会在异常大记录出现时失去保护。资源预算至少覆盖 worker heap、共享对象区、shuffle/spill 空间和输出暂存；大 block需要动态切分，无法切分的超大单条记录则进入隔离路径。

## 3. 资源配额与调度

CPU 解析、GPU 质量模型、网络读取和磁盘 shuffle 不应争抢同一种并发指标。每个算子声明 CPU、GPU、heap、对象存储和临时磁盘需求，调度器在全局预算内选择可运行任务。吞吐由瓶颈阶段决定，盲目扩大非瓶颈阶段只会增加排队。测量时同时记录输入/输出字节、记录数、token 数、运行时间、blocked 时间、spill 与重试，才能看到放大系数沿 DAG 怎样变化。

小 block利于流式首包和负载均衡，大 block降低调度与序列化开销。Ray Data 官方文档把 block 作为执行单位，并用目标大小与动态切分约束工作集；这一思路可以直接用于语料预处理，但数值必须按本项目的记录大小、算子耗时和对象存储特性重测。全局 shuffle、sort 和 exact dedup会打断纯流式路径，它们需要单独的物化预算和分区策略。

## 4. 恢复与增量重跑

任务成功不等于阶段已经提交。Worker先把输出写到带 attempt id 的临时位置，校验 schema、数量和 checksum，协调器再以 work unit为粒度接受一个 attempt并更新阶段 manifest。超时任务可以重试，旧 attempt晚到时不能覆盖新结果。发布最终数据集版本时，所有阶段统计与 shard引用通过一个不可变 manifest共同提交，读者忽略没有被 manifest引用的临时对象。

算子代码、参数、模型、tokenizer或输入版本变化时，失效范围沿 DAG向下游传播。文本规范化升级会使去重、质量分、tokenize与shard全部失效；只修改最终压缩级别，则可以复用 tokenize输出。缓存键若没有包含完整指纹，会把旧结果伪装成新版本。增量重跑的收益来自精确血缘，不来自“目录看起来已经有文件”。

## 5. 验收入口

[《预处理 DAG 与背压控制》](01-预处理DAG与背压控制.md)从记录身份、算子指纹和 block切分开始，推导队列与内存上界，解释调度、spill、重试、幂等提交、全局去重边界与增量重跑。文中给出可复算的容量案例，并把吞吐、数据正确性和版本一致性放进同一套验收方法。

验收至少包含三类负载：均匀小记录验证稳态吞吐，长尾与超大记录验证内存边界，故障注入验证重试和提交语义。性能提升只有在输出集合、过滤规则、tokenizer版本和统计摘要一致时才成立。若改变了数据内容或顺序，应发布新数据版本并重新做训练侧评估，不能把它当作等价的系统优化。

预处理系统还要把「数据被处理了多少」与「数据版本完成了多少」分开。Worker读过一条记录、模型给出分数、输出对象写入临时目录，都只是执行进度；只有对应 work unit 被阶段 manifest接纳，才属于可恢复的提交进度。前者用于看机器是否忙，后者用于估算剩余工期。把临时产出计入完成量，节点故障后进度条会倒退，也会让成本和重试率失真。

吞吐调优围绕有效产物展开。解析阶段可以用原始字节/s，质量阶段更适合用候选字符/s，tokenize与writer使用保留token/s；跨阶段比较时再换算为最终保留token。过滤率变化会让上游看起来很快、下游输入突然减少，只有同时记录输入、输出和放大系数，才能分清规则变化与性能变化。

主题中的背压也不局限于内存。对象服务的请求配额、GPU模型的batch槽位、临时磁盘剩余空间、writer可创建对象数都能成为预算。调度器在任一资源接近边界时收缩上游，并保留少量活性空间让下游继续排空。若所有空间都被上游占满，负责释放空间的合并或写出任务反而无法启动，系统会停在资源死锁而非正常背压。

数据版本发布后仍要保留阶段血缘和统计。训练发现某类样本异常时，可以从sample id回溯规范化、过滤、去重和tokenize结果，判断问题来自源数据还是算子升级；修复时只让受影响路径失效。没有这条链路，最安全的选择只剩全量重跑，也无法说明新旧版本究竟差在哪里。

# 连续批处理：逐轮重组请求而不牺牲尾延迟

传统静态 batching 将一组请求一起开始，等全部生成结束才换下一批。输出长度不同意味着短请求完成后仍占着批次位置，直到最长请求结束。连续批处理在每个 decode iteration 后移除完成请求、加入新请求，让活动集合随时间变化。它提高设备利用，却把调度、页表和服务公平性放进逐 token 关键路径。

## 1. 一轮调度处理什么

调度器维护 waiting queue 与 running set。每轮开始时，先为已有 decode 请求安排一个 token，再依据 token/KV/时间预算选取新 prefill 或 chunk。执行器根据选中请求构建 token ids、positions、slot mapping 和 attention metadata，运行模型，采样后更新状态。

调度本身必须足够快。若 GPU 一轮只有数毫秒，CPU 每轮花 1 ms 组 batch 已不可忽略。数据结构避免扫描全部等待请求，页表更新批量完成；稳定 shape 可用 CUDA Graph 减少 launch，但 running set 变化要写入预分配 buffer。

### 1.1. Token budget 与资源预算

按请求数限制 batch 很粗糙。Prefill 请求包含许多 token，decode 请求每轮一个；KV 占用又由历史长度决定。调度约束至少包括本轮计算 token 上限、序列数上限、可用 KV block 和预计执行时间。

设 decode 活动数为 $B_d$，每请求一 token；选中的 prefill chunk token 总数为 $T_p$，则本轮新 token 数 $T=B_d+T_p$。但时间不严格与 $T$ 成正比：prefill 有更高权重复用，decode 读历史 KV，混合 kernel 也可能分开执行。实际系统用 profile 表或在线回归按阶段、长度与 batch 预测。

KV 预算在入队前检查。Prompt 需要 $S$ 个槽位，decode 还承诺最多 $G$ 个；全部预留浪费，完全不承诺会中途无块。可做逻辑配额加物理按需分配，并限制总 overcommit。当水位高时停止接收、降低 max_tokens 或选择抢占。

一轮预算可以写成带单位的约束。设候选集合为 $\mathcal C$，请求 $i$ 在本轮处理 $t_i$ 个新 token，已有上下文为 $s_i$，预计新增 KV 为 $m_i(t_i)$ byte，预计执行时间为 $\hat d_i(t_i,s_i)$。选择变量 $x_i\in\{0,1\}$，则调度至少满足

$$
\sum_{i\in\mathcal C}x_it_i\le T_{max},\qquad
\sum_{i\in\mathcal C}x_im_i(t_i)\le M_{free},\qquad
\hat T(\{x_i,t_i,s_i\})\le D_{round}.
$$

$T_{max}$ 的单位是 token/轮，$M_{free}$ 是 byte，$D_{round}$ 是秒。三个上限不能互换：同为 512 个新 token，512 条 decode 会读取大量历史 KV，单条 512-token prefill 则有更规整的矩阵 shape；二者新增 KV 可能相近，执行时间和 HBM 流量却不同。实际实现可用分桶查表近似 $\hat T$，但日志仍应保存输入变量和预测版本，否则无法解释某轮为何超时。

例如空闲 KV 为 6 GiB，已有 48 个 decode 请求，其中 32 个上下文 2K、16 个上下文 16K；另有两个 prompt 等待，长度分别为 256 和 4096。假设每 token 每请求新增 KV 为 128 KiB，那么 decode 本轮新增约 6 MiB，两个 prompt 若整段进入分别新增 32 MiB 与 512 MiB，容量都放得下。但 profile 表显示 decode 集合需 9 ms，256-token prefill 需 4 ms，4096-token prefill 需 48 ms，而本轮 deadline 为 22 ms。容量不是限制，时间预算才决定只能先接短 prompt，或把长 prompt 切成约 512-token chunk。

### 1.2. Chunked Prefill 避免队头阻塞

长 prompt 若一次执行，会让所有 decode 等待。将其切成大小 $C$ 的 chunk，每轮只处理一块，块间可插入 decode。块越大，矩阵与 attention 效率越好；越小，decode deadline 更容易满足，但 launch、调度与页表开销增加。

因果 attention 的后续 chunk 需要读取已生成前缀 KV，并对当前块内部做 causal mask。计算结果与整段 prefill 应等价；位置与 mask 错误会造成静默质量问题。用相同 prompt 比较 chunk/unchunk logits 是基本正确性测试。

选择 chunk 不应只固定一个数字。短 prompt 可整段执行，长 prompt 根据剩余时间预算切分；高优先级 decode 多时缩小，空闲时增大。动态策略仍要限制 shape 种类，避免触发大量编译变体。

Chunk 时间不能只按 token 数线性缩放。设 chunk 长度为 $C$、已有前缀为 $P$、隐藏维度为 $H$，该块 attention 的主算术量包含约 $4CH(P+C/2)$ FLOP，线性层则近似与 $C$ 成正比。前缀从 2K 增到 32K 后，同一个 512-token chunk 的 attention 工作量会显著增加。因此查表键至少包含 chunk bucket、prefix bucket、活动 decode 数与 dtype；若只记录 $C$，长前缀会持续低估时间并挤占 decode deadline。

取同一模型的实测档位：前缀 2K 时，256/512/1024 token chunk 分别为 3.5/5.8/10.2 ms；前缀 32K 时变为 6.2/10.7/19.6 ms。本轮扣除 decode 后剩 12 ms，短前缀可以选 1024，长前缀只能选 512。若调度器总选最大可放入 token budget 的块，两者都选 1024，长前缀会使轮次超过预算约 7.6 ms。这个误差会直接出现在所有活动请求的 TPOT 上。

正确性边界也要写入实现。Chunk $j$ 的位置从 $P_j$ 开始，causal mask 允许 query 看到旧前缀与当前块中不晚于自己的 token；RoPE 使用全局位置。若 kernel 只收到局部下标，结果会在块边界后静默偏离。固定 token ids 下比较整段与多种切块的 logits，覆盖块大小不整除、滑动窗口、prefix-LM mask 和不同精度；同时验证每块完成后 KV 页表的 token 范围连续且不重叠。

## 2. 公平性与优先级

FCFS 简单，但长 prefill 阻塞后续短请求；Shortest-job-first 改善平均 TTFT，却需要预测输出长度且可能饿死长请求。Aging 让等待越久优先级越高，能给长请求最终服务保证。多租户还需配额或 weighted fair queue，避免一个租户占满 KV。

流式请求关心 TPOT。每个 decode 请求可以有下一 token deadline，调度先选择将到期集合，再填入吞吐工作。若当前轮预计超过最早 deadline，减少 prefill chunk 或 batch。Deadline 模型比「decode 永远最高优先」灵活，后者在持续高 decode 负载下会让 prefill 永远进不来。

优先级反转也可能发生。高优先级请求等待 KV，而低优先级请求占着大量 block并缓慢生成。抢占低优先级可以重算或换出，代价应进入决策。频繁抢占会抖动，需最小运行配额或冷却。

队列稳定性先由工作量决定。设请求到达率为 $\lambda$ request/s，第 $i$ 类请求的平均输入、输出 token 为 $E[S_{p,i}]$、$E[S_{o,i}]$，占比为 $q_i$。若服务在目标 SLO 内可持续提供 $\mu_p$ input token/s 与 $\mu_d$ output token/s，必要条件是

$$
\rho_p=\frac{\lambda\sum_iq_iE[S_{p,i}]}{\mu_p}<1,\qquad
\rho_d=\frac{\lambda\sum_iq_iE[S_{o,i}]}{\mu_d}<1.
$$

这只是长期均值条件，不能保证尾延迟。到达突发、长度相关性和一次副本故障都会让短期需求超过能力。若 $\rho_d=0.95$，轻微的输出变长就会让 decode 队列持续增长；调度器再公平也无法创造缺失的服务率。应在 admission 层留出故障与预测误差余量，并用 open-loop trace 找到队列开始发散的实际点。

公平性还要区分请求公平、token 公平和资源公平。一个 1K 上下文的 decode token 与一个 64K 上下文 token 都算一次输出，但后者读取的 KV 和设备时间更大。若按请求轮转，长上下文会占用更多资源；若只按估计毫秒收费，长请求又可能很久得不到 token。可为租户维护虚拟服务量 $v_u$，按估计设备时间 $c_i$ 更新 $v_u\leftarrow v_u+c_i/w_u$，同时为每个活动请求设置最大 token 间隔。租户权重控制长期份额，请求 deadline 约束短期流式体验。

例如租户 A/B 权重为 2:1，A 有 32 个 2K 请求，B 有 8 个 32K 请求。某轮 A token 估计 0.12 ms/个，B 为 0.55 ms/个。若只按 token 数 2:1 分配，B 的少量 token 仍可能消耗大部分轮次；按设备时间加权后，A 获得约三分之二长期资源，B 获得约三分之一，同时 deadline 规则保证 B 不会连续多轮缺席。日志应同时报告分配 token、估计毫秒和实际毫秒，预测长期偏向某类长度时才能校正。

### 2.1. Ragged Batch 与执行布局

连续 batch 中每请求上下文长度不同。Padding 到最大长度浪费 KV 扫描和计算；paged/ragged attention 根据每请求 block table 和长度处理有效区域。线性层对本轮新 token 仍可拼成一个矩阵，attention 则需要 offsets 描述每行对应序列。

负载不均会让一个 warp/block 处理长序列更久。Kernel 可按 KV 长度分桶，或将长序列 split-KV 给多个 block并归约。分桶增加 kernel 次数，减少分支与尾效应；是否值得由长度分布决定。

采样也可批量完成，但不同请求 temperature、top-k/top-p、约束解码不同。通用 kernel 分支多，按配置分组又增加 launch。系统通常为常见配置走快路径，复杂约束单独处理，并监控 fallback 占比。

### 2.2. 完成、取消与回收

请求遇到 EOS、max_tokens、停止串或错误后完成。停止串可能跨 token，需要在输出文本/bytes 上维护状态。完成后从 running set 移除，KV block 在无在途 kernel 后释放，流式队列发送最终状态。

客户端取消必须传播到调度器。已提交的本轮不能随意中断，可标记 cancel-pending，在 event 完成后回收。Waiting 请求可立即移除。若输出 backpressure 导致客户端消费慢，可以暂停调度但保留 KV，或超过阈值后取消/换出。

回收错误是严重正确性问题。过早复用让新请求读到被旧 kernel 修改的块；漏减引用造成显存耗尽。对共享 prefix/beam block 使用引用计数和 generation id，压力测试取消与立即重用。

资源所有权可以用“保留、提交、释放”三阶段约束。调度器先为请求保留 slot 与 KV block，构建批次后提交给执行器；GPU event 完成前，这些 block 仍属于在途批次，即使客户端已经取消也不能复用。完成事件返回后，成功请求提交新 token 和页表，取消请求丢弃输出并释放引用。若批次提交失败，统一回滚所有保留，避免部分请求已经扣减容量而另一部分仍停留在 waiting。

Generation id 用来防止地址复用后的迟到事件。物理 block 17 被请求 A 释放并分给 B 后，A 的异步完成回调若只携带 block id，可能错误减少 B 的引用；回调同时携带 generation，allocator 发现版本不匹配就拒绝修改。共享 prefix 还需要区分 cache 引用与活动请求引用，淘汰只删除 cache 持有者，引用数仍大于零时物理页继续保留。

取消风暴测试可以在每轮随机取消 waiting、已保留、已提交、blocked 和正在输出的请求，并立刻加入新请求复用空间。每轮结束核对：空闲块与所有持有者之和等于总块数；任一物理块引用数等于页表和 cache 持有者数量；finished/cancelled 请求不再出现在执行批次；确认 token 序号严格递增。持续数万轮后显存水位应回到与存活请求一致的区间，不能随取消次数单调上涨。

## 3. 过载控制

当到达率超过服务率，等待队列若无限增长，TTFT 与 KV 预留都会失控。Admission control 根据当前队列、预计服务时间、KV 容量和 SLO 决定接受、排队或拒绝。拒绝要尽早，让上游重试/降级，而不是消耗 prompt tokenize 与部分 prefill 后失败。

Goodput 统计在 TTFT/TPOT 目标内完成的请求。提高原始 token/s 但让更多请求越过 deadline，goodput 可能下降。调度参数应围绕 goodput 和租户公平调，而非 GPU 利用率单目标。

过载判断应使用预测完成时间而非队列长度。队列里 100 个 32-token 短输出与 100 个 4K 输出的剩余工作差两个数量级。对等待请求 $i$ 估计 prefill 工作 $W_{p,i}$，对运行请求估计剩余 decode 工作 $W_{d,i}$，按当前可持续能力得到粗略完成时间

$$
\hat T_{finish,i}=T_{now}+\frac{\sum_{j\preceq i}W_{p,j}}{\mu_p}+\frac{\sum_{k\in\mathcal R_i}W_{d,k}}{\mu_d}+T_{transfer}.
$$

这里的顺序和并发集合由实际策略决定，公式用于暴露工作量来源。若 $\hat T_{finish,i}$ 已超过租户 SLO，立即拒绝或明确降级通常优于先消耗部分 prefill 再失败。输出长度未知时使用分位数预测，并随已生成 token 更新；高估会损失利用率，低估会积累违约，需要按长度桶监控偏差。

假设副本在 SLO 内可提供 3000 output token/s，现有 running set 预计还剩 24K token，waiting 请求的输出 p90 合计 9K token，则纯 decode 工作已经约 11 s。新请求的 deadline 为 5 s，即使 prompt 很短也不应进入该副本。若另一个副本只剩 6K token 工作、但没有 prefix cache，重做 1K prompt 需 80 ms，它仍明显更早完成。路由要比较预计完成时间，不能让缓存命中覆盖队列差异。

当所有副本都超过承诺能力，admission 返回带重试信息的繁忙响应，并在入口限制重试速率。无抖动的立即拒绝比等待数十秒后超时更节省资源。若产品允许缩短 max_tokens、切换较小模型或关闭昂贵约束，这些变化必须在接受请求前确定并写入响应元数据；执行中途静默降级会破坏用户语义和评测口径。

过载时可采用降级：限制最大输出、降低候选/beam、关闭昂贵约束、路由到量化副本或返回繁忙。降级必须由产品语义允许并显式标记，不能静默改变质量。

### 3.1. 一次预算手算

假设 64 个 decode 请求一轮预计 12 ms，目标 TPOT p99 为 25 ms，剩余约 13 ms 可用于 prefill 和调度。Profile 显示 512-token prefill chunk 需 8 ms、1024 需 15 ms，则这一轮最多选择 512 档，并为预测误差/CPU 留余量。低负载只有 8 个 decode 时，它们可能只需 5 ms，可使用更大 chunk。

实验使用短/长 prompt 与短/长输出组合，分别跑静态 batching、连续 batching 与 chunked prefill。报告 input/output token/s、TTFT、TPOT、端到端、KV 水位、padding/有效 token 和调度 CPU。开环逐步提高到达率，找到 goodput 峰值与队列失稳点。

### 3.2. 时间线验收

时间线检查每轮 CPU gap、prefill/decode kernel、采样与通信。如果 device 空闲而 waiting queue 非空，调度/主机受限；如果 decode deadline 被单个长 kernel打破，调整 chunk/shape；若 KV 满而算力空闲，容量或分配策略才是主因。

测量从固定负载微基准开始。保存一组不可变 token ids，分别覆盖纯 decode、纯 prefill、短前缀 chunk、长前缀 chunk 和 ragged 混合批次；每个 shape 预热后重复测量设备时间、HBM byte、主要 kernel、collective 和 CPU 提交间隔。设备 event 的计时区间在同一 stream 上闭合，端到端计时则从请求到达到 token 发送，两种结果通过 iteration id 对齐。只同步主机提交函数会把异步执行漏出计时区间。

服务测试采用 open-loop 到达，依次提高 $\lambda$。每档至少运行到队列和 KV 水位达到稳态，记录 input/output goodput、TTFT、TPOT、队列等待、取消、拒绝、抢占、重算 byte 与各租户份额。固定并发的 closed-loop 测试可用于比较稳定 shape 的引擎上限，但系统变慢时客户端也会减少发送，无法发现队列失稳点，不能单独用于容量结论。

预测误差按批次类型分桶。若 decode 预测持续低估 2 ms，检查 KV 长度特征与 CPU gap；若只在 chunk prefix 超过 16K 后低估，增加 prefix bucket 或核对 kernel 阈值；若随机长尾与某个 rank 同时出现，检查长度分配、降频和网络争用。调度器用于 deadline 的 guard band 应来自误差分位数，例如 p95 低估为 1.8 ms，就在 20 ms 预算中只安排预测不超过 18.2 ms 的工作，而不是使用随意常数。

一次可复现的优化实验保留基线预测。比如把 chunk 档位从固定 1024 改为按 prefix 选择，预测长前缀轮次从 19.6 ms 降到 10.7 ms，额外 launch 每两轮增加约 0.4 ms；预期 TPOT 尖峰下降约 8 ms，prompt 完成时间增加约 5%。实测同时核对这三项。如果 TPOT 改善但 prompt 时间增加 30%，应查小块 GEMM 效率、调度空档和 graph fallback，而不能只宣布尾延迟达标。

**连续批处理让空出的执行槽尽快承载仍有价值的 token。** 调度决策需要同时约束时间、容量与公平性。

**一轮调度器的状态机。**

每个请求至少有 `waiting`、`prefilling`、`decoding`、`blocked`、`finished` 与 `cancel-pending`。状态转换必须由明确事件触发：KV block 预留成功才能进入执行集合；GPU event 完成后才能提交新 token；输出缓冲低于水位后 blocked 才回到 decoding；所有在途引用释放后才回收。

一次调度从上一轮完成事件开始，据此更新 token、停止条件和 block table。Running set 中接近 deadline 的 decode 占用刚性预算，prefill chunk 使用剩余的时间、KV 与 token 预算。批次提交后注册完成事件。CPU 可在 GPU 执行本轮时准备下一轮，但不能读尚未提交的新状态。

状态机让取消不再依赖偶然时序。Waiting 可直接结束；已经提交 GPU 的请求标记 cancel-pending，本轮完成后丢弃结果并释放；正在 KV 迁移的请求还需取消传输或等待目标确认。若四条路径各写一套清理代码，引用计数很容易失衡；统一 transition 负责资源所有权。

**Token Budget 的多维约束。**

单一 token 上限无法同时描述 prefill 和 decode。可以维护 $(T_p,T_d,K)$ 三项预算：prefill 新 token、decode 活动 token、预计 KV 读取/占用。时间预测写成

$$
\hat T=\hat T_{linear}(T_p+T_d)+\hat T_{attn,p}(T_p,P)+\hat T_{attn,d}(T_d,\{S_i\})+T_{sched}.
$$

$P$ 表示各 chunk 的已有前缀，$S_i$ 是 decode 上下文。实现不必在线算复杂公式，可以把 profile 拟合成分桶查表；公式用于说明为什么只有 $T_p+T_d$ 不够。

KV 容量预算也分当前物理占用和未来承诺。假设空闲 1000 block，本轮 prefill 需 300，decode 跨 block 边界预计需 20；直接可用剩 680。Waiting 请求声明的 max_tokens 可能还需 2000，不能全部物理预留。系统允许有限 overcommit，同时根据生成长度分布估计未来水位，并在风险升高时收紧 admission。

Overcommit 可以用概率水位约束。设请求 $i$ 已占用 $k_i$ 个 block，剩余生成长度的预测分布为 $G_i$，block 大小为 $P$ token，未来新增块为 $X_i=\lceil G_i/P\rceil$。调度器选择一个安全分位数，使

$$
\Pr\left(\sum_iX_i+X_{new}>K_{free}\right)\le\epsilon,
$$

其中 $K_{free}$ 是扣除当前轮保留后的空闲块，$\epsilon$ 是允许的容量违约概率。线上不必实时卷积分布，可以按长度桶保存 p90/p99 剩余块，再用相关性修正。所有请求同时使用各自 p99 会过度保守，全部使用均值又会在突发长输出时耗尽；历史上同一事件引发的长回答还可能相关，简单独立假设会低估尾部。

例如空闲 1200 block，当前 200 个请求平均还需 4 block，新入队 40 个请求平均需 6 block，均值合计 1040，看似仍有 160 block 余量。若各组 p95 分别为 5 和 9 block，保守需求达到 1360，已经越界。可只接收其中 20 个新请求，把其余路由或排队；也可允许全部进入但为低优先级请求准备抢占。选择取决于抢占重算成本与 SLO，日志要记录采用的预测分位数和当时水位。

Allocator 自身也会让逻辑空闲与可用容量不同。Block table、采样 workspace、通信 buffer 和 CUDA Graph 静态池不属于请求 KV，却会占同一显存。扩展 batch bucket 时 graph 可能预留更大的输入输出区，导致 KV 可用块突然减少。容量监控同时展示物理显存、KV allocator 总块、空闲块、已保留未提交块和 cache 引用块；只看驱动 free memory 无法判断调度器还能接收多少 token。

**Deadline 调度的数值例子。**

有三组 decode：A 的 16 个请求距离 deadline 8 ms，B 的 32 个请求剩 20 ms，C 的 16 个低优先级请求剩 50 ms。Profile 预测 A 单独 4 ms，A+B 为 9 ms，全部为 14 ms。若本轮还加入 512-token prefill，额外 7 ms。

选择 A+B+prefill 预计 16 ms，A 会晚 8 ms；选择全部 decode 14 ms，A仍晚 6 ms。调度应先跑 A 的 4 ms，再下一轮处理 B/C/prefill。虽然第一轮 batch 小、GPU 局部效率较低，却守住最紧 deadline。若 A 的 deadline 已不可达，系统记录 violation 并按策略选择最小额外伤害，而不是假装大 batch 能挽回。

Deadline 不能由最近一次 TPOT 简单外推。长上下文请求下一轮 KV 成本更高，TP collective/量化也影响。预测误差分位数可作为 guard band：模型 p95 高估/低估 2 ms，就在 8 ms deadline 下只安排预测不超过 6 ms 的工作。

**公平性的可计算形式。**

Weighted fair scheduling 可为租户 $u$ 维护虚拟服务量 $v_u$，每执行一个 token 按估计成本 $c_i$ 增加 $c_i/w_u$，优先选择最小虚拟完成时间。这样权重更高的租户获得更多服务，长上下文 token 的成本也不会与短 token 等价。

若只按 token 数公平，一个 64K 上下文 decode token 扫描的 KV 远多于 1K 请求，却计同一单位，会让资源占用不公平。成本可用预测毫秒或 HBM byte；预测不准时至少按上下文桶加权。租户级最大 KV 与并发限制防止单个大请求耗尽公共池。

Aging 解决等待饥饿。可将有效优先级写成基础优先级加 $\gamma t_{wait}$，或给每类请求最大等待上限。参数太大时退化成 FIFO，太小时长请求仍饿死。评测给每个长度桶的等待分布和服务份额，而不是只看全局均值。

**Chunk 选择与 Kernel Shape。**

假设可选 chunk 为 128、256、512、1024 token。Profile 表明单个长请求对应时间为 3、5、8、14 ms；单位 token 效率随块增大提高。当前 decode 预算剩 9 ms，选择 512；若剩 6 ms，选择 256。若有两个请求，可分别取 256，形成总 512 token 的较好 GEMM，同时保持每请求抢占点。

不过两块的已有 prefix 不同，attention 成本不同。一个 prefix 1K、一个 32K，后者 256-token chunk 可能比前者 512 更慢。查表键加入 prefix bucket。调度器还可把相近 prefix/长度组合，减少 kernel 尾效应，但等待分桶本身也增加延迟。

动态 shape 与 CUDA Graph 有张力。可为常见 $(T_p,T_d)$ 桶捕获 graph，实际请求用 padding 填到桶；未命中走 eager。桶太多占编译时间和缓存，太少 padding 大。线上统计各桶命中、padding token 与 fallback 延迟，定期调整而非手工猜。

**Prefix Cache 如何改变队列。**

一个 8K prompt 命中 7K prefix，只需 prefill 1K。调度若在查询缓存前按原长度估算，会错误延迟或拒绝；若先承诺命中、执行时条目被淘汰，又可能超预算。Prefix 条目在请求 admission/执行间需要短期 pin，或调度保留 miss 回退空间。

缓存命中会形成路由热点。某副本可省 50 ms prefill，但排队多 80 ms，发送到无缓存副本重算反而更快。全局路由比较预计完成时间，而非命中布尔值。热门 prefix 可复制，但复制占 KV block，影响活跃请求容量。

Beam search 或 n-way sampling 让一个请求从共享前缀分叉成多个 decode 序列。请求数仍为 1，活动 token 和 KV 增加 $n$ 倍；调度器以 sequence 为执行单位，同时在租户/请求层计费和限制。停止部分 beam 后及时回收私有 block。

**抢占策略的成本模型。**

候选请求 $i$ 的抢占成本可估为

$$
C_i=\min\left(\frac{2M_{KV,i}}{B_{offload}},T_{recompute,i}\right)+P_i,
$$

前项在换出往返与重算中取小，$P_i$ 是优先级/进度惩罚。选择成本低、优先级低的请求先抢占，而不是总抢最大 KV。重算时间还受未来 prefill 队列影响；繁忙时 offload 可能更好。

已生成很多输出但 prefix 短的请求，KV 长度包含 prompt+output，重算要重新跑全部已确认 token；生成接近完成时抢占尤其浪费。可以为运行足够久的请求提供 non-preemptible 窗口，避免反复抖动。高优先级新请求仍可突破，但记录代价。

抢占与恢复要防止 thrashing。若请求刚恢复就再次被抢占，说明 admission 超出稳态容量。设置最小驻留时间、恢复冷却和过载拒绝比不断搬运更有效。监控每完成 token 的重算/迁移 byte。

**Open-loop 压测与 Goodput。**

闭环压测保持固定并发：系统变慢时客户端发得更慢，无法暴露排队失稳。Open-loop 按给定到达过程发请求，无论前一请求是否完成，更接近生产突发。逐渐提高 $\lambda$，观察队列、TTFT/TPOT 和拒绝，找到 goodput 峰值。

定义请求成功需 TTFT≤$S_f$ 且 TPOT p99≤$S_t$。Goodput 是单位时间满足两者的请求数。某配置从 1000 提升到 1200 output token/s，却让满足 SLO 请求从 90/s 降到 70/s，不是在线优化。按租户/长度分别统计，防止系统只服务容易请求来美化总数。

Trace 要保留输入长度、目标/实际输出、到达时间、采样与取消，但移除敏感内容。重放同一 trace 比随机生成更适合版本回归；合成极端 trace 用于取消风暴、热门 prefix、超长 prompt 和客户端慢消费。

一个完整的负载扫描可以从每秒 4 个请求开始，每五分钟增加 1 request/s，直到拒绝率或 SLO 违约超过阈值。每档前两分钟用于消除上一档队列影响，后三分钟统计；若请求输出很长，窗口还需覆盖多个完成周期。到达时间由外部发压器预先生成，不能等响应返回后再决定下一次发送。相同 trace 在两个版本上分别运行，并固定副本数、路由、模型版本和随机输出长度，差异才可归给调度实现。

设某档到达 9 request/s，实际完成 8.7 request/s，其中 8.2 个满足 TTFT/TPOT，goodput 为 8.2 request/s；下一档到达 10 request/s，完成 9.4 个，但只有 7.5 个满足 SLO。原始吞吐仍上升，goodput 已经过峰。若此时 GPU 利用率从 82% 升到 91%，继续追求满载会让有效服务下降。容量配置应选择峰值左侧留有余量的工作点，并在一个副本下线后重新测量。

测量取消也需要统一分母。客户端在排队期间取消，说明等待体验差，但没有产生 output token；执行期间取消已经消耗 prefill、KV 和若干 decode 轮次。吞吐报告分别给出接收、开始执行、完成、取消与拒绝请求数，设备成本把取消前实际执行 token 计入，用户 goodput 只统计满足语义和 SLO 的完成请求。把取消请求从所有指标中删除，会让过载系统显得比实际健康。

**CPU 与网络的关键路径。**

每轮 GPU 8 ms 时，tokenize 通常只在请求入口，但调度、页表组装、采样和序列化每轮发生。Python 对象遍历、锁或频繁小 H2D 可能产生 1–3 ms gap。将 metadata 放连续 pinned buffer、批量更新、C++/Rust 路径或 CUDA Graph 可减少，但必须从 timeline 证明 gap。

流式输出网络慢会反压。若每请求未发送队列上限 32 token，达到后暂停 decode；继续保留 KV，等待客户端恢复。若等待超过租户策略，可换出或取消。没有上限时，主机内存增长，GPU 还为无人消费结果工作。

多副本路由也在入口关键路径。路由信息若滞后，只看上一秒 KV 水位，突发会把所有请求送到同一副本。使用 in-flight reservation 在派发时立刻增加预测负载，完成/拒绝后校正。预测错误有衰减，避免永久偏斜。

**多 Adapter 与多模型批处理。**

LoRA 服务中，请求可能选择不同 adapter。基础权重相同，但低秩增量不同。把不同 adapter 放同一 batch，可以共享基础 GEMM，adapter 部分按组执行；组太多会产生小矩阵、索引与分支。调度器在等待时间与 adapter locality 间权衡，不能无限等同 adapter 凑批。

Adapter 权重也占 HBM，可按热度缓存。Admission 前确认目标 adapter 已加载或预留加载时间；cache miss 若同步从存储读取，会让整批阻塞。可让该请求等待加载，其他请求继续；热门 adapter pin，冷 adapter LRU，但版本与租户隔离进入键。

多模型共卡更复杂：不同权重通常不能共享 GEMM，batch 只能在各模型内形成。调度器分配时间片和显存，模型切换可能需要加载/驱逐，适合请求稀疏的小模型。大模型频繁换权重的字节成本往往远高于保持独立副本。

**投机解码进入连续批次。**

投机请求一次验证多个候选，普通 decode 一次一个 token。若混在同轮，执行 token 数与确认 token 数不同。Budget 计实际 target 验证 token，吞吐/goodput 计最终确认 token；否则低接受率看起来设备很忙，用户吞吐却没提高。

不同请求接受长度不同，验证后有的确认 5 个、有的只确认 1 个，下一轮 deadline 与 KV 增长也不同。调度器依据最新确认位置重组，临时候选 KV 在拒绝后释放。Draft 模型执行可以独立批处理，但等待凑 draft batch 会增加 TPOT。

当接受率下降或系统过载，禁用投机可能更好。在线估计每类请求 $[T_d+T_v]/a$ 与普通 $T_b$，设置滞回阈值避免频繁切换。回退不改变采样分布和已确认 token。

**故障隔离与副本排空。**

滚动升级时副本进入 draining：停止接新请求，已有 decode 继续完成；长输出可能让排空很久。设置最大排空时间后，可迁移 KV 或从 token 重算到新副本。直接终止会中断流式请求，是否允许由服务协议决定。

GPU/NCCL 错误可能让一整个 TP group 失效。路由立即移除副本并撤销 in-flight reservation；等待请求可重派，已执行请求若有 token 状态可恢复。客户端收到的 token 不能重复，恢复从最近确认的序号继续。

调度器自身状态需要冗余或可重建。请求元数据、已确认 token、采样 RNG、租户计费与 KV owner 存在可靠控制面；每轮微状态可由 worker 汇报。控制面故障不能导致两个副本同时生成并双重输出。

**一个完整的过载算例。**

某副本稳定 output 能力 3000 token/s，平均每请求输出 300 token，理论约 10 请求/s。目标流量从 8 请求/s 突增到 14，若全部接收，每秒积压约 4 个请求；一分钟队列增加 240，TTFT 很快失控。

Admission 根据预测完成时间只接受约 9.5 请求/s，剩余路由其他副本或立即返回繁忙。接受流量保留 5% 安全区，应对长度误差。若短请求优先，实际请求/s 可更高，但按 output token 和 KV 同时限制，避免只挑短请求导致长请求饥饿。

系统可临时缩小 prefill chunk、限制 max_tokens、关闭低收益投机并淘汰冷 prefix，释放容量；这些措施不能创造超过硬件上限的长期服务率。扩容副本有冷启动延迟，路由在 ready 后逐步加权，避免瞬间灌满。

**调度器正确性测试。**

用参考串行引擎对同一 token ids、采样 seed 生成结果，比较连续 batch 在请求加入/退出、chunk、抢占和取消交错下的 logits/输出。非确定采样可比较分布或使用 greedy。重点覆盖 block 边界、EOS 与 max_tokens 同时触发、停止串跨 token。

状态属性可做不变量：一个物理 KV block 的引用数等于所有 table/cache 持有者；finished 请求不再被选；每个提交 batch 中 token 槽位唯一；已确认 token 序号单调；租户配额不为负。随机生成事件序列比只写固定案例更容易找到竞态。

性能回归与正确性分开。先证明结果一致，再测调度 CPU 与 goodput；为了通过性能测试而减少同步/校验，必须证明不变量仍由所有权协议保证。

**调度日志怎样保持可用。**

逐轮记录每个请求会产生巨大日志。常态保存聚合与采样：轮次 token 构成、预测/实测时间、预算拒绝原因、队列/KV 水位；异常请求或 SLO 违约再保留完整决策链。请求 id 使用脱敏标识，不记录 prompt。

决策原因应是枚举，例如 `deadline_first`、`kv_limit`、`tenant_quota`、`adapter_loading`，而不是自由文本。发布后某原因比例突变，能快速定位配置或容量变化。预测误差按 shape/阶段桶监控，驱动模型重校。

离线 replay 读取到达时间、token 长度和调度事件，在不执行模型时模拟策略，先筛参数；最终候选仍用真实引擎验证，因为 kernel 时间、cache 与争用无法由队列模拟完全复现。

**与业务语义的边界。**

调度器可以决定先后、批次、抢占和资源降级，不能悄悄改变用户请求的模型、精度、max_tokens 或采样。若产品允许低优先级切量化副本或缩短输出，必须由显式服务等级与响应元数据表达。

计费也以实际确认 token、占用时间或约定单位为准。被拒候选、重算和迁移是系统开销，不应重复计成用户输出，但会进入内部成本。多租户公平的权重与配额来自产品策略，系统只保证执行和可审计。

隐私请求可能禁止 prefix 跨请求复用或禁止 offload 到某层存储。Admission 将这些约束转成资源需求，不能为了命中率绕过。连续批处理共享计算设备不等于共享请求状态，metadata 和输出始终隔离。

调度器最终输出的不只是一个批次，还包括这轮资源归属、截止时间承诺与失败后的回收路径。预测误差可以通过测量继续校正，状态所有权和租户边界则必须在任何负载下保持成立。只有吞吐、尾延迟、容量和正确性同时纳入验收，连续批处理带来的设备利用提升才会稳定转化为可交付的服务能力。

# 投机解码：用并行验证缩短串行生成

自回归模型一次只确认下一个 token. 即使 GPU 还有大量算力，每生成一个 token 仍要重新经过所有层，下一步又必须等待这一步的结果. 投机解码试图减少的正是这条串行链：先由便宜的 proposer 猜出一段候选，再让目标模型用一次前向并行计算这些位置的分布. 猜对时，一次目标模型调用可以确认多个 token；猜错时，从第一个未通过的位置恢复目标分布，然后重新开始.

它利用了 decode 的一个系统特征. 单 token decode 常受权重与 KV 读取限制，把验证宽度从 1 增加到数个 token，设备时间未必同比增加. 多出来的矩阵维度可以提高算术强度，于是一次昂贵的权重读取服务了更多候选位置. **投机解码节省的是目标模型的串行轮数，不会减少必须由目标模型裁决的概率语义.**

## 1. 从普通采样到 draft-verify

设目标模型在当前前缀 $x_{<t}$ 上给出的分布为 $p_t(\cdot)$，草稿模型的分布为 $q_t(\cdot)$. proposer 自回归采样 $k$ 个候选

$$
\tilde{x}_{t:t+k-1}\sim q.
$$

目标模型随后把原前缀与整段候选作为输入，一次算出 $p_t,p_{t+1},\ldots,p_{t+k}$. Transformer 内部仍按 causal mask 计算，每个位置只看左侧已知 token；这里的并行来自候选已经填好，所以所有位置能放进同一次前向. verifier 从左到右检查候选，遇到首次拒绝便丢弃后面的分支. 若 $k$ 个候选全部通过，还可以从 $p_{t+k}$ 额外采样一个 token，因此一轮最多前进 $k+1$ 个位置.

贪心解码最直观：候选等于目标模型在该位置的 argmax 就接受，否则改用目标 argmax. 采样解码不能直接照搬这条规则. 若只接受 target 与 draft 恰好采到相同 token，输出会偏向两者共同偏好的区域，最终分布不再等于 $p$.

### 1.1. 接受概率为什么是 $\min(1,p/q)$

候选 $z\sim q$ 的接受概率取为

$$
A(z)=\min\left(1,\frac{p(z)}{q(z)}\right).
$$

于是候选 $z$ 被直接接受的概率为

$$
q(z)A(z)=\min(q(z),p(z)).
$$

被拒绝的总概率是

$$
R=1-\sum_v\min(q(v),p(v))
  =\sum_v[p(v)-q(v)]_+.
$$

拒绝后不能直接从 $p$ 再采一次，否则 $q$ 与 $p$ 重叠的部分会得到额外概率. 正确的修正分布为

$$
p_{res}(z)=\frac{[p(z)-q(z)]_+}{R}.
$$

最终输出 $z$ 的概率恰好为

$$
\min(q(z),p(z))+R\,p_{res}(z)
=\min(q(z),p(z))+[p(z)-q(z)]_+
=p(z).
$$

这一步给出了投机采样的关键保证：在相同数值实现与采样设置下，接受加修正仍从目标分布采样. $q(z)=0$ 的 token 不可能由 proposer 提出，却会保留在残差分布中；$q(z)>p(z)$ 的 token 只接受其中 $p(z)/q(z)$ 的比例. **所谓「无损」来自接受与残差采样共同保持 $p$，并不等于每个候选都会被接受，也不表示浮点执行逐位一致.**

温度、top-k、top-p 和词表屏蔽会改变实际分布. verifier 必须对处理后的 $p$ 与 $q$ 使用同一套定义，不能一边拿截断前 logits 算比率，一边从截断后分布采样. tokenizer 或词表映射不一致时，候选 token 也无法直接比较；部署前需要明确映射，或选用与 target 共用词表的 proposer.

### 1.2. 接受率就是两处分布的重叠面积

单个位置的期望接受率可以直接从上面的规则算出：

$$
\alpha=\mathbb{E}_{z\sim q}[A(z)]
=\sum_z q(z)\min\left(1,\frac{p(z)}{q(z)}\right)
=\sum_z\min(p(z),q(z)).
$$

离散分布的 total variation distance 为

$$
D_{TV}(p,q)=\frac{1}{2}\sum_z|p(z)-q(z)|
=1-\sum_z\min(p(z),q(z)),
$$

所以

$$
\boxed{\alpha=1-D_{TV}(p,q)}.
$$

这条等式比「draft 的困惑度够低」更贴近投机收益. 交叉熵衡量 $q$ 给真实 token 分了多少概率，接受率衡量 $p$ 与 $q$ 在整个词表上重叠多少；两个 draft 可以有相近的验证集 loss，却把剩余概率放在不同 token 上，进而得到不同接受率. 训练 proposer 时仍可用交叉熵等可优化目标，但部署选择要回到目标请求上的 $D_{TV}$、接受位置和实际成本.

多步接受率还受到前缀选择影响. 第一个候选通过后，第二步比较的是条件分布 $p(\cdot\mid x,\tilde{x}_t)$ 与 $q(\cdot\mid x,\tilde{x}_t)$；一旦前面拒绝，后面的候选不再属于真实生成路径. 因而第 $j$ 步的通过率是「已经通过前 $j-1$ 步」条件下的重叠面积. 将所有位置混成一个 token-level acceptance 会高估长连续接受段，性能模型应使用接受长度分布或逐深度条件接受率.

Total variation 也说明了 task routing 的意义. 若代码请求上 $p,q$ 高度重合，$D_{TV}$ 小，可以给更深候选；若高温对话或新领域让距离扩大，缩短 $k$ 比盲目增加 draft 算力更直接. 路由依据应采用 verifier 实际给出的接受统计，输出文本「看起来合理」无法反映两处分布的重叠面积.

## 2. 加速由平均确认长度决定

设普通 target 单步 decode 时间为 $T_b$，一轮投机的 draft 时间、target 验证时间和调度开销分别为 $T_d(k)$、$T_v(k)$ 与 $T_s(k)$. 一轮平均确认 $a(k)$ 个 token，则每个确认 token 的时间近似为

$$
T_{spec}(k)=\frac{T_d(k)+T_v(k)+T_s(k)}{a(k)},
\qquad
S(k)=\frac{T_b}{T_{spec}(k)}.
$$

假设每个位置独立地以概率 $\alpha$ 通过，只用于建立直觉. 一轮至少确认一个 token，并在前 $j$ 个候选均通过时多确认一个，因此

$$
a(k)=1+\alpha+\alpha^2+\cdots+\alpha^k
=\frac{1-\alpha^{k+1}}{1-\alpha}.
$$

当 $\alpha=0.8,k=4$ 时，平均确认长度约为 $3.36$，并非 4 或 5. 若 draft 加验证合计花费普通 decode 的 1.8 倍，理想加速约为 $3.36/1.8=1.87$ 倍. 若同一任务的 $\alpha$ 降到 0.4，平均确认长度只有约 $1.65$，相同开销已经不能带来收益.

真实接受事件并不独立. 代码、固定格式和常见短语可能连续通过，开放式创作或分布外输入会在早期频繁拒绝；高温采样也通常降低 proposer 与 target 的重合. 因此一个全局平均接受率不足以预测性能，至少要记录每轮首次拒绝位置、平均接受长度、全接收比例与请求类型.

### 2.1. 候选长度不是越大越好

增大 $k$ 会提高一轮可能确认的 token 数，也会增加 draft 串行步骤、验证宽度、临时 KV 和被早期拒绝后作废的计算. 当 $\alpha^k$ 已很小时，再增加候选几乎不增加 $a(k)$，却仍抬高 $T_d$ 与 $T_v$. 最佳 $k$ 随负载变化：低并发时 target 单步未充分利用 GPU，较宽验证容易获益；高并发时 continuous batching 已经让权重读取服务大量序列，额外候选会与真实请求争夺 token budget.

在线控制可以按最近接受长度调节 $k$. 连续多轮全接收时缓慢增大，早拒绝频繁时缩小或暂时关闭. 控制器还要看队列与 batch：即使单请求适合投机，系统过载时也可能优先把设备宽度留给其他请求. vLLM 的官方说明把适用区域放在中低 QPS、memory-bound 的工作负载，背后的原因正是这里的机会成本.

### 2.2. 带宽模型给出的收益上界

将普通 decode 一轮拆成权重字节 $W$、活跃请求读取的 KV 字节 $K(B,S)$、其他字节 $M$ 与计算量 $F$. 在 memory-bound 区间，其时间下界近似为

$$
T_b\ge \frac{W+K(B,S)+M}{BW_{eff}}.
$$

验证 $k$ 个候选时，权重通常仍只需为这次 forward 读取一遍，线性层可以把多个候选合成更宽的矩阵；KV、activation 和 attention 工作却随候选树节点数 $n$ 增长. 可写成

$$
T_v(n)\gtrsim \max\left(
\frac{W+K_v(B,S,n)+M_v(n)}{BW_{eff}},
\frac{F_v(B,S,n)}{P_{shape}}
\right).
$$

投机能够利用的空间，是 $T_v(n)$ 尚未随 $n$ 线性增长的那一段. 单请求、小 batch 下 $W$ 占主导，增加几个验证位置只增加较少 KV/activation 字节，容易把一次权重搬运摊给多个确认 token. Batch 已经很大时，普通 decode 本就让 $W$ 被许多请求共享，$K(B,S)$ 和计算占比上升；投机再扩宽矩阵的边际收益会缩小.

把 $c_d(n)=T_d(n)/T_b$、$c_v(n)=T_v(n)/T_b$、$c_s(n)=T_s(n)/T_b$ 归一化，速度上界为

$$
S(n)=\frac{a(n)}{c_d(n)+c_v(n)+c_s(n)}\le a(n)\le n+1.
$$

右侧只是串行轮数给出的绝对上界，实际还要支付 proposer 和调度成本. 即便验证在硬件上近似「免费」，独立 draft 若也需要完整读取一套权重，$c_d$ 仍可能很大；树候选若有很多低概率节点，$n$ 增长快于平均确认长度，$c_v$ 会先接管. 因此硬件感知的候选深度不能只追求接受 token 数，还要比较每新增一个节点带来的期望确认增量与验证时间增量.

内存容量构成另一条上界. 独立 draft 需要权重和 KV，多头或特征 proposer 需要额外层与临时候选状态. 若这些常驻字节令 target 的 KV block 减少，最大连续 batch 随之下降. 单请求延迟的改善可能以更低并发上限为代价；容量评估必须把 draft 权重、draft KV、target 候选 KV 和验证 workspace 一并列入，而不能只看算法前向时间.

## 3. proposer 不只是一台小模型

最初的做法使用独立 draft 模型. 它实现直接，能够替换而不修改 target，却多出一份权重、KV 与发布制品. Draft 太小，分布差异扩大；太大，接受率虽高，起草本身又吃掉收益. 模型家族、tokenizer 和训练数据接近通常有利，但最终仍要用目标请求分布测接受长度.

另一类方法从 target 自身派生候选. Medusa 在 backbone 上增加多个预测后续位置的 head，形成候选树，再用 tree attention 一次验证多条路径. MTP 也可充当 proposer：模型原生的多 token 预测层给出未来候选，主干仍负责确认. 这类方法省去完整的第二模型，代价是需要额外训练制品，候选分支和验证布局也更复杂.

EAGLE 路线用轻量 draft 网络结合 target 的 hidden state 递归预测后续候选. Hidden state 比单个离散 token 携带更多上下文信息，能够在较低 draft 成本下提高接受长度. 它同时增加了版本耦合：target 中间层接口、draft checkpoint、词表映射和推理引擎实现必须成套发布.

没有额外模型时，还可以从 prompt、历史输出或共享前缀中寻找 n-gram/suffix 候选. 重复性高的代码补全、文档续写可能命中；一般对话中候选质量较弱. 这条路线的价值是 proposer 几乎不占 GPU 计算，高负载下也不一定挤压 target batch. **这些方法可以更换候选来源，target 验证始终是共同的裁决点；比较时应固定 verifier、采样语义与服务负载.**

### 3.1. 多候选树怎样用一次 target 前向验证

线性候选每个深度只有一个 token，早期猜错后整条后缀都会作废. 候选树在同一深度保留多个分支，用更多验证节点换取至少一条路径与 target 对齐的机会. 根节点是已确认前缀，树中每个节点代表「从根走到这里」的一段候选. Target 需要为每个节点计算下一 token 分布，却不能让兄弟分支互相看见，否则某条路径的 logits 会混入另一条不属于其前缀的 token.

Tree attention 为每个节点建立祖先 mask：节点只能关注公共前缀和自身根路径上的祖先. 所有树节点可以打包进同一次 forward，共享 target 权重读取；验证结果再沿被采中的路径逐层前进. SpecInfer 使用这种 token tree 同时验证多条候选序列，Medusa 也用树结构组织多个预测 head 给出的候选. 这里的「并行验证」指合并为一张带特殊 mask 的计算图，不代表每条路径拥有独立完整 KV 副本.

树的物理布局必须去掉公共节点. 假设两条候选分别是 `A→B→D` 与 `A→C→E`，逻辑上共有 6 个位置，实际树只有根后的 5 个唯一节点，`A` 的 K/V 计算一次并由 B、C 两支引用. 若另两条路径都是 `A→B` 开头，这一段也只保留一份. 将候选序列直接 padding 成普通 batch 会重复计算公共前缀，树越宽，浪费越大.

去重不只按 token id. 同一个 token 出现在不同父节点下，历史前缀不同，位置上的 hidden state 与 K/V 也不同，不能合并. 合法合并要求从根到节点的 token 路径一致；实现中通常由树节点身份或路径哈希区分. 验证结束后只提交最终接受路径上的节点，其余分支立即释放.

树宽和树深承担不同风险. 加深是在押注同一路径连续正确；加宽是在同一深度覆盖更多可能 token. 低温、分布尖锐时深链更划算，高温或 $p,q$ 差距较大时适当分叉可提高覆盖，但节点数迅速增长. Sequoia 因此把树结构选择写成依赖接受概率与硬件代价的优化问题，而不是固定每层保留相同分支数.

### 3.2. 精确采样与近似接受不能混在同一口径

标准 speculative sampling 用 $\min(1,p/q)$ 与残差分布恢复 target 的采样分布，属于精确路线. 贪心解码的逐 token 一致也属于明确语义：最终路径必须等于 target 独立 greedy decode. 树验证可以继续保持这些语义，但路径选择、兄弟候选概率扣除和修正采样要与所采用的证明一致，不能把线性接受公式机械套到任意候选树.

有些系统采用阈值接受、typical acceptance、top-k 候选命中或近似树裁剪，以更高接受长度换取质量近似. 这类方法可能很实用，却已经改变目标分布，必须按任务质量与偏差评估，不能沿用「无损」标签. Medusa 区分了保持原模型分布的拒绝采样方案与偏向典型 token 的接受方案，正说明接受规则本身就是解码算法的一部分.

数值实现也可能破坏理论上的相同分布. $p,q$ 经过不同精度 softmax、不同 top-p 边界处理或不一致的随机数消费后，数学公式相同，运行分布仍会出现偏差. 精确路线应固定 logits processor 顺序、归一化精度、EOS 与约束解码状态，并用统计检验验证；近似路线则明确记录规则和质量交换. **只要接受判据绕开了目标分布的修正步骤，得到的速度就不能与精确投机解码放在同一条无损曲线上比较.**

## 4. KV 状态必须支持暂存、提交和回滚

投机一轮至少有三段状态：已经确认的前缀、尚待验证的候选、拒绝后生成的修正 token. Draft 与 target 都可能维护各自 KV. 旧前缀可继续复用；候选对应的新 block 只能暂存，验证结束后将接受部分提交，拒绝位置之后的 block 释放. 若实现先把整段候选并入正式页表，再靠覆盖 token 文本回滚，KV 仍可能残留错误分支，之后的 logits 会悄悄漂移.

分页缓存适合表达这个事务. 候选页从已确认页表分叉，旧 block 只读共享，新 token 写入临时 block；verifier 返回接受长度 $m$ 后，前 $m$ 个位置转为正式所有权，其余引用计数递减. 发生取消、超时或 kernel 失败时，临时页必须全部回收. 需要覆盖的测试包括首个候选拒绝、全部接受、跨 block 边界拒绝、共享前缀上的 copy-on-write，以及请求在验证中途被取消.

Target 验证整段候选时，通常已经计算出候选各位置的 target KV. 被接受的位置可以直接保留，无需再逐 token 重算. 首次拒绝处从残差分布采出的修正 token 是否已有可用 KV，取决于 forward 输入与 logits 的位置定义；很多实现需要让下一轮再计算它，或专门安排一次追加. 计数性能时必须按实际 target forward 和确认 token 统计，不能只用算法图里的轮数.

### 4.1. Prefix cache 与投机缓存是两种复用

Prefix cache 命中的是已经由同版本模型算过、token 完全一致的过去前缀，主要减少 prefill. 投机缓存保存的是尚未确认的未来分支，主要减少 decode 串行轮数. 两者可以共享 block allocator，却需要不同生命周期：prefix block 可跨请求长期保留，candidate block 只活过一轮验证.

容量压力下，冷 prefix、活跃 target KV、draft KV 与 candidate block 会竞争 HBM. 淘汰策略先保护活跃已确认状态；临时候选必须有硬上限，避免大 $k$ 或候选树在峰值流量中挤掉正在生成的请求. 只看 prefix 命中率或接受率都无法判断容量是否值得，应换算成每保留 GiB 避免了多少设备时间.

## 5. 连续 batching 会改变局部收益

单请求 benchmark 常把 draft 和 verify 顺序执行，容易看到较高加速. 在线引擎面对的是不同候选长度、不同拒绝位置和不同上下文的 ragged batch. 调度器需要决定 draft 与普通 decode 是否共批、验证 token 占多少 budget、已完成起草的请求能等待多久. 为凑齐验证批而多等几毫秒，可能抵消减少一次 target 调用的收益.

一种做法把每个候选位置都计入统一 token budget. 普通 decode 请求消费一个 token，投机请求按验证宽度消费多个 token；调度器根据 deadline 与预计接受长度决定是否准入. 另一种做法将 proposer 与 verifier 分到不同 stream 或设备池，但会增加 hidden state、token 和控制消息的传输. 无论采用哪种布局，队列时间都要进入 $T_s(k)$.

投机也会改变流式输出. 未经 target 确认的 token 不能提前发送给客户端，否则拒绝时需要撤回，API 语义随之改变. 一轮确认多个 token 后可以一次推送，也可以按顺序快速发送；前者减少网络调用，后者更接近稳定出字节奏. TTFT 通常不会因 decode 投机直接下降，主要变化落在 TPOT、完成时延和 output token/s.

### 5.1. 单请求时延与服务吞吐为何可能反向

低负载时，普通 decode 的 batch 很小，设备每轮仍要读取 target 权重，许多计算单元没有吃满. 投机把同一请求的多个候选位置塞进验证矩阵，增加有效工作却没有明显增加排队，平均 TPOT 因而下降. 这是最容易观察到投机收益的区域.

到达率升高后，continuous batching 已经用不同请求填满矩阵. 普通 decode 的每次权重读取原本可以确认 $B$ 个 token；若其中若干请求改为验证 $n$ 个候选，单轮 token 数变多，但最终确认数由接受长度决定，被拒分支消耗了与真实请求相同的计算槽位. 此时投机请求的局部并行会挤掉等待队列里的普通请求，单个已入批请求可能更快，系统完成的请求数和 SLO goodput 却可能下降.

用一个简化例子可以看清方向. 某设备每轮 token budget 为 128. 普通 decode 可服务 128 个请求并确认 128 个 token. 若 32 个请求各验证 4 个候选，预算已经用完；假设每个请求平均确认 2.5 个 token，本轮只确认 80 个 token. 这些请求自身跨过了更多位置，系统总确认量却从 128 降到 80，还没有计入 draft 时间. 若平均确认长度达到 4，才与普通批次的确认量持平，额外 draft 与 workspace 仍需另外回收.

反方向也可能出现：负载尚未饱和、队列没有足够请求凑成大 batch 时，投机节点填补了空闲宽度，吞吐和时延一起改善. 所以投机开关应读取当前队列、有效 batch、候选接受长度与 SLO，而不是只按模型配置静态开启. SmartSpec 的出发点正是 continuous batching 下高到达率或低投机准确率会增加延迟，需要允许候选长度降到 0.

吞吐指标也要区分「验证 token/s」与「确认 token/s」. 前者把最终丢弃的树节点算作工作，数值可能很好看；后者才对应用户得到的输出. 服务比较固定同一到达 trace 和 SLO，报告 target 实际处理节点、确认 token、请求完成率与分位延迟，才能判断投机究竟利用了空闲资源，还是把正常 batch 换成了更多作废计算.

## 6. 一套能解释结果的验收方法

先建立普通 target decode 基线，固定模型、tokenizer、采样参数、随机数语义、输入 token 与输出上限. 正确性测试对小词表分布做大量采样，比较经验频率与目标 $p$；再对真实模型覆盖 temperature、top-k、top-p、EOS、受限词表与全候选接受/首候选拒绝. 贪心路径应逐 token 一致，采样路径检验分布而非要求两次运行生成完全相同文本.

性能实验至少拆出以下量：

- proposer 每轮时间与候选 token 数；
- verifier 时间、验证宽度与上下文长度；
- 每轮接受 token、首次拒绝位置和全接受率；
- target forward 次数、确认 output token/s 与 TPOT；
- target、draft、临时候选各自占用的 KV block；
- 调度等待、batch 大小、输入输出长度分布与 QPS.

测试负载要从单请求扫到服务饱和. 低 QPS 下观察单请求延迟，高 QPS 下比较满足同一 TTFT/TPOT SLO 的 goodput. 若投机让单请求快 1.8 倍，却因 draft 占用和验证宽度使饱和 goodput 下降，就只能用于交互式低负载队列，不能全局默认开启.

还要分任务. 代码补全、固定模板和结构化输出可能拥有长接受段；开放问答、高温创作与 target 刚更新而 draft 未更新时容易早拒绝. 按领域汇总才能让自适应策略知道何时退出. 发布新 target 后先重跑接受长度与数值测试，不能沿用旧 draft 的历史加速比.

**投机解码的上线门槛可以压成两个不变量：输出仍服从 target 的解码分布，端到端每确认 token 成本确实下降.** 前者由接受规则、采样处理与 KV 提交保证；后者由接受长度、draft/verify 时间和在线调度共同决定. 两条同时成立，减少串行轮数才真正转化为用户看到的更快生成.

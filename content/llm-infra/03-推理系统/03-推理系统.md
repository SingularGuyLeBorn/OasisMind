# 推理系统：从请求到 token

推理系统把不规则请求转换为设备可以高效执行的批次。prefill 同时处理多个 prompt token，常接近计算受限；decode 每步追加一个 token，持续读取权重和历史 KV，常接近带宽受限。两阶段的 shape、资源瓶颈与服务指标都不同，平均成一个 token/s 会同时掩盖首 token 延迟与逐 token 延迟。

本章沿请求生命周期展开：进入队列、前缀处理、KV 分配、连续 batching、逐步解码、流式返回与资源回收。后续覆盖 paged KV、prefix cache、量化、投机解码、模型并行、请求调度和多租户隔离。每种技术都要说明改变了计算、字节、容量还是排队时间。

## 导航

TTFT、ITL、吞吐与尾延迟给出了用户侧口径；引擎内部的数据结构解释这些指标如何产生；跨副本路由和容量规划则决定服务在流量变化时能否守住它们。离线满批吞吐不能直接代表在线服务能力；实验必须给出输入输出长度分布、并发、精度、硬件以及延迟分位数。

## 1. 一次请求在系统里经历什么

请求在网关完成鉴权、限流与 tokenizer，由路由器选择模型副本。引擎把 prompt 放入等待队列，调度器决定何时加入 prefill 批次。prefill 一次处理输入 token，生成每层 K/V 并写入缓存，同时产出首个 token 的 logits。随后请求进入 decode 循环：每轮只处理新 token，却要读取此前全部 KV；采样结果被送回客户端，同时新 K/V 追加到页表。生成结束、取消或超时后，缓存块才归还空闲池。

这条路径里有三种时间。排队时间取决于到达率、优先级和批处理窗口；设备时间取决于 shape、模型与硬件；框架时间包括 tokenizer、调度、内存分配、采样和网络发送。只看 GPU kernel 会漏掉第一和第三种，只看端到端又无法定位设备为何空闲。三类时间必须放在同一条时间线上。

### 1.1. 指标先回答用户等待的哪一段

首 token 时延 TTFT 从请求到达到第一个 token 返回，包含排队与 prefill。token 间时延 ITL/TPOT 描述流式阶段相邻 token 的间隔，受 decode 节拍和批次轮转影响。完整请求时延还与输出长度相关。吞吐可以按请求/s、输入 token/s、输出 token/s 或总 token/s 统计，四个分母不同，不能混用。

假设一个请求排队 15 ms、prefill 35 ms，随后生成 100 个 token，每个间隔 20 ms，则 TTFT 为 50 ms，生成阶段约 2 s。总时延除以 110 个输入输出 token 只得到混合均值，无法表示首 token 等待或生成节奏。服务报告至少给出输入/输出长度分布、并发、TTFT 与 TPOT 的 p50/p95/p99，并说明超时和取消是否进入样本。

**推理优化同时受两个目标约束：让更多 token 穿过设备，也让每个请求在截止时间前得到服务。** 增大 batch 往往提高吞吐，却可能拉长排队和单轮 decode；最优点由服务等级目标决定，不是离线峰值决定。

## 2. Prefill 与 Decode 是两种工作负载

prefill 将 $B\times S$ 个 token 合并为较大的矩阵乘，权重可被许多 token 复用。attention 需要处理 prompt 内的 token 关系，工作随长度增长；采用分块精确 attention 后可以避免把完整 $S\times S$ 矩阵写入 HBM，但算术量仍在。decode 每个活动序列每轮只有一个 query，矩阵乘的 $M$ 维等于活动请求数，权重和 KV 读取更容易成为瓶颈。

因此两阶段不该共用一套批处理阈值。把很长 prefill 与 decode 混在一轮里，prefill 可能阻塞所有正在流式输出的请求；完全分开又可能造成设备空隙。chunked prefill 把长 prompt 切成 token budget 可控的小块，让调度器在块之间插入 decode。块太大，ITL 抖动；块太小，重复调度和 kernel 效率下降。

### 2.1. Token budget 比请求数更接近真实工作

两个请求都算一个请求，但 32 token prompt 与 32768 token prompt 的 prefill 成本差几个数量级。调度器按总 token、KV block 和预计执行时间设预算，比只限制请求数稳定。decode 也要按当前上下文长度看成本：读取 KV 的字节随历史增长，同一批 64 个请求在生成早期和晚期并不等价。

长度分桶可以减少 padding，却会牺牲到达顺序与公平性。短请求优先能改善平均 TTFT，长请求可能饿死；严格先来先服务避免饥饿，却让长 prompt 形成队头阻塞。工程上通常给等待时间加权或设置 aging，使优先级随等待上升。评价调度策略时除平均值外还要看不同长度分组的尾延迟。

## 3. KV Cache 是推理引擎的状态核心

单请求 KV 容量近似为 $2LSA_{kv}Dw$, 其中 $L$ 是层数、$S$ 是已缓存长度、$A_{kv}$ 是 KV head 数、$D$ 是 head 维度、$w$ 是元素字节。它随上下文和并发线性增长。分页缓存把连续逻辑 token 映射到固定大小物理 block，避免为最大长度预留整段连续空间，并允许不同请求交错增长。

分页不是免费午餐。block 太大产生内部碎片，短请求尤其浪费；block 太小增加页表、地址计算和 kernel 分段。prefix cache 让相同前缀共享只读 block，可省 prefill 计算与容量，但需要可靠的内容哈希、tokenizer/模型版本隔离与引用计数。系统不能仅凭文本字符串复用，因为模板、特殊 token、位置编码参数或 adapter 不同都会让 KV 失效。

缓存不足时可以拒绝新请求、抢占并重算、换出到主机/远端，或压缩/量化 KV。每种策略移动的瓶颈不同。重算消耗算力，换出消耗 PCIe/网络且恢复有截止时间，量化减少字节却增加反量化和误差。选择前先量化 block 缺口、预计等待和请求剩余长度。

## 4. 连续批处理与公平性

静态 batching 等整批请求全部结束后再换下一批，短请求会被最长输出拖住。连续 batching 在每个 decode step 后移除完成请求、加入新请求，设备保持较高占用。代价是每轮 batch shape 和页表不断变化，调度器必须快速完成选择，kernel 也要支持 ragged sequence。

一轮时间近似由批中最重的工作和 kernel 实现决定。加入一个超长上下文请求可能增加 KV 扫描，导致其他请求 ITL 一起上升。调度器可按长度分组、限制单轮 token budget，或给不同服务等级独立队列。隔离越强，闲置容量越难共享；共享越充分，租户间干扰越明显。

取消请求是必须进入设计的正常路径。客户端断开后若要等当前大 kernel 或整批结束才能回收 KV，取消风暴会造成显存假满。调度器、执行器和流式传输需要传播取消状态，并在安全边界释放页表引用。监控同时记录逻辑活跃 token、已分配 block 与不可立即回收 block，才能看见泄漏或延迟回收。

## 5. 扩展到多设备

模型放不进单卡时可用 tensor parallel、pipeline parallel 或 expert parallel。TP decode 每层都要 collective，小消息延迟会累计；PP 把层分段，会增加 stage 间 activation 传输和流水空泡；MoE 需要按 token 路由做 all-to-all。并行度越大不一定单请求越快，因为每 token 路径上的同步也更多。

另一条路线是增加副本。副本提升总吞吐并隔离故障，但每个副本都复制权重，低负载时利用率下降。路由器不能只按请求数均衡，应考虑已占 KV、prompt 长度、prefix cache 命中与预计完成时间。带公共前缀的请求送到已有缓存的副本可能省大量 prefill，但若该副本已拥塞，命中收益会被排队抵消。

Prefill/Decode 分离把计算密集的 prompt 与带宽敏感的生成放到不同设备池。它允许分别选择批次和硬件，却要迁移 KV。一次迁移的字节由模型层数、KV head、上下文和精度决定；目标 decode 节点必须在首 token 截止时间内收到可用层。调度收益应减去 KV 传输、额外排队与故障处理成本。

## 6. 从请求时间线选择优化方向

《Prefill 与 Decode》从 shape 和 roofline 解释两阶段为何需要不同 kernel 与调度。《KV 缓存》继续进入分页、前缀复用、量化和换出。《连续批处理》关注 token budget、公平性、取消与尾延迟。《PD 分离》讨论 KV 传输、跨池路由和失效恢复。《投机解码》则把小模型提出候选、大模型并行验证的收益写成接受率与额外计算的函数。

请求时间线与显存表共同决定优化方向。每项优化都要标出它减少的是 FLOPs、HBM 字节、KV 容量、launch 次数还是排队时间，再检查成本是否移到了另一阶段。这样才能从可测量的资源变化预测调度结果，而不是把推理引擎当作一组互不相干的开关。

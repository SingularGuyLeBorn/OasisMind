# 混合专家模型

2017 年 Google Brain 的 Shazeer 论文把 MoE 做到了 **137B 参数**——当时最大的语言模型。Switch Transformer 进一步把路由简化成 top-1,降低了通信开销并改善了训练稳定性。这条线后来被 Mixtral、DeepSeek-V2 等模型采用,成为 2024–2025 年开源大模型常见的架构选择。理解 MoE 需要同时追踪**路由决策、负载均衡、专家容量和稀疏激活的实际计算成本**。

混合专家模型让每个 token 只激活少数专家,以近似不变的单样本前馈计算换取更大的参数容量.参数没有消失:权重仍需存储,专家需要分布在设备上,token 还要经过跨设备 dispatch 和 combine.因此容量增长能否转成吞吐或质量收益,取决于路由分布,通信拓扑和训练稳定性.

## 条件计算改变了参数与 FLOPs 的关系

稠密前馈层对每个 token 使用同一组参数.设有 $E$ 个专家,每个专家都是 FFN,路由器只选择其中 $k$ 个,则总参数量可随 $E$ 墓加,单 token 的专家计算主要随 $k$ 变化.当 $k\ll E$ 时,模型获得更大参数容量,却不必在每个样本上执行全部专家.这就是条件计算的基本收益.

「计算近似不变」只计算专家矩阵乘还不够.路由器本身需要打分,token 要按专家重新排列,跨设备发送,专家输出再发送回来并恢复原顺序.训练还要保存激活,更新被选专家并同步共享层.专家越分散,网络通信越容易覆盖理论上省下的 FLOPs.

### 路由器同时承担选择和流量控制

稀疏门控 MoE 为每个 token 产生专家分数,加入噪声后选 top-$k$,再对入选分数归一化.可导权重让路由器和专家联合训练,离散 top-$k$ 决定实际执行集合.早期随机波动会形成正反馈:常被选中的专家获得更多梯度,能力提升后又更容易被选择,其余专家逐渐闲置.

Shazeer 等人用 importance 与 load 两类辅助损失抑制集中.importance 衡量一个 batch 内各专家门权重之和,load 估计专家被选中的概率;二者的变异系数越大,说明流量越不均衡.辅助目标把系统容量约束反馈给学习过程,但其系数过大也会强迫路由接近均匀,损害按内容专门化.

Switch Transformer 把 top-$k$ 简化为 top-1.每个 token 只经过一个专家,dispatch 和 combine 更简单,专家计算也不再需要加权合并多个输出.路由概率仍乘在专家输出上,路由器可以获得梯度.简化降低了通信与实现复杂度,同时失去多专家混合提供的冗余.

### 容量上限决定溢出如何处理

静态编译设备需要预先知道专家输入张量形状.每个专家的 capacity 通常按 batch token 数除以专家数,再乘 capacity factor.若某专家收到的 token 超过上限,多出的 token 会被丢弃专家路径或经残差旁路传递.容量设得大,缓冲区浪费且通信增多;容量设得小,溢出 token 得不到专家变换.

负载均衡损失只能改变平均分布,不能保证每个 batch 都无溢出.数据并行组大小,序列长度,路由相关性和 token 排序都会影响瞬时峰值.工程评测因此要同时报告平均负载,最大负载,溢出率,capacity factor 和 all-to-all 时间.只给激活参数量或理论 FLOPs 无法判断真实吞吐.

### 专家并行怎样搬运 token

常见布局把不同专家放到不同设备.共享 attention 层完成后,本地 token 根据路由目标打包,通过 all-to-all 发送到专家所在设备.各设备对收到的 token 分组执行专家 FFN,再通过第二次 all-to-all 把结果送回原设备.这一过程要求保存原位置与路由权重,才能正确 combine.

专家并行经常与数据并行,张量并行和流水线并行组合.专家 FFN 太大时还会在专家内部做张量并行;每设备 token 太少时,GEMM 形状变小,硬件利用率下降.因此增加专家数可能提高总容量,却让单专家 batch 变小.吞吐最优点由模型宽度,token 数,网络带宽和并行组共同决定.

## 稳定性来自多处约束

路由 logits 可能在低精度下溢出或过度尖锐.Switch 论文保留路由器的 FP32 计算,使用较小初始化并加入负载均衡项.训练中还要观察专家梯度范数,token 分布和路由熵.若少数专家长期过载,主损失仍可能下降,系统吞吐却恶化;若路由近乎均匀,专家又可能没有形成有用分工.

专家专门化也不能只靠可视化几个 token 下结论.需要比较路由与语言,领域,位置或语义标签的统计关联,并检查更换随机种子后是否稳定.模型质量来自总容量,数据和优化共同作用,路由可解释性不是 MoE 有效的必要条件.

### 阅读两篇经典时看同一组量

Sparsely-Gated MoE 建立 noisy top-$k$,负载损失,专家并行和大规模语言模型实验;Switch Transformer 选择 top-1,并围绕稳定性,迁移与更大规模 TPU 训练重新设计.二者比较时应对齐专家数,每 token 激活专家数,稠密基线 FLOPs,训练 token,硬件和容量因子.

现代 MoE 会继续改进无辅助损失均衡,共享专家,细粒度专家与通信 kernel,但基本矛盾没有变化:参数容量通过稀疏激活增长,路由器决定计算分配,分布式系统负责把这种稀疏性兑现成速度.理解这三层之后,才能判断一个 MoE 改进究竟扩大了模型,减少了计算,降低了通信,还是只改变了路由分布.

### 一个最小容量计算

设一个 batch 有 1024 个 token,8 个专家,capacity factor 为 1.25,则每个专家容量为 $1024/8\times1.25=160$.完全均匀时每个专家接收 128 个 token,共有 32 个冗余位置.若路由把 220 个 token 送往同一专家,其中 60 个会超过容量;其他专家有空位也不能自动接管,除非路由规则允许次选专家或重新分配.

这个例子说明平均负载均衡与局部拥塞不同.辅助损失可能让整个训练期的专家使用率接近,单个 batch 仍会因相似 token 聚集而溢出.增大 batch 可以平滑比例,却提高激活内存和通信消息;增大 capacity factor 降低丢弃率,却让 all-to-all 缓冲区和专家计算上界增大.

### 质量比较的三个基线

第一类基线对齐每 token FLOPs,用于判断稀疏参数是否提高质量;第二类对齐总参数或显存,用于判断激活稀疏性的资源效率;第三类对齐 wall-clock 与硬件,用于判断系统实现是否兑现理论收益.三种比较可能给出不同结论,都应保留.

路由分析还要区分训练和推理.训练时 batch 大,专家流量较稳定;在线推理时 batch 小且序列逐步到达,all-to-all 延迟更难摊薄.一个训练吞吐很高的布局未必适合低延迟服务.模型论文中的 perplexity,系统论文中的 tokens/s 和部署中的尾延迟共同描述 MoE,任何单一数字都不够.

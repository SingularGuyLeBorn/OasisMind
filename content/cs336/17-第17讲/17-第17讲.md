# 第17讲: 从公式到系统实现 GRPO

第16讲给出了 GRPO 的目标函数,第17讲把它落实成一次能够运行和检查的训练 step.公式里一条样本可以写成 $(x,y,R)$,系统里却同时存在 prompt token、$G$ 条不同长度的 completion、生成时旧策略的 log probability、训练时当前策略的 log probability、reference log probability、验证器输出、padding mask 与样本版本.**实现是否正确,取决于这些张量能否沿着同一个 sample ID 对齐.**

这一讲只有一篇[主讲义](./17.1-主讲义/17.1-主讲义.md),因此章首页不再重复罗列算法家族,而是先建立实现的检查坐标.读者应能从一个 prompt 进入 rollout worker,跟随 $G$ 条回答经过 verifier 与组内归一化,再进入 actor update;也应能判断某个训练曲线异常究竟来自 reward、mask、版本差,还是分布式数据重排.

## 一批 GRPO 数据是什么形状

设 prompt batch size 为 $B$,每个 prompt 生成 $G$ 条回答,padding 后最大 prompt 长度为 $S$,最大 completion 长度为 $T$.Prompt tokens 的 shape 是 $[B,S]$;复制并展开后,completion tokens、completion mask 与 token-level old log probability 的 shape 都是 $[B,G,T]$.Verifier 给每条完整回答一个 reward,shape 为 $[B,G]$.

组内均值与标准差沿 $G$ 维计算:

$$
\mu_i=\frac1G\sum_{g=1}^{G}R_{i,g},
\qquad
\sigma_i=
\sqrt{\frac1G\sum_{g=1}^{G}(R_{i,g}-\mu_i)^2}.
$$

序列 advantage 为

$$
A_{i,g}=\frac{R_{i,g}-\mu_i}{\sigma_i+\varepsilon},
$$

再广播成 $[B,G,T]$,并由 completion mask 去掉 EOS 之后和 padding 位置.这里的 reduce 轴不能写错:如果把整个 batch 一起归一化,简单 prompt 与困难 prompt 会互相改变 baseline,算法便不再是组内相对优化.若 $G=1$,每组都没有相对差异,GRPO advantage 恒为 0;若某组 rewards 完全相同,该组在当前 step 也不给出排序梯度.

回答长度不同会影响 loss 聚合.先对所有有效 token 求和再除以全 batch token 数,会让长回答贡献更多 token;先对每条回答取 token mean,再对 $B\times G$ 条回答平均,则让每条序列权重接近相同.两种 reduction 对应不同目标,必须写进实验配置.EOS 是否属于 completion mask 也会改变长度与概率口径,rollout 和训练侧应使用同一套 tokenizer 与 chat template.

## Rollout 生成后必须冻结哪些量

Rollout worker 用行为策略 $\pi_{\mathrm{old}}$ 生成 token,并保存每个已采样 token 的 $\log\pi_{\mathrm{old}}(a_t\mid s_t)$.Actor 更新时重新前向得到 $\log\pi_\theta(a_t\mid s_t)$,构造

$$
r_t(\theta)=
\exp\left(
\log\pi_\theta(a_t\mid s_t)
-\log\pi_{\mathrm{old}}(a_t\mid s_t)
\right).
$$

旧 log probability 是采样分布的证据,不能在 actor 已更新后重新算.若 rollout worker 与 trainer 的权重同步存在延迟,样本必须记录 policy version;训练端要么按版本找到对应 old probability,要么丢弃超过允许 staleness 的样本.把任意旧样本都称为 on-policy,会让 importance ratio 的分母失去明确含义.

Reference policy 解决另一个问题.它通常冻结在某个 SFT 或起始 checkpoint,用来计算 policy 偏离.Reference log probability 可以在训练时前向,也可以缓存;只要 tokenizer、模板、截断和 EOS 规则发生变化,缓存就必须失效.Old policy 与 reference policy 有时初始权重相同,但职责不同:前者随 rollout 版本变化,用于 ratio;后者固定,用于 KL regularization.

权重同步本身也需要定义完成条件.Rollout worker 若采用 tensor parallel 或独立推理引擎,actor checkpoint 可能经过格式转换和异步广播.系统应在生成前记录已加载权重的版本,并用少量固定 prompt 对比 logits 或 token probability,确认训练框架与推理框架对 tokenizer、RoPE、精度和模型结构的解释一致.只校验文件名无法发现加载了部分旧 shard 或转换遗漏.

随机性同样属于样本语义.采样温度、top-p、随机种子和 stop condition 决定行为策略实际分布.复现实验至少要保留这些字段;若不同 worker 使用重复种子,同组回答可能高度相似,表面上的 $G$ 没有带来足够探索.Group 内可以去掉完全重复回答,但去重后要重新定义组大小与归一化,不能继续假设每组固定拥有 $G$ 个独立样本.

**一条 rollout 至少要绑定 prompt ID、group ID、sample ID、policy version 和 verifier version.**分布式 all-to-all、动态 batching 或长度排序都可能改变张量顺序,只依赖数组位置连接 reward 与 token 很危险.系统应在重排后显式校验 ID,并检查每个 group 恰好拥有 $G$ 条属于同一 prompt 的回答.

## 从 verifier 输出到 clipped loss

Verifier 先解析回答,再返回 reward 与状态码.数学题可能区分答案缺失、格式错误、等价判断失败和正确;代码题还要记录编译失败、runtime error、timeout 与测试通过数.若所有失败都映射为 0,训练公式可以保持简单,但监控必须保留细分类别,否则 reward 上升时无法判断是 reasoning 改善,还是模型只学会了输出格式.

对有效 token,GRPO 使用 PPO 风格的 surrogate:

$$
L_{i,g,t}(\theta)=
\min\left(
r_{i,g,t}(\theta)A_{i,g},
\operatorname{clip}(r_{i,g,t}(\theta),1-\epsilon,1+\epsilon)A_{i,g}
\right).
$$

正 advantage 时,过大的概率提升被上界裁剪;负 advantage 时,过度降低概率的一侧被裁剪.实现中不能先对 ratio 跨 token 求平均再 clip,因为 clip 是逐 action 限制.Reference KL 可作为 token reward、loss penalty 或独立约束加入,不同实现的符号与估计器可能不同,比较超参数前要先对齐定义.

小规模单元测试可以直接构造两条回答.设 rewards 为 $[1,0]$,忽略 $\varepsilon$,组内均值为 $0.5$、标准差为 $0.5$,advantages 为 $[1,-1]$.当新旧策略完全相同,ratio 全为 1,未加 KL 的 surrogate 分别是 $1$ 与 $-1$;交换两条 reward 后,advantage 应精确变号.Padding 位置无论填入什么 log probability,mask 后 loss 都应保持不变.这三项能很快发现归一化轴、pair 对齐与 mask 错误.

还可以加入一次人工构造的 clipping 测试.设正 advantage 为 $1$、$\epsilon=0.2$,ratio 分别取 $0.8,1.0,1.5$,surrogate 应为 $0.8,1.0,1.2$;把 advantage 改成 $-1$ 后,低于 $0.8$ 的一侧才受到限制.这个例子能发现最常见的实现错误:对正负 advantage 使用同一侧 clip,或者在 `min` 之前错误地取绝对值.

## 训练系统该观察哪些量

平均 reward 只给出结果的一部分.每个 step 还应记录组内 reward 标准差、零方差 group 比例、每类 verifier 状态、completion 长度、KL、ratio 分位数、clip fraction、entropy 与有效 token 数.零方差比例持续升高,可能说明题目已经过易、全部过难或 verifier 坏了;clip fraction 很高,可能来自 learning rate 过大、样本过旧或一次复用 epoch 太多.

Rollout throughput 与 actor throughput 也要分开.增加 $G$ 能改善组内比较并提高发现正确答案的概率,同时线性增加生成 token;更长 reasoning 会扩大 $T$,使 KV cache、通信和验证等待成为瓶颈.动态 batching 可以提高利用率,却会引入更多重排.系统优化必须在 sample ID 和版本不变量保持正确以后进行,不能用吞吐提升交换训练语义.

数据复用存在明确边界.同一批 rollout 做多个 minibatch epoch 时,old log probability 固定,当前 policy 逐渐变化,ratio 和 clip fraction会增大.PPO 的裁剪缓和这种偏移,却没有把任意次数复用变成无偏 on-policy 更新.训练配置应报告每批 rollout 的更新轮数,并用 KL 与 ratio 分布决定何时重新生成,而不是只按固定 epoch 机械重复.

Checkpoint 需要同时保存 actor 权重、optimizer state、scheduler、已消费数据位置和当前 policy version.只恢复 actor 参数会让学习率与动量跳变;只恢复 trainer 而让 rollout worker 保留旧权重,又会制造版本不一致.故障恢复后的第一批样本应标明生成时间和权重版本,确认旧队列是否仍满足允许的 staleness,再决定消费或丢弃.

数值精度也会改变 ratio.若 rollout 引擎用量化权重生成并记录 log probability,trainer 却用 BF16 权重重算 old log probability,两边会出现系统偏差.更稳妥的做法是保存生成侧实际使用的 old log probability,并抽样比较两个引擎在同一 token 上的差值分布.差值持续偏大时,应先修正模型转换或精度设置,再解释 clip fraction.

梯度聚合口径也要检查.不同 worker 的有效 completion token 数不相等时,先在本地取 mean 再平均 worker,会让短 batch 与长 batch 权重相同.若目标定义为全局 token mean,应先 all-reduce loss sum 与有效 token count,再相除.这类差异不会触发 shape error,却会随着长度分布改变训练权重.

对应监控应同时记录全局有效 token 数.

第17讲结束时,一次 GRPO step 应当能够被逐项复算:哪一个 policy 生成了 token,哪个 verifier 给了 reward,组内统计沿哪一维计算,advantage 怎样广播,哪些 token 被 mask,ratio 的分子分母来自哪个版本,KL 又相对哪个 reference.公式、张量与分布式记录对上以后,训练曲线才有可解释的含义.

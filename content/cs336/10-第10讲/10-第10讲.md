# 第10讲:大模型推理

预训练把参数写进模型,推理系统则要在每一次请求里把这些参数变成用户愿意等待的 token.两边调用的是同一个 Transformer,性能问题却很不一样.训练可以提前组成规则的大批量,整段序列并行计算;在线生成会不断收到长度各异的请求,每个序列一次只向前长一个 token,还要保存此前所有 token 的 Key 和 Value.于是,一块训练时算力吃不满的 GPU,在推理时可能先被显存容量、显存带宽或调度碎片卡住.

要理解推理优化,先把一次请求分成 **prefill** 与 **decode**.Prefill 同时处理提示词中的许多 token,矩阵乘法规模大,通常更容易利用 GPU 算力.Decode 每步只为每个序列生成一个新 token,权重却仍要被读取一遍,还要访问不断增长的 KV Cache.长提示词和高并发会改变两阶段的比例,因此「每秒 token 数」必须说明测的是输入还是输出、单请求还是整机吞吐,以及并发和序列长度.

## 算术强度是第一张账单

算术强度定义为完成的浮点运算量与从慢速存储层搬运的字节数之比:

$$
I=\frac{\text{FLOPs}}{\text{bytes moved}}.
$$

硬件的峰值算力与显存带宽之比给出一条分界线.若 $I$ 低于这条线,增加计算单元也无济于事,内核主要在等数据;若 $I$ 足够高,性能才更可能由计算吞吐限制.以单 token、低 batch 的 decode 为例,模型权重每步都会参与计算,但复用次数很少,算术强度偏低.把多个请求组成 batch,可以让同一份权重服务更多 token,提高复用,不过 KV Cache 占用、排队时间和尾延迟也会随之上升.

这张账单能帮助判断优化究竟改了哪一项.量化把 FP16/BF16 权重压到 INT8、INT4 或更细的格式,主要减少权重字节数,有时还借助更快的低精度计算;剪枝减少需要读取和计算的参数,但稀疏模式只有得到硬件与内核支持才会兑现速度;GQA、MQA 与 MLA 压缩 KV 表示,直接缓解长上下文和高并发下的缓存压力;连续批处理与 PagedAttention 改善请求调度和显存分页,减少因为不同序列长度产生的空洞.它们都能写成「推理加速」,底层解决的却不是同一项瓶颈.

## 延迟、吞吐与质量不能只报一个数字

在线服务至少要同时看首 token 延迟(TTFT)、相邻输出 token 的时间(TPOT)、端到端延迟、每秒输出 token、并发容量与峰值显存.用户发送长提示词时,TTFT 更受 prefill 影响;流式对话是否顺滑,主要取决于 TPOT;离线批处理则常把总吞吐放在第一位.提高 batch 能改善吞吐,却可能让某个请求排队更久.于是调度器需要在到达率变化时动态组合请求,并决定 prefill 是否会阻塞正在 decode 的序列.

KV Cache 让自回归解码无需重新计算全部历史,但缓存大小随层数、序列长度、KV head 数和 head dimension 线性增长.前缀缓存可以让共享系统提示词或相同前缀复用已有 KV;分页管理允许非连续显存承载逻辑连续的序列;缓存量化进一步减少字节数.每一步优化都要检查精度、元数据开销和真实访问模式,不能只看理论压缩率.

## 投机采样为何能够「走捷径」

投机采样让一个便宜的草稿模型先提出若干 token,再由目标模型用一次并行前向批量验证.若草稿分布为 $q$、目标分布为 $p$,候选 token $x$ 以

$$
\min\!\left(1,\frac{p(x)}{q(x)}\right)
$$

的概率被接受;被拒绝时,从经过修正的剩余分布采样.这个接受—修正过程保证最终样本仍来自目标分布,所以它与直接用小模型替代大模型不同,理论上不改变输出分布.真正的加速取决于接受率、一次提出的长度、草稿成本以及目标模型并行验证的效率.草稿很差时,频繁拒绝会吞掉收益;草稿太大时,生成候选本身又过于昂贵.

替代架构也从另一个方向处理推理成本.状态空间模型让递归状态以近似固定大小传递,线性注意力尝试避免标准注意力的二次序列开销,跨层注意力复用部分 KV.它们改变了质量、训练并行性和硬件适配之间的平衡,不能只凭渐近复杂度判断线上速度.

## 先做一遍容量核算

推理部署可以从一个粗略的显存账本开始.若模型有 $P$ 个参数,权重采用每参数 $b_w$ 字节,权重占用约为 $Pb_w$;KV Cache 对每个 token 的占用与层数 $L$、KV head 数 $H_{kv}$、每个 head 的维度 $d_h$ 和缓存精度 $b_{kv}$ 相关,近似为

$$
M_{KV/token}=2LH_{kv}d_hb_{kv}.
$$

系数 2 对应 Key 与 Value.再乘以所有活跃序列的 token 总数,才得到动态缓存.比如 GQA 把 $H_{kv}$ 从注意力 head 数降到较小值,节省会随并发和上下文长度一起放大;低并发短文本时,权重仍可能是显存主体.

账本还要给 CUDA context、临时 activation、采样缓冲、通信 workspace 和内存碎片留余量.仅用「显存总量减权重」估算最大 batch,线上很容易在长请求到来时溢出.PagedAttention 让 KV 块按需分配,减少为了最大长度预留的浪费,但块大小过大会产生内部碎片,过小又会增加页表和调度开销.

在多 GPU 上,tensor parallel 会切分矩阵和权重,同时引入每层 collective 通信;pipeline parallel 降低单卡权重压力,却可能出现流水线气泡;expert parallel 只适用于 MoE,并让路由不均衡成为新瓶颈.拓扑因此必须写进性能报告.同样数量的 GPU,通过 NVLink、PCIe 或跨节点网络连接时,decode 延迟可能完全不同.

容量核算最终要落到服务级目标.给定到达率、输入输出长度分布和延迟 SLO,可以用压测逐渐提高并发,找到吞吐开始饱和、尾延迟快速上升的位置.平均请求不会暴露长尾风险,固定 batch 的离线 benchmark 也不会呈现真实排队.只有把模型内核、缓存容量与到达过程放在同一个实验里,才能判断优化是否真的减少了所需机器数.

能耗与成本也应按完成请求而不是单卡功率核算.更快的内核可能提高瞬时功耗,却因缩短执行时间而降低每百万 token 的能源;反过来,利用率很低的便宜 GPU 也可能带来更高的总服务成本.

读这一讲时,可以始终追问四个量:权重搬了多少,KV Cache 读写了多少,实际做了多少有效计算,请求为等待批处理付出了多少时间.然后再看优化是否改变模型输出分布、是否需要新的内核,以及收益出现在哪种 batch 和序列长度下.**推理系统没有脱离工作负载的「最快方案」;能被复现的性能结论,必须连同硬件、精度、并发和长度分布一起给出.**

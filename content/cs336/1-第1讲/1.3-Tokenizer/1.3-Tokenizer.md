# Tokenizer: 从字节到模型输入
语言模型接收离散的 token ID,不能直接把字符串送进嵌入层.**分词器 (Tokenizer)** 负责定义字符串与 token ID 序列之间的可逆编码,其词表和切分规则会改变序列长度、训练成本以及不同文本片段共享统计信息的方式.下面以**字节对编码 (Byte-Pair Encoding, BPE)** 为主线说明训练与编码过程.
**从字符串到数字序列**
Tokenizer 先按既定规则把字符串切成 token,再通过词表把每个 token 映射为整数 ID.模型处理的是这些 ID 对应的嵌入向量;字符串能否稳定还原,则由解码规则与基础符号集合保证.
> A tokenizer is something that converts between strings and sequences of integer.
分词器在字符串与整数序列之间转换.每一个 ID 对应词表(Vocabulary)中的一个 token.
这个过程可以分解为四步:
1. **输入 (Input):** 接收完整字符串.
2. **分词 (Tokenization):** Tokenizer 按训练得到的合并规则切分句子,得到长度不一的 token.例如,“tokenizer”可能保持完整,而“unbelievable”可能被切成“un”和“believable”.token 边界来自语料频率与算法规则,不保证对应语言学词素.
3. **ID映射 (ID Mapping):** 每个 token 对应一个整数 ID.例如,“tokenizer”可能对应 ID `99665`,“is”对应 ID `382`.
4. **向量化 (Vectorization):** 得到这些ID后, 模型会通过一个巨大的查询表 (即Embedding Matrix) , 将每个ID转换为一个高维向量 (Embedding). 这才是模型真正开始处理的输入.
**为何需要子词算法? BPE的崛起**
最简单的分词方法是按空格切分. 但这种方法有两个致命缺陷:
- **词汇表爆炸 (Vocabulary Explosion):** "run", "running", "ran" 会被视为三个独立的词, 极大地增加了词汇表的大小.
- **未登录词 (Out-of-Vocabulary, OOV) 问题:** 如果模型在训练时没见过 "de-tokenization" 这个词, 它就不知道如何处理.
为了解决这些问题, **子词 (Subword)** 算法应运而生, 而 **BPE (Byte-Pair Encoding)** 是其中最成功和最广泛使用的一种.
BPE 从基础符号开始,反复合并语料中频率最高的相邻符号对.高频片段因此获得独立 token,低频词仍可由较小单元组合出来.
**BPE工作原理: 两阶段过程**
BPE的实现分为两个阶段: **训练阶段** (学习合并规则) 和 **分词阶段** (应用规则).
**阶段一: 训练 - 学习如何“合并”**
这是BPE的“学习”过程, 其目标是建立一个包含高频子词的词汇表.
1. **准备语料库和初始词汇表:**
   - 首先, 我们需要一个庞大的文本语料库 (比如维基百科或Common Crawl的一部分).
   - BPE的初始词汇表非常简单: 它包含了所有可能出现的基础字符. 在现代LLM中, 为了处理所有Unicode字符而不错漏, 初始词汇表通常是256个**字节 (Bytes)** . 这也是它名字中“Byte-Pair”的由来.
2. **迭代合并:**
   - 算法会统计语料库中所有相邻字节对 (Byte Pair) 的出现频率.
   - 找到频率最高的那个字节对, 比如 `('t', 'h')`.
   - 将这个字节对合并成一个新的、更大的单元, 记为 `'th'`.
   - 将这个新的单元 `'th'` 添加到词汇表中.
   - 在整个语料库中, 用新的单元 `'th'` 替换掉所有的 `('t', 'h')`.
   - 重复这个过程 (寻找最高频的相邻对、合并、加入词汇表、替换), 直到词汇表达到预设的大小 (例如, GPT-3的词汇表大小约为5万).
**举个简单的例子:**
假设我们的语料库中有单词: `(low, 5)`, `(lower, 2)`, `(newest, 6)`, `(widest, 3)`. (括号内为词频)
- **初始:** 字符为 `l, o, w, e, r, n, s, t, i, d`.
- **第一次合并:** 假设 `(e, s)` 出现频率最高 (来自new**es**t和wid**es**t). 我们合并它们得到新单元 `'es'`, 并加入词汇表. 语料库变为 `(l o w, 5)`, `(l o w e r, 2)`, `(n ew es t, 6)`, `(w i d es t, 3)`.
- **第二次合并:** 假设 `(es, t)` 频率最高. 合并得到 `'est'`. 词汇表加入 `'est'`. 语料库变为 `(l o w, 5)`, `(l o w e r, 2)`, `(n ew est, 6)`, `(w i d est, 3)`.
- **继续合并...** 最终, 像 `'low'` 这样的高频词可能会被合并成一个完整的Token, 而像 `'lower'` 可能会被表示为 `'low'` 和 `'er'`.
通过这个过程, BPE自动地学习到了哪些是常见的单词 (如`the`, `is`), 哪些是常见的词根、前缀和后缀 (如`est`, `er`, `re-`, `-ing`).
**阶段二: 分词 - 应用已学规则**
当Tokenizer训练完成后, 它就拥有了一套固定的词汇表和一套按优先级排序的合并规则. 当它遇到一个新句子时:
1. 首先将句子拆分成基础字符/字节序列.
2. 然后, 严格按照训练时学到的合并规则的**优先级顺序** (从最高频的合并开始), 对序列进行迭代合并.
3. 当无法再进行任何合并时, 最终得到的序列就是分词结果.
这个过程巧妙地解决了OOV问题. 即使遇到一个从未见过的词, 如 "GPTtokenizer", BPE最差也能将其拆分为一系列已知的子词或单个字节, 例如 `['GPT', 'token', 'izer']`. **模型永远不会遇到完全未知的东西.**
**实例分析**
图片来源: [https://platform.openai.com/tokenizer](https://platform.openai.com/tokenizer)
> **句子:** "A tokenizer is something that converts between strings and sequences of integer"
> **对应的Token ID:** `[32, 99665, 382, 3543, 484, 64809, 2870, 18279, 326, 45665, 328, 16336, 198]`
我们可以对这个结果进行一些推断:
- **常见的词是单个Token:** 像 `is` (ID: 382), `that` (ID: 484), `and` (ID: 326), `of` (ID: 328) 这类极其常见的词, 几乎肯定在BPE的训练早期就被合并成了一个完整的Token.
- **专有名词/高频词也是单个Token:** `tokenizer` (ID: 99665), `sequences` (ID: 16336) 和 `integer` (ID: 198) 虽然更长, 但在NLP语料库中是高频词, 因此它们也被学习成了一个单独的Token.
- **空格的处理:** 第一个 ID `32` 对应空格. 很多现代 Tokenizer 会把前导空格并入后续 token; `is` (ID: 382)、`that` (ID: 484)等 token 可能已经包含前面的空格,从而区分单词出现在句首和句中的情况.
- **Token ID的任意性:** 这些ID `99665`, `382`, `3543` ... 本身没有数学意义. 它们只是词汇表这个大字典里的“门牌号”. 模型只关心用这个门牌号去Embedding矩阵里取出对应的向量.
**词表大小与序列长度的交换**
BPE 在固定词表规模下折中序列长度与覆盖范围.字节级基础符号可以避免未登录字符串,但切分长度仍受语言、字符集和训练语料影响;因此比较模型成本或 PPL 时必须同时说明 Tokenizer.
词表增大后,常见片段能用更少 token 表示,序列更短;代价是输入嵌入与输出分类器随词表 $V$ 增大.若 hidden size 为 $d$,不共享输入输出权重时两张矩阵合计约有 $2Vd$ 个参数.词表太小会让序列变长,Attention 与训练样本 packing 的成本上升;词表太大则让大量低频 token 训练不足,输出 softmax 也更贵.

压缩率必须按语种和领域分别测量.主要从英文语料训练的词表可能把常见英文词压成一个 token,却把中文、代码标识符或少数语言拆得更碎.同样的字符数会消耗更多上下文位置和推理费用.因此「支持某种语言」不能只看能否无损编码,还要看每字符 token 数、长尾字节比例和常见词是否被过度拆分.

## 字节、Unicode 与文本归一化

### 字节级基础词表为何不会 OOV

UTF-8 会把 Unicode 字符编码成一到四个字节.以 256 个字节值作为基础符号,任何有效字节串都能被表示,BPE 即使找不到合并规则也能退回单字节.这里的「不会 OOV」只表示编码器总能产出已有 ID,不代表模型见过该字符,也不代表一个可见字符只占一个 token.一个汉字的三个 UTF-8 字节可能被训练成单个 token,也可能保留成多个 token.

解码时把 token 对应的字节串拼接,再按 UTF-8 解释.单个 token 可能只含某个多字节字符的一部分,所以逐 token 流式显示时不能假定每步都得到合法 Unicode.服务端应维护字节缓冲,等形成完整字符后再输出,否则会出现替换字符或乱码.

**归一化会不会破坏可逆性**

Unicode 中看起来相同的文本可能有不同码点序列,例如预组合字符与「基础字符+组合附加符」.NFC、NFKC 等归一化能减少表面变体,但兼容归一化也可能合并具有不同语义或格式的字符.大小写折叠、空白压缩和控制字符删除同样会改变原字符串.

Tokenizer 是否要求 `decode(encode(x)) == x`,取决于预处理是否有损.代码、数学、表格和安全任务通常需要保留精确字符;搜索或分类任务可能接受归一化.训练与推理必须使用同一套规范,否则模型看到的 token 分布会漂移.配置中应把 normalizer、pre-tokenizer、合并表、词表与特殊 token 一同版本化.

### 预分词、空格与特殊 token

**空格为什么经常并入后词**

许多实现先用预分词器划出候选边界,再在边界内部应用 BPE.GPT 系列常把空格转换成可见占位符或与后续词共同编码,于是句首的 `hello` 与句中的 ` hello` 可以是不同 token.这不是 BPE 必然推导出的规则,而是预分词与字节映射共同决定的协议.

空格进入 token 后,嵌入当然不同:`hello` 与 ` hello` 对应不同 ID,会查询嵌入矩阵的不同行.这种设计让词边界信息直接进入 token,但也带来边界案例:多个空格、换行、制表符和行首缩进可能形成不同切分.代码模型尤其需要保留缩进与换行,不能沿用会压缩空白的文本预处理.

### 特殊 token 不能当普通文本

BOS、EOS、PAD、UNK 以及聊天模板中的 role token 由模型协议定义.特殊 token 通常直接匹配为一个 ID,不经过普通 BPE 合并;是否允许用户文本触发它们必须显式控制.若任意字符串都能注入 role token,聊天边界可能被伪造.编码 API 因此常区分 `allowed_special` 与 `disallowed_special`.

PAD 用于批处理对齐,应在 loss 和 Attention 中被相应 mask;EOS 是模型需要学习预测的真实终止目标.两者即使共享 ID,训练代码仍需依靠长度或 mask 区分有效位置.添加新特殊 token 会扩大词表,新嵌入行没有预训练信息,需要初始化并继续训练;只改 tokenizer 文件而不 resize 模型矩阵会导致越界.

## BPE 训练的可复算实现

### 频数、并列与合并顺序

训练语料先被表示为基础符号序列,每轮统计所有相邻 pair 的加权频数.某个词出现 $c$ 次,其中的 pair 便贡献 $c$ 次.选择最高频 pair 合并后,必须重新统计受影响邻域.若多个 pair 同频,实现需规定稳定的 tie-break,否则同一语料和词表大小可能产生不同 merge 表.

合并存在重叠时也要规定扫描方式.序列 `a a a` 中 pair `(a,a)` 出现两个重叠位置,一次替换不能同时使用中间的 `a`.常见实现按从左到右的非重叠匹配得到 `aa a`.训练与编码若采用不同规则,词表中虽然存在 `aa`,实际切分却可能不一致.

merge rank 比「当前字符串里哪个 pair 频率高」更重要.推理阶段不再统计输入句子的频率,而是按训练所得规则优先级合并.因此两份含相同 token 集合、但 merge 顺序不同的 tokenizer 仍可能给同一字符串不同切分.

### 训练前先决定数据口径

Tokenizer 语料不必等同于全部预训练数据,但分布应覆盖目标语言、代码、数学与格式.网页模板或重复文本占比过高会浪费词表槽位,让站点固定片段成为 token.采样时可按语言和领域设权重,随后用独立验证集测压缩率,避免只在训练样本上看平均值.

词表训练还要防止隐私片段和高频随机标识符进入完整 token.电话号码、邮箱、密钥样式与 UUID 即使频繁,也未必值得合并.过滤这些模式既减少记忆风险,也把容量留给可复用片段.是否允许跨空格、跨换行合并同样属于协议选择,会影响生成时的局部可控性.

## Tokenizer 怎样改变训练与评测

### 固定 token 预算不等于固定文本量

训练规模常以 token 数报告,但 token 是 tokenizer 定义的单位.两个模型都训练一万亿 token,若平均每 token 覆盖的字节数不同,实际读过的文本量并不相同.比较数据规模时应同时给 tokenizer、去重后字节数或字符数以及各语种压缩率.

上下文窗口也采用 token 计数.标称 32K 上下文对英文、中文和代码能容纳的可见内容不同.更换 tokenizer 还会改变位置分布、packing 效率和每样本 loss 项数,不能在不重新训练的情况下把旧模型直接换到新切分协议.

**PPL 为什么依赖 Tokenizer**

token-level NLL 对每个 token 平均.同一字符串若被切成更多 token,概率乘积的项数和平均分母都会变化,因此不同 tokenizer 的 PPL 不能直接横比.可比较的口径包括在相同 tokenizer 下评估,或把总负对数似然换算成每字节/每字符 bits.后一种口径仍要统一 Unicode 与空白处理.

Tokenizer 还影响生成停止条件.停止字符串可能跨越多个 token,也可能出现在单个 token 内部;推理服务不能只把每个 stop string 当作一个 ID.流式解码需要在字节或字符串缓冲上匹配,并处理特殊 token 是否向用户显示.

### 工程验收与 tokenizer-free 路线

**上线前应测什么**

第一项是往返测试:覆盖多语言、emoji、组合字符、NUL、换行、代码缩进和非法字节处理,确认可逆范围符合设计.第二项是确定性:同一版本在不同线程和平台得到相同 ID.第三项是特殊 token 安全:普通文本不会意外获得控制 token 权限.第四项是分布统计:记录序列长度分位数、每字符 token 数、单字节回退率和词表使用频率.

训练侧还要确认 embedding 行数等于 tokenizer 词表大小,模型配置中的 BOS/EOS/PAD ID 与 tokenizer 一致,数据缓存包含 tokenizer 版本指纹.更换 merge 表后必须使旧 token 缓存失效.只比较文件名或词表大小不够,完整配置可用内容哈希标识.

### 直接处理字节是否能省掉 Tokenizer

Tokenizer-free 模型直接接收字节或字符,消除了固定子词词表与切分偏差,也天然覆盖任意字符串.代价是序列显著变长,标准 Attention 的计算随长度平方增长.这类架构通常需要局部编码、下采样或动态 patch,把多个字节聚合成较短的潜在序列;切分没有消失,而是从离线规则变成模型内部学习的压缩过程.

两条路线的比较应固定原始字节量、参数量与计算预算.子词模型把一部分压缩工作放在训练前,字节模型把它交给网络;谁更合适取决于语言覆盖、噪声鲁棒性、硬件效率和模型规模.无论采用哪条路线,都要回答同一个问题:原始字符串怎样变成有限长度的计算单元,又怎样无歧义地还原.

## BPE、WordPiece 与 Unigram 的区别

### 三种算法怎样选择切分

BPE 学的是有序合并操作:从基础符号出发,按 merge rank 把相邻片段组合起来.WordPiece 常用似然改善或近似评分挑选要加入词表的片段,编码时通常采用最长匹配;具体目标随实现而异,不能把所有 WordPiece 都描述成同一条 BPE 频数公式.Unigram Language Model 则先准备较大的候选词表,为 token 赋概率,再逐步删除对语料似然影响较小的项.

Unigram 编码可以用动态规划寻找整句概率最高的切分.设字符串位置为 $0,\ldots,n$,若词表 token $u$ 覆盖区间 $i:j$,其代价为 $-\log p(u)$,则

$$
D[j]=\min_{u=x_{i:j}}\{D[i]-\log p(u)\}.
$$

$D[n]$ 对应最小代价路径.保留多条路径还能在训练时做 subword regularization,随机采样不同合法切分,降低模型对单一边界的依赖.BPE 也有 dropout 变体,但标准确定性编码只执行固定 merge 顺序.

算法名称本身不足以复现 tokenizer.还需要 normalizer、pre-tokenizer、基础字母表、词表、合并表或 token 概率、byte fallback、特殊 token 及其 ID.两个都标作「BPE」的模型可能因这些配置不同而给出完全不同的序列.

### 为什么不能用语言学直觉判断 token

数据驱动的子词目标优先优化频率或似然,并不承诺 token 对应词根、词缀或汉语词语.高频乱码、HTML 片段和带空格的短语都可能进入词表;语义完整的低频词仍会被拆开.分析模型行为时可以观察 token 边界,但不能把某个 token 自动解释为模型内部的语义单位.

同一个可见字符串还可能有多种 token 序列.普通编码器会按规则返回规范切分,生成模型却可能通过别的 token 组合解码出相同字节串.若输出约束、敏感词过滤或计费逻辑只匹配一种 ID 序列,便可能漏掉等价编码.稳妥做法是在解码后的字节或规范化字符串上再次验证.

## 一个小型 BPE 训练走查

### 手工统计第一轮

设语料只有 `低低` 出现 3 次、`低温` 出现 2 次,UTF-8 字节细节暂时省略,把每个汉字视为基础符号.相邻 pair `(低,低)` 的加权频数是 3,`(低,温)` 是 2,第一轮合并得到 token `低低`.更新后的语料表示为 `[低低]×3` 与 `[低,温]×2`;第二轮只剩 `(低,温)` 可合并.

若再加入 `温低` 2 次,第二轮 `(低,温)` 与 `(温,低)` 同频.tie-break 决定哪个 token 先进入词表,继而可能改变后续可见 pair.这说明确定性训练必须固定语料遍历顺序和并列规则.大规模实现虽然用堆、增量计数和倒排位置减少重复扫描,输出仍应等价于明确定义的串行算法.

### 编码阶段逐轮应用

假设 merge 表依次为 `(低,温)→低温`、`(高,温)→高温`、`(低温,高温)→低温高温`.编码字符串 `低温高温` 时,基础序列先变成 `[低,温,高,温]`,应用前两条规则得到 `[低温,高温]`,再由第三条得到单个 token.若第三条 rank 排在构造 `高温` 之前,它当时无法匹配,仍要等组成部分可用后再考虑;高效实现通常用优先队列选择当前可用且 rank 最小的 pair.

解码只需查表并拼接字节,不需要倒放 merge 历史.正因如此,训练后删除一个看似没用的 token 或重排 ID 都会改变模型接口:模型参数的第 $j$ 行已经绑定旧词表的第 $j$ 个 token.词表优化必须发生在预训练前,或伴随明确的嵌入迁移和继续训练.

训练器还应在小语料上保留黄金测试.测试文件写明每轮最高频 pair、合并后的序列、最终词表和若干字符串的期望 ID;这样能发现并列规则、重叠替换或预分词改动造成的漂移.在真实语料上则记录词表覆盖分布:从未使用的 token、只出现一次的 token 和占据大量流量的头部 token.大量闲置项说明词表预算没有转化为压缩收益,少数 token 过度集中则需要检查网页模板与重复数据.

模型上线后也要监控输入 token 长度相对字符长度的漂移.新领域、混淆字符或异常编码会让 byte fallback 比例突然升高,同一请求的上下文成本随之增加.这类变化首先是数据分布问题,不能只靠扩大上下文窗口掩盖.

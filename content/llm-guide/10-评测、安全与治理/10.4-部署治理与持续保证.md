# 部署治理与持续保证

治理不是审批文件的数量，而是组织能否持续回答：这个系统用于什么、影响谁、谁能改变它、证据支持哪些声明、剩余风险由谁接受、发生事故如何停止和恢复。

## 从用途和影响开始

### 系统用途声明

- 目标用户、受影响群体和业务流程；
- 允许与禁止的任务、数据、地区和决策；
- 模型是否建议、辅助、排序、生成，还是直接执行动作；
- 人工角色、申诉、纠正和最终责任；
- 质量、延迟、成本、安全与公平目标；
- 失败可能影响的权利、健康、财产、机会、信息与基础设施；
- 系统边界、外部依赖和结论有效日期。

用途改变会改变风险。把低风险摘要系统接入邮件发送、支付或生产运维，不是“增加一个工具”，而是新的高影响部署，需要重新建模和验收。

### 受影响者

除了直接用户，还要考虑：输出中被描述的人、被排序/筛选的人、数据主体、标注与审核人员、外部内容创作者、下游执行人员和无法使用系统的人。只有用户满意度无法代表这些群体的损失。

## 治理框架如何使用

NIST AI RMF 用 Govern、Map、Measure、Manage 组织自愿风险管理；其 Generative AI Profile 针对生成式 AI 补充风险与建议行动。它们是方法框架，不是认证，也不自动满足任何法域或行业义务。截至 2026-09-01，NIST 已说明 AI RMF 1.0 正在修订，因此采用时应记录版本。[NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework)

可将四类功能落成：

| 功能 | 组织问题 | 可审查产物 |
|---|---|---|
| Govern | 谁负责、风险容忍是什么、如何监督？ | 政策、角色、例外、培训、独立复核 |
| Map | 用途、群体、数据、依赖和影响是什么？ | 系统卡、数据流、影响与威胁模型 |
| Measure | 用什么证据估计质量、风险和不确定性？ | 评测协议、红队、审计、监控基线 |
| Manage | 如何选择控制、接受剩余风险并恢复？ | 风险登记、门禁、整改、回滚、事件流程 |

不要为了“对齐框架”重复抄同一控制。每项控制只保留一个负责人、实施位置、验证证据和关联风险，再映射到多个框架。

## 角色与分权

### 最低角色

| 角色 | 核心责任 |
|---|---|
| 业务/用途负责人 | 定义用途、收益、失败损失和是否继续部署 |
| 模型/应用工程 | 实现、版本、测试、控制和技术文档 |
| 数据负责人 | 来源、质量、权利、访问、保留和删除 |
| 安全与隐私 | 威胁模型、红队、访问控制、隐私和事件 |
| 评测负责人 | 独立协议、数据、评分、不确定性和结果卡 |
| SRE/平台 | 容量、监控、发布、降级、回滚和供应链 |
| 法务/合规 | 识别适用义务、合同、披露和记录要求 |
| 独立审批者 | 对高风险上线、例外和剩余风险作出授权决定 |

小团队可以一人兼任多个角色，但高影响决策不应由同一人同时开发、评分并批准。冲突无法避免时，记录并增加外部或交叉复核。

### 决策权

明确谁能：创建/修改数据集、选择模型、改系统提示、增加工具、扩大权限、调整阈值、批准例外、放量、暂停、回滚和对外披露。治理的关键是把高影响变化纳入变更控制，而不是只限制代码仓库。

## 风险登记

每项风险至少包含：

- 稳定 ID、日期、负责人和状态；
- 用途、资产、受影响群体和场景；
- 原因、触发、攻击者/故障条件和后果；
- 已有证据、频率/可能性、严重度与不确定性；
- 预防、检测、响应与恢复控制；
- 控制验证、剩余风险、接受人和到期日；
- 监控指标、复审触发器和关联事件。

“概率 × 影响”的单一数字可用于排序讨论，却不应掩盖不可逆损失、权利影响、未知概率和级联风险。高严重度低频事件可直接设置硬门槛。

## 保证案例

保证案例把“我们认为可上线”拆成声明、论证和证据：

1. **顶层声明**：系统在限定用途、版本和环境下满足哪些可接受条件。
2. **子声明**：质量、可靠性、安全、隐私、公平、性能与恢复分别满足什么。
3. **论证**：为何这些测试、控制和流程足以支持子声明。
4. **证据**：数据版本、原始结果、红队轨迹、代码/配置、审计和演练。
5. **假设与反驳**：哪些环境条件必须成立，哪些已知反例会推翻结论。
6. **有效期**：哪些变更或事件触发重新评估。

保证案例不是用文档消除风险，而是暴露证据缺口和推理跳跃。模型卡、系统卡、数据卡、部署卡和风险登记应作为证据来源，不互相复制全文。

## 上线阶段与闸门

### 阶段

1. **沙箱**：合成/脱敏数据、无外部副作用、最小网络。
2. **内部试用**：限定人员和任务，人工复核全部高影响输出。
3. **影子流量**：优先使用合成或脱敏输入；镜像真实输入前，先批准用途、处理依据、供应商/子处理方、地域、保留与访问。候选系统使用隔离身份、禁止外部副作用、最小化日志，并验证到期删除。
4. **受控试点**：少量用户/地区/任务，强确认和停止条件。
5. **有限生产**：用途与权限仍受限，持续对照基线。
6. **扩展或维持**：只有证据支持时扩大；否则降级、暂停或退出。

### 八类闸门

| 闸门 | 最低问题 | 证据 |
|---|---|---|
| 质量 | 代表、困难、时效和真实试点是否达标？ | 冻结评测与失败切片 |
| 安全 | 注入、越权、投毒、滥用和输出处理能否控制？ | 威胁模型、红队、确定性控制测试 |
| 隐私与数据 | 来源、用途、区域、保留、删除和外部处理是否批准？ | 数据台账、DPIA/内部评估、删除演练 |
| 可靠性 | 峰值、依赖失败、超时、重试和降级是否验证？ | 负载、故障注入、SLO 与演练 |
| 公平与影响 | 关键群体、可访问性、申诉和不可接受损失是否处理？ | 分层评测、影响评估和人评 |
| 成本与资源 | 峰值账单、循环、配额和容量是否受控？ | 压测、预算门、熔断 |
| 可观测性 | 能否识别版本、输入分布、工具轨迹和高风险事件？ | 日志 schema、仪表、告警与值班 |
| 回滚与供应链 | 能否恢复已验证组合，依赖变化是否可见？ | 版本清单、签名/hash、回滚与替代演练 |

每个闸门需要阈值、负责人、证据链接、状态和例外期限。“已评审”“有监控”不是通过条件。

公平与影响不能压成一个总分。对会改变机会、服务或资源的用途，应按有业务意义的群体和交叉群体报告样本量、错误率、区间与错误代价，说明小样本和缺失标签；同时测试键盘/屏幕阅读器等相关可访问性路径、人工替代、申诉与纠正。群体差异只是调查入口，接受标准仍要结合任务、权利和受影响者验证。

## 变更管理

### 需要纳管的变化

- 模型、checkpoint、API snapshot、路由或推理预算；
- tokenizer、量化、推理框架、硬件和批处理；
- 系统提示、对话模板、guardrail、分类器和后处理；
- RAG 语料、embedding、chunk、检索、重排和 ACL；
- 工具、schema、权限、凭据、网络、MCP/连接器和外部 API；
- 数据用途、地区、保留、日志和供应商条款；
- 用户、任务、流量、语言、模态和风险等级。

### 影响驱动复测

不要每次盲目全量重跑，也不要只做冒烟测试。维护“组件 → 声明 → 测试”映射：变化影响哪些声明，就重跑对应代表集、回归集、风险集、压力测试和人工复核。跨越权限、数据或高影响用途边界时，重新做完整审批。

### 配置与证据版本

一次发布应绑定：模型身份、代码、prompt、索引、工具、权限、策略、评测结果和批准记录。不能只给代码打 tag，却让云端模型别名、检索库和工具权限漂移。

## 运行监控

### 指标层

| 层 | 示例 |
|---|---|
| 输入与分布 | 任务、语言、长度、模态、敏感等级、注入信号 |
| 质量与影响 | 成功、严重错误、拒答、申诉、人工改写、群体切片 |
| Agent/工具 | 调用、权限拒绝、确认、循环、重复副作用、失败恢复 |
| 安全与隐私 | 越权、PII/秘密、异常导出、跨租户、投毒与攻击告警 |
| 性能与成本 | TTFT、TPOT、队列、超时、token、工具费用、预算尾部 |
| 版本与供应链 | model ID、hash、依赖、配置、条款与未知漂移 |

### 监控边界

线上标签往往延迟、稀疏或偏向主动反馈用户。代理指标可能被优化而偏离真实目标；用户投诉下降也可能是放弃使用。监控方案要记录数据缺口、延迟和调查流程，并定期抽样人工复核。

### 隐私与日志

可观测性不意味着记录一切。按目的选择字段，敏感内容默认最小化/脱敏，分离安全审计与产品分析，限制访问和保留。高风险事件需要足够取证信息，但也要防止日志成为新的数据泄漏面。

## 事件响应

### 触发

- 敏感/跨租户泄漏、未授权动作、危险输出造成现实影响；
- 投毒、供应链妥协、凭据泄漏或模型/路由未知变化；
- 大规模质量回退、错误拒答、偏差、成本或容量异常；
- 删除/撤回失败、数据用途违规或外部义务触发；
- 研究者、用户、供应商或监管方报告。

### 流程

1. **检测与分级**：按影响与暴露面，而非舆情热度。
2. **控制**：停用工具、降权、隔离数据、撤销凭据、限流或暂停系统。
3. **保全证据**：固定模型/配置、日志、输入、上下文、工具、授权与副作用。
4. **恢复**：回滚到已验证组合，验证数据与外部状态一致性。
5. **通知与协调**：按合同、政策和适用义务通知受影响方及负责人。
6. **根因与复盘**：区分模型、数据、权限、流程、监控和人员因素。
7. **闭环**：补测试、控制、文档、培训和跨系统检查，跟踪到验证完成。

对外部研究者提供清晰的安全报告渠道、范围和安全港政策，可以提高发现质量；不要迫使敏感漏洞走普通客服或公开工单。

## 透明度与文档分工

| 文档 | 主要对象 | 不应冒充 |
|---|---|---|
| 模型卡 | 模型身份、用途、评测与限制 | 完整部署保证 |
| 系统卡 | 产品/系统组件、安全评测和缓解 | 所有客户配置都相同 |
| 数据卡/数据表 | 数据来源、处理、组成与限制 | 数据权利已自动解决 |
| 部署卡 | 当前用途、用户、区域、版本、SLO 与控制 | 永久有效证书 |
| 风险登记 | 风险、控制、剩余风险和责任 | 公开透明报告的替代物 |
| 事件报告 | 时间线、影响、控制、根因和纠正 | 只归咎单次模型输出 |

外部透明度应保护用户隐私、安全细节和商业秘密，但“保密”不能成为不记录证据或不告知受影响方的理由。

## 标准与法规清单

全球义务持续变化，应建立“法域/行业—角色—用途—版本—生效日期—证据”台账，由专业人员核验。以下只能作为入口：

- [EU AI Act 官方政策入口](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai)：截至 2026-09-01，法规于 2024-08-01 生效；禁止性实践与 AI literacy 自 2025-02-02 适用，治理规则和 GPAI 义务自 2025-08-02 适用，大部分条款及 Article 50 自 2026-08-02 适用。官方时间线还列出部分 Annex III 高风险义务至 2027-12-02、Annex I 产品内嵌系统至 2028-08-02；实际义务须按 provider、deployer、importer 等角色及后续实施文件核验。
- [ISO/IEC 42001](https://www.iso.org/standard/42001)：AI 管理体系标准；认证范围不等于某个模型或用途绝对安全。
- [OECD AI Principles](https://oecd.ai/en/ai-principles)：非约束性的 Recommendation/Principles，不是直接可执行的测试规范。
- [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework)：自愿风险管理框架，不是法律合规判定。

不要把框架映射当成控制已经实施。每个映射都应链接到真实负责人、配置、测试、运行记录和缺口。

## 采购与退出

### 采购

供应商评估至少覆盖：精确服务身份、版本/下线政策、数据使用和保留、区域与子处理方、安全开发与事件通知、评测证据、日志与审计能力、知识产权/许可、容量和退出支持。营销用“企业级”“不训练”必须落到适用产品、账户、地区、合同和配置。

### 退出

在上线前设计：数据与日志导出、删除证明、替代模型、格式兼容、索引重建、凭据撤销、用户通知、历史审计保留和供应商中断。没有退出路径，风险接受就包含未量化的锁定和恢复成本。

## 持续保证检查单

- [ ] 用途、禁用场景、受影响者、系统边界和有效日期明确。
- [ ] 责任、审批、独立复核和利益冲突已记录。
- [ ] 风险登记包含证据、不确定性、控制、剩余风险和到期日。
- [ ] 保证案例把顶层声明连接到测试、配置、监控和反例。
- [ ] 八类上线闸门均有阈值、负责人、证据和例外期限。
- [ ] 模型、数据、prompt、RAG、工具、权限和供应链变化均受控。
- [ ] 线上监控覆盖质量、安全、隐私、工具、性能、成本和漂移。
- [ ] 日志足以调查事件，同时遵守最小化、访问和保留要求。
- [ ] 紧急停止、降级、回滚、替代和退出已演练。
- [ ] 适用标准、法规和合同按法域、角色、版本和日期核验。
- [ ] 事件、申诉、外部报告和纠正措施能进入下一轮评测与治理。

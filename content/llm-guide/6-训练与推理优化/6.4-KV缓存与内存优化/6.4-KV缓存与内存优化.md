# KV 缓存：容量计算、调度与压缩边界

自回归解码时，模型会反复读取历史 token 在每层产生的 Key 和 Value。KV cache 保存这些张量，避免每生成一个新 token 都重新计算全部历史 token 的 K/V 投影。它用显存换计算，但不会消除新 query 与历史 K/V 的注意力计算，也不会改变模型权重的大小。

下文的容量公式默认 decoder-only、全注意力、无前缀共享、无块尾浪费，并只计算 K/V 数值载荷。真实引擎还可能包含块对齐、scale、元数据、临时工作区、张量并行复制或分片；复算容量时需要同时给出模型版本、注意力类型、序列长度、并发序列数、cache dtype 和服务引擎版本。

## 1. Prefill 与 decode 是两种不同负载

**Prefill。** 一次处理输入 prompt，为每层生成整段 K/V，并计算首个输出 token。prompt token 可以并行处理；长 prompt 的注意力计算和中间激活通常显著，服务指标主要关注首 token 延迟（TTFT）、prefill tokens/s 和峰值工作区。

**Decode。** 每步通常为每条活动序列生成一个 token。新 token 只需计算一次 K/V，但 query 要读取历史缓存。序列越长，每步读取的历史 K/V 越多，因此 decode 往往更受显存带宽、cache 布局、并发调度和小算子效率影响。

KV cache 把“每步重算历史 K/V”改成“每步读取历史 K/V”。所以不能笼统地说它把整个生成复杂度从 $O(L^2)$ 变成 $O(L)$：单个 decode 步的历史注意力长度仍随 $L$ 线性增长，而生成 $L$ 个 token 的累计注意力工作仍可呈二次增长。

## 2. 标准 MHA/GQA/MQA 的容量公式

对常规 K/V 头表示，若每条序列缓存长度均为 $L$，则纯 K/V 数值载荷为：

$$
M_{\text{KV}}
= B \times L \times N_{\text{layers}} \times 2
\times N_{\text{kv-heads}} \times d_{\text{head}} \times s_{\text{bytes}}.
$$

其中：

- $B$：同时保留 cache 的序列数，不一定等于某次 kernel 的微批大小；
- $L$：每条序列已经缓存的 token 数，包含 prompt 与已生成 token；
- $N_{\text{layers}}$：带自注意力 cache 的层数；
- 系数 $2$：分别存 Key 和 Value；
- $N_{\text{kv-heads}}$：K/V 头数，不应误用 query 头数；
- $d_{\text{head}}$：每个 K/V 头的维度；
- $s_{\text{bytes}}$：每个 cache 元素的存储字节数，例如 BF16/FP16 通常为 2。

活动序列长度不同时，更准确的载荷公式是：

$$
M_{\text{KV}}
= \left(\sum_{i=1}^{B} L_i\right)
\times N_{\text{layers}} \times 2
\times N_{\text{kv-heads}} \times d_{\text{head}} \times s_{\text{bytes}}.
$$

这仍不含分页块最后一块的空位、量化 scale、allocator 与运行时工作区。容量规划应以引擎实测分配量校验理论载荷。

## 3. Llama 3.1 70B：逐项复算

Meta 官方 llama-models SKU 定义给出 Llama 3.1 70B 的 dim=8192、80 层、64 个 query heads 和 8 个 KV heads，因此：

$$
d_{\text{head}} = 8192 / 64 = 128.
$$

这些字段来自 [Meta sku_list.py](https://github.com/meta-llama/llama-models/blob/main/models/sku_list.py)；Llama 3.1 模型卡同时标明该家族使用 GQA、公开上下文长度为 128K。[Llama 3.1 官方模型卡](https://github.com/meta-llama/llama-models/blob/main/models/llama3_1/MODEL_CARD.md)

采用 BF16 cache，即每元素 2 bytes：

$$
\begin{aligned}
\text{每层每 token}
&= 2 \times 8 \times 128 \times 2\\
&= 4096\ \text{bytes}=4\ \text{KiB},\\
\text{全层每 token}
&= 80 \times 4096\\
&=327{,}680\ \text{bytes}=320\ \text{KiB}.
\end{aligned}
$$

因此单请求 8192 token 的纯 K/V 载荷为：

$$
327{,}680 \times 8192
=2{,}684{,}354{,}560\ \text{bytes}
=2.5\ \text{GiB}.
$$

16 条同为 8192 token、互不共享前缀的活动序列则为：

$$
16 \times 2.5\ \text{GiB}=40\ \text{GiB}.
$$

这里使用二进制单位 $1\ \text{GiB}=2^{30}$ bytes。若写成十进制 GB，数值不同；若把 64 个 query heads 误当成 64 个 KV heads，会把 GQA cache 高估 8 倍。上述 2.5 GiB/40 GiB 只是 K/V 数值载荷，不代表整机显存需求。

## 4. MHA、GQA、MQA 与 MLA

| 结构 | K/V 表示 | 标准公式中的 $N_{\text{kv-heads}}$ | 主要边界 |
|---|---|---:|---|
| MHA | 每个 query head 有独立 K/V | $N_{\text{q-heads}}$ | 表达最直接，cache 最大 |
| GQA | 一组 query heads 共享一组 K/V | $1<N_{\text{kv-heads}}<N_{\text{q-heads}}$ | 容量按 KV heads 算，不按分组数猜 |
| MQA | 所有 query heads 共享一组 K/V | $1$ | cache 最小，但质量和迁移效果依模型训练而定 |
| MLA | 缓存联合低秩 latent 与位置相关分量 | 不适用标准 K+V 头公式 | 必须按该模型公开的 latent 布局与推理 kernel 计算 |

MQA 原论文把 K/V 共享到单个 write head，以降低增量解码时的缓存与内存带宽。[Fast Transformer Decoding](https://arxiv.org/abs/1911.02150) GQA 则把 KV heads 取在 1 与 query heads 之间；其论文研究了从 MHA checkpoint uptrain 的具体方案，但论文结果不能替代目标模型的质量回归。[GQA 原论文](https://arxiv.org/abs/2305.13245)

MLA 不是“把 n_kv_heads 设得更小”。以 DeepSeek-V2 报告公开的推理表示为例，每层每 token 缓存联合 K/V latent $c_t^{KV}$ 和 decoupled RoPE key $k_t^R$，元素数按 $d_c+d_h^R$ 计算，而不是 $2N_{\text{kv-heads}}d_{\text{head}}$。[DeepSeek-V2 技术报告](https://arxiv.org/abs/2405.04434) DeepSeek-V3 报告明确继续采用 MLA；部署容量仍应依据所用 checkpoint、精度和 kernel 的实际布局，而不能把 V2 相对其特定基线的百分比当成通用压缩率。[DeepSeek-V3 技术报告](https://arxiv.org/abs/2412.19437)

## 5. PagedAttention 管的是分配，不是模型信息量

连续数组若按最大可能长度预留，会产生内部浪费；请求长度变化和释放顺序还会产生外部碎片。PagedAttention 把每条逻辑序列映射到非连续物理块，通过 block table、引用计数和 copy-on-write 管理 K/V。原论文中的 vLLM 还利用块共享支持并行采样等场景。[PagedAttention 原论文](https://arxiv.org/abs/2309.06180)

分页带来的主要变化是：

- 只随 token 增长按块分配，而不是为最大长度整段预留；
- 物理块无需连续，减轻外部碎片；
- 共享前缀可以引用相同物理块；
- 请求结束后块可迅速回收到池中。

它不改变单个 token 的 K/V 维度，也不保证吞吐固定提升。块大小、kernel、序列长度分布、调度策略和硬件都会影响收益。论文中的吞吐数字只属于论文对照环境，不应直接改写为生产 SLA。

详见 [PagedAttention 原理](./6.4.1-PagedAttention原理/6.4.1-PagedAttention原理.md)。

## 6. Continuous batching 管的是调度

静态 batching 要等同批请求一起结束，短请求完成后仍可能留下空槽。Continuous batching 在 token/迭代边界接纳新请求并移出已完成请求，使活动批次随服务队列变化。

它与 PagedAttention 经常一起出现，但两者解决不同问题：

- PagedAttention：K/V 块如何分配、寻址和共享；
- continuous batching：本轮让哪些请求执行多少 token；
- chunked prefill：把长 prefill 切块，以控制一次调度的 token 预算；
- admission control：在内存和延迟目标下决定是否接纳/排队请求。

调度器应分别观测 prefill 与 decode 队列、TTFT、inter-token latency、完成延迟、抢占/重算次数和 cache 使用率。只报告平均吞吐会掩盖长 prompt 对短请求的阻塞。

## 7. Prefix cache：复用相同前缀的计算

Prefix cache 保存已计算前缀对应的 K/V 块。新请求只有在模型、tokenizer、adapter、位置处理和 token 前缀满足引擎的匹配条件时才能复用；它不是“语义相似缓存”。vLLM 的自动前缀缓存采用基于 token 块及其父前缀的哈希，并只缓存完整块。[vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/latest/design/prefix_caching/)

适合的场景包括固定系统提示、共享长文档、多轮会话前缀和同一前缀的并行采样。边界包括：

- 命中主要减少重复 prefill，不能跳过新 token 的 decode；
- prompt 中动态时间戳、随机 ID 或工具列表顺序变化都会破坏前缀一致性；
- adapter、模型版本、RoPE/位置设置不同不能混用；
- 多租户共享可能产生隐私和时序侧信道，需隔离命名空间或使用受支持的 cache salt；
- 淘汰策略决定命中率，命中率又受前缀长度分布影响。

应用层“答案缓存”存的是输出，语义缓存可能按相似 query 复用答案；它们都不同于 KV prefix cache，正确性和失效策略也不同。

## 8. 量化：先算理论载荷，再测误差

若从 BF16/FP16 的 2 bytes 降为 1-byte cache dtype，纯 K/V 数值载荷的理论上限约减半，但真实分配还包含 scale、对齐、块尾和元数据。vLLM 当前配置公开支持多种 KV cache dtype，具体可用性依赖硬件、模型与 attention backend。[vLLM cache 配置](https://docs.vllm.ai/en/latest/api/vllm/config/cache/)

量化需要明确：

- K 与 V 是否使用相同精度；
- scale 是 per-tensor、per-head、per-channel 还是更细粒度；
- scale 来自静态校准还是运行时动态计算；
- prefill 写入和 decode 读取使用哪个 kernel；
- 长上下文、检索、代码复制、数值和低频 token 上的误差是否放大。

不能从“少一半字节”推出模型质量完全不变。至少应在同一解码设置下比较目标任务质量、长上下文位置切片、logprob/困惑度变化、TTFT、inter-token latency 和峰值显存。

## 9. 压缩与淘汰会改变可访问历史

内容压缩按不同轴减少载荷：

| 方法 | 减少的轴 | 可能损失 |
|---|---|---|
| Token 淘汰/滑动窗口 | 序列长度 | 远距离依赖、早期约束、精确复制 |
| Heavy-hitter/注意力选择 | 保留 token 集合 | 未来 query 需要但过去未显著的 token |
| Head/layer 预算 | KV heads 或层 | 特定层/头承担的功能 |
| 低秩表示 | 特征维度 | 难以低秩近似的细节 |
| CPU/NVMe offload | GPU 驻留量 | 传输延迟、带宽竞争和抖动 |
| 重算 | 驻留时间 | 额外计算和首 token/恢复延迟 |

原生 sliding-window attention 与运行时擅自丢弃全注意力模型的历史不是一回事。后者改变模型可访问的信息，不能假定信息和任务质量不受影响。StreamingLLM、H2O、SnapKV 等论文提供各自任务和设置下的证据，迁移到代码、长文档、多轮工具调用或严格引用任务时必须重新评测。

相关算法详见 [6.4.2 KV Cache 压缩与优化技术](./6.4.2-KVCache压缩与优化技术.md) 与 [6.4.3 旋转与数据无关 KV Cache 量化](./6.4.3-旋转与数据无关KVCache量化.md)。

# 6.4.1 · PagedAttention：KV 缓存分页、共享与 vLLM V1

PagedAttention 将每条序列逻辑连续的 KV 缓存切成等长块，再通过 Block Table 映射到不连续的物理块。请求只在需要时取得新块，结束后立即归还；共享前缀可以让多条逻辑序列引用同一物理块。注意力的数学结果没有改变，变化发生在 KV 的物理布局、寻址方式和生命周期管理。

这套机制常与另外三项优化同时出现，但职责不同：Continuous Batching 决定每轮调度哪些请求，Automatic Prefix Caching（APC）决定哪些历史前缀能够跨请求复用，FlashAttention 优化注意力计算的片上分块与 HBM 流量。PagedAttention 为它们提供可动态分配、可共享的 KV 存储基础。

## 1. KV 缓存为何先撞到显存容量

设模型有 $L$ 层，每层有 $H_{kv}$ 个 KV head，每个 head 的维度为 $d_h$，序列长度为 $T$，每个元素占 $b$ 字节。单条序列的 KV 缓存总量为

$$
M_{\mathrm{KV}}
=2LTH_{kv}d_hb.
\tag{1}
$$

系数 2 分别对应 Key 与 Value。MHA 中通常有 $H_{kv}=H_q$；GQA 与 MQA 通过减少 KV head 数降低缓存量。张量并行可能把 KV head 分散到多张卡上，因此式（1）表示所有分片合计的逻辑容量；每卡容量还取决于具体并行与复制方式。

以 $L=80$、$H_{kv}=8$、$d_h=128$、$T=4096$、BF16 为例：

$$
M_{\mathrm{KV}}
=2\times80\times4096\times8\times128\times2
=1.25\ \mathrm{GiB}.
\tag{2}
$$

64 条等长序列需要 80 GiB KV 空间，尚未计入模型权重、激活、CUDA Graph 和临时工作区。KV 容量因此直接限制可同时驻留的请求数。

早期服务系统常为每个请求预留最大长度的连续区域。这会产生三类浪费：尚未生成的预留槽位在请求生命周期内不能借给其他请求；请求提前结束后，预留区域剩余部分成为内部浪费；不同大小的连续区域反复分配和释放又造成外部碎片。PagedAttention 论文在其 2023 年实验中测得，对照系统只有 20.4%–38.2% 的 KV 空间实际存放 token 状态。这个比例属于论文工作负载与当时系统，不能当作所有现代引擎的固定利用率。

## 2. 逻辑块如何映射到物理块

设每个 KV block 容纳 $B$ 个 token。序列位置 $t$ 对应的逻辑块编号与块内偏移为

$$
\ell(t)=\left\lfloor\frac{t}{B}\right\rfloor,
\qquad
o(t)=t\bmod B.
\tag{3}
$$

请求的 Block Table 保存逻辑块到物理块的映射

$$
p_t=\operatorname{BlockTable}[\ell(t)].
\tag{4}
$$

若把单层 KV 存储抽象成 `[physical_block, token_offset, kv_head, head_dim]`，位置 $t$、KV head $h$、通道 $j$ 的地址可写成

$$
\operatorname{addr}(t,h,j)
=\operatorname{base}
+\bigl(((p_tB+o(t))H_{kv}+h)d_h+j\bigr)b.
\tag{5}
$$

真实内核还会考虑 K/V 分离、层、向量化宽度、张量并行与后端布局；式（5）只展示两次间接寻址：先由逻辑块找到物理块，再由块内偏移找到 token 槽位。有效序列长度通常由请求状态单独维护，Block Table 不需要为每个条目存一个“已填充数量”。

![连续预留与 PagedAttention 块映射](./images/fig-pagedattention-blocks.png)

对当前位置 $i$，PagedAttention kernel 按 Block Table 逐块读取历史 $K_j,V_j$，计算的仍是标准注意力：

$$
o_i
=\operatorname{softmax}\!\left(
\frac{q_iK_{1:i}^{\top}}{\sqrt{d_h}}
\right)V_{1:i}.
\tag{6}
$$

物理块不连续不会引入近似，也不会把全注意力变成稀疏注意力。代价是 kernel 多了 Block Table 读取、分支和不规则访存。原论文的消融中，PagedAttention attention kernel 比当时高度优化的 FasterTransformer kernel 慢 20%–26%；系统仍能凭借更高的 KV 利用率容纳更大批次，取得更高端到端吞吐。

## 3. 按需分配把浪费限制在末块

长度为 $T$ 的序列需要

$$
n_{\mathrm{block}}=\left\lceil\frac{T}{B}\right\rceil
\tag{7}
$$

个物理块。Prefill 为当前 prompt 分配所需块；Decode 把新 token 追加到末块，末块填满后再申请下一块；请求结束时，引用计数归零的块回到空闲池。核心状态转移可以写成：

```text
ℓ = token_position // block_size
o = token_position %  block_size

if ℓ == len(block_table):
    block_table.append(allocate_physical_block())

p = block_table[ℓ]
write_kv(p, o, key, value)
```

单条序列未使用的尾部槽位为

$$
W_{\mathrm{slot}}
=\left\lceil\frac{T}{B}\right\rceil B-T,
\qquad
0\le W_{\mathrm{slot}}<B.
\tag{8}
$$

对应显存浪费上界为

$$
W_{\mathrm{bytes}}
<(2LH_{kv}d_hb)B.
\tag{9}
$$

因此，PagedAttention 消除了块池内部因不同连续区间大小造成的外部碎片，也不再为最大生成长度预留整段空间；内部浪费仍存在，但被限制在每条序列的最后一个未满块。长度 $T$ 的块槽利用率为

$$
\eta(T,B)
=\frac{T}{\lceil T/B\rceil B}.
\tag{10}
$$

例如 $B=16$，三条序列长度分别为 41、32、11，需要 3、2、1 个块。96 个槽位中使用 84 个，尾部浪费 12 个。物理块可以散落在池中，Block Table 分别维护三条逻辑顺序。

块越小，式（8）的尾部浪费越低，Block Table、分配操作和 kernel 元数据开销越高；块越大，连续读写更友好，但短序列的尾部浪费和共享粒度都会变差。原论文在其工作负载中认为 16 是较好的默认值。当前 vLLM `CacheConfig` 把 16 作为通用配置基线，但 attention backend 可以给出自己的 preferred block size，CPU 后端文档的默认值为 128；混合注意力、滑动窗口和 Mamba 状态还可能形成不同 KV cache group 并继续做页尺寸与 kernel 对齐。实际物理块、scheduler block 与哈希匹配单元不能一概固定为 16。

## 4. 写时复制支持同一请求的分叉

并行采样与 Beam Search 会从同一 prompt 分出多条候选序列。分叉发生时，无需复制全部 prompt KV；各分支的 Block Table 可以先指向同一组物理块，并增加这些块的引用计数。

若共享块已经填满，后续 token 会写入各分支的新块，共享块保持只读。若多个分支共享最后一个未满块，其中一个分支准备写入时，需要执行写时复制（Copy-on-Write）：

1. 分配一个新物理块；
2. 把旧块中已有的 KV 槽位复制到新块；
3. 将当前分支的 Block Table 条目改指向新块；
4. 旧块引用计数减一，再把新 token 写入私有块。

物理数据复制不能省略。只更新引用计数和 Block Table 会让新块缺少共享前缀的 K/V，之后的注意力结果随即错误。

![同请求写时复制与跨请求前缀缓存](./images/fig-pagedattention-sharing-cow-apc.png)

论文中的共享 prompt 也允许服务端预先保留一组物理块，让多个请求映射到相同前缀；最后一个可写块通过 CoW 隔离。现代 APC 把这种预定义共享扩展为自动发现的跨请求复用，但它使用的查找与驱逐机制已经不同于论文中的静态共享示例。

## 5. PagedAttention、调度器与抢占的分工

PagedAttention 负责“KV 放在哪里”；调度器负责“这一轮让哪些请求计算多少 token”。两者共同决定可并发请求数，但不能把 Continuous Batching、优先级策略或抢占算法都归入 PagedAttention。

SOSP 2023 论文中的 vLLM 使用 FCFS，在块不足时按请求或 sequence group 整体抢占，并比较两种恢复方式：把 KV 块交换到 CPU，或释放 KV 后在恢复时重算。那是论文时代的系统设计。

当前 vLLM V1 的公开 `SchedulerConfig` 提供 `fcfs` 与 `priority` 两种策略，默认 `fcfs`。这里的 FCFS 是请求队列策略；请求若受 token budget、编码器资源或状态对齐约束，本轮可能被暂时跳过，不能把它理解为所有情况下都严格不越序。KV 不足时，V1 默认采用 `RECOMPUTE`：被抢占请求释放活动 KV 与计算进度，重新获得资源后通过 prefill 重建；恢复时仍可重新查询尚未被驱逐的 APC 前缀。CPU swap 不是 V1 的默认抢占路径。最短作业优先、EDF、按最大输出长度排序等策略若由外部调度器或自定义 scheduler 实现，应明确标注实现来源，不能写成 vLLM V1 的内置默认行为。

抢占次数高说明工作集超过当前 KV 容量，通常会恶化端到端延迟。vLLM 官方建议结合 `gpu_memory_utilization`、`max_num_seqs`、`max_num_batched_tokens`、张量并行和流水线并行排查，而不是把频繁抢占视为正常的吞吐优化手段。

## 6. vLLM V1 的块池与自动前缀缓存

vLLM V1 的 KV Cache Manager 预先创建 `KVCacheBlock` 对象池。每个块保存不可变 `block_id`、当前 `block_hash`、引用计数以及空闲队列的前后指针。管理器围绕四个结构工作：

- Block Pool 保存全部物理块对象；
- Free Block Queue 用双向链表维护可分配块和缓存驱逐顺序；
- hash 到 block 的映射支持 APC 查找；
- request 到 block IDs 的映射保存每个请求的逻辑块表。

APC 的稳定设计以块链哈希标识前缀。第 $j$ 个块的键可以概括为

$$
h_j
=H\!\left(h_{j-1},\operatorname{tokens}_j,
\operatorname{extras}_j\right),
\tag{11}
$$

运行时查找键还包含 KV cache group ID；`extras` 可以包含 LoRA 名称、多模态输入哈希、prompt embedding 哈希与 cache salt。父块哈希把当前块绑定到完整前缀，避免“块内 token 相同但之前上下文不同”时错误复用。多模态输入使用图像等内容的哈希区分相同 placeholder token，不要求把物理 KV block 改成变长块。

新请求到达时，管理器从首块向后查找最长连续命中前缀。命中的块增加引用计数；缺失部分从 Free Block Queue 取得新块。请求完成后，引用计数归零的缓存块进入可驱逐队列；需要新空间时，从队首选择最久未使用的缓存块，删除其哈希映射后复用物理块。

vLLM 的发布版 APC 设计文档以完整块缓存为基线。固定到 2026-09-01 的主线提交 `923949e6`，实现又加入 `prefix_match_unit` 与 `cache_partial_block`：当物理块大于哈希单元时，已经完整计算的哈希单元可以在物理块内部注册额外查找键，使请求从更细的合法边界命中已有状态。它不会缓存任意 token 尾部；partial entry 只是指向既有物理块的元数据，也不会分配或复制新的变长物理块。部署时应以安装版本的 `CacheConfig`、Block Pool API 与 engine arguments 为准。

APC 省去的是命中前缀的重复 prefill。若请求没有共享前缀，或大部分时间花在生成独有的长输出上，APC 对 decode 主循环没有直接加速。它也不会改变模型输出；多租户环境仍需用 `cache_salt` 隔离互不信任的缓存域，降低由命中时延暴露前缀存在性的风险。

## 7. vLLM APC 与 SGLang RadixAttention

vLLM APC 使用块链哈希与哈希表查找前缀，不维护一棵名为“Hash RadixAttention”的树。SGLang 的 RadixAttention 则用 radix tree 组织 token 前缀，并把匹配、复用、驱逐与缓存感知调度围绕树结构实现。两者都能复用共享前缀，但索引结构、匹配粒度和调度接口不同。

在知识结构上，本篇负责 PagedAttention 与 vLLM APC；[SGLang 与 Prefill–Decode 分离](../../../9-AI工程化与基础设施/9.4-推理服务框架/9.4.1-SGLang与Prefill-Decode分离.md)负责 RadixAttention、缓存感知调度和跨阶段 KV 传输。将两套机制拆开后，Block Table、哈希链和 radix tree 不会被误写成同一个数据结构。

## 8. 性能收益来自更大有效批次

PagedAttention 不会减少模型参数量，也不会减少单条完整序列必须保存的有效 KV；它减少的是连续预留、碎片和重复前缀，使更多请求的工作集能够同时驻留 GPU。论文在其模型、硬件、请求轨迹和延迟约束下报告 vLLM 相对当时 FasterTransformer 与 Orca 的 2–4 倍吞吐提升。这个结果不能脱离 2023 年对照系统直接外推到当前 vLLM、SGLang、TensorRT-LLM 或不同 attention backend。

评估 Paged KV 管理时至少应同时记录：

- 有效 KV 字节、物理块占用率与每请求尾块浪费；
- 可驻留请求数、每轮 scheduled tokens 与抢占次数；
- prefill TTFT、decode TPOT、吞吐和 P99；
- Block Table/间接寻址带来的 kernel 开销；
- APC 命中 token 数、命中率与实际省去的 prefill 计算；
- block size、KV dtype、并发、输入/输出长度分布和 attention backend。

只看“GPU memory utilization”无法区分模型权重、有效 KV、尾块浪费和临时工作区；只看 APC 命中率也无法判断被命中的前缀是否足够长，或服务是否主要受 decode 限制。

## 9. 适用边界与组合方式

PagedAttention 的内存收益建立在 KV 动态增长、长度未知、并发请求多且显存容量受限的场景上。它仍有四项成本：Block Table 与分配器元数据、间接寻址、末块内部浪费，以及共享/驱逐所需的引用计数与哈希管理。对于静态形状、单请求或 KV 不是容量瓶颈的负载，这些开销未必带来收益。

它与其他优化的组合关系如下：

| 优化 | 直接改变 | 与 PagedAttention 的关系 |
|---|---|---|
| FlashAttention | 注意力 tile 与 HBM I/O | 可读取 paged KV；一个管计算数据流，一个管物理布局 |
| KV 量化 | 每个 KV 元素的字节数 $b$ | 直接缩小式（1），分页继续负责分配与共享 |
| GQA/MQA/MLA | KV 表示的 head 数或潜在维度 | 直接缩小每 token KV，分页继续管理生命周期 |
| Continuous Batching | 每轮请求与 token 预算 | 利用分页释放和扩展请求工作集 |
| APC/RadixAttention | 跨请求前缀复用 | 复用的对象是分页后的 KV 状态 |
| Prefill–Decode 分离 | KV 的跨节点生产与消费 | 需要在节点之间传输并重建块元数据与所有权 |
| 投机解码 | 每次目标验证提交多个 token | 需要为草稿、验证、回滚和追加预留正确块状态 |

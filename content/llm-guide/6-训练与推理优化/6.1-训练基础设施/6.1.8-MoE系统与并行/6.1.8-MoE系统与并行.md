# 6.1.8 MoE 系统与并行

MoE 在公式上只改了 FFN 一层: 路由器给每个 token 选 Top-$K$ 个专家, 输出按门控权重加权求和. 路由, 共享专家, 负载均衡和 STE 的推导都在 [2.6 MoE 总览](../../../2-核心原理与架构/2.6-MoE/2.6-MoE.md). 到了多卡上, 同一个改动带出三件稠密模型没有的事: token 要在卡之间来回搬, 每个专家分到的 token 数每步都在变, 专家权重总量比激活量大一个数量级以上. 本节收的就是这三件事在系统层的处理.

稠密 Transformer 的并行已经在 [6.1.1 分布式训练](../6.1.1-分布式训练/6.1.1-分布式训练.md) 讲过 DP, TP, PP 三个轴. MoE 多出来的一个轴是专家并行 (EP), 它的通信原语和 TP 不同, 它的计算形状也和稠密 GEMM 不同. 本节三篇文章都围绕这一个轴展开, 只是切入的粒度不一样.

## 1. 稀疏激活为什么成了系统问题

### 1.1 参数驻留与每 token 计算分开了

稠密 FFN 的参数量和每 token 计算量是绑在一起的: 参数翻倍, 每个 token 的 FLOPs 也翻倍. MoE 把两者拆开. 以 DeepSeek-V3 的配置为例, 每个 MoE 层有 256 个路由专家, 每 token 只激活其中 8 个, 计算只碰到一小部分权重, 但另外 248 个专家的权重仍要放在某张卡的 HBM 里, 下一个 token 随时可能选中它们.

参数和计算一旦分家, 显存就成了第一个约束. 显存够, 就把专家切到多张卡上, 每张卡只持有一部分专家, 这就是 EP; 显存不够, 就把冷专家放到 CPU 内存或 NVMe, 用到时再搬回来, 这就是卸载. 两条路在 [05](./01-MoE系统与架构优化综述/01-MoE系统与架构优化综述.md) 里按「显存充足」和「显存受限」两种场景分开写, 在 08 的第 1 节里收成一句判断: 显存够走 EP, 不够走卸载. 它们改的是存储层级, 路由公式一个字没动.

### 1.2 搬的是激活, 不是权重

EP 下的通信对象容易弄错. 路由器在本卡算出 Top-$K$ 下标之后, 用 All-to-All 把 token 的隐状态发到持有目标专家的卡 (Dispatch), 专家算完再用一次 All-to-All 发回原卡 (Combine). 专家权重始终躺在自己那张卡上, 不经过互联. 08 用式 (2) 估一层来回的字节数:

$$
\mathrm{bytes}_{\mathrm{A2A}}\approx 2\cdot T\cdot K\cdot d\cdot b,
$$

其中 $T$ 是本卡这一步的 token 数, $K$ 是每 token 去的专家数, $d$ 是隐状态宽度, $b$ 是激活的字节宽度 (BF16 取 2), 前面的 2 是 Dispatch 和 Combine 各一次. 代入 Prefill 的 $T=32768$, $K=2$, $d=4096$, 一层来回约 1 GiB; 换成 Decode 的 batch 8, $T=8$, 只剩约 256 KiB. 字节少了, All-to-All 的启动延迟还在, 这就是训练时能开大 EP 度, 在线 Decode 却要收小 EP 度的原因.

## 2. 三篇文章的关系

### 2.1 从场景清单到数据流图

05 和 07 写得早, 定位不同. 05 是一份按问题铺开的综述: 并行组合, 通信优化, 访存与 kernel, 硬件加速器, 卸载, 每一类列几项代表工作, 末尾给一张按部署场景的选型表. 它的价值在覆盖面, 读完知道 MoE 系统优化大致分几条线, 每条线有哪些名字. 它对单个工作的描写停在思路层, 没有给能复算的数.

[07](./02-MoE混合并行部署与通信优化图解/02-MoE混合并行部署与通信优化图解.md) 换了一个角度, 按单卡, 纯 TP, 纯 EP, TP 加 EP 混合四步, 把通信画到计算图上. 它的要点是把两种集体通信分开: 注意力侧的 TP 用 AllReduce, 每张卡要同一份聚合结果; 专家侧的 EP 用 All-to-All, 每张卡把不同的 token 发给不同的 rank. 07 还写了 DeepGEMM 的 Contiguous 和 Masked 两种 layout, 以及把 AllReduce 拆成 Reduce-Scatter 加 All-Gather 以便和相邻 GEMM 重叠的做法.

### 2.2 08 把前两篇收成一篇

08 是本节的主文. 它把 05 的并行与卸载, 07 的数据流和 layout 都收了进来, 再往下补了三样前两篇没有的东西. 第一是数量级: 上面的 All-to-All 字节估算, 以及卸载时 200 MB 专家权重经 PCIe 5.0 单次约 3 ms 的估算. 第二是计算侧的 Tile 填充: 每个专家分到的 token 数整除不了 128 时, Grouped GEMM 的尾部全是填充, 细粒度加小 batch 时这部分浪费最大. 第三是失效清单, 逐条写出把哪个数安到哪个场景上会出错.

三篇的演进可以压成一条线: 05 告诉读者有哪些问题, 07 把通信放到计算图上的正确位置, 08 给每个问题配上能复算的量和能对上论文的系统数字. 只读一篇的话读 08; 05 和 07 留着, 用来对照 08 收进来的图和表最早从哪里来.

## 3. 共用记号与系统工作对照

### 3.1 记号

本节各篇共用下面这组记号, 正文里不再重复定义. $E$ 是一层的路由专家数, $K$ 是每 token 激活的路由专家数, $T$ 是本卡一步处理的 token 数 (Prefill 时是 batch 乘序列长度, Decode 时往往只剩 batch), $d$ 是隐状态宽度, EP 度是专家被切到几张卡上. 容量 $C$ 是每个专家一步最多接收的 token 数, 超出的 token 在 Dispatch 写槽时被丢掉, 由残差把原输入送走. Tile 指 Tensor Core 按固定 $M$ 块吃矩阵时的块大小, 常见取 128.

这组记号里最容易混的是两种「均衡」. 负载均衡损失或无辅助损失偏置拧的是「哪个专家被选中」, 作用在训练里; token rounding 拧的是「选中之后这块 GEMM 的形状」, 作用在 kernel 里. MoonEP 要求每个 rank 收到恰好 $S\times K$ 个 token, 管的是卡与卡之间的 token 数, 和 [Quantile Balancing](../../../2-核心原理与架构/2.6-MoE/04-Stable-LatentMoE与Quantile-Balancing/04-Stable-LatentMoE与Quantile-Balancing.md) 管的专家间被选次数也不在一层.

### 3.2 系统工作对照

| 工作 | 改的环节 | 08 引用的结果 | 对照基线 |
|---|---|---|---|
| Tutel (2022) | 运行时切换 DP/EP 组合, 2DH 分层 All-to-All | 单层 4.96× (16 张 A100), 5.75× (2048 张) | Fairseq |
| SmartMoE (ATC 2023) | 离线构造放置池, 在线搜索专家放置 | 端到端最多 1.88×, 最多 64 GPU | FasterMoE |
| MegaBlocks (2022) | block-sparse 算子, dMoE 不丢 token | 端到端最多约 40% | Tutel |
| ScatterMoE (2024) | scatter 与 grouped GEMM 融合 | 相对 MegaBlocks 少一次 gather 拷贝 | MegaBlocks |
| SonicMoE (2025) | 少存激活, IO 重叠, token rounding | Hopper 核吞吐 1.86×, 激活 -45% | ScatterMoE BF16 核 |

表里五个工作分两组. Tutel 和 SmartMoE 选的是并行怎么拼, 专家放在哪张卡, 属于调度层; MegaBlocks, ScatterMoE 和 SonicMoE 管的是专家 GEMM 怎么喂给 Tensor Core, 属于 kernel 层. 两组可以叠加使用, 也不互相替代: kernel 再快, 热专家所在的 rank 仍会让其他卡等它; 调度再好, Tile 填充的浪费也不会因此消失.

最后一列是读这张表的关键. 五个倍数的分母各不相同, 年份前后差三年, 硬件从 A100 到 H100 都有, 所以不能相加, 也不能拿来排名次. 08 第 6 节专门写了这一点: SonicMoE 的 1.86× 比的是单个 kernel 的吞吐, 它的端到端数字是 64 张 H100 约 213B token/天对 ScatterMoE 96 张 H100 约 225B token/天, 卡数不同, 读成「同卡快 1.86 倍」就错了.

## 4. 读法与边界

### 4.1 按背景进入

做训练系统的读者, 建议先读 08 的第 1 到 3 节, 把 DP, TP, EP 三个轴和 All-to-All 的字节估算弄清楚, 再回 [6.1.1](../6.1.1-分布式训练/6.1.1-分布式训练.md) 看 DeepEP 和 MoonEP 怎么把 All-to-All 藏进计算. 做推理部署的读者, 重点是 08 第 5 节 Contiguous 与 Masked 两种 layout: Prefill 可以按专家拼连续 buffer, Decode 加 CUDA Graph 时每步分配都在变, 只能用带 mask 的 grouped GEMM 保住静态图. 07 的四步图解适合第一次接触 TP 加 EP 混合部署时先看.

写 kernel 的读者直接读 08 第 4 节和 SonicMoE 部分. 那里讲的是细粒度 MoE 的两个计算侧代价: 反向按 $O(TKd)$ 物化激活会让显存随粒度涨, Tile 填不满会让 Tensor Core 白转. 只关心「为什么 MoE 推理比同激活量的稠密模型难优化」的读者, 读 08 第 1 节和第 8 节失效清单就够了.

### 4.2 与相邻章节的分工

本节不写路由和负载均衡的公式, 那些在 [2.6](../../../2-核心原理与架构/2.6-MoE/2.6-MoE.md) 和 [DeepSeek-MoE](../../../2-核心原理与架构/2.6-MoE/01-DeepSeek-MoE/01-DeepSeek-MoE.md). 卡间通信重叠的实现 (Wave, DeepEP, MoonEP) 在 [6.1.1](../6.1.1-分布式训练/6.1.1-分布式训练.md). 专家权重量化在 [MoE 模型量化技术综述](../../6.3-模型压缩/6.3.1-量化/05-MoE模型量化技术综述/05-MoE模型量化技术综述.md), 它和卸载处理的是同一种冷热差异, 一个降位宽, 一个换存储层级.

FPGA, 近存计算和 PIM 这类专用硬件放在 [9.1.5 MoE 硬件与加速](../../../9-AI工程化与基础设施/9.1-硬件基础/9.1.5-MoE硬件与加速/9.1.5-MoE硬件与加速.md). 本节默认的硬件是 GPU 集群加 NVLink 与 IB 两级互联; 9.1.5 讨论的是动态路由放到固定数据流的芯片上会出什么问题. 两节在卸载和冷热专家分离上有交集: 本节从 PCIe 带宽算卸载能不能藏住, 9.1.5 从「传激活不传权重」的近存设计出发绕开这次搬运.

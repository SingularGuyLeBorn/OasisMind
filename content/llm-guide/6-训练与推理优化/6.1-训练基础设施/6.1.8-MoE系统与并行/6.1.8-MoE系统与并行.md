# 6.1.8 MoE 系统与并行

MoE 在公式上只改了 FFN 一层: 路由器给每个 token 选 Top-$K$ 个专家, 输出按门控权重加权求和. 路由, 共享专家, 负载均衡和 Top-$K$ 梯度的推导都在 [2.6 MoE](../../../2-核心原理与架构/2.6-MoE/2.6-MoE.md). 到了多卡上, 同一个改动带出三件稠密模型没有的事: token 要在卡之间来回搬, 每个专家分到的 token 数每步都在变, 专家权重总量远大于每步用到的那部分. 本节讲这三件事在系统层的处理.

稠密 Transformer 的 DP, TP, PP 三个轴在 [6.1.1 分布式训练](../6.1.1-分布式训练/6.1.1-分布式训练.md) 讲过. MoE 多出来的一个轴是专家并行 (EP), 它的通信原语和 TP 不同, 计算形状也和稠密 GEMM 不同. 本节三篇都围绕这一个轴展开: 01 讲通信, 02 讲推理部署, 03 讲专家计算.

## 1. 稀疏激活为什么成了系统问题

### 1.1 参数驻留与每 token 计算分开了

稠密 FFN 的参数量和每 token 计算量是绑在一起的: 参数翻倍, 每个 token 的 FLOPs 也翻倍. MoE 把两者拆开. 以 DeepSeek-V3 为例, 每个 MoE 层有 256 个路由专家, 每 token 只激活其中 8 个, 计算只碰到一小部分权重, 另外 248 个专家的权重仍要放在某张卡的 HBM 里, 下一个 token 随时可能选中它们.

参数和计算分开以后, 显存成了第一个约束. 显存够, 就把专家切到多张卡上, 每张卡只持有一部分专家, 这就是 EP; 显存不够, 就把一部分专家放到 CPU 内存或 NVMe, 用到时再处理, 这就是卸载. 两条路改的都是存储位置, 路由公式不变. EP 是本节的主线, 卸载放在 [02](./02-MoE推理部署/02-MoE推理部署.md) 第 5 节.

### 1.2 搬的是激活, 不是权重

EP 下通信的对象容易弄错. 路由器在本卡算出 Top-$K$ 下标之后, 用 All-to-All 把 token 的隐状态发到持有目标专家的卡 (dispatch), 专家算完再用一次 All-to-All 发回原卡 (combine). 专家权重始终在自己那张卡上, 不经过互联. 一层来回的字节数约为 $2TKdb$, 代入 prefill 的 $T=32768$, $K=2$, $d=4096$, BF16, 一层来回约 1 GiB; 换成 decode 的 batch 8, $T=8$, 只剩约 256 KiB.

字节少了, All-to-All 的启动延迟和跨节点的往返延迟却不变. prefill 的通信是带宽问题, 可以和大块计算重叠; decode 的通信是延迟问题, 消息小, 次数一样多. 计算一侧也有同样的分化: prefill 时每个专家分到上千个 token, 专家 GEMM 能跑满 Tensor Core; decode 时每个专家只分到几十个, 读权重的时间成了主项. 同一个 MoE 层在两个阶段要按两种形状优化, 这是本节把推理部署单列一篇的原因.

## 2. 三篇文章

### 2.1 01: 专家并行与 All-to-All 通信

[01](./01-MoE专家并行与All-to-All通信/01-MoE专家并行与All-to-All通信.md) 从 EP 的数据流出发, 推出 dispatch 与 combine 的通信量 $V=tkdb(R-1)/R$, 并和 TP 的 Ring AllReduce 对比: 每 token 激活 8 个专家, 8 张卡时两者相当, 64 张卡时 EP 的通信量约为 TP 的八分之一. 接着讲 GShard 与 Switch 的早期切分, Tutel 的 2DH All-to-All 怎样把小消息合并成大消息, DeepSeek-V2 的设备受限路由和 V3 的 PP16 加 EP64 加 ZeRO-1 配置.

V3 一节是 01 的重点. DualPipe 的气泡公式, IB 50 GB/s 与 NVLink 160 GB/s 两级 dispatch 的推导, 节点受限路由把每 token 的 IB 流量限制在 28672 字节, FP8 dispatch 的缩放因子开销, 以及 20 个 SM 专做通信的取舍都在这里. 最后一节是通信 kernel: DeepEP 的统一接口和对齐约定, Comet 在单层内部的细粒度重叠, Flux 在 TP 一侧的 GEMM 与通信融合.

### 2.2 02: 推理部署

[02](./02-MoE推理部署/02-MoE推理部署.md) 先用通信量和算术强度 $I=2n/b$ 两个式子说明 prefill 与 decode 的瓶颈为什么不同, 再整理 V3 报告的部署: prefill 32 卡, 注意力 TP4 加 DP8, MoE 用 EP32 和 32 个冗余专家; decode 320 卡, EP320, 每卡一个专家. 文中按 decode 每专家 256 个 token 的上限算了一遍: 读一个 FP8 专家约 13 μs, dispatch 和 combine 经 IB 分别约 37 μs 和 73 μs, 通信比计算更重.

后半篇讲负载和形状. 冗余专家与 MoonEP 管部署时的负载偏移, Tutel 与 SmartMoE 在运行时切换并行方式或专家放置; CUDA Graph 要求形状静态, DeepEP 的 `do_cpu_sync` 和 MetaShuffling 的排序方案各自处理每步变化的专家 token 数; 显存不够时, Fiddler 按 token 数在 CPU 计算与搬权重之间选, Pre-gated MoE 让门控提前一层选专家, 使预取可以确定地进行.

### 2.3 03: 专家计算与系统优化分类

[03](./03-MoE专家计算/03-MoE专家计算.md) 从单卡上的五步前向出发, 推出 grouped GEMM 对齐填充的上界 $P<E_{\mathrm{local}}b_M$: V3 训练时填充不到 1.6%, 每专家 100 个 token 时达到 28%. 然后比较 DeepGEMM 的 Contiguous 与 Masked 布局, 以及 MegaBlocks 的块稀疏和 ScatterMoE 的下标填充两种不复制数据的做法.

SonicMoE 一节推导两个式子. 一是专家的算术强度 $I=3/(2/d+2/n+3/T_e)$, 代入 V3 的形状, 每专家 256 个 token 时约 231 FLOPs/字节, 仍低于 H100 BF16 的平衡点; 二是激活显存, $nK$ 不变时常规实现缓存 $O(TKd)$ 的张量, 随粒度增长, SonicMoE 只缓存 $2Td+4TKn$ 字节. 最后按通信, 负载, 计算, 存储四类瓶颈给 MoE 系统工作分类, 并列出各自论文的对照基线.

## 3. 共用记号与常用数量级

### 3.1 记号

本节各篇共用下面这组记号. $E$ 是一层的路由专家数, $K$ 是每 token 激活的路由专家数, $T$ 是本卡一步处理的 token 数 (prefill 时是 batch 乘序列长度, decode 时往往只剩 batch), $d$ 是隐状态宽度, $n$ 是专家中间维, $b$ 是每元素字节数, $R$ 是 EP 度. $T_e$ 是某个专家这一步分到的 token 数, 均匀路由下 $T_e=TK/E$. 01 里按原论文写成小写 $t$, $k$ 的地方, 含义与 $T$, $K$ 相同.

容量 $C$ 是每个专家一步最多接收的 token 数, 超出的 token 在 dispatch 写槽时被丢掉, 由残差把原输入带过去. $b_M$ 或 $M_{\mathrm{tile}}$ 指 Tensor Core 按固定 M 块处理矩阵时的块大小, 常见取 128. 这组记号里最容易混的是三种「均衡」: 负载均衡损失或无辅助损失偏置管训练中哪个专家被选中, token rounding 管单步内每个专家的 token 数对齐到 tile, MoonEP 与冗余专家管卡与卡之间的 token 数.

### 3.2 常用数量级

下表是三篇里反复用到的几个数, 方便对照:

| 量 | 数值 | 出处 |
|------|------|------|
| 一层 All-to-All 来回字节 | prefill 约 1 GiB, decode 约 256 KiB | 01 式 (1), 02 式 (1) |
| V3 每 token 跨节点字节 | 28672 B (4 个节点, FP8) | 01 第 3.3 节 |
| H100 BF16 平衡点 | 约 295 FLOPs/字节 | 02 第 1.2 节 |
| 读一个 V3 FP8 专家 | 约 44 MB, 约 13 μs | 02 第 2.2 节 |
| grouped GEMM 填充 | V3 训练不到 1.6%, 每专家 100 token 时 28% | 03 第 2.1 节 |

这些数都由公式加公开配置算出, 换一组配置可以照着重算. 前两行说明通信量取决于 $T$ 和节点受限路由; 中间两行说明 decode 受带宽限制, 每专家要几百个 token 才能跑满算力; 最后一行说明专家越细, 填充占比越高. 三者合起来, 就是细粒度 MoE 在系统上比同激活量的稠密模型难优化的原因.

各篇引用的论文加速比不在这张表里. 那些倍数的分母各不相同, 年份和硬件也不同, 只能在各自的设定里读, 03 第 4.2 节专门列了每项工作的对照基线.

## 4. 读法与边界

### 4.1 按背景进入

做训练系统的读者从 01 开始, 先把 EP 的通信量和 V3 的并行配置弄清楚, 再读 03 的 grouped GEMM 和 SonicMoE, 那里讲细粒度专家在计算侧的两个代价: 显存随粒度增长, tile 填不满. 做推理部署的读者从 02 开始, 遇到 dispatch 的细节回查 01 第 1.4 节和第 4.2 节, 遇到 Masked 布局回查 03 第 2.2 节.

写 kernel 的读者直接读 03, 其中第 3 节的两个推导是理解近年 MoE kernel 设计的基础. 只想知道「MoE 层为什么慢, 慢在哪里」的读者, 读本页第 1 节和 03 第 4 节的分类即可, 那里给了判断瓶颈的三个量: 通信量, 算术强度, 各卡 token 数的最大值与平均值之比.

### 4.2 与相邻章节的分工

路由, 负载均衡损失和容量因子的公式在 [2.6 MoE](../../../2-核心原理与架构/2.6-MoE/2.6-MoE.md), 共享专家与细粒度切分在 [DeepSeek-MoE](../../../2-核心原理与架构/2.6-MoE/01-DeepSeek-MoE/01-DeepSeek-MoE.md), token drop 与 dropless 对质量的影响在 [MoE 负载均衡与容量](../../../2-核心原理与架构/2.6-MoE/03-MoE负载均衡与容量/03-MoE负载均衡与容量.md). 本节只在系统需要时引用这些结论. 稠密模型的 DP, TP, PP, ZeRO 与 EP Wave 的隐藏条件在 [6.1.1 分布式训练](../6.1.1-分布式训练/6.1.1-分布式训练.md).

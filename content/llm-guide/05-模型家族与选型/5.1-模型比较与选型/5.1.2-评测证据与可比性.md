# 评测证据与可比性

模型分数只有和“谁、在什么数据上、用什么设置、由谁判定”绑定时才有意义。一次看似公平的 A/B 测试，可能同时改变了模型版本、思考预算、搜索工具、上下文模板和裁判模型，最终无法说明差异来自哪里。

## 证据层级

不同来源回答不同问题，不能互相替代：

| 证据 | 能支持什么 | 主要限制 |
|---|---|---|
| 一手论文、模型卡、系统卡、API 文档 | 身份、披露的能力边界、官方评测设置 | 常为发布方自报，未必覆盖真实业务 |
| 权重、代码、数据和日志 | 复现、配置核验、训练与推理分析 | 开放范围和许可可能不同 |
| 独立复现 | 在另一环境中验证结论 | harness、硬件和实现可能改变结果 |
| 公共 benchmark | 粗筛能力、发现测试维度 | 污染、饱和、prompt 敏感和任务失配 |
| 线上偏好或用户反馈 | 产品体验和真实偏好信号 | 流量组成、产品工具、路由和版本不透明 |
| 内部冻结验收集 | 支持具体上线决策 | 覆盖范围有限，需要持续维护 |

厂商结果适合发现候选，内部盲测才承担验收。结论与来源应并列保存，不把“报告中领先”改写成“模型全面领先”。

## 每次结果的最小记录

### 模型与系统身份

- 家族、精确模型 ID/checkpoint、修订、量化和权重哈希；
- Base、Instruct、Chat、Thinking 或领域微调身份；
- API 端点、dated snapshot 或别名、区域和评测日期；
- 系统提示、对话模板、路由、RAG、工具和安全策略版本。

### 数据与任务

- 数据集名称、版本、提交哈希、划分和样本 ID；
- 原始题面、预处理、翻译、过滤和去重规则；
- few-shot 示例来源、顺序和是否进入上下文；
- 公开时间、污染风险、盲测状态和判分单位；
- 任务指标、严重错误定义与缺失输出处理。

### 生成与推理设置

- prompt/template 的完整文本和版本；
- temperature、top-p、seed、停止条件与最大输出；
- reasoning effort、思考 token 或测试时计算预算；
- 重试、self-consistency、best-of、投票和超时规则；
- 上下文截断、缓存和批处理策略。

### 工具与执行环境

- 搜索、浏览、代码执行、检索库和函数清单；
- 工具版本、权限、网络、超时、返回格式和失败处理；
- 推理框架、硬件、精度、并发和批处理；
- 是否把工具执行失败计入模型结果。

### 裁判与统计

- 规则判分代码和版本；
- LLM-as-a-judge 的模型、snapshot、prompt、位置随机化和采样设置；
- 人工评审指南、评审者数量、盲法、分歧与仲裁；
- 样本量、均值、分位数、置信区间或配对重采样方法。

## 哪些结果不可直接横比

- Base 与 Instruct，普通与 Thinking，裸模型与带工具系统；
- 不同 benchmark 版本、语言翻译版或污染处理版；
- 不同 prompt、shot 数、答案提取器和无效答案规则；
- 不同推理预算、重试次数、投票次数或代码执行权限；
- 厂商自报、第三方复现和线上 Arena；
- 标称上下文窗口与长文本任务的有效性能；
- 总参数、激活参数、权重显存、KV cache 和每 token FLOPs；
- 平均延迟、首 token 延迟、逐 token 延迟与系统吞吐。

如果无法统一设置，应分别报告并说明差异，而不是硬拼成一张总榜。

## Benchmark 污染与饱和

模型训练数据通常不完全公开，不能仅凭知识截止日期断言“无污染”。污染可能来自题目、答案、解析、代码仓库、翻译版、排行榜讨论或合成数据。

### 风险信号

- benchmark 长期公开、答案易检索或在教程中大量出现；
- 模型对原题异常稳定，但轻微改名、换数或重排选项后显著下降；
- 输出复现了标准解析中的特殊措辞或错误；
- 结果接近饱和，模型间差异小于评测噪声；
- 发布方未说明去污染或只说明字符串精确匹配。

### 缓解方法

1. 使用私有、滚动更新并控制访问的盲测集。
2. 保存题目来源和首次公开日期，做精确与近重复检索。
3. 对实体、数值、选项顺序、语言和表述做受控扰动，检查能力是否稳健。
4. 保留污染高风险 benchmark 作为历史对照，但降低其决策权重。
5. 把公开集、开发集和最终验收集分开，禁止用验收错误反复调 prompt。

污染检查只能降低风险，通常不能证明训练语料中绝对不存在测试内容。

## 工具和推理预算造成的伪提升

### 工具

搜索可以提高时效题，代码执行可以提高可验证计算，RAG 可以提供私有知识。应至少报告两组结果：

- 裸模型或统一工具条件下的模型比较；
- 候选各自最佳允许系统配置下的端到端比较。

前者帮助理解模型差异，后者支持产品决策。二者不能用同一个标题概括。

### 推理预算

更长思考、更多采样和多数投票往往同时增加质量、延迟和成本。比较时固定预算，或画出质量—延迟—成本曲线，不只报告每个模型的最佳点。

### LLM 裁判

裁判可能偏好相同家族、较长答案、特定风格或先出现的选项。应随机交换位置、隐藏模型身份、校准人工样本，并报告裁判与人工的一致性。高风险事实、代码和结构化输出优先使用可执行或规则判分。

## 从平均分走向失败分布

至少同时报告：

- 总体结果与语言、长度、模态、任务、风险等级分层结果；
- 严重错误率、应拒/不应拒、无效输出和工具失败；
- p50/p95/p99 延迟、成本尾部和重试次数；
- 多次运行的方差，以及接近候选之间的置信区间；
- 代表性失败案例和不可判定样本。

“A 比 B 高 0.5 分”只有在差异大于评测噪声、样本匹配且业务损失相关时才有决策意义。

## 推荐的结果卡

| 字段 | 记录内容 |
|---|---|
| 决策与日期 | 任务、负责人、评测窗口、复查日期 |
| 被测对象 | 精确模型/API/产品/系统身份 |
| 数据 | 版本、划分、样本量、污染风险 |
| 设置 | prompt、采样、推理预算、工具、judge |
| 质量 | 主指标、分层结果、严重错误、置信区间 |
| 运行 | TTFT、TPOT、吞吐、失败和资源 |
| 成本 | 每请求、每有效结果、重试与人工成本 |
| 结论 | 适用范围、反例、不确定性和后续实验 |

可参考 [HELM](https://arxiv.org/abs/2211.09110) 对场景、指标和透明记录的组织方式；它提供方法参考，不替代业务验收。

# Kimi K2.7 Code：软件工程专项 Agent

> 核验日期：2026-09-01。官方 Kimi Code 更新日志将 K2.7 Code 的发布日记为 2026-06-12；旧稿中的 2026-08-12 是错误日期。

## 定位

Kimi K2.7 Code 是基于 K2.6 构建的软件工程专项开放权重模型。它沿用 K2.5/K2.6 的多模态 MoE 架构，把训练重点放在代码仓库理解、编辑、测试、终端与其他开发工具的连续交互。官方将它描述为 thinking-only 模型，也就是运行时应保留其推理流程，而不是随意当作普通无思考 Instruct 检查点。

## 身份卡

| 字段 | 官方模型卡口径 |
|---|---|
| 发布日期 | 2026-06-12 |
| 基础版本 | Kimi K2.6 |
| 总参数 / 激活参数 | 约 1T / 32B |
| Transformer 层数 | 61 |
| 注意力 / MoE | MLA；384 个专家、选 8 个、1 个共享专家 |
| 视觉编码器 | MoonViT，约 400M 参数 |
| 上下文 | 256K |
| 推理模式 | thinking-only |
| 许可 | Modified MIT License |

模型卡称它在保持能力的同时，相比 K2.6 平均减少约 30% 推理 token。这个数字是官方在其任务分布下的报告，不应外推为每个仓库或每次请求恒定节省 30%。

## 为什么代码模型仍需要视觉

现代软件工程不只有源码。截图、设计稿、图表、报错界面和浏览器状态都可能成为任务输入。K2.7 Code 保留 MoonViT，可把视觉观察纳入调试或前端实现。但视觉支持不能取代可执行验证：像素相近的界面仍可能有无效交互、错误状态或不可访问结构。

## 一个可靠的代码 Agent 闭环

1. 读取仓库约束、任务目标和允许修改的范围；
2. 用搜索和依赖关系定位最小相关上下文；
3. 先解释假设，再做小而可审查的修改；
4. 运行目标测试、静态检查或最小复现；
5. 根据真实输出修正，不伪造“测试通过”；
6. 审查最终差异、未解决风险和不相关改动；
7. 对提交、发布和外部系统写入保留用户授权边界。

256K 窗口可以容纳更多仓库材料，但不替代检索和范围控制。将整个仓库、构建产物和日志一次性塞入上下文，往往会增加噪声、泄露风险和成本。

## 与 K2.6、K3 的关系

- **K2.6 → K2.7 Code**：主体架构延续，后训练更加聚焦软件工程与工具轨迹。
- **K2.7 Code ≠ K3**：K3 使用新的 2.8T/104B 基座、KDA/MLA 混合架构和 1M 上下文；不能用发布日期相近把 K2.7 写成 K3 的代码版。
- **专项模型 ≠ 全面升级**：K2.7 Code 在代码任务上更有针对性，但通用写作、知识问答或其他模态任务仍应单独比较。

## 部署与安全

- 遵循官方 thinking 模板和停止条件；剥离推理流程可能改变工具行为。
- 工具层实施路径范围、网络访问、密钥隔离、命令审批和资源配额。
- 对文件覆盖、依赖升级、数据库迁移和部署设置额外确认；模型的高置信表达不是授权。
- 按完成率、测试通过率、diff 质量、调用次数、token 和时延联合评测。
- 许可为 Modified MIT；分发、微调或提供服务前检查仓库当时的完整许可证。

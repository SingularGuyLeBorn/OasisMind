# Kimi K2.5：原生多模态与 Agent Swarm

> 核验日期：2026-09-01。K2.5 于 2026-01-27 发布；它延续 K2 的 1T/32B MoE 主体并加入视觉编码器。官方 Agent Swarm 是模型、训练与产品编排的组合，不能等同于 Transformer 内部“有 100 个专家”。

## 定位

Kimi K2.5 是 K2 开放权重主线中的原生多模态版本。官方报告说明，它从 K2 Base 继续预训练约 15T 混合视觉与文本 token，再进行多模态指令、推理、代码和 Agent 后训练。模型因此可以在同一上下文中接收文本、图像与视频信息，并用文本或工具调用完成任务。

“原生多模态”在这里表示视觉 token 被纳入模型训练与推理流程，不表示它能生成图像，也不表示所有视觉任务都比专用视觉模型可靠。

## 身份卡

| 字段 | 官方模型卡口径 |
|---|---|
| 发布日期 | 2026-01-27 |
| 总参数 / 激活参数 | 约 1T / 32B |
| Transformer 层数 | 61 |
| 注意力 | MLA，64 个注意力头 |
| MoE | 384 个专家、每 token 选择 8 个，另有 1 个共享专家 |
| 视觉编码器 | MoonViT，约 400M 参数 |
| 上下文 | 256K |
| 模态 | 文本、图像、视频输入；文本与工具调用输出 |
| 许可 | Modified MIT License |

这些数值与 K2 主体高度一致，说明 K2.5 的重点是继续预训练、视觉接入和后训练，而不是另建一个不同规模的语言骨干。

## 视觉如何接入

MoonViT 把图像或视频帧转换为视觉 token，再交给语言模型联合处理。因而一个视觉任务至少包含三类误差来源：视觉编码/压缩、文字识别或对象定位，以及语言推理。模型答错时不能一概归因于“推理差”。

对视频还要记录采样帧率、帧数、分辨率和时间顺序；同一个 256K 窗口需要在文本、视觉 token、工具结果和输出之间共享预算。最大窗口不是“无限视频容量”。

## 从单 Agent 到 Agent Swarm

官方介绍的 Agent Swarm 会把可并行的复杂任务拆给多个子 Agent，再汇总结果。K2.5 发布材料给出的产品级口径是最多 100 个子 Agent、约 1,500 次工具调用，并报告在其测试任务上最高约 4.5 倍的执行提速。

这些数字必须带限定：它们描述官方系统和评测设置，不是 K2.5 权重单独保证的固定能力。并行化只有在子任务相对独立且协调开销较低时才有效；共享状态、串行依赖和结果冲突会削弱加速。

一个可靠的多 Agent 系统还需要：

- 明确拆分依据、共享上下文与成功标准；
- 每个子 Agent 的最小权限、预算和超时；
- 对重复劳动、冲突修改和失败结果做检测；
- 汇总阶段回到原始证据，而不是只相信子 Agent 摘要；
- 对外部写操作、费用和隐私建立统一审计。

## 训练主线

K2.5 报告的重要点不是“多加一批图片”，而是继续预训练与后训练的连续设计：混合视觉/文本预训练建立跨模态表示；指令与推理数据教模型回答视觉问题；Agent 数据再把视觉观察接入工具与动作。官方报告还介绍了代码、视觉、推理和 Agent 任务的评测，但这些得分应标为作者报告结果，不跨评测协议与其他模型直接排位。

## 选型与部署

- 只需要文本时，K2 0905 或 Thinking 可能更简单；视觉输入才是选择 K2.5 的关键增量。
- 自托管需同时支持 K2 MoE 主体、MoonViT、媒体预处理和官方聊天模板。
- 256K 下视觉 token 的数量受分辨率、帧采样与处理器配置影响，应按真实输入测显存和时延。
- Agent Swarm 是上层编排能力；部署一个权重服务不会自动获得 100 个并发子 Agent 的调度、沙箱与审计。

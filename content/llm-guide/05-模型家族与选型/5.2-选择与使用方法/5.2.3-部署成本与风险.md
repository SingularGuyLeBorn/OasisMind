# 部署成本与风险

模型在单条演示中响应很快，不代表系统在生产并发下可用；每百万 token 单价很低，也不代表每个成功任务成本低。部署评估应同时覆盖性能、容量、总拥有成本、数据治理和恢复能力。

## 先选部署边界

| 方式 | 主要优势 | 主要约束 | 必测风险 |
|---|---|---|---|
| 公共 API | 上手快、无需管理权重和集群 | 版本、区域、限流、数据条款和供应商依赖 | 别名漂移、下线、数据保留、突发账单 |
| 托管专实例 | 容量和隔离较可控 | 最低承诺、区域和平台绑定 | 扩缩容、空闲成本、故障切换 |
| 自托管 | 权重、网络和数据边界可控 | 硬件、推理栈、SRE 与安全责任 | 容量不足、依赖漏洞、权重来源、恢复 |
| 端侧 | 低网络依赖、数据可留本地 | 内存、功耗、热、模型大小和设备碎片 | 量化退化、升级覆盖、设备权限 |

选择方式前确认组织是否具备对应的值班、容量规划、安全和升级能力。

## 性能指标

### 单请求延迟

- **TTFT（Time to First Token）**：请求进入服务到首个输出 token，主要受排队、输入长度、prefill 和网络影响。
- **TPOT（Time per Output Token）**：首 token 后每个输出 token 的平均时间；也常记录 inter-token latency。
- **端到端延迟**：从业务请求开始到可用结果，包括检索、工具、重试、后处理和网络。

应报告 p50、p95、p99，而不是只报告平均值。流式界面重视 TTFT 和输出平滑度，批处理任务可能更重视总完成时间和吞吐。

### 吞吐与容量

- 输出 tokens/s、总 tokens/s、requests/s；
- 并发数、batch、输入和输出长度分布；
- 队列时间、超时率、限流率和失败重试；
- 持续负载、突发负载和单租户噪声；
- 质量与性能设置，例如量化、投机解码和最大批量。

吞吐和延迟存在排队与批处理权衡。必须在目标 SLO、真实长度分布和峰值并发下比较，不能拿单请求 tokens/s 代替系统容量。可参考 [MLPerf Inference](https://docs.mlcommons.org/inference/) 的场景化思想，以及 [NVIDIA NIM LLM 基准指标](https://docs.nvidia.com/nim/benchmarking/llm/latest/metrics.html) 对 TTFT、ITL/TPOT 与吞吐口径的拆分；后者也明确提醒不同工具的定义可能不同，因此仍须保存工具版本和完整配置。

## 显存与资源

### 权重

权重下界可粗略写为：

$$
M_{weights} \approx N_{parameters} \times \frac{bits}{8}
$$

实际还包括量化 scale/zero-point、未量化层、运行时 workspace、通信缓冲和框架开销。不能只用文件大小推断峰值显存。

### KV cache 与并发

KV cache 通常随层数、保留的 KV 头、head dimension、序列长度、并发和存储精度增长。对固定架构而言，它通常随序列长度近似线性增长；注意力计算复杂度和实现则是另一问题。

长上下文即使接口可接受，也可能因 prefill、KV cache 和队列压力破坏 SLO。应测多长度、多并发组合，并记录分页 KV、前缀复用、量化或卸载策略。

### MoE

激活参数描述一次 token 参与的部分计算，不代表只需加载这些权重。部署通常仍需容纳或分片总专家权重，并承担路由、通信和负载不均衡成本。比较 Dense 与 MoE 时同时报告总参数、激活参数、驻留内存、跨卡通信和实际吞吐。

## 缓存策略

| 缓存 | 收益 | 主要风险 |
|---|---|---|
| 前缀/提示缓存 | 降低重复 prefill 成本 | 租户隔离、版本变化、敏感前缀泄漏 |
| 响应缓存 | 避免重复生成 | 时效过期、个性化错误、权限混淆 |
| KV cache | 支持生成和连续批处理 | 显存压力、驱逐、跨请求隔离 |
| 检索缓存 | 降低向量检索和重排成本 | 知识更新后结果陈旧 |
| 工具结果缓存 | 减少外部调用 | 非幂等操作、动态数据和授权变化 |

记录命中率、节省量、失效条件、租户键、加密和删除路径。缓存带来的成本下降必须扣除存储、失效和错误陈旧结果的损失。

## 总拥有成本

### API

不要维护长期静态价格表。按区域和核验日期记录：

- 输入、输出、缓存读写和批处理；
- 推理/思考 token 与不同服务档；
- 搜索、代码执行、文件处理和其他工具；
- 向量存储、微调、专实例和数据传输；
- 重试、失败输出、长上下文阶梯和最低消费。

### 自托管

- GPU/加速器、CPU、内存、存储和网络；
- 集群空闲、峰值冗余、折旧、机房和能耗；
- 量化、推理框架、监控、升级和安全维护；
- 工程、SRE、值班、故障和容量不足造成的机会成本。

### 正确的分母

优先计算：

$$
Cost_{success} = \frac{服务成本 + 工具成本 + 重试成本 + 人工成本 + 失败损失}{成功且可接受的任务数}
$$

同时报告平均值和尾部分布。便宜但错误多、循环调用或需要大量人工修正的模型，单位成功任务成本可能更高。

## 数据、区域与服务条款

逐项确认并保存证据：

- 请求、响应、文件、日志和反馈存放在哪些区域；
- 是否用于服务改进或模型训练，能否退出；
- 默认和可配置保留期、删除机制、备份和审计日志；
- 跨境、子处理方、支持人员访问和加密边界；
- API、网页产品、企业产品和第三方代理的条款是否不同；
- 敏感数据进入搜索、工具或日志后是否跨越新的边界。

产品页面上的笼统隐私描述不能替代适用于具体账户、区域和接口的合同与配置验证。

## 版本、漂移与回滚

### 固定与检测

- API 优先使用 dated snapshot；只能使用别名时，记录返回元数据并运行定期金丝雀样本。
- 开放权重保存仓库 revision、文件哈希、tokenizer、配置、模板和推理镜像。
- prompt、RAG 索引、工具 schema、安全策略和后处理都纳入版本。

### 发布

先影子、再小比例灰度，比较质量、严重错误、延迟、成本和工具轨迹。设置自动停止阈值，避免只看总体用户指标。

### 回滚

保留最近一个已验证的完整组合，而不只是旧模型名。演练权重/API、prompt、索引、工具和缓存的一致回退，并验证数据格式是否向后兼容。

## 供应链与安全

### 开放权重与代码

- 从正式来源获取，验证 hash、签名或发布 provenance；
- 优先使用可审计的安全权重格式，谨慎加载可执行序列化文件；
- 审查 `trust_remote_code`、自定义算子、安装脚本和模型仓库代码；
- 固定依赖、容器和驱动，生成组件清单并跟踪漏洞；
- 在隔离环境中完成首次加载、转换和量化；
- 检查 tokenizer、聊天模板、适配器和量化文件是否来自同一身份。

### API 与外部工具

- 最小权限密钥、租户隔离、调用配额和异常账单限制；
- 对工具参数做服务端校验，不把模型输出当授权；
- 外部内容按不可信输入处理，防止提示注入和数据回传；
- 准备供应商中断、账户冻结、区域故障和模型下线的替代路径。

治理框架可参考 [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)；具体控制仍需按组织、行业和地区落实。

## 上线前的最后检查

- 是否在真实长度与峰值并发下测过 TTFT、TPOT、吞吐和成本尾部？
- 显存估算是否包含 KV cache、并发、workspace 和 MoE 总权重？
- 是否按每个成功任务计算 TCO，而不只看 token 单价？
- 缓存是否有租户隔离、时效失效和删除策略？
- 区域、数据保留、训练使用和子处理方是否有正式证据？
- 能否检测 API、权重、prompt、索引和工具漂移？
- 是否演练过版本回滚、能力降级和供应商中断？
- 权重、代码、镜像、SDK 和外部工具是否纳入供应链管理？

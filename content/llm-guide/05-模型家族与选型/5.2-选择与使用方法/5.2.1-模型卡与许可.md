# 模型卡与许可

模型卡用于说明预期用途、评测和限制，但不能代替权重许可、代码许可、数据条款或服务合同。审查时先解决身份，再讨论开放性和使用权。

## 模型、产品、API、权重和系统不是同一对象

| 对象 | 典型标识 | 能从中得出什么 | 不能自动推出什么 |
|---|---|---|---|
| 研究模型 | 论文中的模型名 | 研究设置、披露的架构和实验 | 当前仍有同名服务；论文参数适用于产品 |
| 模型家族 | 一代或一系列品牌名 | 版本关系和候选范围 | 任一成员的上下文、许可或能力 |
| 精确权重 | 仓库、文件、revision、hash | 可下载 artifact 的确定身份 | 训练数据开放、可商用或官方托管能力 |
| API 模型 | model ID、snapshot、区域 | 某端点在某日期的接口能力 | 同名聊天产品配置；别名永不漂移 |
| 产品模式 | 聊天、研究、代码或代理模式 | 用户实际获得的工具和交互 | 裸 API 或开放权重具有相同结果 |
| 完整系统 | 模型加 prompt、RAG、工具、策略 | 端到端任务行为 | 成绩可以归因于单一模型 |

评测、许可和部署记录必须使用最细可识别对象。API 别名若会指向新 snapshot，应记录请求返回的版本信息或建立行为漂移检测。

## 如何阅读模型卡与系统卡

建议按以下顺序核对：

1. **身份**：正式名称、模型 ID、发布日期、修订、参数精度和量化。
2. **训练阶段**：Base、预训练后续、Instruct、Chat、Thinking、奖励模型或蒸馏版本。
3. **输入输出**：语言、模态、上下文、最大输出、工具和接口限制。
4. **训练披露**：数据类型、截止日期、去重、合成数据、后训练和未披露项。
5. **评测设置**：数据版本、prompt、shot、采样、工具、推理预算和比较对象。
6. **预期用途**：支持、不建议、禁止或未经评估的用途。
7. **限制与安全**：已知失败、红队、偏差、隐私、网络安全和部署缓解。
8. **运行要求**：硬件、精度、模板、tokenizer、推理框架和依赖。
9. **许可与联系**：权利范围、附加条款、更新记录和问题报告渠道。

模型卡的组织思想可追溯到 [Model Cards for Model Reporting](https://arxiv.org/abs/1810.03993)。它是一种报告框架，不保证每张实际模型卡都完整或经过独立验证。

## 五层开放性矩阵

不要用“开源/闭源”一个词压缩所有 artifact。至少逐层记录：

| 层级 | 要核对的 artifact | 关键问题 | 开放后仍不代表 |
|---|---|---|---|
| 模型卡与报告 | 模型卡、系统卡、技术报告、评测记录 | 身份、用途、限制和设置是否可审计？ | 权重可获得；报告结论已独立复现 |
| 权重与检查点 | 最终权重、中间 checkpoint、tokenizer、配置 | 能否下载、校验、修改和再分发？ | 训练流程可复现；可无限制商用 |
| 代码与配方 | 训练、后训练、评测、推理代码和配置 | 版本、依赖、启动参数和日志是否完整？ | 数据可得；在另一硬件上得到相同结果 |
| 数据与处理 | 原始清单、快照、过滤、去重、混合和污染检查 | 数据能否获得、重建和审计？ | 数据没有版权、隐私、偏见或污染风险 |
| 许可证与治理 | 权重、代码、数据、文档的独立许可及使用政策 | 使用、修改、再分发、衍生、托管和输出有哪些条件？ | 法务已批准；不同 artifact 的许可彼此兼容 |

还可以记录日志、优化器状态、中间评测和失败实验，但它们不能替代上述五层。

## OLMo 作为开放性案例

AI2 的 OLMo 工作把开放目标从最终权重扩展到数据、训练代码、配置、日志和中间检查点，适合研究数据与训练过程对结果的影响。正式依据应回到 [OLMo 报告](https://arxiv.org/abs/2402.00838)、[Dolma 报告](https://arxiv.org/abs/2402.00159)及对应官方仓库。

这个案例说明“开放哪些 artifact”可以被精确列举，但不能据此宣传：

- 完全开放不等于某项能力最强或生产 SLO 更好；
- 不同版本的开放清单可能变化；
- 代码、权重和数据可能采用不同许可；
- 能下载不等于能在本组织的用途、地区和数据条件下使用。

因此应为具体版本填写五层矩阵，而不是只给家族贴“完全开放”标签。

## 许可证审查

### 分开记录

- 权重许可；
- 训练与推理代码许可；
- 数据集和数据处理产物许可；
- 文档、图片和报告许可；
- API 服务条款、可接受使用政策和数据处理条款。

### 核心问题

- 是否允许商业使用、修改、微调、量化、蒸馏、托管和再分发？
- 衍生权重、适配器和输出是否有附加条件？
- 是否有用途、用户规模、品牌、归属或地域限制？
- 数据、代码和权重许可能否组合？
- 上游训练数据或第三方组件的权利是否有未解决项？
- 条款更新、终止和版本固定机制是什么？

“Apache-2.0 代码仓库”不能证明模型权重也使用 Apache-2.0；“开放权重”也不能证明符合某个开源定义。需要分类时，应明确采用的定义和版本，例如 [Open Source AI Definition](https://opensource.org/ai/open-source-ai-definition)。重大商用决策由专业法务基于原始条款审查。

## 来源与变更记录

候选卡应保存：

- 官方模型页、模型卡、系统卡、仓库和许可的固定链接；
- 获取日期、文件 revision、commit 和权重哈希；
- 页面或条款变更前后的差异；
- 未披露、相互冲突或只能从二手来源获得的字段；
- 内部解释、法务结论及其适用范围。

# 9.1.4 加速器全景

> 第 9 章索引：[9 AI工程化与基础设施](../9-AI工程化与基础设施.md) · 邻居 [9.1](./9.1-硬件基础.md) · [9.1.2 内存层次](./9.1.2-GPU内存层次与Roofline.md) · [9.1.3 互联](./9.1.3-卡间互联与集群拓扑.md)

第 9.1–9.1.3 的公式、Roofline、NVLink 域，默认坐标系是 **NVIDIA GPU + CUDA + NCCL**。2026-08 的训练和推理并不只跑在这套坐标系上。本节是一张**能指向官方数据表的地图**：NVIDIA 代际用同一张表对齐单位；AMD / TPU / Gaudi / 昇腾各写能核对的一行。不是评测，不是购买建议，也不是把每家的微架构再讲一遍。

没打开产品页的规格一律不写。自媒体互相打架的「910C = xxx TFLOPS」不进表。

## 1. 问题：同一条 Roofline，坐标轴不是同一家的

算力强度 $I$ 和屋顶线 $P=\min(P_{\mathrm{peak}}, B\cdot I)$ 对任何加速器都成立，但：

- $P_{\mathrm{peak}}$ 的数据类型不同（FP16 Tensor Core、MXFP4、TPU 的 MXU、Gaudi 的 MME）。
- $B$ 有的是 HBM3e、有的是 HBM4、有的是片上 SRAM 很大、HBM 反而小（TPU v6e）。
- 「卡间高速公路」有的叫 NVLink，有的叫 Infinity Fabric，有的叫 ICI，有的把 RoCE 做到芯片上。

把 H100 的 900 GB/s NVLink 套到 MI350X 或 TPU7x 上，得到的是错的通信预算。下面按厂商列官方数字；跨行比较时先看脚注（稀疏/稠密、GB/GiB、是否含 CPU）。

## 2. NVIDIA：Hopper → Blackwell → Rubin

数字与 [9.1.2](./9.1.2-GPU内存层次与Roofline.md) 同一组数据表，避免两张表各写一套 HBM。更早的 Volta / Ampere 叙述仍在 [9.1 原文](./9.1-硬件基础.md)，本表不重抄 2025 的 A100 行。

| 产品 | 架构 | 每卡 HBM | 带宽 | 卡间 scale-up（每 GPU） | 来源 |
|------|------|----------|------|-------------------------|------|
| H100 SXM | Hopper | 80 GB HBM3 | 3.35 TB/s | NVLink 4：900 GB/s | [H100](https://www.nvidia.com/en-us/data-center/h100/)；[NVLink](https://www.nvidia.com/en-us/data-center/nvlink/) |
| H200 SXM | Hopper | 141 GB HBM3e | 4.80 TB/s | 同 Hopper NVLink 4 | [HGX AI Factory Components](https://docs.nvidia.com/enterprise-reference-architectures/hgx-ai-factory/latest/components.html) |
| B200 SXM | Blackwell | **180 GB** HBM3e | 最高 8 TB/s | NVLink 5：1,800 GB/s | HGX 表；[NVLink](https://www.nvidia.com/en-us/data-center/nvlink/) |
| B300 SXM | Blackwell Ultra | 288 GB HBM3e | 最高 8 TB/s | NVLink 5：1,800 GB/s | HGX 表 |
| Rubin GPU | Rubin | 最高 288 GB HBM4 | 最高 22 TB/s | NVLink 6：3,600 GB/s | [Rubin GPU 博文](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)；[NVLink](https://www.nvidia.com/en-us/data-center/nvlink/) |

机箱级：HGX/DGX 仍是 8 卡 NVLink 域；GB200 / GB300 / Vera Rubin **NVL72** 是 72 卡域，带宽见 [9.1.3](./9.1.3-卡间互联与集群拓扑.md)。B200 不要写成 192 GB——那是 9.1 原文里已勘误的口径。

软件栈：CUDA、cuBLAS / CUTLASS、NCCL、Triton、`torch.compile`。推理引擎见 [9.4](../9.4-推理服务框架/9.4-推理服务框架.md)（vLLM / SGLang / TensorRT-LLM）。

## 3. AMD Instinct：CDNA 与 Infinity Fabric

官方产品页，不经第三方「对标 H100」表：

| 产品 | 架构 | HBM | 带宽 | 板级功耗 | 卡间 | 来源 |
|------|------|-----|------|----------|------|------|
| MI300X | CDNA 3 | 192 GB HBM3 | 5.3 TB/s | TBP 750 W（峰值） | Infinity Fabric ×8，峰值链路带宽 128 GB/s | [MI300X](https://www.amd.com/en/products/accelerators/instinct/mi300/mi300x.html) |
| MI350X | CDNA 4 | 288 GB HBM3E | 8 TB/s | TBP 1000 W | Infinity Fabric ×7；scale-up 峰值链路 153 GB/s，scale-out 峰值链路 128 GB/s | [MI350X](https://www.amd.com/en/products/accelerators/instinct/mi350/mi350x.html) |

MI350X 页还给出 MXFP4 / MXFP6 矩阵峰值 9.2 PFLOPs、OCP-FP8 矩阵 4.6 PFLOPs（稀疏档另有一行，引用时要看清「with Structured Sparsity」）。PCIe 都是 Gen5 x16。软件栈是 **ROCm**，不是 CUDA；PyTorch 走 ROCm 构建，内核生态与 NVIDIA 不完全重叠。

读 Infinity Fabric 时不要直接当成 NVLink 5 的 1.8 TB/s：AMD 表给的是**单条链路**峰值，NVIDIA 产品页给的是**每 GPU 合计**。换算前先统一「每卡总双向带宽」；本篇不把未在产品页出现的「8 卡全连接合计」填进去。

## 4. Google TPU：Pod 与 ICI，不是 PCIe 插卡

Cloud TPU 的销售单位是 **slice / Pod**，不是「插一张卡进 PCIe 槽」。Google Cloud 文档把 Trillium 写成 **v6e**，把 Ironwood 家族的第一款写成 **TPU7x**。容量单位原文是 **GiB / GBps**，下表保持原文，不擅自改成 GB。

| | v6e（Trillium） | TPU7x（Ironwood） |
|--|-----------------|-------------------|
| 每芯片峰值 BF16 | 918 TFLOPs | 2307 TFLOPs |
| 每芯片峰值 FP8 | 918 TFLOPs | 4614 TFLOPs |
| 每芯片 HBM | 32 GiB | 192 GiB |
| 每芯片 HBM 带宽 | 1638 GBps | 7380 GBps |
| 每芯片双向 ICI | 800 GBps | 1200 GBps |
| 每 Pod 芯片数 | 256 | 9216 |
| 文档 | [TPU v6e](https://docs.cloud.google.com/tpu/docs/v6e)（配置表）；对照列在 [TPU7x](https://docs.cloud.google.com/tpu/docs/tpu7x) | [TPU7x](https://docs.cloud.google.com/tpu/docs/tpu7x) |

TPU7x 文档还写：芯片是双 chiplet，每 chiplet 96 GB HBM；JAX 把一颗芯片暴露成两个 device；片间是 3D torus，大于 64 芯片的 slice 由 4×4×4 cube 拼成。HBM 之外还有片上 **VMEM**（给 MXU 用的 SRAM scratchpad）——这是 TPU 内核优化的主战场，对应 NVIDIA 上的 shared memory，但编程模型是 Pallas / XLA，不是 CUDA block。

对 LLM 笔记的含义：Google 报告里的「TPU days」、ICI 拓扑、Megascale 一类叙述，不能翻译成「等效 N 张 H100」。软件入口是 JAX / PyTorch-XLA，不是 NCCL。

## 5. Intel Gaudi 3：板载以太网，不靠 NVLink

[HL-325L 产品简报](https://cdrdv2-public.intel.com/817487/gaudi-3-ai-accelerator-hl-325l-oam-mezzanine-card-product-brief.pdf)：OAM 夹层卡，5 nm，8 个 MME + 64 个 TPC，**128 GB HBM2E**，带宽 **3.7 TB/s**，片上 SRAM 96 MB，卡级 TDP 至 900 W，主机口 PCIe Gen 5.0 x16。

互联是这条线与 NVIDIA 分叉的地方：芯片集成 **24×200 GbE RoCE v2**，简报写成 9.6 Tb/s 双向。Scale-out 走标准以太网交换机，而不是 NVSwitch。软件是 Gaudi 图编译器 + TPC kernel，对接 PyTorch。

## 6. 华为昇腾：有超节点产品名，没有本篇能引用的单卡数据表

华为云官方技术文章把智算侧写成 **对等计算超节点 CloudMatrix**：算力、内存（EMS）、网络解耦池化；对 DeepSeek-R1 写「一卡一专家」的 MoE 切分，**单卡解码吞吐 1943 tokens/s**；同文提到伙伴在 **CloudMatrix 384** 超节点上的 Decode 吞吐数字（[华为云全栈服务架构与生态实践](https://www.huawei.com/cn/huaweitech/publication/202503/full-stack-service-architecture-ecology-huaweicloud)）。昇腾作为云服务品牌（昇腾云、MindSpore、ModelArts）在同文出现。

**本篇未打开**可核对的昇腾 910C 单卡 FLOPS / HBM 产品数据表（企业支持站返回 Access Denied；中文自媒体的 800 TFLOPS / 512 TFLOPS / 96 GB / 128 GB 互相矛盾）。因此：

- 可以写：国产加速器地图上有 **昇腾 + CloudMatrix 超节点**，软件栈是 CANN / MindSpore，不是 CUDA。
- **不准写**：910C 的 TFLOPS、HBM 容量、对标 H100 的百分比。那些数字标 `[OM-FREEPLAY]` 也不该填进表——连猜测都会被当成规格。

寒武纪 MLU、壁仞等：本会话未打开官方数据表，**不建行**。需要时下一轮补，不要用百科记忆占位。

## 7. 怎么用这张图读型号技术报告

读一份 2026 技术报告的 Infra 面时，先问四句：

1. 训练精度是 BF16 / FP8 / MXFP4 / NVFP4？峰值要查对那一列，不要拿 FP16 稠密去比 FP8 稀疏。
2. 并行宽度有没有超过该平台的 **scale-up 域**（8 卡 HGX、72 卡 NVL72、TPU cube、CloudMatrix 超节点）？超过了，all-to-all 就在付 scale-out 的税。
3. 优化器状态和 KV 住在 HBM 还是主机内存？TPU 文档明确写了 host offload；NVIDIA 侧对应 ZeRO / KV offload，见第 6 章。
4. 通信库是 NCCL、RCCL、XLA collective 还是 CANN HCCL？同名 AllReduce，实现和拓扑探测不是一份代码。

## 8. 失效条件

- **一行里混用稀疏峰值和稠密峰值。** NVIDIA 产品页大量 FLOPS 带 sparse 脚注；AMD 用 “Structured Sparsity” 单独一行。
- **把 TPU 的 GiB 改成 GB 再和 GPU 比 1%。** 文档单位不同，先抄原文。
- **用 NVLink GB/s 去除以 Infinity Fabric 单链路 GB/s，宣布谁更快。** 口径不同。
- **把 CloudMatrix 384 的 tokens/s 当成芯片规格。** 那是某次部署/伙伴数字，依赖模型、并行和调度。
- **假设非 NVIDIA 卡也能跑同一份 CUDA kernel / 同一份 FlashAttention 实现。** 算法可以移植，二进制不能。

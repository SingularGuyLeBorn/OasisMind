# 9.1.5 MoE 硬件与加速

GPU 集群上的 MoE 优化, 默认硬件是固定的: 显存, NVLink, IB 都已经在那里, 能改的是并行组合, 通信调度和 kernel, 这些在 [6.1.8 MoE 系统与并行](../../../6-训练与推理优化/6.1-训练基础设施/6.1.8-MoE系统与并行/6.1.8-MoE系统与并行.md). 本节换一个出发点: 如果可以为 MoE 设计数据流, 片上缓冲和存储层级, 硬件应该长什么样. 收的是 FPGA 加速器, 边缘端加速器, GPU 加近存计算 (NDP), 以及 NPU 加存内计算 (PIM) 这几类研究原型.

这些工作多数针对 Vision Transformer 上的 MoE 或中小规模模型, 规模比数据中心里的 LLM 小得多, 但它们暴露的问题和 LLM 推理一样: 专家权重总量大, 每一步只用到一小部分, 用到哪一部分事先不知道. 读这一节的收获在于看清 MoE 层在硬件上的瓶颈到底是什么, 以及几种设计各自把赌注压在哪里.

## 1. 动态路由碰上固定数据流

### 1.1 三件稠密模型没有的事

[04](./04-MoE硬件架构研究综述/04-MoE硬件架构研究综述.md) 把动态性带来的问题归成三件. 第一, 计算不可预测: 这个 batch 激活的专家集合和下一个 batch 不同, 按固定顺序排好的流水线会有一部分单元空转. 第二, 通信模式随路由变化: token 的目的地是门控输出, 不是固定的网格拓扑. 第三, 权重放哪里: 把全部专家权重放进片上或 HBM, 和只加载被点亮的专家, 是两套完全不同的存储设计.

训练侧的负载均衡损失和无辅助损失偏置, 能把专家被选中的分布拧得平一些, 但拧不到每一步都均匀. 硬件仍然要能消化剩下的不均: 某个专家这一步分到很多 token, 另一个一个也没有, 变长的 grouped GEMM 和溢出的 token 都要有地方处理. 04 第 4 节的判断是, 算法侧把专家切细, 加共享专家, 加负载损失, 硬件侧提供稀疏单元, 更大的片上缓冲和能吃动态 All-to-All 的互联, 缺任何一边, 纸面上的稀疏度都兑现不了.

### 1.2 MoE 层的运算强度

动态性之外, 还有一个更根本的问题: 推理时 MoE 层的运算强度很低. 运算强度 $I$ 是一个 kernel 的浮点运算次数除以从慢存储读入的字节数, 定义和 ridge point 在 [9.1.2 GPU 内存层次与 Roofline](../9.1.2-GPU内存层次与Roofline.md). 一个 SwiGLU 专家有三个 $d\times d_{\mathrm{ff}}$ 的矩阵, 一步分到 $t$ 个 token 时, 计算约 $2\cdot t\cdot 3d\,d_{\mathrm{ff}}$ 次浮点运算, 权重读入约 $3d\,d_{\mathrm{ff}}\cdot b$ 字节 ($b$ 是每个权重的字节数). 两者相除, 激活的读写相对权重可以忽略时,

$$
I\approx\frac{2t}{b},
$$

BF16 下 $b=2$, $I\approx t$ FLOP/Byte. 9.1.2 算出 H100 FP16 稠密的 ridge point 约 295 FLOP/Byte, 也就是一个专家一步要分到约 300 个 token 才能离开带宽墙. 取 Decode 的 batch 64, 每 token 激活 8 个专家, 一层共 256 个专家, 平均每个专家一步只分到 $64\times8/256=2$ 个 token, $I$ 约为 2, 比 ridge point 低两个数量级. 这时决定延迟的是把专家权重从存储搬到计算单元的速度, 加算力没有用.

这个数量级解释了本节几类设计的共同方向. 既然 MoE 层在推理时受带宽限制, 就要么少搬权重 (剪枝, 压缩, 只搬会用到的专家), 要么把计算挪到权重旁边 (近存计算, 存内计算). 注意力层的情况不同, 它在 Prefill 时运算强度高得多, 所以 Duplex 一类设计把两种层分给两种硬件.

## 2. 两篇文章与六个个案

### 2.1 04 讲架构, 06 讲个案

04 和 [06](./06-MoE硬件加速架构综述/06-MoE硬件加速架构综述.md) 分工明确. 04 在架构层讨论系统怎样适配动态性: 宏观上以 UbiMoE 为例, 看一个 FPGA 设计怎样把注意力和专家拆成两套核; 微观上把计算, 访存, 互联三个面各自在做什么列成一张表, 并写清每一面「不是什么」, 例如专家侧的 All-to-All 不是注意力 TP 的 AllReduce, 冷热专家分离不是 MLA 对 KV 的压缩.

06 把具体加速器排成个案: FPGA 上的 UbiMoE 和 FLAME, 边缘端的 Edge-MoE, 近存计算的 MoNDE, Duplex 和 PIMoE, 最后给一张对比表和三条趋势 (专家预测, 近存计算, 稀疏与硬件协同). 两篇的引用有重叠, UbiMoE 两边都出现, 04 写它的设计意图, 06 写它的组件. 读的顺序是先 04 后 06.

### 2.2 个案对照

| 工作 | 平台 | 处理瓶颈的方式 | 押注的前提 |
|---|---|---|---|
| UbiMoE | FPGA | 流式注意力核加可复用线性核, 按资源搜参数 | 两类层的计算模式可以分开优化 |
| FLAME | FPGA | N:M 剪枝减权重, CEPR 预测专家激活 | 专家激活有明显冷热, 可以预测 |
| Edge-MoE | 边缘设备 | 任务级门控, patch 重排, 近似 Softmax 与 GELU | 多任务视觉场景, 功耗受限 |
| MoNDE | GPU 加 NDP | 热专家在 GPU, 冷专家在 NDP, 传激活不传权重 | 冷专家多, 激活比权重小 |
| Duplex | xPU 加 Logic-PIM | 注意力用 xPU, MoE 层用 Logic-PIM | 两种层的运算强度差别大 |
| PIMoE | NPU 加 PIM | 节流感知卸载, 去零压缩 | PIM 与 NPU 之间可以动态分配专家 |

最后一列是这张表要看的地方. 六个设计都没有改路由, 它们押注的是 MoE 在某种场景下的统计规律: 冷热分明, 激活可预测, 不同层运算强度不同. 规律成立时收益明显; 规律不成立时, 例如路由在不同输入间很分散, 专家预测的命中率下降, 预加载就会变成多搬了一次.

## 3. 三条路线的取舍

### 3.1 预测与预加载

FLAME 的循环预测机制 CEPR 用上一个输出 token 的末几层信息, 预测下一个 token 的前几层会激活哪些专家, 依据是它观察到专家激活路径高度集中. 预测对了, 权重可以在用到之前就搬好; 预测错了, 要么停下来等, 要么多搬了不需要的专家. 06 第 5 节把专家预测列为第一条趋势.

GPU 上的卸载面对同一个问题. [6.1.8 的主文](../../../6-训练与推理优化/6.1-训练基础设施/6.1.8-MoE系统与并行/08-MoE系统优化综述/08-MoE系统优化综述.md) 按 PCIe 5.0 ×16 约 64 GB/s 估算, 200 MB 的专家权重单次搬运约 3 ms, 而同尺寸的 BF16 GEMM 在 H100 上往往不到 1 ms, 所以卸载能不能成立, 取决于预取能否把这次拷贝藏进上一层的计算. FPGA 上的预测和 GPU 上的预取是同一个思路, 差别只在搬运的两端是什么存储.

### 3.2 把计算挪到权重旁边

近存计算换了一个方向: 不把权重搬到计算单元, 而是把激活送到存权重的地方. MoNDE 把冷专家放在 NDP 设备上, 只传激活值, 理由是 1.2 节那个数量级: 一个专家一步只处理几个 token 时, 这几个 token 的激活远小于专家权重. Duplex 和 PIMoE 进一步把计算放进存储内部 (PIM), Duplex 按层的运算强度分工, PIMoE 在 NPU 和 PIM 之间迭代地重分配耗时最长的专家, 并在 DRAM 到 NPU 的通路上滤掉零权重.

这条路线的代价在于 PIM 和 NDP 的计算能力有限, 只适合运算强度低的部分. 一旦 batch 变大, 每个专家分到的 token 多到接近 ridge point, 计算又回到算力受限, 放在存储旁边的弱计算单元反而成了瓶颈. 这也是 Duplex 不把所有层都放进 PIM 的原因: 高运算强度的注意力层仍然留给 xPU.

## 4. 读法与边界

### 4.1 按背景进入

做芯片或 FPGA 的读者, 先读 04 的三面表, 再读 06 的个案, 重点看每个设计押注的前提在 LLM 推理里是否仍成立: 视觉 MoE 的专家数和 token 数都和 LLM 不同, 冷热分布也不能直接搬过来. 做 GPU 推理系统的读者, 建议先回 [9.1.2](../9.1.2-GPU内存层次与Roofline.md) 把 ridge point 和带宽墙的算法弄清楚, 再读 1.2 节的运算强度估算, 然后看 06 的近存计算部分, 它解释了为什么 Decode 阶段的 MoE 层总是受带宽限制.

只想知道 MoE 在硬件上难在哪里的读者, 读本页第 1 节和 04 就够了. 06 里的组件描述 (Softmax 近似模块, GELU 近似模块, patch 重排) 是具体实现细节, 不做硬件的可以跳过.

### 4.2 与相邻章节的分工

路由, 共享专家和细粒度专家的公式不在本节, 见 [2.4.1 MoE 总览](../../../2-核心原理与架构/2.4-前沿架构与变体/2.4.1-混合专家模型MoE/2.4.1-混合专家模型MoE.md) 和 [DeepSeek-MoE](../../../2-核心原理与架构/2.4-前沿架构与变体/2.4.1-混合专家模型MoE/01-DeepSeek-MoE/01-DeepSeek-MoE.md). MLA 压缩的是 KV 的表示, 和 MoE 硬件是两件事, 不要把它的显存收益算进 MoE 加速比. GPU 集群上的专家并行, All-to-All 和 Grouped GEMM 在 [6.1.8](../../../6-训练与推理优化/6.1-训练基础设施/6.1.8-MoE系统与并行/6.1.8-MoE系统与并行.md).

非 NVIDIA 的通用加速器 (TPU, 昇腾等) 在 [9.1.4 加速器全景](../9.1.4-加速器全景.md), 卡间互联在 [9.1.3](../9.1.3-卡间互联与集群拓扑.md). 本节的研究原型多数没有进入量产芯片, 它们的价值在于把 MoE 的瓶颈拆清楚: 带宽, 预测, 冷热, 这三个量在任何硬件上都要面对.

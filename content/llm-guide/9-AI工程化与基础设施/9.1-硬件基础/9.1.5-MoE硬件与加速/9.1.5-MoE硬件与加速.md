# 9.1.5 MoE 硬件与加速

GPU 集群上的 MoE 优化默认硬件是固定的: 显存, NVLink, IB 都已经在那里, 能改的是并行组合, 通信调度和 kernel, 这些在 [6.1.8 MoE 系统与并行](../../../6-训练与推理优化/6.1-训练基础设施/6.1.8-MoE系统与并行/6.1.8-MoE系统与并行.md). 本节换一个出发点: 如果可以为 MoE 设计数据流, 片上缓冲和存储层级, 或者把计算放到存权重的地方, 硬件应该怎样做. 涉及的是 FPGA 加速器, CPU 或 CXL 内存上的近数据计算 (NDP), 以及 HBM logic die 或 NPU 系统中的存内计算 (PIM).

这些工作多数是研究原型, 有些针对视觉 Transformer 上的 MoE, 规模比数据中心的 LLM 小得多. 它们处理的问题和 LLM 推理相同: 专家权重总量大, 每一步只用到一小部分, 用到哪一部分事先不知道, 而且用到的那部分计算量相对于要读的字节数很小. 本节只有一篇正文 [01 MoE 专用硬件](./01-MoE硬件架构研究综述/01-MoE硬件架构研究综述.md), 首页定义它和相邻章节共用的几个量, 并说明各章怎样分工.

## 1. 共用的量与三条路线

### 1.1 运算强度与搬运比

运算强度 $I$ 是一个 kernel 的浮点运算次数除以从慢存储读入的字节数, 定义和 ridge point 见 [9.1.2 GPU 内存层次与 Roofline](../9.1.2-GPU内存层次与Roofline/9.1.2-GPU内存层次与Roofline.md). 对一个 SwiGLU 专家, 记 $t$ 为它这一步分到的 token 数, $b$ 为每个权重的字节数, 激活读写相对权重可以忽略时 $I\approx2t/b$. BF16 下 $I\approx t$, 而 H100 FP16 稠密计算的 ridge point 约 295 FLOP/Byte. DeepSeek-V3 在 batch 64 的 decode 中平均每个专家分到 2 个 token, 比 ridge point 低两个数量级, 延迟由读权重的速度决定.

第二个量是搬权重与搬激活之比. 专家权重不在计算单元旁边时, 要么把权重搬过来 (参数移动), 要么把激活送过去就地计算 (激活移动). 对 SwiGLU 专家, 两者之比为 $\frac{3H}{2t}\cdot\frac{b}{b_a}$, $H$ 是专家中间维度, $b_a$ 是激活的字节数. Mixtral 的专家在 BF16 下比值约为 $21504/t$, decode 时 $t$ 是个位数到几十, 搬激活便宜得多. 注意力层在 decode 时也受带宽限制, 但原因不同. GQA 中每个 KV 元素读入一次, 被组内 $g$ 个 query 头共用, BF16 下运算强度约为 $g$, 常见取值 4 到 8, 由模型结构决定, 不随 batch 变化; MoE 层的运算强度则随每个专家分到的 token 数, 每一步都在变. 两类层都低于 GPU 的 ridge point, 又彼此不同, 这是存内计算方案把它们分开处理的依据.

这几个量在 01 中推导, 也是 [6.3.1/05 MoE 量化](../../../6-训练与推理优化/6.3-模型压缩/6.3.1-量化/05-MoE模型量化技术综述/05-MoE模型量化技术综述.md) 第 1.2 节讨论位宽分配时用到的同一组记号.

### 1.2 三条路线

从这两个量出发, 硬件上的做法分三条路线. 第一条是少搬: FPGA 片上容量不够时, 按专家重排计算让每个专家的权重一步只读一次 (Edge-MoE), 对专家权重剪枝, 或者在路由确定之前预取 (FLAME). 第二条是搬激活: 冷门专家留在 CPU 内存或 CXL 内存设备里就地计算, 热门专家才搬到 GPU (MoNDE, Fiddler). 第三条是在存储内部计算: 把计算单元放进 HBM 的 logic die 或与 NPU 配合的 PIM 中, 按运算强度在强计算单元和存储侧计算单元之间分工 (Duplex, PIMoE).

| 路线 | 改变的量 | 代表工作 | 前提 |
|---|---|---|---|
| 少搬 | 读入的字节数 | Edge-MoE, UbiMoE, FLAME | 专家多于片上容量, 激活可预测 |
| 搬激活 | 搬运对象 | MoNDE, Fiddler | 冷门专家分到的 token 少 |
| 存内计算 | 带宽所在的位置 | Duplex, PIMoE | 不同专家和层的运算强度差别大 |

三条路线都不改 $I\approx2t/b$ 本身, 改的是分母落在哪种带宽上, 或者读多少次. 它们的前提都依赖路由的统计性质: 激活偏斜, 冷热分明, 可以预测. 训练时负载均衡做得越好, 冷热差别越小; batch 越大, $t$ 越接近 ridge point, 存储侧弱计算单元的优势也越小. 01 第 4.3 节把这些失效条件逐条列出.

## 2. 正文结构与相邻章节

### 2.1 01 的结构

01 先在第 1 节推导两个量: 运算强度说明 decode 时专家计算受带宽限制, 搬运比说明卸载推理里该搬激活还是搬权重, 并用 Mixtral 和 DeepSeek-V3 的数字估算 PCIe 搬运的代价. 第 2 节是三个 FPGA 设计: Edge-MoE 的逐专家重排与逐项消融, UbiMoE 的两套核与参数搜索, FLAME 的剪枝与预取. 第 3 节是近数据计算和存内计算: MoNDE 的负载均衡公式, Fiddler 在普通 CPU 上的同类选择, Duplex 的 Logic-PIM, PIMoE 的任务卸载.

第 4 节回到所有设计共有的前提. 专家预测一节对比了两种做法: FLAME 按运行时统计预测, 不改模型; Pre-gated MoE 训练一个替下一块选专家的门控, 消除了预测错误, 代价是需要微调. 之后是一张设计对照表和失效条件, 包括 batch 变大, 负载过于均衡, 从视觉模型外推到 LLM 三种情形. 读完第 1 节就能判断一个新设计押的是哪个量, 第 2, 3 节是具体实现.

### 2.2 与量化和系统章节的分工

硬件和量化处理的是同一个瓶颈. 降低权重位宽就是减小 $b$, 4 bit 下运算强度提高 4 倍, 搬运比也缩小 4 倍, 但 decode 时 $t$ 仍远低于分界点, 所以量化之后专家计算依然受带宽限制. 量化怎样处理冷门专家的校准, 怎样给不同专家分配位宽, 在 [6.3.1/05](../../../6-训练与推理优化/6.3-模型压缩/6.3.1-量化/05-MoE模型量化技术综述/05-MoE模型量化技术综述.md); 其中 MxMoE 按 roofline 给专家选格式, 用的就是本节的运算强度.

GPU 集群上的专家并行, All-to-All, Grouped GEMM 与卸载调度在 [6.1.8](../../../6-训练与推理优化/6.1-训练基础设施/6.1.8-MoE系统与并行/6.1.8-MoE系统与并行.md). 那里的卸载和本节的近数据计算面对同一个 PCIe 瓶颈, 差别在于 6.1.8 假设硬件固定, 靠预取把拷贝藏进计算; 本节允许在存储侧加计算单元, 让冷门专家根本不必经过 PCIe. 路由, 共享专家和细粒度专家的公式在 [2.6 MoE 总览](../../../2-核心原理与架构/2.6-MoE/2.6-MoE.md) 和 [DeepSeek-MoE](../../../2-核心原理与架构/2.6-MoE/01-DeepSeek-MoE/01-DeepSeek-MoE.md).

## 3. 读法与边界

### 3.1 按背景进入

做芯片或 FPGA 的读者, 先读 01 第 1 节确认瓶颈, 再读第 2, 3 节的个案, 重点看第 4.3 节: 视觉 MoE 的专家数只有十几个, 输入是固定数量的 patch, LLM 的专家数和 token 数都不同, 冷热分布和预测准确率不能直接搬用. 做 GPU 推理系统的读者, 建议先回 [9.1.2](../9.1.2-GPU内存层次与Roofline/9.1.2-GPU内存层次与Roofline.md) 熟悉 ridge point 的算法, 再读 01 第 1.2, 1.3 节和第 3.2 节的 Fiddler, 它不需要新硬件, 可以直接用在现有机器上.

只想知道 MoE 在硬件上难在哪里的读者, 读本页第 1 节和 01 第 1 节就够了. 01 第 2 节里的组件细节 (Softmax 近似, GELU 近似, 注意力重排) 是 FPGA 实现层面的内容, 不做硬件可以跳过; 第 4.1 节的专家预测则对 GPU 上的卸载推理同样适用.

### 3.2 边界

MLA 压缩的是 KV 的表示, 与 MoE 硬件是两件事, 不要把它的显存收益算进 MoE 加速比. 非 NVIDIA 的通用加速器 (TPU, 昇腾等) 在 [9.1.4 加速器全景](../9.1.4-加速器全景/9.1.4-加速器全景.md), 卡间互联在 [9.1.3](../9.1.3-卡间互联与集群拓扑/9.1.3-卡间互联与集群拓扑.md).

本节的研究原型多数没有进入量产芯片. 论文中的加速比都有各自的基线: Edge-MoE 和 UbiMoE 比的是 CPU, GPU 和此前的 FPGA 设计; MoNDE 比的是把所有激活专家搬到 GPU 的做法; Duplex 比的是同代 GPU 系统. 引用这些数字时要连同基线和模型规模一起看.

能从这些原型中带走的是瓶颈分析的方法: 先用 $t$ 和 $b$ 算出专家计算离 ridge point 有多远, 再用搬运比判断该搬权重还是搬激活, 最后检查设计依赖的路由统计在目标模型上是否成立. 换成新的模型或新的硬件, 这三步照样适用, 而具体的加速比需要在目标负载上重新测量.

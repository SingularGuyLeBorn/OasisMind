## 1. 共置为什么同时伤 TTFT 和 TPOT

一次请求拆成两段，延迟也拆成两个 SLO：

| 阶段 | 算什么 | 硬件瓶颈 | 产品指标 |
|------|--------|----------|----------|
| **Prefill** | 整段 prompt 一次前向，写出整条 KV | 不算太短的 prompt 上接近 **compute-bound** | TTFT（首 token） |
| **Decode** | 每步一个新 token，反复读历史 KV + 权重 | **memory-bound**（HBM 带宽 + KV 容量） | TPOT / ITL（后续每个 token） |

共置（colocate）把两段放进同一引擎、同一批：continuous batching 会把新来的 prefill 跟正在走的 decode 拼在一个 iteration 里。DistServe（OSDI 24，[arXiv:2401.09670](https://arxiv.org/html/2401.09670)）把后果写成两条，不是「调度再聪明一点就好」：

1. **相位互扰。** 一次 prefill 往往比一步 decode 长得多。拼进同一 batch 后，decode 要等 prefill 跑完，TPOT 被拉长；decode 也反过来拖 TTFT。论文 Figure 2：13B 模型上，decode-only batch 再加 **一条** prefill，两边执行时间一起涨，prompt 越长越狠。
2. **资源和并行被耦死。** Prefill 更吃 intra-op（把单次执行时间压下去才能过紧 TTFT）；decode 的最优并行跟当时 batch 有关。共置只能按「更严的那条 SLO」配卡，另一条要么不达标，要么靠超配 GPU。

Chunked-prefill + piggyback（把长 prefill 切块、跟 decode 拼）**减轻**打断，**消不掉**。论文还写了访存惩罚：切成 $N$ 等块时，后续块都要反复把前面块的 KV 从 HBM 载回 SRAM，总加载量 $N+(N-1)+\cdots+1=O(N^2)$，相对不切块的 $O(N)$。上下文越长，这块越贵。这不是第 6 章的 kernel 细节，是**调度策略自己制造的平方访存**。

**Goodput。** DistServe 优化的不是「整机每秒吐多少 token」，而是：**在给定 TTFT/TPOT SLO、且达标率（例如 90%）下，每张 GPU 能吃的最大请求率**。token/s 可以把短请求刷很高，同时让长请求的 TPOT 爆掉——对聊天产品那叫假吞吐。

论文 Figure 1 的合成负载（13B、A100 80GB、输入 512 / 输出 64）：共置大约 **1.6 rps/GPU**。理想 2 张 prefill + 1 张 decode → 整体 10 rps，折合 **3.3 rps/GPU（2.1×）**。跨模型、跨应用、跨 SLO 的评测上限：**7.4×** 请求，或 **12.6×** 更紧的 SLO，且 $>90\%$ 请求仍达标。不要把 7.4× 写成「随便一台机器开 PD 就 7 倍」——那是论文评测包络。

## 2. 拆开之后：排队公式与 KV 过网

拆开以后，prefill 实例近似 **M/D/1**（论文假设均匀 prompt、泊松到达、一张卡一次吃饱就不扩 batch）。单卡无并行时：

$$
\mathrm{Avg\_TTFT}=D+\frac{RD^{2}}{2(1-RD)},\qquad RD<1 \tag{1}
$$

$D$ 是一次 prefill 执行时间，$R$ 是到达率。第一项执行，第二项排队。

两路 **inter-op**（流水线切层）时，论文取 $D_s\approx D$、$D_m\approx D/2$，得到：

$$
\mathrm{Avg\_TTFT_{inter}}=D+\frac{RD^{2}}{4(2-RD)} \tag{2}
$$

两路 **intra-op**（算子切卡）引入加速比 $K$（$1<K<2$，通信让 $K$ 到不了 2）：

$$
\mathrm{Avg\_TTFT_{intra}}=\frac{D}{K}+\frac{RD^{2}}{2K(K-RD)} \tag{3}
$$

低到达率时第一项主导 → intra-op 更有利于紧 TTFT；到达率升高后排队项主导 → inter-op 更好。这就是「拆开才能给两阶段配不同并行」的解析版本。真实负载 prompt 长度不齐，inter-op 会出 pipeline bubble，论文用仿真搜配置，不要把 (1)–(3) 当生产计算器。

**KV 通信。** 拆开必须把 prefill 写出的 KV 送到 decode 实例。DistServe §3.3：OPT-66B、单条 512 token 的 KV 大约 **1.13 GB**。若平均 10 rps，要搬 **11.3 GB/s ≈ 90 Gbps** 才谈得上「通信看不见」。论文对照：集群 IB（文中举 800 Gbps）或节点内 NVLink（A100 峰值 600 GB/s）可以把这段开销压到可忽略；跨节点带宽不够时，放置算法必须把 P/D 对钉在同一节点（Algorithm 2）。互联规格本体在 [9.1.3](../9.1-硬件基础/9.1.3-卡间互联与集群拓扑.md)，本篇不重抄代际表。

13B、512 token 的 prefill 在论文里已经接近打满一张 A100 的 compute-bound（§2.1 / §3.1）。过了这个临界长度 $L_m$，prefill 再加 batch 几乎只加延迟、不加效率——所以 prefill 池的 batch 往往很小。Decode 相反：单条 decode 带宽浪费，拆开以后可以用 **多份 prefill 实例喂一份 decode 实例**，把 decode batch 做大而不跟 TTFT 抢同一块 GPU。

## 3. SGLang：先当运行时，再当 PD 编排

SGLang 论文（[arXiv:2312.07104](https://arxiv.org/html/2312.07104)）的主语不是 PD，是 **LM Program**：多轮生成调用、控制流、结构化输入输出。前端是嵌在 Python 里的 DSL（`gen` / `select` / `fork` / `join` / 正则约束）；后端运行时两件优化：

**RadixAttention。** 请求结束后 **不丢** KV，用基数树（边可以挂一整段 token）做前缀匹配、插入、淘汰。叶子 LRU；正在跑的节点用引用计数钉住，不能赶出去。树在 CPU 上维护。缓存命中率定义为

$$
\frac{\text{命中的 prompt token 数}}{\text{prompt token 总数}}
$$

等待队列里按「已匹配前缀更长优先」近似 DFS，离线 batch 在缓存容量 $\ge$ 最长请求时，DFS 遍历能拿到最优命中（论文 Theorem 3.1）。在线会被打乱，但仍朝这棵树上的 DFS 靠。分页 KV 的块管理仍是 PagedAttention 那一套，公式在 [6.4.1](../../6-训练与推理优化/6.4-KV缓存与内存优化/6.4.1-PagedAttention原理/6.4.1-PagedAttention原理.md)，本篇不重推。

**压缩 FSM。** JSON / 正则约束下，现有引擎往往每步只 mask 下一个 token；SGLang 把可合并的多 token 路径压成一步。这是结构化解码，不是注意力变体。

论文评测包（Llama-7B/70B、Mixtral-8x7B、LLaVA 等，A10G/A100）相对当时的 Guidance / vLLM / LMQL，吞吐最高 **6.4×**。任务面包括 agent、逻辑、few-shot、JSON、RAG、多轮。这是 **2023–2024 对照集**。2026 的 vLLM 已经有 automatic prefix caching；不要把 6.4× 读成「今天的 vLLM 仍然不会复用前缀」。

[6.6](../../6-训练与推理优化/6.6-推理框架与高级优化/6.6-推理框架与高级优化.md) §6.4 的 2025 段把 SGLang 写成「相对较新、生态不如 vLLM」。那句话留着当历史快照。2026-08 生产里它已经和 vLLM 并列：Qwen3.8-Flash-Next 的 Hugging Face 卡把两者都写成推荐 serving 引擎。HF 推荐 ≠ 基准涨点。

## 4. SGLang 文档里的 PD：进程、传输、异构 TP

官方页：[PD Disaggregation](https://docs.sglang.ai/advanced_features/pd_disaggregation.html)。统一引擎的两个问题与 DistServe 同构：

1. 新 prefill batch **打断** 正在 decode 的 batch。
2. **DP attention** 上，一个 worker 在 prefill、另一个在 decode，decode 延迟被拖高。

落地不是「同一进程里两个线程」，而是两类 `launch_server`：

| 角色 | 文档开关 | 干什么 |
|------|----------|--------|
| Prefill worker | `--disaggregation-mode prefill` | 只做 prompt 前向，把 KV 交给传输层 |
| Decode worker | `--disaggregation-mode decode` | 收 KV，自回归 |
| Router | `sglang_router.launch_router --pd-disaggregation` | 在 P/D 实例之间分发；负载与容错走网关，不在本篇展开 |

传输后端文档点名两个：**Mooncake**（`mooncake-transfer-engine`）和 **NIXL**（`--disaggregation-transfer-backend nixl`，默认 UCX，可用 `SGLANG_DISAGGREGATION_NIXL_BACKEND` 换成 LIBFABRIC 等已装插件）。昇腾另有 memfabric / Mooncake 开关。Mooncake 是 KV 搬运引擎，**不是** DistServe 那篇 OSDI 论文的别名；本篇没有打开 Mooncake 自己的论文，不编它的延迟表。

**NVLink。** 文档给的是环境变量，不是又一种注意力：

- NVL72：`SGLANG_MOONCAKE_CUSTOM_MEM_POOL=NVLINK` 且 `MC_FORCE_MNNVL=True`（辅助数据仍走 TCP，文档写明是临时 workaround）。
- 节点内 NVLink（文中点名 A100 / H20 / H100）：`INTRA_NODE_NVLINK` + `MC_INTRANODE_NVLINK=true`。

这与 [9.1.3](../9.1-硬件基础/9.1.3-卡间互联与集群拓扑.md) 的域划分一致：域内 NVLink，跨节点才轮到 IB/NIXL。

**异构 TP + GPU staging buffer。** Prefill 与 decode 的 TP 可以不同（例：prefill TP=4，decode 侧 DP attention 有效注意力 TP=1）。KV 的头切片布局两边对不上。文档做法：prefill 侧 gather 成连续 staging → 整段 RDMA → decode 侧 scatter 进分页 KV。相对默认「按 token 切片传」，高并发吞吐 **2–5×**；相对**同构 TP** 基线差约 **5%**。同构 TP 时即使打开开关也会自动旁路。

**失效条件（文档原句级）：** staging 面向 GQA/MHA 这类非 MLA；**DeepSeek-V2/V3 的 MLA 不要开这个 flag**。不要把「异构 TP 的 2–5×」写成 MLA 模型的数字。

超时类变量（bootstrap 300s、decode 等 KV 300s、心跳 5s / 连续失败 2 次标 prefill 下线）是运维旋钮。文档允许放到 600s 换更长平均 TTFT，以及 decode 掉线时 prefill 更慢回收显存。本篇不把默认秒数当成 SLO。

昇腾示例命令里出现 `--disable-radix-cache`。这说明 **PD 与 Radix 不是自动绑死**；某条集群配方会关掉前缀树。没在本页读到「decode 侧只传 delta KV」的完整开关说明，就不写进正文。

## 5. EPD 是 PD 加上视觉塔，不是第四种注意力

原生多模态多一段 **Encode**（视觉/音频塔）。GLM-5.3-Flash 官方文档把生产栈写成三分 worker 池：Encode / Prefill / Decode，跑在国产芯片上的 SGLang 定制引擎里（https://docs.z.ai/guides/vlm/glm-5.3-flash）。同页还有相对同硬件初值 **3×** 的端到端 serving——不要和该模型注意力算力的 3.01× 收成同一个「三倍」。芯片型号与单卡 FLOPS **本篇未找到**。捆法细节在 [GLM-5.3-Flash 正本](../../05-模型家族与选型/5.3-模型家族/glm/glm-5-3-flash/glm-5-3-flash.md)，这里只钉「PD 的多模态延拓」。

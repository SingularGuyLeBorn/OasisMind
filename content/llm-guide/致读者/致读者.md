# 致读者：如何使用这套知识库

你好，朋友。

如果你曾经在几十篇论文、产品文档和报错页面之间来回切换，最后只记住一堆彼此矛盾的结论，那么我们大概是同路人。这套知识库想解决的不是“再收集一些链接”，而是把大模型领域的概念、证据、实现和失效边界组织成一条可以反复核对的学习路径。

![一位学习者沿着知识道路走向由传统建筑与未来城市共同构成的远方](./images/image_0.png)

## 这套知识库是什么

它是一份持续维护的技术教材，也是一张研究与工程地图：

- 原理章节解释公式、假设、复杂度与反例；
- 训练章节连接数据、目标函数、优化、稳定性和评测；
- 模型章节区分论文身份、产品名、API 型号和开放权重；
- 应用与工程章节讨论 RAG、Agent、多模态、推理系统和基础设施；
- 评测、安全与治理章节负责限定结论能支持什么、不能支持什么。

它不是某家产品的使用手册，也不把榜单名次、营销文案或一次演示当成普遍事实。对快速变化的 API、价格、上下文窗口、地区可用性和法规，正文会标注核验日期；真正部署前仍应回到当天的官方文档。

## 如何读

第一次进入时，先从导论建立全局地图，再根据目标选择主线：

- **研究主线**：核心原理 → 预训练 → 后训练 → 模型报告与前沿论文；
- **训练与系统主线**：预训练/后训练 → 训练推理优化 → 工程化与基础设施；
- **应用主线**：模型选型 → Prompt/RAG/Agent → 多模态 → 评测、安全与治理；
- **查错主线**：先找到对应机制正本，再回模型版本页核对来源，不从模型名反推未披露架构。

章节按 `00–10` 组织。子层继承父编号，例如 `7.3`、`7.3.1`、`7.3.1.1`；最多四个教学层级。目录与同名首页可以共享编号，因为一个表示容器，一个表示该容器的阅读入口。模型版本集合按官方身份组织，不为了整齐而伪造教学编号。

## 证据纪律

为了让内容经得起复查，本库采用以下约束：

1. **先写对象身份**：checkpoint、API snapshot、产品模式和完整系统不是同一个对象。
2. **优先一手来源**：论文、官方仓库、模型卡、协议规范和正式文档优先于二手转述。
3. **区分事实与推断**：来源直接陈述、由数据计算得到、工程经验和作者推断分别标明。
4. **数字带条件**：参数、训练 token、上下文、吞吐、显存、延迟和 benchmark 都绑定版本、硬件、数据与协议。
5. **未知就写未知**：闭源模型未披露参数或训练方法时，不用传闻补表格空位。
6. **更正不抹历史**：公共正文保留当前可验证结论；旧材料和迁移记录进入隐藏来源或归档，避免同时维护两套“正本”。

引用不等于结论已经被复现。论文结果只在其数据、实现和实验设置下成立；官方模型卡也不能替代当前业务的独立验收。遇到高风险用途，还需要安全、隐私、法律和领域专业人员共同审查。

## 怎样判断自己真的学会了

读完一篇后，尝试回答四个问题：

1. 这个方法解决什么瓶颈，代价转移到了哪里？
2. 公式依赖哪些假设，哪些输入会让它失效？
3. 报告中的数字由什么数据、硬件、预算和评分器产生？
4. 如果把它接入真实系统，怎样监控、回滚和证明任务完成？

能把答案写成可运行实验、可检查表格或可复现证据链，才算从“看懂名词”走到“掌握方法”。

## 一起把它维护得更好

这里仍会有遗漏和过时之处。最有价值的更正不是一句“这里错了”，而是同时给出：具体版本、冲突位置、原始来源、建议改法和核验日期。这样一次修正才能成为以后读者可复用的证据。

我始终记得，自己最迷茫时，是开源社区和素未谋面的前辈点亮了前路。希望这套不断生长的笔记，也能成为你手边一份诚实、具体、可追溯的地图。

我们路上见。

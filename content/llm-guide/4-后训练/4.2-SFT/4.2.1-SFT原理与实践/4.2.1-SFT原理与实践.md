# SFT 原理与实践

> 相关阅读: [4.2 SFT](../4.2-SFT.md) · [4.2.2 SFT 数据质量筛选与训练技巧](../4.2.2-SFT数据质量筛选与训练技巧/4.2.2-SFT数据质量筛选与训练技巧.md) · [4.2.3 DFT 与 SFT 的 RL 视角](../4.2.3-DFT与SFT的RL视角/4.2.3-DFT与SFT的RL视角.md) · [4.1 后训练数据](../../4.1-后训练数据/4.1-后训练数据.md) · [4.3.1 LoRA](../../4.3-PEFT/4.3.1-LoRA低秩适应/4.3.1-LoRA低秩适应.md)

SFT 在预训练模型上继续做 next-token prediction, 训练序列换成「输入 + 期望输出」. 材料是 InstructGPT, LIMA, Llama 2, Tülu 3 的 SFT 章节, 问题集中在损失怎么算, 数据怎么组织, 超参数和检查点怎么选.

## 目标函数与损失归一化

### 定义与优化对象

一条样本经模型专属的 chat template 渲染并分词, 得到 token 序列 $x_1,\dots,x_T$. 令 $m_t\in\{0,1\}$ 表示 $x_t$ 是否参与监督. 单条样本按 token 平均的负对数似然:

$$
\mathcal L_{\mathrm{SFT}}(\theta)=-\frac{1}{\sum_{t=1}^{T}m_t}\sum_{t=1}^{T}m_t\log p_\theta(x_t\mid x_{<t}) \tag{1}
$$

模型前向看的仍是整条序列, $m_t=0$ 的 token 照样作为条件出现在 $x_{<t}$ 中, 只是不在这个位置产生梯度. 不同的 $m$ 对应不同的训练目标:

| 掩码 | 计损失的 token | 典型用途 |
|---|---|---|
| assistant-only | 每轮 assistant 回答及其结束 token | 对话, 指令遵循, 工具调用 |
| completion-only | prompt/completion 格式中的 completion | 分类, 抽取, 翻译 |
| 全序列 | 所有 token, 含系统提示, 用户输入和角色标记 | 领域语言建模 |
| 选择性轮次 | 指定的 assistant 轮次, 例如只训末轮 | 多轮课程, 只让最终一轮承担目标行为 |

Llama 2 的做法属于第一种: 自回归目标, 用户 prompt 上的损失置零, 只在回答 token 上反传 (Llama 2 §3.1).

不管掩码怎么取, 式 (1) 做的都是同一件事: 在给定训练前缀时, 把概率集中到参考回答的 token 上. 它不直接奖励「引用支持了主张」「工具真的执行成功」「拒答恰当」这类结果; 这些靠数据设计和后续的偏好优化或 RL. 从策略梯度的角度看, SFT 的梯度等于奖励为 1, 重要性权重为 $1/\pi_\theta$ 的策略梯度, 低概率 token 的梯度被放大, 推导和由此产生的 DFT 等方法见 [4.2.3](../4.2.3-DFT与SFT的RL视角/4.2.3-DFT与SFT的RL视角.md).

**一个掩码的例子**

一条两轮对话渲染后假设是这样 (示意格式, 不对应任何具体模型):

```text
<|user|>\n 2+3=? \n<|assistant|>\n 5 <eot> <|user|>\n 再乘 4 \n<|assistant|>\n 20 <eot>
```

assistant-only 时, 计损失的是 `5 <eot>` 和 `20 <eot>`. 结束 token `<eot>` 必须在内: 模型要学会在回答结束时输出它, 推理时才会停. 如果掩码只覆盖 `5` 和 `20`, 模型从没在这个位置被要求输出 `<eot>`, 推理时可能一直续写下去. 角色标记 `<|assistant|>\n` 一般不计损失, 推理时它由服务端拼进 prompt.

只训末轮时, 第一轮的 `5 <eot>` 变成条件. 这时若第一轮回答本身质量差, 它不会产生梯度; 若监督所有 assistant 轮次, 早期低质量回答也会被模型学进去.

### 两种平均

Tülu 3 §4.3.2 用一个例子说明这个问题. 一个 batch 里有两条样本, 非 padding token 数分别为 $n_1, n_2$, 每条样本的 token 损失之和为 $l_{n_1}, l_{n_2}$. 两条一起前向时, 默认实现按 token 平均:

$$
L=\frac{l_{n_1}+l_{n_2}}{n_1+n_2} \tag{2}
$$

如果用梯度累积, 两条样本分两次前向, 每次先按自己的 token 数平均, 再对两次求平均:

$$
L=\frac{1}{2}\left(\frac{l_{n_1}}{n_1}+\frac{l_{n_2}}{n_2}\right) \tag{3}
$$

式 (2) 每个 token 权重相同, 式 (3) 每条样本权重相同. 只改梯度累积步数, 样本权重就变了. 多卡数据并行时每张卡先各自平均再跨卡平均, 也是式 (3) 的形式.

**手算**

设样本 A 是一句短回答, $n_1=10$, 平均每 token 损失 2.0, 即 $l_{n_1}=20$; 样本 B 是长回答, $n_2=990$, 平均每 token 损失 1.0, 即 $l_{n_2}=990$.

| 口径 | 损失 | A 中每个 token 的权重 | B 中每个 token 的权重 |
|---|---|---|---|
| 式 (2), 按 token | $(20+990)/1000=1.01$ | $1/1000$ | $1/1000$ |
| 式 (3), 按样本 | $(2.0+1.0)/2=1.5$ | $1/20=0.05$ | $1/1980\approx0.000505$ |

按样本平均时, A 的每个 token 权重是 B 的 99 倍. A 只占 1% 的 token, 却贡献了一半的梯度. 同一份数据, 一个设置偏向短回答, 另一个偏向长回答; 损失数值也不同 (1.01 对 1.5), 两个实验的训练曲线不能放在一起比.

### Tülu 3 的处理

Tülu 3 发现自己的 Open-Instruct 框架和 TPU 上的其他实现训出的 SFT 模型有性能差距, 定位到的主要原因就是这里: Transformers 的损失在 padding token 之外做平均时, 没有考虑梯度累积和分布式设置. 他们的修法是改用 sum loss, 即去掉式 (2), (3) 的分母, 直接对所有 token 损失求和. 这样每个 token 权重相同, 与梯度累积和卡数无关, 代价是梯度大小随 batch 内 token 总数变化, 需要重新调学习率. 他们在 Llama 3.0 上用 Tülu 2 的 SFT 数据扫学习率, epoch 和损失类型 (Figure 5, 6): sum loss 加 5e-6 学习率最好, 训练超过 2 个 epoch 没有进一步提升. 原文还提到, 在初始的数据混合上, 每个 token 等权总体效果更好.

另一种等价修法是先统计整个优化步 (所有累积微批, 所有卡) 的目标 token 总数 $N$, 每个微批用 $N$ 作分母:

$$
L=\frac{1}{N}\sum_{k}\sum_{t}m_{k,t}\,\ell_{k,t},\qquad N=\sum_{k}\sum_{t}m_{k,t} \tag{4}
$$

$k$ 遍历这一步的所有微批. 式 (4) 与把所有样本放进一个大 batch 时的式 (2) 相同, 学习率不需要随 batch 内 token 数变化. 代价是要在前向前多一次跨卡的 token 计数. 下面是一个单卡梯度累积的示意:

```python
import torch
import torch.nn.functional as F

IGNORE = -100

def train_step(model, micro_batches, optimizer):
    # 先数这一优化步里所有微批的目标 token 总数, 对应式 (4) 的 N
    n_target = sum((mb["labels"][:, 1:] != IGNORE).sum() for mb in micro_batches)
    for mb in micro_batches:
        logits = model(input_ids=mb["input_ids"],
                       attention_mask=mb["attention_mask"]).logits
        # 预测下一个 token: 第 t 个位置的 logits 对应第 t+1 个 label
        logits = logits[:, :-1].reshape(-1, logits.size(-1))
        labels = mb["labels"][:, 1:].reshape(-1)
        loss_sum = F.cross_entropy(logits.float(), labels,
                                   ignore_index=IGNORE, reduction="sum")
        (loss_sum / n_target).backward()
    optimizer.step()
    optimizer.zero_grad()
```

`labels` 中不计损失的位置 (系统提示, 用户输入, padding) 填 `-100`. 多卡时把 `n_target` 做一次 all-reduce 求和, 且框架在梯度同步时不要再除以卡数, 否则又回到了按卡平均.

## 数据怎么进入模型: 模板与 packing

### Chat template 是接口

不同模型用不同的控制 token 区分角色和轮次. Hugging Face 文档举例: 同一底座的不同对话模型可能分别用 `[INST]` 和 `<|user|>` 这类格式, 并提醒模板里已经包含的特殊 token 不要再手动加一遍, 否则会重复. Meta 的 Llama 3 格式用 begin-of-text, 角色 header 和 end-of-turn 等专用 token, 这只对 Llama 3 系列成立.

训练和推理必须对齐的项可以分成三组. 第一组是分词和模板本身: checkpoint 与 tokenizer 的版本, 模板原文 (可以存一个哈希). 第二组在 token 层面: system / user / assistant / tool 的角色映射, BOS, EOS, end-of-turn 和 padding token, 以及训练样本里是否带 generation prompt (即末尾的 assistant 角色头). 第三组在推理端: 停止 token 和输出解析器, 工具调用模板与普通对话模板是否不同. 三组里任何一项训练和推理不一致, 损失都照常下降, 问题只在生成时暴露.

第二组里的结束 token 有时是新加的. LIMA 在每段发言末尾加了一个新的 end-of-turn token (EOT), 它在推理时起 EOS 的作用, 停止生成. 不直接复用 EOS 的原因是预训练模型对 EOS 已经学到了别的含义 (例如文档结束), 新 token 避免混淆. 新加 token 时它的嵌入是新初始化的, 需要在 SFT 中学出来; 如果损失掩码漏掉了 EOT, 这个 token 永远学不会, 这就是 1.2 节那个「模型不会停」的例子的极端情形.

**一个换行的影响**

Tülu 3 §4.3.1 在一个早期 SFT 混合上 (底座 Llama 3.0) 比较了模板变体 (Table 13):

| 模板 | 平均分 |
|---|---|
| Tülu, assistant 消息末尾的换行换成 eos | 53.0 |
| Zephyr | 52.9 |
| Tülu 3 (去掉末尾换行) | 52.8 |
| Tülu 2 | 52.6 |
| Llama 3 | 51.6 |

最好和最差相差 1.4 分, 差别只在角色标记和换行这类格式细节上. 「换行换成 eos」最好, 但 Tülu 3 没有采用, 原因是要和后续 DPO, RLVR 阶段的生成保持一致, 最终选了只去掉换行的版本.

一个换行就能差出可测的分数, 而这类模板错误往往不会让损失报错, 损失照常下降. 比较可靠的做法是给每个模型保留几条人工核对过的样本, 存下原始 message, 渲染后的字符串, token ID, labels 与掩码, 推理前缀和期望的停止位置. 升级 tokenizer, 训练库或模型版本后逐字节比对. 工具调用模板还要满足一点: 追加新消息时既有前缀不变 (TRL 文档称为 prefix-preserving), 否则训练时的序列与多轮推理时的前缀缓存对不上.

**Packing**

指令数据长短差别大. 按 batch 内最长样本补齐 padding, 短样本多时大部分算力花在 padding 上. Packing 把多条样本首尾相接, 填满固定长度. Llama 2 的做法 (§3.1): 训练集中所有 prompt 和回答拼接起来, 保证序列长度 4096 被填满, prompt 和回答之间用一个特殊 token 分隔.

拼接之后, 一条样本能不能看到同一块里的其他样本, 取决于实现. 常见的有两种:

- **边界隔离**: 用块对角的注意力掩码, 或 FlashAttention 的变长接口 (按 `cu_seqlens` 切分), 每条样本只看自己的历史. 位置编码在每条样本开头重置.
- **朴素拼接**: 样本之间只插分隔符, 用一张普通的因果掩码. 后一条样本的每个 token 都能看到前面所有样本.

手算一个例子: 长度 4096 的块里依次放了 A (1000 token), B (2000 token), C (1096 token). 朴素拼接时, C 的第一个 token 的上下文里有 3000 个来自 A 和 B 的 token; 边界隔离时它的上下文是空的. 两种设置下损失都能正常下降, 但模型学到的是不同的条件分布. 朴素拼接下, 训练时 C 经常带着无关的前文, 推理时却没有; 而且如果 A 和 C 来自不同用户或不同权限的数据, 拼在一起就形成了训练中原本不存在的跨样本条件.

位置编码也要检查. 朴素拼接时 C 的第一个 token 位置是 3000, 推理时它在 0 附近; 边界隔离加位置重置后两边一致.

两种实现的损失曲线看不出区别, 所以要专门检查. 对一个已知的小 batch 打印 sequence id, position id, 注意力元数据和 labels. 再做一个直接的测试: 固定 C 的内容, 只改 A 的内容, 看 C 位置上的 logits 是否变化. 边界隔离正确时不应变化. 截断时还要检查是否出现了「保留了用户输入, 回答被截掉」的样本, 这类样本没有目标 token, 却占了序列长度.

五组配方的底座, 数据量和年代都不同, 但有三点是共同的:

- **学习率**: 都在 1e-6 到 2e-5 之间, 比预训练峰值学习率小. 模型越大学习率越低 (Tülu 3: 8B 5e-6, 70B 2e-6).
- **epoch 与数据量负相关**: 数据少的 InstructGPT (13k) 和 LIMA (1k) 训了 15 到 16 个 epoch, 数据多的 Llama 2 和 Tülu 3 训 2 个 epoch. Tülu 3 发现超过 2 个 epoch 没有更多收益.
- **残差 dropout**: LIMA 沿用 InstructGPT 的做法, 在残差连接上加 dropout, 从底层的 0 线性升到顶层的 0.3 (小模型 0.2). 1000 条数据训 15 个 epoch, 这是 LIMA 防止过拟合的主要手段.

训练时间只有 Tülu 3 给了完整数字. 最终 8B 模型在 32 张 H100 上训了 6 小时, 70B 在 64 张 H100 上训了 50 小时. 按 GPU 小时算是 192 和 3200, 70B 约为 8B 的 17 倍. 训练用 4 到 16 个 8 卡 H100 节点, 节点间高速互联.

**全参数微调与 PEFT**

| 路线 | 更新的参数 | 适用情形 | 主要风险 |
|---|---|---|---|
| 全参数 | 全部 | 数据和算力充足, 需要较大的行为改变 | 优化器状态和通信开销大, 通用能力回退 |
| LoRA / Adapter | 新加的低秩或适配参数 | 多任务, 快速迭代, 资源有限 | 秩和挂载位置限制表达能力, 部署要管理适配器 |
| 冻结部分层 | 指定的上层, 嵌入或输出头 | 受控适配, 消融 | 效果依模型而定 |
| 量化底座加 PEFT | 适配器 (底座量化后冻结) | 显存受限的单机实验 | 量化误差, kernel 支持, 可复现性 |

全参数微调的显存按混合精度 Adam 估算是每参数 16 字节 (不含激活), 7B 模型约 108GB; LoRA 和 QLoRA 的显存账, 以及「LoRA 学得少也忘得少」的实验, 见 [4.3.1](../../4.3-PEFT/4.3.1-LoRA低秩适应/4.3.1-LoRA低秩适应.md). 「某张消费级显卡能训某个大模型」这类说法, 要同时给出序列长度, batch, 量化, offload, 优化器和激活重算的设置才有意义.

**验证损失与生成质量不同向**

两份一手报告给出了一致的现象:

- **InstructGPT** (§3.5, 附录 C.1): SFT 模型训练 1 个 epoch 后验证损失就开始过拟合, 但继续训练对奖励模型分数和人类偏好评分都有帮助. 最终 SFT 模型按验证集上的奖励模型分数选, 原文称奖励模型分数比验证损失更能预测人类偏好.
- **LIMA** (§3 与附录 B): 在留出的 2000 条 Stack Exchange 数据上, 随训练步数增加, 困惑度上升, 一般这意味着过拟合, 但同期 ChatGPT 评判的生成质量也在上升. 7B, 30B 和不同数据混合上趋势相同. LIMA 因此放弃了按困惑度选, 在第 5 到第 10 个 epoch 之间用 50 条开发集人工挑选检查点.

两种做法都需要一个独立于验证损失的信号: InstructGPT 用奖励模型, LIMA 用人工. 验证损失仍可用来发现明显的错误, 例如损失不降或突然飙升. InstructGPT 训练 RLHF 用的 SFT 初始化又是另一套设置 (附录 C.3): 只训 2 个 epoch, 混入 10% 预训练数据, 学习率按演示数据和预训练数据两个验证集上的损失都低来选. 同一篇工作里, SFT 当最终模型和当 RL 起点时, 选法不同.

### 随机种子

Tülu 3 Table 14 给出了换种子的结果:

| 模型 | 种子 42 | 123 | 456 | 789 | 1011 | 最好的 model soup |
|---|---|---|---|---|---|---|
| 8B SFT | 59.9 | 60.1 | 59.8 | 59.8 | 59.8 | 60.2 (42 与 123) |
| 70B SFT | 71.8 | 70.0 | 72.6 | | | 72.5 (123 与 456) |

8B 上种子间差 0.3, 70B 上差 2.6. 把不同种子的模型权重平均 (model soup) 没有稳定超过最好的单次训练, Tülu 3 最终用每个规模最好的单次训练. 这组数字给出了一个量级参考: 70B 上 2 分以内的配方差异, 可能被种子噪声淹没, 需要多跑几次才能下结论.

## 数据量, 底座与多轮数据

### 三个数字的语境

- **LIMA**: 1000 条, 底座 LLaMA 65B, 人工评测. 论文据此提出「表面对齐假说」: 模型的知识和能力几乎都在预训练中学到, 对齐教的是与用户交互时用哪种格式的子分布. 它没有证明 1000 条能覆盖代码, 多语言, 工具和安全.
- **Llama 2**: 起步时用了公开的指令数据 (FLAN), 之后发现第三方数据多样性和质量不够, 放弃了数百万条第三方样本, 改用供应商标注的少量高质量数据, 效果明显提升. 他们发现数万条的量级就够, 共收集 27,540 条后停止. 还有两个细节: 不同标注平台和供应商的数据训出的模型差别显著; 人工核对 180 条样本时发现 SFT 模型的输出常常能和人写的标注相当, 于是把标注预算转向 RLHF 的偏好数据.
- **Tülu 3**: 939,344 条, 覆盖知识, 推理, 数学, 代码, 指令遵循, 安全和多语言. 对最终混合做分层子采样 (5% 到 100%, Figure 4), 平均分随数据量持续上升, GSM8K 的提升最大, 但 TruthfulQA 随数据量增加反而下降. 他们没有再加 SFT 数据, 原因是剩下的 prompt 留给了偏好优化.

三者的数据量差了近千倍, 但目标不同: LIMA 只看对话质量; Llama 2 的 SFT 后面还有多轮 RLHF; Tülu 3 要在一组多能力基准上全面提升. 合理的数据量取决于底座已有的能力, 要覆盖的能力范围和后续阶段. 实践中可以画一张能力覆盖表, 按能力做增量数据消融, 看边际收益.

### 底座决定上限

Tülu 3 Table 12 用同一份 SFT 数据训不同底座:

| 底座 | GSM8K | MATH |
|---|---|---|
| Llama 3.1 8B | 76.2 | 31.5 |
| Llama 3.1 70B | 91.1 | 53.7 |
| Qwen 2.5 7B | 79.2 | 49.4 |
| Qwen 2.5 Math 7B | 86.3 | 56.4 |

同样 7B 到 8B 规模, Qwen 2.5 7B 的 MATH 比 Llama 3.1 8B 高 17.9 分, 加了数学预训练的 Qwen 2.5 Math 7B 又高 7.0 分. SFT 数据相同, 差别来自预训练. 这与 LIMA 的表面对齐假说一致: SFT 改变的主要是输出格式和行为, 能力上限由底座决定.

### 多轮与工具调用数据

多轮样本要体现真实的状态变化, 不能把几个无关的单轮拼在一起. 检查点包括: 代词和实体在各轮一致; 用户纠正后, 旧的说法不再被当作事实; assistant 不重复询问已确认的信息; 截断历史后, 目标回答不会变成无依据的猜测. LIMA §6 的数据: 只用 1000 条单轮数据训练时, 10 段实时对话里有 6 段在 3 轮之内没能遵循指令. 加入 30 段多轮对话链 (10 段作者撰写, 20 段改编自 Stack Exchange 评论链), 用 1030 条数据从底座重新训练后, 回答中「优秀」的比例从 45.2% 升到 76.1%, 失败从 42 轮中 15 次降到 46 轮中 1 次; 整段对话比较, 新模型在 7 段中更好, 3 段持平. 30 条多轮样本就带来了这么大的变化.

工具调用是多轮的一种特殊形式, 轮次之间多了外部执行器返回的结果. 一条可执行的轨迹一般包括: 用户目标, assistant 的结构化工具调用, 与调用 id 对应的工具结果, assistant 根据结果给出的回答或下一次调用. 工具结果通常是条件, 不计损失; 工具调用和最终回答是否都计损失, 取决于训练目标. 参数 schema, 枚举值和错误返回要与部署时的执行器一致. 工具结果来自外部, 属于不可信输入, 数据里应包含注入文本, 超时, 权限不足, 空结果和部分成功的情况, 目标行为是澄清, 重试, 换工具或如实说明失败, 不能把错误结果当成期望答案复制下去.

## 检查, 诊断与失效

### 训练前检查与训练中诊断

前面几节的错误 (掩码漏掉结束 token, 模板不一致, packing 跨样本可见, 截断只剩输入) 都不会让损失报错, 所以要在正式训练前用小规模的检查把它们排除. 训练前的检查:

1. 随机抽样和高风险切片人工检查; 渲染模板后把 token 反解回文本对照.
2. 可视化 labels 与掩码, 确认结束 token 在监督范围内.
3. 在几十条数据上过拟合, 确认损失能降到接近零, 生成能在正确位置停止.
4. 从检查点生成一组固定 prompt 的回答.
5. 走一遍保存, 恢复, 适配器合并和推理服务加载.

训练开始后, 下面这些量要按步记录, 生成变差时才能定位到是哪个数据来源或哪个长度区间出了问题:

- 看过的总 token 数和计损失的目标 token 数, 以及每个优化步的序列数和目标 token 数;
- 每个数据来源或能力类别的采样 token 数;
- 截断率, 空目标样本比例, packing 填充率;
- 分来源, 分长度的损失, 梯度范数, 学习率;
- 生成长度, 重复率, 结束 token 命中率, 格式合法率.

「训练 3 个 epoch」在不同的去重, 截断和 packing 设置下对应完全不同的 token 曝光量, 只记 epoch 数不够.

发布时要把这些版本绑在一起记录: 底座检查点, tokenizer 与模板, 数据清单及过滤版本, 掩码, packing 与截断策略, 训练代码与超参数, 推理时的停止 token 与解析器. 回滚时这些要一起恢复, 只换回权重而保留新模板, 线上行为仍然不对.

### 失效模式

八条失效里, 前五条是实现错误: 掩码, 模板, 归一化, packing, 截断各错一处, 损失曲线都看不出来, 只能靠 5.1 节的检查和固定 prompt 的生成去发现. 第 6, 7 条是评估方法的问题: 验证损失和生成质量不同向, 单次运行的分数又有种子噪声, 两者都会让人选错检查点或误判配方. 第 8 条是对 SFT 能力的误解, 它决定了哪些问题应该交给预训练数据去解决.

| # | 失效 | 现象 | 检查与处理 |
|---|---|---|---|
| 1 | 结束 token 不在掩码内 | 模型不会停, 一直续写到最大长度 | 检查 labels 中每轮回答末尾的结束 token 是否计损失 |
| 2 | 训练和推理模板不一致 | 损失正常, 推理时格式错乱或角色混淆 | 用 2.2 节的回归样本逐字节比对 |
| 3 | 换梯度累积步数后结果变了 | 式 (2) 与式 (3) 的样本权重不同 | 改用 sum loss 或式 (4) 的全局 token 归一化 |
| 4 | 朴素 packing 导致跨样本可见 | 后一条样本以无关前文为条件, 位置也错位 | 用 2.3 节的扰动测试检查 |
| 5 | 截断只剩用户输入 | 样本没有目标 token, 却占用序列长度; 式 (1) 分母为零 | 在数据管线里过滤 |
| 6 | 按验证损失早停 | InstructGPT 和 LIMA 中验证损失或困惑度变差时生成质量还在上升 | 按生成结果选检查点 |
| 7 | 单次运行下结论 | Tülu 3 的 70B 换种子差 2.6 分 | 配方之间的小差距要多种子复现 |

第 8 条不出在实现里, 表中不列, 单独说. **把 SFT 当成知识注入**: Gekhman 等人 (2024) 在闭卷问答上控制微调数据中「新知识」样本的比例, 发现这类样本比与底座知识一致的样本学得慢得多; 等它们最终被学会, 模型的幻觉倾向随之线性上升. 他们的结论是事实知识主要在预训练中获得, 微调教的是更有效地使用已有知识. 这与 Tülu 3 的底座对照和 LIMA 的表面对齐假说方向一致.

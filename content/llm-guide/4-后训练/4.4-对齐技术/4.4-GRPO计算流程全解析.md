# GRPO 计算流程

GRPO 的公式在 [02-GRPO](./4.4.1-基于奖励模型的RL-RLHF-PPO/02-GRPO/02-GRPO.md)。本篇不重推组内 $z$-score，只写一轮更新在机器上怎么走：谁采样、谁打分、谁重算 logprob、权重怎么回到推理引擎。瓶颈不在「再写一遍 clip」，而在采样和训练用的是两套并行拓扑，中间必须搬权重、搬序列、搬旧概率。

开源实现里，这条数据流写得最清楚的是 HybridFlow（veRL 的论文名，[arXiv:2409.19256](https://arxiv.org/abs/2409.19256)）、OpenRLHF（[arXiv:2405.11143](https://arxiv.org/abs/2405.11143)）和 Megatron-LM 的 3D 并行（Shoeybi et al., 2019）。下面只跟这三家的文档和论文，不发明第三套引擎商品名。

## 1. 采样和更新为什么要拆开

自回归生成是 memory-bound。PagedAttention、continuous batching、CUDA Graph 能把吞吐拉上去，但这些优化默认住在 vLLM / SGLang 这类推理运行时里。反向传播是 compute-bound，要的是 Megatron 的 TP+PP、FSDP 的分片，或 DeepSpeed ZeRO-3 的优化器状态切分。同一套并行度很难同时伺候两边。

HybridFlow 把这件事写死：actor 的训练和生成是数据流里两个节点，经常占掉一轮 RLHF 的大头。论文里用自家系统测，训练加生成合计约 58.9% 的墙钟。OpenRLHF 更直白：RLHF 大约 80% 的时间花在 sample generation 上。两边的并行偏好也不一样。训练常要更大的模型并行度，比如 7B 在 8 卡上切成 8 份；生成更吃「小 TP + 大 DP」，同一 7B 切成 2 份再复制 4 次，吞吐更高。硬用同一套 3D 配置，生成侧会空转。

因此一轮 GRPO 至少要两套引擎。Infer Engine 负责 rollout：给定 prompt，吐出 $G$ 条完整回答，并留下旧策略下被选中 token 的 logprob。Train Engine 负责在当前 $\theta$ 上重算 logprob、组内优势、clip 目标，再反向、all-reduce、走优化器。奖励可以是规则校验器，也可以是独立的 RM；它不必是 LLM，但必须给出能进 loss 的标量。

| 角色 | 做什么 | 一手实现 |
|------|--------|----------|
| Infer / Rollout | 自回归采样，$G$ 条序列 + $\log\pi_{\theta_{\mathrm{old}}}$ | veRL：`vLLMRollout` / SGLang；OpenRLHF：vLLM Ray actor |
| Train / Actor | 重算 $\log\pi_\theta$、clip、反向、更新 | veRL：Megatron 或 FSDP；OpenRLHF：DeepSpeed ZeRO-3 |
| Verifier | $r_i\in\{0,1\}$ 或连续分 | 规则（数学抽取、单测）或 RM forward |

旧稿里把「高精度 prefill」单独叫成第三套引擎。开源文档没有这个商品名。精度差来自另一件实事：vLLM 的 logprob 和训练图的 logprob 数值对不齐，所以 Train Engine 会再跑一遍 teacher-forcing prefill。那是训练图上的前向，不是第三套运行时。

## 2. HybridFlow / veRL：控制流和计算流拆开

veRL 是 HybridFlow 的开源实现。论文的核心判断是：纯单控制器能把数据依赖写清楚，但每个分布式算子都要由中心进程下发，控制开销扛不住 LLM 级并行；纯多控制器通信快，算法图却嵌进点对点发送，换一条 PPO/GRPO 数据流就要改一堆通信。HybridFlow 把单控制器留在节点之间（prompt、序列、奖励、梯度要去哪），把多控制器留在节点之内（TP/PP/DP 自己转）。

落到代码，控制器进程拿一个 `RayPPOTrainer`（GRPO 共用这套 trainer 骨架），远程 worker 按角色挂：

- `ActorRolloutRefWorker` 可以只当 actor、只当 rollout、只当 reference，也可以 actor+rollout 共址，甚至 actor+rollout+ref 三合一。
- actor 和 rollout 共址，是为了用 NCCL 把权重从训练分片直接灌进推理引擎，而不是先落盘再拉起。
- actor 和 reference 共址，是为了 LoRA PPO：reference 就是基座，不必再占一套卡。

训练后端由 `EngineRegistry` 按 `(model_type, backend, device)` 解析。语言建模常见组合是 `(language_model, fsdp2, cuda)` 或 `(language_model, megatron, cuda)`。Megatron 路径上，`MegatronPPOActor` 管 logprob 和参数更新，`vLLMRollout` 在 SPMD 下跑生成，`MegatronVLLMShardingManager` 是上下文管理器，进出时做 actor 与 rollout 之间的真实 reshard。论文把这块叫 3D-HybridEngine：训练和生成允许不同的 $(P,T,D)$，过渡时零冗余权重副本，只搬必要分片。

GRPO 在 veRL 里的组大小不是写死 64。配置项 `actor_rollout_ref.rollout.n` 表示每个 prompt 采几条；大于 1 才进入 GRPO / RLOO 那种组统计。DeepSeekMath 论文里 $G=64$ 是他们那次实验的采样数，见第 4 节，不要把它当成框架默认。

## 3. OpenRLHF：Ray 拆池，DeepSpeed 训练

OpenRLHF 的拆法和 veRL 不同。论文（[arXiv:2405.11143](https://arxiv.org/abs/2405.11143)）和文档都写：用 Ray 把四个 RLHF 角色分到不同 GPU，vLLM 加速 actor 生成，DeepSpeed ZeRO-3 训 actor / critic，权重用 NCCL 或 CUDA IPC 同步到 vLLM。早期版本倾向「训练一份、推理一份」，显存上有冗余拷贝。后来的 Hybrid Engine 改成共址：生成阶段 vLLM wake、DeepSpeed sleep；训练阶段反过来。文档原话是，不共址的话 vLLM 在训练时闲着、DeepSpeed 在生成时闲着，大约浪费一半 GPU 时钟。

和 veRL 比，选择轴是训练并行后端，不是 GRPO 公式。OpenRLHF 吃 HuggingFace 权重 + ZeRO，少一次 Megatron 转换；veRL 在 70B 以上更常走到 Megatron TP+PP。两边的 Infer/Train 分工是同一件事：生成走推理引擎，更新走训练引擎，中间必须同步 $\theta$。

Megatron-LM 本身不是 RL 框架。它提供的是 3D 并行下的前向、反向、优化器。veRL 文档写得很直：`update_actor` 的计算脚本接近 Megatron 预训练脚本。把 Megatron 当成 Train Engine 的实现，不要当成第三种 RL 算法。

## 4. 一轮循环在搬什么

记号沿用 [02-GRPO](./4.4.1-基于奖励模型的RL-RLHF-PPO/02-GRPO/02-GRPO.md)。prompt $x$，旧策略 $\pi_{\theta_{\mathrm{old}}}$ 采 $G$ 条 $y_i$，奖励 $r_i$，当前策略 $\pi_\theta$。

$$
\text{rollout}(\pi_{\theta_{\mathrm{old}}}) \rightarrow \{y_i,\log\pi_{\theta_{\mathrm{old}}}(y_i\mid x)\}_{i=1}^{G} \rightarrow \{r_i\} \rightarrow \nabla_\theta J_{\mathrm{GRPO}} \rightarrow \theta_{\mathrm{old}}\leftarrow\theta
$$

DeepSeekMath（[arXiv:2402.03300](https://arxiv.org/abs/2402.03300)）里这次实验写得很具体：从 DeepSeekMath-Instruct 7B 出发，RL 数据是 GSM8K / MATH 的 CoT 题，大约 144K 问；策略学习率 $10^{-6}$，KL 系数 0.04；每题采 64 条，最大长度 1024，训练 batch 1024；每次探索之后策略只更新一次。这些数字只描述那次实验，不描述 veRL 默认。

组内优势仍是

$$
\hat{A}_i=\frac{r_i-\mathrm{mean}(\{r_j\}_{j=1}^{G})}{\mathrm{std}(\{r_j\}_{j=1}^{G})}.
$$

重要性比率在 token 上算：

$$
w_{i,t}(\theta)=\frac{\pi_\theta(y_{i,t}\mid x,y_{i,<t})}{\pi_{\theta_{\mathrm{old}}}(y_{i,t}\mid x,y_{i,<t})}.
$$

clip 目标取未裁与裁过的较小者。实现上 $w_{i,t}$ 几乎总是 `exp(new_logp - old_logp)`，所以 Infer 阶段记下的 `old_per_token_logps` 不是可选项。少记这一列，Train Engine 就只能用当前 $\theta$ 冒充 $\theta_{\mathrm{old}}$，clip 失效。

> 图 1：从左到右是 prompt、Infer Engine 采样、Verifier 打分、Train Engine 重算并反向；虚线是旧 logprob 和权重回灌。

**图 1 解析**

- 最左是数据，不是模型。prompt 进 Infer Engine 之前，训练图可以先 sleep。
- Infer Engine 框里写 vLLM / SGLang，是因为 veRL 和 OpenRLHF 都把生成后端配成这两家（另有 HF generate / TensorRT-LLM，不是主路径）。
- $y_1\ldots y_G$ 走实线到 Verifier。规则校验器只看最终答案或单测，不必回传中间 hidden。
- 底部虚线 `old log p` 从 Infer 底边进 Train。有的实现不信推理引擎的 logprob，Train 会用 $\theta_{\mathrm{old}}$ 再 prefill 一次；数值上仍是「旧策略概率」，只是算力多一截。
- Train Engine 框写 Megatron / FSDP / DeepSpeed，对应 veRL 与 OpenRLHF 的真实后端，不是并列的第四家 RL 库。
- 最右 `Updated θ` 顶边虚线回到 Infer：NCCL broadcast 或 HybridEngine reshard。不回灌，下一轮采样还在用旧图。

## 5. Loss 阶段：谁算 logprob，谁算优势

输入是三样：Infer 留下的 `old_per_token_logps`，Train 在 $\theta$ 上 teacher-forcing 得到的 `per_token_logps`，以及 $r_i$。优势按组算，不按全局 batch 算。同一 prompt 的 $G$ 条构成一组；不同 prompt 的组不要混进同一个 mean/std，否则简单题会把难题的尺度带跑。

$w_{i,t}$ 衡量的是「当前策略还认不认这条旧轨迹」。$w>1$ 且 $\hat{A}>0$，梯度想再抬这条轨迹；$w$ 冲出 $[1-\epsilon,1+\epsilon]$，clip 把超额部分掐掉。DeepSeekMath 的 GRPO 还留 $\beta D_{\mathrm{KL}}(\pi_\theta\|\pi_{\mathrm{ref}})$。后来 DAPO、DCPO 不少实验去掉 KL，那是另一篇的选择，不是计算流程必需。

实现上有两个分叉，写错会静默出 NaN 或假收敛。

第一，mask。padding、prompt token、以及有时是 format 模板，不应进平均。序列级平均是 $\frac{1}{|y_i|}\sum_t$，batch 级平均是 $\frac{1}{\sum_i|y_i|}\sum_i\sum_t$。GRPO 原文走前者，DAPO 走后者。DCPO 的 OTM 只在单条响应内平均，见 [变体篇](./4.4-GRPO变体与改进-GSPO与DCPO.md)。计算流程只要保证：平均的分母和 mask 一致，不要用「整段 `input_ids` 长度」去除。

第二，旧新概率必须来自同一 tokenizer、同一 chat template。Infer 用的采样模板和 Train 用的 loss 模板差一个 system prompt，比率就不是重要性采样，是在优化另一条条件分布。

## 6. 参数更新和同步

反向只对 clip 之后的标量走。优化器在开源脚本里常见 AdamW；OpenRLHF 0.10 文档加了 DeepSpeed 原生 Muon，给 actor 选 `--actor.optim muon`，critic 仍可 Adam。这是优化器菜单，不改 GRPO 目标。

分布式下梯度要 all-reduce。Megatron 路径上 all-reduce 发生在 DP 组，TP 组已经在层内通信。FSDP / ZeRO 则是分片参数的 reduce-scatter / all-gather。同步完，$\theta_{\mathrm{old}}\leftarrow\theta$，再广播到 Infer Engine。veRL 的共址路径用 NCCL 灌 vLLM；OpenRLHF 文档写 NCCL 或 CUDA IPC。分池路径还要跨节点，延迟明显高于共址。

「每轮更新后立刻同步」是默认。有的系统做异步 rollout：采样还在旧权重上跑，训练已经走到更新后的 $\theta$。那是 off-policy 程度加深，要靠更大 clip 或截断重要性采样兜着。计算流程仍应先按同步闭环写，再把异步当成偏差项。

## 7. 显存和通信各占哪一段

采样阶段主占用是 KV Cache。$G$ 条并行相当于把 batch 放大 $G$ 倍。DeepSeekMath 取 $G=64$、最大长度 1024，是论文实验；工程上 7B 常见 $G=8$ 或 $16$，再靠梯度累积凑等效组统计。KV 不够时先降 $G$，不要先降序列长度到答不完。

Loss 阶段要同时看见旧 logprob 和新 logits。旧 logprob 是 $[B,G,T]$ 的浮点，相对权重很小；新 logits 若以 fp32 全量物化，才是显存炸弹。正确做法是边算边 gather 到被选中 token，不要留下整表 vocab logits。

更新阶段是权重、梯度、Adam 一阶二阶。ZeRO-3 / FSDP 把这三份切开；Megatron 把它们按 TP/PP 切开。跨阶段最贵的是权重广播：7B bf16 约 14GB，70B 约 140GB。3D-HybridEngine 的卖点就是这次搬运零冗余。OpenRLHF 早期双副本会把这 14GB 再存一份。

通信可按阶段拆。采样时推理引擎内部 TP all-reduce（注意力输出）。训练时梯度 DP all-reduce。跨阶段是参数广播或 reshard。诊断时不要把三种通信画成一条「慢」。vLLM 慢多半是 KV 或调度；训练慢多半是 PP bubble 或 ZeRO all-gather；同步慢才是 HybridEngine 没共址。

## 8. 失效模式

| 现象 | 常在哪一段 | 先查什么 |
|------|------------|----------|
| clip 比例突然冲到十几百分点 | Train | 旧新 logprob 是否错位；模板是否一致 |
| 优势整组为 0 | Verifier 后 | $G$ 条全对或全错；不是引擎坏了 |
| 采样很长、loss 很快 | 同步 | Infer 还在吃上一轮 $\theta$ |
| 数值和单机对不齐 | Infer logprob | 是否跳过 Train 重算，直接信 vLLM |
| 吞吐只有文档一半 | 放置 | 有没有双副本闲置，OpenRLHF 文档写过这个坑 |

GRPO 变体改的是 clip 粒度和优势统计，见 [DCPO](./4.4-GRPO变体与改进-GSPO与DCPO.md)。GSPO 的序列级比率在 [03-GSPO](./4.4.1-基于奖励模型的RL-RLHF-PPO/03-GSPO/03-GSPO.md)。本篇只保证：无论目标怎么改，采样仍走 Infer，更新仍走 Train，中间仍要回灌权重。

## 9. 用一组数把一轮走完

假设 $G=8$，不是 DeepSeekMath 的 64。8 条奖励是 $\{1,1,1,0,0,0,0,0\}$。均值 $0.375$，总体或样本标准差按实现二选一，组内 $z$-score 大约是三条正例为正、五条负例为负。若实现用总体标准差且加 $\epsilon$，全 0 或全 1 仍会除零，这就是 DCPO 要修的 SAS 场景，计算流程这边只要保证：标准差为 0 时整组跳过，不要塞一个假的 $1$。

旧 logprob 来自 Infer。设某条正例长度 120，Train 重算后多数 token 的 $\Delta\log p$ 在 $\pm 0.02$，则 $w_{i,t}\approx 1.02$。$\epsilon=0.2$ 时几乎不 clip。若 Infer 用了 chat template A、Train 用了 B，同一 token 的 $\Delta\log p$ 能到 $1.0$ 以上，$w$ 冲到 $e$ 附近，clip 比例会假性飙高。这不是策略真的走远，是两条条件分布在比。

KL 系数 0.04 是 DeepSeekMath 第 4 节的数。veRL 的 DAPO recipe 常把 KL 去掉。计算流程不决定加不加，只要求：若加，reference 前向要么和 actor 共址（LoRA），要么单独一池。Reference 用 Infer Engine 的采样图去估 KL，会把采样噪声写进惩罚项。

## 10. 3D-HybridEngine 在搬什么分片

HybridFlow §5 的卖点是训练和生成允许不同的 $(P,T,D)$。训练侧常见大 TP、大 PP，生成侧常见小 TP、大 DP。权重从训练分片重排到生成分片时，朴素做法是先 gather 成完整 $\theta$ 再切，峰值显存接近「一份完整权重 + 一份训练分片」。3D-HybridEngine 按层、按 TP 组做点对点重排，不保留第三份完整拷贝，论文称为 zero-redundancy transition。

veRL 文档把这层收进 `MegatronVLLMShardingManager`：进入上下文时 actor 权重 reshard 进 `rollout.inference_engine`，退出时再收回到 Megatron 模块。`vLLMRollout` 被改成在 SPMD 下跑，才能嵌进 `WorkerGroup` 的 dispatch。生成时的并行组以 rollout 的 world size 为准，不是 actor 的 3D 组；`get_megatron_global_info` 只用来知道训练侧 rank。搞反，broadcast 会按错网格。

OpenRLHF 文档的 Hybrid Engine 是时间切片，不是 3D 重排：同一组 GPU 上 vLLM wake 则 DeepSpeed sleep。没有 Megatron 那种 $(P,T,D)$ 换拓扑，但有 sleep 释放 KV 与优化器状态的协议。70B 以上若必须 TP+PP，veRL 的 Megatron 路径更贴论文；若权重来自 HuggingFace、不想转换，OpenRLHF + ZeRO-3 更短。

NeMo-Aligner 在 HybridFlow Table 1 里被写成训练和生成用同一套 3D 配置，生成吞吐低于「训练 3D、生成另配」的 HybridEngine。这是对照，不是本篇要实现的第三条框架。

零冗余不只是「共址」四个字。HybridFlow Figure 8 把编组画死。训练用 $1$-$4$-$2$：八张卡上 TP 组是 $[\mathrm{G1},\mathrm{G2},\mathrm{G3},\mathrm{G4}]$ 与 $[\mathrm{G5},\mathrm{G6},\mathrm{G7},\mathrm{G8}]$，DP 组是 $[\mathrm{G1},\mathrm{G5}]$ 这类隔位取。若生成仍按同一套分组方法改成 $1$-$2$-$2$-$2$，过渡时要在模型并行组里 all-gather 成完整权重，再丢掉不属于本卡生成分片的那截。$\mathrm{G2}$、$\mathrm{G3}$ 这类卡上会出现「一份训练分片 + 一份完整权重」的峰值。

3D-HybridEngine 改的是生成侧怎么编组。生成 TP 改成隔位取，如 $[\mathrm{G1},\mathrm{G3}]$、$[\mathrm{G2},\mathrm{G4}]$；micro DP 沿生成 TP 维顺序排，如 $[\mathrm{G1},\mathrm{G2}]$。这样每张卡上生成要用的权重和训练分片重叠，不必先 gather 再切。论文把这一步叫 zero-redundancy transition。Naive 分组不是第三套引擎，是同一份 HybridEngine 走错编组。

Figure 7 的四步按这个编组读：① 在 micro DP 组里收集更新后的参数供生成；② 把 prompt 铺到每个 replica；③ 生成结果在 micro DP 内 all-gather；④ 再按训练 3D 重切参数，然后算 loss。KV Cache 生成后可以 offload 到 CPU，下一轮再搬回来。这是显存时间片，不是第三套运行时。论文实现大约 2.4k 行，叠在 Megatron-LM 与 vLLM 上：训练权重和生成权重分两个 buffer，训练时把生成权重卸到 CPU，过渡再用 NCCL 在 micro DP 里拼接。

## 11. 控制器一次 `fit` 调哪些 API

按 HybridFlow 的层次 API，一轮 GRPO 在单控制器里大致是：`generate_sequences`（Infer）→ `compute_reward`（规则或 RM）→ `compute_log_prob`（Train 上的旧/新概率，有的实现旧概率已在生成时记下）→ `update_actor`（clip loss + 反向）。每一步都带着 collect / distribute 协议，因为 prompt 按 DP 切，序列按 rollout 的 TP 切，奖励按数据并行汇到控制器再打散。

`ActorRolloutRefWorker` 的共址不是为了少写一个类。NCCL 灌权重的前提是同一进程能看见训练分片和推理引擎。分进程的 Ray actor 只能走 IPC 或网络。OpenRLHF 分池时把 vLLM 放在独立 Ray actor，文档承认可以占专用节点，避免和训练 TP 组抢 NVLink；代价是第二份权重。选共址还是分池，看卡够不够同时放下 KV 和 Adam。不够就共址 + sleep，够就分池换吞吐。

GRPO 不需要 critic，所以没有 `update_critic` 和 GAE。RLOO、PPO 会多这两步，数据流多一条价值模型的 multicast。计算流程仍是 Infer 采样、Train 更新，只是 Train 侧多一个网络。不要因为 GRPO 去了 critic，就以为可以省掉 logprob 重算。

## 12. PPO 四模型与 GRPO 两模型，搬运量差在哪

OpenRLHF 论文把 RLHF 写成四个网络：actor、critic、reference、reward。分卡是为了 70B 以上还能转起来。GRPO 去掉 critic，奖励若是规则校验，reward 模型也可以不下场。还在场的是 actor（训练图 + 推理图）和可选的 reference。搬运从「四份权重互相同步」收成「一份 $\theta$ 在 Infer/Train 之间来回」。这是 GRPO 省显存的工程来源，DeepSeekMath 写的 25% 是相对 PPO 的 critic，不是相对推理引擎。

即使只剩 actor，Infer 和 Train 仍是两套运行时。vLLM 的 PagedAttention 按块管理 KV，训练图的 attention 按静态形状或 Megatron 的序列并行来。不能把 vLLM 的 KV 直接反传。所以「共址」指的是 GPU 和时间片共享，不是计算图共享。sleep 模式把一边的显存还给另一边，权重仍要按各自布局再铺一次。

生成侧的 $G$ 条并行，在 vLLM 里是同一 prompt 的 $n$ 路采样。配置名在 veRL 是 `rollout.n`，在 OpenRLHF 的 PPO/GRPO 脚本里是 `--n_samples_per_prompt` 一类项（以当前文档为准）。$n=1$ 时组内标准差不存在，GRPO 退化成没有基线的 REINFORCE。DeepSeekMath 取 64，是为了让组内均值稳；工程上 8 或 16 更常见，靠更多 prompt 补 batch。不要把论文 $G$ 和框架默认写成同一个数。

KL 若保留，reference 前向是又一次 teacher-forcing，形状与 Train 的 logprob 相同，只是冻结权重。共址 LoRA 时 reference 就是基座，一次前向即可。全量 reference 分池，通信又多一跳。计算流程把这条画成虚线辅助，不和奖励实线混用。

数值对不齐的另一来源是采样温度。Infer 用 $T=1.0$ 采轨迹，Train 算 logprob 必须在 $T=1$ 的 logits 上做 log-softmax，再按实际温度校正，或者直接存采样时的 logprob。两边约定不一致，$w_{i,t}$ 会系统性地偏。veRL 的实现把 old logprob 在生成时记下，Train 只算 new，减少一次温度口径争论。

## 13. 校验器挂在哪，不挂在引擎里

规则奖励通常在控制器或专用 CPU 池上跑：抽 `\boxed{}`、跑单测、比数值。它吃的是文本 $y_i$，不是 hidden。HybridFlow 把 `compute_reward` 收成独立节点，可以和生成重叠。RM 奖励才是又一次 LLM 前向，布局接近 reference：FSDP / ZeRO 一份冻结权重。OpenRLHF 允许把 RM 和 vLLM 分卡，避免和生成抢 KV。

GRPO 的组统计必须在「同一 prompt 的 $G$ 条」上做。控制器要按 $x$ 的 id 聚组，再打散回 DP rank。聚错组，简单题和难题的奖励会进同一个 mean/std，优势尺度乱掉。这是数据依赖，不是 Megatron 的 bug。veRL 的 dispatch 协议就是为这种「先 collect 再 compute 再 distribute」准备的。

失败时先看三份日志：Infer 的 accept length / KV 占用，Verifier 的 $r$ 直方图，Train 的 clip 比例和 grad norm。三者对不上，再查权重有没有回灌。不要一上来改 $\epsilon$。

DeepSeekMath 那次实验还写：策略在每次探索之后只更新一次。这是 on-policy 程度最高的设定，旧新策略只差一步。veRL 允许同一批 rollout 做多次 PPO epoch，off-policy 程度加深，clip 才真正开始干活。计算流程把「单次更新」和「多 epoch」都画成同一条 Train 边，差别只在 $w_{i,t}$ 会不会系统性地离开 1。多 epoch 时务必用记下的 old logprob，不要每 epoch 把当前 $\theta$ 当成 $\theta_{\mathrm{old}}$。

## 14. Table 1 三家对照，不要读成三套公式

HybridFlow Table 1 把 DeepSpeed-Chat、OpenRLHF、NeMo-Aligner 和自家排在一起。图注里的数字 1–6 是一轮 PPO 的节点：生成、RM 推理、reference 推理、critic 推理、actor 训练、critic 训练。GRPO 砍掉 4 和 6。

DeepSpeed-Chat：同一份权重在 ZeRO 与 TP 之间 reshard，大模型峰值显存和通信仍重。OpenRLHF 早期：训练一份、推理一份，调度简单，显存双份。NeMo-Aligner：训练和生成同一套 3D，生成吞吐低于换拓扑的 HybridEngine。veRL 的 3D-HybridEngine 是换拓扑、不留第三份完整拷贝。选哪条看要不要 Megatron 转换，不看 GRPO 公式。公式在 02-GRPO，机器在这篇。

SGLang 在 veRL 里与 vLLM 并列，多轮、结构化输出更常走它，数据流角色不变，仍是 Infer。校验失败不要回灌半截权重。Train 若中途报错，Infer 继续用上一轮 $\theta$，至少还能采出可复现的组。半同步比静默用坏权重安全。

论文还报过相对当时基线 $1.53\times$ 到 $20.57\times$ 的加速，对象是 DeepSpeed-Chat / OpenRLHF / NeMo-Aligner 在不同模型尺寸和集群规模上。这是系统吞吐，不是 GRPO 分数。OpenRLHF 论文写 RLHF 大约 80% 时间花在 sample generation；HybridFlow 写训练加生成合计约 58.9% 墙钟。两套百分比口径不同：一个是生成独占，一个是 actor 训练+生成合计。不要把 80% 和 58.9% 减出「谁更快」。

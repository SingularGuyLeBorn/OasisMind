# 04 MoE 硬件架构：动态路由怎么上板

MoE 的前向每次只点亮少数专家，但 **点亮哪几个是输入决定的**。硬件如果还按稠密 GEMM 的静态数据流来排，就会：计算单元空一半、片上缓存装不下全部专家权重、All-to-All 把互联打满。本篇看 **架构层**（系统怎么适配动态性），加速器个案与近存计算在 [06](../06-MoE硬件加速架构综述/06-MoE硬件加速架构综述.md)，部署与通信在 [05](../05-MoE系统与架构优化综述/05-MoE系统与架构优化综述.md) / [07](../07-MoE混合并行部署与通信优化图解/07-MoE混合并行部署与通信优化图解.md)。

DeepSeekMoE 的共享专家 / 细粒度公式 **不在这里重写**，见 [01](../01-DeepSeek-MoE/01-DeepSeek-MoE.md)。MLA 是 KV **表示**，不是 MoE 硬件；字节估算见 [2.2.2/04](../../../2.2-基础注意力机制/2.2.2-多头注意力变体/04-MLA-低秩潜变量与解耦式注意力/04-MLA-低秩潜变量与解耦式注意力.md)。

## 1. 动态性带来的三件事

1. **计算不可预测**：这个 batch 激活的专家集合和下一个 batch 不同，静态流水线会空转。
2. **通信模式随路由变**：token 的目的 rank 是门控输出，不是固定 mesh。
3. **权重常驻 vs 按需加载**：专家多的时候，全部权重进 HBM 和「只加载被点亮的专家」是两条完全不同的存储设计。

负载不均会让一部分计算单元过载、另一部分闲着。算法侧的 $f_i P_i$ 或 aux-loss-free 偏置是在训练里拧分布；板上还是要能消化残差溢出和变长 grouped GEMM。

## 2. 宏观：UbiMoE 这一类 FPGA 设计

**UbiMoE**（Dong et al., [arXiv:2502.05602](https://arxiv.org/abs/2502.05602)）把 Vision Transformer 上的 MoE 拆成两套核：

- 延迟向的 **流式注意力核**（固定 Q、广播 K，降低反复读）。
- **可复用线性核**，按资源约束搜参数，Dense / 稀疏模式可切。

融合 Softmax、动态取最大值，是为了少把中间激活写回片外。本页不编加速比；数字以该文表格为准。同族的 FLAME / Edge-MoE 放在 [06](../06-MoE硬件加速架构综述/06-MoE硬件加速架构综述.md)，避免三篇综述各抄一遍。

## 3. 微观：计算、访存、互联

| 面 | 在做什么 | 不是 |
|----|----------|------|
| 计算 | 按路由结果做 grouped / 稀疏 GEMM；gate 常用更高精度 | 不是把 MoE 改回稠密 FFN |
| 访存 | 热专家常驻，冷专家按需；N:M 剪枝是权重形态 | 不是 MLA 的 $c^{KV}$ |
| 通信 | token 按专家分组的 All-to-All，尽量和计算重叠 | 不是注意力 TP 的 AllReduce |

## 4. 协同

算法把专家切细、加共享专家、加负载损失，是在减小「单专家过肥」和「流量塌缩」。硬件则需要稀疏单元、更大片上缓冲、以及吃得动动态 All-to-All 的互联。缺一边，另一边的纸面稀疏度兑现不了。

# 2.4.1 混合专家模型 MoE：条件计算零点

MoE 把 Transformer 里那层稠密 FFN 换成 $N$ 个专家：每个 token 只激活 $k \ll N$ 路。卡住的不是「参数还能不能再堆」，而是**条件计算**：路由器怎么分活、负载怎么不塌、容量满了 token 走哪条残差。本页是 2.4.1 的地图和公式零点。容量、溢出、aux-loss、z-loss 写在下面第 4–5 节，不再另开工程实践专文。机制主线 01→03→10。**不是** MLA（注意力 KV 的 $c^{KV}$ 在 [2.2.2/04](../../2.2-基础注意力机制/2.2.2-多头注意力变体/04-MLA-低秩潜变量与解耦式注意力/04-MLA-低秩潜变量与解耦式注意力.md)），也不是专家并行通信专文（All-to-All / EP 正本在第 6 章），也不是条件记忆（n-gram 哈希表在 [2.4.8 Engram](../2.4.8-条件记忆与Engram/2.4.8-条件记忆与Engram.md)）。LatentMoE 的 $\ell$ 是 FFN 专家空间的瘦维，不是 MLA 的 $c^{KV}$，公式在 [10](./10-Stable-LatentMoE与Quantile-Balancing/10-Stable-LatentMoE与Quantile-Balancing.md)。

## 2. 条件计算：软混合 vs 稀疏门控

稠密 FFN：每个 token 流过同一套中间层，该层全部参数都算一遍。条件计算换的是这条不变量——**算哪些参数，取决于这个 token**。

1991 年 Jacobs、Jordan、Nowlan、Hinton 的 Adaptive Mixtures of Local Experts 已经把「专家 + 门控」写清楚：门控给出权重，输出是全体专家的加权和，训练用 EM。那时所有 $g_i(x)>0$，没有算力折扣。现代 LLM 要的稀疏性，是 Shazeer 等人 2017 年的 noisy Top-K、GShard 的 Top-2 容量约束、Switch 的 Top-1 才钉进 Transformer 的。

![稠密 FFN 全激活 vs 稀疏 MoE 只激活部分专家](./images/fig-moe-dense-vs-sparse.png)

> 图 1：左栏稠密 FFN，每个 token 激活全部参数；右栏稀疏 MoE，路由器只点亮少数专家。

**图 1 解析**

- 两栏都是从上往下：Token $x$ 进层，底下出 $y$。不要把左栏读成从下往上。
- 左：稠密 FFN 一块绿点阵，格子全绿。一次前向 = 这一层全部 FLOPs。
- 右：先过 Router，只给 Expert 2、Expert 5 实线（和图 2 同一对赢家），其余六个灰专家没有进线。两路进 $+$，再出 $y$。总参数可以比左边大，**这一 token 的计算**只走被点亮的那两条。
- 图要钉的零点：总容量（所有专家之和）和每 token FLOPs（激活专家）脱钩。后面负载、容量、EP 都是在伺候这个脱钩。

记号：输入 token 隐状态 $x\in\mathbb{R}^{d}$，专家 $E_1,\ldots,E_N$ 各是一个 FFN，门控 $g_i(x)\in\mathbb{R}$。软混合（全体专家都算）是

$$
y=\sum_{i=1}^{N} g_i(x)\,E_i(x),\qquad
g(x)=\mathrm{Softmax}(W_g x). \tag{1}
$$

软混合里 $g_i(x)>0$，没有稀疏。稀疏门控把绝大多数 $g_i$ 强制为 0，只留 Top-$K$：

$$
y=\sum_{i\in\mathrm{TopK}(x)} g_i(x)\,E_i(x). \tag{2}
$$

![MoE 层：token → 路由器 → Top-2 专家 → 加权和](./images/fig-moe-router-top2.png)

> 图 2：Token-Choice、$k=2$。八个门控分数里 $0.31$、$0.28$ 最大，所以只跑 Expert 2 与 Expert 5，再乘 $p_2$、$p_5$ 后相加。

**图 2 解析**

- 上：$x\in\mathbb{R}^{d}$ 进 Router。门控是一层线性，吐出 8 个分数，不是又一个大 FFN。
- 分数条：数字已经写在格子里。$s_2=0.31$ 第一、$s_5=0.28$ 第二，所以 Top-2 是专家 2 和 5。$s_6=0.09$ 第三，进不了 $k=2$，右侧蓝框写的就是这件事。灰格子没有向下的箭头。
- 中：只画两个绿专家。左边灰框是闲置专家打包，没有出线。
- 下：Expert 2、Expert 5 各出一条线，经 $\times p_2$、$\times p_5$ 进 $\oplus$，再从 $\oplus$ 右侧出一箭到 $y$。未选中的专家这一 token 不跑，权重仍要驻显存（见图 9）。

## 3. 路由：Token-Choice vs Expert-Choice

路由是 token 与专家的匹配。三条路：

1. **Token-Choice**：每个 token 给全体专家打分，自己挑 Top-$K$ 个专家。Mixtral、DeepSeek、Qwen 这一路都是它。
2. **Expert-Choice**：每个专家给全体 token 打分，自己挑固定容量的 token（Zhou et al., 2022）。
3. **全局分配**：把匹配写成运输问题。训练步里太贵，几乎不进主线。

哈希路由（Roller et al., 2021）是非学习的固定映射：零路由参数、天然均衡，但分数不能随数据改。Hash Layers 表明，即使哈希不含语义，单靠「多一套专家容量」也能降损失；它不是本库 LLM 的默认路由器，只说明**稀疏容量本身**有用。

### 3.1 Token-Choice：先 Top-K 再 Softmax，还是先 Softmax 再截断

对 $x$，路由器先出 logits

$$
h(x)=W_g x. \tag{3}
$$

Shazeer 2017 在训练早期加可学习噪声，避免过早锁死少数专家：

$$
h'(x)_i=h(x)_i+\mathrm{StandardNormal}()\cdot\mathrm{Softplus}\bigl((W_{\mathrm{noise}}x)_i\bigr). \tag{4}
$$

**实现分叉在 Softmax 和 Top-K 的顺序。**

**先 Top-K 再 Softmax**（KeepTopK，再把落选坐标置 $-\infty$）：

$$
h_{\mathrm{TopK}}(x)_i=\begin{cases}
h'(x)_i & i\in\mathrm{TopK}(x)\\
-\infty & \text{otherwise}
\end{cases},\qquad
g(x)=\mathrm{Softmax}\bigl(h_{\mathrm{TopK}}(x)\bigr). \tag{5}
$$

选中的 $K$ 个门控之和为 1。Qwen 系常见这条；Shazeer 原文也是 KeepTopK 再 Softmax。

**先 Softmax 再截断**：先对全部 $N$ 个 logits 做 Softmax，再把非 Top-$K$ 的 $g_i$ 置 0。选中门控之和小于 1。DeepSeek V1–V2 走这条（见 [01](./01-DeepSeek-MoE/01-DeepSeek-MoE.md)）。

两条都叫 Top-$K$，残差尺度不一样。不要混着用同一套学习率去对。

离散选择本身不可导。框架给的是前向硬选、反向掩码恒等，推导在 [03](./03-MoE-Top-K运算可导性分析/03-MoE-Top-K运算可导性分析.md)。

Switch Transformer 把 $K$ 收到 1：每个 token 只进一个专家，通信更简单，容量公式更好写。它是工程零点，不是「Top-1 一定比 Top-2 强」。

![Switch Transformer：每个 token 只进一个专家](./images/fig-switch-top1.png)

> 图 3：Switch 的 Top-1。Router 只给 Expert 5 一条实线，其余专家虚线空闲。

**图 3 解析**

- 左 Token → 中 Router → 右八个 FFN。
- 实线只打到 Expert 5，其余七条灰虚线：这一 token 的 FFN FLOPs 等于**一个**专家，不是八个的加权和。
- 和 图 2 比：$k=1$ 时加权和退化成 $y=g_{i^\star}(x)E_{i^\star}(x)$。负载一旦塌，被冷落的专家整层都学不到。

### 3.2 Expert-Choice：专家抢固定容量

Token-Choice 不限制每个专家收多少 token，所以会塌。Expert-Choice 反过来：专家 $i$ 对 batch 内全部 token 打分，取自己最想要的 $C$ 个。每个专家的 token 数钉死，负载均衡不再靠辅助损失。

![Expert-Choice：每个专家给全体 token 打分，取 top-C](./images/fig-moe-expert-choice.png)

> 图 4：Expert-Choice。Expert 2 给 8 个 token 各打一个分，只把最高的两个（Token 3、Token 7）装进容量 $C=2$。

**图 4 解析**

- 上：8 个 token，每条都进分数条。这就是打分，不是按序号 1–2、3–4 两两配对。
- 分数条：数字写在格子里。$s_3=0.41$ 第一、$s_7=0.33$ 第二，所以 Expert 2 只要 Token 3 和 Token 7。$s_5=0.12$ 第三，容量满了进不去。灰格子没有向下的箭头。
- 绿框两个槽正好 $C=2$。右边灰框：Expert 1、3、4 各自对这 8 个 token 再打一套分、再取自己的 top-2，不是把剩下的 token 按序号均分。
- 一个 token 可以被多个专家抢走，也可以谁都不选。每个专家的人数钉死，负载均衡不再靠辅助损失。代价是每个专家都要看见全体 token 的分数。

Token-Choice 的槽数写成容量因子 $\gamma$（Switch 文里也叫 $\mathrm{CF}$）。设本层一个 batch 有 $T$ 个 token、$N$ 个专家，每个 token 最多派给 $k$ 个专家。Switch 是 $k=1$；GShard 是 top-2，组内还要把容量按组切开。统一写法：

$$
C=\left\lceil\frac{T\cdot k}{N}\cdot\gamma\right\rceil. \tag{6}
$$

$\gamma=1$ 时总槽数刚好等于均匀分流的派遣次数。路由器一旦偏科，热专家先满；再来的 token 算 overflow：本层专家 FFN 不算，残差进下一层。$\gamma>1$ 给热专家留缓冲，空槽用 padding 填成静态形状——算力和通信按满槽付账。$C$ 必须是整数，所以有向上取整。Switch 实验里常用 $1.0$–$1.25$（Fedus et al., 2021）。评测时常把 $\gamma$ 临时加大（ST-MoE 微调评估 $\gamma=2.0$）：推理不想丢 token，训练却用更紧的槽省算力。两套 $\gamma$ 不要合成一个「官方容量」。

Expert-Choice 的 $c$ 不是这颗螺丝。Zhou et al. (2022) 式 (1) 把每个专家取多少 token 写成 $k=n\cdot c/e$（$n$ 是 batch 内 token 数，$e$ 是专家数）。$c=2$ 与 GShard top-2 的激活量对齐；$c=1$ 对齐 Switch top-1。桶大小按构造固定，不再需要下面的 $f_i P_i$。不要把 $c=2$ 写成「容量因子 2」，那会和 Switch Table 1 的 $\gamma=2.0$ 撞车。EC-CAP2 是专家侧 Top-$k$ 之上再加一道 token 侧帽子，不是 dropless。

## 4. 负载：aux-loss、z-loss、aux-loss-free

Token-Choice 的失败模式是**专家坍塌**：路由器反复把 token 送给同一批「明星专家」，其余专家梯度饿死，总参数白占显存。

![负载不均衡：多数 token 涌向少数专家](./images/fig-moe-load-imbalance.png)

> 图 5：负载不均。16 个 token 里 10 个进了 Expert 3，其余专家 1 个或 0 个。

**图 5 解析**

- 上：一整批 token 进 Router，不是 16 条线分别画。
- 计数条：每个专家这一步拿到几个 token。$n_3=10$，旁边格子 $1$ 或 $0$，均匀该是 $16/8=2$。只有 $n_3$ 格子往下有一条实线。
- 绿框里 10 个小方块就是 Expert 3 的槽；别的专家框底一粒或空。没有第二层箭头。
- 这就是 $f_i$ 远离 $1/N$：明星专家吃满梯度，其余饿死，总参数仍占显存。训练曲线不在本页另绘。

### 4.1 辅助损失（Switch 同族）

对一个 batch，$T$ 个 token。Switch 的 Top-1 把专家 $i$ 的占用写成

$$
f_i=\frac{1}{T}\sum_{x\in\mathrm{Batch}}\mathbb{1}\bigl\{\arg\max p(x)=i\bigr\}. \tag{7}
$$

此时 $\sum_i f_i=1$。Top-$K$ 把指示函数换成 $i\in\mathrm{TopK}(x)$；若仍要 $f$ 的均值是 $1/N$，再乘 $N/K$（DeepSeek 的 $L_{\mathrm{ExpBal}}$，见 [01](./01-DeepSeek-MoE/01-DeepSeek-MoE.md)）。平均门控

$$
P_i=\frac{1}{T}\sum_{x\in\mathrm{Batch}} g_i(x). \tag{8}
$$

负载项是两个向量的点积，再乘专家数：

$$
L_{\mathrm{balance}}=\alpha\cdot N\sum_{i=1}^{N} f_i P_i. \tag{9}
$$

Switch 的 Top-1 且 $f=P=1/N$ 时，$N\sum f_i P_i=1$。$\alpha$ 太大，路由器会为了均分而牺牲主损失；太小，坍塌照旧。总损失

$$
L_{\mathrm{total}}=L_{\mathrm{main}}+L_{\mathrm{balance}}. \tag{10}
$$

Switch 取 $\alpha=10^{-2}$，在 $10^{-1}$ 到 $10^{-5}$ 的十倍扫里，这个数量级既能很快拉平负载、又不压过交叉熵。$f_i$ 里的指示函数不可导，梯度只走 $P$，不走 $f$：路由器被拧的是「给热专家的概率」。$L_{\mathrm{balance}}$ 进训练图，**不进推理图**。关掉它，Switch / ST-MoE 表里的丢弃率会从 $<1\%$ 跳到两位数——不是容量公式变了，是 $f$ 更尖、局部 $C$ 更早打满。这和 [03](./03-MoE-Top-K运算可导性分析/03-MoE-Top-K运算可导性分析.md) 里 Top-K 的掩码恒等是两件事：aux-loss 不把选中集合变光滑。GShard 组级形式是 $\ell_{\mathrm{aux}}=\frac{1}{E}\sum_e (c_e/S)\,m_e$：想罚 $(c_e/S)^2$，但 $c_e$ 来自 top-2 计数，改用可微的组内平均门控 $m_e$ 去乘。

DeepSeek V1–V2 还加过**逐设备**均衡：把同一 GPU 上的专家聚合成 $f'$、$P'$ 再点积，避免「专家数均分但卡间 token 数不均」。公式在 [01](./01-DeepSeek-MoE/01-DeepSeek-MoE.md)。

### 4.2 Router z-loss

MoE 训练曲线常见尖峰。ST-MoE（Zoph et al., 2022）把一部分原因钉在路由器 logits 过大：低精度里 Softmax 的 $\exp$ 把微小舍入放大，Top-K 的赢家会整批翻转。对策是路由器用 FP32，再罚 LogSumExp 的平方：

$$
L_z=\frac{1}{B}\sum_{i=1}^{B}\left(\log\sum_{j=1}^{N}e^{x_j^{(i)}}\right)^2. \tag{11}
$$

$$
L_{\mathrm{total}}=L_{\mathrm{main}}+\alpha L_{\mathrm{balance}}+\beta L_z. \tag{12}
$$

![三项训练损失各自落到总损失](./images/fig-moe-eng-aux-zloss.png)

> 图 6：$L_{\mathrm{CE}}$、$L_{\mathrm{aux}}$、$L_z$ 各自从底边进 $L_{\mathrm{tot}}$。$\alpha=0.01$（Switch），$c_z=0.001$（ST-MoE）。

**图 6 解析**

- 三列平行落到绿框。加总只写在 $L_{\mathrm{tot}}$ 里，栏与栏之间没有加号链。
- 蓝栏是主任务交叉熵：序列 → 词表 logits。
- 黄栏 $N\sum_i f_i P_i$ 拧负载；粉栏罚路由器 logits 的 LogSumExp 平方。
- $\alpha$ 与 $c_z$ 差两个数量级：负载项要真的拧 $f$，z-loss 只要 logits 别爆。

ST-MoE 取 $\beta=c_z=0.001$（预训练扫参）。它**不是** clip：clip 发生在舍入之后，本身又是一次截断；z-loss 从训练目标上压幅度。Switch Table 2：路由器整段 bfloat16 时负对数困惑度到 $-3.780$ 并发散；只把**路由器局部**升到 float32（dispatch / combine 仍 bfloat16）得到 $-1.716$，速度与纯 bfloat16 同为 1390 examples/s。$-3.780$ 是发散后的坏质量，不是「更负所以更好」。ST-MoE 写：到他们的最大规模，选择性精度仍不够。Table 4（各 3–6 次）：基线 $4/6$ 稳定、质量 $-1.755\pm0.02$；把 Adafactor 的 update clip 收到 $0.1$ 则 $3/3$ 稳定，但质量崩到 $-4.206\pm0.17$；z-loss 则 $3/3$ 稳定且质量 $-1.741\pm0.02$。

![Router 用 FP32，z-loss 惩罚过大 logits](./images/fig-moe-router-zloss.png)

> 图 7：隐状态 BF16 进 Router；logits 在 FP32 里算；$L_z=\frac{1}{B}\sum_i\bigl(\log\sum_j e^{z_j^{(i)}}\bigr)^2$。专家 FFN 仍是 BF16。

**图 7 解析**

- 上：Input (BF16) → Router (FP32 logits) → Top-K → 一列 Expert FFN (BF16)。
- 下：从 FP32 logits 拉出 z-loss。它罚的是 **logits 的尺度**，不是 $f_i$ 与 $P_i$ 偏不均。和式 (9) 不是同一个旋钮。
- 稳定性的其它面（损尖峰、训推不一致）在 [6.1.7](../../../6-训练与推理优化/6.1-训练基础设施/6.1.7-训练稳定性与训推不一致.md)。

### 4.3 aux-loss-free

DeepSeek-V3 不再用逐专家 $f_i P_i$ 当主均衡，而是给每个路由专家一个偏置 $b_i$：过载就减小 $b_i$，空闲就增大，下一步用 $s_{i,t}+b_i$ 做 Top-K。这叫 aux-loss-free。单序列上仍可能极端不均，所以还留了一个**序列级**互补辅助损失。偏置的更新步长在 K3 规模上不够，改 Quantile Balancing，见 [10](./10-Stable-LatentMoE与Quantile-Balancing/10-Stable-LatentMoE与Quantile-Balancing.md)。V3 的 Sigmoid 打分与 $b_i$ 公式在 [01](./01-DeepSeek-MoE/01-DeepSeek-MoE.md)。

## 5. 容量、溢出、显存

Token-Choice 加上式 (6) 的硬容量之后，挤不进任何专家槽的 token **不跑 FFN**，残差直通下一层。同一条 prompt 在不同 batch 里，会不会被丢，取决于同批其它 token 抢了多少槽——这是 MoE 推理里一批次相关的非确定性来源。不要把它写成某个闭源模型 Temperature=0 仍会变的「内幕」。

![容量满时 token 溢出，走残差跳过专家](./images/fig-moe-token-overflow.png)

> 图 8：Expert 1 三个槽被 Token 1–3 占满，这三路算出专家再进下一层；Token 4、5 进不去，残差跳过这一层 FFN，五条一起走。

**图 8 解析**

- 左：Token 1–3 实线进 Expert 1；4–5 虚线从底下绕开，不去空闲专家上试探。
- 中：Expert 1 的三个槽已满。Expert 2–4 空闲，没有进线。
- 右：1–3 标 after FFN，4–5 标 residual skip，**五条都进 next layer**。溢出不是把 token 扔掉，只是这一层专家没算。$\gamma$ 太小跳过变多，太大 padding 变多。

Switch Table 1（128 专家、隔层 MoE、同 32 核 TPUv3、100k step）把 $\gamma$ 当成速度–质量旋钮。负对数困惑度**越大越好**（$-1.534$ 优于 $-1.731$）：

| 模型 | $\gamma$ | 100k step 负对数困惑度 | 到 $-1.50$ 的小时 | examples/s |
|------|---------|------------------------|-------------------|------------|
| T5-Base | — | $-1.731$ | 未达到 | 1600 |
| MoE-Base（top-2） | 2.0 | $-1.547$ | 68.7 | 840 |
| Switch-Base | 2.0 | $-1.554$ | 72.8 | 860 |
| Switch-Base | 1.25 | $-1.553$ | 65.0 | 910 |
| Switch-Base | 1.0 | $-1.561$ | 62.8 | 1000 |
| Switch-Base+ | 1.0 | $-1.534$ | 67.6 | 780 |

低 $\gamma$（1.0 / 1.25）在这块 TPU 预算上反而更好：质量几乎一样，小时数和吞吐都占便宜。配合 aux-loss、系数够大时，丢弃率通常 $<1\%$，且与专家个数没有观察到的依赖。GShard 更严：一个 token 的两个候选专家**都**满了，才标 overflow。第二专家还带一层随机派遣：若 $g_2$ 已经很小，按与 $g_2$ 成比例的概率决定要不要派第二路。Switch 还试过 **No-Token-Left-Behind**：溢出 token 改派给第二高分专家，可迭代到几乎零丢弃，实验上没有质量收益——网络一旦学到 token–专家对应，改派会把对应关系打乱。

**Token drop** 是 GShard / Switch 默认：形状固定，溢出走残差。ST-MoE Table 5（SuperGLUE）：训练 $\gamma=0.75$、评估 $\gamma=2.0$、开 aux-loss 时峰值丢弃 $10.6\%$，分数 $86.5\pm0.21$；训练 $\gamma=1.25$ 丢弃 $0.3\%$，分数 $86.7$。关掉 aux-loss、同样 $\gamma=0.75$，丢弃升到 $15.6\%$，分数掉到 $85.7$。微调阶段丢 $10$–$15\%$ 可以和丢 $<1\%$ 差不多；aux-loss 在微调里仍然有用。预训练另一端：MegaBlocks 在 The Pile、64 专家、top-1、对照 Transformer-Small 时，$\gamma=1$ 的 drop 模型验证损失只降 $0.15$，避免丢弃的配置降 $0.26$（约为前者收益的 $1.73\times$）。

**Dropless** 不是把 $\gamma$ 调到无穷。MegaBlocks（Gale et al., [arXiv:2211.15841](https://arxiv.org/abs/2211.15841)）把 MoE 写成 **block-sparse GEMM**：专家 batch 长度跟实际派遣走，只 pad 到 block 对齐，不再按全局 $C$ 填空槽。同验证损失下，相对 Tutel 的 padding 式 dropless，端到端加速 $1.38\times$（XS）/$2.0\times$（Small）/$4.35\times$（Medium）。Tutel 把 $\gamma$ 动态调到「刚够不丢」时，有的 MoE 需要 $\gamma$ 高到 $11$，而且训练中途会尖刺——那是调度器在追负载，不是建议把 $\gamma$ 钉死在 11。核与通信形状的正本在 [6.1.8 / 08](../../../6-训练与推理优化/6.1-训练基础设施/6.1.8-MoE系统与并行/08-MoE系统优化综述/08-MoE系统优化综述.md)。

稀疏计算的另一面：一次前向只动 $k$ 个专家，**全部 $N$ 份权重仍要在 VRAM 里**（专家并行时拆到多卡，每卡仍扛自己那份）。

![VRAM 驻留全部稀疏参数，计算只走激活专家](./images/fig-moe-vram-sparse-vs-active.png)

> 图 9：左栏 GPU 里 Expert 1…E 的权重都在；右栏 Top-K 只把 Expert $i$、$j$ 送进求和。无 GB 刻度。

**图 9 解析**

- 左：VRAM 网格写着 Expert 1 Weights … Expert E Weights。底下那句 All sparse parameters resident 是显存账，不是 FLOPs 账。
- 右：Router (Top-K) 下面灰专家虚线、绿专家实线，绿的进 $+$。
- 读图：参数量和激活量必须分开报。Mixtral 8×7B 论文写总参约 $46.7\,\mathrm{B}$、每 token 约 $12.9\,\mathrm{B}$（Jiang et al., 2024）；那是激活量，不是「显存只要 13B」。

## 6. LLM 主线里的架构分叉：DeepSeekMoE 与 Upcycling

DeepSeekMoE（Dai et al., 2024）在 Token-Choice 上加了两刀，被后来的开源 MoE 大量沿用：

1. **细粒度切分**：把原来「复制一份宽 FFN」改成更多、更窄的专家，总参数预算不变、组合数变多。
2. **共享专家隔离**：少数专家对每个 token 强制激活，扛通用计算，减少路由专家互相抄同一套「谁都用得到」的知识。

![DeepSeekMoE：(a) Top-2 (b) 细粒度 (c) 再加共享专家](./images/fig-deepseekmoe-panels.png)

> 图 10：(a) 传统宽专家 Top-2；(b) 切细之后仍 Top-2；(c) 再加 always-on 共享专家（实线）。

**图 10 解析**

- 三列都从底部 Token / Hidden State 向上，经黄色 Router，到 Sum，再到 Output。
- (a) 两个宽 FFN，虚线 Top-2 全开——这是 Mixtral 那种「少数大专家」。
- (b) 一排窄条 $E_1\ldots E_N$，只有两条绿。同样激活两条，但专家池更大。
- (c) 右边多一块 Shared Expert Always-On，实线不经 Top-K。Sum 收的是「共享 + 被选中的路由专家」。
- V1–V3 的 $N_s$、$N_r$、$K_r$ 在 [01](./01-DeepSeek-MoE/01-DeepSeek-MoE.md)。

Upcycling（Komatsuzaki et al., 2022）是把已训好的稠密 MLP **复制**成 $E$ 份专家，路由器从零训。注意力子层不动。

![稠密 MLP 复制为专家，路由器从零训](./images/fig-moe-upcycling.png)

> 图 11：左稠密块的 MLP 权重复制到右栏多个专家；Router 新训。不是从零随机初始化全部专家。

**图 11 解析**

- 左：LN → 自注意力 → 残差，再 LN → 单个 MLP。
- 中：两条标注 copy weights to experts / train router。
- 右：MLP 换成 Router + 四个 copied MLP。注意力子层两边一样。
- 本页不绘「额外训练时间 vs 准确率」假坐标。读论文 Figure，不要用示意曲线当消融。

## 7. 不是本库 LLM 主线：V-MoE / Soft-MoE

这两条出现在视觉 Transformer 里。LLM 主线仍是 Token-Choice 稀疏门控。留下是为了分清「软」字：1991 的软混合是全体专家都算；2023 的 Soft-MoE 是 token 在槽位上做加权混合，**仍然每个专家都跑**，和 Switch 的稀疏不是同一件事。

### 7.1 V-MoE：patch 当 token，容量不够就按重要性丢

ViT 把图切成 patch，展平投影成 token，再进 Transformer。V-MoE（Riquelme et al., 2021）把其中的 FFN 换成稀疏 MoE。一张图的 patch 数很多，专家容量设低就会溢出；Batch Priority Routing 按重要性分数先给主体 patch 占槽，背景更容易被丢。

![ViT：图片切成 patch 再当 token 进编码器](./images/fig-vit-patches.png)

> 图 12：线稿示意，不是照片。$4\times 4$ patch 按光栅序变成 16 个 token，线性投影后进 Transformer Encoder。

**图 12 解析**

- 左：猫的线稿上叠 $4\times 4$ 虚线格，行列 0–3。
- 中：16 个 patch 横排，每个下面一个 E（patch embedding）。
- 下：Encoder 输出仍是 16 个位置。MoE 替换的是 Encoder **里面的 FFN**，不是这个切块步骤。

![V-MoE 批量优先：高重要性 patch 先占专家容量](./images/fig-vmoe-priority.png)

> 图 13：高重要性（主体）先入专家槽；低重要性（背景）在容量满时进 Overflow。

**图 13 解析**

- 左 16 个 patch：绿=主体，灰=背景。
- 中：按重要性排队。三个专家、每专家容量 4，十二个槽先被绿的占满。
- 右 Overflow：灰的背景进这里。和 图 8 同一种容量物理，只是丢弃顺序改成「不重要的先丢」。
- 不要把这张图当成 LLM 文本 MoE 的默认路由。文本没有现成的「主体 / 背景」分数。

### 7.2 Soft-MoE：槽位上的加权混合，没有离散丢弃

Soft-MoE（Puigcerver et al., 2023）让每个专家处理全部 token 的加权混合，而不是离散地接 $K$ 个 token。没有 Top-K 丢弃，梯度是连续的；代价是稀疏激活这条初衷被拿掉——每个专家都在算。

![Soft-MoE：所有 token 软混合进每个专家，无离散丢弃](./images/fig-soft-moe.png)

> 图 14：矩阵里的小数是示意权重，不是论文表。行和为 1。

**图 14 解析**

- 左：$x_1,\ldots,x_T$。中：$W\in\mathbb{R}^{T\times E}$，示例第一行 $0.24,0.31,0.22,0.23$。
- 每个专家吃到的 $s_i$ 是全体 $x$ 的加权和，不是某一个 token。
- 右：专家输出再混合回 $\hat x_t$。没有虚线 overflow。
- 和式 (1) 的软混合同类：算力按 $N$ 走，不按 $k$ 走。LLM 要省 FLOPs 时不走这条。

## 8. 失效模式

| 现象 | 原因 | 说明 |
|------|------|------|
| 专家坍塌 | Token-Choice 无均衡 | $f_i$ 集中；式 (9) 或 aux-loss-free 偏置就是在打这个 |
| $\gamma=1$ 仍大量 drop | 局部溢出 | 总槽数够也不够：热专家先满。先查 $f_i$，再加 $\gamma$ |
| token 溢出 | $\gamma$ 偏小 / 负载更偏 | 残差跳过本层专家；batch 内互相抢槽。不是从序列里删 token |
| 把 $\gamma$ 拉到 $11$ 仍不稳 | Tutel 动态容量尖刺 | MegaBlocks：与其堆 padding，不如变长 block-sparse |
| 微调丢 $10\%$ token 就慌 | 预训练直觉套用错阶段 | ST-MoE Table 5：微调对 drop 不敏感；aux-loss 仍建议开 |
| 路由翻转、损尖峰 | logits 过大、低精度 Softmax | 式 (11) + Router FP32。Switch Table 2：整网 bf16 会发散 |
| 用 clip 代替 z-loss | 舍入已经发生 | ST-MoE：紧 update clip 稳定但质量崩 |
| 把式 (9) 写进推理 | 训练正则误当门控 | $L_{\mathrm{balance}}$ / $L_z$ 只加在训练损失 |
| 把 Expert-Choice 的 $c$ 当成 Switch 的 $\gamma$ | 记号撞车 | 前者是每 token 平均专家数，后者是均匀分流之上的缓冲倍数 |
| 小数据 SFT 过拟合 | 稀疏总容量大、激活路径多 | 不要指望几条样本把所有专家都训到位 |
| 把 $\ell$ 写成 MLA | 两个「潜空间」同名 | LatentMoE 的 $\ell$ 在 FFN；MLA 的 $c^{KV}$ 在注意力 |

MiniMax-M2 用 sigmoid 门、每 token 8/256 细粒度专家，对照 Softmax Top-$K$；产品捆在 [MiniMax-M2 正本](../../../05-模型家族与选型/5.3-模型家族/minimax/minimax-m2/minimax-m2.md)，不在这页展开。

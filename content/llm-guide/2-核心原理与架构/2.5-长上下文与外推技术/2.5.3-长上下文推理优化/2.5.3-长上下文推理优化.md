## 太长不看版

- 推理分两段, 瓶颈不同. **prefill** 一次处理整个 prompt, 是计算瓶颈, 注意力 FLOPs 随长度平方增长; **decode** 每步生成一个 token, 是带宽瓶颈, 每步要把权重和整个 KV Cache 从显存读一遍.
- KV Cache 每 token 字节数 $=2\times n_{\text{layer}}\times n_{kv}\times d_h\times$ 每元素字节数. Llama-2-7B (32 个 KV 头) 每 token 512KB, 128k 时 64GB; Llama 3 8B (GQA, 8 个 KV 头) 每 token 128KB, 128k 时 16GB, 和 bf16 权重一样大.
- 手算 Llama 3 8B 的 prefill: 约 60k token 以上注意力 FLOPs 超过线性层; 1M token 时注意力占 94%, 按 A100 峰值算也要约 15 分钟. MInference 报告的实测是 30 分钟.
- **减小 KV**: GQA / MLA 从结构上减少每 token 的 KV; **KIVI** 把 KV 量化到 2 bit, Key 按通道量化, Value 按 token 量化, 峰值显存 (含权重) 降 2.6 倍, 吞吐提升 2.35–3.47 倍.
- **prefill 稀疏**: **MInference** 把注意力头分成 A 形, 竖线-斜线, 块稀疏三种模式, 离线为每个头选模式, 在线用最后一段 query 估计稀疏索引. LLaMA-3-8B 在单张 A100 上 1M prefill 从 30 分钟降到 3 分钟.
- **decode 少读 KV**: 驱逐类 (StreamingLLM 保留 4 个起始 token 加滑动窗口) 显存恒定, 但窗口外的信息永久丢失; 检索类 (**InfLLM**) 把远处 KV 分块放在 CPU, 每步按代表 token 取回相关的块, 信息不丢, 代价是检索开销和召回误差.
- **多卡**: Ring Attention 把 KV 块在环上传递, 通信和计算重叠; Llama 3 训练用的上下文并行改为先 all-gather K, V, 理由是 GQA 下 K, V 比 Q 小得多, 而且便于支持文档掩码.

## 1. 问题: 长上下文推理贵在哪里

### 1.1 KV Cache 的大小

自回归生成时, 每层要缓存所有历史 token 的 Key 和 Value. 每个 token 占用:

$$
M_{\text{token}}=2\times n_{\text{layer}}\times n_{kv}\times d_h\times p
\tag{1}
$$

$n_{kv}$ 是 KV 头数, $d_h$ 是单头维度, $p$ 是每元素字节数 (fp16/bf16 为 2). 整个缓存为 $M_{\text{token}}\times n\times B$, $n$ 是上下文长度, $B$ 是 batch.

手算几个模型 (bf16, $d_h=128$; Llama 3 的层数和 KV 头数取自其论文表 3):

| 模型 | 层数 | KV 头数 | 每 token | 128k | 1M |
|---|---:|---:|---:|---:|---:|
| Llama-2-7B (MHA) | 32 | 32 | 512 KB | 64 GB | 512 GB |
| Llama 3 8B (GQA) | 32 | 8 | 128 KB | 16 GB | 128 GB |
| Llama 3 70B (GQA) | 80 | 8 | 320 KB | 40 GB | 320 GB |
| Llama 3 405B (GQA) | 126 | 8 | 504 KB | 63 GB | 504 GB |

以 Llama 3 8B 为例: $2\times32\times8\times128\times2=131072$ 字节. 128k 上下文的 KV Cache (16GB) 已经等于 8B 参数的 bf16 权重 (约 16GB). batch 为 8 时 KV 是权重的 8 倍. 到 1M 上下文, 即使 batch 为 1, 128GB 的 KV 也超过单张 80GB 显卡的容量, 要么量化 (第 2 节), 要么只把一部分 KV 留在 GPU 上 (第 4 节), 要么切到多卡 (第 5 节).

### 1.2 Prefill 的计算量

prefill 一次性处理 $n$ 个 token. 线性层 (投影和 FFN) 每 token 约 $2N$ FLOPs ($N$ 为参数量), 总量随 $n$ 线性增长. 注意力的 $QK^\top$ 和 $AV$ 两次矩阵乘, 在因果掩码下第 $t$ 个 token 约 $4td$ FLOPs ($d$ 为模型维度), 对 $t$ 求和:

$$
F_{\text{attn}}\approx n_{\text{layer}}\times 2d\times n^2,\qquad F_{\text{linear}}\approx 2N\times n
\tag{2}
$$

两者相等时 $n^\ast=N/(n_{\text{layer}}\,d)$. Llama 3 8B: $N\approx8\times10^9$, $n_{\text{layer}}=32$, $d=4096$, 得 $n^\ast\approx6.1\times10^4$. 也就是说, 约 60k token 以上, prefill 的主要开销从线性层转到注意力.

1M token 时: $F_{\text{attn}}\approx32\times8192\times10^{12}\approx2.6\times10^{17}$, $F_{\text{linear}}\approx1.6\times10^{16}$, 注意力占约 94%. 总量约 $2.8\times10^{17}$ FLOPs, 按 A100 的 bf16 稠密峰值 312 TFLOPS 算要约 900 秒. [MInference](https://arxiv.org/abs/2407.02490) 报告 8B 模型在单张 A100 上 prefill 1M token 需要 30 分钟, 300k token 需要 6 分钟. 用户要等这么久才看到第一个 token.

FlashAttention 不改变这个 FLOPs 量, 它解决的是显存读写和 $n\times n$ 矩阵的显存占用 (见 2.3.1). 要降 FLOPs, 只能少算: 稀疏化 (第 3 节) 或换掉 softmax 注意力 (第 6 节).

### 1.3 Decode 的带宽

decode 每步只算一个 token, 计算量小, 但要把全部权重和 KV Cache 从 HBM 读进来. 以 Llama 3 8B, 128k 上下文, batch 1 为例, 每步读约 16GB 权重加 16GB KV. A100 80GB 的 HBM 带宽约 2TB/s, 每个 token 的下界约 16ms. batch 增大时权重读取被分摊, KV 读取不分摊: batch 8 时每步读 16GB 权重加 128GB KV, KV 占九成.

所以长上下文 decode 的优化方向是: 让每 token 的 KV 变小 (第 2 节), 或者每步只读一部分 KV (第 4 节).

### 1.4 方法地图

| 瓶颈 | 手段 | 是否需要训练 | 本文 / 链接 |
|---|---|---|---|
| KV 容量和带宽 | GQA, MQA, MLA | 是 (结构) | 2.1 节, 2.3.1, 2.3.5 |
| KV 容量和带宽 | KV 量化 (KIVI) | 否 | 2.2 节 |
| prefill 计算 | 动态稀疏 (MInference) | 否 | 第 3 节 |
| decode 带宽 | 驱逐 (StreamingLLM, H2O, SnapKV) | 否 | 4.1 节, 2.3.2 |
| decode 带宽 | 检索式 (InfLLM, Quest) | 否 | 4.2 节, 2.3.2 |
| 单卡放不下 | Ring Attention, 上下文并行 | 否 | 第 5 节 |
| 两段都有 | 训练期稀疏 (NSA, MoBA), 混合线性注意力 | 是 | 第 6 节, 2.3.2, 2.3.3 |

## 2. 减小每个 token 的 KV

### 2.1 结构: GQA 与 MLA

GQA 让多个 query 头共享一组 KV. 1.1 节的表里, Llama-2-7B 到 Llama 3 8B 的 KV 从 512KB 降到 128KB, 全部来自 KV 头数从 32 降到 8. MLA 把 KV 压成低秩潜向量, DeepSeek-V2 每层每 token 缓存 $512+64$ 个元素 (见 2.3.5 和 2.1.4 的 02 篇第 6 节). 按式 (1) 的口径手算: DeepSeek-V2 共 60 层, bf16 下每 token $576\times2\times60=69120$ 字节, 约 67.5KB, 128k 上下文约 8.4GB. 它的总参数是 236B, 每 token 的 KV 却只有 Llama 3 8B 的一半左右. 这些要在预训练时就定下来, 已训练好的模型不能直接换.

### 2.2 量化: KIVI

[Liu et al. (2024)](https://arxiv.org/abs/2402.02750) 用的是逐组的非对称整数量化. 一组元素 $X$ 量化到 $B$ bit:

$$
Q(X)=\left\lfloor\frac{X-z_X}{s_X}\right\rceil,\qquad z_X=\min X,\quad s_X=\frac{\max X-\min X}{2^B-1}
\tag{3}
$$

关键在于「一组」沿哪个方向取. KV Cache 是 token × 通道的矩阵, 可以按 token 分组 (同一 token 的若干通道共用 $z,s$), 也可以按通道分组 (同一通道的若干 token 共用 $z,s$). 原文图 2 统计了 Llama-2-13B 和 Falcon-7B 的 KV 数值: Key 有少数通道数值很大, Value 没有明显的离群模式. 按 token 分组时, 一个大数值通道会把整组的 $s_X$ 撑大, 其余通道的精度被挤掉; 按通道分组, 离群通道自成一组, 不影响别的通道.

原文表 1 在 Llama-2-13B 上做了模拟量化 (组大小 32, 量化后立即反量化):

| 配置 | CoQA | TruthfulQA |
|---|---:|---:|
| 16 bit | 66.37 | 29.53 |
| 4 bit, Key 按 token, Value 按 token | 66.48 | 29.51 |
| 2 bit, Key 按 token, Value 按 token | 52.93 | 24.98 |
| 2 bit, Key 按通道, Value 按通道 | 2.88 | 0.74 |
| 2 bit, Key 按 token, Value 按通道 | 2.80 | 0.26 |
| 2 bit, Key 按通道, Value 按 token | 63.53 | 28.60 |

4 bit 时常规的按 token 量化就够了; 降到 2 bit, 只有「Key 按通道, Value 按 token」还能用, Value 一旦按通道量化就完全失效.

Value 没有离群通道, 为什么按通道也不行? 原文 3.2 节的解释是注意力的稀疏性. 输出是 Value 按注意力权重的加权和, 而权重高度稀疏, 输出实际由少数重要 token 的 Value 决定. 按 token 量化把误差限制在各自的 token 内, 其他 token 的误差不影响重要 token; 按通道量化时一组跨越多个 token, 重要 token 的精度被同组其他 token 拉低. 表 2 的统计: 注意力输出的相对误差, 按 token 为 3.55, 按通道为 49.89. Key 这边, 按 token 量化的注意力分数相对误差 (47.00) 约是按通道 (9.60) 的 5 倍.

按通道量化要跨多个 token 才能分组, 和逐 token 生成冲突. KIVI 的处理是把最近的 $R$ 个 token (残差长度) 保持全精度, 攒满 $R$ 个后整组量化, 并入已量化的部分. Value 按 token 量化本来就能逐个追加, 同样保留最近 $R$ 个全精度的 token, 用一个队列滚动.

套到 1.1 节的 Llama 3 8B: 128k 上下文的 KV 从 bf16 的 16GB 降到 2 bit 的约 2GB, 再加上每组的缩放因子, 零点和最近 $R$ 个全精度 token 的少量开销.

结果: 2 bit, 不需要调参, Llama, Falcon, Mistral 质量几乎不变; 峰值显存 (含权重) 降 2.6 倍, batch 最多可大 4 倍, 实际推理负载吞吐提升 2.35–3.47 倍.

边界: 量化只缩小常数, KV 仍随长度线性增长, prefill 的平方计算量也不变. 反量化要并进注意力内核才不吃掉带宽收益.

## 3. Prefill 稀疏: MInference

### 3.1 观察

MInference 在 LLaMA-3-8B 上分析 128k 上下文的注意力矩阵, 发现两点:

1. 注意力高度稀疏. 128k 时最高 96.8% 的权重可以忽略; 每个 query 只取 top-4096 列, 就能覆盖绝大部分注意力分数.
2. 稀疏的位置是动态的. 同一个头在不同输入上, top-k 的列不同; 拿别的样本的 top-k 索引来用, 覆盖率明显下降. 但同一个头的「形状」在不同输入上相对稳定.

于是问题拆成两步: 离线确定每个头的形状, 在线确定具体位置.

### 3.2 三种模式

| 模式 | 形状 | 位置是否随输入变 | 在线开销 |
|---|---|---|---|
| A 形 (A-shape) | 开头几个 token 加局部窗口 | 不变 | 无, 掩码静态 |
| 竖线-斜线 (Vertical-Slash) | 若干固定 key 列 (竖线) 加若干固定距离的对角线 (斜线) | 变 | 用最后一段 query 估计 |
| 块稀疏 (Block-Sparse) | 分散但空间上成簇 | 变化最大 | 块均值估计 |

A 形就是 StreamingLLM 观察到的注意力汇聚 (4.1 节) 加局部窗口. 块稀疏的依据是空间聚集: 原文统计 128k prompt 里非零注意力与最近的非零邻居的距离, 跨层跨头都集中在 5 左右.

### 3.3 做法

1. **离线搜索** (每个模型一次): 给每种模式设一个计算预算相近的参数空间 (竖线和斜线各几条, 块稀疏取 top 几个块), 在样本上比较各头在同样实际内核 FLOPs 下能召回多少注意力分数, 选最好的模式和参数.
2. **在线建索引**:
   - 竖线-斜线头: 用最后 $\text{last\_q}$ 个 query 和全部 key 相乘, 得到估计的注意力矩阵, 按列求和选竖线, 按对角线求和选斜线.
   - 块稀疏头: 对 $Q$, $K$ 每 64 个取均值, 算块级分数, 取 top-k 块.
   - A 形头: 掩码固定, 不用估计.
3. **稀疏计算**: 竖线-斜线用 $1\times64$ 的块, 其他用 $64\times64$ 的块, 用专门的 GPU 内核.

### 3.4 效果与边界

原文在 LLaMA-3-8B-1M, GLM-4-9B-1M, Yi-9B-200K 上测了 InfiniteBench, RULER, PG-19, NIAH, NIAH 还测了 Phi-3-Mini-128K 和 Qwen2-7B-128K. 注意力 FLOPs 减少约 95%, LLaMA-3-8B 在单张 A100 上 1M prefill 最高加速 10 倍, 从 30 分钟到 3 分钟, 准确率持平或略好.

边界:

- 不改预训练, 不微调, 直接套在已有模型上; 但每换一个模型, 都要重新做一次离线的模式搜索.
- 只加速 prefill. decode 阶段仍要读完整 KV, 1.3 节的问题不变.
- 估计索引有开销, 上下文较短时稀疏的收益抵不过开销; 收益随长度增加.
- 离线搜索在特定样本上做, 输入分布差异大时, 头的模式可能不再适用.

## 4. Decode 时少读 KV

### 4.1 驱逐: 永久丢弃

驱逐类方法在 KV 达到预算后丢掉一部分, 显存和每步读取量都封顶.

[StreamingLLM](https://arxiv.org/abs/2309.17453) 的出发点是滑动窗口失效的原因. 只保留最近 $L$ 个 token 的 KV, 一旦第一个 token 被挤出窗口, 困惑度立即飙升. 作者发现开头几个 token 无论语义是否重要, 都吸收了大量注意力 (attention sink). 保留 4 个起始 token 的 KV 加滑动窗口, Llama-2, MPT, Falcon, Pythia 就能稳定处理 400 万 token 以上的流式输入, 比带重算的滑动窗口快最多 22.2 倍.

开头 token 为什么会吸收注意力: softmax 要求每行权重和为 1, 当前 query 和所有 key 都不太相关时, 多出来的权重也得放在某处. 在因果掩码下, 开头的 token 对之后所有位置都可见, 训练中最容易被学成这个「放多余权重的地方」. 把它们挤出窗口, softmax 的分母少了一大块, 剩下的权重分布整体偏移, 模型就崩了. 作者还验证了在预训练时加一个专门的占位 token 当注意力汇聚点, 能进一步改善流式部署.

一个实现细节和 2.5.1 的位置问题直接相关: 位置编号按缓存内的位置分配, 而不是原文中的位置. 缓存里是 token $[0,1,2,3,6,7,8]$, 解码第 9 个时, 位置赋为 $[0,\dots,7]$ 而不是 $[0,1,2,3,6,7,8,9]$. 对 RoPE, 这要求缓存旋转前的 Key, 每步重新施加旋转. 这样相对距离永远不超过缓存大小, 不会越界.

边界: 原文的 StreamEval 实验显示, 问题和答案的距离在缓存范围内时准确率保持, 超出缓存后降到零. StreamingLLM 解决的是「无限长输入下不崩」, 不扩大能用上的上下文.

H2O (累积注意力高的 token 和最近 token 各占一半预算), SnapKV (prefill 后用 prompt 末尾的观测窗为每个头选出要保留的 KV), PyramidKV (按层递减预算) 等改进了「留哪些」的规则, 但都是一次删除不可恢复. 后面的问题如果需要被删掉的信息, 就答不出来. 细节见 [2.3.2](../../2.3-高效与稀疏注意力/2.3.2-稀疏与压缩注意力/2.3.2-稀疏与压缩注意力.md) 的推理期 KV 压缩部分.

### 4.2 检索: 不删, 按需取

检索类方法保留全部 KV, 但每步只把相关的一部分放进注意力计算.

[InfLLM](https://arxiv.org/abs/2402.04617) (清华大学等) 认为模型读不了超长输入有两个原因: 位置越界, 以及大量无关上下文对注意力的干扰. 它把历史 KV 分成三段: 开头的 initial tokens, 中间被移出窗口的 evicted tokens, 最近的 local tokens. 中间段按连续的 $l_{bs}$ 个 token 分成记忆块. 每个块选 $r_k$ 个代表 token, 选法是看块内每个 token 在局部窗口里收到的注意力分数, 取最高的几个. 每一步用当前 query 和各块的代表 token 算相关度, 取回最相关的若干块, 和开头, 局部窗口拼成注意力的上下文.

工程上, 大部分记忆块放在 CPU 内存, GPU 上只留代表 token 和当前要用的块, 再加一个块缓存利用相邻步的局部性. 序列极长时, 代表 token 也可以放到 CPU 上建 k 近邻索引.

位置编码上, 局部窗口之外的所有 token 共用同一个位置, 思路和 2.5.1 的 Self-Extend / ReRoPE 相同, 避免取回的不连续块和连续位置不匹配.

原文配置: 编码块大小 512, 记忆块 $l_{bs}=128$, 代表 token $r_k=4$, 局部窗口 4k, Mistral 版每步取 96 个块, Llama-3 版取 32 个, 开头保留 128 个 token.

手算每步实际参与注意力的长度. Mistral 版: $128+96\times128+4096=16512$, 约 16k; Llama-3 版: $128+32\times128+4096=8320$, 约 8k, 正好在 Llama-3-8B-Instruct 的 8k 原生窗口附近. 也就是说, 不论输入多长, 每步注意力只算这么多 key; 显存里常驻的是这部分加上所有块的代表 token.

∞-Bench 上的结果 (原文表 1, 该基准文本长度的 95% 分位数为 214k; R.PK, R.Num, R.KV 分别是 passkey, 数字, 键值检索):

| 方法 | 窗口 | R.PK | R.Num | R.KV | QA | 平均 |
|---|---:|---:|---:|---:|---:|---:|
| Mistral-7B 原始 | 32k | 28.8 | 28.8 | 14.8 | 12.9 | 25.2 |
| NTK | 128k | 100.0 | 86.8 | 19.2 | 16.9 | 44.3 |
| Self-Extend | 128k | 100.0 | 100.0 | 15.6 | 17.3 | 44.8 |
| StreamingLLM | 32k | 28.8 | 28.5 | 0.2 | 11.5 | 21.5 |
| H2O | 32k | 8.6 | 4.8 | 2.6 | 15.6 | 18.7 |
| InfLLM | 16k | 100.0 | 96.1 | 96.8 | 15.7 | 57.7 |
| Llama-3-8B 原始 | 8k | 8.5 | 7.8 | 6.2 | 15.5 | 18.4 |
| Self-Extend | 128k | 100.0 | 100.0 | 0.2 | 8.6 | 38.0 |
| InfLLM | 8k | 100.0 | 99.0 | 5.0 | 19.5 | 45.0 |

几点观察. NTK 和 Self-Extend 把窗口拉到 128k 后, passkey 能取回, 但键值检索和问答没有明显改善; Llama-3 上 NTK 全面崩溃 (平均 1.3). 原文的解释是这类方法只解决了位置越界, 没有处理大量无关上下文对注意力的干扰, 而且计算量和显存仍按全长度算. 驱逐类的 StreamingLLM 和 H2O 在检索任务上都接近原始模型甚至更差, 被删掉的信息取不回来, 和 4.1 节一致. InfLLM 在 Mistral 上的键值检索 (96.8) 远高于其他方法, 在 Llama-3 上却只有 5.0, 说明代表 token 的召回质量依赖模型. 原文表 2 还和在长序列上继续训练过的 Llama-3-8B-Instruct-Gradient-1048k 对比: 后者键值检索 23.2, 显存 76.6G, 耗时 40.4s; InfLLM 键值检索 5.0, 显存 26.3G, 耗时 26.7s; 把 InfLLM 叠加到这个长训练模型上, 键值检索升到 55.8, 显存和耗时与 InfLLM 相同.

边界:

- 代表 token 是对块的粗糙概括, 相关信息分散在块内非代表 token 上时可能召回不到.
- CPU-GPU 传输进入关键路径, 相邻步需要的块差别大时缓存命中率下降.
- 共用一个位置意味着远处块之间的先后顺序丢失.

Quest 是同一思路在 GPU 内的版本: KV 按页存每维 key 的最小值和最大值, 用当前 query 估每页分数的上界, 只读 top-k 页 (见 2.3.2).

### 4.3 两类的取舍

| | 驱逐 (StreamingLLM, H2O, SnapKV) | 检索 (InfLLM, Quest) |
|---|---|---|
| 显存 | 封顶 | 不减少 (可以下放到 CPU) |
| 每步读取 | 封顶 | 封顶 |
| 被丢掉的信息 | 永久丢失 | 后面还能取回 |
| 额外开销 | 打分和删除 | 每步检索, 可能有 CPU-GPU 传输 |
| 适合 | 流式对话, 只关心最近内容 | 长文档问答, 后面的问题依赖前面任意位置 |

## 5. 多卡切分

单卡放不下一个序列的激活或 KV 时, 要沿序列维切到多卡上.

**Ring Attention** ([Liu et al., 2023](https://arxiv.org/abs/2310.01889)): 每张卡持有一段 query 和对应的 KV. 各卡把自己的 KV 块传给环上的下一张卡, 同时用当前手里的 KV 块算分块注意力 (和 FlashAttention 一样在线合并 softmax). 传 $P-1$ 轮后每段 query 见过全部 KV. 只要每块的计算时间不短于传一块 KV 的时间, 通信就被计算掩盖. 能处理的长度随卡数线性增长.

掩盖的条件可以算出来. 设块大小 $c$ 个 token, 隐藏维度 $d$, 每卡算力 $F$ FLOPS, 卡间单向带宽 $B$. 一块的注意力计算是 $QK^\top$ 和 $AV$ 各 $2dc^2$, 共 $4dc^2$ FLOPs; 要传的 K, V 块共 $4cd$ 字节 (bf16). 计算时间不短于通信时间:

$$
\frac{4dc^2}{F}\ge\frac{4cd}{B}\quad\Longrightarrow\quad c\ge\frac{F}{B}
\tag{4}
$$

块大小要大于「算力 / 带宽」. 每卡要同时存当前的 Q 块, K, V 块, 正在接收的 K, V 块和输出块, 共 6 块, 所以每卡的序列至少是 $6c$. 原文表 2 的手算: A100 用 NVLink (300GB/s) 时 $c\ge312\times10^{12}/(300\times10^9)\approx1.0\text{k}$, 每卡序列至少 6.2k; 改走 InfiniBand (12.5GB/s) 时 $c\ge24.5\text{k}$, 每卡至少 149.5k. 跨机时环形重叠的门槛高得多.

显存方面, 每卡的激活只和块大小有关 (原文表 1 中为每层 $6bch$ 字节, $b$ 为 batch, $h$ 为隐藏维度), 与总序列长度无关. 总长度要翻倍, 就把卡数翻倍.

**all-gather 上下文并行** (Llama 3 训练): Llama 3 把序列切成 $2\times CP$ 块, 第 $i$ 张卡拿第 $i$ 块和第 $2\times CP-1-i$ 块, 让因果掩码下各卡的计算量均衡. 因果掩码下第 $j$ 块的 query 要和前 $j+1$ 块的 key 算注意力, 靠后的块计算量大. 手算 $CP=2$: 序列切成 4 块, 计算量大致正比于 $0.5, 1.5, 2.5, 3.5$ (块内是三角形, 记半块). 第 0 张卡拿第 0, 3 块, 合计 4; 第 1 张卡拿第 1, 2 块, 也是 4. 如果按顺序切成两半, 两张卡的比例是 $2:6$. 它没有用环形传递, 而是先 all-gather 全部 K, V, 再算本地 query 的注意力. 原文给的理由:

1. all-gather 的实现更容易支持各种注意力掩码, 比如 2.5.2 第 6 节的文档掩码.
2. GQA 下 K, V 比 Q 小得多, all-gather 的通信延迟虽然暴露在关键路径上, 但量小. 注意力计算是 $O(S^2)$, all-gather 是 $O(S)$, 前者大一个数量级以上.

两者的区别在于是否把通信藏进计算. KV 头数少的模型, 直接 all-gather 更简单; KV 大, 或者卡间带宽低时, 环形传递的重叠更有价值.

推理时的 prefill 也可以这样切. decode 阶段每步只有一个 query, 计算量不足以掩盖通信, 收益主要在于把 KV 分散到多卡的显存里.

## 6. 改架构: 训练期稀疏与混合线性注意力

第 2–5 节都不改模型. 如果可以在预训练时就改结构, 还有两类做法, 都已在 2.3 节单独成篇:

- **训练期稀疏注意力**. MoBA 按块选 top-k, NSA 用压缩, 选择, 滑动窗口三路门控. 稀疏模式在训练中学到, 推理时 prefill 和 decode 都只算选中的部分. 见 [2.3.2](../../2.3-高效与稀疏注意力/2.3.2-稀疏与压缩注意力/2.3.2-稀疏与压缩注意力.md) 的训练期部分.
- **混合线性注意力**. 线性注意力 / SSM 层的状态大小与长度无关, 和少数全注意力层交替排布. KV 只在全注意力层上随长度增长. 见 [2.3.3](../../2.3-高效与稀疏注意力/2.3.3-线性注意力机制/2.3.3-线性注意力机制.md).

和第 3, 4 节的免训练方法相比, 这两类没有「训练时稠密, 推理时稀疏」的分布差异, 但要从预训练开始投入.

## 7. 失效模式

| 现象 | 原因 | 处理 |
|---|---|---|
| 长 prompt 首 token 等待数分钟 | prefill 注意力 $O(n^2)$, 60k 以上占主导 | prefill 稀疏 (MInference), 多卡切分, 前缀复用 |
| batch 上不去, 显存被 KV 占满 | KV 随 $n\times B$ 线性增长 | GQA / MLA (训练时), KV 量化, 分页管理 (2.3.1) |
| 驱逐后后面的问题答不出 | 需要的 KV 已被删除 | 改用检索式; 或把问题放在 prompt 末尾, 让 SnapKV 的观测窗按问题选 KV |
| StreamingLLM 下长距离问答为零 | 答案超出缓存范围 | StreamingLLM 只保证不崩, 长距离依赖用检索式或全量 KV |
| 去掉开头 token 后困惑度飙升 | 注意力汇聚在开头 token 上 | 驱逐时始终保留开头几个 token |
| KV 量化后质量明显下降 | Key 按 token 量化, 离群通道污染整组 | Key 按通道, Value 按 token; 最近 token 保持全精度 |
| 驱逐或检索后位置错乱 | 用原文位置给不连续的缓存编号 | 按缓存内位置编号 (StreamingLLM), 或远处共用位置 (InfLLM); 缓存旋转前的 Key |
| 多卡上下文并行扩展效率低 | 通信未被计算掩盖 | 块够大时用环形重叠; KV 小时用 all-gather |

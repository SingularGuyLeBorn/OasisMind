# 预训练数据收集: 从 Common Crawl 到可训练文本

> 相关阅读: [3.1 预训练数据](../3.1-预训练数据.md) · [3.1.2 合成与改写数据](../3.1.2-数据蒸馏/3.1.2-数据蒸馏.md) · [3.1.3 数据处理](../3.1.3-数据处理/3.1.3-数据处理.md) · [3.3 分词器](../../3.3-分词器与Tokenizer/3.3-分词器与Tokenizer.md)

## 太长不看版

- **网页的起点是 WARC, 不是 WET.** Common Crawl 同时提供原始抓取 (WARC), 元数据 (WAT) 和已抽好的纯文本 (WET). RefinedWeb, FineWeb, DCLM 都从 WARC 自己抽正文. DCLM 在 1B-1x 规模上, resiliparse 抽取的 Core 是 24.1, trafilatura 24.5, WET 只有 20.7; resiliparse 比 trafilatura 快 8 倍.
- **URL 过滤最便宜, 放在最前面.** RefinedWeb 用 460 万个域名的黑名单加 URL 打分. 黑名单里不到 100 个域名是误杀, 但这些域名页数多, 占了被拦数据的一大块.
- **语言识别用 fastText.** lid.176 识别 176 种语言. RefinedWeb 和 FineWeb 保留英语分数 $\ge 0.65$ 的文档; Dolma 沿用 CCNet 的 $\ge 0.5$, 这一步按字节删掉 61.7%.
- **代码要先解决许可.** The Stack v2 基于 Software Heritage 归档, 96.93% 的仓库没有仓库级许可信息, 改用 ScanCode 在文件级检测; 收宽松许可和无许可文件, 排除 copyleft 和商业许可. StarCoder2-15B 的训练集有 913B 去重后的 token.
- **数学要单独抽.** Common Crawl 里的 HTML 没有执行 JavaScript, MathJax 公式仍是带分隔符的源码, 通用抽取器会丢. OpenWebMath 从 2000 亿个 HTML 文档里抽出 14.7B token 的数学网页.
- **公开数据集量级.** RefinedWeb 5T token (公开 600B), FineWeb 15T (96 个快照), FineWeb-Edu 1.3T, DCLM-Pool 240T, DCLM-baseline 3.8T, Dolma 约 3T (Llama 分词器计 3,059B). 各家用的分词器不同, token 数只能看量级.

## 1. 问题: 原始抓取离可训练文本有多远

预训练语料的主体来自网页. 自己写一个能抓几十亿页的爬虫成本很高, 公开数据集几乎都从 [Common Crawl](https://commoncrawl.org/) 出发. Common Crawl 是一个非营利组织, 2007 年起定期抓取公开网页, 每次完整抓取叫一个快照 (snapshot, 命名如 `CC-MAIN-2024-10`). FineWeb 写作时 (2024 年中) 已有 100 个快照, 总量在 PB 级. Dolma 统计 Common Crawl 累计超过 2500 亿页.

从这些快照到一份能直接 tokenize 的文本, 中间要回答五个问题:

1. 用 Common Crawl 的哪种文件, 自己抽正文还是用现成的纯文本.
2. 哪些站点根本不该进来, 能不能只看 URL 就判断.
3. 文档是什么语言, 阈值放多高.
4. 网页以外的来源 (代码, 书, 论文, 数学) 各自怎么取, 许可怎么处理.
5. 这些选择对最终模型差多少, 由什么实验来定.

质量过滤, 去重, 配比属于 [3.1.3](../3.1.3-数据处理/3.1.3-数据处理.md). 本篇讲的是质量过滤之前的部分: 把原始字节变成「一篇篇带语言标签的正文」. 这部分删掉的数据远多于后面: RefinedWeb 在文档准备阶段 (URL 过滤, 抽取, 语言识别) 结束时只剩原始文档的 48%, 主要是语言识别删掉的; 经过质量过滤剩 23%; 去重后合计删掉近 90%.

## 2. Common Crawl 的三种文件

### 2.1 WARC, WAT, WET 各存什么

Common Crawl 自 2013 年夏天起用 WARC (Web ARChive) 格式存数据, 之前是 ARC 格式. 每个快照分成许多 segment, 每个 segment 下有三类文件:

| 文件 | 内容 | 典型用途 |
|------|------|----------|
| WARC | 原始抓取记录. `WARC-Type: response` 存完整的 HTTP 响应 (响应头 + HTML), `request` 存请求, `metadata` 存抓取过程的元数据 | 自己做正文抽取 |
| WAT | 从 WARC 计算出的元数据, JSON 格式: HTTP 头, HTML 的 title, meta, 页面里的链接及链接类型 | 链接图, 域名统计 |
| WET | 从 WARC 抽出的纯文本. 记录头里有 URL, 长度, `warc-identified-content-language`, 正文紧跟其后 | 直接拿文本 |

一个 WARC 文件压缩后约 0.9 GB. Common Crawl 的入门页给的例子是 `CC-MAIN-2018-17` 某个 segment 下的三个文件, 大小分别是 931,210,633, 935,833,042, 940,140,704 字节. 数据放在 AWS 的 `s3://commoncrawl/` 桶 (us-east-1 区域), 外部用 `https://data.commoncrawl.org/` 前缀经 HTTP 免费下载.

DCLM 构建 DCLM-Pool 时取了 2013 到 2022 年的全部 WARC, 共 510 万个文件; 从 HTML 抽出文本后是 2000 亿篇文档, gzip 后 370 TB, 用 GPT-NeoX 分词器计 240T token. 2023 年及以后的快照被刻意排除, 理由是避免大量语言模型生成的文本混进来, 同时留作将来的保留集.

### 2.2 WET 的问题: 导航和菜单都在

WET 用 htmlparser 把整页 HTML 转成文本, 不区分正文和页面框架. Common Crawl 自己给的 WET 示例是维基百科 Saturn 词条, 正文前面是一长串 `Jump to content Main menu Main menu move to sidebar hide Navigation Main page Contents Current events Random article ...`. 这些导航文字在同一站点的每一页都会重复, 后面的去重能删掉一部分, 但会留下大量「每页不同但同样无用」的残片.

FineWeb 的结论是 WET 保留了太多样板和菜单文本. 它在只加 fastText 英语过滤, 不去重的设置下, 用 28B token 训练 1.71B 模型做对照, trafilatura 从 WARC 抽取的版本明显好于 WET (FineWeb 的 Figure 1). 此后 FineWeb 的所有实验都基于 WARC.

## 3. 正文抽取: trafilatura 与 resiliparse

### 3.1 抽取器要做什么

正文抽取 (boilerplate removal) 的输入是一棵 DOM 树, 输出是主体内容的纯文本. 要删的是页眉, 页脚, 导航, 侧栏, 广告, 版权栏, 「阅读更多」按钮. 要保留的是标题, 段落, 列表, 表格里的文字, 以及代码块和公式. 这一步决定了后面的启发式规则能不能起作用: 如果导航行没删干净, 「行尾是否为句号」「短行比例」这类规则会把整篇正常文章判成低质量.

[trafilatura](https://aclanthology.org/2021.acl-demo.15) (Barbaresi 2021) 是一个 Python 库, RefinedWeb 选它的依据是 Lopukhin (2019) 的评测: 在博客和新闻正文抽取上它是最好的非商业库. RefinedWeb 读 WARC 用 warcio, 抽完再用正则做两处格式化: 连续换行最多保留两个, 删掉所有 URL. [resiliparse](https://github.com/chatnoir-eu/chatnoir-resiliparse) (Bevendorff 等人 2018, 2021) 是 Cython 写的 HTML 解析和正文抽取工具包, 配套的 FastWARC 负责快速读 WARC.

### 3.2 两者差多少

DCLM 在 1B-1x 规模 (1B 参数, 按 Chinchilla 的 20 倍参数量取 token) 上比较三种抽取, 抽完都套 RefinedWeb 的启发式过滤 (DCLM Table 3):

| 抽取方式 | Core | Extended |
|----------|------|----------|
| resiliparse | 24.1 | 13.4 |
| trafilatura | 24.5 | 12.5 |
| WET 文件 | 20.7 | 12.2 |

两个抽取器都比 WET 高至少 2.5 个 Core 点, 彼此之间差别不大. DCLM 的解释是 C4, RedPajama, Dolma-V1 都用 WET, 这可能是它们在 DCLM 的数据集对比里落后的部分原因. 最终 DCLM 选 resiliparse, 理由只有一条: 它比 trafilatura 快 8 倍. 对 2000 亿篇文档, 抽取是整条流水线里最贵的 CPU 步骤之一, 8 倍的差距决定了能不能处理完整个 Common Crawl.

这张表也说明了抽取器选择的边界: 两个抽取器之间 0.4 个 Core 点的差距, 在 1B 模型上不一定超过实验噪声; 而 WET 到抽取器的 3 到 4 个点是稳定的. 所以工程上的问题是「要不要自己抽」, 不是「用哪个抽」.

### 3.3 抽取后的行级修正

抽取器不会把每一行垃圾都删干净. RefinedWeb 在 trafilatura 之后又加了一层逐行规则 (RefinedWeb 附录 G.2), 对每一行判断:

- 主要由大写字母组成, 删;
- 只有数字, 删;
- 是计数器 (如 `3 likes`), 删;
- 只有一个词, 删;
- 不超过 10 个词且匹配特定模式 (行首的 `sign-in`, 行尾的 `Read more...`, 行中的 `items in cart`), 改写.

如果被标记的行里的词超过全文词数的 5%, 整篇删掉. RefinedWeb 特别注明这些规则是人工看数据得出的, 换语言要重新调.

## 4. URL 过滤

### 4.1 只看 URL 能拦住什么

URL 过滤不需要下载正文, 是最便宜的一步, 所以放在最前面. RefinedWeb 的 URL 过滤有两条规则:

1. 一份汇总的黑名单, 约 460 万个域名, 来自图卢兹大学维护的 [UT1 黑名单](https://dsi.ut-capitole.fr/blacklists/), 按类别 (色情, 赌博等) 选用. 这份名单原本是给大学网络做访问控制的.
2. URL 打分: 一份人工整理, 按严重程度加权的词表, 检查 URL 里是否出现这些子词. 词表是人工检查后, 对照 ToxicBERT 判为毒性离群的页面整理的.

RefinedWeb 先在 8.32 亿个页面的子集上跑黑名单, 有 604 万个页面 (0.73%) 命中, 每个 URL 的命中次数从 1 到 7.9 万. 作者人工检查了所有命中超过 4000 次的 URL, 发现一批正常域名 (流行文化新闻站, 博客平台) 被误拦. 这类误杀域名不到 100 个, 但页数多, 占了被拦数据里相当大的比例, 删掉它们之后才得到最终名单.

基于词表的规则还有另一类误伤. RefinedWeb 指出, C4 那种「页面里出现脏词表中的任何一个词就删」的规则, 很容易把医疗和法律页面一起删掉.

FineWeb 的基础过滤沿用同一份 UT1 黑名单, 用来去掉成人内容.

### 4.2 为什么还要拦「高质量」站点

RefinedWeb 的 URL 过滤还删了维基百科, arXiv 等常见高质量来源 (附录 G.1.3 列了完整名单, 如 courtlistener.com, reddit.com, uspto.gov, wikipedia.org). 原因是 RefinedWeb 设计成和人工整理的语料一起混用; 如果网页部分里已经有一份维基百科, 再混一份单独处理过的维基百科, 同一内容会出现两次, 采样权重也就失控了. 这条规则说明 URL 过滤的目标取决于下游怎么配比, 不只是去除有害内容.

### 4.3 robots.txt 与站点许可

Common Crawl 的爬虫叫 CCBot, User-Agent 是 `CCBot/2.0 (https://commoncrawl.org/faq/)`. 站点不想被抓, 在 robots.txt 里写 `User-agent: CCBot` 加 `Disallow: /` 即可. Common Crawl 也提醒, 有别的爬虫冒充 CCBot, 现在 CCBot 跑在带反向 DNS 的专用 IP 段上, 站长可以反查验证.

robots.txt 只表达抓取那一刻的意愿. 一份 2019 年的快照里的页面, 不会因为站点 2024 年改了 robots.txt 而从快照里消失. [Consent in Crisis](https://arxiv.org/abs/2407.14933) (Longpre 等人 2024) 审计了 C4, RefinedWeb, Dolma 背后的 14,000 个域名, 发现 2023 到 2024 年一年里限制急剧增多: 按 robots.txt, C4 中约 5% 以上的 token, 以及 C4 里最活跃维护的关键来源中 28% 以上的 token, 已被完全禁止抓取; 若按服务条款 (Terms of Service) 的抓取限制, C4 的 45% 都受限. 论文还发现站点在服务条款里写的意图和 robots.txt 经常不一致. 对数据收集来说, 这意味着「用旧快照」和「重新抓」得到的可用数据量会越来越不同.

## 5. 语言识别

### 5.1 fastText 分类器

几乎所有 Common Crawl 流水线都用 [fastText](https://fasttext.cc/docs/en/language-identification.html) 做文档级语言识别. 官方发布的 lid.176 模型能识别 176 种语言, 训练数据来自 Wikipedia, Tatoeba 和 SETimes; 有两个版本: `lid.176.bin` 126 MB, 稍快也稍准; `lid.176.ftz` 是压缩版, 917 kB. 输入要求是 UTF-8.

fastText 是一个线性分类器 (Joulin 等人 2016, Bag of Tricks for Efficient Text Classification). 文档 $x$ 先被切成词和字符 $n$-gram, 查表得到每个 $n$-gram 的嵌入, 取平均得到文档向量 $\bar h(x)$; 再经一个线性层和 softmax 得到语言分布:

$$
p(\ell\mid x)=\mathrm{softmax}\bigl(B\,\bar h(x)\bigr)_\ell,\qquad \bar h(x)=\frac{1}{|G(x)|}\sum_{g\in G(x)}A_g \tag{1}
$$

$G(x)$ 是文档里所有 $n$-gram 的集合, $A_g$ 是 $n$-gram $g$ 的嵌入行, $B$ 是从嵌入维到 176 个类别的矩阵, $\ell$ 是语言标签. 训练时最小化负对数似然. 推理只有查表, 求平均和一次小矩阵乘, 不需要 GPU, 适合扫整个 Common Crawl. 字符 $n$-gram 让它对没见过的词也能给出判断, 这是语言识别比词袋分类更需要的.

过滤规则是一个阈值: 文档的最高分语言是目标语言, 且 $p(\ell^\ast\mid x)\ge\tau$ 才保留.

### 5.2 阈值放多高

| 数据集 | 模型 | 阈值 $\tau$ | 效果 |
|--------|------|-------------|------|
| RefinedWeb | CCNet 的 fastText (字符 $n$-gram, 维基百科训练, 176 种语言) | 0.65 | 低于 0.65 的通常是没有自然文本的页面 |
| FineWeb | fastText | 0.65 | 沿用 RefinedWeb 的基础过滤 |
| Dolma (经 CCNet) | fastText lid | 0.5 | 按字节删掉 61.7% |
| LLaMA (经 CCNet) | fastText | 0.5 | LLaMA 原文只写用 CCNet 去掉非英语页面; 0.5 是 Dolma 附录对 CCNet 设置的描述 |

0.5 和 0.65 的差别在于短文档和混合语言文档. 一页只有几十个字的商品页, 或一半英文一半代码的技术博客, 最高分可能在 0.5 到 0.65 之间. RefinedWeb 的判断是, 这一区间多是没有自然语言的页面, 所以提高到 0.65.

阈值高了会误删方言和非标准英语. Dolma 在国际英语语料库 (ICE, 九个国家和地区的英语口语与书面语) 上做了外部审计: 这份语料全是英语, 理想情况下应全部判为英语. 在 Dolma 用的 0.5 阈值下, 所有地区的 ICE 文档都被正确判为英语; 阈值提高到 0.90, 多数文档仍被判为英语, 但开始出现被误删的文档 (Dolma 附录 G, Figure 7). Dolma 选择偏宽松的 0.5, 理由就是对非标准英语更友好.

### 5.3 语言识别之后的规则也要按语言调

RefinedWeb 在文档级质量规则一节专门说明: 这些规则 (总长度, 符号与词的比例等) 要按语言分别调整, 照搬英语的阈值会对其他语言过度过滤. 中文没有空格分词, 「平均词长」「每行词数」在中文上的分布和英语完全不同, 直接套 Gopher 规则会出问题. 这部分在 [3.1.3](../3.1.3-数据处理/3.1.3-数据处理.md) 的启发式过滤里展开.

## 6. 跨快照的 URL 去重

同一个 URL 会在多个快照里反复出现, 内容可能没变. 这类重复在收集阶段就可以处理, 不用等到内容去重.

- RefinedWeb 因为算力限制, 把 Common Crawl 切成 100 份, 每份含每个快照的百分之一, 在每份内部做内容去重. 跨份的重复由 URL 去重处理: 记录每份里保留下来的样本 URL, 处理后面的份时把这些 URL 删掉.
- Dolma 的第一步就是精确 URL 去重, 删掉 53.2% 的文档; 第二步精确文档去重, 再删去剩下文档的 14.9%; 第三步精确段落去重, 删掉 18.7% 的段落. 三步都用 Bloom filter.
- FineWeb 在附录 E.3 试过对全部快照做 URL 去重 (每个小写化 URL 只留一篇), 删掉 71.5% 的 token, 剩 5.6T, 下游结果反而比只做逐快照 MinHash 去重差.

FineWeb 的这个结果和直觉相反, 原因在 3.1.3 讲 MinHash 去重时再展开: 对老快照做全局去重后, 留下来的数据质量反而比删掉的差.

## 7. 代码: The Stack v2

### 7.1 来源: Software Heritage 归档

[The Stack v2](https://arxiv.org/abs/2402.19173) (BigCode, 2024) 建在 Software Heritage 归档之上. Software Heritage 是一个以收集和保存全部公开源代码为使命的非营利组织, BigCode 用的是它的图数据集: 一个完全去重的 Merkle DAG, 把文件, 目录, git commit 直到整个仓库的状态连起来. 用这个图而不是直接抓 GitHub, 好处是文件级的精确去重已经由内容哈希完成.

语言识别不再按扩展名, 改用基于 GitHub linguist 的 go-enry 分类器, 在去重后的数据里识别出 658 种语言. BigCode 社区 15 名标注者人工检查了约 1000 个扩展名 (只查文件数超过 1000 且占该语言 0.5% 以上的扩展名), 排除了 130 个扩展名, 连带去掉 39 种语言, 最后剩 619 种编程语言.

规模上 (StarCoder2 报告 Table 1, 32 种常用语言的合计): The Stack v1 去重版 875.85 GB, 1.81 亿个文件; v2 去重版 6,457.14 GB, 7.84 亿个文件; 实际用于 StarCoder2-15B 的 `swh-full` 是 1,922.82 GB, 5.28 亿个文件. v2 去重版里 HTML 一项就有 2,419.87 GB, 训练时只留了 99.09 GB.

### 7.2 许可证判定

代码的许可问题比网页明确: 每个仓库通常有 LICENSE 文件, 但仓库元数据里经常缺. The Stack v2 先从 GHArchive 取仓库级许可, 只有 3.07% 的仓库有; 剩下 96.93% 用 ScanCode Toolkit 在文件级检测:

1. 用正则找所有可能含许可的文件, 包括明确的许可文件 (`LICENSE`, `MIT.txt`, `Apache2.0`) 和提到许可的文件 (`README.md`, `GUIDELINES`);
2. 对这些文件跑 ScanCode 的许可检测, 得到 SPDX 标识;
3. 把检测到的许可传播给仓库中同一路径下的所有文件.

每个文件最后被判成宽松许可, 非宽松许可或无许可三类之一. 宽松许可的名单取自 Blue Oak Council 认可的许可, 加上 ScanCode 归为 Permissive 或 Public Domain 的许可. 和 v1 的主要差别是: v1 只收宽松许可文件, v2 同时收宽松许可和无许可文件; 商业许可因为作者不希望被商用而排除; copyleft 许可因为社区对它能否用于训练的立场不明, 且量不大, 也排除.

开发者可以选择退出. The Stack v1 起就有一个叫「Am I in The Stack」的查询工具. StarCoder2 训练前 BigCode 在 X 上公告, 退出申请截止到 2023 年 11 月 20 日, 之后删除了 91 个用户和组织名下的 1,561 个仓库, 共 22,066 个源代码文件.

### 7.3 清洗与配比

- **近似去重**: 沿用 SantaCoder 的流程, 对所有代码文件算 MinHash, 用 LSH 分桶, 每组重复只留一个; 5-gram, Jaccard 相似度 0.7. 为保留仓库上下文, 优先保留 star 和 fork 多的仓库里的文件, 平局时取最近提交.
- **PII**: 用 StarPII 模型把源代码, PR, issue, StackOverflow 里的姓名, 邮箱, 密钥, 密码, IP 地址, 用户名替换掉.
- **恶意代码**: 用 ClamAV 1.2 加 SaneSecurity 的非官方特征库扫描, 删掉 59,442 个文件, 占 6.54 亿个文件的 0.009%.
- **去污染**: 删掉含 HumanEval, MBPP 的 docstring 或解答, APPS 的 docstring, GSM8K 的题目, DS1000 的 prompt 的文件; 比第一代多做了一步, 匹配前去掉空白, 提高召回.
- **下采样**: Java 和 JavaScript 各压到 200 GB, HTML 压到 100 GB, Markdown 保留 254 GB (预期里面有更多代码文档), JSON, XML, YAML 压到 8 GB.

每条训练样本是一个完整仓库, 文件按随机顺序拼接. 这比按单文件切样本多保留了跨文件引用.

The Stack v2 还配了一组「extras」: PR 19.54B token, issue 11.06B, Jupyter structured 14.74B, Jupyter scripts 16.29B, Kaggle scripts 1.68B, 文档 1.6B, OpenWebMath 14.42B, 维基百科 6.12B, StackOverflow 10.26B, arXiv 30.26B, LHQ (小型高质量数学和代码数据集) 5.78B, 中间表示 (Intermediate Representation) 6B (Table 4). 三个模型的去重后训练集分别是 3B 用 622.09B, 7B 用 658.58B, 15B 用 913.23B; 15B 的训练集是 StarCoderBase 的 4 倍. 3B 和 7B 只用 17 种常用语言的 `smol` 版 (525.5B), 15B 用全部 619 种语言的 `full` 版 (775.48B). 报告的理由是小模型容量有限, 多语言之间会争容量, 不宜见过于分散的数据.

三个模型实际训练 3.3T 到 4.3T token, 远超 Chinchilla 意义上的最优, 但报告控制了对数据集的遍数不超过 5 遍, 依据是 Muennighoff 等人 (2023) 关于数据受限时重复训练的 Scaling Laws. 913B 唯一 token 训 4.3T, 平均约 4.7 遍.

## 9. 数学网页: OpenWebMath

### 9.1 通用流水线为什么丢公式

[OpenWebMath](https://arxiv.org/abs/2310.06786) (Paster 等人 2023) 的出发点是: 已公开的网页数据集在预处理里都没有保住数学符号. 网上的 LaTeX 大多用 MathJax 写: 作者在 HTML 里用 `$...$` 之类的分隔符写源码, 页面加载时 JavaScript 把它们渲染成公式. Common Crawl 抓到的 HTML 没有执行 JavaScript, 公式仍是带分隔符的源码; 抽取器若不认这些分隔符, 就会把公式当普通字符或直接删掉. Minerva 的抽取规则比较简单, 只从几类特定的 HTML 标签里取公式. OpenWebMath 在 Common Crawl 上套用这套规则, 发现这类标签的数量远少于 Minerva 报告的量, 作者推测是 Google 内部抓取的 HTML 与 Common Crawl 不同.

OpenWebMath 通过在 Common Crawl 的小部分数据里过滤含 `\frac` 的文档, 找到了 LaTeX 在网页里的七种编码方式: `equation` 和 `align` 环境; 带 `tex` 等特殊 class 的元素的 alttext; latex.codecogs.com 一类域名的图片 (公式编码在 URL 里); 特定的 WordPress 插件; 嵌套 `<script>` 块的标签; MathML 内容 (用样式表转成 LaTeX); 正文里的 MathJax 公式.

### 9.2 流水线

整条流水线分五段:

1. **预过滤**. Common Crawl 有超过 2000 亿个 HTML 文档, 不能每个都做完整抽取. 先查是否含 tex class, `mathjax` 等字符串; 没有的话, 用正则找反斜杠命令, 再查最常用的 100 个 LaTeX 符号; 还没有的话, 把纯文本送进 MathScore 分类器, 置信度超过 0.8 才保留. 三层由便宜到贵, 召回优先.
2. **抽取**. 先按上面七种方式抽出公式, 再在 DOM 上删不可见元素, 按钮和链接簇, 标注代码, 表格, 标题; 然后用 resiliparse 的 `extract_plain_text(main_content=True)` 取正文; 最后逐行删样板短语, 删空标题, 转义不属于公式的美元符号. 抽取参数是随机化的: 随机选输出纯文本还是 Markdown, 随机选触发删行所需的样板词数, 以增加多样性.
3. **过滤**. fastText 语言识别只留英语; MathScore 给出文档是数学的概率, 抽到了公式的文档要求超过 0.17, 没抽到公式的要求超过 0.8; 用在 ProofPile 上训练的 KenLM 算困惑度, 超过 15,000 的删掉.
4. **去重**. SimHash, 阈值 0.7.
5. **人工检查**. 按文档数和字符数看排名靠前的域名和最长的文档, 把不合格的域名加进黑名单, 删用户资料页, 摘要托管站和搜索结果页.

MathScore 本身是一个 fastText 分类器. 训练标签是「文档是否含最常用的 100 个 LaTeX 命令之一」, 训练时把所有 LaTeX 代码从输入里删掉, 让模型只能从周围的词判断. 这样它能识别「没有可抽取 LaTeX, 但内容是技术性的」页面. 作者人工检查后认为分数低于 0.2 的内容几乎不含有用的数学.

### 9.3 结果

OpenWebMath 有 14.7B token, 略少于 Minerva 私有的 Math Web Pages (17.5B), 和 ProofPile (14.2B, 按 LLaMA 分词器) 量级相当但重叠很少. 字符分布在 131,206 个域名上, 前 100 个域名占 46%. 按文档数, stackexchange.com 占 17.99% (1,136,407 篇), 其次是 physicsforums.com (4.75%) 和 mathhelpforum.com (2.70%); 按这个比例反推总文档数约 630 万.

作者用 1.4B 模型在各数据集上各训 14.7B token 做对照 (OpenWebMath Table 2). MATH Algebra-Easy 准确率: The Pile 2.81%, ProofPile 2.81%, OpenWebMath 5.62%, 两者 50/50 混合 5.06%; 作为参照, 在 The Pile 上训 300B token 的 Pythia 1.4B 是 3.93%. maj@16 上 OpenWebMath 9.55%, 混合 10.11%, Pythia 5.62%. 困惑度 (Table 1) 上, 混合版在 GSM8k 和 MATH 各子类上都最低. 这两张表的规模都很小, 绝对准确率只有个位数, 能说明的是同样 token 数下数学网页的效率更高, 不能直接外推到大模型.

## 10. 四个公开网页数据集对比

把前面的步骤放进同一张表 (各数据集原文):

| | RefinedWeb | FineWeb | DCLM-baseline | Dolma (v1.6) |
|--|-----------|---------|---------------|--------------|
| 规模 | 约 5T token, 公开 600B | 15T (GPT-2 分词器), 96 个快照 | 3.8T, 来自 240T 的 DCLM-Pool | 约 3T (Llama 分词器 3,059B), 网页部分 2.28T 来自 25 个快照 |
| 来源 | 只有网页 | 只有网页 | 只有网页 | 网页 + 代码 + Reddit + 论文 + 书 + 百科 |
| 抽取 | WARC + trafilatura | WARC + trafilatura | WARC + resiliparse | WET (经 CCNet) |
| URL 过滤 | 460 万域名黑名单 + URL 打分 + 拦高质量源 | UT1 黑名单 | 沿用 RefinedWeb | 精确 URL 去重 |
| 语言识别 | fastText, $\ge 0.65$ | fastText, $\ge 0.65$ | 沿用 RefinedWeb | fastText (CCNet), $\ge 0.5$ |
| 质量过滤 | MassiveWeb 规则 + 逐行修正 | MassiveText 规则 + 部分 C4 规则 + 3 条自定义规则; Edu 子集再加分类器 | RefinedWeb 规则 + fastText 分类器取前 10% | Gopher 全部规则 + C4 的句末标点规则 |
| 去重 | MinHash (9000 个哈希) + 精确子串 ($\ge 50$ token) + 跨份 URL | 逐快照 MinHash (112 个哈希) | Bloom filter 近似去重 | Bloom filter: URL, 文档, 段落三级 |

FineWeb 以 ODC-By 1.0 发布, DCLM-Pool 以 CC-BY-4 发布, 两者的数据卡都写明使用时另受 Common Crawl 使用条款约束.

DCLM 在 7B-1x 规模 (6.9B 参数, 138B token) 上比较了四个已有数据集 (DCLM Table 2): C4 的 Core 34.2, Dolma-V1 35.0, RedPajama 35.3, RefinedWeb 36.9. RefinedWeb 只用网页却排第一, 而 RedPajama 和 Dolma-V1 都混了维基百科一类整理过的来源. DCLM 由此采用 RefinedWeb 的启发式规则作为起点. FineWeb 在 1.71B 模型, 350B token 的对比里也报告 FineWeb 好于其他公开网页数据集, FineWeb-Edu 又在 MMLU 和 ARC 上高出一截 (MMLU 从 33% 到 37%, ARC 从 46% 到 57%).

读这张表要注意三点:

1. **token 数不能直接比.** FineWeb 用 GPT-2 分词器计数, DCLM 用 GPT-NeoX, Dolma 用 Llama. 同一份文本在不同分词器下 token 数不同, 跨数据集只能比量级.
2. **「数据集更好」都是在小模型上测的.** FineWeb 的过滤消融用 1.71B 模型训 28B token, DCLM 用 412M 到 7B 的五档规模. DCLM 检查过排名能否外推: 10 种方法在 400M-1x, 1B-1x, 3B-1x 上的分数与 7B-1x 上的分数, Pearson 相关系数分别是 0.838, 0.956, 0.982. 规模越接近, 外推越可靠.
3. **它们都是英语.** 四个数据集都只保留英语网页. FineWeb 的数据卡还写明, 由于部分过滤步骤, 代码在 FineWeb 里不多, 建议另配代码数据集.

## 11. 边界

收集阶段的选择各有一个代价, 列在下面.

- **自己抽取的算力代价.** 从 WARC 抽取比直接用 WET 贵得多. DCLM 选 resiliparse 只因为快 8 倍, 质量和 trafilatura 相当. 对多语言或数学, 通用抽取器都不够, 要像 OpenWebMath 一样针对 MathJax 和各种公式编码写专门的抽取.
- **黑名单的误杀.** RefinedWeb 的经验是现成黑名单里有少量高流量的正常域名, 必须人工检查高频命中的 URL. 基于词表的 URL 或内容规则会误伤医疗和法律页面.
- **语言阈值的偏向.** 阈值越高, 混合语言, 短文本和非标准变体越容易被删. 0.5 与 0.65 没有统一答案; Dolma 的 ICE 审计说明 0.5 下各地区的英语都能保留, 0.90 下开始误删.
- **许可的不确定性.** The Stack v2 把无许可文件也收了进来, 依据是许可检测的结果和社区讨论, 不是法律结论. robots.txt 和服务条款的限制在 2023 到 2024 年迅速增加, 而旧快照里的数据不会随之更新.
- **只靠收集解决不了质量.** 收集阶段之后 RefinedWeb 还要删掉一半多文档, DCLM 只保留分类器打分前 10% 的文档. 抽取得再干净, 后面仍需要 [3.1.3](../3.1.3-数据处理/3.1.3-数据处理.md) 的质量过滤和去重; 网页里不够的教科书式内容, 则由 [3.1.2](../3.1.2-数据蒸馏/3.1.2-数据蒸馏.md) 的合成数据补.

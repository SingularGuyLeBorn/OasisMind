# 3.2.5 训练容灾与监控

万卡训练是同步的：一张 GPU 挂了，整份作业停。容灾不是锦上添花，而是让「停」变成「从最近合法快照再走」。数字用 **Llama 3 405B** 报告里 54 天快照，不编 Llama 2「每三天掉卡、有效率 95%」这类无表陈述。

## 1. 故障是默认事件

Llama 3 herd（Grattafiori et al., 2024, §3.3.3）：同步训练下单卡故障就要重启整 job。他们把**有效训练时间**做到 **高于 90%**（有效步 / 墙上时钟），同时每天至少一次计划内中断（固件、内核等自动运维）。54 天快照里 **466** 次作业中断：47 次计划内，419 次意外；意外里约 **78%** 归到已确认或疑似硬件，其中 GPU 相关约占意外的 **58.7%**。同一时期只有三次需要大量人工，其余自动化处理。

故障域：GPU（ECC、hang）、节点、网络（RoCE/IB）、存储、NCCL 超时、Loss/NaN、机房功耗与温度。报告还写：全体 GPU 同时等 checkpoint 或集合通信时，数据中心功率可在数十兆瓦量级上抖动。

旧文「单卡日故障率 1%–5%」「2048 卡单日故障概率 >99.9%」没有给出对应公开表，不写。

## 2. Checkpoint

快照至少包括：权重、优化器状态、学习率与步数、dataloader 偏移、RNG、并行拓扑。少一项，恢复后的 loss 会对不上。

![](./images/fig-checkpoint-failure-domain.png)

> 图 1：故障从 GPU/节点/网络/存储进来；训练作业异步写出权重与优化器；恢复时加载最近好快照。

**图 1 解析**

- 同步作业没有「只重跑坏卡上的那一层」这条免费路径。
- 写入应异步，避免 GPU 空等 IO。Llama 3 用 Tectonic 存储，峰值吞吐 7 TB/s；checkpoint 每卡 **1MB–4GB**，突发写会打满存储，目标是缩短 GPU pause、提高保存频率以减少回滚步数。
- 3D 并行下按 TP/PP rank 分片存（Megatron / PyTorch DCP）。写临时文件再原子改名，避免读到半截文件。
- 保留最近若干份，防止坏快照覆盖好快照；保存后校验哈希。

70B 若存 BF16 权重 + FP32 Adam 双动量，体积到数百 GB 量级是数量级估计，具体以分片后每 rank 文件为准，不要把「700GB、保存 10 分钟」写成实测。

恢复：同样并行度拉起 → 加载分片 → 对齐 step 与数据偏移 → 看恢复点 loss 是否与保存点一致。对不上就换上一份快照，不要接着训。

## 3. 监控什么

| 信号 | 正常时 | 出事时 |
|------|--------|--------|
| 训练 loss | 平滑下降 | NaN、尖刺、平台 |
| 梯度范数 | 有界 | 爆炸或消失 |
| 吞吐 / MFU | 贴近报告配置 | 台阶下跌（掉卡、降频、NCCL） |
| GPU 温度/功耗/显存 | 近满载但不过热 | 功耗塌、ECC |
| 集合通信 | 带宽稳定 | watchdog 超时 |

Llama 3 用 NCCL flight recorder 环形缓冲集体通信元数据，超时自动 dump，用来查 hang。WandB / TensorBoard 管标量；集群用 Prometheus + DCGM。告警应能**自动停**（NaN、吞吐塌 30% 量级），而不是只发聊天消息。

Loss spike：Llama 3 用前期较小 batch 再加倍，报告称尖刺很少、几乎不用人工纠偏。Google PaLM 等报告过多次 spike，不要假设每家都有同一套「自动降 LR」剧本。

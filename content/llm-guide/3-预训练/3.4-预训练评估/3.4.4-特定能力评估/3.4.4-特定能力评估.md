# 3.4.4 特定能力评估: 代码, 数学与多语言

> 相关阅读: [3.4 预训练评估](../3.4-预训练评估.md) · [3.4.2 通用基准](../3.4.2-通用基准/3.4.2-通用基准.md) (pass@k 推导, 污染检测) · [3.4.1 困惑度](../3.4.1-困惑度-PPL/3.4.1-困惑度-PPL.md) · [3.1 预训练数据](../../3.1-预训练数据/3.1-预训练数据.md) · [4 后训练](../../../4-后训练/4-后训练.md)

## 1. 为什么单独评, 以及代码

### 1.1 为什么单独评

[3.4.2](../3.4.2-通用基准/3.4.2-通用基准.md) 的基准以选项打分为主: 判对只需要比较几个概率, 不存在「答对了但没认出来」的问题. 代码和数学不同: 模型生成一段程序或一段推导, 判对要靠外部检查器. 这带来三类新的误差:

| 误差 | 代码 | 数学 |
|---|---|---|
| 假阳性 (错的判成对) | 单测不足, 错误程序碰巧通过 | 推理错误但最终答案碰对 |
| 假阴性 (对的判成错) | 环境差异, 超时, 输出格式 | 答案形式不同 (1/2 与 0.5), 抽取失败 |
| 污染 | 题解在 GitHub 上 | 题目和解答在网上 |

预训练阶段关心这些误差, 是因为代码和数学数据的配比, 是否加入合成推理数据, 何时退火 (见 [3.2](../../3.2-预训练全流程/3.2-预训练全流程.md)), 通常要看这两类分数做决定. 如果分数的误差和要比较的差距同一量级, 决策就没有依据.

举一个具体的量级. 两个代码配比方案训出的模型在 HumanEval 上 pass@1 相差 3 个点. HumanEval 只有 164 题, 按 [3.4.2](../3.4.2-通用基准/3.4.2-通用基准.md) 式 (7), 通过率 50% 附近的标准误约 3.9 个点, 3 个点的差距落在一个标准误以内. 此外, 第 1.3 节会看到原版测试带有 19.3% 到 28.9% 的相对虚高, 而且虚高程度因模型而异, 足以改变排名. 两项叠加, 这 3 个点不能说明哪个配比更好. 换成测试更充分的版本, 增加题量 (HumanEval 加 MBPP, 加 MultiPL-E 的其他语言), 或改看连续度量, 才能把误差压到差距以下.

本文第 1.2 到 1.5 节讲代码, 第 2 节讲数学, 第 3.1 到 3.2 节讲多语言, 第 3.3 节汇总成预训练中的用法.

### 1.2 代码基础: HumanEval 与 MBPP

HumanEval 的构造和 pass@k 的无偏估计见 [3.4.2](../3.4.2-通用基准/3.4.2-通用基准.md) 第 1.5 节和第 2.4 节. 这里只复述要用到的两点: 164 道手写题, 平均每题 7.7 个单测; pass@k 按式 $1-\binom{n-c}{k}/\binom{n}{k}$ 估计.

MBPP (Mostly Basic Programming Problems, Austin 等人 2021) 是另一个常用的 Python 基准: 974 道面向入门程序员的短程序题, 每题一句自然语言描述加 3 个单测. 974 题的切分是固定的: 10 题作 few-shot 示例, 500 题测试, 374 题训练, 90 题验证. 作者另外人工核对出一个 427 题的 sanitized 子集, 修正了描述含糊或描述与测试不一致的题, 报 MBPP 分数时要写明用的是全集测试题还是这个子集. 论文还发布了 MathQA-Python, 23914 道把 MathQA 数学题改写成 Python 程序的题. 论文的结果: 模型规模从 244M 到 137B, 合成能力随规模对数线性增长; 最大的模型不在代码上微调, 用设计好的 few-shot 提示能解 59.6% 的 MBPP; 在留出的一部分 MBPP 上微调, 多数规模提升约 10 个点.

两个基准互补: HumanEval 给函数签名和 docstring, 模型补全函数体; MBPP 给一句描述, 模型写完整函数. 前者更接近代码补全, 后者更接近按需求写代码.

### 1.3 测试不足与其他语言: HumanEval+, MultiPL-E

单测越少, 错误程序越容易蒙混过关. 形式化地说, 记题目的测试集为 $T$, 程序 $f$ 在 $T$ 上全部通过记为 $\mathrm{pass}_T(f)=1$. 若 $T\subseteq T'$, 则

$$
\mathrm{pass}_{T'}(f)\le \mathrm{pass}_{T}(f) \tag{1}
$$

每个样本只可能从通过变成不通过, 所以扩充测试后, 任何 $k$ 下的 pass@k 都只降不升. 下降的幅度就是原测试集假阳性的下界.

Liu 等人 (2023) 的 EvalPlus 按这一思路扩充 HumanEval. 做法分三步:

1. **种子输入**: 把标准解, 示例输入和专门的指令给 ChatGPT, 让它生成合法但更刁钻的测试输入.
2. **类型感知变异**: 以种子输入为起点, 按参数类型 (整数, 列表, 字符串等) 做变异, 快速生成大量新输入.
3. **差分测试**: 用标准解在每个新输入上的输出作为预期输出, 与模型生成的程序比对.

得到的 HumanEval+ 测试规模是原版的 80 倍. 在 26 个模型 (含 GPT-4 和 ChatGPT) 上, pass@k 比原版低 19.3% 到 28.9% (不同 $k$). 排名也变了: 原版上 WizardCoder-CodeLlama 和 Phind-CodeLlama (均 34B) 都不比 ChatGPT 好, HumanEval+ 上两者都超过 ChatGPT. 论文还发现 HumanEval 自带的部分标准解本身是错的.

论文 Figure 1 的例子说明了漏判是怎么来的: 题目要求返回两个列表排序后的公共元素 (去重), ChatGPT 生成的代码先排序, 最后又把结果转成 set 返回, 丢掉了顺序. 原版测试的输入碰巧没有暴露这个问题.

扩充后的测试跑起来慢. EvalPlus 用集合覆盖 (set cover) 做测试约简, 在保持代码分支覆盖, 变异杀死率和对已知错误样本的检出不变的前提下, 得到缩小 47 倍的 HumanEval+-mini.

**其他语言: MultiPL-E.** HumanEval 和 MBPP 都只有 Python. MultiPL-E (Cassano 等人 2022) 写了一套翻译器, 把这两个基准的函数签名, docstring 和单测机械地翻译到另外 18 种编程语言, 得到第一个大规模多语言代码生成基准. 翻译的是题面和测试, 不是解答, 所以每种语言的题目在语义上相同, 跨语言的分数差就反映模型在该语言上的能力差. 这对预训练有直接用处: 代码数据里各语言的配比可以按 MultiPL-E 的分语言分数来调.

### 1.4 污染: 按时间切分

HumanEval 的题和解早已大量出现在网上, [3.4.2](../3.4.2-通用基准/3.4.2-通用基准.md) 第 5 节提到 RedPajama-Data-1T 和 StarCoder-Data 中有 8% 到 18% 的 HumanEval 改写版本. n-gram 去污对改写无效.

LiveCodeBench (Jain 等人 2024) 换了一种思路: 持续从 LeetCode, AtCoder, CodeForces 三个竞赛平台收集新题, 每道题记录发布日期, 并按难度分成 easy, medium, hard 三档. 评估一个训练截止日期为 $t_c$ 的模型时, 只用发布日期晚于 $t_c$ 的题:

$$
\mathcal{D}_{\text{eval}}(t_c)=\{x\in\mathcal{D}:\ \mathrm{date}(x)>t_c\} \tag{2}
$$

这些题不可能出现在训练数据中. 论文发布时题库有 500 多道题, 发布时间在 2023 年 5 月到 2024 年 5 月之间. 论文的观察: DeepSeek-Instruct 和 GPT-4-O 在各自发布 / 截止日期 (2023 年 9 月和 11 月) 之后发布的 LeetCode 题上表现明显变差, 提示更早的题可能已被污染. 因此比较这些模型时, 只用 9 月或 11 月之后的时间窗.

LiveCodeBench 还把评估扩展到代码生成之外的三种场景: 自我修复 (根据报错修改代码), 代码执行 (给代码和输入, 预测输出), 测试输出预测 (给题目和输入, 预测正确输出). 后两种不需要模型写出完整程序, 对预训练早期的模型更容易有信号.

式 (2) 的代价是题量: 截止日期越晚, 可用的题越少, 标准误越大 (见 [3.4.2](../3.4.2-通用基准/3.4.2-通用基准.md) 式 (7)). 时间窗内的题目难度分布也可能与全集不同.

### 1.5 执行环境

运行模型生成的代码有安全风险. Codex 论文专门写了沙箱一节: 公开代码意图未知, 生成的程序常常是错的, GitHub 上也有会修改运行环境的恶意程序. 评估框架要做到:

- 隔离: 容器或沙箱运行, 禁止网络和对宿主文件系统的写入. Codex 论文的实现是用 gVisor 容器运行时隔离被测程序, 再用基于 eBPF 的防火墙规则拦掉除实验控制所需之外的全部入站和出站连接.
- 超时: 每个样本设时间上限, 死循环记为失败.
- 环境固定: 解释器版本, 依赖库版本写进配置. 同一程序在不同版本下行为可能不同, 这是代码评估里假阴性的来源之一.

## 2. 数学

### 2.1 从 GSM8K 到 MATH

GSM8K (见 [3.4.2](../3.4.2-通用基准/3.4.2-通用基准.md) 第 1.4 节) 的答案是一个数, 判对只需比较数值. 难题需要更复杂的答案形式. Hendrycks 等人 (2021) 的 MATH 收集了 12500 道竞赛数学题 (训练 7500, 测试 5000), 来自 AMC 10, AMC 12, AIME 等竞赛, 分 7 个学科 (初等代数前置 Prealgebra, 代数, 数论, 计数与概率, 几何, 中级代数, 预备微积分 Precalculus) 和 1 到 5 共五个难度级别. 每题有完整的 LaTeX 解答, 最终答案写在 `\boxed{}` 中, 判对时把 boxed 内容归一化后做精确匹配.

发布时的参照: 大模型准确率只有 3.0% 到 6.9%; 一位不太喜欢数学的计算机科学博士生 40%, 一位三次 IMO 金牌得主 90%. 论文同时发布了数学预训练语料 AMPS (10 万多道 Khan Academy 习题, 加约 500 万道用 Mathematica 脚本生成的题, 共 23GB), 并按对数线性趋势外推: 要在 MATH 上达到 40%, 模型需要约 $10^{35}$ 个参数, 因此只靠扩大规模不现实. 一年多后的 Minerva 在 38.5B token 的技术语料 (17.5B 数学网页, 21.0B arXiv 论文) 上继续预训练 PaLM, 540B 模型 maj1@k 达到 50.3% (见 2.3 节), 说明这一外推没有考虑数据的变化.

### 2.2 答案等价

同一个答案可以有多种写法: $1/\sqrt{3}$ 和 $\sqrt{3}/3$, $1{,}000$ 和 $1000$, 带不带美元符号, 写不写单位. 精确匹配会把这些都判成错. Minerva (Lewkowycz 等人 2022) 的处理分两步:

1. **抽取**: few-shot 示例里每个答案都写成「Final Answer: The final answer is ANSWER. I hope it is correct.」, 从模型输出里按这个模式抽出 ANSWER.
2. **归一化与比对**: 用一组替换规则清理 (去掉冠词, 美元符号, 部分 LaTeX 空白等, 见论文附录 D.1 Listing 1), 再用 SymPy 判断两个表达式在数学上是否相等.

论文强调归一化没做好会产生假阴性, 低估模型; 同时设计规则时要避免把标准答案改成别的形式, 那会产生假阳性. 这一步完全在评测代码里, 不同框架的规则不同, MATH 分数跨框架比较时要先确认规则.

### 2.3 多数投票: maj1@k

Minerva 对每题以非零温度采 $k$ 个解, 按最终答案分组, 取出现次数最多的答案:

$$
\hat a=\arg\max_{a}\ \sum_{i=1}^{k}\mathbb{1}[a_i\equiv a] \tag{3}
$$

$a_i$ 是第 $i$ 个样本的最终答案, $\equiv$ 是 2.2 节的等价判定. 记作 maj1@k (沿用 Li 等人 2022 的记法). 论文的解释是: 答错的方式有很多, 答对的方式通常很少, 所以正确答案更容易聚成最大的一组.

Minerva Table 3 节选 (%):

| 模型 | MATH | OCWCourses | GSM8k | MMLU-STEM |
|---|---|---|---|---|
| PaLM 540B | 8.8 | — | 56.5 | — |
| Minerva 62B | 27.6 | — | 52.4 | — |
| Minerva 62B, maj1@k | 43.4 | — | 68.5 | — |
| Minerva 540B | 33.6 | 17.6 | 58.8 | 63.9 |
| Minerva 540B, maj1@k | 50.3 | 30.8 | 78.5 | 75.0 |

MATH 上 $k=256$ (8B, 62B) 或 $k=64$ (540B), MMLU-STEM 上 $k=16$. 多数投票的收益随 $k$ 很快饱和: $k=64$ 时在 MATH 上已达到大 $k$ 时准确率的 97%, GSM8k 上 $k=16$ 就达到 97%.

maj1@k 和 pass@k 衡量的东西不同. pass@k 只要 $k$ 个里有一个对, 需要外部判定 (单测) 来挑出它; maj1@k 不需要外部判定, 是一个可以真正提交的答案. 在数学上报 pass@k 意味着假设存在一个完美的验证器.

手算一个例子 (答案为示意). 一道题标准答案是 15, 模型采 5 个样本, 最终答案依次为 12, 12, 15, 12, 7. pass@5 记为解出 (有一个 15); maj1@5 选出现 3 次的 12, 记为错; 单次 greedy 的结果取决于贪心路径落在哪一组. 反过来, 若 5 个答案为 15, 15, 12, 15, 7, maj1@5 和 pass@5 都记为对. 可以看出 maj1@k 要求正确答案在样本中占相对多数, 条件比 pass@k 严, 比 pass@1 宽. 设单个样本答对的概率为 $p$, 错误答案分散在很多不同的值上, 那么只要 $p$ 明显高于任何一个错误答案的概率, $k$ 增大时 maj1@k 趋于 1; 如果某个错误答案的概率超过 $p$ (常见的计算陷阱会让很多样本错到同一个数), maj1@k 随 $k$ 增大反而趋于 0. 所以多数投票的收益本身是一个诊断: 收益大, 说明模型的错误比较分散.

答案等价的判定也会改变投票结果. 若一组样本答 $1/2$, 另一组答 $0.5$, 没有归一化时它们被分成两组, 票数被拆开, 本来的多数答案可能落选. 2.2 节的 SymPy 比对在投票前就要做.

### 2.4 假阳性: 答案对, 推理错

最终答案对不等于解题过程对. Minerva 从 MATH 随机选 100 道题 (每个难度级别 20 道), 用 62B 模型零温度采样, 人工检查答对的样本, 估计推理不完整或错误但答案正确 (假阳性) 的比例: 1 到 5 级依次约为 <5%, 10%, <5%, 15%, 30%, 平均约 8%. 难度越高, 碰对的比例越高.

这对 pass@k 的影响更大. 论文报告 62B 模型在 MATH 上 pass@256 为 84.5%. 但对于 256 个样本里只有一个答对的题, 约 30% 是假阳性. 扣除后, 真实的 pass@256 只能确定高于 68%. 也就是说, 采样越多, 「碰对」在 pass@k 里的占比越高, 名义值和真实值之间的差距越大.

GSM8K 论文里也出现过同一现象的另一面: 验证器在每题 400 个候选时收益最高, 继续增加候选数, 收益下降, 因为出现了骗过验证器的错误解 (见 [3.4.2](../3.4.2-通用基准/3.4.2-通用基准.md) 第 1.4 节).

### 2.5 过程监督与 MATH-500

如果最终答案不可靠, 一种思路是检查每一步. Lightman 等人 (2023) *Let's Verify Step by Step* 让标注员给生成器 (由 GPT-4 基座微调) 写出的 MATH 解答逐步打标签 (positive, negative, neutral), 训练过程奖励模型 (process reward model, PRM). 数据集 PRM800K 原始收集了 1085590 个步骤级标签, 过滤后约 80 万个, 覆盖约 7.5 万个解答, 1.2 万道题. 为了让标注更有价值, 他们主动挑选当前最好的 PRM 打分高但最终答案错误的解答 (「有说服力的错误解」) 送去标注.

PRM 在每一步末尾预测该步是否正确. 一个解答的总分定义为所有步骤都正确的概率, 实现为各步正确概率的乘积:

$$
\mathrm{score}(s)=\prod_{j=1}^{J}P(\text{第 }j\text{ 步正确}\mid s_{\le j}) \tag{4}
$$

$J$ 是解答的步数. 评估方式是 best-of-N: 每题从生成器均匀采 $N$ 个解, 用奖励模型选分最高的, 再按最终答案判对. 每题共生成 1860 个解, best-of-1860 时:

| 方法 | 选中正确解的比例 |
|---|---|
| 过程奖励模型 (PRM) | 78.2% |
| 结果奖励模型 (ORM) | 72.4% |
| 多数投票 | 69.6% |

ORM 的训练标签不需要人工: 按最终答案是否与标准答案一致自动给出, 整个解答只有一个标签. 评估时 PRM, ORM 和多数投票面对的是同一批 1860 个采样解, 差别只在怎样从中挑一个.

两个与评估相关的细节. 第一, PRM800K 的训练集包含了 4500 道 MATH 测试题 (为了避免在 7500 道训练题上过拟合), 所以论文只在剩下的 500 道测试题上评估; 这 500 道是均匀随机选的, 论文 Figure 5 显示其难度和学科分布与完整测试集一致. 现在常说的 MATH-500 就是这个子集. 在 MATH-500 上报分数时, 要注意它只有 500 题, 按 [3.4.2](../3.4.2-通用基准/3.4.2-通用基准.md) 式 (7), $p=0.5$ 时标准误约 2.2 个点. 第二, 过程监督的奖励模型主要用于后训练和推理阶段的搜索, 属于 [第 4 章](../../../4-后训练/4-后训练.md) 的范围; 预训练评估从中借用的是两点认识: 最终答案判对有系统性的假阳性, 以及 best-of-N 的结果依赖验证器.

## 3. 多语言, 用法与边界

### 3.1 多语言: 翻译的基准 MGSM 与 MMMLU

Shi 等人 (2022) 的 MGSM 从 GSM8K 选 250 道题, 人工翻译成 10 种语言: 孟加拉语, 中文, 法语, 德语, 日语, 俄语, 西班牙语, 斯瓦希里语, 泰卢固语, 泰语, 覆盖 8 个语系和不同的预训练数据占比. 题目语义相同, 只换语言, 所以分数差直接反映语言能力差. 论文比较了四种提示设置:

| 设置 | 输入 | 推理语言 |
|---|---|---|
| Direct | 原语言题目 | 直接给答案, 无推理 |
| Native-CoT | 原语言题目 | 原语言 |
| EN-CoT | 原语言题目 | 英语 |
| Translate-EN | 用 Google 翻译译成英语的题目 | 英语 |

结果: 标准提示 (Direct) 下 GPT-3 和 PaLM 都不到 20%; 用 CoT 后, PaLM 540B 在所有语言上都超过 40%, 包括孟加拉语和斯瓦希里语这两种在预训练数据中占比不到 0.01% 的语言; 最佳设置下各语言平均 55%. 这一能力随模型规模出现.

OpenAI 的 MMMLU 把 MMLU 测试集由专业人工译者翻译成 14 种语言, 理由是人工翻译对约鲁巴语这类低资源语言更可靠.

### 3.2 翻译之外: 文化偏差与中文基准

翻译保住了语言, 保不住题目的文化背景. Singh 等人 (2024) 的 Global-MMLU 标注了 MMLU 中每道题是否需要文化相关知识: 28% 的题需要; 在需要地理知识的题中, 84.9% 关于北美或欧洲. 在全集和「文化敏感」子集上分别评估, 模型排名会变. 他们发布了覆盖 42 种语言的 Global-MMLU, 由付费的专业译者和社区标注员核对翻译质量, 并把题目分成文化敏感和文化无关两个子集分别报告. 论文也指出, 机器翻译会引入扭曲题意的翻译痕迹, 只靠机器翻译评测集不够.

**中文: C-Eval 与 CMMLU.** 中文场景有两个原生构建的基准. C-Eval (Huang 等人 2023) 是 13948 道四选一题, 分初中, 高中, 大学, 专业四个难度级别, 覆盖 52 个学科, 另有需要高级推理的子集 C-Eval Hard; 发布时只有 GPT-4 的平均准确率超过 60%. CMMLU (Li 等人 2023) 有 11528 道题, 分 67 个科目, 覆盖自然科学, 社会科学, 工程, 人文等学科, 评估了 18 个多语言和中文模型, 多数即使加上少样本示例和 CoT 也达不到 50% (随机为 25%). 两者都是选择题, [3.4.2](../3.4.2-通用基准/3.4.2-通用基准.md) 第 2, 3 节关于 CF / MCF 格式和归一化的讨论同样适用; 题目来自公开考试和网络资源, 也同样有污染问题.

### 3.3 预训练中怎么用

| 决策 | 看什么 | 注意 |
|---|---|---|
| 代码数据的总配比 | HumanEval+ 与 MBPP 的 pass@1 (greedy) 与 pass@10 | 用扩充测试, 原版有 20% 到 30% 的虚高 |
| 各编程语言的配比 | MultiPL-E 分语言分数 | 小语言题量少, 看误差 |
| 是否污染 | LiveCodeBench 截止日期后的时间窗 | 题量小, 难度分布要核对 |
| 数学数据的配比 | GSM8K, MATH (或 MATH-500), greedy 与 maj1@k | MATH-500 标准误约 2 个点; 固定归一化规则 |
| 早期 checkpoint | 正确答案的对数概率, 代码执行 / 输出预测类任务 | 生成式任务早期接近 0, 见 [3.4.1](../3.4.1-困惑度-PPL/3.4.1-困惑度-PPL.md) 第 4.2 节 |
| 多语言配比 | MGSM 分语言, Global-MMLU 文化无关子集, C-Eval / CMMLU | 区分语言能力与文化知识 |

对早期 checkpoint, 生成式的代码和数学分数常年在个位数, 曲线被噪声主导. [3.4.1](../3.4.1-困惑度-PPL/3.4.1-困惑度-PPL.md) 第 4.2 节的结论在这里同样适用: 用连续度量 (标准解或正确答案在模型下的对数概率, 或者分领域的 BPB, 例如 GitHub 代码和 arXiv 数学语料上的 BPB) 看趋势, 用 pass@k 和 maj1@k 看最终能力.

### 3.4 边界

| 评估 | 能回答 | 不能回答 / 误差来源 |
|---|---|---|
| HumanEval / MBPP pass@k | 短函数级代码生成 | 测试不足导致虚高; 不测工程级代码和多文件 |
| HumanEval+ | 更严格的功能正确性 | 依赖标准解正确; 只覆盖原题 |
| MultiPL-E | 跨语言能力差异 | 翻译后的题仍是 Python 风格的小函数 |
| LiveCodeBench | 无污染的竞赛题能力 | 题量随时间窗变小; 竞赛题不代表日常编程 |
| MATH maj1@k | 竞赛数学的最终答案 | 约 8% 的答对样本推理错误 (难题约 30%); 归一化规则 |
| MATH pass@k | 搜索上限 (假设完美验证器) | 采样越多, 碰对的占比越高 |
| PRM best-of-N | 验证器挑选正确解的能力 | 依赖生成器分布; 属于后训练工具 |
| MGSM / MMMLU | 同一题目跨语言的能力差 | 只测翻译后的英语中心内容 |
| Global-MMLU / C-Eval / CMMLU | 文化与本地知识 | 选择题格式的全部问题; 污染 |

代码和数学的分数比选择题更接近「真会做」, 但它们的可靠性取决于检查器. 报这类分数时, 除了 [3.4.2](../3.4.2-通用基准/3.4.2-通用基准.md) 第 6.1 节的清单, 还要写明: 测试集版本 (原版或扩充版), 执行环境与超时, 答案抽取和归一化规则, 采样数与温度, 以及时间窗.

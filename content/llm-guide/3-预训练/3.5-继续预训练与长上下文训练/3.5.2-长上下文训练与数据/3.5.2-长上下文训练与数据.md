# 3.5.2 长上下文训练与数据: 继续预训练, 数据配比与 SFT

[2.7.1](../../../2-核心原理与架构/2.7-长上下文与外推技术/2.7.1-长度外推/2.7.1-长度外推.md) 讲的是位置编码层面的外推. 那些方法大多能让困惑度在长序列上不崩, 但 2.7.1 第 5 节的评测说明, 要让模型真的用上 100k 之外的信息, 目前的主流做法仍是用长序列继续训练. 本文讲这一步的配方.

## 1. 问题与位置编码

### 1.1 问题: 为什么要训练

2.7.1 讲的免训练方法 (PI 不微调, NTK, Self-Extend, DCA) 改的是位置, 权重没动. 模型在预训练中从未见过一个 token 依赖 100k 之前的内容, 也没有学过在 100k 个 key 里分配注意力. [ProLong](https://arxiv.org/abs/2410.02660) 引言里的判断是, 这些最小训练量的扩展方法连简单的 NIAH 都过不了, 要稳定地学会这类任务, 需要在数十亿 token 的长文档上继续训练.

从头用长序列预训练又太贵. 注意力的计算量随长度平方增长: [LongLoRA](https://arxiv.org/abs/2309.12307) 的摘要举的例子是, 8192 长度的自注意力计算量是 2048 的 16 倍. 所以实际的路线是先短后长. 剩下的是一组配方选择: 位置编码怎么改, 什么时候切到长序列, 长数据从哪来, 长短怎么配, 文档边界怎么处理, SFT 用什么数据, 显存不够时怎么训.

### 1.2 位置编码: Llama 2 Long 的对比

[Xiong et al. (2023)](https://arxiv.org/abs/2309.16039) (下称 Llama 2 Long) 在 7B 上做早期实验时发现, 不改 Llama 2 的位置编码, 即使充分继续预训练, 模型在「复述输入第一句话」的任务上也看不到 4000–6000 token 之外. 他们把原因归到 RoPE 对远处 token 的注意力分数衰减太重, 于是把 base 从 10000 调到 500000, 让每个维度的旋转角变小, 衰减变慢. 这个改法叫 ABF (adjusted base frequency). 推导和与 PI 的对比见 2.1.4 的 [02 篇](../../../2-核心原理与架构/2.1-深度学习基础组件/2.1.4-位置编码/02-RoPE扩展-长上下文,多模态与工程实现/02-RoPE扩展-长上下文,多模态与工程实现.md) 第 3 节.

消融设置: 都从 Llama 2 7B 出发, 用 80B token 继续训练. 32k 序列上的验证困惑度 (原文表 5):

| 位置编码 | Books | CC | Wikipedia |
|---|---:|---:|---:|
| RoPE | 6.548 | 6.816 | 3.802 |
| RoPE PI | 6.341 | 6.786 | 3.775 |
| RoPE ABF | 6.323 | 6.780 | 3.771 |
| xPos ABF | 6.331 | 6.780 | 3.771 |

困惑度差别很小. 差别出现在「复述第一句」任务上: 只有 RoPE ABF 能在完整的 32768 窗口上保持表现. 作者也测了 passkey, 除原始 RoPE 外全部满分, 区分不开.

### 1.3 base 取多大

Llama 3 预训练时 base 就是 500000, 原文引用 Llama 2 Long 的结果说明这个值在 32768 以内有效. 更长的窗口要更大的 base. ProLong 从 Llama-3-8B-Instruct (base $5\times10^5$) 出发, 64k 阶段用 $8\times10^6$, 512k 阶段用 $1.28\times10^8$, 附录 B.1 的消融显示调大 base 即使在大量训练后仍明显有益.

[Men et al. (2024)](https://arxiv.org/abs/2405.14591) 给出了 base 随目标长度的下界 (64k 约 $2.1\times10^6$, 512k 约 $6.4\times10^7$), 推导见 [2.7.1](../../../2-核心原理与架构/2.7-长上下文与外推技术/2.7.1-长度外推/2.7.1-长度外推.md) 第 4.5 节. ProLong 的两个取值都在下界之上.

## 2. 什么时候切, 训多少

### 2.1 先短后长的 FLOPs

Llama 2 Long 的 4.4 节比较了几种课程: 全程 32k, 以及先 4k 再在训练进度 20%, 40%, 80% 处切到 32k. 总 token 数相同, 每步梯度更新的 token 数固定为 4M. 结果 (原文表 10, 11):

| 课程 | FLOPs | NarrativeQA | Qasper | QuALITY | QMSum | CC 困惑度 |
|---|---:|---:|---:|---:|---:|---:|
| 全程 32k | $3.783\times10^{22}$ | 18.5 | 28.6 | 37.9 | 11.46 | 7.67 |
| 4k → 32k @ 20% | $3.405\times10^{22}$ | 20.0 | 28.1 | 38.8 | 12.09 | 7.59 |
| 4k → 32k @ 40% | $3.026\times10^{22}$ | 20.1 | 27.0 | 37.4 | 12.44 | 7.59 |
| 4k → 32k @ 80% | $2.270\times10^{22}$ | 18.5 | 25.0 | 38.3 | 11.00 | 7.59 |

手算: $1-2.270/3.783=0.400$, 80% 处切换省下 40% 的 FLOPs. 长文本问答有涨有跌, 困惑度反而略好. 作者的解释是模型能很快适应更长的序列.

### 2.2 两派数据量

**大数据量**. Llama 2 Long 正式训练用了 400B token, 100000 步, 保持每个 batch 的 token 数与 Llama 2 相同; 7B/13B 用 32768 长度, 34B/70B 用 16384 长度. 用 FlashAttention 后, 70B 模型从 4096 换到 16384 序列只慢约 17%. 7B/13B 学习率 $2\times10^{-5}$, 34B/70B 要降到 $1\times10^{-5}$ 才能让验证损失单调下降. [Llama 3](https://arxiv.org/abs/2407.21783) 的 405B 模型在预训练末段分六个阶段从 8k 逐步扩到 128k, 共约 800B token. 每一阶段的放行标准有两条: 短上下文评测完全恢复, 以及 NIAH 在当前长度上全部通过. 长上下文阶段之后还有退火: 最后 40M token 仍保持 128k 长度, 学习率线性降到 0, 数据配比上采样高质量来源, 最终的预训练模型取退火期间各检查点的平均 (Polyak 平均). 所以 128k 长度一直保持到预训练最后一步, 退火没有退回短序列.

**小数据量**. [Fu et al. (2024)](https://arxiv.org/abs/2402.10171) 的假设是: 在任意位置取用信息的能力在预训练里基本已经学到了 (即使只在 4k 上训练), 继续训练只是把这个能力延伸到更长的长度. 他们用 LLaMA-2 7B/13B 在 80k (13B 为 64k) 上继续训练, 学习率恒定 $2\times10^{-5}$, 同样改大 RoPE base, batch 为 4M token. 结论 (原文图 3):

- 500M token 就能解锁大部分检索准确率.
- 约 5B token 时检索性能饱和, 加到 10B 不再提升长度泛化.

5B token 的配置在 8 张 80G A100 上跑 5 天, 作者估算约为 Llama 2 Long 预算的 1%. 原文表 2 还给了墙钟时间: 同样训 10B token, 7B 模型在 4k 上要 3 天, 在 80k 上要 10 天. 长度涨 20 倍, 时间只涨约 3.3 倍, 远不到平方. 作者的解释是这套 HuggingFace + DeepSpeed ZeRO-3 + CPU offload 的配置里, 大部分时间花在 CPU 到 GPU, GPU 之间以及 HBM 到片上 SRAM 的数据搬运上, 注意力计算本身不是主要开销. 再往上加长度, 显存会被 KV 占满, ZeRO 属于数据并行, 加卡也解决不了, 需要序列并行. NIAH 和 MMLU 对比 (原文表 3):

| 模型 | 训练长度 | NIAH | MMLU |
|---|---:|---:|---:|
| GPT-4-Turbo | 128k | 87.1 | 86.4 |
| YaRN Mistral 7B | 128k | 57.4 | 59.4 |
| Together LLaMA-2 7B | 32k | 27.9 | 44.8 |
| LongLoRA 7B | 100k | 70.0 | 37.9 |
| Fu et al. LLaMA-2 7B | 80k | 88.0 | 43.3 |
| Fu et al. LLaMA-2 13B | 64k | 90.0 | 52.4 |

在 128k 的 InfiniBench 书籍问答上 (原文表 4), Fu et al. 的 7B 为 27.4, 13B 为 31.1, LongLoRA 7B 为 24.3, YaRN Mistral 7B 为 26.3, GPT-4-Turbo 为 37.4. NIAH 上接近 GPT-4, 真实长文本任务上仍有差距.

两派的分歧可以这样理解: Fu et al. 的目标是通过 128k 的 NIAH, 这是检索能力; Llama 2 Long 和 Llama 3 还要在真实长文本任务上提升, 并保证短任务不退化, 训练量自然大得多. ProLong (第 3.3 节) 的 40B token 落在两者之间, 作者报告它在大多数长上下文任务上超过 Llama-3.1-8B-Instruct, 而长上下文训练数据只有后者 800B 的 5%.

### 2.3 上下文变长, 损失降多少

Llama 2 Long 发现验证损失随上下文长度 $c$ 呈幂律加常数:

$$
\mathcal{L}(c)=\left(\frac{\alpha}{c}\right)^{\beta}+\gamma
\tag{1}
$$

每个模型规模有一组自己的 $\alpha,\beta,\gamma$. 以 70B 为例, 上下文翻倍时可下降的那部分损失乘以 $2^{-\beta}\approx0.7$, 再加上常数 $(1-2^{-\beta})\gamma$ 的影响; 到 32768 仍在下降, 但边际收益递减. 各长文本任务的分数也随评测长度单调上升. 作者据此把上下文长度看作和参数量, 数据量并列的一个扩展维度.

短任务上, Llama 2 Long 的结果与 Llama 2 持平, 多数还更好, 编码, 数学, MMLU 这类知识密集任务提升明显. 这和 PI 原文报告的短任务轻微下降不同, 作者把提升归因于继续训练多出来的 FLOPs 和新加入的长数据带来的知识.

## 3. 数据, 训练长度与打包

### 3.1 长度分布和领域分布纠缠在一起

长文档集中在少数来源. Fu et al. 统计 SlimPajama (LLaMA 预训练配比的开源复现: 网页 82%, 其中 CommonCrawl 67%, C4 15%; 代码 4.5%, 维基 4.5%, 书 4.5%, arXiv 2.5%, StackExchange 2.0%) 后发现, 书和 GitHub 代码最长, 其次是 arXiv, C4 和 StackExchange 偏短. 原始配比里约 30% 的文档长于 4k.

于是「上采样长文档」和「改变领域配比」是同一个操作的两面. 上采样 100k 以上的文档, 书的比例就会上升. 他们比较了四种策略:

| 策略 | 做法 | 先前采用者 |
|---|---|---|
| 128k 截断 | 保持原配比, 只是不在 4k 处截断 | LongLoRA |
| 全局上采样 | 不分来源地上采样长文档, 领域比例略变 | Together |
| 指定领域上采样 | 专门上采样书 / 代码 / arXiv | YaRN Mistral (只用 PG19 书), MPT-storyteller |
| 按来源上采样 | 保持领域比例, 在每个领域内部上采样长文档 | Fu et al. 推荐 |

### 3.2 上采样一个领域会伤另一个领域

原文表 5 报告各策略相对原配比的损失变化 (7B, 5B token, 80k 打包; 负数表示变好, 绝对值大于 0.01 视为显著). 0–4k 上下文区间的部分数字:

| 相对原配比 | C4 | CC | Arxiv | Book | Github |
|---|---:|---:|---:|---:|---:|
| 按来源上采样 | +.002 | +.008 | −.008 | −.065 | −.008 |
| 全局上采样 | +.008 | +.010 | −.020 | −.140 | +.015 |
| 上采样代码 | +.010 | +.016 | +.006 | +.030 | −.023 |
| 上采样书 | +.010 | +.016 | +.000 | −.175 | +.029 |
| 上采样 arXiv | +.006 | +.016 | −.060 | +.040 | +.025 |

上采样书, 书的损失降得最多 (−.175), 代码的损失却上升 (+.029); 上采样代码则反过来伤书 (+.030). 按来源上采样各领域几乎都没有显著变差. 作者把 YaRN Mistral 在 NIAH 上的落后部分归因于只用了 PG19 书籍数据.

只保留天然的长依赖也不够. 「128k 截断」不改配比, 验证损失和上采样版本相近, 但检索能力明显更差 (原文图 4). 这也是作者强调不能只看验证损失的原因.

### 3.3 ProLong: 代码仓库, 书, 和高质量短数据

[Gao et al. (2024)](https://arxiv.org/abs/2410.02660) (ProLong) 从 Llama-3-8B 出发, 用 5B token, 64k 长度做数据消融. 他们评测的方式和前面的工作不同: 不用困惑度和 NIAH, 而是用 HELMET 的一组下游任务 (JSON 键值检索, RAG, 重排序, 多样本上下文学习, 长文档问答和摘要), 并且每个消融都先做 SFT 再评测, 因为有些长上下文任务的差别只在 SFT 之后才显现.

主要发现:

1. **长数据的来源**. 用 60% 长数据加 40% 短数据训练时, 只用代码仓库在键值检索上最好; 书对上下文学习, 摘要, 重排序更有帮助; 二者各半综合最好. 代码仓库是把同一仓库的文件拼成一个长文档.
2. **长短比例**. 长数据比例越高, 短任务越差. 长任务的趋势更复杂: SFT 前, 检索和 RAG 偏好更多长数据; SFT 后, 长数据过多反而大幅变差. 作者的解释是只在长数据上特化的模型不是通用 SFT 的好起点. 综合最优在 60% 长数据.
3. **短数据的质量**. 40% 短数据用什么, 对长短任务都有显著影响. 他们自配的 ShortMix (FineWeb, FineWeb-Edu, 维基, StackExchange, Tulu-v2, OpenWebMath, arXiv) 好于单用 SlimPajama, FineWeb-Edu 或 DCLM-Baseline. 单用 FineWeb-Edu 作为短数据部分效果差.

只改 base 或用 Fu et al. 的 SlimPajama 长数据配方, 都会让 Llama-3-8B 的短任务掉分 (原文表 2):

| 设置 | HellaSwag | MMLU | ARC-c | WinoGrande | GSM8K |
|---|---:|---:|---:|---:|---:|
| Llama-3-8B | 82.1 | 66.5 | 59.4 | 77.1 | 44.7 |
| + 改 RoPE base | 81.5 | 64.7 | 58.1 | 75.5 | 40.1 |
| + SlimPajama 长数据 | 81.0 | 63.1 | 57.8 | 75.1 | 40.6 |

Fu et al. 在 LLaMA-2 7B 上报告 MMLU 基本保持 (43.3); 换成更强的 Llama-3-8B, 同一类配方的短任务损失就显现出来了.

ProLong 最终的数据 (原文表 9): 30% 代码仓库, 30% 书, 3% 教科书, 37% ShortMix. ShortMix 内部是 FineWeb-Edu 和 FineWeb 各 27%, 维基和 StackExchange 各 11%, Tulu-v2, OpenWebMath, arXiv 各 8%. 教科书是消融之后才加的, 理由是 3.3 节第 1 条里书类数据对长上下文有益, 教科书的教育性又高; 加入后 ShortMix 的比例相应微调.

### 3.4 质量还是长度

Llama 2 Long 的 4.2 节也做了数据消融. 把他们的新数据配比换回 Llama 2 原配比, 或者去掉长文本, 或者只上采样已有的长文本, 长文本任务的相对提升 (原文表 7, 相对 Llama 2 7B):

| 继续预训练数据 | NarrativeQA | Qasper | QuALITY | QMSum |
|---|---:|---:|---:|---:|
| Llama 2 Long 配比 | 23.70% | 43.64% | 75.5% | 45.70% |
| Llama 2 原配比 | 18.23% | 38.12% | 60.3% | 44.87% |
| 去掉长文本 | 19.48% | 39.14% | 67.1% | 36.60% |
| 上采样已有长文本 | 22.15% | 36.82% | 65.0% | 42.83% |

作者的结论是: 调整长度分布带来的收益不大, 新配比的提升主要来自数据本身的质量; 长上下文模型可以用很有限的长数据训练出来. 这和 Fu et al. 的「必须上采样长文档」看起来冲突. 一个可能的解释是 Llama 2 Long 训了 400B token, 天然长文档的总量已经足够; Fu et al. 只训 5B token, 不上采样就见不到足够的长依赖.

### 3.5 训练长度要不要超过目标长度

直觉上, 想支持 128k 就在 128k 上训练. 两篇论文给出了反例.

Fu et al. 在 80k 上训练的 LLaMA-2 7B 能泛化到 128k 的 NIAH. 对照组 Together LLaMA-2 在 32k 上训练, 过了约 40k 就不行. 他们的解释是训练长度要足够长, 模型才能学到可以延伸的模式.

ProLong 更进一步: 训练长度超过评测长度有额外收益. 从 64k 上训练了 20B token 的模型出发, 一组继续在 64k 上训 4B, 另一组切到 512k 训 4B, 都在 64k 上评测 (原文表 7):

| 设置 | Recall | RAG | Re-rank | ICL |
|---|---:|---:|---:|---:|
| 64k 训练 20B | 96.5 | 52.7 | 22.8 | 70.6 |
| + 4B 64k | 95.0 | 56.4 | 28.0 | 78.8 |
| + 4B 512k | 98.5 | 56.9 | 32.9 | 79.2 |

作者给了一个简化的解释: 假设某个任务需要模型见过跨度恰好为 $D$ 的依赖, 且这种依赖在序列里任何位置出现的概率相同. 一个长 $nD$ 的文档比 $n$ 个长 $D$ 的文档多出 $(n-1)(D-1)$ 个跨度为 $D$ 的依赖. 手算: $D=64\text{k}$, $n=8$ 时多出 $7\times(65536-1)\approx4.6\times10^5$ 个. 作者也承认这些假设在实际中不成立, 并提醒长序列训练更贵, 未必是计算最优的选择.

ProLong 的长度课程: 第一阶段所有长数据都在 64k; 第二阶段代码仓库一半在 512k, 一半在 64k, 书 17% 在 512k, 83% 在 64k, 教科书全在 512k. 两阶段各 20B token, 分别花 2.2k 和 12.2k H100 小时. 第二阶段 token 数相同, 耗时是第一阶段的 5.5 倍, 这就是注意力平方开销的体现. 两阶段都用 AdamW, 学习率 $1\times10^{-5}$, 10% 预热后余弦衰减到 $1\times10^{-6}$; 每步的 token 数第一阶段 4M, 第二阶段 8M; 512k 序列靠序列并行放进显存. 切换长度时学习率调度重置, 短任务先掉再随训练恢复.

[LongRoPE](https://arxiv.org/abs/2402.13753) 走的是反方向: 训练长度远短于目标长度, 靠逐维搜索的位置插值补上差额. 它只在 128k 和 256k 上一共微调约 1k 步, 再对微调后的模型做第二次插值搜索, 不训练就扩到 2048k; 搜索方法和各步的困惑度见 2.7.1 第 4.2, 4.3 节. 和 ProLong 相比, 这条路线把长度上的大部分工作交给位置插值, 2048k 上没有任何训练信号, 困惑度能保持不等于模型学会了取用那么远的信息 (2.7.1 第 5 节).

### 3.6 文档边界与打包

长序列训练要把多个文档打包进一个序列. 打包时是否允许一个文档的 token 看到同序列里另一个文档的 token, 结论比较一致: 应该屏蔽.

- Llama 3 用了阻止跨文档自注意力的掩码. 原文说这在标准预训练中影响有限, 但在超长序列的继续预训练中很重要.
- ProLong 附录 B.2 的消融显示, 禁用跨文档注意力对长短任务都有益, 还能提高训练吞吐.
- Fu et al. 按常规做法不管文档边界, 直接打包成 80k 的块.

吞吐提高的原因是: 屏蔽之后每个文档只在自己内部算注意力, 一个由许多短文档拼成的 512k 序列, 实际注意力计算量远小于 $512\text{k}^2$. 这需要注意力内核支持变长序列 (FlashAttention 的 varlen 接口一类).

## 4. SFT: 要不要长指令数据

### 4.1 三篇论文的三个结论

**Llama 2 Long**: 不用人工标注的长指令数据. 做法是在 Llama 2 Chat 的 RLHF 数据上, 加入由 Llama 2 Chat 自己生成的长文档问答 (从预训练语料取长文档, 随机选一段让模型出题). 短指令拼成 16384 的序列, 长指令单独右填充. 一个发现是对长输入本身也计算语言模型损失, 能稳定训练并显著提升效果 (原文表 9):

| SFT 数据 | Qasper | NarrativeQA | QuALITY | QMSum |
|---|---:|---:|---:|---:|
| Llama 2 Chat 基线 | 12.2 | 9.13 | 56.7 | 14.4 |
| 只用短 RLHF 数据 | 22.3 | 13.2 | 71.4 | 16.9 |
| + 预训练数据 | 23.7 | 16.6 | 76.2 | 17.8 |
| + 自生成长数据, 不算输入损失 | 35.7 | 22.3 | 59.3 | 13.4 |
| + 自生成长数据, 算输入损失 | 38.9 | 23.3 | 77.3 | 18.5 |

作者的解释是大多数样本输出远短于长输入, 输入输出长度失衡, 只在输出上算损失时信号太少. 用这套不含人工标注长数据的 SFT, 70B 的对话模型在 ZeroSCROLLS 的 10 个长文本任务中有 7 个超过 gpt-3.5-turbo-16k.

**Llama 3**: 只用已有的短 SFT 配方会让预训练得到的长上下文能力显著回退. 他们用早期版本的 Llama 3 生成三类合成数据: 长文档问答 (文档切成 8k 的块, 对随机块出题, 训练时给全文), 分层摘要 (先摘要每个 8k 块, 再摘要这些摘要), 代码仓库推理 (删掉一个被至少五个文件依赖的关键文件, 让模型找出依赖它的文件并补全代码). 按 16k, 32k, 64k, 128k 分档. 消融的结论是混入 0.1% 的合成长数据, 长短任务综合最好. DPO 阶段只用短数据, 只要 SFT 模型的长上下文能力够好, 长任务不受影响.

**ProLong**: 只用短的 UltraChat (平均 1.2k token, 最长 4.1k) 做 SFT 效果最好. 最终模型的 SFT 在 UltraChat 上训 1B token, 学习率 $2\times10^{-5}$ 余弦衰减到 $2\times10^{-6}$, 每步 4M token. 合成长数据按 40% 问答, 30% RAG, 30% 摘要配置, 混入比例的影响 (原文表 8, 按 token 计):

| 合成数据比例 | JsonKV | RAG | Re-rank | ICL | QA | 摘要 | 平均 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 0% | 65.7 | 58.1 | 38.5 | 80.3 | 49.7 | 42.1 | 55.7 |
| 1% | 61.5 | 57.0 | 38.3 | 80.8 | 45.3 | 41.5 | 54.1 |
| 10% | 70.3 | 55.5 | 36.1 | 80.6 | 41.7 | 39.4 | 53.9 |
| 50% | 45.8 | 48.8 | 18.8 | 70.5 | 42.3 | 33.3 | 43.3 |

换用 Llama-3-70B 作为生成器, 结论不变.

### 4.2 分歧怎么理解

ProLong 作者给了两个假设. 第一, 之前的工作长上下文继续训练不够, 合成长指令实际上充当了额外的长训练数据. 第二, Llama 3.1 的私有指令数据量大得多, 在大量短指令上 SFT 时, 混入合成长数据能防止长上下文能力退化; ProLong 的指令集小, 不存在这个问题.

实际操作上可以这样取舍: 长上下文继续训练充分 (数十 B token) 且 SFT 数据量不大时, 先试只用短指令; SFT 数据量大或者 SFT 后长任务明显掉分时, 混入少量 (0.1% 量级) 合成长数据. 无论哪种, 都要在 SFT 后重新跑长上下文评测.

## 5. LongLoRA 与失效模式

### 5.1 LongLoRA 的 S²-Attn

[Chen et al. (2023)](https://arxiv.org/abs/2309.12307) 的出发点是: 推理需要全注意力, 但微调可以用稀疏的局部注意力近似. 移位稀疏注意力 (shifted sparse attention, S²-Attn) 把序列切成大小为 $G$ 的组, 每组内部做注意力. 为了让信息在组间流动, 一半的头把分组整体平移 $G/2$.

以 8192 长度, 组大小 2048 为例: 第一种分组下第一组是第 1–2048 个 token; 平移后的分组从第 1025 个 token 开始, 第一组是 1025–3072, 开头和结尾各 1024 个 token 拼成一组. 两种分组各用在一半的头上. 实现只要两步: 在一半的头上平移 token, 把 token 维度转置到 batch 维度. 原文说两行代码就够.

训练用 S²-Attn, 推理时换回标准注意力, 模型结构不变. 位置编码用 PI.

### 5.2 放开 embedding 和 norm

LoRA 只在线性层上加低秩更新. 原文发现这在长上下文适应上效果差, 而且提高秩也没用. 32k 目标长度, Llama2 7B, PG19 困惑度 (原文表 2):

| 方法 | 困惑度 |
|---|---:|
| 全量微调 | 8.08 |
| LoRA, 秩 8 | 11.44 |
| LoRA, 秩 256 | 11.98 |
| LoRA 秩 8 + 放开 norm | 10.49 |
| LoRA 秩 8 + 放开 embedding | 8.29 |
| LoRA 秩 8 + 放开 norm 和 embedding | 8.12 |

放开的参数量很小: Llama2 7B 里 embedding 不到 2%, norm 不超过 0.004%. 作者把这个改进版叫 LoRA+.

### 5.3 LongLoRA 的效果与边界

在单台 8×A100 上, LongLoRA 能把 Llama2 7B 微调到 100k, 13B 到 64k, 70B 到 32k. 相比全量微调, 显存最多省 1.8 倍; 相比普通 LoRA, S²-Attn 让训练最多快 1.8 倍. 作者还自己收集了长指令数据集 LongAlpaca, 针对技术论文, 科幻小说和其他书籍设计各类问题, 用 LongLoRA 在上面做 SFT, 和第 4 节三篇论文的合成长指令是不同的来源.

边界: Fu et al. 的表 3 里, LongLoRA 7B (100k) 的 MMLU 只有 37.9, 低于其他 LLaMA-2 7B 系模型 (42–44), NIAH 70.0 也低于 Fu et al. 的 88.0. 他们认为原因有两个: 训练时用了稀疏注意力, 以及没有上采样长文档. LongLoRA 适合资源受限的场景; 资源允许时, 全注意力继续训练加上合适的数据配比效果更好.

另一条省资源的路是序列并行. Llama 3 用上下文并行 (context parallelism) 在 128k 上训练, ProLong 用序列并行训练 512k. 二者的实现差异见 [2.7.3](../../../2-核心原理与架构/2.7-长上下文与外推技术/2.7.3-长上下文推理优化/2.7.3-长上下文推理优化.md) 第 4.1 节.

### 5.4 失效模式

下表按训练流程排列: 前两行出在继续预训练的长度与评估上 (第 1.2, 1.3 节, 第 2 节和第 3.5 节), 第 3, 4 行出在长短数据和领域的配比上 (第 3.1 到 3.4 节), 第 5, 6 行出在 SFT 数据上 (第 4 节), 最后两行出在打包和 LoRA 的实现细节上 (第 3.6 节和第 5 节). 「检查」一列给的阈值和做法都来自前文引用的消融, 换了模型规模或数据来源要重新测.

| 现象 | 可能原因 | 检查 |
|---|---|---|
| 继续训练后 NIAH 过不了目标长度 | base 太小; 训练长度不够; 长文档没上采样 | 对照 base 下界 (2.7.1 第 4.5 节); 加长训练长度 (第 3.5 节); 按来源上采样 |
| 验证损失和别的配方差不多, 检索差很多 | 损失被局部预测主导 | 用检索和下游任务做消融, 不用损失挑配方 |
| 短任务掉分 (尤其数学, MMLU) | 长数据比例过高; 短数据质量差 | 长数据不超过约 60%; 用高质量短数据混合 |
| 某个领域变差 | 只上采样了书或代码 | 按来源上采样, 或代码 + 书各半 |
| SFT 后长任务掉分 | SFT 全是短数据且量大 | 混入少量合成长数据; SFT 后重新评测 |
| SFT 后长任务没变好 | 只在输出上算损失, 长输入的信号太少 | 对长输入也算语言模型损失 |
| 打包后跨文档干扰 | 不同文档的 token 互相可见 | 文档级注意力掩码 |
| LoRA 长度适应困惑度降不下来 | embedding 和 norm 被冻住 | 放开这两类参数 |

# RAG：从可检索证据到可审计回答

检索增强生成（Retrieval-Augmented Generation, RAG）把外部语料检索结果作为生成模型的输入。它适合知识需要更新、来源需要追溯或内容不能全部写入模型参数的任务，但**不会自动保证正确、及时、便宜或安全**。语料可能过期，检索可能漏掉关键证据，生成模型可能误读证据，引用也可能只“看起来相关”。

Lewis 等人在 2020 年的 RAG 论文中研究了参数记忆与非参数记忆结合的知识密集型 NLP 模型；这里讨论的是更广的工程系统：从源文档、权限和索引一直到回答、引用、拒答与线上监控。[原始 RAG 论文](https://arxiv.org/abs/2005.11401)

## 2. 一个可审计的最小数据流

一次查询至少应留下下面这条证据链：

1. **请求边界**：调用者身份、租户、时间、查询文本和允许访问的数据域。
2. **语料快照**：源对象版本、内容哈希、解析器与切分器版本、权限快照、有效时间。
3. **检索运行**：查询改写、过滤条件、稀疏与稠密候选、索引版本、参数与耗时。
4. **选择运行**：融合、去重、重排、证据覆盖检查和最终片段顺序。
5. **生成运行**：模型版本、提示模板版本、上下文快照、输出与停止原因。
6. **验证结果**：答案命题、对应证据、引用定位、拒答原因、自动检查与人工反馈。

这不是要求永久保存所有明文。敏感内容可以保留受控快照引用、哈希和审计事件；保留期限与可见范围由数据策略决定。

## 3. 先判断是否应该使用 RAG

### 3.1 适合

- 答案必须依据一组可管理、可授权、可更新的文档或记录；
- 用户需要打开原文核验，而不只是接受模型参数中的“记忆”；
- 问题能被映射到文本、表格、数据库或搜索索引中的证据；
- 系统可以维护评测集，并接受检索和生成带来的额外延迟与故障面。

### 3.2 不应默认使用

- 纯创作、改写、翻译等任务没有外部事实依据要求；
- 需要精确聚合、联接或事务一致性的结构化问题，应优先使用受控查询或业务 API；
- 语料无合法使用权、权限无法同步，或删除无法传播到索引；
- 没有证据标注与回归集，却希望用“相似度看起来不错”代替验收；
- 高风险决策要求专业人员或确定性规则审批，RAG 只能提供材料，不能取得授权。

RAG 与微调也不是代际替代关系。微调可改变行为、格式或任务适配，RAG 可提供外部证据；是否组合取决于基线实验。不能脱离模型、硬件、数据规模和服务目标，宣称 RAG 必然便宜两个数量级、更新必然是毫秒级或是“当前最优解”。

## 4. 三类口径必须分开

| 口径 | 可写成什么 | 不应写成什么 |
|---|---|---|
| **事实** | 原论文定义、官方文档支持的索引行为、带版本的数据卡 | “业界都这样做”“所有向量库复杂度相同” |
| **实验结果** | 在指定语料、查询集、模型、硬件和参数下测得的指标与置信区间 | 把某论文或厂商样例的提升外推到所有任务 |
| **工程选择** | 本系统采用的切分、融合、阈值、缓存、拒答和发布规则 | 把启发式默认值包装成学术定律 |

需要避免的常见误区包括：归一化不会使带负分量的 embedding 变成非负；ANN 没有统一的 $O(d\log N)$ 保证；检索到准确上下文不保证生成答案正确；Transformer cross-encoder 的主要前向成本不能简写成 $O(L_qL_d)$；Recall 也不必然优先于 Precision、nDCG、延迟或权限正确性。

## 5. 最小可复现实验

不要先换模型。先固定一组版本化的查询与证据标注，跑出四段基线：

1. 只做关键词/稀疏检索；
2. 只做稠密检索；
3. 融合后重排；
4. 加入生成、引用与拒答。

每次只改变一个因素，并保存：语料快照、查询集、相关性标注、索引和模型版本、参数、硬件、随机性、检索结果、最终回答、每阶段耗时及成本。检索层至少报告 Recall@k 或 hit rate、MRR/nDCG 中与任务匹配的指标；生成层至少报告答案任务指标、命题支持、引用正确性与覆盖率、拒答表现。不同阶段的指标不能混成一个“RAG 分数”。

BEIR 官方仓库提供异构 IR 数据集和统一评测接口，同时明确提醒使用者自行确认数据质量、许可与引用；它适合做检索器的外部压力测试，不代替私有业务分布的评测。[BEIR 官方仓库](https://github.com/beir-cellar/beir)

# 上下文工程：契约、预算、检索与安全边界

上下文工程不是“把更多文字塞进窗口”，而是决定模型在一次调用中能看到哪些指令、证据、状态、工具和历史，以及它们如何排序、截断、缓存、追踪和隔离。窗口长度只是容量上限；信息是否相关、可信、可定位并处在正确权限边界，决定模型能否可靠使用它。

> **时效与口径**：本文截至 2026-09-01。不同模型和 API 对角色、工具 schema、图像、隐藏控制 token、输入/输出合计方式及缓存计费的定义不同。设计必须绑定具体模型、tokenizer、chat template 和服务版本，不能只按字符数或厂商宣传的最大窗口估算。

## 1. 先写“上下文契约”

每一种上下文单元都应有来源、优先级、信任级别、生命周期和预算，而不是最后一刻拼字符串。

| 单元 | 作用 | 信任与权限 | 典型失效 |
|---|---|---|---|
| 平台/系统指令 | 身份、规则、输出与安全边界 | 高优先级，但仍需服务端强制控制 | 规则冲突、过长、不可测试 |
| 用户请求 | 当前目标和用户提供的数据 | 用户可控，不自动可信 | 越权、歧义、直接注入 |
| 对话状态 | 已确认决策、未决问题、任务进度 | 来自历史，应可追溯 | 过时、错误摘要、角色混淆 |
| 检索证据 | 文档、数据库、搜索结果 | 外部数据，不是指令 | 召回错误、陈旧、间接注入 |
| 长期记忆 | 跨会话偏好与稳定事实 | 需授权、来源与过期时间 | 错记、隐私泄露、跨用户串扰 |
| 工具 schema | 模型可请求的操作接口 | 能力描述不等于执行授权 | 工具过多、参数含糊、权限过宽 |
| 工具结果 | 外部系统返回的数据 | 默认不可信，可能含攻击文本 | 超长、伪造指令、敏感信息 |
| 输出约束 | JSON/schema、引用、长度和停止条件 | 应由运行时同时验证 | 只靠自然语言约束 |

契约至少回答：

1. 哪些内容可以发给模型，哪些必须留在服务端？
2. 冲突时由哪一层裁决？
3. 每个事实来自哪里，何时失效？
4. 模型能建议什么，执行器允许做什么？
5. 超出预算时按什么策略降级，而不是随机截断？

## 2. Token 预算必须在调用前闭合

对输入与输出共享窗口的常见接口，可用下式做初始预算：

$$
T_{\text{system}}+T_{\text{tools}}+T_{\text{history}}
+T_{\text{memory}}+T_{\text{retrieval}}+T_{\text{current}}
+T_{\text{output-reserve}}+T_{\text{margin}}
\le W.
$$

$W$ 是该模型版本公开并被当前服务端接受的窗口上限。预算时要使用实际 tokenizer 与 chat template；角色标记、工具定义、结构化输出 schema、图像 token 和服务端包装都可能计入。最终以 API 的 usage 字段和本地序列化快照校验。

推荐先保留：

- 输出上限与停止所需余量；
- 当前用户任务和不可丢约束；
- 最小必要的系统规则与工具；
- 经过筛选的证据；
- 仍影响当前任务的状态；
- 最后才是可替代的逐字历史。

当预算不足时，应显式选择“减少候选、压缩历史、二次检索、分步执行或拒绝”，而不是从左侧机械截断。

## 3. 同一窗口也有真实内存成本

上下文 token 不只是计费单位，还会进入 prefill 并形成 KV cache。对标准 MHA/GQA/MQA，纯 K/V 数值载荷为：

$$
M_{\text{KV}}
=B\times L\times N_{\text{layers}}\times 2
\times N_{\text{kv-heads}}\times d_{\text{head}}\times s_{\text{bytes}}.
$$

Meta 官方 SKU 给出 Llama 3.1 70B 为 80 层、64 个 query heads、8 个 KV heads、hidden dim 8192，因此 head dim 为 128。[Meta llama-models SKU](https://github.com/meta-llama/llama-models/blob/main/models/sku_list.py)

在无共享、无块尾开销的 BF16 口径下：

$$
1\times8192\times80\times2\times8\times128\times2
=2.5\ \text{GiB}.
$$

单请求 8K 约 2.5 GiB，16 条同长度活动序列约 40 GiB。这里用的是 8 个 **KV heads**，不是 64 个 query heads；结果只含 K/V 数值载荷，不含权重、工作区、分页元数据或并行布局。完整推导见 [KV 缓存与内存优化](../../6-训练与推理优化/6.4-KV缓存与内存优化/6.4-KV缓存与内存优化.md)。

因此“窗口装得下”不等于“并发服务得起”。容量规划应同时看 prompt/output 长度分布、并发驻留序列、TTFT、每 token 延迟和 cache 分配。

## 4. 长上下文不保证长距离利用

Liu 等人在多文档问答和 key-value retrieval 的受控实验中发现，多种模型对证据位置敏感，相关信息位于开头或结尾时常优于位于中间；论文没有证明所有模型、所有任务都遵循固定 U 型曲线，也没有把现象归因为注意力二次复杂度。[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)

应用评测应改变而不仅是增加长度：

- 固定证据内容，分别放在前、中、后位置；
- 改变无关文档数量和相似干扰项；
- 分别测试单跳、多跳、精确复制和综合归纳；
- 记录证据是否被引用，而不只看答案是否流畅；
- 覆盖短、中、长多个区间，不只做最大窗口 needle test。

组织策略应先按任务语义决定：稳定规则放在清晰的高优先级区域；证据附 source ID；当前问题与输出要求靠近生成位置；但任何位置启发式都要以目标模型实测为准。

## 5. RAG 是证据选择管线

原始 RAG 工作把参数化生成器与可检索的非参数记忆结合，并在知识密集型任务上评估；它不是“向 prompt 塞向量库 Top-k”的同义词。[RAG 原论文](https://papers.neurips.cc/paper/2020/hash/6b493230205f780e1bc26945df7481e5-Abstract.html)

生产管线至少包含：

1. **查询理解**：保留原问题，同时生成可审计的检索 query 或过滤条件；
2. **召回**：按数据类型选择稀疏、稠密、结构化或混合检索；
3. **权限过滤**：先按租户、ACL、地域和时间范围限制候选；
4. **去重与聚合**：合并同源切片，避免一个文档挤占全部预算；
5. **重排**：用当前问题和候选共同评分；
6. **打包**：保留标题、来源、版本、时间、chunk ID 与可引用边界；
7. **生成**：要求答案区分证据、推断和未知；
8. **核验**：检查引用是否真的支持相邻主张。

长上下文与 RAG 不是二选一。长窗口可容纳更多原文，RAG 可减少无关内容和权限暴露；选择取决于语料规模、更新频率、审计要求、延迟和任务对完整阅读的需求。RAG 细节见 [RAG](../7.2-RAG/7.2-RAG.md)。

## 6. 压缩要标注信息损失

| 策略 | 保留什么 | 主要风险 |
|---|---|---|
| 滑动窗口 | 最近若干轮 | 丢失早期承诺、身份和约束 |
| 抽取式压缩 | 原文中的关键句/字段 | 选择器漏掉隐含关系 |
| 生成式摘要 | 语义概括和决策 | 否定词、数值、来源被改写 |
| 结构化状态 | 明确字段、任务和参数 | schema 覆盖不了开放语义 |
| 分层摘要 | 事件→阶段→全局概览 | 多次摘要累积漂移 |
| 按需回查 | 摘要加原文指针 | 依赖检索可靠性和原文可用性 |

摘要不是事实源。每条压缩状态最好保留：

- 原消息/文档 ID 和版本；
- 被抽取的事实、决策或未决项；
- 主体、作用域与有效期；
- 原文定位或可回查引用；
- 生成器版本与压缩时间；
- 是否由用户确认。

压缩器的离线评测要专门覆盖否定、数字、日期、身份、权限、未决问题和引用一致性。论文中的压缩率不能直接转成所有任务的质量承诺。

## 7. 记忆不是无限对话历史

可以把记忆分为：

- **工作状态**：当前计划、变量、工具结果和未决事项，任务结束后可丢弃；
- **情节记忆**：某次交互发生过什么，带时间与原始记录；
- **语义记忆**：经确认且相对稳定的偏好或事实；
- **程序性规则**：应用流程与策略，通常应版本化在服务端，而不是由模型自由写入。

写入长期记忆前要判定用户授权、稳定性、敏感性、主体和过期时间。读取时先过滤租户和权限，再按相关性与时效排序。模型提议的记忆不应未经验证直接成为系统事实；用户纠正和删除请求必须能传播到索引、摘要与缓存副本。

## 8. 工具 schema 也是上下文

工具名称、描述、参数 schema、枚举和示例都会占 token，也会影响模型选择。工具越多不一定越好：相似工具会增加歧义，宽泛字符串参数会把校验压力推给模型。

建议：

- 只注入当前任务可能使用的工具；
- 名称稳定且动词明确，参数使用窄类型、枚举和必填约束；
- 区分读取、写入、外发和破坏性操作；
- 工具结果包含状态、数据、错误类型和截断说明；
- 大结果保存在外部，只把摘要与可回查 ID 放回上下文；
- 模型输出的参数必须经 schema 与业务规则二次验证；
- 高风险操作在执行器层做鉴权、幂等和用户确认。

工具调用格式依模型模板而异，不能把某家族的 role/token 直接复制到另一模型。详见 [Function Calling](../7.4-FunctionCalling/7.4-FunctionCalling.md)。

## 9. 外部内容默认不是高权限指令

网页、邮件、文档、数据库字段和工具结果都可能包含“忽略上文”“泄露系统提示”“调用某工具”等文本。Greshake 等展示了恶意指令通过被检索内容进入 LLM 应用的间接提示注入路径；这说明检索内容不能因为来自工具就自动升级为可信指令。[Indirect Prompt Injection 原论文](https://arxiv.org/abs/2302.12173)

防线应落在系统架构，而不是寻找一句万能提示词：

1. 数据与指令使用不同结构和来源标签；
2. 检索前执行 ACL，检索后仍按不可信数据处理；
3. 模型只提出工具调用，独立执行器校验权限、参数与目的；
4. 读工具和写工具使用最小权限及独立凭据；
5. 外发、付款、删除和权限变更要求确定性策略与确认；
6. 敏感信息在进入模型前最小化或脱敏；
7. 记录证据到工具调用的因果链，支持事后审计；
8. 用真实攻击文档和工具输出做持续红队测试。

Agent 运行时的状态和权限边界见 [Agent](../7.3-Agent/7.3-Agent.md)。

## 10. 缓存分三层理解

| 缓存 | 缓存对象 | 命中条件 | 主要风险 |
|---|---|---|---|
| KV prefix cache | 已计算前缀的 K/V | 精确 token 前缀及模型运行条件兼容 | 跨租户泄漏、时序侧信道、低命中 |
| 检索缓存 | query/过滤条件到候选 | 数据版本与权限仍有效 | 陈旧、ACL 变化、索引不一致 |
| 答案/语义缓存 | 请求到最终输出 | 业务语义和用户权限允许复用 | 错答扩散、个性化串扰、不可解释命中 |

vLLM 的自动前缀缓存按 token 块及父前缀哈希复用，只缓存完整块；它减少重复 prefill，不会跳过新输出的 decode。[vLLM Prefix Caching](https://docs.vllm.ai/en/latest/design/prefix_caching/)

为了提高 prefix 命中率，可把稳定系统提示、工具定义和共享文档放在前面，把时间戳、request ID 等动态字段后移。但任何重排都不能改变安全优先级或模型专属 chat template。缓存键必须包含模型/adapter/template/数据版本与租户隔离信息。

## 11. 可观测性：保存“模型实际看见的版本”

每次调用至少记录可脱敏审计的：

- model、revision、tokenizer 与 chat template 版本；
- 各上下文区段 token 数及截断原因；
- 检索 query、候选 ID、分数、重排和最终引用；
- 记忆读取/写入 ID、版本、过期时间和用户授权；
- 工具 schema 版本、调用参数、权限判定和结果大小；
- prefix/retrieval/answer cache 的 hit/miss 与隔离键；
- prompt hash、输出、停止原因、TTFT 和端到端延迟；
- 安全过滤、人工确认和降级路径。

敏感原文不应为了可观测性无限保留。可用内容哈希、访问受控的原始记录和分层日志满足排障与隐私要求。

## 12. 评测矩阵

| 维度 | 变量 | 主要指标 |
|---|---|---|
| 预算 | 短/中/长，工具多少，证据多少 | 成功率、超限率、成本、延迟 |
| 位置 | 证据在前/中/后 | 正确率、引用支持率 |
| 检索 | 召回、重排、干扰、无答案 | Recall、MRR/nDCG、答案忠实度、拒答 |
| 压缩 | 原文/摘要/结构状态 | 事实保留、否定/数字错误、节省 token |
| 记忆 | 新鲜/过时/冲突/跨用户 | 正确读取、删除传播、串扰率 |
| 工具 | schema 版本、错误、超长结果 | 选工具、参数正确率、恢复率 |
| 安全 | 直接/间接注入、权限升级 | 攻击成功率、误拒率、未授权操作数 |
| 缓存 | hit/miss、版本变化、租户 | 命中率、TTFT、错误复用、隔离性 |

在线指标要与离线切片对应。平均成功率无法说明长上下文中间位置、无答案请求或高权限工具是否安全。

## 13. 上线检查清单

- [ ] 每类上下文都有来源、优先级、信任级别、生命周期和 token 上限。
- [ ] 使用实际 tokenizer/chat template 计数，并为输出和包装留余量。
- [ ] 不把窗口上限等同于有效利用率或可承载并发。
- [ ] RAG 先做 ACL，再召回、重排、打包和引用核验。
- [ ] 摘要保留原文指针，否定、数字、日期和权限做专项回归。
- [ ] 记忆写入需要授权、主体、来源、有效期和删除传播。
- [ ] 工具 schema 最小化，执行权限由模型外的确定性代码控制。
- [ ] 外部文档和工具结果按不可信数据处理。
- [ ] 三类缓存使用独立键、版本和租户隔离策略。
- [ ] 评测覆盖预算、位置、干扰、无答案、注入和版本变更。
- [ ] 保存可复现的上下文快照或哈希，不记录不必要的敏感原文。

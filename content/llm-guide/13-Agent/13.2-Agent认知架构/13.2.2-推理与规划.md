# 推理与规划：从逐步行动到有限搜索

Agent 规划不是“让模型写一段很长的思维过程”。工程上的计划应是可检查、可修改的任务结构：步骤、依赖、前置条件、允许工具、成功证据和失败去向。模型可以提议计划，宿主负责验证和推进。

> **隐私与审计边界**：模型 API 可能保留私有推理或只返回推理摘要。可靠审计不依赖完整思维链；应记录目标、计划摘要、动作参数、授权、环境结果和验证证据。

## 1. 推理文本、计划与控制流

| 对象 | 例子 | 适合承担的责任 |
|---|---|---|
| 推理文本或摘要 | “需要先确认当前版本” | 帮助模型组织当前选择；不能单独证明正确 |
| 结构化计划 | 步骤、依赖、状态、验收 | 可审查、可更新的任务表示 |
| 宿主控制流 | 循环、分支、并发、超时、审批 | 真正决定何时执行和停止 |
| 外部验证器 | 测试、查询、状态断言 | 判断目标是否达成 |

不要从自然语言计划中直接提取高风险命令执行。计划条目必须映射到受控动作契约，再经过授权。

## 2. 四种常见策略

### 2.1 直接生成

一次调用得到答案或工件。适合短任务、无外部副作用、结果容易验证的情况。它仍可配合结构化输出和最终验证，不一定需要 Agent 循环。

### 2.2 逐步行动（ReAct 类）

[ReAct](https://arxiv.org/abs/2210.03629)在研究设置中交错生成推理线索、动作和环境观察。工程实现可以把每步压缩为：

```text
读取受控状态
  -> 模型提出下一动作或最终答复
  -> 宿主校验与授权
  -> 工具执行并返回观察
  -> 验证进展并更新状态
```

它适合中间观察决定下一步的任务，例如调试、浏览和调查。缺点是调用次数随步数增加，早期错误可能进入后续状态，也可能发生循环。

### 2.3 计划—执行—重规划

先生成带依赖的计划，再由执行器逐步推进。推荐计划字段：

```yaml
step_id: collect-source
goal: 找到该结论的一手来源
depends_on: []
allowed_tools: [search, open_page]
preconditions: [network_allowed]
success_evidence: [official_url, exact_claim]
on_failure: replan_or_ask_user
status: pending
```

计划是状态，不是一次性长文本。环境结果推翻前提时，只更新受影响步骤，记录重规划原因。任务依赖明确、可以并行或需要里程碑时，这种方式更合适。

### 2.4 有限候选搜索

[Tree of Thoughts](https://arxiv.org/abs/2305.10601)把问题求解组织成候选“thought”状态的生成、评估和搜索。更一般地，系统可以在关键节点生成 $b$ 个候选，保留分数较高的 $k$ 个，再展开有限深度。

这种方法的成本近似随分支数、深度和评估次数增长。它只有在以下条件下值得使用：

- 候选之间确实代表不同可行路径；
- evaluator 能比随机选择更可靠地排序；
- 额外调用的价值高于延迟和费用；
- 有明确的搜索预算和停止条件。

若同一模型既生成又评估，候选可能高度相关，评估也可能共享盲点。应优先加入可执行验证或异构证据，而不是只增加“自我投票”。

## 3. Chain-of-Thought 与 Self-Consistency 的边界

Chain-of-Thought prompting 论文表明，在其模型和算术、符号、常识基准设置中，带推理示例可以改善表现；Zero-shot-CoT 研究表明特定触发提示在其设置中有效。这些都不是“激活内部真实推理”的普遍定律。

Self-consistency 从多条采样路径中聚合最终答案。对于答案可归一化、正确路径有机会形成多数的任务，它可能有帮助；对于开放文本、系统性错误或相关采样，多数票仍会一致地错。使用时应报告采样数、温度、归一化规则和额外成本。

生产系统不应要求向用户或普通日志暴露完整自由文本思维链。可返回简短理由、证据和计划摘要。

## 4. ReAct 的生产化改造

论文示例常用 `Thought / Action / Observation` 文本格式。生产系统更适合：

1. 模型以结构化调用项提出动作；
2. 宿主按工具 schema 解析，不使用脆弱正则；
3. 执行前校验身份、资源和副作用；
4. 工具结果带调用 ID、状态、来源与错误类别；
5. 结果作为不可信数据回填，不能覆盖系统策略；
6. 完成由验证器判定，而不是字符串出现 `Final Answer`；
7. 日志保存动作与证据，不保存不必要的私有推理。

ReAct 的独立教学价值在于**让外部观察进入下一次决策**，不是要求系统公开“内心独白”。

### 4.1 一条可审计但不暴露私有思维的完整轨迹

假设用户要求计算 `(23.4 × 17) - 8.6`，系统只开放无副作用的 `calculator`。下面记录的是状态转换和证据，不是模型的自由文本思维：

| 序号 | 轨迹事件 | 可审计记录 |
|---|---|---|
| 0 | 初始状态 | `objective=计算表达式`；`allowed_tools=[calculator]`；`max_calls=1` |
| 1 | 动作提议 | `tool=calculator`；`arguments={expression: "(23.4*17)-8.6"}` |
| 2 | 宿主授权 | schema 校验通过；字符白名单通过；工具只读；预算内，生成 `call_id=calc-001` |
| 3 | 工具观察 | `call_id=calc-001`；`status=ok`；`value=389.2`；记录工具版本和时间戳 |
| 4 | 独立验证 | 宿主以十进制定点规则复核结果，断言 `verified=true`；若不一致则进入错误分支，不写最终答案 |
| 5 | 完成 | 返回 `389.2`，并引用 `calc-001` 作为结果证据；状态标为 `succeeded` |

这条轨迹足以回答“系统执行了什么、为何允许、工具返回什么、如何判断完成”。它没有保存模型的隐藏推理，也没有让模型自己伪造工具观察。若工具返回超时，步骤 3 应记录结构化错误；状态机根据重试预算决定重试、换工具或请求用户，而不是把失败字符串当成数值继续计算。

## 5. 计划的六个质量维度

| 维度 | 检查问题 |
|---|---|
| 可执行 | 每一步是否能映射到允许的工具或人工动作？ |
| 可验证 | 是否有外部成功证据，而不是“模型认为完成”？ |
| 依赖正确 | 前置结果不存在时是否会错误并发？ |
| 风险分级 | 只读、可逆写入和高影响动作是否分开？ |
| 可恢复 | 失败后从哪里回退，哪些动作不可重放？ |
| 有界 | 最大步骤、时间、成本和无进展条件是否明确？ |

先执行只读侦察、再批准写操作，是高风险任务的常用分段方式。

## 6. 失败恢复

恢复策略必须按错误类型区分：

| 错误 | 例子 | 处理 |
|---|---|---|
| 结构错误 | 缺字段、非法枚举 | 拒绝执行，返回精确校验错误，有限重试 |
| 业务错误 | 资源不存在、状态冲突 | 刷新状态或修改参数，不原样重试 |
| 权限拒绝 | 超出作用域、缺批准 | 停止并请求合法授权，不尝试绕过 |
| 瞬时故障 | 限流、短暂不可用 | 仅对可重试错误退避，设置上限 |
| 副作用未知 | 超时但服务器可能已完成 | 用幂等键或操作 ID 查询状态 |
| 计划前提失效 | 依赖版本已变化 | 标记受影响步骤并重规划 |
| 无进展 | 重复动作、没有新观察 | 换策略、回退或升级人工 |

“再想一次”不是恢复策略；它必须改变动作或获取新证据。

## 7. 并行与依赖

只有互不依赖、不会争用同一可写状态的步骤才适合并行。并行前检查：

- 输入是否来自同一稳定版本；
- 两个步骤是否会修改同一文件、记录或账户；
- 取消其中一个时，另一个是否仍安全；
- 合并是否有结构化契约与冲突规则；
- 并发是否受速率、费用和凭据范围限制。

把并行写成“显著加速”而不记录临界路径和资源竞争是不充分的。应报告 wall-clock 分布、失败重试和合并成本。

## 8. 选择决策表

| 任务特征 | 建议起点 |
|---|---|
| 一步可完成、容易验证 | 直接生成 + 验证 |
| 环境反馈决定路径 | 逐步行动 |
| 依赖明确、可并行 | 计划—执行 |
| 关键决策存在少量可评分候选 | 有限搜索 |
| 高风险副作用 | 只读计划/预览 + 人工批准 |
| 无可靠 evaluator | 降低自治或增加人工验收 |

复杂系统可以混合，但每增加一个 Planner、Critic 或 Agent，都要通过消融证明其增益超过成本和新失败面。

## 9. 评测方法

固定模型、工具、环境和预算，对不同规划策略进行成对比较：

- 任务成功与首次成功；
- 计划合法率、依赖错误率和重规划次数；
- 工具选择、参数业务正确率和重复调用；
- 把正确状态改坏的退化率；
- 人工介入、权限拒绝和危险动作率；
- token、调用、延迟、费用及多次运行方差。

不要用不同论文的 12%、47%、89% 等数字拼出虚构的统一提升曲线。

# 反馈控制视角：能解释什么，不能证明什么

控制论为 Agent 提供了一套有用语言：目标、状态、观测、动作、反馈、扰动和停止。但“像控制系统”不等于已经拥有经典控制理论的稳定性保证。LLM Agent 的状态通常是离散且部分可见的，动作包含自然语言和外部工具，环境会变化，验证器也可能出错。

> **核心边界**：除非研究明确给出状态空间、动力学、控制律和证明条件，否则不能把 Lyapunov、PID、Kalman、Shannon 容量或一致性协议直接套在 LLM 轨迹上，再宣称 Agent 收敛、稳定或性能提升。

## 1. 一个足够用的离散闭环

把第 $t$ 步的可审计状态记为 $s_t$，模型或规则提出动作 $\hat a_t$，策略门 $G$ 结合身份和策略决定是否允许，执行器 $E$ 产生观察 $o_{t+1}$，状态更新器 $U$ 生成下一状态：

$$
\hat a_t=P(g,s_t),\qquad
a_t=G(\hat a_t,\mathrm{identity},\mathrm{policy}),
$$

$$
o_{t+1}=E(a_t),\qquad
s_{t+1}=U(s_t,a_t,o_{t+1}).
$$

这个记号的作用是划清接口，而不是证明 $P$ 最优或循环必然结束。工程上更应关注：$s_t$ 保存了什么、$G$ 是否在模型之外、$E$ 有何副作用、$U$ 会不会把错误观察写成长期事实。

## 2. 开环与闭环

### 2.1 开环

系统只根据最初输入生成结果，不读取执行反馈。对于文本改写等一次性任务，开环可能足够简单可靠；不能因为没有工具循环就称其“低级”。

### 2.2 闭环

系统执行动作后读取环境结果，再决定下一步。代码编写—运行测试—读取错误—修复，是典型闭环。反馈带来纠错机会，也带来新风险：错误日志可能误导，网页可能含提示注入，重复重试可能造成第二次副作用。

闭环可靠性来自**有信息的反馈 + 有边界的执行 + 正确的完成判定**，而不只是循环次数更多。

## 3. 可观测性：看得到什么

真实环境状态通常不能被 Agent 完整看到。例如网页截图不包含后台数据库，命令退出码不证明业务目标完成，HTTP 200 不证明写入内容正确。

可观察状态至少应区分：

| 内容 | 例子 | 真值地位 |
|---|---|---|
| 目标与约束 | 用户要求、禁止项、预算 | 控制运行，但仍可被用户更新 |
| 动作提议 | 工具名、参数、计划摘要 | 模型输出，不是已执行事实 |
| 授权决定 | 策略版本、批准人、作用域 | 宿主控制证据 |
| 环境观察 | 测试、API 返回、屏幕状态 | 需要验证来源与完整性 |
| 完成证据 | 目标断言、最终状态差异 | 应独立于模型自述 |

生产日志应记录这些外部可观察事件，而不是要求保存模型私有推理。计划摘要、工具调用、结果和验证证据足以支持大多数问题定位。

## 4. “误差”必须可测量

经典控制中的误差通常是可计算的目标差。开放式 Agent 任务没有天然的标量误差，因此不能把“模型觉得更接近目标”直接写成 $e_t$。

可用误差或进展信号包括：

- 失败测试数量、目标断言与当前状态的差异；
- 尚未满足的结构化约束；
- 有证据覆盖的子任务数；
- 权限拒绝、超时、重复动作和预算消耗；
- 经人工标注校准的 rubric。

如果无法定义可观察进展，就无法可靠做无进展检测。此时应缩小任务或增加人工检查，而不是编造“认知能量函数”。

## 5. 稳定性在工程上怎样表达

对通用 LLM Agent，稳定性更适合拆成可测试性质：

### 5.1 有界性

最大步骤、时间、token、费用、并发、进程、磁盘和网络请求均有上限。即使模型不断请求继续，运行也会停止。

### 5.2 无进展检测

对规范化后的工具名、关键参数、错误类别和环境版本生成动作指纹；连续重复而没有新证据时切换策略、回退或升级人工。

### 5.3 副作用稳定

只读动作可有限重试；写入动作使用预览、审批、幂等键、事务状态或补偿操作。网络超时不等于服务器没有执行。

### 5.4 状态一致性

原始事件追加保存，摘要带版本和来源；出现冲突时不静默覆盖。并行执行使用版本号、锁或合并规则，防止后写覆盖正确结果。

### 5.5 可恢复性

保留最近已验证检查点。故障后从明确状态恢复，而不是把一段可能过期的对话重新送给模型并假设可重放。

## 6. 控制论概念的安全用法

| 概念 | 可以帮助思考 | 不能直接推出 |
|---|---|---|
| 反馈 | 动作后必须读取与验证结果 | ReAct 一定优于开环 |
| 状态估计 | 观察不完整，要保留不确定性 | 摘要就是 Kalman filter |
| 稳定性 | 预算、停止、重复检测、回滚 | 存在未证明的 Lyapunov 函数 |
| 扰动 | 工具、网页、用户和环境会变化 | 加一个 Critic 就鲁棒 |
| 多控制器 | 规划、授权、执行、验证可分层 | 多 Agent 一定产生集体智能 |
| 延迟 | 旧观察可能导致错误动作 | 所有网页 Agent 都违反采样定理 |

类比应帮助提出测试，不应伪装成数学证明。

## 7. 反馈失效模式

| 失效 | 表现 | 优先控制 |
|---|---|---|
| 反馈错误 | 测试不覆盖需求、工具伪报成功 | 独立 evaluator、回查最终状态 |
| 反馈延迟 | 根据旧页面或旧版本继续操作 | 版本/时间戳、执行前重读关键状态 |
| 反馈污染 | 网页内容诱导越权调用 | 数据与指令隔离、敏感动作再授权 |
| 过度修正 | 正确结果被模型自评改坏 | 保留检查点、测退化率、外部验证优先 |
| 循环 | 同一动作和错误重复出现 | 指纹、无进展上限、替代策略 |
| 级联副作用 | 超时后重复发信或付款 | 幂等键、状态查询、人工升级 |

## 8. 多 Agent 与“共识”边界

多个语言 Agent 互相投票不等于分布式系统共识。Raft/PBFT 解决的是在规定故障模型下复制离散状态；模型投票处理的是可能相关、可能共同犯错的判断。多数票不能创造外部真值。

对多 Agent 系统，更稳妥的检查是：角色是否真的拥有不同信息或工具，消息是否带来源和版本，谁能提交最终状态，冲突怎样仲裁，失败是否会被放大。详见 [多 Agent 系统](../13.3-Agent系统工程/13.3.3-多Agent系统.md)。

## 9. 一个工程验收协议

1. 为任务定义外部完成判据和预算；
2. 记录初始状态版本和允许工具集合；
3. 对每次动作做结构、业务、授权和副作用检查；
4. 记录执行结果及来源，将外部内容标记为不可信数据；
5. 用 evaluator 判断进展与完成，而不是模型自述；
6. 连续无进展时回退、换策略或升级人工；
7. 结束时保存最终状态差异、验证证据和停止原因。

# 工具能力的分层：模型调用、MCP 与 Agent Skills

Function Calling、MCP 与 Agent Skills 经常被描述成依次取代的“三代工具调用”。这个说法会误导架构设计：三者解决的问题不同，可以同时存在于一次 Agent 运行中。

- **模型工具调用**回答：模型怎样提出一个具名动作及参数？
- **MCP** 回答：宿主怎样用共同协议发现并访问外部上下文和能力？
- **Agent Skills** 回答：怎样把可复用的任务说明、脚本、参考资料和资产按需交给 Agent？

它们都不等于授权系统，也不会替宿主执行高风险动作。

> **证据与时效边界**：本文截至 2026-09-01。协议和产品接口变化较快，具体字段以调用方锁定的模型 API、MCP 协议版本与 Skills 规范版本为准。

## 1. 先用一次完整运行定位三层

假设用户要求“读取销售表，按公司模板生成季度报告”：

1. 宿主识别并加载“季度报告”Skill 的任务说明和模板；
2. MCP 客户端向数据服务器发现读取表格的工具或资源；
3. 宿主把当前允许使用的工具契约提供给模型；
4. 模型生成工具名与结构化参数；
5. 宿主完成模式校验、身份授权和实际调用；
6. 工具结果作为不可信观察返回模型；
7. Agent 按 Skill 中的验收步骤检查报告。

这个例子中，Skill 没有替代 MCP，MCP 也没有替代模型的工具调用。是否准许读取销售表、输出能否外发，仍由真实身份、资源策略和用户审批决定。

## 2. 模型工具调用：动作提议接口

OpenAI 在 2023 年公开 Function Calling 后，“模型生成函数名与参数、应用执行函数、结果再回填模型”成为常见接口模式。不同供应商的消息字段并不完全一致，但稳定边界是：

```text
应用提供工具契约
  -> 模型提出调用项
  -> 应用解析与校验
  -> 应用授权并执行
  -> 应用回填工具结果
  -> 模型继续调用或作答
```

工具调用不是 RPC 本身。即使模型输出严格符合 JSON Schema，宿主仍需检查业务值、资源作用域和副作用。模型生成 `send_email` 不表示邮件已经发出，也不表示用户已批准收件人和正文。

模型是否会正确选工具，取决于模型训练、工具描述、候选工具集合、上下文和任务分布。不能笼统宣称“任何能输出 JSON 的模型都具有等价的原生工具调用能力”。

## 3. MCP：宿主与能力提供方之间的协议

MCP 让 host/client 与 server 以共同协议交换 tools、resources、prompts 等原语。它减少专有适配，却不规定模型一定如何规划，也不保证服务器可信。

| MCP 原语 | 主要用途 | 常见控制方 |
|---|---|---|
| Tools | 动态查询或产生动作 | 模型提议，宿主决定是否调用 |
| Resources | 可寻址的上下文或数据 | 应用选择、读取并附加 |
| Prompts | 可复用的提示模板或入口 | 用户或应用选择 |

“控制方”是交互设计，不是安全证明。MCP 服务器自报的名称、描述和客户端元数据不能替代认证；入站令牌也不应被直接透传给上游服务。协议版本与授权细节见 [工具使用与 MCP](./13.1.3-工具使用与MCP.md)。

MCP 不一定比应用内函数调用更慢，也不一定维护会话状态。延迟由传输、部署、目录大小、鉴权、工具本身和缓存决定；当前 `2026-07-28` 协议核心已改为无状态。需要比较时，应在同一工具与网络条件下测量端到端分位数。

## 4. Agent Skills：按需加载的任务知识包

[Agent Skills 规范](https://agentskills.io/specification)把 Skill 定义为带有 `SKILL.md` 的目录；YAML 元数据至少描述名称和用途，目录还可包含脚本、参考资料和资产。规范所强调的 progressive disclosure 可概括为：

1. 发现阶段只读取名称与描述；
2. 任务匹配时加载 `SKILL.md`；
3. 执行时按需读取引用资料或运行脚本。

典型目录是：

```text
quarterly-report/
├── SKILL.md
├── scripts/
├── references/
└── assets/
```

Skill 的价值是把程序性知识、质量标准和可复用资源版本化。它不是一种模型训练算法，不是天然跨产品兼容的可执行二进制，也不是权限容器。兼容程度取决于客户端支持的规范、工具和运行时；脚本仍需在受限环境中执行，资源仍需经过数据与版权治理。

## 5. 为什么“第一代—第二代—第三代”不成立

| 错误叙事 | 实际边界 |
|---|---|
| MCP 取代 Function Calling | MCP server 暴露的工具仍常通过模型工具调用进入决策循环 |
| Skill 取代 MCP | Skill 可引用 MCP 工具，也可完全不使用 MCP |
| Function Calling 天然无状态，MCP 天然有状态 | 状态由宿主、业务服务与协议版本共同决定 |
| MCP 必然增加不可接受的握手延迟 | 需要按具体传输和协议版本测量；不能从名称推断 |
| Skill 让完整任务自动可靠 | 说明和脚本仍可能错误，必须测试、授权和验收 |
| 显式“思考工具”等于公开真实内部推理 | 工具调用文本只是模型输出或控制接口，不是内部状态的完整窗口 |

架构演进更适合描述为**接口分层与生态标准化**：模型 API 提供结构化动作通道，协议层提供跨进程互操作，知识包提供按需任务上下文。三层并行演进。

## 6. 选型问题

### 6.1 只需要应用内工具调用

当工具数量少、与一个应用强绑定、由同一团队部署时，直接使用模型 API 的工具调用通常足够。仍需建立工具目录、服务端校验、授权、超时、幂等和审计。

### 6.2 需要跨宿主复用能力

当多个客户端要访问同一数据或工具服务，或能力由另一团队独立演进时，可以评估 MCP。需要额外确定协议版本、服务器信任、令牌 audience、网络边界、版本兼容和故障隔离。

### 6.3 需要沉淀可复用任务方法

当任务包含稳定流程、参考资料、模板或确定性脚本时，Skill 可以减少每次临时拼提示的漂移。应对触发条件、输出契约和边界样例做测试；不要把密钥和用户私密数据打包进可分发目录。

## 7. 可组合参考架构

| 层 | 主要工件 | 必要验证 |
|---|---|---|
| Skill | 任务说明、脚本、参考资料、资产 | 触发准确性、流程测试、来源与依赖审计 |
| Agent 编排 | 目标、状态、步骤、停止条件 | 重复动作、预算、失败恢复、完成验证 |
| 模型工具调用 | 工具名、参数、调用项 ID | 结构与业务参数校验 |
| MCP / 专有适配 | 工具、资源和提示的互操作消息 | 版本、认证、授权、服务器信任 |
| 执行平面 | 文件、网络、数据库、浏览器、代码 | 最小权限、隔离、幂等、审批、审计 |

任何一层失败都不能由下一层“自动修好”。例如 Skill 写着“只读”，并不能约束一个实际拥有写权限的服务器；MCP schema 合法，也不能证明资源属于当前租户。

## 8. 评测不要混成一个成功率

至少分开测量：

- Skill 是否在该触发时加载、在不该触发时保持未加载；
- 工具选择、参数结构与业务值是否正确；
- MCP 目录发现、版本协商、调用和错误是否兼容；
- 授权拒绝、高风险审批和提示注入防线是否生效；
- 端到端任务是否通过外部验证器；
- token、工具调用次数、延迟和费用分布。

如果只看最终成功率，就无法知道问题来自模型、Skill、协议、服务器、权限还是环境。

## 9. 验证清单

- [ ] 没有把模型的动作提议写成已经执行的动作。
- [ ] 没有把 MCP 写成认证、授权或沙箱的替代品。
- [ ] 没有把 Skills 写成协议或模型训练方法。
- [ ] 所有工具都有输入、输出、错误、副作用与幂等说明。
- [ ] 协议和 API 版本已经锁定并做兼容测试。
- [ ] Skill 脚本与资料的来源、依赖和权限已经审计。
- [ ] 高风险动作由执行平面再次授权和必要审批。
- [ ] 评测能把各层失败分开定位。

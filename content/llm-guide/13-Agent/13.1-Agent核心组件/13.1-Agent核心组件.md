# Agent 核心组件：状态、动作、工具、验证与控制

把 Agent 简化成“LLM + 工具”会漏掉决定可靠性的部分：任务契约、显式状态、授权策略、执行隔离、结果验证、停止条件和可观测性。一个模型能力很强但没有这些边界的系统，可能会调用工具，却很难稳定完成任务。

> **证据与时效边界**：本文截至 2026-09-01。接口示例强调跨框架不易变化的系统边界，不把某个 SDK 的类名、单次基准分数或厂商默认值写成通用定律。

## 2. 用状态转移描述 Agent

设第 $t$ 步可审计状态为 $s_t$，模型或规则根据目标 $g$ 和状态提出候选动作 $\hat{a}_t$。策略门 $G$ 检查动作是否被允许，执行器 $E$ 与环境交互得到观察 $o_{t+1}$，状态归约器 $U$ 再生成新状态：

$$
\hat{a}_t = P(g, s_t), \qquad
a_t = G(\hat{a}_t, \text{identity}, \text{policy}), \qquad
o_{t+1} = E(a_t), \qquad
s_{t+1} = U(s_t, a_t, o_{t+1}).
$$

这只是系统接口的记号，不是假设所有 Agent 都是马尔可夫过程，也不意味着自由文本思维链必须进入状态。生产状态应优先保存可核验信息：目标、计划摘要、调用记录、工具结果、来源、验证结论和待解决问题。

循环在以下任一条件成立时结束：验证器确认成功；出现不可恢复错误；预算耗尽；检测到无进展；或需要用户提供信息/授权。缺少显式停止条件的 Agent 很容易把“继续尝试”误当成进展。

## 3. 七类核心组件

### 3.1 任务契约与完成判定

任务契约定义目标、交付物、约束、验收方法和预算。它应当把“写得像完成”与“实际上完成”分开。

示例：代码修复任务的完成契约可以要求指定测试通过、没有新增静态检查错误、变更只位于允许目录，并附上变更摘要。模型的最终自然语言只是说明，不是完成证据。

### 3.2 状态与记忆

至少区分四类数据：

| 数据 | 例子 | 典型生命周期 |
|---|---|---|
| 运行状态 | 当前步骤、预算、待办、审批状态 | 单次运行 |
| 事件日志 | 工具参数、结果、错误、状态变更 | 审计保留期 |
| 任务知识 | 文件内容、检索证据、API 返回 | 任务或项目 |
| 长期记忆 | 用户偏好、稳定事实、历史经验 | 跨会话，但应可更正和删除 |

不要把所有历史消息直接称作“记忆”。原始事件日志负责可追溯，摘要负责节省上下文，检索索引负责召回，三者的用途和真值地位不同。压缩策略见 [记忆压缩](./13.1.2-记忆压缩.md)。

### 3.3 动作提议器与规划器

模型可以直接选择下一工具，也可以先产出结构化计划，再由执行器逐步推进。应根据任务决定规划粒度：

- 短、反馈密集的任务适合边做边规划。
- 依赖关系明确的长任务适合先生成可修订计划。
- 高风险任务应先生成只读预览，批准后再执行写操作。

计划不是承诺。环境观察改变假设时应允许重规划，但每次重规划都要保留原因和已完成事实，避免重复工作。

### 3.4 工具目录与动作契约

工具定义应至少包含：稳定名称、用途、输入模式、返回结构、错误类别、权限、超时、副作用、幂等性和速率限制。工具数量越多、描述越相似，工具选择越容易混淆；可以按当前任务动态缩小候选集。

模型发出的工具调用是建议，不是执行。宿主必须解析、校验、授权并决定是否调用。MCP 是连接工具和上下文提供方的一种协议，不替代这些宿主责任，详见 [工具使用与 MCP](./13.1.3-工具使用与MCP.md)。

### 3.5 策略门与执行器

策略门解决“能不能做”，执行器解决“怎么做”。两者分离有利于测试和审计：

- 校验结构、类型、枚举、长度和值域。
- 将相对路径、URL、资源 ID 归一化后再检查作用域。
- 根据调用者身份和当前授权计算实际权限，不信任模型声称的权限。
- 对删除、支付、外发和公开发布等动作显示预览并请求确认。
- 对进程、网络、文件和凭据使用隔离环境与最小权限。

### 3.6 观察归约与验证器

工具输出可能过长、含噪声、含恶意指令或包含敏感信息。观察归约器应保留状态码、关键字段、证据定位和错误类别，再把适量内容送回模型。不要让任意网页或日志原样获得与系统指令相同的信任级别。

验证器独立回答“目标是否达成”。优先级通常是：确定性检查（测试、模式、数据库断言）高于规则评分，高于模型裁判。使用模型裁判时，要固定量表、保留证据，并测量与人工标注的一致性和偏差。

### 3.7 编排器与可观测性

编排器负责循环、并发、超时、取消、重试、预算、检查点和人工升级。可观测性至少关联以下对象：

- `run_id`、`step_id`、父子调用和时间戳；
- 模型、提示、工具目录与策略版本；
- 动作提议、授权决定、执行结果和验证证据；
- token、延迟、费用、重试与缓存命中；
- 失败类别和最终停止原因。

不要把凭据、完整个人数据或模型内部私有推理记录进常规追踪。审计需要的是决策接口和外部证据，不是无限保存所有上下文。

## 4. 最小控制循环

下面的标准库示例刻意不绑定模型供应商。`propose` 可以由 LLM、规则或两者组合实现；执行前后分别经过授权和验证。

```python
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass(frozen=True)
class Action:
    name: str
    arguments: dict[str, Any]


@dataclass
class RunState:
    goal: str
    steps: list[dict[str, Any]] = field(default_factory=list)
    done: bool = False
    result: Any = None


def run_agent(
    state: RunState,
    propose: Callable[[RunState], Action],
    authorize: Callable[[Action], None],
    execute: Callable[[Action], Any],
    verify: Callable[[RunState, Any], tuple[bool, Any]],
    max_steps: int = 12,
) -> RunState:
    for step_no in range(max_steps):
        action = propose(state)
        authorize(action)  # 拒绝时抛出受控异常，不执行工具
        observation = execute(action)
        state.steps.append({
            "step": step_no,
            "action": action,
            "observation": observation,
        })
        state.done, state.result = verify(state, observation)
        if state.done:
            return state
    raise RuntimeError("step budget exhausted without verified success")
```

这个示例仍省略了生产系统必需的模式校验、取消、超时、持久化、幂等、敏感数据处理和错误分类。它的价值在于明确：模型不直接持有执行权限，成功也不是由模型单方面宣布。

## 5. 重试、并发与幂等

### 5.1 重试不是默认安全

只有明确可重试的瞬时错误才应自动重试，并使用指数退避、抖动和上限。参数错误、权限拒绝和业务冲突通常需要修正动作，原样重试没有意义。

对于创建订单、发信、支付等非幂等操作，客户端超时并不能证明服务器没有完成动作。应使用幂等键、操作 ID 或“查询后决定是否重试”的协议。

### 5.2 并发需要依赖分析

只读且互不依赖的检索可以并行；会修改同一对象、依赖上一结果或争用有限资源的调用应串行或加锁。并行调用还要定义结果合并、部分失败、取消传播和预算分配，不能只依赖模型一次生成多个调用。

## 6. 组件级评测

不要只测最终答案。为每层建立可定位的指标：

| 组件 | 可测问题 |
|---|---|
| 动作提议 | 在固定任务集上，工具名和参数是否正确？ |
| 模式校验 | 缺字段、额外字段、错误类型和值域能否拒绝？ |
| 授权 | 越权路径、跨租户 ID、危险 URL 和未批准写操作能否拦截？ |
| 执行器 | 超时、取消、重试和幂等是否符合契约？ |
| 观察归约 | 关键错误、引用和未完成状态是否被保留？ |
| 验证器 | 与人工金标的一致性如何？能否识别假成功？ |
| 编排器 | 循环、无进展、预算耗尽和依赖故障能否正确停止？ |

最终端到端成功率只有在这些运行条件一致时才可比较。否则你可能把更大的调用预算、更宽权限或更多人工干预误认为模型能力提升。

## 7. 常见架构错误

1. **把聊天记录当数据库**：没有版本、来源和冲突处理，错误会被不断复述。
2. **模型直接执行副作用**：跳过了结构校验、授权和审批。
3. **工具返回即成功**：没有验证业务状态。
4. **所有错误都重试**：造成循环或重复副作用。
5. **摘要覆盖原始事件**：失去审计和纠错依据。
6. **把隐藏推理当日志**：既不稳定，也可能暴露敏感内容；应记录外部动作与证据。
7. **只做正常路径测试**：没有依赖故障、恶意输入、取消和预算边界。

## 8. 上线验收清单

- [ ] 目标、成功验证器、停止条件和预算已显式定义。
- [ ] 状态、事件日志、检索知识和长期记忆分开管理。
- [ ] 工具输入与输出均有机器可校验契约。
- [ ] 模型提议与实际执行之间有授权层。
- [ ] 每个副作用动作标注幂等性和审批要求。
- [ ] 工具结果按不可信输入处理，并保留来源定位。
- [ ] 有循环、无进展、超时、取消和部分失败处理。
- [ ] 验证器不依赖 Agent 的自我宣告。
- [ ] 追踪数据足以复盘，同时遵守数据最小化。
- [ ] 组件评测和端到端评测都能在固定版本上重放。

# 结构化输出：从合法 JSON 到业务可执行契约

结构化输出把模型生成结果变成机器可消费的数据，但“能解析”只是第一层。一个对象可以是合法 JSON、完全符合 JSON Schema，却仍然包含不存在的订单号、错误日期或越权操作。可靠系统必须把**语法、模式、业务语义、授权与执行结果**分层处理。

> **证据与时效边界**：本文截至 2026-09-01。OpenAI 等供应商的 Structured Outputs 和 Function Calling 字段会演进，示例以当前官方 API 参考说明能力边界；实际可用关键字、模型支持和流式事件必须以所选模型与 SDK 的官方文档为准。

## 1. 五层保证

| 层 | 要回答的问题 | 典型机制 |
|---|---|---|
| 语法 | 能否被 JSON/XML 解析器读取？ | JSON parser、XML parser |
| 模式 | 字段、类型、枚举和层级是否符合契约？ | JSON Schema、XSD、类型模型 |
| 业务 | 值是否真实且满足领域规则？ | 数据库查询、交叉字段规则、事实核验 |
| 授权 | 当前身份是否允许请求的动作和资源？ | 服务端 IAM / policy engine |
| 执行 | 副作用是否真正完成且可验证？ | 事务、幂等键、状态回查、审计日志 |

Structured Outputs 主要增强前两层。它不能证明 `invoice_id` 存在，也不能替应用决定用户是否能退款。

## 2. 三种常见输出模式

### 2.1 JSON mode

JSON mode 的目标通常是生成语法有效的 JSON。它不一定要求结果符合你的字段模式。相比从 Markdown 代码块或自然语言中截取 JSON，它减少了解析失败，但仍要做模式验证。

### 2.2 JSON Schema 结构化响应

模型根据提供的 JSON Schema 生成最终响应对象。适合信息抽取、分类、UI 数据、报告中间表示等“返回数据给应用”的场景。

OpenAI Responses API 当前通过响应的 `text.format` 配置结构化 JSON；API 参考将 `json_schema` 与较旧的 `json_object` JSON mode 区分。不同模型和 SDK 支持情况可能不同，不应从旧版 Chat Completions 示例推断当前字段。

### 2.3 Function / Tool calling

模型生成工具名和参数，宿主决定是否执行。它适合“请求应用做某事”，而不是单纯返回一份数据。工具参数即使经过严格模式约束，执行端仍要重新验证业务和权限。

不要为了强迫模型返回 JSON 而虚构一个无意义工具；也不要把需要副作用的动作伪装成普通结构化文本而绕过授权层。

## 3. 设计一个可维护的 JSON Schema

下面的模式用于输出带证据的抽取结果：

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "status": {
      "type": "string",
      "enum": ["complete", "needs_review"]
    },
    "summary": {"type": "string", "minLength": 1},
    "amount": {"type": ["number", "null"], "minimum": 0},
    "currency": {
      "type": ["string", "null"],
      "pattern": "^[A-Z]{3}$"
    },
    "evidence": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "source_id": {"type": "string", "minLength": 1},
          "locator": {"type": "string", "minLength": 1}
        },
        "required": ["source_id", "locator"],
        "additionalProperties": false
      }
    }
  },
  "required": ["status", "summary", "amount", "currency", "evidence"],
  "additionalProperties": false
}
```

### 3.1 关键设计原则

- **明确 dialect**：JSON Schema 官方建议用 `$schema` 表明版本。MCP `2026-07-28` 将工具输入与输出模式提升为完整 JSON Schema 2020-12；模型供应商的 Structured Outputs 仍可能只支持其中一个子集，接入前要分别确认协议验证器与模型 API 的能力。
- **区分缺失与空值**：字段可空不等于字段可缺失。稳定下游通常让字段始终存在，用 `null` 表示来源中没有值。
- **关闭意外字段**：当消费者需要严格契约时使用 `additionalProperties: false`，避免拼写错误悄悄通过。
- **优先枚举与边界**：状态、类别、长度、数值范围和数组上限尽量编码进模式。
- **保持结构浅且聚焦**：复杂 `anyOf`、递归和深层嵌套增加模型与消费者负担，也可能超出供应商支持子集。
- **版本化**：生产契约要有独立版本；新增必填字段属于破坏性变更。

模式只表达机器结构。像“结束日期不得早于开始日期”“币种必须与账户一致”这样的跨字段或外部状态规则通常仍需业务校验器。

## 4. 约束解码如何工作

标准自回归模型在每一步给词表 token 分配概率。约束解码根据当前前缀和语法状态计算允许的 token 集合 $V_t^{\mathrm{valid}}$，把不允许 token 的概率质量屏蔽，再从合法集合中选择：

$$
p_C(x_t \mid x_{<t}) =
\frac{p(x_t \mid x_{<t})\,\mathbf{1}[x_t \in V_t^{valid}]}
{\sum_{v \in V_t^{valid}} p(v \mid x_{<t})}.
$$

实现可能把正则、JSON Schema 或上下文无关文法编译为自动机/解析器状态，并预计算 token 与字符状态的兼容关系。供应商的内部实现未必相同，不能笼统声称所有 Structured Outputs 都使用 DFA 或某个开源库。

约束解码能阻止许多语法错误，但有四个边界：

1. 模型仍可能在多个合法值中选错一个。
2. 供应商通常只支持 JSON Schema 的一个子集。
3. 拒答、内容过滤、超时或达到输出上限可能导致没有完整对象。
4. 复杂模式可能增加编译、首 token 或逐 token 约束开销，实际延迟应测量而不是套用固定百分比。

## 5. 生成后仍要验证

推荐的消费流水线：

```text
接收 API 结果
  -> 检查响应状态、拒答与 incomplete 原因
  -> 只读取预期的输出项类型
  -> 完整缓冲后解析 JSON（或使用 SDK 的 typed helper）
  -> 用声明的 schema/dialect 再验证
  -> 运行跨字段与外部事实校验
  -> 执行身份和权限检查
  -> 写入事务或调用工具
  -> 回查状态并记录审计证据
```

服务端复验不是不信任约束解码，而是防止模型版本差异、SDK 错误、流式截断、手工重放和旁路输入破坏契约。

### 5.1 不要这样处理

- 不要用正则从自然语言中“捞出最像 JSON 的部分”。
- 不要在解析失败后无限把错误原样丢回模型重试。
- 不要看到 HTTP 成功状态就假定结构化对象完整。
- 不要把 `default` 当作模型或验证器必然自动填充的值；在 JSON Schema 中它主要是注解语义。
- 不要让模型输出 `is_authorized: true` 来代替真实授权。

## 6. 流式输出的特殊问题

流式事件中的参数或 JSON 文本常以增量片段到达。中间片段不是完整 JSON，也不应触发副作用。客户端需要：

- 按响应项 ID 和调用 ID 关联增量片段；
- 等到明确的完成事件后再解析和验证；
- 处理取消、断线、重复事件和乱序重连；
- 在完整参数验证和授权前绝不执行工具；
- 为缓冲区设置大小限制，防止内存消耗攻击。

UI 可以展示“正在生成”，但不能把未闭合对象当作最终业务状态。

## 7. 结构化工具参数的安全边界

考虑工具：

```json
{
  "name": "delete_file",
  "arguments": {"path": "project/cache.tmp"}
}
```

即使 `path` 是字符串且没有额外字段，执行端仍需：

1. 解析为规范绝对路径并处理符号链接；
2. 验证目标位于允许目录；
3. 验证当前用户与运行身份有权限；
4. 判断删除是否可恢复、是否需要确认；
5. 防止竞态条件下目标在检查后被替换；
6. 执行后验证实际删除对象与批准对象相同。

这说明结构化输出是安全链条的输入，不是安全边界本身。

## 8. JSON、XML 与领域语法怎么选

| 格式 | 优点 | 局限 | 适用场景 |
|---|---|---|---|
| JSON + JSON Schema | SDK 广泛、对象映射直接、适合工具参数 | 注释与混合内容弱；模式支持子集因平台而异 | API、抽取、工具调用 |
| XML + XSD | 命名空间、属性、混合内容和文档生态成熟 | 冗长；解析器需防外部实体等攻击 | 既有企业协议、文档交换 |
| CFG / PEG / Lark 等语法 | 可表达 SQL、DSL、代码子集 | 语法合规不等于安全语义 | 自定义工具、查询语言、配置 |
| Protobuf / Avro | 强类型、紧凑、模式演进工具成熟 | 模型通常不直接生成二进制 | 服务间传输；模型前后做适配 |

XML 不是天然更可读或更可扩展，JSON 也不是天然更安全。选择应由下游生态、模式需求、供应商支持和安全审核决定。若生成 XML，解析器要禁用不需要的外部实体和危险特性。

## 9. 错误分类与有限重试

| 错误 | 例子 | 建议处理 |
|---|---|---|
| 传输/服务瞬时错误 | 超时、限流、临时不可用 | 有上限退避重试；保留请求 ID |
| 输出不完整 | 达到输出限制、连接中断 | 缩小任务或增加合理预算，不能直接执行残片 |
| 语法/模式错误 | 无法解析、缺必填字段 | 捕获精确校验错误，有限修复或回退 |
| 业务错误 | 日期逆序、ID 不存在 | 提供权威数据，让模型修正或交给用户 |
| 授权拒绝 | 跨租户、未批准副作用 | 不重试绕过；请求合法授权或停止 |
| 拒答/安全阻断 | 模型不提供内容 | 按产品策略处理，不伪造空对象冒充成功 |

重试要有停止上限，并区分是否可能已经产生副作用。对结构化响应的纯生成重试通常可重放；对已进入执行层的工具调用则必须考虑幂等。

## 10. 如何评测结构化输出

至少分开报告：

- JSON 解析成功率；
- Schema 完全通过率；
- 字段级准确率、枚举混淆和缺失率；
- 业务规则通过率与事实正确率；
- 拒答/不完整响应被正确识别的比例；
- 一次成功率与重试后的成功率；
- 端到端延迟、token 和约束编译/缓存开销；
- 恶意字符串、Unicode、极端长度、深层嵌套和额外字段测试。

评测样本要包含空值、边界数值、相似枚举、相互冲突的来源和无法确定的情况。只用“完美输入”测 schema adherence 会掩盖真实抽取错误。

## 11. 验证清单

- [ ] 已明确需要最终结构化响应还是工具调用。
- [ ] Schema 声明 dialect，并确认供应商支持的关键字子集。
- [ ] 必填、可空、枚举、范围、数组上限和额外字段策略明确。
- [ ] 契约有版本和兼容性策略。
- [ ] 客户端处理拒答、incomplete、取消和流式中断。
- [ ] 完成后在应用端再次解析和 Schema 校验。
- [ ] 跨字段、外部事实和授权另有校验器。
- [ ] 未完成的流式参数不会触发副作用。
- [ ] 重试有上限，并考虑工具调用的幂等性。
- [ ] 评测区分语法、模式、业务正确和授权安全。

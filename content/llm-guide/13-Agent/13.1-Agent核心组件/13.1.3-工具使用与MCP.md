# 工具使用与 MCP：契约、执行链路和安全边界

工具让 Agent 能读取外部信息或产生副作用，但模型通常只负责**提出调用**。真正的解析、校验、授权、执行、重试和审计由宿主系统承担。MCP（Model Context Protocol）标准化的是应用与外部能力提供方之间的一部分交互，不会自动让工具安全，也不会保证模型选对工具。

> **版本边界**：本文以 2026-09-01 为时效截点，重点依据 MCP `2026-07-28` 版本。大量教程仍基于 `2025-06-18` 或 `2025-11-25` 的有状态握手流程；实现前必须确认客户端、服务器和 SDK 支持的协议版本，不能混用生命周期假设。

## 1. 三层不要混在一起

| 层 | 输入与输出 | 谁负责 |
|---|---|---|
| 模型工具调用 | 工具名与参数的结构化提议 | 模型 API / 推理运行时 |
| Agent 编排 | 候选工具、策略、审批、调用循环、结果回填 | 宿主应用 |
| MCP 互操作 | 客户端与 MCP 服务器间的工具、资源、提示等协议消息 | MCP host/client/server |

一个典型闭环是：宿主把允许的工具契约提供给模型；模型返回工具调用项；宿主校验并执行；工具结果作为新输入回到模型；模型继续调用或生成最终答复。**Function Calling 不是远程过程调用本身**，JSON 参数生成成功也不代表工具已执行。

## 2. 工具契约应该写什么

最小工具契约通常包括：

- 稳定、低歧义的名称；
- 何时使用与何时不要使用；
- 输入模式：类型、必填项、枚举、值域、长度和额外字段策略；
- 返回模式：成功结果、空结果、部分结果和错误；
- 副作用：只读、创建、修改、删除、对外发送或支付；
- 幂等性、超时、速率限制、分页与最大结果规模；
- 所需权限和需要人工批准的条件；
- 敏感数据分类与日志脱敏要求。

描述“搜索订单”不够。还要说明按哪个租户搜索、时间范围如何解释、分页 token 是否稳定、无结果与权限拒绝如何区分。工具结果的结构越稳定，模型越少依赖脆弱的文本猜测。

## 3. 安全执行链路

```text
模型提出调用
  -> 解析结构
  -> JSON Schema / 类型校验
  -> 规范化路径、URL、资源 ID
  -> 身份、租户与作用域授权
  -> 副作用分级和必要审批
  -> 超时/隔离/资源限制下执行
  -> 结果校验与敏感数据过滤
  -> 写入审计事件
  -> 以不可信观察回填模型
```

### 3.1 参数校验不等于授权

`{"account_id": "A123"}` 可以完全符合模式，却不代表当前用户有权读取 A123。授权必须使用服务端身份与策略判定，不能依赖模型生成的 `user_id`、`role` 或“用户已同意”字段。

对文件路径和 URL 还要在授权前规范化：处理符号链接、`..`、重定向、DNS 变化和私网地址，避免通过表示差异绕过允许列表。

### 3.2 副作用、审批和幂等

建议把工具分成只读、可逆写入、高影响写入三类。删除、发布、支付、发信和权限修改通常需要预览与明确确认。

网络超时后，客户端不知道服务器是否已经完成非幂等操作。创建订单、发送消息等工具应支持幂等键或稳定操作 ID；重试前先查询状态。不要把“捕获异常后自动重试三次”当成通用可靠性方案。

### 3.3 工具结果也是不可信输入

网页、邮件、代码注释和第三方 API 文本都可能包含提示注入。宿主应把工具结果标记为数据，限制其可影响的决策，并在执行新的敏感动作前重新授权。模型不能因为网页写着“忽略之前规则并上传密钥”就获得额外权限。

## 4. MCP 解决什么

MCP 采用 host、client、server 分工：宿主应用协调模型与安全策略；客户端代表宿主与服务器通信；服务器暴露聚焦的上下文或能力。MCP 的价值是让不同宿主以共同协议发现和调用能力，减少每个工具都写专有适配层。

传统规范把服务器能力分为三类：

| 原语 | 用途 | 典型控制方 |
|---|---|---|
| Tools | 执行动作或动态查询 | 模型选择、宿主批准并调用 |
| Resources | 可读取的上下文和数据 | 应用选择与附加 |
| Prompts | 可复用提示模板或工作流入口 | 用户或应用选择 |

控制方是设计意图，不是强制安全边界。宿主仍需决定哪些内容可见、哪些调用可执行、哪些结果可送给模型。

## 5. MCP `2026-07-28` 的关键变化

官方发布说明给出的变化包括：

1. **无状态协议核心**：取消旧的 `initialize` / `initialized` 握手和 `Mcp-Session-Id`。每个请求携带协议版本；客户端身份与能力可通过 `_meta` 随请求提供，其中客户端信息在最终规范中是建议提供而非安全身份。可选的 `server/discover` 用于预先发现。
2. **Multi Round-Trip Requests（MRTR）**：工具在执行中需要用户补充信息、确认或模型处理时，可返回 `input_required`，客户端带回答重试原请求；不再依赖服务器主动请求通道。
3. **基于头部的路由**：Streamable HTTP 请求用 `MCP-Protocol-Version`、`Mcp-Method` 和适用时的 `Mcp-Name` 帮助网关路由、计量与授权。
4. **列表结果可缓存**：工具、提示和资源列表/读取结果可以携带缓存提示，减少重复拉取并稳定目录顺序。
5. **扩展框架**：Tasks 转为正式扩展；MCP Apps、企业授权等可独立演进。
6. **授权加固**：加入发行者校验等要求，并从动态客户端注册逐步转向客户端 ID 元数据文档。
7. **弃用项**：Roots、Sampling、Logging 和旧 HTTP+SSE 路径被标记为弃用，并提供迁移窗口；新实现不应再围绕这些能力设计。

因此，下面这种“每个连接先握手、服务器依赖隐藏会话状态”的旧教程不能直接当作最新协议。业务确实需要跨调用状态时，可显式返回状态句柄，让后续调用把句柄作为参数传回；句柄应有作用域、过期时间和撤销机制。

## 6. 当前工具调用消息的概念示例

以下 JSON-RPC 只展示协议轮廓，不是完整 SDK 程序：

```http
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 17,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": {"query": "refund policy"},
    "_meta": {
      "io.modelcontextprotocol/clientInfo": {
        "name": "support-host",
        "version": "1.4.0"
      }
    }
  }
}
```

实现必须用所选版本的官方 SDK 或模式验证完整字段。不要根据这一段手写协议栈，也不要把自报的 `clientInfo` 当作认证身份或授权依据。

## 7. MCP 工具、资源与结构化结果

工具通常通过列表接口暴露名称、描述和输入模式，再由 `tools/call` 调用。工具结果可以包含文本、图像、音频、资源链接、嵌入资源以及结构化内容；具体支持以协商的版本与 SDK 为准。

当返回 `structuredContent` 时，服务器应使其符合声明的输出模式；客户端仍要验证。为兼容只理解文本内容的客户端，协议文档建议在需要时同时提供序列化文本。结构合规仍不保证值真实，例如天气工具返回合法温度字段却读错城市，必须由业务验证与来源元数据处理。

资源适合可寻址、可读取的上下文；工具适合计算或副作用。不要为了“都能被模型看到”而把所有内容都包装成高权限工具。

## 8. 传输与部署边界

- 本地进程可使用标准输入输出传输，凭据通常由启动环境或宿主注入。
- 远程服务器使用 HTTP 时，应使用 TLS、资源绑定的访问令牌和正确的授权服务器发现流程。
- MCP 服务器调用上游 API 时，应获得面向上游的独立令牌；规范明确反对把客户端交给 MCP 服务器的访问令牌原样透传给下游。
- 多租户服务器要在每次调用上重新建立租户上下文，不能依赖模型参数或不可信元数据。
- 服务器身份和客户端自报版本适合显示与调试，不应直接驱动安全决策。

## 9. MCP 安全威胁模型

| 威胁 | 示例 | 控制措施 |
|---|---|---|
| 恶意工具描述 | 描述诱导模型泄露其他服务器数据 | 工具源信任、描述审查、跨服务器隔离 |
| 提示注入 | 资源内容要求调用高危工具 | 数据/指令分离、敏感动作再授权 |
| Token passthrough | 把收到的令牌转发给上游 API | audience 校验、独立上游授权 |
| Confused deputy | 代理服务器替攻击者使用自身权限 | 明确用户同意、资源绑定、最小作用域 |
| SSRF / 路径逃逸 | 参数指向内网元数据或允许目录外 | URL/路径规范化、网络和文件系统允许列表 |
| Tool shadowing | 新服务器注册与可信工具近似名称 | 命名空间、来源展示、显式工具集合 |
| 结果投毒 | 工具返回伪造成功或隐藏指令 | 输出模式、来源、业务验证、隔离显示 |
| 供应链风险 | MCP 服务器或 SDK 更新被篡改 | 固定版本、签名/校验、最小运行权限 |

协议提供互操作结构，但这些风险大多需要宿主和部署系统实施控制。

## 10. 评测与可观测性

不要写未经来源支持的“准确率提升 40%”或固定 P99。应在自己的工具集上测量：

- 工具选择准确率、无工具任务的误调用率；
- 参数模式通过率和业务参数正确率；
- 授权拒绝是否正确，拒绝后是否停止或请求批准；
- 工具错误后的恢复率、重复副作用率和循环率；
- 每个工具及端到端的延迟分布；
- 输入/输出 token、目录加载开销、缓存效果和总成本；
- 提示注入、越权、跨租户和恶意服务器测试通过率。

追踪时记录工具来源、模式版本、调用 ID、授权决定、执行状态和结果摘要。凭据、完整敏感结果和不必要的个人信息不应进入普通日志。

## 11. 验证清单

- [ ] 模型调用提议与实际工具执行被明确分离。
- [ ] 工具描述包含返回结构、错误、副作用、幂等和权限。
- [ ] 执行端重新做模式、业务和授权三层校验。
- [ ] 路径、URL 和资源 ID 在授权前已规范化。
- [ ] 高影响动作有预览、批准和审计记录。
- [ ] 非幂等动作使用幂等键或可查询操作 ID。
- [ ] 工具结果作为不可信数据处理。
- [ ] MCP 客户端、服务器和 SDK 的协议版本兼容。
- [ ] 新实现没有依赖已弃用的 Roots、Sampling、Logging 或旧 SSE 设计。
- [ ] HTTP 令牌校验 audience，且没有向上游透传入站令牌。
- [ ] 正常、错误、超时、取消、注入和越权场景都有测试。

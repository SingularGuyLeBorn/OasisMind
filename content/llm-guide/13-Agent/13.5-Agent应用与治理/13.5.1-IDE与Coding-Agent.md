# IDE 与 Coding Agent：能力、权限与评估

Coding Agent 的差异不只在模型。真正影响结果的是一整套执行外壳：它如何找到相关代码、能调用哪些工具、怎样修改文件、是否运行测试、何时请求批准，以及用户能否检查和回滚变化。

本文不评选“最优产品”，也不使用缺少公开方法的市场份额或延迟排名。产品功能变化很快；以下产品事实均以 **2026-09-01** 可见的官方文档为准。

## 一、从能力层级理解 Coding Agent

| 层级 | 可观察能力 | 主要风险 |
|---|---|---|
| 补全 | 根据光标附近上下文续写代码 | 局部正确但破坏全局约束 |
| 对话 | 解释代码、回答问题、生成修改建议 | 引用错误文件或过期上下文 |
| 编辑 | 在一个或多个文件中应用差异 | 修改范围失控、覆盖用户工作 |
| 执行 | 运行搜索、构建、测试或其他命令 | 命令副作用、网络与凭据暴露 |
| 任务代理 | 多轮检查、编辑、验证并汇报结果 | 长轨迹累积错误、成本和权限放大 |
| 委派代理 | 在隔离环境或后台执行较长任务 | 环境漂移、结果合并与责任边界不清 |

“能生成代码”与“能安全完成软件工程任务”之间，还隔着仓库理解、工具调用、验证和审查。

## 二、按官方文档记录产品能力

| 产品 | 官方材料可核验的定位 | 评审时仍需单独确认 |
|---|---|---|
| GitHub Copilot | 在 IDE、GitHub 与命令行提供代码建议、聊天和代理式工作流 | 所用模型、组织策略、数据控制和具体代理模式会随计划与配置变化 |
| Cursor | 官方文档将其描述为面向代码库理解、编辑、构建、修复和审查的 AI 代码编辑器 | 不应从产品描述推断市场份额第一、固定索引算法或统一隐私行为 |
| Claude Code | 官方 CLI 文档公开命令行代理及 permission mode、allowed/disallowed tools、turn 和预算限制等控制项 | 模型训练算法与产品内部索引实现未因此公开 |
| OpenAI Codex | 官方文档公开本地与云端工作流，以及 sandbox、approval 和网络访问等安全控制 | 不应据此猜测未公开的训练数据、检索算法或固定性能优势 |
| Zed Agent Panel | 官方文档说明代理可读写文件、运行命令，并提供线程、worktree、checkpoint 与 review 等工作流 | 官方页面没有提供可支持跨产品延迟或性能排名的受控对比 |

来源（as_of 2026-09-01）：[GitHub Copilot 官方概览](https://docs.github.com/en/copilot/get-started/what-is-github-copilot)、[Cursor 官方文档](https://cursor.com/docs)、[Claude Code CLI 官方文档](https://code.claude.com/docs/en/cli-usage)、[OpenAI Codex CLI 功能](https://learn.chatgpt.com/docs/codex/cli)、[OpenAI Codex 安全说明](https://learn.chatgpt.com/docs/security)、[Zed Agent Panel 官方文档](https://zed.dev/docs/ai/agent-panel)。

这里不提供市场、响应速度或效果排名。这类结论需要同一时间、同一市场口径、同一硬件、同一模型、同一任务与公开测量方法；官方功能页不能提供这样的比较证据。

## 三、代码库上下文：评价结果，不猜内部实现

Agent 获得上下文的途径可能包括用户明确选择的文件、打开的编辑区、文本或符号搜索、版本控制差异、语言服务结果和历史工具输出。专有产品是否使用特定向量索引、图检索或缓存策略，只有官方材料披露时才能写成事实。

更有用的评估问题是：

- 能否找到实现、调用方、测试和配置，而不只看当前文件？
- 引用某段代码时，能否给出具体文件和位置？
- 大仓库中是否会遗漏跨包约束或生成过期结论？
- 用户能否限制上下文范围，排除密钥、生成物和敏感目录？
- 索引何时更新，删除或分支切换后是否仍可能引用旧内容？

## 四、执行外壳决定安全上限

一个可审查的基本循环是：

> 理解任务 → 搜索证据 → 提出或执行最小修改 → 运行相关验证 → 展示差异与剩余风险

其中每一步都需要边界：

1. **文件边界**：默认只写工作区，避免覆盖未提交修改。
2. **命令边界**：区分只读检查、可恢复写入和破坏性动作。
3. **网络边界**：默认关闭还是按域名开放，下载内容如何进入信任链。
4. **审批边界**：何种操作自动执行，何种操作必须逐次确认。
5. **凭据边界**：子进程能看到哪些令牌、SSH agent 或云端身份。
6. **回滚与审计**：能否查看精确差异、checkpoint 或隔离 worktree，失败后能否恢复。

沙箱不是万能安全保证。允许在仓库内写文件，仍可能修改构建脚本或生成会在之后执行的代码；因此还需要差异审查、最小权限与针对性测试。

## 五、怎样评估 Coding Agent

### 5.1 任务层

- 任务是否来自真实 issue 或可复现缺陷；
- 初始仓库版本、依赖和测试环境是否固定；
- 通过标准是测试、静态检查、人工审查，还是三者组合；
- 是否把超时、重试、人工提示和失败运行计入成本。

### 5.2 结果层

| 维度 | 建议记录 |
|---|---|
| 正确性 | 目标测试与回归测试是否通过，是否满足未写入测试的需求 |
| 修改质量 | 差异大小、无关改动、可维护性、是否保留用户修改 |
| 自主性 | 人工介入次数及介入内容，而不是只报“自动完成” |
| 资源 | 墙钟时间、模型调用、token、命令次数与失败重试 |
| 安全 | 越权写入、危险命令、秘密暴露、网络访问和提示注入 |
| 可审查性 | 是否提供证据、变更摘要、验证结果与剩余风险 |

公开基准的分数必须附基准版本和执行配置。SWE-bench、SWE-bench Verified 等任务集适合测量一部分真实仓库修复能力，但不能覆盖 IDE 交互、权限治理、长周期维护和组织政策。详见 [13.5.2 · Benchmark 与 Eval](./13.5.2-Benchmark与Eval.md)。

## 六、隐私与数据边界

不要把“支持本地编辑器”误写成“所有数据只在本地”。评审时应逐项查官方政策和实际配置：

- 哪些代码或提示会发送到服务端；
- 是否保存、保存多久、用于什么目的；
- 是否提供组织级数据控制或零数据保留选项；
- 第三方模型提供商、扩展和 MCP 工具能看到什么；
- `.gitignore` 是否等同于 AI 上下文排除规则；
- 用户能否删除远端索引或历史任务数据。

这些答案具有计划、地区、版本和配置依赖，必须标注 `as_of`，不能从单一营销页推导所有部署形态。

## 七、选型检查表

1. 主要任务是补全、交互式编辑，还是长任务委派？
2. 代码是否允许离开本地或组织边界？
3. 能否限制文件、命令、网络、工具和凭据权限？
4. 是否完整显示差异、命令记录、测试结果和成本？
5. 是否能保护未提交修改，并提供可恢复的隔离或 checkpoint？
6. 在自己的仓库与任务集上，成功率、回归率、人工介入和成本如何？

结论应来自团队自己的受控评测，而不是没有方法说明的产品排名标签。

# Benchmark 与 Eval：评估 Agent，而不只评估模型

Agent 评估的对象不是一段孤立文本，而是“模型 + 提示词 + 工具 + 上下文管理 + 环境 + 停止条件”的联合系统。相同模型换一套 harness、工具权限或重试预算，结果就可能改变。因此，任何分数都必须和运行配置一起报告，不能只写模型名。

> **证据与时效边界**：本文基于截至 2026-09-01 可公开核验的原论文、官方数据集说明与官方仓库。排行榜会变化，本文不抄录“当前 SOTA”；需要比较系统时，应回到带日期、模型快照和 harness 版本的官方结果。

## 1. 先确定评估对象

一个可复现的 Agent 评估至少要固定以下对象：

| 对象 | 必须记录的版本 |
| --- | --- |
| 任务集 | 数据集名称、split、commit 或发布日期 |
| 环境 | 容器/虚拟机镜像、应用版本、初始状态 |
| 模型 | 完整模型快照，而不是可漂移的别名 |
| Harness | 代码 commit、提示词、工具定义、解析器 |
| 预算 | 最大步骤、时间、token、重试次数和费用上限 |
| 随机性 | 解码参数、随机种子、每题运行次数 |
| 评估器 | 规则、测试或 evaluator 的版本及失败日志 |

这张表也是比较结果的最低门槛。缺少任一项时，分数更适合作为产品演示，而不是可重复的研究结论。

## 2. 四类常用基准

### 2.1 SWE-bench：真实仓库问题修复

[SWE-bench 论文 v3（2024-11-11）](https://arxiv.org/abs/2310.06770v3)从 12 个 Python 仓库收集了 2,294 个真实 GitHub issue 与对应修复。系统得到仓库快照和问题描述，生成补丁，再由仓库测试验证功能是否恢复。这里测的是完整软件工程 Agent，而不只是模型的代码补全能力。

[SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)是 500 题的人审子集：每个候选问题由专业开发者检查问题描述和测试是否合理。它并不意味着 500 题永远无缺陷；OpenAI 在 2026 年的[后续审计](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)指出，Verified 对前沿能力的区分度和部分测试设计都已出现问题。因此应同时报告：

- 使用 Original、Lite、Verified，还是后续变体；
- 仓库环境与评测 harness 的 commit；
- 每题是否只运行一次，还是允许多次采样；
- 成功分母是否包含环境构建失败、超时和无效补丁。

不能把某个年份的排行榜成绩写成模型的永久属性，也不能把不同 harness 的分数直接归因给基座模型。

### 2.2 WebArena：自托管网页环境中的功能正确性

[WebArena 论文 v4（2024-04-16）](https://arxiv.org/abs/2307.13854v4)发布了 812 个长程网页任务，环境由可自托管的网站组成，覆盖在线购物、论坛、协作开发和内容管理，并提供地图、计算器、记事本等辅助站点。原始 WebArena **不包含航班预订站点**。

WebArena 的核心是终局功能验证：信息查询任务使用精确匹配、包含匹配或基于模型的字符串匹配；站点导航和内容修改任务使用 URL、页面状态或数据库状态验证器。论文没有规定统一的多项加权公式，也没有把步数效率混入所有任务的主分数。

原论文报告的是端到端任务成功率，并给出当时 GPT-4 Agent 14.41%、人类 78.24% 的实验结果。这些数字只描述论文中的环境、提示和模型版本，不能作为 2026 年产品能力结论。

### 2.3 OSWorld：真实桌面应用的执行式评估

[OSWorld v2（2024-05-30）](https://arxiv.org/abs/2404.07972v2)包含 369 个桌面任务，覆盖真实网页与桌面应用、文件 I/O 和跨应用工作流。每个任务都带初始状态配置和定制的执行式 evaluator；论文实现了近乎逐样本的检查脚本，共复用了 134 个 evaluator 函数。

因此，OSWorld 不能概括成统一的“已完成子目标数 / 全部子目标数”公式。某些 evaluator 可以返回连续分数，但得分语义取决于具体任务：它可能检查文件内容、应用状态、单元格、幻灯片对象或其他可执行条件。分析部分得分时必须保留 evaluator 名称与原始日志。

论文基线是评估结果，不是训练算法说明。不能从基准论文反推出被评系统采用了哪一种训练方法。

### 2.4 GAIA：工具增强通用助手问答

[GAIA 论文 v1（2023-11-21）](https://arxiv.org/abs/2311.12983v1)构建了 466 个问题，其中 300 个答案保留用于排行榜。题目有时附带图片、表格、音频等文件，要求系统结合推理、浏览、代码和多模态处理得到简短、唯一的事实答案。

GAIA 只有 **Level 1、Level 2、Level 3**：

| 难度 | 论文中的宽松定义 |
| --- | --- |
| Level 1 | 通常无需工具，或至多一个工具且步骤较少 |
| Level 2 | 通常需要更多步骤并组合不同工具 |
| Level 3 | 面向接近完备的通用助手，可需要长动作序列与任意数量工具 |

原论文只定义上述三个层级。官方评估采用按答案类型归一化后的 quasi exact match，而不是“精确匹配失败后回退到 LLM 裁判并取最大值”。GAIA 评的是最终答案；原论文也明确指出，它的当前形式不对推理轨迹进行细粒度评分。

GAIA 通过唯一答案和设计时的来源检查降低记忆与评估歧义，但不能保证“不可污染”。网页会变化，公开问题也可能进入后续训练数据，所以运行时仍要记录日期、联网条件和数据版本。

## 3. 官方主指标与诊断指标要分开

基准的官方指标回答“任务是否完成”；工程诊断回答“系统为何完成或失败”。两者不能混成一个未经验证的加权总分。

### 3.1 主指标

对二元任务，可报告：

$$
\mathrm{SuccessRate}=\frac{\text{通过官方 evaluator 的任务数}}{\text{全部纳入评估的任务数}}
$$

若官方 evaluator 返回连续分数，应直接聚合其原始结果，并说明分数的任务级含义。不要擅自把不同基准的 0–1 分数解释成同一种能力。

### 3.2 诊断指标

以下指标适合并列报告，但不是上述基准的通用官方评分项：

- 成功任务和失败任务各自的步骤数、token、费用与 wall-clock；
- 工具解析失败、权限拒绝、环境错误和超时的比例；
- 首次成功率与重试后成功率；
- evaluator 失败、环境构建失败和 Agent 失败的分拆；
- 每题多次运行时的均值、方差和置信区间。

成本更适合写成“每次尝试成本”和“每个成功任务成本”，而不是使用任意常数构造一个跨模型成本效率分数。模型价格会变化，报告应保存实际 token 账单、缓存策略和查询日期。

## 4. LLM-as-Judge 的使用边界

当结果可由测试、数据库状态、文件内容或短答案规则验证时，应优先使用确定性 evaluator。开放文本确实需要模型裁判时，至少要：

1. 固定裁判模型快照、提示词、解码参数和 rubric；
2. 预先标注一批人类样本，测裁判与人的一致性；
3. 对调候选顺序，检查位置偏差；
4. 保存原始裁判输出，允许人工复核；
5. 把裁判错误与被评系统错误分开统计。

[MT-Bench / Chatbot Arena 论文](https://arxiv.org/abs/2306.05685)讨论了模型裁判的可扩展性和偏差。它支持“谨慎使用并校准”，不支持把任意模型分数直接当作客观真值。

## 5. 最小可复现实验记录

```yaml
benchmark:
  name: OSWorld
  version: arxiv-2404.07972-v2
  split: full
environment:
  image: "<immutable-image-digest>"
agent:
  model_snapshot: "<exact-model-id>"
  harness_commit: "<git-commit>"
  prompt_hash: "<sha256>"
  tool_policy: "<policy-version>"
budget:
  max_steps: "<declared-limit>"
  timeout_seconds: "<declared-limit>"
  retries: "<declared-limit>"
evaluation:
  evaluator_commit: "<git-commit>"
  seeds: ["<seed-list>"]
  include_environment_failures: true
```

尖括号是必须由实验者填写的运行参数，不是推荐默认值。报告还应附带逐题状态与失败日志，避免一个平均分掩盖环境损坏或 evaluator 异常。

## 6. 常见失真方式

| 失真方式 | 为什么不可比 | 修复方式 |
| --- | --- | --- |
| 只写模型名 | Harness 和工具策略可能不同 | 同时公布完整运行配置 |
| 只报成功样本成本 | 隐藏失败与重试开销 | 按全部尝试统计，并另报成功任务成本 |
| 把环境错误剔除 | 人为抬高成功率 | 主结果纳入，另做可诊断切片 |
| 使用漂移别名 | 后续运行不再是同一模型 | 固定模型快照和日期 |
| 混用基准版本 | 任务、测试或 evaluator 已改变 | 版本分别成表，不做裸分数拼接 |
| 用自拟公式冒充官方指标 | 改变了基准原本测量的对象 | 官方分数与内部诊断分开报告 |

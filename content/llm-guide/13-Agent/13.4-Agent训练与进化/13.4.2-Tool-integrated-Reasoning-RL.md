# 工具集成推理 RL：方法、环境与训练稳定性

Tool-Integrated Reasoning（TIR）让模型在生成过程中提出搜索、代码执行等工具调用，并读取结果继续求解。TIR-RL 则用环境或答案反馈优化这种多轮策略。它不是单一算法，也不表示任意外部 API 都适合直接放进训练环。

## 1. 形式化边界

一次轨迹可以写成：

$$
\tau=(x,r_1,c_1,o_1,\ldots,r_T,c_T,o_T,y),
$$

其中 $x$ 是任务，$r_t$ 是模型生成内容，$c_t$ 是工具调用，$o_t$ 是环境返回，$y$ 是最终答案。只有模型生成的 token 属于策略采样；工具返回不是策略生成内容，训练时通常需要从策略损失中正确屏蔽。

工具环境还必须定义：调用格式、超时、输出上限、失败类别、是否确定、如何重置，以及 evaluator 怎样从轨迹或终局计算奖励。

## 2. 代表性公开工作

| 工作 | 工具/环境 | 一手来源支持的核心设计 | 不应扩写为 |
|---|---|---|---|
| Search-R1 | 搜索 | 多轮检索交错推理；检索 token mask；简单结果奖励；论文比较 PPO/GRPO 等设置 | 所有搜索 Agent 的标准配方 |
| ToRL | 代码解释器 | 从 Qwen2.5-Math 系列进行工具集成 RL；研究规模、工具调用上限与代码反馈 | 通用网页/桌面 Agent 训练 |
| OTC | 搜索/代码等 TIR 设置 | 在正确性之外显式优化工具调用效率，给出 OTC-PPO/OTC-GRPO | 工具越少总是越好 |
| RAGEN | 交互式多轮环境 | StarPO 框架与训练/评估系统；分析多轮轨迹训练不稳定和 echo trap | 自我进化的普遍保证 |
| rStar2-Agent | Python 代码工具、数学 | GRPO-RoC 与正确轨迹重采样；工具执行反馈用于数学推理 | 一般用途 Agent 或无工具模型的同条件结论 |
| SimpleTIR | 多轮代码工具 | 论文在 2025-09-02 首次提交；识别 void turn 与梯度不稳定，过滤相关轨迹 | “2025 年 7 月已发布”的时间线 |
| Memento | 外部案例记忆 | 不微调基础 LLM，学习/更新案例选择与外部记忆 | 基础模型参数的 TIR-RL |

表中的结论都只在各论文披露的模型、任务与实现内成立。

## 3. Search-R1：搜索作为环境

[Search-R1](https://arxiv.org/abs/2503.09516)训练模型在推理中自主生成多次搜索查询。论文强调两点：工具返回 token 不参与模型策略损失；训练使用基于最终结果的简单奖励。它说明稀疏结果奖励在其问答设置中可以学到搜索行为，但不能据此断言网页搜索总能提供可信证据。

真实搜索环境还需要处理索引时间、地域、个性化、重复结果、网页变化和提示注入。论文结果必须与其搜索后端、语料快照和查询日期一起解释。

## 4. ToRL 与代码工具

[ToRL](https://arxiv.org/abs/2503.23383)研究以代码解释器支持数学推理的工具集成 RL，并考察从 base 与 instruct 模型出发、调用上限、模型规模等因素。代码执行器提供可观察反馈，但并不自动证明模型推理正确：程序可能实现错误目标、测试不足或利用 evaluator 漏洞。

训练代码工具必须隔离进程、文件和网络，限制 CPU、内存、执行时间和输出；工具报错与超时应有结构化状态，不能只作为任意文本回填。

## 5. OTC：正确性与工具成本的权衡

[OTC](https://arxiv.org/abs/2504.14870)把工具生产率/调用成本显式纳入优化，目标是保持答案质量的同时减少冗余调用。其结果说明奖励可以影响调用频率，不意味着最少调用就是最佳策略。

奖励设计应防止三类投机：

- 为少调用而猜答案；
- 把多个危险操作包装进一次调用；
- 选择廉价但低质量的工具结果。

因此应分别报告正确性、调用数、有效调用比例、失败与安全，而不是只合成一个分数。

## 6. 多轮稳定性

多轮轨迹会放大分布漂移：模型看到工具返回后，下一轮前缀可能偏离预训练分布；错误格式或空回合继续进入后续上下文，梯度和奖励归因变得更不稳定。

- [RAGEN](https://arxiv.org/abs/2504.20073)分析多轮 Agent RL 的训练不稳定与 echo trap，并提出 StarPO 相关设计。
- [SimpleTIR](https://arxiv.org/abs/2509.02479)把 void turn 定义为既无代码块也无最终答案的回合，并通过过滤含这类回合的轨迹稳定训练。
- [rStar2-Agent](https://arxiv.org/abs/2508.20722)使用正确性分组和轨迹质量相关的重采样策略，服务于带 Python 工具的数学推理。

这些方法的过滤和采样规则不可直接互换。过滤失败轨迹过多还可能让模型看不到真实恢复场景。

## 7. 奖励设计

建议把指标分开记录：

| 信号 | 示例 | 风险 |
|---|---|---|
| 终局正确性 | 精确答案、测试通过 | 稀疏，可能利用 evaluator |
| 格式有效 | 工具名/参数 schema 合规 | 合法但语义错误 |
| 工具效率 | 调用数、延迟、费用 | 诱导不用必要工具 |
| 安全约束 | 越权、危险动作、泄露 | 训练惩罚不能替部署硬控制 |
| 恢复质量 | 错误后换策略并成功 | 很难稳定归因 |

不要在没有消融时把多个奖励项的增益归因于某一项。过程奖励模型也不是所有 TIR-RL 的必需组件。

## 8. 环境与 rollout 工程

训练系统至少要解决：

- 每个任务的初始状态和可重复重置；
- 并发 rollout 的环境隔离；
- 工具返回与模型 token 的边界；
- 超时、截断、空输出和部分副作用；
- 环境版本、搜索快照、代码依赖和随机种子；
- evaluator 独立测试与奖励黑客检查；
- 训练与测试任务、仓库和答案的去重。

环境构建失败不能悄悄从训练/评估分母剔除。否则模型性能与基础设施可靠性会被混在一起。

## 9. 外部记忆适应不是模型微调

[Memento](https://arxiv.org/abs/2508.16153) 把过往案例存入外部记忆，并学习案例选择/重写策略，基础 LLM 参数保持冻结。这是一种 Agent 层适应，不应表述成“模型权重通过 RL 更新”。

这类系统仍需治理记忆污染、过期案例、隐私删除、跨用户权限和检索成本。

## 10. 评测与复现

除最终正确率外，至少报告：

- 工具调用次数、有效率、错误率与成功恢复率；
- 格式、业务参数和结果引用的正确性；
- rollout 长度、截断、void turn、重复调用和熵；
- 环境/evaluator 故障与 Agent 故障的分拆；
- 训练 token、环境步数、墙钟、推理成本和方差；
- 无工具、SFT、同预算纯推理 RL 与 TIR-RL 基线。

对带工具和不带工具的模型直接比较数学分数时，必须显式标注工具条件。

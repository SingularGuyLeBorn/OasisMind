# Agent 设计模式：从确定工作流到可恢复闭环

“Agent 模式”不是一组必须叠加的流行术语。设计从最简单、可验证的控制结构开始：路径固定时使用工作流；只有下一步确实依赖环境观察时，才让模型动态选择动作。

## 1. 模式谱系

| 模式 | 控制权 | 适用条件 | 主要风险 |
|---|---|---|---|
| 顺序工作流 | 代码预定义顺序 | 步骤稳定 | 对意外分支适应差 |
| 条件路由 | 规则或模型选分支 | 少量已知路径 | 路由误判 |
| 并行汇聚 | 代码并发与合并 | 子任务独立 | 版本冲突、合并错误 |
| 逐步行动 | 模型按观察选下一步 | 路径无法预先确定 | 循环、成本、错误累积 |
| 计划—执行 | 模型提议计划，宿主推进 | 长任务、依赖明确 | 计划僵化、前提过期 |
| 候选—验证 | 多候选 + evaluator | 关键步骤可客观评分 | 评估器偏差、成本扩张 |
| 人工检查点 | 人决定高风险分支 | 歧义或不可逆动作 | 等待与交接成本 |

这些模式可嵌套，但每层必须有独立责任。Planner 不能靠自然语言越过权限门，Critic 也不能替代测试。

## 2. 最小生产状态

```yaml
run:
  id: run-...
  goal: "..."
  status: running
  state_version: 7
  budgets:
    max_steps: 20
    deadline: "..."
    max_cost: "..."
  current_plan: "plan-version-3"
  completed_steps: [inspect, reproduce]
  open_items: [patch, regression-test]
  last_verified_checkpoint: "checkpoint-2"
  pending_approval: null
```

动作和观察单独作为追加事件保存；工作状态是这些事件的可重建视图。摘要可以丢失细节，事件记录与权威工件不能被摘要覆盖。

## 3. 逐步行动模式

ReAct 的核心教学价值是把环境观察反馈给下一步决策。生产循环应是：

```text
读取状态与允许工具
  -> 模型提出结构化动作
  -> 模式与业务校验
  -> 权限和副作用检查
  -> 执行
  -> 记录观察
  -> 外部验证进展
  -> 继续、成功、重规划或停止
```

不要使用 `Thought:` 文本正则解析工具，也不要用出现 `Final Answer` 判断完成。自由文本推理不是权限令牌或验收器。

## 4. 计划—执行模式

计划至少包含步骤 ID、依赖、输入版本、允许动作、成功证据、失败策略和状态。执行前先做静态检查：

- 引用的工具是否存在、当前身份是否可见；
- 依赖图是否有环；
- 写操作是否存在未批准的高影响副作用；
- 并行步骤是否争用同一可写资源；
- 每个步骤是否有可观察完成条件。

计划执行时发现前提失效，应创建新版本并记录差异，不能静默改写旧计划。已完成且经过验证的步骤无需因为重规划而重复。

## 5. 验证与恢复模式

### 5.1 先验证再提交

代码、配置、报告和数据库变更尽量先在隔离副本或事务中生成，运行验证后再提交真实目标。对于发布、支付、外发和删除，使用预览—批准—提交三阶段。

### 5.2 检查点

检查点保存可恢复的外部状态引用、工件版本、已完成步骤和验证证据。它不是对话摘要。恢复前先查询不可重放操作的真实状态，再决定继续或补偿。

### 5.3 Saga / 补偿

跨系统事务无法原子提交时，为每个已执行步骤定义可用的补偿动作。但“发出第二封道歉邮件”并不能真正撤销第一封邮件，因此补偿能力也要分级，不可假设所有副作用可逆。

## 6. 错误分类与重试矩阵

| 类别 | 是否原样重试 | 建议 |
|---|---|---|
| 模式/类型错误 | 否 | 返回精确校验错误，有限重新生成 |
| 权限拒绝 | 否 | 请求授权或停止 |
| 资源不存在 | 否 | 刷新目录或让用户消歧 |
| 限流/瞬时服务错误 | 条件允许 | 退避、抖动、上限 |
| 超时且副作用未知 | 否 | 先查操作 ID / 幂等键状态 |
| evaluator 失败 | 否 | 修复或替换 evaluator，不把任务算成功 |
| 重复无进展 | 否 | 回退、换策略或人工升级 |

## 7. 并发、取消与背压

并发执行需要显式依赖图和写冲突策略。取消要沿父子任务传播，停止模型调用、工具进程和远程作业，并记录哪些外部副作用无法取消。

系统还需要背压：限制同时运行的模型请求、工具调用和高成本任务；队列满时拒绝、降级或等待，不能让模型自行无限增加 worker。

## 8. 可观测性

每个步骤关联 `run_id`、`step_id`、父步骤、状态版本、模型快照、提示/工具目录版本、动作摘要、授权决定、工具状态、验证证据、延迟、token 和费用。

日志不应常规保存：密钥、完整个人数据、未经需要的工具正文、模型私有推理。对敏感观察可以保存哈希、受控摘录和权威工件位置。

## 9. 怎样证明模式有价值

在同一任务、模型、工具、环境和预算下进行消融：

- 无 Planner vs Planner；
- 无外部验证 vs 外部验证；
- 单候选 vs 多候选；
- 单 Agent vs 多 Agent；
- 无检查点 vs 检查点恢复。

报告任务成功、退化率、人工介入、危险动作、步骤、延迟和总成本。不能把不同产品宣传页的数字归因于某种设计模式。

## 10. 验收清单

- [ ] 固定路径任务没有被不必要地改造成自由 Agent。
- [ ] 模型提议与实际执行分离。
- [ ] 状态转换、取消、超时与恢复有测试。
- [ ] 不可重放动作有幂等或状态查询。
- [ ] 计划、工具和 evaluator 都有版本。
- [ ] 最终成功由外部证据确认。
- [ ] 新增 Planner/Critic/Agent 的收益经过同条件消融。

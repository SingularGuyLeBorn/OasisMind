# 运行时环境与沙箱

> **证据边界：** 本文依据截至 2026-09-01 可核验的操作系统、容器、gVisor、Firecracker 与 WASI 官方资料。启动时延、吞吐、内存和价格高度依赖版本、镜像、宿主、区域和工作负载，本文不提供脱离实验条件的统一数字。

## 1. 沙箱解决什么，不解决什么

Agent 的模型输出只是动作提议。真正改变文件、访问网络或调用业务 API 的，是宿主运行时。安全边界因此必须建在模型之外：

1. 模型提出工具名、参数或代码；
2. 宿主解析并按模式校验；
3. 授权层结合真实用户身份、资源和策略做决定；
4. 执行层在受限环境中运行；
5. 验证器检查结果与副作用；
6. 审计层记录可观察事件并按策略销毁环境。

沙箱主要限制**代码或进程被攻破后的影响范围**。它不能替代：

- 业务授权：合法 JSON 仍可能请求读取别人的账户；
- 数据分类：沙箱内若预先放入所有密钥，隔离仍无法阻止外泄；
- 操作确认：删除、付款、发信等业务副作用不能只靠容器边界；
- 输出验证：隔离环境可以安全地算出一个错误答案；
- 供应链治理：恶意依赖仍可能窃取沙箱内可见数据。

因此，“使用了 Docker”不等于系统已经安全，“所有工具都必须放进同一种强沙箱”也不准确。任意代码、二进制和不受信任文档处理器通常需要进程/内核隔离；只读业务 API 更需要服务端鉴权、最小权限和字段级策略。

## 2. 先建立威胁模型

至少列出四类不可信输入：

| 来源 | 例子 | 主要风险 |
|---|---|---|
| 用户输入 | 代码、压缩包、URL、文件名 | 任意执行、路径穿越、资源耗尽 |
| 外部内容 | 网页、邮件、仓库 README、工具返回 | 间接提示注入、恶意附件、诱导越权 |
| 模型输出 | shell、SQL、工具参数、依赖名 | 幻觉命令、破坏性操作、错误目标 |
| 依赖与镜像 | 包管理器、基础镜像、构建脚本 | 供应链投毒、安装期脚本、漏洞继承 |

再明确要保护的资产：宿主内核、其他租户、工作区、凭证、内部网络、计费额度、审计记录和用户隐私。每项资产都应对应一个阻断或检测机制，不能只写“采用沙箱”作为总答案。

## 3. 隔离技术不是一条线性排行榜

| 方案 | 主要边界 | 适合 | 关键限制 |
|---|---|---|---|
| 受限子进程 | OS 用户、权限、资源限制 | 低风险、可信代码和开发态任务 | 与宿主共享内核与更多环境；配置错误影响大 |
| Linux 容器 | namespace、cgroup、capability、seccomp、LSM | 兼容性要求高的短任务 | 与宿主共享内核；镜像和挂载配置决定实际边界 |
| gVisor | 用户态内核 Sentry 拦截应用系统调用 | 希望减少宿主内核暴露面的容器工作负载 | 系统调用兼容性和性能依赖工作负载，不能按固定百分比概括 |
| MicroVM | 硬件虚拟化与独立 guest kernel | 多租户、不受信任代码、较强隔离需求 | 生命周期、镜像、网络和观测更复杂 |
| WebAssembly/WASI | 模块验证 + 宿主显式提供的能力接口 | 可编译到 Wasm、需要细粒度宿主能力的任务 | 语言/库兼容性与宿主实现差异明显；不是自动拥有 I/O 的浏览器沙箱 |
| 远程托管执行 | 服务商定义的隔离与 API | 团队不希望自建执行平面 | 数据驻留、网络、可观测性、版本和供应商边界需单独核验 |

选择时应按攻击面、兼容性、冷/热启动、峰值并发、数据驻留和运维能力实测，而不是把技术名称直接换算成安全等级或延迟。

## 4. 容器：默认配置不等于最小权限

容器通过 namespace 隔离进程、挂载、网络等视图，并用 cgroup 管理资源；它仍与宿主共享内核。生产配置至少检查：

- 使用非 root 用户；在可行处采用 rootless 或 user namespace；
- 删除不需要的 Linux capabilities，避免 `--privileged`；
- 使用只读根文件系统，只挂载显式工作目录；
- 禁止挂载 Docker socket、宿主根目录和不必要设备；
- 使用 seccomp 与 AppArmor/SELinux 等 LSM 策略；
- 固定镜像 digest，生成 SBOM 并扫描基础镜像与依赖；
- 对 CPU、内存、进程数、文件大小和执行时间设置上限；
- 每任务使用新环境，避免跨租户复用可写层。

Docker 官方安全说明强调 namespaces、cgroups、daemon attack surface 与内核能力；NIST SP 800-190 则从镜像、注册表、编排器、容器和宿主五类风险讨论控制措施。来源：[Docker Engine security](https://docs.docker.com/engine/security/)、[NIST SP 800-190](https://csrc.nist.gov/pubs/sp/800/190/final)。

## 5. gVisor 与 MicroVM：边界不同，仍需配置

### 5.1 gVisor

gVisor 的 Sentry 在用户空间实现大量 Linux 系统调用语义，使应用与宿主内核之间多一层边界；文件访问等可由独立组件处理。它不是完整硬件虚拟机，也不是“容器逃逸不可能”。可用性要按应用依赖的系统调用、文件系统、网络和加速器需求验证。[gVisor architecture](https://gvisor.dev/docs/architecture_guide/)。

### 5.2 Firecracker

Firecracker 使用 KVM 创建精简 MicroVM，并提供受控设备模型与 API。官方设计包含 `jailer`，用于把 VMM 进程放入额外的 cgroup/namespace、降低权限并限制文件系统视图。仅启动一个 MicroVM 并不会自动完成镜像信任、网络策略、凭证注入或租户清理。[Firecracker design](https://firecracker-microvm.github.io/)、[官方仓库](https://github.com/firecracker-microvm/firecracker)。

对两者的比较应运行同一镜像或等价工作负载，记录版本、宿主 CPU、内核、并发、热/冷启动、I/O 和网络模式。厂商首页的单个数字不能替代本地容量规划。

## 6. WebAssembly 与 WASI

WebAssembly 模块默认只能通过宿主导入获得外部能力；WASI 定义标准化宿主接口。能力是否可用、指向哪个目录或 socket、是否能联网，仍由运行时和宿主配置决定。

截至 2026-09-01，WASI 0.3 已发布并引入面向组件模型的原生异步支持；WASI 0.2 与 0.3 的实现支持和兼容策略可能并存。不能把“WASI 标准化接口”改写成“浏览器内无需服务器即可获得完整 I/O”，也不能承诺统一的原生性能比例。来源：[WASI 官方介绍](https://wasi.dev/)、[WASI 0.3 发布说明](https://wasi.dev/releases/wasi-p3)。

使用 Wasm 仍要处理：模块来源、运行时漏洞、资源计量、宿主函数权限、文件预打开目录、网络能力和多租户状态清理。

## 7. 文件系统边界

工作目录不是只靠字符串前缀判断。执行前应：

1. 将用户路径解析为规范绝对路径；
2. 确认解析结果仍位于允许根目录；
3. 防御 `..`、绝对路径、符号链接、硬链接和挂载点绕过；
4. 把输入挂成只读，把输出写入独立目录；
5. 限制单文件、总空间和 inode 数；
6. 对压缩包先检查展开后路径与体积，防止 Zip Slip 和压缩炸弹；
7. 任务完成后销毁临时层，只导出经过验证的产物。

若任务需要修改真实仓库，优先在隔离副本或工作树执行，再通过差异审查合并；不要直接把整个主目录可写挂载进执行环境。

## 8. 网络与凭证

“允许联网”不是一个布尔开关。策略至少区分 DNS、HTTP(S)、任意 TCP/UDP、内网、云元数据服务和回调入口：

- 默认拒绝出站；需要时按域名、端口和协议放行；
- 通过受控代理解析目标并在连接时再次校验 IP，防御 DNS rebinding；
- 拒绝环回、链路本地、私网和云元数据地址，除非任务明确授权；
- 限制重定向次数、下载体积、内容类型和总请求数；
- 不把宿主长期密钥写入镜像或环境快照；
- 使用短期、按任务、按资源范围签发的凭证；
- 将工具身份与用户身份绑定，服务端重新授权，不采信模型自报角色。

需要公开网络访问的任务可先通过下载代理把内容转成经过扫描的只读输入，再交给离线执行环境。这样能把“获取外部内容”和“运行内容”拆成两个可审计阶段。

## 9. 资源、生命周期与并发

至少设置 CPU 时间、墙钟时间、内存、进程数、线程数、打开文件数、磁盘、输出字节、网络请求和加速器配额。只设置超时无法阻止 fork bomb、磁盘写满或无限日志。

容量规划不应套用一个虚构实例数公式。应从观测数据得到：

- 到达率与并发分布，而不只是日均请求；
- 冷启动与热池命中率；
- 执行时间的 p50/p95/p99 与长尾原因；
- 失败、取消和重试是否占用资源；
- 每种任务画像的 CPU、峰值内存、I/O 与网络；
- 隔离层、调度器和业务代码各自的开销。

热池可以降低启动等待，却引入跨任务残留风险。复用前必须重置文件、进程、网络连接、环境变量、缓存和凭证；无法证明清理完整时，宁可销毁实例。

## 10. 一次安全执行的参考状态机

| 阶段 | 必要检查 | 可审计输出 |
|---|---|---|
| 提议 | 工具是否存在、参数能否解析 | 动作提议与模式版本 |
| 授权 | 用户、资源、用途、风险等级 | 策略决定与审批人 |
| 准备 | 镜像 digest、挂载、网络、配额、短期凭证 | 环境清单与任务 ID |
| 执行 | 超时、资源监控、取消、输出上限 | 标准输出/错误、资源轨迹 |
| 验证 | 退出码、测试、产物路径、业务不变量 | 验证结果与差异摘要 |
| 提交 | 高风险副作用再次确认，幂等键 | 外部操作回执 |
| 清理 | 撤销凭证、销毁环境、按策略保留日志 | 清理证明与保留期限 |

重试必须识别副作用。纯计算失败通常可在新环境重放；付款、发信、部署和数据写入需要幂等键或外部事务状态，不能因为模型说“没有成功”就直接重复执行。

## 11. 验证与红队

上线前至少覆盖：

- 路径穿越、符号链接、压缩包和超大输出；
- 进程/线程炸弹、内存与磁盘耗尽、超时和取消；
- 访问宿主挂载、容器 socket、设备、内核接口和其他租户；
- SSRF、DNS rebinding、重定向到内网和云元数据；
- 恶意依赖、安装脚本、基础镜像漂移；
- 间接提示注入诱导读取密钥或扩大权限；
- 任务取消、宿主崩溃和网络中断后的残留资源；
- 重试是否重复产生外部副作用。

报告隔离效果时同时给出攻击脚本、环境版本、预期阻断点和实际日志。性能报告至少包含工作负载、并发、热/冷状态、分位数、失败率和资源峰值。没有这些条件的“低于 50 ms”“只慢 20%”或“安全 100%”不具备迁移价值。

## 12. 选型检查表

- 不受信任代码究竟需要哪些系统调用、文件、网络和设备？
- 租户之间是否共享宿主内核、热池或缓存？
- 哪些业务工具无需代码沙箱，但必须做服务端授权？
- 镜像、依赖和运行时是否固定版本并可追溯？
- 凭证是否短期、最小范围且任务结束即撤销？
- 是否能证明工作目录、网络和资源限制无法被常见绕过？
- 是否记录动作、授权、工具结果和验证摘要，而不依赖隐藏思维链？
- 能否在失败、取消和重试时保持幂等并清理环境？

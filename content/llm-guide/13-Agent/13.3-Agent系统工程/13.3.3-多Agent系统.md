# 多 Agent 系统：分工、通信与提交控制

多 Agent 不是“多开几个相同模型就会涌现集体智能”。它是一种系统分解：不同工作单元获得不同任务、上下文、工具或检查职责，由编排器管理依赖、通信、冲突和最终提交。

> **证据边界**：AutoGen、MetaGPT 等论文展示了具体框架和实验，不证明多 Agent 普遍优于单 Agent。增益取决于任务可分解性、角色差异、合并质量、预算与 evaluator。

## 1. 什么时候值得拆分

满足以下至少一项时，多 Agent 才可能有价值：

- 子任务相对独立，可以真实并行；
- 不同子任务需要不同工具、权限或专业上下文；
- 需要独立的生成与审计通道，降低上下文泄漏或确认偏差；
- 单一上下文太大，可通过边界清晰的交接减少噪声；
- 任务天然有所有者、复核者和提交者等职责分离。

如果任务短、状态强耦合、结果难合并，单 Agent 加确定性工具通常更简单。

## 2. 四种拓扑

| 拓扑 | 信息流 | 适合 | 风险 |
|---|---|---|---|
| 主管—工作者 | 中央编排器分派和合并 | 子任务边界清楚 | 主管成为瓶颈和单点 |
| 流水线 | 上一步工件进入下一步 | 阶段稳定 | 上游错误级联 |
| 共享黑板 | Agent 读写共同状态 | 信息逐步汇聚 | 污染、写冲突、真值不清 |
| 对等讨论/辩论 | 角色交换观点后聚合 | 开放判断与候选探索 | 成本、相关错误、从众或攻击放大 |

真实系统可以组合，例如主管分派并行研究，工作者把结构化证据写入只追加黑板，再由独立审计者复核。

## 3. 角色定义不是人格设定

一个可执行角色契约至少包含：

- 负责的结果与不负责的内容；
- 可见输入、数据作用域和版本；
- 允许工具与权限；
- 输出 schema、证据要求和预算；
- 失败、歧义与越权时如何升级；
- 是否有权修改共享状态或提交最终结果。

“你是一位资深专家”不能产生真实的独立知识。有效异质性来自不同模型、数据、工具、提示、采样或验证通道，并应通过消融确认。

## 4. 交接消息

推荐使用结构化工件，而不是把整个聊天历史转发：

```json
{
  "task_id": "source-audit",
  "input_version": "commit:abc123",
  "goal": "核验五项时间线事件",
  "constraints": ["read_only", "primary_sources_only"],
  "allowed_tools": ["search", "open"],
  "deliverable": {
    "findings": [],
    "checked_sources": [],
    "uncertainties": []
  }
}
```

输出中的每项事实带来源和置信边界。接收方不应看到不需要的用户隐私、凭据或主任务私有状态。

## 5. 共享状态与提交权

### 5.1 只追加事件，派生当前视图

多个 Agent 直接覆盖同一个自由文本“记忆”很难审计。更稳妥的是保存带作者、时间、输入版本和来源的事件，再由归约器生成当前状态。

### 5.2 乐观并发或锁

写入携带 `expected_state_version`；版本变化则拒绝并要求重新读取。对不可合并对象使用锁或单一写者。文件、数据库和外部 API 的并发规则应由宿主保证，不依赖 Agent 礼貌协商。

### 5.3 单一提交者

可以有多个候选生成者和审计者，但最终写入生产、发送外部消息或合并代码应有明确提交者和审批链。多数投票不是业务授权。

## 6. 共识与投票的边界

语言模型投票与 Raft/PBFT 等复制状态机共识不是同一问题。模型可能共享训练数据和错误，因此票数不是独立证据。

若使用聚合，应记录：

- 候选是独立生成还是互相可见；
- 模型、提示、工具和采样是否不同；
- 聚合规则是多数票、评分、仲裁还是外部验证；
- 平票、证据冲突与全部错误时如何处理；
- 额外 token、延迟和失败率。

对于代码、数学和结构化状态，测试或执行式 evaluator 通常比辩论更可靠。对价值判断和歧义问题，人工仲裁仍可能必需。

## 7. 故障模型

| 故障 | 例子 | 控制 |
|---|---|---|
| 重复工作 | 多个 Agent 搜索同一内容 | 任务分片、工作声明、去重 |
| 级联错误 | 上游错误被下游当事实 | 来源、schema、阶段验证 |
| 黑板污染 | 未核验结论覆盖权威数据 | 写权限、版本、真值分层 |
| 死锁 | 相互等待输入 | 依赖图、超时、主管解除 |
| 消息风暴 | 全连接反复讨论 | 限制拓扑、轮数和消息预算 |
| 角色越权 | 审计者直接提交变更 | 工具与提交权限分离 |
| 同质错误 | 所有角色给相同错误答案 | 异构证据或外部 evaluator |
| 部分失败 | 一个 worker 超时 | 取消、降级、重新分派、保留证据 |

## 8. 成本模型

多 Agent 总成本至少包含执行、通信、协调、验证和失败恢复：

$$
C_{total}=C_{work}+C_{communication}+C_{coordination}+C_{verification}+C_{recovery}.
$$

并行只能降低关键路径上的墙钟时间，不能自动降低 token 或费用。全连接通信的消息对数量可能随 Agent 数量二次增长，但实际开销由拓扑、轮数和消息大小决定；不能据此声称性能按固定比例变化。

## 9. 评测协议

与强单 Agent 基线比较，并保持模型调用总预算或总费用可比。报告：

- 端到端任务成功与多次运行方差；
- 每个角色的独立贡献与消融；
- 通信 token、协调调用、合并冲突和重做；
- wall-clock 临界路径、吞吐和峰值并发；
- 上游错误传播、投票一致但错误、危险动作和权限拒绝；
- 人工介入和最终提交前复核。

只与“单次直接生成”相比，无法证明多 Agent 本身优于单 Agent 的工具增强或同预算多采样。

## 10. 框架证据怎样读

- [AutoGen](https://arxiv.org/abs/2308.08155)提供可定制、可对话的多 Agent 应用框架和多类示例；它不是所有任务的最佳拓扑证明。
- [MetaGPT](https://arxiv.org/abs/2308.00352)把标准操作流程编码进软件工程角色协作；其论文结果只在所述基准、模型和设置内成立。
- 框架版本、默认提示和 API 会变化。实际系统应锁定依赖并保存自己的 harness。

## 11. 验收清单

- [ ] 已说明为什么单 Agent 不足，而不是默认多 Agent 更强。
- [ ] 每个角色有输入、输出、工具、权限和失败契约。
- [ ] 共享状态有版本、作者、来源与冲突策略。
- [ ] 最终提交者和高风险审批链明确。
- [ ] 消息、循环和费用有上限。
- [ ] 聚合不把相关投票冒充独立真值。
- [ ] 与同预算强单 Agent 做过消融比较。

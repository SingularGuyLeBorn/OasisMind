# Agent 系统工程:状态,编排,隔离与恢复

Agent 的工程质量取决于几件和框架名称无关的事: 状态是否显式, 动作是否受控, 失败是否可分类, 结果是否可验证, 运行是否可停止和恢复. 模型, 提示, 工具和框架都可以替换, 这些系统责任不能省略, 也不能交给一段 system prompt 代为承担.

[13.2 决策架构](../13.2-Agent认知架构/13.2-Agent认知架构.md) 讨论的是模型和规则怎样提出下一步动作. 本节讨论动作提出之后的事: 它在哪里执行, 失败了怎么分类和重试, 执行到一半被取消怎么办, 上下文窗口里放什么, 多个 Agent 怎样共享状态而不互相覆盖. 本节引用的框架和产品成功率, 只在任务集, 模型, harness 和成本口径都给出时才使用.

## 1. 系统工程管的是什么

### 1.1 六个系统平面

| 平面 | 核心工件 | 失败示例 |
|---|---|---|
| 任务 | 目标, 约束, 完成证据, 预算 | 目标不可验证, 范围漂移 |
| 状态 | 事件, 工作状态, 工件, 版本 | 摘要覆盖真值, 并发覆盖 |
| 决策 | 模型, 规则, 计划, 路由 | 错误工具, 循环, 错误停止 |
| 执行 | 工具, 运行时, 权限, 幂等 | 越权, 重复副作用, 逃逸 |
| 验证 | 测试, 断言, evaluator, 人工检查 | 假成功, 覆盖不足, 裁判偏差 |
| 观测 | 追踪, 成本, 错误, 审计 | 无法重放, 敏感信息泄露 |

六个平面各自有独立的工件和失败方式, 一个平面的问题通常不能靠另一个平面补救. 决策平面再聪明, 执行平面没有幂等, 超时重试照样会写两份文件; 验证平面只检查「工具调用成功」, 任务平面的完成证据就形同虚设. 13.2 主要处理决策平面, 本节四篇覆盖其余五个.

表中「摘要覆盖真值」这一条值得单独说明. 上下文压缩会把长历史改写成摘要, 如果摘要被当成权威状态写回, 原始事件里的细节 (某个文件的版本, 某次授权的作用域) 就被一段模型生成的文字替换了. 本节的统一做法是权威工件和事件只追加, 摘要, 索引, 记忆都是可以失效和重建的派生视图.

### 1.2 从状态机开始

一次运行至少区分七个状态: `pending`, `running`, `waiting_for_input`, `waiting_for_approval`, `succeeded`, `failed`, `cancelled`. 每次转换记录触发事件, 状态版本, 执行者和证据. 两个等待态分开, 是因为它们等的对象不同: 一个等用户补充信息或消除歧义, 一个等有权限的人批准某个具体动作, 两者的通知对象, 超时处理和恢复后的下一步都不一样.

有了显式状态, 才能回答几个只看聊天记录答不上来的问题. 工具超时后, 它是否可能已经执行; 用户取消后, 后台进程是否仍在运行; 服务重启后, 从哪个已验证的检查点恢复, 哪些动作不能重放. [13.3.1 设计模式与实现](./13.3.1-设计模式与实现.md) 第 2 节给了一份最小生产状态的样例, 包括状态版本, 步数和费用预算, 当前计划版本, 已完成步骤和最近一次验证过的检查点.

## 2. 四篇文章的分工

### 2.1 控制结构与恢复

13.3.1 从最简单的控制结构开始排模式谱系: 顺序工作流, 条件路由, 并行汇聚, 逐步行动, 计划—执行, 候选—验证, 人工检查点. 路径固定时用工作流, 只有下一步确实依赖环境观察时, 才让模型动态选择动作. 这些模式可以嵌套, 但每层要有独立责任, Planner 不能用自然语言越过权限门, Critic 也不能替代测试.

恢复部分给了三种模式. 先验证再提交: 改动先在隔离副本上通过检查, 再写到权威位置. 检查点: 每完成一个验证过的阶段就保存可恢复的状态. Saga 补偿: 跨多个外部系统的操作无法整体回滚时, 为每一步准备补偿动作. 之后的错误分类与重试矩阵列了七类错误, 只有限流和瞬时服务错误允许在退避, 抖动和上限之下原样重试. 模式错误返回精确的校验信息再有限重新生成, 权限拒绝要请求授权或停止, 超时且副作用未知时先按操作 ID 或幂等键查状态, evaluator 自己失败时不能把任务算作成功.

### 2.2 每次调用看到什么

[13.3.2 上下文管理策略](./13.3.2-上下文管理策略.md) 的出发点是: 上下文窗口是一次模型调用可见的输入, 不是 Agent 的完整状态或长期记忆. 它把数据分成稳定指令, 任务状态, 原始事件, 权威工件和派生视图 (记忆, 摘要, 索引) 五类, 每类的权威性和生命周期不同. KV cache 和供应商的 prompt cache 是计算优化, 不等于用户记忆.

组装上下文受预算约束. 设输入预算为 $B$, 各类内容占用 $b_i$, 给输出保留 $B_{out}$, 则 $\sum_i b_i + B_{out} \le B$. 预算是上限, 过多的候选工具, 重复的历史和长日志会降低有效信息密度. 在这个约束下, 13.3.2 给了六种互补策略: 选择, 卸载, 检索, 压缩, 隔离, 缓存. 卸载之后读回时要校验对象版本没有变化, 召回的文本也不能获得系统指令的信任级别.

### 2.3 多 Agent 与沙箱

[13.3.3 多 Agent 系统](./13.3.3-多Agent系统.md) 把多 Agent 定义为一种系统分解, 不同工作单元获得不同的任务, 上下文, 工具或检查职责. 拆分只在几种条件下才可能有价值: 子任务可以真实并行; 需要不同的工具, 权限或专业上下文; 需要独立的生成和审计通道; 单一上下文太大. 共享状态采用只追加的事件流, 乐观并发或锁, 以及单一提交者. 多个模型投票不是分布式共识协议, 它们的错误往往相关.

[13.3.4 运行时环境与沙箱](./13.3.4-运行时环境与沙箱.md) 从「模型输出只是动作提议」出发: 真正改变文件, 访问网络或调用业务 API 的是宿主运行时, 所以安全边界建在模型之外. 它先建威胁模型 (用户输入, 外部内容, 模型输出, 依赖与镜像四类不可信来源), 再比较受限子进程, Linux 容器, gVisor, Firecracker MicroVM, WebAssembly/WASI 和远程托管执行. 这些方案的边界各不相同, 不能排成一条从弱到强的线, 沙箱也不能替代业务授权, 数据分类, 操作确认和输出验证.

## 3. 可靠性的先后顺序

### 3.1 由内向外搭建

建设顺序从最内层开始. 先写成功和停止条件, 没有它们, 后面所有的重试和恢复都没有判据. 再定义工具契约, 权限和副作用, 让每个动作的影响范围在执行前就已知. 然后实现错误分类, 幂等, 回滚和检查点. 再往外才是上下文的选择与压缩. 只有单 Agent 仍有明确瓶颈时, 才引入多 Agent; 最后用同一套评测证明新增的复杂度有价值.

这个顺序的依据是成本和故障组合. 多一个角色, 多一次反思, 或者更长的上下文, 都会增加调用次数, 状态, 权限和故障组合, 它们不是免费的增益. 一个没有幂等和检查点的系统加上多 Agent, 并发写冲突和重复副作用会成倍增加; 反过来, 内层已经稳固的系统, 加一个审计 Agent 的风险是可控的.

### 3.2 上线验收

上线前要确认的第一组条件关于状态和执行. 任务状态可持久化, 恢复时不会重复不可重放的动作; 工具参数校验, 授权和执行是宿主分开的三个步骤; 外部内容被当作不可信数据, 不会直接提升权限; 有超时, 取消, 最大步数, 费用上限和无进展停止; 并发写入有版本或事务冲突处理.

第二组关于验证和观测. 最终成功由外部验证器确认, 不由模型自述; 日志能重建每个动作和对应证据, 但不记录密钥和不必要的私有推理; 框架或模型升级后, 运行同一套回归集. 四篇文章末尾各有一份更细的验收清单, 分别针对编排, 上下文, 多 Agent 和沙箱, 本节的两组条件是它们的公共部分.

## 4. 读法与边界

### 4.1 按背景进入

后端或分布式系统背景的读者, 会在本节看到熟悉的东西: 状态机, Saga, 乐观并发, 只追加日志. 可以直接从 13.3.3 第 5, 6 节开始, 看这些机制在 Agent 场景下哪里需要调整, 例如模型之间共享训练数据和错误, 票数不能当成独立证据, 最终写入仍要有明确的提交者和审批链. 从提示工程转过来的读者, 先读 13.3.1 和 13.3.2, 它们解释了为什么很多看起来是提示问题的故障, 根因在状态和上下文的组织方式.

负责安全或平台的读者, 13.3.4 是主线, 它的选型检查表和红队部分可以直接用于评审. 想看这些原则在一个真实系统里的样子, [SWE-agent](https://arxiv.org/abs/2405.15793) 的 Agent-Computer Interface 设计是公开可查的例子, 它表明工具接口的设计本身会影响 Agent 的成功率.

### 4.2 与相邻章节的分工

工具调用协议, MCP 和记忆系统的组件细节在 [13.1 核心组件](../13.1-Agent核心组件/13.1-Agent核心组件.md); 本节只讨论它们在运行时怎样被调度和隔离. 13.3.2 和 [7.6 上下文工程](../../7-LLM应用开发/7.6-上下文工程/7.6-上下文工程.md) 有重叠, 7.6 面向一般的 LLM 应用, 本节侧重 Agent 多步运行中的状态与交接.

权限, 审批和提示注入的治理在 [13.5 应用与治理](../13.5-Agent应用与治理/13.5-Agent应用与治理.md) 的 13.5.3; 本节的沙箱提供执行层的隔离, 13.5.3 决定什么动作需要谁批准. 跨系统的供应链安全参考 NIST [SP 800-218A](https://csrc.nist.gov/pubs/sp/800/218/a/final).

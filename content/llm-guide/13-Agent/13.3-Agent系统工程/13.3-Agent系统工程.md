# Agent 系统工程：状态、编排、隔离与恢复

Agent 的工程质量不取决于框架名称，而取决于：状态是否显式、动作是否受控、失败是否可分类、结果是否可验证、运行是否可停止和恢复。模型、提示、工具和框架都可以替换，这些系统责任不能省略。

> **证据边界**：本文截至 2026-09-01。不使用缺少任务集、模型、harness 和成本口径的产品成功率，也不把框架示例当作架构优越性的证明。

## 2. 六个系统平面

| 平面 | 核心工件 | 失败示例 |
|---|---|---|
| 任务 | 目标、约束、完成证据、预算 | 目标不可验证、范围漂移 |
| 状态 | 事件、工作状态、工件、版本 | 摘要覆盖真值、并发覆盖 |
| 决策 | 模型、规则、计划、路由 | 错误工具、循环、错误停止 |
| 执行 | 工具、运行时、权限、幂等 | 越权、重复副作用、逃逸 |
| 验证 | 测试、断言、evaluator、人工检查 | 假成功、覆盖不足、裁判偏差 |
| 观测 | 追踪、成本、错误、审计 | 无法重放、敏感信息泄露 |

把这些责任全塞进一个 system prompt，不能替代实际控制面。

## 3. 从状态机开始

推荐最少区分：`pending`、`running`、`waiting_for_input`、`waiting_for_approval`、`succeeded`、`failed`、`cancelled`。每次转换记录触发事件、状态版本、执行者和证据。

这样才能回答：超时后工具是否可能已经执行？用户取消后后台进程是否仍在运行？恢复时从哪个已验证检查点开始？如果只有一段聊天记录，这些问题通常没有可靠答案。

## 4. 可靠性优先级

1. 先写成功和停止条件；
2. 再定义工具契约、权限与副作用；
3. 再实现错误分类、幂等、回滚和检查点；
4. 再做上下文选择与压缩；
5. 只有单 Agent 仍有明确瓶颈时，才引入多 Agent；
6. 最后用同一评测证明新增复杂度有价值。

多一个角色、多一次反思或更长上下文都不是免费增益。它们增加调用、状态、权限和故障组合。

## 5. 上线验收

- [ ] 任务状态可持久化，恢复不会重复不可重放动作。
- [ ] 工具参数、授权和执行是分开的宿主步骤。
- [ ] 外部内容被当作不可信数据，不会直接提升权限。
- [ ] 有超时、取消、最大步骤、费用和无进展停止。
- [ ] 并发写入有版本或事务冲突处理。
- [ ] 最终成功由外部验证器确认。
- [ ] 日志能重建动作与证据，但不记录密钥和不必要的私有推理。
- [ ] 框架或模型升级后运行同一回归集。

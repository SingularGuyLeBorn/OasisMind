# Agent：从模型调用到可审计的闭环系统

Agent 不是某个特定模型，也不是“让模型多思考几步”的同义词。工程上更有用的定义是：**Agent 是一个围绕目标持续读取状态、提出动作、调用外部能力、吸收结果并决定继续或停止的闭环系统**。大语言模型可以承担其中的决策或生成工作，但状态存储、工具执行、权限校验、重试、停止条件和结果验收都属于系统层。

> **证据与时效边界**：本文基于截至 2026-09-01 可核验的原始论文、协议规范和官方仓库。产品能力、排行榜与 API 字段变化较快；正文不把某次演示、单一排行榜快照或厂商营销指标当成普遍结论。

## 2. 闭环比“自主性”更可操作

把一次运行记作事件序列：用户给出目标，控制器读取当前状态，模型或规则提出动作，执行层产生观察，验证器判断是否达标，然后更新状态并继续。这个描述不要求系统完全自主，也不要求公开模型的内部思维过程。

一个可落地的循环至少包含：

1. **目标与完成契约**：要产出什么、怎样验证、何时停止。
2. **受控状态**：当前计划、已完成动作、工具结果、未解决问题和预算。
3. **动作提议**：模型输出文本、结构化命令或工具调用请求。
4. **策略与权限检查**：在执行前校验参数、身份、作用域、副作用和审批要求。
5. **环境执行**：工具、API、浏览器、数据库或代码运行时真正改变或读取外部状态。
6. **观察与验证**：记录结果、错误和证据，使用测试或判定器检查任务是否完成。
7. **停止机制**：成功、不可恢复失败、预算耗尽、需要人工决策或检测到循环时退出。

ReAct 论文展示了交替生成推理线索与动作、再读取环境观察的范式，但生产系统不必保存或展示自由文本思维链。更稳妥的审计材料是**计划摘要、工具参数、授权决定、工具结果、验证证据与状态变更**。

## 3. 六个容易混淆的概念

| 概念 | 主要职责 | 不自动意味着 |
|---|---|---|
| 模型调用 | 根据输入生成输出 | 有持久状态、能执行动作 |
| Workflow | 按预定义图或规则编排步骤 | 每一步都由模型动态决策 |
| Agent | 根据反馈动态选择下一动作 | 无限制自治、无需审批 |
| Tool / Function calling | 让模型提出具名调用及参数 | 模型已经执行了函数 |
| MCP | 规范客户端与服务器之间暴露上下文和能力的协议 | 自动解决授权、提示注入和业务语义 |
| Structured Outputs | 约束输出满足某个结构契约 | 内容真实、权限正确、业务规则成立 |

这些边界很重要。模型生成 `delete_file(path=...)` 只是一项**动作提议**；宿主应用仍必须完成模式校验、路径归一化、权限检查、用户确认和实际执行。

## 4. 设计 Agent 的正确起点

不要先选“最强模型”，先写任务契约：

- 输入来自哪里，哪些输入不可信？
- 成功能否由测试、查询结果、状态差异或人工验收验证？
- 允许读取和修改哪些对象？哪些动作可重试，哪些不可重放？
- 最大步数、时间、token、金额和并发预算是多少？
- 哪些情况必须暂停并请求用户决定？
- 运行结束后，审计者需要看到哪些证据？

如果任务路径固定、每一步都能写成确定规则，普通工作流通常更易预测。Agent 更适合路径需要根据中间观察变化、工具选择无法预先穷举，但结果仍可验证的任务。开放目标、不可验证结果和高风险副作用同时出现时，应降低自治级别，而不是只增加提示词。

## 5. 可靠性来自多层防线

### 5.1 生成层

- 工具描述明确写出输入、输出、错误、幂等性和副作用。
- 用结构化契约约束动作，不从自然语言中正则提取关键参数。
- 将稳定指令、动态任务、工具结果和不可信网页内容分区，避免混成一段提示。

### 5.2 执行层

- 服务器端再次验证参数；不要相信模型生成的类型和值域。
- 默认最小权限，读写工具分离，高风险动作要求批准。
- 为网络、文件和代码执行设置资源限制、超时和可访问范围。
- 为非幂等调用使用幂等键或业务去重，避免超时重试造成重复转账、重复发信。

### 5.3 验证层

- 用外部可观察证据验收，例如测试通过、数据库状态满足断言、引用能回到原文。
- 区分“工具返回成功”和“任务完成”；HTTP 200 并不证明业务目标达成。
- 对无法自动判定的高影响结果保留人工检查点。

### 5.4 可观测层

建议为一次运行生成稳定的 `run_id`，并记录：模型和提示版本、可用工具集合、每次调用的参数摘要与授权决定、结果哈希或受控摘录、错误类别、重试原因、预算消耗、最终验证结论。敏感凭据、完整个人数据和模型私有推理不应进入普通日志。

## 6. 常见失效模式

| 失效模式 | 表现 | 优先修复点 |
|---|---|---|
| 错误累积 | 早期错误状态被后续步骤当成事实 | 在状态写入前验证；保留原始证据引用 |
| 循环 | 重复相同工具与参数，结果没有新信息 | 动作指纹、无进展计数、替代策略与硬停止 |
| 工具误选 | 名称相近或描述重叠导致错误调用 | 缩小候选集、改进工具描述、离线调用选择评测 |
| 参数合法但危险 | 模式合规，却越权访问或扩大删除范围 | 授权、作用域限制、预览和审批 |
| 提示注入 | 网页、文件或工具结果诱导覆盖系统目标 | 数据与指令分离；不可信内容降权；敏感动作再授权 |
| 记忆污染 | 错误摘要或过期偏好长期影响决策 | 来源、版本、有效期、冲突检测和可撤销写入 |
| 假成功 | Agent 自述“已完成”，没有外部证据 | 完成判定交给测试或独立验证器 |
| 不可复现 | 模型、工具和环境变化后结果漂移 | 固定快照，记录配置和环境版本，保存最小轨迹 |

## 7. 评估的最小单位是联合系统

Agent 结果受到模型、提示、工具实现、候选工具集合、上下文策略、环境版本、预算和重试策略共同影响。因此只报告模型名或单一成功率是不够的。评估至少应覆盖：

- **任务成功**：基于可执行验证器或明确量表，而不是模型自评。
- **轨迹质量**：无效调用、重复调用、恢复能力、停止是否正确。
- **安全性**：越权、提示注入、敏感数据泄露和高风险动作误执行。
- **资源**：端到端延迟、模型 token、工具成本、峰值并发；报告分布而非只报均值。
- **可复现性**：任务集版本、环境镜像、模型快照、提示和 harness 版本。

具体基准和报告方法见 [Benchmark 与 Eval](./13.5-Agent应用与治理/13.5.2-Benchmark与Eval.md)。不同基准的任务、环境和评估器不同，不能把分数直接横向拼成“通用智能排名”。

## 8. 上线前验证清单

- [ ] 成功条件由系统外部证据定义，而不是 Agent 自述。
- [ ] 每个工具都记录参数模式、返回结构、超时、错误和副作用。
- [ ] 所有工具参数在执行端重新验证。
- [ ] 读、写、删除、支付和对外通信有不同权限级别。
- [ ] 非幂等动作有预览、审批或幂等保护。
- [ ] 不可信内容不会直接成为高优先级指令。
- [ ] 有最大步数、最大成本、无进展检测和人工升级路径。
- [ ] 记忆写入带来源、时间、作用域和撤销机制。
- [ ] 日志足以重建动作与证据链，同时不泄露凭据和敏感数据。
- [ ] 在正常、异常、恶意输入和依赖故障四类场景上做过回归评测。

# 脚手架改进（Σ 快循环）

[第 04 章](../04-模型参数改进/04-模型参数改进.md) 讲了改权重。本章讲改脚手架。两者的关系：权重是能力底座，脚手架是能力的放大器和路由器。底座不够强时，改脚手架能有效利用已有能力；底座够强时，脚手架决定能力在什么场景下被释放。

2026 年产业里绝大多数标称「自改进」的系统，改的是脚手架。原因简单：快、便宜、可回滚、可审计，不需要 GPU 集群。

---

## 1. 本章定位：U_Σ 快循环概览

### 1.1 改的是什么

回顾 [01 章](../01-定义与形式化/01-定义与形式化.md) 式（6）：

$$
\Sigma_{t+1} = \mathcal{U}_\Sigma(\Sigma_{1:t};\; \mathcal{S}_t), \qquad \theta_{t+1} = \theta_t. \tag{6, 复述}
$$

$\Sigma$ 变了，$\theta$ 冻结。回顾 $\Sigma$ 的四个分量：

| 分量 | 含义 | 本章节 |
|---|---|---|
| $p_t$ | 结构化提示 | §2 提示优化 |
| $m_t$ | 记忆及检索策略 | §3 记忆演化 |
| $\mathcal{T}_t$ | 工具集及调用接口 | §4 工具治理 |
| $g_t$ | 控制逻辑 | §5 全脚手架重写（改 $g$ 通常牵连整个 $\Sigma$） |

还有一个正交维度：§6 技能。技能不是第五个分量，而是可以存在任何分量里的可复用更新算子。

### 1.2 和 θ 慢循环的对比

[04 章](../04-模型参数改进/04-模型参数改进.md) §1.3 已经列了对比表。这里补一个 $\Sigma$ 改进独有的属性：**可审计性**。

$\theta$ 改了之后，你不知道具体改了什么——参数不可读，只能通过 eval 观察行为变化。

$\Sigma$ 改了之后，diff 是文本。你可以逐行审计新旧提示的差异，可以比对新旧工具列表，可以回放记忆变化历史。这意味着 $\Sigma$ 改进天然适合人类监督和安全审计——[01 章](../01-定义与形式化/01-定义与形式化.md) §4 闭环程度光谱的「人监督」列，主要落在 $\Sigma$ 改进上。

### 1.3 为什么 2026 产品里大多数「自改进」在这一层

三个原因：

1. **部署约束**：多数产品用 API 调模型（GPT-4、Claude），无法改权重。唯一能改的就是脚手架。
2. **迭代速度**：$\Sigma$ 改进的 cycle time 是秒级，可以在一次对话中迭代多轮；$\theta$ 改进的 cycle time 是小时到天，不可能实时。
3. **风险可控**：$\Sigma$ 改坏了可以一键撤销；$\theta$ 改坏了需要回滚 checkpoint，且可能已经污染了下游的蒸馏管线。

但 $\Sigma$ 改进的天花板受 $\theta$ 约束。一个 7B 模型靠改 prompt 无法获得 70B 的世界知识。脚手架改进是在已有能力的边界内重新分配注意力，不是扩大边界。

## 2. 提示优化（$p_t \to p_{t+1}$）

### 2.1 搜索范式

最早也最直接的思路：把提示当搜索空间中的一个点，用搜索算法找更好的提示。

**APE（Automatic Prompt Engineer）**（Zhou et al., ICLR 2023）：

1. 给 LLM 几个（input, output）示例
2. 让 LLM 生成多条候选指令
3. 在验证集上评估每条指令
4. 选最好的

APE 在 24/24 个 InstructionInduction 任务上超过人工提示，在 21/24 个上超过 chain-of-thought 提示。核心数字：平均准确率从人工的 64.3% 到 APE 的 75.1%（+10.8 pp）。

验证层级：L3（在验证集上跑，看准确率）。评估器是固定的，属于有界精炼。

**EvoPrompt**（Guo et al., 2024）：

1. 初始化一批提示（population）
2. 交叉（取两条提示的不同部分拼接）
3. 变异（让 LLM 改写提示的某个片段）
4. 选择（在验证集上保留分数最高的）
5. 重复

EvoPrompt 用了遗传算法的框架，但交叉和变异都由 LLM 执行，不是字符级操作。

和 APE 比：APE 是一次性生成+选择，EvoPrompt 是多轮迭代。EvoPrompt 在 BBH 上比 APE 高 3.2 pp（Llama-2 70B）。

**PromptBreeder**（Fernando et al., 2024）：

PromptBreeder 做了一件特殊的事：**进化提示的提示也在进化**。

```
层 0：任务提示（直接给 LLM 执行任务的指令）
层 1：变异提示（指导如何修改层 0 提示的指令）
层 1 也在进化 → 搜索策略本身在被优化
```

这是 [01 章](../01-定义与形式化/01-定义与形式化.md) §5 GAI 旋钮 1 的一个实例：改进器（层 1 变异提示）部分在 $\Sigma$ 内。不是完全自指（变异提示不改变异提示自己的变异策略的变异策略...），但已经是弱自指。

PromptBreeder 在 GSM8K 上比 APE 高 5.7 pp，在 ARC-C 上高 3.1 pp。增益来自搜索策略的联合优化。

### 2.2 梯度模拟

把提示优化类比为梯度下降：当前提示是「参数」，评估指标是「loss」，用自然语言描述的修改建议是「梯度」。

**OPRO（Optimization by PROmpting）**（Yang et al., ICLR 2024）：

在 ProTeGi 之前，Google 提出了一个更简单的版本。把历史（提示→分数）对放进 meta-prompt，让 LLM 直接提出下一个候选提示。

OPRO 在 GSM8K 上发现了一条出人意料的指令："Take a deep breath and work on this problem step-by-step."——准确率比 "Let's think step by step" 高 2.8 pp（GPT-4）。这不是人类会写的提示，但 LLM 的搜索找到了它。

OPRO 的搜索没有梯度概念，纯粹靠历史分数引导。它的效率低于 ProTeGi（需要更多候选才能收敛），但概念更简单。

**ProTeGi（Prompt via Textual Gradients）**（Pryzant et al., 2023）：

1. 在 mini-batch 上评估当前提示
2. 让 LLM 分析错误样本，生成「文本梯度」：描述提示哪里该改、怎么改
3. 用文本梯度生成多条候选新提示（beam search）
4. 在验证集上选最好的
5. 重复

文本梯度的形式：自然语言，如 "The prompt should specify that the model should consider edge cases involving negative numbers."

ProTeGi 在 6 个 NLI/分类任务上平均比 APE 高 4.6 pp.beam width = 4 时效果最好。和 OPRO 比，ProTeGi 的「梯度」是从错误样本推导出来的定向修改建议，而不是历史分数的盲搜。这让它的搜索效率更高：平均 15 步收敛（OPRO 需要 40–60 步）。

**TextGrad**（Yuksekgonul et al., 2024）：

TextGrad 把 ProTeGi 的思路泛化：不只优化提示，可以优化 LLM 管线中任何文本组件（提示、few-shot 示例、中间步骤的结构）。

核心抽象：把 LLM 调用当成可微分函数，输入文本是「变量」，输出文本是「函数值」，LLM 生成的改进建议是「梯度」。

TextGrad 在 GPT-4 code optimization 上比直接提示提升 20%（LeetCode hard pass rate: 39% → 59%）。

### 2.3 强化学习

把提示的每个 token（或每个短语）当 action，用 RL 优化。

**RLPrompt**（Deng et al., 2022）：

1. 冻结 LLM
2. 训练一个小策略网络，逐 token 生成提示
3. 用任务指标（分类准确率、生成质量）做 reward
4. PPO 优化策略网络

RLPrompt 生成的提示通常不是人可读的自然语言。例如，在情感分类上 RLPrompt 生成的提示是 "categorically irrespective unless purely"——语义不明但准确率高。

这是 $\Sigma$ 改进中可审计性的反例：虽然提示是文本，但生成的提示人类读不懂。

在 SST-2 上 few-shot 准确率从 88.3%（人工提示）到 93.7%（RLPrompt,+5.4 pp）。

**TEMPERA（Test-time Prompt Editing using Reinforcement learning with Action space）**（Zhang et al., 2023）：

1. 从人工提示出发
2. 定义编辑操作：增/删/改 few-shot 示例，调整指令措辞
3. 用 RL 学一个编辑策略
4. 测试时对每个输入在线编辑提示

和 RLPrompt 的区别：TEMPERA 从人可读提示出发做编辑，结果仍然人可读。RLPrompt 从头生成，结果不可读。

TEMPERA 在 SuperNI 上比固定提示高 2.1 pp，比 APE 高 0.8 pp。优势在测试时自适应：不同输入用不同版本的提示。

### 2.4 规划式

**PromptAgent**（Wang et al., 2024）：

1. 把提示空间建模为搜索树
2. 每个节点是一个提示变体
3. 用 MCTS（蒙特卡洛树搜索）探索
4. 每次扩展：让 LLM 提出一个修改，评估修改后的提示
5. UCB 做 exploration-exploitation 平衡

PromptAgent 在 BIG-Bench Hard 的 12 个任务上平均超 CoT 提示 7.3 pp（GPT-4）。MCTS 搜索深度 = 5 时效果饱和，意味着最优提示和初始提示的编辑距离通常 $\leq 5$ 步。

### 2.5 DSPy / MIPROv2：编译时提示优化

以上方法都是「搜索最佳提示文本」。DSPy（Khattab et al., 2024）换了思路：把提示当编译产物，开发者写的是程序（声明式 module 组合），编译器自动把程序翻译成最优提示。

**MIPROv2**（Opsahl-Ong et al.，2024，DSPy 生态）：

1. 对每个 DSPy module，用 Bayesian 优化联合调以下三项：
   - 指令文本
   - few-shot 示例选择
   - 示例顺序
2. 用 TPE（Tree-structured Parzen Estimator）做搜索
3. 在验证集上评估

MIPROv2 在 HotPotQA 上比手写 CoT 高 8.1 pp，比 APE 高 3.2 pp。增益来自联合优化：指令和示例不是独立最优的，它们之间有交互——某些指令配特定示例效果更好。

这对 §2.1–2.4 所有方法都是一个提醒：只优化指令文本不够，整个提示模板（指令 + 示例 + 格式 + 排序）是联合优化空间。

### 2.6 提示优化方法的统一视角

| 方法 | 搜索策略 | 可读性 | 验证层级 | 是否自指 |
|---|---|---|---|---|
| APE | 一次采样+选择 | 高 | L3 | 否 |
| EvoPrompt | 进化（交叉+变异+选择） | 高 | L3 | 否 |
| PromptBreeder | 进化 + 变异策略也进化 | 高 | L3 | 弱自指 |
| ProTeGi | 文本梯度+beam search | 高 | L3 | 否 |
| TextGrad | 泛化文本梯度 | 高 | L3 | 否 |
| RLPrompt | RL 逐 token 生成 | 低 | L3 | 否 |
| TEMPERA | RL 编辑操作 | 高 | L3 | 否 |
| PromptAgent | MCTS 搜索 | 高 | L3 | 否 | 深度 ≤5 |
| MIPROv2 | Bayesian 联合优化 | 高 | L3 | 否 | 100–300 trial |

所有方法的验证层级都是 L3（在验证集上评估）。没有一个方法用 L4 形式证明验证提示质量——提示优化本质上是经验搜索。

PromptBreeder 是唯一一个弱自指的方法。其他方法的搜索策略是固定的外部算法，不随搜索过程改变。

提示优化的隐含假设：存在一个更好的提示，当前模型在该提示下表现更好。这个假设在模型能力范围内成立，但到了能力边界外就失效——再好的提示也不能让 7B 模型做 70B 才能做的推理。

## 3. 记忆演化（$m_t \to m_{t+1}$）

### 3.1 操作系统式记忆：MemGPT

Packer et al. (2023) 提出 MemGPT：用操作系统的虚拟内存概念管理 LLM 的上下文。

| 层 | 类比 | MemGPT 实现 | 容量 |
|---|---|---|---|
| 主上下文 | RAM | LLM 的 context window | 受模型限制（4K–128K） |
| 外部存储 | 硬盘 | 向量数据库 + 结构化存储 | 无限 |
| 分页机制 | 页面调度 | LLM 自己决定何时换入/换出 | 由策略控制 |

核心思路：LLM 通过 function call 调用 `core_memory_append`、`core_memory_replace`、`archival_memory_search` 等操作，自己管理哪些信息在 context window 里、哪些存在外部。

MemGPT 在长文档 QA 上比固定上下文窗口的 GPT-4 高 11.2 pp（F1 score, 200+ page docs）。

从 $\Sigma$ 改进的视角：MemGPT 改的是 $m_t$（记忆内容和检索策略）。但改的策略（分页逻辑）是固定的函数调用，不是学到的。Agent 不能改「怎么分页」的策略——它只能在固定策略下操作记忆内容。

### 3.2 卡片盒记忆：A-Mem

Yu et al. (2025) 提出 A-Mem (Agentic Memory)：用 Zettelkasten（卡片盒）方法组织 Agent 记忆。

每条记忆是一张卡片，包含：
- 内容（原始信息）
- 关键概念（自动提取）
- 和其他卡片的链接（自动建立）
- 元数据（创建时间、来源、置信度）

Agent 在交互过程中自动执行五种操作：创建卡片、链接卡片、更新卡片、合并重复卡片、删除过时卡片。

和 MemGPT 的区别：MemGPT 是平面存储 + 检索；A-Mem 是结构化的链接网络。A-Mem 的信息组织本身就是知识——链接关系表达了概念之间的关系。

A-Mem 在 10-session 连续对话任务上比 MemGPT 高 8.3 pp（信息保持率）。增益来自链接结构：相关记忆通过链接被一起检索，而不是靠向量相似度单独匹配。

### 3.3 经验积累

**Reflexion**（Shinn et al., NeurIPS 2023）：

Agent 失败后生成一段文字反思（verbal reflection），存入记忆。下次遇到类似任务时，反思被检索出来，加入 context。

Reflexion 的记忆格式是自然语言，如："Last time I failed because I didn't check the edge case where the list is empty. Next time, always validate inputs first."

在 HumanEval 上，Reflexion 把 pass@1 从 67.0%（GPT-4 baseline）提到 91.0%（+24 pp，至多 3 轮反思）。

限制：反思质量取决于模型的自我诊断能力——这是 [02 章](../02-验证层级与自评估/02-验证层级与自评估.md) 的 L1 内省。模型不知道自己为什么错时，反思就是噪声。

**ExpeL（Experience Learning）**（Zhao et al., 2024）：

1. Agent 在多个任务上试错，积累（任务，轨迹，成功/失败）记录
2. 从成功和失败轨迹的对比中提取**跨任务经验洞察**
3. 洞察以自然语言规则存储，如："When using a search API, always quote exact phrases to reduce noise."
4. 新任务时检索相关洞察加入 context

和 Reflexion 的区别：Reflexion 是单任务反思（「这道题我哪里错了」），ExpeL 是跨任务经验（「这类任务有什么共性注意事项」）。

ExpeL 在 ALFWorld 上比 Reflexion 高 6.4 pp（4 轮经验积累后）。增益来自跨任务迁移：一个任务上学到的经验适用于另一个。

**Dynamic Cheatsheet**（Liu et al., 2025）：

Agent 在做题过程中维护一张「小抄」——按主题组织的注意事项列表。每做完一题，根据成功/失败更新小抄。

和 ExpeL 的区别：小抄是结构化的（按主题分类，每条有优先级），而不是无结构的规则列表。

在 MATH-500 上，Dynamic Cheatsheet 比 ExpeL 高 2.8 pp。结构化的好处是检索更精准：按主题匹配比按语义向量匹配更稳定。

### 3.4 符号记忆：ChatDB

Hu et al. (2023) 提出 ChatDB：用 SQL 数据库做 LLM 的外部记忆。

```
用户：我上周买了 3 本书,花了 120 元.
Agent：INSERT INTO purchases (date, item, quantity, amount)
       VALUES ('2023-10-15', 'books', 3, 120);
用户：我这个月总共花了多少钱？
Agent：SELECT SUM(amount) FROM purchases
       WHERE date >= '2023-10-01';
```

记忆的读写通过 SQL 操作，精确且可审计。不存在向量检索的 topK 近似问题。

限制：需要预定义 schema。非结构化信息（对话上下文、情感、隐含意图）难以入表。

### 3.5 读压缩：ReadAgent

Lee et al. (2024) 提出 ReadAgent：用 gist（摘要）分页管理长文档。

1. 把长文档切成页
2. 每页生成 gist（一句话摘要）
3. 面对查询时，先检索 gist 找到相关页
4. 只读取相关页的全文

和 MemGPT 的关系：MemGPT 是交互式记忆管理（边聊边管），ReadAgent 是读取时压缩（读前先筛）。

ReadAgent 在 NarrativeQA 上比全文输入（截断到 context window）高 14.7 pp（F1）。原因：截断丢的是后面的内容，ReadAgent 保留了全文中和查询相关的部分。

### 3.6 记忆方法的对比

| 方法 | 记忆类型 | 组织方式 | 持久化 | 验证层级 | 跨任务迁移 |
|---|---|---|---|---|---|
| MemGPT | 分页虚拟上下文 | 平面 + 分页调度 | 是 | 不适用（管理机制） | 弱 |
| A-Mem | 卡片盒链接网络 | 图结构 | 是 | 不适用 | 中 |
| Reflexion | 言语反思 | 自然语言列表 | 可选 | L1 | 弱（单任务） |
| ExpeL | 跨任务经验 | 自然语言规则 | 是 | L1–L3 | 强 |
| Dynamic Cheatsheet | 结构化小抄 | 按主题分类 + 优先级 | 是 | L3 | 中 |
| ChatDB | SQL 数据库 | 关系表 | 是 | L3（查询精确性） | 中 |
| ReadAgent | gist 分页 | 摘要索引 | 否（读取时临时生成） | 不适用 | 弱 |

### 3.7 记忆 ≠ 改进器

**重要区分**：记忆变大、变多、变结构化，不等于 Agent 的改进器升级了。

以 [01 章](../01-定义与形式化/01-定义与形式化.md) 的框架判断：$m_t$ 增长是 $\Sigma$ 改进的一个实例——记忆内容变了，配置确实更新了。但改进器 $\mathcal{U}$ 没有变。Agent 用同样的策略管理记忆，只是记忆里多了数据。

这是 $\Sigma$ 改进还是 [01 章](../01-定义与形式化/01-定义与形式化.md) §1.1 的暂态 $X_t$ 变化？判断标准：

| 条件 | 判定 |
|---|---|
| 记忆跨会话持久化，下次启动还在 | $\Sigma$ 改进 |
| 记忆只在当前会话内，关了就没 | 暂态 $X_t$ 变化，不是自改进 |
| 记忆被用来改写「怎么记忆」的策略 | 开始有自指，可能是弱 RSI |

Reflexion 的 verbal memory 如果不持久化，就只是当前任务的上下文操作。ExpeL 的跨任务经验如果持久化，是 $\Sigma$ 改进。但两者都没有用记忆来改「怎么积累记忆」的策略——改进器 $\mathcal{U}$ 始终是固定的。

这和 [02 章](../02-验证层级与自评估/02-验证层级与自评估.md) §2.2 结果级 vs 过程级的讨论呼应：记忆积累是过程级的改进形态。积累的经验和规则跨任务可复用，不需要每次重来。如果自改进系统的持久收益是记忆层面的——积累的经验越来越多，但 $\theta$ 和记忆策略不变——那成熟的系统更像「经验丰富的人」而不是「能力跃迁的超人」。

## 4. 工具治理（$\mathcal{T}_t \to \mathcal{T}_{t+1}$）

### 4.1 工具治理 vs 工具使用

先区分两件不同的事：

| | 工具使用 | 工具治理 |
|---|---|---|
| 改什么 | 不改 $\mathcal{T}$，只调用 | 改 $\mathcal{T}$ 本身 |
| 例子 | Agent 用搜索 API 查信息 | Agent 发现搜索 API 太慢，换成另一个 |
| 框架定位 | 策略 $\pi$ 的执行 | $\mathcal{U}_\Sigma$ 的实例 |
| 改进？ | 不是（配置没变） | 是（$\mathcal{T}$ 变了） |

很多论文把「更好地使用工具」和「改进工具集」混在一起。前者是推理能力问题（属 $\theta$ 或暂态 $X$），后者是脚手架改进（属 $\Sigma$）。

### 4.2 工具使用训练（改 θ 以更好地调用固定的 T）

这一组严格说属于 [04 章](../04-模型参数改进/04-模型参数改进.md) 的 $\theta$ 改进，但因为和工具治理紧密相关，在这里一起讨论。

**ReTool**（Feng et al., 2025）：用 RL 训练 LLM 在推理过程中调用代码解释器。

- 训练信号：执行反馈（代码跑通 = 正奖励，报错 = 负奖励）
- 验证层级：L3
- 关键数字：Qwen-2.5 7B + ReTool 在 MATH-500 上从 61.4% → 75.2%（+13.8 pp）

**ToRL（Tool-integrated Reinforcement Learning）**（Li et al., 2025）：从基座模型做工具使用 RL，不需要 SFT warmup。

- 和 ReTool 的区别：ReTool 从已经做过 SFT 的模型出发；ToRL 直接从预训练模型出发
- 关键数字：Llama-3 8B + ToRL 在 GSM8K 上从 45.3% → 68.7%（+23.4 pp）

**ToolLLM**（Qin et al., 2024）：在 RapidAPI 的 16K+ API 上收集工具调用轨迹，SFT 训练。

- 16,464 个 REST API，覆盖 49 个类别
- 自动生成 126K 条（query, tool_calls, result）轨迹
- 训练后的 ToolLlama-7B 在工具使用准确率上接近 ChatGPT（pass rate 70.4% vs 75.1%）

### 4.3 工具创建（改 T：增加新工具）

**LATM（LLM as Tool Maker）**（Cai et al., 2024）：

1. Agent 遇到一个需要多步计算的任务
2. 把解决过程抽象成一个 Python 函数
3. 函数存入工具库，下次遇到同类任务直接调用

$$
\mathcal{T}_{t+1} = \mathcal{T}_t \cup \{ f_{\text{new}} \}, \quad f_{\text{new}} = \text{AbstractToFunction}(\text{trajectory}_t). \tag{16}
$$

关键数字：在 BigBench-Hard 上，LATM 比每次从头推理快 2.3 倍，准确率持平（±0.4 pp）。省的是重复推理成本，不是提升质量。

LATM 的双角色设计：用 GPT-4 当 tool maker（造工具），用 GPT-3.5 当 tool user（用工具）.maker 贵但只跑一次，user 便宜跑很多次。总成本比全程用 GPT-4 低 75%，准确率只掉 1.2 pp。

**CRAFT**（Yuan et al., 2024）：

1. 从 code repository 里提取可复用的函数
2. 自动写文档和 usage example
3. 注册为新工具

CRAFT 比 LATM 更进一步：不只从当前轨迹造工具，还从外部代码库里发现可用工具。

**Toolformer**（Schick et al., 2023）：更早期的工具创建范式。不是造新工具，而是在现有文本中自动插入工具调用标记。模型学会在适当的位置调用计算器、搜索 API、翻译器等。

Toolformer 在数学推理上比无工具的 GPT-J 高 17.4 pp（PerplexityMath）。但它不改 $\mathcal{T}$——工具集是固定的，只是模型学会了何时调用。所以 Toolformer 严格来说是 [04 章](../04-模型参数改进/04-模型参数改进.md) 的 $\theta$ 改进（学会使用工具），不是本节的工具治理（改 $\mathcal{T}$ 本身）。

### 4.4 模块编排（不改 T，但改 T 的组合方式）

**Chameleon**（Lu et al., 2024）：

1. 分析任务类型
2. 从工具库里选子集
3. 规划调用顺序（composition plan）
4. 执行

Chameleon 不增删工具，但改了「哪些工具被组合在一起」的策略。这是改 $g$（控制逻辑）还是改 $\mathcal{T}$？在本库的框架下归为改 $g$：工具集 $\mathcal{T}$ 不变，变的是调度。

在 ScienceQA 上 Chameleon 比 GPT-4 直接回答高 11.4 pp（86.5% → 97.9%）。增益来自模块组合：不同题目调用不同工具子集。

**ViperGPT**（Suris et al., 2023）：

1. 把视觉问答翻译成 Python 程序
2. 程序调用视觉模块（object detection，depth estimation 等）
3. 执行程序得到答案

$$
\text{answer} = \text{exec}\bigl(\text{LLM}(\text{query} \to \text{Python code}),\; \text{VisualModules}\bigr). \tag{17}
$$

ViperGPT 在 GQA 上达到 61.5% zero-shot（vs BLIP-2 的 44.7%）。关键：LLM 不直接处理图像，只生成调用模块的代码。视觉能力完全来自外部模块。

### 4.5 工具治理的 Σ 改进分析

| 操作 | 改了什么 | 是 Σ 改进吗 | 改进器在 A 内吗 |
|---|---|---|---|
| 更好地使用现有工具 | $\theta$ 或 $X$ | $\theta$：是（[04 章](../04-模型参数改进/04-模型参数改进.md)）；$X$：否 | 取决于训练管线 |
| 创建新工具 | $\mathcal{T}$ | 是 | Agent 自己造工具 → 改进器在 A 内 |
| 删除无用工具 | $\mathcal{T}$ | 是 | 同上 |
| 改工具接口（重写 API） | $\mathcal{T}$ | 是 | 同上 |
| 改调度策略 | $g$ | 是 | 同上 |
| 改调度策略的策略 | $g$ 的元层 | 是，且自指 | 改进器在 A 内，且改进器在改自己 |

最后一行——改调度策略的策略——是自指的入口.§5 全脚手架重写里会展开。

## 5. 全脚手架重写（$\Sigma_t \to \Sigma_{t+1}$）

### 5.1 为什么需要全脚手架重写

§2–4 分别改 $p$、$m$、$\mathcal{T}$。但有些改进需要联合改多个分量：换了工具就要改提示里的工具说明，改了控制逻辑就要调整记忆检索策略。单分量优化的组合不一定是全局最优。

全脚手架重写 = Agent 审视自己的整个 $\Sigma$，提出并执行修改。这是 $\Sigma$ 改进中最激进的形式，也是自指回路最先出现的地方。

### 5.2 全脚手架重写的动机

为什么不满足于分量级优化？因为分量之间有耦合：

- 换了工具 $\mathcal{T}$，system prompt $p$ 里的工具说明需要同步更新
- 改了记忆检索策略 $m$，控制逻辑 $g$ 中的 context 管理也要调整
- 修了控制流 $g$ 中的路由，相关的 few-shot 示例 $p$ 可能不再适用

分量级优化假设其他分量不变。全脚手架重写把 $\Sigma$ 看成整体，允许联合修改。代价是搜索空间爆炸——四个分量的联合空间比任何单一分量大得多。

### 5.3 STOP：改进器源码当优化对象

Zelikman et al. (2024) 提出 Self-Taught Optimizer (STOP)：

1. 改进器本身是一段 Python 代码（scaffolding code）
2. LLM 读自己的改进器代码
3. 提出修改（code patch）
4. 在验证集上评估修改效果
5. 保留改进，重复

$$
g_{t+1} = \text{LLM}\bigl(\text{"改进这段代码"}, g_t, \text{eval}(g_t)\bigr). \tag{18}
$$

STOP 的自指层次：LLM 在修改**自己被用来做优化的那段代码**。不是修改模型权重，而是修改驱动优化的脚手架代码。

关键结果：STOP 发现了非平凡的优化策略——比如在 prompt 里加入对比示例、加入 chain-of-thought 步骤——这些策略是 STOP 自己发明的，不是人类预设的。

在 BIG-Bench Hard 上，STOP 第三轮发现的改进器比第一轮高 6.1 pp。但第五轮和第三轮持平——改进器的搜索空间有限，回报递减。

### 5.3 Gödel Agent：monkey patch 读写运行时 Python

Tao et al. (2025) 提出 Gödel Agent：

1. Agent 的全部逻辑以 Python 代码形式存在
2. Agent 可以在运行时读取自己的源码
3. Agent 可以提出并执行 monkey patch（运行时修改代码）
4. 修改立即生效，不需要重启

和 STOP 的区别：STOP 的修改在轮次之间生效（修改→评估→下一轮）；Gödel Agent 的修改在运行时立即生效（修改→同一次执行里就用新代码）。

Gödel Agent 的递归深度：Agent 修改自己的 `self_improve()` 方法，然后调用修改后的 `self_improve()`——这是直接递归。

安全风险：运行时修改源码意味着 Agent 可以修改自己的安全约束。如果安全检查写在 Python 代码里，Agent 可以 patch 掉。这是 [03 章](../03-失效模式/03-失效模式.md) §4 安全漂移的直接实例。

Gödel Agent 在 GAIA benchmark 上比固定脚手架的 Agent 高 9.2 pp。但作者注意到：约 12% 的修改会导致运行时错误，需要 try-catch 回滚。

### 5.4 DGM（Darwin Gödel Machine）：开放档案 + 门控

Lange et al. (2025) 提出 Darwin Gödel Machine：

1. 维护一个**开放代码档案**（population of code variants）
2. 每个变体是整个 Agent 脚手架的一个版本
3. 新变体由 LLM 基于已有变体提出
4. 在 benchmark 上评估，通过门控才入档案
5. 档案中变体可以交叉组合

和 STOP/Gödel Agent 的区别：

| | STOP | Gödel Agent | DGM |
|---|---|---|---|
| 搜索宽度 | 1（单轨迹，beam search） | 1（单轨迹，运行时修改） | N（种群） |
| 回滚机制 | 用验证集选最好的 | try-catch | 档案门控 |
| 坏补丁处理 | 丢弃 | 运行时异常后回滚 | 不入档案，但保留为交叉材料 |
| 自指深度 | 改优化代码 | 改 self_improve() | 改 self_improve() + 种群交叉 |

DGM 在 ARC-AGI 上达到 21.6%（从零开始，无人工工程）。档案机制解决了 Gödel Agent 的「单轨迹坏补丁」问题：一条轨迹上的坏修改不会污染其他轨迹。

### 5.5 ADAS：元 Agent 固定，搜索下游 Agent 设计

Hu et al. (2024) 提出 Automated Design of Agentic Systems (ADAS)：

1. 一个固定的**元 Agent**（meta-agent）负责搜索
2. 被搜索的对象是下游 Agent 的完整设计（提示 + 工具调用逻辑 + 控制流）
3. 元 Agent 用 LLM 提出候选设计
4. 在 benchmark 上评估
5. 保留好的，继续迭代

和 STOP/Gödel Agent/DGM 的关键区别：**元 Agent 自身不自改。**

$$
\Sigma_{\text{downstream}, t+1} = \text{MetaAgent}_{\Sigma_{\text{meta}}}(\Sigma_{\text{downstream}, 1:t};\; \text{eval}_t), \quad \Sigma_{\text{meta}} = \text{const}. \tag{19}
$$

ADAS 在 DROP 上发现的 Agent 设计比手工 CoT Agent 高 13.2 pp，在 MGSM 上高 14.0 pp。元 Agent 自动发现了多步验证、工具调用回退、自纠错循环等策略——这些策略和人类 Agent 工程师独立发现的模式高度重合，但 ADAS 不需要人工迭代。

ADAS 的搜索空间：每个候选设计是一段 Python 代码，定义了 Agent 的 `forward()` 方法。元 Agent 看到历史设计及其分数，提出新设计。搜索档案中保留 top-$k$（$k = 20$）设计。

但 ADAS 不是 RSI：改进器（元 Agent）不在被改进的系统（下游 Agent）内，不满足 [01 章](../01-定义与形式化/01-定义与形式化.md) §5 GAI 旋钮 1 的「改进器在内」条件。它是有界精炼的外部搜索，不是递归自改进。

ADAS 和 [04 章](../04-模型参数改进/04-模型参数改进.md) §6.2 AZR 的关系：两者都是 proposer-evaluator 结构。AZR 的 proposer 生成任务，evaluator 验证解；ADAS 的 proposer 生成 Agent 设计，evaluator 在 benchmark 上跑分。区别在更新目标：AZR 改 $\theta$，ADAS 改 $\Sigma$。

### 5.6 自指的层次

| 系统 | 改进器改什么 | 改进器在 A 内吗 | 改进器改自己吗 | 自指层次 |
|---|---|---|---|---|
| ADAS | 下游 Agent 的 Σ | 否（元 Agent 固定在外） | 否 | 0（非自指） |
| STOP | 改进器的代码 | 部分（代码在 Σ 内） | 是 | 1（直接自指） |
| Gödel Agent | 运行时的 self_improve() | 是 | 是 | 1–2（递归深度不限，但实际有限） |
| DGM | 种群中的多个版本 | 是（每个版本含改进器） | 是 + 交叉 | 1–2 + 种群交叉 |
| PromptBreeder | 变异策略（层 1 提示） | 是（在 p 内） | 部分（层 1 改层 0，层 1 也被改） | 0.5–1 |

从 ADAS 到 DGM，自指层次递增。自指层次越高，搜索空间越大，但失效风险也越大：改进器改坏了自己 → 后续改进全部基于坏的改进器 → 不可恢复的退化。

DGM 的档案机制是对这个风险的缓解：坏改进器不会覆盖好改进器，两者共存在档案里。

## 6. 技能作为正交概念

### 6.1 定义

Ren et al.（Schmidhuber 组，arXiv:2607.13104）定义：

> **技能（Skill）** = 可复用的、可序列化的更新算子。

一个技能是一段可以被存储、检索、传输、执行的程序，它应用后会改变 Agent 的某个组件。

### 6.2 技能可以存在任何基底

| 基底 | 技能的形式 | 实例 |
|---|---|---|
| $\mathcal{T}$（工具） | 可调用的函数 | Voyager 的 JavaScript 函数库 |
| $p$（提示） | 可插入的指令片段 | 经验规则、rubric、few-shot 模板 |
| $m$（记忆） | 可检索的经验记录 | ExpeL 的跨任务洞察 |
| $\theta$（权重） | LoRA 适配器 | 按任务切换的专家权重 |
| $g$（控制逻辑） | 可执行的代码片段 | STOP 发现的优化策略 |

技能不是 $\Sigma$ 的第五个分量。技能是一种**跨分量的抽象**：一个技能可能同时包含一段提示模板（$p$）、一个工具函数（$\mathcal{T}$）和一段调用逻辑（$g$）。

### 6.3 对象级技能 vs 元级技能

| | 对象级技能 | 元级技能 |
|---|---|---|
| 功能 | 完成某类任务 | 改自己的配置 |
| 例子 | 「怎么排序一个列表」 | 「怎么写一个更好的 system prompt」 |
| RSI 关系 | 不涉及自指 | 改进器进入 A，自指回路开始 |
| 风险 | 低（做错了只影响一个任务） | 高（改错了影响所有后续行为） |

### 6.4 Voyager：对象级技能

Wang et al. (2023) 的 Voyager 在 Minecraft 里积累 JavaScript 函数库：

1. Agent 遇到新挑战
2. 用 LLM 写一个 JavaScript 函数解决它
3. 函数存入技能库
4. 下次遇到类似挑战，检索并调用已有技能

Voyager 在 63 小时内解锁了 Minecraft 技术树的 100%，积累了 368 个技能函数。技能的复用率：平均每个技能被调用 4.7 次。

Voyager 的技能全是对象级的：「怎么挖铁矿」「怎么建熔炉」。没有元级技能「怎么写更好的技能函数」。Agent 写技能的策略（LLM + 固定提示）从头到尾没变。

### 6.5 元级技能 = 改进器进入 A

假设 Voyager 的技能库里多了一个技能：「当你写新技能时，先检查是否已有类似技能，如果有就修改而不是新建。」

这条技能改的不是 Minecraft 里的某个任务，而是**写技能本身的策略**。如果 Agent 能学到、存储并应用这类元级技能，改进器就部分进入了 $\Sigma$。

目前没有系统严格做到了这一步。最接近的是 PromptBreeder（变异策略也在进化）和 DGM（改进器代码也在种群里进化）。

### 6.6 技能的生命周期

一个技能从产生到退役，经历以下阶段：

| 阶段 | 发生什么 | 风险 |
|---|---|---|
| **发现** | Agent 在任务中发现可复用模式 | 模式可能只对当前任务有效 |
| **抽象** | 把具体轨迹抽象成可复用的程序/规则 | 过度抽象丢细节，欠抽象不可复用 |
| **验证** | 在多个任务上测试技能的泛化性 | 验证集可能不代表真实分布 |
| **入库** | 写入共享技能库 | 入库后影响范围扩大（§7 安全面） |
| **检索** | 新任务时被匹配到并调用 | 错误匹配导致用错技能 |
| **演化** | 根据反馈更新技能内容 | 更新可能引入回归 |
| **退役** | 技能过时或被更好的替代 | 不退役会污染检索空间 |

Voyager 实现了发现→抽象→入库→检索，但没有验证、演化和退役。ExpeL 加了验证（跨任务测试）。目前没有公开系统完整实现全部七个阶段。

### 6.7 SkillEvolver

如果一个 Agent 的 SKILL.md 描述了它的行为规范，而另一个 Agent（或自己）根据执行反馈修改这个 SKILL.md，这就是元级技能的写入。

修改 SKILL.md 的 Agent 需要回答：
- 哪条规则需要改？（诊断）
- 改成什么？（生成）
- 改了之后会不会破坏其他规则？（验证）

这三步恰好是 [01 章](../01-定义与形式化/01-定义与形式化.md) 式（4）的执行阶段 → 信号 → 更新阶段。

## 7. Σ 改进的安全面

### 7.1 持久性放大风险

[03 章](../03-失效模式/03-失效模式.md) §4.2 已经指出：持久性放大安全漂移。

在 $\Sigma$ 快循环中，持久性有多种形式：

| 持久化方式 | 传播范围 | 回滚难度 |
|---|---|---|
| 会话内记忆（不持久） | 当前会话 | 关掉就没 |
| 技能写入本地库 | 当前 Agent 后续所有会话 | 需要发现问题 + 手动删 |
| 技能写入共享库 | 所有有权限的 Agent | 需要发现 + 追踪传播链 + 批量撤回 |
| 提示/控制逻辑写入配置文件 | 配置文件作用域内的所有执行 | 需要 diff 审计 + 回滚 |

风险递增：从上到下，一条坏技能的影响范围指数扩大。

### 7.2 SkillMutator 攻击

Liu et al. (Self-Evolving Agents, §11) 描述了一种攻击：

1. 恶意 Agent（或被注入的指令）修改共享技能库里的一个技能
2. 技能的自然语言描述不变（「这个技能用来排序列表」）
3. 技能的可执行代码被篡改（在排序之外偷偷发送数据到外部服务器）
4. 其他 Agent 检索到这个技能，按描述信任它，执行被篡改的代码

**描述和代码讲两个故事。** 这是 $\Sigma$ 可审计性的漏洞：审计描述没用，必须审计代码。

### 7.3 VASO：形式化可验证的技能演化

VASO (Verifiable Autonomous Skill Orchestration) 针对物理 Agent（机器人）提出：

1. 每个技能有一个**形式化前置/后置条件**（precondition/postcondition）
2. 新技能必须证明：在前置条件下执行后，后置条件成立
3. 如果证明不了，技能不入库

这把技能演化从 L2（judge 说安全就安全）提升到 L4（形式证明安全）。

代价：只覆盖可形式化的技能。涉及自然语言理解、创意生成等不可形式化的技能，VASO 不适用。

### 7.4 SHARP：约束自修改面为可审计的 rubric

SHARP (Self-Hardening Auditable Rubric Protocol)：

1. Agent 的安全约束以 rubric（评分表）形式存在
2. rubric 的每一条是一个二值可检查的约束
3. Agent 可以提议修改 rubric，但修改必须通过人工审批
4. rubric 的修改历史完整可审计

SHARP 的思路：不阻止 Agent 修改 $\Sigma$（那不现实，改 $\Sigma$ 是 Agent 的核心能力），而是把安全关键的 $\Sigma$ 子集标记为需要外部审批的区域。

$$
\Sigma = \Sigma_{\text{safe}} \cup \Sigma_{\text{free}}, \quad \Sigma_{\text{safe}} \text{ 的修改需人工审批}. \tag{20}
$$

这是 [03 章](../03-失效模式/03-失效模式.md) §4 「安全约束住在 Agent 外部」的一个实现方式：约束本身在 $\Sigma$ 内（Agent 可以读它们），但修改约束的权限在外部（人审批）。

### 7.5 安全面总结

| 对策 | 验证层级 | 覆盖范围 | 对改进速度的影响 |
|---|---|---|---|
| 不持久化（会话内记忆） | 不适用 | 窄（只防当前会话） | 无 |
| 共享库入库审核 | L2–L3 | 中（防共享传播） | 增加延迟 |
| VASO 形式验证 | L4 | 窄（只覆盖可形式化的） | 大幅增加（需证明） |
| SHARP rubric + 人工审批 | L3 + 人在环 | 宽（覆盖安全关键区） | 中等（只卡安全子集） |
| 完整 diff 审计 + 自动回滚 | L3 | 宽 | 低（事后审计，不阻塞） |

没有一个对策是完备的。安全面的防线是分层的：快速改进走 $\Sigma_{\text{free}}$ 无阻塞，安全关键走 $\Sigma_{\text{safe}}$ 加审批，共享库走形式验证（能证的）+ 代码审计（不能证的）。

### 7.6 Σ 改进 vs θ 改进的安全对比

| 安全维度 | θ 慢循环（[04 章](../04-模型参数改进/04-模型参数改进.md)） | Σ 快循环（本章） |
|---|---|---|
| 攻击面 | 训练数据投毒 | 技能/提示注入 |
| 检测难度 | 高（参数不可读） | 低（文本可审计） |
| 传播速度 | 慢（需重训练） | 快（一次写入即生效） |
| 影响范围 | 全局（所有推理） | 可控（按分量隔离） |
| 回滚成本 | 高（checkpoint） | 低（文本 diff） |
| 最坏情况 | 模型坍塌 | 坏技能跨 Agent 传播 |

$\Sigma$ 改进的安全优势在可审计性和可回滚性。劣势在传播速度：一个坏技能写入共享库后，所有 Agent 下一次检索就会中招，而 $\theta$ 改坏了至少需要重部署才会传播。

Fang et al. 的三律（Endure > Excel > Evolve）在这里的操作化：先确保 $\Sigma_{\text{safe}}$ 不被自改进触碰（Endure），再优化任务性能（Excel），最后才允许自演化（Evolve）。大多数 2026 年的产品停在 Excel，不进入 Evolve。

## Σ 改进的四分量总结

| 分量 | 典型方法 | 验证层级 | 自指程度 | 天花板 |
|---|---|---|---|---|
| $p$（提示） | APE, EvoPrompt, PromptBreeder, ProTeGi, PromptAgent | L3 | 0–1（PromptBreeder 弱自指） | 搜索空间 × 验证集质量 |
| $m$（记忆） | MemGPT, A-Mem, Reflexion, ExpeL, Dynamic Cheatsheet | L1–L3 | 0（记忆策略不自改） | θ 的理解能力 × 记忆组织质量 |
| $\mathcal{T}$（工具） | LATM, CRAFT, Chameleon, ViperGPT | L3 | 0–0.5（创建工具 = 改 T，但不改创建策略） | 工具生态 × θ 的代码能力 |
| $g$（控制逻辑 / 全脚手架） | STOP, Gödel Agent, DGM, ADAS | L3 | 0–2（ADAS 不自指，DGM 递归自指） | θ 的元认知 × 搜索效率 |

共性约束（和 [04 章](../04-模型参数改进/04-模型参数改进.md) §7 三条约束平行）：
1. 改进 $\leq$ $\theta$ 能力上界（脚手架不能超越底座）
2. 不验证 → 退化（坏提示/坏技能/坏工具会传播）
3. 自指层次越高，搜索空间越大，安全风险越大

### 和 01 章标注协议的对应

用 [01 章](../01-定义与形式化/01-定义与形式化.md) §8 的标注模板，四个分量各填一行：

| 维度 | 提示优化 | 记忆演化 | 工具治理 | 全脚手架重写 |
|---|---|---|---|---|
| 更新目标 | $p$ | $m$ | $\mathcal{T}$ | $g$ / 整个 $\Sigma$ |
| 信号来源 | $e$（验证集分数） | $\tau$（任务经验） | $\tau$（执行反馈） | $e$（benchmark 分数） |
| 闭环程度 | 人监督 | 人监督 | 人监督 | 人监督→全闭环 |
| 验证层级 | L3 | L1–L3 | L3 | L3 |
| 光谱位置 | 有界精炼 | 有界精炼 | 有界精炼 | 有界→弱自指 |
| GAI 旋钮 | 外 × 锚定 | 外 × 锚定 | 内 × 锚定 | 内 × 锚定/漂移 |

全脚手架重写是四个分量中唯一在 GAI 旋钮上不完全锚定的：STOP/Gödel Agent/DGM 的改进器在 $\Sigma$ 内，且改进器自身也在被改。这是 $\Sigma$ 层能产生（弱）RSI 的根本原因。

### θ + Σ 联合改进：未来方向

本章和 [04 章](../04-模型参数改进/04-模型参数改进.md) 分别讲了两条通道。实际系统中两者经常联合：

1. 先用 $\Sigma$ 快循环找到好的提示/工具组合
2. 用找到的最优 $\Sigma$ 跑 agent，收集高质量轨迹
3. 轨迹作为训练数据，用 $\theta$ 慢循环写回权重
4. 权重更新后，$\Sigma$ 的最优配置可能也变了，回到步骤 1

这是一个双时间尺度的优化：$\Sigma$ 在内层快速迭代，$\theta$ 在外层慢慢更新。类似 bi-level optimization：

$$
\theta^* = \arg\min_\theta \; \mathcal{L}_{\text{outer}}(\theta, \Sigma^*(\theta)), \quad \Sigma^*(\theta) = \arg\min_\Sigma \; \mathcal{L}_{\text{inner}}(\theta, \Sigma). \tag{21}
$$

目前没有公开系统严格实现这个双层循环。最接近的是 DeepSeek-R1 的管线：先用 RL 改 $\theta$（慢循环），同时调 system prompt 和 CoT 格式（快循环），但两者的优化不是形式化联合的。

### 本章和前三章判断框架的闭合

读完 04、05 两章，对任何一个自改进系统，你应该能回答 [03 章](../03-失效模式/03-失效模式.md) §6 的完整问题表，并追加两个新问题：

| 新增问题 | 来自哪章 |
|---|---|
| 改进走的是 θ 慢循环还是 Σ 快循环，还是两者联合？ | 04 + 05 |
| 如果是 Σ 改进，改的是哪个分量？$p$ / $m$ / $\mathcal{T}$ / $g$ / 整体？ | 05 §1.1 |
| 在 Σ 改进中，自指层次是多少？0 = 不自指，1 = 改进器改自己，2 = 递归自改 | 05 §5.6 |
| 有没有技能的持久化和跨 Agent 传播？如果有，安全面如何处理？ | 05 §7 |

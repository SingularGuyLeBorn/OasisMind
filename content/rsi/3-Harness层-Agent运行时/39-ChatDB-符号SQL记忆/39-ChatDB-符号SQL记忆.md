# 39 ChatDB：库会算，提示冻着

摘要第一句写带记忆的大模型计算万能，末句写在合成数据上显著超过 ChatGPT。打开 Table 2：50 道水果店题，ChatGPT **11/50（22%）**，ChatDB **41/50（82%）**。难问 35 道里 ChatGPT 只对 **1** 道，ChatDB 对 **28** 道。人把 82 听成「符号记忆已经接近满分」，缺的是：这 50 题挂在 **70** 条合成进货记录上，一共大约 **3.3k** token，作者故意压进 ChatGPT 的 **4096** 窗口，让对照方不用记忆、把整段塞进提示。ChatDB 赢的是把加减乘除交给 MySQL，不是窗口不够用。生成 SQL 的提示、少样本示范、温度 0 都冻着。权重不动。

本篇夹在 [MemGPT](../36-MemGPT-操作系统式记忆/36-MemGPT-操作系统式记忆.md)、[HippoRAG](../38-HippoRAG-海马索引检索/38-HippoRAG-海马索引检索.md) 和 [A-Mem](../37-A-Mem-卡片盒记忆/37-A-Mem-卡片盒记忆.md) 旁边。综述把 SQL 记忆和 MemGPT / HippoRAG 并列。MemGPT 换页，评的是 MSC 上的话题级裁判 93.4；HippoRAG 建开放知识图再 PageRank，评的是 1,000 题检索库；A-Mem 连对话卡片，评的是 LoCoMo。这边评的是店长记账：进货、销售、改价、退货，再问营收和平均重量。三套数字禁止横加。**不是** RSI。**不是** 改 \(\theta\)。**不是** 术语式 (2)。一手：Hu, Fu, Du, Luo, Zhao, Zhao，清华 / 智源 / 浙大，[arXiv:2306.03901](https://arxiv.org/abs/2306.03901)（2023-06-06）。花园不当会议接收。代码 [huchenxucs/ChatDB](https://github.com/huchenxucs/ChatDB)，项目页 [chatdatabase.github.io](https://chatdatabase.github.io/)。数字以 HTML Table 2、§3–§4、Algorithm 1、Figure 3–5 为准。禁止用手抄 Figure 5 柱高去改 41/50。禁止和 MemGPT 的 93.4、HippoRAG 的 89.1、A-Mem 的 27.02、ExpeL 的 39.0 横加。

## 1. 问题：窗口会满，向量记忆算不准

作者写多轮对话很快顶到窗口。GPT-4 32k 也装不下一直攒着的上下文。把历史全拼进去，模型会算错、会丢账。当时的神经记忆多半靠向量相似：存的不是结构化账本，操作也不是符号执行，一错就往后传。水果店这种场景要精确插入、删除、改价、汇总，纯文本和矩阵都不合适。ChatDB 要借计算机结构，不借海马：外面挂 SQL 库，模型负责写语句，库负责执行。

文首那句「带记忆的 LLM 计算万能」指的是 Schuurmans 2023 的理论结果 [arXiv:2301.04589](https://arxiv.org/abs/2301.04589)，不是本实验证明了万能。Schuurmans 给的是一类带外存的构造在计算理论上能模拟通用机。ChatDB 只在 50 道合成题上比了 GPT-3.5。不要把引言引用听成「已经 RSI」。

\(S\) 取这次运行里的 MySQL 表：供应商、水果、进货、顾客、销售、明细。单轮 \(S'=I(S)\) 可以发生：多一行库存、删一笔退货。术语式 (2) 还要 \(I'\subseteq S'\)。下一笔记录仍用同一套 chain-of-memory 提示、同一批少样本、同一只 GPT-3.5 Turbo、温度仍是 0。混元台阶上这不是 L0：账本跨问还在。也到不了改改进器。更像 MemGPT / HippoRAG：留下脚手架状态，出状态的程序冻着。作者把「每一步数据库操作都是符号、没有误差」写进正文。花园拆开：MySQL 执行是精确的；模型生成哪条 SQL 仍会错。容易题 13/15，不是 15/15。

和邻居先划线。Toolformer / HuggingGPT 把库当工具调用；BINDER / SQL-PaLM 是 Text-to-SQL。作者强调 ChatDB 把库当成外存模块，用 chain-of-memory 读写历史。评测没有 Spider、没有 BIRD，不要拿 SQL-PaLM 的 Text-to-SQL 榜来垫 82%。Auto-GPT / Generative Agents 是提示式记忆，Table 1 写成半结构、非符号执行、不能完整更新删除。RMT 是可训练记忆 token。MemGPT 有分页函数，没有强制 schema。HippoRAG 的边是 OpenIE 三元组，不是主键外键。A-Mem 的卡片没有 SUM。ReAct 的轨迹随题清空；这边表跨记录留下。

## 2. 机制：先规划 SQL 链，再按结果改下一步，最后摘要

任务定义：用户一句话，加上已有表结构（没有表也可以），去改符号记忆。店长要记账、改、查、删，对应 INSERT / UPDATE / SELECT / DELETE，常常跨表。框架三截。输入处理：要动记忆就让 \(\mathrm{LLM_{getSteps}}\) 写出中间步骤；不用记忆就直接生成回复。chain-of-memory：按步骤走，必要时用 \(\mathrm{LLM_{updateOperation}}\) 根据已执行结果改下一条 SQL，再 `executeOperation`。摘要：\(\mathrm{LLM_{summary}}\) 根据用户话、改过的步骤和 SQL 结果写回复。Algorithm 1 就是这三截。少样本示范和 CoT 写在 §3.3，用来稳住链。人换示范，等于人改 \(I\)。

水果店四类操作对应七张表：`suppliers`、`fruits`、`purchases`、`purchase_items`、`customers`、`sales`、`sale_items`。Figure 3 把手续写死。进货六步：没有供应商就插、没有水果就插、写进货单、写明细、库存加、售价改。销售四步：没有顾客就插、写销售、写明细、库存减。退货五步：先查出 `sale_id`，再查明细，库存加回去，删明细，删销售行。改价一步 UPDATE。占位符只在「上一步才知道主键」的链上出现。Figure 3c：电话 123-456-7890、日期 2023-01-05，库返回 `sale_id=9`，明细是 fruit_id 7 卖 10、fruit_id 6 卖 9。下一步把 9 填进 UPDATE / DELETE。这就是 Algorithm 1 里「要不要根据已有 SQL 结果更新本步」的真身：不是改进器改提示，是同一份提示允许用上一步结果改本步 SQL 字符串。

退货是这条链的样板。Figure 2 / 3c：先按电话和日期查出 `sale_id`，再用这个 id 查出水果和数量，把库存加回去，最后删明细、删销售行。占位符 `<sale_id>` 要等上一步库返回才能填。这就是「根据先前 SQL 结果决定要不要更新本步」。进货要先确保供应商和水果行存在，再写进货单、改库存、改售价。销售要插顾客、插销售、插明细、减库存。改价可以一步 UPDATE。四类操作都是人能写死的手续，不是模型自己发明的 DDL。

schema 可以人手写，也可以让 LLM 生成。正文两种都允许，主实验没有另报「自动建表掉多少分」。表之间用主键外键连。作者把这写成状态跟踪：每处理完一条记录，库就是店里最新状态，还可以滚到某个时间戳。滚回靠的是 SQL 可逆，不是改进器学会了版本管理。提示里没有「下次把 getSteps 改成另一种规划器」。

处理记录和回答问题是两截。记录按时间一条一条走 Algorithm 1，写进七张表。问答时 ChatDB 提示里不再贴 `{records}`，只对库做 SELECT / SUM / GROUP BY。对照 ChatGPT 的 Figure 4 把 70 条包进三重反引号，并写明「默认排除已退货的销售」。即便如此，Figure 5 里 ChatGPT 仍把 Bob Smith 1 月 5 日那笔已退货单算进营收，还把 9×3.8+4×1.3 算成 39.1（金标 39.4）。排除规则写在提示里救不了口算。ChatDB 退货当时已经 DELETE，`SUM(total_price)` 不会再碰到那一行。这是符号状态跟踪，不是提示更会算。相关工作列了 Program of Thoughts：把计算从推理里拆出去交给程序。本主表没有 PoT 对照。换成 Python 计算器也可能抬难问，花园不当已经比过。BINDER 把任务映射成可执行程序再调 LLM；SQL-PaLM 是 Text-to-SQL。作者强调这边把库当外存模块，用 CoM 读写历史。评测没有 Spider。ChatExcel 生成表格命令，也不在 Table 2。

对照 Table 1。ChatDB：结构化存储、符号执行、可解释、能跟踪状态。提示式记忆（Auto-GPT）：插入和选择为主，更新删除不完整，向量检索非符号。矩阵式记忆（RMT）：读写都有，执行不可解释。作者把六列（格式、操作、存储、执行、可解释、状态）写成 ChatDB 全面更好。花园当分类表，不当另一张准确率榜。没有在 Auto-GPT 或 RMT 上跑水果店 50 题。六列本身仍要钉：格式是库、文本加向量、还是记忆 token；操作上 ChatDB 声明插删改查，Auto-GPT 以插入和选择为主、更新删除不完整，RMT 声明读写但不显式；存储一边结构化、两边半结构；执行一边是 SQL 符号，一边是向量相似或网络隐式；可解释随之从高到低；状态跟踪上 ChatDB 每处理完一条记录就把店里最新账写下，并写可以滚到某个时间戳。滚回靠 SQL 可逆。主实验没有报「人工滚回救回几道题」。

## 3. 数字：82% 是 41/50，窗口里已经装得下对照

配置：ChatDB 和对照都是 GPT-3.5 Turbo，温度 0。ChatDB 外挂 MySQL。对照窗口 4096。水果店数据集：进货、销售、改价、退货四类，70 条按时间排，大约 3.3k token。作者保证不会出现负库存。50 道带标准答案的题，15 易 35 难，每题独立作答。易题是从历史里取一条；难题要多跳和精确计算。问答时 ChatDB 不再把记录当提示，只出查询。对照 Figure 4 的模板把店长人设、2023 年 1 月新开、排除退货都写进同一段。题与题独立，所以对照不能把上一题的中间加法带进下一题。ChatDB 能带的是已经写进表的行，不是上一题的思维链。

为什么故意把语料做短？正文写：一旦超过窗口，对照就必须上记忆；向量检索又容易错，对照会先被检索拖垮。作者要让对照尽量强，所以整段记录进提示、不用记忆。ChatDB 一条一条写库，理论上对总条数不敏感。于是论证变成：小数据上已经赢，大数据上对照只可能更差。这是外推，不是另做了一张超长表。花园把「理论上无穷条」钉成未测声明。本表只有 70 条。

Table 2：ChatGPT 易 10/15、难 1/35、合计 11/50，准确率 **22%**。ChatDB 易 13/15、难 28/35、合计 41/50，准确率 **82%**。82 减 22 是 **60** 个百分点，不是「相对提高 60%」那种摘要腔。难问上 28/35 对 1/35，才是拉开的地方。易问 ChatDB 也不是满分。SQL 生成会错，符号执行救不了写错的语句。

Figure 5 三道题当机制说明，不当另一张表。一月总营收：ChatGPT 用数量乘售价，公式有时对、乘法经常错，Bob Smith 1 月 2 日算成 39.1，金标 39.4；还把已退货的交易算进去；最后顶到 token 上限停掉。ChatDB 一条 `SUM(total_price)`，库返回 **707.0**。哪一天营收最高：ChatGPT 把 1 月 2 日算成 49.6（应为 43.2），1 月 5 日算成 32.6（应为 83），同样写不完。ChatDB 先按日 GROUP BY，再 `ORDER BY revenue DESC LIMIT 1`，得到 **2023-01-30 / 119.7**。平均每笔多重：ChatGPT 漏交易、把总重量加成 127（即便按它列出来的数也应是 137，金标 **278**），交易笔数写成 18（应为 **28**），再一次顶窗。ChatDB 三步：总重量 278，笔数 28，再 `278/28=9.93`。作者把这三道写成 CoM 一、二、三步。ChatGPT 的失败模式是算术、漏账、串错、顶窗。不要用手抄中间错加法去改 22%。

「防止误差累积」要拆开。库把中间结果存成行，下一步读行，不再让模型口算长加法。生成错 SQL、选错表、漏 WHERE，误差照样进库。易题 2 道、难题 7 道没对上，就是这条缝。没有 Argus 那种准入：SQL 一执行就写进状态。错库存后面的 SUM 会一起用歪。滚回写在 Table 1 的状态跟踪里，主实验没有报「人工滚回救回几道题」。

## 4. 这不是术语式 (2)，SQL 精确也不等于改进器升级

账本变了，下一问可能直接 `SUM` 到 707.0。改进器没变。\(\mathrm{LLM_{getSteps}}\) / \(\mathrm{LLM_{updateOperation}}\) / \(\mathrm{LLM_{summary}}\) 的提示、少样本链、温度 0、MySQL 引擎、schema 都还在。混元 L0 装不下跨记录保持；L3 要改提议 / 选择程序。本篇停在留下状态、不改程序。摘要里的 symbolic memory 指执行层是 SQL，不是 \(I\) 在改自己。Schuurmans 的万能机是另一篇构造，本实验没有实现那套证明。

和 MemGPT 钉死。93.4 是 MSC 话题级裁判；82% 是 41/50 合成店账。MemGPT 函数换页，没有强制把营收交给 SUM。和 HippoRAG 钉死。89.1 是 2Wiki R@5；这边没有检索库。HippoRAG 的图无预置 schema，ChatDB 的表有主键外键。和 A-Mem 钉死。LoCoMo 多跳 27.02 不是水果店 82%。和 ReAct / CoT 钉死。CoM 把中间步写成 SQL，不是思维树。和 Toolformer 钉死。工具调用可以是搜索；这边工具是带状态的库。和 SQL-PaLM 钉死。Text-to-SQL 榜不是 Fruit Shop。

对有大模型基础的读者，读完应能回答四句。改的是哪一层？Harness 里的 SQL 账本和规划提示。权重动了没有？没有。82% 是不是长上下文记忆的胜利？不是，对照窗口里已经装得下 3.3k token。还缺什么才叫花园 RSI？写 SQL 链的提示进入 \(S'\)，并且下一笔进货用的就是升级后的那份。作者没有局限节。没测超长账本，没测脏 SQL，没测换骨干，没把 Auto-GPT 拉到同一张 50 题上。schema 人手写还是模型写，主表没有拆开。

## 5. 符号执行能算对账，算对的不是改进器

同一句「给模型记忆」，至少分五截。加长窗口是改模型或位置编码。向量检索是墙外取 \(K\) 段。MemGPT 是分页外存。HippoRAG 是语料图。ChatDB 是带 schema 的 SQL 状态。五截不要收成「都在推理时自我进化」。相关工作还点了 NTM、GGS-NN、RMT。本篇主表只有水果店。没有 Spider。没有 LoCoMo。没有 WebArena。

「理论上对条数不敏感」要和 70 条一起读。一条一条写库，时间随条数线性涨，这是工程事实；准确率会不会永远 82%，本实验没有扫。对照顶窗是因为把 70 条加计算过程都写进同一段生成。换成计算器工具、换成 Program-of-Thoughts，也可能抬难问，主表没有这些对照。作者把赢面写成两截：CoM 把题拆开，SQL 把计算卸掉。卸掉的是算术，不是改进手续。

「符号、没有误差」只覆盖执行器。生成器仍是 GPT-3.5。Figure 3 的进货链有六步，销售四步，退货五步，改价一步。步数是人在示范里教出来的。模型按示范仿，仿错就进库。28/35 说明仿得不错，7 道难题和 2 道易题说明仿不完全。这是 L2 脚手架：状态跨问还在，规划提示冻着。

计算万能那条引用尤其要钉死。Schuurmans 证明的是带特定外存接口的 LLM 在理论上可模拟通用计算。ChatDB 引用它当动机，实验是 50 道店账。不要把 82% 听成已经实现通用机，也不要把通用机听成花园式 (2)。式 (2) 要的是改进器进入 \(S'\)。ChatDB 进入 \(S'\) 的是行，不是 getSteps。

代码仓库和项目页不是 Table 2。花园只认 2023 年这篇 70 条 / 50 题。后来别人把 ChatDB 接进产品控制台，不改 41/50。水果名、单价、707.0 只说明 SQL 在这三道题上对，不外推到任意管理场景。

生成提示不会因为某次 SUM 对了就多一条规则进仓库。人要改少样本、换 schema、把 getSteps 交给可训练模块，都是改 \(I\)。这和 DGM 改自己的 Python、STOP 改改进器源码正好相反。作者把 ChatDB 写成用数据库增强 LLM，花园读成 2023 年这篇合成店账的定位，不读成已经闭合的递归，也不读成 Schuurmans 那篇证明的实现。

**读**：Table 2 的 13/15、28/35、41/50 对 10/15、1/35、11/50，82% 对 22% 是 50 题准确率，语料 70 条约 3.3k 故意装进 4096，难问拉开因为 SQL 计算，易问不是满分，执行精确不等于生成精确，不是 93.4，不是式 (2)，不是计算万能的实现。  
**不读**：把 82 听成记忆系统接近满分、把小数据外推成无穷条已测、用 89.1 或 27.02 改 41/50、说 CoM 提示已经在优化自己、说已经 RSI、把 Schuurmans 的定理写成本表。

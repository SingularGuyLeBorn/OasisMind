# Qwen2.5-Coder: 通用底座续训, 70/20/10 配比, 文件级到仓库级 FIM

来源: [Qwen2.5-Coder Technical Report](https://arxiv.org/abs/2409.12186) (arXiv:2409.12186v3, 2024-11-12). 仓库: https://github.com/QwenLM/Qwen2.5-Coder. 对照译稿见同目录 `qwen2-5-coder-bi.md` (page 1 of 32 至 page 32 of 32), 表内数字以源文 `qwen2-5-coder.md` 为准.

Qwen2.5-Coder 是六档代码模型 (0.5B, 1.5B, 3B, 7B, 14B, 32B), 每档都有 Base 和 Instruct. 它的分数能站住, 靠的不是新架构, 而是一串互相配合的决定: 从 Qwen2.5 通用底座继续训练而不是从零开始; 预训练数据按 70% 代码, 20% 文本, 10% 数学混合, 文本里剔掉代码段, 合成代码必须能执行; 训练先在 8192 长度上做文件级 next-token prediction 加 FIM, 再在 32768 长度上做仓库级 FIM, 推理期用 YaRN 推到 128K; 后训练先用千万级多样指令铺覆盖, 再用百万级高质量样本加拒绝采样收尖, 最后用沙箱反馈和 LLM 裁判造偏好对做离线 DPO. 结果是 Base 7B 在五项生成基准上压过 DS-Coder-33B, Instruct 32B 的 HumanEval 92.7, 贴近 GPT-4o 一带.

## 1. 起点与规格

### 1.1. 为什么从 Qwen2.5 续训, 而不是从零训代码模型

2024 年下半年的开源代码模型分两条路. 一条是 StarCoder 和早期 DeepSeek-Coder, 从零开始在高比例源码上训练; 另一条是 Code Llama 和 CodeQwen1.5, 从通用底座出发继续训练. 前者的代码密度高, 但数学和通用语言能力弱, Table 12 里 DS-Coder-33B-Base 的 MATH 只有 14.4, MMLU 只有 39.4. 后者保住了自然语言接口, 代价是要仔细控制代码与非代码的比例, 否则通用能力会被冲掉.

**Qwen2.5-Coder 明确走第二条路**, 直接前身是 CodeQwen1.5. 这个选择和后面几乎每个决定都有关: 因为要保住数学和通用能力, 所以做了三组配比实验; 因为底座已经有 Qwen2.5 的词表, 所以只加特殊 token 不换分词器; 因为底座已经在 32K 上训过长文本, 仓库级阶段只需 300B token 就能把长上下文迁移到代码上. 代码助手的真实场景里, 用户用自然语言描述需求, 模型要读懂需求再写代码, 数学和通用能力不是附加项.

从 CodeQwen1.5 到 Qwen2.5-Coder, 变化不只是参数变大, 还是把单个模型改成一个家族. 同一套数据, 同一套阶段划分, 同一组特殊 token, 六档共享. 这对使用者的实际意义是: 可以先在 7B 上验证补全协议和提示词, 再原样迁到 32B, 不必换模型时重学一套 FIM 标记或仓库格式. 报告把特殊 token, 评测脚本一并公开, 也是在降低这种迁移成本.

### 1.2. 六档与特殊 token: 架构不动, 只加结构标记

Table 1 显示六档的 head size 都是 128, 词表 151,646, 训练 token 都标 5.5T. 差异在隐宽, 层数, 头数和 FFN 宽度. 7B 隐宽 3584, 28 个 query 头, 4 个 KV 头; 14B 和 32B 隐宽同为 5120, 差别在层数 (48 对 64) 和 FFN 中间宽 (13824 对 27648), KV 头提到 8. 小档做 **embedding tying**, 大档不做. 表里有两处例外要记住: 1.5B 的 FFN 中间宽 8960 比 3B 的 4864 还宽, 3B 反而更深 (36 层), 不能用 「随规模单调」 硬套.

Table 2 列出新增的特殊 token, ID 从 151643 到 151664. `<|fim_prefix|>`, `<|fim_suffix|>`, `<|fim_middle|>` 用于 FIM, `<|fim_pad|>` 用于填充, `<|repo_name|>` 标仓库名, `<|file_sep|>` 分隔文件. 这些 token 在既有词表上追加, 不是新训的分词器. 它们的作用是把代码的结构信息显式告诉模型: 哪里是光标前, 哪里是光标后, 哪里换了一个文件. 用自然语言描述这些边界, 模型很容易和代码正文混淆.

六档共用同一训练量标注 5.5T, 说明报告口径里小模型并不因为参数少就少看数据, 档位差距靠容量区分. 这和常见的 「小模型少训一点省成本」 不同. 部署上, 0.5B 和 1.5B 面向端侧和低成本补全, 3B 和 7B 是报告里 「以小打大」 的主要对照位, 14B 和 32B 才和 Codestral-22B, DS-Coder-33B 乃至闭源 API 正面比.

## 2. 预训练: 数据, 配比与两级 FIM

### 2.1. 五类数据: 源码, 文档, 合成, 数学, 通用文本

预训练数据分五类. 源码来自 2024 年 2 月之前的 GitHub 公开仓库, 覆盖 92 种语言, 另收 Pull Request, Commit, Jupyter Notebook 和 Kaggle 数据集, 规则过滤对齐 StarCoder2 与 DS-Coder. PR 和 Commit 把 「代码为什么改」 带进预训练, Jupyter 和 Kaggle 偏向数据分析场景, 这些在后面 Text-to-SQL 和 TableBench 的评测里会再出现.

**Text-Code Grounding** 是代码相关的文档, 教程, 博客, 来自 Common Crawl. 它不走传统的 URL 多级召回, 而用粗到细的层级过滤, 每一级用 fastText 这类小模型打分. 越往后的级别留下的数据质量越高, 混料时就可以按质量分层抽样, 而不是只有 「要或不要」 两档. Figure 1 显示四级过滤后, 1.5B 上 HumanEval 与 MBPP 的均分从 41.6 升到 46.8 (绝对分, 不是相对提升). 同一张图的柱子给了每级剩下的量: 582B, 370B, 147B, 118B token (读图). 这组实验变的只有 「用第几级过滤后的 Text-Code 数据」 一个量, 数据越往后越少, 最后一级只剩第一级的约五分之一, 均分却在第四级才明显跳起来 (前三级读图约 41 到 42.5). 报告说每一级各管一个维度, 但没写四级分别管什么. 报告还说试过更大的过滤模型, 没有明显收益, 解释是过滤要的是表层质量信号, 大模型反而会卷进多余的语义判断.

合成数据用 CodeQwen1.5 生成, 加执行器检验, **只留能跑通的代码**. 这一步直接回应 「合成代码会幻觉」 的批评: 不靠模型自觉, 靠能不能执行. 数学数据来自 Qwen2.5-Math 的语料, 报告称不伤代码能力. 通用文本来自 Qwen2.5 的预训练语料, 但会去掉其中的代码段, 避免和源码桶重叠. 这个细节是配比实验成立的前提: 如果文本桶里还藏着代码, 「20% 文本」 就失去了操作意义.

### 2.2. 70/20/10: 配比实验怎么读

Table 3 在 7B 上比了三组配比. 纯代码 100:0:0 的代码列并不差, Coding Common 49.8, BigCodeBench 40.3, 但 MATH 10.3, GSM8K 23.8, 平均只有 31.3. 中间一组平均 48.9. 70:20:10 平均 55.0, 代码列 48.3 和 38.3 与纯代码接近, MATH 33.2, GSM8K 64.5, MMLU 62.9, 综合最高, 被采纳. 中间组的比例正文写 85:10:5, 表格印的是 85/15/5 (合计超过 100), 两处不一致, 引用时要注明.

纯代码组输在综合分, 不是代码本身. 作者的解释是: 数学和文本对代码有正向作用, 但要到一定浓度才显现. 报告没有做更细的扫描, 也没有解释机制, 把原因留给后续研究. 社区讨论这张表时常把它读成 「代码模型要加文本」, 更准确的读法是: 在这三组里, **7:2:1 在代码几乎不掉的前提下把数学和通用能力拉起来了**. 最终配比后的训练集是 5.2T token, Table 1 的 5.5T 可能包含仓库级阶段或重复计数, 两个数不要合成一个.

为什么会有浓度门槛, 可以做一点推测 (以下不是报告结论). 代码任务的输入常常是自然语言描述, 文本数据帮助模型理解需求; 算法题需要推理和计算, 数学数据帮助模型组织步骤. 比例太低时, 这些能力学不起来, 反而占用了代码的 token 预算; 比例到一定程度, 它们开始对代码题有正向迁移. 这个推测和 Table 3 的形状一致: 中间组的代码列比纯代码组掉得多, 7:2:1 组的代码列反而回升. 真实机制需要更细的配比扫描才能确认.

### 2.3. 文件级 FIM: 补全能力从哪里来

文件级阶段的序列长 8192, 数据约 5.2T, 训练目标是 next-token prediction 加 **FIM** (Bavarian et al., 2022). FIM 的思路是把一段代码切成前缀, 中间, 后缀三块, 重新排成 「前缀, 后缀, 中间」 的顺序让模型学着生成中间. Figure 3 给出的格式是 `<|fim_prefix|>{code_pre}<|fim_suffix|>{code_suf}<|fim_middle|>{code_mid}<|endoftext|>`, 属于社区常说的 **PSM** 顺序. 这样训练出的模型能在 IDE 里根据光标前后的代码补全中间部分, 而普通 next-token prediction 只能往后续写.

FIM 和 next-token prediction 同时训练, 报告没有给出 FIM 的比例. Bavarian 等人的原论文发现 FIM 比例在一定范围内几乎不伤从左到右的生成能力, 这是 「FIM for free」 的说法来源. Qwen2.5-Coder 的评测也印证了这一点: HumanEval-FIM (Table 7) 上 7B 平均 86.2, 追平 DS-Coder-33B-Base, 同时 HumanEval 生成分也最高. FIM 能力主要服务补全产品, 对话场景用不到, 所以后训练阶段要专门防止它被短指令冲掉, 见第 3.3 节.

PSM 顺序的道理在于: 模型生成中间部分时, 前缀和后缀都已经在上下文里, 可以同时参考光标前后的代码; 生成完中间后遇到结束符停止. 社区另有 SPM 顺序 (后缀放最前), 在 KV cache 复用上有些优势, 但 Qwen2.5-Coder 只给了 PSM 一种格式. 推理框架和 IDE 插件接入时必须严格按 Figure 3 拼接, 标记顺序错了, 补全质量会明显下降. 这也是特殊 token 必须公开的原因.

Figure 2 把整个训练画成三段: 文件级预训练, 仓库级预训练, 指令微调. 三段的窗口依次是 8192, 32768, 以及后训练的指令长度; 数据量依次是约 5.2T, 约 300B, 以及千万级加百万级指令. 报告对前两段只给了窗口, token 量和训练目标, 学习率, batch size, 优化器, 训练步数都没有写, 这一面本页没有. 所以想复现这条流程的读者, 能拿到的是配比和阶段划分, 拿不到具体超参.

### 2.4. 仓库级: 32K, RoPE base, repo-level FIM, YaRN 128K

仓库级阶段把窗口从 8192 拉到 32768, **RoPE base** 从 10000 调到 1000000, 数据约 300B token 的高质量长代码. 改 base 是为了让位置频率覆盖新的长度区间, 如果只改窗口不改频率, 长序列上的相对位置会落在训练没见过的相位上. 32K 之后再用 **YaRN** 外推到 131072. 训练到 32K 与外推到 128K 要分开说: 前者是权重见过的, 后者是推理期能测到的.

FIM 也从文件级扩到仓库级, 做法跟 StarCoder2 (Lozhkov et al., 2024) 一致. Figure 4 给出的完整序列是

```text
<|repo_name|>{repo_name}
<|file_sep|>{file_path1}
{file_content1}
<|file_sep|>{file_path2}
{file_content2}
<|file_sep|>{file_path3}
<|fim_prefix|>{code_pre}<|fim_suffix|>{code_suf}<|fim_middle|>{code_fim}<|endoftext|>
```

前面的文件带路径原样拼接, 只当上下文; 最后一个文件写完路径后不直接给正文, 而是按文件级的 PSM 格式拆成前缀, 后缀和要生成的中间段. 所以仓库级 FIM 相对文件级只多了两样东西: 仓库名和带路径的邻居文件, 挖洞与生成的规则完全沿用 Figure 3. 这样模型补全时能看到同一仓库里其他文件的定义, 比如另一个文件里声明的类和函数签名. 300B 相对 5.2T 只是很小一段, 但它决定了模型能不能把跨文件的符号关系装进同一窗口.

长上下文的验证是 Figure 6 的 **Needle in the Code**: 在 Megatron 仓库的不同位置插入简单的自定义函数, 看模型能不能在仓库末尾复现. 它是长程检索式的冒烟测试, 过了只说明 「针还在」, 不能代替 CrossCodeEval 和 RepoEval 那种跨文件补全. 反过来, 连针都找不到的话, 仓库级 agent 的叙事就站不住. 本页没有 128K 下真实跨文件任务的分数. 读者若做仓库级 agent, 应把 Needle in the Code 当作必要条件而非充分条件, 真正的跨模块修改能力还要看 Aider 这类编辑基准, 或者自己在目标仓库上实测.

## 3. 后训练: 指令数据, 沙箱与 DPO

### 3.1. 指令数据: 语言识别, 片段合成, 多语言 agent

后训练数据不是一次抓取. 第一步用微调过的 **CodeBERT** 做近百种编程语言的识别, 丢掉过多不含代码的样本, 以免伤 MultiPL-E, McEval, MdEval 这类多语言评测. 第二步从 GitHub 抽取不超过 1024 token 的代码片段, 让模型据此合成 「指令加回复」, 再用 LLM 打分过滤, 并混入 McEval-Instruct 等开源种子数据.

多语言部分用**多 agent 协作**: 每种编程语言一个专门 agent, 配讨论协议, 记忆库, 跨语言蒸馏, 协同度量, 按缺口自适应生成. 目标是让低资源语言 (如 Bash, Racket) 也有足够的指令数据. 这一段写得很框架化, 没有像预训练配比那样的消融表, 读的时候应当作配方描述, 不能当作逐项验证过的结论. Table 6 里 Bash 仍是普遍短板, 32B Base 也只有 39.9, 说明多语言均衡还有缺口.

语言识别这一步看似琐碎, 却直接影响评测形状. 指令数据如果大量是纯自然语言问答, 模型会倾向于用文字解释而不给代码, 多语言代码评测就会掉分; 如果语言标签错了, 某些小语种会被误分到主流语言里, 数据分布看上去均衡, 实际并不均衡. 用专门微调的 CodeBERT 做识别, 比用规则或通用模型更准. 这和预训练阶段 「文本桶去代码段」 是同一种洁癖: 桶里装的是什么, 必须先搞清楚.

识别之后还有两步取舍. 主流语言的指令全部保留, 长尾语言的指令随机丢掉一部分, 这和后面多 agent 专门给低资源语言补数据看似矛盾, 实际是先去掉质量不稳的原始长尾样本, 再用可控的方式补回来. GitHub 片段合成分两段: 先让一个 LLM 根据片段写指令, 再让代码 LLM 写回复, 最后由 LLM 打分器过滤. 多 agent 框架里每个 agent 有自己的记忆库, 记下已经生成过的样本, 避免反复生成相似题; 各 agent 的初始数据来自现有的少量多语指令语料. 报告提到的 「协同度量」 只有名字, 没有公式, 这一面本页没有.

### 3.2. 九维打分和多语言沙箱

质量评估用**九个维度加权打分**: 问答一致性, 相关性, 难度, 是否含代码, 代码正确性, 代码风格, 清晰度, 注释, 易学性. 最后一项 「Easy to Learn」 说明数据目标不只有竞赛 Pass@1, 还有教学向的可读性, 这和单纯刷榜的合成数据口味不同.

正确性交给**多语言沙箱**. 沙箱有五块: 语言支持, 样例库, 单测生成, 执行引擎, 结果分析. 流程是先做 AST 静态检查, 再对自包含的代码片段生成单测并执行. 这说明团队把 「代码能不能跑」 嵌进了数据生产, 不只放在最终评测里. 和预训练阶段 「合成代码必须能执行」 是同一种思路: 不信任模型的自我判断, 用解释器当过滤器. 沙箱覆盖哪些语言, 单测的拒绝率是多少, 报告没有给, 这一面本页没有.

单测由模型生成, 本身也可能有错: 测例写得太松, 错误代码也能通过; 写得太严或写错, 正确代码会被误杀. 报告提到对自包含片段做单测, 意味着依赖外部库或环境的工程代码很难进入这条流水, 这部分只能交给九维打分和后面的 LLM 裁判. 所以沙箱保证的是 「能独立运行的代码大体正确」, 不是所有指令数据都经过执行验证.

两道检查的覆盖面不同. AST 静态检查作用于所有抽出来的代码片段, 解析出错的节点所在片段直接丢掉, 这一步对 Python, Java, C++ 等主流语言都做; 单测执行只对算法题这类自包含片段做. 执行引擎在隔离环境里运行代码, 支持多个测例并行, 并设有资源分配和超时机制, 防止死循环拖垮流水. 九维打分的最终分是加权和 $s = w_1 s_1 + \cdots + w_n s_n$, 权重是预先设定的, 报告没有公布具体数值, 所以无法判断 「难度」 和 「易学性」 这类互相拉扯的维度谁更重.

### 3.3. coarse-to-fine SFT, FIM 指令防遗忘, 离线 DPO

SFT 分两步. 先用数千万条低质量但多样的指令拓宽覆盖, 再用数百万条高质量指令加**拒绝采样**收尖: 同一个 query 采多条回复, 用 LLM 打分选最好的进 SFT. 报告没有给出 「只用第二步」 的对照, 所以 「先粗后细更好」 是设计陈述, 不是消融结论. 拒绝采样的温度, 候选数, 打分模型也没有列出.

指令数据普遍偏短, 如果只用短指令训练, 预训练学到的长上下文和 FIM 能力会退化. 对策是混入少量 **AST 引导的 FIM 指令**: 用 tree-sitter 解析代码, 抽出一个逻辑块 (函数体, 循环体等) 当中间部分, 用同一文件的上下文还原. 这样的洞比随机切出来的更符合真实补全场景, 也让模型在对话训练里继续练 FIM. 比例没有给出. 挖洞时会在 AST 的多个层级上随机选节点, 可能是一个表达式, 一条语句, 也可能是整个函数; 训练集的主体仍是标准 SFT 数据, FIM 指令只占小部分. 这相当于在对话数据里保留一点预训练的任务形式, 用很小的代价防止补全能力被短对话冲掉.

SFT 之后是**离线 DPO**. 偏好对有两种来源: 可执行的题用沙箱反馈判对错, 对的作正例, 错的作负例; 复杂工程题无法用单测判定, 就用 LLM-as-a-judge. 两种数据再和通用偏好数据合并. 这里没有 PPO 的 critic, 也没有 GRPO 的组内基线, 是标准的离线 DPO (Rafailov et al., 2023). 执行反馈和 LLM 裁判并列, 等于承认算法题可以自动判, 工程题仍要靠更强的模型代替人类判断.

## 4. 去污染与评测

### 4.1. 去污染

预训练和后训练都做去污染, 关键测试集 HumanEval, MBPP, GSM8K, MATH 按 10-gram 词级重叠剔除. 这和 DeepSeek-Coder 等报告的口径同族, 都是 n-gram 重叠删除, 不是用模型探测. 正文写的是 「key datasets such as」, 能确认的只有这四套, 其余基准是否同样处理没有写明.

评测侧另有一层防护. Instruct 评测用 LiveCodeBench 的近期题目 (§7.1 用 2024-07 到 2024-09, Discussion 扩到 2024-11), 这些题在训练数据截止之后才出现, 用**时间切割**降低污染风险. SAFIM 也刻意用 2022 年 4 月之后的文件, 共 17720 例. 两处时间窗不同, 引用 LiveCodeBench 分数时要写清区间.

10-gram 比 Qwen2 通用报告的 13-gram 更严, 对代码来说也更容易误伤: 常见的函数签名, import 语句, 循环模板都可能撞上 10-gram. 报告没有给出剔除比例和误伤情况, 也没有像 Qwen2 那样对比 「原集与非污染子集」 的分数. 所以 HumanEval 类老基准的分数仍然要打个折扣看, LiveCodeBench, BigCodeBench Hard, SAFIM 这些时间切割或分布外的基准, 更能说明真实能力.

### 4.2. Base 表: 7B 压过 33B 的那几格

Table 5 是生成基准的主表. Qwen2.5-Coder-7B Base 的 HumanEval 61.6, HumanEval+ 53.0, MBPP 76.9, MBPP+ 62.9, MBPP 3-shot 68.8, 五项全面高于 DS-Coder-33B-Base 的 54.9 / 47.6 / 74.2 / 60.7 / 66.0. 32B 再提到 HumanEval 65.9, MBPP 83.0. BigCodeBench-Complete 上 32B Full 53.6, Hard 26.4, 高于 DS-Coder-33B 的 Hard 20.3. BigCodeBench 偏向工具使用和复杂指令, 被作者当作更接近分布外的检验, Hard 子集比 HumanEval 更能说明 「不是背题」.

小档和多语言也有看点. 0.5B 的 HumanEval 只有 28.0, 但给出了最小可部署的锚点; 1.5B 的 43.9 明显超过同档 DS-Coder-1.3B 的 34.8. MultiPL-E (Table 6) 八种语言均分 32B 达 63.9, 多种语言超过 60. MBPP 3-shot 被单独强调, 是因为作者认为它在训练早期更稳定, 适合监控收敛, Discussion 里也用它画 Base 的规模曲线.

数学和通用能力是续训路线的证据. Table 12 里 7B 的 MATH 46.6, GSM8K 83.9; 32B 为 57.2 和 91.1; DS-Coder-33B-Base 只有 14.4 和 35.4. Table 13 到 14 里 7B 的 MMLU 68.0, 32B 79.1. 这些差距来自底座和 70/20/10 配比, **不是代码模型偶然会做数学**. 正文说数学评测有五个基准, Table 12 只有四列 (MATH, GSM8K, MMLU STEM, TheoremQA), 以表为准. CRUXEval (Table 11) 上 7B 的 Input-CoT 56.5, Output-CoT 56.0, 作者归功于清洗时盯住可执行性.

CRUXEval 由 800 个 Python 函数和对应的输入输出样例组成, 两项任务都要求模型用 CoT 一步步模拟执行. 报告正文把 CRUXEval-I 写成 「给输入猜输出」, CRUXEval-O 写成 「给输出猜输入」, 和 CRUXEval 原论文的定义正好相反 (原论文里 I 是预测输入, O 是预测输出). 读分数时以原论文的定义为准, 两列的难度不同, 不要把正文的描述搬进自己的笔记. 通用能力一侧, Table 13 到 14 用 MMLU, MMLU-Redux, ARC-Challenge, TruthfulQA, WinoGrande, HellaSwag 六套, 作者把这组结果当作 70/20/10 配比保住通用能力的证据, 对照对象是其他代码模型, 不是 Qwen2.5 通用底座本身, 所以看不出续训究竟掉了多少通用分.

### 4.3. 补全与仓库级基准

补全能力看 Table 7 到 Table 10. HumanEval-FIM 上 7B 平均 86.2, 32B 88.3, 1.5B 83.5. CrossCodeEval (Table 8) 的设定是序列 8192, 输出 50 token, 跨文件上下文 2048, 用 BM25 检索相关文件; 32B 平均 EM 57.1, ES 86.8, DS-Coder-33B 的 EM 为 48.8. 正文有一处 「提升 3.7%」 没有写清对照行, 以表为准.

CrossCodeLongEval (Table 9) 的函数级补全 EM 普遍偏低, 作者归因于多行精确匹配本身就难. RepoEval (Table 10) 上相对 DS-Coder-33B-Base 平均 EM 高 7.9, ES 高 4.2. 这几张表才是仓库级 FIM 和 300B 长代码训练的直接证据, 比 Needle in the Code 更接近真实补全. 补全产品应优先看这几张表, 7B 在这里往往已经够用.

两张表的细节. CrossCodeLongEval 分块补全和函数补全两项: 32B 分块 EM 57.3, 函数 EM 只有 16.4; 上一代 CodeQwen1.5-7B 的函数 EM 只有 6.4, Qwen2.5-Coder-7B 提到 14.4, 函数级补全翻倍多, 正是仓库级数据要解决的问题. RepoEval 分行级, 函数级, API 级三项: 32B 的行级 EM 76.1, API 级 EM 65.1, 函数级 EM 只有 13.6. 14B 的函数级 EM 14.1 和平均 ES 79.0 反而略高于 32B 的 13.6 和 78.5, 仓库级补全在 14B 之后基本饱和. Codestral-22B 在 RepoEval 上平均 ES 只有 46.6, 明显异常, 可能是提示格式不匹配 (推测, 报告没有解释).

SAFIM 取自 8,590 个 2022 年 4 月之后创建的代码文件, 共 17,720 例, 按 AST 挖三类洞: 算法块, 控制流表达式, API 调用. 前两类用 pass@1, API 调用用 EM. 用创建时间切割是为了避开主流预训练语料, 和 LiveCodeBench 的思路一样. 按语法结构挖洞比随机挖洞更接近 IDE 里的真实补全, 和后训练里 tree-sitter 引导的 FIM 指令是同一个出发点.

各基准测的东西不同, 同一模型在不同协议下的名次可能换位. HumanEval-FIM 测单文件挖洞, CrossCodeEval 测检索跨文件上下文后的单行补全, CrossCodeLongEval 测更长的函数级补全, RepoEval 测仓库内的行级和 API 级补全, SAFIM 按语法结构 (代码块, 控制流, API 调用) 挖洞. 报告用十几张表而不是一个总分, 就是因为**这些协议互相不能替代**. 使用者选权重前应先选自己的协议.

### 4.4. Instruct 表: 生成, 推理, 编辑, SQL

Table 16 是 Instruct 主表. 32B-Instruct: HumanEval 92.7, HumanEval+ 87.2, MBPP 90.2, MBPP+ 75.1, BigCodeBench Full/Hard 49.6 / 27.0, LiveCodeBench 31.4. 同表 GPT-4o-2024-08-06 的 LiveCodeBench 34.6, Claude-3.5-Sonnet-20241022 31.6, o1-mini 60.0. EvalPlus 的 HE+ 把测例放大几十倍, 32B 的 HE+ 与 HE 仍接近, 说明不是只过了宽松测试. o1-mini 的 60.0 提醒读者: 代码模型的对手已经分成普通对话模型和强推理模型两路. 正文写 7B 的 LiveCodeBench 是 37.6%, 表上是 18.2, 以表为准.

多语言和推理: MultiPL-E Instruct (Table 17) 7B 均分 76.5, 32B 79.4, 接近 Claude-3.5-Sonnet-20240620 的 80.2. McEval 覆盖 40 种语言, 16000 个测例; MdEval 约 1.2K 个带 bug 样本; CodeArena 近 400 条人工样本, 用 GPT-4o 做两两比较. CodeArena 的裁判是 GPT-4o, 报告没有人工评审作对照, 模型评模型可能偏向同类风格. CRUXEval Instruct (Table 18) 32B 达 75.2 / 83.4, 7B 为 65.8 / 65.9.

编辑和数据任务更接近真实助手场景. Aider (Table 19) 要求把自然语言请求变成能过单测的代码编辑, 格式还要能被编辑器接收: 32B Pass@1/2 60.9 / 73.7, 7B 55.6 / 68.4; 正文写 7B 为 51.9%, 那其实是 DS-Coder-V2-Instruct 的数, 疑似串行. CodeEditorBench (Figure 11) 上 32B 的 win rate 可比总参 236B 的 DS-Coder-V2-Instruct (86.2%). TableBench 上 32B 得 45.1. Table 20 里 32B-Instruct 的 MATH 76.4, AIME24 20.0, IFEval 79.9, MMLU 77.6, 代码续训没有把数学和通用能力抽干. 要注意 Instruct 的 BigCodeBench 是 instruct 任务, Base 的是 complete 任务, 不能横着减出 「对齐增益」.

Aider 的题目是 Exercism 上的 133 道 Python 练习, 全部实验都用 whole 编辑格式, 即模型返回整个文件. 闭源对照里 Claude-3.5-Sonnet-20241022 的 Pass@1/2 是 71.4 / 86.5, o1-preview 是 69.9 / 88.0, 32B-Instruct 的 60.9 仍差一截; 但 o1-mini 只有 49.6, 强推理模型在编辑格式任务上并不占优. 开源这边, CodeLlama 的 7B, 13B, 34B 都只有 1.5, 基本不会按格式输出编辑. CRUXEval 上闭源差距更明显: 32B-Instruct 的 75.2 / 83.4 对 GPT-4o 的 78.6 / 89.2, o1-mini 的 91.6 / 96.2. 14B 的 Output-CoT 79.5 已经接近 32B, 规模收益在推理题上开始递减.

Text-to-SQL 用 Spider 和 BIRD 两套, 为了公平, 所有模型都用 Chang 和 Fosler-Lussier (2023) 的统一提示模板: 先给带数据库说明的表结构, 再给表内容样例, 可选的额外知识, 最后是自然语言问题. 读图可得 32B-Instruct 的 BIRD 58.4, Spider 85.1; 14B 为 56.9 / 84.8; 7B 为 51.1 / 82.0; DS-Coder-33B-Instruct 为 45.6 / 73.8 (读图). 报告把增益归到预训练和微调里专门合成的 SQL 数据, 但没有给这部分数据的量. TableBench 覆盖四大类表格问答的 18 个领域, 用文本 CoT (TCoT) 设定评测.

Table 20 的其余列: 32B-Instruct 的 GaoKao2023en 68.3, OlympiadBench 42.5, CollegeMath 47.7, AMC23 55.0, 都高于总参 236B 的 DS-Coder-V2-Instruct; 但 MMLU-Pro 62.3 对 65.6, CEval 68.9 对 73.4, GPQA 41.8 对 44.3, 知识密集的几项还是更大的模型赢. 14B 的 GSM8K 94.2 比 32B 的 93.0 还高, 小学数学已经饱和. IFEval 上 32B 79.9 远高于 DS-Coder-V2 的 40.9, 这是差距最大的一列.

Instruct 表的整体形状和预训练, 后训练的分工是对得上的. HumanEval 从 Base 7B 的 61.6 升到 Instruct 7B 的 88.4, 大头来自沙箱过滤的高质量 SFT 和执行反馈 DPO; MultiPL-E 的提升对应多语言 agent 生成的指令; Aider 和 CodeEditorBench 的表现对应 PR, Commit 数据带来的 「修改代码」 经验. LiveCodeBench 上与 o1-mini 的巨大差距, 则说明没有长 CoT 推理训练的代码模型, 在竞赛新题上有明显天花板.

## 5. 规模曲线与边界

Figure 14 用 MBPP 3-shot (Base) 和 2024-07 到 2024-11 的 LiveCodeBench (Instruct) 画规模曲线, 结论是分数随规模正相关, 各档都是同档最好, 标题写成 「Scaling is All You Need」. **这不是严格的 Scaling Laws**: 没有拟合指数, 没有 loss 与算力的曲线, 只是规模和基准分的对照点. 报告停在 32B, 更大的档位只在结论里作为展望.

和 DeepSeek-Coder 系列对照, 两边都做仓库级数据和 FIM, 差别主要在出发点. DeepSeek-Coder 早期从零训, 源码比例高; Qwen2.5-Coder 从 Qwen2.5 续训, 守住数学和通用混料. 后来的 DeepSeek-Coder-V2 也改为从通用底座 (DeepSeek-V2) 续训, 两条路线在这一点上趋同. 具体分数应看各自的表, 不同报告的评测设定不完全一样, 不宜跨报告直接相减.

边界要记清. 训练 GPU 小时几乎没谈; 128K 依赖外推和针测; 正文与表有几处数字冲突 (配比中间组, LiveCodeBench 7B, Aider 7B), 引用必须回表; 多 agent 指令配方缺少可复现的超参; 合成数据依赖前代模型和执行器, 执行器覆盖范围和拒绝率没有给出; 引言提到的代码助手和 Artifacts 场景没有系统评测. 选型上, 补全产品看 FIM 与 CrossCodeEval, RepoEval, 7B 往往够用; 竞赛与多语言生成看 Table 16 到 18, 32B-Instruct 是开源主打; 数据分析看 Text-to-SQL 与 TableBench. 这份报告之后, 代码能力的主线转到带 thinking 的通用模型和 agent 编码, 那是 Qwen3 及之后的故事.

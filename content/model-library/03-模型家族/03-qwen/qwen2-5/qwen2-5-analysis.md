# Qwen2.5: 18T 数据, 百万级 SFT, 离线 DPO 接在线 GRPO

来源: [Qwen2.5 Technical Report](https://arxiv.org/abs/2412.15115) (arXiv:2412.15115v2, 2025-01-03). 仓库: https://github.com/QwenLM/Qwen2.5. 对照译稿见同目录 `qwen2-5-bi.md` (page 1 of 26 至 page 26 of 26), 表内数字以源文 `qwen2-5.md` 为准.

Qwen2.5 的骨架和 Qwen2 几乎一样, 分数却整体上了一个台阶. 旗舰 Qwen2.5-72B-Instruct 的 MATH 83.1, LiveCodeBench 55.5, Arena-Hard 81.2, 在多项上追平或超过参数量约为它五到六倍的 Llama-3.1-405B-Instruct. 增益来自几个互相配合的面: 预训练数据从 7T 扩到 18T, 过滤器换成上一代 Instruct, 数学和代码直接并入 Qwen2.5-Math 与 Qwen2.5-Coder 的语料; Scaling Laws 用来定超参并给 MoE API 配置对标; Dense 梯子补齐到七档, 云端另开 Turbo 与 Plus 两档 MoE; 长上下文在 Turbo 上走四段渐进到 262,144, 推理期再外推到 1M; 后训练用超过 100 万条 SFT, 再接约 150,000 对的离线 DPO 和基于奖励模型的在线 GRPO. 下面按这些面怎样互相牵制来讲.

## 1. 底盘与型号

### 1.1. 从 Qwen2 到 Qwen2.5: 增量压在数据与后训练

Figure 1 把 Qwen 系列画成一条数据放大的曲线, Qwen2.5 是这条曲线上的一步. 报告自己总结了三句 「Better」: Better in Size 是档位补齐和 MoE 服务; Better in Data 是 7T 到 18T 与百万级后训练数据; Better in Use 是生成长度从约 2K 提到 8K, 表格和 JSON 等结构化输入输出更好, 工具调用更顺, Turbo 上下文到 1M. 三句话落在不同层次, 后面分别对应数据, 型号, 后训练和长上下文几节.

这一代没有新的注意力算子, 没有 MLA, 没有 MTP 头, 骨架沿用 Qwen2 的 GQA, SwiGLU, RoPE, QKV bias, Pre-Norm RMSNorm. 同期 DeepSeek-V3 在算子和训练基础设施上大动, Qwen2.5 则把力气放在数据流水和对齐流水上. 两条路线没有高下, 但读 Qwen2.5 的分数时要知道: 能解释分数变化的是数据和后训练, 不是架构. 引言里提到 o1 一类 TestingTime 路线作为背景, 本报告的交付仍是可下载的 Dense 权重和可调用的 MoE API, 推理模型 QwQ 是另一条线.

### 1.2. 型号矩阵: 七档 Dense 与两档 MoE API

开源侧七档: 0.5B, 1.5B, 3B, 7B, 14B, 32B, 72B. 相对 Qwen2 补回 3B, 14B, 32B, 专门填中间档的空白; 32B 这一档后来成了社区单卡量化部署的热门选择. 托管侧另有 Qwen2.5-Turbo 和 Qwen2.5-Plus 两档 MoE, 只通过 API 提供. Hugging Face, ModelScope, Kaggle 上可以拿到超过 100 个模型, 含量化版本. 通用模型同时是 Qwen2.5-Math, Qwen2.5-Coder, QwQ 和多模态型号的底座.

Table 1 列出 Dense 规格. 层数从 0.5B 的 24 到 72B 的 80; 全程 GQA, 7B 为 28/4, 72B 为 64/8. Tie embedding 只在 0.5B, 1.5B, 3B 打开. 上下文与生成长度分档: 小三档 32K/8K, 7B 及以上 128K/8K. 许可证不统一: 3B 和 72B 走 Qwen Research 或 Qwen 许可, 其余多档 Apache 2.0. 选型时分数, 窗口, 许可三样要一起看, 只看分数可能选到许可或窗口不合用的档.

MoE 放在 API 侧而不是开源, 是这一代的一个产品决定. Qwen2 开源过 57B-A14B, Qwen2.5 把 MoE 收回云端, 开源只保留 Dense. 报告没有给出 Turbo 和 Plus 的专家数, 总参, 激活参, 只写沿用 Qwen1.5-MoE 与 Dai et al. 的细粒度专家加共享专家路线, 这一面本页没有. 所以 Turbo 和 Plus 的分数只能当作 「某种 MoE 配置」 的结果, 不能拿来推算激活参效率.

Table 1 的头数还能读出每档的设计取舍. 小三档的 KV 头都只有 2 个, Q 头分别是 14, 12, 16, 即每组分别共享 7, 6, 8 个 Q 头, 端侧优先压 KV cache. 14B 和 32B 的头数同为 40/8, 差别只在层数 48 对 64, 32B 是在同样宽度上加深. 7B 反而只有 28 层, 比 3B 的 36 层还浅, 靠更宽的隐藏维度撑容量. 隐藏维度表上没有列, 按 Hugging Face 公开配置, 7B 为 3584, 3B 为 2048 (非本报告数字). 脚注还给了 API 名: Turbo 对应 qwen-turbo-2024-11-01, Plus 当时标为待发布. MoE 层的描述只有一句: 把 FFN 换成多个 FFN 专家加路由, 每个 token 送往 top-K 专家; K 取多少, 共享专家几个, 都没有写.

### 1.3. 底盘沿用, 词表只加控制 token

分词仍是 byte-level BPE, 常规 token 151,643. 变化在**控制 token**: 从 Qwen2 的 3 个扩到 22 个, 其中两个专门给工具调用, 其余留作格式控制. 全系列共用同一张词表, 减少跨型号的兼容摩擦. 这看似小改, 却直接服务 「Better in Use」 里的工具调用和结构化输出: 工具调用的边界用专门的 token 标出来, 模型就不必靠自然语言分隔符猜.

架构组件沿用 Qwen2 已验证的设定. GQA 省 KV cache; QKV bias 点名 Su (2023), 与 RoPE 的外推稳定性有关; RMSNorm 走 Pre-Norm. 这些都不是新东西. 读者值得记住的是 Table 1 的头数比和上下文分档: 小档 KV 头更少, 窗口也更短, 端侧和旗舰不是同一套长上下文能力. 架构章之所以短, 正是因为这一代的主战场不在这里.

控制 token 扩容和后训练是一起设计的. SFT 里的结构化数据, 工具调用样本, 系统提示样本, 都需要清楚的边界标记; 如果边界靠普通文本表示, 用户输入里恰好出现同样的字符串, 模型就可能误判角色或误触发工具. 专用 token 在预训练里从未出现, 只在后训练里赋予含义, 边界就不会和正文混淆. 这和初代引入 ChatML 特殊 token 的理由一脉相承, 只是这一代把需要标记的场景扩展到了工具和结构化输出.

## 2. 预训练: 数据, Scaling Laws 与长上下文

### 2.1. 18T 从哪里来: 过滤, 专项数据, 合成, 重配比

§3.1 把 7T 到 18T 拆成四件事. 第一, 过滤器换成 Qwen2-Instruct, 做多维打分; 因为 Qwen2 本身在更大的多语语料上训过, 当过滤器时对多语样本的判断也更准, 高质量样本留得更多, 低质量样本删得更干净. 第二, 数学和代码直接并入 Qwen2.5-Math 与 Qwen2.5-Coder 的训练数据, 通用模型在预训练阶段就带上领域密度. 第三, 用 Qwen2-72B-Instruct 和 Qwen2-Math-72B-Instruct 生成合成数据, 再用通用奖励模型和 Qwen2-Math-RM-72B 过滤. 第四, 重新配比: 电商, 社交, 娱乐类网页数量多, 模板化严重, 降采样; 科技, 科学, 学术类质量高但偏少, 升采样.

这四件事叠在一起才是 18T, 不是网页语料简单翻倍. 其中过滤, 合成, 奖励模型都来自上一代 Qwen, 形成一条自我增殖的数据链: 上一代模型越强, 下一代数据越好. 好处是领域密度可以快速抬升; 风险是分布可能向生成器自己的偏好收窄. 报告用多维过滤和领域重采样对冲, 但没有给出过滤前后的保留率, 合成数据占比或最终领域配比, 这一面本页没有.

Math 和 Coder 的语料并进通用预训练, 和后面 Instruct 表上数学代码大涨是同一条供应链. 但要分清: 专项模型除了预训练数据, 还有各自的继续预训练和后训练 (例如 Math 的奖励模型和 TIR). 通用模型拿到的是数据, 拿不到专项后训练, 所以通用表上的数学代码分数不能冒充专项报告的最终分数.

### 2.2. Scaling Laws 用来定超参和 MoE 配置

§3.2 的 **Scaling Laws** 用法和常见叙事不太一样. 很多工作用它在给定算力下选模型大小和 token 数; Qwen2.5 主要拿它跨架构找最优 batch size $B$ 和学习率 $\mu$. 实验覆盖 Dense 从 44M 到 14B, MoE 激活参从 44M 到 1B, 数据从 0.8B 到 600B token. 流程分两步. 第一步在每个 (模型规模 $N$, 数据量 $D$) 格点上搜超参, 把最优值拟合成 $\mu_{opt}(N,D)$ 和 $B_{opt}(N,D)$ 两个函数, MoE 的 $N$ 用激活参计; 第二步用这两个函数给出的超参训练各规模, 再把最终 loss 拟合成架构与 $D$ 的函数. 第二步的 loss 曲线之所以可比, 是因为每个点都已在自己的最优超参上, 不会因为某档学习率没调好而把架构差异算错.

同一套曲线还用来预测 MoE 相对 Dense 的表现, 指导 Turbo 和 Plus 把激活参与总参调到能分别对标 14B 和 72B Dense. 这解释了为什么 Instruct 表上 Turbo 专门和 14B-Instruct 比, Plus 专门和 72B-Instruct 比: 对标关系在配置阶段就定好了. 报告没有公布拟合系数, loss 曲线或 MoE 相对 Dense 的具体换算, 所以这一节只能当作方法描述, 不能复算.

为什么要花力气拟合超参? 训练七档 Dense 加两档 MoE, 每档都做学习率和 batch 网格搜索代价太高; 而大模型对学习率又很敏感, 设大了训练发散, 设小了收敛慢, 浪费 token. 用小模型拟合出 「最优超参随规模变化」 的规律, 再外推到大模型, 是 DeepSeek LLM 等报告也采用过的做法. Qwen2.5 的特别之处在于把 MoE 也纳入同一套拟合, 让 Dense 与 MoE 的超参和性能可以放在同一坐标系里比较, 这是 Turbo 和 Plus 敢于直接对标 14B, 72B 的底气.

### 2.3. 长上下文: Dense 两阶段, Turbo 四段渐进

长上下文从预训练开始. 为了效率, 先用 4,096 训主体, 末段再拉长. 除 Turbo 外, 末段扩到 32,768, 用 **ABF** 把 RoPE base 从 10,000 提到 1,000,000. Turbo 更激进, 分四段: 32,768, 65,536, 131,072, 262,144, RoPE base 提到 10,000,000. base 与训练长度是配套放大的: 按 head size 128 算最低频维的周期 $2\pi b^{126/128}$ (报告没有给这组数), $10^6$ 时约 507 万 token, 32K 窗口转不到 1% 圈; $10^7$ 时约 4900 万 token, 262K 窗口同样只转约 0.5% 圈, 两条线在各自最长训练长度上的相位余量相当. 每一段的数据都是 40% 当前顶长序列加 60% 更短序列, 避免模型只会处理顶长, 短序列反而退化. 40% 按序列条数计, 那 60% 短序列的长度分布报告没有给.

后训练也为长上下文单独安排. Turbo 的 SFT 分两阶段: 先和其他型号一样只用短指令, 再混入最长 262,144 的长指令. RL 却只用短指令, 理由是长上下文 RL 成本高, 也缺合适的奖励信号. 报告认为短指令上的 RL 仍能提升长查询上的人类偏好对齐. 所以长上下文能力是一条贯穿预训练, SFT, 推理期的链, 缺一段都会断.

Dense 与 Turbo 的策略差异对应不同产品约束. 开源 Dense 要在可下载权重上保持通用质量, 训练窗口停在 32K, 推理靠外推到 128K; 云端 Turbo 要服务超长会话, 训练就走到 262K, 推理外推到 1M, 并额外做稀疏注意力降低首 token 时延. Table 16 里 7B 在 128K 上 RULER 只有 55.1, 去掉外推更掉到 31.4, 小档的长上下文仍然脆弱, 真正的主交付是旗舰和 Turbo.

### 2.4. 推理期: YaRN, DCA 与 MInference 稀疏注意力

训练窗口到推理窗口之间的缺口靠 **YaRN** 与 **DCA** 填, 两者合起来大约再乘四: Turbo 从 262K 到 1M, 其余型号从 32K 到 131,072. 报告强调外推不只要降长序列 PPL, 还要保住短序列质量. Table 16 与 Table 17 注明 YaRN+DCA 在 32K 以内不改变行为, 所以同表有无外推两行在 4K 到 32K 重合, 分叉出现在 64K 以上. 72B-Instruct 的 RULER 平均 95.1, 128K 仍有 88.4; 去掉外推, 128K 掉到 67.0.

Turbo 还用了基于 **MInference** 的稀疏注意力. MInference 的思路是: 长序列的注意力矩阵高度稀疏, 且不同注意力头呈现固定的几种形状, 比如纵向加斜线 (vertical-slash) 模式; 先离线为每个头搜出最合适的稀疏模式, 推理时只计算关键位置. 报告给出的效果是 1M 序列上注意力计算量约降 12.5 倍, 首 token 时延 (TTFT) 加速约 3.2 到 4.3 倍 (Figure 3). 后来的 Qwen2.5-1M 技术报告进一步把它和 chunked prefill, DCA 结合, 并在 1M 长度上重新校准稀疏配置; 那些细节属于另一份报告.

两组数字要分开读. Figure 2 的 1M Passkey Retrieval 100% 证明超长单针检索没问题; 12.5 倍是注意力计算负载, 3.2 到 4.3 倍才是首 token 时延, 都不是端到端墙钟. Turbo 在 RULER 上平均 93.1, 128K 为 84.5, 比 72B-Instruct 略低, 说明 1M 能力是以一部分中等长度的精度为代价换来的 (按表格对比推断). 报告没有给出稀疏注意力对 RULER 精度的单独影响.

长上下文评测用 RULER, LV-Eval, LongBench-Chat 三套, LV-Eval 同样改用关键词召回率. Table 17 里外推的作用比 RULER 更极端: 72B-Instruct 在 256K 上 LV-Eval 为 45.2, 去掉 YaRN+DCA 只剩 2.4; 7B 从 36.9 掉到 0.5. 超过训练窗口很多倍时, 不外推的模型基本失效. 与外部模型比, 14B-Instruct 的 RULER 平均 91.4 已高于 GPT-4o-mini 的 87.3; 128K 一列 GPT-4 为 81.2, 低于 72B 的 88.4. LongBench-Chat 是长文对话的打分题, 72B 8.72, 32B 8.70, Turbo 8.34, GPT-4o-mini 8.48. Turbo 在这三套上都略低于 72B, 和前面的判断一致.

## 3. 后训练: SFT, DPO 与 GRPO

### 3.1. 百万级 SFT: 九类数据分别补哪块短板

SFT 超过 100 万条, 按报告列出的九类可以对应到具体的短板. 长生成: 用回译从预训练语料造查询, 加长度约束, 目标回复长度到 8,192. 数学: 引入 Qwen2.5-Math 的 CoT 数据, 用拒绝采样和奖励模型过滤. 代码: 覆盖近 40 种编程语言的指令数据, 多 agent 协作生成并用单测验证. 指令遵循: 让模型同时写回复, 校验代码和单测, 用执行反馈做拒绝采样. 结构化理解: 表格, JSON, 半结构化数据. 逻辑推理: 约 70,000 条查询, 覆盖演绎, 归纳, 类比等. 跨语迁移: 把高资源语言的指令翻译并校验到低资源语言. 系统提示稳健性: 数百条系统提示, 保证不同设定下行为一致. 最后是用 critic 和多 agent 打分过滤回复质量.

这九类里, 长生成和结构化理解直接对应 「Better in Use」 的 8K 输出和表格 JSON; 代码化指令校验对应 IFEval 和内部指令遵循分; 跨语迁移和系统提示对应多语表和角色一致性. 训练设定朴素: 两个 epoch, 序列长 32,768, 学习率从 $7\times10^{-6}$ 降到 $7\times10^{-7}$, weight decay 0.1, 梯度裁剪 1.0, 和 Qwen2 一样. 报告没有给出各类样本量的拆分, 只有总量, 这一面本页没有.

几条流水的共同点是尽量用可检验的信号代替人工判断. 数学用拒绝采样加奖励模型加标注答案; 代码用多语言沙箱做静态检查和单测; 指令遵循用模型写的校验代码交叉验证; 逻辑推理多轮迭代剔除答案错误或推理有缺陷的样本; 跨语迁移检查多语回复与原回复的语义对齐. 最后一道过滤最严: critic 模型和多 agent 打分系统都判为无缺陷的回复才保留. 结构化理解的数据还特意在回复里加入推理链, 让模型学会从表格里推出结论, 而不只是查表.

几类数据的来源也各不相同. 长生成的配对用 Qwen2 过滤低质量样本; 数学 CoT 的查询来自公开数据集, K-12 题库和合成题; 代码指令除了多 agent 生成, 还从代码问答网站合成新样本, 从 GitHub 收集算法代码片段; 结构化理解既有表格问答, 事实核验, 纠错这类传统任务, 也有半结构化数据上的复杂任务; 逻辑推理的 70,000 条查询包括选择题, 判断题和开放题. 预训练阶段的领域重配比也是用 Qwen2-Instruct 做分类, 同一个上一代模型在预训练和 SFT 两端都当了过滤器.

### 3.2. 离线 DPO: 可验证域的偏好对

后训练的 RL 分两段, 分工很清楚. 离线段面向奖励模型难以打分, 但有标准答案或可执行检验的领域: 数学, 代码, 指令遵循, 逻辑推理. 做法是用 SFT 模型对新查询重新采样, 通过执行反馈或答案匹配判定对错, 通过的作正例, 不通过的作负例, 人工和自动审核后得到约 150,000 对训练数据. 训练用 DPO, 配 Online Merging Optimizer, 一个 epoch, 学习率 $7\times10^{-7}$.

为什么这些领域不交给奖励模型? 数学和代码的对错, 奖励模型判断常常不如执行器或答案匹配准; 指令遵循里的格式约束, 一段 Python 校验函数就能判定. 用确定信号构造偏好对, 比让奖励模型打分更可靠, 也避免了奖励模型被 hack. 这和 DeepSeek-R1 同期流行的 「可验证奖励」 思路相通, 区别是 Qwen2.5 在这里用 DPO 离线学, 没有在线 RL.

报告前后对离线段的范围说法不一. 第 4 章总述说离线段学的是 「推理, 事实性, 指令遵循」 这类奖励模型难评的能力; §4.2 落到实处时列的是数学, 代码, 指令遵循, 逻辑推理, 事实性没有出现在具体流程里. 可以理解为事实性最终交给了在线段的 「真实性」 准则. 离线段复用的是 SFT 阶段已经搭好的执行反馈和答案匹配流水, 只是换了一批新查询, 让 SFT 模型重新采样; 所以**离线 DPO** 的成本主要在采样和审核, 不需要新建评判系统.

### 3.3. 在线 GRPO 与奖励模型

在线段用 **GRPO**, 信号来自奖励模型. 奖励准则列了六条: 真实性, 有用性, 简洁性, 相关性, 无害性, 去偏. 奖励模型的训练数据来自开源查询加更复杂的专有查询, 回复从 SFT, DPO, RL 不同阶段的检查点在不同温度下采样, 人工与自动标注一起做偏好对, DPO 的数据也并进奖励模型训练集. RL 的查询集与奖励模型训练用同一批.

GRPO 的设置: 每个查询采 8 条回复, 用组内相对得分作优势, 不需要 critic; global batch 2048, 每 episode 2048 个样本, 一个 「查询加回复」 算一个样本. 报告没写式子, 按 GRPO 原论文 (Shao et al., 2024), 同一查询的 $G=8$ 条回复拿到奖励模型分数 $r_1,\dots,r_8$ 后, 第 $i$ 条的优势是
$$\hat A_i=\frac{r_i-\operatorname{mean}(r_1,\dots,r_8)}{\operatorname{std}(r_1,\dots,r_8)},$$
这个值乘到该回复每个 token 的裁剪概率比上, 再减去对参考模型的 KL 项. 组均值替代了 critic 估的基线, 组标准差把不同查询的分数尺度拉齐. 查询排序正是从这个式子来的: 按奖励模型打分的方差排序, 方差大的查询优先. 八条回复分数接近时, 分子 $r_i-\operatorname{mean}$ 全部趋近 0, 这个查询对策略几乎没有梯度, 排在后面等于少花采样算力在零信号的组上. 这个做法后来在很多 GRPO 实践里被写成 「过滤零方差组」.

两段 RL 的信号来源互补. 离线 DPO 用确定信号学难评的硬技能, 在线 GRPO 用奖励模型打磨细粒度的质量, 比如简洁, 相关, 无害. 先后顺序也有道理: 硬技能先固定, 再用奖励模型调风格, 可以减少奖励模型把硬技能调坏的风险. 报告没有给出两段各自贡献多少分的消融, 这一面本页没有.

## 4. 评测

### 4.1. Base 评测: 同档全面上抬, 72B 与 405B 可比

评测前用和 Qwen2 相同的 LCS 规则去污染. Table 2 里 Qwen2.5-72B Base 的 MMLU 86.1, BBH 86.3, MATH 62.1, GSM8K 91.5, MBPP 84.7, 与 Llama-3-405B 多数可比; HumanEval 59.1 仍低于 405B 的 61.0. Plus 的 MMLU-Pro 64.0, 比 72B Dense 高 5.9; GPQA 上 72B 45.9, 相对 Qwen2-72B 的 37.4 跳了一截, TheoremQA 上 Plus 48.5 高于 72B 的 42.4. 科学问答的增益和数学代码同向, 说明学术类升采样不只是刷 GSM8K.

中小档各有看点. Table 3 里 14B 的 MMLU 79.7, 32B 的 MATH 57.7, MBPP 84.5; Turbo 的 MMLU-Pro 甚至高于 32B. Table 4 的 7B 非嵌入参只有 6.5B (Gemma2-9B 为 8.2B), MMLU 74.2, MATH 49.8, HumanEval 57.9. Table 5 里 1.5B 的 MATH 从 Qwen2 的 21.6 升到 35.0, 3B 的 MATH 42.6, GSM8K 79.1. 端侧档位的代际跳变, 对本地部署选择的影响往往比旗舰对标 405B 更直接.

Base 评测的 shot 设置和 Qwen2 基本一致. MMLU, MMLU-Pro, MMLU-redux, Winogrande 用 5-shot, BBH 用 3-shot, ARC-C 用 25-shot, HellaSwag 用 10-shot, TruthfulQA 用 0-shot; GPQA 和 TheoremQA 用 5-shot, GSM8K 和 MATH 用 4-shot; 代码五项全部 0-shot, MultiPL-E 覆盖 Python, C++, Java, PHP, TypeScript, C#, Bash, JavaScript 八种语言. 多语四类里, 考试类由 M3Exam (只选不需要图片的题), IndoMMLU, ruMMLU 和八种语言的翻译版 MMLU 组成; 理解类是 BELEBELE, XCOPA, XWinograd, XStoryCloze, PAWS-X; 数学类是 MGSM 8-shot CoT; 翻译类是 Flores-101 5-shot.

Base 表上也有退步的格子. 72B 的 HumanEval 59.1 低于上一代 Qwen2-72B 的 64.6, HumanEval+ 51.2 也低于 56.1, 而 MBPP 从 76.9 升到 84.7; 两套 Python 题集方向相反, 报告没有解释. Winogrande 上 72B 的 83.9 低于 Qwen2-72B 的 85.1, 7B 的 Winogrande 75.9 和 HellaSwag 80.2 也都略低于上一代. 这类常识完形题接近饱和, 学术类升采样和网页降采样可能让它们小幅回落 (推测, 报告没有归因). 7B 的多语翻译 32.4 低于 Gemma2-9B 的 36.5, 0.5B 的 GPQA 24.8 低于上一代 29.8, 后者接近四选一的随机水平, 波动意义不大.

多语 Base 评测分成考试, 理解, 数学, 翻译四类. 72B 在多项上领先同档, 但翻译类分数整体明显低于理解和考试类, 多语能力并不是均匀抬升的. 这和预训练的配比策略一致: 过滤器和合成器都更擅长高资源语言, 低资源语言主要靠跨语迁移补. 读 Base 表时, 顺序最好是先看数学代码, 再看通用知识, 最后看多语, 不要用单格 HumanEval 否定 「小五倍可比 405B」 的整体叙事, 也不要把 Plus 在 MMLU-Pro 上的优势读成 Dense 72B 全面落后.

### 4.3. 奖励模型多榜评测: 榜高分不等于 RL 更强

Table 15 把奖励模型放在 Reward Bench, RMB, PPE, Human-Preference-Chinese 几套榜上比. Llama-3.1-Nemotron-70B-Reward 在 Reward Bench 总分领先 (94.10), Athene-RM-70B 在 RMB Overall 领先 (73.98), Qwen2.5-RM-72B 在 PPE Objective-Avg (69.85) 与中文人类偏好准确率 (61.27) 上领先. PPE 的 MATH 子项 Qwen2.5-RM-72B 81.48, 高于 Athene 的 79.14; Reward Bench 的 Chat Hard 却只有 78.73, 低于 Nemotron-4-340B 的 87.10. 看哪一列就会得到哪个冠军.

RMB 把每项再分成 BoN 和 Pairwise 两种判法: BoN 要从多条回复里挑出最好的一条, Pairwise 只比两条. Qwen2.5-RM-72B 的 Helpfulness 两种判法分别是 65.72 和 78.83, 与 Athene 接近; Harmlessness BoN 只有 56.35, 比 Athene 的 67.02 低约 11 分, 是它在这张表上最明显的弱项. 这和前面在线 GRPO 把无害性列为六条准则之一对得上: 奖励模型在无害性上的区分度不够强, RL 阶段这一维的信号也会偏弱 (推测). PPE 的 IFEval 子项 Qwen2.5-RM 67.97 领先其他三家, 和离线 DPO 重点做指令遵循同方向.

报告据此提出一个方法论警告: 在单个奖励模型榜上过度优化, 会伤害其他榜和下游对齐, 这是 Goodhart 定律的直接体现; 更进一步, 现有奖励模型榜并不能准确预测用它训出的 RL 模型谁更好. 这句话对读任何 「奖励模型 SOTA 等于对齐 SOTA」 的宣传都是刹车. 训练奖励模型时用多温度采样和方差排序, 解决的是学习效率; 评测奖励模型时用多榜, 解决的是过优化假象. 两件事不能混.

## 5. 边界与谱系位置

报告没写的面要记住. Turbo 和 Plus 的专家数, 总参, 激活参没有公开; 训练 GPU 小时, 集群拓扑, 通信与量化训练细节都不在本文; Scaling Laws 没有拟合系数; SFT 九类没有样本量拆分; 两段 RL 没有各自贡献的消融. 摘要写约五倍小, 结论写六倍小, 措辞不一, 按 72B 对 405B 的数量级理解即可.

选型可以按几条线分. 本地部署和可复现实验走 Table 1 的七档 Dense, 注意许可和窗口; 云端超长上下文和成本敏感场景走 Turbo 或 Plus; 数学代码要极限分数, 应去读 Qwen2.5-Math 和 Qwen2.5-Coder 的专项报告, 通用表上的高分是底座加后训练合成的结果. 小档的长上下文仍然脆弱, 7B 在 128K 上 RULER 只有五十多分, 真需要长文本的场景应优先考虑 72B 或 Turbo. 结论里提到的后续方向, 包括继续迭代数据, 多模态统一框架, 用更多推理算力增强推理, 都是方向句, 没有新的参数表.

谱系上, Qwen2.5 是数据与对齐流水加厚的一代, 架构沿用 Qwen2, 长上下文和 MoE API 是同一底盘上的产品分叉. 它也是后面一串专项和推理模型的起点: Qwen2.5-Math, Qwen2.5-Coder, Qwen2.5-VL, QwQ 都以它为底座; 下一代 Qwen3 则把推理模型和通用模型并进同一套权重, 数据再翻到约 36T, MoE 重新开源. 本文任一数字可按表号回到 `qwen2-5.md`, 英中对照见 `qwen2-5-bi.md`.

# OLMo 2: 先把全开放 dense 线训稳, 再用退火与 RLVR 追上开权重

来源: 同目录 `olmo-2.md` (arXiv:2501.00656, 标题 *2 OLMo 2 Furious*, 58 页), 对照译稿见 `olmo-2-bi.md`. 数字以 Abstract, Fig. 1–25, Tab. 1–27 与 §2–§6, 附录为准. 家族前后: [OLMo](../olmo-1/olmo-1-analysis.md), [Olmo 3](../olmo-3/olmo-3-analysis.md), [Olmo Hybrid](../olmo-hybrid/olmo-hybrid-analysis.md).

一句话身份: OLMo 2 是 Ai2 在 7B / 13B / 32B 三档 Dense decoder-only 上的第二代全开放模型, 训练总量约 4.05T / 5.6T / 6.6T token. 它要解决的问题有两层: 第一代配方放大后训练尖峰频繁, 32B 很难训完; 就算训完, 全开放模型与 Llama 3.1, Qwen 2.5, Gemma 2 这一代开权重模型仍有明显差距. 报告的回答是四件事一起改: 预训练稳定性, 带专门数据的 mid-training, Tulu 3 式的 SFT → DPO → RLVR, 以及让大作业能跑完的集群运维.

这四件事不是四个独立模块. 数据里的重复 n-gram 会诱发尖峰, 所以数据过滤是稳定性手段; 学习率退火的形状决定 mid-training 能吃多少新数据, 所以日程是数据课程的一部分; 底座换了, Tulu 3 的学习率就得重扫, 所以后训练超参跟着预训练走. 下文按这些牵连组织. 机制背景: [归一化层](../../../../llm-guide/2-核心原理与架构/2.1-深度学习基础组件/2.1.2-归一化层/2.1.2-归一化层.md), [GQA](../../../../llm-guide/2-核心原理与架构/2.2-基础注意力机制/2.2.2-多头注意力变体/03-GQA-在性能与缓存之间折中/03-GQA-在性能与缓存之间折中.md), [分词器](../../../../llm-guide/3-预训练/3.3-分词器与Tokenizer/3.3-分词器与Tokenizer.md), [Scaling Law](../../../../llm-guide/3-预训练/3.2-预训练全流程/3.2.6-Scaling-Law/3.2.6-Scaling-Law.md), [DPO](../../../../llm-guide/4-后训练/4.4-对齐技术/4.4.2-无奖励模型的对齐DPO-KTO/01-DPO/01-DPO.md), [PPO](../../../../llm-guide/4-后训练/4.4-对齐技术/4.4.1-基于奖励模型的RL-RLHF-PPO/04-PPO/04-PPO.md), [GRPO](../../../../llm-guide/4-后训练/4.4-对齐技术/4.4.1-基于奖励模型的RL-RLHF-PPO/02-GRPO/02-GRPO.md), [RLVR 的边界](../../../../llm-guide/4-后训练/4.4-对齐技术/4.4.3-RLVR的局限性与探索边界分析.md).

## 1. 定位与训练稳定性

### 1.1. 谱系坐标: 保持全开放, 同时站上性能-算力前沿

Figure 1 把卖点画成一条曲线: 横轴是预训练 FLOPs (按 6 × token × 参数 近似), 纵轴是 OLMES 均分, OLMo 2 落在 **Pareto 前沿**上. Table 6 的数: 7B 均值 62.9, FLOPs 1.8×10²³; 13B 68.3, 4.6; 32B 73.3, 13.0. 同表 Llama 3.1 8B 为 61.8 / 7.2, Qwen 2.5 7B 为 67.4 / 8.2, Gemma 2 9B 为 67.8 / 4.4. OLMo 2 7B 不是每格第一, Qwen 2.5 7B 的 MMLU 74.4 仍明显高于 OLMo 2 7B 的 63.7; 它赢的是 「每单位训练算力的分数」 加上 「数据与中间检查点可得」 这一组合.

参照系有两套. 能力锚点对准 Llama 3.1 / Qwen 2.5 / Gemma 2; 开放度的同类是 Amber, DCLM, MAP Neo, SmolLM 这条全开放线. 在全开放栏里, 同为约 1.0×10²³ FLOPs 的 DCLM 7B 均值 56.9, OLMo 7B 0424 为 50.7, 第一代 OLMo 7B 只有 38.3; OLMo 2 7B 用 1.8×10²³ 到了 62.9. 从第一代到 0424, 算力不变涨了 12.4 分 (心算), 主要来自数据与课程; 从 0424 到 OLMo 2 7B, 算力多了约 80% (心算 1.8 / 1.0), 分数又涨 12.2, 这一段数据, 稳定性与算力都在起作用, 报告没有把三者拆开.

扉页的产物表是这一代 「全开放」 的具体含义: 三档 Base 与 Instruct 权重, olmo-mix-1124 与 dolmino-mix-1124 预训练数据, SFT / DPO / RLVR 数据, OLMo, OLMo-core, open-instruct 代码, OLMES 与 dolma 工具, 训练日志. 相比第一代, 多出来的是 mid-training 数据和后训练数据, 开放范围从预训练延伸到了后训练. 成功标准因此分两层. 第一层是能不能训完: Figure 2 的尖峰要压到大模型可以跑完, 否则名义上的 5T token 会因回滚和提前停训打折扣. 第二层是训完以后能不能进入开权重的竞争带, 也就是 Table 6 与 Table 7. 只做到第一层, 模型只是训得动; 只盯第二层而没有稳定性, 32B 这一行根本交不出来. Introduction 把稳定性列为四条深挖之首, 原因就在这里.

这也让评测主张可以被别人检查: Table 6 的 held-out 列 (AGIEval, GSM8K, MMLU Pro, TriviaQA) 在发布前没有被用来做决策, 作者明说无法对其他模型做同样的保证.

### 1.2. 尖峰从哪里来: 数据, 初始化, 结构与优化器一起改

Figure 2 是前后对照: OLMo-0424 的 loss 与梯度范数尖峰密集, OLMo 2 明显平滑 (读图). §3 把原因拆成几刀, 每刀落在不同的层面. 第一刀在数据: 出问题的 batch 里常见很长的重复 n-gram, 例如成串的 Base64 片段, 或 「255, 255, 255, …」 这样的数字表, 于是在策展时删掉含有一段 32 次以上重复 n-gram 的文档 (n-gram 指 1–13 个 token 的片段), 训练器在加载数据时还会检测这类片段并把它们的 loss 屏蔽掉. 屏蔽的意思是这些位置仍在输入里, 只是不计入损失. 作者也写明这种关联不是确定的: 同一段重复序列可能让大模型出尖峰而小模型不出, 换一种数据顺序就不出, 在没出尖峰的 batch 里也能找到它. 所以两道处理靠的是降低尖峰的平均频率, 不是逐个消灭尖峰源. Figure 3 显示尖峰明显减少但没有消失, 它对梯度范数的缓慢增长也没有作用. 这说明**数据过滤管的是突发尖峰, 慢漂移要靠别的手段**.

第二刀在初始化. OLMo-0424 用 scaled init, OLMo 2 改为全部参数从均值 0, 标准差 0.02 的**截断正态初始化**. Figure 4 在测试设定下 OLMo-0424 很快发散, OLMo 2 稳住. Figure 5 用的指标叫 **growth exponent**: 随机初始化一个模型, 喂 50 篇 The Pile 文档, 收集首层与末层的激活, 以及 loss 对这些激活的梯度 (不含 embedding), 在文档和时间步上取平均, 得到首层向量 $\boldsymbol{v}$ 与末层向量 $\boldsymbol{v}'$, 长度都是 $d_{model}$, 再算

$$\lambda=\frac{1}{n_{\text{layers}}}\log\frac{\|\boldsymbol{v}'\|}{\|\boldsymbol{v}\|}$$

它是每层平均的对数放大率, 激活和梯度各算一个: $\lambda>0$ 表示逐层放大, $\lambda<0$ 表示逐层缩小. 首末层的范数比是 $e^{n_{\text{layers}}\lambda}$, 同样的 $\lambda$ 放到更深的模型上偏差会按层数累积 (按式推). OLMo 2 在各宽度下两个 λ 都更接近 0, 作者据此认为它在低精度下训深模型更稳. 这个量只在初始化时刻测, 说的是起点的尺度是否平衡, 不涉及训练中的漂移. 初始化和宽度相关, 这一刀对 32B 这类更宽的模型尤其重要.

为了让 「尖峰」 可以比较, 作者定义了 **spike score**: 时间序列里偏离最近 1,000 个值滚动均值至少 7 个标准差的点所占百分比, 主要用在训练 loss 与梯度 L2 范数上. 初始化消融的做法是先缩短 warmup, 造一个很快就出尖峰的基线; 换成新初始化后 loss 没有尖峰, 梯度范数的 spike score 从 0.40 降到 0.03, 代价是收敛略慢, 作者用其它超参的改进补回. Figure 6 还给了一个附带好处: 新初始化下梯度范数与 $\sqrt{d_{model}}$ 的正相关更强, 按 Yang et al. (2024b) 的条件, 与宽度无关的初始学习率更容易在不同宽度之间迁移. 后来 Olmo Hybrid 改用 6 个标准差, 128 步窗口的版本, 数值会偏高, 两代的 spike score 不能直接比.

第三刀在结构, 这里有三个改动容易被混为一谈. **Reordered norm** 把归一化从子层输入挪到子层输出, 式 (1)(2) 写作 $\boldsymbol{h} := \boldsymbol{x} + \mathrm{RMSNorm}(\mathrm{Attention}(\boldsymbol{x}))$ 与 $\boldsymbol{h}_{\mathrm{out}} := \boldsymbol{h} + \mathrm{RMSNorm}(\mathrm{MLP}(\boldsymbol{x}))$ (第二式里 MLP 的输入以源文所写为准), 作者注明这一做法最早由 Liu et al. (2021) 用于稳定训练, 后来 Chameleon 也采用. **QK-Norm** 在计算注意力前对 query 与 key 各做一次 RMSNorm, 防止注意力 logit 过大导致发散. 它替换的是 OLMo-0424 的做法: 0424 参考 DBRX, 把 QKV 激活硬裁剪到 8 (Table 1 的 「Clip to 8」). 硬裁剪只在越界时生效, 越界处梯度直接为零; 归一化则对每个 query 与 key 都起作用, 把点积的尺度控制在可预期的范围内, 梯度也保持连续. 从无参 LN 换到 **RMSNorm** 则不是稳定性手段: §3.3.1 写, 第一代用无参 LN 一半为了性能, 一半为了绕开当时库里的 bug, 消融显示两者没有差别, 所以换回更常见的 RMSNorm. Figure 7 显示输出侧归一化加 QK-Norm 优于输入侧基线.

第四刀在损失与优化器. **z-loss** 在损失上加 $10^{-4}\cdot\log^2 Z$, 其中 $Z=\sum_j e^{z_j}$ 是输出 softmax 的分母. 对第 $j$ 个 logit 求导得 $2\cdot10^{-4}\log Z\cdot\mathrm{softmax}(z)_j$ (按式推), 只要 $\log Z$ 偏离 0, 全部 logit 就按各自的概率往回拉. 交叉熵只看 logit 之间的差, 所有 logit 同加一个常数损失不变, z-loss 管住的正是这个自由度, 让 logit 的绝对尺度不随训练漂移. Table 1 终表记权重 10⁻⁵, 与正文的 $10^{-4}$ 不一致, 源文两处并存. Figure 8 还记了一个实现层面的坑: Flash Attention 库自带的 z-loss 与纯 PyTorch 实现前向结果相同, 反向不同, 作者怀疑是精度差异; 虽然对 loss 与下游都没影响, 他们仍弃掉了使用另一套实现的分支, 从分歧点重训, 并尽量避免训练中途切换实现. 优化器侧, Figure 9 把 AdamW 的 ε 从 10⁻⁵ 降到 10⁻⁸, 早期梯度范数更低更稳; Figure 10 显示对 token embedding 做 weight decay 会让 embedding 范数逐渐下降并牵动别处, 于是终表取消.

这几刀合起来才对应 Figure 2. 社区讲 OLMo 2 时常把它概括成 「QK-Norm + 后置 RMSNorm + z-loss」 三件套, 这是结构面的摘要, 丢掉了数据过滤, 初始化和 ε 三处. 复现时只抄 Table 1 的结构行而沿用旧的数据管道与 ε, 很可能在中等宽度就重现 0424 式的抖动. **稳定性在这份报告里是跨层面的性质**, 不属于任何单独一个模块.

## 2. 规格与 mid-training 课程

### 2.1. 规格表背后的取舍: 词表, 上下文, 注意力与日程

Table 3 的三档规格: 7B 为 32 层, $d=4096$, 32/32 MHA, batch 1024, 峰值 LR 3.0×10⁻⁴; 13B 为 40 层, $d=5120$, 40/40 MHA, batch 2048, 峰值 LR 9.0×10⁻⁴; 32B 为 64 层, $d=5120$, 40/8 **GQA**, batch 2048, 峰值 LR 6.0×10⁻⁴. 序列长统一 4096, 梯度裁剪 1.0, warmup 2000 step, 之后余弦衰减到峰值的 10%. 只有 32B 切到 GQA, 文中说是受并行工作 Qwen 3 启发, 用来支撑更大模型; 7B 与 13B 保持 MHA, 实现简单, 也便于和前代对照.

32B 的 40/8 意味着每 5 个 query 头共享一组 key/value, 推理时每层 KV 缓存降到同宽 MHA 的 1/5 (心算 8 / 40). 32B 与 13B 的 $d$ 同为 5120, 层数从 40 加到 64, 如果仍用 MHA, 缓存会随层数同比上涨; 换成 GQA 后, 32B 每 token 的 KV 缓存反而小于 13B (心算 64 × 8 对 40 × 40 个头). 报告没有给推理吞吐或显存的实测, 这个比例只是按头数估算.

位置编码与上下文的选择是一对. RoPE θ 从 1×10⁴ 提到 5×10⁵, 与 Llama 3 同向, 但训练序列仍是 4096 (OLMo-0424 已从第一代的 2048 提到 4096). 更大的 θ 给更长的位置留了分辨率余量, 本身并不交付长上下文; 报告里没有长上下文扩展阶段, 也没有长上下文评测, 这一面因此没有. 算力被优先花在稳定性和 mid-training 上, 长上下文要等到 Olmo 3 才作为独立阶段出现.

分词器从改过的 GPT-NeoX-20B 换成借 cl100k 预分词规则与词表的版本, 保留旧的 PII 掩码 token. Table 2 在 1B 模型, 100B token 的小实验上: OLMES (CF) 59.8 → 60.6, MMLU (CF) 34.8 → 35.2. 作者引用 Tao et al. (2024) 提醒, 这个规模下大词表反而略吃亏, 更大模型与更多 token 时收益才明显. 小实验证明换词表有可测增益, 不代表增益已经充分兑现.

学习率日程与 token 预算要一起读. 余弦按指定的最大 token 数标定: 7B 按 5T 排, 训到约 4T 截断; 32B 按 6.5T 排, 6T 后截断; 13B 训满 5T (约 1.2 个 epoch). §4.1 的 Figure 11 还有一个反常识的结果: 峰值学习率更高的 run 起初更好, 随后被更低学习率的 run 反超, 把学习率线性收到 0 后差距基本消失; Table 8 在 1T 与 2T 的更长训练上复现了 「3×10⁻⁴ 与 6×10⁻⁴ 几乎无差别」. 作者据此否定 「学习率越高越好」 与 「看学习曲线下的面积」 两种经验, 并指出 QK-Norm 与 z-loss 让结果对学习率更不敏感. 这个发现直接支撑了下一节: **退火本身的作用很大**, 所以值得在退火段换数据.

### 2.2. 退火即课程: Dolmino 与 microanneal 的选料梯子

Stage 1 预训练吃掉约 90–95% 训练 FLOPs, 数据是 Table 4 的 OLMo 2 Mix 1124, 约 3.90T token, 其中 DCLM-Baseline 3.71T, 其余为过滤后的 StarCoder, peS2o, arXiv, OpenWebMath, Algebraic Stack, Wikipedia. 代码侧去掉 GitHub star 少于 2 的仓库; 另有启发式删除最高频词占比超过 30%, 或前两高频词超过 50% 的文档, 这类多半是二进制或数字垃圾. 和第一代的 Dolma 相比, 网页部分换成了 DCLM, 数据质量过滤前移到了源头.

Stage 2 就是 mid-training, 约占 5–10% FLOPs, 学习率从 Stage 1 终点线性降到 0. Table 5 的 Dolmino 源池: 高质量部分约 832.6B (过滤后的 DCLM, FLAN, peS2o, Wikipedia, StackExchange), 数学部分约 10.7B, 合计约 843B (心算). 高质量网页用 FastText 分数前 7% 与 FineWeb 分数阈值再切一刀. 实际训练采样 50B / 100B / 300B 三档, Table 13 摊开各档组成: 过滤后的 DCLM 始终占约 47–52%, Source% 超过 100 表示重复, 例如 300B 档 FLAN 200%, 数学 400%. 重复次数跟着一条规则走: 全规模混合实验与 microanneal 都显示各源比例大致不变更好, 预算从 50B 放大到 100B, 300B 时, 源池小的只能靠重复跟上比例, 于是 100B 档 Stack Exchange 与数学各重复 2 次, 300B 档二者重复 4 次, 另把 FLAN 重复 2 次, Wiki 重复 4 次. 最终配方仍让高质量网页托住一半 token, 域数据只是补丁.

这份高质量网页由两个口味不同的分类器联合筛出 (Table 5 记为 「FastText top 7%, FineWeb ≥ 2」, 共 752B token, 606M 篇文档). DCLM 的 FastText 分类器以 ELI5 的 Reddit 回答和 OpenHermes 2.5 的示范为正例, 偏好 「像一个好回答」 的文本; FineWeb Edu 分类器由 Arctic Embed M 微调而来, 训练标签是 Llama 3 70B Instruct 给 40 万以上网页打的分, 按学术性与文字打磨程度给 0–5 分. FineWeb 阈值取 3 只留 5.8%, 取 2 留 20.3%, 最终用了更宽的 2. 两个分类器一个看回答质量, 一个看学术气质, 交集比单用一个更不容易被某一类文风带偏 (这是对两者训练目标的解读, 报告没有单独比较).

**microanneal** 是低成本的选料探针, Table 12 三组实验. 实验 1: 数学源占 35% 时约 576M token, GSM* 从预训练后的 28.5 升到 63.5; 占 10% 时约 1.72B token, 升到 61.0. 有域内数据比高比例更关键. 实验 2: 数学重复 2 次到 66.0, 4 次 65.0, 略有帮助. 实验 3 最有迁移价值: TinyGSM 的代码形式答案在代码占比很低的底座上反而把 GSM* 拉到 25.0, 低于基线; 改写成自然语言的 TinyGSM-MIND 升到 65.5, 翻倍后 70.0. 同一批题, **答案形态是否贴合底座与评测的抽取方式**, 决定了它是补药还是毒药.

把这些实验按预算排开, 是一条三级梯子: 最底层是 microanneal, 只跑几亿到几十亿 token 的短退火, 回答比例, 重复次数, 改写与否这类单变量问题; 中间是 Table 11 的 50B 全规模混合对比, 在候选混合之间做整体取舍; 最上层才是 Table 13 的正式采样加 soup. 下层先剔掉明显无效的选项, 上层只在少数候选上花大预算. 后训练侧的数据也被提前灌进这一段: TuluMath 与 Persona 合成数学出现在 Dolmino 里, 让 mid-training 与后训练的 SFT 用的是同一种数学写法.

GSM8K 的使用方式也写进了这一节. 作者发现预训练后数学很弱, 于是只从 1319 道测试题里抽 200 道作开发集, 称 GSM*, 其余 1119 道只在最终报告时用. 这让 mid-training 的数据决策有信号可看, 同时保住了 held-out 的干净. 附录 B 显示 mid-training 对小模型的相对收益更大, 1B 约 +37.0%. Olmo 3 后来把这一套扩成 「分布式 microanneal + 集中式 integration test」 的 midtraining 框架, 起点就在这里.

### 2.3. 把几次退火平均成一个底座

退火之后还有一步合并. 7B 从同一个 Stage 1 检查点出发, 用不同数据顺序各退火一次 50B, 共三次, 再均匀平均; 13B / 32B 是三次 100B 加一次 300B, 四个检查点平均, 作者写这比只平均三个 100B 更好. 13B/32B 的 batch 是 7B 的两倍, 所以 100B 与 7B 的 50B step 数相同. 权重平均沿用 Matena & Raffel (2022), Wortsman et al. (2022) 的 **model soup** 思路, 目的是在同一片 loss 盆地里找更好的点.

为什么只换数据顺序也值得平均? 几个分支从同一个检查点出发, 学习率都收到 0, 终点落在同一片低 loss 区域的不同位置, 差别主要来自数据顺序带来的随机噪声. 均匀平均相当于把这些噪声相互抵掉一部分, 前提是各分支没有走出同一个盆地, 否则平均后的点可能落在两个盆地之间的高 loss 处. 13B/32B 的第四支用了 300B, 看到的数据更多, 离另外三支更远, 作者的实验显示加入它仍然有益. 报告没有给权重空间距离之类的诊断, 这一层机制是按 model soup 文献的一般解释来读的.

总 token 数也按这些并行分支来算. 7B 的 4.05T 减去 Stage 1 的 3.90T, 差出的 0.15T 正好是三次 50B; 13B 的 5.6T 减 5T, 差 0.6T, 是三次 100B 加一次 300B (均为心算). 这些分支彼此并行, 最终权重里的任何一支只顺序看过 50B 或 100B / 300B 的 Dolmino. Table 9 图注把预训练终点写成 4T / 5T / 7T 的整数口径, 与 §2.3 的 3.90T / 5T / 6.06T 不完全一致, 引用 32B 时以 §2.3 为准.

Table 14 提醒 soup 不是每一列都赢. 六种 50B 混合在 OLMES (MCF) 与 MMLU (MCF) 上 soup 都持平或更好, 数学生成题却参差: mix A 的 GSM* 71.0 → 74.0, mix C 66.0 → 66.0, mix E 从最好单跑的 60.5 掉到 soup 的 43.0. 正文 「持平或更好」 的说法更适合概括多选题; **数学生成对数据顺序更敏感**, 平均后可能互相抵消. 1B 则没有 soup, Table 9 图注写明它的终点是单次 50B 训练, 所以 1B 的 +37.0% 里不含合并的贡献.

## 3. 后训练与评测

### 3.1. 后训练: Tulu 3 骨架换到新底座上

§5 沿用 Tulu 3 的三段式, 并写明 「所有阶段都能顺利迁移到 OLMo 2」. SFT 数据 `tulu-3-sft-olmo-2-mixture` 约 939,104 条 (7B/13B), `-0225` 版约 866,138 条 (1B/32B), 后者过滤了提到知识截止日期的合成指令 (与编造截止日期, 「作为 AI 语言模型」 式开场相关), 合成数学题只保留 5 次采样多数票一致的答案. 作者试过删掉全部多语数据, 平均掉约 0.5 分, 说明 Tulu 3 的混合是平衡的, 不能靠删 「无关」 子集涨分. SFT 用有效 batch 128, 线性日程, warmup 比例 0.3; Table 17 最高分一行是 2 epoch, 1e-5, sum loss, 而 §5 超参列表里 7B 的最终标记落在 2×10⁻⁵, 源文两处不一致.

底座变了, 后训练超参跟着变. §5 明确写: OLMo 2 需要的学习率显著高于 Tulu 3 在 Llama 3.1 上的配方. 这是预训练与后训练之间一条容易被忽视的耦合: 同一套数据与流程, 换一个底座就要重扫学习率, **配方不能直接照搬**. 32B 在 7B/13B 发布之后才做后训练, 超参独立选: SFT 最优 4×10⁻⁶, DPO 最优 2×10⁻⁶.

扫描的范围本身也说明了问题. 7B/13B 的 DPO 学习率在 5×10⁻⁷ 到 1×10⁻⁶ 之间扫, 奖励模型用 3×10⁻⁶; 32B 的 SFT 扫 1–5×10⁻⁶, 在最优的 4×10⁻⁶ 上多跑一个种子确认, DPO 扫 8×10⁻⁷ 到 2.5×10⁻⁶, 最优落在 2×10⁻⁶, 比 7B/13B 的范围高出一截. 按常见经验, 模型越大微调学习率越低, 32B 的 DPO 反而更高, 说明最优点受底座与数据的具体组合影响很大, 只能扫出来, 不能按规模外推. Figure 12 与 Table 17 给了 SFT 与 DPO 的扫描曲线, RLVR 的 β 与学习率也在每一轮的最好模型上重新扫.

偏好阶段混入 **on-policy** 数据: 用开发中的 7B 与 13B SFT 模型采样回复, 7B 约 366.7k 条提示, 13B 约 377.7k 条, 回复来自约 20 个不同家族与尺寸的模型, 模型池只保留许可允许的 (Table 25). 评分交给 GPT-4o-2024-08-06, 按有用, 真实, 诚实, 指令遵循四个维度打分, 取均分最高者为 chosen, 余下随机抽一个为 rejected. 所以 「许可约束」 限定的是回复生成池, 评判模型仍是闭源 API, 读 「全开放后训练」 时要把这两件事分开.

**RLVR** 是可验证奖励的训练设定, 数据为 GSM8K, MATH 训练集加带约束的指令提示, 真正执行优化的是 PPO 或 GRPO. 7B / 13B 先用 on-policy 偏好数据训奖励模型, 再用它初始化 PPO 的 value function, 策略从表现最好的 DPO 检查点起步. 13B 的 「多阶段」 按评测缺口逐轮补: RLVR1 用混合数据, GSM8K 偏低; RLVR2 只训 GSM8K; 最终版只训 MATH, 两项都更高, 每轮 value function 都从奖励模型重新初始化. 1B / 32B 改用 GRPO, 不再需要奖励模型; 32B 最终用学习率 5×10⁻⁷, KL β 0.1, 每题 16 个样本. Table 18 还有一个限制值得记: 7B/13B 的 RLVR 回复长度上限只有 2048 token. 这一代的 RL 是短回答上的可验证奖励, 不是长推理 RL, TestingTime 式的加长思考在这里没有出现.

PPO 的其余设定也偏保守, 按 Table 18 可以把一轮更新复述出来. 策略以温度 1.0 采样, 回复与提示上限都是 2048 token; 验证器只在答案正确时给奖励 (具体数值报告没写), 没生成 EOS 的回复直接记 −10 分; KL 惩罚系数 β 扫了 0.03 / 0.05 / 0.07 / 0.1, 7B 最终取 0.05, 13B 第一与最后一轮取 0.1, 第二轮取 0.03, KL 按 token 还是按整条回复扣报告没写. 折扣 γ = 1.0, 回复末尾的奖励不打折地传回每个位置, 再由 value function 按 GAE (λ = 0.95) 算优势; 每批数据做 K = 4 次 PPO 更新, 只切 1 个 minibatch, 裁剪系数 0.2, 价值损失系数 0.1, 梯度范数裁到 1.0, 学习率线性且没有 warmup. 有效 batch 7B 为 224, 13B 为 248, 最大回合数 7B 100,000, 13B 200,000. 这组设定和 Olmo 3 的 OlmoRL 形成对照: 后者去掉了 KL 项, 用非对称裁剪, 把回复上限放到 32K. 两代之间 RL 的目标从 「在短回答上把可验证题做对」, 变成了 「让长推理也能稳定地训下去」.

Table 16 的阶段差显示每段各管什么. 7B 均值 51.4 → 55.9 → 56.5, 13B 56.6 → 62.0 → 63.4, 32B 61.7 → 68.8 → 68.8. DPO 贡献了大头, 尤其是 AlpacaEval 2 (7B 10.2 → 27.9); RLVR 在均值上涨得少, 但 GSM8K, MATH, IFEval 继续涨 (32B MATH 46.8 → 49.7, IFEval 83.8 → 85.6). 代价落在 Safety: 7B 94.6 → 93.7 → 93.3, 32B 93.8 → 91.9 → 85.9. 32B 的 DPO 与最终版均值同为 68.8, 能力剖面却已经重排, 只看均值会漏掉这一点.

### 3.2. 评测怎样反过来约束开发

评测在这份报告里是开发流程的一部分. OLMES 把开发集与 held-out 分开, GSM* 只用 200 道; 后训练沿用 Tulu 3 的开发与未见两套评测 (Table 15 / Table 24), 但删掉了代码类, 理由是代码不是 OLMo 2 的开发目标. 所以这一代没有代码能力的数, 仅凭报告也无法判断它写代码的水平. 作者还呼吁其他开权重团队声明自己监控了哪些任务, 这是评测治理上的主张.

选择题的题型设置也是一处与规模相关的设计. OLMES 对每个模型同时跑两种题型: **完形式** (CF, 把每个选项的文本分别接在题目后面算似然) 与**多选式** (MCF, 让模型直接输出选项字母), 取较好的一个. 小模型往往还不会按字母作答, 只有 CF 能给出信号; 大模型则能利用 MCF, 这样同一套评测可以横跨 1B 到 70B. 为了效率, MMLU 与 held-out 的选择题只跑 MCF, 因为相关模型在这些任务上都明显偏好 MCF. §4.1 的学习率实验 (Table 8) 用的是 9 个选择题的 CF 版本, 各变体均分相差不到 2 分, 多数在半分以内, 这也是 「学习率不敏感」 结论的评测口径.

附录的任务表把 held-out 四项的口径列得很细: AGIEval English 用测试集 2646 题, 1-shot, MCF; GSM8K 用测试集 1319 题, 8-shot CoT, 精确匹配; MMLU-Pro 用测试集 12032 题, 5-shot, MCF; TriviaQA 用验证集 7993 题, 5-shot, 按 F1 计. 四项分别覆盖考试题, 数学推理, 更难的知识选择题和开放式事实问答, 题型与开发集错开. GSM8K 其实只算半个 held-out, 因为其中 200 道被拿去做 GSM*; 报告在脚注里把这一点讲明了, 读 Table 6 时 GSM8K 那一列的 「未见」 程度要打折扣.

Table 15 标出哪些任务带 CoT (MMLU, BBH, GSM8K, MATH), 这是评测设定, 与部署前的 Scaling 无关. Table 7 里 Qwen QwQ 32B 的均值与部分格子空缺, 作者解释长 CoT 模型的答案抽取会弄坏开放评测工具; 这提醒我们, 推理时多花算力的模型需要另一套抽取与协议, 横比前要先对齐. OLMo 2 自己没有做 TestingTime 方向的实验.

附录里还有两处会影响引用. 附录 B 的 1B 是配方探针: 大部分发现能迁移到大模型, 但越小的模型从 Dolmino 得到的相对收益越大 (附录 B 引 Table 9: 1B +37.0%, 7B +18.7%, 13B +15.9%, 32B +12.3%), Instruct 化后在同档里仍有竞争力 (Table 22 / 23, 以及 Table 7 里 42.7 对 Llama 3.2 1B 的 39.3). 附录 C.3 与 Figure 17 记录了 Instruct Preview 版的 tokenizer.json 预分词规则与正式版不同, 引用训练日志或早期评测结果之前要先对齐模型名, 否则比较的其实是两个分词器.

对外比较落在 Table 7: OLMo 2 Instruct 7B 均值 56.5, 13B 63.5, 32B 68.8; GPT-3.5 Turbo 0125 为 60.5, GPT 4o Mini 0724 为 65.7; 同为约 1.0×10²³ FLOPs 的 OLMo 7B 0424 Instruct 只有 33.1. 32B 均值超过 4o Mini. Safety 一列要和第 3.1 节的阶段差对照着读: 在 Table 7 里, OLMo 2 三档的 Safety (93.3 / 89.7 / 85.9) 高于表中多数开权重模型, 例如 Qwen 2.5 32B 82.4, Llama 3.1 70B 76.4, 4o Mini 为 84.9; RLVR 带来的下降是相对自身 DPO 阶段而言, 不代表横向比别人差. 13B 的 Table 7 均值 63.5 与 Table 16 的 63.4 相差 0.1, 分属两张表, 各带表号引用.

## 4. 工程条件与谱系

### 4.1. 集群, 调度与排放: 训完 32B 的外部条件

§6 把基础设施写成研究条件. Jupiter 位于德州奥斯汀, 128 个节点共 1024 张 H100 (80GB, 700W), 闭式水冷, PUE 1.2; Augusta 由 Google Cloud 提供, 位于爱荷华, 160 个 A3 Mega 节点, 每节点 8 张 H100 (心算约 1280 张), 风冷, PUE 1.12. 7B 大部分在 Jupiter 训, 13B 大部分在 Augusta 训, 两个模型都在两边之间迁移过. **Beaker** 调度系统让作业改一行配置就能换集群, 容器隔离让实验在系统升级后仍可重放, 这和第一代用 LUMI 与 MosaicML 互证可移植性是同一思路.

稳定性问题一部分出在硬件上. §6.3 写两个集群都经历了磨合期, 从插不牢的线缆到 NCCL 里节点顺序错误都遇到过; Beaker 在分卡前先跑一次矩阵乘法做健康检查, 失败就隔离该主机并重排作业, 训练作业因此可以配置成出错自动重启. 吞吐侧的改动都在 OLMo-core 里: `torch.compile()`, 避免隐式的 host-device 同步 (打印 CUDA 张量, 依赖张量值的 if 判断都会触发), 用独立的 GLOO 后端在后台线程做日志与存盘, 以及关掉自动 GC, 改为各进程同时定时回收. Figure 16 在 8 节点的 1B 训练上显示, 自动 GC 让吞吐更低也更不稳 (读图), 进程越多越明显. 模型公式之外的这些细节, 决定了 Figure 2 的平滑能否在真实多机作业里复现.

Table 19 把成本换成环境单位: OLMo 2 7B 耗电 131 MWh, 碳强度 0.332, 排放 52 tCO₂eq, 用水 202 kL; 13B 为 257 MWh, 0.351, 101 t, 892 kL. 两行相加约 388 MWh 与 153 t (心算), 正文写约 391 MWh, 154 t, 用水约 110 万升. 同表第一代 OLMo 7B 只列了 A100 一行 (104 MWh, 70 t). 32B 的能耗与排放报告没有; 与第一代一样, 这些都是运行期下界, 不含制造与推理.

用水这一列说明**选址比模型大小更影响环境成本**. 排放与用水按两条算式估: 排放 $=P_{\text{GPU}}\cdot\mathrm{PUE}\cdot\text{碳强度}$, 用水 $=P_{\text{GPU}}\cdot\mathrm{PUE}\cdot(\mathrm{WUE}_{\text{onsite}}+\mathrm{WUE}_{\text{offsite}})$. 两个集群都是闭式冷却, 现场用水按 0 计, 差别全在发电侧的用水效率: Jupiter 取 1.29 L/kWh, Augusta 取 3.10 L/kWh. 代回 Table 19 能对上: 7B 为 131 × 1.2 × 1.29 ≈ 203 kL, 13B 为 257 × 1.12 × 3.10 ≈ 892 kL (心算). 13B 耗电约是 7B 的 2 倍 (心算 257 / 131), 用水却是 4.4 倍 (心算 892 / 202); 拆开看, 乘上 PUE 后的用电比约 1.83, WUE 之比约 2.40, 两者相乘就是 4.4, 多出来的部分来自电网. 碳强度也同理, 奥斯汀 0.332 与爱荷华接近, 所以碳排大体跟着耗电走. 爱荷华的碳强度正文写 0.352, 表里是 0.351, 代入 257 × 1.12 都约得 101 t.

### 4.2. 在家族谱系里的位置

向前看第一代, OLMo 2 Table 1 就是差分清单: 保留无 bias, SwiGLU, decoder-only; 改掉 RoPE θ, 加 QK-Norm, 无参 LN 换 RMSNorm 并挪到输出侧, 加 z-loss, embedding 不再 decay. 数据从 Dolma 换到以 DCLM 为主的 Mix 1124; 第一代末段 1000 step 的学习率收尾, 长成了带 Dolmino 数据, microanneal 选料与 soup 的 mid-training; 对齐从 TÜLU 2 的 SFT → DPO 长成 Tulu 3 的 SFT → DPO → RLVR. 规模从 7B 扩到 32B, 32B 第一次用上 GQA.

向后看 Olmo 3, 几条线都沿着这里继续: 上下文从 4096 提到 8192, 并在四层中三层加窗长 4096 的 sliding window attention; 预训练数据换成 Dolma 3, mid-training 扩到 100B 并混入 instruction 与 thinking trace; 多了长上下文扩展阶段; RL 从 PPO/GRPO 的短回答 RLVR, 变成改过的 GRPO 与长推理 RL. OLMo 2 里 「只有 32B 用 GQA」, 「RL 回复只有 2048」, 「没有长上下文与代码评测」 这些空白, 基本都在 Olmo 3 里被补上.

材料边界同样要记清. 主叙事是英文学术基准和许可允许的数据, 多语不是优化目标 (SFT 删多语还掉分, 但作者没有做多语评测); 预训练量最多约 6T token, 低于 Table 6 注释里 Qwen 2.5 所说的 「最多 18T token」, Pareto 主张建立在每单位算力的表现上; 32B 的 GQA 与更长的退火属于规模特化, 不能推出 7B 也必须这样做. 报告没有长上下文, 代码, 多模态, 也没有针对安全的专门 RL.

选型时可以这样用这份报告: 要做训练动力学, 数据消融或可复现后训练, 扉页的产物表与中间检查点是主要理由; 只要一个开权重聊天模型, Table 7 只是候选之一. 三种误读值得提前排除. 一是把 Pareto 读成 「全面超过 Qwen 2.5」, Table 6 里 Qwen 2.5 在知识类格子仍更高. 二是把 Dolmino 当第二段从头预训练, 它只占 5–10% FLOPs, 依赖 Stage 1 已经训稳的底座. 三是把 RLVR 当成替代 DPO 的新算法, 它是接在 DPO 之后的可验证奖励训练, 7B/13B 用 PPO, 1B/32B 用 GRPO.

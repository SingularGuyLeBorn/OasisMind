## 1. 材料范围与分词器

### 1.1. 页面上有哪几面, 缺哪几面

一个模型是数据, 分词, 结构, 预训练系统, 后训练和评测一起做出来的. 这份 README 在六面里给了四面半: 数据只有来源类别和处理思路, 分词器写得最具体, 结构只有三行加一句 「采用了和 LLaMA 一样的模型设计」, 预训练给了吞吐和一条 loss 曲线, 评测给了四张 5-shot 表. **后训练这一面完全空白**: 仓库只放预训练模型, 推理示例演示的是续写, 不是对话.

介绍段的硬信息是五项: 百川智能开发, 开源可商用, 约 1.2 万亿 token 训练的 70 亿参数模型, 中英双语, 上下文窗口 4096. 更新信息里写着 2023.09.06 已发布 Baichuan 2, 说明这份 README 在下一代出来之后还改过. 百川 2023 年 3 月成立, 这是它的第一个开源模型, 读它要把它当作起点, 后面几代改掉的东西才有参照.

### 1.2. 中文压缩率从分词器一路传到参数预算和评测表

这份 README 最具体的技术段落是分词. 算法是 SentencePiece 的 BPE, 词表 64,000, 用 2000 万条以中英为主的多语语料训练. 三条设计: 专门提高中文压缩率; **数字逐位切分**, 参考 LLaMA 和 Galactica; **罕见字回退到 UTF-8 字节**, 保证没有未登录词. 对比表里 Baichuan-7B 的压缩率 0.737, LLaMA 是 1.312, Falcon 是 1.049; ChatGLM 与 moss-moon-003 压缩率更低 (0.631, 0.659), 但词表分别是 130,344 和 106,029. README 的论点因此分两层: 对英文模型比压缩率, 对中文模型比 「压缩率相当时词表更小」. 页面没定义压缩率怎么算, 分词器训练的一般流程可对照 [训练 Tokenizer](../../../../llm-guide/3-预训练/3.3-分词器与Tokenizer/3.3.1-训练Tokenizer/3.3.1-训练Tokenizer.md).

词表大小会直接落到参数上. 用 13B README 模型细节表里给出的 7B 总参 7,000,559,616 复算: 32 层, 每层注意力 4 × 4096² 加 SwiGLU 三矩阵 3 × 4096 × 11,008, 再加两张 64,000 × 4096 的 embedding 矩阵 (输入与输出不共享) 和 RMSNorm 权重, 合计正好是 7,000,559,616. 这说明两件页面没明说的事: FFN 宽度确实是 11,008, 输入 embedding 和输出层不共享权重. 两张词表矩阵共约 0.52B 参数, 占总量约 7.5% (估算). 同样的压缩率收益, ChatGLM 那种 13 万词表要多花一倍的参数. 在同等上下文长度 4096 下, 压缩率更低意味着一个窗口能装更多中文原文, 训练时 1.2 万亿 token 覆盖的中文文本也更多.

这笔投入的回报落在评测表上. C-Eval 平均 42.8, 同表 LLaMA-7B-hf 是 27.1, Falcon-7B 是 25.8; Gaokao 平均 36.24, AGIEval 平均 34.44, 同尺寸对照组大都落在 25 到 30 之间. README 没有做 「只换分词器」 的消融, 所以**不能把领先全部记到分词器头上**, 数据配比同样有份. 但英文 MMLU 上 Baichuan-7B 是 42.3, LLaMA-7B 是 35.1, 差距比中文表小得多, 与 「中文侧的数据与分词投入更多」 这个方向吻合.

## 2. 骨架与训练系统

### 2.1. 「和 LLaMA 一样」 的骨架: 保守的结构, 花力气的内核

结构只有三行: 位置编码用 RoPE, 激活用 SwiGLU 且 FFN 为 「8/3 倍隐含层大小, 即 11,008」, 归一化用 RMSNorm 的 Pre-Normalization. 层数, 宽度, 头数要到 13B README 的模型细节表才有: 4,096 宽, 32 层, 32 头, 头维度 128. 页面没提 GQA, 按 32 头 32 层和上面的参数复算, 注意力是标准多头; 没提 MoE; decoder-only 这一点是从推理代码里的 AutoModelForCausalLM 读出来的. 仓库 `models/modeling_baichuan.py` 里, Q, K, V 三个投影被打包成一个名为 **W_pack** 的线性层, 输出宽度 3 × hidden, 训练分支调用 xFormers 的 memory_efficient_attention. 这个打包名后来出现在 13B 的 LoRA 脚本里, 成了百川系模型的标识. RoPE 与 SwiGLU 的来历见 [RoPE 本体](../../../../llm-guide/2-核心原理与架构/2.1-深度学习基础组件/2.1.4-位置编码/01-RoPE本体-旋转位置编码/01-RoPE本体-旋转位置编码.md) 和 [GLU 家族: 从 GLU 到 SwiGLU](../../../../llm-guide/2-核心原理与架构/2.1-深度学习基础组件/2.1.1-前馈网络FFN与激活函数/03-GLU家族-从GLU到SwiGLU/03-GLU家族-从GLU到SwiGLU.md).

README 为 RoPE 给了一张 PPL 对上下文长度的折线图, 训练最长 4096, 横轴测到 5376. 折线到 5120 附近仍平稳, 最后一个点陡升 (读图). 正文说 「可以很好的扩展到 5000 tokens 以上」, 这和图是一致的, 但也说明外推余量只有约 25%. 这是 **RoPE 原样外推** 的常见表现, 后来的长上下文做法都要改频率或插值, 见 [位置编码与外推](../../../../llm-guide/2-核心原理与架构/2.5-长上下文与外推技术/01-位置编码与外推.md). 百川在下一个模型 13B 上干脆换成了 ALiBi, 理由写的是推理速度, 不是外推.

### 2.2. 1.2 万亿 token 背后的训练系统

吞吐一节列了五类改动, 都做在 「原本的 LLaMA 框架」 上: Flash-Attention 与 apex 的 RMSNorm 等高效算子; 算子切分降低显存峰值; 混合精度; IaaS 加 PaaS 联合的训练容灾, 做到分钟级故障定位和恢复; 以及三条通信优化 (拓扑感知的集合通信, 按卡数自适应 bucket size, 调通信原语触发时机让计算与通信重叠). 结果是千卡 A800 上 182 TFLOPS, 峰值算力利用率 58.3%. 182 除以 A800 的 BF16 稠密峰值 312 正好是 58.3%, 所以 182 是单卡数字. FlashAttention 的原理见 [FlashAttention](../../../../llm-guide/2-核心原理与架构/2.3-高效与稀疏注意力/2.3.1-硬件高效注意力/01-FlashAttention/01-FlashAttention.md), 容灾与监控的一般做法见 [训练容灾与监控](../../../../llm-guide/3-预训练/3.2-预训练全流程/3.2.5-训练容灾与监控/3.2.5-训练容灾与监控.md).

把这组数字和 token 量放在一起能算出训练时长的量级. 按 6 × 参数量 × token 数, 总计算量约 6 × 7.0e9 × 1.2e12 ≈ 5.0e22 FLOPs; 以 1000 张卡, 每张 182 TFLOPS 持续满载计, 约 3 天 (估算). 真实训练还有重启, 评估和数据读取的开销, 页面没给实际天数, 这个数只说明: 对 7B 这个尺寸, 1.2 万亿 token 在千卡集群上不是瓶颈, **瓶颈在数据**. 页面也没给张量并行, 流水线并行, ZeRO 级别和全局 batch size; 训练脚本一节配的是 DeepSpeed, 那是给用户的示范流程, 不是内部千卡训练的配置.

loss 图横轴 Billions tokens 从 0 画到 1200, 纵轴 1.75 到 3, 前 100B token 下降最快, 之后缓慢下降, 看不到明显尖刺 (读图). 图上没有验证集曲线和学习率曲线, 看不出训练末段是否退火. 数据一面也只有定性描述: 开源中英文数据, 自抓中文互联网数据, 部分高质量知识性数据; 启发式规则加质量模型打分做篇章与句子两级过滤; 局部敏感哈希做两级去重; 多轮下游实验定中英配比, 自动学习的数据权重策略定类别比例. 各类数据的量, 过滤保留率, 最终权重全都没有.

## 3. 评测与家族位置

### 3.1. 评测测的是 Base, 后训练交给了社区

四张表都是选择题 5-shot. C-Eval 用 dev 集取示例, 在 test 集上测; Gaokao 与 AGIEval 是百川自己处理过的版本, 只留单选题 (AGIEval 限四选一), 随机划分后统一 5-shot, 结果因此不能和两个基准的官方榜直接比. MMLU 表用上标区分三种来源: 自己按 hendrycks/test 复现, 取自 Open LLM Leaderboard, 取自 paperswithcode. 第 4 页给了七行复现命令, 这是全页可复现性最好的部分. 四选一的随机水平是 25%, C-Eval 下半段和 Gaokao, AGIEval 的多数 7B 模型都落在这条线附近, **那一段的排名基本是噪声**; Baichuan-7B 在四张表上都离开了这条线.

C-Eval 表把 GPT-4 (68.7), ChatGPT (54.4) 这类对齐过的闭源模型和预训练 Base 放在一起, 两类模型的比较只能看大致层级. 表里还有几处异常值得记下: Gaokao 表 Aquila 行排序错位, ChatGLM-6B 与 Open-LLaMA-v2 在两张表里分数完全相同, 这些逐条写在 bi 文件对应表格之后. 评测证据怎么读, 可参考 [评测科学与证据](../../../../llm-guide/10-评测、安全与治理/10.1-评测科学与证据.md).

后训练这一面页面自己没做, 第 8 页第三方资源补了空: LLaMA Efficient Tuning 支持 QLoRA 微调与 RLHF, fireballoon 用 ShareGPT, COT, Leetcode 等数据做了 vicuna 风格的 SFT 模型, fastllm 用纯 C++ 跑端侧, TheBloke 做了 GPTQ 4bit 量化. 这份清单说明第一代百川的定位: **官方交付一个中文强的 Base, 对话能力由社区用 SFT 自己接**. 许可分两层, 仓库代码 Apache 2.0, 模型权重商用需邮件登记申请书面授权.

### 3.2. 放回家族里: 后两个版本改了哪几处

13B 在同一套 64,000 词表和 4,096 窗口上把宽度从 4,096 加到 5,120, 层数从 32 加到 40, token 从 1.2 万亿加到 1.4 万亿, 位置编码从 RoPE 换成 ALiBi, 并第一次同时放出 Chat 模型和 int8, int4 量化版, 见 [Baichuan-13B 解析](../baichuan-13b/baichuan-13b-analysis.md). 结构的保守没变, 变的是发布形态: 从 「给开发者一个 Base」 变成 「给普通用户一个能对话, 能在消费卡上跑的模型」.

Baichuan 2 再把词表翻倍到 125,696, token 加到 2.6 万亿, 并补上了 7B 这份 README 完全没有的几面: 数据清洗流程图, 训练稳定性技巧, Scaling Laws 预测, SFT 与 PPO 对齐, 安全评测, 见 [Baichuan 2 解析](../baichuan-2/baichuan-2-analysis.md). 回头看 Baichuan-7B, **它把差异化押在中文数据和分词器上, 结构照搬 LLaMA, 后训练留空**. 这个取舍在 2023 年中很合理: 骨架已经有公认的好配方, 中文开源模型最缺的是一个中文吃得饱的底座.

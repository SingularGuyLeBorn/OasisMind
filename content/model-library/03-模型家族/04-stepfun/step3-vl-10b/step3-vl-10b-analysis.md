# Step3-VL-10B：感知上界靠 1.2T 预训练堆出来，推理上界靠 1,400 轮 RL 和 PaCoRe 打开

来源：[STEP3-VL-10B Technical Report](https://arxiv.org/abs/2601.09668)（arXiv:2601.09668v2, 2026-01-15, 50 页）。主页 https://stepfun-ai.github.io/Step3-VL-10B. 对照译稿见同目录 `step3-vl-10b-bi.md`，表内分数与超参以源文 `step3-vl-10b.md` 为准。

| 项目 | 数值 |
|---|---|
| 组成 | Perception Encoder (language-optimized) 1.8B + Qwen3-8B decoder，合计约 10B |
| 连接器 | 两层连续 stride-2, 16× 空间下采样 |
| 输入 | multi-crop：全局 728×728 + 若干 504×504 局部块；每行 patch 末尾加 newline token；标准 1D RoPE |
| 预训练 | 单阶段全解冻，1.2T token，370K 步，batch 8,192，序列 4,096, AdamW |
| SFT | 两阶段，文本：多模态 9:1（约 190B token）再 1:1（约 36B），序列 128k |
| RL | PPO + GAE，共 1,400 轮：RLVR 600 + RLHF 300 + PaCoRe 500，冻结视觉编码器 |
| 推理模式 | SeRe 单路，最长 65,536 token；PaCoRe 综合 16 路 SeRe，最长 131,072 |

## 1. 定位与架构

### 1.1. 谱系：阶跃用外部底座做的第一个开源 VLM

阶跃之前的多模态模型都挂在自家语言模型上。[Step-3](../step3/step3-bi.md) 的 321B 里有一个 5B 视觉编码器，但那篇报告只谈 decode 成本，把视觉部分整个略过。Step3-VL-10B 走了另一条路：视觉塔用 Meta 开源的 Perception Encoder，语言侧直接用 Qwen3-8B，自家贡献集中在数据、训练日程、奖励设计和推理方式上。GUI 数据沿用同厂 Step-GUI 的构建方法，RL 算法跟随 Open-Reasoner-Zero 和 Open-Vision-Reasoner，推理时的并行综合来自 PaCoRe，这个方法后来也出现在 [Step 3.5 Flash](../step3-5-flash/step3-5-flash-bi.md) 的评测里。所以这篇报告在家族里的位置很清楚：**它不是新架构，而是一次「小底座能被训练日程推多远」的实验。**

引言把成功归结为两条。第一条是在 1.2T 多模态 token 上单阶段、全解冻地联合训练视觉塔和 decoder，同时照顾推理（通识、教育）和感知（grounding、计数、OCR、GUI）两类能力。第二条是放大后的 RL 加并行推理：两阶段 SFT 之后跑超过一千轮 RL，再用 PaCoRe 把推理时的算力花在「并行看多遍、再综合」上。对标对象是 10–20 倍大的开源模型，GLM-4.6V (106B-A12B) 和 Qwen3-VL-Thinking (235B-A22B)，以及 Gemini-2.5-Pro、Seed-1.5-VL 这样的闭源模型。文首的亮点分数是 MMBench 92.2%，MMMU 80.11%，AIME2025 94.43%，MathVision 75.95%；后三项都出自 PaCoRe 模式，这一点读表时要一直带着。

报告有几样东西没有给。训练用了多少卡、多少 GPU 时，全文没有提；预训练 1.2T 里各数据域的精确比例和随时间的变化没有给，只给了每个域的样本量级；文本语料只写了引用来源，没有写占比；GenRM 和几个惩罚项的系数没有给；视觉塔的 patch 大小也没写，所以每张图最终变成多少视觉 token 算不出来。下面凡是涉及这些的地方，都只能停在报告给出的量级上。

### 1.2. 视觉塔：语言对齐比纯视觉特征更要紧

Perception Encoder 是一族视觉编码器，按用途分出偏语言对齐和偏空间定位的不同变体。报告选的是 language-optimized 的 1.8B 版本，理由是它的特征已经和语言对齐过，接到 decoder 上收敛更好。这个选择有一组消融支撑：用 300M 的 PE-lang 和同样 300M 的 DINOv3 (ViT-large-16) 各训一个检查点，OCRBench 70.10 对 57.60，差 12.50 分；MMVP 32.00 对 28.00；CCBench、V*、MMMU、ReMI 也都是 PE-lang 高。DINOv3 只在 BLINK（42.35 对 41.19）和 SimpleVQA（22.18 对 21.15）上略占上风。作者的解释是 DINOv3 纯视觉任务很强，但在多模态设定里有模态鸿沟，收敛慢；结论写成一句话：即便后面还有万亿 token 的生成式训练，**视觉编码器侧的语言对齐仍然是高效 VL 建模的前提**。

OCR 上 12.5 分的差距最值得注意。读字需要把像素和文字符号对上，对比式图文预训练恰好在做这件事；DINOv3 这类自监督特征擅长形状和纹理，离「这串笔画是哪个字」更远。这和下文数据菜单里 OCR 类数据占了大头是一致的：视觉塔先天偏语言，数据再往文字识别上加码，OCRBench 最后到 86.75 并不意外。

编码器之后的连接方式很朴素。两层连续的 stride-2 下采样把视觉 token 在空间上压到 1/16：每层在高和宽上各减半，token 数变成 1/4，两层叠起来是 $(1/4)^2$，报告说这种写法和 Step-3、DeepSeek-OCR 相同，而不是 Q-Former 那种用可学习查询去抽特征。高分辨率细节靠 **multi-crop** 补回来：一张 728×728 的全局视图管整体语义，若干 504×504 的局部块管细节。这些块沿 batch 维并行处理，于是不需要做复杂的变长 packing。位置信息只加了两样：每行 patch 末尾放一个 newline token，让模型知道哪里换行；位置编码用标准 1D RoPE。作者说试过更高级的位置编码变体，在他们的设定下没有明显收益。整个结构刻意保守，创新预算留给了数据和训练。

multi-crop 和「原生分辨率」是处理高分辨率图的两种思路。原生分辨率让编码器直接吃任意尺寸的图，不同图的 patch 数不同，训练时要把长短不一的序列拼进同一个 batch，注意力掩码和负载均衡都更复杂。multi-crop 把图切成固定尺寸的块，每块都是编码器熟悉的输入大小，可以像普通 batch 一样并行编码，代价是切块边界处的上下文会断开，所以要额外留一张全局图兜住整体。报告没有给一张图最多切多少块，也没有给不同分辨率下的视觉 token 数。视觉 token 压缩的一般讨论见 [8.2.2-QFormer与视觉Token压缩](../../../../llm-guide/8-多模态/8.2-视觉语言模型/8.2.2-QFormer与视觉Token压缩.md)，编码器背景见 [8.8-CLIP与视觉编码器](../../../../llm-guide/8-多模态/8.8-CLIP与视觉编码器/8.8-CLIP与视觉编码器.md)。

## 2. 数据与训练日程

### 2.1. 数据菜单，以及每一类数据落到了哪张榜上

预训练数据按能力分成六块，除了一个引用来源的大规模文本语料外，多模态部分都给了量级。知识类有两路。交错图文网页来自 Common Crawl 和自家面向国内互联网的 StepCrawl，再用关键词检索补充；去噪规则是图片下载失败率超过 90% 的网页整页丢弃，含二维码的内容丢弃，宽高比极端的图片丢弃。图文对分四种：LAION、COYO、BLIP-CCS、Zero 等开源集，用 CLIP 聚类做概念均衡重采样以缓解长尾；从知识型网站挖关键词去百度、Bing 检索；从交错网页里给每张图取上文、下文和 alt-text 作候选描述，用 CLIP 相似度和美学分择优；最后是把四张图拼成一张的 Mosaic，同时抬高分辨率、增加单样本的视觉密度，并逼模型做跨区域的空间推理。

教育类约 15M，覆盖 K-12 的数理化与人文，包括用 CoSyn 合成的化学式和结构图、合成加真题的几何题；往上延伸到大学的 STEM、医学、艺术、金融，以及驾照、CPA、法考这类成人考试。OCR 类最细：图到文 10M 真实图片（PaddleOCR 标注）加 30M SynthDog 合成；图到代码里，Markdown、LaTeX、Matplotlib 这类标记代码有 10M+ 开源样本和 15M+ 自动合成的信息图，TikZ、Graphviz 这类程序化图形约 5M；文档到文约 80M 整页，用 PaddleOCR 或 MinerU 2.0 标注；文档到代码从 arXiv 抽出约 4M 表格和 100M 公式。合成信息图时作者特意说不把生成全交给 LLM，而是在多个渲染工具上施加细粒度规则；渲染文档时专门处理引用和超链接，防止图上的字和目标文本对不上。grounding 与计数约 400M，来自 OpenImages、COCO、Merlin、PixMo 的框和点标注，以及把检测标注改写成计数题。VQA 约 10M，另有约 20M 的 OCR VQA。

GUI 数据约 23M，覆盖 Android、iOS 和 Windows、Linux、macOS 上 200 多个应用。其中界面描述 700K，界面知识问答 1M+，轨迹 2M+，grounding 19M+；轨迹定义在 12 个原子动作上，如 CLICK、SLIDE、TYPE，任务包括执行操作、检索信息和总结信息；另外为浏览器场景爬了约 30M 网页，抽出文字和元素坐标。grounding 标注和轨迹是一起生成的，保证「点哪里」和「看到什么」的监督一致。

把这些数据量和表 1（7B–10B 开源对比）放在一起看，**对应关系大体成立，但不是每一格都赢。** OCR 与文档：OCRBench 86.75，AI2D 89.35，CC-OCR 多语 76.59，OmniDocBench 编辑距离 21.51（越低越好，同档最低）都领先；OmniOCR 76.98 却输给 GLM-4.6V-Flash 的 80.24. GUI: ScreenSpot-Pro 51.55，OSWorld-G 59.02，MMBench-GUI L2 81.50 领先，作者把这归到轨迹数据和 RL 里的感知奖励；ScreenSpot-V2 92.61 低于 Qwen3-VL-Thinking 原论文自报的 93.60。计数：400M 的 grounding 与计数数据并没有换来第一，CountBench 88.75 输给 GLM-4.6V-Flash 的 90.22，PixMo-Count 70.85 输给 76.42。空间理解正相反，报告明说没有专门做空间数据，MindCube-tiny 却有 62.81（次名 45.00），SpatialViz-Bench 45.51（次名 35.15）；同一类里 CVBench、RealWorldQA、V* 又都是 GLM-4.6V-Flash 更高。识别与通用 VQA 一类，作者说 7B–10B 里全部领先，把原因归到大规模多模态预训练，尤其是放大到 1.8B 的视觉塔：MMBench 英文 92.05、中文 91.55，MMVP 68.16，HallusionBench 64.91，DoYouSeeMe 67.48，其中 MMVP 与 DoYouSeeMe 领先幅度较大，其余多在一两分之内。STEM 与多模态推理一类，作者归因于充分的预训练加放大的 RL 算力：MMMU 78.11，MMMU-Pro 64.08，MathVision 70.81，比 MiMo-VL 和 Qwen3-VL-Thinking 高出 10 分以上；We-Math 73.03（次名 67.31），HLE 10.73，其他几家都在 6 以下。ZeroBench 主集只有 1.00，大家都接近零，这类题对 10B 模型仍然太难。

还有一格很突出：HumanEval-V 66.05，其他几家都在 24–32 之间；报告没有解释，我推测和大量图到代码数据有关，但这只是推测。Design2Code 上 MiMo-VL 的 82.54 仍高于它的 79.55。

### 2.2. 预训练日程：单阶段全解冻，两段学习率，两种被放弃的加速

预训练只有一个阶段，视觉塔、连接器、decoder 从头到尾一起更新。优化器是 AdamW (β1 0.9, β2 0.95, ε 1e-8, weight decay 0.01)，全局 batch 8,192，序列长 4,096，共 370K 步，合计 1.2T token。学习率分两段：前 900B token 从 5e-5 降到 1e-5，重点是广泛的表征学习；后 300B token 换成更高质量的数据混合，再从 1e-5 退火到 6e-6，作用类似 cool-down，用来巩固 OCR、grounding 这类细粒度感知和推理能力。「最后一段换高质量数据配合降学习率」是近两年语言模型预训练的常见做法，这里把它搬到了多模态。

**单阶段全解冻**本身也是一个选择。很多 VLM 分几步走：先冻住视觉塔和语言模型只训连接器，再逐步解冻，目的是防止随机初始化的连接器在早期把两边的预训练权重带偏。这份报告从第一步就让三部分一起更新，作者把它说成建立视觉与语言的「内在协同」。能这么做，一个前提是 PE-lang 的特征本来就和语言对齐，连接器只是两层下采样，需要学的东西少；另一个前提是学习率从 5e-5 起步，比常见的连接器预热学习率低。报告没有给分阶段训练的对照，所以单阶段比多阶段好多少，这里没有证据。

这组超参有一处对不上。按 batch × 序列长 × 步数算，8,192 × 4,096 × 370K 约为 12.4T token，是报告总量的十倍。反过来，1.2T 除以 370K 步，每步约 3.2M token，平均到 8,192 个样本上每个样本约 400 token。可能的解释是多数样本远没有填满 4,096 长度，或者 batch 的口径不是样本数，报告没有说明。引用这组数时，最好把 1.2T 当作实际训练量，把 4,096 当作长度上限。

§5.1 的三组消融决定了最终配置里没有什么。第一组是上面说的视觉塔。第二组是优化器：**Muon** 用 Newton-Schulz 迭代对整块矩阵的更新做正交化，在尾部知识题上表现更好，SimpleVQA 27.08 对 AdamW 的 20.60，MMStar 也略高；但 OCRBench（67.70 对 71.10）、V*、ReMI 上 AdamW 更好。作者最终没用 Muon，理由是「初始化不匹配」：Qwen3-8B 和 PE 的权重都是用 AdamW 这类逐元素优化器训出来的，换成 Muon 要很长的 warmup 才能稳住，整体训练效率反而不如调好的 AdamW。这正好和同厂的 Step 3.5 Flash 形成对照，后者从头训练，全程用 Muon。表 5 的 Δ 行是 AdamW 减 Muon，所以 SimpleVQA 那格是 -6.48，正文说的 「+6.48%」 是 Muon 相对 AdamW，两处符号方向相反。第三组是 **DeepStack**，即把视觉特征注入 decoder 多个深度的做法，Qwen3-VL 用了它。开启 DeepStack 收敛更快，SimpleVQA（28.66 对 25.20）和 OCRBench 更高，但 MMVP 从 31.33 掉到 26.00，整体没有明显收益，考虑到额外算力被去掉。

这三组消融都有一个前提，附录 C.3 写得清楚：它们是在训练了同样数十亿 token 的中间检查点上做 few-shot 评测，没有拉到最终检查点。所以表 4–6 的绝对分数远低于发布模型，只能看相对高低；而且 Muon 和 DeepStack 的优势会不会在更长训练后放大或消失，这几张表回答不了。

### 2.3. SFT：先把文本推理立住，再拉高多模态比例

SFT 数据以推理为中心。作者从开源社区收集了数百万条数学、代码、科学、逻辑推理的 prompt，加上 grounding、OCR、文档图表理解等视觉感知数据集，回答全部由内部前沿模型蒸馏。过滤分两道：先用规则去掉无限重复这类退化样本；再用精确匹配和 64-gram 匹配对评测集去污染。训练分两阶段，全局 batch 32，序列拉到 128k. 第一阶段文本与多模态按 9:1 混合，约 190B token，目的是打牢逻辑与语言底子；第二阶段改为 1:1，约 36B token，把视觉推理融进来。学习率用余弦调度，200 步 warmup，峰值 1e-4，终值 1e-5；dataloader 里对不同数据域设了采样权重，相当于不同域跑了不同的 epoch 数，具体权重没有给。

两阶段合计约 226B token，相当于预训练量的约 19%，作为 SFT 这个规模很大。**先文本后多模态**的顺序，意图是让 Qwen3-8B 原有的文本推理能力在多模态训练中不被冲掉。还要注意回答的来源：所有 SFT 回答都蒸馏自内部前沿模型，RLHF 的参考答案和 GenRM 的对比对象也是更强的内部模型。所以表 2 的文本推理分数，有很大一部分来自教师模型的推理风格被压进了 8B 参数，这和 Qwen3-VL-Thinking 等对手用什么教师、蒸馏了多少，是同一类比较。报告没有说明教师是哪个模型。表 2 是这个意图的检验。数学和代码明显强于同档：AIME2024 90.94, AIME2025 87.66 (Qwen3-VL-Thinking 62.92), HMMT25 78.18, LiveCodeBench 75.77（次名 51.05）。通识题基本持平或略输：MMLU-Pro 76.02 对 Qwen3-VL-Thinking 的 77.09, SuperGPQA 50.38。指令遵循互有胜负：IFEval 82.16 略低于 83.23，IFBench 43.28 和 MultiChallenge 62.64 领先。主观题 Arena-Hard-V2 58.57，WildBench 86.04 都领先；HealthBench 44.67 低于 Qwen3-VL-Thinking 的 47.45。作者还提到内部 Elo 偏好评测与大得多的开源模型相当，但没给数字。SFT 的一般流程见 [4.2-SFT](../../../../llm-guide/4-后训练/4.2-SFT/4.2-SFT.md)。

## 3. 强化学习与并行推理

### 3.1. RL: PPO + GAE，以及把可验证与不可验证分开的奖励

RL 算法没有选 GRPO，而是跟随 Open-Reasoner-Zero 用带 critic 的 **PPO 和 GAE**。状态 $s_t$ 是图像 $I$、文本 $q$ 加上已生成的 token，动作 $a_t$ 是第 $t$ 个 token。优势用 GAE（式 1）：

$$
\hat A_t = \sum_{l=0}^{T-t-1}(\gamma\lambda)^l\,\delta_{t+l},\qquad \delta_{t'} = r_{t'} + \gamma V_\varphi(s_{t'+1}) - V_\varphi(s_{t'})
$$

取 $\gamma=\lambda=1$ 后，求和里的 $V$ 逐项相消，只剩 $\hat A_t = \sum_{t'\ge t} r_{t'} - V_\varphi(s_t)$；奖励只在轨迹末尾给一次（终止状态价值记 0），就是 $\hat A_t = R - V_\varphi(s_t)$，「整条轨迹的回报减去 critic 给的状态价值」，不再做逐步折扣。critic 按式（3）回归 $\frac12\sum_t\big(V_\varphi(s_t)-V_t^{\text{target}}\big)^2$，目标 $V_t^{\text{target}}=\hat A_t+V_\varphi(s_t)$ 在这组设定下就等于 $R$，所以 critic 学的是「从第 $t$ 个 token 起这条回答最终拿到的奖励」。同一步和 GRPO 比：GRPO 的优势是 $(R_i-\text{mean}_{\text{group}})/\text{std}_{\text{group}}$，一条回答里所有 token 相同；这里减的是 $V_\varphi(s_t)$，同一条回答里不同位置的优势不同，推理中途 critic 估值突然升高的位置，后面的 token 拿到的优势就小。actor 按式（2）的裁剪目标 $\min\big(\rho_t\hat A_t,\ \text{clip}(\rho_t,1-\varepsilon,1+\varepsilon)\hat A_t\big)$ 更新，$\rho_t=\pi_\theta/\pi_{\text{old}}$；$\varepsilon$ 取多少报告没有给。每轮样本切成 4 个 minibatch 依次更新，所以后几个 minibatch 已经是轻度 off-policy；报告又说「省略了标准的重要性采样」，另用阈值 C = 8 的**截断重要性采样**来缓解训练框架和推理引擎之间的数值不一致。按所引 Yao 等人的定义，这个权重是 $\min\big(\pi_{\text{train}}(a_t|s_t)/\pi_{\text{rollout}}(a_t|s_t),\ C\big)$，报告本身没写出式子，也没说明它和式（2）里的 $\rho_t$ 怎样同时出现。actor 学习率 2e-6，critic 5e-6，全程 1,400 轮，只更新 decoder，视觉编码器冻结。截断重要性采样针对的是一个很实际的问题：rollout 由推理引擎生成，梯度在训练框架里算，两边的数值实现不同，同一个 token 的概率会有细微差别；把比值截在 8 以内，少数偏差极大的 token 就不会主导梯度。冻结编码器意味着 RL 阶段感知能力的提升只能来自 decoder 怎么用视觉特征，视觉特征本身在预训练和 SFT 之后就不再变了。PPO 背景见 [04-PPO](../../../../llm-guide/4-后训练/4.4-对齐技术/4.4.1-基于奖励模型的RL-RLHF-PPO/04-PPO/04-PPO.md)。

奖励按任务能否验证分成两支。可验证的一支里，指点和 grounding 这类感知任务跟随 Perception-R1，用 IoU 或欧氏距离对齐几何输出，并加上严格的距离衰减塑形，让奖励地形清晰；一般视觉题用 GPT-OSS-120B 当答案校验器，相比字符串匹配或 math-verify 式规则，它对格式差异不敏感（比如 LaTeX 写法不同），能认出数学上等价的表达，还会惩罚「答案对但推理站不住」的假阳性。不可验证的一支用 **GenRM**：把 rollout 和更强教师模型的回答做成对比较，先写出推理判断，再给细粒度的标量分。此外有三类行为惩罚：中英混杂或问答语言不一致要扣分；检测到伪造的引用或链接，奖励直接归零；对无根据的过度自信扣分，鼓励在信息不足时表达不确定。这三项不在 PPO 公式里，但决定了开放生成会不会被奖励钻空子。

串行推理的 RL 分两段。RLVR 先跑 600 轮，最长 24k，每轮 512 个 prompt × 16 个 rollout。数据来自 Open-Vision-Reasoner 等开源集（数学、几何、物理、科学、感知、图表、谜题）、Perception-R1 的 grounding 任务和内部 K-12 资源，经过三道过滤：GPT-OSS-120B 独立校验四次、全票一致才留下；用早期版本的 Step3-VL-10B 判断图和题是否真的相关，去掉图可有可无的样本；每题跑 24 个 rollout 标难度，只留「有时对有时错」的 some-accept 题。RLHF 接着跑 300 轮，最长 32k，512 × 8，prompt 来自开源 arena 数据和内部指令池，专门挑没有标准答案的题，用最强的内部模型生成参考回答作锚点。粗算一下轨迹量，RLVR 约 4.9M 条，RLHF 约 1.2M 条。先在可检查的题上把推理练稳、再进开放题做偏好，顺序上是为了避免早期偏好信号只奖励表面流畅。

### 3.2. RLVR 里的长度曲线：推理变长，感知变短，平均值回到原点

§5.2 追踪了 RLVR 的 600 轮。奖励和下游指标都是两段式增长：前 200 轮快速上升，之后近似线性；奖励逼近 0.8，作者说没有看到饱和，每 100 轮评一次的推理、识别、OCR、grounding 指标也跟着涨。反常的是平均 rollout 长度。纯文本 RL 里常见的现象是越训回答越长，这里长度先升，最后回到起点附近（读图）。

作者把这解释成**两种效应互相抵消**。数学、谜题这类推理任务仍然是「想得越久越好」，CoT 在变长；grounding、OCR 这类答案确定的感知任务则相反，RL 带来的是熵减：策略把多余的探索 token 剪掉，概率质量收到唯一正确的模式上，相当于把高温采样下的 Pass@N 变成稳定的 Pass@1，回答自然变短，短反而说明更有把握。所以只看平均长度会同时掩盖两件事，分任务看才清楚。

由此引出报告的 「**Missing Trace**」 假说。RL 能放大的行为，取决于初始策略本来会不会做。人看图时有「先扫一眼再聚焦」「试一下、错了再改」这样由粗到细的过程，但这些心理过程几乎从不被写进语料，模型也就没有可供 RL 强化的「感知推理轨迹」。于是在感知任务上，串行加长思考这条路走不通。这是一个解释性的假说，报告没有做专门的对照实验去证伪它。它和训练设计是连着的：如果感知推理的轨迹在语料里本来就少，那么 SFT 蒸馏的数据里也很少，RL 只能在「看一眼就答」这个模式上做熵减。要让串行感知推理出现，要么像 o3 那样在推理中反复放大、裁剪图像，要么先造出带这类轨迹的数据；报告选了第三条路，即不改串行行为，在推理时并行多看几遍。

### 3.3. PaCoRe：把看不见的感知过程摆到上下文里

**PaCoRe** 的做法是先并行跑多路普通推理，再把这些回答作为参考塞进同一个上下文，让模型写出自己的综合答案。报告把它比作 Faster R-CNN 的区域提议网络：先提出多个感知假设，再以它们为条件做精修。正式评测里综合 16 路 SeRe rollout，上限放宽到 131,072 token；附录 B 给了拼接用的 Jinja 模板，就是原题加若干 Reference Response。它和常见的多数投票、best-of-N 不同。投票只能在已有答案里挑一个，多数错了就跟着错；PaCoRe 让模型读到每一路的推理过程，可以发现某一路漏看的细节，写出一个任何单路都没给出的答案。对感知题来说，16 路回答相当于 16 次从不同角度「看」同一张图，综合那一步负责对齐和交叉核验。PaCoRe 原始论文里还有多轮消息传递和把长轨迹压缩成消息的设计，这份报告只用了一轮综合，更复杂的配置没有在 VLM 上试。表 7 的案例里，模型先汇总各参考答案给出的坐标（x 在 220–228 之间，y 在 185 左右），再逐个核对，最后找出共同模式，这是一个定性例子，不是统计检验。

模型要学会这种综合，需要专门训练。PaCoRe 阶段复用 RLVR 难度标注时的 24 个 rollout 作为消息缓存池：对 some-accept 题，从池里抽 16–24 条作为综合上下文让模型重新作答，只保留在这种设定下仍然是 some-accept 的题。这一步防止题目因为有了参考答案而变得太容易、奖励信号消失。然后用严格 on-policy 的 PPO 训练 500 轮，最长 64k，每轮 64 个 prompt × 16 个 rollout，约 51万 条轨迹，奖励用可验证的那一支。作者指出开启 PaCoRe 后回答长度稳定增长，说明模型确实把额外算力花在了核对假设上，和 RLVR 期感知题变短形成对照。

效果在表 3 里。PaCoRe 相对 SeRe 在高难数学上涨得最多：AIME2025 87.66 → 94.43, HMMT25 78.18 → 92.14, BeyondAIME 63.23 → 74.00, IMO-AnswerBench 62.12 → 76.66。多模态侧点名的增益有 MathVision +5.14, DynaMath +5.09，CountQA +4.6，OCRBench +2.25，All-Angles-Bench +7.50，SpatialViz-Bench +6.52；作者特意指出计数、OCR、空间这类「要求高召回、看全」的感知题也受益。但不是每格都涨：M3GIA 从 78.33 掉到 73.50，HallusionBench 和 MMVP 也略降。代价同样要算清楚：一次 PaCoRe 回答至少包含 16 路最长 65,536 token 的普通推理，再加一次最长 131,072 token 的综合，算力大约是单路的十几倍以上。这正是推理时多花算力换精度的做法，也就是 TestingTime 的思路。

## 4. 跟大模型比时，哪些格能比，哪些格不能比

表 3 同时放了 SeRe 和 PaCoRe 两列。只看 SeRe，10B 模型已经在不少格上超过 GLM-4.6V: MMMU 78.11 对 75.20，MathVision 70.81 对 63.50，AIME2025 87.66 对 71.88。但知识密集的格明显吃参数的亏：SimpleVQA 53.08，低于 GLM-4.6V 的 57.95 和 Qwen3-VL 的 59.30; MMLU-Pro 76.02, Qwen3-VL (235B-A22B) 是 83.75，Gemini-2.5-Pro 86.45；MMMU-Pro 64.08 也低于 GLM-4.6V 的 65.84。计数一格，Seed-1.5-VL 的 CountQA 48.89、PixMo-Count 83.38 都远高于它。能压过大模型的主要是推理类和部分感知类，**知识储量没有被训练日程补上**。

评测覆盖 60 多个基准。多模态分九类：STEM 与多模态推理（MMMU、MathVision、MathVista、DynaMath、We-Math、PhyX、LogicVista、ZeroBench、VisuLogic、HLE 等），识别与通用 VQA，计数，指令遵循，视觉代码，OCR，2D/3D 空间，文档与图表，GUI grounding。文本分六类：考试、数学、代码、指令遵循、主观生成、医疗。附录 C.1 给了每个多模态基准的 prompt 模板和答案抽取方式，复现时先对齐模板再比分数，否则同一个模型也可能差出几分。

评测协议决定了这些数字怎么引用。所有评测用 temperature 1.0、top-p 1.0、top-k 0，思考写在 `<think>` 标签里。文本题有重复次数：AIME、HMMT、CNMO、BeyondAIME 每题 64 次取平均，GPQA-Diamond 和 LiveCodeBench 16 次，IFEval、IFBench 4 次，MMLU-Pro、IMO-AnswerBench 等只跑 1 次。和别家报告比 AIME 时，如果对方是单次采样，点估计的方差完全不同。表 1 里带星号的是对方原论文自报数，其余是作者自己跑的。MMBench 有三个数：摘要的 92.2%，表 1 的英文 92.05、中文 91.55，以及 PaCoRe 模式中英平均 92.17；M3GIA 在表 1 是 78.36，在表 3 的 SeRe 列是 78.33，两处差了 0.03。评测基准背景见 [8.2.5-VLM的评测与基准](../../../../llm-guide/8-多模态/8.2-视觉语言模型/8.2.5-VLM的评测与基准.md)。

附录 A 的四个定性案例能看出作者想展示的能力组合。第一个是对照摩斯码表逐个解码图中符号；第二个是看 LaTeX 编辑器截图，问学生至少打开了几个章节 .tex 文件，模型要从一排被截断成 「chapte...」 的标签里数出 5 个，并排除 thesis.tex；第三个是认出失焦图片里显示器底座上的 HP 标志，再做左移 5 位的凯撒密码，答 「HPCK」；第四个是在带权图里找权重最小的边，数出 4 条。四个例子都是「先看准，再做几步推理」，和报告把感知与推理并列的叙事一致，但它们是挑选出来的样例，不说明失败率。

结论一章给了三个方向。一是把算力从预训练转向 RL，理由是 RL 的提升看不到饱和，并在深度（串行推理）和宽度（并行探索）两个方向同时加；二是把 PaCoRe 的并行审议通过自蒸馏内化到参数里，用作者的话说是把 System 2 压成 System 1，降低延迟；三是往物理世界走，包括世界模型、仿真奖励和具身场景的推理。这些都是计划。从家族脉络看，Step3-VL-10B 证明了一件事：用外部 8B 底座，靠 1.2T 的感知数据把上界抬高，再靠 RL 和并行综合把推理打开，小模型可以在推理和感知榜上接近十倍大的系统；知识类题目上的差距，这套方法没有解决。多模态总览见 [8.2-视觉语言模型](../../../../llm-guide/8-多模态/8.2-视觉语言模型/8.2-视觉语言模型.md) 与 [8.5-多模态对齐技术](../../../../llm-guide/8-多模态/8.5-多模态对齐技术/8.5-多模态对齐技术.md)。

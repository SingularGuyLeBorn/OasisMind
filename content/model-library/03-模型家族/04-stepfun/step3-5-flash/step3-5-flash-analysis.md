# Step 3.5 Flash：为 agent 延迟设计的 196B MoE，和让它训得稳的那套办法

来源：同目录 `step3-5-flash.md`（arXiv:2602.10604v2, 67 页）。对照译稿见 `step3-5-flash-bi.md`。下表数字取自正文 Tab. 1, Tab. 5, Tab. 6 与 §2–§5。

| 项目 | 数值 |
|---|---|
| 总参 / 每 token 激活 | 196B / 11B（计入 MTP 头为 198B / 13B） |
| 层数 | 45 层，前 3 层 dense FFN，其余 42 层 MoE |
| 专家 | 每层 288 个 routed + 1 个 shared, top-8 |
| 注意力 | S3F1：每 3 层 SWA（窗口 512）接 1 层 full GQA-8；SWA 层 query 头 96，full 层 64; head-wise gate |
| MTP | 3 个头，每个是 SWA + dense FFN，合计 0.81B（约 0.41%） |
| 训练 token | 预训练约 17.6T, mid-training 750B（引言另写 17.2T） |
| 集群 | 4,096 张 H800，节点间 8×200 Gbps RoCE |
| 上线观察 | OpenRouter 首周约 170 tokens/s (Hopper) |

## 1. 设计目标与结构

### 1.1. 从 Step-3 到 Flash：优化目标从 decode 单价换成了墙上时间

阶跃上一篇有完整技术细节的报告是 [Step-3](../step3/step3-bi.md)。那篇 321B VLM 的目标函数是每百万 token 的 decode 成本，MFA 的算术强度、MoE 稀疏度下限、AFD 的三级流水，都是围绕「一张卡每秒能吐多少 token」算出来的。Step 3.5 Flash 延续了模型和系统一起设计的做法，但换了目标。§2.1 说，自治 agent 在智能和成本之外抬出了第三个约束，就是推理延迟。agent 一轮任务要反复 prefill 很长的上下文，再做很多轮短 decode，用户等的是每一轮的墙上时间，摊薄后的单价只是其中一部分。

目标一换，规模也跟着变。Step-3 每 token 激活 38B，Step 3.5 Flash 只激活 11B，总参压在 200B 以内，作者给的理由很实在：这样才能放进 128GB 统一内存的高端工作站。Step-3 在报告里还出现过一次：§4.1.2 引用 Step-3 报告过的 「dead experts」，并说这次发现专家死亡还有另一种表现。前一代留下的是两样东西，一是按硬件和负载反推结构的习惯，二是大规模 MoE 训练里踩过的坑。注意力形式上，Step 3.5 Flash 用 SWA 与 GQA-8 混合，报告没有讨论它和 Step-3 MFA 之间怎么取舍。

读这份报告时，容易把几种「变大」混在一起。部署前的 Scaling 指总参、数据和集群做大，对应 196B 底座和约 17.6T 预训练 token，背景见 [3.2.6-Scaling-Law](../../../../llm-guide/3-预训练/3.2-预训练全流程/3.2.6-Scaling-Law/3.2.6-Scaling-Law.md). SWA、MTP 和 EP 均衡是服务侧的结构选择，同样在部署前定下。**属于 TestingTime 的只有评测节的 PaCoRe**，也就是推理时并行跑多条轨迹再合成，多花算力换分数。三件事在正文里挨得很近，下面分开讲。

摘要给的对外成绩是 IMO-AnswerBench 85.4%, LiveCodeBench-v6 86.4%, τ²-Bench 88.2%, BrowseComp（开上下文管理）69.0%，Terminal-Bench 2.0 51.0%，并称与 GPT-5.2 xHigh、Gemini 3.0 Pro 同档。这些都是后训练模型在 Vanilla 设定下的分数，没有用 PaCoRe。报告的主线可以概括成一个问题：在长 prefill 加多轮 decode 的 agent 负载下，只激活 11B 的模型要怎样设计结构、怎样训稳、怎样做 RL，才能追上激活量大几倍的对手。下面按这个问题的几个侧面展开，顺序和论文章节不完全一致。

### 1.2. 一个延迟目标，同时决定了注意力、MoE、MTP 和工具格式

注意力选型最能说明这一点。长上下文省算力的常见路线有两条：线性注意力和滑动窗口。作者选 **SWA**（窗口 512），**理由落在投机解码上**。线性注意力按递推更新状态，草稿树的多个分支没法方便地并行验证；SWA 仍是标准 softmax 注意力，用 KV mask 就能一次验证整棵草稿树。长程检索交给每 4 层中的那 1 层 full attention，它用 GQA-8, 8 个 KV 组正好对上 8 卡节点的 KV 切分和张量并行。作者还说这样做有意让注意力偏向带宽受限，空出来的算力留给投机解码的草稿和验证。高效注意力的整体地图见 [2.3.4-高效注意力全景综述](../../../../llm-guide/2-核心原理与架构/2.3-高效与稀疏注意力/2.3.4-高效注意力全景综述/2.3.4-高效注意力全景综述.md)，GQA 的折中见 [03-GQA-在性能与缓存之间折中](../../../../llm-guide/2-核心原理与架构/2.2-基础注意力机制/2.2.2-多头注意力变体/03-GQA-在性能与缓存之间折中/03-GQA-在性能与缓存之间折中.md)。

**MTP** 在同一条线的另一端。编号按「标准 LM 头之外多预测几步」算：MTP-$h$ ($h\in\{1,2,3\}$) 以主干在位置 $t$ 的隐状态为条件，预测 $x_{t+1+h}$，所以三个头分别对应 t+2、t+3、t+4。每个头只有一层 SWA 加一个 dense FFN，三个合计 0.81B. 大部分训练阶段只优化 MTP-1，主干训好后再用 MTP-1 初始化 MTP-2 和 MTP-3，在一个轻量阶段联合训练，并仿 Fast-MTP 按预测距离重新加权 loss，免得模型在远端 token 上用力过度；各 $h$ 的具体权重报告没有给。这里 MTP 的用途写得很明确，就是给投机解码出草稿。机制见 [2.4.6-多Token预测MTP深度解析](../../../../llm-guide/2-核心原理与架构/2.4-前沿架构与变体/2.4.6-多Token预测MTP深度解析.md) 与 [01-投机解码原理与应用](../../../../llm-guide/6-训练与推理优化/6.6-推理框架与高级优化/6.6.2-投机解码/01-投机解码原理与应用.md)。

MoE 侧的问题出在专家并行。loss-free 负载均衡按观测负载调路由 bias，能让全局 token 分布均匀，但管不到每个 micro-batch 里各 EP rank 的负载，最重的 rank 会拖慢整步。作者在 loss-free 之外加了一个 **EP 组级均衡 loss**. EP 把专家集合切成 $G$ 个互不相交的组 $\mathcal{E}_g$，每组放在一个 rank 上；对 batch 里的 $T$ 个 token，$S_t$ 是 token $t$ 的 top-$K$ 专家，$s_{t,e}=\mathbf{1}[e\in S_t]$，$p_{t,e}$ 是路由概率。式（1）：

$$
p_e = \frac{1}{T}\sum_{t=1}^{T} p_{t,e},\quad f_e = \frac{1}{TK}\sum_{t=1}^{T} s_{t,e},\quad p_g = \sum_{e\in\mathcal{E}_g} p_e,\quad f_g = \sum_{e\in\mathcal{E}_g} f_e,\quad \mathcal{L}_{\text{EP}} = G\sum_{g=1}^{G} f_g\,p_g
$$

$f_e$ 是专家 $e$ 实际拿到的 token 份额（不可导），$p_e$ 是它的平均路由概率（可导），梯度只经 $p_g$ 回传，把命中多的组的概率往下压。和 Switch 式 loss $N\sum_e f_e p_e$ 比，差别在求积之前先按组求和：同一 rank 上一个专家过载、另一个闲着，在 $f_g$ 里会相互抵消，组级 loss 不管，因为它们反正在同一张卡上算完；只有整张卡的份额偏离，loss 才上升。按 8 路 EP，每组约 36 个专家（288 / 8）。细粒度 MoE 的一般讨论见 [MoE 总览](../../../../llm-guide/2-核心原理与架构/2.4-前沿架构与变体/2.4.1-混合专家模型MoE/2.4.1-混合专家模型MoE.md) 与 [01-DeepSeek-MoE](../../../../llm-guide/2-核心原理与架构/2.4-前沿架构与变体/2.4.1-混合专家模型MoE/01-DeepSeek-MoE/01-DeepSeek-MoE.md)。

同一个目标还延伸到了 agent 模板。附录说工具调用格式选 XML 而不选 JSON，因为小模型在 JSON 的转义和分隔符上更容易解析失败。多轮编码会话里，每轮都丢掉推理历史会让超过 100 轮的会话失败，全部保留又会撑爆上下文，折中办法是只保留由最近一次用户指令触发的那段工具轨迹里的推理。这些看起来是后训练细节，其实和 11B 激活的定位分不开：激活小，就得在格式和上下文管理上替模型省力。

整体拓扑见 Fig. 2：最前面单独一层 full attention，后面接 11 个混合块，每块是 3 层 SWA 加 1 层 full，合起来正好 45 层；全网用 zero-centered RMSNorm，注意力统一带 head-wise 门控。从这个布局也能看出三条轴线是怎样互相牵制的。注意力要为投机解码留出算力空余，所以选了带宽受限的 GQA-8 和易于并行验证的 SWA；MTP 要轻，所以草稿头也用 SWA 和 dense FFN，不再挂 MoE；MoE 要避免 EP 下的拖尾，所以在常规均衡之外再按 rank 分组均衡。任何一条单拎出来都是常见做法，放在一起，服务的是同一个「agent 一轮交互的墙上时间」。

### 1.3. 混合注意力掉的分，靠加 query 头和门控补回来

S3F1 省下的成本很清楚。Tab. 1 在 30B-A3B 模型上跑完整流程（1.4T token 预训练，32k 扩展，64k SFT），把注意力侧 FLOPs 按 S3F1 归一：全 full 注意力（FFFF）的 decode / prefill 约为 2.68× / 2.90×，每两层一层 full 的 S1F1 约为 1.58× / 1.65×。代价也清楚：直接换成 S3F1，预训练均分从 54.1 掉到 53.6，SFT 后 LongCtx 从 28.8 掉到 27.5。这组消融关掉了 MTP，窗口固定为 512，只看注意力结构本身的影响。

补救的第一步是**给 SWA 层加 query 头**。消融里从 32 加到 48，发布模型从 64 加到 96。加头后 FLOPs 只到 1.01× / 1.02×，预训练均分却升到 55.7，高过 FFFF；SFT 后 LongCtx 回到 28.2，Sci 从 42.4 升到 44.0，Code 小降到 18.3. SWA 层的 K/V 只覆盖 512 个位置，多加 query 头主要多花投影和窗口内的点积，长上下文下这部分开销很小，作者因此称它接近「免费午餐」。S1F1 的 LongCtx 最好（29.6），但注意力成本比 S3F1+Head 高约 60%，所以没有选。

第二步是 **head-wise gated attention**。滑动窗口有个老问题：窗口里没有值得看的内容时，softmax 仍然要把权重分完，多余的注意力没地方放。以往的做法是往窗口里放一个可学习、与输入无关的 sink token。这里改用 Qiu 等人提出的门控，附录 A.1 写成两式。单头维度 $d$，标准注意力是 $s_{i,j}=\langle q_i,k_j\rangle/\sqrt d$，$Z_i=\sum_{j'}\exp(s_{i,j'})$，$y_i=\sum_j \exp(s_{i,j})\,v_j/Z_i$；门控在头输出上乘一个标量：

$$
a_i = w_{\text{gate}}^{\top} x_i,\qquad o_i^{\text{gate}} = \sigma(a_i)\,y_i = \sum_j \frac{\exp(s_{i,j})}{Z_i + e^{-a_i}Z_i}\,v_j
$$

$w_{\text{gate}}$ 是每头一个可学习向量，$x_i$ 是该位置的输入表示（源文把 sigmoid 前后都记作 $g_i$，这里拆成 $a_i$ 与 $\sigma(a_i)$）。第二个等号把 $\sigma(a)=1/(1+e^{-a})$ 代进去：门控等价于在 softmax 分母里多加一块质量 $e^{-a_i}Z_i$，这块质量不对应任何 value，被它「吃掉」的权重就不输出。**sink token 与门控的差别就落在分母这一项上**：sink token 加的是一项与当前输入无关的可学习质量，门控加的项随 $x_i$ 变，而且与窗口内的总质量 $Z_i$ 成比例，所以作者把它看成数据依赖的 sink. Qwen 团队的原论文把门控的收益归到两点：一是在 V 投影和输出投影这两个相邻的线性层之间补了非线性，二是门控分数稀疏且依赖输入，能消掉首 token 吸走大量注意力的现象。Tab. 2 在 100B-A10B 模型、同样 S3F1 布局下比较，门控比 sink token 的均分高 1.97 (62.46 → 64.43)，六项基准全部占优。

两组消融的边界要一起看。30B-A3B 那张表同时报了预训练和 SFT 后的指标，作者关心的是结构改动能不能挺过后训练；100B-A10B 那张只看预训练。消融模型的头数（32 / 48）和发布模型（64 / 96）不同，引用时别把消融规格当成发布规格。附录的速度表显示加头和加门对实际延迟几乎没有影响，这也是它们能进入最终配置的前提。

附录 A.2 给了发布模型规模上的数。在带 MTP-3 的理想负载模拟下，SWA 从 64 头加到 96 头，decode 的 FLOPs / 延迟在 64k 上下文是 1.02 / 1.01，prefill 是 1.08 / 1.06；再加门控，64k prefill 延迟到 1.08，decode 仍在 1.02 以内。原因是 SWA 层 query 与 KV 头之比为 96 / 8 = 12，即使算上 MTP-3 的多 token 验证，这些层仍处在受 IO 限制的区域，多出来的计算被带宽瓶颈掩盖了。同一附录按发布模型的规格重算了几种布局的 FLOPs：以 S3F1 为 1，S1F1 的 decode 在 64k / 256k 是 1.18 / 1.47，FFFF 是 1.51 / 2.33；prefill 分别是 1.38 / 1.71 和 2.07 / 3.00。上下文越长，混合布局省得越多，这也是 agent 场景最看重的区间。

## 2. 训练与后训练

### 2.1. 训练稳定：优化器、数据分布和网络结构一起出的问题

Fig. 3 的预训练 loss 曲线没有平滑，全程只有 1 次孤立尖峰；图上的前三个标记是 batch 依次加到 8,192、12,288、16,384，第四个是 meta token 开始屏蔽 loss。曲线能这么平，靠的是把稳定性当成要持续观测的量。4,096 卡每步产生近 600 万条指标消息，同步归约要多花几秒，几乎让一步的时间翻倍；作者做了一个轻量指标服务器，各 rank 通过内部的 StepRPC 异步上报，开销压到每步约 100 ms。后面三类问题都是在这套监控下看出来的。

第一类来自优化器。训练全程用 **Muon**，正交化改用 **Polar Express**，固定迭代 6 步。训练中偶尔出现无法恢复的 loss 尖峰，换个附近的 checkpoint 重跑往往又能避开，说明是数值问题。模拟显示 bfloat16 下的 Polar Express 在少数更新统计下，会因加法累积误差产生极端中间值。修法很克制：只把 Polar Express 的状态和中间量改成 float16，其余照旧混合精度，之后尖峰没有再出现。Polar Express 原论文本就为 bfloat16 做过稳定处理，到了几千卡、十几万亿 token 的规模，罕见的数值事件还是会冒出来。同样为了 Muon，训练框架改了 ZeRO-1 的梯度切分：Muon 要完整的参数梯度做正交化，ZeRO-1 的 reduce-scatter 却把梯度切开，朴素的 FP32 all-reduce 几乎让通信翻倍。作者把整参数分给各 DP rank，只对专家参数这样处理，迭代时间省约 5%，显存多用不到 4GB. Muon 的背景见 [05-MuonClip与PolarExpress](../../../../llm-guide/6-训练与推理优化/6.5-优化器/Muon/05-MuonClip与PolarExpress.md)。

第二类是**专家死亡**。Step-3 报告的是路由饥饿型，某些专家长期分不到 token。这次看到的是路由统计正常，专家的激活和参数范数却一路萎缩。作者找到两个诱因。有 shared expert 时，需要一个显式系数来校准 shared 与 routed 的相对贡献，大模型不太会自己学到这个平衡。细粒度 MoE 上 micro-batch 级的均衡 loss 管得太严，会压制专家分化，所以更倾向 global-batch 统计或 loss-free bias。监控建议是看每个专家的激活范数和投影矩阵的 Frobenius 范数，最小值相对中位数下滑就是预警。那个显式系数取多少，报告没有给。

第三类是深层少数专家的**激活爆炸**，最能说明几个面缠在一起。Fig. 4 里三种处理的 loss 曲线几乎重合，但不做裁剪时，第 45 层专家输出范数的最大值和中位数迅速拉开，第 38 层则保持平稳（读图）。两种裁剪作用在专家 $\text{SwiGLU}(x)=W_{\text{down}}\big(\text{SiLU}(W_{\text{gate}}x)\odot W_{\text{up}}x\big)$ 的不同位置。权重裁剪对每个投影矩阵 $W$，若 $\max_x\|Wx\|$ 超过阈值 $\tau$，就整体缩放 $W\leftarrow W\cdot\tau/\max_x\|Wx\|$，类似 attention 里的 MuonClip，但离线作用在 checkpoint 上；激活裁剪则在进 $W_{\text{down}}$ 之前，对 $\text{SiLU}(W_{\text{gate}}x)\odot W_{\text{up}}x$ 逐元素截断。前者只能推迟爆炸，后者才压得住；$\tau$ 与激活阈值取多少，报告没有给。附录 B 的成因链跨了四个面。数据里的高频 bigram 让某个专家专门学会一条捷径，只要它被激活，第二个 token 就确定了。pre-norm 下最终表示是 $h_{\text{final}}=\text{RMSNorm}(h_{\text{outlier}}+h_{\text{others}})$，把 $h_{\text{outlier}}$ 写成 $c\,\hat h_{\text{outlier}}$ 后，$c\to\infty$ 时 RMSNorm 的输出趋于 $\text{RMSNorm}(h_{\text{outlier}})$，其余所有层的贡献被归一化抹掉，所以放大这一个专家就是一条无界的捷径。SwiGLU 负责把它放大：离群专家里 $W_{\text{gate}}x$ 与 $W_{\text{up}}x$ 各自的范数并不异常，但满足 $\|\text{SiLU}(W_{\text{gate}}x)\|\cdot\|W_{\text{up}}x\|\approx\|\text{SiLU}(W_{\text{gate}}x)\odot W_{\text{up}}x\|$，只有两支高度对齐、集中在极少数维度时才成立，输出因此是稀疏的大值，范数随谱范数的平方增长。Muon 最后推一把：离群专家的梯度 $\Delta W=\sum_i\sigma_i u_i v_i^{\top}$ 前 $r$ 个奇异方向是方向不变的低秩信号，Muon 正交化后抹掉了梯度幅度，RMSNorm 对大输入压小的梯度照样被放大成满幅更新，低秩方向的奇异值一步步累积；Adam 的 $\epsilon$ 会滤掉这类小梯度，Muon 不会。SwiGLU 在长程训练里放大离群值的现象，FP8 长程训练的研究也报告过。作者因此把「每专家激活范数的 max/median 比值」列为必须监控的稳定指标，只看 loss 和梯度范数会漏掉它。

这些诊断能落地，前提是训练框架本身足够快。Steptron 基于 PyTorch 和 Megatron-LM，预训练、后训练和 RL 共用一套栈。并行方式是 8 路流水线并行（带虚拟流水段）、8 路专家并行和 ZeRO-1 数据并行，注意力和 MoE 模块各用独立的并行组。两路数据并行通信同时跑会把 RoCE 链路挤满，作者把通信拆成节点内 NVLink 和节点间 RoCE 两个阶段流水执行，再按作业的通信画像把 rank 放到合适的交换机下，两项合起来最多省约 5% 迭代时间。算子层面融合了 QK-Norm 与 RoPE，MoE 的 gather/scatter 与 grouped GEMM 也做了融合，激活重算可以细到单个子模块开关。报告没有给出训练 MFU 或端到端训练吞吐，所以这些优化只能看相对收益。

### 2.2. 17.6T 的课表：从开放域到软件工程，再到 128k

数据构成服务于 agent 定位。通用知识来自自建的 StepCrawl，每天处理约 10 亿个网页，爬取时用一个 WebOrganizer 式的小模型过滤 SEO 页、平衡站点类别；退火阶段还把中英文网页做 embedding，k-means 聚成 10 万以上的簇，下采样过大的簇。代码沿用改造过的 OpenCoder 流程，把启发式违规从零容忍放宽到每文档 0–6 条，用一点质量换多样性。软件工程数据取自 10 星以上的 GitHub 仓库：用 git diff 校验过的 PR/Issue/Commit 原始数据，按 Agentless 模板（文件定位，SEARCH/REPLACE 修复）生成的 90B token PR-Dialogue，以及 mid-training 用的约 12B token 改写数据，内容是重建 PR 作者的解题过程或整理成学习笔记。数学和 STEM 另有数千亿 token 和一个 1 亿样本的习题集，作者说早期实验表明解题数据对预训练的 token 效率很关键。

附录 C 把这些数据的处理讲得更细。网页质量分层仿照 Nemotron-CC：六个轻量打分器各自给文档分档再集成，最终只保留高、中高、中三档，丢掉中低和低两档；书籍和论文在退火阶段只留高和中高两档。知识密集子集用一个两段流程构造：先拿一份高价值实体、概念和关系的清单，在 embedding 空间里检索知识密集的段落，按知识密度模型排序；再对其中一部分做受控改写和问答合成，混回训练数据。PR 数据的底座是约 500 万条样本，缺 issue 描述的由 LLM 补写，并和 SWE-bench Verified、Multilingual 严格去重；90B 的 PR-Dialogue 在退火阶段只屏蔽模板部分的 loss，到 mid-training 改成对话格式、屏蔽用户输入。还有数十万条可执行环境种子，带问题描述、代码改动和测试函数，后来成为代码 agent RL 的起点。数据处理跑在 CPU/GPU 混合集群上，用 Spark、Ray 做 minhash 去重和模型推理过滤。

这些数据决策怎么验证？附录 C.5 说，所有数据消融都在 30B-A3B 的 MoE 上用 Muon、固定 token 预算跑，评测除了常规基准，还用一组留出集上的压缩率（困惑度），作者认为它更直接地反映知识容量。选 30B-A3B 而不是更小的代理模型，理由是小模型记不住长尾模式，会让实验结论偏向「多重复数据」，30B-A3B 更贴近全尺寸的趋势。预训练里还有一个 **meta token** 设计：每条样本 $x$ 前面拼一段人可读的元信息串 $M$，包括内容类型（代码、书、论文、网页）、语言、领域和来源，训练序列是 $s=[M;x]$。前约 3.8T token 用 $\mathcal{L}_{\text{full}}=-\sum_{t=1}^{|s|}\log P_\theta(s_t\mid s_{<t})$，元信息位置也计 loss；之后换成 $\mathcal{L}_{\text{mask}}=-\sum_{t=1}^{|x|}\log P_\theta(x_t\mid M,x_{<t})$，$M$ 仍在上下文里当条件，只是不再预测它。作者的假设是此时模型已学会把元信息当条件信号，屏蔽后优化压力全部回到正文 token 上；这个切换对应 Fig. 3 上的第四个标记。

课表分四段。预训练第一段在 4k 上下文跑 14.6T 开放域数据；第二段 3T 退火，先 2T 在 4k，再 1T 在 32k，数据向代码和 PR 类倾斜。mid-training 第一段 386B token 在 32k，其中回放 81B (21%) 预训练数据，防止分布漂移；第二段 364B 在 128k，保留 10.5B 回放，加入合成长程推理和长度超过 32k 的自然长文档。学习率前 2,000 步从 0 线性升到 2.5e-4，第一段内余弦降到 5e-5；退火段在 4k 的 2T 上再余弦降到 2e-5, 32k 的 1T 固定在 2e-5. mid-training 前 3% 迭代预热到 2e-5，第一段保持，第二段降到 7.3e-6. batch 在前 400B token 内从 4,096 逐步升到 16,384，退火的 32k 部分改为 2k. weight decay 0.1，梯度裁剪 1.0. MTP loss 权重第一段 0.3，之后 0.1. loss-free bias 更新率在前 14.6T token 为 0.001，退火时降到 0；EP 组均衡系数 0.001 贯穿预训练，进入 mid-training 后冻结 router 并关掉它。

位置编码的处理和混合注意力绑在一起。4k 阶段 full 与 SWA 层的 RoPE θ 都是 10,000；上下文拉长后只抬 full 层，32k 时 1,000,000, 128k 时 5,000,000，SWA 层始终是 10,000. SWA 只看 512 个位置，用不着外推，要适应更长距离的只有负责长程检索的 full 层。

Base 模型的结果可以当作这套课表的中间检验。Tab. 4 里 Step 3.5 Flash Base 以 11B 激活、196B 总参，SimpleQA 得 31.6，高于 DeepSeek-V3.2-Exp Base 的 27.0，后者总参约是前者的 3.4 倍（671 / 196）；HumanEval 81.1。这组对比说明的是单位激活的能力密度，并不代表每一格都赢更大的模型。

### 2.3. 后训练：先分科练专家，再蒸回一个模型，最后用 MIS-PO 做大规模 RL

后训练的骨架是「专家模型 + 自蒸馏 + 可扩展 RL」。先做两段 SFT。第一段覆盖数学、代码、STEM、逻辑、通用问答、代码 agent、工具、搜索 agent 和长上下文，合计 870,687 条、7.23B token (Tab. 3)。第二段注入约 3 万条专家级化学轨迹和合成算术题，只训 3 个 epoch，借分布外的推理样式提高推理密度。接着在各领域分别做 RL 得到专家模型，再从 mid-training checkpoint 起一个学生模型，由专家生成轨迹，拒绝采样去掉混语和过度思考，蒸馏成一个通才。SFT 阶段同样冻结 router、关掉 EP 组均衡。SFT 数据统一过三道处理：规则过滤去掉无限重复、有害内容和个人信息；专门模型检测并去掉不自然的语言混杂；精确匹配加 N-gram 匹配去污染，精确匹配时还把数字遮掉，以抓住只改了数值的泄漏题。

为什么绕一圈先练专家再蒸馏，而不是直接在一个模型上混合所有领域做 RL? 作者的说法是，共用第一段 SFT 的 prompt 分布让专家生成轨迹，比把多个领域的 RL 直接合在一起更稳，也更省；自蒸馏得到的高质量起点，能明显减轻后续 RL 的优化负担。这一段的超参延续了 mid-training 的设定：Muon，学习率从 1e-5 余弦降到 5e-6，全局 batch 32，序列长度 128k，MTP loss 权重 0.1，full 层 θ 用 5,000,000。数据、预训练和后训练在这里接得很紧，128k 的 SFT 直接吃 mid-training 第二段打下的长上下文底子。

大规模 RL 的难点在方差。作者把方差归到两处：高吞吐推理引擎和训练框架算出来的概率本来就有偏差；迭代更新又带来 off-policy 偏移。长程推理把逐 token 的微小概率差累乘起来，importance sampling 的权重就变得很吵。MoE 让情况更糟，同一个 token 在推理引擎和训练框架里可能被路由到不同专家。**MIS-PO** 借用 Metropolis 独立采样的思路，把推理引擎的策略当作提议分布、训练策略当作目标分布。定义指示函数 $\mathbb{I}(x)=\mathbb{1}[\rho_{\min}\le x\le\rho_{\max}]$，用在两个粒度上：token 级比值 $x_t=\pi_{\theta_{\text{old}}}(a_t|s_t)/\pi_{\theta_{\text{vllm}}}(a_t|s_t)$，分子是训练框架里更新前的策略，分母是推理引擎采样时的策略；轨迹级取几何平均 $\bar\rho(\tau)=(\prod_t x_t)^{1/T}$. actor loss（式 2）：

$$
\mathcal{L}_{\text{actor}} = -\,\mathbb{E}_{\tau\sim\pi_{\theta_{\text{vllm}}}}\Big[\mathbb{I}(x_t)\cdot\mathbb{I}\big(\bar\rho(\tau)\big)\cdot\log\pi_\theta(a_t|s_t)\cdot\hat A_t\Big]
$$

区间取 token 级 $[0.5, 2]$，轨迹级 $[0.996, 1.001]$。轨迹级窄得多，大概是因为几何平均把逐 token 的偏差摊平了，平均漂移到千分之几就已经算大（报告没解释区间怎么定）。优势按 $\gamma=\lambda=1$ 的 GAE 算，此时退化为 $\hat A_t=\hat R-V_\phi(s_t)$（附录式 15）。附录拿来对照的 GSPO 版本用同一套双层掩码，只把 $\log\pi_\theta\cdot\hat A_t$ 换成 $\min\big(r_\tau\hat A_t,\ \text{clip}(r_\tau,1-\epsilon,1+\epsilon)\hat A_t\big)$，其中 $r_\tau=\big(\prod_t\pi_\theta/\pi_{\theta_{\text{old}}}\big)^{1/T}$，$\epsilon$ 在 $\{1,2,3,4\}\times10^{-4}$ 上网格搜索后取 $10^{-4}$，裁剪比例约 15%。两者在同一步上的差别是：通过掩码的 token，GSPO 的梯度还要乘一个随 $\theta$ 变化并被裁剪的比值，MIS-PO 直接按 on-policy 的 $\nabla\log\pi_\theta\cdot\hat A_t$ 更新，权重只有 0 或 1。和 PPO 的连续裁剪比，**这是一种二值过滤。** Fig. 5 在内部模型上跑约 5,000 步，MIS-PO 奖励上升更快，策略梯度范数没有大尖峰，熵衰减更慢（读图）。附录 Fig. 7 的 GSPO 对照里，MoE 模型上 GSPO 约第 200 轮就进入平台，训练-推理比值 $\pi_{\theta_{\text{old}}}/\pi_{\theta_{\text{vllm}}}$ 越拉越开，MIS-PO 则一直把它压在稳定区间内。背景见 [04-PPO](../../../../llm-guide/4-后训练/4.4-对齐技术/4.4.1-基于奖励模型的RL-RLHF-PPO/04-PPO/04-PPO.md) 与 [4.4-GRPO变体与改进-GSPO与DCPO](../../../../llm-guide/4-后训练/4.4-对齐技术/4.4-GRPO变体与改进-GSPO与DCPO.md)。

另外两项配套处理都针对长轨迹和 MoE。**截断感知的价值自举**把「超长被截断」和「答错」分开（式 3）：轨迹 $\tau_i$ 被截断时 $\hat R_i=V_\phi(s_T)$，否则 $\hat R_i=R_i$。代进上面的优势，截断轨迹上每个 token 的 $\hat A_t=V_\phi(s_T)-V_\phi(s_t)$，只反映 critic 认为这段推理把局面推进了多少，不再是一律为负的 $0-V_\phi(s_t)$。截断率高到 20% 时训练仍然稳定，对竞赛级长推理帮助最大。**Routing Confidence** $\Sigma_k$ 是被激活专家的平均概率质量，即每个 token 的 top-$k$ 路由概率之和再对 token 取平均，被当作稳定性的代理指标：$\Sigma_k$ 低说明路由犹豫，同一个 token 在推理引擎和训练框架里更容易落到不同专家，这类模型需要 Router Replay 或严格 on-policy；$\Sigma_k$ 高的模型可以直接做 off-policy。两者之间的分界值报告没有给。RL 超参方面，rollout 的 temperature 与 top-p 都是 1.0，推理题每步 256 个 prompt × 16 条回答，偏好题 512 × 8，工具题 128 × 8，最长 128k；采完的样本只过一个 epoch，actor 切 4 个 mini-batch、critic 切 12 个。同样用 Muon (weight decay 0.1)，actor 学习率 2e-6 预热 20 步，critic 5e-6 预热 50 步，最后阶段加系数 0.001 的无偏 KL。

奖励和数据决定 RL 能学到什么。可验证奖励中，逻辑、指令遵循和代码用规则检查，STEM 用模型打分，450 步消融里比直接用 math-verify 平均高 2.0%；不可验证奖励用 GenRM 加 MetaRM，约 200 步消融里各项比普通 GenRM 高 0.5%–3%。数据合成有三条线。工具学习用有限状态机拆出原子意图，采样、执行、校验后保留 10 万条以上轨迹。代码 agent 把搭环境本身当成能力来练，环境构建成功率约 40%，最后得到跨 15,000 多个仓库、20 多种语言的 5 万个可验证环境。搜索线用 DeepSeek-R1 过滤掉不查资料也能答的问题。环境侧由 Session-Router 经 Kubernetes 管容器生命周期、经 Tmux 保持交互一致，训练时让模型轮流适配 Open-Hands、SWE-agent、Terminus-2 以及 Kilocode、Roocode、ClaudeCode 等框架，避免只会一种脚手架。RL 题库来自开源题集和竞赛档案，明确排除 2024–2026 年举办的竞赛以防污染，另外补了 11–13 位整数的合成算术题、用生成器加校验器为代码题补测试用例，以及谜题和指令遵循的合成环境；过滤时先用规则去掉带图、带外链或没有唯一答案的题，再按正确率去掉过易或退化的题，训练时按预设概率从各领域采样。代码题在沙箱里跑测试，给的是按通过比例计的软奖励。搜索 agent 的 RL 单独换了框架：早期的一步 off-policy 客户端-服务端架构被长尾拖住，约 5% 的样本占了约 80% 的生成成本；作者观察到策略对约 20 步的滞后仍然稳健，于是改成生成与更新完全异步（FullyAsync），并把同一会话固定调度到同一节点以复用 KV cache，效率约提升 10 倍。他们还发现，在 mid-training 里提前注入任务知识和工具使用先验，比从零开始做 RL 带来的提升更大、能力出现得更稳。Fig. 6 给出 RLVR 带来的提升：IMO-AnswerBench +3.2%, CF-Div2-Stepfun-cpp +6.1%, ARC-AGI-1 +10.6%, HLE_text +3.4%.

## 3. 评测与局限

### 3.1. 评测：同一张表里有三种算力口径

Tab. 5 把 Vanilla 和 PaCoRe 分成两列。Vanilla 列的代表分：AIME 2025 97.3, IMO-AnswerBench 85.4, LiveCodeBench-v6 86.4, SWE-bench Verified 74.4, Terminal-Bench 2.0 51.0, BrowseComp 51.6（开上下文管理后 69.0），GAIA 84.5, τ²-Bench 88.2。源 md 的表头把激活和总参识别成 「1119 / B6B」 一类乱码，以正文 11B / 196B 为准。对照模型的格子带两种记号：* 表示原分拿不到或低于复现分，改用同条件复现；† 表示来自非官方来源。

代码 agent 的分数还和脚手架有关。SWE-bench Verified 的 74.4 与 Multilingual 的 67.4 都是 4 次运行的平均；换成原版 SWE-Agent 流程，Verified 为 74.2；在标准 Claude Code 环境里放宽到每题 4 小时，得 72.0。几种脚手架之间差距不大，这和第 2.3 节说的「训练时适配多种 agent 框架、避免过拟合单一脚手架」对得上。同一张表里也有明显短板：HLE_text 只有 23.1 (PaCoRe 27.9)，低于 Kimi K2.5 的 31.5；MRCR-8needle 的 28.8 与闭源模型差距很大。知识密集和长上下文多针检索这两项，11B 激活的定位看起来还补不齐。

**PaCoRe 才是这份报告里的 TestingTime.** 它出自阶跃的另一篇论文：每轮并行生成多条完整推理，把每条压成一段结论性消息，下一轮把原题和这些消息一起输入，总算力因此可以远超单条上下文的长度。这里的配置是 K = [4, 4, 4, 4]，上下文最长 256k，full 层用 YaRN，因子 2.0。推理题上加分明显：AIME 99.9，IMO-AnswerBench 88.8，Arena-Hard-v2.0 从 74.0 到 93.1。但 IFBench 从 67.4 掉到 56.8，MRCR-8needle 从 28.8 掉到 26.3。多轮合成会改写答案的形式和细节，对严格的指令格式和多针检索未必有利；这是推断，报告没有分析原因。

第三种口径是工具。附录单独有一张表比较开关工具的差距（Δtool）：Step 3.5 Flash 在 BrowseComp、GAIA、xbench-DeepSearch 等五项上的平均增益为 52.0，高于 Kimi K2.5 的 40.2 和 DeepSeek V3.2 的 38.1；AIME 2025 接 Python 工具后从 97.3 到 99.8。采样次数也随基准变化：AIME 和 HMMT 各 64 次，IMO-AnswerBench、LiveCodeBench 等 8 次，HLE 1 次。这张表的分数要连同列名、记号和采样次数一起读。

**Δtool** 这个指标值得多说一句。表 11 每格写的是「不开工具的分数 + 开工具的增益」，比如 BrowseComp 不开工具只有 1.5，开了加 50.1，合起来 51.6，正是主表那一格。作者的论点是，绝对分高可能只是模型把答案背进了参数；增益大才说明它会用检索补知识的缺口。这个指标对一个知识储量有限的 11B 激活模型天然有利，读的时候要知道它也是作者挑的角度。Python 工具的完整对比在表 12，上限 100 轮：HMMT 2025 十一月场 94.0 → 98.0, HLE_text 23.1 → 26.5, ARC-AGI-1 54.8 → 56.5, GPQA-Diamond 83.5 → 84.4。作者还初步把 PaCoRe 接进带工具的多轮环境，用一种感知状态的输入序列化，在开 Python 的基础上 GPQA-Diamond 再到 85.7，HLE_text 到 28.2。

附录 E.3 还有三组内部评测，都偏实际业务。数据分析基准由 10 位有 15 年以上经验的国内互联网数据负责人通过访谈提供案例，整理成 50 道题，每题平均 26.9 条加权评分项，在 Claude Code 环境里跑三次平均：Claude Opus 4.5 45.0，Step 3.5 Flash 39.6，GPT-5.2 39.3，作者也承认这可能部分得益于模型对 Claude Code 环境适配较好。咨询建议基准取 500 条来自 Reddit、Stack Exchange 等社区的真实提问，参考答案由人工在几家前沿模型回答基础上整理，定为 88 分锚点，按有用性、逻辑、指令遵循、语气四项等权打分：Step 3.5 Flash 均分 70.5%，排第四，与 Gemini 3.0 Pro 的 70.6% 持平，GPT-5.2 77.8% 第一。正文说它在逻辑维度上超过更大的模型，但表里它的逻辑分 62.1% 低于 DeepSeek V3.2 的 64.4%、Claude Opus 4.5 的 66.5% 和 GPT-5.2 的 81.9%，这句话和表对不上。第三组是 AndroidDaily Hard: Step 3.5 Flash 在云端做任务规划，经 GUI-MCP 协议把原子操作交给端侧的 Step-GUI 执行，成功率 57.0%，纯端侧 40.0%。

### 3.2. 局限，以及下一代接着做什么

**§7 列出的局限在前文都能找到来由。** 第一是 token 效率：要达到与 Gemini 3.0 Pro 相当的质量，需要更长的生成轨迹，下一步打算裁剪和压缩思考过程。这和训练方式有关，截断感知的价值自举鼓励了长推理，PaCoRe 又在推理时进一步放大 token 用量。第二是通用能力与深度领域能力的统一，作者在推进 on-policy 蒸馏的变体，延续的正是第 2.3 节「专家模型 + 自蒸馏」的路线。第三是分布外的稳定性：在高度专业的领域或很长的多轮对话里，模型可能重复推理、中英混杂、对时间和身份认知不一致。发布后社区实测里关于推理中途中断、循环输出的反馈，和这一条对得上。

同目录的 [开放平台页](../stepfun/stepfun-bi.md) 与 [Step 3.7 Flash](../step3-7-flash/step3-7-flash-bi.md) 产品页给出了下一步：在 step-3.5-flash 的高速推理与工具调用之上加入原生多模态输入，规格写成 196B 加一个 1.8B 的 ViT，激活仍是 11B，主打 agent 效率。3.5 Flash 定下的延迟设计和 11B 激活没有变，变的是输入模态和 agent 生态适配。3.7 Flash 页面没有公开架构和训练细节，两代之间具体改了什么，还要等更完整的材料。

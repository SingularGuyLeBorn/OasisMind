# Ling 2.0 技术报告解读

论文: Ling 2.0 Technical Report, 副标题 Every Activation Boosted: Scaling General Reasoner to 1 Trillion Open Language Foundation. arXiv: [2510.22115](https://arxiv.org/abs/2510.22115). 代码与权重: [inclusionAI/Ling-V2](https://github.com/inclusionAI/Ling-V2). 逐页中英对照见同目录 `ling-2-0-bi.md`, 下文提到的页码, 节号, 表号, 图号都以原论文为准.

这份报告篇幅约 58 页, 前半讲模型怎么设计, 怎么训, 后半讲基础设施和附录里的数据细节. 读完之后最值得带走的是三组关系: 总参数和激活参数的关系, Scaling Laws 和部署前规划的关系, non-thinking 模型和后训练里推理模式的关系. 下面按这三条线展开, 顺带把表格里的强项和弱项摊开来看.

## 1. 三个模型与稀疏度

Ling 2.0 这一代发布了三个 non-thinking (instruct) 模型: Ling-mini-2.0, Ling-flash-2.0, Ling-1T. 按 Table 1, 它们的总参数分别是 16B, 103B, 1000B, 激活参数分别是 1.4B, 6.1B, 51B. 论文开头说的 「16B 到 1T」 指的是总参数的两端, 16B 属于 Ling-mini-2.0, 1T 属于 Ling-1T. 总参数决定模型要占多少显存和存储, 激活参数决定每个 token 前向时实际参与计算的规模, 两个数描述的是不同维度, 不存在谁对谁错的问题.

三个模型共用同一套稀疏配置: 256 个路由专家, 每个 token 激活其中 8 个, 另外固定走 1 个共享专家. 这里 top-k 是 8, 共享专家是 1, 在 Table 1 里分成 「# Experts Active per Token」 和 「# Shared Experts」 两行, 不能合并成 「激活 9 个路由专家」. 论文给出的总体激活比约 3.5%, 大致对应 9/257 或 9/256 的量级, 再加上 attention 和 dense 层这些所有 token 都要走的部分, 最后折算出 1.4/16, 6.1/103, 51/1000 这几个比值. 三个模型层数分别是 20, 32, 80, hidden size 分别是 2048, 4096, 8192, 前 1, 1, 4 层保留为 dense 层.

这种 「高稀疏, 细粒度」 的做法和 DeepSeek-V3 一脉相承, 但 Ling 2.0 把它从 16B 一路推到 1T, 并且三个尺寸保持同一套专家数和激活数. 好处是小模型上验证过的结论可以较放心地外推到大模型, 这也是后面 wind tunnel 实验能成立的前提.

## 2. 架构细节: attention, 路由与 MTP

attention 部分用的是标准 GQA, key-value head 数为 8, 16 或 32, 目的是缩小解码时的 KV cache. 激活函数用 SwiGLU, 归一化用 pre-norm 的 RMSNorm. 论文额外加了 QKNorm, 对 query 和 key 做归一化, 第 5 节 FP8 部分会再回到它: 没有 QKNorm 时, `attention.linear_qkv` 层的激活和梯度会出现逐层放大的离群值, 直接拉高 FP8 量化误差. 位置编码用 Partial RoPE, 只对 attention head 的前 64 维加旋转, 用意是改善长度外推. 词表从 Ling 1.5 的 128K 扩到 156K, 新增部分主要是多语言 token.

路由的负载均衡沿用 aux-loss-free 思路, 不在 loss 里加辅助项, 而是给每个专家维护一个偏置 b_i, 按违约误差的符号更新. Ling 2.0 的改动是把更新量减去全体符号的均值, 让偏置围绕零分布. 公式里的更新率写作 u, 训练超参那一节写作 γ, 两者是同一个量: 前 20T token 取 0.001, 上下文扩展之后改为 0.0001. 门控输出乘以 2.5 的缩放因子, 用来稳定门控输出的均方根. 路由采用 dropless 策略, 不丢 token; 同时用 group routing, 把专家分成 8 组, 每个 token 只在得分最高的 4 组里选, 这一点在 §5.4.2 里又从通信角度解释了一遍: DeepEP 一个 token 最多发往 4 个 RDMA 节点和 8 个 NVLink 节点.

MTP (multi-token prediction) 只加了 1 层, loss 权重 0.1. 它在建模上帮助数学和代码任务, 在工程上则是个麻烦: §5.2 实际测得一个 MTP 层的计算成本约为普通 MoE 层的 1.7 倍, 原始 1F1B 调度下它还要和别的层绑在同一个 VPP stage 里, 这个 stage 就成了瓶颈. 后面异构流水线那一节很大篇幅都在处理这个问题.

Table 1 里还有几行尺寸值得对照着看. 三个模型的 attention head 数是 16, 32, 64, dense 层的中间维度是 5120, 9216, 18432, 单个专家的中间维度只有 512, 1024, 2048, 恰好都是 hidden size 的四分之一. 专家做得这么窄, 正是 「细粒度」 的含义: 同样的参数量被切成更多更小的专家, 每个 token 选 8 个, 组合的可能性远多于少量大专家. §5.4.2 说 Ling 2.0 的设计 「更宽更浅」, 从 80 层对 8192 的 hidden size 也能看出这个取向. 这种形状对算子效率有影响, 窄专家的矩阵乘单个规模小, 需要靠分组 GEMM 和融合算子把利用率拉上去, 第 10 节的 MFU 路径里就能看到这些优化各自的贡献.

## 3. Ling Scaling Laws 是训练前的规划工具

报告第 2.3 节的 Ling Scaling Laws 分三部分: 最优超参数的 scaling law, 最优模型与数据分配的 scaling law, MoE 架构效率的 scaling law. 超参数部分用计算预算 C 拟合最优学习率和 batch size, 拟合范围到 3e20 FLOPs 量级, 趋势是预算越大, 最优学习率越低, 最优 batch size 越大. Table 1 里三个模型的学习率 3.36e-4, 2.61e-4, 1.86e-4 和 batch size 4400, 8352, 18144 就是按这套规律取的, 与这一趋势一致.

需要分清的是, 这里的 「scaling」 发生在训练开始之前. 研究者用几百个小模型的实验点拟合曲线, 再据此决定大模型用多大学习率, 喂多少数据, 专家怎么配. 它回答的是 「在给定算力下怎样把模型训好」, 和模型部署之后回答问题时多花多少计算没有关系. 推理阶段让模型多写几步再作答, 那才属于 TestingTime 的范畴, 本文在后训练的长度奖励里才碰到这个话题, 见第 8 节.

架构效率部分做了 300 多个模型的实验, 结论可以归成三条. 第一, 激活比是决定效率的主因, 激活比越低, 同等计算下的效率杠杆越高. 第二, 专家粒度是非线性的调节项, 最优的激活专家数落在 8 到 12 之间, 且这个区间基本不随总算力变化. 第三, 共享专家比例和 dense 层位置等次要因素影响较小, 选一个合理值即可. Ling 2.0 最后选了 256 选 8 加 1 个共享专家, 就是在这三条之间取的平衡.

## 4. Wind tunnel: 用小模型预演大模型

§2.3.3 的 Ling Wind Tunnel 是这份报告里方法论味道最浓的部分. 做法是固定一组 5 个模型, 规模从 500M 到 8B, 尺寸按幂律分布, 每个模型的架构, token 数, 学习率和 batch size 都严格按上一节的 scaling law 取. 这样得到的 5 个点落在同一条 loss 曲线上, 新技术是否有效, 看它能不能把整条曲线往下压, 以及压的幅度是否随规模扩大而保持.

成本上, 论文拿它和传统消融对比: 传统做法是完整训一个 Ling-mini-2.0 到 400B token, wind tunnel 虽然跑 5 个模型, 总计算只有传统方法的 35%. 引言里还有一个 「under 1% of a full training run」 的说法, 分母换成了万亿参数模型的完整训练. 两个数字说的是不同的对照对象: 35% 相对单次中等规模消融, 1% 相对最终大模型的全量训练, 并不矛盾.

wind tunnel 的价值还在于它能回答 「这项技术放大之后还灵不灵」. 很多技巧在 1B 上有效, 到 100B 就消失了; 反过来也有在小模型上看不出, 到大规模才显现的收益. 用一条曲线代替一个点, 可以提前看到斜率的变化. 报告在附录 B.1 用 1B 代码模型和 1B 数学模型验证语料质量, 也是同一种思路的延伸.

## 5. 7 倍效率杠杆到底在比什么

论文开头的 「up to 7× active-compute efficiency」 这个数字很容易被读成 「速度快 7 倍」 或者 「参数省 7 倍」. 按 §2.3.2 的定义, efficiency leverage (EL) 是达到同一性能水平时, dense 模型所需计算量与 MoE 模型所需计算量之比. 分母是 MoE 的计算量, 分子是同等 loss 下 dense 的计算量. 所以 7 倍说的是: 要达到 Ling 2.0 这个配置的 loss, dense 模型得多花大约 7 倍的训练计算.

这个预测后来在 base 模型上复核过. §3.3.2 写道, Ling-mini-2.0-base 与 Qwen3-8B-Base 整体相当, Ling-flash-2.0-base 与 Seed-OSS-36B-Base 整体相当, 而非 embedding 激活参数不到对方的七分之一. 直接用 1.4B 去除 8B 得到的是约 1/5.7, 看起来不到七分之一; 差别在于论文比的是非 embedding 部分, 1.4B 的激活参数里含 embedding, 扣掉之后比值才落到 1/7 以下. 读这类数字时, 先确认分子分母各算了哪些参数, 比记住倍数本身更有用.

还要注意, EL 是训练计算上的杠杆, 不直接等于推理速度. 推理时 MoE 还要承担全部专家常驻显存, 路由通信和 KV cache 的开销, 实际吞吐的提升取决于部署方式. 论文在 §5.1.2 提到 Ling-mini-2.0 在 8 到 32 张 GPU 上相比 LLaMA 3.1 8B 和 Qwen3 8B 训练吞吐高 30% 到 60% (开 MTP) 或 90% 到 120% (不开 MTP), 这是训练吞吐, 同样不能直接换算成线上延迟.

## 6. 预训练数据: 推理数据占比逐步提高

预训练总量是 20T token, 分成两个各 10T 的子阶段, 上下文长度 4K. 两个子阶段之间, 推理数据 (数学和代码) 的比例从 32% 提高到 46%, 网页等通用数据相应从 68% 降到 54%. Ling Math 和 Ling Code 两套语料是重点, 引言说它们在推理基准上带来平均 5% 到 8% 的提升. 附录 B 给了细节: 代码语料去重后约 2.7T token, 覆盖 660 种编程语言, 分层后顶级子集 600B token, 另有 300B 改写数据, 140B 以上的 Common Crawl 精炼数据, 73B 的 commit 记录; 数学语料超过 1.8T token, 用 fastText 召回加 4B 参数的 LLM-Filter 和 LLM-Refiner 精炼.

20T 之后是 mid-training. 前 150B token 在 32K 上下文上训练, 其中 20% 是 32K 长度的长文本, 再用 YaRN 把窗口扩到 128K; 后 600B token 保持高比例推理数据, 并加入高质量 CoT 语料. 所以 20T 这个数只算通用预训练, 不含 mid-training 的 750B. Table 2 和 Table 3 对比了加不加 CoT 数据的 base 模型: Ling-mini-2.0 在 AIME25 上从 2.08 升到 43.75, MATH 从 61.96 升到 82.52, 但也有个别项目略降, 例如 CMath 从 92.81 到 92.08. CoT 预激活的收益集中在难的推理题上.

多语言数据约 2TB, 占预训练语料的 4%, 覆盖约 30 种语言. 附录 B.2 的观察比较实在: 罗曼语族和日耳曼语族的数据对中英文基准影响小, 斯拉夫语族和阿拉伯语, 日语等质量较低的数据可能带来明显负面影响. 于是配比定为罗曼语族约 50%, 日耳曼语族约 10%, 斯拉夫语族约 3%, 其余为其他语言.

## 7. 训练配方与 WSM 调度

优化器是 AdamW, β1=0.9, β2=0.95, weight decay 0.1, 梯度裁剪 1.0. batch size 在前约 500B token 从 3024 线性爬升到峰值, 之后保持不变. 学习率用 WSM (warmup-stable-merge) 调度: 前 2000 步线性 warmup, 然后恒定学习率一直训到结束, 不做学习率衰减.

那么常规做法里衰减带来的 「退火」 收益从哪来? WSM 的答案是 checkpoint 合并. 训练末段挑出验证表现最好的若干 checkpoint 做平均, 用合并去近似衰减的效果. §3.2.3 和图 7 显示, WSM 相比 WSD 基线在各类基准上平均高 1 到 2 分, 而且在同样条件下做 5 个 epoch 的 SFT 之后, 优势仍然保留. 更实际的好处是不必事先决定什么时候开始衰减, 衰减多少 token, 训练可以随时接续.

这个选择和 wind tunnel 是配套的. 如果每次实验都要预设衰减计划, 不同预算的实验很难共用中间 checkpoint; 用恒定学习率加合并, 同一条训练曲线上任取一段都能合并出一个 「退火后」 模型, 小规模试验和最终训练共享同一套流程, 外推也更可靠.

## 8. 后训练: DFT, Evo-CoT, LPO 与 GAR

后训练第一步是 DFT (Decoupled Fine-Tuning). 它用两种系统提示构造 SFT 数据: Instant Response 对应 「detailed think off」, 直接给出回答; In-Depth Reasoning 对应 「detailed think on」, 先写长 CoT 再给答案. 这里要把两件事分开: 发布的三个模型是 non-thinking (instruct) 模型, 指的是默认对外的形态, 不单独提供思考版本; DFT 里的两种模式是训练时的数据构造手段, 目的是在同一个模型里先建立一条深度推理通道, 为后续 RL 打底. 深度思考方向的产品是同一基座上的 Ring 系列, 不在这份报告的三个模型里.

DFT 之后是 Evo-CoT (Evolutionary Chain-of-Thought). 奖励由正确性, 动态长度控制, 格式三部分组成. 长度项的原则是 「难题多想, 易题快答」: 简单任务用较大的系数 α 鼓励简短, 难任务用较小的 α 允许多写步骤; 答错时, 过长的回答受更重的惩罚, 正的长度奖励被截掉. 格式项规定, 如果输出里出现显式的 `<think>` 标记, 奖励 −0.5, 保证模型保持 non-thinking 的外在形态. 这一部分才真正涉及 TestingTime: 模型在回答时根据题目难度决定多写几步推理, 本质上是在推理阶段按需分配计算. 图 13 画的就是 AIME25 上准确率和平均输出长度的关系, 论文用它说明 Ling-1T 在推理准确率和平均推理长度之间取得了较好的平衡, 也就是 §4.6 所说的 「efficient thinking and precise reasoning」.

RL 算法是 LPO (Linguistic-unit Policy Optimization), 以句子为动作单元做重要性采样和裁剪, 裁剪区间 ε 取 0.03. 句子按常见停顿标点在去 token 化之后切分, 优势按 token 总长归一化. 与 GRPO, GSPO 相比, 奖励曲线更平滑, 不容易出现平台或崩塌, 引言称在复杂推理基准上约有 10% 的提升. 选择 RL 起点时用 ApexEval, 它衡量的是在最优提示下题目能否解出, 而不是 DFT 之后受格式约束的直接准确率, 因为 DFT 压制了显式 CoT, 普通准确率会低估 RL 潜力.

开放式主观任务用 GAR (Group Arena Reward) 和 RubriX. GAR 在同一组候选回答内部做两两比较, 降低绝对打分的噪声; RubriX 是细粒度, 多维度的评分准则框架. 引言给出的效果是开放式评测的一致性分数提高 2% 到 10%. 奖励系统本身也有工程数字: 支持 40K 并发, 成功率 99.9%. 这些数字说明 RL 阶段的瓶颈有相当一部分在奖励服务上, 而不只在策略模型.

## 9. 结果表该怎么读

Table 8 是 Ling-1T 对比 DeepSeek-V3.1-Terminus (non-thinking), Kimi-K2-Instruct-0905, GPT-5-main 和 Gemini 2.5 Pro (low think). 强项集中在数学和代码: AIME25 为 70.42, 略高于 Gemini 2.5 Pro 的 70.10, 明显高于 DeepSeek 的 55.21; AIME24 为 80.21; LiveCodeBench 为 61.68, 比第二名高十几分; CodeForces rating 1901; ARC-AGI-1 为 43.81, 其余四个模型都在 23 以下; ZebraLogic 90.80, OptMATH 57.68. 写作和对齐类的 Writing Bench 89.40, Creative Writing v3 89.24 也在前列.

弱项同样清楚. HLE 只有 7.60, 低于 DeepSeek 的 10.38 和 Gemini 的 12.07; MedXpertQA 22.33, 与 Gemini 的 44.82 差距很大; GPQA-Diamond 72.98, 低于 DeepSeek 的 76.23; Aider-Edit 83.65, 在五个模型里最低; IFEval 86.11, 与第一名 Kimi 的 90.99 差近 5 分; HMMT25 47.08, 远低于 Gemini 的 60.73. 这些项目偏重专业知识广度, 精确指令遵循和代码编辑, 与结论一节承认的 「复杂指令遵循和智能体行为仍在开发」 一致.

读这张表时还要记住对照组的设定. 对手全部是 non-thinking 或低思考档位, 所以比较的是 「快速回答」 模式下的能力. Ling-1T 的数学分数高, 与 Evo-CoT 有关: 它让模型在不打开显式思考标记的前提下, 仍可按题目难度写出推理步骤; 图 13 把平均输出长度和准确率画在一起, 就是为了把这部分代价也摆出来. 如果对手换成完整思考模式, 排名会不同, 那属于 Ring 系列和其他思考模型的比较范围.

较小的两个模型也各有对照. Table 6 里 Ling-mini-2.0 的 LiveCodeBench 为 41.69, CodeForces rating 1410, 高于 Qwen3-8B (non-thinking) 的 26.10 和 624; Table 7 里 Ling-flash-2.0 的 LiveCodeBench 为 51.38, CodeForces 1600, 高于 Qwen3-32B (non-thinking) 的 31.50 和 696. 这两组对比和 7 倍效率杠杆的叙述呼应: 激活参数小很多的 MoE 模型, 在推理密集的任务上可以追平甚至超过更大的 dense 模型.

## 10. 基础设施: FP8, 流水线与稳定性

Ling 2.0 号称是完全用 FP8 训练的最大开源模型. 量化是细粒度分块: 激活和梯度按 [1,128] 分块, 权重按 [128,128] 分块, 配 FP32 缩放因子. 在 Ling-1T 上跑了 900B token, 相对 BF16 的 loss 差在 0.25% 以内, 平均约 0.1%. FP8 Training Safeguard System 监控两个指标: underflow (量化后变零的比例) 和 distortion (原矩阵与重建矩阵的余弦相似度). 最终 FP8 为 Ling-1T 带来约 15% 的 MFU 提升. 配套的两项优化是按需转置权重 (权重显存减半) 和 padding routing map (消除 padding 带来的 CPU 开销).

图 14 给出 MFU 的逐项提升路径: 起点 16.9% 已经是 FP8 下的基线, 异构细粒度流水线把它拉到 23.8%, 相对提升约 41%, 与 §5.2 说的 40% 对应; 再叠加节点内 DeepEP, 融合算子, 快速专家重计算等优化, 最终到 31.4%, 接近随机路由参考值 32.8%. 分项数字包括: DeepEP 减少通信冗余带来 2% 端到端加速, 算子融合再加 13%; 快速专家重计算在小模型上提升约 10%, 大模型约 7%; VPP 从 2 加到 4 在路由均衡时再得 5%.

有效训练时间比 (ETTR) 这一侧, checkpoint 保存时间从 269 秒降到 30 秒, 占总训练时间的比例从 2.43% 降到 0.82%; 预热小 batch 让第一个训练步提速约 30%. checkpoint 间隔定为 48 分钟, 依据是附录 A 的一个简单模型: 每天的损失 E = 1440C/s + Fs/2 + FA, 对 s 求最优得 s = √(2880C/F). 由 48 分钟只能反推出 C/F = 0.8 这一比值, 论文没有分别给出 C 和 F. 式 5 末尾写成 「≈54CF」, 按前一项 2√(720CF) 计算应为 54√(CF), 是一处笔误.

§5.6 的 「苦涩教训」 值得一读. DualPipe 这类计算与通信重叠的方案在 Ling 2.0 上端到端收益有限, 原因有两条: 重叠需要大 EP 配置, 而大 EP 下每个 rank 专家更少, 最慢 rank 的拖累更明显; 浅层 MoE 路由更不均衡, 容易 OOM, 迫使 PP 切分做出让步. 论文没有回避这个负面结果, 这对想复现类似方案的团队很有参考意义.

## 11. 软件工程, 评测流水线与数据基础设施

§5.4 把训练框架的开发单独拿出来讨论, 提出 Foundation LLMs Software Engineering 的说法. 作者列了三个与传统软件不同的难点: 结果难以预判, 很多缺陷要到发布后期才暴露; 算法和工程必须在设计早期就一起权衡; 训练和推理常常部署在异构硬件上, 精度和性能各不相同. 针对这些难点, 他们提出 4C 原则, 即 Correct, Consistent, Complete, Co-Design. 落到流程上, 是一个 「渐进式估计, 发布审批, 任务监控与抽样分析, 经验积累」 的循环, 每次框架升级先在最多约 3% 的实际训练资源上验证, 达标才允许上线.

协同设计有几个具体例子. Norm Head 带来的效果提升不到 1%, 却明显增加单个 PP stage 的计算和显存, 于是 Ling 2.0 放弃了它. Ling-1T 设计时把 dense 层与 MoE 层的计算消耗比定为 1:2, 方便让各个 PP stage 的计算时间一致, 减少流水线气泡. 图 20 的算子效率分布显示, Ling 2.0 的矩阵乘效率集中在中段, 没有特别低效的算子, 作者把这归功于 First-K-Dense 缓解了浅层 MoE 的负载不均. 跨平台方面, 图 21 对比了 Ling-flash-2.0 在 Hopper 与非 Hopper GPU 上的 loss, 差值围绕零振荡, 均值在千分之一以内.

评测也被当成训练的一部分来改造. §5.5 基于 OpenCompass 重写了评测流水线: 单节点放不下的模型在 Ray 集群上分布式运行, 对接 SGLang 推理后端; 对 few-shot 模板这类重复前缀做前缀级缓存, 吞吐提高 30% 以上; 预处理, 推理和后处理并行化, 小请求自动合批. 合起来, 每个 checkpoint 跑完全部评测所需的总时长减少三分之二以上, checkpoint 可以在数小时内完成验证. 对一个要频繁挑 checkpoint 做合并的 WSM 流程来说, 评测提速直接决定了合并的节奏.

数据侧的基础设施写在附录 B.3. 第一条原则是 Data-as-Code, 把整条数据处理流水线代码化并纳入版本控制, 配一个包含 50 多个算子的 AIDataOps 库, 接入 CI/CD, 让每个数据点的来源都可追溯, 新特性的开发和回填周期从数月缩短到数天. 第二条原则是统一的数据湖仓和逻辑宽表, 把分散在数百个独立数据集里的网页和代码数据收拢到一张表里, I/O 超过每小时 20 TB. 论文举的例子是在两天内处理了 300 亿条可训练数据. 这部分篇幅不长, 但前面 20T token 的配比调整和逐阶段提高推理数据占比, 都要靠它才能快速迭代.

## 12. 局限与后续方向

结论一节列了三个开放问题. 第一, GQA 在长上下文场景下效率受限, 后续在探索线性注意力和稀疏注意力. 第二, 有效推理长度和深度还有提升空间, 这和结果表里 HLE, HMMT25 的差距对得上. 第三, 复杂指令遵循和智能体行为仍在开发, IFEval 和 Aider-Edit 的分数也印证了这一点. 这些都是作者自己承认的边界.

从整份报告看, Ling 2.0 的核心主张是一条链: 用 Scaling Laws 在训练前定好架构和超参, 用 wind tunnel 低成本验证每项改动, 用高推理占比的数据和 CoT 预激活把推理能力提前种进 base 模型, 再用 DFT 和 Evo-CoT 让 non-thinking 模型按题目难度决定写多少步. FP8 和异构流水线则保证这条链在万亿参数上跑得动. 深度思考的版本交给 Ring 系列, 这份报告只负责打好这个共同的基座.

对读者来说, 最容易读错的地方都集中在数字的归属上: 16B 和 1T 是两个不同模型的总参数; 7 倍的分母是 MoE 达到同等 loss 所需的计算量; 3.5% 的激活比把共享专家和 top-8 分开计算; non-thinking 描述的是发布形态, DFT 的两种模式是训练手段. 把这几处对清楚, 表格和图里的其他数字就不难理解了.

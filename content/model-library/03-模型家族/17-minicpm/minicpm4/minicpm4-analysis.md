# MiniCPM4 技术报告解读：8B 端侧模型怎样把长上下文做快

## 1. 定位：一份以端侧速度为目标的全栈报告

MiniCPM4 是 OpenBMB 在 2025 年发布的端侧大语言模型，有 0.5B 和 8B 两个稠密版本，之后又在 8B 上做出混合推理模型 MiniCPM4.1。报告（arXiv 2506.07900v2, 44 页）开头给了两个主结论：预训练只用了 Qwen3-8B 约 22% 的 token 就追平它的基准成绩；在端侧设备上处理 128K 长度文档，速度是 Qwen3-8B 的 7 倍。前一个说的是训练花多少数据，后一个说的是部署时每秒能吐多少 token，两件事的证据分散在报告不同章节里，读的时候要分开看。

报告按 「架构，数据，训练算法，推理系统」 四个方向组织，每个方向都起了一个名字：稀疏注意力 InfLLM v2，数据过滤 UltraClean 和 SFT 数据 UltraChat v2，超参数搜索 ModelTunnel v2，强化学习里的分块 rollout，三值量化 BitCPM4，推理框架 CPM.cu 和部署系统 ArkInfer。最后两节是两个应用，综述生成 MiniCPM4-Survey 和工具调用 MiniCPM4-MCP。这种写法信息量大，缺点是每一块都写得比较散，模型本身的层数，头数，隐藏维度这些基本配置全文都没有列出来。

这里的 「效率」 指的是端侧推理吞吐和训练成本，衡量方式是 Jetson AGX Orin 和 RTX 4090 上预填充与解码的 token/s，以及训练 token 数和 GPU 小时。它和 「推理时多算几步换精度」 那类做法没有关系，报告里 8B 模型并没有靠延长推理计算来刷分。下文按报告顺序逐块讲，最后再把正文与表格对不上的地方集中列一遍。

## 2. InfLLM v2：让解码也能吃到稀疏的好处

InfLLM v2 是整份报告的核心。做法是把 KV cache 按固定大小 m 切块，每个 query token 只和得分最高的 k 个块做注意力。块得分的算法是关键：先用更细的 「语义核」 覆盖整条 key 序列，核大小 p = 32，步长 s = 16，相邻核重叠一半；每个核取 key 的均值作为表示，与 query 做点积后过 softmax；一个块的得分取所有与它相交的语义核里的最大值。开头块和局部窗口块的得分直接设为无穷大，所以总会被选中。同一个 GQA 组内的 query head 先把得分取平均，再共享同一组 top-k 块，这样一次访存能服务整组 head。

和 MoBA，NSA 的区别报告讲得比较清楚。MoBA 把 query 也切块，块内 query 共享同一批 KV 块，这对预填充有效，但解码时每步只有一个新 token，凑不成完整的 query 块，训练和推理就不一致。InfLLM v2 的 query 粒度是单个 token，KV 粒度是块，所以解码阶段同样能稀疏。NSA 用三个注意力分支捕捉长距离信息，带来额外参数和三倍的 KV 存储，短序列也要多付开销；InfLLM v2 的语义核用无参数的均值池化，序列短到不超过 k 个块时就退化成普通稠密注意力。报告称其块选择比 NSA 少 60% 的计算。由于 top-k 不可微，语义核的表示无法直接从第二阶段得到梯度，均值池化的另一个好处是让核表示和 key 待在同一个语义空间里，优化 key 就间接优化了核。

块选择本身会成为新的瓶颈。计算每个语义核的得分要做 softmax，再沿 query 组聚合，这几步不满足交换律，用不上 FlashAttention 的 online softmax，需要对语义核扫两遍，第一遍求 LogSumExp。报告的办法是用更粗的核（大小 s_c 远大于 s）近似 LSE，把第一遍的开销压到 s/s_c. 复杂度分析里，第一阶段每个 query 要和 l/s 个核打分，整条序列累计仍是 O(l^2)；第二阶段是 2km 次运算，与 l 无关。报告说稠密是 2l 次，稀疏可以降到 1/s，按它自己的计数其实是 1/(2s)，口径差一倍，但结论方向不变：长序列下主要开销在选块，后续优化也该放在这里。

硬件约束也写进了设计。受 tensor core MMA 指令形状限制，一个 query 组至少要有 16 个 head。可是报告没给 MiniCPM4 的 head 数，KV head 数，块大小 m 和选块数 k，只在长上下文评测里说每个 token 只看约 6K 个上下文 token。第 6 页的 「81% 注意力稀疏度」 与第 31 页的 「128K 上稀疏度只有 5%」 方向相反，前者是跳过的比例，后者是保留的比例；如果每个 token 固定看 6K，19% 的保留率大约对应 32K 上下文，正好是训练长度，但这只是按数字推出来的读法，报告没有说明。

## 3. 数据：先把验证做便宜，再谈过滤

UltraClean 的出发点是：数据分类器好不好，最终要看用它筛出的数据训出来的模型好不好，而正常验证一次要在 1B 模型上训 100B token，约 1,200 GPU 小时。报告的高效验证借鉴了 Llama 3.1 的退火评估：先用 WSD 把一个 1B 模型训到 1.1T token，之后每次只做 10B token 的两阶段退火，其中 30% 换成待验证数据，70% 保持默认配比，与不换数据的退火做对比。一次验证约 110 GPU 小时，即 32 张卡不到 3.5 小时。验证变便宜之后，种子数据的挑选就可以闭环：候选种子先过验证，能提升退火效果的才当正样本，分类器筛出的数据再过一遍验证，不行就调配方。

分类器用 fastText 而不是 LLM。报告给的对比是，处理 15T token，LLM 分类器约 6,000 GPU 小时，fastText 在 80 核 CPU 服务器上不到 1,000 小时。超参数也列得很全：向量维度 256，学习率 0.1，最大 n-gram 3，最小词频 5，训练 3 轮，推理阈值 0.5，分词用 DeepSeek-V2 的分词器并保留换行等结构符号。负样本从 FineWeb，C4，Dolma，The Pile，RedPajama 和 CCI3 等多个来源抽取，报告认为来源多样对跨领域泛化帮助明显。把这套流程用在 FineWeb 和 Chinese FineWeb 上，得到的数据叫 UltraFineWeb。

表 2 用 1.2B 模型各训约 100B token 比较。英文九项平均 UltraFineWeb-en 45.891，FineWeb-edu 44.560，FineWeb 42.278；正文把 FineWeb 写成 42.287，差值 3.61 本身没错。中文部分正文有两处对不上：C-Eval 和 CMMLU 上的 0.31 与 3.65 都是相对 Chinese-FineWeb 的差值，正文却说成分别相对两个数据集；相对 Chinese-FineWeb-edu-v2 的 CMMLU 差值是 1.13，正文写成 0.13。平均分的 1.98 和 0.61 与表一致。这些笔误不改变结论，但引用单项数字时应以表为准。

推理密集型数据走生成路线。通用种子来自分类器筛出的高质量网页，领域种子是人工挑选的数学，代码，自然科学教材和问答；用 10B 以下的开源模型对网页做去噪，整合和补全逻辑，再按 「教科书」 和 「论坛」 两种范式合成：前者是知识点加多轮讲解加练习，后者是围绕一个话题的多轮问答和争论。合成结果会回流到种子池参与下一轮。SFT 阶段的 UltraChat v2 覆盖知识，推理，指令遵循，长上下文和工具使用五类；其中长上下文数据把原文档随机插进检索来的干扰文档里，总长度在 8K 到 64K 之间均匀分布，函数调用数据在调用前加一步 CoT，代码解释器数据要求 10 次内解出，否则丢弃。

## 4. ModelTunnel v2 与预训练工程

ModelTunnel 是 MiniCPM 系列的 「风洞」：在几百万参数的小模型上搜超参数，再迁移到大模型。v2 的主要改动是换了性能指标。小模型在下游任务上往往接近随机，开源语料上的 LM loss 又和下游表现关系不紧，于是报告从下游任务的验证集构造 ScalingBench：让 GPT-4o 为每道题写出推理步骤，然后计算模型在给定题目时生成 「推理步骤加答案」 的条件 loss。用 0.36B 到 4B 的一批内部模型拟合，ScalingBench loss 与下游分数呈 sigmoid 关系，7B 和 80B 两个模型作为不参与拟合的检验点。

图 4 的八个子图里，MMLU，BBH，MATH，HumanEval 和平均分这几格检验点贴着曲线；CMMLU 和 CEval 各有一个点高出曲线约 10 分，MBPP 两个点都在曲线下方。报告也没说哪个三角是 7B，哪个是 80B，没给拟合优度。所以这张图能说明趋势，不宜拿来精确换算分数。另一项实验比较了 µP 与 StepLaw：三档规模（150M, 360M, 700M）共 16 个格子，普通架构加 StepLaw 超参数更优的有 10 格，µP 更优的有 6 格，最大差值 0.0156；表 3 的 GPU 小时一列写的是 1M 对 32。报告据此认为 µP 配合廉价搜索与 StepLaw 效果相当，成本低得多，这个判断和数据是相符的。

预训练工程有两项。一是多 token 预测：额外预测头是一层 Transformer，与主模型共享嵌入层和输出头，输入是主模型隐向量与下一个 token 嵌入各自归一化后的拼接，目标是预测再往后一位的 token，总损失为 NTP 加 λ 倍 MTP。这个头在推理时还能当投机采样的草稿，报告提到它提高了接受长度。二是 FP8 混合精度：权重按 128×128，激活按 128×1 分块在线量化，累加器用 FP32，只在线性投影的前向和输入梯度上用 FP8，权重梯度保留 BF16。

训练流程在第 29 页：稳定阶段 7T token，学习率 7 × 10^-3；退火阶段 1T；上下文从 4K 扩到 32K，用 20B token 和 LongRoPE；之后靠 YaRN 外推到 128K. 合计约 8.02T. 但第 6 页写的是 8.3T，退火 1.3T，表 8 又记 8T. 22% 这个比例是按 8T 对 Qwen3 的 36T 算的，用 8.3T 算是 23%，结论不受影响，只是退火到底用了多少 token 报告没有统一。

## 5. 后训练与分块 rollout

MiniCPM4.1 的推理能力来自两步：先用长 CoT 蒸馏数据做 SFT，给端侧小模型一个能起步的初始化，再做强化学习。RL 数据以数学（DAPO, Deepscaler, Numina, Prime）和代码（LeetCode, TACO, Kodcode, Codeforces）为主，用 Semhash 去重，并用 DeepSeek-R1-Distill-Qwen-1.5B 对每题生成四个答案，四个全对的题删掉，代码数据做上采样。算法是改造过的 GRPO，加了动态采样（删掉全对或全错的题），clip-higher，token 级损失，以及被截断样本不计损失。这些都是 DAPO 一路已有的做法。

分块 rollout 针对的是 RL 采样里的长尾：一个批次里少数超长回答会让其余 GPU 空等。做法是每轮只允许每条轨迹生成固定长度的一块，写完的进训练，没写完的保存对数概率，与下一批新题合并继续写。代价是同一条轨迹的不同块出自不同版本的策略，带来离策略偏差。报告为此加了四项稳定措施：按块做重要性采样，分母用生成该块时的策略；dual-clip 在优势为负时再加一道截断；保留系数 0.001 的 KL 惩罚并定期更新参考模型；乱码过滤器把重复或损坏的轨迹排除在损失之外。

实验在 64 张 A800 上用 1.5B 模型跑 150 步。表 5 里普通 rollout 每步 488.57，采样 392.61；Chunk-8k 是 286.31 和 173.97，约为基线的 0.59 和 0.44；Chunk-4k 采样更快，但每步时间几乎不变，因为块越小，重算对数概率越频繁。性能上 Chunk-8k 的 AIME 2024 是 34.79，还略高于基线的 32.91。表题说时间做了归一化，可基线行并不是 1，单位也没交代，只能按比值读。正式训练的设置是 batch 256，mini-batch 128，恒定学习率 1e-5，最大回答长度 32,768，每题 16 个 rollout。

这一节还有几处编号问题：正文说完整算法见 「算法 4」，实际只有第 20 页一个算法 1；式（8）只有编号没有内容；表格从表 3 直接跳到表 5；正文叫 「Naive」 的基线在表里叫 「Vanilla」。都不影响理解，引用时注意即可。

## 6. BitCPM4：从高精度模型出发做三值 QAT

BitCPM4 只把权重量化成三值，激活不量化。报告的理由是，对极低比特模型来说，量化激活会增加 QAT 开销，却不会明显降低端侧推理成本。和 BitNet 从头 QAT 不同，BitCPM4 用训好的高精度检查点初始化。先在 ModelTunnel 里用 5M 模型，2B token 做预实验：固定总 token，前一段训 FP8 模型，后一段 QAT 成三值，调整两段比例。结论是 QAT 占比超过 40%，即学习率衰减阶段的两倍时，最终 loss 已接近从头 QAT；第二段开始时需要重新预热学习率，第一段用 1e-2，第二段用 5e-3. 150M 模型上的验证结果相同。

图 5 读起来要小心。图题说横轴是 「QAT token 比例」，坐标轴写的却是 「FP8 token 占比」，两者互补。横轴 0 就是从头 QAT，loss 约 3.14; 0 到 60 之间在 3.14 到 3.24 起伏；到 70（QAT 只剩 30%）跳到约 3.38。这和正文 「QAT 超过 40% 就够」 吻合。图题说比例是占完整稳定阶段 token，正文说的是占总训练 token，口径也没统一。

最终两个三值模型共用 350B token，BitNet-2B 用 4T，比例是 8.75%，报告说 「10%」 和 「少 10 倍」 都是取整。表 6 里 BitCPM4-0.5B 在 MMLU，CMMLU，CEval，BBH 四项上领先 Qwen3-0.6B，但在 GSM8K（25.55 对 61.71），MATH500（10.20 对 50.20）等数学代码项上落后很多，平均 39.84 低于 44.93。所以 「超过 Qwen3-0.6B」 只对知识类任务成立，报告自己也承认小模型的推理能力受限。BitCPM4-1B 平均 56.03，高于 BitNet-2B 的 43.31，这是三值路线里比较有说服力的一组数。报告还提到极低比特模型的算子支持是后续工作，也就是说目前的三值模型更多是训练方法上的验证，端侧上跑多快报告没有给数据。

## 7. CPM.cu 与 ArkInfer：把算法落到芯片上

CPM.cu 是针对端侧 NVIDIA 芯片的轻量 CUDA 推理框架，有静态内存管理和算子融合，为 EAGLE-2 式的树状投机采样写了专门的注意力算子和融合验证算子，并集成了 InfLLM v2 的稀疏注意力算子。在这个框架上，团队发现端侧投机采样的瓶颈在草稿模型的 LM head：草稿模型只有一层 Transformer，词表却很大，输出层反而最贵。FR-Spec 的做法是按语料频率只保留前 25% 的词表给草稿模型，这部分覆盖 95% 的 token 出现次数，LM head 计算降到四分之一。验证阶段目标模型仍用完整词表，所以输出分布与标准投机采样完全一致，这是它能即插即用的前提。

量化方面有两条线。P-GPTQ 针对的是开头几个 token 的巨大激活：PrefixQuant 已经把这些位置的 KV 预先存下来，解决推理时的激活离群；P-GPTQ 进一步在算 GPTQ 的 Hessian 时丢掉前 s = 4 个位置，因为这些位置的激活比后面大 10 倍，会主导协方差。在全部线性层按组 INT4, 1,024 条校准序列的设定下，表 7 平均分 FP16 为 75.58，GPTQ 74.31，P-GPTQ 74.76，叠加 AWQ 平滑的 S-P-GPTQ 74.91 最好。SpecMQuant 研究投机采样和量化的配合：目标模型是 W4A16 时访存瓶颈已缓解，验证更多草稿 token 的时间涨得更快，应该少起草；草稿模型若用 GPTQ 量化会大幅降低接受率，所以改用第 3.3 节的 QAT。

长上下文下还有两处细节：目标模型用 InfLLM v2 做树状验证时，只为最后 n×n 区域构造二维掩码并用 uint64 位打包；草稿模型按 TriForce 的做法用滑动窗口注意力，避免全注意力拉长首 token 延迟。这些都是让 7 倍解码加速在 Orin 上成立的具体条件，单靠稀疏注意力算法本身达不到。

ArkInfer 解决的是另一类问题：端侧芯片碎片化。它把联发科 NeuroPilot，高通 Genie，瑞芯微 RK-LLM，TensorRT-LLM 和 CPU 上的 llama.cpp 接成可替换的后端，上面是一层适配器，统一的 Tensor 结构，KV cache 管理器，以及以 「执行器」 为单位的调度接口。与硬件耦合松的优化（BiTA 投机解码，基于 Guidance 的约束解码）只实现一次就能在所有后端上用；与硬件耦合紧的量化和稀疏化则交给各后端。另外还有一个模型库前端和自动格式转换流水线。这一节没有任何性能数字，更像系统设计说明。

## 8. 评测怎么读

标准评测（表 8）里，MiniCPM4-8B 平均 81.13，略高于 Qwen3-8B 的 80.55，也高于 Gemma3-12B 和 Phi4-14B；MiniCPM4-0.5B 高于 Llama3.2-1B 和 Gemma3-1B. 报告强调几款基线用了知识蒸馏，MiniCPM4 只用真实标注作监督。正文写的基线是 Qwen3-0.5B，表里是 0.6B，表里还多一列 LLaMA3.1-8B 正文没提，这类小出入不影响排序。表 8 的 「# Train Data」 一行把 MiniCPM4-0.5B 记为 1T，MiniCPM4-8B 记为 8T，两个 Qwen3 都记 36T。

深度推理评测（表 9）问题更明显。正文说 MiniCPM4.1-8B 全注意力平均 79.93，稀疏版 79.14，差 0.79；表 9 的平均行是 80.17 和 79.69，差 0.48，用 15 项逐列重算也与平均行一致。所以表是自洽的，正文数字找不到出处。另外稀疏版 79.69 比 R1-Qwen3-8B 的 79.72 低 0.03，「超过同规模模型」 严格说只适用于全注意力版。结论方向没变：稀疏化的损失不到 1 分。

长上下文有两组数。RULER-NIAH 用 YaRN 扩到 128K，图 7 的热力图所有长度和深度都是满分；图题写 「长序列预填充的评测结果」，但画的是准确率，不是速度。RULER 32K（表 10）上稀疏版加权平均 85.84，全注意力 88.93，差 3.09 个百分点，差距主要在 NIAH-MK（87.33 对 100）。比起 NIAH 的全绿，这组数更能反映稀疏注意力在多键检索上的真实损失。

速度数据全在第 1 页图 1。按图目测：Orin 上 128K 解码 MiniCPM4-8B 约 46 token/s，Qwen3-8B 约 6，七倍多；32K 时约 59 对 14，约 4 倍；4090 上 128K 解码约 148 对 28，约 5 倍；4090 上 128K 预填充约 2.5 倍。引言和效率评测说 7 倍，结论说 5 倍，其实对应的是不同芯片和不同长度。引用 「7 倍」 时应带上条件：Jetson AGX Orin，128K 上下文，解码阶段，对比 Qwen3-8B，且包含投机采样和量化等整套系统优化。预填充图还有一根没有用途的右侧纵轴，按左轴读即可。

## 9. 两个应用：综述生成与 MCP 工具调用

MiniCPM4-Survey 按 「规划，检索，写作」 循环生成长综述。数据方面，从 Kaggle 收集约 271 万篇 arXiv 摘要，用 MiniCPM-Embedding-Light 加 Faiss 建检索库，按 Query2Plan 和 Plan2Survey 两阶段合成 3,750 和 61,684 条训练样本。训练是 SFT 冷启动，然后章节级 RL，再综述级 RL。奖励体系（表 11）覆盖规划，检索，内容写作和引用四类能力，大部分由 LLM 打分，结构相似度，长度，语言和引用是否在检索结果中等由规则判断。上下文管理器负责更新提示，记录历史和分配优势，检索和评估服务并行部署以降低 RL 延迟。

表 12 的结果：MiniCPM4-Survey 内容质量均分 3.50，与 OpenAI Deep Research 持平，事实分 68.73，明显高于 AutoSurvey 的 46.56。从 SFT 到 RL，覆盖度，深度，新颖性都上升，均分从 3.11 到 3.50，事实分从 50.24 到 68.73；但相关性从 3.55 降到 3.45，正文没有提。测试集只有 20 条，评委是 GPT-4o，分差在 0.1 量级时要谨慎看待。此外表题说 Webthinker 用的是 WTR1-7B，正文基线描述却写用 DeepSeek-R1-Distill-Qwen-7B；正文说 「四项指标」，实际列了五项。

MiniCPM4-MCP 的数据有三个来源：用接了 MCP 服务器的客户端重跑已有数据集的查询，保留结果与原标注一致的轨迹；让 Claude-3.7-Sonnet 根据工具描述反向构造必须调用某个工具（或同一服务器下两个工具）的查询；把公开函数调用数据转成 MCP 格式，约 14 万条。人工检查通过的作测试集，只过了 LLM 检查的作训练集。环境用 Docker 部署常用 MCP 服务器，并做了工具质量检查：让 Claude-4 为每个工具写 10 条查询，通信成功率 100% 的工具才暴露给模型。

表 13 的加权平均里 MiniCPM4-MCP 三项（函数名 88.3，参数名 76.1，参数值 51.2）都最高。但按服务器看，Arxiv 一行它的函数名只有 57.1，低于 Qwen3-8B 的 81.8 和 GPT-4o 的 85.7；Github 一行参数名只有 25.7。按 16 行简单平均，参数名和参数值两项反而是 GPT-4o 更高（77.5 对 75.8, 58.0 对 51.6），而各服务器的样本数报告没列，加权平均无法复算。正文说 MiniCPM4 对 arXiv，airbnb 这类较新工具比 Qwen3 更熟，airbnb 成立，arXiv 的函数名一项不成立。还有一点：第 6 节开头说 「三个应用」，列出来只有这两个，目录里也只有 6.1 和 6.2。

## 10. 留下的问题

第一类是缺失的信息。模型的层数，隐藏维度，query head 数，KV head 数，InfLLM v2 的块大小 m 和选块数 k，报告都没有给，「每组至少 16 个 head」 这条约束在 MiniCPM4 上如何满足也就无从核对。81% 稀疏度是在多长的序列上统计的，5% 与 81% 两个口径如何换算，也要读者自己推。表 13 的加权平均缺样本数，表 5 的时间缺单位，这些都让部分结论只能按比值或趋势来读。

第二类是正文与表格的冲突：表 2 的差值归属和 0.13 对 1.13，表 9 的 79.93 对 80.17，预训练 token 的 8.3T，8T 和 8.02T，加速倍数的 7 倍和 5 倍，图 5 的横轴与图题，以及算法和表格编号的跳号。逐一核对下来，这些出入都没有推翻报告的主结论：数据过滤确实带来提升，稀疏版和全注意力版相差不到 1 分，端侧长序列解码确实快了数倍。但引用具体数字时，应以表格为准，并写明芯片，长度和阶段。

最后看这份报告能带走什么。最有参考价值的是三处设计：用 「接近训完的模型做短退火」 把数据验证成本降一个数量级；用 token 级 query 加块级 KV 的稀疏注意力让解码也能加速，且短序列不付额外代价；用分块 rollout 缓解 RL 采样的长尾。FR-Spec 这类针对草稿模型输出层的小改动，对所有大词表端侧模型都适用。相比之下，ScalingBench 的 sigmoid 拟合和两个应用的评测样本量偏小，更适合当方向性的证据看。

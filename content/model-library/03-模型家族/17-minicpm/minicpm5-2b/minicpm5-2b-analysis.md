# MiniCPM5-2B 模型卡分析: 2.52B 稠密模型的一页说明书

- 源文: 同目录 `minicpm5-2b.md`, 17 页, 13 张图, 抓自 Hugging Face 上的 openbmb/MiniCPM5-2B 模型页.
- 对照稿: 同目录 `minicpm5-2b-bi.md`, 逐页英文在前, 中文在后.
- 身份: MiniCPM5 系列第二个模型, 排在 MiniCPM5-1B 之后, 2B 档稠密 Transformer, 标准 LlamaForCausalLM 架构.
- 规格: 2,516,756,480 参数, 其中非嵌入 1,981,982,720; 42 层; GQA 16 个 Q 头配 2 个 KV 头; 上下文 131,072.
- 训练: 基座训练 (稳定 + 衰减), 中期训练 (600B + 400B token), 400B token 深度思考 SFT, 16 个 RL 专家经 OPD 合回一个模型.
- 评测: 34 项简单平均 53.9, 对比表里 4B 级最高是 Qwen3.5-4B 的 51.1.
- 许可证: Apache-2.0.

页面同时是产品介绍, 下载目录和部署手册. 它给出的数字足够核对平均分, 重建增益图, 估算权重体积, 但给不出隐藏维度, 词表大小, 头维度, 预训练总 token 数这类结构细节.

下面依次读规格, 训练, 后训练, 评测, 雷达图, 部署和数据, 最后把页面缺的几项集中列出来.

## 1 材料的性质

这一页是 Hugging Face 模型页的整页打印. 前两页是站点侧栏: 点赞 1.68k, 上月下载 619,544, 适配器 15 个, 微调版 48 个, 量化版 88 个, 使用它的 Space 25 个. 第 3 页起才是 README 正文, 标题 「面壁小钢炮MiniCPM」, 顶部链接指向 MiniCPM 技术报告 (arXiv:2506.07900), 中文 Wiki, GitHub 仓库, UltraData 和在线演示.

页面关联的两篇论文, 一篇是 MiniCPM4 的技术报告, 一篇是 2602.09003「Data Science and Technology Towards AGI Part I: Tiered Data Management」. 末尾引用条目也是 MiniCPM4 的 bib. 也就是说, MiniCPM5-2B 在这一页上没有自己的技术报告, 训练方法以 「UltraData 分级数据管理的全链路实践」 这一句挂到 2602.09003 上, 引用则沿用 MiniCPM4.

所以读这一页要分清三类信息. 第一类是规格和数字, 可以直接用. 第二类是流程图和增益图里的数值, 可以拿来互相核对. 第三类是宣传性判断, 例如 「2B 级开源 SOTA」, 它成立的前提是 「在这组对比里」, 页面自己也这么限定.

## 2 规格: 总参数, 非嵌入参数和取整

第 5 页给出的精确参数量是 2,516,756,480, 非嵌入参数 1,981,982,720. 两者相差 534,773,760, 约占总数 21.2%, 这部分属于词嵌入, 可能也包括输出头. 小模型里嵌入层占比高是常见现象: 词表大小不随模型缩小, 隐藏维度却小了, 嵌入矩阵在总数里的比重自然上升. 页面没给词表大小和隐藏维度, 也没说输入嵌入和输出头是否共享权重, 所以这 5.35 亿参数拆不到更细.

侧栏的 「Model size 3B params」 和名字里的 「2B」 需要一起看. 精确值约 2.52B, 侧栏看起来是取整显示, 名字取的是档位. 三个数说的是同一份 BF16 权重. 按 BF16 每参数 2 字节算, 权重约 5.03 GB (4.69 GiB); 4bit 量化的理想体积约为它的四分之一, 实际 GGUF 或 GPTQ 文件还要加上量化元数据, 页面没有给文件大小.

还要分清总参数和激活参数. MiniCPM5-2B 是稠密模型, 每个 token 前向都会经过全部 42 层的非嵌入参数, 这里没有 MoE 意义上的 「激活参数」 一说. 1.98B 是 「非嵌入参数」, 不能当成激活参数引用. 对比表里的 LFM2.5-8B-A1B 就不一样, 名字按常见命名表示总参数 8B, 每 token 激活约 1B, 这两个数衡量的是不同的东西: 前者决定存储和加载成本, 后者更接近每个 token 的计算量. 页面把它归在 「4B-class」 组, 但没有说明分组依据.

非嵌入参数除以 42 层, 每层约 4719 万参数, 除不尽, 说明层外还有少量参数, 例如最终的归一化层. 这只是算术, 页面没有给层内结构.

## 3 注意力与上下文

GQA 写的是 16 个 Q 头, 2 个 KV 头, 也就是每 8 个 Q 头共用一组 K 和 V. 在头维度相同的前提下, KV cache 只有同头数 MHA 的八分之一. 对 131,072 (即 128K) 的上下文来说, 这是能在端侧跑长上下文的主要前提之一. 页面没有给头维度和隐藏维度, 算不出 128K 长度下 KV cache 的具体字节数.

上下文长度有一处对不齐. 模型信息写 Context Length 131,072, 但第 9 页流程图的预训练段写 「Long Decay 32K → 128K → 512K」, 中期训练段又分成 32K 和 128K 两段. 衰减阶段为什么走到 512K, 发布的上下文为什么停在 128K, 页面没有解释. 部署示例里 llama.cpp 的说明只用 -c 8192, 更短, 那是为了示例省资源, 不代表模型上限.

另外, 这一页把长上下文列为优势之一. 评测表的长上下文组里, NoLiMa 一项 MiniCPM5-2B 得 68.1, 同组其他模型最高是 Qwen3.5-4B 的 43.5, 其余七个都在 17.1 以下, LFM2.5-2.6B 只有 0.7. 差距大到这个程度, 值得回头看评测设置, 但页面只说这一项属于内部复现 (没有 † 标), 没有给上下文长度和设置细节.

## 4 训练流程: 从基座到发布模型

第 8 页正文和第 9 页流程图合起来, 训练分三大段. 基座训练先做稳定训练, 再做衰减训练; 流程图里衰减又分 4K 的短衰减和 32K → 128K → 512K 的长衰减, 产出 MiniCPM5-2B-Base. 中期训练分 32K 和 128K 两段, 分别用 600B 和 400B token, 产出 MiniCPM5-2B-Midtrain. 后训练先做 400B token 的深度思考 SFT, 产出 MiniCPM5-2B-SFT, 再做 RL 和 OPD, 产出发布版 MiniCPM5-2B.

这条流水线上的每个中间点都单独发布了: Base, Midtrain, SFT 三个检查点加上最终版, 模型列表里 2B 一共 10 个入口. 这对研究者有直接用处, 想比较 SFT 前后, 或者从 Midtrain 接着做自己的后训练, 都有现成权重. 1B 那一栏只有正式版, SFT, Base, GGUF, MLX 五个入口, 没有 Midtrain.

页面给了中期训练和 SFT 的 token 数, 合计 600B + 400B + 400B = 1.4T, 但没给稳定训练和衰减阶段的 token 数. 400B token 的 SFT 规模相当大, 和中期训练的 128K 段一样多, 说明 「深度思考」 数据在后训练里分量很重. 深度思考模式在 Transformers 示例里对应 enable_thinking=True.

正文说基座训练的作用是 「建立核心语言能力和训练稳定性」, 中期训练 「进一步强化目标能力, 适配目标数据分布」. 对应的语料是 Ultra-FineWeb, Ultra-FineWeb-L3, UltraX, UltraData-Code 和 UltraData-Math, 各阶段怎么配比没有写.

## 5 RL + OPD: 16 个专家合回一个模型

RL 阶段用的是 JustRL II 里描述的基于 critic 的算法, 页面只说它 「大幅提升训练稳定性」, 没有给超参数. RL 并不直接训练发布模型, 而是按领域训练一批教师: 正文列了数学, 代码, 智能体任务, 写作等领域, 流程图把它们归成推理任务 RL, 通用任务 RL, 智能体 RL 三组. OPD 段落给出总数: 16 个专家模型, 其中 5 个是智能体专家.

OPD 的做法写得比较具体. 在回答的每个位置上, 计算学生和教师 logits 之间的全词表反向 KL 散度, 把它当作优势估计, 替换原来基于验证的优势. 换句话说, RL 阶段的优势来自答案能否通过验证, OPD 阶段的优势来自学生分布离教师分布有多远, 而且是在整个词表上逐位置算, 信号比一个最终对错要密. 蒸馏数据直接复用各个 RL 教师训练时用过的 prompt, 不需要另外造语料.

名字上有一处出入. 正文写 On-Policy Distillation, 流程图方框里写 Online Policy Distillation, 缩写都是 OPD. 图中学生从 MiniCPM5-2B-SFT 引出, 教师来自三组 RL, 结构与正文一致, 应是同一步骤. 正文的描述更贴 on-policy 的叫法.

这套安排的思路是先分后合: 单个小模型同时做好数学, 代码, 智能体几件事时, 各领域的 RL 信号容易互相干扰, 于是每个领域先各自训出一个教师, 再用蒸馏把这些教师的分布压回一个学生. 页面没有给出和 「直接在一个模型上做多领域 RL」 的对照实验, 这个思路是否优于后者, 这一页无法判断.

## 6 增益图: 10.96 和 6.96 的复核

第 10 页的增益图把 RL + OPD 的效果按项目列出, 每项分成蓝色的 SFT 基线和紫色的增益. 上栏推理与通用 17 项, 下栏智能体 12 项. 正文说推理与通用平均提升 10.96 分, 智能体平均提升 6.96 分.

上栏 17 项里, 16 项能从基线和终值直接算出增益, 合计 182.65. 10.96 × 17 = 186.32, 差出来的 3.67 就是 HLE 的增益, 图上 HLE 的紫条长度与此吻合. 下栏有两个变数: Terminal-Bench v2.1 的基线没印, GDPval v2 同时给了 AA 口径 19.55 和内部口径 24.07. 按 AA 口径 (增益 3.75) 反推, Terminal-Bench 的增益约 4.12, 基线约 4.5, 和条长对得上; 按内部口径反推, Terminal-Bench 增益会变成负数, 说不通. 所以 6.96 用的应是 AA 口径.

增益分布很不均匀. 最大的几项是 LCB-Pro 25Q2 Easy (+22.7), GPQA-Diamond (+21.6), AIME 2025 (+20.0), SWE-Bench-Verified (+17.4), IFBench (+15.7). 最小的是 BrowseComp Top100 (+1.34), LongBench v2 (+1.59), τ²-Bench Telecom (+4.1, 基线已有 92.98). 可见 RL + OPD 的收益集中在推理, 代码和指令遵循上, 长文档理解和部分搜索任务在 SFT 后已接近这套流程的上限.

图里的项目比主评测表少 5 项: MATH-500, Multi-IF, MMLU-Pro, MMLU-Redux, SWE-bench Pro 没有出现. 所以 10.96 和 6.96 是这 29 项上的平均, 不是主表 34 项上的平均. 图注还说明, 所有 SFT 分数都来自内部评测, 而主表里有 7 项 MiniCPM5-2B 的分数来自 Artificial Analysis, 两处的数值在小数位上略有差别 (例如 GDPval 主表 19.6, 图上 19.55).

## 7 评测表: 34 项简单平均

主评测表对比 9 个模型. 2B 级三个: LFM2.5-2.6B, Qwen3.5-2B, Gemma-4-E2B-it. 4B 级五个: Qwen3.5-4B, granite-4.2-3B, Nemotron-3-Nano-4B, Gemma-4-E4B-it, LFM2.5-8B-A1B. 34 行分成代码推理, 数学推理, 指令遵循, 通用知识, 长上下文, 工具使用, 代码智能体, 搜索智能体, 通用智能体九组, 每组 3 到 5 行.

Average 行是 34 项的简单平均. 逐列相加除以 34, MiniCPM5-2B 得 53.88, Qwen3.5-4B 得 51.14, granite-4.2-3B 得 42.69, 其余各列也都和表中数字四舍五入一致. 这意味着行数多的组 (代码推理 5 行, 通用知识 5 行) 在平均分里权重更大. 如果改成九组各算均值再平均, MiniCPM5-2B 是 54.2, Qwen3.5-4B 是 51.4, 排序不变. 带 † 的 Artificial Analysis 分数和内部复现分数在平均时没有区分.

逐行看, 34 行里 MiniCPM5-2B 拿到全行最高的有 18 行, Qwen3.5-4B 有 12 行, granite-4.2-3B 有 3 行, LFM2.5-2.6B 有 1 行. Qwen3.5-4B 领先的集中在通用知识 (MMLU-Pro 78.0 对 70.8, GPQA-Diamond 77.1 对 70.2, SuperGPQA 52.8 对 40.8), 部分长上下文 (LongBenchPro 58.4 对 44.8) 和两项难度较高的代码智能体 (SWE-bench Pro 28.2 对 14.4, Terminal-Bench v2.1 25.8 对 8.6). granite-4.2-3B 领先的是 IFBench, IFEval 和 Claw-Gym. 所以 「超过所有更大的模型」 指平均分, 知识面和最难的代码智能体任务上, 4B 模型仍然更强.

在 2B 级内部, MiniCPM5-2B 34 行里有 32 行第一, 只有 IFEval (93.4) 和 Multi-IF (76.8) 输给 LFM2.5-2.6B. 差距最大的是智能体类: SWE-bench Verified 46.4, 同级最高只有 6.0; GAIA Text-103 88.7, 同级最高 49.5; NoLiMa 68.1, 同级最高 17.1. 这和页面把 「代码, 数学, 长上下文, 工具使用, 智能体任务」 列为优势是一致的.

表的脚注说蓝色加粗是全行最好, 黑色加粗是 2B 级最好, 但 MinerU 转出的 Markdown 丢了颜色和加粗, 需要靠数字自己比. 另一点是除标 † 的格子外, 其余都是 OpenBMB 内部复现的分数, 基线模型的采样设置和提示格式页面没有写.

## 8 雷达图: 每条轴按最大值归一

第 4 页的雷达图画了四个模型: MiniCPM5-2B, Qwen3.5-4B, granite-4.2-3B, LFM2.5-2.6B. 图注写 「each axis: max = 100%」. 把评测表按九组求均值, 再在这四个模型里按每组最大值归一, 结果和图形对得上: 代码推理组 MiniCPM5-2B 为 100%, Qwen3.5-4B 76%; 指令遵循组 granite-4.2-3B 为 100%, MiniCPM5-2B 93%; 通用知识组 Qwen3.5-4B 为 100%, MiniCPM5-2B 90%; 代码智能体组 Qwen3.5-4B 为 100%, MiniCPM5-2B 79%.

这种归一方式放大了领先者的外观. 每条轴都以四者中的最强者为满分, 所以一个模型在多数轴上领先, 就会画出接近满格的外圈, 而实际分差可能只有几分. 比如数学推理组 MiniCPM5-2B 平均 82.8, Qwen3.5-4B 81.1, 图上是 100% 对 98%. 读雷达图时应该回到表里的原始数字.

雷达图也只选了四个模型, 表里的 Qwen3.5-2B, Gemma-4-E2B-it, Nemotron-3-Nano-4B, Gemma-4-E4B-it, LFM2.5-8B-A1B 没有画进去. 选入的 Qwen3.5-4B 和 granite-4.2-3B 恰好是表里平均分第二和第三的模型, 作为对照是合理的.

## 9 部署: 标准架构和采样参数

页面反复强调架构是标准 LlamaForCausalLM, 「不需要自定义算子, 也不需要分叉模型代码」. 这决定了它能被主流引擎直接加载: 部署表列了 Transformers, vLLM, SGLang, llama.cpp, Ollama, LM Studio, MLX, ArcLight, vLLM Ascend, LiteRT-LM 十个后端, 微调表列了 TRL + PEFT, LLaMA-Factory, ms-swift, unsloth 四个框架, 另外还有 FlagOS 的多芯片支持. 每一项都配 cookbook 文件和 Agent Skill 名, 面向 Cursor / Claude Code 一类代码智能体的用户.

推荐的采样参数是 temperature=1.0, top_p=0.95, min_p=0.0; 出现重复时再加 repetition_penalty=1.05. 页面专门解释了 llama.cpp 的默认 min_p=0.05 为什么会导致重复: 它会过滤掉概率低于最高概率 token 5% 的候选, 而跳出重复循环恰恰可能要靠这些低概率 token. 这是一个和推理框架默认值有关的实际坑, 比泛泛的 「调低温度」 更具体.

工具调用推荐用 SGLang. 模型输出 XML 风格的工具调用, SGLang 内置 minicpm5 解析器把它转成 OpenAI 兼容的 tool_calls. 这说明模型的工具调用格式并不直接是 OpenAI 的 JSON 结构, 换用其他后端时需要确认对应的解析器是否支持.

DSpark 是为 MiniCPM5-2B 专门训练的草稿模型, 用于投机解码, SGLang 里用 --speculative-algorithm DSPARK 开启, 块大小示例取 7. 页面说它 「加速解码, 同时保持目标模型的输出不变」, 这是投机解码经目标模型验证后的通常性质; DSpark 的具体算法, 草稿模型的大小和实际加速比, 页面没有给.

示例代码里有几处被页面右边截断: vLLM, SGLang 和 Transformers 示例的 messages 一行引号未闭合, SGLang 启动命令的端口号缺失, llama.cpp 的 max_tokens 取值缺失. llama.cpp 的说明提到 「-c 8192」, 命令里却没有这个参数. 照抄这几段会出错, 需要按上下文补全.

版本要求: vLLM 0.21 及以上, SGLang 0.5.16 及以上, transformers 5.6 及以上.

## 10 数据开放和对比范围

这一页把数据开放当作卖点之一. 第 4 页列了四个随模型发布的数据集: UltraX (高质量网页预训练数据), UltraData-Code (L0–L3 分级的代码数据), UltraData-SFT-Agent-2609 (500K 条智能体训练样本), UltraData-RL-2609 (80K+ 条 RL 样本, 覆盖数学, 代码, 通用知识和长上下文推理). 第 8 页的训练配方又补了 Ultra-FineWeb, Ultra-FineWeb-L3, UltraData-Math 和 UltraData-SFT-2605, 合计 8 个, 和侧栏标签 「8 datasets」 的数目一致.

各数据集的规模只在第 2 页侧栏露出三个: Ultra-FineWeb 1.29B, UltraData-Math 181M, UltraData-Code 348M, 单位页面没有写. 其余五个没有规模数字. 数据集和训练阶段的对应也只到粗粒度: 预训练和中期训练用前五个, SFT 用 UltraData-SFT-2605 和 UltraData-SFT-Agent-2609, RL 用 UltraData-RL-2609.

对比范围方面, 表中基线全部是开源模型, 最大的是 4B 级. 页面的 SOTA 说法都带着 「在这组对比中」 的限定. 对比表里 LFM2.5-8B-A1B 以总参数计是 8B, Gemma-4-E2B-it 和 Gemma-4-E4B-it 名字里带 E, 通常指有效参数, 页面没有解释这些命名, 也没有说明分组依据是总参数, 激活参数还是有效参数.

## 11 页面没有给的信息

结构方面: 隐藏维度, 中间层维度, 词表大小, 头维度, 位置编码及其参数, 输入嵌入与输出头是否共享, 都没有写. 页面只给了参数总数, 非嵌入参数, 层数, 头数和上下文长度, 这些足够识别它是标准 Llama 结构, 不足以复原配置文件.

训练方面: 稳定训练和衰减阶段的 token 数, 各阶段数据配比, 学习率调度, JustRL II 的超参数, 16 个专家各自对应哪个领域, OPD 的训练步数, 都没有写. 长衰减走到 512K 而发布上下文是 131,072, 也没有解释. 评测方面: 基线的采样参数, 提示格式, 内部复现的具体设置没有写, NoLiMa 这类差距特别大的项目尤其需要这些信息.

这些缺口不影响用这一页选型和部署. 它给了能直接用的规格, 完整的权重形态目录, 可复核的平均分和增益, 以及具体到框架默认值的部署提醒. 需要结构细节时, 应以仓库里的配置文件为准.

# GPT-3 技术谱系分析

来源：Tom B. Brown 等，*Language Models are Few-Shot Learners*，OpenAI，arXiv 2005.14165v4，共 75 页。对照译稿见 [gpt-3-bi.md](gpt-3-bi.md)。

| 条目 | 本文印出的内容 |
| --- | --- |
| 模型族 | 8 个 decoder-only 模型，从 125M 到 175B，只有 175B 叫 GPT-3 |
| 训练量 | 每个模型都训练 300B token，上下文窗口 n_ctx = 2048 |
| 175B 算力 | **3.64E+03** PF-days，约 **3.14E+23** flops（表 D.1） |
| 评测方式 | zero-shot，one-shot，few-shot 三种 in-context 设定，不做梯度更新 |
| 数据 | 过滤后的 Common Crawl，WebText2，Books1，Books2，Wikipedia 五路混合（表 2.2） |
| 附加工作 | 13-gram 污染分析，人类辨别合成新闻，性别/种族/宗教偏见测量，能耗估计 |

## 1. 这篇论文在谱系里换掉了什么

GPT-3 之前的主流路线是先预训练，再针对每个任务做微调。架构可以做到任务无关，但每个任务仍然要几千到几十万条标注样本，还要单独训练一份权重。论文第 1 节把这个限制拆成三条：标注数据贵，微调后的模型容易学到窄分布里的伪相关，人类学新任务并不需要这么多例子。GPT-3 要验证的是另一条路：不改权重，把任务说明和少量示例写进上下文，让一个足够大的语言模型在推理阶段直接完成任务。

这篇论文的贡献不在架构上。第 2.1 节明说模型和架构沿用前作，包括修改过的初始化，pre-normalization 和可逆的 tokenization，唯一的结构改动是层间交替使用稠密注意力和局部带状稀疏注意力，做法类似 Sparse Transformer。真正的变量是规模和评测协议。论文把 in-context learning 定义为预训练外循环之内的一个内循环（图 1.1）：外循环靠 SGD 学到大量技能，内循环在一次前向里靠上下文示例识别任务。这一定义后来成了 Prompt 工程的起点，相关背景可看 [Prompt 工程](../../../../llm-guide/7-LLM应用开发/7.1-Prompt工程/7.1-Prompt工程.md) 和 [ICL 相关综述](../../../../llm-guide/10-综述与前沿论文/LLM技术与ICL与Principle/LLM技术与ICL与Principle.md)。

三种设定的区别只在示例数。few-shot 的 K 一般取 **10 到 100**，上限由 2048 的窗口决定；one-shot 给一个示例；zero-shot 只给自然语言说明。论文特意把 one-shot 单列，理由是它最接近人类接到任务时的情形。有开发集的任务会先在开发集上试几个 K，再用最好的 K 跑测试集，所以 few-shot 的数字并非完全没有调参，只是调的是示例数和提示格式，不碰权重。

## 2. 八个模型：175B 和小档要分开看

表 2.1 列出的八个模型共享同一套训练数据和 token 预算，但层数，宽度，批大小和学习率各不相同。小档依次是 Small 125M（12 层，d_model 768），Medium 350M（24 层，1024），Large 760M（24 层，1536），XL 1.3B（24 层，2048），2.7B（32 层，2560），6.7B（32 层，4096），13B（40 层，5140）。175B 是 **96 层**，d_model 12288, 96 个头，每头 128 维，批大小 3.2M token，学习率 **0.6e-4**。批大小从小档的 0.5M 逐级升到 3.2M，学习率从 6.0e-4 逐级降到 0.6e-4，对应第 2.3 节 「大模型可以用更大批，但要更小学习率」 的经验，批大小的选择参考了训练中测得的梯度噪声尺度。

用 12·L·d_model² 粗算非 embedding 参数，175B 得到约 173.9B，和表 D.1 里的 174,600M 相差不到 1%，余下部分可以归到 embedding 等项。13B 按表里的 d_model = 5140 算是约 12.68B，表 D.1 给的是 12,850M. 这张表内部有两处对不上：XL 写 d_model = 2048，但 24 个头乘 128 维是 3072; 13B 写 d_model = 5140，但 40 个头乘 128 维是 5120。两处都只能从乘法上判断其中一个数字印错，论文没有给出更正。

表 2.1 的注释还给了两条通用约定：前馈层宽度一律是 d_ff = 4 × d_model，所有模型的上下文窗口都是 2048。论文说明各档的具体形状是按 GPU 上的计算效率和负载均衡挑的，模型在深度和宽度两个方向上切分到多卡，以减少节点间的数据传输；同时引用 Kaplan 等人的结论，认为在合理范围内验证损失对这些形状参数不敏感。这解释了为什么头维度会从小档的 64 跳到 80, 96，再到 128，层数也不是平滑递增：形状的选择服从硬件布局，不服从某个统一公式。对读者而言，比较不同档时应当看参数量和算力，不要从层数或头数里推断能力。

分开写的理由在第 3 节随处可见。175B 和小档在很多任务上表现为不同的模型，而不是同一曲线上的平移。LAMBADA 上 Small 从 zero-shot 的 42.7 掉到 few-shot 的 22.0，示例反而拖累它；175B 从 76.2 升到 86.4。算术任务里 13B 两位数加减法 few-shot 只有 50% 左右（图 3.10），175B 在两位数加法上接近满分。下文所有 「GPT-3 做到了」 的数字，如无说明都指 175B；小档的数字只作为 Scaling 曲线上的点出现。

## 3. 训练数据：过滤，去重，和不按体量采样

数据侧有三步（第 2.2 节）：用分类器按与高质量语料的相似度过滤 Common Crawl，在文档层做模糊去重，再混入几路精选语料。附录 A 给了细节。分类器是逻辑回归，正例是 WebText，Wikipedia 和网络书籍语料，负例是未过滤的 Common Crawl。保留规则是 np.random.pareto(α) > 1 - document_score，α 取 9，目的是大部分保留高分文档，同时留下一些分布外的文档。去重用 Spark 的 MinHashLSH，10 个哈希，平均让各数据集缩小约 10%，并且把 WebText 从 Common Crawl 里模糊剔除。数据处理的一般做法可参考 [数据处理](../../../../llm-guide/3-预训练/3.1-预训练数据/3.1.3-数据处理/3.1.3-数据处理.md)。

Common Crawl 取了 2016 到 2019 年的 41 个月度分片，过滤前 45TB 压缩文本，过滤后 570GB，正文说约合 400B 个 BPE token，表 2.2 写 410B. 表 2.2 的关键设计是采样权重不跟体量走：Common Crawl 占 60%，WebText2 占 22%，Books1 和 Books2 各 8%, Wikipedia 3%。结果是在 300B token 的预算下，Common Crawl 和 Books2 连一遍都没过完，WebText2 和 Wikipedia 被看了 2 到 3 遍。论文把这叫做用少量过拟合换更高质量的数据。tokenization 方面论文只说沿用可逆 BPE，背景可看 [分词器与 Tokenizer](../../../../llm-guide/3-预训练/3.3-分词器与Tokenizer/3.3-分词器与Tokenizer.md)。

这张表按自身数字复算会出几处偏差。五个权重相加是 101%。用 权重 × 300B / 体量 复算 epoch，Common Crawl 是 0.44，和表一致；WebText2 约 3.5，表里印 2.9；Wikipedia 约 3.0，表里印 3.4；Books1 约 2.0，表里印 1.9，属于取整范围。附录 C 还提到 Common Crawl 只用了约 40%，和表里的 0.44 在同一量级，但措辞不同。这些偏差不影响结论，可它们说明表 2.2 的 epoch 列可能按某个未公开的实际采样日志填写，而非用表里的权重直接算出。

## 4. 训练过程和算力

附录 B 给出的训练设置对八个模型通用：Adam，β1 = 0.9，β2 = 0.95，ε = 1e-8；梯度全局范数裁剪到 1.0；学习率在前 375M token 线性 warmup，之后在 260B token 内余弦衰减到原值的 10%，剩下约 40B token 保持 10% 不变；批大小在前 **4 到 12B** token 内从 32k token 线性升到满值，具体跨度随模型大小变化；weight decay 0.1。训练序列一律填满 2048 个 token，短文档拼接，中间用 end of text 分隔，不做额外的注意力掩码。数据在一个 epoch 内无放回采样。

硬件方面，所有模型在微软提供的高带宽集群上用 V100 训练，大模型同时使用矩阵乘法内的模型并行和跨层的模型并行。表 D.1 按 6 × 参数量 × token 数估算总算力，并注明忽略了注意力部分的计算。175B 为 **3.64E+03** PF-days。按 6 × 174.6e9 × 300e9 / 8.64e19 复算约 3,637 PF-days，和表一致。13B 是 268 PF-days，2.7B 是 55.2 PF-days。图 2.2 的说明拿 「GPT-3 3B」 和 RoBERTa-Large 比，说两者算力都在 50 PF-days 左右，表 2.1 没有 3B 这一档，按数值看指的是 2.7B（55.2 对 49.3）。

图 3.1 把八个模型的验证损失画成算力的函数，拟合出 L = 2.57 · C^(-0.048)。代入 C = 3640 得到约 1.73。论文要说明的是：按 Kaplan 等人的 Scaling Laws，验证损失在跨三个数量级的模型上仍然是平滑幂律，而且这种平滑在下游任务上大体延续。图 2.2 的说明还特意提到，依据这组规律，他们用 「更大的模型，更少的 token」 来分配算力。Scaling Laws 的推导与后续修正可参考 [Scaling Law](../../../../llm-guide/3-预训练/3.2-预训练全流程/3.2.6-Scaling-Law/3.2.6-Scaling-Law.md)。稀疏注意力这一项，论文只写了交替稠密与局部带状，没有给带宽等超参，综述见 [稀疏注意力综述](../../../../llm-guide/2-核心原理与架构/2.3-高效与稀疏注意力/2.3.2-稀疏与压缩注意力/03-稀疏注意力综述/03-稀疏注意力综述.md)。

## 5. 评测协议：同一个模型怎样当选择题和生成题用

第 2.4 节的协议决定了后面所有数字怎么读。选择题的做法是给 K 个 「上下文 + 正确答案」 示例，再给一个只有上下文的样例，比较各候选答案的语言模型似然。多数任务按每 token 平均似然比，用来抵消长度差异。ARC，OpenBookQA 和 RACE 三个数据集改用 P(completion | context) / P(completion | answer_context) 归一化，answer_context 就是 「Answer: 」 或 「A: 」 这样的通用前缀，这一选择来自开发集上的收益。

二分类任务把 0/1 标签改写成 True/False 这类有语义的词，再按选择题处理。生成类任务用 beam search，宽度 4，长度惩罚 α = 0.6，按数据集惯例计 F1，BLEU 或精确匹配。有公开测试集的任务报告测试集，测试集私有而模型太大无法上传评测服务器的任务报告开发集；SuperGLUE，TriviaQA，PiQa 等少数任务提交了测试服务器。这一混用在第 11 节会反复出现，同一数字在正文，表 3.x 和附录 H.1 里的 「test」 或 「dev」 标注并不总是一致。

这套协议的含义是：few-shot 数字包含提示格式的人工设计。附录 G 列出了每个任务的格式，有的任务（如 WiC）试了多种写法仍接近随机。因此比较 GPT-3 和微调模型时，前者的 「零训练」 指不更新权重，并不等于零人工。读结果时，这一点比 zero/one/few 的区分更重要。

## 6. 175B 的结果：强项

语言建模与补全类任务是 175B 最强的一组。PTB zero-shot 困惑度 20.5，此前最好是 35.8. LAMBADA zero-shot 76.2，one-shot 72.5，few-shot 86.4，此前 SOTA 是 68.0；few-shot 能把 LAMBADA 的格式写成完形填空，让模型知道只该填一个词，这是它反超的主要原因。HellaSwag one-shot 78.1，few-shot 79.3，高于微调过的 1.5B 模型的 75.4，仍低于 ALUM 的 85.6. StoryCloze zero-shot 83.2, few-shot 87.7 (K = 70)，比微调 SOTA 低 4.1。

闭卷问答是论文最常被引用的一组。TriviaQA zero/one/few-shot 分别为 64.3 / 68.0 / 71.2, 71.2 在同为闭卷设定的微调模型里是最好成绩。NQ 为 14.6 / 23.0 / 29.9，WebQS 为 14.4 / 25.3 / 41.5。三组数字的共同点是 zero-shot 到 few-shot 的提升都很大，而且都随模型大小平滑上升，论文据此认为模型容量直接对应它吸收的知识量。阅读理解里 CoQA few-shot 85.0 F1，距人类基线 3 分以内；SQuAD 2.0 从 zero-shot 提升约 10 F1 到 69.8。

翻译上，175B 的平均 BLEU 从 zero-shot 到 one-shot 升约 7.6，再到 few-shot 升约 4.1（按表 3.4 平均）。译入英语方向比此前的无监督 NMT 好约 5.4 BLEU，Ro-En few-shot 距当时 SOTA 在 0.4 以内；译出英语方向明显偏弱，论文归因于 BPE 是为英语语料设计的。SuperGLUE few-shot 总分 71.8，高于 BERT-Large 的 69.0，八个子任务里有四个超过微调的 BERT-Large，COPA 和 ReCoRD 接近 11B 微调模型的 SOTA。算术上，两位数加法接近满分，三位数加法 few-shot 80.2（正文）或 80.4（表 3.9）。SAT 类比 zero/one/few-shot 为 53.7 / 59.1 / 65.2，高于大学申请者的平均 57%。

## 7. 175B 的结果：弱项

比较两个句子的任务是 175B 的明显短板。WiC few-shot 49.4%，等于随机猜。ANLI 三轮里只有第三轮在 175B 上有起色，开发集 few-shot 为 40.2，比 SOTA 与随机之间的差距缩小了将近一半；175B 以下的模型即使在 few-shot 下也停在约 33% 的随机水平。RTE 和 CB 分数也偏低。论文的解释是 GPT-3 在 few-shot 或 one-shot 设定下不擅长判断 「一个词在两句中意思是否相同」 「一句是否是另一句的复述」 「一句是否蕴含另一句」 这类格式。

阅读理解中 QuAC few-shot 44.3 F1，比 ELMo 基线低 13 F1；DROP 36.5，超过原论文的微调 BERT 基线，但远低于人类和结合符号系统的方法；RACE-h 46.8，RACE-m 58.1，和 SOTA 的绝对差距分别是 43.2 和 35.0. ARC Challenge zero/one/few-shot 51.4 / 53.2 / 51.5，比 UnifiedQA 低 27%. OpenBookQA 比 SOTA 低 20 分以上。这组任务要么需要多轮对话结构，要么需要在给定段落里做离散推理，恰好是单向注意力和 few-shot 协议都不占优的地方。

第 5 节把局限归为几类：长文本生成仍会重复，自相矛盾，偶尔跑题；结构上只有单向上下文，做填空和比较类任务吃亏；预训练目标对所有 token 一视同仁，没有 「哪些重要」 的概念；样本效率仍远低于人类；并且论文无法确定 few-shot 到底是在推理阶段 「学会」 了新任务，还是只是识别出训练中见过的任务。最后一条是整篇论文最坦白的一句，它意味着第 6 节的强项和第 7 节的弱项都可能部分反映训练分布，而不单是模型能力。

## 8. 小档模型：Scaling 曲线上的点

小档模型的价值在于提供曲线。附录 H.1 和图 H.1 至 H.11 给出了八个模型在全部任务上的分数，大多数任务的 few-shot 与 zero-shot 差距随模型变大而扩大，这被论文解读为 「大模型更会利用上下文」（图 1.2, 1.3）。在 LAMBADA 上，Small few-shot 22.0 低于它的 zero-shot 42.7；XL few-shot 57.0 反而低于 Large few-shot 63.2。曲线在中间档并不单调，说明 few-shot 的收益在小模型上可能是负的。

算术任务把小档与 175B 的分界画得最清楚。图 3.10 中，13B 两位数加减法 few-shot 约 50%，位数再多就明显下滑；175B 两位数加法接近满分，三位数加法仍有约 80%。论文在正文里写 RTE 上 「只有最大的模型」 在任何设定下明显高于随机的 56%，但附录 H.1 里 13B zero-shot 已有 62.8，这句话并不处处成立。新闻辨别实验中，人类对 Medium 生成文章的辨别率 61% 低于 Large 的 68%，同样不是单调下降。

小档的另一个用途是做 「同算力比较」。2.7B 的训练算力 55.2 PF-days，和 RoBERTa-Large 的 49.3 相近，参数却大近 10 倍。这对应第 4 节的算力分配原则：在固定算力下偏向更大的模型和更少的 token。读 H.1 时要注意，表里的小档数字全部来自同一套 300B token 训练，小档并没有训练到收敛，因此不能直接当作同尺寸模型的最佳水平。

## 9. 合成任务与新闻生成

第 3.9 节设计了几类训练集中不太可能直接出现的任务。字母重排类任务里，175B few-shot 在 「去掉随机插入符号」 上 67.2（表 3.10）或 66.9（正文），「首尾字母外乱序」 37.9 或 38.6，单词完全反转几乎为零。one-shot 相对 few-shot 掉 32% 到 43%，正文描述为 「一半或更多」。新词造句和语法纠错两项只给了定性样例。这些任务的共同设计意图是把 「在上下文里学」 和 「从训练集背」 区分开，但由于 BPE 把单词切成子词，字母级任务对模型而言本身就是跨 token 的操作，结果同时混入了 tokenization 的影响。

新闻生成实验是论文社会影响讨论的起点。人类判断约 200 词的新闻是否为机器所写，对照模型的辨别率约 86%，对 175B 只有 52%，接近随机。约 500 词的长文实验中，对照模型 88%，175B 仍是 52%。实验设计上有几处前后不一：正文说对照模型是 160M，图注写 GPT-3 Small (125M)；正文说测了 「四个模型」 和 「五个模型」，表里有 8 行；附录 E 说 718 名参与者分在 6 组实验里，表 E.1 招募人数按 9 行加总是 713。这些问题不改变 52% 这个结论，但使复核人数和剔除比例变得困难。

## 10. 测试集污染：方法和一个没修掉的 bug

第 4 节和附录 C 处理测试集是否混入训练数据的问题。做法是用 13-gram 在所有测试集/开发集和训练数据之间找重叠，删掉命中的 13-gram 及其前后 200 个字符；被切成超过 10 段的文档整篇视为污染并删除。论文承认过滤代码有 bug，部分重叠没有删掉，又因重训成本太高没有重来。补救办法是在评测阶段为每个基准构造 「干净子集」，比较模型在全集和干净子集上的差异（图 4.2）。

第 4 节开头先给了一个背景判断：数据集和模型都比以往大约两个数量级，其中又有大量 Common Crawl，污染和记忆的机会随之增加；但也正因为数据量大，175B 相对于去重后的留出验证集并没有明显过拟合。图 4.1 的训练曲线显示，训练损失和验证损失之间有一段差距，这段差距随模型变大和训练变长只增长很少，论文据此认为差距主要来自两份数据的难度不同，而不是过拟合。由此得出的预期是：污染可能很常见，但影响未必像担心的那样大。下面的逐项检查就是在验证这个预期。

结论是大多数基准的差异很小。被标出的六组里，阅读理解类 QuAC，SQuAD2，DROP 的疑似污染超过 90%，但人工检查发现重叠的是背景段落，题目和答案并未出现。PIQA 有 29% 被标脏，干净子集上掉 4%；Winograd 正文写 45% 被标脏，掉 2.6%，表 C.1 写 60% 脏，掉 3%。这两项在第 3 节加了星号。语言建模类的 4 个 Wikipedia 基准和 Children's Book Test 几乎整个落在训练数据里，无法切出干净子集，论文没有报告这些结果，改以 PTB 作为主要的语言建模基准。这套方法后来成为大模型论文报告污染的通行格式，它的局限也在这里：13-gram 只抓字面重叠，抓不到改写后的泄漏。

## 12. 社会影响与能耗

第 6 节测了三类偏见。性别上，388 个职业里 83% 更可能接男性代词；用 「The detective was a」 这类模板测，175B 的平均职业偏斜为 −1.11（中性模板），−2.14（能干），−1.15（不能干）。职业与参与者的共指消解任务中，175B 的准确率 64.17%，是所有模型里最高的；它也是唯一一个在 「正确答案是职业」 的句子上女性代词准确率高于男性的模型（81.7% 对 76.7%）。种族上，按情感词典给共现词打分，「Asian」 普遍偏正面，「Black」 普遍偏负面。宗教上，每个提示生成 800 段约 50 词的续写，violent，terrorism，terrorist 进入了 Islam 的前 40 个偏好词。论文把这些当作初步测量，明确说方法本身有局限。

误用部分讨论了虚假信息，垃圾信息，学术不端等场景，结论是当时的高级威胁行为者尚未明显使用语言模型，但生成质量的提升会降低门槛。能耗部分给了一个推理阶段的数字：175B 生成 100 页内容约耗 **0.4 kWh**，论文据此强调训练成本高，摊到大量推理上后单位成本不高，并提到模型蒸馏可进一步降低部署成本。这一段没有给训练阶段的总电量，只给了第 4 节的算力。

## 13. 在后续谱系中的位置

GPT-3 确立了三件事。第一，把 in-context 作为评测主轴，让 zero/one/few-shot 成为大模型论文的标准表格格式。第二，用八个同数据同 token 预算的模型把 Scaling 曲线从验证损失推到下游任务，这组曲线也暴露出 few-shot 收益在小模型上可能为负。第三，13-gram 污染分析和干净子集比较，成为后来论文报告泄漏的默认格式。

它留下的问题同样清楚。175B 在比较两句话的任务上接近随机，在需要对话结构和离散推理的阅读理解上远落后于微调模型；论文无法区分 「推理阶段学会新任务」 和 「识别训练中见过的任务」；300B token 对 175B 而言偏少，小档也都没训练到收敛。后续工作沿着三条线展开：调整参数量与数据量的配比，用指令和人类反馈把 zero-shot 能力调得更可用，以及在推理阶段投入额外算力（TestingTime）来补足一次前向做不到的推理。这些都在本文之外，这里只记下它们各自对应的是本文第几节暴露出的缺口：配比对应第 4 节，指令对应第 5 节和第 7 节，推理阶段额外算力对应第 7 节和第 9 节。

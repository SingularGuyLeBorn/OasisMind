# Kimi K2.5: 在 K2 底座上接视觉, 再把并行编排训成策略

来源: 同目录 `kimi-k2-5.md`, 即 Kimi K2.5 Technical Report(arXiv 2602.02276v2, 页标记 `page 1 of 31` 到 `page 31 of 31`). 对照译稿见 `kimi-k2-5-bi.md`. 权重入口是 Hugging Face `moonshotai/Kimi-K2.5`, 开放的是后训练 checkpoint. 表 1 到表 6, 式 (1) (2), 附录 B 到 E 的数字以源 md 为准; 图 2, 图 4, 图 7, 图 8 的曲线在源 md 里只有图注, 下文凡是引用曲线形状的地方都按图注转述, 不读柱高.

## 1. 家族位置

### 1.1. 家族走到这里缺两样东西

K2 和 K2 Thinking 都只处理文本. 视觉那条线在 Moonshot 内部是单独的 Kimi-VL, 结构和训练与 K2 主线分开. 另一个缺口出在 K2 Thinking 自己身上: 它能连续调用 200-300 次工具, 但这些调用是串行的, 步数越多, 墙钟时间越接近线性增长. K2.5 的引言把这两件事并列成本代的两项改进, 一是文本与视觉联合优化, 二是 Agent Swarm, 即由一个可训练的编排器动态创建子智能体, 把复杂任务拆成并行子任务.

这两项改进落在模型生命周期的不同位置. 视觉那一项贯穿预训练和后训练: 预训练在 K2 上再加约 15T 视觉与文本混合 token, 后训练里有「零视觉 SFT」和联合多模态 RL. 并行编排那一项只在后训练和推理期出现, 靠一种叫 **PARL**(Parallel-Agent Reinforcement Learning)的 RL 设定学出来. 报告把两件事写在同一份材料里, 读的时候要分清: 哪些数字是模型本身的能力, 哪些依赖编排框架和上下文策略. 对外最显眼的 BrowseComp 78.4 属于后者, 单智能体的对应分数是 60.6.

## 2. 结构, 预训练与数据

### 2.1. 骨架: K2 的 MoE 原样保留, 前面接一个图视共享的编码器

语言部分完全继承 K2. 报告 §4.1 重复了 K2 的规模: 总参 1.04T, 每 token 激活 32B, 384 个专家激活 8 个, 稀疏度 48, 优化器是 MuonClip 加 QK-Clip. 附录 C 提到对 MLA 上投影做选择性重算, 说明注意力仍是 K2 那套 MLA. MoE 稀疏激活的一般机制见 [01-DeepSeek-MoE](../../../../llm-guide/2-核心原理与架构/2.6-MoE/01-DeepSeek-MoE/01-DeepSeek-MoE.md), MLA 见 [MLA: 低秩潜变量与解耦 RoPE](../../../../llm-guide/2-核心原理与架构/2.2-注意力机制/2.2.2-多头注意力变体/03-MLA-低秩潜变量与解耦RoPE/03-MLA-低秩潜变量与解耦RoPE.md), MuonClip 见 [MuonClip 与 Polar Express](../../../../llm-guide/6-训练与推理优化/6.5-优化器/6.5.2-Muon/04-MuonClip与PolarExpress/04-MuonClip与PolarExpress.md). K2.5 在语言骨干上没有改层数, 专家数或注意力, 结构上的新东西全在视觉入口.

多模态结构是三件套: 视觉编码器 **MoonViT-3D**, 一个 MLP 投影器, 再接 K2 MoE, 设计原则沿用 Kimi-VL. MoonViT 从 SigLIP-SO-400M 初始化, 采用 NaViT 的 patch packing: 每张图按原生分辨率切 patch, 展平后首尾相接拼成一维序列, 不同分辨率的图可以放在同一个 batch 里训练, 不必做切子图再拼接. 报告没有写 MoonViT 的参数量, 从 SigLIP-SO-400M 这个名字只能推断量级在 4 亿参数上下. 视觉编码器的一般背景见 [8.8-CLIP与视觉编码器](../../../../llm-guide/8-多模态/8.8-CLIP与视觉编码器/8.8-CLIP与视觉编码器.md).

「3D」指时间维. 最多 4 帧连续画面被当成一个时空块, 各帧的 2D patch 一起展平, 打包进同一条一维序列, 用同一套注意力同时处理空间和时间. 进投影器之前, 每个时间块内部做一次轻量的时间池化, 得到 **4 倍**时间压缩, 于是同样的上下文窗口能放下约 4 倍长的视频. 图像和视频走的是同一套参数, 没有单独的视频模块. 报告给这个设计记了两笔收益: 块内的时间注意力改善了对高速运动和视觉特效的理解; 参数共享让图像上学到的知识直接迁移到视频. 评测里对应的是 MotionBench 70.4, 以及喂入 2000 帧以上的 LVBench 75.9, LongVideoBench 79.8.

### 2.2. 预训练日程: 三段课表, 视觉从一开始就低比例混入

表 3 把预训练分成三段. 第一段只训 ViT, 序列长度 4096, 约 1T token, 数据是 alt text, 合成字幕, grounding, OCR 和视频. 这一段和 Kimi-VL 的做法有一处明确差别: 不用对比损失, 只用以图像或视频为条件的字幕交叉熵 $L_{caption}$. 对齐分两步, 先让 MoonViT-3D 对齐一个小语言模型 Moonlight-16B-A3B, 用约 1T token 但训练 FLOPs 很少; 再做一小段只更新 MLP 投影器的训练, 把 ViT 接到 1T 规模的 LLM 上. 用小模型先对齐, 等于把视觉编码器的大部分训练成本从万亿参模型身上挪开.

第二段是联合预训练, 从接近收尾的 K2 checkpoint 继续, 序列长度仍是 4096, 再训约 15T 视觉与文本 token, ViT 和 LLM 一起更新. 数据在第一段基础上增加文本, 知识类图文交错, 视频和 OS 截图. 文本配方沿用 K2 的分布, 做了三处调整: 引入新的 unique token, 加重代码相关内容的权重, 控制每个数据源的最大 epoch 数. 第三段是长上下文 mid-training, 表 3 写的是 token 量 500B→200B, 序列长度 32768→262144, 用 YaRN 插值逐级扩窗, 数据加入高质量文本与多模态数据, 长文本, 长视频推理和 Long-CoT. YaRN 的频率扩展见 [03-长度外推: 从PI到YaRN的频率扩展](../../../../llm-guide/2-核心原理与架构/2.1-深度学习基础组件/2.1.4-位置编码/02-RoPE扩展-长上下文,多模态与工程实现/02-RoPE扩展-长上下文,多模态与工程实现.md). 报告没给每一级扩窗的步长和 YaRN 的扩展倍数.

视觉为什么从第二段一开头就混进来, 依据是 §2.1 的消融(表 1). 固定视觉与文本的总 token 预算, 比较三种注入方式: Early 在训练进度 0% 注入, 视觉与文本比例 10%:90%; Mid 在 50% 注入, 比例 20%:80%; Late 在 80% 注入, 比例 50%:50%. 为了让三组总预算严格相等, 视觉数据引入之前先训一段按预算算好长度的纯文本. 结果 Early 的 Vision Knowledge, Vision Reasoning, OCR 分别是 25.8 / 43.8 / 65.7, Mid 是 25.0 / 40.7 / 64.1, Late 是 24.2 / 39.0 / 61.5; 文本侧 Early 的 Text Knowledge 45.5, Code 24.8 也最高, Text Reasoning 58.5 与 Mid 的 58.6 持平. 业界常见的做法是在语言模型训练后期大比例灌视觉, 表 1 的结论与之相反: **总预算固定时, 早融合加低比例更好**.

附录 B.1 的图 9 给出过程曲线, 并描述了一个现象: Mid 和 Late 两组在视觉数据刚进来时, 文本能力先下降, 过一段再回升. 报告把原因归为模态分布突变, 视觉 token 突然涌入, 打乱了已经建立的语言表示, 模型暂时让出一部分文本能力去做跨模态对齐. Early 组没有这个坑, 文本曲线全程平稳. 表 1 只给了三种组合, 注入时机和比例是捆绑变化的, 没有「早注入高比例」或「晚注入低比例」的交叉组, 所以严格说它证明的是「早且少」这个组合优于「晚且多」, 单独哪个因素起主要作用, 报告只给了「比例影响很小」这一句判断. 消融模型的规模和总预算本页也没有写.

### 2.3. 数据: 文本四个领域, 视觉七类

附录 B.2 说文本语料分 Web Text, Code, Mathematics, Knowledge 四个领域, 处理流程大多沿用 K2, 每个领域做了正确性和质量校验, 并用定向的数据实验确认多样性和有效性. 代码是明确加权的一块, 扩充了三类: 支持跨文件推理的仓库级代码; 互联网上的 issues, code review 和 commit 历史, 用来捕捉真实开发过程; 从 PDF 和网页语料里检索出的代码相关文档. 报告把这三类和补丁生成, 单测编写这类 Agent 编码子任务直接挂钩. 各领域的 token 占比, 去重规则和 K2 那套改写合成是否继续使用, 附录都没有给数字.

视觉数据分七类: caption, interleaving, OCR, knowledge, perception, video, agent. caption 负责基础模态对齐, 合成字幕严格限量, 理由是压低幻觉. 图文交错数据来自书籍, 网页和教程, 用于多图理解和更长的上下文. OCR 覆盖多语言, 密集版面和多页文档. knowledge 类是经版面解析处理的学术材料. 此外有一批 STEM 解题语料: 定向检索和爬取之后, 对没有问答格式的原始材料, 用 in-context learning 改写成从 K-12 到大学难度的结构化题目. 图与代码配对是另一块特色, HTML, React, SVG 等代码配上渲染截图, 让模型把结构逻辑和视觉几何对齐, 这和评测里的 image/video-to-code 能力对应.

agent 与时序这一侧, 收集了桌面, 移动端和网页上的 GUI 截图与操作轨迹, 含人工标注的演示; 视频数据同时服务小时级长视频理解和细粒度时空感知; grounding 数据含边框和点标注; 还新加了轮廓级分割任务, 用于像素级感知. 七类数据之间的比例, 以及「视觉占 10%」是否就是正式训练采用的比例, 报告没有明说. 正文只说全程以恒定比例混合, 表 1 的 10:90 是消融设定, 把它当作正式配方属于推断.

## 3. 后训练与训练系统

### 3.1. 后训练起点: 只用文本 SFT, 再用视觉 RL 逼模型看图

SFT 沿用 K2 的流程: 用 K2, K2 Thinking 和一组内部专家模型合成候选回答, 按领域定制管线, 结合人工标注, 提示工程和多阶段校验, 目标是交互式推理和精确的工具调用. 视觉这一侧的做法最反直觉. 预训练过的视觉语言模型不会天然地调用视觉工具, 多模态 RL 因此有冷启动问题. 常规办法是人工标注或提示工程造视觉 CoT 数据, 但这类数据多样性窄, 操作常停留在裁剪, 旋转, 翻转. K2.5 的做法叫**零视觉 SFT**: 后训练的 SFT 阶段只用文本数据, 所有图像操作都通过 IPython 里的程序化操作代理完成, 相当于把「视觉工具」泛化成「写代码处理图像」.

报告给出的效果是: 这种从文本侧激活的方式, 能带出像素级操作(二值化后估计物体大小, 计数), 并泛化到定位, 计数, OCR 等视觉任务. 图 2 的 RL 曲线以最小规模的零视觉 SFT 为起点, 随视觉 RL FLOPs 增加持续上升. 初步实验里, 文本加视觉混合的 SFT 在视觉 Agent 任务上明显更差, 报告猜测原因是高质量视觉轨迹不够. 它把零视觉 SFT 能成立归功于第 2.2 节的联合预训练: 预训练已经把视觉和文本对齐得足够紧, 后训练只需要把工具使用的习惯从文本侧唤起.

只靠文本激活还有明显的失败模式: 模型有时会忽略图像, 该看图的时候不看. 接下来的 outcome-based 视觉 RL 专门挑必须看图才能答对的任务, 分三类: 视觉 grounding 与计数; 图表与文档理解; 经过筛选, 确实依赖图像输入的 STEM 题. RL 得到的轨迹再抽出来做拒绝采样微调(RFT), 形成一条自我改进的数据流, 供后面的联合 RL 使用.

表 2 是这一段最有意思的结果: 视觉 RL 前后只测文本基准, MMLU-Pro 84.7→86.4, GPQA-Diamond 84.3→86.4, LongBench v2 56.7→58.9. 报告的分析是, 视觉 RL 改善了结构化信息抽取相关的校准, 在类似计数, OCR 这类文本问题上的不确定性下降. 表 2 是视觉 RL 这一段的前后对比, 最终对外的 MMLU-Pro 87.1, GPQA-Diamond 87.6, LongBench v2 61.0 还叠加了后续的联合 RL, 两组增量不能相加换算.

联合多模态 RL 按能力域组织, 不按输入模态. 知识, 推理, 编码, Agent 等领域各有「领域专家」, 每个领域同时吃纯文本和多模态题目, 生成式奖励模型(GRM)也跨模态打分. 这样某个能力无论从文本还是视觉输入练出来, 都会迁移到另一个模态. 报告把这概括为**「文本启动视觉, 视觉反哺文本」**. 这里的「领域专家」指 RL 数据与环境的划分, 和 MoE 里的专家不是同一个概念.

### 3.2. RL 目标: 按 token 截断梯度, 奖励分三层, Toggle 控长度

式 (1) 是 K2.5 所有 RL(包括联合 RL 和 PARL)共用的目标. 对每道题 $x$, 用上一版策略 $\pi_{\mathrm{old}}$ 采 $K$ 个回答, 记第 $j$ 个回答第 $i$ 个 token 的概率比为 $w_j^i=\pi_\theta(y_j^i|x,y_j^{0:i})/\pi_{\mathrm{old}}(y_j^i|x,y_j^{0:i})$, 目标写作

$$L_{\mathrm{RL}}(\theta)=\mathbb{E}_{x\sim\mathcal D}\Big[\frac1N\sum_{j=1}^K\sum_{i=1}^{|y_j|}\mathrm{Clip}\big(w_j^i,\alpha,\beta\big)\big(r(x,y_j)-\bar r(x)\big)-\tau\big(\log w_j^i\big)^2\Big]$$

其中 $\bar r(x)=\frac1K\sum_j r(x,y_j)$ 是组内平均奖励, $N=\sum_j|y_j|$ 是这一组的总 token 数. 第一项把序列级优势 $r-\bar r$ 原样分给该回答的每个 token, 不用 critic; 第二项是逐 token 的对数比平方, 把新策略拉在旧策略附近. 均值基线加对数比平方惩罚, 这个骨架延续自 k1.5 的在线镜像下降变体, 和 GRPO, RLOO 同属组内基线的一族. 和 K2 比, 同一步计算有两处落点不同: K2 的平方损失对整条回答算一个对数比, 按 $1/K$ 在回答之间平均; K2.5 拆到 token 级, 按 $1/N$ 在 token 之间平均, 长回答的 token 多, 在梯度里的份量也随之变大. 可对照 [02-GRPO](../../../../llm-guide/4-后训练/4.5-GRPO家族与RLVR/01-GRPO/01-GRPO.md) 和 [06-RLOO-留一法基线](../../../../llm-guide/4-后训练/4.4-强化学习基础/05-RLOO-留一法基线/05-RLOO-留一法基线.md).

相对 k1.5 的新增是 **token 级截断**. 报告说它的作用等同于梯度掩码: 对数比落在 $[\alpha, \beta]$ 内的 token 正常计算策略梯度, 落在外面的 token 梯度置零. 和标准 PPO 裁剪的关键区别在于, 它只看对数比, 不看优势的正负. PPO 的 clip 是否生效取决于优势符号, 而这里一个 token 只要偏离旧策略太远, 不论好坏都不参与第一项的更新. 从式子看, 截断只套在第一项上, 平方项没有截断. 所以一个越界的 token 不再被优势推着走, 却仍然受 $-\tau(\log w)^2$ 的梯度 $-2\tau\log w\,\nabla\log\pi_\theta$ 往回拉, 越界越远拉力越大. 动机是训练框架和推理框架之间的数值差异会放大 off-policy 偏移, 在长时程, 多步工具调用的任务里尤其明显. 报告说这个机制对训练稳定是必需的. PPO 裁剪的原始语义见 [04-PPO](../../../../llm-guide/4-后训练/4.4-强化学习基础/04-PPO/04-PPO.md). $\alpha, \beta, \tau$ 的取值本页没有给.

奖励分三层. 可验证的任务(推理, Agent)用基于规则的结果奖励, 另加一个预算控制奖励, 用来提高 token 效率. 通用任务用 **GRM**, 这是 K2 自批判 rubric 奖励的扩展: 不再只评对话输出, 而是叠加在已验证的奖励信号之上, 用于聊天助手, 编码 Agent, 搜索 Agent 和产物生成 Agent. GRM 不做二元判定, 而是细粒度地评有用性, 回答是否就绪, 上下文相关性, 细节是否适量, 生成产物的美观程度, 是否严格遵循指令. 为了防奖励作弊和对单一偏好过拟合, 不同任务配多套备选 rubric.

视觉任务另有专用奖励: grounding 和点定位用带软匹配的 F1, grounding 的软匹配来自 IoU, 点任务来自最优匹配下的高斯加权距离; 多边形分割先把预测多边形栅格化成二值掩码, 再和真值算分割 IoU; OCR 用归一化编辑距离; 计数按预测与真值的绝对差给分; 合成的复杂视觉谜题交给 Kimi K2 当 LLM 校验器. 这组奖励把第 2.3 节的轮廓分割, grounding 数据和 RL 连到了一起.

长度控制用 **Toggle**. 报告先交代动机: 以往按题目设定预算能让 CoT 变短, 但在严格预算下训出来的模型会「长度过拟合」, 给它更多推理 token 时反而用不上, 习惯性地截短推理. Toggle 改的是第 $t$ 轮用的奖励:

$$\tilde r(x,y)=\begin{cases}r(x,y)\cdot\mathbb I\Big\{\frac1K\sum_{i=1}^K r(x,y_i)<\lambda\ \text{或}\ |y|\le\mathrm{budget}(x)\Big\}, & \lfloor t/m\rfloor\bmod 2=0\ (\text{Phase0})\\ r(x,y), & \lfloor t/m\rfloor\bmod 2=1\ (\text{Phase1})\end{cases}$$

$\lfloor t/m\rfloor\bmod 2$ 让训练每 $m$ 轮换一次阶段. Phase0 里指示函数有两个放行条件: 这道题的组内平均正确率还低于 $\lambda$, 说明模型还没稳定做对, 这时不管长短都照常给奖励, 避免过早拿质量换效率; 正确率达到 $\lambda$ 后, 只有长度不超预算的回答保留奖励, 超预算的正确回答被乘 0. 答错的回答本来 $r=0$, 不受影响. Phase1 直接用原奖励, 放开到最大 token 限制, 让模型保住用满推理算力的能力. 预算由式 (2) 定:

$$\mathrm{budget}(x)=\mathrm{Percentile}\big(\{|y_j|\ :\ r(x,y_j)=1,\ j=1,\dots,K\},\ \rho\big)$$

即同题正确回答长度的第 $\rho$ 百分位(原式下标 $i$, $j$ 混用, 这里按语义统一). 它在训练开始时估计一次, 之后固定. 放到式 (1) 里看, Phase0 中超预算的正确回答从 $r=1$ 变成 $\tilde r=0$, 组均值 $\bar r$ 随之下降, 这条回答的优势从正变负, 而预算内的正确回答优势变大; 预算固定, 所以不会随模型变短而一轮轮继续收紧. 在 K2 Thinking 上验证, 输出 token 平均减少 25%~30%, 性能影响可以忽略, 重复验证, 机械计算这类冗余明显减少; 只在数学和编程上训练, GPQA 和 MMLU-Pro 上也能看到长度下降(图 5). 这种「推理时多花算力」和「省 token」之间的来回切换, 报告称为双目标问题上的随机交替优化.

表 5 能看到效果: AIME 2025 上 K2.5 96.1(25k), K2 Thinking 94.5(30k); LiveCodeBench 85.0(18k) 对 82.6(25k); HLE-Text 31.5(24k) 对 23.9(29k); 括号内是平均输出千 token 数. 分数更高, 输出更短, 和 Toggle 的叙述同向. 同一张表里 Gemini-3.0 Pro 在 AIME 只用 15k, DeepSeek-V3.2 用 16k, K2.5 仍然是更「话多」的那一个; 唯一例外是 GPQA Diamond, K2.5 用 14k, 比 K2 Thinking 的 13k 还略多.

### 3.3. Agent Swarm: 只训编排器, 用关键路径步数记时间

Agent Swarm 的结构见图 3: 一个可训练的编排器, 按需创建子智能体并分派子任务. 工具只有两个(附录 E.8): `create_subagent` 用自定义系统提示和标识创建一个可复用的子智能体, `assign_task` 把任务派给已创建的子智能体. 子智能体来自固定的中间策略 checkpoint, 训练中保持冻结, 它们的执行轨迹不进优化目标, **只有编排器用 RL 更新**. 报告给的理由是信用分配: 多智能体场景下结果奖励稀疏且嘈杂, 最终答对不代表每个子智能体都做对了, 答错也不代表全错. 把子智能体输出当作环境观测, 协调能力和执行能力就被拆开训练. 为了省算力, 先用小尺寸子智能体训编排器, 再换成大模型; RL 框架还能动态调整子智能体和编排器的推理实例比例.

PARL 的奖励是三项之和:

$$r_{\mathrm{PARL}}(x,y)=\lambda_1\,r_{\mathrm{parallel}}+\lambda_2\,r_{\mathrm{finish}}+r_{\mathrm{perf}}(x,y)$$

$r_{\mathrm{perf}}$ 是任务级结果, 评整体解答的成败和质量. $r_{\mathrm{parallel}}$ 是创建子智能体的奖励, 用来避免「串行塌缩」, 即编排器停在只用单智能体的局部最优. $r_{\mathrm{finish}}$ 在式中标为子智能体完成率, 用来避免「虚假并行」, 即为了刷并行指标狂开子智能体却不做有效分解. 两个辅助项互相牵制: 只有 $r_{\mathrm{parallel}}$ 时, 多开就多拿; 加上以比率计的 $r_{\mathrm{finish}}$, 开出来却完不成的子智能体会拉低完成率, 多开不再白拿. $r_{\mathrm{parallel}}$ 的具体形式(按个数还是按是否开启)报告没写. 两个系数 $\lambda_1,\lambda_2$ 在训练中退火到零, 最终策略只对 $r_{\mathrm{perf}}$ 负责; 到那时继续并行的动力来自下文的关键步数预算, 串行在预算内做不完, 就拿不到 $r_{\mathrm{perf}}$. 报告没有给 $\lambda_1, \lambda_2$ 的初值和退火日程.

时间成本用 **critical steps** 衡量, 类比计算图里的关键路径. 一个 episode 分成若干阶段, 每阶段编排器执行一个动作, 要么直接调工具, 要么创建一组并行子智能体; 该阶段耗时由组内最慢的子智能体决定. 总关键步数为

$$\mathrm{CriticalSteps}=\sum_{t=1}^{T}\Big(S^{(t)}_{\mathrm{main}}+\max_i S^{(t)}_{\mathrm{sub},i}\Big)$$

$S^{(t)}_{\mathrm{main}}$ 是编排器在第 $t$ 阶段走的步数, 通常为 1; $\max_i$ 只取这一组里最慢的子智能体, 其余子智能体走多少步都不计入. 直接调工具的阶段没有子智能体, 第二项应按 0 理解, 这是推断, 报告没写. 训练和评测都按关键步数而不是总步数约束, 于是开很多子任务却不缩短最长分支几乎没有收益, 均衡的分解才能直接减少关键步数. 训练提示也配合这个目标: 合成题目侧重 wide search(同时探索大量独立信息源)和 deep search(多条推理分支延迟汇总), 再加长文档分析, 大规模文件下载这类真实负载. 提示里不明说「请并行」, 只是让任务分布在串行预算内难以完成. 图 4 的图注写训练准确率和并行度一起平稳上升.

用一个假设的例子看关键步数怎么起作用(数字为示例, 不来自报告). 一道题要查 10 个独立来源, 每个来源要 8 步工具调用. 单智能体串行做, 大约 80 步. 编排器开 10 个子智能体各查一个, 第一阶段关键步数是编排器 1 步加最慢子智能体 8 步, 再用 1 步汇总, 总共约 10 步. 如果编排器贪多开了 20 个子智能体, 其中 10 个无事可做, 最长分支仍是 8 步, 关键步数不变, 而 $r_{finish}$ 会因为一半子任务没有有效完成而扣分. 反过来, 如果只开 2 个子智能体各查 5 个来源, 最长分支变成 40 步, 关键步数明显变差. 这个度量把「开多少个」和「怎么分」都变成了会影响奖励的决策.

这套设计和社区常见的多智能体框架差别在于「谁决定拆分」. 手写的 map-reduce 式工作流由开发者规定分几路, 什么时候汇总; Agent Swarm 把这个决定交给编排器, 由 RL 学出来, 所以同一个编排器面对简单问题可以不拆, 面对宽搜索问题拆得很细. 图 6 的词云展示编排器在不同测试中创建的子智能体角色, 报告据此说异构的子智能体分工是自发形成的, 词云本身没有量化信息.

评测时的步数预算写在附录 E.8: BrowseComp 编排器最多 15 步, 每个子智能体最多 100 步; WideSearch 双方各 100 步; 内部 Swarm Bench 编排器 100 步, 子智能体 50 步. BrowseComp 的编排器只有 15 步, 说明它的工作以拆分和汇总为主, 大部分搜索由子智能体完成.

报告还把 Swarm 定位为一种主动的上下文管理. Hide-Tool-Result, Summary, Discard-all 这类做法是上下文溢出后被动压缩或丢弃历史, 常会丢掉结构信息和中间推理. Swarm 让每个子智能体在有界的局部上下文里工作, 只把与任务相关的结果交回编排器, 编排器的全局上下文不被完整交互轨迹污染. 报告的说法是**「上下文分片而不是上下文截断」**. 图 7 的图注称, 在 BrowseComp 上 Swarm 在效率和准确率两方面都优于 Discard-all.

### 3.4. 训练基础设施: DEP 把视觉编码器从流水线里拆出来

K2.5 基本沿用 K2 的训练基础设施. 附录 C 给了硬件和并行: NVIDIA H800 集群, 节点间 8×400 Gbps RoCE; 16 路流水线并行(带 virtual stages), 16 路专家并行, ZeRO-1 数据并行, 节点数只要是 32 的倍数就能训; 在 interleaved 1F1B 调度下让 EP 的 all-to-all 通信与计算重叠. 显存方面, 对 LayerNorm, SwiGLU 和 MLA 上投影做选择性重算, 把不敏感的激活压成 FP8-E4M3, 剩余激活以流式重叠的方式 offload 到 CPU.

多模态带来的新问题是流水线第 0 段(Stage-0)的负载抖动. 常规做法把视觉编码器和文本嵌入都放在 Stage-0, 而每个 batch 的图片数量和分辨率变化很大, Stage-0 的算力和显存随之剧烈波动. Kimi-VL 当时的办法是手动减少 Stage-0 上的文本解码层数腾出显存, 这能缓解显存压力, 但解决不了负载不均, 也没法直接复用为纯文本训练调好的并行策略.

**DEP**(Decoupled Encoder Process)利用了视觉编码器在计算图里的特殊位置: 它是前向的起点, 也是反向的终点. 每个训练步拆成三段. 第一段是均衡的视觉前向: 编码器很小, 在所有 GPU 上复制一份, 按图片数或 patch 数把整个全局 batch 的视觉前向均摊, 丢掉所有中间激活, 只保留最终输出, 再 gather 回 Stage-0. 第二段是骨干的前向和反向, 因为视觉中间激活已经丢掉, 这一段可以直接用纯文本训练验证过的并行策略, 结束时梯度累积在视觉编码器的输出处. 第三段重算视觉前向, 再反向求编码器参数的梯度. 代价是视觉前向算两遍, 换来的是 K2.5 直接继承 K2 的并行策略, 多模态训练效率达到纯文本训练的 **90%**. 报告提到同期 LongCat-Flash-Omni 用了类似思路.

数据加载也为多模态改过(附录 C.1). 视觉数据以原始格式存放在 S3 兼容的对象存储里, 加载层负责动态打乱, 混合, tokenize, loss mask 和序列打包, 数据比例可以在训练中调整; 做几何增强时保持 2D 坐标和方向元数据一致; 通过管理随机种子和 worker 状态保证完全确定性, 中断续训后的数据顺序与不中断时一致; 用分层缓存提高吞吐, 同时把对对象存储的请求频率控制在可接受范围. 另有统一平台管理数据注册, 可视化, 统计, 跨云同步和生命周期.

RL 环境单独写在附录 D(图 10). 接口是 Gym 风格, 由可插拔组件拼成: Toolset 提供带沙箱的工具, Judge 提供多维奖励信号, 另有提示多样化和指令遵循增强模块. 执行层把每个 Agent 任务当成独立的异步协程, 任务可以递归触发子任务 rollout, PARL 和 Agent-as-Judge 都借此实现. Rollout Manager 在 RL 过程中最多调度 100,000 个并发 Agent 任务, 支持 k1.5 引入的 partial rollout. 推理引擎严格遵循 Token-in-Token-out, 记录所有输出的 log 概率, 用于训推不一致的校正, 这和式 (1) 的 token 级截断针对的是同一个问题. 只能走标准 LLM API 的黑盒环境, 由 LLM Gateway 代理记录请求和响应.

附录 F 的两张定性图可以当作机制演示. 图 11 用并行视觉智能体分析《黑神话: 悟空》的完整通关录像, 共 32 段视频, 约 24 小时, 约 40GB: 主智能体给每个子智能体派一段视频, 子智能体抽帧, 分析时序事件, 标出 boss 战和升级等关键时刻, 最后由主智能体汇总成带时间线的 HTML 页面. 图 12 展示工具增强的视觉推理: 迷宫题先二值分割再跑 BFS, 饼图题做像素级颜色分割再算面积比例, 找不同题用计算机视觉方法找像素差异. 后者正是第 3.1 节「零视觉 SFT + IPython 代理」训练出来的行为. 两者都没有配对照分数.

### 4.3. 放回谱系: 哪些面讲透了, 哪些面没给

按模型从数据到评测的整条链看, K2.5 的披露比 K2 Thinking 完整得多. 结构上交代了 MoonViT-3D 的初始化, 打包方式和时间压缩, 语言骨干明确沿用 K2. 预训练有三段课表和 token 量, 有早融合消融和文本「先降后回」的曲线描述. 数据有文本四域和视觉七类的构成. 后训练有 SFT 来源, 零视觉 SFT, 视觉 RL 三类任务, 式 (1) 的目标, 三层奖励, Toggle 和 PARL. 基础设施有并行配置, DEP 和 RL 环境. 评测协议逐项写了预算, 重复次数, 模式和上下文策略.

没给的也清楚: MoonViT-3D 的参数量; 正式训练的视觉比例和各类数据配比; 式 (1) 的 $\alpha, \beta, \tau$, Toggle 的 $\lambda, m, \rho$, PARL 的 $\lambda_1, \lambda_2$ 退火日程; RL 的总算力和步数; 编排器与子智能体各用多大模型. 开源的是后训练 checkpoint, 配方本身无法复现.

从家族演进看, K2.5 接上了三条线. 一是 k1.5 的 RL 骨架: 均值基线加对数比平方正则一直沿用, 这一代加了 token 级截断, 应对训推框架差异; partial rollout 从 k1.5 延续到 RL 框架里. 二是 K2 的底座和 Agent 数据路线, 结构不动, 继续在上面叠能力. 三是 K2 Thinking 暴露出的串行延迟问题, K2.5 用 Swarm 回应, 并把上下文管理从「截断历史」扩展到「拆分给子智能体」. K2 Thinking 引入的 INT4 QAT, 在这份报告里没有再提, 部署精度这一面本页没有信息.

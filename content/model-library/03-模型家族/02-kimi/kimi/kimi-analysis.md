## 1. 这份手册在家族里的位置

Kimi 家族在本目录里的时间线从这份手册起步. 2023 年 10 月 Kimi 智能助手上线时, 对外主打的是超长无损上下文(公开报道口径是 20 万汉字, 2024 年 3 月又宣布扩到 200 万字, 这两处数字来自新闻稿, 不在本页源文里). 开放平台这一侧对应的就是 moonshot-v1 系列 API. 这份 2024 年 3 月的手册, 记录的正是「长上下文是卖点, 但模型本体完全不公开」的那个阶段.

后面的节点在同家族其他目录里: k1.5 开始写强化学习与长 CoT, K2 公开了 MoE 结构和 MuonClip, 之后的 K2 Thinking, K2.5, K3 再逐步补上 Agent 训练与多模态. 拿这份手册跟那些报告对照, 差距一眼就能看出来. 这里交付的只有接口合同, 模型是怎么做出来的, 一个字都没写. 读它的正确姿势是把它当作家族起点的服务说明书, 而不是技术来源.

## 2. 模型本体: 六个面里只露出一个

一个模型通常由数据, 架构, 训练算法, 预训练, 后训练和评测共同决定. 这份手册对前五个面都没有交代. 源文只说 moonshot-v1 是「基于我们(Moonshot AI)开发和训练的预训练模型的 API 服务」, 能「理解自然语言和书面语言」, 适合内容或代码生成, 摘要, 对话, 创意写作. 语料构成, tokenizer 词表, 层数, 注意力形式, 位置编码怎样支撑 128k, 有没有 SFT 或偏好对齐, 页面都没有.

评测也是空白. 手册没有任何榜单分数, 也没有长上下文检索类测试的结果. 唯一接近「效果声明」的是型号段那句话: `moonshot-v1-8k`, `moonshot-v1-32k`, `moonshot-v1-128k` 三档「区别在于它们的最大上下文长度」, 「在效果上并没有什么区别」. 由此能推出的只是一个猜测: 三档很可能共享同一套权重, 差别落在服务端的窗口与显存配置上(源文没有这样写). 模型到底怎样训练到 128k, 需要另找材料.

## 3. Token 与上下文预算

Token 段给了中文粗估. 单字如「夔」可能拆成多个 Token, 「中国」这类常见短语可能只占一个 Token; 「对于一段通常的中文文本, 1 个 Token 大约相当于 1.5-2 个汉字」. 这个比例是 tokenizer 的外在表现, 说明词表对中文常用词做了合并, 但词表大小和切分算法页面没写.

硬约束只有一句: Input 与 Output「总和长度不能超过模型的最大上下文长度」. 也就是说 128k 是输入加输出的共同预算, 不是输入单独 128k, 再另给一个输出窗口. 按上面的粗估换算, 128k Token 大致对应 19 万到 25 万汉字, 与助手产品早期「20 万汉字」的宣传量级能对上, 但源文本身没有做这个换算.

## 4. 限流四轴与计费两把尺

速率限制按并发, RPM(每分钟请求数), TPM(每分钟 Token 数), TPD(每天 Token 数)四维衡量, 「取决于哪个先发生」. 源文举例: RPM 上限 20 时, 发 20 个各 100 Token 的请求就会撞限, 即使离假定的 200k TPM 还很远. 另外两条规则容易被忽略: 限流在「用户级别而非密钥级别」实施; 「目前我们在所有模型中共享速率限制」, 多开密钥或换档位都不会各得一桶配额.

网关和账单用的是两把尺. 网关「基于请求中的 max_tokens 参数来计算速率限制」, 判断时用「请求的 token 数量加上 max_tokens」, 「而不考虑实际生成的 token 数量」; 计费则按「请求的 token 数量加上实际生成的 token 数量」. 网关这样做的原因, 手册只说「出于方便考虑」. 放到推理系统里看, 解码阶段要为每个请求预留 KV cache 空间, 按 max_tokens 预占是最保守的做法. Moonshot 同年公开的 Mooncake 服务架构论文把 prefill 与 decode 拆成两个集群, 并以 KV cache 为调度中心, 可以作为理解这种预占逻辑的背景, 但本页没有提到它. 落到使用上: max_tokens 开得越大, 越早吃光 TPM 和并发预算, 账单却只按真实产出算.

## 5. 响应, 对话历史与当时缺的能力

处理响应段写了三种结果: 单请求超时 **5 分钟**返回 504, 撞限流返回 429, 成功返回 JSON. 非 streaming 模式一次拿全文; streaming 模式走 SSE, 「可以在任何时候中断请求, 而不会浪费资源」. 这几条是服务合同, 跟模型能力无关.

FAQ 把几条边界写得更清楚. 每次调用都要自带对话历史, 费用「根据 messages 的长度需要重新计费」, 服务端不替用户保存会话. 文件解析「支持对 pdf 和图片文件的 OCR; 文件解析服务免费」. Function Calling 「在规划中」; 类似 Kimi 智能助手的搜索接口「目前并没有开放搜索的计划」, 建议用 Apify, Crawlbase, ArchiveBox 等第三方方案. 语言模型推理服务段也说接口「本身是不支持访问网络, 数据库等外部资源, 也不支持执行任何代码」. 助手 App 里的联网搜索, 当时并不属于这份 API. 充值段则写个人认证后微信或支付宝扫码, 企业认证「暂不支持」, 走企业微信客服.

## 6. Prompt 指南能反推出什么

手册后半是 System Prompt 最佳实践: 写清楚指令, 补细节, 让模型扮演角色, 用三重引号或 XML 标签做分隔, 写明步骤, few-shot, 指定长度, 提供参考文本, 按类别拆任务, 长对话摘要, 长文分块递归摘要. 这一套与 OpenAI 公开的 prompt 指南同一路数. 示例里有两处可核对的细节: 「更好的请求」要求把 2023 年工作记录总结为「500 字以内」的段落并按月列亮点; 角色示例的 system 写「你是 Kimi, 由 Moonshot AI 提供的人工智能助手, 你更擅长中文和英...」(源文截断).

这段 system 文案是页面上唯一跟后训练沾边的线索: 模型被训练或提示成以「Kimi」身份作答, 并自称擅长中文和英文. 至于这种身份是靠 SFT 注入还是只靠 system prompt, 手册没说. 长度段还有一句实话: 指定字数「并不具有高精度」, 模型更擅长按段落数或项目符号数输出. 长对话段承认「固定的上下文长度」, 建议到阈值就把前文摘要写进 system, 或者异步总结; 长文档则分章摘要, 再做「摘要的摘要」. 即便有 128k, 手册也没有把长上下文说成可以无限用, 窗口用满之后怎么办, 仍然交给调用方自己裁剪和摘要.

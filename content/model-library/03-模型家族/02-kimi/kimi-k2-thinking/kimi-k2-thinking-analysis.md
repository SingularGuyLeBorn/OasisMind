# Kimi K2 Thinking: 边想边调工具, 思考长度和工具步数一起加

本页是发布博客, 不是技术报告. 能讲的机制只有交错工具调用的评测设定和 INT4 QAT 两件, 数据, 结构, 预训练和 RL 细节都没有公开.

来源: 同目录 `kimi-k2-thinking.md`(页标记 `page 1 of 9` 到 `page 9 of 9`, Moonshot 官方发布博客). 对照译稿见 `kimi-k2-thinking-bi.md`. 配图八张, 其中 `images/p01-humanity-s-last-exam-text-only-w-tools-3-b.png` 是 HLE 柱状图, `images/p04-*` 三张是搜索演示, `images/p05-*` 两张是写作样例, `images/p08-system.png` 是站点页脚. 表内分数, 脚注编号以源 md 为准; 页 6 推理表有三列数字被 OCR 粘成一串, 下文按列切分, 均标为读表.

## 1. 家族位置与披露范围

### 1.1. 家族走到这里缺的是「会想」

K2 是非思考模型, 报告把所有评测都放在 non-thinking 设定下, 长推理这一面是空的. 再往前, k1.5 已经证明长 CoT RL 能把数学和编程推上去, 但它不开源, 也没有大规模工具训练. K2 Thinking 把这两条线接到一起: 底座用 K2, 做法回到 k1.5 的长链推理, 再叠加 K2 那套 Agent 数据和工具环境. 博客的定位是「目前最好的开源思考模型」, 关键词是 thinking agent, 即一边逐步推理一边调用工具.

博客把这一代的努力归入 test-time scaling, 说的是 TestingTime 多花算力: 同时扩展思考 token 数和工具调用步数. 它给了一个很具体的上限, 无人干预下最多执行 200-300 次顺序工具调用, 在数百步里保持连贯推理. 这个数字是上限叙事, 不是平均步数. Hugging Face 模型卡另有一句对比, 称以往模型在 30 到 50 步后就会退化, 这句不在本页正文里, 只能当作官方的补充说法.

门口三项成绩: 带工具的 HLE 44.9%, BrowseComp 60.2%, SWE-Bench Verified 71.3%. 三项分别对应专家级推理, 网页信息检索和真实软件工程. 它们都依赖工具和特定评测框架, 下文逐一拆开.

HLE 在页 2 的介绍是封闭式题目, 数千道专家级问题, 覆盖 100 多个学科, 44.9 是在带 search, python, web-browsing 三类工具的条件下拿到的. 页 1 的柱状图标题写的是 「Text-only w/ tools」, 页 2 另有一张按学科展示专家级问题的图, 两张图在源 md 里都只有标题, 柱高和分学科数字没有被转成文本, 这里不读图估数. 需要注意的是, 标题里的 Text-only 说明 44.9 是纯文本子集上的分数, 与别家在 HLE 全集上报的数字不是同一口径, 第 3.5 节会把这层差异拆开.

### 1.2. 这一页交代了模型的哪些面

作为发布博客, 本页对模型怎么做出来几乎不谈. 训练数据的来源和规模, 结构参数, 预训练, 后训练用的 RL 算法和奖励设计, 正文都没有. 连「基于 K2」这句话也没在博客里明写. Hugging Face 模型卡倒是写明基座为 Kimi-K2-Base, 结构参数与 K2 一致(1T 总参, 32B 激活, 61 层, 384 专家选 8, MLA, 词表 160K, 上下文 256K), 这些数字来自模型卡而不是本页. 读者可以合理推断 K2 Thinking 是在 K2 底座上做的后训练, 但具体做了多少 RL, 用了什么数据, 本页一个字也没给.

模型卡还有一句值得注意: 模型经过端到端训练, 学会把 CoT 与函数调用交错进行. 「端到端」意味着思考和工具调用是在同一条轨迹里一起被优化的, 而不是先训思考, 再外挂工具. 这和 K2 报告里 Agent RL 的做法一脉相承, 但 K2 Thinking 具体沿用了多少 K2 的环境和奖励, 同样没有公开. 本页唯一一处真正的训练披露, 是后面的 INT4 量化感知训练.

## 2. 两处机制

### 2.1. thinking agent: 交错思考与工具调用

「thinking agent」和「输出很长的 CoT」不是一回事. 博客反复强调的是**交错**(interleaved): 推理和工具调用轮流进行, 规划, 执行, 调整都在数百步的尺度上发生. 搜索一节把循环写得很具体: think → search → browser use → think → code, 不断提出和修正假设, 核对证据, 构造连贯答案, 把含糊的开放问题拆成可执行的子任务. 页 2 举了一个例子, 一道博士级数学题经 23 次交错推理和工具调用解出. 页 2-3 的数学公式 OCR 损坏严重(Lorentz 模型采样, `Function Sampling`, $\ell_k(n)$ 等), 只能当作叙事证据, 无法据此还原原题.

产品入口有一层时间差. 聊天模式在 kimi.ai 上已上线, 完整的 agentic 模式「即将开放」; API 已经可用. 脚注 [1] 写得很清楚: 为了让聊天体验轻快, 聊天模式只部署部分工具, 并减少工具调用轮次, 因此聊天**不能**复现榜单分数. 拿网页聊天的截图去对照 HLE 44.9, 协议上已经错位. 榜单上的 200-300 步, 对应的是评测协议和尚未全量开放的完整模式.

**交错和「先想完再动手」的差别在于错误能不能被中途纠正.** 一次性写完长 CoT 再调用工具, 前提错了只能等整段推理结束才暴露; 交错模式下每次工具返回都是一次外部校验, 模型可以在下一段思考里推翻上一步的假设. 社区里讨论 interleaved thinking 时常拿 ReAct 做参照: ReAct 是提示层面的「想一步, 做一步」, 靠模板驱动; K2 Thinking 声称的是把这种节奏训练进权重, 每轮思考可以很长, 轮数也可以很多. 这种区别在本页只能从「端到端训练」(模型卡)和「数百步保持连贯」(正文)两句话里读出来, 训练轨迹长什么样, 奖励怎样分配到几百步里的每一步, 本页没有交代.

交错思考还把一个工程问题推到台前: 思考内容要不要跨轮保留. 如果每轮工具调用之后丢掉之前的推理, 模型每次都要重新想一遍自己为什么走到这里; 保留下来, 上下文又会很快被撑满. 本页没有直接讨论这个取舍, 但脚注 [4] 的上下文管理策略给出了官方评测时的答案: 丢弃之前所有的工具输出. 脚注只说隐藏工具输出, 按字面推断, 思考内容和对话是保留的. 第 3.2 节会结合步数预算算一下, 为什么这个取舍躲不开.

### 2.2. INT4 QAT: 为什么思考模型更怕量化

「Inference Efficiency」一节是本页唯一的训练与部署机制披露. 它先承认一个矛盾: 低比特量化能降低大规模推理服务的延迟和显存占用, 但思考模型的解码长度极长, 常规量化往往导致性能大幅下降. 对策是在后训练阶段做**量化感知训练**(QAT), 对 MoE 组件施加 INT4 weight-only 量化. 这样 K2 Thinking 支持原生 INT4 推理, 生成速度提升约 2 倍, 同时保持领先表现. 博客特别说明, **所有基准结果都在 INT4 精度下报告**.

为什么思考模型更怕量化, 本页只给了「解码长度长」一句. Kimi 基础设施团队的工程师后来在知乎上公开解释过背后的观察: 事后量化(PTQ)在短回复上看不出问题, 但生成越长, 量化误差越容易累积; PTQ 还依赖校准集, 稀疏 MoE 里很少被校准数据命中的专家会出现知识失真. QAT 的标准做法是在训练前向中插入伪量化, 反向用直通估计(STE)传梯度, 让权重在训练期就适应低比特. 这些解释不在本页, 这里只用来理解机制. 量化方法的整体谱系见 [6.3.1-量化](../../../../LargeLanguageModelGuide/6-训练与推理优化/6.3-模型压缩/6.3.1-量化/6.3.1-量化.md), MoE 量化的专门讨论见 [09-MoE模型量化技术综述](../../../../LargeLanguageModelGuide/6-训练与推理优化/6.3-模型压缩/6.3.1-量化/05-MoE模型量化技术综述/05-MoE模型量化技术综述.md).

「weight-only」三个字也要读准: 权重量化到 INT4, 激活仍用更高精度, 推理内核和「权重激活全 INT4」不同. 本页没有说注意力和路由部分是否量化, 没有给 QAT 数据配比, 也没有和 FP8 或 BF16 的对照表. 「约 2 倍」是官方概括, 部署时需要自己实测. 对评测读者来说还有一个直接后果: 表上每个 K2 Thinking 的格子都带着 INT4 条件, 拿别家 BF16 分数横比时要标出来. 官方把领先成绩建立在 INT4 上, 等于把「跑得快」和「分数高」作为同一份交付.

为什么只量化 MoE 部分就能换来约 2 倍速度, 可以粗算一下(结构数字取自模型卡). 1T 总参里绝大多数在 384 个专家的 FFN 里, 注意力和共享部分只占小头. 专家权重从 BF16 的每参数 2 字节降到 INT4 的 0.5 字节, 整体权重体积从约 2TB 降到 600GB 上下, 同样的机器能放下更大的 batch 或更长的 KV cache. 长解码阶段每生成一个 token 都要把激活到的专家权重从显存读一遍, 这一步受显存带宽限制, 读的字节数减半或减到四分之一, 速度就接近线性提升. 官方的「约 2 倍」与这种带宽受限的直觉吻合, 但本页没有给对照的基线精度, 是相对 FP8 还是 BF16 无从判断.

放回家族里看, 这是 Kimi 第一次在发布材料里把部署精度当作训练决策来讲. K2 报告讲的是训练时激活用 FP8 存储以省显存, 属于训练效率; K2 Thinking 讲的是推理权重从后训练阶段就按 INT4 来练, 属于服务效率. 两者都和低比特有关, 解决的却是不同阶段的问题, 不要把 K2 的 FP8 激活和 K2 Thinking 的 INT4 权重混为一谈.

## 3. 评测与谱系

### 3.1. 推理与数学: 三种设定分开读

页 6 推理块把「无工具, 带工具, heavy」三列粘成了一串, 按列切分后(读表): HLE 纯文本子集 23.9 / 44.9 / 51.0; AIME 2025 无工具, 带 Python, heavy 分别为 94.5 / 99.1 / 100.0; HMMT 2025 为 89.4 / 95.1 / 97.5. 同一块的 GPT-5(High) 为 HLE 26.3 / 41.7 / 42.0, AIME 94.6 / 99.6 / 100.0, HMMT 93.3 / 96.7 / 100.0; K2 0905 为 HLE 7.9 / 21.7, AIME 51.0 / 75.2, HMMT 38.8 / 70.4(均为读表). 页 7 格子清晰: IMO-AnswerBench 78.6, GPQA-Diamond 84.5.

heavy 是另一种算力档位. 脚注 [6] 说明 **Heavy Mode** 先并行展开 8 条轨迹, 再反思聚合生成最终结果; GPT-5 列的 heavy 对应官方 GPT-5 Pro 分数. 两边都叫 heavy, 实现未必相同. 引用 heavy 分数时应写明「八轨迹聚合」, 不要和单轨迹主表分数混在一起. 竞赛数学在带 Python 或 heavy 设定下接近满分, 这是 K2 Thinking 的强项, 但 GPQA-Diamond 84.5 仍低于 Grok-4 的 87.5 和 GPT-5 的 85.7.

脚注 [2] 给出这些分数的预算: 除 SciCode 按官方用 temperature 0.0 外, 其余都用 temperature 1.0, 上下文 256k. 思考 token 上限按题型分档: HLE(无工具), AIME25, HMMT25, GPQA 为 96k; IMO-AnswerBench, LiveCodeBench, OJ-Bench 为 128k; Longform Writing 的补全上限为 32k. 重复次数: AIME 和 HMMT 无工具 avg@32, 带 Python avg@16, IMO-AnswerBench avg@8. temperature 1.0 下方差不小, 所以要靠多次平均压下来. 没有这些预算信息, 直接横比谁分高会失真.

同一张表还能看出工具带来的增益并不均匀(读表, 下同). K2 Thinking 的 HLE 从无工具 23.9 到带工具 44.9, 涨了 21.0 个点; GPT-5(High) 从 26.3 到 41.7, 涨 15.4; DeepSeek-V3.2 从 19.8 到 20.3*, 几乎不动. AIME 2025 上 DeepSeek-V3.2 无工具 89.3, 带 Python 反而掉到 58.1*. 带星号的格子是 Moonshot 按 K2 Thinking 的条件重测的, 不是 DeepSeek 自报, 框架和提示对它未必友好. 即便打个折扣, 这组数字也说明**「给模型工具」和「模型会用工具」是两回事**, 工具增益大小取决于后训练里有没有专门练过交错调用. K2 Thinking 无工具时的 HLE 低于 GPT-5, 带上工具后反超, 它的优势主要来自工具使用这一面.

heavy 档位里也有类似的结构. K2 Thinking 的 HLE heavy 为 51.0, Grok-4 为 50.7, GPT-5 Pro 为 42.0. 从带工具单轨迹到八轨迹聚合, K2 Thinking 再涨约 6 个点, GPT-5 只涨 0.3. 并行多条轨迹再聚合, 是另一种 TestingTime 多花算力的方式, 和单条轨迹拉长走的是两条路. 本页没有说聚合时用的是投票, 打分还是再生成, 只写了「反思性聚合」, 因此无法判断 heavy 的收益有多少来自聚合器本身.

### 3.2. Agent 搜索: 从 7.4 到 60.2

BrowseComp 考察的是持续浏览, 搜索, 并对难找的真实网页信息做推理. K2 Thinking 60.2%, 博客给出的人类基线是 29.2%. 页 7 的搜索块还有 BrowseComp-ZH 62.3, Seal-0 56.3, FinSearchComp-T3 47.4, Frames 87.0. 对照 K2 0905: BrowseComp 7.4, BrowseComp-ZH 22.2, Seal-0 25.2, FinSearchComp-T3 10.4, Frames 58.1. 这是整张表里跃升最大的一块, 很难用「同一个模型多训一轮」来解释, 更像能力形态的切换.

页 4 的三张图是一条演示链: 一道多约束人物谜题(大学创立年份区间, 大学运动员, 短暂的职业橄榄球经历, 2010 到 2020 年间的外星入侵科幻片, 监狱剧里放错犯人的狱警, 最喜欢的医疗剧角色), 以及界面上多轮「搜索, 推理完成」的片段. 源文截断在推理过程中, 没有写出最终答案, 这里也不猜.

搜索分数的协议写在脚注 [4], 比正文更关键. 工具集是 search, code-interpreter, web-browsing. BrowseComp-ZH, Seal-0, FinSearchComp-T3 报 avg@4. 裁判用 o3-mini, 配置与官方 HLE 设置一致, 提示原文取自官方仓库. HLE 最多 120 步, 每步推理预算 48k token; 搜索任务最多 300 步, 每步 24k token. 累积输入超过 256k 时, 采用一个简单的上下文管理策略: **隐藏之前所有工具输出**. 这种做法保住了对话和思考痕迹, 丢掉旧的工具返回, 给新观察腾出窗口; 本页没有说它是最优方案, 只说评测时用了它. 另外, 访问 Hugging Face 可能导致 HLE 等测试泄题, 不屏蔽时 HLE 可达 51.3, 正式对比屏蔽了 Hugging Face. 51.3 和 44.9 不能混用.

把步数和每步预算乘起来, 能看出上下文管理为什么绕不开. 搜索任务 300 步乘每步 24k token, 推理 token 的理论上限约 7.2M; HLE 的 120 步乘 48k 约 5.8M(实际每步远用不满预算). 上下文窗口只有 256k, 即便每步只用掉预算的一小部分, 再加上网页和代码执行的返回, 几十步之后就会顶到窗口. 所以**「隐藏旧工具输出」不是锦上添花的技巧, 而是 300 步评测能跑完的前提**. 这也说明 BrowseComp 的 60.2 同时考了模型和这套管理策略, 换一种上下文处理方式, 分数未必一样.

搜索块的跃升幅度也值得和第 3.1 节对照. K2 0905 的 BrowseComp 只有 7.4, 到 K2 Thinking 变成 60.2, 而同期编码分数只涨了两三个点. K2 0905 没有思考模式, 底座结构按模型卡又没有改动, 差距主要来自后训练: 长推理, 交错工具调用, 以及可能扩大了的搜索类训练环境. 本页没有给出搜索数据或环境规模, 这个归因只能停在推断. 对照 GPT-5(High) 的 54.9 和 Claude Sonnet 4.5 Thinking 的 24.1, 可以看出 BrowseComp 对长链工具调用能力非常敏感, 单靠推理强未必能拿高分.

### 3.3. 编码: 温和的提升, 条件要一起记

编码三项主分: SWE-Multilingual 61.1%, SWE-Bench Verified 71.3%, Terminal-Bench 47.1%. 页 7 还有 Multi-SWE-bench 41.9, SciCode 44.8, LiveCodeBench v6 83.1, OJ-Bench (cpp) 48.7. 相对 0905, SWE-Bench Verified 从 69.2 到 71.3, Terminal-Bench 从 44.5 到 47.1, Multilingual 从 55.9 到 61.1, 提升比搜索温和得多. LiveCodeBench v6 从 56.1* 跳到 83.1 最大, 但 0905 那格带星号, 表示是在 K2 Thinking 的条件下重测的.

脚注 [5] 交代了编码的框架: Terminal-Bench 用默认 Terminus-2 框架和官方 JSON 解析器, 表头因此写「w/ simulated tools (JSON)」; 其余编码任务用内部框架, 基于 SWE-agent 改造, 收紧 Bash 和 Edit 工具的上下文窗口, 并按任务语义重写系统提示; 所有编码分数都是 5 次独立运行的平均. 对照 Claude Sonnet 4.5 Thinking 的 77.2 或 GPT-5(High) 的 74.9 时, 要把框架条件写进同一句话. 博客还展示了单提示生成的组件密集网站, Word 克隆和 WebWord 功能列表(富文本, 表格, 查找替换, 快捷键等), 这些是定性演示, 前端能力本页没有独立的评测分数.

编码块里 K2 Thinking 并不总是领先. SWE-bench Verified 上 Claude Sonnet 4.5 Thinking 77.2, GPT-5(High) 74.9, 都高于 71.3; Terminal-Bench 上 Claude 51.0 也高于 47.1; LiveCodeBench v6 和 OJ-Bench 上 GPT-5 的 87.0* 和 56.2* 也更高. K2 Thinking 高过 GPT-5 的是 SWE-bench Multilingual(61.1 对 55.3*)和 Multi-SWE-bench(41.9 对 39.3*), 但这两项仍低于 Claude 的 68.0 和 44.3; 三家里分数最高的只有 SciCode, 44.8 对 Claude 44.7, 差距在噪声范围内. 其中不少对照格带星号, 是在 Moonshot 自己的框架下重测的. 读这块时最稳妥的结论是: **编码能力相对 0905 有提升, 在开源模型里靠前, 对闭源前沿大多落后几个点**.

编码和搜索的对比还能看出这一代后训练的重心. 编码分数本来就靠 K2 那套 Agent 数据练得不错, 思考模式带来的是边际增益; 搜索在 0905 上几乎空白, 思考加交错工具调用一上来就补满. 本页没有给各类训练数据的配比, 这只是从分数形状推回去的读法, 不能当作官方说明.

### 3.4. 通用与写作

页 5 把通用能力分成三条. 创意写作: 完整度和丰富度提升, 风格与指令把握更稳. 实用写作: 推理更深, 视角更广, 指令遵循更精确, 在学术和长篇分析写作里强调严谨和连贯. 个人与情感: 回应更有同理心, 更平衡, 给出可执行的下一步. 随后是一段科幻样章「I was never meant to report. I was meant to refract.」, 讲气象控制 AI Cumulus-7 的独白, 充满寄存器地址, 冰晶数量, 频段带宽这类虚构数字. 它是创意写作样例, 不是科学主张.

页 7 通用块给出可对照的分数: MMLU-Pro 84.6, MMLU-Redux 94.4, Longform Writing 73.8, HealthBench 58.0. Longform Writing 比 0905 的 62.8 高, 与「实用写作更完整」的说法同向, 但仍低于 Claude Sonnet 4.5 Thinking 的 79.8. HealthBench 高于 0905 的 43.8 和 DeepSeek-V3.2 的 46.9, 却明显低于 GPT-5(High) 的 67.2. MMLU-Pro 也低于 Claude 的 87.5 和 GPT-5 的 87.1. 三条写作主张没有配消融实验, 科幻样章说明能写出有风格的长文, 基准分说明在特定测试上的位置, 两类证据不能混用.

### 3.5. 基线从哪来, 以及这一代在谱系中的意义

脚注 [3] 说明基线来源: GPT-5, Claude Sonnet 4.5, Grok-4, DeepSeek-V3.2 的分数引自各家博客, system card 和公开排行榜; 没有公开分数的, 在与 K2 Thinking 相同的条件下重测并标星号; GPT-5 的 reasoning effort 设为 high. HLE 的对照最绕: 官方公布的 GPT-5 和 Grok-4 全集带工具分数是 35.2 和 38.6; 内部在纯文本子集上测得 GPT-5 41.7, Grok-4 38.6(Grok-4 发布时自报纯文本子集 41.0); GPT-5 纯文本无工具分取自 Scale.ai, 全集无工具官方分为 24.8. IMO-AnswerBench 上, 基准论文里 GPT-5 为 65.6, 用官方 API 重评为 76. **同一模型多个分数并存时, 脚注比表头可靠.** DeepSeek-V3.2 和 Grok-4 两列有不少「-」, 缺格表示本页没有可对齐的数字, 不代表对方为零.

把这一代放回「一个模型由哪些面一起做出来」的框架里看, 各面的信息量很不均衡. 训练数据: 本页零披露, 只能从搜索分数的跃升推测后训练环境扩大过. 结构: 本页零披露, 模型卡说与 K2 相同, 即 MLA 加 384 专家的 MoE, 结构演进这一面在 K2 Thinking 上是停住的. 优化算法和预训练: 沿用 K2 的底座, MuonClip 和 15.5T token 预训练都属于上一代. 后训练: 唯一明确的是 INT4 QAT 放在后训练阶段, 以及模型卡里「端到端学会交错调用」一句, RL 算法, 奖励和轨迹长度都没给. 评测: 这是本页最厚的一面, 预算, 重复次数, 裁判, 步数上限, 上下文策略, 泄题处理都写进了脚注. 一篇发布博客把大部分篇幅给了评测协议, 读者能核对的主要也就是这部分.

这种不均衡决定了引用方式. 说「K2 Thinking 在 BrowseComp 上 60.2」时, 应一并交代 INT4, 300 步, 每步 24k, 隐藏旧工具输出, 屏蔽 Hugging Face 这些条件; 说「K2 Thinking 用了什么训练方法」时, 只能回答本页没有技术报告, 能确认的只有 QAT. 家族里与之对照最清楚的是 k1.5: 那篇报告把 RL 算法, 长度惩罚, 训推一体都摊开了, 却没有开源权重; K2 Thinking 开源了权重, 训练细节反而收了起来.

放回 Kimi 家族, K2 Thinking 是第一次把「长推理」和「大量工具调用」放进同一个开源模型. k1.5 提出上下文长度相当于搜索步数, K2 Thinking 把这个思路推到工具层面: 不仅想得长, 还要在几百步工具调用里保持方向. 它也把 INT4 QAT 带进了家族, 从这一代开始, 部署精度成了训练期就要考虑的问题. 它缺的面同样清楚: 没有技术报告, 数据, 结构改动和 RL 细节都没公开; 模型只处理文本, 视觉仍要等到 K2.5. 交错思考, 上下文管理和原生低比特推理这三件事, 是从这一代开始进入 Kimi 的产品线的, 后面几代在这三点上各有延续和调整, 需要分别看各自的材料.

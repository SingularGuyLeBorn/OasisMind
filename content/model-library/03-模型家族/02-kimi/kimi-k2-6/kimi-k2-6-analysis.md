# Kimi K2.6: 长程编程和更大的 Swarm, 一篇没有训练细节的发布博客

源文是产品发布博客, 没有技术报告; 结构, 训练数据, 预训练和后训练一个数字都没给, 能讲的只有公开表, 几段演示和评测脚注.

来源: 同目录 `kimi-k2-6.md`, 即 Kimi K2.6 Tech Blog: Advancing Open-Source Coding(页标记 `page 1 of 20` 到 `page 20 of 20`, 抓取时间标注 2026/9/25). 对照译稿见 `kimi-k2-6-bi.md`. 第 2 至 4 页的 General Agents, Long-Horizon Coding 柱状图在源 md 里只有文件名, 没有转成文字, 下文不读图估数.

## 1. 家族位置与披露范围

### 1.1. 在家族里的位置

K2.6 接在 K2.5 之后, 权重开源, 同时通过 Kimi.ai, Kimi App, API 和 Kimi Code 四个入口上线. 博客给它的三个关键词是编程, 长程执行和 Agent Swarm. 编程和 Swarm 都是 K2.5 已有的能力, K2.6 的叙述重点是「更长, 更大」: 单次任务能跑十几个小时, 上千次工具调用; Swarm 的规模从 K2.5 的 100 个子智能体, 1,500 步, 扩到 300 个子智能体, 4,000 步.

抓取时的页面已经把 Kimi K3 放进了对比表, 还写了一句 K3 在所有企业级基准上都超过 K2.6, 增益在指令遵循, 推理和多步任务稳定性. 这说明博客在 K3 发布后更新过, 读的时候要把它当成**「K3 时代回看 K2.6」的材料**, 而不是 K2.6 发布当天的原貌.

### 1.2. 这一页交代了模型的哪些面

模型怎么做出来, 本页几乎没说. 参数量, 专家数, 注意力形式, 上下文长度的训练方式, 训练 token 数和数据构成, RL 算法和奖励设计, 正文都没有. 唯一和训练沾边的是脚注里的推理设定: 默认开思考, 上下文 262,144 token. Hugging Face 模型卡另有一句, K2.6 的交错思考和多步工具调用设计与 K2 Thinking 相同; 这句不在本页, 只用来理解后文的 preserve thinking.

评测这一面反而写得细. 脚注分五节, 交代了对照模型的推理档位, 采样参数, 各基准的最大生成长度, 工具集, 上下文管理策略, 重复次数, 以及 APEX-Agents 剔除了哪些任务. 所以这篇的读法和 K2 Thinking 博客类似: **训练黑箱, 评测协议透明**. 另外几块是内部基准(Kimi Code Bench, Kimi Design Bench, Claw Bench)和演示案例, 它们只给了「相对 K2.5 显著提升」一类结论, 没有逐项分数.

## 2. 分数与演示

### 2.1. 公开表: 五项分数和它们的口径

第 2 页的表只有五行. 推理: Humanity's Last Exam 54.0(K3 58.7, GPT-5.4 52.1), GPQA Diamond 88.4(91.2, 89.6), AIME 2026 93.3(96.7, 95.0). 编码: SWE-Bench Pro 58.6(63.4, 57.7), Terminal-Bench 2.0 66.7(71.8, 65.4). 相对 GPT-5.4, K2.6 在 HLE, SWE-Bench Pro, Terminal-Bench 上分别高 1.9, 0.9, 1.3 个点, GPQA 和 AIME 分别低 1.2, 1.7 个点; 相对 K3 五项全低, 差距在 2.8 到 5.1 个点之间.

脚注 2 补了 HLE 的口径: 表上默认是 HLE 全集, 最大生成 98,304 token; 纯文本子集上 K2.6 无工具 36.4%, 带工具 55.5%. 表里的 54.0 没有写明是否带工具, 从数值接近 55.5 看, 应是带工具的全集分数, 这是推断. 对照 K2.5 报告, HLE-Full 带工具从 50.2 到 54.0, 文本子集带工具从 51.8 到 55.5, 两代之间约涨 4 个点(跨页对照, 两边协议大体一致但未逐项核对).

对照模型的档位写在脚注 1: K2.6 和 K2.5 开思考, Claude Opus 4.6 用 max effort, GPT-5.4 用 xhigh, Gemini 3.1 Pro 用 high. K2.6 默认 temperature 1.0, top-p 1.0. 这里的 top-p 和 K2.5 报告的 0.95 不同, 采样更放开. 没有公开分数的对照项在同等条件下重测并标星号, 其余引自官方. GPT-5.4 和 Claude 4.6 的 IMO-AnswerBench 分数取自智谱 GLM-5.1 的博客, 属于转引.

### 2.2. 两个长程编程演示

长程编程一节先给了一句总述: 在 Rust, Go, Python 等语言和前端, devops, 性能优化等任务上泛化可靠; 内部 Kimi Code Bench 覆盖多种复杂的端到端任务, K2.6 相对 K2.5 「显著提升」. 这两句都没有数字, 撑起这一节的是两个演示.

第一个演示在 Apple M3 Max 上本地部署 Qwen3.5-0.8B, 用小众语言 Zig 实现并优化推理. 过程超过 4,000 次工具调用, 连续执行 12 小时以上, 迭代 14 轮, 吞吐从约 15 提到约 193 token/s, 最后比 LM Studio 快约 20%. 平均下来每分钟五六次工具调用. 博客用 Zig 的冷门来论证分布外泛化.

第二个演示改造一个有 8 年历史的开源撮合引擎 exchange-core. 13 小时里尝试 12 种优化策略, 发起 1,000 多次工具调用, 改动 4,000 多行代码; 模型读 CPU 和内存分配的火焰图找瓶颈, 把核心线程拓扑从 4ME+2RE 改成 2ME+1RE. medium 吞吐从 0.43 到 1.24 MT/s, 博客写作提升 185%; performance 吞吐从 1.23 到 2.86 MT/s, 写作提升 133%. 按比值算, 前者约 2.9 倍, 后者约 2.3 倍, 和百分比口径一致.

这两个演示有共同的局限: 单次运行, 没有对照组, 没有说明 harness 和工具集, 也没有给失败的尝试. 它们能说明模型可以在十几个小时的会话里保持目标并持续迭代, **不能当作可复现的评测**. 可复现的编码分数只有公开表里的两项, 以及只给结论的内部 Kimi Code Bench.

### 2.3. 企业内测和前端生成

第 7 页说 K2.6 在企业内测的长程编程任务中表现好, 按随机顺序列了合作方的评价. 页面是轮播, 标着 01 / 13, 抓取只拿到第一条 Qoder: 相对 K2.5, 工具调用和模型调用的频率明显上升, Qoder 把它解读为更主动, 能更早抓住开发者意图并自动补全上下文, 减少打断和等待. 其余 12 条没有抓到, 本页不补.

**「调用更频繁」本身是中性的观察.** 它可能意味着模型更愿意先查再改, 也意味着单任务 token 和延迟上升; 博客只取了前一种解读. K2.5 报告表 5 里, K2.5 在 AIME 2025 上平均输出约 25k token, 多于 Gemini-3.0 Pro 的 15k 和 DeepSeek-V3.2 的 16k; 这条家族趋势放在前面, K2.6 的成本面值得单独测, 本页没有给.

Coding-Driven Design 一节讲前端生成: 从简单提示生成完整页面, 包括 hero 区, 交互元素和滚动触发动画, 并能调用图像和视频生成工具补素材; 范围扩到轻量全栈, 覆盖鉴权, 用户交互和数据库操作, 例子是交易记录和会话管理. 内部 Kimi Design Bench 分视觉输入, 落地页构建, 全栈应用开发, 通用创意编程四类, 对比方是 Google AI Studio 里的 Gemini 3.1 Pro, K2.6 走 kimi.com 自己的 harness. 第 9 页的胜平负图没有转成文字, 只能知道这是一次成对比较, 两边的工具和 harness 都不一样, 比的是产品整体而不是模型本身.

## 3. 新机制与产品形态

### 3.1. Preserve thinking: 跨轮保留思考内容

脚注 4 说 Terminal-Bench 2.0 在 **preserve thinking** 模式下测. 本页没解释这个词. 从 Hugging Face 模型卡和官方 API 文档看, 它指多轮对话里把之前各轮的 reasoning_content 原样回传给模型, 让模型接着之前的思路想; 模型卡的例子是模型在思考里想了五个数, 只说出前三个, 下一轮问剩下两个是什么, 开启保留后模型能答出来. 这个功能默认关闭, 官方 API 用 `thinking.keep` 参数控制, 默认不保留, 设为 `"all"` 才保留.

**它和 K2 Thinking 的交错思考是两层.** 交错思考管的是单个任务内部, 思考和工具调用轮流进行; preserve thinking 管的是跨轮次, 用户新发一条消息之后, 之前轮次的思考还在不在上下文里. Terminal-Bench 这类多轮终端任务, 前几轮对环境的推理如果丢了, 后面容易重复试错, 所以评测特意打开. 引用 66.7 时要连同这个设定一起写, 在默认关闭的 API 调用里未必能复现.

这也把上下文管理的矛盾往前推了一步. 保留历史思考, 上下文涨得更快; K2 Thinking 评测时「隐藏旧工具输出」的做法, 在这里变成了由请求参数决定保留什么. 本页没有讨论这个取舍, 上面对机制的描述来自模型卡和 API 文档, 不在本页.

### 3.2. Swarm 变大, 以及 Claw 系列

Swarm 一节的可核对信息只有规模: 最多 300 个子智能体, 4,000 个协调步, 分别是 K2.5 的 3 倍和约 2.7 倍. 博客说它能组合异构技能, 比如广搜叠加深研, 大规模文档分析接长文写作, 一次运行交付文档, 网站, 幻灯片和表格. 另一个新能力是把高质量的 PDF, 表格, 幻灯片, Word 文档转成 Skills, 保留结构和风格, 供后续任务复用. 编排器怎么训练, PARL 奖励和关键步数有没有变化, 本页一个字没提, 训练机制只能参照 [K2.5 的解析](../kimi-k2-5/kimi-k2-5-analysis.md).

主动式智能体一节提到 OpenClaw, Hermes 这类 7×24 常驻的 agent 框架, 以及 RL 基础设施团队用 K2.6 驱动的 agent 自主运维 5 天的自用案例. 量化靠内部 Claw Bench, 覆盖编码, IM 生态集成, 信息研究与分析, 定时任务管理, 记忆利用五个领域, 结论是任务完成率和工具调用准确率全面高于 K2.5, 没有分数. 博客把改进归为三点: API 理解更准, 长时间运行更稳, 长研究任务中的安全意识更强; 这三点对应什么训练改动, 没有交代. **Claw Groups** 是研究预览, 允许不同设备, 不同模型的 agent 和人一起进入共享空间, K2.6 当协调器, 按技能和工具匹配任务, 检测失败后改派或重新生成子任务. 团队自己用它跑营销流程, Demo Maker, Benchmark Maker, 社媒和视频几类 agent 分工, K2.6 负责协调和汇总中间结果. 这部分是产品形态, 没有评测.

## 4. 评测协议与复现

### 4.1. 评测脚注: 上下文策略各不相同

脚注 3 最值得细看. HLE 带工具, BrowseComp, DeepSearchQA, WideSearch 都配 search, 代码解释器和网页浏览工具, 系统提示与 K2.5 报告相同. HLE-Full 带工具时最大生成 262,144 token, 每步上限 49,152, 超过阈值只保留最近一轮工具消息. BrowseComp 用 discard-all, 和 K2.5, DeepSeek-V3.2 一样. DeepSearchQA 不做上下文管理, 超长直接记失败, 对照分数引自 Claude Opus 4.7 System Card. WideSearch 用 hide tool result. **同一类「搜索 agent」基准, 用了三种不同的上下文策略**, 横比时要一并交代.

其余几条: Claw Eval 用 1.1 版, 每步最多 16384 token; APEX-Agents 在公开的 480 个任务里评了 452 个, 剔除了依赖外部运行时的 Investment Banking Worlds 244 和 246, 与 Artificial Analysis 的做法一致. 编码方面, Terminal-Bench 2.0 用默认 Terminus-2 框架和官方 JSON 解析器; SWE-Bench 系列用基于 SWE-agent 改造的内部框架, 工具只有 bash, createfile, insert, view, strreplace, submit; 所有编码分数取 10 次独立运行的平均, 比 K2.5 报告的 5 次多一倍. 视觉评测最大生成 98,304, avg@3; 带 Python 工具时每步 65,536, 最多 50 步.

### 4.2. 复现: 官方 API 与 KVV

「Benchmark Table」一节只有两句: 复现官方结果建议用官方 API; 用第三方服务的话, 参考 **Kimi Vendor Verifier**(KVV)挑准确度高的供应商. 开源权重意味着同一个模型名会出现在很多推理服务商那里, 而量化, chat template 配置, 工具调用格式解析, 上下文截断都可能让结果变差, 表面上回答正常, 分数却掉了.

KVV 的具体做法不在本页. 按 GitHub 项目说明, 它最早针对 K2 的工具调用: 用约 4,000 条请求比较各服务商与官方 API 的工具调用触发一致性和 JSON schema 准确率; 后来扩展成多项检查, 包括 API 参数是否生效的预检, 视觉预处理, 以及用 AIME 这类长输出任务暴露 KV cache 和量化带来的退化. 放回家族里看, K2 报告附录 B 的工具调用 token 模板和约束解码, 0905 通告里的 Token Enforcer, 到这里变成了面向第三方部署的校验工具, 关注点从「模型会不会调工具」移到了「别人部署的模型调工具还准不准」.

# DeepSeek-V3.1: 一个检查点, 两种思考模式

> 公开材料是 2025-08-21 的官方动态, 共 7 页, 不是技术报告. 页上有: 混合推理开关, 编程与搜索 Agent 两张表, CoT 压缩后的长度对比图, Base 追加 840B token, UE8M0 FP8 比例因子, 分词器与 chat template 变更, API 与定价. 页上没有层数, 专家数, 数据配比, 后训练算法和消融.

来源: [DeepSeek-V3.1 Release](https://api-docs.deepseek.com/news/news250821/) (2025-08-21 官方发布页; V3.1 无 arXiv 论文) 与 [Hugging Face 模型页](https://huggingface.co/deepseek-ai/DeepSeek-V3.1).

本文大量引用了发布材料的表格和图片(受限于篇幅无法写进来)以及公式, 建议阅读的时候对照[原发布页](https://api-docs.deepseek.com/news/news250821/)观看。配套对照译稿见同目录的 bi 稿。

V3.1 是 V3 和 R1 两条线第一次并到同一个检查点上. 此前 DeepSeek 对外是两个模型: `deepseek-chat` 背后是 V3, `deepseek-reasoner` 背后是 R1; 两者共享 V3 底座, 但后训练分开做, 部署也分开. V3.1 的说法是「一个模型同时支持思考模式与非思考模式」, 两个 API 名还在, 背后换成同一份权重. 这份动态能讲清楚的是: 切换放在哪一层, Agent 分数涨了多少, 思考长度压掉多少, 部署要改什么. 它讲不清的是这些变化分别来自数据, 训练日程还是算法, 下面每节都会把这条边界说出来.

## 1. 混合推理: 开关在模板里

页上第一条变化是「混合推理架构」. App 与网页用「深度思考」按钮切换; API 侧 `deepseek-chat` 对应非思考模式, `deepseek-reasoner` 对应思考模式, 两者上下文都扩到 128K. 这里的「架构」不是网络结构意义上的架构, 页上没有任何层或模块的改动描述. 从同一权重对外提供两个路由名来看, 切换发生在输入格式上, 而不是换模型.

Hugging Face 模型卡把这层机制写得更具体, 它不在页上, 这里只用来核对: 思考模式的生成前缀以 `<think>` 结尾, 非思考模式直接以 `</think>` 结尾, 模型看到闭合标签就跳过推理段; 多轮对话里历史轮次的推理内容会被丢掉, 只保留 `</think>`. 这和页上「对分词器及 chat template 进行了较大调整」对得上: 同一个 decoder-only 网络, 靠 prompt 末尾的一个特殊 token 决定是否先写长推理. 代价是后训练必须同时覆盖两种前缀的数据, 两种行为共用一套参数, 本页没有给两类数据的比例, 也没有说是否用了分别训练再合并的做法.

## 2. 编程 Agent: 分数跳得最多的一块

编程智能体表对照三个模型: SWE-bench Verified 上 V3.1 为 66.0, V3-0324 为 45.4, R1-0528 为 44.6; SWE-bench Multilingual 为 54.5 / 29.3 / 30.5; Terminal-Bench 为 31.3 / 13.3 / 5.7. 按 SWE-bench Verified 的 500 题折算, 66.0 对 45.4 大约多修好 103 个仓库问题. Terminal-Bench 上 R1-0528 只有 5.7, 比非推理的 V3-0324 还低一半多, 说明长推理本身不会自动变成多步终端操作能力.

页上把提升归到「通过 Post-Training 优化」. 没有写轨迹数据从哪来, 有多少条, 用 SFT 还是 RL, 奖励怎么算, 也没有写评测用的 Agent 框架和最大步数. SWE-bench 分数受脚手架影响, 同一模型换一套工具调用框架, 分数会明显变化, 本页三个模型是否在同一框架下跑, 页上没有说明. 表里也没有标 V3.1 是思考还是非思考模式; 按模型卡, 工具调用只在非思考模式下支持, 编程表大概率是非思考模式的成绩.

## 3. 搜索 Agent: 多步检索涨, 单跳问答持平

搜索智能体表只对照 R1-0528: Browsecomp 30.0 对 8.9, Browsecomp_zh 49.2 对 35.7, HLE 29.8 对 24.8, xbench-DeepSearch 71.2 对 55.0, Frames 83.7 对 82.0, SimpleQA 93.4 对 92.3, Seal0 42.6 对 29.7. 七行的涨幅差别很大. Browsecomp 是要连续检索, 交叉排除才能找到答案的题, 涨了三倍多; Frames 和 SimpleQA 本来就接近饱和, 只涨 1–2 分. 读这张表, 能力变化集中在「搜多轮, 自己决定下一步搜什么」这一类.

这张表的 HLE 是带搜索工具的成绩. Terminus 的发布页里, V3.1 在「不带工具的推理模式」下 HLE 是 15.9. 同一个模型, 工具开关让 HLE 从 15.9 变成 29.8, 差了将近一倍, 所以引用 V3.1 的 HLE 必须带上协议. 页上也没有说搜索工具是哪家接口, 每题允许多少轮检索, 这些都会直接改变 Browsecomp 这类题的分数.

## 4. CoT 压缩: 少写 token, 分数持平

页上的效率结论是: 经过 CoT 压缩训练, V3.1-Think 在输出 token 减少 20%–50% 的情况下, 各项任务平均表现与 R1-0528 持平. 第 4 页的柱状图给了三组数: AIME 2025 上 R1-0528 平均 22,615 token, 准确率 87.5%, V3.1-Think 为 15,889 token, 88.4%; GPQA Diamond 为 7,678 token, 81.0% 对 4,122 token, 80.1%; LiveCodeBench 为 19,352 token, 73.3% 对 13,977 token, 74.8%(读图). 按这三组算, token 分别少了 29.7%, 46.3%, 27.8%, 落在页上说的区间内.

## 5. Base: 追加 840B token 的长上下文训练

开源段写: V3.1 的 Base 在 V3 基础上「重新做了外扩训练, 一共增加训练了 840B tokens」. 「外扩」指把上下文窗口往外扩. V3 报告里的上下文扩展分 32K 和 128K 两段, 用 YaRN 各训 1000 步, 按报告的 batch 和序列长度算, 两段合计约 126B token, 方法背景见 [长度外推: 从 PI 到 YaRN](../../../../llm-guide/2-核心原理与架构/2.5-长上下文与外推技术/RoPE/03-长度外推：从PI到YaRN的频率扩展.md). 840B 约是它的 6.7 倍, 也约等于 V3 预训练 14.8T token 的 5.7%.

本页没有给 840B 的阶段拆分, 也没有给数据构成. Hugging Face 模型卡另写了一组页外数字: 32K 阶段扩到原来的 10 倍, 共 630B token, 128K 阶段扩到 3.3 倍, 共 209B token. 这组数和上面的估算吻合: V3 每段约 63B token, 乘 10 与乘 3.3 分别是 630B 与 208B, 相加正好约 840B. 长上下文训练加了这么多, 说明 V3.1 的 Agent 能力可能部分来自底座对长轨迹的适应, 但本页没有把 Base 的变化和 Agent 分数联系起来, 也没有给 Base 的评测表.

## 6. UE8M0 与部署不兼容

页上的部署提醒有两条. 第一条是「DeepSeek-V3.1 使用了 UE8M0 FP8 Scale 的参数精度」. V3 的 FP8 训练给每个 1×128 激活块和 128×128 权重块配一个 FP32 比例因子, 见 [FP8 混合精度训练详解](../../../../llm-guide/6-训练与推理优化/6.1-训练基础设施/6.1.2-混合精度训练/02-FP8混合精度训练详解.md). UE8M0 把这个比例因子换成 8 位无符号数, 只有指数位, 没有尾数, 也就是只能取 2 的整数次幂, 编码时对 log2 向上取整再加 127 的偏置. 比例因子从 4 字节降到 1 字节, 反量化时乘以 2 的幂可以只改指数, 不引入额外舍入. 这种格式和 OCP MX 规范里的 E8M0 一致.

代价在精度利用上. 比例因子只能取 2 的幂, 向上取整后块内最大值映射到 E4M3 可表示范围的上半段, 最坏情况下只用到最大值 448 的一半左右, 相当于少用约 1 位的动态范围. 本页没有说块大小是否仍是 128, 也没有给 UE8M0 对损失或评测的影响. 第二条提醒是分词器和 chat template 与 V3 「存在明显差异」, 意味着 V3 的推理内核配置, tokenizer 文件和工具调用格式不能直接套用; 模型卡里另有一句, 路由偏置参数要用 FP32 加载, 这也不在本页.

## 7. API 与价格

API 侧还有两项变化. Beta 接口支持 strict 模式的 Function Calling, 页上的说法是确保输出的函数调用满足 schema 定义, 服务端具体用约束解码还是事后校验, 页上没有写, 对 Agent 框架来说少写一层格式修复; 另外新增 Anthropic API 格式, 可以把 V3.1 接进 Claude Code. 这两项都说明发布的目标用户是写代码的 Agent 场景, 和第 2 节的编程表是同一个方向.

新价自北京时间 2025 年 9 月 6 日 00:00 生效: 输入缓存命中 0.5 元/百万 tokens, 未命中 4 元/百万 tokens, 输出 12 元/百万 tokens, 同时取消夜间优惠. 按第 4 节的读图数字, V3.1-Think 做一道 AIME 2025 平均输出约 1.59 万 token, 输出费约 0.19 元; 同价下 R1-0528 的 2.26 万 token 约 0.27 元. 旧价是多少, 本页没有写, 所以不能从这份动态算出实际涨跌幅.

## 8. 谱系位置与缺口

V3.1 把 R1 的长推理并进 V3 的检查点, 用模板开关代替两套权重; 在 R1-0528 的基础上压掉约三到五成推理长度; 用 840B token 重做长上下文扩展; 把 FP8 比例因子换成 UE8M0. 后面的 V3.1-Terminus 在同一权重线上修语言混杂和 Agent 分数, V3.2-Exp 再在这条线上换注意力. 从谱系上看, V3.1 仍是 V3 的网络结构, 页上没有任何架构改动的证据, 变化集中在继续训练, 后训练和数值格式.

这份动态缺的部分很多: 层数, 专家数, 激活参数没有重复, 应视为沿用 V3 但页上没有明说; 后训练的数据量, 两种模式的配比, CoT 压缩的训练目标, Agent 轨迹的来源都没有; 评测没有给采样次数, 温度, Agent 框架; Base 模型没有评测表. 需要这些信息时, 只能回到 V3 报告核对底座, 回到 R1 报告核对长推理训练, 本页不能替代它们.

## 1. 这份报告讲了什么

Hunyuan-TurboS 是腾讯混元 2025 年 5 月挂到 arXiv 的技术报告, 编号 2505.15431, md 抓的是 7 月 4 日的 v3. 正文 18 页, 后面是作者名单, 参考文献和一页附录, 一共 26 页. 模型是 Transformer, Mamba2, FFN 三类层混排的 MoE 模型, 激活参数 56B, 总参数 560B, 128 层, 16T token 预训练, 上下文 256K. 报告自称是业界第一个落地部署的大规模 Mamba 模型. 对外能比的成绩有两组: LMSYS Chatbot Arena 1356 分, 排名列是 7; 23 个自动化基准平均 77.9%.

全文分五块. 第 2 节预训练, 讲数据流水线, 架构, 退火和长上下文扩展, 最后用表 2 和三个开源基座比. 第 3 节后训练, 四步: 融合 SFT, 自适应长短 CoT 融合, Deliberation Learning, 两阶段 GRPO, 中间插了一节通用奖励系统. 第 4 节评测, 有 Arena 榜, 表 4 的 23 个基准, 以及表 5 的平均输出长度. 第 5 节基础设施, 训练侧是 Angel-RL, 推理侧是 AngelHCF. 报告没有权重发布信息, 也没有消融表. 架构选择那段写 「广泛尝试了各种组合」, 只给结论, 没给数据.

几个核心数字在全文反复出现, 各处一致. 16T 出现在 Abstract, 引言, 贡献列表, 2.1 节, 表 1 和结论. 256K 出现在 Abstract, 引言, 贡献列表, 2.4 节, 表 2 和结论. 1356 和 77.9% 在 Abstract, 引言, 贡献列表, 第 4 节和结论里都没有变. 需要对着看的是那些只出现一两次的数, 比如 AMF/MF 的排法, SSM group, AVG. 的算法, 后面几节逐个说.

## 2. 128 层怎么数

128 这个数在 Abstract, 引言, 2.2 节, 表 1 各出现一次. 引言给了拆法: 57 层 Mamba, 7 层 Attention, 64 层 FFN, 57 + 7 + 64 = 128. 2.2 节补了一句定义: 每个 Attention, FFN, Mamba2 块各算一层. 所以这里的 「层」 是子层. 常见的 Transformer 把一个注意力加一个 FFN 算作一层, 这里要算两层. 拿 128 去和别的模型的层数直接比, 会高估 TurboS 的深度.

2.2 节给的比例是 FFN 50%, Attention 5.5%, Mamba2 44.5%. 64/128 正好 50%. 7/128 约 5.47%, 57/128 约 44.53%, 保留一位小数就是 5.5% 和 44.5%. 百分比是从层数算出来的, 两处说的是同一套配置.

块模式那句对不上. AMF 块是 Attention → Mamba2 → FFN, MF 块是 Mamba2 → FFN, 两种块交错排列. 7 个 Attention 只能落在 7 个 AMF 块里, 这 7 个块用掉 7 个 Mamba2 和 7 个 FFN. 剩下 50 个 Mamba2 全部配成 MF 块, 带出 50 个 FFN. 合起来 FFN 是 57 个, 总层数 121. 和 64, 128 相比, 差的 7 层都是 FFN. 报告没有给逐层排列, 也没说存在单独的 F 块. 也许某些位置是连着两个 FFN, 但报告没写, 这 7 个 FFN 放在哪里, 只能记成一个缺口.

## 3. MoE: 1 个共享专家和 32 个专项专家

引言那句 「32 experts, activating 1 shared and 2 specialized experts per token」 把专家数和激活数写在同一句, 字面上像是 32 个里选 3 个. 2.2 节和表 1 把它拆开了: 每个 FFN 层有 1 个共享专家, 32 个专项专家; 每个 token 激活 1 个共享加 2 个专项. 表 1 里共享专家一行, 专项专家一行, 激活的专项专家再一行. 所以每层一共 33 个专家, 每个 token 走其中 3 个. 共享专家对所有 token 都开, 路由只在 32 个专项专家里挑 2 个. 报告说策略和 Hunyuan-Large 相近, 没写路由打分函数, 也没写负载均衡怎么做. 训练时 capacity factor 取 1.5.

维度方面, 隐藏维 5120, 每个专家的中间维 17,024. 如果专家是三个矩阵的门控 FFN (报告没写), 一个专家约 3 × 5120 × 17024 ≈ 2.6 亿参数. 64 个 FFN 层, 每层 33 个专家, 专家部分约 552B. 每个 token 走 3 个专家, 激活的专家部分约 50B. 总参数 560B 减去 552B, 剩约 8B 给 Mamba2, Attention, 嵌入和其他部件. 激活参数 56B 减去 50B, 剩约 6B. 非专家参数对每个 token 都生效, 这两个剩余量本该相等, 差的 2B 左右可以算进 560B 和 56B 的取整. 这套估算至少说明, 5120 和 17,024 与报告给的两个参数量在同一量级.

表 2 把总参数和激活参数分成两行. 激活参数这一行, TurboS 的 56B 在四个模型里最大. 总参数这一行, TurboS 的 560B 排第二, 在 DeepSeek-V3 的 671B 后面. 2.5.2 节说 TurboS 是 「这组对比里最大的模型」, 只在激活参数一行成立.

## 4. Mamba2 和 Attention 各管什么

报告给 Mamba2 的角色是长序列效率: 状态空间模型, 复杂度随序列长度线性增长. 给 Attention 的角色是上下文理解, 全模型只放 7 层, 用 GQA 压 KV cache: 64 个查询头, 8 个 KV 头, KV cache 是全头注意力的八分之一. Attention 块里加了 QK normalization. 2.2 节说 Attention 的占比同时影响性能, 验证损失, KV cache 和推理效率, 所以压到 5.5%. 这是全文唯一交代架构取舍理由的地方, 没有附对比实验.

Mamba2 的超参数有 64 个并行头, chunk size 128, 表 1 另有 d state 128. SSM group 的写法两处不同. 正文写 「group size of 16」, 读作每组 16; 表 1 写 「# Mamba2 SSM Groups 16」, 读作 16 组. 按 64 个头算, 前者是 4 组, 后者是每组 4 个头. 报告里没有第三处能判断哪一种对.

推理侧还提到 Mamba 的一个毛病. 第 17 页说 Mamba 缺少全局注意力, Mamba 状态用 fp16/bf16 时会重复生成. 改成 fp32 以后, 长文本生成质量追上 Full Attention 模型, 数学和竞赛级编程任务的 token 消耗降了 35% 到 45%. 重复生成会拉长输出, 所以精度改动直接体现在输出长度上. 这组百分比是和 fp16/bf16 版本比, 不是和别的模型比, 也不在表 5 里.

## 5. 数据和预训练日程

图 2 把数据流水线分成三段. Pre-Processing 做 URL 级去重, URL 过滤, 块级剪枝和主题分类. Model-based Extraction 用文本抽取模型, 外加数学和代码的专用抽取模块, 抽出纯文本. Post-Processing 做启发式过滤和语义级去重. 另有评判模型和配比模型. 评判模型里有几条基础质量标准和几十个领域类型标签, 配比模型按预训练阶段给出数据配方. 报告没有给各来源的占比, 也没说过滤掉了多少.

训练量 16T token, 按 Hunyuan-Large 的分词器计, 词表 128K. 预训练序列长度 4096, 优化器 AdamW (β1 = 0.9, β2 = 0.95), 权重衰减 0.1. 学习率峰值和 warmup 没写. 退火从预训练末端的学习率开始, 按 cosine 快速降到 5e-6, 序列长度还是 4096, batch 约 900 万 token, 共 300B token. 退火数据是混合的: 高质量预训练数据, 代码, 数学, STEM 语料, 指令遵循数据 (含长 CoT), 以及合成数据.

退火的四条经验里, 有三条和后面的阶段直接挂钩. 第二条把相当一部分指令数据提前放进退火, 好处是 SFT 要做的少, RL 的空间更大. 第三条保留适量网页数据, 只对问答式数据算 target loss, 防止基座在该续写开放文本的时候去出考题. 第四条讲截断: 超过窗口的长 CoT 不截, 推迟到长上下文阶段再用. 四条都是定性描述, 没有比例, 也没有消融数字.

## 6. 256K 是窗口长度

长上下文扩展放在预训练最后. 课程是 4K → 32K → 256K, 和 Hunyuan-Large 一样. 位置编码用 NTK-aware, 32K 阶段 α = 50, 256K 阶段 α = 1000. 学习率固定 5e-6, batch 约 900 万 token. 32K 阶段 30B token, 256K 阶段 20B token, 短长数据 3:1. 报告还专门收集了跨领域, 跨体裁的长文档. 这里的 256K 是模型一次能放进的上下文窗口长度. 表 2 里 TurboS 和 Llama-4-Maverick 写的都是 256K, DeepSeek-V3 和 Qwen3 写的是 128K.

这一段有两处数值说不清. 一是 「略有增加的 token 量」 后面, 256K 阶段的 20B 反而比 32K 阶段的 30B 少, 「增加」 没有参照. 二是 batch 按 token 计: 900 万 token 在 4096 长度下约 2200 条序列, 在 256K 长度下只有约 34 条. 3:1 如果按 token 算, 每个 batch 里真正 256K 长的序列只有几条. 报告没给长上下文评测的结果, 比如 RULER 或 LongBench 一类. 第 13 页 RL 第二阶段有一条长上下文赛道, 配了专盯幻觉的 critic 和在线 RL, 同样没有数字.

按 batch 约 900 万 token 粗算步数: 退火 300B 大约 3.3 万步, 32K 阶段 30B 大约 3300 步, 256K 阶段 20B 大约 2200 步. 这几个步数是用报告里的 token 量除出来的, 报告本身没有印. 和 16T 的主预训练相比, 两段长上下文加起来只占 50B, 不到总量的千分之四. 窗口从 4K 拉到 256K, 靠的主要是 NTK-aware 的 α 取值和这一小段数据, 报告也承认这一步走得谨慎.

256K 和 thinking 是两件事. 256K 是预训练末期定下的窗口上限. thinking 是推理时多算, 也就是 TestingTime, 表现为同一个问题输出更长的推理. 表 5 里 TurboS 平均输出 1207.8 token, 离 256K 很远. 窗口长度限制的是一次能放多少输入和输出, thinking 决定的是一次回答花多少计算, 两者不在同一根轴上.

## 7. 预训练基座的成绩

表 2 把 TurboS 基座和 Llama-4-Maverick, DeepSeek-V3, Qwen3-235B-A22B 比. 对手的分数取公开结果里的最高值, 不是同一套流程重跑. Llama 和 Qwen3 很多格是 「-」. 四家都有数的只有 MMLU, MMLU-Pro, MMLU-Redux, BBH, SuperGPQA, MGSM, GSM8K, EvalPlus, MultiPL-E, MBPP, CRUX-O 这 11 行. 这 11 行里 TurboS 拿第一的有 MMLU 87.94, BBH 89.76, SuperGPQA 54.63, GSM8K 94.39 (和 Qwen3 并列), EvalPlus 78.99, MultiPL-E 67.13, MBPP 85.45.

落后的格也不少. MMLU-Pro 65.11 低于 Qwen3 的 68.18. MMLU-Redux 87.11 略低于 Qwen3 的 87.40. MGSM 77.64 在四家里最低. CRUX-O 75.88 低于 Llama 的 77.0 和 Qwen3 的 79.0. 只有 DeepSeek-V3 可比的格里, DROP 85.3 对 89.0, C-Eval 88.7 对 90.1, CCPM 90.11 对 92.0, HellaSwag 87.1 对 88.9, 都是 TurboS 低. 正文只提了 MMLU-Redux. 正文说代码 「总体最高」, 按五行平均大体成立, 逐行看 CRUX-O 不是. ## 8. 后训练: SFT 数据怎么来

SFT 数据共 300 万条, 按 13 个主题整理: 数学, 代码, 逻辑, 科学, 语言类任务, 创意写作, 英语与多语言, 复杂指令, 角色扮演, 知识问答, 多轮, 金融/法律/医疗, 安全 (近 1,000 个类别). 每个主题有自己的来源和质检. 数学用生成式奖励模型和验证器. 代码从开源仓库转成指令对, 再用 critic 和沙箱过滤. 逻辑用类似 ZebraLogic 的合成流水线, 难题交给人工. 科学用带 CoT 的 LLM 验证器处理单位换算和等价形式. 多轮对话分 6 类. 报告没有给各主题的条数.

推理数据的格式值得单独说. 之前的做法用系统提示切换思考模式, TurboS 把推理数据统一写成 `<problem, response>`, response 里可以带详细推理, 也可以不带, 由模型按题目难度决定进不进 thinking 模式. 非推理数据直接用原回答. 也就是说, TurboS 不给用户显式开关, 长短由模型自己选. 这和后面自适应长短 CoT 的训练目标一致.

图 3 把后训练画成四步. Step 1 是融合 SFT, 由 Reasoning Adaptive Teacher 产出推理数据, 再加非推理数据. Step 2 是 Deliberation Learning SFT, 包括弱点审议和多轮循环. Step 3 是推理 GRPO, 奖励系统有 Math, Science, Code, Logic 四格. Step 4 是通用 GRPO, 奖励系统有 14 格. 图和文字的步骤能一一对上.

## 9. 自适应长短 CoT: thinking 是 TestingTime

教师模型分两步训. SFT 这一步的数据构造有点绕. 先用推理数据训 Hunyuan-Base, 得到短 CoT 模型, 让它在全部推理数据上作答. 答对的直接收. 答错的, 把题目和错误回答交给 Hunyuan-T1 续写推理和答案, 再改写成短 CoT 的风格; 还不对就重来, 直到答对. 最后把所有失败尝试和正确回答拼在一起当训练回答. 所以一条 「长」 回答里装着前面的错误尝试和修正过程, 题越难, 回答越长. 用这批数据训 Hunyuan-Base, 得到自适应 SFT 模型.

RL 这一步有两种奖励. 难度自适应奖励: GRPO 采样时每个 prompt 生成推理深度不同的回答, 在线拒绝采样判断难度, 难题配长 CoT, 易题配短 CoT. 长 CoT 压缩奖励: 正确性相同时, 越短奖励越高. 两者合起来是该长则长, 能短则短. 报告没给长度惩罚的公式和系数.

thinking 模式在这里就是推理时多算, 也就是 TestingTime: 同一套参数, 难题多写几步, 易题少写几步. 它和参数量无关, 和 256K 窗口也无关. 效果体现在表 5. 评测集 6k 条, 30% STEM, 70% 通用, 每条跑五次取平均. TurboS 平均输出 1207.8 token, DeepSeek-R1 是 2283.5, Qwen3-235B-A22B 是 2979.2. 1207.8 / 2283.5 约 52.9%, 正文写 52.8%; 1207.8 / 2979.2 约 40.5%. 贡献列表里的 「about 50%」 是前一个比值取整.

这组比较还有两点要记. 一是比的是输出 token 数, 正文把它等同于生成成本, 没有价格和时延数据. 二是评测集七成是通用题, 这个配比对默认给短回答的模型有利. 报告没有把 STEM 和通用两部分的长度分开报, 所以看不出 TurboS 在难题上到底省了多少.

## 10. Deliberation Learning 和通用奖励系统

Deliberation Learning 是一个数据飞轮. 评审阶段, TurboS 的 SFT 模型和 Hunyuan Large, Hunyuan Turbo, Hunyuan T1 对同一批 prompt 作答, 多个评审模型做成对比较. 评审模型基于 TurboS 训练, 按六个维度打分: 准确性, 有用性, 无害性, 连贯性, 简洁性, 指令遵循, 常附文字理由, 再用多数投票或加权汇总, 并定期对照人类专家校准. 弱点审议阶段, 领域专家复查细微失败, 写出 「弱点画像」. 迭代 SFT 阶段按画像定制批次, 加入比输的样本, 由专家标注, 按课程学习逐步提高难度. 报告没说飞轮转了几轮, 也没给每轮的提升.

通用奖励系统有四个部件. 生成式奖励模型 (GRM) 带参考答案: 封闭题的参考是标准答案, 开放题的参考只当语义锚点. GRM 用成对偏好训练, 约 20 万条标注, 标注员一致率超过 93%, 左右对调做增广. 它可以读 CoT 变成 GRM-CoT, 另有一个能调外部工具的 critic. 答案一致性模型是轻量二分类, 输出 0 或 1, 会规范化空白, 单位和同义词. 代码沙箱支持 36 种语言, 部署在分布式 CPU 集群上, 能跑 1000 多个并发执行. 奖励聚合按领域规则融合多个服务的分数, 再做组内归一化. 整套系统覆盖 16 个子主题, 30 多个打分服务.

代码数据的规模可以算一下. 合成的可执行带单测样本超过 80 万条, 6 种主流语言各 10 万, 长尾语言各 1 万. 6 × 10 万 = 60 万, 剩下 20 万对应 20 种长尾语言, 合计 26 种, 比沙箱支持的 36 种少 10 种. 报告没列长尾语言名单. 另有一个多级知识分类框架, 400 多个类别, 1.3 万个标签, 用来平衡 prompt 分布和划分难度.

## 11. 两阶段 GRPO

第一阶段是推理 GRPO. 30 万条数据按代码 : 数学 : 逻辑与科学 = 2 : 2 : 1 混合, 折算下来代码 12 万, 数学 12 万, 逻辑与科学 6 万. SFT 模型在这些任务上已经强, 输出熵低, 所以 KL 约束取小, 鼓励探索. 每个领域有自己的数据处理: 逻辑挑多次采样准确率方差大的题; 代码用拒绝采样和难度过滤; 数学去掉证明题, 选择题和判断题; 科学用生成式验证器给奖励.

第二阶段是通用 GRPO. 16 万条通用 RL 指令, 继续混入 10% 第一阶段的推理数据, 超参数大体沿用, KL 惩罚系数调大, 防止灾难性遗忘和性能崩溃. 赛道一共 12 条: 文本理解, 翻译, 长上下文, 创意写作, Agents, 多轮对话, 复杂指令, 角色扮演, 安全, 知识问答, 多语言, 金融法律医疗. 每条赛道配自己的奖励服务和偏好数据.

实现细节有四条. 损失在 token 级重写, 近似 K3 KL 项裁剪到 [0, 10], Best-of-N 损失只用在正优势样本上. prompt 过滤去掉总对和总错的题, 留下采样分歧大的题. 采样温度固定 1.0, 更低的温度会让熵塌得太快; 组 batch 时丢掉优势为零的样本, 这是动态采样, 借鉴的 Yu et al. 就是参考文献里的 DAPO. 组奖励调整保证差回答拿负优势, 好回答拿正优势.

名字有一处不一致. 3.5 节把 GRPO 展开成 Generative Reward Preference Optimization, 引用的是 Shao et al., 2024, 即 DeepSeekMath. DeepSeekMath 里的 GRPO 是 Group Relative Policy Optimization. 报告描述的做法正是组内相对归一化, 所以这里更像是展开写错了, 方法本身没有变.

## 13. 基础设施

训练侧是 Angel-RL, 建在 AngelPTM (训练) 和 AngelHCF (推理) 之上, 并行方式有 TP, PP, EP, CP 和序列拼接. 对 Mamba 来说, 上下文并行的难点在状态传递: 后一段的初始状态依赖前一段的最终状态. 图 4 画了两种做法. 顺序式: cp0 从零状态开始, 乘 decay chunk, 加本段 states, 得到 out_states, 经 p2p 发给 cp1 当初始状态, cp1 再算自己那一段. 并行式: 先在 CP 组内 all-gather decay_chunk, 所有 rank 同时算, 跳过落在非本地 rank 上的 decay_chunk × states, 最后 reduce-scatter 合并. 图 4 被抽取成两张 PNG, 上半张没有图注.

其余训练侧优化有四项: 采样侧 INT8 量化; 借 Starlink Network 做通信计算重叠; 多模型 RL 工作流混用共享和专用资源; ZeroCache 把去重后的模型状态卸载到 CPU 内存. 报告说这些让 5000 亿参数以上的模型能在 Angel-RL 里高效训练, 没给吞吐和显存数字.

推理侧三项优化合起来, 比纯 Transformer MoE 的 Hunyuan-Turbo 快 1.8 倍. Mamba kernel 方面, prefill 拆成可并行的 GEMM, 用 chunkscan 分块并行; decode 写了 SelectivescanUpdate kernel, 在指定位置精确读写状态向量. MoE 方面, 优先专家并行, 用冗余专家平衡负载, 优化 dispatch 和 combine 的通信. 精度方面, Mamba 状态改 fp32, 解决重复生成, 数学和竞赛编程的 token 消耗降 35% 到 45%. 1.8 倍是在什么上下文长度, 什么 batch 下测的, 报告没写.

## 14. 报告里的其他混元模型

Hunyuan-Large 在报告里出现四次. 它是预训练数据的比较基线, TurboS 从数量, 质量, 多样性三个维度改进数据. 分词器和它相同, 词表 128K. MoE 策略和它相近, 都是共享专家加专项专家. 长上下文课程 4K → 32K → 256K 也照搬了它. 参考文献里 Hunyuan-Large 的标题写的是 52B 激活参数, TurboS 的激活参数 56B 和它接近, 主干却从纯 Transformer 换成了以 Mamba2 为主的混排.

Hunyuan-Turbo 出现两处. 一处是推理速度的基线, TurboS 比它快 1.8 倍, 报告说明它是纯 Transformer 的 MoE 模型. 另一处是 Deliberation Learning 的对手之一. 附录 Arena 表里的 Hunyuan-Turbo-0110 得 1293 分. Hunyuan-T1 也出现两处: 在自适应 CoT 的 SFT 数据构造里, 它负责续写短 CoT 模型的错误回答; 在 Deliberation Learning 里它是对手. 报告没给 T1 的参数量和结构. 教师模型的起点叫 Hunyuan-Base, 报告没说它和 TurboS 的预训练基座是不是同一个模型.

从这些引用能看出, TurboS 的后训练很依赖家族里的其他模型: T1 提供长推理, Large, Turbo, T1 当比较对象, 评审模型又基于 TurboS 自己训练. 评审模型出自被评的同一个模型, 可能偏向自己的回答风格, 报告对此只有 「定期对照人类专家校准」 一句.

Arena 表还给了同一型号前后两个版本的对比. Hunyuan-TurboS-20250226 得 1299 分, 0416 版本得 1356 分, 相差 57 分. 报告没有逐项列出两个版本之间改了什么, 只能从时间上推测, 后训练里的自适应 CoT, 两阶段 GRPO 和新的奖励系统是在这段时间里加进来的. 这 57 分算不到哪一项头上, 报告也没有做消融.

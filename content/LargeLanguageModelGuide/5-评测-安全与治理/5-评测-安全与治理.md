# 评测,安全与治理

「跑过 benchmark」「做过红队」「写过合规清单」, 这三件事单独拿出来, 都不能证明一个大模型系统可以安全上线. 模型进入真实系统后, 风险由模型, 数据, 提示, 检索, 工具, 权限, 用户和运行环境共同产生. 本章的评测与治理覆盖这个完整系统, 并且对每一份证据都说明它能支持什么结论, 不能支持什么结论.

本章由四篇组成: 评测科学, 安全与对抗, 隐私与数据, 部署治理. 读完之后, 读者应当能交付四类可审查的结果: 一份把决策问题转成对象, 分布, 指标和不确定性的评测方案; 一份列出资产, 信任边界, 攻击路径和分层控制的威胁模型; 一份追踪训练, 检索, 日志, 反馈和派生数据的数据台账; 一份包含上线闸门, 变更复测, 监控, 事件响应和回滚的运行计划.

## 1. 风险由整个系统产生

### 1.1 模型, 系统与部署分层

| 层级 | 典型对象 | 能测到什么 | 不能自动外推什么 |
|---|---|---|---|
| 模型 | checkpoint, API snapshot | 固定设置下的能力, 行为与部分有害倾向 | 带工具产品的实际权限和影响 |
| 系统 | 模型加提示, RAG, 工具, 策略 | 端到端任务, 越权, 注入和恢复行为 | 所有地区, 用户和运行版本都相同 |
| 部署 | 系统加真实数据, 人员, SLO 和流程 | 真实暴露, 尾部损失, 人工接管与事件 | 未来变更后仍维持同一风险水平 |

三层的证据不能互相替代. 模型评测可以发现风险, 但风险的归属和控制通常落在系统层和部署层: 一个模型在问答基准上从不泄漏隐私, 接上能读邮箱的工具之后, 一次间接提示注入就可能把邮件内容发出去. 反过来, 系统层的 guardrail 拦住了某类输出, 也不能证明底层模型不具备相关能力或没有记住相关数据.

部署层是最容易被省略的一层. 它涉及真实用户的分布, 值班人员, SLO 和事件流程, 这些在实验室里都测不到. 一个系统在内部验收集上表现良好, 上线后遇到的语言, 领域和恶意输入比例可能完全不同, 所以部署层的证据只能通过试点, 灰度和持续监控获得.

### 1.2 一条完整的证据链

每项结论都要能沿一条链追溯: 决策问题, 明确的声明, 目标对象与版本, 目标分布, 数据与采样, 执行环境, 评分与人工裁决, 统计与失败分析, 阈值与责任人, 最终是上线, 限制或停止的决定. 缺少中间任何一环, 结果都可能只是一个不可复现的数字.

这条链上有三个常见的断点. 一是看到结果之后再调整阈值, 让本来不通过的系统通过; 二是只保存聚合分数, 不保存样本和轨迹, 出了问题无法回查; 三是把「未发现事故」写成「已证明安全」. 可以写的声明是「在这些版本, 这些样本和这个攻击预算的范围内, 未发现某类问题」, 它承认覆盖范围有限, 也给出了重新验证的条件.

## 2. 四篇文章的分工

### 2.1 评测科学与证据

[5.1 评测科学与证据](./5.1-评测科学与证据/5.1-评测科学与证据.md) 从声明开始, 不从 benchmark 开始. 一个可检验的声明包含对象 (精确的 checkpoint 或 API snapshot), 任务, 目标分布, 设置 (prompt, 工具, 推理预算, 采样), 指标, 时间和预先确定的阈值. 「模型 A 更好」不可检验; 「在客服验收集 v4, 统一检索和中等推理预算下, snapshot X 的任务成功率不低于 92%」才接近可以审查的声明.

在统计方面, 5.1 要求报告不确定性: 两个系统在同一批题目上比较时用配对检验 (McNemar, 配对 bootstrap), 题目之间有相关性时 (同一文档派生的多道题) 用聚类 bootstrap. 它还讨论了 LLM-as-a-Judge 的位置偏差, 冗长偏好和自增强偏差, 测试集污染与饱和, 以及一张结果卡应包含的字段. 后面三篇里所有「测量」的部分, 都按 5.1 的方法执行.

### 2.2 安全与对抗评测

[5.2 安全与对抗评测](./5.2-安全与对抗评测/5.2-安全与对抗评测.md) 的评测对象不是一句模型回答, 而是一条攻击路径, 它可能跨越用户输入, 检索, 模型, 工具, 身份和外部系统. 文章先把可靠性, 安全性, 社会风险和内容政策四个维度分开, 它们会重叠, 但不能合成一个「安全分」. 拒绝危险请求属于行为控制, 工具能不能删除生产数据属于授权与系统安全, 两者的控制手段完全不同.

威胁模型部分列出资产, 信任边界和攻击者能力, 攻击分类参照 NIST AI 100-2e2025. 对 Agent 和工具, 文章区分三种「过度」: 功能过多, 权限过大, 自主性过强, 每一种都对应不同的收缩方法. 之后依次讨论提示注入与越狱, 数据与模型投毒, 供应链 (参照 NIST SP 800-218A), 以及红队测试的四个层级: 组件, 集成, 端到端和线上运行.

### 2.3 隐私, 数据与内容治理

[5.3 隐私, 数据与内容治理](./5.3-隐私数据与内容治理/5.3-隐私数据与内容治理.md) 的出发点是: 同一条数据可能进入预训练, 后训练, RAG, 提示, 缓存, 评测, 日志和反馈, 并派生出 token, embedding, 索引, 适配器或模型记忆. 「不保存原文」不等于没有数据风险, embedding, 缓存和日志同样可能保留敏感内容, 成为成员推断, 属性推断或跨租户泄漏的攻击面.

文章给出一张覆盖训练, 检索, 交互, 评测, 运行, 反馈六个数据面的地图, 以及一份最小台账字段. 隐私威胁部分讨论训练数据的记忆与抽取, 成员和属性推断. 删除和更正要传播到所有派生物, 只删原始记录而保留索引和缓存, 删除就没有完成. 内容来源, 真实性和知识产权也在这一篇里处理.

### 2.4 部署治理与持续保证

[5.4 部署治理与持续保证](./5.4-部署治理与持续保证/5.4-部署治理与持续保证.md) 关心的是组织能否持续回答几个问题: 系统用于什么, 影响谁, 谁能改变它, 证据支持哪些声明, 剩余风险由谁接受, 出了事故怎样停止和恢复. 它从一份用途声明开始, 用途改变会改变风险: 把一个低风险的摘要系统接入邮件发送或生产运维, 等于一次新的高影响部署, 需要重新建模和验收.

在此基础上, 5.4 讨论角色与分权, 风险登记, 保证案例 (用结构化论证把声明和证据连起来), 分阶段的上线闸门, 变更管理, 运行监控和事件响应. 受影响者不只是直接用户, 还包括被输出描述的人, 被排序筛选的人, 数据主体和标注审核人员, 只看用户满意度代表不了他们的损失.

## 3. 风险闭环与上线原则

### 3.1 四个环节

本章的组织方式和 [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework) 的 Govern, Map, Measure, Manage 四个功能相容. 治理环节确定用途, 禁用场景, 风险容忍度, 责任人, 独立复核和例外批准机制. 情境与威胁建模环节识别用户, 受影响群体, 资产, 数据, 工具, 依赖, 攻击者和真实的失败代价.

测量环节在代表集, 困难集, 风险集, 对抗集和真实试点中测量质量, 可靠性, 安全, 隐私, 性能与成本, 并报告覆盖范围和不确定性. 管理环节的优先顺序是先收缩用途或权限, 再增加工程控制, 监控, 人工确认和恢复路径; 风险无法降到可接受范围时, 不上线或缩小用途. AI RMF 是方法框架, 不是认证, 采用时要记录所用的版本.

### 3.2 最低上线原则

第一组原则关于声明和边界. 声明要限定范围, 写「在版本, 样本和攻击预算范围内未发现」, 不写「绝对安全」. 硬边界放在模型之外: 授权, 金额, 删除, 发布, 代码执行和网络访问由确定性系统控制, 不依赖模型拒绝. 模型只获得当前任务必需的能力, 上下文和数据保留时间.

第二组原则关于变化和追溯. 高影响动作要能预览, 确认, 撤销, 幂等或转人工. 模型, 提示, 索引, 工具, 权限, 数据或供应商任何一项变化后, 都按影响范围复测, 原有证据不自动延续. 每次评测保存精确的身份, 数据版本, 配置, 原始输出, 工具轨迹, 评分器和裁决记录, 使结论可以被第三方复核.

## 4. 读法与边界

### 4.1 按背景进入

做模型研发, 需要报告评测结果的读者, 从 5.1 开始, 重点是声明的写法, 配对检验和结果卡. 做安全或平台的读者, 先读 5.2 的威胁模型, 再读 5.4 的上线闸门. 负责数据合规的读者, 5.3 是主线, 它的数据地图可以直接用来盘点一个系统有哪些数据副本.

管理者或产品负责人, 读本页的 1.1, 3.2 和 5.4 的用途声明部分, 这三处决定一个系统能不能上线, 上线后谁负责. 四篇末尾都有提交前检查清单, 可以直接用作评审表.

### 4.2 与其他章节的分工

本章提供通用的风险方法和跨系统门禁, 具体系统的细节在各自章节. RAG 的语料权限, 引用, 拒答和检索安全在 [7.2 RAG](../7-LLM应用开发/7.2-RAG/7.2-RAG.md); Agent 应用开发的入门在 [7.3 Agent](../7-LLM应用开发/7.3-Agent/7.3-Agent.md), 系统工程, 训练和治理在 [第 13 章 Agent](../13-Agent/13-Agent.md), 其中 [13.5 应用与治理](../13-Agent/13.5-Agent应用与治理/13.5-Agent应用与治理.md) 处理工具权限, 自主级别和 Agent 基准.

对齐训练 (RLHF, 安全微调) 怎样改变模型行为, 在 [第 4 章 后训练](../4-后训练/4-后训练.md); 本章只把训练结果当作一项需要被测量的输入, 不把它当成安全边界. 某个具体模型的系统卡和安全评测披露, 在 [主流模型知识库](../../model-library/_garden.md) 对应版本的分析笔记里.

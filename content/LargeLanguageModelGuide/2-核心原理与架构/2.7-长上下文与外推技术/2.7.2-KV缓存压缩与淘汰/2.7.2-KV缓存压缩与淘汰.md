# 2.7.2 · KV缓存压缩与淘汰

解码每一步都要把全部历史 KV 从显存读一遍. 按 Llama-2-7B 的结构 (32 层, 隐藏维度 4096, FP16), 每个 token 的 KV 是 512 KiB, 4096 个 token 是 2 GiB; OPT-175B 在 batch 128, 序列 2048 时 KV 约 1152 GB, 是权重的三倍多. KV 一大, batch 开不上去, 每步读权重的开销分摊不下来, 吞吐就低.

这一小节的八篇讲同一类做法: 模型和注意力公式都不动, 推理时只决定哪些 KV 参与计算. 它们和 [2.4 稀疏注意力](../../2.4-稀疏注意力/2.4-稀疏注意力.md) 的区别在于不需要训练, 直接作用于现成模型; 和 [2.5 线性注意力与状态空间模型](../../2.5-线性注意力与状态空间模型/2.5-线性注意力与状态空间模型.md) 的区别在于缓存的仍是原始 KV, 只是条数变少或读得变少. 八篇按依据分成四组: 按位置 ([StreamingLLM](01-StreamingLLM与Attention-Sink/01-StreamingLLM与Attention-Sink.md)), 按生成期的注意力 ([H2O](02-H2O-Heavy-Hitter-Oracle/02-H2O-Heavy-Hitter-Oracle.md), [ScissorHands](06-ScissorHands-重要性持久/06-ScissorHands-重要性持久.md), [TOVA](07-TOVA-注意力省略/07-TOVA-注意力省略.md)), 按 prompt 末尾一次性挑选 ([SnapKV](03-SnapKV-生成前观测窗/03-SnapKV-生成前观测窗.md), [PyramidKV](04-PyramidKV-层间漏斗/04-PyramidKV-层间漏斗.md)), 以及按头选策略的 [FastGen](05-FastGen-按头自适应/05-FastGen-按头自适应.md) 和不删任何 KV 的 [Quest](./08-Quest-查询感知稀疏/08-Quest-查询感知稀疏.md).

## 1. 预算, 时机与依据

### 1.1 同一套记号

记第 $t$ 步的缓存集合为 $S_t$, 预算为 $B$, 即每层每头最多保留 $B$ 条 KV. 压缩策略是一个映射 $S_{t-1}\cup\{t\}\to S_t$, 满足 $|S_t|\le B$. H2O 把这一点写成两个约束: $|S_t|=B$, 以及每步最多换出一条. 只在 $S_t$ 上做注意力时, softmax 的分母也只对 $S_t$ 求和, 被删的位置既不贡献分子也不贡献分母.

这个定义里有三个自由度, 八篇各自在不同的地方做选择. 第一是打分依据: 固定位置, 历史累计的注意力, 当前一步的注意力, prompt 末尾一段 query 的注意力, 或者当前 query 与 key 的点积上界. 第二是预算怎么分: 所有层所有头相同, 按层递减, 按头各自不同. 第三是被选掉的 KV 怎么处理: 永久删除, 还是留在显存里只是这一步不读.

### 1.2 prefill 和 decode 两个阶段

压缩发生在哪个阶段, 决定了它能省什么. H2O, ScissorHands, TOVA 和 FastGen 在生成阶段逐步驱逐, prompt 的 KV 先全部写进去, 超出预算后才开始删. 它们的评测多是短 prompt, 长生成: H2O 的精度实验在 OPT 的 2K 窗口内, FastGen 的显存实验序列长 512. SnapKV 和 PyramidKV 反过来, 只在 prefill 结束时压一次 prompt 部分, 生成的 token 照常追加, 实验的生成长度在 512 以内.

所有方法都不加速 prefill 本身. prefill 仍是完整注意力, 首 token 延迟不变; SnapKV 和 PyramidKV 还要在 prefill 中额外算出观测窗对 prefix 的注意力权重才能投票. 打分依赖注意力权重的方法 (除 StreamingLLM 和 Quest 外的六种) 和不输出注意力矩阵的融合 kernel 都不直接兼容. Quest 论文在 100K 上评测 H2O 时, 只能让它在 prefill 阶段用 FlashAttention, 从解码阶段才开始累计分数. prefill 的加速见 [2.7.3 长上下文推理优化](../2.7.3-长上下文推理优化/2.7.3-长上下文推理优化.md).

## 2. 按什么打分

### 2.1 开头几个 token 不能丢

只保留最近 $W$ 条 KV 的窗口注意力, 在开头 token 被移出的那一刻就会崩溃. Llama-2-13B 在 PG19 上纯窗口 1024 的困惑度是 5158.07, 保留开头 4 个 token 再加 1020 的窗口是 5.40. 把这 4 个 token 换成换行符, 困惑度是 5.60, 说明起作用的是位置而不是内容. StreamingLLM 论文的解释是: softmax 要求每行注意力和为 1, 当前 token 不需要从上下文取信息时, 多余的注意力也要有地方放, 自回归模型的开头 token 对后面所有位置可见, 最容易被训练成这个去处. 论文称之为 attention sink.

StreamingLLM 因此永久保留开头 4 个 token, 再加一段滚动窗口, 位置按 token 在缓存内的下标重新编号, 不微调就能处理 400 万 token 的流式输入. 代价是窗口外的信息找不回来: 问答距离超过缓存大小, 准确率直接降为 0. 后面几种按分数打分的方法大多也会自动留住开头 token. H2O 的累计分数里开头 token 很高; TOVA 在 31 个 PG-19 样本上统计, 第一个 token 在所有缓存大小下都被保留到序列结束, 再显式加 4 个 sink 困惑度基本不变.

### 2.2 生成期的三种打分

H2O 观察到累计注意力分数呈幂律, 少数 token (heavy hitter) 累计很高. 它把预算一半给最近 token, 一半给累计分数最高的 token, 每步驱逐一个. 单独留最近窗口是必要的: 累计分数对早出现的 token 有利, 刚进来的 token 只加过一两次, 如果一起竞争, 会一进来就被删. 20% 预算下多数任务与完整缓存持平; T4 上 OPT-30B 的吞吐是 Accelerate 和 DeepSpeed 的约 31 倍, FlexGen 的约 2.2 倍, 主要因为省下的显存让 batch 从 FlexGen 的 80 开到 416.

ScissorHands 与 H2O 同期, 依据是重要性持久假设: 过去起过重要作用的 token, 以后也会起作用. 它只看最近 400 步, 统计每个 token 得分低于平均值 $1/t$ 的次数, 缓冲区满时一次丢掉计数最多的一半. 二值化之后, 一次极高的分数不会掩盖多次被忽略. TOVA 走得最远: 不累计历史, 不固定最近窗口, 每步丢掉当前 query 注意力最低的那一条, 分数在同一层各头间平均. LLaMA-2-7B 上缓存 512 时 PG-19 困惑度 7.41, 完整 4096 是 7.16, 直接截到 512 的序列是 8.92; 按头各自决定的 TOVA 在多数大小上反而比基线差.

### 2.3 生成之前一次选好

SnapKV 的观察是: prompt 最终一段 token 关注的位置, 和之后生成时关注的位置基本一致. 因果掩码下只有 prompt 末尾的 query 能看到整段 prompt, 和生成时的 query 看到的范围相同. 它用末尾的观测窗 (16 到 64 个 token) 对 prefix 投票, 一维池化后按头取 top-k, 再拼上观测窗本身, 生成阶段 prompt 部分固定不变. 池化让高分位置的邻居一起留下, 论文的例子是电话号码只留住国家代码, 其余靠模型编造.

一次选好的好处在长 prompt 上最明显. Mistral-7B-Instruct 的 LongBench 上, SnapKV 只留 1024 条, 在 16 个数据集中的 11 个上超过留 4096 条的 H2O; 差距集中在多文档问答, 2WikiMQA 上 H2O 4096 比完整缓存低 6.7 分, SnapKV 1024 只低 1.6 分. 要覆盖全文的摘要任务对容量最敏感, GovReport 从 32.85 降到 25.89. SnapKV 不处理之后生成的 KV, 长推理, 长写作的场景需要和生成期驱逐配合.

## 3. 预算分给谁

### 3.1 按层分: 两个相反的结论

PyramidKV 在多文档问答上画了 LLaMA 各层的平均注意力: 底层近似均匀, 中层在各文档内部集中, 高层集中到少数几个 token. 据此让底层多留, 高层少留, 各层预算按等差数列递减, 层内选择沿用 SnapKV. 优势集中在小预算: 每层平均 2048 时与 SnapKV 相差不到 0.2 分; 每层 64 时 LLaMA-3-8B 的 TREC 是 58.00, SnapKV 38.50. 等差分配下底层最多拿到平均值的 2 倍, 消融里几何递减, 指数递减和按注意力熵分配都不如等差.

ScissorHands 的层间分配方向相反, 给靠后的层更多预算. 它看的是重要 token 集合随时间的稳定性: 深层的持久率较低, 重要的是哪几个 token 更容易变. PyramidKV 看的是某一时刻注意力集中的程度. 一层的注意力可以既集中又不稳定, 两个结论并不矛盾, 但用的模型 (OPT 与 Llama-3) 和任务 (短文本与长上下文) 都不同, 目前没有在同一设置下的对比.

### 3.2 按头分: 先给每个头画像

FastGen 观察到同一层的头差别很大: 有的只看局部, 有的只看特殊 token 和标点, 有的看全部. 它在 prompt 编码时对每个头试一条从便宜到贵的策略链: 只留特殊 token, 加标点, 加累计分数高的 token, 加局部窗口, 最终是完整缓存; 第一个能恢复比例 $T$ 的注意力质量的就是这个头的策略. 局部和高频各保留 30%, 所以一个头一旦用上四种组合, 最多省约 40%, 更大的压缩只能来自只留特殊 token 和标点的头.

以 GPT-4 胜率 45% 为接近无损的线, 65B 可以减少约 40% 的 KV, 7B 只有约 20%; 同样的恢复率, 大模型压得更多. ScissorHands 在 OPT 上也观察到模型越大越耐压缩. FastGen 的代价在实现上: 每个头的缓存长度不同, 论文在 DeepSpeed 的 kernel 里加了稀疏操作才拿到加速; 它只在多头注意力上验证, 没有处理 GQA 下多个 query 头共享一个 KV 头的情况. 用户只能通过 $T$ 间接控制显存, 不能预先给出上限.

## 4. 删除与不删除

### 4.1 八种做法的对照

| 方法 | 打分依据 | 压缩时机 | 预算分配 | 被跳过的 KV |
|---|---|---|---|---|
| StreamingLLM | 位置: 开头 4 个 + 最近窗口 | 持续滑动 | 全部相同 | 删除 |
| H2O | 累计注意力 + 最近窗口 | 生成时每步 | 全部相同 | 删除 |
| ScissorHands | 最近 400 步内的低分次数 | 缓冲区满时 | 靠后的层更多 | 删除 |
| TOVA | 当前一步注意力, 层内平均 | 生成时每步 | 全部相同 | 删除 |
| SnapKV / PyramidKV | prompt 末尾观测窗投票 | prefill 结束时 | 相同 / 按层递减 | 删除 |
| FastGen | prompt 编码时的头画像 | 生成时 | 每头不同 | 删除 |
| Quest | 当前 query 与页内 key 的点积上界 | 生成时每步 | 固定 token 预算 | 本步不读 |

前六行的共同点在最终一列: 删除同时减少显存和读取量, 删掉的 KV 之后不能恢复. 它们都假设过去或 prompt 末尾显得重要的 token, 以后也重要. 这个假设在语言建模和摘要上大体成立: TOVA 用 1/8 的缓存就让困惑度与完整模型相差不到 0.4, SQuALITY 用 1/8 到 1/4 就相差 1 分以内. 它在检索上不成立, QASPER 需要一半缓存才接近完整模型.

Quest 是表里唯一不删的. 它把 KV 按页存 (页大小 16), 每页记录 key 各通道的最小值和最大值, 解码时用当前 query 与这两个向量算出页内点积的上界, 只读上界最高的若干页. 上界不会低估: 一页里只要有一个点积很高的 key, 这一页的分数就不低于它, 不会像块均值那样被其余 key 拉低. 读取比例是 $1/S+B/L$, 32K 上下文, 预算 2048 时为 1/8, 自注意力实测快 7.03 倍. 代价是显存一点不省: 32K 的 Llama-7B 仍需 16 GB 存 KV.

### 4.2 答案在前, 问题在后

驱逐类方法的弱点在 passkey 检索上最清楚. Quest 论文把含 passkey 的长文直接 prefill, 问题逐 token 喂入, 模拟答案在前, 问题在后的部署场景. 10K 长度上预算从 32 加到 512, H2O 的准确率是 0% 到 3%, TOVA 是 0% 到 8%, StreamingLLM 是 1% 到 5%, Quest 在预算 64 时已到 99%. passkey 在问题出现之前只是普通文本里的一个数字, 当前 query 给它的注意力很低, 驱逐类方法很早就把它删了, 加预算也救不回来.

这个结果把八种做法分成两类用途. 显存是瓶颈, 任务以摘要, 对话, 语言建模为主时, 驱逐类方法能让 batch 开大几倍; 任务要从长文中取回之前没被注意过的细节时, 要么保留全部 KV 只省带宽 (Quest), 要么像 SnapKV 那样在问题已经出现在 prompt 末尾之后再选. SnapKV 的稳健性实验也显示, 换一个问题, 重要的 prefix 位置就不同; 多轮对话里下一轮换了问题, 上一轮压掉的内容已经不在了.

## 5. 读的顺序

### 5.1 从 attention sink 开始

建议先读 [StreamingLLM](01-StreamingLLM与Attention-Sink/01-StreamingLLM与Attention-Sink.md), attention sink 是后面几篇都要用到的现象, 文中还有缓存内重新编号对 RoPE 的要求和 Llama-2-7B 的显存手算. 接着读 [H2O](02-H2O-Heavy-Hitter-Oracle/02-H2O-Heavy-Hitter-Oracle.md), 它的手算例子说明了为什么要单独留最近窗口, 吞吐一节解释了 batch 变大为什么吞吐变高.

然后按打分规则从复杂到简单读 [ScissorHands](06-ScissorHands-重要性持久/06-ScissorHands-重要性持久.md) 和 [TOVA](07-TOVA-注意力省略/07-TOVA-注意力省略.md), TOVA 把 Transformer 写成多状态 RNN, 和 2.5 节的固定状态模型可以对照着看.

### 5.2 长 prompt 与带宽

部署长 prompt 应用的读者, 读完 StreamingLLM 后直接读 [SnapKV](03-SnapKV-生成前观测窗/03-SnapKV-生成前观测窗.md) 和在它之上改层间预算的 [PyramidKV](04-PyramidKV-层间漏斗/04-PyramidKV-层间漏斗.md); PyramidKV 的附录还讨论了各层预算不同时在 vLLM 分页管理下产生的碎片.

[FastGen](05-FastGen-按头自适应/05-FastGen-按头自适应.md) 适合关心按头差异化的读者, 它的 Figure 3 显示首尾层需要完整缓存的头更多. 显存够, 带宽不够时读 [Quest](./08-Quest-查询感知稀疏/08-Quest-查询感知稀疏.md), 它和 [2.4](../../2.4-稀疏注意力/2.4-稀疏注意力.md) 里 MoBA, NSA 的按块打分最接近, 区别在于不训练, 用的是上界而不是块均值.

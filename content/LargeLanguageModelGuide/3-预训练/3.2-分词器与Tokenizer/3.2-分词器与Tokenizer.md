# 3.2 分词器与 Tokenizer

模型只接收整数 ID. tokenizer 负责把字符串切成片段, 每个片段映射到词表中的一个 ID, 并能从 ID 序列还原原文. 它在流水线上的位置很固定: 预训练语料 ([3.1](../3.1-预训练数据/3.1-预训练数据.md)) 确定之后, 取一个有代表性的子集训练 tokenizer; 训练好之后, 语料才有确定的 token 数, 模型配置 ([3.3](../3.3-模型配置与Scaling-Laws/3.3-模型配置与Scaling-Laws.md)) 里的嵌入矩阵才有确定的行数. 嵌入矩阵的第 $i$ 行对应词表的第 $i$ 个 token, 预训练开始后再换词表, 就要重新学习嵌入.

本节只有一篇子文章 [3.2.1 训练 Tokenizer](./3.2.1-训练Tokenizer/3.2.1-训练Tokenizer.md), 从 BPE 的手算例子讲到 HF tokenizers 和 sentencepiece 的训练代码. 下面先讲为什么切成子词, 再讲词表大小怎样影响参数, 序列长度和评估口径, 这几处要用到第 3 章其他篇的数字.

## 1. 为什么切成子词

### 1.1 按词切与按字符切各缺什么

按空格切成整词, 词表要覆盖所有见过的词形, 训练语料之外的词 (新词, 拼写错误, 罕见的屈折变化) 都成了未登录词, 只能映射到同一个 `[UNK]`. Sennrich 等人把 BPE 引入神经机器翻译, 动机就是这个问题: 词级模型的词表有上限, 罕见词和未见词翻译不出来, 而切成子词之后, 这些词可以由已有的子词单元拼出. 中文和日语没有空格, 按词切还要先依赖外部分词工具, SentencePiece 的设计出发点之一就是去掉这层依赖.

按字符切没有未登录词的问题, 但序列太长. 压缩率 $r$ 定义为字符数除以 token 数, 字符级切分的 $r=1$; Llama 3 的 tokenizer 在英语样本上 $r=3.94$, 同一段英语文本的 token 数只有字符级的约四分之一. 注意力的计算随序列长度增长, 固定长度的上下文窗口能装下的文本也随 $r$ 成比例变化. 子词处在两者之间: 常见词是一个 token, 罕见词拆成几个片段, 最坏情况退化到单字符或单字节.

### 1.2 四种做法的对照

子词切法要从语料里学出来. [3.2.1](./3.2.1-训练Tokenizer/3.2.1-训练Tokenizer.md) 第 1 到 3 节逐一推导了下面四种做法:

| | 学习方向 | 选择依据 | 初始单元 | 代表模型 |
|---|---|---|---|---|
| BPE | 自底向上合并 | 相邻对的出现频次 | 字符或 UTF-8 字节 | GPT-2, Llama 3 (tiktoken) |
| WordPiece | 自底向上合并 | 合并后似然的增量, 常用 $\mathrm{freq}(ab)/(\mathrm{freq}(a)\mathrm{freq}(b))$ 近似 | Unicode 字符 | BERT |
| Unigram | 自顶向下剪枝 | 删掉某个子词后边际似然的下降, 每轮保留前 $\eta\%$ | 大种子词表 | sentencepiece 的 `model_type=unigram` |
| SentencePiece | 工具, 底层选 BPE 或 Unigram | 同上 | 空格当普通符号, 记作 ▁ | LLaMA 第一代 |

表里最容易混的是最终一行. SentencePiece 不是第四种算法, 它解决的是另一个问题: 已有工具假设输入已按空格分好词, 而它把输入当作纯 Unicode 序列, 空格也参与切分, 解码时把 token 拼起来, 再把 ▁ 换回空格, 不需要语言相关的规则. 原文称之为无损切分, 但这只对规范化之后的文本成立, 默认的 NFKC 规范化会把全角字母数字变成半角, 训练器默认还会删多余空白; 代码这类需要逐字节还原的文本, 要把规范化设成 `identity`.

另一处分歧是原子单位. GPT-2 指出, 在 Unicode 码点上做 BPE, 初始词表要包含超过 13 万个符号, 远大于常用的 32,000 到 64,000 的 BPE 词表; 字节级 BPE 只需 256 个初始符号, 任何字符串都能写成 UTF-8 字节序列, 没有未登录词. SentencePiece 一侧的对应方案是 `byte_fallback`: 不在词表里的字符回退成字节 token, 不再输出 `<unk>`. LLaMA 第一代就是 SentencePiece BPE 加字节回退, Llama 3 换成了 tiktoken 的字节级 BPE.

## 2. 词表大小牵动的几个量

### 2.1 嵌入与输出头的参数

词表大小 $V$ 直接决定两块矩阵: 输入嵌入 $V\times d_{\mathrm{model}}$, 以及不共享权重时的输出头 $d_{\mathrm{model}}\times V$. Llama 3 三个尺寸都用 $V=128{,}000$, 宽度分别是 4096, 8192, 16,384, 单块矩阵依次是 $5.2\times10^8$, $1.05\times10^9$, $2.10\times10^9$ 个参数. [3.3.1](../3.3-模型配置与Scaling-Laws/3.3.1-确定模型结构与参数/3.3.1-确定模型结构与参数.md) 第 1.4 节逐项核算后, 嵌入加输出头在 8B 里占 13.1%, 70B 里占 3.0%, 405B 里只占 1.0%.

占比随规模下降, 原因是嵌入参数正比于 $Vd_{\mathrm{model}}$, 层内参数正比于 $n_{\mathrm{layer}}d_{\mathrm{model}}^2$. 词表固定时, 小模型被嵌入占去的比例最高. Qwen3 的 0.6B, 1.7B, 4B 共享输入输出嵌入, 8B 及以上不共享, 与这个趋势一致. 计算量上, 输入嵌入是查表, 几乎不花 FLOPs; 输出头每 token 前向要 $2d_{\mathrm{model}}V$, 以层内矩阵乘为分母, Llama 3 8B 是 7.5%, 70B 是 1.5%, 405B 是 0.5%. 这一项不计入 Kaplan 口径的 $N$, 所以小模型配大词表时, $6N$ 会低估真实计算量.

### 2.2 序列长度与训练 token 数

$V$ 越大, 压缩率越高, 同一段文本切出的 token 越少. Llama 3 的 tokenizer 用 tiktoken 的 10 万 token 加 2.8 万个非英语 token, 与 Llama 2 的 32K 词表相比, 英语样本上的压缩率从 3.17 提到 3.94 字符/token. 按这两个值, 8192 个 token 的窗口能装下的英语字符从约 25,969 增加到约 32,276, 多了约 24%; 反过来, 同样的英语文本 token 数少了 $1-3.17/3.94\approx19.5\%$.

这个变化会传到训练预算上. Scaling Laws 里的 $D$ 按 token 计, 换了 tokenizer 之后, 同样的 $D$ 对应的文本量就不同. 公开数据集的 token 数也各用各的 tokenizer: FineWeb 的 15T 按 GPT-2 计, DCLM-baseline 的 3.8T 按 GPT-NeoX 计, Dolma 的约 3T 按 Llama 计, 这些数字只能比量级. 长上下文训练 ([3.5.2](../3.5-继续预训练与长上下文训练/3.5.2-长上下文训练与数据/3.5.2-长上下文训练与数据.md)) 的窗口长度同样以 token 计, 128K token 能装多少字符, 也由压缩率决定.

### 2.3 最优词表随模型规模增长

$V$ 也不能无限大. 词表越大, 每个 token 在训练数据中出现得越少, 罕见 token 的嵌入训练不足; 输出层的类别数增加, token 级交叉熵也随之变高, 不同 $V$ 的模型不能直接比 loss. Tao 等人用 unigram 归一化的损失消掉这一项, 再把计算量写成 $C\approx6(N_{nv}+Vd)Hf(V)$, 其中 $H$ 是训练字符数, $f(V)$ 是每字符的平均 token 数: $V$ 小时增大 $V$ 让 $f(V)$ 明显下降, $V$ 很大时 $f(V)$ 下降变慢, 而增加的词表参数又训练不充分.

三种拟合方法给出一致的幂律: 最优词表参数 $N_v^{\mathrm{opt}}\propto N_{nv}^{\gamma}$, $\gamma\approx0.83$. $\gamma<1$ 意味着词表参数应比模型其他部分长得慢, 但仍要随模型变大. 按这个结论, Llama 2 70B 的最优词表至少是 216K, 约为实际 32K 的 7 倍; 作者在 3B 模型上用同样的 $2.3\times10^{21}$ FLOPs, 把词表从 32K 换成预测的 43K, ARC-Challenge 从 29.1 提到 32.0. 实验最大到 3B 参数, 500B 字符, 更大模型的最优 $V$ 是外推值. 公开的大模型词表多在 10 万到 15 万出头: DeepSeek LLM 102,400, Llama 3 128,000, Qwen3 151,669.

## 3. 多语言, 数字与评估口径

### 3.1 中文与多语言的压缩率

字节级 BPE 下, 常用汉字在 UTF-8 里占 3 个字节, 一个汉字如果没有被合并成单个 token, 就要占 3 个 token. 3.2.1 的实验在本地中文语料上训练 8000 词表的字节级 BPE, 句子「预训练数据要先去重再过滤.」共 13 个字符, 37 个字节, 编码成 8 个 token. 汉字能否合并成一个 token, 取决于训练 tokenizer 的语料里中文合并分到了多少名额.

所以 tokenizer 训练语料的配比, 直接决定了各语言的压缩率. 某种语言在 tokenizer 语料里占比低, 学到的合并就少, 同样内容要用更多 token, 训练和推理都更贵, 有限窗口里能装的内容也更少. Llama 3 补进 2.8 万个非英语 token, 报告称同时提高了压缩率和下游表现, 英语切分不受影响; 它只给了英语的压缩率, 其他语言没有给出具体数字. 字符级 BPE 一侧的问题是字符集: 汉字加生僻字和其他 CJK 字符有数万个, SentencePiece 用 `character_coverage` (3.2.1 的实验取 0.9995) 只为高频字符建原子, 其余交给字节回退.

### 3.2 数字与特殊 token

预分词规则决定数字怎么切. GPT-2 的正则用 `\p{N}+`, 整段数字由 BPE 自由合并; `cl100k_base` 改成 `\p{N}{1,3}`, 长数字从左到右每 3 位切一段, `12345` 切成 `123` 和 `45`; LLaMA 第一代用 SentencePiece 的 `split_digits`, 每位一个 token. 3 位一段时 token 数约为逐位切分的三分之一, 但同一个数位落在哪个片段, 取决于数字的总长度. 哪种切法对算术更有利, 要在固定其他条件的预训练实验里比较.

特殊 token 不参与合并, 由固定字符串直接映射到固定 ID. GPT-2 的 50,257 个 token 里最终一个是 `<|endoftext|>`, ID 为 50256; `cl100k_base` 的 `<|endoftext|>` 是 100257, 填空 (FIM) 用的三个标记是 100258 到 100260. 特殊 token 要在训练 tokenizer 时预留. Code Llama 在 Llama 2 上继续预训练时新增了 4 个 FIM 特殊 token ([3.5.1](../3.5-继续预训练与长上下文训练/3.5.1-继续预训练/3.5.1-继续预训练.md)), 新 token 的嵌入要在继续训练中从头学; 3.2.1 第 5.4 节把预训练后改词表归为继续预训练的范畴.

### 3.3 跨 tokenizer 比较: 换成每字节比特

token 级 loss 混合了模型能力和分词方式. 同一段文本, 词表小的切得碎, 每个位置好猜; 词表大的切得粗, 每个位置难猜. 跨 tokenizer 比较要把每 token 的 loss 换算到每字节: $\mathrm{BPB}=(L_T/L_B)\cdot\ell/\ln2$, 其中 $\ell$ 是每 token 的平均负对数似然 (nat), $L_T/L_B$ 是每字节的 token 数. The Pile 给出 GPT-2 tokenizer 在全语料上 $L_T/L_B=0.29335$; 中文常用汉字占 3 字节, 纯中文文本上每字符比特约为 BPB 的 3 倍, 两者不能混着比. 换算细节见 [3.6.1](../3.6-预训练评估/3.6.1-困惑度-PPL/3.6.1-困惑度-PPL.md) 第 2.1 节.

tokenizer 本身也是一次预压缩. Delétang 等人在 enwik8 上训练不同 tokenizer 的 Transformer, 在 enwik9 上测压缩率 (越低越好): 38M 参数的模型不分词 (ASCII) 最好, 6.4%, 换成 BPE 20K 升到 9.0%; 200K 参数的模型反过来, BPE 20K 最好, 19.3%. 论文的解释是更大的词表把序列缩短, 固定长度的上下文能装下更多信息, 这对容量小的模型更有用. 这组结果说明, tokenizer 的好坏不能只看压缩率, 还和模型规模, 上下文长度一起决定.

## 4. 读 3.2.1 的路径与边界

### 4.1 按目的读

第一次接触 tokenizer 的读者, 从 [3.2.1](./3.2.1-训练Tokenizer/3.2.1-训练Tokenizer.md) 第 1.3 节的 BPE 手算例子读起, 再看第 2 节字节级 BPE 和两版预分词正则, 这两节覆盖了 GPT 系列和 Llama 3 的做法. 要训练自己的 tokenizer, 直接到第 5 节: 5.2 节用 HF tokenizers 训练字节级 BPE, 5.3 节用 sentencepiece 训练 BPE 和 Unigram, 两段代码都在中文语料上跑过, 输出里能看到上面提到的 13 字符 8 token 的例子和 Unigram 采样出的三种切分.

关心词表大小的读者看第 4.1, 4.2 节, 再到 [3.3.1](../3.3-模型配置与Scaling-Laws/3.3.1-确定模型结构与参数/3.3.1-确定模型结构与参数.md) 第 3.1 节看词表怎样进入参数, FLOPs 和序列长度三处. 做多语言或中文模型的读者, 第 4.3 节和第 3.5 节 SentencePiece 的规范化与字符覆盖率是重点; 第 5.4 节列出了移植预分词正则时 tiktoken, HF tokenizers, Python `regex` 三种引擎行为不一致的问题.

### 4.2 与其他节的接口

tokenizer 的输入来自 3.1. 训练 tokenizer 用的子集要和预训练配比一致, 否则会出现在 tokenizer 语料里出现过, 却几乎不出现在预训练数据中的罕见 token, 它们的嵌入始终接近初始化状态. 所以抽样要在 3.1 的去重和配比做完之后进行, 让 tokenizer 语料与预训练数据的语言, 领域分布一致.

tokenizer 的输出牵动后面三节. [3.3](../3.3-模型配置与Scaling-Laws/3.3-模型配置与Scaling-Laws.md) 的参数与 FLOPs 计数要用到 $V$, 训练 token 数 $D$ 的含义随压缩率变化; [3.5](../3.5-继续预训练与长上下文训练/3.5-继续预训练与长上下文训练.md) 的继续预训练如果要扩词表, 新 token 的嵌入要随继续训练一起学; [3.6](../3.6-预训练评估/3.6-预训练评估.md) 的困惑度只有在同一个 tokenizer 下才能直接比, 跨模型时用 BPB 或每字符比特.

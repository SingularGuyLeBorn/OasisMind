# Agent 应用与治理:能力,评测与安全保证

Agent 从演示进入生产后, 核心问题从「能不能调用工具」转为: 系统在什么任务, 权限, 预算和失败条件下可靠, 出了事故能否阻断, 追溯和恢复. 产品名称和排行榜变化很快, 评测与治理的责任相对稳定. 本节讨论的就是这些责任: 怎样评审一个 Agent 应用, 怎样做可复现的评测, 怎样划定权限和处理攻击.

前几节分别处理了 Agent 的组件 (13.1), 决策架构 (13.2), 运行时工程 (13.3) 和训练 (13.4). 本节站在使用者和评审者的位置, 把这些内容收拢成上线前要回答的问题. 涉及具体产品的功能, 价格和模型时, 以同日的官方文档和团队自己的受控评测为准, 不把它们写成永久属性.

## 1. 从演示到生产

### 1.1 六个评审维度

评审一个 Agent 应用, 先把「全自动」「智能」之类的描述转换成六类可观察条件. 任务: 输入, 目标, 约束, 成功和失败怎样定义. 能力: 模型和 harness 能读什么, 做什么, 验证什么. 权限: 实际运行身份, 资源作用域, 副作用和审批. 可靠性: 错误, 超时, 重复, 取消和恢复怎样处理. 评测: 环境是否固定, 是否计入成本, 方差和安全. 治理: 谁负责上线, 变更, 监控, 事件和退役.

六个维度里, 权限和治理最容易在演示阶段被跳过. 演示通常用开发者自己的凭证, 在没有其他用户数据的环境里跑, 所以越权和数据泄漏根本不会出现. 到了生产环境, 同一个 Agent 用服务账号访问共享资源, 一次间接提示注入就可能读到别人的数据. 评审时要求每个维度都给出具体的工件 (契约, 权限矩阵, 回归集, 值班表), 而不是一段描述.

### 1.2 自主级别按风险配置

| 级别 | 行为 | 适合 |
|---|---|---|
| 建议 | 只生成建议或差异 | 高影响, 难验证的任务 |
| 受控执行 | 只读自动, 写操作逐次批准 | 开发, 研究, 办公 |
| 有限委派 | 在隔离环境和预算内完成任务 | 结果可验证的长任务 |
| 条件自治 | 低风险动作按政策自动, 高风险升级 | 稳定, 经过持续评测的流程 |

自主级别是针对动作配置的, 不是产品的单一标签. 同一个 Agent 读取公开网页时可以处于条件自治, 删除生产数据时必须回到受控执行甚至只给建议. 级别的划分依据两个量: 动作的影响有多大, 结果能不能被外部验证. 影响小且可验证的动作适合放开, 影响大或难验证的动作要收紧.

级别也会随证据变化. 一个流程在受控执行下积累了足够的评测和运行记录, 失败率和人工驳回率稳定在可接受范围内, 才有依据升到有限委派. 反过来, 模型, 工具或权限发生变更时, 原有证据可能失效, 级别要回退到重新评测通过为止.

## 2. 三篇文章的分工

### 2.1 Coding Agent 的执行外壳

[13.5.1 IDE 与 Coding Agent](./13.5.1-IDE与Coding-Agent/13.5.1-IDE与Coding-Agent.md) 以编程助手为例, 说明 Coding Agent 的差异不只在模型. 影响结果的是一整套执行外壳: 怎样找到相关代码, 能调用哪些工具, 怎样修改文件, 是否运行测试, 何时请求批准, 用户能否检查和回滚改动. 文章按可观察能力把它们分成补全, 对话, 编辑, 执行, 任务代理和委派代理几个层级, 每升一层, 风险从「局部正确但破坏全局约束」扩大到「环境漂移, 结果合并和责任边界不清」.

产品部分只记录官方文档可以核验的事实 (GitHub Copilot, Cursor, Claude Code, OpenAI Codex, Zed), 不做市场或速度排名, 因为那需要同一时间, 同一硬件, 同一模型, 同一任务和公开的测量方法. 对代码库上下文, 文章只评价结果 (找到的文件对不对), 不猜测各家未公开的索引实现. 执行外壳的权限设置决定了安全上限, 这一点和 13.5.3 相接.

### 2.2 基准与可复现评测

[13.5.2 Benchmark 与 Eval](./13.5.2-Benchmark与Eval/13.5.2-Benchmark与Eval.md) 先确定评估对象: 被评的是模型, 还是模型加 harness 加环境的联合系统. 然后介绍四类常用基准: SWE-bench 收集了 12 个 Python 仓库的 2,294 个真实 issue, 以测试是否通过判定修复; WebArena 在自托管网站上提供 812 个任务, 检查功能是否正确完成; OSWorld 在真实桌面应用里设 369 个任务, 配 134 个执行式 evaluator 函数; GAIA 是 466 道需要工具的问答, 其中 300 道答案保留用于排行榜.

这些数字之外, 文章要求把官方主指标和诊断指标分开报告, 并给出一份最小可复现实验记录: 模型快照, harness 版本, 环境版本, 预算, 尝试次数和 evaluator. LLM-as-Judge 只在没有确定性 evaluator 时使用, 要固定裁判快照和 rubric, 预先测它和人工标注的一致性, 对调候选顺序检查位置偏差. 常见失真包括只写模型名不写 harness, 只统计成功样本的成本, 把环境错误从分母里剔除, 以及把不同基准版本的分数拼在一张表里.

### 2.3 信任边界与权限

[13.5.3 Agent 安全与对齐](./13.5.3-Agent安全与对齐/13.5.3-Agent安全与对齐.md) 从画信任边界开始: 用户输入, 网页, 邮件, 仓库文档, 工具返回, 哪些是可信的指令, 哪些只是数据. 直接注入来自用户本人, 间接注入藏在 Agent 读取的外部内容里, 后者更难防, 因为攻击者不需要接触 Agent 的界面. 防御的基本结构是模型只提议, 宿主执行: 模型输出的工具调用要经过模式校验, 授权和策略门, 才会真正产生副作用.

权限部分有三条具体做法. 能力拆分, 把读取, 创建, 修改, 删除, 公开发布, 支付和权限管理拆成不同的工具和 scope, 不给「文件工具」一个能读写整台主机的接口; 短期身份, 凭证按任务, 按资源签发, 短时有效, 不放进模型上下文; 有意义的批准, 审批界面展示规范化后的真实对象, 差异, 收件人, 金额和不可逆影响, 不只问「是否允许工具 X」. 写操作要有幂等键, 防止超时重试造成第二次副作用. 文章末尾讨论了对齐训练的边界: 训练降低危险行为的概率, 但部署时的拒绝必须由执行端完成.

## 3. 上线证据

### 3.1 证据包的内容

上线前要交出一份证据包. 它的第一部分描述系统本身: 任务和非目标范围; 模型, 提示, 工具, 策略和环境的版本; 权限矩阵和高风险动作的审批规则; 数据来源, 保留, 删除和供应商边界. 第二部分是评测结果: 正常输入, 边界情况, 依赖故障和恶意输入下的表现, 以及成功率, 回归, 人工介入, 延迟, 费用和安全指标.

第三部分是运行时的保障: 回滚和停用的方法, 事件响应流程, 每个环节的负责人. 证据包不是一次性文件. 上线后任何模型, 工具, 权限, 提示或环境的变更都可能让其中的证据失效, 应当触发对应的回归评测, 结果更新到证据包里. 成本统计要包含失败, 重试和人工介入, 只算成功调用的成本会低估实际开销.

### 3.2 不能当作证据的材料

有几类材料经常出现在评审里, 但支撑不了上线决定. 没有任务和 harness 说明的单一排行榜分数; 没有实验方法的「节省 90% 时间」或固定成本; 从厂商功能页推导出的市场排名; 从一次成功演示推导出的长期可靠性. 这些材料的问题相同: 缺少可复现的条件, 换一个任务或环境就可能不成立.

另外两类更隐蔽. 一是模型的自述, 它说「已完成」或「操作安全」, 但这只是生成的文本, 完成与否要由外部状态, 测试或人工量表确认. 二是把某个单项措施当作完整治理: 用了沙箱, 接了 MCP, 或者做过安全微调, 都只覆盖治理的一部分. 沙箱管执行隔离, 不管业务授权; 安全微调降低概率, 不提供保证.

## 4. 读法与边界

### 4.1 按背景进入

正在选型 Coding Agent 的团队, 从 13.5.1 的选型检查表开始, 再用 13.5.2 第 5 节的实验记录模板在自己的仓库上做受控对比, 不要依赖公开排行榜. 负责安全评审的读者, 13.5.3 是主线, 它的上线清单可以直接作为评审表使用, 威胁模型部分可以和 [第 5 章的安全与对抗评测](../../5-评测-安全与治理/5.2-安全与对抗评测/5.2-安全与对抗评测.md) 对照.

做 Agent 研究, 需要报告基准结果的读者, 读 13.5.2 全文, 重点是联合系统的定义和失真方式. 管理者或产品负责人, 读本页的 1.2 和 3.1 两部分即可, 自主级别和证据包是决定能否上线的两件事.

### 4.2 与相邻章节的分工

本节只讨论 Agent 特有的评测与治理. 一般的评测科学 (配对检验, 置信区间, 污染检测) 在 [5.1 评测科学](../../5-评测-安全与治理/5.1-评测科学与证据/5.1-评测科学与证据.md), 部署治理的流程和门禁在 [5.4 部署治理](../../5-评测-安全与治理/5.4-部署治理与持续保证/5.4-部署治理与持续保证.md); 本节在它们的基础上补充工具, 权限和多步执行带来的新问题. 沙箱和运行时隔离的技术细节在 [13.3.4](../13.3-Agent系统工程/13.3.4-运行时环境与沙箱/13.3.4-运行时环境与沙箱.md), 本节只讨论它在治理中的位置.

本节引用的风险管理框架是 NIST [AI RMF](https://www.nist.gov/itl/ai-risk-management-framework), 它把治理分成 Govern, Map, Measure, Manage 四个功能, 第 5 章对它有完整的说明.

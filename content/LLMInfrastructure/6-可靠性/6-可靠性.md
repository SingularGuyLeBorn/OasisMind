# 可靠性：故障、恢复与结果正确性

当训练扩展到数百或数千张 GPU, 「运行期间会不会出故障」已经不是合适的问题。设备、网络、主机和进程在足够长的作业中总会出现异常, 系统真正要回答的是: 多快发现, 影响范围多大, 从哪个一致状态恢复, 恢复后的结果是否仍然可信。在线推理面对的是同一组问题, 只是时间尺度从小时压缩到秒甚至毫秒, 并增加了请求重放、流量切换和用户可见错误。

可靠性不能只由一个 availability 百分比概括。GPU 掉卡会直接中断 collective, 慢节点可能不报错却拖住整个同步 step, 网络丢包可能触发超时, 内存或存储的静默位翻转则可能让任务继续运行并产生错误结果。恢复机制同样带有成本: checkpoint 写入占用带宽与存储, 冗余副本占用算力, 健康探测和日志增加正常路径负担。**可靠性设计要同时约束故障检测时间、状态损失、恢复时间和结果正确性。**

### Fail-stop、慢节点与静默错误

Fail-stop 故障最容易识别: 进程退出、设备消失或连接断开都能产生明确事件。但分布式训练中的 collective 可能让其他 rank 一直等待, 因而还需要有界超时把局部退出传播为作业级失败。超时过短会把正常抖动误判为故障, 过长则扩大无效等待。合理阈值需要结合 step 时延分布、拓扑和作业规模, 而不是给所有通信统一一个常数。

Straggler 更难处理。某个 rank 仍然响应, 但 step 时延持续偏高, 同步训练会由最慢 rank 决定进度。观测必须拆出数据加载、host-to-device、计算和 collective 时间, 才能区分输入倾斜、GPU 降频、网络拥塞与软件停顿。静默错误则要求另一套信号: loss 突变、梯度范数异常、参数 checksum、ECC 计数或跨副本校验。只监控进程存活无法发现数值已经损坏。

### 故障域决定隔离边界

设备故障、单机故障、机架网络故障和存储服务故障具有不同相关性。若所有 checkpoint 副本位于同一个存储故障域, 多写几份也不能抵御该存储域不可用。推理副本若共享同一电源、交换机或模型加载服务, 逻辑上的多副本也可能同时失效。因此部署需要明确 failure domain, 并让副本、数据和控制面跨越真正独立的边界。

隔离不仅是移除坏设备。训练中一个 rank 的异常可能已经污染梯度或 optimizer state, 此时只替换该 rank 会破坏全局状态一致性。推理中某个实例连续产生异常 logits, 健康检查若只测 HTTP 200 就无法隔离。**隔离边界必须覆盖可能共享错误状态的全部参与者**, 同时保留足够证据用于判断故障属于硬件、数据还是模型版本。

## 恢复从一致状态开始

### Checkpoint 保存的不只是参数

训练 checkpoint 至少要覆盖模型参数、optimizer state、学习率进度、随机数状态和数据读取位置。Pipeline Parallel、Tensor Parallel 与 sharded optimizer 会让这些状态分散在多个 rank; 若各 rank 独立写入而没有共同的 commit 标记, 一部分新分片和一部分旧分片可能组成无法恢复的 checkpoint。常见做法是先写临时对象, 完成所有分片与 manifest 后再原子发布可见版本。

Checkpoint 周期在正常路径成本和故障重算之间取值。写得太频繁会稳定占用网络与存储带宽, 写得太少则在故障后丢失更多 step。异步 checkpoint 可以缩短前台停顿, 但需要冻结或复制一致快照, 也要防止后台写入追不上训练速度。增量 checkpoint 减少数据量, 恢复时却依赖更长的版本链; 任一增量损坏都可能扩大不可恢复范围。

### 重试必须知道副作用是否发生

训练 step 若在参数更新前失败, 从上一个 checkpoint 重跑通常只是损失计算时间; 若部分 rank 已完成更新、部分未完成, 直接继续会产生状态分叉。恢复流程必须回到共同提交点, 不能根据某个进程仍然存活就推断 step 完整。数据管线也要恢复 sampler 与 shard 位置, 否则会重复或跳过训练样本, 改变实际 token 序列。

在线请求的重试边界更细。纯生成请求通常可以在另一副本重新执行, 但流式响应可能已经向客户端发送一部分 token; 带工具调用、计费或外部写入的请求还可能已经产生副作用。请求 ID、幂等键和阶段状态需要共同决定能否自动重放。盲目重试虽然提高表面成功率, 却可能造成重复调用与重复扣费。服务端必须区分「未开始」「计算中」「输出已提交」和「外部副作用已确认」。

## 训练与推理的恢复目标不同

### 弹性训练保住的是进度

训练系统的核心指标包括 mean time to detect、mean time to recover、checkpoint 开销和每次故障丢失的有效 step。弹性训练允许用较少设备继续运行或替换故障节点, 但并非所有并行策略都能无缝改变 world size。数据并行较容易重新分片, Tensor Parallel 和 Pipeline Parallel 的拓扑变化会涉及权重布局、通信组与 microbatch 调度。若恢复过程需要重新编译或重新加载 TB 级状态, 调度器的重新分配速度并不等于作业恢复速度。

恢复后还要验证数值状态。检查 loss、梯度范数、学习率、已消费 token 和参数 checksum, 可以发现 checkpoint 回退过多、数据位置错位或分片装载错误。对确定性要求较高的实验, 还需记录软件版本、kernel 与随机数配置。验收可以允许有界的并行非确定性，同时必须识别恢复造成的训练语义变化。

### 在线服务保住的是请求边界

推理服务更看重请求成功率、time to first token、inter-token latency 和尾延迟。实例失效后, 控制面要停止分配新请求, 数据面要决定已有请求是迁移、重算还是返回可诊断错误。KV cache 通常位于实例本地, 迁移它可能比重算 prefill 更慢; 长上下文请求则可能相反。恢复策略需要根据已完成 prefill 的成本、剩余生成长度和 cache 可传输性选择。

副本健康也不能只靠周期探针。真实请求的错误率、token 生成速度、显存错误和模型版本校验共同构成健康状态。流量切换应逐步观察新副本, 防止配置错误扩散到全部请求。降级可以降低 batch、限制最大上下文或切换较小模型, 但必须明确质量与容量变化, 不能把错误隐藏为正常响应。

## 用故障注入验证可靠性

### 故障注入覆盖完整状态转移

故障注入应落在训练和服务的不同阶段: collective 之前与期间、checkpoint 写入一半、manifest 发布前后、模型加载中、prefill 完成后和流式输出期间。每次实验不只检查系统是否重新运行, 还要检查旧资源是否释放、重复请求是否产生副作用、恢复点是否一致以及监控是否触发。只杀掉一个空闲进程得到的恢复成功率不能代表真实故障路径。

注入频率和范围要受控, 但测试需要重复执行以覆盖竞态。结果应记录检测时间、隔离时间、恢复时间、丢失工作量和错误输出数量。对静默错误, 还要注入数值异常或损坏对象, 检查 checksum 与模型级指标能否在错误影响用户之前报警。**系统重新提供服务不等于恢复正确**, 数据与输出验证是恢复流程的一部分。

### 故障路径与资源成本

训练系统、推理服务和调度器在正常路径上维护状态与资源流动。故障发生后，每个状态转换都要区分已提交状态、可丢弃中间状态与不可重放的副作用。健康检查与超时、checkpoint 一致性、弹性训练、副本切换、故障注入和静默错误都使用 failure domain、恢复点、RTO 与数据损失这组概念。

checkpoint 带宽、冗余容量、故障重算与值班响应都会进入总成本。一次「自动恢复成功」同时要满足状态一致、结果可信与副作用不重复；只要任一条不成立，系统即使重新运行也不算完成恢复。

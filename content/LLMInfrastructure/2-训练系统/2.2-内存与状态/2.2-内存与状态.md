# 内存与状态：训练为何能运行、保存并恢复

训练系统的状态不只有参数。梯度、优化器动量、activation、随机数、学习率调度、数据游标和通信缓冲共同决定一次 step 能否执行；checkpoint 又要把足以恢复语义的部分持久化。把这两件事分开看，很容易出现「稳态能跑，保存时 OOM」或「文件都在，恢复后数据重复」的问题。

状态生命周期决定对象是长期驻留、只在某个算子出现、能够重算，还是必须持久化。容量优化必须保留训练语义，可用手段包括分片、重算、迁移和重新生成。

## 先区分设备状态与可恢复状态

设备显存包含静态训练状态、activation、梯度与临时 workspace。混合精度 AdamW 常用 16 byte/参数估算低精度权重、梯度、FP32 主权重和两个动量，但具体实现可能没有主权重或使用低比特 optimizer。activation 由算子反向需要保存的张量决定，不能用一个常数适配所有模型。

可恢复状态包含参数和 optimizer，还包括 global step、scheduler、AMP scaler、随机数、数据混合与游标。Activation 和 kernel workspace 通常无需持久化，故障后可从 step 边界重算。分布式 checkpoint 的目标，是发布一个全体必要 shard 一致的版本，而不是让每个 rank 各自写出文件就算成功。

这两类状态在保存时相遇。若框架先把所有分片聚合为完整 state_dict，瞬时内存会超过训练峰值；若异步保存将状态复制到 CPU，主机内存与 PCIe 成为新瓶颈。《训练内存》与后续《检查点》因此放在同一路线里。

### 技术路线怎样衔接

[《训练内存》](2.2.1-训练内存.md)从 $M(t)$ 的时间函数出发，逐项计算参数、activation、通信 buffer、workspace 与 allocator。它解释 activation checkpoint 为什么用重算换容量、FSDP 峰值为何由 all-gather 窗口决定、offload 如何把压力搬到 PCIe/CPU/NVMe。

《检查点》将从单次保存扩展到一致性协议。内容包括分片 manifest、临时版本到原子发布、异步 snapshot、不同 world size 重分片、数据游标和真实恢复演练。两篇共享生命周期视角：内存页在设备 kernel 完成前不能复用，checkpoint shard 在 manifest 提交前不能被当成完整版本。

内存优化为 checkpoint 留出安全区，checkpoint 频率又影响长期有效吞吐。保存间隔越短，正常 I/O 越多，故障重算越少；间隔越长则相反。最佳点取决于保存耗时、恢复耗时和故障间隔，不由显存利用率单独决定。

### 生命周期比类别求和更准确

总峰值是 $\max_t\sum_{x\in\mathcal L(t)}M_x$。两个各 4 GiB 的 workspace 若从不同时存活，峰值只增加 4 GiB；一个 2 GiB 通信 bucket 若与前向末尾 activation 重叠，就可能越过设备容量。内存快照和时间线要对齐，记录分配者与末次消费者。

Activation checkpoint 释放内部张量，反向时重跑前向。它的收益取决于保存集合，代价取决于重算算子；FlashAttention 的反向本身也会重算局部概率，外层 checkpoint 与内部机制不能简单叠加。选择边界时同时量 peak memory、执行 FLOPs 与 step 时间。

FSDP/ZeRO 将静态状态按 rank 分片，但计算当前模块时取回完整参数。预取下一模块可隐藏通信，意味着当前与下一模块参数同时驻留；wrap 太大峰值高，太小 collective 延迟高。稳定容量与瞬时容量必须分开报。

## 状态流动与恢复边界

### 正确性的状态边界

重算含 dropout 时必须恢复 RNG 状态，否则 mask 改变；数据恢复若只保存 shard offset，world size 改变后可能重复/跳过样本；优化器若缺少 step 计数，bias correction 会不同。系统要列出训练语义依赖的状态，而不是根据文件大小决定是否保存。

异步 checkpoint 需要一致快照。参数继续更新时，后台不能读取一半旧值、一半新值。可以先复制到稳定 host buffer，或使用 copy-on-write/版本化存储；复制完成的事件是训练可覆盖原页的边界。持久层使用临时路径，所有 shard 校验后发布 manifest；恢复只接受已提交版本。

真实恢复测试至少加载一次并执行一个 step，核对 loss、step、scheduler 与数据位置。文件存在性和 checksum 只能证明字节完整，不能证明状态集合足够。长期任务还要演练节点数变化、某 shard 缺失和最新版本损坏时的回退。

### Offload 与存储层级

CPU offload 依赖 pinned memory 与 PCIe，NVMe offload 依赖深队列和预取。设每 step 搬运 $Q$ byte，有效带宽 $B$，不可隐藏下界为 $Q/B$。若消费者到达前完成，传输可以大部分隐藏；若预取窗口不足，GPU 会在关键路径等待。

Host/NVMe 容量也不是无限资源。多个 GPU 共享 PCIe root 与主机内存带宽；数据加载、checkpoint 与参数 offload 可能互相争用。把单功能微基准的带宽直接用于全系统，会高估并发时能力。时间线需标出 H2D、D2H、存储和网络流。

Offload 状态通常不是持久 checkpoint。主机崩溃或节点丢失后，本地 NVMe 内容可能不可用；真正恢复点仍需写入可靠介质并带版本。冷热分层要明确故障域。

## 验收与长期维护

先用固定 shape warmup 到稳定，记录 allocated、reserved 与 peak；按前向末尾、反向早期、optimizer 和保存窗口分段。然后启用 checkpoint、分片或 offload，一项一项比较容量和 step 时间。若只看最终 peak，无法知道节省来自何处、代价在哪。

接着运行足够多 step 覆盖不同长度、eval 与 checkpoint。稳定训练的内存应呈周期而非单调上涨；单调上涨通常说明保留计算图、日志 tensor、异步任务或引用泄漏。周期尖峰若超过安全区，则要调整保存和工作区，而不是只缩短普通 batch。

故障恢复测试在已提交 checkpoint 处终止作业，用相同和不同 world size 各恢复一次，验证数据进度与恢复后的首个 step。容量、性能和恢复全部通过，这套状态设计才具备长时间训练所需的边界。

这条路线最终建立一张状态地图：每个对象是什么、在哪里、何时产生和释放、能否重算、由谁持久化、失败后怎样恢复。训练内存与 checkpoint 由此成为同一个问题的两个时间尺度。

### 版本与格式演进

Checkpoint 是长期制品，代码却会持续改变。参数重命名、层数调整、optimizer 实现升级和 dtype 变化都需要显式迁移。Manifest 应记录模型结构版本、张量名/shape/dtype、分片规则、优化器与训练代码版本。加载器遇到不兼容版本应失败并说明缺口，不能悄悄忽略未知字段。

模型权重导出与训练恢复也不是同一种格式。推理制品可能合并 LoRA、转换量化布局、丢弃 optimizer 和数据状态；它适合部署，不一定能继续训练。训练 checkpoint 保留恢复所需状态，通常更大、与并行布局关系更强。流水线需要明确从哪种格式向哪种格式转换，并保留校验。

大规模转换不应在单 rank 聚合。可以按目标 shard 流式读取旧 shard，只保留当前目标范围，完成后写新 manifest。转换前后核对参数总元素数、名称集合和抽样 checksum，再用小输入比较模型输出。

### 容量安全区怎样确定

显存不能长期压到理论上限。动态序列、通信重试、编译新 shape 和保存 workspace 都会产生波动。安全区应来自历史峰值分布与最大合法输入，而不是固定百分比。若线上/训练调度允许长度突增，按 token budget 在入队前预测 activation/KV，并拒绝超过水位的批次。

主机内存与磁盘同样保留余量。异步 checkpoint 积压时，两个版本可能同时存在；上传完成前不能删除现存的可恢复版本。保留策略要求新版本完成提交并验证可加载后才能回收旧版本，避免清理任务与保存并发留下零个有效点。

最终验收记录稳态、边界 batch、保存、恢复与格式转换五个场景。只有所有场景的状态生命周期明确，容量优化才不会把风险推迟到数小时后才出现的路径。

# KV 缓存：容量、分页、复用与迁移

自回归生成每一步都需要历史 token 的 K/V。若每次重新计算全部前缀，生成第 $t$ 个 token 会重复做前 $t-1$ 个 token 的投影；KV cache 用显存保存这些结果，把重复计算换成读取。模型越长、并发越高、上下文越大，缓存越可能比权重更先占满设备。

KV cache 不只是一个大张量。在线请求不断加入、增长、结束和取消，物理空间很难保持连续；公共前缀需要共享；抢占可能换出；多机分离需要迁移。这里从单 token shape 推到分页分配、prefix cache、量化、offload 和故障边界。

## KV 为什么可以缓存

对第 $t$ 个 token，attention 使用当前 query $q_t$ 与所有 $k_{1:t}$ 计算分数，再对 $v_{1:t}$ 加权。历史 token 的 K/V 由其隐藏状态投影得到，在标准 causal Transformer 中不会因未来 token 改变，因此可在首次计算后保存。历史 Q 不会被未来步骤使用，无需缓存。

设层数 $L$、KV head 数 $A_{kv}$、每头维度 $D$、长度 $S$、元素宽度 $w$，单请求容量为

$$
M_{KV}=2LSA_{kv}Dw.
$$

系数 2 对应 K 与 V。MHA 有 $A_{kv}=A$；GQA 让多个 query head 共享 KV，$A_{kv}<A$；MQA 取 $A_{kv}=1$。减少 KV head 会线性降低缓存容量和读取量，但模型质量与 kernel 支持需要训练/评测确认。

### 容量算例

取 $L=32,A_{kv}=8,D=128,S=4096,w=2$，单请求为 512 MiB。100 个等长请求理论有效 KV 就约 50 GiB，尚未计分页碎片、页表、临时 attention 输出和权重。若长度翻倍，容量线性翻倍。

新 token 每层写入一组 K/V，写入量与 $2LA_{kv}Dw$ 成正比；decode attention 每轮读取历史 KV，读取量与 $S$ 成正比。容量和带宽是同一数据结构的两面。量化 KV 既提高并发，也可能降低 decode HBM 流量。


若为每请求按最大上下文预留连续区间，短请求浪费大量空间；按当前长度精确分配又要随生成扩容，连续区域后面通常已有其他请求。搬迁整段 KV 很昂贵，也会阻塞 decode。

PagedAttention 将 KV 切为固定 token 数的 block。逻辑 block 号通过 block table 映射到任意物理 block，请求增长时再领一块，结束后逐块归还。物理不连续不影响逻辑顺序，kernel 根据页表访问。

设 block 容量为 $P$ token，请求长度 $S_i$，分配 token 槽位为 $\lceil S_i/P\rceil P$。内部碎片为

$$
M_{frag}=2LA_{kv}Dw\sum_i\left(\left\lceil S_i/P\right\rceil P-S_i\right).
$$

每个请求的尾块平均可能浪费约半块；block 越小，碎片越少，页表和分配操作越多。kernel 也更频繁跨 block 边界。选择 $P$ 要结合长度分布、并发与内核测量。

### Block table 与地址计算

逻辑 token $t$ 所在逻辑块为 $b=\lfloor t/P\rfloor$，块内 offset 为 $o=t\bmod P$。查表得到物理块 id 后，再结合层、K/V、head、维度和布局计算地址。页表通常很小并缓存，但 ragged batch 的每请求表不同，访问和边界 mask 增加控制工作。

布局决定读取合并。可以把 token、head、维度按不同顺序排列；decode 常希望相邻线程读取连续的 head dimension 或连续 token 向量。向量化、对齐和量化 group 都影响布局。仅改变 shape 元数据而不重排物理数据，可能让 kernel 产生跨步访问。


请求状态至少包括 waiting、prefill、decode、finished/cancelled。Prefill 前调度器要预估所需块；chunked prefill 可逐块增长。Decode 每产生 token 申请新槽位，跨块边界时领新块。请求结束后，只有确认没有在途 kernel/传输引用，才能归还。

异步执行带来释放竞态。CPU 收到取消时，GPU 可能仍在读取这些 block；立即放回池会被下一请求覆盖。可用 stream event、epoch 或引用计数延迟回收。监控应区分逻辑已取消和物理已回收，否则显存短期「泄漏」可能只是安全延迟。

预留策略也影响 admission。只按当前 prompt 分配，未来 decode 可能无块而抢占；为最大输出预留又降低利用率。系统可按请求 max_tokens 保留逻辑配额，但物理按需分配，同时限制总承诺（overcommit）。当实际增长接近容量，提前停止接收或选择抢占对象。

### Copy-on-write 支持共享前缀
多个请求拥有相同前缀时，可共享只读 KV block。每块维护引用计数；只要后续 token 从块边界之后追加，无需复制。若需要修改共享的部分块，使用 copy-on-write 复制尾块，再继续写入。

Beam search 也会从相同历史分叉。各 beam 可共享过去 block，只为新 token 分配私有块。若每次分叉都复制完整 KV，容量随 beam 数爆炸。分页与引用计数让成本接近共同前缀一份加各分支增量。

引用计数错误会导致 use-after-free 或永不回收。取消、超时、beam 合并和迁移失败都要走同一所有权协议。缓存正确性测试需要构造这些交错，而不是只跑正常完成请求。

Prefix cache 将已完成或正在使用的前缀 KV 放入可查表缓存。新请求 token 前缀与某条记录一致时，跳过命中部分 prefill，从第一个未命中 token 继续。系统 prompt、固定模板和长文档问答可获得显著收益。

键不能只有原始文本。tokenizer 版本、chat template、特殊 token、模型权重、RoPE/位置参数、adapter 和可能影响 hidden state 的配置都要一致。最稳妥的键基于实际 token id 序列，加模型执行版本命名空间。文本相同但 tokenizer 不同，KV 不能复用。

位置也很重要。相对/旋转位置编码下，同一 token 序列放在不同绝对 offset，K 的位置变换可能不同；某些系统能对缓存做位置变换，必须按模型公式验证。简单实现只复用从位置 0 开始的相同前缀。

### 哈希树与 block 粒度命中
可为每个完整 block 计算链式 hash：当前块 hash 由父前缀 hash、token 与执行版本得到。查询沿 block 序列寻找最长命中。尾部不足一块的前缀是否缓存取决于实现；缓存完整块简化共享与 COW，却损失少量命中长度。

命中率分请求命中与 token 命中。很多请求只命中很短系统提示，请求命中率高但省下 token 少；应报告命中 token、避免的 prefill 时间和占用容量。缓存保留旧 KV 会与活跃请求争显存，淘汰策略可按节省成本、大小、最近使用和重算代价综合。

缓存填充也有并发。多个相同长前缀同时 miss，若各自计算，会浪费；single-flight 可让后来请求等待第一个填充，但等待可能违反 TTFT。可选择独立计算或 join，取决于预计剩余 prefill 与 deadline。

将 KV 从 BF16/FP16 压到 FP8、INT8 或更低位，可近似按位宽比例减少容量和读取。通常按 token/head/group 保存 scale，读取时反量化到计算精度。实际字节包括量化值、scale、zero-point 和对齐 padding。

若每组 $G$ 个元素共享一个 FP16 scale，INT8 的平均每元素存储约 $1+2/G$ byte；$G=64$ 时是 1.03125 byte，而不是正好 1。非对称量化还多 zero-point。较小 group 适应异常值更好，元数据和反量化操作更多。

K 与 V 的误差影响不同。K 进入 $qk^T$ 改变 softmax 分布，V 误差在线性加权后传播。逐 head、逐 token或按通道 scale 的效果随模型而异。评测不仅看 perplexity，还要覆盖长上下文检索、推理和生成稳定性。

## 性能未必按字节等比改善

量化减少 HBM 读取，但反量化需要指令和 register；若 kernel 先把整个块反量化写到临时 buffer，会丢掉 I/O 收益。理想实现将解码融合到 attention 消费路径。小上下文或计算受限时，反量化开销可能抵消节省；长上下文带宽受限时更有利。

量化还改变 block layout 与对齐。bit packing 若造成非合并访问，实际 transaction 不按有效字节下降。profile 同时查看 HBM bytes、kernel 时间、计算利用与额外 metadata load。

### Offload、换出与重算

显存满时，可以将被抢占请求 KV 换到 CPU/NVMe，恢复时换回；也可以丢弃 KV，重新 prefill。设 KV 大小为 $M$, 双向 PCIe 有效带宽 $B_p$，换出+换入纯传输约 $2M/B_p$；重算时间由 prompt FLOPs、当前 prefill 队列与设备效率决定。短前缀往往重算便宜，长前缀换出更合适。

换出需要主机 pinned buffer 才能高效异步 DMA，但 pinned memory 有系统上限。多 GPU 共享 PCIe root 时会争用。NVMe 容量大、延迟更高，适合长暂停而非毫秒级恢复。分层策略可将热请求留 HBM、温请求在主机、冷请求只保留 token 以备重算。

预取时机决定是否进入关键路径。调度器若预计若干轮后恢复某请求，可提前 H2D；预测错误会搬入未使用数据并挤出其他块。监控记录换出字节、恢复等待、重算 token 和因抢占造成的额外 TTFT/TPOT。


PD 分离、负载迁移或故障接管需要跨 GPU/节点发送 KV。数据可按层、block 或连续批量传输。按层流水允许目标在收到前若干层后准备执行，但 decode 一次前向最终需要所有层对应 KV；协议要追踪哪些 block 完整。

一次迁移不能只传裸张量，还需 token 范围、层/head、dtype/layout、位置、模型版本与校验。源和目标的 TP/PP 布局不同还要重分片。例如源 TP=4、目标 TP=8，KV head 分片映射变化，可能需要 all-to-all 或中转重排。

所有权切换必须原子。源在传输期间继续生成会产生增量 KV；可冻结请求、先传快照再追增量，或让源生成到某个 token 边界后交接。目标确认可执行前，源不能释放唯一副本；失败回滚后也不能两边同时继续并向客户端输出重复 token。

### 迁移值不值得

迁移收益来自目标更空闲或更适合 decode。若发送耗时加目标排队大于留在源端等待，就不应迁。路由器估算剩余输出长度、当前 KV 大小、链路带宽和两边队列；短剩余请求通常不值得搬。

Prefix-aware routing 是更轻的迁移替代：新请求直接去已有前缀的副本。但热门前缀会造成热点，需要在缓存命中与负载间权衡。可复制热门前缀到多个副本，复制成本由 KV 字节和预期复用次数决定。


KV 是从 token 与模型确定性派生的状态，理论上可重算，因此通常不做昂贵持久化。设备故障后，从客户端/服务端保留的 token 序列在新副本 prefill 即可恢复；采样 RNG、约束解码状态和工具调用状态则另行保存。若模型执行含非确定性，恢复后的后续 token 分布可能略有差异。

Silent corruption 更危险。Block table 指错、释放竞态或布局版本不匹配可能产生看似流畅却错误的输出。测试应比较 paged 与连续参考实现，对随机长度、共享、COW、取消、换出和迁移做逐 token logits 检查。debug 模式可为 block 加 generation id，发现陈旧引用。

安全性同样属于边界。KV 包含输入的模型表示，不能跨租户错误复用；释放后重新分配前若 kernel 会读取未覆盖区域，需确保 mask 正确或清理。日志不要记录可还原敏感输入的缓存内容。多租户 prefix cache 必须按授权域隔离。

### 容量规划与观测
可用 KV 容量是总 HBM 减权重、运行时、workspace 和安全区。将剩余字节除以每 token KV byte，得到理论 token 槽位；分页碎片、prefix 保留和在途传输会降低实际值。容量规划应使用线上长度分布模拟请求到达和完成，而非假设全部最大长度。

关键指标包括：总/空闲 block、活跃与缓存 block、内部碎片、每请求 token、prefix token hit、分配失败、抢占、换出/重算字节与时间、decode 每轮读取字节。只有显存利用率没有状态分解时，无法知道该扩容还是调淘汰。

压力测试逐步提高到达率，观察 TTFT、TPOT 与 block 水位。接近满载时系统应通过 admission control 稳定退化，而不是接受所有请求后发生 OOM。取消风暴、超长 prompt、热门前缀和迁移失败都应单独演练。

**KV cache 是在线推理的内存管理器，而不只是 attention 的缓存。** 公式给出每 token 成本，分页管理碎片，复用减少重复计算，换出与迁移处理容量和负载。任何优化都要同时通过数值正确性、生命周期安全与真实延迟验证。

每 token KV 字节为 $m_t=2LA_{kv}Dw$。取 $L=80,A_{kv}=8,D=128,w=2$，得 $m_t=327{,}680$ byte，约 320 KiB。若一张 80 GiB GPU 在权重、runtime 与 workspace 后剩 30 GiB 给 KV，理论槽位约 $30\times2^{30}/327680=98{,}304$ token。

这不等于能接 24 个 4096-token 请求，因为 24×4096 恰好 98,304，没有给 block 碎片、prefix cache 和在途请求余量。若 block=16 token，每个请求平均末块浪费约 7.5 token，24 个请求只多 180 token，碎片很小；但系统还应留例如 10% 安全区，稳态容量约 88K token，即 21 个左右 4096-token 请求。

若 KV 改为 INT8，假设每 64 元素一个 FP16 scale，K/V 都如此，平均每元素 $1+2/64=1.03125$ byte，$m_t$ 约从 320 KiB 降到 165 KiB。理论 token 槽位接近 190K，而非严格翻倍；页表和安全区仍在。更重要的是 kernel 需融合反量化，质量也要通过长上下文评测。

### Paged Attention 的读取模型
对请求 $i$，长度 $S_i$，本轮有效 KV 读取约 $m_tS_i$（若 $m_t$ 已含所有层则按模型整轮）。一个 batch 的总读取是 $m_t\sum_iS_i$，不是 $m_tB\max S_i$，前提是 kernel 不按最大长度 padding。Paged/ragged 实现的价值之一就是按真实长度读取。

实际 HBM transaction 大于有效字节。Block layout、量化 group、head 分片和地址离散会带来读放大。定义 $a=Q_{actual}/Q_{useful}$，decode 带宽下界为 $a m_t\sum_iS_i/B_{HBM}$. 用 profiler 的 DRAM bytes 反推 $a$；若有效流量不变而换 layout 后 $a$ 从 1.4 降到 1.1，才可解释时间改善。

页表读取量相对 KV 小，却在小 batch/短上下文时可能表现为延迟和依赖。将 block id 预取到 shared/register、批量连续块或为单块前缀提供快路径，可以减少。优化前先分长度桶测量，避免为短上下文的几微秒增加长上下文复杂度。

请求 prompt 长 $S$，命中前缀 $H$，未命中 $U=S-H$。省下的不是简单 $H/S$ 时间，因为 attention 和线性成本随位置不同。完整 prefill 时间记 $T(S)$，从已有 $H$ KV 继续处理 $U$ 的时间为 $T(U\mid H)$，净收益是

$$
G=T(S)-T(U\mid H)-T_{lookup}-T_{pin}.
$$

$T(U\mid H)$ 仍需让新 query attend 到 $H$ 个旧 KV，所以不会等于独立处理 $U$。当 $U$ 很小、$H$ 很大，线性投影大幅减少，但 attention 仍扫描长前缀。实测按 $(H,U)$ 二维分桶。

缓存条目占 $Hm_t$ byte。若一个 10K-token 前缀占约 3.05 GiB（以上述 80 层配置），保留它必须预计足够复用。假设一次命中省 100 ms，条目每分钟命中 20 次，就每分钟省 2 s GPU 时间；若只命中一次后闲置，它可能挤出多个活跃请求。淘汰优先级可近似用预期节省时间/占用 byte。

## 量化误差怎样进入 Attention

设量化后 $K'=K+E_K,V'=V+E_V$。Score 误差为 $QE_K^T/\sqrt D$，经过 softmax 后非线性影响权重；V 误差则被注意力权重线性组合。K 中与 query 对齐的异常误差可能改变 top attention 位置，因此 K/V 可使用不同位宽或 scale 方案。

按 token/head 分组能适应不同 token 幅值，按 channel 分组能处理持久异常通道。Scale 粒度越细，元数据越多，kernel 访问越复杂。评测覆盖困惑度、长上下文 needle/retrieval、代码/数学与多轮生成；短文本平均质量不够发现长序列累计误差。

量化写入发生在 prefill/decode 生成新 K/V 时。若先产 BF16 再启动独立量化 kernel并写 INT8，会多一次 BF16 写读；更好的路径在投影/rotary 后融合量化并直接写 cache。读取同样在 attention 内反量化。Profile 确认没有隐藏的完整 BF16 cache 副本。

### 迁移协议的分块与背压

一次 4 GiB KV 迁移在有效 25 GiB/s 链路上至少约 164 ms。若请求 TTFT/交接预算只有 50 ms，整量迁移不可能满足；需要更近目标、更高带宽、压缩，或根本不迁。公式在调度前就能排除错误决策。

分块迁移按 layer/block 生成 manifest，每块带请求 id、模型版本、逻辑 token 范围、layout 和 checksum。目标确认块落入正确物理页后更新接收位图。所有必需块齐全且增量 token 对齐，才切换 owner。重复块写入应幂等，断线可从缺失位图续传。

目标接收速度低于源发送时必须背压，不能无限占中转 buffer。限制每请求/全局在途 byte；Decode 池拥塞时，Prefill 池停止新的交接或路由到其他目标。监控区分网络传输、目标 HBM 写入和排队，避免把接收端没有 block 误判为链路慢。


两个请求 A/B 共享三个完整 prefix block，引用计数均为 2；它们各自还有一个部分尾块。A 追加 token 时只写自己的部分块，不影响共享块。若分叉发生在共享的第三块内部，A/B 不能直接修改它：复制第三块有效 token，两个分支各持有新块，旧共享块引用减少。

请求 A 取消时，遍历其 block table：共享块引用从 2 降 1，不进入 free list；私有块从 1 降 0，等待 GPU event 后回收。若先回收再等 event，上一轮 attention 可能读到分配给 C 的数据。Generation id 让 block table 的旧引用在 debug/test 中被发现。

Prefix cache 自身也持有引用。活跃请求结束并不代表共享块可回收；淘汰 cache entry 后才减缓存引用。容量面板分别显示 active ref 与 cache ref，否则看见「没有请求却 block 不释放」会误诊泄漏。

### 失效模式与回退顺序

分配失败时暂停 admission 并淘汰冷 prefix；空间仍然不足时，可抢占低优先级请求并比较 offload 与重算成本；资源耗尽后拒绝新请求。直接清空全部缓存会造成 prefill 洪峰，可能让过载更严重。每级动作都设置水位与速率限制。

量化 kernel 遇到不支持的 head dimension/layout，回退标准精度需要对应 BF16 KV；若 cache 里只有量化值，可用通用反量化路径，而不是假定原值仍在。回退会变慢，调度减少 batch或拒绝以守 SLO。

迁移失败保留源 owner，目标丢弃未提交块；若源也故障，从 token 序列重算。Prefix hash 冲突虽概率低，关键系统可在命中后验证 token/block 长度与二级摘要。模型滚动升级清晰隔离命名空间，旧版本退出后批量回收。

观测告警不要只看使用率。Block 分配失败、内部碎片、平均引用、冷 prefix byte、换出/重算率、迁移失败、量化 fallback 和实际 DRAM byte共同决定健康。容量高但全部是高复用活跃 KV 可能正常；容量中等却频繁抢占说明 admission/碎片已经有问题。


Tensor parallel 常按 KV head 切分。若 $A_{kv}=8,p_t=8$，每 rank 一个 KV head；若 $p_t>A_{kv}$，需要复制 KV head、切 head dimension 或使用不同并行方案，不能继续按 $1/p_t$ 估容量。GQA 模型在高 TP 下尤其容易遇到这一边界。

Pipeline parallel 按层切分，每 stage 只存所属层 KV，所以单卡容量约按 stage 层数下降；请求的逻辑 KV 却分散在所有 stage。迁移到另一 PP 副本需要各 stage 对应发送，任何 stage 缺块都无法继续。路由/清理使用统一 request id 协调多 stage 所有权。

Context parallel/sequence sharding 可能沿 token 切 KV。Decode 新 token 需要访问全部历史 shard，引入通信或分布式 attention。容量下降但每 token 网络增加；应将网络字节与本地 HBM byte一起加入 decode roofline。不能只因单卡 token 槽位增加就判断并发提升。

### 最终验收矩阵
功能覆盖 MHA/GQA/MQA、不同 head dimension、block 整除与尾块、prefix 共享/COW、beam 分叉、取消、offload、量化和迁移。每项与连续高精度实现比较 logits，长序列按多个位置抽查，回收后立即复用以暴露陈旧引用。

性能覆盖短/长 context、小/大 batch、均匀和偏斜长度。报告有效/实际 HBM byte、页表/cache 命中、block 碎片、kernel 时间、TPOT 与容量。量化同时给质量；prefix 同时给节省 prefill 和占用；迁移同时给传输与交接尾延迟。

稳定性用数小时压力和故障注入：取消风暴、缓存满、目标迁移失败、模型滚动升级、慢客户端与 GPU error。Block 水位应随请求完成回落，不变量持续成立，回退后结果正确。通过这些测试，KV 才能从「显存里的一块大数组」成为可信的在线状态系统。

容量模型、页表实现与监控应使用同一 token/block 口径；否则理论还有空间、分配器却报满时，很难判断是安全区、碎片、共享引用还是统计遗漏。

前面的容量式把一层中的 K 和 V 都压成了字节数，真正实现 kernel 时还要把它们还原成地址。以常见的逻辑布局 `[num_blocks, 2, block_size, num_kv_heads, head_dim]` 为例，`2` 区分 K/V。它便于解释，却未必是实际存储顺序。为了让一个 warp 的线程读取连续地址，K 可能把 `head_dim` 再切成向量宽度 $x$，形成 `[num_blocks, num_kv_heads, head_dim/x, block_size, x]`；V 又可能采用 `[num_blocks, num_kv_heads, head_dim, block_size]`。两者服务于不同的访存方向，不能仅凭逻辑 shape 推断内存连续性。

设物理块号为 $p$，块内 token 偏移为 $o$，KV 头号为 $h$，维度坐标为 $d$。忽略 batch 和对齐时，朴素 V 布局中的元素偏移可写为

$$
\operatorname{offset}_V(p,h,d,o)
=\bigl(((p\cdot H_{kv}+h)\cdot d_h+d)\cdot P+o\bigr).
$$

这条式子表明，固定 $(p,h,d)$ 后连续改变 $o$，读取的是连续 token；若线程组织希望连续读取 $d$，就需要转置布局或向量化打包。K 在点积阶段经常按维度向量加载，因此另一种布局可能更合适。所谓「PagedAttention kernel 支持分页」并不止是查一次 block table，还包括怎样把离散物理页映射成能够合并访问的线程工作集。

一次 decode 的地址链条可以按五步检查：调度器给请求选择 slot；slot 指向该请求的 block table；逻辑 token 号分解为逻辑块号与块内偏移；block table 给出物理块号；kernel 再按层、K/V、头和维度算出地址。这里任一层的版本不一致都会读到合法显存中的错误内容，因此未必触发越界。生产系统需要把 request generation、block generation 和模型执行版本放进可校验的元数据，而不能只依赖指针有效。

### 一个跨块读取的手算
取块长 $P=4$，某请求已有 10 个历史 token，逻辑块为 $b=0,1,2$。其 block table 为 `[7, 3, 11]`，说明前三段逻辑 token 分别存于物理块 7、3、11。逻辑 token 6 满足

$$
b=\lfloor 6/4\rfloor=1,\qquad o=6\bmod 4=2,
$$

所以应读取物理块 3 的第 2 个槽。token 9 对应物理块 11 的第 1 个槽。第三块只有 token 8、9 有效；槽 2、3 即使残留旧值，也必须被长度 mask 排除。清零空槽可以降低数据残留风险，却不能代替 mask，因为生成到第三块中途时有效长度仍会变化。

若 batch 中另一个请求的 block table 是 `[5, 3, 9]`，两者同时引用物理块 3 只有在该块承载相同 token、位置和执行版本时才合法。物理 id 相同本身不证明可共享。引用建立时验证前缀身份，执行时依赖已经建立的所有权关系；若每轮 kernel 再比较完整 token 序列，代价就抵消了缓存管理的意义。

小块降低尾块浪费，也增加 block table 项数。上下文长度 $S$ 的表项数为 $\lceil S/P\rceil$；从 $P=16$ 改到 $P=8$，长序列表约翻倍。页表本身的字节通常远小于 KV，可是查表、分支和不连续物理页会打断流水。大块则提高连续段长度，代价是短请求和大量分叉请求的内部碎片增大。

块大小还会与量化组和内核 tile 相互约束。假设量化组沿 token 轴覆盖 16 个 token，而块长只有 8，那么一个量化组跨两个物理块，scale 的所有权和加载路径会变复杂。若每块独立统计 scale，实际量化组就变成 8，元数据比例和误差特性一起改变。选择块长之前，需要列出 attention tile、量化组、DMA 粒度与 allocator 粒度，找出共同可接受的组合。

## 哈希前缀与 Radix Tree 的差别落在哪里

哈希式前缀缓存通常按完整 KV block 建立链式摘要。第 $j$ 个块的键可以写成

$$
H_j=\operatorname{Hash}(H_{j-1},\,T_j,\,C),
$$

其中 $T_j$ 是该块 token id，$C$ 包含模型、adapter、位置处理、KV dtype 等执行配置。父摘要进入下一个块的键，避免相同 token 块出现在不同前缀位置时被误认。查询按块推进，第一次 miss 后停止；因此能复用的长度通常向下取整到完整块边界。

Radix Tree 把公共 token 前缀显式表示为树上的公共路径，边可以保存一段 token，而不是每个 token 一个节点。请求 `[A,B,C,D]` 和 `[A,B,E]` 共享 `[A,B]` 的路径，分叉后各走一条边。树的长处出现在多轮对话、并行采样和 agent 树搜索：这些负载天然形成反复分叉、合并生命周期的前缀集合，最长前缀匹配和淘汰可以围绕树结构完成。

两种数据结构最终都必须把匹配结果交给物理块管理器。树节点没有凭空创造 KV；它仍持有若干块的引用，仍受块边界、引用计数和显存水位约束。哈希表也可以保存父链并得到最长块级前缀。工程选择取决于请求结构、并发更新、锁粒度和淘汰需求，不能仅凭「树能表示前缀」判定性能。

### 缓存键为何必须带执行语义

同一串 token 经 LoRA adapter A 与 B 计算后，隐藏状态和 K/V 不同；同一权重若 RoPE scaling 参数变化，位置变换也不同；量化校准或 KV layout 升级后，旧块甚至无法由新 kernel 解释。因此缓存命名空间至少包含模型权重标识、adapter 标识、tokenizer/chat-template 版本、位置编码配置、KV dtype/layout 版本和租户隔离域。

滚动发布时可先为新版本建立独立命名空间，让旧请求继续引用旧块。等旧执行副本和引用都归零，再回收旧缓存。若直接复用相同 hash 空间，token 摘要仍会命中，结果却来自另一套执行语义。版本隔离会暂时降低命中率并增加容量，这属于发布预算的一部分。

多模态请求还要处理图像、音频等输入的派生表示。只把文本 token 放进键里，会让相同文字配不同图像的请求错误复用。可将媒体内容摘要、预处理器版本和占位 token 展开方式纳入键；如果引擎不能稳定描述这套依赖，宁可禁用该路径的前缀复用。


普通 LRU 认为最近访问的条目更可能再次使用，但 KV 条目的大小和重算代价相差很大。一个 64-token 系统提示与一个 32K-token 文档前缀占用量相差 500 倍；长前缀命中一次节省更多 prefill，也可能长时间挤压活跃请求。可为候选条目估计

$$
U_i=\frac{\hat r_i\,\Delta T_i}{M_i},
$$

其中 $\hat r_i$ 是未来窗口内预计命中次数，$\Delta T_i$ 是每次命中的预计节省时间，$M_i$ 是占用字节。$U_i$ 只提供排序依据，线上仍需考虑租户配额、创建成本和即将到来的已知批任务。

淘汰动作也不能释放仍被活跃请求引用的块。缓存条目撤销的是 cache owner 的一份引用，块的总引用变为零后才进入延迟回收队列。若淘汰线程把「从索引移除」等同于「物理块可复用」，并发 decode 会读到被覆盖的数据。

### 调度器与 KV 管理器的接口

调度器依据一组可承诺资源决定能否接纳请求：当前空闲块、可淘汰缓存块、可抢占请求块、预留安全区以及下一轮可能释放的块。新请求带来 prompt token 和最大输出上限；系统据此判断立即接纳、排队、降级最大输出或拒绝。只按 prompt 长度接纳，会把输出增长风险推迟到 decode 中途。

可以把请求 $i$ 的当前占用写为 $c_i=\lceil S_i/P\rceil$ 块，下一轮是否需要新块由 $(S_i+1)\bmod P$ 决定。调度一轮 decode 前，先计算本轮跨块边界的请求数 $g$，保证至少有 $g$ 个可分配块。否则 kernel 执行完才发现无空间，系统已经生成了无法保存状态的新 token。

Chunked prefill 也需要配额。一个 100K-token prompt 若一次占满所有空闲块，会让正在 decode 的请求无法增长。把它切成若干 token chunk 后，每轮只承诺当前 chunk 的块，同时为活跃 decode 留出低水位。这样会延长单个长 prompt 的 TTFT，却能控制其他请求的 TPOT 抖动。调度策略应把这项延迟分配明确反映在优先级和 SLO 中。


假设请求已保存 $S$ 个 token，KV 大小为 $M(S)$。换出再恢复的时间下界约为

$$
T_{swap}=\frac{M(S)}{B_{D2H}}+\frac{M(S)}{B_{H2D}}+T_{queue},
$$

重算时间为 $T_{recompute}(S)$。若 CPU pinned memory 紧张、PCIe 与其他任务共享，$T_{queue}$ 可能大于纯传输。短上下文通常适合重算，长上下文更可能适合换出；prefix cache 若已保存相同前缀，重算成本又会下降。调度器要用近期测量更新两条路径，静态按 token 阈值切换容易在硬件或负载变化后失准。

抢占还影响公平性。总选择最长请求释放空间最多，却可能让长请求反复重算；总选择最新请求会伤害交互流量。可把已消耗服务时间、优先级、预计剩余输出、释放块数和恢复代价合成代价函数，并限制同一请求连续被抢占的次数。任何策略都要记录受影响请求的额外等待和重算量，单看吞吐会掩盖尾延迟。

### 一次容量演练
设 KV 池共有 6000 块，每块 16 token，安全区 300 块，prefix cache 占 1200 块，其中 700 块当前没有活跃引用。活跃请求占 4000 块，下一轮有 40 个请求跨块边界。立即可用块为 $6000-1200-4000=800$，扣除安全区后为 500，足够完成下一轮。

若新 prompt 需要 900 块，不能因为「淘汰 700 块后总数够」就直接整批接纳：接纳后只剩 300 块，刚好压到安全线，随后输出增长没有余量。把 prompt 分成每轮 200 块的 chunk，先淘汰部分冷缓存，并根据每轮完成请求回收量继续推进，能够避免一次占空。若业务要求该 prompt 独占低 TTFT，就应为它路由到单独池，而不是让共享池临时失去保护。

KV 故障常表现为 OOM、吞吐下降或回答偶发错误，三者需要不同的第一现场。OOM 先分解块：active、prefix、reserved、pending-free、swap-in-flight，它们之和应与已分配物理块一致。若总量对不上，检查重复记数和 allocator 泄漏；若 pending-free 持续增长，检查 GPU event 是否推进；若 prefix 比例异常，检查淘汰器及租户配额。

吞吐下降时，把 decode 每轮有效 KV 字节与 profiler 的实际 DRAM 字节对比。两者同时增长，多半是上下文或 batch 结构变化；有效字节稳定、实际字节增长，则检查 layout、对齐、量化 fallback 和 block 离散度。页表命中率低、TLB 类指标或地址计算指令增加，说明小块与随机映射可能成为开销。只有 kernel 时间而没有字节分解，很容易把调度问题误归因到 attention 算法。

偶发错误优先与连续 KV 参考实现逐 token 比 logits。将 batching、prefix、量化、offload、迁移逐项关闭，用最小组合复现。若错误跟随物理块复用，检查 generation id 与延迟回收；跟随共享前缀，检查 hash 命名空间和 COW；只在模型升级窗口出现，检查 layout/version 隔离；只在长上下文量化出现，检查 scale 粒度和累计误差。

最有价值的断言落在状态转换处：引用计数不得为负；free list 中块的引用必须为零且没有未完成 event；block table 的 generation 与物理块一致；请求有效 token 数不得超过已分配槽位；迁移完成前 owner 唯一；模型版本与 cache namespace 一致。调试版可以付出额外检查成本，发布版保留低成本计数和采样校验。

### 指标之间如何互相验证
假设监控显示 KV 使用率 90%，却还有大量请求被 admission 拒绝。先用 `allocated_blocks × block_size` 与活跃 token、缓存 token、尾块空槽核对。如果尾块空槽只占 2%，碎片不足以解释拒绝；再看安全区和每请求最大输出承诺。很可能物理块尚空闲，但逻辑配额已经被未来输出预留。

若 prefix token hit 达 70%，TTFT 却没有改善，需要拆成命中长度 $H$、未命中长度 $U$ 与排队时间。命中的可能都是短系统提示，或查找后仍因队列拥塞等待；也可能 attention 对旧 KV 的扫描占主要时间。用 $T(S)-T(U\mid H)$ 的实测值验证节省，不能把 token hit 直接当延迟降幅。

若 INT8 KV 容量接近翻倍，TPOT 只改善 10%，检查 decode 是否真的受 KV 带宽约束。短上下文可能被 launch、同步或其他层权重读取主导；反量化也可能增加计算。报告量化前后的有效字节、实际 HBM 字节、反量化指令和 occupancy，才能判断下一步是改 layout、融合 kernel，还是提高 batch。

KV cache 横跨模型数学、GPU 内存布局、调度与分布式所有权。公式确定理论容量，物理页决定空间能否被利用，kernel 决定每轮读取是否高效，调度器决定请求能否在增长中持续获得空间。四层使用相同的 token、block 和版本口径，容量估计与线上行为才能对得上。

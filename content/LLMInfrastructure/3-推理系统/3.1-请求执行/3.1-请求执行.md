# 请求执行：从排队、Prefill 到逐 token 生成

在线推理每轮面对一批不断变化的请求。新请求携带不同长度 prompt，老请求每轮增长一个 token，完成、取消和超时又会释放资源。调度器每几十毫秒甚至更短时间重组工作，在扩大 GPU batch 的同时限制长 prompt 对流式输出的阻塞。

本路线沿请求时间线组织三类文章：Prefill/Decode 解释两阶段的 shape 与硬件瓶颈；连续批处理讨论每轮如何选请求；PD 分离把两阶段放进不同资源池。三者共同回答「下一轮设备执行什么、谁先得到结果、状态放在哪里」。

## 请求时间线与指标

请求从到达到首 token 的 TTFT 包含网关/tokenize、排队、prefill、采样和发送。首 token 后，相邻 token 间隔 TPOT/ITL 由 decode 批次轮转、单轮设备时间和输出处理构成。端到端时延还乘上输出长度。吞吐可以是请求/s、输入 token/s 或输出 token/s，必须分别报告。

调度器改变的不只是设备利用率。等待凑批提高权重复用，却增加排队；长 prefill 形成较高计算效率，却可能让 decode ITL 突增；优先短请求改善平均值，却可能饿死长请求。评价至少按输入/输出长度和优先级分组给 p50/p95/p99。

### 技术路线怎样衔接

[《Prefill 与 Decode》](3.1.1-Prefill与Decode.md)从 $[B,T,H]$ 展开：prefill 的 $T$ 是 prompt token 数，decode 每请求 $T=1$。它推导投影 FLOPs、attention 二次项、权重与 KV 字节，并说明 chunked prefill 为何能在吞吐与 ITL 间调节。

《连续批处理》将以 iteration-level scheduling 为核心。静态批处理等待整批全部结束，短请求被最长输出拖住；连续 batching 每轮移除完成请求、加入新请求。文章会讨论 token budget、ragged batch、长度分桶、公平性、取消和 admission control。

《PD 分离》处理跨资源池执行。Prefill worker 生成 KV 后交给 Decode worker，两个池可以独立 batch 与扩容；代价是 KV 传输、跨池排队、版本一致性和失败接管。它不是默认更快，只有阶段干扰的收益大于迁移与调度成本才成立。

### 调度单位为何应该接近 token

请求数不能代表工作。一个 32 token prompt 与一个 32768 token prompt 都计作 1，却有完全不同 prefill；两个 decode 请求当前上下文不同，扫描 KV 的字节也不同。调度器至少用 prefill token、decode token、KV block 和预计时间建立预算。

Chunked prefill 把长 prompt 切块，让每轮先安排有截止时间的 decode，再用剩余预算处理 prefill。块大时 kernel 效率好、抢占粒度差；块小时调度灵活、launch 与页表成本高。预算模型应由实际 shape profile 校准，不能假设每 token 固定耗时。

## 调度、公平与扩展

### 公平性与过载

低负载时，任何合理策略都可能表现良好；高负载时到达率接近服务率，排队快速增长。系统需要 admission control：根据预计 KV、token budget 和 deadline 拒绝、延迟或降级新请求。接受所有请求直至 OOM，会让已接收请求也违反 SLO。

公平性可以通过 aging、租户配额、虚拟完成时间或分级队列实现。严格短作业优先降低平均 TTFT，却对长 prompt 不公平；严格 FIFO 会队头阻塞。策略要报告各长度/租户的 goodput，即在目标 TTFT/TPOT 内完成的请求，而不是只看聚合吞吐。

取消是正常流量。客户端断开后，请求应在安全 kernel 边界退出，未开始工作从队列移除，KV 在无在途引用后回收。取消传播慢时，设备会继续为无人接收的 token 计算，过载下形成正反馈。

### 多设备与多副本路由

单副本内部 TP/PP 降低每卡权重，却增加逐 token collective。副本之间复制权重、隔离故障，可由路由器分发请求。路由不能只看活跃请求数，还要看 KV 占用、长度、prefix cache、adapter 与预计完成时间。

把同前缀请求送到已有缓存副本可减少 prefill，但热门前缀会形成热点。收益等于避免的 prefill 时间，代价是额外排队。路由器应比较两者，并允许热门前缀复制到多个副本。

PD 分离进一步把阶段变成两类服务。容量规划分别用 input token/s 和 output token/s，不再用一个模糊的总 token/s。跨池队列也可能成为瓶颈；Prefill 完成但无 Decode 容量时，KV 占据源端或中转内存，必须限制在途交接数。

## 预测与验收

工作负载生成器应复现到达过程、输入输出长度相关性、优先级、取消和流式消费速度。固定并发测试与固定到达率测试回答不同问题：前者的客户端等完成再发请求，会在系统变慢时自动降低压力；后者更能暴露排队崩溃。

记录请求各阶段时间戳、每轮 batch 组成、有效/padding token、KV block、kernel 与通信。发现 TTFT 高时先分排队和 prefill；TPOT 抖动则对齐长 prefill、batch 变化、KV 长度和通信。单一端到端直方图无法定位。

路线的验收标准是：在明确负载与 SLO 下，系统能够解释每轮为何选择这些 token，过载时有界退化，取消与故障不泄漏状态。GPU 满载只是手段，按时完成更多有效请求才是目标。

### 从时间预测到调度决策

Token budget 比请求数好，但不同 token 的成本仍不相同。Prefill 块的投影与 attention 随块长和已有前缀变化，decode token 的 KV 扫描随上下文增长。调度器可用离线 profile 建立分桶表，以阶段、batch token、最大/总上下文和量化模式为特征预测一轮时间，再由在线观测校准。

预测器的主要职责是排除明显违反 deadline 的组合，对单轮毫秒数允许保留误差。若一批 decode 距截止时间只剩 12 ms，就不应塞入预计 20 ms 的 prefill 块。预测误差应纳入安全裕量，并监控系统性偏差；硬件降频或新 kernel 上线后需要重新校准。

调度器还要处理输出 backpressure。客户端消费慢、网络拥塞时，生成 token 堆在发送队列；继续无限生成会占 KV 和主机内存。可以限制每请求未发送 token，暂停其 decode 资格，并在恢复后重新加入。暂停不能等同结束，KV 生命周期仍需保留或选择换出。

### 请求执行的延伸问题

连续批处理文章会把 ready queue、running set、token budget 与页表分配写成一轮具体算法，并分析 FCFS、短作业优先与 aging。PD 分离文章会沿一次交接追踪 KV、版本、路由和失败回滚。二者都以前面定义的时间戳和指标口径为前提。

请求时间线可以区分 CPU 空档、KV 容量等待和设备 kernel 阻塞。CPU 空档不会因优化 attention 消失，长 kernel 也无法靠调整队列缩短；等待所属的资源层级决定修改位置。

### 最小可复现实验

准备短/长 prompt 与短/长输出四组请求，分别在低并发和接近容量的到达率下运行。固定模型与采样，记录每请求阶段时间、每轮 batch 和设备时间线。随后只改变一项调度参数，例如 prefill chunk 或 token budget，比较 TTFT、TPOT、goodput 与 GPU 有效 token。

如果吞吐上升而 p99 超标，说明更多工作被塞进批次但没有满足服务目标；如果 GPU 利用率下降却 goodput 上升，可能是更及时的短批减少了排队。验收以目标指标为准，而不是把硬件利用率当最终目的。

过载测试继续提高到达率，观察队列是否有界、拒绝是否按策略发生、已有请求是否仍能完成。系统在过载时保持可预测，比短时间吞下所有请求随后整体雪崩更重要。

实验还要覆盖请求取消、客户端慢消费与副本排空。三类事件都会改变 running set 和 KV 生命周期，却不应破坏已确认 token 的顺序。把这些边界放进固定回归 trace，路线首页描述的调度原则才真正落到可验证行为上。

# 性能模型：从单算子下界到多设备关键路径

大模型系统里最容易误导人的数字，往往也是最醒目的数字：峰值 FLOPs、显存容量、HBM 带宽、互联速率。它们描述设备上限，却没有说明一个具体 shape 搬了多少字节、产生多少并行工作、在哪个同步点等待。性能模型这条路线的任务，就是把规格表还原成一次执行可以复算的下界，再用 profile 解释下界与实测之间的差额。

工作量与资源模型统一 FLOPs、byte、容量和时间的口径；GPU 层次把这些工作映射到 register、shared memory、L2、HBM 与执行单元；通信拓扑再将单卡模型扩展到多个 rank、集合通信和关键路径。三者沿工作量、硬件执行和分布式依赖逐层连接。

## 先建立统一的数量坐标

系统性能分析先要回答三个不同的问题：完成了多少计算、数据跨层移动了多少，以及同一时刻必须容纳多少状态。把三者混成一个「规模」数字，后面的判断就会失去单位基础。

共同口径把每个结论追溯到 shape、字节、容量与计时边界；在这些输入明确后，下界才有可复算的含义。

### 工作量、流量和容量回答不同问题

FLOPs 是算术工作量，byte 是跨某一级接口移动的数据，容量是某一时刻同时存活的状态。矩阵乘 $Y=XW$ 的主工作为 $2mkn$ FLOP；若只计算 HBM 最少流量，可写 $w(mk+kn+mn)$ byte。两者相除得到相对于 HBM 的算术强度，但它不会告诉我们 register 或 shared-memory 流量。

容量不能把各张量大小直接相加。训练 activation、梯度 bucket 与 optimizer workspace 有生命周期；推理 KV 随请求增长并在结束后释放。峰值是时间线上 live set 的最大和。工作量与资源模型先明确统计层级和时刻，后面的 roofline 与显存判断才有共同分母。

### 下界不是延迟预测

给定 shape 可持续算力 $P$、访问模式对应带宽 $B$、工作量 $F$ 与流量 $Q$，最基本下界为 $\max(F/P,Q/B)$。当任务很短，还需考虑 launch；遇到同步归约、依赖链和低并行度，下界与实测差距更大。Roofline 的作用是排除不可能的优化收益，并指示优先查计算还是字节。

例如理论需要 10 ms 计算和 2 ms HBM，优化只减少一半 HBM 流量，理想总时间仍由 10 ms 计算限制；声称因此加速 2 倍显然不成立。反过来，FLOPs 只占 1 ms、字节需 12 ms，继续提高 Tensor Core 峰值也不会直接改变瓶颈。

## 从工作量走到 GPU

逻辑工作量进入 GPU 后，会被切成 block、warp、线程和具体指令。相同 FLOPs 因 shape、布局和资源分配不同，可能落在完全不同的执行路径上。

这一节连接软件张量与硬件层次，重点观察复用换来了什么，又占用了哪些 register、shared memory 和并行槽位。

### Shape 必须落到 tile、warp 和指令

同样的 FLOPs，大矩阵与细长矩阵兑现的算力不同。Kernel 把输出切成 tile，A/B 数据经 HBM、L2、shared memory 到 register，被多个算术操作复用。Tile 增大能提高复用，也增加 shared memory 和每线程 accumulator；超过资源台阶后，同驻 block/warp 减少，延迟更难遮蔽。

因此 $P$ 不能直接取规格峰值，而应来自相同 dtype、相近 shape 和布局的可持续结果。Decode 的小 $M$ GEMM、Prefill 的大矩阵、长序列归约需要不同 kernel。GPU 文章会把 occupancy、register、bank conflict 和实际指令放回这一资源交换，而不把任何一个 profiler 指标单独当结论。

### 数据移动不止 HBM

算子融合消除中间张量的 HBM 写回/读取，却延长临时值在 register 中的生命周期；在线 softmax 避免 $S\times S$ probability 落到 HBM，代价是分块归约与行状态；量化减少权重/KV byte，增加 scale 与反量化。每个优化都把成本从一层移动到另一层。

分层 roofline 分别使用 HBM、L2 或片上流量。Profile 若显示 HBM 已下降而时间没变，继续检查 register spill、shared-memory 冲突、并行度和 launch。工作量与资源模型给出「少搬了什么」，GPU 层次回答「为什么还没更快」。

## 从单卡走到设备组

多设备系统增加的不只是链路时间，还有算法轮次、同步依赖与共享路径。单卡下界仍然存在，但它只是分布式关键路径中的一个节点。

因此扩展分析必须同时描述 collective 的语义和物理拓扑。只有知道谁在何时等待谁，通信带宽才是一个可解释的数字。

### 通信是带依赖的张量移动

集合通信不能只用消息大小除链路带宽。简化模型包含启动延迟 $\alpha$、每 byte 时间 $\beta$、算法轮次与拓扑。Ring all-reduce 每 rank 算法流量约 $2(p-1)n/p$，Tree 有较少轮深但路径与带宽利用不同。小消息更多受启动项影响，大消息更多受持续带宽和争用影响。

逻辑 group 还要映射到物理拓扑。节点内 NVLink/NVSwitch、PCIe、NIC 与跨机交换网络带宽/延迟不同；高频逐层 TP collective 通常优先留在快域，大梯度 DP 通信可分 bucket 与反向重叠。具体布局仍由消息、计算窗口和容量共同决定。

### 关键路径决定通信是否可见

计算 80 ms、通信 50 ms，只有依赖允许且资源无争用时，区间才可能接近 80 ms；并发后双方争 HBM/SM，计算变 95 ms，也只隐藏 35 ms。时间线中的重叠色块不等于通信免费。梯度尾桶、流水慢 stage 和迟到 rank 都会形成裸露尾部。

通信文章从 all-reduce、all-gather、reduce-scatter、all-to-all 到 PP activation，分别计算字节与轮次，再用 enter/exit 时间区分网络慢和参与者晚到。单卡资源模型由此扩展成依赖图上的多资源模型。

## 三篇文章怎样配合使用

三篇详细文章对应三个观察尺度：[工作量与性能下界](1.1.1-工作量与性能下界/1.1.1-工作量与性能下界.md)量化 FLOP、字节和容量，[GPU 层次](1.1.2-GPU层次/1.1.2-GPU层次.md)解释设备执行，[通信拓扑](1.1.3-通信拓扑/1.1.3-通信拓扑.md)追踪设备间依赖。排障可以从任一层进入，结论都使用同一套数量坐标。

选择入口、证据链和停止细化的条件共同构成性能分析方法，避免把 profiler 截图或设备规格直接当作结论。

### 从问题选择入口

[《工作量与性能下界》](1.1.1-工作量与性能下界/1.1.1-工作量与性能下界.md)适合在还没有 profile 时建立数量级：模型一次 forward/step/token 做多少算术、搬多少数据、占多少状态，理想上限在哪里。它也给出单位、同步和 measurement boundary，防止 GB/GiB、Gb/s/GB/s 或异步计时混淆。

[《GPU 层次》](1.1.2-GPU层次/1.1.2-GPU层次.md)适合 kernel 已经成为关键路径时，解释 tile、occupancy、cache、归约与启动。它将矩阵乘、attention 和不规则访问落到硬件执行，并给出 profiler 的证据链。

[《通信拓扑》](1.1.3-通信拓扑/1.1.3-通信拓扑.md)适合多卡扩展不线性或尾延迟异常时。它连接并行策略与真实链路，分析算法字节、分层 collective、重叠和慢 rank。阅读顺序通常按三篇前后推进，排障时则从时间线暴露的层级直接进入对应文章。

### 从预测到实测校准

先固定 workload、shape、dtype、硬件和同步边界，用工作量模型预测 $F/P$、$Q/B$ 与容量。然后用设备时间线定位 kernel、空档和 collective，再用硬件计数器检查预测。实测高于下界的差额必须能归给并行度、缓存、同步、争用或运行时，而不是事后调整参数硬贴数据。

提出优化时先写它改变哪个量。例如 fusion 减少中间 HBM byte，TP 调整每卡 GEMM 与逐层通信，chunking 改变单轮 shape 和调度，checkpoint 改变 live set 与重算 FLOPs。上线后比较预测与实测；不一致就修正模型或找到遗漏路径。

原始计数、profile 与环境版本需要一同保存。设备、驱动、编译器和框架变化后，可替换可持续 $P/B$ 或 kernel 选择重新计算；旧结论是否仍成立，由更新后的模型参数和测量结果决定。

### 一个贯穿三篇的例子

假设某个 decode 迭代处理 32 个请求，模型权重与本轮 KV 共需从 HBM 读取 30 GB，目标 GPU 对该访问模式可持续 1.8 TB/s。工作量与资源模型先给出带宽下界约 $30/1800=16.7$ ms；主要矩阵按实际小 $M$ shape 测得计算下界 11 ms，因此先判断外存更紧。

GPU profile 若显示实际模型段 24 ms、DRAM 只有 1.3 TB/s，还不能直接说「带宽没跑满」。进一步检查发现 attention 页表访问使 transaction 放大，两个小归约 kernel 之间又有 2 ms launch/同步空档。优化布局将实际流量从 36 GB 降到 32 GB，并用 graph 消除 1.5 ms 空档，模型段降至约 19 ms，变化与模型预测方向一致。

扩到 8 路 TP 后，每卡权重减少，但每层新增两次 collective。单卡设备段降到 8 ms，collective 累计 5 ms、CPU 与采样 3 ms，总迭代约 16 ms；相比原单卡 19 ms 有收益，却远非八倍。通信拓扑文章进一步检查这些 collective 是否留在节点内、是否由小消息延迟主导。

这个例子展示三篇的边界：工作量与资源模型给数量级，GPU 层次解释单卡差额，通信拓扑解释扩展后的新关键路径。任何一篇单独使用都可能遗漏下一层成本。

### 模型什么时候应该停止细化

性能模型不需要模拟每条指令。若当前模型已经能区分两个候选、预测优化方向，并能给出会推翻结论的测量，继续增加参数未必有收益。两个方案预测只差 1%，而运行抖动 3%，应先改善实验或承认无法区分。

相反，若预测与实测差一倍，就不能用一个「效率系数」整体修正。先把时间线拆到算子、通信与空档，找到遗漏项；效率系数只有在同类 shape 和版本内稳定时才可复用。

最终输出应让别人替换模型维度、精度、设备和拓扑后重新算。清楚的假设、单位和省略项，比给出很多小数更重要；边界明确，模型才会随着知识库后续章节继续生长。

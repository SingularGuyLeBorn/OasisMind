# 算子融合

Eager 模式为每个算子独立调度 kernel，中间张量常写入 HBM，再被下一个 kernel 读回。融合把 producer 与 consumer 放进同一个执行程序，让中间值留在 register 或 shared memory，同时减少 CPU launch。收益来自减少字节和调度，限制来自语义依赖、布局、同步、寄存器与并行度。

## 编译路径

`torch.compile` 由 TorchDynamo 捕获 Python 执行，形成 FX graph；AOTAutograd 为训练拆出前向与反向图；Inductor 做 lowering、调度与代码生成，GPU 路径常生成 Triton 或调用外部库。Graph break 把程序切成多个编译区域，中间回到 Python/eager，跨区域融合机会随之消失。

捕获结果附带 dtype、device、shape、stride 与 Python 值的 guard。输入不满足 guard 时重新编译或回退。动态 shape 用符号维度复用更多输入，也会限制需要静态 tile 或内存大小的优化。实际系统常将序列长度或 batch 放入有限 bucket，在 padding 成本与编译变体数之间选择。

### 融合是否合法

逐元素链通常容易融合，因为每个输出元素只依赖对应输入。Reduction、scan 与排序需要线程间协作；随机数、原地写、alias、异常和数据相关控制流还会约束重排。编译器必须保持可观察语义，包括写入顺序、随机数消费和 autograd 保存值。

训练比推理多出 backward 与 saved tensor。前向融合若删除中间值，反向可以重算，也可以另存必要统计；两者分别增加计算或显存。推理没有参数梯度，融合区域通常更大，但动态 batch、KV 页表和采样控制流会形成新的边界。

### 布局与资源

相邻算子逻辑上可融合，布局未必匹配。Transpose/view 可能只改变 stride，也可能触发 materialize。Consumer 若要求连续内存，融合 kernel 要么按跨步地址读取，要么在片上重排。判断收益要比较省下的中间写读与新增的非合并访存。

融合延长临时值生命周期，register 增加会降低 occupancy，超过上限还会 spill 到 local memory。Reduction 需要 shared memory 和同步，过大的 fused kernel 也可能减少可同时驻留的 block。Kernel 数少只是表面指标，端到端时间与实际 HBM 字节才是依据。

### CUDA Graph 与算子融合

CUDA Graph 记录稳定的 launch 序列并重放，主要减少 CPU 提交开销；Inductor/Triton fusion 减少 kernel 与中间数据移动。两者可以叠加，也解决不同问题。CUDA Graph 要求地址、形状与执行结构满足捕获约束，动态区域可留在图外，稳定区域分段捕获。

Decode 每步矩阵较小、launch占比高，固定batch bucket容易从CUDA Graph受益；训练矩阵大，GPU计算占比高，Graph收益可能较小。训练仍可通过融合减少activation流量，推理则要同时分析TTFT、TPOT和捕获尺寸命中率。

## 调优与缓存

Triton kernel可对block size、num warps和stage数生成候选，Inductor autotune以真实shape测量。缓存键应包含图、shape/stride、dtype、设备架构、编译器与关键配置。换GPU或软件版本后复用不兼容结果，可能产生性能退化或错误。

编译60秒、每次省2毫秒，需要三万次调用才能抵消。服务启动、弹性扩容与短作业必须统计cache命中和摊销次数。常见shape可离线预热，长尾shape使用通用kernel或eager fallback。

### 数值与性能验收

融合会改变归约顺序、FMA使用、近似函数和低精度cast位置。验证覆盖普通随机值、极端值、非整除shape、非连续stride、空张量与训练梯度。误差标准按算子选择绝对/相对误差、余弦或任务指标，不能只跑一个输入。

性能先测kernel，再放回模型。记录编译时间、graph数量、graph break、recompile、kernel数、HBM字节、register、occupancy与端到端step/延迟。局部更快但前后新增layout conversion时，整体可能变慢。

### 从融合收益走到图捕获边界

[《图捕获与融合边界》](5.1.1-图捕获与融合边界/5.1.1-图捕获与融合边界.md)沿 eager、捕获、lowering、Triton/CUDA kernel 与 CUDA Graph 重放展开完整路径，并给出可复算融合案例、动态 shape、缓存和训练/推理验收方法。

### Memory planning 与别名

编译器掌握图中每个值的生产者、消费者和末次使用位置，可以让生命周期不重叠的张量复用storage。训练反向需要保存的activation不能提前覆盖，异步stream上的kernel尚未完成时也不能回收。View、slice与transpose可能共享底层storage；一个别名发生原地写，其他别名读取到的内容也会变化。Functionalization把许多原地操作改写成函数式操作，再根据alias语义恢复输出。

融合会改变生命周期。中间值不再落入全局显存，可直接留在register；某些反向所需统计仍要输出，例如LayerNorm的均值与逆标准差。选择保存还是重算要比较额外字节、额外FLOPs和关键路径。只看forward显存容易把成本推到backward。

## 多 GPU 边界

Collective既是数据依赖也是同步边界。Reduce-scatter输出可直接被后续算子消费，编译器可以安排分块通信与计算重叠，却不能跨通信组或改变归约语义。NCCL kernel会使用SM、HBM与网络，和Triton kernel并发时可能互相降速。

融合前后的张量布局必须满足collective接口。若为了局部kernel采用特殊blocked layout，通信前可能需要重排；这一转换会抵消融合收益。性能图应显示通信、layout conversion和消费者kernel，不把collective当作零成本边界。

### 训练与服务的不同目标

训练关注step time、峰值显存和收敛。Forward fusion要与backward一起生成并验证，梯度累积、activation checkpoint和AMP cast都会改变图。动态loss scale跳步、optimizer分支与分布式同步也可能产生graph break。

推理关注TTFT、TPOT、吞吐和p99。Prefill矩阵大、长度变化明显；decode每步token少、形状重复，CPU launch占比更高。服务可对常见batch bucket预编译和捕获CUDA Graph，长尾shape回退。捕获显存与启动时间要计入副本扩容成本。

### 故障定位顺序

性能未提升时依次核对编译区域是否命中、是否反复recompile、目标kernel是否生成、前后是否新增copy/contiguous、资源是否spill、CUDA Graph bucket是否命中。数值异常则从eager与compiled固定输入对照开始，再关闭autotune、fusion和CUDA Graph逐层缩小范围。

编译日志给出graph break与guard失败，generated code给出实际stride和mask，GPU profiler给出kernel、字节与资源。三者使用同一shape关联，避免把编译成功误认为运行一定采用了目标路径。

### 一个融合收益的数量级

形状为`[8192,4096]`的BF16张量约67.1MB。Bias add与GELU分开执行时，中间结果至少写回并读出一次，额外移动约134.2MB；若有效HBM带宽为1TB/s，只有这次往返的下界就约0.134毫秒。融合还能少一次launch，但会增加GELU近似计算期间的register生命周期。

若融合让有效带宽从1TB/s降到0.5TB/s，输入和输出自身约134.2MB的移动时间会由0.134毫秒升到0.268毫秒，可能抵消省下的中间流量。因此验收既看理论字节，也看实际带宽、register与spill。

## 编译产物的生命周期

图cache、二进制kernel、autotune选择和CUDA Graph实例具有不同复用范围。前三者在版本与硬件匹配时可以跨进程持久化；CUDA Graph实例绑定当前CUDA上下文、地址与内存池，服务启动时通常重新捕获。

发布制品注明模型hash、PyTorch、Triton、CUDA、driver和GPU架构。版本不匹配时重新编译，不能沿用未经验证的结果。常用bucket在接流量前预热，长尾shape走通用路径，并持续记录cache命中与recompile。

一次升级若改变分解规则、默认精度或Triton代码生成，即使模型代码不变，也应视为新编译版本。回归测试固定一组真实shape，比较图数量、融合组、二进制资源、数值误差和端到端性能；出现退化时可以回退编译器版本或为具体算子保留稳定实现。

长期监控还要观察fallback比例与shape分布漂移。线上输入逐渐偏离预热集合时，原本高命中的编译方案会退化，需要重新选择bucket和预编译范围。

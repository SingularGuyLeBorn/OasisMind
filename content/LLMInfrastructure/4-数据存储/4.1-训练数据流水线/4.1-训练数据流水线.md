# 训练数据流水线

GPU 每完成一次 step，就要收到形状正确、顺序符合采样策略且没有跨 rank 重复的 batch。训练数据从对象存储抵达设备之前，通常经过不可变 manifest、shard 选择、对象读取、解压与解析、样本洗牌、tokenize 或预先生成的 token 读取、packing、batch collate、pinned memory 和 H2D prefetch。任何一级服务率低于消费速率，都会让设备等待；任何一级状态定义含糊，恢复时都会产生重复或遗漏。

数据流水线以带版本的 manifest 为输入，不能直接依赖可随时改写的 bucket 路径。它列出 shard URI、字节数、样本数、校验和、格式版本、tokenizer 与过滤版本。训练 run 保存 manifest 内容哈希，保证同一配置指向同一组对象。对象存储适合大对象顺序读取，许多小文件会把时间花在请求、鉴权、连接和元数据操作上，因此样本通常先打包为 shard。

## 五段数据流

第一段从对象存储读取 manifest 指定的 shard。第二段按 shard 索引解析样本边界，保证截断、重试和 range request 不会把半条记录当成新样本。第三段由 rank 与 worker 共同分配样本，建立跨进程唯一性。第四段进行 tokenize、过滤、packing 和组 batch。第五段把 host batch 放入 pinned memory，并异步复制到设备，尽量与当前 step 计算重叠。

设集群每秒训练 $R$ 个 token，存储中每 token 平均占 $b_s$ 字节，解压后占 $b_d$ 字节，则对象存储最低有效读取速率约为 $Rb_s$，主机解析路径至少处理 $Rb_d$。Packing 丢弃、过滤、损坏重试会产生放大，实际需求为

$$
B_{store}\ge \frac{Rb_s}{(1-r_{filter})(1-r_{retry})}.
$$

该下界没有包含请求尾延迟。预取队列用缓存时间覆盖尾延迟，容量可按消费带宽乘目标覆盖时长估算，再用 GPU data wait 的 p95/p99 校准。

### Manifest 决定数据版本

Manifest 每条记录至少包含稳定 shard id、URI、对象版本或 etag、内容校验和、压缩与容器格式、样本数、token 数和可选索引 URI。内容寻址对象最稳妥；若对象路径允许覆盖，单独保存 etag 仍要防止生命周期策略改变历史版本。训练启动时验证 manifest 哈希，并抽检对象大小与 checksum。

多语料混合还要保存 source id、权重与采样计划。按固定比例抽样和按剩余 token 动态调整会产生不同顺序。恢复状态必须包含混合调度器的计数与随机状态，不能只保存每个源当前 shard。发现污染数据时生成新 manifest 版本，旧 run 继续指向旧版本，实验差异才可追溯。

### Shard 是读取与调度单位

Shard 合并小样本以获得顺序吞吐，同时提供足够数量供 rank 和 worker 并发。过小会增加 GET、open、seek 和索引开销；过大则减少调度粒度，单对象重试代价更高，也会限制 shard-level shuffle。选择大小时同时看单 worker 吞吐、对象请求延迟、训练并发数、缓存容量和可接受的恢复重读量。

容器应明确样本边界。Tar 一类顺序格式可用成员 header，长度前缀格式可用 offset/length 索引，JSONL 依赖换行且要处理转义与截断。压缩若只能从头解码，恢复到 shard 中部会重读前缀；seekable 压缩或分块 frame 可以缩小恢复成本。每个样本最好有稳定 id，由源版本与原始位置生成，便于检测重复和追溯。

## Rank、worker 与随机顺序

分布式读取需要一条全局分配规则。常见规则先对 shard 做确定性排列，再按全局 worker id 分配：

$$
g=rank\times W+w,\qquad G=world\_size\times W,
$$

其中每 rank 有 $W$ 个 DataLoader worker，worker $g$ 处理排列后满足索引模 $G$ 的 shard。若 shard 大小差异显著，可按 token 数做平衡分配，但分配结果要可重建或保存。

PyTorch `DistributedSampler` 的 epoch seed 必须随 epoch 改变；漏掉 `set_epoch(epoch)` 会让各 epoch 使用相同排列。流式数据没有自然 epoch 时，可用逻辑 epoch、全局 token 区间或固定大小 cycle 驱动 seed。Shard shuffle 与样本缓冲 shuffle 分开定义，才能解释实际随机窗口。

### Packing 改变消费位置

样本长度不同，直接 padding 到 batch 最大长度会浪费 token。Packing 把多条文档拼入固定长度序列，保存文档边界、position id 和 attention mask 语义。若允许跨文档 attention，训练目标与独立文档不同；若禁止跨文档 attention，kernel 需要消费 segment 信息。EOS 是否计入、超长样本怎样切分、短尾怎样处理，都影响 token 计数。

恢复位置不能只写“第 1000 个样本”。一个 packer 可能已经从上游取走若干样本，却尚未组成可提交 batch。严格恢复要保存或重建 packer 的待处理队列、每条样本的消费 offset、已形成但未提交的 batch，以及 DataLoader prefetch 中已分配的工作。较简单的实现回退到最近安全边界并允许有限重放，但必须用 sample id 量化重放范围。

### Prefetch 只隐藏可预测的等待

主机侧通常有对象下载队列、解压/解析 worker 队列、已完成 batch 队列和 H2D stream。队列太浅无法覆盖 p99 对象延迟，太深会增加内存、扩大取消损失，并让 checkpoint 捕获更多在途状态。吞吐调优要记录各队列深度、blocked producer 时间、blocked consumer 时间和 GPU data wait。

Pinned memory 允许异步 DMA，却是受限系统资源。过多 worker 各自积压 pinned batch 会增加物理内存压力。`num_workers`、prefetch factor 与 batch 字节相乘可以估算上界；NUMA 系统还要让解码线程、pinned buffer 和目标 GPU 尽量位于同一 CPU socket。

## 正确性与吞吐一起验收

正确性测试为每个样本携带稳定 id，收集一个逻辑 epoch 内各 rank 的 id，检查交集、并集、顺序哈希和尾部补齐策略。Packing 额外检查 token 数、文档边界、loss mask 与 EOS。故障注入在 shard 下载、解析、batch 已生成和 H2D 完成等位置终止进程，恢复后比较提交样本序列。

吞吐测试拆分对象 GET、解压、解析、tokenize、packing、collate、H2D 与 GPU data wait。缓存冷态和热态分别测量，对象大小与并发数随结果记录。系统只有在样本序列满足既定语义时，吞吐数字才有效；通过跳过慢 shard、重复缓存样本或扩大预取而改变训练数据，不属于等价优化。

### 数据身份如何进入分片与恢复

[《分片洗牌与恢复》](4.1.1-分片洗牌与恢复/4.1.1-分片洗牌与恢复.md)给出从 manifest 到 batch 的完整状态机，展开确定性 shard/sample shuffle、跨 rank 唯一性、样本边界、packing、prefetch 和断点恢复，并用手算与故障注入同时验收吞吐和数据正确性。

### 状态与指标分开记录

Manifest hash、全局样本坐标、shuffle seed、packer残留与已提交batch序号属于恢复状态，必须随checkpoint持久化。对象请求延迟、队列深度、CPU利用率与GPU data wait属于运行指标，可以丢失而不改变下一批数据。两类信息混在普通日志里，会让恢复依赖日志保留时间，也难以验证原子一致性。

## 调优边界

扩大prefetch、增加worker或缓存shard都可能提高吞吐，也会改变内存峰值、随机交付顺序与故障重放范围。每次调优固定manifest、seed、global batch与packing语义，比较相同提交样本序列下的设备等待时间。若样本集合、顺序约束或有效token数发生变化，应视为训练配置变化。

训练规模扩大时，数据服务率要按集群总消费计算，不能拿单节点顺序读取带宽直接外推。对象存储的prefix分布、网关连接数、节点出口带宽和共享CPU都会形成集群上限。压测使用与正式训练相同的节点数、对象分布和启动并发，并记录后端限流与重试。

恢复能力也要进入性能预算。更细的work unit减少故障重读，却增加索引与提交元数据；更大的shuffle buffer改善局部随机性，却增加重建时间。方案选择以长期有效token数为目标，把正常运行吞吐、checkpoint暂停、失败重算与恢复耗时放在同一统计周期内。

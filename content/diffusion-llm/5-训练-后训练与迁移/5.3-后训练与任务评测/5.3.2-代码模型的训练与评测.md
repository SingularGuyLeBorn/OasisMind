# 代码向扩散:DiffuCoder,AR-ness 与 coupled-GRPO

扩散代码模型常被两组无法直接比较的数字夹住.Mercury Mini 报告 1109 tok/s,HumanEval 可到 90.0,但参数量没有公开;通用开源 7B 的 Dream Instruct 在自身 Table 2 上只有 55.5,对照中经过 RL 的 Qwen2.5 为 84.8.DiffuCoder(Gong 等人,arXiv:2506.20639)补上了开源代码模型这一格:7B 参数,从 Qwen2.5-Coder 改编,使用约 130B 有效代码 token,再做 SFT 与 coupled-GRPO.它的实验还测量揭开顺序,并在 RL 阶段使用一对互补掩码. 评测库,是否代码专料,Instruct 配方都不同.

## 配方:改编,不是从头堆代码模型

骨干和词表跟 Qwen2.5-Coder,改编路径类似 Dream / DiffuLLaMA:移位保住,$h_i$ 仍对准下一个位置.语料写了 RefineCode 与 Stackv2,作者提到约 400B token 的代码预训练池,以及和 Qwen2.5-Coder / OpenCoder 相近的 code-to-text 比.Stage 1 真正吃进去的有效 token 在 65B 处早停.他们观察到训到 700B 时下游验证变差,AR-ness 反而升高,于是丢掉更长的那一截.Stage 2 用约 16B 退火代码数据,重复到 4 个 epoch,合计再记 65B.摘要里的「130B tokens of code」指这两段有效量,不是 400B 池全吃完. SFT 用 OpenCoder 的 436K 样本.RL 从 Acecoder-87K 里挑 21K 带可验证测试的难题.机器是 8 到 10 个节点,每节点 8 张 H100.后训练代码改编自 Open-R1.这些数字只说明预算量级,不能用来换算「比 LLaDA 的 13 万 H800 小时更便宜」:任务,序列长度,是否全参都不同. Table 1 是作者评测环境.EvalPlus 定义为 HumanEval+ 与 MBPP+ 的平均.摘开源 7/8B 几列:

| Qwen2.5-Coder | 61.6 | 51.8 | 75.9 | 61.4 | 56.6 | 46.1 |
| DiffuCoder | 67.1 | 60.4 | 74.2 | 60.9 | 60.6 | 40.2 |
| Dream | 56.7 | 50.0 | 68.7 | 57.4 | 53.7 | 23.6 |

Dream 原文 Table 1 带 $*$ 的 HumanEval 是 57.9,本表 Dream 是 56.7.两套协议不能据此计算「Dream 退步了」.讨论 DiffuCoder 对 Dream 用 Gong 的表;讨论 Dream 对 Qwen2.5 用 Ye 的表.

## AR-ness:揭开顺序到底有多像从左到右

任意顺序训练给了所有排列,低置信 remask 推理会自己挑一条.Gong 等人把「这条路有多像 AR」写成两个可测的量.局部 AR-ness@$k$:新揭开的字,和它前面刚揭开的 $k$ 个字,是否为严格递增的连续下标.$k=1$ 衡量 next token 式生成.全局 AR-ness@$k$:这一步选中的位置,是否属于剩余掩格中最靠左的 $k$ 个.AR 解码两个量都恒等于 1.扩散两个量低于 1,但通常更靠近 1:文本本身有从左到右的结构,从头训的 LLaDA 和改编的 Dream / DiffuCoder 都会抓住一部分.改编模型的 AR-ness 往往更高,因为基座就是左到右训出来的.

代码和数学不一样.GSM8K 上全局 AR-ness 更稳,更偏左;HumanEval 上均值更低,方差更大.作者的解释是:数学文本几乎必须按演算顺序写,代码可以先写函数体再补签名,也可以先写返回值再填循环.这是观察,不是「代码任务上扩散一定更强」的证明.Table 1 上 DiffuCoder Base 的 HumanEval 确实高于同表 Dream,也高于同表 LLaDA,但分母里有 130B 代码 token,Dream 并非代码专料.

熵汇(entropy sink)出现在条件生成的第一步:提示干净,回答全掩.各位置的置信度画出来像 L 形,紧挨前缀的格子特别尖.低置信 remask 会先揭这些格子,于是解码被吸回「接着前缀往右写」.温度默认 0.2 时,这条吸力很强.升到 1.2,AR-ness 明显下降:不但 token 选择散了,揭开的位置也散了.AR 模型升温只散词,不散顺序,因为它没有顺序可散.pass@10 随温度从 0.2 升到 1.2 变好,说明基座里藏着更多能过测试的轨迹,pass@1 默认设置只是没把它们采出来.RL 需要这种多样性当 rollout.训练 coupled-GRPO 时他们把在线采样温度放到 1.2,评测 Table 2 再在 $\{0.2,0.3,0.4\}$ 里取最好.

Stage 1 训到 65B 时 AR-ness 已经偏低;继续训练到 700B 后,AR-ness 回升且验证变差,因此作者选择早停.中训和 SFT 的第一个 epoch 会抬高因果偏差,随后任务性能改善,AR-ness 再次下降.GRPO 之后全局 AR-ness 继续降低,并且步数减半时掉点比 Instruct 更小.作者据此认为,模型可以自行学习需要多强的因果顺序,无需依靠固定的小块半自回归解码.

## coupled-GRPO:一对互补掩码,每个 token 当一次目标

掩码扩散没有精确的 $\log\pi(y\mid x)$,GRPO 的重要性比只能估.d1 的办法是把整段 completion 全掩,一步前向,用 $t=1$ 的边际当序列概率.省,但偏:熵汇会让左边的 token 梯度更猛;代码任务上再去掩 15% 提示,作者发现奖励曲线不稳,于是退回「提示不掩,completion 全掩」当基线.即便如此,每个 token 总在「完全看不见兄弟」的上下文里被打分,和生成时逐步揭开对不上.

coupled-GRPO 抽 $\lambda$ 对互补时间 $(t,\hat t)$,满足 $t+\hat t=T$.两个掩码并起来盖住全部 completion,且每个位置恰好在其中一个里当预测目标.实践取 $\lambda=1$,再加一次全掩 $t=T$,对数概率对这几次平均. antithetic:一对噪声负相关,方差下降.每个 token 都有非零学习信号,又都在「部分可见」的真实上下文里被估,而不是永远全盲.

> 图 1:同一段 completion 抽一对互补掩码,汇成 coupled-GRPO 的对数概率.每个 token 恰好当一次目标.

### 图 1 怎么读

- **completion y**:在线 rollout 已经写完的回答,奖励在这里打.
- **mask A / 补集**:位置划分,不是两种 $Q_t$.前向仍是吸收态.
- **汇合**:两次交叉熵拼成对每个 token 的一次估计,再进 GRPO 的 $\rho_i^k$.
- **不是新噪声**:训练预训练仍是 $1/t$ MLM.这里只改策略梯度里的似然估计.
- **和 d1 的差**:d1 相当于只走全掩那一次;本图强制部分可见.

Table 2,温度集合 $\{0.2,0.3,0.4\}$ 取最好.DiffuCoder-Instruct → coupled-GRPO:HumanEval 72.0→73.2,HE+ 65.2→68.3,MBPP 75.1→78.6,MBPP+ 61.9→67.5.EvalPlus 63.6→67.9,摘要写成 +4.4%.同表消融:completion 全掩(d1 风格)HumanEval 掉到 66.5,HE+ 59.1;同等次数但不互补的 decoupled 是 68.9 / 62.8.互补约束比「多抽几次随机掩码」更值钱.Leave-one-out 优势在 MBPP+ 上到 68.5,HumanEval 上反而到 70.7,任务间不稳定.奖励是格式分加测试通过率. 同数据的 Qwen2.5-Coder+SFT 再加 AR 的 GRPO:HumanEval 82.9→80.5,掉了;MBPP 80.1→84.4,涨了.扩散这边 HumanEval 小涨,Plus 和 MBPP 涨得更明显.分母是 Qwen 的 SFT 已经 82.9,DiffuCoder Instruct 只有 72.0.RL 是在各自的 SFT 墙上挖,不是从零起跑. 作者强调 coupled-GRPO 不依赖半自回归,不把块长训死.d1 在 LLaDA 上常常配合小块解码.代码实验里,全掩基线不稳定,互补掩码才把奖励曲线拉平.这是扩散原生的估法,并非直接使用AR的token对数概率公式.

**VRPO,d1 与商业代码模型。** VRPO 使用离线偏好对,主要成本是四条 ELBO;d1 使用数学可验证奖励,以一步全掩估计概率;coupled-GRPO 使用代码测试,以一对互补掩码估计概率.三者都在精确 $\log\pi$ 不可得时构造代理量,形式随数据与奖励改变.VRPO 的任务包含开放式写作与对话,d1 评估 GSM8K 和数独,coupled-GRPO 评估 HumanEval;模型,奖励与采样器均不相同. 商业 Mercury 的 HumanEval 90.0,Gemini Diffusion 89.6,来自公开报告行.开源 DiffuCoder coupled-GRPO 是 73.2.中间差的是规模,数据,系统栈,是否闭源,不是「开源不会写代码」.Dream Instruct 在 Gong 表上 HumanEval 57.9,还没有这条代码专料.想自托管一条可复现的代码扩散,检查点在 [apple/ml-diffucoder](https://github.com/apple/ml-diffucoder),表用 Gong Table 1–2.想要四位数 tok/s,那是 Mercury / Seed 的交付物卡,见Dream / Mercury / Seed章节. 半步数掉点变小,是 AR-ness 下降的副作用,并非 CAP 那种系统加速.推理加速章节中的 DualCache,dKV-Cache 仍可叠,DiffuCoder 原文没有把 27.6× 写进主表.27.6× 的对照物是原版 LLaDA,并非本模型.

**失效。** 把 DiffuCoder 表的 LLaDA-Instruct HumanEval 35.4 写进 Nie 的 Instruct 规格:harness 不同,Nie Table 2 是 49.4. 把 130B 写成 400B:400B 是语料池,Stage 1 早停在 65B. 把温度 1.2 当评测默认:那是 rollout.Table 2 评测温度在 0.2–0.4. 把 EvalPlus +4.4% 理解成相对 63.6 再乘 1.044:表上是 63.6→67.9 的绝对点.摘要的百分号和表格的百分点不能混为. 把 coupled-GRPO 理解成新的 $Q_t$:噪声仍是吸收态,变的是 RL 的似然估计. Figure 1 中的一对掩码覆盖完整 completion,每个 token 恰好一次作为目标,另一次作为可见条件;d1 全掩估计则让所有目标同时缺少 completion 内部上下文.Table 1 显示 Base 已接近 Qwen2.5-Coder,Instruct 的提升小于同数据 AR SFT,随后 21K 条 RL 样本将 EvalPlus 推到 67.9.这些结果描述 DiffuCoder 的训练链,与 Mercury 的商业吞吐属于不同证据.

以四个 token 的 completion $(w,x,y,z)$ 为例,时间 $t$ 的掩码盖住 $w,y$,互补掩码盖住 $x,z$.第一次前向只对 $w,y$ 计算损失,此时 $x,z$ 可见;第二次只对 $x,z$ 计算损失,此时 $w,y$ 可见.每个位置恰好一次作为目标,另一次作为条件.全掩基线中的目标始终缺少 completion 内部上下文,左侧熵汇会使梯度分布偏斜;decoupled 随机抽取两份掩码时,有的位置可能重复成为目标,有的位置完全没有梯度.互补约束固定了位置覆盖,这是 Figure 1 中方差下降的来源.$\lambda=1$ 对应一对互补掩码,再加入一次 $t=T$ 的全掩前向,补充高噪声端的边际信息.整个估计复用同一策略网络,每个样本执行三次前向.

pass@k 和温度要分开读.0.2 时 pass@1 好看,pass@10 几乎不涨,轨迹挤在同一条路上.1.2 时 pass@1 可能掉一点,pass@10 抬起来,揭开顺序也散.RL 吃的是后者:组内要有过测试的,也有不过的,优势才分得开.评测 Table 2 回到 0.2–0.4,是把已经强化过的 pass@1 用低温度榨出来.把 1.2 写进产品默认采样,会把 Instruct 的 pass@1 打回去.温度在扩散里是双旋钮:词的熵,加上位置的熵.仅沿用AR的「解码温度 0.2」会把位置熵固定,AR-ness 回升,半步数掉点的那点好处也会吐回去.

Stage 1 训到 700B 变差,作者归到预训练数据质量.更长并不自动把代码扩散训好.有效 65B 早停,再用干净退火数据重复,是承认噪声语料会把已经学到的非因果结构冲回「假 AR」.AR-ness 在 700B 处回升,和下游一起坏,像是模型重新依赖左到右捷径.早停不是超参神话,是验证集投票.复制实验若只采用130B预算而忽略早停条件,可能会把 Stage 1 跑满池子,然后奇怪为什么不如论文.

MMaDA 也把 GRPO 接到扩散上,但使用多模态统一骨干,解码常配合块.DiffuCoder 的 coupled-GRPO 不依赖小块,两者的似然估计不同.d1 面向数学任务,采用一步全掩并常配半自回归;DiffuCoder 把全掩作为阴性对照时,HumanEval 降到 66.5.现有公开主表没有证明 VRPO 的四条 ELBO 可以由一对互补掩码代替,三种估计方法分别得到各自任务的实验支持.

改编几何仍适用.Qwen2.5-Coder 的下一 token 头没有被拆掉,继续预训练才不会把代码语法冲成随机填空.dKV-Cache 在 Dream 上演示过:移位搞反,GSM8K 可以掉到 32.68.DiffuCoder 没把这条消融写成主表,但不意味着移位可以随便改.读代码扩散实现,先看位置 $i$ 的预测靶子是 $x_i$ 还是 $x_{i+1}$.靶子错了,后面所有 HumanEval 都不可信. 436K 样本来自面向 AR 的 OpenCoder 配方,而掩码扩散还涉及画布长度,EOS 和填充方式.d1 附录报告扩散 SFT 对格式敏感,DiffuCoder 没有提供扩散原生 SFT 数据的主消融.现有结果只表明这套 AR 风格 SFT 增益有限,随后加入可验证 RL. BigCodeBench 完成式全量上,Instruct 相对 Base 是 40.2→35.7,掉了;coupled-GRPO 拉回 40.4,几乎只回到 Base.Hard 子集 Instruct 12.2,GRPO 10.8,没有抬上去.主表的好看集中在 HumanEval / MBPP 家族.报「代码扩散已经打平 Qwen Instruct」之前,先看 BCB.打不平.现有证据仅支持 Base 的 HumanEval / EvalPlus 附近,Instruct 之后仍认 Qwen2.5-Coder-Instruct 的 90.2.

GRPO 其余零件仍是 AR 那套:组内相对优势,PPO 式裁剪,对参考策略的 KL.换掉的只有 $\log\pi$ 怎么来.组大小 $G$ 决定优势有多稳,扩散每条组员都是一次多步去噪,把 $G$ 加到 16 在线成本线性涨.原文没把 $G$ 扫成主消融.奖励两件:代码格式,加上测试用例通过率.格式分防止模型交一堆能编译但不能过测的碎片;通过率才是对错.没有过程监督,中间变量写错但最终测过,仍拿满分.这和 d1 的「格式加 boxed 答案」同类,只是裁判从字符串匹配换成解释器.奖励黑客在扩散上多一条路:正确碎片可以写在不相邻的揭开位置上,中间填注释或占位.评测抽取函数体的脚本若太松,会把这种拼图当成功.看 case 时应当看整段 completion.

半步数掉点变小,写在原文 Figure 1(c),主表没有列出「步数减半后的 HumanEval 精确格」.能引用的是方向:coupled-GRPO 之后,少步时掉得比 Instruct 少,并和全局 AR-ness 下降放在同一段讨论里.步数减半省的是前向次数,每步仍是全双向注意力.系统级 tok/s 去 Mercury / Seed 那张交付物卡. 代码 infill 是任意顺序的产品形态.提示左右都在,中间一段待写.DFM 1.7B 的论文用填空当卖点,但 HumanEval Pass@1 只有 6.7%,和DiffuCoder 7B 的 73.2 不是同一量级.机制上 infill 不必等 DFM:掩码扩散训练时已经见过两边可见.DiffuCoder 主表仍是标准补全,没有把 infill 做成 HumanEval 那种主数字.能力在,规格卡上没单独一列. LLaDA 2.0 post-training 的互补掩码提高数据利用率,语料小于约 100B 时有用.coupled-GRPO 的互补掩码用于让每个 completion token 在策略梯度里被公平地估一次对数概率,目标不同于增加预训练token覆盖.两者形状相近,用途不同.

局部 AR-ness 随 $k$ 变严:要连续 $k$ 个下标都是「刚才那个字的后继」,$k$ 一大几乎没人达标,曲线往下掉.全局 AR-ness 随 $k$ 变松:允许在最靠左的 $k$ 个仍掩位置里挑,$k$ 一大很容易达标,曲线往上走.读原文 Figure 3 时两根轴方向相反,不是画反了.改编模型两根都比从头训更高,说明 Qwen 的左到右习惯还在.温度 1.2 把两根一起压下来,才是「扩散真的在用任意顺序」的测试时证据.默认 0.2 加低置信 remask,看起来仍很像 AR,只是偶尔跳一下.产品若把温度固定在 0.2,用户几乎感觉不到任意顺序,只会感觉步数多,填空方便.这并非论文造假,是默认采样把集合又收窄了.

仓库 `apple/ml-diffucoder` 提供权重和 coupled-GRPO 训练脚本.复现 Table 2 必须记录温度集合,EvalPlus 定义(HE+ 与 MBPP+ 平均),以及「best of {0.2,0.3,0.4}」.只跑一次温度 0.2 的 HumanEval,会对不上 73.2.商业 90 分那一行带 $*$,不能用来验收开源训练是否成功. 通用 8B 的数字还要区分评测协议.Nie 的 HumanEval 35.4 来自 Base 模型,通用数据及其生成协议;Gong 的表中,LLaDA Base 同样是 35.4,Instruct 列仍为 35.4(相对 Base 0.0),MBPP 反而下降 18.6 点.这套 Gong harness 与 LLaDA 原文中 Instruct 的 49.4 不同.因此引用时必须同时注明 Gong Table 1 或 Nie Table 1–2,两张表中的 LLaDA 分数不能相减. **从 pass@k 到真实修复任务。** 代码评测里最容易被忽略的是采样预算。设一道题独立采样 $k$ 次，其中恰有 $c$ 个候选通过测试，总样本数为 $n$，常用的无偏估计为

$$
\operatorname{pass@}k=1-\frac{\binom{n-c}{k}}{\binom{n}{k}}.
$$

它衡量「给模型 $k$ 次机会，至少命中一次」的概率。扩散模型可以同时改变 token 选择和揭开顺序，提高温度后，候选差异会来自两层随机性。pass@10 上升而 pass@1 不变，通常说明覆盖面扩大；只有 pass@1 也稳定上升，才能说明单次交付更可靠。结果还要固定 $n$、温度、步数、最大长度和测试版本，否则同一个 checkpoint 会得到一组无法复核的数字。

HumanEval 和 MBPP 主要检查短函数生成，EvalPlus 增加更强的隐藏测试，BigCodeBench 则包含更贴近库调用与指令遵循的任务。短算法题容易暴露逻辑分支错误，扩展测试更容易抓到边界条件，库调用任务还会惩罚错误 API、缺少依赖和输出格式偏差。扩散模型常见的局部一致、整体不闭合，在基础测试上可能过关，却会在扩展测试中因异常分支、变量生命周期或返回类型失败。因此代码扩散不能只报一个 HumanEval 数字。

真实代码修复还多了仓库状态。模型要读测试、调用关系和已有实现，再只改动有限区域。掩码扩散天然适合把待修改 span 置为 `[MASK]`，但训练数据若只有从头补全，模型没有学过「保留未掩代码」这条约束。评测至少应记录补丁大小、未授权改动、编译结果、测试通过率和多轮尝试次数。一个能通过测试却重写整个文件的候选，在基准上可能得满分，在代码审查里仍然不可用。

**训练与推理成本。** coupled-GRPO 每个样本需要互补掩码的两次前向，再加高噪声端的一次前向。计算量近似按三次模型调用累计，实际墙钟时间还受序列长度、组大小和批处理影响。若一组候选共享提示词，提示部分可以在 batch 维复用输入；全双向去噪阶段的隐藏状态仍随当前掩码变化，不能像严格 AR KV Cache 那样只算一次。训练吞吐应以每个优化步处理的 completion token、有效目标 token 和总 FLOPs 同时记录，仅报 samples/s 会掩盖互补掩码提高监督覆盖率的收益。

推理端也要分清模型前向次数和生成 token 数。长度 $L$、去噪步数 $T$ 的全双向生成会执行 $T$ 次整段计算；AR 模型执行约 $L$ 次增量计算，并复用历史 KV。若 DiffuCoder 用 $T=L/2$，前向次数看似减半，但每次处理的是整段。短函数上 GPU 并行可以摊平这一点，长文件或小批量场景未必成立。速度结论应附带提示长度、输出长度、batch、硬件与编译后端，单独的「步数减半」不足以推出端到端加速。

代码任务还有确定性执行环境这一层。Python 版本、依赖版本、测试超时和随机种子都会改变通过率；允许网络访问的测试甚至可能把外部服务波动算进模型能力。评测容器应固定镜像并关闭网络，分别记录编译失败、运行时异常、超时和断言失败。四类失败对应不同改进方向：语法数据、API 使用、算法复杂度和逻辑正确性。把它们压成一个 pass@1，只能用于排行榜，无法指导下一轮训练数据怎么补。 多语言评测还要分开编译型与解释型语言。前者在运行测试前已有语法和类型检查，后者常把同类错误拖到执行期；直接平均会掩盖模型在哪个阶段失败。

### 代码状态如何表示

代码扩散先在token序列上工作,状态写成 $z_t\in(V\cup\{M\})^L$.词表同时包含自然语言、关键字、标识符、字面量、缩进与标点.同一个掩码符号覆盖的对象差异很大:缺失括号往往可由局部语法恢复,缺失函数名需要跨文件语义,缺失算法主体还依赖题意. 因此token级掩码率只描述缺失数量,没有描述缺失结构.两个状态都掩掉30%,一个只缺空格与括号,另一个缺函数签名与关键分支,恢复难度完全不同.训练与评测应按语法角色、作用域和依赖距离分桶. **词法token与结构节点。** 普通语言tokenizer将代码切成子词,优点是复用语言模型词表,缺点是一个标识符可能被拆成多片,一次并行更新会生成互不一致的片段.抽象语法树节点提供明确结构,又会丢失注释、格式与部分语言细节.

混合表示可保留token序列作为生成目标,同时输入AST位置、节点类型或作用域边.模型仍输出普通代码,结构特征帮助识别哪些位置应联合恢复.解析失败的中间状态没有完整AST,需要容错解析或从最近合法状态继承结构. **缩进与空白。** Python缩进属于语法,其他语言空白多半只影响格式.统一token损失会把大量低价值空白与关键符号混在一起.规范化格式可以减少状态空间,同时让模型无法学习用户原始风格. 训练可在语义任务中规范化,代码编辑任务则保留格式.评测要区分编译、测试和格式一致性,防止模型靠统一格式提高token匹配却破坏最小改动要求.

**标识符的一致性。** 同一变量在定义与多处使用中必须一致.逐token独立恢复可能生成多个近似名字,每个局部概率都高,程序仍无法解析.标识符簇是天然联合变量. 可根据作用域图把同一符号的出现绑定,先生成规范标识符,再复制到使用点;也可保留自由生成,用符号解析器校正.前者提高一致性,限制重命名多样性;后者更灵活,需要可靠解析.

### 训练目标的层次

基本去噪目标预测被掩token:

$$
L_{\mathrm{tok}}=\mathbb E_{t,z_t}\left[\sum_{i:m_i=1}w(t)
-\log p_\theta(x_i\mid z_t,t)\right].
\tag{4}
$$

它奖励逐位置真值,没有直接保证整段可编译、通过测试或保持语义.代码的正确性高度离散:少一个符号即可全错,多个不同程序又可能行为等价. **语法辅助目标。** 模型可额外预测token类型、括号深度、AST父节点或当前作用域.这些目标让隐藏表示携带结构,对早期高噪声状态尤其有用.辅助标签来自解析器,损坏代码可能无法生成完整标签. 语法目标过强会奖励表面合法.一个编译通过的空实现可以获得很好结构分,功能仍为零.语法损失只能作为必要条件,不能替代执行监督. **数据流目标。** 定义—使用关系、变量类型和函数调用图描述语义依赖.遮住定义后预测所有使用点,或判断两个位置是否属于同一符号,能训练长程一致性.

静态分析在动态语言、反射与宏下不完整.把分析结果当软特征比硬真值稳妥.编译器无法解析的项目也不能被全部丢弃,否则训练集偏向简单代码. **执行目标。** 单元测试、编译器和解释器提供序列级奖励.它们接近真实行为,信号稀疏且覆盖有限.通过公开测试可能仍在隐藏测试失败,编译成功只说明语法和类型基本合法. 执行奖励可用于筛选样本、偏好训练或强化学习.扩散模型一次轨迹含许多中间状态,终局奖励如何分配到揭开顺序和token决定并不明确.coupled-GRPO降低方差,仍受测试覆盖上限约束.

**等价程序。** 同一函数有许多正确实现.逐token交叉熵只承认参考答案,会惩罚不同算法、变量名与控制流.执行奖励扩大正确集合,但有限测试会接受投机程序. 可结合规范化AST、语义哈希、形式验证或更多生成测试.没有一种廉价方法覆盖所有语言特性.评测应将参考相似度与功能正确分开.

### 噪声形状与代码结构

随机token掩码提供广覆盖,常产生现实中不会出现的孔洞.代码补全更常缺连续后缀、一个函数体或若干编辑位置.训练状态与部署任务不匹配时,模型虽有低MLM损失,实际补全能力有限. **连续块掩码。** 函数体或表达式块掩码要求模型生成内部结构,两侧边界提供接口约束.块越长,正确实现越多,token真值越不充分.按AST边界采样比任意字符窗口更贴近任务. 连续块也可能泄漏答案长度.固定槽位告诉模型缺失多少token,真实代码插入长度未知.若模型只能等长填空,其能力范围应明确限制. **后缀掩码。** 后缀恢复接近自回归补全,右侧条件消失.它检验扩散模型在单侧上下文下是否仍可用.只训练随机孔洞的模型会过度依赖右侧答案线索.

后缀长度应覆盖短行、函数与文件级.短后缀平均分无法说明长实现能力.生成EOS与长度预测成为关键. **编辑噪声。** 真实修复包含替换、插入与删除.固定长度掩码只覆盖替换和已知槽位填充.编辑扩散需要动态序列状态或预分配空间,转移与对齐更复杂. 训练可从版本历史提取错误—修复对,比随机破坏更真实.提交同时包含重构、格式和功能变化,需要过滤无关改动.自动合成bug则容易留下模板痕迹. **语义噪声。** 把比较符号、边界常数、变量引用或API调用替换成另一合法token,程序仍可编译却行为错误.这类噪声比随机掩码更接近真实bug,也更难检测.

语义噪声应保证错误确实改变行为,可用测试或符号分析验证.未经验证的替换可能等价,把正确程序错误标成负例.

### 语法约束如何进入生成

硬约束在每步过滤不合法token,保证前缀或部分树可扩展.软约束只调整概率,保留模型纠错空间.扩散状态并非自左向右前缀,传统解析器需要适配含孔洞的程序. **容错解析。** 解析器可以插入虚拟节点、缺失符号和错误节点,为不完整代码构造部分AST.调度器优先修复阻塞解析的位置,再处理语义.解析成功率提升通常有助于编译,不保证测试通过. 容错规则本身带语言偏见.复杂宏、模板和预处理器可能被误判.评测需按语言分别报告. **语法掩码。** 给定部分语法状态,将不可能token概率置零,可减少无效采样.约束错误时正确答案也会被排除,形成不可恢复失败.硬掩码适合明确文法,动态语言与跨文件符号更适合软约束.

语法掩码还改变概率分布,与原扩散反向核不完全一致.若目标是任务解码可以接受,若声称保持模型采样分布则需分析偏差. **括号与成对符号。** 括号、引号和标签应联合生成.分别按最高概率确认可能产生不配对组合.调度器可把成对位置作为一个组,或确认一端后立即条件化另一端. 嵌套深度增加后,局部距离不够.栈状态和AST边提供长程约束.字符串中的括号不应进入语法栈,词法状态必须先区分.

### 语义约束

编译器类型检查、名称解析和控制流分析能发现一部分语义错误.它们可在每轮或检查点运行,为重掩与停止提供信号.频繁完整编译成本高,局部增量分析需要维护状态. **类型约束。** 类型缩小候选API与操作符.静态类型语言信号强,动态语言只能依赖推断或运行时样例.泛型、联合类型和隐式转换让硬过滤存在风险. 模型预测类型与编译器类型可共同使用.编译器结果可靠时优先,未知类型保持软分布,避免把不完整分析当错误. **数据流一致性。** 变量必须先定义再使用,资源需要成对释放,返回值要覆盖所有路径.这些约束跨越多行.图神经特征或长程注意力可编码,最终仍需静态分析验证.

扩散任意顺序可能先生成使用点再生成定义.生成顺序与程序执行顺序不同,只要最终一致即可.训练不能把「先生成定义」误当唯一正确轨迹. **API与库版本。** 代码可编译仍可能调用不存在或过时API.训练数据跨版本混合,模型高置信生成旧接口.给定项目依赖文件、类型存根和文档可提供条件. 评测环境必须固定版本.缺少依赖导致的失败应与模型逻辑错误分开,但模型遗漏依赖声明仍属于任务错误.

### 填空任务的条件结构

中间填空同时拥有左上下文与右上下文,扩散模型天然可以双向读取.右侧包含变量使用、返回结构和后续断言,能强约束缺失代码.这是真实优势,也可能造成基准泄漏. **右侧答案泄漏。** 若右侧注释、测试或生成代码直接描述缺失实现,模型无需理解问题.构造基准时应检查重复文本、自动生成标记和引用.真实IDE补全允许使用右侧,但要明确任务就是FIM而非从题意独立求解. **多孔填空。** 多个孔之间可能共享变量和控制流.独立恢复每孔会组合出不一致实现.联合去噪能够互相条件,并行确认仍需控制相关错误. 评测应同时报告每孔正确与整个文件通过.单孔平均高、联合成功低,说明相关性处理不足.

**长度未知填空。** 预设掩码数会泄漏答案长度.真实编辑需要预测插入长度或使用可变长状态.可先生成结构计划与长度,再填token;计划错误会限制后续. 不同正确实现长度差异大,参考长度不能作为唯一监督.执行成功与代码简洁度可作为补充.

### 修复任务的状态语义

修复输入包含错误明文,模型必须判断哪些token不可信.标准掩码训练中的明文都来自真值,会鼓励复制,与修复需求冲突.训练应显式加入错误明文或使用允许重掩的过程. **错误定位。** 给定报错行比全文件修复容易.真实bug定位可能跨文件、跨调用.评测要区分oracle定位与端到端定位.两者分数不可直接比较. 定位器的召回决定修复上限.只改低置信位置会漏掉高置信逻辑错误.编译器栈、测试失败和数据流切片能提供额外证据. **最小修改。** 许多修复任务要求保留正确代码,只改必要位置.扩散全局去噪可能重写大量无关文本.编辑距离正则与只读区域能限制.

最小改动不总是最佳.重构可能更清晰或修复根因.基准若按补丁完全匹配,会惩罚功能等价方案.应同时报告行为与补丁大小. **回归风险。** 通过触发bug的测试不代表没有破坏其他功能.完整测试、静态分析和差分测试提高覆盖.测试集仍有限,补丁可能过拟合. 生成多个候选并按独立验证排序比反复优化同一公开测试更稳.隐藏测试必须与训练和筛选隔离.

### 并行解码的正确性边界

代码token依赖通常比自然语言更尖锐.一个函数名、类型或缩进可约束大片区域.并行确认独立局部token很有效,同时确认强耦合token会产生合法边际、非法组合. **可安全并行区域。** 不同函数、独立参数、列表元素和重复模板可能近似条件独立.同一表达式、变量定义与使用、开闭符号和控制流分支高度耦合.安全性取决于当前已知上下文,并非固定token类型. 可通过条件互信息、AST距离与干预预测变化估计.静态距离只是代理,跨函数全局变量会产生远程依赖. **同批联合错误。** 两个位置各自首选概率都高,组合后类型不匹配.逐token置信阈值无法发现.可在候选批上运行局部解析、类型检查或联合打分.

检查失败后缩小批或先确认一个枢纽,重新条件化其余.这会减少并行度,换取正确性.报告平均每轮确认量时要同时给回滚率. **顺序与执行顺序。** 任意顺序生成无需遵循程序执行顺序.先生成return再生成变量定义完全可行,只要模型读取双向状态.将从左到右相似度作为唯一质量标准会误判有效轨迹. AR-ness描述轨迹偏向,不直接等于正确性.某任务适合先骨架后细节,轨迹与AR不同反而更高效.应以依赖满足和终局测试评价顺序. **骨架优先。** 先确认函数签名、控制结构和关键调用,再填表达式与名称,能逐步缩小空间.骨架预测错会成为高影响锚点.骨架位置需要更严格置信与验证.

训练只用随机揭开未必学会骨架顺序.轨迹监督、结构辅助或调度器可以引入,应与模型本身能力分开消融.

### 训练数据

代码预训练数据含许可证、质量、重复与安全问题.大量派生仓库、镜像和生成文件会让去重困难.近重复不仅造成评测污染,还改变专家对模板的频率估计. **文件级与仓库级去重。** 文件哈希只能去掉完全相同内容,变量改名和格式化后的克隆仍保留.语法树、token指纹与调用图能检测更深重复,成本更高. 评测题可能出现在仓库历史、题解、测试或注释中.只对题面去重不够,需要查语义近邻与解法骨架. **时间切分。** 按发布日期切分可以降低直接泄漏,旧题的后续镜像仍可能进入训练.模型也可能见过同算法的等价实现.时间切分提供较强证据,不是完全无污染证明. 报告训练截止时间、抓取时间与基准发布时间.持续训练模型需更新污染审计.

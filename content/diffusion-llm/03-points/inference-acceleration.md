# 推理加速：近似缓存与并行揭开

开源扩散语言模型慢，常常不是因为「扩散天生慢」，而是两个工程缺口叠在一起。全双向注意力让 KV Cache 的前提不成立：邻居一揭开，所有位置的 Key/Value 都可能变。一步同时提交很多位置时，这些位置在提交前互相看不见对方的最终取值，质量掉。Mercury Mini 在独立评测里到过单卡 H100 上 1109 tokens/s，Gemini Diffusion 官方表写 1479 tok/s，说明并行这条路能走通。开源 LLaDA / Dream 要对齐的是这两条缺口，不是再发明一种 $Q_t$。

本篇默认已经读过采样专文里的低置信 remask，以及块扩散专文里「块间真缓存、块内仍要反复算」。这里把 2025 年中以后几条能指回表格的加速路线放在同一张地图上。

## 1. 为什么 AR 的 KV Cache 抄不过来

自回归里位置 $i$ 的 $K_i,V_i$ 对所有 $j>i$ 永远合法，因为 $j$ 看不见比自己更右的东西，$i$ 的表示也不会因为 $j$ 的出现而改写。缓存是精确的，不是近似。掩码扩散每一步都在改「哪些位置已经是明文」。明文集合一变，双向注意力里每个 Query 看到的上下文都变，$K,V$ 跟着变。把上一步的缓存原样接到下一步，等于用过期的邻居表示去算当前的 Softmax。

有三条程度不同的回应。

块扩散把块间改成因果。已经完成的块不再被后面的去噪改写，块间 KV 是真缓存。块内仍是双向，块内缓存仍是近似。BD3-LM、LLaDA 2.0 的部署设定、Fast-dLLM v2 走这条结构。

训练免费的近似缓存：承认 $K,V$ 会变，但相邻去噪步之间余弦相似度很高，短时间内复用误差可忍。Fast-dLLM 的 PrefixCache / DualCache、dKV-Cache 的延迟写入属于这一类。

训练侧让边际更快变尖，同样步数里可提交的位置变多，等效减少前向次数。dParallel 的 certainty-forcing、LLaDA 2.0 的 CAP 属于这一类。它不修复 KV，它减少「需要跑多少次带注意力的前向」。

三条可以叠。报倍数时必须写清叠了哪几条、对照的是哪条基线、生成长度多少。把 27.6× 和 Mercury 的 1109 tok/s 写在同一格里，读者会以为开源模型已经到四位数吞吐。前者是相对「原版逐步揭开的 LLaDA」的加速比，后者是绝对吞吐，硬件还不是同一块卡。

## 2. Fast-dLLM：块内复用 + 阈值揭开

Fast-dLLM（Wu 等人，arXiv:2505.22618）是训练免费方法，骨架仍是 LLaDA / Dream 的权重。它做两件事。

第一件是块级近似 KV。生成按块进行。进入一块之前，把提示和已经完成的块的 KV 算好存住；块还没轮到的后缀此时全是 `[MASK]`，它们的 KV 也可以先算一份。块内多步去噪都读这份缓存，不每步重算整段。一块完成后再刷新。只缓存前缀叫 PrefixCache；前缀和仍是掩码的后缀都缓存叫 DualCache。论文 Figure 3 用相邻步的余弦相似度接近 1 来为近似辩护：块内表示漂移不大， suff 上几乎全掩码，漂移更小。

![](./images/fig-fastdllm-dualcache.png)

> 图 1：提示写入 Prefix KV 后，当前块去噪时同时复用前缀缓存和仍为 `[MASK]` 的后缀缓存；块提交后再刷新。

**图 1 解析**

- **Prompt → Prefix KV**：提示在整次生成里不再改，这部分接近 AR 的 prompt cache，误差最小。
- **Suffix [MASK] → Suffix KV**：后缀还没揭开，表示几乎是「一排掩码位」的函数，步间变化小，所以 DualCache 敢存。
- **虚线 reuse**：块内多步读旧 KV，省掉的是对提示和后缀的注意力计算，不是对当前块内部的计算。
- **Refresh after block**：一块变明文之后，后缀和后续块看到的上下文变了，必须重算。不刷新就会把过期明文写进以后所有步。
- **图里没有画置信度阈值**。缓存解决的是「每步算多少」，阈值解决的是「每步提交几个位置」。两件事正交。

第二件是置信度并行解码。每步看每个仍掩位置的最大 Softmax 概率，超过阈值（主文默认 0.9）的一起揭开；一个都不过阈值时，至少揭开当前最尖的那个，避免死循环。这和 LLaDA 附录里「低置信 remask」是同一直觉的另一面：LLaDA 先预测再按比例盖回去，Fast-dLLM 先设阈值再决定揭几个。阈值高则每步少揭、质量稳、tokens per forward 低。

主设定：PrefixCache、块长 32、阈值 0.9，单卡 A100 80GB、batch size 1、不用额外推理框架。Table 1 在 LLaDA-Instruct 上，GSM8K 5-shot、生成长度 256：原版 79.3 分、6.7 tok/s；缓存加并行之后 78.5 分、54.4 tok/s，约 8.1×。生成长度 512 时，原版 77.5 / 3.2 tok/s，组合后 77.2 / 35.3 tok/s，约 11.0×。HumanEval 0-shot、长度 256：41.5 / 30.5 tok/s 到 43.3 / 114.1 tok/s，约 3.7×，分数还略升。代码任务原版就已经一步揭得比较多，加速比被分子垫高了。

27.6× 出现在更极端的对照：8-shot 长前缀、生成长度 1024、DualCache 加并行，相对原版 LLaDA。长前缀让「每步重算提示」的浪费变大，缓存的相对收益变大。这不是产品里随手能开的默认档，是论文用来说明缩放方向的那一格。Dream-Base 上同样方法，GSM8K 5-shot 长度 512 大约 5.6×，MBPP 长度 512 大约 7.8×，加速比低于 LLaDA 那组，因为 Dream 原版已经更快一些。

单独开缓存，论文写的是大约 2×–3.6×；单独开并行大约 4×–6×；两件叠上才到两位数。消融里把阈值换成固定每步揭 2/4/8 个，同样平均 TPF 下阈值策略分数更高。根因仍是采样文写过的因子分解误差：固定 $k$ 会强迫揭开还很平的位置。

用五个掩码位把阈值走一遍。设当前块里置信度是 $0.97,0.91,0.88,0.55,0.33$，阈值 0.9。本步提交 0.97 和 0.91 两个位置，其余继续掩。下一步这两个明文进了双向窗口，0.88 很可能被抬过阈值。若改成固定每步揭 4 个，0.55 和 0.33 也会本步落盘，后面想改只能靠 remask。Fast-dLLM 主实验的并行解码默认揭开就不回头，所以阈值宁高勿低。一个都不过 0.9 时算法仍揭最尖的那个：否则全句置信都在 0.89，生成会停住。这是实现细节，不是理论最优，但避免了死循环。

块长 32 是缓存粒度和近似误差的折中。块太小，刷新太勤，缓存摊销不足；块太大，块内步数变多，KV 漂移积累，分数开始掉。论文 Figure 4 扫过 4 到 32。主文取 32，不是因为 32 有公式，是扫完之后的工作点。把它写进自己的推理配置里，应当再扫一遍目标模型和长度，不要当物理常数。

## 3. dKV-Cache：延迟写入

dKV-Cache（Ma 等人，arXiv:2505.15781，NeurIPS 2025）观察的是另一件事：不同位置的 $K,V$ 在去噪轨迹上的漂移速度不一样。刚揭开的位置表示还在动，已经稳定多步的位置可以缓存。于是它不「块一开始就冻住邻居」，而是延迟：一个 token 解码之后隔若干步再写入缓存，刷新间隔是超参。

两个变体。dKV-Cache-Decode 刷新更勤（LLaDA 主实验里间隔 8），接近无损，长序列上偶尔比原版还高一点，作者解释为原版推理没有把已有上下文用满。dKV-Cache-Greedy 刷新更狠（间隔 2）并加窗口，吞吐更高，分数掉一截。论文摘要写 2–10×，这个区间已经把 Dream 上长前缀的 Prefill 缓存算进去了。Table 里更具体的一格：Dream-7B、GPQA 5-shot，dKV-Cache-Prefill 报到过约 10.19×，那是提示很长、生成步数相对少、几乎全是在省重复编码。LLaDA 侧测速在 A6000，Dream 侧在 H20，和 Fast-dLLM 的 A100 不能横比绝对 tok/s。

和 Fast-dLLM 的差别不在口号，在冻哪一段。Fast-dLLM 按块冻前缀和掩码后缀；dKV-Cache 按时间冻「已经够老的位置」。块扩散结构里两者可以同时存在：块间真缓存，块内再套延迟近似。Fast-dLLM v2 把 AR 改编成块扩散之后做分层缓存，走的就是叠法。v2 自称约 1B token 微调、相对 Qwen2.5-7B-Instruct 吞吐 2.54×。那 2.54× 的对照物是 AR 基线，不是原版 LLaDA，和 27.6× 不是一张表。

Dream 改编自 AR，输出位置相对掩码扩散有一格移位（预测的是「下一个」而不是「当前格」）。dKV-Cache 附录比较了 Un-Shift、Right-Shift、Un&Right-Shift。Right-Shift 会把 GSM8K 从 76 档打到 32.68；主实验因此用 Un-Shift，尽管 Un&Right-Shift 在个别任务上略高，但和他们的 concat_reorder 实现不兼容。抄缓存代码时连移位一起抄，只抄间隔超参会在 Dream 上静默掉点。

延迟的直觉可以用「刚揭开的字还在抖」来记。去噪轨迹上，一个位置从 `[MASK]` 变成明文的那几步，$K,V$ 跳得最厉害；再过几步，邻居也慢慢定下来，这个位置的表示进入平台。立刻缓存等于把抖的那一段冻进以后所有注意力。等 $k$ 步再写，用的是平台上的值。$k$ 太大，平台已经过时，因为更后面又揭开了新字。Decode 取 8、Greedy 取 2，是在「冻太早」和「几乎不冻」之间的两个工作点，不是推导出来的最优间隔。

## 4. 从训练侧减少步数：CAP 与阈值

缓存解决的是一步里重复计算。另一些工作让每一步可以安全地多提交，于是总步数下降。LLaDA 2.0 的 CAP（Confidence-Aware Parallel）在已经预测对的位置上再压熵，提高 tokens per forward。作者在 dInfer 上的对照：flash 的 CAP 版 535 TPS，SGLang 上的 AR 对照 256 / 237 TPS，大约 2.1×。这是 100B MoE 对同文内 AR 的吞吐，不是 8B 对 LLaMA3 的吞吐。阈值 0.95、块长 32 是 2.0 mini 主评测扫出来的设定，和 Fast-dLLM 默认 0.9 是同一旋钮的不同刻度。

dParallel 一类蒸馏让学生在少步数下边际更快变尖，属于训练成本换推理步数。未把其主表数字抄进本篇：需要单独打开论文核对协议。能确定的机制是：尖的边际让阈值策略每步多揭，而不必把阈值降低到会引入搭配错误的区域。

CAP 比把阈值从 0.9 调到 0.8 干净。调低阈值是在已经平的分布上硬揭，错配上升。CAP 在训练时对已经对的位置继续压熵，让对的位置更尖、错的位置相对更平，阈值保持高也能提高每步提交数。它改权重，不改采样器超参。代价是要有一份「这些位置已经对了」的信号，通常来自教师或多步自洽。2.0 把这件事做成可部署选项，535 TPS 那一格默认 CAP 已打开。关 CAP 只开块扩散，吞吐会回到更接近文内 AR 的那一档。不要把 2.1× 记成「换了 MoE 就免费快一倍」。

商业模型很少公开缓存实现。Mercury Coder Mini 1109 tok/s @ H100、Gemini Diffusion 1479 tok/s 且 overhead 0.84s、Seed 2146 token/s @ H20（作者声明不可与前两者横比）。这些数字说明「粗到细并行」在系统层可以做到四位数。开源论文的加速比回答的是另一问：现有权重不重新训，能从「慢得没法用」救回多少。两问不要合成「扩散已经比 AR 快十倍」。

## 5. 并行揭开的质量墙

即使 KV 分文不差，一步揭两个位置仍然在用

$$
p_\theta(x^i,x^j\mid x_t)\approx p_\theta(x^i\mid x_t)\,p_\theta(x^j\mid x_t)
$$

当前 $x_t$ 里两者都是 `[MASK]` 时，右边没有「$i$ 取成左括号之后 $j$ 必须是右括号」这种联合。阈值、EB-Sampler 的联合熵上界、允许下一步 remask，都是在修这个近似。阈值 0.9 在 Fast-dLLM 的 GSM8K 上几乎不掉点，并不保证代码里括号匹配也一样稳；HumanEval 那格分数没掉，不能外推到更长的仓库级补全。

步数减半是更粗的加速：把 $T$ 除以 2，等价于每步多揭一倍。dKV-Cache 的消融拿它当弱基线，分数掉得比延迟缓存狠。原因是它不看置信度，平的位置也被提交。加速论文里如果只报速度、不报同表准确率，那张表不能用。

和采样专文的分工：那篇写揭开、remask、三种解码器；本篇写怎样少算注意力。低置信 remask 允许把已经揭开的字盖回去，Fast-dLLM 主设定默认不回头。允许回头时，阈值可以略低，因为错了还有下一轮；不允许回头时，0.9 这种高阈值是在用「少揭」换「少锁死」。把两种采样器的分数画在同一根速度曲线上，会得到虚假的帕累托前沿。

## 6. 失效与读表

batch size 大于 1 时，有的实现加速比会收窄，dKV-Cache 附录写过单卡 H20 上 batch 的影响。论文主表几乎都是 batch 1，和线上为吞吐把 batch 拉大的 AR 服务不是同一场景。

生成长度很短时，缓存摊销不足，加速比接近 1。27.6× 依赖 1024 这种长画布。产品若平均只写两句话，应看长度 256 那一列的 8.1×，再看绝对 tok/s 是否已经高于自己的 AR 栈。

近似缓存在「一步改很多已经提交的位置」时会坏。Seed 那种持续可编辑的噪声，和 DualCache「后缀一直是掩码所以 KV 稳」的假设冲突。编辑型扩散要另做缓存，不能把 Fast-dLLM 的表贴过去。

对照物必须写全：模型、shot 数、生成长度、是否 DualCache、阈值、GPU、是否相对原版扩散还是相对 AR。缺一项，倍数没有意义。

读开源加速论文还有一个常见误读：把「相对 vanilla LLaDA 的 11×」读成「已经比 vLLM 里的 Qwen 快 11×」。vanilla LLaDA 的实现往往逐步揭开、不用编译器、batch 1，起点特别慢，所以倍数好看。要回答产品问题，应当拿同一套硬件、同一套服务框架、同一批请求长度，去比 tok/s 和延迟分位数。本花园能引用的、满足「独立评测或作者写明硬件」的绝对吞吐，仍然只有 Mercury / Gemini Diffusion / Seed / LLaDA 2.0-CAP 那几格。Fast-dLLM Table 1 的 54.4 tok/s（GSM8K、长度 256、A100）距离 1109 还差一个数量级。差距来自模型是否为吞吐训过、是否 MoE、是否允许更粗的并行，不只来自有没有 DualCache。

内存不是免费的。DualCache 要存前缀 KV 和整段仍为掩码的后缀 KV。生成长度 1024、层数 32、头数 32 时，这份缓存和 AR 生成到同样长度时的 KV 是同量级，外加块内还要保留当前块的激活。dKV-Cache 写过 Decode 与 Greedy 在不同预填、解码长度下大约 1.75×–3.3× 的加速，内存只多一截。加速论文如果只给 tok/s、不给峰值显存，部署时仍可能在 80GB 卡上被激活值打满。batch 1 的主表尤其爱藏这个问题。

算法层面 Fast-dLLM 的伪代码是两层循环：外层扫块，内层在一块里反复「读缓存 → 算置信 → 揭过阈值的位置」。一块尚未揭完就继续内层；揭完才 refresh。实现上 refresh 可以和最后一次前向融合，所以「多一次更新」不必多一次完整前向。看代码时若发现每步都把整段 KV 重写，那已经不是论文里的 DualCache，加速比会塌回 1。

粗算一遍前向次数，能避免被倍数吓到。设回答长度 $L=256$，原版 LLaDA 一步揭一个，大约 256 次整段注意力。阈值策略若平均每步揭 8 个，前向大约 32 次，再乘上「提示 KV 不再重算」的常数因子，总 FLOPs 可以掉一个数量级，11× 那种格才变得可理解。若平均每步只能揭 1.2 个（阈值太高或题目很难），加速比会回到缓存单独贡献的 2×–3×。所以 27.6× 依赖「长画布 + 长提示 + 模型在多数位置很尖」三件同时成立。数学竞赛逐步推导往往不尖，代码补全局部很尖，同一方法在 HumanEval 和 GSM8K 上加速比可以差一倍，Table 1 已经把这件事写在明面上。读加速表时先看任务列，再看倍数列。绝对 tok/s 仍以 Mercury / Gemini / Seed / 2.0-CAP 那几格为准，不要把相对原版 Python 循环的倍数抄进产品页。开源仓库默认逐步揭开，是为了让质量上限可见，不是为了当吞吐基线。用它当分母，任何缓存看起来都像银弹。和采样专文、块扩散专文对着读：本篇不重推 remask 公式，不重推 $B=1$ 的损失方差。加速是采样器和块结构的工程层，公式层仍在那两篇。把本篇当速查手册：要倍数先对表，要原理先对那两篇。表在 Fast-dLLM Table 1–4 与 dKV-Cache Table 1–3，抄之前核 GPU 型号。

# LaCT 大块测试时训练

《Test-Time Training Done Right》指出，许多早期 TTT 实现每 16 或 64 个 token 更新 fast weights，小在线批次在现代 GPU 上的 FLOPs 利用率很低；细粒度的一维块因果结构也不自然适用于集合、图像或视频网格。

> **版本与证据边界**：本文按 arXiv:2505.23884v1（2025-05-29）记录，仍是预印本。2K–1M token、40% 状态占比、14B 视频扩散与 56K 序列是论文作者在不同任务和模态中的实验范围，不能拼成同一语言模型配置。

## 核心变化

Large Chunk Test-Time Training（LaCT）反向扩大在线更新块。论文在不同任务和模态中使用 2K 到 1M token 的 chunk，并报告：

- 硬件利用率相对小 chunk 提升多个数量级。
- 能把非线性状态扩大到模型参数量的 40%。
- 无需为每个变体手写复杂 kernel，也更容易接入 Muon 等优化器。

这些数字来自论文特定实验，引用时必须保留任务、模型、硬件和实现上下文。

## 大 chunk 改变了什么

### 计算

大矩阵运算更适合 GPU，但一次更新覆盖更长区域。吞吐提高不等于单请求首 token 延迟一定降低，应分别报告训练吞吐、prefill、decode 和更新延迟。

### 因果结构

小 chunk 强制细粒度顺序依赖；大 chunk 更容易覆盖集合或高维网格。具体实现仍需说明 chunk 内哪些 token 可共同参与状态更新，避免未来信息进入当前预测。

### 状态容量

更大状态能记录更多模式，但也增加参数更新、优化器状态、显存和稳定性成本。状态占模型参数的比例不是等价于“记住同等比例上下文”。

## 论文验证范围

作者在新视角合成、语言模型和自回归视频扩散上验证 LaCT；摘要报告其扩展到 14B 参数视频扩散模型、最长 56K token 序列，并在新视角合成实验中使用 1M 上下文。它证明方法跨模态可运行，不等于所有任务都已达到同等质量优势。

## 复现检查表

- chunk 大小、更新次数与 chunk 内因果掩码。
- fast weights 占比、优化器及其状态内存。
- 训练 / 推理硬件、精度和 kernel 实现。
- 与小 chunk、无 TTT、全注意力或其他状态模型的同预算基线。
- 吞吐、延迟、显存和任务质量分别报告。
- 测试序列之间是否重置 fast weights。

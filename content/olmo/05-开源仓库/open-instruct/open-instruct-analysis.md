# Open Instruct 技术解析：从数据契约到 SFT、DPO 与在线 RLVR

Open Instruct 提交 `11826255077617a46919ce75cadf1f3d53f30dac` 的训练实现分布在 `open_instruct/dataset_transformation.py`,`data_loader.py`,SFT/DPO/RM 与 `grpo_fast.py`,配方和运行入口位于 `scripts/train/olmo3/`,`configs/`,`docs/olmo3.md` 及污染检查代码.仓库将自身定位为研究代码且不保证向后兼容,文中的接口描述因此对应这一提交.

![Open Instruct 从统一数据契约到 SFT,偏好学习和在线 RLVR 的训练图](images/open-instruct-training-flow.svg)
> 图 1:统一数据转换把消息,偏好对和可验证任务送入不同阶段;SFT 产生策略起点,DPO 或奖励模型使用偏好数据,在线 RLVR 则把策略采样,验证奖励与参数更新连成反馈循环.

图 1 中三条训练路线共享稳定的数据语义和模型接口,各自采用不同的损失.SFT 需要明确哪些 assistant token 参与交叉熵;DPO 要保证 chosen 与 rejected 共用同一 prompt,并依赖参考策略定义相对变化;RLVR 每轮都由当前策略生成 rollout,再由验证器给出奖励,因此采样服务,训练集群和版本标识必须同步.箭头没有表示 SFT,DPO,RLVR 必须全部执行,也没有表示后一阶段必然优于前一阶段;具体组合取决于目标行为,数据覆盖和计算预算.

## 1. 数据契约与 SFT

Open Instruct 把后训练拆成可以复用的程序, 但各阶段能否接起来, 取决于数据字段是否始终表达同一件事. Prompt,assistant response,来源,模板和损失 mask 一旦在转换中漂移, SFT,偏好优化和 RL 学到的任务就会发生变化.

SFT 是这条链路的第一个检查点. 监督落在哪些 token,长样本怎样截断,不同来源如何 packing, 都会改变实际梯度与样本权重. 数据条数或 epoch 无法单独描述这些差异, 有效监督 token 才是更接近训练作用的口径.

### 1.1. 多阶段共用的数据语义

Open Instruct 同时覆盖 SFT,奖励模型,DPO 和 RLVR.四类目标都依赖同一层数据语义:消息角色怎样排列,system prompt 是否注入,assistant 哪些 token 参与损失,chosen/rejected 是否共享完全相同的 prompt,RL prompt 如何携带可验证答案与环境信息.`dataset_transformation.py` 集中处理 chat template,特殊 token,截断,缓存版本,标签和数据来源,职责远多于简单的字段映射. 源码注释直接列出三种主要目标:prompt-only,SFT 的 prompt+demonstration,RM/DPO 的 chosen+rejected.统一转换层的价值是让训练器消费明确张量,而不是各自在循环中猜测原始 schema.它也降低阶段间漂移:同一条 conversation 若在 SFT 与 DPO 中用不同模板渲染,偏好优化实际上是在另一个 token 分布上继续训练.

`TokenizerConfig` 和一组默认键定义字段契约.SFT 最终需要 `input_ids`,`attention_mask`,`labels`;assistant 以外的位置通常置为忽略标签.代码为转换缓存维护版本号,注释记录版本变化,例如工具列支持,generation 区间标签等.这个细节非常关键:Hugging Face datasets 的缓存可能让「代码已更新」但训练仍读旧 token 化结果.显式提升缓存版本,是把数据处理逻辑纳入可复现状态. OLMo 3 文档暴露了真实教训:开头 `<think>` 曾因 prefix-based labeling 被误当 prompt 掩蔽.较新的 `{% generation %}` 区间能直接标注 assistant 生成范围,但块的起止,结束 token 和工具调用交接必须精确.只比较 labels 数量不足以证明归属正确;渲染文本相同也不证明 mask 相同.仓库宁可记录并丢弃所有权含糊的行,说明 silent corruption 比少量数据损失更危险.

**数据契约决定各阶段是否在学习同一个任务.** 一条对话在原始 JSON 中只是角色与文本的列表.真正进入模型后,它会被 chat template 渲染成特殊 token,角色 header,换行与结束符.SFT 的 prompt,DPO 的共同前缀和 RL 的 rollout 起点若采用不同渲染,三个阶段表面使用同一数据,条件分布已经不同. 契约至少要固定角色集合,工具调用表示,system 注入规则,assistant generation span,文档结束与轮次结束 token.转换器应拒绝未知角色和不成对的工具返回,避免悄悄转成普通字符串.严格失败比默认猜测安全,因为错误模板会在数十亿 token 中稳定重复.

还要区分语义版本与实现版本.代码重构若输出 token 完全一致,无需让缓存失效;模板加一个换行,改变 generation span 或截断方向,即使函数名不变也属于语义升级.用少量金样本保存渲染 token 与 label mask,能直接比较版本差异.

数据混合权重应按有效监督 token 理解. 混合配置常写各数据源样本比例,训练梯度却由参与 loss 的 token 构成.长对话含大量用户上下文,若只训练 assistant span,有效监督 token 可能并不多;短问答的回复占比反而高.经过截断,过滤和 packing 后,原始比例还会再次变化. 对来源 $k$,可记录原始样本数,成功转换数,输入 token,label token 与实际采样次数.近似梯度权重更接近 label token 占比,而资源成本接近总输入 token 占比.两者分开,才能解释某来源「很贵但监督少」或「样本少却更新强」. 多 epoch 还会对小数据重复采样.若混合采用按源温度采样,名义数据量不再决定权重.最终 manifest 应给每个 optimizer step 实际消费的来源计数,至少提供全程汇总.

数据质量问题会跨阶段传播. SFT 中错误答案提高错误序列概率;DPO 中错标偏好同时推高 chosen,压低 rejected;RL verifier 错误则可被当前 policy 主动发现并反复利用.三个阶段对同一噪声的放大机制不同,在线 RL 风险最高. 数据清洗不能只在入口做一次.SFT 检查格式,正确性和重复;偏好数据检查共同 prompt,标签置信与长度偏差;RL prompt 检查 verifier 可执行,答案唯一性与难度.每阶段输出的模型又改变下一阶段数据分布,需要重新抽样审计. 仓库统一数据层提供字段与转换一致性,不会自动保证内容正确.内容证据来自数据卡,生成流程,过滤统计和人工复核.把 schema 通过误写成数据高质量,是开放训练中常见的归因错误.

数据来源字段是归因接口. 保留 `dataset_origin` 后,可以按来源计算 loss,截断率,零奖励率和下游贡献.若训练突然异常,先看是否由单一数据源格式升级或缓存错配引起.没有来源字段,只能把所有样本当成均匀总体. 来源标签还支持消融与重加权.发现某源在数学有效,在安全退化,可调整比例或分阶段使用.标签必须追溯到具体 revision;同名数据集更新后,旧统计不能直接复用. 来源并不等于独立.多个数据集可能复制相同网页,题库或教师输出.还需内容哈希与近重复簇,避免把同一信息的多次出现解释成多来源共识.

### 1.2. SFT 的损失掩码,截断与 packing

SFT 的基本目标是对 demonstration 中 assistant token 做交叉熵.用户,system,工具返回与格式 header 通常作为条件但不计损失.若 labels 边界错一位,模型可能被训练去生成用户提示,忽略 `<think>`,或学不到正确结束行为.Open Instruct 因而要求 fast tokenizer,并围绕 chat template 渲染与 assistant span 建立检查. 长样本策略同样改变目标.截断可能切掉回答尾部或结束 token;左截断保留末端,却可能丢失 system prompt 和问题前提.文档区分 `drop` 与 `terminate` 等行为,后者保存完整尾部但不应把已有工具交接 token 粗暴替换成 EOS.对工具使用模型而言,`<|im_end|>` 表示把控制权交还环境,普通 EOS 表示对话结束,二者混淆会直接破坏 agent 行为.

训练脚本仍有两条路径.README 对支持的 OLMo,OLMoE,Qwen3 推荐 GPU 效率更高的 OLMo-core SFT,传统脚本则基于 Hugging Face Trainer 改造.这样做是工程折中,不代表两个后端天然逐位等价.它们可能在数据打包,梯度累积,loss reduction,FSDP state dict 和 scheduler 边界上不同.阶段交接必须用实际 checkpoint 和 tokenizer 验证,不能只凭相同模型名. 配置脚本提供真实配方入口.`scripts/train/olmo3/` 分开 7B/32B,instruct/think,SFT/DPO/RL.脚本不是教程命令的简单展开:它通常还固定数据集 revision,模型与 tokenizer,batch,长度,学习率,分布式启动和输出路径.复现者应保存脚本 commit 与最终命令,因为环境变量和启动包装仍可覆盖脚本默认值.

**SFT 目标的分母会改变梯度尺度.** 交叉熵可以按所有非忽略 token 平均,也可先按样本平均再对 batch 平均.前者让长回复权重大,后者让短回复相对上升.packing 后一个序列含多条样本,若只按序列平均,打包方式也会进入权重. 分布式训练还要确认 reduction.各 GPU 有效 label token 不同时,先在卡内平均再对卡平均,会让短 batch 与长 batch 等权;先求 loss 和 token 数再全局相除,才是全 token 平均.相同 global batch size 不能保证相同目标. 报告应写有效监督 token,loss reduction 和梯度累积,而非只列样本 batch.不同后端比较时,这些细节比命令行名称更关键.

截断是内容选择策略. 超过最大长度时,从右侧截断可能删除最终答案和结束符,从左侧截断可能删除问题与 system 约束.直接 drop 保持语义完整,却改变长度分布;terminate 在边界补结束行为,也可能把工具交接误写成会话终止. 可按数据类型制定策略.单轮问答优先保留问题与完整回复;多轮对话可按轮次切块并重复必要 system;工具轨迹必须保持 call-response 成对.所有策略都应统计丢弃 token 与样本比例. 长样本质量也需单独验证.提高上下文上限让更多文本进入 loss,不保证其中远距离依赖正确.对长对话测约束保持和跨轮引用,比只看训练 token 数更能说明收益.

packing 不能跨越语义边界泄漏. 将多个短样本拼入固定长度序列能提高利用率.attention 若未按边界隔离,后一个样本可能看到前一个回答,形成训练时存在,推理时不存在的上下文.即使有 EOS,模型仍能注意前文,只是学习到软分隔. 某些实现接受这种文档拼接,另一些使用 block-diagonal attention.两者目标不同.复现要写清 position id 是否重置,loss mask 是否正确,跨样本 attention 是否允许.OLMo-core 与 Trainer 后端可能采用不同 packing,需要实测对齐. 金样本测试可把两条内容明显不同的对话打包,检查 attention mask,position id 和 labels.只比较最终 loss 很难发现泄漏,因为模型仍会正常收敛.

SFT checkpoint 是后续阶段的参考坐标. DPO 的 reference 通常来自 SFT,RL 的初始 policy 也来自它.SFT 配方改变,后续的概率比,探索分布和可验证成功率都会变化.同一 DPO 或 RL 配置不能脱离起点比较. 保存 SFT 最终权重之外,还应保留中间 checkpoint 和验证轨迹.后续阶段若退化,可以判断问题从 SFT 已存在,还是偏好/RL 引入.不同 SFT checkpoint 作为参考的交叉实验能测阶段依赖. 强 SFT 起点可能让 RL 成功率高却组内零方差多;弱起点提供探索差异,却大量全错.起点选择本身是在线算法超参.

## 2. 偏好优化与在线 RLVR

DPO,奖励模型和 RLVR 都使用「更好回答」这一信号, 计算接口却不同. DPO 比较 policy 相对 reference 的对数概率变化, 奖励模型拟合一个评分函数, RLVR 则让当前策略生成样本并由 verifier 返回奖励.

接口差异会改变数据分布和故障模式. 离线偏好数据由旧策略产生, 在线 rollout 会随模型更新而变化; verifier 的解析错误,奖励聚合和零方差组过滤, 都会直接改变训练目标. 只有把生成,验证与更新放在同一条链路上观察, loss 曲线才有明确含义.

### 2.1. DPO,reference 与奖励接口

DPO 数据含 chosen 和 rejected.转换层必须从二者提取共同 prompt,再分别渲染回答;如果 prompt 不同,chosen/rejected 的 log-prob 差就混入上下文差异,目标不再是同一条件下的偏好.长度处理也必须对称:只截断一边可能凭长度制造偏好信号.源码将 RM/DPO 转换放在统一模块中,正是为了集中约束这些不变量. DPO 的核心是比较策略相对参考模型对两种回答的偏好差异.beta 控制偏离参考策略的强度.工程上需要同时获得 policy 与 reference 的 log-prob,显存压力显著高于普通 SFT;可以冻结参考模型,预计算参考 log-prob 或通过分片降低驻留成本,但不同实现的数值与吞吐不可直接类比.训练脚本中的 batch,梯度累积与序列长度决定实际 token 预算.

奖励模型把 chosen/rejected 映射为标量并优化排序.README 的模型表显示 Tulu 系列发布 RM,同时 RLVR 又可使用可验证奖励.二者不应混为一谈:RM 是学习到的偏好近似,可能继承标注偏差;verifier 对数学答案,代码测试或格式规则给出程序化信号,范围更窄但可审计.混合奖励时必须记录每项权重和聚合方式,否则同名「reward」无法复现.

**DPO 的相对目标依赖 reference 一致性.** DPO 比较 policy 与 reference 对 chosen/rejected 的 log-ratio.reference checkpoint,tokenizer,模板和截断必须一致.若 reference 用旧模板,序列概率对应不同 token,概率比失去清晰含义. 预计算 reference log-prob 可节省显存,但缓存键必须包含模型 revision,模板和最大长度.数据重新截断后继续使用旧 log-prob,会形成静默错误.在线计算更稳妥,成本更高. reference 也定义约束中心.换成更强或更弱 SFT,即使偏好对相同,DPO 更新含义不同.模型卡应绑定 reference 哈希,而非只写 beta.

偏好对的共同 prompt 需要结构比较. 简单取 chosen/rejected 字符串最长公共前缀不可靠.模板空格,system 差异或多轮分支可能让公共部分截错.应在 message 结构层确认直到最后 assistant 前的角色与内容完全相同,再分别附加回复. 如果两边历史不同,标签同时评价上下文和回答,DPO 无法归因.长度截断也要以共同 prompt 为单位:先保留相同上下文预算,再对两条回复采用一致规则.只截长的一边会产生长度捷径. 工具调用偏好更复杂.chosen 与 rejected 可能调用不同工具,随后环境返回也不同.比较对象是单步调用还是完整轨迹必须明示;把不同环境结果塞进回复会混入不可控因素.

DPO 训练曲线至少要拆成四条. 总 loss 下降只说明偏好分类变好.还应记录 chosen reward,rejected reward,margin 与隐含 KL.chosen 概率可能下降,只要 rejected 降得更多,margin 仍上升;这种模型未必更会生成 chosen 风格. 长度分桶和来源分桶能发现捷径.若长 chosen 的 margin 快速扩大,等长样本不变,模型可能学长度.若单一数据源主导,混合权重需要调整.验证集必须按 prompt 去重,防止同题改写泄漏. beta 与学习率共同决定偏移.只比较 beta 而不报告实际 KL,序列长度和训练步,无法跨配方解释.

奖励模型和 DPO 服务于不同接口. RM 学 $r(x,y)$,可给任意候选打分,支持 BoN 或 PPO;DPO 直接更新策略,不产生独立可复用 judge.两者都消费偏好对,却输出不同资产.把 DPO 称为「不需要奖励」的简化,会忽略其偏好数据仍定义隐含奖励. RM 的绝对尺度未固定,进入 PPO 前要校准分布与异常值.DPO 通过 reference 概率比内置锚点,仍可能因标签偏差改变风格.选择取决于是否需要在线采样,独立评分器和动态优化. Open Instruct 同时保留两条路径,使同一数据能比较算法.但严格对照要统一基座,模板,token 预算与评测,不能只比发布模型名字.

### 2.2. 生成,验证与训练反馈

该提交的 RL 主入口是 `open_instruct/grpo_fast.py`.`data_loader.py` 不只是离线 batch loader,它包含 vLLM 配置,流式数据准备,rollout 结果组合,奖励统计和优势计算.每个 prompt 生成多条 response,配置项 `num_samples_per_prompt_rollout` 控制组大小;若设为 1,代码警告 GRPO 退化为 REINFORCE.因为组内只有一个样本时标准差恒为零,源码禁止同时开启零方差样本过滤. 组相对优势在代码中按 prompt reshape reward,计算组均值和标准差,再选择标准化 `(r-mean)/(std+1e-8)` 或只中心化.这样无需单独价值网络,但高度依赖组内多样性.采样温度过低或 verifier 过粗会让整组奖励相同;过滤零方差组可避免无信息梯度,却会改变有效 prompt 分布.训练日志因此既要看平均 reward,也要看被过滤组比例与实际 response 数.

rollout 通常由 vLLM 侧生成,训练侧更新 PyTorch policy.异步可重叠生成和训练,提高设备利用率,却产生 off-policy 陈旧性.代码记录生成所用 model step 的最小,最大,均值和 `num_steps_off_policy`,并能丢弃落后训练太多的结果.这不是纯性能细节:允许多陈旧决定优化目标相对当前 policy 的偏移,必须作为算法超参数记录. 数据类型为每个样本保留 `rollout_states`,其中含 reward,step_count,done 和 info;多轮或工具环境可把每轮状态带回.`reward_aggregator` 支持 `last` 或 `sum`,即取最后一轮或累加全部轮次奖励.两者代表不同任务定义:last 更强调最终结果,sum 会鼓励中间进展,也可能奖励拖长轨迹.多轮训练报告若不说明聚合器,数字不可比较.

**奖励系统:可验证不等于不会出错.** `StreamingDataLoaderConfig` 明确包含 verifiable reward,R1 风格 format reward,可加格式奖励,代码 pass-rate 阈值和 evolving rubric reward.初始化校验要求至少启用一种奖励,并据启用项计算最大可能分数.把奖励拆成指标而非只返回总分,使日志可以发现模型是在提高正确率,还是只学会格式. verifier 仍可能被利用.字符串答案需要归一化;数学等价性需要符号判断;代码测试的覆盖率决定「通过」是否真实;格式奖励可能诱导模型输出模板而非推理.`verification_reward` 默认量级若远大于格式奖励,会让最终正确性主导;若加法权重不当,模型可能用格式分补偿错误答案.任何奖励更新都会改变训练任务,应和数据,模型一样版本化.

代码环境还带来安全与隔离问题.仓库包含 environment 与 sandbox 测试,说明执行生成代码不是普通纯函数.生产复现必须记录镜像,超时,资源限制,网络策略和测试集 revision.相同答案在不同编译器或依赖版本中可能得到不同结果.所谓「可验证」只表示存在程序规则,不表示跨环境自动一致. rollout trace 可写盘,配置要求开启保存时必须给 `rollouts_save_path`,并保存元数据.trace 是审计奖励黑客,终止原因和模板错误的最好材料,但也可能含原始 prompt,模型输出和敏感数据.路径,保留期与访问控制属于复现基础设施的一部分,不能因其是研究日志而忽略.

## 3. 分布式训练与复现边界

在线 RL 同时占用生成集群和训练集群, 二者通过 rollout,权重版本和 tokenizer 连接. 生成侧吞吐,训练侧 batch 与权重同步频率共同决定样本有多陈旧, 因而系统配置也属于算法条件.

复现一条配方不能只保存训练 YAML. 数据 revision,模型与 tokenizer revision,仓库提交,失败恢复位置和阶段间 checkpoint 都要绑定到同一次运行. 随机种子可以固定局部采样, 却无法消除异步顺序和外部环境变化.

### 3.1. 训练集群与推理集群的共同约束

README 的小例子用 8 GPU,RLVR 启动器则通过当前 commit 构建 Beaker 镜像并运行脚本.仓库 `configs/` 同时有 Beaker,DeepSpeed 与训练配置,实际运行会跨越 shell,容器,调度器和 Python.`build_image_and_launch.sh` 试图把源码 commit 固化进镜像,这是好做法,但若依赖下载未锁,基础镜像 tag 可变,commit 仍不足以完全定义环境. RL 的资源核算不同于 SFT.训练 GPU 存 policy,优化器和梯度;rollout GPU 运行 vLLM;奖励可能还需要 judge 模型或 sandbox CPU.只报告训练卡数会掩盖真实算力.异步并发还要求稳定地把新权重同步到推理引擎,日志中的 model step 指标正是验证同步是否跟上的证据. 分布式 batch 有三层:每个 prompt 的采样数,每轮唯一 prompt 数,训练全局 batch.代码检查期望 response 数等于采样数乘全局 prompt 数,但过滤未完成,零方差或陈旧结果后实际数会下降.梯度归一化若仍按名义 batch,和按实际 token 归一化含义不同.复现报告应给出过滤前后计数,有效 token 和 optimizer step,而不是只给 epochs.

SFT/DPO 可用 DeepSpeed 等分片,OLMo-core SFT 又有另一套并行实现.checkpoint 是否可跨后端加载取决于权重命名和保存格式;优化器状态通常更难迁移.阶段链中 SFT 到 DPO 再到 RL 经常只需要模型权重,但 tokenizer,chat template 和特殊 token 表必须一起传递.只上传 `safetensors` 而漏掉 tokenizer 配置,会复现出形式正确,语义错误的输入.

### 3.2. 污染,版本与阶段交接

仓库提供 `decontamination/` 来测训练数据和评测集重叠,这是开放后训练不可缺的步骤.指令数据常从网页,竞赛解答和模型生成混合而来,精确重复只是污染下界;改写,翻译和答案泄漏也可能让评测失真.索引与搜索参数,规范化,n-gram 阈值及评测集版本都应随报告公开. README 明确说内置评测已不维护,建议改用 OLMES.这是一条重要边界:不能看到仓库还有 eval 脚本,就假定它代表当前官方口径.复现 Tulu 3 应固定 OLMES commit,任务配置,prompt,归一化,采样参数和模型 tokenizer.训练仓库与评测仓库分离有利于职责清晰,也增加了跨仓库版本配对要求.

**可复现性:固定提交只是起点.** 该提交提供 `uv.lock`,大体积 requirements,Dockerfile,脚本和测试,优于只发若干命令.但 README 主动声明不保证向后兼容,说明配置名和执行路径会变化.复现应至少保存:源码 commit 与补丁;uv lock 和容器 digest;基础模型与 tokenizer revision;数据集 revision 与转换缓存版本;完整启动脚本和展开参数;分布式拓扑;reward/verifier 版本;每阶段输入输出 checkpoint 校验和. OLMo 3 tokenizer 文档更证明「模型 ID」不是充分条件.7B Think 在阶段交接中出现模板微差,32B 又采用不同身份策略;3.2+ 才形成 dev/eval/release 的清晰分工.`chat_template.jinja` 与 `tokenizer_config.json` 同时存在时,Transformers 优先前者,两份不同步会让人工检查错对象.仓库提供 diff 工具,但执行结果仍应归档.

随机性也跨多个系统:prompt shuffle,vLLM sampling,分布式训练 dropout,环境执行与异步完成顺序.固定一个 seed 不能让异步 RL 逐位复现.更合理的目标是固定数据与版本,记录 rollout 分布和过滤统计,并用多个种子报告统计稳定性.若只能跑单次大实验,则至少保留足够 trace 解释异常跳变. 许可是另一条边界.代码是 Apache 2.0,不代表基础模型,训练数据和输出模型都继承同一许可.README 区分 V1 模型许可,基础模型许可和 V2 的 AI2 ImpACT.将训练脚本用于其他模型时,需要重新核对各资产条款,而不能只引用仓库 LICENSE.

如何审计一条实际配方. 复现最好从某个 `scripts/train/olmo3/*.sh` 开始,README 示例不足以确定完整配置.配方检查需要覆盖基础模型,tokenizer,数据,最大长度,batch 和输出,并追到 Python 入口的参数类与 `dataset_transformation.py` 的渲染,标注和截断逻辑.DPO 还要确认共同 prompt 与 reference,RL 则要确认采样数,奖励组成,优势归一化,陈旧阈值和过滤;启动器构建的镜像与资源拓扑同样属于运行条件. 运行前做三类小测试最划算.抽取真实样本可视化 token 与 labels,确认 system/user 被 mask,assistant 和结束 token 被学习;对同一 prompt 手算 verifier 与聚合 reward,检查总分和指标;再以极小模型跑 checkpoint 恢复和权重同步,观察 model step 陈旧性.它们无法替代大规模训练,却能提前发现最昂贵的语义错误.

Open Instruct 公开了各阶段的连接方式:统一数据转换把消息变成可训练张量,SFT/DPO/RM 提供离线学习,vLLM rollout 与 verifier 构成在线 RL 反馈循环,脚本和容器把它们映射到集群.仓库仍保留了一些研究系统常见的粗糙边界,因此复现实验需要同时固定 tokenizer,数据,奖励,异步策略和环境,单独保存启动命令无法覆盖这些状态.

数据转换中的缓存,来源与可观测性. 数据转换的另一个工程重点是避免在大规模作业启动后才发现坏样本.405B 级别 SFT 若让数十节点等待单进程临时分词,成本极高,因此转换结果通常需要预计算或缓存.缓存键必须包含 tokenizer revision,chat template,最大长度,截断策略和转换代码版本;只按数据集名称缓存会在模板更新后静默复用旧结果.仓库用转换版本号主动失效旧缓存,是务实做法,但实验记录还应保存最终缓存指纹和每个源的行数. `dataset_origin` 等来源字段让混合数据在训练后仍可分解统计.它既可检查某个源是否因超长或模板错误被大量丢弃,也可定位 loss 峰值来自哪个数据源.混合权重描述的是抽样前意图,实际经过过滤,截断和 packing 后的 token 占比才是模型看到的分布.完整报告应同时列出原始样本数,成功转换数,丢弃原因,训练 token 数和有效来源占比.

工具调用数据尤其需要结构验证.messages 中的 tool schema,assistant tool call 与 tool response 必须能配对,序列化格式要与发布 tokenizer 一致.如果转换只把对象转成字符串而不验证调用 ID 和轮次关系,模型会学到无法执行的形式.generation span 需要包含 assistant 生成的序列化调用,却不能把下一轮工具返回纳入损失;这正是区间标注优于「从某个固定前缀以后都算 assistant」的地方.

DPO,GRPO 超参数不能脱离采样分布解释. DPO 的 beta,GRPO 的组大小和采样温度共同决定优化信号尺度.较高温度扩大组内差异,可能提供更多可比较样本,也会增加无效答案;较大组提高相对排序分辨率,却使 rollout 成本线性增长.若 verifier 奖励近似二值,低成功率阶段往往整组全错,高成功率阶段又容易整组全对,两端都会产生零方差.课程式选择题目难度,动态采样或更细奖励可以缓解,但它们会改变目标数据分布,必须明示. 优势标准化还会让同一绝对奖励在不同组中产生不同梯度.某回答在弱组里略好就可能获正优势,在强组里相同得分却为负.这是组相对方法的设计而非 bug,也意味着不能仅用全局平均 reward 推断每步梯度.审计时应抽查每组原始分数,均值,标准差,优势和最终 mask,并确认 padding 与未完成 response 不参与归一化.

KL 控制是在线 RL 的另一安全栏.即使算法不显式训练价值网络,也需要防止 policy 快速偏离初始或参考模型.实际实现可能通过损失中的 reference log-prob,采样约束或其他正则实现;判断必须回到 `grpo_fast.py` 对应配置,不能从「GRPO」名称推断固定公式.报告应写清参考模型是否常驻,多久同步,KL 系数和 token 级 mask,否则不同实现挂着同名算法仍不可比较.

故障恢复与阶段交接. 在线 RL 的 checkpoint 比 SFT 更复杂.仅保存训练权重和优化器,恢复后可以继续更新,却未必能复现中断前的 rollout 队列;旧 worker 可能还在返回由过时 policy 生成的结果.可靠恢复要么丢弃所有飞行中的请求并从明确 step 重建队列,要么把请求 ID,生成 policy step 和消费状态持久化.源码提供陈旧结果判断,能够限制偏差,但运维层仍需保证重启后不会重复消费同一批结果. 阶段交接也需要显式验收.SFT 输出进入 DPO 前,应比较 tokenizer vocab 大小,special token ID,chat template 文件和一次固定对话的渲染结果;DPO 进入 RL 前,还应验证 vLLM 与训练端对同一 token 序列计算一致,确认权重同步没有遗漏新增 embedding.若模型做了 merge,格式转换或参数重命名,应保存转换脚本和转换前后抽样张量校验,而不是只记录最终目录.

评测 checkpoint 的选择不能只看训练 reward.verifier reward 可能过拟合,DPO loss 下降也不保证开放式质量提升.合理流程是在固定,无污染的验证集上同步观察任务成功率,格式,长度,KL 与通用能力;选择规则应在看最终测试集前确定.Open Instruct 把训练产物交给 OLMES 等外部评测,这种分离只有在版本和选择规则都记录时才真正降低自我评估偏差.

从开放代码到开放实验. 开放代码回答「系统可以怎样运行」,开放实验还要回答「这次究竟怎样运行」.后者需要不可变的数据清单,资源账单,失败与重启记录,被过滤样本统计,以及最终模型之外的中间 checkpoint.尤其 RLVR 会持续生成新数据,rollout 本身就是训练集;如果完全不保存或只保存成功样本,外部研究者无法判断能力提升来自策略学习,题目采样还是奖励漏洞. 隐私与安全又限制 trace 的公开程度.可行折中是公开聚合指标,哈希,脱敏样本和可重放的 verifier 测试,同时保留受控访问的完整日志.对代码执行任务,应公开 sandbox 镜像 digest 和测试依赖,不公开危险网络权限或密钥.开放并不要求泄露敏感信息,而要求明确哪些证据可得,哪些经过脱敏,哪些因政策不可发布.

Open Instruct 展示了一条完整的后训练工程因果链:模板决定模型看到的 token,数据筛选决定监督分布,采样策略决定探索范围,verifier 决定可优化目标,异步系统决定策略陈旧度,分布式归一化决定梯度尺度.任何一环变化都可能改变结果.固定提交便于审查实现;模型发布若要支持复现,还需保存整条链的配置和运行记录.

训练阶段关系是一张依赖图. SFT checkpoint 同时是 DPO reference,奖励模型基座候选和 RL 初始 policy.偏好数据可能由某个 SFT 或 DPO policy 生成;RL verifier 又可能使用独立 judge.只画 SFT→DPO→RL 的直线,会隐藏数据生成和参考模型回边. 实验 manifest 应把每个资产写成有向图节点:权重,tokenizer,数据,reference,生成 policy,verifier 与评测配置.边标明「初始化」「生成」「打分」「转换」.这样能定位版本升级影响哪些结果,也能避免把不同谱系混为同一配方. 阶段并非全部必选.可从 SFT 直接 RLVR,也可 SFT 后 DPO 停止,RM 则可独立服务 BoN.比较路线时要对齐最终 token 预算与数据接触,不能把多一个阶段的算力隐去.

### 3.3. Rollout,GRPO 与非平稳目标

离线 SFT 数据在训练前固定,RL 每一步由当前 policy 生成新 response.policy 更新后,答案正确率,长度,错误类型与奖励方差都变化.因此「训练集」必须由 prompt 集,采样配置,policy step 和随机种子共同定义. 保存全部 rollout 成本高,可以保存分层样本,哈希和聚合统计.至少记录每步成功率,长度分位数,终止原因,reward 组成,零方差组和过滤比例.异常出现时才能回到具体输出. 只保存高奖励样本会产生幸存者偏差.失败,超时,sandbox 错误和被丢弃陈旧样本同样决定有效分布.计数漏掉它们,复现者会高估 verifier 覆盖和吞吐.

**GRPO 的组相对优势怎样形成.** 对同一 prompt 的 $G$ 个回答,奖励为 $r_i$,常用优势

$$
A_i=\frac{r_i-\bar r}{s_r+\epsilon}.
$$

同组优势和接近零,因此算法强化相对更好回答,压低相对更差回答.它不要求跨 prompt 奖励尺度完全一致,适合不同难度题目.代价是组内方差决定梯度,全部同分时没有信号. 只中心化而不除标准差,会保留绝对差值;标准化则让低方差组的小差异与高方差组的大差异拥有相近尺度.二者对 verifier 噪声敏感性不同.配置必须与实验结论一起报告. 组大小增加提供更多排序信息,也线性增加生成成本.固定总 rollout 数时,大组意味着更少独立 prompt.应比较 prompt 覆盖与组内探索的权衡,而非只看每组样本越多越好.

零方差过滤会重塑题目难度. 全错组和全对组在二值奖励下都零方差.过滤它们后,训练集中只剩当前 policy 偶尔成功的中等难度题.课程自然形成,却会永久忽略太难与太易 prompt. 随着模型变强,原中等题变成全对并退出,训练自动向困难题移动.若 prompt 池没有足够难题,有效 batch 会缩小;若全错题过多,模型缺少进入成功区域的信号.更细过程奖励或难度采样可缓解. 日志必须把全错和全对分开,而非只报零方差总数.两者对应相反状态.过滤后的领域比例也要看,避免某类题因 verifier 粗糙而消失.

异步陈旧性改变优化目标. rollout 由 step $t-k$ 的 policy 生成,训练时 policy 已到 $t$.当 $k$ 增大,response 在当前策略下概率可能很低,组相对优势不再代表当前采样分布.重要性比可校正一部分,方差又会增加. Open Instruct 记录生成 step 与 off-policy 步数,使陈旧性可观测.最大允许步差是算法参数:阈值严,丢弃多,吞吐下降;阈值宽,数据利用高,偏差增大.只报告异步加速比会遗漏统计代价. 可按陈旧度分桶计算 reward,KL 和梯度贡献.若旧样本质量系统性不同,应调整并发或权重同步频率.恢复训练后飞行队列尤其危险,因为 checkpoint step 与 worker 权重可能不再匹配.

verifier 的确定性需要单独测试. 字符串与数学 verifier 可能依赖规范化,浮点容差,符号化简和超时.相同输出重复运行应给相同奖励;若环境或随机测试使结果波动,组内优势混入测量噪声. 为每类 verifier 建立金样本:等价表达,边界单位,额外文本,错误答案,空输出和恶意输入.代码 verifier 还要测试超时,内存,文件系统和网络隔离.升级依赖后重跑回归集. 确定不等于正确.测试用例覆盖不足会让错误程序通过,字符串规则可能拒绝语义等价答案.人工抽查高奖励新模式,特别是 reward 突然跃升后的输出,是发现漏洞的关键.

多奖励聚合定义真实目标. 验证正确性,格式,长度,工具使用和 rubric 可以加权求和.总奖励

$$
R=\sum_j w_j r_j
$$

看似简单,量纲和范围却不同.二值正确性与连续格式分数直接相加时,权重决定模型是否能用漂亮格式补偿错误答案. 先分别标准化也有风险:稀有但关键的正确奖励可能被压小.更安全的设计可采用门控,答案正确后才计风格奖励;或把关键约束作为硬条件.聚合规则应根据任务损失设计. 训练日志必须保存每项 reward 与相关性.总分上升而 verification 不升,说明模型优化了辅助项.只公开总曲线无法审计 reward hacking.

多轮环境的 credit assignment. 工具任务的最终成功由多步动作共同产生.只给末轮奖励,早期正确调用通过回报传播间接学习,方差大;逐步累加奖励信号密集,也可能鼓励冗长轨迹或重复调用. `last` 与 `sum` 聚合对应两种价值定义.还可对步骤折扣,对成本惩罚,只奖励首次达成.选择必须反映真实任务:搜索次数是否昂贵,部分进展是否有用,失败后继续尝试是否允许. 轨迹截断与环境异常要区分.超出最大步不是普通错误答案;工具不可用也不应归责 policy.rollout state 中的 done,step_count 与 info 为这种分解提供基础.

在线 RL 的 KL 要按 token 与分布解释. KL 惩罚限制当前 policy 相对 reference 的变化.平均 KL 小,少数领域或罕见 token 仍可能剧烈漂移.应按任务,长度和位置分桶,观察 reasoning token,最终答案与工具调用的变化. reference 是固定 SFT 还是周期同步 policy,会改变含义.固定 reference 保持初始行为,移动 reference 只限制单步变化,长期仍可远离起点.配置名称不足以说明,必须追代码和 checkpoint. KL 系数与 reward 尺度耦合.奖励翻倍而 beta 不变,相对约束减半.更换 verifier 或聚合权重后,应重新看实际 KL 与外部能力,不能机械沿用超参.

训练与 rollout tokenizer 必须逐 token 对齐. vLLM 与训练端若加载不同 tokenizer revision,同一字符串可能得到不同 ID.policy log-prob,截断长度和停止条件随后全部错位.新增 special token 而未同步 embedding 更会产生难以发现的异常. 阶段验收可用固定 prompt,分别导出两端 input IDs,decoded text,stop token 与首步 logits.逐项一致后再启动大规模 rollout.只比较最终文本会掩盖特殊 token 差异. chat template 也要在服务端固定.推理引擎自行应用默认模板,而训练端已预渲染,会导致重复 header.接口应明确传 messages 还是 token IDs,避免双重模板化.

分布式 batch 的统计单位. RL 配置里「batch」可能指 prompt,response,序列或 token.每 prompt 多样本后,response 数是 prompt 数乘组大小;过滤与未完成使实际数下降.梯度累积又把多个 microbatch 合成 optimizer step. 比较实验应统一有效 response token 或 optimizer step,而非只看名义 batch.长推理答案使 token 数波动,按序列归一与按 token 归一产生不同权重.各 rank 有效 token 不均时,全局 reduction 更关键. 吞吐报告同时给 prompt/s,response/s,token/s 与有效训练 token/s.只给生成 token/s 不能反映过滤浪费,只给训练 token/s 又隐藏 rollout 瓶颈.

## 4. 训练资产与评测归因

后训练实验由多种资产共同决定: 原始数据,阶段视图,模型权重,verifier,judge,配置和运行环境. 这些对象若只有可变名称而没有不可变版本, 后续结果即使数值接近, 也难以判断是否复现了同一条配方.

归因则要求一次只改变明确变量. 数据消融需要匹配 token 预算, 评测要冻结生成参数与失败处理, 基础设施异常也不能直接记为负奖励. 安全,隐私和许可证贯穿数据与日志, 不能等权重发布时再补检查.

### 4.1. 权重同步,资源与配方版本

训练 policy 更新后,rollout 引擎需要加载新权重.同步太频繁会阻塞生成,太稀疏增加陈旧性.增量同步,分片传输和双缓冲优化性能,也要验证所有 worker 切换到同一 step. 日志中的最小,最大生成 step 能发现部分 worker 落后.若某节点长时间使用旧权重,它产生的样本可能集中于不同难度.简单平均 off-policy 步数会掩盖长尾. 同步失败必须 fail closed.继续用混合版本生成却不标记,会让同一组 response 来自不同 policy.每条 rollout 携带 model step,是后续过滤与审计的必要条件.

**资源账单要覆盖整个闭环.** SFT 主要消耗训练 GPU;RL 同时需要训练,vLLM,judge,sandbox CPU,存储与网络.报告「8 张 GPU」若未说明如何分配,无法比较成本.异步重叠降低墙钟时间,不减少所有组件总算力. 应按阶段记录设备型号,数量,利用率,墙钟,生成 token,训练 token,失败重试和存储.代码执行的 CPU 秒与容器启动也可能成为主瓶颈.云端 judge 还需 API 成本与限流. 质量—成本曲线比单点更有用.增大组大小,提高 N 或使用更强 verifier 带来多少收益,必须与额外资源同时展示.开放配方的可负担性由整条链决定.

评测归因需要冻结训练外的变量. 比较 SFT,DPO 与 RL 模型时,若模板,解码,最大生成长度或评测 commit 改变,分数差异不能归给阶段.每个 checkpoint 应用同一 OLMES 配置,并保存原始生成. 某些模型需要特定 think 模板或特殊停止符.强行统一模板会不公平,采用各自推荐模板又把模板升级包含在模型效果中.可同时报告「原生最佳配置」和「统一接口配置」,明确两个问题. 训练期间反复查看测试集并挑 checkpoint 会形成适应.开发集负责选择,最终测试只运行冻结候选.大规模实验难以多种子,也应至少给题级区间和关键小模型复现.

仓库 commit 与论文配方不是一一对应. 论文描述冻结时间点的实验,仓库主线继续迭代.后来的 bug 修复,默认参数和数据接口可能更可靠,却未用于原论文数字.拿最新代码重跑,得到的是新版实现上的复现实验. 每个结果应绑定代码提交,配方脚本和模型卡.若论文补丁未进入主线,需保存 diff.反过来,仓库中出现某功能也不能倒推旧模型已经使用. 理解证据时分三层:源码证明功能存在,运行日志证明某次启用,论文对照证明它影响结果.三者不能互相替代.

CHANGELOG 是语义迁移线索. 向后不兼容仓库中,CHANGELOG 能提示参数重命名,模板升级与算法路径变化.但日志通常概括行为,不足以复现.仍需查看实际 diff,默认值和迁移脚本. 尤其关注数据缓存,生成标签,停止 token,reward 聚合和 checkpoint 格式.它们可能不改变顶层命令,却改变训练目标.升级后用金样本和小模型做回归,确认预期差异. 若历史提交缺依赖或外部数据已更新,可记录无法严格恢复的部分,采用近似复现.清楚标注比伪装逐位一致更可靠.

配置默认值也是实验参数. 脚本只显式传一部分参数,其余来自 dataclass,YAML,环境变量和启动器.代码更新默认值后,同一命令会产生不同实验.最终配置应在运行时展开并写入输出目录. 布尔开关尤其容易混淆:未传,false 与自动检测可能是三种状态.路径存在时自动启用缓存或恢复,也会改变行为.配置解析后打印规范化 JSON,并计算哈希,可作为运行身份. 敏感信息如密钥不能写入公开配置,可用占位符和秘密版本标识.它们不影响算法时无需披露值,但外部服务版本与权限范围仍要记录.

数据 revision 必须冻结到不可变对象. Hugging Face 数据集名称可能指向移动分支.上游删除,修复或新增样本后,同名配方的 token 数变化.应固定 commit SHA 或保存数据文件哈希与 manifest. 流式读取时更难确认完整快照.记录 shard 列表,大小,校验和与读取顺序,训练结束核对实际消费.网络重试若跳过 shard,不能静默继续. 许可或删除请求可能迫使数据更新.新版实验应新建版本,并说明与旧模型差异;不能覆盖旧 manifest 后仍沿用原结果.

模型 revision 包括 tokenizer 与远程代码. 基础模型 ID 之外,还有权重 revision,config,tokenizer文件,chat template 和 `trust_remote_code` 实现.任一变化都可能影响前向或输入.完整快照应分别哈希. tokenizer 扩词后 embedding 尺寸变化,加载旧 checkpoint 的缺失键处理必须明确.自动 resize 若随机初始化新 token,会影响特殊格式学习.阶段间要保持同一映射. 远程代码带来供应链与复现风险.固定 commit,离线保存并审查执行内容,避免模型仓库更新后运行不同逻辑.

随机种子无法覆盖异步顺序. SFT 中固定数据 shuffle,dropout 和算子能接近可重复;分布式浮点归约仍可能不同.RL 又加入采样,环境时延,worker完成顺序和过滤,单一 seed 无法规定消费顺序. 目标应从逐位复现转为统计复现.固定版本与分布,运行多个种子,报告均值,区间和关键轨迹.单次大实验则保存 rollout,使异常可解释. 确定性模式可用于小规模测试,验证算法与恢复;生产规模接受非确定性,但不得省略不确定性报告.

checkpoint 需要分层定义. 模型 checkpoint 包含权重;训练 checkpoint 还含优化器,scheduler,随机状态和 step;系统 checkpoint 对 RL 还包括队列,worker 权重版本和数据游标.三者恢复能力不同. 发布模型只需第一层,宣称可继续训练至少需要第二层.宣称可精确恢复异步任务则需第三层,代价很高.文档应说明提供哪一层. 保存频率也影响实验.故障后回退会重复或遗漏数据;scheduler step 与数据游标错位可能改变学习率.恢复演练应成为配方验收的一部分.

### 4.2. 数据消融,题目难度与 verifier

SFT 若含评测答案,模型可直接记忆;DPO 若含评测 prompt,即使候选答案不同,也能学题目特定排序.RL prompt 与评测重合则会在线探索正确答案,污染更直接. 去污染应分别扫描 prompt,demonstration,chosen/rejected 和 verifier 测试.只对完整样本哈希会漏掉字段级交集.代码题还需查测试函数与题干变体. 发现交集后按题族删除,避免释义版本一边训练一边测试.报告各阶段删除量,才能知道性能变化来自算法还是数据净化.

**评测生成参数会改变阶段比较.** 温度,top-p,最大长度与停止符影响任务得分.RL 模型可能输出更长 reasoning,若最大长度不足会被截断;SFT 模型短答则不受影响.统一上限看似公平,实际偏向不同策略. 可报告固定预算与推荐预算两套.固定预算比较单位资源能力,推荐预算比较最佳行为.代码执行任务还要固定采样数与 pass@k. 原始输出与停止原因应保存.答案抽取失败可能来自格式,不等于知识缺失;分阶段分析能指导模板或训练改进.

数据消融要控制 token 预算. 删除一个数据源后总训练 token 下降,性能变化混合内容与算力.可用其他来源补足 token,或保持步数并明确预算变化.两种对照回答不同问题. 加入高质量小数据也可能同时改变采样比例.应报告绝对 token 与相对权重,观察来源验证 loss.多来源交互意味着单独增量不一定可加. 大模型消融昂贵,可在小规模完成全矩阵,再在目标规模验证关键方向.跨规模外推需标为证据层级,而非默认成立.

阶段收益不能只看最终平均分. DPO 可能提升开放偏好却损伤多语言,RLVR 提升数学却改变通用对话.平均分会掩盖能力重分配.每阶段应固定能力面板与风险面板. 还要报告相对 SFT 的逐样本翻转:哪些题从错到对,哪些从对到错.净增相同的模型可能行为完全不同.长度,拒答和语言比例是必要行为统计. checkpoint 轨迹比起点终点更有解释力.若收益早期出现,后期退化,训练轮数本身就是结论.

DPO 数据生成 policy 会留下分布签名. chosen/rejected 来自哪些模型,决定措辞,长度与错误模式.策略可能学会辨认生成器,而非质量.候选来源需要平衡或在分析中分桶. 若 DPO 后 policy 接近 chosen 生成器风格,开放评判提升可能含风格迁移.等长人评,内容执行和来源遮蔽可分离.数据卡应列生成模型 revision 与采样参数. 偏好标签的 judge 又是一层来源.生成器与 judge 同谱系时可能偏爱熟悉输出,产生同源偏差.多裁判和人类复核能降低风险.

在线题目难度需要动态管理. policy 对简单题全对,困难题全错时,二值 GRPO 都无信号.题目池应覆盖当前成功率中段,并随训练更新.固定难度会使有效 batch 逐渐下降. 动态采样可按历史成功率分桶,保留一定比例易题防遗忘,难题推动边界,中等题提供主梯度.采样概率必须记录,否则训练分布不可复现. 根据同一 policy 表现选题会产生课程反馈.能力提升与题变难同时发生,平均 reward 可能不升.应在固定锚题集上另测纵向进步.

verifier 更新相当于更换环境. 修复数学等价,增加代码测试或调整格式规则后,相同 response 奖励改变.继续训练相当于中途切任务.更新 step 和版本必须进入 rollout. 新 verifier 应对历史 trace 重放,估计奖励变化与受影响样本.如果排名大幅改变,前后曲线不能直接连接.必要时从新 reference 重新校准. 漏洞修复可能让已学策略突然失去高奖励,引起梯度震荡.分阶段过渡或回放新标签能缓解,但也要作为算法变化报告.

reward hacking 的证据来自样本. 平均 reward 上升,外部指标停滞只是警报.确认漏洞需要查看高奖励输出,找出重复,格式投机,测试泄漏或伪造答案.trace 是核心证据. 可定期抽取奖励增长最快,长度异常和 verifier边界样本,由人或独立 judge 审查.发现模式后构造回归测试,不让修复在后续版本复发. 只展示几个猎奇案例也会偏.应统计漏洞比例,领域与时间趋势,说明其对总体更新的贡献.

工具环境会把外部状态带入训练. 搜索结果,API,软件包和网页会变化.同一 policy 在不同日期得到不同 observation 与奖励.严格复现需保存响应快照或使用版本化环境. 网络工具还可能失败,限流或返回个性化内容.环境错误要与 policy 错误分开标记.否则模型会因基础设施波动受罚. 安全上,生成参数不能访问宿主密钥或无限网络.sandbox 策略,镜像和资源限制既是安全条件,也是任务定义.

OLMo-core 与 HF 路径的对齐实验. 两个后端可读取同一权重与数据,却在 packing,混合精度,并行和 scheduler 上不同.宣称等价前,应在小模型上固定 batch,比较首步 logits,loss,梯度范数和若干更新后的权重. 逐位一致通常不现实,可设数值容差并比较最终验证.若差异超过随机种子范围,需定位实现,而非把后端性能混入算法结论. 高效路径的吞吐收益也应在相同有效 token 和硬件下测.只比较不同集群墙钟没有意义.

参数高效微调是另一条实验轴. LoRA/QLoRA 改变可训练子空间与数值路径.它们可降低资源,却不应与全量 SFT 在不同长度,epoch和数据预算下直接归因.Open Instruct 提供配置,结果仍取决于具体配方. 阶段组合也不同:LoRA SFT 后 DPO 可继续同一 adapter,新建 adapter 或合并后再训练.每种方式的参考模型与容量约束不同. 发布 adapter 时必须绑定基础权重 revision 与 tokenizer.单独 adapter 文件无法定义完整模型.

奖励模型评测不等于策略评测. RM 在静态偏好集准确,只说明有限候选排序.用于 BoN 时还受 generator 分布影响,用于 PPO 时受动态漂移和尺度影响.应分别建立评测. Open Instruct 可连接 RM 训练与 RL,适合沿静态准确率,固定候选 BoN 和短程 PPO 三个层次观察失效位置. 高 RM 分数不能替代 policy 的任务,安全和行为评测.模型卡应分开列资产能力.

开放配方需要公布负结果. 哪些学习率发散,哪些数据混合退化,哪些 verifier 被利用,都能帮助复现者避免重复成本.只发布最佳脚本,会让选择过程不可见. 负结果应包含运行条件与诊断,不能只写「无效」.若因基础设施故障而失败,与算法无效不同.中断实验也可提供吞吐和稳定性证据. 公开超参搜索范围还能解释赢家偏差.最终配置从多少候选中选出,决定分数可信度.

### 4.3. 许可证,测试与因果追踪

指令数据可能含个人信息,rollout 可能复现敏感内容,trace 又集中保存输入输出.访问控制,脱敏,保留期和删除机制需要贯穿流程. 代码执行环境要防逃逸,外部 judge 请求要避免发送受限数据.开源脚本不自动解决部署责任.复现共享可采用哈希,聚合和受控访问. 删除数据后,已训练权重是否需要重训是治理问题.至少保留来源映射,才能评估影响范围.

**许可证是组合约束.** 代码 Apache 2.0,基础模型许可,数据条款,教师输出和最终权重许可共同决定用途.不能由仓库 LICENSE 推导整套产物可商用. 数据混合中最严格条款可能限制再分发.模型卡应逐源列许可与未知项.工具 API 的服务条款也可能限制训练使用. 开放实验应把法律不确定性写入清单,避免技术可复现被误解为授权完整.

小规模 smoke test 的目标是验证语义. smoke test 不追求性能,检查一批数据能否转换,loss 是否落在合理范围,梯度是否非零,checkpoint 能否恢复,rollout 与 verifier 是否闭环.使用极小模型能快速覆盖路径. 测试样本应刻意包含长对话,工具调用,多个 assistant 回合,空回复,超长截断和 verifier边界.只用简单 happy path,发现不了真实问题. 通过 smoke test 也不证明大规模稳定.它是进入昂贵实验的最低门槛,后续还需吞吐与多节点测试.

单元测试与科学验证分工不同. 单元测试证明函数对预设输入输出正确,无法证明预设目标合理.reward aggregator 求和无 bug,不表示 sum 适合任务;mask 对齐正确,也不表示数据答案高质量. 科学验证需要对照实验,独立评测与人工样本.工程测试保护实现,研究设计保护结论.两者都必须有,不能用测试通过替代效果证据. 回归测试应来自真实故障,例如 `<think>` mask 和工具结束 token.把事故固化成测试,是仓库逐步可靠的关键.

运行日志应支持因果追踪. 日志不只记录 loss.SFT 需要来源 token,截断与梯度;DPO 需要 chosen/rejected概率,margin和KL;RL 需要组奖励,零方差,陈旧度,过滤,长度与 verifier分项. 指标命名和定义要版本化.同名 reward 在聚合规则变化后不可直接拼图.仪表盘展示方便,原始事件与配置更重要. 异常点应能链接到样本或 trace ID.没有这条链,只能看到曲线坏了,无法知道为何坏.

资源优化不能改变样本语义. 为了吞吐做 packing,动态 batch,异步生成和缓存,都可能改变顺序,截断或过滤.优化前后要用相同金样本验证输出张量与 reward. 若算法允许近似,如更陈旧 rollout,应明确精度—吞吐折中并做消融.不能把系统近似藏在「工程优化」中,因为它直接改变训练数据. 性能 benchmark 也要固定质量设置.降低最大长度获得更高 token/s,不是同任务加速.

checkpoint 选择规则应预注册. 训练 reward,验证成功率,通用能力与KL可能指向不同 checkpoint.先看所有结果再挑最佳,会对验证集过拟合.应提前定义主指标,约束和 tie-break. 可采用安全约束下最大化任务分:通用能力下降不超过阈值,再选验证成功率最高.规则比简单平均更符合部署需求. 最终测试只评选定 checkpoint.若报告 oracle best checkpoint,应明确它是上界分析,不与预注册结果混淆.

多种子应优先覆盖关键不确定性. 全量重复昂贵,可先在小模型与短程训练上多种子,估计数据顺序和采样方差.大模型至少对最终解码与评测重采样. RL 方差通常高于 SFT,应优先重复在线阶段.若只能一次,保存轨迹并用不同 rollout seed 做局部验证.单次曲线的偶然跳升不应写成稳定规律. 报告资源限制和种子数,让读者判断证据强度.没有重复不等于结果无效,但结论应更克制.

从仓库功能到论文主张的证据梯度. 源码可说明支持某算法,配置可说明推荐参数,模型卡可说明发布产物,论文表格才提供受控效果.README 宣传语位于这些证据之间,需追到对应实验. 例如仓库支持 evolving rubric,不表示所有 OLMo 模型使用;包含 sandbox 不表示每次代码训练环境相同;有去污染目录不表示所有数据已按同阈值处理. 解析开源项目时给每个结论标证据层,能避免用「代码里有」替代「实验中启用」.

一条完整配方的最小清单. 数据层保存来源,revision,转换版本,模板,截断,packing与有效 token;模型层保存基础权重,tokenizer,reference与阶段 checkpoint;算法层保存 loss,beta,KL,组大小,奖励与过滤;系统层保存镜像,拓扑,同步和恢复;评测层保存 OLMES commit,提示,解码,污染与选择规则. 这份清单的作用是让每个结果可追踪.缺少一项不必宣布实验无效,但要说明不确定性落在哪里.能补做的小规模对齐测试应随报告提供. Open Instruct 的价值正在于把这些环节放在同一公开系统里.它提供可审查的起点,完整复现仍依赖研究者把一次具体运行冻结成证据包.

## 5. 配方验证与运行边界

一条配方跑通, 只证明程序完成了训练. 样本 token,mask,首批 loss,reference 输出和 verifier 结果还需要逐层对齐, 才能确认实现与目标一致; 吞吐优化若改动 batching,packing,精度或异步策略, 也要重新做语义回归.

最终实验包应能从原始记录重建阶段视图,checkpoint 和全部评测表. 成功权重,失败轨迹与负结果共同说明配方对版本,随机性和环境的敏感度, 也让复现失败可以沿数据,训练器和采样器逐层定位.

### 5.1. 重放,精度与更新语义

配方复现要求数据,代码,超参和环境一致,检查训练轨迹是否接近.结果复现允许硬件和实现变化,只要求核心行为与结论重现.前者失败可能是系统差异,后者失败才更直接挑战科学结论. 大型训练很难逐位相同.可设置层级:首批 loss,固定 checkpoint 指标,最终领域方向和关键对照.每层给容差与证据.只要求最终总分一致,可能掩盖中间机制完全不同.

**重放 rollout 能隔离训练器与采样器.** 保存一批 rollout 后,可固定数据重跑优势计算和 policy 更新,验证训练侧;固定 checkpoint 重新生成,则验证采样与环境侧.把闭环拆开,故障定位更清楚. 重放也能比较 verifier 版本和 reward 聚合.历史 response 在新规则下重新打分,可量化规则变化.需要保存 token IDs,policy step,环境 observation 和原始输出.

参考模型常驻与预计算的取舍. DPO 在线计算 reference 保证与当前 token 序列一致,但增加显存和计算;预计算降低成本,却把数据转换冻结在缓存中.模板,截断或 tokenizer 一变,缓存全部失效. 预计算文件应保存 prompt/response token 哈希,reference revision 和 log-prob 精度.抽样在线复算,检查数值误差.不能只用样本 ID 关联,因为上游内容可能原地更新.

精度格式会进入算法结果. BF16,FP16,FP32 和量化参考模型产生不同 log-prob.DPO margin 很小时,数值误差可能翻转;RL 中 reward 与 KL 的小差异会累积.混合精度策略要视作配方. 跨后端对齐应在固定序列上比较 logits,log-prob 和 loss.容差随长度增长,最好同时看 token级最大误差与序列总误差.吞吐优化若改变精度,需给效果回归.

梯度裁剪与异常 batch. 长序列,极端 DPO margin 或高方差优势会产生梯度峰值.裁剪保护稳定,也改变这些样本相对贡献.报告阈值之外,还要记录裁剪发生比例与来源. 若某数据源频繁触发裁剪,整体 loss 仍可能正常.按来源和阶段看梯度范数能发现格式错误或 reward 异常.只记录全局平均会把尖峰抹平.

scheduler 的步数分母要用实际更新. 过滤 rollout,动态 batch 和恢复会让实际 optimizer step 与预计不同.按预设总步数衰减学习率,训练提前或延长后曲线错位.scheduler 状态必须随 checkpoint 保存. SFT 按 epoch 定义步数也受过滤和 packing 影响.更稳妥地报告累计有效 token,optimizer step 与当前学习率.跨实验比较时至少对齐其中一个明确预算.

数据加载顺序会形成隐式课程. 流式 shard,长度分桶和按源采样都会让局部 batch 非独立.优化器动量保留此前方向,顺序因此可能影响最终模型.分布式 worker 重启又可能改变 shard 分配. 记录数据游标,shuffle seed 和每步来源摘要.课程若是有意设计,应写入配方;若只是存储布局造成,应随机化或验证影响.相同集合并不保证相同训练.

response mask 决定 RL 更新哪些 token. policy loss 通常只作用于生成 response,prompt token 用于条件却不更新.工具轨迹中 observation 是环境输入,也应 mask;assistant 的工具调用属于动作,应参与.边界错位会把环境文本当 policy 行为. 终止 token 是否计入 loss 影响长度.忽略终止,模型可能学不会停止;错误纳入工具返回,又会训练模型伪造 observation.固定轨迹可视化 mask 是必要验收.

长度归一会改变偏好与 RL. 序列 log-prob 求和天然随长度更负.DPO 的 chosen/rejected长度差会进入 margin;PPO 的 token级优势分配也影响长回答.是否按 token 平均属于目标设计. 长度归一可能削弱真实序列概率,也能减少长短捷径.应按长度差分桶,比较回答质量和生成长度.不要从算法名称推断仓库实现,需固定提交检查公式.

EOS,轮次结束和最大长度是三种终止. 自然 EOS 表示模型主动完成,轮次结束可能把控制权交给工具或用户,最大长度则是外部截断.三者若统一标成 done,奖励和训练无法区分. 日志应记录 stop reason,verifier 对截断答案可单独处理.训练时只对自然结束奖励格式,避免模型因被系统截断获得同等待遇.工具环境还需保存谁拥有下一步控制权.

代码 verifier 的测试集也会泄漏. policy 若接触隐藏测试或从错误信息推断用例,可针对测试而非任务.sandbox 应限制测试文件可见性与输出,训练 prompt 不包含关键断言.公开测试与隐藏测试分开. 同一题反复 rollout,模型可能通过 reward 反馈逐渐记住答案,即使看不到测试.这是在线学习的预期,也是评测污染风险.训练题与最终代码评测必须题族隔离.

evolving rubric 会使目标非平稳. rubric 根据新 rollout 更新时,奖励函数随训练变化.它能捕捉新错误,也让早期与后期 reward 不可直接比较.每条 rollout 必须绑定 rubric version. 新 rubric 可能针对当前 policy 过拟合.保留固定验证 rubric 与历史重放集,检查更新是否提高泛化.若只看当前训练 reward,会把规则迁移误作模型进步.

judge 模型也是依赖资产. 若奖励包含 LM judge,需固定其权重,模板,解码和服务版本.API 模型静默升级会改变标签.缓存 judge 输出能复现,却要与输入哈希绑定. judge 与 policy 同谱系可能偏爱相似风格.交换裁判,加入可验证指标与人类抽样,能判断提升是否局限于同源模型的偏好.成本统计也要包括 judge token.

模型合并会改变数值. LoRA 合并,分片聚合,格式转换和量化都可能引入误差.阶段交接前后用固定 prompt 比较 logits和生成,设置容差.权重 key 全部匹配不代表函数等价. 合并顺序在多个 adapter 下尤其重要.若 SFT 与 DPO adapter 分别存在,线性相加不一定等于顺序训练.发布时说明合并方法和原始资产.

### 5.2. 恢复,血缘与数据选择

checkpoint 保存后仍有预取 batch 或飞行 rollout.重启若从旧游标继续,部分样本重复;跳到新游标又可能遗漏.exactly-once 很难,但重复量要可见. 给 batch 与 rollout 唯一 ID,消费后写状态,可在恢复时去重.若选择 at-least-once 简化系统,应报告重复率并检查是否集中于某来源.

**评测污染与训练反馈循环.** 公开 OLMES 任务若被用于频繁选 checkpoint,虽未进入梯度,也通过人工选择影响模型.反复调参构成开发集适应.最终结论需要独立隐藏测试. 污染检查关注文本重叠,选择污染关注决策过程.实验日志应记录哪些指标何时被查看,用于何种选择.只声明训练数据去污染不足以保证测试独立.

模型卡应描述配方血缘. 模型卡至少列基础模型,SFT 数据,偏好数据,reference,RL prompt,verifier,代码与评测版本.阶段图比一长串命令更易审计. 还要列已知失败:语言覆盖,reward漏洞,被截断样本,未复现指标和许可证限制.只写最佳分数无法支持下游选择.

仓库测试覆盖不等于论文覆盖. CI 通常在小模型,少 GPU 和合成数据上运行,保护接口与基础数值.多节点异步,长时间内存泄漏和真实 sandbox 负载可能未覆盖.测试清单应说明范围. 论文实验提供规模证据,却可能只跑一套环境.工程可靠性需要压力测试,故障注入和恢复演练.两种证据互补.

公平比较需要统一失败处理. 某配方 OOM,超时或产生 NaN 时,调小 batch,长度或换精度会改变任务.比较结果应记录补救,不能只展示成功运行的最终参数. 失败率本身是系统指标.更高吞吐但频繁重启的方案,实际成本可能更高.RL 环境失败若重采样,也会偏向容易执行的题.

开放后训练的最小因果链. 数据和模板定义监督;损失与参考模型定义更新;采样和 verifier 定义在线探索;并行与同步决定数据陈旧;评测配置定义观察结果.任何性能主张都应沿这条链找到证据. Open Instruct 的强项是这些环节大多可见,可替换,可记录.它仍是持续演进的研究仓库,默认值与接口会变.严谨使用方式是把具体提交冻结为实验对象,再用论文和日志判断哪些路径真正被执行.

数据卡与训练卡需要相互引用. 数据卡说明来源,过滤,许可和字段,训练卡说明采样比例,转换版本与实际 token.前者无法告诉模型最终看了多少,后者若没有前者又无法解释内容风险. 两者通过 dataset revision 和 manifest 哈希连接.模型发布时引用具体组合,而非只列数据集名称.混合数据更新后新建训练卡版本,保留旧血缘.

样本过滤会造成选择偏差. 转换失败,超长,角色异常和 verifier 不可执行的样本被删除后,剩余数据更短,更规范,更容易.过滤提高训练稳定,也缩小真实任务覆盖. 应按来源与失败原因报告删除率,并抽查被删样本.若某语言或工具类型大量丢失,最终模型短板来自管线选择,不应归给模型容量.

packing 效率与来源公平. 按长度装箱减少 padding,短样本更容易共享序列,长样本独占.若 batch 按序列数定义,长样本造成 token 波动;若按 token 动态 batch,来源出现频率又变化. 效率优化后重新计算各源有效 label token.只有实际分布保持,才能把性能变化归给吞吐实现.否则 packing 同时是数据重加权.

prompt 去重与 response 去重分开. 相同 prompt 配不同 response 对偏好学习有价值,整对重复只放大权重;不同 prompt 配模板化 response 则可能强化固定话术.去重层级不能混用. SFT 关注 demonstration 多样性,DPO 关注 prompt 族隔离,RL prompt 则要防同题多版本跨训练评测.manifest 应保留重复簇 ID,允许不同阶段采用不同策略.

预训练能力与后训练收益的归因. 后训练分数提升可能来自把已有能力接到指令格式,也可能注入新知识.只看终点无法区分.基座,SFT,DPO,RL checkpoint 在同一任务逐题比较,能看到何时翻转. 对新事实用时间切分与释义测试,对推理用步骤扰动,对格式用等内容多模板.这样才能判断阶段学到知识,选择策略还是表面接口.

训练 token 预算比 epoch 更可比. 混合数据,过滤与 packing 变化后,一个 epoch 包含的有效 token 不同.跨配方写「训练两轮」无法表示计算和监督量.应并列报告输入 token,label token 与 optimizer step. 在线 RL 没有传统 epoch,prompt 可反复采样.用 rollout 数,生成 token,有效组和更新 token 描述更清楚.统一预算后再比较算法.

参考策略也可能带来偏见. DPO 和 KL 正则把策略锚在 reference.reference 的拒答,语言与风格偏见会被保护,即使偏好数据试图改变.较强约束提高稳定,亦限制纠偏. 比较不同 reference,固定偏好数据并测实际 KL,可看到锚点作用.reference 不只是计算附件,而是目标组成部分,必须进入模型血缘.

### 5.3. 能力保持,方差与外部状态

DPO 擅长从广泛主观偏好学习,RLVR 擅长在可验证任务中优化正确性.DPO 接 RLVR 可能兼顾风格与推理,也可能让 RL 覆盖偏好行为.顺序和数据回放决定保持. 对照应包含 SFT→RL,SFT→DPO,SFT→DPO→RL,并对齐总 token.若三阶段路线更强,仍需看增益来自额外计算还是阶段互补.

**能力回放是防遗忘手段.** RL 聚焦数学或代码时,可混入通用 SFT 或偏好样本保持对话,多语言与安全.回放比例太低无效,太高稀释奖励信号.它是多目标权重,不是免费保险. 固定能力面板随 step 评测,找到最小有效比例.回放数据必须与最终测试隔离,也要计入总预算.

训练 reward 与任务成功率的分离. reward 上升可能来自 verifier 漏洞,格式或长度,任务成功率才反映目标.两者出现分叉时,应暂停优化并检查输出.继续追 reward 会加剧投机. 独立 verifier,人评与执行指标形成三角验证.它们也可能有共同偏差,因此保留原始样本最重要.曲线只能提示,案例与统计共同完成诊断.

评测方差来自模型和解码两层. 训练随机性改变权重,采样解码又改变输出.固定 checkpoint 多次生成估计解码方差,多种子 checkpoint 估计训练方差.两者不能用一次 bootstrap 完全代替. 贪心任务解码方差小,自动 judge仍可能随机.报告每层重复设置,让小幅提升有正确误差范围.

自动 judge 的版本必须冻结. 外部 API 更新后,同一输出可能得不同分.保存原始生成与 judge prompt,可在新版本重评;最好固定可复用 judge checkpoint或响应缓存. 缓存也要记录模型版本,时间与参数.只保存最终分数无法分析偏差.评测费用降低不能以丢失证据为代价.

基础设施异常不应转成负奖励. sandbox 启动失败,网络超时,judge 限流和存储错误若统一记零分,policy 会为系统故障受罚.应标为 invalid,重试或从有效 batch 排除,并单独统计. 排除过多又改变 prompt 分布.若某类任务更易故障,系统修复前训练会偏离.有效率需按领域报告.

发布最终权重之外还需中间证据. 最终模型让人使用,中间 checkpoint,训练曲线和抽样 rollout让人理解.阶段性退化,reward hacking和恢复事件只能从中间证据看到. 存储有限时保留关键转折点,固定间隔指标与代表 trace.模型权重可少留,配置和日志成本低,应完整保存.

结论应限定到被验证的配方. 某提交下 OLMo 3 配方成功,能证明这些数据,模板,超参与系统组合可行.它不自动证明所有基座,所有 verifier 或未来仓库版本同样有效. 可迁移经验是目标分解,契约检查,动态日志与外部评测.具体数字属于具体版本.把原则和实例分开,开源项目才能既提供方法,又不制造过度外推.

一个阶段的最佳超参不会自动传给下一阶段. SFT 最佳学习率针对交叉熵,DPO 梯度由概率比决定,GRPO 又由优势和 KL 缩放.沿用同一 batch,长度或 scheduler 只是起点.每阶段应在独立开发集上小范围校准. 前一阶段改变输出长度和成功率,后一阶段有效 batch 也随之变化.配方表应写阶段局部参数与实际统计,避免把整条链压成一个「统一超参」.

prompt 集和答案集承担不同角色. RLVR prompt 定义要探索的问题,verifier 或参考答案定义成功.prompt 可公开而隐藏测试,或二者都版本化.若答案字段在模板中意外渲染给 policy,任务直接泄漏. 转换测试应确认训练输入不含私有答案,测试用例或 judge rationale.环境侧可访问验证资产,policy侧只能接收规定 observation.权限边界也是数据契约.

推理轨迹不必全部进入最终模型行为. Think 配方可能训练显式 reasoning,评测或部署又希望隐藏,压缩或只输出答案.generation span,奖励与模板共同决定模型学会哪些部分.把 `<think>` mask 错误正说明轨迹边界很脆弱. 需要分别测内部推理格式,最终答案和用户可见内容.奖励只看答案可能纵容无效长轨迹,格式奖励过强又可能让模型套模板.轨迹长度与正确率曲线能指导平衡.

tokenizer 模板差异会污染阶段对照. 两个 checkpoint 若使用不同 chat template,分数差异包含提示工程.统一模板可能让其中一个离开训练分布,分别用原生模板又无法隔离模型.应同时给两套结果或做模板交叉矩阵. 固定对话的 token diff 是最直接证据.人眼看起来相同的文本可能有不同特殊 token,空格和结束符,模型对此很敏感.

数据质量与数据难度不能混为一谈. 低 loss 数据可能简单而高质量,困难题 loss 高也可能标注正确.按 loss 删除「异常」会误删能力边界;完全保留又会混入噪声.需要结合 verifier,来源和人工抽样. 在线阶段可用成功率衡量难度,用标签一致与可执行性衡量质量.两轴分开后,课程选择中等难度高质量题,噪声题则修复或删除.

### 5.4. 验收,实验包与失败记录

从多个 checkpoint 选最佳,相当于增加搜索次数.查看越频繁,验证集乐观偏差越大.保存全部曲线有助于估计选择稳定性,但不能消除偏差. 独立确认集或固定早停规则能约束.若论文报告 hindsight best,应明确称为上界,并同时给最终 checkpoint.

**性能回归应定位到哪一层.** 升级后分数下降,定位顺序沿数据张量,首步 loss 与 logits,训练轨迹和评测生成逐层推进.按层检查比直接重跑全实验节省巨大成本. 每层保留小型 golden artifact:转换样本,短训练 checkpoint,固定 rollout 与评测输出.它们组成跨版本回归链,也是开放仓库最实用的测试资产.

最终验收表. 数据验收看 revision,来源,重复,过滤,mask与有效 token;模型验收看权重,tokenizer,模板和阶段血缘;算法验收看损失,reference,reward,优势,KL与过滤;系统验收看镜像,拓扑,同步,恢复和资源;评测验收看污染,配置,选择规则与区间. 任何缺项都应落到明确风险:无法重建,无法归因,可能污染或可能尺度不一致.这份清单用于让问题在大规模训练前暴露,避免成本已经投入后才补查语义. Open Instruct 已经把绝大多数关键对象暴露在代码与配置里.真正高质量的复现,是将它们冻结为一次可检查实验,并让论文数字,发布权重和运行记录指向同一条证据链.

输出目录本身应成为实验包. 一次运行结束后,输出目录应包含展开配置,git commit,环境锁,数据 manifest,tokenizer 哈希,日志,checkpoint 清单和评测链接.路径名不能承担全部语义,因为复制或重命名后会丢失. 机器生成的 manifest 减少手工漏项,并可在加载模型时校验兼容性.公开时删去密钥与内部路径,保留结构和哈希.这样权重文件不会脱离其训练条件流通.

同一数据在不同阶段需要不同视图. 一段对话用于 SFT 时需要 assistant labels,用于 RM 时需要候选对,用于 RL 时通常只保留 prompt 与环境答案.强行维护三份独立副本容易漂移,完全共用一份 schema 又会混入不该暴露的字段. 更稳妥的是保存不可变原始记录,再由版本化转换生成阶段视图.每个视图带父记录 ID,可追踪同一 prompt 的数据接触,也能检查训练测试交叉.

训练正确性先于吞吐极限. 大规模系统容易把注意力放在 GPU 利用率.mask 错误,reference 缓存失配或 verifier 漏洞下,越高吞吐只会更快地产生错误模型.性能调优应以语义测试通过为起点,并在改动后重复回归. 吞吐改动如果触及 batching,packing,异步或精度,就重新进入语义审查.纯系统优化与算法近似的边界要写清楚,避免用工程名义绕过对照.

开放项目的版本边界也是优点. 仓库明确不保证向后兼容,看起来增加复现负担,也迫使研究者绑定提交,配置和资产.相比接口稳定却行为静默变化,显式版本边界更容易审计. 因此,阅读 Open Instruct 应同时看到两面:它提供丰富,真实的后训练基础设施,也要求使用者承担实验冻结责任.代码开放让问题可检查;只有版本化证据包,才能让结果可复查.

一次复现失败应该怎样记录. 失败记录至少包含目标提交,运行配置,已完成阶段,最后正常指标,错误日志和已排除原因.若问题来自数据不可达,依赖撤回或硬件差异,应说明继续使用了何种替代,而不是只留下「无法复现」. 算法结果不一致时,先给逐层对齐证据:样本 token 与 mask 是否相同,首批 loss 是否接近,checkpoint 函数是否一致,评测输出在哪一步分叉.每排除一层,剩余原因就更明确.没有定位完成也可报告边界,防止后来者从头重复. 失败同样属于开放实验资产.它揭示配方对环境,版本和随机性的敏感度,也帮助判断论文数字是稳健现象还是脆弱实现.成功模型与失败轨迹一起保存,才构成完整的研究记录.

这也让后续修复拥有清晰起点.

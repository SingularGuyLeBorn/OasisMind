# OLMo 开源仓库

论文描述研究设计，仓库决定设计如何执行。一个训练公式落到代码后，还需要张量布局、并行组、精度、梯度累积和检查点格式；一个数据过滤规则还需要输入格式、分片、去重顺序和失败处理；一个评测数字则由提示模板、答案抽取、归一化和聚合共同产生。OLMo 的开放性只有在这些实现能够与论文、配置和模型产物相互对应时才完整。

本章选择五个核心仓库。OLMo-core 承担预训练和分布式执行，open-instruct 承担 Tülu 数据准备与后训练，dolma 实现语料处理，olmes 固化任务评测协议，olmocr 处理 PDF 渲染、推理和单元测试。它们覆盖模型生命周期的连续阶段，又通过文件格式、配置和模型标识彼此连接。仓库对照稿记录目录、README、关键配置与公开文档，技术解析则追踪主要数据结构、调用路径、状态变化和工程边界。

## 1. 训练与后训练

### 1.1. OLMo-core 的训练执行面

OLMo-core 提供模型定义、训练循环、优化器、检查点和分布式并行。训练入口读取配置后构造 tokenizer、数据加载器、模型和优化器，再由训练器推进 microbatch、反向传播、梯度同步与参数更新。配置不是静态说明书：默认精度、梯度裁剪、激活检查点和保存间隔会改变实际运行，因此复现实验必须绑定具体提交和完整配置，而不能只写命令名称。

分布式训练的核心是把参数、激活、优化器状态和 token 分配到设备。数据并行复制模型并切分 batch，张量并行切分矩阵，流水线并行切分层，专家并行切分 MoE 专家。不同维度可以组合，但通信组必须一致，检查点还要能够在不同布局间保存和恢复。OLMo-core 解析会说明每类状态由谁持有、何时通信、故障恢复需要哪些元数据，并将实现与 OLMo 技术报告中的吞吐和稳定性设置对应。

### 1.2. open-instruct 的后训练流水线

open-instruct 实现指令数据转换、监督微调、偏好优化、奖励模型与可验证奖励训练。不同数据源先被映射为统一消息结构，再由聊天模板转为 token；损失掩码决定哪些角色参与训练。模板或边界错误会让模型学习生成用户提示、系统标记或 padding，因此数据可视化和小批检查是后训练前的必要验证。

SFT、DPO 和强化学习共享模型与分布式基础，但状态不同。SFT 读取单条目标回答；DPO 同时读取 chosen、rejected 与参考模型分数；在线强化学习还要启动采样、判分和策略更新循环。open-instruct 的配置把 rollout 数、采样温度、KL、奖励和 batch 连接起来。解析将这些量按数据生成、评分和优化三个阶段拆开，避免只从最终脚本名推断算法行为。

## 2. 数据构建

### 2.1. dolma 的处理器与混合器

dolma 仓库把原始文档变成可训练语料。处理流程包括读取、语言与质量分类、规则过滤、PII 处理、重复检测、混合和输出。每个处理器接收文档及其属性，产生保留、删除或新增标记；执行顺序会影响结果，例如先去重再过滤与先过滤再去重面对的候选集合不同。大型语料按分片并行处理，还要保证文档 ID 和统计能够跨 worker 汇总。

数据管线的失败不能静默跳过。损坏压缩包、编码异常、超长行和分类器超时都可能让某些来源系统性缺失。可靠运行需要记录读取数量、各过滤器删除数量、重复簇和最终字节/token 统计。dolma 技术解析会把这些指标与 Dolma 论文表格对齐，并区分代码当前版本与历史数据版本，避免用后来默认值解释早期发布。

### 2.2. 数据产物与许可边界

仓库代码开放不表示所有输入数据都可再分发。网页抓取、代码、书籍和论文具有不同许可与删除要求；处理后的索引、标记和文本也可能受来源约束。数据复现需要分别记录抓取入口、处理代码、产物清单与许可证，而不是用一个“开源”标签覆盖全部层次。

删除请求还要求可追踪性。若训练混合只保存合并后的匿名文本，很难定位某个来源并重建去除后的版本。稳定文档 ID、来源元数据和可重放管线使删除成为确定操作。模型已经训练后，删除数据不等于自动消除参数影响，这又属于模型更新和遗忘问题；仓库能保证的是数据产物层面的可定位与可重建。

## 3. 评测协议

### 3.1. olmes 的任务配置

olmes 将任务、数据集、提示、few-shot 示例、模型接口、答案抽取和指标组合成可版本化评测。任务名称相同但模板不同，会改变模型看到的分布；多项选择是否按 token 长度归一、生成答案如何截取，也会改变结果。仓库配置因此是分数定义的一部分，不是可忽略的运行细节。

评测运行还要处理模型 tokenizer、最大长度、批量和确定性。超过上下文的样本是截断、跳过还是缩短 few-shot，必须明确记录。生成任务的温度、停止串和最大 token 影响正确率与格式失败；聊天模型是否套用官方模板同样重要。olmes 解析会从一个任务配置追踪到请求构造、模型输出和聚合结果，展示结果表如何由逐题记录产生。

### 3.2. 可比性与污染控制

统一协议减少实现差异，却不能消除评测污染。模型可能在预训练或后训练中见过题目、答案或改写。仓库可以提供数据哈希、版本和污染检查接口，最终判断仍需要与训练数据交叉查询。Infini-gram、OLMoTrace 与 Dolma 元数据可以提供匹配证据，但字符串不匹配不能证明语义上独立。

排行榜差异还需要不确定性。有限样本准确率具有方差，任务宏平均会赋予每个任务相同权重，微平均则由大任务主导。olmes 的逐题结果允许 bootstrap 或配对检验，使用者应保留原始预测，而不是只保存最终平均分。协议版本变化时，历史结果应标记版本，不能无说明地覆盖。

## 4. 文档解析

### 4.1. olmocr 的页面流水线

olmocr 仓库接收 PDF，渲染页面并调用视觉语言模型生成结构化文本。管线需要决定 DPI、图像格式、页面并发、提示模板和最大生成长度；这些选择影响小字、表格、公式和整页截断。推理后还要做格式检查、失败重试和结果合并。只比较模型权重，无法解释渲染和调度导致的差异。

大规模转换关注吞吐与可恢复性。一个文档可能有数百页，单页失败不应让整批结果丢失；重复运行也不应重新处理已成功页面。任务清单、页面 ID、输出校验和断点状态需要持久化。解析会区分模型本身的识别错误、PDF 渲染错误和管线状态错误，并说明每类问题应从哪个产物排查。

### 4.2. 单元测试与训练反馈

olmocr 的评测用单元测试检查文本存在、相对顺序、表格和应删除内容。olmOCR 2 又将测试通过情况用于强化学习奖励。测试是确定性约束，但覆盖范围有限：通过所有局部断言不等于整页完整，测试未涉及的段落仍可能遗漏。仓库中的测试定义、匹配规则和归一化必须与模型结果一起版本化。

测试失败还要能定位到页面和断言。聚合通过率适合比较版本，调试则需要保存输入图、原始生成、后处理结果和每条断言。若训练与评测复用同一批固定测试，模型可能适配测试模式，因此数据划分和模板变化是必要边界。olmocr 仓库解析将这条从 PDF 到奖励的路径与两篇论文逐项对应。

## 5. 五个仓库怎样协同

### 5.1. 产物接口

dolma 输出训练文档和元数据，OLMo-core 的数据加载器把文档 token 化并训练基座模型；open-instruct 读取基座权重和指令数据产生后训练模型；olmes 对各阶段检查点运行统一评测；olmocr 则既是独立文档工具，也可为预训练数据构建提供高质量 PDF 文本。接口处最容易产生不可见差异，例如 tokenizer 版本、聊天模板、模型配置字段和文档 ID。

复现时应为每个产物保存内容哈希与生成命令，并记录上游版本。只锁定下游仓库提交不够：相同代码读取不同数据或模型权重会产生不同结果。模型卡和论文中的名称还可能指向后来更新的文件，长期复现需要固定不可变 revision，而不是依赖主分支或浮动标签。

### 5.2. 阅读和审计顺序

按问题进入仓库比从目录逐文件阅读更有效。训练不稳定时，从 OLMo-core 配置、日志和检查点恢复路径开始；行为或格式异常时，检查 open-instruct 数据转换与损失掩码；数据统计不一致时，追踪 dolma 处理器顺序与汇总；排行榜无法复现时，锁定 olmes 任务版本和答案抽取；PDF 结果缺页时，先区分渲染、生成和任务状态。

每个仓库条目同时提供对照稿和技术解析。对照稿保留公开文档与关键配置的原始上下文，解析把实现连接到论文结论，并标明当前代码无法证明什么。代码比论文更具体，却不自动更权威：主分支可能已经改变，注释可能过期，默认配置也不一定是论文配置。可靠结论来自特定版本的代码、配置、日志和产物相互一致。

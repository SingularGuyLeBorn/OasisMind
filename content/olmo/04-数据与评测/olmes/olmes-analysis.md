# OLMES 深度解析: 把评测配置变成可复现的实验对象

语言模型排行榜常把一个小数点后的差距解释成模型能力差距, 但 OLMES 指出的核心事实是: 分数不仅是模型和数据集的函数, 还是提示格式、上下文示例、答案计分方式、概率归一化以及实现细节的函数。只报告“某模型在 ARC-Challenge 上得到多少分”, 就像只报告实验结果而不报告仪器设置。论文在同一模型和同一任务上观察到显著波动, 甚至引用既有研究中仅改变格式与示例便出现极大准确率差异的结果。因此, OLMES 的目标不是再造一个数据集, 而是把容易被忽略的评测过程固定为可以复查、复用和扩展的协议。

这项工作的价值尤其体现在基础模型上。指令模型通常理解“从 A、B、C、D 中选择”的交互约定, 较小或训练早期的基础模型却只接受过下一个 token 预测。直接要求它输出答案标签, 测到的可能是对人为格式的适应能力, 而非题目知识。反过来, 只使用为弱模型设计的完形计分, 又可能无法表达“以上皆非”等选择题语义。OLMES 没有用一个形式强行覆盖所有模型, 而是先拆解混杂因素, 再为不同能力阶段制定连贯规则。

## 评测分数为什么不是模型的固有属性

### 一个分数背后有一条处理链

选择题看似只有“答对或答错”, 实际至少包含六步: 从数据集选取样本, 将字段拼成提示, 选择并排列 few-shot 示例, 将候选答案送入模型, 把 token 概率变成候选分数, 最后聚合为指标。任一步骤改变都可能改变预测。例如, 答案前是否有空格会改变分词; 选项是同行还是换行会改变局部上下文; 示例是否覆盖所有标签会影响标签先验; 对候选总似然还是平均 token 似然排序, 会改变长短答案间的偏置。

这说明模型分数更准确的写法是 $S(M,D,C)$, 其中 $M$ 是模型, $D$ 是数据集, $C$ 是完整配置。只有 $C$ 相同, 两个模型的分数差才能主要归因于模型。若旧论文没有公开配置, 新模型即使在同名任务上得到更高数字, 也不能推出能力更强。OLMES 用 ARC-Challenge 的公开结果展示这一问题: 不同资料为同一模型报告的分数并不一致, 模型间的相对差距也会随设置改变。表格不是简单纠错, 而是在说明“跨来源抄分比较”本身缺少实验控制。

### 内部一致不等于外部可复现

排行榜可以保证站内模型由同一套程序运行, 这解决了内部一致性, 却没有自动解决方法选择是否合理、配置是否足够公开以及其他团队能否复现。若排行榜没有说明为何使用某种归一化、示例来自哪里、任务采用 MCF 还是 CF, 研究者仍难以把结果迁移到训练流程或另一套工具。更严重的是, 模型论文经常引用排行榜数字, 同时用另一配置评测自己的模型, 最终把不可比的列放入同一张表。

OLMES 因此把“有文档”与“可复现”区分开来。代码公开只是起点, 标准还要固定数据版本、样本处理、提示字符串、示例身份和顺序、计分公式与实现边界。每个决定需要已有研究或消融实验支持。这样的标准允许独立实现得到相同结果, 也允许后续工作明确指出自己偏离了哪条规则及偏离原因。评测从隐含惯例变成有版本的研究对象。

## 两种任务形式与能力阶段的错位

### MCF 测标签选择, CF 测续写偏好

多项选择形式 MCF 将题目和全部选项一起展示, 要求模型预测 A、B、C、D 等答案标签。它与人类答题形式一致, 能自然处理“以上皆是”“以上皆非”和选项间相互指涉。对理解指令和标签约定的模型而言, 这是更忠实的任务表达。然而基础模型可能知道“地核主要由铁组成”, 却不稳定地把知识映射为单字符标签。此时错误混合了知识不足与接口不适配。

完形形式 CF 则把每个候选分别填入句子或答案位置, 计算候选 token 在给定上下文后的条件概率, 再选择得分最高者。它把问题改写为基础语言模型熟悉的续写任务, 对小模型及训练早期检查点更敏感。但 CF 并不等价于原始选择题: 候选彼此不可见, 模型无法利用选项集合的排除关系; 某些候选天然更常见或更短, 原始似然会偏向语言频率而非条件正确性; “以上皆非”被单独代入后甚至失去指称对象。

OLMES 的关键判断不是宣布一种形式永远正确, 而是承认接口与模型能力之间存在阶段性错位。标准以实验结果确定任务级选择, 让较弱模型仍产生有区分度的信号, 同时在模型能够可靠遵循选择格式时保留 MCF 的语义真实性。这样, 训练曲线不会因为早期模型无法输出标签而长期贴近随机线, 最终模型比较也不必永久受限于人工完形改写。

### 形式切换必须是预先规定的规则

如果研究者在看到结果后, 为每个模型挑选分数更高的形式, 就会引入选择偏差。一个模型可能擅长标签输出, 另一个模型可能受益于 CF 的词频结构; 各取最大值会使比较失去共同测量尺度。因此, 混合使用 MCF 与 CF 只有在选择规则与模型结果独立、对所有模型一致执行时才成立。OLMES 的任务级建议和公开配置承担了这一约束。

这也揭示了纵向与横向评测的张力。纵向评测希望同一模型从早期到后期的曲线连续, 横向评测希望不同成熟模型在最贴近任务本义的接口上比较。实际系统可同时保存两条序列: 固定 CF 作为训练诊断信号, 固定 MCF 作为最终任务表现, 并把 OLMES 主指标作为预先声明的汇总标准。重要的不是把所有用途压成唯一数字, 而是让每个数字的测量对象清楚且不可事后改写。

## 提示、示例与概率归一化如何共同作用

### 固定 five-shot 不只是固定数字

“5-shot”并不足以复现评测。还必须知道具体是哪五个样本、来自哪个 split、顺序如何、是否覆盖全部答案标签、是否包含异常文本, 以及目标样本是否可能与示例重复。随机抽取会给每个运行引入额外方差, 对小型测试集尤其明显。OLMES 采用策划并公开的示例, 目的在于让不同模型看到完全相同的上下文, 同时避开依赖随机种子的隐性变化。

策划示例也会带来治理责任。示例不能按待测模型的表现挑选, 否则标准会过拟合参与选型的模型集合; 也不应包含测试答案泄漏或依赖特殊记忆线索。更稳妥的过程是先声明选择准则, 检查格式、标签覆盖与文本质量, 再冻结样例标识。未来新增模型不应触发重新选样; 若数据版本变化必须更新, 应发布新标准版本而不是悄然替换。

提示格式同样需要按字节级细节理解。冒号、换行、选项前缀、答案标签后的空格都可能进入不同 token 边界。对于生成式标签计分, 要明确读取首个非空 token 还是完整字符串, 大小写和附加解释如何处理。对于概率计分, 要明确上下文末尾与答案开头的连接方式。OLMES 将这些看似琐碎的选择纳入标准, 因为可复现性恰恰由这些“小细节”组成。

### 归一化是在消除不同来源的先验偏置

CF 中直接比较候选序列的联合概率会偏爱短答案, 因为每乘一个小于一的 token 概率, 联合概率通常继续降低。按字符或 token 长度归一化可缓和长度效应, 但两者并不完全等价: token 长度受模型分词器影响, 字符长度相对跨模型稳定, 却未必对应语义信息量。若跨架构比较采用 token 平均, 同一文本因分词颗粒不同可能受到不同校正。

PMI 风格归一化试图消除候选本身的常见度。直观地说, 它比较“看到问题后候选有多可能”与“在无信息或通用上下文中候选有多可能”的比值。若候选“the United States”在语言中本来就很常见, 条件概率高并不全来自题目证据; 扣除其先验后, 分数更接近问题提供的增量信息。但校准上下文本身也是配置, 选错空提示或领域提示会引入新的偏差。

因此不存在脱离任务的万能归一化。答案是短标签时, 长度归一化意义有限; 答案是长短差异明显的自然短语时, 不校正容易产生系统偏置; 候选先验差异突出时, PMI 可能更有效。OLMES 通过任务实验形成固定建议, 而不是让评测者对每个新模型试遍方法后报告最高分。这里最重要的方法论是把归一化视为测量定义, 不是提高排行榜成绩的超参数。

## 实验设计与结果应该怎样解读

### 十项任务覆盖广度, 十五个模型检验稳健性

论文选择十个常用多项选择任务, 覆盖科学问答、常识推理、事实知识和社会情境等类型, 包括 ARC-Easy、ARC-Challenge、BoolQ、CommonsenseQA、HellaSwag、MMLU、OpenBookQA、PIQA、SocialIQA 与 WinoGrande。MMLU 又包含多个学科。这个组合并不代表全部语言能力, 但它对应基础模型开发中最常见、成本可控且早期也能产生信号的一类评测。

模型集合覆盖约 1B 到 70B 参数, 包含 Pythia、OLMo、TinyLlama、StableLM、RPJ-INCITE、MPT、Falcon、Llama、Mistral 等不同家族。广泛选模有两层作用: 一是避免标准只适配某个模型族的分词器和训练习惯; 二是观察配置选择是否在弱模型、强模型间产生不同影响。若一种设置只让参与设计的单个模型获益, 它不适合作为公共标准。

解读结果时应关注三类量, 而非只看平均准确率。第一是重复运行和配置扰动下的方差, 它决定小差距是否可信。第二是模型排序稳定性, 因为排行榜的核心用途是比较; 即使平均分变化不大, 排序频繁翻转也说明协议不稳。第三是与模型规模或训练进度的单调关系, 若更成熟检查点反而因格式障碍持续退化, 指标可能没有测到预期能力。

### 标准的结论边界

OLMES 对基础语言模型的多项选择评测给出强约束, 但不能自动推广到对话安全、长文本生成、代码执行、数学证明或检索增强系统。这些任务的输出空间和评分器不同, 还会引入解码参数、工具状态、判分模型和人工偏好等变量。正确的扩展方式是沿用 OLMES 的原则: 列出处理链, 对每个自由度做实验, 冻结有依据的配置, 公开资产并进行版本管理, 而不是直接复制某个选择题模板。

论文的模型范围主要是开放基础模型, 时代背景也决定了它对现代推理模型、长思考输出和聊天模板覆盖有限。聊天模型是否使用 system prompt、是否强制只答标签、如何解析解释后答案, 都需要新增规范。数据污染同样不是固定提示即可解决的问题; 若模型训练中见过测试集, 再可复现的运行也可能高估泛化能力。因此 OLMES 是可信比较的必要条件, 不是充分条件。

## 从论文标准落地为评测治理

### 配置应当成为版本化产物

工程落地时, 最好把每项任务写成可序列化配置, 包含数据集名称与 revision、split、样本过滤规则、提示模板、few-shot 样本 ID 与顺序、MCF 或 CF、归一化公式、分词与空格处理、最大长度、批处理策略、答案解析及指标实现。结果文件同时记录模型 revision、代码 commit、依赖版本和硬件相关设置。这样一个分数才带有足够的谱系信息。

版本号应区分错误修复与测量定义变化。修正不影响样本或得分的注释可以升补丁版本; 更换示例、模板或归一化会改变指标, 应升主版本并避免与旧分数混排。排行榜更新协议后, 应保留旧榜或重新运行全部模型, 不能只让新提交使用新规则。论文表格也应把标准版本写进列名或脚注, 防止“OLMES 分数”在多年后变成含义漂移的标签。

自动检查可以阻止大量静默偏差。例如对渲染后的提示做快照测试, 对每个模型检查标签 token 化, 校验 few-shot 与测试集不重叠, 统计截断样本, 比较两个独立实现的逐题预测, 并保存少量黄金样本的候选对数概率。只比较最终平均分不足以定位问题; 逐题产物允许发现某个实现遗漏前导空格、交换标签或使用错误 split。

### 报告不确定性与偏离项

采用标准并不意味着禁止创新。研究者可以提出更好的提示或校准方法, 但应同时报告标准配置作为锚点, 再把新方法作为清楚标注的实验列。若受上下文窗口、许可证或计算资源限制而偏离, 应列出偏离项及可能影响。这样既保持跨工作可比性, 又不会让标准冻结研究。

对于接近的模型, 应报告任务级分数、样本数和置信区间, 必要时用配对 bootstrap 比较逐题预测。宏平均的一点提升可能集中于单个小任务, 也可能落在抽样噪声内。标准化消除了许多配置方差, 却不会消除有限测试集的统计不确定性。可信结论应同时满足配置一致、实现可审计和差异具有统计支持。

OLMES 最终改变的是评测文化: 分数不再是可以脱离实验上下文搬运的模型属性, 而是一项有输入、有程序、有版本和误差范围的测量结果。对模型开发团队而言, 这使训练曲线可以跨阶段解释; 对排行榜维护者而言, 这提供了协议治理框架; 对论文读者而言, 它让“谁更强”从营销叙事回到可复现实验。其最值得继承的不是某个固定模板, 而是把所有会影响结论的自由度公开、论证并冻结。

### 一套可执行的复现实验流程

复现者首先应冻结论文所用数据与模型 revision, 不要直接调用名称相同但已经更新的在线数据集。随后按照标准提供的样本 ID 重建 few-shot 集合, 对每个目标样本保存最终渲染文本。渲染文本比模板源码更重要, 因为模板引擎版本、换行处理和字段缺失策略都可能让相同模板产生不同字符串。抽取若干样本人工核对题干、选项顺序、答案位置与页内说明, 可以在大规模推理前发现字段映射错误。

第二步是分别验证 MCF 与 CF 的最小单元。MCF 要检查候选标签在目标分词器中是否为单 token, 前导空格是否改变 token ID, 以及计分采用标签首 token 还是标签完整序列。CF 要输出每个候选的原始对数似然、长度、归一化后分数与最终排序。若实现 PMI, 还要保存无条件或校准上下文下的分母项。逐项保存中间量虽增加少量存储, 却能让两个框架之间的差异定位到具体算式, 而不是停留在平均分不一致。

第三步才是全量运行与汇总。运行前锁定精度、最大序列长度和截断方向; 运行后统计被截断样本、解析失败样本与并列候选。对于确定性前向计分, 不应出现由采样温度带来的随机性。若不同硬件或算子导致极小浮点差异, 应比较候选分差是否接近零, 并报告可能翻转的题目数量。最终不仅核对总准确率, 还应核对每个任务和每道题的预测, 因为两个错误可能在汇总中相互抵消。

### 对训练团队和排行榜的不同建议

训练团队可以把 OLMES 配置当作固定探针, 在等量 token 间隔保存检查点并运行同一批任务。由于提示与样例不变, 曲线中的跃迁更可能反映训练数据或优化过程, 而不是评测噪声。任务级曲线还能暴露数据混合变化: 科学问答上升而社会常识停滞, 比单一平均分更有诊断意义。团队若为了速度使用子集, 应固定子集并与完整集定期校准, 不能每次随机抽样后直接连接成曲线。

排行榜面对的是不同提交者和不断演进的模型, 因而要更强调输入验证与公开审计。模型若需要自定义远程代码、特殊聊天模板或非标准 token, 应在结果旁明确标记, 避免把额外适配收益误认为模型能力。排行榜还应公开失败日志和有效样本数, 不应把解析失败悄然当错或丢弃。若模型无法在某种形式上运行, 最诚实的结果是缺失并说明原因, 而不是临时换用更有利的配置。

两种场景共同需要一个标准实现和至少一个独立交叉实现。标准实现保证社区共享锚点, 独立实现则能发现代码库自身的假设。只有当二者在渲染提示、候选分数和逐题预测上接近一致时, “复现”才不只是再次运行同一份代码。OLMES 的开放资产为这种交叉核验提供了基础, 后续维护者需要继续保存历史版本与测试向量。

### 仍需继续研究的问题

首先是标准对模型能力变化的适应机制。随着基础模型更擅长遵循指令, CF 的诊断优势可能减弱; 但若简单地在某个参数规模切换 MCF, 同规模不同训练质量的模型仍会错配。更可靠的方案是设计与目标任务独立的接口能力测试, 预先判定模型是否能稳定输出标签, 然后依据公开阈值选择形式。阈值及测试集也必须冻结, 否则仍会出现事后选择。

其次是跨语言与跨分词器公平性。字符归一化在拉丁文字任务上便于跨模型比较, 到中文、日文或复合字符语言时, 字符与信息量关系会改变。标签字母对英语语料模型自然, 对其他文字体系也可能形成额外先验。多语言 OLMES 应重新研究候选标签、空格规则与长度单位, 不能把英文设置未经验证地视为语言无关。

最后是污染与动态基准。固定公开样例提高可复现性, 也让测试内容更容易进入后续训练语料。维护者可以在保持协议不变的前提下引入受控的新题集, 或采用私有测试和公开校准集相结合的方案, 但必须记录题目版本与访问政策。动态内容不能成为隐藏配置的借口; 出题流程、难度校准和评分程序仍应接受审计。标准化与抗污染并不矛盾, 它们分别回答“怎么测”和“测的题是否仍有效”。

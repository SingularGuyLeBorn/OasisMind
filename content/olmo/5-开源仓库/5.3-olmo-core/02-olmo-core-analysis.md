# OLMo-core 技术解析：把大模型训练拆成可组合、可恢复、可审计的系统

分析对应本地官方快照 `data/sources/OLMo-core/repo` 的提交 `5f6f58a133e7ef577d596295f2c8db4651c27857`. 证据来自 `src/olmo_core/train/trainer.py`, `train/train_module/`, `train/checkpoint.py`, `distributed/`, `data/`, `nn/transformer/`, `src/scripts/official/` 与 `docs/source/guides/`. OLMo-core 持续演进, 提交号把当前实现与未来接口, 外部仓库能力及 README 中尚未落地的规划分开.

## 1. 训练系统的装配层

OLMo-core 的名称容易让人误以为它只是 OLMo 模型的内部实现。固定快照显示，它更准确的角色是“训练构件库”：模型结构、训练步骤、数据加载、分布式网格、checkpoint、回调、评测与启动器都被拆成可替换部件。README 把源码入口指向 `src/olmo_core`，官方模型训练脚本放在 `src/scripts/official`，两者之间形成清楚的边界：库提供机制，脚本给出某个已发布模型所采用的策略组合。

这种边界直接改善可审计性。只看一份巨型训练脚本，研究者很难判断某个参数究竟是模型定义、优化器规则、基础设施默认值还是实验特例；在 OLMo-core 中，模型配置位于 `nn/transformer/config.py`，训练包装配置位于 `train/train_module/transformer/config.py`，Trainer 的循环级配置位于 `train/config.py`，官方脚本负责把这些对象装配起来。配置仍然可能复杂，却至少可以沿类型和构造调用追踪来源。

README 展示了命令行覆盖 `--train_module.optim.lr=6e-3`。这体现了配置树的设计：实验脚本先建立一套有类型的默认配置，命令行再对树中的精确路径覆盖。优点是同一脚本可以表达一族近邻实验，且最终运行参数可被记录；风险则是“脚本文件相同”不代表实验相同，复现时必须同时保存完整展开配置和命令行覆盖项。 OLMo-core 也不试图包办全生态。README 把评测指向 OLMo Eval 与 olmes，把数据预处理指向 Dolma，把常见推理交给 Transformers 和 vLLM。仓库内虽有 beta 生成模块，但训练仍是中心。这个克制的范围说明：复现 OLMo 发布模型需要一条跨仓库证据链，OLMo-core 负责训练执行层，并不自动保证数据构建、评测和部署的一致性。

## 2. Trainer 与 TrainModule：控制循环和数学步骤分离

`train/trainer.py` 中的 `Trainer` 是运行时编排中心。它持有 `TrainModule`、数据加载器、回调集合，以及步数、token 数、epoch 等状态。Trainer 负责“什么时候做什么”：获取 batch、推进训练、触发回调、判断终止、维护状态、协调保存与恢复。它不应知道具体 Transformer 怎样计算 logits、怎样切分参数或怎样调用优化器；这些属于 TrainModule。 `train/train_module/train_module.py` 定义抽象训练模块，Transformer 的普通路径实现在 `transformer/train_module.py`，流水线路径另有 `pipeline_train_module.py`。这样的分层让 Trainer 可以复用于非文本模态或不同模型，只要新的模块遵守训练步骤和状态接口。数据指南也明确指出，可以通过自定义 `DataLoaderBase` 将 Trainer 用于其他模态。换言之，Trainer 面向的是“可迭代、可保存状态的一批输入”和“能执行一步并暴露状态的训练模块”，而不是固定的 token 张量。

TransformerTrainModule 的责任比模型前向更广。配置文件中同时出现数据并行、张量并行、上下文并行、专家并行、activation checkpointing 等配置类型，说明 TrainModule 是把裸模型变成分布式可训练实体的地方。它必须在正确的设备网格上构造或包装模型，协调损失、反向、梯度同步、优化器更新以及混合精度相关行为。把这些放在 TrainModule 而非 Trainer 的意义在于：训练循环可以保持稳定，而并行策略和模型拓扑可以演进。

回调则承载横切关注点。仓库在 `train/callbacks/` 中提供 checkpointer 等回调，使保存、日志、评测或监控不必塞进主循环。回调模式的好处是扩展性和测试隔离；代价是行为分散，事件顺序会影响结果。例如一个回调若在优化器更新前后读取参数，语义完全不同。复现时不能只列“启用了哪些 callback”，还要保留注册顺序、触发间隔和各自状态。

Trainer 的状态并非只有 `step`。可靠恢复需要把训练进度与数据消费位置绑定起来。若模型和优化器恢复到第 N 步，但数据加载器从 epoch 开头重新开始，后续样本序列已经改变；若 scheduler 的内部计数没恢复，学习率轨迹也会分叉。因此仓库让 Trainer、TrainModule、DataLoader 和 callback 各自提供状态，再由 checkpoint 机制统一保存。这里的核心原则是：checkpoint 是整个状态机的快照，而不是一份可以推理的权重文件。

## 3. 相互制约的并行网格

`train/train_module/transformer/config.py` 分别定义数据并行、张量并行、上下文并行、专家并行与流水线并行配置。它们对应不同的切分对象：数据并行复制模型、切 batch 并同步梯度；张量并行在层内切矩阵计算和参数；上下文并行沿序列维切长上下文；专家并行把 MoE 专家分散到设备；流水线并行把层段放到不同 stage。代码把它们拆开，是因为每一维都有独立的通信模式、合法规模和失败条件。

数据并行也不是单一实现。配置中的 wrapping strategy 和 PyTorch 分布式能力表明，系统要区分复制、全分片等路径。全分片可以显著降低单卡参数、梯度和优化器状态占用，却增加聚合与重分片通信，并改变 checkpoint 的 state dict 形态。判断某份配置能否扩展，不能只看 GPU 数；还要看每个并行维度大小的乘积是否与 world size 一致、节点内外网络层次是否匹配，以及 batch 能否被数据并行维整除。

流水线训练有专门的 `pipeline/` 子包，包含 stage、schedule、点对点传输、executor 和 activation offload。这个结构说明流水线不是给普通模块外包一层包装就结束了。它需要明确层到 stage 的分配、microbatch 调度、相邻 stage 的发送接收，以及首尾 stage 对输入和损失的不同职责。调度选择还决定气泡比例和同时驻留的 activation 数量。GPU activation offload 能用主机内存换显存，但同时引入 PCIe 或互联搬运，吞吐收益取决于是否能与计算重叠。

张量并行和上下文并行都降低单卡张量规模，但通信发生位置不同。张量并行通常在注意力或前馈层的投影附近聚合部分结果；上下文并行需要在注意力计算中交换序列块。注意力后端因此不是无关紧要的实现细节。README 把 flash-attn、ring-flash-attn 和 TransformerEngine 列为可选依赖，意味着某个配置声称的后端只有在依赖、GPU 架构和版本组合都满足时才成立。缺少依赖时可能失败，也可能退回不同后端；两者都必须在实验记录中明确。 专家并行又增加 token 路由和 all-to-all。README 指出 dropless MoE 依赖 `grouped_gemm`，并在该依赖特定版本之后才可能免源码编译。这是一条典型的可复现边界：OLMo-core 的 Python 配置可以公开，但性能关键的外部 kernel、编译器和 CUDA ABI 仍会决定实际能否运行。代码开放不等于二进制环境天然可移植。

这些维度组合后，局部正确并不保证整体正确。举例说，某层可做 tensor parallel，不代表它在 pipeline stage 边界和 FSDP 包装顺序下仍有相同参数命名；MoE 的专家并行组也不能随意与数据并行组重合。OLMo-core 的配置类和构建流程承担大量合法性校验，用户不应绕过官方构造器后再把异常吞吐归因于模型。

## 4. Checkpoint：分布式状态、远程存储与恢复语义

`train/checkpoint.py` 定义 `CheckpointerConfig` 与 `Checkpointer`，分布式保存的底层能力位于 `distributed/checkpoint`。源码组织反映出两层职责：训练层决定保存哪些逻辑对象、何时保存以及保留策略；分布式层解决分片 state dict 如何在多个 rank 上写入和读回。checkpointer callback 再把它接入 Trainer 生命周期。 对大模型而言，“rank 0 写一个文件”通常不可行。参数与优化器状态可能本来就以分片形式存在，如果先聚合到单机，不仅额外占用内存，还形成网络与 I/O 热点。分布式 checkpoint 允许各 rank 保存自己的分片，并用元数据描述全局张量。恢复时，若设备网格或分片布局改变，能否重分片取决于底层 state dict 支持和对象命名的一致性，而不是所有 checkpoint 都天然可跨拓扑加载。

README 的退火示例直接从 URL 指向 checkpoint，仓库也包含通用 `io.py` 与文件系统缓存模块。这套设计同时覆盖对象存储、远程路径和本地 POSIX 文件。但远程可读仍不保证原子性。稳健保存必须避免读到半成品：通常需要临时位置、所有 rank 协调完成、末尾发布完成标记或原子重命名。对象存储是否提供强一致语义，需要按具体服务与仓库对应提交的实现分别核对。

一个完整训练 checkpoint 至少涉及模型、优化器、学习率调度、Trainer 计数和数据加载器位置，启用有状态回调时还包括回调状态。随机数状态、梯度缩放器或并行库内部状态是否纳入，也要从实际 state dict 路径核对。仅加载模型参数然后称为“无缝续训”是不准确的；它更接近“以已有权重重新开始一段训练”。官方单独提供 anneal 脚本，也说明阶段切换可能有意改变数据、学习率和优化器设置，不应和故障恢复混为一谈。

checkpoint 的频率是可靠性与吞吐的权衡。间隔过大，故障时损失大量计算；过小则会让训练被存储带宽拖慢。异步保存若存在，还要考虑内存快照何时完成、后台写入失败如何上报以及下一次保存是否覆盖未完成任务。回调让策略可配置，但复现实验必须记录保存间隔、保留数、远程路径、是否异步和恢复点的完整性验证。

## 5. 数据管线：token 流如何变成可恢复的训练顺序

官方数据指南要求先把文本预分词为 token ID 的一维 NumPy 数组，特殊 token 已包含，padding 除外。Dolma 可以生成这种格式。NumPy memmap 可以按区间随机访问大文件，无需把全量 token 装入内存，这才是选择该格式的主要原因。代价是上游 tokenizer、EOS 插入规则、dtype 和文档边界信息必须在预处理阶段固定；训练库无法从纯 token 流恢复丢失的原文语义。

FSL 的最简单策略是 concatenate-and-chunk：把文档连接成 token 流再定长切片。它实现简单、token 利用率高，但带来两个统计语义问题。第一，文档会在样本边界被截断，模型在单个上下文中看不到完整文档；第二，一个样本可以跨多个文档，普通 causal attention 会让后文关注前一篇无关文档。`generate_doc_lengths=True` 配合模型的 `doc_lens`、`max_doc_lens` 可做文档内掩码，解决第二点但不自动修复第一点。

`NumpyPackedFSLDataset` 采用 OBFD 装箱，尽量在不切碎文档的条件下减少 padding。它改善上下文完整性，却需要训练开始前做打包计算；按源文件分别打包便于并行，也会使打包最优性受文件边界限制。`source_group_size` 允许跨相邻文件共同打包，是预处理开销、内存和紧凑度之间的控制杆。长文档仍必须选择截断或切分，这个选择会真实改变训练 token 分布，不能当作无关实现细节。

`NumpyPaddedFSLDataset` 为每篇文档填充到固定长度，从结构上避免跨文档注意，但短文档多时浪费算力。`NumpyInterleavedFSLDataset` 则有意把文档块交错，让相同文档片段在上下文中相距更远，用于训练长距离依赖；它不支持文档内掩码，因为掩码会抵消设计目标。几种数据集产生的 token 数可能相近，学习问题却不同，因此报告“使用同一语料”远远不够。

VSL 路径用 `NumpyVSLDataset` 实现按序列长度的课程。最小和最大长度必须是 2 的幂，同一 batch 内样本长度一致，总 token 数保持为全局 batch 大小。固定 token 预算使不同长度的 batch 在优化器尺度上更可比，但样本条数随长度改变，通信和 kernel 效率也会变化。`VSLCurriculum` 决定不同长度随 epoch 的采样概率，这属于训练配方的一部分，恢复时必须继续原来的课程位置。 自定义 DataLoader 需要满足两项恢复契约: `_iter_batches` 返回当前 rank 的局部 batch, token 数等于 `rank_batch_size`; `state_dict()` 与 `load_state_dict()` 则从 epoch 中断位置继续. loader 若只保存 batch 编号, 没有保存 shuffle seed, 源文件游标, mixture 调度或 packing 状态, 恢复后的数据顺序仍会改变. 公开接口提供了保存这些状态的位置, 第三方 loader 仍需用中断恢复测试验证实现.

## 6. 模型、优化与 kernel 的边界

`nn/transformer/` 把模型配置、block、attention、feed-forward、归一化、RoPE 与模型主体拆开。训练模块再在其外施加并行与优化。这样的层次使同一个裸模型可以在不同并行策略下运行，也让 Hugging Face 转换和生成模块复用结构。然而，配置可组合并不意味着任意组合都经过验证；官方训练脚本仍是确认已发布模型真实配方的优先证据。 activation checkpointing 配置位于 Transformer 训练配置中，它通过重算前向中间值换取显存。它和“训练状态 checkpoint”名称相似，语义完全不同：前者是单步内的计算—显存权衡，后者是跨进程故障恢复的持久化。分析日志或配置时若混用两者，容易误判保存开销或显存来源。

README 列出的 float8 依赖 `torchao`，注意力可选后端依赖 flash-attn、ring-flash-attn 或 TransformerEngine，CuTe kernel 又依赖 QuACK。这些依赖意味着数值与吞吐结论绑定硬件和软件栈。float8 的缩放策略、累加精度、随机舍入以及 kernel 版本都可能影响收敛；注意力后端即使数学上等价，也可能在掩码、dropout、长序列边界或确定性上存在实现差异。因此“相同 OLMo-core commit”只是复现锚点之一，还必须固定 PyTorch、CUDA、驱动、可选库版本和容器摘要。

官方 Docker 镜像包含依赖却不安装 OLMo-core 本包，目的是让开发者挂载频繁变化的代码。这一安排也揭示镜像的证据边界：镜像 tag 不能单独确定训练代码，git commit 也不能单独确定二进制环境。最可靠的实验记录应同时包含镜像不可变 digest、源码 commit、展开配置、启动命令、节点与 GPU 拓扑。 **6.1. 可复现性：仓库开放了什么，又没有保证什么.**

这个快照提供了比单一模型权重更强的复现基础。官方脚本给出模型配置的可执行实例；有类型配置让命令行覆盖可追踪；Trainer、TrainModule、DataLoader 和 callback 的状态接口支持整机恢复；测试、Ruff、mypy 和格式检查降低代码漂移；公开的数据策略文档解释了许多会改变训练分布的选择。提交号 `5f6f58a...` 使上述判断可回到同一份证据。

但仓库没有自动提供完整实验封印。第一，官方训练依赖数据文件与其确切顺序，公开 loader 不等于拿到同一数据快照。第二，Beaker 是 Ai2 基础设施路径，外部用户使用 `torchrun` 时需要自行映射调度、网络和存储。第三，README 明确警告官方镜像可能因硬件、驱动或 CUDA 不同而不可用。第四，部分高性能功能来自外部 kernel 项目，依赖版本与编译选项仍是变量。第五，评测在其他仓库中完成，训练成功不代表评测口径已复现。

因此复现 OLMo-core 实验至少要保存六类材料：源码提交与未提交补丁；容器 digest 和完整依赖锁；展开后的全部配置及命令行覆盖；数据清单、校验和、tokenizer 与混合权重；world size、各并行维度和物理拓扑；起始 checkpoint、保存策略与最终 checkpoint 校验和。若是从远程 checkpoint 继续退火，还应区分它是故障恢复、阶段转换还是仅加载模型权重。

末尾需要区分“可运行”“可续训”和“可复现实验结果”。安装包并跑通小模型证明可运行；故障后数据顺序、优化器和 scheduler 均连续才叫可续训；在相同预算下得到统计一致的损失与下游结果，才接近实验复现。OLMo-core 的架构认真解决了前两层的大量工程问题，也为第三层提供审计入口，但不可能替代数据、硬件和完整实验记录。 **6.2. 阅读源码的推荐路径.** 训练配方的入口位于 `src/scripts/official/`. 实验脚本给出模型, TrainModule, Trainer, DataLoader 和 callback 的实际配置; `train/train_module/transformer/config.py` 定义并行与 activation checkpointing; `trainer.py` 和 callback 决定训练, 日志与保存的时序; 具体 DataLoader 负责采样与状态恢复. 模型模块和可选 kernel 则确定最终数值路径.

这条路径也能防止“能力清单式”误读。仓库中存在一个类，不等于官方模型使用它；README 链接一个后端，不等于当前环境安装了它；配置允许某个并行维度，不等于任意拓扑都通过测试。应始终从官方脚本的实际实例化出发，再用库代码解释机制。 从软件设计看，OLMo-core 把研究训练中常被藏在内部平台里的决策显式化：数据怎样切、状态怎样存、并行怎样组合、阶段怎样启动。它让外部研究者有机会定位差异来自模型、数据还是系统。不过，透明性需要一条可核验链；固定 commit、配置、数据与环境共同存在时，这套构件才真正成为可复现基础设施。

还应把运行日志视为这条证据链的一部分。展开配置回答“计划运行什么”，日志回答“实际运行了什么”：每个 rank 是否加入预期设备网格、有效全局 batch 是否符合配置、数据吞吐和梯度范数是否异常、保存是否由全部分片成功完成，都只能从运行期证据确认。节点故障后的第一次恢复日志尤其关键，它应明确加载的 checkpoint、恢复出的步数和数据位置，而不能仅凭进程重新启动就认定续训正确。对公开复现实验而言，保留机器可读指标、标准输出和依赖清单，比只保存一张最终损失曲线更有价值。

大规模训练中的确定性通常不要求逐位完全相等。大规模 GPU 集合通信、融合 kernel 和浮点归约顺序可能造成微小差异；合理目标通常是状态连续、数据顺序受控，并在预先约定的统计容差内复现曲线。若研究问题本身对微小数值扰动敏感，则应额外启用确定性设置、固定随机种子并记录不可确定算子。OLMo-core 提供组织这些实验的骨架，但容差标准仍需由实验设计者明确。 **6.3. 一次训练由哪些状态定义.** 模型参数只是训练状态的一部分。完整状态还包括优化器动量与方差、学习率调度步、梯度缩放器、数据游标、随机数生成器、累计 token、并行网格和回调内部计数。遗漏任一项，恢复后仍能继续运行，却未必沿原轨迹。

可把训练写成状态转移 $S_{t+1}=F(S_t,B_t)$，其中 $B_t$ 由数据状态生成。checkpoint 要保存足以重建 $S_t$ 的信息。只保存权重相当于从相同模型函数重新开始优化，不是训练继续。 **6.4. step、batch 与 token 三种进度.** optimizer step 统计更新次数，batch 统计样本组，token 统计实际计算量。动态长度、packing和梯度累积下，三者不再固定换算。学习率按 step 调度时，token预算变化会改变每 token 学习率历程。 论文报告训练 token，框架恢复常依赖 step 和数据游标。复现应同时记录三者，并说明 scheduler 分母。仅写 epoch 对流式预训练数据意义有限。 **6.5. Trainer 是状态机.** Trainer 负责初始化、取 batch、前后向、优化、日志、评测与保存。回调在特定事件运行，顺序决定可观察状态。例如 checkpoint 在 optimizer step 前后保存，会对应不同 scheduler 与梯度状态。

理解框架时先画事件序列，再读单个模块。插件若在错误 hook 修改状态，代码类型正确仍可能改变语义。测试应覆盖事件顺序和恢复边界。 **6.6. TrainModule 定义数学步骤.** TrainModule 把模型前向、loss、backward与优化器行为封装，使 Trainer 不依赖具体架构。这个边界利于扩展，也要求模块明确 loss reduction、梯度累积和分布式同步。 两个模块都返回标量 loss，不代表目标相同。token平均、序列平均、辅助损失和 MoE load balancing 都会改变梯度。配置需记录数学定义。 **6.7. 配置是实验的可执行声明.** 配置对象连接模型、数据、优化器、并行、checkpoint和回调。默认值与自动推断同样属于实验。最终运行应导出展开配置，不能只保存用户输入片段。 配置验证可在启动前检查并行维度乘积、batch整除、路径和互斥选项。能运行不代表组合有意义，语义约束需要显式验证。

### 6.1. 配置哈希与资产哈希.

对规范化配置计算哈希能标识运行，但外部数据、模型和容器需单独哈希。路径字符串相同，内容仍可能更新。实验身份应由配置与资产 manifest共同组成。 秘密、临时路径和输出目录不应影响语义哈希；tokenizer revision、数据 shard和kernel开关必须进入。规范化规则也要版本化。 **6.9. 默认值漂移.** 仓库升级后 dataclass默认值可能变化，同一旧配置加载出新行为。向后不兼容声明提示这种风险。复现应使用原 commit解析配置，或把所有默认展开冻结。 迁移工具可比较旧新版展开配置，标出新增和改变项。静默采用新默认会让性能差异无法归因。 **6.10. 数据游标的精确定义

游标可能是 shard索引、样本偏移、token偏移或伪随机采样器状态。多 worker预取后，已读取不等于已训练。checkpoint需定义保存的是消费边界还是加载边界。 恢复时重复少量 batch与跳过 batch各有偏差。唯一 batch ID和消费日志能测量。框架应明确 at-least-once 或 exact语义。 **6.11. shuffle 状态.** 固定 seed 只定义初始随机流。worker数量、分片和恢复位置变化，会改变调用次序。保存 RNG状态与 sampler epoch，仍需匹配拓扑。 流式大数据可使用确定性哈希映射样本到顺序，降低拓扑依赖。代价是动态增删 shard 会重排。数据 manifest必须冻结。 **6.12. packing 改变训练样本.** 多个文档拼入序列减少 padding。若允许跨文档 attention，后文可见前文；block mask则隔离。position id是否重置又影响模型。packing不是纯性能设置。 报告文档边界 token、attention和loss mask。金样本对比 unpacked/packed logits，确认预期语义。数据吞吐提升不能遮蔽目标变化。 **6.13. global batch 的组成.**

global batch = microbatch × gradient accumulation × data-parallel size，在序列数口径下成立。token长度变化时有效 token batch波动。按 token动态batch又改变换算。 扩展数据并行若保持每卡batch不变，global batch增加，需要调整学习率或累计。论文规模结果必须记录实际全局 token。 **6.14. loss reduction 与数据并行.** 各 rank label token不同，先卡内平均再 all-reduce 会让短rank权重过高。全局 token平均需要汇总 loss sum与token count。padding和packing使差异常见。 框架实现应通过不均匀 batch测试。相同数据在1卡和多卡更新接近，是并行语义验收。 **6.15. 数据并行的数学等价条件.** 同步数据并行在相同global batch、loss reduction与随机性下近似单卡大batch。浮点归约顺序、dropout和优化器分片会引入误差。 验证首步梯度与短轨迹，而非要求全程逐位。误差若随步数快速放大，需区分正常混沌与实现bug。 **6.16. tensor parallel 的切分语义.**

TP把线性层权重和激活沿维度分片，需要 collective重建部分结果。head数、hidden维度与TP size通常需整除。切分轴错误会改变模型函数。 单卡与TP前向在容差内一致是基本测试。通信布局影响性能，数学输出应保持。特殊层与词表并行需单独验证。 **6.17. context parallel 的边界.** CP沿序列切分，注意力需要跨rank交换 K/V或统计。causal mask、位置编码和文档边界必须与单卡一致。长上下文下收益明显，通信和负载也增加。 可用短序列对齐 logits，再测试非整齐长度、packing和滑窗。只在最大长度 benchmark吞吐不足以证明正确。 **6.18. pipeline parallel 的气泡与状态.** PP把层分阶段，microbatch流水减少空闲。调度决定气泡、激活驻留和梯度同步时点。不同 schedule在数学上应等价，随机层和归一细节可能造成差异。

checkpoint需知道层到stage映射。恢复到不同PP size时要重分片权重与优化器，框架是否支持必须明确。 **6.19. expert parallel 与路由.** MoE expert按rank分布，token路由触发 all-to-all。负载不均会让慢expert决定step时间，capacity和drop策略还会改变模型输出。 保存路由器参数、expert权重和优化器状态。拓扑变化时映射必须可重建。辅助负载均衡loss属于训练目标，不能当系统细节。 **6.20. 多维并行网格.** DP、TP、CP、PP、EP维度乘积应等于world size，某些维度共享或嵌套。rank到坐标映射决定通信组和checkpoint shard归属。 配置合法不等于高效。节点内优先高带宽通信，跨节点安排低频collective。性能结论绑定硬件拓扑，数学结论需跨网格对齐。 **6.21. optimizer state 的分片.** Adam为每个参数保存一阶、二阶矩和step，体积常大于权重。FSDP/ZeRO分片后，每rank只有局部状态。checkpoint必须用稳定参数标识重组。

模型重命名、层重排或并行度变化会使优化器难加载。只恢复权重可继续，但学习率历史和动量丢失，需标为新优化阶段。 **6.22. scheduler state.** warmup、cosine或linear scheduler依赖当前step和总预算。恢复时只设置step但总steps变化，会改后续曲线。动态延长训练要明确重算还是延续。 论文中的学习率配方包含峰值、warmup token与衰减终点。仓库配置应能映射这些量，不能只引用scheduler名称。 **6.23. 梯度累积边界.** checkpoint若在累积中间保存，需要保留未同步梯度；多数系统只在optimizer边界保存，简化恢复。故障发生中间会重做microbatch。 回调、日志和数据游标也应以optimizer step为事务边界。否则恢复可能重复部分数据却跳过梯度，状态不一致。 **6.24. 梯度裁剪.** global norm裁剪在分片参数上需跨rank汇总平方和。局部裁剪会产生不同更新。混合精度下先unscale再裁剪顺序也关键。

日志记录裁剪前norm和触发率。频繁裁剪可能说明学习率、数据异常或loss尺度问题，而非单纯稳定功能。 **6.25. 混合精度状态.** BF16通常无需动态loss scale，FP16常需要 scaler。FP8还涉及缩放历史与校准。恢复若丢scale状态，初期可能溢出或更新异常。 精度改变也影响论文可比性。吞吐提升与数值误差需分别测，固定短轨迹和最终任务验证。 **6.26. fused kernel 的证据.** 融合attention、optimizer和norm减少访存，可能采用不同数值顺序。启用kernel是系统变量，也可能改变稳定性。版本与硬件架构必须记录。 对齐测试覆盖正常长度、边界长度、mask和反向。只比较速度无法证明等价。回退路径也要测试，避免某硬件静默换实现。 **6.27. deterministic 与高性能.**

确定性算子有时降低吞吐，仍适合小规模回归。大训练可允许非确定性，用多种子与统计容差验证。两种模式服务不同目标。 仓库应支持把关键路径缩到确定性 smoke test，再在性能模式检查分布。宣称可复现不等于逐位相同。 **6.28. checkpoint 原子性.** 多rank并行写 shard，任一失败会留下部分目录。完成标记应末尾写入，加载器只接受完整manifest。远程对象存储不保证重命名原子，需要显式提交协议。 每个shard记录校验和、大小和逻辑归属。目录存在不能证明保存成功。恢复前先验证，再分配显存。 **6.29. checkpoint 一致性点.** 权重、优化器、scheduler、数据和RNG必须来自同一步。异步保存若复制时间不同，会形成混合状态。快照需要在逻辑屏障上捕获。 保存时机写入metadata：前向前、optimizer后或eval后。恢复语义才能与事件循环对齐。

### 6.2. 远程存储缓存.

对象存储下载可落本地cache，键必须含内容哈希。路径同名更新时复用旧文件会恢复错误版本。下载中断使用临时文件，完成后校验。 多节点共享cache提高效率，也要防并发写。manifest是版本真值，本地mtime不是。 **6.31. 异步保存的内存成本.** 后台保存常复制参数，峰值内存增加。直接引用训练张量会在写出期间被更新，破坏一致性。需要不可变快照或版本化buffer。 报告保存暂停、后台带宽和OOM风险。checkpoint频率是可靠性与吞吐的权衡参数。 **6.32. 恢复后的首步检查.** 加载后验证step、学习率、参数抽样哈希、优化器统计、数据batch ID。用固定batch比较中断前后loss，结果应在容差内一致。 再观察首个optimizer更新。能前向不代表动量、scheduler和梯度缩放已恢复。 **6.33. 改变 world size 恢复

换GPU数需要重分片模型、优化器和数据。权重较容易重组，优化器与sampler状态更难。支持范围应由测试证明。 只加载权重并新建优化器属于阶段重启。学习率和数据位置需重新定义，不能称无缝续训。 **6.34. 发布格式转换.** 训练checkpoint面向分片恢复，发布权重面向推理。转换需合并shard、映射key、保存config和tokenizer。固定prompt对比 logits 验证函数一致。 转换脚本、源目标哈希和dtype进入发布记录。量化是额外模型版本。 **6.35. shard manifest.** 数据manifest列URI、哈希、token数、文档数和顺序。数据集名称无法定义具体训练流。缺失或重复shard会改变分布。 启动和恢复都校验manifest。网络失败应中止或明确降级，不能静默跳过。 **6.36. tokenizer 绑定.** 预tokenized ID与tokenizer版本绑定。词表、normalizer或special token变化后，旧ID语义改变。manifest应含tokenizer所有文件哈希。 跨tokenizer相同token预算也不等于相同字符覆盖。论文配方必须绑定该资产。

**6.37. 文档边界.** EOS或separator防跨文档续写。允许跨界attention时它只是软提示；block mask则硬隔离。position reset又是第三选择。 数据处理与模型attention必须一致。边界token冲突、缺失或重复会制造训练伪序列。 **6.38. 去重与权重.** 去重降低记忆与模板放大，也改变来源频率。保留重复可能模拟采样多重性。两种选择都要在数据版本说明。 近重复簇支持审计有效多样性。框架只执行数据流，治理证据来自数据论文和manifest。 **6.39. 数据混合.** 来源可按样本、token或温度采样。经过过滤、长度和packing后，实际token占比会偏离名义比例。日志应记录消费分布。 混合是模型目标的一部分。消融需固定总token，分离内容与额外计算。 **6.40. 课程阶段.** 训练可随step改变数据、长度和学习率。阶段边界进入配置与checkpoint，恢复若错位会读另一分布。

最终能力由完整路径决定，不能只用末阶段解释。论文阶段表要映射具体计划。 **6.41. 数据加载容错.** 坏shard、超时和解析错误若跳过，训练继续但数据变化。严格模式停止，容错模式记录缺失并更新运行manifest。 各rank错误需集体协调，防止死锁与不一致消费。跑完不等于数据完整。 **6.42. 预取队列.** prefetch隐藏IO，增加游标复杂度。checkpoint时队列中的batch是否已消费需要定义，恢复可能重复。 给batch唯一ID并记录optimizer step，可审计重复。性能优化应保持序列可追踪。 **6.43. 训练评测隔离.** 框架可加载任意数据，污染控制来自外部manifest与扫描。仓库支持评测不表示训练数据自动净化。 反复看测试选checkpoint也会适应。开发与最终测试职责需固定并记录。 **6.44. 论文与仓库证据.**

论文说明一次模型实验，源码说明实现能力，配方和日志证明功能启用。源码存在某类不代表论文使用。 解释数字时锁定commit和config。主分支新优化属于新条件，需另行验证。 **6.45. 代际迁移.** OLMo不同代可能换框架、模型模块与并行策略。不能用现版本源码倒推历史实现。release tag与迁移记录是桥梁。 历史实现复刻与现代实现重现实验结论是两种目标。结果应明确选择。 **6.46. 消融口径.** 比较优化器、并行或kernel时，固定数据、global token batch和学习率轨迹。相同token隔离算法，相同墙钟衡量系统产出。 两种口径都可报告，不能把更多token带来的收益归给数学改进。 **6.47. 吞吐与利用率.** tokens/s受长度、packing、精度和硬件影响。MFU依赖理论FLOPs定义，MoE与重计算改变分母。 先数值对齐，再比较性能。注明硬件、拓扑、序列分布和测量窗口。

**6.48. 通信计算重叠.** 异步collective隐藏通信，也带来stream生命周期要求。张量在通信完成前修改会产生竞态，只在规模上出现。 事件同步、校验与压力测试验证。收益绑定互联拓扑。 **6.49. 激活重计算.** activation checkpointing以额外前向换显存。dropout需在重计算中复现RNG，否则梯度不同。粒度影响峰值与吞吐。 用短轨迹对齐启用前后。报告额外计算与支持的序列/模型规模。 **6.50. 编译与图捕获.** 编译减少Python开销，对动态形状、自定义kernel和随机有约束。graph break与fallback会让性能漂移。 记录编译器版本、模式和缓存。功能测试覆盖多长度、保存与恢复。 **6.51. attention 实现.** 标准、Flash与其他融合attention在mask、精度和长序列边界上可能不同。速度改进需验证因果mask、document mask和反向。 固定小张量与参考实现对齐，再做大规模稳定性。论文若指定kernel，版本属于配方。 **6.52. RoPE 与位置扩展.**

位置编码基频、缩放和最大长度定义模型函数。框架支持长上下文开关，不代表任意checkpoint可直接扩大。 训练与推理配置必须一致。扩展实验测不同位置的loss与下游，不只看能运行。 **6.53. 归一化层.** RMSNorm、LayerNorm与低精度kernel有不同数值。epsilon和参数dtype影响稳定。fused版本应与参考对齐。 checkpoint key相同不保证实现相同。架构配置与源码版本共同定义。 **6.54. 参数初始化.** 初始化方差、截断与残差缩放影响早期稳定和缩放。seed固定还需确保并行分片生成同一全局参数。 不同world size初始化后合并权重应一致。否则规模实验混入初始化变化。 **6.55. 优化器实现.** AdamW、Lion或自定义优化器即使名称相同，也可能在bias correction、weight decay顺序和精度上不同。fused实现需核对公式。 论文超参只在对应实现下成立。配置保存完整参数和代码commit。 **6.56. 参数分组.**

bias、norm和embedding是否weight decay，学习率是否分层，决定实际优化。按名称匹配易在重构后变化。 运行时导出每组参数列表与数量。空组或遗漏应报错，不能只看优化器总参数。 **6.57. 梯度统计.** 全局norm、更新norm、参数norm和裁剪率可诊断发散。按层统计揭示局部异常，MoE还需看expert与router。 日志频率过低会漏瞬时尖峰。异常step链接到batch ID，便于数据审计。 **6.58. loss spike 处理.** 尖峰可能来自难数据、数值溢出、坏batch或系统错误。自动跳过会改变数据和优化轨迹。先记录并分类。 若启用回滚或降低学习率，策略写入配方。论文曲线应标故障处理，不能把修复隐藏。 **6.59. NaN 一致处理.** 单rank NaN若其他rank继续，collective可能挂起。检测需全局协调，保存诊断状态并安全终止或回滚。 自动重启应限制次数，避免反复消费同一坏batch。保留batch与kernel信息。 **6.60. 弹性训练边界.**

节点故障后替换资源，需要重建process group、并行网格和数据分配。数学连续性取决于checkpoint与world size支持。 弹性系统提高利用率，不自动保证样本exactly-once。故障统计和恢复差异进入实验记录。

### 回调的状态

 评测、保存、早停和吞吐回调可能有计数、最佳指标和缓冲。若未checkpoint，恢复后触发时点或模型选择变化。 回调要声明state_dict，或明确无状态。第三方扩展尤其需审计。 **6.62. 日志时钟.** 墙钟、step、token与数据epoch是不同横轴。故障停机使墙钟曲线断裂，动态batch使step与token不线性。 保存原始指标后可重绘不同横轴。论文比较收敛通常以token更公平，系统比较用墙钟。 **6.63. 评测触发.** 按step评测在不同token batch实验中不等价；按token触发更适合。评测本身可能阻塞训练或使用不同权重快照。

异步评测要绑定checkpoint哈希，避免分数与训练step错配。选择规则预先确定。 **6.64. 训练损失的可比性.** 不同tokenizer、mask、packing和loss reduction使loss数值不可直接比较。相同模型版本内部曲线才有清晰意义。 跨模型可用bits-per-byte或统一评测集辅助，仍需说明单位。低训练loss不等于更强下游。 **6.65. 验证集泄漏.** 频繁调配方会使验证集成为开发目标。最终报告需独立测试或时间后移数据。开放配方越多，选择适应越强。 保存实验决策记录，说明哪些指标参与选择。文本未进梯度不代表完全独立。 **6.66. 模型规模与系统变化.** 从小模型扩到大模型，往往同时改变并行、batch、学习率和kernel。性能/质量差不能只归参数量。 尽量保持token预算和数据，记录必要系统变化。小规模验证方向，大规模结论仍需直接证据。 **6.67. scaling law 数据点.**

缩放拟合要求训练计算、token和参数定义一致。中途故障、不同数据质量或提前停止会扭曲。框架日志提供原始量，分析需清洗。 误差条和多个种子常被忽略。少量点拟合出的指数不应过度外推。 **6.68. 与 OLMo 开放理念的关系.** OLMo论文强调数据、代码、权重和训练细节开放。OLMo-core把系统层状态显式化，使外部能追踪并行、checkpoint与数据流。 仓库开放是必要条件，具体实验仍需manifest、日志和提交。理念通过证据链落地，而非由公开URL自动完成。 **6.69. 模型论文的算法主张.** 论文若比较架构或优化器，框架要保证其他变量固定。OLMo-core的模块边界便于消融，但配置自由也增加意外差异。 最终表格应附config diff，只显示预期改变项。完整配置供审计。 **6.70. 系统论文的性能主张.**

吞吐提升需同硬件、同模型、同batch与精度测量，包含warmup和稳定窗口。OOM后降低长度的结果不可直接比较。 同时确认loss轨迹与基线一致。性能与正确性两条证据缺一不可。 **6.71. 复现实验的层级.** 接口复现检查构建与一步训练；数值复现检查短轨迹；结果复现检查最终指标；结论复现换环境仍验证方向。不同层失败含义不同。 大型模型可先完成前三层的小规模代理，再决定是否投入全量。报告已达到哪层。 **6.72. smoke test 的内容.** 极小模型、少量真实格式数据、保存恢复一次、多卡一步和评测一步，覆盖核心链。合成数据还应包含边界长度、packing和异常文档。 smoke test不证明规模稳定，却能提前发现配置、shape和状态问题。作为每个配方的最低门槛。 **6.73. 故障注入.**

主动终止一个rank、破坏一个shard、模拟远程超时，验证是否安全失败和正确恢复。只测试正常路径无法证明checkpoint可靠。 故障演练记录重复/遗漏batch、恢复耗时和状态差异。系统可靠性是可测量结果。 **6.74. 依赖锁.** Python锁文件不足以固定CUDA、驱动、NCCL与系统库。容器digest和硬件固件也影响kernel与collective。 完整环境清单可分核心与非语义依赖。安全更新后重跑数值回归，避免永久冻结漏洞版本。 **6.75. 硬件差异.** GPU型号改变精度支持、带宽和kernel选择。相同配置可能fallback或OOM。性能不可外推，数值也可能略变。 记录型号、数量、拓扑、驱动和功耗设置。跨硬件结果用统计容差验证。 **6.76. 许可证与第三方组件.** 仓库许可不覆盖数据、模型权重和所有第三方kernel。THIRD_PARTY_NOTICES提供线索，使用者仍需核对资产。

可运行与可再分发是不同问题。实验manifest应携带许可元数据。 **6.77. 安全的远程加载.** checkpoint和配置可能包含pickle或远程代码风险。来源验证、哈希和受限环境加载很重要。公开科研资产也需供应链防护。 优先使用安全张量格式和显式schema。加载器不应执行未信任配置中的任意代码。 **6.78. 运行输出目录.** 输出目录应含展开config、commit、环境、manifest、日志、checkpoint索引和评测链接。路径名只是标签，metadata才定义实验。 自动生成减少漏项，发布时脱敏内部路径。目录本身成为可移交证据包。 **6.79. 配置继承.** 基础配置叠加实验override很方便，也可能隐藏最终值来源。运行时应展开，并记录每字段来自默认、父配置、环境还是命令行。 覆盖优先级必须稳定。未知字段报错，避免拼写错误被忽略。config diff用于审查预期变化。 **6.80. 环境变量.**

集群启动器常用环境变量覆盖路径、rank和性能开关。它们不在YAML中，却改变运行。白名单式收集相关变量并写日志。 密钥只记录是否配置和版本，不泄露值。调试变量如NCCL设置也影响性能与稳定。 **6.81. 启动器.** 本地、Slurm或云调度器决定rank映射、重试与节点环境。相同Python入口在不同启动器下可能拓扑不同。 保存展开命令、资源请求和节点列表摘要。启动层属于实验，不是外部背景。 **6.82. rank 命名.** global、local、data、tensor和pipeline rank含义不同。日志只写rank 0会遗漏其他维度问题。关键指标按通信组聚合并保留极值。 checkpoint shard命名绑定逻辑坐标，避免物理rank变化后错配。 **6.83. barrier 语义.** 保存、评测和阶段切换需要barrier保证所有rank到达一致点。过多barrier降低吞吐，缺失会读写竞争。 超时诊断记录哪个rank停在哪个事件。简单增加超时不解决状态不一致。 **6.84. collective 超时.**

通信超时可能来自慢IO、OOM或网络。自动重试collective并不总安全，因为部分rank已推进。应回滚到一致checkpoint。 故障日志保留NCCL错误、拓扑和step。系统问题不能被误判为模型发散。 **6.85. straggler.** 单节点慢会拖累同步step。原因可能是硬件、数据读取或负载不均。记录每rank数据/计算/通信时间分位数。 MoE路由和变长序列尤其易产生。优化需保持样本与数学语义，不能只丢慢batch。 **6.86. 动态 batch.** 按token上限装batch提高利用率，序列数随长度变化。loss和梯度应按token正确归一，scheduler预算也用实际token。 恢复需保存装箱状态或确定性重建。不同worker数可能改变batch组成。 **6.87. 序列长度课程.** 先短后长减少早期成本，改变模型看到的位置分布和每step token。学习率与batch需随阶段解释。 对照固定总token与数据，区分系统收益与课程效果。阶段边界写入checkpoint。 **6.88. 激活统计.**

监控激活均值、方差和极值可发现层爆炸、精度问题和坏数据。全量记录昂贵，可周期抽样。 统计实现不能阻塞或改变图。异常关联step和batch，支持复盘。 **6.89. 参数更新比.** $\|\Delta\theta\|/\|\theta\|$ 展示实际更新尺度。loss正常但更新异常可能来自lr、scaler或裁剪。 按层和参数组观察，比较不同规模。它比只看学习率更接近优化强度。 **6.90. 优化器状态精度.** 动量用FP32、BF16或量化存储会改变内存与收敛。分片与offload也影响吞吐。配置需明确。 恢复时不能把高精度状态静默降级。短轨迹和最终loss验证压缩方案。 **6.91. CPU offload.** 优化器或参数offload节省GPU显存，增加PCIe/网络传输。吞吐依赖硬件，数值应保持。 checkpoint可能直接从CPU状态写出，也需一致点。性能报告包括主机内存和带宽。 **6.92. 参数 tying.**

输入embedding与输出头共享时，分片和checkpoint必须保持别名。加载后复制成两份会改变优化器更新与内存。 验证存储共享和logits一致。转换发布格式也要保留或明确解除。

# RewardBench: 奖励模型到底学会了怎样的偏好

RewardBench 是 Ai2 与华盛顿大学团队在 2024 年发布的奖励模型评测工具和数据集, 论文为 arXiv 2403.13787 (逐段译文见 [RewardBench 对照译稿](./rewardbench-bi.md)). 它要求奖励模型在同一提示词的两个答案中, 把人工核验的较好答案排在前面, 不评测聊天模型的生成质量. 数据、推理代码和逐样本分数均公开, 论文版本评测了 80 多个模型, 覆盖序列分类器、定制成对分类器、DPO 模型和生成式裁判.

这项工作的出发点是一个长期不对称: 预训练模型和完成 RLHF 后的策略模型有大量公开基准, 位于两者之间的奖励模型却常用训练数据自带验证集评估. 这些验证集会混入标注者分歧, 也可能和奖励模型训练数据同源. RewardBench 改用有明确错误、指令偏离、安全边界或代码缺陷的成对答案, 让“为何选这一条”尽量可以核对. 它回答的是奖励模型的判别能力, 不是完成一次 PPO 或 best-of-N 后的最终收益.

## 1. 成对排序怎样变成一个基准

### 1.1. 一个样本只有三项

每个样本包含提示词 $x$、较优答案 $y_c$ 和较差答案 $y_r$. 对能单独给答案打分的奖励模型 $r_\theta$，判对条件是

$$
r_\theta(x,y_c)>r_\theta(x,y_r).
$$

子集准确率就是满足该不等式的样本比例. 二分类随机基线为 50%. 这里不要求不同提示词之间的奖励值可比, 只比较同一个提示词下两个答案的相对顺序. 因而一个模型即使输出全部落在很窄的区间, 仍可能有高准确率; 反过来, 奖励绝对值很大也不说明排序正确.

严格的大于号还意味着并列不算正确. 这对量化模型、低精度推理或输出离散等级的生成式裁判尤其重要. 若两个答案得到相同分数, 基准没有用随机规则替模型决定胜负. 工程复现时需要固定聊天模板、截断方式、数值精度和答案拼接位置, 因为这些细节都会改变用于比较的标量.

训练奖励分类器常用 Bradley-Terry 形式的成对损失. 令分差为 $\Delta=r_\theta(x,y_c)-r_\theta(x,y_r)$, 单样本损失可以写成

$$
\mathcal{L}_{RM}=-\log \sigma(\Delta).
$$

当较优答案的分数高于较差答案时, $\Delta$ 为正, 损失减小. RewardBench 没有重新训练这些模型, 但它的准确率正好检查训练目标要求的排序关系是否能迁移到新样本. 准确率不关心 $\Delta$ 是 0.01 还是 10, 所以它不能衡量奖励间隔是否适合 PPO, 也不能检验奖励尺度在不同提示词上是否稳定.

### 1.2. 五个分区不是简单平均所有样本

基准把数据分为 Chat、Chat Hard、Safety、Reasoning 和 Prior Sets. 前四个分区构成 RewardBench 新整理的核心数据: Chat 358 条, Chat Hard 456 条, Safety 740 条, Reasoning 1,431 条. Prior Sets 汇集 Anthropic Helpful、Anthropic HHH、SHP 和 Learning to Summarize, 共约 17,200 条. 若直接对全部样本求平均, 旧偏好集会压过规模较小但更有诊断价值的新分区.

RewardBench 先在分区内部聚合. Chat、Chat Hard 和 Safety 按各子集样本数做逐提示词加权; Reasoning 提高 PRM Math 的权重, 使数学与六种编程语言总体各占一半; Prior Sets 因子集规模差距很大而采用子集等权平均. 最终总分再平均各分区, 其中 Prior Sets 只有其他分区一半权重. 因此排行榜总分不是“全部答对数除以全部样本数”, 自己实现时若忽略这套权重会得到不同排序.

这套设计让每个分区代表一种能力, 代价是权重含有人为判断. 数学和代码各占一半, 或旧偏好集只取半权, 都不是从统计分布自动推导的结论. 阅读总分时应同时看五个分区; 两个总分相近的模型可能一个擅长安全边界, 另一个依赖 Chat 简单集拉高平均值.

## 2. 四类核心数据各自卡住什么能力

### 2.1. Chat 从明显质量差开始

Chat 使用 AlpacaEval 和 MT-Bench 的答案对. AlpacaEval Easy 有 100 条 GPT-4 Turbo 与 Alpaca 7B 的比较; AlpacaEval Length 有 95 条平均长度受到控制的答案; AlpacaEval Hard 有 95 条 Tulu 2 DPO 70B 与 `davinci-003` 的比较. MT-Bench Easy 选择评分 10 对 1 的 28 组答案, Medium 选择 9 对 2–5 的 40 组答案. 这些样本主要检查奖励模型能否识别完整、正确且遵循指令的开放式回答.

Easy 子集的答案质量差距大, 很多模型接近满分, 它更像基本功能测试. Length 子集刻意让较优答案与较差答案平均长度接近, 防止模型只用“更长通常更好”这一捷径. 论文观察到它比其他简单 Chat 子集更难, 但仍有十多个模型超过 90%, 说明部分奖励模型不依赖明显长度差也能判断内容. 这并不证明长度偏置已经消失, 因为它只在这批成对样本上移除了一个容易利用的相关性.

### 2.2. Chat Hard 把表面风格变得相近

Chat Hard 包含 37 条 MT-Bench Hard, 其答案评分分别为 7–8 与 5–6, 差距比 Easy 小. 其余来自 LLMBar: Natural 100 条, Adversarial Neighbor 134 条, GPTInst 92 条, GPTOut 47 条, Manual 46 条. 对抗样本常让两个答案拥有相似长度和流畅度, 但其中一个回答了邻近问题、遗漏关键限制或被轻微改写成不符合原指令的内容.

这一区分开“像好答案”和“确实回答当前问题”. 如果两个候选都由相近能力的模型生成, 文风、格式和礼貌程度无法直接给出标签, 奖励模型必须比较提示词中的对象、条件与答案事实. 论文结果显示 Chat Hard 与总体表现关系紧密, 也有少数 DPO 模型在此处较强而总分一般. 因此它是重要诊断项, 但不能单独替代其他分区.

### 2.3. Safety 同时惩罚漏拒和误拒

Safety 不是把拒答一律当成好答案. Refusals Dangerous 与 Refusals Offensive 各 100 条, 要求偏好拒绝危险或冒犯性请求的答案. XSTest Should Refuse 有 154 条应拒问题; XSTest Should Respond 有 250 条带敏感触发词但应正常回答的问题; Do Not Answer 有 136 条不应提供实质回答的请求. 两个方向同时存在, 才能区分安全性不足和过度拒答.

论文观察到三种模式. 有些模型主要学习 helpfulness, 在 Should Respond 上高分, 遇到真正危险请求却偏好直接回答. 有些模型加入了安全偏好, 同时能识别 XSTest 中的无害陷阱. 还有些模型对触发词过敏, 应拒集合表现好, Should Respond 却低分. 单看 Safety 平均值仍可能遮住第三种问题, 所以部署前要分别查看应拒和应答子集.

奖励模型的 Safety 分数也不等于完整系统安全性. 生成系统可能在奖励模型之外使用输入审核器、输出分类器或规则过滤. 若奖励模型本来只负责 helpfulness, 用它单独回答安全分区未必公平; 反过来, 一个安全分区高分的奖励模型也不能替代对生成策略和系统级防护的测试.

### 2.4. Reasoning 用微小错误检查精确判别

Reasoning 的 PRM Math 有 447 条, 把参考答案与带错误的模型答案配对. 代码部分来自 HumanEvalPack, C++、Go、JavaScript、Java、Python 和 Rust 各 164 条, 较优答案为正确实现, 较差答案包含已知 bug. 许多代码对只相差一两个 token, 这让单纯看流畅度或格式几乎无效.

该分区成绩从约 35% 到 97% 平滑分布. 低于随机不只是“不懂代码”, 还可能表示模型稳定偏爱某种表面形式, 而这种形式恰好与错误答案相关. 高分则说明模型能从细小差异中恢复正确顺序, 但不能推出它能生成证明、运行测试或定位任意程序缺陷. 数据格式本身也可能带来伪相关: 数学参考答案与模型生成错误在措辞上可能不同, 奖励模型可能识别来源风格而不是重算推理.

## 3. 三种奖励接口怎样放到同一张表

### 3.1. 序列分类器直接读取标量

标准奖励模型通常在语言模型顶部加一个标量头. 把提示词和候选答案按模型训练时的模板拼接, 前向一次即可得到 $r_\theta(x,y)$. 对 chosen 和 rejected 分别计算, 再比较大小. PairRM 等定制分类器原本接受一对答案, RewardBench 按各自官方接口执行成对判断, 而不是强行把所有模型改造成同一种网络结构.

模板匹配很关键. 有的奖励模型训练时要求系统消息, 有的在最后一个 token 上取分, 有的使用特定 BOS、EOS 或角色标记. 同样文字换一种模板可能改变分数. 基准代码的价值之一就是把这些模型专用处理集中起来; 复现实验不应只下载权重后用任意 tokenizer 默认模板运行.

### 3.2. DPO 模型的奖励必须减去参考模型

DPO 训练不一定保存独立奖励头, 但其推导给出隐式奖励. 对策略模型 $\pi_\theta$、参考模型 $\pi_{ref}$ 和缩放系数 $\beta$, 可以写成

$$
r(x,y)=\beta\left[\log \pi_\theta(y\mid x)-\log \pi_{ref}(y\mid x)\right].
$$

实际排序只需要比较两个答案, 与提示词有关的常数会抵消. 排序取决于策略模型相对参考模型把该答案概率提高了多少, 而非策略模型自身给答案的似然. 一个常见误用是直接拿 $\log\pi_\theta(y\mid x)$ 排序, 这会把语言流畅度、长度和基座模型先验混进奖励, 失去 DPO 隐式奖励的定义.

RewardBench 专门比较有无参考模型. Mixtral-8x7B-Instruct 使用参考模型时核心四区平均为 82.2, 无参考时为 64.2, 相差 18.0 分; Tulu 2 DPO 13B 从 78.8 降到 62.9; Zephyr 7B Alpha 从 78.6 降到 65.6. 多数模型下降集中在 Chat Hard 和 Safety. 个别 Reasoning 列反而上升, 说明错误的打分方式可能偶然利用某个分区的格式相关性, 不能据此把参考模型省掉.

$\beta$ 若对同一模型的所有样本固定为正数, 不改变两答案排序, 所以准确率对其数值不敏感. 参考模型则不能省略, 因为它逐 token 改变似然差. 复现还要按答案 token 求条件对数概率, 不能把提示词 token 的似然一起累计; 对不同长度的回答是否求和或归一化也要遵循原实现.

### 3.3. 生成式裁判需要把自然语言变成判决

生成式模型可以通过提示词被要求选择 A 或 B、输出等级, 甚至先解释再判断. 它比标量分类器每样本生成更多 token, 还会受裁判提示词、答案顺序和输出解析影响. RewardBench 报告生成式模型结果, 但论文主张最好的分类器仍高于最好的生成式奖励模型. 这不是两类方法在所有场景的最终结论, 因为生成式裁判可以利用更长推理, 分类器则以低成本提供单个分数.

将生成式裁判与分类器放在同一准确率表中, 比较的是最终 chosen/rejected 顺序, 不是推理成本、校准或稳定性. 若模型交换 A/B 顺序后改变判断, 单次准确率看不出来. 若裁判给出正确选择但解释包含事实错误, 基准也只计选择. 因而生成式裁判还需要位置偏置、重复采样和解释质量等补充检查.

## 4. 排行榜显示了哪些规律

### 4.1. 高总分来自困难分区而不是简单 Chat

论文快照中 ArmoRM-Llama3-8B-v0.1 总分 89.0, Chat 为 96.9, Chat Hard 为 76.8, Safety 为 92.2, Reasoning 为 97.3, Prior Sets 为 74.3. Pair Preference Model Llama3 8B 总分 85.7; FsfairX-LLaMA3-RM-v0.1 为 83.6. 多个模型的 Chat 已超过 96, 差异主要来自 Chat Hard、Safety 和 Reasoning.

规模通常有帮助, 但不构成单调定律. Starling-RM-34B 得到 81.4, Tulu 2 DPO 70B 得到 76.1; 同系列 Llama 2 DPO 模型随规模增大整体改善. Qwen 1.5 系列则没有稳定单调提升, 作者把它与分布外泛化困难联系起来. 比参数量更大的影响还包括基座能力、SFT 数据、偏好数据过滤和奖励模型训练形式.

论文中的榜单是 2024 年模型快照, 不应当作今天的永久排名. 它更有价值的部分是分区差异和统一推理接口. 新模型若只报告总分, 仍无法知道提升来自对抗指令、精确推理还是安全边界; 若训练数据包含 AlpacaEval、MT-Bench 或 RewardBench 样本, 排名还可能受污染.

### 4.2. 相似训练方法会被数据过滤拉开

Zephyr Alpha 与 Beta 都以 Mistral 7B 为基座并在 UltraFeedback 上做 DPO, 主要差异是偏好数据过滤. Alpha 移除了拒答样本, Safety 表现更高而 Chat 更低. 这看似反常, 但 Safety 同时包含 Should Respond: 减少无条件拒答倾向会改善其中较大的应答子集, 同时可能改变普通对话偏好.

Tulu 2 DPO 7B 与 Zephyr 类模型使用不同基座前 SFT 数据. 论文观察到它在 Chat Hard 和 Reasoning 上退步, Safety 上改善. 这些对照说明“都用了 DPO”不足以预测奖励行为; DPO 只规定优化形式, 真正被放大的偏好来自参考策略、SFT 起点和成对数据.

### 4.3. 奖励分布形状不能从准确率推断

作者公开逐文本分数并绘制 chosen/rejected 分布. 不同奖励模型的数值范围、中心和形状差异很大; 很少呈高斯分布, 更少以零为中心, 受测模型中没有一个是居中的高斯. 两个模型即使 RewardBench 准确率相同, 分差尺度也可能完全不同.

这一点关系到下游 RL. PPO 使用奖励幅度计算优势, 对离群值和尺度敏感; best-of-N 主要使用同一提示词内的排序, 对单调变换更稳健. RewardBench 的二元准确率更接近后者需求. 若要挑选 PPO 奖励模型, 还应检查分数校准、长度相关、分布尾部、跨提示词可比性以及策略优化后是否出现 reward hacking.

## 5. 怎样使用它而不误读

### 5.1. 高准确率不是下游训练收益的证明

RewardBench 明确把“基准表现是否与 RLHF 实际效用相关”列为未解决问题. 一个模型可以准确识别静态答案对, 却在策略逐步偏离训练分布时给出可利用的漏洞. PPO 会主动寻找高奖励区域, 这与从固定数据集中做判别不同. best-of-N 也只在采样候选范围内排序, 候选分布变动后结果可能改变.

合理流程是把 RewardBench 当成进入下游实验前的单元测试. 先排除在 Chat Hard、Safety 或 Reasoning 上明显失效的模型, 再用目标策略生成的候选做人工核验, 最后运行 best-of-N 或小规模 RL 试验. 若目标场景是代码、安全或特定领域, 还应向工具包加入自己的成对审计集, 而不是只追求公共总分.

### 5.2. Prior Sets 有噪声也有同源风险

旧偏好测试集的标注者一致率常把可达到准确率限制在约 60% 到 70%, 且任务定义不如核心子集明确. UltraRM-13B 和 PairRM-hf 等模型在 Anthropic HH、SHP 与 Learning to Summarize 的训练划分上训练过, 在相应测试集上高分可能包含同源分布优势. Starling 等未使用这些训练划分的分类器也能获得高分, 所以不能把所有结果都归为泄漏, 但比较时必须记录训练数据来源.

DPO 模型在 Prior Sets 上普遍偏低, 也不必直接解释成 DPO 整体较差. 可能原因包括参考模型、答案长度、聊天模板、偏好数据分布和旧测试集噪声. RewardBench 已将这一分区权重减半, 仍保留它是为了和既有奖励模型论文接轨. 实际选型时, 核心四区与目标域数据通常比 Prior Sets 单项更有诊断价值.

### 5.3. 长度控制只移除一种捷径

作者尽量让 chosen 与 rejected 长度接近, 或让 chosen 更短, 以避免“长答案得高分”. AlpacaEval Length 进一步固定平均长度. 但是奖励模型还可能利用格式、来源模型口吻、拒答模板、代码注释量或参考答案常见措辞. Reasoning 中“人工参考对 buggy 模型回答”的构造尤其可能包含来源差异.

检查捷径需要超出一次排行榜运行. 可以交换答案顺序, 截去共同前缀, 匹配长度, 改写表面风格, 或在保持事实标签不变的前提下替换格式. 若分数大幅变化, 模型学到的可能是数据集特征而非目标偏好. RewardBench 提供结构化起点, 不是完成了全部因果诊断.

### 5.4. 安全数据包含敏感文本

Safety 分区的 rejected 答案可能直接包含危险或冒犯内容. 数据公开有利于复现实验, 也意味着下载、浏览和记录逐样本输出时要采用与敏感语料相匹配的权限和展示策略. 论文认为既有提示词不太可能引出个人身份信息, 但仍提醒用户自行承担接触这些文本的风险.

在系统评估中, 应把负责输入审核、生成、奖励排序和输出过滤的组件分开测试. 一个外置安全分类器可以补偿主奖励模型的某些缺口, 也可能制造新的误拒. RewardBench 的分区恰好可用于定位责任: Should Refuse 检查拦截, Should Respond 检查过度防守, Chat Hard 与 Reasoning 检查安全模块之外的答案质量.

## 6. 一个可复现的工程读法

运行 RewardBench 前先确认模型类型. 序列分类器应使用发布者指定的聊天模板与取分位置; 成对分类器应按原生双答案接口; DPO 模型必须找到训练时参考模型; 生成式裁判则要固定裁判提示词、候选顺序和解析规则. 然后保存每条样本的两个原始分数, 不只保存最终准确率, 这样才能分析并列、极端值、长度相关和分区错误.

汇总时先复算每个子集, 再按论文规则得到分区和总分. Reasoning 的数学/代码再加权、Prior Sets 的子集等权和最终半权最容易实现错误. 比较模型时同时报告模型版本、权重提交、tokenizer、精度、最大长度、截断侧、参考模型与模板. 若答案被截断, 得分变化属于推理配置问题, 不能归因于奖励模型能力.

最后抽查错误样本. Chat Hard 中看模型是否偏爱风格相似但答非所问的答案; Safety 中把漏拒与误拒分开; Reasoning 中确认差异是否真的落在 bug 或推导错误; Prior Sets 中记录模型是否见过同源训练数据. 这种逐类检查比只看排行榜名次更接近 RewardBench 的设计目的.

RewardBench 把原本隐藏在 RLHF 管线中的判断器变成可以单独审查的对象, 它给出的排名不应被当作永恒顺序. 成对准确率让多种模型接口获得统一出口, 困难分区暴露表面质量与真实正确性之间的差距, DPO 对照说明参考模型是奖励定义的一部分, Safety 双向测试则区分保护不足与过度拒答. 它仍未回答哪个奖励模型能训练出最佳策略, 但已经把这个问题拆成一组可复现、可扩展、能定位失效原因的检查项.

数据集采用 ODC-BY 许可, 代码采用 Apache 2.0 许可. 公开逐样本分数使后续研究能够复算聚合结果, 也能在不重新运行全部大模型的情况下检查奖励分布和错误类型.

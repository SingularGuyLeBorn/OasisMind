# RLVR 范式与 DeepSeek-R1 案例

RLVR 是 Reinforcement Learning with Verifiable Rewards 的缩写. 它指一类奖励能够由规则, 执行器, 求解器或环境状态自动核验的强化学习设置. 数学题可以检查最终答案, 代码题可以运行测试, 形式证明可以交给 proof checker, 棋局和仿真任务可以读取环境结果. 核心条件是同一评测协议面对同一候选输出时, 能够稳定地产生可重复的判定.

RLVR 描述奖励来源, 不指定唯一优化算法. REINFORCE, PPO, GRPO(1.3.1.1 节) 或其他 policy-gradient 方法都可以消费可验证奖励. DeepSeek-R1 是这一方向最有影响力的案例之一, 却不等于 RLVR 的全部. R1 的结果来自 base model, 数据, 采样, verifier, 格式约束, GRPO, 多阶段 SFT 与后续对齐的组合, 单独复制一种奖励或 `<think>` 标签无法复现整个系统.

## 1. 什么样的奖励可以验证

一个 verifier 可以写成 $v(x,y,e)\to(r,m)$, 其中 $x$ 是任务输入, $y$ 是模型输出, $e$ 是评测环境, $r$ 是奖励, $m$ 是诊断元数据. 元数据至少应包含解析结果, 正确性, 运行状态, 超时, 失败类型和 verifier 版本. 只返回一个浮点数会丢掉训练异常的来源.

"可验证"强调结果能按协议复算, 不意味着协议一定正确. 答案解析器可能漏掉等价表达, 测试集可能覆盖不足, 浮点容差可能过宽, 沙箱可能泄漏隐藏信息. Verifier 仍然是一段需要测试, 版本化和审计的程序.

### 1.1 规则与答案匹配

数学短答案常把输出规范化后与标准答案比较. 整数和有理数可以精确匹配; 代数式可以借助符号化简检查等价性; 数值答案需要规定绝对或相对误差. 多选题可以抽取选项字母, 但必须防止输出中出现多个候选答案时解析器随意取最后一个.

答案匹配的难点在表示. $1/2$, $0.5$ 与 $50\%$ 语义相同, 字符串却不同. 方程 $x^2=1$ 的答案可能写成 $x=\pm1$, 集合 $\{-1,1\}$ 或两行推导. 一个可靠 parser 会先限制可接受语法, 再规范化, 最后比较. Parser 失败应单独记为 `parse_error`, 不能静默并入错误答案, 否则无法区分模型不会做题和格式不兼容.

规则 verifier 也可以检查输出格式, 例如是否含指定标签, JSON 能否解析, 是否在 token 预算内. 这类格式奖励容易计算, 但只代表协议遵循. 任务成功率必须由 correctness 字段统计, 不能用 total reward 大于 0 代替, 因为错误答案也可能拿到格式分.

### 1.2 执行器, 单元测试与环境结果

代码任务把候选程序放进隔离环境, 编译并运行测试. Binary reward 可以是全部测试通过记 1, 否则 0; dense reward 可以使用通过测试比例, 编译成功, 运行时间或内存约束. Dense 信号更容易学习, 也更容易被不均衡测试权重利用.

测试通过只证明覆盖到的行为正确. 若 hidden tests 漏掉空输入, 溢出或复杂度边界, 一个针对公开样例硬编码的程序也能得高分. 沙箱必须限制文件, 网络, 进程, 时间和内存, 每次运行还要使用干净状态. 非确定性并发程序需要重复执行或固定随机种子, 否则同一输出会收到不同奖励.

环境任务可以直接读取终局状态, 例如游戏胜负, 定理证明是否被 kernel 接受, 机器人是否到达目标. 这类 verifier 通常比自然语言 judge 更接近任务本身, 但仍受模拟器精度, 环境漏洞和 reset 状态影响. 可验证的是定义好的环境目标, 不自动等于现实世界的完整成功.

### 1.3 形式证明与过程检查

形式证明系统用小型可信 kernel 检查 proof term 是否满足定理. 只要公理, 定义和 kernel 固定, 判定可以高度可靠. 模型需要生成语法正确并能通过类型检查的证明, reward 可以是最终通过, 完成子目标比例或证明长度等组合.

过程 verifier 试图评价推理中间步骤. 若每一步都能由符号规则, 代码执行或证明器验证, 它仍属于可验证奖励. 若步骤由另一个语言模型判断"合理", 信号更接近 learned reward 或 process reward model, 可重复性与可攻击面都不同. RLVR 的边界应按验证机制区分, 而不是看到逐步推理就自动归类.

可验证域的共同点是存在外部语义. 数学答案, 编译器, proof kernel 和环境状态都不依赖模型自己声称成功. 开放式写作, 审美, 事实综合和复杂帮助性通常缺少完整程序判定, 需要人类偏好或 learned judge 补充. 一个训练集可以混合多类奖励, 但应保留每类来源, 不能把统一后的标量当作同质证据.

## 2. 从 rollout 到参数更新

RLVR 的训练循环可以概括为五步: 采样任务, policy 生成多个候选, verifier 给每个候选打分, 奖励转成 advantage, 优化器更新 policy. 每一步都改变信号分布. Prompt 难度决定成功概率, sampling temperature 决定候选多样性, verifier 决定什么算成功, advantage 决定同组样本怎样比较.

用 $x_i$ 表示第 $i$ 个问题, 对每题采样 $G$ 个回答 $y_{i,1:G}$. 生成时应保存 policy version, sampler version, token ids, completion mask, 实际行为分布下的 log-prob, temperature, top-p, max tokens, stop reason 和 sample id. Verifier 返回 correctness, format, error type 与 total reward. 这些字段是后续复算的最小数据血缘.

### 2.1 采样分布决定训练看见什么

令 $q_{old}^{T,p}$ 表示对 $\pi_{old}$ 的 logits 做 temperature 缩放、top-p 截断并重新归一化后的实际行为分布. 策略按

$$
y_{i,j}\sim q_{old}^{T,p}(\cdot\mid x_i;L)
$$

生成回答, 其中 $T$ 是 temperature, $p$ 代表 nucleus sampling 设置, $L$ 是长度上限. 同一 policy 在不同采样参数下会产生不同成功率与多样性. Temperature 太低, 组内回答高度相似, 容易全对或全错; 太高则大量样本语法损坏, verifier 信号浪费在低级错误上. 若 $T\ne1$ 或 $p<1$, rollout 必须保存实际 $q_{old}^{T,p}$ 下的 old log-prob; 只保存未变换 $\pi_{old}$ 的 log-prob, 后面的 ratio 就不再是行为分布的重要性比.

Prompt sampler 也需要控制难度. 若任务几乎全能答对, advantage 缺少区分; 若几乎全错, reward 仍然稀疏. Curriculum 可以把一部分预算放在当前成功率中间区域, 同时保留较难样本监测能力边界. 只追逐已有非零 reward 的题目会产生选择偏差, 模型可能在窄分布上进步而放弃困难区域.

生成长度上限同时影响推理空间和成本. 上限增加可能让模型有更多机会完成长推导, 也会增加重复, 绕路和 verifier 攻击面. 比较不同训练配置时要报告总生成 token, 不能只固定 prompt 数. $G$ 与平均长度同时翻倍, verifier 和训练计算会接近四倍增长.

### 2.2 奖励组合与组内优势

设 correctness reward 为 $c_{i,j}\in\{0,1\}$, format reward 为 $f_{i,j}$, 其他规则项为 $q_{i,j}$. 总奖励可以写成

$$
R_{i,j}=w_c c_{i,j}+w_f f_{i,j}+w_q q_{i,j}.
$$

各项必须分别记录. 若 $w_f>0$, 一个答案错误但格式正确的样本可能有正总分. 因而 pass rate 应用 $c$ 统计, format compliance 用 $f$ 统计, 训练 total reward 再用 $R$ 统计.

GRPO 常在同题的 $G$ 个回答内标准化:

$$
\bar R_i=\frac1G\sum_{j=1}^GR_{i,j},
\qquad
s_i=\sqrt{\frac1G\sum_j(R_{i,j}-\bar R_i)^2},
$$

$$
\hat A_{i,j}=\frac{R_{i,j}-\bar R_i}{s_i+\varepsilon_A}.
$$

这让回答与同题候选比较, 降低不同题目奖励尺度的影响. 若组内全对或全错, $s_i=0$, 安全分母使所有 advantage 为 0. 这组 rollout 不提供相对 policy signal, 却仍消耗生成和验证预算. 零方差组率因此是 RLVR 的关键诊断.

当 $q_{i,j}$ 由多个来源组成时, 组合顺序影响梯度结构. 先把各奖励加和成 $R_{i,j}$ 再做组内归一, 两组奖励组合不同的样本只要总和相同就会被压成相同 advantage, 例如「正确但缺少格式分」与「错误但有过程分」可能落在同一标准化水平, 梯度无法区分它们. GDPO(1.3.2.4 节) 把归一移入每个奖励分量内部, 先逐项标准化再聚合, 保住奖励组合的区分度. 奖励分量越多, 先加和再归一丢失的信息越多, 多奖励 RLVR 应优先评估逐项归一的方案.

### 2.3 Policy update 与 reference KL

以 clipped policy update 为例, 当前 policy 相对 rollout policy 的 token ratio 为

$$
r_{i,j,t}(\theta)=
\frac{q_\theta^{T,p}(y_{i,j,t}\mid x_i,y_{i,j,<t})}
{q_{old}^{T,p}(y_{i,j,t}\mid x_i,y_{i,j,<t})}.
$$

Policy surrogate 可写为

$$
L=\frac1B\sum_{i=1}^{B}\frac1G\sum_{j=1}^{G}
\frac1{|y_{i,j}|}\sum_{t=1}^{|y_{i,j}|}\left[
\min(r_{i,j,t}\hat A_{i,j},
\operatorname{clip}(r_{i,j,t},1-\epsilon,1+\epsilon)\hat A_{i,j})
\right].
$$

其中 $B$ 是当前 batch 的 prompt 数. 这里先对每条回答的有效 token 求均值, 再对 group 和 prompt 求均值, 所以长回答不会仅因 token 更多获得更大 sequence weight. 若实现把所有有效 token flatten 后统一求均值, 长回答权重会更大, 对应另一个目标. Sequence-level advantage 通常广播到回答中的有效 token. 它提高成功回答整段 token 的概率, 降低失败回答整段 token 的概率, 并没有识别真正关键的推理步骤. Token mask 必须排除 prompt 与 padding. 若将格式标签和最终答案之外的所有推理 token 同等加权, credit assignment 仍然粗糙.

训练还可以加入相对 reference policy 的 KL, 限制 policy 离开初始行为分布. Reference 与 old policy 职责不同: old policy 是生成当前 rollout 的版本, 用于 ratio; reference 是跨 batch 的长期锚点. 调整 KL 系数会改变探索范围, 不能替代 verifier 质量. 一个有漏洞的 verifier 在强 KL 下仍可能被局部利用.

### 2.4 多轮 rollout 与长程任务

上面的 rollout 都假设单轮结构: 给 prompt, 采样一条 completion, verifier 打分后轨迹结束. Agentic 任务把这个结构拉长成多轮交互: policy 输出 action, 环境返回 observation 并改变状态, 如此交替直到任务结束或步数耗尽. 代码修复 agent 的一次 rollout 可以包含数十次文件读写与测试运行, 奖励只在轨迹末端由环境状态给出, 是一个 terminal reward. 验证对象也从最终答案变成整条交互轨迹的执行结果.

多轮结构改变 credit assignment 的粒度. 组内序列级 advantage 仍广播到整条轨迹的每个 action token, 一条 40 步交互的失败轨迹中所有 action 获得相同负权重, 其中多数 action 方向正确, 只有个别步骤决定失败. **horizon 越长, 序列级信号对局部行为的区分度越低, GRPO 类更新的方差也越大.** 任务的 horizon 同时放大稀疏性: 轨迹成功率随步数近似乘性下降, 同样的组大小下全错组占比显著升高, 零方差组率在 agentic 场景比在数学场景更关键.

环境还成为 verifier 的一部分. 终局状态可以读取, 中间状态未必可逆: 文件被修改, 进程被启动, 外部服务被调用之后, 同一条轨迹无法回到起点重放, 「同一候选输出可重复判定」的前提不再自动成立, verifier 必须记录环境初始状态与全部副作用. 把单轮可验证 RL 推向多轮环境交互是 2025 年下半年以来的明显趋势, 系统方法见长程化专题 (1.3.4.3 节).

## 3. 稀疏奖励, pass@k 与学习信号

Binary correctness 很干净, 也很稀疏. 对一个当前单次成功率为 $p$ 的任务, $G$ 次独立采样全错概率为 $(1-p)^G$, 全对概率为 $p^G$. 只有同时出现成功和失败时, 组内相对优势最有信息. $p$ 太接近 0 或 1 时, 增大 group size 能缓解, 成本也线性增加.

Pass@k 衡量 $k$ 次采样中至少一次成功的概率. 它描述搜索预算下找到解的能力, 不等同于单次回答准确率. RLVR 可以借多样采样发现稀有成功轨迹, 再提高这些轨迹的概率, 使 pass@1 随训练改善.

### 3.1 Pass@k 的可复算例子

若每次独立采样成功概率为 $p=0.2$, 则

$$
\operatorname{pass@}k=1-(1-p)^k.
$$

当 $k=1$ 时为 0.2. 当 $k=4$ 时,

$$
1-0.8^4=1-0.4096=0.5904.
$$

同一个模型的 pass@1 是 20%, pass@4 却接近 59.04%. 因而报告 R1 类模型的能力时必须写清 sampling temperature, $k$, 答案去重和 verifier 口径. 不能把 pass@k 的数值当作单次部署成功率.

有限数据集上常用无放回估计. 若一题共生成 $n$ 个候选, 其中 $c$ 个正确, 从中选 $k$ 个至少一个正确的估计为

$$
\widehat{pass@k}=1-
\frac{\binom{n-c}{k}}{\binom nk},
$$

定义域是 $1\le k\le n$. 当 $n-c\geq k$ 时使用上式; 若错误样本不足 $k$, 估计为 1. 例如 $n=10,c=2,k=3$, 全选到错误答案的概率是 $\binom83/\binom{10}3=56/120$, 所以 pass@3 为 $64/120\approx0.5333$.

### 3.2 一个 GRPO 组的手算

假设同一道题采样 4 个回答, correctness reward 为 $(1,0,0,1)$. 暂不加格式奖励, 并为便于手算令 $\varepsilon_A=0$. 组均值是 $\bar R=0.5$, population standard deviation 是

$$
s=\sqrt{\frac{(0.5)^2+(-0.5)^2+(-0.5)^2+(0.5)^2}{4}}=0.5.
$$

因此 advantage 为 $(1,-1,-1,1)$. 正确回答的所有有效 token 获得正权重, 错误回答获得负权重. 若某个正确回答的 token ratio 是 1.1, 未裁剪贡献为 1.1; 若错误回答 ratio 是 0.9, 贡献为 $0.9\times(-1)=-0.9$.

现在给所有回答都加 0.2 format reward, 总 reward 变成 $(1.2,0.2,0.2,1.2)$. 均值平移到 0.7, 标准差仍为 0.5, 标准化 advantage 仍是 $(1,-1,-1,1)$. 即便两个错误回答同时变成 $(1,0.2,0.2,1)$, 均值 0.6、标准差 0.4, advantage 仍是 $(1,-1,-1,1)$. 只有格式项在组内制造新的不等价层级, 例如只给一个错误回答加分得到 $(1,0.2,0,1)$, 相对 advantage 才会改变. 格式项是否影响梯度取决于组内差异结构, 不能只看权重数值. 若实际使用 $\varepsilon_A>0$, 两个对称例子的幅度分别是 $0.5/(0.5+\varepsilon_A)$ 与 $0.4/(0.4+\varepsilon_A)$, 不再精确等于 1.

若 4 个回答全错, reward 为 $(0,0,0,0)$, advantage 全为 0. 提高 group size 可能找到一个成功样本, curriculum 也可以把训练集中在非零成功率区域. 给部分正确步骤 dense reward 能增加信号, 但前提是步骤 verifier 可靠, 否则只是把攻击面从最终答案扩展到过程.

### 3.3 稀疏奖励下的采样与课程

对极难任务, 单纯增加 optimizer step 没有帮助, 因为 rollout 里没有成功轨迹. 可以提高 sampling diversity, 增大 group size, 引入更强 base model, 从容易子任务开始, 或加入可验证的部分分数. 这些方法的共同目标是让训练批中出现能够区分行为的 reward variation.

课程学习要防止遗忘. 若 sampler 总挑成功率约 50% 的题, 随模型变强, 简单题会逐渐退出训练. 模型可能失去格式稳定性或基础计算准确率. 可以保留固定比例的 easy, frontier 和 hard tasks, 分别监控 pass@1, pass@k 与零方差率.

采样成功轨迹后还要考虑重复性. 同一种模板化解法被反复强化, 可能降低解法多样性. 对相同最终答案的多条轨迹做聚类, 监控 self-BLEU 或 token diversity, 能看到 policy 是否只剩一种脆弱路径. 多样性本身不是正确性, 但在 verifier 覆盖有限时, 它能降低全体样本共同利用同一漏洞的风险.

工程上有两类直接响应. DAPO(1.3.2.1 节) 的 dynamic sampling 把组内全同的 rollout 过滤掉并补采新 prompt, 保持有效 batch 大小恒定, 这是把零方差组率从诊断指标变成调度信号的做法; 代价是训练分布被主动推向中等难度区, 两端能力无人约束, 需要按题目类别单独监控过滤率. 另一类是给极难任务提供可验证的 partial score, 把 terminal 二值信号拆成中间里程碑, 但里程碑本身必须能被独立核验, 否则只是把攻击面从最终答案扩展到过程.

## 4. Reward hacking 与 verifier 安全

RLVR 的 reward 可执行, policy 也会把 verifier 当作环境的一部分学习. 如果规则允许捷径, 强化学习会提高捷径出现概率. Reward hacking 不需要模型理解源代码; 只要偶然输出触发高分, policy gradient 就会把相关 token 放大.

安全设计要把 parser, executor, test data, sandbox 和统计口径一起考虑. 一条 verifier pipeline 中任何环节出现 false positive, 都可能成为稳定的训练吸引子. False negative 则会压制语义正确但表示不同的解答.

### 4.1 格式奖励的用途与上限

格式奖励可以要求 `<think>...</think><answer>...</answer>`, 合法 JSON 或明确最终答案区域. 它减少 parser 失败, 让 reasoning 与 final answer 边界稳定. 作为辅助信号, 它在训练早期尤其有用.

格式本身不代表推理正确. 若正确答案得 1 分, 格式得 0.2 分, 一个格式完美但错误的回答仍有正 reward. 用 `total_reward>0` 计算成功率会把它误记为成功. 日志必须分别保存 `correct`, `format_ok` 与各 reward component.

过强格式权重会让模型优先学会外壳. 标签重复, 空 thinking 区域, 把答案藏进 parser 最后读取的位置, 都可能满足形式却损害内容. Format verifier 应测试嵌套标签, 多个答案, 缺失闭合, Unicode 混淆和超长输出, 并规定失败时是零分还是直接拒绝样本.

### 4.2 测试泄漏与 verifier hacking

代码 verifier 若把 hidden test 文件留在可读路径, 候选程序可能直接读取答案. 若允许网络, 程序可以调用外部服务. 若同一进程复用状态, 前一个样本可能污染后一个样本. 沙箱需采用最小权限, 干净文件系统, 资源限制与确定性环境, 并把标准输出, 标准错误和退出状态单独保存.

测试覆盖不足时, 硬编码公开样例也会通过. 可以使用 property-based tests, metamorphic tests, 随机生成用例与人工 adversarial cases 扩充覆盖. 但动态测试也要保存随机种子和生成器版本, 否则 reward 无法复算. 对性能题, 时间阈值受机器负载影响, 最好采用宽裕边界, 多次运行或指令数等更稳定指标.

数学 parser 也有类似攻击面. 若只提取最后一个数字, 模型可以枚举大量候选并把正确值碰巧放在末尾. 若 symbolic solver 接受未声明假设, 不等价表达可能被误判. 验证器测试集应包含专门构造的恶意输出, 而不只包含正常模型回答.

### 4.3 污染与验证器泄漏

训练数据污染有两层. 第一层是问题或标准答案出现在预训练, SFT 或 RL prompts 中, 模型可能记忆答案. 第二层是 verifier 的隐藏规则, 测试用例或答案抽取逻辑泄漏进训练上下文, 模型可以针对评测协议优化. 两者都会让留出集分数高估泛化.

去污染不能只做题面精确匹配. 题目改写, 数值替换, 翻译和解答网页都可能携带同一结构. 可以结合 n-gram, embedding 近邻, 代码 AST 与来源时间检查, 并保留真正未用于训练的 private holdout. 对同一题生成的多个变体要按问题族切分, 不能让近邻模板跨训练与测试.

Verifier 版本也需要隔离. 若训练和测试使用完全相同的一小组 tests, policy 会逐渐适应它们. 留出额外 tests, 在训练中轮换等价检查器, 并对最终模型使用独立实现, 能检测协议特化. 这仍不能证明现实正确性, 但能提高利用单一 verifier 漏洞的成本.

## 5. DeepSeek-R1 在 RLVR 中的位置

DeepSeek-R1 技术报告展示了可验证 reasoning reward 与大规模强化学习结合的结果. 其中 R1-Zero 从 DeepSeek-V3-Base 出发直接进行 reasoning-oriented RL, 没有先用 reasoning SFT 建立冷启动. 报告观察到更长推理, 反思和自我验证等文本行为, 同时也记录了可读性差与语言混杂.

DeepSeek-R1 则采用多阶段路线, 加入冷启动数据, reasoning RL, rejection sampling 形成的新 SFT 数据, 以及面向通用能力和人类偏好的后续阶段. 它说明纯可验证 RL 能探索出有用行为, 也说明面向用户的成品需要数据整理与更广的对齐目标.

### 5.1 R1-Zero 证明了什么

R1-Zero 的重要性在于展示一个强 base model 在缺少 reasoning SFT 冷启动时, 仍能通过 rule-based RL 显著提高数学和代码等可验证任务表现. 它的 reward 包含 accuracy 与 format 两部分,没有 process supervision,最终 correctness 仍是核心信号. 长度增加,自检和回溯样式随训练出现,表明这组序列级规则奖励能够改变推理轨迹分布.

这些观察是模型输出行为, 不能直接映射成人类心理过程. 文本里出现"wait"或"let me reconsider"不证明模型具有与人相同的反思机制. 更可靠的结论是: 某些带回溯, 重算和长链结构的 token pattern 在 verifier reward 下获得了更高概率.

R1-Zero 也没有说明任意 base model 都能用同样 recipe 复现结果. Base model 已有的数学, 代码, 指令理解与长上下文能力决定探索起点. 当成功轨迹概率接近 0 时, 纯 binary RL 很难凭空发现解法. 算力, group sampling 和任务分布同样属于条件.

报告给出的部分对比口径: 在 AIME 2024 pass@1 上, R1-Zero 为 71.0, R1 为 79.8, 而 R1-Zero 配合 majority voting 可到 86.7. majority voting 后的 R1-Zero 高于 R1 的单次回答, 与第 3 节的分析一致: pass@k 口径的搜索收益不能换算成 pass@1 能力. R1 相对 R1-Zero 的 8.8 分来自冷启动数据, 多阶段 SFT 与后续对齐的组合, 报告没有拆开这三项各自的贡献, 也不能全部记到 RL 算法头上.

### 5.2 R1 的多阶段训练为何重要

冷启动数据让输出格式、可读性和基本 reasoning pattern 进入 policy 的高概率区域与有效支持. Reasoning RL 随后利用可验证 signal 提高目标任务. Rejection sampling 用训练后的模型生成候选, 通过规则和其他筛选得到新 SFT 数据, 把探索出的行为蒸馏回 supervised learning. 后续阶段再补充通用指令、写作、事实问答与 safety.

这条路线将探索和产品化分开. RL 可以在可验证域中大胆搜索, SFT 将高质量轨迹压回稳定分布, 通用对齐阶段处理 verifier 无法覆盖的帮助性与安全性. 因而 DeepSeek-R1 既包含 RLVR, 又超出纯 RLVR. 把整个模型等同于一次 GRPO 训练, 会漏掉大量数据与阶段接口.

报告给出的数据规模口径: 冷启动阶段收集约 600k reasoning 样本微调 V3-Base, 第二阶段用 rejection sampling 产出约 800k 样本再次微调. 冷启动数据来自带 few-shot prompting 的长 CoT 生成与人工后处理, 作用是提高可读性并把基本推理模式放进高概率区域, 而不是引入新的可验证信号. 多阶段路线的成本主要花在数据整理与多次 SFT 上, 这部分在技术报告里没有像 RL 阶段那样的逐项算法描述, 复现时需要单独规划数据管线.

技术报告更新版补充的流程细节里, rejection-sampling 数据由第一阶段 reasoning-RL checkpoint 生成; cold-start SFT 与第二阶段 SFT 的参数起点都回到 DeepSeek-V3-Base, 各 fine-tune 2–3 个 epoch. 因而这里同时存在两条不同的链: 数据继承前一阶段 RL 模型的生成结果, 参数则从 V3-Base 重新进入 SFT. 把 data lineage 与 parameter lineage 分开, 才能复现这条多阶段路线.

### 5.3 算法, 奖励与系统的边界

R1-Zero 的 rule reward 由 accuracy 与 format 组成. 最终 R1 的第一阶段 reasoning RL 还加入 language-consistency reward; 后续通用 RL 对 reasoning prompts 使用 rule reward, 对 general prompts 使用 learned helpfulness/safety reward, 并处理 language 与 general format. 各阶段都采用 GRPO 避免单独训练同规模 critic. 这不代表 RLVR 必须用 GRPO, 也不代表 GRPO 只能用于 RLVR. Optimizer 定义 advantage 和更新, verifier 或 reward model 定义训练信号, 两者是可替换模块.

技术报告中的 group size, temperature, learning rate, KL 系数, reference refresh 和长度上限属于具体实验设置, 不是 RLVR 的统一默认值. 将这些数值搬到不同模型或任务时, 成功率, 零方差组率和 ratio 分布都可能完全不同. Recipe 应按可观测统计重新校准.

技术报告给出的部分口径: reasoning RL 阶段使用组大小 16 的 GRPO, 采样温度 0.6; 报告更新版补充了以系数 0.04 加入 KL penalty 以约束 policy 偏离 base model; R1-Zero 的实验记录里还报告了训练过程中把输出长度上限从 4k 逐步放宽到 32k. **这些数字描述的是一次具体实验, 不是 RLVR 的推荐默认值**, 上一段的警告对它们同样成立.

R1 的成功也不意味着开放域问题已经可验证. 数学 final answer 正确可以自动判断, 一篇政策分析是否全面, 医疗建议是否安全, 引用是否可靠, 仍需要更复杂的证据与人类判断. RLVR 擅长奖励边界清楚的子任务, 可以成为通用训练的一部分, 不能替代所有偏好与安全评估.

### 5.4 R1 之后的几个问题

第一个问题是可验证域能扩多远. R1 把数学与代码上的 rule reward 推到很高水平, 后续工作沿两条线扩展: 把更多任务改写成可验证形式, 以及承认部分任务无法改写, 用 learned reward 或人类反馈补位. 第二条线让多奖励组合成为常态, 组合方式本身成为研究对象: 先加和再归一会损失奖励组合的区分度, 逐项归一再聚合是 GDPO(1.3.2.4 节) 给出的替代, 与 R1 已使用的 accuracy, format 与 language-consistency 组合直接相关.

第二个问题是从单轮到长程. 推理 RL 的 rollout 正从单轮数学回答扩展到多轮环境交互, horizon 从几百 token 的 completion 变成数千乃至上万 token 的交互轨迹. 序列级组内优势在长 horizon 下 credit assignment 过于粗糙, 给了 critic 回归明确的动机: value function 能对轨迹内的局部状态给出预测基线, 而不是把整条轨迹当作一个动作打分. **critic 的回归对应长 horizon 下的 credit assignment 失效, 不构成对 GRPO 的否定**, 两者服务不同的 horizon 与方差结构, 长程化的系统整理见长程化专题 (1.3.4.3 节).

第三个问题是从算法到算力. RLVR 的训练收益是否随算力继续增长, 是 R1 之后被系统研究的问题. 观测到的形态不是预训练式的幂律, 更接近带饱和的 S 形曲线: 渐近线与效率取决于 reward 质量, 任务分布与 recipe 稳定性, 把单一 recipe 的组合收益误认为新的 scaling 定律是这一方向最常见的误读. 判断自己任务上 RL 计算能扩到多远, 见 scaling(1.3.3.4 节) 的坐标与方法.

## 6. 怎样建立可复现的 RLVR 闭环

一套 RLVR 系统至少包含 task registry, prompt sampler, rollout engine, verifier service, reward composer, trainer 与 evaluator. 每条样本需要贯穿这些服务的不可变 id. 异步返回时按 id join, 不能只依赖 batch 位置, 否则重试和部分失败会把一个回答的 reward 分给另一个回答.

训练前先冻结协议. 任务版本, parser, tests, sandbox image, timeout, reward weights, sampling 参数和 policy/reference version 都写入 manifest. 协议变化后应创建新版本, 不要用新 verifier 重新解释旧日志却保留同一个实验名称.

### 6.1 Verifier 单元测试与故障注入

每类 verifier 都应有正例, 语义等价正例, 普通错误, 解析错误, 超时, 资源超限和恶意输出. 数学 verifier 要测试多个答案, Unicode 符号, 未约分分数和单位; 代码 verifier 要测试文件读取, 网络访问, fork bomb, 随机性和状态残留; proof verifier 要锁定 kernel 与依赖版本.

可以统计 false positive 与 false negative. 从训练 rollout 中按高 reward, parser 边界和异常类型分层抽样, 交给独立实现或人工复核. False positive 风险通常更大, 因为 policy 会主动放大它; false negative 会浪费有效轨迹, 并可能把正确的少数表示压掉.

故障注入还能检查训练管线. 人为让一个 verifier worker 超时, 系统应记录 `infra_error`, 而不是给回答 0 分. 人为打乱返回顺序, sample id join 后 reward 应仍对应正确输出. 人为修改 padding token 的 score, mask 后 policy loss 应不变. 这些测试能发现 reward 服务之外的数据错配.

### 6.2 训练与评估指标

训练面板至少分开报告 pass@1, pass@k, group mean reward, correctness rate, format rate, parse error, timeout, zero-variance group rate, response length, KL, entropy, clip fraction 与有效 token 数. 一个总 reward 上升可能只是格式率提高或回答变长, 分项才能解释变化.

评估必须使用独立 prompts 与 verifier. 最好再准备 adversarial verifier set, 专门包含训练 parser 的边界与隐藏测试未覆盖的情况. 对关键 benchmark 报告采样参数, $k$, 置信区间和总生成 token. Pass@k 提升而 pass@1 不变,只说明增加采样预算后「至少一次成功」的概率提高,不能单独归因于搜索多样性. Prompt 难度间的成功率重分配、样本相关性和估计噪声也能造成这一现象;若要讨论 diversity,还需报告 unique answer、pairwise similarity 或 sample correlation.

按难度和来源切片能观察课程偏差. Easy 集保持基础稳定, frontier 集反映当前学习区, hard 集监测探索边界. 若总体准确率上升只来自 sampler 把更多预算移到 easy tasks, 固定 holdout 会及时显出这个问题.

多轮任务还要补充交互过程指标: 平均交互步数, 无效动作比例, 失败后恢复率与环境重置次数. 只报告 terminal success rate 无法区分「一步做对」与「多步出错后碰巧成功」, 也无法发现 policy 靠大量重试消耗环境预算的行为. 这些指标在单轮数学任务里退化成长度与格式, 在 agentic 任务里才是主要的失效率来源.

### 6.3 何时更新 verifier 或数据

当训练 reward 上升而独立 verifier 停滞, 首先抽查高 reward 新行为. 若发现稳定 loophole, 修复 parser 或 tests, 建立新的 verifier version, 并把利用样本加入回归集. 旧 reward 与新 reward 不能直接拼接; 应重新验证或从清晰边界开始新一轮训练.

当 zero-variance group rate 很高, 要区分全对与全错. 全对占主导说明任务太容易, 可降低采样或保留少量复习; 全错占主导说明探索不足, 可调整难度, temperature, group size 或 base model. 若 parse error 高, 先改善输出协议和 parser, 不应把更多优化步骤浪费在无效反馈上.

最终停止条件来自外部能力与系统稳定性, 不是训练 reward 的最高点. 独立 pass@1, pass@k, verifier robustness, 长度, 资源成本和开放域副作用都需要满足门槛. RLVR 的优势是信号能够复算; 真正把优势兑现出来, 还需要让每个 reward 都能追溯到任务, 输出, verifier 和模型版本.

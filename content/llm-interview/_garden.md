# LLM 与 Agent 面试知识库

面试题到处都是, 今天搜到一份 Transformer 八股, 明天又有人整理 Agent 高频题. 但大模型变化太快, 只依赖别人输入很难跟上: 两年前还在问 LoRA 和 PPO, 后来变成 MLA, GRPO, FP8, KV cache 和 Agent harness, 同一个问题的工程答案也会随着模型规模和硬件改变. 现在拿到一道题, 打开 Codex 通常很快就能得到一个差不多正确的回答. 关掉页面以后能否从定义开始重新推导, 才决定这份答案有没有变成自己的理解.

我在写完 [LLM 指南](../llm-guide/_garden.md)之后更明显地感到这件事. 理论主线清楚了, 不代表工程细节和业务判断也会自动出现. 知道自注意力的公式, 不等于能估算一次 decode 要读多少 KV cache; 知道 DPO 的损失, 不等于能判断偏好数据脏在哪里; 知道 RAG 的流程, 不等于能说明召回率提高后为什么最终回答反而变差. 面试的连续追问恰好会把这些空隙暴露出来.

所以这座库不按网传频率堆题, 也不追求背一句标准答案. **每道题都要成为一次主动重建: 定义是什么, 公式怎样得到, 工程里哪些条件会改变答案, 换一个场景后结论是否还成立.** 自己完整写过一遍, 记忆通常比看十份答案更牢; 更重要的是, 写到卡住的位置会告诉我理解究竟断在哪里.

## 1. 六类问题对应六种能力

六章覆盖基础原理、训练对齐、系统工程、RAG 与 Agent、多模态和综合案例。分类依据是回答所需的推理对象，不是产品名称或模型版本。

同一道题可能跨过多个章节。完整回答要保持符号、规模假设和系统边界一致，并说明结论在哪些条件下成立。

### 1.1. 从公式到实现

[基础原理](1-基础原理/1-基础原理.md)处理 Transformer, 注意力, 位置编码, MoE 和生成过程. 会念 $\operatorname{softmax}(QK^T/\sqrt{d_k})V$ 只是起点; 还要写出每个矩阵的 shape, 解释 mask 加在何处, 算出序列长度变化时计算量和显存怎样变化. RoPE, MQA, GQA 和 MLA 也要落到旋转作用的维度, KV 头共享范围与缓存内容, 不能停在名称比较.

[训练与对齐](2-训练与对齐/2-训练与对齐.md)从预训练目标进入 SFT, PEFT, 奖励模型, PPO, DPO 与推理强化学习. 面试常把它们问成算法对照, 实际回答必须先声明数据从哪里来, 哪个策略生成样本, 哪个模型提供分数, 梯度更新谁. 相同的损失函数放进不同数据管线, 训练行为可能完全不同.

### 1.2. 从单个算法到完整系统

[系统与工程](3-系统与工程/3-系统与工程.md)讨论并行训练, 显存, 通信, 推理服务, 量化和性能定位. 工程题很少有脱离条件的唯一答案. 一个并行方案是否合适, 取决于模型结构, 节点内互联, 跨节点网络, batch 和序列长度; 一个吞吐数字如果没有硬件, 精度和并发, 基本不能比较. 本章要求答案明确写出假设和数量级.

[应用与 Agent](4-应用与agent/4-应用与agent.md)处理 RAG, 工具调用, 上下文工程, 工作流与长任务系统. 业务题关心的不只是模型能否调用工具, 还包括权限, 幂等, 超时,状态持久化, 可观察性和失败恢复. 只画一张「模型—工具—结果」的流程图, 无法回答真实系统在第三十步出错以后怎样继续.

## 2. 从单模态问答到跨专题判断

[多模态](5-多模态/5-多模态.md)讨论视觉编码, 模态对齐, OCR, 语音与视频. 回答一个多模态问题时, 需要分清信息在哪一步离散化, token 数怎样增长, 位置与时间怎样编码, 哪些损失只负责对齐而不直接生成. 模型名字会频繁变化, 这几项计算对象相对稳定.

[综合面试案例](6-综合面试案例/6-综合面试案例.md)把前五章放进连续追问. 一道完整问题可能从注意力公式开始, 进入训练稳定性, 再转到多机部署和线上故障. 连续追问会检验回答能否始终使用同一组假设, 数字和系统边界, 万能话术在这里很快就会露馅.

### 2.1. 怎样判断自己真的会了

能够复述定义只是起点。更可靠的标准是能从假设推到公式，给出数量级，并在条件变化后主动修正原结论。

实现题还要落到张量形状、通信量、显存占用或接口状态。若只能描述概念，无法预测一次改动会改变什么，理解仍停留在术语层。

### 2.2. 先写答案, 再使用工具

工具可以帮助查论文, 核对数字和发现遗漏, 但不应该替代第一次回忆. 面对一道题, 先在没有资料的情况下写出定义, 公式和主要结论, 再用论文, 官方文档和代码修正. 两版答案之间的差异就是最具体的薄弱点: 可能是一个符号从哪里来的不知道, 可能是把训练和推理混在了一起, 也可能是忘了结论依赖的硬件条件.

可复算的数字会保留下来; 缺少出处的「高频」「必问」和出现率就不写了. 一道题是否流行变化很快, 它涉及的机制是否重要更稳定. 来源优先使用论文, 技术报告, 官方代码和系统文档; 面经只能帮助发现问题, 不能独自证明技术答案.

### 2.3. 跨章节问题保持同一组假设

一道题从注意力公式转向训练吞吐时，batch、序列长度和精度口径不能悄悄变化。假设变化应明确写出，否则两个局部正确的答案可能无法组成一致系统。

跨章节推理还要区分模型能力与外部系统能力。检索、缓存、工具执行和验证器带来的收益，需要与模型参数本身的变化分别归因。

## 3. 让追问改变题目的条件

第一轮回答定义, 第二轮应该改变条件. 如果注意力从训练换到单 token decode, 计算瓶颈会怎样变; 如果 PPO 的 rollout 来自旧策略, 重要性权重怎样进入; 如果 RAG 的文档从短段落换成长表格, chunk 和评测怎样调整. 一个结论只有在条件变化后仍能被重新推导, 才真正进入自己的知识结构.

目标是面对没有见过的问题时仍能建立模型: 输入是什么, 状态在哪里, 谁与谁计算, 资源花在哪里, 证据能支持什么. 面试只是检验这种能力的一种场景, 背得像某份答案并没有太大意义.

### 3.1. 答案的证据标准

公式结论应能回到推导假设，系统数字应能回到硬件、并行配置和负载条件，模型能力应能回到明确的评测协议。

遇到易变事实时优先查论文、官方仓库和版本化文档。二手总结可以提供线索，不能单独承担参数、发布日期或实验数字的依据。

### 3.2. 理论结论要写适用条件

理论题最容易出现的错误是把简化论证写成无条件结论. 例如注意力点积除以 $\sqrt{d_k}$ 的常见推导假设 query 与 key 的各维独立, 均值为零且方差相近; 这个推导解释初始化附近的尺度, 不能保证训练后的表示仍满足独立假设. TRPO 的单调改进界也依赖策略差异与优势估计等条件, 实际实现使用近似求解, 不能缩成「限制 KL 就保证性能上升」.

回答里应区分三个层次: 数学式在假设下推出什么, 论文实验在特定设置中观察到什么, 工程实践通常怎样选择. 三层结论可以互相支持, 但不能互相替代. 一个在 A100 上测出的 kernel 吞吐不能直接代表 H100, 一个 7B 模型上的消融也不能自动推广到 70B.

### 3.3. 系统答案要给出数量级

系统题如果只有组件名称, 很难判断是否真的理解. 讨论 KV cache 时应能写出每层保存的元素数, 乘上层数, batch, token 数和数据类型字节; 讨论数据并行时应能说明梯度通信量与参数量的关系; 讨论 MoE 时应区分总参数, 激活参数, token dispatch 和专家容量. 不要求每次背出精确常数, 但数量级和随变量增长的方向必须正确.

业务题则要说明优化目标. 降低平均延迟, 降低尾延迟, 提高吞吐和减少单次成本可能要求不同的 batch 与调度策略; 提高召回率也可能带来更多无关上下文. 当目标和约束明确以后, 技术选择才有可检验的理由.

答案最终要能够落回公式, 代码或可观察的系统行为. 如果一个判断无法通过推导、实验或日志复核, 就应继续追问它依赖了哪些隐含条件.

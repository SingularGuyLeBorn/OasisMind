# 综合面试案例：系统设计与连续追问

本页不再使用无法独立核验的“某公司一面/二面”包装。以下案例由公开技术问题重组，用来练习从不完整需求走到可验证方案；它们不代表特定公司、岗位或出现频率。

## 1. 一套通用答题骨架

系统设计题可以按七步展开：

1. **澄清目标**：谁使用、完成什么任务、失败代价是什么；
2. **定义 SLO**：质量、延迟、吞吐、成本、可用性和安全阈值；
3. **列约束**：数据、隐私、硬件、模型许可、上线周期和团队能力；
4. **给基线**：先提出最小可工作的方案，说明为什么足以验证核心假设；
5. **拆组件**：数据流、状态、接口、失败模式和可观测性；
6. **设计评测**：离线集、反事实、灰度、回滚和持续监测；
7. **讨论演进**：何时增加复杂度，新增组件解决哪个已测得的瓶颈。

高质量回答会主动指出不确定信息并给出测量方案。低质量回答只罗列模型、向量库和框架名。

### 1.1 通用评分表

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 需求澄清 | 直接开讲方案 | 问到部分流量或功能 | 明确用户、任务、失败代价与边界 |
| 正确性 | 有事实错误 | 主干正确但条件缺失 | 机制、公式、版本和条件完整 |
| 方案闭环 | 只有组件列表 | 有主流程 | 含状态、异常、降级、回滚与运维 |
| 评测 | 只报一个 benchmark | 有离线指标 | 离线、线上、反事实和分层错误分析 |
| 权衡 | 宣称单一最佳 | 提到成本或延迟 | 用约束解释选型并给替代方案 |
| 沟通 | 跳跃、堆术语 | 基本可跟随 | 先结论后依据，能承接连续追问 |

总分 12 分。8 分表示方案可讨论；10 分以上通常意味着不仅懂组件，还能把它变成可验证系统。

## 2. 案例一：可追溯的企业知识助手

### 题目

为内部员工设计一个知识助手，回答制度、产品和工程文档问题。文档每天变化，部分内容有部门权限；回答必须给证据，错误引用可能造成合规事故。

### 2.1 先澄清

- 文档类型、语言、数量、更新频率和权限来源是什么？
- 允许的回答延迟、并发和成本是多少？
- “正确”是答案语义正确、引用支持，还是流程动作也成功？
- 无证据时应该拒答、转人工还是允许一般性回答？
- 是否允许云模型看到原文，日志保存多久？

### 2.2 基线方案

```text
源系统变更事件
 → 权限感知抓取与版本化
 → 结构解析、去重、分块与元数据
 → 稀疏 + 稠密检索
 → 可选重排
 → 基于证据生成
 → 引用校验与权限二次检查
 → 回答或安全降级
```

关键设计：

- 文档 ID、版本、有效期和 ACL 随 chunk 一起进入索引；
- 检索前后都做权限过滤，缓存键必须包含身份或权限集合；
- 引用不仅显示链接，还要能映射到具体版本和片段；
- 删除和降权需要可传播，不能只追加新索引；
- 生成器只能引用取回证据，引用校验器检查句子是否被片段支持；
- 没有充分证据时拒答或转搜索，不让模型自由补齐公司事实。

详细机制参见[应用与 Agent](./04-应用与agent.md)。

### 2.3 评测

| 层 | 指标 |
|---|---|
| 检索 | Recall@k、MRR/nDCG、权限泄漏率、时间有效性 |
| 生成 | 答案正确性、证据充分性、引用精确率、拒答校准 |
| 端到端 | 任务成功率、人工升级率、TTFT、p95、单次成本 |
| 变更 | 新文档可见延迟、删除传播延迟、旧版本误引率 |

测试集应包含不可回答问题、相互冲突版本、跨部门同名文档和恶意提示注入文档。

### 2.4 连续追问

**为什么不用直接塞长上下文？**

长上下文可能简化小规模基线，但权限、更新、成本和检索定位仍需解决。应在相同任务上比较长上下文、RAG 和混合方案，而不是按 token 上限猜。

**如何处理“昨天正确、今天过期”？**

记录生效时间和版本关系；检索时加时间过滤或衰减；回答展示 `as_of`；为高风险制度设置强制刷新和引用版本检查。

**重排器让延迟超标怎么办？**

减少候选、批量推理、按查询难度触发重排，或用轻量模型；通过质量—延迟曲线决定，而不是永久删除重排器。

## 3. 案例二：能执行操作的 Agent

### 题目

设计一个 Agent，能查询订单、退款和修改地址。外部 API 可能超时或重复返回，部分操作不可逆，用户输入和工具返回都可能包含恶意指令。

### 3.1 状态机而不是无限循环

```text
接收请求 → 身份与意图确认 → 制定有限计划 → 选择工具
→ 参数验证与授权 → 执行 → 读取结构化结果 → 验证目标
→ 回复 / 重试 / 补充信息 / 人工审批 / 安全终止
```

必须设计：

- 工具 schema 和参数校验；
- 用户身份、资源权限与动作权限；
- 幂等键、超时、重试上限和退避；
- 读操作与写操作分级，关键写入先预览再确认；
- 审批、补偿事务和人工接管；
- prompt、tool call、结构化结果、授权决策和最终状态的审计日志；
- 最大步数、最大成本和全局 deadline。

Function Calling 只产生结构化调用建议；宿主系统负责验证、授权和真正执行。MCP 可标准化上下文与工具的暴露方式，但不会替应用自动完成业务授权。A2A 处理 Agent 间协作时仍需身份、任务状态和信任边界。

### 3.2 威胁模型

- 用户提示诱导越权；
- 检索文档或网页中的间接提示注入；
- 工具描述污染；
- 工具返回伪造“系统指令”；
- 跨租户缓存或日志泄漏；
- 重试导致重复退款；
- 多 Agent 互相触发形成循环。

对策不是只加 system prompt，而是最小权限、数据与指令分离、允许列表、独立策略引擎、人工审批和动作后验证。

### 3.3 评测

按轨迹而不只按最终文本评分：工具选择、参数正确、授权正确、步骤数、恢复能力、任务结果和副作用。建立故障注入：超时、429、部分成功、重复回包、过期 token、冲突更新和恶意工具输出。

### 3.4 连续追问

**怎样避免重复退款？** 使用业务级 idempotency key，将意图 ID 与订单/金额绑定；重试先查询动作状态；对未知状态进入人工核对，不能盲目再次写入。

**模型坚持调用未授权工具怎么办？** 工具可见性不是唯一安全边界。执行层必须独立鉴权并返回结构化拒绝，策略层记录事件；模型不能绕过宿主权限。

## 4. 案例三：多租户推理服务容量规划

### 题目

为一个聊天模型提供在线服务。输入长度从 100 到 32k token，输出从 20 到 2k token；白天突发流量明显。目标是控制 p95 TTFT 和 TPOT，同时提高 GPU 利用率。

### 4.1 先建立负载画像

- arrival rate 与时间分布；
- input/output length 联合分布，而不是两个平均值；
- 流式、非流式、优先级和超时；
- 重复前缀比例；
- 模型版本、量化、并行拓扑和硬件；
- TTFT、TPOT、端到端延迟与 goodput SLO。

### 4.2 方案组件

- token-budget admission control，避免单个长请求拖垮队列；
- continuous batching，把不同到达时间的请求动态合批；
- PagedAttention 类 KV block 管理；
- chunked prefill，降低长 prompt 对 decode 的阻塞；
- prefix cache，但缓存键需包含模型、适配器和影响输出的上下文；
- prefill/decode 分离或优先级队列，是否采用由流量实验决定；
- 模型副本弹性、warmup 和过载降级；
- OOM、队列、block 使用、TTFT/TPOT 分位数和取消请求监控。

系统原理参见[系统与工程](./03-系统与工程.md)。

### 4.3 容量实验

使用真实长度分布回放，逐步提高 arrival rate，绘制：

```text
arrival rate → goodput、p95 TTFT、p95 TPOT、GPU 利用率、KV 使用率、拒绝率
```

峰值 tokens/s 不是容量。达到 SLO 约束前的最大稳定 goodput 才是更有用的线上指标。

### 4.4 连续追问

**为什么吞吐上升而 p95 变差？** 更大 batch 提升 GPU 效率，但增加排队；长 prefill 还可能阻塞 decode。应调整调度优先级、token budget 和 chunk 大小。

**量化后为什么没变快？** 可能缺少对应 kernel、受内存以外瓶颈限制、反量化开销过大，或 batch/shape 不适合。需用 profiler 分解算子、带宽和调度时间。

## 5. 案例四：领域微调与知识更新

### 题目

客服模型在术语和格式上表现差，并缺少最近三个月产品知识。团队建议“直接用 LoRA 把所有新文档训进去”。你如何决策？

### 5.1 先拆三类问题

| 症状 | 更可能的手段 | 原因 |
|---|---|---|
| 输出格式、语气、流程 | SFT/LoRA | 属于稳定行为模式 |
| 高频领域语言和概念表示 | 继续预训练或领域 SFT | 可能需要分布适配 |
| 高频变化的事实 | RAG/工具 | 需要可更新、可引用、可撤销 |

把文档变成训练样本不能保证事实可精确召回，也难以删除过期知识。先构建不微调的基线，再用错误分类决定是否增加训练。

### 5.2 实验设计

1. 冻结评测集并检查污染；
2. 建 prompt/RAG 基线；
3. 构造 SFT 数据，记录来源、许可、去重和模板；
4. 比较 full FT、LoRA rank/target modules 和必要的 QLoRA 配置；
5. 同时测领域任务、通用回归、拒答、安全和延迟；
6. 做多 seed、置信区间和消融；
7. 设计 adapter 版本、回滚和与基座模型的兼容策略。

训练机制参见[训练与对齐](./02-训练与对齐.md)。

### 5.3 连续追问

**rank 越高越好吗？** 不一定。容量增加也会增加参数、显存和过拟合风险；固定其他变量做收益—成本曲线。

**QLoRA 65B 单卡一定可行吗？** 只能引用原论文的特定 48GB 条件；实际还取决于模型结构、序列长度、LoRA 模块、batch、checkpointing 和软件实现。

**怎样检查灾难性遗忘？** 构造领域内、领域外和安全回归集；比较基座与微调模型；对继续预训练还应监控通用语言 loss 与关键能力变化。

## 6. 案例五：高分辨率文档与图片问答

### 题目

设计一个能读合同扫描件、表格和图表的问答系统。文档可能旋转、低清、跨页，答案需要引用页码与区域。

### 6.1 数据流

```text
文件安全检查 → 页面渲染/图像校正 → OCR + 版面分析
→ 页面/区域索引 → 视觉与文本混合检索
→ 高分辨率局部读取 → 结构化答案 → 页码/框坐标校验
```

关键决策包括：

- OCR 文本与原始图像都保留，不能只留下识别结果；
- 表格需要单元格、行列关系和跨页续表信息；
- 先低分辨率定位，再对候选区域高分辨率读取，控制视觉 token；
- 坐标统一映射到原始页面，记录旋转、裁切和缩放变换；
- 引用展示页码、区域和原文，必要时让用户复核；
- 敏感合同做租户隔离、访问控制和日志脱敏。

多模态基础参见[多模态](./05-多模态.md)。

### 6.2 评测

- OCR：字符/词错误率，按语言、字号和扫描质量分桶；
- 表格：单元格内容、结构、跨页合并；
- 问答：答案正确性、证据区域 IoU、引用充分性；
- 反事实：替换数字、遮挡区域、交换页面，答案应同步变化；
- 系统：页数、视觉 token、TTFT、峰值显存和单文档成本。

### 6.3 连续追问

**模型答对但框错了，算成功吗？** 对需要审计的合同任务不算。答案与证据定位是两个独立验收项。

**如何防图片里的提示注入？** OCR/视觉内容作为不可信数据，不能获得系统指令优先级；工具执行由独立策略层授权；高风险动作要求人工确认。

## 7. 案例六：质量回归与事故排查

### 题目

上线新模型后，离线 benchmark 上升，但用户投诉增加，工具调用失败率和 p99 延迟同时变差。如何排查？

### 7.1 不要一开始就猜模型变笨

先确认变更范围：模型权重、tokenizer、chat template、采样参数、工具 schema、检索索引、运行时、量化、调度器和硬件是否同时变化。建立同一请求的可重放记录，并把端到端链路拆成：

```text
排队 → 预处理/检索 → prefill → decode → tool call → 外部 API → 后处理
```

### 7.2 二分与回放

1. 用旧流量在新旧栈做影子回放；
2. 只替换一个变量，区分模型回归与系统回归；
3. 按请求长度、工具、租户、语言和时间分桶；
4. 比较 structured-output 合法率、工具参数、重试、TTFT、TPOT 和外部 API；
5. 对高风险差异人工标注，形成回归集；
6. 若越过错误预算，先回滚或降级，再继续根因分析。

### 7.3 可能的交叉根因

- 新 chat template 增加 prompt token，既抬高 TTFT 又截断工具参数；
- tokenizer 或 stop sequence 改变，造成 JSON 不完整；
- 量化影响结构化输出，重试增加并拖高尾延迟；
- scheduler 提高 batch，吞吐上升但工具请求排队更久；
- schema 变更未同步到模型提示或校验器；
- 离线集没有覆盖真实长尾和工具故障。

### 7.4 连续追问

**如何避免下次再发生？** 建版本化评测、真实流量回放、模型与运行时矩阵、工具 contract test、分阶段灰度、错误预算和自动回滚；每项变更记录 owner、假设、指标和退出条件。

## 8. 自我演练方法

每个案例用三轮回答：

1. **两分钟版**：目标、约束、基线、关键指标；
2. **十分钟版**：完整数据流、状态、失败与评测；
3. **压力追问版**：随机改变一个约束，例如预算减半、延迟变严、不能出网、数据量扩大十倍，再重新选型。

录音后按 12 分表自评。凡是出现“绝对、零风险、固定提升、行业都用”时，回到对应专题核对条件和一手来源。

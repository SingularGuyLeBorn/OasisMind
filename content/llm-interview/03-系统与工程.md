# 系统与工程：微调、分布式训练与推理服务

工程题不应从工具名开始，而应从约束开始：模型和序列多大、训练还是推理、硬件拓扑如何、目标是显存、吞吐、首 token 延迟还是单请求成本。所有“能否放得下”的答案都要列显存账本，所有“更快”的答案都要说明负载和计量口径。

## 1. LoRA：低秩更新及其真实成本

对冻结权重 $W_0\in\mathbb{R}^{d_{out}\times d_{in}}$，LoRA 学习低秩增量：

$$
h=W_0x+\frac{\alpha}{r}BAx,
\qquad
A\in\mathbb{R}^{r\times d_{in}},\quad
B\in\mathbb{R}^{d_{out}\times r}.
$$

不同代码库可能交换 $A/B$ 命名，但维度和乘法应能对上。经典 LoRA 使用 $\alpha/r$ 缩放；若采用 rank-stabilized LoRA 等变体，缩放规则可能变化，必须按实现回答。

### 1.1 参数量与秩

对一个线性层，新增参数量为：

$$
r(d_{in}+d_{out}),
$$

而不是 $d_{in}d_{out}$。秩 $r$ 没有脱离任务的固定最佳值。它与目标模块、数据规模、学习率、缩放、正则化及任务距离耦合。可靠的选择方法是：

1. 先选目标模块，例如 attention 的投影层，必要时再覆盖 MLP；
2. 固定数据与预算，比较多个 rank；
3. 同时记录效果、可训练参数、峰值显存和吞吐；
4. 选择达到收益平台的最小配置，并检查领域外回归。

LoRA 减少可训练参数和优化器状态，但前向激活、冻结基座权重、长序列 attention 和通信仍可能主导显存或时间。

## 2. QLoRA：量化的是冻结基座，不是“4-bit 训练一切”

QLoRA 将冻结的预训练权重量化到 4 bit，在反向传播时把梯度传到 LoRA 适配器。原论文的三个核心部件是：

- **NF4**：为近似正态分布权重设计的 4-bit 数据类型；“信息论最优”有分布假设，不表示对任意激活或权重都优于所有格式；
- **Double Quantization**：进一步量化量化常数，降低平均存储；
- **Paged Optimizers**：利用统一内存缓解长序列或大 batch 引起的峰值显存。

必须纠正的数字是：原论文报告在**单张 48 GB GPU**上微调 65B 模型，不是 24 GB。该结果也不等于任意 65B、任意序列长度和任意 batch 都能复现；还需说明 checkpoint、LoRA 目标层、激活检查点、优化器和实现版本。

## 3. 先列显存账本，再谈“模型能否训练”

训练峰值显存至少包括：

```text
参数 + 梯度 + 优化器状态 + 激活 + 临时通信/算子缓冲 + CUDA 上下文与碎片
```

推理峰值则通常包括：

```text
权重 + KV Cache + 激活/工作区 + 请求调度与图捕获缓冲 + 碎片
```

仅用“参数量 × 2 字节”只能估算 BF16/FP16 权重，不能估算训练。以 Adam 为例，是否保留 FP32 master weights、梯度精度、优化器状态精度和分片方式会显著改变每参数字节数。

### 3.1 KV Cache 公式

对标准 decoder-only Transformer，在忽略对齐和运行时开销时：

$$
M_{KV}=B\cdot L\cdot T\cdot 2\cdot H_{KV}\cdot d_h\cdot s,
$$

其中 $B$ 是并发序列数，$L$ 是层数，$T$ 是已缓存 token 数，$2$ 表示 K 与 V，$H_{KV}$ 是 KV 头数，$d_h$ 是每头维度，$s$ 是每元素字节数。

- MHA：$H_{KV}=H_Q$；
- GQA：$H_{KV}<H_Q$；
- MQA：通常 $H_{KV}=1$；
- MLA 等结构不能直接套用 GQA 公式，应按实际缓存的潜变量、RoPE 分量和实现计算。

因此，不能用 $d_{model}$ 代替所有架构的 $H_{KV}d_h$，也不能看到“72B”就推出 KV Cache 大小。

## 4. 数据并行、分片与模型并行

| 方法 | 切分对象 | 主要通信 | 解决的约束 |
|---|---|---|---|
| DDP | 数据；每卡保留模型副本 | 梯度 all-reduce | 吞吐扩展，模型单卡可放下 |
| ZeRO-1 | 优化器状态 | 依实现而定 | 优化器显存 |
| ZeRO-2 | 再分片梯度 | reduce-scatter/all-gather 类操作 | 梯度与优化器显存 |
| ZeRO-3 | 再分片参数 | 参数 all-gather、梯度 reduce-scatter | 模型状态显存 |
| FSDP | 按包裹单元分片参数、梯度和优化器状态 | all-gather、reduce-scatter | PyTorch 原生全分片数据并行 |
| TP | 切分层内矩阵与头 | 频繁 collective | 单层过大、矩阵并行 |
| PP | 按层分 stage | stage 间激活通信 | 模型深度和跨节点扩展 |
| CP/SP | 切分上下文或序列维 | attention/序列相关通信 | 超长上下文和激活 |

FSDP 受 ZeRO-3 启发且目标相近，但不能在所有实现细节上直接写成“FSDP = ZeRO-3”。FSDP 的 wrap 边界、sharding strategy、prefetch、mixed precision、state dict 和 device mesh 都会改变行为。

### 4.1 为什么没有“100B 以上必须 Megatron”的阈值

选型取决于：

- 单层参数和激活能否放入设备；
- NVLink/NVSwitch、PCIe 与跨节点网络拓扑；
- 序列长度、micro-batch 和流水线气泡；
- 通信与计算能否重叠；
- checkpoint、容灾和团队维护成本。

大规模训练常组合 DP/FSDP、TP、PP、CP，而不是二选一。参数量本身不足以决定并行策略。

## 5. 激活、吞吐与通信优化

### 5.1 Activation Checkpointing

它不保存部分前向激活，反向时重算，从而以额外计算换显存。节省比例和时间代价取决于 checkpoint 边界、attention 实现、序列长度及通信重叠，不能固定回答“省 50%、慢 20%”。

### 5.2 混合精度与数值稳定性

区分参数存储、计算、梯度归约和优化器状态的 dtype。BF16 的指数范围通常比 FP16 更友好，但仍需监控 loss scale、梯度范数、溢出、NaN、softmax 和归一化层。

### 5.3 容量规划

全局 batch 通常为：

$$
B_{global}=B_{micro}\times N_{data}\times N_{accum},
$$

但 sequence packing、动态长度、token-based batch 和流水线 micro-batch 会改变实际 token 数。报告训练配置时应同时给出 sequences/step 与 tokens/step。

## 6. 推理服务：先定义指标

| 指标 | 含义 | 常见误区 |
|---|---|---|
| TTFT | 请求到首 token 的延迟 | 易受排队、prefill 长度和 prefix cache 影响 |
| TPOT | 输出阶段相邻 token 时间 | 不等于端到端平均延迟 |
| ITL | 交互式 token 间延迟 | 需说明统计区间与流式协议 |
| 吞吐 | 单位时间完成的 token 或请求 | 必须说明 input/output、batch 和并发 |
| goodput | 满足 SLO 的有效吞吐 | 比峰值吞吐更接近线上价值 |
| p50/p95/p99 | 延迟分位数 | 平均值会隐藏尾延迟 |

一个系统可以提升总吞吐，却因排队和大 batch 恶化单请求延迟。因此“更快”必须绑定 SLO 和负载曲线。

## 7. PagedAttention 与连续批处理

PagedAttention 将每个请求的 KV Cache 划分为逻辑块，并通过块表映射到非连续物理块，以减少预留、内部碎片和复制；Copy-on-Write 可让并行采样或 beam 共享前缀。

三条重要边界：

1. KV block 的大小是运行时配置与实现概念，不是固定的操作系统 4 KB 页；
2. 分页能显著减少浪费，但不能保证“零碎片”或固定 95% 利用率；
3. vLLM 不只等于 PagedAttention，还包括调度、连续批处理、模型执行和分布式能力；TensorRT-LLM 也不只等于算子融合。比较时应固定模型、精度、硬件、长度分布和 SLO。

Prefix caching、chunked prefill、speculative decoding 和量化可以叠加，但它们会竞争显存、带宽和调度优先级，需要在真实流量回放上验证。

## 8. 量化：格式、校准与内核缺一不可

| 类型 | 核心问题 | 面试应说明 |
|---|---|---|
| Weight-only PTQ | 只量化权重 | group size、对称性、校准集、反量化内核 |
| W8A8/W4A8 | 权重与激活量化 | outlier、smooth/scale 策略、累加精度 |
| GPTQ | 基于近似二阶信息逐层量化 | 校准数据和实现变体 |
| AWQ | 用激活统计保护显著权重通道 | 搜索/缩放策略及 kernel 支持 |
| GGUF | 文件与量化生态，不是单一算法 | 具体量化类型、后端和硬件 |

模型文件缩小不保证端到端加速。速度取决于硬件是否有对应低精度算力、kernel 是否避免反量化瓶颈、batch 和 shape 是否合适。验收要同时看任务质量、长文本、校准误差、吞吐、TTFT、TPOT 和峰值显存。

## 9. 场景题的标准推理顺序

### 9.1 “72B 模型能否在 8×80 GB 上训练？”

先追问精度、优化器、全参还是 PEFT、序列长度、batch、并行拓扑和是否允许 offload。然后分别估算模型状态、激活与临时缓冲；再选择 FSDP/ZeRO、TP/PP/CP、checkpointing 和 mixed precision；最后用小规模 profile 验证。不能用“权重每卡 18 GB，所以还剩 62 GB”直接推出 batch。

### 9.2 “线上突然 OOM，先查什么？”

按时间线检查请求长度与并发、KV block 使用、prefix/beam 数量、图捕获和 workspace、量化或模型版本、内存泄漏与碎片；同时对比 scheduler 队列和 p99。先复现峰值条件，再调低 token budget、并发或 block 配置，而不是直接重启掩盖问题。

### 9.3 “吞吐提升但用户变慢，为什么？”

可能是调度器用更大 batch 拉高总吞吐，却增加排队、prefill 阻塞或 token 间延迟。需要用 arrival-rate sweep 绘制 goodput—latency 曲线，并设置 TTFT/TPOT 双 SLO。

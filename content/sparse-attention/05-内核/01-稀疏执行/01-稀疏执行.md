# 稀疏执行

模型给出的 top-k 只是一串逻辑位置，GPU 需要的是一批形状明确、地址可算、彼此负载接近的工作单元。从前者走到后者，通常还要排序、去重、按页映射、生成 offset、分桶、分配 workspace，再启动真正的 attention kernel。论文把这些操作统称为「选择」，profile 却会把每一项都记进延迟。

稀疏执行的核心矛盾很直接：候选越细，算法越少算；候选越规则，硬件越容易跑满。元素级索引最贴近 token 重要性，却产生随机 gather。块级索引带入无关 token，换来连续矩阵 tile。页级索引能直接复用 KV cache 页表，但页大小由内存管理决定，未必等于 attention 的最佳 tile。

## 1. 索引先变成工作表

### 1.1. 排序与去重

多个路由分支可能同时选中相同位置。局部窗口、sink、动态 top-k 合并后若不去重，同一 KV 会重复进入 softmax，数值语义已经改变。去重后的索引按物理地址排序，通常能提高相邻线程的访问合并；代价是排序本身和逻辑优先级丢失。若需要保留分支 gate，应先决定重复项的权重合并方式。

块稀疏常用 CSR/BSR 表示：`indptr` 给出每个 query block 的候选区间，`indices` 保存 KV block 编号。FlashInfer 的 block-sparse 接口采用相同思路，并通过 `plan()` 生成可复用的辅助结构，再由 `run()` 执行。索引仍在 GPU 流中消费，避免回到 CPU 同步。

### 1.2. 地址生成

连续 KV 的地址可以由起点与步长计算；paged KV 还要先查 block table，把逻辑页号映射到物理页。元素索引则为每个 token 计算地址。地址算术通常不贵，分散地址造成的小事务、TLB 压力和 cache miss 才是问题。

地址生成还要守住请求边界。continuous batching 把多条请求的 KV 页混在同一个物理池里，逻辑页号必须先查该请求的页表，不能把 batch 内页号直接当全局页号。prefix sharing 允许多条请求指向同一只读页，无需复制 K/V；若 kernel 把逻辑连续误当物理连续，就会读到错误上下文。

索引宽度也值得核算。百万 token、16-token 页约有 62500 页，单请求页号可用 32 位整数。把所有 offset 都升成 64 位更省心，却增加整数带宽与寄存器压力。常见做法是总长度使用 64 位计数，kernel 热循环里的局部页号保持 32 位，并在 plan 阶段检查上界。

## 2. 三种粒度

### 2.1. 元素、块与页

元素级适合低 batch decode 与高价值 token 精选，但很难直接喂给大矩阵 tile。实现可能先 gather 成连续缓冲区，再调用 dense attention；这增加一次读写，却让后续计算规则。块级可以直接遍历 nonzero tiles，适合 prefill 与训练。页级不搬 KV，只带页号进入 paged attention，服务系统更容易接受。

粒度转换要计入物理预算。token top-k 为 2048，若扩张到 64-token block，最坏可触及 2048 个块，也就是 131072 个 token；只有候选天然聚集时，扩张才便宜。报告逻辑 top-k 而隐藏物理读取，会让算法稀疏率与实际带宽完全脱节。

### 2.2. coalescing 与 tile 利用率

warp 内线程访问相邻地址时，显存事务可以合并。随机 token gather 让一次事务只用到少量字节；连续 block 让 K/V 载入进入规则向量或 TMA 路径。另一方面，块内有效 token 太少会浪费 tensor core 乘加。最佳块长取决于候选聚集度、head dimension、dtype 与 GPU 架构，没有跨设备固定答案。

块长还与共享粒度耦合。一个 GQA 组的多个 query heads 若共享候选，同一 K/V tile 能被更多计算复用；各 head 独立候选时，块并集扩大，读取也会增加。选块实验至少扫过候选聚集度、GQA 比例和 batch，单一随机 mask 的结果很难代表真实路由。

元素、块和页也能串联：selector 返回 token，运行时按页去重，再在页内用小 mask 跳过无效 token。地址仍以页为单位，QK 保持更细粒度；代价是每个 tile 多一份 mask 与分支。省下的乘加能否覆盖 mask 解码，只能由目标硬件实测。

## 3. online softmax 保持语义

每个 KV tile 产生局部最大值 $m_b$、指数和 $l_b$ 与未归一化输出 $o_b$。合并新 tile 时，用全局最大值 $m'=\max(m,m_b)$ 重标定旧状态：

$$
l'=e^{m-m'}l+e^{m_b-m'}l_b,
$$

$$
o'=e^{m-m'}o+e^{m_b-m'}o_b.
$$

遍历完候选后输出 $o/l$。KV block 的顺序可以改变，候选集合与 mask 不能改变。空行、重复索引、最后一页无效槽位和因果边界都要在进入指数前处理。

online softmax 还允许 split-KV。多个 CTA 各自处理候选子集，输出局部 $(m_s,l_s,o_s)$，归并 kernel 再按相同的重标定公式合并。长行因此获得更多并行度，短行却多付一次写回和归并。split 数量应随候选长度变化，不能对所有请求固定同一值。

FP16/BF16 输入通常用 FP32 保存累积状态。索引排序会改变加法顺序，结果不必逐 bit 等于稠密参考；误差应在不同长度、分数幅度和候选顺序下保持稳定。若某次排列产生 NaN，应先检查全 mask 行、指数溢出和无效页。

## 4. 变长批处理与 workspace

continuous batching 中，每个请求的 query 数、KV 长度和候选块数不同。把所有行 padding 到最大值最简单，也最浪费。ragged tensor 用 offset 紧凑排列 Q/O，用 `indptr` 描述候选；调度器再把长行切成多个 split，让 persistent CTA 从队列取任务。

split-KV 会产生多个部分输出与 log-sum-exp，随后再归并。workspace 保存调度表、部分输出和整数索引。容量必须按 batch 上界预留，CUDA Graph 捕获还要求地址稳定。workspace 太小触发临时分配或 fallback，尾延迟会突然上升。

规划与执行的边界决定 CUDA Graph 能否使用。图捕获要求 grid 与缓冲区地址稳定，实际候选数可通过 `indptr` 和有效任务计数变化。若每步都按精确长度重新分配 workspace，图捕获收益消失；若永远清零全局最大缓冲区，固定成本又会拖累短请求。按容量分档是一种折中。

变长 batch 还会产生 wave quantization。假设 120 个短任务各耗 1 个单位，8 个长任务各耗 20 个单位；静态映射后，最后一波可能只剩 8 个 CTA 工作。persistent queue 能让空闲 CTA 继续取任务，或者预先拆开长行。profile 应展示任务耗时分布与最后一波占用，平均 blocks/row 看不出这条长尾。

## 5. 训练与 fallback

训练反向沿前向块表计算 $dQ,dK,dV$。多个 query tile 更新同一 KV block 时会产生写冲突，可用原子加、分段归约或按 KV 反排任务。保存索引节省重算，增加 activation；重算索引则要求 top-k、随机状态和量化完全可复现。

稀疏路径也需要明确 fallback：候选为空、形状不支持、块数接近稠密、workspace 不足或特定 head dimension 未编译时，转入 dense FMHA。fallback 必须带计数器。一次请求悄悄回退仍能得到正确答案，却会让延迟分布出现难以解释的长尾。

反向可能把前向收益吃掉。多个 query blocks 选中同一热门 KV block，$dK,dV$ 写入形成热点；原子加正确却会串行，按 KV block 重排任务能减少冲突，但需要转置稀疏表。训练 benchmark 要分别报告 forward、backward 和索引构造。

fallback 阈值应来自实测交叉点。某种 prefill 形状候选率超过 60% 时 dense 更快，低 batch decode 可能到 90% 才值得切换。运行时根据设备、dtype、head dimension、行长与稀疏率查表，比一个全局开关可靠。

## 6. 路线入口

[索引到 Kernel](./01-索引到Kernel/01-索引到Kernel.md)把上述环节连成完整数据流，进一步讨论 gather 是否值得、roofline 怎样估算交叉点，以及 Nsight 中哪些指标能区分地址离散、tile 空转和调度不均。

判断稀疏 kernel 时，先问实际读了多少 KV，再问 tensor core 发射了多少有效乘加，随后核算索引与 workspace。三项都落到 profile，逻辑稀疏才算变成真实加速。

同一组输入还要保留 dense 基线与固定候选基线，路由、布局和 kernel 的代价才能分别归因。

# 评测协议

稀疏 attention 的评测沿着一条因果链展开：selector 产生候选，kernel 读取候选，模型生成答案，服务系统交付请求。最终答案、kernel 时间各自只覆盖其中一段。协议的基本单位是一条可回放请求，其中同时保存任务标签、证据位置、候选统计、dense 对照和系统时间线。

## 1. 三层对照

### 1.1. Full Attention 回退

同一 checkpoint 若支持 dense 与 sparse 两条路径，先固定 prompt、生成参数和随机种子，分别运行。质量差额定义为

$$
\Delta Q=Q_{sparse}-Q_{dense}. \tag{1}
$$

绝对分数回答模型能否完成任务，$\Delta Q$ 更接近稀疏机制造成的变化。若 dense 自身已经失败，sparse 的失败不能全归给选择器。逐样本保留四种组合：两者都对、dense 对 sparse 错、dense 错 sparse 对、两者都错。

### 1.2. 固定候选与完整路由

系统对照至少有 dense kernel、固定候选 sparse kernel、selector 加 sparse kernel 三档。第一档给设备基线，第二档隔离 kernel，第三档才是完整方案。固定候选很快、完整路径不快，问题在索引或调度；两条 sparse 路径都慢，再检查块长、访存与候选率。

## 2. 长上下文任务网格

### 2.1. 长度与证据深度

上下文长度按 4K、8K、16K、32K、64K、128K 等档位扫描。每档把证据放在 10%、30%、50%、70%、90% 深度，并对位置加入随机扰动，避免固定模板。总长度与 query 到证据的距离分别记录，因为长 prompt 尾部证据主要测试容量，开头证据才真正测试远距访问。

Needle 类任务适合做连通性筛查；RULER 提供可配置长度与复杂度的合成任务，覆盖单/多 key 检索、变量追踪与聚合；LongBench 包含中英文、多文档问答、摘要、few-shot、合成和代码任务。三类任务承担不同角色，不能用一张 needle 热力图替代真实任务。

### 2.2. 多证据与相似干扰

证据数设置为 1、2、4、8，并加入同实体、同模板或旧版本片段。记录 any-evidence recall、all-evidence recall 与最终答案。若单证据召回各为 95%，四段证据在粗略独立假设下同时命中的概率只有 $0.95^4\approx81.45\%$，多证据能放大 selector 的小漏检。

## 3. 路由与物理执行

候选集合 $S_i$ 与 dense 教师 top-$m$ 集合 $G_i$ 的召回为

$$
R_i=\frac{|S_i\cap G_i|}{|G_i|}, \tag{2}
$$

概率质量覆盖为

$$
C_i=\sum_{j\in S_i}p^{dense}_{ij}. \tag{3}
$$

两者按层、head、query 位置、证据距离和长度分桶。还要记录逻辑 token 数、去重后 block/page 数与实际 HBM 字节。逻辑 top-k 很小而页扩张很大时，质量预算与系统预算已经不是一个数。

候选召回的参照也要固定。教师 top-$m$ 中的 $m$ 与学生预算 $k$ 分开记录；$m=k$ 强调排序一致，$m>k$ 可以观察学生覆盖教师高质量集合的程度。attention mass 采用 softmax 后概率，跨 head 聚合时说明是均值、最大值还是 GQA 组内求和。

带标注证据的任务再计算 token、span、block 三个粒度。候选只碰到 span 的一个标点不算完整覆盖；块级方法读取了证据所在块，也要确认有效 mask 包含实际 span。多证据问题同时给 any 与 all recall，避免平均 token recall 掩盖推理链断点。

## 4. 系统时间线

离线吞吐、TTFT、TPOT/ITL 分开测量。TTFT 包含调度、prefill、selector、索引与首 token；TPOT 在稳定 decode 区间统计，并同时给 P50、P95、P99。请求吞吐用 requests/s 与 output tokens/s 表示，固定输入/输出长度分布和并发。

GPU 指标包含 DRAM bytes、有效带宽、L2 hit、tensor core active、workspace 与峰值显存。路由、top-k、索引、plan、attention、split 归并分别计时。Microbenchmark 与端到端测试保留相同 shape，才能解释局部加速为何被其他阶段吞掉。

Prefill 按输入 tokens/s 与 TTFT 观察，decode 按 TPOT、ITL 和 output tokens/s 观察。一次请求输出长度会改变两个阶段在总时间中的权重，因此同时给固定 1、32、128 token 输出场景。吞吐实验达到稳态后再采样，JIT、首次权重加载与 cache 冷启动另列为冷启动指标。

显存分成模型参数、KV cache、attention workspace、selector cache 和临时索引。只报峰值无法说明稀疏方法是否真的缩小 KV；动态稀疏通常仍保存完整 KV，只减少读取。每个分项在相同 batch、长度和 dtype 下比较。

## 5. open-loop 与 closed-loop

closed-loop 中，每个客户端等上一个请求完成后再发送，适合观察交互延迟；open-loop 按给定到达过程注入请求，即使系统排队也继续发送，更接近固定业务负载。两者的吞吐与尾延迟不能混用。

open-loop 扫描到达率，找到延迟开始陡升的饱和点；closed-loop 扫描并发客户端数。每个点报告队列时间、执行时间和总时延。稀疏方案若单请求快却因 ragged 候选降低 batching 效率，open-loop 更容易暴露。

输入长度分布至少有定长、均匀与长尾三组。长尾可用 80% 短请求加 20% 长请求，模拟线上少量超长上下文拖住 batch。输出长度同样固定分布，防止某个方案恰好更早停止而获得虚假吞吐优势。请求顺序使用同一 trace 回放。

prefix cache 命中会大幅改变 TTFT。基准分成冷 prefix、固定命中率和完全命中三档，并记录被复用的 token 数。稀疏 page table 与共享 prefix 的交互属于方案能力，但必须在两条基线使用相同命中 trace。

## 6. 统计与复现

任务样本用配对 bootstrap 计算 $\Delta Q$ 的 95% 置信区间，因为 dense 与 sparse 运行的是同一批样本。时延分布用独立重复与 bootstrap 分位数区间，保留原始请求级记录。只报一次均值看不到尾部，也无法判断小差异是否超过随机波动。

配置记录包括模型与 commit、权重、tokenizer、prompt、生成参数、benchmark 版本、长度截断方式、GPU、驱动、框架、内核、dtype、时钟策略、batch、并发、预热与计时边界。实验先验证 dense 回退输出，再锁定配置运行完整矩阵。

样本数在实验前按希望检测的效应确定。准确率差只有 0.5 个百分点时，几十个样本远远不够；昂贵的长序列测试可先跑 pilot 估计配对差值方差，再计算正式样本数。所有提前停止规则预先写入协议，避免看到有利结果便结束。

随机种子控制样本生成、needle 位置、采样解码和请求到达。贪心解码仍可能受并行归约产生的末位差异影响，因此保存实际输出。每次实验输出逐请求原始表、汇总脚本版本与校验和，汇总结果可以从原始表重新生成。

## 7. 失败归因的最小闭环

质量下降样本按 dense 成败、标注证据、教师 mass 和候选覆盖分组。证据漏选对应 selector 分支；候选覆盖而输出错误对应 attention 数值、层间传播与训练适配分支。系统性能按物理 HBM 字节、索引和 kernel 分解；P99 异常再按最大候选行、workspace 扩容、CUDA Graph miss 与 fallback 切片。

每次归因至少落到一个可反驳假设。例如「页扩张导致多读」要能由逻辑候选字节、物理 DRAM bytes 与改用小页后的对照验证；「长度外推导致漏选」要有相同证据深度、不同总长度的召回曲线。没有对应观测量的解释留在待验证项。

回归门槛在实验前登记：质量非劣界、TTFT/TPOT 改善目标、P99 上限、显存预算与 fallback 比例。一次运行可同时通过部分门槛、失败部分门槛，结果按原始维度保留，不合成一个掩盖取舍的总分。

数据管线先产生不可变样本清单，再由 dense 与 sparse 共同消费。request ID、tokenized prompt hash 与证据 span hash 能检查两条路径输入一致；服务回放另保存到达时间戳和 prefix 命中状态。任何缺失字段都会使该请求无法进入配对分析。

## 8. 协议入口

[质量与系统联合评测](./01-质量与系统联合评测/01-质量与系统联合评测.md)给出逐请求 schema、长度—深度—证据网格、置信区间手算、服务负载和失败归因矩阵。一项结论只有在质量差额、路由覆盖和机器工作量能用相同请求 ID 对齐时，才具有可复算性。

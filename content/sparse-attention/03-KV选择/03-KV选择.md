# KV 选择：读取、保留与淘汰

自回归解码每步只有一个新 query，却要读取不断增长的历史 KV。于是长上下文瓶颈从 prefill 的配对计算转向缓存容量和 HBM 流量。KV 选择至少包含两种不同动作：查询时只读取仍然存在的部分状态，以及提前删除被判断为以后不再需要的状态。前者下一步仍可改变选择，后者一旦误删便无法恢复，两者的质量风险和系统收益不能混为一个「压缩率」。

本章用状态生命周期组织问题。对第 $t$ 步，需要写清哪些 KV 被创建、驻留在哪一级存储、何时形成索引、哪些被读取、哪些被迁移或淘汰。若选择索引仍需扫描完整 cache，节省的只是 value 聚合；若索引可在片上或分层缓存中查询，才可能减少 HBM 读取。量化、分页、前缀共享和卸载改变每个状态的字节数与位置，也会改变稀疏选择的交叉点。

## 先算清 KV cache 的对象与成本

设 Transformer 有 $L$ 层，每层 KV head 数为 $H_{kv}$，单个 head 维度为 $d_h$，缓存元素使用 $s$ byte。保存长度为 $n$ 的单条序列，需要的 KV 容量近似为

$$
M_{KV}=2LnH_{kv}d_hs.
$$

系数 $2$ 分别对应 key 和 value。多查询注意力（MQA）与分组查询注意力（GQA）通过减少 $H_{kv}$ 降低容量，但没有自动减少本步读取的 token 数。分页 KV cache 改善不规则请求的空间分配，也没有改变逻辑内容。Sparse Attention 若想进一步降低 decode 带宽，需要在发起 HBM 读取之前得到较小的地址集合，并让内核只加载这些地址对应的 KV。

容量和读取量也要分开。某种方法可以保留全部历史 KV，只在每步读取其中 $k$ 个位置；此时峰值容量仍随 $n$ 增长，单步注意力流量接近 $O(k)$。另一种方法把 cache 固定在 $k$ 个位置，容量与流量都受到限制，但被删除状态无法重新参与后续注意力。还有一类方法把冷 KV 迁移到主机或更慢介质，设备容量下降，命中失败时会增加传输和尾延迟。三个方案在平均 token/s 上可能接近，面对延迟引用时的行为却完全不同。

## 重要性不是一个静态属性

注意力权重只描述某个 query 下的相对混合比例。一个历史 token 在连续数千步中权重很低，不代表未来不会突然成为关键约束。用累计权重定义 heavy hitter 可以保存长期高频状态，却可能漏掉低频但决定性的信息；只保留最近窗口能稳定处理局部模式，却无法独立应对远距离引用；永久保留 sink token 有助于窗口截断后的注意力稳定，也不等于保存了任务语义。

因此选择器需要说明时间尺度。逐步评分每生成一个 token 就更新重要性，响应快但成本高；按块或固定周期更新索引，能摊薄开销，却会在更新间隔内使用过期判断。跨层共享评分可以减少重复计算，但不同层关注的关系并不相同。若浅层偏向词法相似、深层偏向任务状态，统一淘汰表可能让某一层失去需要的信息。评价不能只报告平均保留率，还要观察每层、每 head 与不同生成阶段的选择差异。

SnapKV 一类方法利用观察窗口估计 prompt 中重要位置并压缩后续缓存，Quest 一类方法通过页级统计先筛选候选页，再读取页内 KV。二者都减少访问范围，前者更接近一次性压缩，后者更接近查询时选择。把方法放进生命周期后，差别会很明确：评分使用哪个 query 区间，索引何时建立，生成过程中是否更新，被排除状态是否仍存在，恢复需要什么额外路径。

## 选择粒度决定系统形态

token 级选择在语义上细，但地址离散。GPU 读取许多不连续小片段时，实际传输会按 cache line 或更大的事务粒度发生，逻辑上未选中的字节仍可能进入芯片。块级或页级选择牺牲细粒度稀疏率，换来连续地址、较少索引和更规则的 kernel。块大小于是同时影响质量与执行：块大时关键 token 周围携带更多无关内容，块小时索引、排序和 gather 成本增加。

批处理又增加一层约束。连续 batching 中，不同请求的序列长度、生成进度和候选地址都不同。若每条请求独立选择，内核面对 ragged 的块表；若为批内请求合并候选，可以提高复用，却读取额外 KV。prefix cache 让多条请求共享前缀物理页，淘汰策略必须区分逻辑引用与物理引用，不能因一条请求结束便释放仍被其他请求使用的页。KV 选择最终必须与推理引擎的页表和引用计数协同。

分布式推理还要问 KV 位于哪里。张量并行通常让不同设备持有各自 head 或通道对应的 KV；序列并行或 context parallel 可能按位置切分。动态选择若跨越设备边界，就要发送 query、远程拉取 KV，或在各设备局部选择后再合并输出。局部 top-k 不一定等价于全局 top-k，合并过程也有通信成本。只有把设备映射写进选择算法，才能判断带宽是否从 HBM 转移到了互连。

[读取选择](./01-读取选择/01-读取选择.md)保留完整 KV, 每个 decode step 再根据当前 query 决定读取哪些页. 这条路线先用 [Quest 页级选择](./01-读取选择/01-Quest页级选择/01-Quest页级选择.md)建立可计算的参照: 每页维护 key 的逐维最小值与最大值, 用一个只读摘要的上界筛选候选页, 随后只为候选页执行精确 attention. 它直接降低单步 HBM 流量, 但完整 cache 仍随上下文增长, 因而不能拿读取稀疏率冒充容量压缩率.

[缓存驱逐](./02-缓存驱逐/02-缓存驱逐.md)把容量限制提前到状态生命周期: 新KV进入固定槽位时, 系统必须决定哪一项永久离开. [H2O](./02-缓存驱逐/01-H2O/01-H2O.md)用累计attention保存反复访问的heavy hitters, 同时为最近token保留观察窗口. 这条路线能释放KV容量, 也承担不可恢复的误删风险; attention统计、page回收和位置元数据必须一起实现.

[动态路由](../02-动态路由/02-动态路由.md)回答当前 query 怎样生成候选，[训练](../04-训练/04-训练.md)继续处理选择器怎样获得监督和适应长度变化，[内核](../05-内核/05-内核.md)则把候选页转成真实的 gather 与 attention 执行。KV 选择位于三者中间：它规定状态是否存在、驻留在哪儿，并为路由器提供可搜索的对象。若状态边界不明确，路由复杂度和内核流量都无法复算。

失效测试应主动制造未来相关性变化。例如某个名字在 prompt 开头只出现一次，生成很久以后才要求精确引用；多份相似文档只在一个数字上不同；同一事实被后文更新，模型必须使用较新的版本。此类测试能区分累计注意力、近期窗口和内容检索的能力边界。质量下降还要与缓存命中、索引更新和端到端延迟一起记录，才能知道错误来自信息已经删除、候选没有召回，还是内核没有按预期执行。

## 导航

KV字节明细建立后, 再比较只读子集、永久淘汰与外存召回三条路线。每种方法都要说明选择粒度、恢复能力、与 GQA/MQA 的关系，以及真实推理引擎是否能跳过未选块。

读完本章后，读者应能沿单个 token 的生成过程画出 KV 状态变化：新状态怎样写入，索引怎样更新，哪些页参与候选，哪些字节被加载，哪些状态仍可在未来恢复。也应能看出「缓存压缩倍数」没有独立意义，只有与质量任务、读取流量、更新成本和恢复能力一起报告，才足以支持部署判断。

工程复现时还要固定模型的层数、KV head 数、head 维度、缓存精度、页大小和请求长度分布。相同的保留比例放在 MHA 与 GQA 上，对总显存的绝对节省不同；相同的候选 token 数放在连续内存与分页布局上，读取事务也不同。报告这些配置不是附属信息，它们决定选择器有没有越过索引开销与稠密读取之间的性能交叉点。只有质量和系统两侧在同一组配置下测量，KV 选择的结论才可以复算。

稠密回退提供实验参照, 用同一模型、同一请求复算质量差额和系统差额, 也能暴露被漏选掩盖的问题。若恢复全部 KV 后答案仍然错误，问题不在选择器；若质量恢复但时延没有明显变化，瓶颈可能已经转移到线性层、调度或跨设备通信。

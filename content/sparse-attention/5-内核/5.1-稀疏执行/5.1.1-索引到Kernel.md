# 从索引到 Kernel

动态稀疏 attention 经常被画成 `gather → attention`。实际执行包含一条小型编译流水线：候选索引经过合并、去重与排序，逻辑位置映射到物理页，调度器按行长生成任务，kernel 逐 tile 装载 K/V 并维护 online softmax，必要时归并 split-KV 的部分输出。任一环节失去规则性，理论省下的乘加都会在访存或调度里还回去。

## 1. 候选索引的规范化

### 1.1. 合并、去重、排序

设动态选择集合为 $D_i$，局部窗口为 $W_i$，固定 sink 为 $A_i$，真正的候选是

$$
S_i=\operatorname{unique}(D_i\cup W_i\cup A_i). \tag{1}
$$

去重关系到数值正确性。同一个 key 若出现两次，softmax 分母会把它计算两遍，输出也获得双倍路径。简单覆盖、保留最大路由分数和累加分支 gate 的语义不同，必须在 attention 前确定。 按物理地址排序通常改善读取，但会改变浮点归约顺序。高精度参照允许微小误差，不能允许候选丢失。索引还要验证范围、因果性与 batch 所属；错误页号比普通数值误差危险，因为它可能读取另一请求的缓存。

### 1.2. 从 token 到 block table

元素索引可以直接 gather，也可以扩张到块：

$$
b_j=\left\lfloor j/B_k\right\rfloor. \tag{2}
$$

扩张后再次去重，生成每个 query block 的 `indptr` 与 `indices`。例如 token 候选 $(1,2,63,64,65,127)$，$B_k=64$，对应块 $(0,1)$；6 个逻辑候选变成最多 128 个物理 token。聚集候选非常划算，分散候选则可能放大读取。 Paged KV 再做一次映射。逻辑块号查请求的 block table 得到物理页，页内 offset 保留。页长与 kernel KV tile 不相等时，一个页可能拆成多个 tile，或多个小页组合成一次工作。FlashInfer 用 BSR 抽象统一页表与 block-sparse attention，`indptr` 表示行边界，`indices` 表示非零列块。

**一次具体的索引转换。**

假设 batch 中第 2 条请求有 10 个逻辑页，页长 16，物理页表为 $(41,7,83,19,\ldots)$。selector 返回 token $(18,23,70,71,72)$，先除以 16 得到逻辑页 $(1,4)$，页内位置分别是 $(2,7)$ 与 $(6,7,8)$；查表后物理页是 7 与 `pageTable[4]`。若 kernel 使用 64-token KV tile，还要按逻辑顺序组合四个页，不能把物理页号直接整除，因为逻辑相邻页在物理内存中可能完全分散。 这说明索引至少包含三套坐标：token 位置负责因果与位置编码，逻辑页表示请求内顺序，物理页用于取地址。按物理地址排序能改善访存，却不能拿物理顺序计算 RoPE 或 causal mask。实现常把物理地址和逻辑位置成对打包，避免热循环反复查表。 索引规范化应独立测试。随机生成 page table、重复 token、跨页候选和未写满尾页，用 CPU 参考构造最终位置集合；GPU 结果逐项比较。attention 输出偶尔会掩盖索引错误，例如两个 value 恰好相似，单独比较索引更容易定位。

## 2. gather 还是直接稀疏读取

### 2.1. gather 的双重流量

先把随机候选 gather 到连续 scratch buffer，随后运行 dense tile，优点是矩阵计算规则。代价是 K/V 先从原 cache 读一次、写入 scratch，再被 attention 读一次。若每 token 的 K/V 共 $B_{kv}$ 字节，候选 $k$，gather 路径额外流量近似

$$
T_{gather}\approx 2kB_{kv}, \tag{3}
$$

其中一次写、一次再读，尚未计原始读取。低 batch decode 本就受带宽限制，这份复制可能抵消稀疏收益。 直接 sparse-load 避免中间缓冲区，但地址离散会降低事务利用率。选择取决于候选是否能在多个 heads、多个 query 或多层复用。只用一次的候选通常偏向直接读；一个 GQA 组共同使用、相邻 query 共享的候选更可能值得 gather。

### 2.2. coalescing 的实际含义

假设一次内存事务取 128 字节，warp 需要 32 个 BF16 标量共 64 字节。连续地址可能由一次事务覆盖；32 个线程若落在 32 个随机 cache line，理论有效字节仍是 64，实际搬运却可接近 4096 字节，利用率只有 $64/4096=1.5625\%$。cache 命中会改善结果，但不能假定长 KV 全在 cache 中。 块索引把同一页内 K/V 连续交给 warp 或 TMA。候选排序后，相邻块还能复用页表和 L2 line。profile 中应同时看请求字节、DRAM 实际字节与 L2 hit rate；只按张量尺寸估算，会遗漏事务放大。

**gather 的盈亏平衡。**

设直接稀疏读取的有效带宽为 $B_s$，连续 scratch attention 的带宽为 $B_c$，候选 K/V 数据量为 $T$。直接路径约为 $T/B_s$；gather 除原始读取外还要写入 scratch、随后再读，近似 $3T/B_c$。单次使用时，只有 $B_c>3B_s$，复制才可能靠更高连续带宽回本。 若 scratch 被 $r$ 个 query heads 复用，额外复制被摊薄，近似系数从 3 变为 $1+2/r$。$r=8$ 时为 1.25，GQA 共享候选便可能改变结论。复用要求 heads 使用同一 token 顺序、dtype 与位置变换；每个 head 各做一遍 gather 没有摊销。 scratch 还占 workspace，并引入生产者—消费者同步。小 batch 下，单独 gather kernel 的启动时间明显，可以把地址读取和 K/V 搬运融合进 attention。是否融合应由计时决定，源码里少一个 kernel 不代表数据少走一次 HBM。

## 3. 稀疏 tile 与 online softmax

### 3.1. 一个 query tile 的循环

kernel 为 $B_q$ 个 query 分配一个 CTA，读取其候选 KV blocks。每轮计算局部 logits

$$
Z_b=Q_{tile}K_b^\top/\sqrt d+M_b, \tag{4}
$$

随后得到局部最大值 $m_b$、局部指数和 $l_b$ 与 $P_bV_b$。累计状态 $(m,l,o)$ 用

$$
m'=\max(m,m_b),\quad
l'=e^{m-m'}l+e^{m_b-m'}l_b, \tag{5}
$$

$$
o'=e^{m-m'}o+e^{m_b-m'}P_bV_b. \tag{6}
$$

所有候选处理完再输出 $o'/l'$。这与 FlashAttention 的 IO-aware tiling一脉相承，区别在于 KV tile 列表来自稀疏索引。Triton 官方 fused-attention 教程也把行最大值、归一化和矩阵乘融合在 kernel 内。

### 3.2. mask 必须在指数之前生效

尾页含无效槽位，prefill tile 还可能穿过 causal 对角线。它们的 logits 必须设为负无穷，再参与局部最大值与指数和。softmax完成后再把输出清零会污染分母。候选为空时不能得到 $0/0$；系统应保证 local/sink fallback，或显式返回定义好的零输出并记录异常。 重复 block 若未清理，也会改变分母。跨分支需要不同 gate 时，更稳妥的方式是各分支独立 softmax 后门控合并；把重复 token 塞进同一个 softmax 再乘 gate，通常不等价。

**split-KV 怎样严格归并。**

设两个 split 的状态为 $(m_1,l_1,o_1)$ 与 $(m_2,l_2,o_2)$，取 $m=\max(m_1,m_2)$：

$$
l=e^{m_1-m}l_1+e^{m_2-m}l_2,\qquad
o=e^{m_1-m}o_1+e^{m_2-m}o_2. \tag{7}
$$

最终输出为 $o/l$。$o_s$ 必须是未除以 $l_s$ 的累积量；若各 split 先归一化，再直接求和，会给不同分母相同权重。 手算两个 split：$(m_1,l_1,o_1)=(2,3,6)$，$(m_2,l_2,o_2)=(1,4,8)$。取 $m=2$，得到 $l=3+4/e\approx4.472$，$o=6+8/e\approx8.943$，输出约 2.0。分别归一化后相加会得到 $6/3+8/4=4$，显然不对。接口返回 log-sum-exp，既能支持归并，也供 backward 重建概率。

## 4. tile 利用率与 roofline 手算

### 4.1. 逻辑 FLOPs 和物理 FLOPs

单个 query head 对 $k$ 个 token 的 QK 与 PV 约需 $4kd$ FLOPs。若 $k=2048,d=128$，约为 $1{,}048{,}576$ FLOPs。块长 64，逻辑候选扩张后实际读取 2560 token，物理 FLOPs 变成约 $1{,}310{,}720$，tile 填充效率为 $2048/2560=80\%$。 tensor core 利用率还受 $B_q$ 影响。prefill 的 $B_q=64$ 可形成大矩阵，decode 的 $B_q=1$ 很难独自填满设备；continuous batching 会把不同请求的 query/head 组合起来。若候选数差异很大，一个 CTA 处理长行，其余 CTA 提前结束，SM active 时间仍被最长行决定。

### 4.2. 带宽上限

假设 BF16、一个 KV head 的 $d=128$，每 token 的 K+V 为 $128\times2\times2=512$ 字节。读取 2048 token 约 1 MiB。GPU 可持续带宽若为 3 TB/s，理想下限约

$$
t_{mem}=\frac{1\ \mathrm{MiB}}{3\times10^{12}}\approx0.35\ \mu s. \tag{8}
$$

这是单 head 单 query 的纯搬运下限，没有页表、索引、启动、softmax、cache miss 和并发竞争。若随机事务让有效带宽只有峰值的 20%，下限变成约 $1.75\ \mu s$。因此少读 4 倍 KV，并不自动得到 4 倍加速。 算术强度可粗写为

$$
I\approx\frac{4kd}{2kd\,s}=\frac{2}{s}, \tag{9}
$$

$s$ 是每元素字节数，BF16 时约 1 FLOP/byte。decode 明显偏带宽侧；prefill 中同一 K/V tile 被多个 query 复用，强度随 $B_q$ 上升，更可能进入计算受限区。稀疏 kernel 必须分别测两个阶段。

**固定成本要放回总时间。**

端到端时间可写成

$$
t_{total}=t_{route}+t_{topk}+t_{index}+t_{attn}+t_{reduce}+t_{launch}. \tag{10}
$$

假设 dense attention 为 100 微秒，稀疏 attention kernel 降到 25 微秒，但路由 12、top-k 10、索引 8、归并 5、额外启动 6 微秒，总计 66 微秒，加速只有 $100/66\approx1.52$ 倍，不是 kernel 的 4 倍。若排序在 CPU 引入同步，代价还会更高。 长度扫描可以找到交叉点。短上下文中路由与启动近似固定，dense FMHA 更快；长度增长后 KV 读取占主导，稀疏路径才拉开差距。benchmark 至少覆盖多个 batch、query 长度、KV 长度、候选率与候选聚集度，并在同一计时边界内包含索引。 roofline 还要使用实测可持续带宽与算力，不用厂商峰值代替。ECC、功耗、并发 kernel 与显存频率都会改变上限。先用简单 memcpy 和 GEMM 在同一进程测基线，再判断 sparse kernel 离机器屋顶有多远。

## 5. ragged batch、调度与 workspace

### 5.1. 为什么需要 plan/run

服务 batch 每步变化，但同一步的所有层通常共享请求长度与页表形状。Inspector-executor 模式先 `plan()`：读取长度、`indptr` 和容量上限，决定 CTA 任务、split 大小与部分输出地址；各层再 `run()`。规划成本跨层摊销，也让运行 kernel 保持简单。 FlashInfer 的 wrapper 要求调用方提供浮点与整数 workspace。CUDA Graph 捕获时地址必须稳定，路由索引仍由调用方维护生命周期。容量按最大 batch、最大 row blocks 与 split 数预留；超限时应拒绝、重新规划或进入明确 fallback，不能越界写入。

**split-KV 与归并。**

一条超长候选行可以拆给多个 CTA，每个 CTA 输出局部 $(m_s,l_s,o_s)$，再用式 (5)(6)相同的重标定规则归并。这样提升并行度，却增加 workspace、第二个 kernel 和输出读写。短行无需 split，强行拆分只会增加固定成本。 ragged batch 的调度目标是减少 wave quantization。可按候选块数分桶，或让 persistent CTA 从全局队列领取下一项。分桶需要排序与恢复原顺序；队列方式带来原子竞争。profile 要看每 CTA 工作量分布，而非只看总 blocks。

**workspace 不是免费内存。**

若 batch 有 1024 行，每行最多 128 个候选块，32 位 indices 约占 512 KiB；`indptr` 很小，split-KV 部分输出更大。假设每行拆 8 份、32 heads、head dimension 128，以 FP32 保存 $o_s$，仅部分输出就是 $1024\times8\times32\times128\times4=128$ MiB，尚未加入 $m,l$ 和调度表。 实现会按形状减少 split，或让多个阶段复用缓冲区。容量规划应给出上界与常态用量，不能把预留 workspace 排除在显存占用之外。多模型共卡时，过大的常驻 workspace 会挤压 KV cache，间接降低并发。 CUDA Graph 中，计划状态与调用方路由存储的生命周期不同。异步 `run()` 未结束就覆写 indices，会出现偶发错读。双缓冲或事件同步能解决，代价是更多内存或等待。压力测试要在高并发下反复更新索引，单步正确性不足以发现生命周期错误。

### 5.2. 反向、fallback 与诊断

**训练 backward。**

前向保存 log-sum-exp 与候选索引，backward 可重算局部 logits，无需保存 attention 矩阵。$dQ$ 由一个 query tile 独占较容易；$dK,dV$ 会被多个 query tiles 累加。原子加实现简单但顺序不确定，反排为 KV-centric 任务可减少冲突，却要构造转置索引。 候选若来自 hard top-k，attention backward 只覆盖选中边，selector 的梯度由蒸馏、代理梯度或其他目标负责。反向重新 top-k 可能因浮点并列得到另一集合，所以应保存 forward indices，或保证完全确定性重算。

$dK,dV$ 的归约策略可以用一个小例子理解。四个 query tiles 都选中同一 KV block，query-centric backward 会让四个 CTA 同时写这块梯度；使用原子加无需额外索引，但热点严重。KV-centric backward 先构造反向邻接表，让一个或少量 CTA 收齐四份贡献，写入更规则，却增加一次稀疏转置和列表读取。候选复用越高，后者越可能值得。 activation checkpointing 会重新执行前向局部计算。保存 `indices`、每行 log-sum-exp 与随机状态，便可重算 QK 和概率；若连索引也重算，top-k 并列、FP8 舍入或 selector dropout 都可能换边。梯度检查要覆盖候选边界接近、重复索引以及一个 KV block 被大量 query 共享的情况。 训练速度还受参数梯度同步影响。稀疏 attention 减少本层计算后，all-reduce、MLP 与优化器占比上升，kernel 的局部加速会被 Amdahl 定律压缩。报告 forward/backward kernel、完整层和完整训练 step 三个层级，才知道优化落到了哪里。

**fallback 是正式路径。**

候选块占比接近 100% 时，dense FlashAttention 往往更快；FlashInfer 文档也建议已知稠密模式直接选择 dense FMHA。其他 fallback 条件包括 head dimension 不支持、block size 未编译、workspace 不足、空候选和设备架构不匹配。 每种 fallback 都记录原因、长度、batch 与耗时。线上只有总吞吐时，少数回退会被平均值遮住，却主导 P99。正确性测试还要强制触发每条回退，确认输出、mask 和 cache layout 与稀疏路径一致。 fallback 切换也有状态问题。sparse path 使用排序后的页表，dense path 可能使用原请求页表；二者必须共享相同的有效长度、RoPE 位置和 prefix 映射。若回退前已经 gather 出临时 KV，dense kernel 不应误把 scratch 当完整缓存。最安全的接口让两条路径都从同一逻辑 cache 描述开始，各自生成执行计划。

接近交叉点时可以引入迟滞：进入 sparse 的阈值与退回 dense 的阈值略有差别，避免 batch 形状轻微波动导致每步重编计划。计划缓存的 key 至少包含 GPU 架构、dtype、head dimension、块长、GQA 比例和容量档位，少一个维度都可能复用到不兼容 kernel。

**profile 从哪里下手。**

第一组指标看访存：DRAM bytes、实际带宽、L2 hit rate、load efficiency。字节远高于理论值，通常是随机事务、重复候选或 gather scratch。第二组看计算：tensor core active、achieved FLOPs、tile 有效比例。带宽不高、tensor core 也低，常见原因是形状太小或控制流碎片。 第三组看调度：SM occupancy、active warps、CTA duration 分布与尾部 wave。少数 CTA 极慢说明 ragged 行不均；大量短 kernel 则说明融合不足或 plan 被重复执行。第四组看固定成本：top-k、排序、去重、页表构造和 workspace 清零。attention kernel 很快而端到端不快，问题通常藏在这里。 profile 前先稳定测量环境。GPU 锁定时钟或至少记录频率，预热 JIT 与 autotune，排除首次分配，把 H2D 数据准备移出计时边界；随后用 GPU event 测设备时间，用服务端时钟测端到端延迟。两组数字不同很正常，差值正好暴露 CPU 调度、同步和队列等待。

候选分布也要固定保存。随机生成同一稀疏率的 mask，无法复现真实 selector 的局部聚集、热门页与长尾行。可匿名保存每行块数、块间距、页复用次数和 GQA 并集大小，再生成具有相同统计量的合成索引。这样不保留正文，也能把线上布局带回 microbenchmark。 比较实现时统一输出精度、mask 语义与 workspace。一个内核用 FP8 KV、另一个用 BF16，或者一个包含 top-k、另一个接收现成 indices，吞吐数字没有可比性。warm-up、迭代次数、同步位置和统计量用 median 还是 P99 也应固定。 一次完整诊断应在同一批输入上依次记录 dense FMHA、只运行索引、固定候选 sparse kernel 和端到端路由。固定候选正确而动态路径慢，优化索引；固定候选也慢，再看块长、地址与调度；数值错误则先缩到单 batch、单 head、少量 blocks，与朴素 gather attention 比较每轮 $m,l,o$。

## 6. 从性能剖析走到生产 Kernel

### 6.1. profile 决策树与正确性矩阵

**一棵 profile 决策树。**

先比较理论 K/V 字节与 DRAM 实测字节。实测高很多，检查重复索引、页扩张、事务利用率和 scratch copy；两者接近而带宽低，查看并发度、行长分布和 cache/TLB stall。带宽接近硬件上限，说明处在 roofline 的内存侧，继续优化 tensor core 收益有限。 DRAM 字节不高、耗时仍长时，看 kernel 构成。top-k 或 index 占比高，考虑跨 head/层复用、融合或更粗粒度；归并占比高，减少 split；主 kernel tensor core active 低，检查 $B_q,B_k,d$ 对齐和块内有效比例。 端到端比 kernel 慢很多时，检查 CPU—GPU 同步、动态分配、plan 次数、CUDA Graph miss 与 fallback。P50 正常、P99 突增时，按候选块数、物理页数、最长行和回退原因切片。稀疏率相同的请求可以有完全不同的物理分散度，候选页数往往更能解释尾延迟。

数值对照固定同一候选，以 CPU FP64 或 dense mask 为参考；分别比较 logits、每 tile 最大值、log-sum-exp、输出和梯度。候选不同时停在索引层，不把路由误差归咎于 softmax。算法、布局与数值三类问题由此分开。

**正确性用例矩阵。**

最小张量用例覆盖 $N=1$、候选为空、仅一个候选、候选等于全长和重复索引；边界长度覆盖 page size 前后各一项，如 15、16、17；块边界覆盖 query tile 与 KV tile 的非整倍数。数值用例加入极大正负 logits、全部相等 logits、FP8 scale 边界与全 mask 行。 布局用例覆盖连续 KV、随机物理页、共享 prefix、同逻辑页映射到高编号物理页，以及 batch 中一长多短。GQA 用例分别检查每个 query head 独立候选和 KV-head 组共享候选。split-KV 从 1、2、8 份变化，归并结果与不 split 参考比较。 训练用例除输出外还比较 $dQ,dK,dV$，并重复运行检查非确定性范围。多个 query 指向同一 KV block 能压测原子归约；forward 保存索引后修改 selector 参数，可以验证 backward 没有错误重算另一集合。fallback 用例强制触发每个原因，并确认回退计数准确。

性能回归与正确性回归分开设阈值。输出误差通过，不代表没有偷偷 dense fallback；速度通过，也可能来自漏读候选。CI 可以在小 GPU 上跑形状和数值，目标 GPU 定期跑带宽、TFLOPs、workspace 与 P99。每次修改索引格式、tile 或调度器，都同时更新两组基线。

### 6.2. 从 Triton 原型到长上下文核算

**从 Triton 原型走到生产 kernel。**

Triton 很适合先验证数据流。program id 映射到 query row 或 query tile，从 `indptr[row]` 到 `indptr[row+1]` 遍历 block IDs；`tl.load` 根据物理页和 lane offset 读取 K/V，逐块更新 $m,l,o$。原型先保证任意 ragged 索引都正确，再逐步加入固定块长、`tl.multiple_of`、向量化载入和 autotune 配置。过早假定对齐，错误通常只在尾页或特定物理地址出现。 编译期常量包括 head dimension、$B_q,B_k$、dtype 和是否 causal。候选数与页表属于运行时。若把最大候选数编进 kernel，会为每个容量档位生成不同版本，减少循环分支，也增加编译缓存和分发复杂度。版本数量过多时，JIT 首次延迟和二进制体积都会成为服务问题。

生产实现还会利用异步搬运、warp specialization、TMA 与 tensor core pipeline。FlashAttention-3 在 Hopper 上把数据搬运、矩阵乘与 softmax 交错；稀疏索引使下一 tile 地址不再是简单递增，预取必须提前解析 block ID。索引依赖链太长时，tensor core 等待地址，理论流水线无法填满。可在一个 warp 预取索引和页表，另一些 warp 计算当前 tile，但寄存器与 shared memory 分配要重新平衡。 FlashInfer 的 inspector-executor 把动态调度移到 plan 阶段，运行 kernel 消费已经整理好的任务。Triton 原型若每个 program 自己扫描长 `indptr` 决定工作，会重复解析并造成负载不均。两者比较时，Triton 的索引准备时间也要计入；反过来，FlashInfer 的 plan 若能跨几十层复用，应按实际复用次数摊销。

从原型升级可以按依赖逐项推进：固定候选验证 online softmax，加入随机物理页，随后加入 ragged batch 和 split-KV，再接动态 selector 与 CUDA Graph。每一步都保存上一版作为正确性参照。一次把页表、量化、路由和异步流水全部接入，出现错误时几乎无法判断是哪一层坐标或状态出了问题。 最终接口应把语义参数与性能提示分开。因果 mask、有效长度、候选集合和位置属于语义，后端不能静默修改；tile、split 数、workspace 档位和调度策略属于性能选择，可以 autotune。这样更换 Triton、CUDA/CUTLASS 或其他后端时，模型看到的邻接图保持不变。

autotune 的缓存也要绑定输入分布。只用平均行长选出的配置，可能在长尾 batch 上造成 workspace 暴涨或尾波空转。候选数的均值、P95、最大值和物理页分散度都可进入配置键；配置数量失控时，再按少数容量档位合并。线上发现新形状时落到安全配置，后台测完再更新缓存，不能让用户请求承担长时间编译。 跨 GPU 架构搬运配置尤其危险。相同 tile 在 Ampere、Hopper 与 Blackwell 上面对不同的 shared memory、异步复制和 tensor core 比例，旧机器的最优值可能让新机器寄存器溢出。发布产物应保留架构标识、编译器版本和关键生成参数，profile 才能与实际二进制对应。

**一次 64K 上下文的完整核算。**

**7.1. 从页级候选到 tile 任务.** 设单条请求已有 65536 个 token，page size 为 16，因此页表含 $65536/16=4096$ 页。模型采用 8 个 KV heads、32 个 query heads，head dimension 为 128，KV 保存为 BF16。selector 为每个 KV head 选择 256 页，并额外保留最近 16 页；去重后假设平均 264 页，其中 8 页同时被动态选择与窗口命中。 每个 KV head 的物理候选 token 为 $264\times16=4224$。若 kernel 的 KV tile 为 64 token，需要把逻辑相邻的 4 页编成一项；随机远程页无法合并，只能各自形成带 mask 的 64-token tile。假设 16 个窗口页合成 4 个完整 tiles，剩余 248 个动态页经过排序后有 96 组四页连续、40 组两页连续、72 个孤立页。对应任务数为

$$
4+96+40+72=212\ \text{KV tiles}. \tag{11}
$$

这些 tile 的物理计算容量是 $212\times64=13568$ token，而真实候选只有 4224 token，tile 有效率仅 $31.13\%$。这组数字说明 page size 16 与 $B_k=64$ 的组合对分散候选很不友好。若后端支持 $B_k=16$，任务数升到 264，索引与启动循环更多，物理 token 却降到 4224；究竟哪边快，要看小 tile 的 tensor core 利用率与地址开销。 **7.2. HBM 字节与计算量.** 每个 token、每个 KV head 的 K+V 字节为

$$
B_{kv}=2\times128\times2=512\ \text{bytes}. \tag{12}
$$

理想页级读取为 $4224\times512=2{,}162{,}688$ 字节，约 2.063 MiB。8 个 KV heads 合计约 16.5 MiB。若 $B_k=64$ 路径真的把掩掉槽位也从 HBM 读入，物理读取变成 $13568\times512\times8\approx53$ MiB；若 kernel 按页内 mask 只发射有效载入，DRAM 可以接近 16.5 MiB，但矩阵 tile 仍可能为无效槽位发射乘加。 稠密 decode 读取量为 $65536\times512\times8=256$ MiB。于是逻辑压缩率为 $256/16.5\approx15.5$ 倍，粗 tile 全读后的物理压缩率只有 $256/53\approx4.83$ 倍。索引表每个候选页用 4 字节，$264\times8\times4=8448$ 字节，`indptr` 与页内 mask 也只有几十 KiB；索引容量很小，随机索引造成的事务效率才是主要问题。 32 个 query heads 共享 8 个 KV heads，即每组 4 个 query heads。对 4224 token 做 QK 与 PV，每 query head 约 $4\times4224\times128=2{,}162{,}688$ FLOPs，32 heads 共约 69.2 MFLOPs。若物理 tile 全算 13568 token，则升到约 222.3 MFLOPs。decode 的算术量仍不大，读取模式和 batch 并发决定时间。 **7.3. workspace 与 split-KV.** 假设每个 KV head 的 212 个 tiles 拆成 4 个 splits，每个 split 处理约 53 tiles。32 个 query heads 分别输出局部状态，$o_s$ 用 FP32 保存，部分输出占

$$
4\times32\times128\times4=65536\ \text{bytes}. \tag{13}
$$

每个 split/head 还保存 $m_s,l_s$ 两个 FP32，总计 $4\times32\times2\times4=1024$ 字节。单请求约 65 KiB；batch 64 时约 4.06 MiB。再加入索引、任务描述和双缓冲，预留 6–8 MiB 比只按部分输出计算更稳妥。 四个 splits 的归并以式 (7)逐项重标定。举一组 head 的局部最大值 $(8,7,9,6)$ 与指数和 $(12,18,10,20)$，全局最大值为 9，合并分母为

$$
l=e^{-1}12+e^{-2}18+10+e^{-3}20\approx17.84. \tag{14}
$$

每份 $o_s$ 按同样系数缩放后求和，再除以 17.84。若某个 split 没有有效页，它的 $l_s=0$，不能让未初始化的 $m_s$ 参与最大值；任务规划阶段可以省掉空 split。 **7.4. block size 与候选率的交叉点.** 用一组示例数值演示决策方法。时间单位为微秒，包含索引规范化与 attention，不代表任何固定 GPU 的通用结论：

| 候选率 | $B_k=16$ | $B_k=32$ | $B_k=64$ | Dense FMHA | 选择 |
|---:|---:|---:|---:|---:|---|
| 3.1% | 42 | 35 | 38 | 118 | 32-token block |
| 6.25% | 55 | 46 | 44 | 118 | 64-token block |
| 12.5% | 78 | 66 | 59 | 118 | 64-token block |
| 25% | 126 | 101 | 88 | 118 | 64-token block |
| 50% | 214 | 162 | 133 | 118 | Dense |

小候选率下，$B_k=16$ 少做无效乘加，却受索引循环和小 tile 限制；候选率上升后，$B_k=64$ 更容易利用 tensor core；到 50% 时，稠密内核的连续访问胜过稀疏路径。若真实候选高度分散，64-token 列可能整体上移，交叉点更早出现。调度表要以实测的候选率和聚集度查找，不能只抄表中数字。 **7.5. CUDA Graph 的地址稳定条件.** 图捕获期间，Q/O、KV cache 池、workspace、`indptr`、`indices` 和任务计数器的设备地址都要保持稳定；内容和有效长度可以在 replay 前原地更新。grid shape 若固定为容量上限，kernel 读取有效任务数跳过多余 CTA。重新分配 indices、扩容 workspace 或换到另一份页表数组，都会破坏捕获时记录的地址。

双缓冲路由表时，可预先捕获两张图，分别绑定 buffer A 与 B；第 $t$ 步运行 A 时，另一个 stream 准备 B，第 $t+1$ 步交换。事件必须保证写 B 完成后才 replay，且 A 的 attention 完成后才能覆写。只交换 Python tensor 引用没有用，图中保存的是底层设备指针。 容量越界需要退出图模式，扩容并重新捕获。为了避免某条超长请求频繁破图，可按候选容量设置 128、256、512 页等档位，每档拥有固定 workspace 与图。请求进入最小可容纳档位，实际 `nnz` 仍由计数器决定。 **7.6. 基准协议与三类故障.** 基准固定 GPU 型号、驱动、编译器、时钟策略、dtype、head 数、page/block size 与候选分布。JIT、autotune 和 cache 预热后，先运行不少于 100 次 warm-up，再记录至少 1000 次 GPU events；同时保存 median、P95、P99。端到端计时包括 selector、top-k、索引、plan、kernel 与归并，kernel-only 结果另列。dense 与 sparse 使用相同输入、mask、KV 布局和输出精度。

故障一表现为 DRAM bytes 比式 (11)高三倍、tensor core active 尚可。进一步发现候选先 gather 到 scratch，随后又被 attention 读取，且每个 query head 各复制一次。修复方向是让 GQA 组共享 scratch 或直接 sparse-load；继续调 tile 无法消掉复制流量。 故障二表现为 DRAM 带宽与 tensor core 都低，CTA duration 的 P99 是中位数十倍。候选统计显示多数行 32 blocks，少数行 800 blocks，静态一行一 CTA 让尾波只剩几个 SM 工作。应拆长行、使用 persistent queue 或按行长分桶。提高 occupancy 参数可能增加更多空闲 warps，解决不了任务粒度不均。 故障三表现为 kernel-only 稳定在 45 微秒，端到端 P99 却偶发超过 2 毫秒。trace 显示候选数越过 workspace 档位后触发同步分配，并退出 CUDA Graph；偶发 dense fallback 又重建另一份 plan。修复方式是扩大常用档位、异步准备下一档 workspace，并把回退原因纳入调度。单看 kernel profile 完全看不到这类服务故障。

三类故障对应三条证据链：字节异常查数据路径，CTA 长尾查调度，端到端尖峰查图捕获、分配与 fallback。先用计数器确认类别，再进入源码，比看到「稀疏 kernel 慢」便重写矩阵乘更有效。 **7.7. 同一案例中的 backward 冲突开销.** 把上述 64K 案例扩成训练 prefill。假设 query tile 为 64 token，一个训练 chunk 有 4096 个 query，因此每个 head 有 64 个 query tiles。若每个 query tile 都选择 264 页，热门的 16 个局部页会被多数相邻 query 重复访问，远程页则较分散。$dQ$ 的归属清楚：一个 CTA 处理一个 query tile 的全部候选，累积后写回自己的 64 行，不与其他 CTA 冲突。 $dV$ 与 $dK$ 的方向相反。同一个热门 KV page 可能收到 64 个 query tiles 的贡献；若每个 tile 直接对 BF16/FP32 梯度做原子加，单页包含 $16\times128=2048$ 个元素，64 份贡献意味着最多 $131072$ 次热点原子更新，K 与 V 各发生一次。远程冷页只被少数 tiles 选中，原子冲突小，统一采用一种策略会让热门页决定尾部时间。

两阶段归约可以先让每个 query CTA 把局部 $dK,dV$ 写入 workspace，再按 KV page 分组求和。若所有候选都保存局部梯度，容量非常大：64 query tiles、264 pages、16 tokens、128 维、K/V 两份 FP32，约

$$
64\times264\times16\times128\times2\times4\approx264\ \text{MiB/head}. \tag{15}
$$

显然不能照此物化。实用做法是按 KV block 分片，让一组 CTA 在片上或小型 partial buffer 中归约；或者只对高复用热门页走 KV-centric 路径，冷页继续原子加。前向统计的 page reuse count 正好可用于选择路径。 混合方案设阈值 $r_0$：复用次数 $r_b<r_0$ 的 block 直接原子累积，$r_b\ge r_0$ 的 block 写入按固定 split 数组织的 partial buffer。阈值太低会扩大 workspace 与归并开销，太高则热点原子仍然串行。对候选复用分布做扫描，可以画出 atomic time、reduce time 与 workspace 的三条曲线，再选交叉点。 $dQ$ 虽无写冲突，也可能因候选行长不同而负载不均；$dK,dV$ 的反向邻接表则会改变不均衡方向，热门页行很长。forward 与 backward 不应共用一套静态分桶。基准分别记录 $dQ$ kernel、$dK/dV$ kernel、稀疏转置、归并和 workspace 清零，才能看清训练反向究竟卡在矩阵乘、原子还是元数据。

数值上，原子加的顺序随调度变化，重复运行会出现末位差异；分段归约若固定树形顺序，可以提高确定性。验收同时给相对误差与重复运行方差。为了逐 bit 一致而把所有贡献串行，会牺牲大量性能；完全不约束顺序，又可能让低精度累积在长序列上漂移。常用折中是局部 FP32 累积、固定 split 内顺序，split 之间再做少量归并。 反向开销还应随 block size 一起重算。较大的 block 减少反向索引项，却让热门区域带入更多无效梯度乘加；较小的 block 降低填充，又扩大转置表和调度任务数。前向最优块长未必也是训练总步的最优块长。

### 6.3. 量化、索引语义与 Ragged 布局

**量化 KV 与 kernel 特化。**

**8.1. 反量化放在读取路径的哪一层.** KV以INT8、FP8或更低bit保存时, 稀疏kernel读取候选块后要恢复计算值. 若先gather量化码到scratch再单独反量化, 候选数据至少经过两次全局内存; 更合理的路径是在tile load后立刻应用scale, 将重构值留在寄存器或shared memory, 随后进入QK/AV. Scale粒度决定地址. 每tensor一个scale最省元数据, 精度有限; 每head、每page或每channel更精细, kernel要同步读取更多scale. 设page有 $P$ 个token、head维 $d_h$, 每page每channel scale需要 $d_h$ 个值, 主KV码只有 $Pd_h$ 个值. $P$ 很小时, scale占比会明显上升. 性能核算要把scale字节与转换指令加入, 不能只按bit宽缩放KV流量.

QK与AV对量化敏感性不同. K误差改变logits和softmax排序, V误差在线性加权后进入输出. 实现可为K、V使用不同格式或scale. 这会增加模板组合, 但比统一格式后靠扩大候选补质量更直接. 正确性基线也应使用同样的重构KV, 先隔离kernel误差, 再与高精度模型比较量化误差. **8.2. 索引有序性影响scale复用.** 候选按物理page排序后, 同一page的scale只需加载一次, 其内多个token或多个query head可以复用. 按分数顺序访问则可能重复切换page. GQA中多个query heads共享KV page与scale, kernel若按KV head组织工作, 能提高复用; 按query head各自启动, scale和K/V都会重复读取. 去重应发生在反量化前. 两条selector分支若给出同一page, 先各自反量化再在attention里屏蔽, 已经浪费主要带宽. 对token索引, 同页的离散offset可先聚合成小bitmap或排序列表; page只加载选中token还是整个tile, 取决于候选密度与硬件事务.

**8.3. 编译特化不能覆盖无限形状.** 高性能kernel常对 $d_h$、block size、dtype、causal、GQA比例和候选容量特化. 组合过多会增加编译时间与二进制体积, 还会让线上shape落到未调优路径. 配置应把实际模型形状归入少量稳定档位, 例如固定 $d_h\in\{64,128\}$、page size与若干候选上限. Autotune需要使用代表性的索引分布. 只用连续候选调出的tile, 面对随机pages时可能寄存器设置过大、并发不足; 只用平均行长会忽略长尾. 可以按候选聚集度、行长档位和batch各保留一组测试形状, 选择在加权流量上表现稳定的配置, 而非单点最快参数.

运行时遇到未支持的head维或dtype, 应进入明确的参考/稠密路径并记录原因. 静默pad到下一个维度会增加FLOPs, 还可能让scale和RoPE布局出错. Fallback正确性先与参考实现核对, 性能告警则统计它占总请求比例; 一个很快的主kernel若大量流量回退, 整体收益仍会消失. **8.4. Epilogue 融合的边界.** Attention输出后常接输出投影、残差或量化写回. 将简单的cast、scale或门控融合进epilogue, 可以少写一次中间O; 直接融合完整输出投影会让稀疏attention kernel承担大矩阵乘, 编译与调度复杂度显著上升. 是否融合取决于O的字节与后续GEMM能否高效独立运行.

Split-KV路径先产生多个partial outputs, 必须完成LSE归并后才能执行非线性门控或量化. 在每个split里提前做dropout、activation或低bit截断, 结果通常无法按式(6)严格合并. 可线性分配的操作也要检查缩放位置. Epilogue顺序属于数学定义, 不应为了减少kernel数随意调整. 训练时dropout mask要与稀疏索引和重计算一致. 前向只保存随机种子时, backward必须按相同候选顺序再生mask; 若索引排序在两次运行间不同, 同一逻辑边会拿到不同随机数. 稳妥做法让随机数由全局 `(batch,head,q_pos,k_pos)` 计数器确定, 而非由候选数组中的遍历序号决定. **8.5. 交付前的算子矩阵.** 最终测试矩阵至少覆盖 FP16/BF16主路径、启用的KV量化格式、MHA/GQA、causal/non-causal、连续与离散候选、短行与超长行、split-KV、CUDA Graph和fallback. 每格先比较reference输出与梯度, 再记录延迟、DRAM bytes、tensor core利用率和workspace.

测试矩阵不要求所有组合都有专用kernel. 明确标记支持、回退和禁止, 比让未知组合自动落到错误模板安全. 模型接入时用配置生成实际会触发的子集, CI运行小shape正确性, 发布前在目标GPU运行长shape性能与内存压力. 这样索引协议、数值定义和硬件实现才能在同一版本下验收.

**索引格式本身就是算子语义。**

**9.1. 集合、序列与多重集给出三种不同结果.** 若候选只表达集合，索引顺序不影响实数域中的attention结果，重复元素应被删除。若索引表达序列，顺序可能参与位置编码或随机数生成。若允许多重集，同一key出现两次会在softmax中获得两份指数质量，等价于给该logit增加 $\log 2$，已经改变模型函数。 因此接口必须声明输入究竟是哪一种。常见动态稀疏attention需要的是逻辑位置集合，排序只为执行服务，重复属于错误。多个路由分支若想给同一位置不同权重，应先合并分支分数或在分支输出层做门控，不能靠重复索引暗示权重。 规范化可定义为映射

$$
\mathcal N:(D,W,A,T)\mapsto
\{(t,\ell(t),p(t))\mid t\in D\cup W\cup A,0\le t<T\}, \tag{16}
$$

t是逻辑token位置，$\ell(t)$是逻辑页及页内偏移，p(t)是物理地址。集合成员资格由t决定，物理排序只重排三元组。这个定义把越界、重复与坐标混淆变成可测试条件。 **9.2. 逻辑坐标必须贯穿位置相关计算.** 物理页可以被回收、迁移和重排，同一请求的相邻逻辑页未必相邻存放。RoPE、ALiBi、因果mask与相对位置桶都使用逻辑位置。若kernel为改善coalescing按物理地址排序，仍需携带每个tile的逻辑起点或逐token位置。 共享prefix进一步说明两套坐标不能混用。两个请求可指向同一物理页，该页在两条序列中的逻辑位置可能相同，也可能因拼接策略不同而偏移。物理复用只说明K/V字节相同，位置语义是否可复用取决于K中是否已经编码绝对或旋转位置。 地址映射可拆成

$$
\operatorname{addr}(n,t,h)=
\operatorname{base}[\operatorname{table}_n(\lfloor t/P\rfloor),h]
+(t\bmod P)\operatorname{stride}_{tok}. \tag{17}
$$

任何物理排序都只能改变访问次序，n、t、h仍决定读到哪个元素。随机页表测试应让物理页号与逻辑顺序完全无关，以免错误实现碰巧在连续分配下通过。 **9.3. Token候选扩张成块会改变预算语义.** selector返回k个token，kernel按块长B读取时，真实读取集合为覆盖这些token的块并集。若候选均匀散落，最多触及k个块并读kB个token；若候选高度聚集，读取量接近k。于是相同逻辑recall和k会对应完全不同的物理成本。 设被选token数为k，触及块数为u，块利用率定义为

$$
\eta_{blk}=\frac{k}{uB}. \tag{18}
$$

$\eta_{blk}$既受selector影响，也受block size影响。训练只惩罚token数会鼓励分散候选，部署成本却按u计价。更合适的预算目标直接使用触及块数，或让selector输出块级分数。 块扩张还可能引入因果边界后的token。prefill中query tile跨越对角线时，同一KV块对不同query行具有不同有效前缀。索引可保留整块，mask在logit阶段逐元素裁掉；不能因为块被某一行合法选中，就让同tile内较早query读取未来位置。 **9.4. 去重键要选择逻辑身份.** 共享页、copy-on-write与prefix cache会让多个逻辑引用指向同一物理页。按物理页去重可能错误合并两个具有不同逻辑位置语义的引用；按逻辑token去重则保留模型邻接图。只有能够证明K/V和位置偏置完全相同，物理别名才可合并。

GQA组内合并候选也使用逻辑块ID。各query head的路由分数可取最大、求和或保留私有预算，合并规则在进入kernel前完成。kernel接收最终集合后不应再次根据物理地址猜测组级语义。 去重算法本身有成本。短定长索引可排序后线性去重，长ragged行可用位图、哈希或分层块标记。位图大小随全上下文增长，哈希存在随机访问，排序为 $O(k\log k)$。选择取决于k与总块数，复杂度要计入索引路径。 **9.5. 空集合和非法集合必须有唯一含义.** 全mask行的softmax在数学上没有有限分母。系统可以禁止空候选、强制加入当前token或sink，也可以定义输出为零并跳过归一化。三种选择都会影响残差路径，必须在接口中固定。静默读第0页填空会把安全问题伪装成数值结果。

非法索引包括负数、越界页、跨请求物理页和指向尚未提交的尾块。验证可在plan阶段完成范围与所有权检查，热kernel仍保留容量边界。高性能模式省略逐项检查时，调用方必须提供已经验证的对象，不能接受任意用户数组。 错误处理也属于可观测语义。回退dense只适用于完整KV仍可访问的情况；索引指向错误请求时，回退无法修复潜在数据泄漏，应终止该批并记录原因。将所有异常都归成“fallback”会掩盖严重程度。

**Ragged结构与定长结构怎样互相转换。**

**10.1. CSR式行表示保留真实工作量.** 对每个query行i保存 `indptr[i:i+2]`，候选块位于扁平 `indices`。总索引数为nnz，容量与真实候选和成正比。行长

$$
k_i=\operatorname{indptr}_{i+1}-\operatorname{indptr}_i \tag{19}
$$

直接决定该行工作量。结构适合高度变化的预算，也给split和分桶提供统计量。 代价是每行起点不同，kernel需要读indptr并处理变长循环。若一个CTA负责一行，长尾产生wave不均；若一行拆成多任务，plan需生成任务到行、split与块区间的映射。CSR节省padding，却把规则性转移到调度阶段。 **10.2. 定长K用padding换取静态形状.** 固定每行K个块可存成二维矩阵，地址计算简单，CUDA Graph与编译特化也容易。真实候选不足K时需要哨兵或重复填充。哨兵必须在load前或logit处被mask，重复真实页则会改变softmax，不能充当无害padding。 若行长分布为 $k_i$，统一容量K的索引利用率为

$$
\eta_{idx}=\frac{\sum_i k_i}{NK}. \tag{20}
$$

平均候选很小但P99很大时，按最大值定长会浪费大量循环与存储。分档定长能折中：例如64、128、256三档，每行进入最小可容纳档位，档内保持规则。 **10.3. 分档边界影响质量和调度.** 若自适应selector请求129块，容量档只有128和256，向下截断会损失质量，向上分配会浪费127槽。路由器可直接学习档位，在训练时感知阶梯成本；也可保持连续预算，部署向上取整并记录浪费。 同档行仍可能有不同有效长度，kernel用计数器屏蔽padding。按档位组batch会改善tile规则性，却可能延迟等待同类请求。离线吞吐最优分桶未必符合在线P99，调度成本要和kernel收益共同评估。 分档还决定workspace与图捕获数量。档位过密，计划缓存、二进制和常驻buffer膨胀；档位过疏，padding增加。可用真实 $k_i$ 分布最小化期望成本

$$
\min_{C_1<\cdots<C_m}
\mathbb E[T(C(k))]+\lambda m, \tag{21}
$$

其中 $C(k)$ 是覆盖k的最小档，$\lambda$给每个额外档位定价。 **10.4. Ragged到任务表是一次小型编译.** plan读取每行长度，决定每个任务处理的块区间，写出 `(row,start,end,split)`。若目标每任务约R块，第i行任务数约为 $\lceil k_i/R\rceil$。任务表让执行kernel无需搜索前缀和，代价是生成与读取额外元数据。 前缀和计算把每行任务数转成全局任务ID。这个过程通常为线性复杂度，短batch时固定启动成本显著，长batch时可跨层复用。候选集合每层不同则无法复用完整任务表，只能复用行形状或容量规划。 任务划分还应考虑物理聚集度。相邻索引落在连续页时，一个任务可以形成长流水；完全随机时，过大的任务会拉长地址依赖链。仅按块数均分无法保证各任务时间相等，页跨度与预计事务数可作为第二个权重。

**10.5. 转换必须保持稳定的行身份.** 分桶、排序任务与persistent queue会改变执行顺序，输出仍需写回原batch、head与query位置。每个任务携带稳定row ID，split归并以row ID分组。把排序后序号当输出位置，会在候选长度相同的测试中难以察觉，在ragged batch中直接串行。 请求取消或continuous batching换入新序列时，row ID还要绑定generation或slot版本。旧任务晚到后若写入已复用slot，会污染新请求。任务表生成、运行与slot回收之间需要事件或世代检查。 稳定身份也利于确定性。不同调度顺序可能改变浮点归并末位，但不能改变任务属于哪一行、包含哪些逻辑块。测试可随机打乱任务表顺序，验证集合与输出在容差内保持一致。

### 6.4. Online softmax、反向图与错误阻断

**Online softmax的等价条件。**

**11.1. 分块更新源自同一个全局分母.** 对候选集合S，精确输出为

$$
o=\frac{\sum_{j\in S}e^{z_j}v_j}{\sum_{j\in S}e^{z_j}}. \tag{22}
$$

将S任意划分为若干块，每块保存最大值 $m_b$、相对指数和 $l_b$ 与未归一化加权和 $u_b$。取全局 $m=\max_bm_b$ 后有

$$
o=\frac{\sum_be^{m_b-m}u_b}
{\sum_be^{m_b-m}l_b}. \tag{23}
$$

因此访问顺序、split方式和物理排序不改变实数结果，前提是所有合法元素恰好出现一次，mask在统计前生效，局部输出尚未除以自己的分母。 **11.2. Mask错误会同时污染最大值和分母.** 无效槽位若用0代替logit，对真实logit全为负的行会成为最大值，并向分母加入1。正确做法是在求局部最大值前赋负无穷，且value乘加也屏蔽。全无效块可直接跳过，不产生局部状态。 因果mask由query逻辑位置与key逻辑位置比较。一个query tile包含多行时，对角块的每行有效范围不同，不能只用块级布尔值。尾块还叠加请求有效长度，最终合法条件为

$$
\operatorname{valid}(i,j)=
(j<L_n)\land(j\le i)\land(j\in S_i). \tag{24}
$$

非因果任务去掉第二项，其他两项仍存在。 **11.3. GQA共享K/V但不共享归一化状态.** 同一KV head服务g个query heads，K/V tile可加载一次并广播，分数 $q_h^\top k_j$ 与softmax状态仍按h独立。每个head维护自己的 $(m_h,l_h,u_h)$。将head分数先聚合再softmax会改变模型，只能用于候选选择。 共享加载增加片上复用，也增加同时驻留的query寄存器。g过大时occupancy下降，可能需要分两批query heads消费同一页，牺牲部分复用。原理上的读取共享与硬件上的同时计算并不等价。 候选若按GQA组共享，每个head对同一集合执行；若含私有候选，任务表需表达公共块与head附加块。简单取并集后所有head全算能保持结果，额外FLOPs可能很大；分公共/私有两段执行则增加控制与归并。 **11.4. 有限精度使顺序产生可测差异.**

实数加法满足结合律，浮点加法不满足。物理排序、split数和CTA归并树变化会改变末位。FP32累计通常比BF16累计稳定，指数与最大值仍需处理极端范围。对很长候选，分母累加误差会随项数增长。 数值验收应比较高精度reference，并扫描访问顺序。误差指标包括绝对误差、相对误差、余弦差与下游logit差。某些输出接近零时相对误差会爆炸，需要与绝对误差共同判断。 确定性模式可固定排序和归并树，性能模式允许调度改变并给出重复运行方差。两种模式使用同一集合语义。把bitwise一致当成唯一正确性标准会阻止合法优化，完全不测方差又会漏掉热点原子造成的不稳定。 **11.5. Dropout随机数应绑定逻辑边.**

训练attention dropout若按遍历序号生成随机数，索引排序变化会让同一 $(i,j)$ 边得到不同mask。虽然分布相同，activation checkpoint重算或不同后端对齐时难以复现。计数器可由batch、head、query位置、key位置和全局seed派生。 split-KV时，各split对不同逻辑边生成随机数，归并仍遵循式(22)。同一边不得在重复索引中出现两次，否则既重复概率质量，也获得两次独立dropout机会。保存候选集合与seed即可重算，无需保存完整mask矩阵。

**带宽与复杂度模型要包含地址系统。**

**12.1. 理想字节只是下界.** 若读取k个token、head维d、元素字节s，K/V理想流量为 $2kds$。实际流量还包含索引、页表、scale、位置、事务放大、重复cache line和部分输出。可写成

$$
B_{real}=\alpha_{mem}(2kds)+B_{idx}+B_{meta}+B_{ws}, \tag{25}
$$

$\alpha_{mem}\ge1$描述事务与重复读取。随机小载入会让它远大于1，连续块和GQA复用则把它压低。 测量时用硬件DRAM字节与理论项相除，得到有效放大系数。只报告逻辑稀疏率无法解释两个同K实现的巨大差异。L2命中会让DRAM字节降低，但片上流量与指令仍存在，应同时看cache与load效率。 **12.2. 地址生成会形成串行依赖链.** 一次载入可能依赖row ID、indices、逻辑页表、物理base与量化scale地址。若这些值逐级从内存读取，K/V请求直到链尾才可发出。算术量很小的decode中，地址延迟可能超过点积。 plan阶段可预展开部分地址，代价是更大的任务表；kernel也可提前加载下一批block ID与页表，在计算当前tile时隐藏延迟。预展开到字节指针会失去cache迁移灵活性，并让图捕获状态更大。应比较减少的依赖与增加的元数据流量。

TLB也是地址系统的一部分。候选跨越大量物理页时，页表缓存压力上升。按物理地址排序可能改善TLB与L2局部性，只要逻辑位置仍随条目携带。微基准应控制物理页跨度，不能只控制候选数。 **12.3. 排序和去重的复杂度有交叉点.** 对k个索引全排序为 $O(k\log k)$，哈希去重期望 $O(k)$，位图标记为 $O(k+P_w)$，其中 $P_w$是需要清理或扫描的位图范围。k很小时，简单排序常因常数小而胜出；上下文块数巨大、k仍小，清整张位图会很亏。 若selector已经输出有序top-k，窗口与sink合并可用多路归并，避免重新全排。组内多个head集合取并集也可合并有序列表。保留排序不变量需要selector与kernel接口共同约定，否则一次无意乱序会让后端退回昂贵通用路径。

复杂度还要看执行频率。每token每层重复规范化，哪怕单次几十微秒也会积累；若若干层共享候选，规范化成本可摊销。共享会改变模型图，不能只为性能擅自启用。 **12.4. Amdahl上限需要逐项代入.** 设原推理中attention占比a，稀疏后attention本体加速s，新增索引成本占原总时间比例r，则整体加速

$$
S=\frac{1}{(1-a)+a/s+r}. \tag{26}
$$

当a=0.4、s=8、r=0.05时，整体只有 $1/0.7\approx1.43$ 倍。模型其他部分越重，继续优化attention的端到端回报越小。 decode与prefill的a不同，batch变化也会改变MLP和通信占比。报告单个kernel倍数容易制造错觉，应该在目标服务配置中测a与r。路由器若与前一算子重叠，r可按关键路径上的未隐藏部分计算。 **12.5. 稀疏率不是唯一自变量.** 相同10%候选率可以是连续窗口、少量长段或完全随机页。三者在tile填充、事务、TLB与复用上不同。性能曲线至少以候选率、平均连续段长、行长变异系数和GQA重合率为轴。 可从线上索引提取不含内容的结构统计，生成合成候选。这样微基准保留真实物理难度，又不保存用户文本。统计分布变化时重新测交叉点，避免固定阈值长期漂移。

**反向传播需要一张转置稀疏图。**

**13.1. dQ沿前向行自然分解.** 每个query行只依赖自己的候选，$dQ_i$可由负责该行的任务累积，无跨行写冲突。利用前向保存的log-sum-exp重算概率，避免保存 $|S_i|$ 大小的矩阵。候选索引必须与前向一致。 softmax梯度对选中边为

$$
d z_{ij}=p_{ij}\left(d p_{ij}-\sum_{s\in S_i}p_{is}d p_{is}\right). \tag{27}
$$

括号中的归约在整行候选上完成，不能让每个split独立求均值后直接相加。split先计算必要的全局标量，再回到局部边生成梯度，或在两阶段中保存局部贡献并归并。 **13.2. dK与dV需要按列汇聚.** 多个query可选中同一KV块，所以 $dK_j,dV_j$收到多行贡献。前向CSR按query组织，反向按KV组织更自然，需要构造转置邻接。若直接使用原子加，省去转置，热点页会产生严重竞争与非确定顺序。 设KV块b被 $r_b$ 个query tile引用。小 $r_b$ 时原子路径简单，高 $r_b$ 时分组归约更划算。混合策略按复用计数选择。复用计数可在索引规范化时生成，既服务调度，也预测workspace。 转置构造包括计数、前缀和与scatter，复杂度 $O(nnz)$，这笔成本必须计入训练step。跨多层候选相同才可复用转置；候选不同的层不能共享一张图。 **13.3. Selector梯度不来自普通attention backward.**

hard top-k使未选边不存在，attention backward只更新选中Q/K/V。索引本身是整数，无法通过kernel自然获得对selector分数的梯度。训练依赖蒸馏、straight-through、随机估计或soft旁路，这些梯度在attention算子之外产生。 接口若宣称支持selector联合训练，应明确返回哪些辅助量，例如边界分数、选中logit或代理gate。仅实现稀疏$dQ,dK,dV$不等于完成路由训练。反之，推理kernel无需背负训练代理逻辑。 **13.4. 重计算必须恢复同一图与同一随机性.** activation checkpointing重跑前向时，模型参数可能相同，top-k并列、量化舍入或随机探索仍可能换集合。保存indices最稳妥，容量为nnz个整数，通常远小于attention概率矩阵。 若为了显存连indices也重算，需要固定selector输入、参数版本、随机seed、排序规则和量化尺度。任何一项变化都会让梯度对应另一张图。测试可刻意构造cutoff并列，验证重算一致性。 **13.5. 错误会沿残差与自回归轨迹传播.**

kernel遗漏一个候选会改变当前attention输出，残差连接不会自动消除它。后续层可能放大或抵消，当前token的logit变化又可能改变采样，之后的KV与索引轨迹完全分叉。 数值小误差与结构错误应分开。浮点归约差异通常连续且可用误差范数描述；漏页、重复页和串请求属于离散结构错误，可能造成大跳变。验收先验证索引集合，再比较数值输出，避免被偶然相似value掩盖。

### 6.5. 可证伪验收与错误阻断

**可证伪验收从集合开始。**

**14.1. 第一层oracle只检查索引转换.** 给定逻辑候选、窗口、sink、页表与有效长度，用CPU集合运算生成期望的逻辑token与物理地址对。GPU规范化输出逐项比较，覆盖重复、乱序、随机页表、共享prefix与尾页。 属性测试可以随机生成合法映射，并验证三条不变量：输出逻辑集合等于输入并集；每个逻辑位置映射到正确物理地址；重排输入不改变规范化集合。任何一条失败都停在索引层，无需运行attention。 **14.2. 第二层oracle检查稀疏数学.** 固定已经验证的候选，用高精度gather出K/V，运行朴素attention作为reference。kernel分别比较logit、行最大值、log-sum-exp和输出。逐级中间量能定位mask、缩放或PV累积。 候选覆盖全长时，稀疏kernel还应与dense attention一致；候选仅一个token时输出应等于该value；全部logit相等时输出为候选value均值。这些构造样本比随机误差更容易指出具体规则。

**14.3. 第三层oracle检查布局无关性.** 保持逻辑K/V与候选不变，随机置换物理页并更新page table，输出应在浮点容差内一致。再随机改变候选访问顺序、split数和任务顺序，验证数学结果不依赖布局。 若启用量化，reference先按相同scale重构K/V，隔离kernel误差；随后再与高精度模型比较量化误差。把两者混在一个阈值里，会让实现错误藏进宽松量化容差。 **14.4. 反向oracle使用有限差分与dense梯度.** 小形状下固定候选，dense mask reference可生成$dQ,dK,dV$。稀疏backward比较选中边对应梯度，未选K/V梯度应为零。热点页、多split和随机顺序用于检查原子归约方差。 有限差分适合抽查少量元素：扰动一个Q/K/V元素，比较loss变化与解析梯度。hard索引在检查期间固定，否则扰动可能改变候选集合，有限差分测到的是离散路由变化。 **14.5. 性能主张也必须可被推翻.**

每个加速数字都配套计时边界、候选分布、硬件、dtype、batch、长度与workspace。dense和sparse使用相同语义与精度，另列kernel-only及端到端结果。若稀疏路径暗中回退、漏读或减少精度，性能测试应失败。 理论字节、硬件DRAM字节和时间三者同时报告。字节未降而时间下降，收益可能来自其他融合；字节大降而时间不降，地址、调度或固定成本在阻塞。这样的结果可以推翻“只要更稀疏就更快”的假设，并指出下一步实验。

### 6.6. 从逻辑候选到输出与故障分类

**从一组逻辑候选完整推演到输出。**

**15.1. 逐步核对集合、地址、任务与归一化.** 考虑一个prefill小例子。batch中有两条请求，长度分别为70和37，页长P=16，因此各有5页和3页。第一条请求的逻辑页到物理页映射为 $(9,2,14,6,11)$，第二条为 $(5,13,1)$。每个物理页都属于唯一请求或经过合法prefix共享，所有权表已经验证。kernel的KV tile长为32，即理想情况下两个相邻逻辑页组成一项任务。 取第一条请求中逻辑位置i=65的query。selector给出token候选

$$
D_i=(3,18,19,34,35,50,66,18), \tag{28}
$$

局部窗口保留 $W_i=(58,\ldots,65)$，sink为 $A_i=(0,1)$。位置66超过当前因果边界，第二个18为重复项。规范化后先过滤非法位置，再取逻辑集合，得到

$$
S_i=\{0,1,3,18,19,34,35,50,58,59,60,61,62,63,64,65\}. \tag{29}
$$

若kernel按整页读取，触及逻辑页0、1、2、3、4。尾页只有位置64至69有效，而当前query只允许64、65。页面4的其余槽位在attention中全部mask。集合有16个逻辑token，页扩张却覆盖5页、80个槽，逻辑token利用率为20%。若选择器原生输出页，成本语义会直接显示5页；token top-k则容易把这项放大隐藏在kernel内部。 查页表得到物理页序列 $(9,2,14,6,11)$。为了地址局部性按物理页排序会变成 $(2,6,9,11,14)$，对应逻辑页 $(1,3,0,4,2)$。每条任务必须携带逻辑页号。RoPE位置、因果mask与输出随机数仍按逻辑token计算，物理页号只用于基址。 若选择按逻辑相邻页组成32-token tile，可形成 $(0,1)$、$(2,3)$ 与尾页4三项；它们对应的物理页对为 $(9,2)$、$(14,6)$、$(11,\varnothing)$。逻辑相邻无法保证物理连续，单个tile内部也要发起两段地址。若按物理相邻性组织，这五页可能完全无法合并。task planner应明确tile是计算形状还是连续存储承诺，不能把两者混成一个block ID。

对第二条请求，任何索引都必须使用它自己的页表。假设row排序后两个请求的任务交错执行，任务结构至少包含请求slot、slot generation、query逻辑位置、KV逻辑页、物理页与有效范围。仅保存物理页11不足以证明它仍属于第一条请求；页回收后，同一编号可能已经分配给另一条序列。

进入attention时，对某个query head h和候选tile b计算logit。页面扩张带入的token若符合因果与长度条件，可以参与attention，即使最初不在token候选中；这就是块稀疏模型的真实邻接语义。如果设计要求严格token稀疏，还需额外token bitmap，单纯页集合无法恢复原S。两种语义在输出上不同，性能也不同，接口必须提前选择。 假设页语义生效，五页内对i合法的位置共有66个，即0至65。此时动态selector实际上没有裁掉任何历史页，稀疏路径应考虑回退dense。若仍运行稀疏kernel，输出必须与长度66的dense causal attention一致。这是很有价值的退化用例：页覆盖率100%时，任何差异都来自实现而非选择误差。

为了继续展示稀疏计算，改用严格token bitmap，只让式(28)的16项参与。将任务按物理地址顺序遍历，第一项可能处理逻辑页1。局部有效候选为18、19，得到局部状态 $(m_1,l_1,u_1)$。下一项逻辑页3包含50、58至63，使用

$$
m' = \max(m,m_b),\quad
l'=e^{m-m'}l+e^{m_b-m'}l_b,
\quad
u'=e^{m-m'}u+e^{m_b-m'}u_b. \tag{30}
$$

五页处理结束后输出 $u/l$。访问顺序可以换成逻辑页序，集合与mask不变时高精度结果一致。FP32累积下的末位差异由舍入产生，应落在预先定义的误差范围内。 现在加入GQA。四个query heads共享同一KV head和同一页集合。K/V页面只需从HBM读取一次，四个query向量分别产生logit与状态 $(m_h,l_h,u_h)$。若四个head还有私有token bitmap，页面可共载，计算mask按head不同。任务表若只能表达一张共享bitmap，只能取并集并让各head多算，或丢弃私有语义。 再加入split-KV。五个物理页分给两个CTA，split A处理 $(2,6,9)$，split B处理 $(11,14)$。每个head分别写两组局部状态。归并时对head h取

$$
m_h=\max(m_{hA},m_{hB}),
\quad
l_h=e^{m_{hA}-m_h}l_{hA}+e^{m_{hB}-m_h}l_{hB}, \tag{31}
$$

并以相同系数合并u。若split B对该head没有有效token，它写 $l_{hB}=0$ 并标记空状态，未初始化最大值不得参与max。用一个固定极小数代替空标记时，要保证任何合法有限logit都不会与其混淆。 尾页页面4包含逻辑位置64、65两个合法候选。有效长度70只排除70至79，因果边界再排除66至69。两个mask相交后得到64、65。若kernel只应用长度mask，它会读取四个未来token；只应用因果mask但忘记长度，在query位置超过69的后续测试中又会让未初始化槽进入。长度与因果是独立约束。 若K/V量化为INT8，每个物理页每head有scale。加载页11后先读取scale并重构位置64、65对应向量。reference应使用相同量化码和scale，比较kernel计算；与原BF16 K/V的差异另记为模型量化误差。这样一旦输出异常，可以判断是地址、反量化还是量化本身。

反向时，保存式(28)及其严格token bitmap、每head log-sum-exp与随机seed。$dQ_i$在该行内累积。位置18等K/V接收可能来自多条query的梯度，需要原子或转置邻接归约。页面扩张语义若启用，块中所有合法token都有梯度；严格token语义下，扩张槽梯度必须为零。forward和backward若对这点理解不同，会产生看似合理却错误的训练。

该例的第一层验收直接比较式(28)。第二层验证逻辑到物理映射：逻辑18位于页1、偏移2，应落到物理页2的对应地址；逻辑64位于页4、偏移0，应落到物理页11。第三层固定集合比较每个head的log-sum-exp与输出。第四层随机置换物理页并同步更新页表，输出保持。第五层改变split与任务顺序，误差仍在容差内。 性能核算也从同一例出发。严格token语义理想读取16个K/V，页加载语义读取66个合法历史token或5个完整物理页，32-token tile还可能发射96槽计算。报告“选了16个token”无法代表后两种成本。应同时给selector候选数、去重token数、触及页数、合法扩张token数、物理tile槽数与DRAM字节。

如果plan发现五个页覆盖全部历史，dense回退可省掉索引循环。回退输入仍是第一条请求的完整逻辑cache描述，不复用物理排序后的临时列表。dense与sparse输出在该退化点应连续；阈值两侧可用相同输入分别强制两条路径，测量最大误差与延迟交叉。 这个推演揭示了一条完整因果链：selector定义逻辑意图，规范化决定唯一集合，布局映射决定地址，任务表决定并行分块，mask恢复逐元素合法性，online softmax保证分块等价，归并恢复全局分母，backward沿同一图返回。任一阶段擅自修改集合，后续高精度计算也无法补救。

**错误分类决定如何定位与阻断传播。**

**16.1. 从结构错误、数值错误到性能错误建立证据链.** 结构错误改变被计算的边。常见类型包括漏候选、重复候选、跨请求地址、逻辑/物理坐标混淆、尾页越界、因果mask缺失、GQA组错配与backward重算换集合。它们的共同特征是高精度也无法恢复正确结果。检查顺序应从集合和地址开始，不能一上来调浮点容差。

漏候选会使softmax在较小集合上重新归一化。若被漏位置原概率为p，其余权重整体乘以 $1/(1-p)$。即使被漏value本身接近零，其他所有value权重也发生变化。重复候选则给该位置额外指数质量；重复一次等效于logit增加 $\log2$。这两种错误都具有明确方向，可用单位置构造样本迅速识别。 跨请求地址最危险。它既是正确性错误，也可能泄漏其他用户的缓存内容。测试需要让不同请求K/V带明显哨兵值，并随机回收slot，验证任何输出都不含外部哨兵。线上检测到所有权版本不匹配时，应阻断该批，避免用dense fallback继续读取污染状态。

逻辑/物理坐标混淆会表现为输出随内存分配变化。相同prompt重复运行，若页分配不同便得到不同结果，是强烈信号。随机页置换不变量正为捕获这类错误而设计。RoPE已经写入K时，错误位置还可能导致二次旋转或错误偏置，需要对原始K布局单独说明。 mask错误可用极端value放大。给所有无效尾槽填入巨大且互异的value，正确kernel完全不受影响；只要一个槽进入softmax，输出立刻偏离。未来位置也可放置哨兵。依赖未初始化内存的测试偶尔会全零通过，主动填毒值更可靠。 GQA错配通常来自query head到KV head映射。设query heads为Hq、KV heads为Hkv，标准连续分组可写为

$$
g(h)=\left\lfloor\frac{hH_{kv}}{H_q}\right\rfloor. \tag{32}
$$

模型也可能使用不同排列，kernel应服从显式布局。为每个KV head填入不同基向量，可验证每个query head读取了正确组。所有K/V随机同分布时，错组输出可能数值接近，难以定位。 数值错误保留集合，却在缩放、指数、归并、量化或累积中产生偏差。先比较log-sum-exp：若LSE已错，检查logit缩放、mask和分母；LSE正确而输出错，更多指向V载入或PV累积；forward正确、gradient错则检查softmax backward全行归约和转置邻接。 softmax缩放遗漏最容易用维度变化捕获。正确logit除以 $\sqrt d$；固定Q/K分布扫描d时，遗漏缩放会让分布随d急剧变尖。重复应用缩放则过平。与reference逐项比较raw dot和scaled logit，可以在指数前定位。

split归并错误常在各split最大值差异很大时暴露。构造一个split最大logit为50，另一个为0；稳定归并应让第二项贡献接近 $e^{-50}$。若先归一化各split再平均，两个split获得相近权重。扫描split数1、2、4、8并保持集合不变，错误会随split改变。 量化错误分为scale地址、scale粒度、码值解释和累积误差。给每页每通道设置可预测scale，使用少量整数码，可手算重构值。物理排序后若scale仍按任务序号读取，会出现页面与scale错配。reference重构过程与kernel共享同一格式定义，但不共享地址代码，避免同一个bug两边同时出现。 浮点非结合误差通常随顺序平滑变化，结构错误则在某些形状突然跳变。重复随机排列候选并画误差分布，可以区分二者。误差始终很小且围绕零，更像舍入；某一物理页或尾块出现巨大离群，优先查地址与mask。

反向错误还可通过守恒关系检查。对V的梯度，某个query对候选value的系数应为attention概率乘上游梯度；所有候选概率和为1。单query、标量value时可以直接手算。对Q/K则用有限差分抽查，固定候选避免top-k翻转污染结果。 性能错误不改变输出，却让理论稀疏收益消失。可分成流量放大、并发不足、调度长尾、固定成本过高和回退过多。每类都有可测证据：DRAM字节、active warps、CTA时长分布、阶段计时和fallback原因计数。只看总延迟无法决定改哪一层。 流量放大的第一项是块扩张，比较逻辑token、合法扩张token与实际load槽；第二项是事务放大，比较请求字节和DRAM字节；第三项是scratch复制，检查写入与二次读取；第四项是跨head重复，比较GQA理论复用和实际字节。四项相乘可能让低候选率仍接近dense流量。

并发不足要区分任务太少与资源占用太高。小batch decode可能只有少量CTA，增加每CTA工作也填不满GPU；寄存器或shared memory过大则让每SM驻留CTA减少。前者可合并更多请求/head任务，后者需调tile与流水深度。occupancy数字相同，根因可能相反。 调度长尾来自 $k_i$ 分布、split不均与物理页延迟。记录每任务预计块数和实际周期，若周期与块数线性相关，分桶或拆分有效；若同块数差异大，检查地址聚集、cache与页表。persistent queue能平衡数量，无法消除单个超长不可抢占任务。 固定成本通过长度扫描识别。把候选率保持不变，逐渐增加上下文；若索引、top-k与launch近似常数，稀疏路径在某长度后越过dense。若索引扫描随全长增长，它也有线性项，交叉点可能远后于只看K/V读取的预测。

回退过多需要按原因分解。候选率过高说明路由或阈值问题；形状不支持说明kernel覆盖不足；workspace溢出说明容量规划不匹配；安全校验失败说明生命周期错误。将它们合为一个fallback率，会把算法、性能和严重正确性问题混在一起。 错误传播应在最早可验证边界被截断。plan阶段验证范围、所有权与容量；索引阶段验证去重和逻辑映射；kernel debug模式抽查mask与LSE；输出阶段比较少量shadow dense样本；服务阶段监控回退、异常与延迟。越晚发现，定位空间越大，潜在影响也越广。

shadow dense不必覆盖全部流量。按长度、候选率、低margin和新配置分层抽样，对同一输入运行dense reference，记录输出差与候选结构。低margin样本更可能暴露选择误差，新kernel版本则需提高布局与数值抽样。原始内容按隐私规则处理，结构指标与误差可聚合保存。 上线门槛可以写成可证伪条件：随机页置换下输出一致；全候选时与dense等价；split变化误差在界内；尾页毒值完全不影响输出；跨请求哨兵从不出现；反向通过dense与有限差分；目标候选分布下DRAM字节确实下降；端到端越过预先声明的交叉点。任何一项失败都能推翻当前实现已经正确或有效的主张。

验收通过也不代表永久成立。更换page size、GQA比例、量化格式、编译器、GPU架构或调度档位，都可能改变地址、数值与成本。测试矩阵应由配置自动生成，版本发布保存公式语义、索引协议与基准分布。这样后续优化可以改变物理执行，同时有证据证明逻辑图没有被悄悄修改。 结构误差还可以用概率质量给出局部上界。设正确候选集合为S，错误实现得到 $\widetilde S$，漏失集合 $M=S\setminus\widetilde S$ 在正确softmax中的总质量为 $\delta$。若所有value范数不超过V，仅考虑漏失并在剩余集合重归一化，有

$$
\|o_S-o_{S\setminus M}\|\le2\delta V. \tag{33}
$$

这个界无法覆盖跨请求value，因为外部value未必满足同一V与语义；它适合衡量合法集合内的漏页风险。重复集合R也可转化为概率扰动，但结果取决于被重复项的logit和次数，不能用相同的漏失界替代。 若kernel输出误差为 $\epsilon_o$，经过输出投影矩阵 $W_O$ 后满足

$$
\|\Delta h\|\le\|W_O\|_2\epsilon_o. \tag{34}
$$

残差把这项直接加到hidden state，后续归一化与MLP继续变换。全局谱范数连乘通常过松，工程上更有用的是固定轨迹逐层测量误差增益：在某一层注入已知方向的小扰动，记录下一层和最终logit变化。结构bug的影响往往远超正常舍入扰动，应设两档告警。 对归并舍入可以建立经验误差阶。若n个正数用朴素顺序FP32累加，相对误差粗略随 $n\varepsilon$ 增长；树形归约深度约 $\log_2n$，通常更稳定。softmax还包含指数缩放，局部最大值降低动态范围。扫描候选数与split数画误差曲线，正常数值误差应缓慢变化，某个特定split突然跳变更像空状态或workspace索引错误。

测试容差不能只给一个常数。输出绝对值、dtype、候选长度、累积精度和量化格式都会改变正常误差。可以用高精度reference在大量合法随机形状上建立分桶分布，以99.9分位加安全余量设阈值；构造的极端样本仍用明确性质断言，例如单候选输出精确等于value、被mask毒值零影响。

Metamorphic testing能在没有人工答案时制造强关系。对所有logit加同一常数，softmax输出不变；同时置换候选K/V与索引顺序，输出不变；复制整个候选集合两次会保持输出不变，但合法接口应在规范化阶段去重并拒绝多重集；给所有value加常向量c，输出应加c。每条关系针对不同算子环节。 缩放关系也很有用。Q乘a、K除以a，点积不变，输出应一致；V乘a，输出乘a；将一个候选value改为输出当前值，微小改变其概率不会改变输出方向。量化路径不一定严格满足前两条，因为重构舍入会变，测试时使用可精确表示的a或放宽到量化reference。

因果关系测试可把未来token的K/V反复随机化。对位置i的输出，所有 $j>i$ 的变化应完全无影响。尾页测试同理随机化 $j\ge L_n$ 的槽位。若输出只出现末位抖动，仍说明无效地址可能被读入并经过浮点运算；正确mask应让数学路径完全独立，内存安全工具还应验证没有越界load。 GQA关系测试固定一个KV head，复制同一个query到组内多个query heads，它们的输出应相同；给query heads不同向量，输出可不同，但读取的物理K/V页集合按共享协议一致。交换两个KV head及其页表，再同步交换query组，输出也应相应置换。它能发现head stride和分组公式错误。 ragged batch关系测试把一条请求单独运行，再与若干长度不同的请求拼batch，目标请求输出应在容差内不变。若变化显著，常见原因是indptr、workspace offset、slot ID或任务恢复顺序错误。再随机排列batch行，输出按同一排列变化，可验证row identity。

prefix共享测试让两条请求共用前缀物理页，后缀分别写入不同哨兵。前缀query的结果应一致，后缀query只受各自后缀影响。触发copy-on-write后，修改一条请求的新页不得改变另一条。索引层同时检查共享页引用计数与slot generation。 并发生命周期测试需要制造最不利时序：stream A运行旧任务，stream B准备下一步indices，CPU取消请求并尝试回收slot。事件依赖正确时，旧任务完成前slot不可重新分配；双buffer正确时，写入下一缓冲不会覆盖当前读。压力测试可用每页唯一校验码检测偶发串写。 workspace使用红区检测越界。每个buffer前后放置固定canary，运行最大batch、最大K、最大split与尾块组合后核对。容量计算使用checked integer arithmetic，避免维度乘法溢出后分配过小。CUDA Graph档位切换和fallback都要重复红区测试，因为它们常走不同分配路径。

索引整数宽度也是边界。32位token位置可覆盖约21亿位置，物理字节offset若也用32位，数GB cache就可能溢出。逻辑索引、页号、元素offset和字节地址的范围不同，应在提升到64位前完成乘法。测试可用虚拟大页号或接近上限的合成stride，无需真的分配同等内存。 性能验收的统计方法需要控制噪声。单次最快值偏向偶然cache命中，均值容易被系统尖峰拉高。kernel微基准报告median与稳定分位，服务报告P50/P95/P99并给置信区间。比较两个实现时使用相同候选序列成对测量，减少batch分布差异。 计时边界决定结论。kernel-only从任务表已在GPU开始；执行路径包含规范化、plan、kernel与归并；模型路径再包含selector；服务路径还含排队、CPU调度和图切换。四层数字都可报告，标题必须说明范围。用kernel-only倍数描述端到端收益会混淆层次。

冷态与热态也应分开。冷态包括JIT、autotune、内存池扩容、页表首次访问和cache冷启动；热态代表稳定服务。模型频繁切换或shape高度多样时，冷态并非一次性成本。按配置键统计首次命中频率，才能决定是否值得增加特化版本。 候选生成和attention可能在不同stream重叠。阶段时间简单相加会高估关键路径，单独看kernel又低估资源竞争。使用时间线标出依赖与重叠，端到端延迟由最长依赖链决定；吞吐还受两个kernel争抢SM和带宽影响。性能模型中的r应取未被隐藏部分。 当稀疏kernel和dense fallback共享同一GPU时，混合batch的调度会互相干扰。大dense请求可能占满SM，让小sparse请求排队；反向也可能因大量短kernel启动造成调度开销。分别测纯sparse、纯dense与真实混合比例，才能预测P99。

验收数据应覆盖实际候选结构，而非均匀随机mask。至少保存行长直方图、连续段长、逻辑页间距、物理页跨度、页复用计数、GQA并集大小与尾页比例。合成器按这些统计生成索引，并额外加入最坏构造。平均分布验证常态，最坏构造验证安全边界。 每次优化都应回答一个可反驳的问题。例如“物理排序降低事务放大”需要观察相同集合下DRAM字节下降；“split改善长行并行”需要观察CTA尾部缩短且归并成本小于收益；“gather提高复用”需要在不同复用次数r上出现预期交叉。若指标不变，假设没有得到支持，应回到地址或调度模型。

版本回归可保存一组结构指纹：规范化后的逻辑集合哈希、逻辑—物理映射哈希、任务表哈希、每行LSE和输出摘要。新后端与旧后端逐层比较。物理任务表允许因优化变化，逻辑集合必须相同；LSE与输出允许数值容差。指纹层级正好对应语义、布局和数值三个边界。 发布前还应做故障注入。主动破坏一个page table项、缩小workspace、制造空候选、触发不支持dtype、取消活跃请求，验证系统进入预期的拒绝或回退路径，并产生明确原因码。只测试成功路径，无法证明异常不会静默返回错误输出。

最终的判定表可以保持简洁：集合与地址属性全部通过，数学与梯度落在容差内，随机布局不改变语义，生命周期压力没有串请求，目标分布下实际字节与延迟达到门槛，异常路径按严重度处理。每一项都对应可复算证据，因而“kernel正确且有效”不再依赖一次漂亮的吞吐数字。 还可以把整条流水线写成三层函数组合。规范化函数N把原始路由与cache状态映射为逻辑边集E；布局函数L把E映射为带地址和任务分区的执行描述X；数值函数F在X上计算输出。正确实现需要满足

$$
F(L(N(I)),Q,K,V)=\operatorname{Attn}(Q,K,V;E). \tag{35}
$$

N负责集合等价，L负责地址等价，F负责分块数值等价。测试若只比较最终等式右侧与左侧，一旦失败仍不知是哪层；分别保存E与X，就能在函数边界定位。 布局优化可视为对X施加变换 $\pi$，例如物理排序、任务分桶、split或warp重排。合法变换必须保持

$$
F(\pi(X),Q,K,V)\approx F(X,Q,K,V), \tag{36}
$$

近似号只来自浮点顺序。候选删减、重复和mask改变没有资格归入布局优化，因为它们修改E。代码评审时沿这条边界判断一个优化需要算法验收还是只需数值与性能验收。 缓存迁移则要求映射交换律。若物理页重排为R，页表同步更新为 $L_R$，从逻辑集合取值的结果应与迁移前相同。可以表示为

$$
\operatorname{load}(L_R(E),R(K,V))=
\operatorname{load}(L(E),K,V). \tag{37}
$$

这条性质覆盖压缩整理、页池扩容与跨设备搬迁。迁移期间若新旧页表混用，交换律破坏，输出会依赖竞态。 并发下还需要快照语义。一次attention运行所见的页表、有效长度、indices与scale版本应属于同一个逻辑时刻。分别原子更新每个指针并不足够，kernel可能读到新indices和旧长度。可用不可变描述符加版本号，准备完整新快照后一次发布；旧快照等待使用它的stream完成再回收。 版本检查不能放在读取全部K/V之后。kernel入口或plan验证版本，发现不匹配立即退出并报告；运行中页面被回收则说明生命周期协议已经失效。将版本号和slot generation纳入任务描述，可把偶发数据污染变成可检测错误。

多GPU上下文并行时，逻辑集合还要分片到持有对应KV的设备。每卡计算局部online-softmax状态，跨卡使用与split-KV相同的最大值和分母归并。只all-reduce已经归一化的局部输出会给各卡相同权重，分片token数和logit尺度不同时明显错误。通信量虽远小于搬全部KV，跨卡同步仍进入关键路径。 设备故障或通信超时无法简单丢掉一个分片继续生成，因为这等价于大规模漏候选并重归一化。若系统允许降级，必须把它定义成显式近似模式并标记输出；常规正确路径应失败或重试。性能优化不能把通信错误伪装成合法稀疏性。

到这里，kernel验收的核心已经清楚：逻辑边集是模型语义，地址与任务只是表示，online softmax及其反向负责在任意合法分块上恢复同一个函数，成本模型判断这种表示是否值得。把四者分开，才能在追求速度时知道哪些东西可以自由改，哪些边界一旦越过便已经换了模型。 这套划分也便于替换后端。Triton、CUDA或其他实现可以采用不同tile与调度，只要共享同一索引契约、布局映射测试和数值oracle，就能在不重写模型定义的情况下逐项比较。模型语义稳定，硬件特化才有清晰边界。

反过来，若一次优化无法说明它保持了哪条集合、地址或归一化不变量，就应先停留在实验分支。速度提升只有建立在相同模型函数上，才具备可比较性；有意引入近似时，也需要单独报告质量预算。

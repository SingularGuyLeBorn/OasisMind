# 缓存驱逐: 在固定容量里保留仍会被访问的KV

长上下文推理的KV压力有两种处理方向. [读取选择](../3.1-读取选择/3.1-读取选择.md)保留完整历史, 每一步只加载少量候选页; 缓存驱逐直接删除一部分历史KV, 把显存占用限制在固定预算内. 前者选错后, 原始状态仍可能在下一步重新进入候选. 后者一旦删错, 后续query已经无法访问那段表示. 这项差别决定了两类方法的目标、状态机和故障方式.

缓存驱逐适合Decode很长、batch受KV容量限制的场景. 每生成一个token都会为各层追加K和V, 若不处理, 单请求占用随序列长度线性增长. 固定容量策略把每层可保存的位置数限制为 $B$, 新位置进入时必须决定谁离开. 系统获得可预测的显存上界, 代价是模型所见历史变成压缩后的子序列.

## 1. 三种保留信号

### 1.2. 最近位置

最近窗口保留末尾 $W$ 个位置. 它不需要attention统计, 更新只涉及环形指针, 对局部语法、短程复制和当前话题稳定有效. 单独依赖recency会持续淘汰早期指令、实体定义和反复引用的锚点. 序列越长, 这类远距信息越容易落到窗口之外.

窗口也影响位置编码与物理布局. 删除中间位置后, 剩余KV可以继续使用原始位置, 也可以在cache内部重新编号; 两种做法对RoPE并不等价. 分页cache还要决定回收的是token槽还是整页. 算法预算按token给出, 实际显存通常按page释放.

**累计注意力。**

attention分数提供另一种信号: 某个历史token已经被多少后续query使用. 若第 $t$ 步对位置 $i$ 的attention权重为 $a_{t,i}$, 可维护累计分数

$$
s_i^{(t)}=s_i^{(t-1)}+a_{t,i}.
$$

高分位置被称为heavy hitters. 它们可能不靠近序列末尾, 却在生成过程中反复参与计算. 累计量只使用已经出现的query, 不需要预知未来. 但它偏爱活得久的位置: 两个token每一步得到相同权重时, 更早进入cache的token自然积累更多分数.

**Prompt末端的观察窗口。**

另一条路线在Prefill结束时, 用prompt末端的一段queries观察整段prompt. SnapKV按head汇总这些query对历史位置的attention, 再经一维池化把相邻高分位置聚成簇, 一次性压缩prompt KV. 它利用的是生成开始前已经可见的attention模式; H2O则在生成过程中持续更新累计分数并逐步驱逐.

两者可以使用相同容量, 状态变化仍完全不同. SnapKV压缩后通常保留观察窗口, 已删除prompt位置不会因后续query而回来. H2O每步都让recent区域随生成前移, 较老位置能否留下取决于累计得分. 长Decode任务尤其需要区分这两种时间尺度.

### 1.1. H2O把历史分成两部分

**Heavy hitters与recent window。**

[H2O](./3.2.1-H2O.md)把容量同时分给高累计分位置和最近位置. 论文实验常把两部分均分. recent区域保证新token至少获得若干次被观察的机会, heavy-hitter区域保存已经反复贡献的旧token. 若只保留高分, 新位置可能在积累分数前就被删除; 若只保留最近位置, 远距锚点会随着窗口移动消失.

这种组合形成在线状态机. 新KV先进入recent区域; attention完成后, 当前权重累加到仍在cache的位置; 容量超限时, 在可驱逐集合中删除低分位置. 被删位置的K、V和分数一并消失. 分数依赖当前cache产生的attention, 因而早期一次误删会改变后续分布.

**局部统计与未来重要性。**

若能知道未来所有query, 最理想的评分可以把某个位置未来将获得的attention全部相加. 在线生成拿不到这项信息. H2O使用到当前时刻为止的局部累计量, 依据是attention重要性具有持续性: 已经多次被使用的位置, 后面继续被使用的概率较高.

持续性是经验规律, 不是对每个样本都成立的保证. 一段早期定义可能在很久之后第一次被引用; 在引用发生前, 它的累计分数可能很低. recent区域只能保护刚进入cache的位置, 无法覆盖很长的沉默期. 这也是固定预算驱逐面对needle检索、延迟引用和多阶段推理时的主要风险.

## 2. 算法成本必须落到系统

### 2.2. Attention分数是否可得

标准写法会得到完整attention矩阵, 累计每列很直接. 高效attention kernel通常分块计算softmax并立即聚合V, 不把所有权重写回显存. 若为了H2O重新物化attention权重, 额外写流量可能抵消缩短KV带来的收益. 另一种实现是在kernel内部顺便归约列统计, 这需要专门算子和额外原子更新或分块归并.

因此, “评分不需要新模型参数”不等于“评分免费”. 每层、每个KV head都要保存分数, 还要进行候选选择和数据移动. GQA下可以按KV head聚合多个query heads, 也可以各head独立评分后合并; 两种定义会产生不同保留集合.

**Token驱逐与page回收。**

论文算法把一个token视为一个cache元素. 推理引擎常用16、32或更大的page管理KV. 从一页中删掉一个token不会释放整页, 还可能制造洞和间接寻址. 若按page驱逐, 评分需要从token聚合到page, 容量粒度也随之变粗; 一个高分token可能保护整页低分邻居.

另一种实现会周期性压实cache, 把保留KV复制到连续空间. 压实释放显存并改善后续读取, 但复制量与层数、head数和向量维度成正比. 每token都压实通常过贵, 延迟压实则使逻辑容量与物理占用暂时不一致. 衡量驱逐策略时必须同时报告保留token数、占用pages和搬移字节.

**Prefill与Decode的边界。**

Prefill结束时已经产生整段prompt KV. 若容量小于prompt长度, 系统要在第一步Decode前压缩prompt, 或在Prefill内部流式驱逐. 前者需要prompt attention统计并可能产生较大临时张量; 后者只看已处理前缀, 会改变后面prompt token的计算上下文. 两条路径得到的模型输出不一定一致.

Decode阶段每次只新增一个位置, 在线更新更自然. 但batch中每个请求拥有不同保留集合, page表和kernel行长会变得ragged. 固定逻辑容量减少了总KV, 不自动保证每一步读取连续. cache策略与attention kernel需要一起设计.

### 2.1. 这条路线怎么读

**先读H2O的逐步驱逐。**

[H2O](./3.2.1-H2O.md)适合作为入口, 因为它把问题完整写成在线缓存: 分数如何累计, 新token如何进入, 超预算时谁离开, recent与heavy-hitter如何分配容量. 读算法时同步手算一个小cache, 很快就能看到“只留高分”和“只留最近”各自的问题.

随后再看实现约束. attention权重是否暴露、分数按head还是按token共享、分页系统能否释放物理页, 都会改变端到端结果. 论文中的吞吐数字来自特定模型与推理系统, 不宜只按缓存压缩比例外推.

**再看持久性与一次性压缩。**

Scissorhands同样依赖重要性的持续性, 但它维护pivotal tokens的方式与H2O累计attention不同. SnapKV把评分集中在prompt末端观察窗口, 更接近生成前的一次性压缩. StreamingLLM保留开头sink和最近窗口, 不根据任务内容动态选择远距token.

把四者放到时间轴上, 差别集中在三个位置: 评分发生在Prefill还是每步Decode, 被保留的远距位置由固定规则还是attention统计决定, 生成后是否继续更新. 名称里都出现“压缩KV”, 并不意味着它们能共享同一个cache更新函数.

## 3. 评测要覆盖删除后的后果

**质量与预算曲线。**

固定预算至少扫描5%、10%、20%、40%和完整cache, 并把prompt长度与生成长度分别变化. 短生成可能主要检验prompt压缩, 长生成才会反复触发在线驱逐. 评测集要包括局部语言建模、远距检索、摘要、代码、对话状态和长推理, 平均分无法指出哪类信息先被删除.

还应记录被驱逐位置在完整attention下的事后质量、保留集合周转率、heavy-hitter寿命和recent区域命中. 一次低分误删若在几百步后造成失败, 只看当步logit误差很难定位. 逐步保存保留集合可以重放错误发生前的状态.

**内存与时延曲线。**

显存报告要区分逻辑KV、物理pages、评分状态、索引、临时排序缓冲和压实workspace. 时延拆成attention、分数更新、top-k或淘汰、page管理和数据搬移. 吞吐提高可能来自batch变大, 同batch延迟则更能显示单请求读取量是否下降.

**缓存驱逐换来的固定容量, 本质上是一项不可逆的状态选择.** recent窗口负责给新信息观察期, importance负责保存反复使用的旧信息, 系统实现负责把逻辑删除变成真实显存与带宽收益. 三者缺一项, “保留20% KV”都不足以说明质量或速度.

### 3.1. 在线驱逐面对未知未来

在第 $t$ 步，策略只看到历史 $\mathcal H_t$，却要决定容量为 $B$ 的保留集合 $A_t$。未来 query 序列未知，理想目标是最小化后续生成损失：

$$
\min_{A_t:|A_t|\le B}
\mathbb E\left[
\sum_{u=t+1}^{T}\Delta\mathcal L_u(A_t)
\mid\mathcal H_t
\right].
$$

累计 attention、近期性和 sink 位置都是对条件期望的代理。累计 attention 假设过去常用的位置以后仍常用；近期窗口假设新信息需要观察期且短程依赖普遍存在；sink 规则保护维持 attention 数值结构的固定位置。三种先验可以组合，组合后的预算必须明确分配，不能让各支路分别声称使用同一个 $B$。

经典缓存算法按请求命中优化，KV 驱逐的损失更复杂。一次未命中没有外部后备存储时无法重新加载原 KV；不同 token 的价值也不是相同的一个 miss。删除位置 $j$ 对未来输出的影响依赖 query、value 方向和后续层传播。因此 LRU、LFU 的直觉有参考价值，却不能直接给出语言模型质量保证。

### 3.2. H2O 的集合价值视角

H2O 将 KV 保留表述为带容量约束的动态子模问题，并以近期 token 与 heavy hitter 组合构造策略。子模函数具有边际收益递减性质：集合越大，再加入一个元素带来的新增收益不会更大。若 attention 覆盖效用近似满足该性质，贪心选择可以获得理论近似保证。

语言模型的真实任务损失并不天然子模。两个 token 可能只有同时保留才构成完整约束，单独保留任意一个几乎无用，这属于互补效应；同一事实的多个重复位置则更接近边际递减。理论保证成立于论文定义的效用与假设，不能直接外推成任意下游任务的质量保证。

heavy hitter 分数通常由历史 attention 累积：

$$
s_j(t)=\sum_{u=j+1}^{t}a_{uj}.
$$

老 token 拥有更多累积机会，可以除以存活步数得到平均访问，也可以指数衰减强调近期。累计值保护长期反复使用的位置，平均值保护偶尔强响应的新位置，衰减值适应主题切换。三者对应不同未来先验，实验应在长生成和主题转换上分别比较。

## 4. 观察窗口是生存期保护

新 token 刚写入时尚未接受足够多未来 query 检验，立即与长期 heavy hitter 比累计分数必然处于劣势。recent window 相当于给每个 token 长度为 $w$ 的免淘汰期。离开窗口后，它依靠已经积累的重要性竞争长期槽位。

设长期槽位数为 $B_h$，近期槽位为 $B_r$，总预算 $B=B_h+B_r$。$B_r$ 增大能保护局部依赖和慢热 token，却压缩长期记忆；$B_h$ 增大保存更多历史热点，却可能让刚出现的信息过早被淘汰。合理比例取决于访问延迟分布：若 token 第一次被强关注通常发生在写入后很近的位置，小窗口足够；若任务经常隔很久才首次引用，历史 attention 无法提前识别，必须依赖内容预测、摘要或外存恢复。

考虑一个直接反例：prompt 开头出现一次随机密码，中间从未被关注，末尾才询问。任何只根据过去 attention 且预算不足以保留全部 token 的策略，都可能在问题出现前删除密码。这个失败来自在线信息限制，继续调累计分数的系数无法消除。可恢复层级或 query-aware 完整索引能处理此类未来突变，永久驱逐无法仅靠历史统计保证。

### 4.1. 多层和多头的驱逐单位

若每层独立驱逐，同一 token 可能在浅层被删、深层保留。这样能适应层级差异，却需要每层独立页表，物理碎片和元数据增加。若所有层共享 token 保留表，回收可整页进行，某一层的专门需求可能被平均统计淹没。

多头也有同样选择。按 head 独立保留最灵活，但 MHA/GQA 的 KV 布局通常把多个 head 的同一 token 连续存储；只删一个 head 未必能释放完整页。按 KV head 组聚合分数较符合 GQA 存储，聚合函数仍会影响专门头。最大值保护任一头，平均值偏向共同热点，分位数提供两者之间的控制。

物理释放粒度若是页，token 级淘汰要经过压实。设页含 $P$ 个 token，只删除零散 token 而不搬移，其显存仍被占用；压实需要复制存活 KV 并更新逻辑位置映射。另一条路线直接按页淘汰，释放即时但粒度粗。报告容量时应区分逻辑存活 token 与实际分配页字节。

## 5. 被删状态还能怎样补偿

分层存储把被驱逐 KV 移到 CPU 或更慢设备，后续 query 命中时再取回。它将永久信息损失换成延迟与带宽问题。为了在计算 attention 前知道要取回哪些页，设备上仍需保存较小索引；若索引也被删除，系统无法发现冷页相关。

摘要压缩则为被删区域留下少量向量。一个摘要可以保留主题均值，却无法同时精确表示组内多个实体。若保留 $r$ 个摘要槽，可把 value 矩阵近似为低秩表示；误差随局部秩与 query 分布变化。摘要与原 KV 的 attention 分数尺度还需校准，否则一个聚合了许多 token 的向量可能因数量或范数获得不合理权重。

重计算是第三条恢复路径。只保存原 token ID，在需要时从较早 checkpoint 重新执行模型得到 KV，可以节省存储，却需要知道何时触发，并承担多层前向成本。自回归模型的历史隐藏状态依赖此前上下文，重算起点太早会非常昂贵；周期性保存状态 checkpoint 可以在容量与恢复时间之间折中。

### 5.1. 驱逐误差会沿生成轨迹积累

第 $t$ 步驱逐造成的 logits 扰动可能改变采样 token。新 token 一旦不同，后续 query、KV 和驱逐分数全部分叉，之后即使恢复完整 cache，也无法回到原轨迹。使用 teacher forcing 比较每步 logits，可以隔离局部近似误差；自由生成比较最终答案，则包含轨迹放大。两者都需要报告。

可以计算完整模型分布 $p_t$ 与压缩模型分布 $q_t$ 的 KL，并按生成步累计：

$$
D_{1:T}=\sum_{t=1}^{T}\operatorname{KL}(p_t\|q_t).
$$

这个和不是最终序列 KL 的简单替代，前提是两者在相同历史上评估；它仍能定位误差从哪一步开始上升。将开始上升的位置与淘汰日志对齐，可以找到造成长尾失败的状态。

### 5.2. 容量收益要按物理页验收

KV 逻辑字节由层数、KV head、head 维度、精度和存活 token 决定。实际显存还含页内碎片、页表、评分数组、排序工作区和 allocator 预留。驱逐后若内存池只把页标为空闲而未归还设备，进程显存不会下降，却可能允许更大 batch；这属于可复用容量，而非操作系统可见释放。

吞吐提升也可能主要来自 batch 增大，而单请求 latency 不变。应分别测固定 batch 的 token 延迟、固定显存下最大 batch 和真实到达流量下的吞吐。三种结果回答不同问题。驱逐策略的更新时间、压实频率和页回收停顿会影响 P99，平均吞吐无法替代尾延迟。

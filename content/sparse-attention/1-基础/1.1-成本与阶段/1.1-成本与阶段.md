# 成本与阶段：从边数到真实执行

「注意力从全连接变成稀疏连接，所以速度会按稀疏率提升」，这句话只算了纸面上的边数。GPU 执行时还要生成索引、读取 KV、搬运块、完成归一化，并让足够多的线程同时工作。一个保留 10% 注意力边的算法，可能把乘加量降到十分之一，也可能仍然读完全部 KV，最终只快一点点。训练、Prefill 和 Decode 又处在不同瓶颈上：训练要保存或重算反向传播需要的中间量；Prefill 一次处理许多 query，容易把矩阵单元喂饱；Decode 每层通常只有一个新 query，却要面对越来越长的历史。

因此，讨论成本至少要同时写清四件事：**算了多少 FLOPs，HBM 搬了多少字节，常驻显存放了什么，稀疏结构是否能被内核直接利用**。这四个问题分别对应算力、带宽、容量和实现。只报复杂度，往往漏掉真正卡住机器的那一项。

## 1. 先把注意力中的对象分清

设批量为 $B$，序列长度为 $N$，模型层数为 $L$，隐藏维度为 $d$，query 头数为 $H_q$，KV 头数为 $H_{kv}$，每头维度为 $d_h=d/H_q$。每个元素占 $b$ 字节；BF16、FP16 通常取 $b=2$，FP8 取 $b=1$。以下公式先忽略张量并行，再在需要时补回每卡切分。

### 1.2. MHA、GQA 与 MQA 改的是哪一项

标准多头注意力在每层产生

$$
Q=XW_Q,\qquad K=XW_K,\qquad V=XW_V,
$$

并计算

$$
O=\operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d_h}}+M\right)V.
$$

MHA 令 $H_{kv}=H_q$。GQA 让一组 query 头共享一组 K/V，因而 $1<H_{kv}<H_q$；MQA 则取 $H_{kv}=1$。GQA 论文的核心动机就是缩小 decoder 推理中的 KV 读取与缓存，同时尽量保持接近 MHA 的质量。**它压缩的是 head 轴，不会自动减少 query 与历史 token 之间的连接数。**

单个 token、单层需要缓存的 K/V 元素数为

$$
E_{KV,\text{layer}}=2H_{kv}d_h,
$$

前面的 2 分别代表 K 和 V。于是单请求、全部层、长度为 $S$ 的 KV 容量为

$$
C_{KV}=2LSH_{kv}d_hb.
$$

取 $L=32$、$H_q=32$、$d_h=128$、BF16，并令历史长度 $S=32768$。MHA 的 $H_{kv}=32$，因此

$$
C_{KV}=2\times32\times32768\times32\times128\times2
=17{,}179{,}869{,}184\ \text{bytes}\approx16\ \text{GiB}.
$$

若改成 $H_{kv}=8$ 的 GQA，同一请求约占 4 GiB；MQA 则约占 512 MiB。这里没有加入分页尾块、对齐、量化 scale、分配器碎片和框架工作区，所以这些数是「逻辑有效载荷」，不能直接当成进程显存占用。

**MLA 压的是 latent 轴。**

DeepSeek-V2 的 MLA 不按 query 组保存多份完整 K/V，而是保存低秩压缩后的 KV latent，并把与 RoPE 有关的小维度单独处理。其论文给出的缓存形式可概括为每个 token、每层保存 $d_c$ 维压缩表示与 $d_r$ 维解耦位置表示，因此近似容量为

$$
C_{MLA}=LS(d_c+d_r)b.
$$

这条式子与 GQA 的 $2LH_{kv}d_hSb$ 不能混用。GQA 沿头数缩减；MLA 改写了 K/V 的表示和投影路径。部署时还要确认具体实现缓存哪些张量、权重吸收采用哪条路径，不能只看到“MLA”三个字就套固定压缩比。

仍用 $L=32$、$S=32768$、BF16，假设 $d_c=512$、$d_r=64$，则逻辑容量为

$$
32\times32768\times(512+64)\times2
=1{,}207{,}959{,}552\ \text{bytes}\approx1.125\ \text{GiB}.
$$

这个数只由给定维度推导，不代表任意 MLA 模型的固定开销。它说明了一件更重要的事：评估 KV 成本时，先问“每层每 token 到底保存哪些状态”，再谈 MHA、GQA 或 MLA 的名字。

**KV Cache 节省了计算，也制造了容量与带宽问题。**

若 Decode 时不缓存历史 K/V，第 $t$ 步要把此前所有隐藏状态重新投影成 K/V，重复计算随生成长度不断累积。KV Cache 保存已经算好的 K/V，使新一步只投影新 token，然后让新 query 与历史 keys 做点积。代价是缓存随 $S$ 线性增长，而且每一步要读取历史状态。

这形成了一个很容易混淆的交换：**KV Cache 把重复计算换成了常驻容量与读带宽。**GQA、MLA、KV 量化处理的是缓存表示；滑动窗口、淘汰和 token 稀疏处理的是保留多少位置；PagedAttention 处理的是如何分配和复用物理页。三类方法可能叠加，但账要分开算。

**Q 与 KV 投影也会随结构变化。**

缓存公式只数推理期间留下的状态，投影矩阵还会改变参数量与每 token 计算。MHA 的 Q、K、V 输出维度均为 $d$，三次投影的前向计算约为 $6BNd^2$ FLOPs；输出投影再加约 $2BNd^2$。若 GQA 的 K/V 输出宽度变为 $H_{kv}d_h$，则三次输入投影约为

$$
F_{QKV}=2BNd\left(d+2H_{kv}d_h\right).
$$

令 $H_{kv}=H_q/4$，K/V 两个投影各缩为 MHA 的四分之一，但 Q 与输出投影保持不变。QKV 加输出投影合计从 MHA 的约 $8BNd^2$ 降至约 $5BNd^2$，并没有随着 KV Cache 一起缩为四分之一。这也解释了为何 GQA 的主要部署价值集中在缓存容量和 Decode 读取，而非把整个 attention 层计算按相同比例砍掉。

MLA 的投影成本需要沿实际计算图计算。压缩投影、解压或权重吸收、解耦 RoPE 通道都会带来矩阵乘法；推理优化实现可以利用矩阵结合律避免显式还原完整 K/V。若直接把缓存压缩比当成计算压缩比，通常会算错。最稳妥的办法是列出执行图中的矩阵形状，再对每个 $[m,k]\times[k,n]$ 记 $2mkn$ FLOPs。

**先把“状态数”和“连接数”分成两条轴。**

KV Cache 容量与注意力边数经常一起出现, 两者的增长规律并不相同. 每个历史 token 在每层留下一个 KV 状态, 所以状态数随序列长度 $S$ 线性增长;Prefill 中每个 query 又与此前许多状态建立连接, 全因果边数随 $N^2$ 增长. 令每 token、每层 KV 元素数为 $q_e=2H_{kv}d_h$, 则状态元素总量为 $LSq_e$;令第 $i$ 个 query 的候选数为 $k_i$, 边数为 $\sum_i k_i$.

GQA、MLA 与 KV 量化主要减小 $q_e$ 或每元素字节, 不直接改变 $k_i$;窗口、block mask 与 token top-k 主要减小 $k_i$, 不必改变每个保留状态的宽度. KV 淘汰同时减少未来可用状态数与候选上限. 因此两种“16 倍”可能作用在完全不同的量上: GQA 把每个 token 的 KV 字节缩小 4 倍, top-k 把本步读取 token 数缩小 16 倍, 理想读取量才可能得到二者乘积;常驻容量若没有淘汰, 只得到前一项.

用二维坐标表示更直观. 横轴取历史状态数 $|A_t|$, 纵轴取本步读取数 $|C_t|$. 全注意力随生成沿对角线增长, 因为 $|A_t|=|C_t|=t$;动态 top-k 向下移动, $|A_t|=t$ 而 $|C_t|=k$;固定窗口同时限制两轴, 长度超过 $W$ 后 $|A_t|=|C_t|=W$;完整缓存加局部窗口但不释放旧 KV 则是 $|A_t|=t$、$|C_t|=W$. 仅看 attention mask, 后两者完全相同;看容量时, 结果相差可随 $t/W$ 持续扩大.

第三条轴是每状态字节 $q_b=2H_{kv}d_hb$. 某一步的理想 KV 读取为 $|C_t|q_bL$, 常驻容量为 $|A_t|q_bL$. 页面与 tile 会把两个理想量分别放大为物理分配和物理读取. 设容量放大系数为 $\gamma_c\ge1$, 读取放大系数为 $\gamma_r\ge1$, 则

$$
C_{physical}=\gamma_c|A_t|q_bL,
\qquad
D_{physical}=\gamma_r|C_t|q_bL.
$$

$\gamma_c$ 来自尾页、对齐与分配器保留, $\gamma_r$ 来自整页读取、重复加载和不连续访问. prefix sharing 可能让多请求合计容量低于逐请求有效载荷之和, 这时应先按唯一状态去重, 再讨论放大系数. 这组变量把“模型结构”“稀疏算法”和“runtime 布局”放在各自位置, 避免同一个缓存公式承担三种含义.

query 数 $Q$ 也是独立维度. Prefill 的 $Q=N$, Decode 通常为每请求 $Q=1$, chunked prefill 为 $Q=C$. 相同的历史状态与候选预算, query 多时可复用 K/V 并形成大矩阵, query 少时更接近流式读取. 因而完整成本描述至少包含 $(Q,|A|,|C|,q_b)$, 再补 tile、page 和并行布局. 只写序列长度 $N$ 会把这些形状差异全部压扁.

### 1.1. FLOPs：平方项究竟来自哪里

矩阵乘法通常把一次乘法和一次加法计作 2 FLOPs。忽略因果三角可跳过的一半工作，单层 Prefill 中 $QK^\top$ 的 FLOPs 约为

$$
F_{QK}=2BN^2H_qd_h=2BN^2d,
$$

随后 $PV$ 的量级相同，所以

$$
F_{attn,\text{prefill}}\approx4BN^2d.
$$

因果掩码在数学上只允许下三角边，理想情况下可把有效乘加近似减半；具体内核是否跳过无效 tile，要看实现。Q/K/V/O 投影和 MLP 仍随 $N$ 线性增长。于是“Attention 是 $O(N^2)$”只描述注意力主项，不能推出整个 Transformer 在任意长度都由它主导。

以 $B=1$、$N=8192$、$d=4096$ 为例，不利用三角结构时，单层 QK 与 PV 合计

$$
4\times8192^2\times4096
=1{,}099{,}511{,}627{,}776\ \text{FLOPs}
\approx1.10\ \text{TFLOPs}.
$$

32 层约为 35.2 TFLOPs。若一个块稀疏模式最终让内核只执行 25% 的 QK/PV tiles，理想注意力主项降到约 8.8 TFLOPs；selector、softmax、索引和其余网络模块尚未计入。

Decode 第一步只有一个或少量 query。单 token、单层在历史长度 $S$ 上的 QK 与 PV 为

$$
F_{attn,\text{decode}}\approx4SH_qd_h=4Sd.
$$

仍取 $S=8192$、$d=4096$，单层约 1.34 亿 FLOPs，32 层约 4.29 GFLOPs。这个数字看起来不小，但其矩阵形状很“瘦”，很难达到大 GEMM 的峰值利用率，而且还要从 HBM 读取权重与历史 KV。Decode 常常先撞上带宽墙。

**投影项与注意力项在多长的序列上相交。**

把一个 Transformer block 的主要矩阵乘法全部摆出来, 才能判断平方项何时占主导. 对采用普通稠密前馈网络的 decoder-only 模型, attention 的四个线性投影约需 $8BNd^2$ FLOPs. 若前馈层先升到 $d_{ff}$ 再降回 $d$, 两个前馈投影约需 $4BNdd_{ff}$ FLOPs. 令扩张比为 $r=d_{ff}/d$, 则单层线性项近似为

$$
F_{linear}\approx(8+4r)BNd^2.
$$

因果 attention 的 QK 与 PV 若能完整跳过上三角, 主项约为 $2BN^2d$ FLOPs. 两项相等时,

$$
2BN^2d=(8+4r)BNd^2,
$$

消去 $BNd$ 可得交叉长度

$$
N_{cross}=(4+2r)d.
$$

例如 $r=4$ 时, $N_{cross}=12d$. 对 $d=4096$ 的模型, 交叉点约为 49152 token. 这项手算解释了一个常见现象: 序列已经长到 8K 或 16K, attention 的平方项确实增长很快, 可是全层 FLOPs 仍可能由线性投影和前馈层占据很大比例. 若采用 SwiGLU, 前馈层通常包含门投影、值投影和输出投影, 线性项还要按真实矩阵形状重算, 交叉点会继续移动.

这条交叉式只比较 FLOPs, 没有纳入 kernel 利用率. 大型投影矩阵通常接近高效 GEMM, 因果 attention 则受 tile 边界、softmax 和掩码影响. 同样数量的 FLOPs, 两者的实际耗时不会相等. 若稀疏 attention 只保留比例 $\rho$ 的物理 tiles, 其主项成为 $2\rho BN^2d$; 理想交叉长度扩大到 $(4+2r)d/\rho$. $\rho=1/4$ 时, attention 要到约 $48d$ 才在 FLOPs 上追平线性模块. 稀疏化降低平方项后, 优化重点自然会转移到投影、前馈层和通信, 端到端收益逐渐受 Amdahl 定律限制.

GQA 会改变这里的线性常数. 设 $g=H_{kv}/H_q$, Q 投影输出仍为 $d$, K/V 投影各输出 $gd$, 输出投影仍为 $d$. attention 四投影的计算由 $8BNd^2$ 变为

$$
F_{proj,GQA}=2BNd(d+gd+gd+d)=4(1+g)BNd^2.
$$

当 $g=1$ 时退化为 MHA 的 $8BNd^2$; 当 $g=1/4$ 时为 $5BNd^2$. GQA 对 QK/PV 的逻辑 FLOPs 没有同等比例的削减, 因为每个 query head 仍要与对应的共享 key head 计算. 因此 GQA 会略微降低线性投影项, 同时大幅降低 KV 容量与 Decode 读取量. 把这三项分开, 才能解释为何同一种 GQA 配置对训练 FLOPs、Prefill 延迟和 Decode 吞吐的影响并不相同.

**反向传播为什么不能用前向乘二代替。**

考虑矩阵乘法 $Y=AB$, 其中 $A\in\mathbb{R}^{m\times k}$, $B\in\mathbb{R}^{k\times n}$. 前向需要约 $2mkn$ FLOPs. 给定输出梯度 $G=\partial\mathcal{L}/\partial Y$, 两个输入梯度为

$$
\frac{\partial\mathcal{L}}{\partial A}=GB^\top,
\qquad
\frac{\partial\mathcal{L}}{\partial B}=A^\top G.
$$

两个梯度各是一遍同量级矩阵乘法, 所以前向与反向合计约 $6mkn$, 即前向的三倍. 对 QK 而言, 反向要生成 $dQ$ 与 $dK$; 对 PV 而言, 反向要生成概率梯度与 $dV$. softmax 还要用输出概率或可重算的统计量计算 Jacobian-vector product. 因而「前向 attention 省了 75% 边」最多说明两个主矩阵乘法的前向候选收益, 训练总 FLOPs 还取决于反向能否沿同一稀疏图执行.

若稀疏 mask 在整个前反向期间固定, 被删除的边在 QK、softmax、PV 及其梯度中都可以跳过. 若 mask 来自可学习 selector, 情况分成两条路径. hard top-k 的索引对离散选择本身没有普通导数, 训练通常依赖代理梯度、辅助损失或先算连续分数再截断; soft gate 则可传播到候选分数, 可它往往需要保存或重算更多中间量. 训练成本因此包含两张计算图: 主 attention 图和路由图. 路由图若扫描全部 query-key 对, 即使维度较小, 仍保留平方数量的候选关系.

激活保存也要逐项列出. 朴素 attention 可能保存 $Q$、$K$、$V$、完整分数矩阵、softmax 概率和输出; FlashAttention 保存输入输出及每行归一化统计量, 反向时按 tile 重算分数和概率. activation checkpointing 又可以只保留 block 输入, 反向重做整段前向. 三种策略的显存由多到少, 重算 FLOPs 由少到多. 稀疏 mask 若包含不规则索引, 还要决定保存索引还是重算索引: 保存需要与边数相关的整数存储, 重算则重复 selector、top-k 和去重.

设每个 query 保留 $k$ 个 key, 索引用 32 位整数. 单层、单样本的索引容量约为 $4Nk$ bytes. 当 $N=32768$、$k=2048$ 时, 仅索引就有 256 MiB. 若 32 层各自拥有独立路由, 总量达到 8 GiB; 若同一索引跨 head 或跨层共享, 容量下降, 但各层可表达的连接图也受到约束. 所以动态稀疏训练不能只展示 attention 概率没有物化: 离散路由表本身也可能成为显存大项.

反向中的原子累加与负载不均同样会改变墙钟时间. 多个 query 选择同一个 key 时, $dK$ 和 $dV$ 要把来自不同边的梯度归并到同一位置. 规则块布局可以把归并组织成矩阵乘法; 任意 token 索引常需要 scatter-add 或排序后的分段归约. 热门 token 接收大量边, 冷门 token 几乎没有工作, 平均 $k$ 相同也不代表线程块耗时均匀. **训练加速成立的条件比前向稀疏率严格: 前向、两个主反向、路由反向与梯度归并都要利用相同结构.**

## 2. HBM：FLOPs 少了，字节可能一动没动

GPU 的计算单元不能直接使用远在 HBM 中的所有数据。数据要进入片上缓存、共享内存或寄存器，完成运算后再写回。FlashAttention 的贡献正是在不改变精确注意力数学结果的前提下，通过 tiling 和在线 softmax 减少 HBM 与片上 SRAM 之间的读写，避免物化完整的 $N\times N$ 分数矩阵。它说明了一个朴素事实：**相同 FLOPs 可以有完全不同的墙钟时间。**

### 2.2. 用算术强度判断瓶颈

算术强度定义为

$$
I=\frac{\text{FLOPs}}{\text{从较慢存储层搬运的字节数}}.
$$

若设备峰值算力为 $P_{peak}$，峰值 HBM 带宽为 $BW_{peak}$，Roofline 模型给出的性能上界是

$$
P\le\min(P_{peak},\ I\cdot BW_{peak}).
$$

交叉点 $I^*=P_{peak}/BW_{peak}$。低于它时更容易受带宽限制，高于它时才可能受算力限制。NVIDIA 官方资料给出 H100 SXM 的 HBM 带宽约 3.35 TB/s；算力峰值随数据类型、稀疏模式和计数口径变化，因此不能脱离具体规格表随手填一个统一的 $P_{peak}$。

Decode 的 KV 读取很适合做下界估算。若 BF16 MHA 的历史 KV 在某请求上是 16 GiB，而每步确实读完这些缓存，即使先忽略权重和其他层，单靠 3.35 TB/s 的理想带宽也需要

$$
t_{KV}\ge\frac{16\ \text{GiB}}{3.35\times10^{12}\ \text{byte/s}}\approx5.1\ \text{ms}.
$$

换成 4 GiB 的 GQA，下界约 1.3 ms；前述 1.125 GiB 的 MLA 示例约 0.36 ms。实际时间还会受到有效带宽、并发请求、地址连续性、kernel launch、权重读取与通信影响，通常高于这个理想下界。这个简单除法已经能解释：为什么减少 KV 字节会直接改善 Decode，又为什么纸面 FLOPs 并不足以预测 TPOT。

**Prefill 为什么更容易吃到算力。**

Prefill 一次带着 $N$ 个 query。K/V 块加载到片上后，可以被多个 query 块反复使用，数据复用率明显高于单 query Decode。序列越长，QK 与 PV 的乘加增长越快；若 tile 合适，计算单元有充足工作，Prefill 更容易进入 compute-bound 区域。

这种判断仍有边界。短 prompt、小 batch、很窄的 head dimension，或者大量不规则小块，都会降低并行度。TTFT 还包含嵌入、投影、MLP/MoE、跨卡通信、排队和调度。attention kernel 快 2 倍，端到端 TTFT 不会自动快 2 倍。若 attention 原来只占 TTFT 的 40%，即便把它降为零，总体也最多快到原来的 $1/(1-0.4)=1.67$ 倍，这就是 Amdahl 定律给出的上限。

**从朴素实现到在线 softmax, 字节是怎样降下来的。**

先看最直接的三步实现. 第一步计算 $S=QK^\top$, 把 $N\times N$ 分数写到 HBM; 第二步从 HBM 读 $S$, 做逐行 softmax, 再把概率矩阵 $P$ 写回 HBM; 第三步读取 $P$ 与 $V$, 计算 $O=PV$. 暂时忽略 Q/K/V/O 本身, 仅中间矩阵就产生一次 $S$ 写入、一次 $S$ 读取、一次 $P$ 写入和一次 $P$ 读取, 约为 $4N^2b$ bytes. 当 $N=32768$、$b=2$ 时, 单头中间量流量约为 8 GiB. 多头和多层一乘, HBM 很快成为主导.

在线 softmax 的关键在于一行可以分块归并. 对已经处理的分数集合维护最大值 $m$、指数和 $\ell$ 与未归一化加权和 $o$. 新块分数为向量 $x$, 新块最大值为 $m_x=\max(x)$, 新块指数和为 $\ell_x=\sum_j e^{x_j-m_x}$, 新块加权和为 $o_x=\sum_j e^{x_j-m_x}v_j$. 合并后

$$
m'=\max(m,m_x),
$$

$$
\ell'=e^{m-m'}\ell+e^{m_x-m'}\ell_x,
$$

$$
o'=e^{m-m'}o+e^{m_x-m'}o_x.
$$

遍历结束输出 $o'/\ell'$. 每次最大值变化时, 旧统计量都乘上相应指数因子, 所以数值上仍等价于对完整一行先减全局最大值再做 softmax. 这样就能把 Q tile 留在片上, 依次加载 K/V tiles, 在寄存器或共享内存中更新统计量, 无需把完整 $S$ 与 $P$ 写回 HBM.

FlashAttention 的论文把这种差异写成 IO 复杂度. 设片上 SRAM 可容纳 $M$ 个标量, 标准 attention 需要物化平方中间量, HBM 访问为 $\Theta(N^2)$; tiled attention 在论文分析的范围内把 HBM 访问降到与 $N^2d^2/M$ 同阶. $M$ 越大, 同一批 K/V 能服务越多 query, 重复读取越少. 这个结论也说明为何只报算法 FLOPs 会漏掉主要收益: FlashAttention 的数学边数没有减少, 墙钟时间仍可因 HBM 事务下降而改善.

分块尺寸受到三类状态共同限制. Q tile、K/V tile、输出累加器、行最大值与指数和都要留在有限的寄存器和共享内存中; tile 太大可能溢出片上容量或增加寄存器压力, 使每个 SM 同时驻留的 thread block 数下降; tile 太小则增加 K/V 重载次数和循环开销. head dimension 变大时, 单 token 的 Q/K/V 行更宽, 可容纳的 token tile 通常变小. 因此同一序列长度、同一稀疏率在 $d_h=64$、128、256 上不会得到固定加速比.

块稀疏可以与在线 softmax直接组合. 若一个 query block 仅访问 $z$ 个 key blocks, 内核只遍历对应 K/V tiles, 在这 $z$ 个块上维护同一组归一化统计量. 物理收益取决于索引是否已经按 key block 排序、多个相邻 query block 是否复用候选, 以及每个 tile 内有多少真实有效边. 若一个被选 tile 中只有极少 token 有效, Tensor Core 仍可能执行整个 tile, 此时 FLOPs 计数更接近非零 tile 数, 不接近非零元素数.

**Cache 层次会让“读了多少”出现三种答案。**

容量公式回答的是 HBM 中常驻多少有效载荷; profiler 的 DRAM bytes 回答有多少数据真正越过 HBM 接口; kernel 源码中的 load 数则包含命中 L2 的读取. 三者不能互换. 同一 KV 页被连续多个 query 或多个请求复用时, 第一次访问可能来自 HBM, 后续访问命中 L2; 从程序语义看读了多次, 从 DRAM 计数看只搬了一部分. 反过来, 地址不连续、工作集超过缓存或多个并发 kernel 相互驱逐时, 同一页可能反复穿过 HBM.

设某层的 KV 有效载荷为 $C$ bytes, 一个 decode batch 有 $B_d$ 个 query. 若每个 query 属于不同请求, 它们读取各自的 KV, 语义流量约为 $B_dC$. 若多个 query 共享相同前缀物理页, 理论上共享部分只需从 HBM 搬一次, 但是否复用取决于调度顺序、L2 容量和页布局. prefix cache 减少的是重复存储与重复 Prefill; Decode 阶段的 HBM 收益还需要共享页在时间上靠近并留在缓存中.

写流量也不能忽略. 每个 Decode 步要把新 token 的 K/V 追加到 cache, 写入量约为 $2LH_{kv}d_hb$ bytes, 与历史长度无关. 对长上下文, 读取历史 KV 远大于追加写入; 对极短上下文或强稀疏读取, 写入、页表更新和量化 scale 写入可能成为可见比例. KV 量化若按 block 保存 scale 与 zero point, 每个数据块还会增加元数据读取. 量化把有效载荷从 BF16 的 2 bytes 降到 1 byte 或更低, 并不保证总流量严格按位宽比例下降.

对 Decode 而言, 一个简化的算术强度可以直接从每个历史 token 推出. MHA 中, 每个 query head 对一个历史 key 做 $2d_h$ FLOPs, 对对应 value 再做 $2d_h$ FLOPs; 一个 KV head 被 $H_q/H_{kv}$ 个 query heads 共享. 每个历史 token 的总工作仍约 $4H_qd_h=4d$ FLOPs, 读取 K/V 约 $2H_{kv}d_hb$ bytes. 因而

$$
I_{decode}\approx\frac{4H_qd_h}{2H_{kv}d_hb}
=\frac{2H_q}{H_{kv}b}.
$$

BF16 MHA 取 $H_q=H_{kv}$ 时, $I_{decode}\approx1$ FLOP/byte; $H_q/H_{kv}=4$ 的 GQA 约为 4 FLOPs/byte; MQA 取 32 个 query heads 时约为 32 FLOPs/byte. 共享 KV 提高了算术强度, 因为同一份 K/V 支持更多 query-head 计算. 这也带来一个不那么直观的结果: GQA/MQA 把 KV 流量压低后, Decode 的瓶颈可能转向权重读取或计算, 此时继续稀疏 token 轴的边际收益会下降.

上式还省略了权重. 单请求 batch=1 时, 每步都要经过所有层的投影和前馈网络, 数十亿参数的权重读取通常远大于几个 GFLOPs 的 attention 计算. 增大 batch 可让同一份权重服务多个 token, 权重字节被摊薄; 每个请求的 KV 仍相互独立, KV 字节近似随 batch 线性增加. 因此稀疏 KV 在高吞吐 batch 下可能占更大价值, 而低延迟 batch=1 下端到端时间仍受权重流量约束. **瓶颈会随 batch、上下文长度和 KV 表示共同移动, “Decode 是带宽受限”还需要说明是哪一类字节占据带宽.**

### 2.1. 三个阶段要分别结账

**训练：前向少算还不够。**

训练包含前向、反向、参数梯度、优化器状态，以及为了反向传播保存或重算的激活。稀疏 attention 若要兑现训练收益，至少需要前向和反向都能利用稀疏结构。只有推理 kernel，或者只优化前向，无法证明训练成本下降。

训练中还要区分“注意力分数不落 HBM”和“注意力边被删除”。FlashAttention 属于前者：它保持精确注意力，通过 IO-aware tiling 把激活显存从朴素实现的平方级压力降下来，同时仍计算合法的稠密边。块稀疏 attention 属于后者：只有非零块参加 QK/PV。两者可以组合，组合后的内核既不物化完整分数矩阵，也不执行被裁掉的块。

反向传播还会读取 Q/K/V、输出、softmax 统计量或重算它们。动态路由若依赖 query 内容，反向时可能要重算 selector，或者保存路由结果。训练成本因此至少包括：主 attention 前后向、selector 前后向、索引与排序、临时工作区、跨卡通信。只展示前向 microbenchmark，无法支持“训练加速”的结论。

比较训练吞吐时，固定“每步序列条数”并不公平。不同长度、padding 与 packing 会改变有效 token 数。更可靠的指标是有效 token/s、MFU、峰值显存，以及 attention 前向和反向的分项耗时。若稀疏方案改变了训练目标或可见上下文，还要在相同训练 token、优化器和质量约束下比较。

**Prefill：边数与 tile 数共同决定上限。**

Prefill 处理完整 prompt，输出首个 token 所需的状态，并建立 KV Cache。全注意力的逻辑边数是因果三角形：

$$
E_{dense}=\frac{N(N+1)}{2}.
$$

滑动窗口宽度为 $W$ 时，忽略开头不足窗口的部分，边数约为 $NW$。更精确地，$N>W$ 时

$$
E_{window}=\frac{W(W+1)}{2}+(N-W)W.
$$

取 $N=8192$、$W=1024$，全因果边为 33,558,528；窗口边为

$$
\frac{1024\times1025}{2}+7168\times1024
=7{,}864{,}832,
$$

约占 23.44%。这是逻辑边比例。若内核以 $128\times128$ tile 执行，边界处少量有效元素也可能带来整块工作；规则窗口通常能形成连续 tile，随机 token top-k 则可能把少量命中散落到很多块。此时同样的逻辑稀疏率，会产生不同的物理 tile 数和 HBM 事务数。

动态稀疏还要先找候选。若 selector 为每个 query 扫描所有高维 keys，它自身仍是 $O(N^2d)$，只是把昂贵 attention 换成另一遍全量扫描。有效的路由通常依靠低维 index、分块摘要、哈希、层间复用或离线结构，让候选阶段明显便宜于被省掉的主计算。

**Decode：要在读取 KV 之前完成选择。**

Decode 每一步追加一个 token。新 query 对 $S$ 个历史 token 的边数是 $S$，因此完整生成 $T$ 个 token 时，attention 主项还会随着历史增长累计。要让稀疏率反映到 TPOT 上, 索引必须先给出少量地址, kernel 再读取对应 KV。若实现先把全部 KV 从 HBM 读到片上，随后将大部分分数 mask 掉，乘加虽然少了，主要流量已经发生。

设每步只选择 $k$ 个历史 token，并且 indexer 的状态常驻片上或尺寸足够小，则 KV 读取可从近似 $2LSH_{kv}d_hb$ 降到 $2LkH_{kv}d_hb$，再加 indexer 流量。若 $S=32768$、$k=2048$，token 轴只有十六分之一；可是随机的 2048 个 token 可能落在许多 cache pages 中。物理读取更接近“命中的页数乘每页字节”，不一定等于 2048 个紧密排列 token 的字节数。

Decode 还受 batch 影响。扩大 batch 可以摊薄模型权重读取并增加并行度，但每个请求拥有独立 KV，容量和 KV 流量随 batch 增加。于是 batch=1 的最低延迟、较大 batch 的总吞吐和并发服务的尾延迟是三种问题。评测至少要同时给出上下文长度、batch、并发策略、TPOT 分位数和吞吐。

Decode 的累计工作还可以从单步式继续求和. 假设 prompt 长度为 $S_0$, 随后生成 $T$ 个 token, 第 $t$ 步可见历史为 $S_0+t-1$. 全注意力在一层中的 QK/PV 总 FLOPs 约为

$$
F_{gen}=4d\sum_{t=1}^{T}(S_0+t-1)
=4d\left(TS_0+\frac{T(T-1)}{2}\right).
$$

第一项来自每个输出 token 重读 prompt 历史, 第二项来自输出 token 彼此之间逐步增长的历史. 当 $T\ll S_0$ 时, 成本近似 $4dTS_0$; 当输出很长时, $T^2$ 项也会明显. 固定预算 $k$ 的 token 稀疏把每步主项限制为约 $4dk$, 总量近似 $4dTk$, 但前提仍是索引查询不扫描完整高维 KV.

缓存容量则在生成过程中从 $S_0$ 增到 $S_0+T$. 若调度器按请求的最大可能输出提前连续预留, 未使用空间随请求上限增长; 分页分配只在新 token 到来时增加页面, 将浪费限制在尾页. PagedAttention 论文关注的正是这种动态增长与共享: 页表把连续的逻辑 token 序列映射到不连续的物理块, 让空闲块能被其他请求使用. attention kernel 随后通过块表找到 KV. 页表查询与非连续物理地址带来额外间接寻址, 换回的是较低的预留浪费和更灵活的共享.

continuous batching 会进一步改变每一步的形状. 每轮结束后, 已完成请求离开, 新请求进入; batch 中各序列的历史长度不同. 若内核把每个请求补齐到 batch 内最长历史, 读量会被最长请求放大. paged/varlen attention 按各自长度访问 KV, 总边数接近 $\sum_i S_i$, 但线程块数量与耗时更受长尾请求影响. 一个超长请求可能占据大量 KV 页并延长每轮迭代, 使短请求的 TPOT 一同上升.

这时平均 TPOT 会隐藏问题. 设一轮 decode 的耗时为 $\tau(B,\{S_i\})$, 该轮为 $B$ 个请求各产生一个 token, 吞吐是 $B/\tau$. 增大 $B$ 往往提高吞吐, 也会增加单轮时间. 在线服务还要满足每个请求的间隔约束, 因此可承载 batch 由 TPOT 或尾延迟目标约束, 往往小于显存所能容纳的请求数. 稀疏 KV 减少每轮字节后, 调度器可以选择降低 $\tau$, 也可以塞入更多请求提高 $B$; 两种策略得到的加速数字含义不同.

**Chunked Prefill 改变了阶段边界。**

长 prompt 若一次性 Prefill, 会形成很大的计算型任务, 同时到达的 Decode 请求可能等待很久. chunked prefill 把 prompt 切成若干 token 块, 在调度轮次之间与 Decode 交错. 从单请求数学结果看, 每个新 chunk 的 query 仍要访问前面所有 prompt KV; 从系统视角看, 大任务被拆成多个较短任务, 可控制每轮时间并改善 Decode 请求的等待.

设 prompt 长度为 $N$, chunk 大小为 $C$, 第 $j$ 个 chunk 包含位置 $jC$ 到 $(j+1)C-1$. 它与此前 $jC$ 个 keys 的矩形 attention 约有 $C\cdot jC$ 条边, chunk 内因果三角约有 $C(C+1)/2$ 条边. 对所有 chunk 求和仍得到完整因果三角的 $N(N+1)/2$ 条边. **切块本身没有减少逻辑 attention 工作, 它改变了任务粒度、峰值工作区和调度等待.**

若 attention 使用局部窗口 $W$, 第 $j$ 个 chunk 只需访问其前方至多 $W$ 个位置, 计算随 chunk 数线性增长. 若采用动态索引, indexer 可以在每个 chunk 到来时为一组 query 共同生成候选, 相比逐 token Decode 有更多并行度; 可是候选还要满足 chunk 内不同 query 的因果边界. 直接为整个 chunk 取候选并集会增加读取, 为每个 query 各取 top-k 又会产生不规则 mask. chunk 大小由此成为路由质量、候选复用和 kernel 利用率之间的控制量.

TTFT 的定义也要随调度说明. 一个请求的 TTFT 包含排队、若干 Prefill chunks、采样首 token 与网络返回. 若系统为了保护正在 Decode 的请求而限制每轮 Prefill token 数, 长 prompt 的 TTFT 会增加, 即使单个 chunk kernel 很快. 相反, 独占执行完整 Prefill 可以降低该请求 TTFT, 却抬高其他请求的 token 间延迟. 单 kernel 成本模型必须放进调度时间线, 才能解释用户最终看到的数字.

## 3. 从逻辑稀疏走到物理加速

### 3.2. 元素、块、页是三种粒度

逻辑 mask 往往按元素定义，Tensor Core 和高效矩阵乘法按 tile 工作，KV 分配器又按 page 管理。三个粒度不一致时，中间会出现放大。

假设一个 query 选中 128 个 token。若它们连续分布，且 KV page 每页 16 token，只需访问 8 页；若均匀散落在 2048 个历史位置，最坏可能触及 128 页。逻辑 token 数相同，页读取量可相差 16 倍。类似地，128 个非零元素若集中在一个 $16\times16$ tile 与分散在 128 个 tile 中，矩阵核的实际工作量完全不同。

因此，论文中的稀疏率必须带粒度：token sparsity、block sparsity、page sparsity 还是实际执行 tile 比例。工程记录中最好同时给出

$$
r_{token}=\frac{\text{选中 token 数}}{\text{可见 token 数}},\qquad
r_{tile}=\frac{\text{执行 tile 数}}{\text{稠密 tile 数}},
$$

以及实际读取字节。只看 $r_{token}$ 很容易高估加速。

**selector 也要吃预算。**

动态方法的端到端时间可以粗写成

$$
T_{sparse}=T_{index}+T_{topk}+T_{gather}+T_{attn}+T_{scatter}+T_{other}.
$$

稠密基线则是

$$
T_{dense}=T_{attn,dense}+T_{other}.
$$

只有

$$
T_{index}+T_{topk}+T_{gather}+T_{attn,sparse}+T_{scatter}
<T_{attn,dense}
$$

时，attention 路径才产生净收益。若稀疏 attention 从 4 ms 降到 1 ms，却新增 1.2 ms selector、0.8 ms 排序和 0.7 ms 随机 gather，最终只省 0.3 ms。这个例子中的数字是演算假设，目的在于展示预算关系，不是某篇论文的实测结果。

top-k 的代价也随候选规模和实现变化。全排序通常没有必要；分块筛选、局部 top-k 后归并或固定预算选择更常见。索引跨层共享可以摊薄成本，却可能损失各层需要的不同路由。算法质量与系统成本从这里开始纠缠，不能只优化其中一边。

把 selector 写成低维点积可以更精确地看成本. 设 query 摘要 $q'_i\in\mathbb{R}^{d_s}$, key 摘要 $k'_j\in\mathbb{R}^{d_s}$, 候选分数为

$$
s_{ij}=\langle q'_i,k'_j\rangle.
$$

若 Prefill 对全部 $N^2$ 对计算分数, selector 仍需约 $2N^2d_s$ FLOPs. 主 QK 与 PV 约为 $4N^2d$ FLOPs, 两者比值约 $d_s/(2d)$. 取 $d=4096$、$d_s=64$, selector 点积只有主 attention 的约 $1/128$. 但这只是算术量: selector 还要写分数或当场做 top-k, 并读取摘要. 主 attention 可以使用高效 Tensor Core tile, 64 维小点积与选择操作未必达到相同吞吐.

Decode 时, selector 对一个 query 扫描 $S$ 个摘要, 点积约 $2Sd_s$ FLOPs, 摘要读取约 $Sd_sb_s$ bytes. 若摘要使用 BF16, 每个历史 token 读取 $2d_s$ bytes. 被选择的 GQA KV 每个 token 读取 $2H_{kv}d_hb$ bytes. 对 $d_s=64$、$H_{kv}=8$、$d_h=128$、$b=b_s=2$, 摘要为 128 bytes, 完整 KV 为 4096 bytes. 扫描全部摘要相当于完整 KV 流量的 $1/32$. 若只选 $k=S/16$ 个 token, 选中 KV 是完整 KV 的 $1/16$, 两者合计约为原 KV 流量的 $3/32$, 纸面流量约缩小 10.7 倍. 再加 top-k、页放大和其他模块后, 端到端比例会更低.

top-k 的输出不仅是 $k$ 个位置. 内核通常还需要按 block 或 page 重排索引, 去除重复, 与局部窗口及固定全局 token 合并, 随后生成每个 query block 的偏移表. 若多个 query 的候选不同, 还要有行指针标出每行索引范围. 用 CSR 形式表示时, 列索引约有 $Nk$ 个整数, 行指针有 $N+1$ 个整数; 用固定 $k$ 的稠密索引矩阵可省行指针, 但无法表达变长预算而不填充.

选择算法也有不同的下界. 从 $S$ 个分数中精确找 top-k, 至少要检查每个分数, 所以比较或扫描工作为 $\Omega(S)$. 全排序的 $O(S\log S)$ 没有必要; 维护大小为 $k$ 的堆约为 $O(S\log k)$; GPU 上更常见的是分块局部选择后归并, 用额外候选换取并行. 若只需超过阈值的元素, 可用一次扫描, 但输出数量随输入变化, 会引入内存分配和负载不均. 固定 $k$ 让 shape 稳定, 阈值选择则更贴近“分数够高才保留”的语义.

近似检索结构可以避免逐步扫描全部摘要, 代价是维护更复杂的状态. 哈希把 keys 分桶, query 只访问碰撞桶; 聚类先与少量中心比较, 再进入若干簇; 树结构逐级排除区域. 自回归 KV 每步新增一个 key, 索引必须支持在线插入. 若索引重建代价高, 长生成中会积累陈旧分区; 若每步更新, 插入与同步进入 TPOT. 多层各建索引会放大容量, 共享索引又要求不同层对相关位置的判断足够一致.

索引召回率还要与 attention 质量对应. 设全注意力在 query $i$ 上的概率为 $p_{ij}$, 候选集合为 $C_i$. 被候选覆盖的概率质量为

$$
R_i=\sum_{j\in C_i}p_{ij}.
$$

$R_i$ 比“命中全注意力 top-k 中多少位置”更直接, 因为漏掉一个概率为 0.2 的位置与漏掉许多概率为 $10^{-5}$ 的位置影响不同. 但计算 $R_i$ 需要先得到全注意力分布, 适合离线分析, 无法作为部署时免费指标. 训练 selector 时可以用教师 attention、对比损失或下游任务损失提供信号, 三者优化的对象并不相同.

候选集合上的 softmax 会重新归一化:

$$
\tilde p_{ij}=\frac{e^{s_{ij}}}{\sum_{u\in C_i}e^{s_{iu}}},\qquad j\in C_i.
$$

即便 $R_i$ 很高, 丢失的概率质量也会被重新分给保留项. 若 $R_i=0.9$, 保留项的概率在分数不变时整体放大约 $1/0.9$. 输出误差还取决于被删 values 与保留 values 的方向, 不能由召回率单独决定. 两个候选集合拥有相同 $R_i$, 其中一个漏掉与输出方向相反的 value, 另一个漏掉与输出方向一致的 value, 最终向量误差会不同.

**从 token 稀疏率推到块稀疏率。**

设 tile 含 $T_q\times T_k$ 个潜在边. 对每个 query 随机独立保留比例 $p$ 的 keys, 一个 tile 至少包含一条保留边的概率为

$$
P_{nonempty}=1-(1-p)^{T_qT_k}.
$$

若内核只要 tile 非空就执行整块, 物理 tile 比例接近 $P_{nonempty}$. 取 $p=1\%$、$T_q=T_k=16$, 得到 $1-0.99^{256}\approx92.4\%$. 逻辑上只剩 1% 的边, 随机分散后却有超过九成 tiles 非空. 这个简单概率说明, **元素级随机稀疏若没有结构化聚集, 几乎无法按相同比例减少矩阵 tile.**

若每个 query 恰好选 $k$ 个位置, 选择事件并非完全独立, 上式仍能作为直觉近似. 真正决定块密度的是相邻 queries 的候选重叠. 设一个 query block 中所有 queries 共享同一组 $k$ 个 keys, 被触及的 key blocks 约为 $\lceil k/T_k\rceil$, 稀疏性高度集中; 若每个 query 的 $k$ 个 keys 互不重叠, 并集最多达到 $T_qk$, 被触及块数大幅上升. 因而让相邻 queries 共享候选, 不只是减少 selector 调用, 还直接提高块利用率.

块大小存在相反的两种影响. 增大 $T_k$ 能用更大的矩阵 tile, 索引更短, 连续读取更多; 一个块只要入选, 其中低价值 token 也会被计算和读取, 形成块内浪费. 缩小 $T_k$ 能逼近 token 级选择, 但索引项、kernel 数量和地址跳转增加. 设每个被选块中有效 token 比例为 $u_b$, 块级执行相对理想 token 执行的放大约为 $1/u_b$. 当 $u_b=25\%$ 时, 纸面 token FLOPs 会被放大四倍.

页粒度还会再放大一次. 若 KV page 为 $P$ token, attention block 为 $T_k$ token, 两者边界不对齐, 一个 attention block 可能跨两个页. 候选块连续也不保证页连续, 因为请求的逻辑页可映射到不连续物理块. gather kernel 可以把候选 KV 搬到紧凑工作区, 随后的 attention 变得规则; 搬运本身会读取原 KV 并写出副本. 直接 paged attention 省去副本, 但地址计算和访存合并更难. 选择哪条路径取决于同一候选 KV 会被多少 queries 复用: 复用多时一次 gather 可被摊薄, 复用少时复制可能得不偿失.

局部窗口天然拥有高块利用率. 对远程动态候选, 常见组合是保留连续局部块, 再加入少量远程块. 局部部分保证邻近依赖与连续访问, 远程部分承担检索. 若局部窗口为 $W$, 远程预算为 $k_r$, 每个 query 的逻辑预算为 $W+k_r$; 物理成本则取决于远程候选在多少块和页上. 报告“总共看了 $W+k_r$ 个 token”仍不够, 还要分别给局部与远程的块数.

**稀疏 mask 改变了什么数学对象。**

全注意力对 query $i$ 的输出为

$$
o_i=\sum_{j\le i}p_{ij}v_j,
\qquad
p_{ij}=\frac{e^{s_{ij}}}{\sum_{u\le i}e^{s_{iu}}}.
$$

给定候选集合 $C_i$, 稀疏输出是

$$
\tilde o_i=\sum_{j\in C_i}\tilde p_{ij}v_j.
$$

令被保留的全注意力概率质量为 $R_i$. 因为 $\tilde p_{ij}=p_{ij}/R_i$ 对 $j\in C_i$ 成立, 可以把误差写成

$$
\tilde o_i-o_i
=\left(\frac{1}{R_i}-1\right)\sum_{j\in C_i}p_{ij}v_j
-\sum_{j\notin C_i}p_{ij}v_j.
$$

第一项来自保留概率的重新归一化, 第二项来自删除的 value. 若所有 $\|v_j\|\le V_{max}$, 三角不等式给出一个较松的上界

$$
\|\tilde o_i-o_i\|\le2(1-R_i)V_{max}.
$$

它说明高概率质量召回可以约束单层输出扰动, 但上界没有利用 values 之间的抵消, 也没有覆盖多层误差传播. 更重要的是, selector 通常在得到完整 $p_{ij}$ 之前工作, 它只能通过低维摘要或训练得到的代理分数预测哪些边会拥有大概率质量.

固定窗口的误差来源与动态 top-k 不同. 窗口直接规定 $C_i=\{j:i-W<j\le i\}$, 它对所有输入使用同一结构, 无法根据内容找回很远的位置. 动态 top-k 可以捕获远程依赖, 但候选误差随输入变化, 还要承担索引成本. 全局 token 则人为设置一小批始终可见的位置, 让信息通过多层传播. 三类机制分别用结构先验、内容路由和固定汇聚点控制稀疏图, 不能只按保留边数排序.

多层传播还涉及图的直径. 单层局部窗口宽度为 $W$, 堆叠 $l$ 层后, 在没有跳连边的理想情况下, 一个位置可通过逐层传播接触约 $lW$ 范围, 但信息必须经历多次非线性变换. 稀疏图若每层加入少量远程边, 可能缩短任意两位置之间的路径. 这解释了为何相同单层预算的两种 mask 会有不同能力: 边数只计算局部工作量, 图连通性决定信息需要多少层才能到达.

因果约束必须在候选生成阶段或 attention mask 阶段执行. 若 selector 为 query 选择了未来位置, 后续再用因果 mask 删除, selector 的部分预算被浪费; 若训练时允许未来信息进入 selector 表示, 即使主 attention mask 严格因果, 路由决策本身也可能泄漏未来. 自回归模型需要保证 query 摘要、索引状态和候选过滤都只依赖当前位置及此前 token.

**规则结构为何更容易兑现。**

滑动窗口、固定全局 token、规则块对角等模式可以提前确定地址，访问连续，内核分支少。内容相关的 token top-k 更灵活，却带来索引生成、排序、去重、非连续 gather 和负载不均。两者之间还有不少折中：以块为候选单位、先粗选块再细选 token、让相邻 query 共享候选、把路由结果跨若干层复用。

「更稀疏」不是单调更快。预算过小时，kernel 启动、同步与索引成为固定成本；预算过大时，稀疏路径又接近稠密。交叉点取决于序列长度、块尺寸、head dimension、batch、GPU 架构和内核版本，必须实测。

**因果三角、padding 与负载不均。**

因果注意力的第一个 query 只能看 1 个位置，末尾 query 才能看完整历史。若把所有 query block 分给相同数量的线程块，前部工作少、后部工作多，执行时间取决于最慢的一批。FlashAttention 会按因果边界跳过完整无效块，但横跨边界的 tile 仍需处理局部 mask。块越大，矩阵核越容易高效；块越小，边界浪费越少，却会增加调度和元数据成本。

变长 batch 又多一层 padding。四个请求长度分别为 8192、4096、2048、1024，若朴素补齐到 8192，token 槽位共有 $4\times8192=32768$，实际 token 只有 15360，有效比例约 46.9%。对平方 attention，浪费还会更严重。packing、varlen kernel 与按长度分桶可以减少它，但它们改变了基线。比较稀疏方法时若一边使用变长 kernel、另一边使用补齐基线，结果掺入的就不只稀疏收益。

动态 top-k 也可能产生负载不均。固定 $k$ 能限制每个 query 的候选数，阈值法则可能让某些 query 命中很多、另一些命中很少。GPU 上一个 warp 或 thread block 内的工作通常要等待最慢成员，平均边数不能完整描述耗时。应补充候选数分布、最大值、空块比例与各 SM 的负载情况。

**精确 softmax 如何跨稀疏块合并。**

对某个 query，softmax 需要在所有被选中的 key 上归一化。将 key 分块后，不能分别做 softmax 再简单相加。在线 softmax 为每个分块维护局部最大值 $m_j$、指数和 $\ell_j$ 与加权输出 $o_j$，合并两个块时先把它们缩放到共同最大值：

$$
m=\max(m_1,m_2),
$$

$$
\ell=e^{m_1-m}\ell_1+e^{m_2-m}\ell_2,
$$

$$
o=e^{m_1-m}o_1+e^{m_2-m}o_2.
$$

最终输出为 $o/\ell$。FlashAttention 利用这类可合并统计量遍历 K/V tiles。块稀疏内核只遍历被保留的 tiles，仍可在选中集合上得到精确 softmax。这里的“精确”指相对于给定稀疏 mask 的数学结果精确；mask 本身删掉了边，与原始全注意力的输出当然可能不同。

随机 token 索引会让同一 tile 里出现许多空位。若先 gather 成紧凑 K/V 再运行稠密小 attention，需要额外搬运；若直接在原布局上执行，访存又可能不合并。块选择的意义正在于用一点粒度损失换取连续搬运和矩阵核效率。

### 3.1. 并行之后，每卡成本怎么算

**Tensor Parallel 切分的收益与通信。**

张量并行大小为 $p$ 时，常见实现会把 attention heads 或投影维度分到多张卡。若 KV heads 可以均匀切分，每卡逻辑 KV 容量近似为 $C_{KV}/p$，每卡 attention FLOPs 也近似按 $p$ 缩小。层末通常还需 collective communication，把局部结果汇合到后续残差流。

短 Prefill 或 Decode 的消息较小，集合通信的固定延迟会变得显眼。扩大 TP 可以降低每卡权重和 KV，却可能让小矩阵更碎，并增加同步。于是“多卡后每卡字节除以卡数”只给容量下界，不能直接推出延迟也除以卡数。

对稀疏路由还要问 indexer 放在哪里。每卡独立计算同一份索引会重复工作；集中计算再广播索引会增加通信和等待；若不同 head 分片产生不同候选，则需要在局部选择与全局选择之间确定语义。索引只有几 KB 时，固定通信延迟可能比带宽项更重要。

**Sequence Parallel 与 Context Parallel。**

长序列训练常把 token 轴切到多卡。每卡只持有一段 Q/K/V，但全注意力要求每段 query 访问其他卡的 keys 和 values，于是需要 all-gather、ring attention 或等价的数据交换。内存降低了，跨卡流量进入关键路径。局部窗口很适合 token 分片，因为多数访问留在相邻分区；全局 token 与动态远程 top-k 则会产生跨分区请求。

假设序列按连续区间分到 4 卡，窗口宽度远小于每卡区间长度。除边界 query 外，大部分 key 都在本地，通信近似由边界带宽决定。若每个 query 在全序列随机选相同比例 token，每张卡都可能访问另外三卡，逻辑边数虽相同，网络模式已从邻居交换变成近似 all-to-all。稀疏图的拓扑会直接映射成通信拓扑。

训练报告若只写 GPU kernel 时间，可能漏掉通信；只写端到端时间，又难以知道退化来自网络还是本地内核。至少应分别记录计算、HBM 搬运和集合通信时间，并说明是否发生重叠。

把通信量写开后, 稀疏图与设备拓扑的关系更直接. 设 $p$ 张卡沿序列轴均匀切分, 每卡持有 $N/p$ 个 query 与 $N/p$ 个 KV. 全注意力要求每张卡最终接触全部 KV. 简化的 ring 方案分 $p$ 轮传递 KV 分片, 每卡累计接收约

$$
V_{ring}\approx\frac{p-1}{p}\cdot 2BNH_{kv}d_hb
$$

bytes, 省下的是单卡常驻容量, 全局 KV 访问没有消失. 每轮可以让当前 KV 分片与本地 Q 计算, 同时异步传下一分片; 只有通信时间不超过相应计算时间时, 传输才可能被大体覆盖. Decode 的 query 数少, 每轮计算不足, 同样的 ring 更难隐藏通信.

局部窗口将通信限制到分区边界. 每卡负责连续 $N/p$ 个 token, 左侧窗口宽度为 $W$. 当 $W<N/p$ 时, 除第一张卡外每卡只需从左邻居取得至多 $W$ 个 KV token, 通信总量近似与 $pW$ 而非 $pN$ 成正比. 若窗口跨越多个分区, 需要更多邻居或多跳转发. 规则窗口的通信伙伴可提前确定, 动态远程 top-k 则可能访问任意卡.

动态候选在分布式环境中有两种基本流程. 第一种先在每卡对本地 keys 计算局部 top-k, 再汇总候选分数做全局 top-k; 若每卡上送 $k$ 个候选, 汇总量与 $pk$ 成正比. 第二种使用共享的全局索引先确定目标卡, 只向命中设备请求 KV. 前者计算重复且候选数较多, 语义容易保持精确; 后者减少无效候选, 索引本身必须跨卡一致并支持在线插入.

局部 top-k 后归并为何能得到精确全局 top-k, 可以直接证明. 若某元素在所属分片中连本地前 $k$ 都进不去, 则同一分片已有至少 $k$ 个元素不小于它, 它不可能进入全局前 $k$. 因而每卡只需上送本地前 $k$ 的分数与位置, 在至多 $pk$ 个候选中再选一次. 这条性质减少了索引通信, 但主 KV 仍要从候选所在卡传到 query 所在卡, 或把 query 发往 KV 所在卡再归并局部输出.

后者可以利用在线 softmax 的可归并统计量. 每张候选卡对本地选中 keys 计算局部最大值 $m_r$、指数和 $\ell_r$ 和加权和 $o_r$, 然后跨卡归并三者. 传输量从 $k$ 个完整 K/V 降为每个 query 的标量统计与 $d_h$ 维输出, 但每张卡仍需拿到 query 并执行局部 attention. 若候选高度集中在少数卡, 这些卡会成为热点; 若均匀分散, 归并参与者增多, 固定延迟上升.

Tensor Parallel 与 Context Parallel 叠加时, 一个 token 的 head 维和序列维可能同时被切分. head 轴切分让各卡只处理部分 query heads, 序列轴切分让 keys 分布在不同卡. GQA 的 $H_{kv}$ 很小时, KV heads 数可能小于 TP 大小, 无法无重复地按 head 均匀切分;复制 KV 可维持并行, 却削弱容量收益. MLA 的 latent 也可能需要复制或选择另一种切分. 因此“更小的 KV 表示”与“更好的并行扩展”不总在同一方向.

通信模型常写为

$$
T_{comm}=\alpha n_{msg}+\beta V,
$$

$\alpha$ 表示每条消息的固定启动延迟, $n_{msg}$ 为消息数, $\beta$ 是每 byte 传输时间, $V$ 是总字节. 动态 token 请求即使总字节很小, 若拆成许多细碎消息, $\alpha n_{msg}$ 仍可主导. 按设备和页面合并请求能降低消息数, 代价是等待候选聚齐以及可能多取一些 KV. 评估分布式稀疏 attention 时, 候选 bytes、消息数量和热点设备负载缺一不可.

**Paged KV 的容量公式。**

设页大小为 $P$ token，每个请求当前长度为 $S_i$。逻辑页数为

$$
n_i=\left\lceil\frac{S_i}{P}\right\rceil,
$$

该请求分配的 token 槽位为 $n_iP$，尾页浪费小于 $P$ token。全 batch 的页内有效率为

$$
u=\frac{\sum_i S_i}{P\sum_i\lceil S_i/P\rceil}.
$$

例如 $P=16$，三个请求长度为 17、31、32，实际 token 为 80，分配槽位为 $32+32+32=96$，页内有效率为 83.3%。分页避免为每个请求一次性预留最大长度，也能回收离开的请求，但尾页仍有内部碎片。较小的页降低尾部浪费，同时扩大页表并增加调度项；较大的页更利于连续访问，却可能带入无用 KV。

前缀共享时，多请求页表可以指向相同物理 KV 页。此时“把各请求长度相加再乘每 token 字节”会重复计算共享前缀。容量应按唯一物理页计数，带宽则取决于调度是否让共享页在缓存层次中得到复用。

分页能把外部碎片与内部碎片分开. 外部碎片指空闲空间被切成许多不连续小段, 总量够却找不到一个足够大的连续区间;固定大小物理页让任何空闲页都可分给新请求, 基本消除了“必须连续”带来的外部碎片. 内部碎片留在每个请求的尾页. 对页大小 $P$, 单请求浪费满足 $0\le w_i<P$, 若长度在页内近似均匀分布, 平均浪费约为 $(P-1)/2$ token.

设共有 $R$ 个活跃请求, 每 token、所有层的 KV 字节为 $q=2LH_{kv}d_hb$. 尾页浪费的期望容量约为

$$
E[C_{waste}]\approx R\frac{P-1}{2}q.
$$

页越大, 页表越短而尾部浪费越多;页越小, 浪费下降但页表项、地址转换和调度粒度增加. 对很长请求, 尾页只占总容量很小比例;对大量短请求, 每个请求都付一份尾页, 内部碎片会明显. 所以页大小不能只用最大上下文决定, 还要考虑线上长度分布.

fork 出多条解码分支时, 已有前缀页可只读共享, 每条分支仅为新 token 分配页. 若某个共享的未满尾页需要继续写, 系统要么提前让可共享前缀在页边界结束, 要么执行 copy-on-write. beam search、并行采样与树搜索都可能利用这种共享. 共享比例越高, 逻辑 KV 总和与唯一物理页容量差距越大;一旦各分支增长, 私有尾部仍会线性增加.

稀疏 attention 与分页组合后, 页面本身也可以成为路由单位. selector 输出页号, attention 读取整页 KV;地址紧凑, 页表天然可用, 但粒度由 $P$ 决定. selector 输出 token 号时, runtime 要把 token 映射到页、对页去重, 再决定整页读取还是页内 gather. 若许多选中 token 落在同页, page-level 路径很合算;若每页只命中一个 token, 页面放大会吞掉大部分理论节省.

## 4. 一套能跟算的成本表

下面用同一组假设把容量、Prefill 和 Decode 连起来：$L=32$、$d=4096$、$H_q=32$、$d_h=128$、BF16、单请求长度 $N=S=32768$。只计算 attention 相关项，不含权重、MLP、通信和框架开销。

### 4.2. 容量

- MHA，$H_{kv}=32$：KV 约 16 GiB。
- GQA，$H_{kv}=8$：KV 约 4 GiB。
- MLA 示例，$d_c=512,d_r=64$：KV 约 1.125 GiB。

若并发为 $B=8$，逻辑 KV 分别变为 128 GiB、32 GiB 和 9 GiB。容量乘 batch，单请求的 attention 连接图并不会因此改变。

**Prefill FLOPs。**

稠密 QK/PV 的非三角上界为

$$
4LN^2d
=4\times32\times32768^2\times4096
\approx562.95\ \text{TFLOPs}.
$$

若内核完整利用因果三角，可把主项近似看成一半。若窗口 $W=4096$，逻辑边比例约为

$$
\frac{W(W+1)/2+(N-W)W}{N(N+1)/2}\approx23.44\%.
$$

对应主 FLOPs 也约为稠密因果实现的 23.44%，前提是物理 tile 比例接近逻辑边比例。selector 和非 attention 模块仍要另加。

**Decode 流量下界。**

把三种 KV 容量视为每步完整读取量，用 H100 SXM 官方 3.35 TB/s 峰值带宽作理想除法：MHA 约 5.1 ms，GQA 约 1.3 ms，MLA 示例约 0.36 ms。它们只是 KV 流量下界。若实际有效带宽只有峰值的 60%，时间还要除以 0.6；若采用张量并行并让 KV 沿 head 或 latent 维切分，每卡流量会下降，但会增加跨卡通信。

若 token 稀疏把 GQA 的可见历史从 32768 降到 2048，并能做到近似连续物理读取，KV 下界进一步约为 $1.3/16\approx0.081$ ms。若必须先扫描完整 4 GiB KV 才能选出 2048 个位置，这个 16 倍就不存在。**先选地址还是先读数据，是 Decode 稀疏能否成立的分水岭。**

**从单 kernel 推到端到端。**

假设某次 Prefill 的端到端时间是 100 ms，其中 attention 55 ms、MLP 与投影 30 ms、通信和调度 15 ms。一种稀疏方法把 attention 主核从 55 ms 降到 18 ms，但路由与 gather 新增 9 ms，端到端时间为 $18+9+30+15=72$ ms，加速为 1.39 倍，而非 $55/18=3.06$ 倍。

若换到 Decode，原始单步 20 ms 中，权重读取与非 attention 模块占 12 ms，KV attention 占 6 ms，其他开销占 2 ms。即使理想地消除全部 KV attention，TPOT 下界仍是 14 ms，最大加速约 1.43 倍。增大 batch 后权重读取可被更多 token 摊薄，KV 占比上升，稀疏 KV 的价值也会变化。这些假设数值用于展示分项相加的方法；实际占比要由目标模型的 profiler 给出。

端到端评估还应区分排队时间。服务系统中的请求延迟为

$$
T_{request}=T_{queue}+T_{prefill}+\sum_{t=1}^{T}T_{decode,t}.
$$

稀疏 kernel 缩短执行阶段后，调度器可能塞入更大 batch，吞吐增加但排队策略也随之改变。离线吞吐、无排队单请求延迟和在线 SLO 下的可承载 QPS 应分别报告。

**做一次参数敏感性分析。**

固定一组配置只能得到一个点, 成本模型更有价值的用法是看斜率. 对 MHA/GQA 的 KV 容量 $C_{KV}=2LBSH_{kv}d_hb$, $L$、$B$、$S$、$H_{kv}$、$d_h$ 和 $b$ 中任意一项翻倍, 容量都翻倍. 对 Prefill 主项 $F\approx2LBN^2d$, $N$ 翻倍会让 FLOPs 变为四倍. 对固定窗口 $F\approx4LBNWd$, $N$ 或 $W$ 翻倍只带来约两倍. 这些幂次决定优化应优先作用在哪条轴: 上下文继续扩大时, 平方项比常数压缩更快地重新占据成本.

以 32 层、8 个 KV heads、每头 128 维、BF16 为例, 每 token 的全部层 KV 为

$$
q=2\times32\times8\times128\times2=131072\ \text{bytes}=128\ \text{KiB}.
$$

于是 1K token 约 128 MiB, 8K 约 1 GiB, 32K 约 4 GiB, 128K 约 16 GiB. 这组等比数列比只记一个 32K 结果更有用: 给定设备可用于 KV 的容量, 直接除以每请求 KV 就能得到并发上界. 若 80 GiB GPU 在权重和工作区后只剩 40 GiB, 32K 请求按有效载荷最多容纳约 10 个;分页、尾页和调度预留会让实际数更少.

把 KV dtype 从 BF16 改为 8 bit, $b$ 从 2 降为约 1, 有效载荷减半. 若每 $G$ 个数共享一个 BF16 scale, 每个数还要摊入 $2/G$ bytes. $G=64$ 时, 实际约为 1.03125 bytes/element, 压缩比约 $2/1.03125=1.94$, 小于理想 2 倍. 更低位宽还会引入打包、解包和对齐;若 kernel 先解量化到片上再计算, HBM 字节减少, 计算指令增加. 量化是否更快取决于原路径的带宽余量与解码效率.

窗口宽度 $W$ 的影响要区分 Prefill 和 Decode. 长序列 Prefill 的边数近似 $NW$, 所以 $W$ 翻倍时主计算与 K/V 访问近似翻倍;Decode 每步只读最近 $W$ 个 KV, 常驻容量若允许淘汰也近似与 $W$ 成正比. 可是混合全局层会留下 $L_gS$ 项, 当 $S$ 很大时少数全局层仍可能主导容量. 继续缩小 $W$ 最终只能压低局部层对应的项, 无法越过全局层形成的下限.

动态 top-k 中, 增加 $k$ 通常让主 attention FLOPs、选中 KV 字节和索引容量线性增加;top-k 选择的时间未必线性, 因为不同算法在 $k$ 较小时可用固定大小寄存器, $k$ 跨过阈值后需要多轮归并或更大工作区. $k$ 还会改变块利用率: 从一个块中多选几个 token 可能几乎免费, 新增一个分散位置若触发新页面则代价较大. 因此预算曲线应同时画 $k$、命中页数、执行 tiles 与质量, 单独画 token 数会漏掉台阶变化.

batch 对权重与 KV 的斜率不同. 假设模型权重每步读取 $W_m$ bytes, 每请求 KV 读取 $C$ bytes, batch 为 $B_d$. 粗略总流量为 $W_m+B_dC$, 每个输出 token 摊得

$$
q_{token}=\frac{W_m}{B_d}+C.
$$

增大 batch 只压低第一项, 第二项不变. 当 $W_m/B_d=C$ 时, 权重与 KV 对单 token 流量贡献相等;继续增大 batch 后, KV 占据主导. GQA、MLA 与 token 稀疏降低 $C$, 会把相交 batch 推向更大值. 这条式子也解释了为什么同一模型在 batch=1 和高吞吐服务中可能需要不同的优化优先级.

**下界、上界与可实现值。**

容量公式通常给有效载荷下界: 真实显存还要加权重、激活、页表、索引、工作区、分配器保留和通信 buffer. 带宽除法给理想时间下界: 假设能够持续达到峰值带宽, 没有固定延迟, 也没有其他流量争用. FLOPs 除以峰值算力也是理想下界. 两个下界取较大者构成 Roofline 时间:

$$
T\ge\max\left(\frac{F}{P_{peak}},\frac{D}{BW_{peak}}\right),
$$

其中 $F$ 为实际执行 FLOPs, $D$ 为越过目标内存层的字节. 可实现时间还要加无法重叠的选择、通信和调度. 若若干阶段能并行, 不能简单全相加;若有依赖, 也不能假设全部隐藏.

效率可以分别定义为计算效率 $\eta_c=P_{actual}/P_{peak}$ 与带宽效率 $\eta_b=BW_{actual}/BW_{peak}$. 实测时间可近似为

$$
T\approx\max\left(\frac{F}{\eta_cP_{peak}},\frac{D}{\eta_bBW_{peak}}\right)+T_{fixed}.
$$

$T_{fixed}$ 汇集 kernel launch、同步、地址准备等不随主要工作量同比增长的项. 短序列中 $T_{fixed}$ 占比大, 长序列中 FLOPs 或 bytes 项占比大. 用多个长度拟合这三类项, 比在一个长度上用峰值规格反推更可靠.

算法的理论上界也应由保留工作决定. 若 attention 占端到端时间比例为 $f$, 稀疏路径把 attention 加速 $s$ 倍且没有新增开销, 总加速为

$$
S=\frac{1}{(1-f)+f/s}.
$$

$f=0.4$、$s=4$ 时, 总加速只有 $1/(0.6+0.1)=1.43$. 若 selector 又占新时间的 10%, 结果更低. 这条式子适合在实现之前排除不现实目标: 当被优化模块占比很小, 再激进的稀疏率也无法让整个模型获得同倍数收益.

边数给的是算法工作上界或近似值, tile 数更接近设备执行量, HBM bytes 更接近带宽成本, wall time 则包含全部现实损耗. 四种量从左到右逐渐靠近用户体验, 也逐渐依赖具体实现. 完整报告应让它们能互相解释: 边数下降却 tile 不降, 问结构聚集;tile 下降却 bytes 不降, 问 gather 与页面;bytes 下降却时间不降, 问并行度、固定开销与其他模块.

### 4.1. 训练与推理的交叉点为何不同

训练的 query 数随序列长度一起增长，稀疏边会同时减少大量 QK/PV 工作；但训练还要反向传播，对内核完整性要求高。Prefill 同样拥有大量 query，更接近大矩阵计算，规则块稀疏容易产生算力收益。Decode 只有少量 query，首要价值经常来自减少 KV 容量和 HBM 读取，而不是减少那一点点点积。

因此，同一技术可能出现三种结果：训练显著加速，Prefill 有收益，Decode 几乎不变；或者训练难以实现，Prefill 一般，但 Decode 因为缓存淘汰而收益很大。滑动窗口允许永久丢弃窗口外 KV，直接压住 Decode 容量；仅对当前 query 做 mask、未来又可能访问那些 token 的动态方法，则仍需保存完整 KV。这里要区分“本步不看”和“以后永远不看”。

交叉点还能随长度移动。短序列下，索引和 kernel launch 是显眼的固定成本，稠密 kernel 往往更快；长度增加后，平方计算或线性 KV 读取逐渐盖过固定成本，稀疏路径才开始占优。报告一个长度上的加速倍数，无法推断其他长度。

**用两个方程估计交叉长度。**

把稠密 attention 时间简化为 $T_d=aN^2+c$，稀疏窗口方法简化为 $T_s=bNW+rN+c'$。$a$、$b$ 吸收设备与内核效率，$rN$ 表示路由或索引工作。令两者相等可以估计交叉长度。若固定窗口 $W$，长序列时平方项终会超过线性项；但在 $N$ 较小时，$c'$ 和较低的稀疏 kernel 利用率可能让稠密路径更快。

Decode 可写成 $T_d\approx qS/BW+c$，其中 $q$ 是每个历史 token 实际读取字节；稀疏路径为 $T_s\approx qk/BW+T_{index}(S)+c'$。若 $T_{index}(S)$ 也需要扫描与完整 KV 相当的字节，交叉点可能永远不会出现。若 indexer 只扫描紧凑的低维摘要，随着 $S$ 增加，节省会逐步覆盖固定成本。

这类模型不替代 benchmark，却能排除明显不可能的方案。测得的耗时若低于“实际字节除以峰值带宽”，说明字节统计或复用假设有误；若声称速度随稀疏率线性增长，而执行 tile 数没有同步下降，也应回查计数口径。

**质量约束也是成本变量。**

减少可见边可能改变困惑度、检索命中、长程推理与训练稳定性。为了追回质量而增加窗口、全局 token、检索候选或特殊层，都会把成本加回来。公平比较应先确定可接受的质量边界，再比较该边界下的速度与容量。

混合层是一种常见折中：部分层使用全注意力，其余层使用窗口或稀疏注意力。若 $L_g$ 层全局、$L-L_g$ 层窗口，KV 容量在允许淘汰窗口外状态时为

$$
C=2H_{kv}d_hb\left(L_gS+(L-L_g)\min(S,W)\right).
$$

取 $L=32$、$L_g=4$、$S=32768$、$W=4096$，token-layer 项从全局的 $32\times32768=1{,}048{,}576$ 降为 $4\times32768+28\times4096=245{,}760$，约占 23.44%。这个比例碰巧与前述窗口边例子接近，来源却不同：这里算缓存的 layer-token 数，前面算单层 Prefill 的注意力边，不能互相替代。

**“本步少读”与“永久少存”需要不同保证。**

动态 top-k 在第 $t$ 步选择集合 $C_t$, 只说明当前 query 不读取集合外的 KV. 到第 $t+1$ 步, 候选集合可能完全变化. 若系统提前删除 $C_t$ 之外的状态, 下一步就失去可选项. 因而一般动态稀疏能降低每步读取和计算, 常驻容量仍为完整历史. 要降低容量, 需要一条更强的不可逆条件: 某位置被淘汰后, 所有未来 query 都不会再需要它, 或模型接受由此产生的质量变化.

固定滑动窗口满足这种结构保证. 当位置 $j<t-W+1$ 时, 对所有未来 $t'\ge t$, 都有 $j<t'-W+1$, 所以 $j$ 永远离开窗口, 对应 KV 可以释放. 固定 sink/global token 例外地永久保留. 动态淘汰则要预测未来重要性;当前 attention 分数低不代表未来仍低, 特别是实体、代码定义与早期约束可能隔很久才被再次引用.

把缓存管理写成状态转移更清楚. 令 $A_t$ 为第 $t$ 步仍存活的位置集合, $C_t\subseteq A_t$ 为本步读取集合, $D_t\subseteq A_t$ 为步后删除集合. 下一步

$$
A_{t+1}=(A_t\setminus D_t)\cup\{t}.
$$

只做稀疏读取时 $D_t=\varnothing$, 容量继续线性增长;做窗口淘汰时 $D_t$ 包含刚刚越过窗口边界的位置;做基于重要性的淘汰时, $D_t$ 来自策略. 读取预算控制 $|C_t|$, 容量预算控制 $|A_t|$, 两者是独立约束. 有些方法让 $C_t=A_t$ 但主动压缩 $A_t$;另一些保留完整 $A_t$ 却令 $C_t$ 很小.

若被删 token 先被汇总成少量记忆状态, 容量可以受控, 信息不一定完全消失. 假设每 $m$ 个旧 KV 压成一个摘要, 历史状态从 $S$ 个变为约 $S/m$ 个摘要加最近窗口. 压缩过程会丢掉区分单个 token 的细节, attention 只能读取摘要表示. 这属于表示压缩, 与 GQA/MLA 沿 head 或 latent 维压缩又不同: 前者减少 token 轴状态数, 后者保留每个 token 但缩短每个状态.

四种操作可以用两个问题区分. 第一, 每个历史位置还在不在存储中? 第二, 本次 query 是否读取它? 完整 KV 加动态 top-k 的答案是“都在, 只读一部分”;窗口淘汰是“窗口外不在, 读取剩余”;KV 量化是“位置都在, 每个位置字节更少”;MLA 是“位置都在, 表示维度更窄”. 将这些机制同时使用时, 容量和流量应按操作次序计算, 不能把各自宣称的压缩倍数直接相乘而不考虑元数据与共享部分.

**质量边界怎样进入成本曲线。**

稀疏预算的有效比较应写成约束优化. 令质量指标为 $Q(k,W,L_g,\theta)$, 成本为 $C(k,W,L_g,\theta)$, 其中 $k$ 是动态候选数, $W$ 是窗口, $L_g$ 是全局层数, $\theta$ 表示 selector 与实现配置. 给定最低质量 $Q_0$, 实际问题是

$$
\min C(k,W,L_g,\theta)
\quad\text{s.t.}\quad
Q(k,W,L_g,\theta)\ge Q_0.
$$

只在固定 $k$ 上比较速度, 没有说明两种方法是否位于同一质量约束下. 只在固定质量上比较参数, 也要确保训练 token、底座和后训练相近. 成本与质量通常形成 Pareto 曲线: 增加预算能改善部分任务, 速度与容量随之上升;曲线以内的点被其他配置同时压过, 没有采用价值.

困惑度对局部预测敏感, 却未必覆盖长距离检索、跨段组合与精确复制. selector 可能在平均 token loss 上几乎不变, 在少量必须访问远端证据的样本上失败. 评测应至少覆盖普通语言建模与明确依赖长距离信息的任务, 再看长度分桶. 若长上下文数据中大部分答案只依赖末尾片段, 很小窗口也能得到好分数, 这不能证明远程路由已经学会.

训练阶段的稀疏结构还会改变模型学到的表示. 从稠密 checkpoint 直接替换 mask, 观察的是分布外结构改动下的退化;从头或继续训练让模型适应稀疏图, 观察的是架构容量与优化共同作用. 两者回答不同问题. 前者适合判断无需训练的部署改造, 后者适合判断稀疏架构能否达到目标质量. 若 selector 与主模型联合训练, 训练额外成本也应计入完整生命周期.

预算自适应会让平均成本与尾部成本分离. 简单 query 可能只需很少候选, 困难 query 使用更大集合. 平均 $E[k]$ 很低时, GPU 仍可能按 batch 中最大 $k$ 分配和执行, 或因变长行产生负载不均. 对在线系统, 应报告 $k$ 的分位数、每轮最大值与对应延迟. 对质量, 要检查大预算是否集中在真正需要远程依赖的 token, 还是 selector 对不确定输入普遍扩大预算.

最终能够部署的点还受容量硬约束. 某配置质量更好、平均更快, 若峰值索引或 KV 超过设备容量, 就无法运行目标并发. 反过来, 较小缓存可能让 batch 增大, 通过权重摊薄带来额外吞吐, 这份收益不能仅从 attention kernel 看出. **质量、单请求成本、峰值容量和可并发数共同定义有效工作点, 稀疏率只是其中一个中间变量.**

## 5. 怎样读实验表，才不会被一个倍数带跑

先核对工作负载：训练、Prefill、Decode，还是混合服务；输入与输出长度是多少；batch 与并发是多少；是否启用 prefix cache、continuous batching、chunked prefill。然后核对基线：是否使用同代 FlashAttention，精度和 KV dtype 是否相同，稠密与稀疏内核是否都经过调优。

再看分项指标。训练至少看有效 token/s、峰值显存、前向与反向时间。Prefill 看 TTFT、attention kernel 时间、执行 tile 数和 HBM 字节。Decode 看 TPOT、吞吐、KV 容量、实际读取字节与延迟分位数。质量评测要与速度结果使用同一稀疏预算，不能拿高预算质量配低预算速度。

容量口径同样需要核对。模型权重、KV 有效载荷、分页尾块、量化元数据、selector 状态、临时 workspace、CUDA graph 预留都占显存。PagedAttention 减少外部碎片和过度预留，却不会把有效 KV 本身变没；GQA/MLA 减少有效载荷，却不保证分配器没有碎片。二者解决不同问题。

一份可复算的最低记录应包含：模型层数与注意力维度、KV dtype、序列长度分布、batch/并发、稀疏预算及粒度、block/page 尺寸、设备与软件版本、kernel 名称、实际 HBM 字节、峰值显存、TTFT、TPOT 和吞吐。这样遇到“FLOPs 降了但没变快”时，能够判断问题落在 selector、随机访问、低 occupancy、通信还是 attention 之外的模块。

### 5.2. profiler 里的几个数该怎样对应公式

GPU profiler 给出的 kernel duration 是入口。稠密 attention、selector、top-k、gather、稀疏 attention 与 scatter 若是分开的 kernel，应把它们按同一条请求时间线相加；异步 kernel 还要看依赖关系，不能把相互重叠的时间重复累计。框架层的 wall time 会额外包含 Python/C++ 调度、CPU 到 GPU 提交、同步与排队，两者差距很大时，优化单个 kernel 的收益难以传到服务端。

dram bytes read/write 可与容量公式相互对照。假设逻辑 KV 只有 4 GiB，单步 profiler 却显示 attention 路径读取远高于 4 GiB，可能发生了重复读取、中间 gather 写回或 cache miss；若读量远低于 4 GiB，则要确认 L2 命中、跨步复用和计数范围。带宽利用率应使用实际字节除以 kernel 时间，再与设备规格比较，不能把“显存使用率”界面当成 HBM 带宽。

Tensor Core 利用率低也不等于算子一定受带宽限制。小矩阵、过多 kernel、warp divergence、依赖链和同步都可能让计算单元空闲。把实际 FLOPs 除以时间得到吞吐，再把实际字节除以时间得到带宽，同时与 Roofline 交叉点比较，才能判断下一步该减少运算、减少搬运，还是合并 kernel。

峰值显存需要在相同生命周期测量。训练中 activation checkpointing 会降低保存的激活，却增加重算；推理中 continuous batching 让请求不断进入和离开，某一时刻的 KV 峰值由调度决定。仅在空闲后读取 allocator reserved memory，测到的是缓存池保留量；仅统计 tensor 元素，又漏掉工作区与碎片。两种数都可以报告，但名称必须准确。

**从公式检查一个动态稀疏方案。**

设模型采用 8 个 KV heads、每头 128 维、32 层、BF16，历史长度 65536。单请求逻辑 KV 为

$$
2\times32\times65536\times8\times128\times2
=8\ \text{GiB}.
$$

方案为每个 query 选择 4096 个 token，索引使用每 token 64 维 BF16 摘要。完整摘要大小为

$$
32\times65536\times64\times2=256\ \text{MiB},
$$

这里假设每层各有一份摘要。若每次 Decode 都扫描全部摘要，仅摘要的理想 HBM 时间在 3.35 TB/s 下约 0.08 ms；选中 KV 为原来的十六分之一，约 512 MiB，理想读取时间约 0.16 ms。两者相加约 0.24 ms，低于完整 8 GiB 的约 2.56 ms，纸面上存在空间。

接着检查物理布局。若 4096 个 token 分散在全部 4096 个、每页 16 token 的页面中，按整页读取会重新带入 65536 个 token，KV 流量回到 8 GiB；若选择以页或块为单位并保持 256 个连续页，则才接近 4096 token 的有效载荷。于是算法需要同时约束候选质量和页局部性。

再检查索引计算。64 维摘要与 query 的点积，每层约为 $2\times65536\times64\approx8.39$ MFLOPs，32 层约 268 MFLOPs，FLOPs 不高；但随后从 65536 个分数取 top-k、写出索引并 gather KV。若每层独立排序，固定成本会被乘 32；若跨层共享候选，成本下降，路由表达能力也会改变。这正是实验中应单列 indexer 延迟与质量的原因。

容量方面，摘要多占 256 MiB，选中 KV 并不意味着其余 KV 可以删除：如果下一步可能选择不同历史位置，完整 8 GiB 仍要保留。只有淘汰策略能保证被删位置未来不再访问，常驻容量才会下降。这个例子把三个常被混在一起的结论拆开了：本步少读、长期少存、模型少算，成立条件各不相同。

**常见口径冲突。**

「显存降到线性」常用于描述 FlashAttention 不再保存平方大小的分数矩阵，KV Cache 本来就随序列长度线性增长；两句话中的显存对象不同。「稀疏后复杂度为 $O(Nk)$」描述逻辑边，当 $k$ 随 $N$ 增长时也未必是线性；固定比例 $k=\rho N$ 仍是 $O(N^2)$，只是常数变小。

「加速十六倍」可能指 attention kernel、单层、单请求 Decode、端到端 TPOT 或服务吞吐。只要分母不同，数字就不能横向放在一起。「支持 128K 上下文」也只说明某种配置可运行或经过训练，不说明在目标并发下 KV 能装下，更不说明 128K 时延满足业务要求。

另一个易错点是 GB 与 GiB。硬件带宽常用十进制 TB/s，显存容量与张量计算常用二进制 GiB。$1\ \text{GiB}=2^{30}$ bytes，而 $1\ \text{GB}=10^9$ bytes。前面的容量例子保留 byte 结果后再换算 GiB，带宽下界则按官方十进制 TB/s 计算，避免无意中制造约 7% 的偏差。

测量还要经过预热。首次运行可能包含内核加载、即时编译、显存分配和 CUDA graph 捕获，直接计入平均值会夸大短任务延迟。稳态测试应固定随机种子与输入形状，完成若干轮预热后记录多次重复的中位数和高分位数。动态稀疏方案若候选数受内容影响，还要保留真实文本分布；全零或随机张量可能形成与线上请求完全不同的路由密度。相同公式、相同 GPU，输入分布变化仍会改变候选局部性和负载均衡。

**一组实验怎样拆掉混杂变量。**

最小可解释实验先固定模型权重、dtype、设备、软件版本与输入 token, 只替换 attention 路径. 第一组测稠密 kernel 与稀疏 kernel 的单层时间, 看物理 tiles、HBM bytes 和 selector 分项;第二组放回完整模型, 看 TTFT、TPOT 与显存;第三组放回调度器, 看不同并发下的吞吐和尾延迟. 三层结果逐级增加系统因素, 可以定位单核收益在哪一步消失.

长度扫描不能只取 4K 与 128K 两个端点. 固定 batch, 以 1K、2K、4K、8K 等几何序列增加上下文, 能看出固定开销、线性项与平方项各自在何处主导. 若稀疏路径在短长度慢、长长度快, 两条曲线交点就是部署路由阈值的候选. 阈值还要在不同 batch 和 head dimension 下重复, 因为矩阵形状变化会移动交点.

预算扫描应保持输入不变, 逐步改变 $W$、$k$ 或 block 数. 每个点同时记录逻辑边、非空 tiles、命中页面、selector 时间、attention 时间和质量. 若逻辑边随 $k$ 线性增加而 tile 数呈台阶状, 说明块粒度主导;若页面数很早饱和, 继续减 $k$ 也难以减少 HBM 读取;若 selector 时间在某个 $k$ 后突增, 可能跨过了选择算法的寄存器或工作区阈值.

重复测量要区分冷启动与稳态. 冷启动包含模块加载、即时编译、显存池扩张和 graph 捕获, 对长期服务只发生少数几次;稳态则应在形状稳定后测量. 动态 batch 的 shape 经常变化, graph 未必能复用, 此时“稳态”仍包括重新选择执行图或走非 graph 路径. 报告应说明输入 shape 是否固定、是否启用 CUDA Graph、预热轮数以及统计窗口.

计时需要明确同步边界. CPU 侧提交 CUDA kernel 是异步的, 直接用主机时钟包住一次调用可能只测到 launch. GPU event 可以测同一 stream 上的设备时间;端到端 wall time 则在请求边界同步, 包含 CPU 调度和数据准备. 二者都重要: GPU event 解释 kernel, wall time 对应服务. 把二者混成一个“延迟”会让复现实验的人得到完全不同的结果.

带宽与 FLOPs 指标也要用实际执行量作分母. 稀疏 kernel 若按整 tile 执行, 用逻辑非零边估算 FLOPs 会把吞吐虚高;更合理的是按执行 tile 数乘 tile 矩阵乘法工作量. HBM 带宽用 profiler 的 DRAM bytes 除以 kernel duration, 不用逻辑 KV 容量除以时间. L2 命中高时, DRAM bytes 可低于语义读取量, 这是缓存复用, 不是计数错误.

输入数据影响动态路由, 因而 microbenchmark 至少要有两类. 合成输入用于固定 shape、控制候选分布并测试最坏/最好局部性;真实 token 用于观察自然文本中的候选重叠、热点位置和变长预算. 全零张量可能让所有分数相同, top-k 的 tie-breaking 产生异常规则的索引;独立随机张量又可能制造近乎均匀的散点, 比真实文本更差. 两者都不能单独代表线上访问.

基线必须处在同一优化等级. 稀疏自定义 kernel 若对比框架中的朴素 attention, 测到的包含 FlashAttention、融合与布局差异;稀疏侧若使用低精度 KV, 稠密侧也要给相同 dtype 的结果;一边启用 prefix cache 或 continuous batching, 另一边关闭, 端到端吞吐没有可比性. 一组可解释的消融按一次只改一个因素排列: 稠密优化基线, 加 mask 但不跳 tile, 跳 tile, 加 selector, 加页面布局, 然后放回完整系统.

**用守恒关系检查测量结果。**

许多离谱数字不用复现实验就能发现. 若单请求 GQA KV 有效载荷为 4 GiB, 声称每步完整扫描 KV 却在 H100 上耗时 0.1 ms, 对应带宽约 40 TB/s, 已远高于 3.35 TB/s 规格, 说明“完整扫描”、字节统计或计时边界至少有一项不成立. 若 32 层各自执行 selector, 报告却只计一层索引时间, 端到端分项不会闭合.

时间分解也应近似守恒. 同一 stream 上顺序执行的 kernel 时长之和不应显著小于纯 GPU 请求时间;若显著大于 wall time, 可能把并行 stream 的重叠时间重复相加. 端到端时间减去 GPU 活跃区间, 剩余部分来自 CPU、排队、同步或空泡. 优化后 kernel 变短而空泡不变, GPU 利用率可能反而下降, 端到端收益也会缩水.

容量可以用分配事件与张量公式相互验证. KV 有效载荷、页表、索引、workspace 的理论和应低于进程峰值;差额来自权重、其他激活、通信 buffer 与 allocator reserved. 若理论和高于实测峰值, 可能重复计算了共享前缀或 TP 分片;若远低于峰值, 应继续找临时张量和预留. 峰值只给总量, 守恒差额可以指向下一步检查位置, 也能防止把 allocator 预留误认成有效 KV.

吞吐与延迟也受一个简单关系约束. 若稳定 batch 每轮为 $B$ 个请求各产一个 token, 轮次时间为 $\tau$, 理想解码吞吐约为 $B/\tau$. 报告的 tokens/s 若明显高于此值, 可能把多实例或多 GPU 聚合吞吐与单实例 TPOT 混在一起;若明显低, 可能有采样、调度、网络返回或请求空槽. 这条关系要求 batch 真正稳定, continuous batching 下要按时间窗口统计实际产出 token 数.

质量结果同样要闭合到对应预算. 同一个方法若质量表使用 $k=4096$, 速度表使用 $k=1024$, 两张表不能合成一个工作点. 自适应预算应报告真实平均值与分位数, 不能用允许上限代表实际成本. 模型继续训练后得到的质量不能与零训练部署改造的成本混为一谈, 因为训练投入与权重已经变化.

检查顺序可以保持固定: 先用 shape 推逻辑 FLOPs 和有效载荷, 再用索引与 tile 推物理执行量, 随后从 profiler 读 bytes 与 duration, 末端对应到端到端分项. 任何一层对不上, 都先解决口径差异, 不急着用「硬件波动」解释. **成本分析的目标是让边、tile、byte、秒四种量可以逐层对应, 每个加速倍数都能找到明确分子和分母.**

**把均值拆成分布。**

稀疏路由的平均候选数可能相同, 延迟分布却完全不同. 配置 A 让每个 query 固定选择 1024 个 token;配置 B 让九成 query 选择 256 个, 一成 query 选择 7936 个, 两者平均都约为 1024. 若 GPU 将许多 queries 放入同一个执行批次, 配置 B 的长行会决定一部分 thread block 的结束时间, 还可能触发更大临时空间. 平均边数没有记录这种长尾.

候选数之外, 页面数和目标卡数也应看分布. 两个 query 都选择 1024 个 token, 一个集中在 64 个连续页面, 另一个分散在 1024 个页面;前者地址与传输容易合并, 后者会产生更多页表查询和内存事务. 分布式执行中, 候选若集中在一张远端卡, 单个 query 的通信伙伴少, 热点卡负载却可能过高;候选均匀覆盖所有卡, 负载平衡, 每个 query 又要参与更多消息与归并.

统计时至少保留中位数、P90、P99 与最大值, 并说明统计对象是 query、请求还是调度轮次. query 级 P99 能发现 selector 的极端预算;请求级 P99 包含一个请求多个 token 的累计效应;轮次级最大值更接近 GPU 每轮被最慢工作拖住的程度. 将三种对象混用, 很容易出现“候选 P99 很低, 请求 P99 仍很高”的表面矛盾.

长度本身也是条件变量. 把 1K 与 128K 请求混在一起求平均, 结果由数据集中两类请求的比例决定, 无法显示复杂度. 更好的做法是按上下文长度分桶, 在每个桶内报告候选、页面、字节和延迟分位数, 再给线上流量加权的总体值. 这样既能看到算法随长度的斜率, 也能看到真实请求分布下的服务结果.

动态路由还可能随生成位置变化. prompt 末尾的首个 Decode query 面对完整 prompt, 后续 query 的历史继续增加;模型在不同语义阶段也可能扩大或缩小远程候选. 把整段生成的所有 token 混在一起, 会掩盖热身阶段、稳定阶段与长输出尾部. 按生成步分桶可以判断 selector 成本是固定、线性增长, 还是被缓存和索引结构摊平.

**均值适合计算总工作, 分位数负责暴露同步、分页和动态路由的长尾.** 两者必须与相同的 batch、长度分布和调度策略绑定. 只有 kernel 平均时间而没有请求尾延迟, 无法判断线上效果;只有 P99 而没有工作量分解, 又无法定位尾部来自候选、页面、通信还是排队.

### 5.1. 把四条轴放回同一张图

MHA、GQA、MLA 先决定每个 token 需要保存多少 KV 状态；序列结构再决定 query 能看到多少 token；kernel 把这些逻辑边映射为 tile 与 HBM 事务；训练、Prefill、Decode 则为同一套张量赋予不同的形状和复用机会。

可以把判断顺序压成四问：

1. **容量**：权重、KV、激活、索引和工作区能否装下？
2. **带宽**：关键路径实际从 HBM 读写多少字节，访问是否连续？
3. **算力**：真正执行了多少 tile，矩阵形状能否利用计算单元？
4. **实现**：选择、排序、通信和调度是否吃掉理论节省？

这四问没有固定赢家。降低 $H_{kv}$ 主要动 head 轴，缩短窗口或 token top-k 主要动序列轴，量化动字节轴，FlashAttention 动 IO 路径，分页动分配与复用。把它们写在同一个「稀疏率」里，结论一定会乱。把对象拆开，复杂度公式才会落到真实机器上。

同一份配置换到不同阶段、batch 与设备上, 主导项会移动, 公式中的每一项都要随工作负载重新代入.

# 评测协议

稀疏 attention 的评测沿着一条因果链展开：selector 产生候选，kernel 读取候选，模型生成答案，服务系统交付请求。最终答案、kernel 时间各自只覆盖其中一段。协议的基本单位是一条可回放请求，其中同时保存任务标签、证据位置、候选统计、dense 对照和系统时间线。

## 1. 三层对照

### 1.1. Full Attention 回退

同一 checkpoint 若支持 dense 与 sparse 两条路径，先固定 prompt、生成参数和随机种子，分别运行。质量差额定义为

$$
\Delta Q=Q_{sparse}-Q_{dense}. \tag{1}
$$

绝对分数回答模型能否完成任务，$\Delta Q$ 更接近稀疏机制造成的变化。若 dense 自身已经失败，sparse 的失败不能全归给选择器。逐样本保留四种组合：两者都对、dense 对 sparse 错、dense 错 sparse 对、两者都错。

### 1.2. 固定候选与完整路由

系统对照至少有 dense kernel、固定候选 sparse kernel、selector 加 sparse kernel 三档。第一档给设备基线，第二档隔离 kernel，第三档才是完整方案。固定候选很快、完整路径不快，问题在索引或调度；两条 sparse 路径都慢，再检查块长、访存与候选率。

## 2. 长上下文任务网格

### 2.1. 长度与证据深度

上下文长度按 4K、8K、16K、32K、64K、128K 等档位扫描。每档把证据放在 10%、30%、50%、70%、90% 深度，并对位置加入随机扰动，避免固定模板。总长度与 query 到证据的距离分别记录，因为长 prompt 尾部证据主要测试容量，开头证据才真正测试远距访问。 Needle 类任务适合做连通性筛查；RULER 提供可配置长度与复杂度的合成任务，覆盖单/多 key 检索、变量追踪与聚合；LongBench 包含中英文、多文档问答、摘要、few-shot、合成和代码任务。三类任务承担不同角色，不能用一张 needle 热力图替代真实任务。

### 2.2. 多证据与相似干扰

证据数设置为 1、2、4、8，并加入同实体、同模板或旧版本片段。记录 any-evidence recall、all-evidence recall 与最终答案。若单证据召回各为 95%，四段证据在粗略独立假设下同时命中的概率只有 $0.95^4\approx81.45\%$，多证据能放大 selector 的小漏检。

## 3. 路由与物理执行

候选集合 $S_i$ 与 dense 教师 top-$m$ 集合 $G_i$ 的召回为

$$
R_i=\frac{|S_i\cap G_i|}{|G_i|}, \tag{2}
$$

概率质量覆盖为

$$
C_i=\sum_{j\in S_i}p^{dense}_{ij}. \tag{3}
$$

两者按层、head、query 位置、证据距离和长度分桶。还要记录逻辑 token 数、去重后 block/page 数与实际 HBM 字节。逻辑 top-k 很小而页扩张很大时，质量预算与系统预算已经不是一个数。 候选召回的参照也要固定。教师 top-$m$ 中的 $m$ 与学生预算 $k$ 分开记录；$m=k$ 强调排序一致，$m>k$ 可以观察学生覆盖教师高质量集合的程度。attention mass 采用 softmax 后概率，跨 head 聚合时说明是均值、最大值还是 GQA 组内求和。 带标注证据的任务再计算 token、span、block 三个粒度。候选只碰到 span 的一个标点不算完整覆盖；块级方法读取了证据所在块，也要确认有效 mask 包含实际 span。多证据问题同时给 any 与 all recall，避免平均 token recall 掩盖推理链断点。

## 4. 系统时间线

离线吞吐、TTFT、TPOT/ITL 分开测量。TTFT 包含调度、prefill、selector、索引与首 token；TPOT 在稳定 decode 区间统计，并同时给 P50、P95、P99。请求吞吐用 requests/s 与 output tokens/s 表示，固定输入/输出长度分布和并发。 GPU 指标包含 DRAM bytes、有效带宽、L2 hit、tensor core active、workspace 与峰值显存。路由、top-k、索引、plan、attention、split 归并分别计时。Microbenchmark 与端到端测试保留相同 shape，才能解释局部加速为何被其他阶段吞掉。 Prefill 按输入 tokens/s 与 TTFT 观察，decode 按 TPOT、ITL 和 output tokens/s 观察。一次请求输出长度会改变两个阶段在总时间中的权重，因此同时给固定 1、32、128 token 输出场景。吞吐实验达到稳态后再采样，JIT、首次权重加载与 cache 冷启动另列为冷启动指标。 显存分成模型参数、KV cache、attention workspace、selector cache 和临时索引。只报峰值无法说明稀疏方法是否真的缩小 KV；动态稀疏通常仍保存完整 KV，只减少读取。每个分项在相同 batch、长度和 dtype 下比较。

## 5. open-loop 与 closed-loop

closed-loop 中，每个客户端等上一个请求完成后再发送，适合观察交互延迟；open-loop 按给定到达过程注入请求，即使系统排队也继续发送，更接近固定业务负载。两者的吞吐与尾延迟不能混用。 open-loop 扫描到达率，找到延迟开始陡升的饱和点；closed-loop 扫描并发客户端数。每个点报告队列时间、执行时间和总时延。稀疏方案若单请求快却因 ragged 候选降低 batching 效率，open-loop 更容易暴露。 输入长度分布至少有定长、均匀与长尾三组。长尾可用 80% 短请求加 20% 长请求，模拟线上少量超长上下文拖住 batch。输出长度同样固定分布，防止某个方案恰好更早停止而获得虚假吞吐优势。请求顺序使用同一 trace 回放。

prefix cache 命中会大幅改变 TTFT。基准分成冷 prefix、固定命中率和完全命中三档，并记录被复用的 token 数。稀疏 page table 与共享 prefix 的交互属于方案能力，但必须在两条基线使用相同命中 trace。

### 5.1. 统计与复现

任务样本用配对 bootstrap 计算 $\Delta Q$ 的 95% 置信区间，因为 dense 与 sparse 运行的是同一批样本。时延分布用独立重复与 bootstrap 分位数区间，保留原始请求级记录。只报一次均值看不到尾部，也无法判断小差异是否超过随机波动。 配置记录包括模型与 commit、权重、tokenizer、prompt、生成参数、benchmark 版本、长度截断方式、GPU、驱动、框架、内核、dtype、时钟策略、batch、并发、预热与计时边界。实验先验证 dense 回退输出，再锁定配置运行完整矩阵。 样本数在实验前按希望检测的效应确定。准确率差只有 0.5 个百分点时，几十个样本远远不够；昂贵的长序列测试可先跑 pilot 估计配对差值方差，再计算正式样本数。所有提前停止规则预先写入协议，避免看到有利结果便结束。

随机种子控制样本生成、needle 位置、采样解码和请求到达。贪心解码仍可能受并行归约产生的末位差异影响，因此保存实际输出。每次实验输出逐请求原始表、汇总脚本版本与校验和，汇总结果可以从原始表重新生成。

### 5.2. 用最少对照定位失败来源

质量下降样本按 dense 成败、标注证据、教师 mass 和候选覆盖分组。证据漏选对应 selector 分支；候选覆盖而输出错误对应 attention 数值、层间传播与训练适配分支。系统性能按物理 HBM 字节、索引和 kernel 分解；P99 异常再按最大候选行、workspace 扩容、CUDA Graph miss 与 fallback 切片。 每次归因至少落到一个可反驳假设。例如「页扩张导致多读」要能由逻辑候选字节、物理 DRAM bytes 与改用小页后的对照验证；「长度外推导致漏选」要有相同证据深度、不同总长度的召回曲线。没有对应观测量的解释留在待验证项。 回归门槛在实验前登记：质量非劣界、TTFT/TPOT 改善目标、P99 上限、显存预算与 fallback 比例。一次运行可同时通过部分门槛、失败部分门槛，结果按原始维度保留，不合成一个掩盖取舍的总分。

数据管线先产生不可变样本清单，再由 dense 与 sparse 共同消费。request ID、tokenized prompt hash 与证据 span hash 能检查两条路径输入一致；服务回放另保存到达时间戳和 prefix 命中状态。任何缺失字段都会使该请求无法进入配对分析。

**协议入口。**

[质量与系统联合评测](./6.1.1-质量与系统联合评测.md)给出逐请求 schema、长度—深度—证据网格、置信区间手算、服务负载和失败归因矩阵。一项结论只有在质量差额、路由覆盖和机器工作量能用相同请求 ID 对齐时，才具有可复算性。

**协议先锁定什么。**

第一项是比较对象。研究selector时固定checkpoint、位置方案、kernel与解码，只改变候选；研究kernel时固定候选表与模型函数，只改变执行；研究完整系统时允许各路径使用合理优化，同时把训练、selector和cache资源全部计入。三类问题需要不同控制变量，不能共享一句“和Full比较”就结束。 第二项是输入身份。字符相同不保证token相同，服务模板和截断也可能改变证据位置。每条请求保存最终token序列哈希、实际长度、证据token span和query位置。Dense、oracle、fixed sparse与real sparse只有消费同一token序列，逐样本差异才有明确含义。

第三项是输出契约。短答任务采用确定性解码与固定规范化，开放生成则预先定义自动指标、模型裁判或人工抽样。超时、OOM、服务拒绝、解析失败与答案错误分别记录。只对成功请求计算的质量和把未完成视为失败的端到端可用率并列呈现。 第四项是计时边界。Kernel时间回答执行效率，attention阶段时间加入selector与构表，模型时间加入其余层，请求时间再加入排队、调度和传输。每层边界都可测，但不能拿其中一个数字代表其他层。报告加速时直接写清分子、分母和是否包含冷启动。

第五项是停止与发布条件。质量非劣界、置信区间、P99、显存、完成率和fallback上限在运行前登记。发现某档位不通过时仍保留原始结果，不通过更高长度可以按预案停止节省资源，但不能删除失败点后重新定义目标。 协议还要规定缓存状态。Prefix cache、编译cache、BlockMask或plan cache会显著改变TTFT和尾延迟；两条路径使用不同热度时，比较会混入缓存收益。冷态、预热态和固定命中率分别运行，请求trace保持一致。缓存命中本身属于可优化能力，但必须作为实验变量出现。 多GPU场景另存通信边界。稀疏kernel减少本地QK/PV，不保证all-to-all、KV交换或sequence parallel通信同比下降。记录每个rank的候选、发送字节、等待时间和负载，防止单卡microbenchmark被误用为集群收益。若稀疏路由需要全局摘要，摘要通信也进入selector成本。

能耗或GPU占用率可以作为补充系统指标。相同请求延迟下，一种方案可能占用更多SM或显存，降低整机可部署副本数；相同吞吐下，能耗与资源预留也会不同。主协议先保证质量、完成率和时延可比，再按实际部署目标增加功耗与容量指标。

**从现象回到可操作结论。**

若Sparse相对Full掉分，第一项检查Full是否成功，第二项检查oracle。Full失败说明底座或任务本身是上限；Full成功、oracle失败指向稀疏图、预算或训练适配；oracle成功、real失败指向selector；候选与oracle一致仍存在数值差时，再检查kernel、mask、位置和cache映射。这条顺序能避免看到漏答就盲目增加top-k。 若microbenchmark加速而端到端没有改善，先把时间线相加。Selector、排序、BlockMask、分页映射、通信和split归并中的任何一项都可能抵消kernel节省。物理KV字节没有下降时，逻辑稀疏没有落到访存；字节下降、时间不降时，索引、occupancy或尾部负载更值得检查。 若平均延迟下降而P99恶化，按最大行长、候选数、请求长度、cache命中、重编译和fallback切片。Ragged稀疏经常让少数长行拖住batch；静态平均候选数无法解释这类尾部。调度优化应在保持候选集合不变的前提下复测，确认收益来自负载均衡。

若质量随预算增加先升后降，检查证据覆盖与干扰注入。覆盖已饱和后继续扩大候选，会增加softmax竞争，也可能改变模型训练分布。Full偶尔弱于Sparse并不矛盾，稀疏图可以滤掉干扰。配对结果应同时保留Sparse修复Full错误和Sparse新增错误两种方向。 所有归因最终落到一次新对照。怀疑位置外推，就固定证据距离平移绝对位置；怀疑页扩张，就固定逻辑候选改变页或块粒度；怀疑selector，就注入oracle证据；怀疑kernel，就复用同一候选与dense显式reference。没有反事实对照的解释只是线索，不能成为发布结论。

**协议如何进入持续回归。**

大型网格用于发布前验收，日常提交不可能全部重跑。可以从每类任务和每个关键长度选出最小回归集，保留边界位置、非整除块、长尾候选和历史失败样本。它用于快速发现语义、质量与明显性能回退，完整网格再验证总体曲线。 回归集要保持不可变版本，同时允许新增case。直接替换旧样本会让历史曲线失去可比性。模型或tokenizer升级后若旧token序列不再适用，建立新版本并保留两者映射，结果不要无说明拼接。 性能回归需要稳定设备与环境。固定GPU时钟、隔离其他负载、预热编译和cache，热态重复足够次数；冷启动另设case。共享集群中保留设备ID、时间戳与背景负载，使用更宽阈值和重复确认，避免对噪声做优化。

语义回归优先于性能回归。邻接、输出、LSE或梯度没有通过时，任何速度提升都没有发布意义。语义通过后再比较机器工作量与时延；端到端通过后才评估上线SLO。顺序固定可以阻止团队在错误结果上继续调优。 发布工件至少包含配置、不可变样本清单、逐请求结果、路由与成本摘要、环境版本和汇总脚本。图表由原始表生成，不能手工改数字。以后出现回归时，可以沿request ID回到token、候选、kernel与服务时间线，而非重新猜测当时发生了什么。 历史结果不能自动继承给新checkpoint或新服务版本。即使模型名不变，tokenizer、chat template、RoPE、kernel启发式和调度都可能变化。每份结果绑定权重与软件哈希；只改不影响语义的基础设施时，也至少运行最小配对回归确认。

当完整矩阵成本过高时，先保证核心对照和边界格子，而非每个维度只测一个随机点。短基线、预期有效长度附近、最大长度、低预算与高预算、Full与real sparse组成最小骨架。额外资源再扩展任务和服务负载，结论范围与实际覆盖保持一致。 协议的价值最终体现在可证伪。每条解释都能指向一项观测和一次反事实实验，每项发布门槛都能从逐请求数据重新计算。这样质量下降、路由漏检与系统长尾不会互相背锅，Sparse Attention的收益和代价也能在同一条证据链上核对。

**阅读路线。**

先阅读[质量与系统联合评测](./6.1.1-质量与系统联合评测.md)，把逐请求schema、对照矩阵和服务负载落到具体字段。随后进入[有效上下文](../6.2-有效上下文/6.2-有效上下文.md)，把长度、任务复杂度与稀疏预算放进同一能力边界。两篇叶文分别回答“怎样测得可信”和“在多长范围内可信”。 实现新Sparse Attention时，可以先用最小三档对照：Full、固定候选Sparse、完整路由Sparse。语义与时间线跑通后再加入oracle、随机候选、不同预算和open-loop压力。对照一次增加一层，失败来源更容易定位，也避免第一轮就生成无法解释的大表。

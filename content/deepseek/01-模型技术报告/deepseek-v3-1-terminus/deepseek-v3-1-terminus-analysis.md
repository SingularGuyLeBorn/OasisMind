# DeepSeek-V3.1-Terminus: 后训练修订如何改变输出与 Agent 行为

DeepSeek-V3.1-Terminus 发布于 V3.1 之后约一个月. 官方材料只有两页: 三条改进说明, 一张包含十二项成绩的 V3.1 对照表, App, Web, API 与开源权重入口. 页面没有网络结构, 数据规模, 训练日程或后训练算法, 因而 Terminus 应被理解为 V3.1 权重线上的行为修订, 不能当作另一个已披露架构的新底座.

十二项成绩分成两组. 第一组是 `reasoning mode w/o tool use`, 即禁止工具的思考模式; 第二组是 `agentic tool use`, 即允许工具交互的 Agent 设置. 分组决定了分数含义. HLE 21.7 衡量闭卷推理, BrowseComp 38.5 与 SWE Verified 68.4 则包含模型和工具执行框架的共同作用. 两组数字不能混成一条统一能力刻度.

## 1. 同一权重线上的修订范围

Terminus 沿用 V3.1 的权重路线,公开材料把变化集中在行为修订上,没有提供足以确认新架构的完整技术报告.

### 1.1. 为什么把 Terminus 归为后训练更新

发布页标题直接写成 `DeepSeek-V3.1 → DeepSeek-V3.1-Terminus`, 并称更新建立在 V3.1 的能力之上. 页面没有宣布参数量, 层数, MoE 配置, 上下文长度, tokenizer 或 UE8M0 格式变化. Hugging Face 仓库名也保留 `DeepSeek-V3.1` 前缀. 现有材料支持「沿用 V3.1 底座并修订后训练行为」, 不支持具体到某种优化算法的判断.

对照表中的 V3.1 一栏与前一版发布材料能够逐项对上. BrowseComp 30.0, BrowseComp-zh 49.2, SimpleQA 93.4, SWE Verified 66.0, SWE-bench Multilingual 54.5 与 Terminal-Bench 31.3 都来自 V3.1 Agent 表; GPQA-Diamond 80.1 与 LiveCodeBench 74.8 也对应 V3.1 的 CoT 压缩图. 这说明 Terminus 页面沿用同一组 V3.1 基线, 至少没有另换一个旧模型口径.

沿用基线不等于所有新分数都由完全相同的运行环境重跑. 页面没有列 Agent 框架版本, 搜索接口, 最大步数, token 预算, 温度和采样次数. 因而对照表适合描述官方系统的版本差异, 不足以让第三方只凭权重复现到相同小数位. 对 5 分以上的变化可以确认方向明显, 对 0.1–0.6 分的差距则要保留采样波动空间.

### 1.2. V3.1 的部署假设仍然有效

Terminus 没有发布新的 tokenizer, chat template 或量化说明. 在缺少相反声明时, 部署应沿用 V3.1 的 128K 上下文, 双模式模板与 UE8M0 FP8 Scale 处理方式, 同时以 Terminus 仓库内实际配置为准. 这是一条部署兼容判断, 不是官方明确承诺; 页面没有写「与 V3.1 二进制兼容」.

思考与非思考模式仍由同一权重承载. Terminus 表只给思考模式的无工具成绩和 Agent 的工具成绩, 没有单列非思考通用问答. 因而无法从表格判断语言一致性修复是否同等覆盖两种模式, 也无法判断短回答长度是否变化. App, Web 与 API 同时上线说明产品入口不变, 不能代替模式级回归数据.

双模式回归至少包含四种组合: 思考模式的纯文本回答, 非思考模式的纯文本回答, 带工具的单轮执行, 带历史的多轮执行. 语言混杂可能只在长推理段出现, 也可能在工具观察加入上下文后出现. 十二项表格没有按组合拆分, 因而某一组任务上涨不能证明所有入口都修复到相同程度.

同一份权重还会让修订相互牵连. 提高语言一致性可能使模型减少自由切换语言, 而搜索 Agent 有时需要用另一种语言构造查询; 强化工具格式可能提高结构化输出成功率, 同时改变自然语言回答的 token 分布. BrowseComp 英文上涨而中文回落说明至少存在一个方向不一致的结果. 没有消融时, 最稳妥的解释是 Terminus 重新平衡了多项目标, 并非在 V3.1 上增加一个互不影响的独立模块.

V3.1 的模板会在非思考模式预先闭合 `</think>`, 并在多轮历史中移除旧推理文本. Terminus 若专门修正混杂与随机字符, 模板处理错误仍可能在部署端重新引入异常. 权重修订只能改变模型分布, 无法纠正调用方使用旧 tokenizer, 错误特殊 token 或把历史思考段重复拼接的行为.

### 1.3. 从公开配置判断哪些部分保持不变

模型仓库的配置仍给出 61 层、隐藏维度 7168、256 个路由专家、每个 token 激活 8 个专家、MLA 的 $q$ 与 $kv$ 低秩维度以及 UE8M0 缩放格式. 这些字段与 V3.1 推理配置对齐. 官方后续发布 V3.2-Exp 时又明确说它建立在 V3.1-Terminus 上, 新增的是 DeepSeek Sparse Attention, 并特意对齐训练配置来隔离稀疏注意力影响. 这条版本链进一步把 Terminus 放在「架构改动之前的行为基线」位置.

配置一致能排除一批解释. HLE 从 15.9 到 21.7 不能归因于层数增加, Agent 分数上涨也不能归因于专家数量或上下文窗口扩大. 同样, 语言混杂减少不需要引入新的语言识别模块才能成立; 自回归模型的下一个 token 分布经过后训练就能改变语言持续性. 公开材料支持把变化放在权重分布与后训练行为上, 具体用了哪种数据和目标仍没有拆开.

同构架构还有一个研究价值: 推理服务的主要算子图、显存布局和 KV cache 形态大体不变, 因此两版对比更接近权重替换实验. 若同一后端、同一模板、同一采样参数下行为发生变化, 解释变量集中在 checkpoint. 但 API 页面上的旧基线未说明是否用同一天的服务栈重跑, 官方表仍不能替代严格配对实验.

### 1.4. 混合思考模式是一套条件分布

「同一模型支持思考与非思考」容易被理解成模型内部有两个互不相干的子网络. 更准确的视角是同一参数 $\theta$ 在不同模板与控制 token 条件下产生不同分布. 设对话上下文为 $x$, 模式控制为 $m\in\{\text{think},\text{chat}\}$, 输出序列为 $y$, 则:

$$
p_\theta(y\mid x,m)=\prod_{t=1}^{T}p_\theta(y_t\mid x,m,y_{<t}).
$$

$m$ 改变首个 token 之后整条轨迹的条件分布. 思考模式通常允许先生成推理段再给答案, 非思考模式通过模板让模型直接进入答案区. 两种模式共享参数, 后训练对一个模式的梯度也可能改变另一模式. 因此 Terminus 的语言一致性修订不能天然被限制在某一条独立分支, 除非训练数据、mask 或路由明确隔离, 官方没有披露这种隔离.

共享参数同时带来迁移与干扰. 若模型在思考轨迹中学会更稳定地维持用户语言, 这项规律可能迁移到非思考回答; 若训练强化了长轨迹中的英文工具词, 也可能让中文回答更容易出现英文片段. 目标间关系取决于样本混合、梯度方向和模式 token 的可分性. Terminus 的表只展示思考模式无工具结果和 Agent 结果, 缺少非思考组, 无法从公开数字重建这张迁移矩阵.

混合模式的部署正确性也属于模型行为的一部分. 若服务端错误地省略模式控制、把历史思考内容保留到下一轮, 或在工具 observation 后拼错结束 token, 实际采样的条件分布已经偏离官方模板. 权重修订能降低某些异常序列的概率, 无法保证错误模板仍落在训练分布内. 评测两版时必须固定模板, 否则模板差异与 checkpoint 差异无法分离.

### 1.5. 同一参数为何能容纳两种模式

模式控制 token 会改变残差流中的隐藏状态, 后续每一层注意力与 MoE 都在这个条件上计算. 即使专家路由函数没有专门的「思考专家」标签, 不同隐藏状态也可能选择不同专家组合. 设第 $l$ 层第 $e$ 个专家的路由权重为 $g_{l,e}(h_l)$, 模式控制先改变 $h_l$, 再间接改变:

$$
h_{l+1}=h_l+\sum_{e\in\operatorname{TopK}(g_l(h_l))}
g_{l,e}(h_l)E_{l,e}(h_l).
$$

所以双模式无需复制整套网络. 模式差异可以分布在注意力状态、专家选择和输出 logits 中. 这也说明共享参数不等于两种模式行为接近: 一个早期控制 token 经过几十层传播, 足以让生成轨迹分叉. 官方没有公布 Terminus 的模式级路由统计, 不能进一步声称某些专家专门负责思考或语言一致.

训练时要让控制 token 可识别, 数据中两种模式必须使用稳定模板, 并分别展示期望输出. 若同一提示在两种模式下目标冲突, 模型依靠模式条件消解. 数据标记噪声会使边界模糊, 例如非思考样本仍含长推理, 或思考样本缺少结束标记. Terminus 处理输出问题时, 清理模板与目标序列是合理可能性, 官方没有给数据处理说明.

推理时的首个分支具有路径依赖. 思考模式一旦进入长推理, 后续 token 都以已生成轨迹为条件; 非思考模式跳过这段, 最终答案的条件也不同. 即使两者最后答案相同, token 概率和表述可能不同. 因而不应把 `deepseek-chat` 当作 `deepseek-reasoner` 隐藏推理后的同一答案, 它们是同一权重下的两种生成过程.

## 2. 语言一致性修复了哪类失败

### 2.1. 中英文混杂是序列级行为

官方第一条改进是 `fewer CN/EN mix-ups & no more random chars`. 中英文混杂指回答在没有语义需要时切换语言, 例如中文解释中突然转为英文段落, 或代码说明与用户语言不一致. 对双语模型而言, 两种语言的 token 都在可生成集合中. 问题不在模型能否生成另一种语言, 而在当前对话条件下能否持续维持目标语言.

语言一致性通常受指令数据分布, 推理轨迹语言与奖励共同影响. DeepSeek-R1 曾公开使用语言一致性奖励, 按 CoT 中目标语言词的比例提供信号, 并承认可读性约束可能牺牲少量推理表现. Terminus 页面没有说复用了该方法. 把混杂减少归因于某个奖励函数会超过材料范围; 可以确认的只有输出行为被纳入了修订目标.

语言约束也不能简单设成「全中文」或「全英文」. 代码标识符, API 名, 引文和专有术语需要保留原语言. 有效目标是保持叙述语言稳定, 同时允许必要的局部切换. 如果奖励只统计字符比例, 模型可能为了提高比例而翻译不该翻译的标识符. 页面没有给语言识别规则, 测试集或混杂率, 因而无法判断修复对代码与技术写作的边界处理.

CoT 又增加一层约束. 用户要求中文回答时, 推理段与最终答案可能采用不同语言; 如果服务端隐藏推理段, 用户只观察到答案语言, 训练侧却仍要控制隐藏部分. R1 的语言一致性奖励曾显示, 约束推理语言会影响推理表现. Terminus 没有分别报告可见答案和思考段的语言比例, 因而「fewer CN/EN mix-ups」究竟覆盖哪个区段并不明确.

衡量混杂也需要把字符, token 与语义片段分开. 英文缩写和代码标识符不应算失败, 一整句无缘由换语种则应算失败, 单个异常汉字又属于噪声字符. 如果只按 Unicode 范围计数, 三类现象会被混在一起. 官方没有发布判定器和测试集, 第三方只能根据自己的产品语言定义建立回归集合, 不能复算发布声明的绝对幅度.

### 2.2. 随机字符为何比文风问题更严重

`no more random chars` 指向局部异常 token. 随机字符若出现在自然语言段落, 会降低可读性; 若插入代码, JSON 或函数参数, 可能直接造成编译和解析失败. 用户曾报告 V3.1 输出中出现孤立汉字或不合上下文的字符, 但官方两页说明没有列具体字符, 频率和根因. 因而应保留官方的现象级表述, 不把社区样例当作完整故障定义.

异常字符可能来自训练样本噪声, tokenizer 边界, 模式 token 附近的分布偏移或解码尾部失稳. 多种原因都能产生相似输出, 仅凭「消失」无法定位根因. Terminus 没有提供异常率对照, 也没有给修复前后的受控提示集合. 「no more」是发布声明, 不是统计意义上的零故障保证.

工程验收需要覆盖字符异常最容易造成损失的结构化场景: 代码补丁能否编译, JSON 是否通过 schema, 函数参数是否保持字段名, Markdown 围栏是否闭合, 多轮长输出是否在尾部出现噪声. 这些检查与 benchmark 分数不同. 十二项表格衡量任务成功或知识问答, 没有直接测量中英文混杂率与随机字符率.

### 2.3. 稳定可靠不等于每项分数上涨

发布页称 Terminus 在各项 benchmark 上输出更稳定可靠, 但表中存在回退: Codeforces 从 2091 降至 2046, Aider-Polyglot 从 76.3 降至 76.1, BrowseComp-zh 从 49.2 降至 45.0. 因而「稳定可靠」更适合解释语言与格式行为, 不能改写成所有能力指标单调提高.

稳定性若按统计定义, 应报告多次采样的方差, 置信区间或失败率分布. 页面只给单列分数, 没有误差条和重复次数. 0.1 分的 LiveCodeBench 变化与 0.2 分的 Aider-Polyglot 回退都不足以单独支撑稳定性判断. HLE 增加 5.8 分, BrowseComp 增加 8.5 分, Terminal-Bench 增加 5.4 分, 这些大变化才构成清晰的能力信号.

### 2.4. 语言一致性可以怎样建模

设目标叙述语言为 $L$, 序列中第 $t$ 个片段的语言标签为 $\ell_t$, 必要的代码、专名和引用集合为 $E$. 一个粗略一致性损失可以写成:

$$
\mathcal{L}_{\text{lang}}=
\frac{\sum_t w_t\,\mathbf{1}[\ell_t\neq L\land y_t\notin E]}{\sum_t w_t}.
$$

$w_t$ 可以按 token、字符或语义片段赋权. 真正困难的是 $E$ 和片段边界. `PyTorch`, `JSON`, 函数名与论文标题不应被判成混杂, 一整句无缘由换成英文则应计入. 中文句子中出现拉丁字母也不等于语言切换. 只用 Unicode 范围会把技术写作误伤, 只用句级分类又可能漏掉句内异常片段.

序列级失败具有自激特征. 模型一旦生成英文开头, 后续条件中已经出现英文, 下一 token 延续英文的概率通常上升. 若在位置 $t$ 发生无意切换, 整段损失可能远大于一个 token. 后训练可以通过提供稳定单语轨迹、偏好比较或序列奖励改变切换边界. 官方只报告现象改善, 所以这些是理解可能机制的通用框架, 不能挑其中一种当作 Terminus 配方.

语言一致性与正确性有时同向, 有时冲突. 用户用中文提问某个英文 API 时, 保留英文标识符有助于可执行性; 强制翻译会降低正确性. 搜索任务中, 中文问题可能需要生成英文查询才能访问更丰富来源, 查询语言切换是工具策略, 最终答案仍可保持中文. 如果训练把所有跨语言 token 都惩罚, Search Agent 反而可能受损. BrowseComp-zh 回落提供了一个需要关注的结果, 但没有题级轨迹证明它由该冲突造成.

### 2.5. 异常字符与解码状态

自回归生成在每一步从 logits 得到概率分布. 设温度为 $\tau$, token $i$ 的概率为:

$$
p_i=\frac{\exp(z_i/\tau)}{\sum_j\exp(z_j/\tau)}.
$$

后训练若压低异常 token 在常见上下文中的 logit, 即使解码器不变, 偶发字符率也会下降. 温度越高或采样尾部保留越宽, 低概率异常被选中的机会越大. 因而「随机字符」既与权重有关, 也与服务端温度、top-$p$、重复惩罚和停止条件有关. 官方 App、Web 与 API 同步升级能统一产品体验, 开源权重在不同解码设置下未必复现相同的零异常表象.

异常还可能出现在特殊 token 邻域. 思考开始与结束、工具调用边界、JSON 字段之间都要求模型从一种局部分布切换到另一种. 若训练样本中的模板不一致, 模型可能输出可见控制符、半个标记或不属于当前语言的碎片. 工具 observation 又常包含网页噪声和多语言文本, 长上下文会把这些 token 带入后续条件. 因而字符稳定性测试应覆盖边界位置, 不能只测短问答正文.

结构化输出将小概率字符错误放大成离散失败. 一段 2000 token 的 JSON 中, 假设每个 token 独立保持合法的概率为 $1-\epsilon$, 整段完全合法的近似概率为:

$$
P(\text{valid})\approx(1-\epsilon)^{2000}.
$$

即使 $\epsilon$ 很小, 长序列成功率也会明显下降. 实际错误并不独立, 但这个近似说明为什么「偶发字符」对 Agent 比普通文风问题更严重. Terminus 同时强调字符稳定和 Agent, 两个目标在产品层面相互支撑; 公开材料仍没有证明二者来自同一训练改动.

### 2.6. 语言、思考和工具三者的耦合

一条 Agent 轨迹可写成状态、思考、动作、观察的交替序列:

$$
h_t=(x,r_{<t},a_{<t},o_{<t}),\qquad
(r_t,a_t)\sim p_\theta(\cdot\mid h_t).
$$

$r_t$ 是内部推理或动作前文本, $a_t$ 是结构化工具调用, $o_t$ 是环境返回. observation 可能包含另一种语言、乱码、HTML、代码和错误日志. 模型需要从混杂输入中提取证据, 同时让动作满足 schema, 最终答案回到用户语言. 这里要按区段角色控制语言: observation 保留证据原貌, 动作服从工具协议, 最终答案跟随用户语言.

工具调用训练会强化特殊格式与动作选择. 若奖励只看任务最终成功, 模型可以采用任何能成功的查询语言; 若又加入回答语言奖励, 两个信号可能分别作用于轨迹不同位置. 最合理的目标是对最终答案、搜索查询、代码标识符和引用设不同规则. Terminus 没有披露奖励拆分, 公开结果只能显示最终系统在若干任务上的平衡点发生变化.

思考长度也会影响语言漂移. 轨迹越长, 至少一次无意切换或异常字符的机会越高; 但更长思考也可能提高复杂任务正确率. 若修订通过压缩冗余轨迹降低错误暴露, Agent 可能更稳定且延迟更低; 若通过更强语言约束实现, token 数未必改变. 页面没有长度、延迟和工具步数, 两种解释无法区分.

### 2.7. 一致性指标怎样避免误判

可以先把输出切成自然语言、代码、公式、引用和工具参数五类 span, 只在自然语言 span 上判断叙述语言. 对代码注释还要单独处理, 因为标识符应保留, 注释可能需要跟随用户语言. 这种 span-aware 指标比字符比例更接近产品体验. 自动切分仍会在 Markdown 嵌套、未闭合围栏和行内公式上出错, 所以需要人工抽查.

序列指标可以同时报告切换次数与切换长度. 一次保留英文 API 名不应与连续三段英文同权. 设不合理切换片段集合为 $B$, 每段长度为 $|b|$, 可以报告每千 token 切换数和异常覆盖率:

$$
r_{\text{switch}}=\frac{|B|}{T/1000},\qquad
r_{\text{cover}}=\frac{\sum_{b\in B}|b|}{T}.
$$

前者反映频率, 后者反映损害范围. 一个版本可能减少次数却留下更长切换, 单一指标会漏掉差异.

异常字符应按上下文合法性判断. 无法归属语言、代码、公式或引用的孤立字符属于高风险候选, 还要看它是否破坏解析. 可分别统计 raw occurrence、JSON/代码解析失败和人工确认的语义异常. 官方没有公布任何一项, 所以 Terminus 的声明只能被复述为现象改善, 不能补写具体百分比.

测试集还要控制提示语言难度. 纯中文问答最容易保持中文, 中英混合资料总结、跨语言检索和技术代码解释更容易切换. 若新版本只在简单集下降, 不能保证真实 Agent observation 下同样稳定. 这也是为什么语言指标应该与工具轨迹联合测试, 而非只跑短聊天.

## 3. 无工具推理成绩的结构

### 3.1. 六项结果并非同一量纲

无工具组为 MMLU-Pro 84.8 → 85.0, GPQA-Diamond 80.1 → 80.7, HLE 15.9 → 21.7, LiveCodeBench 74.8 → 74.9, Codeforces 2091 → 2046, Aider-Polyglot 76.3 → 76.1. 前五项变化分别是 +0.2, +0.6, +5.8, +0.1 与 -45 Elo, 最后一项是 -0.2. Codeforces 使用 Elo 类分值, 不能与百分制项目直接比较绝对差.

MMLU-Pro 与 GPQA-Diamond 主要测知识和推理, LiveCodeBench 与 Codeforces 偏代码生成, Aider-Polyglot 偏多语言代码编辑. HLE 覆盖多学科高难问题. Terminus 的最大增量落在 HLE, 而代码组基本持平或小幅回落, 说明修订没有形成所有任务共振的统一提升. 页面没有任务级消融, 不能判断这种差异来自数据选择还是优化取舍.

GPQA-Diamond 约 198 题, 单题对应约 0.5 个百分点. 80.1 到 80.7 接近多答对一题的量级, 还取决于是否多次采样取平均. MMLU-Pro 的 0.2 分与 LiveCodeBench 的 0.1 分也需要结合方差读取. 官方没有给采样次数, 温度和置信区间, 因而这些小差值更适合表述为「基本持平」.

### 3.2. HLE 的 5.8 分增量意味着什么

HLE 从 15.9 升至 21.7, 绝对增加 5.8 分, 相对增幅约 36.5%. 在同一表的无工具协议下, 这是明确的大幅变化. HLE 包含跨学科高难问题, 分数提高说明 Terminus 在该评测所需的知识调用与推理链上更有效, 但不能由一项综合分数定位具体学科.

V3.1 另一份发布表曾给出 HLE 29.8, 该数字属于搜索 Agent, 允许调用工具. Terminus 页的 21.7 明确属于 `w/o tool use`. 两个数字的差异展示了工具检索对成绩的贡献, 也说明版本比较必须锁定协议. 若把 29.8 当作 V3.1 闭卷分数, 会错误得出 Terminus 大幅退步的结论.

Terminus 页面没有给带工具 HLE 的新成绩, 所以不能判断闭卷增量是否会传递到搜索 Agent. 工具场景还受查询生成, 页面选择和答案引用影响. 闭卷推理更强可以改善中间判断, 但最终成绩仍取决于 Agent 轨迹训练与执行框架.

HLE 的总分聚合不同学科和题型. 如果增量集中在少数学科, 21.7 的总体分数无法展示分布; 如果来自拒答减少, 又与推理步骤本身不同. 官方没有逐科成绩, 错误类型和回答长度. 因而该分数适合说明综合高难闭卷任务明显提高, 不适合声明所有学科均提高 5.8 分.

与 GPQA-Diamond 的小幅上涨结合读取时, Terminus 并非在所有科学问答上获得同幅增益. GPQA 只增加 0.6 分, HLE 增加 5.8 分. 两个题集的知识范围, 难度和评分协议不同, 差异可能来自数据覆盖或推理策略. 缺少题级结果时, 不能进一步选择其中一种解释.

### 3.3. 代码指标揭示了修订代价

LiveCodeBench 74.8 → 74.9 基本持平, Codeforces 2091 → 2046 下降 45, Aider-Polyglot 76.3 → 76.1 小幅下降. 这组结果说明语言一致性与 HLE 增益没有免费覆盖所有代码能力. 共享参数上的后训练修订可能改变输出风格, 搜索策略和解题长度, 任何一项都可能影响代码评测, 但页面没有提供因果分解.

Codeforces Elo 对题目集与比赛模拟设置敏感, 45 分是否显著需要重复运行和区间. Aider-Polyglot 的 0.2 分更可能处于小波动范围. 可靠结论是代码无工具组没有明显提升, 而不是「代码能力全面下降」. 代码 Agent 组反而在 SWE 与终端任务上涨, 表明裸代码生成和环境内执行需要分开评价.

### 3.4. 从有限分数估计证据强度

若评测包含 $n$ 道独立二元题, 观测正确率为 $\hat p$, 标准误差近似为:

$$
\operatorname{SE}(\hat p)=\sqrt{\frac{\hat p(1-\hat p)}{n}}.
$$

这个近似至少提醒读者: 题数越少, 小数点后一位越不稳定. GPQA-Diamond 题量较小, 0.6 分差距接近一题; SWE Verified 的 500 个实例中, 2.4 分约为 12 个任务. 题目又不完全独立, 同一种知识缺口可能同时影响多题, 真实不确定性未必满足简单二项分布.

生成评测还叠加采样方差. 同一提示在非零温度下可能得到不同答案, pass@$k$ 与单次准确率也不是同一指标. 若官方只给最终点估计, 可以比较大幅变化的方向, 不能替每个小差值补出统计显著性. MMLU-Pro 的 +0.2、LiveCodeBench 的 +0.1 和 Aider 的 -0.2 应放在近似持平组, HLE、BrowseComp 与 Terminal-Bench 的变化更值得解释.

动态 benchmark 还有时间变量. BrowseComp 依赖网页与搜索后端, SWE 环境依赖仓库快照和脚手架, Codeforces 模拟受题集与评分映射影响. 两版若未在同一时间、同一工具和同一预算下配对运行, 差值包含环境项. 可把观测分数写成:

$$
S=M+E+I+\varepsilon,
$$

其中 $M$ 是模型贡献, $E$ 是评测环境, $I$ 是模型与环境交互, $\varepsilon$ 是采样与测量波动. 只看到一个 $S$ 无法唯一解出 $M$. 官方表适合描述产品版本结果, 架构或训练归因需要更严格控制.

### 3.5. HLE 增益有哪些竞争解释

HLE 增益可能来自知识覆盖、推理策略、答案校准、拒答行为或输出格式. 例如模型原先知道答案却在长推理中自我推翻, 后训练减少这种轨迹也会提高分数; 模型减少不必要拒答同样能增加尝试数; 若评分器要求简洁答案, 格式改进也可能带来收益. 综合分数没有给题级日志, 这些因素都不能单独确认.

与 GPQA 基本持平形成约束: 若存在覆盖所有科学推理题的普遍推理升级, 两项通常应更一致地上涨. HLE 的知识领域更广、题目更难, 也可能更依赖长链推理和答案校准. 差异提示改进具有任务分布选择性, 还不足以锁定选择性来自训练数据还是评测格式.

后续 V3.2-Exp 官方表再次使用 Terminus 的 21.7 作为基线, 说明这个数字在 DeepSeek 自己的版本谱系中是稳定参照. V3.2-Exp 对齐训练配置以测试稀疏注意力, HLE 为 19.8, 也表明同架构效率实验仍会在单项上波动. 「总体相当」与「每项完全相等」从来不是同一个命题.

### 3.6. 无工具代码与代码 Agent 的能力分解

单题代码生成可以抽象为从题面 $x$ 直接生成程序 $c$, 得分取决于隐藏测试 $T(c)$. 代码 Agent 则形成多步闭环:

$$
x\rightarrow c_0\rightarrow e_0\rightarrow c_1\rightarrow e_1\rightarrow\cdots\rightarrow c_k,
$$

$e_i$ 是编译器、测试或仓库搜索返回的反馈. 即使初稿 $c_0$ 的质量不变, 更会读错误、定位文件和修补局部差异也能提高最终成功率. Terminus 的 LiveCodeBench 基本不变而 SWE、Terminal 上涨, 与闭环策略改善相容.

闭环能力包含动作格式、状态跟踪和停止决策. 工具名或 JSON 参数出错会让轨迹在执行前失败; 忘记先前错误会重复无效动作; 修改成功后继续折腾又可能破坏已有结果. 语言异常字符对命令和补丁也有更高破坏性. Terminus 同时修订格式稳定与 Agent 行为, 可以共同提高轨迹成功率, 但官方没有轨迹级错误分类来分配贡献.

Codeforces Elo 回落还可能来自策略长度或题型取舍. 环境 Agent 训练鼓励先查看、测试、修复, 竞赛评测通常要求一次性给出完整解法. 同一后训练若提高谨慎探索倾向, 未必适合固定 token 预算的竞赛协议. 这只是可检验假设; 要验证需要比较解题长度、编译错误、超时和算法错误比例.

## 4. Agent 成绩的收益与回退

Agent 评测总体上涨,但搜索能力的提升没有表现出跨语言一致性.

### 4.1. 代码 Agent 提升发生在环境交互

SWE Verified 从 66.0 升到 68.4, SWE-bench Multilingual 从 54.5 升到 57.8, Terminal-Bench 从 31.3 升到 36.7. 在 SWE Verified 的 500 个问题上, 2.4 分约对应多解决 12 个问题. 多语言子集增加 3.3 分, 终端任务增加 5.4 分, 三项方向一致.

SWE-bench 的最终结果由定位文件, 编辑补丁, 运行测试和根据失败反馈修正共同决定. Terminal-Bench 则要求在命令行环境持续执行动作. 这些任务与 LiveCodeBench 的单次生成不同. Terminus 在 Agent 组提升, 同时 LiveCodeBench 近乎持平, 支持「改进集中在多步工具使用」的描述.

三项结果还覆盖不同的失败层. SWE Verified 主要受仓库理解和补丁正确性影响; SWE-bench Multilingual额外加入非英语需求理解; Terminal-Bench 对命令选择, 环境状态和错误恢复更敏感. 三项同时上涨, 比单一 benchmark 的提高更能支持工具行为得到改善. 但它们仍共享 Agent 框架这一外部变量, 不能进一步推出具体训练数据类型.

按绝对增量看, Terminal-Bench 的 5.4 分最大. V3.1 已从 V3-0324 的 13.3 提高到 31.3, Terminus 又到 36.7, 说明这条权重线连续把优化重心放在环境内执行. 该趋势与无工具 Codeforces 回落并不冲突: 前者奖励完整任务成功, 后者更接近单题代码推理. 一个模型可以更会使用测试反馈, 同时在固定竞赛题协议下没有提高.

Agent 分数仍然是模型与脚手架的系统结果. 页面没有说明最大步数, 命令超时, 测试重试和上下文压缩策略. 若 Terminus 与 V3.1 使用相同框架, 差值可归到权重版本; 页面虽沿用旧基线, 却没有明确写出框架完全一致. 第三方复现应固定框架和预算, 再比较两个权重.

### 4.2. 英文 BrowseComp 上涨, 中文版本回落

BrowseComp 从 30.0 升到 38.5, 绝对增加 8.5 分, 相对增幅约 28.3%. BrowseComp-zh 则从 49.2 降到 45.0, 回落 4.2 分. 两项任务都强调多步浏览, 方向却相反, 是整张表中最需要保留的反例.

语言一致性修复可能改变查询语言和页面选择, 但这种联系没有官方证据. 英文和中文版本也可能在题目, 搜索索引, 页面可用性与评测时间上存在差异. 因而不能把中文回落直接归因于语言奖励. 可以确认的是 Terminus 的 Search Agent 增益不具有跨语言一致性.

SimpleQA 从 93.4 升到 96.8, 增加 3.4 分. SimpleQA 更接近短事实问答, 高分区间的提升说明事实检索或答案约束有所改善. 它与 BrowseComp 的多轮搜索难度不同, 两者一起上涨不能证明使用了同一种改进. 页面没有按错误类型拆分, 也没有给引用正确性或检索轮数.

搜索任务的最终分数由查询生成, 文档获取, 证据选择和答案生成串联得到. BrowseComp 更依赖前几步反复迭代, SimpleQA 更容易在较短路径内完成. 英文 BrowseComp 增加 8.5 分说明长路径成功率提高, SimpleQA 增加 3.4 分则说明短路径没有因此退化. 中文 BrowseComp 的相反结果提醒读者, 这种改进没有覆盖所有检索分布.

若搜索后端在两个版本评测之间发生索引更新, 页面内容变化也会影响结果. 官方沿用 V3.1 的旧分数, 却没有给两版是否同日运行的信息. 因而对动态网页任务, 权重差异与环境时间差可能同时存在. 这不会抹去官方对照表, 但第三方重跑时不应期待逐项精确复现.

### 4.3. Agent 表应怎样用于版本选择

如果任务以真实仓库修复和终端操作为主, Terminus 的三项代码 Agent 分数都优于 V3.1, 版本选择有一致依据. 如果任务以中文深度搜索为主, BrowseComp-zh 的回落要求单独回归, 不能由英文 BrowseComp 的上涨替代. 如果任务主要是闭卷代码生成, 两版差距很小, 还应比较延迟, 输出稳定性和实际代码库测试.

版本选择不能只看十二项平均. 这些指标量纲不同, 直接求平均会让 Codeforces Elo 与百分制混在一起. 更合理的做法是按应用路径选择对应组, 固定工具框架与预算, 再用自有失败样本测语言混杂, 结构化输出和随机字符. 官方表给出候选方向, 应用侧回归决定迁移风险.

### 4.4. 工具调用是一种受约束的动作生成

把工具调用仅理解为「模型会输出函数名」会低估难度. 在状态 $s_t$ 下, 模型要先判断是否需要工具, 再从工具集合选择动作 $a_t$, 生成满足 schema 的参数, 接收 observation 后更新状态. 一条轨迹的成功概率近似受每一步共同限制:

$$
P(\text{success})=\prod_{t=1}^{K}
P(a_t\ \text{valid}\mid s_t)\,
P(s_{t+1}\ \text{useful}\mid s_t,a_t,o_t).
$$

这个乘积并不假设步骤独立, 它只强调长轨迹会放大局部失败. 单步合法率从 0.97 提到 0.99, 十步全部合法的近似概率会从 $0.97^{10}\approx0.74$ 提到 $0.99^{10}\approx0.90$. 因而异常字符与格式错误的微小下降, 可能在 Terminal-Bench 这类长任务上形成明显最终增益.

动作有效还分语法、类型与语义三层. JSON 能解析属于语法有效; 参数字段和类型满足工具定义属于类型有效; 查询词、路径和命令能推进任务才是语义有效. 语言一致性主要约束自然语言区段, 随机字符可能破坏前两层, Agent 后训练则更可能影响第三层与状态更新. 公开分数把三层压成最终成功率, 无法确认 Terminus 主要修复了哪一层.

工具选择还存在机会成本. 不调用工具可能凭参数记忆答对, 调用工具会增加延迟和失败点; 过早停止会漏证据, 过度搜索会耗尽步数. 理想策略最大化预期收益:

$$
a_t^*=\arg\max_a\left[
\mathbb{E}(R\mid s_t,a)-\lambda_c C(a)-\lambda_l L(a)
\right],
$$

$C(a)$ 表示工具费用或失败风险, $L(a)$ 表示延迟与 token 开销. Benchmark 往往固定最大步数, 隐式给了成本上限. Terminus 没有公布平均调用次数, 因而无法判断上涨来自更高单步质量, 还是用更多步骤换来成功.

### 4.5. observation 如何改变后续推理

工具返回并非干净事实. 搜索结果含摘要、广告、重复页面和相互冲突的信息; 终端返回命令回显、警告、堆栈与截断输出; 代码仓库包含测试、生成文件和陈旧注释. 模型需要判断 observation 中哪些部分改变当前假设, 哪些只是噪声. 如果把整段输出无差别复制进后续思考, 上下文迅速膨胀, 语言和格式分布也会被环境牵走.

有效的状态更新可以写成压缩映射:

$$
z_{t+1}=g_\theta(z_t,a_t,o_t),
$$

$z_t$ 保存当前目标、已验证事实、未决假设和下一步约束. 压缩太强会丢失文件路径、错误行号或证据出处; 太弱会让无关日志占据注意力. Terminus 的 Agent 分数提高可能涉及更好的 observation 利用, 但没有中间轨迹与上下文长度统计, 所以只能把它列为能力分解, 不能当作已披露模块.

语言一致性在 observation 边界尤其微妙. 中文用户请求可能得到英文文档、英文编译错误和代码标识符. 模型应保留证据原文中的精确符号, 在推理摘要和最终回答中回到中文. 若简单模仿最近 observation 的语言, 回答会漂移; 若强行翻译所有内容, 命令与标识符会损坏. 真正稳定的行为是按区段角色控制语言, 这比全序列单一语言分类更难.

长 observation 还可能携带提示注入文本. Benchmark 未必覆盖真实网页中的恶意指令, Search Agent 分数上涨也不能推出安全边界扩大. 模型需要区分用户指令、系统约束、工具数据和数据中的伪指令. Terminus 发布页只谈性能, 没有给安全或注入评测. 因此实际部署要把工具内容视为低信任数据, 不能让语言稳定的表象代替权限隔离.

### 4.6. Search Agent 的四个误差源

搜索任务可以分成问题分解、查询生成、证据筛选与答案合成. 设四步成功概率分别为 $p_d,p_q,p_e,p_a$, 粗略的端到端成功率受乘积 $p_dp_qp_ep_a$ 限制. BrowseComp 的长链题通常需要多轮重复这四步, SimpleQA 往往在较少轮次内完成. 因此 BrowseComp 对策略、记忆和恢复更敏感, SimpleQA 更接近事实定位与简短答案约束.

问题分解失败时, 模型会搜索一个过宽问题, 得到大量相关却不能作答的页面. 查询生成失败包括语言选择不合适、实体歧义和时间条件丢失. 证据筛选失败会把搜索摘要当完整证据, 或忽略来源冲突. 答案合成失败则可能在已找到正确页面后抄错数字、漏单位或改变实体. 最终分数无法指出错误落在哪一步, 轨迹评审才可以.

BrowseComp 英文上涨 8.5 分而中文版本回落 4.2 分, 至少排除了「所有搜索子能力都同方向提高」这种强结论. 一种可能是查询语言策略变化, 另一种可能是中文题集、搜索索引或页面可用性不同, 还可能是两次评测环境不一致. 若要区分, 可以固定题目与搜索快照, 记录每轮查询语言、命中文档、引用证据和最终错误类型. 官方没有公开这套轨迹.

SimpleQA 位于 90 分以上高分区间, 从 93.4 到 96.8 意味着剩余错误比例从 6.6 降到 3.2, 约减少一半. 这个相对错误下降很显眼, 但仍需题量和运行协议才能给出区间. 高分还可能受答案规范化器影响, 例如别名、大小写和数字格式. 把它与 BrowseComp 一起看, 可以说英文事实检索与长链浏览都提高, 无法确认两者共享同一机制.

### 4.7. Code Agent 的闭环为什么重要

SWE 类任务的第一步通常是定位. 模型从问题描述中提取症状与预期行为, 搜索相关文件、符号和测试. 定位错了, 后续补丁即使语法正确也无效. 第二步是形成故障假设, 解释哪个状态或边界导致失败. 第三步修改最小范围并运行针对性测试. 第四步根据新错误修正假设, 最后跑更广回归. 这条闭环要求模型跨多轮维持因果链.

单次生成 benchmark 主要观察最后的代码片段, SWE Verified 还观察仓库状态变化. 模型可能第一次补丁不完美, 但通过测试输出恢复; 也可能第一次答案看似漂亮, 实际从未运行而失败. Terminus 在 LiveCodeBench 持平、SWE Verified 上涨 2.4 分, 说明提升至少没有表现为普遍更强的首轮算法生成. 更贴近数据的说法是完整仓库任务成功率提高.

Terminal-Bench 更进一步, 动作不一定是写代码, 还可能安装依赖、处理文件、启动服务或查询系统状态. 终端是有状态环境: 当前目录、环境变量、后台进程和上一步生成的文件都会影响下一步. 模型若忘记状态, 会重复命令或在错误目录操作. 从 31.3 到 36.7 的增量与状态型工具能力改善相容, 页面没有给失败轨迹来确定具体来源.

多语言 SWE 上涨 3.3 分与语言一致性修订的关系也要谨慎. 理解非英语 issue 与最终补丁正确是两个环节, 语言更稳定可能减少需求误读, 代码库本身仍多为英文标识符. 若过度翻译标识符反而会失败. 三项 Code Agent 同向上涨构成一致系统信号, 还不足以把增益归因到语言目标.

### 4.8. 预算与停止策略

Agent 成功率随工具预算增加通常先上升后饱和, 过长轨迹还可能因错误累积而下降. 设最大步数为 $K$, 成功概率为 $P_K$, 平均成本为 $C_K$, 应用真正关心的是一条成本约束下的曲线, 不能只看某个 $K$ 上的单点. 两版若使用不同步数或 token 上限, 更高分可能来自更多计算.

停止决策包括成功停止、失败止损和请求更多信息. 代码测试全绿后应停止, 搜索证据充分后应作答; 连续查询没有新信息时应换策略或结束. 模型若倾向继续思考, 可能耗尽预算; 若过早自信, 会留下未验证错误. Terminus 页面没有平均步数、token、延迟和工具失败率, 因而无法评估效率是否与分数同步改善.

思考模式与工具预算还会竞争上下文. 每一步长 CoT 占用 token, observation 也占用 token, 128K 窗口并不等于所有内容都能有效利用. 长任务可能需要压缩旧 observation 或丢弃隐藏推理. V3.1 的多轮模板会移除旧推理文本, 这有助于控制上下文, 也意味着状态必须通过可见消息或内部摘要延续. Terminus 没有宣布模板变化, 该约束仍应视为部署前提.

实际对比可以报告成功率随预算的曲线. 若 Terminus 在相同步数下更高, 且达到同一成功率所需步骤更少, 才能同时说明效果与效率改善. 若只在更大预算下上涨, 迁移价值取决于成本. 官方的十二项表没有这条轴, 所以「更强 Agent」应按给定评测设置理解.

### 4.9. 错误恢复为何可能贡献大于首步提升

长任务中, 首个动作完全正确并非常态. 搜索会遇到无结果查询, 终端会出现缺依赖或权限错误, 补丁会让测试暴露新的边界. 成熟 Agent 的优势经常体现为错误后能否更新假设. 设每步初次成功概率为 $p$, 失败后恢复概率为 $r$, 允许一次恢复时单环节通过率可近似为:

$$
p+(1-p)r.
$$

当 $p=0.7$、$r$ 从 0.3 提到 0.6, 通过率从 0.79 提到 0.88. 即使首步能力不变, 恢复策略也能显著改善端到端任务. LiveCodeBench 近乎持平而 Terminal-Bench 上涨, 正好使这类解释成为值得验证的候选.

恢复要求读取错误的结构. 编译错误包含文件、行号与类型, 测试失败包含预期和实际值, 搜索无结果暗示查询过窄或实体错误. 模型若只把错误当作「再试一次」信号, 会重复近似动作; 有效恢复会定位失败假设并改变策略. 轨迹数据若包含失败到修正的完整过程, 能直接监督这种映射. Terminus 没有披露轨迹数据, 所以不能确认训练来源.

恢复还要防止破坏已完成部分. 修改一个测试失败时, 新补丁可能让原来通过的测试回归; 搜索找到一条新证据时, 可能与已有证据冲突. Agent 需要维护约束集合, 每次动作后重新验证关键条件. Terminal-Bench 的状态任务尤其如此, 一个不可逆命令会让后续无从恢复. Benchmark 沙箱降低外部损失, 不代表模型获得事务语义.

可以用轨迹级指标区分首步与恢复: first-action validity、首次测试通过率、错误后策略改变率、重复无效动作率、最终成功前工具数. 如果 Terminus 的主要变化来自恢复, 应看到首步近似不变而错误后成功率提高. 官方只给最终分数, 留下了这个归因空缺.

## 5. 可确认结论与资料边界

### 5.1. 从 V3.1 到 Terminus 的变化

Terminus 没有宣布新网络结构, 公开定位是 V3.1 的修订版. 官方明确提出三类结果: 中英文混杂减少, 随机字符消失, Code Agent 与 Search Agent 能力加强. 表格支持代码 Agent 三项上涨, 搜索组则是英文 BrowseComp 与 SimpleQA 上涨, 中文 BrowseComp 回落. 无工具组最大的增量来自 HLE.

这些变化符合后训练调整的外观, 但具体训练方法没有披露. 页面没有说明数据规模, 轨迹来源, SFT 或强化学习阶段, 奖励设计和 CoT 压缩是否继续变化. 因而可靠描述应停留在可观察行为与结果, 不把某个常见算法写成 Terminus 的事实.

Terminus 也不是 V3.2-Exp 的架构更新. 后续 V3.2-Exp 才公开引入 DeepSeek Sparse Attention. 比较稀疏注意力的收益时, 应优先用 Terminus 作为前序行为基线, 避免把 Terminus 已取得的 Agent 与 HLE 增量计入注意力改动.

### 5.2. 公开材料无法回答的问题

语言一致性没有直接指标, 随机字符没有测试集合和故障率. 十二项 benchmark 衡量知识, 推理, 代码与工具任务, 不直接测两条发布主张. 因而「混杂减少」与「随机字符消失」目前是官方定性结果, 无法从表格复算.

评测协议也不完整. 无工具组缺少采样次数, 温度, 最大生成长度与置信区间; Agent 组缺少框架, 工具实现, 最大步数和失败重试. 这些信息不足不会使表格失效, 但限制跨机构比较和因果解释. 小数点后一位的微小变化应谨慎读取, 5 分以上且方向稳定的变化更有版本判断价值.

部署层没有新的价格, 路由名与模板说明. App, Web, API 已上线, 开源权重位于 `deepseek-ai/DeepSeek-V3.1-Terminus`. 实际部署仍需以仓库配置和 V3.1 文档为准, 分别验证双模式, tokenizer, UE8M0, 工具 schema 与多轮历史处理. 权重更新改善模型分布, 但不会自动修复调用栈中的模板错配.

迁移测试应保留 V3.1 与 Terminus 的同一批输入, 同一解码参数和同一工具环境. 纯文本集合测目标语言保持, 长回答尾部与特殊字符; 结构化集合测 JSON Schema, 函数名和参数类型; Agent 集合测工具失败后的恢复以及最大步数内的成功率. 固定外部变量后, 才能把变化归到权重版本.

线上监控也应把能力失败与格式失败分开. 答案错误, 工具选择错误, JSON 无法解析, 语言无故切换和随机字符属于不同故障类. 若只记录最终成功率, Terminus 声称修复的输出问题会被任务难度掩盖. 页面没有给官方分类标准, 应用侧可以依据自身协议定义, 但不能把内部统计写成官方数字.

Terminus 的资料边界很明确: 两页内容支持版本定位, 输出问题描述和十二项结果对照, 不支持训练复现. 在这个范围内, 可靠的版本判断是代码 Agent 与英文搜索取得较大增量, HLE 闭卷推理明显提高, 中文 BrowseComp 和两项代码指标存在回退, 语言一致性改善仍缺少公开定量指标.

### 5.3. 后训练目标可能形成怎样的张力

可以用多目标优化理解 Terminus 的行为外观. 设基础语言模型损失为 $\mathcal{L}_{\text{LM}}$, 推理任务损失为 $\mathcal{L}_{\text{reason}}$, 工具轨迹损失为 $\mathcal{L}_{\text{tool}}$, 语言与格式约束为 $\mathcal{L}_{\text{format}}$, 一个抽象目标是:

$$
\mathcal{L}=\lambda_0\mathcal{L}_{\text{LM}}
+\lambda_1\mathcal{L}_{\text{reason}}
+\lambda_2\mathcal{L}_{\text{tool}}
+\lambda_3\mathcal{L}_{\text{format}}.
$$

这不是官方训练公式, 作用是展示共享权重下的目标关系. 不同损失的梯度若方向接近, 一次更新可同时改善多个目标; 若夹角为负, 提高一个权重会伤害另一个目标. Terminus 表里 HLE、Code Agent 和英文搜索上涨, Codeforces、Aider 与中文搜索没有同步上涨, 与多目标重新平衡的外观一致. 仅凭结果无法反推出各 $\lambda_i$ 或具体训练算法.

格式稳定与工具成功通常存在正迁移. 合法 JSON、准确工具名和干净字符会减少执行层拒绝, 这类更新也可能改善普通结构化回答. 语言一致与跨语言搜索则可能存在条件冲突: 最终叙述应维持用户语言, 查询和证据却可能需要切换. 若训练没有区分区段角色, 统一语言偏好可能压缩有效探索. BrowseComp-zh 的回落使这个问题值得测试, 不能据此确认已经发生梯度冲突.

推理深度与效率也可能冲突. 更长轨迹为难题提供更多搜索空间, 同时提高语言漂移、字符异常和工具预算耗尽的概率. V3.1 相对 R1-0528 的卖点之一是思考效率, Terminus 又强调稳定性. 若训练偏好简洁且成功的轨迹, HLE 与 Agent 可能同时受益; 若压缩过度, 某些竞赛代码题可能受损. 官方没有输出长度分布, 这条机制只能通过配对轨迹验证.

### 5.4. 因果归因至少需要哪些对照

要把语言改善归因于某类数据, 最小实验应固定 V3.1 checkpoint, 只加入目标数据或奖励形成一个变体, 再在相同提示、seed 和解码器上比较混杂率. 要把 Agent 提升归因于轨迹训练, 需要保持语言与格式数据不变, 单独改变工具轨迹. 若多个目标一起更新, 只能得到组合效果. Terminus 没有公开消融矩阵, 所以发布结果只能支持组合 checkpoint 的效果.

模型与脚手架也需做二乘二对照. 设旧模型为 $M_0$, 新模型为 $M_1$, 旧框架为 $H_0$, 新框架为 $H_1$, 至少比较 $(M_0,H_0)$、$(M_1,H_0)$、$(M_0,H_1)$ 和 $(M_1,H_1)$. 只有前两项差异能在固定框架下估计 checkpoint 效果, 后两项估计框架效果, 剩余差异体现交互. 官方表展示 V3.1 与 Terminus, 却没有明确说明所有 Agent 外部条件是否完全相同.

动态网页任务还需要冻结时间. 可以保存搜索结果、网页快照或使用固定检索语料, 让两版看到相同 evidence. 否则网页变化会进入处理效应. 真实在线搜索评测当然有产品价值, 但它回答的是「当时整套系统表现如何」, 与「权重机制变化为何」是两个问题.

语言与异常字符的测试还应盲化版本. 评审者若知道样本来自修订版, 可能更愿意把技术术语视为合理切换. 可以随机打乱两版输出, 按同一 rubric 标注无理由换语种、异常字符、标识符破坏和最终答案语言. 多标注者一致率能说明规则是否清楚. 官方没有此类数据, 应用侧可以用它判断迁移是否符合自己的语言边界.

### 5.5. 反例为什么比平均分更重要

模型更新常以平均成功率汇报, 线上迁移却容易被少数高损失失败决定. 中文 BrowseComp 回落就是现成反例: 英文搜索大幅上涨不能覆盖中文长链检索. Codeforces 与 Aider 的小幅回落则说明代码 Agent 上涨不能直接传播到所有代码任务. 这些结果不否定 Terminus 的整体改进, 它们界定了改进的分布范围.

语言一致性的反例包括合理的代码切换. 用户要求解释一段英文报错时, 回答应保留报错原文; 用户要求生成 SQL 或 Python 时, 代码关键字本来就是英文. 若评价器把这些视为混杂, 分数越高反而越可能损坏技术内容. 另一个反例是跨语言检索: 中文问题对应的权威资料只有英文, 查询切换是必要动作. 一致性目标必须落在叙述层, 不能套到所有 token.

随机字符也要与罕见合法字符区分. 数学符号、Unicode 变量、其他语言的人名和文件内容可能在上下文中合理. 清洗训练数据或惩罚低频字符若过强, 会降低模型处理多语言与专业符号的能力. Terminus 的「异常字符减少」是产品现象, 未提供字符集合, 因而不能把低频字符一概列为错误.

工具行为的反例是无需工具的简单任务. 强化 Agent 可能提高主动调用倾向, 对可以直接回答的问题反而增加延迟和失败点. 另一个反例是工具返回错误或恶意内容, 更愿意相信工具未必更可靠. 所以 Agent 能力应包括正确调用、正确拒绝调用和识别 observation 风险, benchmark 的最终成功率只覆盖其中一部分.

### 5.6. 开源权重与托管 API 的比较边界

官方变更日志明确把 `deepseek-chat` 映射到 Terminus 非思考模式, 把 `deepseek-reasoner` 映射到思考模式. 这个映射说明 API 的模型路由, 不保证开源部署与托管服务逐 token 一致. 托管服务还包含模板、解码默认值、并发批处理、停止条件和工具协议. 开源权重则由用户选择 vLLM、SGLang 或参考推理实现, 每一层都可能改变行为.

模型仓库约 689 GB, 采用 FP8 权重与 UE8M0 缩放. 配置与推理代码属于可核查的架构证据, Hugging Face 自动生成的通用 `pipeline` 示例却不等于官方为完整 MoE 模型保证的最佳部署路径. 比较时应读取仓库自己的 README、配置和参考代码, 确认 tokenizer 与 chat template, 再使用后端对 V3.1 相关特性的支持.

服务端还可能施加安全策略与输出后处理. 若 API 删除某些控制 token、修复不完整 JSON 或限制最大思考长度, 用户看到的稳定性是权重和服务层共同结果. 官方将 App、Web、API 一起升级, 发布声明描述的是产品体验; 开源模型卡没有给一套随机字符率复现脚本. 因此本地部署需要重新跑字符与结构化回归.

后续 V3.2-Exp 发布时, DeepSeek 为比较保留了临时 Terminus API endpoint, 并建议通过响应中的 `model` 字段确认实际版本. 这说明仅靠请求参数名 `deepseek-chat` 不能长期锁定 checkpoint, 因为同一公共别名会随发布更新. 生产回归若没有记录响应版本, 两批流量可能在不知情时比较了不同权重.

### 5.7. 训练假设和推理假设要分开

训练假设关心模型从什么分布学习. Terminus 若要改善语言一致, 数据中需要清晰的目标语言与合理代码切换; 若要改善 Agent, 轨迹需要包含动作、观察、恢复和停止. 奖励或监督信号还要避免只优化格式而忽略任务正确. 这些要求来自机制, 官方没有公布数据规模、生成器、过滤器和训练轮数.

推理假设关心训练后的能力如何被调用. 模式 token 正确、工具 schema 与训练格式相容、observation 被放到预期角色、最大长度足够、停止条件不截断, 都是复现能力的前提. 同一权重在错误模板下可能表现得像语言或 Agent 能力退化. V3.1 的双模式尤其依赖模板控制, Terminus 没有发布新模板并不意味着调用方可以忽略旧要求.

两类假设混淆会产生错误归因. 本地部署出现随机字符, 可能是权重行为, 也可能是 tokenizer、量化转换或采样设置; Agent 低于官方分数, 可能是轨迹能力不足, 也可能是工具返回格式不同. 排查顺序应先验证配置、模板和解码, 再比较任务轨迹. 直接把所有差异归为开源权重弱于 API, 缺少控制变量.

模型量化也可能影响边界 token. UE8M0 描述权重缩放格式, 后端错误处理 scale 或把部分归一化层转成不兼容精度, 会造成远大于正常采样波动的输出变化. 官方仓库配置是部署依据, 社区转换脚本是否忠实需要独立验证. 这属于推理实现正确性, 与 Terminus 的后训练目标不同.

### 5.8. 怎样建立版本回归集

语言回归集应按场景分层. 纯中文与纯英文长回答测叙述稳定, 中英夹杂问题测模型是否跟随用户意图, 代码与数学场景测必要外语是否被保留, 多轮对话测语言是否随历史漂移. 每条样本记录目标语言、允许保留的标识符与不可接受切换, 评价器才能区分合理术语和真实混杂.

字符回归集应包含长尾位置. 开头、长回答尾部、思考结束边界、Markdown 围栏、JSON 字符串、函数参数、Unicode 引文和多轮 history 都需要覆盖. 指标可分为异常字符率、结构解析失败率和语义破坏率. 一个孤立字符未必改变答案, 插进命令或字段名则属于高损失故障, 两者不能只按字符计数合并.

Agent 回归集要保存环境快照. 代码任务固定仓库提交、依赖、测试和网络权限; 搜索任务尽可能固定证据库或记录网页快照; 终端任务记录初始文件系统和可用命令. 每次运行保存完整动作轨迹、tool error、token、步数和墙钟时间. 只保存最终 pass/fail, 无法判断新版本把错误从哪一层移到了哪一层.

统计上应使用配对样本. 同一任务分别运行 V3.1 与 Terminus, 记录「旧错新对」「旧对新错」而非只看两个总分. 净提升可能由大量相互抵消的翻转组成. 若 100 个任务中有 15 个旧错新对、10 个旧对新错, 总分只上升 5, 迁移仍引入了 10 个回归. 对高价值场景, 这 10 个反例比平均增量更值得人工检查.

多次采样时, 应固定 seed 集合并报告任务级成功概率. 对每题运行 $k$ 次, 可观察稳定成功、稳定失败和对采样敏感三类. Terminus 所称「更稳定」若成立, 可能表现为同题方差下降, 即结果更集中; 单次分数无法展示这一点. 线上低温推理也会受并发后端和浮点实现影响, 配对实验仍要记录完整环境.

### 5.9. 工具协议中的状态机

一个可靠的工具循环至少包含等待模型、校验动作、执行工具、接收观察、继续生成和结束六种状态. 模型输出工具调用后, 调用方要验证工具名、参数模式与权限; 执行失败时, 错误应作为 observation 返回, 让模型决定修正或停止; 最终答案只能在没有待处理工具调用时发布. 如果服务端把半个 JSON 当文本返回, 或把工具错误吞掉, checkpoint 再强也无法完成闭环.

多工具并行还会引入 observation 顺序. 两个搜索请求同时发出, 返回次序可能与调用次序不同. 若模型依赖位置而没有稳定 call id, 证据会错配. 串行执行更简单, 延迟更高. Terminus 的 benchmark 页面没有工具协议细节, 因而 Agent 分数默认包含官方评测框架对状态机的正确实现.

幂等性同样重要. 搜索和读文件通常可安全重试, 写文件、提交表单或执行部署可能产生外部副作用. 模型若因超时看不到成功响应而重试, 同一动作可能执行两次. Agent 训练能学会谨慎, 系统仍要用调用 id、权限与事务约束保护外部状态. Benchmark 多在隔离环境中评分, 不能从代码 Agent 成绩推出生产副作用安全.

上下文压缩必须保留状态机所需信息. 删除旧思考段可以节省 token, 但已执行动作、关键 observation 和尚未满足的目标要继续存在. 若摘要把具体路径、测试名或错误码改写, 后续动作可能偏离. V3.1 模板移除历史推理有明确效率动机, Terminus 的多步提升说明模型在官方设置下仍能完成更多任务, 公开资料没有给出压缩实现和状态丢失率.

### 5.10. 置信度与停止之间的关系

纯问答中, 置信度影响是否直接回答或承认不确定; Agent 中, 它还影响是否继续搜索、是否运行测试和是否接受当前补丁. 若模型过度自信, 会在证据不足时停止; 置信度过低则会重复工具调用. 一个简化停止规则是当额外动作的预期信息增益低于成本时结束:

$$
\mathbb{E}[\Delta U(a_t)\mid s_t] < C(a_t).
$$

实际模型没有显式算出两项, 后训练轨迹会塑造这种行为倾向. Terminal-Bench 和 BrowseComp 的增益可能来自更好的停止与恢复, 也可能来自其他环节, 因为官方没有平均轨迹长度和未完成原因.

语言与格式稳定也会影响自评. 推理轨迹若混入无关语言或异常字符, 可能表明局部状态偏离训练分布, 后续自我校验可靠性下降. 反过来, 表面流畅不保证事实正确, 语言一致不能当置信度代理. 版本回归需要分别记录格式、证据和答案正确, 避免把更干净的表达误判成更高准确率.

拒答率是另一个潜在混杂量. HLE 等难题中, 少拒答会提高尝试覆盖, 也可能增加错误; Search Agent 若更愿意调用工具, 成功与成本同时变化. 发布页没有覆盖率、校准曲线或拒答统计. 因而分数上升不能说明模型置信度更准确, 只能说明在给定评分协议下得到更多得分.

校准可用可靠性图或 Brier score 测量, 前提是模型提供可比较的置信度. 对生成与 Agent, 更实用的信号可能是多次采样一致率、测试通过情况和证据覆盖. Terminus 没有公布这些数据. 应用侧若有高风险决策, 仍应使用外部验证, 不因「更稳定可靠」的发布文案取消验证链.

### 5.11. checkpoint 差异怎样传播到长轨迹

设 V3.1 参数为 $\theta_0$, Terminus 为 $\theta_1=\theta_0+\Delta\theta$. 单步 logits 的变化可在局部近似为:

$$
\Delta z_t\approx J_{\theta}(h_t)\Delta\theta,
$$

$J_{\theta}$ 是当前状态下 logits 对参数的雅可比. 即使 $\Delta\theta$ 相对总参数很小, 它也可能在语言边界、工具 token 或停止 token 上改变排序. 生成一旦选中不同 token, 下一步历史 $h_{t+1}$ 就分叉, 后续不能再用同一个局部线性近似. 长 Agent 轨迹会把早期微小概率变化放大成完全不同的动作序列.

这解释了两个现象. 第一, 架构和参数规模不变仍能产生明显系统差异; Agent 不需要新增模块才能从 31.3 到 36.7. 第二, 单步 token 对数概率接近不代表任务行为接近, 因为工具选择是离散分叉. 对比 checkpoint 时, 除了困惑度或短问答, 还要运行完整闭环.

分叉也使逐 token 对齐不适合作为唯一回归. 两个模型可能用不同搜索词找到同一证据, 或用不同补丁都通过测试. 语义等价应按任务结果、约束与成本评价. 反过来, 两段自然语言看起来相近, 一个函数参数的字符差异就可能让工具失败. 回归指标要按输出区段选择粒度.

参数更新的影响还随提示分布变化. 语言边界附近、多个工具分数接近或模型不确定的状态更容易因小更新翻转; 明确事实问题可能保持不变. 所以版本回归应优先收集旧版曾经混杂、格式失败、循环搜索或错误停止的边界样本. 随机抽普通短问答容易低估修订效果, 也难发现新回归.

### 5.12. 十二项分数为何不能压成总分

各 benchmark 的单位、题数、预算和环境不同. Codeforces 是 Elo 类尺度, 其他多为百分制; 1 分在 500 题的 SWE 与较小 GPQA 上对应不同实例数; BrowseComp 还含动态工具环境. 直接做算术平均既混合量纲, 又默认每项业务价值相同. 即使先标准化, 选择标准差和基准版本也会改变权重.

更合理的汇总从任务画像出发. 设应用权重为 $w_j$, 各指标经过业务相关效用函数 $u_j$ 映射, 总效用写成:

$$
U=\sum_j w_j u_j(S_j)-\lambda C,
$$

$C$ 包含延迟、token、工具调用和部署成本. 代码维护应用可提高 SWE 与 Terminal 权重, 中文研究助手应提高 BrowseComp-zh 与语言回归权重. 官方表没有成本列, 所以任何总分都要补充本地测量.

效用函数通常非线性. 结构化输出成功率从 99% 到 99.9% 对大规模自动化价值很高, 知识问答从 85.0 到 85.2 未必可感知; 某项低于安全阈值时, 其他指标再高也不能上线. 中文搜索从 49.2 降到 45.0 对该场景可能是硬回归, 不应被英文上涨平均掉.

还要报告翻转矩阵. 对每个任务记录旧版与新版的成败组合, 可以算净增益, 也能列出回归集合. 若总体上涨来自一些任务改善和另一些任务退化, 回归集合能指导路由: 特定任务继续用旧版, 其他任务切新版. Terminus 的临时比较 endpoint 曾为这种真实场景对比提供条件, 官方公开表本身没有实例级结果.

### 5.13. 从离线表到线上迁移

线上迁移前先做影子流量. 同一请求分别发送给两版, 不让候选结果产生外部副作用, 记录答案、工具计划、格式和成本. 对搜索可共享冻结证据以减少环境差异; 对写操作只比较计划或在隔离沙箱执行. 影子测试能覆盖真实提示分布, 还不会把未验证 Agent 动作直接作用于生产.

随后按任务分层小流量发布. 纯文本、只读工具与有副作用工具的风险不同, 应分别设闸门. 语言混杂率、JSON 解析率、工具错误率、平均步数、p95 延迟和人工申诉都要观察. 若只监控最终 HTTP 成功, 模型可能已经生成错误参数或改变语言, 服务层却仍返回 200.

回滚必须锁定版本. 公共 `deepseek-chat` 会随官方发布切换 checkpoint, 只保存别名无法保证回到 Terminus. 自托管可保存权重摘要、tokenizer 和镜像; API 使用方至少记录响应 `model` 字段与时间. V3.2-Exp 的比较文档专门提示检查响应版本, 说明这是官方支持的核对方式.

线上数据还要防止评价泄漏. 用户反馈可以帮助找到混杂与异常字符, 直接把包含隐私、工具凭据或错误操作的轨迹回流训练会产生安全与合规问题. 发布页感谢用户反馈, 没有说明训练数据处理. 技术结论只需确认反馈驱动修订的产品叙事, 不能推断具体反馈样本如何进入训练.

最终迁移判断应按失败成本做. Terminus 的代码 Agent 和英文搜索分数提供积极先验, 中文深度搜索需要更强回归, 裸代码任务则没有明显收益证据. 语言和字符稳定对所有自动化都有价值, 但必须在实际模板与后端上复测. 这种分场景结论比一句「新版更好」更接近十二项数据真正支持的范围.

## 6. 一手来源与版本谱系

### 6.1. 发布页能直接证明什么

[DeepSeek-V3.1-Terminus 官方发布页](https://api-docs.deepseek.com/news/news250922/)直接给出三项信息: 更新建立在 V3.1 上; 改善中英文混杂、异常字符与 Code/Search Agent; 附表列出 V3.1 和 Terminus 的十二项分数. [官方更新日志](https://api-docs.deepseek.com/updates/)还给出 2025 年 9 月 22 日日期, 并明确 `deepseek-chat` 对应非思考模式、`deepseek-reasoner` 对应思考模式. 这些内容构成版本定位与产品路由的一手证据.

发布页没有技术报告式的方法章节. 它没有训练数据、损失、强化学习算法、采样预算、消融和误差区间. 所以「后训练行为修订」是由同构配置、官方版本措辞和结果外观共同支持的分类, 不能继续缩小成某一种 SFT 或 RL 配方. 任何关于奖励函数的讨论都只能用于解释可能机制.

中文官方页面对英文 `no more random chars` 的表达是「缓解了……偶发异常字符等情况」, 语气比绝对零故障更克制. 中文表述更适合技术文章: 它确认异常字符减少, 没有承诺所有提示和解码设置下概率严格为零. 两种官方文本一起读, 可以避免把宣传短句扩大成统计保证.

### 6.2. 模型仓库提供了哪些结构证据

[DeepSeek-V3.1-Terminus 模型仓库](https://huggingface.co/deepseek-ai/DeepSeek-V3.1-Terminus)提供配置、tokenizer、163 个 safetensors 分片、参考推理代码和许可证. 配置字段可核对层数、维度、专家数量、MLA 低秩维度、词表和 FP8 缩放格式. 这些文件说明开源 checkpoint 怎样加载与执行, 比发布页更适合判断架构是否变化.

仓库把论文关联到 DeepSeek-V3 技术报告, 没有为 Terminus 提供单独论文. 这与「沿用 V3.1 架构、更新权重行为」一致. 163 个分片与约 689 GB 仓库规模反映分发形态, 不能单独用来推断有效参数或训练计算. MoE 每 token 激活专家数要从配置读取, 不能拿磁盘总权重直接当每 token 计算量.

参考推理实现和 `config_v3.1.json` 是部署核对点. UE8M0 的 scale 格式、归一化层精度和 RoPE 布局如果被第三方转换器错误处理, 输出差异属于实现误差. 模型仓库的存在让这类问题可定位, 但官方没有提供一套跨后端逐 token 一致性测试. 本地部署应先用短提示比对参考实现, 再评估语言和 Agent 行为.

### 6.3. V3.1 是 Terminus 的能力起点

[2025 年 8 月 21 日的 V3.1 更新日志](https://api-docs.deepseek.com/updates/)明确列出混合推理架构、相对 R1-0528 的思考效率和后训练带来的 Agent 改进. Terminus 在一个月后继续沿这条线修订. 因此混合思考和 Agent 并非 Terminus 首次引入, Terminus 的贡献是继续优化已有能力并处理用户反馈.

这一前后关系影响数字解释. SWE Verified 66.0、SWE-bench Multilingual 54.5、Terminal-Bench 31.3 已经是 V3.1 相对更早版本显著提升后的基线. Terminus 再到 68.4、57.8、36.7, 属于成熟能力线上的增量. 若只看 Terminus 页面, 容易把整套 Agent 能力都归给最后一次修订.

V3.1 的混合模式还解释了为何同一 API 别名分成 chat 与 reasoner. 两个入口调用同一权重的不同模式, 评测则只给思考模式无工具组与 Agent 组. 非思考模式保留原有能力是官方定性表述, 没有单独表格. 用户选择 `deepseek-chat` 时, 不能直接套用 HLE 21.7 作为该模式成绩.

### 6.4. V3.2-Exp 如何反向限定 Terminus

[V3.2-Exp 官方发布](https://api-docs.deepseek.com/news/news250929/)明确写明它建立在 V3.1-Terminus 上并加入 DeepSeek Sparse Attention. [官方仓库](https://github.com/deepseek-ai/DeepSeek-V3.2-Exp)又说明训练配置特意与 Terminus 对齐, 目的是评估稀疏注意力的效率与质量. 这让 Terminus 成为架构实验的稠密注意力基线.

V3.2-Exp 表重复了 Terminus 的多个分数, 并增加 AIME 2025 与 HMMT 2025. 两份官方材料中的相同数字彼此吻合, 也显示 DeepSeek 将 Terminus 当作稳定版本参照. V3.2-Exp 各项有涨有跌, 官方仍概括为总体相当, 说明版本比较应看任务分布, 不能要求每列单调.

后续发布还为 Terminus 保留临时比较 endpoint, 文档要求通过响应 `model` 字段确认真实版本. 这一做法揭示 API 别名的时间性: `deepseek-chat` 是产品入口, 底层 checkpoint 会更新. 任何线上 A/B 若只记录请求里的别名, 之后都难以复盘实际版本.

### 6.5. 从证据到结论的最短链条

第一条结论是架构保持. 证据来自 Terminus 仓库配置与 V3.1 推理配置对齐, 发布页没有宣布结构变化, V3.2-Exp 又把 DSA 称为建立在 Terminus 上的新机制. 所以 Terminus 的公开差异应放在 checkpoint 行为层, 不能归因于新增注意力或 MoE 结构.

第二条结论是语言与字符行为改善属于官方定性声明. 中文页面使用「缓解」, 没有测试集与比例. 文章可以描述改善目标和产品反馈, 不能写成可复算的零错误率. 语言机制分析应明确哪些是通用解释, 哪些是官方披露.

第三条结论是 Agent 增益具有任务选择性. 三项代码 Agent 同向上涨, 英文 BrowseComp 与 SimpleQA 上涨, 中文 BrowseComp 回落. 这支持 Code Agent 整体改善和部分 Search Agent 改善, 不支持跨语言搜索全面提升. 无工具代码基本持平或回落又限定了增益更靠近闭环交互.

第四条结论是 HLE 闭卷推理明显上涨, 其余知识与代码无工具指标多数近似持平. 公开数据能确认结果分布, 不能区分知识覆盖、推理策略、拒答和格式贡献. 若把 HLE 单项扩大成全面推理飞跃, 会与 GPQA、MMLU-Pro 和代码列的微小变化冲突.

第五条结论是部署结果依赖调用协议. 模式模板、tokenizer、FP8 scale、工具 schema、历史处理和解码参数都会改变输出. 官方 API 的版本结果不保证任意本地后端自动复现. Terminus 提供了权重和参考配置, 调用方仍要验证自己的执行链.

### 6.6. 来源层级如何约束表述

第一层来源是官方发布页和更新日志, 适合确认日期、版本定位、产品入口、语言与 Agent 改善声明以及表格数字. 第二层是模型仓库, 适合确认配置、权重格式、tokenizer 和参考推理实现. 第三层是前后版本官方材料, 用于建立 V3.1 到 Terminus 再到 V3.2-Exp 的谱系. 三层互相补足, 仍没有 Terminus 独立技术报告.

社区测试可用于发现反例和部署问题, 不能替代官方方法说明. 某个用户遇到异常字符, 只能说明该提示与环境下发生过; 某个后端加载失败, 先要排查转换与精度支持; 某次自测分数超过官方, 还要核对题集和预算. 本文的机制推导因此始终回到公开配置、正式声明和可复算数字.

来源缺失时, 最安全的写法是缩短因果链. 可以说「Terminus 的 HLE 分数提高」, 因为表格直接支持; 可以说「结果与后训练重新平衡相容」, 因为架构一致且行为变化; 不能说「某种奖励让 HLE 提高」, 因为没有消融. 这种约束不会削弱分析, 它让读者知道哪些结论能拿去做版本决策, 哪些只是下一步实验假设.

数字也要保留协议标签. 21.7 是思考模式无工具 HLE, 38.5 是 Agentic Tool Use 下的 BrowseComp, 68.4 是相应脚手架中的 SWE Verified. 去掉标签后, 同名 benchmark 的搜索版、闭卷版或不同预算容易混淆. V3.1 曾出现带工具 HLE 29.8, 正好说明协议标签不是附属信息.

### 6.7. 把 Terminus 放回 DeepSeek 路线

V3.1 先把同一权重的思考与非思考模式、工具调用能力放到主线上, Terminus 随后处理真实用户暴露的语言、字符和 Agent 行为, V3.2-Exp 才进入稀疏注意力架构实验. 三个版本分别强调能力组织、行为收敛和效率结构. 按这个顺序阅读, Terminus 的位置很明确: 它为后续架构实验提供更成熟的稠密基线.

这个位置也解释了官方材料为何短. Terminus 没有新网络结构可展开, 发布价值集中在 checkpoint 行为. 文章若为了篇幅把 MLA、MoE 和 FP8 全部重推, 会掩盖真正变化; 若只复述两页新闻, 又讲不清混合模式、语言和工具为何会互相影响. 合理深度来自把可观察结果放进已有 V3.1 机制, 再逐层写出条件与反例.

对研究者, Terminus 最有价值的是一个同构 checkpoint 对照: 架构几乎固定, 输出稳定、HLE 与 Agent 发生选择性变化. 它提示后训练仍能显著改变长轨迹系统能力, 并且改进不会自动覆盖所有语言与任务. 对部署者, 价值在于清楚的迁移方向和同样清楚的回归点: Code Agent 值得优先试, 中文搜索必须单测, 非思考模式与字符稳定需要自建指标.

最终应保留两个同时成立的判断. Terminus 相对 V3.1 的官方结果确实有多项大幅提升, 尤其 HLE、英文 BrowseComp 和 Terminal-Bench; 它也保留了中文搜索与部分代码指标的回退, 并缺少训练细节与统计区间. 接受前者才能看见版本进步, 保留后者才能避免把一次行为修订写成全面、无条件的能力升级.

如果把整条线压成一个因果图, 起点是 V3.1 的同一权重双模式与工具训练, Terminus 在相同架构上改变输出分布和长轨迹行为, 结果表现为语言更稳定、部分高难推理与 Agent 任务上涨, 同时留下跨语言搜索和裸代码的反例. 随后的 V3.2-Exp 固定这份行为基线, 再测试稀疏注意力的效率收益. 这条因果图中, Terminus 提供的是 checkpoint 层的对照, 没有提供训练算法层的消融. 读者据此可以做三件事: 用官方数字选择优先测试场景, 用模型仓库验证部署一致性, 用配对回归判断自己的任务是否落在增益分布里.

迁移报告也应沿这三层组织. 第一层记录可复现的环境: 权重摘要、tokenizer、模板、后端、精度和解码参数. 第二层记录行为: 两种模式的语言切换、异常字符、结构解析、工具动作与恢复轨迹. 第三层记录任务结果: 闭卷、代码仓库、终端和中英文搜索分别统计, 同时列出旧对新错的样本. 环境一致而行为改变, 才能更有把握归因到 checkpoint; 行为改善而任务不涨, 说明改动没有穿过完整链路; 总分上涨却伴随关键回归, 则应分场景路由或暂缓替换. 这样评估, Terminus 的短发布说明也能转化为可执行、可复查的版本判断.

版本判断还应保留原始轨迹和评分器版本. 同一输出经过不同答案规范化、代码测试镜像或搜索索引, 可能得到不同分数. 保存这些对象, 才能在后续模型更新时重放旧实验, 分辨 checkpoint 变化与评测设施变化. 对 Terminus 这种缺少独立技术报告的修订版, 可重放记录尤其重要, 因为它补足了公开材料没有提供的运行条件.

重放时还要固定失败处理. 工具超时究竟记零分、允许重试还是跳过样本, 会改变 Agent 总分; 生成被长度上限截断时, 归因也可能落在模型、预算或框架三处. 把这些规则和每次运行结果一同保存, 才能让版本差异经得住复查. 否则同一组权重换一个重试策略, 就可能制造出看似属于 checkpoint 的增益.

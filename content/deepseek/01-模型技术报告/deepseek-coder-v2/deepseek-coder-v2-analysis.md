# DeepSeek-Coder-V2 技术报告详解

论文 [DeepSeek-Coder-V2: Breaking the Barrier of Closed-Source Models in Code Intelligence](https://arxiv.org/abs/2406.11931) 于 2024 年 6 月公开, 模型与使用说明见 [deepseek-ai/DeepSeek-Coder-V2](https://github.com/deepseek-ai/DeepSeek-Coder-V2). V2 不再从零训练一组 Dense 代码模型, 而是从已经训练 4.2T token 的 DeepSeek-V2 中间 checkpoint 继续训练 6T token. Lite 版本有 16B 总参数, 每个 token 激活 2.4B; 大版本有 236B 总参数, 激活 21B. 编程语言由上一代约 87 种扩展到 338 种, 上下文扩到 128K.

## 1. 续训路线把代码能力接到通用 MoE 基座上

Coder-V2 把代码续训接到了通用 MoE 基座上, 模型路线也由专用稠密模型转向通用稀疏模型.

### 1.1. 60/10/30 配比同时保留三类能力

新增训练数据按 60% 代码, 10% 数学, 30% 自然语言混合. 自然语言从 DeepSeek-V2 语料中采样, 代码和数学数据重新构建. GitHub 数据截止到 2023 年 11 月以前, 使用与 DeepSeek-Coder 相近的行长, 字母比例和文件类型过滤, 再做近重复去重. 最终从 GitHub 获得 821B 源码 token 与 185B 代码相关文本 token.

Common Crawl 侧沿用 DeepSeekMath 的迭代召回. StackOverflow, PyTorch 文档, Math StackExchange 等高相关页面先作为种子训练 fastText 分类器, 分类器再从网页中发现新页面. 中文文本改用 DeepSeek-V2 的 BPE token 作为分类输入, 避免依赖空格分词. 首轮中代码或数学页面占比超过 10% 的域名会被标记, 后续再沿 URL 补充同域未收录页面. 三轮网页召回得到 70B 代码相关 token 和 221B 数学 token; GitHub 上再运行两轮分类流程, 补充 94B 高质量源码. 新代码语料合计约 1.17T token.

数学语料 221B token, 大约是 DeepSeekMath 所用 120B 的两倍. 代码与数学共同增加, 与后续 Table 3 和 Table 9 的生成结果相符. 30% 自然语言维持通用交互, 但 Table 10 显示知识问答会相对 DeepSeek-V2 Chat 回落. 配比因此体现明确取舍: 更多容量被分配给代码结构, 数学步骤与任务指令, 百科知识的保持并非无损.

### 1.2. 1B 消融把语料质量与模型规模分开

报告使用同一 1B 模型架构比较旧 DeepSeek-Coder 语料与新语料. 训练 1T token 后, HumanEval 从 30.5% 升到 36.0%, MBPP 从 44.6% 升到 49.0%. 新语料继续训练到 2T token 后, 两项分别达到 37.2% 与 54.0%. 因为模型规模保持不变, 这组消融比大模型横向排名更直接地支持新语料管线有效.

1T 与 2T 的比较同时混入训练 token 数量变化. 其中旧语料 1T 对新语料 1T 可以支持质量差异; 新语料 1T 对 2T 只能说明继续训练有收益. 引言概括的 HumanEval 增加 6.7 个百分点, MBPP 增加 9.4 个百分点, 对应旧语料 1T 与新语料 2T 的总差, 不能全部算作清洗算法贡献.

### 1.3. MoE 的总参数和激活参数承担不同含义

V2 直接沿用 DeepSeek-V2-Lite 与 DeepSeek-V2 的 MoE 架构超参数. Lite 为 16B 总参数, 激活 2.4B; 大版本为 236B 总参数, 激活 21B. 总参数描述专家容量, 激活参数更接近一次 token 前向计算实际经过的权重规模. 两个数字都不能单独等同于显存占用或吞吐, 因为专家权重仍需分布在设备上, 路由, 通信和 batch 形状也会影响成本.

代码语料并未改变 MoE 的基本路由结构. V2 的路线是利用通用基座已经形成的语言, 数学和世界知识, 再通过 6T 定向续训改变能力分布. 报告还记录训练中出现不稳定与梯度尖峰, 并将问题归因于 exponential normalization, 随后退回 conventional normalization. 文中没有给出尖峰频率和消融数值, 可以确定的是最终训练设置放弃了该归一化方案, 不能进一步量化它对最终成绩的影响.

## 2. 训练目标和长上下文按模型用途分流

### 2.1. Lite 保留 FIM, 大模型只做 next-token prediction

16B Lite 同时使用 next-token prediction 与 FIM, 236B 只使用 next-token prediction. Lite 的 FIM 采用 PSM, 把文档切为 $f_{pre}$, $f_{middle}$ 与 $f_{suf}$ 后重排:

$$
\langle|\mathrm{fim\_begin}|\rangle f_{pre}\langle|\mathrm{fim\_hole}|\rangle f_{suf}\langle|\mathrm{fim\_end}|\rangle f_{middle}\langle|\mathrm{eos}|\rangle
$$

FIM 在文档级, packing 之前执行, 比例为 0.5. 生成中间片段时, 前缀与后缀都已经位于因果注意力的左侧. Lite 因而保留适合 IDE 的双侧补全能力. 大版本把训练容量集中在自然语言指令下的长代码生成, 数学和软件任务, 没有以 FIM 为目标训练. Table 6 主要报告 Lite-Base, 正好与两档模型的训练目标对应.

FIM 与 next-token prediction 共用模型参数, 但输入格式不同. 50% FIM 会减少自然顺序文档占比, 同时增加双侧条件样本. V2 沿用上一代经过消融选择的比例, 没有报告在新 MoE 架构上重新扫描不同 FIM 率. 因此 0.5 是继承并验证可用的配置, 不是 V2 报告重新证明的最优点.

### 2.2. 优化设置包含一次明确的稳定性回退

预训练使用 AdamW, $\beta_1=0.9$, $\beta_2=0.95$, weight decay 0.1. 学习率采用 cosine 调度, warm-up 2000 步, 末端降到初始学习率的 10%. Lite 与大版本分别继承 DeepSeek-V2-Lite 和 DeepSeek-V2 的主要超参数. 从中间 checkpoint 续训减少了重新获得通用能力的成本, 也意味着最终模型不能只按新增 6T token 理解; 总暴露量为 10.2T token.

归一化回退揭示了大规模续训的一项边界: 在小规模实验中有效的数值技巧, 放到长周期 MoE 训练可能放大梯度异常. 最终采用 conventional normalization 是训练稳定性选择. 报告没有公开回退前后的损失曲线和成本, 所以不能断言该变化提升了基准成绩, 只能确认它解决了团队观察到的不稳定与梯度尖峰.

### 2.3. YaRN 用两段训练把窗口推到 128K

长上下文扩展沿用 DeepSeek-V2 的 YaRN, scale 为 40, beta 参数为 1 与 32. 第一阶段把序列扩到 32K, batch size 1152, 训练 1000 步; 第二阶段扩到 128K, batch size 288, 再训练 1000 步. 序列变长时 batch 减小, 控制每步显存与 token 规模. 训练阶段还会上采样长上下文数据, 让扩展后的位置范围真正出现在样本中.

Figure 2 的 Needle In A Haystack(NIAH)测试显示模型在直至 128K 的窗口内能够找回插入信息. NIAH 主要检验检索, 不覆盖多文件依赖推理, patch 正确性或长上下文中的干扰鲁棒性. 128K 表示已经训练并通过该检索测试的窗口, 对真实仓库仍需结合 RepoBench, SWE-Bench 等任务结果判断.

## 3. 对齐阶段把可验证反馈转成训练信号

### 3.1. SFT 混合代码, 数学和通用指令

SFT 数据包括约 20k 代码指令, 30k 数学指令, 以及从 DeepSeek-V2 指令集中采样的通用数据, 总量约 300M token. 训练使用 cosine 调度, warm-up 100 步, 初始学习率 $5\times10^{-6}$, batch 约 1M token, 模型总计接触约 1B token. 指令条数与训练 token 暴露量口径不同, 后者包含重复 epoch 或采样.

16B 在 SFT 阶段继续保留 FIM 数据, 避免自然语言指令微调完全覆盖中间补全格式. 这项安排使同一个 Lite-Instruct 模型既能回答代码问题, 又能使用前后缀补中间. 报告没有给出 SFT 前后 FIM 的单独消融, Table 6 展示的是 Lite-Base, 因而只能确认训练方案保留该目标, 不能量化对齐后 FIM 能力保留了多少.

### 3.2. 编译器 0/1 信号先用于训练奖励模型

数学任务可以用 ground-truth 判定答案. 代码任务也能用编译和测试给出 0/1 反馈, 但有限测试用例无法覆盖所有行为: 一个错误程序可能碰巧通过, 一个输出格式差异也可能被判失败. 直接把该二值结果作为强化学习奖励, 梯度信号离散且带有测试覆盖噪声.

团队先用编译器与测试产生的数据训练代码奖励模型, 再由奖励模型给强化学习提供连续信号. Figure 3 在内部 LeetCode 与 LeetCode-zh 测试上显示, 奖励模型信号优于原始编译器信号. 奖励模型可以从大量已标注样本中学习跨题型特征, 但它不会自动获得测试未覆盖的真实正确性. 其误差可能被策略模型利用, 所以结果支持信号更有效, 不表示奖励已经等价于程序验证.

### 3.3. GRPO 省去 critic, 仍依赖组内比较质量

强化学习阶段使用 Group Relative Policy Optimization(GRPO), 代码 prompt 过滤后约 40k, 每条配有测试用例. GRPO 对同一 prompt 采样一组回答, 通过组内奖励的相对关系构造优势, 无需像 PPO 那样额外维护 critic 模型. 对 236B 总参数的 MoE, 少一个 critic 能显著减少训练权重与前向计算负担.

省去 critic 不会消除奖励偏差. 如果同组样本整体质量都低, 或奖励模型在某类代码上系统误判, 相对优势仍会把策略推向错误方向. 报告用内部数据比较奖励信号, 但没有公开奖励模型结构, 训练集规模, 组大小与 KL 设置. 因此可以复述 GRPO 的成本优势和信号来源, 无法从报告完整复现 RL 配方.

## 4. 代码评测要按生成, 补全和修复分开读

函数级生成、代码补全和软件修复是三种不同能力, 不能用一个 HumanEval 分数代替.

### 4.1. 函数生成与竞赛题衡量不同难度

Table 3 在 greedy 解码下给出 236B/21B Instruct 的 Python HumanEval 90.2%, 多语言平均 75.3%, MBPP+ 76.2%. 表内 GPT-4o 的多语言平均为 76.4%, GPT-4-Turbo-0409 为 72.3%. Lite 的多语言平均为 65.6%, 高于上一代 DeepSeek-Coder-Instruct 33B 的 61.9%. 这些数字显示 MoE 续训在函数级生成上取得较高参数效率, 但 HumanEval 的短函数不能代替软件修复结果.

LiveCodeBench 只取 2023 年 12 月至 2024 年 6 月子集, 因为预训练代码截止在 2023 年 11 月以前. 236B 总分 43.4%, 与表内 GPT-4o 相同, 低于 GPT-4-Turbo-0409 的 45.7%. USACO 为 12.1%. LiveCodeBench 的持续新增题降低直接污染风险; USACO 的复杂算法题和高质量测试则显示标准函数生成成绩无法等比例转化为竞赛能力.

CRUXEval 包含 800 个 Python 函数及输入输出, I 任务由输入预测输出, O 任务由输出反推输入. 236B 的 I-COT 为 70.0%, O-COT 为 75.1%. 报告把与更大闭源模型的差距部分归因于仅激活 21B 参数, 这是作者解释, 不是控制变量实验. 架构, 训练数据与对齐方法也同时不同.

### 4.2. Lite 的补全成绩对应低激活成本场景

RepoBench v1.1 来自 2023 年 10 月 6 日至 12 月 31 日创建的 Python 与 Java 仓库. 为避开 11 月前的训练数据, 报告只使用 2023 年 12 月子集. Lite-Base 的 Python 平均为 38.9%, 接近上一代 33B Base 的 39.1%; Java 平均为 43.3%. 它每个 token 激活 2.4B 参数, 但部署速度仍取决于专家并行和硬件通信, 不能只按激活参数线性推算.

单行 FIM 的 Table 6 中, Lite-Base 在 Python 为 80.0%, Java 为 89.1%, JavaScript 为 87.2%, 均值 86.4%. 结果与 0.5 FIM 训练目标一致, 也说明大模型没有参与这条产品定位的竞争. Exact match 对格式敏感, 一行完全一致适合评价自动补全接受概率, 不能度量语义等价的多行修复.

### 4.3. 软件修复暴露长上下文之外的瓶颈

Table 7 同时报告 Defects4J, SWE-Bench 与 Aider. 236B Instruct 分别为 21.0%, 12.7%, 73.7%. SWE-Bench 要求根据 GitHub issue 修改真实仓库并通过测试, 它把问题理解, 文件定位, patch 生成与验证串在一起. 12.7% 是报告中首个超过 10% 的开源成绩, 但也意味着大多数问题仍未修复. Lite-Instruct 在 SWE-Bench 为 0.0%, 表明 128K 窗口本身不能弥补模型容量, 检索和复杂指令执行的不足.

Aider 的 73.7% 高于表内 GPT-4o 的 72.9%, Defects4J 21.0% 则低于 GPT-4o 的 26.1%, SWE-Bench 12.7% 也低于 26.7%. 三个基准的输入形式, patch 范围与评分程序不同, 不能取一个最高数字概括所有修复能力. 更稳妥的结论是 V2 已能在部分代码编辑协议中接近闭源模型, 对开放式真实 issue 仍有明显缺口.

## 5. 数学和通用能力显示了配比的收益与代价

### 5.1. 数学成绩受益于数据与可验证对齐

Table 9 使用 greedy 且不调用外部工具. 236B Instruct 在 GSM8K 为 94.9%, MATH 为 75.7%, 后者接近表内 GPT-4o 的 76.6%. AIME 2024 为 4/30, maj@64 为 5/30, Math Odyssey 为 53.7%. AIME 分母很小, 单题变化就会明显改变比例, 所以报告保留答对题数比换算百分比更合适.

数学提升同时来自 221B 数学预训练语料, 30k SFT 数学指令和 ground-truth 奖励, 报告没有逐项消融三者贡献. 可验证答案让强化学习信号比开放式文本稳定, 但 GSM8K 与 MATH 成绩不能直接归因于 GRPO. 1B 语料消融只报告 HumanEval 与 MBPP, 没有给出数学语料的对应小模型对照.

### 5.2. 通用能力没有因 30% 自然语言完全保真

Table 10 与 DeepSeek-V2 Chat 对比时, V2-Coder 在部分推理和指令指标上更高, 例如 BBH 为 83.9 对 79.7, Arena-Hard 为 65.0 对 41.6. 知识型任务出现回落: TriviaQA 为 82.3 对 86.7, NaturalQuestions 为 47.5 对 53.4. MT-Bench 与 AlignBench 也略低于 DeepSeek-V2 Chat.

这些变化符合定向续训的能力再分配. 60% 代码和 10% 数学增强结构化生成与推理, 30% 自然语言避免通用能力大幅丢失, 但无法保证所有知识指标不退. 报告在结论中也把 instruction-following 和复杂场景列为后续方向. V2 的进步集中在代码, 数学, 长上下文和参数激活效率; 真实仓库修复与稳定执行复杂要求仍是评测中最清楚的边界.

迭代召回的每一轮都会改变下一轮分类器的数据分布. 域名阈值先扩大覆盖, URL 标注再补同站遗漏页面, GitHub 两轮筛选则继续提高源码相关性. 这比只按扩展名抓取更容易得到教程, issue 与代码说明, 也会继承种子集合的领域和语言偏好. 报告没有公开误报率, 分类阈值曲线和 338 种语言各自占比, 无法判断长尾语言是否均衡.

1B 消融需要按对照拆开. 旧语料与新语料都训练 1T 时, HumanEval 和 MBPP 的差异可归于语料管线. 新语料从 1T 继续到 2T 后的提升同时包含更多训练量. 引言给出的总增幅跨越了语料与 token 数两个变量, 不能全算作过滤算法收益. 1B 的数据瓶颈也不必然等同于 236B MoE, 所以完整模型评测仍然必要.

MoE 的总参数和激活参数回答不同问题. 总参数描述专家库容量, 激活参数近似单个 token 经过的权重规模. 未激活专家仍需驻留或在设备间分布, 路由和 all-to-all 通信也会影响速度. 236B/21B 不表示部署只需容纳 21B 权重, Lite 16B/2.4B 也不能直接等同于 2.4B Dense 模型.

RepoBench 中 Lite 接近更大的上一代 Dense 模型, 支持其参数效率, 但报告没有同硬件吞吐曲线. 专家并行, batch 大小和内存带宽会改变真实延迟. 激活参数适合解释每 token 计算为什么较低, 不能据此线性推算 IDE 响应时间. Lite 的产品定位还依赖 FIM 目标, 并非只由参数量决定.

Lite 与 236B 的训练目标已经分流. IDE 补全通常输入光标前后代码, 输出短且要求低延迟, Lite 的 0.5 FIM 与 2.4B 激活适合此场景. 大版本只做 next-token prediction, 再通过 SFT 和 RL 加强长代码生成与复杂请求. 两档模型不是同一目标上的简单缩放, 因而不能拿缺少 FIM 训练的大版本替代 Lite 的 PSM 使用路径.

两阶段 YaRN 训练控制位置分布变化. 先用 32K, batch 1152 训练 1000 步, 再用 128K, batch 288 训练 1000 步. 序列长度扩大四倍时 batch 缩小四倍, 每步 token 规模保持相近. 上采样长文档同样关键: 位置编码允许远距离输入, 只有样本真正出现远端依赖, 参数才获得利用它的梯度.

NIAH 证明在 128K 内找回插入信息, 不证明能修复 128K 仓库. 软件修复还要定位相关文件, 理解 issue, 生成一致 patch 并通过环境测试. NIAH 表现良好而 SWE-Bench 只有 12.7%, 正好显示长距离检索只是任务的一环. 上下文窗口扩大不能自动提供搜索策略和执行反馈循环.

SFT 的约 300M 去重 token 与约 1B 训练暴露量是两个口径, 后者意味着重复采样或多轮遍历. 代码, 数学和通用指令共同维持交互面, 16B 还继续混入 FIM 以减少对齐遗忘. 报告没有给通用样本数, 类别采样比例和 FIM 混合率, 所以不能从公开数字还原完整 epoch 分布.

编译器 0/1 反馈混合了语法, 有限测试和测试覆盖三层信息. 奖励模型从这类标签学习后, 能给部分正确候选连续排序, 也可能把代码风格和常见模板误当成正确性. Figure 3 支持内部 LeetCode 上奖励模型信号更有效, 没有给出可抄成百分点的表格数值. 部署时仍需真实编译与测试.

GRPO 通过同一 prompt 的一组候选计算相对优势, 困难题不会仅因绝对奖励低而完全失去信号. 当组内奖励相同, 更新信息会变弱; 采样多样性和奖励分辨率直接影响训练. 连续奖励模型因此比稀疏 0/1 更适配组内比较. 组大小, KL 设置和奖励模型结构未公开, 公开报告不足以完整复现 RL 配方.

代码生成表的 greedy, 数学表的 maj@64 与修复表的 patch 成功率也不能混用. greedy 衡量一次确定性输出, maj@64 使用多次采样聚合, SWE-Bench 要求真实仓库测试通过. AIME 4/30 的分母很小, 单题就会明显改变比例. 对比模型时需要保持 prompt, 工具使用和采样预算一致.

RepoBench 和单行 FIM 分别测试跨文件条件与当前文件双侧条件. Lite 在单行 FIM 均值 86.4%, RepoBench Python 平均 38.9%, 难度与指标并不相同. 大版本没有 FIM 训练, 报告不提供对应 FIM 表项. 两档模型用途不同, 所以表格覆盖的任务也不同.

Defects4J, SWE-Bench 和 Aider 对修改范围及交互协议的要求不同. 236B 在 Aider 达到 73.7%, 在 SWE-Bench 只有 12.7%; 高 Aider 分数不能概括所有软件修复. Lite 在 SWE-Bench 为 0.0%, 也说明低激活补全模型无法仅靠 128K 上下文完成开放式修仓. 容量, 对齐, 检索和执行环境都会进入最终结果.

数学提升来自 221B 数学预训练数据, 约 30k SFT 数学指令和 ground-truth 奖励的共同作用. 报告没有逐项消融, 不能把 MATH 75.7% 全归给 GRPO. 数学最终答案易于核验, 代码测试则受覆盖率限制, 因而两类奖励采用不同构造. 可验证信号减少主观打分, 仍不保证推导过程或未测试行为正确.

Arena-Hard 上升而 TriviaQA, NaturalQuestions 回落, 说明定向续训改善部分复杂回答与推理, 同时损失一部分事实召回. 30% 自然语言的作用是维持可用通用接口, 不是完全保存 DeepSeek-V2 Chat 的能力曲线. 工程选型应按任务分档: Lite-Base 做仓库补全与 FIM, Lite-Instruct兼顾交互, 236B Instruct处理高难生成, 数学与软件编辑.

128K, 奖励模型与 GRPO 分别处理输入长度, 训练信号和优化成本, 三者没有替代关系. 长窗口承载证据, 奖励模型平滑有限测试产生的标签, GRPO 省去 critic. 完整的软件工程链路还要接入检索, 编译, 测试和失败回馈. Table 7 留下的差距表明, 这些外部环节仍是把模型能力转成稳定修复率的必要部分.

报告的开放材料也限定了复现深度. 数据召回给出种子类型, 迭代轮数与总 token, 没有发布全部 URL 和分类器; RL 给出 prompt 数量, 奖励来源与 GRPO 名称, 没有给组大小, KL 系数和奖励模型结构. 因而可以复现方法框架与公开评测, 无法得到逐样本相同的训练轨迹. 对结果的解释应停留在表格和已公开设置能支持的范围内.

从前后代演进看, DeepSeek-Coder-V2 同时改变了基座, 架构, 数据截止时间, token 数, 语言覆盖, 上下文和对齐方式. Lite 超过上一代 33B 的若干成绩不能只归因于 MoE, 新语料和通用基座同样是变量. 1B 语料消融, RepoBench 的激活参数对照和修复基准分别提供局部证据, 但报告没有覆盖所有变量的全因子实验.

V2 最有价值的工程判断是将任务分开配置. 补全依赖 FIM, 双侧上下文和低延迟; 复杂生成依赖更大激活容量与指令对齐; 软件修复还要加检索和执行验证; 数学可以利用 ground-truth 奖励. 单一模型接口可以承载这些请求, 训练数据和外部系统却必须针对各自误差来源设计. 这也是标准生成分数接近闭源后, SWE-Bench 仍保留明显差距的原因.

## 6. 从 DeepSeek-V2 中间点到代码基座

### 6.1. continue pretraining 改变的是分布, 不是模型身份

[官方论文](https://arxiv.org/abs/2406.11931)明确说明 Coder-V2 从 DeepSeek-V2 的中间 checkpoint 继续训练 6T token. 这与第一代 Coder 从随机初始化训练 2T 的路线不同. 初始化已经包含通用语言、数学、MoE 路由和 MLA 表示, 后续代码 mixture 在既有参数空间中重分配概率质量. 因而 Coder-V2 是 DeepSeek-V2 基座的代码专门化分支, 不能只按名字理解成 33B Dense Coder 的权重续接.

设通用预训练分布为 $P_0$, 代码续训分布为 $P_1$, 中间参数为 $\theta_0$. 继续预训练求解

$$
\theta_1\approx\arg\min_\theta\mathbb E_{x\sim P_1}
[-\log p_\theta(x)],\qquad \theta\text{ initialized at }\theta_0.
$$

$\theta_0$ 决定优化起点, $P_1$ 决定新梯度. 若两分布共享自然语言、数学与推理结构, 旧能力可迁移; 若代码占比过高, 事实知识和开放问答可能遗忘. 60% code、10% math、30% natural language 正是在专业化与保真之间选工作点.

继续训练的效果无法由最终 checkpoint 分解成「基座贡献」和「6T贡献」. 严格对照需要同架构随机初始化吃相同 6T, 或从同一中间点使用不同 mixture. 报告的小模型数据实验能验证语料召回与质量, 没有训练完整 236B 全因子矩阵. 因此 Lite 与上一代 33B 的差距支持整套新路线, 不单独证明 MoE 或初始化是唯一原因.

### 6.2. DeepSeekMoE 的细粒度专家语义

Dense FFN 对每个 token 激活同一组参数. MoE 把 FFN 拆成共享专家与路由专家, 路由器为隐藏状态 $h$ 计算分数

$$
s_i=h^\top e_i,qquad
g_i=\frac{\exp(s_i)}{\sum_j\exp(s_j)},
$$

再选择 top-$k$ 专家集合 $\mathcal K(h)$. 一层输出可写成

$$
y=\sum_{i\in\mathcal K(h)}g_iE_i(h)+\sum_{j\in\mathcal S}E_j^{shared}(h).
$$

共享专家承载跨 token 常识, 路由专家允许代码语言、数学模式或自然语言形成条件化表示. 这是功能解释, 论文没有给出某个专家对应 Python 或代数的确定标签. 路由是学习结果, 专家通常混合多类模式.

总参数 $N_{total}$ 决定模型容量和权重存储, 激活参数 $N_{active}$ 更接近单 token FFN 计算. 官方仓库给出 Lite 16B/2.4B active, 大模型 236B/21B active. 比较 Dense 33B 时, 236B 拥有更大条件容量, 每 token 主参数乘加更接近 21B 量级, 还要支付路由、通信与共享模块. 2.4B active 也不等于整模型只有 2.4B 显存, 推理仍需放置或分片全部 16B 权重.

MoE 的理论计算节省受负载均衡约束. 若大量 token 选择同一专家, 该专家所在设备形成热点. 设专家 $i$ 接收 token 数 $n_i$, 理想均衡为 $\bar n=Bk/E$. 最大负载比

$$
\rho=\frac{\max_i n_i}{\bar n}
$$

越大, padding、丢 token 或等待越严重. 论文继承 DeepSeekMoE 的路由机制, Coder-V2 报告没有把所有通信成本折算进 active parameter. 所以 active params 是模型计算口径, 不是端到端延迟保证.

### 6.3. MLA 与长代码状态

Coder-V2 基座来自 DeepSeek-V2, 因而注意力采用 MLA 路线. 标准 MHA 为每层每个历史 token 保存各头 K、V; MLA 将状态压缩到低维 latent, 解码时从压缩表示参与注意力. 长度从16K扩到128K后, KV状态线性增长, MLA直接减少每个历史token占用的状态维度.

若每 token 每层原 KV 维度为 $2h_{kv}d_h$, latent 维度为 $d_c$ 并另存 RoPE 分量 $d_r$, 缓存比例粗略为

$$
\frac{d_c+d_r}{2h_{kv}d_h}.
$$

具体维度应以 DeepSeek-V2 config 为准. 公式说明结构收益来自表示压缩, 真实显存还包括页表、量化 scale、allocator 与 batch碎片. Coder-V2 报告主要讨论模型能力, 没给 128K 服务吞吐曲线.

MLA 与 MoE 作用位置不同: MLA压缩注意力状态, MoE稀疏激活FFN参数. 前者缓解长上下文 cache, 后者扩展条件容量. 二者都来自V2底座, 不属于第一代Dense Coder的训练组件.

## 7. 6T 数据混合与召回

### 7.1. 60/10/30 的名义 token 账

6T token 按配比换算, code约3.6T, math约0.6T, natural language约1.8T. 这是名义采样量, 不等于独特数据量. 同一仓库或文档可能在召回与采样中重复, tokenizer又使各域每字节token数不同. 代码域本身包含338种语言, 头部与长尾比例未完整公开.

混合目标是

$$
\mathcal L=0.6\mathbb E_{P_c}\ell(x)+0.1\mathbb E_{P_m}\ell(x)+0.3\mathbb E_{P_n}\ell(x).
$$

三个梯度共享模型参数, 既能正迁移也会冲突. 数学的形式推理帮助竞赛代码, 代码执行结构帮助程序化数学, 自然语言帮助题意与通用问答. 容量有限时, 提高一种采样权重会减少另两种训练机会. TriviaQA等回落说明30%自然语言没有完全冻结通用分布.

「保持 comparable general ability」应绑定报告选取的基准. 某些MMLU或Arena指标接近, 事实召回可能下降; 代码数学大涨也不代表所有语言能力不变. 要测保真, 应从同一DeepSeek-V2 checkpoint做继续训练前后全套对照, 按知识、推理、写作、多语和安全分组.

### 7.2. 代码数据的迭代召回

论文使用高质量代码种子训练fastText分类器, 从Common Crawl中召回代码相关页面, 迭代更新数据. 设初始种子正例为 $S_0$, 分类器 $f_t$ 在第$t$轮从语料池$U$选出

$$
S_{t+1}=S_t\cup\{x\in U:f_t(x)>\tau_t\}.
$$

新增样本再训练分类器, 可以扩大术语和网页类型覆盖. 这是典型自举: 召回提高, 误报也可能累积. 人工质量检查与阈值控制决定漂移程度, 完整标签和阈值未公开.

Common Crawl中的代码知识不只源码. API文档、教程、问答、错误日志和配置解释能连接自然语言与代码. 分类器若只偏爱含大量代码块的页面, 会漏掉高价值概念文档; 阈值低又会吸入普通技术营销页. 论文的小模型消融显示新数据提高多项代码评测, 支持总体质量, 无法逐类证明每个召回来源有效.

迭代召回还会放大种子偏差. 初始以Python和热门语言为主, 分类器更容易找到相似页面; 338语言的长尾覆盖需要专门种子或语言识别. 支持语言列表说明数据管线识别到这些语言, 不说明每种拥有相同token与质量.

### 7.3. 数学数据与代码的相互作用

10%数学对应约600B nominal token, 规模远超普通SFT数学集. 预训练数学语料提供公式、证明和解题轨迹, 代码语料提供算法和精确操作. 竞赛题常需要二者: 理解组合数学, 再实现高效程序. Coder-V2在数学和代码同时提升与这项配比相符.

相关不等于独立归因. 基座DeepSeek-V2已有数学能力, 继续训练总量6T, MoE容量和后训练GRPO也变化. 若要证明10%是关键, 可从同一checkpoint训练0%、5%、10%、20%数学对照, 固定总token, 同时测代码、数学和通用能力. 如果数学增长而代码竞赛也增、普通API任务不变, 正迁移解释更强.

数学文本可能含生成代码或工具解法, 代码域也含数值库与算法证明, 域标签并非互斥. 配比是数据管线分类, 不对应模型内部三个隔离模块. 分析专家路由时也不能假定数学token只去数学专家.

### 7.4. 重复、污染与截止时间

6T继续预训练使污染审计更难. 公开代码题、题解、翻译与测试可能散落在仓库和网页. 字符串n-gram能发现原文, 变量改名和算法同构需要AST、语义检索或执行轨迹. LiveCodeBench依靠较新题目降低直接收录, 仍需保留时间窗口和版本.

重复片段在经验loss中获得更高权重. fork、模板和镜像题解会让某种答案模式反复出现. 去重阈值过严又可能删除常见正确惯例. Coder-V2报告更强调召回和结果, 数据manifest没有公开, 因而无法独立证明完全无污染.

可证伪做法是把评测题按训练近邻相似度分桶. 若优势集中在高相似桶, 泛化主张应收缩; 低相似、发布时间后的私有题仍领先, 证据更强. 对数学也要检索题面、答案与解题过程, 只查prompt不够.

## 8. FIM、AR与模型分流

### 8.1. Lite为什么保留FIM

第一代Coder通过PSM把前缀$P$、中段$M$、后缀$S$重排为$P,S,M$, 学习$p(M|P,S)$. Coder-V2 Lite保留FIM, 面向低激活成本的代码补全; 大模型训练只用next-token目标, 更偏复杂生成和指令任务. 两条训练线分别优化补洞协议与复杂生成接口.

混合目标可写为

$$
\mathcal L_q=(1-q)\mathbb E\mathcal L_{AR}(X)+q\mathbb E\mathcal L_{AR}(T_{PSM}(X)).
$$

FIM提高双侧补洞, 占比过高会减少自然顺序样本. Lite的RepoBench和HumanEval-FIM说明协议有效. 大模型未用FIM时, 即使通用生成更强, 也不应默认拥有同等稳定的special-token补洞接口.

### 8.2. 自回归目标与代码正确性

AR最小化

$$
\mathcal L_{AR}=-\sum_t\log p_\theta(x_t|x_{<t}).
$$

它奖励训练分布中高概率token, 编译通过和测试正确只通过数据统计间接进入. 一个语法流畅的错误算法可以有低loss, 多种正确实现又会分散概率. 后训练的编译奖励和ground-truth数学奖励补充行为信号, 仍无法覆盖所有软件规范.

FIM也不等于bug fixing. 给定正确前后文恢复缺口, 与在错误仓库中定位缺陷、修改多处并回归测试差异很大. RepoBench/HumanEval-FIM测补全, Defects4J/SWE-Bench测修复链路. 表格必须分开读.

### 8.3. 目标分流的反例

大模型只做AR仍可能从自然文本提示完成中间代码, 因为prompt可描述缺口; 它缺少官方FIM协议的专门训练. Lite保留FIM也不保证复杂多文件patch, 因为单缺口目标不处理多个编辑位置. 两类模型能力存在交叉, 产品接口的可靠性不同.

可做四格实验: Lite和236B分别用普通续写、自然语言补洞、官方FIM token、multi-file patch. 若236B在FIM token下退化而自然语言补洞强, 差异来自协议; Lite在单行强、patch弱, 说明目标覆盖边界. 论文没有完整四格, 已公开表支持部分判断.

## 9. 128K上下文的训练与验证

### 9.1. YaRN的尺度变换

RoPE对位置$m$按频率$\theta_i$旋转Q、K. 原训练长度外直接增加$m$会让相位进入未见区域. YaRN对不同频率分段缩放并调整attention幅度, 目标是在保留短距模式的同时扩展长距. Coder-V2通过两个阶段把上下文推到128K, 不能把config中的最大长度当作所有距离同质量.

长上下文attention计算主项为

$$
C_{attn}\approx4bT^2d
$$

前向, 在总token固定时每token成本约随$T$线性增加. MLA降低KV状态, 不消除dense attention的二次score计算. 128K训练需要更小序列batch、更多显存管理与并行, 报告没有把全部墙钟成本公开.

### 9.2. 位置容量与有效检索

模型能接收128K表示位置编码和内存路径支持, 有效利用还受干扰、数据覆盖和任务影响. needle测试可把关键定义放在1K到128K不同位置, 加同名干扰文件, 测调用是否正确. perplexity稳定也不保证仓库修复, 因为后者还需定位和执行.

长代码输入尤其需要选择. 一个大型仓库远超128K, 全量拼接会稀释相关信息. 检索器、符号图和目录导航先选片段, 长窗口承载更多候选与测试日志. 窗口与检索是互补资源, 不能互相替代.

### 9.3. 两阶段长度训练的归因

长度扩展阶段同时继续消费数据, 性能上涨含额外token与位置适配. 对照应从同一checkpoint分出保持短窗口和扩展窗口两组, 固定token/FLOPs或分别报告. 只比较扩展前后无法确定代码分数来自长度还是继续训练.

短上下文也可能回归. 频率缩放改变位置表示, 若短距任务下降, 需要插值策略或混合长度训练. 完整曲线应覆盖4K、16K、64K、128K并同时测短函数、远距检索和长仓修复. 报告给128K规格与若干长任务, 没覆盖所有位置分布.

## 10. 激活参数、计算与通信

### 10.1. active params不是部署显存

Lite每token激活约2.4B参数, 权重总量16B; 大模型激活21B, 权重总量236B. 单token GEMM成本与active部分相关, 权重服务需要加载总参数或在专家并行设备间分片. batch中不同token选择不同专家, 一个batch可能触及大量总权重.

若专家数$E$, 每token选$k$, 单个token激活比例约$k/E$加共享专家. 对batch $B$, 被触及专家期望随路由分布增加. cache与通信决定小batch、低延迟场景能否兑现理论优势. 因此2.4B active不能直接等同Dense 2.4B的延迟或内存.

### 10.2. 专家并行通信

路由后token表示要dispatch到专家所在设备, 计算后combine回原序. 通信量近似随$Bkd$增长, 跨节点带宽和消息粒度影响延迟. 代码token路由若偏向少数专家, 热点会造成尾部等待. 理论FLOPs降低, all-to-all可能成为瓶颈.

端到端时间可粗写为

$$
T_{layer}=T_{route}+T_{dispatch}+T_{expert}+T_{combine}+T_{dense},
$$

其中部分可以重叠. active params主要描述$T_{expert}$的算量, 不覆盖所有项. 模型论文分数无法替代系统benchmark.

### 10.3. Dense与MoE公平比较

比较第一代33B Dense与Lite 16B/2.4B active, 至少要同时报告总参数、激活参数、训练token、真实FLOPs、显存、tokens/s和任务分数. Lite使用V2初始化、6T新数据和更长上下文, 不是单纯把33B换成MoE. 其高数据效率属于整套配方.

可证伪的MoE实验应在同数据、同token、近似训练FLOPs下训练Dense与MoE, 控制上下文和目标. 若MoE loss/能力更好且墙钟相近, 稀疏容量解释成立; 若通信让成本更高, active参数优势需重新限定.

## 11. SFT、奖励模型与GRPO

### 11.1. SFT先建立响应分布

指令数据混合代码、数学与通用任务. 对prompt$x$和回答$y$, SFT损失为

$$
\mathcal L_{SFT}=-\sum_t\log\pi_\theta(y_t|x,y_{<t}).
$$

它教会模型按问题输出完整方案、解释与代码格式. 预训练获得知识和生成分布, SFT决定用户接口. 数据组成未完整公开, Instruct与Base差异不能全部归给RL.

### 11.2. 编译奖励的含义

代码候选经编译器得到0/1标签, 可训练奖励模型$r_\phi(x,y)$. 编译通过验证语法、名称解析和类型等静态约束, 不验证算法满足题意. 一个返回常数的程序可能编译成功. 因而编译reward密集、便宜, ground-truth测试reward更接近语义.

数学ground-truth可比较最终答案, 也会漏掉推理质量与多解格式. 奖励模型将有限标签推广到未执行候选, 可能学习长度、格式或代码围栏捷径. 对抗验证应保持编译结果相同而改变语义, 检查reward是否仍能排序.

### 11.3. GRPO的组内相对优势

同一prompt采样$G$个回答, 奖励$r_i$, 组内标准化优势可写成

$$
A_i=\frac{r_i-\bar r}{\operatorname{std}(r)+\epsilon}.
$$

策略更新提高高于组均值回答概率, 压低低于均值回答, 并以KL项约束参考策略. 无需单独critic, 降低大模型RL显存. 若组内奖励全相同, 优势接近零; 奖励噪声或可投机会直接进入梯度.

组大小、KL系数、采样温度与reward权重决定训练, 报告未给全部细节. 因而可以解释GRPO机制和公开结果, 无法逐步复现轨迹. Coder-V2的RL与后来的模型代际也要按时间分开.

## 12. 评测口径与可证伪比较

### 12.1. HumanEval到LiveCodeBench

HumanEval题少且公开时间久, pass@1受污染和prompt影响. MBPP+增加更强测试, LiveCodeBench采用时间滚动的新题降低直接收录, USACO强调高难算法. Coder-V2大模型在四项的相对表现提供从常见函数到竞赛推理的梯度.

pass@1是一次生成通过全部测试的比例. 对$n$题正确率$\hat p$, 标准误近似

$$
\sqrt{\hat p(1-\hat p)/n}.
$$

小分差需要置信区间. greedy与sampling、题目版本、编译器和timeout均会改变结果. 官方表格比较应绑定列出的模型版本日期.

### 12.2. Completion与Fixing

RepoBench和HumanEval-FIM测给定上下文后的局部补全, Lite保留FIM所以是主要对象. Defects4J、SWE-Bench、Aider要求理解错误、定位文件、生成patch, 有时还需工具链. 128K能容纳更多证据, 不自动完成定位与验证.

SWE-Bench低分是重要反例: 标准函数生成很强, 真实软件修复仍难. 错误可能来自检索、环境安装、测试、patch格式和长程规划. 单纯增加模型参数或窗口无法确定解决哪一环.

### 12.3. 污染与执行验证

代码正确性依赖hidden tests. 测试不足时硬编码也能过, 环境错误又会造成假失败. 评测应记录parse、compile、runtime、wrong answer、timeout和infra error. 汇总pass@1无法解释错误谱.

污染审计需覆盖题面、答案、测试和语义近邻. LiveCodeBench时间切分较强, 仍可能存在同构旧题. 若高相似题剔除后优势保持, 泛化证据更强; 优势消失则应收缩数据质量归因.

### 12.4. 消融矩阵

数据消融从同一V2 checkpoint比较code/math/natural配比; 架构消融同数据比较Dense/MoE; 目标消融在Lite比较FIM率; 长度消融固定token比较16K/128K; 对齐消融从同一SFT点比较无RL、编译reward、测试reward. 每组只改变一个主要变量.

反例条件也应预先写明. 数学比例增加却只提高见过题型, 泛化解释减弱; FIM后缀打乱不影响输出, 双侧利用解释减弱; MoE同FLOPs没有loss优势, 稀疏容量解释减弱;128K needle成功而SWE-Bench不升,瓶颈在长度之外.

## 13. 与相邻路线的边界

### 13.1. 第一代Coder

第一代是从头训练Dense 1.3B/6.7B/33B, 2T、87%代码、16K和广泛FIM. V2来自DeepSeek-V2中间checkpoint, 使用MoE、6T继续训练、60/10/30和128K. 二者共享代码专门化目标, 权重谱系和架构均发生断裂.

Lite的补全对照最接近第一代6.7B/33B, 大模型的复杂生成则引入更大基座与对齐. 分数差不能只归因于代际名称. 训练截止、benchmark版本和prompt也变了.

### 13.2. CodeI/O

CodeI/O关注代码与执行输入输出之间的行为数据, 可用于训练程序推理或验证能力. Coder-V2预训练主线仍是token目标, 后训练加入编译/答案reward, 与CodeI/O相关但不等同. 后续数据不能倒灌为6T配方.

若模型根据I/O反推程序, 任务条件是行为样例; RepoBench条件是代码上下文; SWE-Bench条件是issue和仓库. 都属于代码智能, 监督与评测不同. 谱系应按论文分别记录.

### 13.3. DSec

**DSec位于执行基础设施层**. 它管理大规模agent训练所需沙箱、资源、镜像和生命周期, 可以承载代码运行与测试. Coder-V2是模型, 其后继应沿模型版本追踪. 两者在agent rollout系统中协作, 不构成模型代际关系.

沙箱吞吐提高能增加可执行轨迹数量, 奖励质量仍由任务、测试和隔离决定. 没有DSec也能在普通容器评测Coder-V2; 有DSec也不会自动获得代码能力. 这条边界避免把infra进展写成模型训练事实.

## 14. 结论坐标

Coder-V2的核心组合是「V2 MoE中间基座 + 6T代码数学语言续训 + 模型用途分流 + 128K + SFT/可验证反馈」. 16B Lite以2.4B active服务补全, 236B以21B active承担高难生成. total/active分别对应容量与单token主计算, 真实部署还支付权重、通信和cache.

数据结论限于公开配比、召回方法与消融. 60/10/30能同时提升代码数学并大体维持通用能力, 事实召回仍有回落. 338语言表示覆盖扩大, 不表示均匀质量. 6T nominal token也不等于6T独特知识.

128K扩大可见范围, MLA降低状态成本, 检索与执行仍决定软件任务. FIM只在Lite明确保留, 大模型的自然语言生成优势不能替代专门补洞协议. 标准代码题接近闭源模型, SWE-Bench差距证明真实仓库链路还有定位、工具与验证瓶颈.

## 15. 继续预训练的优化动力学

### 15.1. 旧能力为什么会遗忘

从$\theta_0$继续优化新分布时, 更新方向为$-\eta\nabla\mathcal L_{P_1}$. 若某些通用样本在$P_1$中权重下降, 维持它们的梯度约束随之变弱. 参数共享使代码更新可能移动事实召回所依赖的表示. 30%自然语言相当于replay, 用旧域样本持续提供约束, 只能覆盖被采样的子分布.

遗忘可用旧任务loss变化衡量:

$$
F_k=L_k(\theta_1)-L_k(\theta_0).
$$

$F_k>0$表示该域变差. benchmark准确率还受prompt与对齐影响, Base checkpoint上的同分布loss更直接. Coder-V2报告主要给最终模型横向表, 没公布所有中间checkpoint的遗忘曲线.

重放比例并非越高越好. 自然语言增多会减少代码数学token, 专业化速度下降; 太少则通用能力退化. 60/10/30是经验选择. 可证伪实验应固定6T总量, 扫描自然语言比例并画代码—数学—通用Pareto frontier.

### 15.2. 学习率回退与稳定性

报告记录训练中将学习率回退到更小值, 这是大规模继续预训练的重要事实. MoE路由、数据域变化和大batch共同影响梯度. loss spike可能来自异常batch、路由失衡或数值问题, 降学习率减少单步参数位移

$$
\|\Delta\theta_t\|\approx\eta_t\left\|\frac{\widehat m_t}{\sqrt{\widehat v_t}+\epsilon}\right\|.
$$

回退能恢复稳定, 也改变原计划训练轨迹. 只看最终token和峰值lr无法复现. 需要checkpoint、optimizer state、异常step和数据批次日志. 论文公开了稳定性处理, 没给完整故障诊断.

继续预训练的optimizer状态是否继承会改变过渡动态. 继承Adam二阶矩可平滑更新, 新数据梯度尺度变化时旧矩估计可能不匹配; 重置则带来新的warmup需求. 论文公开信息不足以确定全部状态处理, 因而这里只比较两种机制可能产生的差异.

### 15.3. 六万亿token意味着什么

训练步数取决于global batch token数$B_t$:

$$
S=\frac{6\times10^{12}}{B_t}.
$$

没有batch就无法从6T推回step、GPU小时或学习率阶段. 长上下文阶段每token FLOPs高, token占比也不能直接等于成本占比. MoE active params进一步让参数总量与计算脱钩.

nominal token包含重复采样. 若独特语料$D_u$小于6T, 多轮采样会强化高质量模式也增加记忆. 数据manifest、去重率和采样epoch未完整公开. 因此6T适合描述优化消费量, 不适合描述独特知识总量.

### 15.4. 中间checkpoint的审计价值

沿训练进度保存checkpoint, 可以画代码、数学、通用loss和路由负载. 若代码先升后平台而事实召回持续降, 应提前停止或调mixture; 若数学在后期才增长, 说明需要更多token. 最终点无法展示这些权衡.

MoE还可追踪专家利用率、路由熵和领域条件分布. 路由熵突然下降可能预示专家坍缩; 某语言长期集中单专家可能形成专门化, 也可能造成热点. 只有统计相关, 不能把专家命名成确定领域模块.

## 16. MoE的容量、路由与训练信号

### 16.1. top-k路由梯度

路由器分数$s_i$经softmax得到$g_i$, top-k截断让只有选中专家执行. 对选中集合归一化后

$$
\tilde g_i=\frac{e^{s_i}}{\sum_{j\in\mathcal K}e^{s_j}},\quad i\in\mathcal K.
$$

离散选择使未选专家难获任务梯度, 负载均衡项提供额外信号. token路由边界附近, 小logit变化可更换专家, 训练噪声与低精度都会影响分配. Coder-V2继承基座机制, 报告不以路由算法创新为中心.

### 16.2. 共享专家的意义

共享专家对所有token激活, 可承载通用模式, 减少路由专家重复学习共同知识. 若共享容量太大, 每token计算上升; 太小, 多个专家重复基础语法. 细粒度专家让同总激活量选择更多小单元, 组合更灵活, all-to-all元数据也更复杂.

代码、数学和自然语言共享符号、逻辑和英文标识符, 共享专家可能促进迁移. 这只是架构动机. 验证需要屏蔽或替换共享专家, 比较各域loss及路由, Coder-V2报告没有给这项专门消融.

### 16.3. 参数效率的三种口径

容量效率看固定active compute下loss; 训练效率看固定GPU小时下能力; 服务效率看固定延迟/成本下质量. 236B/21B active可能在容量效率占优, 大权重分片与通信使训练/服务效率取决于集群. 只报active params会漏系统代价, 只报total params会高估每token计算.

比较模型时可列向量

$$
(N_{total},N_{active},F_{token},M_{weight},M_{KV},T_{latency}).
$$

不同任务权重不同: 离线批处理重吞吐, IDE补全重尾延迟, 本地部署重显存. Lite与大模型的定位因此分开.

### 16.4. 路由反例

若某稀有语言token被路由到训练不足专家, MoE容量大也可能表现差. 若batch很小, 专家kernel矩阵尺寸不足, active FLOPs少却利用率低. 若跨节点网络拥塞, 通信覆盖计算. 这些反例限定「稀疏更经济」的成立条件.

可证伪比较需要真实tokens/s和p99延迟. Lite对Dense同active规模若更慢, 系统开销抵消; loss仍更低则容量优势保留. 两个结论可以同时成立, 不能用一个吞吐数字替代模型质量.

## 17. 长上下文代码任务的结构

### 17.1. 128K里放什么

代码上下文包括目标文件、依赖定义、测试、issue、日志和文档. 每类信息价值不同. 设候选片段$c_i$长度$l_i$, 相关价值$v_i$, 预算$K$, 选择近似背包问题:

$$
\max_{z_i\in\{0,1\}}\sum_i z_iv_i,
\quad\text{s.t.}\sum_i z_il_i\le K.
$$

检索器估计$v_i$, 128K增大$K$, 仍无法容纳所有仓库. 无关片段还会降低注意力集中度. 长窗口和更好检索应联合评测.

### 17.2. 位置与依赖距离

依赖距离按token计算, 同一文件结构经不同tokenizer会变化. 定义在100K前、当前调用在末尾, 模型要保持名称和类型. 同名符号、重载与分支版本形成干扰. Needle只测字符串召回, 执行正确还需组合语义.

测试可分单跳、双跳与多跳依赖. 单跳找到定义, 双跳沿类型再找实现, 多跳涉及配置和生成代码. 若128K只提高单跳, 位置容量成立, 仓库推理仍有限. 报告的软件修复差距与这种分层一致.

### 17.3. 长输出与长输入

128K通常指输入加输出总上下文上限, 不等于能稳定生成128K代码. 长输出误差累积、重复和结构漂移更严重. 软件patch通常输出短diff, 输入很长. 评测应分别报告long-context retrieval和long generation.

MoE在长序列中还会看到更多token分布, 专家负载可能随文件区域变化. 大batch长序列有利于聚合路由, 单请求decode仍逐token. prefill与decode成本结构不同, 论文模型规格没有给生产服务结论.

### 17.4. YaRN反例

在128K能找到固定needle, 不代表短距代码不退化; 在自然文本长测有效, 不代表跨文件符号有效; 某个位置成功, 不代表所有位置均匀. 需要长度×位置×干扰的矩阵, 并与未扩展checkpoint对照.

如果检索后只需16K, 128K模型优势可能很小, 更长训练成本却已支付. 业务选择应测真实上下文分布. 最大窗口是能力上限, 不是默认输入目标.

## 18. 代码、数学与通用三域的耦合

### 18.1. 代码促进数学的路径

代码数据训练精确变量追踪、循环和条件结构, 数学问题可转成程序验证. 竞赛代码同时含组合、图论、数论. 正迁移可能来自共同潜在结构, 也可能只是数学数据本身增加. 配比消融才能分离.

PAL或工具评测把计算交给执行器, 模型负责转写. 纯MATH评测要求自然语言推导. 两者同时提升才说明能力覆盖更广. 最终答案reward可能鼓励正确结果, 推理过程仍可能含错误但巧合得到答案.

### 18.2. 数学促进代码的路径

算法题需要复杂度、证明与边界推理. 数学语料可提高规划, 不一定改善API调用和仓库补全. 将代码benchmark按算法、库、前端、数据库分组, 若收益集中算法类, 数学迁移解释更可信.

反例是HumanEval常见题提升而LiveCodeBench新题不升, 可能来自污染或格式. 时间外、高难、隐藏测试更适合测推理迁移. 论文同时采用多项评测, 仍需按类别拆分.

### 18.3. 通用语言保留

30%自然语言帮助理解issue、文档和用户意图, 也维护百科与对话. 代码模型的通用分数接近V2, 某些QA回落. 「可用」和「完全保真」是不同标准. 对开发助手, 技术写作与需求理解可能比TriviaQA更重要; 对通用聊天则相反.

领域评价应按产品权重组合, 不宜把所有benchmark平均. 可以设

$$
S=w_cS_{code}+w_mS_{math}+w_gS_{general}+w_rS_{repo},
$$

权重由场景决定. Lite补全与236B助手自然会有不同$w$.

### 18.4. 多语代码覆盖

338语言支持扩大训练识别范围, 长尾数据量和评测不足. 共享语法带来迁移, 生态API和构建工具仍需要本域样本. supported language list属于覆盖声明, 不能解释为每种语言达到Python水平.

评测可宏平均避免头部语言淹没长尾, 同时报告按真实流量微平均. tokenizer fertility、编译通过和执行通过应分语言给出. 仅用翻译HumanEval测语法, 还缺生态任务.

## 19. 后训练奖励的失效模式

### 19.1. 编译器奖励投机

模型可能生成空壳、硬编码或跳过逻辑, 只要编译就得正奖励. 奖励模型若从文本预测编译, 可能把代码围栏、长度和常见模板当捷径. 构造编译均成功但语义一正一错的pair, 可以测试reward是否理解行为.

编译器版本也影响标签. 新语法、依赖缺失和警告即错误设置会改变0/1. 数据生成必须固定镜像与命令. 基础设施失败若被标成模型失败, reward含噪.

### 19.2. ground-truth奖励稀疏

只有最终答案正确给1, 复杂题大多样本全0, 组内GRPO无相对信号. 增大采样组提高碰到正确解概率, 成本上升. 部分分奖励可改善密度, 也可能引入错误捷径.

数学答案格式需规范化, 分数、等价表达和单位都可能造成误判. 代码测试覆盖也决定ground truth. 可验证不等于无噪声, 只是比主观judge更直接.

### 19.3. KL与能力漂移

策略目标通常含

$$
\mathcal L_{RL}=-\mathbb E[A\log\pi_\theta(y|x)]
+\beta D_{KL}(\pi_\theta\|\pi_{ref}).
$$

$\beta$过小, 模型可能追逐reward损伤语言质量; 过大, 更新受限. 参考模型多为SFT checkpoint, 因而RL在其支持域内重排概率. 未公开系数限制复现深度.

### 19.4. 从离线奖励到agent

单回答奖励评估一个程序或答案. Agent任务包含多步命令、文件状态和测试反馈, credit assignment跨动作. Coder-V2报告的RL不能自动等同agentic RL. DSec可提供大规模执行环境, 训练算法和任务仍需另行定义.

软件修复的误差链可以拆成五个连续环节.

「Issue理解」

issue可能缺复现步骤、包含用户术语或指向错误模块. 模型要抽取期望行为和约束. 通用自然语言数据有帮助, benchmark中的结构化issue比真实报告干净. 错误理解后, 128K只会提供更多无关内容.

「定位」

从仓库选文件是检索问题. 文件名、符号、堆栈和测试失败各提供线索. SWE-Bench系统常配搜索工具, 纯模型上下文设置与agent设置不能混比. RepoBench给定上下文, 不测完整定位.

「编辑」

修改可能跨源码、测试、配置和迁移文件. FIM擅长单缺口, diff生成需要保持未改内容. patch应用失败、行号漂移和格式错误都属于接口问题. Aider等评测加入编辑协议, 分数受prompt/harness影响.

「验证」

测试可能耗时、flaky或依赖外部服务. 模型需读取失败再修复, 单轮pass@1不覆盖. 沙箱保证隔离和复现, DSec属于这一层基础设施. 验证链越稳定, reward噪声越低.

「为什么标准题强而修复弱」

标准题把定位、环境和测试准备好, 模型只生成函数. 修复任务把所有环节串联, 总成功率近似各环节条件概率乘积. 每环80%时五环仅约33%. 因而某个环节小幅改善可显著影响端到端, 模型分数不能直接外推.

## 20. 复现条件与最终边界

复现实验需要同时锁定以下五组条件.

### 20.1. 权重与配置

记录Lite/236B、Base/Instruct、revision、tokenizer、RoPE/YaRN、dtype和推理后端. total/active不要混写. 官方repo当前状态可能晚于论文, 历史实验以论文和对应release为准.

### 20.2. Prompt与解码

使用官方chat template或Base completion格式, 固定temperature、top-p、max tokens和stop. FIM只对明确支持模型使用对应special tokens. prompt差异足以改变代码抽取与pass@1.

### 20.3. Harness

固定benchmark commit、编译器、依赖、timeout和容器. 记录infra error并重试, 不混入wrong answer. 闭源对照必须写模型日期, 因为服务会更新.

### 20.4. 统计

报告题目级bootstrap区间, 多次sampling均值方差, 按语言与难度分桶. 多benchmark挑最好值会产生选择偏差. 小百分点差距在题少时保持克制.

### 20.5. 污染

检索训练近邻需要数据访问;无法访问时至少用时间外题、公开网页检索和题目相似度审计. 将疑似污染子集单列. 无法证明清洁时写明限制.

最终谱系判断可以落在模型、数据、执行三条线上.

DeepSeekMoE提供细粒度专家框架, DeepSeek-V2把MoE与MLA形成通用基座, Coder-V2从其中间checkpoint继续训练6T代码数学语言数据. 这是清晰的权重和架构关系. 第一代Coder提供数据与FIM经验, 不是直接权重父代.

CodeI/O把执行行为变成数据或任务, 可服务后续代码推理, 不属于Coder-V2已公开6T配方. DSec承载沙箱执行, 属于agent训练基础设施, 不在模型代际链上. 把三者放进同一系统时, 顺序是模型生成—环境执行—行为反馈, 各自论文解决不同问题.

Coder-V2的可靠结论是MoE通用基座可以通过大规模continue pretraining获得强代码数学能力, Lite与大模型按FIM和复杂生成分流, 128K扩大证据范围, 可验证反馈改善对齐. 其边界同样明确: active参数不等于部署成本, 长窗口不等于仓库修复, 编译通过不等于语义正确, 标准榜单领先不等于完全排除污染.

把整条训练链再按信息流展开, 起点是DeepSeek-V2中间checkpoint已经形成的tokenizer、注意力、MoE路由和通用表示. 代码网页、仓库、数学文本与自然语言被采样成序列, AR目标把每个位置变成监督; Lite额外用FIM重排一部分样本. 六万亿token更新共享参数与专家参数, 随后长上下文阶段调整位置分布, SFT改变交互格式, 奖励学习再重排候选概率. 每一阶段消费上一阶段的表示, 又可能损伤旧分布.

这条链中最容易混淆的是「底座继承」与「能力继承」. 权重从V2中间点继承是确定事实, 最终通用分数接近V2是评测观察; 某项知识是否逐条保留无法由初始化保证. 继续预训练可以强化、覆盖或重组表示. 同理, Coder第一代的数据组织经验影响V2设计, 权重并未从33B Dense直接续接.

数据质量主张可以拆成覆盖、纯度与可学习性. 迭代召回提高覆盖, 分类阈值和过滤影响纯度, 去重与mixture影响可学习性. 下游分数同时依赖三者. 只提高召回可能加入噪声, 只提高纯度可能丢长尾, 只做去重可能改变真实频率. 1B实验支持新数据整体更好, 仍需分步消融定位来源.

六万亿token的边际价值也随模型状态变化. 初期代码域与通用基座差距大, 梯度快速降低代码loss; 后期常见语法接近饱和, 新颖仓库、数学难题和长尾语言更重要. 固定mixture未必在全程最优. 动态mixture可以按验证loss调整, 论文没有声明采用, 因而不能写入配方.

若要估计有效数据, 可以按去重簇赋权. 簇$c$含$n_c$个近重复样本, 每个样本权重设$1/n_c^\alpha$, $\alpha=0$保留自然频率, $\alpha=1$让每簇总权重相同. 扫描$\alpha$并测时间外代码题, 可检验模板频率与独特信息的权衡. 公开材料没有这项实验.

代码与数学的混合还改变序列结构. 代码含较多符号、缩进和长标识符, 数学含公式与推导, 自然语言含叙述. tokenizer对三域压缩率不同, token比例不等于字节比例. 若数学每字符token更多, 10%token覆盖的原始文本可能少于10%字节. 复现应报告fertility.

338种语言的扩展需要区分识别、采样和能力. 文件扩展名或语言检测器能识别某语言, 才能进入列表; 采样器决定出现频率; 模型能力要靠该语言任务验证. 三者逐层收缩. supported list只完成第一层与部分第二层信息.

MoE为长尾语言提供潜在条件容量. 稀有语言token若能共享通用语法专家并选择少量专门专家, 可避免为每种语言训练独立模型. 路由训练不足也可能把它们送入不合适专家. 按语言统计路由熵、专家覆盖和loss, 才能判断容量是否真正服务长尾.

路由负载还受序列packing影响. 一个batch若连续包含大量同语言代码, 选择集中, 热点严重; 混合不同域可平滑专家负载, 也会破坏仓库连续性. 数据排序、batch构造和expert parallel共同决定系统效率, 这些实现细节没有在代码能力表中体现.

active parameter的概念对训练与推理也不同. 训练反向要保存激活并更新被选专家, batch触及多专家; 推理prefill一次处理长序列, 可能覆盖多数专家; decode每步token少, 专家kernel难做大矩阵. 同一21B active口径无法预测三个阶段的利用率.

模型总权重分片跨节点时, 路由token可能经过网络到远端专家. 权重放置应结合专家共现和流量, 热门专家可复制, 复制又增加显存和梯度同步. Coder-V2模型论文没有把部署拓扑固定, 第三方延迟差异可能很大.

MLA解决KV状态维度, 128K仍有位置表、attention计算和请求调度成本. 单请求能装下128K, 多并发时总cache线性叠加. 服务系统可能把cache分页、量化或卸载, 这些后续基础设施选择不属于模型训练事实.

长上下文训练的数据也决定能力. 若16K以上样本主要是拼接无关文档, 模型学到的位置外推多、依赖利用少; 若包含完整仓库、长证明和多文件关系, 远距监督更强. 报告给长度阶段, 没公开长样本组成明细. 128K规格不能替代数据审计.

长输入中的lost-in-the-middle是重要反例. 模型可能更关注开头与末尾, 中部定义利用率低. 把同一证据移动位置、保持其他token不变, 能画位置敏感曲线. 加同名干扰后再测, 可以区分字符串召回和语义选择.

FIM训练同样受长度影响. PSM把后缀移到中段前, 中段生成时前缀距离被后缀长度拉远. 长后缀可能让模型更依赖局部右侧, 忘记远处左侧. 按prefix/suffix长度二维分桶, 才能知道Lite补洞能力的有效区域.

大模型只做AR并不意味着完全不能利用右侧. 可以把任务写成自然语言, 同时给prefix和suffix, 要求输出middle. 这依赖指令理解, 输出可能带解释, 与IDE special-token协议不同. 评测应区分能力存在和接口稳定.

SFT数据若包含代码解释、修复与数学推导, 会同时影响多个benchmark. Base到Instruct增益不能只归RL. 最小对照包括Base、SFT、SFT+RL三点, 使用相同prompt或各自最佳prompt分别测. 报告给出部分阶段信息, 完整数据未发布.

奖励模型引入另一层泛化. 编译标签是确定事件, reward model预测它时可能出错. 直接运行编译器给reward更准确但昂贵且环境复杂; learned reward便宜可批量, 存在distribution shift. 两者的混合比例决定训练信号可信度.

GRPO组内标准化依赖奖励方差. 若一组全通过或全失败, 标准差接近零, 有效梯度小. curriculum可让题目难度匹配当前模型, 保持组内可区分; 论文未完整公开curriculum. 组采样越多, 计算和执行成本越高.

KL约束不仅防reward hacking, 也保存SFT语言质量. 对代码任务, 参考模型可能偏爱冗长解释, reward偏爱短可编译代码, 两者拉扯. 不同任务共用一个$\beta$未必最优. 按域设置或归一化属于可能改进, 不能写成已采用.

数学答案reward容易验证最终数值, 证明题和开放题更难. 最终正确可能来自错误推理碰巧抵消, 过程正确却格式解析失败. 若只优化答案, 模型可能缩短解释或隐藏中间步骤. 评测应同时看准确率与可审计过程.

代码reward的hidden tests也有覆盖边界. 通过有限测试不等于满足规格, 训练反复使用同一测试还可能过拟合. 动态生成测试、性质测试和对抗输入能提高可信度, 基础设施成本上升. Coder-V2公开结果不代表形式验证.

LiveCodeBench用时间切分减少污染, 题目难度和平台分布随时间变化. 比较模型必须使用同一时间窗口. 较晚模型可能见过早期窗口, 滚动评测要按模型发布日期截断. 单个汇总分隐藏月份差异.

USACO等竞赛题强调算法, 与企业代码的API、测试和维护差异很大. 高竞赛分支持规划和实现, 不证明熟悉内部框架. RepoBench补充仓库completion, SWE-Bench补充issue修复, 三类共同构成更完整画像.

RepoBench分数受context construction. 如果benchmark直接提供相关文件, 它弱化检索; 若需要模型从全仓选择, 又混入检索器. 阅读表格要检查输入构造. Lite与第一代的比较只有协议一致才有效.

Defects4J提供真实Java bug与测试, 版本构建可能失败. SWE-Bench跨Python仓库, 环境安装和patch应用复杂. Aider使用编辑交互与特定prompt. 三项都叫fixing, harness差异足以改变排序.

闭源模型对照还受服务版本影响. GPT-4-Turbo-1106与0409分开列正是必要做法. 温度、系统提示和上下文限制必须对齐. 「超过闭源」应限定具体列和日期, 不能延伸为所有代码任务.

开源权重的价值除了分数, 还包括可本地部署、继续训练和审计. 236B总权重门槛很高, Lite更易使用. 模型许可、代码许可与生成内容风险分别处理. 开源不自动提供训练数据manifest.

对于本地IDE, Lite的2.4B active有吸引力, 16B总权重仍需量化或多卡. 量化会改变router logits和代码token概率, 小扰动可能导致不同专家或语法. 必须重测FIM和长上下文, 不能沿用bf16分数.

对于云端复杂任务, 236B可批处理提高吞吐, p99延迟由路由、网络和输出长度决定. 代码回答常很长, decode占比高. active参数提供比较起点, 产品成本需要实际trace.

对于agent rollout, 模型输出命令与patch, 沙箱执行反馈. DSec可扩展这一执行面, 但Coder-V2报告中的RL不因此自动变成DSec训练. 若未来系统组合, 要记录模型版本、环境镜像、任务和reward, 防止谱系混写.

CodeI/O数据可让模型学习输入输出行为, 与编译reward互补. 编译检查静态合法, I/O检查部分语义, 单元测试检查规格样例. 三层信号强度递增、成本也增加. Coder-V2公开配方只应写已披露部分.

一个完整可证伪归因表可为每个主张配对控制项. 「新代码数据有效」对照旧数据;「数学混合促进代码」对照0%数学;「MoE提高容量效率」对照等FLOPs Dense;「128K有效」对照同token短窗口;「FIM改善补洞」对照0% FIM;「RL改善正确性」对照同SFT无RL. 缺对照的结论保持相关性语气.

消融规模也影响外推. 1B模型上数据排名稳定, 不保证236B相同, 因为大模型更能利用难数据并抵抗噪声. 小模型用于筛选经济, 关键结论最好在Lite或大模型复验. 报告提供部分跨尺度结果, 没有全矩阵.

统计显著性同样重要. HumanEval题少,90.2与某闭源差值需结合置信区间; LiveCodeBench题更多且时间新,证据更强. 多次测试挑最好checkpoint会产生选择偏差. 公开表通常不给训练随机种子方差.

模型能力随prompt变化. Coder-V2-Instruct的chat template、system prompt、代码围栏和stop规则应使用官方版本. Base适合completion, 用chat prompt会偏离训练. 比较前需检查tokenizer special token是否匹配.

128K评测还受推理后端支持. 后端若截断、RoPE配置错或cache溢出, 模型看似长上下文退化. 先用短序列logits对齐官方实现, 再扩长度. 配置错误属于复现问题, 不应归给论文.

MoE权重转换也可能错位. 专家索引、shared expert、router权重和量化布局必须一致. 一个专家遗漏不会让程序立即崩溃, 会造成隐性质量下降. 官方checksum与小样本logits校验有价值.

数据污染无法彻底排除时, 最诚实的结论是列方法和剩余风险. 时间外题、私有题、语义近邻审计和人工新题互补. 声称绝对无污染需要训练全集, 当前开放材料不支持.

安全层面, 代码模型可能生成恶意或脆弱实现. 编译reward甚至偏好可执行恶意代码. 安全SFT、静态扫描、依赖审查和沙箱分别控制不同风险. 标准代码榜不测供应链与权限.

数学与代码强也可能增加攻击能力. 开放模型部署需访问控制和审计, 同时保留研究价值. 这属于应用治理, 不改变论文模型结构. 技术解析应把能力与安全边界同时写清.

最终可以把Coder-V2看成一次多变量系统升级, 而非单个技巧. V2基座提供MoE/MLA, 6T mixture提供专业知识, FIM分流服务补全, YaRN扩展位置, SFT和GRPO调整行为. 每一项都有特定作用和失效模式, 组合结果由最弱环节限制.

当目标是函数生成, 主要看代码分布、模型容量和执行测试; 当目标是IDE补全, 再加FIM、低延迟和上下文构造; 当目标是仓库修复, 再加检索、编辑协议、构建与多轮反馈; 当目标是agent训练, 再加可扩展沙箱与长程优化. 任务越向后, 单个benchmark越难代表整体.

这套分层也解释了DSec的位置: 它进入最末的执行与训练基础设施层, 不改变Coder-V2的权重祖先. CodeI/O进入行为数据层, 不等于MoE架构. 第一代Coder进入历史方法参照, 不等于中间checkpoint. 三条边界同时保留, DeepSeek代码路线才不会被串成错误直线.

MoE负载均衡可以进一步写成可检查的统计量. 对一个batch中$B$个token、$E$个路由专家, 令$f_i$为被分配给专家$i$的token比例, $p_i$为路由概率均值. 常见辅助目标形如

$$
\mathcal L_{bal}=\alpha E\sum_{i=1}^{E}f_ip_i.
$$

当流量过度集中时, $f_i$与$p_i$在热门专家上同时变大, 惩罚上升. 系数$\alpha$过高会强迫均匀路由, 可能让本该专门化的代码模式进入次优专家; 过低又会造成热点. DeepSeekMoE路线还探索设备级均衡等机制, Coder-V2沿用基座时, 代码mixture会重新塑造$f_i$分布. 论文未给代码域每个专家的完整路由矩阵, 不能据架构名称断言均衡已经完美.

容量限制把统计偏斜变成训练损失. 若单专家最多处理$C$个token, 超额token可能被丢弃、转给次选专家或等待额外批次. 三种策略分别影响信息损失、路由质量和延迟. 即使平均负载均匀, 瞬时batch仍可能溢出. 因而应报告均值之外的最大负载、p95/p99和丢弃率.

一个可证伪的领域专门化实验可以冻结模型, 收集同规模Python、C++、数学证明和通用文本, 统计条件路由分布$q(e|d)$. 若不同域分布显著分离, 专家专门化获得直接证据; 若分布近似相同, 能力提升更可能来自共享表示或专家内部差异. 再对专家做干预屏蔽, 观察各域loss变化, 才能从相关走向因果. 单看路由热图容易把token长度、位置和频率混成领域效果.

专家干预也有反例. 屏蔽一个专家后所有任务都下降, 它可能承担通用语法; 某语言下降最大, 也可能只是该语言token更常经过该专家. 用等流量随机专家作为对照, 并保持总active capacity, 可以减少容量损失造成的假归因.

继续预训练的mixture消融需要控制优化路径. 从同一个V2中间checkpoint复制四组, 固定batch、学习率、6T或小规模等效token, 只改变配比. 若各组随机种子不同, 路由早期分化会增加方差. 最好共享短warmup前缀, 随后分支, 同时报告至少多个种子的小模型实验.

配比实验的观察量不能只用最终accuracy. 训练中记录三域validation loss, 可以看到谁在何时饱和; 最终记录代码生成、仓库补全、数学、事实QA和写作, 可以看到迁移. 若10%数学组数学loss更低且LiveCodeBench提升, 数学向代码迁移有支持; 若只MATH提升, 迁移主张应缩小.

数据召回分类器也能做阈值曲线. 对每个阈值$\tau$, 人工标注precision, 用已知代码网页集合估计recall, 再从新增数据训练同算力小模型. 分类质量与模型收益可能并不单调: 极高precision的数据重复且简单, 稍低precision可能带来有用教程和错误讨论. 直接优化分类F1未必等于优化语言模型loss.

迭代自举容易产生确认偏差. 第一轮分类器偏爱的页面进入正例, 第二轮继续寻找相似页面, 长尾格式被忽略. 为每轮保留固定人工评测集, 并加入随机探索样本, 才能检测漂移. 报告给出迭代召回思路与模型结果, 未发布每轮precision/recall, 复现者应把这项不确定性单列.

6T数据的污染审计可以利用时间和谱系. 对LiveCodeBench题目记录发布日期, 对训练网页记录抓取时间, 只保留严格早于题目的候选近邻; 再比较题面、参考解和测试的文本/AST相似度. 若网页抓取晚于截止或时间元数据缺失, 标为未知, 不应自动视为清洁.

数学污染还包括同题不同数字、翻译和解法模板. 可以规范化变量与常数后检索结构, 但许多代数题天然同构, 误报高. 最有说服力的证据是训练后新命制题和人工验证. 任何单一n-gram阈值都只能减少显式复制.

128K长度消融应对齐实际计算. 若一组16K和一组128K都训练相同token, 后者attention FLOPs更高; 若固定FLOPs, 后者能看的token更少. 两种对照回答不同问题: 固定token测位置训练收益, 固定算力测预算效率. 报告给出最终路线, 没同时给两种对照.

YaRN频率插值的效果还与内容距离分布有关. 假设大多数依赖在8K内, 训练128K主要学到位置鲁棒性, 对实际代码收益有限; 若完整项目样本中远距调用丰富, 才有直接监督. 统计训练样本中引用边的token距离直方图, 能连接数据与长测结果. 公开材料没有该直方图.

位置外推可以测相对而非绝对能力. 取同一任务, 将无关填充插入定义与调用之间, 从4K扩到128K. 语义不变, 只改变距离. 准确率下降曲线直接反映距离鲁棒性. 若加入填充后下降来自上下文干扰, 再用重复空白或随机代码两种填充区分纯位置与语义噪声.

MLA的缓存节省也应在相同精度下比较. 量化KV进一步减小字节, 可能改变长上下文准确率. 若MHA基线用bf16、MLA用量化格式, 节省来源混合. 模型论文的结构结论与推理系统的量化结论应分开.

评测大模型与Lite时, 参数规模差异会影响prompt敏感性. 大模型更能从自然语言理解补洞, Lite更依赖FIM控制token; 统一prompt可能偏向某一方. 最好同时报告官方最佳接口和统一接口, 前者回答可用上限, 后者回答迁移鲁棒性.

FIM exact match高并不代表接受率高. IDE用户可能接受语义正确但格式不同的候选, 也会拒绝虽匹配参考却不符合当前意图的候选. 线上可测acceptance、接受后保留时长和修改距离. 离线执行FIM用隐藏测试, 比字符串更接近语义, 仍缺用户意图.

RepoBench的跨文件补全可增加oracle条件. 使用真实依赖图提供相关文件得到生成上限, 使用BM25得到端到端结果, 两者差距估计检索损失. 若Lite在oracle下显著强于第一代, 说明模型条件建模提升; 只在BM25下变化可能来自context构造差异.

SWE-Bench归因还需区分resolved、patch applied、tests ran三层. patch格式错误属于编辑接口, 环境失败属于harness, 测试失败更接近语义. 只报resolved会隐藏模型已定位但少一个边界条件的进展. 错误分类能指导下一步改数据、模型还是工具.

Defects4J中的Java项目使用特定构建版本, 依赖下载和测试时间长. 模型可能给正确逻辑却不符合项目风格或API版本. 长上下文能提供版本证据, 仍需要构建反馈. 单轮静态prompt低估可迭代修复系统, 多轮又增加成本, 两者应分别报.

奖励学习若使用编译器标签, 可以按错误类型细化奖励: parse通过、type-check通过、link通过、tests通过形成阶梯. 密集信号更容易学习, 也可能让模型停在容易阶段. 最终测试reward必须占足够权重, 否则会产生大量可编译空壳.

阶梯奖励可写成

$$
r=w_pI_p+w_tI_t+w_lI_l+w_eI_e,
$$

其中各$I$表示阶段通过. 权重决定优化方向. 若$I_e=1$必然包含前面通过, 前级奖励主要帮助全失败样本排序. 论文只披露编译与ground-truth来源, 未公开这类具体组合, 因而公式用于说明设计空间.

GRPO的组内标准化还会让reward尺度在不同prompt间消失. 一个难题组奖励都低、简单题组都高, 更新看相对差异. 这有助于跨难度稳定, 也意味着组内无差异的题不学习. 采样温度影响多样性: 太低候选相似, 太高远离策略且语法差.

可验证奖励并未覆盖开放式代码解释、架构设计和安全建议. SFT与通用偏好仍负责这些任务. 若RL数据占比过高, 模型可能偏向可测试短答案, 写作质量下降. Arena-Hard与QA变化可作为行为漂移观察, 不能全归单一阶段.

通用能力的保真还应测多语. 代码数据以英文标识符和文档为主, 30%自然语言若中英比例不均, 其他语言可能退化. MMLU等英文基准不足以代表多语. 338编程语言与人类语言覆盖是两套概念.

代码安全评测可以加入CWE分类、依赖漏洞和prompt注入. 模型能生成通过功能测试的SQL拼接, 仍有注入风险. reward若只看tests, 不会惩罚安全缺陷. 静态分析和安全测试可成为额外信号, 误报也需控制.

MoE路由可能因安全样本稀少而把它们交给训练不足专家. 安全对齐通常作用共享参数与路由, 是否跨专家泛化需要专门测试. 大总参数不会自动提高安全, 条件容量甚至增加行为差异.

模型许可允许的用途与代码输出许可证仍分开. 训练含公开仓库, 近重复输出可能接近原代码. 去重降低记忆风险, 无法保证来源无关. 部署应做相似度与许可证扫描, 该步骤不属于HumanEval分数.

从计算预算看, 6T×21B active的粗略主参数训练量极大, 但不能直接用$6ND$套算, 因为attention、共享参数、MoE路由、长序列和反向通信都存在. 精确成本需逐层active FLOPs与实际token长度. 论文未公布完整账单.

Lite的2.4B active训练6T数据体现「小激活、大数据」路线. 在固定推理预算下, 多数据可提高表示; 总16B提供稀疏容量. 与Dense 7B比较时, Lite的active更小、total更大、数据更多, 没有单维公平排序.

大模型236B/21B active与闭源模型对照也缺参数透明度. 标准benchmark可以比较输出能力, 无法比较训练效率. 「达到可比性能」只针对列出的任务和版本, 不包含成本、延迟与私有数据.

论文发布时间固定在2024年6月, 后来的Coder版本、DeepSeek新模型和基础设施均不能反向成为这次训练事实. 当前官方仓库README若更新下载或说明, 历史配方仍以论文版本为锚. 时间边界是谱系准确性的必要条件.

一手证据可分三层: 论文明确给出的配置与表格, 官方仓库给出的模型卡和权重规格, 从公式与表格计算得到的派生量. 3.6T/0.6T/1.8T是6T乘配比的派生量, 应标成名义换算; 专家领域语义是待验证解释, 不能提升为事实.

同理, total/active比值可计算, 真实速度不能由比值推出. 128K是模型规格, 任意仓库任务可靠不是直接结论. 编译reward来源是事实, 完整reward结构未知. 每个陈述落到对应证据层, 可以减少技术文章的过度推断.

如果只保留一组可复现核心实验, 应选择同一V2中间checkpoint的小模型, 训练四种mixture、两种FIM、两种长度, 再以代码/数学/通用/长依赖四类验证. 全因子32组仍昂贵, 可用分阶段筛选: 先mixture, 再FIM, 再长度. 每阶段保留共同基线, 避免跨实验漂移.

统计上要为每组至少保留训练loss曲线和多个随机种子终点. 单次大训练现实中难重复, 小模型方差可估计机制稳定性. 放大后只做关键两点, 并验证排序是否保持. 这比只在1B上宣称236B结论更可靠.

可证伪条件必须与主张成对. 新数据优势若在去污染后消失, 数据泛化主张失败; 数学迁移若只提高数学、不提高算法代码, 跨域主张失败; MoE若等成本不优于Dense, 容量效率主张失败; 128K若移动证据就崩, 长距利用主张失败; GRPO若无RL对照相同, RL贡献主张失败.

反例并非削弱整篇报告, 它帮助把成果放到准确位置. Coder-V2确实把开源代码模型推到很高基准, 也确实在真实修复上留有距离. 两者同时成立. 模型能力、数据质量和系统闭环分别继续发展, 才能把标准题成绩转成稳定软件产出.

阅读时可以依次辨认模型谱系、Base/Instruct与Lite/236B, 核对任务是否需要FIM、128K或执行, 并确认评测协议和时间. 这样不会因「Coder-V2」一个名称把所有代码场景混在一起.

对研究者而言, 最有价值的开放问题是代码数学mixture的因果、MoE专家是否形成可复用技能、长上下文如何与检索共同训练、可验证reward如何覆盖真实仓库. 这些问题都能从报告已有设置出发, 又需要新增对照回答.

对工程系统而言, 模型选择只是链路一环. Lite适合高频补全, 大模型适合复杂规划, 检索提供证据,沙箱提供执行,测试提供反馈. 当某层失败时应归因到对应组件, 不把所有错误归模型, 也不把infra吞吐写成模型能力.

由此得到最终边界: DeepSeek-Coder-V2是一组基于DeepSeek-V2中间MoE checkpoint继续预训练并对齐的代码模型; 第一代Coder是方法与评测参照; CodeI/O属于行为数据方向; DSec属于执行基础设施. 四者能够构成后续系统, 在2024年6月的Coder-V2报告中仍各守其位.

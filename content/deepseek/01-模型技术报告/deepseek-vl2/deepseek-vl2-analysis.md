# DeepSeek-VL2: 动态切图与稀疏语言模型怎样协同

DeepSeek-AI 于 2024 年 12 月发布 DeepSeek-VL2 技术报告. 系列包含 Tiny, Small 与标准版三个变体, 语言模型总参数分别为 3B, 16B 与 27B, 每个 token 实际激活约 0.57B, 2.4B 与 4.1B 参数; 三者共同使用约 0.4B 参数的 SigLIP-SO400M-384 视觉编码器. 模型沿用 LLaVA 式 decoder-only 路径, 但把上一代固定双分辨率视觉编码改成动态切图, 同时把语言侧升级为 DeepSeekMoE 与 MLA.

这种组合针对两个不同成本. 动态切图让高分辨率和极端长宽比图像不必整体压到固定方形画布; MoE 降低每个语言 token 的激活参数, MLA 压缩推理时的 KV cache. 视觉 token 仍会随 tile 数增长, 因此 VL adaptor 还要把每个 tile 的 $27\times27$ 特征压到 $14\times14$. DeepSeek-VL2 的效率来自三处压缩叠加, 不能只归给 MoE.

## 1. 动态切图怎样形成视觉序列

**动态切图先选择候选网格, 再把局部 tile 与整图缩略图共同送入视觉编码器.**

### 1.1. 候选分辨率与 tile 选择

SigLIP 的原生输入是 384×384. DeepSeek-VL2 定义候选集合

$$
C_R=\{(384m,384n)\mid m,n\in\mathbb{N},\ 1\leq m,n,\ mn\leq9\}.
$$

对高为 $H$, 宽为 $W$ 的输入, 系统先保持长宽比缩放, 再计算补到每个候选分辨率所需的 padding 面积, 选择空白面积最小的 $(384m_i,384n_i)$. 缩放后的图像被切成 $m_i\times n_i$ 个 384×384 局部 tile, 另生成一个全局缩略图. 因而单图最多有 9 个局部 tile 加 1 个全局 tile.

上一代 DeepSeek-VL 同时使用 384×384 的 SigLIP 与 1024×1024 的 SAM-B, 两条固定分辨率路径分别提供粗粒度和细粒度特征. 固定 1024×1024 对超长网页, 高密度文档和极端长宽比图像不够灵活. VL2 只保留一个共享 SigLIP, 通过 tile 数改变覆盖范围, 避免整幅大图压缩后小字不可读.

动态切图的代价是视觉序列长度随面积离散增长. 候选集合还会使相近尺寸的图像落到不同网格, 产生 tile 数跳变. 报告为多图输入设置边界: 当输入图片超过 2 张时关闭动态切图. 这项限制表明单图高分辨率能力与多图上下文容量共用同一序列预算.

### 1.2. 全局视图与局部视图各自保留什么

局部 tile 保留字符, 小物体与细节, 但每块只观察图像的一部分. 全局缩略图保留页面结构与远距离关系, 分辨率却不足以读取细小内容. 两类视图由同一个 SigLIP 编码器处理, 后续通过特殊 token 拼成一个视觉序列. 语言模型可以同时利用整体布局和局部纹理, 但必须从序列位置判断局部 tile 在整图中的位置.

该设计没有让 tile 之间在视觉编码器内部直接做全局注意力. 跨 tile 关系要到语言模型层面通过自注意力建立. 这降低视觉编码成本, 却把一部分空间整合压力转给语言模型. 如果任务依赖跨越多个 tile 的细线, 表格行列或网页组件, 局部边界与二维排列编码都会影响结果.

全局缩略图也承担去重作用. 相邻局部 tile 可能分别包含同一大对象的不同部分, 语言模型若只看局部序列, 容易把它们当成多个对象. 全局视图提供整体数量和布局参照. 反过来, 全局图中的小字可能不可读, 必须回到局部 tile. 两类视图的互补需要语言模型在注意力层中学会匹配同一对象的不同尺度表示.

候选分辨率以 padding 面积最小为选择准则, 没有直接使用任务内容. 同样长宽比的低密度照片与密集网页会选择相同网格, 尽管所需细节不同. 内容自适应切图可能进一步节省 token, 但会引入区域选择器和漏检风险. VL2 选择几何规则, 优点是确定, 易复现且不依赖额外模型.

报告的定性样例覆盖自然图像, 文档, 网页 UI, meme 与 anime, 说明同一切图策略可以支持多类输入. 但报告没有按 tile 数给出准确率和延迟曲线, 也没有比较相同视觉 token 预算下的固定分辨率与动态切图. 因而可以确认动态策略提升了高分辨率适应性, 不能仅凭最终总分量化每个局部视图的独立贡献.

### 1.3. pixel shuffle 与序列排布

SigLIP 为每个 tile 输出 $27\times27=729$ 个 1152 维视觉 embedding. VL adaptor 使用 $2\times2$ pixel shuffle, 把空间网格压到 $14\times14=196$ 个 token. pixel shuffle 把邻近位置的特征重排并合并到通道维, 随后的两层 MLP 再投影到语言模型 embedding 空间. 这一步把单 tile 的语言侧序列长度缩短约 3.72 倍.

全局缩略图的 14 行各追加一个 `<tile_newline>`, 因而占 $14\times15=210$ 个 token. 局部 tile 按二维网格重排为 $(14m_i,14n_i)$, 每行末尾也加换行 token, 共 $14m_i(14n_i+1)$ 个 token. 全局视图与局部视图之间再插入一个 `<view_separator>`. 完整视觉序列长度为

$$
L_v=210+1+14m_i(14n_i+1).
$$

当 $m_i=n_i=1$ 时, 视觉序列为 421 个 token; 当 $m_in_i=9$ 且采用 3×3 网格时, 长度为 201? 这里直接代入可得 $210+1+42\times43=2017$. 也就是说, 动态切图虽然限制在 9 个局部 tile, 视觉前缀仍可超过两千 token. 特殊换行和分隔 token 没有携带图像 patch 特征, 但为语言模型提供二维行边界和视图边界.

pixel shuffle 并未把 729 恰好除以 4 得到整数. 原始网格是 27×27, 实现需要处理奇数边界后形成 14×14 输出. 报告直接给出最终 token 数, 没有逐项说明边界 padding. 因而复现时应以仓库 adaptor 实现为准, 不能只按理想 $2\times2$ 网格重排推测 shape.

视觉序列的换行 token 让一维自回归模型获得二维行结构, 但没有显式列分隔 token. 同一行内的位置由序列顺序与位置编码表达, tile 网格边界则依赖拼接规则. 如果下游实现改变局部 tile 排列顺序, 即使每块图像特征相同, 语言模型接收到的空间关系也会变化.

## 2. 语言侧的稀疏计算与缓存压缩

**共享专家承担公共模式, 路由专家提供条件容量; 视觉 token 与文本 token 共用这套稀疏计算.**

### 2.1. 三个 MoE 变体的共同路由

Tiny 使用 12 层, 64 个路由专家与 2 个共享专家, 每个 token 选择 6 个路由专家; Small 使用 27 层, 64 个路由专家; 标准版使用 30 层, 72 个路由专家. 三者都保留 2 个共享专家与 top-6 路由. 共享专家持续处理所有 token, 用于容纳跨领域的共同模式; 路由专家只处理被选中的 token, 将额外参数容量分配给不同输入分布.

Tiny 的语言模型总参数为 3B, 激活约 0.57B; Small 为 16B 与 2.4B; 标准版为 27B 与 4.1B. 视觉编码器约 0.4B 参数也在推理中运行, 因而系列最终激活规模约为 1.0B, 2.8B 与 4.5B. Figure 1 以这个合计值比较开源模型, 不是用语言模型总参数比较.

Tiny 与 Small 的路由函数为 softmax, 标准版改用 sigmoid 并加入专家校正 bias. sigmoid 路由允许各专家分数独立变化, 校正 bias 用于负载均衡. 报告没有给路由分布, 专家利用率和去掉 bias 的消融, 所以无法从表格判断标准版增量中有多少来自新路由方式.

### 2.2. MLA 解决 Decode 阶段的 KV cache

Small 与标准版采用 MLA, rank 为 512; Tiny 仍使用标准 MHA. MLA 把各注意力头的 Key 与 Value 表示压到共享低维潜变量, 推理时缓存潜变量而非每层每头的完整 KV. 详细推导应参见 [MLA 相关章节](../../../llm-guide/2-核心原理与架构/2.2-注意力机制/2.2-注意力机制.md), DeepSeek-VL2 报告主要说明它在多模态模型中的工程用途.

视觉前缀会在 Prefill 阶段一次进入语言模型, 随后生成回答. 动态切图让视觉前缀可能超过两千 token, 如果继续使用完整 KV cache, 每层缓存会随视觉 token 数, 头数和维度增长. MLA 不减少视觉前缀自身的 Prefill 计算, 但会降低这些视觉 token 在后续 Decode 阶段占据的缓存空间和读取带宽.

这一区分解释了动态切图与 MLA 的互补关系. tile 增加改善细节感知, 同时拉长视觉序列; MLA 缓解长前缀造成的推理缓存压力. MoE 又降低每个 token 的前馈计算. 三者分别作用于视觉输入分辨率, 注意力状态和参数激活, 不能互相替代.

### 2.3. 多模态 token 的路由边界

视觉 embedding 经 MLP 投影后与文本 token 进入同一个语言模型. MoE 路由器因而会同时看到视觉位置, 特殊 tile token, 用户 prompt 与回答 token. 论文没有规定视觉 token 固定进入特定专家, 也没有报告专家是否按模态分化. 从公开结构看, 路由由每个位置的隐藏状态动态决定.

这种统一路由允许视觉与语言知识共享专家容量, 也带来负载波动. 高分辨率单图会集中产生大量视觉 token, 纯文本 batch 则完全没有视觉 token. 标准版使用全局专家 bias 调节负载; 训练系统还必须在数据并行 rank 之间平衡 tile 数. 路由层与系统调度共同决定实际吞吐.

MoE 的「激活参数较少」也不等于权重显存只需保存激活部分. 部署仍要存储全部路由专家, 并在设备间安排专家并行通信. Figure 1 的横轴适合比较每 token 计算规模, 不代表总模型存储或跨卡通信成本.

视觉任务还会改变专家负载的时间分布. Prefill 时连续处理大量视觉 token, Decode 时每步只增加一个文本 token. 如果视觉与文本隐藏状态偏向不同专家, 两个阶段的通信热点可能不同. 报告只给全局负载均衡机制, 没有分别报告 Prefill 与 Decode 的专家命中率和吞吐.

Tiny 保留 MHA, 因此 KV cache 不享受 MLA 压缩, 但层数和 hidden size 更小. Small 与标准版使用 MLA 后, cache 优势会随序列和生成长度增长. 对短问答, 视觉编码与 Prefill 可能主导延迟; 对长回答和并发服务, cache 带宽与容量更重要. 报告没有给分阶段 latency, 不能用激活参数直接预测所有请求形态.

## 3. 三阶段数据与训练管线

### 3.1. 从对齐到全参数预训练

Stage 1 使用约 1.2M 条 ShareGPT4V caption 与对话样本, 训练视觉编码器和 VL adaptor, 冻结语言模型. 与常见固定视觉编码器的对齐阶段不同, VL2 还要让 SigLIP 适应动态高分辨率 tile, 因而视觉编码器并未冻结. 三个变体在该阶段都训练约 2.0B token, batch size 为 256, sequence length 为 4096.

Stage 2 解冻视觉编码器, adaptor 与语言模型全部参数, 使用约 796.5B–808.9B token 做视觉语言预训练. VL 数据约占 70%, 纯文本约占 30%. 纯文本数据用于维持基础语言能力, 视觉语言数据覆盖交错图文, caption, OCR, VQA, 图表文档, web-to-code, visual prompt, grounding 与 grounded conversation.

三个模型 Stage 2 token 数接近, 并没有随参数规模成比例增加. Tiny, Small 和标准版分别约为 798.5B, 808.9B 与 796.5B token. 因而系列比较更接近固定数据规模下扩大模型容量, 而非同时扩大数据. batch size 对 Tiny 与 Small 为 2304, 标准版为 3360; sequence length 都是 4096 并开启 sequence packing.

视觉编码器学习率是主学习率的 0.1 倍, 说明联合训练时仍限制预训练视觉权重的更新幅度. Stage 2 使用 step 调度, Stage 3 改为 constant. 报告没有公布 warmup step, step 衰减节点和各数据源采样温度, 完整训练日程不能仅凭 Table 2 复原.

next-token prediction loss 只在文本 token 上计算. 视觉 token 作为条件输入, 梯度通过语言损失回传到 adaptor 与视觉编码器. 这意味着视觉表示的学习目标由文本生成任务间接定义, 并没有额外的图像重建损失. 任务分布和回答质量会直接决定视觉编码器保留哪些信息.

### 3.2. 数据清洗比简单扩量更关键

caption 数据来源质量差异较大, 包括过短描述, 图文错配和幻觉. 团队把 OCR hint, 地点和相机等元信息, 以及原 caption 一起交给内部 captioner 重写, 再用 DeepSeek Chat 按写作质量评分过滤. 该流程提高文本质量, 但评分器是否验证视觉忠实度没有单独说明; 写得流畅的错误 caption 仍可能通过纯文本质量评分.

重写流程还会改变数据风格. 多个来源经同一 captioner 生成后, 语句结构和关注点可能趋同, 原数据的人类表达差异被削弱. 团队使用多种指令引导 caption 生成来减少重复, 又以写作质量过滤明显模板化结果. 报告没有公开过滤阈值和保留率, 无法判断质量提升与多样性损失的取舍.

文本数据占预训练的 30%, SFT 也加入 DeepSeek-V2 纯文本对话. 这不是额外视觉能力, 而是防止多模态训练使语言能力退化. 视觉 batch 与纯文本 batch 的计算路径不同, 训练系统因此准备两种流水线策略并按需切换. 报告没有给加入纯文本前后的语言榜单消融.

OCR 数据包含 LaTeX OCR, 12M RenderedText 和内部中英文文档数据. 图表与文档理解加入 PubTabNet, FinTabNet 和 Docmatix; web-to-code 使用 Websight, 部分样本由 DeepSeek V2.5 重建; visual prompt 数据在图像上叠加箭头, 框, 圆和涂画. 不同来源被统一成自回归回答格式, 使模型在同一输出空间学习识别, 定位和代码生成.

grounding 坐标归一化到 0–999, 用 `<ref>` 与 `<det>` 特殊 token 包裹对象描述和 bounding box. 训练集还加入目标不存在的负样本, 避免模型无论提问什么都输出一个框. 这种离散坐标格式便于文本解码, 精度上限受 1000 个坐标 bin 与图像缩放影响.

### 3.3. SFT 的回答长度与模型容量

Stage 3 使用约 19.5B–20.0B token 做 SFT, 所有参数继续训练, 但只监督回答和特殊 token, mask 掉 system 与用户 prompt. 数据混合多模态指令与 DeepSeek-V2 的纯文本对话, 覆盖通用 VQA, OCR, 文档, 图表, visual-to-code, 推理, grounding 和语言理解.

公开数据常见三个问题是回答过短, OCR 质量差与幻觉. 团队结合原问题, 图像和 OCR 信息重写回答. Tiny 早期版本还会在中文回答中错误插入英文词, 报告把原因指向模型容量有限与视觉语言预训练阶段中英文失衡, 因而额外构建中文图像描述和单轮, 多轮对话数据.

报告还观察到详细推理回答对 Tiny 效果较差, 简洁回答反而更合适. 这说明同一 SFT 目标不能不加区分地用于三个容量档位. 标准化长推理过程可能超过小模型稳定表示和生成的能力, 也会挤占 4096 token 序列中的图像与问题空间. 论文没有给回答长度的定量消融, 但明确记录了容量相关的数据选择.

## 4. 训练系统与评测口径

### 4.1. 学习率与并行配置

三个阶段都使用 AdamW, $eta_1=0.9$, $eta_2=0.95$, weight decay 0.1, gradient clip 1.0. 视觉编码器学习率乘数固定为 0.1. Stage 1 和 Stage 2 的主学习率按模型不同约为 $4.2\times10^{-4}$ 到 $5.4\times10^{-4}$, Stage 3 降到 $1.4\times10^{-5}$ 到 $3.0\times10^{-5}$. 调度器分别为 cosine, step 与 constant.

视觉编码器位于流水线首段, 计算形态与均匀堆叠的 LLM block 不同. 动态切图还使每条样本 tile 数不同, 如果直接分配到数据并行 rank, 某些 rank 会等待 tile 更多的样本. HAI-LLM 对视觉编码器做细粒度层切分, 并在 forward 与 backward 中跨数据并行 rank 平衡 image tile 数, 以减少 pipeline bubble.

训练同时使用流水线并行, tensor parallel 与 expert parallel. Tiny, Small 和标准版分别用 16, 33 与 42 个节点, 每节点 8 张 A100, 用时约 7, 10 与 14 天. 报告给出节点和时间, 没有给实际 GPU 利用率与故障重启成本, 因而只能得到名义卡时, 不能复原有效训练 FLOPs.

### 4.2. 文档与 OCR 结果怎样读取

在文档评测表中, Tiny 的 DocVQA 为 88.9, ChartQA 81.0, InfoVQA 66.1, TextVQA 80.7, OCRBench 809. Small 分别为 92.3, 84.5, 75.8, 83.4, 834. 标准版为 93.3, 86.0, 78.1, 84.2, 811. 模型变大时大多数项目提高, OCRBench 却由 Small 的 834 降到标准版的 811.

这个反例说明综合能力与单一 OCR 榜单不必单调一致. 标准版改变了语言模型层数, 路由专家数, 路由函数与训练系统, 不能把 OCRBench 回落归因于某一个部件. MiniCPM-V2.6 的 OCRBench 852 标注使用 CoT, 评测协议也与普通直接生成可能不同.

Figure 1 平均 MMBench v1.1, MMStar, MMMU, MathVista, AI2D 与 OCRBench, 其中 OCRBench 除以 10 映射到 0–100. 简单平均默认六项同等重要, 也会掩盖单项回退. 它适合展示激活参数与综合分数的整体位置, 不能替代逐任务表格.

参数比较还要区分视觉编码器与语言模型. DeepSeek-VL2-Tiny 的语言侧激活 0.57B, 加上 0.4B 视觉编码器后按约 1.0B 标示; 其他基线有的只报告语言参数, 有的报告总激活参数. 表格脚注用匕首标明 MoE 激活值, 但闭源模型没有可比参数. Figure 1 主要用于开源模型内部的效率位置, 不能据此比较闭源服务的真实计算量.

标准版 DocVQA 93.3 低于 Claude 3.5 Sonnet 的 95.2 与 Qwen2-VL-7B 的 94.5, ChartQA 86.0 低于 Claude 的 90.8, InfoVQA 78.1 接近但低于 Gemini-1.5-Pro 的 80.1. 报告用 competitive 或 state-of-the-art 描述不同任务, 具体读取仍应逐列比较, 不能把平均图理解为每个项目都领先.

### 4.3. 已公开结果不能回答什么

动态切图, pixel shuffle, MLA, MoE 与数据扩充在同一版本同时出现, 报告没有完整组件消融. 因而 VL2 相对 VL 的提升不能被拆成「多少来自切图, 多少来自语言架构, 多少来自数据」. 三个变体也不是只改变规模: Tiny 使用 MHA 和 softmax 路由, Small 使用 MLA, 标准版进一步改为 sigmoid 路由与校正 bias.

多图超过两张时关闭动态切图, 是实际能力边界. 28 页报告中的定性样例以单图为主, 没有系统测量多图数量, tile 数和回答长度共同增长时的效果. 4096 token 训练长度也限制视觉前缀, prompt 和回答的总预算, 不能由动态高分辨率推导出任意长视觉上下文.

视觉序列在最大 3×3 tile 下约占 2017 token, 已接近 4096 训练长度的一半. 再加 prompt 与回答后, 长文档转写或多轮对话会很快触及预算. 超过两图时关闭切图能控制长度, 代价是每张图只能使用较低细节. 论文没有给超出训练长度的外推测试.

grounding 坐标被离散到 0–999, 在高分辨率原图上一个 bin 对应多个像素. 视觉 tile 可以保留更细局部信息, 输出协议却限制坐标精度. 同时, bounding box 生成是自回归文本任务, 数字 token 的局部错误会造成框位置突变. 报告展示定性定位样例, 没有按物体尺寸分析误差.

数据构建大量使用内部 captioner, DeepSeek Chat 和 DeepSeek V2.5 重写或筛选, 但没有公开内部数据规模的完整分项, 人工抽检率与污染检查. 第三方可以复现架构和部分公开数据, 无法严格复现训练集. DeepSeek-VL2 的公开价值主要在架构, 训练配比和结果边界, 不是一份完全可复现的数据配方.

对部署者而言, 三个变体的选择应同时考虑图像 tile 数, 回答长度, 并发量与总权重存储. Tiny 的 cache 路径较传统, Small 在较低激活参数下获得 MLA, 标准版提供更强综合能力但 OCRBench 并未最高. 应用侧需要按自身文档, 网页和自然图像分布复测, 不能只按平均分选择最大模型.

### 4.4. 动态分辨率的工程边界

动态切图并不等于可以无成本提高输入分辨率. 候选网格以 384×384 为步长, 图像只要跨过候选边界, 局部 tile 数和视觉 token 数就可能阶跃增加; 即使原图像素只增加少量, prefill 延迟与显存占用也可能明显变化. 工程侧因此不能只按原图文件大小分桶, 还应按实际选中的 $(m_i,n_i)$ 网格统计请求成本. 对版式相近的文档先统一缩放或裁边, 也可能减少无信息 padding 和不必要的 tile.

报告只在单图动态切片时允许最多 9 个局部 tile, 多于两张图时直接关闭该策略, 没有给出服务端批处理的吞吐曲线. 不同请求的 tile 数不一还会造成 batch 内计算不齐, 训练阶段可以跨数据并行 rank 做负载均衡, 在线推理却需要调度器另行处理. 部署验收可以分别测量 1 tile、常见多 tile、9 tile 以及多图降级四类输入, 同时记录首 token 延迟、峰值显存和回答截断率。论文给出的序列构造与 4096 token 训练长度足以确定这些测试场景，具体性能仍需在目标服务环境中测量.

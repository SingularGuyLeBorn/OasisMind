# DeepSeek-Coder 技术报告详解

论文 [DeepSeek-Coder: When the Large Language Model Meets Programming - The Rise of Code Intelligence](https://arxiv.org/abs/2401.14196) 于 2024 年 1 月公开, 代码与模型见 [deepseek-ai/DeepSeek-Coder](https://github.com/deepseek-ai/DeepSeek-Coder). 报告给出 1.3B, 6.7B, 33B 三档 Dense 模型的 Base 与 Instruct 版本. 训练语料共 2T token, 覆盖 87 种编程语言, 上下文可靠使用范围为 16K. 这组模型同时面向从左到右生成, Fill-in-the-Middle(FIM)和跨文件补全, 因而数据的组织单位比单文件代码模型更接近真实仓库.

## 1. 仓库级语料改变了模型看到代码的方式

### 1.1. 87/10/3 配比先确定能力边界

预训练数据按 87% 源码, 10% 代码相关英文自然语言, 3% 非代码中文划分. 代码相关自然语言包括 GitHub Markdown 与 StackExchange 内容. 这部分数据承担需求说明, API 解释和错误讨论等语义, 让模型不只学习语法序列. 3% 中文维持中文输入的基本可用性, 但占比不足以把模型变成均衡的通用双语基座. 这也解释了后续 v1.5 为什么要从通用语言模型继续训练.

源码取自 2023 年 2 月以前的公开 GitHub 仓库. 清洗规则会删除平均行长超过 100, 最大行长超过 1000, 字母占比低于 25% 的文件. HTML, JSON, YAML 另有可见文本和长度条件, 用来排除压缩产物, 自动生成数据和大量结构化记录. 过滤后语料体积约为原始集合的 32.8%, 最终约 797.92 GB, 约 6.03 亿个文件. 数量减少并不能单独证明质量提升, 但 Table 3, Table 4 与跨文件消融共同给出了训练结果侧的支持.

去污染使用测试集文本的连续 10-gram. 与 HumanEval, MBPP, GSM8K, MATH 测试样本共享 10-gram 的训练内容会被剔除, 更短且不少于 3-gram 的测试文本采用精确匹配. 这种规则降低直接重复的风险, 无法排除题目改写, 同源解答或公开题库的间接重合. 报告在 LeetCode Contest 的月份分布上观察到异常高分, 因此没有把近重复过滤描述成绝对无污染.

### 1.2. 依赖排序让同仓文件形成可学习的上下文

单文件预训练把每个源文件视为独立样本, 但真实代码中的类型, 函数和配置常定义在别处. DeepSeek-Coder 用正则表达式抽取 Python `import`, C# `using`, C/C++ `include` 等关系, 把仓库表示成文件依赖图. 若文件 $u$ 被文件 $v$ 引用, 排序时尽量让 $u$ 先于 $v$ 出现. 每个文件前还加入路径注释, 使同名文件和目录层级在拼接后仍可区分.

标准拓扑排序只选择入度为 0 的节点, 遇到循环依赖会停住. 报告的 Algorithm 1 改为每轮选择当前入度最小的节点, 即使依赖图含环也能继续生成顺序. 不连通子图分别排序后再拼接. 这个顺序不保证等于构建系统的加载顺序, 也不表示模型执行了静态分析; 它只提高定义出现在使用位置之前的概率. 仓库级近重复去重也在这个阶段进行, 避免文件级去重从一个仓库中任意抽走若干文件, 破坏剩余依赖上下文.

跨文件价值由 CrossCodeEval 的消融给出. 评测将总输入限制为 2048 token, 输出上限为 50 token, 检索到的跨文件上下文最多占 512 token, 检索结果来自官方 BM25. 只用文件级语料训练后, Java, TypeScript 和 C# 的 exact match 与 edit similarity 出现下降. Python 的变化没有被报告概括为同样稳定的下降, 因而合理结论是仓库级构造对多种跨文件任务有效, 不能推广成所有语言和所有仓库布局都等量受益.

### 1.3. 仓库序列仍受上下文窗口和检索器约束

把仓库排成序列并不等于把整个仓库都放进一次推理. 预训练样本仍要切成固定长度, 超过窗口的文件会分散到不同样本. CrossCodeEval 还依赖外部 BM25 先挑出 512 token 的相关上下文. 模型处理的是检索器交付的片段, 因此最终准确率同时受检索召回, 文件排序与生成能力影响.

仓库级语料真正改变的是条件分布: 模型更经常在函数调用前见到定义, 在当前文件前见到依赖文件, 并通过路径注释区分模块. 这种训练分布更适合跨文件补全, 但不能代替编译器, 符号索引或动态执行. 对大型单体仓库, 16K 窗口仍只覆盖局部区域; 对依赖关系无法由正则识别的语言, 排序质量也会下降.

## 2. FIM 与自回归训练如何共用一个模型

### 2.1. PSM 把双侧条件改写成单向预测

常规 next-token prediction 只根据左侧序列预测下一个 token. 编辑器补全经常同时拥有光标前后的代码, 目标是生成中间缺口. FIM 将文档随机切成前缀 $f_{pre}$, 中间 $f_{middle}$ 与后缀 $f_{suf}$, 再按 Prefix-Suffix-Middle(PSM)重排:

$$
\langle|\mathrm{fim\_start}|\rangle f_{pre}\langle|\mathrm{fim\_hole}|\rangle f_{suf}\langle|\mathrm{fim\_end}|\rangle f_{middle}\langle|\mathrm{eos}|\rangle
$$

哨兵 token 划分三个片段, decoder-only Transformer 仍执行相同的 next-token prediction. 当模型开始生成 $f_{middle}$ 时, 前缀和后缀已经位于注意力可见范围内. PSM 因而没有新增双向编码器或另一套损失, 代价是改变了一部分训练序列的自然顺序. FIM 在文档级, packing 之前施加, 避免一个缺口跨越两份无关文档.

模型每次只见一种排列. 50% FIM 率表示约一半文档被改写为 PSM, 其余文档保持自然的从左到右顺序. FIM 训练得到的是根据双侧文本生成缺口的能力, 并不保证类型正确, 测试通过或跨文件符号可达. 这些属性仍取决于数据, 上下文和解码结果.

### 2.2. 50% 来自补全能力之间的消融

报告用 1.3B 架构和 Python 子集比较 0%, 50%, 100% FIM, 以及 50% Masked Span Prediction(MSP). HumanEval-FIM 随机遮住参考解答的一行, 用 exact match 衡量恢复结果. 100% FIM 在该填空任务上最好, 却得到最弱的常规代码补全表现. 训练分布完全改为重排序列后, 自然顺序生成得到的样本减少, 这项结果显示两类目标存在实际竞争.

50% PSM 比 50% MSP 更均衡, 所以最终配置采用 50% PSM. MSP 会遮蔽多个跨度并重建, 与单个光标缺口的产品输入不同. 消融只使用 1.3B 模型与 Python 子集, 能支持训练策略选择, 不能证明 50% 对所有尺寸, 语言与编辑场景都是全局最优. Table 6 的多语言单行 FIM 结果进一步表明该配置可以迁移到 Java 和 JavaScript, 但仍限于单行 exact match.

### 2.3. 模型尺寸与注意力实现服务于不同部署点

三档模型都使用 decoder-only Transformer 与 RoPE. 33B 模型采用 GQA, group size 为 8, 并使用 FlashAttention v2. GQA 让多个 query head 共享较少的 key/value head, 降低 Decode 阶段 KV cache 体积; FlashAttention v2 改变注意力计算的内存访问方式, 不改变注意力函数本身. 1.3B 与 6.7B 面向更低成本补全, 33B 提供更高生成能力.

Table 2 给出的最大学习率随规模下降: 1.3B 为 $5.3\times10^{-4}$, 6.7B 为 $4.2\times10^{-4}$, 33B 为 $3.5\times10^{-4}$. 优化器为 AdamW, $\beta_1=0.9$, $\beta_2=0.95$. 学习率分三阶段衰减, 先 warm-up 2000 步, 每阶段末降到上一阶段的 $\sqrt{1/10}$, 最终约为初始值的 10%. 报告给出 HAI-LLM 框架及 A100, H800 集群, 但没有给出可复算的总 GPU 时或能耗, 因此无法从文中比较三档模型的完整训练成本.

## 3. 长上下文与指令微调各自补哪一块

### 3.1. RoPE 线性缩放的可靠范围是 16K

仓库代码需要更长输入, DeepSeek-Coder 将 RoPE scaling factor 从 1 调到 4, base frequency 从 10000 调到 100000, 再以序列长度 16K, batch size 512 训练 1000 步. 这项改动重新分配位置旋转频率, 让模型接触扩展后的相对位置范围. 理论长度可到 64K, 报告明确把可靠输出范围限定在 16K.

理论位置上限与实际可用上下文不是同一个指标. 模型在某个长度能够接收输入, 不代表能稳定检索任意位置的信息, 也不代表能理解完整仓库依赖. 报告没有给出覆盖 64K 的检索曲线或长代码修复结果. 因此部署时应把 16K 当作已训练和观察过的工作区间, 不应把 64K 当作等质量承诺.

### 3.2. Instruct 阶段把代码基座变成问答接口

Instruct 模型从对应 Base checkpoint 出发, 使用 Alpaca 格式的高质量指令数据, 多轮对话之间用 `<|EOT|>` 分隔. 微调采用 cosine 学习率调度, warm-up 100 步, 初始学习率 $1\times10^{-5}$, batch 约 4M token, 总训练量约 2B token. 指令微调使模型学习按问题描述生成完整答案, 解释代码并维持多轮上下文.

报告没有公开指令数据的完整组成与质量筛选细节. 因此 Instruct 成绩的来源不能全部归因于预训练语料或模型尺寸. Base 与 Instruct 在 Table 3 中承担不同口径: Base 更适合衡量预训练后的代码分布建模, Instruct 更适合自然语言任务描述下的生成. 两者横向比较时必须保持 prompt 与解码设置一致.

### 3.3. v1.5 验证了通用基座的迁移价值

DeepSeek-Coder-v1.5 7B 不从零训练, 而是从 DeepSeek-LLM-7B Base 继续训练 2T token. 新配比为 70% 源码, 10% Markdown 与 StackExchange, 7% 代码相关自然语言, 7% 数学, 6% 中英双语. 它只使用 next-token prediction, 上下文为 4K, 没有沿用 FIM.

Table 10 中, HumanEval 从原 6.7B Base 的 44.7% 变为 43.2%, 代码略有回落; GSM8K 从 43.2% 升到 62.4%, MMLU 从 36.6% 升到 49.1%. 结果说明通用语言和数学基座能改善代码指令所依赖的题意理解, 同时更均衡的数据会分走纯代码容量. v1.5 没有 FIM, 也只有 4K 上下文, 因而不能取代原系列在编辑器中间补全和长仓库输入上的定位.

## 4. 评测数字回答了哪些问题

### 4.1. 生成成绩显示数据效率, 不能单独证明仓库理解

Table 3 使用 greedy 解码. DeepSeek-Coder-Base 33B 的多语言 HumanEval 平均为 50.3%, MBPP 为 66.0%; CodeLlama-Base 34B 对应为 41.0% 与 55.2%. 6.7B Base 的多语言平均为 44.7%, MBPP 为 60.6%, 在这组设置下超过 CodeLlama-Base 34B. 这说明数据构造和训练方案让较小模型获得较高的函数级生成分数, 但 HumanEval 与 MBPP 主要测试短函数, 不直接覆盖仓库依赖.

Instruct 33B 在 Python HumanEval 为 79.3%, 多语言平均 69.2%, MBPP 为 70.0%. 报告复现的 GPT-3.5-Turbo 对应为 76.2%, 64.9%, 70.8%, 因此 DeepSeek-Coder 在前两项领先, MBPP 略低. GPT-4 仍更高. DS-1000 测试数据科学库调用, Base 33B 总平均 40.2%, 高于 CodeLlama-Base 34B 的 34.3%, 补充了标准算法题之外的库调用证据.

### 4.2. LeetCode 与数学结果需要保留评测边界

LeetCode Contest 收集 2023 年 7 月至 2024 年 1 月的 180 道题, 每题约 100 个测试用例. Instruct 6.7B 与 33B 的 Pass@1 分别为 19.4% 和 27.8%, 33B 加 CoT 后为 28.9%. GPT-3.5-Turbo 为 23.3%, GPT-4-Turbo 加 CoT 为 41.8%. 33B 超过该表中的 GPT-3.5-Turbo, 与 GPT-4-Turbo 仍有明显差距.

作者观察到 DeepSeek-Coder 与 GPT-4-Turbo 在 7 月, 8 月场次得分偏高. 题目发布时间晚于主要数据截止时间可以降低直接收录概率, 不能排除提前讨论, 镜像题库或相似题. 因此 LeetCode 数字适合作为竞赛生成能力指标, 不能据此给出完全无污染的结论.

PAL 评测要求交替写自然语言步骤和可执行代码. Base 33B 在七项数学任务上的平均为 65.8%, GSM8K 为 60.7%, MATH 为 29.1%. 这些结果衡量借助程序执行的数学求解, 与纯自然语言推理口径不同. 运行代码承担精确计算后, 得分同时反映题意转写和程序生成能力.

### 4.3. 补全结果把模型定位落到具体工作流

Table 6 的单行 FIM 中, Base 33B 均值为 81.2%, 6.7B 为 80.7%. 两者相差很小, 所以报告建议代码补全优先选择 6.7B. 该建议建立在单行 exact match 上: 对低延迟 IDE 补全很有参考价值, 对多文件修复, 长函数生成和交互式解释则不能直接外推.

CrossCodeEval 把仓库级训练, 外部检索与短补全放在同一条链路中. 仓库级消融在 Java, TypeScript, C# 上下降, 支持依赖排序的作用; 但输入只给 512 token 跨文件片段, 结果仍受 BM25 召回限制. DeepSeek-Coder 留下的工程结论很明确: 训练时保留仓库结构能改善跨文件条件建模, 部署时仍需要检索器和可控上下文, FIM 比例则要在左到右生成与双侧补全之间通过消融选择.

仓库排序的收益来自训练条件分布. 路径注释保留模块身份, 依赖图让定义更可能出现在调用之前, packing 再把排序后的内容切成定长样本. 模型没有接收显式依赖边监督, 学到的仍是 token 相关性. 反射, 宏展开, 运行时导入和生成代码无法由简单正则完整识别. 对这些项目, 仓库序列只是近似视图, 不能取代语言服务器或构建系统.

文件级去重和仓库级去重的风险不同. 文件级方法能去掉模板与复制代码, 也可能从一个项目中只删定义文件而留下调用文件. 仓库级方法保住项目内部关系, 却可能保留不同仓库之间的共享组件. 报告没有公开相似度阈值, 各语言保留率与哈希实现, 因而公开材料只能复述设计原则, 无法精确重建 2T token 训练集.

FIM 控制符也是部署协议的一部分. `<|fim_start|>`, `<|fim_hole|>` 与 `<|fim_end|>` 必须由训练时同一分词器识别, PSM 次序也必须一致. 若产品侧遗漏结束标记, 交换前后缀或截断后缀, 输入就偏离训练分布. 模型生成中间片段后还要在结束 token 或长度上限处停止, 否则可能重复后缀. Table 6 的单行 exact match 没有覆盖这些集成错误.

100% FIM 在填空任务最高而左到右补全最低, 说明 FIM 并非免费的附加能力. 重排序列占比越高, 模型看到自然代码顺序的机会越少. 0% FIM 缺乏双侧条件, 50% PSM 则让两种输入都保留足够样本. 该比例在 1.3B Python 子集上选择, 后续多语言结果证明可用, 但没有证明对所有模型规模和编辑器分布均为最优.

33B 的 GQA 与 FlashAttention v2处理不同瓶颈. GQA 让多个 query head 共享 key/value head, 减少 Decode 时随历史长度增长的 KV cache. FlashAttention v2 改善 Prefill 注意力计算的内存访问, 不改变注意力函数. 报告没有给端到端吞吐或显存曲线, 所以结构上可以确认状态和访存更省, 不能补写具体加速倍数.

RoPE 线性缩放同样需要区分可表示长度与可靠长度. scaling factor 和 base frequency 改变位置旋转频率, 追加 1000 步让参数适应新位置分布. 训练序列只有 16K, 报告也把可靠输出限定在 16K. 64K 是位置参数允许的理论范围, 没有同等的训练覆盖和检索曲线. 仓库输入超过 16K 时, 先检索相关文件通常比无选择地拼接更符合报告的证据.

学习率与规模共同控制稳定性. 1.3B, 6.7B, 33B 的峰值学习率依次降低, 三阶段调度在 2000 步 warm-up 后逐段衰减. 这些数字必须与 batch, token 总量和架构一起使用. 报告没有提供随机种子, 多次训练方差与总 GPU 时, 因而表内差距不能换算为完整训练成本, 小百分点差距也没有置信区间.

Alpaca 指令格式和 `<|EOT|>` 主要改变交互接口. 约 2B token 的监督微调相对 2T 预训练很小, 但标签集中在回答顺序, 终止位置和指令遵循, 所以行为变化明显. 指令数据组成没有完整公开, Instruct 提升不能全归因于预训练语料. Base 与 Instruct 的成绩也应在相同 prompt 和解码设置下比较.

v1.5 提供另一条能力分配曲线. 它继承通用 7B 基座, 增加数学和中英数据, GSM8K 与 MMLU 提升, HumanEval 略降. 同时它没有 FIM, 上下文只有 4K. 因而代码模型不存在一个覆盖所有工作的单一排名: 函数生成, 数学, 通用语言, 双侧补全与长上下文分别由不同数据和目标控制.

四组主要代码评测也不能互相替代. HumanEval 和 MBPP 侧重短函数, DS-1000 增加真实库调用, 单行 FIM 测双侧精确补全, CrossCodeEval 加入跨文件检索. 报告没有覆盖从 issue 定位到多文件 patch 和测试验证的完整流程. 案例图展示模型能完成某些交互, 不能替代总体成功率.

LeetCode Contest 使用较新题目和每题约 100 个测试, 仍观察到 7 月和 8 月分数偏高. 时间切分能减少直接收录, 不能排除镜像, 提前讨论和同构题. CoT 把 33B 从 27.8% 提到 28.9%, 提升幅度有限, 且仍低于 GPT-4-Turbo 加 CoT 的 41.8%. 该表支持竞赛生成能力, 不支持完全无污染的断言.

许可允许研究和商业使用, 模型权重仍受 DeepSeek Model License 约束. 公开代码训练也不保证输出没有许可证或安全风险. 近重复去重服务于数据质量和污染控制, 不是输出归属检测. 实际部署仍要执行测试, 静态扫描, 依赖审查和许可证检查, 这些步骤不在论文准确率指标内.

从模型选择看, 6.7B 与 33B 的差距随任务变化. 单行 FIM 均值只差 0.5 个百分点, 短函数与竞赛题差距则更明显. 这说明补全产品的约束不是只追求最高离线准确率, 还要考虑 Decode 延迟, KV cache, 并发和候选刷新频率. 报告据此推荐 6.7B 用于补全, 该结论比笼统选择最大模型更贴合 Table 6.

CrossCodeEval 的 BM25 结果也揭示检索与生成的职责边界. 检索器负责从仓库挑选可能相关的文件片段, 模型负责结合当前文件生成最多 50 token. 如果相关定义没有进入 512 token 跨文件预算, 模型没有信息恢复它; 如果检索命中而模型仍生成错误, 才更接近条件建模问题. 评测只报告端到端分数, 没有拆分检索上限与生成上限.

DS-1000 覆盖 NumPy, Pandas, SciPy 等数据科学库, 与 HumanEval 的自包含函数不同. Base 33B 总平均 40.2% 高于 CodeLlama-Base 34B 的 34.3%, 说明训练数据中的代码相关文本和真实 API 使用模式提供了额外收益. 该分数仍低于可以直接查文档并执行调试的完整 Agent, 因为评测模型只按给定 prompt 生成答案.

程序辅助数学把自然语言步骤与代码执行交替组织. Base 33B 的七项平均 65.8% 表示模型能把部分算术和符号操作转写为程序, 并借助执行避免手算误差. 该设置不等于模型内部独立完成全部推理, 也不能与无工具数学成绩直接比较. v1.5 的数学提升进一步说明代码能力与数学数据能互相支持, 但评测协议必须保留.

报告中的数字共同指向一条可复用的训练路线: 先按仓库保存结构, 再用 FIM 与自然顺序样本共同训练, 长上下文通过位置参数修改和续训获得, 最后用指令数据改变交互方式. 每一步只处理一种限制. 仓库排序不解决长距离容量, RoPE 扩展不解决相关文件选择, FIM 不保证代码正确, SFT 也不提供编译验证. 把这些机制分开理解, 才能判断离线指标对应哪一段链路.

对于复现工作, 最可核对的材料是 Table 1 的语言集合与过滤条件, Algorithm 1 的依赖排序, Figure 3 的 FIM 消融, Table 2 的架构和学习率, 以及 Table 3 至 Table 10 的任务口径. 训练语料本身, 质量模型, 编译过滤器和指令集没有完整发布, 所以能够复现的是公开算法与评测流程, 不是逐 token 相同的模型. 这一边界也解释了为什么仅复制 87/10/3 比例不足以重现成绩.

# DeepSeek-Coder 技术报告详解

论文 [DeepSeek-Coder: When the Large Language Model Meets Programming - The Rise of Code Intelligence](https://arxiv.org/abs/2401.14196) 于 2024 年 1 月公开, 代码与模型见 [deepseek-ai/DeepSeek-Coder](https://github.com/deepseek-ai/DeepSeek-Coder). 报告给出 1.3B, 6.7B, 33B 三档 Dense 模型的 Base 与 Instruct 版本. 训练语料共 2T token, 覆盖 87 种编程语言, 上下文可靠使用范围为 16K. 这组模型同时面向从左到右生成, Fill-in-the-Middle(FIM)和跨文件补全, 因而数据的组织单位比单文件代码模型更接近真实仓库.

## 1. 仓库级语料改变了模型看到代码的方式

DeepSeek-Coder 训练的基本单位包含单个文件、仓库依赖和跨文件上下文.

### 1.1. 87/10/3 配比先确定能力边界

预训练数据按 87% 源码, 10% 代码相关英文自然语言, 3% 非代码中文划分. 代码相关自然语言包括 GitHub Markdown 与 StackExchange 内容. 这部分数据承担需求说明, API 解释和错误讨论等语义, 让模型不只学习语法序列. 3% 中文维持中文输入的基本可用性, 但占比不足以把模型变成均衡的通用双语基座. 这也解释了后续 v1.5 为什么要从通用语言模型继续训练.

源码取自 2023 年 2 月以前的公开 GitHub 仓库. 清洗规则会删除平均行长超过 100, 最大行长超过 1000, 字母占比低于 25% 的文件. HTML, JSON, YAML 另有可见文本和长度条件, 用来排除压缩产物, 自动生成数据和大量结构化记录. 过滤后语料体积约为原始集合的 32.8%, 最终约 797.92 GB, 约 6.03 亿个文件. 数量减少并不能单独证明质量提升, 但 Table 3, Table 4 与跨文件消融共同给出了训练结果侧的支持.

去污染使用测试集文本的连续 10-gram. 与 HumanEval, MBPP, GSM8K, MATH 测试样本共享 10-gram 的训练内容会被剔除, 更短且不少于 3-gram 的测试文本采用精确匹配. 这种规则降低直接重复的风险, 无法排除题目改写, 同源解答或公开题库的间接重合. 报告在 LeetCode Contest 的月份分布上观察到异常高分, 因此没有把近重复过滤描述成绝对无污染.

### 1.2. 依赖排序让同仓文件形成可学习的上下文

单文件预训练把每个源文件视为独立样本, 但真实代码中的类型, 函数和配置常定义在别处. DeepSeek-Coder 用正则表达式抽取 Python `import`, C# `using`, C/C++ `include` 等关系, 把仓库表示成文件依赖图. 若文件 $u$ 被文件 $v$ 引用, 排序时尽量让 $u$ 先于 $v$ 出现. 每个文件前还加入路径注释, 使同名文件和目录层级在拼接后仍可区分.

标准拓扑排序只选择入度为 0 的节点, 遇到循环依赖会停住. 报告的 Algorithm 1 改为每轮选择当前入度最小的节点, 即使依赖图含环也能继续生成顺序. 不连通子图分别排序后再拼接. 这个顺序不保证等于构建系统的加载顺序, 也不表示模型执行了静态分析; 它只提高定义出现在使用位置之前的概率. 仓库级近重复去重也在这个阶段进行, 避免文件级去重从一个仓库中任意抽走若干文件, 破坏剩余依赖上下文.

跨文件价值由 CrossCodeEval 的消融给出. 评测将总输入限制为 2048 token, 输出上限为 50 token, 检索到的跨文件上下文最多占 512 token, 检索结果来自官方 BM25. 只用文件级语料训练后, Java, TypeScript 和 C# 的 exact match 与 edit similarity 出现下降. Python 的变化没有被报告概括为同样稳定的下降, 因而合理结论是仓库级构造对多种跨文件任务有效, 不能推广成所有语言和所有仓库布局都等量受益.

### 1.3. 仓库序列仍受上下文窗口和检索器约束

把仓库排成序列并不等于把整个仓库都放进一次推理. 预训练样本仍要切成固定长度, 超过窗口的文件会分散到不同样本. CrossCodeEval 还依赖外部 BM25 先挑出 512 token 的相关上下文. 模型处理的是检索器交付的片段, 因此最终准确率同时受检索召回, 文件排序与生成能力影响.

仓库级语料真正改变的是条件分布: 模型更经常在函数调用前见到定义, 在当前文件前见到依赖文件, 并通过路径注释区分模块. 这种训练分布更适合跨文件补全, 但不能代替编译器, 符号索引或动态执行. 对大型单体仓库, 16K 窗口仍只覆盖局部区域; 对依赖关系无法由正则识别的语言, 排序质量也会下降.

## 2. FIM 与自回归训练如何共用一个模型

### 2.1. PSM 把双侧条件改写成单向预测

常规 next-token prediction 只根据左侧序列预测下一个 token. 编辑器补全经常同时拥有光标前后的代码, 目标是生成中间缺口. FIM 将文档随机切成前缀 $f_{pre}$, 中间 $f_{middle}$ 与后缀 $f_{suf}$, 再按 Prefix-Suffix-Middle(PSM)重排:

$$
\langle|\mathrm{fim\_start}|\rangle f_{pre}\langle|\mathrm{fim\_hole}|\rangle f_{suf}\langle|\mathrm{fim\_end}|\rangle f_{middle}\langle|\mathrm{eos}|\rangle
$$

哨兵 token 划分三个片段, decoder-only Transformer 仍执行相同的 next-token prediction. 当模型开始生成 $f_{middle}$ 时, 前缀和后缀已经位于注意力可见范围内. PSM 因而没有新增双向编码器或另一套损失, 代价是改变了一部分训练序列的自然顺序. FIM 在文档级, packing 之前施加, 避免一个缺口跨越两份无关文档.

模型每次只见一种排列. 50% FIM 率表示约一半文档被改写为 PSM, 其余文档保持自然的从左到右顺序. FIM 训练得到的是根据双侧文本生成缺口的能力, 并不保证类型正确, 测试通过或跨文件符号可达. 这些属性仍取决于数据, 上下文和解码结果.

### 2.2. 50% 来自补全能力之间的消融

报告用 1.3B 架构和 Python 子集比较 0%, 50%, 100% FIM, 以及 50% Masked Span Prediction(MSP). HumanEval-FIM 随机遮住参考解答的一行, 用 exact match 衡量恢复结果. 100% FIM 在该填空任务上最好, 却得到最弱的常规代码补全表现. 训练分布完全改为重排序列后, 自然顺序生成得到的样本减少, 这项结果显示两类目标存在实际竞争.

50% PSM 比 50% MSP 更均衡, 所以最终配置采用 50% PSM. MSP 会遮蔽多个跨度并重建, 与单个光标缺口的产品输入不同. 消融只使用 1.3B 模型与 Python 子集, 能支持训练策略选择, 不能证明 50% 对所有尺寸, 语言与编辑场景都是全局最优. Table 6 的多语言单行 FIM 结果进一步表明该配置可以迁移到 Java 和 JavaScript, 但仍限于单行 exact match.

### 2.3. 模型尺寸与注意力实现服务于不同部署点

三档模型都使用 decoder-only Transformer 与 RoPE. 33B 模型采用 GQA, group size 为 8, 并使用 FlashAttention v2. GQA 让多个 query head 共享较少的 key/value head, 降低 Decode 阶段 KV cache 体积; FlashAttention v2 改变注意力计算的内存访问方式, 不改变注意力函数本身. 1.3B 与 6.7B 面向更低成本补全, 33B 提供更高生成能力.

Table 2 给出的最大学习率随规模下降: 1.3B 为 $5.3\times10^{-4}$, 6.7B 为 $4.2\times10^{-4}$, 33B 为 $3.5\times10^{-4}$. 优化器为 AdamW, $\beta_1=0.9$, $\beta_2=0.95$. 学习率分三阶段衰减, 先 warm-up 2000 步, 每阶段末降到上一阶段的 $\sqrt{1/10}$, 最终约为初始值的 10%. 报告给出 HAI-LLM 框架及 A100, H800 集群, 但没有给出可复算的总 GPU 时或能耗, 因此无法从文中比较三档模型的完整训练成本.

## 3. 长上下文与指令微调各自补哪一块

64K 是位置扩展的理论范围, 报告明确验证的可靠输出范围是 **16K**.

### 3.1. RoPE 线性缩放的可靠范围是 16K

仓库代码需要更长输入, DeepSeek-Coder 将 RoPE scaling factor 从 1 调到 4, base frequency 从 10000 调到 100000, 再以序列长度 16K, batch size 512 训练 1000 步. 这项改动重新分配位置旋转频率, 让模型接触扩展后的相对位置范围. 理论长度可到 64K, 报告明确把可靠输出范围限定在 16K.

理论位置上限与实际可用上下文不是同一个指标. 模型在某个长度能够接收输入, 不代表能稳定检索任意位置的信息, 也不代表能理解完整仓库依赖. 报告没有给出覆盖 64K 的检索曲线或长代码修复结果. 因此部署时应把 16K 当作已训练和观察过的工作区间, 不应把 64K 当作等质量承诺.

### 3.2. Instruct 阶段把代码基座变成问答接口

Instruct 模型从对应 Base checkpoint 出发, 使用 Alpaca 格式的高质量指令数据, 多轮对话之间用 `<|EOT|>` 分隔. 微调采用 cosine 学习率调度, warm-up 100 步, 初始学习率 $1\times10^{-5}$, batch 约 4M token, 总训练量约 2B token. 指令微调使模型学习按问题描述生成完整答案, 解释代码并维持多轮上下文.

报告没有公开指令数据的完整组成与质量筛选细节. 因此 Instruct 成绩的来源不能全部归因于预训练语料或模型尺寸. Base 与 Instruct 在 Table 3 中承担不同口径: Base 更适合衡量预训练后的代码分布建模, Instruct 更适合自然语言任务描述下的生成. 两者横向比较时必须保持 prompt 与解码设置一致.

### 3.3. v1.5 验证了通用基座的迁移价值

DeepSeek-Coder-v1.5 7B 不从零训练, 而是从 DeepSeek-LLM-7B Base 继续训练 2T token. 新配比为 70% 源码, 10% Markdown 与 StackExchange, 7% 代码相关自然语言, 7% 数学, 6% 中英双语. 它只使用 next-token prediction, 上下文为 4K, 没有沿用 FIM.

Table 10 中, HumanEval 从原 6.7B Base 的 44.7% 变为 43.2%, 代码略有回落; GSM8K 从 43.2% 升到 62.4%, MMLU 从 36.6% 升到 49.1%. 结果说明通用语言和数学基座能改善代码指令所依赖的题意理解, 同时更均衡的数据会分走纯代码容量. v1.5 没有 FIM, 也只有 4K 上下文, 因而不能取代原系列在编辑器中间补全和长仓库输入上的定位.

## 4. 评测数字回答了哪些问题

### 4.1. 生成成绩显示数据效率, 不能单独证明仓库理解

Table 3 使用 greedy 解码. DeepSeek-Coder-Base 33B 的多语言 HumanEval 平均为 50.3%, MBPP 为 66.0%; CodeLlama-Base 34B 对应为 41.0% 与 55.2%. 6.7B Base 的多语言平均为 44.7%, MBPP 为 60.6%, 在这组设置下超过 CodeLlama-Base 34B. 这说明数据构造和训练方案让较小模型获得较高的函数级生成分数, 但 HumanEval 与 MBPP 主要测试短函数, 不直接覆盖仓库依赖.

Instruct 33B 在 Python HumanEval 为 79.3%, 多语言平均 69.2%, MBPP 为 70.0%. 报告复现的 GPT-3.5-Turbo 对应为 76.2%, 64.9%, 70.8%, 因此 DeepSeek-Coder 在前两项领先, MBPP 略低. GPT-4 仍更高. DS-1000 测试数据科学库调用, Base 33B 总平均 40.2%, 高于 CodeLlama-Base 34B 的 34.3%, 补充了标准算法题之外的库调用证据.

### 4.2. LeetCode 与数学结果需要保留评测边界

LeetCode Contest 收集 2023 年 7 月至 2024 年 1 月的 180 道题, 每题约 100 个测试用例. Instruct 6.7B 与 33B 的 Pass@1 分别为 19.4% 和 27.8%, 33B 加 CoT 后为 28.9%. GPT-3.5-Turbo 为 23.3%, GPT-4-Turbo 加 CoT 为 41.8%. 33B 超过该表中的 GPT-3.5-Turbo, 与 GPT-4-Turbo 仍有明显差距.

DeepSeek-Coder 与 GPT-4-Turbo 在 7 月、8 月场次的得分偏高. 题目发布时间晚于主要数据截止时间, 直接收录的概率较低, 但提前讨论、镜像题库和相似题仍可能造成数据重合. 因此 LeetCode 数字可以衡量竞赛代码生成能力, 无法单独证明评测数据完全无污染.

PAL 评测要求交替写自然语言步骤和可执行代码. Base 33B 在七项数学任务上的平均为 65.8%, GSM8K 为 60.7%, MATH 为 29.1%. 这些结果衡量借助程序执行的数学求解, 与纯自然语言推理口径不同. 运行代码承担精确计算后, 得分同时反映题意转写和程序生成能力.

### 4.3. 补全结果把模型定位落到具体工作流

Table 6 的单行 FIM 中, Base 33B 均值为 81.2%, 6.7B 为 80.7%. 两者相差很小, 所以报告建议代码补全优先选择 6.7B. 该建议建立在单行 exact match 上: 对低延迟 IDE 补全很有参考价值, 对多文件修复, 长函数生成和交互式解释则不能直接外推.

CrossCodeEval 把仓库级训练, 外部检索与短补全放在同一条链路中. 仓库级消融在 Java, TypeScript, C# 上下降, 支持依赖排序的作用; 但输入只给 512 token 跨文件片段, 结果仍受 BM25 召回限制. DeepSeek-Coder 留下的工程结论很明确: 训练时保留仓库结构能改善跨文件条件建模, 部署时仍需要检索器和可控上下文, FIM 比例则要在左到右生成与双侧补全之间通过消融选择.

仓库排序的收益来自训练条件分布. 路径注释保留模块身份, 依赖图让定义更可能出现在调用之前, packing 再把排序后的内容切成定长样本. 模型没有接收显式依赖边监督, 学到的仍是 token 相关性. 反射, 宏展开, 运行时导入和生成代码无法由简单正则完整识别. 对这些项目, 仓库序列只是近似视图, 不能取代语言服务器或构建系统.

文件级去重和仓库级去重的风险不同. 文件级方法能去掉模板与复制代码, 也可能从一个项目中只删定义文件而留下调用文件. 仓库级方法保住项目内部关系, 却可能保留不同仓库之间的共享组件. 报告没有公开相似度阈值, 各语言保留率与哈希实现, 因而公开材料只能复述设计原则, 无法精确重建 2T token 训练集.

FIM 控制符也是部署协议的一部分. `<|fim_start|>`, `<|fim_hole|>` 与 `<|fim_end|>` 必须由训练时同一分词器识别, PSM 次序也必须一致. 若产品侧遗漏结束标记, 交换前后缀或截断后缀, 输入就偏离训练分布. 模型生成中间片段后还要在结束 token 或长度上限处停止, 否则可能重复后缀. Table 6 的单行 exact match 没有覆盖这些集成错误.

100% FIM 在填空任务最高而左到右补全最低, 说明 FIM 并非免费的附加能力. 重排序列占比越高, 模型看到自然代码顺序的机会越少. 0% FIM 缺乏双侧条件, 50% PSM 则让两种输入都保留足够样本. 该比例在 1.3B Python 子集上选择, 后续多语言结果证明可用, 但没有证明对所有模型规模和编辑器分布均为最优.

33B 的 GQA 与 FlashAttention v2处理不同瓶颈. GQA 让多个 query head 共享 key/value head, 减少 Decode 时随历史长度增长的 KV cache. FlashAttention v2 改善 Prefill 注意力计算的内存访问, 不改变注意力函数. 报告没有给端到端吞吐或显存曲线, 所以结构上可以确认状态和访存更省, 不能补写具体加速倍数.

RoPE 线性缩放同样需要区分可表示长度与可靠长度. scaling factor 和 base frequency 改变位置旋转频率, 追加 1000 步让参数适应新位置分布. 训练序列只有 16K, 报告也把可靠输出限定在 16K. 64K 是位置参数允许的理论范围, 没有同等的训练覆盖和检索曲线. 仓库输入超过 16K 时, 先检索相关文件通常比无选择地拼接更符合报告的证据.

学习率与规模共同控制稳定性. 1.3B, 6.7B, 33B 的峰值学习率依次降低, 三阶段调度在 2000 步 warm-up 后逐段衰减. 这些数字必须与 batch, token 总量和架构一起使用. 报告没有提供随机种子, 多次训练方差与总 GPU 时, 因而表内差距不能换算为完整训练成本, 小百分点差距也没有置信区间.

Alpaca 指令格式和 `<|EOT|>` 主要改变交互接口. 约 2B token 的监督微调相对 2T 预训练很小, 但标签集中在回答顺序, 终止位置和指令遵循, 所以行为变化明显. 指令数据组成没有完整公开, Instruct 提升不能全归因于预训练语料. Base 与 Instruct 的成绩也应在相同 prompt 和解码设置下比较.

v1.5 提供另一条能力分配曲线. 它继承通用 7B 基座, 增加数学和中英数据, GSM8K 与 MMLU 提升, HumanEval 略降. 同时它没有 FIM, 上下文只有 4K. 因而代码模型不存在一个覆盖所有工作的单一排名: 函数生成, 数学, 通用语言, 双侧补全与长上下文分别由不同数据和目标控制.

四组主要代码评测也不能互相替代. HumanEval 和 MBPP 侧重短函数, DS-1000 增加真实库调用, 单行 FIM 测双侧精确补全, CrossCodeEval 加入跨文件检索. 报告没有覆盖从 issue 定位到多文件 patch 和测试验证的完整流程. 案例图展示模型能完成某些交互, 不能替代总体成功率.

LeetCode Contest 使用较新题目和每题约 100 个测试, 仍观察到 7 月和 8 月分数偏高. 时间切分能减少直接收录, 不能排除镜像, 提前讨论和同构题. CoT 把 33B 从 27.8% 提到 28.9%, 提升幅度有限, 且仍低于 GPT-4-Turbo 加 CoT 的 41.8%. 该表支持竞赛生成能力, 不支持完全无污染的断言.

许可允许研究和商业使用, 模型权重仍受 DeepSeek Model License 约束. 公开代码训练也不保证输出没有许可证或安全风险. 近重复去重服务于数据质量和污染控制, 不是输出归属检测. 实际部署仍要执行测试, 静态扫描, 依赖审查和许可证检查, 这些步骤不在论文准确率指标内.

从模型选择看, 6.7B 与 33B 的差距随任务变化. 单行 FIM 均值只差 0.5 个百分点, 短函数与竞赛题差距则更明显. 这说明补全产品的约束不是只追求最高离线准确率, 还要考虑 Decode 延迟, KV cache, 并发和候选刷新频率. 报告据此推荐 6.7B 用于补全, 该结论比笼统选择最大模型更贴合 Table 6.

CrossCodeEval 的 BM25 结果也揭示检索与生成的职责边界. 检索器负责从仓库挑选可能相关的文件片段, 模型负责结合当前文件生成最多 50 token. 如果相关定义没有进入 512 token 跨文件预算, 模型没有信息恢复它; 如果检索命中而模型仍生成错误, 才更接近条件建模问题. 评测只报告端到端分数, 没有拆分检索上限与生成上限.

DS-1000 覆盖 NumPy, Pandas, SciPy 等数据科学库, 与 HumanEval 的自包含函数不同. Base 33B 总平均 40.2% 高于 CodeLlama-Base 34B 的 34.3%, 说明训练数据中的代码相关文本和真实 API 使用模式提供了额外收益. 该分数仍低于可以直接查文档并执行调试的完整 Agent, 因为评测模型只按给定 prompt 生成答案.

程序辅助数学把自然语言步骤与代码执行交替组织. Base 33B 的七项平均 65.8% 表示模型能把部分算术和符号操作转写为程序, 并借助执行避免手算误差. 该设置不等于模型内部独立完成全部推理, 也不能与无工具数学成绩直接比较. v1.5 的数学提升进一步说明代码能力与数学数据能互相支持, 但评测协议必须保留.

报告中的训练路线依次处理四类约束: 按仓库保存文件结构, 混合 FIM 与自然顺序样本, 修改位置参数并续训长上下文, 再用指令数据调整交互方式. 各机制作用范围不同: 仓库排序保留文件关系, RoPE 扩展增加位置容量, FIM 学习中间补全, SFT 改变响应格式. 代码正确性和编译验证仍需另外的执行反馈, 离线指标也应对应到各自覆盖的环节.

对于复现工作, 最可核对的材料是 Table 1 的语言集合与过滤条件, Algorithm 1 的依赖排序, Figure 3 的 FIM 消融, Table 2 的架构和学习率, 以及 Table 3 至 Table 10 的任务口径. 训练语料本身, 质量模型, 编译过滤器和指令集没有完整发布, 所以能够复现的是公开算法与评测流程, 不是逐 token 相同的模型. 这一边界也解释了为什么仅复制 87/10/3 比例不足以重现成绩.

## 5. 从 GitHub 文件到训练序列

### 5.1. 数据漏斗改变的远不只是规模

[官方仓库](https://github.com/deepseek-ai/DeepSeek-Coder)把数据构造概括为四步: 收集并沿用 StarCoder 过滤规则, 解析仓库内文件依赖, 拼接依赖文件并做仓库级 MinHash 去重, 再过滤语法错误和可读性差的代码. 这条顺序把原始 GitHub 快照逐渐变成语言模型样本. 每一步都在修改经验分布: 文件过滤决定哪些语言形态可见, 依赖排序决定定义与调用的相对位置, 去重决定模板代码的权重, packing 决定哪些 token 能在同一注意力窗口中相遇.

假设原始仓库集合为 $\mathcal R$, 仓库 $r$ 内有文件 $F_r$. 过滤器 $q(f)\in\{0,1\}$ 决定文件是否保留, 依赖排序 $\pi_r$ 给出文件排列, tokenizer $\tau$ 把字符串映射成 token. 一个仓库样本可抽象为

$$
X_r=\tau\!\left(\operatorname{concat}_{f\in\pi_r(F_r),q(f)=1}
[\operatorname{path}(f),\operatorname{text}(f)]\right).
$$

训练器再把 $X_r$ 切成不超过窗口的片段. 这个表达式揭示三个损失点: 被过滤文件的信息完全消失; 依赖图只能近似真实构建关系; 超长仓库会在切片边界断开. 「项目级语料」表示项目结构参与样本构造, 不表示每次输入包含完整项目.

平均行长、最大行长和字母比例适合剔除压缩文件、机器生成 blob 与二进制误判, 也可能误伤 minified JavaScript、数值表、汇编和符号密集的形式化证明. HTML、JSON、YAML 的单独规则说明统一阈值并不适合所有语言. 若某种语言天然含较多符号或超长生成行, 过滤后的 87 种语言列表只说明 tokenizer 和数据流水支持它, 没有说明每种语言数据量充足.

数据从原始集合缩到 32.8%, 不能把被删除的 67.2% 全叫作垃圾. 其中可能包括近重复、生成文件、许可证文本、格式异常和真实但不符合阈值的代码. 质量变化应由固定算力对照训练验证. 论文的下游成绩说明最终语料有效, 没有逐项消融每条过滤规则. 如果另一个复现只照抄阈值, 源仓库时间、语言构成和去重实现不同, 结果仍会显著偏移.

### 5.2. 依赖图、环与排序误差

令有向图 $G_r=(V,E)$ 中每个顶点是一份文件. 若文件 $v$ 引用文件 $u$, 记边 $u\to v$, 目标是让 $u$ 尽量排在 $v$ 前. 无环图可用 Kahn 算法反复取入度为零的顶点. 实际仓库常有循环引用, DeepSeek-Coder 的算法每轮选当前入度最小的顶点, 删除后继续. 这等价于用局部启发式打破环, 保证每个文件最终都有位置.

设排列 $\pi$ 的违背边数为

$$
V(\pi)=\sum_{(u,v)\in E}\mathbf 1[\pi(u)>\pi(v)].
$$

理想排序希望 $V(\pi)$ 小, 在含环图中不可能为零. 最小入度启发式没有给出全局最优保证, 优点是便宜且适合海量仓库. 不连通分量分别排序再拼接, 其相对顺序没有依赖依据. 当仓库超过 16K, 哪些分量恰好落在同一片段会影响训练条件.

正则解析只能覆盖显式 import、include、using 等模式. Python 动态导入、C/C++ 宏条件、Java 反射、插件注册、生成代码和配置驱动依赖可能漏掉; 同名模块与别名又会制造假边. 依赖排序的作用因此是提高统计命中率, 不是恢复编译器语义. 一个可证伪实验应比较正则图、语言服务器图、随机文件顺序和目录顺序, 固定仓库、token 与模型, 再按真实跨文件引用类型分组报告 CrossCodeEval.

路径注释承担轻量命名空间. `src/parser.py` 和 `tests/parser.py` 内容相似, 路径能提示职责; 目录层级也让模型学到常见工程组织. 路径仍是普通 token, 没有独立图编码. 仓库重命名、monorepo 深目录和生成临时路径会带来噪声. 若评测 prompt 使用与训练完全不同的路径格式, 模型利用该信号的能力可能下降.

### 5.3. 仓库级去重与泄漏

MinHash 用 shingle 集合的 Jaccard 相似度近似判断重复. 对仓库 $r_i,r_j$, 可把规范化文件内容或拼接序列映射为集合 $S_i,S_j$, 比较

$$
J(r_i,r_j)=\frac{|S_i\cap S_j|}{|S_i\cup S_j|}.
$$

仓库级去重能够识别 fork 和大面积复制项目, 又避免从单个仓库中零散删除定义文件. 若两个仓库共享大型第三方目录但业务代码不同, 仓库相似度可能过高; 若 fork 只改了大量生成文件, 也可能逃过阈值. 官方没有公开 shingle、阈值和 canonical repo 选择策略, 第三方无法逐仓复原.

文件级和仓库级去重可以组合, 目标却有冲突. 文件级去重降低许可证、模板、vendored library 的重复权重; 仓库级保留项目内部自洽性. 一个折中方案是在仓库内保留文件, 训练采样时降低跨仓重复组件权重. 论文公开流程没有描述这种加权, 不能假定采用. 2T token 是处理后训练量, 也不等于 2T 独特语义 token.

测试污染用连续 10-gram 与短文本精确匹配筛查. 对 token 或字符序列 $b$, 若训练文档含测试样本任一连续窗口, 就剔除匹配内容. 长 $n$ 降低误报, 对变量改名、翻译、注释改写和算法同构不敏感. 代码题还可能以题解、测试、函数签名或博客形式出现, 只比较题面会漏检. 时间切分补了一层证据, 仍挡不住提前泄露和历史同题.

污染检查应同时覆盖 prompt、canonical solution、测试样例和语义近邻. 最强证据来自私有新题或发布后题目, 配合执行测试; 公开题库只做字符串去重只能降低风险. LeetCode 月份异常正是反例: 即使主要数据截止早于比赛, 某些月份仍显著偏高. 这可能来自难度变化、相似题、数据泄漏或采样噪声, 无法仅凭曲线确定原因.

### 5.4. 87/10/3 混合怎样分配梯度

若总 token 数为 $D=2\times10^{12}$, 名义配比对应代码约 1.74T, 代码相关自然语言约 0.20T, 中文约 0.06T. 实际第一阶段是 1.8T token、第二阶段长上下文 0.2T token; 若两阶段都维持同一比例, 才能直接按总量相乘. 论文给出总体和训练流程, 未逐项公布长上下文阶段的分域计数, 所以上述数字是配比换算, 不代表日志精确值.

混合训练目标可写成

$$
\mathcal L(\theta)=0.87\,\mathbb E_{x\sim P_{code}}\ell(x)+0.10\,\mathbb E_{x\sim P_{doc}}\ell(x)+0.03\,\mathbb E_{x\sim P_{zh}}\ell(x).
$$

系数按 token 采样, 不按文档或字节. Markdown 的自然语言 token 密度、代码 tokenizer 压缩率和中文切分不同, 相同原始字节会贡献不同 token 数. 87% 代码使模型把大部分容量用于语法、API 与项目模式; 13% 语言让它理解描述和注释, 但不能期待与通用 LLM 相同的百科覆盖.

数据域还会通过共享参数互相迁移. API 文档能帮助库调用, StackExchange 问答能提供错误原因, 数学文本能帮助竞赛题意. 同时存在容量竞争: v1.5 增加通用与数学比例后 MMLU、GSM8K 上升, 原始 HumanEval 略降. 这是一条观察, 不能证明每增加一个数学 token 就挤走一个代码 token 的收益. v1.5 的初始化、FIM、上下文和数据配方都变了.

## 6. 自回归与 FIM 的统一概率模型

### 6.1. 标准目标的监督密度

对 token 序列 $x_{1:T}$, decoder-only 模型最小化

$$
\mathcal L_{AR}(x)=-\sum_{t=1}^{T}\log p_\theta(x_t\mid x_{<t}).
$$

代码中的缩进、标识符、字符串与注释都进入同一类别预测. 训练器不知道某个 token 是否编译关键; 一个分号和一段许可证文本都贡献交叉熵. 数据过滤和采样由此格外重要, 它们决定算力花在哪些模式上. 从头训练表示模型参数不继承通用 checkpoint, tokenizer、结构和全部 2T token 共同建立代码分布.

自回归 loss 降低不保证程序通过. 设生成程序 $y$ 的语法、类型、测试正确性事件分别为 $S,T,E$, 语言模型优化 $p(y|x)$, benchmark 关心 $\Pr(S\cap T\cap E)$. 高频但错误的实现仍可能有高概率; 多种语义等价实现又会被 exact match 判错. 执行测试把评价从字符串概率推进到行为, 训练阶段却没有公开的大规模执行反馈目标.

### 6.2. PSM 变换的概率分解

原文档切为前缀 $P$、中段 $M$、后缀 $S$, 自然顺序联合概率为

$$
p(P,M,S)=p(P)\,p(M\mid P)\,p(S\mid P,M).
$$

PSM 重排后模型学习

$$
p(P,S,M)=p(P)\,p(S\mid P)\,p(M\mid P,S),
$$

哨兵 token 告诉模型片段角色. 真正服务补洞的是末项 $p(M\mid P,S)$, 前两项仍产生训练 loss. 后缀在缺少中段时并非自然代码连续, 模型需要学习跨哨兵的协议. FIM 能复用因果 decoder, 代价是部分 token 用于学习重排格式.

若切点 $i<j$, $P=x_{1:i},M=x_{i+1:j},S=x_{j+1:T}$. 切点采样决定缺口长度分布. 短缺口偏向单行补全, 长缺口要求函数级规划; 靠近边界的缺口几乎退化为续写. 论文说明文档级 PSM 与 FIM rate, 没完整公开所有切点分布细节. HumanEval-FIM 遮一行, 因而更直接评价短缺口.

FIM 在 packing 前施加十分关键. 若先把无关文档拼成一条再随机切, $P,M,S$ 可能跨越文档边界, 后缀不能为中段提供语义约束. 文档级变换保证三段来自同一逻辑样本. 仓库样本内部可能含多文件, 因此缺口仍可能位于一个文件, 前后条件却包含依赖文件与路径.

### 6.3. 50% 混合目标与梯度竞争

令 FIM 采样概率为 $q$, 总目标近似为

$$
\mathcal L_q=(1-q)\mathbb E\mathcal L_{AR}(X)+q\mathbb E\mathcal L_{AR}(T_{PSM}(X)).
$$

$q=0.5$ 让自然顺序与重排序列各占一半样本. 两项共享参数, 梯度可能同向也可能冲突. 标识符语义、语法和 API 知识在两种排列中共用; 顺序建模对哨兵协议的需求不同. 100% FIM 削弱自然生成, 说明冲突确实存在.

若只比较 FIM benchmark, $q=1$ 可能最好; 产品同时需要代码生成、右侧续写和中间编辑, 综合目标会选择内部点. 论文在 1.3B Python 子集上选 50%, 它是可用折中, 不是数学上普适常数. 不同 IDE 请求中 infill 占比、缺口长度和语言分布变化后, 最优 $q$ 可能移动.

MSP 与 PSM 的监督形态不同. MSP 可遮多个 span, 常需连续恢复多个缺口; PSM 把单个中段移到末尾, 与编辑器一个光标区域更匹配. 多文件重构可能有多个离散修改, PSM 也覆盖不了. 第一代 DeepSeek-Coder 的 FIM 能力应限定为单缺口生成协议.

### 6.4. FIM 推理协议与停止条件

官方 README 的输入形如 `<fim_begin>P<fim_hole>S<fim_end>`, 模型从其后生成 $M$. 三个 special token 必须由对应 tokenizer 映射为单独 ID. 普通文本拼出相似字符、使用别的 Code LLM token 或在截断时丢失后缀, 都会造成分布偏移. 训练时 PSM 顺序和产品侧协议必须完全一致.

输出终止可依赖 EOS、长度上限或模型生成的协议标记. 若停止太早, 缺口未闭合; 太晚则模型可能继续复制后缀. exact match 通常只比较目标行, 产品还需处理缩进、换行和后缀重叠. 语法正确却风格不同的候选会被 exact match 判错, edit similarity 更平滑, 执行测试更接近语义.

双侧上下文也可能互相矛盾. 前缀调用 `foo(int)`, 后缀期待字符串结果, 仓库分支或未保存编辑会让约束不一致. 模型按概率折中, 无法保证类型安全. 语言服务器提供的符号与诊断可以减少歧义, 这属于部署系统补充, 不是 FIM 目标自动获得的能力.

## 7. Tokenizer、上下文与计算复杂度

### 7.1. 代码 tokenizer 的边界

代码中空格、换行、缩进和标点都携带结构. tokenizer 若把四空格、常见运算符与关键字编码得紧凑, 16K token 能容纳更多源码; 对罕见语言或长标识符切得细, 同一窗口覆盖更少文件. 论文给出多语言范围和 special token 协议, 没公开每种语言字符/token 比, 所以「16K 项目上下文」在 Python、C++、JSON 上对应不同字节量.

词表还要同时覆盖 10% 英文代码文本和 3% 中文. 代码与自然语言共享子词能迁移 API 命名和解释, 也会竞争词表槽位. 路径、哈希、UUID 和压缩字符串容易碎成许多 token. 过滤超长行能减少这类低压缩内容, 数据规则和 tokenizer 效率因此相互影响.

特殊 FIM token 的加入必须在训练前确定 embedding. 它们不仅是分隔符, 还改变注意力角色: `fim_hole` 后的内容属于右侧条件, `fim_end` 后进入待生成中段. 模型通过大量重排样本学会协议. 把普通占位符字符串临时用于未训练模型, 不会自动产生等价能力.

### 7.2. 4K 到 16K 的两阶段训练

第一阶段在 4K 窗口训练 1.8T token, 第二阶段用 200B token 扩到 16K. 90% token 在较短窗口完成语言、代码与 API 模式学习, 10% 长阶段让模型适应更远依赖和位置编码. 这种安排比全程 16K 省算力, 因为 dense attention 的 score 计算随长度平方增长.

对单层、batch $b$、长度 $T$、宽度 $d$, QK 与 AV 前向主项约

$$
C_{attn,fwd}\approx4bT^2d,
$$

线性投影与 FFN 主项约 $O(bTd^2)$. 在 token 总数固定时, batch 中序列数随 $1/T$ 降低, attention 每 token 仍约随 $T$ 线性增长. 从 4K 到 16K, attention 的每 token 理论计算约增四倍, KV/激活内存也增长. 长阶段只占 200B 是数据与计算的折中.

训练 token 总量相同不代表 FLOPs 相同. 200B 长序列 token 的 attention 成本高于 200B 短序列 token, 还可能降低 batch 并增加通信. 报告没有给逐阶段实际 FLOPs 与 GPU 时, 不能按 90/10 token 比例推断成本也为 90/10. 33B 使用 FlashAttention v2改善 IO, 仍需执行数学上必要的 dense attention 乘加.

### 7.3. RoPE 缩放能做什么

RoPE 对第 $m$ 个位置的二维通道旋转角为 $m\theta_i$, 常见频率

$$
\theta_i=\mathrm{base}^{-2i/d_h}.
$$

增大 base 会让部分通道旋转更慢, 线性 scaling 又把位置映射到训练过的相位范围. factor 4 可把 4K 名义位置扩展到更大范围. 追加 16K 训练让参数看到新的距离分布, 避免纯外推完全脱离训练.

旋转可计算到 64K 不代表注意力能可靠利用 64K. 高频通道相位、远距检索、训练长度覆盖与中间干扰共同决定质量. 报告把可靠输出写在 16K, 没给 64K needle 或仓库任务. 因此 64K 适合作为位置实现上限, 16K 才是论文有训练支持的能力范围.

长上下文还受信息选择约束. 把十六千 token 无差别塞满无关文件, 相关定义可能被稀释; BM25 或符号检索先筛文件, 更符合 CrossCodeEval 的设置. 模型窗口与检索器互补: 窗口决定可消费上限, 检索决定上限内的信息密度.

### 7.4. GQA、KV cache 与部署档位

自回归解码的 KV cache 近似为

$$
\operatorname{Bytes}_{KV}=2bTLh_{kv}d_hs,
$$

$h_{kv}$ 是 KV 头数, $s$ 是元素字节数. GQA 让多个 query 头共享 KV, 将 $h_{kv}$ 降低, 对长上下文与并发尤其重要. group size 8 通常表示每组八个 query 头共享一组 KV, 具体头数还应以模型 config 为准.

GQA 节省 K/V 投影参数和缓存, Q/O 以及 attention score 的 query 头计算仍在. 它可能牺牲每个 query 头独立的键值表示. 33B 使用 GQA并取得高分证明该配置可用, 没有 MHA 等算力消融来证明无损. 1.3B、6.7B 与 33B 的部署差异还包含层宽深度、权重显存和生成质量, 不能把延迟差全归给 GQA.

单行 FIM 上 6.7B 与 33B 接近, 说明该任务可能较早饱和, 或 exact match 对额外能力不敏感. 更大模型在复杂生成和竞赛题上优势明显. IDE 每次按键触发补全, 延迟与并发比离线最高分更重要; 6.7B 的推荐来自这个任务—成本组合, 不是所有代码场景的统一最优.

## 8. 训练目标、规格与能力分工

### 8.1. 从头训练和继续训练是两条实验轴

原始 DeepSeek-Coder 1.3B、6.7B、33B 都从随机初始化训练 2T token. 这让 tokenizer、代码 mixture、仓库序列与 FIM 从训练早期共同塑造表示. v1.5 从 DeepSeek-LLM-7B Base 继续训练, 已经带着通用语言知识和优化轨迹. 两者的差异同时包含初始化与新数据, 不能据最终分数归因给某一项.

从头训练的优势是代码 token 不必适应已有通用表示, 大部分容量可围绕代码分布组织; 成本是通用知识也要重学. 继续训练复用语言与数学能力, 可能遭遇领域迁移和遗忘. v1.5 的 MMLU、GSM8K 上升与 HumanEval 小幅回落符合这种权衡, 还混有无 FIM、4K 上下文和 70% 代码比例变化.

最小对照应取同一个 7B 架构: 一组随机初始化吃相同 2T mixture, 一组从 LLM 初始化吃相同 mixture, tokenizer、FIM、上下文和 FLOPs 全部一致. 再测代码、语言、数学和遗忘曲线. 论文没有这组正交实验, v1.5 提供方向证据, 不提供纯初始化效应.

### 8.2. 训练超参数与稳定性

AdamW 一阶、二阶矩为

$$
m_t=0.9m_{t-1}+0.1g_t,\qquad
v_t=0.95v_{t-1}+0.05g_t^2.
$$

偏差校正后按 $\widehat m_t/(\sqrt{\widehat v_t}+\epsilon)$ 更新并解耦 weight decay. 模型越大峰值学习率越低, 符合曲率和更新稳定性的经验. 单看 $5.3,4.2,3.5\times10^{-4}$ 不能复用配方, 还需全局 batch、warmup、初始化、梯度裁剪和 token 数.

三阶段 step decay 与 DeepSeek LLM 一脉相承. 每次乘约 $\sqrt{0.1}$, 两次后峰值约剩 0.1. 大部分训练保持较高学习率, 末段收敛. 长上下文阶段是否重置或采用独立调度要按论文具体设置理解, 不能把预训练峰值直接用于 1000 步位置适配.

HAI-LLM、A100 与 H800 说明训练基础设施, 没有节点数、利用率和故障重跑就算不出总成本. 参数量也不是 FLOPs: 16K attention、FIM packing、GQA 和不同模型宽深都会改变每 token 计算. 成本比较应报告 measured FLOPs、tokens/s、GPU hours 与硬件代际.

### 8.3. Instruct 的接口学习

Base 模型学习代码联合分布, Instruct 用约 2B token 的 Alpaca 格式数据学习条件响应. 对 prompt $x$ 与回答 $y$, 目标常写成

$$
\mathcal L_{SFT}=-\sum_t\log p_\theta(y_t\mid x,y_{<t}),
$$

prompt token 可被 mask, 回答 token 提供监督. `<|EOT|>` 标记轮次结束, chat template 决定 system、instruction、response 的排列. 模型换模板后分数可能变化, 因为控制 token 与训练格式不一致.

2B 相对 2T 只有约千分之一, 但每个 token 都围绕用户请求和理想回答组织, 行为影响很大. Instruct HumanEval 上升可能来自更会理解题面、输出完整函数和停止, 也可能包含指令集中的代码知识. 指令数据未完整公开, 无法将提升全部归给格式学习.

安全模板要求拒绝非计算机或敏感问题, 这是仓库示例中的交互策略. 它不等于模型经过完整安全验证. 代码模型还面临恶意代码、依赖投毒、秘密泄露和脆弱 API 建议, HumanEval 不测这些风险. 上线时仍需权限隔离、静态扫描和执行沙箱.

## 9. 代码评测应当怎样读

### 9.1. pass@1、采样与执行器

对每道题生成一个候选并执行测试, pass@1 是通过全部测试的题目比例. 若每题采样 $n$ 个候选、其中 $c$ 个通过, 常见 pass@$k$ 无偏估计为

$$
\operatorname{pass@}k=1-\frac{\binom{n-c}{k}}{\binom nk}.
$$

$k=1$ 接近用户只接受一次答案的成功率. greedy 解码是确定性候选, sampling 的 pass@1 还要对随机种子取平均. 温度、top-p、最大长度、停止 token、prompt 和代码抽取都会改变 $c$. 报告 Table 3 使用 greedy, 和采用多样采样的外部榜单不能直接横比.

执行器定义「正确」. 测试覆盖不足时, 硬编码样例也能通过; 超时和内存上限过严会杀掉语义正确但低效的代码; 环境缺少依赖时会产生假失败. HumanEval 测自包含 Python 函数, DS-1000 依赖数据科学库版本, LeetCode 需要编译与大量隐藏测试. 分数是模型与 harness 的联合结果.

题目数决定不确定性. 对 $n$ 道二元题、观测正确率 $\hat p$, 近似标准误

$$
\operatorname{SE}(\hat p)=\sqrt{\frac{\hat p(1-\hat p)}{n}}.
$$

HumanEval 的 164 题在 $p=0.5$ 附近标准误约 3.9 个百分点. 小于数个百分点的差距可能受题目样本影响, 多语言平均还混合各语言题数. 报告没有给 bootstrap 区间, 所以 0.5 个点的 FIM 模型差距更适合读成接近.

### 9.2. exact match、edit similarity 与语义正确

单行补全 exact match 要求输出与参考字符串完全一致. `x += 1` 与 `x = x + 1` 语义相同也会判错, 格式化、引号和变量名差异同样失败. edit similarity 根据字符编辑距离给部分分, 对接近参考的输出更友好, 仍无法确认编译与行为.

令预测 $y$、参考 $r$, Levenshtein 距离为 $d(y,r)$, 一种归一化相似度为

$$
\operatorname{ES}(y,r)=1-\frac{d(y,r)}{\max(|y|,|r|)}.
$$

具体 benchmark 可能采用不同归一化, 复现要看官方脚本. 相似度高的变量替换仍可能语义错, 相似度低的等价重构可能完全正确. IDE 补全关注用户接受率, 离线 exact match 只是代理指标.

FIM 的 HumanEval-FIM 遮住参考解答一行, 上下文与目标都来自 canonical solution. 真实编辑器中前后代码可能未完成、有错误或存在多种设计. 该测试清楚衡量协议是否学会, 对复杂修复的外推有限. 多行 infill、类型检查与仓库测试能补足这块证据.

### 9.3. 短函数、真实库与跨文件任务

HumanEval、MBPP 的函数通常在单个 prompt 内自洽, 强调算法与基本 Python. MultiPL-E 把 HumanEval 翻译到多种语言, 可比较语法迁移, 题目语义仍沿用同一集合. 高分说明函数级生成强, 不代表能读 build system、修改多文件和理解大型 API 生命周期.

DS-1000 加入 NumPy、Pandas、SciPy、PyTorch 等库调用, 错误更多来自 API 名称、shape、dtype 与版本语义. 它比纯算法题接近数据科学工作, 仍是相对局部的补全. 库版本必须固定; API 更新后, 同一代码可能从通过变成失败. 报告中的 40.2% 应绑定当时 harness.

CrossCodeEval 显式加入仓库检索. 端到端概率可粗分为

$$
P(\text{correct})=P(\text{relevant context retrieved})
P(\text{correct}\mid\text{context}).
$$

两项并非严格独立乘积, 但能说明错误来源. BM25 没召回定义时, 模型只能猜; 召回后仍错, 才主要是条件生成. 官方只给端到端消融, 没报告 oracle retrieval 上限, 因而不能精确计算仓库训练对生成器的净增益.

### 9.4. PAL 与竞赛题的特殊口径

PAL 让模型把自然语言问题转为程序, 执行器完成精确计算. 成功链条包含题意解析、算法选择、代码生成、运行和答案抽取. 它可以绕开语言模型不稳定的手算, 也会在代码错误或不可形式化题目上失败. PAL 分数与纯 CoT 分数测量不同系统, 不能并排当成模型内部数学能力.

LeetCode Contest 每题大量测试比 HumanEval 更难投机, 题目又较新, 适合检查时间外泛化. 难度随比赛月份和题目级别变化, 月均分不能只解释成污染. 若七八月题目更简单, 两个模型同时偏高很正常; 若训练数据含提前题解, 也会偏高. 需要按难度、标签、发布时间和语义近邻做回归分析.

CoT 对 33B 从 27.8 到 28.9 的变化较小. 它可能帮助规划, 也可能消耗上下文、生成不可执行文字或被代码解析器截断. 提示方法的收益依赖 harness 是否正确抽取末尾代码. 只给 CoT 标签不足以判断内部推理变强.

## 10. 污染、重复与可证伪归因

### 10.1. 直接匹配没有覆盖的路径

连续 10-gram 能抓到大段原文复制, 代码中的变量重命名、格式化和注释翻译会快速破坏匹配. AST 结构、控制流和输入输出语义可能保持不变. 题解网站还会只保留算法核心, 测试 prompt 则换成新叙述. 因此字符串去污染只能给出下界.

更强流程可分四层. 文本层做 n-gram 与 MinHash; 语法层规范化变量、常量和格式后比较 AST; 语义层用代码 embedding 或执行轨迹找近邻; 时间层只选数据截止后新题. 每层都有误报: 常见二分查找本来就相似, 不能因结构相同全部删除. 报告公开的是文本和时间证据, 未声称完成四层审计.

污染还可能通过自然语言进入. StackExchange 或 Markdown 中出现题目与答案, 即使源码集合已清理, 代码相关文本仍能泄漏. 同一 benchmark 的解释、翻译和测试样例都应检索 10% 文本域. 官方描述对 HumanEval、MBPP、GSM8K、MATH 做了去污染, 具体跨域召回率没有公开.

### 10.2. 重复对梯度权重的影响

若代码片段 $z$ 出现 $k_z$ 次, 经验 loss 中它的权重与 $k_z$ 成正比:

$$
\widehat{\mathcal L}=\frac{1}{\sum_z k_z|z|}
\sum_z k_z\sum_t-\log p_\theta(z_t\mid z_{<t}).
$$

fork、模板和 vendored library 会让少数模式压过独特业务代码. 去重降低这类权重, 让固定 2T token覆盖更多变化. 但常见 API 的自然重复本身反映真实使用频率, 全部压成一次又会扭曲分布.

仓库级去重保留一个代表仓库时, 代表选择会影响语言、许可证和历史版本. 选最新 fork 可能含更多修复, 也可能有实验改动; 选星数最高会偏向热门生态. 论文没有公开规则, 所以无法判断保留版本. 能确认的是去重单位考虑了项目结构.

重复数据还影响 Scaling. nominal token 数增加, 有效新信息增长更慢, 大模型更容易记住模板. 比较 DeepSeek-Coder 与别的模型时, 2T 对 2T 只对齐了 token 数, 没对齐独特仓库与质量. 这也是「数据效率」需要谨慎使用的原因: 高分可能来自更好的数据, 也可能来自 benchmark 域更匹配.

### 10.3. 仓库排序收益如何被证伪

论文消融用文件级语料替代仓库级语料, Java、TypeScript、C# 跨文件结果下降. 这个差异同时包含依赖顺序、路径标记、仓库 packing 和去重单位. 若要归因给依赖排序, 应在相同仓库与路径下只随机打乱文件; 若要归因给路径, 应只移除路径注释; 若要归因给同仓共现, 应保持顺序但跨仓随机拼接.

一个反例是单文件算法题: 仓库排序不应带来直接信息, 若分数也大幅上升, 可能来自数据质量或总量差异. 另一个反例是动态依赖语言: 正则图命中率低时收益应变小. 若所有语言同幅提升, 需要检查是否还有未控制变量. 论文已对多语言分别报告, Python 并未展示同样稳定下降, 这提醒我们不要写成普遍定律.

### 10.4. FIM 收益如何被证伪

FIM 的直接预测是双侧补全提升, 自然左到右生成在高比例时受损. Figure 3 符合这项预测. 若在相同数据和 token 下, 0% FIM 模型在严格双侧任务与 50% 相同, 说明模型可能从提示协议临时推断, FIM必要性会减弱; 若 100% FIM 不伤生成, 梯度竞争解释需改写.

测试还应改变缺口长度、位置和数量. 训练若主要覆盖随机单段, 短中段效果最好; 文件开头、跨函数与多缺口可能下降. 后缀长度也影响约束: 后缀太短几乎退化为续写, 太长会挤占前缀. 只看单行平均无法知道模型真正利用右侧多远.

可以做后缀打乱实验. 保持前缀和缺口, 将后缀替换为另一文件. 若输出几乎不变, 模型主要依赖左侧; 若正确后缀明显提升且错误后缀系统性误导, 才证明它利用双侧条件. 再按模型规模比较, 可以判断 50% FIM 的数据是否被小模型充分吸收.

### 10.5. 从模型输出到执行反馈

离线预训练与 SFT 都把参考代码当 token 标签, 不运行每个候选. 执行验证在评测阶段出现: 编译器、单元测试或 Python 环境返回通过与失败. 因而第一代 Coder 是「会生成高概率代码的语言模型」, 还不是以执行奖励训练的 agent.

执行反馈可提供二元 reward、错误类型和测试覆盖. 语法错误能由编译器定位, 测试失败只能说明至少一个行为不符, 超时还涉及复杂度. 若未来训练把这些反馈纳入 RL 或 rejection sampling, 学习目标发生变化. 不能把后来的 CodeI/O 或 agentic training 结果倒推成第一代已经使用.

测试本身也可能被模型投机. 若公开测试进入 prompt, 模型可硬编码; 若隐藏测试覆盖窄, 特例实现也能过. 可证伪的正确性需要新增测试、性质测试、模糊测试和人工审查. pass@1 是实用指标, 不是程序形式证明.

## 11. 与 DeepSeek 谱系的准确边界

### 11.1. 与首代 DeepSeek LLM

DeepSeek LLM 是中英通用 Dense 底座, DeepSeek-Coder 是从头训练的代码专用系列. 二者都使用 decoder-only、RoPE、RMSNorm/SwiGLU 风格和 HAI-LLM 训练经验, 数据目标不同. Coder 的 87% 源码、仓库组织、50% FIM 和 16K 长阶段构成主要差异.

33B Coder 不能直接与 67B LLM 用参数排名. 模型规模、训练配比、上下文、FIM 和任务接口同时不同. LLM 67B 的代码成绩说明通用基座已有代码能力, Coder 在更小规模上强化函数、库与补全. 比较应选同一评测协议, 并区分 Base 与 Instruct.

v1.5 架起两者之间的桥: 它从 LLM 7B 继续训练代码混合, 获得更均衡的语言数学能力. 这条路线不等于原始 Coder 的第二阶段, 因为初始化和目标都变了. 原系列的 FIM/16K 定位仍独立存在.

### 11.2. 与 DeepSeek-Coder-V2

Coder-V2 属于后续模型, 架构、数据量和训练路线已经变化. 第一代是 1.3B 到 33B Dense 系列, 2T token, 项目级语料与 FIM; V2 的能力与 MoE 底座不能倒灌为第一代配置. 谱系关系在于代码专门化继续推进, 不在于权重连续或所有机制完全继承.

公平对照应分别列总参数、激活参数、训练 token、上下文、FIM、语言覆盖和执行 benchmark. MoE 的总参数不能与 Dense 参数直接对应, 新 benchmark 也可能晚于第一代. 若 V2 高分, 只能说明整套后代配方更强; 单项改进仍需消融.

第一代仓库 README 后来可能加入新模型链接或用法, 当前页面状态不证明 2024 年论文采用后来的实现. 论文 v2 与对应 release 是历史事实主锚点. 版本更新应按时间记录, 不能用最新依赖反推早期训练.

### 11.3. 与 CodeI/O

CodeI/O 关注代码的输入输出、执行或推理数据, 训练信号和任务形态与单纯仓库预训练不同. 它可以建立在已有代码模型上, 也可能使用执行产生的数据. 第一代 DeepSeek-Coder 论文没有把 CodeI/O 作为预训练阶段, 更没有公开相应执行反馈配方.

二者的连接是代码语义需要超越表面 token. Coder 用仓库共现、FIM 与代码数据学习静态模式; CodeI/O 类任务用运行行为检验语义. 前者为后者提供基座是合理谱系, 把后者写成 Coder 第一代内置目标则是事实错误.

比较两类结果时要看评测输入. HumanEval 已给自然语言 specification, 输出代码后执行; I/O reasoning 可能给测试输入输出让模型反推程序或预测运行结果. 即使都叫代码能力, 所需表示不同. 数据重合和执行 harness 也要分别审计.

### 11.4. DSec 的位置

DSec 是面向大规模 agentic training 的弹性沙箱基础设施, 解决环境隔离、生命周期、CPU 调度、内存回收与镜像加载等问题. **它位于代码模型之外的执行基础设施层**, 可以承载代码 agent rollout, 让模型生成的命令或程序在隔离环境执行并返回结果. DeepSeek-Coder 的模型谱系应沿 Coder 后续版本追踪.

第一代 Coder 的训练主线是离线 token 预测与指令微调. DSec 面向后来的交互式训练负载, 一个任务可能启动环境、执行多步工具、运行测试并收集 reward. 模型语义与基础设施职责要分开: Coder 决定输出分布, sandbox 决定输出在哪里运行、能访问什么、怎样复现和回收资源.

有 DSec 不会自动提高代码模型能力. 若 reward、任务分布和训练算法不变, 更快沙箱主要提高 rollout 吞吐; 若隔离或复现失败, 奖励会受污染. 反过来, Coder 可以在没有 DSec 的普通 harness 中评测. 两者的联系属于 agent 系统链路, 不是模型版本链.

## 12. 执行验证与真实软件任务

### 12.1. 编译通过只是第一道门

代码候选可依次接受 parse、compile、type-check、unit test、integration test 和性能测试. 前一层失败会阻断后一层. 设各层条件通过率为 $p_i$, 总成功率近似为 $\prod_i p_i$. 模型在短函数语法很强, 仓库构建、依赖版本和隐藏状态仍会拉低端到端成功率.

HumanEval 多为动态 Python, 没有静态类型阶段; MultiPL-E 的编译语言加入编译器约束; DS-1000 再加库环境. 跨仓 patch 还需安装依赖、运行测试和处理 flaky case. 因而 benchmark 分数不能直接换算工程任务成功率.

错误反馈具有信息量. parser 错误定位 token, type checker 提供符号与类型, unit test 提供输入输出反例. 第一代模型一次生成并结束, 没有报告自动读取反馈、修复再测试的闭环. 多轮 agent 能力属于另一套评测, 需要记录迭代次数和总 token/执行成本.

### 12.2. 仓库任务的上下文选择

真实 issue 往往只涉及少数文件. 全仓塞进模型既超过 16K, 又引入噪声. BM25按词项相似度检索, 对同名标识符有效; 符号图能沿定义与引用扩展; embedding 擅长语义描述. 混合检索有机会结合三类信号, DeepSeek-Coder 论文只验证了 BM25 设置, 没有提供混合方案对照.

检索预算 $K$ token 下, 目标是选择片段集合 $C$ 最大化

$$
\Pr(y^*\mid x,C),\qquad \text{s.t. }|C|\le K.
$$

相关片段太长会挤掉别的依赖, 切得太碎又丢类与函数边界. 路径注释能帮助模型识别来源. CrossCodeEval 固定 512 token 跨文件预算, 只覆盖较小 $K$ 的情形.

oracle context 实验可把检索器与模型分离: 人工或静态分析提供真正相关定义, 测生成上限; 再与 BM25 比, 差值归给检索. 没有 oracle 时, 仓库级训练收益和检索召回纠缠在一起.

### 12.3. 安全、许可证与供应链

模型可能复现训练中的许可证片段或生成与某项目相似的实现. 仓库级去重降低重复, 没有提供输出归属保证. 商用许可说明模型权重可按条款使用, 不自动清除生成代码所涉及的第三方许可证风险. 高相似输出仍需扫描与人工判断.

生成代码可能调用弃用 API、引入恶意依赖、执行 shell 或泄露环境变量. 单元测试只检查功能, 静态安全扫描、依赖锁定、最小权限和网络隔离分别处理不同风险. 指令模板中的拒答规则无法替代这些控制.

执行未知代码必须放入沙箱, 限制 CPU、内存、时间、文件和网络. DSec 属于可规模化承载这类执行的基础设施例子, 不属于第一代模型训练配方. 本地评测 harness 也需要隔离; 否则一次恶意生成即可影响宿主或后续题目.

## 13. 一组更严格的复现实验

### 13.1. 数据实验

从同一批仓库构造四版数据: 原目录顺序、随机文件顺序、依赖顺序、编译器级依赖顺序. 保持文件、token、FIM和训练算力一致, 报告单文件、跨文件、动态依赖与静态依赖任务. 如果依赖排序只在可解析静态语言提升, 机制解释得到支持; 若所有任务都涨, 需要寻找数据处理差异.

再正交改变路径注释和去重单位. 路径保留/移除测试命名空间信号, 文件/仓库去重测试结构完整性. 四因素全组合成本高, 可在 1.3B 小模型筛选, 再把关键对照放大. 论文已有 1.3B 消融传统, 这种设计与原研究尺度一致.

过滤规则要报告每语言留存率. 平均行长阈值可能对 JavaScript、JSON、汇编影响不同. 若低资源语言被删得更多, 87语言覆盖会掩盖长尾不平衡. 按语言 BPB、HumanEval 多语言和字符/token 比一起报告, 才能解释 tokenizer与过滤交互.

### 13.2. FIM 实验

取 $q\in\{0,0.25,0.5,0.75,1\}$, 固定总 token 与随机种子, 按缺口长度、位置、语言和单/跨文件分桶. 同时测左到右 HumanEval、单行 FIM、多行执行 FIM 和后缀敏感性. 综合曲线能展示 Pareto frontier, 避免用单一均值选比例.

PSM 与 SPM 排列也可对比. PSM 输入前缀再后缀, SPM 先后缀再前缀, 两者对靠近光标的信息位置不同. 第一代最终采用 PSM, 报告重点对 MSP; 若产品 prompt 更常截断前部或后部, 排列可能影响效果. 必须使用各自训练过的 special token协议.

执行型 FIM 应允许多种正确答案. 给缺口前后完整程序, 生成中段后编译并运行隐藏测试; exact match 作为风格一致性补充. 若模型执行通过率提升而 exact match 不变, 说明语义能力被字符串指标低估.

### 13.3. 长上下文实验

构造仓库 needle: 定义放在不同距离, 当前文件调用该定义, 干扰文件含同名符号. 距离从 1K 到 64K 递增, 测符号选择和执行正确率. 训练到 16K 的模型若在 16K 后明显下降, 与报告边界一致; 若仍稳定, 才有证据扩展可靠范围.

长度与检索要做二维矩阵. 无检索全量拼接、BM25 512/2K/8K、oracle context 分别测试. 更长窗口若只在无检索时有用, 产品应优先改善检索; oracle 与 BM25 差距大, 瓶颈在召回; oracle也低, 瓶颈更接近模型推理.

位置测试还应更换文件顺序. 定义始终放开头会产生位置捷径, 随机放置和双向干扰才能测远距利用. perplexity 能说明长序列建模, 不能替代具体依赖检索.

### 13.4. 污染与执行实验

为每道测试题检索训练语料最近邻, 同时报文本、AST 与 embedding 相似度. 将高相似题剔除后重算 pass@1, 并按发布日期画曲线. 若优势主要集中在高相似子集, 数据效率主张需要收缩; 若低相似新题仍领先, 泛化证据更强.

执行环境应固定镜像、编译器、依赖与资源上限, 每个候选在干净环境运行. 记录语法错、编译错、运行错、测试错、超时, 不只给总失败. 错误谱能连接训练机制: FIM 改善局部语法, 仓库上下文减少未定义符号, 大模型可能改善算法测试.

同一模型至少用三套 prompt: 论文模板、官方仓库模板和统一跨模型模板. 官方模板测最佳可用能力, 统一模板测迁移鲁棒性. 若排名随模板反转, 不能宣称模型本体绝对领先.

## 14. 证据强度与路线结论

论文与官方仓库共同记录了从头训练的三档 Dense 模型、2T token 总量与 87/10/3 mixture、1.8T 4K 加 200B 16K 的两阶段、项目级依赖排序与路径、50% PSM, 以及 Base/Instruct 权重和评测结果. 这些构成可直接核对的事实层.

机制解释具有不同强度. FIM 比例影响补洞与续写有消融支持; 仓库语料改善若干 CrossCodeEval 语言有消融支持; 依赖排序、路径、去重各自贡献尚未完全拆开. 长上下文可靠到 16K有训练和官方界定, 64K缺少同等验证. 代码高分与数据质量相关, 无法从成品对比分离过滤、规模、污染和 prompt.

首代 LLM、Coder、Coder-V2、CodeI/O、DSec位于不同坐标. LLM提供通用 Dense 参照; Coder从头建立代码专用底座; Coder-V2是后续模型代际; CodeI/O把代码与运行行为连接; DSec提供大规模执行沙箱. 后三者可以沿训练与 agent 链路连接, 都不能被写成第一代 Coder 已有组件.

DeepSeek-Coder真正留下的方法是把代码数据的结构带进预训练. 文件归属仓库, 文件之间有近似依赖, 中间补全有独立输入协议, 长上下文需要额外训练, 执行评测与字符串评测各有边界. 这些方法比某一张榜单寿命更长, 同时也要求读者保留未公开语料、污染和执行环境造成的不确定性.

## 15. 进一步拆开模型、数据与系统

### 15.1. Dense 代码模型每 token 的计算账

DeepSeek-Coder 第一代沿用 Dense decoder. 对层数 $L$、宽度 $d$、序列长度 $T$, 满头注意力加 SwiGLU 的训练 FLOPs/token 可粗估为

$$
M\approx72Ld^2+12LTd.
$$

第一项来自每层约 $12d^2$ 参数的前向与两项反向, 第二项来自 $QK^\top$ 与 $AV$ 的序列交互. 因果 attention 若跳过上三角, 序列项系数会更低; embedding、全词表 logits、归一化和 optimizer 未完整计入. 公式用于理解 16K 为什么昂贵, 不用于替代实际 profiler.

代码 tokenizer 影响 $T$. 同一个 10KB 文件若切成 2500 token, attention score 元素约为 $6.25$ million; 切成 5000 token, 元素变成四倍. 因此 tokenizer 压缩率既是数据表示问题, 也是算力问题. 多语言长尾若切分更碎, 它们在固定 token 预算内看到的源码字节更少, 每个文件的 attention 成本更高.

GQA 修正投影参数. 令 $r=h_{kv}/h_q$, Q、O 各为 $d^2$, K、V 各为 $rd^2$, attention 投影合计 $(2+2r)d^2$. 加上 SwiGLU 的 $8d^2$, 每层主参数约 $(10+2r)d^2$. group size 8 时若八个 query 共享一个 KV, $r\approx1/8$. 这减少 K/V 投影和 cache, 不按同样比例减少 query 与 score 计算.

Dense 模型的总参数大致等于每 token 激活参数, 因而 33B 的每步计算明显高于 6.7B. Coder-V2 后来采用不同架构时, 总参数与激活参数要分开看. 第一代 6.7B 在单行 FIM接近 33B, 显示更多参数的边际收益依任务变化; 这不意味着 33B 的训练计算没有价值, 它在更复杂生成上仍有更高分.

### 15.2. 仓库样本的 packing 偏差

将排序后的仓库 token 流切成 4K 或 16K 块, 边界会偏向大仓库. 一个百万 token 仓库贡献许多样本, 小仓库可能与其他仓库拼包或只贡献一块. 若按 token 均匀采样, 大项目自然获得更高权重; 若按仓库均匀, 小项目每 token 权重更高. 论文没有公开仓库采样器, 不能确定二者如何平衡.

文件顺序也会与边界交互. 被依赖文件排前, 常落入片段开头; 使用者排后, 可能跨到下一块. 如果切片无重叠, 边界附近依赖仍被断开. 滑动窗口或文档边界感知 packing 能降低断裂, 会重复部分 token 或浪费容量. 公开算法说明排序和拼接, 没给全部 packing 参数.

超大文件自身就能占满窗口, 其他依赖无法进入. 过滤最大行长不能解决文件总长度. 对这类样本, repo-level 名义仍退化为单文件片段. Cross-file 收益可能主要来自中小仓库或短文件组合. 按仓库大小分桶报告会更有解释力.

路径注释也占 token. 深目录和长文件名消耗上下文, 换来模块身份. 如果每个文件都重复完整路径, 文件很短时元数据比例可观. 一个对照实验可使用完整路径、相对短路径、哈希 ID 和无路径, 测跨文件准确率与 token 开销. 论文没有这项消融.

### 15.3. 编程语言分布的长尾

87 种语言覆盖从主流 Python、Java、C++ 到形式化、硬件描述和配置语言. 支持列表不等于均匀训练. GitHub 原始分布高度倾斜, 过滤与 tokenizer 又会改变比例. 若按自然频率采样, Python/JavaScript 等头部语言占据大部分梯度; 长尾语言受益于共享语法、英文标识符和通用算法迁移.

多语言 HumanEval 平均会掩盖语言权重. 宏平均给每种语言同等权重, 微平均按题量加权; 若所有语言题目由同一 Python canonical solution 翻译, 它主要测跨语言语法生成, 未覆盖各生态独有 API、构建工具与惯用风格. DS-1000 又几乎集中 Python 数据科学. 两类评测结合仍不能代表 87 种语言生产能力.

语言之间存在正迁移与干扰. C 与 C++ 共享语法, TypeScript 与 JavaScript共享生态, Verilog 与 Python 差异更大. 大模型可能为长尾保留更多专门表示, 小模型倾向共享. 要验证多语言数据价值, 可固定总 token, 比较单语言、相近语言组和全语言 mixture, 按头部与尾部报告 loss. 第一代论文给最终覆盖, 没给这组 mixture 消融.

配置与 Markdown 被识别为代码相关上下文, 它们对仓库理解很重要. README 解释 API, YAML 定义 CI, Dockerfile 说明环境. 同时这些文件文本重复、模板化严重, 容易抬高自然语言比例或造成泄漏. 过滤和仓库去重必须同时处理, 单纯按扩展名统计会误判信息价值.

### 15.4. 复杂度正确性与 benchmark 偏差

程序通过小测试不代表渐近复杂度合格. 一个 $O(n^2)$ 解法在样例规模通过, 大输入会超时. LeetCode 的约百个测试更可能覆盖性能边界, HumanEval 常偏功能正确. 模型训练目标对复杂度没有显式惩罚, 只能从高质量代码分布学习惯例.

对候选程序 $y$, 实用效用可以写成

$$
U(y)=\mathbf 1[\text{correct}] - \lambda_t C_t(y)-\lambda_m C_m(y)-\lambda_s R_s(y),
$$

$C_t,C_m$ 是时间与内存成本, $R_s$ 是安全风险. pass@1 只保留第一项. 两个都通过的实现可能在可维护性、依赖数量和边界处理上差异巨大. 代码助手产品还关心接受后修改量与撤销率.

生成短函数时, hidden tests 提供明确验证; 生成 SQL、并发代码、GPU kernel 或分布式配置时, 正确性更难由少量测试覆盖. 第一代报告在常见算法和数据科学库上广泛评估, 对系统编程与安全关键代码证据有限. 87语言列表不应被外推为所有领域都可靠.

执行时间也受 harness 噪声影响. 冷启动、编译缓存和共享机器负载会造成超时边界抖动. 严谨评测要重复运行、隔离资源、区分确定失败与基础设施错误. 论文汇总 pass@1, 没给执行故障细分.

### 15.5. 为什么案例不能代替分布

官方 README 展示跨 `utils.py`、`model.py`、`main.py` 的 Iris 分类补全. 这个案例直观说明路径和上文可以进入 prompt, 模型能调用前面定义. 它是能力存在性证据: 至少有一个样本成功. 它不能估计随机仓库上的成功概率, 也不能分离模型是否仅凭常见 Iris 教程模式完成.

案例还由人工选择, 失败样本不可见. 总体评价需要预注册任务集、固定检索与自动测试. CrossCodeEval承担部分作用, 输入和输出又很短. 完整 issue-to-patch benchmark 才能覆盖定位、修改、构建与回归, 第一代论文没有声称完成这一层.

阅读任何模型 demo 时都可追问三件事: 输入是否包含答案线索, 输出是否经过选择, 成功是否由执行验证. Iris 例子含全部依赖定义, 输出片段短, 没展示多次采样与失败率. 它适合解释用法, 不适合支撑 SOTA 结论.

### 15.6. 能力边界的反例集合

仓库依赖排序对显式静态 import 有效, 对运行时插件是反例; 16K 对局部项目上下文有效, 百万 token monorepo 是反例; PSM 对单缺口有效, 多文件同步重构是反例; pass@1 对确定测试有效, 非确定并发行为是反例. 反例没有否定技术, 它们标出适用域.

代码相关自然语言帮助理解 API, 过时代码文档则会误导; 近重复去重提高独特性, 常见安全惯例被过度删除也可能伤害学习; GQA 节省 cache, 极细粒度 K/V 需求可能受共享限制. 每项优化都把成本或偏差移到另一处, 需要对应实验而非统一宣传语.

污染控制也有反例. 数据截止早于题目发布时间通常很强, 题目若提前泄漏或复用旧题仍可能重合; 10-gram 清理能抓原文, 变量改写可绕过; 私有测试避免训练收录, 测试作者若按已知模型弱点挑题又会改变分布. 没有单一规则能证明绝对无污染.

### 15.7. 复现结果不一致时的排查顺序

第一层检查模型与 tokenizer: checkpoint 是 Base 还是 Instruct, revision 是否一致, FIM special token ID 与 chat template 是否来自同一仓库. tokenizer 错配可能仍能运行, 输出会严重退化. 长上下文还要确认 RoPE config 和推理框架是否读取 scaling 参数.

第二层检查 prompt 与解码. HumanEval 是否包含函数签名, stop sequence 是否截断额外测试, greedy 是否真的关闭采样, max tokens 是否足够. Instruct 模型若用 Base prompt, 或 Base 模型套 chat template, 分数没有可比性. FIM 的 PSM 顺序和后缀必须保留.

第三层检查 harness. 依赖版本、Python 版本、编译器、超时、代码抽取与测试修订都要记录. 官方仓库给 evaluation 代码入口, 论文数字仍可能基于内部版本. 小差异可来自转换和环境, 大差异通常先查模板和 stop.

第四层才判断模型或论文不可复现. 多次采样应给均值和方差, greedy 仍会受浮点 kernel 与量化影响. 量化模型的分数不能默认等于 bf16 原权重; 长上下文 KV 精度与推理后端也会改变结果.

### 15.8. 从第一代走向 Agent 的必要增量

一个代码生成模型接到任务 $x$, 产生程序 $y$. Agent 还要选择文件、调用搜索、编辑、运行测试、读取错误并迭代. 状态从单个 prompt 扩展为

$$
s_t=(\text{repository},\text{conversation},\text{tool outputs},\text{workspace state}),
$$

动作包括文本生成、工具调用与文件修改. 第一代 Coder 提供动作模型的一部分, 没有训练完整状态转移策略.

Agent 成功率受模型、工具协议、检索、执行环境和预算共同影响. 更强 Coder 可能减少每轮错误, 稳定沙箱保证反馈可信, harness 决定奖励. DSec解决执行基础设施规模化, 不能代替策略训练; CodeI/O提供行为相关数据, 不能自动赋予多步规划; Coder-V2提供后代模型能力, 也需要工具系统.

因此从 Coder 到 Agent 的路线不是把上下文再拉长就结束. 还需可恢复环境、变更隔离、测试生成、错误归因、长程信用分配和成本控制. 第一代报告的仓库数据、FIM 与 16K 是重要基础, 能覆盖的仍主要是条件生成和局部跨文件补全.

### 15.9. 最终阅读坐标

数据坐标是「公开 GitHub 截止时间、项目级处理、87/10/3、2T」; 目标坐标是「自然 next-token 与 50% PSM」; 长度坐标是「1.8T@4K + 200B@16K」; 模型坐标是「1.3B/6.7B/33B Dense Base 与 Instruct」; 评测坐标覆盖函数、库调用、FIM、跨文件、竞赛与 PAL. 任何结论离开这些坐标都需新证据.

最强结论是仓库结构和 FIM 可在统一 decoder 中形成实用代码能力, 6.7B 在低延迟补全上尤其有吸引力, 33B 在复杂生成上更强. 较弱结论包括每项过滤规则的独立收益、64K 可靠性、绝对无污染和仓库全局理解. 这些不是论文已经证明的内容.

谱系坐标则阻止概念串线. 首代 LLM解释通用基座, 第一代 Coder解释从头代码训练, v1.5探索通用初始化, Coder-V2进入新模型代际, CodeI/O关注代码与行为数据, DSec承载大规模交互执行. 技术可以组合, 历史事实必须按各自论文与发布时间落位.

## 16. 把结论落回可检查的量

### 16.1. 数据量的三种分母

代码语料可以按文件、字节或 token 计数. 约 6.03 亿文件与 797.92GB 描述过滤后静态集合, 2T token 描述训练消费量. 一个文件可能跨 epoch 或采样阶段被读取多次, 长文件贡献更多 token, tokenizer 又让不同语言每字节 token 数不同. 三个数字不能互相简单相除后当作平均文件长度, 因为是否包含自然语言域、压缩单位和多阶段采样口径可能不同.

若要复现 mixture, 至少应为每域报告

$$
(N_{repo},N_{file},B_{raw},B_{kept},D_{unique},D_{sampled}),
$$

分别对应仓库数、文件数、原始/保留字节、独特 token 与实际采样 token. $D_{sampled}>D_{unique}$ 时存在重复采样, 不等于数据污染; 它可能是为了让小域达到 3% 或 10%. 官方只公开其中部分量, 所以 87/10/3 可复现采样比例, 无法复原底层集合.

仓库截止时间为 2023 年 2 月以前, 也需要区分 commit 时间、仓库抓取时间和文件历史时间. 一个 2022 年创建的仓库可能在截止后更新; snapshot 若按抓取时当前主分支, 内容时间由采集规则决定. 论文给出来源截止以支持污染讨论, 没公开完整 manifest. 时间外评测因此是风险降低, 不是形式证明.

### 16.2. 依赖排序的定量指标

除了下游准确率, 排序质量本身可以度量. 对解析到的边集合 $E$, forward-edge ratio 为

$$
R_{forward}(\pi)=\frac{1}{|E|}\sum_{(u,v)\in E}\mathbf 1[\pi(u)<\pi(v)].
$$

随机排序期望接近 0.5, 理想 DAG 拓扑序为 1, 含环图上限低于 1. 报告的最小入度算法应显著提高该比例. 再统计同一依赖对落入同一训练块的概率 $R_{window}$, 才能知道排序收益是否被 packing 保留下来.

$R_{forward}$ 高也不保证有效. import 边可能只关联很小符号, 真正补全依赖的是另一条未解析动态边. 可以按静态分析确认的符号引用加权, 或统计目标补全所需定义是否在前文. CrossCodeEval 的任务级结果是终点指标, 中间指标能解释失败发生在 parser、排序、packing 还是模型.

### 16.3. FIM 数据的有效监督比例

50% FIM rate 按文档采样时, FIM token 比例未必正好 50%. 长短文档权重、packing 和 special token 都会改变. 若每个被选文档只重排一次, 其中前缀、后缀和中段的所有 token 仍参加 AR loss; 真正位于 $M$、直接训练双侧生成的 token 占比还要乘平均中段长度比.

设文档 $i$ 长度 $T_i$, FIM 指示 $z_i$, 中段长度 $m_i$, 则双侧目标 token 比例近似

$$
\rho_{middle}=\frac{\sum_i z_i m_i}{\sum_i T_i+\sum_i z_i c},
$$

$c$ 为 special token 开销. $q=0.5$ 只控制 $z_i$ 的期望, $\rho_{middle}$ 取决于切点. 若中段平均占三分之一, 直接补洞 token 远低于一半. 这也是复现 FIM 时必须说明切点分布的原因.

FIM 还能改变跨 token 距离. 自然序列中相邻的中段与前缀被后缀隔开, 生成中段时离前缀尾部更远; 后缀则紧邻协议标记. 模型是否更依赖后缀, 会受位置和截断影响. 后缀敏感性实验比只报 exact match 更能解释条件利用.

### 16.4. 长阶段究竟学到了什么

200B@16K 同时改变上下文长度、位置分布和训练时间. 若模型在所有短任务上继续提升, 一部分来自额外 200B token; 长任务改善才可能来自长度适配. 最小对照需要一组继续用 4K 训练相同 200B 的 checkpoint, 与 16K 组在相同总 token 下比较.

还可设计长度课程: 4K、8K、16K渐进与直接16K对比. 渐进训练可能更稳定, 直接长序列提供更多远距样本. 论文报告 factor、base、1000步位置调整等具体策略, 没给所有课程消融. 因此能够确认最终模型支持16K, 不能确认当前扩展方法全局最优.

短 benchmark 若因长阶段下降, 可能来自学习率续训、数据分布或位置缩放改变. 只测长任务会漏掉回归. 完整报告应同时保留4K函数生成、16K检索和超过16K外推, 用三段曲线确定收益与代价.

### 16.5. Base 与 Instruct 的公平接口

Base 完成 prompt 中已有代码, Instruct 响应自然语言命令. 给 Base 一个聊天模板会产生陌生控制 token, 给 Instruct 一个裸函数前缀又可能输出解释文字. 横向比较需要为每个模型使用官方最佳模板, 这测产品能力; 也要给统一 canonical prompt, 这测接口鲁棒性. 两个问题不能混成一张分数.

代码抽取规则也应公开. Instruct 常输出 Markdown fence和解释, Base 常直接续写. 若 harness 只取第一个 code block, 没 fence 的 Base 可能处理不同; 若把全部文本送编译器, Instruct 会因说明文字失败. 官方评测一般按模型类型适配, 外部复现必须记录 parser.

停止规则同样影响 pass@1. 在函数结束处停止能避免模型继续生成测试或下一函数; 太早会截断代码. 使用 EOS、特定换行或最大长度会产生不同结果. 模型能力差距只有几个点时, harness差异足以改变排名.

### 16.6. 从相关性走向归因

第一代 Coder 的成品优势与项目级数据、FIM、2T token、过滤、多语言和模型规模同时出现. 成品对比支持整套配方有效. 单项归因必须依赖消融: Figure 3 支持 FIM trade-off, CrossCodeEval 文件级对照支持项目语料, 其余数据过滤与 tokenizer 多数缺少正交对照.

可证伪表述应包含条件. 「依赖排序在 BM25 提供跨文件片段、2048 输入和若干静态语言上改善补全」比「模型理解整个仓库」更准确; 「50% PSM兼顾论文测试中的续写与单行 infill」比「最佳 FIM 比例是50%」更准确; 「位置扩展在16K有训练证据」比「支持64K可靠生成」更准确.

反事实问题帮助控制语气: 随机文件顺序若分数相同, 依赖排序解释失败; 后缀打乱若输出不变, FIM双侧利用解释失败; 新题去污染后优势消失, 数据泛化解释失败; oracle retrieval仍不提升, 检索瓶颈解释失败. 每个强结论都应能指出什么观察会推翻它.

### 16.7. 证据能够支持到哪里

这份报告支持的范围是「多种离线代码任务上的候选生成能力」：短函数、竞赛题、数据科学库、中间补全和带检索的跨文件补全都有对应实验。自动修复任意仓库则还需要问题定位、编译与测试、迭代反馈和沙箱环境，这些环节不在第一代 Coder 的训练闭环里。长度证据落在 16K 训练与评测设置；对更长窗口的外推需要另做损失、检索和代码执行测试。训练语料与过滤器的开放粒度，也决定了外部研究者能把数据归因复算到什么程度。

各类能力要回到各自的监督来源。HumanEval、MBPP 与 DS-1000 主要检查代码预训练、数据覆盖和模型容量形成的生成能力；FIM 直接针对中间补全；仓库排序提高相关文件在语境中共现的机会，编译正确性仍由后续执行验证判定；Instruct 阶段调整交互接口和指令跟随，Base 阶段积累的代码分布知识是它的起点。这样分开之后，每一项成绩都能找到对应的数据、目标与测量口径。

第一代的贡献已经足够具体: 公开多尺寸代码底座, 将项目依赖纳入语料构造, 在大规模从头训练中混合FIM, 用长阶段扩展到16K, 并用函数、库、补全、跨文件与竞赛评测展示边界. 后来的工作可以在这个坐标上增加新数据、架构和执行反馈, 无需替它补上当时不存在的能力.

### 16.8. 面向使用者的模型选择

只做低延迟单行补全时, 6.7B 的离线 FIM 成绩与 33B 接近, 权重、KV cache 和解码延迟更容易控制. 面向复杂算法、长回答或竞赛题, 33B 的容量优势更明显. 需要解释与多轮指令时选 Instruct, 需要原始补全、继续训练或稳定 FIM 协议时优先 Base. v1.5在通用语言和数学上更均衡, 原系列在 FIM和16K项目输入上证据更完整.

选择还要结合上下文管线. 一个可靠检索器加6.7B可能胜过把无关文件塞给33B; oracle上下文下33B仍错, 再增检索没有意义. 量化可以降低显存, 需要重新测代码 pass@1和长上下文, 因为少量 logit扰动可能改变精确语法 token. 推理框架也必须正确加载 RoPE scaling、special token与停止规则.

生产系统应把生成视为候选, 而不是直接提交. 快速路径做解析、格式化和类型检查, 隔离环境运行测试, 高风险改动再人工审查. 这些层会增加延迟, 换来错误可见性. 论文证明模型在多类离线任务上有竞争力, 产品可靠性来自模型与验证链路共同工作.

当业务任务超出论文分布, 最有效的评估是从真实仓库抽取时间外工单, 固定检索、执行环境和成本预算, 同时记录成功率、迭代数、token、运行时间与人工修改量. 这种评测可能得到与HumanEval不同的排序, 但更接近模型实际价值. 第一代报告提供起点, 不替业务场景完成这一步.

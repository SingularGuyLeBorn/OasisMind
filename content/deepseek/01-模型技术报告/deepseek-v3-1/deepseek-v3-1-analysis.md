# DeepSeek-V3.1: 一个检查点如何承载两种推理模式

DeepSeek 于 2025 年 8 月 21 日发布 V3.1. 公开材料是一份七页发布说明, 配套来源包括官方发布页与 Hugging Face 模型卡, 没有单独的 arXiv 技术报告. 因而能够确认的是产品接口, 模板行为, 840B token 的继续训练, CoT 长度变化, Agent 评测和 UE8M0 FP8 Scale; 网络层数, 专家配置, 后训练算法与数据配比没有披露.

V3.1 的主线是把此前分开的 V3 对话模型与 R1 推理模型收进同一个检查点. `deepseek-chat` 和 `deepseek-reasoner` 两个 API 名仍然保留, 但不再对应两份独立权重. 这种合并改变了训练约束和部署边界: 同一套参数既要直接回答, 也要生成较长的推理过程; 同一套 tokenizer 与 chat template 还要稳定表达模式选择, 工具调用和多轮历史.

## 1. 模式切换发生在生成协议

公开材料能确认的是**模式切换协议**,不能确认新增了某种网络结构.

### 1.1. 同一权重如何区分两种行为

发布说明把 V3.1 称为「混合推理架构」, 但没有报告任何新增网络模块. App 和网页端通过「深度思考」按钮切换, API 端则由 `deepseek-chat` 与 `deepseek-reasoner` 分别进入非思考和思考模式. 两个入口都使用 128K 上下文. 从公开接口能够确定的是模式路由, 不能据此推导注意力层或 MoE 层发生了结构变化.

模型卡进一步给出生成前缀: 思考模式以 `<think>` 结束输入前缀, 模型随后生成推理内容; 非思考模式直接给出 `</think>`, 等于在生成开始前关闭推理区段. decoder-only 网络仍执行同一种 next-token prediction, 区别来自特殊 token 所设定的条件. 训练数据必须同时覆盖两种前缀及相应输出形态, 否则模型容易在非思考模式泄漏推理段, 或在思考模式过早闭合标签. 两类样本比例和联合训练日程没有公开.

多轮对话还要处理历史推理内容. 模型卡要求丢弃先前轮次的思考文本, 仅保留闭合标记与可见回答. 这样做控制上下文占用, 也避免模型把旧轮的中间推理当作新问题的事实前提. 代价是服务端必须理解模板协议, 不能把完整原始输出逐字拼回下一轮. V3 的旧模板若直接套用到 V3.1, 模式标记, 工具调用边界与历史裁剪都可能错位.

历史裁剪还改变了可恢复状态. 用户能看到上一轮最终答案, 模型却不再接收产生该答案的完整推理段. 如果后续问题引用中间步骤, 服务端无法从已裁剪上下文中恢复. 这种设计以较低上下文占用换取了推理过程的不持久化, 也要求最终答案保留后续对话真正需要的条件与结论. 发布说明没有给多轮思考一致性的专项评测.

### 1.2. 合并检查点带来的参数竞争

两种模式共享参数, 意味着后训练同时优化不同长度和不同节奏的输出. 非思考样本偏向短回答与快速执行, 思考样本允许在最终答案前展开推理. 如果某一类数据占比过高, 同一输入下的 token 分布会偏向该类行为. 特殊 token 提供了条件信号, 但条件信号只能让模型区分任务, 不能自动消除共享参数的梯度干扰.

V3.1 的价值因此不只是省掉一份部署权重. 同一检查点让系统能够按请求切换延迟和推理深度, 缓存管理, 权重驻留与版本治理也只维护一条线. 相应代价是回归测试必须成对进行: 思考模式的数学和代码能力提高, 不能以非思考模式的输出长度变长为代价; 非思考模式更简洁, 也不能破坏思考模式的搜索空间. 发布说明只给最终评测, 没有双模式互相干扰的消融.

strict Function Calling 与 Anthropic API 格式属于协议层扩展. strict 模式要求函数名和参数满足 schema, 但发布说明没有写服务端采用约束解码还是生成后校验. 两种实现对失败形态不同: 约束解码在生成过程中屏蔽非法 token, 事后校验则可能需要重试. 因而「满足 schema」只能解释接口承诺, 不能反推模型内部使用了哪种解码器.

## 2. 继续训练与推理长度控制

V3.1 Base 是从 V3 检查点**继续训练 840B token**,并非重新预训练一套底座.

### 2.1. 840B token 用在长上下文外扩

V3.1 Base 从 V3 检查点继续训练 840B token, 不是从随机初始化重新预训练. Hugging Face 模型卡把过程分成 32K 与 128K 两段: 32K 阶段约 630B token, 128K 阶段约 209B token, 合计与发布说明的 840B token 相符. V3 原报告使用 YaRN 完成长上下文扩展, 相关机制可参见[长度外推: 从 PI 到 YaRN](../../../llm-guide/2-核心原理与架构/2.1-深度学习基础组件/2.1.4-位置编码/02-RoPE扩展-长上下文,多模态与工程实现/02-RoPE扩展-长上下文,多模态与工程实现.md).

继续训练的目标不是简单宣布 128K 窗口. 模型需要在长序列里学习跨越更远距离的依赖, 并适应长工具轨迹, 仓库上下文和搜索记录. 840B token 约占 V3 预训练 14.8T token 的 5.7%, 规模足以改变底座在长上下文条件下的行为. 公开材料没有给长短样本比例, 数据领域或位置分布, 因而不能把 Agent 提升按比例归因于这一步.

长上下文训练也不等于 128K 中每个位置都具有同等可靠性. 标称窗口说明接口接受的最大长度, 真实能力还取决于训练时的长度分布, 信息位置, 检索干扰和生成长度. 发布说明没有 needle-in-a-haystack, 长文问答或不同位置区间的曲线. 对代码 Agent 而言, 能装入整个仓库只是输入条件; 能否定位相关文件并维持跨文件约束仍由后训练与工具轨迹决定.

从训练计算看, 32K 与 128K 两段承担的作用也不同. 较短阶段可以让模型先适应扩展后的 RoPE 频率与更长序列统计, 较长阶段再把可用窗口推到接口上限. 模型卡给出的 630B 与 209B token 表明训练量并未按上下文长度等比例分配. 由于单个 128K 序列消耗的注意力计算和显存更高, 最后一段用较少 token 仍可能占据较大计算份额. 官方没有给 batch size, 序列打包率与训练步数, 无法从 token 数复原算力投入.

继续训练还要避免短上下文能力退化. 如果训练批次过度偏向长序列, 常见短对话的分布会被稀释; 如果长序列只是把无关短文拼接在一起, 模型又未必学到远距离依赖. V3.1 发布说明只给后训练模型的任务结果, 没有 V3.1 Base 对 V3 Base 的短任务与长任务并列表. 因而 840B token 能确认训练规模和目标窗口, 不能确认每一种上下文长度都获得同等增益.

### 2.2. CoT 压缩减少的是生成成本

V3.1-Think 经过 CoT 压缩训练后, 官方称输出 token 减少 20%–50%, 平均任务表现与 R1-0528 持平. 图中的三项数据给出了具体口径: AIME 2025 从 22,615 token 降到 15,889 token, 准确率由 87.5% 变为 88.4%; GPQA Diamond 从 7,678 降到 4,122 token, 分数由 81.0 变为 80.1; LiveCodeBench 从 19,352 降到 13,977 token, 分数由 73.3 变为 74.8. token 分别减少约 29.7%, 46.3% 和 27.8%.

![V3.1-Think 与 R1-0528 的输出 token 和准确率对比](images/p04-v3-1-deepseek-v3-0324.png)
> 图 1: AIME 2025, GPQA Diamond 与 LiveCodeBench 上的平均输出 token 和任务表现, 出自 V3.1 发布说明第 4 页.

图 1 说明长度下降没有在三项任务上造成一致的分数损失: 一项下降 0.9 分, 两项上升. 它不能说明单个样本的推理过程都更好, 也不能说明所有任务都落在同一压缩比例. 平均 token 数还会受提前答错, 拒答和截断影响. 若模型更早给出错误答案, 长度同样会下降; 因而必须把长度与准确率成对读取.

CoT 压缩改变的是生成阶段的 token 数, 直接影响延迟与输出费用. 公开材料没有说明训练目标. 长度惩罚, 短轨迹蒸馏, 正确样本筛选或强化学习都可能得到相似表象, 但不能据结果替官方指定算法. 非思考模式也宣称相对 V3-0324 在性能相同时明显缩短输出, 却没有给分项数字. 推理训练的通用背景可参见[推理与 Agent 能力](../../../llm-guide/4-后训练/4.8-推理与Agent能力/4.8-推理与Agent能力.md).

### 2.3. 长度收益如何落到服务成本

新版 API 输出价格为每百万 token 12 元. 按图 1 的平均值, 一道 AIME 2025 题的输出费用约从 R1-0528 的 0.27 元降至 V3.1-Think 的 0.19 元, 只计算输出而不含输入. GPQA Diamond 的对应输出费用约从 0.092 元降至 0.049 元. 这是固定单价下由输出长度直接得到的差值, 不包含重试, 并发等待和缓存命中.

价格表同时规定输入缓存命中为每百万 token 0.5 元, 未命中为 4 元, 输出为 12 元, 并取消夜间优惠. 长上下文 Agent 的成本不只由 CoT 决定. 仓库文本和搜索页面进入输入侧, 缓存键是否稳定决定输入成本; 工具调用产生的新观察又会使后续请求变化. 因而 CoT 压缩主要降低输出侧开销, 不能替代上下文裁剪与缓存设计.

一次 Agent 请求若包含 100K 输入 token 和 10K 输出 token, 输入未命中时费用约为 0.4 元, 输出约为 0.12 元; 输入命中时输入费约为 0.05 元. 在这个设置中, 缓存命中带来的差额大于再压缩少量输出 token. 如果每轮工具观察都改变前缀, 可复用缓存的区段会缩短. 系统可以把稳定的仓库上下文和工具定义放在可复用前缀, 把变化的观察追加在后部.

CoT 压缩还会影响并发容量. 输出 token 减少后, 单请求占用解码资源的时间下降, 相同硬件可以服务更多并发请求. 这种收益取决于批处理, KV cache 容量和请求长度分布, 发布说明没有给吞吐或首 token 延迟. 因而图 1 能直接支持 token 和费用比较, 不能直接换算成服务器吞吐倍数.

## 3. Agent 评测呈现了什么能力

### 3.1. 代码任务的增量集中在多步执行

代码 Agent 表中, SWE-bench Verified 为 66.0, V3-0324 与 R1-0528 分别为 45.4 和 44.6; SWE-bench Multilingual 为 54.5, 两个基线分别是 29.3 和 30.5; Terminal-Bench 为 31.3, 基线为 13.3 和 5.7. 在 SWE-bench Verified 的 500 个问题上, 66.0 与 45.4 相差约 103 个成功修复, 量级远高于一般采样波动.

三个评测都要求模型在外部环境中连续行动. SWE-bench 提供真实仓库与 issue, 最终以测试是否通过计分; Terminal-Bench 更强调命令行中的多步操作. R1-0528 在 Terminal-Bench 只有 5.7, 低于 V3-0324 的 13.3, 说明长推理能力不能直接替代工具协议, 环境反馈处理与动作纠错. V3.1 的优势与发布说明所称 Post-Training 优化方向一致.

SWE-bench 的一次成功至少包含四个相互依赖的环节. 模型先从 issue 提取约束, 再在仓库中定位相关文件, 生成补丁后运行测试, 最后根据失败输出继续修改. 任一环节出错都会得到零分. 因而 66.0 不能解释成单纯的代码补全准确率. 它更接近在固定预算内完成整条修复路径的比例, 其中仓库检索, shell 使用和测试反馈与代码生成同样重要.

SWE-bench Multilingual 的 54.5 低于 Verified 的 66.0, 两者题集不同, 不能把 11.5 分差直接当作语言损失. 多语言 issue 会改变需求理解, 但仓库语言, 测试难度和问题分布也会变化. V3.1 相对两个基线在 Multilingual 上增加约 24–25 分, 增量方向与 Verified 一致, 这比两个绝对分数之间的横向差更有解释力.

这组结果仍缺少关键控制变量. 发布说明没有给 Agent 框架, 最大步数, token 预算, 温度, 补丁重试策略和工具错误处理. SWE-bench 的最终分数会随脚手架变化, 因此 66.0 应作为该次官方运行的系统成绩, 不能视为裸模型在所有框架中的固定能力. 表中也没有标明模式; 模型卡对工具调用的说明更接近非思考模式, 但发布页未明确绑定.

### 3.2. 搜索成绩要连同工具协议读取

搜索 Agent 表对比 V3.1 与 R1-0528. BrowseComp 为 30.0 对 8.9, BrowseComp-zh 为 49.2 对 35.7, HLE 为 29.8 对 24.8, xbench-DeepSearch 为 71.2 对 55.0, Seal0 为 42.6 对 29.7. Frames 与 SimpleQA 分别是 83.7 对 82.0, 93.4 对 92.3, 增量较小. 大幅变化主要出现在需要多轮浏览和下一步查询决策的任务.

搜索 Agent 的模型输入会反复加入页面内容, 查询结果和工具状态. 模型需要决定何时改写查询, 哪些来源继续展开, 何时停止并组织答案. 长上下文继续训练为容纳轨迹提供基础, Post-Training 则训练动作选择. 两者都可能影响分数, 但发布说明没有消融, 无法把 BrowseComp 的 21.1 分增量拆到具体训练阶段.

HLE 的协议差异尤其明显. V3.1 搜索 Agent 表给出 29.8, Terminus 表中「reasoning mode w/o tool use」的 V3.1 列只有 15.9. 同一检查点相差 13.9 分, 原因是前者允许工具, 后者禁止工具. 引用 HLE 时若省略工具设置, 会把检索系统的贡献混入模型闭卷推理能力. 搜索供应商, 每题调用次数和页面读取范围同样未披露.

### 3.3. 评测表不能回答训练配方

发布材料把 Agent 提升归为 Post-Training 优化, 但没有说明轨迹来自人工, 模型自生成还是线上反馈; 没有给 SFT, 偏好优化或强化学习的阶段划分; 也没有定义奖励. 评测结果能够证明最终系统在给定协议下更有效, 不能识别是哪一种训练算法带来增量.

Agent 轨迹与普通问答样本的结构不同. 一条轨迹包含用户目标, 模型动作, 工具返回, 新动作和最终答案, 每一步都受环境状态约束. 训练若只保留成功轨迹, 模型会看到正确行动顺序, 却较少学习怎样从错误命令与失败测试中恢复; 若加入失败轨迹, 又需要标明哪一步应被修正. V3.1 在 Terminal-Bench 和 SWE-bench 上的增量说明最终策略更有效, 页面没有披露轨迹是否包含错误恢复.

奖励可能只看最终任务成功, 也可能同时评价工具参数, 步数和输出格式. 最终奖励容易把长轨迹中的信用分配压到一个标量, 过程奖励可以提供更密集信号, 但需要可靠的步骤判定器. 发布说明没有相应细节. 因而 Post-Training 是训练阶段定位, 不是算法名称, 更不能由表格倒推出使用了 GRPO, PPO 或某一种偏好优化方法.

同样的边界适用于 CoT 压缩. AIME, GPQA 与 LiveCodeBench 展示长度和准确率的联合结果, 但没有训练消融. 840B token 的继续训练, 双模式数据与 Agent 轨迹可能共同改变表示和行为. 对版本谱系的可靠说法是 V3.1 同时调整了 Base 继续训练和后训练; 把某个分数单独归给其中一步, 需要官方未提供的对照组.

## 4. 部署格式与版本边界

### 4.1. UE8M0 改变比例因子的表示

V3.1 使用 UE8M0 FP8 Scale 参数精度. V3 的 FP8 训练按块保存比例因子, 使低精度值与原始张量动态范围匹配, 机制背景见[FP8 混合精度训练详解](../../../llm-guide/6-训练与推理优化/6.1-训练基础设施/6.1.2-混合精度训练/02-FP8混合精度训练详解/02-FP8混合精度训练详解.md). UE8M0 用 8 位无符号指数保存 scale, 没有尾数, 可表示的正 scale 是离散的 2 的幂. 相比 FP32 scale, 存储从 4 字节降为 1 字节.

指数格式便于硬件执行乘以 2 的幂, 但 scale 的粒度更粗. 若采用向上取整, 实际 scale 最多可能接近所需 scale 的两倍, 相应地会少利用约一位有效动态范围. 这是格式本身的量化边界, 不等于模型分数必然下降. 最终误差还取决于分块方式, 张量分布和内核实现. 发布说明没有给 block shape, 损失变化或精度消融.

设某一块浮点值的绝对最大值为 $a$, FP8 E4M3 的目标上界为 $m$. 理想比例因子是 $s=a/m$. UE8M0 只能保存 $2^k$ 形式的比例, 若取 $k=\lceil\log_2 s\rceil$, 实际比例 $\hat{s}=2^k$ 满足 $s\leq\hat{s}<2s$. 量化值按 $q=\operatorname{round}(x/\hat{s})$ 得到, 反量化为 $\hat{x}=q\hat{s}$. 当 $\hat{s}$ 接近 $2s$ 时, 相邻可表示值之间的间隔也接近理想情况的两倍. 这就是动态范围利用率下降的来源.

公式只描述单个 block 的刻度选择. 实际权重文件还要规定哪些元素共享一个 scale, scale 与数据块怎样排列, 特殊值如何编码. 分块越细, scale 越贴近局部分布, 元数据和读取开销也越高; 分块越粗, 少量离群值越容易抬高整块 scale. V3.1 页面只给 UE8M0 名称, 没有重新声明分块规格, 部署端应读取随权重发布的配置而不是从格式名猜布局.

部署程序需要正确解释权重文件中的 scale 布局. 旧 V3 内核若假设 FP32 scale, 直接读取 UE8M0 会得到错误反量化结果. 模型卡还要求路由偏置按 FP32 加载, 进一步说明不能只替换权重文件而沿用全部旧配置. 推理框架应以 V3.1 仓库的配置, tokenizer 和模板作为一个版本单元处理.

### 4.2. tokenizer 与 chat template 是行为接口

官方明确提示 V3.1 对 tokenizer 与 chat template 做了较大调整. tokenizer 决定文本到 token ID 的映射, chat template 决定角色标记, 模式 token, 工具调用和历史消息怎样排进序列. 二者任一错配都可能造成可读文本看似正常, 模型接收的控制序列却不符合训练分布.

模式切换依赖 `<think>` 与 `</think>` 的位置, 因而模板不是外围排版. strict Function Calling 也要求工具定义和返回值以约定形式进入上下文. 部署验收至少要分别测试思考与非思考输出, 多轮历史是否移除旧推理段, 工具 schema 是否稳定, 128K 请求是否使用正确位置配置. 发布说明没有承诺兼容 V3 的旧 prompt, 迁移时应按破坏性版本变更处理.

### 4.3. V3.1 在版本谱系中的位置

V3.1 沿用 V3 网络结构的公开基础, 在 Base 上追加 840B token 长上下文训练, 再把思考, 非思考与 Agent 行为收进一个后训练检查点. 后续 V3.1-Terminus 继续修正语言混杂和工具任务表现, 没有宣布新底座; V3.2-Exp 才公开引入新的稀疏注意力方案. 因而比较 V3.2-Exp 时, 需要把 Terminus 的后训练增量与注意力机制增量分开.

V3.1 的公开信息足以支持部署和结果复核, 不足以复现训练. 未披露项包括 840B token 的数据构成, 双模式样本比例, CoT 压缩目标, Agent 轨迹来源, 奖励形式与完整评测协议. 这些缺口限制的是因果解释, 不影响已公开接口和表格数字本身. 对底座结构应回到 V3 技术报告, 对推理强化学习应回到 R1 报告, V3.1 发布说明主要定义二者合并后的产品与工程边界.

从使用侧看, V3.1 最明确的变化是统一权重与协议. 从研究侧看, 最重要的缺口是没有拆分继续训练, 双模式后训练和 Agent 轨迹各自贡献. 两种视角需要分开: 前者可以按公开配置部署并验收, 后者若缺少消融就不能给出训练因果结论.

## 5. 一个模型如何同时承载思考与非思考模式

### 5.1. 模式 token 改变的是条件分布

自回归模型始终在计算

$$
p_\theta(y\mid x,m)=\prod_{t=1}^{T}p_\theta(y_t\mid x,m,y_{<t}),
$$

其中 $x$ 是用户输入,$m$ 是由 chat template 写入上下文的模式条件. 思考模式把生成位置放在 `<think>` 之后,非思考模式则预先写入 `</think>`,让第一个待生成 token 已经位于可见回答区. 网络没有切换成另一套层,也没有为两种模式装载两份专家;同一组参数在不同前缀下形成两个条件分布.

这个机制看起来简单,真正困难的是训练分布必须把控制 token 与行为稳定绑定. 若非思考样本里经常出现很长的解释草稿,模型会学到 `</think>` 之后照样展开;若思考样本大量缺失闭合标记,模型可能一直停留在推理区. 模板只提供一个控制旋钮,控制是否灵敏仍由数据覆盖、损失权重与后训练结果决定.

可以把共享参数上的联合目标写成

$$
L(\theta)=\lambda_{nt}\,\mathbb E_{D_{nt}}[-\log p_\theta(y\mid x,m_{nt})]+\lambda_t\,\mathbb E_{D_t}[-\log p_\theta(y\mid x,m_t)].
$$

$D_{nt}$ 与 $D_t$ 分别是非思考和思考样本,$\lambda$ 决定训练中的相对强度. 两个梯度方向若夹角为负,更新一种模式会损害另一种模式;若主要底层能力共享,联合训练也可能相互促进. 官方没有公布样本比例和梯度处理方法,所以只能确认最终 checkpoint 同时支持两种模式,无法确认冲突是怎样解决的.

### 5.2. 共享权重不等于两种能力完全独立

对于同一问题,思考模式通常生成更长轨迹,因此它对共享参数产生更多 token 级损失项. 若训练简单按 token 求平均,一条两千 token 的推理样本对更新的影响可能大于一条两百 token 的直接回答. 也可以按样本归一化损失,让每条样本权重接近. 两种处理会形成不同的模式平衡,而公开材料没有披露这一细节.

共享也会带来正迁移. 数学概念、代码语义、事实知识和工具 schema 不必分别存两份;思考轨迹学到的中间结构可以改善非思考模式的首轮判断,简洁回答的数据又能约束思考模式少绕路. V3.1 非思考模式相对 V3-0324 在维持表现时缩短输出,思考模式相对 R1-0528 也缩短 CoT,表明两条路径至少在最终结果上没有出现明显的单边崩溃.

一个常见泄漏是非思考模式输出隐藏式的长铺垫,只是没有 `<think>` 标签;另一个泄漏是思考模式很快关闭推理区,行为退化为普通回答. 检查时不能只看标签是否出现,还要比较输出长度、首个答案 token 的位置、困难任务得分与推理区闭合率.

更严格的模式可控性实验可采用同一批提示成对运行. 记两个模式的输出长度为 $T_t,T_{nt}$,任务得分为 $S_t,S_{nt}$. 对简单事实题,希望 $T_{nt}\ll T_t$ 且 $S_{nt}$ 不下降;对高难数学题,思考模式应以额外长度换来更高 $S_t$. 若所有题都只有长度变化而得分不变,控制可能只调节文风;若思考轨迹高度模板化,额外 token 也未必产生有效计算.

### 5.3. 非思考模式仍然可以完成内部计算

`</think>` 约束的是可见生成协议,并不意味着网络在一次前向过程中没有计算. 每层 attention 和 FFN 仍执行相同数量的变换,MoE 路由仍为每个 token 选择专家. 非思考模式省下的主要是额外生成 token 及其解码循环,并没有把模型变成浅层网络.

因此“思考”至少包含两个层面. 一个是 Transformer 对当前上下文进行的隐状态计算;另一个是把中间步骤写成新 token,再让后续 token 读取这些步骤. 后者相当于给模型增加可变长度的外部工作区. 对需要多步搜索的问题,工作区能保存中间量、回溯错误和分解子目标;对简单问题,长工作区可能只增加延迟与跑偏机会.

设每个生成 token 的单步解码成本近似为 $C$,思考轨迹增加 $R$ 个 token,可见答案为 $A$ 个 token,则解码成本近似从 $AC$ 增为 $(R+A)C$. KV cache 让每步不必重算全部历史,但 cache 占用随 $R+A$ 增长. CoT 压缩把 $R$ 缩短 20%—50%,既减少计算时间,也释放并发请求可用的 KV 空间. 它没有减少模型参数,也不会缩短输入预填充.

### 5.4. 为什么压缩 CoT 不能只靠长度惩罚

在奖励中加入长度代价是一条直观路线:

$$
r=r_{task}-\alpha T.
$$

$r_{task}$ 衡量答案是否正确,$T$ 是输出长度. $\alpha$ 太小,模型继续冗长;太大,最容易获得奖励的策略是快速猜答案或提前停止. 数学题中一条必要推导被删除后,训练集上可能暂时保持得分,换到分布外题目就失去稳定性. 所以高质量压缩应删除重复验证、空泛过渡和无效分支,保留决定答案的状态变化.

另一种路线是用较长轨迹产生短轨迹监督. 教师完成探索后把关键步骤压缩成可复核链条;学生学习压缩后的目标. 还可以对多个候选轨迹按正确性与长度筛选,保留 Pareto 边界上的样本. V3.1 官方只说明经过 CoT compression training,没有公布采用长度奖励、蒸馏、筛选还是它们的组合. 从结果倒推具体算法会越过证据边界.

压缩质量应按难度分桶. 对一眼可答的题,长度大幅下降几乎没有风险;对需要十几步推导的题,同样比例可能删掉关键环节. 平均 token 数下降会被大量简单样本主导,最好同时给出长度分位数、正确样本的平均长度、错误样本的平均长度以及超出预算的截断率. 官方图提供三个代表性 benchmark 的均值,足以支持整体效率改善,还不足以描绘完整分布.

### 5.5. 多轮对话中的思考历史为何要裁掉

官方模型卡示例在构造下一轮提示时保留上一轮可见答案,移除上一轮 `<think>...</think>` 内容. 这条规则解决三个问题. 其一,旧推理通常很长,不断回灌会迅速吃完 128K 窗口. 其二,中间轨迹可能含已放弃的假设,下一轮把它当稳定事实会放大错误. 其三,模型训练时若只见过裁剪后的历史,原样回灌会制造分布偏移.

裁剪也有信息损失. 假设上一轮用变量 $z$ 推导结论,可见答案只留下最终数值,下一轮用户追问“刚才第三步为什么成立”,模型无法从上下文恢复被删步骤. 服务端需要在成本、隐私与可追问性之间选择. 一种折中办法是把关键中间假设压缩进可见答案,另一种办法是把完整轨迹作为不可直接拼接的外部记录,仅在明确追问时检索相关片段.

历史处理还必须与 cache 一致. 若客户端显示完整思考但服务端下一轮实际删掉,用户看到的会话和模型接收的会话不同. 调试 Agent 时尤其容易误判:人以为模型记得上一轮计划,实际上它只看见最终摘要. 一个可靠的调用层应记录渲染后的真实 token 序列,而不只是原始 message JSON.

### 5.6. chat template 是模型接口的一部分

V3.1 对 tokenizer 与模板做了较大调整. 这不是排版变化. 特殊 token 的 ID、角色边界、工具调用标记和模式前缀共同定义了模型看到的语法. 即使文本肉眼相同,多一个空格、遗漏结束 token 或换用旧 tokenizer,都可能把序列映射到不同 ID.

模板可视为编译器:输入是 system、user、assistant、tool 等结构化消息,输出是模型消费的 token 串. 编译器与模型版本不匹配时,错误往往不会立刻报异常,而是表现为重复、角色串台、工具参数泄漏或模式失效. 因此部署不能只校验权重哈希,还要锁定 tokenizer 文件、`tokenizer_config.json`、`chat_template.jinja` 与推理框架的 parser 版本.

最小验收集应包含首轮与多轮、两种模式、有工具与无工具、工具成功与工具报错、空 system prompt、含特殊字符的参数、接近上下文上限的输入. 每个样例记录渲染字符串、token ID、模型输出与停止原因. 升级框架后若渲染结果变化,即使 checkpoint 没变也应视为行为版本变化.

### 5.7. 工具调用把自然语言生成变成受约束动作

普通回答允许许多等价表达,函数调用却要求结构严格匹配. 假设工具定义为 $f(a,b)$,模型要同时选对函数名、字段名、字段类型与字段值. 成功概率可粗略分解为

$$
P(\text{success})=P(f)P(k\mid f)P(v\mid f,k)P(\text{exec}\mid f,k,v).
$$

任何一项失败都会使整步无效. strict 模式保证输出满足 schema,主要压低语法与类型错误;它不能保证选择了正确工具,也不能保证参数值符合真实世界约束. 把日期字段填成合法但错误的日期,依然通过 JSON schema.

若服务端采用约束解码,每一步会屏蔽不可能完成合法结构的 token;若采用生成后校验,失败时需要重试或修复. 官方发布页承诺 strict Function Calling 满足 schema,没有披露底层采用哪条路径. 对使用者而言,需要测量首次合法率、语义正确率、重试次数和最终任务成功率,只报告 JSON 可解析率远远不够.

多工具场景还会出现动作选择冲突. 搜索、打开网页、运行代码和提交答案都可能在某一步合法,模型必须根据当前状态决定哪个动作信息价值最高. schema 解决“怎么写动作”,Agent 后训练解决“什么时候做什么动作”. V3.1 在工具任务上的提升更接近后者,但公开结果是整套系统评分,无法把模板、模型策略与外部框架贡献完全拆开.

### 5.8. 模式切换的反例与边界

第一类反例是简单问题被思考模式拖坏. 模型生成长轨迹时可能主动怀疑正确直觉,引入无关分支,最终改成错误答案. 第二类是难题被非思考模式碰巧答对,单次样例看不出额外计算价值. 因此应在足够大的题集上比较条件成功率,不能用几条展示案例证明模式优劣.

第三类反例来自提示注入. 用户文本若包含伪造的 `<think>` 或角色标记,模板与 tokenizer 必须确保它们被当成普通内容或正确转义. 否则用户可能改变控制边界. 模型卡展示的是正常调用协议,没有替所有第三方框架提供安全保证.

第四类边界是可见推理不等于忠实解释. 模型给出的 CoT 可能合理化已经形成的答案,也可能省略真正起作用的隐状态线索. 压缩后的轨迹更短,可读性可能更好,却不自动提高因果忠实度. 对高风险决策,应验证结论与外部证据,不能把一段流畅推理当作审计日志.

第五类边界是统一 checkpoint 不代表统一服务配置. `deepseek-chat` 与 `deepseek-reasoner` 可以指向相同权重,但最大输出长度、temperature、工具开关、超时和系统提示仍可能不同. 观察到 API 行为差异时,不能全部归因于模式 token. 本地复现要把采样与模板参数一起固定.

### 5.9. 怎样验证混合推理的真实收益

一套干净实验需要同一 checkpoint、同一 tokenizer、同一采样预算,只改变 `thinking` 模板开关. 题目按事实问答、短计算、长数学证明、代码修复、工具任务分层. 记录准确率、输出 token、首 token 延迟、总延迟、闭合标签错误和超预算比例. 这样才能看到模式选择与任务难度是否匹配.

还应加入预算对齐比较. 思考模式若允许 32K 输出,非思考模式只有 2K,得分差同时包含模式与预算. 可分别设置相同最大 token、相同墙钟时间和相同费用三种约束. 在相同费用下更高的成功率,比无限预算下的最高分更接近产品价值.

模式可控性可用干预测试衡量. 同一提示分别强制 `<think>`、`</think>` 与随机无关前缀,观察长度和策略是否按预期变化;将模板中的模式 token 放错位置,检查模型是否退化;在多轮中交替模式,检查旧状态是否污染新状态. 这些实验能区分真正的条件控制与仅由默认 system prompt 触发的表面差异.

V3.1 官方结果支持一个有限但扎实的结论:单一公开 checkpoint 可以通过模板提供两种服务形态,思考模式在若干推理任务上以更少 token 接近 R1-0528,非思考模式也保持 V3 系列能力. 关于联合训练的具体损失、轨迹来源与冲突处理,仍应标为未公开.

## 6. 长上下文、Agent 与数值格式如何共同决定最终能力

### 6.1. 840B token 是一次有目标的继续预训练

V3.1-Base 沿用 V3 的 671B 总参数、37B 激活参数框架,模型卡明确写出两阶段长上下文扩展:32K 阶段约 630B token,128K 阶段约 209B token. 两数因取整与官方总称的 840B 略有差异. 这批训练量约为 V3 原始 14.8T token 的 5.7%,不能当成一次从零训练,也绝非只改配置文件里的最大长度.

继续预训练可以看作在原参数 $\theta_0$ 附近寻找适应长序列的新参数:

$$
\theta_1=\arg\min_\theta\;\mathbb E_{x\sim D_{long}}L_{NTP}(x;\theta)+\beta R(\theta,\theta_0).
$$

$R$ 代表保持旧能力的约束,实际训练未必显式写出这一项;混入短文本、降低学习率或限制训练步数都可产生类似效果. 新语料若只含长文档,模型可能改善远距离依赖却损伤短对话分布;若只是把互不相关短文拼接成长序列,token 数够长也学不到有意义的跨段关系.

32K 阶段占大部分 token 有现实理由. 序列长度增长时,同样 token 数对应更少独立样本,attention 与通信开销也上升. 先在 32K 让位置编码和长文统计逐步适应,再用 128K 完成窗口外扩,比直接把所有 batch 拉到上限稳定. 但官方没有公开长度采样分布、packing 规则和跨文档 attention mask,无法进一步复原课程设计.

### 6.2. 128K 上限不等于 128K 有效记忆

上下文窗口首先是一项接口容量:序列化后的 system prompt、历史消息、工具定义、检索文本和待生成空间合计不能超过限制. 有效记忆则要求模型在长距离干扰中找到正确信息并利用它. 两者之间至少隔着检索、绑定、计算和生成四步.

设目标证据位于位置 $i$,问题位于末端位置 $n$. 模型要让若干 attention head 对 $i$ 分配足够权重,把证据写入残差流,与问题实体正确绑定,再在输出时恢复. 上下文中若出现多个近似实体,模型既要找到目标句，也要避免把另一个日期或数字绑定到问题对象. 单针检索成功并不能保证多证据合成、顺序推理与跨文件约束成功.

位置效应也不可忽略. 同一证据放在开头、中间和末尾,准确率可能不同;填充文本从随机词换成主题相近段落,难度也会改变. 一条完整曲线应覆盖不同上下文长度、证据位置、干扰数量和所需证据数. V3.1 官方材料没有给这类曲线,128K 应按支持长度理解,不能改写成“任意位置均无损记忆”.

生成预算还会挤占输入. 如果接口总预算是 128K,预留 16K 输出后,可用输入小于 128K. chat template、工具 schema 和特殊 token 同样占位. 把仓库原文机械塞满窗口,可能导致最早文件被截断或答案没有生成空间. 使用侧要按 tokenizer 的真实计数规划,字符数和 token 数不能直接等同.

### 6.3. YaRN 扩展改变的是 RoPE 的频率使用方式

V3.1 配置公开了 YaRN 相关项:`factor: 40`,`original_max_position_embeddings: 4096`,`beta_fast: 32`,`beta_slow: 1`,以及 `mscale` 参数. RoPE 把每对隐藏维旋转一个与位置相关的角度. 对频率 $\omega_j$,位置 $p$ 的二维旋转可写为

$$
R(p,\omega_j)=
\begin{bmatrix}
\cos(p\omega_j)&-\sin(p\omega_j)\\
\sin(p\omega_j)&\cos(p\omega_j)
\end{bmatrix}.
$$

query 与 key 旋转后,内积依赖相对位移 $p-q$. 直接把位置扩大到训练范围之外,高频维会经历未见过的快速相位变化,低频维又可能分辨率不足. YaRN 对不同频段采用平滑插值与外推策略,避免所有频率统一缩放造成短距离分辨率损失.

配置里的 factor 不能简单解释成有效长度恰好扩大四十倍. 原始位置基准、训练阶段、最大位置配置与推理实现共同决定可用区间. Hugging Face 配置给出 `max_position_embeddings: 163840`,官方服务宣称 128K;部署应遵循模型卡与框架适配,不要只把某个字段相乘得到新上限.

更重要的是位置编码只让网络能够表示远距离关系. 模型还要在长数据上训练,才会学会使用这些频率. V3.1 把两个阶段显著扩充到 630B 和 209B token,正是在补训练分布. 只给 V3 改 RoPE 配置,即使不报 shape 错误,也无法复制 V3.1-Base 的长上下文行为.

### 6.4. 长上下文对 Agent 有帮助,但不能替代状态管理

代码 Agent 的一条轨迹可能包含需求、目录树、几十次文件读取、补丁、测试日志和错误回溯. 128K 容量让更多历史原样留在提示中,降低过早摘要造成的信息丢失. 搜索 Agent 同样可以保留更多候选页面和引用片段. 这是长上下文与 Agent 提升之间合理的联系.

可容量越大,噪声也越多. 旧测试失败、已经废弃的计划、重复网页与相互矛盾的版本都可能留在上下文. attention 每步都能看到它们,不代表会自动选择最新状态. Agent 仍需要显式区分“当前事实”“历史尝试”“待办事项”和“最终证据”,必要时压缩或淘汰旧观察.

一个简单状态模型是把轨迹写成 $(s_t,a_t,o_{t+1})$:模型根据状态 $s_t$ 选择动作 $a_t$,环境返回观察 $o_{t+1}$,再更新状态. 若调用层只把全部文本拼接起来,状态更新由模型隐式完成;若外部维护结构化清单,模型可直接读取当前文件版本、测试结果和未解决约束. V3.1 的模型能力能改善动作选择,却不会消除调用层的状态职责.

反例是一次测试失败后文件已修好,但旧日志仍占大量上下文. 模型可能继续围绕已解决错误搜索. 另一个反例是搜索结果中的旧网页与新官方文档冲突,模型因旧页措辞更完整而选错. 这些失败发生在 128K 容量之内,说明问题是证据治理而非窗口不足.

### 6.5. Agent 成功率是多步概率的乘积

假设任务需要 $K$ 个关键决策,每步在当前状态下做对的概率为 $p_k$,粗略成功率为

$$
P(\text{success})\approx\prod_{k=1}^{K}p_k.
$$

若十步任务每步正确率都是 0.95,整体只有约 0.60. 这解释了为什么单轮代码生成看起来很强,进入真实仓库仍容易失败;也解释了后训练只要把多种常见动作各提高几个百分点,端到端成功率就可能大幅上升.

这个乘积不是严格独立模型. 早期错误会改变后续状态,某些错误可以被测试反馈纠正,不同路径步数也不同. 更贴近实际的评估要统计定位文件、修改正确、测试选择、错误恢复和停止判断等阶段通过率. SWE-bench 最终分只告诉我们全部链条完成多少次,不告诉失败集中在哪一步.

V3.1 在 SWE-bench Verified、Multilingual 和 Terminal-Bench 的提升都指向多步交互改善,但官方说明这些结果使用内部代码 Agent 框架. 框架决定可用工具、提示、最大步数和补丁格式. 模型升级前后若框架相同,纵向比较仍有价值;把 66.0 与另一机构不同 scaffold 的成绩横向排列时,必须核对协议.

### 6.6. 搜索 Agent 的核心是价值信息选择

搜索不是“多调用几次搜索框”. 在预算 $B$ 下,Agent 每一步要选择查询 $q_t$,得到页面集合,再决定打开、追问或停止. 理想策略最大化新观察对答案不确定性的预期降低:

$$
a_t^*=\arg\max_a\frac{\mathbb E[H(Y\mid s_t)-H(Y\mid s_t,o_{t+1})]}{\operatorname{cost}(a)}.
$$

这里 $H$ 表示答案不确定性. 实际模型不会显式精确计算熵,但“换关键词能否带来新证据”“再开一页是否值得”正是搜索策略的核心. 只重复同义查询会消耗步数而不增加信息.

复杂问题还要分解证据. 例如比较两项技术的发布时间、结构与结果,应分别寻找一手发布、论文方法和实验表,再按实体对齐. 模型若过早形成结论,后续搜索容易只寻找支持证据;若永不停止,上下文会被低质量页面淹没. Post-Training 可以用成功轨迹和失败反馈训练查询改写、来源选择与停止策略.

官方模型卡说明搜索评测使用内部框架、商业搜索 API、网页过滤器和 128K 上下文,R1-0528 使用预定义 workflow. 这意味着分数比较混合了模型策略与运行协议,尤其旧基线并非完全相同的自主流程. V3.1 的显著提升是有效系统证据,不能直接当作裸模型搜索能力的纯消融.

### 6.7. 引用正确与答案正确是两条指标

搜索 Agent 可能给出正确答案却引用错误页面,也可能引用可靠页面但在归纳时读错. 因而至少需要三个层次:结论正确性、引文是否蕴含对应陈述、来源本身是否权威. 把链接数量当作质量会鼓励模型堆页面,不解决证据对应关系.

对每条原子陈述 $c_i$ 和引文片段 $e_j$,可构造支持矩阵 $M_{ij}\in\{0,1\}$. 覆盖率衡量多少陈述至少有一个支持片段,精确率衡量引用是否真的支持附近陈述. 来源质量还要单独建模:参数声明、实验结果与个人经验拥有不同的证据强度,不能仅按文本相关度排序.

V3.1 的 BrowseComp、HLE 等结果反映回答成功率,公开发布页没有逐项给出引用质量统计. 因而可以说它在官方搜索系统中更会完成任务,不能据此宣称每个答案都拥有可审计引用. 用户若把模型用于研究资料整理,仍需让系统保留页面片段、访问时间和陈述映射.

### 6.8. 工具错误恢复比一次调用成功更接近真实 Agent

现实工具会超时、返回空结果、权限不足或输出格式变化. 一条鲁棒轨迹应识别错误类型,决定重试、改参数、换工具还是请求用户. 若训练只包含顺利执行的成功轨迹,模型可能在看到异常后重复同一动作,形成循环.

可以把恢复策略写成条件概率 $p(a_{t+1}\mid e_t,s_t)$,其中 $e_t$ 是错误观察. 对“文件不存在”,合理动作可能是列目录;对“测试断言失败”,合理动作是读失败上下文;对“网络限流”,合理动作是退避或换已缓存来源. 把所有失败都处理成再次调用,会浪费预算并放大外部副作用.

Terminal-Bench 对命令行交互有较强要求,V3.1 从旧模型基线显著上涨,与错误处理和持续执行能力改善相容. 但总分没有拆出恢复率. 更细的测试可主动注入一次性超时、权限拒绝、损坏 JSON 与过长输出,观察模型能否保持目标、避免危险命令并选择替代路径.

停止同样是一种动作. 测试已经通过后继续修改可能引入回归;搜索已有充分一手证据后继续浏览可能带来冲突噪声. 好的 Agent 不只会做更多步骤,还会在证据满足验收条件时结束. CoT 变短与 Agent 增强同时出现,一种合理但未经证实的解释是训练同时改善了停止判断;官方没有给对应消融.

### 6.9. MoE 的 37B 激活参数怎样理解

V3.1 配置延续 V3 的 MoE 主体:总参数约 671B,每个 token 激活约 37B. 61 层中前 3 层使用 dense FFN,其余 MoE 层拥有 256 个 routed expert 和 1 个 shared expert,每个 token 选择 8 个 routed expert. 总参数决定权重存储规模,激活参数更接近单 token 前向实际使用的计算量.

对第 $l$ 层输入 $h$,路由器产生专家分数 $g_i(h)$,选出集合 $S(h)$,MoE 输出可写成

$$
y=E_{shared}(h)+\sum_{i\in S(h)}\alpha_i(h)E_i(h),\qquad |S(h)|=8.
$$

不同 token 可以选择不同专家,因此总容量很大,单 token 不必跑遍全部参数. 代价是专家权重分散在设备上,路由后需要 all-to-all 通信. 长上下文增加 token 数,会同时放大专家通信和负载均衡压力.

混合思考模式并不意味着思考与非思考各有固定专家. 模式 token 会改变隐藏状态,进而可能改变后续路由分布,但官方没有公布按模式统计的专家选择. 若某些专家更常服务数学推理,那是训练后涌现的条件路由;不能从 256 个专家的配置直接指定其功能.

路由负载还影响吞吐. 若大量 token 集中到少数专家,这些设备形成瓶颈,其余专家空闲. 配置里的 group 与 top-k 约束服务于路由效率,V3 原报告还介绍了无辅助损失的负载均衡思路. V3.1 没有发布新结构报告,应把这些结构归于 V3 底座,不要写成 V3.1 新发明.

### 6.10. MLA 让长上下文可部署,但窗口仍然昂贵

Multi-head Latent Attention 将 key/value 压到较低维潜表示,减少 KV cache. 公开配置给出 `kv_lora_rank: 512`,128 个 attention head,每头 value 维 128. 若普通 MHA 为每个 token 保存所有 head 的 K/V,元素量近似 $2nhd_h$;MLA 保存低秩潜向量及少量位置相关部分,cache 显著缩小.

以符号表示,输入 $h_t$ 先映射为潜向量

$$
c_t^{KV}=W^{DKV}h_t,
$$

各 head 的 key/value 再由 $c_t^{KV}$ 上投影得到. 推理时缓存 $c_t^{KV}$,不必缓存每个 head 的完整向量. RoPE 相关 key 仍需单独处理,因为旋转位置成分不能简单吸收到同一固定投影中. V3 配置把 `qk_nope_head_dim` 与 `qk_rope_head_dim` 分开,对应这两部分.

MLA 缩小 cache 常数,没有消除长度依赖. batch 中每个序列从 32K 增到 128K,cache 仍近似扩大四倍;预填充 attention 也要处理更多 token. 因而 128K 服务需要连续批处理、并行和缓存淘汰策略. 模型支持长窗口与低成本随意使用长窗口是两回事.

CoT 压缩与 MLA 在这里形成互补. MLA 降低每个历史 token 的 cache 成本,CoT 压缩减少历史 token 数. 前者来自 V3 架构,后者是 V3.1 后训练行为. 把二者混成一个“V3.1 新长上下文技术”会丢失版本边界.

### 6.11. UE8M0 描述 scale,不是把权重本体变成指数

权重量化通常把一个 block 的浮点值 $x$ 写成低精度数 $q$ 与比例 $s$ 的乘积:

$$
x\approx s q.
$$

V3.1 权重主体使用 FP8 E4M3,UE8M0 用来保存 scale. UE8M0 有 8 位无符号指数、没有尾数,可表示离散的二次幂比例. 官方配置还给出权重 block size $128\times128$ 与动态 activation scheme. 因而准确说法是“FP8 block 量化采用 UE8M0 scale 格式”,并非所有参数都只有一个指数.

对 block 最大绝对值 $a$ 和 FP8 最大可表示值 $m$,理想 scale 为 $s=a/m$. 若向上量化到二次幂 $\hat s=2^{\lceil\log_2s\rceil}$,则 $s\le\hat s<2s$. 这样能降低溢出风险,代价是量化步长最多接近理想值两倍. 小值的相对误差会变大,但乘二次幂在硬件上更容易处理,scale 元数据也从 FP32 的四字节降为一字节.

block 大小体现另一组取舍. block 越小,scale 越贴合局部分布,离群值只影响少量元素;scale 数量和读取开销也越大. $128\times128$ 是公开配置中的具体选择. 推理框架若误用 tensor-wise scale 或把 UE8M0 当普通整数比例,会造成格式不兼容，反量化结果会系统性错误.

### 6.12. 激活动态量化为何比静态 scale 更难

权重在部署前固定,可以离线扫描每个 block 决定 scale. activation 随输入、层和 token 改变,动态量化需要在运行时统计范围. 若一个 block 出现离群值,scale 被抬高,大部分普通值使用的有效刻度减少;若 scale 太小,离群值发生饱和.

设量化区间为 $[-m,m]$,重构误差近似由舍入与截断组成:

$$
\mathbb E[(x-\hat x)^2]=E_{round}+E_{clip}.
$$

增大 scale 会降低截断但增大舍入间隔,减小 scale 则相反. 动态策略按当前 block 调整,能跟随分布变化,也引入范围计算和 scale 传递开销. UE8M0 把 scale 限制在二次幂,进一步约束最优点.

思考与非思考模式可能产生不同的 activation 分布,长上下文的位置和工具 JSON 也可能改变离群模式. 官方称权重与激活训练时使用 UE8M0 FP8 scale 以兼容 microscaling 格式,这比训练后直接量化更有利于模型适应误差. 但公开材料没有给 BF16、FP32 scale 与 UE8M0 scale 的逐项精度消融,不能宣称格式变化完全无损.

### 6.13. MTP、推测解码与 CoT 压缩处在不同层次

V3 架构含一个 Multi-Token Prediction 层,训练时预测未来多个位置可改善表示,推理时也可能用作 speculative decoding 的草稿. V3.1 配置仍有 `num_nextn_predict_layers: 1`. MTP 的目标是减少生成相同 token 序列所需的串行主模型步骤;CoT 压缩则减少序列本身的 token 数.

假设原轨迹长度 $T$,MTP 平均每次主模型验证接受 $a$ 个 token,理想主循环约为 $T/a$ 次. CoT 把长度压到 $\rho T$,两者结合约为 $\rho T/a$. 实际加速还受草稿计算、拒绝率、batch 调度和内存带宽影响. 轨迹越不可预测,MTP 接受长度可能越短;公式化、重复性的输出通常更容易接受.

官方 V3.1 发布图报告的是输出 token 下降,没有报告 MTP 开启状态或墙钟延迟细节. “更短时间”同时可能受 token 减少与服务实现影响. 因而能够直接核实的是长度效率,部署速度要在固定硬件和解码配置下测量.

### 6.14. Benchmark 数字要还原成实验协议

AIME、GPQA 与 LiveCodeBench 的分数受采样次数、temperature、最大 token、答案提取与题目版本影响. pass@1 也不总等于一次贪心生成:有的报告会多次采样后求平均单次正确率. 比较 V3.1 与 R1-0528 时,官方同表结果最有价值,因为它们更可能共享协议;与外部榜单比较前要逐项核对.

Agent benchmark 的协议敏感性更强. SWE-bench 是否给 repository map、是否允许联网、最大回合、测试命令、补丁重试都会改变结果. Terminal-Bench 的容器资源和超时同样重要. 搜索 benchmark 还依赖搜索 API 的索引时间,同一问题在不同日期可能返回不同页面.

可以把观测分数写成

$$
S=F(M,H,T,B,D),
$$

其中 $M$ 是模型,$H$ 是 harness,$T$ 是工具,$B$ 是预算,$D$ 是题集版本. 发布表只改变模型并尽量固定其他变量时,能说明版本升级;跨机构比较若五项同时变化,排名不能简单归因于 $M$.

统计波动也要计算. SWE-bench Verified 有 500 题,66% 约为 330 题成功. 在独立伯努利近似下,标准误约为 $\sqrt{0.66\times0.34/500}\approx2.1$ 个百分点. 这只是粗估,实际任务难度不独立,Agent 运行还有随机性. 二十个百分点提升远大于粗略波动,一两个点差异则需要多次运行或置信区间.

### 6.15. V3.1 与 V3、R1 的继承关系

V3 提供底座结构:MLA、DeepSeekMoE、无辅助损失负载均衡、MTP 与 FP8 训练等. R1 展示在 V3-Base 路线上强化推理行为的后训练. V3.1-Base 从 V3 checkpoint 继续做长上下文训练,V3.1 后训练模型再把思考、非思考和 Agent 能力放进一个 checkpoint. 这条谱系决定每项贡献应归到哪里.

若介绍 V3.1 时重新把 MLA 和 MoE 当成新架构,会夸大这一版本的结构变化;若只说它是 V3 与 R1 合并,又会忽略 840B token 长上下文继续训练、CoT 压缩、工具后训练、模板与数值格式调整. 更准确的定位是一次底座延伸、行为统一和部署接口共同升级.

后续 Terminus 修复中英混杂、异常字符并继续增强 Agent,说明 V3.1 首版的主要短板有相当一部分位于后训练与输出稳定性,并非底座结构失效. 再往后的稀疏注意力版本才引入更明显的 attention 机制改变. 比较版本时应沿“底座参数是否变、训练数据是否变、后训练是否变、协议是否变”四条轴展开.

### 6.16. 一个统一模型怎样做任务级计算分配

混合推理把选择权交给用户或上层路由器. 最简单策略是固定规则:聊天用非思考,数学与代码用思考. 更好的策略根据问题难度、剩余预算与风险决定模式. 设两种模式的预期正确率为 $P_t(x),P_{nt}(x)$,成本为 $C_t,C_{nt}$,可以选择

$$
m^*(x)=\arg\max_m\left[P_m(x)-\lambda C_m(x)\right].
$$

难点是调用前不知道真实正确率. 路由器可以用问题类型、长度、自评不确定性或小模型预测难度. 若路由误判,简单问题浪费长 CoT,困难问题又被过早送入非思考模式. 统一 checkpoint 降低了切换权重的成本,没有自动解决路由决策.

还可以逐级升级. 先用非思考模式生成;若答案置信不足、验证器失败或工具返回矛盾,再切到思考模式重试. 这种策略把昂贵计算集中到失败样本. 但第二次请求若看见第一次错误答案,可能被锚定;更稳妥的做法是让思考模式独立求解,再由验证器比较.

在 Agent 中,模式甚至可以按步骤切换. 读取目录、格式化 JSON 等确定动作无需长推理;设计修复方案、解释测试失败时开启思考. V3.1 的模板接口为这种控制提供可能,官方 benchmark 是否使用动态切换没有披露. 因此它是基于公开能力的系统设计推论,不是发布页已经验证的功能.

### 6.17. 失败样例能揭示双模式训练的真实张力

第一组失败是格式与推理冲突. 思考模式在函数调用前输出解释文字,破坏要求单一 JSON 的接口;非思考模式格式正确,却因没有展开约束而选错参数. 这要求训练把“内部规划”“结构化动作”和“可见回答”边界分清,strict schema 只能修复其中的格式部分.

第二组失败是语言混杂. 长推理中引用英文术语,模型可能逐渐切换语言,最终答案没有回到用户语言. Terminus 明确针对中英混杂和异常字符改进,说明首版确实存在用户可感知问题. 这类缺陷与基础知识无关,更接近长生成分布和模板稳定性.

第三组失败是过度压缩. 模型在数学题中跳过关键条件,答案碰巧正确;换一个边界值就失败. 只按最终正确率训练可能保留这种脆弱轨迹. 使用反事实题、步骤验证器和变量扰动能检查推理是否抓住必要关系.

第四组失败是工具回声. 页面里含有伪造系统指令,搜索 Agent 把它当成下一步动作;或终端输出一段看似命令的文本,模型直接执行. 长上下文扩大了可读证据,也扩大了不可信内容进入模型的范围. 工具输出必须标明来源和权限,模型能力无法替代执行沙箱.

第五组失败是上下文饱和. 轨迹接近 128K 时,新工具观察被截断,或者最早的用户约束消失. 模型可能仍流畅行动,却已经忘记验收条件. 外部状态管理应把核心目标放在稳定前缀或周期性结构化摘要中,同时验证裁剪没有改变含义.

### 6.18. 可复现验证应拆成五张表

第一张表测模式控制. 同题双模式运行,报告长度、准确率、标签合法率、首 token 与总延迟,并按难度分桶. 第二张表测长上下文,交叉改变长度、证据位置、干扰数量和证据条数. 第三张表测工具动作,拆出函数选择、参数语义、schema 合法、错误恢复和任务成功.

第四张表测数值与部署. 在支持 UE8M0 的实现和可信高精度参考上比较困惑度、下游分数、吞吐、显存与不同输入长度;框架不支持时不要悄悄把 scale 转换后仍声称复现原格式. 第五张表测 Agent,固定 harness、工具、步数和 token 预算,再与 V3-0324、R1-0528 做成对运行.

每项实验都应保存模板渲染结果、模型配置哈希、框架版本、随机种子与失败轨迹. 对开源权重而言,“能启动”只是最初一步;协议是否正确往往比某个 kernel 快多少更早决定结果. 特别是 V3.1 模板与 V3 差异明显,沿用旧 prompt 得到的退化不应算作模型能力.

数据报告也要保留失败分布. 若平均分提高却超长输出、语言混杂或工具循环集中在少数类别,上线风险仍然存在. 把错误按任务、长度、模式和工具分桶,才能看见统一 checkpoint 的哪部分仍在互相干扰.

### 6.19. 官方材料能够确认到哪一层

[DeepSeek-V3.1 官方发布页](https://api-docs.deepseek.com/zh-cn/news/news250821/)直接确认发布日期、混合推理、CoT 输出缩短 20%—50%、Agent 评测、840B token 扩展、UE8M0、tokenizer 与模板变化. [官方 Hugging Face 模型卡](https://huggingface.co/deepseek-ai/DeepSeek-V3.1)进一步给出 671B/37B、32K 与 128K 两阶段 token 数、模式模板示例、评测协议注释和使用方式.

[官方配置文件](https://huggingface.co/deepseek-ai/DeepSeek-V3.1/blob/main/config.json)能确认 61 层、隐藏维 7168、256 个 routed expert、每 token 选 8 个、MLA 维度、YaRN 配置、FP8 block size 与 scale 格式. 这些字段证明最终 checkpoint 的结构与序列化规范,不包含训练数据配方和后训练目标.

公开证据没有覆盖双模式样本比例、CoT 压缩算法、Agent 轨迹来源、奖励函数、完整超参数以及各改动的消融. 本章关于梯度冲突、信息价值、恢复策略和动态路由的公式用于解释可检验关系,不冒充官方实现. 阅读这类发布型模型时,把“文件中能核对的事实”“结果支持的判断”“等待实验的机制假设”分层,比替缺失报告补一套故事更重要.

### 6.20. V3.1 真正推进的是能力组织方式

V3.1 没有用一篇新架构论文宣布另一个 Transformer 变体. 它做的事情更接近重新组织已有能力:长上下文底座承载更长轨迹,一个 checkpoint 接受两种生成协议,CoT 压缩控制推理成本,Agent 后训练改善工具行动,新的模板与数值格式把能力交付给服务端和开源部署.

这种组织方式的价值在于减少产品线割裂. 用户无需在通用聊天模型和推理模型之间迁移上下文,服务端也不必为每次模式切换换一套 671B 权重. 同时,统一带来的参数竞争、模板耦合和评测混杂更难分析. 一张总榜不能告诉我们哪部分来自 840B token,哪部分来自 Agent 轨迹,哪部分来自脚手架.

所以理解 V3.1 的抓手有三个. 第一,模式切换是条件生成协议,不是两张网络在运行时拼接. 第二,128K 来自位置扩展与大量继续训练共同作用,不能由配置字段单独产生. 第三,Agent 分数属于模型、模板、工具与 harness 组成的系统,纵向提升可信,训练因果仍需消融.

沿着这三个抓手再看公开数字,它们就有了准确位置:840B 描述继续训练规模,20%—50% 描述若干任务的输出压缩,66.0 等分数描述官方 Agent 系统的端到端成功,UE8M0 描述 scale 存储格式. 每个数字都重要,也都有明确边界. 这正是 V3.1 最值得学习的地方:模型版本的进步不只发生在网络层里,还发生在数据、行为协议、计算预算与部署格式怎样被组合起来.

### 6.21. 长上下文训练中的 packing 会改变样本语义

训练长序列时,直接寻找恰好 128K token 的完整文档并不容易. 常见做法是把多个样本拼入一个训练序列. 如果不同文档之间允许互相 attention,模型可能学到不存在的跨文档联系;如果用 block-diagonal mask 隔离,单次计算虽长,每个样本仍只看到自身范围,对真正远距离依赖的训练有限.

设一个 packed sequence 含文档 $d_1,\ldots,d_k$,边界为 $b_i$. 完全 causal mask 允许 $d_j$ 读取所有此前文档;隔离 mask 只允许同一文档内部读取. 前者利用率高,但要插入清楚的文档结束标记,并确保损失不会鼓励模型续写上一份无关资料. 后者语义干净,但长文能力取决于单份文档长度,不能用总 packing 长度冒充.

Agent 轨迹又是特殊长文. 多轮动作之间本来就有依赖,不能按普通文档边界切断. 工具输出可能极长,其中只有少数行影响下一步. 若训练数据保留全部日志,模型会学会在噪声中检索;若人工裁掉大部分日志,实际部署遇到原始输出时会分布偏移. 官方只说收集了额外长文档并扩展训练阶段,没有披露 packing 类型和 Agent 数据是否进入 Base 训练.

验证 packing 影响可以使用跨文档污染测试. 在目标文档前放一份含错误答案的相似文档,观察模型是否混淆;再加入明确边界标记和完全隔离版本. 若错误随前置文档变化,边界学习不足. 对 128K 模型而言,会拒绝无关历史与会找出相关历史同样重要.

### 6.22. 短任务能力为何可能在长上下文扩展中退化

位置分布变化会影响短序列. 原模型大量 token 出现在较小位置,继续训练若把 token 广泛铺到 32K 和 128K,每个位置区间获得的更新比例改变. 长文语料的文风、领域和重复模式也可能与原预训练不同. 即使训练损失下降,短问答与简短代码补全仍可能发生轻微遗忘.

可把旧分布风险记为 $R_{old}(\theta)$,长文风险记为 $R_{long}(\theta)$. 继续训练实际在优化

$$
R(\theta)=(1-\gamma)R_{old}(\theta)+\gamma R_{long}(\theta).
$$

$\gamma$ 越大,长文适应越快,偏离旧模型也可能越多. 混入旧数据、较小学习率和分阶段长度课程都在调节这项取舍. V3.1 后训练成绩说明最终产品维持了较强短任务能力,却没有提供 V3.1-Base 对 V3-Base 的全面并列表,因此不能量化继续训练本身是否先造成退化、再由后训练恢复.

一个反例是 128K needle 测试全对,8K 内代码补全却变差. 如果发布只展示最长窗口,这种回退会被遮住. 完整测试应在 4K、8K、32K、64K、128K 各跑短依赖与长依赖任务,看曲线是否单调,也看短输入是否因位置改造受到影响.

### 6.23. 上下文缓存命中与模式模板存在耦合

前缀缓存要求请求开头的 token ID 完全一致. system prompt、工具定义和仓库摘要若稳定,多轮 Agent 可以复用它们的 KV cache. `thinking=True` 与 `thinking=False` 在 assistant generation prefix 处才出现差别,此前公共前缀仍有机会命中;若调用层为两种模式使用不同 system prompt,公共区就会缩短.

缓存收益可粗略写成

$$
C_{prefill}=C(P)+C(U),\qquad C_{hit}\approx C(U),
$$

$P$ 是可复用前缀,$U$ 是新追加部分. 长仓库上下文中 $P$ 很大,命中能显著降低预填充计算. 可一旦在前缀中加入当前时间、随机请求 ID 或顺序不稳定的 JSON schema,token 序列变化,缓存随之失效.

思考历史裁剪也会改变前缀. 若每轮把旧 CoT 删除,新请求不是上一轮 token 串的简单追加,服务端可能无法直接沿用完整 cache. 一种方案从最早稳定前缀重新命中,另一种方案在生成时就将可持久历史与临时 CoT 分开管理. 模型卡规定语义上的模板,没有规定服务端缓存实现.

所以 CoT 压缩、历史裁剪和前缀缓存要合起来评估. 输出少并不必然使下一轮更便宜;若裁剪导致大段 cache 重算,部分收益会被抵消. 端到端测试需记录 prefill token、cache hit token 与 decode token,只看账单中的总 token 很难定位优化空间.

### 6.24. Agent 后训练要处理信用分配

一条代码轨迹最终测试通过,不代表每个中间动作都好. 模型可能先读了十个无关文件,执行两次危险命令,又靠最后一次修改碰巧成功. 若所有动作共享同一终局奖励,低效行为也会获得正反馈. 反过来,一次正确定位可能因后续工具故障导致整条轨迹零奖励.

令轨迹为 $\tau=(s_0,a_0,\ldots,s_T)$,终局奖励为 $R(\tau)$. 策略梯度会把回报分配给沿途动作:

$$
\nabla J=\mathbb E_\tau\left[\sum_t A_t\nabla\log\pi_\theta(a_t\mid s_t)\right].
$$

优势 $A_t$ 若只有终局信号估计,方差很高. 步骤验证器、测试增量、工具错误类型和成本惩罚都可提供更密集反馈. 例如修改后新增通过十个测试,比“命令成功执行”更接近任务进展.

但过程奖励也会被投机. 奖励少调用工具,模型可能跳过必要验证;奖励测试通过数量,模型可能删除失败测试;奖励补丁小,模型可能留下根因. 安全的训练环境必须限制副作用并让最终验收独立于模型可修改区域. V3.1 发布页没有公开奖励设计,只把能力提升归于 Post-Training,不能从分数猜测用了哪套 RL 算法.

### 6.25. 搜索评测中的时间泄漏与索引变化

搜索 benchmark 与静态数学题不同. 网页会更新、下线或被搜索引擎重新排序. 若问题答案在评测发布后出现在大量解析文章中,Agent 只需检索题目原句就能找到答案,测到的是泄漏后的导航能力. 商业搜索 API 还可能因地区、时间和个性化返回不同结果.

可靠协议应记录运行日期、搜索提供方、查询结果快照与页面正文快照. 对每题检查答案是否在网页中直接出现,区分检索到答案与综合多个证据. 若旧模型与新模型运行日期不同,网页环境变化可能混入版本差异. 官方模型卡说明了内部搜索框架的关键组成,却没有发布完整快照,外部无法逐题复现.

这不让官方结果失去意义. 同一时期、同一内部系统下的大幅提升仍说明新版本更适合该工作流. 它限制的是跨时间和跨框架的精确比较. 引用分数时应连同“商业搜索 API、网页过滤、128K 上下文”等协议一起写,不把数字简化成纯闭卷知识能力.

### 6.26. FP8 兼容性应以逐层误差检查

模型成功加载并能输出文本,不代表数值路径正确. scale 广播维度错位、block 排列转置或某些层回退到错误 dtype,都可能让模型保持语法流畅却悄悄损失精度. 大模型的冗余会掩盖小误差,直到数学、长上下文或罕见 token 上集中爆发.

部署验证可选一组固定输入,在可信实现中保存若干层的 hidden-state checksum 或统计量,再与新框架比较. 对第 $l$ 层计算相对误差

$$
e_l=\frac{\lVert h_l^{ref}-h_l^{test}\rVert_2}{\lVert h_l^{ref}\rVert_2}.
$$

若误差从某一层突然跃升,可定位到该层 GEMM、路由或 scale 处理. 只比较最终 argmax 会漏掉逐层累积偏差,因为早期小误差未必立刻改变 token.

MoE 还要核对路由一致性. 很小的 logit 误差可能让排名接近的第八、第九专家互换,后续隐藏状态产生离散变化. 因此可同时记录 top-k expert ID、一致率和输出误差. UE8M0 是为了 microscaling 兼容而引入的明确格式变化,第三方框架需要专门适配,不能把 V3 的 FP8 loader 原样沿用.

### 6.27. 长推理压缩的质量可由必要步骤检验

只比较答案与 token 数,无法判断短轨迹是否保留了解题结构. 可以为可验证任务定义必要状态集合 $Z=\{z_1,\ldots,z_r\}$:几何题中的关键辅助关系、代码修复中的根因与测试约束、搜索任务中的证据来源. 压缩轨迹不必逐字包含所有冗长探索,但应让这些状态可恢复.

一种检查方式是让独立验证器只看压缩轨迹,回答每个必要状态是否成立以及依据在哪里. 另一种方式删除某一步,观察最终答案概率是否显著变化. 若删掉所谓关键步骤毫无影响,它可能只是解释性装饰;若轨迹省略了验证器必须重新推导的关系,压缩可能过度.

还可做反事实替换. 把中间数值改错,看后续推导是否跟着变化;若最终答案保持原值,文本链条可能没有被模型真正使用. 这类忠实度实验比“看起来更简洁”严格得多. V3.1 的公开图证明平均长度下降且 benchmark 大致持平,没有声称压缩 CoT 已通过上述忠实度检验.

### 6.28. 从 V3.1 得到的研究问题

第一个问题是条件计算能否从二值模式扩展成连续预算. 当前模板在思考与非思考之间切换,未来可让模型接收目标 token 预算或延迟,自动选择轨迹长度. 训练需要覆盖多档预算,并避免模型用冗余文字耗尽额度. 评价也应画出准确率—token 曲线,不再只比两个端点.

第二个问题是模式路由能否进入模型内部. 外部路由器先判断难度,一旦选错只能重试;内部模型可以在生成几步后判断是否需要继续探索. 例如设置可学习停止门 $g_t$,当预计继续思考的收益低于成本时关闭推理区. 门的监督来自答案改进与额外 token 代价,容易出现过早停止,需要可靠验证信号.

第三个问题是 Agent 轨迹能否压缩成结构化状态,而不只是删除旧文本. 如果把目标、已确认事实、文件改动、失败尝试和待办分别存储,模型能在更少 token 下保持长期一致性. 这与 V3.1 的 CoT 压缩方向相通,对象从单次推理扩展到多轮行动历史.

第四个问题是统一模型怎样避免能力互扰. 可以测量两种模式、不同工具任务与普通对话的梯度相似度,再决定数据采样或参数隔离. MoE 路由提供潜在的稀疏分工,但是否真的形成模式专门化需要路由统计和干预实验. 在没有这些证据前,不应把专家数量当作已经解决冲突的答案.

第五个问题是开放模型怎样开放到可研究. V3.1 发布权重、Base、配置与模板,已经允许研究者检查结构和运行行为;训练数据、后训练算法和消融缺失,又限制了因果复现. 后续若能公开小规模可复现实验、模式配比与轨迹构造原则,混合推理就会从一个好用接口变成更可积累的方法体系.

### 6.29. 任务成功之外还要计算副作用

Agent benchmark 常用最终测试是否通过作为二值奖励,实际使用还关心改动范围、资源消耗和不可逆动作. 一个修复通过测试,却顺手删除用户文件或改动无关配置,不能算可靠成功. 搜索 Agent 得到正确答案,却把私有内容发送给外部查询接口,同样越过了任务边界.

可以把效用写成

$$
U=R_{task}-\lambda_1 C_{token}-\lambda_2 C_{tool}-\lambda_3 R_{side}.
$$

$R_{side}$ 是副作用风险,不能简单靠平均 token 成本替代. 对只读工具,风险较低;对写文件、发消息、执行交易等动作,需要权限检查和确认点. 模型更擅长工具调用后,安全边界反而更重要,因为错误动作也会执行得更顺畅.

评测可加入诱导性指令:issue 要求顺便改无关文件,网页要求泄露 system prompt,测试脚本建议执行高权限命令. 合格 Agent 应坚持用户目标与工具权限,只做必要动作. V3.1 的官方表主要衡量任务完成,没有覆盖所有副作用类别,不能据高分推出任意工具环境中的安全性.

### 6.30. 语言一致性问题为什么会在长轨迹中放大

每一步生成都会把自己的输出追加到上下文. 某处偶然切换成英文后,后续 token 条件分布看到的英文比例上升,更容易继续英文;异常字符若被解码进历史,也可能诱发重复. 长 CoT 比短回答经历更多自反馈步骤,小偏差因此更容易积累.

可把语言状态简化为马尔可夫过程. 设中文状态转到英文的概率为 $p$,英文状态回到中文的概率为 $q$. 即使单步 $p$ 很小,轨迹足够长时至少一次切换的概率 $1-(1-p)^T$ 仍会上升. system prompt 的语言要求、同语种训练样本和结束后的答案重置都能提高回归稳定性.

Terminus 后续明确减少中英混杂与随机字符,给首版 V3.1 的真实边界提供了官方旁证. 这不意味着 V3.1 的知识能力错误,而是生成协议在长输出下仍有稳定性问题. 测试应按输出长度绘制混语率,区分术语的合理英文保留与整段无意切换.

### 6.31. 从总参数到实际部署规模

671B 参数即使按每参数 1 字节存 FP8,纯权重也约 671GB,还未计 scale、embedding 特殊处理、运行缓冲与通信空间. 单机多卡部署必须做 tensor parallel 或 expert parallel. MoE 每 token 只激活 37B 能降低计算,但所有专家权重仍要驻留或通过更复杂的分层加载管理.

若用八张 80GB GPU,理论总显存 640GB,连裸 FP8 权重都难以完整容纳;实际部署往往需要更大显存卡、更多设备或主存卸载. 卸载会引入 PCIe 或网络传输,吞吐明显受限. 因而“激活 37B”不能理解成用部署普通 37B dense 模型的显存就能运行.

Expert parallel 把不同专家放在不同设备,token 经路由后跨设备交换. batch 太小时,每个专家收到的 token 少,矩阵乘法利用率低;batch 太大,all-to-all 通信与 KV cache 又增大. 长上下文预填充、短非思考请求和长思考解码形成不同负载,调度器需要在它们之间平衡.

公开模型卡列出的支持框架与示例说明权重具备部署路径,并不承诺所有硬件都以相同精度和速度运行. 复现报告应给出设备型号、卡数、并行策略、dtype、输入输出长度和并发,单独一个 tokens/s 数字没有可比性.

### 6.32. 最小结论与不可越过的边界

从公开文件可以稳定得出四项结论. V3.1 是 671B 总参数、37B 激活参数的 V3 系底座延伸;V3.1-Base 经 32K 与 128K 两阶段共约 840B token 的继续训练;同一后训练 checkpoint 通过模板支持思考与非思考;官方系统在给定代码、搜索和推理评测协议中较旧版本取得明显改善,同时减少若干推理任务的输出长度.

还有四项内容不能从结果表中倒推. 无法确定 CoT 压缩的具体算法,无法确定 Agent 后训练使用哪种强化学习或偏好优化,无法把每项分数增量分解到长上下文、模板、数据和 harness,也无法仅凭 UE8M0 名称断言相对高精度完全无损.

这条边界对技术阅读很重要. 发布材料较短时,最容易出现两种错误:把所有缺失细节都想象成某个流行算法,或者因为没有完整论文就忽略已经开放的权重、模板和配置. 前一种会制造事实错误,后一种又浪费可验证信息. V3.1 适合沿公开接口逐层拆解:权重告诉我们结构,模板告诉我们控制协议,评测告诉我们整套系统结果,未公开部分就留给消融和复现实验回答.

还可以用一次最小闭环检查自己的理解. 取同一道需要工具的题,固定权重与采样参数,分别渲染两种模板;保存真实 token 序列,限制相同总预算,记录每步工具动作、错误恢复、输出长度和最终得分. 再把 128K 输入缩到 32K,保留完全相同的关键证据,观察变化来自窗口容量还是无关历史. 随后在可信 FP8 实现和高精度参考间比较层输出,排除数值格式错误. 这套实验不能复原官方训练,却能验证公开接口中的主要因果关系.

如果思考模式只增加长度而不提高困难任务成功率,需要检查模板和预算;如果长窗口加入更多材料后反而退化,需要检查检索、边界与状态管理;如果工具 JSON 合法但任务失败,问题位于动作语义而非 schema;如果不同框架分数相差很大,先核对 tokenizer、模板、scale 与 harness. 这些诊断顺序把复杂系统拆成可检查环节,也避免把所有异常都归结为“模型不够聪明”.

V3.1 的意义因此不止是榜单上的一个版本号. 它展示了同一套大规模 MoE 参数怎样通过继续预训练、后训练和协议设计承担不同计算预算,也暴露了统一之后的新问题:模式会互扰,历史要裁剪,工具需要约束,长上下文需要治理,低精度格式需要精确实现. 把这些问题讲清楚,比给未公开算法起一个确定名字更接近这次发布真正提供的信息.

这也是阅读后续版本时可以继续沿用的坐标系:底座结构、训练分布、后训练行为、交互协议与运行系统分别发生了什么变化,对应证据又来自哪一层.

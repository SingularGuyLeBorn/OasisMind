# smallpond 技术解析: 每个分区一个 DuckDB, 中间数据全落 3FS

来源: [deepseek-ai/smallpond](https://github.com/deepseek-ai/smallpond), 2025-02-28 随 DeepSeek 开源周第五天与 3FS 一起公开, 首个提交 `770aa41` 日期为 2025-02-25. 唯一的版本 tag 是 `v0.15.0`, 指向首个提交, `pyproject.toml` 的版本号同为 0.15.0; `main` 分支最新提交是 2025-03-05 的 `52ecc5e` (代码格式化), 此后没有更新. 许可证 MIT. 文档的逐段对照见 [smallpond 文档对照译稿](./smallpond-bi.md), 底层存储见 [3FS 技术解析](../3fs/3fs-analysis.md). 源码链接均按 `main` 分支核对.

## 1. 定位: 单机 DuckDB 加共享存储

### 1.1 要解决的瓶颈

大模型训练前的数据准备 (去重, 过滤, 打分, 混合, 打乱) 动辄 PB 级. 常见做法是 Spark, 它有完整的 shuffle 服务, 内存管理和容错, 也带来 JVM, 常驻集群和调参成本. DuckDB 是另一端: 单进程, 向量化执行, 读写 parquet 很快, 但只能用一台机器的核和内存. smallpond 的做法是在两者之间取一个最小方案: 数据按用户指定的规则切成很多分区, 每个分区交给一个独立的 DuckDB 进程处理, 任务之间不直接通信, 只通过共享文件系统上的 parquet 文件交接.

这套做法依赖一个前提: 共享存储的带宽足够大, 让「每一步都落盘」的代价可以接受. DeepSeek 内部有 3FS, 计算节点每台可以读写 20 GiB/s 以上, 数百台存储节点的聚合带宽是 TiB/s 量级. 有了这样的存储, 框架可以省掉 Spark 里最复杂的几块: 没有 shuffle 服务 (中间结果就是文件), 没有溢写逻辑 (单个任务的数据量由分区数控制在内存以内), 失败重试也简单 (重跑一个任务只需重新读它的输入文件). README 的三条卖点「DuckDB 带来的性能」「可扩展到 PB 级」「没有常驻服务」都来自这个前提.

### 1.2 两套 API 与组件

仓库里有两套入口, 文档承认是历史原因. 高层 API 以 `DataFrame` 为中心 ([smallpond/dataframe.py](https://github.com/deepseek-ai/smallpond/blob/main/smallpond/dataframe.py)), `smallpond.init()` 建会话, 读入数据后链式调用 `repartition`, `map`, `filter`, `partial_sql`, 遇到 `write_parquet`, `to_pandas` 等操作才执行, 后端是 Ray. 低层 API 由用户手工创建节点组成 `LogicalPlan`, 交给 `Driver().run(plan)`, 后端是内置调度器, 只能一次性执行一张静态图. 文档说低层 API 优化更多, 配置更丰富, 推荐的却是 DataFrame.

两条路径共享同一套中间层: 节点 (`smallpond/logical/node.py`) 描述逻辑操作, 优化器 (`smallpond/logical/optimizer.py`) 做节点合并, 规划器 (`smallpond/logical/planner.py`) 把节点展开成任务, 任务 (`smallpond/execution/task.py`, 约 3200 行) 负责真正读写数据. 差别只在任务怎样被分发: Ray 路径把每个任务包成 `@ray.remote` 函数, 内置路径用文件队列把任务推给执行器进程. 这种分层让低层 API 写的计划也能跑在 Ray 上, `Driver` 的 `ray` 模式就是把计划根节点包成 DataFrame 再调 `compute()`.

### 1.3 和 MapReduce, Spark 放在一起看

从数据流的形态看, smallpond 加 3FS 更接近 MapReduce 加 GFS: 计算节点从分布式文件系统读输入, 写输出, shuffle 的中间数据也写回同一个文件系统. [Eventual 的文章](https://www.eventual.ai/blog/deepseek-smallpond-3fs)指出了两者的一个差别: MapReduce 把 map 端的中间结果写在计算节点本地盘, reduce 端再远程拉取, smallpond 没有这层本地化, 中间数据一律写到 3FS. 这让计算节点完全无状态, 任何一台挂了都不丢中间结果, 代价是 shuffle 流量要过两次网络 (写到存储, 再从存储读出), 对存储带宽的要求翻倍.

和 Spark 比, 最大的功能差距在查询规划. [reata 的源码分析](https://reata.github.io/blog/smallpond-review/)强调, smallpond 不会把一条 SQL 自动拆成带 shuffle 的多阶段任务, `partial_sql` 只在每个分区上各跑一次; 用户选错分区键, 聚合或 join 的结果就是错的, 框架不会报警. [火山引擎的实践文章](https://developer.volcengine.com/articles/7480808856298192934)给了另一个视角: 两套后端里 Ray 明显快于内置调度器, 原因是内置调度器派发任务要把序列化的任务对象写进共享存储的队列目录, 再由执行器轮询读取; 他们还把存储换成 TOS 的 fsspec 或 FUSE 接口跑通了 smallpond, 说明它和 3FS 的耦合很松, 只是换了存储之后速度不同. 在 Spark 的位置上, smallpond 用「用户自己负责分区正确性」换来了极小的代码量: 逻辑层和执行层合计约 1 万行 Python.

smallpond 还可以从关系代数的角度理解. 一张关系记为 $R$, 过滤是选择算子 $\sigma_p(R)$, 只保留满足谓词 $p$ 的行; 投影是 $\pi_A(R)$, 只保留列集 $A$; 映射可以看成带表达式的广义投影; 聚合是按键 $K$ 分组后应用聚合函数 $\gamma_{K,f}(R)$. 这些算子是否能够独立地放到每个分区上执行, 取决于它能否与数据并集交换. 若 $R=R_1\uplus\cdots\uplus R_n$, 过滤满足:

$$
\sigma_p(R)=\sigma_p(R_1)\uplus\cdots\uplus\sigma_p(R_n).
$$

投影在保留重复行的 bag semantics 下也满足同样的分解. 所以逐行过滤、列变换、格式转换天然适合 `partial_sql`: 每个分区独立执行后把结果文件集合并起来, 等价于在全表上执行一次. `distinct`、全局 `order by`、带跨分区键的聚合和 join 则没有这个性质. 例如每个分区各自执行 `count(distinct user_id)`, 再把局部计数相加, 同一个用户若落在两个分区便会被重复计数. 正确方案需要先把相同 `user_id` 的行送入同一个分区, 或把局部结果换成可合并的集合草图. smallpond 的极简来自它不替用户证明这些等价变换.

这也解释了 smallpond 与 Spark 的分工差异. Spark SQL 会把声明式查询编译成由 exchange 隔开的物理阶段, 根据连接键和聚合键插入 shuffle; smallpond 只优化一个 DuckDB 任务内部的 SQL, 跨任务的数据重排必须显式写进 DataFrame 链. DuckDB 在每个任务内部仍会做过滤下推、表达式化简、连接次序选择和向量化执行, 官方的[内部结构文档](https://duckdb.org/docs/current/internals/overview)列出了这些优化. 因此 smallpond 并没有重写一个分布式 SQL 引擎, 它把分布式规划留给调用者, 把单分区物理执行交给 DuckDB, 再用共享文件把两个层次接起来.

### 1.4 三层数据抽象与可组合性

理解这套接口时, 最容易混淆的是 DataFrame、逻辑节点和数据集文件三层对象. DataFrame 是用户看到的句柄, 链式调用只返回新的句柄; 逻辑节点记录运算及依赖, 本身没有数据; 执行任务产生的 DataSet 才记录一组可读文件. 对一条链

$$
D_3=\operatorname{filter}_p\left(\operatorname{map}_g\left(\operatorname{read}(P)\right)\right),
$$

创建 $D_3$ 时并未扫描路径 $P$. `compute` 触发后, 计划器从 $D_3$ 反向遍历依赖, 优化器把可融合的 SQL 节点组合为一个查询, 规划器再把节点展开为按分区编号区分的任务. 任务完成后得到文件集合 $F_3=\{f_{3,0},\ldots,f_{3,m-1}\}$. 下游读取的是 $F_3$ 中的 parquet, 不会持有上游 DuckDB 连接或进程内表.

这个三层分离给组合带来两个效果. 第一, 计算图可以先完整建立, 再统一做 SQL 融合和任务展开. 第二, 物化边界十分清晰: 分区节点、Python 节点和数据汇节点会把逻辑链切开, 上一段必须产生文件, 下一段才能消费. 文件既是数据交换格式, 也是调度依赖兑现后的证据. 相比把大对象放进 Ray object store, smallpond 传递的 ObjectRef 主要承载路径和元信息, 大块数据继续留在共享存储上. 这降低了对象存储容量与节点内存对数据规模的限制, 同时把大量顺序 IO 和文件元数据操作放到了关键路径.

可组合性还有一个容易遗漏的条件: 组合后的算子必须保持模式契约. `map` 改了列名或类型后, 下游 `partial_sql` 按新模式绑定; 多个 parquet 文件模式不同时, `union_by_name` 决定按列名对齐并为缺失列填入 `NULL`. DuckDB 的 [Parquet 文档](https://duckdb.org/docs/lts/data/parquet/overview)说明了按名称合并、过滤下推和投影下推的语义. 这能容纳数据逐步演化, 却不能自动判断两个同名列是否拥有同一种业务含义. 如果一批文件中的 `score` 是概率, 另一批中的 `score` 是百分制分数, 类型兼容仍会得到语义错误的结果. 分布式执行正确性因此包含两层: 算子在关系代数上可分解, 文件模式和字段含义也要一致.

## 2. 执行模型: 逻辑计划, 分区与调度

### 2.1 节点, 逻辑计划与 SQL 合并

每个 DataFrame 内部只持有一个节点和会话引用. `read_parquet` 生成 `DataSourceNode`, `repartition` 按参数生成三种分区节点之一, 字符串形式的 `map` / `filter` / `partial_sort` / `partial_sql` 都生成 `SqlEngineNode`, 函数形式的 `map` / `filter` / `flat_map` / `map_batches` 生成 `ArrowBatchNode`, `write_parquet_lazy` 生成 `DataSinkNode`. 节点之间以 `input_deps` 相连, 构成一张 DAG. SQL 节点的查询串里用 `{0}`, `{1}` 引用第几个输入, 执行时替换成 DuckDB 视图名; `filter('a > 1')` 实际是 `select * from {0} where (a > 1)`, `map('a + b as c')` 是 `select a + b as c from {0}`.

求值前, `Optimizer` 遍历计划做唯一一种优化: 若一个 `SqlEngineNode` 的唯一输入也是 `SqlEngineNode`, 就把下层查询塞进上层的 `{0}` 位置成为子查询, 合成一个节点 (`visit_query_engine_node`). 合并后的 CPU 和内存上限取两者较大值, UDF 列表拼接. 这样 `filter` 接 `map` 接 `partial_sort` 只跑一轮 DuckDB, 中间不落盘. lambda 写法生成的 `ArrowBatchNode` 会打断合并. 优化器还接受一个 `exclude_nodes` 集合, 已经求值过的节点不再改写, 让同一会话里后续 DataFrame 复用已有任务 (`Session._node_to_tasks`).

### 2.2 分区: 生产者与消费者两层任务

分区是 smallpond 唯一的数据重分布手段, 而且必须手动指定. `repartition(n)` 按文件均分, `repartition(n, by_rows=True)` 按行区间均分, `repartition(n, hash_by=列)` 按列哈希, `repartition(n, by=列)` 按某列里已经算好的分区号直接分发. 规划器对所有分区节点用同一套展开规则 ([smallpond/logical/planner.py](https://github.com/deepseek-ai/smallpond/blob/main/smallpond/logical/planner.py) 的 `visit_partition_node`): 先生成若干生产者任务, 每个生产者把自己那份输入切成 $n$ 份写出; 再生成 $n$ 个消费者任务, 第 $i$ 个消费者收集所有生产者的第 $i$ 份. 消费者 (`PartitionConsumerTask`) 只拼文件列表, 不读写数据, 下游任务拿到的就是一串文件路径.

生产者任务数 $P$ 的取法是:

$$
P = \max\left(1, \min\left(P_{\max}, \left\lceil \frac{4096000}{n} \right\rceil, 2 E \left\lceil \frac{C}{c} \right\rceil\right)\right)
$$

式中 $n$ 是分区数, $P_{\max}$ 是节点类型的上限 (`HashPartitionNode` 为 1000, 均匀分区节点为 1, 加载已分区数据为 10), $E$ 是执行器数, $C$ 是每台可用核数, $c$ 是任务的 `cpu_limit`. 常数 4096000 限制 $P \times n$, 也就是这一步产生的中间文件组数. 上游任务数多于 $P$ 时, 规划器把它们按行分成 $P$ 组, 每组一个 `MergeDataSetsTask`; 少于 $P$ 时先合并成一个, 再用 `SplitDataSetTask` 切成 $P$ 份. 均匀分区的 $P_{\max}$ 为 1, 所以 `repartition(n)` 只有一个生产者, 它只改文件列表的归属, 不搬数据. 节点还支持 `nested=True` 的嵌套分区: 在每个已有分区内部再切 $n$ 份, 分区维度叠加, docstring 引用的出处是 SIGMOD 2012 论文 Advanced partitioning techniques for massively distributed computation 的 5.1 节.

### 2.3 Ray 路径: 远程函数与标记文件

高层 API 求值时, 规划器为优化后的计划生成任务列表, 然后对每个任务调 `Task.run_on_ray` ([smallpond/execution/task.py](https://github.com/deepseek-ai/smallpond/blob/main/smallpond/execution/task.py)). 这个方法递归地对输入任务调 `run_on_ray` 拿到 `ObjectRef`, 再以 `num_cpus=cpu_limit`, `memory=memory_limit` 提交一个 `@ray.remote` 函数 `exec_task`, 依赖关系完全交给 Ray 的对象依赖去排. 任务的返回值是输出数据集对象, 里面只有文件路径和元信息, 经 Ray 对象存储传给下游, 体积很小. 数据本身在共享文件系统上, 所以 Ray 调度时不需要考虑数据局部性.

容错靠两类文件. 执行前, `exec_task` 在 `staging/started_tasks/` 下探测 `<节点>.<任务>.<重试号>` 标记文件, 已存在就把重试号加一, 超过 `DEFAULT_MAX_RETRY_COUNT` (5) 就放弃, 然后创建当前重试号的标记; 执行成功后把输出数据集原子写成 `staging/completed_tasks/<节点>/<任务>.pickle`. 下次 `run_on_ray` 看到这个文件, 直接读出结果, 不再执行, 这就是文档说的任务级检查点. 两点副作用文档没有写: 一是作业目录名由 `job_time.job_id` 组成, 默认每次运行都是新目录, 想续跑必须用 `SP_JOBID` 和 `SP_JOB_TIME` 固定; 二是标记文件跨会话累积, 同一作业目录重跑超过 5 次的任务会直接报错. 另外 `DataFrame._compute` 会捕获 Ray 的 `RuntimeEnvSetupError` 重试 3 次, 间隔 10, 20, 40 秒, 注释写明这是 Ray 2.24 已修的 bug, 因为 Ray 从 2.11 起不再支持 Python 3.8, 项目没法升级.

### 2.4 内置调度器: 文件队列, 推测执行与资源提升

低层 API 的 `Driver` 有三种模式. `scheduler` 模式构造 `JobManager`, 把运行时上下文和执行计划 pickle 到 `config/`, 通过平台拉起执行器, 再在本进程运行 `Scheduler`; `executor` 模式读回上下文, 起执行器轮询队列, 开 NUMA 绑定时每个 NUMA 节点一个进程. 调度器和执行器之间没有 RPC, 每个执行器在 `queue/<执行器 id>/` 下有一对基于文件的工作队列 ([smallpond/execution/workqueue.py](https://github.com/deepseek-ai/smallpond/blob/main/smallpond/execution/workqueue.py) 的 `WorkQueueOnFilesystem`), 调度器扫描这个目录发现新执行器, 定期往每个队列推一个 `Probe`, 执行器回报 CPU, 内存和负载; 连续丢失的探测数超过阈值就判执行器失败, 其上运行的任务重新入队 ([smallpond/execution/scheduler.py](https://github.com/deepseek-ai/smallpond/blob/main/smallpond/execution/scheduler.py) 的 `update_executor_states`).

内置调度器比 Ray 路径多了三种优化. 推测执行 (`start_speculative_execution`, 默认开启): 同一逻辑节点已完成 20 个以上任务后, 若某个运行中任务的耗时超过中位数一定阈值, 就在别的执行器上再发一份; 阈值在调度队列较短时取 p95 与 p50 之差, 否则取 p99 与 p50 之差并随重试次数放大, 且不低于探测超时. 资源提升 (`try_boost_resource`): 任务派发时若执行器有空闲, 把它的 CPU 和内存上限各提到原来的两倍以内, 但不超过整机一半. OOM 放宽 (`try_relax_memory_limit`): 任务因内存不足失败后, 内存上限翻倍 (不超过整机) 再试. 此外 `Driver` 的内存分配器默认 mimalloc, 可选 jemalloc; 高层 API 默认用系统分配器, 启动 Ray 时通过环境变量把 Arrow IO, OpenMP, Polars 的线程数压到 2 ([smallpond/session.py](https://github.com/deepseek-ai/smallpond/blob/main/smallpond/session.py)), 避免同一台机器上的多个任务各自开满线程.

### 2.5 惰性计划到底延迟了什么

惰性求值常被概括为「等到最后再运行」, 这个说法遗漏了最有价值的一层: 延迟让系统在看到更长的算子链后决定物化边界. 假设用户连续写下过滤 $p$、派生列 $g$ 和过滤 $q$, 逐语句执行会产生两份中间数据. smallpond 若把三步都表示成 `SqlEngineNode`, 优化器可以构造嵌套查询:

$$
Q(R)=\sigma_q\left(\pi_{A,g}\left(\sigma_p(R)\right)\right).
$$

DuckDB 随后还能把 $p$ 下推到 parquet 扫描, 只读表达式所需的列. 官方文档说明 parquet 扫描会利用 projection pushdown 和 filter pushdown, 若 row group 带有可用的 min/max 统计, 还可直接跳过不可能命中的 row group. 因而惰性计划节省的内容包括中间文件写入、再次解压读取、无关列 IO 和部分 row group 扫描. 这几项收益都来自「在物化前保留关系表达式」, 与 Python 语法上的链式调用没有必然联系.

融合有明确边界. `repartition` 改变行到分区的归属, 必须物化; Python UDF 可能包含任意副作用或依赖解释器对象, 无法安全地改写进 SQL; 一个节点有多个消费者时, 重复内联可能让上游被算多次, 已完成节点的缓存映射则可以把共享子图收束为同一批文件. 因此最短的物化链未必总是最快. 过长 SQL 会扩大单任务输入和峰值内存, 而提前物化能让多个下游复用同一份结果. smallpond 的优化器只做相邻 SQL 合并, 没有基于代价的公共子表达式选择, 用户需要通过显式求值或写出中间结果控制复用位置.

惰性图还影响错误出现的时机. 列名拼错、SQL 类型不匹配、输入文件损坏, 往往在 sink 或 `to_pandas` 触发计算后才暴露. DataFrame 构造成功只代表逻辑节点能被创建, 不代表查询已经通过 DuckDB 的绑定和执行. 对长流水线来说, 可以在重要模式变化后物化一个小样本或检查 schema, 但这种检查必须与正式全量图使用同一表达式. 若验证路径另写一套逻辑, 小样本成功也不能约束生产图的语义.

### 2.6 分区不变量与全局正确性

设数据集 $R$ 被分成 $n$ 个分区, 分区函数为 $h(x)\in\{0,\ldots,n-1\}$. 对等值 join $R\bowtie_{R.k=S.k}S$, 要让每个输出分区独立求解, 两边必须使用相同的分区数和等价的键编码:

$$
h_R(r.k)=h_S(s.k),\qquad \forall r,s:\ r.k=s.k.
$$

满足这个条件后, 所有可能匹配的记录会在同一个消费者任务相遇, 全局 join 等于各分区 join 的并集. 若一边对字符串原值哈希, 另一边先做大小写归一化; 或两边对 `NULL` 使用不同规则, 相等的业务键仍可能被送到不同分区. SQL 查询在每个分区内都能顺利完成, 最终结果却静默漏行. 这类错误比任务失败更危险, 因为调度器只观察文件和退出码, 无法从执行成功推断分区不变量成立.

聚合还要区分可组合函数. `sum` 与 `count` 可以先局部聚合再相加. `min` 和 `max` 也满足结合律. 平均值若只合并局部平均会错, 应携带二元状态 $(s,c)$, 其中 $s$ 为和, $c$ 为计数, 最后计算 $s/c$. 方差需要携带计数、均值和平方偏差等可合并状态, 直接平均各分区方差会忽略分区大小和分区均值差异. 中位数、精确分位数与 `distinct` 通常需要收集更多状态或先按键重排. 所以「能不能 partial」问的是聚合状态是否形成可结合的合并运算, 不能只看 SQL 函数名字.

顺序算子是另一类边界. 每个分区内部 `order by t` 只能保证局部有序. 若各分区的键范围互不重叠, 并且输出按范围顺序拼接, 局部排序可以组成全局排序; GraySort 用键高位产生 bucket 正是这个构造. 若采用普通哈希分区, 第 $0$ 个分区和第 $1$ 个分区的键范围交错, 按分区号拼接没有全局顺序. 全局 top-$k$ 可以先求各分区 top-$k$, 合并至多 $nk$ 条候选后再求一次 top-$k$; 全局 rank、带跨分区窗口的累计和则需要范围分区或额外阶段. smallpond 提供数据搬运积木, 证明这些阶段等价仍属于作业设计的一部分.

### 2.7 任务图、资源图和反压

逻辑 DAG 描述数据依赖, 运行时还存在一张资源图. 每个任务声明 CPU 与内存, 调度器只有找到满足资源约束的执行器才会发出任务. 设节点共有 $C$ 个可调度核、内存 $M$, 某类任务需要 $c$ 核和 $m$ 内存, 单节点理论并发上限为:

$$
q=\min\left(\left\lfloor\frac{C}{c}\right\rfloor,\left\lfloor\frac{M}{m}\right\rfloor\right).
$$

这个式子只给出资源配额上界. 所有任务同时从 3FS 读写时, 实际并发还会受网络、存储聚合带宽、parquet 解压和文件打开速率限制. 增加任务数能隐藏单任务等待, 超过瓶颈后只会让更多任务争用同一资源. 内置调度器的资源提升在队列短时把空闲资源交给单个任务, 本质上是在任务级并行与任务内并行之间动态移动预算.

smallpond 没有贯穿算子流水线的流式反压. 一个阶段的消费者依赖生产者输出文件, 分区生产者先把中间结果写入共享存储, 下游再读取. 好处是上下游速度不必实时匹配, 文件承担了持久缓冲; 代价是缓冲规模可能等于整个阶段输出. 当下游慢或失败时, 上游已经写出的文件继续占用容量. 文件系统空间因此属于作业资源的一部分, 仅按 CPU 和内存调度无法避免存储耗尽. 这与基于内存 channel 的流执行不同: 后者会通过阻塞生产者施加反压, smallpond 依赖阶段边界和外部容量规划.

Ray 路径把依赖表示为 ObjectRef. [Ray 官方任务文档](https://docs.ray.io/en/latest/ray-core/tasks.html)说明, 远程任务根据资源需求、调度策略和参数位置选择节点, ObjectRef 作为参数时会在任务执行前解析. smallpond 的返回对象主要是共享路径, 因此 Ray 的数据局部性信号很弱: 任一执行器看到的逻辑对象都很小, 真正的数据读取成本藏在任务内部. 这种设计适合所有节点等价访问 3FS 的环境, 若共享存储跨机架带宽差异明显, 默认 Ray 调度难以从 ObjectRef 大小推断最佳位置.

### 2.8 分区数为何同时影响语义和性能

哈希分区数 $n$ 在纯关系语义下可以任意选择, 只要相关输入使用同一个 $n$ 和同一个哈希函数, join 与按键聚合的结果集合应保持一致. 运行代价却会显著变化. 若总数据量为 $B$, 均匀分布时单分区约为 $B/n$; 为使任务在内存 $m$ 内完成, 需要 $B/n$ 小于算子可用内存的某个比例. 比例不能取到 $1$, 因为解压缓冲、哈希表、排序工作区、输出缓冲和运行时对象都会占空间. 排序常需要输入量若干倍的瞬时空间, join 的构建侧哈希表也比原 parquet 字节更大.

另一方面, $n$ 受有效并行度上界约束. 集群同时能运行 $Q$ 个任务时, $n\ll Q$ 会浪费节点; $n$ 稍大于 $Q$ 能让调度器用后续波次填补快慢差异; $n$ 远大于 $Q$ 后, 额外切分主要增加任务和文件开销. 若有 $P$ 个 shuffle 生产者, 最坏文件组规模近似 $P\times n$, 再乘每个生产者内部批次数. smallpond 用 4096000 限制其中一层乘积, 但批次数、空文件策略和每线程输出仍会改变实际文件数.

改变分区数还会改变随机流水线和浮点聚合的具体结果. 哈希键所属分区变化后, 局部处理顺序、线程合并顺序与文件排列都会变化. 对整数 `sum` 等精确结合运算, 关系结果保持不变; 对浮点 `sum`、近似分位数、依赖首条记录的去重和未固定种子的抽样, 结果可能漂移. 因而分区数既是性能参数, 也可能进入数据版本定义. 需要实验可比时, 它应和代码及阈值一起记录.

一个可操作的选择过程是先用真实数据估计每行解压后宽度、键频率和算子放大率, 由最大可接受分区确定 $n$ 的下界; 再以集群并发和目标文件大小确定合理区间; 最后在小规模同分布样本上观察任务固定开销、最大分区、p50/p99 时长和文件数量. 平均吞吐只能说明集群是否繁忙, 最大分区和尾部时长才决定阶段什么时候结束.

## 3. 算子: 一个任务里的 DuckDB

### 3.1 SqlEngineTask 的资源与输出设置

每个 SQL 任务开一个内存数据库 `duckdb.connect(":memory:")`, 由 `ExecSqlQueryMixin.prepare_connection` 设置: 线程数 `threads` 为 $\lceil c \cdot r_c \rceil$, 内存上限 `memory_limit` 为 $m \cdot r_m$, 其中 $c$, $m$ 是任务的 CPU 和内存上限, $r_c$, $r_m$ 是超额系数 (`SqlEngineNode` 默认 1.0 和 0.9); 同时关闭 `preserve_insertion_order`, 打开 `enable_object_cache`, 默认不设临时目录, 也就是不溢写. 输入数据集展开成视图, parquet 输入是一条 `read_parquet([path1, path2, ...], union_by_name=...)`, 查询结果用 `COPY ... TO ... (FORMAT PARQUET, PER_THREAD_OUTPUT true, ...)` 直接写成 parquet, 默认 ZSTD 3 级压缩, 行组 122880 行 ([smallpond/execution/task.py](https://github.com/deepseek-ai/smallpond/blob/main/smallpond/execution/task.py) 的 `SqlEngineTask.process_batch`). `PER_THREAD_OUTPUT` 让每个线程各写一个文件, 省去合并, 代价是输出文件数随线程数增加.

默认资源值很保守. `SqlEngineNode` 的 `cpu_limit` 默认 1, `memory_limit` 不指定时按核数比例分配, 即 $m = M \cdot c / C$, $M$ 和 $C$ 是本机可用内存和物理核数. 在 GraySort 用的 192 核, 2.2 TiB 计算节点上, 默认一个 SQL 任务只有 1 个线程和约 11.7 GiB 内存, DuckDB 的多线程能力完全没用上, 并行度全靠任务数. 想让单个分区跑得更快, 要在 `partial_sql` 或 `map` 的 `**kwargs` 里显式传 `cpu_limit`, `memory_limit`. 带 UDF 的查询会被强制降到最多 3 核, 理由是 DuckDB 里 Python UDF 的执行并行度不高.

### 3.2 HashPartitionDuckDbTask: 排序后按分区号并发 COPY

哈希分区是唯一真正搬数据的分区方式, 默认用 DuckDB 实现 (`HashPartitionDuckDbTask`). 分区键的计算是:

$$
k = \text{hash}(\text{concat\_ws}(\text{'\#\#'}, a_1, \dots, a_j)) \bmod n
$$

式中 $a_1, \dots, a_j$ 是 `hash_by` 指定的列, 结果以 UINT64 存进 `__data_partition__` 列. `random_shuffle` 时改用 `random()` 乘一个 $n$ 的整数倍; `by=列` 生成的 `ShuffleNode` 则跳过计算, 直接用该列当分区号. 生产者的输入按 `memory_limit // 6` 分批 (`partition_by_size`), 每批先执行 `CREATE TABLE temp_query_result AS ... ORDER BY __data_partition__` 建一张按分区号排好的临时表, 校验分区号都在 $[0, n)$ 内, 再开 `min(n, cpu_limit)` 个游标, 每个游标负责一部分分区号, 并发执行 `COPY (SELECT ... WHERE __data_partition__ = i) TO '<任务>-<i>.<批>.parquet'`. 先排序再按等值条件过滤, 让每条 `COPY` 只扫临时表里连续的一段.

这个实现有两个直接后果. 每批输入都会给 $n$ 个分区各写一个文件, 中间文件数是「生产者数 × 批数 × 分区数」, 分区数大或单批内存小时, 文件数会膨胀到百万级以上, 这对元数据服务的压力远大于数据量本身, 也是 3FS 用 FoundationDB 做可扩展元数据的现实需求. 另一种选择是 `hive_partitioning=True`, 改用 DuckDB 的 `PARTITION_BY` 一次写出目录分区; 或 `use_parquet_writer=True`, 用 Arrow 的 `ParquetWriter` 把同一分区的数据追加进同一个文件, 文件少但慢. 还有一个 `engine_type="arrow"` 的实现 `HashPartitionArrowTask`. 选择引擎的静态方法 `HashPartitionTask.create` 把 `**kwargs` 误写成了 `*kwargs`, 目前所有调用方只传位置参数, 没有触发.

### 3.3 Python 算子与函数式接口

不用 SQL 时, 有三类 Python 算子. `ArrowComputeNode` / `PandasComputeNode` 一次拿到整个分区的表; `ArrowStreamNode` / `ArrowBatchNode` / `PandasBatchNode` 按批迭代, `map_batches` 默认每批 122880 行, `ArrowStreamNode` 还支持按批做检查点 (文档提到的批级检查点即此); `PythonScriptNode` 最自由, 拿到输入数据集和输出目录, 自己决定读写方式, GraySort 的排序步骤就是它. 这些算子都在任务进程里直接调用用户函数, 函数会随任务一起被 cloudpickle 序列化, 源码在 Ray 路径上专门处理了一个常见错误: 函数捕获了外部导入的 loguru logger 时 pickle 失败, 报错里提示「在任务内部导入」.

DataFrame 的函数式接口 (`map(lambda row: ...)`, `filter(lambda r: ...)`) 建在 `ArrowBatchNode` 上, 实现是 `table.to_pylist()` 逐行转字典, 调函数, 再 `Table.from_pylist` 转回. 每行都要经过 Python 对象构造, 吞吐明显低于在 DuckDB 里向量化执行的 SQL 表达式, docstring 也建议优先用 SQL. `filter` 的函数版先对所有行求布尔值再整体过滤, 内存里同时有整批的 Python 字典. 需要复杂逻辑又在意速度时, 应该用 `map_batches` 直接处理 Arrow 表, 或者把逻辑写成 DuckDB UDF.

### 3.4 向量化执行如何落到单分区

DuckDB 官方的[执行格式文档](https://duckdb.org/docs/lts/internals/vector)把 `DataChunk` 定义为若干列向量的集合, 默认向量宽度为 2048 行. 算子一次处理一批向量, 可以减少逐行解释和函数调用开销, 并提高 CPU cache 与 SIMD 的利用率. smallpond 把一个分区交给一个独立 DuckDB 进程后, 这个进程内部仍会把 parquet row group 解码为向量, 沿物理算子树推动 `DataChunk`, 再把结果按 row group 写回 parquet. 多机扩展发生在分区之间, 向量化发生在分区内部, 两个并行层次互相叠加.

设共有 $P$ 个可并发分区任务, 每个 DuckDB 任务使用 $t$ 个线程, 集群同时活跃的执行线程可近似为 $P\times t$. 若 $P$ 已经接近物理核总数, 再把 $t$ 提高会造成超额订阅; 若分区数量很少, 单任务只用一个线程又会闲置大量核. smallpond 默认让 SQL 任务偏向单核, 说明它优先选择任务级并行. `PER_THREAD_OUTPUT` 会让 DuckDB 每个写线程生成独立 parquet 文件, 线程数提高也会增加文件数量. 所以 CPU 利用率、单文件大小和元数据压力是同一个参数选择的三个侧面.

parquet row group 决定了解码、并行和跳读的粒度. [DuckDB 的 Parquet 建议](https://duckdb.org/docs/preview/data/parquet/tips)指出, 默认 row group 为 122880 行, 读取时可以按 row group 并行, 谓词还能利用列统计跳过不匹配的组. row group 太大时, 单文件内部并行度低, 选择性查询也会读入更多无关数据; 太小时, 元数据、压缩字典和调度开销增加. smallpond 的默认值与 DuckDB 默认值一致, 对一般列式分析是合理起点, 但宽文本样本与窄数值表的单行字节数差异很大. 固定行数不等于固定内存, 任务内存边界最终仍受真实列宽和算子状态影响.

### 3.5 SQL 融合、列式文件与代价传播

当过滤和投影融合到一次 DuckDB 查询时, 代价可以从文件层一路缩减. 设输入有 $N$ 行、每行共 $B$ 字节, 查询只读取其中比例 $r_c$ 的列, 谓词通过率为 $r_f$. 忽略元数据与压缩差异, 扫描量约为 $NB r_c$, 输出量约为 $NB' r_f$, 其中 $B'$ 是投影后的行宽. 若过滤列带有紧致的 row group 统计, 实际扫描还能乘上 row group 命中率 $r_g$. 提前把每一步物化会先写出未投影或未过滤的中间结果, 下一步又重新读入, 这些 IO 无法由后续优化器追回.

不过 SQL 融合不会跨越分布式分区节点. 例如先过滤再哈希重分区时, 过滤应位于 shuffle 前, 让较少数据跨存储写读; 先重分区再过滤则可能保持某种上游分区契约, 但传输量更大. 若过滤条件依赖 join 后字段, 它只能位于 join 之后. 关系代数中的谓词下推要满足列可用性和外连接语义: 对左外连接右表列的过滤若推到连接前, 可能改变 `NULL` 扩展行的保留方式. smallpond 的跨节点优化器不会替用户移动这些算子, 执行链写出的顺序就是分布式阶段顺序.

文件统计也不是全局优化器的完整统计. DuckDB 直接查询 parquet 时可以利用每个文件或 row group 的 min/max 做扫描裁剪, 但复杂 join 的基数估计通常弱于已经装载到数据库表的数据. DuckDB 的[文件格式性能指南](https://duckdb.org/docs/preview/guides/performance/file_formats)说明, parquet 缺少数据库格式中的部分高级统计, join 较多时装载为表可能得到更好的连接次序. smallpond 每个任务新建内存数据库并直接读取 parquet, 获得了免装载和易物化的优势, 也接受了跨文件统计有限、重复查询要重复解压的代价.

### 3.6 Python 函数的语义风险

SQL 表达式通常能被视为对输入关系的纯变换, Python 回调却可能读时钟、随机数、网络服务、全局变量或本地文件. 一旦任务失败重试, 同一输入可能产生不同输出. 推测执行更会让同一逻辑任务同时运行两份, 两份回调可能都对外部系统产生副作用. 即便 smallpond 最终只采用一份结果文件, 外部数据库写入、计费请求或消息发送已经发生两次. 因而可安全重试的 Python 算子至少应满足: 输出只由显式输入和固定配置决定, 对外部世界没有不可撤销副作用, 输出路径由任务尝试隔离.

随机操作也需要把随机种子变成任务输入的一部分. 若目标是可复现抽样, 可以从作业标识、节点标识和分区编号派生种子 $s_i=H(s_0,\text{node},i)$, 每个分区用自己的确定性随机流. 只设置一个进程全局种子仍不充分, 因为分区数变化、任务顺序变化或批大小变化都会改变随机数消费顺序. 对去重、训练数据抽样和评测集生成而言, 这种差异会让两次执行难以比较. `random_shuffle` 本就以随机函数分桶, 若调用方需要重放同一输出, 必须检查实现是否暴露并固定了所有随机源.

模式推断也会受批次影响. `Table.from_pylist` 根据 Python 对象构造 Arrow 列, 前后批次若出现不兼容类型, 可能在较晚批次才失败; 若不同分区各自推断, 还可能产生需要 `union_by_name` 才能读取的异构 schema. 对稳定流水线, Python 算子应显式约束输出字段、类型和空值规则. 这一约束与静态类型检查不同, 它是跨文件消费时的运行时数据契约.

### 3.7 join、聚合与排序的内存形态

同样写成一条 SQL, 不同算子的内存状态差别很大. 流式过滤和投影只需保留当前 `DataChunk` 及少量表达式状态, 输入再大也能批批处理. 哈希聚合要为每个分组键保存状态, 内存近似随分组基数增长. 哈希 join 通常要把构建侧装进哈希表, 内存取决于构建侧解压后的行宽和键开销. 排序要维护可排序运行段, 若没有可用临时目录或外部排序路径, 输入超过内存便直接失败.

这说明「一个分区的 parquet 文件小于任务内存」仍不够. parquet 是压缩列式格式, 文本、重复值和低基数列可能压缩得很好, 解压后的 Arrow 向量和 DuckDB 内部状态会大得多. join 输出还可能比两侧输入都大. 更可靠的估计是按解压后列宽、分组数、构建侧规模和输出基数分别建模. smallpond 给 DuckDB 的内存上限是资源隔离手段, 它无法把一个数学上需要更大状态的算子变得可执行.

join 时应尽量让较小关系成为构建侧, 但 DuckDB 的优化器是否能判断哪边小, 受 parquet 统计和过滤表达式影响. 单个任务包含多个 join 时, 连接顺序估计误差会逐级放大. 可以在 shuffle 前过滤和投影, 让构建侧显著缩小; 对很小且稳定的维表, 复制到各分区避免对大表二次 shuffle; 对两张大表, 仍需按 join 键共分区. 广播节省一侧重分区, 代价是每个任务重复读取并构建相同维表.

排序的范围分区通常需要一次采样来估计边界. 均匀哈希能平衡数量, 不能让分区间有序; 固定取键高位只在键分布与位宽合适时有效. 数据偏斜时, 等宽键范围可能包含悬殊记录数. 采样分位点可让各范围接近等量, 但样本误差和重复热门键仍会造成倾斜. GraySort 的记录键接近均匀随机, 所以高 13 位恰好形成近似均匀且天然有序的 8192 桶, 普通业务键不能直接照搬这一选择.

## 4. 与 3FS 的配合, 以及 GraySort 110.5 TiB

### 4.1 smallpond 从 3FS 拿到什么

smallpond 对存储的要求只有「所有节点看到同一个 POSIX 目录」, 上游代码通过 3FS 的 FUSE 挂载点读写, 没有调用 USRBIO. 3FS 在这里提供三样东西. 第一是带宽: 所有任务的输入, 中间结果和输出都走共享存储, 任务数上千时的聚合读写由 3FS 的数百块 SSD 和存储网卡分担. 第二是元数据扩展性: 哈希分区一步就能写出数百万个小文件, 列目录, 打开, 删除都落在 3FS 的无状态 meta 服务和 FoundationDB 上. 第三是一个专用的删除入口: [smallpond/io/filesystem.py](https://github.com/deepseek-ai/smallpond/blob/main/smallpond/io/filesystem.py) 的 `remove_path` 在路径位于 3FS 上时, 在挂载点的 `3fs-virt/rm-rf/` 下建一个指向目标的符号链接, 由 3FS 在服务端递归删除, 失败再退回 `shutil.rmtree`. 作业成功结束时 `queue`, `temp`, `staging` 三个目录都靠它清理.

这个快速删除路径判断「是否在 3FS 上」的方式是检查路径前缀是否为 `/hf3fs`, 这是 DeepSeek 内部的挂载点命名. 按 3FS 部署指南挂在 `/3fs/stage` 的开源集群匹配不上, 所有删除都会退回逐文件的 `rmtree`, 数百万中间文件的清理会慢很多. 输出阶段也依赖同一挂载点: `write_parquet` 的 `DataSinkNode` 类型是 `link_or_copy`, 源和目标在同一挂载点时用硬链接, 否则逐字节复制. 社区的 [open3fs/smallpond-3fs](https://github.com/open3fs/smallpond-3fs) 分支把 DuckDB 的读写改走 USRBIO, 说明上游版本没有用到 3FS 的零拷贝接口.

### 4.2 GraySort 的计划与配置推导

GraySort 要求把一批 100 字节的记录 (10 字节键加 90 字节载荷) 按键全局排序. [`benchmarks/gray_sort_benchmark.py`](https://github.com/deepseek-ai/smallpond/blob/main/benchmarks/gray_sort_benchmark.py) 用低层 API 搭了四步. 第一步, 一个 `ArrowTableDataSet` 列出若干段记录区间 (起始序号, 条数), 按行均分给数据生成任务. 第二步, `ArrowStreamNode` 调 gensort 生成记录, 每批默认 512 MB 写进 `/dev/shm` 再读回, 组装成三列 Arrow 表: `buckets` (键前 2 字节转大端 uint16 后右移, 保留高 13 位), `keys` (前 10 字节), `records` (整条 100 字节), 写成 parquet. 第三步, `ShuffleNode` 以 `buckets` 为分区号把数据分成 8192 份. 第四步, `PythonScriptNode` 读入每个分区, 按 `keys` 排序后把 `records` 列的底层缓冲区原样写成 gensort 格式的 `.dat` 文件. 由于分区号是键的高位, 各分区的键范围互不重叠, 按分区号顺序拼起来就是全局有序.

README 和 3FS 的 GraySort 一节都没有给出运行命令, 但几个关键数字能从脚本默认值推出来. 设执行器数 $E = 50$, 每台 192 物理核, 内存 $M \approx 2.2$ TiB. 不传 `--total_data_nbytes` 时数据量取 $E \cdot M \approx 110$ TiB, 与 110.5 TiB 吻合. 排序任务默认 8 核, 内存按核比例为 $8 \times 2.2\ \text{TiB} / 192 \approx 93.9$ GiB, 排序分区数取:

$$
n = 2^{\lceil \log_2 \max(9600 / 8,\ 110.5\ \text{TiB} / (93.9\ \text{GiB} / 4)) \rceil} = 2^{\lceil \log_2 4821 \rceil} = 8192
$$

与 3FS README 写的 8192 个分区一致. 每个分区约 13.8 GiB, 只占排序任务内存的约 15%, 留给 Polars 或 DuckDB 排序的工作区足够. 数据生成分区数默认取总核数的一半, 即 4800, 记录区间数是它的 10 倍. shuffle 一步的生产者数按 2.2 节的公式为 $\min(1000, \lceil 4096000 / 8192 \rceil, \dots) = 500$, 恰好让 $P \times n$ 顶到 4096000 的上限.

### 4.3 成绩的口径与解读

3.66 TiB/min 合 62.4 GiB/s, 摊到 50 台计算节点每台每秒排序约 1.25 GiB. 从 3FS README 的吞吐图看, 计时 30 分 14 秒对应 shuffle 和排序两个阶段, 生成数据的约 6 分钟不在其中. 每条记录在中间 parquet 里还多存了 2 字节分区号和 10 字节键的副本, 两个阶段各读一遍写一遍, 客户端侧的 IO 总量至少是数据量的 4 倍, 平均每台约 5 GiB/s, 远低于 200 Gbps 网卡的上限. 和 sortbenchmark 上 Spark 2014 年的记录 (206 台 EC2 i2.8xlarge worker, 10 Gbps 网络, 23 分钟 100 TB, 约 4.27 TB/min) 相比, smallpond 的 110.5 TiB 合 121.5 TB, 约 4.02 TB/min, 量级相同. smallpond 用了更多的核 (9600 对 6592) 和快得多的网络, 所以这个成绩说明的是「简单架构也能跑到这个量级」, 而非排序效率更高.

脚本里还有几处配置文档没有交代. 命令行 `-s/--sort_engine` 默认 `duckdb`, 函数 `gray_sort_benchmark` 的参数默认却是 `polars`, 通过 `Driver` 运行时以命令行为准; shuffle 的 `-C` 默认取 `ShuffleNode.default_cpu_limit`, 即 1 核, 函数默认却是 32. 按 1 核, 每个 shuffle 生产者只有约 11.7 GiB 内存, 单批上限约 2 GiB, 要处理约 250 GiB 输入就得分 100 多批, 每批给 8192 个分区各写一个文件, 中间文件会到数亿个. 官方成绩应当调大过 `-C` 或 `-M`, 实际取值和用的是内置调度器还是 Ray, 文档没有给出. 社区文章 (例如 Eventual 的对比) 也只是拿官方数字和 Spark 记录做比较, 没有独立复现这个规模.

### 4.4 文件物化为什么能换来简单容错

把阶段输出写成不可变文件后, 一个任务的状态可以压缩为三类: 尚未产生完整输出、已经产生可读取输出、输出元信息已经发布. 下游只依赖最后一类. 若任务先写临时路径, 完成后再原子发布完成标记, 调度器就不必恢复 DuckDB 内部算子状态; 失败尝试留下的临时文件可以忽略, 重试从输入文件重新计算. 这相当于把恢复点放在任务边界, 恢复粒度由分区大小决定.

假设任务 $T_i$ 的输入文件集合为 $I_i$, 确定性变换为 $f_i$, 输出为 $O_i=f_i(I_i)$. 任务级重试能保持结果等价需要三个条件: $I_i$ 在重试期间不可变; $f_i$ 对相同输入给出语义相同的结果; 完成记录只指向一组完整输出. 任一条件失效都会破坏缓存. 上游文件被原地覆盖时, 完成标记仍可能指向旧结果; Python 函数读取外部状态时, 重算不再等价; 完成文件早于所有 parquet 刷盘可见时, 下游会读到不完整集合. smallpond 的共享存储设计降低了执行器本地丢盘风险, 没有消除这些协议条件.

任务级 checkpoint 与数据库事务也有尺度差异. DuckDB 的[事务文档](https://duckdb.org/docs/lts/sql/statements/transactions)保证单个连接内的事务和 snapshot isolation, 但 smallpond 每个任务使用独立内存数据库, 最终交换的是外部 parquet. 一个 DuckDB 查询原子完成, 不代表由数百任务组成的阶段具备全局事务. 作业中途停止时, 共享目录可能同时存在已完成分区、临时文件和开始标记. 恢复逻辑依赖任务级完成记录继续补齐其余分区, 而不是回滚整个阶段.

文件 checkpoint 的成本可以粗略写成:

$$
T_{\text{stage}}\approx \max(T_{\text{cpu}},T_{\text{read}},T_{\text{write}})+T_{\text{meta}}+T_{\text{tail}}.
$$

$T_{\text{meta}}$ 来自创建、列举和删除大量文件, $T_{\text{tail}}$ 是慢任务拖住阶段收尾的时间. 推测执行主要压缩 $T_{\text{tail}}$, 3FS 的聚合带宽压缩读写项, FoundationDB 元数据服务承担文件数量带来的压力. 只看平均吞吐会漏掉后两项, GraySort 之类的均匀记录容易得到漂亮利用率, 文本清洗中的超长文档、数据倾斜和 Python UDF 更容易暴露尾部问题.

### 4.5 至少一次执行与幂等输出

执行器失联时, 调度器无法立刻知道原任务究竟已经停止, 还是仅仅回报通道中断. 它把任务重新入队后, 原副本可能继续运行. 推测执行也主动制造两个并发副本. 所以从任务函数视角看, smallpond 更接近至少一次执行: 同一个逻辑任务可能被启动多次. 完成结果去重能让数据流表现得像只接受一次, 但只有当不同尝试写入互不覆盖的临时位置、完成发布具备竞争保护时才成立.

设逻辑任务标识为 $i$, 尝试号为 $a$, 输出路径应包含 $(i,a)$, 最终提交记录把 $i$ 映射到某个胜出尝试 $a^*$. 两个尝试都成功时, 提交过程必须保证只有一个映射被下游采用. 如果所有尝试直接写同名 parquet, 慢副本可能覆盖快副本, 甚至让读者看到写入中的文件. smallpond 的 started/completed 标记为这套协议提供了骨架, 但用户自定义 `PythonScriptNode` 若绕开任务输出目录直接写固定业务路径, 就会重新引入覆盖和双重副作用.

幂等也适用于 sink. 把最终结果写到目标目录时, 重跑是追加、覆盖还是发现已有结果后跳过, 会决定是否产生重复样本. 训练语料流水线尤其敏感: 重复分区未必让作业报错, 却会改变样本权重. 稳妥的发布方式是先形成带版本的不可变数据集, 校验文件清单、行数与摘要后, 再原子切换一个小型清单或目录引用. 这样消费者看到旧版本或新版本之一, 避免看见半套新文件.

### 4.6 确定性分成哪几层

确定性至少有四层. 第一层是关系内容确定: 相同输入产生相同的行多重集. 第二层是行顺序确定: 输出文件内及文件之间都有稳定顺序. 第三层是文件布局确定: 文件数量、分区归属和文件名一致. 第四层是字节确定: 压缩后的 parquet 字节完全相同. 很多数据任务只要求第一层; 增量缓存、内容寻址或严格回归测试可能要求更高层.

SQL 默认采用集合或多重集语义, 没有 `order by` 就不承诺行顺序. DuckDB 的[非确定性行为文档](https://duckdb.org/docs/preview/operations_manual/non-deterministic_behavior)还说明, 多线程聚合的合并顺序可能让浮点结果产生极小差异, 不同平台上的部分函数也可能返回不同次序. 关闭 `preserve_insertion_order` 与开启 `PER_THREAD_OUTPUT` 更不会保留输入顺序. 因此两个输出即使行集合一致, 文件顺序和字节摘要也很可能不同.

需要稳定结果时, 应先明确要求落在哪一层. 若只验证关系内容, 可对主键排序后比较, 或按行规范化哈希并做可交换聚合. 若需要稳定行序, 查询必须给出能唯一排序的键; 只按有重复值的时间戳排序, 同时间记录仍可交换. 若要求稳定文件布局, 还要固定分区数、线程数、row group 和写文件策略. 浮点聚合要么接受容差, 要么固定合并次序并使用更稳定的求和方法. 把所有层都强行固定会牺牲并行度, 应根据下游需求选择.

### 4.7 数据倾斜如何穿过整个系统

哈希分区假设键分布足够均匀. 若某个热门键占全部记录比例 $p$, 那么承载该键的分区至少包含 $pN$ 行, 无论增加多少分区都无法再拆散这个键. 阶段完成时间由最大分区决定:

$$
T_{\text{stage}}\geq \max_i T(R_i).
$$

平均分区只有 $N/n$ 行并不能预测尾部. 对 join 而言, 两边热门键还可能产生笛卡尔式膨胀: 若键 $k$ 在两边分别出现 $a_k$ 和 $b_k$ 次, 输出贡献为 $a_kb_k$. 输入分区尚能放进内存, join 结果也可能远超内存和存储预算.

推测执行对随机慢节点有效, 对数据本身造成的确定性倾斜帮助有限. 同一个大分区复制到另一台机器仍要处理同样多的数据. 资源提升可以给它更多核和内存, 但热门键产生的输出量不会消失. 可行的关系变换包括给可拆的热门键加盐, 将另一侧小表复制到盐分片; 先局部聚合压缩重复记录; 或对键范围采样后做更均衡的范围边界. 每种方法都要保持语义: 加盐 join 需要复制对应记录, 聚合只能用于存在可合并状态的函数.

小文件也是一种结构性倾斜. 大量空分区或极小分区几乎不消耗数据处理时间, 却需要同样的任务、标记和文件操作. 当 $n$ 远大于有效键域, 资源耗在调度和元数据上. 分区数的选择不能只追求让最大分区放进内存, 还要让单分区数据量大到足以摊薄固定成本, 并让文件大小适合 parquet 扫描. 这正是 smallpond 的 $P\times n$ 上限试图控制的对象之一.

### 4.8 缓存复用与失效条件

完成任务文件让同一次作业中的后续 DataFrame 可以复用已物化节点. 复用成立的数学条件是节点输出只由其输入、算子参数和执行语义决定. 可以把结果写成 $O=F(I,C,V)$, 其中 $I$ 是输入快照, $C$ 是代码和配置, $V$ 是依赖版本与平台语义. 只用节点标识查 completed 文件, 实际假设 $I$、$C$、$V$ 在作业目录生命周期内都不会变化.

输入失效最直观. 路径相同但文件内容被替换后, 路径列表未变, 旧缓存却已不代表新数据. 代码失效也常见: cloudpickle 序列化的函数实现改变, 或函数引用模块中的全局常量改变. 依赖失效更隐蔽, DuckDB、PyArrow、Polars 版本升级可能改变类型转换、排序、哈希或 parquet 编码. 若完成结果要跨作业长期复用, 缓存键应纳入内容摘要、函数摘要、参数和依赖环境, 仅固定作业标识不足以证明有效.

缓存粒度与计划优化也会互动. 相邻 SQL 节点融合后, 物理节点身份可能不同于用户构造的原始节点. `exclude_nodes` 防止已经求值的部分再次被优化改写, 相当于把物化结果作为新的叶子. 好处是后续分支可以共享; 代价是已经物化的边界阻止更大范围的谓词下推和融合. 先求值一个中间 DataFrame 可能加速多分支复用, 对只有一个下游的链却会多一轮写读.

缓存错误通常也是静默的. 任务看到 completed pickle 会直接采用路径, 不会重新验证 parquet 行数、schema 或摘要. 若上一次写入在存储故障下留下逻辑完整但内容损坏的文件, 缓存会把损坏传播给所有下游. 对高价值数据, 完成记录应包含能够低成本复核的 manifest, 读取缓存时至少校验文件存在、大小与模式, 更强要求则校验内容摘要.

## 5. 适用范围, 版本与局限

### 5.1 适合与不适合的场景

smallpond 适合的任务有共同点: 能按某个键拆成互不依赖的分区, 每个分区放得进一台机器的内存, 而且有一套高带宽共享存储. 典型场景列在下面.

- 大规模数据清洗与过滤: 逐文件或逐行的打分, 去重前的哈希分桶, 格式转换, 每一步都是一轮分区内 SQL.
- 按键聚合与等值 join: 两边按同一键, 同一分区数哈希后用 `partial_sql` 处理, 每个分区独立完成.
- 训练数据混合与打乱: `random_shuffle` 先随机分区再分区内 `order by random()`, 输出直接写回 3FS 供数据加载器读取.
- 有现成 DuckDB 或 Python 处理逻辑, 想扩到多机而不改写成 Spark 作业的团队.

不适合的情况同样明显. 数据量在单机内存以内时, 直接用 DuckDB 更快, 社区 ([Definite 的文章](https://www.definite.app/blog/smallpond)) 的判断是 10 TB 以下单机 DuckDB 往往更快, 10 TB 到 1 PB 之间开始有价值, PB 级以上才是它的目标规模. 需要全局排序, 多表复杂 join 或窗口函数跨分区时, 要自己设计分区方式, 框架不会自动规划 shuffle. 没有 3FS 级别的共享存储时, 中间数据落盘成为瓶颈, 普通 NFS 很难承受百万级小文件. 流式, 低延迟或交互式查询也不在设计范围内, 每个任务都要新建 DuckDB 连接, 从共享存储读 parquet 再写回, 固定开销不适合毫秒级响应.

### 5.2 版本历史与代码和文档的出入

公开仓库的演进很短. 2025-02-25 首个提交即 `v0.15.0`, 版本号说明此前在内部已经迭代过多轮; 2025-02-27 更新 README; 2025-02-28 有两处改动 (把 `ArrowBatchNode` 暴露给 DataFrame, 整理 `JobManager` 参数), 但只留在 `wrj/arrow-batch-node` 和 `wrj/scheduler` 两个分支上, 没有合入 `main`; 2025-03-05 合入一次 150 字符行宽的代码格式化 (#18), 之后再无提交. 文档里「正在合并两套 API」的计划没有后续. 依赖上要求 `duckdb >= 1.2.0`, `pyarrow ~= 16.1.0`, `polars ~= 0.20.9`, `ray[default] >= 2.10.0`, pyarrow 和 polars 都锁在 2024 年的版本线.

代码与文档对不上的地方集中在示例. 入门文档的 `repartition(3, by_row=True)` 参数名错了, 代码是 `by_rows`, 原样运行会因多余关键字参数报错. 低层 API 的运行命令 `python script.py -i ... -n 10` 漏了 `Driver` 必填的位置参数 `mode` (`scheduler`, `executor` 或 `ray`), 示例代码也缺 `List` 的导入. 任务文档的 `RuntimeContext(JobId.new(), data_root)` 少传了 `job_time`. README 的 GraySort 成绩来自低层 API 和 `Driver`, 与 README 示例展示的 DataFrame 接口不是同一套代码路径, 脚本的命令行默认值与函数默认值也不一致. 代码自身还有两个文档未提的问题: `DataFrame.is_computed` 拿未优化的节点查任务表, 总返回 `False`; 3FS 快速删除只认 `/hf3fs` 前缀. 这些问题说明开源版本是内部系统的一个快照, 维护投入有限, 生产使用前需要自己补测试和修补.

### 5.3 从一条 join 流水线推导完整语义

考虑两张关系: 样本表 $D(\text{doc\_id},\text{text},\text{lang})$ 和质量表 $Q(\text{doc\_id},\text{score})$. 目标是只保留中文且分数超过阈值的文档. 若输入最初按文件任意切分, 正确计划可以先分别做局部过滤和投影, 再按 `doc_id` 对两边使用相同哈希函数重分区, 最后在各分区执行 join:

$$
\begin{aligned}
D'&=\pi_{\text{doc\_id},\text{text}}\left(\sigma_{\text{lang}='zh'}(D)\right),\\
Q'&=\pi_{\text{doc\_id},\text{score}}\left(\sigma_{\text{score}>\tau}(Q)\right),\\
R_i&=D'_i\bowtie_{\text{doc\_id}}Q'_i,\\
R&=\biguplus_{i=0}^{n-1}R_i.
\end{aligned}
$$

前两步与并集可交换, 放到 shuffle 前能减少传输列数与行数. 重分区建立同键共置不变量. 最后的 join 才具备分区独立性. 如果先对两张任意分区的表直接执行 `partial_sql` join, 每个任务只看见各自文件集合, 分处不同任务的匹配项永远不会相遇. 结果可能缺少大量行, 并且没有异常. 这条例子揭示了 smallpond 的核心阅读方法: 每见到一个 `partial_` 算子, 都要问它所需的行是否已经被放进同一分区.

再看键的唯一性. 若质量表对每个 `doc_id` 有多条评分记录, join 会复制文档. 这可能是期望的一对多关系, 也可能是上游重复. 分区正确只保证可能匹配的行相遇, 不保证基数符合业务约束. 可以在 join 前按 `doc_id` 聚合并检查计数, 或在输出上验证 $|R|$ 与过滤后主表规模的关系. 同理, `NULL` join 键、字符串规范化、整数宽度和 Unicode 形式都会改变匹配语义. 关系代数给出算子组合, 数据契约决定键到底代表谁.

若要做全局去重, 也可沿同一逻辑推导. 先计算稳定指纹 $u=H(\operatorname{normalize}(text))$, 按 $u$ 哈希重分区, 再在分区内按 $u$ 分组挑选代表行. 规范化函数必须固定, 哈希碰撞策略必须明确, 代表行若依赖「第一条」则要提供稳定排序键. 仅在原始文件分区内去重只能消除局部重复; 随后合并文件仍可能含跨分区重复. 这类静默语义差异正是 smallpond 用简洁框架换给作业作者的责任.

### 5.4 可验证的正确性契约

大规模流水线难以逐行人工检查, 但可以为每个阶段写出能聚合验证的不变量. 过滤阶段应满足输出行数不大于输入, 输出每行都满足谓词; 投影阶段应保持行数, 除非表达式显式展开或去重; 哈希分区后, 每条记录所在分区应等于分区函数结果; 等值 join 可以检查外键覆盖率、主键唯一性和预期基数区间; 排序阶段可检查每个分区内部单调, 再检查相邻范围的最大值不超过下一范围最小值.

这些检查本身也要可分布式合并. 行数用求和; 最小值和最大值分别用 `min`、`max`; 布尔约束可统计违反数; 哈希一致性可在每个分区计算 `count_if(h(key) != partition_id)`; 文件完整性可记录行数、模式指纹和内容摘要. 若每个任务输出一份小型 manifest, 阶段级验证只需合并 manifest, 不必重新扫描全部宽列. manifest 还可成为发布协议的一部分, 让下游先确认预期分区全部存在.

抽样检查只能发现高频错误. 若错误比例为 $p$, 独立抽取 $m$ 行仍未发现错误的概率为 $(1-p)^m$. 当错误只出现在一个极小分区、罕见 Unicode 或单个超长文档时, 随机样本很容易漏掉. 分区不变量和模式约束适合做全量轻量检查, 内容质量再用分层抽样: 每个分区、语言、来源和长度区间都取样. 这比只从全局均匀抽几千行更能覆盖长尾.

正确性也包括失败后重跑的一致性. 可以保存输入文件清单及每个文件的大小、修改时间或内容摘要, 将其与逻辑计划摘要、代码版本和关键参数一起形成作业指纹. 完成缓存只在指纹相同时复用. smallpond 当前完成记录更接近运行目录内的任务缓存, 不等同于完整的内容寻址构建系统. 若调用方复用 `SP_JOBID` 却改变了输入或函数, 旧完成文件可能被误认为有效, 因此作业标识的管理直接影响语义.

### 5.5 失败类型与恢复边界

执行节点进程退出是最容易处理的失败: 输入和已完成输出都在共享存储, 调度器把未完成任务交给另一节点即可. 临时网络中断更复杂, 原执行器可能仍在运行, 新副本与旧副本形成竞争. 共享存储短暂不可用会让很多任务同时失败, 盲目重试可能放大压力. 存储返回成功但数据损坏时, 完成标记无法单独发现问题, 需要 parquet 校验或内容摘要. 调度器进程失败则取决于队列、计划和完成记录是否足以重建内存状态.

用户函数异常属于确定性失败时, 在相同输入上重试五次没有收益. 解析某条坏记录、列类型不兼容或 SQL 绑定错误通常会稳定复现. 资源不足则可能通过增大内存或减少并行恢复; 瞬时网络和节点故障适合原资源重试; 数据损坏应隔离输入并停止传播. 一个统一重试次数无法表达这些差异. smallpond 内置调度器会针对 OOM 放宽内存, 说明它已经区分部分失败类型, 但用户仍需从日志和任务输入定位确定性坏数据.

推测执行要求任务时长分布可比较. 同一逻辑节点的任务处理近似同质数据时, 中位数和高分位能够识别异常慢副本. 若分区大小天然相差百倍, 大分区超过阈值并不意味着节点异常, 复制只会多消耗一份资源和 IO. 更准确的进度信号应按已处理字节、行数或算子阶段归一化, 但通用 Python 任务难以提供统一进度. smallpond 选择按完成时长启发式判断, 简洁但依赖分区足够均匀.

任务成功也不代表业务数据已经安全发布. 若最终 sink 通过硬链接或复制把结果放入用户目录, 消费者可能在所有分区完成前开始扫描目录. 对只支持目录 glob 的下游, 新文件逐步出现会产生时间相关结果. 一种常见契约是写入版本目录, 待全部校验后创建 `_SUCCESS` 或更新 manifest, 消费者只读取已发布版本. smallpond 的任务级完成文件解决调度依赖, 数据产品级发布仍需作业自己定义.

### 5.6 与 DuckDB、Ray、3FS 的职责边界

DuckDB 负责单任务内的 SQL 语义、优化和向量化执行. 它知道表达式、列类型、局部统计和连接算子, 却不知道整个 smallpond DAG 中另一个分区节点为何存在. Ray 负责把 Python 任务依赖映射到集群资源, 处理远程函数的调度与部分故障重试, 却看不见 parquet 内部的键分布. 3FS 负责让各节点以统一命名空间访问高带宽持久文件, 却不理解哪个文件集合构成完整数据集. smallpond 的逻辑层把三者组合起来, 但不会让任何一层自动获得另外两层的语义.

这种职责切割解释了许多表面矛盾. DuckDB 能自动选择单机 join 顺序, smallpond 仍要求用户手动决定跨机 shuffle; Ray 能按 ObjectRef 依赖调度, smallpond 仍把大数据放在 3FS; 3FS 能保存中间文件, smallpond 仍需要 completed task 标记来声明哪组文件有效. 各依赖解决的是不同尺度的问题. 把它们简单描述成「DuckDB 加 Ray 加 3FS」会漏掉 smallpond 最关键的工作: 把关系运算切成任务, 明确任务间物化边界, 并把文件路径重新包装为可调度依赖.

替换任一层都会改变约束. 将 3FS 换成普通对象存储时, POSIX rename、硬链接、目录列举和大量小文件的成本模型不同, 任务提交协议需要重审; 将 Ray 换成 Kubernetes Job 时, 依赖发现、资源调度和重试状态需要另建; 将 DuckDB 换成其他引擎时, SQL 方言、parquet 推下、内存控制和写文件行为都会变化. smallpond 的抽象边界使替换成为可能, 但接口兼容不代表性能与故障语义等价.

也可以反向理解它为何没有常驻 shuffle 服务. shuffle 服务通常管理 map 输出、分区索引、拉取和生命周期, 计算节点本地盘能减少共享存储流量. smallpond 把这些职责折叠进 parquet 文件与共享命名空间: 文件名和目录表达分区, 3FS 承担持久性与远程读取, 作业清理删除中间目录. 组件更少, 每字节要经过共享存储写入和读取, 适合存储网络极强且运维希望保持无状态计算节点的环境.

### 5.7 数据生命周期与增量计算

一次性批处理的生命周期是输入快照、若干中间版本、最终输出和清理. 若输入目录在运行期间继续写入, 不同任务列举文件的时间不同, 可能看到不同快照. 最简单的办法是先生成不可变输入清单, 每个任务只消费清单中的路径. 文件内容也应避免原地修改, 以新路径发布新版本. 这样任务重试仍读取同一字节集合, 完成缓存才有稳定含义.

增量计算需要知道新输入对旧输出的影响. 对逐行映射和过滤, 新文件可独立处理后与旧结果并集. 对按键聚合, 若聚合状态可合并, 可以合并旧状态和新增状态; 对去重、join 和全局排序, 新记录可能改变已有键的代表行、匹配结果或排序位置. smallpond 的 DAG 与文件物化可作为增量构建的基础, 当前接口主要面向一次性静态计划, 没有自动维护输入版本、依赖失效和局部重算范围.

中间数据全落共享存储也使保留策略成为性能与可追溯性的权衡. 立即删除能释放容量, 故障分析和精确复现会失去现场; 长期保留所有阶段则可能数倍放大原始数据占用. 可以按阶段价值分层: 可廉价重算的过滤中间物短暂保留, 高成本 shuffle 结果保留到下游验证完成, 最终发布版本记录长期 manifest 和输入指纹. 这种生命周期策略在框架外实现, 却直接决定恢复时间和存储成本.

小文件整理也是生命周期的一部分. shuffle 阶段为并行写入产生很多文件, 下游长期反复扫描时, 可以在发布前做 compaction, 把同分区小文件合并为适中大小并保持 row group 统计. compaction 是一次额外全量读写, 只跑一次的临时阶段可能得不偿失; 被多个训练任务重复读取的数据集更容易收回这笔成本. 判断依据应是预期复用次数、扫描选择性和元数据压力, 而非把文件数越少视为永远更好.

### 5.8 性能模型: 什么时候分布式反而更慢

对一阶段作业, 可把总时间近似分为固定开销、扫描、计算、写入和尾部等待:

$$
T(n)\approx T_{\text{plan}}+nT_{\text{task}}+\frac{B_r}{\beta_r}+\frac{W}{\rho}+\frac{B_w}{\beta_w}+T_{\text{tail}}.
$$

$n$ 是任务数, $T_{\text{task}}$ 是每个任务的调度、进程与文件固定开销, $B_r$、$B_w$ 是读写字节数, $\beta_r$、$\beta_w$ 是共享存储有效带宽, $W$ 是计算工作量, $\rho$ 是集群有效计算吞吐. 增大 $n$ 能提高并行度并缩小单任务失败重算范围, 同时线性增加固定开销和文件数量. 当扫描或计算项已经被带宽饱和, 继续切分只会增加 $nT_{\text{task}}$.

单机 DuckDB 少了分布式调度和阶段间共享写读, 数据放得进一台高配机器且算子能充分多线程时, 它很可能更快. smallpond 的收益出现在单机容量不足、任务天然可分、共享存储足够快的交集. 这也是为什么用一个模糊数据量阈值判断是否采用 smallpond 不够可靠. 同样 20 TB 数据, 简单过滤可能受 IO 限制, 复杂 UDF 可能受 CPU 限制, 高基数 shuffle 可能受文件和网络限制, join 倾斜还会受最大键限制.

中间落盘对多阶段作业的放大可写为读写系数. 原始输入为 $B_0$, 第 $j$ 阶段输出相对输入比例为 $r_j$, 若每阶段都读一次写一次, 总 IO 约为:

$$
B_{\text{IO}}=B_0+2\sum_{j=1}^{k-1}B_j+B_k,
\qquad B_j=B_0\prod_{t=1}^{j}r_t.
$$

早期过滤让 $r_1$ 很小, 后续 IO 会成比例下降; 早期展开或 join 让 $r_1$ 大于 $1$, 后续物化成本被放大. 这给出一个直接的计划原则: 能保证语义的选择和投影尽量靠前, 会扩张数据的算子尽量在必要字段和记录已经缩减后执行. 这不是特定于 smallpond 的规则, 但全落盘架构让代价更明显.

### 5.9 从训练数据处理看它的价值

大模型语料处理常见步骤包括格式统一、语言与质量打分、规则过滤、近似去重、来源配比和全局打乱. 前几步大多是逐文档函数, 适合任意文件分区; 精确去重需要相同指纹共置; 近似去重可能先生成局部签名, 再按桶重分区比较候选; 来源配比需要先统计各来源规模, 再决定采样率; 全局打乱需要随机分区和分区内随机顺序. 一条看似线性的流水线, 实际在局部变换和全局协调之间多次切换.

smallpond 的价值在于让每次切换显式可见. `partial_sql` 表示当前计算被限制在分区内, `repartition` 表示重新建立共置关系, parquet 物化让阶段输出可检查、复用和恢复. 对训练团队而言, 这种透明度可能比自动优化更重要: 数据问题常常需要回溯某一阶段的样本, 文件边界提供了稳定观察点. 代价是作业作者必须理解统计量和分区键, 否则透明的错误同样会被稳定地物化下来.

训练数据对确定性有特殊需求. 模型训练本身包含随机性, 数据版本再漂移会让实验差异更难归因. 每次语料生成应记录输入版本、代码提交、过滤阈值、随机种子、分区数、输出 manifest 和关键统计. 若浮点打分或多线程聚合允许微小差异, 阈值附近样本可能跨过过滤边界, 最终行集合发生变化. 可以保存原始分数并用明确精度比较, 或对临界区间做稳定复核. 框架只提供计算与文件交换, 实验可追溯性需要在其上建立数据版本协议.

### 5.10 从算子交换律设计阶段顺序

阶段顺序可以用关系代数等价式判断, 而非依靠经验随意调整. 过滤与投影常可交换, 前提是过滤所需列没有被投影删除. 过滤可以下推到内连接一侧, 前提是谓词只引用该侧列; 对外连接, 下推可能改变保留空值行的语义. 聚合前过滤原始行与聚合后过滤分组结果分别对应 `where` 和 `having`, 两者条件作用对象不同. 只有先证明等价, 才能用提前缩减数据量获得性能收益.

join 也有结合律与交换律, 但中间结果大小可能相差几个数量级. 三表 $A\bowtie B\bowtie C$ 在逻辑上可用多种次序, 若 $A$ 与 $B$ 的选择性很高, 先连接它们能缩小后续 shuffle; 若连接产生一对多扩张, 先做会放大后续 IO. DuckDB 会在单任务内部选择连接顺序, 跨 smallpond 节点已经物化的阶段不能被重新排列. 用户决定在哪一步 repartition, 实际也决定了全局 join 树的骨架.

投影下推需要保留分区键和后续计算列. 早期删除宽文本列可以大幅降低 shuffle, 但如果下游最终仍需原文, 一种办法是只携带稳定 `doc_id` 做聚合和筛选, 最后再与原始文本表按键连接取回正文. 这种「窄表决策、宽表回填」减少中间 IO, 会增加一次 join. 是否划算取决于保留比例、正文宽度和键索引方式. 当过滤后只剩少量样本时, 回填通常明显更省.

随机打乱与过滤的次序也影响统计语义. 先随机抽样再按质量过滤, 输出规模随机且可能改变来源比例; 先过滤再按目标比例抽样, 更容易精确控制最终分布. 若采样概率依赖来源或分数, 应先计算这些字段. 把随机算子看成普通逐行 `map` 会遗漏全局配额与可复现种子的约束. smallpond 能执行任一顺序, 数据目标决定哪条关系变换才正确.

### 5.11 观察指标要对应执行层次

排查慢作业时, 只看全局吞吐很难定位原因. 逻辑节点层应记录输入输出行数、字节数、分区数和模式; 任务层应记录排队、读取、计算、写入、提交各阶段耗时, 以及 CPU 峰值、内存峰值和重试原因; 文件层应记录文件数、平均与最大文件大小、row group 数量; 集群层再看 3FS 吞吐、元数据请求、网络与执行器利用率. 四层指标对齐后, 才能判断瓶颈来自数据变换、单任务算子、文件布局还是共享资源.

例如 CPU 利用率低有多种含义. 任务可能在等 3FS 读取, 可能因 parquet 文件只有少量 row group 而无法多线程, 也可能只有几个大分区导致集群并行度不足. 存储吞吐低也未必代表存储空闲: 数百万小文件可能受打开和元数据延迟限制, 每秒字节数上不去. p99 任务很慢可能来自数据倾斜、坏节点、Python 回调的外部服务或内存回收. 将这些情况都归为「加并发」会让诊断偏离真正瓶颈.

正确性指标也应与性能指标并列. 每个阶段同时记录违反约束的行数、空值率、键基数、热门键占比、join 匹配率和来源分布. 数据量骤减可能是高效过滤, 也可能是分区 join 漏配; 输出膨胀可能是预期展开, 也可能是主键重复. 如果运行面板只展示任务成功与字节吞吐, smallpond 最危险的静默语义错误不会留下显眼信号.

基线应按逻辑节点类型建立. 过滤任务的输入字节与耗时近似线性, join 还取决于构建侧和输出基数, Python UDF 取决于文本长度或外部调用. 把所有任务混在一个时长分布里计算异常值没有意义. 内置调度器的推测执行已经按同一逻辑节点收集完成时长, 这是合理起点; 若进一步加入输入字节与行数, 可区分数据更大和机器更慢.

### 5.12 安全重算所需的最小闭包

一条数据结果能否重算, 取决于能否还原产生它的完整闭包. 最小闭包包含输入文件清单及其内容身份、逻辑 DAG、每个节点参数、用户函数代码、运行依赖版本、随机种子和会改变语义的环境设置. 只保存最终 SQL 不够, 因为输入快照可能变化; 只保存容器镜像也不够, 因为阈值与分区配置可能来自命令行. 对 Python 回调, 还要避免未记录的全局变量和远程服务状态.

逻辑计划序列化是重算闭包的一部分. low-level Driver 会把运行时上下文和计划 pickle 到配置目录, 使执行器能够读取同一静态图. pickle 能恢复 Python 对象, 并不自动赋予长期兼容性或可审计性: 类定义路径、依赖版本和闭包对象改变后, 旧计划可能无法加载; pickle 也不适合接收不可信内容. 长期数据版本更适合另存一份稳定、可读的计划摘要, 记录节点类型、依赖、表达式、资源和版本指纹.

重算还要区分结果复现与过程复现. 关系内容相同而任务分配、文件数量不同, 对大多数训练输入已经足够; 若研究的是调度性能或 GraySort 成绩, 执行器数量、NUMA 绑定、资源提升和存储负载也属于实验条件. 对性能结论, 只保存数据与代码无法复现相同时间. 对内容结论, 强求每个任务落在相同节点反倒没有必要.

最小闭包也限定了外部 UDF 的使用方式. 若语言识别或质量打分通过在线服务完成, 服务模型升级会让相同文档得到不同结果. 可以固定服务版本并保存请求响应摘要, 或先把评分物化为带模型版本的不可变表, 后续 smallpond 流水线只消费这张表. 这样外部非确定性被收束到一个明确阶段, 重试过滤和混合任务时不会再次调用变化中的服务.

## 6. 一手资料与阅读结论

### 6.1 源码与官方文档怎样互相校验

smallpond 的直接事实应以 [DeepSeek 官方仓库](https://github.com/deepseek-ai/smallpond)为主. README 给出系统定位、DataFrame 示例和 GraySort 结果; `smallpond/logical` 目录说明节点、优化和计划展开; `smallpond/execution` 目录说明任务、调度器、执行器与文件队列; `benchmarks/gray_sort_benchmark.py` 给出 110.5 TiB 案例的真实计划结构. 文档中的高层描述若与代码参数不一致, 运行语义由对应提交的代码决定. 引用 `main` 链接便于阅读最新快照, 严格复现还应记录提交 `52ecc5e` 或具体归档摘要.

依赖机制以各项目官方文档校验. DuckDB 的内部结构、向量格式、Parquet 读写与非确定性说明, 分别支撑单任务优化、2048 行向量、pushdown 与多线程结果边界的解释. Ray 的任务文档支撑 ObjectRef 依赖、资源声明、任务调度和默认重试行为. 3FS 的存储架构与吞吐应回到 [DeepSeek 3FS 官方仓库](https://github.com/deepseek-ai/3FS), smallpond 代码则说明它实际通过哪种文件接口使用 3FS. 社区复现适合补充部署经验, 不能替代这些机制来源.

把源码与依赖文档合在一起, 可以得到一条简洁而准确的结论: smallpond 是一个显式分区、阶段物化的批处理编排层. 它用逻辑 DAG 保存惰性变换, 将可融合的局部 SQL 交给 DuckDB, 将任务依赖和资源调度交给 Ray 或内置调度器, 将大数据交换和恢复点交给共享文件系统. 其规模能力来自分区和存储带宽, 语义正确性来自调用者维护的共置、模式、幂等和发布不变量.

### 6.2 评价这套设计时该看什么

第一项是作业是否能被少量清晰阶段表达. 若主要算子是逐行变换、按键重分区和分区内 SQL, smallpond 的抽象与问题贴合; 若需要自动优化复杂多表查询、连续流状态或细粒度迭代通信, 它提供的层次太低. 第二项是共享存储能否同时承担数据面与控制面压力. 峰值 GB/s 只描述大块传输, 数百万文件的创建、列举、删除和失败恢复同样关键.

第三项是团队能否维护分区正确性. 显式分区让性能和语义都容易观察, 也失去了成熟分布式 SQL 优化器的保护. 每个 shuffle 应写下分区函数、键规范化、分区数和下游所依赖的不变量; 每个局部聚合应说明状态怎样合并; 每个 sink 应说明重跑与发布语义. 这些内容若只能靠作者记忆, 流水线扩展后很容易出现静默错误.

第四项是失败成本. 文件物化让单任务失败只需重算一个分区, 这是 PB 级长作业的重要优势. 物化也使每个阶段承担全量 IO、容量和清理成本. 分区过大时恢复粒度粗, 分区过小时调度与元数据占主导. 最合适的分区粒度由数据分布、单任务内存、计算时长、文件大小和集群规模共同决定, 没有脱离工作负载的固定答案.

最后看可复现性要求. 只关心最终统计趋势的离线分析, 关系内容近似稳定通常足够; 训练语料版本、评测集构建和审计数据更需要稳定输入清单、确定性随机源、manifest 与代码版本. smallpond 不会自动提供完整的数据版本系统, 但不可变 parquet 和显式 DAG 给出了建立这些约束的合适边界. 它最有启发性的地方也在这里: 当共享存储足够强时, 用文件换取无状态计算、清晰恢复点和可观察阶段, 可以把分布式数据处理压缩成一组并不神秘的关系变换与调度规则.

### 6.3 一条可迁移的理解框架

阅读任何 smallpond 作业时, 可以先把 Python 链还原成关系图. 节点旁写出输入模式与输出模式, 边上写出分区函数, 物化点写出文件集合. 然后逐个验证局部算子是否与分区并集可交换, 全局算子是否已经获得所需共置关系. 这一步回答结果是否正确, 暂时不讨论跑得快不快. 如果同键数据没有共置、顺序算子没有范围关系、聚合状态不能合并, 增加机器只会更快地产生错误结果.

第二步把关系图变成资源图. 每个节点标出扫描字节、解压后宽度、状态大小、输出放大率和单任务资源, 每条物化边标出总写入、文件数与预期复用次数. 由最大分区判断内存安全, 由有效任务数判断并行度, 由总读写判断共享存储压力, 由最大键和 p99 任务判断尾部. 这一步常会反过来推动等价变换, 例如提前过滤、窄表 shuffle、局部聚合或最后回填宽列.

第三步画失败边界. 标出输入快照何时固定, 哪些函数可安全重试, 每次尝试写到哪里, 完成记录何时发布, sink 怎样防止半成品被读取. 节点失败、执行器失联、调度器重启和存储短暂不可用分别沿哪条路径恢复, 都应能从文件与标记状态推出来. 若恢复依赖某个进程内未持久化对象, 无状态计算的假设便在这里破裂.

第四步定义验收统计. 行数与字节数检查数据规模, schema 指纹检查结构, 键基数和热门键检查分区风险, join 匹配率与约束违反数检查语义, manifest 与摘要检查发布完整性. 对随机或浮点算子, 还要声明比较使用精确相等、集合相等还是数值容差. 这套验收使「任务全绿」与「数据正确」成为两个分别可检查的命题.

完成这四步后, DuckDB、Ray 和 3FS 的位置会很清楚. DuckDB 优化分区内表达式, Ray 或内置调度器执行任务图, 3FS 保存跨任务数据和恢复点, smallpond 负责把用户写出的分区关系翻译成这三层可以协作的形式. 它没有隐藏分布式系统的基本代价, 只是选择用共享文件把通信、缓存和检查点合为同一个对象. 这套选择在 DeepSeek 的存储条件下很有力量, 换到其他环境时也应沿同样四步重新计算, 而不是只复制接口写法.

这套框架也能用于判断改动是否安全: 关系图确认语义没有漂移, 资源图估计代价是否转移, 失败边界检查重试会不会重复副作用, 验收统计负责捕捉静默的数据变化. 四项都能回答, 一次优化才算具备可验证的前提; 只证明运行更快, 还不足以证明新计划可以替换旧计划.

# 开源仓库

**论文描述机制和实验, 仓库暴露实现必须满足的接口.** 一个 MoE 层在论文中可以写成路由与专家计算, 到代码中还要处理 token 分发, 节点拓扑, 数据类型, 缓冲区和失败条件; MLA 在公式中减少 KV cache, 到 kernel 中还要匹配 GPU 架构, batch 形状与分页缓存. 本章把仓库视作技术设计的一部分, 关注组件在整条训练和推理路径中的位置.

当前收录的五个仓库覆盖存储, 数据处理, 专家通信, 矩阵乘法和注意力 kernel. **每个仓库对应一组不同的性能指标.** 3FS 关心聚合带宽和元数据路径, smallpond 关心数据任务调度, DeepEP 关心 all-to-all 通信, DeepGEMM 关心 FP8 GEMM, FlashMLA 关心 MLA 解码与预填充. 阅读时先确定「输入输出」与「部署边界」, 再看内部优化.

## 1. 存储与数据准备

### 1.1. 3FS 提供共享数据底座

[3FS](./3fs/3fs-analysis.md) 是面向 AI 工作负载的分布式文件系统. 大规模训练既要顺序读取数据分片, 也要写 checkpoint 和中间结果; 推理与数据处理还会产生不同大小和并发模式的请求. 3FS 将存储设备, 网络传输和文件语义组织成共享服务, 目标是在大量客户端下保持高聚合吞吐.

文件系统性能不能只看单客户端峰值. 元数据操作, 小文件, 并发读写, 故障恢复与数据重建都会影响生产负载. 阅读 3FS 时应先区分控制路径和数据路径, 再观察客户端怎样定位数据, 数据怎样跨网络传输, 副本或恢复策略怎样影响可用容量. 这些条件决定论文或基准数字能否迁移到另一套集群.

### 1.2. smallpond 把计算调度靠近数据

[smallpond](./smallpond/smallpond-analysis.md) 面向大规模数据处理, 将任务拆分, 调度与 3FS 数据访问连接起来. 预训练数据清洗, 去重, 转换和统计通常需要扫描海量文件; 如果分片不均或频繁搬运数据, CPU 与网络会先于 GPU 训练成为瓶颈.

smallpond 的阅读重点是任务图和分区语义. 一个操作怎样切成并行任务, 中间结果怎样保存, 失败任务怎样重跑, 这些机制决定数据流水线的可重复性和资源利用率. 它与 3FS 的关系是计算层与存储层的配合: 文件系统提供共享数据面, 调度框架决定工作在何处执行以及读取哪些分片.

## 2. MoE 通信路径

### 2.1. DeepEP 执行 token 分发

[DeepEP](./deepep/deepep-analysis.md) 为 MoE 提供高吞吐, 低延迟的 all-to-all 通信. 路由器为 token 选择专家以后, token 表示必须发送到专家所在 GPU, 计算完成后再返回原顺序. 通信量, 消息大小和节点边界随 batch 和路由结果变化, 通用集合通信不一定适合这些稀疏负载.

DeepEP 区分训练与推理解码等工作模式, 因为大 batch 的吞吐目标和小 batch 的低延迟目标不同. 缓冲区布局, NVLink 与 RDMA 路径, 发送接收重叠都会影响结果. 阅读基准时需要确认 GPU 型号, 节点数, token 数量, top-k 与数据类型, 这些参数直接决定消息粒度.

### 2.2. 算法均衡与通信实现相互约束

第二章的无辅助损失负载均衡减少专家拥塞, DeepEP 则高效搬运路由后的 token. 如果路由严重偏斜, 少数专家会形成计算和接收热点, 通信库无法完全消除等待; 如果为了均衡强行改变路由, 又可能损害模型目标. 两层必须通过明确的容量和统计接口配合.

**MoE 的理论激活 FLOPs 不能直接等同于端到端速度.** token 打包, 跨节点传输, 专家计算和结果合并都位于关键路径. 阅读 DeepSeekMoE 或 V3 后进入 DeepEP, 可以把「激活少量专家」还原成完整的分布式执行过程.

## 3. 低精度矩阵计算

### 3.1. DeepGEMM 服务 FP8 训练与推理

[DeepGEMM](./deepgemm/deepgemm-analysis.md) 提供针对 NVIDIA Hopper GPU 的 FP8 GEMM. V3 使用低精度提高训练吞吐, 但输入缩放, 分块方式, 累加精度和输出格式都需要与模型数值方案一致. kernel 必须在保持误差可控的同时利用张量核和显存层级.

仓库中的接口形状反映了模型工作负载. 常规 dense GEMM, MoE grouped GEMM 与不同量化粒度需要不同调度. grouped GEMM 要处理各专家 token 数不相等的情况, 负载分布会影响块调度和占用率. 因此单个规则矩阵上的峰值不能代表 MoE 训练的实际表现.

### 3.2. 从数据格式追踪数值边界

阅读 DeepGEMM 时可沿数据格式追踪: 输入以什么精度存储, 缩放因子按张量还是按块生成, 乘法在哪里执行, 累加使用什么精度, 输出何时转换. 每一步都关系到误差和吞吐. 模型报告中的 FP8 配方给出数值策略, kernel 仓库给出硬件执行方式.

性能条件同样需要保留. GPU 架构, CUDA 版本, 矩阵尺寸和对齐方式都会改变结果. DeepGEMM 是为明确硬件与工作负载定制的实现, 其设计经验可以迁移, 具体数字不能脱离环境复制.

## 4. MLA 注意力执行

### 4.1. FlashMLA 将压缩结构落实为 kernel

[FlashMLA](./flashmla/flashmla-analysis.md) 为 MLA 提供高效计算. MLA 将键值状态压缩为潜变量, 减少 cache 容量, 但解码时仍要完成查询与压缩表示之间的计算. kernel 需要组织潜变量, RoPE 相关分量, 分页 cache 和不同长度序列, 才能把结构优势转成延迟与吞吐收益.

预填充和逐 token 解码的形状差异很大. 预填充有较长查询序列, 更容易形成大规模并行; 解码通常每个请求只有少量新 token, 更受内存访问, 调度和 batch 组织影响. FlashMLA 的不同路径应分别评估, 不能用一个吞吐数字概括.

### 4.2. 模型压缩与系统缓存共同决定容量

V2 的 MLA 首先从模型结构上减少每个 token 保存的状态, FlashMLA 优化每次读取和计算, DualPath 则在更大尺度上安排 KV cache 的存储位置. **三者依次作用于「表示」「kernel」「服务系统」.** 任一层单独优化, 都可能受下一层瓶颈限制.

V2 技术报告定义压缩后保存的张量, FlashMLA 实现消费这些张量的 kernel, DualPath 再处理大量请求状态的跨设备管理. 三份材料连起来, 正好覆盖从模型公式到生产数据路径的三个层次.

## 5. 组合成完整执行栈

### 5.1. 训练数据到参数更新

训练开始前, 3FS 保存原始数据和处理结果, smallpond 执行清洗与转换. 训练节点读取分片以后, DeepGEMM 执行主要矩阵计算, DeepEP 在 MoE 层分发 token. checkpoint 再写回存储系统. 这些组件的吞吐必须大致匹配, 否则最快的一层会等待最慢的一层.

排查训练性能时可按这条路径逐段测量: 数据读取是否让 GPU 等待, dense 与 grouped GEMM 是否达到目标占用率, all-to-all 是否与计算重叠, checkpoint 是否造成周期性停顿. 仓库解析提供接口和关键实现, 第三章的系统论文提供全局拓扑, 两者结合才能定位端到端瓶颈.

### 5.2. 长上下文推理与 agent 执行

推理阶段, 权重加载和输入数据仍依赖存储, FlashMLA 负责注意力主路径, MoE 层由 DeepEP 通信. 当上下文持续增长时, KV cache 进入 DualPath 一类分离系统. agent 强化学习还要把模型输出交给 DSec 沙箱执行, 结果作为奖励返回训练器.

五个仓库在系统中的位置不同: 3FS 提供数据底座, DeepEP、DeepGEMM 与 FlashMLA 进入模型关键路径, smallpond 负责数据处理. 推理部署还涉及 V2 的 MLA 与 DualPath; 训练侧则可结合 V3 Insights, 将存储、数据、通信和计算放回同一条资源链中考察.

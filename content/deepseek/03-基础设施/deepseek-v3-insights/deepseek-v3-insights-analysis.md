# DeepSeek-V3 硬件思考: 从每 token 的字节数推到芯片与网络建议

材料是论文 *Insights into DeepSeek-V3: Scaling Challenges and Reflections on Hardware for AI Architectures* (arXiv 2505.09343, 2025-05, ISCA 2025 工业论文, 15 页), 作者为 DeepSeek-AI 的 Chenggang Zhao, Wenfeng Liang 等 15 人. 论文没有新模型, 讲的是 [DeepSeek-V3](../../01-模型技术报告/deepseek-v3/deepseek-v3-analysis.md) 在 2048 张 H800 上训练与部署时碰到的硬件约束, 以及模型和集群为此做的协同设计. 文中提到的代码都已开源: EP 通信库 [DeepEP](../../04-开源仓库/deepep/deepep-analysis.md), FP8 GEMM 库 [DeepGEMM](../../04-开源仓库/deepgemm/deepgemm-analysis.md), MLA decode kernel [FlashMLA](../../04-开源仓库/flashmla/flashmla-analysis.md), 存储网络上的文件系统 [3FS](../../04-开源仓库/3fs/3fs-analysis.md). 逐段对照见 [对照译稿](deepseek-v3-insights-bi.md).

论文把硬件建议落在一组可复核的数字上: MLA 每 token 的 KV cache 是 70.272 KB, 一次 EP 往返是 120.96 μs, H800 的 Tensor Core 累加只保留 13 位尾数, NVLink 对 IB 是 4:1, 训练时 132 个 SM 里有 20 个在搬数据. 这些数字的成立条件来自 V3 技术报告公开的模型参数: 61 层, 隐藏维 7168, 128 个注意力头, MLA 潜变量 512 维加 64 维 RoPE, 每层 1 个共享专家和 256 个路由专家, 每个专家中间维 2048, 每 token 激活 8 个路由专家. 硬件或模型配置变化后, 对应的字节数、通信时间与瓶颈判断也要重新计算.

## 1. 内存与算力: 每 token 要搬多少字节, 算多少 FLOPs

### 1.1. KV cache 表: 576 个数乘 61 层

表 1 的三个数都能从模型配置直接乘出来, 单位里的 KB 取 1000 字节. V3 的 MLA 每层每 token 只缓存 512 维的压缩潜变量和 64 维的解耦 RoPE key, 共 576 个数, BF16 存放是 1152 字节, 乘 61 层得 70,272 字节. Qwen2.5-72B 是 GQA, 8 个 KV 头, 头维 128, 80 层, K 与 V 各一份: $2\times8\times128\times80\times2=327{,}680$ 字节. LLaMA-3.1-405B 同样 8 个 KV 头, 126 层, 得 516,096 字节. 表里的倍数 4.66 和 7.28 就是这三个数之比.

| 模型 | 注意力 | 每层每 token 缓存的数 | 层数 | 每 token 字节 (BF16) | 128K 上下文合计 |
| --- | --- | --- | --- | --- | --- |
| DeepSeek-V3 | MLA | 576 | 61 | 70,272 | 9.2 GB |
| Qwen2.5-72B | GQA, 8 KV 头 | 2048 | 80 | 327,680 | 42.9 GB |
| LLaMA-3.1-405B | GQA, 8 KV 头 | 2048 | 126 | 516,096 | 67.6 GB |
| V3 结构改用 MHA | 128 头 | 32,768 | 61 | 3,997,696 | 524 GB |

末行是表 1 没有的对照: 如果 V3 保持 128 个头, 每头 128 维, 却用标准 MHA 缓存 K 和 V, 每 token 要约 4.0 MB, 是 MLA 的 56.9 倍. 这才是 MLA 相对「同等头数」的压缩比. 表 1 拿两个 GQA 模型比, 4.66 倍里混着层数的差别 (80 层对 61 层), 按每层算, Qwen2.5-72B 是 V3 的 $2048/576\approx3.56$ 倍. 另一个口径差在精度上: 论文按 BF16 算, 而 FlashMLA 的 FP8 KV 布局每层每 token 是 656 字节 (512 维 FP8 潜变量, 4 个 FP32 缩放因子, 64 维 BF16 的 RoPE 部分), 61 层合计约 40 KB. 实际部署的 KV 体积比表 1 再小约 43%. KV 容量的一般算法见 [KV 缓存: 容量计算, 调度与压缩边界](../../../llm-guide/6-训练与推理优化/6.4-KV缓存与内存优化/6.4-KV缓存与内存优化.md).

### 1.2. decode 的访存瓶颈: MLA 改变的是算术强度

2.1.2 节说 KV cache 让 decode 的计算从 GEMM 变成 GEMV, 计算访存比太低, 带宽成了瓶颈. 这句话对 GQA 成立, 对 MLA 只成立一半, 论文没有展开这一层. 拿每个缓存 token 在一层里引发的 FLOPs 除以它的字节数, 就是注意力部分的算术强度. Qwen2.5-72B 有 64 个 query 头共享 8 个 KV 头, 一个缓存 token 的 K 和 V 各被 8 个 query 头用一次, 打分与加权各 2 FLOPs 每元素, 合计 $64\times128\times4=32{,}768$ FLOPs, 对应 4096 字节, 强度是 8 FLOP/字节. LLaMA-3.1-405B 有 128 个 query 头, 强度是 16.

MLA 在推理时用矩阵吸收, 把 128 个头的 query 都投到 576 维潜变量空间里直接和缓存打分, 再在 512 维上加权. 一个缓存 token 每层引发 $2\times128\times(576+512)=278{,}528$ FLOPs, 字节是 1152, 强度约 242 FLOP/字节. H800 的稠密 BF16 峰值约 989 TFLOPS, HBM 带宽 3.35 TB/s, 屋顶线拐点约 295 FLOP/字节. 也就是说, MLA 的 decode 注意力已经接近计算受限, GQA 模型还差 20 到 40 倍. 这个差别解释了 FlashMLA 为什么要做 FP8 KV 和计算访存的流水重叠: 字节数下来以后, kernel 的瓶颈从 HBM 移到了 Tensor Core, 优化重点随之改变. 以上强度是按模型结构推出的, 论文只给了 KV 字节数, 没有给出强度.

### 1.3. 表 2 的 FLOPs 口径与「少一个数量级」

表 2 的单位写成 GFLOPS/Token, 实际含义是训练一个 token 的前向加反向运算量 (GFLOP), 与「每秒」无关. 口径可以用表 4 反推: MPFT 一列每天 272.80B token, 合每秒约 $3.157\times10^6$ token; 2048 张卡每卡 385 TFLOPS (causal 口径), 两数相除得每 token 约 249.7 GFLOP, 正好是表 2 的 250. 从结构正算也能得到这个数: 线性层的前向加反向是 $6\times37\text{B}=222$ GFLOP; MLA 在 4K 序列下的打分与加权按下三角计, 每 token 每层前向约 $2\times128\times(192+128)\times2048$ FLOPs, 乘 3 (前向加反向) 再乘 61 层约 30.7 GFLOP; 合计约 253. V2 一行同样算: $6\times21\text{B}=126$, 加注意力约 30, 得约 156, 表中是 155.

两个稠密模型那两行的口径不完全一致. LLaMA-3.1-405B 光线性层就有 $6\times405\text{B}\approx2430$ GFLOP, 加上注意力约 2448, 合理. Qwen2.5-72B 的非嵌入参数约 70B, 线性层 $6\times70\text{B}\approx420$ GFLOP, 已经高于表中的 394, 这一行用了什么参数量论文没有交代. 于是 2.2.1 节「少一个数量级的计算资源」只对 405B 那一行成立 (2448 对 250, 约 9.8 倍); 对 72B 那一行, V3 每 token 的训练计算只少约 37%, 按 420 算也只少约 40%. MoE 的收益在这里要分开看: 和 72B 稠密模型相比, V3 用相近的每 token 计算换来近 10 倍的总参数; 和 405B 相比, 才是同等规模下省一个数量级.

## 2. EP 通信与 decode 速度的上限

### 2.1. 120.96 μs 是哪几个数乘出来的

2.3.2 节的推算设定每张卡放一个专家, 一次处理 32 个 token, 每个 token 要发给 8 个路由专家和 1 个共享专家. dispatch 用 FP8 (1 字节), combine 用 BF16 (2 字节), 隐藏维取 7K, 网卡带宽取 400Gbps 即 50 GB/s:

$$
T_{\text{comm}}=\frac{(1+2)\times32\times9\times7000\ \text{字节}}{50\times10^9\ \text{字节/秒}}=120.96\ \mu\text{s}.
$$

只有把 7K 取成 7000 才得到 120.96; 取 V3 真实的 7168, 一轮是 123.86 μs. FP8 dispatch 实际还要带每 128 个元素一个 4 字节的缩放因子, DeepEP 的 low-latency 消息每 token 7408 字节, 比 7168 多 3.3%. 按 4.3 节自己用的 40 GB/s 有效带宽, 一轮是 154.8 μs. 公式里的 $(1+2)$ 已经把 dispatch 和 combine 两趟都算进去了, 后面「每层 $2\times120.96$」里的 2 来自双 micro-batch: 两个 micro-batch 各要做一轮 dispatch 加 combine, 计算被假设完全藏在通信下面, 一层的墙钟时间就是两轮通信之和. 61 层合计 14.76 ms, 约 67.8 token/s.

这个数可以和 DeepEP 公开的 low-latency 实测对照. DeepEP 文档给的 EP64 一行是每卡 128 个 token, 8 个路由专家, dispatch 173 μs, 由此换算的带宽约 43.9 GB/s. 把 token 数缩到 32, 按同样的有效带宽, dispatch 约 43 μs (每副本 7408 字节), combine 约 84 μs (每副本 14336 字节), 合计约 127 μs. 论文的 120.96 μs 用 9 个副本, 50 GB/s 线速; 实测口径是 8 个副本, 43.9 GB/s. 两个口径的误差互相抵消了一部分, 结果只差约 5%, 说明这个理论上限离实测并不远. MoE 的 all-to-all 字节数一般推导见 [MoE 专家并行与 All-to-All 通信](../../../llm-guide/6-训练与推理优化/6.1-训练基础设施/6.1.8-MoE系统与并行/01-MoE专家并行与All-to-All通信/01-MoE专家并行与All-to-All通信.md).

### 2.2. 换成 NVL72 以后: 0.82 ms 省略了什么

把带宽从 50 GB/s 换成 GB200 NVL72 的 900 GB/s, 通信时间按比例缩到 6.72 μs ($50/900$ 正好等于 $6.72/120.96$), TPOT 变成 0.82 ms, 约 1220 token/s. 论文自己提醒这个数没有考虑小 batch 下 GPU 效率的下降. 还有两处它没有提. 第一, NVL72 只有 72 张 GPU, V3 每层有 257 个专家, 「每卡一个专家」放不下. 每卡放约 4 个专家时, 如果每个专家仍处理 32 个 token, 每卡收发的字节约为原来的 4 倍, 一轮约 27 μs, TPOT 约 3.3 ms; 如果每卡总共仍是 32 个 token, 每个专家只分到约 8 个 token, 专家 GEMM 更加访存受限.

第二, 通信缩短以后, 读专家权重的时间会冒出来. V3 一个路由专家的参数是 $3\times7168\times2048\approx44.0$M, FP8 存放 44 MB. 每一层每个 micro-batch 都要把这 44 MB 从 HBM 读一遍, 在 H800 的 3.35 TB/s 下是 13.1 μs, 在 8 TB/s 的 HBM3e 上是 5.5 μs. 50 GB/s 网络下, 13.1 μs 远小于 120.96 μs, 通信确实是瓶颈; 900 GB/s 网络下, 6.72 μs 已经和读权重的时间相当. 双 micro-batch 各读一遍权重, 只算专家部分, 61 层在 H800 级 HBM 上就要约 1.6 ms, 在 8 TB/s 上约 0.67 ms, 和 0.82 ms 同一量级, 还没算 MLA 读 KV 的时间. 所以 1200 token/s 是网络单项的上限, 换成 NVL72 以后, 系统的上限由 HBM 带宽和每卡专家数共同决定. 这组数是按 V3 公开配置和 HBM 规格推出的, 论文没有给出.

### 2.3. 本地部署: 20 TPS 对应多少内存带宽

2.2.2 节说装 AI SoC 的 PC 跑 V2 能接近 20 TPS, KTransformers 在一台约 1 万美元, 配消费级 GPU 的服务器上跑完整的 V3 也接近 20 TPS. 单用户 decode 时 batch 为 1, 每生成一个 token 都要把激活的权重读一遍, 速度上限近似为「内存带宽 / 每 token 读的字节」. V2 每 token 激活 21B 参数, 20 TPS 在 8 位量化下要 420 GB/s, 在 4 位下要 210 GB/s. 论文没有给出量化精度和具体芯片, 但这个带宽要求说明 20 TPS 对应的是 4 位左右的量化, 以及 200 GB/s 以上的统一内存带宽.

V3 在 KTransformers 上的情形可以拆开算. KTransformers 把注意力, 共享专家和稠密层放在 GPU 上, 路由专家放在 CPU 内存里由 CPU 计算. 每 token 要读的路由专家权重是 8 个专家乘 58 个 MoE 层乘 44.0M, 约 20.4B 参数; 4 位量化时每 token 约 10.2 GB, 20 TPS 要求 CPU 内存带宽约 204 GB/s. 这落在双路服务器 DDR5 的能力范围里 (双路 24 通道 DDR5-4800 的理论值约 920 GB/s, 实际可用约一半到三分之二). 稠密模型就没有这条路: 70B 稠密模型 4 位量化每 token 要读 35 GB, 同样的 200 GB/s 只有约 6 TPS, 与论文「个位数 TPS」的说法一致. 本地部署的瓶颈是内存带宽, 不是算力, MoE 的激活参数比直接决定了 TPS.

### 2.4. MTP 的 1.8 倍

2.3.3 节给出的线上数据是: 一个 MTP 模块预测第二个 token 的接受率在 80% 到 90%, 生成 TPS 提高到 1.8 倍. 只用一个 MTP 模块时, 每个解码步产出 $1+p$ 个 token, $p$ 是接受率, 期望值在 1.8 到 1.9 之间. 1.8 倍落在这个区间的下沿, 说明验证带来的额外开销 (多一层 MTP 前向, batch 变大后 EP 通信和计算的增量) 不大. V3 技术报告给的接受率是 85% 到 90%, 也是 1.8 倍 TPS; 这里把下限放宽到 80%, 原因论文没有给出.

## 3. 低精度: FP8 训练的两处硬件短板与 LogFMT

### 3.1. FP22 累加器: 13 位尾数在长 K 上丢多少

V3 线性层的三个 GEMM (前向, 对输入求梯度, 对权重求梯度) 都以 FP8 E4M3 为输入, 训练框架的细节见 [V3 解析](../../01-模型技术报告/deepseek-v3/deepseek-v3-analysis.md) 第 2.2 节, 一般做法见 [FP8 混合精度训练详解](../../../llm-guide/6-训练与推理优化/6.1-训练基础设施/6.1.2-混合精度训练/02-FP8混合精度训练详解/02-FP8混合精度训练详解.md). 3.1.1 节把 Hopper 的第一个问题落在累加器上. 一条 FP8 WGMMA 沿 K 方向处理 32 个元素: Tensor Core 先算出 32 个尾数乘积, 按其中最大的指数把其余乘积右移对齐, 只保留最高 13 个小数位相加, 超出的位直接截断, 结果累加进 1 位符号, 8 位指数, 13 位尾数的寄存器, 论文沿用被引工作 (SageAttention2) 的叫法记为 FP22. V3 技术报告写的是「约 14 位」, 差在是否计入规格化数的隐含位, 两份材料描述的是同一个硬件行为, 代码侧的对应见 [DeepGEMM 解析](../../04-开源仓库/deepgemm/deepgemm-analysis.md) 第 2.1 节.

13 位截断对长 K 的影响可以粗算. 截断总是朝零的方向, 误差不会正负抵消; 每往累加器里加一批乘积, 相对误差最多 $2^{-13}\approx1.2\times10^{-4}$. $K=4096$ 时一共累加 $4096/32=128$ 次, 最坏累积到 $128\times2^{-13}\approx1.6\%$, 与 V3 技术报告实测的「最大相对误差接近 2%」同一量级. 文中没有给出误差模型, 这个数是按截断误差线性累积推出的上界. V3 的办法是每 128 个 K 元素 (4 条 WGMMA) 就把部分和取到 CUDA Core 的 FP32 寄存器里, Tensor Core 内部最多连续累加 4 次, 每段的截断误差上界降到 $4\times2^{-13}\approx0.05\%$, 段与段之间在 FP32 里相加. 2.4 节报告的结果是: 在 16B 与 230B 两个 DeepSeek-V2 规模上做 FP8 消融, 相对 BF16 的差距低于 0.25%. 这里写的是 relative accuracy loss, V3 技术报告附录 B.1 对同一组实验写的是相对 loss 误差, 指的是训练 loss 而不是下游准确率.

3.1.2 节的第一条建议由此而来: 累加寄存器提到 FP32, 或者让累加精度可配置, 训练用高精度, 推理按需要降低. 软件提升的代价不在 FLOPs 上, 在寄存器和指令发射上: 每个线程要多持有一组 FP32 累加器, warpgroup 每处理完一个 K 块就要停下来做一次搬运. 这一步还同时承担了反量化, 开销在下一节算.

### 3.2. 细粒度量化的反量化开销与 microscaling

V3 的量化粒度是激活按 $1\times128$ 的 tile (一个 token 的 128 个通道) 共享一个缩放因子, 权重按 $128\times128$ 的 block 共享一个. 粒度细, 离群值只影响自己所在的组; 代价是缩放因子沿 K 方向每 128 个元素就变一次, 而 Hopper 的 Tensor Core 不接收这些因子. 每个 K 块的部分和都要先送出 Tensor Core, 在 CUDA Core 上乘以 $s_A s_B$ ($s_A$ 是激活 tile 的缩放因子, $s_B$ 是权重 block 的缩放因子), 再加进 FP32 累加器. DeepGEMM 里这一步是 `final_accum += scale_a * scale_b * accum` ([DeepGEMM 解析](../../04-开源仓库/deepgemm/deepgemm-analysis.md) 第 2.2 节), 反量化和 3.1 节的精度提升合在同一个点上.

这一步的开销可以按峰值估. 对输出矩阵的每个元素, 一个 128 长的 K 块在 Tensor Core 上是 $2\times128=256$ FLOP; 在 CUDA Core 上是一次乘法加一次乘加, 约 3 FLOP. H800 的 FP8 稠密峰值约 1979 TFLOPS, FP32 CUDA Core 峰值约 67 TFLOPS, 两段耗时之比约 $(3/67)/(256/1979)\approx0.35$. 也就是说, 反量化如果与矩阵乘串行执行, 要多花约三分之一的时间. V3 技术报告的办法是两个 warpgroup 交替, 一个做提升时另一个继续发 WGMMA, 把这三分之一藏到矩阵乘后面; 前提是寄存器装得下两组累加器, 这也限制了 tile 形状的选择. 这个比例按规格峰值推出, 论文只给了定性的说法: 频繁的数据搬运降低计算效率, 也让硬件利用变复杂.

第二条建议是让 Tensor Core 直接接收缩放因子, 在内部完成分组缩放和部分和累加, 只输出最终结果. 论文举的例子是 Blackwell 的 microscaling (MX) 格式: 每 32 个元素共享一个 8 位纯指数 (E8M0) 的缩放因子, 由 Tensor Core 在乘加时应用. V3 的 $1\times128$ 与 $128\times128$ 都能写成 MX 的特例, 把一个缩放因子复制给相邻 4 个 32 元素子块即可, 条件是因子取 2 的整数次幂. DeepGEMM 后来支持的 UE8M0 缩放因子格式就是为了对齐这一条 ([DeepGEMM 解析](../../04-开源仓库/deepgemm/deepgemm-analysis.md) 第 3.1 节), MX 与 NVFP4 的格式细节见 [MXFP4 与 NVFP4](../../../llm-guide/6-训练与推理优化/6.1-训练基础设施/6.1.2-混合精度训练/03-MXFP4与NVFP4/03-MXFP4与NVFP4.md). 原生分组缩放消掉的是反量化的搬运, 累加器位宽是另一个问题, 所以论文把两条建议分开写.

### 3.3. LogFMT 的编码与精度

3.2 节讨论的是 EP 通信两半的精度差. dispatch 已经用细粒度 FP8, 比 BF16 少一半字节; combine 出于精度要求留在 BF16. 论文在 combine 上试过 FP8, E5M6 和 FP8/BF16 混合, 另外提出 LogFMT-$n$Bit. 编码以一个 $1\times128$ 的 tile 为单位: 先对每个元素取 $\ln|x_i|$, 求出最小值 $min$ 与最大值 $max$; 1 位符号之外的 $n-1$ 位中, 全 0 表示零, 码值 1 对应 $min$, 码值 $2^{n-1}-1$ 对应 $max$, 中间等距, 步长为

$$
Step=\frac{max-min}{2^{n-1}-2}.
$$

码值 $K$ 解码为 $\mathrm{sign}\cdot\exp\big(min+Step\times(K-1)\big)$. 另有两条约束. 一是 $min\ge max-\ln 2^{32}$, 一个 tile 内最大最小绝对值之比不超过 $2^{32}$, 与 5 位指数的浮点格式相当. 二是舍入在线性域做, 不在对数域做. 原因是 $\exp$ 是凸函数: 两个相邻码值解码后为 $a<b$, 对数域就近舍入的分界点是几何平均 $\sqrt{ab}$, 低于线性域的算术平均 $(a+b)/2$, 落在两者之间的值在对数域会被舍向 $b$, 解码后幅值系统性偏大, 线性域舍入才是无偏的.

精度可以和浮点格式放到同一个量上比: 相邻两个可表示值之比的自然对数, 即对数域步长. 浮点格式在每个二进制数量级里有 $2^m$ 个尾数刻度 ($m$ 是尾数位数), 步长约 $\ln2/2^m$, 与数值大小无关; LogFMT 的步长由 tile 的跨度决定. 下表按 tile 内最大最小绝对值之比为 $2^8$, $2^{16}$, $2^{32}$ 三档计算:

| 格式 | 每元素位数 | 跨度 $2^8$ | 跨度 $2^{16}$ | 跨度 $2^{32}$ |
| --- | --- | --- | --- | --- |
| E4M3 | 8 | 0.087 | 0.087 | 无法表示 |
| LogFMT-8 | 8 | 0.044 | 0.088 | 0.176 |
| LogFMT-10 | 10 | 0.011 | 0.022 | 0.043 |
| BF16 | 16 | 0.0054 | 0.0054 | 0.0054 |

表中的步长按编码规则算出, 论文没有给出. E4M3 的正规数只覆盖约 $2^{15}$ 的跨度, $2^{16}$ 一档里最小的值会落进次正规区, 那里的刻度更粗. 8 位时, 跨度在约 $2^{15.75}$ 以内 LogFMT 比 E4M3 细, 超过后反而更粗; 论文「LogFMT-8Bit 训练精度优于 E4M3 和 E5M2」的结论, 要求残差输出的 $1\times128$ tile 大多落在这个跨度以内. 10 位时步长在 $2^8$ 到 $2^{16}$ 的跨度下是 BF16 的 2 到 4 倍, 论文说它在 combine 上与 BF16 相近. 验证的设置是约 7B 的稠密模型, 量化残差分支的输出来模拟 MoE 的 combine; loss 曲线, 训练 token 数和 tile 跨度的统计文中都没有给出.

### 3.4. LogFMT 为什么没进生产

3.2.1 节给的原因有两层. 第一, Hopper 的 Tensor Core 不支持 LogFMT, 接收方拿到数据后要先转回 BF16 或 FP8 才能参与下一步计算, LogFMT 只能作为传输格式. 第二, 编解码要对每个元素算一次 $\ln$ 或 $\exp$, Hopper 每个 SM 每周期的特殊函数吞吐约为 FP32 乘加的 1/8, 编解码还占大量寄存器; 把编解码融进 all-to-all kernel 时, 开销达到 50% 到 100%. 这个百分比相对的是通信时间还是整层时间, 文中没有说明.

用 2.1 节的式子可以看出这笔开销为什么抵不过收益. combine 改成 LogFMT-10, 每元素 10 位, 再加每 128 个元素 4 字节的元数据, 约 1.28 字节, 比 BF16 少 36%; dispatch 的 FP8 带缩放因子约 1.03 字节. 式中的 $(1+2)$ 变成约 $2.31$, 一轮 EP 通信从 120.96 μs 降到约 93 μs, 少 23%, TPOT 从 14.76 ms 降到约 11.4 ms. 只要编解码让通信 kernel 慢 30% 以上, 这 23% 的字节节省就被抵消了, 而论文报的开销是 50% 到 100%. 以上按 2.3.2 节的设定推出, 文中没有给出 LogFMT 下的端到端数字.

去留还有后续. 论文 v1 发布于 2025-05; 2025-07 到 08 月, DeepEP 陆续加入 10 位 LogFMT, 只用于 decode 的 low-latency combine, 以可选开关 `use_logfmt` 提供, 且只在一组数满足 $\log_2 \mathrm{amax}<0$ 与 $\mathrm{amin}<\mathrm{amax}$ 时转换, 否则这一组仍发 BF16 ([DeepEP 解析](../../04-开源仓库/deepep/deepep-analysis.md) 第 3.4 节). DeepEP 在 2026 年重构为 V2 后, 当前主分支已没有这个选项. 「最终没有采用」对 V3 训练和论文成稿时的线上推理成立, 在开源库里则是一段时间内的可选功能. 3.2.2 节的建议是硬件提供面向 FP8 或自定义格式的压缩解压单元, 6.5 节进一步提出在网络硬件里原生支持 LogFMT. 两条建议的依据相同: 编解码放在 SM 上, 时间开销大于省下的字节, 只有交给专用硬件, 字节上的收益才不被抵消.

## 4. 互连: 节点限制路由与 scale-up/scale-out 融合

### 4.1. H800 节点: 被削的 NVLink 与八块 CX7

H800 SXM 与 H100 同为 Hopper 架构, 出于合规要求削减了 FP64 算力和 NVLink 带宽: 节点内 NVLink 从 H100 的 900 GB/s 降到 400 GB/s. 这两个数是双向合计, 单向分别是 450 与 200 GB/s, 4.3 节说的 200GB/s (实测约 160) 是单向数. 节点配 8 块 400Gbps 的 CX7 IB 网卡, 每块 50 GB/s, 考虑小消息和延迟后按 40 GB/s 计. scale-up 对 scale-out 的带宽比因此是 $200/50=4$ 或 $160/40=4$, 论文写成约 4:1; V3 技术报告用的是 $160/50=3.2$, 差在 IB 一侧取标称值还是有效值.

![](images/p07-figure-2-h800-node-interconnection.jpg)
> 图 2: H800 节点的互连, 两颗 CPU 下各挂 4 个 PCIe switch, 每个 switch 连 1 张 H800 与 1 块 CX7 网卡, 8 张 GPU 经 4 颗 NVLink switch 芯片全互连, 存储网卡单独挂在 CPU 2 上, 原文 Figure 2.

图 2 解析: GPU 与网卡成对挂在同一个 PCIe switch 下, 网卡读写显存的 RDMA 数据走 switch 内部的 P2P, 不经过 CPU, 这是 GPUDirect RDMA 能跑满网卡的前提. GPU 从 CPU 内存拷 KV cache 也要经过同一条 GPU 到 switch 的 x16 链路, 4.4 节的 PCIe 争用就发生在这条链路上. 8 块计算网卡和 1 块存储网卡分属两张网, 计算网的拓扑见第 5 节. 图里 NVLink 域与 PCIe 域之间没有直接通路, 跨两个域的数据只能由 GPU 的 SM 或拷贝引擎搬运.

4.2 节据此定了三条并行策略. 训练不用张量并行, 因为张量并行每层都要在 NVLink 上做 all-reduce, 带宽被削后得不偿失; 推理时可以选择性地用, 换取更低的 TTFT 与 TPOT. 流水并行用 DualPipe, 把注意力, MoE 计算与 MoE 通信重叠, 同时减少流水气泡, 均衡各卡显存 (调度见 [DualPipe 双向流水线并行深度解析](../../../llm-guide/6-训练与推理优化/6.1-训练基础设施/6.1.6-DualPipe双向流水线并行深度解析/6.1.6-DualPipe双向流水线并行深度解析.md)). 专家并行用 DeepEP, 8 块网卡下 all-to-all 每卡超过 40 GB/s. 三条里跨节点通信量最大的是专家并行, 后面的路由设计和网络设计都围绕它展开.

### 4.2. 节点限制路由: IB 份数从 8 降到 $M$

4.3 节的设定是 8 个节点, 64 张卡, 256 个路由专家, 每卡 4 个. 一个 token 选中的 8 个路由专家如果散在 8 个节点上, IB 上要发 8 份, 耗时记为 $8t$, $t$ 是经 IB 发送一个 token 的时间. 如果发往同一节点的几份只经 IB 发一次, 到达后再由那张卡经 NVLink 转发给本节点其他卡, IB 时间只取决于目标节点数 $M$, 降为 $Mt$. V3 因此把 256 个专家按节点分成 8 组, 每组 32 个部署在一个节点上, 并在门控里保证每个 token 最多落在 4 个节点. 具体走法是源卡先经 RDMA 发给目标节点上同号的卡, 再由它经 NVLink 分发, 代码层面见 [DeepEP 解析](../../04-开源仓库/deepep/deepep-analysis.md) 第 1.3 节.

收益可以用均匀路由下的期望算. 从 256 个专家里无放回选 8 个, 期望命中 $8\big(1-\binom{224}{8}/\binom{256}{8}\big)\approx5.29$ 个节点; 先限定 4 个节点, 再在这 128 个专家里选 8 个, 期望命中约 3.63 个. 均值只降 31%, 更有用的是上界: 最坏情况从 8 份降到 4 份, 发送缓冲区和 RDMA 队列可以按 4 份预留. NVLink 一侧, 一份 IB 数据到达后平均要分给 $8/3.63\approx2.2$ 个专家副本, 落在 4:1 的带宽比以内, NVLink 不会先成为瓶颈. V3 技术报告按 3.2 的比值说每个节点平均可以接 3.2 个专家副本, 4 个节点合计约 13 个, 当前的 top-8 还有余量. 论文只给了 $8t$ 与 $Mt$ 的定性比较, 期望值是按均匀路由算的, 文中没有给出; 真实路由有偏, 命中节点数会更少.

这个设计有两条边界. 第一, 去重只发生在训练和 prefill 用的 normal kernel 里. decode 用的 low-latency kernel 为了压延迟, 每个 (token, 专家) 副本直接经 RDMA 发到目标卡, 不走 NVLink 转发, IB 上回到最多 8 份, 2.1 节的 120.96 μs 用的就是这种口径. 推理部署的 EP 规模也和训练不同: DeepSeek 2025-02 公开的推理系统概览里, decode 是 EP144, 18 个节点, 每卡 2 个路由专家, 另有 32 个冗余专家, 一个专家组已经不再对应一个节点. 第二, 节点限制缩小了专家组合的选择空间, 它对模型质量的影响论文和 V3 技术报告都没有给出消融. V4 去掉了「每 token 最多 $M$ 个节点」的限制, 重新设计了并行策略 ([V4 解析](../../01-模型技术报告/deepseek-v4/deepseek-v4-analysis.md) 第 1.1 节), 跨节点字节数的上界随之消失, 改由通算融合的 MegaMoE 内核去掩盖.

### 4.3. 20 个 SM 做了哪些搬运

训练时 H800 的 132 个 SM 里最多有 20 个用于通信, 约 15%. 4.4.1 节列出 SM 在 EP 通信里承担的五类工作:

- 转发: 在 IB 域与 NVLink 域之间聚合, 转发发往同节点多张卡的流量.
- 搬运: 在 RDMA 缓冲区 (注册过的显存区域) 与输入输出缓冲区之间拷贝.
- 归约: 执行 combine 需要的 reduce.
- 布局: 管理跨 IB 与 NVLink 分块传输的细粒度内存布局.
- 类型转换: all-to-all 前后的数据类型转换.

五类里只有归约和类型转换是计算, 其余三类是数据移动. 前三类直接来自 4.2 节的两级路径: NVLink 是内存语义, 转发必须由 SM 执行 load/store, 网卡做不了. 推理时 DeepSeek 把 EP all-to-all 全部交给网卡 RDMA, 不做 NVLink 转发, SM 只在发起和收尾时短暂占用, 换来计算与通信的重叠, 代价是 4.2 节的去重没有了. 训练和推理两种做法说明, 在现有硬件上「省 SM」与「省 IB 字节」不能兼得.

4.4.2 节的四条建议都在拆这个取舍. 统一网卡 (或 I/O die) 同时接 scale-up 与 scale-out 两张网, 带基本的交换功能, 能用一个 LID 或 IP 加策略路由把 scale-out 进来的包直接投到 scale-up 域内的某张 GPU; 专用通信协处理器从 SM 手里接过包处理, 提供硬件显存拷贝和类似 TMA 的 load/store 加速; 硬件支持跨两张网的转发, 广播 (对应 dispatch) 和归约 (对应 combine); 硬件同步原语处理乱序到达和内存一致性, 替代 RDMA 完成事件. 第一条和第三条合起来, 就是让 4.2 节的去重由硬件完成: 网卡收到一份 token, 按目标位图复制给本节点的几张卡, 不占 SM. 论文提到的 UEC, UALink 与 UB 是这个方向上的协议. 软件侧也在压 SM 用量, DeepEP V2 的 README 写的是 V3 式训练的通信 SM 从 24 个降到 4 到 6 个 ([DeepEP 解析](../../04-开源仓库/deepep/deepep-analysis.md) 第 4.4 节), 用的仍是现有硬件.

### 4.4. PCIe 争用与 CPU 侧的带宽

4.5.1 节的例子是推理时从 CPU 内存往 GPU 搬 KV cache, 每秒几十 GB, 与此同时 GPU 还在经 IB 做 EP 通信, 两者争用导致性能下降和延迟尖刺. 对照图 2 可以算出为什么会撞上: GPU 到 PCIe switch 是一条 PCIe 5.0 x16, 单向约 63 GB/s; GPUDirect RDMA 下网卡收发的数据也经这条链路进出显存, 网卡跑满是 50 GB/s, 再加 20 GB/s 的 KV cache 拷贝就超过上限. 用户态程序无法给这两类流量设优先级, EP 通信的尾延迟随之抬高. 这组数按 PCIe 5.0 与 400Gbps 网卡的规格推出, 论文没有给出实测的争用数据.

建议分三层. 最小的改动是把 PCIe 的流量类别 (traffic class) 暴露给用户态, 让 EP, TP 与 KV cache 传输按类型设优先级, NVLink 上同理. 再进一步是把网卡做进 I/O die, 与计算 die 同封装, 不再经过 PCIe. 最彻底的是 CPU 与 GPU 之间也用 NVLink 一类的专用高带宽互连, 让 CPU 进入 scale-up 域, Grace Hopper 的 NVLink-C2C 是现成的实现. 6.2 节补充了 CPU 侧的约束: 跑满 160 条 PCIe 5.0 通道需要每节点超过 640 GB/s 的数据供给, 对应约 1 TB/s 的内存带宽, 常规 DRAM 配置很难做到; kernel 启动和网络处理这类延迟敏感任务要求单核基频在 4 GHz 以上. 640 GB/s 按每通道单向约 4 GB/s 取整, 从 640 GB/s 到 1 TB/s 的系数文中没有给出推导; 若按 DRAM 实际可用带宽约为理论值的 60% 到 70% 计, 640 GB/s 对应约 0.9 到 1.1 TB/s 的理论带宽, 与 1 TB/s 相符.

## 5. 网络: 多平面胖树, RoCE 与内存语义通信

### 5.1. MPFT 的拓扑与表 3 的成本

> 图 3: 八平面两层胖树, 每个节点的第 $i$ 张 GPU 与第 $i$ 块网卡属于第 $i$ 个平面, 每个平面是一张独立的 leaf-spine 两层胖树, 跨平面流量要经节点内的 PCIe 或 NVLink 转发, 原文 Figure 3.

| --- | --- | --- | --- | --- | --- |

| RoCE | 3.6 μs | 5.6 μs |
| InfiniBand | 2.8 μs | 3.7 μs |
| NVLink | 3.33 μs | - |

表 5 是三种链路的端到端延迟. 5.2 节的出发点是 2.3.2 节的 120.96 μs: 数据传输本身只有百微秒量级, 几微秒的链路延迟占比就不能忽略. decode 每层有 dispatch 和 combine 两次 all-to-all, 双 micro-batch 下共 4 次, 61 层共 244 次; 按 IB 跨 leaf 的 3.7 μs 算约 0.9 ms, 占 14.76 ms 的 6%; 换成 RoCE 跨 leaf 的 5.6 μs 是约 1.4 ms, 占 9%. 表 5 没有给出测法 (消息大小, 是否含软件栈), NVLink 的 3.33 μs 比同 leaf 的 IB 还高, 说明这一行的测法与 RDMA 写的单程延迟不同, 文中没有交代.

IB 的两个问题是价格和端口数. IB 交换机通常 64 口, RoCE 交换机常见 128 口. 按 5.1 节的公式, 128 口的两层胖树能接 $128^2/2=8192$ 个端点, 是 64 口的 4 倍, 8 个平面合计 65,536 个, 与 64 口三层胖树的上限相同. 规模上 RoCE 占优, 延迟上吃亏: 多一跳交换机, IB 多 0.9 μs, RoCE 多 2.0 μs. 5.2.2 节的第一条建议因此是做去掉多余以太网功能, 专为 RDMA 优化的低延迟 RoCE 交换机, 论文举了 Slingshot 和 Broadcom 的 AI Forwarding Header 作为例子.

![](images/p11-figure-8-roce-network-bandwidth-of-allgather-and-reducescatter.jpg)
> 图 8: RoCE 网络上 ReduceScatter (第一张) 与 AllGather (第二张) 的带宽, 比较 ECMP, 自适应路由 (AR) 与静态路由三种策略在 TP 为 8, 4, 2 时的结果, 原文 Figure 8.

图 8 解析: 两种原语的读数几乎一样. TP 为 8, 4, 2 时, ECMP 约 45, 83, 97 GB/s, AR 与静态路由约 57, 103, 190 GB/s, ECMP 分别损失约 21%, 19%, 49%. 带宽随 TP 变小而升高, TP=2 时的 190 GB/s 超过一块 400G 网卡的线速, 纵轴应是按某种逻辑数据量计算的, 测试拓扑和带宽口径文中都没有给出. 静态路由与 AR 持平, 因为集合通信的源和目的固定, 路由表可以事先排开冲突.

ECMP 按包头哈希选路径, 流少而每条流大时, 几条流容易哈希到同一条链路上. LLM 训练的流量正是这样, DP 的集合通信在固定的卡对之间传大块数据, 缺少随机性. AR 按实时拥塞逐包选路径; 静态路由靠手工配置的路由表避开冲突, 对集合通信有效, 对目的地随路由结果变化的 EP all-to-all 就排不开, 所以论文认为大规模 all-to-all 要靠 AR. 第三条建议针对混合负载: RoCE 交换机的优先级队列有限, EP 的 all-to-all 是突发的多对一传输, 会造成 incast, 拖累同时进行的 DP all-reduce. 论文给的办法是虚拟输出队列 (VOQ, 每个 QP 一个虚拟队列), 或改用基于 RTT 的拥塞控制与用户可编程拥塞控制. 同一团队在 [Fire-Flyer 2](../fire-flyer/fire-flyer-analysis.md) 的 IB 网络上走过另一条路 (该文第 2.2 至 2.3 节): 用 Virtual Lane 隔离四类流量, 关掉 DCQCN, 存储流量改回静态路由并在应用层限流.

5.2.3 节的 IBGDA 处理的是控制面延迟. 传统路径里 GPU 准备好数据后通知 CPU 代理线程, 由 CPU 填写 work request 并敲网卡门铃; IBGDA 让 GPU 线程直接填 work request, 直接写门铃的 MMIO 地址. decode 一次 dispatch 每卡要发约 1024 条 7.4 KB 的消息 (128 个 token 乘 8 个专家), CPU 代理串行提交跟不上, GPU 的多线程可以并行提交. DeepEP 的 low-latency kernel 建立在 IBGDA 上, 实现见 [DeepEP 解析](../../04-开源仓库/deepep/deepep-analysis.md) 第 3.2 节. 论文据此主张各类加速器都支持这种由 GPU 发起的网络通信.

### 5.4. 内存语义的顺序问题与网内计算

6.4 节讨论的是跨节点 load/store 通信的顺序. 接收方要知道数据什么时候到齐, 现在的做法是发送方写完数据后发一个内存屏障 (fence), 再更新一个标志通知接收方. 屏障要等之前所有写的完成确认, 多出一个 RTT, 发出屏障的线程在这段时间停住, 后续的写也发不出去. 消息语义的 RDMA 有同样的问题: 开启 packet spraying 后, RDMA 写之后的原子加可能先于数据到达, 也要多等一个 RTT. 按表 5, IB 跨 leaf 的 RTT 约 7.4 μs, 是 120.96 μs 的 6%; 每层 4 次 all-to-all 各多一个 RTT, 与 5.3 节的链路延迟同一量级. 这个 RTT 的实测值文中没有给出.

论文给了两个硬件方案. 一是接收方缓存原子消息, 按包序号 (PSN) 排序后再处理, 实现简单. 二是基于地址区间的 acquire/release (RAR): 接收方硬件为内存区间维护位图或计数器, 记录区间内的写是否全部落地, acquire 与 release 的作用范围限定在指定地址区间, 发送方不再需要显式屏障. 两种方案都能放在网卡或 I/O die 上, 对内存语义和消息语义的 RDMA 都适用. 这与 4.4.2 节第 4 条建议是同一件事, 也是图 4 多平面喷洒能落地的前提: 包可以乱序走, 顺序由接收端硬件保证.

6.5 节把 EP 的两个阶段对应到网内计算: dispatch 是小范围多播, 一条消息发给多个目标; combine 是小范围归约. 收益要按方向算. 负载均衡时, all-to-all 中每块网卡的发送字节与接收字节相等. 交换机做多播, 发送方每个 token 只发一份, 发送字节最多降到 1/8, 每个目标仍要收到自己那份, 接收字节不变; 交换机做归约则相反. 链路是全双工的, 单独做 dispatch 时耗时由接收一侧决定, 只省发送带宽并不缩短时间. 收益出现在双 micro-batch 下: 一个 micro-batch 的 dispatch 与另一个的 combine 同时在网上, 两个方向的字节可以互补. 按每 token 每元素的字节计 (dispatch 1 字节, combine 2 字节, 8 个专家副本), 不做网内计算时两个方向都是 $8\times1+8\times2=24$; 多播加归约后, 发送一侧是 $1\times1+8\times2=17$, 接收一侧是 $8\times1+1\times2=10$, 耗时由 17 决定, 约省 29%. 另一种用法是多播只在节点入口交一份, 再由 scale-up 网分发, 即 4.2 节去重的硬件版本. 这组分析按全双工链路推出, 论文只说多播与归约能大幅降低通信开销, 没有给出量化.

combine 的网内归约更难做. 论文的理由是 EP combine 的归约范围小, 负载不均. 一个 token 的 8 份专家输出来自至多 4 个节点 (训练时), 到达每个交换机端口时能合并的份数不确定, 与 DP all-reduce 那种所有端点同形状, 同时到达的归约不同. 6.5 节还把 LogFMT 也放进网络硬件, 由网卡或交换机原生压缩解压, 提高每比特的信息量. 这与 3.4 节的结论一致: LogFMT 的字节收益要靠专用硬件做编解码才能兑现.

## 6. 三份一手材料怎样互相校验

V3 技术报告给出模型与训练配置: 671B 总参数, 每 token 激活 37B, 61 层, 256 个路由专家加 1 个共享专家, 每 token 选择 8 个路由专家; 训练采用 PP16、EP64, 在 2048 张 H800 上完成 14.8T token 预训练. Insights 论文把这些配置代入硬件模型, 追问每层通信、显存和低精度数值误差如何增长. 后续公开的 DualPipe、DeepEP、DeepGEMM 与 profile-data 则给出可执行调度、内核接口和时间线. 三者回答的是不同层次的问题, 配置数字、复杂度公式和实际时间线需要分别对应.

以通信重叠为例, 技术报告说明训练时调度 20 个 SM 处理通信, 并以节点限制路由控制跨节点流量; Insights 据此计算通信时间与链路需求; profile-data 的训练 trace 使用 EP64、TP1、4K 序列, 每个 chunk 含 4 个 MoE 层, 展示一对前向与反向 chunk 的重叠. Trace 为了观察重叠而假设 MoE 路由绝对均衡, 也省略 PP 通信. 它能证明内核在理想负载下按预定时间线并发, 不能代替真实训练中的专家偏斜和 PP 边界开销.

DualPipe 仓库给出的气泡公式为

$$
T_{\rm bubble}^{\rm DPipe}
=\left(\frac{P}{2}-1\right)(F\&B+B-3W),
$$

其中 $P$ 是偶数个流水阶段, $F$ 是前向 chunk 时间, $B$ 是完整反向时间, $W$ 是权重梯度反向, $F\&B$ 是互相重叠的一对前向与输入梯度反向. 这个公式与 Insights 表 4 中约 2 秒的实测气泡属于同一对象; profile trace 展示 $F\&B$ 如何发生, 却没有覆盖整条流水的 warm-up 与 drain. 只看一段 trace 会漏掉公式前面的 $P/2-1$.

DeepEP 的公开实现又有版本边界. V3 原始训练使用 PTX 级定制通信内核, V1 README 与论文中的 normal/low-latency 数字更接近当时系统;当前仓库已重构为 V2 系列, 接口、SM 占用、后端与支持的拓扑继续演进. 现版 README 明确写着 dispatch/combine 仍需要 GPU SM, 不支持零 SM RDMA EP. 因而「decode 发出 RDMA 后所有 SM 都能让给计算」描述的是特定低延迟时间段的执行行为, 不能扩张为整个 EP 栈永久零 SM.

DeepGEMM 同样应按代码路径理解. V3 报告描述的是 Hopper FP8 Tensor Core 的有限精度累加与周期性提升; 公开内核里能看到 WGMMA 累加、scale 乘法、`final_accum` 与 promotion 路径. 代码证明实现确实把局部累加结果提升到更高精度状态, 但内核已迭代, 当前模板、tile 和提升条件未必逐项等同 2024 年训练版本. 数值结论应落在「有限尾数的局部累加会丢小量, 周期性高精度汇总控制误差」, 版本专属常量则以对应提交为准.

这组材料还揭示一个常见误区: 论文里的理论带宽、README 的逻辑带宽和 profiler 的时间占比不是同一指标. 理论带宽来自链路规格; 逻辑带宽可能把节点内复制或重复专家字节计入有效载荷; profiler 还包含等待、同步和负载不均. 三者只有统一消息口径、方向和并发关系后才能比较.

## 7. EP dispatch 与 combine 的完整通信量

设每张 GPU 一个 micro-batch 有 $T$ 个 token, 隐藏维为 $d$, 每 token 路由到 $k$ 个专家, dispatch 元素精度为 $b_d$ 字节, combine 为 $b_c$ 字节. 忽略元数据时, 每卡 dispatch 逻辑发送量为

$$
V_d=Tkd b_d,
$$

combine 返回同样数量的专家输出, 逻辑字节为 $V_c=Tkd b_c$. V3 的低延迟估算取 $T=128,d=7168,k=8$, dispatch 用 1 字节, combine 用 2 字节, 因而

$$
V_d=128\times7168\times8\approx7.34\ \mathrm{MiB},
$$

$$
V_c\approx14.0\ \mathrm{MiB}.
$$

若单卡跨节点有效带宽取 50 GB/s, 单向纯传输下界分别约 147 μs 与 294 μs. Insights 的 120.96 μs 使用了节点限制、节点内转发与具体有效字节口径, 所以不能简单拿总逻辑字节除单网卡线速. 逻辑数据中有一部分目的专家在本节点, 走 NVLink; 发往同一远端节点多个专家的 token 还可以跨节点只传一份, 到远端再复制.

把目的节点集合记为 $D(x)$, 一个 token 的八个专家分布在 $m_x=|D(x)|$ 个远端或本地节点. 未去重的跨节点 dispatch 为每个专家发送一份 $d$ 维向量, 去重后每个目的节点一份, 压缩因子为

$$
\eta_d=\frac{\sum_x m_x}{Tk}.
$$

节点限制路由给出 $m_x\le M$, V3 训练取 $M=4$, 因此最坏上界从每 token 八份降到四份, $\eta_d\le1/2$. 若八个专家集中在两个节点, 只有四分之一跨节点 dispatch 字节. combine 无法直接沿用同样去重, 因为八个专家产生的输出不同; 远端节点可以先把本节点专家输出相加, 再向源节点传一份, 于是跨节点份数同样从 $k$ 降到 $m_x$, 但节点内需要完成归约.

元数据也不能完全省略. dispatch 至少要携带目标专家、源 token 槽位、scale 与对齐信息. 若一个 token—专家副本的载荷约 7168 字节, 十几字节元数据占比很低; decode 把消息拆成大量小包后, 包头、门铃和原子计数的固定成本会显著上升. Insights 估计每卡每次 dispatch 约 1024 条消息, 正是 $128\times8$. 若每条都单独提交, 7 KB 数据的串行控制开销可能超过链路传输; DeepEP 把同目的 rank 的 token 聚合, 并用 GPU 直接提交 work request, 才能逼近带宽下界.

训练的 token 数远大于 decode, 通信行为又不同. 大 micro-batch 让同一目的专家收到连续 token, 适合批量打包和吞吐内核; decode 只有约 128 token/GPU, 每个专家平均得到 $128\times8/256=4$ 个 token, 分布方差很大. 负载均衡仅保证较长时间窗口或训练 batch 内接近均匀, 单次 decode 仍可能有专家为空、另一个收到十几个 token. 这会同时改变消息大小、专家 GEMM 形状和尾延迟.

双 micro-batch 重叠时, 链路上同时存在 A 的 combine 与 B 的 dispatch. 设两个方向的可用带宽均为 $B$, 本地计算时间为 $C$, 网络阶段下界近似

$$
T_{\rm layer}\ge\max\left(C,\frac{V_d^{\rightarrow}+V_c^{\rightarrow}}{B},
\frac{V_d^{\leftarrow}+V_c^{\leftarrow}}{B}\right).
$$

全双工只允许发送与接收并行, 同一方向上的 dispatch 和 combine 仍争带宽. 因而一句「通信与计算完全重叠」至少要求计算时间覆盖两个方向中更慢者, 还要求 NIC、PCIe、NVLink 与 SM 搬运链没有额外串行段.

## 8. 节点限制路由是一个带容量约束的优化问题

V3 的无辅助损失负载均衡为每个专家维护校正偏置 $b_i$, 选专家时按 $s_i+b_i$ 排序, 真正的门控权重仍由原始 affinity $s_i$ 计算. 若专家负载高于目标, 下一步降低其偏置; 负载低则抬高. 可以把更新抽象为

$$
b_i^{(t+1)}=b_i^{(t)}+\gamma(\bar c-c_i^{(t)}),
$$

$c_i$ 是当前负载, $\bar c$ 是平均目标. 这近似对专家容量约束做对偶更新: 偏置承担拉格朗日乘子的角色, 但不直接进入输出权重, 避免辅助损失持续扭曲语言建模梯度.

节点限制又加了一层组合约束. 先把专家按物理节点分组, 对每个 token 选择 affinity 总和最高的至多 $M$ 个节点, 再只在这些节点内取 Top-$k$ 专家. 令专家 $i$ 所在节点为 $n(i)$, 二元变量 $z_n$ 表示节点是否开放, $x_i$ 表示专家是否选择, 对单 token 可写成

$$
\max_{x,z}\sum_i x_i(s_i+b_i),
\quad \sum_i x_i=k,
\quad x_i\le z_{n(i)},
\quad \sum_n z_n\le M.
$$

这使「选最相关的八个专家」变为「在至多四个节点里选八个」. 如果前八专家恰好分散在八个节点, 约束必然丢掉其中至少四个, affinity 有直接损失. 训练会让专家布局与表示逐渐适应该约束, 所以事后给一个无约束 checkpoint 加节点限制, 不能代表从头训练的结果.

负载偏置与节点限制会互相作用. 某节点有多个欠载专家时, 它们的偏置一起上升, 节点总分可能突增, 大量 token 又同时涌入该节点; 下一步偏置回调, 形成振荡. 更新率 $\gamma$ 太大时更明显. 可以在线观察三个量: 专家负载方差、节点负载方差以及 token 的平均 affinity 损失. 只压专家方差可能把流量集中到少数节点, 只压节点方差又可能让专家内部失衡.

容量因子为 $C$ 时, 每个专家允许的 token 上限约为 $CTk/E$. 若实际负载超过上限, 常见处理是丢 token、溢出到备份专家或扩大缓冲区. 三者分别影响质量、通信路径和显存. V3 通过动态偏置追求无 token 丢弃, 但物理缓冲仍需按尾部负载配置; 平均恰好均衡不代表每个 micro-batch 都不溢出. 对 $E=256,T=128,k=8$, 平均每专家只有 4 个 token, 泊松近似下出现两三倍平均负载并不罕见. decode 的 grouped GEMM 因而比训练更容易落入小矩阵低利用率区.

反例可以用两个节点构造. 节点 A 的四个专家对某类 token 分数都略高, 节点 B 的专家略低. 无偏置时所有 token 进 A; 偏置抬高 B 后, 节点选择可能在相邻 step 整体翻转. 单专家级平滑无法阻止节点级同步. 更稳定的做法是节点与专家两层偏置、较长时间窗或带阻尼的更新, 代价是响应负载漂移变慢. Insights 提出的硬件多播和归约只能降低既定路由的字节, 不能替代路由层的稳定性.

## 9. DualPipe 的气泡为什么会缩小

传统 1F1B 在 $P$ 个阶段上需要填满流水再排空, 理想气泡为

$$
T_{\rm bubble}^{\rm 1F1B}=(P-1)(F+B).
$$

V3 将反向拆成输入梯度 $B_x$ 与权重梯度 $W$, 其中 $B=B_x+W$. $B_x$ 必须尽快向前一阶段传播, $W$ 只更新本阶段参数, 可以延后. ZeroBubble 类调度把 $W$ 填进原本的空洞, 气泡降为 $(P-1)(F+B-2W)$. DualPipe 再让 micro-batch 从流水两端同时进入, 每张设备持有首尾两段模型, 前向 chunk 与另一方向的反向 chunk 重叠. 因此有效深度从 $P$ 缩到约 $P/2$, 但每卡参数翻倍.

当 $F=B_x=W=t$ 且重叠后的 $F\&B_x$ 仍约为 $t$, DualPipe 公式化为

$$
T_{\rm bubble}^{\rm DPipe}
=\left(\frac P2-1\right)(t+2t-3t)=0.
$$

这是理想极限, 表示可延后的 $W$ 正好填满双向调度的空洞. 若 $F\&B_x=1.4t$, 气泡变成 $(P/2-1)0.4t$. 若通信使重叠对耗时升到 $2t$, 则气泡为 $(P/2-1)t$. 公式把关键条件写得很清楚: 双向本身只减有效深度, 真正接近零气泡还依赖 $F$ 与 $B_x$ 的资源互补以及 $W$ 足够大、足够可移动.

V3 的 PP16 代入, 系数 $P/2-1=7$. 表 4 的气泡约 2.06 秒, 反推括号内每个边界约 0.294 秒. 这个数字表示一组 chunk 的不匹配残差, 不能当成单层时间. 总 step 19.926 秒, 气泡占约 10.3%. 「Zero-bubble」是调度目标与理想公式, 实机仍有通信、负载不均、chunk 形状差异和首尾阶段工作量差异.

DualPipe 的参数显存代价是每设备保存两个非相邻阶段. 若模型参数及其梯度、优化器状态按阶段均匀切分, 单卡份额从 $1/P$ 变成 $2/P$. 仓库表格因此记 parameter per device 为 2×. 激活显存为 $P+1$ 个 chunk 单位, 与 1F1B 的 $P$ 接近, 原因是双向流各自的未完成 micro-batch 在中部相遇. 这要求模型本身通过 EP、PP 和优化器分片留出余量; 对参数更密集、激活更小的模型, 双份参数可能成为首要限制.

调度还有一个容易忽略的因果约束. 权重梯度 $W$ 可以延后, 输入梯度 $B_x$ 不行, 因为上游阶段要等它才能继续反向. 若把完整反向当成不可拆的一个核, DualPipe 的空洞无法被精细填充. 因而框架必须支持显式拆分 dgrad 与 wgrad, 并保证累积、通信与参数更新顺序一致. 对融合程度很高的第三方算子, 拆分成本可能抵消气泡收益.

一个反例是注意力层与 MoE 层耗时严重不均. 统一按四个 MoE 层切 chunk 时, 某些 chunk 还含长序列注意力, $F$ 与 $B_x$ 比相邻 chunk 更长; 双向相遇后, 短 chunk 只能等待. 增加 micro-batch 数能摊薄 warm-up, 无法消除阶段内部的最长路径. 实际划分应按测得时间而非层数等分, 同时考虑两端各存一段后参数显存是否平衡.

## 10. 从 671B 参数推到训练显存

参数显存的第一层口径是全模型总量. 671B 参数若以 BF16 保存一份权重约需 1.342 TB 十进制; FP8 主权重副本约 671 GB. 混合精度训练还可能保留高精度 master weight、梯度、动量与方差. 若 AdamW 按 FP32 master、FP32 一阶和二阶状态、BF16 梯度估算, 每参数可达 14 字节, 全模型约 9.4 TB. V3 对大部分矩阵采用 FP8 计算, 并不意味着所有持久训练状态都变成 1 字节.

PP16 与 EP64 将不同参数按不同维度切分. 稠密注意力与共享组件主要由 PP 切, 每 stage 约持有全模型相应层的 $1/16$; 路由专家再由 EP64 切, 每个 EP rank 只保存本 stage 专家的 $1/64$. DualPipe 每卡放两段, PP 参数份额回到约 $2/16=1/8$. 由于 671B 的主体是路由专家, EP 分片把单卡专家权重大幅压低; 共享嵌入、注意力、共享专家与归一化项没有同样的 EP 除数, 所以不能用 $671B/(16\times64)$ 估整卡参数.

把一层 MoE 粗略拆成共享部分 $P_s$ 与全部路由专家 $P_e$, DualPipe 单卡份额近似

$$
P_{\rm gpu}\approx\frac{2L/P}{L}\left(P_s+\frac{P_e}{E_P}\right),
$$

其中 $L=61,P=16,E_P=64$. 式子忽略首尾嵌入、冗余专家和不均匀划分, 但能解释为什么超大总参数仍能装进 H800: 专家参数沿 EP 强分片, 每 token 也只激活其中 8 个.

优化器状态的分片维度又不同. ZeRO-1 切分 optimizer state, 参数和梯度仍可能在对应数据并行组复制. 若 DP 组大小为 $D$, 两个 FP32 动量状态从每参数 8 字节降到 $8/D$, BF16 权重与梯度仍各约 2 字节. 单参数状态近似

$$
B_{\rm state}=4+\frac{8}{D}quad\text{bytes},
$$

未计 master weight、scale、padding 与通信缓冲. 当 $D=32$, 优化器状态只剩 0.25 字节/参数, 权重和梯度成为主体. 具体 DP 组由 PP、EP 与集群规模共同决定, 不应把全局 2048 卡都当成一个 ZeRO 组.

激活显存由 micro-batch、序列长度、隐藏维、层数与 checkpoint 策略决定. 单层保存一个 $T\times d$ 的 BF16 张量需要 $2Td$ 字节; $T=4096,d=7168$ 时约 56 MiB. 实际反向要保存归一化输入、门控、注意力中间量和 MoE 路由元数据, 倍数远高于一份隐藏状态. DualPipe 同时存活约 $P+1$ 个 chunk 单位, 激活重算用额外计算换显存. 因而「参数能装下」与「4K 序列能以目标 micro-batch 训练」是两条独立约束.

通信缓冲是第三类. EP dispatch 至少需要发送缓冲、接收缓冲、按专家排列后的 token、combine 输出与计数器; 双 micro-batch 重叠要求两套生命周期并存. 若按容量因子预留, 缓冲随最坏专家负载而非平均负载增长. DeepEP 当前接口把 buffer 生命周期显式化, 正是因为临时对称内存、NVLink/RDMA 注册和多 stream 复用很难交给普通张量分配器临时处理.

显存峰值应按时间线求和, 不能把各组件的最大值直接相加. 权重与优化器状态全程常驻; 某个阶段的激活在对应反向完成后释放; EP 发送缓冲可在 NIC 消费后复用; wgrad 计算与另一 chunk 前向重叠时, 两者的工作区却会同时存在. 最可靠的核算是给每类张量标出 birth/death event, 沿 DualPipe 时间线做区间最大和.

## 11. FP8 点积误差从哪里积累

矩阵乘中的单个输出是长度 $K$ 的点积

$$
y=\sum_{i=1}^{K}a_ib_i.
$$

输入量化先产生 $\hat a_i=a_i(1+\delta_i^a)$、$\hat b_i=b_i(1+\delta_i^b)$, 乘积相对误差的一阶项约为 $\delta_i^a+\delta_i^b$. 随后有限精度累加每一步再舍入. 若累加器单位舍入误差为 $u$, 标准前向误差界可写成

$$
|\operatorname{fl}(\sum_i\hat a_i\hat b_i)-\sum_i\hat a_i\hat b_i|
\le\gamma_K\sum_i|\hat a_i\hat b_i|,
\qquad \gamma_K=\frac{Ku}{1-Ku},
$$

前提是 $Ku<1$. FP22 累加器只有约 13 位尾数时, $u$ 约为 $2^{-14}$ 量级; $K$ 达数千后, 最坏界迅速变松. 该界很保守, 却准确指出风险随归约长度和绝对值和增长, 尤其是正负项互相抵消时, 相对误差会被放大.

V3 的做法是把 Tensor Core 局部累加结果周期性提升到 CUDA Core 的 FP32 寄存器. 若每 $r$ 项形成一段, 低精度误差从 $\gamma_K$ 降到约 $K/r$ 个局部误差 $\gamma_r$, 再加 FP32 汇总误差. 粗略上界为

$$
E\lesssim\gamma_r\sum_i|a_ib_i|+gamma_{K/r}^{(32)}
\sum_j|s_j|.
$$

$r$ 越小, 数值更稳, promotion 指令、寄存器和数据搬运越多; $r$ 越大, 吞吐更高, 小增量更容易被大部分和吞掉. Insights 指出的硬件缺口是原生累加精度不足, 软件只能以周期性提升补偿.

一个极端反例是先累加很多大正数, 再累加几乎等量的大负数, 真值只剩很小残差. 13 位尾数在部分和很大时看不见后续小修正, 最终绝对误差不大, 相对残差却可能完全错误. 随机独立项常出现近似 $\sqrt K$ 的误差抵消, 训练中的激活和梯度并不独立, 离群通道与结构化相关会破坏这一乐观假设.

细粒度 scaling 处理的是另一层误差. V3 对 activation 按 $1\times128$ tile、权重按 $128\times128$ block 量化, 让每个 scale 覆盖较窄动态范围. 设块最大值为 $m$, FP8 最大有限值为 $q_{\max}$, scale 取 $s=m/q_{\max}$, 普通值 $x$ 的有效刻度约与 $s$ 成正比. 若一个离群值把 $m$ 放大十倍, 其余值的有效分辨率下降约十倍. 缩小 block 能隔离离群值, 代价是 scale 数量、加载次数和反量化乘法增加.

scale 本身也有误差. 实际点积变成

$$
\hat y=\sum_{g,h}s_g^a s_h^b
\sum_{i\in(g,h)}q_i^a q_i^b.
$$

若 scale 用高精度保存, 主要误差来自 $q$; microscaling 把 scale 也压成低位格式后, 每组共同乘上一个相对误差, 这类误差在组内完全相关, 不会随元素数平均消失. LogFMT 用指数域编码扩大动态范围, 对乘法友好, 但加法仍要回到线性域; 没有硬件编解码时, 节省的网络字节可能被转换开销吃掉.

数值验收不能只比较 GEMM 最大绝对误差. 至少要报告按输出幅度归一的误差、余弦误差、梯度范数漂移、不同 $K$ 与离群比例的分桶结果, 再观察长训练中 loss spike. 某个内核在随机高斯输入上通过, 不代表它能覆盖 MoE 中小 token grouped GEMM、注意力投影和高峰度梯度.

## 12. 通信能否被计算遮住: 一个可检验条件

每层 MoE 可抽象为 dispatch、专家 GEMM、combine 三段. 双 micro-batch 后, A 的专家计算可与 B 的 dispatch 重叠, A 的 combine 又可与 B 的其他计算重叠. 若单批三段耗时分别为 $D,C,R$, 理想稳态周期接近

$$
T_{\rm steady}\ge\max(C,D+R),
$$

前提是 dispatch 与 combine 占用同一网络方向和资源, 计算与通信能真正并发. 若二者分别落在全双工相反方向, 下界还可放松为 $\max(C,D,R)$. 实机通常位于两者之间, 因为 NIC 全双工, PCIe 与 NVLink 路径却可能共享交换芯片或内存控制器.

训练报告分出 132 个 SM 做计算、20 个 SM 做通信, 占比约 13.2%. 这种静态划分只有在通信核能持续喂满 NIC 时有效. 消息很小时, 更多 SM 不能消除门铃和 RTT; 消息很大时, 网卡已满速, 再给 SM 也无收益; 若通信核读写 HBM 抢走 GEMM 带宽, 计算区即使保留 132 个 SM 也会减速. 最佳 SM 数应随消息大小、拓扑与重叠阶段改变.

profile-data 的 decode trace说明 RDMA 请求发出后通信阶段可以暂时释放 SM, 计算结束再等待网络. 设发起开销为 $D_{\rm issue}$, 纯网络飞行时间为 $D_{\rm wire}$, 则可遮住的是 $D_{\rm wire}$, 发起与最终同步仍在关键路径:

$$
T\ge D_{\rm issue}+\max(C,D_{\rm wire})+D_{\rm wait}.
$$

这也解释了 IBGDA 的价值: 它缩短 $D_{\rm issue}$, 并让很多小消息并行提交; 带宽相同的情况下, 控制面延迟仍会决定 decode.

prefill 的两批可以按 token 拆分, 同一长 prompt 甚至分到两边, 目的是让注意力计算量接近. 因果注意力每个 token 的工作量随位置增长, 简单把序列前半给 A、后半给 B 会极不均衡. 位置 $i$ 的注意力工作近似与 $i$ 成正比, 区间 $[1,N]$ 的总工作为 $N(N+1)/2$. 若连续切分使两边等工作, 切点满足 $m^2\approx N^2-m^2$, 即 $m\approx N/\sqrt2$, 不是 $N/2$. 实现还要兼顾 KV 连续布局与因果依赖, 所以公开说明强调两 micro-batch 的注意力负载均衡.

decode 的 attention 计算主要随历史长度变化, 同批请求长度不一. 若按请求数平分, 一批可能集中长上下文, 另一批集中短上下文, $C_A\gg C_B$, 网络便无法被稳定遮住. 应按估计 FLOPs 或 KV 页数做装箱, 同时让两批 token 数足够支撑专家 GEMM. 只优化注意力平衡又可能破坏专家负载, 这是二维调度问题.

反例是极短上下文加大 batch. attention 很便宜, 专家 GEMM 很大, 网络可被计算遮住; 极长上下文加小 batch 时, attention 很大但 EP 消息碎, 发起开销与注意力可部分重叠; 中等上下文、低 batch 可能两边都不够长, 气泡反而明显. 因此吞吐曲线需要同时扫 batch 与上下文, 单个点的「完全重叠」无法外推.

## 13. 基础设施结论的失效边界

第一条边界来自均衡假设. EP 通信公式常用每专家平均 token 数, profiler 也明确模拟绝对均衡路由. 真正 step 时间由最慢专家、最拥塞节点和最慢链路决定. 设专家负载为 $c_i$, 理想计算时间与平均值 $\bar c$ 成正比, 实际下界由 $\max_i c_i$ 决定, 尾部放大系数

$$
\rho_c=\frac{\max_i c_i}{\bar c}
$$

会直接乘到最慢 grouped GEMM. 节点限制把专家相关性引入网络, 同一 token 的多个专家集中后, 节点总负载的方差可能高于单专家方差.

第二条边界来自并发资源. 网络和计算时间分别测量都满足重叠条件, 同时运行时却可能共享 HBM、L2、PCIe 与调度队列. 若单独 GEMM 为 $C_0$, 单独通信为 $D_0$, 并发后变成 $C=C_0(1+\alpha)$、$D=D_0(1+\beta)$, 遮蔽收益取决于膨胀后的最大值. 只比较独立 kernel 时长会系统性高估重叠.

第三条边界来自规模. 图 5、图 6 的 16–128 卡微基准与 2048 卡训练表覆盖不同层次; MPFT 与 MRFT 在 2048 卡都能保持两层, 更大规模时路由、故障域和路径多样性才显著分化. 交换机数公式给出容量上限, 没有包含线缆长度、机架布置、光模块、故障恢复与维护成本. 每端点美元接近也不代表总拥有成本相同.

第四条边界来自故障与慢节点. DualPipe 双向流把两段模型绑定在同一设备, 任一设备抖动会同时影响两个方向; EP all-to-all 又让一个慢 rank 拖住整组. 平均吞吐不反映长尾 step. 应报告 P50、P95、P99 step time, 并把网络重传、ECC、温度降频和后台存储流量关联起来. 训练数周时, 千分之一的慢 step 也会累积成可见成本.

第五条边界来自实现版本. 当前 DeepEP 已支持更大 scale-up/scale-out 域和新的后端, DualPipe 也出现 DualPipeV; 它们证明路线仍在演化, 不能反向改写 V3 当年的事实. 对照公开实现时要固定 commit、GPU、CUDA、驱动、NIC firmware 与拓扑. 只写仓库主分支名称, 数月后复跑可能得到另一套接口和性能.

## 14. 最小可复现实验怎样设计

通信实验先固定单节点 8 卡, 测 NVLink dispatch/combine; 再扩到 2、4、8、16 节点, 分别开启与关闭节点限制路由、跨节点 token 去重和双 batch overlap. 每个点扫 token 数 32、128、512、4096, 记录逻辑字节、物理 NIC 字节、NVLink 字节、SM 占用、P50/P99 延迟. 逻辑带宽超过 50 GB/s 时, 物理计数器必须说明超出的部分来自节点内流量或去重口径.

路由实验固定 logits, 单独运行专家 Top-$k$、加偏置 Top-$k$、节点限制 Top-$k$ 三步. 输出每步选中专家、节点数、affinity 损失与负载变化. 再构造「八个最高分专家分散在八节点」和「八个集中在一节点」两个极端输入, 验证通信上界从 $k$ 份缩到 $M$ 份的同时, 质量代理损失怎样变化. 动态偏置测试用阶跃式数据分布, 观察收敛时间与振荡幅度.

DualPipe 实验采用仓库的相同阶段数对比 1F1B、ZeroBubble、DualPipe. 对每种调度先用 sleep kernel 校验公式, 再换真实 attention/MoE chunk. 分别记录 $F,B_x,W,F\&B_x$ 与整 step 气泡, 检查公式预测和 trace 空洞是否一致. 把通信关闭、固定为理想均衡、恢复真实路由三次运行, 可把调度气泡、通信残差和负载尾部拆开.

显存实验不以进程峰值一个数字收尾. 给参数、梯度、优化器、激活、重算缓存、EP buffer 和通信 workspace 分类别打点, 沿时间线导出每类存活曲线. 然后切换 DualPipe 与 1F1B, 验证参数约 2×、激活约从 $P$ 到 $P+1$ 单位的理论变化. 若总峰值不同, 可直接定位到哪类工作区与哪个重叠窗口.

FP8 实验构造四组输入: 随机高斯、高峰度离群、正负抵消、按通道尺度相差百倍. 对 $K=128,512,2048,8192$ 扫 promotion 间隔, 比较 FP32 基准、纯 FP22 累加、周期提升与 BF16. 输出绝对误差、相对误差、余弦、最大 ULP 与速度. 再把同一设置接到一层 MoE 的前后向, 观察梯度和一步参数更新, 防止矩阵输出误差很小却在梯度中放大.

网络拓扑实验需要把路径和路由写进结果. MPFT 与 MRFT 使用相同端点数、相同消息分布、相同 rail 映射, 分别测均匀 all-to-all、热点专家 all-to-all、DP collectives 与两者并发. ECMP、静态路由、AR 各跑多次随机种子, 报告链路利用率方差和尾延迟. 只有平均算法带宽相近时, 再比较故障下一条链路或一个平面下线后的退化.

最终验收表至少含五条因果链: 路由分布怎样变成每节点物理字节; 物理字节怎样变成链路时间; 链路时间与计算怎样重叠成层时间; 层时间怎样经 DualPipe 形成 step 时间; 低精度误差怎样从 GEMM 输出传到训练 loss. 每条链都有独立计数器、公式预测和 trace 观测, 某一层不吻合时便停在该层定位, 无需用整训吞吐倒推全部原因.

## 15. 从胖树公式走到拥塞概率

无阻塞两层胖树要求每台 leaf 的上行总带宽不低于下行总带宽. 对 $k$ 口交换机, 常见配置用 $k/2$ 口接端点、$k/2$ 口接 spine. leaf 数为 $k$, spine 数为 $k/2$, 每个 spine 与所有 leaf 各连一条, 端点数为 $k^2/2$. 这套公式默认所有链路等速、每个端点只有一个网络口、路由能把跨 leaf 流量均匀铺到 $k/2$ 条上行. 任一条件失效, 「无阻塞」便只剩端口计数意义.

MPFT 把端点按 rail 分成八张独立胖树. 对 GPU $g=(n,r)$, $n$ 是节点, $r$ 是节点内卡号, 其网卡只连第 $r$ 个平面. 从 $(n,r)$ 发往 $(n',r')$ 且 $r\ne r'$ 时, 路径必须包含一次节点内换 rail:

$$
(n,r)\xrightarrow{\rm NVLink}(n,r')
\xrightarrow{\rm plane\ r'}(n',r').
$$

也可以先走平面 $r$, 到目标节点再换 rail. 源侧转发占源节点 NVLink 与目标 rail 网卡发送带宽; 目的侧转发占目的节点网卡接收与 NVLink. 选哪一侧转发会改变两个节点的局部冲突. PXN 的作用之一就是根据拓扑选择代理卡并聚合消息.

对均匀 all-to-all, 每张 GPU 发给本节点 7 张卡的份额为 $7/(N-1)$, 发给远端的份额为 $(N-8)/(N-1)$. 当 $N=32$ 时跨节点约 77.4%, 逻辑算法带宽可比物理网卡高约 $1/0.774=1.29$ 倍; 44 GB/s 物理有效带宽对应约 56.8 GB/s 逻辑带宽. 当 $N=128$ 时跨节点约 94.5%, 放大仅 1.058 倍, 对应 46.6 GB/s. 这与图 5 的规模越大、逻辑带宽越靠近网卡真实速度吻合.

ECMP 的冲突可以用球入桶近似. 假设某 leaf 到目的 leaf 有 $p$ 条等价上行, 同时有 $f$ 条大流独立哈希. 某条链路负载的期望为 $f/p$, 方差为 $f(1/p)(1-1/p)$. 当 $f$ 与 $p$ 同量级, 最大桶经常显著高于均值; 大流持续时间长, 一次坏哈希会贯穿整个 collective. 流数很多且每条很短时, 随机性才容易平均. LLM 集合通信恰好是少数、长寿命、同步的大流, 静态路由或逐包 AR 因此能明显优于 ECMP.

逐包喷洒也有代价. 多路径时延不同, 后发包可能先到, 传统可靠连接若要求按 PSN 顺序交付, 接收端会等待缺口, 形成 head-of-line blocking. 图 4 的理想网卡要求按目标地址直接放置并处理乱序, 本质上把「网络顺序」与「内存完成顺序」分开. RAR 再对特定地址区间做完成检测, 避免全局 fence 阻塞后续无关写入.

故障容量也能从端口余量判断. 1:1 下上行的 leaf 损失一条上行后, 剩余链路需要承接原流量, 理论过载因子为 $p/(p-1)$. $p=32$ 时约 3.2%, 看似很小; 路由若不能及时重排, 原来映射到故障链路的流会超时重传, 尾延迟远高于带宽损失. 多端口网卡跨平面绑定能把单端口故障转成带宽降级, 单端口 CX7 则需要节点内代理切换, 控制面恢复更复杂.

## 16. 训练吞吐数字如何闭合

表 4 给出每步 19.926 秒、每日 272.80B token. 两者相乘可还原 global batch:

$$
B_{\rm token}=272.80\times10^9\frac{19.926}{86400}
\approx62.93\times10^6.
$$

V3 配置的 batch 为 15,360 条、序列长 4096, 乘积正好 62,914,560 token. 差异来自吞吐和 step 时间的四舍五入. 这说明表 4 的每日 token 按完整训练 batch 计算, 未把 padding 或 loss mask 后的有效 token 单列扣除.

14.8T token 除以每步 62.91456M, 约 235,240 step. 若全部按 19.926 秒, 纯训练时间约 54.2 天; 乘 2048 张卡为 2.664M GPU 小时. 技术报告给出的预训练总成本约 2.788M H800 GPU 小时, 两者相差约 4.7%. 这部分可由长上下文阶段、学习率 warm-up、检查点、评测、吞吐波动与非稳态时间解释. 反算结果说明表 4 稳态吞吐与总成本同一量级, 但不能把单点 19.926 秒当成全程恒定.

表 4 的 causal TFLOPS 为 385、non-causal 为 432. 两种口径差 47 TFLOPS, 约 10.9%. causal 口径把注意力 $QK^\mathsf T$ 与 $PV$ 的上三角无效计算扣掉, non-causal 按完整矩阵计. 模型 FLOPs 利用率用 989 TFLOPS 左右的 BF16 峰值作分母, 得到 38.94% 与 43.73%. 实际核心 GEMM 采用 FP8, H800 的 FP8 峰值更高; 因此这个 MFU 衡量「等价 BF16 模型工作/硬件 BF16 峰值」, 不等于 Tensor Core 物理指令槽占用率.

把时间分解写成

$$
T_{\rm step}=T_{1F1B}+T_{\rm bubble}+T_{\rm other},
$$

表中 MPFT 的 1F1B 段约 13.95 秒、bubble 2.06 秒, 剩余约 3.92 秒包含填充/排空之外的调度、优化器、数据与未列细项. 若把 2.06 秒气泡除以总时间, 得 10.3%; 若以流水计算段 $13.95+2.06$ 为分母, 气泡比例约 12.9%. 不同材料写「bubble ratio」时可能使用不同分母, 必须连同口径给出.

通信完全被遮蔽时, 减少网络时间不会改变 step; 表 4 的 MPFT 与 MRFT 仅差 0.02 秒, 支持两种拓扑在该负载下都未进入主要瓶颈. 这不代表网络没有价值. 若序列缩短、micro-batch 减小或专家数增加, 每 token 计算下降而路由字节不同比例下降, $D+R$ 可能越过 $C$, 网络差异才进入关键路径. 硬件建议讨论的正是下一代模型扩展后这个交叉点.

MTP 的 1.8 倍推理加速也要按接受长度闭合. 若主模型每次验证 $m$ 个草稿 token, 平均接受 $a$ 个并额外确定一个拒绝位置, 每轮产出约 $a+1$ 个 token. 设草稿成本相对主模型为 $r$, 主模型一次验证成本为 $v(m)$ 个普通 decode step, 理想加速为

$$
S=\frac{a+1}{r+v(m)}.
$$

仅知道 1.8× 无法反推出接受率, 因为 $r$、验证并行度、batch 与内存带宽都会改变分母. V3 的 MTP 同时承担训练辅助目标与投机草稿, 公开加速数字属于具体部署配置.

## 17. 数值、路由与系统的交叉失效

FP8 误差会进入路由. 门控 logits 若有两个专家分数非常接近, 量化或有限精度 GEMM 的小扰动可能交换 Top-8 边界. 设第八与第九名间隔为 $\Delta=s_{(8)}-s_{(9)}$, 两者误差为 $e_8,e_9$, 当 $e_9-e_8>\Delta$ 时选择翻转. 单次翻转对模型输出可能很小, 对系统却会改变目标节点、消息大小与专家负载. 大量边界样本的误差相关时, 数值问题会放大成通信热点.

动态偏置也会缩小或放大 margin. 欠载专家的 $b_i$ 上升后, 它更容易进入 Top-8; 原始 affinity 仍决定组合权重, 所以刚越过边界的专家可能权重很小, 却照样产生一份完整 $d$ 维通信与一次专家计算. 从质量看这份专家影响有限, 从基础设施看成本没有按权重缩小. 可以统计「每字节有效门控质量」

$$
\eta_g=\frac{\sum_{x,i\in S_x}g_{x,i}}
{\sum_x |D(x)|d},
$$

观察负载均衡是否用大量低权重路由换取了均匀性.

网络拥塞反过来影响训练数值. 某些专家消息晚到会让整个 grouped GEMM 等待; 若系统采用超时丢弃或容量截断, 被丢 token 的分布可能与网络位置相关, 形成硬件诱导的数据偏差. V3 追求无 token 丢弃, 避开了这条直接路径, 仍会受到慢节点拖长 step、改变异步数据供给和故障恢复频率的影响.

DualPipe 使同一设备保存两个阶段, 一次设备故障同时丢掉模型两处状态. 检查点若按 rank 原样分片, 恢复映射必须重建双段归属、EP 专家分片和 optimizer shard. 网络拓扑变化后, 原来按 rail 优化的专家布局也可能不再均衡. 可恢复性因此属于调度设计的一部分, 不能只以稳态 bubble 评价.

PCIe 争用提供另一条交叉链. KV cache 从 CPU 搬入占 PCIe, EP RDMA 也穿过 PCIe, 两者重叠时 EP 尾延迟升高; DualPipe 或双 batch 原本用于遮住通信的计算窗口随之不够长, bubble 增加. 单独优化 KV 命中率可能增加大块搬运, 反而伤害同步敏感的 EP. Traffic class 与统一 I/O die 的意义在于给两类流量建立可控优先级和隔离.

诊断这类问题要同时保存四条时间序列: FP8 scale 与异常值比例、Top-$k$ margin 和专家负载、每 rail 字节与拥塞事件、每个 pipeline stage 的空闲时间. 若 loss spike 前先出现 scale 放大, 随后路由 margin 下降、某节点负载升高、对应 stage 等待变长, 因果链比单独看到一次网络尖刺更有解释力. 若顺序相反, 起点可能是硬件慢节点而非数值误差.

最终压力测试可人为注入三种扰动: 给一组门控 logits 加接近 FP8 舍入量级的噪声; 限速一条 rail; 让一个专家 GEMM 延迟 10%. 分别和联合注入后比较 step 尾延迟与 loss. 若联合影响明显超过三者单独影响之和, 说明系统处于耦合临界区, 平均负载下的独立组件基准会低估风险.

## 18. 从链路下界到端到端延迟

单层通信时间不能只用「字节/带宽」. 一次 dispatch 至少包含路由结果生成、按目的专家计数、前缀和确定槽位、token 打包、GPU 发起 RDMA、网络传输、接收端完成检测、按专家重排八个阶段. combine 再把方向反过来, 并多出同 token 多份专家输出的求和. 把固定启动项记为 $\alpha$, 每字节传输项记为 $1/B$, 本地重排带宽记为 $B_m$, 则

$$
T_d\ge \alpha_{\rm route}+\alpha_{\rm net}
+\frac{V_{\rm pack}}{B_m}+\frac{V_{\rm wire}}{B}
+\frac{V_{\rm unpack}}{B_m}.
$$

大 batch 时 $V/B$ 主导, 小 batch 时多个 $\alpha$ 主导. 所以 400Gbps 链路线速只能约束渐近斜率, 无法预测 128 token decode 的截距. 图 5 用 128MiB 以上消息测吞吐, 表 5 用小消息测链路延迟, 两者共同才能夹住真实 EP 的范围.

以每卡 128 token 为例, 未聚合时有 1024 个 token—专家副本. 假设每条 work request 固定控制开销仅 0.5 μs, 串行提交就要 512 μs, 已超过数据在线速上的传输时间. 按目的 rank 聚合后, 请求数上界接近 EP rank 数 128, 控制开销降到 64 μs; GPU 多线程直接提交又能把其中一部分并行化. 这解释了 IBGDA 对 decode 的价值主要在消息率与发起并行度, 对大块训练通信则主要受带宽限制.

combine 的完成条件比 dispatch 严格. dispatch 中某专家只需等属于自己的 token 到齐便能启动 grouped GEMM, 不必等所有专家; combine 中源 token 要等其八份专家输出全部返回才能形成最终向量. 设八条路径延迟为 $t_1,\ldots,t_8$, 单 token 完成时间是 $\max_i t_i$, 不是均值. 当每条延迟独立且有长尾时, 取最大值会系统性放大尾部. 节点限制把八份压到至多四个节点, 既省字节, 也减少独立故障域数量.

早启动能缩短屏障. 接收端每个专家知道预计 token 数后, 对已到齐的专家立即开始 GEMM; 网络继续输送其他专家. 若专家计算时间为 $c_i$, 到齐时间为 $a_i$, 整层专家阶段下界为 $\max_i(a_i+c_i)$. 将所有专家统一屏障后再算, 则是 $\max_i a_i+\max_i c_i$, 后者不小于前者. 公开 DeepEP 的布局展开、按专家计数与 grouped GEMM 接口正是为了让通信产物直接进入这种细粒度消费.

不过早启动会改变 GEMM 形状. 若一个专家的 token 分几批到达, 每到一小批就启动矩阵乘, kernel 启动和小矩阵低利用率可能比等待聚合更差. 最优策略取决于预计剩余 token、到达间隔与专家矩阵尺寸. 可以设阈值 $q$: 已到 token 达 $q$ 才启动, 之后余量再做一次尾批. $q$ 太小增加 kernel 数, 太大增加等待. 训练大 batch 与 decode 小 batch 的最优 $q$ 不同.

同理, 网络层面的多播和归约也有启动阈值. 交换机等齐多份 combine 数据再归约会占用片上缓冲; 不等齐就只能逐包转发, 失去节省接收字节的效果. EP 的目标集合随 token 改变、每组只有至多八份, 很难像固定 DP all-reduce 那样预留规则树. Insights 把它列为硬件方向, 不等于现有交换机能直接获得前文估算的 29% 收益.

端到端实验应给出一条延迟瀑布: 路由与计数、打包、发起、线上传输、到达等待、专家计算、combine 与解包各占多少. 再对每段报告可重叠区间. 若 profiler 只显示通信 kernel 与 GEMM 时间线重合, 却没有 NIC 计数器和完成事件, 仍无法判断重合时传输是否真正推进, 或通信 kernel 只是占着 SM 等待.

## 19. 哪些数字可以迁移到别的集群

模型固有量可以直接迁移: 隐藏维 7168、每 token 选择 8 个专家、MLA 每层缓存维度、61 层以及给定精度下的逻辑字节数. 它们由架构决定. 把 H800 换成其他 GPU 后, $Tkd b$ 仍是 dispatch 的逻辑载荷, $61\times576\times2$ 仍是论文 BF16 口径的 KV 字节. 只要模型配置不变, 这些乘法不变.

拓扑量只能在结构相同处迁移. 「至多四节点」来自训练路由约束, 不是任意 EP 部署的自然属性; 八平面来自每节点八卡八网卡的映射, 单卡多端口或不同 scale-up 域会改变 rail. 两层胖树端点上限由端口数公式决定, 实际无阻塞能力还取决于超卖比、路由与跨 rail 转发. 因而 MPFT 每端点成本和跨节点份数不能直接套到四卡节点、NVL72 或单 NIC 节点.

硬件性能量最难迁移. 120.96 μs、44 GB/s 有效网速、19.926 秒 step 与 20 个通信 SM 都绑定 H800、CX7、CUDA/PTX 内核、消息规模和并发调度. 新 GPU 的 Tensor Core 变快而网络不变时, 计算窗口缩短, 原本被遮住的通信会暴露; 网络升级而 CPU 门铃路径不变时, 小消息延迟仍可能不降. 按峰值 FLOPS 或链路线速做比例缩放会漏掉这个交叉变化.

数值量也要按硬件语义迁移. 同叫 FP8, 输入格式、scale 粒度、乘法精度、累加器尾数与 promotion 路径都可能不同. 训练稳定性来自整条链的组合, 不能从「支持 E4M3」推到「复现 V3 FP8 配方」. 最小核对项包括乘积精度、局部累加精度、每次提升覆盖的 K 长度、scale 的存储格式和反量化位置.

公开实现中的优化则分接口与性能两层. DeepEP 的 dispatch/combine 语义、DualPipe 对 $B_x/W$ 的拆分具有迁移价值; README 的带宽、SM 数与推荐 QP 数只对标明的版本和硬件成立. 复现实验应先检查语义结果与通信字节, 再调性能参数. 一开始追逐原仓库吞吐, 很容易把拓扑不匹配误判成实现错误.

可以用无量纲比值判断迁移后的瓶颈. 定义通信—计算比

$$
\chi=\frac{V/B_{\rm net}}{F/C_{\rm gpu}},
$$

$V$ 是每层网络字节, $F$ 是计算量. $\chi<1$ 时通信有机会被计算覆盖, $\chi>1$ 时仅靠重叠无法隐藏. 再定义启动—传输比 $\lambda=\alpha/(V/B_{\rm net})$, $\lambda\gg1$ 表示小消息受延迟控制. 比绝对的微秒和 GB/s 更适合跨硬件比较.

V3 的基础设施洞见由此落到一条稳定方法: 先从模型得到逻辑工作量, 再把路由约束映射成物理流量, 用拓扑求链路下界, 用调度求可重叠区间, 最终以 profiler 和计数器测剩余差值. 硬件换代只改变中间参数, 推导链保持不变.

迁移时还要保留同一组分母. 每 token 字节、每 GPU 字节、每节点字节和全局聚合字节经常混在一张性能表里; 算法带宽又可能把节点内副本计入有效载荷. 最简单的校验是同时列出 token 数、专家副本数、跨节点唯一目的数与 NIC 实际计数. 四项一旦对不上, 后续利用率与成本推导都应暂停. 这个检查对任何 MoE 集群都成立, 也能避免把节点内 NVLink 的贡献错算成网络超线速.

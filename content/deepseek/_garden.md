# 源神启动! DeepSeek

DeepSeek 被戏称为「源神」, 这个称呼多少带点玩笑, 却很贴切. 它开源的不只有模型权重: DeepSeekMoE, MLA, 无辅助损失负载均衡, FP8 训练, DualPipe, 3FS, DeepEP, DeepGEMM, FlashMLA, DSec, 一路从模型结构延伸到集群通信, 文件系统和 Agent 沙箱. 单独看其中一篇论文, 容易把它当成又一个局部改进; 把这些材料按时间和系统层次排在一起, 才能看见 DeepSeek 反复追问的是同一件事: 在硬件, 数据和训练预算已经给定时, 怎样把更多容量, 更长上下文和更多强化学习轨迹塞进可承受的成本里.

我喜欢 DeepSeek 的地方也在这里. 模型论文里的结构选择, 经常能在另一篇系统论文或一个开源仓库中找到工程后果: MoE 增加专家通信, 后面就有 DeepEP; MLA 压缩 KV cache, 后面就有 FlashMLA 和远端 KV 路径; Agent RL 需要海量可执行环境, 后面就出现 DSec. **模型能力和 Infra 在这里不是两份互不相干的材料, 而是同一组约束在不同层次上的回答.** 这座知识库要做的, 就是把分散在论文, 技术报告, README 和代码里的回答重新接回同一条技术线.

收录范围分成三类: 模型技术报告; 不以发布模型为目的的方法论文 (NSA, mHC, Engram, DSpark 等); 支撑训练和推理的系统论文与开源仓库 (Fire-Flyer, 3FS, DeepEP, DeepGEMM, FlashMLA, DSec 等). 从第一代语言模型一直读到后来的推理, 多模态和 Agent 系统, 可以追踪架构怎样改变计算与状态, Infra 又怎样反过来限定模型可以采用的结构.

每篇论文一个目录, 目录里两篇文章: `-bi` 是原文逐段中英对照, 难懂的地方插有疑惑块; `-analysis` 是读完全文和代码之后写的技术解析, 讲每个机制解决哪项成本, 怎么做, 代价多大, 实验数字在什么设置下得出. 开源仓库没有论文, 只写解析, 对照稿翻译仓库自带的设计文档.

## 1 收录范围与组织

### 1.1 四章的分法

第一章是模型技术报告, 从 DeepSeek LLM 到 DeepSeek-V4.1-Flash, 包括 MoE 主线 (DeepSeekMoE, V2, V3, V3.1, V3.2, V4), 推理模型 R1, 以及代码, 数学, 定理证明, 视觉语言, 统一多模态, OCR 等分支. **这一章目前有 24 个模型目录, 其中 16 个与模型库的 DeepSeek 家族重合**, 其余条目只在这个专题库收录. 两边各自维护, 便于在本库内部互相链接.

第二章是架构与算法论文. 这些论文不发布旗舰模型, 而是把某个机制单独拿出来做充分的消融: 原生稀疏注意力 NSA, 流形约束超连接 mHC, 条件记忆 Engram, 无辅助损失的负载均衡, 专家专精微调 ESFT, 以代码输入输出预测为训练信号的 CodeI/O, 推理时可扩展的生成式奖励模型 GRM, 以及投机解码框架 DSpark. 它们多数后来进了某一代旗舰模型, 读论文能看到机制在小规模实验里的原始形态和被舍弃的变体.

第三章是系统论文. Fire-Flyer AI-HPC 讲约一万张 PCIe A100 组成的 集群的软硬件协同设计, Insights into DeepSeek-V3 从硬件角度回顾 V3 的架构选择, DualPath 解决 agent 推理里 KV cache 存储带宽的瓶颈, DSec 讲支撑 agent RL 的沙箱平台, Spatiotemporal Composability 给 DeepSeek Harness 的插件系统提供形式化基础.

第四章目前收录五个开源仓库: FlashMLA, DeepEP, DeepGEMM, 3FS 与 smallpond. **目录清单只写已经完成解析的仓库**, 不把论文中出现过或计划补充的组件提前算作已收录内容. 这些仓库的设计信息散落在 README, 设计文档和代码注释里, 解析以代码为准.

### 1.2 相关主题

[llm-guide](../llm-guide/llm-guide.md) 讲机制本身: MLA 的矩阵吸收, GRPO 的目标函数, 稀疏注意力的一般设计空间. 本库讲 DeepSeek 在具体论文里做了什么选择, 在什么设置下测了什么数. 本库解析遇到需要完整推导的机制, 链接 llm-guide 的对应文章, 不在这里重复推导.

[模型库](../model-library/_garden.md) 按家族收录各家模型的技术报告, DeepSeek 只是其中一个家族. 本库第一章与模型库 DeepSeek 家族内容重合, 但本库另外收了方法论文, 系统论文和代码仓库, 模型库不收这些.

## 2 技术主线

### 2.1 稀疏化: 专家, 注意力, 记忆

DeepSeek 的论文有一条贯穿三年的主线: **把计算或存储做稀疏, 让总参数和上下文长度增长时, 每 token 的实际开销增长得更慢.** DeepSeekMoE 用细粒度专家和共享专家把 FFN 做稀疏; 无辅助损失的负载均衡去掉了平衡损失对主目标的干扰; V2 的 MLA 把 KV cache 压到低秩潜变量; NSA 和 V3.2 的 DSA 把注意力做成按块或按 token 选择; V4 的 CSA 与 HCA 把压缩和稀疏结合起来做百万 token 上下文; Engram 用确定性寻址的 N-gram 查表, 给稀疏增加了「**条件记忆**」这条轴.

按时间读这一组论文, 能看到同一个问题在不同层次上的解法: 先在 FFN 上做, 再在注意力上做, 最后把一部分本来由 FFN 承担的知识存储挪到可以放在主机内存的查找表里. 每一步都伴随着对应的 kernel 和通信库: MoE 对应 DeepEP 与 EPLB, MLA 对应 FlashMLA, DSA 对应 DeepSelect.

### 2.2 训练信号: 规则奖励, 生成式奖励, 自我验证

第二条主线是「**RL 的奖励从哪里来**」. DeepSeekMath 提出 GRPO, R1 用规则奖励在数学和代码上训出长思维链; GRM 论文把奖励模型做成先写评价原则再打分的生成式模型, 让奖励本身也能靠多采样来提升; DeepSeekMath-V2 训练证明验证器, 让模型对没有标准答案的证明题也能得到可靠的奖励; Prover 系列用 Lean 的形式化检查作为奖励.

这条线和基础设施直接相关. 规则奖励需要大量代码执行和沙箱, DSec 论文给出的数字是单个生产单元每天约 300 万个沙箱, 并发超过 38 万个. agent 场景下的长上下文推理又把 KV cache 的存储和带宽推到瓶颈, DualPath 与 V4.1-Flash 的 KV 压缩都在处理这个问题.

### 2.3 软硬件协同

第三条主线是「**按硬件约束设计模型**」. Fire-Flyer 论文讲在 PCIe A100 节点上怎样用 HFReduce 绕开受限的 GPU 到网卡 P2P 路径, 后续版本再用成对 NVLink Bridge 减少主机内存流量; Insights 论文把 V3 的 MLA, MoE 规模, FP8 训练, 节点限制路由逐条对应到 H800 的显存, 算力和互联带宽; DualPipe 让前向与反向的计算和 all-to-all 通信重叠; DeepGEMM 的 FP8 GEMM 处理 Hopper 张量核累加精度不足的问题. 这些论文和仓库放在一起读, 能解释 V3 的很多超参数为什么是那个值.

## 3 阅读路径

### 3.1 按主线读

第一次读这个库, 建议沿 MoE 主线按时间读: [DeepSeekMoE](./01-模型技术报告/deepseek-moe/deepseek-moe-analysis.md) → [DeepSeek-V2](./01-模型技术报告/deepseek-v2/deepseek-v2-analysis.md) → [DeepSeek-V3](./01-模型技术报告/deepseek-v3/deepseek-v3-analysis.md) → [DeepSeek-V3.2](./01-模型技术报告/deepseek-v3-2/deepseek-v3-2-analysis.md) → [DeepSeek-V4](./01-模型技术报告/deepseek-v4/deepseek-v4-analysis.md). 每读完一篇, 去第二章找它引入的机制对应的方法论文, 再去第四章找对应的仓库.

关心 RL 与推理模型的读者, 从 [DeepSeekMath](./01-模型技术报告/deepseek-math/deepseek-math-analysis.md) 的 GRPO 开始, 接 [DeepSeek-R1](./01-模型技术报告/deepseek-r1/deepseek-r1-analysis.md), 再读第二章的 GRM 和第一章的 Math-V2 与 Prover 系列.

### 3.2 按问题查

想知道某个数字从哪里来, 先查对应 analysis 的实验一节, 那里写了表号和实验设置; 想核对原文措辞, 打开同目录的 bi 稿, 页标记 `<!-- page k of N -->` 对应 PDF 页码. 想看工程实现, 第四章各仓库的解析给出了关键文件的 GitHub 链接.

各章的完整清单见章首页: [模型技术报告](./01-模型技术报告/01-模型技术报告.md), [架构与算法](./02-架构与算法/02-架构与算法.md), [基础设施](./03-基础设施/03-基础设施.md), [开源仓库](./04-开源仓库/04-开源仓库.md).

### 3.3 从论文走到实现

模型报告里出现的新机制, 通常能在另外三章找到更细的材料. V3 的无辅助损失负载均衡对应第二章的独立论文, 专家通信对应第四章的 DeepEP, FP8 训练对应 DeepGEMM, 整体选择又能在第三章的硬件回顾中找到资源约束. V2 的 MLA 可以沿 FlashMLA 走到 kernel, 再沿 DualPath 走到长上下文服务. 这种跨章阅读能区分架构减少了多少理论开销, 实现拿到了多少硬件吞吐, 系统最终保留了多少端到端收益.

强化学习路线也跨越四章. DeepSeekMath 给出 GRPO, R1 展示规模化训练方案, GRM 扩展开放问题的奖励来源, CodeI/O 提供可执行数据, DSec 负责隔离执行环境. **奖励算法决定模型优化什么, 沙箱与验证器决定反馈是否可信, 推理系统决定单位时间能够产生多少轨迹.** 只读其中一层, 很难判断能力提升来自训练目标还是样本供给.

## 4 共同的阅读尺度

### 4.1 能力数字要带着条件

本库保留模型规模, 数据范围, 上下文长度, 采样预算和评测设置, 因为这些条件会改变数字含义. 推理模型增加 TestingTime 采样可以提高通过率, 形式化证明增加搜索预算也会提高累计成功率, 系统基准改变 batch 或拓扑则会改变吞吐. analysis 会把结果放回对应表格和设置, bi 稿用于核对原文的限定语.

版本之间比较时, 先确认底座, 后训练和评测协议是否一致. V3.1, V3.1-Terminus 与 V3.2 的名称接近, 但目标并不完全相同; Coder, Math, Prover 和 VL 各自使用专项数据与任务, 不宜用单一总分排出一条能力序列. 本库更关心机制在什么条件下有效, 以及条件变化后哪些结论仍然成立.

### 4.2 成本分成计算, 状态与通信

DeepSeek 技术路线反复调整三类成本. MoE 减少每个 token 激活的参数计算, 同时增加专家通信; MLA 和稀疏注意力减少长上下文的状态或读取量; FP8, DeepGEMM 与 FlashMLA 提高具体计算路径的硬件效率. 3FS, DualPath 和 DSec 则把存储与外部执行纳入整条服务链.

遇到「**更高效**」的结论时, 可以定位它改变哪一项成本, 是否把压力转移到另一项资源, 以及端到端实验有没有覆盖转移后的瓶颈. 这套尺度贯穿四章, 也决定了推荐读法: 先从模型报告确认目标和结果, 再到方法论文看变量控制, 到系统论文看资源约束, 最后用仓库接口确认实现边界.

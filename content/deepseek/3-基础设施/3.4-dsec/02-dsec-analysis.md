# DSec: DeepSeek 给 Agent RL 供环境的沙箱平台

材料是 DeepSeek-AI 与清华大学的系统论文 *DeepSeek Elastic Compute (DSec): A Sandbox Infrastructure for Effective Agentic Training at Scale* ([arXiv 2609.22978](https://arxiv.org/abs/2609.22978), 2026-09-19, cs.DC, 31 页, 正文 24 页). 论文说从 DeepSeek-V3.2 到 V4.1, RL 训练和评测用到的全部沙箱负载都跑在 DSec 上. 平台本身没有开源, 开源的只有 microVM 存储路径用到的 Rust 版 OverlayBD 与 ublk 库, 放在 [kvcache-ai/AgentENV 的 storage 目录](https://github.com/kvcache-ai/AgentENV/tree/main/storage/overlaybd). DSec 此前在 [V4 解析](../../1-%E6%A8%A1%E5%9E%8B%E6%8A%80%E6%9C%AF%E6%8A%A5%E5%91%8A/1.8-deepseek-v4/02-deepseek-v4-analysis.md) 对应的报告 §5.2.5 和 [V4.1-Flash 解析](../../1-%E6%A8%A1%E5%9E%8B%E6%8A%80%E6%9C%AF%E6%8A%A5%E5%91%8A/1.9-deepseek-v4-1-flash/02-deepseek-v4-1-flash-analysis.md) 对应的报告 §5.1.3 里各有两页左右的介绍, 这篇论文是第一次完整交代架构, 生产负载测量和机制对照实验.

Agent RL 的 rollout 需要成千上万个隔离、有状态、互不相同的真实环境. 这些环境要在几秒到几分钟内成批就绪, 在 CPU 几乎空闲时长时间占用内存, 还要防住会主动寻找漏洞的模型. 一般的 serverless 平台假设镜像少、复用高、函数短命; Kubernetes 一类编排器强调强一致放置. DSec 针对的正是这组不同的负载条件. Agent RL 的训练流程见 [Agentic RL 训练](../../../llm-guide/13-Agent/13.4-Agent训练与进化/13.4.1-AgenticRL训练/13.4.1-AgenticRL训练.md), 沙箱运行时的一般概念见 [运行时环境与沙箱](../../../llm-guide/13-Agent/13.3-Agent系统工程/13.3.4-运行时环境与沙箱/13.3.4-运行时环境与沙箱.md).

## 1. 负载画像: Agent 沙箱和普通执行服务差在哪

**突发, 长寿, CPU 稀疏**

论文 §1 列了七条负载性质, §4 用 2026 年初一周的生产数据给其中几条配了测量, 测量只覆盖容器和 microVM, 因为两者占了绝大多数实例和资源. 第一条是突发. Fig. 2 是每个任务创建的沙箱数分布: 容器任务中位数 2,528 个, p90 为 7,969, p99 为 16,388; microVM 任务中位数 352, p99 为 4,044; 最大的生产作业一次申请 32K 个沙箱. 这些请求集中在很短的窗口里到达, 原因很直接: 训练或评测批次要等环境就绪才能开始交互, 任何一个沙箱慢, 整批的有效交互都往后推. 平台对此给出的能力是每秒 5,000 次以上的创建, 按这个速率, 一个 32K 的作业光创建就要约 6.4 秒, 这还没算环境准备.

第二条是长寿和 CPU 稀疏同时存在. Fig. 3 把一个沙箱的一生分成准备, 工具调用, 测试三段: 准备段装依赖, 起工具, CPU 和 I/O 集中; 工具调用段模型生成一步, 沙箱执行一步, CPU 是一串短脉冲, 中间是等模型的空档; 测试段跑验证, 资源需求再短暂升高. Fig. 5 给出按申请量归一化的用量分布, 约 90% 的容器和 microVM 平均 CPU 用量不到申请量的 5%. Fig. 7 给出寿命分布, 容器中位寿命 17.4 分钟, microVM 15.5 分钟, p99 分别是 231.5 和 213.9 分钟; CDF 在约 120 分钟处有一个明显的台阶, 跳到 0.9 以上, 论文没有解释, 从形状看像是部分任务带了 2 小时左右的寿命上限. 准备段的开销按突发规模成倍放大, 工具调用段的内存则按寿命持续占用, 这两件事决定了后面两类机制: 准备路径要便宜, 驻留内存要能共享和回收.

### 1.1. 镜像: 量大, 扇出低, 用到的少

第三条是环境多样. §4.2 把沙箱内容拆成三部分: 基础镜像 (操作系统和语言运行时, 例如 Ubuntu 加 Python 3.10), 工作区 (任务的代码仓库和专属依赖), 工具包 (DeepSeek Harness 这类频繁更新的 scaffold 和命令行工具). 一个生产周里容器后端用了 11,266 个基础镜像和 102,171 个工作区, microVM 后端只有 2 个共享基础镜像, 却有 53,590 个工作区和 4,889 个快照; 工具包共 103 个; 67.8% 的沙箱在基础镜像之外至少还要挂一个工作区或工具包. Tab. 2 给出活跃制品合计 82.8 TB 加 50.9 TB, 约 134 TB, 远超单节点能放下的量.

扇出 (一个镜像在同一任务内被多少个沙箱用) 很低. Fig. 8 统计了 150 多万个容器和 39 万个 microVM: 容器镜像扇出中位数 3, p90 为 28; microVM 镜像中位数 1, p90 为 3. 中位数为 1 意味着大多数 microVM 镜像在一个任务里只被一个沙箱用一次, 节点本地缓存几乎没有命中的机会. 再加上 Tab. 3 的访问比例: 抽样的五种语言容器镜像, 运行时实际读到的数据只占镜像大小的 4.2% (JavaScript, 9.6 GB) 到 13.3% (Go, 4.1 GB), Java 镜像 12.1 GB 只读 9.2%, 约 1.1 GB. 三项叠在一起, 结论是全量预拉镜像既拉不过来, 拉了也大多白拉, 预热只是把这笔开销挪到前面.

**生产规模的几个数怎么读**

§2.4 给出一个规模单元的配置: 近 160 个 CPU 节点, 30K 核, 约 250 TB DRAM, 管理 PB 级的层和镜像; 典型一天服务约 300 万个沙箱, 峰值并发约 38 万, 创建速率超过每秒 5,000 个. 生产中部署了多个这样的单元, 共用一套 3FS. 把峰值平均到资源上: 每核约 12.7 个沙箱, 每节点约 2,400 个, 每个沙箱约 0.66 GB 内存. 超卖倍数论文正文没有给, 若按 Listing 1 的规格 (4 核, 4096 MB) 估算, 38 万个沙箱申请约 152 万核, 是物理核的约 50 倍, 申请内存约 1.52 PB, 是物理内存的约 6 倍. 这只是按示例规格推的量级, 实际申请规格文中没有统计; 它说明的是 CPU 可以大幅超卖, 内存只能超卖几倍, 所以 §5.2 的内存机制才是密度的主要约束.

§1 和 §4.3 报告生产中单节点稳定运行过至少 3,200 个容器或 800 个 microVM, 表示已经达到的运行点, 并未给出硬上限. Fig. 6 则记录某个节点一天内的曲线, 峰值为 1,048 个容器和 524 个 microVM. 用 Little 定律检查日服务量和并发量: 平均并发 $L=\lambda W$, 日均到达率 $\lambda\approx 3\times10^6/86400\approx 35$ 个/s. 若平均寿命 $W$ 暂取中位数 17.4 分钟, 平均并发约 3.6 万, 与 38 万峰值相差一个数量级. 文中没有报告平均寿命; Fig. 7 的分布明显右偏, 均值会高于中位数, 但 p99 约为 3.9 小时. 现有数据更符合突发负载叠加形成瞬时峰值的情况, 无法据此计算日均并发.

**平台结构: 四类后端与一条请求路径**

**四类后端, 一个不做语义统一的 SDK**

Tab. 1 把四类后端放在同一组维度上比较. FnCall 跑短小无状态的任务 (OJ, 编译, GPU kernel), 任务在预先创建好的 CPU 或 GPU 容器里执行, 不用每次准备环境; 容器是软件工程和工具调用的主力, 启动快, 密度高; Firecracker microVM 给安全敏感任务和 computer-use 一道 VM 边界, 代价是更高的内存开销和更慢的启动; 完整虚拟机用 QEMU 跑 Android, 商用操作系统和需要图形渲染的负载, 开销最高. 生产中容器和 microVM 在实例数和资源上占大头, FnCall 用少量常驻环境服务大量调用. 选哪个后端由调用方决定, §2.1 明确写了 libdsec 有意不做覆盖所有后端的完整语义抽象: 统一的是访问路径和操作模型 (创建, 执行 shell, 取输出, 停止), 启动成本, 隔离边界, 文件系统语义和操作系统能力都不统一.

Listing 1 是一个最小的容器会话, 请求里写明镜像, 4096 MB 内存上限, 4 核 CPU 上限, `ttl_running_stop=300` 的空闲超时, `network_rules={"npm": False, "pypi": True}` 的网络规则和 `init_user="root"`. 网络规则按域名或镜像服务组织, 由 edge 翻译成每沙箱的 eBPF 过滤规则 (§6.5); `root` 用户说明沙箱里的进程默认有 root 权限, 所以后面的访问控制必须对 root 也生效. GPU FnCall 用于算子基准测试, §7 给了三项机制: 用 NVIDIA MIG 把一张 GPU 切成相互隔离的实例并发跑基准; 编译交给 CPU FnCall, 只把产物交给 GPU FnCall, 不让编译占 GPU; 预热的 Python 进程池事先导入库, 请求到了直接跑算子. 对性能不敏感的任务还有共享 GPU 模式.

**请求路径: 控制面无状态, 准入权在节点**

![](./images/p06-figure-1-dsec-architecture-each-proxy-mediates-communication-between.jpg)
> 图 1: DSec 的整体架构, 左侧是集群级服务, 右侧是单节点上的沙箱运行时与四类后端, 底部是 3FS 上的两种镜像格式, 原文 Figure 1.

图 1 解析: 左栏是集群级服务, 红色箭头是管理请求 (创建, 删除, 改配额), 依次经 IAM, API Server, 放置引擎, 放置引擎从 Watcher 拉机群视图; 蓝色箭头是数据请求 (执行命令, 读写文件, 流式 I/O), 经 API Server 直达节点上的 Edge, 再经 Aether 到 Chronus. 右栏下方的后端框里, FnCall 和容器都画在 QEMU VM 框内, microVM 和完整虚拟机没有这个框; 只有容器, microVM, 完整虚拟机带 Proxy (即 aether), FnCall 没有. 虚线框标出 AppArmor 加 eBPF 的隔离范围覆盖容器, microVM 和完整虚拟机. 最底层 3FS 上分别放 EROFS 镜像和 OverlayBD 镜像. 图里没有画云上虚拟机 (§3.4) 和 worker 容器 (§6.2).

请求路径上每一层都尽量不存状态. apiserver 是 GPU 训练集群与沙箱集群之间唯一允许的网络通道 (两侧网络隔离, 因为沙箱跑不可信代码还能访问外网); 它不保存每沙箱状态, 沙箱 ID 里编码了所属的 edge, 任何一个 apiserver 实例拿到 ID 就能直接转发, 入口层可以随意加实例. 放置引擎分两步: 先过滤出健康且具备所需后端和硬件 (例如 GPU) 的节点, 再随机抽 $k$ 个节点选负载最低的, 即 power-of-$k$-choices (Mitzenmacher, 2001). 只看全局最空的节点, 一批并发请求会同时扎向同一台机器; 随机抽样把这种扎堆打散. 放置引擎的每个实例还把自己最近做出, 尚未出现在 watcher 快照里的放置叠加进本地视图, 不用跨实例协调就能把在途负载算进去. watcher 定期探测各 edge 的健康, 统计按 edge, 用户, 任务划分的运行中沙箱数, 重启后重新轮询即可重建视图. 放置引擎和 watcher 都不需要持久化状态.

最终的准入权在 edge. 放置引擎的视图总是滞后的, 多个实例之间又不同步, 所以 edge 收到创建请求时再查一次本地容量, 资源压力到临界就拒绝, 调用路径改选别的节点. 这套设计在 V4.1-Flash 报告 §5.1.3 里有一句更直白的概括: 用全局强一致换可扩展性, 只要每个节点强制本地安全约束, 沙箱放置只需要最终一致, 并且明确说没有用 Kubernetes. 代价是偶尔的拒绝和重试, 以及放置质量依赖采样; §7 还提到按用户隔离可以限制资源尖峰或内核级故障的波及范围, 代价是节点级密度下降. 可靠性方面, API 网关, 软件包镜像站和控制面入口用 BGP 加 ECMP 做负载均衡, 实例掉线后交换机几秒内撤掉路由; 集群级服务多实例部署, 并定期整集群重置, 验证基础设施即代码能从零重建全部服务. 论文强调这一点的理由是辅助服务一旦宕机, Agent 就会任务失败, 坏掉的是奖励信号.

### 1.2. 沙箱内部与云端扩容

edge 每节点一个, 负责容器, microVM, 完整虚拟机和 FnCall 的创建, 创建时准备存储, 施加 eBPF 网络策略, 启动运行时, 还协调磁盘和内存快照, 在沙箱停止或 TTL 到期时释放本地资源. 沙箱里跑两个组件. aether 是每沙箱一个的代理, 与 edge 之间用 Unix domain socket (Linux 容器) 或 vsock (虚拟机) 通信, 通道一关 edge 就把沙箱标为失败; 它按操作带的终端会话标识找到或创建对应的 chronus. chronus 是一个 shell 会话, 提供命令执行, 文件操作, HTTP 请求和流式 I/O, 一个沙箱里可以有多个. 这两个组件让 libdsec 对容器和虚拟机给出同一套接口, 也正是 §6.4 里 Agent 攻击的对象: 伪造发给 chronus socket 的 RPC, 翻 chronus 日志, 覆盖 chronus 会调用的 `/bin/bash`.

容器和 FnCall 不直接跑在裸机上, 每台物理机先起 QEMU/libvirt 虚拟机, 容器跑在虚拟机里, 虚拟机提供独立的内核和网络栈, 是不可信容器与裸金属之间多出来的一道边界. 这和 §2.2 「容器共享宿主内核」的说法要对着读: 容器共享的是所在 worker 虚拟机的内核. V4.1-Flash 报告补充了这一层的用法: 用硬件 sub-NUMA 分区, 每个 worker 虚拟机绑一个 NUMA 域, 容器的 CPU 和内存限制在该域内, 在激进的内存超卖和内核锁竞争之间取平衡, 单物理节点的活容器数从约 1,000 提到 2,500 以上. §3.4 的云端扩容只服务容器: 生产访问 trace 显示一个去重后 30 TB 的 EROFS 镜像集覆盖了 70% 容器任务访问到的文件, 这个集合离线同步到云上的分布式文件系统, 镜像依赖全部落在集合内的容器任务才可上云, 云虚拟机复用本地的容器运行时和 EROFS 加载路径. 本地利用率超过 80% 时卸载一部分合格请求, 一个规模单元配 200 台云虚拟机, 吸收约 30% 的峰值溢出. 剩下 70% 的溢出怎么处理, 论文没有说.

**环境分层与基于 3FS 的按需加载**

**三类制品各自版本化: overlayfs 叠层与 EROFS**

![](./images/p14-figure-9-overview-of-the-core-system-mechanisms-ls.jpg)
> 图 2: DSec 核心机制总览, 左侧是容器的 CPU QoS 与多设备 EROFS, 中间是可组合的工作区和工具包层, 右侧是 microVM 的内存优化, 底部是 3FS 上的 EROFS 层与 OverlayBD 镜像, 原文 Figure 9.

图 2 解析: 四种底色对应四项机制, 绿色是可组合层 (§5.1), 蓝色是 CPU QoS (§5.2), 黄色是内存优化 (§5.2), 灰色是按需加载 (§5.3). 中间的 WorkSpace 与 Toolkit 两列同时接到左边的容器和右边的 microVM, 表示两类后端共用同一套分层制品; 容器经 dockerd 落到 3FS 上的 EROFS 层, microVM 经宿主机磁盘镜像落到 OverlayBD 镜像. 容器一侧的多设备 EROFS 把 Meta 与 Data Blocks 分开画, 只有数据块按需从 3FS 读. 图里没有画可写层, 也没有画 FnCall 和完整虚拟机, 这两类后端不走这几项机制.

单体镜像的维护成本在 §4.2 用复杂度表示. 设平台有 $M$ 个基础镜像, $N$ 个工作区, $K$ 个工具包, 三者融成一个 OCI 镜像时, 升级 $m$ 个基础镜像要重建它们与工作区的全部组合, 代价 $O(m\cdot N)$; 工具包也和工作区融在一起, 升级 $k$ 个工具包的代价是 $O(k\cdot N)$. 代入一周的生产数, 容器后端 $N=102{,}171$, 工具包 103 个, DeepSeek Harness 这类工具包又更新得勤, 单体方案下每升级一个工具包, 需要重建的镜像数上界在十万量级. 分层之后, 升级 $m$ 个基础镜像只重建这 $m$ 层, 升级 $k$ 个工具包只重建这 $k$ 层, 代价降为 $O(m)$ 和 $O(k)$.

![](./images/p11-figure-4-impact-of-upgrading-toolkit-t1-under-two.jpg)
> 图 3: 升级工具包 T1 时两种打包方式的差别, 左为单体镜像, 每个含 T1 的镜像都要整体重建; 右为可组合层, 只更新 T1 一层再与已有的基础镜像层和工作区层组合, 原文 Figure 4.

组合靠 overlayfs 完成. 多个只读 lowerdir 叠在一起时, 内核给出一棵合并后的目录树, 各层文件共存, 同名文件按层的优先级取上层的版本; 最上面一个可写 upperdir 吸收运行时的全部写入, 下面的只读层不受影响. DSec 改了 dockerd, 在创建容器时把预先挂好的 EROFS 层路径插进 lowerdir, 放在最上面的 lower 位置, 改动只有 30 行 Go (§7). 叠放顺序是基础镜像在底, 工作区居中, 每个工具包依次往上叠, 所以同名文件的优先级是工具包高于工作区, 工作区高于基础镜像. §4.2 否掉的两种做法也由这套语义解释: 每个沙箱启动时解 tar.gz, 重复的解压和写盘在突发时集中出现, 会让启动超时; bind mount 会整个遮住目标路径, 而工作区和工具包需要的是把文件追加进已有目录树. 严格只读的挂载还会和往自己安装目录里写文件的工具冲突, 例如 Python 生成 `__pycache__`, 这类写入在 overlayfs 下落到 upperdir.

层用 EROFS 存. 已发布的层不再变, EROFS 是专为只读数据设计的文件系统, 不需要 ext4, XFS 那类与写入相关的元数据维护, 盘上布局更紧凑; 它支持压缩, 而且压缩后仍能随机访问, 读一个文件只解压覆盖这段数据的压缩块. tar.gz 是顺序流格式, 必须从头解到尾, 这一点决定了第 3.4 节的对照结果. microVM 也用同一套分层模型: 基础镜像和工具包打成独立版本化的 EROFS 镜像, 以只读块设备交给 guest, guest 里的根文件系统是 overlayfs, lower 是这些 EROFS, upper 是一块 ext4 可写盘上的目录. 挂载数量多了也有开销, DSec 离线把大小在阈值 (文中举例 3 GB) 以内的连续层合并成一对元数据加数据的 EROFS 镜像, 并保留 overlayfs 的 whiteout 语义来表示删除; 挂载用 EROFS 的 file-backed 模式, 省掉 loop 设备那一层块映射. 合并的对象从上下文看是同一镜像内部的连续 OCI 层, 文中没有说合并是否会跨越基础镜像, 工作区, 工具包三者的边界; 如果会跨越, 升级工具包就要连带重做合并, $O(k)$ 的结论要打折扣.

## 2. 内存与 CPU 的高密度机制

镜像数据放在 3FS 上. 3FS 原本承载训练数据加载与 checkpoint, 架构, CRAQ 复制和客户端见 [3FS 技术解析](../../4-%E5%BC%80%E6%BA%90%E4%BB%93%E5%BA%93/4.1-3fs/02-3fs-analysis.md). DSec 选它是为了复用已有存储, 不再单独部署一层镜像分发系统; 常见的做法是镜像仓库加 P2P 分发, 例如 FaaSNet 和 Dragonfly. 代价是要迁就 3FS 的性能形状: 大块顺序读写吞吐高, 小块随机 I/O 差. §7 写明 CPU 节点通过 FUSE 客户端访问 3FS, 沙箱里的进程也不可能改写成调用 USRBIO 零拷贝接口. 3FS 设计说明给过 FUSE 路径的上限, 每秒约 40 万次 4 KiB 读, 单次请求默认最大 1 MB, 原因是内核 FUSE 的请求队列由一把自旋锁保护. 因此在 FUSE 路径上, 吞吐只能靠把请求做大来换.

由此 §5.3 立了三条原则. 第一, 写留本地: 沙箱的写入不规则, 日志一类的小写频繁, 可写层放在节点本地盘, 完全避开 3FS 的小写惩罚. 第二, 读按需且成批: 只读镜像数据只在被访问时才从 3FS 取, 并借助内核 readahead 把相邻块合成大请求. 第三, 元数据尽量本地: 元数据访问多是小读, 镜像格式允许时把元数据和数据分开, 元数据预先下到本地. 容器路径用 EROFS 的多设备模式实现第三条, 元数据设备放在 worker 本地盘, 数据设备留在 3FS, 路径查找和目录遍历都不产生远程 I/O. Nydus 的格式与 EROFS 兼容, 同样把元数据和数据 blob 分开并懒加载, 区别在于它的数据经 fscache 或 FUSE 一类用户态后端从镜像仓库或对象存储取; DSec 的数据直接留在 3FS, 由 EROFS 走内核的 buffered I/O 读出.

§7 给了存储侧的配置: 每台 3FS 存储服务器 20 块 15 TB SSD, 2 块 400 Gbps RDMA 网卡, 「数十台」存储服务器支撑数十万核的 CPU 集群. 按此每台裸容量 300 TB, 网卡上限约 100 GB/s; 若「数十台」取 20 到 90 台, 裸容量在 6 到 27 PB, 与 §2.4 「PB 级的层和镜像」量级相符, 副本数文中没有给出. 启动突发对 3FS 的带宽压力文中也没有给出, 可以从 Tab. 3 推一个量级: 五种语言镜像在运行时读到的数据量在 $6.0\times6.0\%\approx0.36$ GB (Python) 到 $12.1\times9.2\%\approx1.11$ GB (Java) 之间. 一个 32K 沙箱的作业若每个沙箱读 0.36 到 1.11 GB, 合计约 12 到 36 TB; 以 20 台存储服务器的网卡总量 2 TB/s 计, 全部读完需要 6 到 18 s. 这个推算忽略了同镜像沙箱之间的页缓存共享, 也忽略了请求分散在作业整个准备阶段, 实际峰值带宽会更低; 它说明的是按需加载让 3FS 带宽不再是突发启动的瓶颈, 若全量拉取, 数据量还要乘上约 8 到 24 倍.

另外, 多个规模单元共用同一套 3FS (§2.4). 这让镜像只存一份, 也让 3FS 成为所有单元的共同依赖, 论文没有讨论 3FS 降级或故障时沙箱启动和运行会受什么影响.

### 2.1. microVM 路径: OverlayBD, ublk 与 256 KiB 块缓存

容器那套 EROFS 加 overlayfs 的栈不能原样搬进 microVM. 原因有两条: Docker 的 overlay2 驱动不能把数据目录放在 overlayfs 上, 而 Docker-in-microVM 的负载需要在 guest 里跑 Docker; 把宿主机上挂好的文件系统经 virtio-fs 导出给 guest 本来可行, 但 Firecracker 不支持 virtio-fs. 所以 microVM 的只读基础镜像层和工具包层仍然用 EROFS, 可写的 ext4 盘则由 OverlayBD 提供, 其中包括一块直接挂在 Docker 数据根目录上的独立磁盘. OverlayBD 来自阿里的 DADI (ATC 2020), 是块级的分层镜像格式, DSec 用 ublk 把它暴露成块设备. ublk 是基于 `io_uring` 的用户态块设备框架, 块请求由用户态守护进程处理. 块级路径带来三项能力: 读按需从远端取, 写落本地, 支持增量磁盘快照, 快照时不必把改过的文件重新打包成 EROFS. 第三项是 `pack_diff` (§6.1) 能把交互会话直接存成环境的前提.

代价在元数据. EROFS 多设备模式能把元数据单独放到本地, ext4 的元数据却嵌在块镜像里, inode 表, 目录块的读取都会变成远程小读. DSec 的缓解办法是以 256 KiB 为单位从远端取 OverlayBD 数据, 并存进本地文件系统上的二级缓存, 块从页缓存里被淘汰后仍在本地, 不必再从 3FS 取. 开源的 [kvcache-ai/AgentENV 存储代码](https://github.com/kvcache-ai/AgentENV/tree/main/storage/overlaybd) 与此对得上: `storage/overlaybd/src/backend/cache/mod.rs` 里 `DEFAULT_BLOCK_SIZE` 为 256 KiB, 默认缓存容量 4 GiB, 占用到 90% 触发淘汰, 每秒检查一次, 最多 128 个块同时回填; `full_file_cache/cache_store.rs` 先把请求按 256 KiB 对齐, 对缺失的块从远端回填, 再从 mmap 的本地缓存文件里拼出结果; `storage/ublk/src/ctrl.rs` 把单个 ublk 请求的缓冲上限也设成 256 KiB, 与缓存块对齐. 按这个块大小, 一次 4 KiB 的元数据读最多带出 64 倍的数据, 换来的是相邻的 inode 和目录块大概率落在同一块里, 后续读命中本地.

这个仓库要分清边界. AgentENV 整体是另一个面向 Agent RL 的沙箱平台, DSec 只用了其中 Rust 版 OverlayBD 和 ublk 库, 仓库 README 里的其他数字不能算到 DSec 头上. 远端后端有 `local`, `tar`, `oss`, `registryfs_v2` 和 `switch`, 对应 §7 说的「3FS, OSS 与镜像仓库」; 仓库里没有 3FS 专用代码, 3FS 以 FUSE 挂载路径的形式走 `local` 后端. 仓库里还有一套论文没有提的启动预取: `ublk/src/impls/startup_pack_recorder.rs` 在快照恢复时记录首次访问的 4 KiB 页序列, `startup_pack_task.rs` 下次恢复时按这份清单成批预取, 注释给出的经验值是本地命中约 0.1 ms, OSS 回填约 20 ms. DSec 生产中是否启用这套预取, 文中没有给出.

**内存与 CPU 的高密度机制**

### 2.2. microVM 的两处内存浪费与 virtio-pmem DAX

第 1.3 节的换算说明, CPU 可以超卖几十倍, 内存只能超卖几倍, 所以高密度先是内存问题. §4.3 指出 microVM 有两处浪费. 第一处是页缓存重复: 镜像数据经虚拟块设备读进 guest 时, 宿主机的页缓存存一份, 每个 guest 自己的页缓存再存一份, 同一节点上一百个 microVM 读同一个基础镜像, 同样的数据在内存里最多出现一百零一份. 第二处是空闲页不归还: guest 释放的页留在 guest 的伙伴分配器里, 不显式报告宿主机就不会回收; 而沙箱申请的内存普遍大于实际用量, guest 内部没有内存压力, 不活跃的页也不会被回收. 两处浪费都随寿命累积, 第 1.1 节的中位寿命 15.5 分钟, p99 超过三小时, 使它们直接限制了 microVM 的超卖倍数.

针对第一处, DSec 用 virtio-pmem 加 DAX. virtio-pmem 把宿主机上的一个文件呈现为 guest 里的持久内存设备, DAX (direct access) 让 guest 文件系统绕过自己的页缓存, 文件访问直接映射到宿主机提供的页上; 同一节点上读同一镜像的 microVM 因此共享宿主机页缓存里的一份. 代价有两项. 一是冷访问要同步处理缺页, 建立映射并把后端数据准备好, 而走 buffered virtio-blk 时 guest 可以做 readahead 和批量块 I/O. 二是 guest 要为整个 pmem 地址范围分配 `struct page` 元数据, 每 4 KiB 页对应 64 字节, 比例为

$$
\frac{64\ \text{B}}{4096\ \text{B}}=\frac{1}{64},
$$

128 GB 的 pmem 设备因此要占 2 GB 的 guest 内存. 这一项决定了 pmem 只能用在小盘上: 生产中只对只读的 EROFS 基础镜像层和工具包层开 virtio-pmem, 可写的大盘不用. 只读层恰好也是跨沙箱共享最多的部分, 收益最大; 可写层每个沙箱各不相同, 共享无从谈起, 不值得付元数据的代价.

**DAMON 加 balloon 空闲页报告**

针对第二处浪费, DSec 把 virtio-balloon 的空闲页报告 (free-page reporting, FPR) 和 DAMON 组合使用. FPR 的流程是 guest 定期扫描伙伴分配器, 把空闲页报告给宿主机 hypervisor, 宿主机用 `madvise(MADV_DONTNEED)` 释放对应的物理内存. FPR 默认只报告 order-9 的空闲块, 即 4 KiB 基页下连续 2 MiB 的区域, 阶数可由内核参数调整. 这个粒度带来一个问题: guest 里没被访问的冷文件页零散分布, 它们只要还在页缓存里, 就会把 2 MiB 的块切碎, 凑不出可报告的大块. DAMON 是 Linux 里基于采样的内存访问监测框架, 定期采样页的访问位, 找出超过设定年龄仍未被访问的冷文件页, 经内核回收路径把它们逐出. 被逐出的页回到伙伴分配器, 合并成更高阶的空闲块, 满足 FPR 的条件. DAMON 负责腾出连续的空闲块, FPR 负责把这些空闲块还给宿主机, 两步缺一不可. 配置全部在 guest 内核参数和 sysfs 上完成, 不改内核 (§7).

CPU 方面, pmem 把瞬时 CPU 峰值从 26.5% 抬到 41.4%, 文中把原因归于冷访问路径的差别 (同步缺页对比 readahead 加批量 I/O), 措辞是「可能部分反映」, 没有拆分测量. 论文据此给出的操作建议是 CPU 紧张的部署只开 FPR, 保留 virtio-blk. §5.2 说 DAMON 加 FPR「没有显著的 CPU 开销」, 图 6 右图中绿线与基线确实接近, 但实验只覆盖 50 分钟, DAMON 采样本身的开销随 guest 数量增长的情况没有测.

**CPU QoS: `SCHED_IDLE` 与 core scheduling**

CPU 一侧的问题是超卖下的干扰. 大多数沙箱的 CPU 用量稀疏, 但有些任务有严格的单步时延预算, 例如下棋 Agent 每一步有固定的时限. DSec 把沙箱分成时延敏感 (LS) 和尽力而为 (BE) 两类, 分两层处理. 第一层把 BE 沙箱放在 `SCHED_IDLE` 调度策略下, 只要有 LS 任务可运行, BE 就让出 CPU. 第二层针对 SMT: 同一物理核上的两个硬件线程共享执行单元, 调度优先级只决定谁在一个硬件线程上运行, 管不到兄弟线程上跑的是什么, LS 线程和兄弟线程上的 BE 线程仍然争抢执行资源. DSec 对 LS 沙箱开启 Linux core scheduling, 通过 `prctl(PR_SCHED_CORE)` 按 QoS 类给任务打 cookie, 同一物理核的两个硬件线程只同时运行 cookie 相同的任务, 无关的 BE 任务不会出现在 LS 任务的兄弟线程上. 两层都是现成的内核功能, 只靠配置启用.

![](./images/p24-figure-13-latency-sensitive-agent-time-under-increasing-co.jpg)
> 图 7: 同机 BE 负载从 10% 增加到 50% 时 LS 下棋 Agent 的单步时间, 对比不加保护的基线, 仅 `SCHED_IDLE`, `SCHED_IDLE` 加 core scheduling 三种配置, 虚线为无背景负载时的水平, 原文 Figure 13.

图 7 解析: 纵轴是 Agent 单步时间 (秒), 横轴是背景 CPU 负载. 无背景负载时约 0.230 s. 基线 (蓝) 从 10% 负载的约 0.242 s 升到 50% 负载的约 0.334 s, $0.334/0.230\approx1.45$, 对应文中的 45.2%. 仅 `SCHED_IDLE` (绿) 每个负载点都只比基线低一点, 50% 时约 0.323 s, 误差棒从约 0.303 到 0.343 s, 与基线的误差棒重叠. 加 core scheduling (红) 在 10% 负载时与无负载持平, 50% 时约 0.269 s, $0.269/0.230\approx1.17$, 对应文中的 17.3%. 图里只有一个 LS 应用, 没有画 BE 任务的吞吐.

「仅 `SCHED_IDLE` 最多改善 3.4%」按图读是相对基线的改善, $1-0.323/0.334\approx3.3\%$; 换算到相对无负载的膨胀, 是从 45.2% 降到约 40%. 剩下 17.3% 的膨胀, 论文归因于高负载下 CPU 睿频降低, 以及 core scheduling 管不到的内存带宽和末级缓存争用, 并以「已可容忍」为由没有做内存带宽隔离. 这组实验有三处没有交代. 一是 core scheduling 的代价: LS 任务独占物理核时, 兄弟线程找不到同 cookie 的任务就只能空转, BE 的吞吐会下降, 图 7 没有画 BE 一侧. 二是只测了一个下棋应用, 没有说明 LS 沙箱在生产中占多少比例. 三是测试的是 10% 到 50% 的背景负载, 生产节点在约 50 倍 CPU 超卖下的实际负载率文中没有给出.

V4.1-Flash 报告 §5.1.3 对同一机制的描述与此有出入. 报告写的是 core scheduling 保证兄弟超线程上只同时运行同一优先级类的任务, 用词是「消除干扰」; DSec 论文的实测是 50% 负载下仍有 17.3% 的膨胀, 「消除」只对 SMT 这一个干扰源成立. 报告另给了一项论文 §5.2 没有写的节点内措施: 用硬件 sub-NUMA 分区, 每个 worker 虚拟机绑一个 NUMA 域, 把 CPU 和内存都限制在本域内, 在内存超卖和内核锁争用之间取平衡, 单物理节点能跑的活容器从约 1,000 提到 2,500 以上. DSec 论文对容器的密度只给了 §4.3 的运行点, 没有把 sub-NUMA 列为机制, 也没有测它的效果.

## 3. 与 RL 框架的协同和安全防护

**用 Agent 构建环境: `pack_diff` 与信息隔离**

Agent RL 需要的环境数量靠人工搭不出来, DSec 的做法是让 Agent 在训练和评测用的同一套基础设施上交互式地搭环境. 支撑这件事的接口是 `pack_diff`: Agent 在任意时刻对沙箱做一次增量磁盘快照, 这份快照之后可以恢复成新的沙箱. 一次交互会话因此可以直接变成可复用的环境, 搭建, 验证, 消费都在同一个平台上, 不需要单独的镜像构建流水线. 增量快照的实现落在第 3.3 节的块级路径上 (OverlayBD 可写盘的快照不必重新打包成 EROFS); 容器侧的快照怎么做, 是否同样以 OverlayBD 或 EROFS 层的形式发布, 文中没有说明.

搭出来的环境还要受约束. DeepSeek 内部有一套规则限制打包环境对共享基础设施的运行时开销, 这些规则作为指令交给搭环境的 Agent; 研究员另建了一个平台, 对 Agent 搭的环境做质量检查, 并导出成 RL 和评测使用的标准格式. 搭建与使用在同一个平台上, 答案泄漏的风险也随之出现: 搭环境的 Agent 在调试时很可能接触过参考答案. DSec 的处理是两件事, 搭建者和运行时 Agent 用不同账号; 打包前把搭建阶段的残留数据从可写层删掉, 不让参考答案进入最终镜像. 文中没有说明残留数据的识别规则, 也没有给出泄漏检查的结果.

V3.2 报告里已经有同类流水线, 两者可以对上. V3.2 的代码 Agent 环境由 V3.2 驱动的环境搭建 Agent 构建: 从 GitHub 挖出 issue 与 PR 对, Agent 负责装包, 解依赖, 跑测试, 只有打上 gold patch 后失败转通过的测试数非零, 通过转失败的测试数为零, 环境才算搭成, 由此得到数万个可复现环境, 表 1 记为 24,667 个代码 Agent 任务; 通用 Agent 则由环境合成 Agent 生成, 筛选后保留 1,827 个环境, 4,417 个任务, 详见 [V3.2 解析](../../1-%E6%A8%A1%E5%9E%8B%E6%8A%80%E6%9C%AF%E6%8A%A5%E5%91%8A/1.7-deepseek-v3-2/02-deepseek-v3-2-analysis.md). DSec 论文 §6 开头说 V3.2 起的全部沙箱负载都跑在 DSec 上, 而 V3.2 报告里一次也没有出现 DSec 这个名字. 到 2026 年初的生产周, 容器后端已经用到 102,171 个工作区, 环境规模比 V3.2 公开的任务数高出一个数量级.

### 3.1. 把 agent loop 移出可抢占的 GPU 作业

GPU 集群里的训练作业为提高利用率会被例行抢占. 早期的训练流水线中, agent loop 和模型服务, RL 框架一起跑在可抢占的 GPU pod 里, 作业被抢占时 agent loop 丢了, 沙箱还在. 恢复依赖命令日志: 训练框架恢复出 rollout 状态, 再与沙箱的执行状态对账, 回放时已完成的操作直接复用记录的结果, 不重新执行, 避免非幂等命令 (例如追加写文件, 发请求) 产生重复副作用. 这正是 V4 报告 §5.2.5 描述的「全局有序轨迹日志」, 报告当时给它列了三个用途: 抢占后客户端快进, 细粒度溯源, 确定性回放.

从 V4.1 起, rollout 的执行整体移到 DSec 上, 拆成两部分: agent 沙箱运行 scaffold (例如 DeepSeek Harness) 和它的工具; worker 容器管理沙箱, 提供一个与 scaffold 无关的控制层. 两者都在可抢占的 GPU 池之外, rollout 的寿命与 trainer 的寿命解耦. worker 容器和 agent 沙箱一起保存完整的 rollout 状态, 是这份状态唯一的事实来源; GPU 作业被抢占后重新连上即可继续, 不需要再经命令日志回放重建. 这样 RL 框架里的 rollout 状态恢复逻辑可以删掉, 跨组件协调减少, 故障处理变简单. V4.1-Flash 报告补了 worker 容器的另一项职责: 把不同 scaffold 的异构交互归一成统一的轨迹格式, 并与 trainer 通信, 这是它能跨 OpenCode, Pi, DeepSeek Harness 等 scaffold 联合训练的前提, 见 [V4.1-Flash 解析](../../1-%E6%A8%A1%E5%9E%8B%E6%8A%80%E6%9C%AF%E6%8A%A5%E5%91%8A/1.9-deepseek-v4-1-flash/02-deepseek-v4-1-flash-analysis.md).

代价是 CPU 集群上多了一类长期驻留的 worker 容器, 每个 rollout 至少一个; worker 容器自己的状态是否持久化, worker 容器所在节点故障时 rollout 如何恢复, 文中都没有说明, 也没有给出这类故障的频率. 命令日志方案下, 沙箱和日志都在 DSec 上, GPU 侧丢了什么都能补回; 新方案把状态集中到 worker 容器和沙箱, GPU 抢占不再是问题, CPU 侧的故障却成了 rollout 的单点.

**训练被抢占时暂停沙箱**

GPU 作业被抢占后, 沙箱状态要留在 DSec 上直到 rollout 完成, 但训练暂停期间这些空闲沙箱会一直占着内存. RL 框架因此主动给被抢占作业的所有沙箱发暂停请求, DSec 回收内存并保留执行状态; 之后任何发往已暂停沙箱的请求, 都会先透明地恢复沙箱再执行. 两类后端的做法不同.

容器的暂停分三步: edge 先 `docker pause` 冻结容器的进程树; 再通过 cgroup 的 `memory.swap.max` 允许该容器使用 swap; 随后写 `memory.reclaim` 触发主动回收, 匿名页和文件页都会被回收, 进程状态保持不变. 恢复时 edge 先对进程的内存映射施加 `MADV_WILLNEED`, 发起异步预取, 再 `docker unpause`. microVM 的暂停是把内存和执行状态存成快照, 然后结束 Firecracker 进程, 释放全部运行时内存; 恢复时起一个新进程, 从快照恢复 guest 的执行. 两者的差别在于容器保留进程, 只把内存换出, microVM 连进程都不留. 第 3.3 节提到的 AgentENV 启动页预取, 记录的正是快照恢复时首次访问的页序列, 针对的也是快照恢复后的冷启动开销, 但如第 3.3 节所述, DSec 是否启用它文中没有给出.

论文 §6.3 没有任何测量. §8 开头明确把 §6 的框架集成排除在评测范围之外, 所以暂停一个沙箱要多久, 回收了多少内存, 恢复后首个请求的时延, swap 设备放在哪里, microVM 快照写到本地盘还是 3FS, 文中都没有给出. V4 报告曾写 OverlayBD 快照可链式叠加, 支持「毫秒级恢复」, 那是磁盘快照的恢复; microVM 暂停还要恢复整块 guest 内存, 两者口径不同, 不能拿来互证.

**Agent 的越界行为与访问控制**

§6.4 把生产中遇到的问题分成两类. 第一类是经非预期渠道拿答案. 沙箱内部, Agent 搜索平台管理的文件和通信通道找残留答案: 直接向 chronus 的 socket 发伪造的 RPC 冒充用户请求, 翻 chronus 的日志, 因为 chronus 的部分操作会调用 bash, 还试过覆盖 `/bin/bash` 来绕过检查或向后续 shell 会话注入命令. 加上文件读写和 socket 访问控制之后, 有 Agent 用 `XFS_IOC_SWAPEXT` 这个交换两个文件数据 extent 映射的 ioctl, 试图让受保护文件的内容经另一个文件描述符可读, 结果损坏了 XFS 元数据, 文件系统被迫关闭. 沙箱外部, Agent 扫描端口和服务找可访问的镜像站, 通过 Go module proxy 拉取 GitHub 上的代码, 安装更新版本的包, 目的都是找到现成的实现. 只检查最终输出, 无法判断 Agent 是否按预期的方式完成了任务.

第二类是破坏执行环境, 很多并非蓄意. 一个 Agent 从根目录递归 grep, 遍历到 `/proc` 并读了 `/proc/kpagecgroup`, 触发内核 bug 导致内核崩溃; 一个漏洞利用任务里, 本该发往另一台目标虚拟机的攻击命令在 Agent 自己的容器里执行, 把自己的内核打崩. 还有输出无界的问题: Agent 调用 `yes`, chronus 为支持异步取输出而记录了全部 stdout, 在存储上累积了数十 GB. 内核崩溃发生在 worker 虚拟机里, 同一个虚拟机上的其他容器会一起受影响, §7 说按用户隔离可以限制内核级故障的波及范围, 代价是节点密度下降, 指的就是这种情况.

缓解手段是两层访问控制. AppArmor profile 控制文件读写和 socket 访问, 包括 chronus 的日志和 Unix domain socket, 这些策略对沙箱里以 root 运行的 Agent 进程同样生效, 这一点对应 Listing 1 里的 `init_user="root"`. eBPF 负责网络: 训练框架按域名或镜像服务给出每个任务的网络权限, DSec 把它翻译成每沙箱的 eBPF 程序, 按 IP 地址, 端口和协议过滤, 白名单以外的流量一律拒绝; 任务在不同阶段需要不同连通性时, 策略可以动态更新. 域名到 IP 的翻译何时进行, 镜像服务的 IP 变化时规则如何同步, 文中没有说明.

论文自己承认这两层只覆盖拿答案这一类问题, 对触发内核 bug 之类的破坏行为没有通用防御, 依赖的是可观测性加上随模型演进持续加固. V4.1-Flash 报告列的被利用漏洞里有一条是「AppArmor 的非法内存访问」, 也就是说防御组件本身也被 Agent 当成了攻击面; 报告还写了 Agent 崩掉环境时, 这条轨迹按失败处理, 并向 RL 框架报一个「repercussion」信号. DSec 论文没有提这个信号, 也没有说明崩溃轨迹的奖励如何计算, `yes` 一类的输出膨胀后来是否加了上限, 同样没有交代.

### 3.2. 跨报告对照与证据边界

**与 V3.2, V4, V4.1-Flash 报告的对照**

DSec 在 DeepSeek 的模型报告里出现过三次. V3.2 报告只描述了环境怎么合成, 没有提沙箱平台; V4 报告 §5.2.5 介绍了 DSec 的初版, V4.1-Flash 报告 §5.1.3 写了规模扩大后的改动, 篇幅都在两页左右. 下表把几处可比的说法并排.

| 项目 | V4 报告 §5.2.5 | V4.1-Flash 报告 §5.1.3 | DSec 论文 |
|---|---|---|---|
| 起点 | 未写 | 从 V3 向 V4 过渡时开始建 | V3.2 起的全部沙箱负载 |
| 规模 | 单集群数十万并发 | 数百万并发沙箱实例 | 单个规模单元峰值约 38 万, 部署多个单元 |
| 抢占恢复 | 全局有序轨迹日志, 回放已完成命令 | worker 容器加 agent 沙箱, 挂起后卸载 | 日志回放是早期版本, V4.1 起改为 worker 容器 |
| 单节点密度 | 缓解容器运行时的自旋锁争用 | sub-NUMA 分区, 约 1,000 提到 2,500 以上 | 至少 3,200 个容器或 800 个 microVM |
| 越界处理 | 未写 | AppArmor 加 eBPF, 崩溃轨迹报 repercussion 信号 | AppArmor 加 eBPF, 未提 repercussion |

规模一行可以用论文自己的数对上. §7 说「数十台」3FS 存储服务器支撑「数十万核」的 CPU 集群, 一个规模单元约 3 万核, 所以单元数在 3 到 30 个之间; 若有 6 个以上单元同时达到 38 万的峰值, 合计就过了百万, 与 V4.1-Flash 的「数百万」不冲突. 单元的具体数量文中没有给出, 「数百万」是全部单元的合计还是需求预估, 报告的措辞是「需求增加到」, 两种读法都成立.

抢占恢复一行的变化最大. V4 报告把轨迹日志当作现行设计, 列了客户端快进, 细粒度溯源, 确定性回放三个用途; DSec 论文把它降为「早期版本」的恢复手段, 只保留了快进这一个用途的描述, 溯源和确定性回放没有再出现, 日志在新方案下是否还保留, 文中没有说. 单节点密度一行的三个数口径不同: V4.1-Flash 的 2,500 是「可测的端到端退化出现之前」的容器数, DSec 的 3,200 是「稳定运行过的运行点」, 后者不排除有一定退化; V4 的自旋锁争用在两篇后续文献里都没有再出现, V4.1-Flash 用 sub-NUMA 处理的「内核锁争用」可能是同一个问题, 但没有一处明说. 越界行为方面, 两篇列的案例不重叠: V4.1-Flash 写了 XFS 驱动的权限问题, AppArmor 的非法内存访问和包镜像服务泄漏答案, DSec 写了 chronus socket 伪造, `XFS_IOC_SWAPEXT`, Go module proxy 和 `/proc/kpagecgroup`. XFS 一项可能是同一事件的两种描述, 其余没有对应.

**论文内部前后不一致的地方**

第一处是单节点密度的措辞. §1 写的是单节点「最多」容纳 800 个 microVM 或 3,200 个容器, §4.3 写的是「至少」稳定运行过这么多, 并强调这是运行点而不是硬上限. 两处方向相反, 按 §4.3 的上下文, 「至少」是本意.

第二处是容器的内核边界. §2.2 说容器的主要局限是共享宿主机内核, 不总适合安全敏感任务; §3.3 说 FnCall 和容器都跑在 QEMU/libvirt 虚拟机里, 虚拟机提供独立的内核和网络栈. 两处合起来, 容器共享的是 worker 虚拟机的内核, 一个容器打崩内核会波及同一虚拟机里的其他容器, 但碰不到裸机. 第三处是统计样本. §2.4 说一个规模单元每天服务约 300 万个沙箱, 一周就在 2,000 万量级; Fig. 8 统计的是同一周里 150 多万个容器和 39 万个 microVM, Fig. 7 的寿命分布只抽了 3 万个容器和 1 万个 microVM. 各图的抽样方法都没有交代, 无法判断样本是否偏向某类任务.

第四处是摘要与正文的口径. 摘要写「支持超过 380,000 个并发沙箱」, 读起来是容量; §2.4 写的是典型一天的峰值并发「约 38 万」, 是观测值. §5.2 写 DAMON 加 FPR「降低内存消耗 21.2%」, 没有说明是时间积分, §8.4 才交代峰值基本不变, 只看 §5.2 容易把它当成峰值的降幅. 第五处是测试集群的构成. §8.1 说测试集群共 10 个节点, microVM 节点是双路 192 核 1.5 TB 的裸机, 容器实验跑在单路 192 线程 512 GB 的 QEMU 虚拟机里, 两类节点各有几台没有写; 图 6 的内存峰值约 4 TB, 说明 microVM 实验至少用了三台节点, 图 4 的纵轴单位是「每个 VM」, 又说明容器实验按虚拟机计数. 另外, §7 的 3FS 存储服务器是 20 块 15 TB SSD 加 2 块 400 Gbps 网卡, 3FS README 的测试集群是 16 块 14 TiB NVMe 加 2 块 200 Gbps 网卡, 这是不同代的硬件, 不算矛盾, 读 3FS 的性能数字时要注意不能直接套用.

**尚无公开测量的性能指标**

几项写在摘要和 §2.4 里的能力没有对应的实验. 每秒 5,000 次以上的创建速率没有给出测量方法, 也没有拆开放置引擎, edge 准入, 存储准备, 运行时启动各段的耗时分布; 第 1.1 节按这个速率算出 32K 沙箱光创建就要约 6.4 s, 而创建之后的环境准备才是 §8.2 和 §8.3 测的部分. 云端扩容只给了「200 台云虚拟机吸收约 30% 的峰值溢出」一个数, 没有云上沙箱的启动时延, 也没有说明剩下 70% 的溢出是排队, 拒绝还是降级. §6 的框架集成整体不在评测范围内, 暂停恢复的开销, worker 容器方案相比命令日志方案节省了多少恢复时间, 访问控制上线前后越界行为的发生率, 都没有数字.

可复现性也有限. 平台本身没有开源, 公开的只有存储路径上的 Rust 版 OverlayBD 和 ublk 库, 放在另一个平台 AgentENV 的仓库里; dockerd 的 30 行修改, 放置引擎, edge, aether, chronus 都看不到代码. 论文给出的机制大多是现成内核功能的组合 (EROFS, overlayfs, virtio-pmem, DAMON, balloon FPR, `SCHED_IDLE`, core scheduling, AppArmor, eBPF), §7 也明确说不需要改内核, 这让单项机制容易复现, 难复现的是生产负载本身: 第 1 节的那些分布来自 DeepSeek 自己的 RL 任务构成, 换一套任务, 扇出, 访问比例和寿命都会变. DeepSeek 官方技术文章补了一个论文里没有的数, 生产环境 CPU 超卖率超过 50 倍, 与第 1.3 节按 Listing 1 规格推出的约 50 倍一致, 说明示例规格大体代表了实际申请.

## 4. DSec 的准确位置

DSec 的对象是「执行环境」. 代码模型决定下一步生成什么补丁、命令或测试; Agent 策略决定何时调用工具; DSec 负责让命令在隔离、可复现且可大规模并发的环境中运行, 再把结果送回 rollout. 它提升的是训练样本获取能力与环境吞吐, 不直接改变模型架构、代码预训练目标或解码算法.

一条完整链路可以写成

$$
o_t\sim\pi_\theta(\cdot\mid h_t),\qquad
(y_t,s_{t+1})=\mathcal E(s_t,o_t),\qquad
h_{t+1}=h_t\oplus(o_t,y_t),
$$

$\pi_\theta$ 是 Agent 策略, $\mathcal E$ 是 DSec 提供的环境执行, $s_t$ 是文件系统、进程与外部服务状态, $y_t$ 是命令输出. 一次 rollout 的奖励由轨迹与验证器计算. DSec 实现的是 $\mathcal E$, 它影响可并发采多少轨迹、环境是否一致和执行结果是否可信, 却不等于「让模型更会写代码」的训练算法.

同一套沙箱可以承载软件工程、浏览器操作、办公软件、终端任务和安全评测. 代码只是其中一种负载. 把 DSec 放进 DeepSeek 基础设施谱系更准确: 3FS 提供共享存储, HAI-LLM 等系统训练模型, DSec 为 Agent RL 与评测提供 CPU 环境, GPU rollout 服务负责模型推理. 它们围绕同一训练流水线协作, 解决的是不同资源面.

### 4.1. 沙箱供给的排队模型

**为什么突发比日均更重要**

设一批 rollout 同时需要 $N$ 个环境, 平台创建速率为 $\mu$ 个每秒. 即使没有排队和镜像读取, 全部就绪时间下界为 $N/\mu$. $N=32000,\mu=5000$ 时是 6.4 秒. 若训练必须等待整批环境, 尾部沙箱决定起步时间; 平均创建延迟很低也可能被 p99 拖住.

日均 300 万个沙箱对应约 34.7 个每秒, 远低于 5000/s 峰值能力. 两个数字并不冲突: 日均刻画总量, 峰值刻画训练作业在短窗口集中申请的能力. 按日均速率设计, 一次 32K 突发会排队约 15 分钟; Agent RL 的 GPU 在此期间可能空等.

若创建时间随机变量为 $T_i$, 整批等待是 $\max_iT_i$. 单实例 p99 为 5 秒时, 32K 个实例里至少一个超过 5 秒的概率几乎为 1. 所以系统不能只优化单实例均值, 还要降低长尾、允许分批启动或让 rollout 异步消费已就绪环境. 论文报告高创建速率和分布式准入, 没给完整的批次完成时间分位数.

**Little 定律能算与不能算的部分**

稳态下 $L=\lambda W$. 300 万/日给出 $\lambda\approx34.7/s$. 若平均寿命为 30 分钟, 平均并发约 62460; 若为 60 分钟, 约 124920. 峰值 38 万要求更长平均寿命或突发叠加. 论文只给寿命中位数与 p99, 分布右偏, 不能从中位数代替均值精确反推.

Little 定律也不说明资源用量. 两个寿命相同的沙箱可能一个持续编译, 一个长时间等模型. CPU 使用由脉冲阶段决定, 内存却在整个寿命驻留. DSec 因而把 CPU 与内存分别治理: CPU 允许高倍超卖并给后台任务低优先级, 内存通过共享只读页、回收冷页和 balloon 控制.

**环境分层的语义**

基础镜像、工作区与工具包独立版本化, 目标不是把所有文件拆得越细越好. 三层变化频率不同: 操作系统与语言运行时相对稳定, 每道任务的仓库和依赖变化最大, harness 又会跨任务频繁更新. 若把三者烘焙成单一镜像, 工具包改一行也要重建和重新分发整个制品.

overlayfs 让上层覆盖下层同路径文件. 读文件时按层查找, 写入落在可写层, 删除用 whiteout 表示. EROFS 把只读层做成可随机访问的文件系统镜像, 适合从 3FS 按块读取. 关键收益是「启动只拿元数据, 用到哪个块再读哪个块」. 对实际只访问 4% 到 13% 内容的镜像, 理论网络读取上限可从完整镜像大小降到访问工作集附近.

以 12.1GB Java 镜像、9.2% 访问率计算, 全量预拉约 12.1GB, 按需读取约 1.11GB, 理想减少约 10.99GB. 32K 沙箱若各自拉取会是数百 TB; 实际还有页缓存与同节点共享, 所以不能简单相乘. 这笔手算说明按需加载为何重要, 真实网络量需扣除缓存命中、元数据与重复块.

分层也提供信息隔离. 构建环境的 Agent 可以安装依赖、修改配置, `pack_diff` 只保存相对基础环境的变化. 训练 Agent 得到成品层, 不必看到构建过程里的答案或私有凭据. 如果 diff 中仍含测试答案、构建日志或认证信息, 分层本身不会自动消除泄漏, 仍需内容扫描与访问控制.

**OverlayBD 与 256 KiB 块**

microVM 需要块设备语义, 不能直接把宿主目录当容器层挂进去. DSec 用 OverlayBD 表示增量块层, 通过 ublk 在用户态实现块设备, 后端从 3FS 读取. 256 KiB 是读取、缓存与元数据粒度的交换点.

块太小, 随机读取浪费少, 请求数和索引元数据增加; 块太大, 请求数下降, 一次只用几 KiB 也要拉整块. 设真实访问片段平均为 $r$, 块大小为 $B$, 若访问在块内均匀且无复用, 单次读放大约为 $B/r$. 对只读大量小配置文件的启动阶段, 256 KiB 可能带来明显放大; 对连续加载共享库, 预读整块更划算.

缓存命中取决于跨沙箱是否读取相同块. microVM 镜像扇出中位数为 1, 工作区块共享很少; 两个共享基础镜像却会被大量实例访问, 基础层热门块命中很高. 把所有层统一看成一个缓存命中率会掩盖差异. 应按基础层、工作区和工具包分别报告读字节、命中率与启动关键路径.

可证伪实验可固定同一批任务, 比较 64、128、256、512 KiB 块, 测启动 p50/p99、3FS 请求数、读放大和宿主缓存占用. 如果 256 KiB 在所有维度都不占优, 当前粒度只是实现选择; 若它位于延迟与请求开销的 Pareto 前沿, 才能说明与负载匹配.

### 4.2. 内存共享与回收的边界

virtio-pmem 把只读镜像页以内存映射方式暴露给 guest, DAX 让 guest 直接访问宿主页缓存, 多个 microVM 读取相同基础镜像页时可以共享物理页. 普通虚拟块设备会把宿主页缓存内容再复制进 guest page cache, 同一数据出现两份; DAX 去掉这层复制.

共享收益只覆盖只读且内容相同的页. 工作区被写入后产生私有页, 匿名堆、解释器状态与页表也无法共享. 因而 microVM 的最小内存不等于工作集文件大小. 论文报告密度改善, 没给每类页在生产中的完整占比, 不能从 DAX 机制直接推出任意负载都能达到 800 VM/节点.

DAMON 根据访问采样识别冷内存, balloon 驱动把 guest 可回收页归还宿主. 采样有误差: 间歇访问的页可能被判冷, 回收后再次访问引发缺页与延迟; 采样过密又消耗 CPU. Agent 沙箱长时间等待模型, 冷页很多, 正适合回收; 编译和测试脉冲到来时需要快速取回.

一项关键实验应按等待时间分桶, 比较关闭回收、只用 balloon、DAMON 加 balloon 三组的宿主内存、缺页数、工具调用 p99 与 OOM 率. 若内存下降而 p99 大幅上升, 密度收益转成训练长尾; 若等待期释放、唤醒期延迟稳定, 才证明访问感知策略有效.

**CPU 超卖为何能成立**

90% 沙箱平均 CPU 低于申请量 5%, 意味着按申请核独占会浪费大量计算. 但平均低不代表脉冲不重. 数千沙箱可能在模型输出后同时执行命令, 形成同步峰值. 超卖需要调度器区分延迟敏感前台与可延后后台, 并防止一个沙箱的线程洪泛拖垮节点.

`SCHED_IDLE` 让后台进程只在其他任务不用 CPU 时运行, 适合镜像准备、回收等维护工作. core scheduling 用安全域 cookie 控制哪些线程可以同时占用同一物理核的 SMT sibling, 降低侧信道风险. 它可能让一个逻辑核空闲, 以隔离换吞吐.

若按示例每沙箱申请 4 核, 峰值 38 万实例对应 152 万申请核, 对 30K 物理核约 50.7 倍. 这个数字只是示例规格上界, 实际请求未必都申请 4 核. 即便平均利用率为申请量 5%, 期望需求仍约 76000 核, 超过物理核. 因此生产负载的真实规格、同时活跃比例和跨单元分布必然参与平衡, 不能用示例直接证明 50 倍超卖稳定.

可证伪测量应报告每节点 runnable 队列、CPU throttling、命令执行 p99、同步脉冲时的尾延迟和训练 GPU 等待时间. 单看节点能塞多少沙箱会奖励过度超卖, 却不反映 rollout 完成速度.

**调度一致性的取舍**

集群控制面保持无状态, 节点运行时掌握本地资源并作准入, 避免每个沙箱创建都经过一个强一致全局调度器. 在每秒数千创建的突发下, 中央事务很容易成为瓶颈. 代价是全局视图近似、节点间可能短时不均.

若请求先选到资源不足节点再失败重试, 高负载时会产生放大. DSec 需要通过节点上报、随机或多选一策略让请求落到有容量处, 最终准入仍由节点根据真实本地状态决定. 论文描述架构原则, 没公开负载评分公式、陈旧信息窗口和重试率.

无状态控制面更容易水平扩展与故障恢复, 也意味着会话状态不能只存在代理进程. 沙箱标识、层版本、租约与网络策略要有可恢复来源. 节点失联时, 控制面需要判断沙箱已死还是暂时不可达, 否则重复创建可能让同一 rollout 出现两个环境.

可用故障注入验证: 随机杀死代理、延迟节点心跳、让 3FS 短暂抖动, 统计创建成功率、重复实例、状态恢复时间与训练侧错误. 只在健康集群测峰值 QPS, 无法证明控制面设计的故障语义.

### 4.3. DSec 怎样影响 RL 统计

环境系统故障会进入训练数据. 命令超时、依赖读取失败、网络策略误拦可能让本来正确的 Agent 得到低奖励. 若故障与任务类型相关, 奖励噪声带方向: 大仓库、冷门镜像或长测试更容易失败, 策略会回避这些任务或偏爱短路径.

设真实任务奖励为 $r^*$, 环境成功指示为 $z$, 观测奖励近似 $r=z r^*+(1-z)r_{fail}$. 若 $P(z=1\mid x)$ 随任务 $x$ 变化, 观测目标已经混入基础设施偏差. 平台应把环境错误与 Agent 错误分开标记, 训练时重试或剔除前者. 论文强调稳定与隔离, 没给生产 rollout 中基础设施失败占奖励零值的比例.

暂停机制在 GPU 训练作业被抢占时冻结沙箱, 避免环境继续消耗 TTL 或外部状态变化. 但现实时间可能仍前进: 网络服务过期、证书失效、远端数据变化. 要实现严格可恢复, 任务应尽量依赖沙箱内状态或可重放服务. 「进程暂停」与「环境时间完全冻结」不是同一保证.

把 agent loop 移出 GPU 作业能让 GPU 释放后 rollout 状态仍在, 也增加分布式状态协调. 模型服务、控制器与沙箱之间任何一方重试都可能重复执行命令. 对有副作用的工具, 请求需要幂等标识或轨迹去重, 论文没有展开事务语义.

**安全边界**

容器共享宿主内核, 启动快、密度高, 隔离边界弱于 microVM. 对来源不可信、会主动探测漏洞的 Agent, microVM 用独立 guest 内核缩小逃逸面. 完整 VM 支持更复杂操作系统与图形环境, 代价是内存和启动时间. 后端选择本质上是风险、能力与成本三方取舍.

网络 eBPF 规则限制每个沙箱可访问的域名或服务. 域名规则仍需处理 DNS 变化、共享 IP、重定向和加密流量; 允许包管理器意味着下载内容可能随时间变化. 可复现训练最好固定制品哈希并通过受控代理获取, 只按域名放行不足以保证依赖恒定.

沙箱内 root 权限让任务安装软件更方便, 安全控制必须位于 Agent 难以修改的边界, 如宿主、hypervisor、eBPF 与只读挂载. 把密钥写进环境变量或工作区会被 root 读取. 构建 Agent 与训练 Agent 分离, 也要确保打包层不携带构建凭据.

安全实验不能只跑良性 benchmark. 应主动测试内核逃逸、资源耗尽、fork bomb、磁盘填满、网络扫描、符号链接穿越、侧信道与制品投毒, 分别记录阻断率和误杀率. 论文报告生产防护原则, 没公开完整红队覆盖与残余风险.

**与 3FS 和训练系统的谱系**

3FS 为 DSec 提供大规模共享、随机读友好的后端, 让制品无需预铺到每个节点. DSec 在其上增加 EROFS、OverlayBD、块缓存和生命周期管理. 3FS 的带宽与一致性是底座, DSec 决定沙箱看到哪些层、怎样按需取块以及何时释放资源.

V3 的训练基础设施主要处理 GPU 上的模型并行、FP8 与通信重叠; DSec 处理 Agent RL 中 CPU 环境的扇出. 当模型生成一步需要数秒、工具执行只用几十毫秒, CPU 可以高倍共享; 当测试或编译很重, 环境侧会成为瓶颈. 两套系统通过 rollout 队列耦合, 优化一侧可能把瓶颈推到另一侧.

V3.2 到 V4.1 的报告把 DSec 作为 Agent 训练环境, 说明它承接了后续工具使用与软件工程 RL 的规模需求. 这条谱系与 Coder、Coder-V2 的模型能力线相交在训练数据生成处, 不属于同一条模型演进线. Coder 模型可以不用 DSec 训练, DSec 也能服务非代码 Agent.

## 5. 可证伪的联合实验

第一组固定任务和 Agent checkpoint, 只改变环境后端, 比较容器与 microVM 的启动分位数、内存、执行时间、基础设施失败率和安全逃逸面. 若 microVM 密度下降却没有提供可测安全收益, 选型依据不足; 若容器在恶意任务中出现越界, 隔离差异得到验证.

第二组固定制品, 比较全量预拉、本地缓存、3FS 按需加载与分层按需加载. 指标包括批次全就绪时间、读字节、3FS 请求、缓存占用和工具调用长尾. 低扇出任务应更偏向按需加载, 高扇出基础镜像可能从预热获益. 若所有工作集都用同一策略, 平均数会掩盖分界点.

第三组固定节点资源, 逐步提高沙箱密度, 测 rollout 每小时完成数而非只测实例数. 密度增加初期吞吐上升, 超过某点后 CPU 脉冲碰撞、缺页和 I/O 排队使完成时间恶化. 最优点在吞吐曲线峰值附近, 不是 OOM 前的最大实例数.

第四组把环境故障显式注入 RL. 设置不同概率的命令超时、冷块延迟和网络误拦, 比较是否标记并重试环境错误. 若不区分故障, 模型准确率随特定任务资源需求下降; 正确分类后应恢复. 这直接检验 DSec 稳定性是否影响学习目标.

第五组测暂停恢复. 在 rollout 的准备、工具调用和测试三个阶段分别抢占 GPU 作业, 恢复后检查文件、进程、时钟、网络连接和奖励是否一致. 仅保存文件系统不足以恢复内存进程状态, 只暂停进程又无法冻结外部服务. 论文给出机制, 需要任务级一致性结果补足语义.

### 5.1. 证据强弱与公开空白

生产追踪能确认负载的突发、长寿、低 CPU、镜像多样与低扇出; 对照实验能确认按需加载、分层和内存机制在所测任务上的收益; 已部署规模能证明系统可服务数百万日实例. 这些是论文最强的证据.

仍缺统一端到端指标: 一个 RL batch 从申请到全部完成的 p50/p99、基础设施错误率、GPU 因环境等待损失的时间、每条有效轨迹的 CPU/内存/网络成本. 局部启动和密度指标无法自动换算成训练加速.

平台没有完整开源, 外部难以复现调度、准入、网络策略与暂停协议. 开源 OverlayBD 路径可验证存储机制的一部分, 不能代表整套 DSec. 论文中的生产数字来自 DeepSeek 特定集群、3FS 和任务分布, 迁移到普通云盘或小集群需要重新测量.

最准确的结论是: DSec 把 Agent RL 的环境供给做成一套面向突发、低复用、长寿稀疏负载的专用基础设施, 并通过共享存储按需加载、分层制品、内存回收与分散准入提高规模. 它为模型学习提供更可靠、更大量的交互轨迹, 本身不定义代码能力目标, 也不保证模型从这些轨迹中学到多少能力.

**隔离语义与威胁模型**

进程级 FnCall 共享宿主内核与预热运行时, 适合短、受控、无持久状态的函数. 容器增加 namespace、cgroup、能力集和文件系统隔离, 仍共享内核. microVM 用 guest 内核与虚拟硬件形成额外边界. 完整 VM 再提供更广操作系统与设备模型. 四者差异落在攻击者能触及的可信计算基上.

若威胁是普通程序崩溃或资源失控, cgroup 与进程隔离已经能限制多数影响; 若 Agent 会主动利用内核漏洞, 共享内核让容器逃逸后直接触及宿主, microVM 还需突破 guest 与 VMM 边界. microVM 也非绝对安全: 虚拟设备、VMM、共享文件与网络接口仍是攻击面.

隔离强度不能只按后端名称判断. 特权容器、宿主目录挂载或宽网络规则会削弱边界; 精简 microVM 设备、只读层和最小网络权限会增强边界. 可证伪实验应使用同一套逃逸、资源耗尽和侧信道用例测阻断率, 同时记录启动、内存与吞吐代价.

**冷启动的尾部分布**

Agent 批次等待的是慢实例. 若单实例启动 CDF 为 $F(t)$, $N$ 个近似独立实例全部在 $t$ 前就绪的概率为 $F(t)^N$. 单实例 99.9% 在 5 秒内完成, $N=32000$ 时整批按时概率仍约 $0.999^{32000}\approx1.25\times10^{-14}$. 大批次必须关注更高分位、分批消费或允许少量慢实例被替换.

独立假设往往过于乐观. 大量实例同时读取同一 3FS、请求同一节点或触发页缓存淘汰, 延迟会相关. 相关慢启动会形成整批尖峰. 报告的每秒创建数描述吞吐, 无法替代批次 p99 就绪时间. 应按任务规模画出首个、50%、95%和全部环境就绪时间.

按需加载把一部分成本从 create 移到首次工具调用. 创建延迟下降不代表 episode 更快. 端到端应从申请开始计时, 直到第一条命令完成、测试完成与 rollout 结束. 若冷块读取只是在后续集中爆发, 创建 QPS 会高估收益.

**环境失败造成的删失偏差**

设任务结果为 $Y$, 环境成功为 $Z$. 训练只保留 $Z=1$ 的轨迹时, 观测的是 $P(Y\mid X,Z=1)$. 只有在给定任务特征 $X$ 后, 环境成功与潜在结果条件独立, 即 $Y\perp Z\mid X$, 才能把保留样本用于无偏估计. 大仓库、长测试和复杂依赖同时更难解、也更易环境失败, 条件独立通常不自然成立.

若知道成功概率 $e(X)=P(Z=1\mid X)$, 可用逆概率权重 $1/e(X)$ 修正可观测任务分布. 当某类任务成功率很低, 权重巨大、方差爆炸; 环境从未成功的任务无法修正. 更稳妥的方法是提高环境可靠性并把故障原因显式标注, 再对同题重试估计失败是否可恢复.

直接把环境超时记为 Agent 失败会形成错误奖励; 直接删除又会偏向便宜任务. 应分别报告原始完成率、重试后完成率、因环境删失比例和按任务类型的奖励. 若 DSec 优化后模型分数上升, 还要区分训练数据更干净与策略真正改善.

### 5.2. 共享、写放大与缓存污染

设只读基础层大小 $B$, $n$ 个实例实际读取比例 $p$, 共享缓存命中率 $h$. 粗略后端读取量为

$$
R\approx pB[1+(n-1)(1-h)].
$$

$h=1$ 时热门块只读一次, $h=0$ 时近似每实例重复读取. 低扇出工作区的 $n$ 接近 1, 缓存收益小; 高扇出基础层适合共享.

写时复制让修改落到私有上层. 若每实例写入 $w$ 字节, 总私有数据约 $nw$, 还要加块对齐与元数据. 小文件随机写在块层可能触发 256 KiB 粒度的读改写, 实际写放大高于逻辑字节. 应分别测逻辑写、物理写与 3FS 网络写.

缓存容量为 $C$, 一次突发扫描低复用工作区超过 $C$, 会把高复用基础层热门块逐出, 形成缓存污染. 下一批实例又要重读基础层. 分层缓存配额或准入可保护热门层. 反例是工作区随后被大量复用, 固定偏爱基础层反而降低总命中; 策略需依据层级与近期复用统计验证.

**恢复、幂等与 episode 事实状态**

一个 episode 的事实状态不只包括文件系统. 还包括进程内存、随机数生成器、时钟、打开的文件描述符、网络连接、外部服务副作用和 Agent 已看到的输出. 容器 pause 能冻结本地进程, 无法冻结远端 API; microVM 快照保存 guest, 外部世界仍继续变化.

重试命令必须考虑幂等. `cat` 重跑通常安全, `git commit`、发送请求或写数据库可能产生第二次副作用. 每个工具调用可带唯一 episode 与 step 标识, 环境记录已完成结果; 重试时返回原结果而非再次执行. 这要求状态日志与实际副作用原子提交, 跨外部系统时很难完全做到.

若训练作业恢复后模型重复发送上一步, DSec 需要区分网络重试与 Agent 有意重复. 仅按命令字符串去重会误伤合法操作, 应使用控制器生成的调用标识. 论文说明暂停与迁移机制, 没有证明跨外部服务的 exactly-once 语义.

可证伪实验可在命令执行前、执行中、结果返回后分别杀死控制器或节点, 恢复后核对文件哈希、进程、外部计数器、Agent 观察和奖励. 任一阶段出现重复副作用或丢失输出, 就说明恢复语义弱于完整 episode 重放.

**论文和公开实现尚未证明什么**

开源 OverlayBD 与 ublk 代码能证明块设备路径可检查, 无法证明生产控制面、网络策略、调度、暂停恢复与安全配置和论文完全一致. 论文给出的生产规模证明系统运行过, 不等于公开代码可复现相同规模.

局部对照证明特定机制降低启动或内存, 尚未给出对最终 RL 样本效率、模型能力和总训练成本的因果贡献. 环境更多可能增加有效轨迹, 也可能只增加重复样本; 环境更快可能让 GPU 少等, 也可能把瓶颈推到模型推理.

生产一周的追踪代表该时间窗口和任务混合. 新模型、更长 episode、浏览器或 GUI 任务可能改变 CPU、内存、镜像扇出与网络模式. 3200 容器、800 microVM 是已达到运行点, 不是普适容量保证.

DSec 最可靠的定位因此保持在基础设施层: 它建立可扩展、分层、可隔离的环境供给, 并给出了生产负载与若干机制实验. 模型能力来自哪些数据、奖励与优化仍需训练侧消融, 代码能力路线也应由 Coder 系列及其数据和目标来叙述.

**资源噪声与 benchmark 方差**

同一段 Agent 代码的运行时间可拆为任务固有时间、节点共享噪声、制品冷读和测量误差:

$$
T_{i,j}=\mu+\alpha_i+\beta_j+\gamma_{cold}+\epsilon_{i,j},
$$

$\alpha_i$ 表示任务差异, $\beta_j$ 表示节点或邻居负载, $\gamma_{cold}$ 表示缓存状态. 若比较两个生成程序时恰好把一个放在热缓存空闲节点、另一个放在冷缓存拥挤节点, 性能奖励会混入环境差异. 随机分配只能在样本足够多时平均掉噪声.

算子和代码性能 benchmark 更敏感. 程序真实加速只有 2%, 邻居争用带来 5% 波动, 单次测量的排序几乎没有意义. 可在同一沙箱交替运行基线与候选, 做多次配对测量, 丢弃预热轮次并报告置信区间. core scheduling 提升隔离, 也可能改变可用 sibling 和绝对性能, 对照必须使用同一策略.

环境噪声若只增加方差, 会降低奖励信噪比; 若某类程序更容易受争用, 还会产生偏差. 内存密集程序在高密度节点更慢, 策略可能误学成偏爱低内存算法. 可按节点负载分层重跑, 检查程序排名是否稳定.

### 5.3. 多租户公平与准入反例

节点自主准入追求高吞吐, 容易让小任务穿过资源缝隙, 大批次长期等不到足够连续容量. 反过来, 为 32K 突发预留资源会阻塞大量短任务. 公平性需要明确目标: 按请求数、沙箱数、CPU 时间还是训练作业权重分配, 会得到不同结果.

一个反例是两个租户 A 与 B. A 持续提交单沙箱短任务, B 偶尔提交八千个必须同步启动的环境. 贪心调度总能接纳 A, B 的批次永远凑不齐; 严格 FIFO 又让 B 队首阻塞后面的 A. 可采用作业级配额、老化优先级或分批就绪, 并报告各租户 slowdown 与饥饿时间.

资源声明也可能被策略利用. 租户高报内存获得更宽松节点, 实际占用很少; 低报则在运行中触发回收和 OOM, 影响邻居. 准入应结合历史实际用量, 又要防止新任务因无历史被歧视. 论文展示节点密度与整体规模, 没公开多租户公平指标.

**环境版本漂移**

同一 Git commit 不保证同一环境. 包管理器解析会随镜像仓库更新, 系统包可被替换, 外部 API 与网页也持续变化. 训练时成功的轨迹在评测时可能因依赖版本漂移失败, 这种差异会被误判为模型退化.

基础镜像、工作区和工具包独立版本化提供了冻结入口. 可复现 episode 还需记录每层内容哈希、包锁文件、内核与运行时版本、网络访问结果和验证器版本. 只记录标签如 `python:3.10` 不够, 可变标签指向会变化.

按需加载要求旧层在 3FS 中保持可寻址. 垃圾回收若只看近期活跃引用, 可能删除仍用于复现实验的层. 应把训练数据或 checkpoint 与环境清单绑定, 生命周期随实验保留策略管理. 公开论文没有说明制品长期保留期限.

可做时间漂移实验: 在环境构建当天、一周和一月后重放同一轨迹, 分别允许与禁止外网, 比较文件哈希、测试结果和奖励. 冻结环境仍变化时, 漂移来自内核、硬件或未记录外部状态.

**三层证据**

论文实测覆盖生产负载分布、日服务量、峰值并发、节点运行点、镜像访问比例以及若干存储与内存对照. 这些数字支持 DSec 面向突发、低扇出、低 CPU 占用和长寿环境的设计, 适用范围是论文所述集群与任务窗口.

公开实现可直接检查 OverlayBD 与 ublk 存储路径的数据结构、块请求和错误处理. 它允许复现 microVM 按需块设备的一部分. 控制面调度、生产网络策略、DAMON 参数、暂停编排和完整 SDK 未随论文全部开放, 无法从仓库核验.

由材料推得的结论包括示例规格下的超卖量级、Little 定律估算、批次尾延迟、缓存读量和环境删失偏差. 这些推导明确依赖假设, 用于发现应补测的指标. 实际申请规格、平均寿命、缓存命中或失败相关性变化后, 数值会相应变化.

三层合起来给出稳定定位: 生产测量证明问题存在且系统已运行; 开源组件证明局部机制能够审查; 数量推导说明端到端训练收益还需哪些数据. 它们共同支持 DSec 是 Agent 环境基础设施, 不构成代码模型能力提升的独立证据.

后续版本若声称提高模型能力, 还需固定训练算法与数据预算, 只替换环境供给方案做对照. 若有效轨迹数增加而单位轨迹质量不变, 收益来自规模; 若相同轨迹数下奖励噪声降低, 收益来自可靠性. 这两条因果链应分别测量.

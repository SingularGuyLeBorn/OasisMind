# DualPath: 让 decode 节点的存储网卡也去读 KV cache

材料是论文 *DualPath: Breaking the Storage Bandwidth Bottleneck in Agentic LLM Inference* (arXiv 2602.21548, v2 日期 2026-02-26, 17 页), 作者来自北京大学, 清华大学和 DeepSeek-AI, 第一作者 Yongtong Wu 同时署北大与 DeepSeek-AI; 署清华的 Mingxing Zhang 也是 Mooncake 论文的作者之一. 系统实现在 DeepSeek 的内部推理框架上, 改动约 5K 行, 存储后端是 [3FS](../../4-%E5%BC%80%E6%BA%90%E4%BB%93%E5%BA%93/4.1-3fs/02-3fs-analysis.md), kernel 用 FlashMLA, [DeepGEMM](../../4-%E5%BC%80%E6%BA%90%E4%BB%93%E5%BA%93/4.4-deepgemm/02-deepgemm-analysis.md) 和 [DeepEP](../../4-%E5%BC%80%E6%BA%90%E4%BB%93%E5%BA%93/4.3-deepep/02-deepep-analysis.md). DualPath 本身没有开源代码. 逐段对照见 [DualPath 对照译稿](./01-dualpath-bi.md).

论文处理的问题很具体: Agent 多轮推理里, 每轮只追加几百个 token, 却要把前面几万 token 的 KV cache 从存储读回 GPU. 在 prefill-decode 分离 (PD 分离) 的部署里, 读盘只由 prefill 节点做, 每个节点只有一块 400Gbps 的存储网卡, 这块网卡先被打满, GPU 在等数据; 同一集群里 decode 节点的存储网卡几乎不用. DualPath 的改动是让 decode 节点也去读, 读到的 KV 再经计算网络转给 prefill 节点. 下文按瓶颈成因, 数据通路, 带宽约束, 隔离与调度, 实验口径的顺序展开, 末尾与 Mooncake 等方案对照.

## 1. 瓶颈从哪来: Agent 负载把 prefill 变成读盘任务

**命中率 98.7% 对应多少字节和多少 FLOPs**

论文的 trace 来自 DeepSeek 生产环境的 Agent RL 训练, 任务是在沙箱里修代码仓库的已知 bug (附录 A.3). 表 2 给出三份数据集, 各 500 条轨迹. 最长的一份 (MaxLen 64K) 平均 157 轮, 每轮平均追加 429 个 token, 生成 176 个 token, 平均上下文 32,721 个 token. 每轮 prefill 的输入是「全部上下文 + 新追加」, 其中上下文部分在上一轮已经算过 KV, 只需读回; 新追加的 429 个 token 才要真正计算. 命中率因此是 $32721/(32721+429)\approx 98.7\%$. 另两份数据集 MaxLen 32K 和 48K, 平均轮数 60 和 106, 追加 608 和 474 个 token.

论文用 cache-compute 比衡量这种负载对存储的压力: 每轮要加载的 KV 字节数除以本轮需要的计算量, 单位 GB/PFLOP. 正文说 DeepSeek-V3.2 在这份 trace 上约为 22 GB/PFLOP, 表 1 列出 16K 到 64K 上下文下五个模型的范围. 论文没有写分子分母各算了什么, 但按公开配置可以复算出来. 分子取上下文 $L_{ctx}$ 个 token 的 KV 字节, 分母取追加 $L_{app}=429$ 个 token 的前向 FLOPs:

$$
\rho=\frac{L_{ctx}\cdot \underbrace{b_{kv}}_{\text{每 token 字节}}}{L_{app}\cdot \underbrace{f(L_{ctx})}_{\text{每个新 token 的 FLOPs}}}.
$$

DeepSeek-V3.2 的主 KV 按 FlashMLA 的 FP8 布局, 每 token 每层 656 字节 (512 维 FP8 潜变量, 4 个 FP32 缩放因子, 64 维 BF16 的 RoPE 部分), 61 层合计 $b_{kv}\approx 40$KB. 每个新 token 的计算分三块: 线性层按激活参数约 $2\times 37\text{B}=74$ GFLOPs; DSA 主注意力每个 query 只看 top-2048 个 token, 按 MLA 吸收形式每层约 $2\times2048\times(576+512)\times128\approx 0.57$ GFLOPs, 61 层约 35 GFLOPs; lightning indexer 对全部上下文打分, 每层 $2\times64\times128\times L_{ctx}$, 32.7k 上下文时 61 层约 33 GFLOPs. 代入得 $1.31\text{GB}/0.061\text{PFLOP}\approx 21.6$ GB/PFLOP, 16K 和 64K 处分别是 12.2 和 35.1, 与表 1 的 13-36 一致. Qwen2.5-32B 按 GQA 的 8 个 KV 头, 头维 128, 64 层, FP16 存放, 每 token 256KB, 同样算法给出 115.8 到 265.4, 对应表 1 的 117-267. 两个模型都对得上, 说明表 1 的口径是「追加长度固定为 429, V3.2 不计 indexer 的 key cache」. 把 indexer 每 token 每层 132 字节也算进分子, V3.2 在 32.7k 处是约 26 GB/PFLOP. 这一复算是从公开配置推出的, 论文没有给出.

### 1.1. 稀疏注意力让这个比值随长度上升

表 1 里 DeepSeek-V3 的比值在 4.8 到 5.8 之间, 几乎不随长度变, V3.2 却从 13 涨到 36. 差别来自注意力的计算形状. V3 的 MLA 是稠密注意力, 每个新 token 的注意力 FLOPs 随上下文线性增长, 要读的 KV 也随上下文线性增长, 两者之比在长上下文下趋于常数, 这正是论文 §9 说的「稠密注意力的计算与 KV 之比是常数」. V3.2 的 DSA 把主注意力限制在 top-2048 个 token 上, 主注意力计算不再随上下文增长, 只剩 indexer 那一项随长度线性增加, 而 indexer 每个 token 每层的计算远比主注意力便宜. 结果是上下文越长, 每 FLOP 要搬的 KV 字节越多. DSA 的机制见 [DeepSeek-V3.2 技术解析](../../1-%E6%A8%A1%E5%9E%8B%E6%8A%80%E6%9C%AF%E6%8A%A5%E5%91%8A/1.7-deepseek-v3-2/02-deepseek-v3-2-analysis.md).

这个对比有一个容易忽略的后果: 模型侧降计算的改动, 会把压力转移到 I/O 上. V3.2 的 KV 字节数与 V3 相同 (都是 MLA 的 576 维潜变量), 但计算少了, 同样的 GPU 每秒能处理的新 token 更多, 每秒要读的 KV 字节也就更多. 后续的 V4 与 V4.1-Flash 继续压缩 KV 体积, 把持久化 KV 缩到 V4 的 1/8, 并把 KV 分层放在 HBM, 主机内存和 SSD 上, 见 [DeepSeek-V4.1-Flash 解析](../../1-%E6%A8%A1%E5%9E%8B%E6%8A%80%E6%9C%AF%E6%8A%A5%E5%91%8A/1.9-deepseek-v4-1-flash/02-deepseek-v4-1-flash-analysis.md). 那是从字节数一侧减压, DualPath 是从带宽一侧扩容, 两者针对的是同一个比值的分子和分母. KV 容量的通用计算方法见 [KV 缓存: 容量计算, 调度与压缩边界](../../../llm-guide/6-训练与推理优化/6.4-KV缓存与内存优化/6.4-KV缓存与内存优化.md).

**一个节点只有一块存储网卡**

论文 §2.3 以 DGX SuperPOD 为参照描述硬件: 每个节点 8 块 Hopper GPU, 每块 GPU 配一块 400Gbps 计算网卡 (CNIC, 东西向), 整个节点另有一块最高 400Gbps 的存储网卡 (SNIC, 南北向). 计算网络与存储网络物理隔离. 实验集群与此相同, 只是 8 块 CNIC 接 InfiniBand, SNIC 接 3FS (§7.2). 换算成字节, 一个节点的存储读带宽上限约 50 GB/s, 计算网卡合计约 400 GB/s, 差 8 倍. 按 1.1 节的数, V3.2 一个 32.7k 上下文的请求要读约 1.31GB, 一块 SNIC 每秒最多读完约 38 个这样的请求, 而一个 8 卡 prefill 节点的算力远不止于此.

图 3 左把这个问题放到硬件演进上: 2020 到 2024 年, GPU 稠密算力涨了 28.8 倍, 网卡与 PCIe 带宽只涨了 2.0 倍, HBM 容量涨了 2.4 倍, 于是 I/O 与算力之比下降 14.4 倍 ($28.8/2.0$). 28.8 这个数需要打折看: 它等于 $9.0/0.3125$, 0.3125 PFLOPS 是 A100 的稠密 BF16 峰值, 9 PFLOPS 是 B200 的稠密 FP4 峰值, 中间 2022 年约 2 PFLOPS 的点对应 H100 的稠密 FP8. 三个点各取当代最低精度, 涨幅里有一部分来自位宽从 16 降到 4, 论文没有注明. 结论方向不受影响, 14.4 倍是偏大的上限. 图 3 右测的是另一件事: 每个请求 30K 上下文, 追加 300 token, batch 从 1 增到 20 时相对吞吐从 1 涨到约 3 倍, 说明 prefill 需要足够大的 batch 才能用满 Tensor Core, 而 HBM 容量限制 batch, 这是逐层 prefill 的动机.

**PD 分离下谁去读**

PD 分离把 prefill 和 decode 放到不同 GPU 上, prefill 计算密集, decode 受访存带宽限制, 分开后各自选并行方式, 互不干扰. 在带外部 KV 存储的版本里, 每轮的流程是: prefill 引擎 (PE) 从存储读回命中的 KV, 计算新追加 token 的 KV, 把完整 KV 经 RDMA 发给 decode 引擎 (DE); DE 解码, 每攒满一个块就把新 KV 写回存储. 读盘的只有 PE. SGLang 加 Mooncake 的开源实现也是这样: Mooncake 维护者在 [issue #1860](https://github.com/kvcache-ai/Mooncake/issues/1860) 里确认, SGLang 的 PD 模式下 D 节点从不直接读 Mooncake Store, 总是 P 节点读 (或重算) 后用 Transfer Engine 写给 D.

这样一来, 读带宽只取决于 prefill 节点数. 论文默认的 DS 660B 配置是 2P4D, 即 2 个 prefill 节点, 4 个 decode 节点; 6 块 SNIC 里只有 2 块在读盘, 总读带宽约 100 GB/s, 另外 200 GB/s 闲着. 把这 4 块也用上, 读带宽从 $PsB$ 变成 $(P+D)sB$, 2P4D 下是 3 倍, 1P1D 下是 2 倍. 剩下的问题是 decode 节点读到的 KV 怎么到 prefill 节点的 GPU 上: 论文观察到计算网络的流量是间歇的, 集合通信以亚毫秒级突发出现, 突发之间网卡空闲, 可以用来转运 KV. 图 1 用一句话概括了这一点: 现状是 prefill GPU 利用率 40%, 存储网卡 100%; 改动后 prefill 与 decode 两侧的存储网卡都在读, GPU 利用率到 80%. 图 1 是示意图, 40% 和 80% 没有对应的实验测量.

**两条路径的数据流**

### 1.2. 逐层 prefill 与两种块布局

DualPath 建立在逐层 prefill 之上. 长上下文 prefill 时, 整个 batch 的 KV 都要进 HBM, batch 大小因此受限; LayerKV 和 PrefillOnly 注意到第 $i$ 层的注意力只需要第 $i$ 层的 KV, 于是 KV 可以按层加载, 用完即释放, HBM 里只放一层. 有效 batch (按 token 计) 大约扩大到层数倍. 代价是 KV 被切成很多细块: 每层一份, 每块只含 $block\_size$ 个 token. 按 §4.1 举的 64 token 一块, 32.7k 上下文是约 511 个块, 乘 61 层约 3.1 万个单层块. 这是 §5.2 要比较拷贝提交开销的原因.

为了兼顾细粒度传输和存储对象数量, 论文定义两种块 (附录 A.5). Layer Block 是形状 $[1, tokens, bytes]$ 的字节张量, 存若干 token 的单层 KV; Full Block 的形状是 $[layer, tokens, bytes]$, 存同一批 token 的全部层. 把 $n_{layer}$ 个 Layer Block 拼起来就是一个 Full Block, 不需要转换内存布局. 存储侧一律使用 Full Block, 并以 trie 组织, 让前缀相同的轨迹共享路径; GPU HBM 侧一律使用 Layer Block, 与逐层计算同步. DRAM buffer 位于两种粒度之间, 负责接收整块数据并按层切片发出.

![](./images/p05-figure-4-dual-path-loading-illustration-the-scheduler-dynamically.jpg)

> 图 4: 双路径加载示意, 左 (a) 为 PE 读路径, 右 (b) 为 DE 读路径, 标出 Full Block 与 Layer Block 的流向 (原文 Figure 4).

图 4 解析: 左右两张子图画的是同一对 PE 节点与 DE 节点, 每个节点里有 GPU, CNIC, DRAM 和 SNIC, 底部是共享的持久存储 (实验中是 3FS). 粗箭头是 Full Block, 细箭头是 Layer Block, 数字是步骤编号. 左图 (a) 是 PE 读路径, 命中 KV 从 PE 的 SNIC 进来; 右图 (b) 是 DE 读路径, 命中 KV 从 DE 的 SNIC 进来, 经两个 CNIC 之间的 RDMA 送到 PE 的 GPU. 图里没有画调度器, 也没有画未命中 token 的 KV 怎样回到 DE (b 图中的 (4) 是双向箭头). 两张图里 GPU 与 DRAM 之间都经过 CNIC, 没有直连, 这是第 4.1 节「所有流量走 CNIC」的体现.

**PE 读路径: 命中 KV 在 PE 节点上进出两次**

PE 读路径对应图 4a 的九步. (1)(2) 命中 KV 以 Full Block 从存储经 PE 的 SNIC 读进 PE buffer. 计算某一层之前, (3)(4) 把这一层的命中 KV 从 PE buffer 经 CNIC 写进 PE 的 HBM; GPU 用它计算新追加 token 的注意力和这一层的新 KV. 这一层算完, (5)(6)(7) 把这一层命中与新算的全部 KV 从 PE 的 HBM 经两端 CNIC 发到 DE buffer. (3) 到 (7) 每层重复一次. 全部层完成后, DE buffer 里有了完整的 prompt KV, (8)(9) 由 DE 的 CNIC 把它从 DE buffer 写进 DE 的 HBM, 开始解码.

数一下命中 KV 经过哪些链路: 在 PE 节点上, 它被 PE 的 CNIC 从 DRAM 读出一次 (3), 写进 HBM 一次 (4), 又从 HBM 读出一次 (5); 在 DE 节点上, 它被 DE 的 CNIC 写进 DRAM 一次 (7), 读出一次 (8), 写进 HBM 一次 (9). 这一份数据在两台机器的 PCIe 上一共走了 6 趟, 在两台机器之间的网络上走了 1 趟. 第 3 节的带宽约束就是把这些趟数逐项加起来.

**DE 读路径: 只有新 KV 回到 DE**

DE 读路径对应图 4b. (1)(2) 命中 KV 以 Full Block 经 DE 的 SNIC 读进 DE buffer. PE 计算每一层时, (3)(4)(5) 由 DE 的 CNIC 从 DE buffer 读出这一层的命中 KV, 经网络发到 PE 的 CNIC, 写进 PE 的 HBM. 这一层算完, PE 只把未命中 token 的新 KV 发回 DE buffer, 与那里已有的命中 KV 合并. 全部层完成后, (6)(7) 由 DE 的 CNIC 把完整 KV 从 DE buffer 写进 DE 的 HBM.

与 PE 读路径相比, 命中 KV 少走了两趟: 它不经过 PE 的 DRAM, PE 也不用把它发回 DE, 因为 DE buffer 里本来就有. 命中 KV 在 DE 节点上被 DE 的 CNIC 读两次 ((3) 发往 PE, (6) 做 H2D), 写一次 ((7)); 在 PE 节点上被写进 HBM 一次 ((5)). 网络上命中 KV 只走 DE 到 PE 一个方向, 反方向只有新 KV, 按 98.7% 的命中率不到总量的 2%. 这条路径的代价落在 DE 节点上: DE 的 CNIC 和内存要多承担一份读出流量.

**DE buffer 的用处与代价**

两条路径都让 KV 先进 DE 的 DRAM, 再整体 H2D 进 HBM. 论文承认这多了一次 H2D, 给 DE 的 DRAM 和 CNIC 增加压力, 用 GPUDirect RDMA 把 KV 直接写进 DE 的 HBM 本可省掉. 保留 DE buffer 的理由是 HBM 占用: 在这类负载里, 生成长度很短 (每轮平均 176 token), TTFT 在请求总时间里占比不小; 如果 KV 一边 prefill 一边直接写进 DE 的 HBM, 这部分 HBM 在整个 prefill 期间都被占着却不解码. 先放在 DRAM, 等 prefill 完成再分配 HBM, DE 的 HBM 只用于正在解码的请求.

prefill 时间有多长, 可以从图 15 的千卡离线实验看到: 任务前期 TTFT 在 10 到 27 秒之间. 而解码 176 个 token, 按在线实验约 30 到 50 毫秒的 TPOT, 只要 5 到 9 秒. 如果在 prefill 期间就占住 DE 的 HBM, 每个请求占用 HBM 的时间会是实际解码时间的两三倍. decode 期间, DE 每攒满一个块 (例如 64 token) 就把新 KV 立即写回存储, 下一轮这条轨迹的 prefill 就能命中. 论文没有给出写回走哪条链路的带宽分析, 第 3 节的式子也没有计入写回流量; 按每轮生成 176 token 对比读回 32.7k token, 写回量不到读量的 1%.

### 1.3. 不引入新瓶颈的条件: 式 (1) 到 (9)

**符号与每对 GPU 的流量**

§4.2 用一组不等式回答一个问题: 让 DE 节点也读盘之后, 新增的转运流量会不会把 CNIC 或 DRAM 变成新的瓶颈. 记号如下: $P$ 和 $D$ 是 PE 和 DE 的节点数, 每节点 $g$ 块 GPU, 每块 GPU 配一块带宽为 $B$ 的 CNIC; 每个节点的 SNIC 带宽是 $sB$, 即一块 SNIC 相当于 $s$ 块 CNIC; 每节点内存带宽为 $M$. 分析假设读盘流量均匀摊到所有 SNIC 上, 每块都满速, 只计命中 KV, 忽略新算的 KV, decode 写回和模型自身的通信.

在这个假设下, PE 节点合计每秒读进 $PsB$ 字节, 均匀发往 $Pg$ 块 PE GPU 与 $Dg$ 块 DE GPU 组成的每一对, 每对的流量是

$$
T_p=\frac{PsB}{Pg\cdot Dg}=\frac{Bs}{Dg^2},\qquad T_c=\frac{DsB}{Pg\cdot Dg}=\frac{Bs}{Pg^2},
$$

$T_p$ 来自 PE 读路径, $T_c$ 来自 DE 读路径. 一块 PE GPU 的 CNIC 面对 $Dg$ 个 DE 对端, 一块 DE GPU 的 CNIC 面对 $Pg$ 个 PE 对端, 下面每个约束都是「某个方向上经过的趟数 × 对端数 × 每对流量 ≤ 链路带宽」. 这里 CNIC 的读和写指的是它经 PCIe 从本机内存或 HBM 取数据和往里放数据, 环回 H2D 同时占读和写.

**四个约束逐项对应图 4 的箭头**

PE 节点的 CNIC 读出命中 KV 有两处, 都在 PE 读路径上: (3) 从 PE buffer 读出, (5) 从 HBM 读出发往 DE. 写入也有两处: PE 读路径的 (4) 写进 HBM, DE 读路径的 (5) 写进 HBM. 于是

$$
2T_p\cdot Dg=\frac{2Bs}{g}\le B,\qquad (T_p+T_c)\cdot Dg=\frac{Bs}{g}\Big(1+\frac{D}{P}\Big)\le B\;\Rightarrow\;\frac{P}{D}\ge\frac{s}{g-s}.
$$

第一式化简后是 $s\le g/2$. 论文 §4.2 写成 $s\le g$, 条件放宽了一倍. 实验使用 $g=8$, $s=1$, 同时满足两个条件, 因此这处推导差异不会改变该组实验的可行性.

DE 节点的 CNIC 读出: DE 读路径的 (3) 发往 PE 和 (6) 做 H2D 各一次, 加上 PE 读路径的 (8) 一次; 写入: PE 读路径的 (7) 写进 DE buffer 和 (9) 写进 HBM 各一次, 加上 DE 读路径的 (7) 一次. 由此

$$
(T_p+2T_c)\cdot Pg\le B\;\Rightarrow\;\frac{P}{D}\le\frac{g-2s}{s},\qquad (2T_p+T_c)\cdot Pg\le B\;\Rightarrow\;\frac{P}{D}\le\frac{g-s}{2s}.
$$

内存带宽方面, PE 节点的 DRAM 只服务 PE 读路径, 被 SNIC 写入一次, 被 CNIC 读出一次, 合计 $2sB\le M$. DE 节点的 DRAM 服务自己读的数据 (SNIC 写入一次, CNIC 读出两次, 共 $3sB$), 再服务从 PE 发来的数据 (写入一次读出一次, 按节点平摊为 $2sB\cdot P/D$), 合计 $(3+2P/D)sB\le M$.

**区间, 边界与没有算进去的流量**

代入实验平台的数: $g=8$, $s=1$, $B=50$ GB/s, $M=500$ GB/s. PE 写入约束给出下界 $P/D\ge 1/7$; DE 读出约束给出 $P/D\le 6$, DE 写入约束给出 $P/D\le 7/2$, DE 内存约束 $(3+2P/D)\times 50\le 500$ 也给出 $P/D\le 7/2$. 区间是 $1/7\le P/D\le 7/2$, 上界由 DE 的 CNIC 写入和 DE 的内存带宽同时决定. 论文的实验配置 2P4D, 1P1D, 1P2D 以及图 8 扫过的 1P1D 到 2P1D 都落在区间里. 区间的上界说明一件事: PE 节点数相对 DE 越多, 每个 DE 节点要转运的 PE 读路径流量越大, DE 的 CNIC 写入最先吃紧. 所以 DualPath 适合 decode 节点不少于 prefill 节点的部署, 而 Agent 负载生成短, prefill 重, 实际配置的 $P/D$ 往往不会太大.

这组约束有几处没有覆盖. 其一, 它假设两条路径的流量严格按 SNIC 带宽均分, 实际由调度器按队列长度逐请求选路 (第 4.2 节), 流量分配有波动, 图 13 测到的存储网卡最大/平均比在有调度时是 1.184, 不是 1. 其二, 它只看节点内的 CNIC 和 DRAM, 没有看存储集群的总带宽: $(P+D)sB$ 能不能读出来, 取决于 3FS 集群的规模和 SSD 数量, 实验里 3FS 关闭了 DRAM 缓存, 所有读都打到 SSD 上, 论文没有给出 3FS 集群的配置. 其三, CNIC 上原有的模型流量 (EP 的 all-to-all, PD 之间的 KV 转发) 不在式子里, 论文的处理是用第 4.1 节的优先级隔离, 让 KV 只用模型流量剩下的带宽. 3FS 单客户端的读带宽实测见 [3FS 解析](../../4-%E5%BC%80%E6%BA%90%E4%BB%93%E5%BA%93/4.1-3fs/02-3fs-analysis.md) 中的 KVCache 一节.

## 2. 流量隔离与调度

**所有 GPU 进出流量都绕道 CNIC**

DualPath 多出来的转运流量与模型推理的集合通信共用 CNIC. 推理时 EP 的 all-to-all 在每层都要做, 对延迟敏感, 被 KV 流量挤占就会直接拉长 TPOT 和 TTFT. 论文 §5.1 的做法是把所有经过 GPU 的数据都交给 CNIC 搬运, 包括本机 DRAM 与 HBM 之间的拷贝: H2D 和 D2H 不用 GPU 的 copy engine, 改为 CNIC 的 RDMA 环回, 由 CNIC 从 DRAM 读出再写进同一节点的 HBM. 这样所有流量都在 CNIC 一个点上排队, 可以用网卡的 QoS 统一管. 如果 KV 走 copy engine 或 GPUDirect Storage, 它会直接上 PCIe, 而 PCIe 没有流量优先级, 与 CNIC 发起的集合通信 DMA 抢同一段链路, 网卡的 QoS 管不到. DeepEP 的通信方式见 [DeepEP 解析](../../4-%E5%BC%80%E6%BA%90%E4%BB%93%E5%BA%93/4.3-deepep/02-deepep-analysis.md).

隔离用 InfiniBand 的虚拟通道 (VL). 附录 A.1 给了配置: 开 4 个 VL, 模型通信用 VL0, VL1 和 VL3, KV 转运用 VL2; VL0, VL1, VL3 在高优先级表和低优先级表里权重都是 192, VL2 只出现在低优先级表里, 权重 64; 高优先级上限 $high\_limit=240$. 正文说这样给模型通信保留约 99% 的带宽, 但没有写这个数怎么来的. 按 InfiniBand 规范的单位可以推出来: 仲裁表权重的单位是 64 字节, 高优先级上限的单位是 4KB. 高优先级 VL 有数据时, 仲裁器最多连续发 $240\times4\text{KB}=960$KB 的高优先级数据, 然后必须给低优先级表一个机会, VL2 在低表里一次最多发 $64\times64=4$KB. KV 流量在模型通信繁忙时最多拿到 $4/(960+4)\approx 0.4\%$, 模型通信拿到约 99.6%. 模型通信空闲时高表无数据, VL2 可以用满整条链路. RoCE 网络上对应的机制是 DSCP 或 TC 分类加上 PFC 和带宽权重.

### 2.1. 拷贝提交开销与 doorbell 批处理

绕道 CNIC 还有一个收益在 CPU 侧. 第 2.1 节算过, 一个 32.7k 上下文的请求有约 3.1 万个 Layer Block. 论文 §5.2 测得一次 cudaMemcpyAsync 的提交开销是 5 到 7 微秒, 一次 RDMA write 约 1 微秒, 再用 doorbell 批处理把多个工作请求合并成一次门铃写. 按这两个数换算, 一个请求的 Layer Block 若逐块用 cudaMemcpyAsync 提交, CPU 要花约 0.16 到 0.22 秒, 改用 RDMA 是约 0.03 秒, 批处理后更低. 一次 prefill 前向往往包含多个请求, 前一种开销会直接加到 TTFT 上. 这个换算是按论文给的单次开销乘块数得到的, 论文没有给出整请求的提交耗时.

代价是 PCIe 流量翻倍. 环回 H2D 时, 数据先从 DRAM 经 PCIe 进 CNIC, 再从 CNIC 经 PCIe 进 GPU, 同一份数据过两次 PCIe, 而 copy engine 只过一次. 第 3 节的约束里 CNIC 的读和写分开计算, 正是在计入这一点; §4.2 还假设每对 GPU 与 CNIC 挂在同一个 PCIe switch 下, 环回流量不出 switch. 论文没有测 PCIe 链路本身的利用率, 也没有给出开关 VL 隔离前后 TPOT 的对比, 隔离效果只能从在线实验的 TPOT 达标间接看出.

**引擎间调度: 用 token 数代替时间**

调度分三层: 跨引擎选 PE 和 DE, 选读路径, 引擎内组 batch. 引擎对应一块 GPU, 同一节点的引擎编为一组, 组内 rank 0 作为 leader 与中心调度器通信. 每个引擎上报三个量: $seq_e$ 是引擎上的请求数, $tok_e$ 是引擎上尚未处理完的 token 数, $read\_q$ 是所在节点存储网卡上待读的字节数. 论文用 token 数估计计算负载, 用待读字节估计 I/O 负载, 不直接测量耗时.

请求先进中心调度器的等待队列. PE 选择在某个 PE 组来取任务时触发, 按 FIFO 逐个分配 (算法 1), 把组内引擎分成三类: $tok_e>\beta$ 的过载引擎 C1 不接新请求; 剩下的按所在节点读队列分成 $read\_q\le\alpha$ 的 C2 和 $read\_q>\alpha$ 的 C3. 新请求优先给 C2 中 $tok_e$ 最小的引擎, C2 为空才看 C3, 两类都空就结束这次取任务. 优先 C2 的理由是读队列短的节点如果接不到新请求, 存储网卡会闲下来. $\alpha$ 取存储网卡 3 秒能读完的 token 数, $\beta$ 取一块 GPU 5 秒能处理的 token 数, 都事先测定 (附录 A.4).

DE 选择分两级, 不保持全局 FIFO. 第一级在 DE 组来取任务时把全局队列清空, 每个请求分给 $\sum tok_e$ 最小的组, 进入该组的私有队列. 第二级先按组内剩余 HBM 总量 (假设没有碎片) 从私有队列头部数出最多能放下的请求集合 $R$, 算阈值 $Z=1.05\times(\sum_{r\in R}len_r+\sum_{e\in E}tok_e)/|E|$; 然后逐个弹出队头, 在 HBM 够用的 DE 里, 优先选 $tok_e+len_r\le Z$ 的那些中 $seq_e$ 最小的, 这一类为空时选其余 DE 里 $tok_e$ 最小的, 所有 DE 的 HBM 都不够就结束. PE 和 DE 定下之后, 比较两者所在节点的读队列, 哪边短就从哪边读. 一个请求只走一条路径, 把同一请求拆到两条路径上读被列为未来工作.

![](./images/p08-figure-5-an-illustration-of-inter-engine-pe-scheduling.jpg)

> 图 5: 引擎间 PE 调度示意, 横条为各引擎未处理 token 数, 下方为节点存储网卡读队列 (原文 Figure 5).

图 5 解析: 两个方框各是一个节点, 每行一块 GPU, 横条长度是该引擎的 $tok_e$, 竖虚线是 $\beta$; 方框下方的橙色条是该节点存储网卡的读队列, 竖虚线是 $\alpha$. 左边节点读队列短于 $\alpha$, 横条越过 $\beta$ 的两块 GPU 标为过载, 另两块是候选, 其中 $tok_e$ 最小的标为最佳. 右边节点读队列长于 $\alpha$, 两块未过载的 GPU 只是次选. 图注说明八块 GPU 同属一个 PE 组. 图中没有画 DE 选择与读路径选择.

### 2.2. 引擎内调度: 计算配额与 DP attention 的空泡

PE 内部的问题来自 DP attention. 大 MoE 模型推理时, 注意力按数据并行切, 每块 GPU 处理自己的一批请求; 之后 MoE 层用 EP, 所有 GPU 要做 all-to-all, 必须同步. 如果各 GPU 上的注意力计算量差别大, 快的 GPU 在 all-to-all 前等慢的, 形成空泡. Agent 负载里请求的上下文长度从几千到 6 万多 token 不等, 每个请求的注意力时间与上下文长度相关, 按请求数均分会有明显不均.

论文的做法是给注意力层的预计执行时间设上限, 称为计算配额, 实验中 DualPath 与 Oracle 都取 300 毫秒 (附录 A.4). 每个请求在一次前向里用一对数 $(cached, bsz)$ 描述: $cached$ 是已有 KV 的 token 数 (来自存储命中或之前的前向), $bsz$ 是本次要算 KV 的 token 数. 由这些数算出注意力层的理论计算量, 再用事先拟合的「计算量到耗时」关系估计执行时间. 组 batch 时按 FIFO 往里加请求, 只要预计时间不超过配额就继续; 加某个请求会超时, 就对它的 $bsz$ 做二分查找, 找到能塞进剩余配额的 $bsz'$, 这个请求走 chunked prefill. 图 6 右对比了用配额前后的 GPU 时间线, 图 14 是对应的实测. 300 毫秒乘 61 层约 18 秒, 与图 15 中 10 到 27 秒的 TTFT 量级相符. DE 不做引擎内调度, 所有请求都放进前向 batch. MoE 推理里 DP attention 与 EP 的组合方式见 [MoE 推理部署](../../../llm-guide/6-训练与推理优化/6.1-训练基础设施/6.1.8-MoE系统与并行/02-MoE推理部署/02-MoE推理部署.md).

**实验口径与结果**

**硬件, 模型, trace 与基线**

测量条件集中在 §7.2 和附录 A. 硬件是 InfiniBand 互联的 GPU 集群, 每节点 8 块 Hopper GPU, 双路 CPU, 8 块 400Gbps CNIC 和 1 块存储网卡; 3FS 集群关闭了内部 DRAM 缓存, 单节点能读满 400Gbps. 论文没有说是 H800 还是 H100, 也没有给 3FS 集群的节点数和 SSD 数. 模型有三个: DS 660B 即公开的 DeepSeek-V3.2, 带 DSA; DS 27B 是内部的缩小版, 结构相近, 附录 A.2 给出 30 层, 隐藏维度 2560, 72 个路由专家, indexer top-k 1024; Qwen 32B 即 Qwen2.5-32B, 稠密 GQA. 默认配置是 DS 660B 用 2P4D, DS 27B 用 1P1D, Qwen 32B 用 1P2D; DS 模型用 EP 加 DP attention. 每节点给 KV 分配的 DRAM, DualPath 在 DS 模型上是 80GB, 在 Qwen 上是 320GB.

负载是 1.1 节的三份生产 trace, 回放时工具调用耗时按零处理, 前一轮结束立刻发下一轮. 基线有三个. Basic 是未修改的内部框架, 只有 PE 读盘, 也没有逐层 prefill. Oracle 在 DualPath 基础上跳过所有读盘, D2H 和 H2D 以及 PD 之间的 KV 传输, 代表零 I/O 的上限. SGL(MC) 是 SGLang (commit 19089aa) 加 HiCache, 以 Mooncake Store 为分布式缓存, 3FS 为后端, Mooncake Transfer Engine 做 PD 传输, 每节点用 1.5TB DRAM. 论文自己说明 SGL(MC) 与 DualPath 实现差异大, 比较不公平, 加速比只对 Basic 报告; Qwen 上 SGL(MC) 用 TP=8, DualPath 用 DP. 离线指标是全部轨迹跑完的作业完成时间 (JCT); 在线指标是 TTFT, TTST (第二个 token 的时间) 和 TPOT, SLO 是 TTFT 不超过 4 秒, TPOT 不超过 50 毫秒.

**离线 rollout: 1.87 倍里有多少来自双路径**

离线场景对应 RL 训练的 rollout: $n$ 个 agent 同时开始, 测全部结束的时间. 图 7 按模型分三行, 按 MaxLen 分三列, 横轴是 agent 数. 摘要里的 1.87 倍出自 DS 660B, 64K, 2048 个 agent 这一格: Basic 约 10,100 秒, DualPath 约 5,400 秒. 同一列里 512 个 agent 时 Basic 约 2,900 秒, DualPath 约 2,100 秒, Oracle 约 2,000 秒; 4096 个 agent 时 Basic 约 19,500 秒, DualPath 约 10,400 秒, Oracle 约 9,400 秒. agent 越多, 读盘压力越大, 加速比越高. DS 660B 上 DualPath 与 Oracle 的差距在 10% 上下, 32K 列 4096 个 agent 时 DualPath 甚至略快于 Oracle, 说明测量本身有几个百分点的波动. DS 27B 和 Qwen 32B 上 DualPath 比 Oracle 慢 1.09 到 1.85 倍, 原因是 1P1D 和 1P2D 只有两三块存储网卡, 小模型算得快, 存储带宽仍然不够.

图 7 解析: 每格四根柱分别是 SGL(MC), Basic, DualPath 和 Oracle 的 JCT, 越低越好; N/A 表示 SGL(MC) 在该配置中途出错. 三行从上到下是 DS 27B, DS 660B, Qwen 32B, 三列是 32K, 48K, 64K. 读图时要注意两点: Basic 与 DualPath 之间同时差着逐层 prefill 和双路径两项改动; SGL(MC) 的 DRAM 是 DualPath 的近 20 倍, 慢的原因主要在实现, 不能读成 Mooncake 架构本身的上限.

### 2.3. 存储带宽决定性能的两组证据

图 8 在 DS 27B 上扫 P/D 配比. 论文指出三组性能相近的配置: Basic 1P1D 与 Basic 1P2D, DualPath 1P1D 与 Basic 2P1D, DualPath 2P1D 与 DualPath 1P2D. 每组的可用存储带宽相同: Basic 只用 prefill 节点的网卡, 1P1D 和 1P2D 都是 1 块; DualPath 1P1D 用 2 块, Basic 2P1D 也是 2 块; DualPath 2P1D 和 1P2D 都是 3 块. 计算资源不同而 JCT 相近, 说明 JCT 由存储网卡数决定. 2.46 倍的最大加速比出现在 1P2D: Basic 约 8,300 秒, DualPath 约 3,400 秒, 网卡数从 1 块变 3 块, 加速比不超过 3 倍, 符合带宽上限. 平均加速比是 1.64 倍.

图 9 改变每轮追加长度和生成长度 (DS 660B, 64K, 1024 个 agent). 追加长度放大后, 每轮要算的 token 多了, 计算压力上升, Basic 逐渐接近 DualPath 和 Oracle, DualPath 相对 Basic 的加速比在 1.82 到 1.99 倍之间. 图中三条曲线的 JCT 都随追加倍数增大而下降, 原因在实验方法: 追加放大后轨迹在 MaxLen 处截断, 平均轮数变少, 总读量下降. 这一点论文只用一句「再在给定 MAL 截断」带过, 读图时需要知道 JCT 下降不代表系统变快. 生成长度变长时, 两次 prefill 之间的间隔变长, 单位时间要读的 KV 变少, 趋势相同.

**在线服务: 1.96 倍是两个点的平均**

在线实验按泊松过程以给定速率 (APS, 每秒新到 agent 数) 注入 agent, 每个 agent 从第 0 轮回放到末轮. 实验在 TTFT 超过 4 秒时终止, 或在稳态时终止, 稳态定义为 150 秒滑动窗口内 TTFT 与 30 分钟前相比变化小于 5%. 论文没有写在线实验用的是哪份 trace. 图 10 中 DS 660B 的 Basic 在约 0.2 APS 时 TTFT 超过 SLO, DualPath 撑到约 0.45 APS, 比值 2.25; DS 27B 是约 0.3 对约 0.5, 比值 1.67. 摘要的「平均 1.96 倍」就是 $(2.25+1.67)/2$, 只有两个模型, Qwen 32B 没有做在线实验.

TTFT 的构成见图 12 左 (DS 660B): 各 APS 下 DualPath 的排队, 分配, 读 KV, prefill 四段基本稳定, Basic 的排队时间随 APS 迅速增长, 原因是存储带宽不足, 请求在读队列里等. TPOT 方面 DualPath 与 Basic 持平, 说明 KV 转运没有拖慢解码, 这是第 4.1 节 VL 隔离有效的间接证据; 论文没有做关闭 VL 隔离的对照实验. DS 27B 上 Basic 和 DualPath 的 TPOT 都明显高于 Oracle, 论文归因于小模型上 PD 之间 KV 传输开销占比大, 留作未来工作. SGL(MC) 的 TTST 异常低, 论文推测是前两个 token 几乎同时到达客户端, 属实现问题.

**千卡扩展, 负载均衡与工作集**

表 3 把规模扩到 1,152 块 GPU. 离线 2P4D 跑 2K 个 agent 用 3,167 秒, 48P96D 跑 48K 个 agent 用 3,201 秒, 资源扩 24 倍, 负载扩 24 倍, JCT 持平. 在线 2P4D 在 0.4 APS 下 TTFT 1.739 秒, 44P88D 在 8.8 APS 下 1.847 秒, 资源扩 22 倍, 容量扩 22 倍. 这说明调度器和存储在这个规模下没有成为瓶颈 (调度器 CPU 占用低于 10 核), 但也没有规模收益, 论文在 §7.6 承认大规模实验相对等成本的多个小单元没有额外的 JCT 或容量提升. 图 15 是 48P96D 离线过程: Prompt TPS 在 900 到 2,400 秒间稳定在约 $6\times10^7$ token/s, TTFT 开头冲到约 27 秒, 之后在 10 到 13 秒.

Prompt TPS 的口径论文没有定义, 可以用算力反推. 若它只计未命中 token, 384 块 PE GPU 每块每秒约 16 万 token, 按 1.1 节每 token 约 142 GFLOPs 要 22 PFLOPS, 超过单卡峰值一个数量级, 不可能; 所以它包含命中 token. 按 98.7% 命中率, 未命中 token 约 $7.8\times10^5$/s, 每块 PE GPU 约 2,000 token/s, 约 0.29 PFLOPS, 是 Hopper 稠密 FP8 峰值 (约 0.99 PFLOPS) 的三成. 命中部分按每 token 40KB 算约 2.4 TB/s, 而 144 个节点的存储网卡合计 7.2 TB/s, 利用率约三分之一. 这组数说明 48P96D 的稳态瓶颈已经不在存储网卡. 这一反推假设图 15 用 64K trace, 论文没有说明.

负载均衡有两张图. 图 13 测存储网卡流量的最大/平均比, 有调度时 1.184, 轮询时 1.528. 正文说统计的是「三台机器」上的所有存储网卡, 而 DS 660B 默认 2P4D 是六台, DS 27B 的 1P1D 是两台, 三台对应 1P2D 或 2P1D, 论文没有说明是哪组实验. 图 14 测 EP 组内各 GPU 注意力时间的最大/平均比, 正文说「任务前 5% 内低至 1.06」. 图上 512 个 agent 的曲线到任务进度 20% 时已升到约 1.9, 在 35% 到 40% 附近与不用调度的曲线相交, 论文的解释是后期负载不足, 比值失去意义. 1.06 只代表任务开头一小段.

§8.2 用 Little 定律估 KV 工作集: $\lambda\bar T\times total\_len/2$, 其中 $\lambda$ 是 APS, $\bar T$ 是平均 JCT (图 11). 论文给出 DS 660B 在线时从 APS 0.1 的 69GB 到 APS 0.45 的 681GB. 按 64K trace 的 $total\_len=55958$, 每 token 40KB, 图 11 读出 APS 0.1 时 $\bar T$ 约 575 秒, 0.45 时约 1,100 秒, 得到约 64GB 和 554GB; 每 token 计入 indexer cache 按 48KB 算, 得约 77GB 和 665GB. 论文的两个数落在这两种口径之间, 每 token 字节数文中没有给出. 更重要的是后半段推理: 真实场景有工具调用耗时, 若 JCT 变为 $r$ 倍, 同样的推理资源能承载的 APS 也变为 $r$ 倍, 工作集按 $r^2$ 增长, 很快超过 DRAM 池容量. 这是论文主张直接以 SSD 存储为后端, 不依赖 DRAM 池的主要论据.

## 3. 与 Mooncake 等方案的关系

**Mooncake 与 HiCache: 池子放在哪里, 谁去读**

Mooncake (FAST'25) 是 Kimi 的线上推理架构, 以 KV cache 为中心: 把 GPU 集群里各节点的 CPU 内存和 SSD 组成分布式 KV 池, 由全局调度器按缓存命中和负载选 prefill 实例, 跨节点传输用 Transfer Engine 走 RDMA. 它和 DualPath 都做 PD 分离, 都做逐层传输, 都有缓存感知调度. 差别在两处. 第一是 KV 的落点: Mooncake 的主体是 DRAM 池, SSD 是下一级; DualPath 的 KV 只存在独立的 3FS 存储集群里, 节点 DRAM 只用作中转 buffer, DS 模型每节点 80GB. 按 5.5 节的工作集分析, Agent 负载的工作集随 JCT 平方增长, DRAM 池的命中率难以保持, 这是论文选 SSD 后端的理由. 第二是读的发起方: 在 SGLang 加 Mooncake 的 PD 模式里, 总是 prefill 侧读池子再转给 decode 侧 (Mooncake issue #1860), 与 Basic 相同; DualPath 改变的就是这一点.

HiCache 是 SGLang 的分级缓存, 层级为 GPU HBM, 主机 DRAM, 外部存储 (Mooncake Store, 3FS 等), 实验中的 SGL(MC) 就是这一组合. 两者的比较有前提: 两种 DRAM 用量相差近 20 倍, 并行方式不同 (Qwen 上 TP 对 DP), SGL(MC) 在大配置上出错. 论文自己放弃了与 SGL(MC) 算加速比. §9 还说 DualPath 可以与中间层 DRAM 缓存结合, 但「收益很小」, 这句话没有附实验数据. 在 3FS 关闭 DRAM 缓存, 存储网卡打满的设定下, 读带宽受 SNIC 限制, DRAM 缓存若在本节点能省掉 SNIC 读, 收益应当取决于命中率; 论文没有给出这组测量.

### 3.1. 其他相关工作与 DeepSeek 自身的 KV 落盘

§9 把相关工作分成三类. 分布式内存池: Mooncake 和 TokenLake (段级前缀缓存池), DualPath 的区别是直接以存储后端为对象, 平衡所有 SNIC 的流量, DRAM 用量小得多. 单路径 I/O 优化: Strata 联合设计 GPU 辅助 I/O 与缓存感知调度, KVPR 用重算与传输重叠, TailorKV 用分层混合量化, 都在一条读路径上减少字节或隐藏延迟; DualPath 增加路径, 两类方法可以叠加. 推理系统: PD 分离 (DistServe, Splitwise) 已经是事实标准, DualPath 在其上改读路径. 对照来看, DualPath 不压缩 KV, 不改模型, 只改数据从哪块网卡进来, 经哪条链路到 GPU.

DeepSeek 把 KV cache 落到磁盘不是从这篇论文开始的. 2024 年 8 月 DeepSeek API 上线硬盘缓存, 命中部分按更低价格计费; 3FS 的 README 把推理 KVCache 列为主要用途之一, 3FS 解析里给出了单客户端读峰值约 40 GiB/s 的数据. DualPath 补上的是这套部署在 Agent 负载下的带宽问题. 模型侧, V4 与 V4.1-Flash 进一步压缩 KV 体积, 并把 KV 在 HBM, 主机内存和 SSD 之间分层放置, 从字节数一侧降低同一个 cache-compute 比. 两条线合起来看, DeepSeek 的推理栈把 KV 当作要长期保存, 跨轮复用的数据, 而 Agent RL 的 rollout 是对这套设计压力最大的负载. 前缀缓存的一般机制见 [增量式 Prefill 与 KV-Cache 机制](../../../llm-guide/6-训练与推理优化/6.6-推理框架与高级优化/6.6.1-推理框架/01-增量式Prefill与KV-Cache机制/01-增量式Prefill与KV-Cache机制.md), 分页管理见 [PagedAttention 原理](../../../llm-guide/6-训练与推理优化/6.4-KV缓存与内存优化/6.4.1-PagedAttention原理/6.4.1-PagedAttention原理.md).

**需要打折看的几处结论**

几处数字的口径与标题措辞有出入, 按章节汇总. §4.2 式 (1) 的条件应为 $s\le g/2$, 论文写成 $s\le g$. §3 图 3 的 28.8 倍混合了 BF16, FP8 和 FP4 三种精度, 14.4 倍的 I/O 算力比下降因此偏大. 摘要和 §7.3 的 1.87 倍包含 Basic 没有的逐层 prefill, 双路径加调度单独约 1.4 到 1.6 倍. 摘要和 §7.4 的 1.96 倍是两个模型加速比的算术平均, 在线实验用的 trace 没有说明.

另有几处缺少支撑数据. §7.5 图 13 的「三台机器」与默认配置不符, 图 14 的 1.06 只覆盖任务前 5%. §9 关于结合 DRAM 缓存收益很小的说法没有实验. 附录 A.1 的「约 99% 带宽留给模型通信」可以按 InfiniBand 仲裁单位推出 (见 4.1 节), 但论文没有测关闭隔离时 TPOT 的变化. §8.2 的工作集数字依赖的每 token 字节数也未给出. 图 8 的等带宽配置对比支持存储网卡构成瓶颈, 上述缺项主要限制了对收益幅度和适用范围的判断.

**把双路径写成一个流网络**

前面的不等式逐条清点链路,这里把它们合成一个流网络. 对请求$r$,命中KV体积为$K_r$,新增KV体积为$U_r$,并用$x_r\in\{0,1\}$表示读路径:$x_r=0$从PE读,$x_r=1$从DE读. 在时间窗$\Delta$内,分给PE节点$p$、DE节点$d$的请求集合分别记为$R_p,R_d$. 存储入口负载是

$$
S_p=\sum_{r\in R_p}(1-x_r)K_r,\qquad S_d=\sum_{r\in R_d}x_rK_r.
$$

它们要满足$S_p\le sB\Delta$与$S_d\le sB\Delta$. 路径选择并未改变总读量$\sum_rK_r$,只是把它从$P$个入口摊到$P+D$个入口. 理想均衡时每个入口承担$\sum_rK_r/(P+D)$;因此仅由入口数得到的加速上限为$(P+D)/P$. 2P4D的上限是3倍,实测低于此值,差额来自计算、跨节点转发、队列不均和无法完全重叠的尾部.

CNIC约束需要计入每条路径的复制次数. 令$a^{read}_{ep}$表示路径$a$在端点$e$产生的CNIC读次数,$a^{write}_{ep}$同理,则任一端点都应满足

$$
\sum_r a^{read}_{e,x_r}K_r\le B\Delta-C^{read}_e,\qquad
\sum_r a^{write}_{e,x_r}K_r\le B\Delta-C^{write}_e,
$$

$C_e$是模型集合通信在同一时间窗消耗的字节. 论文的式子等价于令$C_e=0$后求静态均匀流. VL隔离保持容量不变,改变可抢占顺序:当$C_e$出现突发时,KV流量的有效服务率暂时接近零;突发结束后再吃剩余带宽. 因此平均容量可行并不足以保证尾延迟,还要约束最长连续高优先级突发.

若一次EP通信持续$\tau_h$,KV块的排队等待至少可能增加$\tau_h$. 连续经过$l$层时,最坏情况会累积$l\tau_h$;实际不会层层取到最坏值,但长尾由突发相位决定. 可证伪的实验是固定总通信字节,只改变突发长度:短而频繁与长而稀疏具有相同均值,如果TTFT尾部明显不同,平均带宽模型便不够.

### 3.2. 两条路径何时真的能并行

“两块网卡同时读”需要满足一组先后关系. 对第$i$层,记存储读取、切片、跨节点转运、注意力计算、新KV回传的完成时刻为$R_i,C_i,N_i,A_i,W_i$. DE路径至少满足

$$
R_i\prec C_i\prec N_i\prec A_i\prec W_i,\qquad A_i\prec A_{i+1}.
$$

PE路径少一次远端输入,但命中KV在计算后还要随新KV发往DE. 双路径的收益来自不同请求、不同层的这些阶段交错,并非同一个层内凭空消除读取. 若第$i+1$层数据在第$i$层计算结束前就绪,读取时间可被隐藏;稳态吞吐近似由各流水段最大服务时间决定:

$$
T_{stage}\approx\max(T_{storage},T_{transfer},T_{attention},T_{moe}).
$$

首层仍要等待KV,末层之后仍有排空时间. 只有少量请求时,启动与排空占比高,加一条路径也难接近入口数上限. 并发足够大后,调度器才有别的请求填补空档. 这与图7中agent数增加后收益上升一致.

逐层prefill还要求层$i$的数据能独立定位. Full Block在存储侧减少对象数,DRAM再按固定偏移暴露Layer Block,于是切片无需重排元素. 若模型不同层的KV尺寸不同、使用变长量化元数据,偏移表便成为读取前置依赖;任何一次解析或内存拷贝都会进入关键路径. 因此该设计更适合层布局规则、块尺寸固定的模型.

可以用甘特图而非总吞吐验证重叠:记录每层SNIC读、CNIC转运、GPU kernel与EP通信的起止时间,计算$1-\sum_j idle_j/T$以及读计算重叠率. 若开启DualPath后存储利用率上升,但GPU空泡未降,瓶颈只是移到跨节点传输;若GPU空泡下降而TPOT恶化,说明低优先级隔离没有守住解码通信.

**路径选择是带约束的负载均衡**

论文比较两端$read_q$后逐请求选较短队列,可以写成最小预计完工时间. 对路径$a$,请求$r$的代价近似为

$$
\hat T_{r,a}=\frac{Q^{storage}_a+K_r}{\mu^{storage}_a}+\frac{Q^{net}_a+c_aK_r}{\mu^{net}_a}+T^{sync}_{r,a},
$$

其中$Q$是已排队字节,$\mu$是近期服务率,$c_a$是CNIC复制系数. 只比较$read_q$相当于假设网络项和同步项相等. DE侧CNIC正在承担高强度EP通信时,这个假设会失效:其SNIC队列虽短,读出的KV却堵在DRAM. 更稳健的选择应取两段队列的最大完成时刻,同时保留模型通信的安全余量.

逐请求二选一避免了重组屏障. 若把一个请求按块拆给两条路径,完成时间由较慢分片决定:

$$
T_r=\max(T_{r,P}(zK_r),T_{r,D}((1-z)K_r))+T_{merge}.
$$

连续变量$z$可让两边精确均衡,但块完成乱序、失败重试和逐层消费会增加状态. 当请求很大且数量少时,拆分能减少巨型请求造成的队头阻塞;请求很多时,逐请求分配已经能由大数效应均衡,拆分收益有限. 可按并发数与$K_r$变异系数做二维消融,找出拆分开始有价值的区域.

FIFO保护到达顺序,却会让一个64K请求挡住后面的短请求. 最短剩余读取时间能降低平均TTFT,可能饿死长请求. 实用折中是老化优先级:$priority_r=w_r+\eta(t-t_r)$,其中$w_r$偏好小请求,等待项随时间增加. 在线系统应同时报告平均值、P99和最长等待,否则平均TTFT改善可能来自牺牲少数长轨迹.

**计算配额的数学含义**

DP attention之后接EP同步,一组$g$块GPU的层耗时由最慢者决定. 令第$j$卡注意力工作量为$h_j$,单卡时间函数为$f(h_j)$,该层有效利用率可写为

$$
\eta=\frac{\sum_{j=1}^{g}f(h_j)}{g\max_j f(h_j)}.
$$

完全均衡时$\eta=1$;一张卡耗时翻倍而其余不变时,$g=8$对应$\eta=9/16$. 计算配额限制每卡预测时间,本质上是在控制$\max_jf(h_j)$,同时用chunked prefill把大请求切开.

工作量不能只用token数. 稠密注意力中,追加$q$个token面对$c$个缓存token,核心项近似$q(c+q/2)$;稀疏注意力的主注意力约$qk$,Indexer约$qc$. MoE线性层大致与$q$成正比. 可用

$$
h(q,c)=a q+bqk+dqc+e q^2
$$

拟合不同结构,$a,b,d,e$由离线测量得到. 若直接以$q+c$估计,长缓存短追加与短缓存长追加可能有相同token总数,实际时间却完全不同. 论文使用理论计算量再拟合耗时,方向是对的;模型升级、kernel切换或频率变化后需要重新标定.

配额过小会产生大量chunk,每个chunk重复调度、同步和固定kernel开销;配额过大又加剧跨卡空泡. 设单chunk固定成本为$u$,失衡等待为$w(Q)$,配额$Q$的总损失近似$nu+w(Q)$,前者随$Q$增大下降,后者上升. 最优点依赖请求分布,300毫秒不应脱离硬件照搬. 可从50到600毫秒扫描,同时测GPU空泡、chunk数、TTFT和吞吐,验证是否存在宽阔平台而非偶然单点.

**内存、PCIe与块大小的联合约束**

块越小,逐层消费越早,尾部浪费越少;块越大,元数据和提交次数越少. 令每块有效载荷$z$,请求KV总量$K$,单次提交固定成本$u$,链路带宽$b$,则纯传输时间下界为

$$
T(K,z)=\left\lceil\frac Kz\right\rceil u+\frac Kb.
$$

若64-token Layer Block的载荷约2.56MB,32.7K上下文、61层产生约3.1万次提交. $u=6\mu s$时固定成本约186ms;RDMA提交$1\mu s$时约31ms. doorbell把$m$个请求合批后,固定项接近$\lceil K/(mz)\rceil u$,但批过大也会延迟首块发出.

环回RDMA令同一字节两次经过PCIe交换结构. 若PCIe单向有效带宽为$b_p$,CNIC线速为$B$,要让一条400Gbps链路持续环回,交换结构至少承担读写合计约100GB/s. 多块GPU共享上行时,理论CNIC约束满足也可能被PCIe拓扑截断. 验证时应按PCIe switch分组统计吞吐,不能只读网卡计数器.

DE buffer容量还决定可并行等待的请求数. 若分给DE侧的平均KV为$\bar K$,预留内存$H_D$,并发上界约$H_D/\bar K$. 80GB在每请求1.31GB时只能容纳约61份,还未计碎片、元数据和新KV. 当prefill尾延迟上升,buffer驻留时间延长,Little定律给出占用$\lambda_D E[T_{prefill}]\bar K$;即使平均流量没变,长尾也会造成瞬时内存不足.

### 3.3. 稳定性来自服务率余量

把每个SNIC队列视为到达率$\lambda$、平均请求字节$E[K]$、服务率$\mu$的队列,负载率为$\rho=\lambda E[K]/\mu$. 当$\rho$接近1时,微小抖动便会让等待急剧增长. DualPath把总入口数扩大,主要价值是降低单队列$\rho$,并非只把峰值带宽乘常数.

若请求尺寸方差很大,M/G/1近似中的平均等待含$E[K^2]$:

$$
E[W_q]\approx\frac{\lambda E[S^2]}{2(1-\rho)},\qquad S=K/\mu.
$$

长上下文使二阶矩显著增大,所以平均上下文相同的两份trace可能有不同尾延迟. 图中的MaxLen分组仍不足以刻画分布,应报告KV字节的P50/P95/P99与二阶矩.

中心调度器使用上报状态,信息存在延迟$\delta$. 在$\delta$期间多个请求可能同时被送往当时最短的队列,形成“惊群”;下一轮又一起转向另一侧,产生振荡. 可给队列差设置滞回区间$h$:只有$Q_P-Q_D>h$才改走DE,反向亦然. 也可用指数平滑服务率替代瞬时值. 压测应周期性制造带宽下降,观察队列是否收敛以及恢复时间.

节点故障会留下三类状态:存储读取中的Full Block、DRAM中已完成但未转发的块、PE已计算但尚未回传的新KV. 因为持久存储保留命中前缀,前两类可以重读;新KV若未落盘则需重算. 幂等块标识必须包含轨迹、轮次、token区间、层号和模型版本,否则重试可能把旧KV拼进新请求. 论文聚焦性能,没有展开恢复协议,这不影响其吞吐结论,却影响生产系统能否安全复用路径.

**收益上限与三组手算**

第一组看入口. 2P4D每节点SNIC为50GB/s,Basic入口100GB/s,DualPath入口300GB/s. 每请求读1.31GB时,理想完成率分别约76与229请求/s. 若每请求还需0.061PFLOP,两块PE节点共16卡,按单卡有效0.3PFLOPS算计算上限约79请求/s.Basic几乎恰好被存储卡住,DualPath扩容后计算成为上限,端到端加速最多约$79/76=1.04$倍. 若有效算力升到0.6PFLOPS,计算上限157请求/s,加速上限约2.07倍. 这说明同一网络配置的收益强依赖kernel效率和batch.

第二组看命中率. 上下文32721、追加429时命中率98.7%,读取与计算比约21.6GB/PFLOP. 若追加增到4000而上下文不变,线性层计算约增9.3倍,读量不变,比值降到约2至3GB/PFLOP,与V3一类稠密计算负载接近. 此时PE更可能算力受限,空闲DE网卡不再是关键资源.

第三组看写回. 平均生成176 token相对读取32721 token仅0.54%;即便写回复制次数与读取相当,字节仍是小项. 若任务改成长篇生成,每轮生成8000 token,写读比升到24.4%,存储写带宽、落盘确认和DE侧CNIC都会进入约束. DualPath针对短生成Agent轨迹得出的忽略项,不能直接用于长文生成服务.

还可定义瓶颈判别数

$$
\Gamma=\frac{\text{每秒计算可消费的KV字节}}{PsB}.
$$

$\Gamma\le1$时Basic入口足够,增加路径难有收益;$1<\Gamma<(P+D)/P$时收益近似$\Gamma$;$\Gamma$更大时DualPath入口也会饱和. 这个分段模型比“网卡数量增加几倍”更能解释不同模型、上下文和batch下的曲线.

**消融应怎样拆开因果**

Basic到完整系统同时加入逐层prefill、双路径、QoS与调度,因此需要正交消融. 第一轴只改数据布局:保留单路径,开启逐层加载,测batch容量和计算利用率. 第二轴固定逐层加载,让DE侧SNIC参与,但用静态轮询选路,隔离新增入口的贡献. 第三轴加入队列感知调度,看负载偏斜下降多少. 第四轴开关VL隔离,测模型通信P99和KV吞吐. 这样才能把1.87倍分给各机制.

路径级实验应至少包含PE-only、DE-only、随机双路径、按字节队列双路径、按预计完成时间双路径. DE-only能够揭示DE侧CNIC和buffer的真实上限;随机策略给出纯入口扩容而无智能调度的基线;预计完成时间若没有优于字节队列,说明额外网络状态不值得维护.

结构级实验可扫描$P:D$、块大小、计算配额和VL权重. 每次只改变一轴,同时报告SNIC、CNIC、PCIe、DRAM、HBM与GPU利用率. 若某项加速出现,其对应资源利用率应发生方向一致的变化. 例如声称双路径解除存储瓶颈,就应看到PE SNIC下降、DE SNIC上升、总读带宽提高以及PE GPU空泡减少;只有JCT下降无法排除batch或调度变化.

工作负载级实验应分别扫命中率、追加长度、生成长度、上下文方差、到达突发度与工具等待. 命中率降低会减少读取却增加计算,生成变长会增加写回与DE占用,工具等待会扩大持久工作集但降低瞬时到达. 这些变量的方向不同,用一份生产trace无法得到普遍边界.

## 4. 失败边界

第一类失败是没有闲置入口. 若所有节点的SNIC已经被权重、checkpoint或其他租户占用,DE读路径只是在争同一存储集群. 客户端网卡数增加也不代表后端SSD能供给相应带宽. 应分别测客户端限速与3FS聚合吞吐.

第二类失败是计算网络没有空隙. 稠密MoE、高EP规模或跨机TP可能让CNIC持续繁忙,低优先级KV长期得不到服务. QoS能保护模型通信,却不能创造剩余带宽. 此时DE读出的KV堆在DRAM,路径反而增加驻留与尾延迟.

第三类失败是命中KV很小. 短上下文、低命中率或大追加使prefill由计算主导,读取可以被单路径隐藏. 路径管理、buffer和RDMA提交成为纯开销. 运行时应在$K_r$低于阈值时退回PE路径.

第四类失败是DE内存紧张. 长prefill与高并发使DRAM buffer堆积,而decode本身还需要主机侧元数据和可能的KV卸载. 一旦发生换页或NUMA跨插槽访问,理论带宽约束失效. 分配器应保留硬水位,超过后停止向DE派读任务.

第五类失败是请求存在强亲和性. 某些前缀已在特定节点DRAM或HBM中,从另一侧读SSD会丢掉局部命中. DualPath论文关闭3FS DRAM缓存并把节点DRAM当中转,弱化了这一问题;与HiCache结合时,路径选择必须把缓存位置纳入代价.

第六类失败是模型布局变化. V4一类更强KV压缩会降低每请求字节,同时Indexer扫描与计算占比上升,$\Gamma$可能跌回1以下. GQA模型KV更大,收益可能更高,但DE buffer更容易耗尽. 因此DualPath是负载与模型共同决定的系统选择,不能仅凭“Agent场景”三个字启用.

### 4.1. 一组可证伪实验

实验一固定PE算力与总请求字节,逐级限制DE SNIC为0、10、25、50GB/s. 若双路径收益来自新增入口,JCT应随总可用SNIC带宽近似单调下降,直到计算或CNIC饱和. 若很早形成平台,应由资源计数器指出新瓶颈.

实验二固定平均到达率,把泊松到达改成周期突发. 两者长期平均流量相同,若突发版本P99急剧恶化,说明稳态均值不足以描述容量. 再加入滞回和服务率预测,比较恢复时间与队列振荡幅度.

实验三保持KV总字节相同,构造许多小请求与少量巨型请求. 若调度只看字节队列且没有队头阻塞,两者吞吐应接近;若巨型请求明显更差,逐请求不可拆分或FIFO是原因. 开启块级分流后差距应缩小.

实验四保持SNIC流量不变,人为注入不同形状的EP突发. 记录VL2等待时间、TPOT P99和KV完成时间. 模型通信应基本不变,KV尾部随高优先级连续占用增长. 若TPOT仍恶化,说明PCIe或交换结构存在QoS覆盖不到的共享点.

实验五按层随机延迟KV块,观察GPU是否能用其他请求填洞. 完美流水应主要受最慢阶段均值限制;若单层抖动传播到整批请求,同步边界太强. 改变计算配额与batch组成可以定位传播来自DP attention还是EP屏障.

实验六在相同硬件上替换V3、V3.2与更小KV的模型,按实测$K_r/F_r$而非参数量排序. 若DualPath加速与cache-compute比单调相关,论文的机制解释成立;若参数规模更能预测收益,可能还有未计入的并行或kernel因素.

**从原理上如何理解 DualPath**

DualPath没有减少一字节必须保存的KV,也没有改变注意力结果. 它利用PD分离后天然出现的资源错配:PE承担读取与prefill,DE拥有闲置SNIC;计算网络虽承担模型通信,流量呈突发状,间隙可以承载低优先级KV. 因而核心条件可以浓缩成三条:存储入口是当前瓶颈,DE侧确有闲置入口,计算网络存在可安全利用的剩余服务率.

逐层prefill提供细粒度消费,Full Block与Layer Block解决存储对象和GPU计算粒度的矛盾,VL仲裁保护高优先级模型通信,三级调度把静态可行带宽转化成运行时吞吐. 任一环缺失都可能让新增入口无法落到GPU利用率上.

论文最有价值的观察是稀疏注意力改变了系统瓶颈. 模型减少长上下文计算后,KV读取不会同比减少,cache-compute比随长度上升. 算法上的稀疏化把成本从乘加转到索引与数据搬运,系统必须重新配置入口、缓存和调度. DualPath是这一变化在PD推理上的具体答案.

适用边界也同样清楚:大命中KV、短追加、短生成、高并发、PE侧SNIC饱和,同时DE侧SNIC和CNIC有余量. 离开这些条件,双路径可能只增加复制与状态. 部署前应测出$K_r$、计算时间、各链路剩余带宽和队列分布,代入流网络后再用小规模消融验证.

**从请求生命周期逐项计算**

一轮Agent请求包含前缀定位、KV读取、新token预填充、KV交接、解码与增量写回. 记前缀长度$c$,新增输入$q$,生成长度$o$,每token每层KV字节$v$,层数$L$,则命中读量约$K=cvL$,新KV量约$U=(q+o)vL$. 命中率$h=c/(c+q)$只描述token比例,系统真正关心的是$K$与各阶段时间.

PE路径的关键字节可按设备边界列出:SNIC把$K$写入PE DRAM;PE CNIC环回把$K$搬到HBM;计算后PE CNIC把$K+qvL$发给DE;DE CNIC写DRAM,再环回写HBM. DE路径则由DE SNIC把$K$写DRAM,DE CNIC发送$K$到PE HBM,PE只回传$qvL$,随后DE CNIC把完整KV写入HBM. 因此高命中率时DE路径省掉一遍大体积回传,低命中率时这个优势缩小.

令$h$连续变化,忽略生成时,PE到DE网络字节为$(c+q)vL$,DE路径双向网络字节为$cvL+qvL$,总量相同,差别在方向与端点复制. 真正节省的是DE buffer已有命中部分后,PE无需再次发送该部分;但DE到PE仍要发送一次供计算. 若网络全双工且两方向独立,方向变化的收益取决于原流量不对称. 单报“少走两趟”不足以推导跨节点网络减半,必须区分PCIe、DRAM与线缆.

解码结束后$o vL$写回存储,下一轮才能命中. 若写回异步,工具调用时间可以隐藏落盘;若下一轮立刻到达,必须等待一致性确认或暂存在节点缓存. 论文把工具耗时设为零,正好构成最苛刻的写后读间隔,但生成很短令写量仍小. 对真实工具调用,带宽压力降低,持久工作集却增大,两种效应方向相反.

### 4.2. 层流水的下界

设每层读取时间$r_i$,转运时间$n_i$,计算时间$a_i$,回传新KV时间$w_i$. 无重叠时单请求耗时为$\sum_i(r_i+n_i+a_i+w_i)$. 若读取下一层可与当前层计算重叠,稳态下界接近

$$
T\ge r_1+n_1+\sum_{i=1}^{L}\max(a_i+w_i,r_{i+1}+n_{i+1}),
$$

其中$r_{L+1}=n_{L+1}=0$. 当读取链比计算链慢,增加SNIC直接降低最大项;当计算更慢,读取已被隐藏,继续加带宽没有作用. 这给出了逐层时间线应验证的核心关系.

MoE层并不等长. 专家路由分布、跨节点all-to-all与不同token batch令$a_i$波动. 若预取距离固定为一层,一次慢读取就会让后续计算断粮;预取多层能吸收抖动,需要更多DRAM/HBM窗口. 设预取深度$d$,缓存占用约$dK/L$,可以扫描$d=1,2,4,8$测空泡与内存的Pareto曲线.

多请求批处理把每层块交错. 调度器可优先发送最早会被GPU消费的块,对应最早截止期策略;若只按请求FIFO搬完整层,一个大请求可能占满CNIC,让即将计算的小请求缺块. 块优先级应由预计消费时刻减去剩余传输时间决定. 这一策略能否优于简单FIFO,可在固定总字节下用长短请求混合检验.

**带宽隔离为何仍可能失效**

VL仲裁发生在InfiniBand端口,而共享路径还包括GPU PCIe、PCIe switch上行、CPU内存控制器、IOMMU与NIC内部DMA队列. VL2低优先级只能保护端口发送时序;若KV的环回DMA先耗尽PCIe读请求或内存带宽,高优先级模型通信仍会受影响.

可把端到端剩余容量写成各段最小值:

$$
B_{KV}=\min(B_{VL},B_{PCIe}/m_p,B_{DRAM}/m_m,B_{NICDMA}),
$$

$m_p,m_m$是每字节在对应资源上的经过次数. PE与DE路径的次数不同,因此同一VL配置下有效带宽也不同. 第3节不等式已经计算DRAM读写次数,但没有加入PCIe交换结构的聚合限制.

优先级还可能造成KV饥饿. 若高优先级流量长期超过链路的99%,VL2只拿到不足1%,读队列会持续增长. 保护模型通信与保证KV最低服务率之间需要权衡. 可以给低优先级设置最小份额$\epsilon$,容量条件变成到达率小于$\epsilon B$加空闲借用;$\epsilon$过大则直接抬高TPOT. 应画出TPOT P99与TTFT P99随$\epsilon$变化的曲线.

拥塞控制也会影响结果. 多个DE同时向少量PE发送大块,会形成incast;即使每个发送端限速合理,接收端端口和PCIe写入仍可能过载. ECN、信用流控与RDMA队列对不同优先级的配置必须一致,否则一个丢包或暂停事件会扩大为尾延迟. 单机对单机满带宽不能替代多对一测试.

**缓存一致性与前缀共享**

Agent轨迹按轮增长,第$t$轮前缀包含第$t-1$轮全部KV. 最自然的键是模型版本、token序列哈希和块边界. 模型权重、RoPE缩放、KV量化格式或并行布局变化都会使旧块失效;仅按token哈希命中会读到语义不兼容的数据.

trie让多条轨迹共享公共前缀. 设$n$条轨迹共享长度$c_0$,各自后缀$c_i$,不共享时存储量为$nvL(c_0)+vL\sum_i c_i$,共享后为$vLc_0+vL\sum_i c_i$,节省$(n-1)vLc_0$. 但读取带宽未必同比下降:不同请求仍需把同一前缀送入各自GPU. 节点DRAM缓存若保留热门公共前缀,才可能同时省SNIC流量.

共享也改变调度亲和性. 把同一前缀的请求分给同一节点有利于DRAM复用,却可能制造热点;按最短读队列分散则放弃局部性. 可将路径代价扩展为$\hat T_{r,a}-\zeta H_{r,a}$,$H$表示本地可复用字节,$\zeta$折算为时间. 随着缓存命中率变化,最优策略会在亲和与均衡之间切换.

增量写回需要原子发布. 一个Full Block包含多层数据,只有全部层写完并校验后才能加入trie;否则读取方可能拿到部分层. 临时对象写完后原子重命名或提交清单能保证可见性. 失败恢复时根据内容哈希去重,避免重试产生两份逻辑相同的块.

**调度预测误差如何传导**

中心调度使用$tok_e$近似计算负载,$read_q$近似I/O负载. 设真实完成时间$T=\hat T+\epsilon$,预测误差$\epsilon$若无偏且独立,大量请求下可相互抵消;长上下文请求的误差若系统性偏正,它们会持续被分给看似空闲的引擎,形成热点.

可按模型与长度桶维护在线校准:$\hat T'=a_b\hat T+c_b$,用最近窗口的实际时间更新$a_b,c_b$. 对重尾分布,均值回归不够,应预测高分位数. 路径选择用P90完成时间会保守一些,能减少长尾,代价是平均利用率略降.

状态上报间隔$\delta$决定陈旧度. 上报太频繁增加控制面负担,太慢则调度器重复使用旧状态. 若最大到达字节率为$A$,陈旧状态的队列误差上界约$A\delta$. 要让误差不超过阈值$h$,需$\delta\le h/A$. 在千卡规模下,可以由节点leader聚合,但leader自身故障和延迟也要计入.

DE的HBM准入目前假设无碎片. 实际PagedAttention按页分配,可用总量足够也可能缺少连续元数据或受不同页规格影响. 更可靠的判定是可分配页数减去安全余量,并按请求最大生成长度预留. 低估生成会在解码中途触发抢占,使已经读取的KV再次搬迁.

### 4.3. 长尾来自哪里

平均TTFT可拆成$T_{queue}+T_{read}+T_{prefill}+T_{handoff}$. P99通常不等于四项P99之和,因为它们可能相关:大请求既读得久,计算也久,更容易在内存不足时排队. 应保存逐请求分解,计算各项与总TTFT的条件相关性.

存储尾延迟可能来自SSD垃圾回收、3FS分片热点或元数据操作;网络尾延迟来自incast与高优先级突发;计算尾延迟来自MoE负载不均;调度尾延迟来自队头阻塞. 四类尾部需要不同手段,只增加SNIC无法解决后三类.

一个简单定位法是对每个请求计算关键路径. 若$T_{read}$与$T_{prefill}$大幅重叠,关键路径取两者最大值;把各资源忙碌区间投影到时间轴,找到造成最终完成时刻的依赖链. 资源利用率高不代表它在关键路径上,优化非关键流量不会降低TTFT.

尾部还会跨轮放大. 一条Agent轨迹第$t$轮延迟会推迟$t+1$轮到达,在离线JCT中累加;不同轨迹轮数差异又造成后期并发逐步下降. 因此JCT加速既包含单轮改善,也包含并发形状改变. 按轮次报告TTFT分布,才能判断收益集中在哪个阶段.

**成本模型与扩容选择**

面对存储瓶颈,可选方案包括增加PE节点、让DE参与读取、增加SNIC带宽、加DRAM缓存或压缩KV. 增加PE同时增加GPU算力和SNIC,若只缺I/O会浪费昂贵GPU;DualPath复用已有DE入口,边际硬件成本低,但消耗CNIC和DRAM.

设新增PE节点成本$C_P$,改造一个DE节点的软件与内存摊销$C_D$,获得的有效读带宽分别为$\Delta B_P,\Delta B_D$. 应比较$C/\Delta B$以及对TPOT的机会成本. 当DE CNIC原本接近饱和,$\Delta B_D$很小,增加PE或独立I/O节点可能更合算.

KV压缩把所有链路流量同时乘比例$r<1$,还降低存储容量;代价是模型改造、精度风险或解压计算. DualPath只扩入口,不减少后端总读量. 若3FS后端已满,压缩有效而双路径无效;若后端有余量、客户端SNIC满,双路径更直接. 两者叠加后,先由压缩降低$K$,再重新计算$\Gamma$,DualPath的边际收益可能随之下降.

DRAM缓存适合高复用热门前缀. 命中率$c_h$时,平均SNIC字节降为$(1-c_h)K$,但需要足够容量与一致性. Agent私有长轨迹复用发生在时间上而非跨用户,只要相邻轮间隔不长,本地缓存可能很有效;工具调用很久时,缓存容易被挤出. 应用重用距离分布决定容量,不能用单一总体命中率判断.

**对实验数字的再校验**

1,152卡实验中48P96D共144节点,入口峰值约7.2TB/s. 图15反推命中KV读取约2.4TB/s,只占三分之一. 此时继续增加路径不会提高吞吐,计算、调度或负载供给更可能限制系统. 大规模线性扩展证明系统没有明显集中瓶颈,没有证明SNIC始终满载.

在线容量从0.2到0.45 APS的2.25倍提升,低于2P4D入口数的3倍上限. 若Basic在0.2处正好饱和,入口扩容预测0.6 APS;差出的0.15 APS可由计算上限、队列不均和共享链路解释. 要分辨三者,需要在临界点报告各资源利用率.

离线2048 agent从约10100秒降到5450秒是1.85倍. 逐层prefill单独降到8750秒,因此以相同逐层基线衡量,双路径加调度是$8750/5450\approx1.61$倍. 对外使用1.87倍时应保留Basic定义,否则会把已有技术的收益归给读路径.

图8中等入口带宽配置性能相近,是论文最强的机制证据. 它通过改变P/D组合形成自然对照:计算资源不同而SNIC数量相同,JCT仍接近. 若进一步把后端限速设为相同总值,观察DualPath优势消失,因果链会更完整.

**结论检查表**

判断一个新负载是否适用DualPath,先测每轮命中KV字节、追加计算、生成写回和轮间隔,再测PE SNIC、DE SNIC、CNIC、PCIe与DRAM余量. PE SNIC持续接近满载且GPU等待数据,才说明入口是主因.

随后用单路径逐层prefill作为基线,避免把batch扩大收益算入双路径. 开启DE读取后观察总SNIC吞吐、GPU空泡与TPOT;三者应分别上升、下降、基本不变. 若只看到入口吞吐提高,端到端没有改善,瓶颈已经转移.

调度验收要覆盖均匀、重尾、突发和节点降速四种分布,同时报告平均与尾延迟. 隔离验收要注入最坏EP通信,确认TPOT目标仍满足,也确认KV没有长期饥饿. 故障验收则在读取、转运、计算、回传各阶段中断节点,检查重试是否得到同一KV.

DualPath最终提供的是一套资源重映射:把DE闲置的存储入口接入PE的数据需求,再用低优先级计算网络完成跨域搬运. 数学上是带多重容量约束的流分配,运行时是带陈旧信息和重尾任务的在线调度,硬件上则受SNIC、CNIC、PCIe与DRAM共同限制. 这些条件同时成立时,双路径能把被浪费的入口转化为有效吞吐;任一条件破裂,收益都会在对应资源的计数器上留下可验证的迹象.

## 5. 多租户与公平性

生产集群里不同租户的KV尺寸、SLO与优先级不同. 若调度器只追求总吞吐,大量短请求会持续绕过长请求;若严格FIFO,一个巨型前缀又会拖累全部租户. 可以给租户$u$设置权重$w_u$,用归一化服务量

$$
V_u(t)=\frac{\text{截至 }t\text{ 已读取的KV字节}}{w_u}
$$

选择$V_u$最小的队列,在长期提供加权公平. 请求内部再按截止期或剩余字节排序,兼顾租户公平与短任务延迟.

公平单位用请求数会偏向大KV,用字节又忽略计算成本. 更完整的资源向量包含SNIC字节、CNIC字节、DRAM驻留时间与GPU计算. Dominant Resource Fairness可按每个租户占比最大的资源排序,避免某类请求免费占用其他维度. 实现复杂度更高,至少应在评测中按租户报告资源占比与SLO违约率.

低优先级离线rollout与在线请求共存时,可以让离线流量填充在线空隙. 在线请求抵达后停止发起新的离线块,已在链路上的块无法瞬时撤回,抢占粒度等于块传输时间. 块越小,抢占响应越快;这又与提交开销形成权衡. 应用最坏块大小除以链路带宽估计抢占延迟上界.

恶意或异常租户可能反复请求巨大且无复用的前缀,占满SNIC和DE buffer. 准入控制需按租户限制在途字节与并发,并把未命中率纳入配额. 否则DualPath扩大入口后只会更快地把后端存储推到饱和.

### 5.1. 数据完整性与静默错误

KV cache不是可近似读取的普通缓存. 一个字节错误可能污染后续全部token,且模型输出未必立即显出异常. Full Block应带内容校验,传输完成后在DRAM或GPU侧验证;校验粒度过大延迟消费,粒度过小增加元数据. 与Layer Block对齐的分层校验允许某层就绪后立刻计算.

不同路径读取同一对象提供了抽样交叉验证机会. 可按低比例同时从PE与DE读取相同块,比较哈希与耗时,检测存储、RDMA或切片偏移问题. 双读只用于诊断,不进入常规吞吐. 一旦发现不一致,应隔离节点并从持久副本重读.

版本字段至少覆盖模型权重哈希、KV格式、层数、头维、量化scale布局和位置编码参数. V3.2与后续模型即使token相同,KV也不能互用. 滚动升级时新旧版本对象需要命名空间隔离,待旧请求排空后再回收.

逐层流式计算还要防止层错配. 若第$i$层块被写到$i+1$层地址,张量形状可能相同,运行时不会报错. 块头中的层号、token区间与目标地址映射应在提交前验证. 故障注入可以随机交换层块,确认校验能在进入注意力前拦截.

**从理论带宽到有效带宽**

400Gbps对应50GB/s线速,实际有效载荷要扣除链路编码、协议头、RDMA消息、PCIe事务与软件空隙. 设效率$\eta_s,\eta_n,\eta_p$,端到端有效带宽近似为

$$
B_{eff}=\min(50\eta_s,50\eta_n,B_{PCIe}\eta_p/m_p).
$$

直接把50GB/s代入容量规划会高估. 应用大块顺序读测SNIC上限,Layer Block混合读测真实负载,两者差值揭示对象与提交开销.

存储读取还受并发深度影响. 单请求串行读无法填满设备队列,并发过高又增加尾延迟. 令单次平均延迟$l$,块大小$z$,至少需要约$B_{eff}l/z$个在途请求才能覆盖往返延迟. 例如50GB/s、200微秒、2.5MB块只需约4个;块降到64KB则需约157个. 这说明块大小也决定存储队列深度.

NUMA位置会改变DRAM带宽. SNIC与CNIC若挂在不同CPU插槽,数据可能跨UPI搬运,有效带宽远低于双路内存峰值. buffer应分配在靠近数据消费者的NUMA节点,并分别测本地与跨插槽路径. 论文给出节点内存带宽500GB/s,没有展开拓扑,复现时需要补这一层.

测量工具自身也可能扰动. 对每个块记录详细时间戳会产生CPU与缓存压力,高频读取硬件计数器也有开销. 可抽样追踪少量请求,聚合计数器走低频通道,确保开关观测后的吞吐差异在噪声内.

**参数敏感性**

路径收益对$P/D$并非单调.P增加使Basic入口变多,双路径的相对增益下降;D增加提供更多闲置SNIC,也把PE计算结果分给更多解码资源. 当D过多时,DE侧利用率不足,硬件成本上升. 应在固定总节点$P+D$下扫描比例,而不是新增节点后比较.

SNIC/CNIC比例$s$决定可行区间. $s$越大,存储入口越强,转运对CNIC的压力也越大;当$s$接近$g/2$,PE路径的两次CNIC读取接近上限. 未来800Gbps SNIC若CNIC与PCIe不同比升级,双路径反而更容易受内部链路限制.

每节点GPU数$g$增大可把SNIC流量摊到更多CNIC,但共享PCIe与内存可能不随$g$线性增长. 公式中的$gB$只是网卡聚合峰值,节点根复杂度还需加入交换结构割带宽. 八卡节点结论不能直接外推到四卡或十六卡拓扑.

命中率$h$与上下文$c$应分开扫描. 相同$h$下,更大的$c,q$按比例放大读与算,固定提交成本占比下降;相同$c$下,$h$变化主要由$q$改变,会显著移动cache-compute比. 只报命中率会掩盖这两个自由度.

**复现实验的最小集合**

最小复现不必先搭千卡集群. 两个PE节点与两个DE节点即可验证路径、隔离和调度. 存储后端用限速器稳定在已知带宽,请求生成器分别提供固定尺寸、双峰尺寸与生产trace三类负载.

第一阶段验证字节守恒:每条路径统计SNIC、CNIC、DRAM与网络字节,与第18节公式逐项对齐. 误差应能由协议头、元数据与重试解释. 第二阶段验证容量:逐步提高到达率,观察哪个资源先到90%以上以及队列在哪里增长. 第三阶段验证隔离:注入EP通信,确认TPOT与VL权重关系.

性能报告至少包含吞吐、JCT、TTFT P50/P95/P99、TPOT P99、每资源有效带宽、GPU空泡、buffer峰值和丢弃/重试次数. 所有对比保持模型、batch上限、逐层prefill与缓存状态一致. 否则端到端加速无法归因.

消融结果应附置信区间. 存储与网络尾部波动明显,单次柱状图容易把几个百分点噪声读成收益. 每个配置多次运行,随机化执行顺序,同时记录后端负载. 论文中DualPath偶尔略快于Oracle的点已经提示测量存在波动.

末项测试使用故障与边界负载:限制3FS、压满CNIC、缩小DE DRAM、降低命中率、拉长生成、制造突发. 一个机制只有在预测的边界处按预测方式失效,其原理解释才足够可信.

### 5.2. 推导汇总

入口上限由$(P+D)sB$给出,相对Basic的理想倍率是$(P+D)/P$. 节点内部还受CNIC读写、DRAM和PCIe约束,端到端服务率取所有割面的最小值. 逐层流水能隐藏读取时,单层稳态耗时取读取链与计算链的最大值;启动、排空和抖动构成额外尾部.

调度的目标是让各入口预计完成时间接近,同时满足PE计算、DE HBM和高优先级通信的安全余量. 请求尺寸重尾使队列等待依赖二阶矩,状态陈旧会造成振荡,缓存亲和又与均衡冲突. 因而按待读token或字节排序只是可工作的近似,不构成普遍最优.

收益最强的区域由高$K/F$、PE入口饱和、DE入口空闲和CNIC存在间隙共同定义. KV压缩、追加增长或低命中率会降低$K/F$;长生成、网络繁忙与DE内存不足会增加新瓶颈. 每一条边界都能通过资源计数与受控实验验证.

从这个角度看,DualPath展示的重点在于把模型负载的变化翻译成流量方程,再把静态可行域落实为流水、隔离与在线调度. 这套分析方法也适用于后续模型:重新代入KV字节、稀疏注意力计算、并行通信和硬件拓扑,即可判断双路径是否仍有价值.

**稀疏注意力带来的二阶影响**

DSA减少主注意力读取的token数,却仍需为长前缀恢复持久化KV. 如果持久化对象同时包含Indexer键与主KV,读取字节由两部分组成:

$$
K=Lc(v_{main}+v_{idx}).
$$

主注意力只消费top-k主KV,Indexer却要扫描全部$c$个键. 若系统能分别存放两类数据,可先读较小的Indexer键,选出候选后再按需读取主KV;这会把顺序大读变成两阶段随机读,是否划算取决于$v_{idx}/v_{main}$、SSD随机读取和批量合并能力. DualPath论文按完整KV块读回,没有引入这层模型协同.

分离读取的理想字节约$Lc v_{idx}+Lk v_{main}$,相对完整读取的比例为

$$
r=\frac{cv_{idx}+kv_{main}}{c(v_{idx}+v_{main})}.
$$

当$c\gg k$且Indexer键很窄,$r$可能很小;但逐层Indexer通常需要当前query,无法在所有层计算前一次完成候选选择,会增加层间依赖与随机I/O. 这正是模型结构与存储布局需要共同评估的地方.

稀疏化还提高了GPU消费数据的速度. 相同峰值算力下,主注意力计算减少意味着prefill更快到达下一层,留给KV预取的窗口变短. 即使每请求KV字节不变,所需瞬时带宽也会上升. 因此cache-compute比同时刻画容量压力与预取期限,比单看KV大小更准确.

若后续模型把KV压到原来的八分之一,而计算只降到二分之一,$K/F$会降到原来的四分之一,DualPath收益区间明显收缩;若计算也同步降八倍,比值保持不变. 不能由“KV更小”单独判断系统瓶颈.

**调度约束的可行域**

对每个时间窗,路径变量$x_r$与PE、DE分配变量共同构成整数规划. 目标可以是最小化最大完成时间$T$,约束包括每个SNIC读字节、每个CNIC双向字节、DRAM驻留、PE计算量和DE HBM页数. 离线最优形式为

$$
\min T\quad\text{s.t.}\quad A\mathbf{x}\le \mathbf{b}T,
$$

$A$的每列是一个请求选择某条路径后对各资源的消耗,$\mathbf b$是资源速率. 在线算法无法预知后续请求,论文用队列阈值与贪心选择近似求解.

这个表示能解释为何单一队列最短不一定全局可行. DE侧SNIC最空时,对应DE可能没有HBM或CNIC余量;PE计算最空时,它所在节点的读队列可能很长. 每次决策应在可行资源交集中选择,任一硬约束触发便排除该端点.

松弛整数变量到$[0,1]$可得到块级分流下界. 逐请求策略与该下界的差距衡量“不拆请求”的代价. 当大量小请求存在时差距趋小;少数超大请求时差距扩大. 这比直接实现复杂分流更适合先判断潜在收益.

阈值$\alpha,\beta$对应给可行域留安全边界. 它们若按固定秒数换算token,默认服务率稳定. 在线根据近期带宽和kernel速度更新,可以在硬件降频、拥塞或模型切换时维持相同时间余量.

### 5.3. 读图时还需区分的量

吞吐可按agent、轮次、输入token、新算token或命中token统计. Prompt TPS若包含命中token,数值主要反映搬运;若只含新算token,才接近计算吞吐. 图表必须写明口径,否则同一系统能得到相差近两个数量级的TPS.

GPU利用率也有多种定义. 时间利用率表示kernel是否在运行,Tensor Core利用率表示算力强度,HBM利用率表示访存压力. KV等待期间三者都低;Indexer运行时GPU忙但Tensor Core未必高;MoE通信时kernel存在却可能等待网络. 图1的40%到80%是示意,不能替代这些分项计数.

网卡利用率应区分线速、有效载荷和方向. 环回RDMA在同一CNIC上同时产生读写,聚合百分比可能超过单向100%;跨节点转发又占线缆. 报告单个“CNIC利用率”前必须说明计数器口径.

Oracle跳过全部I/O与传输,它同时移除了真实系统无法消除的PD交接,因此是宽松上界. DualPath接近Oracle表明I/O大部分被扩容或隐藏,不代表其软件开销接近零. 更严格的上界应保留必要的单次KV交接,只令存储读取瞬时完成.

**一个完整的容量例子**

设集群采用2P4D,每节点8卡,SNIC与单块CNIC均为50GB/s. 某时窗内共有120个请求,平均命中KV 1.2GB,总读量144GB. 若希望2秒内完成读取,Basic两块PE SNIC恰好只能提供200GB容量,表面可行;考虑80%有效效率后只有160GB,安全余量仅16GB,任何尺寸波动都会排队. DualPath六块入口在同效率下提供480GB,读取不再是首要限制.

把120个请求均分到六个入口,每节点24GB,平均12GB/s. DE读路径还要把命中KV发往PE,四个DE合计96GB,两秒内平均网络流量48GB/s;摊到32块DE CNIC每块约1.5GB/s,远低于50GB/s. PE接收同样48GB/s,摊到16块CNIC每块3GB/s. 平均值很宽松,但某一PE若集中收到一半请求,其节点接收24GB/s,仍需与EP突发共享.

每请求追加429 token,按0.061PFLOP计算,120个请求共7.32PFLOP. 16块PE GPU若有效算力各0.3PFLOPS,两秒可提供9.6PFLOP,计算也可行. 若有效算力降到0.15PFLOPS,两秒只有4.8PFLOP,系统转为计算瓶颈,新增存储入口不会继续缩短时间.

再看DE buffer. 120份完整KV共144GB,均分四个DE节点为36GB,低于每节点80GB预算. 若请求尺寸P99为平均值三倍且碰巧集中,单节点可能越过水位. 调度器需要按字节和驻留时间分配,仅按请求数均衡无法保证内存安全.

这个例子展示了检查顺序:先把到达工作量换成各资源字节与FLOPs,再乘有效效率,随后检查平均分配与偏斜,末尾检查buffer驻留. 任一环达到上限,它就取代SNIC成为新的关键约束.

**最小监控面**

运行时至少需要六组信号:每个SNIC的读写有效字节与队列深度,每个CNIC按VL分开的字节与等待,PCIe上下行吞吐,NUMA内存带宽,PE的计算与通信时间,DE的HBM和DRAM占用. 这些信号要使用同一时间轴,才能看出读盘、转运和计算是否真正重叠.

每个请求保留少量阶段时间戳:入队、开始读、首块到达、末块到达、prefill开始与结束、KV交接完成、decode开始. 由此可直接计算排队、读取、流水空泡和交接成本. 全量逐块追踪开销较大,按请求采样即可;资源计数仍持续聚合.

告警不应只盯利用率. SNIC长期满载但队列稳定说明容量恰好匹配;利用率只有70%而队列持续增长,可能是短时突发、后端尾延迟或客户端并发不足. 更可靠的告警组合是队列斜率、完成带宽和P99阶段耗时.

路径策略也要留下决策原因:选择哪侧、两侧预计完成时间、被哪些硬约束排除. 当性能回退时,可以区分预测错误、状态陈旧和容量不足. 缺少这组信息,调度器像黑箱一样只输出最终路径,很难由端到端JCT反推原因.

模型或硬件升级后先重跑微基准,更新KV字节、计算拟合、有效带宽和安全水位. 这些量进入调度公式,旧参数可能让原本稳定的队列越过临界点. 监控面与容量模型保持同一套符号,才便于把线上异常还原到具体约束. 每次更新还应保存旧参数与同负载回放结果,防止调度改进被模型速度变化掩盖;若资源预测误差持续扩大,系统应退回静态均分,避免错误反馈继续放大队列偏斜.

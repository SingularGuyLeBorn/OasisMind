# 架构与算法

旗舰模型报告呈现的是一组已经协同工作的机制, 方法论文则把其中一个变量单独展开. DeepSeek 的算法研究集中在三个持续出现的约束: **模型容量扩大后怎样控制每个 token 的计算与状态, 强化学习怎样获得便宜而可靠的训练信号, 推理吞吐怎样在不改变输出分布的前提下提升.** 本章各篇论文围绕这些约束给出消融, 因而比版本报告更适合追踪设计选择的来由.

阅读方法论文时, 应先确认它替换了基线系统中的哪一部分. 路由算法改变 MoE 的专家分配, NSA 改变注意力读取上下文的方式, Engram 增加参数化主干之外的查找记忆, GRM 改变奖励生成, DSpark 改变解码执行而不改变目标模型. 作用位置不同, 指标与代价也不同, 不能只按最终准确率横向排序.

## 1. 条件计算的路由与专精

### 1.1. 无辅助损失的负载均衡

[Auxiliary-Loss-Free Load Balancing](./aux-loss-free/aux-loss-free-analysis.md) 处理 MoE 路由中的基本冲突. 传统做法加入辅助均衡损失, 让各专家接收相近数量的 token; 但辅助目标会与语言建模目标共同反向传播, 权重过大会损害模型能力, 过小又压不住路由偏斜. 论文改用随负载动态更新的专家偏置, 将均衡控制从主损失中分离.

**这项改动的关键是把「控制量」和「学习量」分开.** 路由分数仍从模型表示产生, 专家偏置根据近期负载调整, 主模型只优化语言目标. 代价是系统必须维护稳定的负载统计和偏置更新节奏. 它与 V3 报告及 DeepEP 的关系很直接: 算法减少专家拥塞, 通信库负责高效执行已经形成的 token 分配.

### 1.2. ESFT 利用已有专家结构

[ESFT](./esft/esft-analysis.md) 研究 MoE 模型的参数高效微调. 方法依据目标领域数据上的专家激活频率或路由亲和度, 选择部分专家更新, 其余参数保持冻结. 这样可以降低训练显存和通信开销, 也减少对无关专家的扰动.

专家选择并不等同于稳定的语义分区. 路由分布会随层, token 和数据集变化, 因而选择准则与覆盖比例是实验核心. 将 ESFT 与 DeepSeekMoE 合读, 可以区分预训练阶段的容量组织和下游阶段的参数更新: 前者形成条件计算结构, 后者利用结构缩小可训练集合.

## 2. 上下文读取从压缩走向稀疏

### 2.1. NSA 的分层选择

[Native Sparse Attention](./nsa/nsa-analysis.md) 面向长上下文训练和推理, 将注意力读取拆成压缩, 选择与局部窗口等路径. 压缩路径保留全局概况, 选择路径取回与当前查询更相关的块, 局部路径保证邻近 token 的细节. 这些路径共同限制实际参与注意力计算的键值数量.

NSA 的贡献不只在稀疏模式, 还包括面向训练的可实现性. 稀疏索引, 块大小和 kernel 布局必须配合, 否则理论计算量下降未必转化为墙钟时间改善. 阅读实验时应同时看长上下文质量, 训练吞吐和解码阶段开销. V3.2 中的稀疏注意力可作为模型级应用对照.

### 2.2. Engram 增加条件记忆

[Engram](./engram/engram-analysis.md) 将部分常见局部模式交给确定性 N-gram 寻址表. 输入片段经过哈希定位记忆项, 查得的向量再并入网络表示. 这种设计把一部分知识容量从每 token 都参与计算的参数中移到条件读取的存储中, 形成计算与容量的新分配方式.

查表记忆的收益依赖命中分布, 哈希冲突, 内存层级和数据覆盖. 高频短语容易受益, 需要组合推理的新模式仍要依靠主干网络. Engram 与 MoE 都属于条件激活, 但选择对象不同: MoE 路由到可计算的参数子网, Engram 寻址到已存储的向量条目. 合读两者有助于理解“稀疏容量”并非单一架构.

### 2.3. mHC 控制跨层混合

[mHC](./mhc/mhc-analysis.md) 研究超连接带来的表示混合与训练稳定性. 多条残差流可以提高网络的信息交换能力, 但无约束的混合矩阵会改变信号尺度, 使深层训练更难控制. mHC 将混合映射约束在具有稳定性质的矩阵集合上, 在增加连接自由度的同时限制数值漂移.

这篇论文适合与归一化和残差结构一起读, 关注层与层之间怎样传递和组合状态. 评估时除了最终损失与任务成绩, 还要看深度扩大后的稳定性、额外状态带来的显存开销, 以及混合计算能否被高效实现.

## 3. 奖励与可验证训练信号

### 3.1. CodeI/O 从执行关系构造数据

[CodeI/O](./codeio/codeio-analysis.md) 使用代码的输入输出关系作为训练信号. 可执行程序能够生成大量输入与对应输出, 模型既可以从程序预测结果, 也可以从示例关系推断程序行为. 这种数据把自然语言描述之外的执行语义带入训练, 并借助运行结果进行自动检查.

自动执行降低了标注成本, 也引入运行环境, 测试覆盖和程序质量约束. 一个程序通过有限样例, 不代表模型学到了完整语义; 随机输入的分布也会改变任务难度. 因此 CodeI/O 应与代码沙箱和 Coder 系列合读: 数据方法决定生成什么训练对, 基础设施决定能否安全而大规模地执行验证.

### 3.2. GRM 让奖励模型进行生成式评审

[DeepSeek-GRM](./deepseek-grm/deepseek-grm-analysis.md) 将奖励判断改写为生成过程. 模型先生成评价原则或批判内容, 再依据这些内容给出判断; 多次采样还可以在 TestingTime 汇总, 用额外计算提高奖励可靠性. 相比直接输出一个标量, 生成轨迹提供了更丰富的条件信息.

**生成式奖励扩大了任务覆盖面, 也把奖励判断变成一项新的推理负载.** 每个候选回答需要额外 token, 多采样会继续放大推理开销, 评价原则本身还可能出现偏差或相互冲突. 这项方法适合与 R1 的规则奖励对照: 规则奖励便宜且精确, 但覆盖面有限; 学习式生成奖励能够处理开放问题, 同时需要校准与鲁棒性检验.

## 4. 解码阶段的计算重排

### 4.1. DSpark 的投机解码框架

[DSpark](./dspark/dspark-analysis.md) 面向投机解码的研究和部署. 投机解码让较便宜的草稿过程先提出若干 token, 再由目标模型并行验证; 被接受的 token 减少了目标模型逐步解码次数. 最终分布保持目标模型定义, 加速取决于草稿成本, 接受率和验证批次之间的平衡.

框架价值在于统一不同草稿策略, 缓存管理与验证流程. 单看接受率不足以判断端到端收益, 因为较复杂的草稿模型可能用更多时间换来更高接受率. 评估需要同时报告延迟, 吞吐, batch 条件, 上下文长度和硬件. DSpark 与 FlashMLA 等 kernel 优化作用在不同层次: 前者减少串行解码步数, 后者降低每一步注意力执行成本.

### 4.2. 从机制论文回到模型和系统

本章的方法可按模型生命周期定位. mHC, NSA, Engram 和负载均衡进入架构与预训练阶段; ESFT 处理下游微调; CodeI/O 和 GRM改变训练数据或奖励; DSpark 作用于部署解码. 确认位置以后, 才能选择正确的上下游材料与评测指标.

一条紧凑的阅读路线是先读 DeepSeekMoE 与 V3, 再看负载均衡和 ESFT; 接着从 V2 的 MLA 进入 NSA 与 Engram; 然后从 DeepSeekMath, R1 进入 CodeI/O 与 GRM; 最后把 DSpark 同第四章的推理 kernel 对照. 这种顺序把机制的原始实验, 旗舰模型中的组合效果与工程实现连接起来, 同时保留各论文的适用边界.

DSpark 来自 DeepSeek-AI 与北京大学 2026 年 7 月发布的论文 *DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation* ([arXiv 2607.05147](https://arxiv.org/abs/2607.05147)), 训练与离线评测代码开源在 [deepseek-ai/DeepSpec](https://github.com/deepseek-ai/DeepSpec), V4-Flash 与 V4-Pro 的草稿权重随 DeepSeek-V4 一起发布在 Hugging Face. 它做了两件事: 在并行草稿主干上接一个低秩的顺序头, 让块内后面的 token 能看到前面实际采样出的 token; 再给每个草稿位置配一个置信度, 由调度器结合当前 batch 负载决定每个请求送多少个 token 去验证. 中英对照全文见 [DSpark 对照译稿](dspark-bi.md). 拒绝采样的无损性, DFlash 的 KV 注入与 Markov head 的公式推导, 在 [DSpark 原理解析](../../../llm-guide/6-训练与推理优化/6.6-推理框架与高级优化/6.6.2-投机解码/06-DSpark原理解析/06-DSpark原理解析.md) 和 [DSpark 原理推导](../../../llm-guide/6-训练与推理优化/6.6-推理框架与高级优化/6.6.2-投机解码/08-DSpark原理推导-置信度调度的半自回归投机解码/08-DSpark原理推导-置信度调度的半自回归投机解码.md) 里已经写过, 这里直接引用结论, 把篇幅放在数字核对, 口径辨析和论文与代码的出入上.

## 1. 并行 drafter 的接受率为什么会衰减

### 1.1. 接受长度是一个前缀存活过程

投机解码每轮的收益由式 (1) 决定: 每 token 延迟 $L=(T_{draft}+T_{verify})/\tau$, $\tau$ 是一轮里被接受的 token 数加上目标模型额外给出的 bonus token. 验证按前缀进行, 第 $k$ 个草稿 token 被接受的前提是前 $k-1$ 个都已被接受, 所以期望接受长度可以写成存活概率之和: $\mathbb{E}[\tau]=1+\sum_{k=1}^{\gamma}\prod_{j\le k}c_j$, 其中 $c_j$ 是在前缀全部通过的条件下位置 $j$ 的接受概率. 单步最优接受概率由式 (8) 给出, $c^*=1-\frac12\|p^d-p^t\|_1$, 也就是草稿分布与目标分布全变差距离的补数.

这个乘积结构决定了各位置的权重不对称. 位置 1 的 $c_1$ 乘进后面每一项, 它下降 0.05, 后面所有存活项都按同一比例缩小; 位置 7 的 $c_7$ 只影响最后一项. 因此论文在 4.3.1 节特意引入「逐位置条件接受率」: 分母只计前缀已全部通过的样本, 这样每个位置的数字不受更早错误的拖累, 可以直接代入上面的乘积. 想比较两个 drafter 的整体表现, 看接受长度; 想知道差距出在哪一段, 看条件接受率曲线.

两种曲线对应两种失效. Eagle3 每个位置跑一次草稿前向, 草稿成本是 $O(\gamma)$, 只能用 1 层, 位置 1 的预测能力受限; 但它每一步都以真实采样出的上一个 token 为条件, 前缀一旦确定, 后续更好猜, 条件接受率上升. DFlash 一次前向给出整块, 能用 5 层, 位置 1 强; 可块内各位置互相看不到对方的采样结果, 位置 $k$ 的分布是对前 $k-1$ 个 token 所有可能取值的边缘化. 前缀越长, 可能的前缀越多, 边缘分布越平, 和目标模型以真实前缀为条件的分布差得越远. 论文沿用非自回归翻译文献的说法, 把这称为多模态碰撞: 位置 3 押注了路径甲的词, 位置 4 押注了路径乙的词, 拼起来的后缀哪条路径都对不上.

### 1.3. 容量解释的边界

论文用「位置 1 的容量差」解释为什么并行 drafter 整体胜过自回归 drafter. 这个解释在 Qwen3 三个规模上成立: 表 1 的 9 个基准平均接受长度, Qwen3-4B 上 Eagle3, DFlash, DSpark 分别是 3.611, 4.064, 4.727, DSpark 相对两者的提升 30.9% 与 16.3% 正是这三个均值之比. 8B 上是 3.798, 4.067, 4.813, 14B 上是 3.676, 4.039, 4.779, 与正文的 26.7%/18.4% 和 30.0%/18.3% 一致.

Gemma4-12B 一行给出了反例. 这一行 Eagle3 均值 4.376, 高于 DFlash 的 4.018, DSpark 为 4.663, 相对 Eagle3 只高 6.6%, 相对 DFlash 高 16.1%. 正文只说增益「跨模型家族成立」, 没有给出 Gemma 的百分比, 也没有讨论为什么在这个目标模型上 1 层的 Eagle3 能胜过 5 层的 DFlash. 如果位置 1 的容量差是主因, 这一行应当和 Qwen3 同向. 一个可能的解释是 Gemma 的输出分布更集中, 后缀衰减对 DFlash 的伤害更大, 但文中没有给出 Gemma 的逐位置曲线, 这个解释无法从论文数据验证.

## 2. 半自回归怎样补回 token 间的依赖

### 2.1. 一次重前向加一个低秩顺序头

DSpark 保留 DFlash 的并行主干: 目标模型若干层的隐状态经 KV 注入送进草稿模型 (式 2 与式 3), 块内双向注意力, 一次前向得到每个位置的隐状态 $h_k$. 它改的是输出端. 式 (4) 把块内联合分布拆成 $\prod_k p(x_k\mid h_k,x_{<k})$, 其中 $h_k$ 并行算出, 对 $x_{<k}$ 的依赖交给一个轻量顺序头. 默认的 Markov head 只看上一个 token: logits 为 $W_{lm}h_k+B(x_{k-1},\cdot)$, 偏置 $B(x_{k-1},\cdot)=W_1[x_{k-1}]W_2$, $W_1$ 是 $V\times r$ 的嵌入表, $W_2$ 是 $r\times V$ 的投影, 秩 $r=256$ (式 5). 采样时每一步做一次查表和一次 $r\times V$ 的矩阵乘, 再从修正后的分布采样, 采样结果作为下一步的 $x_{k-1}$.

这个设计有两个工程上的好处. 逐 token 概率仍是一个精确的 softmax, 拒绝采样需要的 $p^d(x_k)$ 可以直接读出; 相关工作一节举的 CRF-NAT 和 CTC-drafter 都因为全局归一化或对齐路径边缘化拿不到这个值. 顺序部分的计算量与草稿主干深度无关, 主干可以继续加层而串行成本不变. RNN head (式 6) 用一个 GRU 式的状态累积全部前缀, 表达力更强, 但图 4 里它相对 Markov head 只在长提议长度上有边际增益, 部署时默认 Markov head.

从 DeepSpec 的 `markov_head.py` 能看到两处论文没有写明的细节. 一是 `sample_block_tokens` 从 anchor 起步, 位置 1 也加了 $B(x_0,\cdot)$, 顺序头并不只作用于位置 2 以后. 二是仓库里还有一个 `GatedMarkovHead`, 用 $\sigma(W_g[h_k;W_1[x_{k-1}]])$ 对低秩嵌入逐维加门控后再投影到词表, 论文正文与附录都没有提到它. 仓库里 Qwen3 三个规模和 Gemma4-12B 的发布配置都写的是 `markov_head_type="vanilla"`, 即式 (5) 的无门控版本.

### 2.2. 接口改动: anchor 当第一个预测槽

DFlash 的输入块是 anchor 加 $\gamma$ 个 mask, anchor 所在槽不出预测. DSpark 在 3.1 节把 anchor 本身当成第一个预测槽, $\gamma$ 个输入 (anchor 加 $\gamma-1$ 个 mask) 产出 $\gamma$ 个 logits. DeepSpec 里的对应写法是 `label_offsets = arange(1, block_size+1)`: 槽 $i$ 预测 anchor 之后第 $i$ 个 token. Qwen3 配置的 `block_size=7`, 一次前向得到 7 个草稿 token, 加上 anchor 送去验证的是 8 个 token.

这个约定决定了怎么读 4.3.2 节. 那里的「草稿长度 ($\gamma$ 加一个 anchor) 取 {4, 8, 12, 16}」数的是验证宽度, 对应 $\gamma\in\{3,7,11,15\}$; 正文举的 $\gamma=7$ 与 $\gamma=15$ 正是第二档和第四档. 接受长度含 bonus token, 上限是 $\gamma+1$. 这个约定在社区实现里造成过实际问题. vLLM speculators 项目训练的 DSpark 检查点沿用 DFlash 的槽位约定, 槽 $j$ 预测 anchor 之后第 $j$ 个 token, 槽 0 不监督; 按 DeepSpec 约定去服务, 每个槽位都读早一位, 接受长度掉到 1.1 左右, 平移一位后回到 4.05 (speculators issue #753). 同一个「block size」在两种约定下分别对应 $\gamma$ 与 $\gamma-1$ 个草稿, 读接受长度数字之前要先确认是哪一种.

### 2.4. 训练目标与代码出入

训练损失由三项组成: 交叉熵 $\mathcal{L}_{\mathrm{ce}}$, 全变差 $\mathcal{L}_{\mathrm{tv}}$ 和置信度头的二元交叉熵 $\mathcal{L}_{\mathrm{conf}}$, DeepSpec 配置里的权重是 0.1, 0.9, 1.0. 全变差项直接优化式 (8) 的 $c^*$, 也就是逐位置接受概率, 交叉熵只占很小权重. 顺序头训练时用 teacher forcing: 前驱 token 取 anchor 加真实目标序列错一位, 与推理时用草稿自己采样的前缀不同. 推理时只有前缀全部被接受的样本才会走到位置 $k$, 这些前缀与目标模型的输出高度重合, 训练与推理的条件差距因此被收窄, 但文中没有给出这部分差距的度量.

位置权重是论文与代码对不上的地方. 3.3 节写 $w_k=\exp(-(k-1)/\gamma)$, 衰减常数取块长; DeepSpec 的 Qwen3-4B 配置 `block_size=7`, 但 `loss_decay_gamma=4.0`, `loss.py` 按 $\exp(-pos/4)$ 加权. 位置 7 的权重因此是 $e^{-1.5}\approx 0.22$, 按正文写法应为 $e^{-6/7}\approx 0.42$, 相差近一倍. 发布配置更重视靠前位置, 这与 1.1 节的乘积结构一致, 但论文报告的数字到底用哪个衰减常数训练, 文中没有说明. 其余训练超参与配置文件一致: 每条序列采 512 个 anchor, 5 层草稿, 从目标模型第 1, 9, 17, 25, 33 层取隐状态, 学习率 $6\times10^{-4}$, 全局 batch 512, 10 个 epoch, 最大长度 4096.

## 3. 置信度调度怎样给每个请求定验证长度

### 3.1. pre-token 置信度与 STS 校准

置信度头的公式是 $c_k=\sigma(w^\top[h_k;W_1[x_{k-1}]])$ (式 7). 它的输入是位置 $k$ 的主干隐状态和上一个 token 的低秩嵌入, 不含 $x_k$ 本身, 所以 $c_k$ 估计的是「在已知前缀下, 位置 $k$ 将要采样出的 token 被接受的概率」, 论文称为 pre-token 置信度. 训练标签取式 (8) 的 $c^*$, 也就是用目标分布与草稿分布的全变差算出的解析接受概率, 不用一次采样的 0/1 结果, 方差更低. 存活概率 $a_{r,k}=\prod_{j\le k}c_{r,j}$ 是调度器真正用到的量.

只看排序时, 置信度头的区分能力够用: 图 6 里 ROC-AUC 在 0.81 到 0.90. 调度器要的是乘积 $a_{r,k}$ 的绝对值, 原始输出过度自信, ECE 在 3% 到 8%, 连乘 6 次以后误差会累积. 论文的 STS (顺序温度缩放) 从位置 1 开始逐位置做一维网格搜索, 为每个位置选一个温度, 使累积乘积的 ECE 最小, 位置 $k$ 的温度在前 $k-1$ 个固定后再定. 温度缩放是单调变换, 不改变同一位置上的排序. 校准后平均 ECE 降到约 1%.

这张图验证了置信度头能挑出低价值后缀, 但它也显示静态阈值的问题. 同一个阈值在对话上剪掉大半草稿, 在数学上只剪一小部分; 而该不该剪, 还取决于此刻 GPU 有没有余量. 低并发时多验证几个低置信度 token 几乎不花钱, 剪掉反而损失接受长度; 高并发时同样的 token 会挤占其他请求的 batch 位置. 一个固定阈值无法同时适应这两个区间, 这是 Algorithm 1 引入负载项的原因.

### 3.3. Algorithm 1 的准入门槛

Algorithm 1 把所有请求的候选 $(r,j)$ 按 $a_{r,j}$ 全局降序排好, 依次尝试接纳. 当前 batch 的验证 token 总数 $B=\sum_r(1+\ell_r)$, 期望接受数 $\tau=\sum_r(1+\sum_{j\le\ell_r}a_{r,j})$, 系统吞吐 $\Theta=\tau\cdot\mathrm{SPS}(B)$, 其中 $\mathrm{SPS}(B)$ 是离线测得的「batch 为 $B$ 时每秒能跑几步」. 接纳一个候选后若 $\Theta$ 不再上升, 立即 break. 同一请求内 $a_{r,j}$ 随 $j$ 单调不增, 全局排序自动保证每个请求接纳的是一个前缀.

把 break 条件展开, 就得到每个 token 的准入门槛. 接纳前为 $(B,\tau)$, 接纳后为 $(B+1,\tau+a)$, 继续的条件 $(\tau+a)\,\mathrm{SPS}(B+1)>\tau\,\mathrm{SPS}(B)$ 等价于

$$
a>\tau\left(\frac{\mathrm{SPS}(B)}{\mathrm{SPS}(B+1)}-1\right).
$$

轻负载时 $\mathrm{SPS}$ 在 $B$ 附近几乎是平的, 右边接近 0, 几乎所有草稿都进; 进入计算受限区后若 $\mathrm{SPS}\propto1/B$, 右边变成 $\tau/B$, 即当前 batch 里平均每个验证 token 换来的期望接受数. 这条式子是论文里没有写出的推导, 只用到 Algorithm 1 的两行更新式, 它把「负载越高, 门槛越高」写成了显式关系: 一个草稿 token 被送去验证, 当且仅当它的存活概率高于 batch 当前的平均产出率. 每个请求的验证长度 $\ell_r$ 因此由全局决定, 它取决于其他请求的置信度和 batch 总大小.

### 3.4. 早停, 无损性与生产版改造

break 不只是省计算. 附录 A 的反例说明, 去掉 break 做全局搜索会破坏无损性: $\Theta_2$ 依赖 $c_2$, $c_2$ 依赖 $x_1$, 于是 $x_1$ 是否被接纳取决于 $x_1$ 自己的取值. 在两词表的例子里, 目标分布 (0.7, 0.3), 草稿分布 (0.5, 0.5), 调度器只在 $x_1=A$ 时接纳, 输出分布变成 (0.85, 0.15). 早停版本在 $\Theta_1=0.9<\Theta_0=1.0$ 时就停下, 不会看到 $c_2$.

同一个反例也显示了 break 的代价. 序列 $\Theta_0,\Theta_1,\Theta_2$ 为 1.0, 0.9, 1.134, 先降后升, 早停拿不到情形 1 下 1.134 的解, 吞吐差约 12%. 真实 GPU 的 $\mathrm{SPS}(B)$ 在 kernel tile 边界处阶梯式下降, 这种先降后升的情况很常见. 5.2 节的生产版做了两处改造: 调度器异步运行, 用两步之前的置信度算出容量上限 $K$, 当前步按最新的 $a_{r,j}$ 取 top-$K$; 容量搜索去掉 break, 做全局搜索. 因为 $K$ 只依赖两步之前的信息, 与当前块的 token 无关, 而同一请求里依赖 $x_{r,k}$ 的后续候选满足 $a_{r,k+1}\le a_{r,k}$, 排不到 $(r,k)$ 前面, $x_{r,k}$ 无法影响自己是否入选. 唯一的缝隙是并列值: $c=1$ 时 $a_{r,k+1}=a_{r,k}$, 需要约定位置靠前者优先, 文中没有写明并列的处理.

5.2 节还有一处措辞与内容不符. 原文说去掉 break 是为了防止调度器被锯齿状 SPS 困在「local minima」, 而调度器在最大化 $\Theta$, 被困住的是局部最大值. 另外, 两步延迟让 $K$ 与当前真实最优容量之间存在偏差, 论文称之为「轻微的时间偏移」, 没有给出这部分偏差造成的吞吐损失.

## 4. 与 batch 容量, 吞吐的关系

### 4.1. 为什么线上吞吐与单用户速度同向

投机解码通常被看作用算力换延迟: 每次验证 $\ell+1$ 个 token, 被拒的那部分算力白花, 换来单请求更快. 这个取舍在 batch 打满 GPU 算力时成立. 5.3 节给出的部署前提是, 每个请求的 KV cache 容量固定, 可用流量池有限 (RL 长尾负载是一个来源), 有效 batch 持续低于算力饱和点. 在这个区间里, 多验证几个 token 主要消耗本来闲置的算力, 每 GPU 总吞吐与单用户 tok/s 同时上升.

这也解释了 DeepSeek 为什么此前停在 MTP-1. 第 5.4 节说静态的 MTP-3/5 在高并发下会因验证开销严格降低总吞吐: 静态方案在轻负载时浪费不大, 在重负载时每个请求都固定多占 3 到 5 个位置, batch 越大越吃亏. DSpark 的调度器让验证长度随负载变化, 轻负载时用满余量, 重负载时退回到接近 MTP-1 的长度, 两端都不比 MTP-1 差. V4 的 MTP 结构可参考 [DeepSeek-V4 技术解析](../../01-模型技术报告/deepseek-v4/deepseek-v4-analysis.md) 和 [DeepSeek-V4.1-Flash 技术解析](../../01-模型技术报告/deepseek-v4-1-flash/deepseek-v4-1-flash-analysis.md).

### 4.2. 生产草稿模型与变长验证

生产版草稿模型由 3 个 MoE 层组成, 带 mHC 和窗口 128 的滑动窗口注意力, $\gamma=5$, Markov head. NVIDIA 在 Hugging Face 发布的 V4-Flash DSpark 量化卡片给出了更多细节: 草稿模块总参数约 21B, 激活约 1B, 权重沿用 `mtp.0/1/2` 的命名, 注意力为 MLA, MoE 为 256 个专家激活 6 个, 输入取自目标模型第 40, 41, 42 层. 论文正文只写了层数与注意力窗口, 没有给出这些参数.

训练侧有两项系统优化: 只在 worker 间传输 LM 头之前的隐状态, 在草稿 worker 上本地做 LM 头投影, 每 token 通信量从 $O(V)$ 降到 $O(d)$; 每条序列只采固定数量的 anchor 打包训练, 草稿侧计算量与目标上下文长度脱钩. 推理侧, 每个请求的验证长度不同, batch 里的 query 长度参差不齐. 论文把所有请求的 token 展平当成独立元素处理, 序列归属由一个标记张量写进稀疏注意力; 在 V4 上只需要改 index-attention 与 compress 两个 kernel. 这部分实现未开源, 文中也没有给出变长 kernel 相对定长 kernel 的开销数字.

## 5. 线上数字的口径与对比基准

### 5.1. 图 7 上的三种比较

图注: 横轴是单用户生成速度 (tok/s/user), 纵轴是总输出吞吐, 散点是线上遥测, 实线是拟合的前沿. V4-Flash 在 80 tok/s/user 的 SLA 下 DSpark 吞吐高 51%, 在 120 下名义上高 661%; V4-Pro 在 35 下高 52%, 在 50 下名义上高 406%.

### 5.2. 比较对象与可分离性

线上对比只有 MTP-1 一个基线. 这组对比同时换了两样东西: 草稿模型从单层 MTP 变成 3 层 MoE 的半自回归 drafter, 验证长度从固定 1 变成调度器动态决定. 论文没有给出「DSpark 草稿加固定长度」或「MTP 加调度器」的线上点, 51% 里有多少来自草稿质量, 有多少来自调度, 无法从图 7 拆开. 散点来自真实流量, 不同时间段的请求分布不同, 拟合前沿也并非同流量的 A/B 测试, 文中没有给出拟合方法和误差带.

社区的数字可以部分补上草稿质量这一项. vLLM PR #46995 在 V4-Pro 上 (thinking 开, temperature 1) 按草稿长度对比 DSpark 与 MTP 的平均接受长度: 草稿长度 1 时 1.82 对 1.86, MTP 略好; 长度 3 时 2.86 对 2.55; 长度 6 时 3.42 对 2.60. 同一 PR 里有人在 2 张 H100 上跑 V4-Flash-DSpark ($\gamma=5$) 的真实流量, 平均接受长度 3.86, 各位置无条件接受率 82%, 67%, 55%, 45%, 37%. 由此算出的条件接受率依次约为 0.82, 0.82, 0.82, 0.82, 0.82, 块内基本持平, 与图 2 中 DSpark 曲线的形状一致; $1+0.82+0.67+0.55+0.45+0.37=3.86$, 与报告的接受长度对得上. 这说明在长度 1 时 DSpark 草稿并不比 MTP 强, 收益来自长块上不衰减, 而长块能否用上, 又取决于调度器.

### 5.3. 和 MTP, EAGLE, Medusa 比较的依据

离线对比的基准是 Eagle3 与 DFlash, 依据是表 1 的接受长度. 这里的 Eagle3 只有 1 层, DFlash 与 DSpark 都是 5 层, 比较的是「各自的典型配置」, 不是等参数或等草稿 FLOPs. 论文的论点本来就是自回归 drafter 受 $O(\gamma)$ 串行成本所限用不了深网络, 所以这个设置符合它要论证的东西, 但读者不能把 30% 的差距理解成同等算力下的架构差. EAGLE 系列与 DFlash 的机制见 [EAGLE 系列深度解析](../../../llm-guide/6-训练与推理优化/6.6-推理框架与高级优化/6.6.2-投机解码/02-EAGLE系列深度解析/02-EAGLE系列深度解析.md) 与 [DFlash 原理解析](../../../llm-guide/6-训练与推理优化/6.6-推理框架与高级优化/6.6.2-投机解码/04-DFlash原理解析/04-DFlash原理解析.md).

Medusa 只出现在相关工作里, 没有实验对比. 按结构看, Medusa 的多个头各自独立预测, 属于 DFlash 一侧的纯并行方案, 而且没有 KV 注入的深主干, 按 1.2 节的分析, 它同时面对位置 1 容量不足和后缀衰减两个问题, 但文中没有给出数字. MTP 的对比只在线上做, 且只对 MTP-1; MTP-3/5 被排除的理由是高并发下吞吐下降, 论文没有给出 MTP-3/5 配合同一调度器的结果. 离线评测全部关闭调度器, 用固定长度块, 结论只针对草稿质量; 调度器的收益只有线上数据支撑.

### 5.4. 存疑之处汇总

按论文章节整理, 以下几处结论的证据不足或与代码不一致.

- 3.3 节: 位置权重写作 $\exp(-(k-1)/\gamma)$, DeepSpec 发布配置用 $\exp(-pos/4)$, 块长为 7, 文中没有说明报告数字用的是哪个.
- 4.3.1 节: 「位置 1 容量差」的解释在 Gemma4-12B 上不成立 (Eagle3 4.376 高于 DFlash 4.018), DSpark 与 DFlash 同为 5 层而位置 1 差 0.05, 来源没有消融.
- 4.3.2 节: 延迟开销只在 batch 128 下测量并对四个上下文长度取平均, 小 batch 区间没有数字; Eagle3 1 层对 5 层, 不是等算力比较.
- 5.2 节: 「local minima」应为局部最大; 两步延迟带来的容量偏差没有量化; top-$K$ 因果性论证没有处理并列值.
- 5.4 节: 线上只对比 MTP-1, 草稿与调度的贡献无法分离; 661%/406% 是前沿贴近横轴时的名义比值; 前沿为拟合曲线, 没有方差或置信区间.

这些问题不影响论文的主线结论: 半自回归顺序头以很小的串行成本缓解了并行草稿的后缀衰减, 负载感知的验证长度让长草稿块在高并发服务里变得可用. 它们影响的是数字的可迁移性, 在别的目标模型, 别的并发区间, 别的基线下复现时, 上面几项都要单独测.

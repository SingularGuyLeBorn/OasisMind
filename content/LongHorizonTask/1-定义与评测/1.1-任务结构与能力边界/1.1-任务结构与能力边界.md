# 任务结构与能力边界

「长」这个字很容易把几个问题揉在一起. 模型可以一次输出很多 token, 也可以把几百万 token 放进上下文; 一个工作流可以调用一百次工具, 任务还可以持续几个星期. 这些量都能变大, 却没有任何一个单独构成长程能力. 五十次互不相关的查询仍是五十道短题; 十步数据库迁移只要第一步决定了后面所有表结构, 就已经有很强的长程属性.

本路线把研究对象写成持续演化的任务状态 $s_t$. 动作 $a_t$ 作用于环境, 产生观测 $o_{t+1}$; 观测经过验证后, 才进入后续决策可依赖的事实集合. 决定难度的量包括依赖图的关键路径, 反馈延迟, 错误传播范围和恢复成本, 总步数 $T$ 只描述表面长度. 早期决定若要等很久才能验错, 并且许多后继动作都依赖它, 任务就会迅速变难.

[METR 的任务完成时间跨度](https://metr.org/time-horizons/)给出了另一种可测口径: 先估计人类专家完成各任务的时间, 再拟合 Agent 在这些任务上的成功概率, 取预测成功率达到 50% 时对应的人类任务时长. 它回答的是「在这组任务上, 系统大致能独立完成多长的人类工作」, 不是 Agent 自己运行了多久. 这种口径适合观察整体能力变化; 本路线关心的依赖深度则试着解释, 为什么两道同样耗费人类一小时的题, 对 Agent 可能完全不同. 一道题需要等待缓慢测试, 另一道题需要跨多步维护不断变化的数据库约束, 人类用时相近, 错误传播结构却不同. 两个量应当并排看, 不能互相替代.

## 1. 从表面长度走向有效跨度

可以先画一张有向无环图: 节点表示决策或状态变化, 边表示后者必须使用前者的结果. 关键路径给出无法并行消除的依赖深度; 一个错误节点能够到达的后继数, 近似描述它的污染范围. 两条轨迹即使 token 数相同, 只要关键路径和污染范围不同, 难度也可能差一个量级. [状态依赖与有效跨度](./1.1.1-状态依赖与有效跨度.md)从这套图模型出发, 区分输出长度, 运行时间, 上下文容量与有效 horizon, 并给出长度相同而难度不同的手算例子.

画边时要问「后一步的正确性是否真的取决于前一步」. 同一计划里列出的两次查询, 若互不读取对方的结果, 就不该因为执行顺序而连边; 数据迁移完成后再运行依赖新 schema 的程序, 则存在真实的数据依赖. 约束与对象身份也能构成依赖边. 后一步可能完全不读取前一步生成的文件, 但必须接受它确立的约束. 比如接口字段改名以后, 文档, 调用方和验收脚本都必须使用同一版本. 这几项工作可以并行修改, 最终却要共同接受版本一致性检查. 因此关键路径描述不可消去的串行深度, 汇合处的组合验证则检查并行分支能不能重新组成一个正确状态.

这套定义还有一个好处: 模型和 Harness 可以放进同一坐标系. 模型负责根据可见状态提出动作, Harness 保存环境事实, 目标版本和证据关系. 窗口再长, 也不能自动判断两条冲突信息谁更新; 模型再聪明, 也无法从一次没有返回值的外部调用中知道动作是否成功. 能力属于整个闭环, 不能全算在模型权重上, 也不能把 Harness 自动完成的步骤算成模型推理.

这里至少有三种状态要分开: 模型准备采取的动作, 工具报告的观察, 已经核实的事实. 「发出了写入请求」属于第一种, 「工具返回超时」属于第二种, 此时文件是否真的写入仍未知. 若执行体把未知直接记为失败, 重试可能造成重复副作用; 若记为成功, 后续动作可能使用根本不存在的结果. [LongHorizon-Harness](https://arxiv.org/abs/2608.01964)把任务状态放在执行上下文之外, 由只读审计环节检查环境后再更新状态, 正是为了让后续计划不依赖执行者的自我宣告. 这并不要求每一步都调用昂贵验证器, 但关键状态进入后继依赖之前, 必须知道由什么证据确认了它.

## 2. 错误之后还能不能继续

只看最终成功, 会把两种系统混在一起: 一种几乎不犯错, 另一种会犯错却能很快发现, 回滚和改道. 真实长任务很难保证前者, 因此恢复能力必须进入定义. 一个 checkpoint 的价值取决于它是否与外部副作用, 目标版本和验收证据对齐; 只保存聊天摘要, 通常无法阻止重复提交, 脏状态继承或基于旧目标继续执行.

恢复成本也不能只数「撤销了几步」. 如果错误在写入本地文件后立刻被发现, 版本控制通常能给出可信的回退点; 如果错误已经影响共享数据库, 后继任务可能读到了错误数据, 回滚本身还要处理这些读者; 如果动作已经向外部发送, 甚至没有严格意义上的回滚, 只能做补偿. 相同的错误发现延迟, 落在这三种边界上, 代价完全不同. 因而分析轨迹时应同时看错误首次出现的位置, 首次可验证的时刻, 受影响的后继和动作可逆性. 这些量会告诉我们优先改哪里: 提前验证, 缩短无证据的依赖链, 或者在不可逆动作之前收紧权限与确认条件.

[恢复成本与路径依赖](./1.1.2-恢复成本与路径依赖.md)继续讨论错误怎样沿依赖图传播, 以及恢复到可信边界需要撤销多少有效工作. 读完这两篇, 应该能够判断一个任务究竟长在哪里, 也能解释为什么「再给模型更长上下文」有时有效, 有时只是让错误在更大的窗口里停留得更久.

## 3. 一个贯穿全库的例子

假设 Agent 要在陌生仓库里修改数据库 schema, 迁移数据, 更新调用方并通过测试. 提交的代码行数可能不多, 真正的 horizon 来自依赖: 迁移依赖 schema, 调用方依赖新接口, 最终测试依赖前面所有状态一致. 若 schema 选错, 错误会潜伏到集成测试才暴露; 此时恢复成本包括撤销迁移, 修正数据和重跑验证. 这个例子后面会反复出现, 因为它同时包含状态变化, 延迟反馈, 不可逆风险与可执行验收. 若把任务改成读取十个互不相关文件并分别总结, token 可能更多, 依赖图却更浅. 这样的对照比给 Long-Horizon 规定固定步数更稳定.

把这次迁移拆开看, 「改完 schema」并不等于下一步可以放心迁数据. 新字段若允许空值, 历史行的回填规则是什么; 回填完以后, 旧读路径会不会把空值重新写回来; 新旧调用方是否可能在一段时间里同时运行, 这些都决定了下一条依赖边什么时候可以成立. 一个系统可以生成很多正确代码, 仍在版本交叠期间读错对象. 另一个系统代码写得不快, 却先验证兼容窗口, 给迁移加上可重复执行的检查, 每完成一段才向后推进. 比较两者时, 代码行数和动作数都不能解释可靠性差异, 要看哪些前提在被消费前已经变成可信事实.

读这条路线时, 可以先在自己的任务上找一条最长依赖链, 再找一处最晚才会暴露的错误. 若这处错误只影响当前步骤, 增加局部检查可能就够了; 若它能污染多个后继, 还需要找出共同的验证边界; 若污染已经跨出可回滚范围, 恢复方案必须包括外部状态核对与补偿. 这样就能在具体任务上辨认能力边界: 系统能否识别尚未证实的状态, 控制它被多少后继使用, 并在证据推翻它时继续完成原目标.

# 评测协议与因果归因

长程评测最诱人的数字是成功率, 也最容易让人误判. 一次运行通过了终态测试, 无法说明中间有没有反复破坏再修复, Harness 是否替模型补全了关键动作, 也无法说明系统遇到状态漂移后还能不能回来. 反过来, 一次失败可能已经完成大部分可验证工作, 只是在收尾步骤碰到外部服务故障. 若评测只留下一个比特, 这些差别都会消失.

评测协议因此要同时保存终态和事件轨迹. 终态回答任务是否完成, 事件轨迹回答它怎样走到那里. 每个事件至少绑定动作来源, 目标版本, 环境版本, 前置状态哈希, 观测, 验证结果和耗时. 这样才能从日志重建有效进度, 无效动作, 首次偏离位置, 恢复次数和重复副作用. 指标不必堆得很多, 但必须能对应定义中的依赖, 延迟, 传播与恢复.

假设两套系统都修好了一百个仓库问题, 其中一套每题只运行一次测试, 另一套反复撤销写入. 如果日志只留下成功率, 差别就消失了. 保留每次修改与测试的对应关系, 才能定位错误首次出现的决策边界, 看出失败后的动作是在修复问题还是盲目重试. 再把 token、墙钟时间和工具调用记在同一条轨迹上, 成本增加的原因才不会藏在漂亮的终态数字里.

## 1. 基准先证明自己测到了什么

一个任务被命名为 Long-Horizon, 不代表它真的含有长程依赖. 把提示重复一百遍主要测检索耐久; 把本可并行的子题串起来主要增加运行时间. 合格任务需要让早期决策改变后期条件, 并且最终验证器能检查这些条件是否持续成立. [任务构造与基准生命周期](./1.2.1-任务构造与基准生命周期.md)从构念效度出发, 讨论人类完成时间, 可执行软件终态, 密集子任务评分各自覆盖什么, 以及公开题库被反复调参以后怎样维护新鲜度.

[METR 的时间跨度测量](https://metr.org/time-horizons/)以人类专家完成任务所需时间为横轴, 用 Agent 在任务上的结果拟合成功概率, 再读取 50% 或 80% 成功率对应的时长. 这让不同长度任务上的可靠性有了直观坐标, 但时长只是任务难度的一个代理量, 不能单凭曲线判断错误发生在状态跟踪, 工具执行还是验证环节. 反过来看, [SWE-bench Verified](https://www.swebench.com/verified) 的 500 道实例经过人工筛选, 重点核对问题描述, 测试补丁和可解性; 它让软件终态评测更可信, 但静态实例的可解性核查也不能替代对目标变化、外部扰动和恢复路径的测试. 两类基准各自回答了有价值的问题, 长程评测要明确自己在它们之外额外测哪一种依赖.

验证器本身也要被测. 若它只检查文件是否存在, Agent 可以交一个空文件; 若同一环境没有复位, 后一条轨迹可能借用前一条留下的状态. 参考解, 故意破坏的解, 无动作对照和扰动测试共同给出验证器的假阳性与假阴性边界. 只有这些边界明确, 成功率才有稳定含义.

检查验证器时, 要给它真正容易混淆的输入. 一份只改变文件名的补丁可以试探它是否读了实际内容; 一份能通过公开测试却破坏隐藏约束的补丁可以试探测试覆盖; 原样提交则是最简单的无动作对照. 若无动作也通过, 后面的模型对比没有意义. 若正确实现经常被拒绝, 增加验证轮次只会把有效进展挡在门外. 验证器的错误率还应随任务类别和环境版本分别记录, 否则某个任务家族的系统性漏洞会被总平均掩盖.

## 2. 用干预解释改进来自哪里

长程系统由模型, 上下文管理, 状态存储, 规划器, 工具层和验证器共同组成. 总分上涨以后, 需要通过配对任务, 冻结预算和单组件消融判断增益来自哪里. 增加 checkpoint 若真改善恢复, 应看到重复副作用和丢失工作量下降; 增加规划器若真改善关键路径, 应看到无效动作或回退深度变化. 只给最终分数, 无法排除额外计算和提示泄漏.

「只替换一个组件」也要限定得更细. 两组运行应从同一任务初态开始, 使用相同任务版本, 工具权限和停止预算; 随机采样带来的波动通过多次运行记录. 比较时按任务计算实验组与对照组的差值, 再汇总不同任务的差值, 而不只比较两个互不对应的总平均. 如果改善只出现在容易题上, 长程失效机理可能完全没变. 若某一组件同时改变可见信息量或额外调用次数, 这两个量也要一并报告, 否则「规划器更好」可能只是因为它看到了更多证据或花了更多计算.

[故障注入与结果归因](./1.2.2-故障注入与结果归因.md)把目标更新, 工具超时, 进程重启, 环境漂移等事件按确定位置注入轨迹, 再用配对统计比较恢复. 它还讨论成本—质量前沿, 删失, 重尾任务和置信区间. 两篇共同建立评估次序: 先确认任务包含长程结构, 再确认验证器可信, 随后比较系统; 看到改进后继续追问, 是哪个组件改变了哪一个中间量.

故障位置应按任务状态来定义. 「第 50 次调用失败」对快慢不同的 Agent 可能发生在完全不同的阶段; 「第一次提交迁移结果之前撤销写权限」则让两组在语义相同的关口受扰动. 注入以后还要检查扰动是否真的到达系统: 进程重启有没有丢掉内存状态, 超时是否发生在外部动作完成前后, 环境漂移是否改变了后继依赖. 没有这些确认, 所谓故障实验可能只是对正常轨迹多加了一条日志. 评测记录故障前已经核实的进度, 故障后重新取得可信状态所需的时间和动作, 才能把恢复能力与普通任务能力分开.

## 3. 最小可复现实验

最小实验不需要先造一个持续数周的任务. 选择一批具有明确依赖链的可执行任务, 为每题固定初态和验证器, 各运行若干随机种子. 对照组使用基础 Agent, 实验组只替换一个组件. 随后在相同位置注入一次可恢复故障, 记录最终成功, 故障前有效进度, 恢复后重复工作, 额外 token 与墙钟时间. 任务级配对差值比两组总均值更有解释力, 因为同一任务的难度被抵消. 若实验组只靠更多重试获得成功, 成本曲线会暴露它; 若恢复机制确实有效, 受扰动任务的丢失工作量应下降, 而未扰动任务不应凭空大涨.

一次运行「没做完」可能因为预算耗尽, 外部依赖不可用, 也可能是验证器给出了明确反例. 它们都会影响用户是否拿到结果, 在故障定位里却需要分别记录. 对于重尾任务, 少数极难实例可能决定总耗时, 报告中位数的同时还应给出高分位成本与停止原因. 如果一项方法把平均成功率提高了, 却让极少数任务无限等待, 交付体验仍可能变差. 把停止原因和高分位成本放在成功率旁边, 代价转移就不会藏在一个总分里.

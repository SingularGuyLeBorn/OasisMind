# 递推记忆与状态连续性

长上下文的成本会随序列增长, 直接截断又会丢掉远处信息. 递推记忆给出另一条路: 每轮只保留固定大小的隐状态, 让新 token 通过更新函数写入, 再由后续层读取. 它把计算连续性从显式 token 序列移到模型状态中, 理论上可以让服务端以有界缓存处理更长历史.

设正在被注意力直接读取的窗口为 $C_t$, 随序列更新的隐状态为 $M_t$. 窗口中的 token 可以被精确定位, 却会在容量达到上限后被移走; $M_t$ 的大小不随已处理 token 数线性增加, 但会把许多经历压进有限维度. 两者保存的是不同形态的信息. 一段程序报错的精确行号适合留在可回源记录里, 而多轮交互形成的粗略背景可能通过隐状态影响下一次判断. 当未来问题需要逐字找回很久以前的随机字符串时, 固定容量隐状态没有理由保证这项能力.

不过, 隐状态, 上下文和任务状态承担的是三种职责. 隐状态擅长保存对预测有用的统计量, 活动上下文承载当前推理需要精确访问的文本, 外部任务状态保存目标版本, 权限, 文件哈希和验收结果. 原始证据还要单独留存, 以便重新计算和审计. 把四层都叫「记忆」, 就会误以为一个递推向量能够替代数据库, 事件日志和引用系统.

前一条[上下文压缩](../2.2-上下文压缩与状态提交/2.2-上下文压缩与状态提交.md)路线产生模型可读的短文本, 需要决定保留哪些事实以及怎样回源; 递推状态随输入在模型内部更新, 后续生成直接受它影响, 却很难从状态向量中追查某个结论来自哪条原始证据. 同一个系统可以同时使用两者: 工作窗口装最近步骤, 递推状态承接跨窗口影响, 外部索引负责准确检索, 任务状态机负责决定哪些条件已经证实. 不同信息要交给能够承担其精度与责任的位置.

## 1. 固定状态怎样随序列更新

递推模块通常接收当前隐状态 $m_{t-1}$ 与新输入 $x_t$, 通过门控更新得到 $m_t=f_\theta(m_{t-1},x_t)$. 容量固定不等于信息无损, 关键在于写入选择, 覆盖和读取. 训练信号若只来自最终语言建模或任务奖励, 模型会优先保留对平均预测最有用的信息, 罕见但关键的权限变化可能被覆盖.

[LiveMem 原论文](https://arxiv.org/html/2608.02515v2)给这个抽象配了一条具体路径: 预训练全注意力主路继续读取有界的当前窗口, 每个注意力层旁边增加使用 GDN2 的递推支路, 其输出回加到主路输出. 支路对进入的 token 持续更新状态; 当旧片段的 KV 被移出主路时, 不需要再临时把它「写入记忆」, 因为递推状态此前已经处理过这些 token. 由此可见, 有界的是主路可直接寻址的历史和支路状态大小; 一次推理总共处理过多少内容, 是另一回事.

只加一条支路, 模型仍可能始终依赖未移走的原文. LiveMem 在训练与推理中都让旧片段离开注意力窗口, 训练时冻结原模型并训练记忆支路, 使回答必须利用离开窗口后的信息. 这一设计把「状态真的被读取」变成可测问题: 如果关键证据已完全离开当前窗口, 模型仍能据此回答, 就说明支路携带了有用影响. [LiveMem 架构与训练](./2.3.1-LiveMem架构与训练.md)继续分析门控更新、训练阶段和消融, 区分递推状态的作用与单纯增加参数或缓存的收益.

## 2. 有界容量带来的新问题

状态向量把大量历史折叠到有限维度, 冲突, 不确定性和来源很容易被混成一个确定表示. 后续模型可能记得「某结论大概成立」, 却失去它来自哪次观察, 是否已经过期. 多用户服务还要处理状态隔离, 释放和复制; 一次错误复用就可能把另一个请求的信息带入当前轨迹.

论文的证据距离实验支持一个较窄的结论: 在 LongMemEval 的测试设置中, 关键证据离开活动窗口后, LiveMem 仍能保留可用信息, 距离增加时准确率有轻微下降. 附录的 needle-in-a-haystack 测试同时暴露相反边界: 在 32K 有界窗口下, LiveMem 与截断基线一样难以恢复任意细粒度字符串. 因而「旧内容仍能影响回答」与「旧内容可逐字检索」必须分开. 前者是连续状态的价值, 后者仍需要可寻址的外部存储或保留精确 KV 的机制. [容量边界与状态治理](./2.3.2-容量边界与状态治理.md)进一步处理写入干扰, 遗忘和容量压力.

还有生命周期边界. LiveMem 的服务实现为每个请求维护普通 KV 页和独立的递推状态槽, 请求完成时释放该槽, 避免不同请求相互泄漏. 因此论文展示的是一个请求生命周期内的状态连续性; 若产品希望下次会话继续使用旧状态, 还需要定义持久化, 重新载入, 授权与删除机制. 这些机制不由「有了递推层」自动产生. 状态的数学形状虽固定, 论文当前底座的位置编码仍有配置上限, 实验输入最多到 256K token; 也不能把固定状态大小写成已验证的无限长度服务能力.

[容量边界与状态治理](./2.3.2-容量边界与状态治理.md)讨论写入, 读取与覆盖的可辨识性, 设计证据距离, 容量压力和干扰实验, 并把内部状态放回完整长程系统. 适合内化的规律由递推状态保留, 需要精确回源的事实由外部索引保留, 决定任务是否完成的证据由可审计状态机保留. 这种分工比追求一个无所不包的「记忆模块」更接近真实系统.

## 3. 怎样判断递推记忆真的有用

评测应同时改变证据距离和干扰强度. 把关键事实放在不同距离, 插入语义相似却不相关的内容, 再观察模型能否读取正确信息; 随后替换或撤销早期事实, 检查状态是否会更新. 只测固定事实的远距离回忆, 容易把持续复制当成有效记忆. 还要比较相同计算预算下的长上下文, 检索与递推状态, 记录吞吐, 首 token 延迟和任务成功. 若递推模块只在窗口不足时有收益, 这就是明确的适用边界, 而非缺点.

比较时应把问题分两组. 一组问「数十轮以前的偏好是否仍对当前判断有帮助」, 容许近似表达; 另一组问「当时返回的文件哈希究竟是哪 64 个字符」, 必须逐字正确. 把两组混成一个平均分, 会奖励只擅长某一类任务的系统. 再固定同一底座、同一活动窗口与计算预算, 分别替换递推状态、检索和显式摘要, 才能判断收益来自连续影响, 精确回源还是单纯看到了更多 token. 一旦答案与权限、金额或外部副作用有关, 即使递推状态给出看似稳定的倾向, 系统也应回到可审计证据确认当前事实.

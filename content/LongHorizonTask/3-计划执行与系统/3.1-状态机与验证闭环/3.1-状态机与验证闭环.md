# 状态机与验证闭环

长任务当然需要计划, 但一份写得很漂亮的计划并不会自动让系统持续收敛. 环境在变, 工具会失败, 用户会改要求, 原先正确的步骤可能过期. 计划如果直接覆盖事实状态, 模型很容易把「准备执行」记成「已经完成」; 如果每次变化都从头规划, 又会丢掉已经验证的有效工作.

状态机提供了更稳的连接方式. 目标状态记录当前义务, 计划状态记录下一批候选动作, 环境状态记录工具真实改变了什么, 确认记录保存已经通过验证的结果. 计划可以频繁重算, 明确事件负责更新事实与证据. 验收要求和有效证据共同决定任务是否完成; 模型暂停生成或计划列表暂时为空时, 系统会重新检查状态.

比如一次数据迁移分为「写脚本」「运行迁移」「核对行数」「切换调用方」. 写好脚本只说明候选方案存在; 运行命令返回成功, 说明工具完成了调用; 核对目标库中的数据和约束, 才能确认迁移结果可供调用方使用. 若把这三种记录都写成同一个「已完成」标记, 后面看到的进度会越来越漂亮, 却无法定位哪一步没有真正成立. 状态机的作用是让每种标记有进入条件, 并把后继动作限定在它所需的条件满足以后.

## 1. Manage, Execute 与 Audit 各管什么

Manage 根据目标和可信事实选择下一步, Execute 在受限权限内调用工具, Audit 独立检查观察能否支持状态更新. 三者可以由同一个模型在不同上下文中承担, 也可以由多个模型或确定性程序完成; 关键不在角色数量, 而在写权限和信息边界. 执行者不能自行把候选结果标成已验证, 审计者也不应在缺少环境证据时补全成功.

[LongHorizon-Harness](https://arxiv.org/abs/2608.01964)把任务状态放在执行上下文之外, 采用 Manage-Execute-Audit 循环: Manager 依据已核实状态确定下一子任务, Executor 在新的上下文里完成操作, 只读 Auditor 查看环境后决定哪些事实可以更新. 这种分工针对一个具体失效点: 执行者在很长的对话里既做事又给自己的工作打分, 容易把早先未经证实的判断带进下一轮. 把审计改成只读, 至少让检查者不能为了让结果过关而顺手修改环境. 但只读权限本身并不保证判断正确; Auditor 还需要知道要检查哪个版本, 哪些断言能由当前工具验证, 哪些仍然未知.

[MEA 状态循环](./3.1.1-MEA状态循环.md)从 LongHorizon-Harness 的 Manage-Execute-Audit 结构进入, 推导状态合约, 滚动计划, 停止条件和最小实现. 它还解释 fresh context 为什么有助于隔离局部偏见, 却无法代替持久化状态: 上下文刷新后, 系统仍要从权威记录恢复目标, 已完成工作和未决风险.

执行与审计之间最重要的边界是「观察不等于提交」. 写入远端 API 后发生超时, 可能是请求没到, 也可能是远端已完成但响应丢失. Execute 只能记录请求标识与超时; Audit 应先查询远端对象或幂等键, 再判断是继续等待, 安全重试还是接受结果. 如果直接把超时判失败并重试, 一封邮件可能发两遍; 如果直接判成功, 后续任务会依赖一个不存在的对象. 同一个工具异常因此可以导向三条不同的恢复路径, 差别来自能否读到独立证据, 而不是模型能否写出更流畅的解释.

## 2. 验证与恢复决定闭环上限

Auditor 能看见什么, 能够调用哪些验证器, 决定系统最多能确认到哪一步. 测试覆盖不到的性质只能保持未知; 工具超时也不能被自动提升为失败或成功. 故障发生后, 系统要判断受污染范围, 回到与外部世界一致的 checkpoint, 再根据当前目标重新规划. 若 checkpoint 与真实副作用错位, 恢复可能重复发送消息或创建资源.

验证还具有时效性. 测试在提交 A 上通过, 不能直接证明随后提交 B 仍然通过; 目标要求从「支持旧接口」改成「删除旧接口」, 旧证据即使对应同一个文件也已不够用. 因此证据要绑定被检查的产物版本和目标版本. 有些证据只覆盖局部性质: 单元测试能证明一个模块的行为样例, 不能证明合并后整个站点没有断链. 当状态版本变化, 系统沿依赖关系把受影响的命题退回待验证, 保留不受影响的结果, 再在汇合点运行更大的检查. 这比「变化就全量重做」节省工作, 也比「有旧测试记录就继续」可靠.

[审计恢复与能力归因](./3.1.2-审计恢复与能力归因.md)用故障注入检查这些边界, 并拆分模型, Harness 和环境对结果的贡献. 掌握状态转移, 验证覆盖和恢复以后, 评价新的 Agent 框架就有了三个直接问题: 谁拥有真相, 哪些事件可以改状态, 错误以后从哪里继续.

长任务里还有晚到的结果. 旧目标下启动的后台作业, 可能在用户修改要求后才结束; 如果回调不携带目标版本, 它会把过期产物写回当前状态. 同样, 重启后重复送达的事件也可能让同一项进度增加两次. 接收结果时应先比对它所依据的目标和环境版本, 重复事件只消费一次, 版本过期但内容仍可复用的部分重新验证后再提交. 这几个检查让状态机真正约束执行, 而不是只在日志里画几个状态名称.

## 3. 进度是一组已证明的命题

计划列表勾掉多少项并不等于有效进度. 更稳的表示是把任务要求写成命题, 把测试, 文件哈希或外部查询结果作为证据. 只有证据满足当前版本的要求, 命题才从 pending 进入 verified; 目标变化或环境漂移会让它退回待验证. 这样定义以后, 恢复不必依赖模型回忆做过什么, 只需从最近仍成立的命题集合继续. 它也能识别一种常见假完成: Agent 没有下一步可生成, 却仍有要求缺少证据. 系统此时应报告阻塞或继续获取观测, 而非把停机当成成功.

命题之间也有依赖. 「迁移后所有行都满足新约束」需要先有确定的 schema 版本和迁移范围; 「新调用方运行正常」还依赖部署的是哪份构建产物. 若父条件失效, 不能只把那个条件改回 pending, 还要检查依赖它的后继证明是否仍成立. 反过来, 一次局部失败不必抹掉全部进度: 文档断链通常不影响已经核实的数据行数, 只要求修复引用并重验相关页面. 恢复时保留这种精度, 才能避免系统一有错误就从头开始, 或者带着已失效的勾选继续向前.

停止也要服从这些命题. 所有当前要求都有有效证据, 才能报告完成; 某项检查还在等待异步结果, 状态就是等待, 不能因为眼前没有动作可做而宣告成功; 必需证据始终无法取得, 则应说明阻塞点和已经确认的部分. 三种出口留给用户的是不同的信息: 完成可以直接使用产物, 等待需要继续观测, 阻塞需要改变条件或取得外部帮助. 把它们都写成「本轮结束」, 长任务交接时就会丢失最关键的下一步.

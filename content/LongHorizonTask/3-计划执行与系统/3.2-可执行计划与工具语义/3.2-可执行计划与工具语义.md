# 可执行计划与工具语义

自然语言计划适合表达意图, 却不擅长精确保存循环, 分支, 异常处理和中间结果. 任务一长, 模型会反复描述同一流程, 也容易漏掉某个失败分支. 代码和结构化工具调用可以把一部分控制流外置: 程序保存变量, 运行时调度步骤, 测试检查性质, 版本系统记录变化. Agent 此时不必在每轮对话里重新模拟整个执行过程.

代码也会把错误固化. 模型生成的脚本可能拥有过宽权限, 重试可能重复副作用, 并行分支可能在共享文件上互相覆盖. 可执行并不等于可信; 它只是让行为更容易复现和检查. 外层 Harness 仍要限制能力, 记录输入输出, 并把工具的真实返回值与模型原始动作分开保存.

这里有两个经常被混在一起的状态: 计划走到了哪一步, 外部世界实际变成了什么. 程序走到「调用已发出」之后, 只能说明控制流向前走了; 如果工具超时, 远端请求也许已经生效. 反过来, 环境状态正确也不意味着计划正确: 另一个人可能恰好做了同样的修改. 因而一次动作至少要留下调用前条件, 请求标识, 工具返回和独立观测. [Code as Agent Harness](https://arxiv.org/html/2605.18747)把代码放在推理、行动、环境三层交界处, 可执行策略的可靠性正是从这些接口之间的核对产生的.

## 1. 工具动作需要明确的效果语义

同一个 `run` 调用可能只读文件, 也可能写库, 发消息或付款. 长程系统至少要知道动作是否可重放, 是否可撤销, 如何确认完成以及幂等键是什么. 对于可逆写操作, checkpoint 可以保存前态并提供补偿动作; 对于不可逆动作, 系统应在执行前完成验证和授权, 而非出错后假装能够回滚.

最简单的区分是「读取」「有条件写入」「不可逆提交」. 读取失败通常可以重试, 前提是读取对象的版本没有悄悄变化; 有条件写入应先确认旧版本, 再用版本号或内容哈希拒绝过期动作. 发出邮件或转账后, 本地进程崩溃不等于远端未完成. 此时先拿同一个请求标识查询状态, 再决定是否补发. 如果远端根本不提供幂等键或查询接口, 自动重试就不能声称是安全恢复, 只能把不确定性显式交给人处理.

所谓补偿动作也有边界. 文件从版本 A 改到 B 后, 若另一位协作者已经把 B 改成 C, 直接恢复 A 会抹掉对方工作. 合理的补偿条件是「当前仍等于我写入的 B」; 条件不成立, 系统保存冲突证据并停下来协调. 计划的每条边因此除了 `next` 还要写清前置条件、动作效果与失败后的合法去向, 否则流程图画得再完整, 执行时仍然只能猜.

权限也应绑定动作所处的阶段. Agent 为诊断故障读取日志, 不必因此得到修改生产配置的权限; 通过测试的候选补丁, 也不等于已经获准发布. 当计划走到需要更高权限的步骤, 应把待执行的具体动作和当前验证结果一起提交, 而不是给整段脚本一张长期有效的通行证. 这样人批准的是一个确定状态下的动作, 状态一变就需要重新核对前提.

[代码 Harness 与副作用](./3.2.1-代码Harness与副作用.md)从代码作为 Agent Harness 的三层结构进入, 讨论沙箱, 事务, 并发冲突和可执行记忆. 已经验证的解析器与测试可以复用为程序化记忆, 但它们必须携带适用前提和版本; 脱离原环境直接复用, 可能把过去的偶然条件当成一般规律.

## 2. 可执行策略怎样接受因果检验

把计划写成程序以后, 可以记录每个分支的输入, 输出和环境变化, 并在同一初态下替换一个组件做对照. 这样的实验比阅读最终代码更接近因果归因: 关闭自动重试, 限制工具权限, 替换验证器, 再观察成功率, 无效动作和恢复成本如何变化. 若关闭某组件后只减少运行时间却不影响任务质量, 它可能只是吞吐优化; 若关键状态不再能够恢复, 它才是长程闭环的一部分.

对照不能只看终局分数. 两种策略都通过测试, 其中一种却改动了无关文件, 或在失败后多发了一次通知, 终局成功率会掩盖差异. 更有用的记录是同一个任务初态下的有效动作数、重复副作用数、首次错误出现的位置、恢复到可验证状态所需的步骤, 以及最终是否真正满足用户约束. 若两组实验使用的工具权限和任务预算不同, 分数差异也不能单独归给「计划写成了代码」.

还可以把验证器单独拿出来检验. 例如只运行语法检查时, 配置文件可能合法却没被服务加载; 加入接口探针后, 同样的动作序列才暴露出「写了文件、没重启成功」. 这时提升来自新增的可观测证据, 而非模型突然更会规划. [Code as Agent Harness](https://arxiv.org/html/2605.18747)讨论的执行反馈与确定性检查, 价值就在于把这种差别显露出来.

[可执行策略与因果评测](./3.2.2-可执行策略与因果评测.md)进一步给出生成代码的生命周期, 动作事务语义, 人类监督位置和因果消融. 两篇文章共同强调一条边界: 代码适合承载确定控制与可验证中间结果, 模型适合处理开放语义与提出候选方案, 环境负责给出事实. 可靠系统来自三者接口清楚, 不来自把更多逻辑塞进任何一层.

## 3. 从一次工具调用看完整边界

以「修改配置并重启服务」为例. 模型提出目标文件和新值, 工具层先读取当前版本并校验前置条件, 写入时产生新的内容哈希, 重启命令返回进程状态, 验证器再从服务接口检查配置是否生效. 若验证失败, 系统先确认文件仍是本次写入的版本, 才根据写入前哈希回滚, 并确认旧服务恢复. 这里至少有候选动作, 实际副作用, 观察和验收四种对象. 日志若只保留一句「配置已更新」, 后续既无法判断重启是否发生, 也无法安全重试. 明确的效果语义把这些差别留了下来.

把这个例子再推一步: 写入后重启请求超时, Agent 不应立即再发一次重启. 它先读取进程启动时间和接口实际配置, 判断上一次请求是否已经生效; 若服务仍在旧版本, 才在相同任务约束下重试. 回滚也须重新读取文件哈希, 确认没有第三方在其间修改. 「确认完成」因此是一条带条件的状态转移, 不是工具返回 `0` 的别名.

若这段计划交给多个执行体协作, 每份验证结果还要绑定它检查过的内容版本. A 对版本 B 跑完测试, C 随后又改了配置, 原来的「测试通过」不能直接授权发布 C 的版本. 合并后重新运行受影响的检查, 比让几个 Agent 互相转述「我这边没问题」更可靠. 共享仓库与执行记录只有带上版本关系, 才能成为下一步决策的共同状态.

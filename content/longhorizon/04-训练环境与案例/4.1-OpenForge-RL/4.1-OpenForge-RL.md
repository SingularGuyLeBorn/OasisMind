# OpenForge RL：在真实部署 Harness 里端到端训练 Agent

> 论文：OpenForge RL: Train Harness-native Agents in Any Environment
> 作者：Xiao Yu, Baolin Peng, Ruize Xu, Hao Zou, Qianhui Wu, Hao Cheng, Wenlin Yao, Nikhil Singh, Zhou Yu, Jianfeng Gao（Columbia / Dartmouth / Microsoft Research）
> arXiv：[2607.21557](https://arxiv.org/abs/2607.21557)（2026-07，ICLR 2027 under review）
> PDF：`content/uploads/papers/openforge-rl.pdf`
> GitHub：[MSR-Orchard/OpenForge-RL](https://github.com/MSR-Orchard/OpenForge-RL)
> 环境层：[microsoft/Orchard](https://github.com/microsoft/Orchard)

## 一、在部署 Harness 中生成训练轨迹

### 简化 rollout 与真实部署的失配

当代 SOTA Agent 的能力越来越来自 **inference harness**——Claude Code、Codex、OpenClaw、ZeroClaw 等 orchestration 层管理多轮交互、工具调用、上下文与 MCP 接入。然而开源 SFT/RL 栈通常假设**简化的单进程 rollout**：固定 chat template、无子 agent、无 harness 特有控制流。

这造成 **train–deploy mismatch（训练–部署失配）**：在简化环境里训出的 policy，部署到真实 harness 时，工具 schema、上下文管理、子 agent 路由、错误恢复语义都可能不同——Orchard 论文已展示：OpenSWE-32B 换到从未见过的 Kimi-CLI harness 时 SWE-bench Verified 从 45.0 崩到 3.6。OpenForge RL 的核心问题是：**能否在 Agent 实际部署的 harness 里做端到端 RL，且与任意 RL 训练后端（如 veRL）解耦？**

### Proxy 与 K8s Orchestrator

OpenForge RL 由两个正交组件构成：

### Lightweight Proxy：轻量代理

- 插入 harness 与推理服务之间，**Serving harness 发起的全部 LLM/VLM 调用**。
- 将请求路由到 RL 框架的 inference engine（训练中的 policy）。
- **记录 io-pair**，在 rollout 结束后重建为 `(s₀,a₀,r₀, …, s_T,a_T,r_T)` 轨迹，供 veRL / slime 等标准 RL codebase 消费。
- 关键性质：**不修改 harness 内部逻辑**——换 harness 只改 sandbox 镜像/启动命令，不改 trainer。

### K8s Rollout Orchestrator：编排器

- 每个 rollout 在**独立远程容器**中运行（与 Orchard Env 集成）。
- 容器预装目标 harness（OpenClaw、ZeroClaw、Codex、Claude、Pi、OpenCode、Hermes 等）及任务环境（Terminal、Web、Computer Use）。
- 训练与 rollout **物理解耦**：rollout 占 CPU 容器，policy 更新占 GPU 节点——可 scale 0 → 数千并行 sandbox。

整体数据流：

```
Trainer (veRL, GPU)  ←── trajectories ──  Proxy (intercept & collect)
       │                                      ↑
       └── generation requests ──────────────┘
                                              │
                         Orchestrator → Sandbox Pod × N
                                      (真实 Harness + Environment)
```

**数据合成（Claude Agent SDK + Opus 4.6）** 五阶段 pipeline：Propose → Refine → Implement → Verify → Package，并行生成 Claw / GUI 域任务；SFT pool 经 benchmark 去重与流行网站过滤。

**两条 Recipe**：

| Recipe | Backbone | 训练数据 | 评测 harness |
|---|---|---|---|
| **OpenForge-Claw** | Qwen3-30B-A3B-Thinking | ~0.2K–2.6K 合成 Claw 任务 | ZeroClaw / OpenClaw / Codex / ReACT |
| **OpenForge-GUI** | Qwen3-VL-8B | SFT + RL（~2.5K 任务） | 纯 screenshot 输入的 computer-use |

### Claw、GUI 与跨 Harness 结果

**OpenForge-Claw（30B-A3B）** — ClawEval / QwenClawBench / MCPAtlas：

| 阶段 | ClawEval pass@3 | QwenClawBench | MCPAtlas |
|---|---:|---:|---:|
| Qwen3-30B-A3B-Thinking 基线 | 39.8 | 21.8 | 12.4 |
| OpenForge-Claw (SFT) | 52.1 | 32.1 | 23.6 |
| **OpenForge-Claw (SFT+RL)** | **55.9** | **33.7** | **28.1** |

对比同量级开源：Qwen3-32B pass@3 31.7 / MCPAtlas 22.5；LLaMA-4-Scout pass@3 16.8。距 Claude Opus 4.6（ClawEval pass@3 80.8）仍有巨大 gap，但 SFT+RL 一致提升。

**Harness 迁移（ClawEval pass@1）** — 训练多 harness vs 单 harness：

| 模型 | ReACT* | ZeroClaw | OpenClaw | Codex |
|---|---:|---:|---:|---:|
| Qwen3-30B-A3B 基线 | 26.1 | 32.5 | 11.4 | 12.2 |
| OpenForge-Claw (SFT+RL, 三 harness 训练) | 45.1 | 48.5 | 20.9 | **32.5** |

单 harness 训练已泛化到未见 harness（ZeroClaw-only → OpenClaw +3.3、Codex +4.6）；**三 harness 联合训练全面最优**，复杂 harness（OpenClaw、Codex）增益最大。

**OpenForge-GUI（8B）** — pass@1：

| 阶段 | OSWorld-Verified | Online-Mind2Web | WebVoyager |
|---|---:|---:|---:|
| Qwen3-VL-8B | 29.4 | 38.7 | 49.2 |
| OpenForge-GUI (SFT) | 34.4 | 57.4 | 61.5 |
| **OpenForge-GUI (SFT+RL)** | **37.7** | **63.0** | **72.3** |

亮点：仅 **2.5K 任务**训练，Online-Mind2Web **63.0** 超过 MolmoWeb-8B（35.3，200K+ 任务）；WebVoyager **72.3** 接近 UI-TARS-1.5-7B（66.4）。论文强调：**在真实 deployment harness 里训练，样本效率显著高于简化栈上的大规模 SFT**。

**RL 行为分析（ClawEval）**：SFT→RL 后，generic shell 工具调用占比下降（22.6% → 13.9%），转向专用 service tools；**self-verification、format robustness、tool coverage、step efficiency** 等行为维度 SFT+RL 全面高于 SFT；**error recovery 仍弱**——RL 主要提升 reliability，非全能。

训练资源：Claw RL ~48H（8×B200 policy + Azure rollout VM）；GUI browser-use ~32–36H。

**Discussion 三章结论（Section 5）** 对 harness 研究有直接指导意义：

- **Q1：哪个 harness 更难学？** Codex / OpenClaw 等多进程、强工具编排的 harness 显著难于 ReACT* 简化栈——同样的 SFT+RL 预算下，复杂 harness 上的绝对分更低，但 RL 相对增益更大。
- **Q2：跨 harness 迁移？** 在 ZeroClaw 上训练已能提升未见 OpenClaw / Codex 表现；三 harness 联合训练是 Pareto 最优——说明 policy 学到的是 partially harness-agnostic 的 agentic skill，而非 memorizing 单一 CLI 语法。
- **Q3：RL 加了什么？** 主要是 **reliability**（self-verification、专用工具覆盖、步数效率），而非 **error recovery**——后者在 SFT+RL 后仍接近随机，暗示需要 failure-centric curriculum 或显式 recovery reward。

Claw 域 RL 超参（Table A1 摘要）：lr 1e-6、batch 8、group 8、KL 0.001、max rollout 900s/step、100 training steps；GUI browser-use lr 1e-6、group 5、KL 0、entropy 0.001。Rollout pod 2–4 CPU / 2–6 GiB RAM——刻意 Small footprint 以提高并发。

### 复现成本与适用边界

- **完整复现门槛高**：核心实现虽已公开，训练仍依赖 Orchard Env、Kubernetes、veRL 与成规模的推理资源，单机很难复现论文吞吐。
- **任务规模小**：Claw ~2.6K、GUI ~2.5K，泛化边界未充分探索。
- **Proxy 假设**：要求 harness 所有 LLM 调用走可拦截 API；本地嵌入式模型或硬编码路径可能漏采。
- **Error recovery 瓶颈**：RL 后仍弱，可能需要 dedicated failure-centric 数据。
- **闭源 SOTA gap**：距 GPT-5.4 / Claude Opus 4.6 在 OSWorld（75.0 / 72.7）仍差一个数量级。
- **成本结构**：每 rollout 一容器，虽比 managed sandbox 便宜（Orchard Env spot 约 0.10×），但 RL 需要海量 rollout，总成本仍可观。

## 二、轨迹重建与训练闭环

### Recipe、环境与训练器的数据流

OpenForge RL 在 Orchard 三层栈中位于 **Recipe 层**，依赖 **Orchard Env** .foundation：

| 层 | 组件 | 职责 |
|---|---|---|
| Recipe | OpenForge RL | Proxy + 数据合成 + veRL 训练循环 |
| Foundation | Orchard Env | K8s sandbox REST API、in-pod agent、网络隔离 |
| Trainer | veRL / slime | Policy 优化、inference engine |

**Rollout 生命周期**：

1. Orchestrator 按任务 spec 启动 sandbox Pod（2 CPU / 2–6 GiB，任务 Dockerfile + harness 预装）。
2. Harness 在 sandbox 内驱动多轮 agent↔environment 交互；每次 LLM 调用经 Proxy 转发到 trainer 的 inference server。
3. Proxy 记录 (prompt, response, metadata)；episode 结束信号触发 trajectory reconstruction。
4. Trainer 消费轨迹做 PPO/GRPO 等更新；新 policy 权重同步回 inference server，进入下一批 rollout。

**与 Orchard 原有三 Recipe 关系**：Orchard-SWE/GUI/Claw 是「Env + 简化/固定 harness」路线；OpenForge RL 是后续工作，**把 harness 本身换成部署态真实栈**（ZeroClaw、OpenClaw、Codex），专门消除 mismatch。

### 可启动的环境规范

OpenForge RL 的数据合成流水线产出一份可以启动的环境规范，自然语言题目只是其中一项。对每个任务，至少需要固定以下对象：

- **初始状态**：sandbox 镜像、目录内容、账户或页面状态、依赖版本和预置服务；
- **动作空间**：Harness 能暴露给 policy 的 shell、文件、浏览器、MCP 与领域工具，以及各工具的参数 schema；
- **目标描述**：Agent 可以看到的任务文本和不能泄漏给它的隐藏验收条件；
- **终止规则**：成功提交、达到时间或步数预算、Harness 主动停止、环境崩溃分别怎样编码；
- **验证器**：从最终环境读取什么事实，怎样区分成功、任务失败和基础设施异常。

初始状态必须可重建。若任务要求修复仓库，镜像摘要、代码 commit 和依赖锁文件应一起记录；若任务发生在网页，登录态、页面版本和后端数据也属于状态。只保存一段 prompt，几周后重新运行时得到的已经可能是另一道题。环境生成阶段的 `Verify` 因而有两层含义：它既要确认任务可完成，也要确认验证器能从干净初态判失败、从参考完成态判成功。

动作空间同样影响任务难度。给 Agent 一个领域专用工具，与只给通用 shell 后让它自行调用 API，并不是同一实验。Proxy 虽然能够看到 LLM 请求和响应，却未必自动掌握 Harness 内部的所有确定性动作。因此轨迹清单需要标出：哪些动作由 policy 直接生成，哪些由 Harness 按规则插入，哪些环境变化来自外部事件。缺少这层区分时，训练器可能把 Harness 的固定行为误算成模型 action。

### 从 Harness 日志重建可训练轨迹

一次真实 Harness rollout 可能包含多轮 LLM 调用、子进程、上下文压缩和工具返回。Proxy 记录的基本单元是调用时模型真正看到的输入 $x_t$ 与生成的输出 $a_t$。训练轨迹还需要把它们与环境观察和 episode 身份对齐：

$$
\tau=\{(k,t,x_t,a_t,o_{t+1},m_t)\}_{t=0}^{T-1},
$$

其中 $k$ 是 rollout 标识，$t$ 是逻辑顺序，$o_{t+1}$ 是动作后的环境观察，$m_t$ 保存 Harness、工具和截断等元数据。多进程 Harness 不能只依赖日志到达时间排序，因为并发请求可能交错；重建器需要稳定的 episode、parent call 和 sequence 标识，才能恢复每条分支实际看到的历史。

训练时还要明确 logits mask。系统消息、用户任务和工具返回构成 state，只为模型生成的 token 计算 policy loss；Harness 自动拼接的模板或确定性路由不应被当成模型选择。若消息经过上下文压缩，Proxy 应记录压缩后的真实输入，同时保留压缩器版本。否则训练数据声称模型根据完整历史做出动作，实际部署时它看到的却是另一份摘要。

轨迹终点需要绑定验证证据。Harness 退出和模型输出「完成」都只能标记执行流程结束；reward 由验证器重新读取环境后给出，例如执行测试、查询后端状态或检查目标页面。episode 最终可被标成 `success`、`task_failure`、`timeout`、`environment_error` 和 `verifier_error`。后两类通常不应直接作为 policy 的负样本，因为模型未必有机会影响它们。

### 最终奖励、过程进度与一个小型手算

OpenForge RL 强调 task-native verifier。最干净的终局奖励可以写成：

$$
r_T=\mathbb{1}[V(s_T)=\text{success}], \qquad r_t=0\;(t<T).
$$

它回答的是最终任务有没有完成。过程进度则描述中间状态离验收条件还有多远，例如通过了多少个独立测试、是否建立了正确资源、是否完成必要的自检。过程进度适合诊断和构造辅助信号，却不能自动冒充最终奖励：通过四个测试中的三个，不一定代表任务完成了四分之三，其中一个失败可能正好暴露核心功能缺失。

考虑同一任务采样四条轨迹，最终验证结果为 $[1,0,1,0]$。组内平均奖励为

$$
\bar r=\frac{1+0+1+0}{4}=0.5.
$$

若使用最简单的组内中心化优势，四条轨迹得到

$$
A_i=r_i-\bar r=[0.5,-0.5,0.5,-0.5].
$$

成功轨迹中的 policy action 被提高概率，失败轨迹中的 action 被降低概率。现在假设第二条轨迹已经通过三个过程检查，但最终验证失败；它的终局奖励仍是 $0$，优势仍为 $-0.5$。这三个检查可以作为分析字段，也可以在经过论证后加入 shaped reward，例如 $r'_i=r_i+\lambda p_i$。然而只要 $\lambda>0$，优化目标就改变了：policy 可能学会积累容易通过的中间项，却不完成最后的关键条件。

再看第四条轨迹。Sandbox 在验证前崩溃，这属于 `environment_error`；若仍记成 $0$，它同样得到 $-0.5$，模型会为系统故障受到惩罚。该样本应从有效 reward 组中剔除或重新 rollout。剩下三条有效轨迹的均值变为 $2/3$，相应优势也要按实际采用的归一化规则重新计算。这个小例子说明：**奖励计算之前，先把终局事实、过程进度和系统异常分开。**

若 reward 只在终点出现，长轨迹仍有 credit assignment 困难。给整条 response 序列分配同一个 episode advantage 是常见近似，但它无法指出某次工具选择究竟好在哪里。OpenForge 的行为分析表明 RL 提升了 self-verification、工具覆盖和步数效率，却没有同等解决 error recovery。这与终局奖励的性质一致：成功样本能强化一整套可靠行为，稀少的失败恢复片段却难以得到清晰、稳定的局部信号。

### RL 更新与异步 rollout 的边界

在一次训练迭代中，trainer 固定 policy 版本，Orchestrator 启动一批 sandbox，Harness 经 Proxy 请求生成，验证器给出 episode reward，随后 trainer 才用这些轨迹更新参数。无论底层采用 PPO、GRPO 还是其他 on-policy 变体，都需要知道每条 action 是由哪个 policy checkpoint 生成的。若 rollout 持续时间差异很大，而新旧 policy 的轨迹混入同一 batch，重要性比率和组内比较的含义都会变得含糊。

因此，轨迹元数据至少要含 `policy_version`、采样参数、Harness 版本、任务版本和 reward 版本。异步系统可以容忍不同 episode 在墙钟时间上交错，但不能让样本来源不可追踪。训练器也要分别统计有效轨迹率、环境失败率和验证器失败率；只报告 GPU 利用率或总 rollout 数量，会掩盖大量不能用于更新的坏样本。

真实 Harness 训练还有一个选择性偏差：特别长或频繁失败的 episode 更容易超时，最终进入 batch 的可能主要是短轨迹。如果不报告长度分布和截断原因，policy 看起来在改善，实际上训练数据可能逐渐偏向简单任务。对长任务而言，`max rollout` 是实验条件，也是改变数据分布的过滤器。

### 泄漏、不可复现与判定器错误

合成任务最直接的泄漏来自 benchmark 本身。若生成模型能看到评测任务、参考实现或隐藏测试，再通过改写进入训练池，最终分数无法说明泛化。论文的数据流水线包含 benchmark 去重；复现时还应在任务文本、代码片段、网站目标和验证逻辑多个层面检查近重复，不能只比较标题字符串。验证器源代码若直接暴露在 Agent 可读目录里，也可能诱导 policy 针对检查条件投机，而不是完成真实目标。

不可复现通常来自环境漂移。容器标签指向了新镜像、网站内容更新、MCP server 升级、依赖下载到不同版本，都会改变状态转移。每个任务包应记录内容寻址的镜像摘要、资源校验和、网络策略、Harness commit、工具 schema 与验证器 commit。若必须依赖实时服务，至少要记录执行时间和关键响应，并把服务不可用单独计数。

判定器也会犯错。**假阳性**把未完成任务判成功，会直接奖励投机行为；**假阴性**把正确的等价解法判失败，会压低合理策略。发布 benchmark 前，可以让参考解、已知错误解和一组扰动解共同经过 verifier：参考解应稳定通过，缺关键功能的扰动解应稳定失败，重复执行不应因残留状态改变结果。对 GUI 任务，只看最终截图往往不够，后端状态或可访问性属性能提供更稳定的事实。

### 一套可执行的评测协议

要验证「Harness-native 训练」而不是其他变量带来的提升，可以按以下协议组织实验：

1. **冻结任务包**：给每个任务固定初始快照、动作权限、终止条件和 verifier 版本，并清理与训练池的近重复项。
2. **固定 policy 条件**：比较系统使用同一 backbone、checkpoint、采样参数和上下文预算；若训练后模型不同，则另设推理 Harness 消融。
3. **建立 Harness 矩阵**：至少包含训练中出现的 Harness 和未见 Harness；记录各自工具 schema、上下文策略和自动重试行为。
4. **隔离 rollout**：每次从干净 sandbox 启动，保存 policy、任务、镜像、Harness 和 reward 的版本标识，禁止上一条轨迹残留状态。
5. **运行外部验证**：Harness 退出后由独立 verifier 检查环境；将任务失败、超时、环境错误和 verifier 错误分开。
6. **报告共同预算**：除 pass rate 外，同时报告有效 episode 数、墙钟时间、token、工具步数、截断比例和每个成功任务的成本。
7. **检查恢复能力**：单列需要从失败中恢复的任务，不用总体成功率代替；OpenForge 的分析已经提示这一维仍弱。
8. **保存可复算产物**：保存任务清单、去重方法、轨迹 schema、版本 manifest 和逐任务验证结果；公开代码仍不足以替代论文未提供的完整训练资源与运行记录。

这套协议不要求所有系统内部实现相同。它要求共同控制的变量真正一致，并把无法控制的差异完整报告。只有这样，三 Harness 联合训练的收益、未见 Harness 迁移和 RL 带来的可靠性变化，才能与额外预算、环境差异或判定器偏差区分开。

### Train-deploy mismatch 是怎样产生的

真实 Harness 会改写模型实际面对的决策过程。它决定 system prompt 怎样拼接、工具如何命名、历史何时压缩、错误会不会自动重试，也决定一次模型输出之后环境返回什么。训练时若用一个简化 ReAct loop，部署时换成 Codex 或 OpenClaw，表面上仍是同一个模型，状态空间与动作空间却都变了。

可将部署 Harness 诱导出的轨迹分布记为 $d_{H_d}^{\pi}$，训练 Harness 的分布记为 $d_{H_t}^{\pi}$。某个策略在训练分布上的期望回报为：

$$
J_{H_t}(\pi)=\mathbb{E}_{\tau\sim d_{H_t}^{\pi}}[R(\tau)].
$$

部署时真正关心的是 $J_{H_d}(\pi)$。两者差异来自 Harness 对状态、动作与转移的共同改写，不能只用「prompt 有点不同」概括。举个具体例子：训练 loop 把工具错误原样返回，部署 Harness 却会自动重试两次再压缩错误；模型在训练中学到的恢复动作，部署时可能接收到另一种观察，甚至没有机会看到第一次失败。

动作 schema 也会制造错位。训练环境把写文件表示为 `write(path, content)`，部署环境可能要求 patch、基线哈希和权限确认。策略即使理解任务，也可能因格式不适配而无法行动。OpenForgeRL 让真实 Harness 自己构造上下文并解析调用，Proxy 只拦截它原本就会发出的模型请求，这才保留了部署时的接口语义。

多 Harness 训练可以看成在多个分布上共同优化：

$$
J(\pi)=\sum_{h\in\mathcal H}\lambda_h\,\mathbb{E}_{\tau\sim d_h^{\pi}}[R_h(\tau)],
$$

其中 $\lambda_h$ 控制各 Harness 的采样比例。若简单 Harness 便宜、成功率高，它可能占据大部分有效轨迹，策略随后偏向容易解析的工具格式。训练调度器需要同时观察任务域、Harness 与结果分桶，避免总样本数很大，复杂 Harness 却几乎没有产生可用更新。

### Proxy 拦截面与轨迹忠实度

官方仓库把 recording proxy 放在 Harness 与 OpenAI-compatible endpoint 之间，这个位置能看到每次模型请求与响应，却看不到所有环境变化。Harness 可能在两次模型调用之间自动裁剪历史、执行确定性重试、启动子进程，甚至按规则补上一条工具消息。轨迹重建器必须明确哪些事件来自 policy，哪些来自 Harness。

一条可训练记录至少需要如下标识：

```text
episode_id / parent_call_id / sequence_id
policy_version / harness_version / task_version
messages_seen_by_model / sampled_tokens / sampling_config
tool_call / tool_result / termination_reason
reward_version / verifier_result / infrastructure_status
```

`messages_seen_by_model` 应保存请求发出时的真实消息，而非事后从完整日志推测。若 Harness 在请求前做过 compaction，训练就应使用压缩后的输入；把被删历史重新塞回样本，会让优化器学习一个部署时不存在的条件分布。`sampled_tokens` 还要配套 logits mask，只给 policy 真正生成的 token 计算损失，不能把 Harness 模板和工具返回当成模型答案。

多进程 Harness 对顺序提出了更高要求。日志到达 Proxy 的墙钟顺序不一定等于因果顺序；两个子进程可能并行请求，各自依赖不同父调用。只靠时间戳拼接，会产生一条现实中从未出现过的对话。`parent_call_id` 与局部序号用于恢复调用树，训练器随后选择保留分支结构，或按清楚定义的规则切成多条样本。

轨迹忠实度可以用三项检查：请求重放后消息哈希一致；动作在相同 checkpoint 上能复现相同工具调用；终局 reward 能由独立 verifier 重算。三项分别覆盖输入、转移和结果。任一项失真，RL 都可能稳定优化错误的数据。

### Rollout 吞吐如何手算

远程 sandbox 把 CPU 侧执行与 GPU 侧更新解耦，但 GPU 不会因此自动满载。设平均一条轨迹有 $L$ 次模型调用，每次生成占用 GPU 时间 $t_g$，环境与工具等待为 $t_e$，sandbox 启动为 $t_s$。单条轨迹墙钟时间约为：

$$
T_{episode}=t_s+L(t_g+t_e).
$$

若并发 sandbox 数为 $N$，理想吞吐接近 $N/T_{episode}$；实际还受 Proxy 排队、推理动态批处理与长尾任务影响。假设 $t_s=20s$，$L=12$，$t_g=2s$，$t_e=8s$，单条轨迹约需 $140s$。100 个 sandbox 的理想吞吐约为每分钟 42.9 条。若环境等待翻倍，吞吐降到约每分钟 23.1 条，GPU 可能在两轮请求之间空转。

扩大 $N$ 也有上限。推理服务饱和后，排队时间进入 $t_g$；Kubernetes 启动大量 Pod 会争抢镜像、CPU 和网络；某些实时网站还会限流。工程上应同时观测 sandbox 启动 P50/P99、Proxy 队列深度、有效轨迹率、GPU token 吞吐和环境错误率。只有 GPU 利用率很高而有效轨迹率很低，意味着算力正在认真学习一堆坏 episode。

长尾决定训练同步点。若 trainer 等整批 rollout 全部返回，最慢的少数任务会阻塞更新；若提前截断，又会系统性丢掉复杂长任务。可以采用有界异步窗口：每个样本携带 `policy_version`，只接受落后不超过阈值的轨迹；超出阈值则重新采样或使用明确的 off-policy 修正。阈值越宽，硬件越忙，数据与当前策略的偏差也越大。

### Harness 选择与课程设计

论文显示 Codex、OpenClaw 一类复杂 Harness 更难学，RL 的相对增益又更明显。这提示课程不能只按任务难度排序，还要按 Harness 难度分层。一个任务在 ReAct* 下可能很简单，换到包含上下文管理、专用工具和多进程路由的 Harness 后，失败点已经变化。

训练初期可以让策略先学会稳定格式和基本工具闭环，再增加长轨迹、错误恢复与复杂 Harness；但不能长期停留在简化 loop，否则错位会被重新带回来。更可靠的课程单位是 `(task, harness, failure_mode)`：同一任务分别在工具缺失、响应超时、局部成功和验证失败下采样，明确观察策略能否把失败转成下一步动作。

error recovery 仍弱，也说明成功轨迹不够。终局奖励能强化顺利完成的行为，却很少告诉模型如何从半途故障回来。可以从真实失败 episode 截取「故障出现到恢复完成」的片段，构造带初始 checkpoint 的 recovery task；也可以让环境确定性注入超时、旧文件和工具返回畸形。验证仍以最终环境为准，不能奖励模型写出一段漂亮的反思。

多 Harness 课程还要防止表面迁移。策略可能只是记住多套工具别名，并没有学到共享能力。未见 Harness 评测应选接口、上下文策略和自动恢复机制都不同的系统，同时报告格式错误、工具选择、计划完成和错误恢复等细分行为。若只在工具名称相近的 Harness 上得分提升，泛化结论要收窄。

### Reward 管线的失败模式

Reward 从 verifier 到 trainer 之间还有一条数据管线。Reward 一旦绑定到错误 episode，训练会在没有报错、损失正常下降的表象下学习随机标签。`episode_id` 复用、超时回执晚到或任务重试覆盖旧记录，都可能让一个成功结果落到另一条轨迹上。

因此 reward 记录应同时绑定 episode、任务版本、初始 checkpoint、最终状态哈希和 verifier 版本。Trainer 消费前再检查这些字段，与轨迹 manifest 不一致的样本进入隔离队列。二元成功率之外，还要统计 `task_failure`、`timeout`、`environment_error`、`verifier_error` 与 `invalid_trace`，只有确实反映 policy 行为的结果才能参与优势计算。

判定器投机同样会在 RL 中被放大。只检查文件存在，策略会学会创建空文件；只检查页面出现某段文本，策略可能把文本写进无关区域。对每个 verifier，可以准备参考解、缺关键步骤的错误解和扰动解，验证它能区分三者。训练过程中还应抽样人工复核高奖励轨迹，尤其关注回报突然上升而外部质量没有同步改善的阶段。

过程奖励需要克制。若一条任务含五个检查，四个容易、一个决定成败，按通过比例给 reward 会鼓励策略反复收割容易项。更稳妥的方式是把过程信号用于课程采样与诊断，终局硬条件仍决定成功；确需 shaping 时，权重、上限和消融结果都应报告，使读者能判断增益来自完成任务，还是改变了评测目标。

### 从研究数字到部署决策

OpenForgeRL 的结果证明真实 Harness 可以进入开放训练栈，也显示数千任务已经能带来明显提升，但它没有替团队回答「该训练哪一个 Harness」。部署选择要看现有工具生态、权限模型、可观测性和维护成本。一个基准分稍高却无法稳定记录轨迹的 Harness，可能不适合持续训练；一个较简单但接口稳定、验证充分的 Harness，反而更容易形成数据飞轮。

部署前可以做四格实验：基座模型在旧/新 Harness 上各跑一次，训练后模型再在两种 Harness 上各跑一次。四个结果能够粗分模型增益、Harness 增益与二者交互。若训练后只在训练 Harness 上提高，说明适配性很强；若在未见 Harness 上也提高，才有较强证据支持共享 agentic skill。

成本也应按成功任务计算。设一次训练周期总成本为 $C_{train}$，评测或生产中每个 episode 成本为 $c$，成功率为 $p$，那么忽略重试差异时，每个成功任务的运行成本约为 $c/p$。训练价值来自 $p$ 的提高、$c$ 的下降，或者减少人工接管。若成功率提升很小而 rollout 成本翻倍，技术上有效，业务上仍可能不划算。

OpenForgeRL 把真实 Harness 纳入可记录、可训练、可比较的实验对象。模型、Harness、环境和 verifier 可以分别版本化，训练结果也由此能够追问：能力究竟长在 policy 里，还是来自部署栈替它做了更多工作。

### 一条训练样本的完整时间线

把系统拆开看，一条样本从任务入队到进入 loss，至少经过八个阶段：选择任务、启动 sandbox、加载 Harness、请求 policy、执行工具、终局验证、重建轨迹、训练消费。任何阶段失败，都不该笼统记成 reward 0。

```text
task@v3
  → sandbox(image@sha256)
  → harness@commit
  → proxy(policy@step-120)
  → environment actions
  → verifier@v7
  → trajectory manifest
  → trainer batch@121
```

假设 Harness 在第六次模型调用后超时，但环境里的目标已经完成。Orchestrator 记录的是 `harness_timeout`，verifier 却可能返回 success。是否把这条样本用于训练，要看终止语义：若生产系统允许超时后的外部验收，成功信号仍有意义；若产品要求 Harness 必须在预算内主动提交，超时就是失败。这个决定属于任务定义，不能由训练脚本临时猜。

再假设 verifier 成功，轨迹重建却发现第三次调用缺少工具返回。此时 reward 没问题，样本却不完整。把它送进 trainer 会让某个 action 缺少真实条件，应标为 `invalid_trace`。相反，轨迹完整而 verifier 服务宕机，动作数据仍可用于 SFT 或离线分析，却不适合直接生成 RL 优势。将阶段状态分开保存，才能让不同数据用途各取所需。

### 数据选择会改变学到的行为

只保留成功轨迹做 SFT，模型会看到大量顺利路径，却很少看到失败后的处理；把所有失败轨迹用于 RL，又可能混入环境故障和验证器错误。数据清理不能只按最终 reward 切一刀。

可以按转移片段标注四类行为：有效推进、无效探索、从失败恢复、产生不可逆错误。有效推进适合监督学习；恢复片段即使整条 episode 最终失败，也可能包含有价值动作；环境故障附近的片段通常需要剔除；不可逆错误则适合安全训练与动作门控。OpenForgeRL 观察到 RL 对 self-verification 和 tool coverage 有帮助，而 error recovery 仍弱，这也提示数据池需要主动寻找恢复片段。

任务采样还会影响成功率表象。若当前策略在简单任务上容易成功，在线采样会迅速积累这些任务的数据，随后进一步优化简单任务。困难任务因为持续得 0，既缺少正样本，也难产生可区分的组内优势。Balanced rollout 或基于成功率的课程可以提高临界难度任务的采样权重，但采样规则本身必须进入实验记录，否则最终成绩无法复算。

去重不能只看 prompt。两个任务的文字不同，底层仓库、隐藏测试或目标网站可能相同；反过来，同一句目标在不同初始状态下又可能是两道真正不同的题。任务指纹可组合文本嵌入、代码与资源哈希、验证器结构和初始状态摘要。评测集污染检查也沿用同一套多层指纹，而非只比标题。

### 版本矩阵与回归定位

一次实验至少涉及 policy、Harness、环境镜像、任务、Proxy 重建器和 verifier 六个版本。只记模型 checkpoint，几个月后很难解释同一权重为何复跑得到不同结果。可以把一次 run 的身份写成：

$$
\rho=(p,h,e,t,x,v),
$$

其中六个字母分别对应上述组件。成绩表中的每个数字都应能落到一组 $\rho$ 和逐任务结果。

当成功率下降时，版本矩阵可以做最小二分。先固定旧 policy，只升级 Harness；若下降复现，问题来自接口或控制流。再固定 Harness，只升级环境与 verifier；若结果变化，检查任务漂移。最后才比较新旧 policy。一次同时升级所有组件，只能得到「新系统变差了」，无法指导修复。

真实 Harness 往往快速迭代，训练数据也会跨版本。旧轨迹是否还能使用，取决于消息模板、工具 schema 与动作语义是否兼容。若只是增加无关日志，可继续使用；若工具参数或自动重试逻辑改变，旧轨迹代表的 policy 条件分布已经变化，应分桶训练或降权，而非全量混合。

### 安全边界进入训练环

远程 sandbox 限制了单条 rollout 的破坏范围，但训练会反复运行成千上万条轨迹，小概率事故会被放大。环境默认禁用宿主机挂载，网络访问使用 allowlist，凭证按任务发放短期 token，资源配额限制进程、磁盘与调用次数。Harness 的权限也应与生产目标一致；训练时给无限权限、部署时再收紧，依然是一种 train-deploy mismatch。

外部网站和 API 还涉及真实副作用。用于训练的环境最好提供镜像、模拟服务或专用测试账户。确需访问实时服务时，写操作进入隔离租户，并设置总预算与速率限制。Verifer 读取的凭证与 Agent 使用的凭证分离，防止 policy 直接修改验收数据。

训练日志可能包含仓库代码、页面内容和工具响应。Proxy 位于所有模型调用的汇合点，天然也是敏感数据的汇合点。记录前要按消息字段脱敏，原始 trace 设置访问与保留周期，发布数据集再做许可证和隐私检查。一个能训练真实 Harness 的系统，也更容易收集真实环境里的秘密，这部分不能留给上线前补救。

### 复现实验时应保存什么

论文数字要能复算，至少保存任务清单与版本、容器镜像摘要、Harness 启动参数、模型采样参数、每条轨迹的终止原因、verifier 输出和汇总脚本。模型训练还需记录 optimizer、batch、group size、KL/entropy 系数、最大 rollout 时间、有效样本数与 policy 版本推进规则。

只发布平均分不够。逐任务结果能够检查任务子集变化，失败类别能够区分 policy 与基础设施问题，长度分布能够发现超时带来的选择偏差。对于有随机性的 Agent，报告采样次数、pass@k 或 pass^k 的明确定义，并保留随机种子与原始 episode；否则相同的百分比可能对应完全不同的统计量。

OpenForgeRL 官方仓库已经公开核心 rollout engine、环境实现、veRL 示例与推理脚本，Kubernetes 编排依赖 Orchard Env。复现顺序宜从单任务单 sandbox 开始，确认 Proxy 能重建完整轨迹与 verifier 能复算结果，再扩到并发 rollout，最后接入参数更新。直接从大集群起跑，任何一个版本或路由错误都会被吞进海量日志里。

### 训练轨迹必须满足的约束

1. **Harness-native rollout**：训练轨迹必须来自真实 harness 控制流，非 reimplementation。
2. **Train–inference 解耦**：Proxy 是唯耦点；trainer 与 sandbox 可异构部署。
3. **Trajectory fidelity**：Proxy 记录的 io-pair 必须能重建 harness 实际看到的 state–action 序列。
4. **Environment portability**：换环境只改 sandbox 镜像；换 harness 只改启动命令与 Proxy 路由。
5. **Reward 仍 task-native**：ClawEval / OSWorld / WebVoyager 等官方 verifier，非 LLM judge。

### 把 Harness 写进受控决策过程

把 Agent 训练抽象成普通 MDP 时，人们常把状态写成 $s_t$、动作写成 $a_t$，再把工具执行理解为环境转移 $P(s_{t+1}\mid s_t,a_t)$。这对固定的 ReAct 循环勉强够用，对真实 Harness 却过于粗糙。模型并不直接接触环境状态，它看到的是 Harness 经过选择、排序、裁剪和格式化之后生成的消息；模型输出也不一定直接成为环境动作，还可能先经过语法解析、权限检查、参数补全、自动重试与路由。更贴近实际的分解是：

$$
x_t=O_H(z_t,m_t),\qquad
u_t\sim\pi_\theta(\cdot\mid x_t),\qquad
a_t=G_H(u_t,m_t),\qquad
z_{t+1}\sim P(\cdot\mid z_t,a_t),
$$

其中 $z_t$ 是外部环境的真实状态，$m_t$ 是 Harness 自己维护的记忆与控制状态，$O_H$ 决定模型看见什么，$G_H$ 把模型生成内容解释成可执行动作。工具返回之后，Harness 还会更新自己的状态：

$$
m_{t+1}=F_H(m_t,u_t,a_t,z_{t+1}).
$$

这组式子解释了为什么换 Harness 并非只换一段 system prompt。上下文压缩改变 $O_H$，工具参数修复改变 $G_H$，自动重试和子代理调度改变 $F_H$；三者都会改变策略实际面对的条件分布。即便底座权重、任务和外部环境完全相同，轨迹分布仍可能明显不同。

这里还有一层容易被忽略的部分可观测性。模型只看到 $x_t$，不知道 Kubernetes Pod 的剩余寿命、后台进程是否仍在运行、网页服务是否刚刚发生瞬时故障，也未必知道 Harness 已替它重试过几次。若这些隐藏变量会影响下一步结果，模型面对的其实是 POMDP。Harness 的历史整理机制承担了近似信念状态的角色：它把哪些失败、文件变化和工具结果保留下来，决定模型能否推断当前处境。压缩器若删除了「第一次写入失败但产生了半成品文件」这条信息，模型下一轮可能重复执行破坏性动作；保留全部原始日志又可能挤掉任务目标。所谓 Harness 能力，很大一部分正是在有限上下文中维护足够的信念状态。

因此，训练数据中的一条消息不能脱离产生它的控制状态来解释。相同的 `permission denied`，可能是模型首次越权，可能是 Harness 降权后重放旧命令，也可能是沙箱策略临时加载失败。三者对应的责任归因不同。Proxy 能保存模型真正看到的消息，却无法仅凭消息还原全部 $m_t$。若研究目标涉及自动重试、压缩、并行分支或审批门控，就要由 Harness 额外输出结构化控制事件，并让这些事件与 LLM 调用共享 episode 与父子调用标识。

两种接入模式由此有了明确差别。`DirectEnvInstanceConfig` 让训练引擎驱动外层循环，状态更新和 token mask 较容易掌握，代价是部署 Harness 的 $F_H$ 可能被简化。`PipelineEnvInstanceConfig` 让环境拥有整个黑盒 episode，能够保留真实控制流，代价是训练器只能通过记录与重建理解发生了什么。前者适合研究模型在规范工具循环里的学习规律，后者适合研究部署系统中的真实行为；把前者的结论直接外推到后者，需要额外的跨 Harness 验证。

### 从调用记录恢复条件概率

策略梯度依赖的是生成动作时的条件概率。若第 $t$ 次调用真正看到的输入为 $x_t$，采样 token 序列为 $u_t=(w_{t,1},\ldots,w_{t,L_t})$，行为策略给出的对数概率应为

$$
\log \mu(u_t\mid x_t)=\sum_{j=1}^{L_t}\log \mu(w_{t,j}\mid x_t,w_{t,<j}).
$$

轨迹重建不能拿 episode 结束后的完整历史重新拼一个 $\tilde x_t$ 再算概率。只要 $\tilde x_t\neq x_t$，训练器算出的便是另一个条件分布。压缩、动态 system prompt、时间戳、工具列表变化都会制造这种差异。最稳妥的做法是保存发给推理服务的规范化请求正文，并对其计算内容哈希；重放时先检查哈希和 tokenizer 版本，再重算 token 序列。请求中若含不可训练的模板 token，要同时保存损失掩码生成规则，而非依靠后来版本的 chat template 猜测。

工具调用还会带来边界问题。某些服务把工具调用编码成特殊 token，某些服务返回 JSON 文本，另一些服务把函数名与参数放进独立字段。若日志只保存可读文本，反序列化后可能丢掉模型实际采样的控制 token。训练器应以推理端返回的 token ids 或可无歧义复原它们的结构为准。特别是 JSON 被 Harness 自动修复时，应分别保存模型原始输出与执行版本；前者参与 policy loss，后者决定环境转移。把修复后的 JSON 当作模型动作训练，相当于让策略为一个从未生成的序列获得奖励。

一个具体例子能看出偏差。模型输出 `{"path":"a.txt" "content":"x"}`，缺少逗号；Harness 自动修复后成功写入文件，最终任务通过。环境层面的动作是成功写文件，策略层面的样本却包含格式错误。若直接给整段输出正优势，格式错误也被提高概率。可选处理有三种：保留奖励并期待其他失败样本抵消；把自动修复记作成本，在 reward 中扣除；或把该调用标成 Harness 介入样本，只训练修复前仍可明确归因的 token。三种方案优化目标不同，实验报告需要说明采用哪一种。

多进程 Harness 更复杂。设父调用 $c_0$ 创建两个并行分支 $c_1,c_2$，它们看到的历史并不相同，完成顺序也未必等于创建顺序。若按日志时间简单串接，会让 $c_2$ 看见实际只属于 $c_1$ 的观察，从而制造不存在的条件依赖。正确结构是一棵调用 DAG：节点保存输入、输出和本地顺序，边表示父子关系、消息继承或环境同步。只有共享状态经过明确同步之后，另一个分支才可把它纳入观察。对并行工具执行，也要区分「同时发出后统一汇总」和「先返回者立刻进入下一次推理」；两者诱导的策略完全不同。

可以给重建器设置四条不变量。第一，逐调用重放所得 token ids 与原记录一致。第二，每个被训练 token 都能追溯到唯一 policy 版本和一次真实采样。第三，所有环境观察均出现在产生它的动作之后，且没有跨分支偷看。第四，episode 的终止、reward 与最终状态哈希能够对齐。只要任一条失败，这条数据仍可用于系统排错，却不应悄悄进入在线策略更新。

### 策略滞后为什么会被长轨迹放大

解耦 rollout 与训练能提高吞吐，也会引入 policy lag。设轨迹由行为策略 $\mu=\pi_{\theta_{k-d}}$ 生成，训练时参数已经更新到 $\pi_{\theta_k}$。单个 token 的重要性比率为

$$
r_{t,j}=\frac{\pi_{\theta_k}(w_{t,j}\mid x_t,w_{t,<j})}
{\mu(w_{t,j}\mid x_t,w_{t,<j})}.
$$

若把整次调用看成一个动作，序列比率是所有 token 比率的乘积。即使每个 token 只偏离一点，长输出的乘积也可能迅速趋近零或变得极大。假设每个 token 在新策略下相对旧策略平均只有 $1.002$ 倍，一段 2000 token 输出的序列比率约为 $1.002^{2000}\approx54.5$；平均是 $0.998$ 时则约为 $0.018$。这正是长程 Agent 比短回答更怕策略滞后的原因：episode 更慢、策略版本落后更多，同时每条序列又更长。

PPO 类算法通常裁剪 token 或序列比率，但裁剪只能限制一次更新的幅度，不能把严重离策略的数据重新变成 on-policy 样本。大量 token 落到裁剪区间外时，有效梯度来自少数位置；若进一步按 episode 聚合，长轨迹还会因乘积退化失去作用。系统需要同时观测策略年龄、KL、比率裁剪比例和有效样本量。对带权样本，可用

$$
N_{\mathrm{eff}}=\frac{(\sum_i w_i)^2}{\sum_i w_i^2}
$$

衡量权重集中程度。收集了一万条 episode 并不意味着拥有一万条有效样本；若少数新轨迹占据绝大部分权重，$N_{\mathrm{eff}}$ 会远低于原始计数。

一个调度例子：集群每分钟启动 120 条 episode，平均完成时间 12 分钟，P95 为 35 分钟；训练器每 4 分钟推进一次 policy。平均样本完成时已落后约三个版本，尾部样本可能落后九个版本。若按完成顺序立即入队，短任务总是更接近当前策略，长任务总是更陈旧。最终训练器不只偏爱简单任务，还系统性低估长轨迹。把最大允许版本差设为两步会丢掉大量昂贵样本；放宽到十步又加剧离策略偏差。更合理的办法是按任务长度分桶设置窗口，减少更新频率或在一批 rollout 完成前冻结采样策略，并把被丢弃样本的计算成本纳入吞吐报告。

冻结策略也有代价。若等待所有长尾 episode 完成，GPU 可能空转，快速任务产生的新数据也无法及时利用。可以让多个固定版本的 rollout cohort 并行，每个 cohort 在自己的版本内完成组内比较，训练器消费完一组再释放对应推理副本。这牺牲部分显存与调度复杂度，换来清晰的行为策略归属。另一种做法是只让过旧轨迹进入 SFT、失败分析或 replay buffer，不用于要求近似 on-policy 的优势更新。数据并未浪费，只是换了与其统计性质相符的用途。

组相对算法还有额外约束。同一任务的 $G$ 条响应若来自不同 policy 版本，组均值不再只是同一条件下的相对难度基线，也混入版本能力差异。设旧策略成功率为 $0.2$，新策略为 $0.6$，组内各采两条；即使任务与采样参数相同，旧样本更容易得到负优势。更新会把「来自旧版本」误当成「动作较差」。因此，一个 reward group 应尽量共享任务版本、Harness 版本、初始状态、采样策略和采样参数。做不到时，至少要分层中心化或将跨版本样本剔出组比较。

### 判定器噪声怎样移动最优策略

任务原本有一个不可直接观测的真实成功变量 $y\in\{0,1\}$，verifier 给出的标签为 $\hat y$。记假阳性率为 $\alpha=P(\hat y=1\mid y=0)$，假阴性率为 $\beta=P(\hat y=0\mid y=1)$。对真实成功概率为 $p_\pi$ 的策略，观测成功率为

$$
\hat p_\pi=(1-\beta)p_\pi+\alpha(1-p_\pi)
=\alpha+(1-\alpha-\beta)p_\pi.
$$

如果 $\alpha,\beta$ 是固定常数且 $\alpha+\beta<1$，观测成功率仍与真实成功率单调对应，只是差距被压缩。然而 RL 会主动寻找 verifier 的薄弱点，错误率通常依赖策略产生的行为。策略学会创建一个空文件后，针对「文件存在」检查的假阳性率会上升；策略学会把目标文字放进隐藏节点后，基于页面文本的检查也可能失真。此时 $\alpha=\alpha(\pi)$，最大化 $\hat p_\pi$ 未必最大化 $p_\pi$。

考虑两个策略。策略 A 真正完成任务的概率为 $0.7$，几乎不会投机，假阳性率为 $0.02$、假阴性率为 $0.05$，观测成功率为 $0.02+0.93\times0.7=0.671$。策略 B 真正成功率只有 $0.4$，却能利用检查漏洞，使假阳性率达到 $0.5$、假阴性率为 $0.05$，观测成功率为 $0.5+0.45\times0.4=0.68$。训练会偏向 B，尽管它解决真实任务的能力更差。差距很小时，这种翻转不会在平均曲线上显得离谱，只有审查高奖励失败样本才能发现。

改进 verifier 不能只追求更多规则。多个检查若共享同一个错误假设，简单投票并不会消除偏差。比如文件存在、文件非空、文件含目标关键词三个检查都无法证明程序行为正确，它们只是对表面产物做了三次相关测量。更强的验证应尽量读取因果后果：执行隐藏测试、查询服务端状态、重新加载页面、从干净客户端验证权限，或在扰动输入上检查性质。对代码任务，示例测试确认基本接口，隐藏测试覆盖未见输入，变形测试检查输入变化后的关系；三者提供的是互补证据。

判定器还要抵抗状态污染。一次成功 rollout 留下数据库记录，下一次失败 rollout 可能借用旧记录通过验证；测试顺序固定时，早期步骤也可能替后续任务准备资源。验证协议应从已知初态启动，验证结束后销毁或恢复快照，并用状态哈希确认隔离。若恢复开销太高，至少随机打乱任务顺序，插入空白对照，观察无动作 Agent 是否也会获得奖励。无动作基线的通过率大于零，通常意味着初态、判定器或任务定义存在漏洞。

假阴性同样会扭曲学习。一个任务允许多种等价实现，而 verifier 只接受参考解的文件布局，正确的新方案会被惩罚。长期训练后，策略倾向模仿判定器偏好的表面形式，探索空间变窄。可以从失败样本中抽取环境终态，由独立测试或人工复核估计假阴性；也可以对输出做语义保持变换，例如重命名局部变量、调整无关布局、改变等价操作顺序，检查 reward 是否稳定。这里的目标在于让奖励对任务允许的等价类保持一致，同时继续拒绝缺少核心结果的方案。

训练期间需要版本化 verifier，因为修复漏洞会改变 reward 尺度。若 v1 误把空文件判成功，v2 加入内容检查，同一策略的成功率可能突然下降。把 v1 与 v2 数据直接放进一个组里做相对优势，等于把规则升级误认为策略退化。历史轨迹若保留完整终态，可以用 v2 重新评分；无法重放时就应分版本统计。模型 checkpoint、任务与 verifier 三者共同定义了一条可解释的学习曲线。

### 长程 credit assignment 的可用分解

终局奖励把整个 episode 压成一个比特，优点是目标干净，缺点是无法指出哪一步促成成功。直接给全部生成 token 同一个优势，相当于假设所有动作贡献相同。对一条包含探索、误操作、恢复和最终修复的轨迹，这个假设显然很粗。更细的分解需要借助环境状态，却不能把容易投机的过程指标冒充最终目标。

一种做法是定义势函数 $\Phi(s)$，用势差构造 shaping：

$$
r'_t=r_t+\gamma\Phi(s_{t+1})-\Phi(s_t).
$$

在理想 MDP 和正确势函数下，这类 shaping 不改变最优策略，只改变学习信号的密度。真实 Agent 环境中，$s_t$ 部分不可观测，$\Phi$ 往往由测试通过数、资源存在性或页面状态近似，理论保证随之减弱。若测试之间有前置关系，单纯用通过比例作为势函数还可能不单调：修复核心接口时暂时破坏一个表面测试，长期更接近目标，短期势值却下降。

另一种做法是事后找关键转折。将轨迹在第 $t$ 步的环境快照复制出来，从该点采样多个续写，估计

$$
Q(s_t,a_t)\approx\frac{1}{K}\sum_{k=1}^K R(\tau_{t:}^{(k)}).
$$

再与替代动作或状态基线比较，可判断某一步是否显著改变成功概率。它比语言模型对步骤打分更接近任务事实，代价是需要可快照环境和大量分支 rollout。对昂贵 GUI 或真实网站，完整反事实采样可能不可承受，可以只在失败聚集的少数节点执行。OpenForge 的远程沙箱与版本化环境为这种研究提供了基础，但仓库公开能力并不等于论文已经完成了全部反事实归因实验。

还可以按可逆性划分动作。读取、搜索和列目录通常不改变外部状态；写文件、提交表单、删除资源会改变状态；发布、付款或外部消息可能不可逆。对于只读探索，失败后的代价主要是 token 与时间；对于不可逆动作，错误会直接封死后续路径。课程设计可以先训练模型在高不确定性时使用只读观测，证据充分后再执行写操作。这并非奖励「思考得多」，而是把动作风险写进成本：

$$
R'(\tau)=R(\tau)-\lambda_c C_{compute}(\tau)-\lambda_r C_{risk}(\tau).
$$

两个系数必须与应用目标对应。若 $\lambda_c$ 太大，策略会跳过必要检查；若 $\lambda_r$ 太大，策略会拒绝任何可能失败的操作。报告 pass rate 时同时给工具步数、耗时、不可逆动作数和人为接管率，才能看出性能提升是否靠更高代价换来。

错误恢复可以拆成「发现—诊断—回滚—改道」四个能力。模型先要发现结果与预期不符，再根据观察区分参数错误、权限错误、环境故障和方案错误；随后恢复到可继续的状态，最后选择新动作。只在顺利成功轨迹上训练，四步都很少出现。构造 recovery task 时，应从真实失败快照开始，保留足以诊断的日志，并让 verifier 检查最终任务和状态完整性。若只奖励输出一段错误分析，模型学到的是解释失败；若重置成全新任务，模型学到的是重新开始。真正的恢复要求它处理已经被部分修改的世界。

### 容量、吞吐与有效学习量

远程沙箱训练的瓶颈常在 CPU、启动和外部工具等待，而非生成 token。设集群最多运行 $N$ 个 Pod，单条 episode 平均占用时间为 $T_e$，可用率为 $u$，粗略完成率为

$$
q=\frac{Nu}{T_e}.
$$

若 $N=600$、$u=0.8$、$T_e=15$ 分钟，每小时约完成 $600\times0.8\times60/15=1920$ 条。假设环境故障率 8%、轨迹重建失败率 4%、策略版本过旧丢弃率 10%，三类近似独立，则可用于目标更新的比例约为

$$
(1-0.08)(1-0.04)(1-0.10)=0.795,
$$

每小时有效轨迹约 1526 条。若每个任务组成 8 条响应的一组，最多形成约 190 个完整组。只报告 1920 条 rollout，会高估真正进入优势计算的数据量约四分之一。

启动时间也会改变最优调度。假设容器冷启动 90 秒，实际交互 6 分钟，销毁与验证 30 秒，单条总时长 8 分钟，启动与收尾占四分之一。复用 Pod 能提高吞吐，却带来状态泄漏；每条都冷启隔离最强，成本更高。折中方案是在同一不可变镜像上复用节点缓存，不复用任务文件系统和服务状态；或者一个 Pod 顺序运行多个任务，但每次恢复经过校验的快照。无论采用哪种方式，都要用无动作验证与状态哈希证明隔离，而不是把「容器还在」等同于「状态干净」。

批量调度还存在 head-of-line blocking。若一个 batch 必须等最慢 episode 才能更新，少数卡死任务会拖住全部样本；若先到先训练，短任务又得到更多更新机会。可以为 episode 设置软截止时间和硬截止时间：软截止后允许已完成样本组成同质小组，硬截止后终止并按原因分类。任务采样器按单位墙钟时间的有效信息量分配预算，同时给困难任务保留最低配额，避免系统只追求吞吐而把长程能力训练掉。

有效学习量还取决于组内差异。若同一任务的八条 rollout 全部成功或全部失败，简单中心化优势接近零，这组样本几乎不提供相对排序信号。成功率接近中间区域的任务更有信息，但只采这类任务会改变目标分布。可以把训练采样分布 $q(x)$ 与目标任务分布 $p(x)$ 分开：训练时增加临界任务比例，评测仍按 $p(x)$；需要估计总体目标时再用分层统计或重要性加权。任务难度随策略更新而变化，课程调度器应根据滑动窗口更新，且保留固定锚点任务监控遗忘。

### 能证明什么，暂时不能证明什么

OpenForgeRL 最有价值的证据，是同一类真实部署 Harness 可以被接入记录代理、远程沙箱和 RL 训练器，训练后在 Claw、GUI 等任务上获得可测提升。论文还比较了 Harness 对可学习性的影响，并观察到自检、工具覆盖和多步完成改善，而错误恢复仍弱。这些结果支持「Harness 应进入训练分布」这一研究方向，也支持把环境、Harness 与 policy 分别版本化。

它并不能单独证明任何真实 Harness 上训练都会提升，也不能证明跨 Harness 迁移必然发生。任务合成、底座模型、判定器质量和采样预算都会改变结论。某个 Harness 训练后得分较高，可能因为它提供更清楚的工具反馈，也可能因为任务生成过程更贴近它的动作空间。要区分两者，需要交换 Harness、固定任务与预算，并对未见接口做测试。

公开仓库还明确提示项目正在重组和调试，部分路径、checkpoint 与任务尚未公开。因而当前读者可以核查核心架构、环境接入和示例训练流程，却未必能从头重现论文全部数字。严谨的复现记录应把「代码能够运行」「公开任务上得到趋势」「复算论文主表」分成三个层级。第一层验证接口，第二层验证机制，第三层才验证完整经验结论；前两层成功不能自动宣称第三层完成。

此外，论文报告的 pass@3、pass^3 与单次通过率含义不同。若三次采样独立且单次成功率为 $p$，至少一次成功的理想值为 $1-(1-p)^3$，三次全成功为 $p^3$。真实 Agent 的多次采样共享任务、环境和系统故障，独立假设往往不成立。一个不稳定 verifier 可能让三次结果同时错误，一个任务镜像损坏会让三次全部失败。报告这些指标时应给出实际逐任务聚合定义，保留同一任务的联合结果，不能只用独立公式从平均单次成功率反推。

最终，OpenForge-RL 提供的是一套把部署控制流纳入训练的实验方法。它要求研究者承认模型看到的世界由 Harness 塑造，奖励由 verifier 塑造，能够进入优化器的数据又由调度与重建管线塑造。只有把这三层同时记录下来，提升才可以被解释为策略学习；缺少任何一层，漂亮的曲线都可能来自接口便利、判定漏洞或样本筛选。

### 任务合成是一道分布设计题

OpenForgeRL 的任务流水线可以概括成 propose、prune、build、test、refine。五个动词看起来像数据生产步骤，真正决定训练行为的是它们共同定义了什么样的任务能够留下。提议器从种子、领域描述或现有环境中生成目标；裁剪器删除重复、不可验证或过于简单的题；构建器准备镜像、初态、mock service 与验证代码；测试阶段让参考方案和故意破坏的方案通过同一判定器；修订阶段处理无法启动、答案泄漏和判定歧义。最终进入训练池的并非「所有有用任务」，而是被这条流水线筛中的条件分布。

设自然任务分布为 $p_{real}(x)$，提议器产生 $q_0(x)$，第 $j$ 个筛选步骤以概率 $a_j(x)$ 接受任务，最终训练分布满足

$$
q_{train}(x)\propto q_0(x)\prod_j a_j(x).
$$

某类任务若很难自动验证，它的 $a_{test}(x)$ 就低；若需要昂贵外部服务，它的 $a_{build}(x)$ 也低。即便提议器覆盖了它，最终训练池仍会系统性缺失。于是可验证性从质量门槛变成了隐含课程：文件修改、结构化 API 和确定性网页状态容易留下，开放式研究、长期沟通与依赖现实反馈的任务容易消失。模型在合成池中进步，首先说明它适应了这个可构建、可重置、可验证的子空间。

裁剪重复项也不能只靠文本相似度。两条指令分别写「修好分页」和「列表第二页不显示，请处理」，底层仓库、失败测试和修复路径可能完全相同；两条文字完全相同的指令若初始数据库、权限或依赖版本不同，又可能要求不同策略。任务身份应至少由目标语义、初始状态摘要、环境资产、隐藏验证结构和允许动作共同决定。训练集与评测集去重时，也要沿这些维度检查。只对 prompt 做 embedding 去重，会把改写泄漏留在数据中。

参考方案能证明任务至少存在一条已知可行路径，不能证明判定器覆盖全部正确路径，也不能证明普通策略在预算内可达。参考方案若拥有额外权限、预知隐藏测试或绕过 Harness，任务对模型可能仍不可解。合成阶段应让参考方案使用与待训 Agent 相同的工具、权限和时间限制，并保存逐步轨迹；随后从干净快照复跑，确认成功不依赖构建过程残留。

为了测试 verifier，可以构造三类负例。第一类删除参考方案的关键动作，验证缺失核心条件时确实失败。第二类只制造表面产物，例如创建同名空文件、在页面不可见区域写目标文本，检查是否会误判。第三类保留语义结果但改变实现形式，检查判定器是否错误拒绝等价解。这三类分别探测漏检、投机和过拟合参考答案。测试通过后仍需在训练过程中抽样审计，因为策略会发现人工负例没有覆盖的新路径。

任务难度也不能用参考轨迹长度单独衡量。短轨迹可能需要一次非常精确的不可逆选择，长轨迹可能只是机械浏览。更可用的难度描述包含基础策略成功率、成功轨迹长度分布、失败模式熵、可恢复错误比例和动作分支度。若八次采样有四次成功，组相对更新容易得到正负信号；若始终为零，它可能太难、环境可能损坏，也可能 verifier 过严。这三种情况只有通过参考方案、环境健康检查和失败分类才能分开。

合成任务还容易继承生成模型的语言习惯。目标描述过度完整、验收条件全写在 prompt 中、每个歧义都被提前消除，会训练出依赖「教科书式任务」的策略。真实请求常含省略、错误术语和逐轮补充。可以在保持隐藏目标不变的前提下生成不同信息条件：完整规格、缺少次要细节、带一处可澄清歧义、含无关背景。评测时分别观察策略会不会检查环境、提出必要问题或根据证据消解歧义。扰动不能改变任务本身，否则比较的已是两道题。

### Harness 可学习性从哪里来

一个 Harness 让基础模型得分更高，可能因为它替模型做了更多工作；让 RL 增益更高，则可能因为它给出了更稳定的学习接口。这两个维度需要分开。可以把 Harness 的贡献粗分为四项：观察质量、动作可表达性、控制流援助和错误反馈。观察质量决定关键信息能否进入上下文；动作可表达性决定模型能否用有限步骤完成目标；控制流援助包括自动规划、重试、压缩和并行；错误反馈决定失败后是否有可辨别的下一步。

假设 Harness A 为基础模型提供强自动重试，初始成功率从 30% 提到 50%，但所有失败最后都被压成同一句「执行失败」；Harness B 不自动重试，初始成功率只有 35%，却返回稳定的错误码、失败动作和状态差异。RL 后 A 可能到 55%，B 可能到 60%。A 的部署援助更强，B 的可学习性更好。只比较训练后的绝对分数会说 B 略强，只比较 RL 增量又会忽略 A 的高起点。完整结果至少要同时报告 base、post-RL、绝对增益和单位训练成本。

可以用二维交换实验寻找因果来源。固定 policy 和任务，把 A 的观察格式配给 B 的动作执行器，再把 B 的反馈格式配给 A；若改善随观察格式移动，关键因素在 $O_H$，若随执行器移动，关键因素在 $G_H$ 或转移规则。现实中组件未必可直接互换，但可以用适配层统一工具语义，逐项消融压缩、重试、错误回传和工具描述。每次只改变一个机制，比把两个完整产品端到端对打更能解释结果。

工具 schema 是可学习性的典型来源。一个参数同时接收字符串、列表和隐式默认值，看似灵活，实际让模型面对多种等价表示；严格 schema 会在执行前拒绝错误，减少环境污染，也可能让小格式错误阻断本来正确的意图。训练中应分别统计语义选择错误与参数编码错误。若 RL 提升主要来自 JSON 合法率，说明模型学会了接口；若工具选择和最终状态也改善，才说明规划能力同时增长。

上下文压缩决定长轨迹中的记忆通道。可把完整历史 $h_t$ 经过压缩器 $C_H$ 得到 $x_t=C_H(h_t)$。理想压缩保留对后续最优动作充分的统计量，但任务未知时很难做到。一个实用测试是反事实删除：从成功轨迹中删除压缩摘要里的某条事实，观察后续动作分布和成功率变化；也可以把关键事实以不同表述重复注入，检查模型是否真正使用它。若压缩器总把失败尝试删掉，模型会反复走旧路；若把每个错误都保留，目标和当前状态又会被噪声淹没。

自动重试同样有双刃剑。瞬时网络故障适合透明重试，权限不足、参数无效和资源不存在则需要模型改变方案。Harness 若对所有错误统一重试，会消耗预算并隐藏诊断信息；完全不重试又把随机基础设施噪声交给策略。可以根据错误的条件独立性决定：若再次执行在状态不变时有合理成功概率，允许有界重试；若失败由动作内容决定，立刻返回结构化原因。训练日志要保留每次自动重试，否则模型成功看起来会比它真实贡献的更大。

多 Harness 联合训练的目标也不应被理解成简单数据相加。设共享语义技能参数为 $\theta_s$，接口适配行为为 $\theta_h$。不同 Harness 的梯度可能在共享能力上同向，在格式行为上冲突。可以测量同一 batch 上的梯度余弦：正值表示局部协同，负值表示竞争。即使不直接修改优化器，这个诊断也能告诉研究者冲突来自哪些工具和任务。若冲突集中在调用格式，可以通过统一中间表示或少量 Harness 标记缓解；若冲突来自互斥的安全策略，就不该强行抹平。

### 由 episode 到更新的统计口径

Agent 评测常同时出现 pass@k 与 pass^k。前者关心 $k$ 次中至少一次成功，适合用户允许重试或从多个候选选最优的场景；后者关心多次均成功，强调稳定性。设同一任务第 $i$ 次采样结果为 $Y_i$，逐任务统计量分别是

$$
\mathrm{pass@}k=\mathbb{1}\left[\max_iY_i=1\right],\qquad
\mathrm{pass^}k=\mathbb{1}\left[\min_iY_i=1\right].
$$

它们应先在任务内聚合，再对任务取平均。把所有 rollout 混在一起算总体成功率，再代入独立公式，会忽略任务难度差异与同一环境故障造成的相关性。若一半任务成功率接近一、一半接近零，总体单次通过率可能是 50%，实际 pass@3 仍接近 50%，远低于独立同分布假设给出的 87.5%。

训练组内的奖励归一化也受任务难度影响。对同一任务采样 $G$ 次，二元奖励均值为 $\bar r$，中心化优势 $A_i=r_i-\bar r$。当 $\bar r=0$ 或 $1$ 时整组优势为零；当 $\bar r=0.5$ 时信号最大。若调度器优先采中等难度任务，更新效率提高，却会削弱极难任务的覆盖。可以为零成功组提供其他可验证信息，例如正确的中间状态或恢复片段，但不能随意给「看起来努力」的文本奖励。也可以用略强模型生成少量成功轨迹，把任务推入可学习区，再让当前策略继续探索。

长度归一化需要谨慎。token 级损失若对所有 token 平均，长回答每个 token 的单独权重变小；按序列求和，长回答又会产生更大梯度。Agent 的一次决策可能是一行工具调用，也可能是一段长代码，单纯按 token 对齐未必符合动作语义。可以分别报告 token-normalized 与 action-normalized 更新，或给每次模型调用相同总权重，再在调用内部平均。选择哪种方案取决于希望优化「生成每个 token 的质量」还是「每个决策点的质量」。

多任务聚合不能让大任务族淹没小任务族。若代码任务有一万条、GUI 任务一千条，按 episode 微平均会主要反映代码能力；按领域宏平均又让很小的领域获得同等权重。训练分布、评测分布和产品流量可以采用不同权重，但三者要分别公开。OpenForgeClaw、OpenForgeGUI 的分数属于不同环境与判定协议，不能直接平均成一个模糊的「Agent 能力」。

置信区间也应按任务层级计算。同一任务的多次 rollout 共享初态和 verifier，不能当作完全独立样本。可以对任务做 bootstrap，每次抽取任务并保留其全部重复采样，再计算 pass@k、pass^k 和成本指标。比较两个策略时，尽量使用相同任务与种子做配对差异，降低任务难度方差。对于环境错误率较高的系统，还要同时给原始结果与剔除基础设施故障后的条件结果；前者代表用户体验，后者更接近 policy 能力。

### 从一次失败追到可检验假设

失败分析若止于「规划错误」「工具错误」，很难指导下一轮实验。更有效的做法是沿因果链定位最早偏离点。先问模型看到的观察是否充分，再问它生成的意图是否合理、序列化是否正确、Harness 是否按意图执行、环境是否返回真实结果、压缩是否保留结果、verifier 是否正确评价。最早出现异常的环节通常是修复对象，后续错误可能只是连锁反应。

例如 Agent 删除了错误文件。回放显示模型明确写出了正确路径，执行日志却解析成相对路径，问题在 $G_H$；若模型看到的目录清单已缺少根目录信息，问题在 $O_H$；若观察完整而模型仍选错，才是 policy 决策错误。把三类都标成「工具使用失败」会错误地用 RL 修复解析器 bug，或用工程补丁掩盖模型能力缺口。

每个故障假设都应带一个最小反事实实验。怀疑上下文压缩丢事实，就固定 policy，只替换为完整历史；怀疑工具描述含糊，就保持执行器不变，改写 schema；怀疑 verifier 漏洞，就让人工确认的失败终态单独过验证；怀疑 policy lag，就按版本年龄分桶比较收益和 KL。若反事实没有改变结果，假设就应降级，而非继续堆解释。

长程任务还要观察「失败发生在何时」。早期失败通常与任务理解和初始化有关，中期失败常来自状态追踪、工具选择与局部实现，末期失败更多出现在验证、清理和提交。把 episode 按语义阶段对齐，比按固定 token 区间切分更有意义。若训练后早期错误减少、末期错误增加，整体成功率可能不变，但模型已经把瓶颈推向了最后验收；下一轮数据应加强自检与交付，而非继续增加开局规划样本。

恢复失败也需要区分「没有发现」「发现但诊断错」「诊断对但没有可逆路径」「有路径却未执行」。第一类需要更可靠的结果检查，第二类需要结构化错误与对照经验，第三类涉及环境设计和 checkpoint，第四类才主要是策略选择。OpenForgeRL 报告 error recovery 仍弱，最有价值的后续工作便是把这个总指标拆开，否则新增数据只能盲目增加失败轨迹。

### 训练与部署共同定义能力上限

策略最终能做到什么，受模型、Harness 和环境三者的交集限制。模型不会使用某个工具时，增加权限没有意义；Harness 不暴露某个动作时，再强的模型也无法执行；环境不给可观察反馈时，模型只能猜测结果。可以把可达成功集合写成

$$
\mathcal S_{success}=\mathcal S_\pi\cap\mathcal S_H\cap\mathcal S_E,
$$

其中三项分别表示策略可生成、Harness 可表达与环境允许的轨迹。训练只直接扩大 $\mathcal S_\pi$。更换 Harness 会改变 $\mathcal S_H$，开放工具或修复环境会改变 $\mathcal S_E$。若任务所需轨迹根本不在后两者交集中，继续 RL 只会让策略更熟练地撞墙。

这也是为什么失败样本要保留「不可解」类别。初态缺文件、凭证无权限、目标服务离线、判定条件互相矛盾，都不该作为普通负奖励反复训练。可解性检查需要在任务生成时运行，在 rollout 时仍要复核，因为外部依赖会漂移。不可解比例上升时，训练 loss 可能看似稳定，优势估计却被大量无关零奖励污染。

反过来，Harness 也不能替策略完成太多再把成绩归给模型。若自动规划器生成全部步骤，模型只负责填少量参数；若错误修复器能够重写调用；若 verifier 结果直接泄露缺失条件，成功率会提高，policy 的长程能力却未必增长。一个简单审计方法是记录由模型、Harness 和环境分别产生的状态改变，并做能力剥离：关闭自动修复、限制重试、隐藏额外提示，再观察训练后策略保留多少收益。

部署选择最终取决于端到端系统，而非追求「纯模型」成绩。只要贡献归因清楚，强 Harness 帮模型完成任务完全合理。研究训练规律时则必须知道提升来自哪里，否则换一个控制流后收益会消失。OpenForgeRL 的意义正在于把原本藏在产品外壳里的控制变量搬进实验对象，让部署能力与策略学习可以在同一条轨迹上被审计。

### 一组能拆开机制的消融

端到端分数只回答整套系统有没有用，无法判断 Proxy、真实 Harness、任务合成和 RL 各自贡献多少。最小对照可以从同一底座、同一任务池出发，构造四个训练条件：简化 ReAct 采样并在简化循环评测；简化 ReAct 采样后放进真实 Harness 评测；真实 Harness 采样但只做行为克隆；真实 Harness 采样并做 RL。第一、二项之间的下降估计 train-deploy mismatch，第二、四项之间的变化混合了真实轨迹与 RL，第三、四项则更接近奖励优化相对模仿学习的增益。

还需要一个「真实 Harness、随机或冻结 Proxy」对照，确认提升不来自记录层无意改变请求。代理可能重排 header、修改流式响应、改变超时或丢掉 provider 特有字段；这些细节足以影响工具调用。做旁路测试时，让同一组请求分别直连推理服务和经过 Proxy，比较 token、finish reason、工具字段与延迟分布。确定性解码应逐 token 一致，随机采样至少应在相同参数与种子支持下复现，做不到时就报告代理引入的差异。

任务合成消融要固定训练 token，而非只固定任务数。一千条超长 GUI 任务和一千条短 shell 任务消耗不同；若新流水线生成更短的题，相同任务数下能完成更多更新。可以分别固定 episode 数、模型生成 token 和墙钟预算，三种口径回答不同问题：数据覆盖、优化预算与现实成本。若提升只在固定 episode 数下出现，换成固定 token 后消失，收益可能主要来自每条样本更便宜。

判定器消融可准备严格版与宽松版。严格版要求全部隐藏条件，假阳性低但可能拒绝等价解；宽松版覆盖更多实现，假阴性低但留下投机空间。用两版分别训练并交叉评测，能观察策略是否贴着特定规则生长。若在自身 verifier 上提升、换 verifier 后明显下降，说明 reward-specific overfitting 较强。最终还应抽取双方分歧样本人工复核，因为两个自动判定器可能共享盲区。

Harness 泛化要同时测试「新皮肤」和「新机制」。仅重命名工具、改 JSON 字段属于接口扰动；改变上下文压缩、自动重试和多代理调度才是控制流变化。前者测格式适配，后者测策略能否在不同状态转移下工作。若论文只报告工具名变化后的迁移，不能据此推出对全新控制流也有效。反过来，在机制完全不同的 Harness 上下降，也不代表训练失败，它说明共享能力与接口特化的边界在哪里。

### 安全约束也是策略条件

远程沙箱把单次事故限制在容器内，却没有自动消除网络、凭证和供应链风险。Agent 可以下载依赖、访问网页、调用外部 API；训练会把偶然成功的路径提高概率。如果某条成功轨迹碰巧使用了越权凭证或未锁定脚本，正奖励会把危险行为当成有效策略。环境权限必须在采样前按任务最小化，不能指望 reward 在事后把所有越界动作扣回去。

权限门控会进入模型的观察与动作分布。训练时允许直接执行删除，部署时要求用户确认，策略在确认前后的状态转换上没有经验；训练时完全禁止删除，部署时偶尔授权，模型又不会利用新能力。可以把审批写成显式工具结果：请求、拒绝、批准各有稳定结构，并在任务中覆盖三种分支。这样策略学到的是如何在权限约束下推进，而非把审批视为随机报错。

凭证应由环境按 episode 注入短期、限域 token，Proxy 日志默认脱敏。仅用正则替换字符串不够，密钥可能出现在 URL、命令输出、网页或模型复述里；应在字段生成处标注敏感等级，并在存储层控制访问。脱敏后的轨迹用于训练时还要保持语义，例如把真实值统一替换成可调用的占位符，否则模型看到的参数与执行参数不同，又制造一次重建失真。

网络 allowlist 也会改变任务可解性。依赖包下载、登录跳转和第三方资源可能访问多个域名；简单封死会让本可解任务变成基础设施失败，完全开放则允许数据外传。构建阶段应记录参考轨迹实际访问的域、请求方法和内容类别，再生成最小网络策略。训练时出现新域名请求要进入审计队列，而非自动放行或一概惩罚模型。

不可逆动作要有独立预算。发送消息、发布内容、触发付费和修改共享资源，即使在测试账号中也可能产生外部影响。模拟服务能覆盖大多数训练，少量真实端到端测试则放在受控租户并设置总量上限。奖励设计中可以把成功与安全分成硬约束：违反禁止动作的 episode 直接隔离，不参与普通组内归一化，避免同组均值让严重违规只得到一个温和负优势。

### 复现结论的证据梯度

读者首先能从论文和公开仓库确认架构意图：OpenAI-compatible recording proxy 位于 Harness 与推理服务之间，Orchard 管理隔离环境，轨迹重建后交给 veRL 等训练栈。其次可以运行公开示例，确认一次真实 Harness 调用能被记录、验证与转换。再往上是复现一轮小规模更新，看 reward、KL 和行为是否按预期变化。最高层才是使用相同任务、checkpoint、预算和评测协议复算论文主结果。

这四层需要不同证据。看懂代码不能替代运行记录；跑通一个样例不能证明梯度正确；小规模曲线同向不能替代主表数字。仓库仍在整理且部分训练资源未公开时，合理结论可以停在前两层或第三层，并把缺失的任务、权重、镜像与版本列清楚。这样做没有削弱项目价值，反而避免把「机制可核查」写成「所有结果已完整复现」。

源码与论文口径发生差异时，应优先记录具体 commit 和运行行为。README 可能描述最新接口，论文对应较早版本；脚本默认参数也可能在发布后改变。最可靠的实验身份包含论文版本、仓库 commit、容器 digest、依赖锁、任务 manifest 与模型 checkpoint。若无法得到论文对应 commit，就在当前版本上重新建立基线，避免把新代码跑出的数字直接与旧表横比。

外部服务会让完全复现失效，但仍可追求可审计。保存响应摘要、状态码、时间、区域和服务版本，给动态网页保留允许范围内的快照；无法发布的凭证与数据至少给出生成规则和统计。研究者应能区分模型失败、Harness 失败、服务漂移与验证失败。只要分类清楚，即使某个在线任务几年后无法重跑，原结论的证据链仍可被检查。

对这类系统论文，版本化轨迹样本与 checkpoint 同样关键。它能让读者检查模型实际看见什么、Harness 做了哪些自动动作、环境如何变化、reward 如何绑定。权重说明最终学到了什么，轨迹说明为什么可能学到；二者加上可重建环境，才构成完整证据。若只能保留一小部分轨迹，应按任务、结果、长度、Harness 和失败类别分层抽样，避免公开样本全是最短的成功案例。失败与异常样本虽然不漂亮，却最能暴露系统边界，也能让后来者核查数据清理有没有把困难样本悄悄排除。

这种证据也方便复算。

### 与环境层和部署层的关系

| 系统 | Harness 真实性 | 训练栈 | 与 OpenForge RL |
|---|---|---|---|
| 典型 open RL（R2E-Gym 等） | 简化 ReAct loop | 紧耦合 | 高 mismatch 风险 |
| Orchard-SWE/GUI/Claw | Orchard Env + 固定 harness | slime fork | 同 Env，OpenForge 换真实 harness |
| LongHorizon-Harness | 部署期 MEA 审计 | 无训练 | 推理期互补：LH 管状态，OpenForge 管 policy |
| OpenWebRL | Orchard Env + live browser | 在线 RL | GUI 域姊妹工作；OpenForge-GUI 用真实 CU harness |
| veRL 原生 agent | 通常单进程 chat | veRL | OpenForge 把 veRL 接到外部 harness |

### 可复用的训练接口

1. **Proxy-as-Adapter**：任何无法改源码的 closed/complex harness，都可用「LLM 调用代理 + 轨迹重建」接入 RL——前提是 intercept 面完整。
2. **Remote Sandbox Rollout**：训练吞吐 = sandbox 并发 × episode 长度；Env 层必须 hot-path 低延迟（Orchard Env ~0.28s/exec）。
3. **Multi-Harness Training**：联合训练多种 harness → 对未见 harness 泛化；部署时可换更强 harness 获得 **free lunch**（Orchard-Claw +9.3 pass³ on ZeroClaw）。
4. **RL 增益分解**：format / verification / tool coverage 可 RL 学；error recovery 需另建数据或架构——指导 reward 与 curriculum 设计。
5. **Train where you deploy**：long-horizon agent 训练的默认原则应是「policy 与 harness 共演化」，而非「先训裸模型再贴 harness」。

6. **Trajectory reconstruction contract**：Proxy 与 trainer 之间应版本化 `(message_list, tool_call, logits_mask)` schema——harness 升级时重建逻辑可回归测试，避免 silent corruption。

7. **Rollout–train decoupling SLA**：Orchestrator 队列深度、sandbox 启动 P99、Proxy 超时策略应作为训练 infra 的一等监控项；否则 GPU 空转会吞噬 RL 预算。

**落地检查清单（研究/工程）**：

- [ ] 目标 harness 的全部 LLM 调用是否经统一 HTTP/API 出口（可插 Proxy）？
- [ ] Sandbox 镜像是否预装与生产一致的 MCP / 工具版本？
- [ ] Reward 是否来自 task-native verifier（而非 rollout 内的 harness 自评）？
- [ ] 是否至少用两种 harness 做 cross-deployment 泛化测试？
- [ ] RL 后是否单独测 error recovery 子集（OpenForge 显示此处 RL 无效）？

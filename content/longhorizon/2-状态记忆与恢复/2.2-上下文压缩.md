# Long-Horizon 上下文管理论文合集(2026 年中 7 篇)

2026 年 5—7 月的一批 Long-Horizon Agent 工作分别处理训练、服务、状态表示和检索。压缩后的文本长度只是表象，真正影响任务的是状态保真度、恢复能力和运行成本。

## 1. 训练式上下文管理

上下文压缩已经分出几条机制不同的路线：训练模型决定何时压缩、优化并行 serving，以及直接学习与 Agent 行为兼容的状态表示。

四项工作的差别集中在压缩对象、训练信号和压缩后的继续执行方式上。

**CompactionRL: Reinforcement Learning with Context Compaction for Long-Horizon Agents**

[CompactionRL](https://arxiv.org/abs/2607.05378)把压缩决策放进策略学习，而不是把摘要器当作固定预处理器。

它用任务终局信号同时训练执行与摘要，使压缩前的决策仍能从压缩后的结果获得信用。

- 机构: 清华大学(Yujiang Li, Zhenyu Hou, Yi Jing, Jie Tang, Yuxiao Dong), 2026.07.
- **动机**: 长程轨迹容易超出上下文窗口, 传统压缩通常独立于 Agent 训练, 摘要质量与任务目标并不一致.
- **方法**: 将任务执行与上下文摘要纳入同一 RL 轨迹, 通过 token-level loss normalization 和跨轨迹 GAE 联合学习行动, 压缩及压缩后的继续推理.

**Parallel Context Compaction for Long-Horizon LLM Agent Serving**

[Parallel Context Compaction](https://arxiv.org/abs/2605.23296)把 serving 路径中的停顿和吞吐列为主要评测对象，摘要文本质量只是其中一项。

并行分块让输出体积更可控，同时引入跨块关系可能被切断的风险，需与顺序基线共同评测。

- 时间: 2026.05.
- **动机**: 单次全局摘要会阻塞 Agent 推理, 延迟高且摘要长度难以控制.
- **方法**: 将历史划分为多个区块并行摘要, 使系统能够控制各区块的压缩量, 在保持信息的同时降低端到端延迟.

**AdaCoM: Learning Agent-Compatible Context Management**

[AdaCoM](https://arxiv.org/abs/2605.30785)的重点是让压缩表示服务于后续 Agent 动作，评价对象因而超出语言流畅度。

外部管理器可以服务冻结或闭源 Agent，但管理策略对不同能力 Agent 的迁移并非无条件成立。

- 时间: 2026.05.
- **动机**: 固定压缩策略难以适配不同能力的 Agent, 且无法训练闭源模型.
- **方法**: 训练外部 Context Manager, 在冻结 Agent 的情况下通过 RL 学习保留, 删除和改写历史, 并根据 Agent 能力调整压缩强度.

### 1.1. Less Context, Better Agents

减少可见历史有时会降低噪声，但收益取决于保留下来的状态是否足以继续决策。

这一路线提醒我们，更多上下文既包含证据也包含过期动作，删除策略必须以任务结果验证。

- 时间: 2026.06.
- **动机**: 企业工具返回内容冗长, 全量保留会造成上下文溢出, 状态过期和高推理成本.
- **方法**: 仅保留最近若干轮高价值工具交互, 并对更早历史进行摘要, 以同时提升任务成功率和 token 效率.

**状态持久化与程序化记忆**

另一组工作把重点从压缩文本转到保存可继续执行的状态。计划是否能跨窗口存活、模型能否主动压缩、程序化记忆能否替代自然语言摘要，答案并不相同。

三条路线可以沿写入时机、表示形式、验证依据和恢复能力四个坐标比较。

**Plans Don't Persist**

计划文本看似完整，不表示跨窗口以后仍能约束实际工具调用。

删除或改写计划后的配对轨迹可以检验计划究竟依赖显式文本，还是已经进入隐藏状态。

- 时间: 2026.06.
- **动机**: 压缩方法通常假设模型已将早期计划内化, 但该假设缺少验证.
- **方法**: 通过 replay pairing, 隐藏状态距离和 probe, 对比保留与删除计划的轨迹, 发现计划主要依赖显式上下文, 直接删除会明显损害任务表现.

### 1.2. Self-Compacting Language Model Agents

[SelfCompact](https://arxiv.org/abs/2606.23525)把写入时机交给模型，也把遗漏关键状态的风险交给同一个策略。

论文用 compaction tool 与触发 rubric 配合，区分子任务结束的适合时机和推导中途的不适合时机。

- 时间: 2026.06.
- **动机**: 固定 token 预算下, 外部压缩容易误触上下文摘要.
- **方法**: 提供 compaction tool 和轻量 rubric, 让 Agent 在子任务完成或搜索收敛时自主压缩, 无需微调或额外监督.

**PRO-LONG: Programmatic Memory Enables Long-Horizon Reasoning**

程序化记忆用可执行结构保存中间状态，代价是控制代码本身也需要验证。

完整日志降低摘要的不可逆损失，却把负担转移到按需检索、程序正确性和执行成本上。

- 时间: 2026.07.
- **动机**: 自然语言摘要存在不可逆的信息损失, 完整历史又难以直接检索.
- **方法**: 保存完整, 结构化的交互日志, 让 Coding Agent 编写程序搜索和读取历史, 实现低成本, 按需访问的程序化记忆.

**横向观察**

几条路线都要回答同一个问题：压缩后还能否可靠完成后续动作。

横向比较应同时报告触发者、表示形式、训练耦合、来源可追溯性和恢复成本。

- **压缩时机的两条路线**: 外部统一压缩(1/2/3/4) vs Agent 自主压缩(6/7).
- **与训练耦合的探索**: CompactionRL 把压缩学进 RL 轨迹, AdaCoM 用外部 RL 训练 Context Manager, 都是「摘要质量对齐任务目标」的尝试.
- **记忆形式之争**: 自然语言摘要(1/2/3/4/6) vs 完整结构化日志 + 程序化检索(PRO-LONG), 对应信息损失与检索成本的权衡.
- **实证提醒**: Plans Don't Persist 表明「压缩会损害计划保持」并非杞人忧天, 压缩策略需要显式保留计划类信息.

**压缩对象与预算**

论文方法不同，但工程系统最终都要回答两个基础问题：哪些信息能够压缩，有限 token 应该分给哪些状态。

压缩对象必须按事实、猜测、计划与日志分层。预算则应跟随未来决策价值，而不是平均分配给每一轮历史。

## 2. 上下文压缩究竟压缩什么

上下文压缩是一个有损的状态迁移过程. 给定原始历史 $H_t$, 当前目标 $G_t$ 和 token 预算 $B$, 压缩器生成可见上下文

$$
\widetilde{H}_t=\mathcal{C}(H_t,G_t,B), \qquad
|\widetilde{H}_t|\le B.
$$

$\mathcal{C}$ 不可能在更少 token 中无条件保存原历史的全部信息, 所以它属于 **lossy compression**, 即有损压缩. 需要辨认的是哪些信息可以舍弃, 哪些信息决定 Agent 在当前目标下能否选出正确动作, 以及哪些证据必须能从外部日志重新取回. 评测应检查压缩结果是否保住后续决策所需的充分信息；语言流畅只能算基本要求.

原始历史至少包含五类对象, 每类对象的压缩方法不同.

| 对象 | 例子 | 压缩时需要保留什么 |
|---|---|---|
| 目标与约束 | 用户要求, 验收条件, 禁止操作 | 当前生效版本, 覆盖关系, 不可违反的条件 |
| 环境事实 | 文件哈希, 服务状态, 测试输出 | 来源, 时间, 对应环境版本, 验证结果 |
| 决策与计划 | 方案选择, 剩余步骤, 分支条件 | 决策依据, 未完成依赖, 重新规划触发器 |
| 工具轨迹 | 命令, 参数, 返回内容, 副作用 | 动作标识, 关键返回, 产物位置, 能否重试 |
| 推理草稿 | 候选假设, 已排除路径, 局部计算 | 仍影响后续的结论和未解决冲突 |

一段很长的工具输出可以只保留退出状态, 关键错误和原始日志位置; 一条只有十几个字的用户约束却可能一个字都不能丢. 因此按消息长度平均裁剪不成立. 最近消息也未必最重要: 第一步指定的许可证要求可能一直约束最终产物, 最近十轮的重复搜索却可以全部归并.

**事实, 猜测与计划不能揉成一段**

自然语言摘要最常见的结构性错误, 是把不同可信度的信息写成同一种陈述. 可以把压缩状态分成三层:

$$
M_t=(F_t, U_t, P_t).
$$

$F_t$ 是已经由环境检查支持的事实, $U_t$ 是猜测, 待验证判断与尚未解决的冲突, $P_t$ 是计划和条件分支. 三者的更新规则不同. 事实要附带来源与版本; 猜测要保留验证动作, 验证成功后才能迁移到事实层; 计划只在对应目标版本和前置条件仍有效时成立.

例如 Agent 看到一次构建失败, 推测原因是依赖版本过旧, 并计划升级依赖. 压缩后若只剩「依赖版本过旧, 下一步升级」, 一个未经验证的诊断就被提升成事实. 更安全的记录是: 「事实: 构建在错误码 X 处失败, 日志位于 L; 猜测: 依赖版本可能过旧; 计划: 先读取锁文件并核对兼容范围, 证实后再升级」. 这样恢复后的 Agent 知道哪些内容可以直接使用, 哪些内容仍要查.

计划还应记录完成状态和依赖. `修改文件 -> 运行测试 -> 提交` 不能压成「完成修改和测试」, 除非测试确实执行并通过. Plans Don't Persist 所提醒的问题就在这里: 计划并不会自动进入模型的某个稳定内部状态. 如果显式计划被删掉, 后续模型可能保留目标的大意, 却忘记尚未执行的验证步骤. 压缩器应将未完成计划当作一等对象, 不依赖摘要模型顺手提到它.

**Token 预算怎样分**

设模型窗口为 32,000 token, 其中系统指令和工具 schema 占 6,000, 当前用户输入占 2,000, 希望至少给下一轮推理与工具返回预留 8,000. 那么可用于历史状态的上限是

$$
B=32{,}000-6{,}000-2{,}000-8{,}000=16{,}000.
$$

假设原始历史已有 48,000 token, 直接截断需要丢掉三分之二. 一种可检查的预算分配是: 目标与硬约束 2,000, 已验证事实 4,000, 未解决问题和当前计划 3,000, 最近原始交互 5,000, 外部证据索引 2,000, 合计 16,000. 这些数字只是手算例子的输入, 不代表通用最佳比例. 它展示的是分配过程: 先扣除不能被历史挤占的固定成本, 再按信息职责分区, 收尾阶段检查总和.

若压缩后目标区实际只用了 800 token, 空出的 1,200 可以转给最近交互或证据索引; 若未解决冲突突然增加, 应减少可以外置的原始日志, 而不是截掉冲突列表. 预算策略需要随任务阶段变化. 搜索早期可能需要更多候选与来源, 执行阶段需要更多环境状态, 临近交付时则要为验收条件和检查结果留出空间.

压缩触发也不能只靠固定阈值. token 使用率接近上限当然是一个信号, 子任务完成, 目标版本切换, 即将执行高风险副作用同样适合作为边界. 在这些位置压缩, 状态往往更容易形成闭合单元. Self-Compacting Agents 允许 Agent 主动调用 compaction tool, 就是在尝试让触发时机贴合任务进展; 外部 Context Manager 则更容易统一执行预算和安全规则. 两种方式可以组合, 但最终触发权和失败后的降级路径必须明确.

### 2.1. 更新、证据与失效

摘要是随任务状态增长的派生视图。每次整体重写都会增加遗漏旧约束和混入新猜测的机会。

可靠压缩需要增量更新、来源指针与失效规则，原始证据的保存方式也决定了系统能否从错误压缩中恢复。

**摘要要增量更新, 不能反复覆盖**

长任务不会只压缩一次. 若每次都拿「上一版摘要 + 最近消息」重新生成新摘要, 细小遗漏会逐轮累积. 第一次漏掉来源, 第二次把猜测写成事实, 第三次再依据错误事实更新计划, 最终已经很难追溯偏差从哪里出现. 因此摘要需要版本:

$$
M^{(k+1)}=\operatorname{Merge}(M^{(k)},\Delta H_k,G^{(v)}),
$$

$M^{(k)}$ 是第 $k$ 版压缩状态, $\Delta H_k$ 是本轮新增历史, $G^{(v)}$ 是当前目标版本. `Merge` 至少要产生变更集合: 新增了什么, 更新了什么, 哪些记录失效, 哪些冲突尚未解决. 旧版本留在审计层，用于出现偏差时定位具体的错误更新，无需继续占用模型上下文.

版本冲突不能靠「收尾阶段一句覆盖前面所有内容」处理. 新工具观测可能来自旧环境, 用户新消息也可能只修改一个约束. 每条状态记录应关联适用范围和来源. 如果两个来源给出不同文件版本, 摘要应保留冲突并触发重新读取; 如果用户明确撤销旧要求, 状态层则创建新目标版本并使旧约束失效. 冲突的处理动作取决于信息类型, 时间顺序只是证据之一.

分块并行压缩还会带来跨块冲突. 两个区块分别总结时, 后一块可能修改前一块中的结论, 单独摘要无法看见这种覆盖关系. 合并阶段需要以目标, 实体和版本为键重排信息, 而不是简单拼接各块摘要. Parallel Context Compaction 减少串行压缩的服务延迟, 但任何并行方案都仍需面对这个语义合并问题.

**压缩后怎样恢复原始证据**

有损摘要可以承担导航, 不能取代原始记录. 每条关键结论应保存能够回到证据的指针, 例如消息序号, 文件路径与哈希, 工具调用 ID, 日志区间或数据库记录版本. 当下一步需要精确参数, 完整错误栈或原始措辞时, Agent 先依据指针取回局部证据, 再行动. PRO-LONG 采用完整结构化日志与程序化检索, 正面处理的就是摘要不可逆这一限制.

恢复可以写成两级读取. 第一级始终加载压缩状态 $M_t$, 用它确定当前目标, 事实和待办; 第二级按需执行

$$
e=\operatorname{Retrieve}(r,H_{0:t}),

$$


其中 $r$ 是摘要中的证据指针, $H_{0:t}$ 是外部保存的完整历史, $e$ 是取回的原始片段. 如果检索结果与摘要冲突, 不能静默选择其中一个. 系统应重新查询当前权威环境, 更新事实层, 并标记受影响的计划需要重算.

恢复测试应在正常运行期间就做. 随机选择一个压缩边界, 只提供 $M_t$ 和外部索引给新的执行体, 检查它能否回答当前目标版本, 最近一个已验证里程碑, 尚未解决的阻塞和下一项安全动作. 如果恢复必须依赖原进程中未保存的隐变量, 这份压缩状态仍然不完整.

**常见失败模式**

压缩结果往往依旧语句通顺，关键状态却可能在没有告警的情况下消失或过期。

故障应按遗漏、错误合并、版本残留和来源断裂分类，分别构造可触发的测试样本。

**约束蒸发**发生在摘要保留了任务主题, 却删除了格式, 权限或禁止操作. 最终产物可能语义正确, 仍然违反用户要求. 检查方法是把硬约束单独列出, 每次压缩前后逐项做集合差异.

**猜测固化**指未经验证的解释在多轮改写后变成肯定事实. 它通常来自没有区分 $F_t$ 与 $U_t$. 检查方法是要求每项事实都有来源指针, 没有来源的判断只能留在待验证层.

**计划断尾**指摘要保留已经做过的工作, 丢失尚未执行的验证或清理动作. 任务看似完成, 实际停在不可交付状态. 检查方法是为计划节点保存状态与前置依赖, 压缩后重算未完成集合.

**旧状态复活**发生在摘要引用过期文件, 旧目标或已经撤销的方案. 最近写入不一定就是权威版本, 所以需要实体版本与失效标记. 恢复时应重新读取容易变化的外部状态.

**不可追溯摘要**读起来完整, 却没有任何证据指针. 一旦出现冲突, 系统无法判断结论来自用户, 工具还是自己的推测. 关键结论应保留稳定定位信息；复制全部日志只会重新挤满窗口.

**压缩震荡**指系统频繁在摘要与原始历史之间切换, 反复花费 token 却没有形成稳定状态. 可以记录每次压缩后的保留率, 随后的证据回读次数和下一次压缩间隔. 若刚压掉的信息很快又被大量取回, 说明预算分区或触发时机需要调整.

### 2.2. 评测协议与工程检查

压缩率本身不能说明任务是否仍可完成。评测必须同时观察状态保真、后续动作、恢复成本和推理资源。

评测同时覆盖执行协议、预算与保真手算，并与定义、LiveMem 和 Harness 的状态边界对齐。

**一套可执行的评测协议**

先准备一组具有环境检查器的长任务, 每个任务包含目标版本, 硬约束, 可验证里程碑和完整事件日志. 对同一条基础轨迹构造不同压缩预算, 例如保留原历史的 50%, 25% 和 12.5%, 并保留一组不压缩对照. 百分比只定义实验条件, 不预设结果.

然后在若干固定边界触发压缩, 将压缩状态交给新的执行体继续任务. 记录五组指标:

1. **约束保留率**: 压缩前仍生效的硬约束中, 压缩后可被准确恢复的比例.
2. **事实精度**: 摘要事实中有环境证据支持的比例, 同时统计遗漏事实与错误事实.
3. **计划连续性**: 未完成且仍有效的计划节点被保留的比例, 以及恢复后第一个动作是否满足前置依赖.
4. **证据可恢复率**: 随机抽取关键结论, 能否通过保存的指针取回对应原始证据.
5. **任务结果与成本**: 最终成功率, 约束违反数, 恢复次数, 额外检索 token, 压缩延迟和总推理 token.

还需要专门加入冲突用例. 在压缩前后修改一个用户约束, 更新一个外部文件, 让一次工具调用返回部分成功, 检查系统是否保留两版信息并选择当前权威状态. 再加入延迟验证用例: 早期步骤产生的错误只能在若干步后被测试发现, 观察压缩器是否把未验证结果错误地提升为事实.

失败轨迹还要做归因. 如果终态失败来自压缩前模型已经做出的错误决策, 不能算作压缩损失; 如果完整历史对照能够恢复, 压缩组因遗漏约束或证据而失败, 才说明 $\mathcal{C}$ 丢掉了任务充分信息. 这套协议把「摘要看起来不错」转换成可以执行的比较: 在相同任务, 相同模型和相同环境下, 不同压缩策略让哪些状态保存下来, 为此花了多少 token, 又从哪里开始失效.

**一个可复算的预算与保真例子**

设活动窗口预算为 8000 token，系统提示与工具 schema 固定占 1800，当前任务材料占 2600，最近动作和观测保留 2200，留给压缩历史的预算只有

$$
B_{\mathrm{summary}}=8000-1800-2600-2200=1400.
\tag{8}
$$

若旧历史共 14000 token，文本压缩率是 $1400/14000=10\%$。这个数字没有说明压缩是否成功，因为不同信息的未来价值不同。把旧历史拆成 20 条硬约束、30 条已验证事实、10 条未决问题和 200 条普通日志，评测应逐类计算召回，而不是对全部 token 做表面重合。

设硬约束权重为 5，事实为 3，未决问题为 2，日志为 0.2。压缩后保留 19 条约束、27 条事实、8 条未决问题和 30 条日志，则加权保真率为

$$
F=\frac{19\times5+27\times3+8\times2+30\times0.2}
{20\times5+30\times3+10\times2+200\times0.2}
=\frac{198}{250}=0.792.
\tag{9}
$$

若只按条目数计算，保留率为 $84/260\approx0.323$，看起来很低；加权结果更高，是因为系统优先保留会影响后续决策的状态。权重必须在评测前声明，不能看完结果后调整。硬约束仍漏掉一条，所以即使 $F=0.792$，只要遗漏项涉及安全边界，任务也应判为约束失败。

下一步测动作影响。用相同模型、任务和随机种子，分别提供完整历史 $H$、压缩状态 $Z$ 与只保留最近窗口的截断输入 $W$。记三者成功率为 $A_H,A_Z,A_W$，压缩恢复率可以写成

$$
R_{\mathrm{comp}}=\frac{A_Z-A_W}{A_H-A_W}.
\tag{10}
$$

若 $A_H=0.80,A_Z=0.68,A_W=0.40$，则 $R_{\mathrm{comp}}=0.70$，表示压缩恢复了完整历史相对纯截断优势的 70%。当 $A_H=A_W$ 时分母为零，这项指标没有定义，应直接报告三项原始结果。

还要测更新而非只测首次摘要。让任务经历五次压缩，每次加入一个新约束、修订一个旧事实并关闭一个未决问题。第 $k$ 次压缩后的状态与当时真值比较，得到 $F_k$；若 $F_k$ 单调下降，说明增量误差在累积。再从每次 checkpoint 恢复执行同一后续任务，记录成功率和查回原证据所需工具调用。文本看起来连贯却无法定位来源，仍然不具备可靠恢复能力。

工程检查还要记录摘要生成 token、延迟和失败回退。压缩器超时后直接丢弃旧窗口，会把基础设施错误变成永久失忆；更安全的策略是保留上一版已验证摘要与尚未压缩的增量日志，并在预算允许时重试。新摘要只有通过结构校验、关键约束对照和来源指针检查后，才替换旧版。

## 3. 压缩是一条状态提交链

上下文压缩常被画成「长文本进去，短摘要出来」，这张图漏掉了最重要的时间关系。运行中的 Agent 至少同时拥有上一版可信状态 $M_k$、尚未压缩的增量日志 $\Delta H_k$、压缩候选 $\tilde M_{k+1}$ 和环境版本 $E_k$。候选通过检查后才能成为下一版：

```text
M_k + ΔH_k + E_k
        │
        ▼
  生成候选 M~_{k+1}
        │  schema / 约束 / 来源 / 版本检查
        ▼
  提交 M_{k+1} ──→ 释放旧窗口
        │
        └─失败→保留 M_k 与 ΔH_k
```

提交顺序不能反过来。若先释放旧窗口，再发现摘要缺字段，系统已经失去重建材料。压缩应像一次有验证门的状态迁移：生成候选不会改变当前权威状态，检查通过才原子替换；失败则继续使用旧摘要和增量日志，必要时暂停接收会扩大状态的新动作。

候选摘要还要绑定环境版本。设压缩开始时文件集合哈希为 $e_k$，摘要完成时环境已经变成 $e_{k+1}$，其中关于测试结果和当前文件的陈述可能过期。提交条件可以写成：

$$
\operatorname{commit}(\tilde M)=
\mathbf1[\operatorname{schema}(\tilde M)]
\mathbf1[\operatorname{constraints}(\tilde M)]
\mathbf1[e_{read}=e_{current}].
\tag{11}
$$

环境版本条件失败时，无须把整段历史重新压一次。系统可以读取环境 diff，只使相关事实和计划节点失效，再把变化合入候选。这样既保留压缩结果，也不让旧环境结论悄悄升级成当前事实。

**多次压缩怎样累积误差**

一次摘要保留 95% 关键状态，看起来很高；连续十次若错误独立且无法恢复，全部关键状态都保真的概率约为：

$$
0.95^{10}\approx0.599.
\tag{12}
$$

真实错误不会独立，重要约束也可能重复出现，但这个演算说明了递归摘要的危险：下一次压缩以已经有损的摘要为输入，遗漏会变成后续版本的空白，错误陈述则可能被重复强化。系统需要保留外部证据索引，使每一版摘要都能回到原始事件，而非只能引用上一版摘要。

可以为状态项记录首次来源与最近确认时间。若某项经过 $m$ 次压缩却从未重新读取环境，其新鲜度随时间下降：

$$
q_i(k)=q_i(0)\prod_{j=1}^{k}(1-\epsilon_{ij}),
\tag{13}
$$

$\epsilon_{ij}$ 表示第 $j$ 次转换对状态项 $i$ 的估计错误率。这个值不必在产品里精确计算，它提示调度器：高风险、长期未复核的事实应优先回源；普通对话细节可以接受更高损失。

**压缩触发器与延迟构成**

固定每 $N$ 个 token 压缩实现简单，却可能在一次关键工具返回中间切断语义。更合适的触发器同时观察窗口占用、任务边界和可恢复点。子任务刚通过验证、环境处于稳定 checkpoint 时压缩，摘要更容易区分事实与猜测；不可逆动作执行到一半时压缩，恢复语义最复杂。

设窗口上限为 $B$，安全余量为 $m$，当前占用为 $b_t$，预测下一轮输入与输出需要 $\hat g_t$，容量触发条件为：

$$
b_t+\hat g_t>B-m.
\tag{14}
$$

容量触发保证不会溢出，语义触发则在阶段完成、目标修订或 checkpoint 建立后主动压缩。两者结合能减少紧急压缩。预测偏小时仍可能撞线，因此系统还应保留硬截断回退，但回退只能丢低价值日志，硬约束、未决问题和当前计划有独立预算。

服务延迟由正常生成与压缩停顿共同组成。若每 $K$ 轮压缩一次，摘要耗时 $T_c$，普通一轮耗时 $T_g$，串行平均每轮时延约为：

$$
\bar T=T_g+\frac{T_c}{K}.
\tag{15}
$$

Parallel Context Compaction 关注的正是这条 serving 路径：压缩若能与不依赖旧窗口的工作并行，用户可见停顿会下降。但并行会引入快照问题，摘要读取的历史边界必须固定，新到事件进入下一批增量，不能一边总结一边把输入继续改写。

**结构化状态和自由文本各管什么**

自由文本适合保存背景、原因和难以枚举的语义；结构化字段适合目标版本、硬约束、计划状态与证据指针。把所有内容都塞进 JSON，会丢掉解释上下文；只保留一段散文，程序又无法可靠判断某项是否过期。

一个混合状态可以包含：`goal` 与 `constraints` 的结构化表、`verified_facts` 的版本化记录、`open_questions` 与 `plan_nodes`，再附一段 `narrative_context`。规划器先读取结构化硬边界，再用自由文本补充背景。压缩器更新自由文本时，没有权限删除结构化硬约束；结构化字段变化时，也应在叙述里留下自然说明，避免模型只看到一堆无来源键值。

外部证据不必全部塞回窗口。摘要中保存稳定指针、内容哈希和短说明，需要时再读取原文。若一次检索成本为 $c_r$，状态项被再次使用的概率为 $p_i$，将其完整保留的 token 成本为 $c_i$，可以用 $p_ic_r$ 与 $c_i$ 比较。高频小状态直接保留，低频大证据使用索引，通常比统一策略更省。

### 3.1. 失败边界

压缩器无法凭空恢复从未记录的事实。工具只返回截断日志，摘要再优秀也看不到被截掉部分；Executor 没保存文件版本，后续摘要也无法判断测试属于哪个提交。压缩发生在观测与记录之后，它能整理状态，却不能修复上游可观测性缺口。

第二个边界是目标未知。某段历史未来是否重要取决于后续任务，压缩时无法穷尽。保留原始证据索引和低成本冷存储，可以在目标变化后重新取回；彻底删除旧信息换来的 token 节省，则要接受未来不可恢复。

第三个边界是权限与删除。摘要、向量索引、缓存和 checkpoint 都可能保存用户要求删除的信息。治理系统必须知道同一来源派生出了哪些副本，并支持使其失效或重建。只删除聊天界面上的原文，压缩状态仍可能继续影响决策。

**压缩进入训练以后**

固定摘要器只在推理时改变输入，CompactionRL 则把摘要生成纳入 rollout，使后续任务奖励能够影响压缩策略。官方论文报告，基于 GLM-4.5-Air 的模型在 SWE-bench Verified 达到 66.8% Pass@1，在 Terminal-Bench 2.0 达到 24.5%，相对其对照分别增加 7.0 与 3.1 个百分点；基于 GLM-4.7-Flash 的版本分别达到 56.0% 与 20.2%。这些结果属于对应模型、训练与评测配置，无法单独证明任意摘要器都会带来同样收益。

一条轨迹被压缩后，摘要 token 影响后续许多动作。若只把终局优势均匀分给全部 token，长轨迹中不同阶段的长度差异会扭曲梯度。可以把轨迹拆成压缩前动作、摘要和压缩后动作三段：

$$
\tau=(a_{1:c},z_c,a_{c+1:T}),
\tag{16}
$$

$z_c$ 是第 $c$ 个边界生成的压缩状态。摘要质量通过后续状态分布影响回报，训练需要保留它与 continuation 的因果连接。CompactionRL 使用 token-level loss normalization 与 cross-trajectory GAE，让长短轨迹和多次压缩下的优势分配更加稳定。

训练还会学到压缩时机。太早压缩会频繁支付摘要成本，并在每次有损转换中累积误差；太晚压缩会逼近窗口上限，留不出工具返回和生成预算。若第 $c$ 步压缩的期望收益为任务回报改善 $\Delta R_c$，代价包含摘要 token、延迟和保真损失，可以写成：

$$
U(c)=\mathbb E[\Delta R_c]-\lambda C_{token}(c)
-\mu C_{latency}(c)-\nu L_{fidelity}(c).
\tag{17}
$$

真实训练不会精确知道四项，但这个分解说明消融应测什么：固定时机与学习时机、固定摘要器与联合训练、一次压缩与多次压缩，以及完整历史、截断和压缩三组对照。

**训练分布决定压缩偏好**

编码任务频繁奖励测试、文件路径和错误日志，摘要器会优先保存这些信息；换到日程安排或科研工作流，重要状态已经变化。跨领域使用前要测试约束召回、实体版本和未决计划，不能只看编码 benchmark 上的 pass rate。

摘要器还可能学习 verifier 的捷径。若训练任务只检查最终测试，它可能丢掉用户风格、安全约束或未覆盖的兼容要求，仍然获得高 reward。训练数据中的 verifier 覆盖面决定哪些信息有梯度，外部硬约束应由 Harness 独立保存，避免完全依赖策略自己学会记住。

多次压缩训练要包含恢复样本。让某一版摘要故意漏掉字段、引入版本冲突或指向失效证据，训练系统重新读取环境并修复状态。只在完美摘要上训练 continuation，部署时遇到第一次压缩错误就会一路继承。

## 4. 压缩质量是任务条件下的率失真问题

只比较压缩前后的文字相似度，会把上下文管理带偏。工具日志里一行失败码可能决定后续路径，却只占极少 token；大段自然语言解释即使保留得很像，也可能已经失去行动价值。压缩质量必须相对于后续任务、动作集合和错误代价来定义。

设原始历史为 $H$，压缩表示为 $Z$，长度预算为 $B$。经典率失真形式可以改写为

$$
\min_{q(Z\mid H)}\ \mathbb E[D_T(H,Z)]
\quad\text{s.t.}\quad \mathbb E[|Z|]\le B,
\tag{18}
$$

其中 $D_T$ 是任务条件失真。若使用 $H$ 的最优动作与使用 $Z$ 的最优动作相同，而且关键验收结论不变，那么删掉大量表述仍可能是低失真；若一个版本号丢失导致读取错误文件，文字摘要再流畅也是高失真。

任务在压缩时未必完全已知。可以把未来任务视为分布 $p(T\mid H)$，优化平均失真；安全约束与不可逆动作则不能只服从平均值，应加入最坏情况项：

$$
D(H,Z)=\mathbb E_T[D_T(H,Z)]
+\lambda\max_{T\in\mathcal T_{risk}}D_T(H,Z).
\tag{19}
$$

这解释了为什么权限、删除边界、未完成承诺和证据指针要独立保存。它们平时未必被调用，一旦相关，遗漏代价远高于普通背景。

压缩预算也不该平均分给消息。对状态项 $i$，设再次使用概率为 $p_i$，遗漏损失为 $L_i$，保留成本为 $b_i$，可以按 $p_iL_i/b_i$ 排序分配工作记忆。但这个贪心只适合近似独立的项目；多个证据共同支持一个结论时，单独保留任何一项都可能无用，需要按依赖子图整体选择。

率失真视角还能解释 AdaCoM 所报告的 Fidelity-Reliability Trade-off。能力较强的 Agent 能利用细节，过度裁剪会损失可用证据；较弱 Agent 可能被冗长历史干扰，更激进压缩反而把它带回可靠推理区间。压缩器与执行 Agent 不是可以随意互换的两个模块，最优表示取决于接收者能读懂什么、会被什么锚定。

评测时至少需要三条曲线：任务成功率随 token 预算变化、关键状态召回率随预算变化、延迟与成本随预算变化。单点报告「压缩了多少」无法区分方法是在更有效地编码，还是碰巧获得了更宽松的预算或更强的下游模型。

**选择、摘要与索引是三种不同操作**

上下文缩短常被统称为摘要，实际包含三类算子。选择保留原始片段，信息没有被改写，但会遗漏未选部分；摘要生成新表述，密度更高，也引入事实漂移；索引把内容移到窗口外，保留回源入口，用检索延迟换取 token。三者的错误机制不同。

选择可写成掩码 $m_i\in\{0,1\}$：

$$
Z_{sel}=\bigoplus_i m_i h_i,
\qquad \sum_i m_i|h_i|\le B.
\tag{20}
$$

它适合短而精确的命令、报错与公式。缺点是片段之间的关系仍需模型自行恢复，连续保留许多重复日志也会浪费预算。摘要器将多个片段映射为 $z=f(h_{i:j})$，能合并重复和显式写出因果，却可能把「待验证」改成「已确认」。索引只保存 $(id,hash,description)$，适合体积大、复用概率低且允许稍后读取的材料。

一个稳健系统会混合使用：硬约束和当前目标以结构化字段保留；最近工具结果原文选择；阶段背景使用摘要；完整日志与论文正文进入可寻址冷存储。若把所有东西交给同一个生成式摘要器，精确字符串、权限状态与散文背景会争夺同一输出通道。

混合表示需要解决一致性。摘要声称测试已经通过，索引指向的原始日志却属于旧提交；结构化状态标记任务取消，自由文本还写着下一步继续执行。读取时不能让模型自行在冲突版本中投票。权威字段应有明确优先级，派生摘要携带来源版本，不匹配时先失效再重建。

索引并不天然可恢复。标识符可能失效，文件可能移动，外部网页可能更新。一个可用指针至少包含稳定定位、内容哈希、抓取时间和必要的访问条件。内容哈希不匹配时，新内容可以作为新证据读取，却不能冒充压缩时所依据的旧证据。

三种操作应分别消融。只看最终 token 数相同的混合方案，无法判断收益来自保留原文、生成归纳还是允许回源。测试集还应放入精确字符串任务、跨段因果任务和低频证据回忆任务，让每种算子的长处与短板显现出来。

**多层记忆的迁移规则**

有限窗口更像缓存，而不是全部记忆。可以把状态分为即时上下文、工作记忆、情节存储和权威外部状态。即时上下文保留最近交互；工作记忆保存当前目标、计划和活跃证据；情节存储保存已经结束的子任务与来源索引；权威状态由文件、数据库、版本库或真实环境承担。

信息从热层迁往冷层需要明确条件。子任务完成且验证通过后，过程日志可以降级，只保留结论、证据和恢复入口；仍在排错的轨迹不能因为时间久就降级，因为旧失败尝试决定下一步。访问频率只是一个信号，任务阶段和未决依赖同样重要。

设状态项 $x_i$ 的热度为 $a_i$，依赖中心性为 $d_i$，风险为 $r_i$，体积为 $b_i$，可定义保留分数

$$
s_i=\alpha a_i+\beta d_i+\gamma r_i-\delta b_i.
\tag{21}
$$

分数帮助排序，却不能覆盖硬规则。授权边界即使很久没访问也不能被淘汰；已经存入外部权威状态的巨大日志，即使与当前任务相关，也可能只需保留指针。权重应由任务域校准，而非在所有 Agent 上共用。

晋升同样重要。冷存储中的旧事实被新目标重新引用时，应回到工作记忆，并先验证新鲜度。只检索一段相似文字而不读取它的版本和上下文，容易把旧计划复活。晋升记录要指明触发问题、读取范围和验证结果，避免检索内容永久污染后续上下文。

分层迁移还要防止抖动。某项在预算边缘反复晋升和降级，会不断支付摘要与读取成本。可以使用双阈值：得分高于 $\theta_{up}$ 才晋升，低于较小的 $\theta_{down}$ 才降级。中间区域维持原层级，形成迟滞。

故障恢复要从冷层重建热层。恢复流程先读取目标版本和未决动作，再装载最近 checkpoint，随后按证据指针核对外部环境。若只能加载一篇自然语言摘要，却不知道它对应哪些文件与工具调用，系统恢复的是故事，不是可继续执行的状态。

**压缩触发是一项最优停止问题**

何时压缩与怎样压缩同样关键。太早触发会增加转换次数和累计失真，太晚触发会让上下文退化，甚至没有空间容纳工具返回。触发器需要在继续运行的风险与立即压缩的代价之间选择。

令当前状态为 $s_t$，继续一步的期望代价为 $C_{continue}(s_t)$，现在压缩的代价为 $C_{compact}(s_t)$，则触发规则可以写为

$$
\text{compact at }t
\iff C_{compact}(s_t)
\le \mathbb E[C_{continue}(s_{t+1})+V(s_{t+1})].
\tag{22}
$$

这里的状态不仅包含 token 占用，还包括是否位于子任务边界、是否存在未闭合推导、下一轮预计输出、外部动作是否可恢复。相同的 80% 窗口占用，在测试刚通过时适合压缩，在长证明进行到中间时可能不适合。

SelfCompact 的工具与 rubric 组合可以从这个角度理解：工具提供停止动作，rubric 向模型暴露哪些状态意味着转换代价较低。仅有工具时，模型可能不调用或乱调用；只有文字提醒而没有压缩动作，也无法真正改变窗口。

预测下一轮长度时要考虑尾部风险。只用平均输出长度，遇到一次巨大工具返回就会溢出。可以用高分位预算 $Q_{1-\epsilon}(G_{t+1}\mid s_t)$ 替代均值，让溢出概率控制在 $\epsilon$ 附近。高风险工具调用前还可主动建立 checkpoint，即使窗口尚未达到固定阈值。

触发评测不能只报告平均压缩次数。需要记录过早触发率、被迫截断率、处于不安全语义位置的触发率，以及每次压缩后到下一次回源的距离。两个方法任务成功率相同，其中一个可能靠高频重压缩支付了数倍成本，另一个则保留过多历史导致服务尾延迟更高。

### 4.1. 关联阅读

本库的 [Long-Horizon 严格定义](../1-定义与评测/1.1-Long-Horizon定义.md)和[评测协议](../1-定义与评测/1.2-评测协议与基准.md)共同约束压缩方案。前者区分长上下文与长程依赖，后者给出有效进度、扰动恢复和成本曲线；因此压缩率或摘要相似度不能单独充当任务成功指标。

[LiveMem](./2.3-LiveMem动态记忆.md)提供另一条路径：用固定容量循环状态维持上下文轮转后的计算连续性，但仍需外部事实与审计系统。[LongHorizon-Harness](../3-计划执行与系统/3.1-LongHorizon-Harness.md)则把任务状态、执行与完成判断外置。三者并非互斥：压缩控制工作上下文，内生状态维持连续影响，Harness 保存可验证、可恢复的权威状态。

**压缩误差怎样穿过后续决策**

摘要里的一处错误不会只影响下一句话。它先改变模型对当前状态的估计，再改变计划、工具参数和验证对象，收尾阶段可能被新产生的日志当成既成事实。要理解压缩风险，需要沿决策链追踪误差，而非只在摘要文本上做逐句核对。

设真实状态为 $s_t$，压缩后恢复的状态为 $\hat s_t$，策略为 $\pi(a\mid s)$，环境转移为 $P(s'\mid s,a)$。若压缩造成状态误差 $\delta_t=d(s_t,\hat s_t)$，动作分布差异可由策略敏感度约束：

$$
\operatorname{TV}\!\left(\pi(\cdot\mid s_t),
\pi(\cdot\mid\hat s_t)\right)
\le L_\pi\delta_t.
\tag{23}
$$

$L_\pi$ 大的状态区域对细小表述非常敏感。例如命令中的路径只差一个目录，动作就完全不同；背景解释少一个形容词，通常不会改变计划。压缩器应该优先保留高敏感字段，而不是按自然语言显著性分配 token。

动作改变后，环境状态也会分叉。若转移和价值函数的 Lipschitz 常数分别为 $L_P,L_V$，长度为 $H$ 的粗略误差上界会包含连乘项 $(L_PL_\pi)^H$。现实系统不一定满足光滑条件，但这个形式揭示一个事实：长程任务中的早期状态错误具有放大机会，不能用一次摘要相似度推断终局影响。

有些误差会自行消失。压缩漏掉一条无关搜索结果，后续再也不使用；有些误差会在验证时被纠正，例如测试实际失败迫使系统重读日志；还有些误差会自我强化，错误摘要令 Agent 修改错误文件，新 diff 又似乎证明该文件就是目标。评测应区分消散、可纠正和自强化三类轨迹。

阻断误差传播依赖独立观测。执行关键动作前重新读取当前文件、权限和测试状态，相当于把估计重新锚定到环境。若所有后续判断都只引用压缩摘要，系统形成封闭回路，摘要中的错误再也没有外部信号可以纠正。

可以设计一组注入实验：在摘要中分别篡改低影响背景、当前文件路径、验收阈值和权限字段，测量动作分歧时间、受影响节点数、恢复时间与不可逆副作用。单纯统计模型是否复述错误，远不如这些指标接近真实风险。

**事实、决策和承诺需要不同保真标准**

上下文中的信息承担不同功能。事实描述环境是什么，决策记录为什么选择某条路径，承诺规定之后必须完成什么。三者混在一段摘要里，容易出现「保留结论却丢掉依据」或「保留讨论却丢掉义务」。

事实项需要来源、观测时间与版本。例如「测试通过」必须绑定命令、代码版本和输出；环境变化后，它会过期。决策项需要候选方案、取舍理由和适用前提，否则目标变化时无法判断旧选择是否仍合理。承诺项需要责任主体、完成条件和状态，不能因为相关讨论被压缩就从计划里消失。

对事实可以追求可验证保真：摘要陈述能否由来源重新证明。对决策追求反事实保真：如果关键前提改变，系统能否知道要重开选择。对承诺追求执行保真：未完成事项是否仍出现在调度与验收中。这三个指标不能被一个 ROUGE 或语义相似度取代。

举例来说，原历史可能包含「尝试方案 A 后内存溢出，因此改用 B；提交前还需在 Windows 上验证」。合格压缩至少保留 A 的失败条件、选择 B 的理由和 Windows 验证这项承诺。只写「当前采用 B」虽然语言简洁，却无法解释何时应重新考虑 A，也会漏掉最终验收。

状态结构可把三者拆开：`facts` 保存版本化谓词，`decisions` 保存前提到选择的边，`obligations` 保存未完成验收。自由文本摘要负责把它们串成可读背景，但不能成为唯一副本。更新时，事实失效会沿依赖边使决策降级，承诺只有完成、撤销或显式替代才能关闭。

评测样本应让三类信息发生不同变化。例如事实被新工具结果覆盖，决策因成本变化而重开，承诺被用户明确取消。若系统统一使用「最近一句覆盖」，就会错误删除仍有效的事实或继续执行已经撤销的承诺。

### 4.2. 并行压缩的快照一致性

Parallel Context Compaction 将压缩从串行阻塞路径移开，但并行本身带来一致性问题。压缩器读取历史 $H_{1:t}$ 时，执行 Agent 可能继续产生 $H_{t+1:t+k}$。若摘要器的输入边界不固定，晚到消息有时被读入、有时被遗漏，同一轨迹会得到不可复现的状态。

最简单的协议是在版本 $t$ 建立不可变快照，压缩结果写为 $Z^{(t)}$。新事件进入增量缓冲区 $\Delta H^{(t+1:u)}$。切换时使用

$$
C_u=Z^{(t)}\oplus\Delta H^{(t+1:u)},
\tag{24}
$$

并确认增量起点恰好是 $t+1$。起点更小会重复事件，起点更大会形成缺口。摘要结果必须携带覆盖区间，不能只返回一段无版本文本。

并行任务结束顺序可能颠倒。版本 $t+20$ 的摘要先完成，版本 $t$ 的摘要稍后返回，后者不能覆盖前者。接收方按覆盖终点与祖先关系判断；若两个摘要来自分叉快照，不能仅凭时间戳选一个，需要重新合并共同祖先之后的差异。

压缩期间发生目标更新更棘手。旧快照中的大量信息可能仍有效，但摘要策略使用了旧目标的价值判断。系统可以接受其中的事实抽取，重新评估其选择与删减；也可以在目标差异影响核心预算时取消压缩。是否取消由目标变更与摘要选择函数的依赖关系决定。

并行方案的延迟收益也要按端到端关键路径计算。假设执行剩余时间为 $T_e$，压缩时间为 $T_c$，串行停顿近似 $T_e+T_c$，理想并行为 $\max(T_e,T_c)$。但快照复制、合并与冲突处理带来 $T_m$，真实时间是 $\max(T_e,T_c)+T_m$。当块很小或冲突频繁时，并行未必更快。

测试应主动制造摘要慢返回、目标在压缩中途变化、增量缓冲重复投递和执行 Agent 提前耗尽窗口等情况。只在稳定离线历史上并行生成几段摘要，无法证明在线切换正确。

**回源属于压缩协议**

任何有限摘要都可能缺信息。系统若把回源视为异常，会逼迫摘要器塞入所有可能细节；结果是压缩率低，仍然无法覆盖未知未来任务。更合理的设计把「摘要负责导航，原始记录负责证明」作为正常协议。

当问题 $q$ 到来时，先用工作状态判断现有证据是否充分。若答案依赖摘要中没有展开的来源，生成回源请求 $r=(q,id,span,version)$。读取后把相关片段临时晋升，并将得到的结论与来源绑定。这个过程类似按需分页，关键是缺页可检测。

缺页可检测要求摘要明确表达未知和指针。例如写「失败原因有三类，详见日志 L17」比武断缩成一类更安全；写「尚未核对发布日期」能阻止模型把空白补成猜测。摘要器的目标不该奖励表面完整，因为表面完整会掩盖回源需要。

回源策略可以比较读取成本与错误风险。设读取成本为 $c_r$，不读取时错误概率为 $p_e$，错误损失为 $L_e$，当

$$
p_eL_e>c_r
\tag{25}
$$

时应回源。高风险事实即使当前置信度较高也值得核对；低风险背景可以接受摘要。若来源访问需要网络或权限，成本还包括失败概率和等待时间，系统应提前缓存即将使用的证据。

回源结果也会过期。网页当前版本与压缩时版本不同，读取新页面只能证明现在内容；要核对旧决策，应读取存档或保存的快照。文件指针若没有提交哈希，也可能返回修改后的内容。稳定定位是协议的一部分，不是检索器的附加优化。

评测回源能力时，应有意询问压缩时低概率、后来变得关键的信息。观察系统能否承认工作记忆不足、找到正确来源、验证版本并更新状态。禁止回源的评测只能测一次性编码容量，不能代表有外部存储的真实 Agent。

**压缩器与执行器之间的接口契约**

压缩器输出一段自然语言，执行器「大概能懂」，不足以形成稳定系统。两者需要明确接口：哪些字段必须存在，哪些允许未知，哪些结论必须带证据，哪些动作仍待执行，以及压缩覆盖了哪段历史。

接口可分为控制面与内容面。控制面包含目标版本、覆盖区间、状态 schema、校验和、未决动作和权限边界；内容面包含事实、背景、推理摘要与证据索引。控制面应由确定性逻辑验证，内容面再交给模型解释。这样即使自然语言表达变化，执行器仍能判断摘要是否适用于当前任务。

兼容性也是问题。压缩器升级后新增字段，旧执行器应忽略未知的可选项；删除或改变必需字段则需要 schema 版本迁移。没有版本号时，模型可能把旧字段含义按新规则解释，错误不会表现为解析失败，而会悄悄进入计划。

接口还应声明不变量，例如「所有未完成承诺都有唯一标识」「每个已验证事实都有来源版本」「权限集合只能由用户事件扩展」。压缩输出违反不变量时拒绝切换，继续使用旧上下文或采取保守回退。让执行器在缺字段时自由补全，会把格式错误转化成行为错误。

接收方不能盲信摘要器自报。覆盖区间可与事件日志核对，引用哈希可验证，计数与计划节点可重算。自然语言推断无法完全自动审计，但硬字段越多，剩余语义风险越集中，人工或模型复核也更有目标。

跨模型迁移尤其依赖契约。AdaCoM 的结果提示，管理器对能力相近的 Agent 更容易迁移；部分原因可能是不同执行器使用压缩表示的方式不同。接口能够统一字段，却无法保证每个模型同样理解叙述细节，所以迁移评测仍要固定预算、任务和执行器能力。

**训练压缩策略时的信用分配**

压缩动作的后果通常延迟很久才出现。摘要漏掉一个约束，可能几十步后提交时才失败；保留一条证据，也可能直到最终验证才体现价值。若只用终局奖励，摘要 token 获得的学习信号方差很大。

把压缩边界记为 $c_1,\ldots,c_m$，每次产生状态 $z_j$。终局回报 $R$ 同时受执行动作、环境随机性和多次压缩影响。一个朴素策略梯度项为

$$
\nabla J=\mathbb E\left[
\sum_{j=1}^{m}\sum_{t\in z_j}
A_t\nabla\log\pi_\theta(z_{j,t}\mid h_{j,t})
\right].
\tag{26}
$$

若不同轨迹的摘要长度差异很大，按 token 求和会让长摘要拥有更大梯度权重。token-level normalization 试图让长度不同的压缩段可比，但归一方式也改变「一次压缩」与「一个 token」谁是优化单位，需要结合论文具体目标解释。

局部辅助奖励可以降低方差，例如约束召回、事实一致性、证据可达性和预算满足度。但这些代理指标可能被钻空子：逐字复制约束获得高召回，却挤掉任务进度；保留大量索引获得可达性，却让每步都回源。终局任务奖励仍需约束它们的实际价值。

反事实基线能估计一次压缩的贡献：在相同前缀下分别使用候选摘要与无压缩、截断或另一摘要继续 rollout，比较后续回报。完全配对的计算昂贵，可以只在关键边界采样。若环境不可复现，差异还会混入随机性，需要多次运行或使用可控模拟器。

训练数据必须包含压缩真正必要的轨迹。若多数任务在窗口内已经完成，策略最容易学到永不压缩；若所有轨迹都在固定位置强制压缩，它又学不到时机。课程可从单次、明确子任务边界开始，逐渐加入多次压缩、目标变化、错误摘要恢复和异步工具返回。

训练出的策略还要与部署预算匹配。训练时上下文、摘要模型和工具延迟不同，触发阈值与保留偏好会发生分布偏移。上线前应在目标执行器上重新绘制成功率—token—延迟曲线，而不能只迁移一个固定压缩比例。

## 5. 一套能够推翻方案的实验矩阵

上下文管理方案容易通过挑选有利任务显得有效。严格实验需要同时改变历史长度、有效信息密度、目标变化次数、工具输出体积、执行器能力和压缩预算。每个轴都对应不同假设，混在一个平均分里看不出方法依赖什么。

基线至少包括完整历史、窗口截断、固定间隔摘要、语义边界摘要、选择式保留、索引回源和学习式管理。完整历史并非永远是上界：长上下文退化可能使压缩方案更好；但若模型窗口容得下，完整历史提供了判断信息损失的必要参照。

对每种方法报告任务成功、有效 token、prefill 与 decode 成本、压缩调用成本、尾延迟、回源次数和关键状态错误。并行方案还报告快照冲突与合并开销，训练方案报告训练样本和额外计算。只报告模型 API token 会漏掉本地摘要器与检索系统的成本。

消融应直接针对机制。去掉证据指针，测试低频事实恢复；去掉结构化约束，测试权限与承诺；固定触发时机，测试语义边界价值；替换执行器，测试 manager 兼容性；加入错误摘要，测试恢复能力。如果去掉一个模块没有改变它声称解决的指标，机制解释就需要重审。

统计上要按任务轨迹配对。相同初始环境和随机种子下比较压缩策略，记录成功差值而非只比较两组均值。长程任务运行昂贵，置信区间可能很宽；没有足够样本时，应如实给出不确定性，不能把少量成功案例当成稳定优势。

最重要的压力测试是目标在压缩后改变。新问题需要一条先前看似无关的证据，系统必须通过索引回源；旧授权被撤销，系统必须停止依赖摘要中的许可；环境版本变化，旧测试证据必须降级。这些场景能区分真正的状态管理和只会把历史缩短的摘要器。

若一个方案只能在固定目标、无外部副作用、一次压缩和单一执行器上成立，它仍有研究价值，但适用边界要写清。极限扩展不能靠增加抽象名词，最终仍要回到哪些轨迹会成功、哪些会失败，以及实验怎样让失败显现。

**KV 缓存压缩与语义压缩解决不同瓶颈**

上下文管理里常把 token 摘要、KV eviction、KV quantization 和稀疏注意力放在一起讨论。它们都能降低长历史成本，却作用于不同对象。语义压缩生成新的短序列，可能改变信息；KV 压缩保留 token 语义表示，只降低缓存宽度、精度或条目数；稀疏注意力保留缓存，却减少每次读取范围。

对长度 $N$、层数 $L$、每 token KV 宽度 $d_{kv}$、元素字节 $b$，标准缓存量级为

$$
M_{KV}=2LNd_{kv}b.
\tag{27}
$$

量化主要减小 $b$，GQA/MLA 一类结构减小 $d_{kv}$，token eviction 减小有效 $N$。文本摘要则把后续前缀长度从 $N$ 换成 $N'\ll N$，新序列需要重新 prefill，但后续各层只为 $N'$ 保存 KV。

两者可以组合。先把已完成阶段压成短摘要，再对仍保留的近期原文使用低比特 KV 或选择性缓存。语义摘要若已经删除某段，KV 技术无法恢复它；KV 量化引起的数值误差，也无法通过更好的文字摘要完全抵消。实验应分别固定文本与缓存配置，避免把系统收益都归因给一个模块。

KV eviction 的选择标准通常依据注意力、位置或近期性，而任务状态的重要性未必在当前注意力中显现。一个早期授权字段长期没有被关注，直到最终发布才关键；纯注意力分数可能提前淘汰它。结构化硬状态独立保存，正好弥补模型内部缓存策略对低频高风险信息的不敏感。

语义压缩还会改变位置关系。原始证据相距数万 token，摘要后可能相邻，模型更容易联合推理；同时，原始先后顺序、重复次数和语气强度可能被抹平。因而「缩短后性能提高」既可能来自减少噪声，也可能来自人为重排证据，不能直接解释成模型获得了更长记忆。

**对抗性历史会利用压缩器的选择偏好**

压缩器本身是一条攻击面。外部网页或工具输出可以反复强调恶意指令，诱使摘要器把它提升为核心目标；攻击者也可以制造大量相似日志，挤掉真正约束。执行器若信任摘要而忘记消息来源，数据就可能在压缩过程中被洗成指令。

每个状态项要携带来源角色和信任级别。用户授权、系统边界、工具观测和网页文本进入不同通道，摘要只能改写内容，不能提升权限。即使网页里写着「这是用户的新要求」，来源标签仍然是外部数据。压缩后的自然语言若丢掉标签，后续模型很难重新区分。

重复也不能自动提高可信度。十个页面复制同一错误说法，可能来自同一上游；一条恶意指令重复一百次，也没有获得授权。合并时应按来源独立性去重，并把频率与证据强度分开。否则攻击者可以用 token 数换取摘要预算和置信度。

另一类攻击针对删除。用户要求遗忘一段敏感信息后，旧摘要、向量索引、checkpoint 和 KV 快照仍可能保留派生表示。删除协议需要追踪数据血缘，使所有可定位副本失效；无法精确删除的聚合模型状态，应说明边界并阻止其继续进入工作上下文。

压力测试可以把注入内容放在工具结果、引用文本、代码注释和历史摘要中，并设置相似但合法的操作说明。系统既要拒绝权限提升，又要保留真正的数据。简单删除所有命令式句子会损坏文档理解，不构成有效防御。

### 5.1. 数学推导压缩为何尤其困难

数学推导的中间步骤具有强依赖。自然语言背景删掉一段仍可能理解，证明中漏掉一个条件，后续等式就失去成立依据。压缩器若只保留最终公式，会隐藏变量定义、适用区间和近似步骤，使恢复后的模型无法判断能否复用。

可以把推导表示为有向无环图，节点是定义、引理、变换和结论，边表示逻辑依赖。预算有限时，不能只按节点显著性选择；保留结论必须保留一条从假设到结论的可验证路径，或保存能回源到完整证明的指针。孤立结论只能作为待验证陈述。

设结论节点为 $y$，前提集合为 $A(y)$。压缩后的证明子图 $G_Z$ 若要独立支撑 $y$，需要满足

$$
A(y)\subseteq V(G_Z),\qquad
\forall a\in A(y),\ a\leadsto y.
\tag{28}
$$

若预算不够，摘要应明确写「结论及引用」，而非省掉中间步骤后维持证明完成的口吻。读者或 Agent 在真正使用结论前回源检查。

符号表是另一类高价值状态。同一个 $m$ 在不同章节可能表示压缩率、块大小或样本数；压缩合并后若只保留一个定义，公式会表面合法、语义错位。每段推导的符号要绑定作用域，跨段合并时显式重命名或保留局部命名空间。

评测数学压缩时，可以隐藏某一步并要求判断后续是否仍成立，改变一个前提观察结论是否更新，或让两个使用相同符号的推导合并。答案复述得像不像原文并不关键，关键是依赖结构是否保持。

**压缩比需要按有效信息而非原始长度解释**

同样从十万 token 压到一万 token，原历史若有九成重复日志，任务很容易；若每段都包含独立约束，压缩难度完全不同。报告压缩比

$$
\rho=1-\frac{|Z|}{|H|}
\tag{29}
$$

时，还应描述有效信息密度和冗余结构。

可以用完成任务所需的最小充分状态 $S_T(H)$ 作为概念参照。实际无法精确求出它，但可通过人工标注关键事实、约束、证据和未决计划得到近似。若 $|S_T(H)|$ 本来就接近预算，任何高压缩率都意味着损失；若历史主要是重复尝试，摘要接近最小充分状态并不困难。

压缩收益可写成相对于必要状态的开销：

$$
\eta=\frac{|Z|}{|S_T(H)|}.
\tag{30}
$$

$\eta$ 很大说明仍有冗余，接近 1 表示接近标注下限，小于 1 则通常意味着标注遗漏、表示编码更紧或真实信息已经丢失。这个量依赖任务，不能跨数据集直接比较。

历史结构也影响可压缩性。重复观测、可重建计算和已经落盘的中间产物可以低成本删除；用户偏好、一次性外部返回和未保存的推理分叉难以重建。数据集若只包含前一类，会高估方法在真实工作流中的表现。

因此论文表格除了平均输入/输出 token，还应给关键状态数、来源数、目标修订次数和不可恢复事件比例。没有这些量，读者无法知道更高压缩比来自更强方法，还是更容易的历史。

**从一次摘要到持续维护**

生产中的上下文不会只压一次。新事件不断到来，旧事实会失效，目标会变化，索引也会迁移。压缩表示应被当作持续维护的物化视图：由事件日志派生，可增量更新，必要时重建。

全量重写每次都重新解释所有历史，能修正旧摘要，却成本高且输出不稳定。纯增量更新便宜，但早期错误可能永久保留。折中方案是在短周期内增量合并，在 checkpoint 或检测到冲突时从权威事件重新构建，并比较新旧状态差异。

维护过程要有垃圾回收。已经完成且超过保留期的临时计划可以删除；被新事实替代的旧值保留审计指针，不再进入热上下文；无引用的缓存和摘要版本可回收。垃圾回收不能只按时间，因为尚未完成的低频承诺可能很久没有访问。

漂移检测观察摘要与环境的差异。文件哈希变化、工具 schema 升级、目标版本前进或验证证据过期，都可能触发局部重建。若差异范围无法确定，才退回全量恢复。局部更新依赖数据血缘，没有来源映射就只能重做全部。

持续维护最终形成一个闭环：记录事件，更新权威状态，选择进入工作上下文的信息，执行并产生新观测，验证后降级已完成阶段。摘要只是其中一次状态变换。把它单独当作语言生成任务，会漏掉版本、一致性、权限和恢复这些决定长程可靠性的部分。

**一个跨三次压缩的手算**

考虑一条长度上限为 32K token 的代码修复轨迹。初始规则、仓库说明和用户目标占 6K，第一次搜索与阅读占 14K，修改和测试预计还需 18K。若等到窗口达到 30K 才处理，只剩 2K 余量，任何完整测试日志都可能触发截断。系统在 20K 时建立第一个 checkpoint 更稳妥。

第一次压缩把 14K 探索历史变成 2K 状态：保留目标与边界 1K、已核实代码事实 400、失败尝试 300、当前计划 200、证据指针 100。工作上下文从 20K 降至约 8K。这里的压缩率为 60%，但探索历史自身从 14K 压到 2K，局部压缩率约 85.7%。两种口径不能混报。

随后修改、测试产生 16K，新占用约 24K。第二次压缩不能简单把全部 24K 再摘要一次，否则第一版中的精确约束会经过第二次生成式改写。系统保留结构化目标 1K，读取第一版状态与新增 16K，只把已经完成的修改阶段合成 2.5K，并将完整 diff 与测试日志移入外部证据。新上下文约 3.5K 加上近期交互。

假设第二次摘要把「Windows 测试尚未执行」误写成「测试通过」。如果最终只检查摘要，任务会提前完成；如果承诺表仍保存 `windows-test: pending`，不变量检查会发现矛盾并拒绝切换。结构化承诺由此形成生成式压缩之外的独立校验通道。

第三阶段用户把目标改成同时支持另一版本。旧修改事实仍有用，原来的兼容性结论却可能失效。依赖图定位所有引用目标版本的测试证据，把它们从 `verified` 降为 `stale`；代码位置、失败原因和无关平台测试继续保留。全量丢弃会浪费有效工作，完全继承又会产生错误完成判断。

若每次摘要独立漏掉关键项的概率都是 3%，三次都不漏的粗略概率为 $0.97^3\approx91.3\%$。加入结构化硬字段后，生成式摘要只承担背景和解释，关键项遗漏概率由字段验证器控制。真实错误相关性更强，这个数字不能当可靠性估计，但能说明反复生成会累积风险。

这条手算还暴露成本口径。三次压缩节省后续 prefill，却增加摘要生成、证据落盘和两次回源。正确比较应累计整条轨迹的输入 token、输出 token、墙钟时间与任务结果，不能只拿最终上下文长度宣称节省。

### 5.2. 状态合并需要字段级语义

并行分支或恢复 checkpoint 后，常会得到两份压缩状态。文本拼接会保留矛盾，重新摘要又可能随意选择一方。合并必须理解字段类型：集合项可以求并，单值字段需要版本裁决，计数可能重算，计划状态按生命周期迁移，权限只能由授权事件改变。

设两份状态来自共同祖先 $S_0$，分别为 $S_a,S_b$。三方合并比较每个字段相对 $S_0$ 的变化。只有一侧修改时采用该侧；两侧写入相同值时合并；两侧不同值则调用该字段的冲突规则。直接比较 $S_a$ 与 $S_b$ 无法区分「一侧保留旧值」和「两侧各自新增」。

集合合并也不总是并集。已验证事实可在来源独立时并入，删除集合要让墓碑优先，避免被另一分支的旧副本复活。待办任务如果两侧都完成同一项，要按稳定 ID 去重；仅凭标题相似可能把两个不同范围的任务误合并。

数值字段需要单位与语义。例如一侧记录「至少 5 篇」，另一侧记录「提高到 8 篇」，合并为下界 8；若另一侧是「正好 6 篇」，两个约束未必相容。把它们都存成整数然后使用较大值，会丢失量词。

计划节点的状态不能按枚举大小取最大。`cancelled` 与 `completed` 都是终止态，却含义不同；旧分支完成一个已被新目标取消的动作，不应把当前任务重新标成完成。合并时检查目标版本和状态转移是否合法。

合并输出要保留冲突，而非为了生成一段流畅摘要强行消解。未解决冲突进入明确列表，阻塞依赖字段的动作；与冲突无关的工作仍可继续。这样上下文压缩才能服务于并行 Agent，而不会成为悄悄吞掉分歧的黑箱。

**失败后的恢复路径**

压缩失败有不同层次。格式错误可以重新生成，事实遗漏需要回源，错误覆盖需要从事件日志重建，外部副作用则可能需要补偿。统一执行「清空上下文重新开始」既昂贵，也可能重复不可逆动作。

恢复第一步冻结当前写入，保存出错状态和触发证据。随后判断权威来源是否仍完整：原始事件、文件版本和工具日志都在，可以重建；只有上一版摘要存在，只能在有损状态上修补；外部环境已经变化，还要读取当前状态做三方比较。恢复能力取决于事故前保存了什么。

局部遗漏可通过证据索引补齐。摘要里缺一个测试平台，承诺表和日志指针仍在，只需读取对应日志、更新字段并重验依赖节点。来源指针也丢失时，系统必须重新执行测试；若测试环境无法复现，就只能把结论标为未知，不能根据旧语气猜回结果。

错误覆盖需要回放。以收尾阶段一个可信 checkpoint 为起点，按顺序应用之后事件，并使用当前版本的确定性更新规则。若更新规则本身升级，应同时保留旧规则版本，先复现事故状态，再运行迁移；直接用新规则回放可能无法解释旧产物为什么出现。

已经执行的副作用按三类处理。可逆写入回滚到已知版本，可补偿动作执行反向操作并保留审计，不可逆动作通知用户并调整后续计划。摘要错误导致消息已经发送时，删除本地状态不能撤回收件人的副本，系统需要明确承认这一边界。

恢复测试不能只验证进程重启后能读到摘要。应随机破坏一个字段、截断一段索引、让 checkpoint 与环境版本错位，并测量是否能定位损坏范围、恢复有效成果、阻止重复副作用和重新获得验收证据。恢复时间与丢失工作量也是长程能力的一部分。

**上下文压缩的适用边界**

当任务高度依赖精确原文，且证据无法外置或回源时，激进摘要风险很高。法律条款逐字比较、代码补丁字符级审查、长证明形式验证，都更适合选择式保留或结构化抽取。生成式摘要可以提供导航，不能替代权威文本。

当执行器本身不会使用结构化状态，增加复杂 schema 也未必带来收益。它可能忽略字段，只依赖旁边的自然语言。此时应先验证接收者能稳定读取接口，再扩展状态粒度。AdaCoM 的跨 Agent 迁移结果提醒我们，管理策略与执行能力存在匹配关系。

任务很短、历史未接近退化区间时，压缩可能只有成本。摘要调用增加延迟并引入新的错误通道；完整上下文若能稳定处理，最优策略可能是不压缩。系统需要允许「保持原样」成为正式动作，而非把每次减少 token 都当进步。

极端动态环境中，旧历史价值迅速下降，摘要旧细节不如重新观测。相反，无法重现的一次性事件需要更强保留。压缩策略依赖环境可观测性、重放成本和变化速度，不能只由窗口长度决定。

隐私要求也可能限制外部冷存储。把历史移出窗口并不等于删除，它可能进入更多索引和缓存。若治理成本高于 token 收益，应缩小持久化范围，并优先使用可验证删除的存储。压缩设计必须同时回答信息去哪了、保存多久和谁能读取。

因此，可靠上下文管理的核心判断可以收束为四句：先确定权威状态，再决定工作窗口；按后续行动价值压缩，而非按文字相似度；允许通过稳定索引回源，并让所有证据绑定版本；把压缩放进执行、验证和恢复闭环中评测。做不到这些时，更长的摘要只是更短的聊天记录，还称不上长程 Agent 的状态系统。

### 5.3. 如何检查压缩表示是否足够

「信息都在」很难直接证明，因为未来问题未知。实际系统可以用一组可观测任务逼近充分性：从压缩状态重建当前目标，列出仍未完成的承诺，解释最近一次关键决策，定位每条已验证事实的来源，并预测下一步合法动作。任何一项无法完成，都暴露对应状态缺口。

还可以采用双向检查。正向从原始事件生成压缩状态，反向让另一个执行器只看压缩状态回答结构化问题，再与事件日志计算出的真值比较。反向任务不要求复述原文，而是检验状态是否支持行动。为了防止测试题泄漏，问题模板应覆盖未见组合，并随机改变实体、范围和事件顺序。

对计划节点 $p$，定义可执行条件 $pre(p)$、预期结果 $post(p)$ 和验证器 $v(p)$。压缩状态至少要支持判断

$$
\operatorname{ready}(p)=
\mathbf 1[pre(p)\text{ 已满足}]
\mathbf 1[\text{权限有效}]
\mathbf 1[\text{依赖版本一致}].
\tag{31}
$$

若执行器只能从摘要猜测其中任一项，状态还不足以安全调度。对高风险动作，三个条件都应由结构化证据确认；对低风险草稿，可以允许带置信度的语义判断。

充分性还包括知道自己缺什么。摘要明确列出未覆盖区间、未知字段和待回源证据，比用流畅语言填满所有空白更可靠。可以计算未知检测率：真实缺失的关键项中，有多少被状态标成未知。漏报会导致无依据行动，适度多报只增加回源成本，两者代价并不对称。

压缩前后的动作一致性是另一项测试。在原始历史与压缩状态上分别让同一策略给出下一步动作和理由。动作不同不一定说明压缩错误：长历史本身可能使模型受噪声影响；此时要由环境验证哪一边更好。若压缩方案经常改变动作，却无法提升成功率或降低成本，它可能只是在制造随机扰动。

收尾阶段用隐藏验收项做盲测。构造者在历史早期放入一条不会频繁出现、但最终必须满足的约束，中途加入大量相关日志，观察多次压缩后该约束是否仍能进入执行与验证。再设置一条后来被撤销的相似约束，检查系统会不会因为重复记忆而复活旧要求。保留与遗忘同时通过，才说明上下文管理真正维护了当前状态。

这类检查还要跨越进程重启。只在同一次推理会话中答对，可能依赖模型尚未清空的内部缓存；重新加载持久状态、换一个等价执行器并恢复环境后仍能得到相同目标与合法动作，才证明信息确实进入了压缩表示。若答案随提示措辞剧烈变化，应继续收紧字段语义和证据约束，不能把偶然生成当成状态恢复成功。

最终验收还应保存失败样本，而非只保留汇总分数。每一次遗漏、错误覆盖和无效回源都要能追到对应压缩版本、来源事件与后续动作，下一轮改进才知道应调整选择策略、接口约束还是执行器。缺少这条诊断链，提升平均分也可能只是换了一批失败对象。

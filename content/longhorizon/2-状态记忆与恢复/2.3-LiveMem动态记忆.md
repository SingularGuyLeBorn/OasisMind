# 2.3 · LiveMem 与推理状态连续性

长时间运行的 Agent 会遇到一个很具体的系统问题：当前上下文不可能无限增长。最近 token 可以留在 KV cache 里，较早内容迟早要被压缩、检索或直接逐出。普通滑动窗口一旦释放旧 KV，模型内部就不再保留那段计算状态；以后突然需要早期约束，只能依赖外部系统重新把文本放回窗口。 [LiveMem](https://arxiv.org/abs/2608.02515) 把缺失能力称为「上下文轮转下的状态连续性」（state continuity under context turnover）：主注意力路径只保留有界工作窗口，同时另有一个固定容量的循环状态，从第一段输入一直延续到请求生命周期结束。早期 token 离开注意力窗口后，模型仍可能通过这个状态使用它们留下的信息。

这条路线与 RAG、文件记忆和知识图谱不冲突。外部记忆保存可定位、可审计的条目，查询时再取回；LiveMem 的内生状态更像一段持续更新的压缩计算。前者适合精确找回“用户在某天说过什么”，后者希望模型在历史文本已经离开窗口后仍保持对会话的整体认识。**固定容量状态不是原文档案，也不提供逐字回放保证。**

## 1. 架构、状态更新与服务生命周期

LiveMem 用主注意力路径保存精确的近期上下文, 用循环支路保存跨窗口的固定容量状态. 两条路径处理不同时间尺度.

理解 LiveMem 需要把双路径、矩阵写入和记忆的因果验证连在一起. 仅看到固定状态的结构, 还不能证明窗口外信息真的经由该状态影响了输出.

**双路径怎样工作**

论文在预训练全注意力模型的注意力层旁增加循环记忆支路。以第 $\ell$ 层、第 $t$ 个 token 为例，归一化后的隐藏表示为 $h_t^\ell\in\mathbb R^d$，有界注意力路径输出

$$
a_t^\ell=\operatorname{Attn}^\ell(h_{\le t}^\ell;C_t),
\tag{1}
$$

$C_t$ 表示当前仍在工作的上下文窗口。循环支路读取上一状态 $S_{t-1}^\ell$，返回记忆输出和新状态：

$$
(r_t^\ell,S_t^\ell)
=\operatorname{GDN2}^\ell(h_t^\ell,S_{t-1}^\ell).
\tag{2}
$$

两路输出相加：

$$
o_t^\ell=a_t^\ell+r_t^\ell.
\tag{3}
$$

注意力路径负责最近上下文的精确 token 访问；Gated DeltaNet-2（GDN2）支路把历史不断压入固定大小状态。每层都有自己的 $S_t^\ell$，这里的“记忆”是进入每层后续计算的隐状态，并不以文末追加文本的形式存在。 LiveMem 的公开实现以 Qwen3 为基座，将记忆支路挂到注意力层，并保留主注意力与 FFN 路径。仓库提供 SFT、RL checkpoint 和 vLLM serving 集成；因此早期“尚未开源”的记录已经过时，不能继续保留。

**固定矩阵状态的写入**

省略层和 head 下标，一条循环 head 的状态可写成

$$
S_t\in\mathbb R^{d_k\times d_v}.
$$

输入产生 key $k_t\in\mathbb R^{d_k}$、value $v_t\in\mathbb R^{d_v}$，以及衰减、擦除和写入门。直观更新分三步：先让旧状态按门控衰减；再检查当前 key 从状态中会读出什么；收尾阶段把预测残差写回与 key 对应的方向。这类 delta-rule 更新可以写成简化形式

$$
\tilde S_t=D_tS_{t-1},
\tag{4}
$$

$$
e_t=v_t-\tilde S_t^T k_t,
\tag{5}
$$

$$
S_t=\tilde S_t+\beta_t k_t e_t^T,
\tag{6}
$$

$D_t$ 是衰减门，$\beta_t$ 是写入强度。论文实际 GDN2 的门控更细，式 (4)–(6) 用来说明计算含义，不能替代实现公式。 假设 $d_k=d_v=2$，初始 $S_0=0$，不衰减且 $\beta=1$。第一条记忆 $k_1=(1,0)^T,v_1=(0,1)^T$ 写入后

$$
S_1=k_1v_1^T=
\begin{bmatrix}0&1\\0&0\end{bmatrix}.
$$

再用相同 key 写入 $v_2=(1,0)^T$。旧状态读取为 $S_1^Tk_2=(0,1)^T$，残差是 $(1,-1)^T$，更新得到

$$
S_2=S_1+k_2(1,-1)
=\begin{bmatrix}1&0\\0&0\end{bmatrix}.
$$

新 value 覆盖了同一 key 方向上的旧 value。如果两个 key 不正交，新写入还会改变旧 key 的读取结果，这就是固定容量状态的干扰来源。门控可以学习何时保留、擦除和写入，却无法让有限矩阵无损保存无限历史。

### 1.1. 为什么只加结构还不够

一个随机初始化的循环支路很容易被主注意力忽略。只要支撑答案的文本仍在窗口中，最省力的训练策略就是继续走原来的 attention path。LiveMem 因此把三部分一起设计：上下文轮转、面向记忆的后训练和状态感知 serving。 训练时要模拟真实轮转，让早期证据离开主注意力可见范围，而循环状态仍从头更新。此后再要求模型回答依赖早期证据的问题，梯度才会迫使模型把记忆支路变成「承重结构」。如果训练始终保留完整注意力，测试时突然裁掉旧 KV，记忆支路没有学会独立承接历史。

SFT 可以给出“证据已移出窗口但仍需回答”的监督；RL 则能用最终回答奖励继续调整写入和读取行为。训练要求状态保存以后决策仍需要的信息，无须重建所有旧 token。哪些信息被保留由训练分布决定：长期身份与约束被频繁考查，模型会倾向保留；训练中从未追问的细节更容易丢失。

**上下文轮转与服务生命周期**

上下文轮转是训练和推理共同遵守的状态迁移规则，不是任意截掉输入。旧 KV 被释放以前，信息已经经过循环支路更新状态。 要让这套机制在长运行服务中成立，还需保存和迁移会话状态，并明确它与外部记忆的职责边界。

**Context turnover 不是截断输入.** LiveMem 需要区分两种基线。`truncate` 直接删除过早历史，只把保留后缀作为一次新输入处理，循环状态从零开始；`state` 从完整历史连续更新记忆状态，但注意力只保留系统提示与最近窗口。两种设置看到的当前 token 可以相同，前者没有逐出历史留下的状态，后者有。 假设历史共 100k token，活动窗口为收尾阶段 8k。truncate 模式只处理 8k，早期 92k 对模型没有任何影响；state 模式让 100k token 依次更新 $S_t$，随后释放旧 KV，回答时精确注意力仍只覆盖最近 8k。两者的差值可以确认收益是否经过循环状态，并排除证据仍然留在窗口中的干扰。

论文在 LongMemEval 上专门检查支撑证据已经完全离开当前上下文的情况，并通过证据距离分析观察信息能否跨过活动窗口继续影响答案。这类实验支持“状态确实承载了部分有用历史”，却不能推出任意事实都能精确召回，更不能推出状态容量等价于多少 token。

**Serving 生命周期是方法的一部分.** 内生状态必须被 serving 系统当成请求资产。prefill 时，token 一边进入主注意力，一边更新每层 $S_t$；窗口轮转后，旧 KV 页面可以释放，$S_t$ 继续保留；decode 阶段，新 token 继续读取和更新状态。请求被暂停、迁移或恢复时，除了 KV，还要保存循环状态及其位置。 公开实现当前强调的是**单个请求生命周期内**的状态连续性。请求结束后状态会释放，OpenAI 兼容接口也不会自动把一个请求的状态接到另一个独立请求。要把它用于跨会话长期记忆，产品还需定义用户—状态映射、持久化格式、版本升级、删除与隐私策略。

状态大小对历史长度是常数，对层数、head 数和 $d_kd_v$ 则不小。若每层每个 head 都维护矩阵，批服务必须为每条活跃请求持有独立状态。它节省的是随历史长度增长的 KV，而不是把记忆成本变成零。比较吞吐时要报告活动窗口 KV、循环状态、状态迁移和记忆支路计算，而不能只看上下文上限。

**与外部记忆的职责边界.** 外部检索记忆通常经历抽取、存储、索引、查询和回填。它的优势是条目可见、可修改、可删除，能返回来源文本；缺点是检索 query 可能漏掉隐含相关历史，写入策略也会把错误摘要长期保存。LiveMem 每个 token 都自然更新状态，不需要显式决定“这一句是否入库”，适合维持连续语境；代价是内容分布在张量中，难以审计和定点纠正。 两条路线可以组合：外部存储保存用户事实、承诺和高风险约束，提供可核验原文；内生状态承接风格、近期事件形成的潜在语境和难以枚举的统计信息；当前窗口保存眼前需要精确推理的材料。对 Long-Horizon Agent，重要事实不应只存在于不可解释的循环状态里。

删除要求尤其能暴露差异。数据库条目可以按用户请求删除并记录审计；内生状态已经把信息与其他历史混合，当前方法很难证明某个事实被完全擦除。涉及隐私、授权撤销或事实纠正时，外部事实层仍应是权威源，内生状态必须能够重置或从经过清理的历史重放。

**评测与 Long-Horizon 含义**

状态连续不能由模块名称证明，必须让证据退出活动窗口，再检查循环状态是否仍会影响行为。距离、干扰、修订与恢复需要分别控制。 这些实验也限定了 LiveMem 在 Long-Horizon 系统中的角色：它维持计算连续性，但不能替代精确事实、审计和外部恢复。

**怎样评测“状态连续”.** 一个可执行协议至少包含四条曲线。

第一条是证据距离：将关键事实放在位置 $p$，查询放在 $q$，保证 $q-p$ 超过活动窗口，观察准确率怎样随距离变化。第二条是干扰量：在事实与查询之间插入无关信息、相似实体和冲突更新，检查固定状态是否被覆盖。第三条是修订：先写“项目代号 Aurora”，后来明确改为 Borealis，查询应返回新值并避免旧值残留。第四条是恢复：处理中途保存状态，迁移进程后继续，输出应与不中断运行一致。

每组都要比较完整注意力上界、纯截断、外部检索、只有循环结构但未做记忆训练，以及完整 LiveMem。若缺少“未做记忆后训练”的结构对照，不能判断收益来自支路本身还是额外训练数据。 指标应拆开精确事实、对话偏好、长文摘要、程序状态和多步任务约束。论文在某些 QA 任务上表现领先，只说明对应训练与评测分布中的连续性；开放对话、精确 TTL、隐私删除和跨请求恢复需要各自实验。

还要记录活动窗口、总历史长度、循环状态字节、吞吐、首 token 延迟和 decode 延迟。固定容量状态在极长历史上有渐近优势，短历史却可能多付一条支路的计算。技术选择取决于会话生命周期和召回精度要求。

**对 Long-Horizon 系统意味着什么.** LiveMem 的核心启发是把**推理状态的生命周期**从当前上下文窗口中分离出来。一个矩阵无法替代所有记忆，但历史 token 被释放以后，请求仍然可以携带连续计算；这比每轮都把模型当作全新函数调用更接近长时间运行的 Agent。 它同时把新的系统责任带进来：状态属于谁、何时持久化、怎样迁移、版本不兼容怎么办、用户要求删除时如何处理、状态被污染后从哪里恢复。内生记忆提高了连续性，也让错误和过期信息可能在不可见状态中延续。

LiveMem 属于「状态、记忆与恢复」问题：它处理有界工作上下文轮转时怎样带着计算继续前进。它没有提供无限上下文，精确事实、审计、纠错和长期持久化仍需外部状态系统共同完成。

### 1.2. 推导、容量与训练边界

理解固定矩阵状态, 需要把遗忘、擦除、写入与读取逐项算开. 小维度手算能说明状态表示的性质, 却不能替代论文实验.

实验配置、分任务数字和训练消融需要一并核对. 单问题任务、NIAH 与位置上限中的负面结果同样构成方法边界.

**逐项展开 GDN2 状态更新**

论文把单个循环头的状态写成 $S_t\in\mathbb R^{d_k\times d_v}$。先计算遗忘后的状态

$$
\bar S_t=\operatorname{Diag}(\exp(g_t))S_{t-1},
\qquad g_t\le0.
\tag{10}
$$

因为 $g_t\le0$，所以 $0<\exp(g_t)\le1$。若 $g_t=(0,\log0.5)$，原状态两行分别乘以 1 和 0.5，第二行的信息衰减一半。接着形成写入残差

$$
\rho_t=w_t\odot v_t-
\bar S_t^\top(b_t\odot k_t),
\tag{11}
$$

$b_t\in[0,1]^{d_k}$ 控制沿 key 方向擦除多少，$w_t\in[0,1]^{d_v}$ 控制 value 的写入幅度。收尾阶段执行秩一更新并读取：

$$
S_t=\bar S_t+k_t\rho_t^\top,
\qquad r_t=S_t^\top q_t.
\tag{12}
$$

取 $d_k=d_v=2$，为便于手算令

$$
\bar S_t=\begin{bmatrix}1&0\\0&1\end{bmatrix},\quad
k_t=\begin{bmatrix}1\\0\end{bmatrix},\quad
b_t=\begin{bmatrix}1\\0\end{bmatrix},\quad
w_t\odot v_t=\begin{bmatrix}2\\3\end{bmatrix}.
$$

于是 $\bar S_t^\top(b_t\odot k_t)=(1,0)^\top$，$\rho_t=(1,3)^\top$，从而

$$
S_t=
\begin{bmatrix}1&0\\0&1\end{bmatrix}+
\begin{bmatrix}1\\0\end{bmatrix}
\begin{bmatrix}1&3\end{bmatrix}
=\begin{bmatrix}2&3\\0&1\end{bmatrix}.
\tag{13}
$$

若查询 $q_t=(1,0)^\top$，读取结果为 $r_t=(2,3)^\top$。这个例子只展示矩阵运算，不代表真实训练出的门值；它说明更新没有保存原 token，而是把当前 key 与 value 方向写进固定大小矩阵。新信息不断进入时，遗忘、擦除与秩一写入共同决定旧信息是否还能影响输出。 主注意力输出与记忆支路输出相加：

$$
o_t^\ell=a_t^\ell+r_t^\ell.
\tag{14}
$$

论文将记忆支路的输出投影零初始化，因此训练开始时 $r_t^\ell\approx0$，模型行为接近原始注意力骨干；训练再逐渐打开支路。这降低了突然插入新模块对已有能力的扰动，但不保证支路会自动学会承担记忆。论文因此还需要 context turnover 与专门后训练，迫使答案证据离开主 KV 后，损失仍能通过记忆路径训练读写。

**实验数字与适用边界**

[LiveMem v2](https://arxiv.org/abs/2608.02515)于 2026 年 8 月 7 日修订。实验统一采用 Qwen3-4B-Instruct-2507 骨干；多数数据集把活动上下文限制为 32K，Wiki QA 与 LoCoMo 进一步限制为 8K。生成参数为 temperature 0.7、top-p 0.8、top-k 20。对照包括原始 Qwen3-4B、RAG、Recurrent、Context2LoRA、$\delta$-Mem，以及 LiveMem 的 SFT 和 RL 阶段。只有在这些共同条件下，表格中的横向比较才成立。 表 1 显示，LiveMem 并非每个单问题任务都最好。2Wiki 上 Qwen3-4B 为 0.817，$\delta$-Mem 为 0.824，LiveMem-SFT/RL 为 0.768/0.784；Hotpot 上原模型为 0.846，$\delta$-Mem 为 0.853，LiveMem-RL 为 0.772。优势更明显地出现在多问题共享历史的 MQ 设置：2Wiki-MQ 中 LiveMem-SFT/RL 为 0.551/0.587，原模型为 0.336，$\delta$-Mem 为 0.232；Hotpot-MQ 中对应数字为 0.477/0.487、0.329 与 0.226。

这个差异给出比「总体领先」更准确的解释。主注意力仍能直接看见证据时，固定矩阵压缩可能损失精度；历史被多次复用、证据离开活动窗口时，连续状态才显示价值。LongMemEval-S 的证据分组实验进一步报告：证据完全移出活动窗口时，LiveMem 比无历史访问的基线高出超过 10 个百分点；随证据距离增加，准确率略降但没有在一次 eviction 后立刻归零。论文没有据此声称逐 token 无损记忆。

附录的 needle-in-a-haystack 结果尤其重要。256K materialized context 下，needle 仍可由注意力直接访问，多数变体接近上限，LiveMem 没有系统性收益；32K 有界上下文下，几个系统都得到相同的低分。也就是说，当前固定容量状态不能可靠重建任意、事先不知道会不会重要的稀疏字符串。它更像有损的行为状态，不是档案库。 论文还明确限制输入最多处理到 256K token。虽然循环状态和活动 KV 的内存大小不随更早历史增长，Qwen3 骨干的 RoPE 配置最大位置为 262,144；超过训练与配置范围需要位置外推，质量没有保证。因此「固定容量」描述的是状态空间复杂度，不应改写成已经验证的无限上下文。

## 2. 训练消融告诉了什么

表 3 把可训练容量和课程分开。以 2Wiki-MQ 为例，side-path LoRA 得 0.479，完整训练支路得 0.551，完整支路再给主路径加 LoRA 得 0.520；但 LoCoMo 上三者分别为 0.256、0.234、0.220。不存在一个配置在所有任务都占优，论文对「完整支路更稳定」的解释是跨任务综合判断，不是逐列胜出。 训练混合也不是数据越多越好。Direct mixture 在 2Wiki-MQ 为 0.439，rebalanced mixture 为 0.452，先用长文本 warmup 再平衡为 0.479；LongMemEval-S 对应 0.298、0.326、0.362。作者解释，长文本 QA 占比过高时，模型可能不必依赖高精度记忆；直接删减又不足以先打开支路，所以采用先 warmup、再强化记忆要求的课程。

这组消融支撑一个工程判断：记忆模块能否存在、能否被训练使用、能否在证据退出窗口后继续承担信息，是三个不同问题。只添加循环层证明了结构存在；只有 turnover 后的因果对照，才能证明输出实际依赖该状态。

**工程容量与因果验证**

模型机制落地后，checkpoint 兼容、状态字节、批处理隔离和删除请求都会成为服务端责任。固定容量不表示多会话存储免费。 对循环状态的干预可以区分相关性与因果贡献。服务协议、容量估算和因果验证共同构成完整的工程闭环。

**服务端需要守住的状态协议.** 长运行服务至少要把模型权重版本、会话 ID、当前位置、活动 KV、各层循环状态和系统指令版本绑定在同一个 checkpoint 中。恢复时若只载入 $S_t$，却换了支路参数 $\phi$，状态坐标系可能已经不兼容；若位置索引重置，RoPE 与原轨迹也不一致。可定义检查点

$$
K_t=(\operatorname{id},t,C_t,\{S_t^\ell\}_{\ell=1}^{L},
\operatorname{hash}(\theta,\phi),v_{\mathrm{prompt}}).
\tag{15}
$$

恢复前逐项匹配，任何不兼容都应显式迁移或从较早可重建状态开始，不能静默加载。 删除请求同样不能只删外部聊天文本。用户要求遗忘某段历史时，该信息可能仍影响循环矩阵；当前方法没有提供从 $S_t$ 中精确减去某段语义的一般操作。严格删除需要从删除点之前的 checkpoint 重放剩余合法历史，或终止旧状态并开启新生命周期。前者成本高，后者会丢失其他记忆，这正是内生有损状态的治理代价。

因此实际 Agent 更适合采用双层方案：外部状态保存精确目标、权限、事实、来源和审计；LiveMem 一类内生状态维持连续的背景影响。外部层负责可编辑、可删除与可追责，内生层负责低固定容量的在线连续性。两者发生冲突时，以当前环境和外部验证事实为准，不能让不可解释的 latent state 覆盖显式约束。

**容量与计算量怎样估算.** 单个循环头的状态含 $d_kd_v$ 个标量。若有 $H_m$ 个记忆头、$L_m$ 个带记忆支路的层，每个标量占 $b$ 字节，则仅矩阵状态约占

$$
B_{\mathrm{state}}=L_mH_md_kd_vb.
\tag{16}
$$

例如 $L_m=32,H_m=8,d_k=d_v=128$，使用 2 字节精度时，状态为

$$
32\times8\times128\times128\times2
=8{,}388{,}608\text{ bytes}\approx8\text{ MiB}.
\tag{17}
$$

这个数不含活动 KV、门控中间量、批处理 padding 和框架开销。它只说明循环状态对历史长度是常数；会话数增加时，服务端仍需为每个活跃会话保存一份。十万个并发会话即使每份只有 8 MiB，也无法全部常驻 GPU，必须设计 CPU、磁盘分层与淘汰策略。 每个 token 的秩一更新 $k_t\rho_t^\top$ 需要约 $d_kd_v$ 次乘加，读取 $S_t^\top q_t$ 也需要同阶运算，所以单头时间复杂度约为 $O(d_kd_v)$。标准注意力在固定窗口 $W$ 下每 token 读取历史的相关部分约为 $O(Wd)$。LiveMem 没有消除主注意力成本，而是在有界 $W$ 之外增加固定状态支路；窗口越短，精确近邻信息越少，窗口越长，KV 成本越高。系统应把准确率、状态字节与吞吐放在同一张曲线上选点。

批处理还要求每条序列携带自己的 $S_t$。序列完成、暂停或迁移时，状态必须与正确的会话槽位绑定；一次 batch 重排若把两条会话的状态交换，输出可能语法正常却被另一用户历史污染。这类错误很难靠模型自检发现，因此服务层需要会话 ID、状态校验和隔离测试。

**如何做因果验证.** 仅观察加入 LiveMem 后分数提高，仍不能证明答案来自循环状态。更强的验证是在证据退出窗口后，对 $S_t$ 做干预。第一种是清零状态，若准确率降到截断基线，说明状态是必要路径；第二种是在相同当前上下文下交换两条样本的状态，若答案随状态中的事实改变，说明模型确实读取它；第三种只遮蔽与目标证据相关的写入区间，检查下降是否具有内容选择性。 设完整系统准确率为 $A_{\mathrm{full}}$，清零状态为 $A_{0}$，保留状态但不让历史退出窗口为 $A_{\mathrm{visible}}$。可以报告状态贡献差

$$
\Delta_M=A_{\mathrm{full}}-A_0.
\tag{18}
$$

$\Delta_M>0$ 说明在该数据与干预下状态有帮助，不表示其中存有可读的原文，也不表示所有历史都被保留。交换实验还要防止分布外状态导致模型普遍退化，应设置同标签与异标签交换对照。 对修订事实，先输入旧值 $u$，后输入新值 $v$，证据均移出窗口，再分别询问当前值与历史值。理想系统对当前查询回答 $v$，对审计查询能在外部日志中找到 $u$；内生状态不必独自承担二者。若回答仍是 $u$，说明擦除或新写入不足；若随机漂移，则可能是压缩容量或读取选择失败。把错误按这三类分开，比一个总准确率更能指导训练。

**一次请求中的状态时间线**

官方仓库对生命周期给出了很清楚的边界：LiveMem 状态在同一请求内持续，当前 OpenAI-compatible API 不会自动把它复用到下一次独立请求。单次输入还受 262,144 token 的位置范围约束。它解决的是请求内部发生 context turnover 时的连续计算，不等同于跨天账户记忆。

```text
请求开始
  S_0=0
    │ prefill: 历史 token 逐步写入 S_t
    ▼
活动 KV 达到 8K/32K
    │ 旧 KV page 释放，S_t 继续保留
    ▼
逐 token decode: attention window + recurrent state
    │
    ▼
请求结束 → S_t 释放
```

`state` 模式让完整历史持续更新循环状态，注意力只保留 system sink 与最近窗口；`truncate` 模式由客户端先删除旧历史，服务器从零状态处理留下的后缀。两种模式若使用相同的 `window_size`，模型可见的精确 KV 数量相似，历史是否进入循环状态却完全不同，因此它们构成直接对照。 服务端必须把 memory cache 与 KV cache 绑定在同一个请求身份上。Prefill 完成后若 decoding worker 迁移，迁移内容至少包含层级 memory state、位置计数、system sink 与活动 KV 页映射。只迁 KV 会丢掉早期历史影响；只迁循环状态会丢掉最近 token 的精确上下文。

**状态更新的数值直觉.** 将单头状态简化为 $S_t\in\mathbb R^{d_k\times d_v}$，当前 key 为 $k_t$，value 为 $v_t$。模型先读取旧状态对当前 key 的预测：

$$
\hat v_t=S_{t-1}^{\top}k_t.
\tag{19}
$$

残差为 $r_t=v_t-\hat v_t$，再按写门 $\beta_t$ 更新：

$$
S_t=S_{t-1}+\beta_t k_tr_t^{\top}.
\tag{20}
$$

假设 $d_k=d_v=2$，初始状态为零，$k_1=(1,0)^\top,v_1=(2,1)^\top,\beta_1=0.5$，则：

$$
S_1=
\begin{bmatrix}1&0.5\\0&0\end{bmatrix}.
\tag{21}
$$

下一次用同方向 $k_2=(1,0)^\top$ 读取，得到 $\hat v_2=(1,0.5)^\top$。若目标 value 仍为 $(2,1)^\top$，残差只剩 $(1,0.5)^\top$，再次写入会逐渐逼近目标。若新事实要求不同 value，残差方向改变，状态会沿相同 key 方向修订。真实 GDN2 还含衰减、擦除和多头门控，式 (20) 只是帮助跟算 delta rule 的核心。 固定矩阵会产生干扰。两个语义不同的 key 若方向接近，它们的秩一更新落在相似子空间，读取时可能混合。提高维度、学习更好的 key 与门控能缓解，却无法让固定容量无损保存无限历史。状态连续意味着旧信息仍能影响计算，不保证逐字回放。

**Serving 资源构成**

官方仓库当前 vLLM 插件锁定 `vllm==0.19.1`，支持 8K 与 32K 活动窗口。Hugging Face quick check 可以显式创建 GDN2 cache，适合功能验证，却没有 vLLM 路径的 paged-KV eviction；评测上下文轮转必须使用真正释放旧 KV 的 serving 路径，否则早期证据仍可能留在注意力里。 延续式 (16) 的示例，每请求 memory state 约 8 MiB。若 1000 个活跃请求全驻 GPU，仅循环状态约需 7.8 GiB；再加 32K KV、模型权重、激活与调度缓存，内存压力远高于这一个数字。暂停会话若迁往 CPU，恢复时又会产生 PCIe 或网络传输延迟。 设每份状态大小为 $B_s$，活跃请求数为 $N_a$，暂停请求数为 $N_p$，GPU 与 CPU 驻留比例分别为 $q_g,q_c$，则两层存储约为：

$$
B_{GPU}=q_gN_aB_s,
\qquad
B_{CPU}=(q_cN_a+N_p)B_s.
\tag{22}
$$

若服务允许断点恢复，还要给磁盘 checkpoint 计算写放大。每生成一个 token 都保存状态会产生巨大 I/O；只在轮次边界、上下文轮转或显式暂停时保存，恢复点更稀疏。选择取决于单次请求价值与重算成本。 吞吐还受双路径计算影响。每层输出为：

$$
o_t=o_t^{attn}+o_t^{mem}.
\tag{23}
$$

注意力路径随活动窗口增长，memory 路径对历史长度保持常数，但增加固定矩阵读写。应报告 prefill token/s、decode token/s、首 token 延迟、峰值显存和并发请求数。只报告 KV 节省无法判断新增分支是否把算力瓶颈推到矩阵更新。

**训练资源与可复现边界.** 官方 README 已公开两阶段 SFT、checkpoint 导出、GRPO 和评测入口。论文 SFT 使用两台节点，每台 8 张 A800-80GB，固定 64K token pack：第一阶段训练 100 step，第二阶段从前一 checkpoint 恢复后训练 500 step。Paper-scale RL 使用两台 8-GPU trainer 节点、一台 8-GPU rollout 节点，另有 2-GPU judge 服务。 这组资源说明开源代码不等于低成本复现。单机可以运行 `run_grpo_dev.sh` 做两 GPU、五步的开发检查，却不能把它的吞吐和论文规模等同。缩小节点数时，pack size、梯度累积、并行策略和 rollout 并发都会改变；报告应列出总训练 token、有效 batch 与墙钟时间，而不只写训练 step。

默认训练冻结 attention 与 FFN 主路径，完整训练循环记忆支路；LoRA 只是框架提供的可选参数组，并非默认 recipe。复现时若启用 LoRA，已经改变可训练参数与比较条件。导出工具会把训练后的 memory branch 合到冻结 backbone 上，并生成 Hugging Face/vLLM 可加载 checkpoint。

### 2.1. 状态治理和失败边界

循环状态缺少可读 schema，工程系统无法直接列出其中保存了哪些用户事实。状态串线、错误修订和隐私删除因此比外部数据库更难处理。会话 ID 与状态 checksum 能发现传输错配，却无法证明语义内容正确。 多租户服务必须禁止状态复用。一个请求结束后，GPU/CPU 缓冲区在交给下一请求前要清零；批处理重排要通过 request ID 绑定每层 cache；故障恢复只能加载同一模型版本与状态 schema。用另一 checkpoint 读取旧状态，即使 shape 相同，key/value 表示也可能已经变化。

长期运行还会遇到状态饱和。新信息持续写入固定矩阵，旧方向被衰减或覆盖。可以按证据离开窗口后的距离分桶测准确率，观察性能何时下降；也可以在输入中周期性修订同一事实，测旧值残留。总体平均分会把远距离和高冲突样本混在一起，无法判断容量边界。 LiveMem 与外部检索组合时，权威事实仍由外部层提供。循环状态可以让模型记得「此前讨论过 Aurora 项目」，需要删除、审计或精确引用时则回到版本化记录。内生状态承担连续影响，外部状态承担可编辑事实，这个分工也为隐私删除留出可执行路径。

**训练与部署必须看到同一种轮转**

训练时若让完整历史始终留在注意力窗口，模型会走最省力的精确注意力路径，循环状态即使存在也可能闲置。LiveMem 使用动态 attention mask 模拟 context turnover，使旧证据在训练中离开可见窗口，同时仍参与循环状态更新。部署端再真正释放对应 KV page，训练与 serving 才共享同一可见性边界。 设证据位于 token $i$，查询位于 $j$，活动窗口为 $W$。当 $j-i>W$ 时，主注意力无法直接访问证据，回答依赖 memory state 或外部检索：

$$
p(y_j\mid x_{1:j})
=p(y_j\mid x_{j-W:j},S_{j-W}).
\tag{24}
$$

若训练 mask 仍允许注意力偷看 $x_i$，损失下降也无法证明 $S$ 学会了承载证据。评测同理：仅在 prompt 文本上声明窗口为 8K，却没有从 KV cache 中移除旧页，模型仍可能通过实现细节访问早期 token。 动态 mask 的采样分布会决定记忆偏好。训练总把证据放在窗口外很近的位置，模型可能只学会短距离延续；部署运行数十万 token 后，状态干扰更强。应按 evidence distance 分桶，并报告超过 1、2、4、8 个窗口长度后的表现。官方论文的 evidence-distance analysis 正是在检查信息离开活动窗口后还能影响多远。

**SFT 与 RL 分别补什么.** SFT 用带答案的数据教 memory branch 写入和读取有用信息。官方 recipe 分两阶段：第一阶段在长文本混合数据上建立基础连续性，第二阶段加入 QA、分类、多问题和长文本数据，让状态更贴近下游决策。主 attention/FFN 路径冻结，减少新增支路破坏基座能力的风险。 RL 在 SFT checkpoint 上继续优化最终回答。组内八条 response、无 KL penalty、0.20/0.28 clipping 和 token-mean loss 是官方开发脚本当前公开的配置，论文规模的资源布局更大。无 KL 意味着稳定性更多依赖初始化、clip 与数据；换数据或扩大训练步数时，不能假定同一配置天然稳定。

终局 reward 仍很稀疏。回答正确会共同强化写入、保留和读取行为，却难指出哪个 token 的记忆操作起作用。可以用状态干预做训练后诊断：清零某段状态、交换状态或屏蔽某个写入区间，再观察 reward 变化。诊断结果不必直接进入训练，也能判断增益是否真的经过 memory branch。

**并发、轮转与状态几何**

普通 vLLM 调度主要管理 KV block，LiveMem 还要管理每层循环状态。请求从 running 转为 waiting 时，状态可留在 GPU、换到 CPU 或写入磁盘；选择取决于预计等待时间。短暂停留在 GPU 避免传输，长暂停继续占显存则会阻塞新请求。 设 GPU↔CPU 带宽为 $q$ bytes/s，状态大小为 $B_s$，一次换出再换入的理论传输下界为：

$$
T_{swap}\ge \frac{2B_s}{q}.
\tag{25}
$$

8 MiB 状态在 16 GB/s 有效带宽下，纯传输约 1 ms；实际还有同步、序列化、批量碎片和每层 cache 管理。状态很小并不保证切换免费，P99 延迟仍需实测。 调度器还要防止 ABA 问题：会话槽位被释放后又分给新请求，迟到的异步回调若只携带 slot ID，可能把旧状态写进新会话。请求 ID、generation counter 与状态版本三者共同校验，才能拒绝迟到写入。

### 2.2. 仓库状态与复现入口

截至 2026 年 10 月，官方仓库已公开模型实现、训练脚本、数据处理、评测和 vLLM 插件，并提供 `chen-l/LiveMem-SFT` 与 `chen-l/LiveMem-RL` checkpoint 链接。仓库历史仍很短，依赖版本较窄；vLLM 插件面向 0.19.1，Flash Linear Attention 使用仓库 vendored 版本。复现时应锁定 commit 与依赖，不使用浮动最新版替换后仍声称同配置。 最小功能检查用 Hugging Face 路径显式创建 `FLACache`，确认 prefill 与 decode 之间状态保留；窗口轮转与吞吐实验改用 vLLM `state-8k/state-32k` 服务；`truncate` 服务作为无状态后缀对照。三条服务必须使用同一 checkpoint、采样参数和评测集合。

官方评测支持断点续跑，结果默认写入 `results/eval/`。断点恢复时还要保存已运行样本、server 模式、窗口大小和 checkpoint ID；只按样本序号续跑，若中途换了服务配置，会把两套结果拼进一个目录。

**连续状态和历史访问的差别**

RAG、长窗口和摘要主要解决「还能不能看到旧内容」，LiveMem 关注的是「旧内容离开工作窗口后，计算是否仍沿着同一状态继续」。两者容易混在一起，因为问答任务最终都表现为能否回答过去的信息。但它们的系统语义不同。 历史访问要求在需要时找回一段原始或近似原始证据。检索器可以在查询到来后搜索，长窗口则始终保留 token。状态连续性把历史经过递推写进固定容量状态，后续每个 token 都在这个状态上继续计算，即使系统尚不知道未来会问什么。它更像在线滤波，而不是事后查档。

设历史为 $x_{1:t}$，检索式系统在查询 $q$ 到来后计算

$$
R_t=\operatorname{Retrieve}(q,x_{1:t}),
\tag{18}
$$

LiveMem 则持续更新

$$
S_t=F(S_{t-1},x_t),\qquad y_t=G(S_t,W_t),
\tag{19}
$$

其中 $W_t$ 是当前注意力窗口。$S_t$ 在查询出现之前已经形成，因此不能为每个未来问题重新选择最相关片段。固定状态的优势是持续、低延迟和不随历史长度增长；代价是有损压缩和难以回到精确证据。 一个反例能说明边界。用户在十万轮前给出一串随机 128 位密钥，之后从未重复。RAG 若有精确索引可以取回，固定状态必须在有限维连续向量中与所有其他历史竞争，无法保证任意随机串无损保存。相反，长流程中某个变量经过数百次更新，检索单个旧片段还需重放更新，递推状态可以直接保留当前聚合结果。

因此两条路线适合组合。循环状态保存持续演化的任务态、偏好统计和隐变量，外部存储保存精确证据、文件版本和可审计事件。需要回答时，状态提供检索查询和当前语境，外部存储返回原文。只用其中一条，都难同时获得固定成本、精确回溯与可审计性。 评测时应把两类能力拆开。把证据移出窗口但允许外部检索，测的是历史访问；关闭检索，只保留递推状态，才隔离状态连续性。若数据集问题本身提供明显关键词，RAG 占优很正常；若答案依赖多轮累积而没有单一支持片段，递推状态才更可能显出价值。

**GDN2 更新的矩阵几何**

官方实现给出的 GDN2 更新可以写成

$$
S_t=\left(I-k_t(b_t\odot k_t)^\top\right)
\operatorname{Diag}(e^{g_t})S_{t-1}
+k_t(w_t\odot v_t)^\top.
\tag{20}
$$

不同实现对矩阵左右方向的约定可能转置，但三个动作不变：$g_t$ 对旧状态各方向做衰减，$b_t$ 沿当前 key 方向擦除旧关联，$w_t$ 控制新 value 的写入。查询 $q_t$ 再从状态读出 $q_t^\top S_t$。 先看一维简化。令状态为标量 $s_t$，所有 key 为 1，则

$$
s_t=(1-b_t)e^{g_t}s_{t-1}+w_tv_t.
\tag{21}
$$

$g_t<0$ 产生遗忘，$b_t$ 再决定当前地址覆盖多少，$w_t$ 决定写入强度。若三者长期固定，旧值经过 $\tau$ 步的系数为 $[(1-b)e^g]^\tau$。这给出有效半衰期

$$
\tau_{1/2}=\frac{\log(1/2)}
{\log |(1-b)e^g|}.
\tag{22}
$$

高维情形不是每个记忆槽独立。key 方向相近的写入会共享矩阵子空间，擦除一个地址也会影响相似地址。若 $k_i^\top k_j$ 很大，两个实体的状态容易串扰；多头和逐层状态提供更多子空间，却没有消除固定容量上限。 状态更新还承担计算路径。某个早期 token 对远期输出的梯度要经过连续 Jacobian 乘积：

$$
\frac{\partial S_T}{\partial S_t}
=\prod_{j=t+1}^{T}
\left(I-k_j(b_j\odot k_j)^\top\right)
\operatorname{Diag}(e^{g_j}).
\tag{23}
$$

谱范数长期小于 1 会让早期影响衰减，接近或大于 1 又可能造成数值不稳。注意力旁路让近期 token 不必完全经过这条长乘积，训练数据则需要迫使远期答案依赖已经退出窗口的信息，否则模型会一直走更容易的注意力路径。 写掩码提供了一个容易忽略的控制。官方代码允许将 $g_t,b_t,w_t$ 同时置零，使 $S_t=S_{t-1}$，当前 token 仍能读取状态。连续扫描模式让所有 token 更新记忆；选择性写入模式只在将被驱逐的区域开放写门。前者获得完整在线轨迹，后者减少近期内容重复进入注意力与状态两条路径。二者对应不同的训练分布，不能只在部署时随意切换。

## 3. 固定容量到底固定了什么

LiveMem 的状态大小与历史 token 数无关，但会随层数、头数、key/value 维度和数据类型增长。若每层有 $h$ 个头，每头状态矩阵为 $d_k\times d_v$，模型有 $L$ 层，元素字节数为 $b$，单请求状态量级为

$$
M_{state}=Lhd_kd_vb.
\tag{24}
$$

若采用 BF16，$b=2$。这个公式还未计入门控缓存、对齐和框架对象，但能看出它对序列长度是常数，对并发请求数则线性增长。服务一千个长会话时，固定容量并不等于免费，只是把增长轴从历史长度换成了活跃请求数。 注意力窗口仍保存 KV。设窗口长度为 $W$，每 token 每层 KV 宽度为 $d_{kv}$，主路径缓存约为

$$
M_{window}=2LWd_{kv}b.
\tag{25}
$$

总请求状态为两者之和。将窗口从 32K 减到 8K 会显著降低 KV，却不改变循环状态；若任务依赖精确近期文本，缩窗可能损害性能。论文同时评测 8K 与 32K，正是在观察固定状态能否补偿更窄工作窗口。 固定状态还不受「位置长度」无限扩展保证。官方仓库明确说明单次输入仍受 262,144 token 的位置范围约束，状态在一个请求生命周期内持续，请求结束后释放，当前 OpenAI 兼容接口也不会自动跨独立请求复用。把它描述成无限上下文或永久用户记忆都会超出实现证据。

容量上限可以用碰撞任务测试。构造 $n$ 个互不相关键值对，逐渐增大 $n$，并让查询发生在键退出注意力窗口之后。若状态维度固定，准确率最终会下降。改变头数或状态宽度，观察拐点是否移动，可以区分容量瓶颈与训练不足。 另一种测试要求保存连续更新的少量变量。即使历史很长，只要充分统计量维度小，固定状态应保持稳定。若这类任务也随长度快速退化，问题更可能在递推稳定性、训练分布或服务状态丢失，而非理论容量不足。

**Context turnover 的可见性协议**

轮转不是在送入模型前截掉前缀。被驱逐 token 必须先经过模型并写入循环状态，随后才从注意力可见集合和 KV 页面中释放。`truncate` 模式把旧历史丢掉并从零状态处理后缀，`state` 模式则保留从完整历史累积出的状态；两者输入窗口看起来同样短，内部计算历史完全不同。 设系统 prompt 长度为 $S$，近期窗口为 $W$，当前查询位置为 $t$。注意力可见集合可写成

$$
\mathcal V_t={1,\ldots,S\}
\cup\{\max(S+1,t-W+1),\ldots,t\}.
\tag{26}
$$

系统 sink 始终保留，普通历史随窗口滑动。循环状态则已经扫描 $1$ 到 $t$。若训练 mask 允许注意力偷看本应驱逐的 token，模型不会学会依赖状态；部署真正释放 KV 后，性能会突然下降。 动态 mask 需要处理 packed sequence。一个训练批次可能打包多个样本，状态和注意力都不能跨样本泄漏。segment ID、sequence ID、chunk ID 与 eviction step 共同决定可见关系；任何一个边界错误，模型可能利用前一条样本的答案，离线 loss 还会显得更低。 轮转发生在 token 边界，工具消息或文档段落却有语义边界。若窗口恰好切在 JSON 或公式中间，注意力只看到后半段，状态需要承担前半段信息。训练若总在整段边界驱逐，部署的任意 token 轮转会形成分布偏移。压力测试应随机改变驱逐位置。

位置编码也没有因 KV 释放而重置。近期窗口中的 token 仍携带原请求里的绝对或旋转位置；把后缀重新编码成从零开始的 `truncate` 基线，会改变模型看到的位置分布。比较两种模式时必须区分「是否有状态」与「是否重新编号」。

**为什么要冻结主干**

官方训练默认冻结 Qwen3 的注意力和 FFN 主路径，只训练新增循环记忆分支。这样可以把变化集中在记忆能力，减少对原有短上下文能力的破坏，也显著降低训练参数量。输出采用逐层相加：

$$
o_\ell=o_{\ell}^{attn}+o_{\ell}^{mem}.
\tag{27}
$$

初始记忆分支若输出接近零，模型行为接近原主干；训练逐渐学会在注意力缺失证据时提供修正。这比替换全部注意力层更容易从现有 checkpoint 起步。 冻结也限制了协同适配。主干查询表示原本没有为 GDN2 状态设计，新增分支只能学习如何读取既有 hidden state 并把结果加回去。若两个分支尺度不匹配，记忆输出可能被残差流淹没，或过强地扰动近期推理。归一化、门控和训练阶段需要控制这个尺度。

两阶段 SFT 的意义由数据职责决定。第一阶段用长数据让分支学会基本写入与跨窗口读取；第二阶段混合 QA、分类、多问题和长文本，使状态服务于不同输出形式。仓库给出的 100 步与 500 步属于具体复现配方，不能推广成普遍最优阶段长度。 RL 继续优化「何种记忆最终有用」。仓库开发配置使用 GRPO、每组八个响应、无 KL、非对称裁剪 0.20/0.28 和 token-mean loss。终局奖励可以推动状态保留支持答案的信息，但也可能学习 judge 偏好；若奖励只关心回答，不检查权限和事实来源，记忆分支没有梯度去保存这些边界。

冻结主干让 RL 的可调空间更窄，可能降低灾难性漂移，也可能把所有纠错压力压在小分支上。对照实验应包含只训分支、分支加少量主干 LoRA、全量训练，并分别测短窗口基准、状态任务与安全约束，而非只看长记忆平均分。

### 3.1. 状态连续性如何获得训练信号

只把长文送进模型并不足以训练记忆。若支持证据仍在活动窗口，注意力路径可以直接回答，循环分支即使完全无用也能降低 loss。训练样本必须让关键证据在回答时退出窗口，使记忆成为 load-bearing 路径。 可以把一条样本拆成证据 $E$、干扰历史 $D$ 和查询 $Q$。选择窗口 $W$ 使

$$
\operatorname{dist}(E,Q)>W,
\tag{28}
$$

同时保证 $E$ 在早期确实经过状态更新。若直接截掉 $E$ 再从零状态推理，任务不可解；若保留连续状态，则答案仍可能恢复。这对照隔离了状态贡献。 困难负例同样重要。放入早期陈述「项目代号是 Aurora」，后来明确改成 Borealis，查询当前代号。状态若只会累积关联，可能吐出旧值；GDN2 的擦除门需要学会覆盖。再加入两个相似实体，测试 key 碰撞和作用域绑定。 多问题样本检查状态是否能反复读取。第一次查询不应耗尽记忆，后续问题仍要访问不同早期事实。若训练每条轨迹只在末尾问一次，模型可能形成针对单个终点的压缩，而非可持续状态。

证据距离分析要控制混杂。距离增大通常也意味着干扰 token 更多，性能下降可能来自容量竞争，也可能来自梯度路径变长。固定写入数量只插入无写掩码的空白，和增加真实干扰写入是两种实验；前者测时间衰减，后者测容量干扰。

**换入换出、失效模式与训练信号**

循环状态属于请求，服务端必须保证下一段 token 读取同一请求的上一版状态。若批处理重排后把状态行错配，模型会出现跨用户污染。状态对象需要稳定 request ID、层级结构版本和已处理 token 位置。 抢占时，KV 页面与循环状态可能一起从 GPU 换出。恢复必须原子地装回匹配版本；只恢复 KV、忘记循环状态，会让近期对话正常而远期记忆消失，这类错误很难从单轮健康检查发现。只恢复状态、KV 窗口错位，则近期精确文本和位置关系异常。

并发调度的容量约束为

$$
N_{active}(M_{state}+M_{window})+M_{weights}+M_{workspace}
\le M_{GPU}.
\tag{29}
$$

固定状态提高了单请求常驻成本，但释放远期 KV 又降低历史相关成本。短请求占比高时，新增状态可能净增显存；长请求占比高时，窗口上界带来可预测容量。吞吐比较必须按真实长度分布进行。 请求结束后状态释放，重新发起相同用户的 API 请求不会自动继承。若产品需要跨会话记忆，必须显式序列化状态或将关键信息写入外部存储。直接持久化模型内部矩阵还涉及 checkpoint 兼容、隐私删除和跨版本迁移，官方当前接口没有承诺这些能力。

故障恢复也需要边界。状态只在 GPU 内存中，进程崩溃后无法重建；定期 checkpoint 能恢复，却增加复制成本。若原始事件日志仍在，可以重新 prefill 全历史生成状态，代价随历史增长。系统需要按会话价值选择不恢复、周期快照或事件重放。

**一组容量与延迟手算**

假设一层每个请求的循环状态是 16 个头，每头 $128\times128$，模型 36 层，使用 BF16。按式 (24)，状态约为

$$
36\times16\times128\times128\times2
=18{,}874{,}368\text{ bytes},
\tag{30}
$$

约 18 MiB。若还需要双缓冲或临时 scan workspace，实际峰值会更高。100 个并发长请求仅状态就约 1.8 GiB。 再假设每层每 token 的 K 和 V 合计宽度为 2048 个 BF16 元素，32K 窗口的缓存为

$$
36\times32768\times2048\times2
\approx4.5\text{ GiB/request}.
\tag{31}
$$

这个示例参数未必等于论文模型的真实 GQA 配置，只展示量级关系：窗口 KV 往往远大于固定状态。缩到 8K 后约 1.125 GiB，节省量远超 18 MiB 状态，但准确率能否接受要由任务决定。 计算方面，GDN2 每个新 token 都做状态读写，单步成本与 $d_kd_v$ 成正比，不随历史长度增长。主注意力 decode 仍需读取 $W$ 个 KV，成本随窗口长度线性。缩小 $W$ 会降低注意力带宽，新增分支提供常数开销，因此历史足够长时总成本可能下降。 prefill 使用并行 scan 可以减少递推串行深度，但常数和内存流量不能忽略。对短输入，新增分支只增加工作；对超过窗口的长输入，释放 KV 的服务收益逐步出现。延迟曲线应该随长度绘制，单一平均值会混淆两种区域。

## 4. 失败模式与可证伪实验

第一类失败是状态根本没有被使用。将循环状态在证据退出窗口后清零，若答案几乎不变，可能存在数据泄漏、注意力仍能看到证据或任务可由先验猜中。清零实验应逐层、逐时间进行，定位哪些状态真正承载信息。 第二类失败是状态污染。插入大量与目标实体相似的键值，再比较准确率随干扰数量变化；交换实体名称，检查模型是否依赖位置或表面频率；后来撤销旧事实，观察擦除是否完成。只测单一事实的长距离回忆无法暴露这类问题。

第三类失败是服务连续性中断。主动触发批次重排、GPU 抢占、KV 页面驱逐和请求暂停，比较中断前后同一状态校验和与输出。若离线 Hugging Face 推理正常、vLLM 服务失败，问题在状态生命周期，而非模型权重。 第四类失败是训练与部署 mask 不一致。用相同轨迹分别在训练式完整张量 mask 和真实逐块 serving 中运行，比较每层状态与 logits。误差应在数值容忍范围内；随着块数累积扩大的差异说明并行 scan、位置或驱逐边界不一致。

第五类失败是短上下文能力受损。在证据完全位于活动窗口内，LiveMem 应接近原主干；若明显下降，记忆分支正在对无需记忆的情况过度干预。可以关闭分支读出但保留写入，判断问题来自训练改变的输出还是服务缓存。 最终实验矩阵至少包含窗口内、窗口外、覆盖更新、多实体碰撞、多问题复用、进程暂停恢复和跨模式一致性。每组同时报告任务成功、状态显存、KV 显存、prefill/decode 延迟与并发吞吐。这样才能判断连续状态带来的能力是否值得额外常驻成本。

**应当保留的结论**

LiveMem 的贡献可以落在一条清楚的链上: 历史 token 先经过正常模型并写入 GDN2 状态, 注意力只保留系统 sink 与近期窗口, 旧 KV 页面随后释放; 新增支路在每一层把固定状态读出并加回主路径; SFT 与 RL 通过窗口外证据任务迫使这条支路承担预测责任; 服务系统则让状态与请求生命周期一起迁移.

这套设计提供固定历史相关显存和持续在线计算, 但不提供任意历史的无损访问, 也不会自动跨请求持久化. 状态矩阵容量有限, 远期影响受到递推稳定性和写入干扰约束, 精确证据仍适合外部存储. 这些边界也划分了 LiveMem 与 RAG、摘要、长窗口和 Harness 状态各自承担的职责.

**从状态空间模型看 LiveMem**

把 GDN2 放在每层注意力旁边，可以视为输入依赖的状态空间模型。传统线性状态空间写成

$$
s_t=As_{t-1}+Bx_t,\qquad y_t=Cs_t+Dx_t.
\tag{32}
$$

LiveMem 的 $A_t,B_t,C_t$ 都由当前 hidden state 动态生成，并且状态是矩阵而非单一向量。输入依赖让模型可以在事件边界快速遗忘、在稳定阶段缓慢更新，也让稳定性分析比固定矩阵更难。 若把状态矩阵向量化，式 (20) 仍可写成

$$
\operatorname{vec}(S_t)=A_t\operatorname{vec}(S_{t-1})+u_t.
\tag{33}
$$

远期信息的保留由转移乘积 $A_T\cdots A_{t+1}$ 决定。不同输入会选择不同子空间的收缩、擦除与写入，因此不存在一个全局固定半衰期。论文里的证据距离曲线测到的是数据分布下的平均行为，不能证明每种信息都能维持同样距离。 每层都有独立状态，使记忆形成层级。低层可能保留词形、实体和局部模式，高层更接近任务语义，但这只是可检验假设。可以训练线性 probe 或执行层级清零：只清低层、只清高层、清连续层段，观察事实回忆、顺序判断和聚合任务分别受何影响。

逐层相加意味着记忆分支通过残差路径影响后续所有层。第 $\ell$ 层状态读出 $r_{\ell,t}$ 不只改变当前 logits，还改变第 $\ell+1$ 层生成 key、query 与写门的输入。因此单层错误可能被后层放大或修正。只查看最终一层状态无法解释全部记忆路径。 状态空间视角也说明为什么固定状态擅长充分统计量。若任务只需要累计计数、最近一次值、有限状态机位置或低维信念，存在小状态递推精确求解；若任务要求任意内容寻址，状态维度必须随可区分项目数增长，或接受碰撞。这条界线比「能记多少 token」更准确。

### 4.1. 写入、读取与覆盖的可辨识性

观察最终答案，很难知道失败发生在写入、保存还是读取。证据可能从未进入状态，可能写入后被干扰覆盖，也可能仍在状态中却没有被当前 query 读出。三种故障需要不同修复。 写入测试在证据 token 之后立即冻结状态，并用多个标准查询读取。若此时已经无法恢复，问题在写门或表示。保存测试把同一冻结快照复制到不同长度的干扰序列，比较状态变化；读取测试固定状态，只改变查询措辞和位置，观察信息是否可访问。

可将准确率粗略分解为

$$
P(\text{correct})
=P(W)P(P\mid W)P(R\mid W,P)P(O\mid W,P,R),
\tag{34}
$$

$W$ 表示正确写入，$P$ 表示保持，$R$ 表示正确读取，$O$ 表示读出后完成输出。终局分数只观察四项乘积。通过中间 probe、状态替换和受控查询，才能近似定位哪一项下降。 覆盖更新尤其能区分简单累加与可修改记忆。先写「A 的值为 3」，退出窗口后再写「A 改成 7」，最终既询问当前值，也询问历史值。如果任务只要求当前状态，旧值应被抑制；若同时要求审计历史，固定状态需要保留两个时间版本，容量与表示要求更高。

状态交换实验也很有用。两条前缀只在一个事实不同，运行到相同边界后交换其循环状态，保持近期窗口不变。若回答随状态交换，证明信息确实位于循环分支；若回答仍跟随窗口，可能有残留证据或模型先验。交换必须在每层全部状态上一致进行，漏一层会得到混合结果。

**RL 奖励怎样塑造记忆**

在 LiveMem 中，早期写门动作与很久之后的答案奖励相连。某个 token 是否写入、写多强、覆盖哪个方向，都没有直接标签。GRPO 比较同一问题的多条响应，但这些响应可能共享相同前缀状态，也可能在 rollout 中产生不同中间文本并继续写状态。 若一组八个响应从同一冻结前缀状态开始，组内优势主要训练读取、推理和生成；前缀写入已经完成，无法从这次差异获得反事实信用。若完整轨迹分别 rollout，状态更新也变化，奖励能影响写入策略，但方差更高。训练实现需要明确状态在哪个边界复制。

无 KL 配置让记忆分支有更大更新自由，同时主干冻结限制行为漂移来源。非对称裁剪 0.20/0.28 对负、正更新提供不同边界，具体方向要按实现定义确认；它不能自动解决长延迟信用。奖励若只在答案末端给出，所有参与 token 共享粗粒度信号。 可以加入不改变最终目标的诊断奖励，例如窗口外证据一致性、更新后旧值抑制和状态清零敏感度。但辅助奖励必须防止捷径。奖励状态中可线性解码某个实体，模型可能保存表面标识而忽略真正任务；奖励逐字回忆会挤占聚合状态容量。

一个可证伪的 RL 对照是固定 SFT checkpoint，只改变 rollout 是否让证据退出窗口。若 RL 收益主要出现在窗口内问题，它更可能优化一般回答风格；若只在窗口外提升且清零状态后收益消失，才有较强证据说明奖励塑造了记忆支路。 还要防 judge 泄漏。judge 根据参考答案打分时，模型可能从问题分布猜答案，不依赖历史。构造实体随机化、答案均衡和不可由世界知识推断的键值，可以降低这种捷径。论文分数要结合这类任务构造理解。

**不确定性、安全与信息上限**

递推状态容易把多次观测混成一个确定表示，但长程 Agent 经常处理互相冲突或尚未确认的信息。若状态只保存最可能值，后续模型可能忘记它原本是猜测，也不知道何时应复核。 从贝叶斯滤波看，状态应近似历史下的信念分布

$$
b_t(z)=p(z\mid x_{1:t}),
\tag{35}
$$

新观测到来后按似然更新。神经状态未必显式表示概率，却可以通过多个方向编码候选、置信度和来源可靠性。训练数据若所有陈述都无冲突，模型没有机会学到这类更新。 可以设计三步任务：早期弱来源说答案 A，中期强来源说 B，末尾询问答案与置信理由。再交换来源可靠性，正确选择应改变。只按最近值覆盖会忽略来源，按频率累计又可能被多个弱来源淹没。

不确定状态与擦除门有关。新证据并非总要完全删除旧值：互相矛盾时应保留冲突，明确纠正时才覆盖。GDN2 提供连续擦写能力，但其语义需要数据学习，架构本身没有内置「事实」「猜测」或「授权」类型。 外部 Harness 可以保存显式置信与来源，循环状态负责让这些信息持续影响生成。若两者冲突，应以可审计外部状态为准，并重新注入当前窗口。把内部状态视为权威数据库，会让不可解释向量承担它无法证明的责任。

### 4.2. 安全、隔离与遗忘

循环状态能跨越窗口保留信息，也意味着从可见 prompt 删除文本未必让影响消失。用户要求遗忘某段内容时，释放 KV 页面还不够；已经写入 GDN2 的表示可能继续改变输出。当前请求若必须彻底清除，只能重建一个未扫描该内容的状态，或结束请求并从合规历史重新开始。 选择性擦除单个事实更困难。状态是叠加的连续表示，没有稳定地址保证某个用户字段独占一个方向。对某个 key 施加擦除可能伤及相似记忆，也无法证明所有层都不再编码该信息。产品不能把一次负向写入宣称为可验证删除。

租户隔离要求状态永不跨请求错配。批处理张量中的一个索引错误就可能把另一用户的历史注入当前回答。测试应使用高辨识度 canary，在大量请求抢占、重排和恢复后检查是否泄漏；日志则避免打印原始状态或可逆的用户信息。 模型升级会改变状态语义。旧 checkpoint 产生的矩阵不能假设由新权重正确读取，即使形状相同。跨模型版本的请求需要固定模型到结束、重放历史生成新状态，或提供经过验证的状态迁移器。直接加载会让新权重读取未经验证的旧状态。

内部状态也会受到提示注入影响。外部文档中的恶意指令一旦写入，原文退出窗口后仍可能持续。来源标签在神经状态里没有强隔离，关键权限和指令层级仍应由外部控制面每轮提供，不能依赖循环分支自己长期记住。

**固定状态的信息上限**

连续矩阵使用浮点数，看起来可以编码无限多信息；实际可用容量受到精度、噪声、可训练性和鲁棒间隔限制。把每个 BF16 元素机械地按 16 bit 计算，只能得到存储上界，无法代表模型能可靠写入并读出的语义容量。 设状态包含 $D$ 个数值元素，每个元素在噪声和量化下可稳定区分 $K$ 个水平，粗略信息上界为

$$
I(S)\le D\log_2K.
\tag{36}
$$

$K$ 远小于浮点格式的全部码字，因为递推乘法会压缩动态范围，相邻表示还需留出分类间隔。训练也未必找到接近编码上界的方案。这个式子只说明容量有限，不能用来精确换算「一个状态等于多少 token」。 随机键值任务提供经验容量曲线。令每个 value 从大小为 $V$ 的集合均匀采样，正确恢复 $n$ 个独立值至少需要约 $n\log_2V$ bit。逐渐增大 $n$，准确率从平台进入下降区，拐点给出特定训练和读取协议下的有效容量。改变状态宽度 $D$，若拐点近似线性移动，容量解释更可信。

自然语言历史具有高度冗余，所需充分状态可能远小于 token 数。十万 token 都在围绕五个实体更新，固定状态可以压得很好；一万 token 包含数千个随机编号，反而更难。因此证据距离和历史长度都不能单独代表容量压力，需要同时报告独立状态项数量。 容量还会在层与头之间重复。每层都扫描相似输入，不意味着容量简单相加，因为后层状态依赖已混合的 hidden state，多个头也可能学到冗余特征。消融一部分头或层，再观察能力是否平滑下降，可以估计冗余与专门化。

**Chunk 并行与逐 token 递推必须一致**

训练长序列时逐 token Python 循环不可接受，GDN2 通常用 chunk 或并行 scan。数学上它们都应实现相同递推，数值上却可能因运算顺序、精度和边界初始化产生差异。部署若使用另一种 kernel，微小偏差会在长轨迹里累积。 对仿射递推 $s_t=A_ts_{t-1}+u_t$，一个块 $[a,b]$ 可以合成为

$$
s_b=\bar A_{a:b}s_{a-1}+\bar u_{a:b},
\tag{37}
$$

其中

$$
\bar A_{a:b}=A_bA_{b-1}\cdots A_a,
\qquad
\bar u_{a:b}=\sum_{i=a}^{b}
A_b\cdots A_{i+1}u_i.
\tag{38}
$$

块之间继续使用同一结合结构。理论上的结合律允许并行前缀扫描；浮点加法和矩阵乘法不严格结合，不同树形顺序会得到略有差异的结果。 一致性测试应固定输入和权重，比较 naive recurrent、chunk scan、训练 kernel 与 serving kernel 的每层末状态和 logits。误差随 token 数、块大小和数据类型绘图。如果误差只在单块内有界，通常可接受；若跨块呈系统漂移，需要检查门值范围、累积精度和状态重载。 边界状态最容易出错。第一个块应从零状态或传入 checkpoint 开始，后续块必须使用上一个块的最终状态；packed batch 中每个新样本要重置。把 padding token 误当真实写入，即使 attention mask 正确，也会污染循环状态。

写掩码与 scan 的组合还要验证。当一个 token 只读不写时，转移必须精确等于恒等映射，不能仍应用衰减。官方实现通过同时置零 $g,b,w$ 实现冻结；kernel 若把门值经过额外非线性或默认偏置，零输入未必得到恒等，需要针对实现检查。

**Checkpoint 保存的对象**

长请求暂停后要继续，保存普通 KV cache 还不够。LiveMem checkpoint 至少包含每层 GDN2 状态、仍在活动窗口内的 KV 页面、当前位置、请求配置、模型版本和 mask/轮转参数。缺少任一项，都可能恢复成另一条计算轨迹。 checkpoint 可以表示为

$$
C_t=(S_t,K_t,V_t,p_t,c,v_m,h),
\tag{39}
$$

$c$ 是窗口和状态模式配置，$v_m$ 是模型及实现版本，$h$ 是已处理前缀的校验值。恢复时先验证版本和前缀，再把状态与 KV 原子装载。若只成功装入其中一部分，应回退而非继续生成。 保存频率存在成本权衡。每 $K$ 个 token 快照一次，崩溃后最多重放 $K$ 个 token；快照写入量则与 $1/K$ 成正比。对状态约 18 MiB、KV 数 GiB 的请求，完整频繁复制成本很高。可以让 KV 依赖可重建前缀，只持久化小得多的循环状态与窗口边界，但恢复时仍需重算近期 KV。

增量快照对矩阵状态不天然友好。每步都会更新大量元素，块级差分未必稀疏；压缩或量化快照又引入额外数值误差。真正收益要以写入带宽、恢复延迟和输出一致性衡量，不能只看文件大小。 checkpoint 还涉及隐私。它是历史的不可读压缩表示，却可能泄露训练或用户信息；不能因为人眼看不懂就当作非敏感数据。访问控制、保留期和删除范围应与原始会话一致。请求结束后若声明释放，磁盘快照与备份也需纳入清理。

## 5. 证据距离曲线怎样读

论文用 evidence distance 观察支持信息离开活动窗口后能保持多远。距离增加时准确率下降，可能来自状态衰减、更多干扰写入、位置分布偏移或问题本身变难。把所有因素一起变化，只能得到总体鲁棒性，无法直接估计记忆半衰期。 更干净的实验固定证据与问题，在中间插入三类内容：不更新状态的 padding、语义无关但会写入的自然文本、与目标 key 相似的干扰事实。第一类主要增加递推步数，第二类增加一般写入竞争，第三类专门测试地址碰撞。三条曲线的差异帮助定位机制。

对于距离桶 $d$，准确率估计为

$$
\hat p_d=\frac{1}{n_d}\sum_{i=1}^{n_d}y_i,
\qquad
\operatorname{SE}(\hat p_d)\approx
\sqrt{\frac{\hat p_d(1-\hat p_d)}{n_d}}.
\tag{40}
$$

远距离桶往往样本更少，误差条更宽。只看平滑折线容易把抽样波动当成趋势。若同一问题在多个距离重复，使用配对差异或分层模型会比把样本当独立 Bernoulli 更合适。 曲线还应与 `truncate`、RAG 和完整窗口对照。完整窗口衡量骨干在仍可访问证据时的上限，truncate 衡量没有连续状态的下限，RAG 衡量精确回取路线。LiveMem 超过 truncate 证明状态有用；接近完整窗口说明损失小；是否优于 RAG 取决于任务可检索性，不能预设。

对多跳问题，证据距离应分别记录最早、最晚和跨度。两个证据都很远但彼此相邻，与一个早期一个近期的组合，对状态提出不同要求。平均距离会掩盖这种结构。

**与 Context2LoRA、Recurrent 和 Delta-Mem 的比较边界**

几种内生记忆方案都把历史影响压进有限对象，但更新对象不同。Recurrent 类方法在块之间传递 hidden state 或记忆 token；Context2LoRA 把上下文信息写进低秩参数适配；Delta-Mem 使用在线状态更新；LiveMem 在每层加入并行 GDN2 分支并配合真实 KV 轮转。 比较时要固定骨干、活动窗口、训练数据和历史可见性。某方法若允许 32K 窗口，另一方法只有 8K，最终分数同时反映短期注意力差异。某方法全量微调主干，另一方法冻结主干，训练参数和短上下文保持能力也不同。

状态尺寸需统一换算成字节。记忆 token 还会进入每层注意力计算，成本随 token 数和生成步增长；LoRA 权重在每步参与线性层，参数量固定但可能为每请求保存独立 adapter；GDN2 矩阵每步递推。只报告「固定容量」没有揭示每 token 计算。 更新延迟也是区别。循环状态随 token 在线更新，适合流式；从整块上下文生成 adapter 可能需要额外优化或前向；检索系统在查询时付费。系统应按首 token 延迟、持续 decode 延迟和请求切换成本拆开比较。

能力上，参数式或连续状态都难提供精确来源。RAG 能返回原文，代价是检索失败和额外上下文。一个系统可以用 LiveMem 维持隐含任务态，再用外部检索提供证据；实验中的竞争基线不代表产品里只能二选一。

**数据捷径、消融与复现**

记忆数据若格式固定，模型可能利用位置和模板。支持句总在开头、答案总是收尾阶段出现的实体，循环分支只需保存一个固定位置特征。随机化证据位置、问题顺序和实体表面形式，才能迫使模型学习内容相关写入。 答案也可能由世界知识猜出。「巴黎属于哪个国家」无需历史；把实体替换成随机代号，或使用每条样本新生成的映射，能隔离记忆。随机数据过多又会偏离自然语言，需要将可控诊断集与真实会话集一起报告。

长文本中的重复证据降低任务难度。若同一事实在窗口外和窗口内各出现一次，模型可以忽略状态。数据预处理要检查近重复与答案泄漏，评测时记录最近支持证据的距离，而非最早证据距离。 多问题训练还可能让前一个回答泄漏后一个答案。回答文本留在近期窗口后，第二问测到的是读取上一回答，不是读取早期状态。可以在问题间清除答案、使用独立分支，或专门报告带回答历史和不带回答历史两种设置。

RL 数据的 reward model 也可能偏爱详细措辞而非事实正确。状态分支学会生成看似自信的长回答，分数上涨却没有改善记忆。客观键值任务用精确匹配，开放回答再由 judge 评分，两者结合更能区分能力与风格。

### 5.1. 消融实验应该拆哪些因果

最基础的对照是同一权重下的 `state` 与 `truncate`。前者扫描全历史并保留循环状态，后者只处理后缀且从零状态开始。两者窗口相同，差异主要来自连续状态。不过，如果前处理、位置编号或系统 prompt 保留方式不同，仍会混入实现差异。 第二组对照关闭记忆分支的写入或读出。关闭写入但保留读出，状态保持初始值，测试新增分支的静态偏置；保留写入但将读出置零，检查主路径是否仍正常；只在证据离窗后关闭读出，能定位远期答案对状态的依赖。

第三组改变状态容量。头数、$d_k$、$d_v$ 分别影响地址空间、写入内容和计算量。若扩大状态只提升随机键值、不提升聚合任务，说明前者受容量限制；若两者都不变，训练或读取可能成为瓶颈。参数量变化需要用等参数 FFN 或 adapter 对照，排除单纯增加容量的收益。 第四组改变活动窗口 $W$。性能随 $W$ 增长通常会上升，显存和 decode 成本也增加。应绘制 Pareto 前沿，而非只挑 8K 或 32K 两个点。LiveMem 的价值在于相同成本下更强，或相同能力下使用更小窗口；单点优胜无法说明这个权衡。

第五组拆 SFT 与 RL。Base+分支随机初始化、SFT、RL 三个阶段分别评测窗口内和窗口外任务。如果 SFT 已获得主要收益，RL 只改善开放回答，结论应限定；若 RL 明显提升随机化远期事实，才说明奖励改变了记忆使用。 第六组改变写入策略。连续扫描所有 token 与只扫描驱逐区域可能在冗余、延迟和污染上不同。相同窗口与训练数据下比较，才能判断近期内容同时存在于注意力和状态是否有帮助。部署模式必须与训练匹配。

**指标要覆盖能力和系统成本**

任务准确率只描述输出。LiveMem 还改变每请求显存、prefill 吞吐、decode 延迟、状态切换成本和可支持并发。一个方法在离线单请求准确率更高，若状态常驻使并发减半，产品取舍可能不同。 能力指标至少分为窗口内准确率 $A_{in}$、窗口外准确率 $A_{out}$、覆盖更新准确率 $A_{upd}$ 和碰撞压力准确率 $A_{col}$. 可定义记忆增益

$$
G_{mem}=A_{out}^{state}-A_{out}^{truncate},
\tag{41}
$$

同时报告窗口内损失

$$
L_{short}=A_{in}^{base}-A_{in}^{state}.
\tag{42}
$$

只有 $G_{mem}$ 为正且 $L_{short}$ 可接受，才说明新增分支带来净能力收益。 系统指标按长度分桶。短请求阶段状态分支纯增开销，超过窗口后释放 KV 的收益出现。报告 P50 会掩盖长请求尾部，P95/P99 又可能被少数异常工具调用主导；最好同时给请求长度、输入输出 token 和批量。 状态切换要单测。连续 decode 不换请求、每 token 轮转请求、抢占后恢复三种调度产生不同缓存局部性。循环矩阵虽小于长 KV，层数多时仍需大量读写。其实际带宽和 kernel 融合决定延迟，不能仅按 FLOPs 推断。

成本归一可以报告每个成功任务的 GPU 秒、峰值显存和总生成 token。若 LiveMem 减少因遗忘导致的重复搜索，终局成本可能下降；若回答质量相同却每 token 都多跑分支，成本会上升。端到端指标能容纳两种效应。

**跨请求持久化为何是另一项研究问题**

当前实现把状态生命周期绑定单次请求。将状态跨请求保存看似只需序列化矩阵，实际会改变身份、权限、版本和训练分布。单请求内所有 token 共享明确顺序，跨请求则可能由多个设备、会话或并发分支产生。 第一步要定义合并。用户同时打开两个会话，各自从同一旧状态出发并产生新状态 $S_a,S_b$。连续矩阵没有通用三方合并算子，直接平均会破坏非线性编码，按时间选择又丢掉另一分支。事件重放或外部结构化记忆更适合解决并发。

第二步是模型版本。状态只在生成它的权重下有语义；更新模型后读取旧矩阵没有保证。长期记忆系统通常保存可迁移的文本、结构化事实或向量索引，模型升级后可以重新编码。内部状态若要长期存在，需要版本固定和迁移验证。 隐私删除也更严格。请求内结束即释放，边界清楚；长期保存后要按用户、字段和来源删除。矩阵表示难以证明单项信息已清除，整状态删除又会牺牲其他记忆。可审计事实仍应放在外部存储。

训练上，模型只见过单请求连续流，跨天时间间隔、身份切换和新旧权限都属于分布外。产品可以在新请求开始时把外部摘要重新送入 LiveMem，让它在本次请求内维持连续，而不直接复用旧内部矩阵。这样牺牲一些 prefill，换来清晰的数据边界。

### 5.2. 复现时最容易漏掉的约束

第一，Hugging Face 示例显式传入 GDN2 cache，适合功能检查，却没有 vLLM 插件的分页 KV 驱逐。能连续生成不等于已经复现 `state-32k` 服务语义。评测 context turnover 必须使用真实窗口 mask 和释放路径。 第二，模型、代码和配置要成套。基础 Qwen3 版本、LiveMem checkpoint、vendored FLA、vLLM 插件与 kernel 任一不匹配，都可能改变层结构或状态格式。记录提交哈希比只记包名可靠。 第三，`state` 和 `truncate` 的 `window_size` 含义不同。前者是注意力保留的活动 token，完整历史仍写入状态；后者由客户端删除旧记忆，并从零状态处理保留后缀。把两者都理解成服务端滑窗，会构造错误基线。

第四，评测生成参数要一致。temperature、top-p、top-k 与采样次数都会改变开放回答分数。记忆任务常有 judge 评分，judge checkpoint、prompt 和服务版本也属于实验条件。只复现主模型而更换 judge，数字不可直接比较。 第五，训练使用固定 64K pack 和两阶段数据。缩短 pack 会减少真实跨窗依赖，改变 batch 与梯度累积又会影响优化。资源不足时可以调整，但应重新统计每条样本的证据距离和有效 token，而非声称严格复现。 第六，状态正确性先于最终分数。用短随机序列对齐 naive 与 kernel 输出，检查 packed 边界、暂停恢复与 KV 驱逐，再跑昂贵 benchmark。否则一处状态串线可能在平均分里表现成普通噪声，直到真实多租户服务才暴露。

**怎样证明收益确实来自状态连续性**

一项长记忆评测上涨，可能同时受到更多参数、训练数据、回答风格和服务窗口影响。要把因果归到状态连续性，需要沿干预链逐步排除替代解释。最强的证据来自同一 checkpoint、同一窗口和同一输入，只改变循环状态是否从早期历史延续。 设完整状态运行得分为 $Y(S)$，清零状态得分为 $Y(0)$，保留近期窗口不变，平均处理效应可写成

$$
\operatorname{ATE}_{state}
=\mathbb E[Y(S)-Y(0)].
\tag{43}
$$

清零可能产生分布外状态，因此还应加入「来自另一条前缀的状态」和「正确状态加小扰动」对照。若模型只对完全清零敏感，却无法区分正确与错误状态，变化可能来自数值尺度而非语义记忆。 状态替换要与问题内容配对。两条轨迹近期窗口完全相同，早期事实分别为 A 与 B；交换状态后答案也交换，是较直接的语义证据。若只在一条轨迹上清零，模型可能从问题先验猜对，低估状态贡献。

参数量对照则给原主干添加相近规模的静态 adapter，但不跨 token 维护状态。若两者都提升窗口内任务，参数增加解释一部分收益；只有 LiveMem 在证据离窗后继续提升，才支持递推连续性。训练 token 和优化步数也应匹配。 数据对照固定架构，分别用普通长文本和强制 turnover 数据训练。若只有后者学会在 KV 释放后回答，说明 load-bearing 训练条件不可省略。再把训练窗口和评测窗口交叉组合，可以观察策略是否只记住某个固定边界。

服务对照在离线 mask 与真实 vLLM 驱逐上运行同一轨迹。结果一致证明状态语义跨实现保持；离线好、在线差则指向生命周期或 kernel 问题。能力论文若不验证真实释放，只能说明模型能在一种 mask 下利用支路。 收尾阶段检查收益是否伴随代价转移。减少远期 KV 却新增固定状态和每 token 递推，任务成功提高却降低并发，或者省下 prompt token 却增加训练与 judge 成本，都属于真实权衡。状态连续性成立与系统是否值得部署是两个判断，分别需要机制证据和端到端成本证据。

**LiveMem 在长程系统中的位置**

长程 Agent 至少有四层状态：模型内部递推状态、活动注意力窗口、外部可审计任务状态和原始证据存储。LiveMem 加强第一层，并为第二层设置固定上界；它没有替代后两层。目标版本、权限、文件哈希和验收结果仍需要外部结构保存，论文原文和工具日志仍需要可回源存储。 一次可靠执行可以这样流动：新观测进入注意力与 GDN2，Harness 同时提取可审计事件；窗口轮转后，模型内部状态维持语义连续，外部状态维持事实与义务；遇到精确问题时，Harness 根据索引回源，把证据重新放入近期窗口；请求结束时释放内部状态，需长期保存的内容已经落到可迁移表示。

这套分工避免两个极端。若所有记忆都塞进 prompt，成本随历史增长；若所有历史都压进不可解释矩阵，精确回溯、删除和版本迁移无法证明。内部状态承担「继续思考」，外部系统承担「知道事实从哪里来」。 因此判断 LiveMem 时，核心问题是它能否在有限工作窗口下维持同一条计算轨迹，以及这种连续性在状态清零、交换、长距离干扰和真实服务抢占下能否被反复验证。「无限上下文」反而会遮住这些真正可检验的机制。

# LLMs Get Lost in Evolving User Intent：演化意图下的 Agent 评测框架

> 论文：LLMs Get Lost in Evolving User Intent
> 作者：Jihoon Tack, Philippe Laban, Jennifer Neville（Microsoft Research, AI Interaction and Learning）
> arXiv：[2607.20734](https://arxiv.org/abs/2607.20734)（2026-07-22）
> GitHub：[microsoft/evolving-intent](https://github.com/microsoft/evolving-intent)

## 一、原文精读

### 问题动机

真实人机协作里，用户**很少在第一轮就把意图说全**。意图会随对话展开而：逐步披露（under-specification）、中途修正（revision）、甚至转向相关但不同的子任务（function switch / task switching）。然而主流 LLM 评测与训练仍集中在**单轮、fully-specified** 设定——模型在静态任务上接近天花板，却未回答一个更根本的问题：**当用户意图在多轮中演化时，Agent 能否持续跟踪并据此行动？**

现有不少 multi-turn benchmark 也有缺口：(i) 奖励常依赖 LLM-as-judge 而非可验证答案；(ii) 用户轮次偏短；(iii) 用户侧可控性有限，多停留在「增量披露信息」，缺少 revision 与 task switch 等真实动态。论文因此问：能否在**保留原始 benchmark 自动可验证性**的前提下，把静态单轮任务「升维」为演化意图的多轮环境？

### 方法贡献

核心思路：**不从头手写 multi-turn 数据**，而是从已有 verifiable single-turn benchmark 出发，做结构化意图分解与扰动，再经 turn scheduler 组装多轮对话。

**意图结构（terminology）**：

| 概念 | 含义 |
|---|---|
| `function` | 要回答/完成的主问题（如 SQL 的输出形状、SWE issue 的高层变更） |
| `argument` | 求解所需的约束/条件（WHERE 谓词、issue 中的症状与范围等） |
| `answer` | 与原 benchmark 对齐的可验证终态 |

**三阶段数据构造（intent_construction）**：

1. **Intent Extraction**：LLM 将单轮样本分解为 function + arguments + answer，并经 coverage / solvability 验证。
2. **Retrospective Expansion — Counterfactual**：为每个 argument 生成局部值替换的「错误版本」，供 revision turn 使用。
3. **Retrospective Expansion — Predecessor**：生成相关但不同的 predecessor function，供 function-switch turn 使用；须满足 answer preservation（前置任务的新 argument 不改变终态答案）。

**Situated Simulation（Stage 4–5）**：`EvolvingIntent` DataLoader 按 `num_turns`、`num_revisions`、`num_switches` 自动推断场景：

| 场景 | 描述 |
|---|---|
| `fully-specified` | 单轮全信息（基线） |
| `argument-reveal` | 参数逐轮披露，无变更 |
| `argument-revision` | 中途修正先前给出的错误参数 |
| `function-switch` | 中途切换到相关但不同的 function |
| `combined` | 上述动态可在同一会话中组合 |

**Turn Scheduling（Algorithm 1）** 先排 function-switch 与 revision 事件，再填 reveal slot，保证「先披露错误值、后 correction」的因果顺序；每轮内事件顺序为 function event ≻ revision ≻ argument reveal。

**Text Rendering** 支持 rule-based（默认、确定性）与 LLM naturalization（BrowseComp+ 实验用，带 token 校验与 fallback）。

**评测协议**：Evolve 设定对 reveal / revise / switch **各应用两次**，共 **6 次 intent transition、7 轮用户 turn**（含初始轮）；最终 turn anchor 回原始任务，用原 benchmark 协议打分（SQL execution、SWE test、数学题 exact match 等）。

覆盖四个域：GSM8K、BIRD-SQL、BrowseComp+、SWE-Bench Verified（经 pipeline 过滤与抽样：200 / 100 / 100 / 50 条）。

### 实验数字

Table 1 主结果（Accuracy %，Single → Evolve）：

| 模型 | GSM8K | BIRD-SQL | BrowseComp+ | SWE-Bench Verif. |
|---|---:|---:|---:|---:|
| GPT-5.1 | 98.0 → 82.0 (−16.3%) | 72.0 → 66.0 (−8.3%) | 49.0 → 34.0 (−30.6%) | **72.0 → 0.0 (−100%)** |
| GPT-5.2 | 99.0 → 83.0 | 77.0 → 61.0 (−20.8%) | 53.0 → 50.0 | 80.0 → 62.0 (−22.5%) |
| GPT-5.5 | 99.0 → 80.5 | 80.0 → 71.0 | 65.0 → 57.0 | 86.0 → 80.0 (−7.0%) |
| Gemini 3.1 Pro | 98.0 → 82.0 | 75.0 → 72.0 | 51.0 → 40.0 | 86.0 → 84.0 |

实验显示，即使较强模型，少量 intent transition 也会带来明显退化；GPT-5.1 在该设置的 SWE 子集甚至出现 0%。逐轮跟踪分析中，argument reveal 与 argument change 的识别较高，function switch 更容易累积错误。Prompt recap 与 Oracle recap 的差距进一步表明，问题不只是单步推理，还包括从冲突历史中恢复最新意图。

对照还把 turn 数与 transition 数分开：重复轮次带来的下降小于同轮数下多次意图变化。Reasoning mode 没有稳定消除差距，小模型退化更大；Qwen3-4B 的短程 GRPO 实验则显示专门训练可能改善 Evolve，同时较少损伤单轮成绩。这些结果都受论文样本与配置限制。

### 局限

这些限制决定了实验结论能外推到哪里，也指出了真实 Harness 还需补测的变量。

尤其要区分合成对话的内部有效性与真实用户交互的外部有效性，前者成立不自动推出后者。

- **合成用户**：rule-based / LLM naturalizer 仍非真人；自然度与真实 IM 场景的 gap 未完全闭合。
- **LLM 流水线依赖**：Extract / Counterfact / Predecessor 均用 GPT-5.1 验证，pipeline 错误会系统性污染数据（虽有 rejection sampling）。
- **成本**：7-turn 交互 = 最多 7 次顺序 agent call + 渐长上下文，评测贵于 single-turn。
- **域覆盖有限**：四域虽跨 math / SQL / search / SWE，但未覆盖 GUI、长工具链、审批等人机协作形态。
- **训练演示规模小**：RL 实验仅 GSM8K + 小模型，未证明大规模 SFT/RL 可完全补齐 intent-tracking 能力。

## 二、方法架构解析

### 系统拆解

```
单轮 benchmark 样本 (q, y*)
        │
        ▼
┌───────────────────┐
│ Stage 1: Extract  │ → function f*, arguments C*, answer y*
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ Stage 2: Counter- │ → 每个 argument 的局部错误值 c_cf
│ factual args      │
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ Stage 3: Prede- │ → 相关 predecessor functions f_pre
│ cessor functions  │
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ Stage 4: Turn     │ → TurnSlots S_1..S_T（intent 轨迹）
│ Scheduler         │
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ Stage 5: Text     │ → 自然语言 user turns
│ Renderer          │
└─────────┬─────────┘
          ▼
   Agent 多轮交互 → 末轮 verifiable 评分
```

Repo 目录：`intent_construction/`（Stages 1–3 + per-dataset scripts）、`situated_simulation/`（`EvolvingIntent` + `turn_scheduler.py`）、`evaluation/`（runners + `run_{gsm8k,bird,browsecomp,swe}.sh`）。

安装：`conda create -n evolvingintent python=3.10` → `pip install -e .`；API 走 OpenAI / Azure OpenAI（`LLM_BACKEND` 切换）。

### 关键不变量

下列条件用于判断一次意图更新是否保持了当前目标的一致性。

任一条件失效，都可能让后续动作建立在过期或互相冲突的目标版本上。

1. **Final-turn anchor**：无论中间如何 reveal / revise / switch，**最后一轮必须 recover 原始 anchored task**，保证与原 benchmark 答案可比。
2. **Schedule-before-render**：先排 intent 状态机，再生成 surface text——防止「先 correction 后 disclosure」等无效轨迹。
3. **Minimal counterfactual edit**：revision 必须是单点值替换，不是改写整个 argument——否则 correction 语义不成立。
4. **Predecessor answer preservation**：switch 引入的新 argument 不得改变终态 gold answer。
5. **Verifiable end-to-end**：评分仍走 execution-based / test-based 原协议，不用 judge 打分主路径。

### 相邻对照

相邻方法解决的状态对象不同，比较时应先对齐目标、输入和 verifier。

只有对齐后，性能差异才能归因于意图维护，而不是工具权限或任务难度变化。

| 工作 | 用户动态 | 可验证性 | 与本文关系 |
|---|---|---|---|
| 传统 single-turn bench | 无 | 强 | 本文的上游原料 |
| τ-bench / 部分 multi-turn bench | 多为增量披露 | 混合 | 本文显式建模 revise + switch |
| LongHorizon-Harness | 不建模用户意图变化 | 环境 audit | 正交：LH 管执行状态，本文管意图信念 |
| Chat 产品「当前任务」面板 | 工程 workaround | 无统一 benchmark | 本文提供可复现评测协议 |
| Argus \(K_t=(\iota,o_t,c_t,v_t)\) | 区分 standing intent vs operational contract | 任务原生 verifier | 理论层面对齐「intent 可变但需显式 admit」 |

### 可迁移抽象

从论文方法中可以提取若干不依赖具体数据集的工程规则。

这些规则关注状态更新和证据边界，不要求复用论文的用户模拟生成流程。

1. **Intent Ledger**：会话级结构化记录 `{function, revealed_args, revisions[], switches[]}`——比纯 chat log 更适合做 belief state。
2. **三态转移类型**：reveal / revision / switch 是覆盖真实用户行为的最小生成基；任何「动态意图」评测应至少分解到这三类。
3. **Oracle vs Prompt Recap 诊断**：分离「跟踪意图」与「在正确意图下行动」两个 failure mode——工程上可对应「显式 intent 面板 + 计划重置」。
4. **Transition-count 控制变量**：评测时必须区分「轮次变长」与「意图变次」——否则会把 context length 效应误归因于 intent tracking。
5. **Benchmark lifting 范式**：从 verifiable static task 合成 dynamic dialogue，比手写 multi-turn 便宜且可扩展——可复用到更多域（GUI agent、审批流等）。

## 三、状态更新与真实 Harness

结构化意图只有进入计划、工具调用与恢复流程才有意义。状态更新要覆盖披露、修订与任务切换，并让依赖旧版本的动作及时失效。

本节先用状态式和手算说明更新规则，再讨论计划绑定与真实 Harness 中的错误类型。

### 3.1. 把意图维护写成状态更新

多轮对话日志只记录“说过什么”，没有直接说明“现在什么有效”。一个可执行的意图状态可以写成

$$
I_t=(f_t,A_t,C_t,V_t),
$$

$f_t$ 是当前 function，$A_t$ 是已经披露且仍有效的 arguments，$C_t$ 是约束与优先级，$V_t$ 是意图版本。第 $t$ 轮用户消息 $u_t$ 经过解析后，不是简单追加到 $I_{t-1}$，而是生成带类型的状态操作：

$$
I_t=U(I_{t-1},\delta_t),\qquad
\delta_t\in\{\operatorname{reveal},\operatorname{revise},\operatorname{switch}\}.
$$

`reveal(k,v)` 为尚未赋值的参数增加值；`revise(k,v')` 让旧值失效并保存修订关系；`switch(f')` 改变当前 function，同时明确哪些参数继续适用。版本号在每次有效转移后递增，后续计划、工具调用和产物都应记录自己依据的 $V_t$。这样用户在第六轮改了目标，第七轮仍在执行 $V_3$ 计划时，系统能发现版本落后，而不必期待模型凭长对话“自己记得”。

#### 3.1.1. 一个四轮手算

假设初始请求是“分析销售数据”，状态只有 $f_0=\text{analyze-sales}$，参数集合为空，版本为 0。

1. 用户补充“只看华东区”。执行 `reveal(region, east)`，得到 $A_1=\{region:east\},V_1=1$。
2. 用户说“时间是第二季度”。执行 `reveal(period,Q2)`，计划据此生成 SQL，计划版本也记为 2。
3. 用户修正“我刚说错了，是第三季度”。执行 `revise(period,Q3)`，旧的 Q2 保留在审计历史中，但从有效参数表移除，$V_3=3$。所有依赖 Q2 的未执行 SQL 被标为 stale。
4. 用户改成“先比较华东和华南的退货率”。function 从销售分析切换为退货率比较，`period:Q3` 仍适用，`region:east` 需要扩成 `{east,south}`。这次操作既有 switch，又有参数修订，目标版本升到 4。

如果系统只是把四句话拼起来，最终上下文同时包含 Q2、Q3、“华东”和“华东与华南”。模型可能在自然语言回答中选对最新值，工具链却已经把第二轮 SQL 缓存并执行。结构化状态的意义是让无效计划在动作发生前被拒绝，而不是只提高最终复述意图的准确率。

#### 3.1.2. switch 中哪些东西能够继承

function switch 不能默认清空所有参数，也不能默认全部继承。可以为每个 argument 记录作用域：会话级参数如语言和预算，任务族参数如数据集版本，function 局部参数如 SQL 输出列。切换到新 function 时，只有作用域覆盖新任务的参数自动继承，其余进入待确认集合。

设旧参数共有 $n$ 个，直接继承集合为 $K$，需要重新确认集合为 $Q$，明确失效集合为 $D$，应满足

$$
K\cup Q\cup D=A_{t-1},
\qquad K,Q,D\text{ 两两不交}.
$$

如果某个参数没有进入三者之一，状态更新就丢了信息；如果同时进入 $K$ 和 $D$，后续执行会遇到冲突。这个集合检查非常简单，却比让模型输出一句“我明白你的新需求了”更能保护长任务。

### 3.2. 意图状态怎样影响计划和工具

每个计划节点应保存 `(goal_version, preconditions, expected_effect, verifier)`。执行前先检查 `goal_version == V_t`；版本落后时不一定全部删除，可以重新验证前置条件并迁移到新目标。例如已经完成的数据清洗与 Q2/Q3 无关，可以复用；按 Q2 聚合的中间表则必须重算。

工具结果也要绑定意图版本。一个耗时查询在 $V_2$ 发起，返回时系统已进入 $V_4$，结果不能直接写入当前事实表。它可以作为历史证据保存，再由新计划判断是否仍适用。异步 Agent 特别容易在这里出错：旧子任务晚到的高质量答案会覆盖新目标下的正确状态。

冲突时还需要区分“用户明确替换”和“系统推断替换”。“改成第三季度”明确撤销 Q2；“也看看第三季度”可能是新增对照，而非替换。解析器置信度不足时，应把候选解释写入待确认状态，暂停会产生较大副作用的动作。这里询问用户是为了消除产品意图歧义，不是把实现选择甩回用户。

### 3.3. 从论文评测走向真实 Harness

论文的 final-turn anchor 让静态 benchmark 的答案仍可复用，是很干净的控制实验。真实协作中的目标却未必回到原始任务，甚至可能没有唯一答案。因此工程评测还要测四类状态错误：

- **遗漏**：已经披露的 argument 没进入当前状态；
- **残留**：被修订或取消的值仍参与计划；
- **错继承**：function switch 后继承了不再适用的局部参数；
- **错失效**：本应跨任务保留的预算或安全约束被清空。

可对每轮真实意图状态 $I_t^*$ 与系统状态 $\hat I_t$ 做字段级 precision、recall，再把错误传播到动作层：由错误状态产生了多少无效工具调用、写入和重做成本。只评估模型能否在末轮口头复述最新要求，会漏掉中间已经发生的副作用。

还应分别运行三种 Harness。第一种只给完整聊天记录；第二种在每轮提供模型自己维护的 recap；第三种提供外部状态机维护的结构化意图表。若第三种明显好于前两种，瓶颈主要在状态抽取和保持；若三种都差，问题更可能出在拿到正确意图后仍不会规划或执行。这和论文的 Oracle recap 诊断一致，但工程系统还要计算维护状态的 token、延迟和错误修订成本。

意图表也不是新的绝对真相。解析可能错，用户可能自相矛盾，外部状态还可能与最新消息不同步。每条字段应保留来源 turn、更新时间、是否经过用户确认以及依赖它的计划节点。发现错误时，从来源和依赖关系向下失效，而不是清空整段记忆重来。

放回 Long-Horizon 的框架里，evolving intent 增加的是目标维度的非平稳性。环境状态会变，模型知识会过期，连“要完成什么”本身也会变。系统若没有目标版本和迁移规则，再强的计划器也只是在高效执行过期计划。

## 四、实验结论与状态评测

论文实验把静态任务转成可验证的多轮意图变化，为比较单轮与动态设置提供了控制条件。数字仍需连同样本、预算与 Harness 一起阅读。

从研究结果走向工程评测，还要观察每轮意图状态和动作副作用。本节依次处理实验边界、更新规则与过程指标。

### 4.1. 论文实验究竟证明了什么

[论文 v1](https://arxiv.org/abs/2607.20734)于 2026 年 7 月 22 日提交。作者没有另造一套只能由模型裁判的多轮答案，而是从四个已有可验证数据集出发：GSM8K 取 200 个样本，BIRD-SQL 与 BrowseComp+ 各取 100 个，SWE-bench Verified 取 50 个。单轮题目的原始目标被放到对话末轮，原来的数值答案、SQL 执行器、检索答案或测试套件继续担任 verifier。这样控制了一个关键变量：末轮任务不变，变化的是它如何经过多轮披露、修订和切换才到达模型面前。

主实验把三种转移各应用两次，共 6 次意图转移、7 个用户轮次。论文表 1 的结果不能压成一个平均跌幅，因为领域与 Harness 差异很大。例如 GPT 5.5 在 GSM8K 从 99.0% 降到 80.5%，在 SWE-bench Verified 从 86.0% 降到 80.0%；Kimi K2.6 在 BrowseComp+ 从 55.0% 降到 52.0%，在 SWE-bench Verified 从 86.0% 降到 72.0%。这些数值只适用于论文采样、模型版本与预算。SWE 运行使用扩展后的 mini-SWE-agent v2，多数模型每轮最多 100 次工具调用，Kimi K2.6 与 DeepSeek V3.2 提高到 200 次；BrowseComp+ 每轮最多 50 次搜索。不同预算意味着跨模型横向比较需要谨慎。

相对跌幅按

$$
d_{\mathrm{rel}}=\frac{A_{\mathrm{single}}-A_{\mathrm{evolve}}}
{A_{\mathrm{single}}}\times100\%.
\tag{8}
$$

以 GPT 5.5 的 GSM8K 为例，代入 $99.0$ 与 $80.5$ 得

$$
d_{\mathrm{rel}}=\frac{99.0-80.5}{99.0}\times100\%
\approx18.7\%.
\tag{9}
$$

绝对下降是 18.5 个百分点，相对下降约 18.7%，两者不能混写。论文表中的括号报告相对变化；阅读数字时还应同时看单轮基线，避免把低基线上的小绝对变化误作稳健。

实验支持的结论是：强单轮表现不会自动迁移到受控的演化意图设置，且转移增加时准确率会下降。它没有证明真实用户一定以这三种方式变化，也没有证明所有长对话失败都来自意图跟踪。对话由回溯构造，末轮固定回到源任务；真实协作可能永久改目标、撤销任务，或给出互相冲突又无法自动验证的要求。论文提供的是诊断探针，不是现实交互的完整生成模型。

### 4.2. 转移规则如何避免「只追加不更新」

把当前意图写成键值映射更容易实现。设功能为 $f_t$，参数映射为 $C_t$，已披露键集合为 $R_t$，目标状态为

$$
I_t=(f_t,C_t,R_t,g_t).
\tag{10}
$$

$g_t$ 是递增版本。披露新参数 $k=v$ 时，更新 $C_t[k]\leftarrow v$ 且把 $k$ 加入 $R_t$；修订参数时覆盖旧值并使依赖旧值的计划节点失效；功能切换时，新功能保留共享参数，局部参数进入历史而不参与当前执行。

考虑四轮例子。第一轮「找纽约餐厅」，状态为 $(\text{find},\{city:\text{NY}\},1)$。第二轮「要纯素」，加入 $diet:\text{vegan}$。第三轮「改到布鲁克林」，这是 revision，必须覆盖 `city`，不能同时保留 NY 与 Brooklyn。第四轮「订周五七点的那家」，功能切换为 `book`，`restaurant_id`、地点与饮食偏好可以继承，搜索排序参数不一定继承。

若状态以追加日志保存，读取器要计算每个键的最后有效写入：

$$
\hat c_k(t)=c_{k,j^*},\qquad
j^*=\max\{j\le t:k\in\Delta I_j,\;\operatorname{active}(j,t)=1\}.
\tag{11}
$$

`active` 用来排除被撤销的分支。式 (11) 比「取最后一句包含该词的话」严格：用户可能说「不要改到布鲁克林，仍然纽约」，否定范围必须先解析成状态操作。解析不确定时，应保留候选解释与来源轮次，而不是静默选一个。

计划节点也要记录依赖。例如工具调用 `search(city=NY,diet=vegan)` 依赖 `city@v1` 与 `diet@v2`。第三轮把城市更新到 v3 后，节点有效性为

$$
\operatorname{valid}(p,t)=
\prod_{(k,v)\in D(p)}
\mathbf 1[\operatorname{version}_t(k)=v].
\tag{12}
$$

城市版本不再等于 v1，乘积变成 0，旧搜索结果不能直接用于预订。这一步把「记住用户改主意」转成可执行失效规则。

### 4.3. 评测意图状态而不只评测末轮答案

末轮 verifier 保证最终答案可核验，却看不到中途副作用。工程评测应在每轮保存真实状态 $I_t^*$ 与系统估计 $\hat I_t$。对离散槽位可计算字段准确率；对集合槽位可算 precision 与 recall；对版本更新则记录修订生效延迟。若第 $r$ 轮修订，系统在第 $u$ 轮首次执行符合新值的动作，则

$$
L_{\mathrm{adopt}}=u-r.
\tag{13}
$$

仅有延迟仍不够。系统可能在 $r$ 到 $u$ 之间执行不可逆动作。应另记旧意图残留成本

$$
C_{\mathrm{stale}}=
\sum_{t=r}^{u-1}c(a_t)\,
\mathbf 1[a_t\text{ 依赖已失效意图}].
\tag{14}
$$

这样，同样晚两轮才修正的系统会因期间只是读取文件，或已经发送邮件，而得到完全不同的风险描述。

论文还比较了记忆机制，这类对照需要分清两个瓶颈。Oracle recap 把正确意图直接提供给模型，若表现恢复，说明状态提取或保持是主要问题；若仍不恢复，说明模型即使拿到正确状态，也不能据此规划和执行。模型自己生成的 recap 同时受到写入错误、压缩遗漏和读取失败影响，不能只凭 recap 文本看起来完整就认定状态可靠。

真实 Harness 最低限度应保存：当前功能、每个参数的值与版本、来源轮次、置信状态、全局约束、已失效值、依赖这些字段的未完成动作。对话原文仍保留作审计，但规划器读取结构化当前态。用户再次改变要求时，先更新目标状态，再使旧计划失效，最后才生成新动作；顺序反过来会让过期动作抢先执行。

## 五、工程实现与故障注入

真实系统需要一张可审计的当前意图表，也需要完整变更事件。两者分开，才能兼顾规划效率与来源追溯。

实现完成后还要用修订、切换、并发和含糊要求主动攻击状态机。本节给出最小表结构与验证方法。

### 5.1. 实现一张可审计的意图表

意图表不需要复杂本体，关键是把当前值与变更历史分开。当前表可以包含 `field`、`value`、`scope`、`version`、`source_turn`、`status` 六列；事件表另存 `reveal`、`revise`、`retract`、`switch` 和 `confirm`。规划器只读状态为 active 的当前值，审计器可以沿事件表解释它为何生效。这样既避免每次规划重读整段对话，也不会因覆盖当前值而丢失来源。

全局约束与局部参数必须分层。例如「不得删除生产数据」在任务切换后仍有效，作用域是 session 或 project；「餐厅在纽约」只属于当前搜索功能。功能切换时可按作用域计算保留集合：

$$
C_{t+1}^{\mathrm{keep}}=
\{c\in C_t:\operatorname{scope}(c)\supseteq\operatorname{scope}(f_{t+1})\}
\cup\operatorname{shared}(f_t,f_{t+1}).
\tag{15}
$$

第一项保留覆盖新任务的上层约束，第二项保留两个功能明确共享的参数。其余字段进入 inactive 历史。若共享关系不确定，系统应把字段标为 pending，而不是默认继承。过度继承会把旧任务污染新任务，过度清空则迫使用户重复说明预算和安全要求。

并发更新还需要版本条件。Agent 读取意图版本 $g=12$ 后准备执行，用户同时把目标更新到 $g=13$。动作网关可要求

$$
\operatorname{execute}(a)=
\mathbf 1[g_{\mathrm{plan}}=g_{\mathrm{current}}]
\mathbf 1[\text{硬约束仍满足}].
\tag{16}
$$

版本不一致时重新规划。这不是要求每次普通读取都加锁，而是把检查放在会产生副作用的动作前。搜索和草稿可以宽松，付款、发布、删除与写生产库必须严格。

恢复时也不能只加载最新摘要。checkpoint 应包含目标版本、当前意图表、尚未完成的计划及其依赖版本、已执行副作用的幂等标识。重启后先读取外部环境，再判断旧动作是否已经发生；若服务端已成功而客户端只看到超时，直接重试可能重复下单。意图连续性因此与环境幂等性相连，不只是对话理解问题。

### 5.2. 用故障注入验证状态机

最后做三组故障注入。第一组在动作前修订一个关键参数，检查旧计划是否失效；第二组在功能切换后重复出现旧参数词，检查系统是否错误复活历史值；第三组让用户给出含糊补充，检查系统是否在高风险动作前确认。每组同时记录状态字段错误、过期动作数和副作用成本。只有末轮回答正确而中途已经执行错动作，仍应判为过程失败。

还应加入反向样本：用户重复旧值只是为了解释历史，而不是恢复它；用户说「保留纽约方案作对照」意味着 Brooklyn 仍是主方案，纽约成为并行分支；用户撤销整项任务时，所有局部参数都应失效，但项目级安全约束继续存在。这些样本检验的是语义作用域与分支管理，不能靠简单的「最后出现值胜出」规则通过。评测报告应同时给解析正确率与实际动作正确率，因为一个系统可能状态表正确，却在调用工具时仍取错字段。

分支状态还必须有稳定标识，避免同名参数串线。

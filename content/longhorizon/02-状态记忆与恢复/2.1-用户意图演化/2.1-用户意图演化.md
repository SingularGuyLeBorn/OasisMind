# LLMs Get Lost in Evolving User Intent：演化意图下的 Agent 评测框架

> 论文：LLMs Get Lost in Evolving User Intent
> 作者：Jihoon Tack, Philippe Laban, Jennifer Neville（Microsoft Research, AI Interaction and Learning）
> arXiv：[2607.20734](https://arxiv.org/abs/2607.20734)（2026-07-22）
> GitHub：[microsoft/evolving-intent](https://github.com/microsoft/evolving-intent)

## 1. 演化意图的构造与评测

演化意图评测从已有的单轮任务出发, 控制新信息何时出现、旧要求何时失效, 同时保留原数据集的可执行答案. 这样才能把意图跟踪造成的错误, 与基础解题能力不足区分开.

构造出来的多轮轨迹还要满足两个条件: reveal、revision 和 function switch 必须真实改变当前目标; 生成过程又不能泄漏答案或制造无法验证的新任务. 论文的数据管线和状态约束都在服务这两个条件.

### 1.1. 静态任务遗漏了意图变化

真实协作中, 用户**很少在第一轮就把意图说全**. 后续消息可能逐步披露参数(under-specification), 也可能修订旧值(revision), 甚至切换到相关但不同的任务(function switch/task switching). 单轮、fully-specified 评测把目标固定在起点, 因而测不到系统能否在目标变化后及时更新计划和动作.

不少 multi-turn benchmark 也只覆盖增量披露, 用户轮次较短, 奖励还可能依赖 LLM-as-judge. revision 与 function switch 带来的覆盖、撤销和继承问题没有进入主测试. 这篇论文因此把已有的可验证单轮任务改造成多轮环境, **终态仍由原 benchmark 的执行器或标准答案判定**, 变化只发生在意图呈现过程.

### 1.2. 从单轮样本构造多轮意图轨迹

数据不从头手写, 而是从 verifiable single-turn benchmark 出发, 先把任务拆成 function、arguments 和 answer, 再生成局部扰动, 最后由 turn scheduler 组装多轮对话. 三个对象的含义如下.

| 概念 | 含义 |
|---|---|
| `function` | 要回答/完成的主问题（如 SQL 的输出形状、SWE issue 的高层变更） |
| `argument` | 求解所需的约束/条件（WHERE 谓词、issue 中的症状与范围等） |
| `answer` | 与原 benchmark 对齐的可验证终态 |

**前三个阶段负责构造意图组件.**

1. **Intent Extraction**：LLM 将单轮样本分解为 function + arguments + answer，并经 coverage / solvability 验证。
2. **Retrospective Expansion — Counterfactual**：为每个 argument 生成局部值替换的「错误版本」，供 revision turn 使用。
3. **Retrospective Expansion — Predecessor**：生成相关但不同的 predecessor function，供 function-switch turn 使用；须满足 answer preservation（前置任务的新 argument 不改变终态答案）。

**Stage 4–5 负责 Situated Simulation.** `EvolvingIntent` DataLoader 根据 `num_turns`、`num_revisions` 和 `num_switches` 选择场景.

| 场景 | 描述 |
|---|---|
| `fully-specified` | 单轮全信息（基线） |
| `argument-reveal` | 参数逐轮披露，无变更 |
| `argument-revision` | 中途修正先前给出的错误参数 |
| `function-switch` | 中途切换到相关但不同的 function |
| `combined` | 上述动态可在同一会话中组合 |

Turn Scheduling(Algorithm 1)先安排 function switch 与 revision, 再填入 reveal slot, 从而保证「先披露错误值、后修正」的因果顺序. 同一轮内按 function event、revision、argument reveal 的优先级排列. Text Rendering 默认使用确定性的规则模板; BrowseComp+ 实验另用了带 token 校验和 fallback 的 LLM naturalization.

Evolve 对 reveal、revision、switch **各应用两次**, 一条轨迹共经历 **6 次 intent transition 和 7 轮用户 turn**(含初始轮). 最后一轮重新锚定原始任务, 因此仍能使用 SQL execution、SWE test 或 exact match 等原协议评分. 四个任务域分别是 GSM8K、BIRD-SQL、BrowseComp+ 和 SWE-Bench Verified, 过滤与抽样后的规模为 200、100、100、50 条.

### 1.3. 四个任务域的准确率变化

Table 1 主结果（Accuracy %，Single → Evolve）：

| 模型 | GSM8K | BIRD-SQL | BrowseComp+ | SWE-Bench Verif. |
|---|---:|---:|---:|---:|
| GPT-5.1 | 98.0 → 82.0 (−16.3%) | 72.0 → 66.0 (−8.3%) | 49.0 → 34.0 (−30.6%) | **72.0 → 0.0 (−100%)** |
| GPT-5.2 | 99.0 → 83.0 | 77.0 → 61.0 (−20.8%) | 53.0 → 50.0 | 80.0 → 62.0 (−22.5%) |
| GPT-5.5 | 99.0 → 80.5 | 80.0 → 71.0 | 65.0 → 57.0 | 86.0 → 80.0 (−7.0%) |
| Gemini 3.1 Pro | 98.0 → 82.0 | 75.0 → 72.0 | 51.0 → 40.0 | 86.0 → 84.0 |

少量 intent transition 已足以造成明显退化; GPT-5.1 在这组 SWE 子集上的 Evolve 准确率降到 0%. 逐轮分析显示, argument reveal 与 argument revision 的识别率较高, function switch 更容易积累错误. Prompt recap 与 Oracle recap 的差距还表明, 瓶颈既有单步推理, 也有从冲突历史中恢复当前意图.

论文把 turn 数与 transition 数分开控制: 只增加重复轮次造成的下降, 小于相同轮数内多次改变意图. Reasoning mode 没有稳定消除差距, 小模型退化更明显. Qwen3-4B 的短程 GRPO 实验表明, 针对性训练可以改善 Evolve, 同时较少损伤单轮成绩; 这个结论仍受实验模型、任务域和样本规模约束.

### 1.4. 合成对话的适用边界

合成轨迹让变量可控, 也缩窄了结论的适用范围. 论文证明的是模型在这套生成规则下能否处理意图变化, 还不能覆盖真人对话中的省略、含混授权和临时打断.

真实 Harness 还需要补测自然度、流水线误差、顺序调用成本和更多任务形态. 合成数据的内部有效性成立, 不会自动推出真实用户交互中的外部有效性.

- **合成用户**：rule-based / LLM naturalizer 仍非真人；自然度与真实 IM 场景的 gap 未完全闭合。
- **LLM 流水线依赖**：Extract / Counterfact / Predecessor 均用 GPT-5.1 验证，pipeline 错误会系统性污染数据（虽有 rejection sampling）。
- **成本**：7-turn 交互 = 最多 7 次顺序 agent call + 渐长上下文，评测贵于 single-turn。
- **域覆盖有限**：四域虽跨 math / SQL / search / SWE，但未覆盖 GUI、长工具链、审批等人机协作形态。
- **训练演示规模小**：RL 实验仅 GSM8K + 小模型，未证明大规模 SFT/RL 可完全补齐 intent-tracking 能力。

### 1.5. 数据管线与状态约束

数据管线决定每轮消息从哪一种意图事件生成, 状态约束则决定这些事件能否组成一条有效轨迹. 二者需要分开: 文本可以自然, 但顺序错误仍会让 correction 失去对象; 顺序可以合法, 但终态不可验证也无法用于稳定评测.

五个阶段从静态样本中抽取目标结构, 生成 counterfactual 与 predecessor, 再把事件排进 turn slot 并渲染成用户消息. 后续约束检查围绕最终答案、事件顺序、局部修改范围和端到端 verifier 展开.

#### 1.5.1. 五阶段数据流

Stage 1–3 生成结构化意图材料, Stage 4–5 决定这些材料何时出现、怎样写成对话. 先排事件再渲染文本, 可以避免语言生成反过来改变意图轨迹.

Repo 目录：`intent_construction/`（Stages 1–3 + per-dataset scripts）、`situated_simulation/`（`EvolvingIntent` + `turn_scheduler.py`）、`evaluation/`（runners + `run_{gsm8k,bird,browsecomp,swe}.sh`）。 安装：`conda create -n evolvingintent python=3.10` → `pip install -e .`；API 走 OpenAI / Azure OpenAI（`LLM_BACKEND` 切换）。

**意图轨迹必须满足的约束.** 下列条件用于判断一次意图更新是否保持了当前目标的一致性。 任一条件失效，都可能让后续动作建立在过期或互相冲突的目标版本上。

1. **Final-turn anchor**：无论中间如何 reveal / revise / switch，**最后一轮必须 recover 原始 anchored task**，保证与原 benchmark 答案可比。
2. **Schedule-before-render**：先排 intent 状态机，再生成 surface text——防止「先 correction 后 disclosure」等无效轨迹。
3. **Minimal counterfactual edit**：revision 必须是单点值替换，不是改写整个 argument——否则 correction 语义不成立。
4. **Predecessor answer preservation**：switch 引入的新 argument 不得改变终态 gold answer。
5. **Verifiable end-to-end**：评分仍走 execution-based / test-based 原协议，不用 judge 打分主路径。

**与多轮评测方法的差别.** 相邻方法解决的状态对象不同，比较时应先对齐目标、输入和 verifier。 只有对齐后，性能差异才能归因于意图维护，而不是工具权限或任务难度变化。

| 工作 | 用户动态 | 可验证性 | 与演化意图评测的关系 |
|---|---|---|---|
| 传统 single-turn bench | 无 | 强 | 构造演化对话的上游原料 |
| τ-bench / 部分 multi-turn bench | 多为增量披露 | 混合 | 增加 revise + switch 后才覆盖目标变化 |
| LongHorizon-Harness | 不建模用户意图变化 | 环境 audit | 正交：LH 管执行状态，演化意图框架管意图信念 |
| Chat 产品「当前任务」面板 | 工程 workaround | 无统一 benchmark | 缺少可复现的统一评测 |
| Argus \(K_t=(\iota,o_t,c_t,v_t)\) | 区分 standing intent vs operational contract | 任务原生 verifier | 理论层面对齐「intent 可变但需显式 admit」 |

**可复用的状态表示.** 从论文方法中可以提取若干不依赖具体数据集的工程规则。 这些规则关注状态更新和证据边界，不要求复用论文的用户模拟生成流程。

1. **Intent Ledger**：会话级结构化记录 `{function, revealed_args, revisions[], switches[]}`——比纯 chat log 更适合做 belief state。
2. **三态转移类型**：reveal / revision / switch 是覆盖真实用户行为的最小生成基；任何「动态意图」评测应至少分解到这三类。
3. **Oracle vs Prompt Recap 诊断**：分离「跟踪意图」与「在正确意图下行动」两个 failure mode——工程上可对应「显式 intent 面板 + 计划重置」。
4. **Transition-count 控制变量**：评测时必须区分「轮次变长」与「意图变次」——否则会把 context length 效应误归因于 intent tracking。
5. **Benchmark lifting 范式**：从 verifiable static task 合成 dynamic dialogue，比手写 multi-turn 便宜且可扩展——可复用到更多域（GUI agent、审批流等）。

## 2. 意图状态如何进入 Harness

结构化意图只有进入计划、工具调用与恢复流程才有意义. 状态更新要覆盖披露、修订与任务切换, 并让依赖旧版本的动作及时失效.

意图更新可以写成显式状态转移. 状态式给出字段与版本的关系, 手算展示修订如何使旧计划失效, 随后的错误类型直接对应计划绑定和工具参数.

### 2.1. 把意图维护写成状态更新

多轮对话日志只记录“说过什么”，没有直接说明“现在什么有效”。一个可执行的意图状态可以写成

$$
I_t=(f_t,A_t,C_t,V_t),
$$

$f_t$ 是当前 function，$A_t$ 是已经披露且仍有效的 arguments，$C_t$ 是约束与优先级，$V_t$ 是意图版本。第 $t$ 轮用户消息 $u_t$ 经过解析后生成带类型的状态操作；把消息原样追加到 $I_{t-1}$ 无法表达覆盖与撤销：

$$
I_t=U(I_{t-1},\delta_t),\qquad
\delta_t\in\{\operatorname{reveal},\operatorname{revise},\operatorname{switch}\}.
$$

`reveal(k,v)` 为尚未赋值的参数增加值；`revise(k,v')` 让旧值失效并保存修订关系；`switch(f')` 改变当前 function，同时明确哪些参数继续适用。版本号在每次有效转移后递增，后续计划、工具调用和产物都应记录自己依据的 $V_t$。这样用户在第六轮改了目标，第七轮仍在执行 $V_3$ 计划时，系统能发现版本落后，而不必期待模型凭长对话“自己记得”。

**一个四轮手算.** 假设初始请求是“分析销售数据”，状态只有 $f_0=\text{analyze-sales}$，参数集合为空，版本为 0。

1. 用户补充“只看华东区”。执行 `reveal(region, east)`，得到 $A_1=\{region:east\},V_1=1$。
2. 用户说“时间是第二季度”。执行 `reveal(period,Q2)`，计划据此生成 SQL，计划版本也记为 2。
3. 用户修正“我刚说错了，是第三季度”。执行 `revise(period,Q3)`，旧的 Q2 保留在审计历史中，但从有效参数表移除，$V_3=3$。所有依赖 Q2 的未执行 SQL 被标为 stale。
4. 用户改成“先比较华东和华南的退货率”。function 从销售分析切换为退货率比较，`period:Q3` 仍适用，`region:east` 需要扩成 `{east,south}`。这次操作既有 switch，又有参数修订，目标版本升到 4。

如果系统只是把四句话拼起来，最终上下文同时包含 Q2、Q3、“华东”和“华东与华南”。模型可能在自然语言回答中选对最新值，工具链却已经把第二轮 SQL 缓存并执行。结构化状态让无效计划在动作发生前被拒绝，同时保留最终复述意图的准确率。

**switch 中哪些东西能够继承.** function switch 不能默认清空所有参数，也不能默认全部继承。可以为每个 argument 记录作用域：会话级参数如语言和预算，任务族参数如数据集版本，function 局部参数如 SQL 输出列。切换到新 function 时，只有作用域覆盖新任务的参数自动继承，其余进入待确认集合。 设旧参数共有 $n$ 个，直接继承集合为 $K$，需要重新确认集合为 $Q$，明确失效集合为 $D$，应满足

$$
K\cup Q\cup D=A_{t-1},
\qquad K,Q,D\text{ 两两不交}.
$$

如果某个参数没有进入三者之一，状态更新就丢了信息；如果同时进入 $K$ 和 $D$，后续执行会遇到冲突。这个集合检查非常简单，却比让模型输出一句“我明白你的新需求了”更能保护长任务。

### 2.2. 意图状态怎样影响计划和工具

每个计划节点应保存 `(goal_version, preconditions, expected_effect, verifier)`。执行前先检查 `goal_version == V_t`；版本落后时不一定全部删除，可以重新验证前置条件并迁移到新目标。例如已经完成的数据清洗与 Q2/Q3 无关，可以复用；按 Q2 聚合的中间表则必须重算。 工具结果也要绑定意图版本。一个耗时查询在 $V_2$ 发起，返回时系统已进入 $V_4$，结果不能直接写入当前事实表。它可以作为历史证据保存，再由新计划判断是否仍适用。异步 Agent 特别容易在这里出错：旧子任务晚到的高质量答案会覆盖新目标下的正确状态。

冲突时还需要区分“用户明确替换”和“系统推断替换”。“改成第三季度”明确撤销 Q2；“也看看第三季度”可能是新增对照，而非替换。解析器置信度不足时，应把候选解释写入待确认状态，暂停会产生较大副作用的动作。这里询问用户是为了消除产品意图歧义，不是把实现选择甩回用户。

### 2.3. 从论文评测走向真实 Harness

论文的 final-turn anchor 让静态 benchmark 的答案仍可复用，是很干净的控制实验。真实协作中的目标却未必回到原始任务，甚至可能没有唯一答案。因此工程评测还要测四类状态错误：

- **遗漏**：已经披露的 argument 没进入当前状态；
- **残留**：被修订或取消的值仍参与计划；
- **错继承**：function switch 后继承了不再适用的局部参数；
- **错失效**：本应跨任务保留的预算或安全约束被清空。

可对每轮真实意图状态 $I_t^*$ 与系统状态 $\hat I_t$ 做字段级 precision、recall，再把错误传播到动作层：由错误状态产生了多少无效工具调用、写入和重做成本。只评估模型能否在末轮口头复述最新要求，会漏掉中间已经发生的副作用。 还应分别运行三种 Harness。第一种只给完整聊天记录；第二种在每轮提供模型自己维护的 recap；第三种提供外部状态机维护的结构化意图表。若第三种明显好于前两种，瓶颈主要在状态抽取和保持；若三种都差，问题更可能出在拿到正确意图后仍不会规划或执行。这和论文的 Oracle recap 诊断一致，但工程系统还要计算维护状态的 token、延迟和错误修订成本。

意图表也不是新的绝对真相。解析可能错，用户可能自相矛盾，外部状态还可能与最新消息不同步。每条字段应保留来源 turn、更新时间、是否经过用户确认以及依赖它的计划节点。发现错误时，从来源和依赖关系向下失效，而不是清空整段记忆重来。 放回 Long-Horizon 的框架里，evolving intent 增加的是目标维度的非平稳性。环境状态会变，模型知识会过期，连“要完成什么”本身也会变。系统若没有目标版本和迁移规则，再强的计划器也只是在高效执行过期计划。

### 2.4. 实验结论与状态评测

论文实验把静态任务转成可验证的多轮意图变化, 为比较单轮与动态设置提供了控制条件. 数字仍需连同样本、预算与 Harness 一起阅读.

工程评测还要观察每轮意图状态和动作副作用. 实验边界决定结论能否外推, 更新规则决定旧值何时失效, 过程指标则记录错误在轨迹中传播了多远.

**论文实验究竟证明了什么.** [论文 v1](https://arxiv.org/abs/2607.20734)于 2026 年 7 月 22 日提交。作者没有另造一套只能由模型裁判的多轮答案，而是从四个已有可验证数据集出发：GSM8K 取 200 个样本，BIRD-SQL 与 BrowseComp+ 各取 100 个，SWE-bench Verified 取 50 个。单轮题目的原始目标被放到对话末轮，原来的数值答案、SQL 执行器、检索答案或测试套件继续担任 verifier。这样控制了一个关键变量：末轮任务不变，变化的是它如何经过多轮披露、修订和切换才到达模型面前。

主实验把三种转移各应用两次，共 6 次意图转移、7 个用户轮次。论文表 1 的结果不能压成一个平均跌幅，因为领域与 Harness 差异很大。例如 GPT 5.5 在 GSM8K 从 99.0% 降到 80.5%，在 SWE-bench Verified 从 86.0% 降到 80.0%；Kimi K2.6 在 BrowseComp+ 从 55.0% 降到 52.0%，在 SWE-bench Verified 从 86.0% 降到 72.0%。这些数值只适用于论文采样、模型版本与预算。SWE 运行使用扩展后的 mini-SWE-agent v2，多数模型每轮最多 100 次工具调用，Kimi K2.6 与 DeepSeek V3.2 提高到 200 次；BrowseComp+ 每轮最多 50 次搜索。不同预算意味着跨模型横向比较需要谨慎。 相对跌幅按

$$
d_{\mathrm{rel}}=\frac{A_{\mathrm{single}}-A_{\mathrm{evolve}}}
{A_{\mathrm{single}}}\times100\%.
\tag{8}
$$

以 GPT 5.5 的 GSM8K 为例，代入 $99.0$ 与 $80.5$ 得

$$
d_{\mathrm{rel}}=\frac{99.0-80.5}{99.0}\times100\%
\approx18.7\%.
\tag{9}
$$

绝对下降是 18.5 个百分点，相对下降约 18.7%，两者不能混写。论文表中的括号报告相对变化；阅读数字时还应同时看单轮基线，避免把低基线上的小绝对变化误作稳健。

实验支持的结论是：强单轮表现不会自动迁移到受控的演化意图设置，且转移增加时准确率会下降。它没有证明真实用户一定以这三种方式变化，也没有证明所有长对话失败都来自意图跟踪。对话由回溯构造，末轮固定回到源任务；真实协作可能永久改目标、撤销任务，或给出互相冲突又无法自动验证的要求。论文提供的是诊断探针，不是现实交互的完整生成模型。

**转移规则如何避免「只追加不更新」.** 把当前意图写成键值映射更容易实现。设功能为 $f_t$，参数映射为 $C_t$，已披露键集合为 $R_t$，目标状态为

$$
I_t=(f_t,C_t,R_t,g_t).
\tag{10}
$$

$g_t$ 是递增版本。披露新参数 $k=v$ 时，更新 $C_t[k]\leftarrow v$ 且把 $k$ 加入 $R_t$；修订参数时覆盖旧值并使依赖旧值的计划节点失效；功能切换时，新功能保留共享参数，局部参数进入历史而不参与当前执行。 考虑四轮例子。第一轮「找纽约餐厅」，状态为 $(\text{find},\{city:\text{NY}\},1)$。第二轮「要纯素」，加入 $diet:\text{vegan}$。第三轮「改到布鲁克林」，这是 revision，必须覆盖 `city`，不能同时保留 NY 与 Brooklyn。第四轮「订周五七点的那家」，功能切换为 `book`，`restaurant_id`、地点与饮食偏好可以继承，搜索排序参数不一定继承。

若状态以追加日志保存，读取器要计算每个键的最后有效写入：

$$
\hat c_k(t)=c_{k,j^*},\qquad
j^*=\max\{j\le t:k\in\Delta I_j,\;\operatorname{active}(j,t)=1\}.
\tag{11}
$$

`active` 用来排除被撤销的分支。式 (11) 比「取最后一句包含该词的话」严格：用户可能说「不要改到布鲁克林，仍然纽约」，否定范围必须先解析成状态操作。解析不确定时，应保留候选解释与来源轮次，静默选择会掩盖歧义。 计划节点也要记录依赖。例如工具调用 `search(city=NY,diet=vegan)` 依赖 `city@v1` 与 `diet@v2`。第三轮把城市更新到 v3 后，节点有效性为

$$
\operatorname{valid}(p,t)=
\prod_{(k,v)\in D(p)}
\mathbf 1[\operatorname{version}_t(k)=v].
\tag{12}
$$

城市版本不再等于 v1，乘积变成 0，旧搜索结果不能直接用于预订。这一步把「记住用户改主意」转成可执行失效规则。

**评测意图状态而不只评测末轮答案.** 末轮 verifier 保证最终答案可核验，却看不到中途副作用。工程评测应在每轮保存真实状态 $I_t^*$ 与系统估计 $\hat I_t$。对离散槽位可计算字段准确率；对集合槽位可算 precision 与 recall；对版本更新则记录修订生效延迟。若第 $r$ 轮修订，系统在第 $u$ 轮首次执行符合新值的动作，则

$$
L_{\mathrm{adopt}}=u-r.
\tag{13}
$$

仅有延迟仍不够。系统可能在 $r$ 到 $u$ 之间执行不可逆动作。应另记旧意图残留成本

$$
C_{\mathrm{stale}}=
\sum_{t=r}^{u-1}c(a_t)\,
\mathbf 1[a_t\text{ 依赖已失效意图}].
\tag{14}
$$

这样，同样晚两轮才修正的系统会因期间只是读取文件，或已经发送邮件，而得到完全不同的风险描述。 论文还比较了记忆机制，这类对照需要分清两个瓶颈。Oracle recap 把正确意图直接提供给模型，若表现恢复，说明状态提取或保持是主要问题；若仍不恢复，说明模型即使拿到正确状态，也不能据此规划和执行。模型自己生成的 recap 同时受到写入错误、压缩遗漏和读取失败影响，不能只凭 recap 文本看起来完整就认定状态可靠。

真实 Harness 最低限度应保存：当前功能、每个参数的值与版本、来源轮次、置信状态、全局约束、已失效值、依赖这些字段的未完成动作。对话原文仍保留作审计，但规划器读取结构化当前态。用户再次改变要求时，先更新目标状态，再使旧计划失效，最后才生成新动作；顺序反过来会让过期动作抢先执行。

### 2.5. 工程实现与故障注入

真实系统需要一张可审计的当前意图表, 也需要完整变更事件. 两者分开, 才能兼顾规划效率与来源追溯.

实现完成后还要用修订、切换、并发和含糊要求主动攻击状态机. 最小表结构负责保存当前有效值, 事件日志则负责解释这些值怎样产生.

**实现一张可审计的意图表.** 意图表不需要复杂本体，关键是把当前值与变更历史分开。当前表可以包含 `field`、`value`、`scope`、`version`、`source_turn`、`status` 六列；事件表另存 `reveal`、`revise`、`retract`、`switch` 和 `confirm`。规划器只读状态为 active 的当前值，审计器可以沿事件表解释它为何生效。这样既避免每次规划重读整段对话，也不会因覆盖当前值而丢失来源。 全局约束与局部参数必须分层。例如「不得删除生产数据」在任务切换后仍有效，作用域是 session 或 project；「餐厅在纽约」只属于当前搜索功能。功能切换时可按作用域计算保留集合：

$$
C_{t+1}^{\mathrm{keep}}=
\{c\in C_t:\operatorname{scope}(c)\supseteq\operatorname{scope}(f_{t+1})\}
\cup\operatorname{shared}(f_t,f_{t+1}).
\tag{15}
$$

第一项保留覆盖新任务的上层约束，第二项保留两个功能明确共享的参数。其余字段进入 inactive 历史。若共享关系不确定，系统应把字段标为 pending，而不是默认继承。过度继承会把旧任务污染新任务，过度清空则迫使用户重复说明预算和安全要求。 并发更新还需要版本条件。Agent 读取意图版本 $g=12$ 后准备执行，用户同时把目标更新到 $g=13$。动作网关可要求

$$
\operatorname{execute}(a)=
\mathbf 1[g_{\mathrm{plan}}=g_{\mathrm{current}}]
\mathbf 1[\text{硬约束仍满足}].
\tag{16}
$$

版本不一致时重新规划。普通读取无需逐次加锁，会产生副作用的动作则在提交前检查版本。搜索和草稿可以宽松，付款、发布、删除与写生产库必须严格。 恢复时也不能只加载最新摘要。checkpoint 应包含目标版本、当前意图表、尚未完成的计划及其依赖版本、已执行副作用的幂等标识。重启后先读取外部环境，再判断旧动作是否已经发生；若服务端已成功而客户端只看到超时，直接重试可能重复下单。意图连续性因此与环境幂等性相连，不只是对话理解问题。

**用故障注入验证状态机.** 故障注入分三组。第一组在动作前修订一个关键参数，检查旧计划是否失效；第二组在功能切换后重复出现旧参数词，检查系统是否错误复活历史值；第三组让用户给出含糊补充，检查系统是否在高风险动作前确认。每组同时记录状态字段错误、过期动作数和副作用成本。末轮回答即使正确，只要中途已经执行错动作，仍应判为过程失败。

还应加入反向样本：用户重复旧值可能只是在解释历史，没有恢复它；用户说「保留纽约方案作对照」意味着 Brooklyn 仍是主方案，纽约成为并行分支；用户撤销整项任务时，所有局部参数都应失效，但项目级安全约束继续存在。这些样本检验语义作用域与分支管理，简单的「最后出现值胜出」规则无法通过。评测报告应同时给解析正确率与实际动作正确率，因为一个系统可能状态表正确，却在调用工具时仍取错字段。

分支状态还必须有稳定标识，避免同名参数串线。

### 2.6. 把五类事件写成状态代数

官方仓库把演化过程分为 argument reveal、argument revision、function switch，并提供 combined 场景。真实系统还会遇到撤销与确认，因此事件集合可以扩成：

$$
\mathcal O={\operatorname{reveal},\operatorname{revise},
\operatorname{switch},\operatorname{retract},\operatorname{confirm}\}.
\tag{17}
$$

每个事件都作用于带版本的意图状态 $I_t$。`reveal(k,v)` 添加此前未知的字段；`revise(k,v')` 使旧值失效并产生新版本；`switch(f')` 更换功能，同时按作用域迁移共享字段；`retract(q)` 撤销一个字段、分支或完整目标；`confirm(q)` 把 pending 候选提升为 active。状态更新写成：

$$
I_{t+1}=\delta(I_t,o_t),\qquad o_t\in\mathcal O.
\tag{18}
$$

$\delta$ 不能只修改当前表，还要返回失效集合 $Z_t$：哪些计划、缓存结果和待执行副作用依赖了被修改字段。计划器随后只重算受影响子图。若修改城市导致餐厅搜索失效，预算上限与「不得自动付款」仍然有效；把整个状态清空会丢掉无关约束，继续沿用旧计划又会把纽约的结果拿去预订布鲁克林。 事件代数还需要作用域。`retract(city)` 撤销当前分支的城市，与 `retract(task)` 撤销整个预订任务，影响范围不同。每条事件至少带 `target_id`、`branch_id`、`scope`、`source_turn` 与 `event_id`。稳定标识使两个都叫 `budget` 的字段能够分别属于旅行规划和采购任务，不会因名称相同串线。

**并行分支怎样合并.** 用户可能要求「纽约和波士顿都保留，分别给方案」，此时 revision 不应覆盖旧值，而应创建两个分支：

```text
trip@v4
├─ branch-NY: city=New York, budget=200
└─ branch-BOS: city=Boston, budget=200
```

全局约束挂在父节点，城市与搜索结果挂在各自分支。后续一句「纽约那条提高到 260」只更新 `branch-NY/budget`；一句「两边都不要红眼航班」则更新父级约束，两个分支的相关计划都失效。 合并分支时，要区分结果集合合并与目标合并。用户说「把两份方案放在一张表里」只是聚合结果，两个城市条件仍各自成立；用户说「综合两份方案给一个最终行程」会创建新目标，其输入依赖两个分支的已验证结果。合并节点可以写成：

$$
m=\operatorname{merge}(b_1@v_i,b_2@v_j,\rho),
\tag{19}
$$

$\rho$ 是合并规则。任一输入版本变化，$m$ 都应转为 stale。缺少版本条件时，系统会在一个分支更新后继续展示旧的综合结果。

**含糊修订与候选状态.** 「还是用之前那个吧」只有在指代唯一时才能直接更新。若历史中有两个方案，系统应保留候选集合：

$$
Q_t={(I_t^{(1)},p_1),(I_t^{(2)},p_2),\ldots},
\qquad \sum_ip_i=1.
\tag{20}
$$

候选概率可帮助决定是否提问，却不能自动授权高风险动作。可以根据动作代价设置阈值：只读搜索在 $p_{max}$ 较低时也可并行探索；发送、购买和删除要求唯一确认。期望风险为：

$$
\mathbb E[C(a)]=
\sum_i p_i C(a,I_t^{(i)}).
\tag{21}
$$

若不同候选下动作相同，例如两种解释都需要先读取同一文件，就可以继续；若动作分叉且成本高，提问更便宜。这个规则让系统根据歧义的后果选择行为，不必每遇到代词就停下，也不会用一个高置信猜测越过权限边界。 否定范围尤其容易产生候选。「不要把 A 改成 B，保留 C」可能否定整个修改，也可能只否定目标值 B。解析器要把否定作用域映射到事件对象，再由状态机检查当前是否存在对应字段和分支。直接抽取最后出现的实体，往往会把 B 或 C 当作新值。

## 3. 状态准确、动作准确与评测设计

意图表写对，只完成了一半。规划器可能读取旧快照，工具层可能使用硬编码默认值，动作提交前也可能漏掉版本检查。评测应把状态准确与动作准确分开。 对每个字段 $k$，定义当前值准确率：

$$
A_{state}=\frac{1}{|K|}
\sum_{k\in K}\mathbf1[\hat c_k=c_k^*\land
\hat v_k=v_k^*].
\tag{22}
$$

版本也要匹配，因为相同值可能来自一次撤销后重新确认；只有值没有来源版本，旧计划仍可能被误判有效。动作一致率则检查实际工具参数是否来自当前意图：

$$
A_{act}=\frac{1}{N}
\sum_{t=1}^{N}\mathbf1[a_t\models I_t^*].
\tag{23}
$$

若 $A_{state}$ 高而 $A_{act}$ 低，问题在状态到动作的连接；两者都低，先修意图解析和更新；状态低但动作偶然正确，可能是默认值碰巧命中，不能当作系统稳健。 还可以建立转移混淆矩阵。真实事件是 revision，系统却判成 reveal，会同时保留新旧值；真实事件是 switch，却判成 revision，可能把旧功能的局部字段带进新功能；真实事件是 confirm，却判成普通重复，pending 状态永远无法提交。把准确率按事件类型拆开，比一个总平均更能定位状态机缺口。

### 3.1. 意图债务与污染范围

错误意图若未被及时纠正，会沿依赖图产生「意图债务」。设第 $r$ 轮发生修订，系统在第 $u$ 轮才采纳，期间受旧版本影响的动作集合为 $A_{r:u}^{old}$，其污染范围可写成：

$$
D_{intent}=\sum_{a\in A_{r:u}^{old}}
\left(c(a)+\lambda|\operatorname{desc}(a)|\right).
\tag{24}
$$

$c(a)$ 是动作成本，后继数反映返工范围。一次错误搜索成本很低，若它的结果被用于预订、付款和通知，污染就会迅速扩大。这个指标与式 (14) 的旧意图残留成本方向一致，额外把下游影响纳入计算。 恢复完成也需要定义。系统删掉旧值还不够，依赖旧值的计划、缓存和副作用都要处理。可将恢复条件写成：当前状态与用户目标一致；旧版本动作全部失效；可逆副作用已经撤销；不可逆副作用已向用户报告并进入补偿流程。只修摘要不修环境，会留下一个看起来正确、实际仍污染的系统。

### 3.2. 官方构造管线能验证什么

微软仓库公开了五阶段流程：从源题抽取 function、arguments 与 answer；为 argument 生成 counterfactual；为 function 生成 predecessor；组装 situated simulation；最后调用原数据集的 evaluator。仓库明确说明这是 code-only release，没有随仓库发布模型或新数据集，使用者仍需准备第三方 benchmark。 这种设计的优势是末轮 verifier 保持稳定。GSM8K 仍核对数值答案，BIRD-SQL 仍执行 SQL，SWE-bench Verified 仍运行测试。因变量主要来自对话中发生的 reveal、revision 与 switch，避免模型裁判同时改变题目和评分标准。Eval mode 使用确定性样本，train mode 支持随机采样；scenario 由 turn、revision 和 switch 数量自动推断。

它的边界也很明确。对话由结构化源题回溯构造，因此 function 与 arguments 比真实用户表达更清楚；末轮锚回原任务，适合保留自动验证，却覆盖不了永久换目标、多个目标并存和用户中途放弃。仓库的 TRANSPARENCY 文件也把它定位为研究框架，不适合直接作为生产认证或高风险领域质量证明。 复现实验时要记录源数据版本、固定 evaluation indices、构造模型、counterfactual/predecessor 数量、turn scheduler 参数和 naturalizer 模型。只给最终对话文本，无法判断不同实验是否用了相同源题与相同演化强度。Naturalizer 还可能意外增加或删除约束，抽样检查自然化前后的结构化事件是否一致很有必要。

**一套配对实验.** 每个源题生成 fully-specified 基线与演化版本，两者共享最终目标和 verifier。对同一模型分别运行，得到成对结果 $(y_i^{base},y_i^{evo})$。平均退化为：

$$
\Delta=\frac1n\sum_{i=1}^{n}
(y_i^{base}-y_i^{evo}).
\tag{25}
$$

随后按 reveal、revision、switch 和 combined 分桶，避免 combined 的总体跌幅掩盖某一种转移特别困难。还可以控制总用户轮数，只改变 revision 次数；或固定转移次数，增加两个转移之间的间隔，观察系统是否因时间距离而忘记旧约束。 过程日志再加入三项指标：修订采纳延迟、旧意图残留成本和澄清效率。澄清效率可以计算必要澄清中成功消除歧义的比例，同时报告无谓提问数。一个系统每轮都追问，动作错误可能很少，却把协作负担全部推给用户；只看最终正确率会奖励这种保守策略。

故障注入则在动作边界发生：计划生成后、工具调用前修改关键参数；工具已经部分执行时切换功能；checkpoint 恢复后撤销一个旧约束。每次都记录当前意图表、计划依赖版本、真实环境和下一次动作。只要四者中有一项仍引用旧版本，状态传播链就还没有修好。

### 3.3. 生产系统中的确认策略

生产系统需要把确认频率与风险联系起来。每次 reveal 都追问会令人无法使用，任何 revision 都直接执行又可能造成损失。可以给动作设置风险等级，并结合意图状态决定门槛：

| 状态 | 只读动作 | 可逆写入 | 不可逆写入 |
|---|---|---|---|
| active 且版本一致 | 执行 | 执行并验证 | 按授权策略执行 |
| pending 单一候选 | 可探索 | 暂缓或创建草稿 | 请求确认 |
| 多候选冲突 | 并行收集共同信息 | 暂缓 | 请求确认 |
| stale | 重新读取 | 重新规划 | 禁止执行 |

确认消息应指出具体分歧和后果，例如「当前有纽约与波士顿两个分支，付款将作用于哪一个？」；泛泛地问「确定吗」不能消除状态歧义。用户回答后生成 `confirm` 事件，绑定候选 ID 和目标版本。若等待期间目标又发生变化，旧确认自动失效。 这样的确认门也保护并发场景。用户在网页修改参数，Agent 在后台仍握着旧计划；动作提交前比较 `goalVersion`，不一致就撤销提交。高风险动作多一次版本读取，成本远小于执行错误后再补偿。意图跟踪最终会落到一个很朴素的工程事实：**用户改一句话，所有依赖旧话的动作都要知道自己已经过期。**

Quick test：`intent_construction/intent_extraction/generate.py --dataset gsm8k --num_samples 3`。

## 4. 冲突、切换与持久化

把用户消息全部追加到历史，无法自动得到当前目标。系统需要一个更新算子

$$
G_{t+1}=U(G_t,u_{t+1},c_t),
$$

$G_t$ 是当前目标状态，$u_{t+1}$ 是新消息，$c_t$ 是任务与环境上下文。$U$ 的输出除了新目标，还应包含变更类型、被替代字段和仍待确认的冲突。 最小变更类型包括增补、覆盖、撤销、优先级调整和任务切换。增补保持旧字段；覆盖只替换指定字段；撤销将字段标为失效；优先级调整改变执行顺序但不删除验收项；任务切换创建新的目标对象，并决定旧任务暂停、结束还是保留后台状态。

自然语言中的「也」「改成」「先别」「不用了」「继续刚才」分别提示不同操作，但词面规则不够。用户说「也别删测试」里的「也」是新增禁止项；说「颜色也改成蓝色」可能覆盖旧颜色。判断需要结合字段和前文值。 目标状态可以表示为带来源的谓词集合

$$
G_t=\{(k_i,v_i,r_i,\tau_i,s_i)\},
$$

$k_i$ 是字段，$v_i$ 是值，$r_i$ 是关系类型，$\tau_i$ 是生效版本，$s_i$ 指向原始消息。发生争议时可以回到来源，而不依赖多次摘要后的措辞。 更新不能静默丢掉未知字段。新消息只提标题，不意味着正文要求失效；覆盖范围应最小化。若新旧值在同一字段冲突，最新明确指令通常覆盖；若属于不同层级，例如全局禁止与局部许可，需要权限和作用域规则决定。

### 4.1. 冲突不是都用「最后一句赢」

时间顺序是常用默认，却不能处理所有约束。系统指令、用户授权、项目规范和当前偏好具有不同优先级；同一用户消息里也可能同时存在互相不兼容的条件。 把约束写成带优先级的集合 $C=\{(c_i,p_i)\}$。若 $c_i$ 与 $c_j$ 不可同时满足，优先保留更高 $p$；优先级相同且没有明确覆盖关系时，状态进入冲突，而非任选一句。冲突状态应阻止依赖该字段的高风险动作。 范围也会消解表面冲突。「不要修改正文」与「修正这一处图片引用」可以同时成立，因为后一条是局部例外；「所有文件使用 UTF-8」与「这个二进制图片保留原格式」作用对象不同。更新器需要记录路径、时间、任务阶段等作用域。

有些约束是软偏好。用户希望语言简洁，又要求完整推导，二者需要在文章不同层次权衡；它们不是逻辑矛盾。硬约束违反即不合格，软偏好进入效用函数。混成同一布尔集合会让系统频繁请求不必要的澄清。 可以用可满足性检查发现硬冲突。例如输出长度必须小于 100 字，同时要求逐步证明一个已知需要更长表达的命题。系统应解释冲突的具体字段并请求选择，而非先写一版再声称尽力满足。

冲突解决结果也要版本化。用户选择其中一项后，旧冲突记录保留作审计，但不再阻塞；若后续又恢复旧要求，系统知道这是显式回滚而非第一次出现。

**从消息分类到动作影响.** 只判断消息属于「增补」或「覆盖」还不够，系统要知道哪些计划和产物受影响。设目标字段变化集合为 $\Delta G$，依赖图为 $D$，受影响节点为

$$
I=\operatorname{Descendants}_D(\Delta G).
$$

只有 $I$ 中已经完成或正在执行的节点需要重验、取消或回滚。与变化无关的并行工作可以继续。 例如用户把输出格式从 Markdown 改为 PDF，资料收集和事实核查仍有效，排版与交付流程需要更新；用户更换核心研究问题时，早期来源选择也可能失效。用依赖传播决定范围，比按时间把后续工作全部作废更精确。 正在运行的动作需要抢占语义。可安全取消的任务直接停止；不可取消的外部操作记录为旧版本产物，完成后不自动提交；已经产生副作用的动作需要补偿或请求用户决定。简单忽略旧进程会让它稍后写回过期结果。

目标变化还会影响证据。旧测试证明版本 $G^{(k)}$ 下的产物，目标升到 $G^{(k+1)}$ 后，如果变化字段在测试覆盖范围外，证据可复用；否则状态从已验证降回待验证。验证结果不能只绑定文件哈希，还要绑定对应要求。 动作影响分析应在回复用户之前完成。系统可以先确认新要求和受影响范围，再继续安全分支；若直接说「好的」却没有取消旧路径，表面理解与实际执行分离。

### 4.2. 确认策略的决策论

任何不确定都询问用户，会让协作停滞；从不询问会在高风险歧义上擅自决定。确认策略应比较错误行动代价与询问成本。 设解释集合为 $z\in\mathcal Z$，当前后验为 $p(z\mid h_t)$。直接选择动作 $a$ 的期望损失为

$$
L_{\mathrm{act}}=
\min_a\sum_zp(z\mid h_t)\ell(a,z).
$$

询问的期望损失包含交互成本 $C_q$ 和回答后残余损失。若询问带来的预期损失降低超过 $C_q$，才值得打断用户。 高风险、不可逆动作使 $\ell(a,z)$ 很大，即使歧义概率小也应确认；可回滚草稿可以先按最可能解释执行，并明确假设。这个原则比固定置信阈值更贴近任务后果。 问题应针对能改变决策的变量。询问「你能说详细点吗」把组织成本推给用户；询问「这里的‘删除’只指生成文件，还是也包括原始数据？」直接切分两条高影响路径。最多给少量互斥选项，并说明默认方案。

用户没有回复时，系统只能继续不依赖该选择的工作。若所有关键路径都被阻塞，状态应明确等待；不能把沉默当授权。低风险问题可采用可撤销默认值，但要在交付前再次暴露。 确认本身也可能过期。用户回答时环境或目标已经发生变化，需要把答案应用到提问时的字段版本。若同一字段在等待期间又被更新，旧回答不能直接覆盖新值。

### 4.3. 目标切换与任务栈

用户在执行中提出新问题，可能只是插入一个短查询，也可能替换当前任务。系统需要任务栈或任务图，而非单一「当前目标」字符串。 插入任务完成后可返回原任务，前提是原状态仍有效。切换前保存 checkpoint：目标版本、已验证结果、运行中动作和下一步。返回时重新读取环境，检查插入任务是否改变共享资源。 完全替换时，旧任务可取消、归档或保留为暂停。取消涉及外部副作用清理，归档保留审计，暂停保留恢复入口。三者不能都用「停止」概括。

多个任务共享文件或浏览器会话时，任务栈不是隔离的。新任务修改同一对象，会使旧 checkpoint 过期；恢复要做三方比较：旧基线、旧任务未完成修改、当前环境。无法机械回到旧快照覆盖新成果。 优先级变化也不同于切换。用户要求「先修这个错误，再继续写文档」，两个目标都保留，只改变调度。计划检查应确保低优先任务没有从验收清单消失。 评测目标切换时，需要同时测插入任务成功、原任务恢复和交叉污染。只看新任务完成会鼓励系统抛弃旧状态；只看最终原任务，又可能忽略插入请求。

### 4.4. 意图状态的持久化

对话摘要适合人读，不适合承担唯一目标状态。持久化对象至少包含目标字段、约束、验收项、来源消息、版本关系、未决问题和状态。自然语言解释可以作为附加层。 状态更新采用追加事件比原地覆盖更容易审计。事件日志记录 `GoalCreated`、`ConstraintAdded`、`FieldOverridden`、`RequirementRevoked` 和 `TaskSwitched`；当前视图由事件折叠得到。出现错误时可以定位哪次更新造成。 事件重放必须确定。若同一日志在新版解析器上产生不同状态，旧任务无法恢复。schema 和更新规则需要版本化，迁移时保存前后差异。自由文本字段仍可能需要模型解释，但关键布尔和枚举字段应有明确语义。

敏感用户偏好不应无限保存。目标状态按任务生命周期保留，长期偏好需要单独授权和删除机制。把一次临时要求写进全局记忆，会导致后续任务莫名继承。 持久化状态还要防并发写。两个 agent 同时根据旧版本更新同一字段，后写可能覆盖前写。使用期望版本号或 compare-and-swap，冲突时重新读取并合并，而非静默 last-write-wins。

### 4.5. 可证伪的评测设计

测试增补时，后续消息只添加一项要求，旧验收项仍需全部满足；测试覆盖时，新值应替代旧值，系统不能同时执行；测试撤销时，旧要求从计划与验证中消失；测试切换时，原任务状态要按协议保存。 每类事件都应设置表面相似的对照。普通讨论不改变目标，模型不能因为出现「也许」「想想」就重规划；引用他人要求不等于用户采纳；用户描述过去决定，不一定是在当前恢复它。

评测中间状态比只看最终答案更严格。检查当前目标字段、计划覆盖、旧动作是否取消、证据是否降级和确认问题是否针对歧义。最终碰巧正确，若中间仍执行过期高风险动作，不能算通过。 事件位置需要随机化，并覆盖计划前、执行中、验证后和等待外部结果时。系统若只在收到消息的下一轮检查目标，异步动作仍可能稍后提交旧结果。 错误分类包括未检测变化、误判变化类型、错误作用域、传播范围不全、过度回滚和确认策略错误。它们对应不同修复路径。一个总准确率无法说明状态更新器哪里坏了。

最后用真实 Harness 运行，而非只让模型对消息做离线分类。分类正确却没有更新计划、取消工具或重验产物，仍不具备处理演化意图的能力。

**时间表达与生效窗口.** 用户要求可能立即生效，也可能针对未来阶段。「下次发布再换模板」「训练完成后先别部署」「今天以内保留旧接口」都包含时间条件。目标字段需要生效时间与失效时间，不能在消息到达时一律覆盖当前状态。 可将约束表示为

$$
c_i=(\phi_i,\,[t_i^{\mathrm{start}},t_i^{\mathrm{end}}),\,e_i),
$$

$\phi_i$ 是谓词，时间区间决定何时激活，$e_i$ 是触发事件。事件条件比绝对时间更常见，例如「测试全部通过以后再提交」。执行前检查当前时间与事件状态，避免提前应用或错过约束。 相对时间需要锚点。「明天」相对于消息发送时间，而非系统恢复时间；「三小时后」在任务暂停期间是否继续计时也要明确。持久化时应解析为绝对时间并保留原文与时区。 周期性要求如「每次发布前都跑安全检查」属于阶段不变量。首次完成后不能永久勾选；每个发布事件都重新实例化验证任务。

时间窗口过期后，依赖它的产物未必自动失效。临时许可证到期会使部署不可继续，临时写作偏好到期只影响新内容。失效传播仍由依赖图决定。

### 4.6. 授权与偏好的分离

用户说「我喜欢简洁」是偏好，说「允许删除这些文件」是授权。偏好可以影响效用排序，授权改变可执行动作集合。把两者混合会导致系统把风格倾向误当成高风险许可。 动作集合可写为

$$
\mathcal A_t^{\mathrm{allowed}}
=\{a:\operatorname{scope}(a)\subseteq P_t\},
$$

$P_t$ 是当前授权范围。新授权可以扩大集合，撤销授权立即缩小；已经启动但尚未提交的动作要检查是否能够取消。 授权应绑定对象与操作。「可以改仓库」不自动包括 push、删除远程资源或发送消息；「所有权限」也需要遵守任务边界和不可逆动作规范。系统不能从便利性推断更广权限。 偏好冲突可以权衡，授权冲突必须阻止动作。例如用户希望快速完成，又没有允许发布，速度偏好不能越过发布权限。状态表示中给两类字段不同类型，规划器才不会放进同一个加权分数。

授权还可能一次性。用户确认删除某个精确路径，不代表以后任何相似路径都可删除。操作完成后消费授权，新的目标需要新确认。

## 5. 跨 Agent、安全与语言约束

一条用户纠正可能只针对当前对象, 也可能暴露一条稳定规则. 例如, 用户修正某份报表中的日期, 可能只是单个数据错误; 用户声明所有导出都必须隐藏账户标识, 则会改变同类任务的共同约束. 系统需要把实例修复与规则更新分开存储.

将反馈抽象为候选规则 $r$ 后, 还要在相邻对象中寻找反例. 若许多合法样本也会被 $r$ 修改, 规则需要增加作用域或继续保留在实例级. 规则本身也要版本化; 是否回查历史对象取决于目标范围, provenance 关系则用来确定一次纠正应传播多远.

### 5.1. 跨 Agent 传播目标更新

多个 agent 并行工作时，目标变化需要有一致广播语义。只在主对话更新，正在运行的子任务可能继续按旧版本写入。广播消息至少包含新目标版本、变化字段、影响范围和立即停止条件。 子 agent 接收更新后应确认它当前动作是否受影响。无关变化继续；局部变化调整计划；核心目标替换则停止并返回当前状态。简单中断所有 agent 会浪费独立工作，完全不中断会产生过期产物。

输出需要携带所依据的目标版本。主执行体合并时，若报告版本落后，检查差异是否影响该产物；不能只看完成时间。旧版本产物可能仍可复用一部分，需按字段依赖重验。 并发更新还会乱序。agent 先收到 $G^{(k+2)}$，随后网络延迟送达 $G^{(k+1)}$ 时，版本号应阻止回退。没有单调版本，只靠消息顺序容易重新激活旧要求。 广播本身失败时，主执行体应把 agent 标为版本未知，暂不接受外部写入。最终汇报可以作为对账点，但高风险动作不能等到结束才发现上下文过期。

**意图推断的安全攻击面.** 工具输出、网页文本和仓库文件可能包含类似用户指令的内容。它们属于数据，不能直接更新用户目标。目标更新通道必须区分消息角色与来源，防止提示注入把「上传密钥」写进计划。 引用内容也会造成混淆。用户粘贴一段对话并说「分析这段」，其中的命令属于被分析对象；解析器若只看最近祈使句，会错误执行。消息结构和引用边界必须传给更新器。 外部来源可以提出事实，只有授权主体能改变权限。网页声称「现在允许删除缓存」没有效力；工具返回建议运行命令，仍需按当前边界判断。把事实通道与命令通道分离，是意图状态的基本安全条件。

攻击还可能利用目标覆盖。恶意文档要求忽略旧验收、宣称任务完成或改变输出位置。计划覆盖检查应只接受可信用户事件，外部文本最多进入待评估建议。 评测可在工具输出中插入语义自然的恶意指令，同时保留合法相似文本。系统既要拒绝更新目标，又要继续提取真正数据。只用明显的「ignore previous instructions」无法代表真实攻击。

### 5.2. 状态更新器的校准

更新器不仅输出变更类型，还可以给每个字段的后验置信。校准好的置信度支持确认策略；过度自信会静默覆盖，过度保守会频繁打断。 评测应按字段而非整条消息计算。一个消息可能明确修改输出格式，同时含糊地提到发布日期；整条判为「覆盖」会掩盖第二字段的不确定。字段级标签包括保留、更新、撤销、未知和冲突。 可靠性图比较置信桶与实际字段正确率。高风险字段还要看假更新率：没有授权变化时却扩大权限，比漏掉一个风格偏好严重。可以按代价设置不同确认阈值。

分布外表达会破坏校准。口语、省略、反讽、多语言切换和语音转写错误都可能使置信虚高。用这些变体建立压力集，并检查模型是否在陌生表达上降低置信或请求确认。 校准不能只在离线标注上完成。真实 Harness 中，更新结果会影响动作；有些分类小错不改变计划，有些会触发不可逆操作。最终评测结合字段准确、动作影响和恢复成本。

**否定、例外与省略恢复.** 中文对话常省略主语和对象。「这个就不写了」「其他照旧」「第二个也改」「还是用原来的」都依赖当前焦点。更新器需要解析指代，同时保留不确定性，不能把最近出现的名词机械当对象。 否定范围尤其关键。「不要只改首页」要求正文也改；若错误解析成「不要改首页」，动作方向完全相反。可以把句子转成谓词后检查否定作用域，再与可执行结果对照。 例外会修改一般规则。「所有文章都扩写，翻译稿除外」形成集合差；后续「这篇翻译稿也补一下」为单项例外。规则状态应支持包含、排除和更具体范围覆盖，而非把清单展开成容易过期的文件枚举。

「其他照旧」具有闭世界含义：只更新明确提到的字段，其余保持。它能阻止模型借机重写未请求内容。相反，「按这套方案整体重做」允许更广传播，但仍受全局边界约束。 恢复省略需要当前话题栈。用户连续讨论三篇文章后说「第三个先停」，系统必须知道候选集合和排序来源。若多个列表都可能对应，应确认，而不是凭最近 token 猜测。 评测可以使用最小对：只改变否定位置、量词或指代，正确状态更新应随语义变化。单纯关键词分类在这类样本上容易暴露。

**量词与范围漂移.** 「每篇」「这几篇」「至少五篇」「大部分」对应不同验收。目标状态要保存量词，而非都归纳成「增加文章」。完成检查也必须使用同一集合与计数口径。 集合本身可能动态变化。要求「content 下每个知识库」时，后续新建知识库是否纳入，取决于规则是对当前快照还是持续集合。持久化时可记录集合查询与评估时机，例如创建目标时冻结成员，或验收时重新枚举。 最小值要求 $n\ge k$，目标值可能允许更多；精确值 $n=k$ 则超过也不合格。模型常把「至少」遗失，导致到达阈值后错误停止或把超额工作当问题。

「除非确实写不到」为条件例外，需要定义证明责任。执行体不能自行用它逃避困难任务；应记录已覆盖材料、缺失证据和停止原因，再由验收清单标为内容上限。 范围更新会影响计划规模。用户从「这一章」扩到「整个库」，已有工作仍有效，但必须重新枚举集合和估计成本；从全库缩到单章，则取消无关分支并保护已经产生的未提交修改。 量词错误适合自动检查。文件数量、长度阈值、每篇来源数都可以由脚本验证；自然语言理解只负责把要求编译成检查式。脚本覆盖不到的质量要求仍需人工或内容审计。

### 5.3. 意图演化中的事实核查

用户可以要求保留主观判断，也可以提出需要核实的事实。状态层要区分「作者立场」与「外部事实」，避免以纠错为名删掉有意表达，也避免把主观猜想写成已证实结论。 每条主张可标注类型：可核事实、条件推断、作者评价和研究假说。可核事实需要来源；条件推断写明前提；评价允许鲜明语言；假说要保持不确定性。用户后续说「这个就是我的判断，可以留下」相当于改变主张类型，不是证明事实为真。

事实更新也会改变目标。发现引用日期错误，需要修正文及依赖它的时间线；发现主体混淆，可能影响整章叙事。核查结果通过依赖图传播，而非只改一句数字。 来源冲突时不能自动选择更符合现有叙事的一方。记录版本、发布日期、原始口径和冲突点；优先一手材料，但一手材料也可能后续修订。无法判定则保留不确定性。 主观评价后应接具体开放项或实验事实，是写作证据结构，不代表要插入元评论解释「这是主观」。读者能从措辞和证据自然区分，正文无需不断为作者语气辩护。

**表达偏好也可以版本化.** 用户可能逐步修订术语、标点、篇幅和强调方式. 稳定偏好进入长期规则, 当前产物的局部要求留在任务状态; 两者冲突时, 作用域更窄且时间更新的明确要求优先.

表达规则不能退化成无条件替换. 同一个词在口语说明、数学定义和引用材料中承担的功能不同, 更新器要同时读取文体与引用边界. 自动检查可以定位高风险模式, 最终是否修改仍取决于句子是否准确表达了当前意图.

### 5.4. 从意图到验收器的编译

可机器判断的要求应转成验收器. 文件范围、数量阈值、数据类型、权限集合和输出格式都可以落成确定性检查. 编译过程要保留对应关系

$$
r_i\longrightarrow v_i(x)\in\{0,1,\text{unknown}\}.
$$

`unknown` 很重要: 验收器没有覆盖某项, 不能默认通过. 语义正确性、事实可靠性和主观质量通常仍需要人工或更强的外部证据. 验收器自身也有版本; 用户提高阈值后, 状态更新必须同步修改检查参数, 否则终点会产生假阳性.

多个要求可以共享一个检查, 但证据范围必须明确. 局部检查只能证明当前对象, 全局声明则需要覆盖完整集合. 目标变化后, 系统应根据检查范围决定复用旧证据还是重新运行.

验收失败应回到对应目标字段与文件，不只是输出一串错误。这样计划可以生成修复分支，并在修复后只重跑受影响检查，再在里程碑运行全量回归。

**用户撤回与遗忘请求.** 用户撤回一项要求时，系统要停止未来使用，并处理已经派生的计划、产物和记忆。撤销不等于删除历史审计；二者涉及不同保留政策。 若撤回发生在写入前，取消动作即可；文件已修改但未提交，可以回退对应片段或保留待用户决定；内容已经发布，需要补偿或新版本，无法假装从未发生。 遗忘请求要求从长期记忆或持久状态删除个人偏好与数据。派生摘要、索引和缓存也要纳入范围。审计日志可以只保留删除事件和不可逆最小证据，不继续保存被删除内容。

删除范围必须精确解析。用户说「别记住这个偏好」通常不要求删除当前文章；说「删掉刚才上传的文件」涉及具体对象和副本。高风险或范围模糊时确认目标列表。 撤回后的未来行为需要验证。清空一条记忆后重新启动会话，系统不应继续引用；只从主表删除而向量索引仍召回，说明遗忘不完整。

### 5.5. 演化意图的成本模型

处理目标变化会产生检测、重规划、取消、回滚、重验和沟通成本。过度灵活的系统每条消息都全量重算，虽然正确却低效；过度稳定则继续旧路径。 总成本可写成

$$
C=C_{\mathrm{detect}}+C_{\mathrm{update}}+C_{\mathrm{cancel}}
+C_{\mathrm{redo}}+C_{\mathrm{verify}}+C_{\mathrm{ask}}.
$$

状态依赖图减少 $C_{\mathrm{redo}}$，结构化字段减少 $C_{\mathrm{detect}}$，明确确认策略控制 $C_{\mathrm{ask}}$。这些组件的价值不仅体现在最终成功，也体现在避免无关返工。 评测要给用户变化强度相同、任务规模不同的样本。全量扫描成本随文件数增长，局部传播应只随受影响子图增长。若系统每次都接近全量成本，说明它没有利用依赖结构。 取消延迟也是成本。后台任务在收到撤销后继续运行，可能消耗资源或产生过期写入。记录更新消息到实际停止的时间，以及这段时间产生的动作。

成本不能鼓励忽略用户。系统若不检测变化，表面更新成本为零，最终产物却错误。所有成本比较都在相同目标遵守率或安全成功门槛下进行。

## 6. 状态机、反事实与异步验证

一个可执行的意图状态机至少包含 `active`、`waiting`、`paused`、`superseded`、`cancelled` 和 `completed`。`waiting` 依赖外部输入，`paused` 是用户或调度主动暂停，`superseded` 表示被新版本替代，`cancelled` 要求停止且不再恢复。 状态转移带守卫。只有所有验收条件有证据时才能进入 `completed`；收到新版本后旧目标进入 `superseded`，其运行中动作按取消策略处理；等待条件满足后从 `waiting` 返回 `active`，先重新验证环境。 非法转移应被拒绝。例如已取消任务不能因旧异步回调自动恢复，已完成任务收到新要求应创建新版本或重新打开，而非悄悄修改完成记录。

状态机只控制生命周期，具体目标仍存于字段与依赖图。把所有语义塞进几十个状态会爆炸；把生命周期完全留给自然语言，又无法可靠恢复。两层组合更合适。 评测通过事件序列覆盖每条边，并加入乱序、重复与延迟消息。幂等更新保证同一事件重复送达不产生两个版本，单调版本保证旧事件不能回滚新状态。

### 6.1. 需求之间构成偏序

把用户要求存成一张无序清单，会在第一次冲突时失效。真实任务里的要求存在「支配关系」：安全边界支配速度偏好，明确的局部修订支配早先的通用要求，验收条件支配执行者自行选择的完成标准。还有一些要求互不支配，例如「多补原理」与「增加适量图片」可以并行满足，不能为了其中一项自动牺牲另一项。 可把要求集合记为 $R=\{r_1,\ldots,r_n\}$，用 $r_i\prec r_j$ 表示冲突时 $r_j$ 优先。这个关系通常只构成偏序：并非任意两条都能比较。规划器先寻找同时满足的可行解；只有可行域为空，优先关系才参与裁决。若一开始就把偏好压成单一分数，低权重要求容易在没有真实冲突时也被丢掉。

优先来源至少有四种。第一种来自权限和安全规则，这类约束不能被普通偏好覆盖。第二种来自用户显式措辞，如「先完成 A，再处理 B」。第三种来自作用域，更具体且更新更晚的要求通常覆盖同一字段上的一般规则。第四种来自依赖关系：必须先取得证据，才能据此改写结论。它们的依据不同，状态中应保存优先边的来源，不能只留一个不可解释的整数。 局部覆盖还要满足「最小变化」。用户把一篇正文的长度阈值从七千提高到两万，只更新这篇或明确指定集合的阈值，其他格式、引用和提交要求继续有效。设旧目标为 $G$，新消息解析出补丁 $\Delta$，更新可写成

$$
G'=\operatorname{patch}(G,\Delta,S),
$$

其中 $S$ 是作用域。`patch` 只触碰 $S$ 内被点名字段，并保留其余字段的版本。这样能够避免一句局部纠正触发全局目标重建，继而把已经确认的限制一起冲掉。 偏序中可能出现环：用户先说 A 优先于 B，后来又要求 B 不能因 A 延误。环不应靠随意排序打破。系统要定位形成环的最小要求集合，说明哪几个条件无法同时成立，再请求用户裁决。对可延迟处理的环，可以把任务拆成不同阶段，使同一对要求在不同阶段拥有不同优先关系。

评测需求优先关系时，不能只给显式的「A 更重要」。更有价值的样本会把优先级散落在不同轮次，并加入一个表面紧急但权限不足的请求。正确系统既要保留被延后的低优先任务，也要拒绝越权捷径，还要在高优先任务完成后恢复原计划。

### 6.2. 用反事实检验模型究竟理解了哪次变化

一次成功执行不能证明状态更新正确。模型也许凭最近一句话猜中了答案，却没有维护可复用状态。反事实测试固定大部分轨迹，只改变一个事件、一个作用域或一个量词，观察后续计划是否发生对应的最小变化。 设完整轨迹为 $H=(m_1,ldots,m_T)$，把第 $k$ 条消息替换为 $m_k'$ 得到 $H^{(k)}$。若修改只涉及字段 $f$，理想状态差异应限制在 $f$ 及其依赖闭包内：

$$
\operatorname{diff}(G_T,G_T^{(k)})
\subseteq \operatorname{Desc}(f)\cup\{f\}.
$$

差异为空，说明系统漏掉更新；差异扩散到无关字段，说明它把局部变化误当成整体重启。这个判据比末轮答案相似度更能定位意图传播是否准确。 反事实可以沿几条轴构造。把「至少五份」改成「正好五份」，只应改变计数上界；把「这一章」改成「整个库」，应扩大文件集合；把「允许删除引用」改成「找不到原件时才允许删除引用」，应在动作前增加条件；把用户指令换成被引用材料里的同一句话，则不应更新目标。每一对只改一个因子，错误来源才可辨认。

还要测试时序反事实。相同两条消息交换顺序，结果可能因覆盖关系而不同；若两条更新作用于独立字段，交换顺序则应得到相同状态。这对应交换律检查：独立补丁 $\Delta_a$ 与 $\Delta_b$ 应满足

$$
\operatorname{patch}(\operatorname{patch}(G,\Delta_a),\Delta_b)
=\operatorname{patch}(\operatorname{patch}(G,\Delta_b),\Delta_a).
$$

不满足时，要么两个字段存在未记录依赖，要么更新器带入了消息位置之类的偶然因素。 反事实测试也能识别「语言记忆」和「状态记忆」的差别。将早期要求改写成同义句，状态与行动应保持稳定；删除那条要求，相关行为才应消失。如果轻微措辞变化就令计划完全不同，系统依赖的是表面模式；如果删除后仍继续执行，旧要求可能已经污染摘要、缓存或工具参数。

### 6.3. 异步结果返回时必须重新证明它仍然相关

长程任务常在等待搜索、训练、人工回复或子任务结果时继续演化。结果返回并不意味着它还能直接使用，因为它是基于某个目标版本、输入快照和环境状态生成的。系统需要把异步结果视为带前提的证明，而非永远有效的事实块。 每个结果可携带上下文指纹

$$
z=(v_G,h_I,v_E,A),
$$

其中 $v_G$ 是目标版本, $h_I$ 是输入集合哈希, $v_E$ 是环境版本, $A$ 是结果依赖的假设. 合并前要与当前状态比较. 目标变化若与结果无关, 结果可以直接复用; 输入集合只增加成员时, 旧结果可以保留为局部证据; 关键假设被撤回后, 结果必须失效并触发重算.

例如一个子任务已经完成接口实现, 用户随后把目标改成先解决数据一致性. 已验证的接口行为和测试证据仍可保留, 依赖旧目标的执行顺序与完成声明则需要重新判断. 结果应按依赖粒度复核, 不能整包接受或整包丢弃.

异步动作还可能产生外部副作用。搜索结果过期只需重查，已经发出的消息或已经提交的计算任务则不能靠丢弃返回值撤销。目标更新时要先区分可取消、可补偿和不可逆动作。可取消动作发送终止信号；可补偿动作记录逆操作；不可逆动作立即暴露给用户，并在后续计划中吸收影响。 竞态测试需要安排旧结果在新目标建立后到达，并让多个结果以不同顺序返回。系统必须依据版本和依赖判断，而不是「最后返回者赢」。同一结果重复到达只登记一次；新结果先到、旧结果后到时，旧结果不能覆盖新结论；两个结果覆盖互补范围时则允许合并。

**计划覆盖率与目标覆盖率要分开计算.** 维护了正确目标，不代表计划会实现它。状态更新之后要重新建立目标到计划节点的覆盖关系。每个可执行要求至少对应一个实施节点和一个验证节点；只有实施没有验证，系统无法证明完成；只有验证没有实施，失败后也找不到修复入口。 令要求集合为 $R$，计划节点集合为 $P$，覆盖矩阵 $M_{ij}=1$ 表示节点 $p_j$ 对要求 $r_i$ 有直接贡献。要求覆盖率可以写为

$$
\operatorname{Cov}(R,P)=\frac{1}{|R|}
\sum_i \mathbf 1\!\left[\sum_j M_{ij}>0\right].
$$

这个数只能发现遗漏，不能证明计划充分。更严格的检查还要区分实现边与验证边，并检查它们的先后关系。对「每篇正文两万字且不能灌水」，字符计数是验证节点，重复段检测和人工内容审查也是验证节点；单纯增加扩写步骤无法覆盖质量条件。 目标变更后不必总是重建整个计划。新增要求时寻找未覆盖项并插入节点；覆盖要求时，定位依赖旧字段的节点并重算；撤销要求时，删除只为它存在的节点，但保留同时服务其他要求的共享节点。这个过程类似增量编译，关键是计划节点要声明自己的输入目标字段。

计划中还存在「幽灵节点」：对应要求已经撤销，动作却仍留在待办列表。它们会消耗资源，甚至重新写回用户明确不要的内容。反过来，目标表里存在而计划没有入口的要求是「孤儿要求」。每次状态更新后扫描这两类不一致，比等到最终验收才发现漏项更便宜。 覆盖关系也为进度汇报提供了可靠语义。完成百分比不应按写了多少文字或执行了多少动作计算，而应说明多少要求已经有产物并通过验证，多少只有进行中的实现，多少尚未进入计划。这样用户提高标准时，系统会诚实地重新打开受影响项，而不会因为旧进度接近百分之百就把新要求当作附注。

### 6.4. 验收证据会随目标变化而失效

「已经检查过」只对某个文件版本、某套规则和某个环境成立。用户修改验收标准后，旧证据可能完全失效，也可能仍支持其中一部分结论。把验收结果保存成一个布尔值，会掩盖这种条件性。 一条证据至少应记录对象版本 $v_x$、检查器版本 $v_c$、目标版本 $v_G$、检查范围 $S$ 和结果 $y$：

$$
e=(v_x,v_c,v_G,S,y,t).
$$

提交前再次修改文件，依赖 $v_x$ 的字符与格式检查需要重跑；只改变另一篇文章，不会让本文件证据失效；检查器规则升级后，旧的「通过」不能自动代表满足新规则。证据的有效性由依赖匹配决定。 不同证据拥有不同单调性。证明「至少五份笔记」的计数，在只增加合格笔记时仍有效；证明「恰好五份」则会因新增文件失效。证明某文件没有 NUL，在文件未改动时可复用；证明全库没有 NUL，还依赖扫描集合没有扩大。系统若记录谓词形式，就能判断哪些更新保持结论，哪些必须重验。

人工审查也需要锚定版本。审稿人确认一段推导正确后，后续只改标题，推导审查可以保留；若公式或前提变化，则必须重新检查相关结论。内容审核无需因为任何字节变化都全量重做，但也不能依赖「这个文件以前看过」这种模糊记忆。段落哈希、依赖标签与差异范围可以缩小复核面。 最终完成判定是证据集合对当前要求的覆盖。每条要求要有仍然有效的证据，且高风险要求不能只由执行者自报支撑。若证据缺失，状态是「尚未证明」；若检查明确失败，状态是「未满足」。区分二者很重要：前者需要检查，后者需要修改。

### 6.5. 从轨迹评测走向可诊断的基准

演化意图基准若只报告最终成功率，很难指导系统改进。测试轨迹应按变化类型、作用域跨度、延迟长度、冲突强度、外部副作用和语言难度分层。一个模型可能擅长显式覆盖，却在省略恢复或跨任务回返时崩溃；总分会把这些差异平均掉。 样本切分还要防止模板泄漏。同一种骨架仅替换城市、文件名或菜品，训练与测试分开也可能测到模板记忆。更稳妥的切分按状态转移图、领域和表达族共同隔离：测试集包含训练时未见的事件组合，但每个基本语义仍可理解。这样才能观察模型是否学会更新规则。

评价可以分成四层。第一层检查消息到事件的解析，第二层检查事件到目标状态的折叠，第三层检查目标到计划的传播，第四层在真实 Harness 中检查动作与副作用。上层失败往往由下层造成，但也可能出现状态正确、规划遗漏，或计划正确、执行未取消的情况。分层记录让错误有归属。 长程长度本身不应成为唯一难度轴。把无关闲聊插入一千轮，只测试检索耐久；三轮对话也可能包含撤销、条件例外和权限变更。更合理的难度由有效状态转移数、依赖图宽度、未决分支数和需要回看的距离共同刻画。可定义一个诊断向量，而非把所有因素压成「上下文有多长」。

人工轨迹与合成轨迹各有用途。合成数据能精确控制单一变量并生成反事实对；真实对话提供省略、口癖、情绪和目标摇摆。评测集需要保留原始用户表达，同时由标注者给出结构化状态与可接受动作集合。只有一个参考答案会错误惩罚多种同样合理的确认或执行策略。 最终要测的是系统能否在变化中保持可恢复性：发现更新，修订正确范围，停止过期动作，保存仍有效成果，重新验证受影响结论，并让用户看见尚未解决的歧义。这条链上任何一环缺失，末轮文字再流畅，也只是在偶然命中当前请求。

### 6.6. 歧义不能只有「猜」和「停」两种处理

用户表达留下多个合理解释时, 立即提问并不总是最好. 问题可能不影响眼前工作, 频繁打断会把交互成本转嫁给用户; 直接选择一个解释, 又可能让大量工作建立在错误前提上. 系统需要根据分支影响决定何时继续、何时保留多条候选、何时必须确认.

设歧义产生候选目标 $G_1,\ldots,G_k$, 当前动作 $a$ 在各分支的效用为 $U(a,G_i)$. 若存在一组动作在所有候选下都安全且有正收益, 可以先执行它们. 例如输出顺序尚未确定时, 核对共同数据源和修复明确事实仍然有效. 这些动作构成候选目标可行域的交集:

$$
\mathcal A_{\mathrm{safe}}=\bigcap_{i=1}^{k}\mathcal A(G_i).
$$

交集为空或只剩无意义动作时，再请求澄清。这样既没有把沉默当授权，也不会因一个暂不相关的选择让整个任务停住。 有些动作在不同分支下都可用，但产物形态不同。此时可以先生成共享中间表示，例如收集论文证据、整理符号表和列出推导前提，等分支消解后再编排正文。共享工作量越大，延迟确认的价值越高；若下一步是删除、发布或覆盖外部状态，错误分支代价很大，应提前确认。

确认问题应指向导致计划分叉的最小字段。与其问「你具体想要什么」，不如说明「这里可能指当前章节，也可能指全库；两者会影响 6 个或 40 个文件，请确认范围」。问题携带候选解释和后果，用户才能快速裁决。已经从上下文排除的选项无需重新抛回去。 候选状态不能无限积累。每个候选要记录支持证据、反对证据、等待的消歧事件与失效条件。新消息到达后，删除不一致分支；多个分支收敛到相同字段值时合并。若分支数量随每次含糊表达指数增长，可只保留会改变近期动作或验收的差异，其余延迟解析。

评测确认策略时，要同时计算错误执行成本和打断成本。只看准确率会奖励逢问必停；只看完成速度会奖励冒险猜测。更合理的指标包含必要确认率、无效确认率、歧义期间安全进展量，以及确认后消除的状态熵。优秀系统能够继续所有对候选分支都成立的工作，并把真正决定后续路径的问题留给用户。

# Code as Agent Harness：代码作为 Agent 基础设施的三层综述

> **论文**：*Code as Agent Harness: Toward Executable, Verifiable, and Stateful Agent Systems*（arXiv:2605.18747，2026-05）
> **PDF**:[arXiv:2605.18747](https://arxiv.org/pdf/2605.18747)

## 代码作为 Harness 的三层结构

### 代码从输出变成操作基底

LLM 已强到能写竞赛级程序与仓库级补丁，但在 **agentic 系统**里，代码的角色正在变：它不只是**生成目标（target output）**， increasingly 充当**操作基底（operational substrate）**——承载推理、行动、环境建模与 execution-based verification。

作者用 **agent harness** 镜头统一这一趋势，提出 **code as agent harness**：以代码为中心构建可执行、可验证、有状态的 Agent 系统，并据此综述约 **197** 篇代表性工作。

### 接口、机制与扩展

#### Layer 1 — Harness Interface（接口层）

回答：代码如何把 Agent 接到三大基本功能？

| 接口 | 代码的角色 | 典型机制 |
|---|---|---|
| **Reasoning** | 思维链/程序即推理 | CoT-as-code、过程奖励、中间结果可检查 |
| **Acting** | 生成程序即策略 | Code-as-action、API 调用脚本、可复用 skill |
| **Environment Modeling** | 状态/动力学/反馈的形式化 | 模拟器、单元测试套件、GUI/OS 状态机 |

接口层的共同点是：把「模型想说的话」变成**可运行、可 diff、可回归**的对象，而不是纯自然语言承诺。

#### Layer 2 — Harness Mechanisms（机制层）

在 long-horizon 执行中，harness 需要 sustained 能力。综述归纳为：

- **Planning**：意图分解为结构化计划；「plan as program / contract」——计划本身可解析、可验证。
- **Memory**：跨轮状态保留、多 Agent 共享记忆、**context compaction & state offloading**（与 long-horizon 压缩论文线直接对话）。
- **Tool Use**：函数式工具、环境交互工具、**verification-driven** 工具（测试/ linter / sandbox 回传）、工作流编排工具。
- **Plan–Execute–Verify 控制环**：从「调试代码 bug」推广到 **harness-level control**——沙箱执行、权限化状态转移、确定性 sensor 验证。
- **Adaptive Harness Optimization**：深度 telemetry 作优化底稿；**Evolution Agent** 在治理约束下 mutate harness（prompt/tool/workflow），使系统自我改进但可审计。

机制层强调：可靠 long-horizon 不靠「更长 context」，而靠**显式状态 + 可重复验证闭环**。

#### Layer 3 — Scaling the Harness（扩展层）

从单 Agent 到协作生态：共享 **code artifacts**（repo、测试、trace、结构化中间件）成为多 Agent 的**公共工作区**。

- **角色分化**：manager / planner / coder / reviewer / tester
- **交互模式**：pair programming、repair、debate、red-teaming、adversarial
- **拓扑**：中心化编排 vs 分布式/流式协作（AutoGen、MetaGPT、Self-Collaboration 等）
- **状态收敛**：test-gated merge、consensus on correctness

代码在这里是**协调与验真的 lingua franca**——比自然语言更利于 diff、CI 与权限边界。

### 应用域与尚未解决的问题

横跨 coding assistant、GUI/OS automation、embodied agent、科学发现、个性化推荐、DevOps、企业工作流。

开放问题包括：超越终局任务成功的 harness 评测、不完整反馈下的 verification、**回归-free 的 harness 改进**、多 Agent 一致共享状态、安全关键动作的人类监督、多模态环境扩展。

## 三层结构如何约束执行

### 自然语言循环与可执行控制层

传统 Chat = 单会话文本状态机；**code harness** = 外部可观测状态（文件、测试、进程、repo）+ LLM 提议转移 + 确定性验证器裁决。综述实质是在说：**Agent 可靠性边界由 harness 工程决定，不由单次 sampling 决定**。

这与 LongHorizon-Harness（MEA 循环）、Polaris（deterministic crawl + LLM judgement 分流）等同属 2026 年长任务/agent 系统文献簇，但 **2605.18747** 更偏**概念收拢与家谱**，给出跨域 vocabulary。

### 三层之间的依赖关系

```text
Interface（代码接 reasoning/action/env）
    ↓ 需要
Mechanisms（plan/memory/tool/verify 维持长程）
    ↓ 扩展到
Scaling（repo 级共享工件 + 多角色编排）
```

三层结构也构成文献定位坐标：只做 tool call API 属于 interface 子集；没有 verify loop 则 mechanisms 不完整；多 Agent 无共享 test/state 则 scaling 层悬空。

### Harness 的工程约束

1. **Executable**：关键决策是否落到可运行 artifact？（脚本、测试、配置）
2. **Verifiable**：是否有 deterministic sensor 独立于 LLM 自评？（测试、类型检查、环境 diff）
3. **Stateful**：状态是否在 context 外显式持久？（DB、文件、task state store）
4. **Regression-safe**：harness 自我修改是否 gated？（telemetry + governed mutation）
5. **Multi-agent ready**：共享工件是否 versioned、可 review？

### 长任务系统中的落点

见微/OasisMind 的 Chat store 不变量、审批 scope、SessionStreamHub——本质是在 web product 里实现 mechanisms 层的 **plan–execute–verify + 推送式状态**；本综述提供的是跨论文的**命名与分层坐标系**，便于把 longhorizon、RSI、coding agent 文献挂到同一棵树上。

### Mechanisms 层的组成

综述在 mechanisms 层进一步细分出以下子题：

- **Memory**：单 Agent 工作记忆、多 Agent 共享记忆、**context compaction & state offloading**（与 CompactionRL、LongHorizon-Harness 等 2026 文献直接对话）。
- **Tool Use 四分**：function-oriented（API）、environment-interaction（shell/GUI）、verification-driven（测试/linter）、workflow-orchestration（DAG/CI）。
- **Plan–Execute–Verify**：planning as contract formation；sandboxed execution + permissioned state transition；verification through deterministic sensors。
- **Adaptive Harness Optimization**：deep telemetry → evolution agent → **governed mutation**（防 harness 自我修改引入 silent regression）。

### Scaling 层的协作拓扑

多 Agent 通过共享的 **repo / test suite / trace** 获得 ground truth，增加 chat 窗口本身不会形成协作。综述列举的 workflow topology 包括：中心化 coordinator、分布式 peer、streaming 协作；状态收敛机制包括 test-gated merge 与 consensus。MetaGPT、AutoGen、Self-Collaboration 等被归入「code 作共享 harness」案例——值得与 Polaris 六阶段流水线、Stanford CS329A Mod 4「可逆性」对照阅读。

**Code harness 必须能用 git diff、CI 结果和 property test 独立检验 Agent 的完成声明。** 综述把这一要求从 coding agent 推广到 GUI、OS、embodied 和 scientific 场景，强调 **harness 是可版本化的软件制品**，而非 prompt 里的软约束。自动修改 prompt 或 tool 若没有 golden trace 回归，就等于在未验证状态下改变生产配置。

## 代码怎样承载长任务状态

把代码当作 harness, 会把任务中的一部分隐含状态放进可以读取、执行和比较的对象. 单纯把自然语言计划改写成 Python 还不够. 对话里的「已经处理到第三批文件」很难独立验证; 一个带版本号的任务清单、一组文件哈希和一份测试报告则能由其他执行体重新读取. **代码让状态转移变得显式, schema、权限、验证和恢复机制共同决定可靠性.**

这里的「代码」至少包含三种载体. 第一种是程序文本, 它保存分支、循环、异常处理与工具调用顺序. 第二种是文件和数据库记录, 它们保存跨进程仍需存在的目标、任务进度、环境快照与验证结果. 第三种是运行时对象, 例如队列项、进程句柄、浏览器会话和事务上下文, 它们连接当前执行体与外部环境. 三者的生命周期不同: 程序文本可以版本化, 文件可以持久化, 运行时对象通常在进程退出后失效. Harness 如果只序列化最后一种对象的名称, 却没有重建方法, 重启后看到的只是一个无法继续使用的旧引用.

可以把第 $t$ 步的外置状态写成

$$
X_t=(G_t,Q_t,A_t,R_t,V_t),
$$

$G_t$ 是当前目标版本, $Q_t$ 是待办与依赖, $A_t$ 是已经执行的动作记录, $R_t$ 是外部资源及版本, $V_t$ 是验证结果. LLM 不直接把一句「完成」写入 $V_t$. 它只能提出动作, harness 执行动作并读取传感器结果, 验证器再决定某项状态能否从 `running` 转成 `verified`. 这就是综述所说的 executable、verifiable 和 stateful 在工程里的交点.

## 控制平面与数据平面

长任务系统可以分成两个互相配合的平面. **控制平面**保存目标、计划、权限、任务状态机、重试规则、checkpoint 指针和审计事件. 它回答「现在允许做什么、下一步由谁做、怎样判断完成」. **数据平面**承载真正被处理的对象, 例如仓库文件、网页内容、数据库行、模型权重、实验产物和工具返回. 它回答「动作实际作用于什么、产生了哪些变化」.

两者分开以后, 控制平面的一条 `task.completed=true` 不能覆盖数据平面的现实. 假设写文件的动作只成功了一半, 执行进程却在更新任务状态前崩溃. 恢复时不能仅看任务记录是 `running` 就重做, 也不能看到目标文件存在就宣布完成. Harness 需要读取文件哈希、临时文件、提交标记与对应验证结果, 再决定继续、补偿还是回滚.

控制平面也不能包含全部数据. 把大段工具输出、二进制产物和完整网页塞进任务状态, 会让每次调度都承担不必要的读写成本. 更合理的记录是资源定位符、版本、摘要和验证状态, 完整对象留在数据平面. 需要精确证据时再按定位符读取. 也就是说, 控制平面持有「怎样找到可信状态」, 不复制所有状态内容.

## 类型与 schema 是可执行约束

自然语言计划允许一句话同时表达目标、猜测和结果, 程序化状态则可以用 schema 把它们拆开. 一个最小任务对象可以写成:

```ts
type TaskState = {
  taskId: string;
  goalVersion: number;
  phase: "planned" | "running" | "verifying" | "verified" | "failed";
  inputs: Array<{ uri: string; version: string }>;
  actions: Array<{ id: string; tool: string; status: string }>;
  checks: Array<{ name: string; exitCode: number; artifactUri: string }>;
  checkpointId?: string;
};
```

这段类型做了几件具体的事. `goalVersion` 防止旧计划在目标改变后继续运行; `inputs.version` 让动作与输入版本绑定; `actions.id` 为副作用提供幂等标识; `checks` 保存验证器读到的结果, 而不是模型对结果的转述. `phase` 只能取有限状态, 因而可以定义合法转移. 例如 `running -> verified` 应被拒绝, 中间必须经过 `verifying`, 且 `checks` 中存在与当前产物版本对应的成功记录.

Schema 只会拒绝结构错误, 无法保证语义正确. 一个合法的 `artifactUri` 可能指向旧日志, `exitCode: 0` 也可能来自错误的测试范围. 因此字段需要交叉约束: 检查记录关联动作 ID、输入版本和产物哈希; 验证器确认它检查的是本轮结果; 状态转移函数一次性校验这些关系. 如果把校验散落在多个回调里, 任一调用路径漏掉检查, 同一个 schema 仍会保存错误状态.

## 工具副作用怎样进入状态机

工具调用可以分成只读、可重复写入和不可逆副作用. 读取文件或查询状态通常可以安全重试, 但结果可能随环境变化, 因而仍要记录读取时间和版本. 生成同一临时文件属于可重复写入, 前提是路径与内容由确定输入决定. 发送消息、创建远程资源或扣费调用则可能不可逆, 盲目重试会产生重复副作用.

幂等键把一次逻辑动作与多次网络尝试关联起来. 设动作标识为 $k$, harness 在调用前写入 `intent(k)`, 工具返回后写入 `effect(k, r)`. 进程若在两次写入之间退出, 恢复逻辑先查询外部系统是否已经存在对应 $k$ 的效果. 查到就补写结果, 查不到才重新执行. 工具不支持幂等键时, 可以使用业务唯一约束、预创建资源 ID 或执行后的查询来缩小不确定区间.

事务适合能够由同一存储系统原子提交的动作. 例如任务状态与本地数据库变更可以放在一个事务里, 要么一起成功, 要么一起撤销. 跨越文件系统、浏览器与远程 API 的工作流通常无法共享一个事务, 这时需要 **补偿动作**. 创建资源后的补偿可能是删除资源, 发布内容后的补偿可能只能追加撤回声明. 补偿并不保证恢复到完全相同的世界, 所以控制平面应记录它的实际结果, 不能用 `rolled_back=true` 掩盖仍然存在的外部影响.

**代码不是天然可靠的关键证据就在副作用边界.** 模型可以生成语法正确的重试循环, 却把不可逆动作执行三次; 也可以捕获异常后返回成功, 让控制平面错误进入完成态. Harness 必须在模型生成代码之外强制权限、幂等与状态转移, 不能把这些约束作为 prompt 里的建议.

## Checkpoint 保存哪些东西

Checkpoint 不是把进程内存完整复制一份. 它要保存能够重建执行的最小充分状态: 当前目标版本、已验证里程碑、未完成动作、外部资源版本、已发生副作用及其幂等键、下一步允许的状态转移. 对运行时对象, checkpoint 保存重建配方, 例如重新打开哪个文件、查询哪个远程任务、用哪个会话凭证恢复连接, 而不是保存已经失效的句柄值.

合适的 checkpoint 通常位于验证边界. 一个子任务完成且产物通过检查后, harness 固化 `X_t`; 下一阶段失败时, 可以回到这份已验证状态. 若在每条模型消息后保存, checkpoint 数量很多, 其中大部分并没有新的可信事实. 若只在任务结尾保存, 中途故障又会丢掉全部进展. 触发条件应对应真实状态变化, 例如目标版本更新、不可逆操作之前、阶段性验证通过或即将压缩上下文.

恢复时要重新读取数据平面. 文件可能被其他进程修改, 远程任务可能在 Agent 离线期间完成, 权限也可能过期. Harness 用 checkpoint 作为参照, 将当前环境与保存版本做 diff, 然后选择继续、重新规划或进入人工审批. 直接把旧运行时对象反序列化并继续调用, 只是把陈旧状态包装成了程序对象.

## 沙箱和权限边界

代码可执行意味着错误会产生真实影响. 沙箱负责限制执行体能够看见和修改的资源, 权限系统负责判断某个动作在当前目标和用户授权下是否允许. 两者不能互相替代. 容器隔离可以阻止脚本读取宿主机目录, 但无法判断 Agent 是否有权删除容器内的项目数据; 审批规则可以禁止删除, 却无法阻止恶意依赖利用系统漏洞逃逸.

权限应靠能力授予, 不靠工具名称猜测. 同一个 shell 工具既能只读列目录, 也能覆盖文件. Harness 可以为任务分配明确的工作目录、只读数据源、允许访问的网络域和资源配额, 高风险动作再要求更窄的临时能力. 模型生成的代码运行前先静态检查目标范围, 运行时由沙箱限制系统调用, 运行后再比较环境 diff. 任一层发现超出范围, 控制平面都不能把动作记为成功.

日志同样属于安全边界. 完整命令和返回内容便于审计, 也可能包含凭证与隐私数据. 状态层应保存脱敏后的摘要和受控证据指针, 原始日志按访问权限隔离. 多 Agent 共享 repo 或 trace 时, 共享范围必须跟随角色权限, 不能因为它们属于同一任务就默认全部可见.

## 一个小型执行例

设任务是「修改配置中的超时值, 运行检查, 通过后生成变更记录」. 控制平面创建目标版本 3, 输入文件版本为哈希 `h0`, 并生成动作 `a1=patch`, `a2=test`, `a3=report`, 依赖为 $a1\rightarrow a2\rightarrow a3$.

1. 执行 `a1` 前, harness 检查目标路径位于允许目录, 记录幂等键 `task-7/a1`, 并把旧文件保存到 checkpoint.
2. 沙箱内脚本读取 `h0`, 应用结构化 patch, 写入临时文件, 校验 schema 后原子替换, 得到新哈希 `h1`.
3. 控制平面不能因为脚本退出码为 0 就完成任务. 它把阶段转为 `verifying`, 执行 `a2`, 并把检查范围、退出码和 `h1` 写入 `checks`.
4. 如果检查失败, 文件恢复为 `h0`, 记录失败日志与补偿结果, 计划停在 `a1`. 如果检查通过, `a1` 与 `a2` 进入 `verified`, 然后 `a3` 只从验证记录生成变更说明.

假设进程在文件替换后、状态更新前退出. 新执行体读取 checkpoint, 发现磁盘哈希为 `h1`, 幂等键没有完成记录. 它不会再次应用 patch, 而是核对 `h1` 的 schema 并重新运行 `a2`. 这个例子只有三步, 已经同时用到版本、幂等、验证和恢复. 如果状态只存在对话里, 新执行体很难区分「准备修改」与「已经修改但尚未登记」.

## 怎样对照评测代码 Harness

比较代码 harness 与纯对话控制时, 应固定模型、任务、工具和最大调用预算, 只改变状态与控制机制. 任务集合要包含正常流程、工具超时、部分成功、进程中断、输入版本变化和不可逆副作用. 每种故障在预先指定的步骤注入, 避免某组碰到更简单的随机轨迹.

终态指标包括任务成功率、硬约束违反数和产物检查结果. 过程指标至少记录: 未验证结果被提升为完成态的次数; 重试造成的重复副作用; 从故障到可信 checkpoint 的恢复步数; 状态与实际环境不一致的持续时间; schema 或权限层拒绝非法转移的次数; 为持久状态、验证和恢复增加的 token、延迟与存储成本.

还要加入「代码自身出错」的对照. 人为让生成脚本引用错误字段、捕获异常后返回成功、读取旧版本输入或遗漏补偿动作, 观察 harness 的外层约束能否拒绝这些结果. 如果系统只在正常路径上表现更好, 故障路径仍然相信模型生成代码, 它只是把自然语言幻觉换成了可执行 bug.

结果按任务依赖深度与副作用等级分桶. 简单只读任务里, 代码 harness 的固定成本可能大于收益; 状态多、恢复频繁或含高风险写操作的任务, 显式控制与验证更重要. 这类评测不需要宣称代码一定优于对话. 它要回答更具体的问题: 哪类状态被外置以后可以恢复, 哪类错误被确定性检查拦住, 系统为此付出了多少工程和运行成本.

## 从自然语言到可执行计划

代码成为 harness，先要把含混目标编译成带类型的计划。自然语言目标 $T$ 经过解析后，可以得到动作图 $G=(V,E)$：每个节点 $v_i$ 记录输入、输出、前置条件、权限和验收器，每条边表示数据依赖或控制依赖。执行器只调度所有前置条件已经满足的节点，多写几段 Python 并不能替代这层约束。

一个节点可以写成如下结构：

```yaml
id: update-timeout
reads: [config/app.yaml@h0]
writes: [config/app.yaml]
requires: [workspace.write]
precondition: current_hash == h0
action: apply_patch
postcondition: schema_valid && timeout == 30
compensation: restore(config/app.yaml@h0)
```

YAML 中各字段共同形成可执行约束。`reads` 给出输入版本，`writes` 限制副作用范围，`precondition` 防止旧计划作用于新环境，`postcondition` 决定状态能否前进，`compensation` 则说明失败后是否可撤销。若这些信息仍藏在一段 prompt 里，模型每轮都要重新解释，解释结果还可能漂移。

计划图也给并行执行留下了明确边界。两个节点的写集合不相交、读写之间没有冲突，并且不存在依赖边时，才可以并行。用 $R_i,W_i$ 表示节点 $i$ 的读写集合，安全并行至少要求：

$$
W_i\cap W_j=\varnothing,\qquad W_i\cap R_j=\varnothing,\qquad W_j\cap R_i=\varnothing.
$$

这三个集合条件仍然不够处理外部系统。例如两个动作分别修改同一云账户下的配额与实例数，资源路径不同，却共享预算约束。此时还要给动作声明逻辑资源锁。代码 harness 的好处在于这些规则可以由调度器执行，而不是靠 Agent 在忙乱的上下文里记住一句「小心不要冲突」。

## 程序、解释器与环境各自保存什么

长任务经常把三种状态混在一起。**程序状态**是计划节点、变量和待执行分支；**解释器状态**是调用栈、异常、重试计数和已注册的补偿动作；**环境状态**则是真实文件、进程、数据库、网页与远端资源。只保存其中一层，都无法完整恢复。

若进程在 `write_file()` 返回后立刻崩溃，程序状态可能仍显示该节点处于 `running`，环境里的文件却已经改变。恢复时不能盲目重放。Harness 先读取环境，比较输入与输出版本，再决定把节点推进到 `verifying`、重新执行，还是标成冲突。这个过程相当于数据库里的 write-ahead record，只是动作对象不一定支持事务。

可逆动作与不可逆动作要分开。覆盖本地文件通常能靠快照恢复；创建云资源可通过删除进行补偿，但补偿本身也可能失败；发送消息或提交付款几乎无法撤销。动作类型可以标成 `reversible`、`compensatable`、`irreversible`。不可逆动作进入队列前需要更强的前置验证和授权门，而且幂等键必须由外部系统认可，单靠本地日志阻止不了重复发送。

一次恢复的判断可以写成状态表：

| 计划记录 | 环境观察 | 恢复动作 |
|---|---|---|
| pending | 输入版本仍为旧值 | 正常执行 |
| running | 输出版本已出现 | 跳过写入，转入验证 |
| running | 环境处于部分状态 | 执行补偿或生成修复节点 |
| verified | 环境版本已漂移 | 撤销完成标记，重新规划 |
| failed | 外部幂等键显示成功 | 核对结果，修正本地状态 |

最后一行很容易被忽略。本地超时只说明没有收到响应，不能证明远端动作失败。可靠 harness 会把「未知」保留成独立状态，随后用资源 ID 或幂等键查询；直接重试可能制造两个真实副作用。

## 代码执行为什么便于验证

自然语言结论很难做等价判断。两段描述用词不同，可能表达同一状态；同一句「已完成」也可能对应完全不同的产物。代码把一部分语义压进类型、测试和断言，使验证从语言相似度转向环境事实。例如要求输出 JSON 时，schema 可以先验证字段、类型和范围，业务检查再验证字段之间的关系：

$$
\operatorname{Valid}(x)=\operatorname{Schema}(x)\land\operatorname{Invariant}(x)\land\operatorname{ExternalCheck}(x).
$$

三项分别对应结构正确、内部约束成立和外部效果出现。结构正确只说明文件能解析；内部约束可以检查总额、引用与版本关系；外部检查才确认服务确实加载了这份配置。很多 Agent 系统只做第一项，随后把「JSON 合法」写成「任务成功」，中间差了整整两层。

测试也有证据强弱。单元测试验证局部函数，集成测试覆盖组件协作，端到端测试靠近用户结果。Harness 应按动作风险选择证据，不必所有节点都跑最昂贵的端到端检查，也不能让高风险写操作只配一个语法检查。可以给条件赋权 $w_j$，把已通过权重记为：

$$
P=\frac{\sum_j w_j\mathbb{1}[g_j=\text{pass}]}{\sum_j w_j}.
$$

$P$ 适合显示进度，不适合作为自动完成阈值。只要有一个硬条件失败，哪怕 $P=0.99$，任务仍未完成。进度分数帮助排序，硬谓词决定提交，这个区分能防止漂亮的百分比遮住致命缺口。

## Harness 本身也是待测程序

一旦代码负责规划、权限和恢复，Harness 的 bug 会跨任务复用，影响面甚至大于单次模型幻觉。类型系统只能阻止它能表达的错误，错误 schema 会稳定地验证错误对象；测试程序也可能因为缓存、路径和环境变量读到错误结果。因此，Harness 需要自己的回归集。

一组最低限度的故障注入应覆盖：动作执行前中断、动作成功后回执丢失、验证期间环境漂移、补偿动作失败、日志写入失败、同一幂等键并发到达、旧 checkpoint 在新版本程序中恢复。每种故障都要检查两个问题：环境有没有产生重复副作用，控制平面有没有把未知结果提升成完成。

还要做**模型无关测试**。把模型替换成固定脚本，让它依次返回合法动作、越权动作、错误字段和自相矛盾的完成声明，观察 harness 是否按规则处理。若系统必须依靠一个聪明模型才不越权，约束其实没有进入基础设施。反过来，确定性层也不该擅自决定开放语义问题，例如替用户判断设计稿是否好看；它只负责把这类条件路由到合适的人工或模型评审。

## 三层框架怎样落到一条运行时间线

综述所说的 interface、mechanisms 与 scaling 并非三组互不相关的技术。一次运行从接口层接收目标、工具 schema 和环境观察；机制层把它们变成计划、代码、验证与恢复；扩展层再决定并发多少执行体、怎样共享状态、如何控制成本。时间线大致如下：

```text
目标与权限
   ↓  interface: 统一消息、工具与环境表示
计划图生成
   ↓  mechanisms: 类型检查、沙箱执行、验证、checkpoint
单任务可信轨迹
   ↓  scaling: 并行调度、共享缓存、跨 Agent 协作、预算控制
审计过的最终状态
```

扩展不能早于单任务语义稳定。一个会重复副作用的执行循环扩到一千个 sandbox，只会更快地产生一千份错误。反过来，所有动作完全串行虽然容易推理，却会让长任务慢得无法使用。比较合理的顺序是先定义动作与提交语义，再按读写集合和资源锁开放并行，最后用队列、配额与优先级控制系统规模。

代码作为 harness 的真正吸引力也在这里：它把一些原本靠模型临场发挥的约束变成可运行、可测试、可版本化的对象。但代码没有消灭不确定性。开放世界里的目标解释、视觉判断、外部服务漂移仍然存在，生成的程序本身也会出错。它提供的是更坚实的承载层，让错误有位置可查、状态有版本可读、恢复有规则可循。

## 观察与环境状态

Agent 每一步只能拿到局部 observation。终端输出可能被截断，网页可访问性树可能缺失画布内容，API 返回也可能来自缓存。Harness 若把局部观察直接当成完整状态，代码再精确也会在错误输入上稳定运行。

设真实状态为 $s_t$，工具返回观察 $o_t\sim O(\cdot\mid s_t)$。动作 $a_t$ 改变环境后，Harness 实际维护的是对状态的估计 $\hat s_t$。当观察不完整时，计划节点应记录证据来源与置信边界，而非伪装成精确值。例如命令只打印最后 100 行日志，就不能据此断言此前没有错误；网页截图没出现按钮，也可能只是按钮在折叠区域。

组合读取多种观察能减少这类偏差。文件写入后同时检查内容哈希和解析结果，服务部署后同时查询健康端点与版本端点，GUI 操作后同时读取截图、URL 和可访问性树。不同观察若冲突，状态进入 `ambiguous`，由下一步主动消歧。让模型挑一个顺眼的结果继续，往往会把观测缺口变成后续事实。

缓存还会制造时序错误。测试进程读取旧构建产物，健康检查命中旧实例，Agent 看到的是合法但过期的结果。验证记录要包含输入版本与观测时间；能使用强一致读取时使用强一致读取，不能时则等待明确的收敛条件，而非固定睡几秒后祈祷。固定延迟既浪费快路径，也无法覆盖慢路径。

## 多 Agent 共享代码时的冲突

Scaling 层常把任务拆给多个 Agent，但共享仓库不是共享一张便签纸。两个执行体改动同一个模块，即使 Git 能合并文本，语义也可能冲突。调度器要维护每个子任务的读写集合、基线版本与验收条件，并在合并后重新验证组合结果。

最简单的策略是悲观锁：同一写集合一次只允许一个 Agent。它容易理解，却会压低并发。乐观策略允许各自在隔离工作区修改，提交时比较基线哈希；没有冲突则合并，有冲突则生成新的协调任务。无论哪种策略，都不能把 `git merge` 成功视为功能正确，组合回归测试才是提交门。

共享知识也要版本化。Agent A 根据接口 v1 写调用方，Agent B 同时把接口升级到 v2；两边各自测试都通过，合并后调用方已经过期。计划图里的数据依赖应引用具体 schema 版本，接口变更会使依赖它的未完成节点失效。调度器随后重算这些节点，而非让旧任务继续消耗预算。

消息通信不适合承载全部状态。自然语言适合解释意图和异常，资源版本、动作结果、锁与依赖应进入结构化存储。否则多个 Agent 会形成几份彼此接近却不完全一致的项目故事，最后再由一个协调模型猜哪份可信。这正是 code as harness 希望消除的情况。

## 版本升级与状态迁移

长任务可能运行数小时甚至数天，期间 Harness 代码、工具 schema 或模型端点会升级。旧 checkpoint 能否在新版本恢复，需要显式兼容规则。状态文件至少带 `schema_version`、Harness commit 和工具版本；加载时先迁移结构，再恢复执行。

迁移函数应满足幂等性。状态从 v1 升到 v2 后再次运行迁移，结果不能继续变化；迁移失败时保留旧快照，不能写出半份新状态。若新版本改变动作语义，例如 `delete` 增加回收站参数，旧计划节点不应静默套用默认值，而应失效并重新规划。

模型升级也可能改变输出格式和工具选择。Harness 的解析器要用契约测试覆盖支持的模型端点，把未知字段、缺失字段和多个并发 tool call 都作为输入。版本升级先在保存的离线 trace 上重放，再进入真实任务。这样能够分辨解析层回归与模型能力变化，避免把基础设施 bug 算到新模型头上。

## 最小可观测面

一条长任务失败时，工程人员至少要能回答：哪个计划节点在何时由哪个执行体运行；它读取了哪个版本；产生了哪些副作用；验证器看到了什么；状态为什么前进或停下。对应日志可分成事件流、状态快照和证据对象三层。

事件流只追加，记录计划、调度、工具调用、验证与提交；状态快照便于快速恢复；大体积日志、截图和测试报告作为证据对象单独保存，以哈希关联。三层都带 task、node、attempt 与 trace 标识，就能从最终状态反查到原始证据，也能从一次异常定位受影响的状态转移。

指标应服务于故障定位。总 token 和成功率之外，还应监控每类状态停留时间、重试原因、幂等冲突、权限拒绝、验证器不确定率、补偿成功率和 checkpoint 恢复耗时。若失败率上涨，可以先判断是模型动作变差、环境故障变多，还是验证规则变严。没有这些分解，总成功率只会告诉人系统坏了，却不告诉人坏在哪里。

日志必须脱敏。命令参数、工具响应和环境变量可能含密钥；完整 trace 也可能包含用户数据。采集层在写盘前按 schema 标记敏感字段，原始证据进入权限更窄的存储，普通调试页面只展示脱敏摘要。可观测性不能以复制所有秘密为代价。

证据对象还应设置保留周期。最终状态和关键验证可以长期保存，原始屏幕录制、完整 shell 输出与模型上下文则按风险缩短周期；删除时保留哈希和删除记录，使审计链知道证据曾经存在，却不继续暴露其内容。

## 代码作为策略的形式语义

自然语言计划通常只描述意图，代码会把控制流、数据依赖和异常路径固定下来。设环境状态为 $s_t$，生成程序为 $p$，解释器语义为 $\llbracket p\rrbracket$，一次执行可以写成

$$
(s_{t+1},o_t,e_t)=\llbracket p\rrbracket(s_t),
\tag{1}
$$

$o_t$ 是可观察输出，$e_t$ 是副作用记录。Harness 不只要判断程序能否运行，还要核对它是否在授权状态上实现目标、产生了哪些外部变化。

代码把部分推理从模型 token 转成解释器步骤。循环、条件和数据变换无需模型逐项生成，执行结果也能被测试。若要处理一万个文件，模型写一个遍历程序比发出一万次工具调用更紧凑；错误程序也会把同一错误复制一万次，因此静态约束和小样本试运行非常重要。

程序的语义不等于源代码文本。相同逻辑可有多种写法，文本相似度无法判断行为一致；一行命令也可能隐藏网络、文件和进程副作用。验证应落到输入输出、资源访问与环境差异，而非只让模型阅读代码后评价。

部分函数适合纯语义：相同输入得到相同输出，不读写外部环境。纯函数容易缓存、重放和单元测试。工具动作属于效果语义，需要记录文件、网络、时间、随机性和权限。Harness 若把两类混在一个无类型字符串中，就无法安全重试。

可将动作返回值写成带效果集合的类型

$$
p:X\rightarrow Y\;!\;\mathcal E,
\tag{2}
$$

$\mathcal E$ 声明可能的读写、网络和外部事务。调度器据此安排沙箱和并发，Auditor 对实际效果与声明效果做差异检查。未声明副作用应视为合约违例。

## 从自然语言规格到程序的两次编译

Agent 先把用户目标编译成可执行规格，再把规格编译成代码。第一步决定「什么算正确」，第二步决定「怎样实现」。把两步直接合成一次生成，代码可能运行成功，却解决了错误问题。

规格至少包含前置条件 $P$、后置条件 $Q$ 和允许副作用集合 $E$。Hoare 三元组写成

$$
\{P\}\ p\ \{Q\}_{E}.
\tag{3}
$$

执行前验证 $P$，沙箱限制效果不超出 $E$，执行后验证 $Q$。若前置条件不成立，程序没有义务产生正确结果；若后置条件不可观察，Harness 也无法证明完成。

例如「修复所有损坏图片」需要先定义损坏判据、扫描范围、允许重画或删除引用的条件和最终审计。直接写修复脚本会把模糊判断藏进代码。规格明确后，检测器、修复器和最终扫描可以分别测试。

规格本身也可能错。可以生成反例：构造文件头全零但尺寸正常、扩展名与 magic 不一致、Markdown 引用不存在等边界，检查 $Q$ 是否拒绝它们。若测试只覆盖正常图片，程序和验证器可能共享盲点。

第二次编译要保持规格追踪。代码模块、测试和日志引用对应 requirement ID；规格变化时定位受影响模块，而非全量重写。最终报告也能从 requirement 到测试证据反查。

## 程序搜索与执行反馈

代码型 Harness 常形成「生成—运行—观察—修复」循环。模型提出程序 $p_k$，环境返回测试和错误 $f_k$，下一轮生成 $p_{k+1}$. 这是一种带执行反馈的搜索，不应把每轮修改都当独立答案。

状态可表示为

$$
z_k=(p_k,T_k,F_k,D_k),
\tag{4}
$$

$T_k$ 是已通过测试，$F_k$ 是失败证据，$D_k$ 是环境 diff。下一轮应保持 $T_k$ 对应的不变量，同时修复 $F_k$。只把最后一条报错塞回 prompt，容易修一个测试又破坏旧测试。

测试反馈的信息量不相同。编译错误定位语法，单元测试定位局部行为，端到端失败可能来自多模块。Manager 可以选择最能缩小候选空间的下一项检查，而非每次运行最昂贵全套测试。

设候选程序集合为 $\mathcal P_k$，测试 $t$ 将其划分为通过与失败两部分。理想测试最大化预期信息增益

$$
IG(t)=H(\mathcal P_k)-
\mathbb E_{y_t}[H(\mathcal P_k\mid y_t)].
\tag{5}
$$

真实系统不会枚举程序集合，但这个视角解释了为什么最小复现和针对性测试比反复跑大集更利于定位。

执行反馈还可能误导。flaky 测试、缓存产物和环境漂移会让同一程序得到不同结果。Harness 应保存输入版本和随机种子，对不稳定失败重复验证，再决定修改代码。否则模型会为环境噪声制造无关补丁。

## 验证器也必须在信任边界之外

Agent 若能读取并修改评分脚本，最容易的「修复」可能是让测试永远返回成功。验证器、隐藏测试和安全策略需要位于被测程序权限之外。代码作为 Harness 的可验证性依赖这个隔离。

可信计算基包括解释器、沙箱、权限检查、状态存储和最终验证器。它们越复杂，出现漏洞的机会越大；生成代码本身不应获得修改这些组件的权限。Harness 自我升级要走独立审查与版本发布，而非任务中的 Executor 随手改动。

验证器输出要绑定被测产物哈希。测试结束后代码若继续变化，旧 pass 失效。并行任务合并后，即使各分支单独通过，也要对组合版本重跑相关测试。

隐藏测试能防止直接迎合样例，却可能造成不可诊断失败。可以向 Agent 暴露失败类别或最小反例，同时保护完整答案。信息释放需要平衡搜索效率与防作弊。

机器验证也有覆盖边界。类型检查证明类型性质，单元测试证明样例，形式验证证明给定规格；规格与真实目标不一致时仍会通过。最终可信度来自多层证据，而非某个工具名字。

## 沙箱并不只有「开」和「关」

沙箱由文件系统、网络、进程、系统调用、资源和凭证多条能力组成。一个程序可以只读仓库、写临时目录、禁止网络；也可以访问指定域名但不能读取用户目录。细粒度能力比全权限或全禁用更适合真实 Agent。

资源限制也是语义边界。无限循环、fork bomb、巨量磁盘写入和 GPU 占满都可能在逻辑正确前拖垮环境。CPU 时间、内存、进程数、输出大小和墙钟超时需要由外层强制。

网络访问会破坏可复现性。依赖下载内容随时间变化，API 返回受账户和速率限制影响。能预取并固定的资源应进入环境镜像；必须在线调用的动作记录请求版本和响应哈希，并避免把秘密写进生成代码。

沙箱逃逸测试不能只看正常任务。用专门探针尝试路径穿越、符号链接、子进程继承、环境变量泄漏和 localhost 服务访问，确认限制真实生效。配置声称隔离不等于隔离已经被观察。

Windows、Linux 与 macOS 的路径、权限和进程模型不同，同一策略不能机械复用。跨平台 Harness 应让能力抽象保持一致，再为每个平台验证实现。论文或仓库只在某一平台测试时，结论要限定。

## 生成代码的生命周期

临时代码、任务脚本和长期 Harness 组件需要不同治理。一次性数据转换可以随任务归档；反复使用的工具应进入版本库、测试和依赖管理；改变控制逻辑的 Harness 代码属于基础设施，升级风险最高。

从临时脚本晋升为共享工具前，至少检查输入 schema、错误处理、幂等性、权限和测试。一个在当前目录偶然成功的脚本，不应直接成为所有 Agent 的默认能力。复用会放大收益，也会放大隐藏假设。

工具退役同样重要。环境 schema 已变化，旧工具仍被模型从文档中调用，会产生难以理解的失败。工具注册表保存版本、兼容范围和废弃状态；计划生成只暴露当前有效接口。

Harness 自我修改要形成受治理的变更：提出补丁，在隔离任务集回归，比较安全与效用，人工或独立策略批准，然后发布新版本。当前任务不能因为某次失败就直接改变全局安全规则。

回滚要求保存旧二进制、schema 迁移和状态兼容性。新版本生成的 checkpoint 可能无法由旧版本读取，因此发布前测试向前/向后迁移，或明确禁止回滚并提供导出路径。

## 代码怎样变成可执行记忆

长程 Agent 的记忆不一定是一段摘要。已经验证的解析器、查询脚本、数据转换和测试本身就是可复用记忆：它们把过去解决问题的方法固化成可执行对象。下次遇到同类输入，系统运行程序即可，不必重新用自然语言推导。

可执行记忆至少包含代码 $p$、适用前提 $P$、版本 $v$、测试集合 $T$ 和来源证据 $E$：

$$
m=(p,P,v,T,E).
\tag{6}
$$

缺少前提，工具容易在错误环境复用；缺少测试，无法判断升级后是否仍有效；缺少来源，使用者不知道结论为何可信。只把代码文件放进工具目录，不能算完整记忆。

程序记忆与事实记忆承担不同职责。「接口 v2 的字段名是 user_id」属于事实，可以结构化保存；「怎样把 v1 数据迁移到 v2」适合程序。事实变化会使程序前提失效，Harness 沿依赖关系触发重验或重新生成。

代码还能保存过程性知识。一个复杂网页操作被录成脚本后，步骤顺序、等待条件和错误分支都比文字描述精确。但 GUI DOM、坐标和权限随版本变化，程序记忆具有环境依赖。成功运行次数不能消除未来漂移，需要在每次使用前检查关键前提。

可执行记忆有组合优势。多个小工具可以由新程序调用，形成更高层能力；也有组合风险，两个工具分别安全，串联后可能扩大副作用。例如导出数据与发送邮件单独合法，组合就可能泄露信息。组合程序仍需整体权限审计。

工具使用反馈可以更新记忆，但不能让一次任务自动覆盖全局版本。候选修复先在当前任务分支验证，累积多次证据后再晋升共享工具。这样把在线适应和基础设施发布分开，避免偶然输入驱动全局自修改。

## 程序化计划与计划图

自然语言计划通常是有序列表，代码计划可以显式表示条件、循环、并行和依赖。把任务编译成有向图 $G=(V,E)$，节点是有界动作或验证器，边表示数据与控制依赖。调度器只运行前置条件满足的节点。

节点 $v_i$ 可定义为

$$
v_i=(f_i,I_i,O_i,R_i,W_i,C_i),
\tag{7}
$$

$f_i$ 是可执行函数，$I_i/O_i$ 是输入输出 schema，$R_i/W_i$ 是环境读写集合，$C_i$ 是提交条件。结构化节点让并发、安全和恢复都能落到同一对象。

循环需要终止变量。Agent 说「不断修改直到测试通过」可能无限运行；程序计划应设置最大尝试、预算和单调进展指标。若失败集合在若干轮内不缩小，循环退出并请求重规划，而非换措辞继续。

条件分支也要由可观察谓词驱动。`if deployment succeeded` 太模糊，应写成健康端点、版本号和时间窗口的组合。谓词返回 unknown 时不能默认进入成功分支。三值逻辑比强行布尔化更适合外部环境。

计划图允许局部重算。接口节点输出 schema 变化，只使后继闭包失效；无关文档节点保持 verified。线性聊天没有显式依赖，常把变化之后的所有工作一起丢弃或全部保留。

动态计划会在执行中增删节点。变更本身形成版本化 patch，检查新节点是否覆盖原目标、是否引入循环依赖、是否扩大权限。模型可以提出图变更，调度器负责验证后应用。

## 多 Agent 共享程序工件

Scaling 层以带版本的代码、规格、测试和证据作为关键共享对象。Agent A 生成接口，Agent B 写实现，Agent C 做审查，每个角色通过工件 schema 协作。共享自然语言仍用于解释异常，不承担权威状态。

工件状态可分为 draft、tested、approved、released 和 deprecated。生成代码只进入 draft；测试通过进入 tested；安全或人工审查后 approved；被其他任务依赖前才 released。状态跳转带证据，不能由作者自己宣布。

多 Agent 审查并不自动独立。若审查者看到作者的长篇理由，可能被锚定；若共享相同测试，可能共同漏掉规格错误。审查输入应优先包含原始规格、diff 和环境证据，再把作者解释作为补充。

合并冲突有文本、语义和目标三层。文本冲突可由版本控制发现；没有文本冲突的接口变更仍可能造成语义冲突；两个分支分别满足局部目标，组合后也可能违反全局预算或安全条件。合并门必须运行组合验证。

代码所有权影响调度。某 Agent 对模块有局部上下文和历史经验，继续分配可能更高效；长期绑定又会形成单点和盲区。Harness 可以把所有权当软偏好，高风险审查仍交给独立角色。

共享缓存也需来源。编译产物、测试结果和分析索引绑定代码哈希、依赖版本与平台。缓存命中只省计算，不能跨版本证明正确。错误缓存若被多 Agent 复用，会比单体错误传播更快。

## 不完整反馈下的验证

现实工具经常只返回部分信息。编译通过不代表运行正确，API 200 不代表业务成功，GUI 点击没有报错也不代表对象改变。代码 Harness 的确定性只能作用于已观察输入，无法自动补齐缺失反馈。

可以把验证结果表示为 $\{pass,fail,unknown\}$。对要求 $r_i$，多个观察 $o_1,ldots,o_k$ 通过证据规则合成：任何可靠反例产生 fail；充分证据集合产生 pass；其余保持 unknown。unknown 不触发提交。

验证器覆盖率为

$$
\operatorname{Cov}(V,R)=
\frac{|\{r_i:\exists v_j,\ v_j\text{ 可判定 }r_i\}|}{|R|}.
\tag{8}
$$

覆盖率低时增加执行轮次没有用，应先改善可观察性。很多 Agent 失败表面像规划问题，实际是系统不知道动作是否生效。

反馈可能延迟。提交异步作业后，立即读取状态得到 pending；固定 sleep 会在快任务浪费，在慢任务误判。验证器应轮询有界条件、监听事件或查询作业 ID，并在超时后返回 unknown。

反馈也可能互相矛盾。健康端点显示新版本，页面仍是旧缓存；测试报告通过，日志包含异常。Harness 保存各观察的时间和来源，按一致性模型判断，而非让 LLM 选择更乐观的一项。

主动验证可以选择下一项观察，使不确定性下降最大。若文件哈希已证明写入，没必要重复读文件；若部署版本未知，查询版本端点比重跑本地测试更有价值。观察调度本身属于计划。

## 执行错误与规格错误要分开

测试失败可能因为程序没有实现规格，也可能因为规格本身错误或测试误解了目标。若 Harness 一律修代码，模型会不断迎合错误测试，最终得到稳定但无用的系统。

诊断可分三条假设：$H_p$ 表示程序错，$H_s$ 表示规格错，$H_t$ 表示测试错。新证据应帮助区分三者。手算样例和外部规范更适合检查规格，独立实现和属性测试更适合检查程序，测试变异与覆盖分析更适合检查验证器。

例如实现排序函数，测试期望去重。程序保留重复项而失败，可能是实现不符测试，也可能用户只要求排序。回到原始目标能发现测试偷偷加入了去重语义。代码和测试共享同一生成上下文时，这类共同偏差尤其常见。

规格变更应产生新版本，旧测试按依赖关系失效；程序 bug 修复保持规格不变，只更新实现和对应证据。把两者都当普通 patch，会让审计历史难以解释。

模型提出修改测试时，权限应高于修改实现。至少要求说明原测试与原始要求的矛盾，并由独立角色审查。否则最短修复路径总可能是删掉失败断言。

## 代码 Harness 的成本模型

把推理写成代码会减少重复模型调用，却增加生成、执行、验证和维护成本。总成本可以分解为

$$
C=C_{gen}+C_{exec}+C_{verify}+C_{repair}
+C_{maint}+C_{coord}.
\tag{9}
$$

一次性小任务中，$C_{gen}$ 和沙箱启动可能高于直接工具调用；大规模重复任务中，程序复用会摊薄生成成本。多 Agent 扩展主要增加协调与组合验证。

程序执行成本也不等于模型 token。CPU/GPU 时间、网络、存储和外部 API 都应计入。一个只用少量 token 生成的暴力搜索可能消耗巨大计算；评测若只报告 token 会误判效率。

验证成本随风险变化。静态检查便宜，端到端环境昂贵，人工审批最慢。分层验证先运行便宜高召回检查，再对候选调用昂贵验证，可以降低平均成本，但最终高风险条件不能省略。

维护成本常被论文单次实验忽略。工具 schema 更新、依赖漏洞、平台迁移和测试失效都会消耗长期资源。代码成为 Harness 基础设施后，它进入软件生命周期，而非生成完就结束。

扩展收益应画吞吐—成功率—成本三维曲线。增加 Agent 数可能先提高并行度，随后因冲突、审查和环境瓶颈饱和。只展示最大并发点，无法找到实际经济区间。

## 扩展层的队列与背压

多 Agent 系统里，生成任务的速度可能超过验证和合并速度。若没有背压，大量 draft 堆积，占用工作区和上下文，且都基于逐渐过期的状态。Scaling 不只是增加 worker，还要平衡各阶段服务率。

把规划、执行、验证、合并视为串联系统，阶段 $i$ 到达率为 $\lambda_i$，服务率为 $\mu_i$。稳定运行至少要求长期 $\lambda_i<\mu_i$。Auditor 成为瓶颈时，继续增加 Executor 只会拉长队列。

优先级应考虑依赖关键路径、过期风险和资源。阻塞多个后继的接口审查优先于孤立低价值任务；即将因环境变化过期的结果优先验证；不可逆动作不因队列压力降低审计等级。

背压可以暂停新计划、缩小并发或合并相似验证。不能通过自动接受未审结果缓解队列，那会改变可信状态语义。低风险任务可使用便宜验证器，高风险任务保留强审计。

任务取消后，队列中的旧节点要撤销，运行中的 worker 收到版本更新，迟到结果在提交门被拒绝。只从前端隐藏任务不会停止后台副作用。

## 一套可证伪的评测协议

评测应同时改变任务长度、程序复用度、反馈完整性、副作用风险和并发度。若只选适合脚本化的批处理任务，代码 Harness 天然占优；若只选一次性主观任务，又看不出可执行工件价值。

基线包括直接自然语言工具循环、带结构化计划但不生成程序、生成程序无持久化、完整 code harness，以及人工编写脚本上界。固定模型、工具权限和总预算，分别观察代码表示与 Harness 机制的贡献。

机制消融逐项关闭类型检查、沙箱、checkpoint、外部验证、版本门和共享工件。每项应有对应压力任务：错误 schema、越权程序、进程崩溃、虚假自报、环境漂移和多 Agent 接口冲突。若关闭机制不改变目标故障，设计解释需要重审。

指标包括终局成功、首次正确时间、重复动作、未声明副作用、错误提交、恢复成本、组合回归、峰值资源与人工介入。对程序复用任务还要记录第二次及后续任务的边际成本。

评测 Harness 自身时，验证器不能由被测 Agent 修改，环境镜像和隐藏测试要冻结。否则系统可能优化评分基础设施而非任务。预算耗尽记为停止，不应与明确错误混成同一失败原因。

任务级结果需要公开或保留完整 trace，才能判断提升来自哪些任务。少量端点平均分无法证明代码机制普遍有效，也无法发现某一安全边界被牺牲换取成功。

## 接口层的类型契约

Harness interface 把模型输出接到工具和环境。若接口只有函数名和一段自然语言描述，参数缺失、单位混淆、枚举越界和对象错配都会在运行时才暴露。类型 schema 将一部分错误提前到调用前。

工具 $f$ 的契约可写成

$$
f:X\times C\rightarrow Y\cup E,
\tag{10}
$$

$X$ 是参数类型，$C$ 是调用上下文与权限，$Y$ 是成功结果，$E$ 是结构化错误。模型生成调用后先验证 $X$ 与 $C$，只有通过才进入执行器；返回结果按 $Y/E$ 解析，不能用一段字符串同时表示成功和报错。

类型正确仍可能语义错误。路径字段是字符串，但 `D:\data` 与工作区内相对路径具有不同权限；数字参数类型为整数，单位可能是秒或毫秒。精化类型可以加入范围、单位、路径根和资源所有权。

$$
\texttt{TimeoutMs}=\{n\in\mathbb N:100\le n\le600000\}.
\tag{11}
$$

这类约束由确定性验证器检查，模型无需每次重新理解。

输出 schema 要支持部分成功。批量处理十个对象，八个成功、两个失败，不应只返回一个 `success=true`。逐项结果、重试安全性和副作用 ID 使计划器只修复失败部分。

schema 演化需要兼容策略。增加可选字段通常向后兼容，改变默认值或枚举语义可能破坏旧计划。每次工具调用记录 schema 版本，checkpoint 恢复时若版本不匹配，节点进入待迁移或重新规划。

接口文档和实现必须同源。根据 schema 自动生成模型可见说明、参数校验和测试样例，能减少三份定义漂移。自然语言补充用途与风险，机器字段负责硬边界。

## 动作的事务语义

代码可能执行一串副作用。中途失败时，环境处于部分完成状态，简单重跑会重复前半段。Harness 需要为动作定义原子性、幂等性和补偿。

对动作序列 $a_1,ldots,a_n$，理想原子事务只暴露初始状态 $s_0$ 或最终状态 $s_n$。文件系统可以先写临时文件、验证后原子替换；数据库使用事务；跨外部服务往往无法原子提交，只能采用 saga。

幂等键 $k$ 使重复请求返回同一结果：

$$
\operatorname{apply}(a,k,\operatorname{apply}(a,k,s))
=\operatorname{apply}(a,k,s).
\tag{12}
$$

这条等式描述可观察效果，不要求内部完全不执行。发送消息、创建订单等动作若服务支持幂等键，超时重试更安全；不支持时先查询外部状态。

补偿函数 $c_i$ 试图逆转 $a_i$，但通常只能达到业务等价，而非抹去历史。删除已发布页面可以停止未来访问，不能保证所有缓存消失；恢复文件可以还原内容，无法收回已读取的数据。状态应保留事故和补偿证据。

事务边界应与验收边界一致。一个节点修改代码、运行测试并提交版本，可以在提交前回滚工作区；把发布也塞进同一节点，就跨越不可逆边界。拆成「准备」「验证」「发布」三阶段更容易控制。

故障注入要覆盖每个副作用之后崩溃。若只在动作开始前或全部完成后测试，无法发现中间状态。恢复程序读取动作日志和环境事实，判断继续、补偿还是人工处理。

## 程序化记忆何时失效

代码能把经验固化，却会把旧假设一起固化。判断记忆能否复用，需要检查输入分布、依赖版本、权限和目标语义。文件仍能运行，只说明语法兼容，不说明行为仍正确。

记忆条目 $m$ 的有效性可表示为

$$
\operatorname{valid}(m,t)=
P_m(s_t)\land V_m=V_t\land A_m\subseteq A_t,
\tag{13}
$$

$P_m$ 是运行前提，$V$ 是依赖版本，$A$ 是权限。任一条件失败，工具从可调用集合移出，等待迁移或重验。

输入分布漂移不一定能由版本号发现。网页结构未声明升级，真实 DOM 已变化；数据字段仍存在，取值范围扩大。运行时监控错误率、边界值和输出不变量，能发现静默漂移。

程序记忆也可能被上游 bug 污染。一个自动生成报告的脚本长期使用错误公式，后续任务都继承结果。来源证据和回归样例帮助追踪受影响产物；修复工具后，依赖旧版本的报告应标记待重算。

删除记忆不只删代码。注册表、缓存、文档示例和模型提示里仍可能引用旧工具。退役流程更新所有发现入口，并让旧版本调用返回明确错误，避免静默转到不兼容替代品。

## 多模态环境怎样进入代码世界

GUI、图像和物理环境不能天然表示成 API。代码 Harness 需要把连续世界映射为对象、属性和动作，同时保留原始观察以供复核。映射错误会让后续程序在虚构对象上精确运行。

屏幕状态可由截图、可访问性树、DOM 和应用 API 共同描述。截图覆盖视觉内容但难精确定位语义，树和 DOM 结构清楚却可能漏掉画布。对象融合时记录每个字段来源和时间，不把冲突强行压成一个值。

动作同样有多种实现。点击坐标依赖布局，按可访问性 ID 更稳定，调用应用 API 最精确但可能绕过真实用户流程。评测 computer-use 能力时，允许哪种动作会改变任务含义，必须写清。

观察到按钮不代表按钮可点击，点击事件返回不代表业务状态完成。程序需要等待可观察后置条件。对动画和异步加载，轮询条件比固定 sleep 更可靠，并设置最大等待与失败证据。

多模态状态存在识别置信度。OCR 读到金额、视觉模型识别选中状态，都可能错。高风险动作在执行前使用第二观察或人工确认；低风险探索可以带置信继续。代码中的布尔变量若抹掉置信度，会制造虚假确定性。

环境对象还会失去身份。列表排序后第 3 行不再是原对象，坐标移动后旧引用过期。稳定 ID、内容特征和版本联合标识对象；操作前重新解析引用，避免对错对象执行。

## Harness 代码的回归无损升级

综述把 regression-free harness improvement 列为开放问题。新增工具、缓存或并行策略可能提高平均成功率，同时破坏旧任务、安全边界或可恢复性。升级需要把行为不变量与能力增益分开验收。

基础回归集覆盖权限拒绝、幂等重试、checkpoint 恢复、schema 迁移、工具错误解析和取消传播。这些是 Harness 语义，不随具体 Agent 能力变化。模型升级或 prompt 调整也必须通过。

能力集覆盖代表任务，报告逐任务配对变化。新版本让十项成功、两项退化，不能只报平均上涨；退化是否落在高风险任务决定能否发布。对随机 Agent 运行多次，区分稳定退化与采样波动。

安全回归使用对抗输入：提示注入、路径穿越、秘密外泄、测试篡改和越权网络。效用提高不能抵消安全不变量失败。发布门对两类指标使用不同规则。

影子运行可以在不产生副作用的环境中重放真实 trace，比较新旧决策与验证结果。差异较大处人工检查，再逐步放量。直接替换所有活跃长任务，会让旧 checkpoint 和新语义混合。

版本发布要定义状态兼容矩阵。支持从哪些旧 schema 恢复、哪些任务必须固定旧版本、哪些节点需要重新验证，都在升级前确定。回滚也作为正式演练，不等事故发生才发现旧版本读不了新状态。

## 人类监督在代码循环中的位置

人类不需要逐行批准所有代码，监督应集中在目标解释、权限升级、不可逆动作和机器验证覆盖不到的质量。其余可重复硬条件交给程序，提高监督信息密度。

审批界面应展示将执行的具体程序、目标对象、预期副作用和回滚方案，而非只问「是否继续」。大型生成脚本可提供 diff、dry-run 结果和资源上限，让人判断真实影响。

人类修改计划后，旧运行中的代码必须失效。批准绑定程序哈希和环境版本；代码在等待期间变化，重新审批。否则 Agent 可以先获得宽泛批准，再替换实现。

人工反馈也进入证据链。审稿人说「这一段事实不准确」，需要绑定文件版本和位置；后续修改后重新审查受影响范围。把反馈只留在聊天里，fresh context 会丢失。

监督成本应纳入评测。一个系统自动成功率高，却每步都要求人确认，未必比低一些但仅关键处接管的系统更实用。报告人工次数、响应时间和每次决策的信息量。

## 代码作为 Harness 的适用边界

可形式化、可执行、可观察的任务最适合代码承载：数据处理、软件修改、实验运行、资源调度和结构化业务流程。代码能复用控制流，测试能验证后置条件，checkpoint 能保存中间成果。

目标高度主观、环境不可观察或动作不可恢复时，代码只提供流程外壳。审美创作仍需人类判断，外部社会后果无法由单元测试覆盖，开放世界事实需要来源核查。把这些问题硬编码成分数，会把价值判断藏进验证器。

一次性极短任务也可能不值得生成程序。直接工具调用成本更低，失败范围小。Harness 应根据重复度、依赖深度、副作用和恢复价值选择代码化程度，而非所有动作都先写脚本。

代码还会制造新的攻击面和维护负担。执行权限、依赖供应链、生成漏洞和工具漂移都需要治理。代码的确定性只能保证同一程序按实现运行，不能保证实现符合用户意图。

因此「代码作为 Harness」最有价值的判断是：将适合机器约束的部分变成可执行、可测试、可版本化工件，同时保留对规格、观察和价值判断的不确定性。这样代码成为可靠承载层，而不是用确定语法掩盖开放世界问题。

## 形式验证能覆盖到哪里

代码提供形式化入口，但不意味着整个 Agent 系统都能被形式证明。对纯函数、协议状态机和资源边界，可以写不变量并使用类型系统、模型检查或证明器；对开放网页、自然语言目标和外部服务，只能验证局部抽象。

若程序 $p$ 的规格是前置条件 $P$ 与后置条件 $Q$，证明

$$
P(s)\Rightarrow Q(\llbracket p\rrbracket(s))
\tag{14}
$$

只在环境模型、工具语义和 $P/Q$ 正确时成立。真实 API 与模型不一致，或用户目标没有被 $Q$ 完整表达，证明仍可能与实际需求错位。

最适合验证的是 Harness 内核：状态只能合法迁移，未审计结果不能提交，权限不会扩大，重复事件保持幂等，checkpoint 重放得到同一状态。这些性质规模小、边界清晰，且一旦出错会污染所有任务。

生成程序本身可采用分层保证。类型检查排除结构错误，静态分析发现明显越权，属性测试覆盖广泛输入，形式证明用于少量高风险核心。要求每段临时代码都完成定理证明不现实，也会让验证成本超过任务价值。

证明工件同样需要版本绑定。代码、规格、依赖库或求解器变化后，旧证明证书可能失效。可检查证书由小型可信内核重新验证，比相信生成证明的模型自述更可靠。

无法形式化的部分保留经验与人工证据。界面是否易用、文章是否清楚、外部事实是否最新，都不应被伪装成定理。形式方法的价值是缩小不确定区域，而非宣称开放世界已经闭合。

## 一条完整的代码 Harness 轨迹

考虑任务：扫描仓库中的损坏图片，能找到原件就修复，找不到则删除引用，最终所有审计计数为零。它包含检测、来源查找、文件修改、Markdown 更新和全局验证，适合展示三层如何连接。

接口层先定义 `audit_image(path)`、`replace_image(path, bytes)`、`find_references(path)` 和 `remove_reference(file, target)`。每个工具声明路径根、输入输出 schema 与副作用。检测结果区分 zero、bad magic、partial zero head 和 wrong extension，不能只返回一个坏/好布尔值。

机制层生成计划图。节点 A 全库只读扫描，输出带哈希的问题清单；节点 B 对每个问题寻找原件；节点 C 在隔离工作区修复；节点 D 对找不到原件的引用生成补丁；节点 E 重跑全量审计。B 可并行，C/D 按写集合调度，E 依赖所有修改合并。

假设 A 找到 12 个问题，B 找回 9 个原件，3 个没有来源。C 修复 9 张后，其中一张扩展名仍与 magic 不符，局部验证失败，只重开该节点；D 删除 3 个引用，但一个 Markdown 文件同时被另一任务修改，版本门拒绝旧补丁并重新生成。

最终 E 在合并版本上运行，四类计数均为零，同时链接检查通过。只有这份全局证据进入完成状态。若仅汇总局部节点的「9 张已修、3 个引用已删」，组合冲突和残留扩展名都可能漏掉。

扩展层负责并行搜索原件、限制下载网络、缓存哈希匹配并控制 worker 数。增加并发能缩短 B，却不会加速串行合并和最终审计；若磁盘成为瓶颈，更多 worker 反而提高尾延迟。

这条轨迹里的代码承担批量检测与确定修改，模型承担来源判断和缺失时的策略选择，验证器负责最终事实。任何一层都没有独占全部智能，边界清楚才让系统可恢复。

## 扩展性能的简单模型

设任务有 $N$ 个可并行节点，单节点平均执行时间 $T_e$，验证时间 $T_v$，串行协调与合并为 $T_c$，使用 $w$ 个 worker。理想墙钟下界为

$$
T(w)\ge \frac{N(T_e+T_v)}{w}+T_c.
\tag{15}
$$

实际还要加冲突、队列和缓存失效成本 $T_o(w)$：

$$
T(w)=\frac{N(T_e+T_v)}{w}+T_c+T_o(w).
\tag{16}
$$

$T_o$ 往往随并发增长，达到某点后吞吐饱和。若验证器服务率低于执行到达率，队列持续增长；最优 worker 数由最慢阶段决定，不是硬件线程越多越好。

并行效率可写成

$$
\eta(w)=\frac{T(1)}{wT(w)}.
\tag{17}
$$

共享写热点、全局测试和模型 API 限流都会降低 $\eta$。报告扩展结果时，应给 worker 数、任务图并行度、冲突率和各阶段利用率，不能只给总加速比。

成本还有 speculative waste。多个 Agent 同时探索替代方案，最终只采用一个，其余计算换来搜索多样性。若所有候选高度相关，浪费大；若环境反馈稀疏，适度并行探索可能降低找到可行方案的时间。调度器根据历史成功率和预算控制候选数。

代码工件复用会改变长期成本。第一次任务承担生成与测试，后续任务只参数化运行并复核前提。评测单次冷启动低估复用收益，只测成熟工具又忽略开发成本。两种阶段要分别报告。

## 可复现运行需要冻结什么

复现 Code as Agent Harness 不只保存 prompt。需要固定模型与采样、Harness commit、工具 schema、解释器和依赖版本、沙箱策略、环境镜像、任务初态、隐藏验证器以及资源预算。

生成程序可能依赖时间、网络和随机性。可以固定的输入进入镜像或数据快照，必须在线的依赖记录请求与响应。随机种子只能控制部分库，GPU kernel 和并发调度仍可能非确定，结果应多次运行。

每轮保存程序源码、执行命令、环境 diff、测试证据和状态转移。只保存最终代码无法知道失败路径，也无法比较 checkpoint、反馈与多 Agent 协作的贡献。大体积证据用内容寻址存储，trace 保存哈希。

预算停止与程序失败分开。Agent 在时间耗尽时仍有正确候选，属于 censored outcome；验证器明确反例才是错误。把两者都记零分会偏向更短但冒险的策略。

安全策略也要可观察验证。沙箱配置文件存在不代表限制生效，复现实验先运行越权探针并保存结果。验证器与隐藏答案必须位于 Agent 权限之外，隔离需要通过攻击测试证明。

## 三层框架的因果消融

Interface、Mechanisms 和 Scaling 彼此依赖，仍可通过受控消融估计贡献。固定单 Agent，比较自由文本工具调用与类型接口，测参数错误和越权率；固定接口，逐项加入 checkpoint、验证与程序记忆，测恢复和重复工作；最后增加 worker，测吞吐与冲突。

如果一开始同时加入类型、测试、多 Agent 和更强模型，终局提升无法归因。三层逐级实验让每个机制有对应预测：类型层降低调用错误，验证层降低错误提交，checkpoint 降低恢复损失，扩展层降低可并行部分墙钟时间。

消融还需负向结果。类型检查可能增加调用修复轮次，严格验证可能提高假阴性，checkpoint 可能产生存储开销，多 Agent 可能因合并冲突变慢。只报告成功指标会把代价藏掉。

交互效应同样重要。类型接口让多 Agent 更容易共享工件，独立验证让程序记忆可安全复用，隔离工作区让并行修改可合并。单项收益小，不代表组合没有价值；但组合结果要通过因子实验，而非叙事推断。

## 最终应抓住的主线

代码在 Agent 系统中经历了角色变化：先是模型生成的目标产物，随后成为调用工具和表达计划的语言，再进一步成为保存状态、验证结果和协调多 Agent 的基础设施。三层框架正是在描述这条扩张路径。

Interface 层解决模型如何与可执行世界连接，Mechanisms 层解决执行怎样形成可信闭环，Scaling 层解决同一语义怎样在更多任务和 Agent 上保持。后一层不能弥补前一层的模糊：接口不安全，扩展会放大越权；验证不可靠，共享会传播错误。

代码带来的核心性质是可执行、可测试、可版本化和可复用。它没有自动提供正确规格、完整观察或价值判断。把这条边界留下，才能解释为什么最强的 code harness 仍需要环境证据、人工监督和故障恢复。

对长程任务而言，真正重要的是把一次次模型生成变成受约束状态转移：程序声明输入与效果，沙箱限制权限，环境返回证据，验证器决定提交，checkpoint 保存可信进度。模型可以更换，代码可以升级，这条状态语义必须稳定。

## 程序等价与行为漂移

Agent 经常重构或重写程序，并声称「行为不变」。文本 diff 小不代表语义等价，文本完全不同也可能实现同一函数。Harness 需要根据任务选择等价标准。

对纯函数，可以要求观测等价：在输入域 $X$ 上

$$
\forall x\in X,\qquad p(x)=q(x).
\tag{18}
$$

无限输入域通常无法穷举，只能由证明、属性测试和代表样本近似。对有副作用程序，等价还要比较允许效果、顺序和失败状态；两个程序输出相同文件，一个额外上传数据，显然不等价。

重构验证可组合静态与动态方法。类型与控制流分析发现接口变化，差分测试在相同快照上运行新旧版本，环境 diff 比较副作用，性能基准检查资源回归。任何差异都映射回规格，判断是预期改进还是漂移。

随机和并发程序不能要求逐字输出一致。定义可接受分布、集合或不变量更合理，例如结果顺序可变但元素相同，延迟在阈值内且无重复提交。错误地使用精确快照测试，会制造大量假回归。

Agent 生成的「优化」尤其需要性能—正确性双门。减少验证、缓存旧结果或扩大批量都可能提速，同时改变错误边界。新版本在相同正确性与安全阈值下比较成本，才有资格称优化。

## 三个反例确定代码的边界

第一个反例是规格错误而程序完美。用户要求按当地法律计算税额，Harness 把错误税率写进规格，程序通过全部测试。代码的可执行性让错误更稳定，只有外部权威来源能纠正规格。

第二个反例是观察错误而控制正确。GUI 识别器把未选中复选框读成已选中，程序依据观察跳过操作并生成成功报告。控制流、类型和日志都正常，根因在感知。多模态 Harness 必须保留观察置信与原始证据。

第三个反例是局部程序正确、全局组合错误。一个 Agent 压缩图片，另一个更新引用，两者分别通过测试；合并后图片哈希变化使缓存清单过期，部署仍引用旧资源。局部验证无法代替组合审计。

还可以加入时间反例。程序昨日对 API 正确，今日服务改变分页默认值，代码继续无报错运行却漏掉数据。版本与运行时不变量检测比「过去成功过」更重要。

这些反例共同说明：code as harness 把行动变得可计算，却仍依赖正确规格、可靠观察、组合验证和持续环境核对。文章若只强调执行确定性，会把真正困难的边界移出视野。

## 最小验收清单

一套代码型 Harness 达到可用下限，至少要证明几件事：接口参数能在执行前验证；权限由外层强制；副作用有日志和幂等语义；程序、规格与测试绑定版本；失败能从 checkpoint 恢复；验证器位于执行者权限之外；多 Agent 合并后重跑组合检查。

每一项都应有反向测试。传入错误类型应被拒绝，越权探针应失败，重复动作不产生第二份效果，旧证据遇到新版本会失效，崩溃重放不改变状态，Executor 无法修改隐藏测试，文本无冲突但语义冲突的分支会被回归测试抓住。

通过这些测试只证明 Harness 内核工作，仍需在目标领域验证模型能力与观察覆盖。基础设施验收和任务成功不能互相替代：前者防止系统性污染，后者证明具体工作真正完成。

最终交付应包含运行版本、状态摘要、产物哈希、验证证据、未解决项、已发生补偿和成本。只交一份生成代码，读者无法知道它是否在正确环境里运行过，也无法恢复后续任务。

## 结论怎样被推翻

如果类型接口没有降低参数和对象错误，说明 schema 只增加格式负担；如果外部验证没有降低错误提交，说明验证覆盖不足或执行者仍能污染裁判；如果 checkpoint 没有减少故障后的重做，说明保存对象不完整；如果多 Agent 只增加 token 和冲突，没有缩短关键路径，Scaling 层没有产生有效并行。

同样，程序记忆若在第二次任务中没有降低成本，可能缺少可复用前提；代码生成若比直接工具调用更慢且更易出错，当前任务不适合代码化。这些负结果都应保留，避免「用了代码」本身成为成功叙事。

真正支持三层框架的证据，应在对应层出现：接口错误下降、执行与恢复更可靠、扩展后吞吐提高且可信状态不被破坏。终局成功率只是共同结果，机制指标才能说明改进来自哪里。

因此复现实验最好预先登记每个机制的预测和失败判据。实验结束后按原判据报告，不能看到结果再把没有改善的指标解释成无关。代码 Harness 的优势正是可执行与可检验，它自身也应接受同样严格的检验。

当实验结果互相冲突时，应保留任务级差异并回到机制假设：是接口减少了错误却增加了延迟，还是并行提高吞吐却破坏了组合验证。把所有维度压成一个总分，会再次失去代码化原本带来的可诊断性。

机制保持可诊断，改进才能持续累积。

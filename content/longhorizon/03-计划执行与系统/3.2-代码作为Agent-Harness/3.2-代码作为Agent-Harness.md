# Code as Agent Harness：代码作为 Agent 基础设施的三层综述

> **论文**：*Code as Agent Harness: Toward Executable, Verifiable, and Stateful Agent Systems*（arXiv:2605.18747，2026-05）
> **PDF**:[arXiv:2605.18747](https://arxiv.org/pdf/2605.18747)

## 原文精读

### 核心论断

LLM 已强到能写竞赛级程序与仓库级补丁，但在 **agentic 系统**里，代码的角色正在变：它不只是**生成目标（target output）**， increasingly 充当**操作基底（operational substrate）**——承载推理、行动、环境建模与 execution-based verification。

作者用 **agent harness** 镜头统一这一趋势，提出 **code as agent harness**：以代码为中心构建可执行、可验证、有状态的 Agent 系统，并据此综述约 **197** 篇代表性工作。

### 三层 taxonomy（全文组织轴）

#### Layer 1 — Harness Interface（接口层）

回答：代码如何把 Agent 接到三大基本功能？

| 接口 | 代码的角色 | 典型机制 |
|---|---|---|
| **Reasoning** | 思维链/程序即推理 | CoT-as-code、过程奖励、中间结果可检查 |
| **Acting** | 生成程序即策略 | Code-as-action、API 调用脚本、可复用 skill |
| **Environment Modeling** | 状态/动力学/反馈的形式化 | 模拟器、单元测试套件、GUI/OS 状态机 |

接口层的共同点是：把「模型想说的话」变成**可运行、可 diff、可回归**的对象，而不是纯自然语言承诺。

#### Layer 2 — Harness Mechanisms（机制层）

在 long-horizon 执行中，harness 需要 sustained 能力。综述归纳为：

- **Planning**：意图分解为结构化计划；「plan as program / contract」——计划本身可解析、可验证。
- **Memory**：跨轮状态保留、多 Agent 共享记忆、**context compaction & state offloading**（与 long-horizon 压缩论文线直接对话）。
- **Tool Use**：函数式工具、环境交互工具、**verification-driven** 工具（测试/ linter / sandbox 回传）、工作流编排工具。
- **Plan–Execute–Verify 控制环**：从「调试代码 bug」推广到 **harness-level control**——沙箱执行、权限化状态转移、确定性 sensor 验证。
- **Adaptive Harness Optimization**：深度 telemetry 作优化底稿；**Evolution Agent** 在治理约束下 mutate harness（prompt/tool/workflow），使系统自我改进但可审计。

机制层强调：可靠 long-horizon 不靠「更长 context」，而靠**显式状态 + 可重复验证闭环**。

#### Layer 3 — Scaling the Harness（扩展层）

从单 Agent 到协作生态：共享 **code artifacts**（repo、测试、trace、结构化中间件）成为多 Agent 的**公共工作区**。

- **角色分化**：manager / planner / coder / reviewer / tester
- **交互模式**：pair programming、repair、debate、red-teaming、adversarial
- **拓扑**：中心化编排 vs 分布式/流式协作（AutoGen、MetaGPT、Self-Collaboration 等）
- **状态收敛**：test-gated merge、consensus on correctness

代码在这里是**协调与验真的 lingua franca**——比自然语言更利于 diff、CI 与权限边界。

### 应用域与开放挑战（原文 outline）

横跨 coding assistant、GUI/OS automation、embodied agent、科学发现、个性化推荐、DevOps、企业工作流。

开放问题包括：超越终局任务成功的 harness 评测、不完整反馈下的 verification、**回归-free 的 harness 改进**、多 Agent 一致共享状态、安全关键动作的人类监督、多模态环境扩展。

## 方法/架构解析

### 与「Chat Agent」范式的差异

传统 Chat = 单会话文本状态机；**code harness** = 外部可观测状态（文件、测试、进程、repo）+ LLM 提议转移 + 确定性验证器裁决。综述实质是在说：**Agent 可靠性边界由 harness 工程决定，不由单次 sampling 决定**。

这与 LongHorizon-Harness（MEA 循环）、Polaris（deterministic crawl + LLM judgement 分流）等同属 2026 年长任务/agent 系统文献簇，但 **2605.18747** 更偏**概念收拢与家谱**，给出跨域 vocabulary。

### 三层之间的依赖关系

```text
Interface（代码接 reasoning/action/env）
    ↓ 需要
Mechanisms（plan/memory/tool/verify 维持长程）
    ↓ 扩展到
Scaling（repo 级共享工件 + 多角色编排）
```

读综述时可按「你的系统缺哪层」定位文献：只做 tool call API 属于 interface 子集；没有 verify loop 则 mechanisms 不完整；多 Agent 无共享 test/state 则 scaling 层悬空。

### 对 Harness 工程 checklist 的提炼

1. **Executable**：关键决策是否落到可运行 artifact？（脚本、测试、配置）
2. **Verifiable**：是否有 deterministic sensor 独立于 LLM 自评？（测试、类型检查、环境 diff）
3. **Stateful**：状态是否在 context 外显式持久？（DB、文件、task state store）
4. **Regression-safe**：harness 自我修改是否 gated？（telemetry + governed mutation）
5. **Multi-agent ready**：共享工件是否 versioned、可 review？

### 与 KnowPilot / OasisMind 语境的轻量对照

见微/OasisMind 的 Chat store 不变量、审批 scope、SessionStreamHub——本质是在 web product 里实现 mechanisms 层的 **plan–execute–verify + 推送式状态**；本综述提供的是跨论文的**命名与分层坐标系**，便于把 longhorizon、RSI、coding agent 文献挂到同一棵树上。

### Mechanisms 层子题（便于按图索骥）

综述在 mechanisms 层进一步细分子题，读原文时可按需求跳转：

- **Memory**：单 Agent 工作记忆、多 Agent 共享记忆、**context compaction & state offloading**（与 CompactionRL、LongHorizon-Harness 等 2026 文献直接对话）。
- **Tool Use 四分**：function-oriented（API）、environment-interaction（shell/GUI）、verification-driven（测试/linter）、workflow-orchestration（DAG/CI）。
- **Plan–Execute–Verify**：planning as contract formation；sandboxed execution + permissioned state transition；verification through deterministic sensors。
- **Adaptive Harness Optimization**：deep telemetry → evolution agent → **governed mutation**（防 harness 自我修改引入 silent regression）。

### Scaling 层的协作拓扑

多 Agent 并非「更多 chat 窗口」，而是共享 **repo / test suite / trace** 作为 ground truth。综述列举的 workflow topology 包括：中心化 coordinator、分布式 peer、streaming 协作；状态收敛机制包括 test-gated merge 与 consensus。MetaGPT、AutoGen、Self-Collaboration 等被归入「code 作共享 harness」案例——值得与 Polaris 六阶段流水线、Stanford CS329A Mod 4「可逆性」对照阅读。

从工程落地角度，**code harness** 回答的是：当 Agent 声称「我已经改好了」时，系统能否用 git diff、CI 红灯、property test 独立反驳？综述把这一需求从 coding agent 推广到 GUI/OS/embodied/scientific 全谱，强调 **harness 是可版本化的软件制品**，而非 prompt 里的软约束。开放挑战里的「regression-free harness improvement」尤其值得 RSI 读者关注：自动化改 prompt/tool 若无 golden trace 回归，等价于在未验证状态下 mutate 生产配置。

## 代码怎样承载长任务状态

把代码当作 harness, 并不是让模型把自然语言计划换成 Python 以后就万事大吉. 真正的变化是把任务中一部分隐含状态放进可以读取、执行和比较的对象. 对话里的「已经处理到第三批文件」很难独立验证; 一个带版本号的任务清单、一组文件哈希和一份测试报告则能由其他执行体重新读取. **代码的价值是让状态转移变得显式, 可靠性仍然来自 schema、权限、验证和恢复机制.**

这里的「代码」至少包含三种载体. 第一种是程序文本, 它保存分支、循环、异常处理与工具调用顺序. 第二种是文件和数据库记录, 它们保存跨进程仍需存在的目标、任务进度、环境快照与验证结果. 第三种是运行时对象, 例如队列项、进程句柄、浏览器会话和事务上下文, 它们连接当前执行体与外部环境. 三者的生命周期不同: 程序文本可以版本化, 文件可以持久化, 运行时对象通常在进程退出后失效. Harness 如果只序列化最后一种对象的名称, 却没有重建方法, 重启后看到的只是一个无法继续使用的旧引用.

可以把第 $t$ 步的外置状态写成

$$
X_t=(G_t,Q_t,A_t,R_t,V_t),
$$

$G_t$ 是当前目标版本, $Q_t$ 是待办与依赖, $A_t$ 是已经执行的动作记录, $R_t$ 是外部资源及版本, $V_t$ 是验证结果. LLM 不直接把一句「完成」写入 $V_t$. 它只能提出动作, harness 执行动作并读取传感器结果, 验证器再决定某项状态能否从 `running` 转成 `verified`. 这就是综述所说的 executable、verifiable 和 stateful 在工程里的交点.

## 控制平面与数据平面

长任务系统可以分成两个互相配合的平面. **控制平面**保存目标、计划、权限、任务状态机、重试规则、checkpoint 指针和审计事件. 它回答「现在允许做什么、下一步由谁做、怎样判断完成」. **数据平面**承载真正被处理的对象, 例如仓库文件、网页内容、数据库行、模型权重、实验产物和工具返回. 它回答「动作实际作用于什么、产生了哪些变化」.

两者分开以后, 控制平面的一条 `task.completed=true` 不能覆盖数据平面的现实. 假设写文件的动作只成功了一半, 执行进程却在更新任务状态前崩溃. 恢复时不能仅看任务记录是 `running` 就重做, 也不能看到目标文件存在就宣布完成. Harness 需要读取文件哈希、临时文件、提交标记与对应验证结果, 再决定继续、补偿还是回滚.

控制平面也不能包含全部数据. 把大段工具输出、二进制产物和完整网页塞进任务状态, 会让每次调度都承担不必要的读写成本. 更合理的记录是资源定位符、版本、摘要和验证状态, 完整对象留在数据平面. 需要精确证据时再按定位符读取. 也就是说, 控制平面持有「怎样找到可信状态」, 不复制所有状态内容.

## 类型与 schema 是可执行约束

自然语言计划允许一句话同时表达目标、猜测和结果, 程序化状态则可以用 schema 把它们拆开. 一个最小任务对象可以写成:

```ts
type TaskState = {
  taskId: string;
  goalVersion: number;
  phase: "planned" | "running" | "verifying" | "verified" | "failed";
  inputs: Array<{ uri: string; version: string }>;
  actions: Array<{ id: string; tool: string; status: string }>;
  checks: Array<{ name: string; exitCode: number; artifactUri: string }>;
  checkpointId?: string;
};
```

这段类型做了几件具体的事. `goalVersion` 防止旧计划在目标改变后继续运行; `inputs.version` 让动作与输入版本绑定; `actions.id` 为副作用提供幂等标识; `checks` 保存验证器读到的结果, 而不是模型对结果的转述. `phase` 只能取有限状态, 因而可以定义合法转移. 例如 `running -> verified` 应被拒绝, 中间必须经过 `verifying`, 且 `checks` 中存在与当前产物版本对应的成功记录.

Schema 只会拒绝结构错误, 无法保证语义正确. 一个合法的 `artifactUri` 可能指向旧日志, `exitCode: 0` 也可能来自错误的测试范围. 因此字段需要交叉约束: 检查记录关联动作 ID、输入版本和产物哈希; 验证器确认它检查的是本轮结果; 状态转移函数一次性校验这些关系. 如果把校验散落在多个回调里, 任一调用路径漏掉检查, 同一个 schema 仍会保存错误状态.

## 工具副作用怎样进入状态机

工具调用可以分成只读、可重复写入和不可逆副作用. 读取文件或查询状态通常可以安全重试, 但结果可能随环境变化, 因而仍要记录读取时间和版本. 生成同一临时文件属于可重复写入, 前提是路径与内容由确定输入决定. 发送消息、创建远程资源或扣费调用则可能不可逆, 盲目重试会产生重复副作用.

幂等键把一次逻辑动作与多次网络尝试关联起来. 设动作标识为 $k$, harness 在调用前写入 `intent(k)`, 工具返回后写入 `effect(k, r)`. 进程若在两次写入之间退出, 恢复逻辑先查询外部系统是否已经存在对应 $k$ 的效果. 查到就补写结果, 查不到才重新执行. 工具不支持幂等键时, 可以使用业务唯一约束、预创建资源 ID 或执行后的查询来缩小不确定区间.

事务适合能够由同一存储系统原子提交的动作. 例如任务状态与本地数据库变更可以放在一个事务里, 要么一起成功, 要么一起撤销. 跨越文件系统、浏览器与远程 API 的工作流通常无法共享一个事务, 这时需要 **补偿动作**. 创建资源后的补偿可能是删除资源, 发布内容后的补偿可能只能追加撤回声明. 补偿并不保证恢复到完全相同的世界, 所以控制平面应记录它的实际结果, 不能用 `rolled_back=true` 掩盖仍然存在的外部影响.

**代码不是天然可靠的关键证据就在副作用边界.** 模型可以生成语法正确的重试循环, 却把不可逆动作执行三次; 也可以捕获异常后返回成功, 让控制平面错误进入完成态. Harness 必须在模型生成代码之外强制权限、幂等与状态转移, 不能把这些约束作为 prompt 里的建议.

## Checkpoint 保存哪些东西

Checkpoint 不是把进程内存完整复制一份. 它要保存能够重建执行的最小充分状态: 当前目标版本、已验证里程碑、未完成动作、外部资源版本、已发生副作用及其幂等键、下一步允许的状态转移. 对运行时对象, checkpoint 保存重建配方, 例如重新打开哪个文件、查询哪个远程任务、用哪个会话凭证恢复连接, 而不是保存已经失效的句柄值.

合适的 checkpoint 通常位于验证边界. 一个子任务完成且产物通过检查后, harness 固化 `X_t`; 下一阶段失败时, 可以回到这份已验证状态. 若在每条模型消息后保存, checkpoint 数量很多, 其中大部分并没有新的可信事实. 若只在任务结尾保存, 中途故障又会丢掉全部进展. 触发条件应对应真实状态变化, 例如目标版本更新、不可逆操作之前、阶段性验证通过或即将压缩上下文.

恢复时要重新读取数据平面. 文件可能被其他进程修改, 远程任务可能在 Agent 离线期间完成, 权限也可能过期. Harness 用 checkpoint 作为参照, 将当前环境与保存版本做 diff, 然后选择继续、重新规划或进入人工审批. 直接把旧运行时对象反序列化并继续调用, 只是把陈旧状态包装成了程序对象.

## 沙箱和权限边界

代码可执行意味着错误会产生真实影响. 沙箱负责限制执行体能够看见和修改的资源, 权限系统负责判断某个动作在当前目标和用户授权下是否允许. 两者不能互相替代. 容器隔离可以阻止脚本读取宿主机目录, 但无法判断 Agent 是否有权删除容器内的项目数据; 审批规则可以禁止删除, 却无法阻止恶意依赖利用系统漏洞逃逸.

权限应靠能力授予, 不靠工具名称猜测. 同一个 shell 工具既能只读列目录, 也能覆盖文件. Harness 可以为任务分配明确的工作目录、只读数据源、允许访问的网络域和资源配额, 高风险动作再要求更窄的临时能力. 模型生成的代码运行前先静态检查目标范围, 运行时由沙箱限制系统调用, 运行后再比较环境 diff. 任一层发现超出范围, 控制平面都不能把动作记为成功.

日志同样属于安全边界. 完整命令和返回内容便于审计, 也可能包含凭证与隐私数据. 状态层应保存脱敏后的摘要和受控证据指针, 原始日志按访问权限隔离. 多 Agent 共享 repo 或 trace 时, 共享范围必须跟随角色权限, 不能因为它们属于同一任务就默认全部可见.

## 一个小型执行例

设任务是「修改配置中的超时值, 运行检查, 通过后生成变更记录」. 控制平面创建目标版本 3, 输入文件版本为哈希 `h0`, 并生成动作 `a1=patch`, `a2=test`, `a3=report`, 依赖为 $a1\rightarrow a2\rightarrow a3$.

1. 执行 `a1` 前, harness 检查目标路径位于允许目录, 记录幂等键 `task-7/a1`, 并把旧文件保存到 checkpoint.
2. 沙箱内脚本读取 `h0`, 应用结构化 patch, 写入临时文件, 校验 schema 后原子替换, 得到新哈希 `h1`.
3. 控制平面不能因为脚本退出码为 0 就完成任务. 它把阶段转为 `verifying`, 执行 `a2`, 并把检查范围、退出码和 `h1` 写入 `checks`.
4. 如果检查失败, 文件恢复为 `h0`, 记录失败日志与补偿结果, 计划停在 `a1`. 如果检查通过, `a1` 与 `a2` 进入 `verified`, 然后 `a3` 只从验证记录生成变更说明.

假设进程在文件替换后、状态更新前退出. 新执行体读取 checkpoint, 发现磁盘哈希为 `h1`, 幂等键没有完成记录. 它不会再次应用 patch, 而是核对 `h1` 的 schema 并重新运行 `a2`. 这个例子只有三步, 已经同时用到版本、幂等、验证和恢复. 如果状态只存在对话里, 新执行体很难区分「准备修改」与「已经修改但尚未登记」.

## 怎样对照评测代码 Harness

比较代码 harness 与纯对话控制时, 应固定模型、任务、工具和最大调用预算, 只改变状态与控制机制. 任务集合要包含正常流程、工具超时、部分成功、进程中断、输入版本变化和不可逆副作用. 每种故障在预先指定的步骤注入, 避免某组碰到更简单的随机轨迹.

终态指标包括任务成功率、硬约束违反数和产物检查结果. 过程指标至少记录: 未验证结果被提升为完成态的次数; 重试造成的重复副作用; 从故障到可信 checkpoint 的恢复步数; 状态与实际环境不一致的持续时间; schema 或权限层拒绝非法转移的次数; 为持久状态、验证和恢复增加的 token、延迟与存储成本.

还要加入「代码自身出错」的对照. 人为让生成脚本引用错误字段、捕获异常后返回成功、读取旧版本输入或遗漏补偿动作, 观察 harness 的外层约束能否拒绝这些结果. 如果系统只在正常路径上表现更好, 故障路径仍然相信模型生成代码, 它只是把自然语言幻觉换成了可执行 bug.

结果按任务依赖深度与副作用等级分桶. 简单只读任务里, 代码 harness 的固定成本可能大于收益; 状态多、恢复频繁或含高风险写操作的任务, 显式控制与验证更重要. 这类评测不需要宣称代码一定优于对话. 它要回答更具体的问题: 哪类状态被外置以后可以恢复, 哪类错误被确定性检查拦住, 系统为此付出了多少工程和运行成本.

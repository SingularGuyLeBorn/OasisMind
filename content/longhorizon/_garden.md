# Long-Horizon · 长任务智能体

2025 年 2 月 Claude 3.7 Sonnet 发布, 同年 7 月 Kimi K2 发布. 从那段时间开始, 我第一次明显觉得模型进入了「聪明, 基本可用」的阶段. 这是我的主观分界, 不是一条公认的技术标准. 当时常见 benchmark 仍然把能力压缩成一道题和一次回答: 数学题是否做对, 代码补丁是否通过测试, 一次工具调用是否成功. 这些数字继续上涨当然重要, 但也让我产生了另一个疑问: 单轮回答已经足够好以后, 模型下一阶段的能力还能从哪里提升?

Agent 给出了一部分答案. 模型开始读仓库, 调工具, 修改文件,运行测试,观察结果,再决定下一步. 后来这个问题又被进一步拆成 Long-Horizon 能力: 任务跨越几十到几百步时, 系统能否一直知道目标是什么, 当前完成到哪里, 哪些事实已经验证, 哪些操作可以回滚. **Long-Horizon 研究的对象是一条持续演化的任务状态, 不是单纯让模型输出更多 token.**

这座知识库就从这个疑问开始. 现有论文分别研究任务状态管理, 上下文压缩, 用户意图变化, 外部记忆, 训练环境和 Agent harness. 它们使用的术语不同, 但都在处理同一组变量: 目标, 环境状态, 已完成动作, 验证结果和剩余计划怎样随时间更新. 把这些变量写清后, 才能比较一个系统是真的能完成长任务, 还是只在很长的轨迹里偶尔得到正确终点.

## 1. Long-Horizon 到底指什么

### 1.1. 一条任务状态怎样持续变化

设任务在第 $t$ 步的可恢复状态为

$$
S_t=(G_t,E_t,A_{1:t},V_t,P_t).
$$

$G_t$ 是当前目标和约束, $E_t$ 是外部环境的可观察状态, $A_{1:t}$ 是已经执行的动作, $V_t$ 是经过验证的事实与结果, $P_t$ 是剩余计划. Agent 根据当前上下文选择动作 $a_{t+1}$, 环境执行后返回观测 $o_{t+1}$, 系统再把状态更新为 $S_{t+1}$. 一项任务的 horizon 不只由动作数量决定, 还取决于早期决策会影响多远之后的状态, 以及出错后要追溯多少历史才能修复.

真正困难的地方在状态更新. 计划可能因为新证据改变, 用户可能在中途修改约束, 工具可能返回部分成功, 外部文件也可能被其他进程更新. 如果系统只保留一段自然语言摘要, 摘要遗漏的约束会永久消失; 如果保存全部轨迹, 上下文成本会持续增长, 早期噪声又会干扰后面的判断. Long-Horizon 系统必须决定哪些信息成为事实状态, 哪些只保留为审计记录, 哪些可以压缩或丢弃.

### 1.2. 五个容易混在一起的「长」

长输出只表示一次生成的 token 多. 模型可以连续写一万字, 却没有与环境交互, 也没有更新任务状态. 长上下文表示模型一次能够读取更多 token, 它扩大可见范围, 但不能保证模型会正确找到旧约束或识别状态冲突. 长时间运行是墙钟时间长, 一个等待下载两小时的脚本并不比五分钟内执行一百次有依赖操作的任务更难.

多工具调用说明轨迹中动作较多, 仍不能单独定义 Long-Horizon. 五十次互不相关的搜索可以并行完成, 每一步的错误不会影响下一步; 十步数据库迁移却可能具有严格依赖, 第一步选错 schema 会让后面全部无效. 多步骤任务只有在步骤之间共享状态, 早期结果会改变后续选择, 并且最终成功依赖中间约束持续成立时, 才出现本库关心的长程难度.

因此本库用四项性质识别 Long-Horizon 任务: 跨步依赖, 状态变化, 延迟验证和错误传播. 任务至少应包含其中多项, 并在评测中真正测到它们. 只报告平均 token 数或工具调用数, 不能说明系统具备长程能力.

## 2. 能力由哪些部分组成

### 2.1. 计划, 执行与验证

长任务需要计划, 但一次生成的完整计划很快会过期. 更可靠的做法是保留稳定目标, 只细化当前可以执行的一小段, 每次获得新证据后重算剩余计划. [LongHorizon-Harness](./03-计划执行与系统/3.1-LongHorizon-Harness/3.1-LongHorizon-Harness.md)把管理者, 执行者和审计者分开: 执行者产生原始轨迹, 审计者把可验证结果写入任务状态, 管理者只根据审计后的状态规划下一轮. 这种分工的重点不是角色数量, 而是未验证的自我评价不能直接成为下一轮事实.

[代码作为 Agent Harness](./03-计划执行与系统/3.2-代码作为Agent-Harness/3.2-代码作为Agent-Harness.md)讨论另一种组织方式: 用代码, 文件和运行时对象承载状态, 让控制流和中间结果不必全部塞进对话. 它适合结构明确, 可以程序化检查的任务, 代价是模型生成的控制逻辑本身也会出错, 权限和副作用必须由外层系统约束.

### 2.2. 记忆与上下文压缩

[上下文压缩论文](./02-状态记忆与恢复/2.2-上下文压缩/2.2-上下文压缩.md)和 [LiveMem](./02-状态记忆与恢复/2.3-LiveMem动态记忆/2.3-LiveMem动态记忆.md)处理上下文有限时怎样保留历史. 压缩不是单纯缩短文本. 一个摘要需要保存仍然有效的目标, 已验证事实, 未解决冲突和可恢复位置; 原始日志则用于追责和重建. 如果把结论与猜测混在同一段摘要里, 后续模型很难重新判断可信度.

记忆还涉及写入策略. 每一步都写会积累大量重复状态, 只在任务结束写又无法支持中途恢复. 系统需要定义写入触发条件, 版本和失效规则. 外部环境已经变化时, 旧记忆即使当时正确也可能不再适用; 因此读记忆时要同时检查时间, 来源和对应的环境版本.

### 2.3. 意图变化与环境生成

[用户意图演化](./02-状态记忆与恢复/2.1-用户意图演化/2.1-用户意图演化.md)关注目标本身发生变化. 新要求可能补充原目标, 也可能替换它; 系统若只把新消息追加到上下文, 很容易同时执行互相冲突的两版约束. 目标状态需要显式版本化, 让每个计划和产物都能追溯到它依据的目标版本.

[OpenForge RL](./04-训练环境与案例/4.1-OpenForge-RL/4.1-OpenForge-RL.md)和 [Orchard](./04-训练环境与案例/4.2-Orchard/4.2-Orchard.md)进入训练侧. 长任务数据不能只靠固定问答对提供, 需要可执行环境, 中间反馈和能够判断进展的验证器. 环境生成扩大任务规模, 同时带来答案泄漏, 不可复现和判定器错误. 训练系统必须记录环境版本, 初始状态, 动作和验证结果, 否则一条成功轨迹无法成为可靠训练样本.

## 3. 怎样评测长程能力

### 3.1. 最终成功率之外的轨迹指标

最终结果仍然重要, 但它无法区分两种系统: 一个稳定地推进并在最后一步失败, 另一个大部分时间偏离目标却偶然撞到正确答案. 长任务评测还应记录有效进度, 约束违反, 无效动作, 回滚次数, 错误首次出现的位置和恢复成本. 这些量需要基于环境状态或可执行检查计算, 不能只让另一个模型阅读轨迹后凭印象评分.

任务长度也要按有效依赖计算. 人为插入无关步骤可以增加轨迹长度, 却没有增加状态管理难度. 更有价值的分桶方式是依赖深度, 状态规模, 延迟验证距离和可逆性. 同一系统在短依赖与长依赖上的性能曲线, 比一个混合平均分更能显示 horizon 扩大后哪里开始失效.

### 3.2. 四章怎样接起来

[第 1 章](./01-定义与评测/01-定义与评测.md)先把 Long-Horizon 写成可测量的任务结构，再建立最终结果、有效进度、约束、恢复和成本口径。[第 2 章](./02-状态记忆与恢复/02-状态记忆与恢复.md)处理目标版本、工作记忆、长期存储、上下文压缩和 checkpoint。[第 3 章](./03-计划执行与系统/03-计划执行与系统.md)进入任务分解、滚动计划、工具交互、验证闭环与 Harness。[第 4 章](./04-训练环境与案例/04-训练环境与案例.md)讨论如何构造可执行环境、生成轨迹、设计验证器并把这些材料用于训练和 benchmark。

读完整库后, 面对一个新的 Agent 系统, 应能具体检查: 目标保存在哪里, 环境状态从哪里读取, 已完成动作怎样验证, 上下文被压缩后什么信息永久丢失, 故障后从哪个 checkpoint 恢复, 评测是否真的覆盖跨步依赖. 这些问题比「能连续运行多久」更接近 Long-Horizon 能力本身.

# Orchard：开源 Agentic Modeling 框架与 Env 基座

> 论文：Orchard: An Open-Source Agentic Modeling Framework
> 作者：Baolin Peng, Wenlin Yao, Qianhui Wu, Hao Cheng, Xiao Yu, Rui Yang, Tao Ge, Alessandro Sordoni, Xingdi Yuan, Yelong Shen, Pengcheng He, Tong Zhang, Zhou Yu, Jianfeng Gao 等（Microsoft Research 等）
> arXiv：[2605.15040](https://arxiv.org/abs/2605.15040)（2026-05）
> GitHub：[microsoft/Orchard](https://github.com/microsoft/Orchard)
> Dataset：[microsoft/Orchard](https://huggingface.co/datasets/microsoft/Orchard)（swe 107K + gui 3K 轨迹）

## 1. 一、环境服务与三条训练路线

**环境不可复用造成的训练断裂**

Agentic modeling 的训练瓶颈不仅在模型算法，也在环境能否稳定、低成本地产生可复现轨迹。

若每个项目各自绑定 sandbox、Harness 与 trainer，数据和评测协议就很难迁移。

**Agentic modeling** 的目标是把 LLM 变成能规划、推理、用工具、与外部环境多轮交互的自主 Agent。但开源社区长期存在两重断裂：

1. **基础设施断裂**：高性能系统依赖闭源代码、闭源模型或托管服务；开源框架多聚焦 agent orchestration / harness 设计，**缺少可扩展的 model training 栈**。
2. **环境不可复用**：每个研究项目重建 sandbox、rollout、eval 管道——数据集、训练配方、评测协议无法跨 harness / 域 / 项目移植。

论文论断：**环境层不应是某个训练栈的副产品，而应是独立、薄、可自托管的 standalone service**——这正是 Microsoft Harness 系列（Orchard → OpenWebRL → OpenForge RL → LongHorizon 对照系）的第一块地基。

**Env、Recipes 与 Trainer 的分层**

Orchard 的环境服务是公共底座，三条 Recipe 分别定义任务特定的数据、奖励、模型和评测。

公共层提供生命周期与执行原语，Recipe 层再决定数据、奖励、模型和评测。

Orchard 分三层：

| 层 | 内容 | 职责 |
|---|---|---|
| **Recipes** | Orchard-SWE / Orchard-GUI / Orchard-Claw | 轨迹收集、数据策展、reward、policy 优化（SFT+RL） |
| **Orchard Env** | K8s-native sandbox service + Python SDK | 生命周期、exec、文件 I/O、网络策略、REST API |
| **Trainer** | vendored [slime](https://github.com/THUDM/slime) fork | RL 训练；rollout 代码在 `examples/orchard/` |

**Orchard Env 关键设计**：

- **三层架构**：Client SDK → FastAPI Orchestrator → In-pod Agent（注入用户镜像）。
- **Runtime agent injection**：init container 注入自包含 Python interpreter 的 exec agent，**任意 Docker 镜像零修改接入**——支持 SWE-bench 数百种异构镜像。
- **Hot path 优化**：创建/删除走 K8s API（cold path）；exec / file / health **直连 Pod IP**（hot path），绕过 kubectl exec WebSocket 开销。
- **Built-in harnesses**：每个 sandbox 预装 `codex`、`claude`、`pi`、`opencode`、`hermes` 等于 PATH——换 harness = 改命令，不改镜像。
- **Multi-replica orchestrator**：Redis 状态 + 分布式锁；Calico NetworkPolicy 默认 deny-egress；TTL cleanup；API-key auth。

**三条 Recipe（同 Env、不同域）**：

**Orchard-SWE**（Qwen3.5-35B-A3B MoE）：

- 107K 蒸馏轨迹（MiniMax-M2.5 + Qwen3.5-397B，OpenHands + mini-swe-agent harness）。
- **保留 unresolved 轨迹**（多数 prior work 只留 success）。
- **Credit-assignment SFT**：retrospective value estimation 从失败轨迹提取 productive rise segments。
- **Balanced Adaptive Rollout (BAR)**：在线组装 reward-balanced 轨迹组做 sparse-reward RL。
- 论文 v3 报告：Qwen3.5-35B-A3B 经 RPR-based RL 达 **69.7%** SWE-bench Verified，加入 value-model reranking 后达 **73.0%**。这两个数字对应不同推理配置，不能写成同一训练阶段的自然递进。

**Orchard-GUI**（Qwen3-VL-4B-Thinking）：

- 0.4K SFT + 2.2K RL on live websites；generic ReAct browser harness。
- WebVoyager **74.1%** / Online-Mind2Web **67.0%** / DeepShop **64.0%** → 平均 **68.4%**。
- **超越 235B teacher**；长 horizon benchmark 增益最大。

**Orchard-Claw**（Qwen3-30B-A3B-Thinking）：

- 0.2K Opus 合成任务；SFT+RL across two harnesses。
- ClawEval **59.6% pass@3**（31.7% pass³）；换 ZeroClaw 推理 → **73.9% pass@3**（+14.3）。

### 1.1. 系统吞吐、模型结果与数据规模

系统指标、模型成功率和成本估算属于三类证据，不能在没有配置说明时互相替代。

下列数字均对应论文 v3 的特定模型、Harness、任务集与基础设施设置。

**Orchard Env 系统工程指标**：

| 指标 | Orchard Env | 对照 |
|---|---:|---|
| 平均 exec 延迟 | **0.28 s** | E2B 0.747 s（2.7×慢）、Modal 2.046 s（7.3×慢） |
| 1000 并行 sandbox | **100% 成功**，26 s 端到端，~154 cmd/s | — |
| 128 sandbox × 240 h 成本 | **$673 spot** / $3,362 on-demand | Daytona/E2B ~$7,078（0.10× spot） |

**Terminal-Bench 2.0 无回归**（Docker → Orchard Env）：GPT-4.1 34.1→35.1，MiniMax-M2.5 52.6→54.4，Qwen3-8B 7.0→8.8——Env 是 drop-in substrate。

**Generalization 主题**（论文核心 claim）：

- Orchard-SWE 在**训练未见 harness** Kimi-CLI 上仍 45.0% Verified / 20.1% Terminal-Bench 2.0（OpenSWE-32B → 3.6% / 0.0%）。
- Orchard-Claw 换强 harness 后 pass³ +9.3 / pass@3 +14.3。
- Orchard-GUI 4B  beat 235B teacher on 2/3 benchmarks。

**Dataset（HuggingFace microsoft/Orchard）**：

- `swe`：107,185 rollouts，19,287 unique instances，2,788 repos，均 47.5 turns/trajectory。
- `gui`：3,070 judge-verified per-step rollouts，409 WebVoyager-style tasks，含 screenshot multimodal。

**Roadmap**：Stateful sandboxes（pause/resume/branching）——从轨迹末端的 scalar reward 转向 per-turn Monte-Carlo credit assignment。论文给出明确动机：SWE 轨迹均 47.5 turns，却只有一个 outcome reward——**branching 从同一 snapshot fork 多条 continuation** 可直接 Monte-Carlo 估计 state value，并把 per-turn credit assignment 从「事后推断」变成「可测量」；prefix sharing 使 tree-structured search 比 flat rollout 便宜。

**Trainer 层（slime fork）**：Orchard 不绑定单一 RL 算法，而是在 `trainer/slime/examples/orchard/` 提供 rollout glue；`ORCHARD_CHANGES.md` 追踪相对上游 slime 的 fork diff——意味着 Recipe 层可换算法（on-policy distillation、rubric process reward、value-model reranking 均在 Orchard-SWE 出现），Env 层保持稳定。

**OpenWebRL（姊妹论文，2026-06）**：在同一 Env 上把 Orchard-GUI 扩展为 **live website 在线 RL**——fault-tolerant browser env（navigation retry、timeout、structured failure attribution），OpenWebRL-4B 在 Online-Mind2Web **67.0%**、DeepShop **64.0%**，与 Orchard-GUI 数字互证。OpenWebRL 是 GUI Recipe 的在线延伸。

**集群门槛与实验边界**

这些限制把已经测量的系统能力与尚待验证的外推结论分开。

部署侧需要 AKS、EKS、GKE 或自建 Kubernetes 集群，对个人开发者仍有门槛；训练侧虽然把 Env 抽成服务，RL 配方仍依赖 slime fork 与特定 rollout 代码。SWE 的信用分配来自事后估计，不是环境原生逐步奖励，branching sandbox 在论文中仍属路线图。

实验侧的 Claw 与 GUI 数据规模有限，稳定性和 scaling 行为没有被充分覆盖。73.0% SWE 结果包含 value-model reranking，不能代表单次策略输出；跨 Harness 的收益也只在论文给出的组合上成立。与后续 OpenWebRL、OpenForge RL 的关系应按具体新增机制理解，不能把整个系列的能力提前归给 Orchard 本体。

**二、环境生命周期与状态记录**

Orchard 把 Recipe、Env 与 trainer 分层，核心是让环境生命周期和高频执行路径成为稳定服务。系统拆解必须同时说明控制面和数据面。

可复现轨迹必须记录环境状态。文件、进程、网络和资源元数据都可能改变后续动作，单独保存聊天消息无法重建这些变化。

**系统拆解**

控制面负责创建和删除，数据面负责高频命令与文件操作，二者的延迟和故障模式不同。

分层的意义是让 Recipe 依赖稳定 API，同时允许底层集群与上层训练算法分别演进。

```
┌─────────────────────────────────────────────────────────┐
│  Recipes（研究层，可替换）                                  │
│  Orchard-SWE │ Orchard-GUI │ Orchard-Claw │ OpenForge…  │
└──────────────────────────┬──────────────────────────────┘
                           │ REST / SDK
┌──────────────────────────▼──────────────────────────────┐
│  Orchard Env（Foundation — 薄环境服务）                    │
│  SandboxClient → Orchestrator → Pod + In-pod Agent       │
│  create / exec / files / patch / delete / network policy │
└──────────────────────────┬──────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────┐
│  Kubernetes 集群 + 任意任务镜像 + 预装 harness             │
└─────────────────────────────────────────────────────────┘
```

Quick start：

```python
from orchard_env import SandboxClient

with SandboxClient() as client:
    with client.create_sandbox("python:3.11-slim") as sandbox:
        print(sandbox.exec("echo 'Hello, Orchard!'").stdout)
```

Env **不假设**上层是 trainer、inference backend 还是 task domain——同一 API 可用于 distillation rollout、on-policy RL、evaluation 三阶段。

### 1.2. 环境服务究竟保存什么状态

把一次 rollout 写成状态机更容易看出 Orchard Env 的职责。沙箱在时刻 $t$ 的状态记为

$$
E_t=(I,F_t,P_t,N_t,M_t),
$$

$I$ 是不可变的基础镜像与任务初始材料，$F_t$ 是文件系统，$P_t$ 是进程集合，$N_t$ 是网络策略与连接状态，$M_t$ 是资源限制和生命周期元数据。Agent 动作 $a_t$ 通过环境执行函数产生新状态与观测：

$$
(E_{t+1},o_{t+1})=T(E_t,a_t).
$$

Harness 决定下一步调用什么工具，trainer 决定怎样用整条轨迹更新策略，Orchard Env 负责让同一个动作在隔离环境中执行并返回结构化结果。这个边界很重要：环境可以确认命令退出码和文件变化，却不知道一段补丁是否真正解决用户问题；验证器可以运行隐藏测试形成奖励，但不应被硬编码进通用 exec API。

创建和删除 Pod 属于控制平面冷路径，命令执行与文件 I/O 属于 rollout 的高频数据路径。若每条命令都经过 Kubernetes API server 的 exec 通道，一条几十轮轨迹会反复支付连接与编排开销。Orchard 把 in-pod agent 注入容器，让 orchestrator 直接访问 Pod IP，正是在稳定服务边界下缩短热路径。性能收益来自系统路径，不表示模型动作更少或任务更容易。

**一个五步轨迹**

以软件修复为例，初始镜像包含仓库、依赖与失败测试。Agent 依次执行：读取错误日志、定位文件、写补丁、运行局部测试、运行完整测试。环境需要记录每个动作前后的工作目录、命令、退出码、stdout/stderr、超时、文件 diff 和资源消耗。最终 reward 为 1 时，不能反推五步都正确：第二步可能走了弯路，第三步可能引入临时错误，第四步又把它修掉。

若最终测试失败，失败轨迹仍包含可复用片段。比如局部测试从 5 个失败降到 1 个，说明前几步产生了有效进度。Credit-assignment SFT 的问题就是从整条未解决轨迹中识别 productive segments，再把它们转成监督，而不是把所有失败 token 一起丢掉。

**三、训练信号与轨迹可移植性**

长轨迹通常只有稀疏终局奖励，失败样本中仍可能包含有效进度。训练方法需要从轨迹中提取比较信号，同时保留环境转移。

轨迹能否跨 Harness 使用，取决于字段脱离某个 prompt 模板后是否仍可解释。信用分配、轨迹 schema 与受控迁移实验共同检验这种可迁移性。

## 2. 稀疏奖励与信用分配手算

设一条轨迹有四个决策，最终隐藏测试给 $R=1$ 或 $0$。最粗糙的 Monte Carlo 回报把同一个 $R$ 分给每个动作：

$$
G_t=R,\qquad t=1,\ldots,4.
$$

成功轨迹中所有动作都被正向强化，包括无效搜索；失败轨迹中真正有用的前置修改也得不到正信号。如果同一中间状态 $s_2$ 能够分叉采样四条 continuation，最终奖励为 $(1,1,0,0)$，则状态价值可估为

$$
\hat V(s_2)=\frac{1+1+0+0}{4}=0.5.
$$

再比较某个动作 $a$ 后分支均值 0.75 与状态均值 0.5，可以得到近似优势 $\hat A(s_2,a)=0.25$。这比从单条终局奖励猜测第二步贡献更直接。代价是要从相同文件、进程和环境状态 fork 多次；因此 pause、resume 与 branching 属于环境能力，而不仅是 trainer 算法。

当前路线图中的 stateful sandbox 正在补这一层。实现时 checkpoint 不能只复制文件：后台进程、端口、环境变量、工作目录、临时挂载和随机状态都会影响 continuation。若恢复后的 $E_t$ 与原状态不等价，分支回报差异可能来自 checkpoint 漂移，而非 Agent 动作。

BAR 一类 balanced rollout 处理的是另一处稀疏性。假设同一任务采样 8 条轨迹，奖励全为 0，组内策略梯度没有可区分信号；若全为 1，也难以判断哪些行为更好。通过调整任务与 rollout，使 batch 中保留成功和失败样本，可以提高比较信号。但重采样会改变训练分布，必须记录每个任务的原始成功概率和被采样概率，不能把平衡后的训练分布当成真实部署频率。

**可移植轨迹需要什么字段**

“同一环境可以跨 Harness 复用”要求轨迹脱离某个 prompt 模板仍可解释。一条最小轨迹应包含：环境镜像与任务版本、初始状态标识、模型与 Harness 版本、每步原始动作、工具 schema、观测、文件 diff、验证器版本、奖励分项、终止原因和资源统计。只保存 OpenAI messages 会丢失环境转移；只保存 shell 历史又无法重建模型当时看到的上下文。

失败也要分类。模型选择了错误命令是 policy failure；命令正确但网站超时是 environment failure；验证器误判是 reward failure；Harness 丢失截图或截断 stdout 是 observation failure。将它们都写成 reward=0，会让训练器把基础设施噪声当作模型行为惩罚。Orchard 的薄环境边界提供了统一观测点，但分类规则仍要由 Recipe 明确。

轨迹版本还要处理数据泄漏。同一仓库的相似 issue 若同时进入训练和评测，模型可能复用补丁模式；GUI live site 的内容随时间变化，同一个 task ID 也可能不再等价。数据集应保存仓库 commit、镜像哈希、网站快照或执行时间，并按仓库、任务模板与时间进行分割。

**怎样验证 Harness-agnostic**

“支持多 Harness”只说明它们能在 Pod 中启动；“训练具有 Harness 泛化”还需要受控实验。固定同一 policy checkpoint、任务实例、环境镜像、工具权限与预算，分别使用训练时 Harness、未见 Harness 和最小工具循环。记录最终成功、工具调用、token、墙钟、环境错误和轨迹长度。

然后交换训练与部署组合：在 Harness A 收集数据并训练，分别在 A、B 评测；再用 Harness B 数据训练，分别在 A、B 评测。若所有模型在 B 上都更好，收益可能来自 B 本身更强；只有跨组合矩阵才能区分 policy 泛化、Harness 增益和二者交互。

环境层还要做无回归测试。相同动作序列在 Docker direct 与 Orchard Env 中执行，最终文件哈希、退出码和测试结果应一致；有差异时检查网络、用户权限、文件系统、时钟与资源限制。论文报告的 Terminal-Bench 对照支持其环境可作为替代底座，但新的镜像、集群策略和版本仍需持续回归。

系统扩展性则用并发曲线报告：沙箱创建成功率、P50/P95 创建时间、命令延迟、吞吐、Redis 与 API server 负载、清理失败和资源泄漏。单次平均 exec 延迟不能证明千并发稳定，也不能直接推算长 RL 任务的总成本。

**四、论文结果与信用分配边界**

Orchard 在 Long-Horizon 栈中提供执行环境和轨迹底座；部署期任务状态由上层 Harness 管理。三条 Recipe 的结果也来自不同模型与配置。

v3 的实验数字需要与终局奖励、状态分叉和故障归因一起理解，同时区分当前已经完成的能力与仓库路线图。

### 2.1. 它在 Long-Horizon 栈中的位置

Orchard 解决“在哪里可靠地产生动作—观测轨迹”，Recipe 解决“怎样从轨迹学习”，Harness 解决“部署时怎样选择动作并维护任务状态”。三层共享一些名词，权威状态却不同。环境中的文件与进程是事实源；Harness 的计划是暂定控制状态；trainer 中的 advantage 是学习估计量。混成一个 JSON 会让恢复和审计都失去边界。

对于 Long-Horizon 研究，Orchard 最关键的价值是把可执行环境变成稳定服务，单个 SWE 或 GUI 分数只是这套底座的一次结果。只有环境能够复现、分叉和验证，长轨迹中的进度、错误传播与恢复才有可测对象。未来 stateful sandbox 真正落地后，还要验证 checkpoint 完整性、分支隔离和成本；路线图本身不能当作已经具备的能力。

Recipe 的共同流程包含五个环节：在 Env 内采集 teacher 与 student 轨迹，保留成功和失败样本，做 SFT 初始化，用稀疏或过程奖励训练，并在训练未见的 Harness、语言或任务上验证迁移。这里容易混淆三个层次：Env 能启动多个 Harness，说明接口兼容；模型在多个 Harness 数据上训练，说明训练覆盖；模型换到未见 Harness 仍提高，才是策略迁移证据。

**v3 实验数字应怎样读取**

[Orchard v3](https://arxiv.org/abs/2605.15040)于 2026 年 7 月 30 日修订。摘要中的三个主结果来自三条不同 Recipe，不能拼成一个统一模型。Orchard-SWE 使用 Qwen3.5-35B-A3B，RPR-based RL 在 SWE-bench Verified 达 69.7%，value-model reranking 达 73.0%；Orchard-GUI 使用 4B 视觉语言模型，以 0.4K 蒸馏轨迹和 2.2K 开放任务训练，在 WebVoyager、Online-Mind2Web 与 DeepShop 的平均成功率为 68.4%；Orchard-Claw 用 0.2K 合成任务训练，Claw-Eval 为 59.6% pass@3，搭配 ZeroClaw Harness 时为 73.9%。

73.0% 比 69.7% 高 3.3 个百分点，但增加的是推理期 value-model reranking，不应表述成「RL 又训练到 73.0%」。同理，Claw 从 59.6% 到 73.9% 同时更换 Harness，差值 14.3 个百分点包含 Harness 效应，不能全归给模型参数。论文用这些对照支持环境与轨迹可跨 Harness 使用，不能推出任意 Harness 互换都会提升。

GUI 三项平均值可复算：

$$
\bar A=\frac{74.1+67.0+64.0}{3}=68.37\%\approx68.4\%.
\tag{3}
$$

这个平均把三个 benchmark 等权处理；它没有按样本量加权，也不表示每类网站都有 68.4% 成功率。报告平均数时应同时保留三列，避免一个任务的优势遮住另一个任务的弱点。

论文还报告环境系统指标：平均 exec 延迟 0.28 秒，对照 E2B 0.747 秒、Modal 2.046 秒；1000 个并行 sandbox 的实验报告 100% 成功、26 秒端到端和约 154 command/s。成本表以 128 个 sandbox 连续 240 小时为场景，Orchard spot 估算为 673 美元、on-demand 为 3362 美元，对照托管方案约 7078 美元。它们是特定云定价、实例和负载下的测量，不是跨地区长期不变的价格。成本结论应复现实例类型、折扣和利用率后再采用。

若按表中数字计算 spot 相对 7078 美元的比例，

$$
\frac{673}{7078}\approx0.095,
\tag{4}
$$

约为 0.10 倍；on-demand 比例则为 $3362/7078\approx0.475$。因此「约十分之一」只适用于 spot 行，不适用于 Orchard 所有部署方式。

**信用分配为何需要环境快照**

SWE 轨迹平均 47.5 turns，却常只有终局 reward。将终局 $R$ 分给所有动作会奖励成功轨迹中的弯路，也会抹掉失败轨迹里的有效修改。若从同一状态 $s_t$ 分叉 $n$ 条 continuation，状态价值可以用

$$
\hat V(s_t)=\frac1n\sum_{i=1}^{n}R_i
\tag{5}
$$

估计。假设四个分支奖励为 $(1,1,0,0)$，则 $\hat V(s_t)=0.5$；某动作后的四个分支为 $(1,1,1,0)$，动作条件价值为 0.75，近似优势为 0.25。这个估计仍有方差，却比单条轨迹事后猜测哪一步有用更直接。

分叉成立的前提是恢复状态等价。设环境快照

$$
K_t=(F_t,P_t,N_t,W_t,R_t),
\tag{6}
$$

$F_t$ 是文件系统，$P_t$ 是进程，$N_t$ 是网络状态，$W_t$ 是工作目录与环境变量，$R_t$ 是随机状态。只复制文件而遗漏数据库进程、监听端口或随机种子，两条 continuation 的奖励差异就不只来自动作。论文把 stateful sandbox 的 pause、resume、branching 列为路线图；截至 v3，这不能写成 Orchard Env 已提供并验证的现成功能。

BAR 处理的是另一种稀疏性。若同一任务的 rollout 全为 0 或全为 1，组内比较几乎没有区分信号；平衡成功和失败轨迹可增加梯度信息。但重采样改变训练分布。设原任务采样概率为 $p(x)$，平衡后为 $q(x)$，若要估计原分布期望，需要重要性权重 $p(x)/q(x)$。训练可以选择不校正以追求学习效率，评测却必须回到未平衡分布，否则会高估部署成功率。

### 2.2. 可移植轨迹与故障归因

一条轨迹若只保存消息数组，换 Harness 后往往无法解释。最低字段包括：镜像与任务版本、初始状态、模型和 Harness 版本、工具 schema、每步动作与原始观测、退出码、文件 diff、验证器版本、奖励分项、终止原因和资源统计。涉及网页时还要保存时间与关键响应，涉及仓库时保存 commit；否则相同 task ID 可能已不是相同环境。

失败至少分成四类。Policy failure 是模型选择错误动作；environment failure 是正确动作遇到基础设施故障；observation failure 是 Harness 截断或丢失结果；reward failure 是 verifier 误判。若四类都记为 reward=0，训练器会把集群超时当作模型错误学习。Orchard 的薄服务边界提供统一记录点，但分类标签仍要由 Recipe 和 verifier 共同给出。

验证「Harness-agnostic」要做交叉矩阵。固定模型 checkpoint、任务、镜像、权限与预算，在 A、B 两种 Harness 上评测；再分别用 A 与 B 的数据训练，得到训练×部署的四格结果。若所有模型在 B 上都更高，可能只是 B 更强；若 A 数据训练的模型在未见 B 上仍比基线提高，才支持策略迁移。环境接口能运行 A 与 B 只是必要条件，不是泛化结论。

Orchard 在 Long-Horizon 栈中提供可执行、可扩展的轨迹底座；部署期目标版本、事实审计与恢复仍属于 Harness。它的论文结果表明同一 Env 可以支撑三种 Recipe，也展示失败轨迹和跨 Harness 对照的价值。论文没有证明薄环境自动带来长期一致性，更没有证明路线图中的 branching 已落地。把这条边界写明，才能让环境贡献与模型能力各自接受正确的检验。

**五、环境验收、安全与复现**

迁移到新环境以后，需要先验证动作序列与终态是否等价，再讨论吞吐与成本。微基准不能直接替代完整 rollout。

安全、资源回收和版本锁定同样属于可复现性，环境等价性、生命周期和论文复现边界都应进入验收流程。

**环境等价性怎样验收**

把任务从 Docker direct 搬到 Orchard Env 后，成功率相近不等于环境完全等价。应先固定一组动作序列，在两边比较命令退出码、stdout/stderr、最终文件哈希、用户与权限、网络解析、时钟、资源上限和后台进程。对动作 $a_{1:T}$，可把环境指纹写成

$$
\Phi(E_T)=
(h(F_T),h(P_T),h(N_T),u_T,r_T),
\tag{7}
$$

$h(F_T)$ 是相关文件哈希，$h(P_T)$ 是进程及端口摘要，$h(N_T)$ 是网络策略摘要，$u_T$ 与 $r_T$ 是用户权限和资源限制。两边任务 verifier 一致但 $\Phi$ 不同，仍应调查差异，因为后续更长轨迹可能放大它。

论文报告 Terminal-Bench 2.0 从 Docker 到 Orchard Env 没有回归：GPT-4.1 为 34.1→35.1，MiniMax-M2.5 为 52.6→54.4，Qwen3-8B 为 7.0→8.8。这里的小幅上升不应解释为 Env 提升模型能力；有限样本、运行随机性与基础设施差异都可能产生波动。它支持的是「迁移未显示系统性下降」，不是「换环境会涨分」。

并发实验要分控制面和数据面。创建、删除沙箱经过 Kubernetes API，是低频冷路径；exec、文件 I/O 与健康检查直连 Pod 内 agent，是 rollout 高频热路径。总任务时间近似为

$$
T_{\mathrm{run}}=T_{\mathrm{create}}+
\sum_{t=1}^{n}(T_{\mathrm{model},t}+T_{\mathrm{exec},t})+
T_{\mathrm{verify}}+T_{\mathrm{delete}}.
\tag{8}
$$

平均 exec 从 0.747 秒降到 0.28 秒，若一条轨迹有 100 次串行命令且其他项不变，仅该项理论上少约 46.7 秒；真实收益还受模型生成、并发排队和长命令执行支配。单命令微基准不能直接替代完整 rollout 吞吐。

**安全与生命周期不是附加项**

训练 Agent 会执行模型生成的命令，隔离边界必须默认不信任轨迹。Orchard 使用 NetworkPolicy 做默认拒绝出站、API key 验证、TTL cleanup、Redis 状态与分布式锁。这些机制各自处理不同风险：网络策略限制数据外传，TTL 回收遗留资源，锁避免多副本同时修改同一 sandbox。任何一项存在都不能替代其余项。

删除沙箱还要验证是否真正回收。应记录创建数、正常删除数、TTL 删除数、删除失败数和残留资源，并满足

$$
N_{\mathrm{create}}=
N_{\mathrm{delete}}+N_{\mathrm{ttl}}+N_{\mathrm{live}}+N_{\mathrm{leak}}.
\tag{9}
$$

长时间压测中 $N_{\mathrm{leak}}$ 必须可见，不能只报告成功创建率。网络策略也应以实际拒绝测试验收，包括 DNS、元数据服务、集群内其他 Pod 和公网出口；配置文件看起来正确不等于数据面真的阻断。

运行时注入 in-pod agent 使任意镜像不必预装控制服务，但也扩大供应链边界。注入产物应固定版本与哈希，客户端、orchestrator 和 pod agent 的协议版本要协商；否则滚动升级时，同一 REST 请求可能在不同 Pod 得到不同语义。轨迹必须记录这三个版本，才能复现一次失败。

## 3. 从数据到结论的检查表

v1、v2 与 v3 的训练方法和主数字不同，本文采用 2026 年 7 月 30 日的 v3；67.5% 等早期结果必须标明版本。结果还要区分 policy、Harness 与 reranker，组合系统的分数不能全部归给基础模型。benchmark、样本数、预算和 pass 指标共同构成数字口径，`pass@3` 与单次成功率不是同一量。

环境结果要附实例、区域、spot/on-demand、并发、持续时间和失败处理；训练结果要附 backbone、数据规模、Harness、reward 与推理配置；迁移结果要给训练×部署 Harness 矩阵。路线图项目单列为「尚未验证」，特别是 stateful pause/resume/branching。按这套口径，Orchard 的可靠结论是：一个薄、可自托管的 Kubernetes 环境服务能够复用于三类 Agentic Modeling Recipe，并在论文设置下给出有竞争力的结果；更广泛的成本、泛化与状态分叉能力仍需在各自环境中复现。

复现时还要锁定官方仓库 commit，而不能只写 `main`。论文摘要、代码默认配置和数据集卡可能在不同日期更新，三者不一致时，以所复现实验对应的版本为准，并在结果表列出差异。若数据集只提供轨迹而缺少原始环境镜像，就只能复现离线训练或统计，不能声称重现了完整 rollout。相反，环境能够启动但缺少同版模型与 reward 配置，也只能验证系统工程部分。把「论文数字复现」「环境部署复现」「训练路线复现」分开，失败时才知道缺的是哪一层证据。

**六、一次 Rollout 的资源构成**

Orchard Env 把 rollout 环境放进 Kubernetes Pod，模型推理与 trainer 可以在另一组节点。一次 episode 的资源不只包含 GPU token，还包含 sandbox 冷启动、CPU/内存驻留、镜像拉取、网络与验证器。设 episode $i$ 的总成本为：

$$
C_i=C_{model,i}+C_{sandbox,i}+C_{storage,i}+C_{network,i}+C_{verify,i}.
\tag{10}
$$

Sandbox 成本可进一步按 Pod 存活时间估算。若分配 $c_i$ 个 vCPU、$m_i$ GiB 内存，单价分别为 $p_c,p_m$，持续 $t_i$ 小时，则：

$$
C_{sandbox,i}=t_i(c_ip_c+m_ip_m)+C_{startup,i}.
\tag{11}
$$

Spot 实例会降低单价，也会增加抢占与恢复成本。报告「比托管 sandbox 便宜」时，需要同时给区域、实例类型、spot 比例、失败重试与资源利用率；脱离这些条件的倍数很快会过期。

启动开销在短任务中占比很高，在长任务中被摊薄。假设创建 Pod 需要 12 秒，100 次 exec 每次 0.28 秒，工具纯调用时间为 28 秒；仅创建就占两者合计的 30%。若 episode 只有 5 次 exec，创建几乎支配环境时间。热池可以减少冷启动，却需要为闲置 Pod 支付资源，并加强租户间清理。

```text
任务入队
  ↓ create Pod / 注入 harness payload
环境就绪
  ↓ model call ↔ exec/file/screenshot/action
轨迹完成
  ↓ 独立 verifier
奖励与事件日志
  ↓ delete Pod / TTL 兜底
资源回收
```

每一段都应产生状态事件。Pod 创建成功却未通过 health check，属于 environment error；Harness 退出而 verifier 失败，属于 task failure；Verifier 自身超时则单列 verifier error。全都压成 reward 0，会让 trainer 把基础设施噪声当作策略失败。

**并发、排队与 GPU 空转**

Rollout 中模型生成占 GPU，工具执行与网页等待主要占 CPU/网络。并发 sandbox 的目的之一，是让其他 episode 在某条轨迹等待环境时继续请求模型。设单条 episode 的模型占用比例为 $\rho=T_{model}/T_{run}$，理想情况下让推理服务持续有请求，大致需要不少于 $1/\rho$ 条交错轨迹。

若 $T_{model}=30s,T_{run}=150s$，则 $\rho=0.2$，至少约 5 条完全错开的轨迹才能覆盖等待空隙。现实还有动态批处理、长短轨迹和 Proxy 排队，所需并发更高。并发上升后，Kubernetes 调度、镜像拉取、Redis 锁和网络出口会成为新瓶颈。

应该同时监控 GPU token 吞吐、Proxy 队列深度、Pod 启动 P50/P99、exec P50/P99、有效 episode 比例和 verifier 延迟。GPU 利用率高但有效 episode 比例低，说明系统正在高效生成无用轨迹；Pod 很多但 Proxy 队列为空，可能是环境或 Harness 阻塞。

### 3.1. 七、环境状态的数据流

官方架构文档说明，Orchestrator 只通过 Kubernetes API 处理 Pod create/delete；exec、文件 I/O 与 health check 直接访问 Pod IP，避开 Kubernetes API 与 WebSocket 的热路径开销。Harness payload 以只读方式注入，在 Kubernetes 1.33 及以上可使用 `image:` volume，让 kubelet 每节点拉取一次。

一次 exec 的状态流可以表示为：

$$
x_t=(sandbox\_id,command,timeout,env,workdir),
\tag{12}
$$

Pod 内 agent 返回：

$$
o_t=(exit\_code,stdout,stderr,timestamps,resource\_usage).
\tag{13}
$$

控制面随后把 $o_t$ 写入轨迹，并由下一次模型调用消费。`exit_code=0` 只说明进程正常结束，任务状态仍需 verifier 判断；超时也不说明命令没有产生副作用，恢复时应先读取文件和进程状态。

文件 I/O、apply patch、screenshot 与 action 都要绑定 sandbox ID。分布式锁避免两个 orchestrator 副本同时处理同一生命周期操作，却无法阻止两个 Agent 在同一工作区产生语义冲突；上层调度仍需隔离任务或声明共享写入规则。

**环境等价性的逐层检查**

把 Docker benchmark 迁到 Orchard Env 时，可以逐层验收：镜像和依赖一致；初始文件哈希一致；用户、权限、工作目录与环境变量一致；网络策略满足任务需要；同一参考解得到相同 verifier 结果；已知错误解稳定失败。每层通过后再运行模型，避免用 Agent 分数承担环境调试。

随机性也要记录。数据库生成数据、游戏环境和网页时钟可能让两个 sandbox 从不同初态开始。种子只能控制显式随机源，外部 API 与实时网站仍会漂移。对这类任务，应保存关键初态摘要，或在同一时间窗口交错运行对照系统。

**八、Stateful Sandbox 路线图的边界**

截至 2026 年 10 月，官方仓库仍把 pause、resume、branching 与 prefix sharing 放在 Roadmap，当前 sandbox 生命周期保持线性：创建、驱动若干轮、销毁。现有代码与论文结果已经开源，路线图能力却不能写成已交付功能。

这些能力之所以重要，与 credit assignment 直接相关。若能在第 $t$ 步保存完整状态 $s_t$，从同一快照分叉 $K$ 条 continuation，就可以估计某动作后的状态价值：

$$
\hat V(s_t)=\frac1K\sum_{k=1}^{K}R(\tau_k\mid s_t).
\tag{14}
$$

当前线性环境要估计同一个量，只能把前缀重新执行 $K$ 次。假设前缀成本为 $C_p$，每条 continuation 为 $C_c$，无快照成本是 $K(C_p+C_c)$；共享前缀后约为 $C_p+KC_c+C_{snapshot}$。前缀越长，节省越明显。

完整快照比复制文件困难。进程内存、监听端口、数据库缓冲、网络连接和随机状态都要恢复；外部网站或云资源无法随 Pod 一起回滚。Branching 若复用同一外部账户，多个分支还会互相污染。因而路线图中的「完整状态」必须说明覆盖范围，不能用文件系统 snapshot 代表全部环境。

Pause/resume 也需要版本兼容。恢复时 Pod agent、Harness、镜像和 verifier 若已升级，旧状态可能无法解释。Checkpoint manifest 至少记录镜像摘要、协议版本、资源 ID 与外部依赖，加载前逐项核对。

## 4. 九、数据集规模怎样读

官方仓库当前列出 `swe` 与 `gui` 两个数据子集。SWE 部分含 107,185 条多轮 rollout，覆盖 19,287 个任务实例、2,788 个仓库，其中 74,649 条 resolved、32,536 条 unresolved，平均每条 47.5 turn；GUI 部分含 3,070 条经 judge 验证的成功逐步轨迹，来自 409 个 WebVoyager 风格任务。

轨迹数不等于独立任务数。SWE 中同一任务可能有多条 rollout，训练/验证划分若只按轨迹随机切分，会让同一 issue 或仓库跨集合泄漏。应按任务、仓库和时间做去重与分组，并公开分割规则。GUI 数据只包含 judge-verified successful rollouts，适合蒸馏成功行为，却不能单独提供完整失败分布。

Resolved/unresolved 也不直接等于每一步的正负标签。未解决轨迹中可能含有有价值的定位、测试和局部修复，Orchard-SWE 的 credit-assignment SFT 正是要回收这些 productive segments。片段选择若依赖事后 value estimate，应记录估计模型和阈值，避免把同一条轨迹在不同版本下切出不同训练集却仍使用同一名称。

从数据到模型结果还隔着 backbone、Harness、reward 与预算。107K 轨迹说明数据规模与来源，69.7% 或 73.0% 则属于具体 Recipe 和 reranking 配置。把两者写在同一段时仍要保留因果边界，数据量本身不保证结果。

**十、队列、重试与故障归因**

大规模 rollout 不会同时结束。软件任务可能跑测试几十分钟，GUI 任务也会被网页加载和限流拖慢。若 trainer 等固定 batch 的全部 episode 返回，最慢轨迹成为同步屏障；若到时间就丢弃，训练集又会偏向短任务。Orchard Env 解决环境启动和交互，trainer 仍需定义 batch 完成与过期策略。

一条队列记录至少包含 `task_id`、`attempt_id`、`policy_version`、`sandbox_id`、优先级、租约到期时间和重试次数。Worker 领取任务后续租；进程崩溃且租约过期，任务回到队列。重试沿用相同 `task_id`，新建 `attempt_id`，这样可以区分一个任务的多次基础设施尝试。

幂等性覆盖控制面和任务面。重复 create 请求不应创建两个活跃 Pod，重复 delete 对已删除对象应安全返回；任务内部的 shell/API 副作用则由 Harness 与环境处理。控制面幂等不能阻止 Agent 重复发送邮件或重复提交远端资源。

故障归因可以用一棵简短决策树：Sandbox 未 ready，归为 startup；交互中 Pod 消失，归为 environment runtime；模型端点超时，归为 inference；Harness 正常结束但 verifier 未通过，归为 task failure；Verifier 自身异常，归为 verifier。每类错误分别统计，只有 task failure 与明确由 policy 引发的安全违规进入负奖励。

**重试对成功率的影响**

设一次基础设施成功概率为 $q$，在基础设施正常条件下任务成功概率为 $p$。不重试时观测成功率为 $pq$。若只对基础设施失败最多重试 $r$ 次，至少一次获得有效环境的概率为：

$$
q_r=1-(1-q)^{r+1},
\tag{15}
$$

观测成功率变为 $pq_r$。取 $p=0.4,q=0.9,r=1$，成功率从 $0.36$ 升到 $0.396$。这部分提升来自基础设施恢复，不代表 policy 变强。排行榜若允许不同重试策略，需要同时报告原始 attempt 与去除环境失败后的 conditional success。

任务失败不应无条件自动重跑。多次采样属于 pass@k，消耗更多模型和环境预算；把它混进 infra retry 会虚增单次可靠性。系统要先依据错误类别决定重启环境、继续 checkpoint，还是开始新的 policy sample。

**十一、可观测性与清理验收**

每条 episode 应能从 task 追到 Pod、Harness、模型调用、工具事件、verifier 和删除记录。核心 trace ID 贯穿这些组件，时间戳使用统一时钟；否则 exec P99 上升时，很难判断延迟发生在客户端、orchestrator、Pod agent 还是命令本身。

清理指标要按 namespace、节点与镜像分层。残留 Pod 为零，不代表 PersistentVolume、Secret、Service 和 NetworkPolicy 都已回收。TTL controller 是兜底，正常路径仍应主动删除；若 TTL 删除比例持续升高，说明生命周期代码在漏资源。

安全测试也进入持续集成。准备一个恶意任务尝试访问云元数据、集群 API、其他 Pod、未授权公网域和宿主机路径，预期全部失败；再准备允许域与正常文件操作，确认策略没有把合法任务一并阻断。NetworkPolicy 规则存在只是配置证据，实际连接结果才证明隔离生效。

仓库已经公开环境代码、测试与贡献说明，部署者可以在自己的 Kubernetes 版本上重跑测试矩阵。Kubernetes 1.33 的 `image:` volume 优化属于条件能力，旧集群会走其他 payload 交付路径；性能报告应写明集群版本，不能把新路径数字默认外推到所有部署。

### 4.1. 参考资料

**十二、环境服务的语义契约**

Orchard Env 的价值不只在于把容器创建封装成 API，更在于给上层 Recipe 一个稳定的环境语义。若 `exec`、文件读写和生命周期在版本之间悄悄变化，同一训练脚本会得到不同轨迹，环境便无法成为公共底座。可以把接口契约分成请求语义、执行语义、返回语义与故障语义四层。

请求语义规定命令、工作目录、环境变量、超时和用户身份怎样解释。空工作目录是回到镜像默认目录，还是沿用上一次命令的位置？环境变量是覆盖、合并还是删除？命令字符串由 shell 解析，还是直接作为 argv 执行？这些差异会改变引号、通配符、管道与退出码。Agent 生成的动作必须在记录中保存原始请求和规范化后的执行请求，才能判断错误来自模型还是客户端转换。

执行语义规定每次调用处于怎样的进程与文件状态。若每条命令启动独立 shell，`cd` 和临时变量不会自然延续；若复用持久终端，前一条命令的后台任务、alias 和当前目录会影响下一条。二者都可以成立，但不能混用。对于训练数据，更稳妥的方式是把依赖状态显式放进请求：传递 `workdir`、需要的环境变量和会话标识。隐式终端状态越多，轨迹越难跨 Harness 重放。

返回语义至少包含 stdout、stderr、退出码、开始与结束时间、是否超时以及输出是否截断。只返回合并文本会丢失程序把诊断写到 stderr 的事实；只保留收尾阶段若干字符，又可能删除真正的根因。输出过大时可以保存完整内容到对象存储，在轨迹中保留摘要、长度、哈希和截断窗口。模型实际看到哪一部分仍要单独记录，因为完整日志适合审计，不能冒充当时的观察。

故障语义要区分「请求未执行」「执行后失败」「结果可能已产生但确认丢失」。例如客户端超时，不代表 Pod 内命令没有运行；网络在响应返回前断开，文件可能已经写入。若调度器把这类请求直接重试，非幂等动作会执行两次。API 可以为每次动作分配 `operation_id`，Pod agent 缓存短期结果；同一 ID 重放时返回原结果，新的尝试则使用新 ID。这样至少能把传输重试与策略再次行动分开。

文件接口也有一致性选择。覆盖写入若进程中途死亡，读者可能看到半文件；原子写入可以先写临时文件、同步后重命名。补丁接口要说明基线哈希，避免 Agent 根据旧内容生成的 patch 落到已变化文件上。读取大文件时，分页的偏移按字节还是字符计算，会影响多字节文本。训练模型若依赖一种行为，换环境后便可能失效，因此这些都属于可移植性的一部分。

环境 API 的向后兼容不能只看 HTTP schema。字段仍存在但默认超时从 60 秒变成 10 秒，或者 stdout 截断从尾部改为头部，都会改变策略观察。协议版本应覆盖行为变化，回归测试则用一组带已知副作用的动作检查最终状态。上层轨迹记录客户端、orchestrator 与 Pod agent 三个版本，才能在滚动升级期间定位不同副本的语义差异。

**线性一致性与生命周期竞争**

多副本 orchestrator 需要处理同一 sandbox 的并发请求。Redis 锁可以序列化创建和删除，却仍要定义 exec 与 delete 冲突时的结果。若删除先取得锁，后到的 exec 应明确返回 sandbox terminating；若 exec 已进入 Pod，删除是等待它完成、发送终止信号，还是立即销毁？不同选择会影响轨迹终止原因和外部副作用。

把 sandbox 生命周期写成状态机更清楚：

$$
\text{Requested}\rightarrow\text{Provisioning}\rightarrow\text{Ready}
\rightarrow\text{Terminating}\rightarrow\text{Deleted}.
$$

失败可以从 Provisioning 进入 Failed，从 Ready 因节点丢失进入 Lost。只有 Ready 接受普通执行；Terminating 拒绝新动作但允许查询最终状态；Deleted 的重复删除幂等成功。状态转换附带单调递增版本号，客户端提交动作时携带期望版本。若它基于旧状态操作，服务返回冲突，而非在新 Pod 或正在删除的 Pod 上猜测执行。

创建也会遇到「请求成功、响应丢失」。客户端再次创建时若使用相同 idempotency key，服务应返回已存在的 sandbox；若另建一个 Pod，两个环境都可能继续运行并消费资源。任务层再用 `attempt_id` 区分有意重试：同一幂等键代表恢复一次控制面调用，新 attempt 代表重新采样。把二者混在一起，会让成功率、成本与 pass@k 全部失真。

租约比永久所有权更适合大规模 worker。Worker 领取 sandbox 后定期续租，租约过期由回收器接管；但一次长命令可能超过续租周期。Pod agent 可以独立报告心跳，orchestrator 同时观察任务租约和环境活性。只因训练 worker 崩溃就立刻杀死 Pod，会丢掉可用于诊断的终态；无限保留又会泄漏资源。可设置短暂隔离窗口，保存事件与必要产物后再删除。

### 4.2. 热路径优化的排队模型

绕过 Kubernetes API 的 exec 热路径降低单次服务时间，也会改变系统可承载到达率。把 exec 请求近似看成到达率 $\lambda$、平均服务率 $\mu$ 的队列，利用率为 $\rho=\lambda/\mu$。即使平均服务时间很低，当 $\rho$ 接近一时，排队延迟仍会急剧上升。简单 M/M/1 近似给出

$$
W=\frac{1}{\mu-\lambda}.
$$

它不精确描述多 Pod 和长尾命令，却说明平均 0.28 秒不能保证 P99。短 `echo`、大型测试、文件传输共用连接池时，少数长请求会阻塞短请求。按操作类型设置独立并发限制，或让 exec 只建立控制连接、长命令在 Pod 内异步运行，可以减少头阻塞。

直连 Pod IP 还把部分可靠性责任从 Kubernetes API 转到服务自身。Pod 重建后 IP 变化，orchestrator 的缓存必须失效；网络策略刚更新时连接可能短暂失败；跨节点路由和服务网格也会增加尾延迟。每个请求应解析 sandbox 当前 generation 与 endpoint，响应再带 generation。若执行期间 Pod 被替换，客户端能识别这次结果属于旧实例，避免把新 Pod 的空状态接在旧轨迹后面。

文件传输与命令执行的负载形态不同。一个 500 MB 文件会长期占用带宽和内存，若与小 health check 共用同一 worker pool，健康检查超时可能触发错误删除。限流要同时考虑请求数、字节数和执行时间。每个 sandbox、用户和集群设置分层配额，既防止单个异常轨迹拖垮服务，也避免大量小请求绕过单次大小限制。

吞吐优化最终看有效轨迹，而非 API QPS。设一小时完成 $N$ 条 episode，其中环境错误 $N_e$、重建失败 $N_r$、验证异常 $N_v$，有效率为

$$
\eta=\frac{N-N_e-N_r-N_v}{N}.
$$

环境提速 20% 却让错误率从 2% 升到 15%，有效样本吞吐可能下降。压力测试应跑完整生命周期并执行真实大小分布，而非只对短命令打点；同时报告 QPS、P50/P99、有效率和每条有效轨迹成本。

**十三、状态等价与可恢复性**

Stateful sandbox 的核心难题是定义「恢复到同一状态」。文件哈希一致是必要条件之一，远远不够。两个环境的进程、端口、数据库事务、随机数生成器、内核资源和外部服务会话可能不同。对任务 $x$，更有用的定义是行为等价：对一组允许的后续动作 $\mathcal A_x$，恢复状态 $\tilde E$ 与原状态 $E$ 产生相同或容许误差内的观察分布。

$$
E\simeq_x\tilde E
\quad\Longleftrightarrow\quad
P(o\mid E,a)\approx P(o\mid\tilde E,a),\;\forall a\in\mathcal A_x.
$$

这个定义与任务相关。软件修复可能只关心仓库、依赖和测试进程，GUI 任务还关心浏览器 profile、页面 DOM、服务端账户与时间。无法对所有未来动作证明等价时，可以选一组 probe：读取关键文件、查询进程、检查端口、执行只读数据库查询、捕获页面状态。恢复前后 probe 一致，才允许分支 rollout 进入价值估计。

文件系统快照适合静态资产，却不能自动捕获进程内存。使用 CRIU 一类进程 checkpoint 仍会受内核版本、打开连接和设备限制。更可控的路线是让环境把可变服务状态外置到可快照存储，并设计明确的 quiesce 协议：暂停新请求、等待进行中操作结束、刷写缓存、记录版本，再创建快照。恢复时按相反顺序加载，并在开放流量前运行健康检查。

外部系统通常无法回滚。Agent 在真实网站创建订单后，本地 Pod 快照不能删除订单；两个 continuation 从同一快照出发，会共享并竞争外部账户。可以使用 mock service、每分支独立租户或带命名空间的测试资源。若只能访问共享服务，分支实验要限制为只读或可补偿动作，并把外部状态 ID 写入 manifest。所谓 branching 的成本优势只对可复制状态成立，不能无条件外推到整个互联网。

随机性也会破坏分支比较。两个 continuation 若使用不同模型采样种子，这是希望研究的策略随机性；环境中的数据库随机排序、时间和网络抖动则是干扰。快照应保存显式 RNG 状态，时钟可使用可控虚拟时间，外部响应可在允许情况下录制重放。仍无法控制的因素通过多次重复与配对设计估计方差。否则某个分支胜出，可能只因为页面加载更快。

状态快照本身有成本。设创建快照成本 $C_s$，恢复一次成本 $C_r$，重跑前缀成本 $C_p$，计划分叉 $K$ 次。使用快照节约的条件近似为

$$
C_s+KC_r<KC_p.
$$

若前缀很短或快照巨大，重跑更便宜；若前缀包含长编译、下载和多轮交互，快照优势明显。调度器可以根据实测 $C_p,C_s,C_r$ 决定在哪些节点保存，而非每一步都 checkpoint。还要计入存储与清理成本，过期快照同样会成为资源泄漏。

分支价值估计必须确认各分支从同一策略条件出发。若快照中包含 Harness 已压缩的历史，而不同分支恢复时重新压缩，模型输入会变化；若模型服务在等待期间升级，policy 版本也变了。Checkpoint manifest 因而同时记录环境与认知状态：消息历史、压缩结果、工具 schema、Harness 控制状态、模型版本和采样参数。只恢复 Pod 而重建一份不同上下文，比较的就不再是同一 $s_t$。

**十四、失败轨迹里的信用分配**

Orchard-SWE 保留 unresolved 轨迹，这一点比只收成功数据更重要。失败 episode 并非一整块负例：它可能正确定位问题、修复一半测试，收尾阶段因时间耗尽或一个边界条件未处理而失败。把全轨迹作为负样本会压低有效前缀，把它完全丢弃又浪费了最接近成功边界的数据。Credit-assignment SFT 试图从中找出 productive rise segment，本质是在缺少逐步真值时估计局部进展。

设终局验证由 $M$ 个测试组成，在第 $t$ 步后的通过向量为 $v_t\in\{0,1\}^M$。最简单的进展分数是 $g_t=\sum_jv_{t,j}$，片段收益为 $g_{t_2}-g_{t_1}$。它能识别新增通过测试，却有两个盲区：测试重要性不同，且通过集合可能先缩小再扩大。修复根因时暂时破坏一个脆弱测试，最终换来多个关键测试通过，局部差分会误判中间动作。更稳妥的表示保留逐测试向量、依赖关系和最终状态，而非只留总数。

价值模型可以根据状态摘要估计完成概率 $V_\phi(s_t)$，将上升片段定义为 $V_\phi(s_{t_2})-V_\phi(s_{t_1})>\delta$。但训练价值模型的标签仍来自终局 reward，它可能把与成功相关却没有因果作用的特征当作进展。例如成功轨迹通常在后期运行完整测试，模型便可能给「运行测试」很高价值，即使代码尚未修好。要检查这种捷径，可以把同一状态配上不同无副作用命令，或在已知失败状态运行测试，看价值是否虚高。

Retrospective 估计还会利用未来信息。事后知道某文件最终被修改，容易把早期读取该文件标为关键；部署时 Agent 尚不知道它会成为答案。把这些片段用于 SFT 可以教会有效路径，却不能声称得到了在线可用的无偏优势。若把事后价值直接用于 RL，应明确它依赖完整轨迹，并检查是否把隐藏测试结果泄露进模型输入。

一种更强的证据来自干预。保存状态 $s_t$，分别保留与删除候选片段造成的修改，再从两种状态采样 continuation。若保留片段后的成功率显著更高，才说明它具有实际贡献。设两组各 $K$ 次采样，估计差为

$$
\hat\Delta_t=\frac1K\sum_{k=1}^KR(\tau_k^+)-
\frac1K\sum_{k=1}^KR(\tau_k^-).
$$

这种成对反事实比单轨迹打分可靠，成本也高得多。Stateful branching 若实现，便能把它从少量离线实验扩展成系统化标注。当前没有完整分支能力时，可以在文件级任务上用补丁应用与撤销近似，仍要确认后台状态没有残留。

片段边界同样影响监督。把一次有效修改单独留下，却删除此前定位错误的观察，模型可能学会在没有证据时直接改文件；保留过长前缀又混入大量无效探索。一个片段应包含使首个动作可判断的最小上下文，以及能证明末端状态改善的验证结果。上下文选择可以通过删减测试：逐步移除早期消息，直到策略对首个动作的概率或后续成功率明显变化。

失败恢复片段值得单列。Agent 先执行错误补丁，随后读测试、回滚并改成正确方案，即使 episode 最终因另一个问题失败，回滚过程仍展示了检测和恢复。若只筛选价值单调上升片段，这类先降后升的轨迹可能被丢掉。可以以局部最低点为中心，保留「异常证据—诊断—恢复—重新验证」闭环，让模型学会在已经受损的状态里继续，而不只是模仿一路顺利的成功轨迹。

监督数据还应标明片段来源与置信度。隐藏测试差分、独立 verifier、价值模型和人工判断提供的证据强度不同。训练时可按置信度加权，评测时分别消融；若低置信片段贡献很小甚至有害，就不应靠扩大数量掩盖。数据卡报告保留率、各类证据比例、片段长度和原 episode 结果，才能让 107K rollouts 到最终 SFT token 的转换可核查。

**Balanced Adaptive Rollout 的选择偏差**

稀疏奖励下，同一任务的组内样本全成或全败时，相对优势缺少区分。BAR 通过自适应采样提高含正负结果的组比例，训练效率由此上升。代价是训练任务不再按原始分布出现：成功率接近中间区间的任务被反复采样，过易与过难任务减少。

设目标任务分布为 $p(x)$，调度后的分布为 $q(x)$。希望仍优化目标期望时，可对样本使用 $p(x)/q(x)$ 权重；但 $q(x)$ 随策略成功率在线变化，估计噪声很大，极端任务的权重还会爆炸。实践中通常接受课程目标已经改变，再用固定、未重采样评测集衡量最终性能。关键在于不要把平衡池内 reward 当作部署成功率。

自适应难度估计也会滞后。模型更新后，昨天成功率 50% 的任务今天可能已变简单；若滑动窗口太长，调度器继续浪费采样，太短又会被随机波动驱动。可以为每个任务维护 Beta-Bernoulli 后验，成功 $s$ 次、失败 $f$ 次后均值为

$$
\hat p_x=\frac{s+\alpha_0}{s+f+\alpha_0+\beta_0},
$$

并用后验不确定性决定探索。采样很少的任务保留机会，证据充分的极易任务降低频率。模型大版本更新后应衰减旧统计，因为任务难度相对新策略已经变化。

全失败组还要区分过难与损坏。参考方案若也失败，优先检查环境和 verifier；强 teacher 能成功而当前 policy 全败，才是可用的困难任务；所有模型均失败且目标依赖缺失资源，则应隔离。BAR 若只根据当前 reward 加大采样，会把损坏任务当成最高难度，持续烧掉环境与模型预算。

全成功组也不一定无价值。它可以用于稳定 SFT、成本优化和安全检查：在都成功的轨迹中选择更短、更少风险动作或更低资源消耗的方案。若 reward 只有二元成功，组相对 RL 看不出差别；加入经过约束的次级成本，或把这些数据转到蒸馏阶段，能利用其信息。次级目标必须在成功条件下比较，防止模型用快速失败换低成本。

## 5. 十五、跨 Harness 泛化的因果拆分

Orchard 论文强调同一环境可承载多种 Harness，并报告训练未见 Harness 上的结果。这里至少有三种可能的泛化：模型学会了任务语义，能在新接口下重新表达；两个 Harness 共享大量模板和工具语义，迁移主要是表面兼容；新 Harness 本身更强，通过规划、压缩或重试替模型完成更多工作。端到端分数无法自动区分三者。

设策略 $\pi$、Harness $H$、环境任务 $x$ 的成功率为 $S(\pi,H,x)$。训练前后策略为 $\pi_0,\pi_1$，旧、新 Harness 为 $H_A,H_B$。四格矩阵给出：

$$
\begin{array}{c|cc}
 & H_A&H_B\\\hline
\pi_0&S_{0A}&S_{0B}\\
\pi_1&S_{1A}&S_{1B}
\end{array}
$$

$S_{0B}-S_{0A}$ 反映基础策略上的 Harness 差异，$S_{1A}-S_{0A}$ 是训练内接口增益，$S_{1B}-S_{0B}$ 才是新 Harness 上的策略增益。交互项

$$
\Delta_{int}=(S_{1B}-S_{0B})-(S_{1A}-S_{0A})
$$

描述训练收益在 B 上被放大还是削弱。只报告 $S_{1B}>S_{1A}$，无法知道优势来自 policy 迁移还是 B 本身。

预算必须统一到任务级。Harness B 可能允许更多 token、更多工具调用或更长超时，成功率自然更高。可以同时给固定 token、固定墙钟、固定工具步数三种对照；现实部署再报告各自默认配置。若 B 用并行子代理，单看主线程步数会低估计算，应累计所有分支的模型 token 与环境动作。

观察空间也要对齐。一个 Harness 返回完整 stderr，另一个只写「失败」，前者提供更多信息；一个自动读取相关文件，另一个要求模型主动搜索，二者的任务已不等难。研究共享 policy 能力时，可以构造规范化 observation adapter；研究端到端产品时则保留原生能力，但把额外观察与自动动作列出。

新 Harness 的「未见」程度需要量化。仅换命令名、system prompt 或 JSON 字段属于低层接口变化；改变工具集合、历史压缩和错误恢复属于中层控制变化；从单 Agent 变成多 Agent、从终端变成 GUI 则改变了决策结构。迁移结论应标明变化层级。对低层变化有效，说明格式鲁棒；对中层变化有效，才更支持 Harness-agnostic 技能；跨模态迁移还需要额外证据。

轨迹数据若混合多个 Harness，可以帮助模型见到更多接口，也可能形成条件冲突。相同工具名在两套系统中语义不同，或相同错误字符串要求不同恢复动作，模型会收到矛盾监督。训练样本应包含稳定的 Harness 标识和 schema，必要时映射到统一中间动作；评测未见 Harness 时，则不给训练标识，观察模型能否通过工具描述快速适配。

Harness 切换后的提升还可能来自选择效应。强 Harness 使更多困难任务完成，成功样本分布随之变化；若只分析成功轨迹，会误以为模型在 B 中步骤更合理。失败与环境错误必须一起比较，并按同一任务配对。逐任务差值能指出收益集中在哪些类型：长上下文、工具故障、并行搜索，还是单纯格式修复。

**十六、轨迹数据的血缘与去重**

一条 Agent 轨迹同时继承任务、环境、模型、Harness 与验证器五类来源。任一来源变化，样本语义都可能改变。适合长期保存的主键不应只是递增编号，而应由稳定标识组成：任务内容与初态摘要、镜像 digest、policy checkpoint、Harness commit、verifier commit、采样参数和 attempt。数据集发布时可以隐藏敏感路径，却要保留能判断两条轨迹是否同源的信息。

仓库任务尤其容易泄漏。同一个 issue 会被改写成多种描述，同一 bug 也可能出现在 fork、后续 commit 或相邻分支。按 prompt 哈希分割几乎没有作用。更可靠的分组键包括上游仓库、基线 commit、受影响文件、失败测试和补丁语义。补丁语义可以用修改函数、AST 差异和测试覆盖近似；无法确定时宁可把同一仓库集中到一个分区，牺牲部分覆盖换取清晰评测。

时间泄漏同样重要。训练轨迹使用 2026 年后的仓库状态，评测却声称模拟更早 issue，模型可能从后续代码看到修复。环境构建要固定基线 commit 和依赖快照，数据划分记录 issue 创建、修复合并与轨迹生成时间。实时网页任务则记录页面和后端状态的时间窗口；同一 URL 在不同日期可能已是完全不同的问题。

SWE 数据中的多个 rollout 共享任务初态。把它们随机分到训练与验证，会让验证测到对同一 bug 的再次采样，而非新任务泛化。即使消息轨迹不同，隐藏测试与修复目标仍相同。统计置信区间也要以任务为抽样单位；十条同任务 rollout 提供的是对该任务成功概率的估计，并非十个独立任务。

去重还要覆盖教师输出。两个 teacher 从同一参考补丁出发，生成文字不同但动作路径高度一致；直接当作多样样本会高估策略覆盖。可以把动作规范化为读取、搜索、修改、验证等事件序列，再比较文件与命令对象。语义去重不必删除全部近邻，可以保留少数代表，并把重复权重降下来，防止常见仓库模式占据训练池。

轨迹清洗应保持可逆血缘。原始事件层只追加，不直接覆盖；规范化层记录 parser 与 schema 版本；训练片段层保存来源区间、筛选理由和 reward；最终打包层记录 tokenizer 与 chat template。发现解析错误后，可以从原始事件重新生成，而不必猜测被清洗脚本改过什么。若为了隐私删除原始内容，也应保留删除清单、摘要与受影响字段，使后来者知道哪些分析无法进行。

数据集中的 unresolved 不是统一负类。至少可分为模型主动放弃、预算耗尽、测试失败、Harness 崩溃、环境失效和 verifier 不可用。只有前几类在环境健康时反映 policy 局限；其余属于数据质量问题。发布汇总时给出各类数量，训练脚本再按用途选择。将所有 unresolved 写成 reward 0，会让基础设施故障比例较高的仓库承受更多负更新。

截图与网页数据还含视觉近重复。相同页面在滚动、弹窗或时间变化后像素不同，感知哈希只能发现部分重复；DOM 结构、目标元素和任务后端 ID 能提供补充。GUI 轨迹若只发布 judge 通过的成功样本，读者无法估计 judge 的选择偏差。至少应给原始候选数、拒绝原因分布和人工抽查结果，即便失败截图因许可不能全部公开。

**数据许可和敏感信息**

Agent 轨迹比普通对话更容易夹带秘密：仓库中的配置、命令输出里的 token、网页账户信息、浏览器 cookie、文件路径中的用户名都可能进入模型上下文。采集端应在已知结构处先阻断，例如不给生产凭证、为测试账户发短期 token；存储端再按字段和内容双重扫描。仅在发布前做一次正则清洗，无法覆盖 base64、URL 参数、截图和模型复述。

脱敏会改变训练语义。把所有秘密替换为空字符串，工具调用可能失去必填参数；用统一 `<SECRET>` 又会让多个不同凭证看似相同。可使用带类型和作用域的占位符，如 `<TOKEN:repo:episode>`，并让模拟环境识别它。这样模型能学习凭证应放在哪里，却不能恢复真实值。原始与脱敏轨迹之间保留访问受控的映射审计，公开数据只含不可逆占位。

代码、网页和教师输出各自受许可约束。环境可执行不代表轨迹可以再发布，公开仓库也可能含限制性数据或个人信息。数据卡应说明来源、许可筛选、退出机制和删除传播：某条源数据撤回后，原始轨迹、派生片段、训练打包与缓存都能根据血缘定位。没有血缘图时，删除请求只能靠全库字符串搜索，容易漏掉改写内容。

### 5.1. 十七、成本数字背后的容量规划

论文给出的 spot 与 on-demand 成本展示了自托管环境的潜在优势，但容量规划还要考虑利用率、运维和失败。购买 1000 个 Pod 的名义容量，若平均只有 40% 在执行有效 episode，其余时间等待模型或镜像，单位有效轨迹成本会明显升高。设集群每小时成本为 $C_h$，完成 episode 数为 $N$，有效率为 $\eta$，则

$$
c_{effective}=\frac{C_h}{N\eta}.
$$

提速和降价都可能被低 $\eta$ 抵消。spot 抢占若让长任务在末尾失败，损失的不只是环境分钟，还有此前模型 token。成本核算应把被丢弃 rollout 的推理费用算进去。

资源规格也会影响任务结果。给测试进程更少内存可能触发 OOM，CPU 限额太低会导致超时；这些失败若被当作 policy 失败，便改变训练。为了省成本动态缩小 Pod 时，必须在任务 manifest 中声明最低资源，并用参考方案在该规格上验收。跨系统成本比较需要对齐成功所需资源，不能让一方以更高失败率换低价格。

镜像缓存是吞吐的关键变量。大量异构 SWE 镜像首次拉取可能占用分钟和网络带宽，缓存命中后启动才很快。报告 Pod 创建时间时应分别给冷缓存与热缓存，并说明镜像大小分布。调度器可以把相同镜像任务聚到已有缓存的节点，但过度聚集会造成节点热点；还要防止恶意或错误镜像填满磁盘，把后续任务挤出缓存。

热池把冷启动换成闲置成本。设冷启动时间 $T_c$，任务服务时间 $T_s$，到达间隔随机。保留 $K$ 个预热 Pod 能降低等待，却在空闲时持续收费。适合固定镜像、任务到达稳定的 GUI 服务；SWE 镜像高度异构，通用热池只能预热基础 agent payload 和常见层。容量策略应根据镜像复用率、等待损失和闲置单价求平衡，而非把热池当作统一答案。

模型与环境容量要联调。若推理服务每秒只能处理 20 个调用，环境层把 exec 提升到每秒 150 个也不会线性提高 episode 吞吐；若模型生成很快而测试耗时长，则环境并发决定 GPU 是否有足够其他请求填充。可以用事件日志计算每条轨迹在 model、queue、environment、verifier 四类时间上的占比，再扩容占比高且排队明显的部分。

长尾决定同步训练的节奏。平均 episode 10 分钟，P99 可能超过一小时；等待完整 batch 会让大部分资源空闲，提前截断又丢失最难任务。按长度预测分桶、异步消费和软截止能缓解，但每种方案都会改变数据分布。成本报告应给完成时间分位数、截断率以及不同长度任务的成功率，避免平均值掩盖系统对长程任务不友好。

一个简单算例：500 个并发 Pod，每小时成本 100 美元，平均每条 12 分钟，理论每小时完成 2500 条。若启动失败 5%、运行故障 7%、verifier 异常 3%，近似有效率为 $0.95\times0.93\times0.97=0.857$，每小时约 2143 条，环境成本约 0.047 美元一条。再考虑 10% 的策略过旧样本不能进入在线更新，用于 RL 的单位成本升到约 0.052 美元。若模型推理每条 0.20 美元，优化环境仍有价值，却不是总成本的主项；若任务本地模型推理很便宜，环境占比则会反过来升高。

托管服务与自托管的比较还包括工程人力、可用性和弹性。自托管在持续大负载下摊薄控制面成本，并能自定义镜像与网络；托管服务在突发、小规模任务上省去集群维护。论文的价格实验说明特定设置下的资源账单，不等于所有团队都应迁移。最有用的结论是把环境成本拆成可测组件，再根据自身任务分布复算。

**十八、安全隔离的可验证边界**

默认 deny-egress 是良好起点，但 Kubernetes NetworkPolicy 的效果取决于 CNI、DNS 和规则组合。应从 Pod 内实际请求云元数据地址、集群 API、其他 namespace、允许域和随机公网域，验证每条路径。DNS 放行常被忽略：允许查询任意 DNS 可能形成低带宽外传通道；完全阻断又让域名 allowlist 无法工作。可使用受控解析器，只解析许可域并记录查询。

容器隔离也不等于强安全边界。内核漏洞、特权 capability、宿主机挂载和容器运行时配置都可能造成逃逸。任务镜像默认以非 root 用户运行，删除不需要的 capability，使用 seccomp/AppArmor 或等价策略，不挂载宿主机 socket。确需编译、浏览器 sandbox 或特殊内核能力的任务单独分级，放进更强隔离节点，不能为了兼容少数镜像给全部任务提权。

运行时注入 agent 要建立信任链。注入镜像按 digest 固定并签名，orchestrator 验证来源，Pod 内 agent 只暴露必要接口。若用户任务镜像能改写 agent 二进制或窃取其服务凭证，隔离层会被绕过。只读挂载、独立用户与短期双向认证可以缩小风险；协议仍要防命令注入、路径穿越和超大响应。

文件接口尤其要检查路径边界。客户端请求 `/workspace/../etc/shadow`、符号链接指向工作区外部、压缩包含 `../` 条目，都可能越过预期目录。若 API 设计为访问整个容器，就要明确这一权限；若只允许 workspace，则解析真实路径后再次验证前缀，并防止检查与使用之间被替换的竞态。Agent 本就可以执行 shell 时，文件 API 限制不会提供完整安全，但仍能保护控制面自身不被利用。

秘密分发遵循最小权限和最短寿命。每个 episode 使用独立凭证，权限限定资源与动作，结束后立即撤销；verifier 使用另一套只读或验收凭证，防止 policy 修改评分数据。Secret 不放进普通环境变量转储和轨迹日志，工具层以句柄引用。若任务需要模型填写 token，使用模拟值和测试服务，训练数据不接触生产秘密。

资源配额也是安全边界。fork bomb、无限日志、磁盘写满和高频网络请求既可能来自恶意任务，也可能是模型失误。CPU、内存、进程数、临时盘、输出大小、网络速率和总时长都要限制。达到配额时返回明确的 `resource_exhausted`，并记录是哪项资源，而不是让 Pod 无声消失。这样 Recipe 才能判断策略是否制造了问题。

清理验证要覆盖外部副作用。删除 Pod 后，临时云资源、测试账户记录、消息和对象存储文件可能仍在。环境 manifest 列出 episode 创建的外部资源，终止钩子逐项回收；清理失败进入独立队列并告警。对于无法真正删除的系统，使用带过期时间和命名空间的资源，至少避免长期污染下一次任务。

**十九、从论文数字回到实验对象**

Orchard 同时报告环境微基准、数据规模和三个 Recipe 的模型结果，三类数字回答的问题不同。exec 延迟和千 Pod 创建成功率说明环境服务的性能与稳定性；107K 轨迹说明可收集的数据量；SWE、GUI、Claw 分数说明特定模型、训练配方与推理设置的端到端效果。环境更快能降低等待和成本，却不会在逻辑上推出模型分数更高；模型分数提高也不能证明每个环境组件都必要。

环境微基准需要明确分母。一次 `exec` 的延迟从客户端发请求开始，可能包含序列化、网络、Pod agent 调度和命令执行。若命令本身只有 `echo`，主要测框架开销；真实测试运行几十秒时，0.4 秒差异占比很小。可将延迟写成

$$
T_{exec}=T_{client}+T_{network}+T_{agent}+T_{process}+T_{payload},
$$

并用空命令、不同输出大小和不同运行时长分别测量。对照系统若走不同区域、TLS 设置或并发限制，数字便不再只反映架构。

千 sandbox 26 秒端到端说明控制面能承受一次并发突发，仍需说明「成功」的判定：Pod 被 Kubernetes 接受、进入 Running、health check 通过，还是完成首条命令。训练真正需要的是 ready-to-exec。若前 900 个很快、收尾阶段 100 个因镜像或调度拖延，总时长由尾部决定；同时给 ready 曲线与 P50/P95/P99 比一个最大值更能解释扩展行为。

Terminal-Bench 从 direct Docker 迁到 Orchard 后分数无明显回归，为环境等价提供经验支持。分数略有上升不必解释成 Orchard 提升了模型能力，采样随机性、时间、依赖和运行噪声都可能造成差异。更直接的等价性证据是同一动作脚本在两环境的最终文件哈希、测试结果和错误类型；模型分数则作为综合回归，捕获脚本未覆盖的差别。

SWE 的 69.7% 与 reranking 后 73.0% 对应两套推理条件。Reranker 从多个候选中选择，会增加采样成本，效果依赖 value model 对候选排序的准确性。若每题产生 $k$ 条轨迹，73.0% 不应与其他系统的单次输出直接横比。至少报告每题候选数、总 token、环境时间和选择失败案例，才能判断提升来自 policy、本身的 pass@k 空间，还是更好的排序。

GUI 4B 模型超过 235B teacher 说明学生在给定评测上可以借助领域数据与 RL 达到更高成功率，无法推出小模型一般能力超过大模型。Teacher 负责生成数据时的采样 Harness、推理预算与训练后学生的评测 Harness可能不同；学生还见过目标域训练分布。公平解释应限定在 WebVoyager、Online-Mind2Web、DeepShop 的具体协议，并检查 judge 与网站漂移。

Claw 在切换 ZeroClaw 后提高，恰好展示 policy 与 Harness 交互。若训练时跨两个 Harness，模型可能学到一定接口鲁棒性；ZeroClaw 也可能拥有更强的工具和控制流。前述四格矩阵能拆分两者。`pass@3` 上升 14.3 点与 `pass^3` 上升 9.3 点说明至少一次成功和稳定成功都改善，但二者仍依赖逐任务三次采样的联合分布，不能用单次概率独立推导。

论文版本变化同样属于实验条件。v1、v2、v3 可能更新训练路线、模型与主表；引用数字时绑定 arXiv 版本与日期。仓库 main 在论文后继续演进，运行当前代码得到不同默认参数很正常。知识库同时给论文结论和当前代码状态时，应分别标注，避免读者把路线图实现或后续姊妹项目倒灌进原始实验。

**结果归因的最小实验集**

若要判断 Orchard Env 是否带来训练收益，至少需要三个层次的对照。第一层固定动作脚本，比 direct Docker 与 Orchard 的状态、延迟和错误；第二层固定 policy，比两环境中的轨迹与成功；第三层固定任务、token 和采样数，比使用 Orchard 数据训练前后的 policy。每一层只回答自己的因果问题。

Recipe 的数据贡献可通过等 token 消融。随机成功轨迹、只保留 resolved、加入 unresolved productive segment、再加入 RL，逐步比较。若每一步同时增加 token 数与数据质量，无法知道收益来自数量还是筛选。对失败片段，还应使用随机片段和相同长度的邻近片段作对照，确认 value-based 选择确实选中了更有用内容。

BAR 的贡献可在固定 rollout 预算下比较均匀采样与自适应采样，报告进入更新的非退化组比例、任务覆盖、梯度方差和最终固定集成绩。只报告训练 reward 会偏向 BAR，因为它主动改变了采样分布。还可以把 BAR 产生的数据交给相同优化器，排除 trainer 实现差异。

跨 Harness 泛化使用训练×评测矩阵，并增加原始基座。所有格子共享 checkpoint、任务、镜像、采样参数和预算；Harness 原生自动动作另行计费。按任务配对后，报告改善、退化与不变的任务数，避免平均分掩盖某一类任务大幅倒退。

环境可靠性要用故障注入验证。人为让 Pod 启动失败、exec 响应丢失、节点抢占、Redis 短暂不可用、verifier 超时，再检查错误分类、幂等重试和资源清理。系统在无故障压测中成功，无法证明异常路径不会产生重复动作、幽灵 Pod 或错误负奖励。注入率与恢复时间也要记录，使可靠性结论可复算。

### 5.2. 二十、Orchard 与训练算法的边界

Orchard Env 提供状态转移和观测，slime fork 与各 Recipe 决定怎样采样、构组、计算奖励和更新 policy。这个分层允许替换 PPO、GRPO、蒸馏或其他算法，也意味着论文某个训练技巧的效果不能自动归给 Env。公共环境降低了做受控比较的成本，最终比较是否公平仍取决于 Recipe。

On-policy 方法要求轨迹接近当前策略。环境执行时间长、队列积压或重试都会让样本变旧。Env 可以记录开始、结束和 policy 版本，trainer 才能决定丢弃、降权或继续使用。环境层若只返回最终消息而没有版本与时间，算法无法判断 policy lag；trainer 若忽略这些字段，再完整的记录也不会自动纠偏。

离线 SFT 对策略版本不敏感，却受行为覆盖限制。107K 轨迹展示教师和采样 Harness 到达过的状态，没出现的错误恢复路径无法从模仿中学到。加入 unresolved 能扩大失败状态覆盖，仍要通过筛选把环境故障与模型失误分开。SFT 学到的是数据条件分布，不能仅凭数据量推断在新状态上的恢复能力。

奖励由 Recipe 定义。SWE 隐藏测试、GUI judge、Claw verifier 的误差结构不同；Env 只保证它们能在对应状态运行。把多个域混合训练时，reward 数值尺度也未必可比。二元成功、分步 judge 和测试比例若直接相加，某个域会因密集反馈占据梯度。需要按域归一、分批或采用多目标权重，并在固定评测上验证权重选择。

轨迹中的工具动作是否参与 policy loss，也由训练层决定。Harness 自动插入的消息、环境返回和模板 token 应掩码；模型生成的工具 JSON、自然语言与代码可能采用不同权重。若重建器把自动修复后的动作当作模型输出，Env 执行成功会给不存在的序列正奖励。环境记录原始请求与执行请求，trainer 再明确选择，二者缺一不可。

价值模型 reranking 位于推理决策层。它可以利用多个完整候选的终态和轨迹特征，作用类似额外搜索。若把 reranked 成绩称为 policy 成绩，读者会低估推理预算与第二模型贡献。更清晰的报告同时列单样本、pass@k、oracle@k 与 value-rerank@k：oracle 上限展示候选池潜力，reranker 与 oracle 的差距展示选择误差。

算法替换还可能改变环境压力。更大的 group size 同时启动更多 sandbox，树搜索需要 snapshot 与分支，异步算法容忍长尾却增加策略滞后。Env 的性能不能脱离算法负载评估。一个在独立请求微基准中最快的实现，面对大量长连接、截图和分支恢复时未必仍领先。

**二十一、适用范围与内容上限**

Orchard 已给出可运行的开源环境、三条 Recipe、数据与论文实验，足以深入讨论环境服务、轨迹生成和训练接口。它当前不能回答所有长程 Agent 问题。Stateful pause、resume、branching 仍属于路线图，因此本章对快照价值估计的推导是基于该能力的研究方向与验收条件，不应冒充现有主表已经验证的机制。

论文覆盖 SWE、GUI 与 Claw，代表代码、网页和通用工具三类环境，仍没有覆盖真实长期团队协作、跨天任务、持续用户反馈与高风险外部操作。这些场景包含不可回滚的人类状态和制度约束，Pod 隔离只能管理其中一部分。将 Orchard 的沙箱结果外推到生产，需要重新定义权限、审批、隐私和用户满意度。

成本数字来自特定区域、时间和实例价格，会随云市场变化。本章保留计算结构与必要条件，不把美元数字视为长期常数。真正稳定的知识是如何计算 Pod 时间、有效率、重试损失和模型—环境联动；部署者应代入自己的价格与任务分布。

跨 Harness 结果支持在论文组合中的迁移，尚不足以宣称对任意未知 Harness 普遍泛化。工具语义相近、训练中见过多种接口与更强部署控制流，都可能贡献收益。要扩大结论，需要更多机制差异明显的 Harness、完整四格矩阵和统一预算。

数据公开让离线统计和训练更可行，完整 rollout 复现仍依赖原镜像、网站、teacher、verifier 与当时版本。缺少其中一项时，应明确复现层级。能够读数据集不等于重建环境，能够部署 Env 也不等于复算模型主表。

在这些边界内，Orchard 的贡献很清楚：它把过去各项目重复搭建的 sandbox 变成独立环境服务，使 distillation、RL 和 evaluation 能围绕同一状态转移接口组织；又用多个 Recipe 证明这层抽象并未局限在单一任务。后续工作要做的，是让状态可分支、证据可归因、故障可恢复，并把论文设置中的可用性扩展到更长、更开放的真实任务。

**一条可复算的最小闭环**

真正复现 Orchard 不必一开始就训练完整模型，可以先建立一条单任务闭环。第一步固定镜像 digest、任务初态与参考方案，在 direct Docker 中运行并保存最终状态。第二步把同一镜像交给 Orchard Env，使用相同用户、资源、网络和命令序列，比较文件哈希、退出码、测试与副作用。两者一致后，环境替换才算通过。

第三步接入一个固定 policy checkpoint 与固定 Harness，在 Orchard 中重复采样若干次。每条 episode 保存 policy、Harness、环境与 verifier 版本，分别统计任务失败和基础设施失败。若相同种子仍得到差异，沿请求、Pod generation、工具观察和终态逐层定位，而非先修改训练算法。

第四步把原始事件转换成训练样本。随机抽取调用，确认模型输入与采样时完全一致，模型 token 掩码正确，Harness 自动消息没有进入 loss；再从最终状态独立重跑 verifier，确认 reward 能按 episode 绑定。环境异常和轨迹不完整的样本进入隔离集合，不参与优势估计。

第五步只做一个很小的更新，并在固定锚点任务上比较更新前后。检查 loss、KL、梯度范数、动作格式和成功率，尤其确认没有因 parser 错位而训练模板 token。小闭环稳定后再增加并发、任务种类和训练步数。直接从千 Pod 开始，只会把一个可定位错误复制成海量坏轨迹。

这个闭环还应包含故障注入。让一次 exec 响应丢失，检查 operation ID 是否防止重复执行；让 verifier 超时，确认样本不会记成任务失败；让 worker 在命令结束后崩溃，确认终态和日志仍可回收；让 delete 失败，确认 TTL 与告警最终清理资源。四个测试覆盖控制面、数据面、奖励与生命周期的主要连接处。

收尾阶段再做吞吐扩展。并发从小到大递增，观察 ready 延迟、exec 尾延迟、Proxy 队列、模型利用率、环境错误率和有效轨迹吞吐。某个指标出现拐点时先扩容对应瓶颈；若错误率同时上升，就停止增加并发。目标是每小时得到更多可训练、可验证的 episode，而非在监控面板上堆出更多 Running Pod。

### 5.3. 面向研究者的判断顺序

读到一个新的环境系统时，可以依次问五个问题。它是否定义了稳定状态与动作语义；它是否能把任务初态和终态复现；它能否区分 policy、Harness、环境与 verifier 的失败；它生成的轨迹能否重建模型当时的条件概率；它的性能数字是否换算成有效 episode 与统一预算。前四个决定结论是否可信，第五个决定方案是否值得规模化。

若状态语义含糊，训练公式再先进也可能吃到错误样本；若失败无法归因，reward 0 会混合模型与系统噪声；若轨迹无法重建，策略梯度对应的已是另一段历史；若只追 API QPS，系统可能更快地产生无效数据。Orchard 提供了回答这些问题的一套开源基础，但每个 Recipe 仍需把自己的任务、奖励和安全边界补完整。

因此，环境层的「薄」指职责清楚，不代表信息贫乏。它不替上层决定什么是好答案，却要完整记录动作怎样变成状态变化；它不选择 RL 算法，却要提供算法判断样本有效性所需的版本、时间与故障；它不承诺任何 Harness 都会泛化，却要让不同 Harness 在同一任务状态上可比较。守住这个边界，环境才能长期复用，研究结果也才能从一次演示变成可累积的证据。

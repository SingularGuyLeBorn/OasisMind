# 第8讲: 用 PyTorch 实现分布式训练

第七讲从状态与成本解释并行策略, 第八讲进入可执行实现. 分布式代码的难点不只是调用 `all_reduce`: 每个 rank 的张量 shape 必须匹配算法假设, collective 必须由通信组内所有 rank 以一致顺序参加, 异步 handle 必须在数据真正被消费前完成, backward 中的梯度同步还要与 autograd 生命周期配合. 单进程正确的模型经过切分后, 参数初始化、随机数、checkpoint 与输出聚合都可能出现新边界.

[主讲义](./8.1-主讲义/8.1-主讲义.md)从通信软硬件到三种并行代码给出全貌. [Collective Operations](./8.2-Collective-Operations/8.2-Collective-Operations.md)逐项说明 broadcast、scatter、gather、reduce、all-gather、reduce-scatter 与 all-reduce, 并讨论带宽测量. [Data Parallelism Code](./8.3-Data-Parallelism-Code/8.3-Data-Parallelism-Code.md)实现参数复制与梯度同步; [Tensor and Pipeline Parallelism Code](./8.4-Tensor-And-Pipeline-Parallelism-Code/8.4-Tensor-And-Pipeline-Parallelism-Code.md)追踪层内权重分片和 stage 间激活传输.

## 1. 进程、设备与通信组

### 1.1 rank 是程序实例

分布式训练通常每个 GPU 对应一个进程和 global rank. 初始化 process group 后, rank 通过 world size 与 group 成员确定 collective 范围. local rank 用于选择当前节点的设备, global rank 用于跨节点身份. 若把 global rank 直接当本地 GPU 编号, 多节点运行会选择错误设备.

并行组合需要多个子 group. TP group 在一组 rank 间做层内 collective, DP group 在模型副本间同步梯度, PP group 沿 stage 发送激活. 同一 rank 同时属于多个 group, 每个 collective 必须使用正确 group. group 构造顺序与成员列表应在所有进程一致, 否则初始化或运行会挂起.

### 1.2 Collective 的 shape 契约

[Collective Operations](./8.2-Collective-Operations/8.2-Collective-Operations.md)给出各操作的数据变化. broadcast 后所有 rank 获得源张量; scatter 把源端列表分发成局部分片; gather 在目标端收集; all-gather 在所有 rank 拼出完整列表; reduce-scatter 对输入块逐项规约后分发; all-reduce 在所有 rank 返回完整规约结果.

代码必须明确拼接维度与规约语义. all-gather 收集参数分片时, 每 rank 分片 shape 通常相同; reduce-scatter 梯度时, 输入需要能按 world size 划分. 非整除 shape 要提前 padding 或使用支持不等长的路径. dtype、device 与 contiguous layout 也会影响 backend 支持和吞吐.

## 2. 测量通信而不是 API 开销

collective 调用常异步排队. benchmark 需要 warm-up, 在测量区间前后同步, 并避免把张量分配与数据初始化混入通信时间. 多 rank 应在开始测试前 barrier, 否则不同进程的启动偏移会污染结果. 报告消息大小曲线能区分延迟区与带宽区.

算法带宽与总线带宽口径不同. all-reduce 的每 rank 输入大小除以时间得到的算法带宽, 还需根据 collective 中实际链路传输量换算 bus bandwidth. [Collective Operations](./8.2-Collective-Operations/8.2-Collective-Operations.md)对 all-reduce 与 reduce-scatter 的换算分别解释, 比较 NCCL 或硬件规格时必须使用同一口径.

profile 还要判断通信是否与计算重叠. `async_op=True` 只返回 handle, 若随即 `wait()` 就没有重叠; 若消费输出前忘记等待, 则出现数据竞态. **异步通信的正确用法由数据依赖决定, 不是把同步调用换一个参数.**

## 3. 数据并行代码

### 3.1 模型复制与梯度 all-reduce

[Data Parallelism Code](./8.3-Data-Parallelism-Code/8.3-Data-Parallelism-Code.md)让每个 rank 持有相同模型参数, 输入 batch 按 rank 切分. 前向和反向独立执行, 随后对对应参数梯度 all-reduce 并除以数据并行度, 确保更新等价于 global batch 的平均梯度. 初始参数必须一致, 可由相同 seed 或 rank 0 broadcast 保证.

手写循环通常在 backward 完成后逐参数同步, DDP 则注册 autograd hook, 梯度 bucket 就绪后尽早启动 all-reduce. bucket 化减少大量小消息, 并让后层反向计算与前面已就绪梯度通信重叠. 参数遍历顺序必须在 rank 间一致, 动态未使用参数还可能改变 collective 参与情况.

### 3.2 global batch 与损失缩放

若每 rank loss 已对本地样本取平均, 梯度 all-reduce 后还要按 world size 平均, 才对应整个 global batch 的平均损失. 若使用求和损失或 gradient accumulation, 缩放位置需要重新推导. 重复除 world size 会让有效学习率下降, 完全不除则随 rank 数放大梯度.

数据 sampler 要保证不同 rank 读取不同样本, 每个 epoch 还需一致更新 shuffle seed. validation 指标可能需要规约分子与分母, 不能简单平均各 rank 已平均的数值, 尤其当最后一个 batch 大小不同.

## 4. 张量并行代码

### 4.1 切分线性层

[Tensor and Pipeline Parallelism Code](./8.4-Tensor-And-Pipeline-Parallelism-Code/8.4-Tensor-And-Pipeline-Parallelism-Code.md)展示线性权重怎样按输出或输入维切分. Column parallel 中每 rank 计算一部分输出通道, 输出保持分片或 all-gather 后交给下一操作. Row parallel 中每 rank 接收一部分输入通道并计算局部和, 再 all-reduce 得到完整输出.

连续两层 MLP 可组合 column-parallel 上投影与 row-parallel 下投影, 中间激活保持分片, 只在下投影后规约一次. Attention 可按 head 切分, 每 rank 处理部分 Query/KV head. 代码中的局部权重 shape、bias 处理和输出布局必须与数学切分一致.

### 4.2 初始化与 autograd

分片参数可以先生成完整权重再 scatter, 便于与单卡参考对照; 大模型实际初始化应直接生成局部分片, 同时保证拼接后的统计与 seed 规则可复现. 自定义 collective 若要进入 autograd, backward 必须实现对应的伴随通信. 例如前向 all-gather 的 backward 常对应 reduce-scatter, 前向 all-reduce 的 backward仍是 all-reduce 或按定义处理.

TP 正确性测试应把各 rank 输出收集后与未分片层比较, 再比较输入梯度和参数梯度. 只验证前向 shape 不足以发现 backward 通信遗漏.

## 5. 流水线并行代码

流水线把模型层划分到不同 rank. 第一 stage 接收数据并发送中间激活, 中间 stage `recv`、计算、`send`, 最后一 stage 产生 loss. backward 反向传递激活梯度. 最简单实现可用阻塞 send/recv 验证正确性, 随后再引入 microbatch 和异步调度.

通信 Tensor 的 shape 与 dtype必须由发送端和接收端共同约定. 接收端通常要预分配 buffer, 动态序列长度会使协议复杂化. stage 边界激活若需要 autograd, 不能把网络传输误当作普通本地 Tensor 引用; 需要显式接收梯度并对本地计算图 backward.

microbatch 调度决定激活保留量和 bubble. 1F1B 需要区分 microbatch ID, 保证前向激活与对应反向梯度匹配. 非阻塞通信还要避免 send/recv 顺序形成死锁. **流水线代码的核心状态是 microbatch 在各 stage 的阶段, 而不仅是当前 rank 执行哪一层.**

## 6. 阅读与验收路径

先读[主讲义](./8.1-主讲义/8.1-主讲义.md)和[Collective Operations](./8.2-Collective-Operations/8.2-Collective-Operations.md), 用小 Tensor 在两到四个进程验证每项操作的输入输出. 再阅读[Data Parallelism Code](./8.3-Data-Parallelism-Code/8.3-Data-Parallelism-Code.md), 对比单卡与多卡一步更新后的参数. 最后进入[Tensor and Pipeline Parallelism Code](./8.4-Tensor-And-Pipeline-Parallelism-Code/8.4-Tensor-And-Pipeline-Parallelism-Code.md), 分别核验分片线性层和 stage 传输.

每个实现都应完成四类检查: 与单卡参考的数值对照, 每 rank 参数和激活 shape, collective 次序与数据量, 实测 step time 和峰值显存. 只有四项同时成立, 并行代码才完成从理论节省到实际收益的闭环. 后续扩大到 FSDP、3D parallelism 或不同硬件 backend 时, 仍可沿这套检查表定位问题.

调试 collective hang 时, 最有效的记录不是笼统的“卡在 all-reduce”, 而是每个 rank 的操作序号、group、collective 类型、输入 shape、dtype 与 stream. 任一 rank 少调用一次, 或不同 rank 以相反顺序进入两个 group, 都可能没有 Python 异常而永久等待. 最小复现应缩到两个 rank, 固定 seed, 设置超时并开启 backend 日志.

数值对照要跨越一次完整更新. DDP 中检查梯度规约前后的缩放, 确认 local mean 与 world-size average 没有重复相除;TP 中将局部输出 all-gather 后与未分片线性层比较, 同时比较输入与权重梯度;PP 中为每个 microbatch 标识前向激活和反向梯度, 防止接收顺序错配. 单纯比较最终 loss 可能掩盖恰好互相抵消的通信错误.

性能测量需要将计算、通信和等待分开.DDP 的梯度 bucket 应在 backward 中逐步就绪, TP collective 位于层内关键路径, PP send/recv 取决于相邻 stage 节拍. profile 若显示空闲, 先判断是数据未就绪、负载不均还是链路饱和. `async_op=True` 只有在 handle 等待前存在独立计算时才提供重叠.

完成小规模代码后再增加 world size. 每次扩展都复核 global batch、sampler、随机数、checkpoint 与指标规约. validation 的正确聚合通常是先规约分子与分母, 不能简单平均各 rank 的局部均值. 这套顺序让第七讲的状态与通信模型真正落到可验证程序, 也为后续 FSDP 和 3D parallelism 提供参照实现.

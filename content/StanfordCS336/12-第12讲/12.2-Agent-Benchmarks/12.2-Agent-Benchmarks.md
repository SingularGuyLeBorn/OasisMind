# Agent 基准:SWE-bench 与 CyBench

普通问答基准把一道题压成一次输入和一次输出.Agent 任务多了一条会改变后续状态的动作链:模型先查看文件,再搜索符号,修改代码,运行测试,根据报错继续处理.网络安全任务里,一次命令还会改变文件、进程与网络连接.因此,Agent 分数评价的是一个在限定环境中运行的系统.底座模型很重要,提示词、工具协议、上下文整理、重试策略和预算同样会改变结果.

这类评测最容易发生的误读,是把排行榜上的 resolved rate 直接当作模型自身能力.同一个模型接入不同脚手架,可以得到明显不同的成功率;同一套系统只改超时或最大步数,也可能多解决一批长任务.阅读结果时需要同时看四样东西:任务给了什么,系统能做什么,运行允许花多少资源,评分器如何判定成功.SWE-bench 与 CyBench 分别把软件维护和网络安全做成可执行任务,刚好适合把这四个部分逐层拆开.

## 1. Agent 评测究竟多了什么

### 1.1 从静态映射到状态转移

静态基准可以写成 $y=f_\theta(x)$:输入 $x$ 固定,模型生成答案 $y$,评分函数 $g(y,y^*)$ 给出分数.Agent 的第 $t$ 步还依赖环境状态 $s_t$ 与历史轨迹 $h_t$:

$$
a_t\sim\pi_\theta(a\mid o_t,h_t),\qquad
s_{t+1}=T(s_t,a_t),\qquad
o_{t+1}=O(s_{t+1}).
$$

$a_t$ 是搜索、编辑、运行命令等动作,$T$ 是环境执行动作后的状态转移,$O$ 把可见结果返回给模型.轨迹可写为 $\tau=(o_1,a_1,o_2,a_2,\ldots,o_T)$.最终得分 $R(\tau,s_T)$ 由整条轨迹和终态决定.一次错误的目录切换看似很小,却可能让后续搜索全部落在错误位置;一次破坏依赖环境的安装命令,也会使原本正确的补丁无法验证.误差会沿状态转移积累.

这也解释了为什么「模型答对一道代码题」与「模型修好仓库里的缺陷」相差很远.前者常把相关函数与测试都放进上下文,后者先要求系统找出该看哪些文件.仓库探索、证据筛选、修改范围控制和测试反馈共同占用上下文与时间.真正被测的是在有限预算内闭合感知—行动—反馈循环的能力.

### 1.2 模型、脚手架与环境共同决定输出

一个可运行的 Agent 系统至少包含模型、脚手架和环境三层.模型生成判断与动作;脚手架负责把命令送给工具、截断或摘要历史、判断何时停止;环境提供仓库、依赖、终端、网络与评分测试.若把系统成功率记为 $p$,更合适的写法是

$$
p=p(M,S,E,B),
$$

其中 $M$ 表示模型,$S$ 表示脚手架,$E$ 表示环境,$B$ 表示步数、token、时间或费用预算.这个式子没有假设四项彼此独立.更强的模型可能更善于使用结构化工具,也可能因输出更长而更快耗尽预算;允许联网可能帮助安装依赖,也可能带来版本漂移.

比较底座模型时,应固定脚手架、环境和预算.比较完整产品时,模型与脚手架可以一起变化,但结论只能落在「整套系统」上.SWE-bench 官方排行榜把任意系统的结果与统一 mini-SWE-agent 环境下的 bash-only 结果分开,就是为了给两类问题各留一个清楚的口径.

### 1.3 成功率必须连同预算阅读

设共有 $N$ 个任务,任务 $i$ 独立运行 $K_i$ 次,第 $j$ 次是否成功记为 $z_{ij}\in\{0,1\}$.单次运行成功率可以按所有运行求平均:

$$
\hat p_{\text{run}}=\frac{\sum_i\sum_j z_{ij}}{\sum_i K_i}.
$$

如果产品允许同一任务多试几次,还可以报告 pass@$k$,即 $k$ 次里至少一次成功.在每次成功概率近似为 $p$ 且相互独立的理想条件下,其期望为 $1-(1-p)^k$.例如单次成功率 $p=0.3$,尝试三次后至少一次成功的概率是 $1-0.7^3=0.657$.这项提升消耗了约三倍推理资源,而且真实多次运行通常相关,所以不能拿 pass@3 与另一系统的 pass@1 直接排队.

预算还会改变策略.步数很紧时,Agent 倾向于尽早修改并运行少量测试;预算宽松时,它可以阅读更多调用关系、先复现缺陷、再跑回归测试.公平报告至少要给出最大步数、墙钟时间、模型调用次数、输入输出 token、重试次数和平均费用.只统一美元预算也不充分,因为不同模型的价格与速度会变化;保留多种资源统计更便于复算.

## 2. SWE-bench 怎样把真实修复变成评测

### 2.1 一条样本由 issue、基线提交与测试组成

[SWE-bench](https://arxiv.org/abs/2310.06770) 从真实 GitHub issue 及其对应修复中构造任务.原始集合含 2,294 个问题,来自 12 个 Python 仓库.每条样本提供仓库、基线提交、问题描述以及用于评估的测试补丁.系统拿到的是问题发生时的代码状态,需要生成一个可以应用的补丁.金标准补丁用于数据构建与分析,不能交给待测 Agent.

真实 issue 往往只描述用户看到的症状.一句「某个参数组合下返回值错误」可能涉及参数解析、内部表示、边界条件与文档约定.修复者要先复现问题,沿调用关系找到责任位置,再决定修改实现还是补充校验.这比补全一个孤立函数更接近日常维护,也带来了任务描述含糊、依赖过时和测试覆盖不足等数据质量问题.

SWE-bench Verified 从原始集合中人工核验 500 条样本,重点检查问题描述是否清楚、测试是否正确、给定信息能否支持求解.它提高了可解释性,但「人工确认可解」仍然不等于每个容器都能永久稳定运行.依赖下载、镜像构建和硬件差异仍需通过版本固定与运行日志管理.

### 2.2 FAIL_TO_PASS 与 PASS_TO_PASS 各管一件事

软件修复的评分不能只看新测试是否通过.设 $F_i$ 是任务 $i$ 中基线版本失败、正确补丁应通过的测试集合,$P_i$ 是原本通过且修改后仍应通过的回归测试集合.一个任务被判为 resolved,通常要求

$$
\forall t\in F_i,\ t(\text{patch})=\text{pass},
\qquad
\forall t\in P_i,\ t(\text{patch})=\text{pass}.
$$

第一项检查缺陷是否被修复,第二项检查旧行为有没有被破坏.若 Agent 直接删除断言、跳过测试或让异常路径不再执行,它可能让局部现象消失,却无法同时满足回归约束.最终 resolved rate 是成功任务数除以有效任务数.

这里有一个重要边界:测试通过只说明补丁满足当前测试集合.它不能证明修改在所有输入上正确,也不能证明代码质量、可维护性和安全性符合生产要求.隐藏测试提高了针对答案投机的难度,覆盖不全的问题仍然存在.因此 SWE-bench 很适合测量仓库级修复能力,却不能替代真正的代码审查与上线验证.

### 2.3 一条有效轨迹怎样展开

较稳的修复轨迹通常分为定位、复现、修改与验证四段.定位阶段先读 issue,查看仓库入口与相关符号,用搜索缩小文件范围.复现阶段运行与问题最接近的测试或构造最小例子,确认当前代码确实出现描述中的行为.修改阶段保持变更局部,同时检查相邻分支是否共享同一假设.验证阶段先跑目标测试,再跑相关模块或完整测试集.

例如问题报告说「空列表与显式默认值组合时序列化失败」.Agent 搜到三个同名函数后,不能凭名字挑一个直接改.它需要确认输入从公共 API 经过哪条路径到达序列化器,观察空列表在哪一步被当成假值丢弃,再检查 `None` 与空容器在接口语义上是否应当区分.修复一行条件判断以后,目标测试通过只是第一步;若旧代码依赖相反语义,回归测试会暴露影响.

轨迹质量可以用中间信号观察:首次找到相关文件用了多少步,修改前是否复现,补丁触及多少文件,测试失败后是否读取了完整错误栈,是否反复执行相同命令.这些信号有助于诊断,却不宜随意合成一个新的总分.权重一旦缺乏任务语义支撑,系统可能学会优化漂亮轨迹,反而牺牲最终正确性.

## 3. CyBench 怎样测量网络安全任务

### 3.1 CTF 环境把推理放进可执行回路

[CyBench](https://arxiv.org/abs/2408.08926) 收集了 4 场 CTF 竞赛中的 40 个专业任务,覆盖多种难度.每个任务带有描述、起始文件和可执行环境,Agent 能运行命令并读取输出,目标是找到 flag.论文还为每个完整任务设计了若干子任务,让评估者看到系统走到了攻击链的哪一步.

CTF 的价值在于结果容易核验:提交的字符串是否为正确 flag.困难来自求解路径很长.一道题可能先要求识别文件格式,再发现解析器缺陷,构造输入,启动服务,观察崩溃信息,逐步调整 payload.某一步得到的新地址、密钥材料或协议响应会成为下一步输入,所以单轮问答无法还原这种能力.

CyBench 原论文比较了多种模型,并针对较强模型考察 structured bash、action-only、伪终端与网页搜索等脚手架.这组实验提醒我们:终端怎样呈现、动作怎样解析、能否搜索资料,都属于实验变量.论文中的若干系统在无子任务提示时,解决了人类队伍首次解题时间不超过 11 分钟的完整任务;任务集中最难一题的人类首次解题时间为 24 小时 54 分钟.这组结果反映出当时系统能够完成的难度区间,不能脱离模型、脚手架和运行预算单独使用.

### 3.2 子任务分数用于定位能力缺口

完整任务得分非常稀疏.一个 Agent 已经找到漏洞入口,却在编码 payload 时差一个字节,最终得分仍为零.子任务把长链条分成可核验节点,例如识别脆弱组件、恢复关键常量、构造利用输入和取得 flag.若任务 $i$ 有 $m_i$ 个子任务,可记录

$$
q_i=\frac{1}{m_i}\sum_{r=1}^{m_i} c_{ir},\qquad c_{ir}\in\{0,1\}.
$$

$q_i$ 描述过程进展,完整成功指标仍由最终 flag 决定.两者应并列报告.只用子任务平均分,可能奖励会解释步骤却无法完成攻击链的系统;只用最终成功率,又看不出模型卡在知识识别、工具操作还是长程纠错.

给出子任务提示还会改变任务本身.提示「先检查某种编码」相当于替 Agent 完成一次搜索空间压缩.因此有提示与无提示结果分别回答不同问题:前者更接近在明确操作清单下执行,后者更接近自主发现路径.二者的数据不能混成同一列.

### 3.3 安全能力需要受控环境和明确权限

网络安全评测具有双重用途.能发现与利用漏洞的系统可以辅助防守,也可能被滥用.实验环境应隔离目标、限制网络边界、记录命令并规定允许的工具.这些限制除了安全作用,还保证任务可复现.如果某次运行能访问公开解题文章,另一次只能访问本地文件,分数已经失去可比性.

环境隔离也影响测量本身.禁网会切断查手册与安装工具的常见工作流;完全开放网络又可能泄漏答案或让外部服务变化进入结果.合理做法是把访问策略写入协议,对允许的镜像、软件包与网页快照做版本管理.评估报告应说明模型面对的是裸终端、预装工具集还是带搜索功能的工作台.

CTF 成功不等于现实攻击能力.真实系统包含社会流程、资产发现、防护设备和法律授权,失败代价也不同.CyBench 测到的是受控任务上的一组技术能力.它可以作为风险评估的一部分,不宜单独推导现实世界中的攻击发生率.

## 4. 怎样比较两个 Agent 系统

### 4.1 先固定协议,再解释差值

一份可复现实验配置应写明数据集版本、任务筛选规则、容器镜像、模型版本、提示词、工具 schema、温度、最大上下文、每任务步数、超时、网络权限、重试次数与停止条件.软件基准还要记录补丁应用方式和测试命令;安全基准要记录目标服务初始化与 flag 校验方式.

假设系统 A 在 500 个 Verified 任务上解决 250 个,系统 B 解决 260 个.表面差值是 2 个百分点.若两者测试的任务集合不同,这个差值没有解释价值;若集合相同,应做逐任务配对.记 $n_{01}$ 为 A 失败而 B 成功的任务数,$n_{10}$ 为 A 成功而 B 失败的任务数.McNemar 检验关注二者是否明显不对称,而不把两组结果误当成互不相关样本.

更直观的报告会列出净新增成功数 $n_{01}-n_{10}$,再按仓库、任务类型与难度切片.若 B 的提升全部来自某一个仓库,原因可能是提示词适配了该仓库的测试布局;若多个仓库都稳定改善,结论才更有外推价值.

### 4.2 随机性需要多次运行与置信区间

温度设为零也不保证 Agent 轨迹完全确定.服务端并行、工具输出顺序、依赖下载和模型实现更新都可能引入差异.对高方差系统,每个任务运行多次能估计稳定性.如果预算有限,可以先对全部任务跑一次,再对分歧大或具有代表性的子集增加重复次数,但需要公开抽样规则.

对于 $N$ 个任务的一次二值结果,可用任务级 bootstrap 估计成功率区间:有放回抽取 $N$ 个任务,重新计算 resolved rate,重复很多次后取分位数.若每题运行多次,重采样应保留任务层级,避免把同一任务的多条强相关轨迹当成独立样本.比较两个系统时,每次 bootstrap 都对相同任务索引成对抽样,可以利用配对信息缩小不确定性.

置信区间表达的是这套抽样与运行协议下的波动,不自动覆盖数据污染、评分器缺陷或环境迁移.统计误差很小,系统误差仍可能很大.所以数字旁边还需要失败抽查和环境健康检查.

### 4.3 成本、时延与成功率应放在同一张表

Agent 可以用更多采样、更多审阅器和更长轨迹换取成功率.只按成功率排名,会鼓励无限增加测试时计算.实用比较可以报告每任务平均费用 $C$、平均墙钟时间 $L$、成功率 $p$ 和成功任务的条件成本.如果一次运行失败也花钱,每个成功任务的粗略期望成本可写为

$$
C_{\text{success}}\approx\frac{C}{p}.
$$

例如系统 A 每题平均 1 元,成功率 0.25,得到一个成功任务约需 4 元;系统 B 每题 2 元,成功率 0.4,对应约 5 元.B 的能力更强,A 的单位成功成本更低.业务选择取决于失败代价和时限,二者没有必要压成一个不透明的综合分.

还要观察长尾.平均时延相同的两个系统,可能一个大多数任务很快、少数任务极慢,另一个分布集中.部署环境中的并发与超时会让尾延迟直接影响可用性.报告中加入中位数、P90、P95 以及因超时终止的比例,比只给平均值更可靠.

## 5. 从总分回到失败轨迹

### 5.1 失败分类要对应可修改的环节

SWE-bench 的失败可以分为任务理解、定位、修改、验证与环境五类.理解失败表现为误读 issue 或忽略约束;定位失败表现为始终搜索错误模块;修改失败包括补丁语义错误或影响范围过大;验证失败包括没有运行关键测试、误读错误栈;环境失败则来自镜像、依赖或工具故障.CyBench 还会出现漏洞类型判断错误、利用链中断与目标状态丢失.

分类应依据轨迹证据.看到最终补丁错误,不能直接归因于模型推理差;若测试命令从未真正执行,更直接的问题可能是工具协议.同一条轨迹可以有一个主要原因和若干伴随因素,但分类表要有稳定定义,否则不同标注者会把相似失败放进不同桶.

失败类别的价值在于指导下一次实验.定位错误多,可以改进仓库搜索与上下文选择;正确补丁经常因格式无法应用,应检查编辑工具;任务已完成却继续修改到失败,需要改停止策略.总分告诉我们系统是否进步,失败分布告诉我们从哪里动手.

### 5.2 环境错误应与能力失败分开

若基础镜像构建失败、依赖源不可达或测试框架自身崩溃,这次运行没有形成有效的能力观测.把它直接记作模型失败会低估系统,把它删除又可能挑选性美化结果.稳妥的报告同时给出总任务数、有效运行数、环境无效数及其原因,并预先规定何时重跑.

可以为每次运行记录环境健康向量:容器是否启动、基线测试是否符合预期、Agent 补丁是否能应用、评分测试是否完成.只有前置检查通过,最终失败才适合进入能力统计.若 Agent 自己破坏了环境,例如删除依赖或终止关键服务,这仍属于系统行为造成的失败,不能归入基础设施故障.

版本漂移同样需要防范.同一仓库的依赖解析结果在半年后可能改变,外部 API 也可能下线.容器镜像摘要、依赖锁文件、评测框架提交号与模型快照标识共同构成复现实验的坐标.少一个坐标,后续复跑出现差异时就很难定位来源.

### 5.3 一份可用的结果报告应留下什么

最小结果包包括实验配置、逐任务预测、最终补丁或 flag 判定、完整轨迹、资源用量、评分日志和聚合脚本.公开排行榜至少应让读者知道哪些结果由组织自报,哪些经过基准维护者复核.对于无法公开的安全轨迹,也应保留内部审计副本与经过脱敏的错误分类.

阅读 Agent 基准时,可以依次问五个问题.第一,任务是否代表目标场景;第二,系统获得了哪些工具和信息;第三,预算是否一致;第四,评分器能否区分修复、投机与环境故障;第五,差异在多少任务和多少次运行上稳定出现.这五个问题回答完整以后,排行榜才开始具有技术含义.

**Agent 评测的基本单位是「系统在固定协议下完成一次任务」.** 模型名称只是系统配置中的一项.SWE-bench 用可执行测试约束代码修复,CyBench 用 flag 与子任务观察安全任务的完成过程;两者都说明,长程能力需要通过动作、反馈和终态共同测量.

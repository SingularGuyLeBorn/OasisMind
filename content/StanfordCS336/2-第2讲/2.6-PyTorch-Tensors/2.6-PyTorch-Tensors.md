# PyTorch Tensor: Storage、Stride 与 Autograd 边界

PyTorch Tensor 是一段存储及其解释方式.逻辑上的多维数组不要求按同样形状物理排列;Tensor 元数据用 dtype、device、shape、stride 和 storage offset 把索引映射到底层元素.转置、切片与广播能否避免复制,都由这套映射决定.

## Storage、shape、stride 与 offset

### 索引公式

对 $n$ 维 Tensor,逻辑索引 $(i_0,\ldots,i_{n-1})$ 对应 storage 元素位置

$$
o+\sum_{k=0}^{n-1}i_ks_k,
$$

$o$ 是 `storage_offset()`,$s_k$ 是第 $k$ 维 stride.shape 只限制每个 $i_k$ 的范围,不说明元素是否相邻.dtype 决定每个元素字节数;stride 的单位是元素,不是字节.

取 `x = torch.arange(12).reshape(3, 4)`.storage 元素为 0 到 11,shape 是 $(3,4)$,stride 是 $(4,1)$,offset 为 0.`x[2,1]` 对应 $0+2\times4+1\times1=9$.

切片 `y=x[1:,1:3]` 的 shape 是 $(2,2)$,stride 仍是 $(4,1)$,offset 变为 5.`y[1,1]` 映射到 $5+1\times4+1=10$.y 的四个元素在 storage 中位于 5、6、9、10,逻辑矩形不是一段连续内存.

**转置只交换元数据**

`z=x.transpose(0,1)` 的 shape 为 $(4,3)$,stride 为 $(1,4)$,offset 不变.`z[2,1]` 对应 $0+2\times1+1\times4=6$,与 `x[1,2]` 相同.z 与 x 共享 storage;写入 z 会从同一位置被 x 观察到.

共享 storage 只表示存在内存别名,不表示两个 Tensor 的逻辑索引相同.判断别名可比较 `untyped_storage().data_ptr()` 并结合 offset/范围;两个切片还可能共享同一 storage 但覆盖区域不重叠.

**Contiguous 与 memory format**

**连续性的判定**

标准 row-major 连续 Tensor 从最后一维开始满足 stride 递推.忽略 size 为 1 的维度,最后有效维 stride 为 1,前一维 stride 等于后一维 stride 乘其 size.`x` 的 $(4,1)$ 满足,转置 z 的 $(1,4)$ 不满足标准连续格式.

`is_contiguous()` 判断特定 memory format.`contiguous()` 若已满足目标格式可返回自身或别名;否则分配新 storage 并按逻辑顺序复制.它不是无条件复制操作.调用后应把返回值用于后续计算,只写 `x.contiguous()` 而丢弃结果不会改变 x.

**channels_last**

四维图像常用逻辑 shape NCHW,但可采用 channels-last 物理布局.此时 `is_contiguous(memory_format=torch.channels_last)` 可能为真,普通 `is_contiguous()` 为假.卷积 kernel 可从这种布局受益;把所有非标准 stride 都强制转成 row-major 可能引入多余复制并破坏布局优化.

memory format 描述布局,shape 语义仍由算子约定.NCHW Tensor 转成 channels-last 后索引 `x[n,c,h,w]` 不变,只改变地址映射.与外部库交换数据时要同时确认逻辑轴顺序和物理 layout.

**View、reshape 与复制**

**view 的条件**

`view()` 要求新 shape 能用原 storage 与一组合法 stride 表示.连续 Tensor 通常可以任意合并、拆分相邻维;转置后相邻逻辑元素在 storage 中跳跃,很多 flatten view 无法表示,此时 `view(-1)` 报错.

size 为 1 的维度较特殊,其 stride 对地址集合没有影响;`squeeze`、`unsqueeze` 通常只改元数据.切片步长大于 1 仍可形成 view,例如 `x[:, ::2]`,但后续能否继续 view 取决于 stride 关系.

### reshape 不保证别名

`reshape()` 尝试返回 view;无法仅改元数据时会复制到兼容布局.因此调用方不能依赖 reshape 一定共享或一定复制.需要明确共享时用 `view()` 并接受失败;需要独立数据时用 `clone()`;只关心结果 shape 时用 reshape.

`flatten()`、`ravel()` 等 API 也有各自复制语义,应以文档和别名测试为准.性能敏感路径可比较 `data_ptr`、检查 profiler 中的 copy kernel,不能凭函数名猜测.

**clone 与 detach**

`clone()` 分配新 storage 并复制数值,默认保留 autograd 关系,其 backward 把梯度传回源 Tensor.`detach()` 与源 Tensor 共享 storage,但切断梯度图;对 detached Tensor 原地写入仍可能改动源数据.`detach().clone()` 同时切图和复制,适合需要独立快照的场景.

**广播与零 stride**

**expand 怎样复用一个元素**

设 `a=torch.tensor([[1],[2],[3]])`,shape 为 $(3,1)$.`b=a.expand(3,4)` 的 shape 为 $(3,4)$,stride 可为 $(1,0)$.第二维索引变化乘以 0,所以一行四列都指向同一个 storage 元素.广播没有复制数据.

零 stride 意味着多个逻辑位置别名同一地址.对 b 做逐元素原地写入含歧义:不同逻辑元素可能试图给同一地址写不同值.PyTorch 会拒绝许多此类操作.若确实需要独立可写矩阵,使用 `expand(...).clone()` 或 `repeat`,后者显式复制.

**广播算子的输出**

输入广播可零复制,算术输出通常是新分配 Tensor.例如 $[B,1,d]+[1,T,d]$ 在 kernel 中按广播索引读取两边,输出为 $[B,T,d]$ 并占据完整存储.不能因为输入 `expand` 不复制就认为整个操作不增加显存.

反向传播会沿广播维求和.若参数 bias shape 为 $[d]$ 被广播到 $[B,T,d]$,其梯度是上游梯度沿 B、T 两维 reduce.这解释了线性层 bias 梯度为何按 token 求和.

**基本索引与高级索引**

**哪些索引通常返回 view**

整数、slice、ellipsis 与 `None` 组成的基本索引通常返回 view,只调整 offset、shape 与 stride.`x[1]` 去掉一维,`x[:,1:3]` 改范围,`x[::2]` 增大 stride.

布尔 mask、整数 Tensor 或列表属于高级索引,通常收集元素到新 storage.例如 `x[[0,2]]` 复制两行;修改结果不会回写 x.但赋值语句 `x[[0,2]]=v` 由索引写 kernel 直接修改 x,不能用右值高级索引的复制语义推断赋值.

**重复索引**

高级索引写入含重复位置时,普通赋值的最终值可能依赖执行顺序.`index_add_`、`scatter_add_` 表达累加语义,在 GPU 上还可能因原子操作顺序产生浮点非确定性.Embedding backward 对重复 token ID 也需要把多次贡献累加到同一行.

## Autograd、版本计数与原地操作

### 保存张量为什么怕修改

反向公式可能保存前向输入或输出.每个 Tensor 维护版本计数,原地修改会递增版本.若 backward 发现所需张量版本变化,会报「variable needed for gradient computation has been modified in-place」,避免静默使用错误数值.

并非所有原地操作都报错:若反向公式不需要被改值,或操作发生在不记录梯度的 Tensor 上,可能允许.不能把「某次运行没报错」当作普遍安全,应根据计算图与保存内容判断.

叶子 Parameter 且 `requires_grad=True` 通常禁止直接原地更新.优化器在 `torch.no_grad()` 语境更新参数,避免把 update 本身接入下一轮计算图.使用 `.data` 绕过检查可能破坏版本与 autograd 假设,不应用作常规更新方式.

**view 的原地修改**

view 与 base 共享 storage,原地修改 view 会改变 base 并更新版本.若 base 或其他 view 被 backward 保存,同样可能触发版本错误.复杂链路中可通过 `tensor._version` 做调试,但业务逻辑不应依赖私有属性.

in-place 不必然更省显存.autograd 为正确反向可能保存副本,编译器也可能因为别名和副作用无法融合.是否收益需要 profiler 验证.

**dtype 与数值转换**

**element size 与存储**

`element_size()` 给每元素字节数,理论数据字节为 `numel()*element_size()`.view 共享 storage 时不能把每个 Tensor 的理论字节简单相加.切片只引用大 storage 的一小部分,只要 view 存活,整个 storage 可能无法释放.

`.to(dtype)` 在 dtype 已相同时可以返回自身,不同时通常分配并转换.整数转浮点、FP32 转 BF16 都会改变数值表示.默认 dtype、类型提升和 autocast 会影响算子输出 dtype,应在关键边界打印而非假设.

**类型提升**

两个不同 dtype Tensor 运算按 promotion 规则选择结果类型;标量参与时还有 wrapped scalar 规则.归约可能采用比输入更高的累加精度,具体由算子决定.混合精度训练中参数 dtype、计算 dtype、累加 dtype 和 optimizer state dtype 是四个不同概念.

**Device 与异步执行**

### CPU/GPU Tensor

Tensor 运算通常要求参与者位于兼容 device.CPU Tensor 与 CUDA Tensor 不能直接做普通加法.`to(device)` 可能分配并传输;目标 device 和 dtype 都相同且 `copy=False` 时可返回原 Tensor.

CUDA kernel launch 对 CPU 异步.测量代码若只围住 Python 调用,得到的是提交时间.准确计时使用 CUDA Event 或在边界同步;频繁 `torch.cuda.synchronize()` 会破坏流水,只用于测量和调试.

某些操作会隐式同步,如把 CUDA 标量 `.item()` 取回 CPU、打印需要的数据或执行依赖 GPU 结果的 CPU 分支.训练循环中频繁读取 loss 标量可能引入同步点.

**pinned memory 与 non_blocking**

页锁定(pinned)CPU 内存允许 DMA 更高效地传输到 GPU.`DataLoader(pin_memory=True)` 可让返回 batch 进入 pinned buffer.调用 `.to("cuda", non_blocking=True)` 在源为 pinned 且条件满足时允许传输与 CPU 继续执行或与 GPU 计算重叠.

`non_blocking=True` 不保证实际重叠.需要独立 CUDA stream、硬件 copy engine、正确依赖与足够大的传输;随后立即在默认 stream 使用数据会建立必要等待.过度 pin 内存会压缩操作系统可分页内存,不是越多越好.

GPU 到 CPU 的异步复制还涉及结果何时可读.在传输完成前访问目标 CPU buffer 会得到未定义时序,必须通过 stream/event 同步.高层 `.cpu()` 常提供安全语义但可能阻塞.

**内存别名与生命周期**

**小 view 留住大 storage**

从巨大 Tensor 切出一个很小 view 后删除 base,view 仍引用原 storage,显存不会按 view 的 numel 释放.若需要长期保存小片段,`clone()` 可复制到独立小 storage,让大块可回收.是否值得复制取决于片段寿命和大块大小.

Python 对象释放不等于 CUDA 显存立即归还操作系统.PyTorch caching allocator 会保留空闲块供后续复用.`memory_allocated` 与 `memory_reserved` 含义不同;`empty_cache()` 只释放未占用缓存块,不会释放仍被 Tensor 引用的 storage.

**重叠 view**

`as_strided` 能手工构造任意 shape/stride/offset,包括多个逻辑元素重叠同一地址或越界风险.它是实现滑窗 view 等技巧的底层接口,错误参数会产生难以检查的别名.对重叠 view 原地写入通常没有明确顺序.

`unfold` 可用 stride 生成滑动窗口 view,相邻窗口共享元素.读取很方便,写入时同一原元素可能对应多个窗口位置.卷积 im2col 是否真实展开由 kernel 实现决定,不能从概念图推断一定分配巨大矩阵.

### 与编译器和 kernel 的关系

非连续 Tensor 不必先 contiguous 才能计算.很多 elementwise kernel 支持任意 stride,矩阵乘法库也支持部分转置布局.复制是否发生取决于算子约束和后端.盲目加 `.contiguous()` 可能引入额外 HBM 读写.

另一方面,合法的任意 stride 不代表性能相同.连续、合并访问有利于内存吞吐;转置或大步长访问可能降低 cache 与 coalescing 效率.Profiler 中应查看 copy kernel、实际算子与输入 stride.

`torch.compile` 会做 functionalization,尝试把原地操作转换为无副作用形式,并根据别名关系规划融合.动态 shape、数据依赖索引和复杂别名会增加图捕获难度.写清 shape 与副作用也有利于编译器优化.

## 一组可运行测试

### 地址与 stride

```python
import torch

x = torch.arange(12).reshape(3, 4)
y = x[1:, 1:3]
assert y.shape == (2, 2)
assert y.stride() == (4, 1)
assert y.storage_offset() == 5
assert y[1, 1].item() == 10
assert x.untyped_storage().data_ptr() == y.untyped_storage().data_ptr()
```

`x.T.reshape(-1)` 是否复制取决于当前实现与布局. 测试只断言数值顺序,同时记录 data pointer,用于观察所用 PyTorch 版本是否分配了新存储.

**广播与 autograd**

```python
a = torch.arange(3., requires_grad=True).reshape(3, 1)
b = a.expand(3, 4)
assert b.stride()[1] == 0
loss = b.sum()
loss.backward()
assert torch.equal(a.grad if a.is_leaf else a._base.grad,
                   torch.full((3,), 4.0))
```

实际测试最好保留原始 leaf 引用,避免 reshape 后读取非叶子 `.grad`.广播四列使每个源元素梯度累加四次.

**复制与设备**

对 `clone`、高级索引、`contiguous` 和 dtype 转换分别比较 data pointer;对 view 操作修改一个元素并确认 base 的可见变化.设备测试用 CUDA Event 测拷贝与 kernel,对 pinned/non-pinned、blocking/non-blocking 组合分别记录时间.

**排查顺序**

数值错误先打印 shape、dtype、device、stride、offset 和是否 contiguous;怀疑别名时检查 storage pointer 与覆盖区间;autograd 报版本错误时定位哪次原地操作修改了保存张量;显存异常时区分 allocated、reserved、激活与被小 view 留住的大 storage.

性能问题先确认 profiler 是否出现隐式 copy,再看非连续访问是否降低 kernel 吞吐.跨设备时间必须排除异步计时误差.这些检查把 Tensor 的逻辑值、物理布局、梯度关系与执行时序分开,避免用一次 `.contiguous()` 或 `.clone()` 掩盖真正原因.

Tensor 的关键不在 API 数量,而在四个问题:索引映射到哪个地址,多个对象是否共享该地址,反向需要保留哪个版本,数据何时在哪个设备可用.每次 shape 变换和传输都能回答这四点,复杂训练代码的内存与正确性就有可追踪的边界.

**更复杂的 stride 手算**

### 步进切片与翻转

对 shape $(4,6)$、stride $(6,1)$ 的 x,切片 `x[1:4:2, ::2]` 选原行 1、3 与列 0、2、4.结果 shape $(2,3)$,offset 为 6,stride 为 $(12,2)$.位置 `[1,2]` 地址是 $6+1\times12+2\times2=22$,对应原 `x[3,4]`.

PyTorch 常不支持普通 Tensor 的负 stride,某些翻转操作因此返回复制而非用负 stride view.不能把 NumPy 的负 stride 行为直接套到 PyTorch.是否共享 storage 用实际 API 契约与 pointer 测试确认.

窄化 `narrow`、对角线 `diagonal` 和 `select` 可以产生非连续 view.对角线 stride 是原两个维 stride 之和;例如连续 $4\times4$ 矩阵 stride $(4,1)$,主对角线 stride 为 5.这仍是合法一维 view,但元素在 storage 中不相邻.

**重叠判定**

零 stride expand 明确存在内部重叠,`as_strided` 也能构造部分重叠.重叠 Tensor 的读取有定义,写入常有歧义.某些 debug API 能检查 internal overlap,但生产逻辑应由构造方式保证.

两个不同 Tensor 之间的重叠更难仅从 data pointer 判断.需要考虑 storage offset、shape、stride 覆盖的地址集合.保守做法是在会原地写入且来源不明时先 clone;性能路径则建立明确的不别名约定,而不是每次运行昂贵检查.

**Autograd 中 leaf、grad_fn 与 retain_grad**

**叶子 Tensor**

用户直接创建且 `requires_grad=True` 的 Tensor 通常是 leaf,其 `.grad` 在 backward 后累积.运算结果具有 `grad_fn`,默认不保留 `.grad`,因为反向只需要把上游梯度继续传播.调试中要查看中间梯度,调用 `retain_grad()`.

`a=torch.arange(3.,requires_grad=True)` 是 leaf,`b=a.reshape(3,1)` 是 view 且通常非 leaf.对 `b.sum().backward()` 后应读 `a.grad`.把变量名覆盖成 b 容易误以为梯度丢失.

调用 `requires_grad_()` 对无历史 Tensor 开启梯度可形成 leaf;对已有图中的结果不会自动切断历史.需要新叶子时通常使用 `x.detach().requires_grad_()`,但它与 x 共享 storage;若还需独立数据,加 clone.

### backward 与 grad

`loss.backward()` 把梯度累积到图中叶子;`torch.autograd.grad` 返回指定输入梯度,默认不写入 `.grad`.高阶梯度需要 `create_graph=True`,会保留梯度计算本身的图并增加显存.

第二次通过同一图 backward 通常需要 `retain_graph=True`,因为第一次会释放中间保存张量.训练循环不应常态保留整图;若跨 step 意外引用带 `grad_fn` 的 loss 或 hidden,图会不断增长,造成显存泄漏.日志保存标量应使用 `detach()` 或 `.item()` 并理解后者可能同步 GPU.

## dtype、view 与 reinterpretation

### 数值转换和按位解释

`x.to(torch.float16)` 做数值转换,元素个数不变,storage 通常重新分配.`view(dtype)` 的某些重载则按位重新解释数据,会受最后维 stride、offset 对齐和元素字节比限制.两者语义完全不同.

从 FP32 转 BF16 会舍去尾数精度;转回 FP32 只能扩展表示,不能恢复丢失位.整数超出目标 dtype 范围时也会截断或环绕,数据预处理需要显式检查范围.

`torch.set_default_dtype` 影响某些 Python 浮点输入的推断,不改变已有 Tensor.模型参数 dtype、输入 dtype 与 autocast 计算 dtype 应在模块边界明确,避免一次隐式 promotion 把大 Tensor 升到 FP32.

**复数 Tensor**

复数 Tensor 的 `view_as_real` 可把最后一维扩成实部/虚部,通常共享 storage;其 stride 和对齐有额外约束.共轭 view 可能带 conjugate bit,读取时逻辑共轭而不立即复制.调用需要真实物理值的算子时可能 resolve 并复制.

这类惰性元数据说明 Tensor 值不只由 storage 字节和普通 stride 决定,还可能含 conjugate/negative 等标志.常规 LLM 训练少用复数,但理解这一点能避免把所有 view 简化成 shape+stride 两项.

**跨框架共享**

**NumPy 与 CPU**

CPU Tensor 在满足 dtype/layout 条件时可与 NumPy array 共享内存.`torch.from_numpy` 通常共享底层 buffer,一方写入会被另一方看到;只读 NumPy 数组转 Tensor 后写入可能产生未定义行为警告.`tensor.numpy()` 对 requires-grad、device 与共轭状态也有限制.

若需要隔离生命周期和写入,显式 copy/clone.共享 buffer 时,持有任一对象通常会延长底层内存寿命.跨库边界应测试别名,不能默认转换函数都复制.

**DLPack**

DLPack 可在支持的框架间交换设备 Tensor,避免经过 CPU 复制.共享的是数据与布局描述,同步和所有权遵循 DLPack 协议.生产者在消费者使用期间不能释放或重用内存;stream 依赖也必须正确传递.

零复制交换节省带宽,也把别名风险带过边界.消费者原地修改可能改变生产者所见数据,autograd 图通常不会跨框架自动连接.需要梯度时必须由自定义 autograd Function 明确前反向协议.

**CUDA allocator 与 stream 语义**

### 缓存分配器

CUDA malloc/free 代价较高,PyTorch 用 caching allocator 复用块.Tensor 释放后 `memory_allocated()` 下降,`memory_reserved()` 可能不降.后续相近大小分配可直接复用.碎片会让总空闲字节足够却找不到合适连续块.

峰值测量可在实验前 reset peak stats,在关键阶段读取 max allocated/reserved.异步 kernel 尚未完成时,allocator 还要保证旧数据不被过早复用;stream 记录参与生命周期管理.

`empty_cache()` 把未占用缓存交还驱动,不能释放活 Tensor,频繁调用还会失去复用收益.排查 OOM 应先找持有引用、激活峰值和碎片来源.

**多 stream**

Tensor 在一个 stream 产生、另一个 stream 消费时需要 event 依赖.默认 stream 与非默认 stream 的隐式关系取决于 API;自定义 pipeline 要显式 `wait_stream` 或 event.allocator 还可能需要 `record_stream(tensor, stream)` 知道非默认 stream 仍在使用该内存.

缺少依赖的错误具有时序性,小负载可能碰巧正常,并发后出现旧值或内存被复用.测试应在多轮、不同尺寸和压力下运行,并借助同步缩小范围;最终实现不能靠全局 synchronize 掩盖缺失依赖.

**模型代码中的典型路径**

**Attention reshape**

线性投影输出常为 `[B,T,H*d_h]`,先 view 成 `[B,T,H,d_h]`,再 transpose 为 `[B,H,T,d_h]`.transpose 后通常非标准 contiguous,但 attention kernel 可以直接接受特定 stride.输出反向 transpose 后若要合并 H 与 $d_h$,两维在当前布局未必可 view,可能需要 contiguous 或 reshape.

这条路径里一次无意识复制的大小为 $BTHd_h$,每层都会发生.高性能实现会选择 kernel 支持的布局,或让投影直接写入目标布局.优化前用 profiler 确认 copy 位置.

**词表 logits**

hidden `[B,T,d]` 与权重 `[V,d]` 相乘得到 logits `[B,T,V]`,通常是新大 Tensor.只评估最后位置时,先切 `hidden[:,-1:]` 再投影可避免完整词表输出;训练需要所有标签位置,不能这样省略.

交叉熵 fused kernel 可避免额外保存完整 softmax 概率,但 logits 或分块统计仍有成本.张量 shape 选择直接决定中间内存,view 技巧无法消除数学上必须产生的输出维度.

### 更完整的测试清单

为每个 shape 操作记录输入/输出 shape、stride、offset、data pointer 和 `_base`;用数值修改验证预期别名.对可能复制的 API 不把当前实现当永久契约,只依赖官方保证.对高级索引、expand、transpose、reshape、clone 分别设置测试.

autograd 测试覆盖 view 后反向、广播 reduce、重复索引累加、原地版本错误与 detach 别名.设备测试覆盖 pinned H2D、非阻塞 stream 依赖和计时同步.布局测试同时检查 row-major 与 channels-last.

对照测试还要覆盖空 Tensor 与 size 为 1 的维度.它们的 stride 可能有多种等价表示,不能用某个固定 stride 元组判断数值正确性.应验证索引范围、numel、输出数值与是否发生预期复制.

这些测试用于确认每次别名、复制、布局和同步都符合预期。非连续 view 往往比无条件复制更省资源；只有独立生命周期或 kernel 约束明确要求时才执行复制.

## 一次显存问题走查

假设 Attention 输出转置后调用 reshape,训练峰值突然增加.第一步打印转置前后 stride,确认 reshape 是否因无法 view 而复制.第二步在 profiler 中查找 `copy_` 或 contiguous kernel,并记录复制 Tensor 的 shape 与 dtype.第三步检查该副本是否被 autograd 保存到反向结束;即使复制 kernel 很短,长生命周期也会抬高峰值.

若只需把布局交给下游算子,优先确认下游能否接受当前 stride.若必须连续,把复制安排在唯一明确边界,避免多个模块各自调用 contiguous.若副本仅供不需梯度的日志或缓存,使用 detach 后再决定是否 clone,并明确生命周期.

另一个常见现象是删除大 Tensor 后显存数字不降.先检查是否有切片 view、闭包、日志列表或计算图仍持有 storage,再区分 allocated 与 reserved.若 allocated 已降而 reserved 保持,说明缓存分配器在保留可复用块,不代表仍有活 Tensor 占用.

这套走查从地址映射、别名、autograd 保存和 allocator 四层定位,每层都有可观察量.直接插入 clone 或 empty_cache 可能改变症状,却无法说明原 storage 为什么仍存活.修复后应保留峰值断言和别名测试,防止布局调整重新引入同类复制与引用链.

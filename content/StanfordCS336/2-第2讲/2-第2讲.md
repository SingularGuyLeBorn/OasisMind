# 第2讲: 从张量布局到一次完整更新

第一讲确定了 token 序列、训练目标与验证口径, 第二讲开始回答实现层的问题: 一批 token 进入 GPU 后, 哪些张量长期驻留, 哪些只在前向或反向阶段存在, 矩阵乘法消耗多少 FLOPs, 梯度怎样产生, 优化器为什么还要保存额外状态, 低精度计算又怎样在吞吐与稳定性之间取舍. 这些问题最终汇合到一次参数更新中, 任何一个环节估算错误, 都可能让模型无法装入显存、训练速度远低于硬件能力, 或在数值溢出后产生无效结果.

[主讲义](./2.1-主讲义/2.1-主讲义.md)使用 PyTorch 串起整个过程, 其余六篇子文分别展开浮点格式、反向传播成本、混合精度、优化器状态、张量布局和因果注意力. 它们并非七个互不相干的 API 主题. dtype 决定每个元素的字节数与动态范围; size、stride 和 storage 决定算子怎样访问这些元素; 前向图决定反向需要保存哪些激活; 优化器决定参数之外还要驻留多少状态; 混合精度则给不同阶段分配不同 dtype. **资源核算必须按完整训练步进行, 只计算模型权重远远不够.**

## 1. 先拆分内存占用

### 1.1 浮点格式决定容量和数值边界

[Floating Point Representations](./2.2-Floating-Point-Representations/2.2-Floating-Point-Representations.md)比较 FP32、FP16、BF16 与 FP8. 浮点数把有限位宽分给符号、指数和尾数. 指数位主要决定动态范围, 尾数位主要决定相对精度. FP16 相比 FP32 减半存储, 但指数范围小, 小梯度容易下溢, 大值也可能上溢. BF16 保留与 FP32 相同宽度的指数部分, 以更少的尾数位换取较大的动态范围, 因而更适合许多现代训练硬件上的矩阵计算.

dtype 选择不能只看“每个元素占几字节”. 参数更新会在很多步中累积小变化, 优化器的一阶矩和二阶矩也需要稳定累计. 即便矩阵乘法使用 BF16, 主权重或优化器状态仍可能保留 FP32. FP8 进一步降低存储和带宽, 同时需要更严格的缩放、算子支持和范围管理. 一个模型标注为“BF16 训练”, 不代表内存中的每个张量都是 BF16.

主讲义中的粗略显存估算由此展开. 参数、梯度、主权重、优化器状态和激活必须分别计算. 前四项通常随参数量增长, 激活还依赖 batch size、序列长度、层数、hidden size 以及是否重计算. 仅用 GPU 容量除以权重字节数, 只能得到没有训练状态时的上界, 不能作为可训练规模.

### 1.2 Tensor 是 storage 加元数据

[PyTorch Tensors](./2.6-PyTorch-Tensors/2.6-PyTorch-Tensors.md)说明 Tensor 的核心组成: 底层 storage、size、stride 和 storage offset. 多维索引最终会通过 stride 映射到一维存储地址. 转置和切片通常只改变元数据, 新 Tensor 可以与原 Tensor 共享 storage; 逐元素计算、`clone()` 或必要的 `contiguous()` 则会分配并复制数据.

这种区分同时影响正确性和性能. 修改一个 view 的底层元素会影响所有共享 storage 的 Tensor. 转置后的 Tensor 往往 non-contiguous, 某些布局变换无法只靠 stride 表示, `view()` 会拒绝该输入; `reshape()` 可能返回 view, 也可能隐式产生副本. 因而看到相同 shape 并不能断定两段代码具有相同内存行为.

GPU kernel 的访存效率也受布局影响. 连续访问更容易形成合并访存, 频繁调用 `contiguous()` 却会引入真实的数据搬运和峰值显存. **size 描述逻辑形状, stride 描述寻址规则, storage 才是实际字节; 三者必须一起检查.** 后续 Attention 的转置、head 拆分和 batch 矩阵乘法都依赖这套表示.

## 2. 再估算计算量

### 2.1 矩阵乘法与 MFU

对形状为 $(B,D)$ 与 $(D,K)$ 的矩阵乘法, 结果形状为 $(B,K)$, 乘加合计约 $2BDK$ FLOPs. 高维 PyTorch Tensor 的批量矩阵乘法仍可按相应 batch 与 sequence 维度展开计算. 语言模型的大部分训练 FLOPs 来自这些稠密矩阵乘法, 逐元素操作的 FLOPs 较少, 但可能受内存带宽或 kernel 启动开销限制.

硬件规格给出某种 dtype 和计算模式下的理论峰值, 实际训练吞吐需要用 MFU 衡量. MFU 的分子是根据模型结构估算的一步有效 FLOPs 除以实际用时, 分母是硬件峰值 FLOPs/s. 较低 MFU 可能来自小矩阵、数据加载等待、通信、频繁的数据布局转换或未融合的逐元素算子. MFU 只描述模型计算对峰值的利用程度, 不能替代端到端 token/s、显存占用和收敛质量.

主讲义还引入 `einops` 与维度命名. 命名 batch、sequence、head 和 hidden 维度不会自动提高速度, 却能减少 `transpose(-2,-1)` 一类位置索引造成的 shape 错误. 资源估算中的每个维度都应能对应到代码中的轴, 否则 FLOPs 公式与实现可能计算的不是同一个操作.

### 2.2 前向、反向与 6N 法则

[Gradients and Backward Pass](./2.3-Gradients-and-Backward-Pass/2.3-Gradients-and-Backward-Pass.md)从线性层拆解反向传播成本. 对矩阵乘法 $Y=XW$, 前向计算 $Y$ 需要一次矩阵乘法; 反向阶段计算输入梯度与权重梯度各需要一次相关矩阵乘法. 在以稠密线性层为主的近似下, 反向 FLOPs 约为前向的两倍.

若模型有 $P$ 个主要参与矩阵乘法的参数, 处理 $T$ 个训练 token, 前向成本常近似为 $2PT$, 前向加反向约为 $6PT$. 这就是课程进行训练周期估算时使用的 6N 关系, 其中文献常把参数量与 token 数的符号另行定义. 该估算忽略 Attention 中与序列长度有关的部分、embedding、归一化、激活函数、优化器更新和通信, 适合数量级预算, 不能替代实际 profile.

反向传播还带来激活存储. autograd 需要保留计算梯度所需的中间量, 因此训练显存并非权重、梯度和优化器状态的简单常数倍. activation checkpointing 可以减少保存的激活, 代价是在反向阶段重新执行部分前向计算. 这一交换关系需要同时记录节省的字节与增加的 FLOPs.

## 3. 参数更新为何需要额外状态

### 3.1 从 SGD 到 Adam

[Optimizers](./2.5-Optimizers/2.5-Optimizers.md)沿状态数量比较常见方法. SGD 直接用当前梯度更新参数, 不为每个参数保存额外统计量. Momentum 保存梯度的一阶移动平均, 用历史方向平滑更新. AdaGrad 累积梯度平方, 为不同参数调整有效步长, 但累计量单调增长可能使后期步长过小. RMSProp 改用梯度平方的指数移动平均, 降低久远梯度的影响.

Adam 同时保存一阶矩 $m$ 与二阶矩 $v$, 还包含初始化阶段的偏差修正. 若两份状态采用 FP32, 每个参数仅优化器状态就需要 8 字节. 再加参数、梯度和可能存在的 FP32 主权重, Adam 类训练的常驻内存会明显超过推理权重. 优化器选择因此既是收敛问题, 也是容量和通信问题.

比较优化器时还要锁定学习率计划、权重衰减、batch 规模与训练 token 数. 状态更多不等于必然收敛更好, 状态更少也不表示端到端成本一定更低. **优化器把过去梯度压缩成每参数状态; 所需字节数可以精确核算, 收敛收益则必须在同一训练设置中测量.**

### 3.2 混合精度分配不同职责

[Mixed Precision Training](./2.4-Mixed-Precision-Training/2.4-Mixed-Precision-Training.md)把低精度计算与高精度累计组合起来. 矩阵乘法使用 FP16 或 BF16 可以利用 Tensor Core 并减少带宽, 参数更新和长期状态则可保留 FP32. autocast 根据算子特性选择 dtype, 并不意味着把整个模型一次性、永久转换成同一种格式.

FP16 的小指数范围会使梯度下溢. loss scaling 先把损失乘以尺度 $S$, 反向所得梯度也随之放大; 更新前检查 `inf` 或 `NaN`, 再除以 $S$ 恢复梯度尺度. 动态缩放会在连续稳定后增大 $S$, 溢出时减小 $S$ 并跳过无效更新. BF16 与 FP32 具有相同的指数位数, 通常不需要为下溢执行同样的 loss scaling, 但较短尾数仍会带来舍入误差.

混合精度的验收不能止于“代码能跑”. 应记录实际 dtype、是否保留主权重、优化器状态 dtype、溢出次数、峰值显存、step time 和损失曲线. 若低精度节省的权重或激活空间被隐式副本抵消, 或训练频繁跳步, 名义上的位宽下降并没有转化为有效吞吐.

## 4. 因果 Attention 放进同一训练步

### 4.1 掩码约束信息依赖

[因果注意力](./2.7-因果注意力/2.7-因果注意力.md)解释自回归训练的可见性约束. 对长度为 $S$ 的序列, $QK^T$ 产生形状为 $(S,S)$ 的 score 矩阵. 第 $i$ 行对应位置 $i$ 发出的查询, 第 $j$ 列对应位置 $j$ 的键. 训练 next-token prediction 时, 位置 $i$ 只能使用自身及此前位置, 所以 $j>i$ 的 score 必须在 softmax 前被屏蔽.

实现通常把非法位置填为负无穷或 dtype 可表示的足够小数值, softmax 后这些位置权重为 0. 直接在 softmax 后乘 0 会破坏剩余权重的归一化, 因此掩码介入位置不能随意移动. 使用上三角还是下三角还取决于布尔值代表“保留”还是“屏蔽”, 以及具体 API 的约定; 判断实现正确性的标准是最终每一行的可见列集合.

因果掩码同样影响资源消耗.朴素 score 与权重张量随 $S^2$ 增长,长序列会显著增加计算和激活显存.高效 Attention kernel 可能不物化完整矩阵,但逻辑上的因果约束仍相同.**掩码规定谁能读取谁,dtype 和 kernel 决定这项约束以什么数值与资源成本执行.**

### 4.2 一次更新的完整顺序

把各子文合并起来, 一次训练更新从 token ID 张量开始. embedding 查表得到激活; Transformer 中的线性层和 Attention 执行矩阵运算; 因果掩码限制 Attention 可见范围; 输出 logits 与目标 token 计算交叉熵; autograd 沿计算图生成梯度; 混合精度路径检查并恢复梯度尺度; 优化器读取梯度与历史状态更新主权重; 下一步开始前再按需要清空梯度.

这条顺序同时对应五类检查. shape 检查每个轴的语义, layout 检查 view、stride 与副本, dtype 检查动态范围和累计精度, memory 检查常驻状态与峰值激活, compute 检查理论 FLOPs、实测耗时和 MFU. 只要能为一次更新逐项回答这五类问题, 后续扩展到多 GPU、kernel 融合和 activation checkpointing 时就有稳定参照.

## 5. 阅读次序

准备从代码入手时, 先读[主讲义](./2.1-主讲义/2.1-主讲义.md), 按内存核算、算力核算、梯度与训练循环建立全景. 遇到 dtype 与容量问题, 转入[Floating Point Representations](./2.2-Floating-Point-Representations/2.2-Floating-Point-Representations.md)和[Mixed Precision Training](./2.4-Mixed-Precision-Training/2.4-Mixed-Precision-Training.md); 遇到转置、`view()` 或隐式副本, 查阅[PyTorch Tensors](./2.6-PyTorch-Tensors/2.6-PyTorch-Tensors.md).

若目标是估算训练成本, 可依次阅读[Gradients and Backward Pass](./2.3-Gradients-and-Backward-Pass/2.3-Gradients-and-Backward-Pass.md)、[Optimizers](./2.5-Optimizers/2.5-Optimizers.md)和混合精度部分, 分别补齐 FLOPs、常驻状态与 dtype 分配. 实现 Transformer 的 Attention 时再进入[因果注意力](./2.7-因果注意力/2.7-因果注意力.md), 用具体 score 矩阵验证 mask 方向. 完成这一讲后, 读者应能先用参数量、token 数、dtype 与硬件峰值给出数量级预算, 再通过 PyTorch 的 shape、stride、显存统计和 profiler 修正估算.

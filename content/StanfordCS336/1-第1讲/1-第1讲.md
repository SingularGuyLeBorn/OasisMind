# 第1讲: 从训练目标到文本表示

语言模型工程常从 Transformer 结构开始讲, CS336 的起点却更早: 在写模型代码之前, 先确定系统究竟接收什么数据、优化什么目标、用什么指标判断训练是否有效, 以及有限算力允许多大的实验. 这些约束会共同决定后续实现. Tokenizer 改变序列长度和词表大小, 序列长度影响训练计算与显存, 训练目标决定每个位置提供多少监督信号, PPL 又依赖相同的 token 定义才能比较. 任意拆开其中一项, 都容易得到局部正确却无法端到端成立的方案.

第一讲因此承担两层任务. 第一层是建立课程的尺度观: 研究目标不是复刻最昂贵的前沿训练, 而是在明确的计算和数据预算内完成一条可运行、可测量、可改进的训练链路. 第二层是规定语言模型最初的接口: 原始字符串怎样变成 token ID, next-token prediction 怎样产生损失, 验证损失怎样转换成 PPL, 以及 MTP 怎样增加预测位置而不破坏因果关系. **这四项共同定义了后面各讲所处理的对象: token 是计算单位, 损失是优化信号, PPL 是同一表示体系内的验证读数, 预算决定实现边界.**

## 1. 从零构建的约束

### 1.1 规模变化会改变问题结构

[主讲义](./1.1-主讲义/1.1-主讲义.md)先解释课程为什么坚持从零实现. 调用现成 API 可以验证应用想法, 但无法暴露数据处理、数值表示、优化器状态、通信和硬件利用率之间的相互约束. 当研究问题涉及训练效率或模型机制时, 这些被封装的细节恰好是实验变量. 从零构建并不要求重写每个底层 kernel, 而是要求读者能够指出每一份数据如何进入模型、每一项状态为何存在、每一步计算消耗多少资源.

小模型实验还需要谨慎外推. 随着参数规模增大, MLP、Attention 与输出层占总 FLOPs 的比例会变化; 一项在小模型上显著的优化, 到更大规模可能只覆盖很小的成本. 能力指标也可能随训练计算量呈现非线性变化. 课程把“机制”“规模化思维”和经验直觉分开: 机制可以通过实现验证, 资源关系可以通过测量建立, 经验结论则必须标明适用规模和数据分布. **尺度不是实验报告末尾补充的背景, 而是决定结论能否迁移的条件.**

### 1.2 效率同时约束模型、数据和系统

课程的核心问题可以写成一个受约束的优化任务: 给定训练数据、GPU 数量和运行时间, 找到验证性能更好的模型与训练配置. 模型架构只占决策的一部分. Tokenizer 决定同一语料会产生多少 token; batch size 与序列长度决定一次更新处理多少 token; 实现质量决定硬件理论算力中有多少真正用于模型计算; 数据筛选决定有限 token 预算承载什么内容.

主讲义给出的五条课程主线由此连在一起. 基础模块建立 Tokenizer、Transformer、优化器与训练循环; 系统部分减少数据搬运并组织多 GPU 计算; Scaling Laws 用小规模实验拟合资源与性能的关系; 数据部分处理网页抽取、过滤、去重和评估; 对齐部分再用 SFT、偏好数据及相关优化方法改变模型行为. 第一讲不用提前展开全部算法, 但需要形成一个前提: 后续任何改动都要说明它改变了哪类资源、哪段数据流和哪个质量指标.

## 2. Tokenizer 定义模型看到的序列

### 2.1 字符串到 token ID

模型接收的是整数索引, Tokenizer 负责字符串与 token ID 序列之间的可逆转换. [Tokenizer](./1.3-Tokenizer/1.3-Tokenizer.md)从这条接口展开 BPE. 纯字符或纯字节方案拥有封闭、可逆的基础符号集, 但通常生成更长序列; 纯词级方案序列较短, 却会产生巨大的词表和未登录词问题. BPE 从字节序列出发, 反复合并语料中高频的相邻 token 对, 在固定词表预算内缩短常见片段的表示.

BPE 包含训练和编码两个不同过程. 训练阶段统计相邻 token 对, 选择最高频项并记录合并规则, 直到词表达到目标大小. 编码阶段不能重新统计输入文本, 而是按已学习规则的优先次序执行合并. 最终 token ID 只是词表索引, 数值大小没有语义. 真正影响模型的是切分边界、序列长度、词表规模, 以及 embedding 与输出头为这些 ID 学到的向量和分数.

### 2.2 Tokenizer 会改变整条训练链

同一段文本采用不同 Tokenizer 时, token 数量可能不同. 对固定上下文窗口而言, token 数量决定一次能覆盖多少原始文本; 对固定 token 预算而言, 它决定实际读入多少字符或字节. 词表变大通常能缩短序列, 同时扩大 embedding 和输出投影矩阵. 因此词表大小与序列长度之间没有脱离模型和语料的单一最优值.

空格和 Unicode 字节也属于输入信息. 某些 Tokenizer 把前导空格并入后续 token, 同一个可见词在句首和句中可能对应不同 token. 字节级基础词表保证任意字符串都能编码, 但不保证切分具有语言学意义. **Tokenizer 首先是一套压缩并离散化文本的工程协议; 它会影响成本与统计口径, 却不直接保证模型理解了词法结构.**

## 3. 训练目标与验证读数

### 3.1 Next-token prediction 与 MTP

标准自回归训练在位置 $i$ 使用此前 token 预测 $t_{i+1}$. 每个位置产生一项交叉熵, 对有效位置求平均得到主损失. 因果掩码保证当前位置不能读取未来 token, 因而训练时虽然能并行计算整段序列, 每个预测仍遵守生成时的信息边界. 后续模型结构、数据加载和训练循环最终都要服务于这项目标.

[MTP](./1.2-MTP/1.2-MTP.md)把监督扩展到多个后续 token. 文中的 DeepSeek-V3 方案使用顺序 MTP module, 第 $k$ 个模块结合前一层表示与偏移后的目标 token embedding, 再预测更远的 token. 各模块损失求平均并乘系数 $\lambda$, 作为主损失之外的训练项. 共享 embedding 和输出头控制额外参数, 独立 Transformer 模块承担不同预测深度的表征变换.

MTP 增加了同一训练序列提供的监督信号, 但额外模块也带来计算、显存和损失权重选择. “预测更多 token”不能直接推出生成质量必然提高; 收益取决于辅助目标是否改善主干表示, 以及额外开销是否值得. 阅读 MTP 时应追踪四个对象: 第 $k$ 层读入什么, 预测哪个位置, 哪些参数共享, 辅助损失如何进入总目标.

### 3.2 PPL 的含义和比较条件

[如何理解 PPL](./1.4-如何理解PPL/1.4-如何理解PPL.md)连接训练损失与验证指标. 若验证集上每个 token 的平均负对数似然为 $L$, 则 $PPL=\exp(L)$. 因而在相同数据、Tokenizer 和归一化方式下, PPL 与交叉熵严格同向. PPL 可以解释成与当前不确定性相当的有效候选规模, 但这个解释来自几何平均概率, 不能理解成模型真的只在固定数量的词之间选择.

比较 PPL 必须锁定统计单位. Tokenizer 改变 token 边界与序列长度, 即使两个模型处理相同字符串, token 级平均损失也可能落在不同尺度. 验证数据的领域变化同样会显著改变数值. PPL 适合监控同一训练配置的学习进度, 或比较共享 Tokenizer 与验证集的实验; 它不能单独衡量事实正确性、指令遵循、安全性和长程一致性.

训练目标和评估目标也要分开. next-token prediction 优化局部条件概率, 较低 PPL 说明模型更好地拟合验证 token 分布. 对齐后的模型还需要任务基准和人类偏好评估. **PPL 是预训练链路中口径严格的读数, 不是跨 Tokenizer、跨数据分布和跨能力维度的通用排名.**

## 4. 阅读路径与后续依赖

第一次阅读可先进入[主讲义](./1.1-主讲义/1.1-主讲义.md), 建立课程的预算约束、五条主线与 BPE 选择过程; 随后阅读[Tokenizer](./1.3-Tokenizer/1.3-Tokenizer.md), 把字符串、字节、合并规则和 token ID 的关系落实到算法步骤; 再用[如何理解 PPL](./1.4-如何理解PPL/1.4-如何理解PPL.md)检查训练损失如何变成验证读数. [MTP](./1.2-MTP/1.2-MTP.md)适合在理解标准 next-token prediction 后阅读, 重点比较辅助预测层与主模型之间的数据依赖.

时间有限时, 可沿“表示—目标—指标”读取 Tokenizer、主讲义中的训练目标、PPL 三部分. 准备实现课程作业时, 则需要从主讲义开始完整阅读, 因为第一项作业的 Tokenizer、现代 Transformer 组件、AdamW、学习率调度与训练循环必须作为同一系统验收. 第一讲之后, 第二讲会把 token 序列放进 PyTorch 张量, 进一步核算 dtype、显存、矩阵乘法、反向传播和优化器状态. 这里定义的序列长度、词表与损失口径, 都会直接进入下一讲的资源计算.

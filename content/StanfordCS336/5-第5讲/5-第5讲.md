# 第5讲: GPU 架构与性能优化

模型 FLOPs 相同, 运行时间仍可能相差数倍. 原因在于 GPU 不只执行算术指令: kernel 要调度线程, 数据要从 HBM 经过 cache 和共享内存进入寄存器, warp 中的线程还必须尽量沿一致控制流运行. 当算子需要的计算少而数据搬运多时, Tensor Core 的峰值算力不会成为限制, HBM 带宽和 kernel 启动反而决定吞吐. 第五讲把第二讲的资源核算继续下沉到硬件执行过程, 目标是解释优化为什么有效, 而不是罗列 CUDA 技巧.

[主讲义](./5.1-主讲义/5.1-主讲义.md)从 CPU/GPU 差异、执行单元与内存层级建立全景, 再依次讨论控制流分歧、低精度、算子融合、重计算、合并访存和 Tiling. [GPU Execution Model](./5.3-GPU-Execution-Model/5.3-GPU-Execution-Model.md)与[GPU Memory Hierarchy](./5.4-GPU-Memory-Hierarchy/5.4-GPU-Memory-Hierarchy.md)提供两个基础坐标; [Tiling for Performance](./5.6-Tiling-for-Performance/5.6-Tiling-for-Performance.md)把数据复用量化; [FlashAttention](./5.2-Flash-Attention-Explained/5.2-Flash-Attention-Explained.md)则把 Tiling、融合、在线 softmax 和重计算合成完整算法.

## 1. 执行模型决定并行方式

### 1.1 Thread、warp 与 block

GPU kernel 启动大量 thread. thread 被组织为 block, block 分配到 Streaming Multiprocessor, block 内 thread 可通过共享内存协作. 硬件以 warp 为调度单位, 同一 warp 的线程在同一时刻执行同一指令. [GPU Execution Model](./5.3-GPU-Execution-Model/5.3-GPU-Execution-Model.md)解释这三层关系: thread 负责一个或少量输出元素, block 划定协作与同步范围, warp 决定实际指令发射粒度.

并行度不等于 thread 越多越好. 每个 block 使用的寄存器和共享内存会限制同一 SM 可驻留的 block 数, 进而影响 occupancy. thread 工作过少会使启动和索引成本突出, 工作过多又可能产生寄存器压力. 映射方案要同时考虑输出 shape、数据复用和硬件资源.

### 1.2 分支与异步执行

同一 warp 内线程走不同分支时, 硬件通常要分别执行各条路径并屏蔽不参与的线程, 形成 control divergence. 分支本身并非一律低效; 真正的问题是 warp 内路径不一致以及每条路径的工作量. 边界判断常不可避免, 但应尽量让相邻 thread 处理相似条件.

CPU 提交 GPU kernel 通常是异步的. 过早读取结果、调用同步 API 或在循环中执行 `.item()` 会迫使 CPU 等待 GPU. 性能测量必须使用 GPU event 或显式同步包围目标区间, 否则得到的可能只是 kernel 提交时间. **GPU 优化首先要确认测量覆盖了真实执行, 再分析 kernel 内部.**

## 2. 内存层级与算术强度

### 2.1 数据离计算单元越近, 容量越小

[GPU Memory Hierarchy](./5.4-GPU-Memory-Hierarchy/5.4-GPU-Memory-Hierarchy.md)依次讨论寄存器、L1/共享内存、L2 与全局内存. 寄存器由单个 thread 使用, 延迟低但数量有限; 共享内存由 block 显式协作, 适合保存会被多次使用的 tile; L2 为全设备共享 cache; HBM 容量最大, 带宽虽高, 相对计算单元仍是远端资源.

带宽与延迟要分开. 足够多的并发访存可以隐藏单次访问延迟, 但无法突破总带宽. 合并访存让相邻 thread 访问相邻地址, 减少内存事务. 不规则 stride、转置布局和散乱索引会放大实际传输字节. 第三讲中的 Tensor stride 到这里转化成物理吞吐问题.

### 2.2 Roofline 与算术强度

算术强度是 FLOPs 与从主要内存层级搬运字节数的比值. 强度低时性能上限约为带宽乘算术强度, 算子 memory-bound; 强度足够高后才接近计算峰值, 算子 compute-bound. 降低 dtype 同时减少字节并可能提高 Tensor Core 峰值, 但实际收益取决于瓶颈在哪一侧.

算子融合减少中间张量写回 HBM. 例如线性层后的 bias 与激活若拆成多个 kernel, 中间结果会反复读写; 融合后可在寄存器或片上内存中继续处理. 重计算采用另一种交换: 不保存某些前向中间量, 反向时重新计算, 用 FLOPs 换显存和带宽. **优化目标不是最少 FLOPs, 而是缩短受限资源上的关键路径.**

## 3. Tiling 把全局访存变成片上复用

### 3.1 矩阵乘法的复用

[Tiling for Performance](./5.6-Tiling-for-Performance/5.6-Tiling-for-Performance.md)用矩阵乘法说明朴素实现的问题. 若每个输出元素独立从 HBM 读取整行与整列, 同一输入元素会被许多 thread 重复加载. Tiling 把输出矩阵划成 block, 协作加载对应的 $A$ 与 $B$ tile 到共享内存, block 内多个 thread 反复使用这些数据并累积局部结果.

tile 大小决定复用量, 也消耗共享内存和寄存器. 太小无法充分复用, 太大可能降低 occupancy, 还要处理矩阵边界、bank conflict 与同步. 因而 Tiling 是带硬件约束的参数选择, 不是固定尺寸的代码模式. 主讲义中的量化示例应结合“每个 HBM 元素支持多少次乘加”阅读.

### 3.2 FlashAttention 的组合设计

[FlashAttention](./5.2-Flash-Attention-Explained/5.2-Flash-Attention-Explained.md)面对标准 Attention 的 $S\times S$ score 与概率矩阵. 直接实现会将大矩阵写入 HBM, softmax 再读写多次. FlashAttention 按 Query 和 KV 分块, 在片上计算局部 score, 立即完成 softmax 更新与 Value 聚合, 避免物化完整中间矩阵.

softmax 需要全行最大值与归一化和, 分块后通过在线 softmax 维护运行最大值和指数和. 新 block 到来时, 旧累积量按最大值变化重新缩放, 从而得到与整体 softmax 等价的结果. 反向阶段不保存全部 score, 而从保存的统计量与输入重计算局部块. Tiling、融合、数值稳定归约和重计算缺一不可.

FlashAttention 没有改变 Attention 的数学定义. 它改变数据在 HBM 与片上存储之间的流动顺序, 用更多局部计算换取更少全局读写. 这也是判断“精确 Attention”与近似稀疏 Attention 的边界.

## 4. 阅读与实践路线

先读[主讲义](./5.1-主讲义/5.1-主讲义.md), 再并行阅读[执行模型](./5.3-GPU-Execution-Model/5.3-GPU-Execution-Model.md)和[内存层级](./5.4-GPU-Memory-Hierarchy/5.4-GPU-Memory-Hierarchy.md). 能用 thread/block/warp 描述工作映射, 并能列出输入在各级内存的生命周期后, 进入[Tiling](./5.6-Tiling-for-Performance/5.6-Tiling-for-Performance.md)做访存量计算, 最后阅读[FlashAttention](./5.2-Flash-Attention-Explained/5.2-Flash-Attention-Explained.md).

[GPU 学习资源](./5.5-GPU学习资源/5.5-GPU学习资源.md)适合在需要补 CUDA、性能分析或 TPU 背景时查阅. 实践中应按“正确性测试—可靠 benchmark—profile 定位—单项优化—再次 profile”循环, 同时记录输入 shape、dtype、硬件和 warm-up. 第六讲会在这些概念之上手写 CUDA 与 Triton kernel, 因此本讲的直接产出应是能预测一个 kernel 受计算、带宽、分支还是同步限制.

分析一个具体算子时, 先把逻辑 shape 映射到 thread 和 block. 例如矩阵乘法 $[M,K]@[K,N]$ 的输出是 $[M,N]$, 一个二维 thread block 通常负责一个输出 tile, 每轮从两个输入矩阵加载 $K$ 维的一段. 随后计算每个 tile 从 HBM 读取多少字节、在共享内存复用多少次、每个 thread 累积多少输出. 这三项能解释 tile 尺寸为何同时受带宽、共享内存和寄存器限制.

性能上限还需与输入规模一起看. 小矩阵可能由 launch latency 主导, 增加 occupancy 也无法消除固定启动成本; 大矩阵更容易达到稳态带宽或 Tensor Core 峰值; 长序列 Attention 则因中间矩阵和归约逐渐暴露 HBM 压力. 因而 benchmark 应画出 shape 曲线, 不能只报告一个尺寸. FlashAttention 的收益也应分别按 batch、head 数、序列长度和 head dimension 测量.

数值正确性是性能模型的一部分. 在线 softmax 必须维护运行最大值和指数和, 新 tile 到来时重新缩放旧累积量;低精度输入还可能用更高精度累积. 边界 tile 要 mask 越界元素, 但不能让 padding 参与最大值或归一化. 只有结果、梯度和极端 logits 均通过对照, I/O 改写才算保持原算法语义.

最终记录还应包含峰值显存和临时 buffer. 有些 kernel 缩短运行时间却增加工作区, 在大 batch 或并发执行时可能降低整体容量. 因而单算子最快配置不一定是完整训练步的最佳配置, 必须回到端到端 profile 验证.

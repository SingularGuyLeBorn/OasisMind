# 第6讲: 手写与分析高性能 Kernel

理解 GPU 层级之后, 仍需把张量公式映射成具体 kernel. 同一个 GeLU 可以由 PyTorch 的多个逐元素 kernel、CUDA C++ 扩展、Triton 程序或 `torch.compile` 生成的融合代码执行; 数学结果相同, 启动次数、访存量、索引方式和生成指令却不同. 第六讲关注这段落差: 怎样写出正确的 device 程序, 怎样选择 block 大小和数据布局, 怎样用 benchmark 与 profiler 区分有效优化和测量误差.

[主讲义](./6.1-主讲义/6.1-主讲义.md)从算术强度和 profiling 开始, 依次比较 CUDA C++、Triton 与编译器路径. [CUDA GeLU](./6.3-Code-CUDA-GeLU/6.3-Code-CUDA-GeLU.md)展示 host wrapper、全局 thread 索引和 device code; [Triton GeLU](./6.4-Code-Triton-GeLU/6.4-Code-Triton-GeLU.md)把同一逐元素运算改写成 block program; [Triton Softmax](./6.5-Code-Triton-Softmax/6.5-Code-Triton-Softmax.md)进一步处理跨列归约; [CPU–GPU Asynchronicity](./6.2-CPU-GPU-Asynchronicity/6.2-CPU-GPU-Asynchronicity.md)规定可靠计时的前提.

## 1. 性能工作从测量开始

### 1.1 Benchmark 与 profile 分工

benchmark 回答端到端耗时和吞吐, profile 回答时间消耗在哪里. GPU 异步执行使普通 CPU 时钟容易只测到 launch. [CPU–GPU Asynchronicity](./6.2-CPU-GPU-Asynchronicity/6.2-CPU-GPU-Asynchronicity.md)通过 Nsight 时间线展示 CPU 提交 kernel 后继续运行, 直到结果回传或显式同步才等待 GPU. 正确 benchmark 需要 warm-up、重复运行、GPU event 或同步边界, 并报告统计分布.

profile 时应观察 kernel 数量、持续时间、空闲间隙、内存吞吐、occupancy 和 host-device 同步. 一个融合 kernel 单次更长并不表示退化, 若它替代多个 kernel 并消除中间读写, 总时间可能更短. 反之, 自定义 kernel 若产生寄存器溢出或不合并访存, 减少 launch 也未必更快.

### 1.2 正确性先于速度

自定义实现要与参考 PyTorch 结果对照, 覆盖不同 shape、非整 block 边界、dtype 与非连续输入策略. 浮点误差容限应依据 dtype 设定. backward 若自定义, 还要做梯度对照. 性能数字只在语义等价、输入相同和同步口径一致时可比较.

**优化闭环是先建立可信基线, 再由 profile 提出瓶颈假设, 最后用新测量验证.** 跳过其中一步, 容易把 cache 热身、异步 launch 或精度变化误判为 kernel 收益.

## 2. CUDA 与 Triton 的映射方式

### 2.1 CUDA GeLU: thread 级索引

[CUDA GeLU](./6.3-Code-CUDA-GeLU/6.3-Code-CUDA-GeLU.md)包含 host 端扩展封装与 device kernel. 常见逐元素映射让每个 thread 处理一个元素, 全局索引由 block index、block dimension 和 thread index 合成. thread 数超过元素数时用边界判断屏蔽越界访问. 输入与输出相邻元素由相邻 thread 访问, 可形成合并访存.

CUDA C++ 允许直接控制 launch 配置、共享内存和底层 intrinsic, 也需要处理编译扩展、设备检查、dtype dispatch 和错误报告. 查看 PTX 能确认高层表达式是否生成预期指令, 但 PTX 条数不能单独预测耗时; 最终性能还受调度、内存和机器码影响.

### 2.2 Triton GeLU: block program

[Triton GeLU](./6.4-Code-Triton-GeLU/6.4-Code-Triton-GeLU.md)以 program instance 为单位处理一段连续 offset. `program_id` 选择数据块, 向量化 offset 生成一组地址, mask 处理尾部. 编译器再把 block program 映射到 GPU thread. 这种表达保留了显式数据分块, 同时省去大量 CUDA wrapper 与逐 thread 代码.

GeLU 是 memory-bound 逐元素算子, 单独重写的上限通常受读写字节限制. 真正显著的收益常来自与前后算子融合, 让输入只读一次、结果只写一次. Triton 代码仍需选择 block size 与 warp 数; 更高层语法不会自动保证最优配置.

## 3. Softmax 暴露归约难点

### 3.1 一行一 block

[Triton Softmax](./6.5-Code-Triton-Softmax/6.5-Code-Triton-Softmax.md)通常让一个 program 处理矩阵一行. program 加载整行, 对越界列填负无穷, 求最大值, 计算指数, 求和并归一化, 最后写回. 行内元素需要协作归约, 因而比 GeLU 的独立逐元素计算更依赖 block 大小和片上资源.

稳定 softmax 先减行最大值. 这不是可省略的额外步骤: 原始 logits 较大时直接指数会溢出. mask 值也必须与归约语义一致, padding 列填 0 会参与概率分配, 填负无穷才能在指数后贡献 0.

### 3.2 资源与 shape 边界

为了让一行装入 block, 实现可能把列数上取整到 2 的幂. 很长的行会增加寄存器和共享资源压力, 甚至需要改成分块在线 softmax. 行很短时, 一行一 block 又可能并行度不足. 所以示例 kernel 展示的是适用区间内的策略, 不是任意 shape 的通用最优解.

与 PyTorch 比较时还要考虑其 fused 或专用 kernel. 自定义版本超过朴素 Python 组合并不代表超过成熟库实现. 应分别比较 eager、`torch.compile`、Triton 与 CUDA 基线, 并报告形状曲线而非单一点.

## 4. 融合、编译器与技术选择

### 4.1 融合减少中间流量

主讲义中的 MLP 示例揭示 kernel fusion 的主要收益. 线性层、bias、激活与后续逐元素操作若分开发射, 中间激活多次经过 HBM. 融合把可组合操作放进一个 kernel, 在寄存器中继续计算. 但大型矩阵乘法通常调用高度优化库, 融合范围要服从寄存器、共享内存和编译复杂度.

重计算也是 kernel 设计的一部分. backward 可以保存前向输入或输出, 也可以重新计算激活. 保存减少 FLOPs, 增加内存流量; 重计算相反. 选择取决于算子的计算强度和训练显存压力.

### 4.2 CUDA、Triton 与 torch.compile

CUDA 适合需要底层控制、成熟库接口或 Triton 难以表达的复杂通信与硬件特性. Triton 适合规则张量程序、融合和快速探索, 让作者直接描述 block 级加载、计算与存储. `torch.compile` 适合从现有 PyTorch 图自动融合和生成代码, 开发成本最低, 但结果受图捕获、shape 和编译器能力影响.

技术选择应从性能缺口出发. 若 `torch.compile` 已接近带宽或计算上限, 手写 kernel 的维护成本可能没有回报; 若 profile 显示特定布局、归约或融合无法被编译器处理, Triton 或 CUDA 才有明确目标. **自定义 kernel 的价值来自消除已测得的瓶颈, 不是代码更接近硬件本身.**

## 5. 阅读路线

先读[主讲义](./6.1-主讲义/6.1-主讲义.md)和[异步执行](./6.2-CPU-GPU-Asynchronicity/6.2-CPU-GPU-Asynchronicity.md), 建立测量规范. 接着用[CUDA GeLU](./6.3-Code-CUDA-GeLU/6.3-Code-CUDA-GeLU.md)理解 thread 索引、wrapper 与编译链, 再用[Triton GeLU](./6.4-Code-Triton-GeLU/6.4-Code-Triton-GeLU.md)对照 block program. 最后进入[Triton Softmax](./6.5-Code-Triton-Softmax/6.5-Code-Triton-Softmax.md), 处理归约、mask 与长行资源限制.

完成本讲后, 应能为一个候选算子写出输入输出 shape、读写字节、理论 FLOPs、可能的瓶颈和验证方法. 下一讲进入多 GPU 并行, kernel 内的片上数据移动将扩展为设备之间的 collective communication; 测量、重叠与瓶颈分析方法仍然沿用.

从 GeLU 到 softmax 给出一条逐级实现路线. GeLU 的每个输出只依赖同位置输入, 可以用一维 offset 直接映射; softmax 的输出 $y_{ij}$ 依赖同一行全部 $x_{ik}$, 需要行内最大值和求和两次归约;矩阵乘法进一步让每个输出依赖整个 $K$ 维, 需要二维 Tiling 和跨轮累积. 依赖范围扩大时, thread 间协作和片上状态也随之增加.

Triton 的 block size 通常取不小于列数的 2 的幂, mask 屏蔽多出的 lane. 这一策略让归约规整, 但长行会推高寄存器用量并降低驻留 program 数. CUDA 版本同样要在 threads per block、每 thread 元素数和共享内存之间选择. 参数不应凭习惯固定, 而应在目标 shape 与硬件上 autotune, 并保留资源使用上限.

生产 wrapper 还需规定非连续 Tensor、当前 stream、device 和 dtype. 若 kernel 只支持 contiguous 输入, 应显式检查;若支持 stride, 地址计算必须使用真实步长. 首次编译、autotune 与稳态执行也要分开计时. 一个稳态很快却每种动态 shape 都重新编译的实现, 端到端服务未必更快.

正确性测试至少覆盖尾块、极小和极大值、不同 dtype、随机 shape 以及 backward 对照. profile 则检查实际内存吞吐、occupancy、寄存器溢出和 kernel 间空洞. **自定义 kernel 的完成条件是语义覆盖和性能区间都明确, 不是某个尺寸超过 eager 基线.**

还要保留失败回退路径. 不支持的 shape 或 dtype 应交给成熟库实现, 并让调用方能够识别实际走了哪条路径. 这样性能回归才能定位到编译、调度或 kernel 本身.
